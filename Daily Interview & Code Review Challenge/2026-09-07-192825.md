# Code Review Challenge 1 — Direct upload lên Azure Blob Storage chạy nhanh nhưng mở rộng quyền quá mức và tạo lỗ hổng isolation

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Blob Storage, SAS, Managed Identity, authorization, file-upload security, multi-tenant isolation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 11–14 vấn đề

## Bối cảnh

Một enterprise document platform chạy ASP.NET Core .NET 8 trên Azure App Service. Hệ thống có nhiều tenant và cho phép user upload tài liệu lớn trực tiếp từ browser lên Azure Blob Storage để tránh proxy toàn bộ file qua backend.

Yêu cầu nghiệp vụ:

- mỗi user chỉ được upload vào tenant của mình;
- file tối đa 500 MB;
- browser được phép upload trực tiếp vào Blob Storage;
- backend phải tạo một upload session trước khi cấp quyền upload;
- mỗi session chỉ dành cho một object cụ thể;
- upload link phải hết hạn nhanh;
- sau upload, backend sẽ chạy malware scanning và metadata extraction;
- file chưa scan không được phép download công khai;
- production chạy nhiều App Service instances;
- storage account dùng Microsoft Entra ID / Managed Identity cho backend;
- team muốn tránh lưu storage account key trong application configuration.

Production/security review gần đây phát hiện:

- một user có thể thay đổi `tenantId` trong request và nhận upload URL cho tenant khác;
- SAS đang cấp quyền ở cấp container và thời hạn 24 giờ;
- SAS URI bị log đầy đủ trong Application Insights;
- frontend có thể tự chọn blob name và content type;
- có các blob tên như `invoice.pdf.exe`, `../../x`, tên Unicode khó đọc và tên trùng nhau;
- một số file đã upload nhưng database không có record tương ứng;
- một số record database ở trạng thái `Uploaded` nhưng blob không tồn tại do client abort;
- backend tin `Content-Type` do browser gửi;
- team đề xuất bật public access cho container `uploads` để simplify download testing.

Implementation hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/uploads")]
[Authorize]
public sealed class UploadsController : ControllerBase
{
    private readonly BlobServiceClient _blobServiceClient;
    private readonly AppDbContext _db;
    private readonly ILogger<UploadsController> _logger;

    public UploadsController(
        BlobServiceClient blobServiceClient,
        AppDbContext db,
        ILogger<UploadsController> logger)
    {
        _blobServiceClient = blobServiceClient;
        _db = db;
        _logger = logger;
    }

    [HttpPost("create")]
    public async Task<IActionResult> CreateUpload(
        [FromBody] CreateUploadRequest request,
        CancellationToken cancellationToken)
    {
        var container = _blobServiceClient
            .GetBlobContainerClient("uploads");

        var blobName = $"{request.TenantId}/{request.FileName}";
        var blob = container.GetBlobClient(blobName);

        var sas = new BlobSasBuilder
        {
            BlobContainerName = container.Name,
            Resource = "c",
            StartsOn = DateTimeOffset.UtcNow.AddMinutes(-5),
            ExpiresOn = DateTimeOffset.UtcNow.AddHours(24)
        };

        sas.SetPermissions(
            BlobContainerSasPermissions.Read |
            BlobContainerSasPermissions.Write |
            BlobContainerSasPermissions.Create |
            BlobContainerSasPermissions.Delete |
            BlobContainerSasPermissions.List);

        var sasUri = container.GenerateSasUri(sas);

        var upload = new UploadRecord
        {
            Id = Guid.NewGuid(),
            TenantId = request.TenantId,
            FileName = request.FileName,
            BlobName = blobName,
            ContentType = request.ContentType,
            Status = "Uploaded",
            CreatedUtc = DateTime.UtcNow
        };

        _db.Uploads.Add(upload);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Created upload {UploadId} for {TenantId}. Sas={SasUri}",
            upload.Id,
            request.TenantId,
            sasUri);

        return Ok(new
        {
            upload.Id,
            uploadUrl = sasUri,
            blobName
        });
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review implementation như một Senior .NET Developer/Technical Lead chịu trách nhiệm security và production reliability.

Bạn cần:

1. xác định authorization và multi-tenant isolation problems;
2. phân tích SAS scope và permission hiện tại;
3. đánh giá việc dùng container-level SAS thay vì blob-level SAS;
4. đánh giá thời hạn SAS và revocation implications;
5. phân tích secret leakage qua logs;
6. đánh giá filename/blob-name trust boundary;
7. phân tích `Content-Type`, extension và file-signature assumptions;
8. tìm consistency gap giữa database và Blob Storage;
9. thiết kế upload state machine và post-upload verification;
10. giải thích khi nào direct-to-Blob upload hợp lý hơn backend proxy;
11. đề xuất Managed Identity / user delegation SAS approach;
12. giải thích testing và production telemetry cần có.

## Câu hỏi gợi mở

1. `[Authorize]` có chứng minh `request.TenantId` thuộc về caller không?
2. Nếu SAS có `Resource = "c"` và quyền `List/Delete`, browser được phép làm nhiều hơn việc upload một blob cụ thể ở mức nào?
3. SAS URI có được xem như secret/bearer capability không?
4. Khi backend tạo record `Status = "Uploaded"` trước khi browser thực sự upload, trạng thái đó có phản ánh sự thật không?
5. Nếu client abort giữa upload hoặc upload blob khác với `blobName` mà backend dự kiến, hệ thống phát hiện thế nào?

## Kết quả code review tham khảo

### Critical — Broken tenant authorization qua `request.TenantId`

**Vấn đề:**  
Backend dùng `request.TenantId` trực tiếp để tạo blob path và database record nhưng không chứng minh caller có quyền trên tenant đó.

**Tại sao xảy ra:**  
Authentication bị nhầm với resource authorization. `[Authorize]` chỉ cho biết caller đã authenticated; nó không tự xác nhận arbitrary tenant identifier do client gửi.

**Ảnh hưởng production:**  
User hợp lệ có thể yêu cầu upload capability cho tenant khác và ghi dữ liệu vào namespace không thuộc quyền sở hữu của mình.

**Cách sửa:**  
Resolve tenant từ trusted current-user/current-tenant context hoặc kiểm tra resource authorization trước khi tạo upload session. Không chấp nhận tenant ownership chỉ từ request body.

---

### Critical — Container-level SAS cấp capability rộng hơn requirement

**Vấn đề:**  
SAS được tạo cho container (`Resource = "c"`) và cấp `Read`, `Write`, `Create`, `Delete`, `List`.

**Tại sao xảy ra:**  
Capability được thiết kế theo storage convenience thay vì theo business operation “upload đúng một object”.

**Ảnh hưởng production:**  
Nếu SAS bị lộ hoặc bị caller lạm dụng, quyền có thể mở rộng ra nhiều blobs trong container thay vì một object cụ thể, tùy chính xác loại SAS và permissions đã cấp.

**Cách sửa:**  
Ưu tiên blob-scoped SAS cho exact blob name và chỉ permission cần cho upload. Không cấp `List`, `Delete` hoặc `Read` nếu upload flow không cần. Principle of least privilege phải được áp dụng cả về resource scope lẫn permission set.

---

### Critical — SAS URI bị ghi đầy đủ vào logs

**Vấn đề:**  
Structured log chứa toàn bộ SAS URI.

**Tại sao xảy ra:**  
SAS bị xem như ordinary URL trong khi nó là một bearer capability có quyền truy cập storage trong thời gian hiệu lực.

**Ảnh hưởng production:**  
Bất kỳ người hoặc hệ thống nào đọc log trong thời gian SAS còn hiệu lực có thể reuse capability trong phạm vi quyền của token. Log export, support access hoặc downstream telemetry có thể mở rộng blast radius.

**Cách sửa:**  
Không log SAS query string/token. Log `UploadId`, blob path đã sanitize, expiry timestamp, permission profile và correlation ID. Nếu cần diagnostic URL, log URI không có credential query.

---

### High — SAS tồn tại quá lâu và quyền quá rộng

**Vấn đề:**  
Token có hiệu lực 24 giờ cho một thao tác upload ngắn.

**Tại sao xảy ra:**  
Expiry không bám vào expected upload duration và risk model.

**Ảnh hưởng production:**  
Token bị leak có cửa sổ lạm dụng lớn hơn cần thiết. Với một số loại SAS, revocation không đơn giản như thu hồi một application session tùy cách token được ký và policy được dùng.

**Cách sửa:**  
Dùng expiry đủ ngắn cho kích thước/network profile thực tế, ví dụ vài phút đến khoảng thời gian có bounded margin. Nếu file 500 MB trên mạng chậm, cần đo upload duration trước khi chọn TTL. Capability renewal nên là explicit authenticated action.

---

### High — Storage credential strategy không phù hợp yêu cầu tránh account key

**Vấn đề:**  
`GenerateSasUri` trên client chỉ hoạt động khi client có credential có khả năng ký SAS theo cách phù hợp; design hiện tại không cho thấy rõ backend đang dùng account key hay user delegation flow.

**Tại sao xảy ra:**  
Team muốn Managed Identity nhưng code đang giả định có signing capability ở client abstraction mà không mô tả identity boundary.

**Ảnh hưởng production:**  
Application có thể vô tình quay lại lưu account key trong configuration hoặc cấp quyền rộng cho identity.

**Cách sửa:**  
Với Azure Blob Storage, ưu tiên Microsoft Entra credentials cho backend. Khi client cần SAS, user delegation SAS là lựa chọn phù hợp khi có thể: backend dùng Managed Identity để xin user delegation key theo RBAC phù hợp, sau đó tạo SAS giới hạn resource, permission và thời gian. Không cấp RBAC rộng hơn cần thiết.

---

### High — Blob name do client kiểm soát và trộn display name với storage identity

**Vấn đề:**  
`request.FileName` đi thẳng vào blob name.

**Tại sao xảy ra:**  
Tên user-facing được dùng làm physical object identity.

**Ảnh hưởng production:**  
Có thể gây collision, khó normalization Unicode, path-like names, overwrite semantics ngoài ý muốn và coupling giữa display name với storage lifecycle. Các chuỗi như `../` không nên được coi là security path traversal theo filesystem semantics vì Blob Storage object names không phải local filesystem paths, nhưng vẫn có thể tạo namespace khó kiểm soát và bug khi các layer khác diễn giải tên như path.

**Cách sửa:**  
Sinh storage identity ở server, ví dụ `tenant/{tenantId}/uploads/{UploadId}` hoặc random object key. Giữ original filename như metadata sau khi validate/sanitize cho display/download header.

---

### High — Record được đánh dấu `Uploaded` trước khi upload thực sự hoàn tất

**Vấn đề:**  
Database ghi `Status = "Uploaded"` ngay trong API tạo session.

**Tại sao xảy ra:**  
Intent creation bị nhầm với successful blob write.

**Ảnh hưởng production:**  
Database có thể nói file đã upload trong khi client chưa bắt đầu, abort hoặc SAS hết hạn.

**Cách sửa:**  
Dùng state machine rõ ràng, ví dụ:

```text
PendingUpload
  -> UploadedUnverified
  -> Scanning
  -> Ready
  -> Rejected
  -> Expired
  -> Failed
```

API tạo session chỉ commit `PendingUpload`. Một complete/verify endpoint hoặc event-driven process kiểm tra blob existence, expected key, size và metadata trước khi chuyển trạng thái.

---

### High — Không có protocol để reconcile orphan blob và orphan database record

**Vấn đề:**  
Upload trực tiếp tạo một distributed consistency gap giữa database và Blob Storage.

**Tại sao xảy ra:**  
Browser write vào storage nằm ngoài database transaction.

**Ảnh hưởng production:**  
Có thể có:

- record mà không có blob;
- blob mà không có record hoàn tất;
- session hết hạn nhưng blob tồn tại một phần hoặc đã upload xong;
- retry tạo nhiều blobs.

**Cách sửa:**  
Thiết kế reconciliation. Mỗi blob key phải gắn với `UploadId`. Session hết hạn cần cleanup policy. Complete/verify endpoint phải idempotent. Có scheduled reconciliation cho stale `PendingUpload` và orphan blobs theo prefix/metadata nếu operationally cần.

---

### High — Tin `Content-Type` do browser gửi

**Vấn đề:**  
Backend lưu `request.ContentType` và client tự đặt `Content-Type` khi upload.

**Tại sao xảy ra:**  
Metadata do client cung cấp bị xem như bằng chứng file type.

**Ảnh hưởng production:**  
Attacker có thể upload executable/script content với misleading MIME type hoặc extension. Nếu sau này nội dung được serve inline, rủi ro XSS/content-sniffing hoặc file execution trong downstream tooling tăng.

**Cách sửa:**  
Không tin extension/MIME đơn lẻ. Validate allowed extensions theo business policy, kiểm tra file signature/magic bytes khi phù hợp, malware scan, và khi download set safe `Content-Disposition`/`Content-Type` theo verified metadata. Untrusted uploads không nên được public-serve trực tiếp.

---

### High — Không enforce kích thước và expected object properties ở upload session

**Vấn đề:**  
Scenario yêu cầu tối đa 500 MB nhưng API không persist hoặc verify expected size.

**Tại sao xảy ra:**  
Direct upload bypass backend request body validation.

**Ảnh hưởng production:**  
Client có thể upload object lớn hơn policy, làm tăng storage cost và scanning workload.

**Cách sửa:**  
Persist expected size từ authenticated session request và verify actual blob properties sau upload. Nếu cần hard enforcement trước upload, đánh giá protocol/storage feature phù hợp; không giả định SAS tự encode arbitrary application file-size policy.

---

### Medium — Không có overwrite/idempotency rule rõ ràng

**Vấn đề:**  
Blob key dựa vào filename; cùng tên có thể collide.

**Tại sao xảy ra:**  
Storage key không chứa upload identity.

**Ảnh hưởng production:**  
Retry hoặc hai users cùng filename có thể ghi đè object nếu permission/HTTP condition cho phép.

**Cách sửa:**  
Dùng unique server-generated key. Nếu protocol yêu cầu create-only semantics, dùng conditional request phù hợp hoặc kiểm tra state theo upload ID thay vì filename.

---

### Medium — Đề xuất public container phá vỡ security boundary

**Vấn đề:**  
Team muốn bật public access cho `uploads` để test download.

**Tại sao xảy ra:**  
Operational convenience được ưu tiên hơn lifecycle `untrusted -> scanned -> ready`.

**Ảnh hưởng production:**  
Unscanned/private tenant data có thể bị truy cập ngoài application authorization boundary.

**Cách sửa:**  
Giữ container private. Download phải đi qua authenticated authorization hoặc cấp short-lived read SAS sau khi record ở trạng thái `Ready`. Có thể tách quarantine/private upload container khỏi serving container nếu lifecycle phức tạp.

---

### Medium — Telemetry không đủ để chứng minh upload lifecycle

**Vấn đề:**  
Log hiện tại ghi secret nhưng lại thiếu các business transitions quan trọng.

**Tại sao xảy ra:**  
Telemetry tập trung vào URL thay vì workflow identity.

**Ảnh hưởng production:**  
Khó điều tra session nào expired, blob nào orphan, scan nào fail hoặc tenant nào đang tạo upload bất thường.

**Cách sửa:**  
Dùng structured telemetry với `UploadId`, tenant, expected size, actual size, state transition, blob existence, scan result, duration, failure category và trace/correlation ID. Không log SAS token hoặc sensitive document content.

## Phiên bản đề xuất

Ví dụ sau minh họa một API tạo upload session với server-generated blob key. Chi tiết cấp user delegation SAS phụ thuộc exact Azure SDK version và RBAC configuration; implementation production cần đối chiếu SDK/documentation hiện hành và không hard-code permissions rộng.

```csharp
[ApiController]
[Route("api/uploads")]
[Authorize]
public sealed class UploadsController : ControllerBase
{
    private readonly BlobServiceClient _blobServiceClient;
    private readonly AppDbContext _db;
    private readonly ICurrentTenant _currentTenant;
    private readonly IUserDelegationSasFactory _sasFactory;
    private readonly ILogger<UploadsController> _logger;

    public UploadsController(
        BlobServiceClient blobServiceClient,
        AppDbContext db,
        ICurrentTenant currentTenant,
        IUserDelegationSasFactory sasFactory,
        ILogger<UploadsController> logger)
    {
        _blobServiceClient = blobServiceClient;
        _db = db;
        _currentTenant = currentTenant;
        _sasFactory = sasFactory;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> CreateUpload(
        CreateUploadRequest request,
        CancellationToken cancellationToken)
    {
        if (request.SizeBytes <= 0 ||
            request.SizeBytes > 500L * 1024 * 1024)
        {
            return BadRequest("Invalid file size.");
        }

        var originalFileName = Path.GetFileName(request.FileName);

        if (!AllowedExtension(originalFileName))
        {
            return BadRequest("File type is not allowed.");
        }

        var uploadId = Guid.NewGuid();
        var tenantId = _currentTenant.Id;
        var blobName = $"{tenantId}/pending/{uploadId:N}";

        var upload = new UploadRecord
        {
            Id = uploadId,
            TenantId = tenantId,
            OriginalFileName = originalFileName,
            BlobName = blobName,
            ExpectedSizeBytes = request.SizeBytes,
            ClientContentType = request.ContentType,
            Status = UploadStatus.PendingUpload,
            ExpiresUtc = DateTime.UtcNow.AddMinutes(20),
            CreatedUtc = DateTime.UtcNow
        };

        _db.Uploads.Add(upload);
        await _db.SaveChangesAsync(cancellationToken);

        var container = _blobServiceClient
            .GetBlobContainerClient("uploads-private");

        var blob = container.GetBlobClient(blobName);

        var expires = DateTimeOffset.UtcNow.AddMinutes(15);
        var uploadUri = await _sasFactory.CreateWriteOnlyBlobSasAsync(
            blob,
            expires,
            cancellationToken);

        _logger.LogInformation(
            "Created upload session {UploadId} for tenant {TenantId}. ExpiresUtc={ExpiresUtc} ExpectedBytes={ExpectedBytes}",
            uploadId,
            tenantId,
            expires,
            request.SizeBytes);

        return Accepted(new
        {
            uploadId,
            uploadUrl = uploadUri,
            expiresUtc = expires,
            completeUrl = Url.ActionLink(
                nameof(CompleteUpload),
                values: new { uploadId })
        });
    }

    [HttpPost("{uploadId:guid}/complete")]
    public async Task<IActionResult> CompleteUpload(
        Guid uploadId,
        CancellationToken cancellationToken)
    {
        var tenantId = _currentTenant.Id;

        var upload = await _db.Uploads
            .SingleOrDefaultAsync(
                x => x.Id == uploadId && x.TenantId == tenantId,
                cancellationToken);

        if (upload is null)
        {
            return NotFound();
        }

        if (upload.Status != UploadStatus.PendingUpload &&
            upload.Status != UploadStatus.UploadedUnverified)
        {
            return Conflict();
        }

        var blob = _blobServiceClient
            .GetBlobContainerClient("uploads-private")
            .GetBlobClient(upload.BlobName);

        if (!await blob.ExistsAsync(cancellationToken))
        {
            return Conflict("Blob has not been uploaded.");
        }

        var properties = await blob.GetPropertiesAsync(
            cancellationToken: cancellationToken);

        if (properties.Value.ContentLength != upload.ExpectedSizeBytes)
        {
            upload.Status = UploadStatus.Rejected;
            upload.FailureReason = "SizeMismatch";
            await _db.SaveChangesAsync(cancellationToken);
            return Conflict("Uploaded file does not match the session.");
        }

        upload.Status = UploadStatus.UploadedUnverified;
        upload.UploadedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        return Accepted(new
        {
            uploadId,
            status = upload.Status.ToString()
        });
    }

    private static bool AllowedExtension(string fileName)
    {
        var extension = Path.GetExtension(fileName);
        return extension.Equals(".pdf", StringComparison.OrdinalIgnoreCase) ||
               extension.Equals(".docx", StringComparison.OrdinalIgnoreCase);
    }
}
```

`IUserDelegationSasFactory` nên:

- authenticate backend bằng Microsoft Entra credentials/Managed Identity;
- tạo user delegation SAS khi phù hợp;
- scope đúng blob cụ thể;
- chỉ cấp quyền cần cho upload;
- đặt short expiry dựa trên expected upload duration;
- không trả SAS vào log;
- không cache/reuse một SAS cho nhiều upload sessions trừ khi requirement và security model chứng minh điều đó an toàn.

Sau `UploadedUnverified`, workflow scanning có thể chạy qua background worker/durable queue. Chỉ khi scan và validation thành công mới chuyển `Ready`.

## Giải thích thiết kế sau khi sửa

### 1. Tenant identity đến từ trusted context

Client không tự quyết định ownership boundary.

### 2. Storage key được server tạo

Original filename chỉ là metadata/display value. Upload ID trở thành stable object identity.

### 3. SAS là capability tối thiểu

Token được giới hạn theo exact resource, permission và duration cần thiết.

### 4. Upload thành công không được suy ra từ việc session được tạo

Backend verify blob properties và cập nhật state machine sau upload.

### 5. Untrusted file không trở thành downloadable content ngay lập tức

Scanning/verification là một lifecycle stage độc lập.

## Trade-offs

- Direct-to-Blob upload giảm bandwidth/memory pressure ở backend nhưng tăng distributed-workflow complexity.
- Backend proxy đơn giản hơn về authorization/validation nhưng có thể tăng compute, network và request-lifetime cost cho file lớn.
- User delegation SAS giảm phụ thuộc storage account key nhưng cần RBAC/identity setup đúng và thêm logic tạo delegation key/token.
- Short-lived SAS an toàn hơn nhưng mạng chậm có thể yêu cầu renewal flow.
- Tách quarantine/ready containers giúp security boundary rõ hơn nhưng tăng operational/storage lifecycle steps.

## Cách kiểm thử

1. **Authorization test:** user tenant A không thể tạo session hoặc complete upload thuộc tenant B.
2. **Security test:** SAS không có `List/Delete/Read` ngoài requirement và chỉ tác động exact blob key dự kiến.
3. **Failure-path test:** client abort trước upload, upload quá hạn, blob thiếu hoặc actual size khác expected; state phải reconcile đúng.
4. **Malware/file validation test:** extension/MIME giả, double extension và malicious test sample không được promote thành `Ready`.
5. **Concurrency/idempotency test:** complete endpoint gọi nhiều lần hoặc browser retry upload; state transition không tạo duplicate business record.

## Quan sát trong production

Theo dõi:

- upload sessions created/completed/expired;
- age của oldest `PendingUpload`;
- actual vs expected bytes;
- blob verification failure rate;
- scan latency/failure/rejection rate;
- orphan blob và orphan record count từ reconciliation;
- SAS issuance count và expiry profile, nhưng không log token;
- Azure Blob dependency duration/error/throttling telemetry;
- tenant-level upload volume;
- duplicate/retry rate;
- Application Insights trace correlation bằng `UploadId`;
- alert khi stale pending uploads hoặc scan backlog vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào backend proxy upload hợp lý hơn direct-to-Blob upload dù file lớn?
2. Nếu browser cần resume một upload 500 MB, bạn sẽ thay đổi upload protocol và session model thế nào?
3. Nếu requirement yêu cầu download link chia sẻ ra ngoài hệ thống trong 30 phút, bạn sẽ thiết kế authorization/SAS scope và revocation strategy thế nào?

### Critical — Secret production được commit plaintext trong manifest

**Vấn đề:**  
Database username/password nằm trực tiếp trong YAML.

**Tại sao xảy ra:**  
Configuration và secret material bị trộn vào deployment artifact.

**Ảnh hưởng production:**  
Credential xuất hiện trong Git history, code review, CI logs hoặc artifact copies. Rotation khó và blast radius lớn.

**Cách sửa:**  
Dùng Kubernetes Secret hoặc secret-store integration phù hợp với platform, và tốt hơn nữa dùng workload/service identity khi dependency hỗ trợ. Secret object bản thân không nên được coi là tự động “an toàn” nếu chỉ base64; cần encryption/access-control/secret-management practices của cluster. Rotate credential đã bị commit.

---

### Critical — Readiness probe kiểm tra nhầm liveness endpoint

**Vấn đề:**  
`readinessProbe` gọi `/health/live`.

**Tại sao xảy ra:**  
Process-alive semantics bị dùng thay cho traffic-ready semantics.

**Ảnh hưởng production:**  
Pod có thể được add làm backend cho Service chỉ vài giây sau process start dù warm-up cần 20–45 giây. Request thật vào pod chưa ready gây 5xx/timeout.

**Cách sửa:**  
Readiness phải gọi `/health/ready`, và endpoint này phải phản ánh “có thể nhận traffic” chứ không chỉ process sống.

---

### Critical — Liveness probe phụ thuộc readiness và có thể restart healthy process

**Vấn đề:**  
`livenessProbe` gọi `/health/ready` với failure threshold rất thấp.

**Tại sao xảy ra:**  
Readiness có thể fail do startup chưa xong hoặc dependency tạm thời degraded; liveness nên chủ yếu phát hiện process/application state không thể tự phục hồi nếu restart có ý nghĩa.

**Ảnh hưởng production:**  
Một transient SQL/pricing failure hoặc slow startup có thể kích hoạt container restart, khiến pod không bao giờ đủ thời gian warm-up và tạo cascading failure.

**Cách sửa:**  
Liveness gọi endpoint process-local như `/health/live`. Readiness xử lý traffic eligibility. Với startup chậm, dùng `startupProbe` để trì hoãn liveness/readiness behavior cho tới khi application thực sự khởi động theo policy.

### High — Không có `startupProbe` cho application startup 20–45 giây

**Vấn đề:**  
Liveness bắt đầu sau 3 giây.

**Tại sao xảy ra:**  
Manifest giả định startup gần như tức thời.

**Ảnh hưởng production:**  
Container có thể bị restart lặp lại trước khi startup hoàn tất.

**Cách sửa:**  
Dùng `startupProbe` với budget lớn hơn worst-case startup hợp lý. Khi startup probe được cấu hình, liveness/readiness probe không nên can thiệp trước khi startup probe thành công theo semantics Kubernetes hiện hành.

### High — Rolling update cho phép mất 50% capacity và không có surge

**Vấn đề:**  
Với 4 replicas, `maxUnavailable: 50%` cho phép một phần đáng kể pods không available trong rollout; `maxSurge: 0` không tạo capacity tạm thời.

**Tại sao xảy ra:**  
Rollout setting không dựa trên SLO/load headroom.

**Ảnh hưởng production:**  
Nếu normal traffic cần gần 4 pods, rollout có thể giảm serving capacity xuống mức không đủ, gây latency/5xx dù manifest vẫn đúng cú pháp.

**Cách sửa:**  
Chọn rollout values dựa trên headroom. Ví dụ `maxUnavailable: 0` và `maxSurge: 1` cho workload cần giữ full capacity, nếu cluster có đủ resource. Nếu cluster capacity hạn chế, có thể chọn trade-off khác nhưng phải load-test và định nghĩa availability target.

---

### High — CPU limit thấp hơn normal workload gây throttling

**Vấn đề:**  
Application thường dùng 300–500m nhưng CPU limit là 300m.

**Tại sao xảy ra:**  
Limit được chọn không dựa trên measured runtime profile.

**Ảnh hưởng production:**  
Linux cgroup CPU limit có thể throttle container khi chạm ceiling; latency tăng dù node còn CPU. Với burst cần khoảng 1 CPU, limit 300m triệt tiêu burst headroom.

**Cách sửa:**  
Đo CPU usage/p95/p99 và benchmark dưới production-like load. Set request phản ánh scheduler reservation cần thiết, limit theo platform policy và latency trade-off. Không mặc định “limit càng thấp càng an toàn”.

### High — CPU request quá thấp làm scheduler placement không phản ánh capacity thật

**Vấn đề:**  
Request chỉ 50m trong khi steady usage cao hơn nhiều.

**Tại sao xảy ra:**  
Scheduler dùng requests để quyết định placement/capacity accounting.

**Ảnh hưởng production:**  
Node có thể bị overpacked nếu nhiều workloads cũng under-request, dẫn tới contention dù mỗi manifest riêng lẻ trông tiết kiệm.

**Cách sửa:**  
Đặt request dựa trên measured baseline, có margin phù hợp và review cùng autoscaling/node capacity strategy.

---

### High — Memory limit thấp hơn observed peak dẫn tới OOM kill

**Vấn đề:**  
Memory limit 512 MiB trong khi observed range có thể 350–600 MiB và payload lớn còn cao hơn.

**Tại sao xảy ra:**  
Limit thấp hơn realistic peak.

**Ảnh hưởng production:**  
Container có thể bị OOMKilled khi vượt memory limit. Restart không sửa root cause nếu workload tiếp tục đòi memory tương tự.

**Cách sửa:**  
Profile managed heap, LOH, response buffering và peak RSS. Giảm allocation/buffering nếu có bug, đồng thời set request/limit phù hợp với measured workload. Theo dõi OOMKill/restart reason thay vì chỉ tăng replica.

---

### High — `terminationGracePeriodSeconds: 5` mâu thuẫn graceful shutdown 20 giây

**Vấn đề:**  
Pod chỉ được 5 giây trước khi termination có thể bị forceful theo lifecycle của container runtime.

**Tại sao xảy ra:**  
Deployment config không phản ánh application shutdown behavior.

**Ảnh hưởng production:**  
In-flight requests có thể bị cắt, background cleanup chưa hoàn tất và client nhận connection reset/5xx trong rollout.

**Cách sửa:**  
Set termination grace lớn hơn required shutdown budget có margin. Application phải handle termination signal, dừng nhận new work, readiness chuyển false sớm và hoàn tất in-flight work trong bounded time. Nếu cần `preStop`, hiểu rõ nó cũng tiêu tốn termination grace budget.

---

### High — Mutable image tag `latest` làm rollout không reproducible

**Vấn đề:**  
Deployment dùng `pricing-api:latest`.

**Tại sao xảy ra:**  
Release identity không pin vào immutable artifact.

**Ảnh hưởng production:**  
Khó chứng minh pod nào chạy binary nào; restart ở thời điểm khác có thể pull artifact khác nếu registry tag đã thay đổi, tùy pull policy/cache behavior.

**Cách sửa:**  
Pin image bằng immutable version/tag gắn build/commit và tốt nhất digest trong environment cần reproducibility. Telemetry phải expose build/commit identity.

---

### Medium — Probe thresholds quá nhạy cho workload có transient latency

**Vấn đề:**  
`periodSeconds` ngắn và `failureThreshold: 1` khiến một failure đơn lẻ thay đổi state/restart rất nhanh.

**Tại sao xảy ra:**  
Probe config tối ưu cho tốc độ phản ứng thay vì signal quality.

**Ảnh hưởng production:**  
Transient GC pause, network hiccup hoặc dependency jitter có thể gây churn.

**Cách sửa:**  
Tune timeout/period/failure threshold bằng startup/latency profile và desired failover time. Probe phải rẻ, deterministic và không tự tạo load đáng kể.

---

### Medium — Chỉ tăng replicas không giải quyết root cause

**Vấn đề:**  
Team muốn scale lên 20 pods ngay.

**Tại sao xảy ra:**  
Capacity symptom bị xử lý trước khi phân biệt CPU throttling, readiness bug, OOM và rollout configuration.

**Ảnh hưởng production:**  
Có thể tăng cost nhưng vẫn restart/throttle; thậm chí tăng downstream pressure lên SQL/pricing service.

**Cách sửa:**  
Đo resource throttling, restart reason, readiness transition, dependency saturation và load profile trước. Scale-out chỉ khi bottleneck thực sự parallelizable và downstream chịu được.

## Giải thích thiết kế sau khi sửa

### 1. Startup, readiness và liveness có semantics riêng

Startup probe cho application đủ thời gian khởi động; readiness quyết định traffic; liveness chỉ restart khi process/application thật sự ở trạng thái không nên tiếp tục sống.

### 2. Rollout giữ serving capacity

`maxUnavailable: 0` bảo vệ capacity tốt hơn trong scenario này, đổi lại cần cluster có headroom cho surge pod.

### 3. Resource config dựa trên measurement

Requests phản ánh scheduler reservation; limits là runtime ceiling. CPU ceiling quá thấp có thể throttle, memory limit quá thấp có thể dẫn tới OOM kill.

### 4. Shutdown là một phần của availability

Readiness và termination grace phải phối hợp với ASP.NET Core graceful shutdown để rollout không cắt request đang chạy.

### 5. Release artifact immutable

Image version/digest giúp rollback, RCA và deployment validation đáng tin cậy.

## Trade-offs

- `maxUnavailable: 0` + `maxSurge: 1` cần spare cluster capacity trong rollout.
- Resource request cao hơn có thể giảm bin-packing efficiency nhưng cải thiện scheduling predictability.
- CPU limit cao hơn giảm throttling nhưng cần quota/cost governance phù hợp.
- Startup probe budget quá dài có thể trì hoãn phát hiện pod thực sự bị kẹt; quá ngắn lại tạo restart loop.
- Readiness nếu check dependency quá sâu có thể loại toàn bộ pods khỏi traffic khi shared dependency fail, tạo outage nặng hơn; health design phải phân biệt dependency nào thực sự làm pod không thể serve request hữu ích.
- Kubernetes mang lại deployment/control primitives nhưng cũng tăng operational complexity; nếu App Service đã đáp ứng availability, scaling và deployment requirements với chi phí thấp hơn, không nên migrate chỉ vì Kubernetes phổ biến.

## Cách kiểm thử

1. **Deployment validation:** rollout 4 replicas dưới steady load; xác minh không giảm ready endpoints ngoài policy và 5xx không tăng bất thường.
2. **Startup test:** inject startup 45–60 giây; startup probe không restart pod trước budget, readiness không cho traffic sớm.
3. **Failure-path test:** làm pricing dependency fail tạm thời; verify readiness/liveness behavior đúng design và không tạo restart storm.
4. **Load/resource test:** đo CPU throttling, RSS, managed heap, GC, p95/p99 dưới normal/burst load; xác minh request/limit phù hợp.
5. **Graceful shutdown test:** terminate pod khi có in-flight requests; app dừng nhận traffic và hoàn tất request trong grace period hoặc fail theo bounded policy.

## Quan sát trong production

Theo dõi:

- desired/available/ready replicas;
- pod restart count và termination reason;
- OOMKilled events;
- readiness/liveness/startup probe failure count;
- rollout duration và unavailable replicas;
- CPU usage và CPU throttling;
- memory working set/RSS, managed heap và GC telemetry từ application;
- p50/p95/p99 latency và 5xx;
- node/namespace scheduling pressure;
- SQL/pricing dependency latency/error rate;
- termination/graceful-shutdown duration;
- image/build/commit identity;
- alert khi ready replicas dưới safe minimum, restart rate tăng hoặc throttling/OOM vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào readiness endpoint nên fail vì SQL Server unavailable, và khi nào việc đó có thể làm outage nặng hơn?
2. Nếu cluster không có headroom cho `maxSurge: 1`, bạn sẽ cân bằng rollout safety và resource capacity thế nào?
3. Với workload này, điều gì phải chứng minh trước khi chọn Kubernetes thay vì tiếp tục Azure App Service?

- Authentication không thay thế tenant/resource authorization.
- SAS phải được coi như bearer capability: scope hẹp, permission tối thiểu, expiry ngắn và không xuất hiện trong logs.
- Managed Identity/Microsoft Entra credentials giúp tránh storage account key; khi cần SAS cho Blob, user delegation SAS là một lựa chọn phù hợp cần được cấp RBAC đúng mức.
- Upload state phải phân biệt intent, object tồn tại, validation/scanning và ready-for-download.
- Trong Kubernetes, `Running`, `Ready` và `Alive` là các khái niệm khác nhau.
- Startup/readiness/liveness probe sai semantics có thể tự tạo cascading failure.
- CPU requests/limits và memory limits có operational behavior khác nhau; tuning phải dựa trên measurement.
- Rolling update và graceful shutdown là một phần của application availability, không chỉ platform configuration.

## Mẫu tư duy cần nhớ

1. **Least privilege phải áp dụng cả identity, resource scope, permission và lifetime.**
2. **Đừng biến một distributed workflow thành “transaction” chỉ vì các bước xảy ra gần nhau.**
3. **Phân biệt health signal theo mục đích: startup, traffic readiness và process liveness.**
4. **Measure before tuning resources; symptom như 5xx có thể đến từ throttling, OOM, readiness hoặc dependency failure.**
5. **Deployment configuration phải phản ánh runtime behavior thật của application, không phải các con số mặc định.**
