# Câu 1 — SQL Server: Keyset pagination và sự thật về thứ tự dữ liệu

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, query plan, isolation, API pagination, tính đúng đắn.

## Bối cảnh

Một API ASP.NET Core .NET 8 cung cấp danh sách giao dịch cho portal nội bộ. Bảng `Transactions` có 24 triệu hàng; mỗi ngày có thêm 200.000 giao dịch. Endpoint dùng EF Core:

```csharp
var page = await db.Transactions
    .AsNoTracking()
    .Where(x => x.TenantId == tenantId && x.Status == status)
    .OrderByDescending(x => x.CreatedAtUtc)
    .Skip((pageNumber - 1) * 50)
    .Take(50)
    .Select(x => new TransactionDto(x.Id, x.CreatedAtUtc, x.Amount))
    .ToListAsync(ct);
```

Trang đầu mất 45 ms, trang 8.000 có lúc mất 2,5 giây. Trong khi người dùng chuyển trang, giao dịch mới liên tục được thêm vào. Đôi khi một giao dịch xuất hiện ở hai trang, giao dịch khác không xuất hiện ở trang nào. `CreatedAtUtc` không unique. Business muốn giữ khả năng lọc theo `Status`, đi tiếp/trở lại và có thể nhảy đến trang N.

## Câu hỏi chính

Giải thích chính xác cơ chế khiến latency và tính nhất quán của pagination thay đổi theo trang; thiết kế phương án phù hợp, bao gồm giới hạn của giải pháp khi dữ liệu liên tục được ghi.

## Câu hỏi làm rõ nên cân nhắc

1. Người dùng thực sự cần nhảy đến trang N hay chỉ duyệt tuần tự và tải thêm?
2. Có yêu cầu snapshot nhất quán giữa các request hay chấp nhận danh sách live?
3. `TenantId`, `Status`, `CreatedAtUtc`, `Id` có kiểu dữ liệu và phân bố như thế nào?
4. Có bộ lọc hoặc sort khác và giới hạn độ trễ p95 nào?
5. Truy vấn có join, global query filter, hoặc `CountAsync` đi kèm không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt chi phí tìm điểm bắt đầu của trang với chi phí trả về 50 hàng.

### Gợi ý 2
Xem xét tính ổn định của `ORDER BY` khi nhiều bản ghi có cùng timestamp.

### Gợi ý 3
Một cursor gồm hai trường và điều kiện so sánh từ điển có thể giải quyết duyệt tuần tự; nhưng không tự tạo snapshot liên request.

## Cấu trúc trả lời đề xuất

1. Làm rõ UX và consistency.
2. Giải thích `OFFSET/FETCH` và thứ tự không unique.
3. Kiểm chứng bằng execution plan, logical reads và timing.
4. Thiết kế cursor, index, API contract.
5. Phân tích insert/update/delete giữa các request.
6. So sánh với offset và snapshot; xác định test và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
Nêu chi phí skip lớn; `ORDER BY CreatedAtUtc` không bảo đảm thứ tự duy nhất; inserts làm dịch vị trí offset; keyset với cặp `(CreatedAtUtc, Id)`; index phù hợp và kiểm tra plan.

### Điểm cộng
Xử lý cursor có chữ ký/validation, filter thay đổi, forward/backward, `CountAsync`, key immutability, tenant isolation.

### Senior+
Phân biệt stable ordering với snapshot consistency; đề xuất UX/contract và chiến lược đo lường trước khi chọn index.

## Hướng giải quyết tham khảo

**Cơ chế.** `Skip(n)` thường dịch thành SQL `OFFSET n ROWS FETCH NEXT ...`. SQL Server vẫn phải xác định thứ tự và đi qua hoặc xử lý lượng hàng bị bỏ qua; index phù hợp có thể giảm sort nhưng không khiến skip lớn thành hằng số. Nếu chỉ sort `CreatedAtUtc`, các hàng cùng timestamp không có thứ tự xác định; plan khác nhau có thể trả thứ tự khác nhau. Khi insert trước vị trí hiện tại, offset trang sau bị dịch, gây duplicate hoặc missing ngay cả khi thứ tự unique.

**Kiểm chứng.** Capture SQL qua EF Core logging có kiểm soát, actual execution plan trong môi trường phù hợp, `SET STATISTICS IO, TIME ON` trên bản sao dữ liệu, logical reads, sort spill, index seek/scan, p95 theo `pageNumber`. Đo riêng query count; tránh logging giá trị nhạy cảm. Kiểm tra index hiện có trước khi tạo index mới.

**Thiết kế.** Nếu UX chấp nhận next/previous, sắp xếp `CreatedAtUtc DESC, Id DESC`. Trang đầu lấy 51 hàng để biết `hasNext`. Trang kế tiếp dùng cursor chứa timestamp và Id cuối cùng:

```csharp
var query = db.Transactions.AsNoTracking()
    .Where(x => x.TenantId == tenantId && x.Status == status);
if (cursor is not null)
{
    var lastTime = cursor.CreatedAtUtc;
    var lastId = cursor.Id;
    query = query.Where(x =>
        x.CreatedAtUtc < lastTime ||
        (x.CreatedAtUtc == lastTime && x.Id.CompareTo(lastId) < 0));
}
var rows = await query
    .OrderByDescending(x => x.CreatedAtUtc)
    .ThenByDescending(x => x.Id)
    .Select(x => new TransactionDto(x.Id, x.CreatedAtUtc, x.Amount))
    .Take(51)
    .ToListAsync(ct);
```

Đoạn so sánh `CompareTo` chỉ mang tính minh họa: phải kiểm tra EF Core provider có dịch biểu thức đó sang SQL hay không; nếu `Id` là `long`, dùng trực tiếp `x.Id < lastId`. Với SQL Server, một ứng viên index cần benchmark là `(TenantId, Status, CreatedAtUtc DESC, Id DESC)` và `INCLUDE (Amount)`; cân nhắc write overhead, index size, selectivity, các bộ lọc khác. Cursor nên chứa filter/sort và có cơ chế chống sửa tùy yêu cầu bảo mật; luôn xác thực tenant từ server, không tin tenant trong cursor.

**Giới hạn.** Keyset giữ vị trí tương đối tốt khi có insert mới phía trước cursor, nhưng update sort key, delete, hoặc thay đổi Status có thể làm tập kết quả biến động. Không được hứa snapshot ổn định xuyên request. Nếu cần export/report nhất quán, cân nhắc tạo snapshot/materialized result hoặc phiên bản dữ liệu có vòng đời; giữ transaction snapshot dài xuyên nhiều HTTP request thường không phù hợp. Nếu bắt buộc nhảy trang bất kỳ, offset có thể được giữ cho UX này kèm giới hạn, cảnh báo latency, hoặc thiết kế search/navigation khác. Backward pagination cần đảo chiều predicate và ordering rồi đảo kết quả trả về.

**Testing:** Dữ liệu trùng timestamp; insert/delete giữa trang; tenant isolation; cursor không hợp lệ; load test trang sâu; plan với filter phổ biến và hiếm. **Monitoring:** p50/p95/p99 theo phương thức pagination, logical reads, SQL duration, CPU, spill, timeout, count query.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ hỏi trước liệu người dùng cần nhảy đến trang bất kỳ hay chỉ next/previous và có cần snapshot hay không. `OFFSET` ở trang sâu khiến SQL Server phải xử lý nhiều hàng trước khi trả 50 hàng; thêm nữa sort theo timestamp không unique và insert liên tục làm offset bị dịch. Tôi sẽ xác minh qua execution plan và logical reads thay vì thêm index ngay. Nếu duyệt tuần tự là chủ yếu, tôi chuyển sang keyset theo `CreatedAtUtc, Id` với index phù hợp và cursor gắn với filter. Cách này giảm chi phí duyệt sâu nhưng không bảo đảm snapshot khi trạng thái hoặc sort key thay đổi. Nếu nghiệp vụ đòi snapshot hoặc nhảy trang N, tôi sẽ thiết kế contract khác thay vì hứa keyset giải quyết tất cả. Tôi sẽ test concurrency, plan và p95 trước/sau.”

## Câu hỏi đào sâu

1. Khi `Status` thay đổi giữa hai lần gọi, cursor có thể bỏ sót hàng như thế nào?
2. Nếu Product bắt buộc nhảy trực tiếp trang 10.000, bạn đề xuất gì và chấp nhận trade-off nào?
3. Index bao phủ query giúp read nhưng có thể gây vấn đề gì cho write workload?

## Lỗi trả lời thường gặp

- Chỉ nói “thêm index” mà không đọc plan.
- Dùng `CreatedAtUtc` làm cursor duy nhất.
- Khẳng định keyset luôn bảo đảm snapshot.
- Bỏ qua `TenantId` và cursor tampering.
- Đánh đồng latency query với toàn bộ API response.

## Thang điểm 0–10

# Câu 2 — Azure App Service: lỗi xác thực chỉ xuất hiện sau scale-out

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core authentication, Data Protection, App Service, deployment, observability, incident response.

## Bối cảnh

Portal quản trị ASP.NET Core .NET 8 sử dụng cookie authentication sau đăng nhập qua Microsoft Entra ID. Khi App Service chạy một instance, hệ thống ổn định. Sau tăng từ 1 lên 4 instances và triển khai phiên bản mới bằng deployment slot, một nhóm người dùng gặp vòng lặp redirect về login, lỗi xác thực cookie hoặc bị đăng xuất không đều. Có request thành công, request kế tiếp thất bại. API dùng bearer token ở một số endpoint không gặp cùng triệu chứng. Một số log ghi `CryptographicException` trong quá trình xử lý authentication ticket, nhưng chưa rõ tỷ lệ và nguyên nhân. Không được tắt authorization để khôi phục dịch vụ.

## Câu hỏi chính

Bạn là người phụ trách incident: sẽ đánh giá ảnh hưởng, ổn định dịch vụ, chứng minh hoặc bác bỏ các giả thuyết nào, sửa như thế nào và triển khai an toàn ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. Cookie authentication hay OIDC nonce/correlation cookie nào thất bại; middleware nào phát lỗi?
2. Data Protection key ring hiện lưu ở đâu; application name, slot, instance có chia sẻ không?
3. Lỗi có tương quan với instance ID, slot swap, phiên bản app, domain hoặc cookie path không?
4. Có thay đổi secret, certificate, clock, SameSite, proxy headers hay encryption settings không?
5. Tỷ lệ login fail, user impact và rollback/scale-down có khả thi không?

## Gợi ý tư duy

### Gợi ý 1
Phân tách lỗi browser redirect, OIDC callback và giải mã authentication ticket.

### Gợi ý 2
Một cookie được bảo vệ bởi một instance phải được instance khác giải mã.

### Gợi ý 3
Kiểm tra key ring, application discriminator, key lifecycle và slot boundaries trước khi thay đổi authentication architecture.

## Cấu trúc trả lời đề xuất

1. Định lượng ảnh hưởng và phân loại auth failure.
2. Thực hiện biện pháp ổn định có thể rollback.
3. Liên kết request với instance, slot và deployment.
4. Đưa nhiều giả thuyết và phép kiểm chứng.
5. Sửa cấu hình/triển khai với bảo mật phù hợp.
6. Test scale-out, swap, rotation, rollback.
7. Theo dõi kết quả và làm postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không tắt security; hiểu ASP.NET Core Data Protection được dùng bảo vệ cookie; kiểm tra khả năng chia sẻ và tồn tại của key ring; không kết luận từ một exception; có incident mitigation và telemetry.

### Điểm cộng
Phân biệt slot isolation, application name, Managed Identity, Key Vault/Blob permissions, cookie domain, OIDC state và forward headers.

### Senior+
Thiết kế rollout/rollback với key compatibility, tránh xóa key cũ và xác định failure mode khi key store unavailable.

## Hướng giải quyết tham khảo

**Impact:** Dùng Application Insights đếm login challenge, callback failure, 302 loop, 401/403 theo user journey (không log cookie/token), correlation ID, instance, deployment version, slot. Ước lượng người dùng bị ảnh hưởng và thời điểm bắt đầu; mở incident, thông báo trạng thái.

**Stabilize:** Nếu có bằng chứng rõ regression sau swap, cân nhắc rollback slot hoặc quay lại phiên bản trước với kiểm tra key compatibility. Nếu giảm số instance giúp ổn định, có thể tạm scale down với đánh giá capacity và risk; không coi sticky sessions là giải pháp căn bản. Không xóa cookie hàng loạt hoặc rotate key tùy tiện; không disable authorization.

**Giả thuyết cạnh tranh:**
- Key ring khác nhau giữa instances hoặc slots: một instance mã hóa ticket, instance khác không giải mã được. Kiểm tra nơi lưu key, key IDs (không log key material), application name, deployment slot và instance correlation.
- Key ring có thể dùng chung nhưng application discriminator khác hoặc key bị xóa/revoked: đối chiếu config/version và key lifecycle.
- OIDC nonce/correlation cookie bị chặn do SameSite/Secure/domain/proxy scheme; lỗi sẽ xuất hiện ở callback và có đặc trưng khác với ticket decrypt failure.
- Cookie quá lớn/truncated bởi proxy/browser, lệch clock hoặc sai auth scheme; cần đối chiếu dấu hiệu thực tế.
- Dependency Key Vault/Blob unavailable hoặc identity không đủ quyền: quan sát dependency failures và key store access.

**Khắc phục có điều kiện:** Nếu nguyên nhân là key ring không ổn định, cấu hình ASP.NET Core Data Protection dùng shared persistent store phù hợp môi trường (ví dụ Azure Blob Storage) và bảo vệ key at rest theo security policy (có thể tích hợp Azure Key Vault), cùng `SetApplicationName` nhất quán cho các instances thực sự cần chia sẻ ticket. Cấp quyền tối thiểu qua Managed Identity; không dùng secret trong source. Cân nhắc việc production và staging slot có nên chia sẻ key ring: cùng key ring giúp tránh logout khi swap nhưng tăng phạm vi tin cậy; phân tách ứng dụng/tenant bằng cấu hình và quyền phù hợp. Đảm bảo các key cũ còn đọc được trong thời gian ticket hợp lệ, có chiến lược rotation và backup.

**Xác minh:** Integration/E2E test login, chuyển request qua nhiều instances, slot swap, restart, key rotation, dependency outage, rollback. Quan sát tỷ lệ decrypt failure, auth challenge loop, successful session continuity, p95 auth endpoints, store dependency health. Cảnh báo theo tỉ lệ lỗi và business SLO, không dựa chỉ vào số exception.

**Quyết định thay đổi:** Nếu lỗi thực tế do SameSite hoặc reverse proxy, sửa cookie/proxy settings thay vì triển khai shared key store vô cớ. Nếu portal chỉ dùng bearer token stateless, mô hình failure sẽ khác; cần xác định scheme thực tế.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi đây là sự cố authentication có ảnh hưởng người dùng và giữ nguyên authorization. Đầu tiên đo tỷ lệ lỗi theo instance, slot và deployment, xác định thất bại ở OIDC callback hay lúc giải mã authentication cookie. Scale-out và slot swap gợi ý Data Protection key ring hoặc application discriminator không nhất quán, nhưng tôi cũng kiểm tra SameSite, proxy headers, key-store permissions và rotation. Tôi ưu tiên rollback hoặc scale-down có kiểm soát nếu giảm tác động, sau đó xác minh bằng telemetry. Nếu đúng key ring, tôi thiết kế persistent shared key store với Managed Identity và quản lý key lifecycle; đồng thời cân nhắc ranh giới trust giữa slots. Trước rollout tôi sẽ test login qua nhiều instances, swap, restart, rollback và key-store outage. Thành công phải thể hiện bằng giảm login loops và tỷ lệ authentication failure, không chỉ hết exception.”

## Câu hỏi đào sâu

1. Vì sao bật ARR affinity có thể che triệu chứng mà không giải quyết nguyên nhân?
2. Nếu Azure Blob Storage chứa key ring tạm unavailable, hệ thống nên xử lý và monitor thế nào?
3. Khi chia sẻ key ring giữa staging và production, rủi ro bảo mật và vận hành nào cần cân nhắc?

## Lỗi trả lời thường gặp

- Tắt cookie validation hoặc authorization để chữa cháy.
- Kết luận chắc chắn do Data Protection mà không kiểm tra OIDC callback.
- Xóa key ring hoặc rotate key làm mọi session cũ mất hiệu lực.
- Không kiểm tra ảnh hưởng của slot swap và rollback.
- Ghi raw cookie, ID token hoặc access token vào log.

# Câu 3 — Thiết kế đồng bộ dữ liệu CRM sang nền tảng tìm kiếm khách hàng

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** PostgreSQL, Elasticsearch, Azure Service Bus, API boundaries, eventual consistency, privacy, reliability, cost of complexity.

## Bối cảnh

Một enterprise portal ASP.NET Core phục vụ đội kinh doanh. PostgreSQL là nguồn dữ liệu chính của hồ sơ khách hàng, thông tin liên hệ và trạng thái đồng ý nhận marketing. Product muốn tìm kiếm gần đúng theo tên/công ty, lọc theo khu vực, phân trang, hiển thị dữ liệu gần real-time. Hệ thống có khoảng 2 triệu khách hàng, trung bình 40 thay đổi/giây, có đợt import lớn. Mục tiêu ban đầu: thay đổi xuất hiện trong search trong 30 giây ở điều kiện bình thường; khi dependency lỗi phải có khả năng phục hồi. PII và quyền xem theo tổ chức là bắt buộc. Team có kinh nghiệm SQL, .NET, Azure Service Bus, Elasticsearch; chi phí vận hành hạn chế.

## Câu hỏi chính

Bạn chọn search trực tiếp PostgreSQL, bổ sung Elasticsearch, hay một thiết kế kết hợp? Hãy đề xuất kiến trúc end-to-end, data ownership, update/delete flow, consistency, authorization, recovery và cách chứng minh lựa chọn phù hợp.

## Câu hỏi làm rõ nên cân nhắc

1. Search là exact/prefix/fuzzy/full-text, ngôn ngữ nào, relevance cần tinh chỉnh không?
2. SLA 30 giây áp dụng p95 hay mọi update; delete và revoke consent có yêu cầu nghiêm ngặt hơn không?
3. Phân quyền theo tenant, organization hay từng record; quyền thay đổi thường xuyên không?
4. Các query phổ biến, concurrency, traffic burst, khả năng query PostgreSQL hiện tại?
5. Có yêu cầu audit, GDPR-like erasure, disaster recovery, và ngân sách vận hành cụ thể không?

## Gợi ý tư duy

### Gợi ý 1
Bắt đầu từ query patterns và data ownership, không từ công nghệ search.

### Gợi ý 2
Một DB transaction và một external index update không tự động atomic.

### Gợi ý 3
Phân biệt freshness SLA, privacy deletion SLA, permission enforcement và reconciliation.

## Cấu trúc trả lời đề xuất

## Hướng giải quyết tham khảo

**Lựa chọn.** Trước hết benchmark PostgreSQL với index, `pg_trgm` hoặc full-text search nếu query phù hợp; với traffic vừa phải, PostgreSQL có thể đủ và giảm đáng kể vận hành. Nếu relevance, autocomplete, analyzer, faceting và tải search độc lập vượt khả năng giải pháp SQL sau khi đo, thêm Elasticsearch làm **read model**; PostgreSQL vẫn là source of truth.

**Boundary:** `Customer` aggregate thuộc CRM service/module; SearchIndexer chỉ nhận projection tối thiểu cần thiết. API `GET /customers/search?q=&region=&cursor=` nhận identity từ authentication, kiểm tra authorization server-side. Không để client tự đặt tenant filter rồi coi đó là bảo mật. Với permission nhạy cảm, chỉ dùng search để lấy candidate IDs và xác nhận quyền + trạng thái hiện tại ở authoritative DB trước khi trả dữ liệu; nếu validation thất bại, fail closed. Tùy traffic, có thể kết hợp security filtering ở index nhưng phải thiết kế propagation/verification cho revoke.

**Write flow:** Trong cùng PostgreSQL transaction, cập nhật Customer và ghi Outbox event với `entityId`, `version`, `eventType`, `occurredAt`. Publisher đọc outbox, gửi Azure Service Bus, đánh dấu tiến độ theo cơ chế chịu retry; không giả định publish và DB commit là atomic. Consumer lấy dữ liệu authoritative hoặc payload projection được phép, cập nhật index idempotently. Dùng monotonic version và xử lý event đến trễ; không để update cũ ghi đè update mới. Delete/revoke cần tombstone/version và đường xử lý ưu tiên phù hợp policy. Trường hợp delete event trễ, lớp authorization ở read path vẫn phải ngăn lộ dữ liệu; cân nhắc không đưa PII không cần thiết vào index.

**Recovery:** Queue có retry/backoff, DLQ và công cụ replay; reconciliation quét các entity/version chênh lệch, kiểm tra outbox lag và index freshness. Bulk import dùng batch và throttling để tránh áp đảo cluster; reindex sang index mới, xác thực count/sample/queries rồi đổi alias có kế hoạch rollback. Không coi Elasticsearch index là backup của PostgreSQL. Với search unavailable, trả lỗi có kiểm soát hoặc fallback SQL giới hạn nếu đạt yêu cầu security và capacity; không tự động trả stale PII không kiểm tra quyền.

**Consistency:** 30 giây chỉ là target bình thường, cần đo distribution `indexedAt - committedAt`, xác định p95/p99, alert khi lag vượt threshold. Nếu requirement là read-your-writes, có thể trả authoritative record ngay sau update hoặc cho UI trạng thái “đang đồng bộ”, không hứa Elasticsearch strong consistency. Nếu revoke phải có hiệu lực tức thì, enforce ở DB/read path hoặc cơ chế denylist có tính tin cậy tương đương, không phụ thuộc chỉ vào asynchronous indexing.

**Operations:** Structured logs với `entityId` đã kiểm soát PII, `eventId`, `version`, `traceId`; metrics outbox age, queue depth, DLQ, consumer errors, index freshness, query p95, rejected authorization candidates. Alert theo SLO; phân quyền Managed Identity nơi hỗ trợ, secrets trong Key Vault, index access tối thiểu. Triển khai schema/event version backward-compatible trước, canary, feature flag search path, rollback không làm mất outbox.

**Trade-offs:** PostgreSQL-only đơn giản, transaction consistency rõ, nhưng relevance/faceting có giới hạn tùy workload. Elasticsearch tăng khả năng search và scale độc lập nhưng thêm consistency lag, indexing, cluster operations, chi phí và surface chứa PII. Service Bus tăng độ bền và decoupling nhưng đòi idempotency, DLQ, monitoring. Không cần microservices nếu modular monolith với outbox và worker là đủ.

**Testing:** Search relevance trên bộ dữ liệu đại diện; concurrency/out-of-order event; queue downtime và replay; delete/revoke authorization race; bulk reindex; load test query và ingest đồng thời; rollback schema/event. Điều kiện thay đổi quyết định: nếu benchmark SQL đạt SLA với ngân sách tốt, hoãn Elasticsearch; nếu strict transactional search visibility là bắt buộc, async index một mình không đáp ứng.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu từ query patterns, freshness và quyền truy cập, rồi benchmark PostgreSQL trước khi quyết định thêm Elasticsearch. Nếu fuzzy search và relevance thực sự cần engine chuyên biệt, tôi dùng PostgreSQL làm source of truth và Elasticsearch làm read projection. Tôi tránh dual-write bằng transactional outbox, publisher sang Service Bus và consumer idempotent theo version để chịu duplicate hoặc out-of-order. Điều quan trọng nhất là security: search index có thể stale, nên với quyền hoặc consent nhạy cảm tôi xác thực lại từ authoritative source trước khi trả PII. Tôi sẽ thiết kế DLQ, replay, reconciliation và reindex có alias, đo freshness p95/p99 cùng query latency. Nếu PostgreSQL đáp ứng tốt, tôi ưu tiên kiến trúc đơn giản hơn; nếu cần read-your-writes hay revoke tức thì, phải có đường đọc và kiểm quyền riêng thay vì kỳ vọng async search luôn nhất quán.”

## Câu hỏi đào sâu

1. Nếu update version 12 được index trước version 11, bạn chống stale overwrite thế nào?
2. Khi một khách hàng vừa bị thu hồi quyền xem nhưng index chưa cập nhật, làm sao bảo đảm không lộ PII?
3. Nếu chi phí Elasticsearch tăng gấp đôi trong khi SQL vẫn đáp ứng latency, bạn quyết định gì?

## Lỗi trả lời thường gặp

- Chọn Elasticsearch ngay mà không benchmark SQL.
- Ghi trực tiếp DB và index trong request rồi coi là atomic.
- Tin event ordering tuyệt đối hoặc exactly-once processing.
- Chỉ filter tenant ở client.
- Không có replay/reconciliation và privacy deletion plan.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- SQL pagination phải xét cả chi phí truy vấn, thứ tự deterministic và biến động dữ liệu giữa request; keyset không đồng nghĩa snapshot.
- ASP.NET Core cookie authentication phụ thuộc vào khả năng giải mã Data Protection ticket nhất quán; scale-out và slot swap làm lộ các cấu hình không ổn định, nhưng incident cần chứng cứ trước khi kết luận.
- Search architecture cần tách source of truth, read projection, event delivery, authorization và recovery. Eventual consistency là quyết định nghiệp vụ lẫn kỹ thuật.

## Mẫu tư duy cần nhớ

1. **Clarify before designing:** xác định UX, consistency và security contract.
2. **Measure before optimizing:** execution plan, p95/p99 và query patterns trước khi thêm công nghệ.
3. **Stabilize before deep investigation:** giảm tác động incident mà không hạ chuẩn bảo mật.
4. **Design retry together with idempotency:** duplicate và out-of-order là failure path phải test.
5. **Treat derived data as potentially stale:** quyền truy cập phải dựa trên nguồn có thẩm quyền.
