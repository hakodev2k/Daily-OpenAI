# Code Review Challenge 1 — Inventory reservation dưới flash sale

**Chủ đề:** C#/.NET 8, EF Core, SQL Server, concurrency, e-commerce
**Độ khó:** Senior+
**Thời gian review đề xuất:** 45 phút
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Một API checkout giữ hàng theo SKU và warehouse. Sáu Azure App Service instances dùng chung SQL Server. Trong flash sale, 100 request cùng giữ 10 sản phẩm; một số đơn bị giữ trùng khi client retry sau timeout. `StockItems` chứa `Sku, WarehouseId, Available`; `Reservations` chứa `OrderId, Sku, WarehouseId, Quantity`. Chưa xác minh unique constraints, isolation level, thời hạn reservation và quyền theo tenant.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/inventory")]
public sealed class InventoryController : ControllerBase
{
    private readonly ShopDbContext _db;
    private readonly IPartnerInventoryApi _partner;
    private readonly ILogger<InventoryController> _log;

    public InventoryController(ShopDbContext db,
        IPartnerInventoryApi partner, ILogger<InventoryController> log)
    {
        _db = db;
        _partner = partner;
        _log = log;
    }

    [HttpPost("reserve")]
    public async Task<IActionResult> Reserve(ReserveRequest request)
    {
        var stock = await _db.StockItems.SingleOrDefaultAsync(x =>
            x.Sku == request.Sku && x.WarehouseId == request.WarehouseId);

        if (stock is null) return NotFound();
        if (stock.Available < request.Quantity)
            return Conflict("Insufficient stock");

        stock.Available -= request.Quantity;
        _db.Reservations.Add(new Reservation
        {
            OrderId = request.OrderId,
            Sku = request.Sku,
            WarehouseId = request.WarehouseId,
            Quantity = request.Quantity,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();
        await _partner.NotifyReservedAsync(
            request.OrderId, request.Sku, request.Quantity);

        _log.LogInformation("Reserved {Sku} for {OrderId}",
            request.Sku, request.OrderId);
        return Ok(new { request.OrderId, stock.Available });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Lost update và oversell

**Vấn đề:** Read-check-write không atomic.
**Tại sao xảy ra:** Nhiều requests có thể cùng đọc giá trị cũ và ghi đè; không có concurrency token hay conditional update.
**Ảnh hưởng production:** Reservations vượt hàng thực có.
**Cách sửa:** Atomic conditional UPDATE với `Available >= quantity`, kiểm tra affected rows; hoặc rowversion + bounded retry.

### [Critical] — Duplicate reservations

**Vấn đề:** Retry sau ambiguous commit tạo reservation mới.
**Tại sao xảy ra:** Thiếu unique business key và idempotent response.
**Ảnh hưởng production:** Giữ hàng nhiều lần.
**Cách sửa:** Unique index theo reservation identity đã xác nhận từ business; trả kết quả cũ khi payload giống, conflict khi khác.

### [High] — External side effect không recover được

**Vấn đề:** Commit SQL xong mới gọi partner, nhưng lỗi partner khiến request báo failure.
**Tại sao xảy ra:** HTTP không nằm trong SQL transaction.
**Ảnh hưởng production:** Trạng thái hai hệ thống lệch; retry có thể lặp side effect.
**Cách sửa:** Transactional Outbox + dispatcher + stable idempotency key; reconciliation nếu partner không hỗ trợ.

### [High] — Không validate Quantity

**Vấn đề:** Quantity bằng 0, âm hoặc quá lớn được chấp nhận.
**Tại sao xảy ra:** Thiếu input/domain validation.
**Ảnh hưởng production:** Tồn kho có thể tăng hoặc dữ liệu sai.
**Cách sửa:** Positive bounds và CHECK constraints ở database.

### [High] — Thiếu authorization theo tenant/warehouse

**Vấn đề:** Controller không thể hiện ownership check.
**Tại sao xảy ra:** Tin vào identifiers do client gửi.
**Ảnh hưởng production:** Giữ hàng trái phép nếu không có kiểm tra ở tầng khác.
**Cách sửa:** Authentication + resource authorization server-side.

### [Medium] — Thiếu cancellation và timeout policy

**Vấn đề:** DB và partner không nhận CancellationToken.
**Tại sao xảy ra:** Không xác định lifecycle request/dependency.
**Ảnh hưởng production:** Connections bị chiếm lâu, timeout khó phân loại.
**Cách sửa:** Truyền RequestAborted cho request work; notification durable chạy riêng với timeout/backoff.

### [Medium] — Reservation không có expiry

**Vấn đề:** Không có expiration/cancel/release workflow.
**Tại sao xảy ra:** Thiếu lifecycle contract.
**Ảnh hưởng production:** Hàng bị giữ vô hạn.
**Cách sửa:** State machine, expiry worker idempotent, audit và reconciliation.

### [Low] — Telemetry thiếu context

**Vấn đề:** Log chỉ ghi thành công, không có outcome/latency/correlation.
**Tại sao xảy ra:** Thiếu observability design.
**Ảnh hưởng production:** Không phân biệt duplicate, lock contention và partner outage.
**Cách sửa:** Structured logs, traces, metrics và invariant audits.

## Phiên bản đề xuất

Giả định một reservation cho mỗi `(OrderId,Sku,WarehouseId)`, unique index và CHECK constraints đã được migration. Ví dụ service dưới dùng `ReserveResult` và `OutboxMessage.ForReservation` là domain types giả định.

```csharp
public async Task<ReserveResult> ReserveAsync(
    ReserveCommand cmd, CancellationToken ct)
{
    if (cmd.Quantity <= 0 || cmd.Quantity > 10000)
        return ReserveResult.Invalid();

    await using var tx = await _db.Database.BeginTransactionAsync(ct);
    var existing = await _db.Reservations.AsNoTracking()
        .SingleOrDefaultAsync(x => x.OrderId == cmd.OrderId
            && x.Sku == cmd.Sku && x.WarehouseId == cmd.WarehouseId, ct);

    if (existing is not null)
        return existing.Quantity == cmd.Quantity
            ? ReserveResult.AlreadyReserved(existing.Id)
            : ReserveResult.Conflict();

    var affected = await _db.Database.ExecuteSqlInterpolatedAsync(
        $@"UPDATE StockItems
           SET Available = Available - {cmd.Quantity}
           WHERE Sku = {cmd.Sku}
             AND WarehouseId = {cmd.WarehouseId}
             AND Available >= {cmd.Quantity}", ct);

    if (affected != 1) return ReserveResult.Insufficient();

    var reservation = new Reservation
    {
        Id = Guid.NewGuid(),
        OrderId = cmd.OrderId,
        Sku = cmd.Sku,
        WarehouseId = cmd.WarehouseId,
        Quantity = cmd.Quantity,
        CreatedAt = DateTime.UtcNow
    };
    _db.Reservations.Add(reservation);
    _db.OutboxMessages.Add(OutboxMessage.ForReservation(reservation));
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return ReserveResult.Created(reservation.Id);
}
```

Nếu hai requests cùng key đều thấy existing null, unique index vẫn cần chặn một transaction. Request thua race phải rollback toàn bộ transaction, dùng DbContext mới đọc reservation đã commit rồi so payload; không trả success cho payload khác. Nếu bật EF Core execution strategy retry, cần bao trùm toàn transaction theo API strategy và xử lý ambiguous commit có xác minh. Dispatcher claim outbox bằng lease, retry có backoff và gửi idempotency key; không cam kết exactly-once nếu partner không hỗ trợ.

## Giải thích thiết kế sau khi sửa

Atomic conditional UPDATE bảo vệ invariant trên SQL Server xuyên nhiều instances. Unique index bảo vệ business identity; stock decrement, reservation và outbox nằm trong một transaction. Partner là dependency ngoài transaction, do dispatcher xử lý độc lập.

## Trade-offs

Hot SKU gây lock contention; đo lock waits và throughput trước khi partition/shard. Outbox thêm lag, worker và reconciliation. Redis distributed lock không thay thế database constraints. Nếu ERP là source of truth, phải xác nhận ownership trước khi chọn local inventory model.

## Cách kiểm thử

1. Concurrency integration: 100 requests cho 10 units, tổng reserved không vượt 10.
2. Idempotency: concurrent duplicate requests tạo một reservation; payload khác trả conflict.
3. Crash injection: commit thành công nhưng response mất; retry trả reservation cũ.
4. Partner outage: outbox còn pending và retry; không gửi trùng khi có idempotency support.
5. Security/database: unauthorized warehouse bị từ chối; CHECK/unique constraints được thực thi.

## Quan sát trong production

Application Insights traces từ API đến SQL/outbox; metrics inventory conflicts, duplicate rate, outbox oldest age, partner failures, p95/p99. SQL Server theo dõi lock waits/deadlocks, affected rows, hot SKUs. Alert khi invariant audit lệch hoặc outbox backlog vượt SLO.

2. Nếu SQL commit response bị mất, làm sao xác minh transaction outcome?
3. Nếu partner không có idempotency API, bạn cam kết mức consistency nào?

# Code Review Challenge 2 — Vue search hiển thị sai tenant khi đổi bộ lọc

Component đôi khi được giữ sống khi đổi tab.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Ticket = { id: string; subject: string; customerEmail: string }
const query = ref('')
const tenantId = ref(localStorage.getItem('tenant') || '')
const tickets = ref<Ticket[]>([])
const loading = ref(false)
const error = ref('')
const cache = new Map<string, Ticket[]>()

async function search() {
  const key = query.value.trim()
  if (cache.has(key)) {
    tickets.value = cache.get(key)!
    return
  }

  loading.value = true
  const response = await fetch(
    `/api/tickets?tenant=${tenantId.value}&q=${encodeURIComponent(key)}`,
    { credentials: 'include' }
  )
  const data = await response.json()
  tickets.value = data.items
  cache.set(key, data.items)
  loading.value = false
}

watch(query, search)
watch(tenantId, search)
onMounted(search)

function changeTenant(id: string) {
  tenantId.value = id
  localStorage.setItem('tenant', id)
}
</script>

<template>
  <section>
    <input v-model="query" aria-label="Tìm ticket" />
    <select :value="tenantId"
      @change="changeTenant(($event.target as HTMLSelectElement).value)">
      <option value="a">Tenant A</option>
      <option value="b">Tenant B</option>
    </select>
    <p v-if="loading">Đang tải...</p>
    <p v-if="error">{{ error }}</p>
    <ul>
      <li v-for="ticket in tickets" :key="ticket.id">
        {{ ticket.subject }} — {{ ticket.customerEmail }}
      </li>
    </ul>
  </section>
</template>
```

## Phiên bản đề xuất

Giả định auth store cung cấp `sessionKey` đổi khi login/logout và tenant list đã được backend xác minh. Không cache PII ở client trong phiên bản này.

```ts
import { ref, watch, onScopeDispose } from 'vue'

type Ticket = { id: string; subject: string; customerEmail: string }
const query = ref('')
const tenantId = ref('')
const sessionKey = ref('') // bind từ auth store
const tickets = ref<Ticket[]>([])
const loading = ref(false)
const error = ref('')
let generation = 0
let controller: AbortController | undefined

watch([query, tenantId, sessionKey], (_next, _prev, onCleanup) => {
  const id = ++generation
  controller?.abort()
  tickets.value = []
  error.value = ''
  loading.value = false
  const q = query.value.trim()
  const tenant = tenantId.value
  if (!sessionKey.value || !tenant || q.length < 2) return

  const abort = new AbortController()
  controller = abort
  const timer = setTimeout(async () => {
    if (id !== generation) return
    loading.value = true
    try {
      const params = new URLSearchParams({ tenant, q })
      const response = await fetch(`/api/tickets?${params}`, {
        credentials: 'include', signal: abort.signal, cache: 'no-store'
      })
      if (!response.ok) throw new Error(`HTTP ${response.status}`)
      const body: unknown = await response.json()
      if (!isTicketPage(body)) throw new Error('Invalid response')
      if (id === generation && !abort.signal.aborted)
        tickets.value = body.items
    } catch (e) {
      if (id === generation && !abort.signal.aborted)
        error.value = e instanceof Error ? e.message : 'Search failed'
    } finally {
      if (id === generation) loading.value = false
    }
  }, 300)
  onCleanup(() => { clearTimeout(timer); abort.abort() })
}, { immediate: true })

onScopeDispose(() => { generation++; controller?.abort() })

function isTicketPage(x: unknown): x is { items: Ticket[] } {
  return typeof x === 'object' && x !== null && 'items' in x
    && Array.isArray(x.items)
    && x.items.every((t: unknown) =>
      typeof t === 'object' && t !== null
      && 'id' in t && typeof t.id === 'string'
      && 'subject' in t && typeof t.subject === 'string'
      && 'customerEmail' in t && typeof t.customerEmail === 'string')
}
```

Template dùng authorized tenant options, explicit empty state và accessible status. Nếu component dùng KeepAlive, thêm onDeactivated để cancel/invalidate và onActivated để revalidate. Server trả `Cache-Control: private, no-store` với PII; browser fetch cache option không thay thế HTTP cache policy.

## Giải thích thiết kế sau khi sửa

Cleanup hủy timer/request cũ; generation guard ngăn stale completion. Xóa tickets ngay khi context đổi bảo vệ confidentiality. Server vẫn enforce authorization, pagination và rate limiting.

## Trade-offs

Debounce thêm khoảng 300ms nhưng giảm request amplification. Abort không đảm bảo backend ngừng SQL query; backend cần cancellation propagation. Không cache tăng network traffic; chỉ bổ sung cache nếu có measurement và invalidation theo identity.
