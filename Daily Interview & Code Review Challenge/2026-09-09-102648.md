# Code Review Challenge 1 — Middleware ghi request/response body làm lộ secrets, tăng memory và phá streaming dưới tải

**Chủ đề:** C#, ASP.NET Core, middleware, logging, security, streams, buffering, cancellation, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một ASP.NET Core API trên .NET 8 phục vụ cổng quản trị doanh nghiệp. Để điều tra lỗi production nhanh hơn, team thêm middleware ghi toàn bộ HTTP request và response body vào application logs.

Hệ thống có các endpoint:

- đăng nhập và refresh token;
- cập nhật hồ sơ người dùng;
- upload JSON document từ vài KB đến hàng chục MB;
- download/export report lớn;
- một số endpoint trả dữ liệu dạng stream;
- API chạy nhiều instances và gửi logs sang hệ thống tập trung.

Sau khi middleware được deploy:

- log volume tăng rất mạnh;
- security team phát hiện access token, refresh token và một số thông tin cá nhân xuất hiện trong logs;
- p99 tăng đáng kể khi upload/export lớn;
- memory và allocation rate tăng trong peak traffic;
- một số response streaming không còn bắt đầu gửi dữ liệu sớm như trước;
- khi client disconnect, server đôi khi vẫn tiếp tục copy/serialize/logging khá lâu;
- team đề xuất tăng log-storage quota và scale-out application.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class BodyLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<BodyLoggingMiddleware> _logger;

    public BodyLoggingMiddleware(
        RequestDelegate next,
        ILogger<BodyLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var requestReader = new StreamReader(
            context.Request.Body,
            Encoding.UTF8,
            detectEncodingFromByteOrderMarks: false,
            leaveOpen: true);

        var requestBody = await requestReader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        _logger.LogInformation(
            "HTTP request {Method} {Path}. Authorization={Authorization}. Body={Body}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers.Authorization.ToString(),
            requestBody);

        var originalResponseBody = context.Response.Body;
        await using var responseBuffer = new MemoryStream();
        context.Response.Body = responseBuffer;

        try
        {
            await _next(context);

            responseBuffer.Position = 0;
            var responseBody = await new StreamReader(responseBuffer)
                .ReadToEndAsync();

            _logger.LogInformation(
                "HTTP response {StatusCode}. Body={Body}",
                context.Response.StatusCode,
                responseBody);

            responseBuffer.Position = 0;
            await responseBuffer.CopyToAsync(originalResponseBody);
        }
        finally
        {
            context.Response.Body = originalResponseBody;
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề security, privacy, correctness, performance và reliability.
2. Giải thích impact production của từng vấn đề quan trọng thay vì chỉ nêu style issue.
3. Phân tích memory/allocation amplification khi request hoặc response lớn và khi nhiều requests chạy đồng thời.
4. Phân tích behavior của buffering đối với streaming/large responses.
5. Đề xuất logging design an toàn hơn, có sampling/redaction/limits phù hợp.
6. Giải thích cancellation/client disconnect cần được xử lý ra sao.
7. Đề xuất testing và production telemetry để chứng minh middleware mới tốt hơn.

## Câu hỏi gợi mở

1. Có dữ liệu nào tuyệt đối không nên xuất hiện trong logs dù đang debug production không?
2. `EnableBuffering`, `ReadToEndAsync`, `MemoryStream` và `ReadToEndAsync` ở response tạo bao nhiêu lần materialization/copy?
3. Điều gì xảy ra với endpoint muốn flush dữ liệu theo từng chunk?
4. Nếu response là 200 MB và có 20 requests đồng thời, peak live memory có thể khác gì so với chỉ nhìn kích thước một response?
5. Khi client đã disconnect, các thao tác copy/log hiện còn nhận cancellation signal nào không?

### Gợi ý 1

Observability không được biến production logs thành một bản sao của toàn bộ traffic.

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Ghi nguyên `Authorization` header vào logs

**Vấn đề:** Middleware ghi trực tiếp bearer token hoặc credential tương đương vào hệ thống log tập trung.

**Tại sao xảy ra:** Logging được thiết kế như traffic capture thay vì security-aware telemetry.

**Ảnh hưởng production:** Người hoặc hệ thống có quyền đọc logs có thể lấy credential còn hiệu lực; blast radius của log platform trở thành blast radius của authentication system.

**Cách sửa:** Không log secret-bearing headers. Dùng allowlist cho metadata được phép log thay vì blacklist vài header. Nếu cần nhận diện request, dùng trace/correlation ID và identity non-secret phù hợp.

### Critical — Request/response body có thể chứa password, refresh token, PII hoặc business secrets

**Vấn đề:** Toàn bộ payload được ghi ở mức `Information` cho mọi endpoint.

**Tại sao xảy ra:** Code không có classification, redaction hay endpoint/content-type policy.

**Ảnh hưởng production:** Tạo data leakage lâu dài trong log retention, backup và downstream analytics; có thể vi phạm internal security/privacy controls.

**Cách sửa:** Mặc định không log body. Chỉ cho phép body logging ở use case đã phê duyệt, với schema-aware redaction, kích thước tối đa, environment/role controls và retention phù hợp. Các field như password/token/secret phải bị loại bỏ chứ không chỉ che một phần tùy tiện.

### High — Request body bị materialize toàn bộ thành `string`

**Vấn đề:** `ReadToEndAsync` đọc toàn bộ request vào managed memory trước khi business handler chạy.

**Tại sao xảy ra:** Middleware cần nội dung để log nhưng không đặt payload limit hoặc sampling boundary.

**Ảnh hưởng production:** Large uploads làm allocation rate/GC tăng; concurrent uploads nhân peak memory và p99. Request bắt đầu xử lý muộn hơn vì middleware phải đọc hết body trước.

**Cách sửa:** Không đọc body mặc định. Nếu endpoint thực sự cần diagnostic sampling, chỉ capture tối đa một prefix nhỏ và chỉ với content type/size được cho phép. Dùng request-size limit ở đúng layer theo business requirement.

### High — Response luôn bị buffer toàn bộ trong `MemoryStream`

**Vấn đề:** Mọi response bị thay output stream bằng một in-memory buffer và chỉ copy sang client sau khi `_next` hoàn tất.

**Tại sao xảy ra:** Middleware muốn đọc response body sau khi endpoint tạo xong.

**Ảnh hưởng production:** Streaming bị vô hiệu hóa về mặt thực tế; time-to-first-byte tăng; report/download lớn tạo memory pressure rất cao; nếu endpoint phát vô hạn hoặc rất lớn thì design không còn bounded.

**Cách sửa:** Không buffer response chung cho toàn API. Log metadata/status/duration. Nếu một số small JSON responses cần diagnostic capture, áp dụng endpoint/content-type/size policy và bounded tee/capture thay vì bắt mọi response đi qua full `MemoryStream`.

### High — Memory amplification xảy ra qua nhiều representation/copy

**Vấn đề:** Request body có underlying buffer + decoded string; response có `MemoryStream` buffer + decoded `string` + copy ra network. Logger/provider còn có thể giữ/serialize dữ liệu thêm.

**Tại sao xảy ra:** Code chỉ nhìn kích thước payload chứ không nhìn lifetime và concurrent live set.

**Ảnh hưởng production:** 50 MB payload không đồng nghĩa chỉ tốn 50 MB. Nhiều requests đồng thời có thể gây Gen 2/LOH pressure, allocation spikes và process memory exhaustion.

**Cách sửa:** Giữ telemetry bounded; đo bytes captured/logged; tránh duplicate materialization; dùng streaming cho business payload; đặt concurrency/admission controls cho endpoint large-payload nếu workload cần.

### High — Logging ở `Information` cho mọi request tạo log amplification và chi phí I/O/ingestion

**Vấn đề:** Mỗi payload lớn được serialize và gửi vào log pipeline bất kể request thành công hay thất bại.

**Tại sao xảy ra:** Không có sampling, severity policy hay volume budget.

**Ảnh hưởng production:** Logging backend có thể bị throttling, storage cost tăng, application dành CPU/memory/network cho telemetry thay vì user traffic.

**Cách sửa:** Log structured metadata nhỏ ở mức phù hợp; sampling cho high-volume successful requests; giữ error diagnostic có chọn lọc; đặt log-size/cardinality budget và alert cho ingestion anomalies.

### High — Cancellation/client disconnect không được propagate vào các thao tác đọc/copy

**Vấn đề:** Các bước đọc body/copy response không truyền `HttpContext.RequestAborted` một cách nhất quán.

**Tại sao xảy ra:** Middleware coi logging như work bắt buộc ngay cả khi request đã mất consumer.

**Ảnh hưởng production:** Khi client disconnect, server có thể tiếp tục làm memory/CPU/I/O work không còn giá trị, đặc biệt với payload lớn.

**Cách sửa:** Propagate request cancellation tới operations hỗ trợ cancellation. Tuy nhiên logging cleanup không được phụ thuộc vào việc flush một payload khổng lồ sau cancellation; design chính vẫn phải bounded.

### Medium — Response có thể không được log/copy đúng trong exception path

**Vấn đề:** Nếu `_next(context)` ném exception, phần code đọc/copy response không chạy. Behavior còn phụ thuộc vị trí middleware exception handling trong pipeline.

**Tại sao xảy ra:** Middleware đang vừa intercept body vừa làm observability nhưng không có error semantics rõ.

**Ảnh hưởng production:** Telemetry không nhất quán; nếu pipeline ordering sai có thể khó hiểu response thực tế được tạo bởi exception handler nào.

**Cách sửa:** Tách request timing/error metadata khỏi body capture. Đặt middleware theo pipeline semantics có chủ đích và để centralized exception handler/ProblemDetails chịu trách nhiệm response error.

### Medium — Không giới hạn content type, endpoint và payload class

**Vấn đề:** Binary download, JSON, form data và potentially sensitive endpoints đều bị xử lý giống nhau.

**Tại sao xảy ra:** One-size-fits-all middleware.

**Ảnh hưởng production:** Binary data có thể bị decode/log vô nghĩa; memory/log volume tăng và rủi ro security cao.

**Cách sửa:** Policy allowlist dựa trên endpoint metadata, media type, expected size và data classification.

### Medium — Log raw path có thể kéo theo cardinality hoặc dữ liệu không mong muốn

**Vấn đề:** Nếu path chứa identifiers nhạy cảm hoặc unbounded values, raw path logging có thể làm log-cardinality/PII issue tùy routing design.

**Cách sửa:** Ưu tiên route template/endpoint name cho aggregate metrics; chỉ log identifier cần thiết theo classification policy.

## Phiên bản đề xuất

Thay vì capture toàn bộ traffic, middleware nên ghi **structured request metadata** và chỉ hỗ trợ bounded diagnostic capture qua policy riêng.

```csharp
public sealed class RequestTelemetryMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? failure = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            failure = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);
            var endpoint = context.GetEndpoint()?.DisplayName;

            _logger.Log(
                failure is null ? LogLevel.Information : LogLevel.Error,
                failure,
                "HTTP {Method} endpoint={Endpoint} status={StatusCode} durationMs={DurationMs} traceId={TraceId} requestBytes={RequestBytes} responseBytes={ResponseBytes}",
                context.Request.Method,
                endpoint,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.TraceIdentifier,
                context.Request.ContentLength,
                context.Response.ContentLength);
        }
    }
}
```

Nếu business/support thật sự cần payload để điều tra một nhóm endpoint, tôi sẽ tạo một capability riêng với các guardrails như:

- endpoint metadata phải opt-in;
- chỉ small textual media types;
- capture tối đa vài KB theo policy, không phụ thuộc payload thực tế;
- schema-aware redaction trước khi ghi;
- tuyệt đối không capture authentication endpoints hoặc secret-bearing fields;
- sampling/rate limit;
- restricted log sink/retention nếu data classification yêu cầu;
- không thay response stream bằng unbounded in-memory buffer;
- request/response capture failure không được làm hỏng business request.

Con số giới hạn cụ thể phải lấy từ requirement và capacity test của hệ thống, không hard-code theo ví dụ chung.

## Trade-offs

- Không log full body làm giảm “instant visibility” khi debug một lỗi payload-specific, nhưng đổi lại giảm đáng kể security risk, memory pressure và log cost.
- Bounded diagnostic capture cần thêm policy/redaction code; đổi lại blast radius rõ và kiểm thử được.
- Sampling làm mất một số events; distributed tracing + correlation ID + targeted debug enablement thường cho signal tốt hơn việc capture mọi payload.
- Nếu compliance yêu cầu audit business actions, audit event nên là schema riêng với field được phép lưu, không tái sử dụng raw HTTP logging.

## Testing

### Security tests

- Request chứa bearer token, refresh token, password, API key, PII → assert logs không chứa raw values.
- Endpoint không opt-in → body không xuất hiện trong logs.
- Redaction policy với nested JSON/optional fields/malformed payload.

### Performance/load tests

- Small request baseline trước/sau middleware mới.
- Upload/download lớn dưới concurrency thực tế.
- Đo allocation rate, managed heap, GC pause, working set, TTFB và p95/p99.
- Log sink chậm/throttled để kiểm tra telemetry không kéo sập request path.

### Behavior tests

- Streaming response phải bắt đầu gửi trước khi toàn bộ payload hoàn tất.
- Client disconnect/cancellation giữa upload/download.
- Endpoint ném exception trước/sau khi viết response.
- Binary response và unsupported content type.

## Production observability

Theo dõi tối thiểu:

- request rate, p50/p95/p99 và error rate theo endpoint;
- request/response size distributions;
- process working set, managed heap, allocation rate, Gen 2/GC pause;
- log events/bytes per second và log sink throttling/failure;
- cancellation/client-disconnect count nếu có signal phù hợp;
- streaming/download TTFB;
- redaction/drop/sampling counters ở dạng không chứa dữ liệu nhạy cảm;
- trace correlation xuyên API → downstream dependencies.

## Mẫu trả lời code review

“Em xem đây trước hết là security bug chứ không phải logging improvement. Authorization header và raw body có thể chứa token, password, PII nên không được ghi mặc định. Ngoài ra middleware materialize toàn request và buffer toàn response trong memory, vì vậy large payload + concurrency sẽ tạo allocation amplification, tăng GC/p99 và phá streaming vì client chỉ nhận dữ liệu sau khi `_next` hoàn tất.

Em sẽ đổi default sang structured metadata: endpoint, status, duration, trace ID, size và dependency spans. Payload capture chỉ được opt-in, bounded, sampled và schema-redacted; auth/secrets bị cấm. Em không dùng unbounded response `MemoryStream`, propagate cancellation cho work có thể hủy và tách audit business events khỏi raw HTTP logs.

Để chứng minh fix, em test secret leakage, streaming TTFB, client disconnect và load với payload lớn; production theo dõi allocation/heap/GC, p99, log ingestion bytes và trace correlation.”

## Lỗi review thường gặp

- Chỉ nói “không nên log password” nhưng bỏ qua bearer token và data-classification policy.
- Chỉ sửa `new StreamReader`/`using` style mà không thấy full buffering.
- Đề xuất tăng RAM/log quota trước khi giảm payload capture.
- Cho rằng `EnableBuffering()` tự động an toàn cho payload mọi kích thước.
- Không test streaming, cancellation và log-sink degradation.

## Thang điểm 0–10

- **0–2:** Chỉ tìm style/disposal issues.
- **3–4:** Nhận ra sensitive logging hoặc memory issue nhưng chưa phân tích production impact.
- **5–6:** Có security redaction, bounded capture, streaming/cancellation và load testing.
- **7–8:** Có policy-by-endpoint, observability budget, failure behavior và telemetry đầy đủ.
- **9–10:** Kết nối data classification, stream semantics, allocation/lifetime, telemetry economics và production operability thành design có guardrails rõ.

# Code Review Challenge 2 — SQL pagination càng xuống trang sâu càng chậm, query plan khó ổn định và API vẫn có thể trả trùng/mất item

**Chủ đề:** SQL Server, query performance, indexing, pagination, consistency, parameterization, ASP.NET Core API design, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–10 vấn đề

## Bối cảnh

Một admin portal có endpoint tìm kiếm orders. Bảng `Orders` có hàng chục triệu rows và tiếp tục tăng. User có thể lọc theo tenant, status, thời gian và search theo order number. UI dùng page number/page size.

Production có các triệu chứng:

- trang 1 thường nhanh;
- trang vài trăm/vài nghìn chậm rõ rệt;
- CPU/reads trên SQL tăng mạnh khi users export hoặc duyệt sâu;
- trong lúc orders mới liên tục được tạo, user đôi khi thấy một order lặp ở hai trang hoặc một order “biến mất” giữa các lần next page;
- team thường thêm index mới mỗi khi một filter chậm;
- một developer muốn tăng `CommandTimeout`;
- một developer khác muốn build SQL bằng string interpolation để hỗ trợ nhiều sort options nhanh hơn.

Query hiện tại được giản lược như sau:

## Đoạn code cần review

```csharp
public async Task<IReadOnlyList<OrderListItem>> SearchAsync(
    Guid tenantId,
    string? status,
    DateTime? fromUtc,
    DateTime? toUtc,
    string sortBy,
    int page,
    int pageSize,
    CancellationToken cancellationToken)
{
    var offset = (page - 1) * pageSize;

    var sql = $"""
        SELECT
            Id,
            OrderNumber,
            Status,
            CreatedAtUtc,
            TotalAmount
        FROM dbo.Orders
        WHERE TenantId = @tenantId
          AND (@status IS NULL OR Status = @status)
          AND (@fromUtc IS NULL OR CreatedAtUtc >= @fromUtc)
          AND (@toUtc IS NULL OR CreatedAtUtc < @toUtc)
        ORDER BY {sortBy}
        OFFSET @offset ROWS
        FETCH NEXT @pageSize ROWS ONLY;
        """;

    return await _db.Database
        .SqlQueryRaw<OrderListItem>(
            sql,
            new SqlParameter("@tenantId", tenantId),
            new SqlParameter("@status", (object?)status ?? DBNull.Value),
            new SqlParameter("@fromUtc", (object?)fromUtc ?? DBNull.Value),
            new SqlParameter("@toUtc", (object?)toUtc ?? DBNull.Value),
            new SqlParameter("@offset", offset),
            new SqlParameter("@pageSize", pageSize))
        .ToListAsync(cancellationToken);
}
```

Giả sử `sortBy` hiện được truyền từ query string của API sau một lớp mapping chưa được review kỹ.

## Nhiệm vụ của ứng viên

1. Xác định vấn đề security/correctness/performance trong query và API semantics.
2. Giải thích vì sao deep `OFFSET` có thể tốn kém dù chỉ trả 50 rows.
3. Phân tích duplicate/missing rows giữa pages khi dữ liệu thay đổi đồng thời.
4. Đề xuất sort allowlist và deterministic ordering.
5. So sánh offset pagination với keyset/cursor pagination.
6. Đề xuất index strategy dựa trên access pattern, không phải “index mọi filter”.
7. Giải thích cách kiểm thử với realistic data distribution và cách theo dõi production query behavior.

## Câu hỏi gợi mở

1. Database phải làm gì với hàng trăm nghìn rows đứng trước `OFFSET` trước khi trả 50 rows tiếp theo?
2. Nếu nhiều rows có cùng `CreatedAtUtc`, chỉ sort theo timestamp đã deterministic chưa?
3. Nếu một order mới được insert giữa page 1 và page 2, offset của các rows cũ thay đổi thế nào?
4. `ORDER BY {sortBy}` có thực sự được parameterize không?
5. Các predicates dạng `@p IS NULL OR Column = @p` ảnh hưởng plan/selectivity thế nào dưới nhiều tổ hợp filter?

## Gợi ý

### Gợi ý 1

Pagination là cả bài toán performance lẫn consistency semantics.

### Gợi ý 2

Một cursor tốt thường encode vị trí trong một **stable total ordering**, không chỉ page number.

## Kết quả code review tham khảo

### Critical — Dynamic `ORDER BY` có SQL injection risk nếu `sortBy` không được allowlist chặt

**Vấn đề:** Identifier/direction được chèn trực tiếp vào SQL text. SQL parameters bảo vệ values, không biến arbitrary SQL syntax/identifier thành safe parameter.

**Tại sao xảy ra:** Code dùng string interpolation cho phần SQL không parameterize được theo cách thông thường.

**Ảnh hưởng production:** Nếu mapping upstream cho phép attacker-controlled expression lọt qua, query có thể bị thay đổi ngoài ý muốn; mức exploitability cụ thể phụ thuộc driver/API và validation nhưng design không nên tin raw input.

**Cách sửa:** Map public sort enum/token sang các SQL fragments cố định trong code, ví dụ `created-desc`, `created-asc`, `amount-desc`. Không truyền raw SQL fragment từ client.

### High — Deep `OFFSET` có cost tăng theo vị trí trang

**Vấn đề:** Query chỉ trả một page nhỏ nhưng SQL Server vẫn phải tìm/order và bỏ qua các rows đứng trước offset theo execution plan.

**Tại sao xảy ra:** Offset pagination định vị theo số lượng rows cần skip chứ không theo một seek boundary.

**Ảnh hưởng production:** Logical reads, CPU, sort/worktable pressure và latency tăng ở trang sâu; nhiều deep requests có thể làm database chịu tải lớn dù response nhỏ.

**Cách sửa:** Nếu product requirement cho phép next/previous traversal, dùng keyset/seek pagination với boundary của sort key + unique tie-breaker. Nếu bắt buộc random page-number navigation, chấp nhận trade-off và giới hạn page depth/export path hoặc thiết kế riêng cho report/export.

### High — Ordering không chắc deterministic nếu sort key không unique

**Vấn đề:** Nếu `ORDER BY CreatedAtUtc` hoặc `Status` mà nhiều rows cùng giá trị, database không có total order ổn định giữa ties.

**Ảnh hưởng production:** Row có thể xuất hiện ở page khác giữa executions ngay cả khi data gần như không đổi; cursor cũng sai nếu chỉ encode non-unique key.

**Cách sửa:** Luôn thêm unique stable tie-breaker, ví dụ `(CreatedAtUtc DESC, Id DESC)` và cursor chứa cả hai values.

### High — Offset pagination không cho snapshot consistency khi dataset thay đổi

**Vấn đề:** Page 1 và page 2 là hai queries ở hai thời điểm; insert/delete/update vào vùng sort trước boundary làm offsets dịch chuyển.

**Ảnh hưởng production:** User có thể thấy duplicate hoặc missing item giữa pages.

**Cách sửa:** Chọn semantics rõ. Keyset pagination ổn định hơn trước inserts “phía trước” boundary khi sort immutable/stable. Nếu business yêu cầu snapshot tuyệt đối cho export/report, cần snapshot/versioned job/materialized result hoặc transaction/isolation strategy phù hợp — không thể hứa chỉ bằng cursor.

### High — Optional predicate pattern có thể tạo plan/selectivity trade-offs

**Vấn đề:** Một query shape dùng cho nhiều tổ hợp filter có distribution rất khác: tenant nhỏ/lớn, status phổ biến/hiếm, date range hẹp/rộng.

**Tại sao xảy ra:** Optimizer phải chọn plan cho parameterized query shape; predicates kiểu `@p IS NULL OR ...` còn có thể làm việc estimate/index access khó tối ưu trong một số workloads.

**Ảnh hưởng production:** Một plan tốt cho tổ hợp này có thể tệ cho tổ hợp khác; p99 dao động và team dễ “chữa” bằng thêm index ngẫu nhiên.

**Cách sửa:** Đo actual execution plans/query-store data cho các shapes quan trọng. Cân nhắc generate một số query shapes cố định theo filter phổ biến, dynamic SQL được parameterize đúng cho **values**, hoặc các kỹ thuật plan handling phù hợp sau khi có evidence. Không blanket `OPTION(RECOMPILE)` hay hint mà chưa đo CPU/compile trade-off.

### High — Không validate `page`, `pageSize` và integer arithmetic

**Vấn đề:** Negative/zero/huge values hoặc multiplication overflow có thể tạo behavior không mong muốn hoặc resource abuse.

**Cách sửa:** API đặt bounds dựa trên product/capacity requirement; validate page/pageSize trước query. Với cursor API, limit vẫn phải bounded.

### Medium — Index strategy chưa gắn với leading access pattern

**Vấn đề:** Team thêm index theo từng filter riêng lẻ có thể làm write/storage overhead tăng mà query vẫn cần scan/sort.

**Cách sửa:** Bắt đầu từ workload: mọi query đã scope theo `TenantId`, sau đó thường sort/filter theo `CreatedAtUtc` và có tie-breaker `Id`. Một candidate index có thể bắt đầu từ các key phù hợp với equality/range/order pattern và `INCLUDE` projection columns khi evidence cho thấy lợi ích. Nhưng exact index order phải dựa trên query mix, selectivity và execution plan thực tế; không có một index chung đúng cho mọi sort option.

### Medium — Page-number API trộn interactive browsing với export use case

**Vấn đề:** Export thường đọc dataset rất lớn; lặp page 1...N bằng deep OFFSET nhân database work.

**Cách sửa:** Tách export thành job/streaming pipeline riêng, dùng seek/batch traversal hoặc server-side export strategy phù hợp; rate limit/admission control theo workload.

### Medium — Chỉ tăng `CommandTimeout` che triệu chứng

**Vấn đề:** Timeout dài hơn cho expensive query nhiều thời gian tiêu thụ resource hơn mà không giảm logical reads/sort cost.

**Cách sửa:** Dùng timeout như guardrail phù hợp SLO sau khi query/index/pagination được thiết kế đúng, không làm root-cause fix.

## Phiên bản đề xuất

Ví dụ một API chỉ cho sort theo `CreatedAtUtc DESC, Id DESC` có thể dùng keyset cursor:

```csharp
public sealed record OrderCursor(DateTime CreatedAtUtc, Guid Id);

public async Task<IReadOnlyList<OrderListItem>> SearchNextAsync(
    Guid tenantId,
    string? status,
    DateTime? fromUtc,
    DateTime? toUtc,
    OrderCursor? cursor,
    int pageSize,
    CancellationToken cancellationToken)
{
    pageSize = Math.Clamp(pageSize, 1, 100);

    var query = _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (status is not null)
        query = query.Where(x => x.Status == status);

    if (fromUtc is not null)
        query = query.Where(x => x.CreatedAtUtc >= fromUtc);

    if (toUtc is not null)
        query = query.Where(x => x.CreatedAtUtc < toUtc);

    if (cursor is not null)
    {
        var createdAt = cursor.CreatedAtUtc;
        var id = cursor.Id;

        query = query.Where(x =>
            x.CreatedAtUtc < createdAt ||
            (x.CreatedAtUtc == createdAt && x.Id.CompareTo(id) < 0));
    }

    return await query
        .OrderByDescending(x => x.CreatedAtUtc)
        .ThenByDescending(x => x.Id)
        .Select(x => new OrderListItem
        {
            Id = x.Id,
            OrderNumber = x.OrderNumber,
            Status = x.Status,
            CreatedAtUtc = x.CreatedAtUtc,
            TotalAmount = x.TotalAmount
        })
        .Take(pageSize)
        .ToListAsync(cancellationToken);
}
```

Điểm quan trọng không phải đoạn LINQ cụ thể mà là:

- public sort options được allowlist;
- total ordering có unique tie-breaker;
- cursor encode đúng sort boundary;
- page size bounded;
- query shape và index được kiểm chứng bằng execution plan/data distribution;
- cursor nên được encode/sign/validate ở API boundary thay vì cho client tự tạo arbitrary object nếu integrity của cursor quan trọng.

Với sort khác như `TotalAmount`, cursor phải chứa `TotalAmount + Id` theo cùng direction. Không thể dùng một cursor schema mơ hồ cho mọi sort mode mà không encode sort identity/version.

## Trade-offs

- **Offset pagination:** dễ hiểu, hỗ trợ jump-to-page; performance và consistency kém hơn ở deep pages.
- **Keyset pagination:** seek hiệu quả và ổn định hơn cho next/previous traversal; khó jump tới page N và cursor gắn với sort/filter semantics.
- **Snapshot export:** consistency mạnh hơn cho report nhưng thêm storage/job lifecycle/latency.
- **Nhiều indexes:** có thể tăng read speed nhưng làm writes, storage và maintenance đắt hơn; phải chọn theo workload ưu tiên.
- **Query-shape specialization:** có thể cải thiện plans nhưng tăng code/operational complexity; chỉ thêm khi telemetry chứng minh cần.

## Testing

### Correctness tests

- Nhiều rows có cùng `CreatedAtUtc` → không duplicate/missing khi next cursor.
- Insert row mới giữa các lần fetch page.
- Update field dùng để sort trong khi paging → document semantics rõ và test được.
- Cursor sai sort mode/filter/version → reject hoặc handle theo contract.
- Invalid page size/sort token → validation error.

### Security tests

- `sortBy` chứa SQL expression/punctuation bất kỳ → không được chèn trực tiếp vào SQL.
- Public sort enum chỉ map tới fixed known query expressions.

### Performance tests

- Dataset đủ lớn và distribution gần production.
- So page 1, deep offset và keyset ở cùng filter.
- Đo elapsed time, CPU, logical reads, rows read, sort/spill nếu có.
- Test tenant nhỏ vs tenant lớn, status phổ biến vs hiếm, date range hẹp vs rộng.
- Test export/burst concurrency riêng với interactive search.

## Production observability

Theo dõi:

- query duration p50/p95/p99 theo normalized query/search mode;
- logical reads/CPU và execution-plan regressions qua SQL observability/Query Store phù hợp;
- timeout/cancellation rate;
- page size/deep-offset usage nếu legacy endpoint còn tồn tại;
- rows scanned/read so với rows returned khi telemetry cho phép;
- tempdb/sort spill signals nếu workload liên quan;
- database CPU/IO và connection pool pressure;
- API latency/error rate theo filter/sort mode;
- export queue/run duration nếu export được tách thành job.

## Mẫu trả lời code review

“Em thấy ba nhóm chính. Một là security: `ORDER BY {sortBy}` không được parameterize như value, nên client input phải map qua allowlist cố định. Hai là correctness: sort phải có unique tie-breaker, và page-number offset không cho snapshot semantics khi rows được insert/delete giữa requests nên có thể duplicate/missing. Ba là performance: deep OFFSET vẫn phải xử lý/skip rất nhiều rows trước khi trả page nhỏ.

Nếu UX chủ yếu next/previous, em chuyển sang keyset cursor dựa trên total order như `CreatedAtUtc DESC, Id DESC`; page size bounded. Nếu business thật sự cần jump page N hoặc snapshot export, em tách requirement đó thay vì giả vờ cursor giải quyết tất cả.

Index em chọn từ workload và actual plan — thường tenant scope + sort/range pattern + projection — chứ không index mọi filter. Em test với data skew thật, duplicate timestamps, concurrent inserts và deep pages; production theo dõi p99, logical reads, plan changes, timeout và export pressure.”

## Lỗi review thường gặp

- Chỉ phát hiện SQL injection mà bỏ qua pagination correctness/performance.
- Nói “dùng index” nhưng không gắn với predicate/order/selectivity.
- Dùng cursor chỉ có `CreatedAtUtc` dù timestamp không unique.
- Khẳng định keyset pagination tạo snapshot consistency tuyệt đối.
- Tăng timeout/page size mà không đo reads/plan.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất thêm index hoặc tăng timeout.
- **3–4:** Nhận ra deep OFFSET nhưng thiếu deterministic ordering/security reasoning.
- **5–6:** Có allowlist, keyset + tie-breaker, realistic indexing và tests.
- **7–8:** Có consistency semantics, plan/selectivity reasoning, export separation và production telemetry.
- **9–10:** Cân bằng UX contract, database execution behavior, consistency, security và workload economics bằng recommendation có điều kiện.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- HTTP observability phải được thiết kế theo **data classification + bounded telemetry**, không phải capture toàn bộ request/response.
- Buffering toàn payload có thể tạo memory amplification, tăng GC/p99 và làm mất streaming semantics dù business handler không đổi.
- Cancellation, log-sink failure và large payload phải được coi là production failure paths của middleware.
- Pagination là đồng thời bài toán **API semantics, SQL execution cost và consistency**.
- Keyset pagination cần stable total ordering; cursor không tự động tạo snapshot consistency và cũng không thay thế index/workload analysis.

## Mẫu tư duy cần nhớ

1. **Security boundaries trước observability convenience:** không để logs trở thành kho secrets/PII.
2. **Bound resource usage:** payload, page size, logging, concurrency và export đều cần giới hạn dựa trên workload.
3. **Measure execution, not response size:** response 50 rows vẫn có thể buộc database đọc/sort rất nhiều rows.
4. **Define consistency semantics explicitly:** “next page ổn định” và “snapshot tuyệt đối” là hai requirement khác nhau.
5. **Use evidence before tuning:** allocation/GC, execution plan, logical reads và production distributions quan trọng hơn default recipes.
