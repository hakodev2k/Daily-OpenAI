# Code Review Challenge 1 — Azure Service Bus xử lý hoàn tiền trùng khi retry

**Chủ đề:** C#/.NET 8, Azure Service Bus, SQL Server, idempotency, transaction boundary  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một worker ASP.NET Core chạy trên ba Azure App Service instances nhận sự kiện `RefundRequested` từ Azure Service Bus queue. Mỗi sự kiện yêu cầu ghi trạng thái hoàn tiền vào SQL Server và gọi payment gateway. Gateway hỗ trợ `Idempotency-Key` nhưng team chưa cấu hình. Trong đợt gateway chậm, khách hàng báo có hai lần hoàn tiền cho cùng đơn. Hệ thống cần không mất yêu cầu khi restart và có thể retry khi gateway trả lỗi tạm thời. Giả định `Refunds` có khóa chính `Id`, các cột `OrderId`, `Amount`, `Status`; `IPaymentGateway.RefundAsync` thực hiện HTTP call và trả `GatewayRefundId`. Chưa biết gateway có endpoint tra cứu giao dịch hay không.

## Đoạn code cần review

```csharp
public sealed record RefundRequested(Guid OrderId, decimal Amount);

public sealed class RefundWorker : BackgroundService
{
    private readonly ServiceBusClient _bus;
    private readonly IServiceScopeFactory _scopes;
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<RefundWorker> _logger;

    public RefundWorker(ServiceBusClient bus, IServiceScopeFactory scopes,
        IPaymentGateway gateway, ILogger<RefundWorker> logger)
    {
        _bus = bus;
        _scopes = scopes;
        _gateway = gateway;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var receiver = _bus.CreateReceiver("refund-requests");
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await receiver.ReceiveMessageAsync(
                TimeSpan.FromSeconds(5), stoppingToken);
            if (message is null) continue;

            try
            {
                var request = message.Body.ToObjectFromJson<RefundRequested>();
                using var scope = _scopes.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                var existing = await db.Refunds
                    .FirstOrDefaultAsync(x => x.OrderId == request.OrderId);
                if (existing is null)
                {
                    var result = await _gateway.RefundAsync(
                        request.OrderId, request.Amount);
                    db.Refunds.Add(new Refund
                    {
                        Id = Guid.NewGuid(),
                        OrderId = request.OrderId,
                        Amount = request.Amount,
                        Status = "Completed",
                        GatewayRefundId = result.GatewayRefundId
                    });
                    await db.SaveChangesAsync();
                }

                await receiver.CompleteMessageAsync(message);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Refund failed: {Message}", message.Body);
                await receiver.AbandonMessageAsync(message);
            }
        }
    }
}
```

## Kết quả code review tham khảo

### Critical — Gateway refund không idempotent

**Vấn đề:** Gọi gateway không có `Idempotency-Key`.  
**Tại sao xảy ra:** Retry sau crash hoặc mất kết nối không biết request cũ đã được gateway thực hiện hay chưa.  
**Ảnh hưởng production:** Hoàn tiền nhiều lần, sai lệch tài chính.  
**Cách sửa:** Dùng `RefundOperationId` bất biến và cùng idempotency key cho mọi lần retry; xác nhận hợp đồng gateway, retention của key và hành vi khi payload khác nhau. Nếu gateway không hỗ trợ, dùng reconciliation/manual resolution khi outcome không rõ; không tự động gọi lại vô hạn.

### Critical — Check-then-act không có ràng buộc duy nhất

**Vấn đề:** `FirstOrDefaultAsync` rồi gọi gateway không bảo vệ khỏi nhiều consumers.  
**Tại sao xảy ra:** Các instance đọc trước khi bất kỳ instance nào ghi.  
**Ảnh hưởng production:** Hai HTTP side effects đồng thời.  
**Cách sửa:** Unique constraint trên `RefundOperationId` (hoặc business key chính xác theo nghiệp vụ); claim operation bằng insert/atomic transition trước khi gọi gateway; có lease/ownership và reconciliation để xử lý claim bị bỏ dở.

### High — Không có durable state machine cho outcome không chắc chắn

**Vấn đề:** Chỉ ghi `Completed` sau HTTP call.  
**Tại sao xảy ra:** SQL và gateway không có distributed atomic transaction.  
**Ảnh hưởng production:** Gateway thành công nhưng DB không có record; retry có thể gây duplicate.  
**Cách sửa:** Persist `Pending` trước; trạng thái `Processing`, `Completed`, `NeedsReconciliation`; query gateway bằng operation ID khi timeout nếu hỗ trợ.

### High — Message lock có thể hết hạn

**Vấn đề:** Receiver thủ công không renew lock; HTTP call có thể vượt lock duration.  
**Tại sao xảy ra:** Peek-lock có thời hạn và có thể bị giao lại.  
**Ảnh hưởng production:** Concurrent processing, settlement lỗi, delivery count tăng.  
**Cách sửa:** Dùng `ServiceBusProcessor` với auto lock renewal phù hợp và timeout được kiểm soát; idempotency vẫn bắt buộc vì renewal không bảo đảm exactly-once.

### High — Cancellation và shutdown không được truyền

**Vấn đề:** EF, HTTP và settlement không dùng `stoppingToken`.  
**Tại sao xảy ra:** Worker chỉ kiểm tra token ở vòng nhận.  
**Ảnh hưởng production:** Shutdown kéo dài, operation bị ngắt giữa chừng.  
**Cách sửa:** Truyền token tới I/O, cấu hình graceful drain; phân biệt cancellation khi đang xử lý với trạng thái gateway chưa rõ.

### Medium — Retry không phân loại lỗi và không có poison policy

**Vấn đề:** Mọi exception đều `Abandon` ngay.  
**Tại sao xảy ra:** Không phân biệt validation, permanent gateway errors và transient errors.  
**Ảnh hưởng production:** Retry storm, tốn tài nguyên, message bị chuyển DLQ mà không có cảnh báo.  
**Cách sửa:** Phân loại lỗi, giới hạn attempts, backoff, DLQ với lý do rõ ràng; theo dõi DLQ và quy trình replay có kiểm soát.

### Medium — Logging có nguy cơ lộ dữ liệu và thiếu correlation

**Vấn đề:** Ghi toàn bộ message body, thiếu operation/message/trace ID.  
**Tại sao xảy ra:** Log không cấu trúc theo business operation.  
**Ảnh hưởng production:** Rò rỉ dữ liệu, khó điều tra.  
**Cách sửa:** Chỉ log safe identifiers, outcome, attempt, exception category; dùng distributed tracing.

### Medium — Receiver và scope lifecycle chưa hoàn chỉnh

**Vấn đề:** Receiver không dispose async; scope sync không tối ưu khi scoped service cần async disposal.  
**Tại sao xảy ra:** Quản lý lifetime chưa khép kín.  
**Ảnh hưởng production:** Resource cleanup kém, đặc biệt khi restart.  
**Cách sửa:** `await using` receiver/scope hoặc để hosted processor quản lý vòng đời rõ ràng.

## Phiên bản đề xuất

Bản dưới minh họa **core flow**, không phải drop-in implementation. `IRefundOperations` phải dùng unique index, atomic claim với lease fencing và durable state; `IGateway` phải cam kết idempotency theo key hoặc có reconciliation. Settlement/renewal thuộc Service Bus processor được cấu hình riêng.

```csharp
public sealed record RefundCommand(
    Guid OperationId, Guid OrderId, decimal Amount);

public sealed class RefundHandler
{
    private readonly IRefundOperations _operations;
    private readonly IPaymentGateway _gateway;

    public RefundHandler(IRefundOperations operations, IPaymentGateway gateway)
    {
        _operations = operations;
        _gateway = gateway;
    }

    public async Task HandleAsync(RefundCommand cmd, CancellationToken ct)
    {
        if (cmd.Amount <= 0) throw new InvalidRefundCommandException();

        var claim = await _operations.TryClaimAsync(
            cmd.OperationId, cmd.OrderId, cmd.Amount, ct);

        if (claim.State == RefundState.Completed) return;
        if (!claim.IsOwner)
            throw new RefundBusyException("Retry later with same operation ID");

        try
        {
            var result = await _gateway.RefundAsync(
                cmd.OrderId, cmd.Amount,
                idempotencyKey: cmd.OperationId.ToString("N"), ct);

            await _operations.CompleteIfOwnerAsync(
                cmd.OperationId, claim.FencingToken,
                result.GatewayRefundId, ct);
        }
        catch (GatewayOutcomeUnknownException)
        {
            await _operations.MarkForReconciliationIfOwnerAsync(
                cmd.OperationId, claim.FencingToken, CancellationToken.None);
            throw;
        }
    }
}
```

`TryClaimAsync` cần kiểm tra payload trùng key có khớp, ghi claim bằng transaction và unique constraint; `CompleteIfOwnerAsync` phải so fencing token để owner cũ không ghi đè owner mới. Trong production, không dùng `CancellationToken.None` vô hạn: áp dụng bounded cleanup token độc lập shutdown và dựa vào reconciler khi cleanup thất bại. Worker chỉ complete message khi trạng thái durable đã xác nhận; khi trạng thái `NeedsReconciliation`, tùy contract có thể complete và chuyển sang durable reconciliation queue thay vì retry gateway mù quáng.

## Giải thích thiết kế sau khi sửa

Operation ID phải được tạo từ lúc request hoàn tiền được chấp nhận, không tạo lại mỗi delivery. SQL chịu trách nhiệm uniqueness và trạng thái; gateway chịu trách nhiệm idempotent external effect. Queue chỉ vận chuyển work, không làm nguồn sự thật tài chính. Nếu gateway không hỗ trợ idempotency, yêu cầu quy trình đối soát và khóa xử lý nghiệp vụ trước khi retry. Nếu dùng Service Bus duplicate detection, vẫn không thay thế application-level idempotency.

## Trade-offs

Thêm state machine, unique index, reconciliation job và retention policy làm tăng complexity, storage và chi phí vận hành; đổi lại kiểm soát rủi ro hoàn tiền trùng. Khóa phân tán đơn thuần không giải quyết được crash giữa HTTP và DB. Chọn mức tự động hóa phụ thuộc gateway contract và yêu cầu tài chính.

## Cách kiểm thử

1. **Concurrency integration:** 20 consumers nhận cùng operation; gateway mock ghi nhận đúng một logical refund key và DB có một operation.
2. **Failure injection:** Gateway thành công nhưng DB commit timeout; retry cùng key và reconciliation không tạo refund thứ hai.
3. **Lock expiry:** Giả lập handler vượt lock duration, duplicate delivery và settlement failure.
4. **Poison test:** Payload sai, gateway 4xx vĩnh viễn và 5xx tạm thời đi đúng retry/DLQ policy.
5. **Shutdown test:** Cancel giữa gateway call và persist; restart phục hồi đúng state.

## Quan sát trong production

Application Insights traces liên kết `operation_id`, `message_id`, `delivery_count`, gateway request ID; metrics duplicate suppression, `NeedsReconciliation` age, DLQ count, lock-lost, retry rate, gateway p95/p99, mismatched payment/DB records. Alert cho bất kỳ nghi vấn double refund và reconciliation tồn đọng quá SLA.

## Câu hỏi phỏng vấn mở rộng

1. Nếu gateway không có idempotency API lẫn query-by-reference, bạn xử lý timeout không rõ kết quả thế nào?
2. Tại sao Service Bus sessions hoặc distributed lock không đủ để đảm bảo exactly-once external side effect?
3. Làm sao rollout unique constraint khi dữ liệu cũ đã có duplicates?

## Kết quả code review tham khảo

### High — Liveness phụ thuộc SQL và partner API

**Vấn đề:** `/health` gọi hai dependencies; lỗi đối tác làm pod bị restart.  
**Tại sao xảy ra:** Kubelet coi probe thất bại liên tiếp là container không khỏe, dù process vẫn hoạt động.  
**Ảnh hưởng production:** Restart storm, tăng load cho dependencies đang lỗi.  
**Cách sửa:** Liveness chỉ xác nhận process có thể tiến triển; dependency health đưa vào readiness hoặc telemetry, cân nhắc chính sách degraded mode.

### High — Readiness không phản ánh khả năng phục vụ

**Vấn đề:** `/ready` trả 200 ngay sau startup.  
**Tại sao xảy ra:** Chưa xác nhận config, schema compatibility hoặc thành phần thiết yếu.  
**Ảnh hưởng production:** Traffic đi vào pods chưa sẵn sàng, lỗi 5xx.  
**Cách sửa:** Readiness kiểm tra local initialization và dependencies thực sự bắt buộc với timeout ngắn; tránh để partner API không thiết yếu làm toàn bộ app unready.

### High — Rollout làm giảm capacity mạnh

**Vấn đề:** `maxUnavailable: 2` với 3 replicas, `maxSurge: 0`.  
**Tại sao xảy ra:** RollingUpdate cho phép giảm đáng kể số pods sẵn sàng trong lúc thay phiên.  
**Ảnh hưởng production:** Thiếu capacity, 503 dưới tải.  
**Cách sửa:** Dùng `maxUnavailable: 0`, `maxSurge: 1` nếu cluster đủ quota; có `minReadySeconds`, capacity headroom và rollout checks.

### High — Secret được nhúng trực tiếp trong manifest

**Vấn đề:** Token đối tác nằm ở env plaintext trong manifest.  
**Tại sao xảy ra:** Giá trị có thể xuất hiện trong Git, CI logs, deployment artifacts.  
**Ảnh hưởng production:** Rò rỉ credential, khó rotation.  
**Cách sửa:** Secret store (Azure Key Vault/CSI hoặc Kubernetes Secret với encryption và RBAC), workload identity khi phù hợp; rotate token đã lộ, không commit secrets.

### Medium — Mutable image tag

**Vấn đề:** Dùng `:latest`.  
**Tại sao xảy ra:** Tag không định danh artifact bất biến.  
**Ảnh hưởng production:** Rollback/reproduction khó, pods khác nhau có thể chạy digest khác.  
**Cách sửa:** Pin image digest hoặc immutable release tag, lưu SBOM/build SHA trong release record.

### Medium — Resource sizing thiếu căn cứ

**Vấn đề:** Request/limit rất thấp, chưa có đo đạc.  
**Tại sao xảy ra:** CPU throttling và OOMKilled có thể xảy ra dưới tải.  
**Ảnh hưởng production:** Latency, probe timeout, restarts.  
**Cách sửa:** Đo peak working set, CPU throttling, GC và p95/p99; benchmark để điều chỉnh requests/limits, không chọn số tùy tiện.

### Medium — Thiếu startupProbe và drain strategy

**Vấn đề:** Probe bắt đầu sớm, chưa có startup grace và graceful termination plan.  
**Tại sao xảy ra:** Cold start hoặc shutdown khi rollout có thể cắt request đang xử lý.  
**Ảnh hưởng production:** Restart khi startup chậm, dropped in-flight requests.  
**Cách sửa:** `startupProbe`, `terminationGracePeriodSeconds`, ASP.NET Core graceful shutdown, cân nhắc `preStop` sau khi đo endpoint removal latency.

### Medium — Schema compatibility không được bảo vệ trong rollout

**Vấn đề:** Migrations ở pipeline khác nhưng không có compatibility gate.  
**Tại sao xảy ra:** Old/new pods có thể cùng chạy với schema thay đổi.  
**Ảnh hưởng production:** Query failure hoặc rollback thất bại.  
**Cách sửa:** Expand/contract migrations, verify old/new schema compatibility, deployment gate và rollback rehearsal.

```yaml
            failureThreshold: 2
```

Các giá trị resource chỉ là **starting hypothesis**, không phải benchmark. Thay digest placeholder bằng digest thực trước khi apply. Có thể thêm CPU limit sau khi kiểm chứng throttling. Nếu readiness SQL probe gây load cao, dùng lightweight bounded check hoặc internal readiness state được refresh có kiểm soát. Thiết lập PodDisruptionBudget, topology spread và HPA theo yêu cầu availability thực tế, không coi chúng là mặc định bắt buộc.

## Giải thích thiết kế sau khi sửa

Startup probe bảo vệ giai đoạn warm-up; liveness xác nhận tiến trình còn hoạt động; readiness quyết định có nhận traffic không. Không cho lỗi partner API không thiết yếu làm toàn bộ pod restart. Rollout ưu tiên giữ số ready replicas nhưng cần capacity cho surge. Image digest cho phép truy vết và rollback chính xác. Secret phải được cấp qua quyền tối thiểu, rotate và không xuất hiện trong logs.

## Trade-offs

`maxUnavailable: 0` đòi thêm cluster capacity và có thể khiến rollout chờ lâu nếu readiness không đạt. Readiness phụ thuộc SQL có thể loại toàn bộ pods khi DB outage; với chức năng đọc cache/degraded mode, có thể cần endpoint phân tách hoặc chính sách phục vụ một phần. Health probes quá sâu tăng traffic; probes quá nông gây false-ready. Kubernetes chỉ hợp lý nếu yêu cầu vận hành bù được complexity so với App Service.

## Cách kiểm thử

1. **Deployment validation:** Rollout dưới tải, xác nhận ready replicas và error rate không vượt SLO; rollback bằng digest cũ.
2. **Failure injection:** Partner API timeout; liveness vẫn ổn và tính năng không phụ thuộc partner tiếp tục phục vụ.
3. **Database test:** SQL unavailable và restored; readiness phản ánh đúng hợp đồng, không restart storm.
4. **Load test:** Đo CPU throttling, OOM, GC, p95/p99 khi scale/rollout.
5. **Security test:** Manifest/Git/CI artifacts không chứa token; xác minh secret rotation và RBAC.

## Quan sát trong production

Kubernetes events: `Unhealthy`, `Killing`, `OOMKilled`, restarts, ready endpoints, rollout progress, CPU throttling, memory working set. Application Insights: 5xx, p95/p99, SQL dependency duration, partner timeouts, trace correlation theo image digest/release SHA. Alert theo SLO burn rate và rollout failure; so sánh trước/sau release.

## Câu hỏi phỏng vấn mở rộng

1. Khi SQL outage toàn vùng, bạn chọn readiness fail hay degraded mode và vì sao?
2. Nếu cluster không đủ capacity cho `maxSurge: 1`, kế hoạch rollout an toàn thay thế là gì?
3. Làm thế nào thực hiện expand/contract migration khi phải hỗ trợ rollback phiên bản cũ?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai lớp reliability khác nhau: **financial side effects cần idempotency bền vững và reconciliation**, còn **deployment reliability cần phân biệt liveness/readiness, capacity và artifact immutability**. Không nên suy ra exactly-once từ queue hay suy ra healthy service chỉ từ HTTP 200.

## Mẫu tư duy cần nhớ

1. Xác định ranh giới transaction trước khi thiết kế retry.
2. Mọi external side effect phải có chiến lược outcome-unknown.
3. Phân biệt failure của process, dependency và business capability.
4. Đo capacity và p95/p99 trước khi thay resource/rollout settings.
5. Kiểm thử failure path và rollback, không chỉ happy path.
