# Code Review Challenge 1 — Azure Service Bus consumer ghi nhận thanh toán hai lần

**Chủ đề:** C#/.NET 8, Azure Service Bus, idempotency, EF Core transaction  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một hệ thống đặt chỗ nhận sự kiện `PaymentCaptured` từ Azure Service Bus queue. Mỗi message có `EventId`, `BookingId`, `Amount`. Một booking chỉ được cộng tiền thành công một lần cho mỗi event. Ứng dụng chạy 4 replicas trên Azure App Service; handler dùng EF Core với SQL Server. Sau đợt tăng tải, một số booking bị cộng tiền hai lần, một số message chuyển DLQ, và thời gian xử lý tăng. Giả định `Booking.PaidAmount` là decimal và `PaymentAudit.EventId` hiện chưa có unique constraint. Không giả định queue bảo đảm exactly-once.

## Đoạn code cần review

```csharp
public sealed record PaymentCaptured(Guid EventId, Guid BookingId, decimal Amount);

public sealed class PaymentConsumer(
    ServiceBusClient bus,
    IServiceScopeFactory scopes,
    ILogger<PaymentConsumer> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var processor = bus.CreateProcessor("payment-captured",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 16
            });

        processor.ProcessMessageAsync += async args =>
        {
            using var scope = scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var evt = args.Message.Body.ToObjectFromJson<PaymentCaptured>();

            if (await db.PaymentAudits.AnyAsync(x => x.EventId == evt.EventId))
            {
                await args.CompleteMessageAsync(args.Message);
                return;
            }

            var booking = await db.Bookings.SingleAsync(x => x.Id == evt.BookingId);
            booking.PaidAmount += evt.Amount;

            db.PaymentAudits.Add(new PaymentAudit
            {
                EventId = evt.EventId,
                BookingId = evt.BookingId,
                Amount = evt.Amount
            });

            await db.SaveChangesAsync();
            logger.LogInformation("Payment processed: {EventId}", evt.EventId);
            await args.CompleteMessageAsync(args.Message);
        };

        processor.ProcessErrorAsync += args =>
        {
            logger.LogError(args.Exception, "Consumer error");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Check-then-act không atomic

**Vấn đề:** `AnyAsync` không ngăn hai handler đồng thời cùng áp dụng event.  
**Tại sao xảy ra:** Hai transaction đều thấy audit chưa tồn tại; không có unique index.  
**Ảnh hưởng production:** Double-charge logic, sai số dư, audit trùng.  
**Cách sửa:** Unique index `PaymentAudit.EventId`; insert audit và cập nhật booking trong cùng database transaction. Xử lý unique violation thành duplicate đã xử lý, không chạy lại update.

### [High] — Commit thành công nhưng settlement thất bại

**Vấn đề:** SQL và Service Bus không nằm trong một transaction phân tán.  
**Tại sao xảy ra:** Mất mạng/crash sau `SaveChangesAsync`, trước `CompleteMessageAsync`.  
**Ảnh hưởng production:** Redelivery là hành vi bình thường; nếu không idempotent sẽ ghi đôi.  
**Cách sửa:** Consumer idempotent bằng database invariant; không dựa vào exactly-once delivery.

### [High] — Lost update trên cùng booking

**Vấn đề:** Hai event khác nhau cùng đọc `PaidAmount` rồi ghi giá trị tính trong memory.  
**Tại sao xảy ra:** Read-modify-write không được bảo vệ bằng concurrency token hoặc atomic SQL update.  
**Ảnh hưởng production:** Một khoản thanh toán có thể biến mất khỏi tổng tiền dù audit vẫn tồn tại.  
**Cách sửa:** Atomic SQL increment trong cùng transaction, hoặc optimistic concurrency với retry có giới hạn.

### [High] — Exception và poison message chưa được phân loại

**Vấn đề:** Handler có thể throw vì JSON, missing booking, SQL hoặc settlement.  
**Tại sao xảy ra:** Không có policy riêng cho lỗi permanent/transient.  
**Ảnh hưởng production:** Redelivery liên tục, DLQ khó phân tích, mất khả năng quan sát.  
**Cách sửa:** Validation, dead-letter có lý do không nhạy cảm cho payload invalid; transient error để retry với bounded delivery policy; log theo event.

### [Medium] — Cancellation và shutdown không sạch

**Vấn đề:** Processor không được stop/dispose trong `finally`; DB calls và settlement không nhận cancellation token.  
**Tại sao xảy ra:** Lifetime của processor không được quản lý đầy đủ.  
**Ảnh hưởng production:** Shutdown khó dự đoán, xử lý dở dang, redelivery tăng.  
**Cách sửa:** `await using`, `StopProcessingAsync` trong finally, propagation token có cân nhắc cho settlement.

### [Medium] — Thiếu input invariant

**Vấn đề:** Không kiểm tra `Amount > 0`, event ID rỗng, booking tồn tại hay business status hợp lệ.  
**Tại sao xảy ra:** Tin tưởng payload từ queue.  
**Ảnh hưởng production:** Dữ liệu sai hoặc sự kiện không hợp lệ có thể thay đổi số tiền.  
**Cách sửa:** Validate payload và business transition trước transaction.

### [Medium] — Throughput không được kiểm soát theo database

**Vấn đề:** `MaxConcurrentCalls = 16` trên mỗi replica, tổng tối đa 64 handler; không có benchmark.  
**Tại sao xảy ra:** Queue concurrency tách rời SQL connection pool và lock contention.  
**Ảnh hưởng production:** Lock waits, timeout, lock renewal, redelivery.  
**Cách sửa:** Load test rồi tune concurrency, SQL indexes, latency và auto lock renewal.

### [Low] — Telemetry thiếu correlation

**Vấn đề:** Log chỉ có event ID và exception chung.  
**Tại sao xảy ra:** Không đo delivery count, booking ID, duration, duplicate outcome.  
**Ảnh hưởng production:** Khó xác minh nguyên nhân incident.  
**Cách sửa:** Structured logs và metrics không chứa dữ liệu thanh toán nhạy cảm.

## Phiên bản đề xuất

Ví dụ sau giả định SQL Server, EF Core 8+, `EventId` có unique index, và `ExecuteUpdateAsync` thực hiện atomic increment. Các kiểu entity và `AppDbContext` là thành phần ứng dụng cần định nghĩa. Lỗi settlement sau commit vẫn an toàn nhờ idempotency.

```csharp
modelBuilder.Entity<PaymentAudit>()
    .HasIndex(x => x.EventId).IsUnique();

public async Task HandleAsync(
    PaymentCaptured evt, CancellationToken ct)
{
    if (evt.EventId == Guid.Empty || evt.BookingId == Guid.Empty ||
        evt.Amount <= 0)
        throw new InvalidPaymentEventException();

    await using var tx = await db.Database.BeginTransactionAsync(ct);
    try
    {
        db.PaymentAudits.Add(new PaymentAudit
        {
            EventId = evt.EventId,
            BookingId = evt.BookingId,
            Amount = evt.Amount
        });
        await db.SaveChangesAsync(ct);

        var updated = await db.Bookings
            .Where(b => b.Id == evt.BookingId && b.Status == "Confirmed")
            .ExecuteUpdateAsync(s => s.SetProperty(
                b => b.PaidAmount, b => b.PaidAmount + evt.Amount), ct);

        if (updated != 1)
            throw new InvalidPaymentEventException();

        await tx.CommitAsync(ct);
    }
    catch (DbUpdateException ex) when (IsUniqueEventViolation(ex))
    {
        await tx.RollbackAsync(CancellationToken.None);
        // Confirm duplicate EventId via fresh read; do not suppress other constraints.
        if (!await db.PaymentAudits.AsNoTracking()
            .AnyAsync(x => x.EventId == evt.EventId, ct))
            throw;
    }
}
```

`IsUniqueEventViolation` phải kiểm tra mã lỗi unique-index đúng provider và constraint cụ thể; không được bắt mọi `DbUpdateException` như duplicate. Nếu booking đã bị đổi status, transaction rollback cả audit. Cần bảo đảm status và amount invariants phù hợp domain; nếu event có thể đến trước booking, xác định chính sách retry/defer riêng. Khi transaction commit nhưng response mất, duplicate sẽ được xác nhận bằng audit. Handler của `ServiceBusProcessor` chỉ `CompleteMessageAsync` sau khi `HandleAsync` return; permanent invalid payload được dead-letter có reason, transient exception được abandon/để redeliver theo policy. Processor được `await using`, stop trong `finally`, và `ProcessErrorAsync` ghi telemetry.

## Giải thích thiết kế sau khi sửa

Unique index là hàng rào correctness tại database, không phải optimization. Transaction gắn audit với increment; atomic update ngăn lost update giữa các event khác nhau. Service Bus là at-least-once ở mức thiết kế consumer; message settlement không thay thế database invariant. Có thể dùng Inbox table riêng nếu cần lưu thêm trạng thái xử lý, nhưng với một side effect trong cùng SQL database, audit unique key đủ đơn giản.

## Trade-offs

Unique index tăng chi phí ghi và yêu cầu dọn dữ liệu trùng trước migration. Transaction và atomic update tăng contention ở booking nóng; có thể cần sharding/aggregation khi đo được bottleneck. Dead-letter sớm giảm retry vô ích nhưng có nguy cơ loại nhầm event nếu lỗi nghiệp vụ thực ra tạm thời. Không thêm distributed lock khi database constraint đã giải quyết correctness.

## Cách kiểm thử

1. **Concurrency integration:** gửi 100 message cùng `EventId` qua nhiều consumer; assert một audit, một increment.
2. **Concurrency integration:** gửi nhiều `EventId` khác nhau cho cùng booking; assert tổng chính xác.
3. **Failure injection:** commit SQL rồi mô phỏng mất connection trước settlement; redelivery không tăng tiền.
4. **Failure-path:** payload invalid, booking missing, SQL timeout; xác minh retry/DLQ đúng chính sách.
5. **Load test:** 4 replicas, theo dõi p95 processing, lock waits, delivery count và queue age.

## Quan sát trong production

Application Insights trace theo `EventId`/message ID, metric `payment_processed_total`, `payment_duplicate_total`, `payment_failed_total`, SQL deadlocks/lock waits, Service Bus active message count, DLQ depth, delivery count và message age. Alert khi duplicate rate tăng bất thường, DLQ có item hoặc backlog vượt SLO. Không log full payload/PII.

## Câu hỏi phỏng vấn mở rộng

1. Nếu side effect thứ hai là gọi external payment API thì cần Outbox/Inbox hoặc reconciliation như thế nào?
2. Nếu thứ tự event ảnh hưởng state machine thì dùng Service Bus sessions hay version check?
3. Làm thế nào migration unique index khi production đã có duplicate audits?

# Code Review Challenge 2 — CMS preview bị cache công khai qua CDN

## Bối cảnh

Marketing site dùng ASP.NET Core 8 với CMS headless adapter. Public pages được cache ở CDN trong 10 phút; editor có thể xem preview chưa publish. Một endpoint trả HTML theo slug và query `preview=true`. CDN dùng URL làm cache key mặc định, nhưng một rule cấu hình có thể bỏ query string để tăng hit ratio. Sau release, editor thấy nội dung cũ; một số khách báo nhìn thấy banner chưa công bố. Hệ thống cần SEO ổn định và không làm lộ draft. ## Đoạn code cần review

```csharp
app.MapGet("/pages/{slug}", async (
    string slug,
    bool preview,
    HttpContext http,
    ICmsContentService cms,
    IMemoryCache cache) =>
{
    var key = $"page:{slug}";
    if (!cache.TryGetValue(key, out CmsPage? page))
    {
        page = await cms.GetPageAsync(slug, includeDraft: preview);
        if (page is null)
            return Results.NotFound();

        cache.Set(key, page, TimeSpan.FromMinutes(10));
    }

    if (preview && http.User.Identity?.IsAuthenticated != true)
        return Results.Unauthorized();

    http.Response.Headers.CacheControl = "public, max-age=600";
    http.Response.Headers["Surrogate-Control"] = "max-age=600";

    var html = $"""
        <html>
          <head><title>{page.Title}</title></head>
          <body><h1>{page.Title}</h1><article>{page.HtmlBody}</article></body>
        </html>
        """;

    return Results.Content(html, "text/html; charset=utf-8");
});
```

## Kết quả code review tham khảo

### [Critical] — Draft bị cache chung với public

**Vấn đề:** `page:{slug}` dùng chung cho preview và published; cache được điền trước kiểm tra quyền.

**Ảnh hưởng production:** Lộ nội dung chưa công bố cho người dùng ẩn danh.  
**Cách sửa:** Tách hẳn preview route, authorization trước khi truy xuất; không cache preview ở shared cache.

### [Critical] — Preview thiếu authorization theo nội dung

**Vấn đề:** Chỉ kiểm tra `IsAuthenticated`, không kiểm tra quyền preview page/site.  
**Tại sao xảy ra:** Authentication bị nhầm với authorization.  
**Ảnh hưởng production:** User đăng nhập nhưng không có quyền editor vẫn xem draft.  
**Cách sửa:** Policy/permission check theo resource và tenant trước khi lấy draft; trả 403 hoặc 404 theo threat model.

### [High] — Public caching headers áp dụng cho draft

**Vấn đề:** `public, max-age=600` và `Surrogate-Control` cho mọi response.  
**Tại sao xảy ra:** Không phân biệt personalized/sensitive và public representation.  
**Ảnh hưởng production:** CDN/browser lưu preview, phát lại cho user khác tùy edge configuration.  
**Cách sửa:** Preview `private, no-store`, không dùng shared cache; cấu hình CDN bypass preview, auth cookies và query variation.

### [High] — CDN cache key không khớp origin behavior

**Vấn đề:** Edge có thể bỏ query string; URL public và preview bị gộp.  
**Tại sao xảy ra:** App giả định edge giữ query trong cache key.  
**Ảnh hưởng production:** Cross-user leakage hoặc stale representation.  
**Cách sửa:** Preview ở path riêng bị bypass tại edge; kiểm thử cấu hình thực tế, không chỉ dựa vào headers.

### [Medium] — Publish invalidation không có

**Vấn đề:** TTL 10 phút ở app và CDN độc lập với publish.  
**Tại sao xảy ra:** Không có versioned key, purge hoặc event invalidation.  
**Ảnh hưởng production:** Nội dung cũ, SEO metadata không đồng bộ, campaign sai thời điểm.

**Ảnh hưởng production:** Stored XSS nếu editor/input không được kiểm soát.  
**Cách sửa:** HTML-encode plain text; sanitize rich HTML theo allowlist tại ingestion/render, CSP defense in depth.

### [Medium] — Không propagate cancellation và thiếu telemetry

**Vấn đề:** CMS fetch không nhận `RequestAborted`; không có cache provenance.  
**Tại sao xảy ra:** Endpoint tối giản hóa failure handling.  
**Ảnh hưởng production:** Origin lãng phí tài nguyên khi client disconnect; khó điều tra leak/stale.  
**Cách sửa:** CancellationToken, structured metrics cho cache hit/miss, content version, edge status, publish-to-visible latency.

## Phiên bản đề xuất

Ví dụ sau minh họa boundary, không phải drop-in implementation của Optimizely. `CanPreviewAsync` phải kiểm tra quyền trên resource; `GetPublishedAsync` tuyệt đối không truy xuất draft. `RenderSafeHtml` phải encode title và sanitize/allowlist rich HTML.

```csharp
app.MapGet("/editor/preview/{slug}", async (
    string slug, HttpContext ctx, ICmsContentService cms,
    IContentPermissionService permissions, CancellationToken ct) =>
{
    ctx.Response.Headers.CacheControl = "private, no-store";
    ctx.Response.Headers["Surrogate-Control"] = "no-store";

    if (ctx.User.Identity?.IsAuthenticated != true)
        return Results.Unauthorized();

    if (!await permissions.CanPreviewAsync(ctx.User, slug, ct))
        return Results.Forbid();

    var draft = await cms.GetDraftAsync(slug, ct);
    return draft is null
        ? Results.NotFound()
        : Results.Content(RenderSafeHtml(draft), "text/html; charset=utf-8");
}).RequireAuthorization();

app.MapGet("/pages/{slug}", async (
    string slug, HttpContext ctx, ICmsContentService cms,
    IMemoryCache cache, CancellationToken ct) =>
{
    var version = await cms.GetPublishedVersionAsync(slug, ct);
    if (version is null) return Results.NotFound();

    var key = $"published:{slug}:{version}";
    var page = await cache.GetOrCreateAsync(key, async entry =>
    {
        entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);
        return await cms.GetPublishedAsync(slug, ct);
    });
    if (page is null) return Results.NotFound();

    ctx.Response.Headers.CacheControl = "public, max-age=60";
    ctx.Response.Headers["Surrogate-Control"] = "max-age=600";
    return Results.Content(RenderSafeHtml(page), "text/html; charset=utf-8");
});
```

Điều kiện bổ sung: route preview phải bị bypass ở CDN bằng rule kiểm thử được; reject hoặc redirect legacy `?preview=true` để tránh cache key ambiguity. `GetOrCreateAsync` không mặc nhiên chống cache stampede; nếu CMS chịu tải lớn, cân nhắc single-flight và kiểm thử. Version lookup mỗi request có chi phí: có thể thay bằng publish event invalidation kết hợp cache version lookup phù hợp SLO. Khi publish, purge edge bằng URL/tag và xác minh purge hoàn tất; không cho public fallback sang draft.

## Giải thích thiết kế sau khi sửa

Boundary theo URL và authorization tách public/personalized content rõ ràng. Published cache chỉ chứa representation công khai. Cache version gắn nội dung với phiên bản publish, còn edge purge giảm stale window. HTML rendering phải có trust model riêng: text encode, rich HTML sanitize. CDN configuration là một phần của security review, không chỉ tối ưu hiệu năng.

## Trade-offs

Preview no-store tăng origin traffic nhưng bảo vệ confidentiality. Version lookup làm tăng latency/DB calls; cần đo trước khi tối ưu. Purge CDN phụ thuộc external API và có eventual propagation; TTL giới hạn stale duration khi purge lỗi. CSP không thay thế sanitization. Route riêng cần cập nhật link từ CMS editor và regression test.

## Cách kiểm thử

1. **Security integration:** editor preview draft rồi anonymous GET public; assert không bao giờ thấy draft.
2. **Authorization:** authenticated non-editor hoặc editor sai tenant nhận 403/404 theo policy.
3. **CDN E2E:** kiểm tra preview bypass bằng response headers và cache status thực tế, kể cả query normalization.
4. **Publish test:** publish version mới, xác minh origin invalidate và edge purge; đo stale window.
5. **XSS test:** title có markup và rich HTML chứa script/event handler không được thực thi.

## Quan sát trong production

Log có route type, content version, slug đã chuẩn hóa, cache hit/miss, publish event ID, edge request ID, không log draft body. Dashboard theo CDN hit ratio, origin p95, purge failures, publish-to-visible latency, số request preview bị deny. Alert khi preview response có shared-cache hit hoặc header `public`. Kiểm tra Akamai edge rule qua staging và synthetic probes.

## Câu hỏi phỏng vấn mở rộng

1. Nếu website có nhiều ngôn ngữ và audience segmentation, thiết kế cache key thế nào để tránh cache explosion?
2. Khi CDN purge API bị lỗi, ưu tiên consistency hay availability cho trang chiến dịch?
3. Làm sao migrate từ CMS truyền thống sang headless mà giữ canonical URLs và SEO?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message delivery có thể lặp lại; database invariant và transaction mới bảo vệ side effect.
- Atomic update ngăn lost update khi nhiều event khác nhau sửa cùng aggregate.
- Preview là dữ liệu có phân quyền; không được đi qua public/shared cache.
- CDN cache key, origin cache key và authorization phải được kiểm chứng cùng nhau.
- Incident response cần containment, evidence, root cause, verification và prevention.

## Mẫu tư duy cần nhớ

1. Xác định invariant trước khi chọn công nghệ.
2. Thiết kế retry cùng idempotency và failure injection.
3. Kiểm tra security boundary trước mọi lớp cache.
4. Đo latency, lock waits và cache provenance trước khi tối ưu.
5. Test production topology, không chỉ unit test trên một instance.
