# Code Review Challenge 1 — Consumer xử lý booking bị trừ quota hai lần

**Chủ đề:** Concurrency, idempotency, EF Core transaction, message processing  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một worker .NET nhận message từ RabbitMQ để xác nhận booking sự kiện. Mỗi booking chỉ được trừ quota một lần. RabbitMQ có thể redeliver message khi consumer mất kết nối hoặc process chết trước khi ACK. Production thỉnh thoảng ghi nhận quota âm và một booking có hai notification. Lỗi khó tái hiện local và tăng khi traffic cao.

## Đoạn code cần review

```csharp
public sealed class BookingConsumer
{
    private readonly AppDbContext _db;
    private readonly INotificationService _notifications;

    public BookingConsumer(AppDbContext db, INotificationService notifications)
    {
        _db = db;
        _notifications = notifications;
    }

    public async Task HandleAsync(BookingMessage message)
    {
        var booking = await _db.Bookings
            .FirstOrDefaultAsync(x => x.Id == message.BookingId);

        if (booking == null || booking.Status == BookingStatus.Confirmed)
            return;

        var eventBooking = await _db.EventBookings
            .FirstAsync(x => x.Id == booking.EventBookingId);

        if (eventBooking.RemainingSlots <= 0)
            throw new InvalidOperationException("No slots available");

        eventBooking.RemainingSlots--;
        booking.Status = BookingStatus.Confirmed;
        booking.ConfirmedAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        await _notifications.SendAsync(
            booking.UserId,
            $"Booking {booking.Id} confirmed");
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định lỗi correctness.  
2. Tìm rủi ro concurrency, duplicate delivery và failure.  
3. Giải thích tác động production.  
4. Ưu tiên vấn đề theo severity.  
5. Đề xuất implementation tốt hơn.  
6. Nêu cách test fix.  
7. Đề xuất logs, traces và metrics.

## Câu hỏi gợi mở

- Hai consumer có thể cùng đọc `RemainingSlots = 1` không?
- `SaveChangesAsync()` thành công nhưng gửi notification thất bại thì chuyện gì xảy ra?
- Message redelivery có đồng nghĩa business operation được chạy đúng một lần không?
- Check `booking.Status` ở application memory có đủ để chống race condition không?
- Transaction database giải quyết được phần nào và không giải quyết được phần nào?

### Gợi ý 1

### Gợi ý 2

Một transaction không thể tự làm cho database update + external notification trở thành atomic. Hãy nghĩ đến optimistic concurrency/conditional update, idempotency key và transactional outbox.

## Kết quả code review tham khảo

### 1. Check-then-update không atomic

- **Problem:** Hai consumer có thể cùng thấy slot còn lại và cùng confirm.
- **Why:** Read và write tách rời; điều kiện `RemainingSlots > 0` không được enforce atomically tại database.
- **Impact:** Overselling, quota sai.
- **Severity:** Critical.
- **Fix:** Conditional update/optimistic concurrency hoặc transaction + concurrency control phù hợp; đảm bảo affected rows cho biết update có thắng race hay không.

### 2. Không có idempotency bền vững

- **Problem:** `Status == Confirmed` chỉ là guard dựa trên trạng thái đọc được.
- **Why:** Concurrent deliveries có thể đọc trạng thái cũ trước khi một transaction commit.
- **Impact:** Duplicate processing.
- **Severity:** Critical.
- **Fix:** Lưu `MessageId`/operation key với unique constraint hoặc thiết kế state transition atomic.

### 3. Database commit và notification không atomic

- **Problem:** DB có thể commit rồi process chết trước/sau khi gửi notification.
- **Why:** External side effect nằm ngoài transaction DB.
- **Impact:** Missing hoặc duplicate notification khi retry.
- **Severity:** High.
- **Fix:** Transactional outbox; dispatcher gửi notification riêng và consumer phía notification cũng nên idempotent.

### 4. Không truyền cancellation token

- **Problem:** Query, save và external call tiếp tục dù worker đang shutdown/cancel.
- **Impact:** Shutdown kéo dài, work không cần thiết, khó kiểm soát retry.
- **Severity:** Medium.
- **Fix:** Propagate `CancellationToken`.

### 5. Exception `No slots` có thể bị retry vô ích

- **Problem:** Business rejection có thể bị xem như transient failure.
- **Impact:** Retry storm/dead-letter noise.
- **Severity:** Medium.
- **Fix:** Phân loại permanent vs transient failure và cập nhật trạng thái booking phù hợp.

### 6. Thiếu observability cho message identity và state transition

- **Problem:** Không có correlation/message ID trong logs.
- **Impact:** Khó chứng minh duplicate delivery hay race.
- **Severity:** Medium.
- **Fix:** Structured logging + tracing với MessageId, BookingId, EventBookingId và processing outcome.

### 7. `DateTime.UtcNow` khó test và không đồng nhất abstraction thời gian

- **Severity:** Low.
- **Fix:** Dùng `TimeProvider` khi cần deterministic tests.

## Phiên bản code đề xuất

```csharp
public sealed class BookingConsumer
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public BookingConsumer(AppDbContext db, TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task HandleAsync(BookingMessage message, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        if (await _db.ProcessedMessages.AnyAsync(x => x.MessageId == message.MessageId, ct))
            return;

        var booking = await _db.Bookings
            .SingleOrDefaultAsync(x => x.Id == message.BookingId, ct)
            ?? throw new InvalidOperationException("Booking not found");

        if (booking.Status == BookingStatus.Confirmed)
        {
            _db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId));
            await _db.SaveChangesAsync(ct);
            await tx.CommitAsync(ct);
            return;
        }

        var affected = await _db.EventBookings
            .Where(x => x.Id == booking.EventBookingId && x.RemainingSlots > 0)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.RemainingSlots, x => x.RemainingSlots - 1), ct);

        if (affected != 1)
            throw new NoSlotsAvailableException(booking.EventBookingId);

        booking.Status = BookingStatus.Confirmed;
        booking.ConfirmedAtUtc = _timeProvider.GetUtcNow().UtcDateTime;

        _db.ProcessedMessages.Add(new ProcessedMessage(message.MessageId));
        _db.OutboxMessages.Add(OutboxMessage.BookingConfirmed(booking.Id, booking.UserId));

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

`ProcessedMessages.MessageId` cần unique constraint. Outbox dispatcher chịu trách nhiệm gửi notification và đánh dấu outbox record đã xử lý. Với workload lớn, cần thiết kế cleanup/partitioning cho bảng deduplication/outbox.

## Trade-offs

Conditional update đơn giản và tránh giữ lock lâu nhưng cần xử lý rõ trường hợp affected rows = 0. Optimistic concurrency bằng concurrency token phù hợp khi entity có nhiều update cạnh tranh nhưng có thể tạo retry contention. Pessimistic locking có thể hữu ích ở một số invariant nghiêm ngặt nhưng tăng blocking/deadlock risk. Outbox tăng schema, worker và operational complexity nhưng đổi lại có recovery path rõ ràng cho side effect.

## Cách kiểm thử

1. Chạy 50 consumer đồng thời với một slot; chỉ một booking được confirm và quota không âm.
2. Deliver cùng `MessageId` nhiều lần; business state và outbox chỉ thay đổi một lần.
3. Giả lập crash sau DB commit trước khi dispatcher gửi; notification cuối cùng vẫn được xử lý.
4. Giả lập notification provider timeout; outbox retry không làm booking bị trừ slot lần nữa.
5. Test cancellation trong query/save/dispatcher và kiểm tra transaction rollback khi chưa commit.

## Quan sát trong production

Log structured `MessageId`, `BookingId`, attempt và outcome; metric duplicate-message count, no-slot rejection, outbox backlog/age, retry count và processing latency; trace consumer → DB transaction → outbox dispatcher → provider; alert khi outbox oldest-age hoặc retry/dead-letter tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Unique constraint và inbox table có đủ để đảm bảo exactly-once end-to-end không?
2. Nếu PostgreSQL và SQL Server cùng phải được hỗ trợ, bạn sẽ thiết kế conditional update/concurrency abstraction thế nào?
3. Khi nào bạn chấp nhận notification at-least-once thay vì cố deduplicate tuyệt đối?

# Code Review Challenge 2 — API export báo cáo làm cạn connection và memory dưới tải

**Chủ đề:** HTTP client usage, async/cancellation, memory allocation, sensitive logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

ASP.NET Core API tạo báo cáo nhân sự bằng cách gọi một internal service rồi trả file JSON cho frontend. Bình thường endpoint ít traffic, nhưng cuối tháng có nhiều request đồng thời. Production xuất hiện latency tăng, socket/network errors, memory spike và pod/container restart. Một số logs còn chứa payload nhân sự.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(ILogger<ReportsController> logger)
        => _logger = logger;

    [HttpGet("employees")]
    public async Task<IActionResult> Export(string officeId)
    {
        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromMinutes(10);

        var url = $"https://employee-service/api/employees?officeId={officeId}";
        var response = await client.GetAsync(url);
        var json = await response.Content.ReadAsStringAsync();

        _logger.LogInformation("Employee export response: {Response}", json);

        if (!response.IsSuccessStatusCode)
            return StatusCode((int)response.StatusCode, json);

        var employees = JsonSerializer.Deserialize<List<EmployeeDto>>(json)!;
        var output = JsonSerializer.Serialize(employees);

        return File(
            Encoding.UTF8.GetBytes(output),
            "application/json",
            $"employees-{officeId}.json");
    }
}
```

## Kết quả code review tham khảo

### 1. Tạo/dispose `HttpClient` mỗi request

- **Problem:** Không tận dụng handler/connection pool theo mô hình được quản lý tốt.
- **Impact:** Connection churn; dưới tải có thể làm latency và socket pressure tăng.
- **Severity:** High.
- **Fix:** Dùng configured `HttpClient` qua `IHttpClientFactory`/typed client.

### 2. Buffer và copy payload nhiều lần

- **Problem:** Response → string → object graph → string → byte[].
- **Impact:** Allocation lớn, GC pressure và memory spike với report lớn/concurrency cao.
- **Severity:** High.
- **Fix:** Nếu chỉ chuyển tiếp JSON, stream downstream response tới output thay vì deserialize/reserialize toàn bộ.

### 3. Không propagate request cancellation

- **Impact:** Client đã disconnect nhưng server vẫn giữ connection và xử lý payload.
- **Severity:** High.
- **Fix:** Truyền `HttpContext.RequestAborted` vào downstream operation và copy stream.

### 4. Log toàn bộ dữ liệu nhân sự

- **Problem:** Sensitive/business data đi vào log store.
- **Impact:** Data exposure, tăng log cost và retention risk.
- **Severity:** High.
- **Fix:** Log metadata cần thiết; redact/minimize dữ liệu.

### 5. Trả nguyên downstream error body cho caller

- **Problem:** Internal service có thể trả implementation detail hoặc sensitive information.
- **Severity:** Medium.
- **Fix:** Map lỗi sang API contract an toàn; giữ chi tiết trong internal telemetry phù hợp.

### 6. Timeout 10 phút quá rộng và không dựa trên SLO

- **Impact:** Request treo lâu giữ tài nguyên khi dependency suy giảm.
- **Severity:** Medium.
- **Fix:** Timeout theo SLO/use case; resilience policy có budget rõ ràng, tránh retry mù với request lớn.

### 7. `officeId` không được validate/encode rõ ràng

- **Impact:** URL sai hoặc unexpected downstream query semantics.
- **Severity:** Medium.
- **Fix:** Validate domain format và dùng query construction/encoding thay vì nối chuỗi thô.

### 8. Null-forgiving sau deserialize che giấu malformed payload

- **Severity:** Low.
- **Fix:** Nếu cần deserialize, validate result/schema và xử lý `JsonException`.

## Phiên bản code đề xuất

```csharp
public sealed class EmployeeClient
{
    private readonly HttpClient _http;

    public EmployeeClient(HttpClient http) => _http = http;

    public Task<HttpResponseMessage> GetEmployeesAsync(
        string officeId,
        CancellationToken ct)
    {
        var url = $"api/employees?officeId={Uri.EscapeDataString(officeId)}";
        return _http.GetAsync(url, HttpCompletionOption.ResponseHeadersRead, ct);
    }
}

[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly EmployeeClient _client;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(EmployeeClient client, ILogger<ReportsController> logger)
    {
        _client = client;
        _logger = logger;
    }

    [HttpGet("employees")]
    public async Task<IActionResult> Export(string officeId, CancellationToken ct)
    {
        if (string.IsNullOrWhiteSpace(officeId) || officeId.Length > 50)
            return BadRequest();

        using var response = await _client.GetEmployeesAsync(officeId, ct);

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogWarning(
                "Employee service failed. OfficeId={OfficeId}, Status={Status}",
                officeId,
                (int)response.StatusCode);

            return StatusCode(StatusCodes.Status502BadGateway,
                new ProblemDetails { Title = "Employee service unavailable" });
        }

        Response.ContentType = "application/json";
        Response.Headers.ContentDisposition =
            $"attachment; filename=\"employees-{officeId}.json\"";

        await using var stream = await response.Content.ReadAsStreamAsync(ct);
        await stream.CopyToAsync(Response.Body, ct);
        return new EmptyResult();
    }
}
```

Typed client nên được đăng ký bằng `AddHttpClient<EmployeeClient>` với `BaseAddress`, timeout/resilience policy phù hợp hệ thống. Nếu business cần transform/filter dữ liệu, streaming JSON hoặc background export + blob download có thể phù hợp hơn cho report rất lớn.

## Trade-offs

Streaming giảm peak memory và time-to-first-byte nhưng sau khi response bắt đầu, khả năng đổi status/error response bị hạn chế. Với export lớn hoặc mất nhiều phút, asynchronous job + object storage thường dễ kiểm soát timeout/retry hơn nhưng làm UX và architecture phức tạp hơn. `IHttpClientFactory` giúp quản lý handler lifetime; không có nghĩa mọi downstream failure nên retry.

## Cách kiểm thử

1. Load test nhiều export lớn đồng thời; theo dõi memory, GC, connection count và latency.
2. Client disconnect giữa chừng; downstream call/copy phải nhận cancellation.
3. Dependency trả 500 với sensitive body; caller và logs không được lộ body đó.
4. Dependency trả payload lớn; endpoint không tạo nhiều full-size copies trong managed memory.
5. Dependency chậm/timeout; API fail theo policy và telemetry phân biệt timeout/cancellation/downstream error.

## Quan sát trong production

Theo dõi outbound HTTP duration/status, active connections, request cancellation, export bytes, allocation/GC metrics, process working set và container restarts. Trace request qua downstream dependency. Alert trên p95/p99 latency, downstream error rate, timeout rate và memory saturation. Logs chỉ chứa identifiers/metadata cần thiết, không chứa full employee payload.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào singleton `HttpClient` hợp lý và khi nào `IHttpClientFactory` mang lại lợi ích rõ hơn?
2. Nếu cần transform từng employee trước khi export, bạn sẽ tránh load toàn bộ JSON vào RAM thế nào?
3. Với report 1–5 GB, bạn còn giữ synchronous HTTP export hay chuyển sang background job + blob? Vì sao?
