# Code Review Challenge 1 — QA runner tạo browser không giới hạn và treo tài nguyên khi test lỗi

**Chủ đề:** async/await, cancellation, concurrency, resource lifetime, memory/performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Team có một dịch vụ nội bộ chạy Playwright để kiểm tra smoke test sau deployment. Mỗi đợt chạy có thể chứa 20–200 test case. Service chạy dưới dạng `BackgroundService` trong ASP.NET Core, nhận danh sách test từ database và chạy song song để giảm thời gian kiểm tra.

Ở môi trường staging, implementation hiện tại thường chạy ổn. Tuy nhiên khi production deployment kích hoạt nhiều test cùng lúc, team quan sát thấy:

- CPU tăng đột biến và memory có lúc vượt giới hạn container.
- Chromium process đôi khi còn tồn tại sau khi job đã báo hoàn tất.
- Khi deployment bị hủy, test runner vẫn chạy thêm vài phút.
- Một test timeout có thể làm cả batch chậm bất thường.
- Có lúc hàng chục browser được tạo cùng lúc và node bị OOM.
- Log chỉ ghi `Smoke test failed`, không biết test nào, URL nào, thời gian bao lâu hoặc browser có được cleanup hay không.

Yêu cầu business là hoàn thành smoke test nhanh, nhưng không được làm ảnh hưởng tới node đang chạy API và phải dừng sớm khi deployment bị hủy.

## Đoạn code cần review

```csharp
using Microsoft.Playwright;

public sealed class SmokeTestWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly ILogger<SmokeTestWorker> _logger;

    public SmokeTestWorker(
        IServiceProvider services,
        ILogger<SmokeTestWorker> logger)
    {
        _services = services;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            using var scope = _services.CreateScope();
            var repository = scope.ServiceProvider.GetRequiredService<ISmokeTestRepository>();

            var tests = await repository.GetPendingAsync();

            var tasks = tests.Select(test => RunTestAsync(test));
            await Task.WhenAll(tasks);

            await Task.Delay(TimeSpan.FromSeconds(10));
        }
    }

    private async Task RunTestAsync(SmokeTestDefinition test)
    {
        var playwright = await Playwright.CreateAsync();
        var browser = await playwright.Chromium.LaunchAsync(
            new BrowserTypeLaunchOptions { Headless = true });

        var page = await browser.NewPageAsync();

        try
        {
            await page.GotoAsync(test.Url);
            await page.GetByRole(AriaRole.Button, new() { Name = "Login" }).ClickAsync();
            await page.WaitForURLAsync(test.ExpectedUrl);

            _logger.LogInformation("Smoke test passed");
        }
        catch
        {
            _logger.LogError("Smoke test failed");
        }

        await repositoryUpdate(test.Id, true);
    }

    private Task repositoryUpdate(Guid id, bool completed)
    {
        using var scope = _services.CreateScope();
        var repository = scope.ServiceProvider.GetRequiredService<ISmokeTestRepository>();
        return repository.MarkCompletedAsync(id, completed);
    }
}
```

## Kết quả code review tham khảo

### 1. `Task.WhenAll` tạo concurrency không giới hạn

**Problem:** Mỗi test tạo một task ngay lập tức, không có giới hạn số test chạy đồng thời.

**Why it happens:** LINQ tạo tập task cho toàn bộ batch và `Task.WhenAll` chờ tất cả, nhưng không có semaphore, channel hoặc worker pool để giới hạn concurrency.

**Production impact:** Với 100–200 test, service có thể tạo hàng chục hoặc hàng trăm Chromium process/context cùng lúc, làm CPU/memory tăng đột biến, gây OOM, node thrashing hoặc ảnh hưởng API chạy cùng host.

**Severity:** Critical

**Recommended fix:** Dùng bounded concurrency, ví dụ `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, `SemaphoreSlim`, hoặc queue + fixed worker count. Concurrency limit phải cấu hình được và đo thực tế theo CPU/memory của môi trường.

### 2. Browser và Playwright không được cleanup đáng tin cậy

**Problem:** `playwright`, `browser` và `page` không được dispose/close trong `finally`.

**Why it happens:** Cleanup chỉ dựa vào việc method chạy đến cuối, trong khi exception có thể xảy ra ở `CreateAsync`, `LaunchAsync`, `NewPageAsync`, navigation hoặc repository update.

**Production impact:** Chromium child process hoặc native resources có thể tồn tại lâu hơn dự kiến; số process tích tụ sau nhiều batch và gây memory/resource leak.

**Severity:** Critical

**Recommended fix:** Dùng lifecycle rõ ràng: tạo Playwright/browser ở cấp phù hợp, `await using`/`using` nếu API hỗ trợ hoặc gọi `CloseAsync` trong `finally`. Trong nhiều runner, có thể reuse một browser trong batch rồi tạo `BrowserContext` riêng cho từng test để giảm startup cost và vẫn cô lập session.

### 3. `BackgroundService` bỏ qua `stoppingToken`

**Problem:** Vòng lặp `while (true)` và `Task.Delay` không sử dụng cancellation token.

**Why it happens:** Worker không kiểm tra host shutdown signal.

**Production impact:** App shutdown/deployment có thể kéo dài; test vẫn tiếp tục chạy sau khi pod/container nhận termination signal; quá trình rollout có thể bị force-kill giữa chừng.

**Severity:** High

**Recommended fix:** Dùng `while (!stoppingToken.IsCancellationRequested)`, truyền token xuống repository nếu hỗ trợ, dùng `Task.Delay(..., stoppingToken)`, và map token sang timeout/cancellation phù hợp cho Playwright operation.

### 4. Scope bị dispose trước khi async repository operation hoàn tất

**Problem:** `repositoryUpdate` tạo scope bằng `using`, lấy repository rồi trả `Task` trực tiếp mà không `await` trước khi thoát method.

**Why it happens:** Scope được dispose ngay khi method trả `Task`, trong khi `MarkCompletedAsync` có thể vẫn đang dùng scoped dependency như `DbContext`.

**Production impact:** Có thể xuất hiện `ObjectDisposedException`, lỗi cập nhật trạng thái không ổn định hoặc failure chỉ xảy ra dưới timing nhất định.

**Severity:** High

**Recommended fix:** Đổi method thành `async Task`, `await repository.MarkCompletedAsync(...)` bên trong scope rồi mới dispose scope.

### 5. Failure bị nuốt và test vẫn bị đánh dấu completed thành công

**Problem:** Catch mọi exception, chỉ log chung rồi sau đó luôn gọi `MarkCompletedAsync(id, true)`.

**Why it happens:** Không có state machine phân biệt success/failure/cancelled và không rethrow hay trả result có cấu trúc.

**Production impact:** Test thất bại bị mất retry, dashboard báo sai, deployment có thể được coi là healthy dù smoke test thực tế fail.

**Severity:** High

**Recommended fix:** Trả về `SmokeTestResult` có status rõ ràng. Chỉ đánh dấu success khi assertion thành công; failure cần lưu error category, attempt, duration và retry policy nếu phù hợp.

### 6. Không có timeout/cancellation policy ở mức test

**Problem:** Code dựa vào default timeout của Playwright và không có deadline tổng cho từng test.

**Why it happens:** Không phân biệt timeout của từng thao tác với timeout của cả scenario.

**Production impact:** Một test bị kẹt ở dependency ngoài có thể chiếm browser slot quá lâu và kéo chậm toàn batch.

**Severity:** High

**Recommended fix:** Đặt timeout tổng ở application layer, kết hợp Playwright timeout phù hợp cho navigation/action. Khi deadline hết, cancel test, cleanup context/browser và ghi rõ timeout reason.

### 7. Tạo browser mới cho từng test gây startup overhead lớn

**Problem:** Mỗi test gọi `Playwright.CreateAsync` và `Chromium.LaunchAsync`.

**Why it happens:** Isolation được thực hiện bằng process thay vì browser context.

**Production impact:** CPU, memory và startup latency cao; throughput thấp hơn nhiều so với reuse browser hợp lý.

**Severity:** Medium

**Recommended fix:** Thường nên reuse Playwright/browser ở lifecycle dài hơn và tạo context/page riêng cho test. Nếu test yêu cầu process isolation thật sự, giữ process-per-test nhưng concurrency limit phải thấp hơn.

### 8. Log thiếu context và mất exception

**Problem:** Log chỉ ghi `Smoke test passed/failed`, không log test id, URL, duration, attempt hoặc exception.

**Why it happens:** Logging không được thiết kế như một phần của runner.

**Production impact:** Khó phân biệt lỗi app, lỗi test script, DNS/network, timeout hoặc browser crash; MTTR tăng.

**Severity:** Medium

**Recommended fix:** Structured logging với `TestId`, `DeploymentId`, `Target`, `Attempt`, `DurationMs`, `Result`, `FailureCategory`, trace/correlation id; log exception bằng overload có `Exception`.

### 9. Polling loop không xử lý failure ở cấp batch

**Problem:** Exception từ `GetPendingAsync`, `Task.WhenAll` hoặc delay có thể làm `ExecuteAsync` kết thúc hoàn toàn.

**Why it happens:** Không có policy cho transient infrastructure failure ở outer loop.

**Production impact:** Worker chết âm thầm cho đến khi process restart hoặc health check phát hiện.

**Severity:** Medium

**Recommended fix:** Bọc outer iteration với exception handling có phân loại lỗi, backoff và logging; không catch `OperationCanceledException` khi shutdown như lỗi thông thường.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa bounded concurrency, lifecycle rõ ràng, cancellation và state update an toàn. Concurrency limit là giả định cấu hình, không phải con số tối ưu cố định.

```csharp
public sealed class SmokeTestWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<SmokeTestWorker> _logger;
    private readonly int _maxConcurrency = 4;

    public SmokeTestWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<SmokeTestWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var playwright = await Playwright.CreateAsync();
        await using var browser = await playwright.Chromium.LaunchAsync(
            new BrowserTypeLaunchOptions { Headless = true });

        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                List<SmokeTestDefinition> tests;

                await using (var scope = _scopeFactory.CreateAsyncScope())
                {
                    var repo = scope.ServiceProvider
                        .GetRequiredService<ISmokeTestRepository>();
                    tests = await repo.GetPendingAsync(stoppingToken);
                }

                await Parallel.ForEachAsync(
                    tests,
                    new ParallelOptions
                    {
                        MaxDegreeOfParallelism = _maxConcurrency,
                        CancellationToken = stoppingToken
                    },
                    async (test, ct) =>
                    {
                        await RunTestAsync(browser, test, ct);
                    });

                await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Smoke test batch failed");
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
            }
        }
    }

    private async Task RunTestAsync(
        IBrowser browser,
        SmokeTestDefinition test,
        CancellationToken ct)
    {
        var started = Stopwatch.GetTimestamp();
        string status = "Failed";
        string? error = null;

        await using var context = await browser.NewContextAsync();
        var page = await context.NewPageAsync();

        try
        {
            ct.ThrowIfCancellationRequested();

            await page.GotoAsync(test.Url, new() { Timeout = 30_000 });
            await page.GetByRole(AriaRole.Button, new() { Name = "Login" })
                .ClickAsync(new() { Timeout = 10_000 });
            await page.WaitForURLAsync(test.ExpectedUrl, new() { Timeout = 30_000 });

            ct.ThrowIfCancellationRequested();
            status = "Succeeded";
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            status = "Cancelled";
            throw;
        }
        catch (Exception ex)
        {
            error = ex.Message;
            _logger.LogWarning(ex, "Smoke test {TestId} failed for {Url}", test.Id, test.Url);
        }
        finally
        {
            var duration = Stopwatch.GetElapsedTime(started);

            await using var scope = _scopeFactory.CreateAsyncScope();
            var repo = scope.ServiceProvider.GetRequiredService<ISmokeTestRepository>();
            await repo.RecordResultAsync(test.Id, status, error, duration, CancellationToken.None);

            _logger.LogInformation(
                "Smoke test {TestId} finished with {Status} in {DurationMs} ms",
                test.Id,
                status,
                duration.TotalMilliseconds);
        }
    }
}
```

## Trade-offs

- Reuse một browser giảm startup overhead nhưng nếu browser process crash thì nhiều test có thể bị ảnh hưởng; runner cần khả năng recreate browser.
- Browser context cho isolation tốt hơn nhiều trường hợp, nhưng một số test đặc biệt có thể cần process isolation thật sự.
- Concurrency thấp bảo vệ resource nhưng làm batch lâu hơn. Cần đo CPU, memory, test duration và deployment SLA để chọn giới hạn.
- Persist kết quả trong `finally` giúp audit tốt hơn, nhưng cần cân nhắc shutdown nhanh: có thể dùng một token có deadline riêng cho cleanup thay vì bỏ qua cancellation hoàn toàn.

## Cách kiểm thử

1. **Load test:** tạo 100–200 test giả, xác nhận số browser/context chạy đồng thời không vượt giới hạn cấu hình và memory không tăng không kiểm soát.
2. **Cancellation test:** cancel host khi đang chạy batch; xác nhận runner dừng nhận test mới, các test hiện tại được hủy/cleanup và process shutdown trong deadline mong muốn.
3. **Failure-path test:** làm navigation timeout/browser crash; xác nhận resource được cleanup và status lưu là `Failed`, không phải success.
4. **Scope lifetime integration test:** repository dùng EF Core scoped `DbContext`; xác nhận không có `ObjectDisposedException` khi cập nhật kết quả.
5. **Recovery test:** làm `GetPendingAsync` lỗi transient một lần; xác nhận worker log lỗi, backoff và tiếp tục vòng sau thay vì chết vĩnh viễn.

## Quan sát trong production

- Metrics: active tests, queued tests, browser contexts, success/failure/cancel rate, test duration p50/p95/p99, batch duration, process memory, CPU.
- Logs: `TestId`, deployment id, environment, target URL dạng an toàn, attempt, result, failure category, duration.
- Traces: span cho fetch queue, browser launch/context creation, navigation, assertion và persistence.
- Alerts: worker không poll trong N phút, failure rate tăng, queue backlog tăng, memory gần limit, browser crash rate bất thường.
- Process observation: số Chromium child process trước/sau batch để phát hiện leak.

# Code Review Challenge 2 — Offboarding job ghi DB “Completed” trước khi Microsoft Graph thành công

**Chủ đề:** Background jobs, error handling, consistency, idempotency, transaction boundaries, observability  
**Độ khó:** Senior+

## Bối cảnh

Một Hangfire job xử lý offboarding nhân viên. Khi đến `EndTime`, hệ thống cần:

1. Disable một số quyền nội bộ.
2. Cập nhật trạng thái offboarding trong database.
3. Gọi Microsoft Graph/Exchange-related integration để cập nhật mailbox/forwarding theo cấu hình.
4. Ghi audit history.

Job có thể bị retry nếu process restart hoặc dependency ngoài timeout. Trong production, team từng gặp tình trạng database báo `Completed` nhưng mailbox chưa được cập nhật. Một số record khác bị xử lý lại nhiều lần sau khi Hangfire retry.

Không có distributed transaction giữa SQL database và external API. Business yêu cầu có thể biết chính xác record nào hoàn tất, record nào đang chờ retry và record nào cần thao tác thủ công.

## Đoạn code cần review

```csharp
public sealed class EmployeeOffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IGraphMailboxClient _graph;
    private readonly ILogger<EmployeeOffboardingJob> _logger;

    public EmployeeOffboardingJob(
        AppDbContext db,
        IGraphMailboxClient graph,
        ILogger<EmployeeOffboardingJob> logger)
    {
        _db = db;
        _graph = graph;
        _logger = logger;
    }

    public async Task RunAsync(Guid configurationId)
    {
        var config = await _db.EmployeeOffboardingMailConfigs
            .FirstOrDefaultAsync(x => x.Id == configurationId);

        if (config == null || config.Status == "Completed")
            return;

        config.Status = "Completed";
        config.CompletedAt = DateTime.UtcNow;

        _db.EmployeeOffboardingHistories.Add(new EmployeeOffboardingHistory
        {
            ConfigurationId = config.Id,
            Action = "Completed",
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        try
        {
            if (config.ForwardTo != null)
            {
                await _graph.SetForwardingAsync(
                    config.EmployeeEmail,
                    config.ForwardTo);
            }

            if (config.AutoReplyMessage != null)
            {
                await _graph.SetAutoReplyAsync(
                    config.EmployeeEmail,
                    config.AutoReplyMessage);
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Failed to update mailbox for {Email}", config.EmployeeEmail);
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Ghi `Completed` trước khi external side effects thành công

**Problem:** Database được đánh dấu hoàn tất trước khi mailbox được cập nhật.

**Why it happens:** Code coi `SaveChangesAsync` như điểm hoàn tất business transaction dù external API chưa chạy.

**Production impact:** Nếu process crash hoặc Graph call fail, record vẫn là `Completed`; lần retry tiếp theo return ngay và không sửa mailbox nữa. Đây là inconsistency nghiêm trọng và có thể khiến offboarding không được áp dụng.

**Severity:** Critical

**Recommended fix:** Dùng state machine như `Pending -> Processing -> Completed` và chỉ chuyển `Completed` sau khi tất cả required side effects đã đạt trạng thái xác nhận thành công. Nếu lỗi retryable, chuyển/giữ `PendingRetry` hoặc lưu attempt information.

### 2. Catch exception rồi nuốt lỗi làm Hangfire tưởng job thành công

**Problem:** Exception từ Graph chỉ được log và không được propagate.

**Why it happens:** Job không phân biệt “đã log lỗi” với “job execution failed”.

**Production impact:** Hangfire không kích hoạt retry mặc định cho lỗi đó; record có thể bị bỏ lại vĩnh viễn ở trạng thái sai.

**Severity:** Critical

**Recommended fix:** Phân loại lỗi. Với transient/retryable failure, lưu attempt/audit cần thiết rồi throw để job infrastructure retry, hoặc schedule retry rõ ràng. Với permanent failure, chuyển sang `ManualReview`/`FailedPermanent` và không retry vô hạn.

### 3. Hai side effect không nguyên tử nhưng code không lưu checkpoint

**Problem:** Forwarding có thể thành công, auto-reply thất bại.

**Why it happens:** Hai external operations độc lập nhưng database chỉ có một trạng thái tổng quát.

**Production impact:** Retry có thể chạy lại forwarding dù nó đã thành công; khó biết bước nào còn thiếu và có thể tạo side effect không mong muốn nếu API không idempotent.

**Severity:** High

**Recommended fix:** Lưu step-level state hoặc thiết kế commands idempotent. Ví dụ `ForwardingAppliedAt`, `AutoReplyAppliedAt`, hoặc một operation table với từng step. Retry chỉ chạy bước chưa hoàn tất.

### 4. Race condition khi hai execution cùng đọc status chưa Completed

**Problem:** Hai worker có thể cùng đọc record `Pending`, cùng chuyển state và cùng gọi external API.

**Why it happens:** Không có optimistic concurrency token, atomic state transition hoặc distributed job uniqueness đủ mạnh ở data layer.

**Production impact:** Duplicate calls, audit trùng, side effect lặp hoặc dữ liệu cuối phụ thuộc thứ tự execution.

**Severity:** High

**Recommended fix:** Dùng optimistic concurrency (`rowversion`/concurrency token) hoặc atomic update kiểu “claim record nếu status = Pending”. Chỉ worker claim thành công mới tiếp tục. Không nên chỉ dựa vào in-process lock.

### 5. Audit history ghi `Completed` sai thời điểm

**Problem:** Audit nói business action đã hoàn tất trước khi mailbox update xảy ra.

**Why it happens:** Audit đang ghi state transition mong muốn thay vì outcome thực tế.

**Production impact:** Điều tra sự cố và compliance report bị sai; operator không phân biệt “đã bắt đầu” với “đã hoàn tất”.

**Severity:** High

**Recommended fix:** Ghi các event/state rõ ràng như `ProcessingStarted`, `ForwardingApplied`, `AutoReplyApplied`, `Completed`, `FailedRetryable`, `FailedPermanent`.

### 6. Không có cancellation token hoặc timeout contract ở application layer

**Problem:** Method không nhận `CancellationToken`; external calls có thể phụ thuộc hoàn toàn vào timeout mặc định của client.

**Why it happens:** Job signature chưa model hóa deadline/cancellation.

**Production impact:** Worker slot có thể bị giữ lâu khi dependency treo; shutdown hoặc retry scheduling bị chậm.

**Severity:** Medium

**Recommended fix:** Có timeout/cancellation policy rõ ràng trong Graph client. Với Hangfire, cần hiểu cancellation semantics của job host và truyền token phù hợp qua application layer nếu infrastructure hỗ trợ.

### 7. Không phân loại transient và permanent errors

**Problem:** Mọi exception được xử lý giống nhau.

**Why it happens:** Integration client không trả error taxonomy hữu ích hoặc job không map HTTP/service errors thành business retry policy.

**Production impact:** Có thể retry vô hạn lỗi cấu hình/permanent hoặc ngược lại không retry lỗi timeout/throttling tạm thời.

**Severity:** Medium

**Recommended fix:** Phân loại timeout, throttling, network/5xx là ứng viên retry; invalid recipient, permission denied, malformed config có thể cần permanent failure/manual intervention tùy contract thực tế.

### 8. Query và SaveChanges không dùng concurrency protection

**Problem:** Check `Status == "Completed"` chỉ là check ở application memory.

**Why it happens:** Không có concurrency token/version trong entity.

**Production impact:** Lost update hoặc duplicate progression khi nhiều process xử lý cùng record.

**Severity:** Medium

**Recommended fix:** Thêm concurrency token và xử lý `DbUpdateConcurrencyException`, hoặc dùng conditional update trong DB để claim state atomically.

### 9. Logging dùng email trực tiếp mà chưa nói rõ policy PII

**Problem:** Email nhân viên được ghi vào log mà không thể hiện policy phân loại dữ liệu.

**Why it happens:** Logging phục vụ debug nhưng chưa gắn với privacy policy.

**Production impact:** Có thể mở rộng phạm vi PII trong log storage và quyền truy cập.

**Severity:** Low

**Recommended fix:** Dùng internal employee/configuration id hoặc pseudonymized identifier nếu policy yêu cầu; chỉ log email khi thật sự cần và storage/access được kiểm soát.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa state transition, concurrency token và step-level checkpoint. Tên state chỉ là đề xuất; hệ thống thực tế nên dùng enum/value object thay cho magic string.

```csharp
public sealed class EmployeeOffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IGraphMailboxClient _graph;
    private readonly ILogger<EmployeeOffboardingJob> _logger;

    public EmployeeOffboardingJob(
        AppDbContext db,
        IGraphMailboxClient graph,
        ILogger<EmployeeOffboardingJob> logger)
    {
        _db = db;
        _graph = graph;
        _logger = logger;
    }

    public async Task RunAsync(Guid configurationId, CancellationToken ct)
    {
        var config = await _db.EmployeeOffboardingMailConfigs
            .SingleOrDefaultAsync(x => x.Id == configurationId, ct);

        if (config is null || config.Status == "Completed")
            return;

        if (config.Status is not ("Pending" or "Retry" or "Processing"))
            return;

        config.Status = "Processing";
        config.LastAttemptAt = DateTime.UtcNow;
        config.AttemptCount++;

        _db.EmployeeOffboardingHistories.Add(new()
        {
            ConfigurationId = config.Id,
            Action = "ProcessingStarted",
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(ct);

        try
        {
            if (config.ForwardTo is not null && config.ForwardingAppliedAt is null)
            {
                await _graph.SetForwardingAsync(
                    config.EmployeeEmail,
                    config.ForwardTo,
                    ct);

                config.ForwardingAppliedAt = DateTime.UtcNow;
                await _db.SaveChangesAsync(ct);
            }

            if (config.AutoReplyMessage is not null && config.AutoReplyAppliedAt is null)
            {
                await _graph.SetAutoReplyAsync(
                    config.EmployeeEmail,
                    config.AutoReplyMessage,
                    ct);

                config.AutoReplyAppliedAt = DateTime.UtcNow;
                await _db.SaveChangesAsync(ct);
            }

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;
            config.LastError = null;

            _db.EmployeeOffboardingHistories.Add(new()
            {
                ConfigurationId = config.Id,
                Action = "Completed",
                CreatedAt = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(ct);
        }
        catch (MailboxPermanentException ex)
        {
            config.Status = "ManualReview";
            config.LastError = ex.Message;
            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogError(ex,
                "Offboarding {ConfigurationId} requires manual review",
                configurationId);
        }
        catch (Exception ex)
        {
            config.Status = "Retry";
            config.LastError = ex.Message;
            await _db.SaveChangesAsync(CancellationToken.None);

            _logger.LogWarning(ex,
                "Offboarding {ConfigurationId} failed and will be retried",
                configurationId);

            throw;
        }
    }
}
```

Một production-grade version còn cần **atomic claiming/concurrency token** để ngăn hai worker xử lý đồng thời. Ví dụ entity có `RowVersion` và EF Core cấu hình concurrency token; execution thua race phải dừng trước external side effect. Nếu muốn state transition mạnh hơn nữa, có thể dùng một command/outbox table để tách “ghi intent bền vững” khỏi worker thực thi external side effects.

## Trade-offs

- Step-level checkpoint làm schema và code phức tạp hơn nhưng tăng khả năng resume an toàn sau partial failure.
- Throw lại transient exception tận dụng Hangfire retry nhưng phải tránh retry storm; cần backoff và giới hạn attempt.
- Outbox/operation table tăng độ tin cậy và auditability nhưng có thêm worker, schema và operational complexity. Với volume thấp, state machine trong cùng modular monolith có thể đủ.
- Không phải external operation nào cũng tuyệt đối idempotent; cần kiểm tra contract của integration và nếu cần đọc state hiện tại trước khi apply.
- `CancellationToken.None` cho persistence failure state giúp cố gắng ghi nhận kết quả ngay cả khi request token bị cancel, nhưng cần deadline riêng để không làm shutdown treo vô hạn.

## Cách kiểm thử

1. **Crash-window test:** giả lập process chết sau khi forwarding thành công nhưng trước auto-reply; retry phải chỉ thực hiện bước còn thiếu và cuối cùng chuyển `Completed`.
2. **Concurrency test:** chạy đồng thời hai execution cùng `configurationId`; xác nhận chỉ một execution claim record và gọi external API.
3. **Transient failure test:** Graph timeout ở attempt đầu, thành công ở attempt sau; state phải đi qua `Retry` và audit/history không ghi `Completed` sớm.
4. **Permanent failure test:** giả lập permission/config error không retryable; record chuyển `ManualReview`, có last error và không retry vô hạn.
5. **Database concurrency test:** gây `DbUpdateConcurrencyException`; xác nhận execution thua race không tiếp tục gọi external API.

## Quan sát trong production

- Metrics: pending/retry/manual-review count, attempts per configuration, success rate, transient/permanent failure rate, job duration, external API latency.
- Logs: `ConfigurationId`, current state, step, attempt, failure category, external correlation/request id nếu có; tránh ghi secrets hoặc payload nhạy cảm.
- Traces: span cho claim record, forwarding, auto-reply, persistence và retry scheduling.
- Alerts: record ở `Processing` quá lâu, retry count vượt ngưỡng, `ManualReview` tăng, Graph latency/error rate tăng.
- Database observations: age của oldest pending record, distribution theo state và các record có checkpoint không nhất quán.

## Câu hỏi phỏng vấn mở rộng

1. Nếu external API không idempotent, bạn sẽ thiết kế retry-safe operation như thế nào?
2. Khi nào bạn chọn outbox pattern thay vì giữ toàn bộ state machine trong bảng offboarding hiện tại?
3. Nếu một bước đã thành công ở external system nhưng response bị timeout nên client không biết kết quả, bạn sẽ reconcile trạng thái thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Concurrency phải được **giới hạn có chủ đích** khi mỗi task tiêu thụ tài nguyên nặng như browser process, connection hoặc memory.
- `BackgroundService` cần propagation cancellation, bounded work và cleanup deterministic; shutdown behavior là một phần của correctness.
- Async resource lifetime phải bao trùm toàn bộ async operation; không trả `Task` ra khỏi một scope đã bị dispose.
- Database transaction không thể biến external API thành cùng một atomic transaction. Cần thiết kế consistency, retry và recovery explicitly.
- Trạng thái business phải phản ánh **outcome thực tế**, không phải chỉ intent. Audit cũng phải phân biệt Started/Completed/Failed.
- Retry phải đi cùng idempotency, checkpoint và concurrency control; nếu không, retry có thể làm hệ thống sai hơn.

## Mẫu tư duy cần nhớ

1. **Bound concurrency before optimizing throughput.** Tài nguyên nặng cần worker pool/semaphore thay vì `Task.WhenAll` vô hạn.
2. **Own the full resource lifecycle.** Tạo resource ở đâu thì xác định rõ nơi close/dispose ngay cả khi exception/cancellation xảy ra.
3. **Design retries together with state transitions and idempotency.** Đừng thêm retry sau cùng như một patch.
4. **Persist intent, checkpoint progress, mark completed only after verified outcome.**
5. **Treat observability as part of recovery design.** Log/metric phải cho biết đang kẹt ở bước nào và operator phải làm gì.
