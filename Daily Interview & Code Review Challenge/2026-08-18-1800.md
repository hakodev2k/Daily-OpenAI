## Câu 1 — EF Core Tracking và truy vấn ngoài ý muốn trong hệ thống đặt lịch

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 15 phút
**Kỹ năng được đánh giá:** EF Core, query execution, performance debugging, production reasoning

## Bối cảnh

Một hệ thống Event Management dùng ASP.NET Core và EF Core. Sau một đợt release, API lấy danh sách sự kiện của người dùng tăng latency từ 200ms lên 4s khi dữ liệu tăng. Developer cho rằng nguyên nhân là database chậm nhưng SQL monitoring cho thấy không phải tất cả thời gian đều nằm ở SQL.

## Câu hỏi chính

Hãy giải thích EF Core xử lý tracking, query execution và materialization như thế nào trong trường hợp này. Vì sao cùng một LINQ query có thể tạo ra hành vi khác nhau tùy cách viết? Bạn sẽ xác minh giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Query trả về entity hay DTO?
- Số lượng bản ghi trung bình và lớn nhất?
- Có sử dụng Include nhiều navigation không?
- Database provider là SQL Server hay PostgreSQL?

## Gợi ý tư duy

- Gợi ý 1: Phân biệt thời gian database và thời gian xử lý trong application.
- Gợi ý 2: Xem xét tracking, projection và execution pipeline.
- Gợi ý 3: Kiểm tra query plan, logging SQL và memory allocation.

## Cấu trúc trả lời đề xuất

1. Làm rõ triệu chứng.
2. Giải thích cơ chế EF Core.
3. Đưa ra giả thuyết.
4. Đo lường trước khi sửa.
5. So sánh trade-off.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu IQueryable chưa thực thi ngay.
- Hiểu tracking tạo overhead.
- Biết dùng projection khi chỉ cần dữ liệu đọc.

### Điểm cộng
- Nhắc đến AsNoTracking.
- Phân tích Include gây Cartesian explosion.

### Nâng cao
- Đề xuất profiling và benchmark.

## Hướng giải quyết tham khảo

Giả định API chỉ đọc dữ liệu. Nên dùng DTO projection, kiểm tra SQL sinh ra, giảm navigation loading không cần thiết. AsNoTracking phù hợp cho read-only workload. Tuy nhiên nếu cần update entity sau query thì tracking vẫn cần thiết.

## Mẫu trả lời trong phỏng vấn

"Em sẽ không kết luận database chậm ngay. EF Core có nhiều bước ngoài SQL như expression translation, materialization và change tracking. Em sẽ đo SQL duration, application duration, memory allocation và xem generated SQL trước khi quyết định tối ưu."

## Câu hỏi đào sâu

- Khi nào không nên dùng AsNoTracking?
- Split query giải quyết vấn đề gì?
- Làm sao kiểm soát query regression sau release?

## Lỗi trả lời thường gặp

- Chỉ nói thêm index database.
- Không phân biệt LINQ execution và SQL execution.
- Tối ưu trước khi đo.

## Thang điểm 0–10

- Requirement clarification: 2
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 2
- Production readiness: 2

## Câu 2 — Thiết kế nền tảng Background Job cho xử lý tài liệu

**Loại câu hỏi:** System design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** Architecture, reliability, background processing, observability

## Bối cảnh

Công ty cần xây hệ thống upload và xử lý hàng triệu tài liệu mỗi tháng. MVP hiện dùng ASP.NET Core API và Hangfire. Mỗi file cần scan virus, extract text và tạo notification khi hoàn thành.

## Câu hỏi chính

Thiết kế giải pháp backend phù hợp. Hãy trình bày component, data flow, retry, idempotency, monitoring và trade-off.

## Câu hỏi làm rõ nên cân nhắc

- Kích thước file tối đa?
- Có yêu cầu xử lý real-time không?
- Có dữ liệu nhạy cảm không?
- SLA xử lý là bao lâu?

## Gợi ý tư duy

- Gợi ý 1: Bắt đầu từ requirement và failure mode.
- Gợi ý 2: Quan tâm transaction, queue và retry.
- Gợi ý 3: Thiết kế recovery trước khi scale.

## Cấu trúc trả lời đề xuất

1. Assumptions.
2. Components.
3. Data flow.
4. Reliability.
5. Security.
6. Observability.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Có trạng thái job.
- Có idempotency.
- Có retry strategy.

### Điểm cộng
- Outbox pattern.
- Dead letter handling.

### Nâng cao
- Phân tích modular monolith trước microservices.

## Hướng giải quyết tham khảo

Có thể bắt đầu bằng modular monolith + Hangfire/queue. Lưu trạng thái processing trong database, lưu file ở blob storage, worker xử lý độc lập. Retry phải đi cùng idempotency key.

## Mẫu trả lời trong phỏng vấn

"Em sẽ ưu tiên thiết kế flow chịu lỗi trước khi tách service. Một job có thể chạy lại nên business operation phải idempotent."

## Câu hỏi đào sâu

- Khi nào cần RabbitMQ?
- Làm sao xử lý duplicate job?
- Khi worker crash giữa transaction thì sao?

## Lỗi trả lời thường gặp

- Tách microservices ngay.
- Không nói về duplicate processing.
- Không có monitoring.

## Thang điểm 0–10

Đánh giá theo requirement, architecture, reliability, security và communication.

## Câu 3 — Xây dựng AI Code Review Agent an toàn

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** AI agents, context engineering, evaluation, security

## Bối cảnh

Một team .NET muốn tạo AI agent hỗ trợ review pull request. Agent có quyền đọc repository, issue và test result.

## Câu hỏi chính

Thiết kế AI review agent sao cho hữu ích nhưng tránh hallucination, lộ source code và review sai.

## Câu hỏi làm rõ nên cân nhắc

- Agent chạy cloud hay local?
- Repository có secret không?
- Có human approval không?
- Tiêu chí đánh giá review quality là gì?

## Gợi ý tư duy

- Gợi ý 1: Không để model tự quyết định mọi thứ.
- Gợi ý 2: Context, permission và validation rất quan trọng.
- Gợi ý 3: Cần evaluation loop.

## Cấu trúc trả lời đề xuất

1. Define AI boundary.
2. Design tools.
3. Control context.
4. Validate output.
5. Measure quality.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Giới hạn quyền.
- Structured output.
- Human review.

### Điểm cộng
- RAG với coding guideline.
- Regression evaluation.

### Nâng cao
- Audit trail và cost control.

## Hướng giải quyết tham khảo

Agent chỉ nên phân tích và đề xuất. Build pipeline gồm context collector, LLM, validator và reviewer approval. Không cho phép agent tự merge code.

## Mẫu trả lời trong phỏng vấn

"Em xem AI agent như một hệ thống hỗ trợ quyết định, không thay thế kiểm soát kỹ thuật. Output phải được validate bằng rule deterministic."

## Câu hỏi đào sâu

- Làm sao đo agent tốt hơn?
- MCP tool permission nên thiết kế thế nào?
- Khi nào không nên dùng AI?

## Lỗi trả lời thường gặp

- Chỉ nói dùng GPT.
- Không đề cập security.
- Không có evaluation.

## Thang điểm 0–10

Đánh giá theo AI reasoning, architecture, security, evaluation và trade-off.
