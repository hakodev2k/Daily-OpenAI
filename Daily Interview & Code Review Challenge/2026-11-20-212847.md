# Câu 1 — GC/LOH và xuất CSV gây memory pressure

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** .NET 8, GC, LOH, ASP.NET Core, EF Core

## Bối cảnh

API ASP.NET Core xuất CSV 100 MB từ PostgreSQL: ToListAsync → StringBuilder → Encoding.UTF8.GetBytes → File(byte[]). 30 exports đồng thời làm RSS tăng, Gen 2 GC tăng, instances App Service restart. RSS không giảm ngay sau khi request xong. Chưa có heap dump; các số liệu là giả định.

## Câu hỏi chính

Giải thích cơ chế allocation/LOH/GC, phân biệt leak với memory retention và thiết kế cách xác minh, giảm peak memory mà không làm sai dữ liệu.

## Câu hỏi làm rõ nên cân nhắc

1. Giới hạn memory và lý do restart có phải OOM?
2. Heap managed/native, allocations/request, live objects và RSS khác nhau thế nào?
3. Dữ liệu có bị materialize trước khi encode?
4. CSV cần resume, Content-Length, escaping, timeout và audit không?

## Gợi ý tư duy

### Gợi ý 1

Một report có thể tồn tại ở nhiều biểu diễn cùng lúc.

### Gợi ý 2

LOH/Gen 2 và committed memory không giống live objects.

### Gợi ý 3

Streaming chỉ hiệu quả nếu không buffer toàn bộ dữ liệu ở bước trước.

## Cấu trúc trả lời đề xuất

1. Đo memory budget và request concurrency
2. Vẽ pipeline allocations
3. Phân biệt GC pressure và retention
4. Profile và so sánh giả thuyết
5. Thử streaming, cancellation, quotas, rollback

## Ý chính của câu trả lời tốt

### Bắt buộc

Nêu nhiều bản sao entities/string/byte[]; large objects thường vào LOH; RSS cao không chứng minh leak; streaming phải end-to-end.

### Điểm cộng

Dùng dotnet-counters, dotnet-dump/gcdump, allocation profiler, cancellation và CSV escaping.

### Senior+

Định lượng peak theo concurrency, chọn Blob-based background export khi cần resumability.

## Hướng giải quyết tham khảo

Với ToListAsync, toàn bộ rows ở managed heap. StringBuilder, ToString nếu dùng, và UTF-8 byte[] có thể tồn tại đồng thời. Mảng lớn thường vào LOH, được thu gom cùng Gen 2; GC không bắt buộc trả committed memory ngay cho OS. Đầu tiên xác minh restart/OOM, đo managed heap, LOH fragmentation, allocation rate, RSS và native allocations. Chụp heap snapshot sau idle để tìm retention paths; không chữa bằng GC.Collect. Đề xuất project từng row từ EF Core AsAsyncEnumerable, ghi StreamWriter trực tiếp lên Response.Body, flush và truyền RequestAborted tới DB; bảo vệ CSV escaping và spreadsheet formula injection theo consumer policy. Giới hạn exports concurrent và áp dụng backpressure. Khi report quá dài hoặc phải resume, background job xuất Blob Storage, cung cấp URL có authorization/expiry và lifecycle cleanup. Streaming giảm peak nhưng giữ HTTP connection lâu; khi headers đã gửi thì không thể trả ProblemDetails bình thường nếu lỗi giữa chừng. Load test concurrent exports, cancellation, encoding, error injection và đo GC pause, memory, p95, restarts.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak khi chỉ có RSS tăng. Tôi đo heap và allocation theo từng export, kiểm tra OOM/restart và phân biệt live object với committed memory. Pipeline đang có nguy cơ giữ rows, chuỗi và byte array cùng lúc; concurrency nhân peak memory. Tôi giảm concurrency để ổn định rồi thử streaming từ database tới response có cancellation. Nếu cần resumable export, tôi chọn background job và Blob Storage, chấp nhận thêm orchestration để giảm rủi ro giữ HTTP lâu. Tôi kiểm thử output, memory profile và failure path trước rollout.”

## Câu hỏi đào sâu

1. ArrayPool có giải quyết được ToListAsync không?
2. DB lỗi sau khi response headers đã gửi thì xử lý ra sao?
3. Nếu cần resumable downloads, bạn còn dùng direct streaming không?

## Lỗi trả lời thường gặp

- Đồng nhất RSS cao với leak
- Gọi GC.Collect định kỳ
- Gọi streaming dù đã ToListAsync
- Bỏ qua concurrency và cancellation

# Câu 2 — IIS 503 và mất phiên sau modernization release

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET Core, .NET Framework, Octopus Deploy

## Bối cảnh

Một ứng dụng .NET Framework 4.5 đang dần chuyển sang ASP.NET Core .NET 8, chạy trên hai IIS Windows Server. Sau deployment TeamCity/Octopus, 1–2% request 502/503 và một số user phải đăng nhập lại. IIS log có PID thay đổi; chưa rõ recycle policy, process crash, readiness hay Data Protection/session. Rollback yêu cầu dưới 10 phút và không mất đơn hàng.

## Câu hỏi chính

Hãy điều phối incident từ ổn định business đến kiểm chứng root cause và xây release strategy ngăn tái diễn.

## Câu hỏi làm rõ nên cân nhắc

1. 5xx tập trung node/endpoint/time window nào?
2. Event Viewer, ANCM logs, IIS recycle reason ghi gì?
3. Session, Forms Auth machineKey và ASP.NET Core Data Protection keys được lưu ở đâu?
4. Load balancer có readiness/draining không?
5. Database schema có tương thích với binary rollback không?

## Gợi ý tư duy

### Gợi ý 1

503 không đồng nghĩa application crash.

### Gợi ý 2

So sánh PID, recycle reason, deployment timeline và node.

### Gợi ý 3

Auth continuity có thể là vấn đề riêng với process availability.

## Cấu trúc trả lời đề xuất

1. Đo tác động orders, error rate
2. Tạm dừng rollout, drain node lỗi
3. Thu thập evidence theo node
4. So sánh competing hypotheses
5. Fix, canary, validate rollback và monitor

## Ý chính của câu trả lời tốt

### Bắt buộc

Không restart cả cluster trước khi thu thập evidence; phân biệt recycle/crash/startup/routing; bảo vệ đơn hàng và schema compatibility.

### Điểm cộng

Application Insights correlation, IIS logs, Event Viewer, ANCM, crash dump, shared key ring cho ASP.NET Core.

### Senior+

Expand/contract migrations, immutable artifact checksum, canary/draining, order reconciliation.

## Hướng giải quyết tham khảo

Ổn định trước: tạm dừng release, phân nhóm 5xx theo node/build, drain node có lỗi nếu có evidence và kiểm tra orders ở trạng thái chưa rõ trước khi retry. Không rollback DB bằng cách xóa dữ liệu. Thu thập Event Viewer, IIS logs, ANCM logs, PID, recycle reasons, crash dumps, deployment markers, Application Insights dependency traces. Giả thuyết: scheduled recycle, memory-limit recycle, OOM/crash, missing runtime/config, proxy routing vào node chưa ready, deployment interruption, session/key mismatch. Đăng nhập lại có thể do session in-memory hoặc ASP.NET Core Data Protection key ring khác nhau; legacy Forms Authentication dùng machineKey, không được gộp cơ chế. Xác minh từng giả thuyết theo timeline và thử tái hiện. Sửa đúng nguyên nhân; triển khai từng node, warm-up, health/readiness, drain requests, artifact checksum, shared keys bảo vệ phù hợp, persistent session nếu yêu cầu. Database migration theo expand/contract để rollback binary an toàn. Test recycle lúc checkout, forced startup failure, mixed-version rollout, auth continuity và order idempotency. Theo dõi 5xx/node, restart, auth failures, order reconciliation và deployment markers.

## Mẫu trả lời trong phỏng vấn

“Tôi ưu tiên tác động lên checkout và tính đúng của đơn hàng, tạm dừng rollout rồi cô lập node lỗi. Tôi không suy ra PID đổi nghĩa là crash; cần Event Viewer, IIS recycle reason, ANCM và timeline deployment. Tôi điều tra độc lập nguyên nhân 5xx và mất login vì session hay key management có thể khác. Rollback chỉ an toàn nếu database schema tương thích. Sau fix tôi canary một node, kiểm thử recycle và in-flight orders, theo dõi error rate và auth continuity trước khi mở traffic.”

## Câu hỏi đào sâu

1. Nếu 503 xảy ra sau 29 giờ uptime chứ không gần release thì sao?
2. Rollback binary khi migration đã xóa cột cũ có an toàn?
3. Sticky sessions có thay thế shared key ring không?

## Lỗi trả lời thường gặp

- Cho rằng mọi 503 do recycle
- Restart mọi node trước khi lấy evidence
- Dùng sticky sessions làm giải pháp duy nhất
- Bỏ qua schema rollback
- Không kiểm tra duplicate orders

# Câu 3 — Optimizely CMS + Akamai: publish freshness và product data

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai CDN, Vue.js, SEO, e-commerce

## Bối cảnh

Website marketing/e-commerce ở 6 thị trường, Optimizely quản lý pages/blocks/translations, Vue.js hiển thị product widgets từ API bên ngoài, Akamai cache public HTML. Editor muốn publish thấy trên edge trong 60 giây nhưng hiện stale 20 phút. Product price/stock phải đúng theo business contract; SEO cần canonical/hreflang/sitemap và crawlable HTML. Giả định 2 triệu pageviews/ngày. Team đề xuất microservices + Kubernetes + cache mọi response. Chưa xác nhận SLO, API rate limits, cache-key variations.

## Câu hỏi chính

Thiết kế content delivery, invalidation, integration failure và SEO với trade-offs rõ ràng; khi nào chọn kiến trúc đơn giản thay vì microservices?

## Câu hỏi làm rõ nên cân nhắc

1. 60 giây là p95 hay hard bound, tính đến edge hay browser?
2. Giá/tồn kho có personalized theo market, account, currency không?
3. Product API có SLA, webhook, rate limit, bulk endpoint không?
4. CMS dùng traditional/headless/hybrid rendering?
5. Preview, localization, rollback và SEO migrations yêu cầu gì?

## Gợi ý tư duy

### Gợi ý 1

Mỗi lớp dữ liệu có freshness và privacy khác nhau.

### Gợi ý 2

CMS publish không đồng nghĩa edge và browser đã cập nhật.

### Gợi ý 3

Cache key và ownership quan trọng hơn số lượng services.

## Cấu trúc trả lời đề xuất

1. Phân loại SLO/data ownership
2. Vẽ publish và request flows
3. Thiết kế cache keys, invalidation và failure isolation
4. Đảm bảo SEO/security
5. So sánh hosting và complexity
6. Đo, test, rollout

## Ý chính của câu trả lời tốt

### Bắt buộc

Phân biệt editorial/public catalog/personalized; không shared-cache auth/checkout; đo publish-to-visible lag.

### Điểm cộng

Idempotent publish events, purge/reconciliation, SSR/prerender, product API circuit breaker.

### Senior+

Chỉ tách service nếu boundary/team/scale chứng minh; đánh giá stale fallback và edge propagation.

## Hướng giải quyết tham khảo

Giả định CMS là source of truth editorial, product platform sở hữu price/stock. Phân loại public pages, assets, widgets và private checkout. Dùng Optimizely page types/blocks cho editorial; ASP.NET Core render SEO-critical HTML hoặc hybrid với Vue widgets. Akamai cache public HTML với key có market, locale, host, currency nếu ảnh hưởng response; assets versioned có TTL dài, private responses no-store/private theo contract. CMS publish event chứa content ID/version; worker idempotent xác định dependent URLs và purge theo khả năng CDN, có retry/reconciliation và synthetic probes kiểm tra edge visibility. Nếu purge theo tags không được hỗ trợ, dùng URL inventory hoặc TTL/version strategy và đo origin load. Browser cache cần chính sách riêng. Product API được gọi với timeout, bounded retries, circuit breaker và rate limiting; stale price/stock không được dùng để xác nhận checkout, chỉ fallback nếu business cho phép. Preview cần auth/no-store và không index. SSR/prerender cho crawler, canonical/hreflang pairs, sitemap và 301 redirects. Canary release, contract tests, Playwright SEO tests, publish-to-edge probes và monitor CDN hit ratio, purge failures, origin p95, product API errors. Bắt đầu modular application + CDN; microservices/Kubernetes chỉ khi independent scaling/deployments/ownership vượt chi phí vận hành. TTL thấp tăng origin load; purge tăng operational complexity.

## Mẫu trả lời trong phỏng vấn

“Tôi phân loại dữ liệu trước: CMS sở hữu editorial, product platform sở hữu giá và tồn kho, còn checkout không được dùng shared cache. Tôi xác nhận 60 giây là SLO gì và cần đo tới edge hay browser. Public pages có Akamai cache với key đúng market/locale, invalidation theo publish event và probes kiểm tra freshness. Product widgets có timeout và degradation, nhưng checkout phải xác minh nguồn giá/tồn kho. SEO-critical HTML cần SSR hoặc prerender. Tôi chưa chọn Kubernetes: modular delivery hiện tại có thể đủ; chỉ tách services khi nhu cầu scale, ownership và release independence có evidence.”

## Câu hỏi đào sâu

1. Một block dùng trên 30.000 pages thì purge thế nào?
2. Nếu CDN không hỗ trợ purge tags thì sao?
3. Headless hoàn toàn có đáng đổi lấy complexity preview/SEO không?

## Lỗi trả lời thường gặp

- Cache mọi response cùng TTL
- Cho rằng purge ACK là edge freshness
- Lưu giá checkout trong CMS
- Chọn microservices không có evidence
- Quên preview security và SEO
