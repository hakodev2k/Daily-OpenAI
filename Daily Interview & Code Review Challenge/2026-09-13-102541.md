# Code Review Challenge 1 — Search index đôi lúc quay về dữ liệu cũ sau khi nhiều worker đồng bộ Elasticsearch song song

**Chủ đề:** C#/.NET 8, EF Core, SQL Server, Elasticsearch, eventual consistency, out-of-order processing, idempotency, refresh semantics, bounded concurrency, retry, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một e-commerce platform dùng SQL Server làm source of truth cho product catalog và Elasticsearch để phục vụ full-text search. Mỗi lần product thay đổi, application ghi một record vào bảng `SearchIndexJobs`. Nhiều `BackgroundService` instances chạy song song để đọc các job chưa xử lý và cập nhật Elasticsearch.

Business chấp nhận **eventual consistency** trong vài giây, nhưng không chấp nhận trường hợp một product đã cập nhật giá/tên mới rồi vài giây sau search lại quay về dữ liệu cũ.

Production hiện có các triệu chứng:

- thỉnh thoảng search hiển thị giá hoặc tên cũ dù SQL đã đúng;
- cùng một `ProductId` có thể xuất hiện nhiều jobs gần nhau khi editor/import process update liên tục;
- khi scale từ 2 lên 8 application instances, lỗi stale overwrite xuất hiện nhiều hơn;
- Elasticsearch indexing latency tăng mạnh trong giờ import catalog;
- CPU Elasticsearch tăng và search latency cũng tăng khi worker backlog cao;
- logs chỉ cho biết `ProductId`, không có source version/job identity;
- team thêm `Refresh.WaitFor` vào mọi index request vì muốn document “thấy ngay”, nhưng throughput giảm rõ rệt;
- một developer đề xuất retry toàn bộ failed batch mà không phân biệt item nào đã thành công.

Mỗi row `Product` có `Version` tăng đơn điệu sau mỗi business update. `SearchIndexJobs` lưu snapshot của dữ liệu tại thời điểm event được tạo.

## Đoạn code cần review

```csharp
public sealed class ProductSearchIndexer : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ElasticsearchClient _elastic;
    private readonly ILogger<ProductSearchIndexer> _logger;

    public ProductSearchIndexer(
        IServiceScopeFactory scopeFactory,
        ElasticsearchClient elastic,
        ILogger<ProductSearchIndexer> logger)
    {
        _scopeFactory = scopeFactory;
        _elastic = elastic;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var jobs = await db.SearchIndexJobs
                .Where(x => x.ProcessedAt == null)
                .OrderBy(x => x.CreatedAt)
                .Take(500)
                .ToListAsync(stoppingToken);

            if (jobs.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
                continue;
            }

            var tasks = jobs.Select(async job =>
            {
                var document = JsonSerializer.Deserialize<ProductSearchDocument>(
                    job.Payload)!;

                var response = await _elastic.IndexAsync(
                    document,
                    i => i
                        .Index("products")
                        .Id(document.ProductId)
                        .Refresh(Refresh.WaitFor),
                    stoppingToken);

                if (!response.IsValidResponse)
                {
                    throw new InvalidOperationException(
                        $"Index failed for {document.ProductId}");
                }

                job.ProcessedAt = DateTimeOffset.UtcNow;

                _logger.LogInformation(
                    "Indexed product {ProductId}",
                    document.ProductId);
            });

            await Task.WhenAll(tasks);
            await db.SaveChangesAsync(stoppingToken);
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, concurrency, reliability và performance trong worker.
2. Giải thích cách một snapshot cũ có thể overwrite document mới hơn trong Elasticsearch dù jobs được query bằng `OrderBy(CreatedAt)`.
3. Phân tích behavior khi nhiều application instances cùng đọc các rows `ProcessedAt == null`.
4. Review cách `DbContext` và các tracked entities đang được dùng bên trong `Task.WhenAll`.
5. Đánh giá việc đặt `Refresh.WaitFor` trên mọi index request.
6. Đề xuất cơ chế bảo vệ khỏi stale overwrite dựa trên source version hoặc canonical state.
7. Đề xuất cách claim/process jobs an toàn hơn khi scale-out.
8. Giải thích retry strategy khi một phần batch thành công và một phần thất bại.
9. Nêu tests và telemetry cần có để chứng minh search index không regresses về version cũ.

## Kết quả code review tham khảo

### Critical — Snapshot cũ có thể overwrite document mới hơn

**Vấn đề:** Mỗi job index toàn bộ snapshot vào cùng `_id = ProductId` nhưng không có cơ chế version guard.

**Tại sao xảy ra:** `OrderBy(CreatedAt)` chỉ sắp xếp rows tại thời điểm query. Khi nhiều jobs chạy song song hoặc nhiều instances cùng xử lý, completion order không còn bằng creation order. Job version 43 có thể ghi trước, sau đó job version 42 hoàn tất muộn hơn và overwrite document bằng state cũ.

**Ảnh hưởng production:** Search có thể “quay ngược thời gian”: giá, tên, availability hoặc metadata mới bị thay bằng snapshot cũ. Đây là correctness bug, không chỉ là eventual consistency bình thường.

**Cách sửa:** Mỗi update cần gắn source version tăng đơn điệu và Elasticsearch write phải từ chối version cũ hơn, hoặc indexer phải đọc canonical latest state từ SQL thay vì tin snapshot cũ. Nếu dùng source version làm concurrency contract, implementation cần chọn API/versioning semantics phù hợp với Elasticsearch client/version đang chạy và verify conflict behavior bằng integration test. Một lựa chọn đơn giản khác là coalesce jobs theo `ProductId`, đọc current row từ SQL và index current state; tuy nhiên delete/tombstone và races vẫn phải được thiết kế rõ.

### Critical — Nhiều workers có thể claim cùng một job

**Vấn đề:** Query `ProcessedAt == null` chỉ đọc rows, không có atomic claim/lease.

**Tại sao xảy ra:** Hai instances có thể chạy cùng lúc, cùng thấy một set rows chưa processed và cùng bắt đầu xử lý.

**Ảnh hưởng production:** Duplicate indexing, tăng cluster load, log noise và tăng xác suất out-of-order writes. Nếu job có side effects khác trong tương lai, duplicate có thể nghiêm trọng hơn.

**Cách sửa:** Claim jobs bằng database-enforced state transition, ví dụ `Pending → Processing` với `WorkerId`/`LeaseUntil`, thực hiện atomic update có concurrency condition. Hoặc dùng queue/message broker nếu system đã có và complexity hợp lý. Không dùng in-memory lock vì không bảo vệ multi-instance.

### High — `DbContext` và tracked entities bị chạm từ nhiều tasks song song

**Vấn đề:** `jobs` là tracked entities của cùng một `DbContext`; mỗi task đồng thời gán `job.ProcessedAt`.

**Tại sao xảy ra:** `Task.WhenAll` tạo concurrent access vào objects/change tracking state thuộc cùng unit of work. EF Core `DbContext` không nên được dùng cho parallel operations.

**Ảnh hưởng production:** Behavior khó reason, có thể phát sinh concurrency exceptions ở những phiên bản code mở rộng thêm DB calls trong task, và làm transaction/state ownership mơ hồ.

**Cách sửa:** Tách phases. Claim jobs trong DB trước; process external work với DTO immutable ngoài `DbContext`; sau đó persist outcome bằng short-lived context/atomic update theo từng batch hoặc item. Nếu cần parallelism, mỗi parallel unit phải có state ownership rõ ràng, không share một `DbContext`.

### High — Mark `ProcessedAt` sau external write tạo at-least-once behavior nhưng code chưa thiết kế idempotency

**Vấn đề:** Elasticsearch có thể index thành công rồi process chết trước `SaveChangesAsync`.

**Tại sao xảy ra:** SQL job state và Elasticsearch write không nằm trong một distributed transaction.

**Ảnh hưởng production:** Job sẽ được thực thi lại. Duplicate cùng version có thể harmless nếu indexing idempotent, nhưng nếu request dùng snapshot khác/version semantics sai thì retry có thể gây stale overwrite hoặc load thừa.

**Cách sửa:** Chấp nhận at-least-once và thiết kế write idempotent/version-aware. Job state machine cần retry count, last error, next attempt và poison/dead-letter policy khi lỗi không transient.

### High — `Refresh.WaitFor` trên từng document làm giảm throughput không cần thiết

**Vấn đề:** Mỗi `IndexAsync` chờ document trở nên visible với search trước khi hoàn thành.

**Tại sao xảy ra:** Team đang dùng search visibility như một per-document synchronization primitive dù business đã chấp nhận eventual consistency vài giây.

**Ảnh hưởng production:** Worker latency tăng, concurrent pending operations nhiều hơn và refresh pressure có thể ảnh hưởng cả indexing/search performance. Khi import lớn, throughput giảm và backlog tăng.

**Cách sửa:** Nếu business không cần read-your-write cho từng document, để normal refresh policy xử lý visibility. Nếu một workflow cụ thể cần chắc chắn search thấy thay đổi sau write, `refresh=wait_for` có thể dùng có chọn lọc. Không gọi explicit refresh hay force visibility cho mọi event nếu không có requirement.

### High — Unbounded per-batch parallelism tạo burst 500 index requests

**Vấn đề:** `Take(500)` sau đó `Task.WhenAll` toàn bộ 500 jobs.

**Tại sao xảy ra:** Batch size bị đồng nhất với concurrency level.

**Ảnh hưởng production:** Burst network/CPU, tăng memory, connection pressure và tạo load spike lên Elasticsearch. Khi cluster chậm, nhiều operations giữ tài nguyên lâu hơn và retry storm dễ xảy ra.

**Cách sửa:** Tách batch size khỏi concurrency. Dùng bounded concurrency, ví dụ `Parallel.ForEachAsync` với `MaxDegreeOfParallelism` hoặc channel/worker pool. Chọn mức dựa trên load test và cluster metrics. Với volume lớn, Bulk API có thể giảm overhead nhưng phải xử lý per-item result.

### High — Failure của một task ngăn toàn batch được đánh dấu, kể cả items đã index thành công

**Vấn đề:** Nếu một task throw, `Task.WhenAll` throw trước `SaveChangesAsync`.

**Tại sao xảy ra:** Outcome toàn batch bị model như all-or-nothing trong khi external writes đã thực tế xảy ra từng item.

**Ảnh hưởng production:** Hàng trăm items đã index thành công có thể bị retry lại. Dưới persistent bad item, cùng batch có thể quay vòng nhiều lần.

**Cách sửa:** Track result theo item. Với Bulk API, luôn inspect từng item vì HTTP-level success không đồng nghĩa mọi item thành công. Persist successes, schedule retry cho transient failures, và isolate poison/non-retryable items.

### Medium — Deserialize payload bằng null-forgiving operator và thiếu schema/version validation

**Vấn đề:** `Deserialize(...)!` giả định payload luôn hợp lệ và đúng contract.

**Tại sao xảy ra:** Durable job có thể sống lâu hơn code version tạo nó.

**Ảnh hưởng production:** Malformed/old payload có thể crash loop hoặc bị retry vô hạn.

**Cách sửa:** Version event schema, validate required fields và phân loại deserialization failure là non-transient để chuyển sang failed/dead-letter state có diagnostic metadata an toàn.

### Medium — Không có per-product ordering/coalescing strategy

**Vấn đề:** Hệ thống đối xử 20 updates liên tiếp của cùng product như 20 independent writes dù search chỉ cần latest state.

**Tại sao xảy ra:** Job model mirror từng change event thay vì use case của projection.

**Ảnh hưởng production:** Lãng phí indexing capacity và tăng xác suất reorder.

**Cách sửa:** Nếu audit/event history không cần được phản ánh từng bước trong Elasticsearch, coalesce nhiều pending jobs cùng product về latest version hoặc đọc latest state từ SQL khi indexing. Nếu phải preserve mọi transition, cần explicit ordering/partitioning strategy theo aggregate.

### Medium — Logs thiếu job identity, version và retry context

**Vấn đề:** Log chỉ có `ProductId`.

**Tại sao xảy ra:** Projection pipeline chưa được instrument như distributed asynchronous workflow.

**Ảnh hưởng production:** Không thể chứng minh stale overwrite do version nào, worker nào hay retry nào.

**Cách sửa:** Structured logs/traces nên có `JobId`, `ProductId`, source `Version`, worker instance, attempt, claim timestamp, Elasticsearch result/status và latency. Không log toàn payload nếu có dữ liệu nhạy cảm.

## Phiên bản đề xuất

Một hướng đơn giản là biến job thành **trigger để rebuild latest projection** thay vì source of truth cho snapshot. Worker claim job atomically, đọc latest product từ SQL và index latest version. Đoạn dưới minh họa processing boundary; phần atomic claim phụ thuộc database strategy cụ thể và nên được implement bằng conditional update/lease thay vì query rồi sửa trong memory.

```csharp
public sealed record ClaimedSearchJob(
    long JobId,
    int ProductId,
    long RequestedVersion);

public sealed class ProductSearchIndexer : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ElasticsearchClient _elastic;
    private readonly ILogger<ProductSearchIndexer> _logger;

    public ProductSearchIndexer(
        IServiceScopeFactory scopeFactory,
        ElasticsearchClient elastic,
        ILogger<ProductSearchIndexer> logger)
    {
        _scopeFactory = scopeFactory;
        _elastic = elastic;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var jobs = await ClaimJobsAsync(
                batchSize: 100,
                leaseDuration: TimeSpan.FromMinutes(2),
                stoppingToken);

            if (jobs.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
                continue;
            }

            await Parallel.ForEachAsync(
                jobs,
                new ParallelOptions
                {
                    MaxDegreeOfParallelism = 8,
                    CancellationToken = stoppingToken
                },
                async (job, ct) =>
                {
                    try
                    {
                        await IndexLatestAsync(job, ct);
                        await MarkCompletedAsync(job.JobId, ct);
                    }
                    catch (OperationCanceledException) when (ct.IsCancellationRequested)
                    {
                        throw;
                    }
                    catch (Exception ex)
                    {
                        await MarkFailedOrRetryAsync(job.JobId, ex, ct);
                    }
                });
        }
    }

    private async Task IndexLatestAsync(
        ClaimedSearchJob job,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var product = await db.Products
            .AsNoTracking()
            .Where(x => x.Id == job.ProductId)
            .Select(x => new ProductSearchDocument
            {
                ProductId = x.Id,
                Name = x.Name,
                Price = x.Price,
                Category = x.Category.Name,
                SourceVersion = x.Version
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (product is null)
        {
            await DeleteProjectionSafelyAsync(job.ProductId, cancellationToken);
            return;
        }

        var response = await _elastic.IndexAsync(
            product,
            i => i
                .Index("products")
                .Id(product.ProductId),
            cancellationToken);

        if (!response.IsValidResponse)
        {
            throw new InvalidOperationException(
                $"Elasticsearch indexing failed for job {job.JobId}.");
        }

        _logger.LogInformation(
            "Indexed product {ProductId} at source version {SourceVersion} from job {JobId}",
            product.ProductId,
            product.SourceVersion,
            job.JobId);
    }
}
```

Đoạn trên giảm stale snapshot risk vì mỗi job re-project **latest canonical state** tại thời điểm xử lý. Tuy nhiên nếu hai workers cùng index cùng product và SQL thay đổi giữa hai reads, vẫn cần xác định ordering guarantee mong muốn. Với yêu cầu chặt hơn, nên dùng source `Version` làm concurrency guard tại Elasticsearch để write version thấp không thể thay write version cao. Cơ chế cụ thể phải được verify theo Elasticsearch/client version đang dùng; không nên tự invent version semantics.

Một alternative là dùng Bulk API với batches vừa phải. Bulk giúp giảm request overhead nhưng response phải được kiểm tra từng item. Nếu 97/100 items thành công, không được retry mù cả 100 nếu việc đó có thể tạo correctness/load problem.

Delete cũng cần first-class design. Nếu product bị xóa khỏi SQL trước khi worker đọc, projection cần tombstone hoặc delete job đủ thông tin để xóa document; không được coi `null` đơn giản như transient failure.

## Giải thích thiết kế sau khi sửa

Thiết kế mới coi Elasticsearch là **derived projection**, không phải authority. SQL quyết định state hiện tại. Job chỉ nói “projection của product này cần reconcile”. Điều này cho phép coalesce duplicate jobs và làm retry an toàn hơn.

Atomic claim/lease giải quyết competition giữa nhiều instances. Lease có expiry để job không bị kẹt vĩnh viễn nếu worker crash. Khi lease hết, worker khác có thể retry.

Bounded concurrency bảo vệ cả application và Elasticsearch khỏi burst. Con số `8` chỉ là minh họa; production phải dựa trên throughput, bulk size, Elasticsearch CPU, indexing latency và search SLO.

Không đặt `Refresh.WaitFor` mặc định vì business đã chấp nhận eventual consistency. Visibility delay là một phần contract. Nếu UI admin có flow “save rồi search ngay”, có thể dùng direct SQL read cho confirmation hoặc selective wait-for behavior thay vì bắt toàn bộ ingestion pipeline trả chi phí đó.

## Trade-offs

Đọc latest product từ SQL cho mỗi indexing job tăng DB reads. Nếu update rate rất cao, có thể batch/coalesce IDs và query nhiều products một lần. Nếu payload snapshot đã đủ và source versioning được enforce chính xác ở Elasticsearch, dùng snapshot có thể giảm DB read nhưng contract phức tạp hơn.

Lease table/state machine tăng complexity so với simple polling. Nếu hệ thống đã có Azure Service Bus và vận hành tốt, chuyển trigger sang queue có thể hợp lý; tuy nhiên queue vẫn không loại bỏ duplicate/out-of-order business semantics, nên version/idempotency vẫn cần.

Bulk indexing tăng throughput nhưng làm error handling tinh vi hơn vì mỗi item có outcome riêng. Batch quá lớn cũng tăng memory và retry blast radius.

Strong ordering theo từng `ProductId` có thể giảm parallelism. Nếu chỉ cần final state đúng, version guard/coalescing thường đơn giản hơn việc xây per-key distributed ordering tuyệt đối.

## Cách kiểm thử

1. **Concurrency integration test:** tạo version 42 và 43 cho cùng product, cố tình delay version 42 để nó hoàn tất sau; xác minh search cuối cùng không thể quay về version 42.
2. **Multi-worker test:** chạy nhiều worker instances cùng claim một pool jobs; xác minh một active lease chỉ thuộc một worker và abandoned lease có thể recovery.
3. **Failure-path test:** index thành công rồi mô phỏng crash trước khi mark completed; retry phải giữ final projection đúng và không tạo stale regression.
4. **Load test:** import hàng chục nghìn updates, so sánh bounded concurrency/bulk strategy với per-item `Refresh.WaitFor`; đo indexing throughput, search p95/p99 và cluster CPU.
5. **Partial-failure test:** một bulk batch có một malformed/non-retryable item và một transient item; xác minh success không bị retry mù, transient được backoff và poison item được isolate.

## Quan sát trong production

Theo dõi:

- pending/processing/failed job count;
- age của oldest pending job;
- attempts và lease-expiration count;
- `ProductId` + source version + indexed version;
- count của rejected stale writes/version conflicts nếu dùng version guard;
- Elasticsearch indexing latency/error rate;
- Bulk API per-item failures;
- refresh/segment/indexing pressure và Elasticsearch CPU;
- search latency p50/p95/p99;
- divergence sampling giữa SQL version và Elasticsearch `SourceVersion`;
- correlation từ product update → job → indexing attempt → searchable version.

Alert khi oldest job age vượt freshness SLO, failed jobs tăng, hoặc reconciliation phát hiện Elasticsearch version thấp hơn SQL trong thời gian dài hơn eventual-consistency budget.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL có 10 updates/giây cho cùng một hot product, bạn chọn coalescing, per-key ordering hay external/version guard dựa trên tiêu chí nào?
2. Nếu business đổi requirement thành “save xong search phải thấy ngay trong cùng request”, bạn có giữ architecture asynchronous hiện tại không?
3. Khi nào bạn sẽ chuyển polling table sang Azure Service Bus, và những correctness problems nào vẫn không tự biến mất sau khi chuyển?

# Code Review Challenge 2 — Octopus rollback đưa binary cũ lên IIS nhưng database đã migrate khiến production lỗi nặng hơn

**Chủ đề:** Octopus Deploy, IIS, Windows Server, .NET deployment, immutable artifacts, database migration, rollback/roll-forward, sensitive variables, health checks, release safety, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một enterprise management portal đang chạy ASP.NET Core trên IIS/Windows Server. CI build package, sau đó Octopus Deploy triển khai sang hai web servers sau load balancer.

Release mới thêm một cột bắt buộc và thay đổi cách application đọc dữ liệu. Team hiện deploy bằng một custom PowerShell step. Khi release gần đây gặp lỗi application, operator chọn redeploy release trước để rollback.

Production sau đó xuất hiện outage dài hơn:

- binary cũ không tương thích với schema database mới;
- một server đã có file version mới, server còn lại có mix file cũ/mới trong vài giây;
- một request đang chạy bị terminate giữa chừng khi App Pool recycle;
- health check chỉ kiểm tra HTTP `200` của trang root;
- script in connection string ra deployment log để debug;
- package được lấy từ một share bằng tên `EmployeePortal-latest.zip` thay vì artifact gắn cố định với release;
- database migration chạy lại mỗi lần deploy hoặc rollback;
- operator không biết rollback code có nên rollback database hay không.

Business ưu tiên availability và auditability. Deployment phải có khả năng xác định chính xác artifact nào đang chạy trên từng target. Database có dữ liệu người dùng mới được tạo sau deployment nên restore database tùy tiện có thể làm mất dữ liệu.

## Đoạn code cần review

```powershell
$sitePath = "C:\inetpub\wwwroot\EmployeePortal"
$packagePath = "\\buildshare\releases\EmployeePortal-latest.zip"
$db = $OctopusParameters["ConnectionStrings.MainDb"]

Write-Host "Deploying with database: $db"

Write-Host "Running database migration"
& "C:\tools\EmployeePortal.DbMigrator.exe" `
    --connection "$db"

Write-Host "Extracting application package"
Expand-Archive `
    -Path $packagePath `
    -DestinationPath $sitePath `
    -Force

Import-Module WebAdministration
Restart-WebAppPool "EmployeePortal"

$response = Invoke-WebRequest `
    -Uri "https://employee.company.internal/" `
    -UseBasicParsing

if ($response.StatusCode -ne 200) {
    throw "Deployment failed"
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề deployment safety, correctness, security và rollback trong script.
2. Giải thích vì sao redeploy release cũ không đồng nghĩa database tự quay về schema cũ an toàn.
3. Review cách artifact được chọn và giải thích vì sao `latest.zip` phá release reproducibility.
4. Đánh giá cách script ghi sensitive configuration ra logs.
5. Phân tích rủi ro khi extract trực tiếp vào live IIS directory.
6. Đề xuất release process an toàn hơn cho hai web servers sau load balancer.
7. Thiết kế database migration theo hướng backward-compatible/expand-contract khi cần rolling deployment.
8. Giải thích khi nào rollback binary hợp lý và khi nào roll-forward an toàn hơn.
9. Đề xuất health validation, smoke tests, rollback criteria và telemetry.

## Câu hỏi gợi mở

1. Một Octopus release nên tham chiếu artifact immutable hay một filename mutable như `latest.zip`?
2. Nếu migration thêm/đổi schema mà old binary không hiểu, redeploy binary cũ có thật sự là rollback hoàn chỉnh không?
3. `Expand-Archive -Force` vào thư mục đang serve request có thể để user quan sát trạng thái file nào trong lúc extraction?
4. HTTP `200` ở `/` có chứng minh database/API dependencies và critical user flow hoạt động không?
5. Nếu production đã ghi dữ liệu mới theo schema mới trong 30 phút, database restore về trước release gây hậu quả gì?

## Gợi ý

### Gợi ý 1

Rủi ro chính là coi deployment như **copy file + restart**, trong khi release thực tế là một state transition gồm artifact, application processes, configuration, schema và traffic.

### Gợi ý 2

Tách rõ **application rollback** khỏi **database rollback**. Với database có state mới phát sinh, “quay về bản backup cũ” có thể tạo data loss và thường không phải default rollback strategy.

## Kết quả code review tham khảo

### Critical — Connection string/credential bị ghi vào deployment logs

**Vấn đề:** `Write-Host "Deploying with database: $db"` xuất toàn bộ connection string.

**Tại sao xảy ra:** Sensitive variable bị dùng như diagnostic text thông thường.

**Ảnh hưởng production:** Secret có thể tồn tại trong Octopus task log, export, support screenshot hoặc log retention dài hạn. Đây là credential disclosure.

**Cách sửa:** Mark variable là sensitive trong deployment platform và quan trọng hơn là **không đưa giá trị secret vào output**. Chỉ log logical target/database name không chứa credential hoặc một redacted identifier an toàn.

### Critical — Migration và old binary không có compatibility contract

**Vấn đề:** Migration chạy trước deploy, nhưng rollback chỉ redeploy code cũ mà không chứng minh code cũ tương thích schema mới.

**Tại sao xảy ra:** Database schema được xem như artifact có thể đảo ngược đồng bộ với binary, trong khi database chứa state sống và có thể đã nhận dữ liệu theo schema mới.

**Ảnh hưởng production:** Rollback code có thể tạo outage mới, query lỗi hoặc corrupt semantics. Restore database có thể làm mất dữ liệu phát sinh sau deployment.

**Cách sửa:** Thiết kế schema changes backward-compatible khi cần rolling deploy/rollback. Dùng expand-contract: bước đầu thêm schema additive/null-compatible, deploy code hiểu cả old/new, migrate/backfill nếu cần, sau đó mới contract ở release sau khi old code không còn. Với breaking migration, rollback strategy phải được thiết kế trước và thường ưu tiên roll-forward fix thay vì restore mù.

### High — `latest.zip` làm release không reproducible

**Vấn đề:** Script lấy artifact theo tên mutable trên network share.

**Tại sao xảy ra:** Deployment không dùng package/version được snapshot cùng release.

**Ảnh hưởng production:** Cùng một release number có thể deploy binary khác nhau theo thời điểm. Audit, rollback và root-cause analysis mất độ tin cậy.

**Cách sửa:** CI tạo versioned immutable package. Octopus release tham chiếu đúng package version/artifacts tại lúc release creation. Promote cùng artifact qua environments, không rebuild/re-point bằng `latest`.

### High — Extract trực tiếp vào live site có thể tạo mixed-version file set

**Vấn đề:** `Expand-Archive -Force` ghi file từng phần vào directory mà IIS đang serve.

**Tại sao xảy ra:** Deployment target directory đồng thời là live runtime directory.

**Ảnh hưởng production:** Request có thể load assembly/static/config từ hai versions khác nhau tùy timing. File lock có thể làm deploy partial. Với nhiều servers, trạng thái càng khó kiểm soát.

**Cách sửa:** Dùng deployment mechanism hỗ trợ application offline/drain hoặc versioned staging directory rồi switch có kiểm soát. Với ASP.NET Core trên IIS có thể dùng `app_offline.htm`/Web Deploy/Octopus IIS deployment patterns phù hợp. Quan trọng là traffic phải được drain khỏi target trước khi thay file và chỉ đưa target trở lại load balancer sau validation.

### High — Database migration chạy lại cả khi rollback/redeploy mà không phân biệt deployment mode

**Vấn đề:** Script luôn gọi migrator.

**Tại sao xảy ra:** Deployment process không phân loại deploy mới, redeploy cùng release và rollback release cũ.

**Ảnh hưởng production:** Rollback có thể cố chạy migration package cũ trên schema mới, gây failure hoặc thao tác không mong muốn. Redeploy cũng có thể rerun non-idempotent migration.

**Cách sửa:** Migration phải idempotent/version-aware và deployment process phải có explicit policy về thời điểm chạy. Không mặc định rerun destructive DB step khi redeploy/rollback. Với Octopus, deployment mode/step conditions hoặc runbook riêng có thể được dùng theo process design, nhưng correctness phải đến từ migration strategy chứ không chỉ condition expression.

### High — Restart App Pool đột ngột có thể cắt in-flight work

**Vấn đề:** Script restart ngay sau extraction mà không có drain/graceful handling.

**Tại sao xảy ra:** Không có coordination với load balancer và application shutdown behavior.

**Ảnh hưởng production:** Request đang xử lý có thể fail giữa chừng; background operations có thể bị duplicate hoặc partial nếu cancellation/shutdown không được thiết kế.

**Cách sửa:** Deploy từng target: remove/drain target khỏi traffic, chờ bounded in-flight drain, stop/offline app khi cần, deploy, start, warm up, health-check, rồi rejoin. Sau đó mới chuyển target tiếp theo. Background jobs cần graceful shutdown/idempotency riêng.

### High — Root `200 OK` là validation quá yếu

**Vấn đề:** Script chỉ kiểm tra homepage trả `200`.

**Tại sao xảy ra:** Availability của một URL được đồng nhất với release correctness.

**Ảnh hưởng production:** App có thể trả `200` nhưng database migration sai, authentication lỗi, critical API fail hoặc dependency config sai.

**Cách sửa:** Có liveness/readiness/health endpoint phù hợp, cộng với smoke test các critical paths có side effects an toàn. Validate version endpoint/build SHA để chắc target chạy đúng artifact. Không biến health check thành full destructive E2E flow.

### Medium — Không verify package integrity/version trước deploy

**Vấn đề:** Script không kiểm tra package version, checksum/signature hoặc release metadata.

**Tại sao xảy ra:** Artifact discovery dựa vào đường dẫn share.

**Ảnh hưởng production:** Có thể deploy nhầm/corrupt package và khó truy vết.

**Cách sửa:** Dùng Octopus package feed/release snapshot hoặc artifact source có immutable version. Log package ID/version/hash an toàn trong deployment telemetry.

### Medium — Không có explicit rollback/roll-forward decision gate

**Vấn đề:** Operator có thể redeploy release trước theo phản xạ mà không kiểm tra schema/data compatibility.

**Tại sao xảy ra:** Runbook không định nghĩa conditions để rollback an toàn.

**Ảnh hưởng production:** Incident response có thể khuếch đại outage.

**Cách sửa:** Runbook/checklist nên ghi rõ: artifact compatibility, schema compatibility, data written since release, downstream contract changes, feature flags và rollback window. Nếu conditions không thỏa, ưu tiên roll-forward hotfix hoặc feature-disable.

### Medium — Không validate configuration scope theo environment/target

**Vấn đề:** Script lấy một variable name nhưng không có guard chống scoping nhầm environment/tenant/target.

**Tại sao xảy ra:** Configuration được xem là opaque string.

**Ảnh hưởng production:** Sai connection string có thể deploy production binary trỏ nhầm database.

**Cách sửa:** Scope variables đúng environment/target, dùng sensitive variables cho secrets, và thêm non-secret guardrails như expected environment name/database server identifier trước destructive migration.

### Medium — Thiếu deployment telemetry/version marker ở runtime

**Vấn đề:** Sau deploy không có cách chắc chắn từ application telemetry biết server nào chạy release nào.

**Tại sao xảy ra:** Release metadata không được propagate vào logs/health endpoint.

**Ảnh hưởng production:** Khi hai targets lệch version, support khó xác định request đã vào server nào.

**Cách sửa:** Expose safe build/release metadata qua health/version endpoint và structured logs. Application Insights/Kibana nên có instance ID + release version + commit SHA trên request traces.

## Phiên bản đề xuất

Thay vì custom script copy `latest.zip`, process nên dùng artifact version cố định của release và triển khai từng target có drain/health gate. Một pseudo-PowerShell orchestration có thể như sau:

```powershell
$releaseVersion = $OctopusParameters["Octopus.Release.Number"]
$packagePath = $OctopusParameters["Octopus.Action.Package.PackageFilePath"]
$sitePath = "C:\inetpub\wwwroot\EmployeePortal"
$stagingPath = "C:\deploy\EmployeePortal\$releaseVersion"

Write-Host "Deploying EmployeePortal release $releaseVersion"

if (-not (Test-Path $packagePath)) {
    throw "Release package was not provided by the deployment process."
}

New-Item -ItemType Directory -Force -Path $stagingPath | Out-Null
Expand-Archive -Path $packagePath -DestinationPath $stagingPath -Force

# Migration is intentionally NOT executed blindly here.
# It should be a separately controlled, version-aware deployment step.

# Put this target out of rotation before replacing the live application.
& "C:\deploy\Drain-EmployeePortalTarget.ps1"

$appOffline = Join-Path $sitePath "app_offline.htm"
"Deployment in progress" | Set-Content $appOffline

try {
    & "C:\deploy\Replace-EmployeePortalFiles.ps1" `
        -Source $stagingPath `
        -Destination $sitePath

    Import-Module WebAdministration
    Restart-WebAppPool "EmployeePortal"

    & "C:\deploy\Wait-ForEmployeePortalReady.ps1" `
        -ExpectedRelease $releaseVersion `
        -TimeoutSeconds 120

    & "C:\deploy\SmokeTest-EmployeePortal.ps1"
}
finally {
    Remove-Item $appOffline -ErrorAction SilentlyContinue
}

& "C:\deploy\Return-EmployeePortalTargetToRotation.ps1"
```

Đây là pseudo-code để thể hiện **deployment phases**, không phải template nên copy nguyên vào production. Trong thực tế nên tận dụng built-in Octopus deployment/IIS/package capabilities thay vì tự viết toàn bộ orchestration nếu platform đã hỗ trợ đúng requirement.

Database nên có deployment step riêng. Ví dụ release N có thể:

1. chạy additive migration (`NewColumn` nullable hoặc có safe default);
2. deploy application N hỗ trợ cả old/new representation;
3. backfill dữ liệu có kiểm soát và telemetry;
4. chuyển read path sang schema mới;
5. ở release sau, khi không còn old binaries, mới remove old column/constraint theo contract step.

Nếu deployment N gặp lỗi application sau additive migration, redeploy N-1 có thể an toàn **nếu** N-1 vẫn tương thích schema đã expand. Nếu migration breaking/destructive đã chạy, không được giả định rollback code là an toàn. Khi production đã ghi dữ liệu mới, restore backup chỉ nên là incident decision có đánh giá data loss/reconciliation rõ ràng.

Octopus có khái niệm release snapshot và hỗ trợ redeploy release trước, nhưng điều đó không tự đảo các external/stateful changes một cách an toàn. Rollback success vẫn phụ thuộc contract giữa application, database và dependencies.

## Giải thích thiết kế sau khi sửa

Artifact identity là nền tảng của release reproducibility. Một release phải biết chính xác package version nào được deploy, không phụ thuộc file mutable trên share.

Drain-deploy-validate-return-to-rotation giúp mỗi target chuyển state có kiểm soát. Với hai web servers, chỉ deploy target thứ hai khi target thứ nhất đã healthy, nhờ đó giữ capacity nếu traffic headroom cho phép.

Database migration được tách khỏi file deployment vì lifecycle khác nhau. Application binary là gần như stateless/reversible; database chứa user state và thường không thể rollback bằng cách “copy version cũ”.

Release metadata trong logs/health giúp incident investigation xác định chính xác instance/version nào tạo failure.

## Trade-offs

Rolling target deployment lâu hơn copy file trực tiếp và cần load balancer/drain integration. Đổi lại blast radius nhỏ hơn và rollback decision rõ hơn.

`app_offline.htm` tạo downtime cho một target; nếu chỉ có một server thì cần maintenance strategy khác hoặc slot/blue-green-style capacity. Với hai servers sau load balancer, drain từng server thường đơn giản hơn full blue-green nếu SLO cho phép.

Expand-contract kéo database change qua nhiều releases và yêu cầu discipline, nhưng đổi lại hỗ trợ rolling deploy/rollback tốt hơn. Với hệ thống nhỏ có maintenance window chấp nhận được, stop-the-world migration có thể đơn giản hơn; decision phải theo availability requirement.

Giữ database backup là cần thiết nhưng backup không đồng nghĩa rollback button. Restore có RPO/RTO và data-loss implications, đặc biệt sau khi users đã ghi dữ liệu mới.

Built-in Octopus steps giảm custom code nhưng vẫn cần engineering judgment về schema compatibility, health criteria và secrets. Tooling không tự giải quyết contract design.

## Cách kiểm thử

1. **Deployment validation:** tạo release và xác minh cùng release luôn dùng đúng package version/hash ở Test, Staging và Production; không tham chiếu `latest`.
2. **Rolling deployment test:** dưới representative traffic, drain một server, deploy, warm/health check rồi rejoin; xác minh request error rate không spike và server còn lại giữ capacity.
3. **Rollback compatibility test:** chạy old binary với expanded schema và new binary với transitional schema; xác minh rollback window thật sự tồn tại trước production.
4. **Migration failure-path test:** làm migrator fail giữa deployment; xác minh application targets không bị đưa vào mixed incompatible state và operator có clear recovery path.
5. **Security test:** kiểm tra task logs/artifacts không chứa connection string/password; sensitive variables không bị echo bởi script hay error output.

## Quan sát trong production

Theo dõi:

- release/version/commit SHA theo từng IIS instance;
- deployment start/end, target drain/rejoin timestamps;
- health/smoke-test result theo target;
- request p50/p95/p99 và 5xx trong deployment window;
- App Pool recycle/process restart count;
- active/in-flight requests trước shutdown;
- migration version, duration, result và lock/blocking metrics;
- database errors theo release version;
- config validation failures;
- rollback vs roll-forward incident decisions và outcome;
- Application Insights/Kibana correlation gồm instance ID + release version.

Alert deployment nên dựa trên SLO signal như 5xx, latency, dependency failures và readiness chứ không chỉ “step completed successfully”.

## Câu hỏi phỏng vấn mở rộng

1. Nếu migration đã thêm nullable column nhưng new code lỗi, bạn cần kiểm tra điều gì trước khi redeploy old release?
2. Nếu schema change bắt buộc phải destructive trong cùng ngày, bạn thiết kế maintenance/backup/verification và rollback decision như thế nào?
3. Khi nào blue-green deployment đáng chi phí hơn rolling deployment từng IIS target trong hệ thống này?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Elasticsearch là derived projection thì correctness phải dựa trên source-of-truth version/state, không dựa vào assumption rằng async jobs sẽ hoàn tất theo thứ tự tạo.
- Scale-out worker cần atomic claim/lease hoặc tương đương; polling `ProcessedAt == null` không tạo ownership giữa nhiều instances.
- Retry và duplicate processing chỉ an toàn khi write được thiết kế idempotent/version-aware; external write và SQL job state không có distributed atomicity mặc định.
- `Refresh.WaitFor` giải quyết visibility semantics, không giải quyết ordering/versioning; dùng nó trên mọi write có thể làm giảm indexing throughput.
- Deployment rollback của stateless binaries khác hoàn toàn database rollback. Release safety cần artifact immutability, schema compatibility, drain/health gates và explicit rollback/roll-forward policy.
- Với stateful database changes, expand-contract thường tạo rollback window an toàn hơn việc cố reverse migration sau khi production đã nhận dữ liệu mới.

## Mẫu tư duy cần nhớ

- Ordering assumption phải được enforce bằng version/ownership, không dựa vào timing.
- Thiết kế retry cùng với idempotency và partial-failure handling.
- Tách search visibility khỏi search correctness.
- Treat deployment như state transition, không chỉ là copy files.
- Roll back code chỉ khi data/schema contracts vẫn tương thích; nếu không, cân nhắc roll-forward.
