# Code Review Challenge 1 — Đồng bộ CRM làm cạn connection và khuếch đại lỗi dependency

**Chủ đề:** C#/.NET, HttpClient, async/concurrency, cancellation, resilience, external API integration, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một ASP.NET Core API có endpoint đồng bộ tối đa 2.000 customer records sang CRM bên thứ ba. Production chạy nhiều instances. CRM bình thường phản hồi 100–300 ms nhưng đôi lúc chậm 5–15 giây hoặc trả `429`/`503`.

Khi một vài người dùng chạy sync cùng lúc, API p99 tăng mạnh, số outbound connections tăng, một số request khác tới cùng CRM cũng timeout. Sau khi client hủy request, backend đôi lúc vẫn tiếp tục gửi hàng trăm request. Team đề xuất tăng timeout lên 2 phút để “giảm lỗi”.

CRM hỗ trợ idempotency key cho mỗi update nhưng không có bulk endpoint. Requirement hiện tại chưa nói rõ HTTP request có cần chờ toàn bộ 2.000 records hoàn tất hay không.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/crm")]
public sealed class CrmSyncController : ControllerBase
{
    private readonly IConfiguration _configuration;
    private readonly ILogger<CrmSyncController> _logger;

    public CrmSyncController(
        IConfiguration configuration,
        ILogger<CrmSyncController> logger)
    {
        _configuration = configuration;
        _logger = logger;
    }

    [HttpPost("sync")]
    public async Task<IActionResult> Sync(
        IReadOnlyList<CustomerDto> customers)
    {
        var tasks = customers.Select(async customer =>
        {
            using var client = new HttpClient
            {
                BaseAddress = new Uri(_configuration["Crm:BaseUrl"]!),
                Timeout = TimeSpan.FromSeconds(30)
            };

            client.DefaultRequestHeaders.Authorization =
                new AuthenticationHeaderValue(
                    "Bearer",
                    _configuration["Crm:ApiToken"]);

            var response = await client.PostAsJsonAsync(
                "/api/customers",
                customer);

            if (!response.IsSuccessStatusCode)
            {
                _logger.LogWarning(
                    "CRM sync failed for {CustomerId}: {Status}",
                    customer.Id,
                    response.StatusCode);

                throw new InvalidOperationException("CRM sync failed");
            }
        });

        await Task.WhenAll(tasks);

        return Ok(new { Synced = customers.Count });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems.
2. Xác định performance/security/reliability concerns.
3. Giải thích production impact và điều kiện kích hoạt.
4. Xếp thứ tự ưu tiên theo severity.
5. Đề xuất implementation/design đã sửa.
6. Giải thích testing strategy, đặc biệt khi dependency chậm hoặc rate-limit.
7. Nêu telemetry cần có để chứng minh bottleneck và hiệu quả của fix.

## Câu hỏi gợi mở

1. `Task.WhenAll` ở đây tạo ra bao nhiêu outbound operations khi input có 2.000 customers?
2. Việc tạo/dispose `HttpClient` theo từng customer ảnh hưởng connection reuse như thế nào?
3. Client disconnect có dừng các outbound requests hiện tại không?
4. Retry `429`/`503` cần liên hệ thế nào với idempotency và backoff?
5. Nếu CRM chỉ cho phép một throughput giới hạn, giới hạn concurrency nên nằm ở đâu?

### Gợi ý 2

## Kết quả code review tham khảo

### High — Fan-out không giới hạn tới dependency

**Vấn đề:** `Select` tạo một task cho mọi customer và `Task.WhenAll` cho phép hàng nghìn outbound calls cùng tranh tài nguyên.  
**Tại sao xảy ra:** Không có concurrency limit/backpressure.  
**Ảnh hưởng production:** Connection pressure, queueing, timeout, `429`, ThreadPool/HTTP pipeline pressure và cascading failure tới các request khác.  
**Cách sửa:** Giới hạn concurrency theo capacity đã đo của CRM và application, ví dụ `Parallel.ForEachAsync` với bounded `MaxDegreeOfParallelism`, `SemaphoreSlim`, hoặc chuyển thành durable background workflow nếu request không cần synchronous completion.

### High — Tạo `HttpClient` cho từng customer

**Vấn đề:** Mỗi operation tạo và dispose một `HttpClient`.  
**Tại sao xảy ra:** Client lifetime gắn với từng item thay vì dùng managed handler/client lifetime.  
**Ảnh hưởng production:** Giảm connection reuse và có thể tạo connection/socket pressure khi tải cao.  
**Cách sửa:** Dùng `IHttpClientFactory`/typed client hoặc một client được quản lý đúng lifetime; cấu hình handler/DNS lifetime theo môi trường thay vì tự tạo per call.

### High — Không propagate request cancellation

**Vấn đề:** Endpoint không nhận/truyền `CancellationToken`.  
**Tại sao xảy ra:** `PostAsJsonAsync` chạy mà không gắn `HttpContext.RequestAborted`.  
**Ảnh hưởng production:** Client timeout/disconnect nhưng backend tiếp tục tiêu thụ CRM capacity và network.  
**Cách sửa:** Nhận `CancellationToken` và truyền xuyên suốt; nếu chuyển sang durable job thì cancellation semantics phải được định nghĩa khác vì job có thể cần tiếp tục sau khi HTTP request kết thúc.

### High — Failure của một item làm toàn batch trả lỗi nhưng side effects đã xảy ra

**Vấn đề:** `Task.WhenAll` throw nếu một task fail, trong khi nhiều customer khác đã được CRM cập nhật.  
**Tại sao xảy ra:** HTTP response được coi như một transaction cho nhiều external side effects nhưng CRM không tham gia transaction local.  
**Ảnh hưởng production:** Client thấy failure và retry toàn batch, có thể lặp side effect hoặc tạo ambiguity về item nào đã thành công.  
**Cách sửa:** Xác định batch semantics rõ ràng; dùng per-item result + idempotency key, hoặc durable job có trạng thái từng item và retry chọn lọc.

### High — Chưa sử dụng idempotency capability của CRM

**Vấn đề:** Retry/replay không có stable idempotency key.  
**Tại sao xảy ra:** Request chỉ gửi payload.  
**Ảnh hưởng production:** Timeout sau khi CRM đã xử lý có thể khiến retry tạo side effect lặp nếu API không tự idempotent theo customer identity.  
**Cách sửa:** Dùng stable operation key phù hợp business semantics, ví dụ sync-operation/customer/version; không tạo key mới cho mỗi retry của cùng logical operation.

### Medium — Không có retry policy phân loại lỗi

**Vấn đề:** Mọi non-success đều biến thành cùng một exception.  
**Tại sao xảy ra:** Không phân biệt transient `429/5xx` với validation/auth `4xx`.  
**Ảnh hưởng production:** Không tận dụng retry an toàn cho transient failure; hoặc nếu thêm retry mù sẽ khuếch đại outage.  
**Cách sửa:** Retry có giới hạn chỉ cho lỗi phù hợp, exponential backoff + jitter, tôn trọng `Retry-After` khi áp dụng và kết hợp idempotency.

### Medium — Timeout 30 giây áp dụng máy móc

**Vấn đề:** Một timeout cố định không được liên hệ với end-to-end latency budget và concurrency.  
**Tại sao xảy ra:** Timeout được chọn như một magic number.  
**Ảnh hưởng production:** Timeout quá dài giữ tài nguyên khi dependency degraded; quá ngắn tạo false failures.  
**Cách sửa:** Đặt timeout theo SLO/budget và đo dependency latency. Tăng timeout không phải mặc định đúng khi CRM đang quá tải.

### Medium — Secret được lấy trực tiếp từ configuration mà chưa xác định secret source

**Vấn đề:** Code giả định API token tồn tại như configuration value.  
**Tại sao xảy ra:** Chưa thể hiện Managed Identity/Key Vault hoặc secret provider/rotation strategy.  
**Ảnh hưởng production:** Nếu token nằm trong appsettings/repository/pipeline variables không được bảo vệ, nguy cơ leakage và rotation khó.  
**Cách sửa:** Dùng secret store phù hợp như Azure Key Vault với Managed Identity khi deployment hỗ trợ; không log token.

### Medium — Validation/batch limit chưa rõ

**Vấn đề:** Endpoint nhận arbitrary list size và chưa validate duplicate/invalid customer records.  
**Tại sao xảy ra:** Contract không enforce operational limits.  
**Ảnh hưởng production:** Một request có thể tạo workload quá lớn hoặc gửi duplicate customer updates.  
**Cách sửa:** Validate size/duplicates/input; nếu requirement cần hàng nghìn items, cân nhắc asynchronous job API.

### Low — Telemetry thiếu dependency-level context

**Vấn đề:** Chỉ log failure từng customer.  
**Tại sao xảy ra:** Không có metrics/traces cho concurrency, queueing, latency và retry.  
**Ảnh hưởng production:** Khó phân biệt CRM chậm với local connection pressure.  
**Cách sửa:** Theo dõi dependency duration/status, active concurrency, queue wait, retry count, rate-limit responses, timeout/cancellation và batch outcome.

## Phiên bản đề xuất

```csharp
public sealed class CrmClient
{
    private readonly HttpClient _http;

    public CrmClient(HttpClient http) => _http = http;

    public async Task<SyncResult> SyncAsync(
        CustomerDto customer,
        string idempotencyKey,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Post,
            "/api/customers")
        {
            Content = JsonContent.Create(customer)
        };

        request.Headers.TryAddWithoutValidation(
            "Idempotency-Key",
            idempotencyKey);

        using var response = await _http.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        return new SyncResult(customer.Id, response.StatusCode);
    }
}

[HttpPost("sync")]
public async Task<IActionResult> Sync(
    IReadOnlyList<CustomerDto> customers,
    CancellationToken cancellationToken)
{
    if (customers.Count is 0 or > 2000)
        return BadRequest();

    var results = new ConcurrentBag<SyncResult>();

    await Parallel.ForEachAsync(
        customers.DistinctBy(x => x.Id),
        new ParallelOptions
        {
            MaxDegreeOfParallelism = 16,
            CancellationToken = cancellationToken
        },
        async (customer, ct) =>
        {
            var key = $"customer-sync:{customer.Id}:{customer.Version}";
            var result = await _crm.SyncAsync(customer, key, ct);
            results.Add(result);
        });

    return Ok(results);
}
```

`16` chỉ là giá trị minh họa, không phải recommendation cố định. Phải chọn concurrency dựa trên CRM rate limit, dependency latency, instance count và load test. Với 2.000 items hoặc thời gian xử lý dài, thiết kế tốt hơn có thể là tạo một sync job durable rồi trả `202 Accepted`, sau đó worker xử lý bounded concurrency và lưu trạng thái từng item.

Retry policy nên được cấu hình ở typed client/resilience pipeline với giới hạn rõ ràng, chỉ retry lỗi transient phù hợp và dùng idempotency key ổn định.

## Giải thích thiết kế sau khi sửa

Thiết kế tách HTTP connection management khỏi batch orchestration. Concurrency được bounded thay vì fan-out theo input size. Cancellation được propagate trong synchronous request model. Idempotency bảo vệ ambiguous retry. Nếu business không cần user chờ, durable asynchronous job giảm coupling giữa HTTP request lifetime và CRM availability.

## Trade-offs

Bounded concurrency giảm peak throughput nhưng bảo vệ dependency và application. `IHttpClientFactory` giải quyết handler/client lifecycle nhưng không tự giải quyết rate limiting hoặc retry correctness. Durable job tăng reliability và khả năng resume nhưng thêm persistence, worker, job-status API và operational complexity; không nên thêm nếu batch nhỏ và synchronous SLA thực sự phù hợp.

## Cách kiểm thử

1. Integration test với fake CRM server đo active requests và xác minh concurrency không vượt limit.
2. Failure-path test `429` có `Retry-After`, `503`, timeout và permanent `400`; xác minh chỉ transient failures được retry.
3. Cancellation test: client abort và xác minh outbound calls nhận cancellation trong synchronous model.
4. Idempotency test: giả lập timeout sau khi CRM đã accept rồi retry cùng logical operation; key phải giữ nguyên.
5. Load test nhiều API instances để đo connection count, p95/p99, CRM error rate và throughput trước/sau fix.

## Quan sát trong production

Theo dõi Application Insights dependency duration/result code, outbound active requests, connection errors, timeout/cancellation, `429/503`, retry count, retry delay, batch size, queue wait nếu có, p95/p99 và correlation giữa inbound request với CRM calls. Alert dựa trên sustained failure/latency thay vì một lỗi đơn lẻ.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển flow này từ synchronous HTTP sang durable background job?
2. Nếu CRM rate limit áp dụng toàn bộ account chứ không phải từng application instance, per-instance semaphore còn thiếu điều gì?
3. Nếu CRM không hỗ trợ idempotency key, bạn có thể và không thể guarantee điều gì khi timeout xảy ra sau khi request đã tới CRM?

# Code Review Challenge 2 — PostgreSQL pagination càng về cuối càng chậm dù đã có index

**Chủ đề:** PostgreSQL, SQL performance, keyset pagination, query planning, indexing, API design, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một reporting API hiển thị audit events theo tenant. Bảng `audit_events` có khoảng 180 triệu rows. Mỗi tenant có từ vài nghìn đến hơn 20 triệu rows. UI hiển thị 100 rows/page, sort mới nhất trước và cho phép lọc theo khoảng thời gian.

Trang đầu thường dưới 150 ms nhưng page 5.000 có thể mất nhiều giây. CPU database tăng mạnh khi nhiều user export/duyệt sâu. Team nói query đã có index trên `tenant_id` và đề xuất thêm Redis cache cho mọi page.

Schema rút gọn:

```sql
CREATE TABLE audit_events (
    id uuid PRIMARY KEY,
    tenant_id uuid NOT NULL,
    occurred_at timestamptz NOT NULL,
    actor_id uuid NULL,
    event_type text NOT NULL,
    payload jsonb NOT NULL
);

CREATE INDEX ix_audit_events_tenant
    ON audit_events (tenant_id);
```

## Đoạn code cần review

```sql
SELECT
    id,
    tenant_id,
    occurred_at,
    actor_id,
    event_type,
    payload
FROM audit_events
WHERE tenant_id = $1
  AND DATE(occurred_at) >= $2
  AND DATE(occurred_at) <= $3
ORDER BY occurred_at DESC
LIMIT $4
OFFSET $5;

SELECT COUNT(*)
FROM audit_events
WHERE tenant_id = $1
  AND DATE(occurred_at) >= $2
  AND DATE(occurred_at) <= $3;
```

API tính `$5 = (page - 1) * pageSize` và chạy cả hai query cho mọi request để trả `totalPages`.

## Nhiệm vụ của ứng viên

1. Xác định correctness/performance risks.
2. Giải thích vì sao page sâu chậm dù `LIMIT 100`.
3. Review khả năng sử dụng index với filter và sort hiện tại.
4. Đề xuất query/index/API contract tốt hơn.
5. Nêu trade-off của keyset pagination so với OFFSET.
6. Giải thích cách đo bằng execution plan và production telemetry.
7. Đề xuất tests/load tests phù hợp với data distribution thật.

## Câu hỏi gợi mở

1. Database phải làm gì với hàng triệu rows đứng trước một deep `OFFSET`?
2. `DATE(occurred_at)` ảnh hưởng predicate/index usage như thế nào?
3. Index chỉ có `tenant_id` có hỗ trợ đồng thời filter + ordering tốt không?
4. `occurred_at` có thể trùng; cursor cần thêm field nào để ordering deterministic?
5. UI có thực sự cần exact `COUNT(*)` ở mọi page không?

## Gợi ý

### Gợi ý 1

Đừng bắt đầu bằng “thêm Redis”. Hãy xem execution plan, số rows scanned/sorted và cách pagination hoạt động.

### Gợi ý 2

Tìm cách biến “bỏ qua N rows” thành “tiếp tục sau row cuối của page trước”, với ordering ổn định và index phù hợp.

## Kết quả code review tham khảo

### High — Deep OFFSET có chi phí tăng theo vị trí page

**Vấn đề:** API dùng page-number pagination trên dataset rất lớn.  
**Tại sao xảy ra:** Database vẫn phải xác định/bỏ qua các rows trước offset trước khi trả page nhỏ tiếp theo.  
**Ảnh hưởng production:** Deep pages scan/process nhiều rows, latency và CPU tăng theo độ sâu.  
**Cách sửa:** Nếu UX cho phép sequential navigation/export streaming, dùng keyset/cursor pagination theo `(occurred_at, id)`.

### High — Function trên `occurred_at` làm predicate khó tận dụng index thông thường

**Vấn đề:** `DATE(occurred_at)` biến đổi column trong predicate.  
**Tại sao xảy ra:** Query không so sánh trực tiếp range của `timestamptz`.  
**Ảnh hưởng production:** Có thể tăng lượng rows phải filter và cản trở access path tối ưu với index theo timestamp.  
**Cách sửa:** Chuyển input ngày thành UTC/time-zone-aware range phù hợp business semantics và query `occurred_at >= $from AND occurred_at < $toExclusive`.

### High — Index không phù hợp filter + order

**Vấn đề:** Index chỉ có `tenant_id`.  
**Tại sao xảy ra:** Query cần lọc tenant, time range và order theo thời gian.  
**Ảnh hưởng production:** Planner có thể phải scan nhiều rows và sort.  
**Cách sửa:** Sau khi xác minh workload/plan, cân nhắc composite index như `(tenant_id, occurred_at DESC, id DESC)` để hỗ trợ tenant-scoped range và deterministic ordering. Không thêm index mà không đo write/storage cost.

### High — Ordering không deterministic khi timestamp trùng

**Vấn đề:** Chỉ `ORDER BY occurred_at DESC`.  
**Tại sao xảy ra:** Nhiều events có thể cùng timestamp.  
**Ảnh hưởng production:** Rows có thể dịch chuyển/duplicate/missing giữa pages, đặc biệt khi dữ liệu mới được insert.  
**Cách sửa:** Dùng stable tie-breaker, ví dụ `ORDER BY occurred_at DESC, id DESC`; cursor chứa cả hai values.

### Medium — Exact COUNT trên mỗi request có thể là workload đắt riêng biệt

**Vấn đề:** Mọi page chạy thêm `COUNT(*)` trên toàn result range.  
**Tại sao xảy ra:** API contract yêu cầu `totalPages` chính xác dù UI có thể không cần.  
**Ảnh hưởng production:** Count có thể chiếm đáng kể DB CPU/I/O và nhân đôi pressure.  
**Cách sửa:** Xác minh requirement. Có thể trả `hasMore`, cursor, count riêng/on-demand hoặc approximate/precomputed count nếu business chấp nhận.

### Medium — `payload jsonb` được trả cho mọi list row

**Vấn đề:** Listing lấy payload có thể lớn dù UI chỉ cần summary.  
**Tại sao xảy ra:** Projection không tách list view và detail view.  
**Ảnh hưởng production:** Tăng DB I/O, serialization, network và memory.  
**Cách sửa:** Chỉ select fields cần cho list; fetch payload khi mở detail nếu UX cho phép.

### Medium — Page size/offset cần server-side bounds

**Vấn đề:** Contract có thể cho pageSize hoặc page number cực lớn.  
**Tại sao xảy ra:** Chưa thể hiện validation.  
**Ảnh hưởng production:** Một client tạo query rất đắt hoặc response lớn.  
**Cách sửa:** Enforce max page size; với cursor API validate opaque cursor và tenant ownership/context.

### Low — Chưa có evidence trước khi đề xuất cache

**Vấn đề:** Team nhảy thẳng sang Redis.  
**Tại sao xảy ra:** Chưa xác định scan/sort/count là bottleneck nào.  
**Ảnh hưởng production:** Cache tăng invalidation/key cardinality/consistency complexity nhưng không sửa query shape gốc.  
**Cách sửa:** `EXPLAIN (ANALYZE, BUFFERS)` trên representative data, đo rows examined, sort, buffer hits/reads, execution time và query frequency trước.

## Phiên bản đề xuất

Index candidate sau khi xác minh plan/workload:

```sql
CREATE INDEX CONCURRENTLY ix_audit_events_tenant_time_id
    ON audit_events (tenant_id, occurred_at DESC, id DESC);
```

Cursor query:

```sql
SELECT
    id,
    occurred_at,
    actor_id,
    event_type
FROM audit_events
WHERE tenant_id = $1
  AND occurred_at >= $2
  AND occurred_at < $3
  AND (
        $4::timestamptz IS NULL
        OR (occurred_at, id) < ($4, $5)
      )
ORDER BY occurred_at DESC, id DESC
LIMIT $6;
```

Cursor đầu tiên không có `$4/$5`; page tiếp theo dùng `(occurred_at, id)` của row cuối page trước. Trong implementation thực tế nên encode/sign cursor hoặc ít nhất validate toàn bộ filter context để client không vô tình tái sử dụng cursor với tenant/time range khác.

Nếu UUID không có ordering semantics mong muốn ngoài tie-breaker, nó vẫn có thể tạo total ordering cùng timestamp; lựa chọn key thực tế phải phù hợp schema và index strategy. Time-zone conversion của `$2/$3` phải dựa trên requirement: “ngày” của tenant theo timezone nào, sau đó chuyển thành range chính xác trước khi query.

## Giải thích thiết kế sau khi sửa

Keyset pagination thay work proportional to deep offset bằng seek từ cursor gần vị trí cần đọc. Composite index align với equality predicate `tenant_id`, time range và ordering. Projection nhỏ giảm I/O. Exact total count được tách thành product/API decision thay vì mặc định trả ở mọi request.

## Trade-offs

Keyset pagination không hỗ trợ nhảy trực tiếp tới page 5.000 theo số page một cách tự nhiên. Nếu requirement bắt buộc random page access, OFFSET có thể vẫn cần và phải chấp nhận/giới hạn cost hoặc thiết kế một strategy khác. Composite index tăng storage và write amplification. `CREATE INDEX CONCURRENTLY` giảm blocking so với build thường nhưng vẫn là production operation cần capacity/monitoring và rollout plan.

## Cách kiểm thử

1. Dùng production-like distribution: tenant nhỏ và tenant >20 triệu rows; so sánh page đầu/deep OFFSET/keyset bằng `EXPLAIN (ANALYZE, BUFFERS)`.
2. Correctness test nhiều rows cùng `occurred_at`; duyệt nhiều cursors không duplicate/missing trong snapshot assumptions đã xác định.
3. Test boundary của date/timezone, đặc biệt end-exclusive range và DST nếu tenant timezone có DST.
4. Load test concurrent list requests và count requests; đo DB CPU/I/O/p95/p99.
5. Migration/deployment validation cho index creation trên dataset lớn, gồm thời gian build, disk headroom và rollback/abort plan.

## Quan sát trong production

Theo dõi query duration p95/p99, rows returned so với rows scanned, shared buffer hit/read, temp sort/spill nếu có, database CPU/I/O, active sessions, lock waits, slow-query statistics và request dimensions như tenant-size bucket/page strategy. Không log raw cursor nếu nó chứa dữ liệu nhạy cảm; correlation ID nối API trace với DB dependency telemetry.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc người dùng nhảy trực tiếp tới page bất kỳ, bạn sẽ đánh giá những lựa chọn nào thay vì ép keyset pagination?
2. Nếu audit rows có thể được backfill với `occurred_at` cũ trong lúc user đang paging, consistency của cursor sẽ thay đổi thế nào?
3. Khi nào một index covering thêm columns bằng `INCLUDE` đáng cân nhắc, và bạn cần đo trade-off write/storage gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Outbound concurrency phải được giới hạn theo capacity của application và dependency; `Task.WhenAll` không tự tạo backpressure.
- Retry phải được thiết kế cùng timeout, cancellation, idempotency và failure classification.
- Deep `OFFSET` có cost tăng theo vị trí page; pagination strategy là một phần của API/data-access design.
- Index hiệu quả phải phù hợp query shape thực tế: equality/range/order, không chỉ “đã có index”.
- Exact count, large projection và cache đều là trade-off cần evidence và requirement rõ ràng.

## Mẫu tư duy cần nhớ

- Bound concurrency trước khi dependency tự tạo backpressure bằng timeout/429.
- Thiết kế retry cùng idempotency; không retry mù.
- Propagate cancellation qua toàn bộ I/O chain.
- Đọc execution plan trước khi thêm cache/index.
- Chọn pagination theo access pattern, consistency và UX requirement.
