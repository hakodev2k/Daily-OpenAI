# Code Review Challenge 1 — Elasticsearch sync worker báo “checkpoint thành công” nhưng search index vẫn mất hoặc trùng dữ liệu

**Chủ đề:** C#/.NET 8, `BackgroundService`, EF Core, Elasticsearch, bulk indexing, checkpointing, eventual consistency, concurrency, cancellation, retries, bounded parallelism, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một e-commerce platform dùng SQL Server làm source of truth và Elasticsearch cho product search. Một `BackgroundService` đọc các product đã thay đổi từ SQL rồi đẩy sang Elasticsearch.

Yêu cầu:

- search có thể eventual-consistent trong khoảng vài chục giây;
- không được mất update khi process restart hoặc Elasticsearch lỗi;
- duplicate delivery/reprocessing phải an toàn;
- application chạy 4 instances;
- mỗi batch có thể có vài nghìn products;
- Elasticsearch đôi lúc trả partial failure trong bulk request;
- shutdown phải graceful;
- indexing không được tạo tải SQL/Elasticsearch không giới hạn;
- operations cần biết indexing lag, batch success/failure và item failures.

Sau khi scale từ 1 lên 4 instances, production xuất hiện:

- một số product đã update trong SQL nhưng search vẫn giữ dữ liệu cũ;
- một số product được index nhiều lần;
- checkpoint tiếp tục tăng ngay cả khi Elasticsearch có lỗi;
- khi restart deployment, logs đôi lúc có `ObjectDisposedException` hoặc cancellation noise;
- Elasticsearch CPU tăng mạnh theo batch;
- team nói “bulk request trả HTTP 200 nên batch đã thành công”.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductIndexWorker : BackgroundService
{
    private readonly AppDbContext _db;
    private readonly IElasticClient _elastic;
    private readonly ILogger<ProductIndexWorker> _logger;

    public ProductIndexWorker(
        AppDbContext db,
        IElasticClient elastic,
        ILogger<ProductIndexWorker> logger)
    {
        _db = db;
        _elastic = elastic;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var checkpoint = await _db.IndexCheckpoints
                .SingleAsync(x => x.Name == "products", stoppingToken);

            var products = await _db.Products
                .Where(x => x.ChangeVersion > checkpoint.LastVersion)
                .OrderBy(x => x.ChangeVersion)
                .Take(5000)
                .AsNoTracking()
                .ToListAsync(stoppingToken);

            if (products.Count == 0)
            {
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
                continue;
            }

            var tasks = products.Select(async product =>
            {
                await _elastic.IndexDocumentAsync(product);
            });

            await Task.WhenAll(tasks);

            checkpoint.LastVersion = products.Max(x => x.ChangeVersion);
            await _db.SaveChangesAsync(stoppingToken);

            _logger.LogInformation(
                "Indexed {Count} products through version {Version}",
                products.Count,
                checkpoint.LastVersion);
        }
    }
}
```

## Câu hỏi gợi mở

1. Bốn application instances có thể cùng đọc một checkpoint và cùng xử lý một range hay không?
2. `Task.WhenAll` trên 5.000 products tạo mức concurrency nào và có phù hợp với downstream capacity không?
3. HTTP-level success có chứng minh mọi Elasticsearch indexing operation thành công không?
4. Nếu một phần batch thành công nhưng một phần thất bại, checkpoint nên tiến tới đâu?
5. Nếu nhiều products có cùng `ChangeVersion`, chỉ lưu một scalar checkpoint có đủ để resume chính xác không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **checkpoint semantics không được gắn chặt với việc xác nhận từng mutation đã được Elasticsearch chấp nhận**, trong khi nhiều workers có thể cùng sở hữu một batch.

### Gợi ý 2

Reasoning theo failure windows: `read changes → send index writes → inspect item results → persist progress`; sau đó đặt process crash, partial failure và concurrent instances vào từng khoảng.

## Kết quả code review tham khảo

### Critical — Nhiều instances có thể xử lý cùng checkpoint mà không có ownership/coordination

**Vấn đề:**  
Mỗi worker đọc cùng row `products`, lấy cùng `LastVersion` và có thể index cùng range.

**Tại sao xảy ra:**  
Không có lease, distributed lock, partition ownership, queue consumer semantics hoặc optimistic-concurrency guard khi claim work.

**Ảnh hưởng production:**  
Duplicate work, load amplification, race khi ghi checkpoint và khó reasoning về progress. Nếu document ID/versioning không idempotent, kết quả search có thể sai.

**Cách sửa:**  
Chọn một ownership model rõ: single designated worker, database-backed lease/claim, queue/outbox consumers, hoặc partition work theo key. Nếu duplicate processing vẫn có thể xảy ra, Elasticsearch writes phải idempotent.

### Critical — Progress được lưu theo batch nhưng không có cơ chế xử lý partial success an toàn

**Vấn đề:**  
Code giả định `Task.WhenAll` hoàn tất nghĩa là toàn bộ indexing có thể checkpoint tới `Max(ChangeVersion)`.

**Tại sao xảy ra:**  
Elasticsearch bulk/index APIs có thể có item-level failures; application cần inspect response semantics tương ứng. Với implementation hiện tại, abstraction cũng không ghi lại per-item result để quyết định retry/progress.

**Ảnh hưởng production:**  
Nếu checkpoint vượt qua một product chưa index thành công, update đó có thể bị bỏ qua vĩnh viễn.

**Cách sửa:**  
Dùng bulk indexing có explicit per-item success/failure handling; chỉ advance durable progress khi mọi record trước boundary an toàn, hoặc persist per-event processing state/retry queue.

### High — `Task.WhenAll` fan-out tới hàng nghìn calls không có bounded concurrency

**Vấn đề:**  
Một batch 5.000 products tạo hàng nghìn asynchronous operations gần như cùng lúc.

**Tại sao xảy ra:**  
LINQ enumerable được materialize khi `Task.WhenAll` enumerate nó; không có concurrency limiter.

**Ảnh hưởng production:**  
Connection pressure, downstream saturation, memory growth, latency spikes và self-inflicted Elasticsearch overload; 4 instances còn khuếch đại tải.

**Cách sửa:**  
Prefer bulk API với bounded batch size; nếu phải gọi song song, dùng bounded concurrency (`SemaphoreSlim`, channel, `Parallel.ForEachAsync` với giới hạn hợp lý) dựa trên measurements.

### High — Shared scoped `DbContext` trong long-lived worker có lifetime không phù hợp

**Vấn đề:**  
`BackgroundService` là singleton-hosted service nhưng giữ `AppDbContext` như dependency dài hạn.

**Tại sao xảy ra:**  
`DbContext` thường được đăng ký scoped và không nên được giữ xuyên suốt lifetime của singleton worker; state/tracking/connection behavior cũng trở nên khó kiểm soát.

**Ảnh hưởng production:**  
Lifetime violation, stale tracking state, resource retention hoặc runtime resolution failure tùy registration.

**Cách sửa:**  
Dùng `IServiceScopeFactory` tạo scope cho mỗi iteration/batch hoặc `IDbContextFactory<AppDbContext>`.

### High — Cancellation không được propagate tới Elasticsearch calls

**Vấn đề:**  
`IndexDocumentAsync(product)` không nhận `stoppingToken`.

**Tại sao xảy ra:**  
Worker chỉ cancel SQL/Delay, còn outbound work có thể tiếp tục trong shutdown.

**Ảnh hưởng production:**  
Deployment shutdown kéo dài, work bị cắt giữa chừng, noisy exceptions và khó xác định checkpoint state.

**Cách sửa:**  
Propagate cancellation tới calls hỗ trợ token; vẫn thiết kế idempotency/checkpoint để restart an toàn vì cancellation không phải transaction rollback toàn hệ thống.

### High — Checkpoint scalar có thể bỏ sót records khi ordering key không unique

**Vấn đề:**  
Query dùng `ChangeVersion > LastVersion`, order chỉ theo `ChangeVersion`, rồi `Take(5000)`.

**Tại sao xảy ra:**  
Nếu nhiều records có cùng `ChangeVersion` và batch cắt giữa nhóm, checkpoint tới value đó khiến các records cùng version nhưng chưa nằm trong batch bị bỏ qua.

**Ảnh hưởng production:**  
Silent data loss trong index.

**Cách sửa:**  
Dùng cursor có total ordering, ví dụ `(ChangeVersion, ProductId)`, hoặc một immutable unique event/outbox sequence.

### Medium — Không có explicit retry/backoff/dead-letter strategy cho item failures

**Vấn đề:**  
Một transient failure có thể fault toàn iteration, còn permanent mapping/data failure không có nơi cách ly.

**Tại sao xảy ra:**  
Retry semantics không phân biệt transient với permanent lỗi.

**Ảnh hưởng production:**  
Worker có thể crash-loop hoặc liên tục retry poison records.

**Cách sửa:**  
Có bounded retry với backoff/jitter cho transient failures; persist/capture poison items để operator xử lý mà không chặn toàn pipeline nếu business cho phép.

### Medium — Không có lag metric và item-level diagnostics

**Vấn đề:**  
Log chỉ nói batch “Indexed” với count/version.

**Tại sao xảy ra:**  
Không đo oldest pending age, items attempted/succeeded/failed/retried hoặc ownership instance.

**Ảnh hưởng production:**  
Dashboard xanh nhưng search vẫn stale; khó phát hiện silent indexing gap.

**Cách sửa:**  
Thêm structured metrics/traces cho lag, cursor, batch duration, bulk errors, retry count và index/version identifiers.

### Medium — Source model bị gửi thẳng sang search document

**Vấn đề:**  
`product` entity được index trực tiếp.

**Tại sao xảy ra:**  
Persistence schema và search schema bị coupling; accidental field exposure/mapping drift dễ xảy ra.

**Ảnh hưởng production:**  
Breaking mapping, index bloat hoặc leak field không nên searchable.

**Cách sửa:**  
Map sang explicit `ProductSearchDocument` với schema/versioning rõ.

## Phiên bản đề xuất

Một hướng đơn giản nếu throughput chưa buộc phải chạy nhiều consumers là chỉ có **một active indexer**, dùng stable cursor và bulk API. Nếu cần scale-out, thay single ownership bằng lease/partitioning nhưng giữ cùng progress invariants.

```csharp
public readonly record struct ProductCursor(long ChangeVersion, Guid ProductId);

public sealed class ProductIndexWorker : BackgroundService
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IProductSearchIndexer _indexer;
    private readonly IProductIndexLease _lease;
    private readonly ILogger<ProductIndexWorker> _logger;

    public ProductIndexWorker(
        IDbContextFactory<AppDbContext> dbFactory,
        IProductSearchIndexer indexer,
        IProductIndexLease lease,
        ILogger<ProductIndexWorker> logger)
    {
        _dbFactory = dbFactory;
        _indexer = indexer;
        _lease = lease;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var ownership = await _lease.TryAcquireAsync(
                "products",
                stoppingToken);

            if (ownership is null)
            {
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
                continue;
            }

            await ProcessOneBatchAsync(stoppingToken);
        }
    }

    private async Task ProcessOneBatchAsync(CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var state = await db.IndexCheckpoints
            .SingleAsync(x => x.Name == "products", ct);

        var rows = await db.Products
            .Where(x =>
                x.ChangeVersion > state.LastVersion ||
                (x.ChangeVersion == state.LastVersion && x.Id.CompareTo(state.LastProductId) > 0))
            .OrderBy(x => x.ChangeVersion)
            .ThenBy(x => x.Id)
            .Take(500)
            .AsNoTracking()
            .Select(x => new ProductSearchDocument(
                x.Id,
                x.Name,
                x.CategoryId,
                x.Price,
                x.ChangeVersion))
            .ToListAsync(ct);

        if (rows.Count == 0)
        {
            await Task.Delay(TimeSpan.FromSeconds(2), ct);
            return;
        }

        var result = await _indexer.BulkIndexAsync(rows, ct);

        if (!result.AllSucceeded)
        {
            throw new ProductIndexBatchException(result.Failures);
        }

        var last = rows[^1];
        state.LastVersion = last.ChangeVersion;
        state.LastProductId = last.Id;

        await db.SaveChangesAsync(ct);

        _logger.LogInformation(
            "Product index batch succeeded. Count={Count} CursorVersion={Version} CursorProductId={ProductId}",
            rows.Count,
            state.LastVersion,
            state.LastProductId);
    }
}
```

`IProductSearchIndexer.BulkIndexAsync` nên:

- dùng deterministic document ID = product ID;
- kiểm tra từng bulk item;
- classify transient/permanent failures;
- không trả `AllSucceeded=true` chỉ dựa trên HTTP status;
- dùng bounded batch size;
- emit metrics cho attempted/succeeded/failed items.

Nếu throughput cần nhiều workers, một hướng tốt hơn nữa là dùng transactional outbox/change log với unique monotonically ordered event IDs rồi consumers xử lý idempotently. Không cần thêm queue hoặc distributed lock nếu measured workload chưa đòi hỏi complexity đó.

## Giải thích thiết kế sau khi sửa

Correctness boundary nằm ở **durable source progress**. Cursor chỉ được tiến khi batch trước boundary đã được search index chấp nhận theo semantics mà application xác minh được. Deterministic document ID làm re-index cùng product trở nên idempotent ở mức replace/upsert thích hợp.

Stable `(ChangeVersion, ProductId)` cursor tránh mất rows khi nhiều products có cùng version. Database-backed lease chỉ là một ví dụ về ownership; nếu deployment có thể bảo đảm một active worker thì giải pháp đơn giản hơn là tốt hơn.

Elasticsearch vẫn là read/search projection, không phải source of truth. Nếu projection bị hỏng, system nên có khả năng rebuild index từ durable source hoặc event log.

## Trade-offs

- Single active worker đơn giản và dễ correctness nhưng giới hạn throughput.
- Lease/partitioning hỗ trợ scale-out nhưng thêm failure/expiry/ownership complexity.
- Outbox/change-log cung cấp audit/replay tốt hơn nhưng tăng storage và operational components.
- Chỉ advance checkpoint khi cả batch thành công có thể reprocess các successful items sau partial failure; deterministic IDs làm trade-off này thường chấp nhận được và đơn giản hơn per-item checkpoint.
- Bulk batch lớn tăng throughput nhưng tăng failure blast radius/memory; batch nhỏ giảm blast radius nhưng tăng request overhead.

## Cách kiểm thử

1. **Failure-path test:** bulk response có 499 success + 1 transient failure; checkpoint không được vượt qua failed boundary, retry phải không làm sai document cuối.
2. **Restart test:** kill worker sau Elasticsearch success nhưng trước DB checkpoint; sau restart batch được reprocess idempotently và cursor cuối vẫn đúng.
3. **Concurrency test:** chạy 4 worker instances; xác minh lease/ownership ngăn concurrent claim hoặc duplicate processing vẫn an toàn nếu intentionally allowed.
4. **Database cursor test:** tạo hơn batch-size records có cùng `ChangeVersion`; xác minh không record nào bị bỏ qua qua nhiều batches.
5. **Load test:** đo SQL duration, bulk size, indexing throughput, Elasticsearch CPU/rejection rate và indexing lag để chọn batch/concurrency dựa trên evidence.

## Quan sát trong production

Theo dõi structured telemetry:

- `index_batch_duration_ms`;
- `index_items_attempted_total`, `succeeded_total`, `failed_total`, `retried_total`;
- `index_lag_seconds` hoặc age của oldest unindexed change;
- current durable cursor;
- lease owner/renewal failures nếu dùng lease;
- Elasticsearch bulk item error category/status;
- SQL query duration/rows read;
- worker restarts/cancellations;
- correlation giữa source change ID và search indexing trace.

Alert không chỉ theo worker exception mà còn theo **lag vượt SLO** và persistent item failures. Kibana/Elasticsearch health metrics cần được correlate với application traces thay vì chỉ nhìn HTTP 200.

# Code Review Challenge 2 — React render CMS HTML trực tiếp và giữ access token trong `localStorage`: tiện nhưng trust boundary đang ở đâu?

**Chủ đề:** React.js, TypeScript, ASP.NET Core API integration, XSS, `dangerouslySetInnerHTML`, token storage, Content Security Policy, authorization, URL validation, frontend error handling, observability

## Bối cảnh

Một marketing portal dùng React cho frontend và ASP.NET Core API cho backend. Editorial content được lấy từ CMS; một số page blocks cho phép rich text và CTA links. User có thể đăng nhập để thấy nội dung cá nhân hóa.

Yêu cầu:

- CMS rich text phải hiển thị được formatting cần thiết;
- unpublished/admin-only content không được leak;
- user-specific API vẫn phải authorize ở server;
- external links phải xử lý an toàn;
- frontend không được biến một CMS compromise hoặc stored malicious content thành account-wide XSS;
- security team muốn giảm blast radius nếu third-party script bị compromise;

## Đoạn code cần review

```tsx
import { useEffect, useState } from 'react';

type Page = {
  title: string;
  html: string;
  ctaUrl?: string;
};

export function MarketingPage({ slug }: { slug: string }) {
  const [page, setPage] = useState<Page | null>(null);
  const [profile, setProfile] = useState<any>(null);

  useEffect(() => {
    const token = localStorage.getItem('access_token');

    Promise.all([
      fetch(`/api/pages/${slug}`).then(r => r.json()),
      fetch('/api/me', {
        headers: { Authorization: `Bearer ${token}` }
      }).then(r => r.json())
    ]).then(([pageResult, profileResult]) => {
      setPage(pageResult);
      setProfile(profileResult);
    });
  }, [slug]);

  if (!page) return <div>Loading...</div>;

  return (
    <main>
      <h1>{page.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: page.html }} />

      {page.ctaUrl && (
        <a href={page.ctaUrl} target="_blank">
          Continue
        </a>
      )}

      {profile && <p>Welcome, {profile.displayName}</p>}
    </main>
  );
}
```

## Kết quả code review tham khảo

### Critical — Unsanitized CMS HTML tạo stored XSS

**Vấn đề:**  
`page.html` được đưa trực tiếp vào `dangerouslySetInnerHTML`.

**Tại sao xảy ra:**  
React không escape nội dung được đưa qua API này. Nếu HTML chứa event handlers, dangerous URLs hoặc payload khác mà browser thực thi, attacker có code execution trong origin của application.

**Ảnh hưởng production:**  
Stored XSS có thể ảnh hưởng mọi user mở page, thực hiện actions với quyền user, đọc browser-accessible data và pivot sang authenticated APIs.

**Cách sửa:**  
Ưu tiên CMS structured content/components thay vì arbitrary HTML. Nếu rich HTML bắt buộc, sanitize bằng một battle-tested allowlist-based sanitizer ở trusted boundary và defense-in-depth ở server; không tự viết regex sanitizer.

### Critical — Browser-readable bearer token làm XSS blast radius lớn hơn

**Vấn đề:**  
Access token được lấy từ `localStorage`.

**Tại sao xảy ra:**  
JavaScript chạy trong cùng origin có thể đọc `localStorage`. Vì vậy một XSS hoặc compromised third-party script có thể exfiltrate bearer token.

**Ảnh hưởng production:**  
Token theft có thể tiếp tục được sử dụng ngoài page tùy token lifetime/scope, làm incident nghiêm trọng hơn.

**Cách sửa:**  
Đánh giá authentication architecture theo threat model. Với browser application cùng backend, một BFF/session-cookie design với `HttpOnly`, `Secure`, appropriate `SameSite` cookie có thể giảm token exposure cho JavaScript; nếu SPA buộc phải giữ/access token ở browser, giữ lifetime/scope tối thiểu, tránh persistent storage khi có thể và đặc biệt phải ngăn XSS. Cookie-based auth kéo theo CSRF considerations cần xử lý riêng.

### High — Client không kiểm tra `response.ok`

**Vấn đề:**  
401/403/500 vẫn đi vào `.json()` và có thể được dùng như data thành công.

**Tại sao xảy ra:**  
Fetch chỉ reject cho một số network failures, không tự reject mọi HTTP error status.

**Ảnh hưởng production:**  
UI state sai, exceptions khó hiểu, unauthorized response có thể bị render theo shape không mong đợi.

**Cách sửa:**  
Centralize fetch wrapper kiểm tra status, parse `ProblemDetails` khi phù hợp và classify auth/network/server failure.

### High — Request cũ có thể ghi đè state sau khi `slug` thay đổi

**Vấn đề:**  
Effect không cancel hoặc guard response ownership.

**Tại sao xảy ra:**  
Hai asynchronous fetch groups có thể complete ngược order khi navigation nhanh.

**Ảnh hưởng production:**  
Page B có thể hiển thị content/profile state từ request A; với authorization-dependent content đây còn là data correctness risk.

**Cách sửa:**  
Dùng `AbortController` và/or monotonically increasing request generation; chỉ latest effect được update state.

### High — CTA URL không có scheme/destination validation

**Vấn đề:**  
CMS-controlled value được gắn trực tiếp vào `href`.

**Tại sao xảy ra:**  
Content có thể chứa protocol/destination không được business cho phép, tạo phishing/open-navigation hoặc dangerous URL behavior tùy browser/context.

**Ảnh hưởng production:**  
User bị điều hướng tới malicious destination hoặc trust của site bị lạm dụng.

**Cách sửa:**  
Parse URL và enforce allowlist/rules, ví dụ chỉ `https:` và approved domains nếu requirement yêu cầu. Relative internal URLs nên được normalize riêng.

### Medium — `target="_blank"` cần explicit link hardening theo support policy

**Vấn đề:**  
Code không khai báo `rel`.

**Tại sao xảy ra:**  
Modern browsers có defenses tốt hơn trước đây, nhưng explicit `rel="noopener noreferrer"` vẫn làm intent rõ và hỗ trợ compatibility/security policy, đồng thời `noreferrer` có analytics/privacy trade-off.

**Ảnh hưởng production:**  
Tùy browser/support matrix, opener relationship hoặc referrer leakage có thể không phù hợp policy.

**Cách sửa:**  
Dùng `rel="noopener noreferrer"` khi outbound-link requirement phù hợp; cân nhắc chỉ `noopener` nếu cần referrer analytics.

### Medium — `Promise.all` làm public content phụ thuộc vào authenticated profile request

**Vấn đề:**  
Nếu `/api/me` fail, toàn chain reject và page content cũng không được commit vào state.

**Tại sao xảy ra:**  
Hai concerns có availability khác nhau bị coupling thành một all-or-nothing promise.

**Ảnh hưởng production:**  
Identity/profile outage có thể làm anonymous marketing page mất usability.

**Cách sửa:**  
Fetch public page và optional profile độc lập hoặc dùng `Promise.allSettled` với explicit degradation semantics.

### Medium — Không có abort/error cleanup và loading semantics rõ

**Vấn đề:**  
Effect không catch/retry/classify failure, không abort on unmount, và loading chỉ phụ thuộc `page`.

**Tại sao xảy ra:**  
Happy-path-only state model.

**Ảnh hưởng production:**  
Unhandled rejection/noisy telemetry, stale UI và poor UX khi dependency lỗi.

**Cách sửa:**  
Dùng explicit `loading/error/content/profile` states và cleanup controller.

### Medium — `any` cho profile làm mất compile-time contract ở security-sensitive boundary

**Vấn đề:**  
Response shape không được typed/validated.

**Tại sao xảy ra:**  
`any` bỏ TypeScript checking; JSON từ network vẫn là untrusted runtime input.

**Ảnh hưởng production:**  
Breaking API changes hoặc malformed payload đi sâu vào UI khó phát hiện.

**Cách sửa:**  
Dùng typed DTO và runtime validation khi boundary/risk xứng đáng; server vẫn là authority cho authorization.

## Phiên bản đề xuất

Một hướng an toàn hơn là **structured content**. CMS trả về các blocks đã typed, frontend map sang React components, tránh arbitrary HTML. Nếu migration chưa cho phép, sanitize rich text trước khi render và giới hạn allowed tags/attributes/URLs.

```tsx
import { useEffect, useState } from 'react';
import DOMPurify from 'dompurify';

type Page = {
  title: string;
  html: string;
  ctaUrl?: string;
};

type Profile = {
  displayName: string;
};

function safeExternalUrl(value?: string): string | undefined {
  if (!value) return undefined;

  try {
    const url = new URL(value, window.location.origin);

    if (url.origin === window.location.origin) {
      return url.pathname + url.search + url.hash;
    }

    if (url.protocol !== 'https:') {
      return undefined;
    }

    const allowedHosts = new Set([
      'www.example.com',
      'support.example.com'
    ]);

    return allowedHosts.has(url.hostname) ? url.toString() : undefined;
  } catch {
    return undefined;
  }
}

async function getJson<T>(url: string, signal: AbortSignal): Promise<T> {
  const response = await fetch(url, {
    signal,
    credentials: 'include'
  });

  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }

  return response.json() as Promise<T>;
}

export function MarketingPage({ slug }: { slug: string }) {
  const [page, setPage] = useState<Page | null>(null);
  const [profile, setProfile] = useState<Profile | null>(null);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    setPage(null);
    setError(null);

    void getJson<Page>(`/api/pages/${encodeURIComponent(slug)}`, controller.signal)
      .then(setPage)
      .catch(error => {
        if (error.name !== 'AbortError') setError('Unable to load page');
      });

    void getJson<Profile>('/api/me', controller.signal)
      .then(setProfile)
      .catch(error => {
        if (error.name !== 'AbortError') setProfile(null);
      });

    return () => controller.abort();
  }, [slug]);

  if (error) return <div role="alert">{error}</div>;
  if (!page) return <div>Loading...</div>;

  const safeHtml = DOMPurify.sanitize(page.html, {
    USE_PROFILES: { html: true }
  });
  const ctaUrl = safeExternalUrl(page.ctaUrl);

  return (
    <main>
      <h1>{page.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: safeHtml }} />

      {ctaUrl && (
        <a href={ctaUrl} target="_blank" rel="noopener noreferrer">
          Continue
        </a>
      )}

      {profile && <p>Welcome, {profile.displayName}</p>}
    </main>
  );
}
```

Đoạn trên minh họa risk reduction, không phải tuyên bố `DOMPurify` một mình giải quyết toàn bộ content-security architecture. Sanitizer configuration phải được test theo allowed CMS features, dependencies phải được maintained, và server-side publication pipeline có thể sanitize/validate thêm để mọi consuming channel nhận content an toàn hơn.

Nếu application dùng cookie/session/BFF, backend phải có CSRF defense phù hợp cho state-changing requests. Nếu dùng OAuth/OIDC SPA architecture, token strategy cần tuân theo identity provider/library guidance; không tự xây token lifecycle chỉ từ đoạn minh họa này.

## Giải thích thiết kế sau khi sửa

React escape text interpolation như `{page.title}` và `{profile.displayName}`, nhưng `dangerouslySetInnerHTML` là explicit escape hatch nên trust decision nằm ở application.

Defense tốt nhất là giảm executable surface: structured CMS blocks → typed React components. Sanitization là boundary control khi rich HTML thực sự cần thiết. CSP có thể giảm impact của một số injection classes nhưng không thay việc sanitize/avoid unsafe HTML.

Authentication storage và authorization là concerns khác nhau. Dù frontend có token/session hợp lệ, backend vẫn phải authorize mọi protected resource; frontend visibility không phải security boundary.

## Trade-offs

- Structured content an toàn/maintainable hơn nhưng cần CMS model và frontend component governance.
- Sanitization cho phép rich text linh hoạt nhưng có maintenance burden và có thể strip editor features nếu allowlist quá chặt.
- BFF/HttpOnly cookie giảm JavaScript token exposure nhưng thêm backend/session/CSRF concerns.
- `noreferrer` giảm referrer leakage nhưng có thể ảnh hưởng analytics attribution.
- CSP nghiêm ngặt tăng defense-in-depth nhưng cần inventory scripts/styles và rollout cẩn thận để tránh phá site.

## Cách kiểm thử

1. **Security test:** đưa CMS payload chứa `<script>`, event handler, malicious URL và SVG/HTML edge cases; xác minh sanitizer/structured renderer không thực thi code.
2. **Auth integration test:** `/api/me` trả 401/403 trong khi page public vẫn render; protected backend endpoints vẫn deny dù client cố giả profile state.
3. **Navigation race test:** chuyển nhanh từ slug A → B với A response chậm hơn; B phải luôn là page cuối được render.
4. **URL validation test:** kiểm tra relative URL, approved `https` host, `javascript:`, malformed URL và unapproved domain.
5. **Browser E2E test:** dùng Playwright kiểm tra CSP violations, outbound links, auth-expiry behavior và không có access token trong browser-readable storage nếu architecture đã chuyển sang BFF/session cookie.

## Quan sát trong production

Theo dõi:

- frontend page-fetch/profile-fetch error rate và latency;
- HTTP status categories 401/403/5xx;
- route/slug + client request correlation ID, không log token;
- CSP violation reports nếu rollout CSP reporting phù hợp;
- sanitized/rejected CMS content events ở publication pipeline;
- invalid CTA URL count;
- backend authorization failures và suspicious repeated access patterns;
- frontend unhandled rejection/error boundary events;
- release/version correlation khi security policy hoặc sanitizer config thay đổi.

Không gửi raw access token, session cookie hoặc full sensitive HTML payload vào Application Insights/logging.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bắt buộc cho editors nhúng một số third-party widgets/script, bạn tạo trust boundary và sandboxing/CSP strategy thế nào?
2. Một teammate nói chuyển token từ `localStorage` sang cookie là đủ để “fix XSS”. Bạn phản biện thế nào, và rủi ro nào chuyển thành CSRF concern?
3. Nếu CMS content được dùng đồng thời bởi React website, mobile app và email renderer, bạn đặt sanitization/validation ở đâu để tránh mỗi client tự hiểu trust khác nhau?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Một search projection chỉ đáng tin khi **ownership, idempotency và durable progress semantics** được thiết kế cùng nhau; checkpoint không được đi trước những mutations chưa được xác nhận an toàn.
- Scale-out background worker làm lộ các assumption vốn vô hại ở single-instance: duplicate ownership, load amplification và race trên progress state.
- Elasticsearch/HTTP success ở transport level không nên được đồng nhất với mọi item trong logical batch thành công; application phải kiểm tra semantics của operation thực tế.
- Browser security cần reasoning theo trust boundary: CMS content là untrusted data, `dangerouslySetInnerHTML` bỏ lớp escaping mặc định, và browser-readable bearer credential làm XSS blast radius lớn hơn.
- Security control nên nhiều lớp: structured content/sanitization, URL validation, CSP, safe credential architecture và server-side authorization; không control đơn lẻ nào thay thế toàn bộ các lớp còn lại.

## Mẫu tư duy cần nhớ

- **Progress chỉ được commit sau khi side effect tương ứng đã được xác nhận theo invariant.**
- **Scale-out biến local state thành distributed coordination problem.**
- **Bound concurrency theo downstream capacity; đừng dùng `Task.WhenAll` như một performance switch.**
- **Dữ liệu đi vào executable context phải được coi là một trust-boundary decision.**
- **Defense-in-depth không thay thế root-cause control: CSP không thay sanitization, token storage không thay authorization.**
