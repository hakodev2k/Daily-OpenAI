# Câu 1 — Endpoint có `[Authorize]` nhưng custom middleware vẫn thấy `User.Identity.IsAuthenticated == false`: request pipeline thực sự chạy như thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, middleware pipeline, endpoint routing, authentication, authorization, claims, endpoint metadata, middleware ordering, security, production diagnostics

## Bối cảnh

Một ASP.NET Core .NET 10 API dùng JWT bearer authentication và policy-based authorization. Team thêm custom middleware để ghi audit context và chặn một số tenant-specific requests.

Cấu hình giản lược:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.Authority = builder.Configuration["Identity:Authority"];
        options.Audience = "orders-api";
    });

builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("Orders.Read", policy =>
        policy.RequireClaim("permission", "orders.read"));
});

var app = builder.Build();

app.UseMiddleware<RequestAuditMiddleware>();
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();

app.MapGet("/orders/{id}", GetOrder)
   .RequireAuthorization("Orders.Read");

app.Run();
```

Custom middleware:

```csharp
public sealed class RequestAuditMiddleware
{
    private readonly RequestDelegate _next;

    public RequestAuditMiddleware(RequestDelegate next)
        => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        var endpoint = context.GetEndpoint();
        var isAuthenticated = context.User.Identity?.IsAuthenticated == true;
        var subject = context.User.FindFirst("sub")?.Value;

        Console.WriteLine(
            "Endpoint={Endpoint}; Authenticated={Authenticated}; Sub={Sub}",
            endpoint?.DisplayName,
            isAuthenticated,
            subject);

        await _next(context);
    }
}
```

Production ghi nhận:

- endpoint có `.RequireAuthorization("Orders.Read")` vẫn reject user thiếu permission đúng như mong đợi;
- nhưng `RequestAuditMiddleware` thường log `Endpoint=null`, `Authenticated=false`, `Sub=null`;
- một developer kết luận JWT middleware “chạy bất đồng bộ nên chưa authenticate xong”;
- developer khác muốn gọi `AuthenticateAsync()` thủ công trong custom middleware;
- một số middleware khác cần đọc endpoint metadata để quyết định policy riêng;
- API chạy sau reverse proxy và có cả public endpoints lẫn authenticated endpoints;
- chưa xác minh pipeline ordering ở tất cả environments vì một extension method nội bộ có thể thêm middleware khác.

## Câu hỏi chính

Hãy giải thích **request pipeline của ASP.NET Core thực sự chạy theo thứ tự nào**, `UseRouting`, `UseAuthentication`, `UseAuthorization` và endpoint metadata ảnh hưởng ra sao đến `HttpContext.GetEndpoint()` và `HttpContext.User`. Vì sao custom middleware trong ví dụ có thể thấy `Endpoint=null` và user chưa authenticated trong khi endpoint cuối cùng vẫn được authorize đúng? Sau đó đề xuất cách đặt middleware hợp lý, khi nào việc gọi `AuthenticateAsync()` thủ công là cần thiết hoặc không cần thiết, và cách bạn xác minh behavior này trong production.

## Câu hỏi làm rõ nên cân nhắc

1. Custom middleware cần endpoint metadata, authenticated principal hay cả hai trước khi thực hiện logic?
2. Extension methods khác có gọi `UseRouting`, `UseAuthentication`, `UseAuthorization` hoặc branch pipeline bằng `Map`/`UseWhen` không?
3. Có nhiều authentication schemes hay chỉ một default JWT bearer scheme?
4. Audit middleware cần log cả anonymous request hay chỉ authenticated request sau khi identity được xác lập?
5. Tenant-specific check là authentication concern, authorization concern hay business validation concern?

## Gợi ý tư duy

### Gợi ý 1

Nhìn pipeline như một chuỗi delegates chạy **theo thứ tự đăng ký trên request path**, rồi unwind ngược lại trên response path.

### Gợi ý 2

`GetEndpoint()` chỉ có ý nghĩa sau khi routing đã chọn endpoint; `HttpContext.User` chỉ phản ánh authentication sau khi authentication step phù hợp đã chạy.

### Gợi ý 3

Đừng biến custom middleware thành một authorization framework thứ hai. Xác định rõ responsibility trước khi quyết định vị trí và API cần dùng.

## Cấu trúc trả lời đề xuất

1. Clarify middleware responsibility.
2. Vẽ request pipeline theo thứ tự thực thi.
3. Giải thích routing và endpoint selection.
4. Giải thích authentication thiết lập principal.
5. Giải thích authorization đọc endpoint metadata/policy.
6. Chỉ ra vì sao middleware hiện tại chạy quá sớm.
7. Đề xuất ordering hoặc refactor responsibility.
8. Nêu trường hợp hợp lý cho explicit authentication.
9. Test pipeline với anonymous/authenticated/forbidden paths.
10. Instrument production để verify actual order và selected endpoint.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Middleware được gọi theo thứ tự đăng ký trên request path; ordering có thể ảnh hưởng security, functionality và performance.
- `RequestAuditMiddleware` đang đứng trước `UseRouting`, nên tại thời điểm nó chạy, endpoint thường chưa được route/select và `context.GetEndpoint()` có thể là `null`.
- Middleware cũng đứng trước `UseAuthentication`, nên `HttpContext.User` chưa nhất thiết chứa authenticated principal từ JWT bearer handler.
- Sau khi request đi tiếp qua `UseAuthentication` và `UseAuthorization`, endpoint vẫn có thể được authorize đúng; điều đó không mâu thuẫn với việc middleware trước đó thấy anonymous state.
- Nếu middleware cần cả endpoint metadata và authenticated user, một vị trí thông thường là sau routing và authentication, đồng thời trước endpoint execution; authorization placement phụ thuộc middleware cần chạy trước hay sau authorization decision.
- Không nên gọi `AuthenticateAsync()` thủ công chỉ để bù cho pipeline ordering sai nếu framework authentication middleware đã được cấu hình phù hợp.
- Authentication và authorization là hai concern khác nhau: authentication xác định principal; authorization quyết định principal có được phép truy cập resource/policy hay không.
- Custom tenant checks có thể phù hợp hơn với authorization policy/handler nếu chúng là access-control rule gắn với endpoint/resource.

### Điểm cộng

- Nhận ra Minimal API/WebApplication có thể tự thêm một số middleware trong một số điều kiện, nhưng khi cần precise ordering với CORS/custom middleware thì explicit ordering rõ ràng hơn.
- Nếu middleware cần endpoint metadata nhưng chưa cần identity, đặt sau `UseRouting` có thể đủ.
- Nếu audit cần ghi outcome 401/403 và duration, có thể đặt middleware ở vị trí cho phép nó wrap authentication/authorization rồi quan sát response status sau `_next`.
- Dùng structured logging với trace ID, endpoint route pattern và authentication scheme thay vì log raw token/claims nhạy cảm.
- Test custom extension methods vì hidden middleware insertion có thể thay pipeline giữa environments.

### Senior+

- Phân biệt middleware-level cross-cutting concerns với authorization handlers/resource-based authorization; không duplicate policy logic trong middleware.
- Nếu có multiple authentication schemes, explicit `AuthenticateAsync("scheme")` có thể có lý do trong specialized flow, nhưng phải hiểu nó thay đổi assumptions và có thể authenticate nhiều lần.
- Nhận ra endpoint metadata chỉ tồn tại sau routing và có thể khác giữa branches/pipeline maps.
- Xem pipeline ordering là một security boundary: CORS, authentication, authorization, exception handling, forwarded headers và rate limiting đều có order semantics cần thiết kế có chủ đích.

## Hướng giải quyết tham khảo

Trong ASP.NET Core, middleware tạo thành request pipeline. Với explicit pipeline như ví dụ, request đi qua middleware theo thứ tự đăng ký:

```text
Request
  ↓
RequestAuditMiddleware
  ↓
UseRouting
  ↓
UseAuthentication
  ↓
UseAuthorization
  ↓
Endpoint
  ↑
Response unwinds theo chiều ngược lại
```

Do `RequestAuditMiddleware` chạy trước `UseRouting`, `HttpContext.GetEndpoint()` chưa có selected endpoint nên có thể trả `null`. Do nó cũng chạy trước `UseAuthentication`, JWT bearer handler chưa chạy để populate authenticated principal theo normal pipeline, vì vậy `context.User.Identity.IsAuthenticated` có thể là `false`.

Sau khi middleware gọi `_next(context)`, request tiếp tục. Routing chọn endpoint, authentication xử lý credentials/token, authorization đọc endpoint metadata và policy `Orders.Read`. Vì vậy endpoint vẫn có thể trả 401/403 chính xác dù audit middleware trước đó thấy anonymous state.

Một ordering phù hợp hơn nếu middleware cần endpoint + user:

```csharp
app.UseRouting();
app.UseAuthentication();

app.UseMiddleware<RequestAuditMiddleware>();

app.UseAuthorization();

app.MapGet("/orders/{id}", GetOrder)
   .RequireAuthorization("Orders.Read");
```

Tuy nhiên vị trí này còn tùy responsibility. Nếu middleware cần biết authorization **outcome**, một pattern khác là để nó wrap authorization:

```csharp
app.UseRouting();
app.UseAuthentication();

app.UseMiddleware<RequestAuditMiddleware>();

app.UseAuthorization();
```

Trong middleware:

```csharp
public async Task InvokeAsync(HttpContext context)
{
    var endpoint = context.GetEndpoint();
    var userId = context.User.FindFirst("sub")?.Value;
    var started = Stopwatch.GetTimestamp();

    try
    {
        await _next(context);
    }
    finally
    {
        _logger.LogInformation(
            "Request {TraceId} Endpoint={Endpoint} User={UserId} Status={Status}",
            context.TraceIdentifier,
            endpoint?.DisplayName,
            userId,
            context.Response.StatusCode);
    }
}
```

Nếu tenant rule thực chất là “user phải có tenant claim phù hợp với resource/route”, tôi ưu tiên policy-based/resource-based authorization thay vì custom middleware:

```csharp
options.AddPolicy("TenantMember", policy =>
    policy.RequireAuthenticatedUser()
          .AddRequirements(new TenantAccessRequirement()));
```

Sau đó handler đọc route/resource/context phù hợp và trả authorization result. Điều này giữ access-control semantics trong authorization system, dễ test hơn và tránh việc middleware tự tạo 401/403 không nhất quán.

`AuthenticateAsync()` thủ công không phải fix mặc định. Nó hữu ích trong specialized flows khi cần chủ động authenticate một scheme cụ thể hoặc khi component cố ý chạy ngoài normal auth middleware semantics. Nhưng nếu chỉ vì custom middleware được đặt trước `UseAuthentication`, sửa order đơn giản và rõ hơn.

Kế hoạch xác minh production:

- log pipeline markers trong non-sensitive diagnostic environment;
- log selected endpoint after routing;
- log authentication scheme/result nhưng không log JWT raw token;
- correlate `TraceIdentifier`/Activity trace ID;
- test 4 cases: anonymous public, anonymous protected, authenticated-but-forbidden, authenticated-and-authorized;
- verify branches (`Map`, `UseWhen`) và extension methods nội bộ;
- integration test bằng `WebApplicationFactory` để bảo vệ ordering khỏi regression.

Microsoft Learn hiện tại mô tả middleware order là critical và hướng dẫn typical order gồm routing → authentication → authorization. Tài liệu tham khảo:

- ASP.NET Core middleware: `https://learn.microsoft.com/aspnet/core/fundamentals/middleware/?view=aspnetcore-10.0`
- ASP.NET Core authentication overview: `https://learn.microsoft.com/aspnet/core/security/authentication/`
- ASP.NET Core authorization: `https://learn.microsoft.com/aspnet/core/security/authorization/introduction`

## Mẫu trả lời trong phỏng vấn

“Em sẽ giải thích từ pipeline trước. Middleware chạy theo thứ tự đăng ký trên request path. Ở code này audit middleware chạy trước `UseRouting`, nên endpoint chưa được select và `GetEndpoint()` có thể null. Nó cũng chạy trước `UseAuthentication`, nên JWT handler chưa populate authenticated principal. Sau khi audit gọi `_next`, request mới đi qua routing, authentication rồi authorization, nên endpoint vẫn reject thiếu permission đúng.

Nếu audit cần endpoint và user, em đặt nó sau routing + authentication. Nếu tenant check là access-control rule thì em ưu tiên authorization policy/handler thay vì duplicate authorization trong middleware. Em không gọi `AuthenticateAsync()` thủ công chỉ để chữa ordering sai; explicit authenticate chỉ dùng khi có specialized multi-scheme flow hoặc component cố ý cần chủ động authenticate.

Em verify bằng integration tests cho anonymous/401/403/200, log trace ID + endpoint + scheme/result ở mức không lộ secret, đồng thời review các `Map`/`UseWhen` và extension methods có thể thay pipeline. Với pipeline, ordering là một phần của security design chứ không chỉ style.”

## Câu hỏi đào sâu

1. Nếu audit middleware cần ghi cả endpoint metadata trước request và authorization outcome sau request, bạn đặt nó ở đâu và code structure thế nào?
2. Nếu application dùng cả cookie authentication cho CMS editor và JWT bearer cho API, bạn quyết định default scheme/policy scheme và explicit authentication ra sao?
3. Một teammate muốn đưa tenant authorization hoàn toàn vào middleware để “nhanh hơn policy handler”. Bạn sẽ phản biện hoặc đồng ý trong trường hợp nào?

## Lỗi trả lời thường gặp

- Cho rằng authentication chạy song song nên middleware “đọc quá sớm”.
- Gọi `AuthenticateAsync()` thủ công ở mọi request mà không sửa pipeline ordering.
- Nhầm authentication với authorization.
- Đọc endpoint metadata trước routing rồi kết luận endpoint metadata bị lỗi.
- Đưa access-control logic quan trọng vào custom middleware mà không đánh giá policy/handler semantics và testability.

## Thang điểm 0–10

- **0–2:** chỉ nói “đổi thứ tự middleware” mà không giải thích cơ chế.
- **3–4:** hiểu routing/auth ordering nhưng chưa phân biệt trách nhiệm và security impact.
- **5–6:** giải thích đúng endpoint selection, principal population, authorization và đề xuất ordering phù hợp.
- **7–8:** có policy/handler judgment, multiple-scheme awareness, integration tests và production diagnostics.
- **9–10:** phân tích pipeline như security boundary, branch behavior, audit outcome semantics và biết khi nào explicit authentication là justified.

# Câu 2 — Kubernetes pods restart liên tục đúng lúc SQL chậm: app chết thật, readiness sai hay liveness đang tự khuếch đại incident?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core health checks, liveness, readiness, startup probes, SQL Server, load behavior, rolling deployment, resource limits, observability, incident response, failure isolation

## Bối cảnh

Một ASP.NET Core .NET 8 API chạy trên Kubernetes với 12 pods. API phụ thuộc SQL Server và Redis. Traffic đi qua Kubernetes Service/Ingress.

Deployment có probe configuration giản lược:

```yaml
containers:
  - name: api
    image: registry.example.com/orders-api:2026.09.10
    ports:
      - containerPort: 8080
    readinessProbe:
      httpGet:
        path: /health
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2
    livenessProbe:
      httpGet:
        path: /health
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "1"
        memory: "768Mi"
```

Endpoint `/health` hiện kiểm tra:

- process/app startup state;
- kết nối SQL bằng một query nhỏ;
- `PING` Redis;
- một external pricing API.

Incident lúc 10:15:

- SQL p95 tăng từ 80 ms lên 3–6 giây trong khoảng 12 phút;
- Redis vẫn ổn;
- external pricing API có vài timeout nhưng không outage hoàn toàn;
- nhiều pods chuyển NotReady rồi sau đó restart;
- tổng throughput giảm mạnh;
- remaining pods nhận nhiều traffic hơn và latency tiếp tục tăng;
- logs có request timeout nhưng không có unhandled process crash rõ ràng;
- `kubectl describe pod` cho thấy liveness probe failures trên một số pods;
- CPU khoảng 55–70%, memory dưới limit trên phần lớn pods;
- HPA scale thêm pods nhưng warm-up mất khoảng 25 giây;
- team đề xuất tăng `failureThreshold` thật lớn để “hết restart”;
- team khác muốn bỏ probes hoàn toàn;
- chưa biết `/health` có cache result, timeout từng dependency hay gọi dependencies tuần tự.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo flow **impact → stabilize → evidence → competing hypotheses → verification → root cause → remediation → prevention**. Giải thích sự khác nhau về operational semantics giữa readiness, liveness và startup probe; vì sao dùng cùng một dependency-heavy `/health` cho cả readiness và liveness có thể tạo cascading failure; và cách bạn thiết kế lại health checks/probes cho một ASP.NET Core application phụ thuộc SQL/Redis/external API.

## Câu hỏi làm rõ nên cân nhắc

1. API có thể phục vụ degraded traffic khi SQL chậm hoặc pricing API lỗi không, hay các dependency đó đều bắt buộc cho mọi endpoint?
2. Pod restart là do liveness failure, OOMKilled, process exit hay deployment rollout?
3. `/health` mất bao lâu cho từng dependency và có timeout budget riêng không?
4. Startup warm-up 25 giây có thể bị liveness probe đánh fail trước khi app thật sự ready không?
5. SQL degradation ảnh hưởng toàn cluster đồng đều hay một subset connections/queries/tenants?

## Gợi ý tư duy

### Gợi ý 1

Readiness trả lời “có nên gửi traffic vào pod này không?”, còn liveness phải gần hơn với “process này có ở trạng thái mà restart có khả năng cứu được không?”.

### Gợi ý 2

Nếu liveness phụ thuộc trực tiếp vào một shared database đang chậm, restart application pods không sửa database — nhưng có thể giảm capacity và tăng load trên pods còn lại.

### Gợi ý 3

Health check design cần phản ánh **failure ownership và degradation semantics**, không chỉ gom mọi dependency vào một endpoint.

## Cấu trúc trả lời đề xuất

1. Xác định business/user impact và blast radius.
2. Stabilize traffic/capacity trước khi deep-dive.
3. Xác nhận chính xác reason của pod restarts.
4. Correlate probe failures với SQL latency và request latency.
5. Phân biệt readiness/liveness/startup semantics.
6. Liệt kê competing hypotheses ngoài probe misconfiguration.
7. Sửa immediate probe behavior nếu evidence rõ.
8. Điều tra SQL root cause riêng.
9. Thiết kế health endpoints theo dependency criticality.
10. Test failure injection/load/slow-start.
11. Monitor probe status, restarts, endpoint saturation và dependency health.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Liveness failure có thể khiến kubelet restart container; readiness failure chủ yếu làm pod không nhận regular service traffic; startup probe bảo vệ slow-starting container khỏi liveness/readiness bắt đầu quá sớm.
- Dùng cùng dependency-heavy endpoint cho readiness và liveness có thể sai semantics.
- Nếu SQL là shared dependency bị chậm, liveness fail vì SQL rồi restart pod thường không chữa được SQL; nó có thể làm giảm serving capacity và tăng traffic trên remaining ready pods.
- Nếu tất cả pods đồng thời fail readiness do một dependency shared outage, Service có thể mất gần toàn bộ endpoints; cần cân nhắc dependency criticality và degraded behavior.
- Liveness nên kiểm tra trạng thái mà restart application có khả năng khắc phục, không nên mặc định fail chỉ vì external dependency bị chậm.
- Startup probe hữu ích khi application legitimately cần warm-up lâu; chỉ tăng liveness delay tùy tiện không phải lúc nào cũng rõ semantics bằng startup probe.
- Cần xác minh actual restart reason, không suy từ biểu đồ restart count.
- Probe timeout/period/failure threshold là operational knobs, nhưng tune values không thay thế đúng health semantics.
- Incident còn cần điều tra SQL latency root cause; probe bug có thể chỉ là amplifier, không phải nguyên nhân ban đầu.

### Điểm cộng

- Tách `/health/live`, `/health/ready` và có thể dependency-specific diagnostics không public.
- Liveness chỉ kiểm tra process/event-loop/runtime critical state; readiness có thể kiểm tra dependencies bắt buộc cho serving traffic.
- Optional dependency như reviews/pricing có thể degrade feature thay vì làm entire pod NotReady nếu business cho phép.
- Dùng timeout budgets nhỏ và parallelize health dependency checks có kiểm soát nếu readiness thật sự cần nhiều dependencies.
- Tránh health checks tạo load đáng kể lên SQL/third-party API khi 12 pods probe mỗi vài giây.
- Có PodDisruptionBudget/rollout settings hợp lý nhưng không dùng chúng để che liveness misconfiguration.

### Senior+

- Nhận ra probe traffic bản thân có thể tạo synchronized dependency load; jitter không phải probe feature mặc định để dựa vào, nên endpoint phải rẻ và downstream-safe.
- Phân tích positive feedback loop: dependency chậm → probes fail → pods removed/restarted → capacity giảm → load/pod tăng → latency tăng → thêm probe failures.
- Tách application health khỏi downstream health và dùng circuit breaker/degradation/admission control theo business semantics.
- Đưa probe behavior vào chaos/failure-path testing chứ không chỉ deployment smoke test.
- Nhận ra readiness fail toàn bộ fleet trong shared-dependency outage có thể làm ingress behavior khó đoán; cần explicit fallback/maintenance strategy tùy system.

## Hướng giải quyết tham khảo

### 1. Stabilize

Tôi sẽ không bắt đầu bằng việc tăng threshold hoặc restart toàn bộ deployment. Trước hết xác nhận:

```bash
kubectl get pods
kubectl describe pod <pod>
kubectl get events --sort-by=.lastTimestamp
kubectl logs <pod> --previous
```

Mục tiêu là phân biệt:

- liveness-triggered restart;
- OOMKilled;
- process crash;
- rollout replacement;
- node issue.

Nếu evidence cho thấy liveness đang fail vì `/health` timeout theo SQL degradation, một mitigation có thể là hotfix probe endpoint/route hoặc tạm thời chuyển liveness sang app-only check có semantics đúng, thay vì vô hiệu hóa toàn bộ health model.

Đồng thời stabilize SQL/downstream: giảm expensive traffic nếu có feature flag, throttle high-cost requests, pause non-critical background work, scale database/capacity nếu evidence hỗ trợ và có runbook cho phép.

### 2. Semantics

Kubernetes documentation hiện mô tả:

- **Readiness probe:** pod có sẵn sàng nhận traffic hay không; failure làm pod bị loại khỏi matching Service endpoints.
- **Liveness probe:** xác định khi nào container nên được restart.
- **Startup probe:** xác định application đã startup chưa; nếu cấu hình, liveness/readiness không chạy cho tới khi startup probe thành công.

Tài liệu:

- `https://kubernetes.io/docs/concepts/workloads/pods/probes/`
- `https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/`

### 3. Vì sao endpoint hiện tại nguy hiểm

`/health` gọi SQL + Redis + pricing API. Giả sử SQL p95 tăng 6 giây trong khi probe timeout 2 giây:

```text
SQL slow
  ↓
/health > 2s
  ↓
liveness fails repeatedly
  ↓
pod restarted
  ↓
capacity temporarily decreases
  ↓
traffic concentrates on remaining pods
  ↓
request latency / downstream load rises
  ↓
more probe failures
```

Restart pod không sửa shared SQL service. Đây là classic case health signal không align với recovery action.

### 4. Thiết kế lại health endpoints

ASP.NET Core health checks có thể tag checks và map endpoints riêng:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<ProcessHealthCheck>(
        "self",
        tags: new[] { "live" })
    .AddCheck<SqlReadinessHealthCheck>(
        "sql",
        tags: new[] { "ready" })
    .AddCheck<RedisReadinessHealthCheck>(
        "redis",
        tags: new[] { "ready" });

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = registration => registration.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = registration => registration.Tags.Contains("ready")
});
```

YAML concept:

```yaml
startupProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 5
  failureThreshold: 8

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 2
```

Các con số chỉ là ví dụ concept; production values phải lấy từ measured startup time, dependency latency và desired detection/recovery window.

Nếu pricing API chỉ ảnh hưởng một optional enrichment trên 10% endpoints, tôi có thể không đưa nó vào global readiness. Thay vào đó endpoint đó degrade/fail riêng với timeout/circuit breaker/fallback phù hợp.

Nếu SQL là absolutely required cho mọi useful request, readiness check SQL có thể hợp lý. Nhưng check phải rẻ và có timeout budget rõ. Nếu SQL outage khiến tất cả pods NotReady, operational behavior đó phải được chấp nhận có chủ đích và có upstream maintenance/error strategy.

### 5. Competing hypotheses

Không nên dừng ở “probe sai”. Cần kiểm tra:

- SQL blocking/deadlock/query regression;
- connection pool exhaustion;
- CPU throttling dù average CPU nhìn thấp;
- ThreadPool starvation;
- DNS/network latency;
- pod/node-specific issue;
- HPA scaling signal lag;
- health endpoint sequential calls làm tổng timeout lớn;
- external pricing API slowdown cùng thời điểm;
- startup probes thiếu khiến new HPA pods restart trước warm-up xong.

### 6. Testing

- failure injection: SQL latency 5–10 giây, verify pods không restart chỉ vì shared SQL slowdown;
- readiness test: critical SQL dependency unavailable, verify pod leaves traffic according to intended policy;
- slow startup test 25–40 giây với startup probe;
- load test trong khi một dependency degraded để xem positive feedback loop có xuất hiện;
- rollout test với partial pods ready/unready.

### 7. Observability

Theo dõi cùng timeline:

- pod restart reason/count;
- readiness/liveness failure rate;
- ready pod count;
- request RPS/p95/p99/error rate mỗi pod;
- CPU throttling, memory/OOM;
- SQL dependency duration/errors/waits;
- connection pool metrics;
- HPA desired/current replicas;
- health endpoint duration và per-check duration;
- Application Insights traces/correlation nếu dùng.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xác nhận restart reason trước; không suy từ restart count. Nếu `describe pod` cho thấy liveness fail đúng lúc SQL p95 3–6 giây, em coi probe configuration là một amplifier mạnh. Readiness quyết định pod có nhận traffic; liveness quyết định có restart container; startup probe bảo vệ slow startup. Dùng cùng endpoint gọi SQL/Redis/external API cho cả readiness và liveness khiến một shared dependency slowdown có thể restart app dù restart không sửa dependency.

Em stabilize bằng cách pause các thay đổi gây thêm load, tách liveness sang app-only health nếu evidence rõ, đồng thời điều tra SQL root cause. Sau đó em tách `/health/live` và `/health/ready`; chỉ dependency thực sự bắt buộc mới ảnh hưởng readiness, optional dependency degrade riêng. Với warm-up 25 giây, em dùng startup probe được tune từ measured startup time.

Em test SQL slow, dependency outage, slow startup và load để chắc rằng failure không tạo vòng lặp restart → capacity giảm → load/pod tăng. Telemetry phải correlate probe failures, ready pod count, restart reason, request latency và SQL dependency metrics. Em không bỏ probes; em sửa semantics để recovery action phù hợp signal.”

## Câu hỏi đào sâu

1. Nếu SQL là bắt buộc cho 95% endpoints nhưng một số static/config endpoints vẫn dùng được, readiness nên phản ánh toàn pod hay nên tách workload/routes?
2. Nếu bạn bỏ SQL khỏi liveness và process bị deadlock nhưng `/health/live` vẫn trả 200 từ một path khác, bạn thiết kế self-health thế nào để restart thực sự hữu ích?
3. Một teammate đề xuất liveness gọi cả SQL, Redis, Service Bus và ba external APIs vì “health phải kiểm tra tất cả”. Bạn sẽ dùng nguyên tắc nào để phản biện?

## Lỗi trả lời thường gặp

- Thấy pod restart rồi chỉ tăng memory limit mà không xem restart reason.
- Dùng dependency-heavy check cho liveness mà không xét recovery action.
- Bỏ probes hoàn toàn vì một incident do probe thiết kế sai.
- Chỉ sửa probes nhưng không tiếp tục điều tra SQL degradation ban đầu.
- Tune threshold bằng cảm tính, không dựa trên startup/latency/failure-window measurements.

## Thang điểm 0–10

- **0–2:** chỉ tăng threshold, replicas hoặc restart cluster.
- **3–4:** biết readiness/liveness khác nhau nhưng chưa gắn với cascading failure.
- **5–6:** có incident flow, đúng probe semantics và tách live/ready hợp lý.
- **7–8:** có failure ownership, degraded dependency policy, startup behavior, test/telemetry rõ.
- **9–10:** mô hình hóa positive feedback loop, recovery action vs health signal, shared-dependency failure và operational trade-offs có điều kiện.

# Câu 3 — Upload file lớn lên Azure Blob Storage: backend proxy toàn bộ hay cấp quyền upload trực tiếp cho browser/mobile?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, SAS, user delegation SAS, large-file upload, security, authorization, metadata, reliability, resumability, malware scanning, observability, API design, architecture trade-offs

## Bối cảnh

Một document-management module cho phép user upload attachments từ web và mobile client.

Requirements ban đầu:

- file phổ biến 1–20 MB;
- một số file 500 MB–5 GB;
- cần hỗ trợ nhiều application instances;
- backend ASP.NET Core chạy trên Azure App Service;
- Azure Blob Storage là candidate chính cho object storage;
- user phải chỉ upload vào logical area mà họ được authorize;
- file chưa được scan malware không được phép trở thành downloadable/public content;
- business muốn progress bar và retry tốt cho mạng mobile không ổn định;
- metadata nghiệp vụ nằm trong SQL Server;
- file binary không cần transaction atomically cùng SQL metadata nếu có recovery/reconciliation rõ;
- public anonymous upload không được phép;
- download có cả private authenticated flow và một số share links có expiry;
- security team không muốn storage account key nằm trong source/config nếu có lựa chọn tốt hơn;
- team đang tranh luận hai hướng:
  1. browser/mobile upload multipart vào ASP.NET Core API, backend stream sang Blob;
  2. backend authorize rồi cấp SAS ngắn hạn để client upload trực tiếp Blob Storage.
- chưa chốt max concurrency, regions, exact antivirus product, retention hoặc legal hold.

## Câu hỏi chính

Hãy thiết kế upload/download architecture cho hệ thống này. So sánh **backend-proxy upload** với **direct-to-Blob upload bằng scoped short-lived SAS**, bao gồm authorization, Managed Identity, blob naming, metadata transaction boundary, large-file/resumable upload, malware-scanning workflow, failure recovery, share links, observability và deployment. Bạn phải chỉ ra khi nào solution đơn giản qua backend là đủ và khi nào direct upload đáng complexity hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads và typical egress/ingress volume qua App Service là bao nhiêu?
2. Có requirement phải resume upload sau app/browser restart hay chỉ retry chunk/request?
3. File nào được phép download trước scan, nếu có, và scan SLA là bao lâu?
4. Share link có cần revocation trước expiry không hay expiry-only là đủ?
5. Metadata record được tạo trước upload, sau upload hay theo explicit upload-session state machine?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu bằng trust boundary: backend phải authorize **ai được upload cái gì vào đâu**, dù binary có đi xuyên backend hay không.

### Gợi ý 2

Direct upload giảm application bandwidth/copying nhưng chuyển thêm responsibility sang upload-session, scoped credentials, client retry và reconciliation.

### Gợi ý 3

“Blob đã tồn tại” không đồng nghĩa “file đã được business chấp nhận”. Hãy thiết kế lifecycle trước scan và sau scan.

## Cấu trúc trả lời đề xuất

1. Clarify file size/concurrency/security requirements.
2. Xác định data ownership: SQL metadata vs Blob binary.
3. So sánh proxy vs direct upload.
4. Thiết kế authorization + credential flow.
5. Thiết kế blob key/naming và overwrite prevention.
6. Thiết kế upload-session state machine.
7. Xử lý chunk/resume/network failure.
8. Thiết kế malware scan/quarantine/publish.
9. Thiết kế download/share-link authorization.
10. Reconciliation/cleanup orphan data.
11. Observability, quotas và abuse controls.
12. Deployment/rollout và trade-offs.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không expose storage account key cho browser/mobile.
- Backend vẫn phải authenticate/authorize user trước khi cấp quyền upload trực tiếp.
- Direct upload credential phải giới hạn resource, permissions và lifetime; không cấp container-wide broad access nếu chỉ cần một blob/session.
- Managed Identity có thể được dùng cho backend access tới Azure Storage/để lấy user delegation key khi RBAC phù hợp, tránh lưu account key trong application.
- User delegation SAS được ký dựa trên Microsoft Entra credentials và là lựa chọn Microsoft khuyến nghị khi SAS cần thiết.
- Backend-proxy streaming đơn giản hơn về control path nhưng tiêu tốn application bandwidth/connections và có thể trở thành bottleneck/cost point với multi-GB concurrent uploads.
- Direct-to-Blob giảm data path qua backend nhưng cần state/reconciliation/security design tốt hơn.
- Binary Blob và SQL metadata không có distributed atomic transaction mặc định; cần explicit state machine/idempotency/reconciliation.
- File chưa scan nên ở trạng thái quarantine/pending và không được expose qua normal download path.
- Filename do user cung cấp không nên được dùng trực tiếp làm authoritative blob path nếu nó tạo overwrite/path/security ambiguity.

### Điểm cộng

- Dùng server-generated immutable `UploadId`/blob key; original filename chỉ là metadata đã sanitize/encode phù hợp khi hiển thị.
- Tạo upload session với expected size/content type/checksum policy và expiry.
- Với large files, dùng block blob/chunked upload semantics và retry individual blocks nếu client SDK hỗ trợ.
- Sau upload, client gọi finalize API hoặc storage event/workflow kích hoạt verification; backend kiểm tra blob properties/size trước chuyển state.
- Malware scanning async và idempotent; infected file chuyển `Rejected/Quarantined`, clean file chuyển `Available`.
- Cleanup job xóa orphan/pending uploads hết hạn theo retention policy.
- Private download có thể backend-authorized rồi redirect/cấp read SAS ngắn hạn; share link cần revocation model nếu business yêu cầu.

### Senior+

- Tách upload authorization token/session khỏi final business record, tránh client tự quyết blob destination hoặc owner metadata.
- Với direct upload, backend tạo user delegation SAS chỉ cho blob cụ thể, write/create permissions tối thiểu và TTL ngắn; client không được list container.
- Nhận ra SAS là bearer credential: ai có token trong lifetime có permissions được grant; cần TLS, tránh log URL query, và có incident/revocation strategy.
- Thiết kế dedupe/checksum như optional optimization chứ không biến client-provided hash thành trust signal duy nhất.
- Có state machine chịu được mọi thứ tự failure: SQL session created nhưng upload chưa xảy ra; blob có nhưng finalize mất; scan thành công nhưng DB update fail; client retry finalize.
- Chọn proxy/direct theo measured file distribution và concurrency, không theo “cloud best practice” tuyệt đối.

## Hướng giải quyết tham khảo

### 1. Ownership

Tôi tách:

```text
SQL Server
- UploadSession
- DocumentAttachment
- owner / tenant / permissions
- original filename
- content type
- size/checksum
- scan status
- lifecycle timestamps

Azure Blob Storage
- binary object
- storage metadata tối thiểu
```

SQL giữ business authorization/state. Blob path không phải authorization database.

Một state machine đơn giản:

```text
Created
  → Uploading
  → Uploaded
  → Scanning
  → Available
  ↘ Failed / Expired / Rejected
```

Transitions phải idempotent.

### 2. Option A — Backend proxy

Flow:

```text
Client
  → ASP.NET Core API
      → authorize
      → stream request body
      → Blob Storage
      → update metadata
```

Ưu điểm:

- control path đơn giản;
- client không cần SAS logic;
- backend dễ enforce policy trong cùng request path;
- phù hợp nếu files nhỏ, concurrency thấp và App Service bandwidth không là bottleneck.

Nhược điểm:

- mỗi byte đi qua App Service;
- application giữ request/network resources lâu hơn;
- multi-GB concurrent uploads làm scale/cost/failure handling phức tạp;
- retry có thể phải upload lại nhiều dữ liệu nếu protocol không hỗ trợ chunk/resume tốt.

Nếu dùng proxy, phải **stream**, không buffer toàn file vào memory:

```csharp
await blobClient.UploadAsync(
    request.Body,
    overwrite: false,
    cancellationToken: ct);
```

Actual implementation cần size limits, content-type policy, timeout strategy và SDK options phù hợp.

### 3. Option B — Direct-to-Blob

Flow:

```text
1. Client → POST /upload-sessions
2. Backend authenticates + authorizes
3. Backend creates UploadId/blob key + DB session
4. Backend obtains constrained upload SAS
5. Client → Azure Blob Storage directly
6. Client → POST /upload-sessions/{id}/complete
7. Backend verifies blob properties
8. Scan workflow
9. State → Available
```

Backend trên Azure có thể dùng `DefaultAzureCredential`/Managed Identity cho Blob service access phù hợp với environment/RBAC. Khi cần SAS, Microsoft khuyến nghị user delegation SAS thay vì account-key-signed SAS khi có thể.

Conceptual C#:

```csharp
var credential = new DefaultAzureCredential();
var serviceClient = new BlobServiceClient(
    new Uri(storageAccountUrl),
    credential);

var startsOn = DateTimeOffset.UtcNow.AddMinutes(-1);
var expiresOn = DateTimeOffset.UtcNow.AddMinutes(10);

var delegationKey = await serviceClient.GetUserDelegationKeyAsync(
    startsOn,
    expiresOn,
    ct);

var sasBuilder = new BlobSasBuilder
{
    BlobContainerName = containerName,
    BlobName = blobName,
    Resource = "b",
    StartsOn = startsOn,
    ExpiresOn = expiresOn
};

sasBuilder.SetPermissions(
    BlobSasPermissions.Create | BlobSasPermissions.Write);

var sas = sasBuilder.ToSasQueryParameters(
    delegationKey.Value,
    serviceClient.AccountName);
```

Đây là concept; exact SDK APIs/permissions phải được verify với package version đang dùng.

Tài liệu hiện hành:

- User delegation SAS: `https://learn.microsoft.com/rest/api/storageservices/create-user-delegation-sas`
- Authorize Blob access with Microsoft Entra ID: `https://learn.microsoft.com/azure/storage/blobs/authorize-access-azure-active-directory`
- Azure Blob Storage .NET client: `https://learn.microsoft.com/azure/storage/blobs/storage-quickstart-blobs-dotnet`

SAS phải được xem như bearer credential. Không log full SAS URI. TTL ngắn, resource scope hẹp, HTTPS-only, permissions tối thiểu.

### 4. Blob naming

Không dùng:

```text
/{tenant}/{userSuppliedFileName}
```

như authoritative key nếu có overwrite/collision ambiguity.

Dùng server-generated key:

```text
/{tenantId}/{uploadId}/{blobId}
```

Original filename lưu SQL và chỉ dùng cho display/download `Content-Disposition` sau khi sanitize/encode.

### 5. Upload verification

Client nói “upload thành công” không đủ. Finalize endpoint kiểm tra:

- session thuộc user/tenant;
- session chưa expired;
- blob đúng expected path;
- blob tồn tại;
- size hợp lệ;
- optional checksum/header requirements;
- state transition chưa bị finalize trước đó.

Finalize phải idempotent vì mobile network có thể mất response rồi retry.

### 6. Malware scanning

Không đưa blob mới upload trực tiếp vào normal downloadable container/path nếu chưa scan.

Một flow:

```text
Uploaded blob
  ↓
Queue/Event/scan worker
  ↓
Scanning
  ├─ clean     → Available
  ├─ infected  → Rejected/Quarantined
  └─ transient failure → retry / manual review
```

Có thể cùng container với access policy/state gate hoặc quarantine container riêng tùy security model. Quan trọng là normal download API chỉ cấp access khi SQL status = `Available` và blob identity match expected record.

Scan result processing phải idempotent. Nếu scan clean nhưng DB update fail, retry transition. Nếu blob event delivered duplicate, same UploadId/blob key không tạo duplicate attachment.

### 7. Download/share links

Private download:

```text
Client → API → authenticate/authorize → short-lived read access → Blob
```

Có thể backend proxy download khi file nhỏ/sensitive policy cần full mediation; hoặc issue read SAS/redirect khi volume lớn.

Share link không nhất thiết chính là long-lived Blob SAS. Một design an toàn hơn khi cần revoke trước expiry:

```text
Public share token → application validates share record/status/expiry
                   → application issues very short-lived Blob read SAS
```

Như vậy revoke share record ở application layer có hiệu lực cho future downloads, dù một short-lived SAS đã phát vẫn sống tới expiry của nó.

### 8. Failure recovery

Cases phải xử lý:

- DB session created, client không upload → expire + cleanup;
- blob uploaded, complete call lost → client retry/reconciliation finds blob;
- complete succeeds, scan event lost → periodic reconciliation enqueues pending scan;
- scan complete, DB update fails → idempotent retry;
- user cancels midway → uncommitted blocks/session expiry cleanup;
- SAS expires giữa upload → authenticated client request new SAS for same authorized session, không tạo owner/path mới tùy tiện.

### 9. Security

- authenticate + authorize trước session/SAS creation;
- no account keys in client;
- backend uses Managed Identity/RBAC when appropriate;
- validate quotas/max file size/content type but do not trust MIME extension alone;
- malware scan before availability;
- escape/sanitize filename on UI/download headers;
- prevent overwrites unless explicit versioning semantics;
- avoid logging SAS query strings;
- rate-limit upload session creation;
- storage firewall/private endpoint decisions depend on whether direct public client upload is required.

Một trade-off quan trọng: direct browser upload tới Blob requires network access path from clients to Blob endpoint. Nếu organization requires storage reachable only via private network inaccessible to public/mobile clients, backend proxy or different edge architecture may be required.

### 10. Testing

- integration test authorization: user không thể xin SAS cho document/tenant khác;
- failure-path test SAS expires giữa multi-block upload và session resumes safely;
- large-file test 5 GB với network interruption/retry;
- malware workflow test duplicate events + scanner timeout;
- reconciliation test orphan blob/session và lost finalize callback;
- security test share-link revoke/expiry và log redaction.

### 11. Observability

Metrics/traces:

- upload session created/completed/expired;
- bytes uploaded và duration;
- proxy bandwidth nếu Option A;
- direct upload completion/error rate nếu Option B;
- SAS issuance count + TTL category, không log token;
- scan queue depth/age/failure;
- time `Uploaded → Available`;
- orphan cleanup count;
- Blob 4xx/5xx/throttling;
- finalize retry/idempotency hits;
- download authorization failures/share-link usage.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn direct Blob chỉ vì file lớn; em lấy distribution và concurrency trước. Với file 1–20 MB và traffic thấp, backend streaming có thể đơn giản và đủ tốt. Nhưng nếu nhiều uploads 500 MB–5 GB chạy đồng thời, proxy toàn bộ byte qua App Service tạo bandwidth/resource bottleneck, nên direct-to-Blob đáng cân nhắc.

Dù direct upload, backend vẫn authenticate/authorize trước. Em tạo UploadSession + server-generated blob key, rồi cấp short-lived scoped SAS chỉ cho blob đó. Backend dùng Managed Identity; nếu cần SAS, em ưu tiên user delegation SAS thay vì expose account key. Client upload trực tiếp, sau đó finalize idempotently; backend verify blob rồi đưa vào `Scanning`, chỉ chuyển `Available` khi malware scan sạch.

SQL metadata và Blob không atomic nên em thiết kế state machine + reconciliation cho orphan session/blob, lost finalize và duplicate scan event. Private download hoặc share link sẽ qua application authorization; nếu cần revoke share link sớm, public share token có thể đổi lấy read SAS rất ngắn thay vì phát SAS dài hạn.

Em test large-file retry, expired SAS, cross-tenant authorization, scan failures và cleanup; monitor upload completion, scan latency, Blob errors và orphan rate. Complexity của direct upload chỉ đáng khi measured size/concurrency và user experience thực sự cần nó.”

## Câu hỏi đào sâu

1. Nếu security yêu cầu Storage Account chỉ dùng Private Endpoint và mobile clients ở Internet không có private-network access, direct-to-Blob design phải thay đổi thế nào?
2. Nếu upload 5 GB đã hoàn tất nhưng client mất mạng trước khi gọi `complete`, bạn làm sao phân biệt orphan blob với valid upload cần recover?
3. Một teammate đề xuất cấp container-level SAS 24 giờ để client tự retry thoải mái. Bạn đánh giá trade-off và thiết kế thay thế thế nào?

## Lỗi trả lời thường gặp

- Phát storage account key hoặc broad SAS cho client.
- Dùng original filename làm blob key và cho phép overwrite ngoài ý muốn.
- Xem Blob upload success là đủ để file trở thành downloadable trước scan.
- Giả định SQL metadata + Blob write có atomic transaction chung.
- Chọn direct upload hoặc proxy upload tuyệt đối mà không dựa trên file size, concurrency, network/security constraints.

## Thang điểm 0–10

- **0–2:** chỉ nói “dùng Blob + SAS” mà không có security/state model.
- **3–4:** hiểu direct vs proxy nhưng bỏ qua scan/reconciliation/authorization scope.
- **5–6:** có session, scoped credential, state machine, scan và failure handling cơ bản.
- **7–8:** có Managed Identity/user delegation SAS, idempotency, resumability, share-link revocation và production observability.
- **9–10:** phân tích trust/network boundaries, distributed failure states, lifecycle security và lựa chọn architecture conditional theo measured traffic + operational constraints.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- ASP.NET Core middleware ordering quyết định khi endpoint metadata và authenticated principal thực sự khả dụng; pipeline ordering là một phần của security behavior.
- Authentication xác định identity, authorization quyết định quyền truy cập; tenant/resource rules nên ở đúng abstraction thay vì duplicate tùy tiện trong middleware.
- Kubernetes readiness, liveness và startup probe có recovery semantics khác nhau; một health signal chỉ tốt khi action sau failure phù hợp với nguyên nhân mà signal đại diện.
- Shared dependency slowdown có thể bị liveness misconfiguration khuếch đại thành cascading failure qua vòng lặp restart → capacity giảm → load tăng.
- Azure Blob direct upload giảm data path qua backend nhưng yêu cầu authorization, scoped credentials, upload-session state machine, malware scan và reconciliation rõ ràng.
- SQL metadata và object storage là hai consistency boundaries; reliability đến từ idempotency + recovery workflow chứ không từ giả định atomicity không tồn tại.

## Mẫu tư duy cần nhớ

- **Place cross-cutting logic only after the runtime state it depends on actually exists.**
- **Match health signals to recovery actions; do not restart an app for a failure restart cannot fix.**
- **Stabilize first, then prove competing hypotheses with correlated evidence.**
- **Treat temporary credentials as bearer secrets: minimize scope, permission and lifetime.**
- **Design explicit state + reconciliation whenever one workflow crosses storage/system boundaries.**
