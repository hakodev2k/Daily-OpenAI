# Code Review Challenge 1 — `HttpClient` retry biến một request checkout thành nhiều payment attempts

**Chủ đề:** C#/.NET, ASP.NET Core, `HttpClient`, resilience, retry, timeout, idempotency, partial failure, SQL Server, third-party API, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core checkout API gọi payment provider bên thứ ba. Production thỉnh thoảng có customer bị charge hai lần khi provider chậm hoặc trả `5xx`. Team đã thêm retry để tăng reliability và thấy tỷ lệ request thành công cao hơn.

Tuy nhiên, logs cho thấy có trường hợp payment provider đã nhận request nhưng client timeout trước khi nhận response. Sau đó retry gửi lại request. Database chỉ ghi `PaymentId` sau khi provider trả success. Provider có hỗ trợ một `Idempotency-Key` header nhưng implementation hiện tại chưa dùng.

Bạn được giao review code sau. Không giả định rằng retry một HTTP `POST` có side effect là an toàn chỉ vì lỗi là transient.

## Code cần review

```csharp
public sealed class PaymentService
{
    private readonly HttpClient _httpClient;
    private readonly AppDbContext _db;
    private readonly ILogger<PaymentService> _logger;

    public PaymentService(
        HttpClient httpClient,
        AppDbContext db,
        ILogger<PaymentService> logger)
    {
        _httpClient = httpClient;
        _db = db;
        _logger = logger;
    }

    public async Task<string> ChargeAsync(
        Guid orderId,
        decimal amount,
        CancellationToken cancellationToken)
    {
        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                var response = await _httpClient.PostAsJsonAsync(
                    "/payments",
                    new { orderId, amount },
                    cancellationToken);

                if ((int)response.StatusCode >= 500)
                    continue;

                response.EnsureSuccessStatusCode();

                var payment = await response.Content
                    .ReadFromJsonAsync<PaymentResponse>(cancellationToken);

                var order = await _db.Orders
                    .SingleAsync(x => x.Id == orderId, cancellationToken);

                order.PaymentId = payment!.Id;
                order.Status = "Paid";

                await _db.SaveChangesAsync(cancellationToken);

                return payment.Id;
            }
            catch (TaskCanceledException ex)
            {
                _logger.LogWarning(ex,
                    "Payment timeout for order {OrderId}, retrying", orderId);
            }
        }

        throw new InvalidOperationException("Payment failed after retries");
    }
}
```

## Nhiệm vụ review

1. Xác định correctness/reliability risks quan trọng và failure windows.
2. Giải thích tại sao timeout không chứng minh provider chưa thực hiện charge.
3. Thiết kế idempotency boundary phù hợp giữa order, local database và payment provider.
4. Phân biệt retryable transport failure, provider response và business rejection.
5. Đề xuất test, telemetry và rollout strategy để chứng minh bản sửa chịu được partial failure.

## Gợi ý

### Gợi ý 1

Hãy dựng timeline: request rời application → provider commit side effect → response bị mất → client retry.

### Gợi ý 2

Một database transaction local không thể rollback charge đã xảy ra ở hệ thống bên ngoài.

### Gợi ý 3

Stable operation identity quan trọng hơn số lần HTTP request được gửi.

## Các vấn đề cần tìm

### Bắt buộc

- Retry `POST /payments` không có idempotency key có thể tạo duplicate charge.
- Timeout/cancellation có trạng thái **unknown outcome**; không được suy ra payment chưa xảy ra.
- `TaskCanceledException` có thể đến từ caller cancellation hoặc timeout; retry khi caller đã hủy là sai semantics.
- Retry loop không có backoff/jitter và có thể tăng pressure khi provider degraded.
- `5xx` bị retry mù quáng mà không xét provider contract và idempotency guarantee.
- Local order chỉ được cập nhật sau external success response, tạo failure window giữa remote side effect và local persistence.
- Không có durable payment-attempt state/idempotency record để reconcile trạng thái không chắc chắn.
- `response` chưa được dispose rõ ràng trong loop.
- Không validate order state/amount ở boundary này; concurrent checkout attempts có thể cùng charge một order.

### Điểm cộng

- Dùng stable idempotency key gắn với logical payment attempt, không tạo key mới cho mỗi retry.
- Local unique constraint hoặc concurrency control giúp ngăn nhiều logical payment attempts cho cùng business operation khi requirement yêu cầu.
- Với unknown outcome, query/reconcile provider bằng idempotency key hoặc provider transaction reference nếu API hỗ trợ.
- Tách transport retry policy khỏi business workflow state machine.
- Không log credential/payment-sensitive payload.
- Cân nhắc `IHttpClientFactory`/resilience pipeline theo architecture hiện tại, nhưng library không tự giải quyết idempotency.

## Hướng giải quyết tham khảo

Trước khi gọi provider, hệ thống nên tạo hoặc lấy một durable logical payment attempt có stable identity. Identity này được dùng làm provider `Idempotency-Key` cho mọi retry của cùng operation. Nếu process crash hoặc timeout sau khi provider đã charge, lần retry/recovery tiếp theo dùng cùng key thay vì tạo payment mới.

Order/payment state nên biểu diễn được ít nhất các trạng thái như pending/processing/succeeded/failed/unknown tùy business requirement. Khi outcome không chắc chắn, không tự động chuyển sang “failed” rồi charge lại; cần reconciliation với provider.

Retry chỉ áp dụng cho lỗi được contract xác định là retryable và phải tôn trọng cancellation của caller. Backoff/jitter và timeout budget phải được thiết kế cùng downstream capacity. Một retry policy generic không biến non-idempotent operation thành idempotent.

Local transaction có thể bảo vệ local state nhưng không tạo distributed transaction với payment provider. Vì vậy workflow phải chịu được crash tại mọi boundary: trước request, sau provider commit, trước local `SaveChanges`, và sau local commit nhưng trước response cho caller.

## Test nên có

- Integration/fault-injection test: provider thực hiện charge nhưng response bị timeout; retry phải không tạo charge thứ hai.
- Test hai checkout requests concurrent cho cùng order.
- Test caller cancellation không tiếp tục retry.
- Test provider `400/409/429/500/503` theo contract cụ thể.
- Test process crash giữa provider success và local persistence, sau đó recovery/reconciliation.
- Test idempotency key ổn định qua retry/restart.

## Production observability

Theo dõi payment attempt ID, order ID, provider correlation/reference, attempt count, outcome classification, timeout rate, unknown-state count, reconciliation result và duplicate-prevention events. Không log secrets/card data. Trace phải cho phép dựng timeline local DB ↔ HTTP dependency nhưng không coi absence của response là absence của side effect.

## Trade-offs

- Retry tăng availability cho transient failures nhưng có thể nhân side effects nếu operation không idempotent.
- Durable workflow state tăng schema/implementation complexity nhưng giảm ambiguity khi crash/timeout.
- Reconciliation có thể tăng latency hoặc tạo asynchronous UX, đổi lại tránh charge mù quáng.
- Provider idempotency giúp mạnh đáng kể nhưng vẫn phải hiểu retention window và semantics chính thức của provider.

## Câu hỏi đào sâu

1. Nếu provider chỉ giữ idempotency keys trong 24 giờ nhưng order có thể được retry sau 3 ngày, bạn thiết kế local state/reconciliation thế nào?
2. Nếu application nhận `429`, bạn cần evidence/contract gì trước khi retry và điều chỉnh concurrency?
3. Nếu payment thành công nhưng `SaveChangesAsync` deadlock rồi fail, recovery flow nào tránh charge lại?

## Thang điểm 0–10

- **0–2:** Chỉ tăng số retry hoặc timeout.
- **3–4:** Nhận ra duplicate risk nhưng chưa xử lý unknown outcome.
- **5–6:** Dùng stable idempotency key và phân loại retry/cancellation hợp lý.
- **7–8:** Thiết kế durable state + reconciliation + concurrency protection + failure tests.
- **9–10:** Reasoning đầy đủ về partial failure, provider contract, operational telemetry, rollout và cost of complexity.

# Code Review Challenge 2 — Optimizely content cache làm sai personalization và purge tạo “cache stampede” vào origin

**Chủ đề:** Optimizely CMS, CMS architecture, Akamai/CDN, caching, personalization, HTTP cache semantics, Redis, performance, availability, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một marketing website dùng Optimizely CMS trên ASP.NET Core, chạy nhiều Azure App Service instances phía sau Akamai. Trang product landing có content blocks chung nhưng một block hiển thị offer khác nhau theo market và membership tier.

Để giảm origin load, team cache toàn bộ rendered HTML theo URL trong Redis và trả `Cache-Control: public, max-age=600`. Khi editor publish content, application gọi `FLUSHDB` để tránh stale content. Trong campaign lớn, publish làm Redis cache trống và CDN purge toàn site; ngay sau đó origin CPU, SQL và CMS content-load latency tăng mạnh. Một số user báo thấy offer của market/tier khác trong vài phút.

## Code cần review

```csharp
public sealed class LandingPageService
{
    private readonly IDatabase _redis;
    private readonly IContentLoader _contentLoader;

    public LandingPageService(
        IDatabase redis,
        IContentLoader contentLoader)
    {
        _redis = redis;
        _contentLoader = contentLoader;
    }

    public async Task<string> RenderAsync(
        ContentReference pageRef,
        string url,
        string market,
        string membershipTier)
    {
        var key = $"page:{url}";

        var cached = await _redis.StringGetAsync(key);
        if (cached.HasValue)
            return cached!;

        var page = _contentLoader.Get<LandingPage>(pageRef);

        var html = RenderTemplate(
            page,
            market,
            membershipTier);

        await _redis.StringSetAsync(
            key,
            html,
            TimeSpan.FromMinutes(10));

        return html;
    }

    public async Task OnContentPublishedAsync()
    {
        await _redis.ExecuteAsync("FLUSHDB");
        await PurgeCdnAsync("/*");
    }
}
```

Controller sau đó trả response với:

```http
Cache-Control: public, max-age=600
```

## Nhiệm vụ review

1. Xác định correctness, privacy, cache-invalidation và availability risks.
2. Giải thích vì sao cache key hiện tại không đúng boundary của rendered response.
3. Phân tích chuỗi Redis flush + full CDN purge có thể tạo cache stampede/thundering herd thế nào.
4. Đề xuất architecture cache/invalidation tốt hơn cho public content và personalized content.
5. Nêu evidence, test và telemetry cần có trước/sau rollout.

## Gợi ý

### Gợi ý 1

Cache key phải đại diện cho mọi dimension làm thay đổi output, hoặc output cần được tách thành các phần có cache policy khác nhau.

### Gợi ý 2

`public` cacheability có ý nghĩa ở shared caches; hãy hỏi liệu response có chứa user/segment-specific data không.

### Gợi ý 3

Invalidation toàn bộ có correctness đơn giản nhưng operational blast radius rất lớn.

## Các vấn đề cần tìm

### Bắt buộc

- Redis key chỉ dùng URL trong khi HTML thay đổi theo `market` và `membershipTier`; user có thể nhận variant của request trước.
- `Cache-Control: public` cho response chứa personalized/segment-specific offer có thể làm shared CDN cache sai variant nếu cache key/policy không phản ánh segmentation.
- `FLUSHDB` xóa toàn bộ database, có blast radius lớn và có thể ảnh hưởng dữ liệu/cache khác dùng chung Redis logical database.
- Full Redis flush cộng full CDN purge làm mọi request trở thành miss gần đồng thời, gây thundering herd vào App Service/CMS/SQL.
- Mọi content publish đều invalidate toàn site dù chỉ một content item thay đổi.
- Không có protection/coalescing khi nhiều requests cùng rebuild một hot key.
- Redis outage/error behavior chưa được xử lý; cache failure không nên mặc định làm website mất availability nếu origin còn phục vụ được.
- URL raw có thể tạo key fragmentation nếu query/canonicalization không được định nghĩa.

### Điểm cộng

- Tách public/cacheable shell hoặc shared content khỏi personalized offer khi architecture cho phép.
- Nếu cache variant, key phải gồm stable dimensions cần thiết và cardinality phải được kiểm soát.
- Dùng dependency/tag/version-based invalidation hoặc targeted purge dựa trên content relationships thay vì global flush.
- Có TTL jitter/stale-while-revalidate/request coalescing tùy layer để giảm synchronized expiry.
- CDN cache key, `Vary` và origin cache semantics phải được thiết kế nhất quán; không thêm `Vary` máy móc nếu CDN không được cấu hình hiểu dimension đó.
- Publish event cần resilient propagation; invalidation failure phải observable và có recovery path.

## Hướng giải quyết tham khảo

Trước tiên phân loại output. Nếu phần lớn landing page là public nhưng offer phụ thuộc membership, một design thường sạch hơn là cache public content/shell ở CDN và lấy/render personalized fragment qua boundary riêng với cache policy phù hợp. Nếu business bắt buộc render toàn trang theo variant, cache key ở mọi shared layer phải phản ánh đúng dimensions và không được public-cache dữ liệu user-specific ngoài security/privacy policy.

Invalidation nên theo dependency. Khi một block/page publish, xác định các cache entries bị ảnh hưởng qua content dependency/version/tag và chỉ invalidate/purge chúng. Một versioned-key strategy có thể tránh scan/delete hàng loạt: publish tăng content version và requests mới dùng namespace/version mới; entries cũ hết hạn tự nhiên. Cách cụ thể phụ thuộc topology và Optimizely integration hiện tại.

Để chống stampede, có thể dùng request coalescing/single-flight cho hot keys, staggered TTL/jitter, stale-while-revalidate hoặc controlled warming cho critical pages. Distributed lock chỉ là một lựa chọn coordination và không thay thế failure handling; nếu lock holder chết, design vẫn phải phục hồi.

Redis nên là optimization layer nếu business cho phép. Khi Redis timeout, application cần bounded timeout/circuit behavior và fallback tới origin thay vì treo request lâu. Nhưng fallback cũng phải có load protection để Redis outage không biến thành origin outage.

## Evidence cần thu

- Cache hit/miss ratio theo CDN, Redis và origin.
- Top hot URLs/variants và request cardinality theo market/tier.
- Origin p50/p95/p99, CPU, SQL/CMS dependency duration sau publish.
- Timeline publish → invalidation → CDN purge → traffic spike.
- Redis command latency/error rate và keyspace ownership.
- Akamai cache-key configuration và actual response cache headers.
- Content dependency graph: block nào xuất hiện trên những pages nào.

## Test nên có

- Test cùng URL với hai markets/tiers không trả nhầm variant.
- E2E test publish một block và xác nhận đúng pages đổi, pages không liên quan vẫn cache được.
- Load test cold-cache event để đo origin amplification.
- Failure test Redis unavailable/slow.
- Concurrency test hàng trăm requests vào cùng hot key sau expiry/purge.
- Test CDN behavior với representative cache headers/key configuration.
- Test canonical URL/query handling để tránh cache fragmentation hoặc collision.

## Production observability

Dashboard nên có CDN hit ratio, Redis hit ratio, origin request rate, render latency, CMS/SQL dependencies, Redis latency/errors, purge count/scope và publish-to-visible latency. Alert không chỉ trên CPU mà cả sudden cache-hit collapse và origin amplification. Correlation ID/event ID cho publish giúp nối content change với performance incident.

## Trade-offs

- Fine-grained invalidation giảm blast radius nhưng tăng dependency metadata/complexity.
- Variant caching giảm render cost nhưng tăng key cardinality và invalidation surface.
- Personalized fragment tách riêng giúp public CDN caching hiệu quả hơn nhưng tăng frontend/composition complexity.
- Stale-while-revalidate tăng availability/performance nhưng business phải chấp nhận bounded staleness.
- Warming cache giúp campaign traffic nhưng cần tránh biến deploy/publish thành một load spike khác.

## Câu hỏi đào sâu

1. Nếu một content block được reuse trên 5.000 pages, targeted invalidation còn tối ưu hơn versioning/stale strategy không? Bạn cần dữ liệu gì để quyết định?
2. Nếu Redis down 10 phút trong peak traffic, fallback nào giữ website sống mà không làm SQL/CMS collapse?
3. Nếu offer chỉ phụ thuộc `market` nhưng membership price đến từ API theo từng user, bạn sẽ chia cache boundaries giữa CDN, origin và browser thế nào?

## Thang điểm 0–10

- **0–2:** Chỉ thêm `market` vào Redis key hoặc tăng TTL.
- **3–4:** Nhận ra variant leak và global purge risk nhưng chưa thiết kế multi-layer cache.
- **5–6:** Tách cache boundary, targeted invalidation và Redis fallback hợp lý.
- **7–8:** Kết nối CDN/Redis/origin, stampede protection, publish dependency và load testing.
- **9–10:** Có data-driven cache architecture, privacy/correctness reasoning, failure-mode design, observability và trade-off vận hành rõ ràng.
