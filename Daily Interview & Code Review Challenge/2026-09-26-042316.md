# Câu 1 — API export làm memory tăng vọt dù “đã dùng async”

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#/.NET runtime, async/await, allocation, GC, LOH, ASP.NET Core, streaming, observability

## Bối cảnh

Một ASP.NET Core .NET 8 API có endpoint export báo cáo CSV. Mỗi request đọc dữ liệu từ SQL Server, dựng CSV rồi trả file cho browser. Khi chỉ vài người export, endpoint hoàn thành trong 4–8 giây. Khi 30–50 người export gần đồng thời, memory của process tăng từ khoảng 1.2 GB lên hơn 5 GB, GC pause tăng, p99 của các API không liên quan cũng xấu đi và một instance đôi lúc bị restart.

Code hiện tại đại ý:

```csharp
public async Task<FileContentResult> Export(CancellationToken ct)
{
    var rows = await _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= _from)
        .ToListAsync(ct);

    var sb = new StringBuilder();

    foreach (var row in rows)
    {
        sb.Append(row.Id).Append(',');
        sb.Append(row.CustomerName).Append(',');
        sb.Append(row.Total).AppendLine();
    }

    var bytes = Encoding.UTF8.GetBytes(sb.ToString());

    return File(bytes, "text/csv", "orders.csv");
}
```

Một developer nói rằng method đã dùng `async/await` nên không thể gây memory pressure. Developer khác đề xuất gọi `GC.Collect()` sau mỗi export. Team chưa có allocation profile, GC counters hay số liệu về kích thước export theo request.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra trong managed memory từ lúc query materialize dữ liệu đến lúc response được gửi, vì sao `async/await` không giải quyết allocation/memory pressure, các assumption nào đang sai, và bạn sẽ xác minh rồi redesign endpoint như thế nào để giảm peak memory mà vẫn giữ correctness và cancellation?

## Câu hỏi làm rõ nên cân nhắc

1. Một export điển hình và worst-case có bao nhiêu rows, kích thước CSV cuối cùng bao nhiêu?
2. Endpoint có bắt buộc tạo toàn bộ file trước khi response bắt đầu hay có thể stream dần?
3. Query hiện projection toàn entity hay chỉ các cột cần cho CSV?
4. Có reverse proxy/CDN nào buffer response, và timeout/cancellation behavior hiện tại ra sao?
5. Instance có memory limit nào và concurrent export có bị giới hạn hay backpressure không?

## Gợi ý tư duy

### Gợi ý 1

Hãy đếm các representation của cùng dữ liệu đang cùng tồn tại: EF materialized objects, `StringBuilder`, `string`, `byte[]`.

### Gợi ý 2

`async` chủ yếu giúp thread không bị block trong lúc chờ I/O; nó không biến allocation lớn thành streaming và không làm object biến mất sớm hơn một cách kỳ diệu.

### Gợi ý 3

Tách bài toán thành query shape, allocation pattern, response buffering, concurrency và evidence từ GC/allocation telemetry.

## Cấu trúc trả lời đề xuất

1. Làm rõ export size và concurrency.
2. Vẽ lifetime của các object lớn.
3. Giải thích async/I/O khác với memory allocation.
4. Xác minh bằng counters, trace và allocation profile.
5. Giảm materialization/projection.
6. Thiết kế streaming hoặc bounded batching.
7. Xử lý cancellation, disconnect và backpressure.
8. Kiểm thử load/memory.
9. Theo dõi sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `ToListAsync` vẫn materialize toàn bộ result set.
- `StringBuilder` giữ buffer; `ToString()` tạo `string`; `GetBytes` tạo thêm `byte[]`.
- `async/await` không đồng nghĩa ít allocation hay ít memory.
- Object/array lớn có thể tạo áp lực lên GC/LOH; không nên kết luận chi tiết GC cụ thể nếu chưa profile.
- `GC.Collect()` per request không phải remediation mặc định và có thể làm pause/throughput tệ hơn.
- Cần ưu tiên projection + streaming/batching nếu requirement cho phép.

### Điểm cộng

- Dùng `AsAsyncEnumerable()` hoặc reader/batched query hợp lý thay vì materialize tất cả.
- Chỉ select các cột cần thiết.
- Dùng `Response.BodyWriter`/streaming response hoặc `FileStreamResult` tùy thiết kế.
- Nhận ra proxy buffering có thể làm application streaming nhưng end-to-end vẫn không đạt mục tiêu mong muốn.
- Giới hạn concurrent heavy exports hoặc chuyển export rất lớn sang background workflow có durable storage.

### Senior+

- Phân biệt “giảm retained peak memory” với “giảm tổng allocations”.
- Xem export lớn như workload cần admission control/backpressure thay vì để mọi request cạnh tranh tài nguyên với latency-sensitive APIs.
- Nếu export mất hàng phút hoặc cần retry/download lại, cân nhắc background job tạo Blob rồi cấp quyền download thay vì giữ HTTP request sống lâu.
- Đo `gc-heap-size`, allocation rate, GC collections/pause, process working set, request concurrency và export size cùng nhau.

## Hướng giải quyết tham khảo

Tôi không bắt đầu bằng `GC.Collect()`. Code hiện tạo nhiều representation lớn cùng lúc. `ToListAsync` chỉ làm database I/O bất đồng bộ; sau khi hoàn thành, toàn bộ rows vẫn được giữ trong list. `StringBuilder` tiếp tục tích lũy CSV. `sb.ToString()` tạo một `string` hoàn chỉnh, sau đó `Encoding.UTF8.GetBytes` lại tạo `byte[]` hoàn chỉnh. Trong một khoảng thời gian, nhiều graph lớn có thể cùng reachable. Nhân với hàng chục exports đồng thời, peak memory có thể tăng mạnh.

Tôi sẽ xác minh thay vì suy đoán: log export row count và output size; dùng .NET runtime counters/traces để quan sát allocation rate, GC heap size, collection/pause và process memory; allocation profile để biết type nào chiếm phần lớn; correlate với concurrent exports và p99. Nếu memory limit/restart đến từ container/App Service, tôi cũng lấy platform evidence.

Nếu business cho phép stream, query chỉ projection các cột cần thiết và enumerate dần. Tôi ghi CSV theo từng row hoặc bounded batch trực tiếp vào response stream/BodyWriter, flush hợp lý chứ không flush mỗi row. Điều này tránh `List<T>`, full `StringBuilder`, full `string` và full `byte[]` cùng tồn tại. Tôi propagate `CancellationToken` xuống database và write path để browser disconnect có thể dừng work.

Streaming không tự động giải quyết mọi thứ. Tôi cần kiểm tra reverse proxy có buffer không, database query có giữ connection quá lâu không, và một export quá lớn có ảnh hưởng workload khác không. Có thể cần semaphore/admission limit cho export để bảo vệ instance, nhưng limit phải dựa trên load test và capacity, không phải số ngẫu nhiên.

Nếu requirement là export hàng trăm MB, cần retry, audit hoặc download lại, tôi nghiêng về asynchronous export: API tạo job, worker đọc dữ liệu theo batch, ghi trực tiếp vào Azure Blob Storage, sau đó client lấy trạng thái và download. Thiết kế này thêm complexity, storage lifecycle và eventual completion nhưng tách heavy workload khỏi request path.

Tôi test correctness của CSV, cancellation, client disconnect, export lớn, nhiều concurrent exports và dependency slowdown. Sau rollout theo dõi peak memory, allocation rate, GC pause, p95/p99 của cả export lẫn API khác, DB connection usage và restart count.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi `async` là memory optimization. `ToListAsync` vẫn materialize toàn bộ rows; sau đó code còn giữ `StringBuilder`, tạo full `string`, rồi tạo full `byte[]`. Với 30–50 requests đồng thời, peak retained memory có thể nhân lên rất nhanh và gây GC pressure cho cả process.

Em sẽ đo export size, allocation rate, GC heap/pause và profile allocations trước. Nếu requirement cho phép, em projection đúng cột và stream CSV dần từ query sang response, propagate cancellation và kiểm tra proxy có buffer không. Em cũng cân nhắc giới hạn concurrent exports để bảo vệ latency-sensitive endpoints.

Nếu file rất lớn hoặc cần retry/download lại, em chuyển sang background export ghi Blob rồi trả trạng thái/download link. Em không gọi `GC.Collect()` mỗi request vì đó chỉ ép collection và có thể làm pause/throughput tệ hơn. Sau fix em load-test và theo dõi memory, GC, DB connections và p99.”

## Câu hỏi đào sâu

1. Nếu streaming giữ một SQL connection mở 90 giây, bạn đánh đổi memory với connection-pool pressure như thế nào?
2. Nếu reverse proxy buffer toàn response trước khi gửi client, recommendation của bạn thay đổi ra sao?
3. Một teammate muốn dùng `ArrayPool<byte>` ngay lập tức. Khi nào pooling có ích, và vì sao nó không thay thế việc sửa full materialization?

## Lỗi trả lời thường gặp

- Cho rằng `async` đồng nghĩa memory thấp.
- Gọi `GC.Collect()` như fix chính.
- Chỉ tối ưu `StringBuilder` nhưng vẫn `ToListAsync` toàn bộ.
- Streaming mà bỏ qua cancellation, DB connection lifetime hoặc proxy buffering.
- Đề xuất background job cho mọi file nhỏ mà không cân nhắc complexity.

## Thang điểm 0–10

- **0–2:** Chỉ nói tăng RAM hoặc gọi GC.
- **3–4:** Nhận ra allocation lớn nhưng chưa giải thích object lifetime.
- **5–6:** Hiểu materialization, multiple buffers và có streaming/projection.
- **7–8:** Có measurement, cancellation, concurrency control và failure reasoning.
- **9–10:** Kết nối runtime memory với workload isolation, DB/proxy behavior và conditional architecture decision.

# Câu 2 — Search API trả dữ liệu cũ sau deploy và backlog indexing tăng dần

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, eventual consistency, background processing, deployment, production troubleshooting, observability

## Bối cảnh

Một marketplace dùng SQL Server làm source of truth cho product data và Elasticsearch phục vụ search. Khi product thay đổi, application ghi SQL rồi tạo work item để index document sang Elasticsearch. Search không yêu cầu strong consistency tức thời; Product chấp nhận độ trễ khoảng vài chục giây.

Sau một deployment, support báo một số sản phẩm đã đổi giá trong admin nhưng search vẫn hiển thị giá cũ sau hơn 20 phút. Search API vẫn nhanh và cluster Elasticsearch không báo đỏ. Dashboard cho thấy indexing backlog tăng đều; CPU application không cao; SQL vẫn healthy. Rollback application version làm tốc độ tăng backlog chậm lại nhưng backlog cũ không tự biến mất.

Team biết release có thay đổi mapping/index alias và nâng logic transform product document. Worker chạy nhiều instances. Một số log có `mapper_parsing_exception`, một số item retry nhiều lần, nhưng log không có stable product/event ID ở mọi bước. Một developer muốn tăng số worker; người khác muốn xóa index và reindex toàn bộ ngay.

## Câu hỏi chính

Bạn đang xử lý incident. Hãy đi theo **impact → stabilize → collect evidence → hypotheses → verification → remediation → prevention** để xác định vì sao backlog tăng và search stale. Bạn sẽ phân biệt throughput shortage, poison work, mapping incompatibility, retry loop và deployment-order problem như thế nào, và phục hồi dữ liệu ra sao mà không làm source of truth hoặc search index tệ hơn?

## Câu hỏi làm rõ nên cân nhắc

1. Work item được lưu ở durable queue/table hay chỉ trong memory, và retry/DLQ semantics hiện tại thế nào?
2. Mapping mới được tạo trước hay sau khi application version mới bắt đầu publish documents?
3. Alias hiện trỏ tới index nào, và read/write alias có cùng target không?
4. Backlog age, retry count và failure rate phân bố thế nào; có một nhóm product shape lặp lại lỗi không?
5. Có sequence/version nào để ngăn event cũ ghi đè document mới hơn khi nhiều workers xử lý out-of-order không?

## Gợi ý tư duy

### Gợi ý 1

Queue depth chỉ cho biết work tích tụ; hãy nhìn **age + processing rate + failure classification + retry distribution**.

### Gợi ý 2

Một poison item được retry không giới hạn có thể tiêu capacity mà thêm worker chỉ khuếch đại lỗi.

### Gợi ý 3

Mapping, transform code, index creation và alias cutover là một deployment protocol, không phải bốn thay đổi độc lập.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và freshness SLO.
2. Stabilize release/indexing path.
3. Dựng timeline deployment và alias/mapping changes.
4. Phân loại success/retry/permanent failure.
5. Đo backlog age/throughput/failure.
6. Verify competing hypotheses bằng sample IDs.
7. Fix compatibility/retry policy.
8. Drain/replay/reindex có kiểm soát.
9. Reconcile SQL với search.
10. Bổ sung deployment guardrails và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- SQL là source of truth; search index là derived representation.
- Search nhanh không chứng minh index fresh.
- Phải phân biệt transient failure với permanent mapping/data error.
- Retry vô hạn cho permanent error có thể tạo retry storm/poison backlog.
- Tăng worker trước khi biết bottleneck có thể làm Elasticsearch/dependency pressure tệ hơn.
- Reindex cần kế hoạch index mới + validation + alias cutover/rollback thay vì xóa index đang phục vụ production một cách mù quáng.

### Điểm cộng

- Theo dõi oldest-message age bên cạnh queue depth.
- Có DLQ/quarantine cho permanent failures và replay sau fix.
- Stable correlation/product/event ID xuyên SQL change → queue → worker → Elasticsearch.
- Dùng version/sequence strategy để tránh stale event ghi đè state mới nếu pipeline có out-of-order delivery.
- Canary transform/mapping compatibility trước rollout.

### Senior+

- Tách “catch up incremental backlog” khỏi “full reconciliation/reindex”.
- Dùng blue/green index migration: tạo index version mới, apply mapping, backfill, verify counts/sample/business invariants, catch up delta rồi atomic alias switch nếu architecture hỗ trợ.
- Định nghĩa freshness SLO và alert trên indexing lag/oldest age thay vì chỉ cluster health.
- Deployment ordering phải backward/forward compatible nếu old/new worker cùng tồn tại trong rolling deployment.

## Hướng giải quyết tham khảo

Tôi coi SQL là source of truth và Elasticsearch là read model. Việc search API latency tốt chỉ nói read path khỏe; stale data cộng với backlog tăng cho thấy write/indexing path đang không theo kịp hoặc đang thất bại.

Đầu tiên tôi xác định phạm vi: bao nhiêu products stale, oldest backlog age, business fields nào bị ảnh hưởng. Nếu release mới rõ ràng tạo permanent failures, tôi có thể tạm dừng rollout hoặc rollback worker để ngăn tạo thêm lỗi, nhưng không xóa backlog. Tôi capture evidence trước khi thay đổi lớn: deployment timeline, mapping/index versions, alias targets, success rate, retry count, exception classification và sample product IDs.

Các hypotheses gồm: capacity không đủ; transform mới tạo document không phù hợp mapping; mapping được deploy sai thứ tự; alias write/read lệch; một nhóm poison messages retry liên tục; dependency throttling; hoặc out-of-order events làm state cũ ghi đè. Tôi chọn sample từ success, first-failure và high-retry cohorts rồi trace end-to-end.

Nếu `mapper_parsing_exception` là permanent với một product shape, retry exponential mãi không giúp. Tôi quarantine/DLQ item với đủ context, sửa mapping hoặc transform dựa trên intended schema, rồi replay có kiểm soát. Nếu mapping migration không tương thích với rolling deployment, tôi sửa deployment protocol: schema/index version mới phải chấp nhận document từ versions đang chạy hoặc rollout phải có phase rõ ràng.

Tôi không xóa index production. Nếu cần rebuild, tôi tạo index version mới, apply mapping/settings, backfill từ SQL, kiểm tra document counts và business samples, sau đó catch up changes phát sinh trong quá trình backfill. Khi validated, switch alias và giữ index cũ đủ lâu cho rollback theo policy. Nếu chỉ backlog incremental và schema hiện đã đúng, drain backlog với concurrency được đo theo bulk indexing throughput/error/throttling thay vì tăng worker vô hạn.

Nếu events có thể out-of-order, document update cần versioning/sequence semantics phù hợp để event cũ không ghi đè state mới. Chi tiết implementation phụ thuộc pipeline hiện tại; tôi cần xác minh contract trước.

Prevention: structured logs có product/event/correlation ID, metrics về enqueue rate, processing rate, failure category, retry count, oldest age, DLQ size và indexing latency; alert theo freshness SLO. Release test phải chạy representative documents qua transform + mapping trước production, và migration/alias switch cần rollback path.

## Mẫu trả lời trong phỏng vấn

“Em coi SQL là source of truth và Elasticsearch là derived search model. Search latency vẫn tốt không có nghĩa index fresh. Em sẽ stabilize release, lấy timeline mapping/index/alias và phân loại backlog theo success, transient retry và permanent failure. Em đặc biệt trace các `mapper_parsing_exception` bằng stable product/event ID.

Nếu permanent mapping error đang retry vô hạn, tăng worker chỉ tạo retry storm. Em sẽ quarantine/DLQ, sửa schema/transform rồi replay. Nếu cần rebuild, em không xóa index đang live; em tạo versioned index mới, backfill từ SQL, verify, catch up delta rồi switch alias với rollback path.

Em cũng kiểm tra out-of-order processing và version semantics để event cũ không ghi đè state mới. Sau incident em alert trên oldest backlog age/freshness lag, không chỉ queue depth hay cluster health, và đưa mapping compatibility vào deployment validation.”

## Câu hỏi đào sâu

1. Nếu mapping fix làm worker xử lý lại được nhưng backlog cần 6 giờ để drain, bạn quyết định tăng concurrency dựa trên evidence nào?
2. Nếu Product yêu cầu giá trong search không bao giờ được cũ quá 5 giây, kiến trúc hiện tại cần thay đổi contract hoặc read path thế nào?
3. Một teammate muốn dùng Elasticsearch làm source of truth để loại bỏ sync problem. Bạn phản biện hoặc chấp nhận trong điều kiện nào?

## Lỗi trả lời thường gặp

- Chỉ nhìn Elasticsearch cluster health.
- Tăng worker mà không phân loại failure.
- Retry permanent mapping error vô hạn.
- Xóa live index rồi reindex trực tiếp.
- Không có reconciliation/version strategy cho derived data.

## Thang điểm 0–10

- **0–2:** Chỉ scale worker hoặc xóa index.
- **3–4:** Nhận ra mapping/retry nhưng thiếu incident method.
- **5–6:** Có evidence, failure classification, DLQ và safe recovery.
- **7–8:** Có versioned reindex, alias rollback, ordering và freshness telemetry.
- **9–10:** Reason đầy đủ về deployment compatibility, derived-state recovery, SLO và operational trade-offs.

# Câu 3 — Modernize ứng dụng .NET Framework mà không biến migration thành rewrite nhiều năm

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework 4.5, IIS, Windows Server, ASP.NET Core/.NET 8, Azure App Service, CI/CD, migration strategy, architecture trade-offs

## Bối cảnh

Một enterprise management portal đã chạy nhiều năm trên .NET Framework 4.5, ASP.NET MVC và IIS/Windows Server. Ứng dụng là một monolith khoảng vài trăm nghìn dòng code, dùng SQL Server, Windows Authentication cho một số internal flows, file share nội bộ, scheduled jobs chạy trong web process và một số third-party libraries cũ.

Business muốn trong 12–18 tháng giảm rủi ro vận hành, đưa phần lớn workload lên modern .NET và cloud hosting, nhưng không chấp nhận freeze feature development trong một năm. Team có kinh nghiệm ASP.NET Core, .NET 8, Azure App Service, SQL Server, CI/CD và container concepts. Kubernetes được nhắc tới như một lựa chọn nhưng chưa có requirement bắt buộc.

Hiện release qua pipeline cũ rồi deploy lên IIS. Automated integration/E2E coverage còn mỏng. Database được nhiều module dùng chung. Một architect đề xuất rewrite toàn bộ thành microservices trên Kubernetes. Một developer khác muốn chỉ nâng target framework “một lần” rồi deploy ngay.

## Câu hỏi chính

Bạn sẽ thiết kế **migration strategy và target architecture** như thế nào để modernize hệ thống từng bước, vẫn giao feature, có rollback, đo được rủi ro và không mặc định rằng Microservices/Kubernetes/Clean Architecture là đích đến? Hãy nêu cách bạn phân loại dependencies, chọn migration seams, xử lý database/auth/background jobs, CI/CD và quyết định hosting dựa trên evidence.

## Câu hỏi làm rõ nên cân nhắc

1. Những third-party libraries nào chỉ hỗ trợ .NET Framework/Windows và có source/replacement không?
2. Windows Authentication/file share là hard requirement hay có thể chuyển sang Microsoft Entra ID/Blob/Managed Identity theo từng flow?
3. Module nào có boundary rõ, change frequency cao hoặc pain vận hành lớn nhất?
4. Database coupling đến mức nào: shared tables, stored procedures, cross-module transactions?
5. SLO, deployment frequency, rollback requirement và acceptable coexistence period giữa legacy/modern là gì?

## Gợi ý tư duy

### Gợi ý 1

Migration không bắt đầu từ folder structure. Hãy lập dependency/compatibility map và tìm **seams** có thể tách hoặc thay thế với blast radius nhỏ.

### Gợi ý 2

“Modern .NET” và “Microservices/Kubernetes” là các quyết định khác nhau. Hosting/architecture phải phục vụ operational requirement, không phải danh sách công nghệ.

### Gợi ý 3

Coexistence cần contract, routing, data ownership, authentication và observability rõ ràng; rollback phải được thiết kế trước cutover.

## Cấu trúc trả lời đề xuất

1. Làm rõ business goals và non-functional constraints.
2. Inventory dependencies và blockers.
3. Baseline test/telemetry trước migration.
4. Xác định module seams và migration order.
5. Chọn target architecture tối thiểu đủ dùng.
6. Thiết kế legacy/modern coexistence.
7. Xử lý auth, data và background jobs.
8. Thiết kế CI/CD, rollout và rollback.
9. Đo success theo từng increment.
10. Chỉ tăng architecture complexity khi evidence yêu cầu.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite-from-scratch.
- Inventory dependency compatibility trước khi chọn migration path.
- Tách framework modernization khỏi service decomposition/hosting decisions.
- Có characterization/integration tests cho critical flows trước khi thay đổi lớn.
- Có incremental cutover và rollback.
- Scheduled jobs không nên tiếp tục phụ thuộc vào web-process lifetime nếu cần reliability.
- Database coupling và transaction boundaries phải được hiểu trước khi tách service.

### Điểm cộng

- Dùng strangler-style migration/routing khi phù hợp.
- Bắt đầu bằng module có boundary rõ và giá trị/risk ratio tốt, không nhất thiết module dễ nhất.
- Có anti-corruption/adapter boundary cho legacy integration.
- Azure App Service có thể là target đơn giản hơn Kubernetes nếu workload không cần orchestration capabilities.
- Chuyển secrets sang managed configuration/Key Vault và service identity khi phù hợp, nhưng không gắn migration thành “big bang identity rewrite”.

### Senior+

- Có compatibility matrix: runtime, NuGet/third-party, Windows-specific API, auth, filesystem, COM/native dependency, deployment assumptions.
- Dùng branch-by-abstraction hoặc façade để thay implementation dần khi cần coexistence.
- Database extraction theo ownership và transaction requirement; tránh “database per service” trước khi boundary thực sự tồn tại.
- Định nghĩa migration SLO/metrics: defect rate, deployment lead time, rollback success, legacy traffic %, operational incidents.
- Có explicit exit criteria cho mỗi phase và phương án dừng migration nếu economics thay đổi.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng mục tiêu kinh doanh: giảm operational risk, modernize runtime/hosting và vẫn giao feature. Tôi không gộp mục tiêu đó với “phải có microservices” hay “phải chạy Kubernetes”.

Phase đầu là discovery có đầu ra cụ thể: dependency map cho third-party libraries/NuGet, Windows-only APIs, Windows Authentication, filesystem/file share, scheduled jobs, IIS assumptions, SQL coupling và external integrations. Tôi baseline production telemetry và thêm characterization/integration tests cho critical business flows để biết migration có phá behavior không.

Sau đó tôi tìm seams. Ví dụ một module read-heavy có API boundary rõ và ít cross-table transaction có thể được chuyển sang ASP.NET Core/.NET 8 trước. Routing/proxy có thể đưa một subset endpoints sang modern app trong khi phần còn lại vẫn legacy. Nếu code quá coupled, branch-by-abstraction/façade có thể tạo seam trước khi chuyển runtime. Tôi không tách thành service chỉ để đổi framework.

Target architecture ban đầu có thể là một modern modular monolith hoặc vài independently deployable components nếu boundaries đã rõ. Azure App Service có thể đủ nếu team cần managed hosting, autoscale và deployment slots mà không có requirement orchestration phức tạp. Kubernetes chỉ hợp lý nếu workload/organization cần capabilities và chấp nhận operational cost của nó.

Data là phần khó. Tôi map table ownership, stored procedures và transaction boundaries. Trong giai đoạn coexistence, tôi tránh tạo dual-write không kiểm soát. Với module chưa thể sở hữu data độc lập, modern component có thể vẫn truy cập shared SQL qua boundary rõ trong thời gian chuyển tiếp; sau đó mới tách schema/data ownership khi business transaction cho phép. Nếu phải sync data, cần idempotency/reconciliation và failure semantics rõ.

Auth cũng migration theo contract. Tôi xác minh flows nào thật sự phụ thuộc Windows Authentication. Public/cloud-facing flows có thể chuyển dần sang Entra-based identity, còn Windows-only dependency có thể giữ ở legacy boundary tạm thời. Không ép mọi flow đổi identity cùng một release.

Scheduled jobs quan trọng nên rời web process sang Worker Service, Azure Functions hoặc scheduler phù hợp dựa trên duration/retry/idempotency; lựa chọn dựa trên workload chứ không theo trend. File share dependency được phân loại: nếu cần SMB/Windows semantics thì chưa chắc Blob là drop-in replacement; nếu chỉ object storage, Blob + Managed Identity có thể phù hợp.

CI/CD cần build/test legacy và modern artifacts độc lập, integration contract tests giữa hai phía, database migration strategy tương thích backward/forward trong rollout, deployment slot/canary nếu phù hợp và rollback đã rehearsal. Schema changes nên theo expand/contract khi old/new versions cùng chạy.

Tôi đo migration bằng tỷ lệ traffic/code path đã chuyển, production defects, deployment frequency/lead time, p95/p99, incident rate và rollback success—not bằng số microservices tạo ra. Mỗi phase có exit criteria. Nếu một module không đem lại đủ value để tách, giữ nó trong modular monolith là quyết định hợp lệ.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách ba quyết định: nâng runtime, tách architecture boundary và chọn hosting. Chúng không bắt buộc xảy ra cùng lúc. Đầu tiên em inventory third-party/Windows-only dependencies, auth, file share, jobs và SQL coupling; đồng thời thêm characterization/integration tests cho critical flows và baseline telemetry.

Sau đó em chọn một seam có boundary rõ để chuyển sang .NET 8, route một phần traffic sang modern app và giữ rollback. Target ban đầu có thể là modular monolith trên App Service; em chỉ chọn microservices/Kubernetes nếu scaling, deployment independence hoặc operational requirements thực sự justify complexity.

Database migration phải theo ownership/transaction boundary; em tránh dual-write tùy tiện và dùng expand/contract khi old/new versions coexist. Jobs quan trọng sẽ rời web-process lifetime sang worker/scheduler phù hợp. CI/CD build/test/deploy hai thế hệ độc lập với contract tests, canary/slot và rollback rehearsal.

Em đo thành công bằng defect/incident rate, deployment lead time, legacy traffic còn lại và SLO chứ không bằng số service. Nếu economics không justify tách thêm, giữ phần còn lại trong modular monolith vẫn là kết quả tốt.”

## Câu hỏi đào sâu

1. Nếu 60% business logic nằm trong stored procedures dùng chung bởi nhiều module, migration order và service boundaries của bạn thay đổi thế nào?
2. Architect yêu cầu Kubernetes “để future-proof”. Bạn cần những evidence hoặc requirements nào trước khi chấp nhận chi phí đó?
3. Nếu old và new application phải cùng chạy 9 tháng nhưng database schema liên tục thay đổi, bạn thiết kế compatibility và rollout thế nào?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ rồi mới cutover.
- Đồng nhất modernization với microservices/Kubernetes.
- Bỏ qua Windows-specific dependencies và third-party compatibility.
- Tách database trước khi hiểu transaction/data ownership.
- Không có test baseline, observability hoặc rollback.
- Chỉ nâng framework mà không xử lý operational assumptions của IIS/web-process jobs.

## Thang điểm 0–10

- **0–2:** Big-bang rewrite hoặc “upgrade target framework là xong”.
- **3–4:** Có incremental migration nhưng thiếu dependency/data/rollback reasoning.
- **5–6:** Có inventory, seams, tests, coexistence và hosting trade-off.
- **7–8:** Có data/auth/job/CI-CD strategy và measurable rollout.
- **9–10:** Tách rõ modernization khỏi architecture fashion, quản trị compatibility dài hạn và đưa conditional decisions theo risk/economics.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `async/await` giải quyết cách chờ asynchronous work, không tự động giảm allocation; memory pressure phải được reason từ object lifetime, buffering và concurrency.
- Elasticsearch/search index là derived state: cần đo freshness của indexing path, phân loại transient/permanent failure và có reconciliation/rebuild strategy an toàn.
- Modernization cần tách runtime upgrade, architecture decomposition và hosting thành các quyết định riêng; migration tốt ưu tiên compatibility, seams, incremental rollout và rollback hơn rewrite theo trend.
- Observability phải chứng minh hypothesis: GC/allocation evidence cho memory, backlog age/failure category cho indexing, và migration/production metrics cho modernization.

## Mẫu tư duy cần nhớ

- Measure before optimizing.
- Derived data cần reconciliation và safe rebuild path.
- Retry phải đi cùng failure classification; permanent error không nên retry vô hạn.
- Tách technology upgrade khỏi architecture decision.
- Thiết kế rollback trước cutover.
