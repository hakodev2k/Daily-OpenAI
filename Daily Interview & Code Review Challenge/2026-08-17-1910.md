# Code Review Challenge 1 — Webhook tester biến thành SSRF proxy vào mạng nội bộ

**Chủ đề:** Input validation, authentication & authorization, HTTP client usage, sensitive-data exposure, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một hệ thống multi-tenant cho phép admin cấu hình webhook URL để nhận sự kiện khi nhân viên được tạo mới, cập nhật hoặc offboard. Để tiện kiểm tra cấu hình, team thêm endpoint `POST /api/webhooks/test` cho phép admin nhập một URL bất kỳ và payload mẫu, sau đó backend gọi URL đó rồi trả status/body về giao diện.

API chạy trong Azure, có quyền truy cập nhiều service nội bộ và một số endpoint metadata/management chỉ có thể gọi từ mạng backend. Production gần đây ghi nhận:

- một tenant gửi webhook tới hostname nội bộ thay vì domain public,
- một số request test webhook mất rất lâu vì endpoint đích không phản hồi,
- response body vài chục MB làm memory tăng,
- log chứa đầy đủ URL có query string và đôi khi chứa token bí mật,
- security review cảnh báo endpoint có thể bị lợi dụng để dò port hoặc đọc tài nguyên mà browser người dùng không truy cập trực tiếp được.

Business vẫn cần chức năng test webhook, nhưng chỉ được phép gọi các destination hợp lệ theo policy. Hệ thống phải giới hạn thời gian, response size, redirect behavior và không được biến thành proxy tùy ý.

[ApiController]
[Route("api/webhooks")]
public sealed class WebhooksController : ControllerBase
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<WebhooksController> _logger;

    public WebhooksController(
        HttpClient httpClient,
        ILogger<WebhooksController> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    [HttpPost("test")]
    public async Task<IActionResult> Test(
        TestWebhookRequest request,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Testing webhook {Url} with payload {Payload}",
            request.Url,
            request.Payload);

        using var message = new HttpRequestMessage(
            HttpMethod.Post,
            request.Url);

        message.Content = JsonContent.Create(request.Payload);

        var response = await _httpClient.SendAsync(
            message,
            cancellationToken);

        var responseBody = await response.Content
            .ReadAsStringAsync(cancellationToken);

        return Ok(new
        {
            status = (int)response.StatusCode,
            body = responseBody,
            headers = response.Headers.ToDictionary(
                x => x.Key,
                x => string.Join(",", x.Value))
        });
    }
}

## Kết quả code review tham khảo

### 1. Backend gọi URL tùy ý do người dùng cung cấp

**Problem:** `request.Url` được chuyển trực tiếp vào `HttpRequestMessage`.  
**Why it happens:** Code chỉ dựa vào khả năng parse URL của HTTP stack, không có destination policy.  
**Production impact:** Endpoint có thể trở thành SSRF primitive để gọi loopback, private network, metadata service hoặc service nội bộ mà người dùng không truy cập trực tiếp được.  
**Severity:** Critical  
**Recommended fix:** Chỉ cho phép destination theo policy rõ ràng: ưu tiên allowlist domain/host đã đăng ký; nếu business bắt buộc cho URL linh hoạt thì kiểm tra scheme, port, DNS resolution và từ chối loopback/private/link-local/reserved address theo policy hạ tầng.

### 2. Không có resource authorization rõ ràng

**Problem:** Đoạn code không thể hiện rằng caller phải có quyền quản lý webhook của tenant hiện tại.  
**Why it happens:** Endpoint tập trung vào network call và bỏ qua resource-level authorization.  
**Production impact:** User có quyền thấp hơn có thể dùng chức năng test như một network oracle hoặc proxy nếu authorization ở nơi khác bị thiếu/sai.  
**Severity:** Critical  
**Recommended fix:** Enforce authentication và policy-based/resource authorization trước khi cho phép test; tenant boundary phải được xác định từ identity đáng tin thay vì request body.

### 3. Redirect có thể vượt qua validation ban đầu

**Problem:** Nếu handler tự follow redirect, destination cuối có thể khác host đã kiểm tra ban đầu.  
**Why it happens:** Validation thường chỉ áp dụng URL đầu vào, trong khi HTTP redirect tạo request mới tới location khác.  
**Production impact:** Attacker có thể dùng public URL hợp lệ redirect sang private/internal address.  
**Severity:** High  
**Recommended fix:** Với webhook tester nhạy cảm, nên tắt automatic redirect hoặc validate lại từng redirect hop theo cùng destination policy và giới hạn số hop.

### 4. DNS rebinding / thay đổi resolution chưa được xử lý trong threat model

**Problem:** Chỉ validate hostname string không đủ để đảm bảo destination thực sự là public.  
**Why it happens:** Hostname có thể resolve thành nhiều IP hoặc thay đổi theo thời gian.  
**Production impact:** Request có thể đi tới private/reserved IP dù hostname có vẻ hợp lệ.  
**Severity:** High  
**Recommended fix:** Thiết kế outbound networking có lớp egress policy ở hạ tầng và application. Application validate resolved address theo policy; network layer/firewall vẫn phải chặn các destination không được phép. Không nên coi application validation là lớp bảo vệ duy nhất.

### 5. Không có timeout policy riêng cho webhook tester

**Problem:** Code phụ thuộc hoàn toàn vào timeout mặc định/configuration của `HttpClient`.  
**Why it happens:** Endpoint không xác định SLA cho thao tác test.  
**Production impact:** Destination chậm có thể giữ request, connection và tài nguyên server quá lâu; burst nhiều request làm suy giảm throughput.  
**Severity:** High  
**Recommended fix:** Dùng timeout ngắn, có giới hạn hợp lý cho connect/overall operation; kết hợp với request cancellation token.

### 6. Đọc toàn bộ response body vào memory không giới hạn

**Problem:** `ReadAsStringAsync` materialize toàn bộ body thành string.  
**Why it happens:** Endpoint muốn trả body trực tiếp về UI nhưng không có response-size budget.  
**Production impact:** Một destination trả payload rất lớn có thể gây allocation lớn, GC pressure hoặc resource exhaustion khi nhiều request chạy đồng thời.  
**Severity:** High  
**Recommended fix:** Dùng `HttpCompletionOption.ResponseHeadersRead`, stream response và chỉ đọc tối đa N byte theo policy; truncate có đánh dấu rõ ràng.

### 7. Log URL và payload nguyên bản

**Problem:** URL query string và payload được ghi thẳng vào `Information` log.  
**Why it happens:** Diagnostic log không được phân loại dữ liệu nhạy cảm.  
**Production impact:** Secret, token, PII hoặc business data có thể bị lưu lâu trong log/observability backend.  
**Severity:** High  
**Recommended fix:** Log destination host/port đã sanitize, tenant id, operation id, status, duration; không log query secret hoặc payload nguyên bản trừ khi có cơ chế redaction được kiểm soát.

### 8. Trả gần như toàn bộ response headers về client

**Problem:** Code serialize tất cả `response.Headers`.  
**Why it happens:** Tester muốn cung cấp nhiều thông tin debug.  
**Production impact:** Có thể vô tình expose header nhạy cảm từ hệ thống nội bộ nếu SSRF xảy ra hoặc destination trả thông tin không nên hiển thị.  
**Severity:** Medium  
**Recommended fix:** Chỉ trả allowlist headers cần thiết cho troubleshooting; redaction các giá trị nhạy cảm.

### 9. Không giới hạn số request test / backpressure

**Problem:** Endpoint có thể bị gọi nhiều lần song song.  
**Why it happens:** Không thấy quota/rate limit theo tenant/user.  
**Production impact:** Có thể dùng để tạo outbound flood, tăng chi phí hoặc làm cạn connection/resource.  
**Severity:** Medium  
**Recommended fix:** Thêm rate limit/quota cho test operation và concurrency budget theo instance/tenant tùy yêu cầu.

### 10. Không kiểm soát scheme/port theo business policy

**Problem:** Code chấp nhận mọi URI mà handler hỗ trợ.  
**Why it happens:** Không có allowlist `https` và port mong muốn.  
**Production impact:** Tăng bề mặt tấn công và cho phép dò service ở port không mong muốn.  
**Severity:** Medium  
**Recommended fix:** Chỉ cho `https`; giới hạn port theo policy, thường 443 hoặc tập port cụ thể nếu có lý do business.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa application-level guard. Trong production vẫn nên có outbound egress policy ở network layer vì validation ở code không phải lớp bảo vệ duy nhất.

```csharp
public interface IWebhookDestinationPolicy
{
    Task<bool> IsAllowedAsync(
        Uri destination,
        CancellationToken cancellationToken);
}

[ApiController]
[Route("api/webhooks")]
public sealed class WebhooksController : ControllerBase
{
    private const int MaxPreviewBytes = 64 * 1024;

    private readonly HttpClient _httpClient;
    private readonly IWebhookDestinationPolicy _destinationPolicy;
    private readonly IAuthorizationService _authorization;
    private readonly ILogger<WebhooksController> _logger;

    public WebhooksController(
        HttpClient httpClient,
        IWebhookDestinationPolicy destinationPolicy,
        IAuthorizationService authorization,
        ILogger<WebhooksController> logger)
    {
        _httpClient = httpClient;
        _destinationPolicy = destinationPolicy;
        _authorization = authorization;
        _logger = logger;
    }

    [HttpPost("test")]
    public async Task<IActionResult> Test(
        TestWebhookRequest request,
        CancellationToken cancellationToken)
    {
        var authResult = await _authorization.AuthorizeAsync(
            User,
            resource: null,
            policyName: "ManageWebhooks");

        if (!authResult.Succeeded)
            return Forbid();

        if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri) ||
            uri.Scheme != Uri.UriSchemeHttps)
        {
            return BadRequest("Webhook URL is not allowed.");
        }

        if (!await _destinationPolicy.IsAllowedAsync(uri, cancellationToken))
            return BadRequest("Webhook destination is not allowed.");

        using var timeoutCts = CancellationTokenSource
            .CreateLinkedTokenSource(cancellationToken);
        timeoutCts.CancelAfter(TimeSpan.FromSeconds(10));

        using var message = new HttpRequestMessage(HttpMethod.Post, uri)
        {
            Content = JsonContent.Create(request.Payload)
        };

        var started = Stopwatch.GetTimestamp();

        using var response = await _httpClient.SendAsync(
            message,
            HttpCompletionOption.ResponseHeadersRead,
            timeoutCts.Token);

        await using var stream = await response.Content
            .ReadAsStreamAsync(timeoutCts.Token);

        using var buffer = new MemoryStream();
        var chunk = new byte[8192];
        var total = 0;

        while (total < MaxPreviewBytes)
        {
            var count = await stream.ReadAsync(
                chunk.AsMemory(0, Math.Min(chunk.Length, MaxPreviewBytes - total)),
                timeoutCts.Token);

            if (count == 0)
                break;

            await buffer.WriteAsync(
                chunk.AsMemory(0, count),
                timeoutCts.Token);

            total += count;
        }

        var preview = Encoding.UTF8.GetString(buffer.ToArray());
        var durationMs = Stopwatch.GetElapsedTime(started).TotalMilliseconds;

        _logger.LogInformation(
            "Webhook test completed. Host={Host} Port={Port} Status={Status} DurationMs={DurationMs} PreviewBytes={PreviewBytes}",
            uri.Host,
            uri.IsDefaultPort ? 443 : uri.Port,
            (int)response.StatusCode,
            durationMs,
            total);

        return Ok(new
        {
            status = (int)response.StatusCode,
            bodyPreview = preview,
            truncated = total >= MaxPreviewBytes
        });
    }
}
```

`IWebhookDestinationPolicy` nên dùng rule rõ ràng của hệ thống. Nếu domain phải được đăng ký trước, allowlist theo tenant đơn giản và an toàn hơn nhiều so với cho phép arbitrary internet URL. Automatic redirect nên tắt hoặc được kiểm tra từng hop ở handler phù hợp.

## Trade-offs

- **Allowlist domain** an toàn, dễ audit nhưng giảm tính linh hoạt.
- **Arbitrary public URL + IP validation** linh hoạt hơn nhưng complexity tăng mạnh và vẫn cần network egress control.
- **Tắt redirect** an toàn hơn cho tester; nếu cần redirect vì business, phải validate lại từng hop.
- **Response preview giới hạn** giảm khả năng debug full payload nhưng tránh biến tester thành proxy tải dữ liệu lớn.
- Với nhu cầu test chuyên sâu, có thể chạy outbound call trong isolated worker/subnet có quyền mạng tối thiểu thay vì từ application process chính.

## Cách kiểm thử

1. **Security test:** gửi URL tới `localhost`, loopback, private IP, link-local/reserved address và xác nhận bị chặn.
2. **Redirect test:** public endpoint redirect sang private destination; xác nhận request không follow hoặc destination mới bị reject.
3. **Response-size test:** destination trả payload 20 MB; xác nhận service chỉ giữ preview tối đa và memory không tăng theo full body.
4. **Timeout/cancellation test:** destination giữ connection không trả body; xác nhận request dừng theo timeout hoặc client cancellation.
5. **Authorization test:** user khác tenant hoặc role không có `ManageWebhooks` không thể sử dụng tester.

## Quan sát trong production

Nên theo dõi:

- số webhook test theo tenant/user,
- success/failure/timeout rate,
- outbound duration p50/p95/p99,
- số request bị chặn bởi destination policy,
- số redirect bị từ chối,
- response bytes read/truncated count,
- DNS/connect/TLS/HTTP timing trong distributed trace,
- active outbound requests và connection pool pressure,
- alert khi một tenant tạo volume bất thường hoặc tỷ lệ destination bị chặn tăng cao.

Log không nên chứa full URL query, authorization header, payload bí mật hoặc response body nguyên bản.

# Code Review Challenge 2 — Chuyển quota giữa hai phòng ban gây deadlock và retry làm cập nhật lặp

**Chủ đề:** EF Core transaction handling, SQL locks/deadlocks, concurrency, idempotency, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API nội bộ cho phép chuyển số giờ budget từ phòng ban A sang phòng ban B. Mỗi lần chuyển phải đảm bảo:

- quota nguồn không âm,
- tổng quota giữa hai phòng ban không thay đổi,
- cùng một request retry không được trừ/cộng lặp,
- các request song song phải tạo kết quả xác định.

API chạy trên 4 instance. Cuối tháng có nhiều batch điều chỉnh quota, đôi lúc hai request chạy theo hướng ngược nhau: một request chuyển từ `Department 10 -> 20`, request khác gần như đồng thời chuyển từ `20 -> 10`.

Production ghi nhận:

- SQL Server thỉnh thoảng báo deadlock victim,
- client retry sau timeout có lúc làm quota bị chuyển hai lần,
- log chỉ có exception tổng quát nên khó biết transaction nào xung đột,
- một số developer đề xuất “cứ retry toàn method 3 lần” mà chưa bàn về idempotency.

## Đoạn code cần review

```csharp
public sealed class DepartmentQuotaService
{
    private readonly AppDbContext _db;
    private readonly ILogger<DepartmentQuotaService> _logger;

    public DepartmentQuotaService(
        AppDbContext db,
        ILogger<DepartmentQuotaService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task TransferAsync(
        int fromDepartmentId,
        int toDepartmentId,
        decimal hours,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var from = await _db.DepartmentQuotas
            .SingleAsync(
                x => x.DepartmentId == fromDepartmentId,
                cancellationToken);

        var to = await _db.DepartmentQuotas
            .SingleAsync(
                x => x.DepartmentId == toDepartmentId,
                cancellationToken);

        if (from.AvailableHours < hours)
            throw new InvalidOperationException("Insufficient quota");

        from.AvailableHours -= hours;
        to.AvailableHours += hours;

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Transferred {Hours} from department {From} to {To}",
            hours,
            fromDepartmentId,
            toDepartmentId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và concurrency.
2. Phân tích vì sao hai transfer ngược chiều có thể deadlock hoặc mất update tùy isolation/concurrency setup.
3. Giải thích production impact khi transaction bị chọn làm deadlock victim và client retry.
4. Ưu tiên vấn đề cần sửa trước.
5. Đề xuất implementation có lock ordering, database invariant và idempotency rõ ràng.
6. Giải thích cách test deadlock/concurrency/retry.
7. Đề xuất logs, traces và database metrics hữu ích.

## Câu hỏi gợi mở

1. Hai transaction `10 -> 20` và `20 -> 10` đang đọc các row theo cùng thứ tự hay ngược thứ tự?
2. Nếu cả hai request cùng đọc số dư trước khi update, điều gì bảo vệ invariant khỏi lost update?
3. Nếu transaction commit thành công nhưng client không nhận được response rồi retry, chuyện gì xảy ra?
4. “Retry deadlock 3 lần” có an toàn nếu operation không có idempotency key không?
5. Invariant `AvailableHours >= 0` nên chỉ kiểm tra trong application hay cần database guarantee?

## Gợi ý

### Gợi ý 1

Hãy phân tích cả **lock acquisition order** lẫn **retry semantics**; deadlock và duplicate transfer là hai vấn đề khác nhau nhưng có thể tương tác với nhau.

### Gợi ý 2

Một thiết kế tốt thường có **canonical row ordering**, concurrency/invariant được bảo vệ ở database, và một `TransferId`/idempotency key bền vững để retry không tạo thêm side effect.

## Kết quả code review tham khảo

### 1. Operation không có idempotency key

**Problem:** Mỗi lần gọi method đều tạo một transfer mới về mặt business dù payload giống hệt.  
**Why it happens:** Method không nhận `TransferId`/request id và database không lưu processed operation.  
**Production impact:** Nếu commit thành công nhưng response bị mất, client retry sẽ trừ/cộng quota lần nữa.  
**Severity:** Critical  
**Recommended fix:** Yêu cầu caller cung cấp idempotency key ổn định; lưu `DepartmentQuotaTransfer` có unique constraint trên key và trả lại kết quả cũ khi retry.

### 2. Hai transaction có thể acquire row theo thứ tự ngược nhau

**Problem:** Request `10 -> 20` đọc row 10 rồi 20; request `20 -> 10` đọc row 20 rồi 10.  
**Why it happens:** Lock/order phụ thuộc chiều business của request.  
**Production impact:** Khi database cần lock các row để update, hai transaction có thể chờ vòng tròn và một transaction bị chọn làm deadlock victim.  
**Severity:** High  
**Recommended fix:** Xác định canonical ordering, ví dụ luôn xử lý row có `DepartmentId` nhỏ trước rồi row lớn sau, bất kể chiều transfer.

### 3. Check `AvailableHours` ở application chưa đủ để bảo vệ invariant dưới concurrency

**Problem:** Hai transaction có thể cùng đọc số dư đủ trước khi một trong hai commit.  
**Why it happens:** Read-check-write không tự động là atomic business rule.  
**Production impact:** Tùy isolation/concurrency mechanism, có nguy cơ lost update hoặc số dư nguồn bị âm nếu không có constraint/concurrency protection phù hợp.  
**Severity:** High  
**Recommended fix:** Dùng optimistic concurrency token hoặc conditional update/locking strategy phù hợp, đồng thời có database constraint `AvailableHours >= 0` nếu schema/business cho phép.

### 4. Không validate input cơ bản

**Problem:** Method không chặn `hours <= 0` hoặc `fromDepartmentId == toDepartmentId`.  
**Why it happens:** Business validation chưa được explicit.  
**Production impact:** Negative transfer có thể đảo nghĩa debit/credit; self-transfer vô nghĩa nhưng vẫn tạo load/audit noise.  
**Severity:** High  
**Recommended fix:** Validate `hours > 0`, source khác destination, và các giới hạn business khác trước transaction.

### 5. Transaction retry chưa được thiết kế cùng idempotency

**Problem:** Một deadlock exception có thể được retry ở infrastructure/client layer mà operation không có identity bền vững.  
**Why it happens:** Team coi retry là giải pháp độc lập.  
**Production impact:** Sau ambiguous failure, retry có thể tạo duplicate side effect nếu lần trước thực tế đã commit.  
**Severity:** High  
**Recommended fix:** Retry transient/deadlock chỉ khi operation có idempotency semantics rõ ràng; log/trace từng attempt cùng `TransferId`.

### 6. Không có transfer ledger/audit record trong cùng transaction

**Problem:** Chỉ thay đổi balance hiện tại.  
**Why it happens:** Thiết kế persistence chỉ giữ snapshot quota.  
**Production impact:** Khi sai lệch xảy ra khó điều tra ai chuyển, request nào, trước/sau bao nhiêu và retry có lặp không.  
**Severity:** Medium  
**Recommended fix:** Lưu `DepartmentQuotaTransfer` trong cùng transaction với from/to balance, gồm transfer id, source, target, amount, timestamp và actor.

### 7. Không có concurrency conflict handling rõ ràng

**Problem:** Nếu thêm row version/concurrency token, code hiện tại chưa có flow xử lý conflict.  
**Why it happens:** Happy path không phân biệt insufficient quota với concurrent modification.  
**Production impact:** Client nhận 500 chung chung hoặc retry mù.  
**Severity:** Medium  
**Recommended fix:** Map conflict thành domain result phù hợp; nếu retry tự động thì reload state và chạy lại validation trong giới hạn attempt rõ ràng.

### 8. Log thiếu operation identity và before/after state

**Problem:** Log chỉ có source/target/hours.  
**Why it happens:** Không có transfer id/correlation id.  
**Production impact:** Khó nối deadlock, retry và balance change trên nhiều instance.  
**Severity:** Medium  
**Recommended fix:** Log structured `TransferId`, source, target, amount, attempt, duration, result và conflict type; không log dữ liệu nhạy cảm không cần thiết.

### 9. Không giới hạn transaction scope bằng cách chuẩn bị dữ liệu trước

**Problem:** Validation đơn giản có thể thực hiện trước khi mở transaction.  
**Why it happens:** Method mở transaction ngay đầu.  
**Production impact:** Dù nhỏ trong snippet, pattern này làm transaction sống lâu hơn cần thiết nếu sau này thêm validation/I/O.  
**Severity:** Low  
**Recommended fix:** Validate input thuần trước; transaction chỉ bao quanh persistence cần atomicity.

## Phiên bản code đề xuất

Ví dụ sau minh họa ba mục tiêu: canonical ordering, idempotency key và ledger trong cùng transaction. Phần concurrency token/database constraint cần cấu hình trong model/schema thực tế.

```csharp
public sealed class DepartmentQuotaService
{
    private readonly AppDbContext _db;
    private readonly ILogger<DepartmentQuotaService> _logger;

    public DepartmentQuotaService(
        AppDbContext db,
        ILogger<DepartmentQuotaService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<TransferResult> TransferAsync(
        Guid transferId,
        int fromDepartmentId,
        int toDepartmentId,
        decimal hours,
        CancellationToken cancellationToken)
    {
        if (hours <= 0)
            throw new ArgumentOutOfRangeException(nameof(hours));

        if (fromDepartmentId == toDepartmentId)
            throw new ArgumentException("Source and destination must differ.");

        var existing = await _db.DepartmentQuotaTransfers
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == transferId,
                cancellationToken);

        if (existing is not null)
        {
            return new TransferResult(
                existing.Id,
                existing.FromDepartmentId,
                existing.ToDepartmentId,
                existing.Hours);
        }

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var firstId = Math.Min(fromDepartmentId, toDepartmentId);
        var secondId = Math.Max(fromDepartmentId, toDepartmentId);

        var quotas = await _db.DepartmentQuotas
            .Where(x => x.DepartmentId == firstId ||
                        x.DepartmentId == secondId)
            .OrderBy(x => x.DepartmentId)
            .ToListAsync(cancellationToken);

        if (quotas.Count != 2)
            throw new InvalidOperationException("Department quota not found.");

        var from = quotas.Single(x => x.DepartmentId == fromDepartmentId);
        var to = quotas.Single(x => x.DepartmentId == toDepartmentId);

        if (from.AvailableHours < hours)
            throw new InvalidOperationException("Insufficient quota.");

        from.AvailableHours -= hours;
        to.AvailableHours += hours;

        var transfer = new DepartmentQuotaTransfer
        {
            Id = transferId,
            FromDepartmentId = fromDepartmentId,
            ToDepartmentId = toDepartmentId,
            Hours = hours,
            CreatedAt = DateTime.UtcNow
        };

        _db.DepartmentQuotaTransfers.Add(transfer);

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            await tx.RollbackAsync(cancellationToken);
            throw new InvalidOperationException(
                "Quota changed concurrently. Retry with the same transfer id.");
        }

        _logger.LogInformation(
            "Quota transfer completed. TransferId={TransferId} From={From} To={To} Hours={Hours}",
            transferId,
            fromDepartmentId,
            toDepartmentId,
            hours);

        return new TransferResult(
            transferId,
            fromDepartmentId,
            toDepartmentId,
            hours);
    }
}
```

Database nên có:

- unique primary/unique constraint trên `DepartmentQuotaTransfer.Id`,
- concurrency token phù hợp cho `DepartmentQuota`,
- constraint đảm bảo `AvailableHours >= 0` nếu rule này luôn đúng ở database level.

Nếu cần automatic retry khi deadlock/transient error, retry phải dùng **cùng `transferId`** và toàn operation phải được thiết kế để có thể chạy lại an toàn.

## Trade-offs

- **Optimistic concurrency** phù hợp khi conflict không quá thường xuyên; khi contention cao, retry có thể tốn kém.
- **Pessimistic locking/conditional SQL update** có thể cho semantics rõ hơn trong hot-path nhưng tăng lock contention và phụ thuộc database nhiều hơn.
- **Canonical ordering** giảm một lớp deadlock phổ biến nhưng không chứng minh hệ thống sẽ không bao giờ có deadlock; vẫn cần transient error handling và telemetry.
- **Ledger table** tăng storage nhưng cải thiện auditability, idempotency và khả năng reconciliation.
- Nếu transfer volume rất cao và quota là hot aggregate, có thể cần mô hình khác như serialized command processing theo key, nhưng chỉ khi đo được contention thực sự justify complexity.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời hàng trăm transfer `10 -> 20` và `20 -> 10`, xác nhận không mất invariant tổng quota và deadlock rate giảm rõ rệt.
2. **Idempotency test:** gửi cùng `transferId` nhiều lần, kể cả song song; chỉ một ledger entry và một lần thay đổi balance được phép tồn tại.
3. **Insufficient quota test:** nhiều request cùng debit một source gần cạn quota; không request nào làm balance âm.
4. **Ambiguous failure test:** giả lập commit thành công nhưng response bị mất, rồi gọi lại với cùng `transferId`; balance không thay đổi lần hai.
5. **Conflict/retry test:** tạo concurrent modification để phát sinh concurrency exception; xác nhận retry policy giữ nguyên transfer identity và không bỏ qua validation.

## Quan sát trong production

Nên theo dõi:

- transfer success/failure/conflict rate,
- deadlock victim count,
- lock wait duration và blocked session trên database,
- transaction duration,
- retry attempts theo `TransferId`,
- duplicate-idempotency hits,
- quota invariant violation alert,
- trace spans cho query/load/save/commit,
- top department pairs có contention cao.

Khi điều tra incident, cần có correlation giữa application trace và database session/query để phân biệt deadlock, lock wait, optimistic conflict và client retry.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- SSRF không chỉ là kiểm tra URL syntax; cần xem xét destination policy, DNS/IP resolution, redirect, network egress và response/resource limits.
- Mọi outbound HTTP feature nhận URL từ người dùng đều phải được xem như một security boundary.
- Transaction retry không thể tách rời idempotency; ambiguous failure sau commit là tình huống cần thiết kế trước.
- Deadlock thường liên quan thứ tự acquire lock và contention; canonical ordering giúp giảm rủi ro nhưng không thay thế monitoring/retry policy.
- Business invariant quan trọng nên có database guarantee phù hợp thay vì chỉ phụ thuộc `if` ở application layer.

## Mẫu tư duy cần nhớ

- Treat outbound destinations as untrusted input.
- Enforce business invariants at the strongest practical boundary.
- Design retries together with idempotency.
- Acquire shared resources in a deterministic order.
- Treat observability and failure recovery as part of the design.
