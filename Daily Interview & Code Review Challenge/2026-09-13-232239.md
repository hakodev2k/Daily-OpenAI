# Code Review Challenge 1 — Service Bus consumer xử lý payment trùng khi lock hết hạn và retry sau lỗi mạng

**Chủ đề:** C#/.NET 8, Azure Service Bus, Peek-Lock, manual settlement, duplicate delivery, idempotency, retry, DLQ, external API, bounded concurrency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một order-processing service chạy trên Azure App Service. Service đọc message từ Azure Service Bus queue `payment-requests` để capture payment qua một third-party payment provider.

Mỗi message chứa `MessageId`, `OrderId`, `PaymentAttemptId` và `Amount`. Business yêu cầu:

- một logical payment attempt chỉ được capture tiền tối đa một lần;
- message có thể được redeliver và consumer phải xử lý an toàn;
- một số payment provider request mất 2–6 phút trong giờ cao điểm;
- một số trường hợp provider đã capture thành công nhưng client bị timeout trước khi nhận response;
- queue có poison-message handling và DLQ;
- service chạy 6 instances;
- throughput quan trọng nhưng không được đánh đổi correctness;
- production phải trace được từ Service Bus message → payment provider request → database state.

Production hiện có các triệu chứng:

- một số order bị capture hai lần;
- logs cho thấy cùng `MessageId` được xử lý bởi hai instances cách nhau vài phút;
- thỉnh thoảng `CompleteMessageAsync` báo lỗi lock đã mất;
- khi payment provider chậm, số delivery tăng;
- một số message lỗi validation bị retry nhiều lần trước khi vào DLQ;
- team tăng `MaxConcurrentCalls` lên 64 để xử lý backlog nhưng provider bắt đầu trả 429 nhiều hơn;
- developer cho rằng `MessageId` giống nhau nghĩa là Service Bus sẽ tự động bảo đảm consumer chỉ xử lý một lần;
- một developer khác đề xuất chỉ tăng lock duration để giải quyết duplicate payment.

## Đoạn code cần review

```csharp
public sealed class PaymentMessageWorker : BackgroundService
{
    private readonly ServiceBusProcessor _processor;
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<PaymentMessageWorker> _logger;

    public PaymentMessageWorker(
        ServiceBusClient serviceBusClient,
        IDbContextFactory<AppDbContext> dbFactory,
        IPaymentGateway gateway,
        ILogger<PaymentMessageWorker> logger)
    {
        _dbFactory = dbFactory;
        _gateway = gateway;
        _logger = logger;

        _processor = serviceBusClient.CreateProcessor(
            "payment-requests",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 64,
                MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(2)
            });
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        _processor.ProcessMessageAsync += HandleMessageAsync;
        _processor.ProcessErrorAsync += HandleErrorAsync;

        await _processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }

    private async Task HandleMessageAsync(ProcessMessageEventArgs args)
    {
        var request = args.Message.Body.ToObjectFromJson<PaymentRequest>()!;

        await using var db =
            await _dbFactory.CreateDbContextAsync(args.CancellationToken);

        var alreadyProcessed = await db.PaymentAttempts
            .AnyAsync(
                x => x.PaymentAttemptId == request.PaymentAttemptId &&
                     x.Status == "Captured",
                args.CancellationToken);

        if (alreadyProcessed)
        {
            await args.CompleteMessageAsync(args.Message, args.CancellationToken);
            return;
        }

        try
        {
            var result = await _gateway.CaptureAsync(
                request.OrderId,
                request.Amount,
                args.CancellationToken);

            db.PaymentAttempts.Add(new PaymentAttempt
            {
                PaymentAttemptId = request.PaymentAttemptId,
                OrderId = request.OrderId,
                ProviderTransactionId = result.TransactionId,
                Status = "Captured",
                CapturedAt = DateTimeOffset.UtcNow
            });

            await db.SaveChangesAsync(args.CancellationToken);

            await args.CompleteMessageAsync(
                args.Message,
                args.CancellationToken);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Payment failed for {OrderId} attempt {PaymentAttemptId}",
                request.OrderId,
                request.PaymentAttemptId);

            await args.AbandonMessageAsync(
                args.Message,
                cancellationToken: args.CancellationToken);
        }
    }

    private Task HandleErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(
            args.Exception,
            "Service Bus error from {ErrorSource}",
            args.ErrorSource);

        return Task.CompletedTask;
    }

    public override async Task StopAsync(CancellationToken cancellationToken)
    {
        await _processor.StopProcessingAsync(cancellationToken);
        await _processor.DisposeAsync();
        await base.StopAsync(cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

## Kết quả code review tham khảo

### Critical — Check-then-act không ngăn duplicate payment giữa nhiều consumers

**Vấn đề:** Code query `PaymentAttempts` trước rồi mới gọi `_gateway.CaptureAsync`. Hai consumers có thể cùng thấy chưa có row `Captured` và cùng gửi capture.

**Tại sao xảy ra:** `AnyAsync` và external side effect không nằm trong một atomic transaction. Application đang dùng một pre-check như distributed lock.

**Ảnh hưởng production:** Duplicate delivery hoặc concurrent handling có thể charge khách hàng nhiều lần.

**Cách sửa:** Xây idempotency ở business-operation level. `PaymentAttemptId` phải là stable operation key; database cần unique constraint cho key này và provider request nên dùng cùng idempotency key nếu provider hỗ trợ. Local state machine phải phân biệt `Pending`, `Processing`, `Captured`, `Unknown`, `FailedPermanent` thay vì chỉ check row `Captured`.

### Critical — Ambiguous timeout sau external side effect có thể tạo duplicate charge

**Vấn đề:** Provider có thể capture thành công nhưng client timeout trước khi nhận response, khiến code vào `catch`, abandon message và retry toàn bộ operation.

**Tại sao xảy ra:** HTTP timeout chỉ cho biết client không biết outcome, không chứng minh provider chưa thực hiện side effect.

**Ảnh hưởng production:** Redelivery có thể gửi capture lần hai.

**Cách sửa:** Dùng provider-supported idempotency key nếu có. Nếu không có, cần reconciliation protocol: query transaction status bằng stable external reference trước khi retry một non-idempotent operation. Trạng thái `Unknown` nên được xử lý như first-class state thay vì retry mù.

### Critical — Local row chỉ được tạo sau khi payment đã được capture

**Vấn đề:** Không có durable record cho operation trước external call.

**Tại sao xảy ra:** Application chỉ persist success outcome, không persist intent/ownership.

**Ảnh hưởng production:** Nếu process crash sau provider success nhưng trước `SaveChangesAsync`, lần redelivery không có local evidence rằng attempt đã từng được gửi.

**Cách sửa:** Persist payment attempt intent trước external call bằng unique business key. Có thể transition `Pending → Processing → Captured/Unknown/Failed`. Transaction local không thể bao trùm provider, nhưng durable intent giúp recovery/reconciliation deterministic hơn.

### High — Message lock có thể hết hạn trước khi handler hoàn tất

**Vấn đề:** `MaxAutoLockRenewalDuration` là 2 phút trong khi processing có thể kéo dài 6 phút.

**Tại sao xảy ra:** Sau khi lock không còn được renew và hết hạn, message có thể được redeliver trong lúc handler cũ vẫn đang chạy.

**Ảnh hưởng production:** Hai instances có thể cùng process cùng logical payment. `CompleteMessageAsync` của handler cũ có thể thất bại vì lock lost dù external side effect đã xảy ra.

**Cách sửa:** Cấu hình lock renewal phù hợp với normal processing budget và tối ưu handler để không giữ message lâu không cần thiết. Tuy nhiên lock renewal chỉ giảm concurrent redelivery; nó không thay idempotency.

### High — Tăng lock duration không giải quyết crash/network ambiguity

**Vấn đề:** Đề xuất “chỉ tăng lock” coi temporary ownership là correctness guarantee.

**Tại sao xảy ra:** Process có thể crash, connection có thể mất, settlement có thể fail và message vẫn được redeliver.

**Ảnh hưởng production:** Duplicate business side effect vẫn có thể xảy ra dù lock dài hơn.

**Cách sửa:** Dùng lock cho delivery coordination; dùng idempotency/durable state cho business correctness.

### High — Mọi exception đều bị abandon và retry như nhau

**Vấn đề:** Invalid payload, business validation, auth failure, provider 400 và transient timeout đều đi cùng một path.

**Tại sao xảy ra:** Error taxonomy chưa được model hóa.

**Ảnh hưởng production:** Poison message tiêu tốn delivery attempts, tạo noise, làm backlog tăng và có thể che lỗi permanent.

**Cách sửa:** Phân loại lỗi. Permanent validation lỗi nên dead-letter kèm reason an toàn; transient dependency lỗi có thể abandon/retry theo policy; ambiguous payment outcome nên chuyển `Unknown`/reconciliation thay vì retry capture mù.

### High — `MaxConcurrentCalls = 64` không gắn với capacity của payment provider

**Vấn đề:** Consumer concurrency được tăng để giảm queue backlog mà không xét provider rate limit, connection budget hoặc database capacity.

**Tại sao xảy ra:** Throughput queue được tối ưu độc lập với downstream bottleneck.

**Ảnh hưởng production:** 429/timeouts tăng, lock giữ lâu hơn, retry nhiều hơn và backlog có thể nặng hơn.

**Cách sửa:** Chọn bounded concurrency dựa trên measured dependency latency, provider quota, expected throughput và SLO. Có thể thêm client-side rate limiting/bulkhead nếu provider contract yêu cầu.

### Medium — Dedupe state không có database uniqueness enforcement rõ ràng

**Vấn đề:** Đoạn code không cho thấy unique constraint trên `PaymentAttemptId`.

**Tại sao xảy ra:** Correctness phụ thuộc application pre-check.

**Ảnh hưởng production:** Concurrent inserts có thể tạo nhiều rows cho cùng logical attempt hoặc tạo race khó xử lý.

**Cách sửa:** Enforce unique index/constraint ở database. Handle unique-conflict như một expected concurrency outcome và đọc lại canonical state.

### Medium — Cancellation của message handler bị dùng trực tiếp cho mọi bước recovery

**Vấn đề:** Nếu processing token bị canceled do shutdown/lock lifecycle, code recovery như `AbandonMessageAsync` có thể cũng bị cancel ngay.

**Tại sao xảy ra:** Processing cancellation và settlement/recovery budget không được phân biệt.

**Ảnh hưởng production:** Settlement có thể không thực hiện được; message sẽ phụ thuộc lock expiry để redeliver.

**Cách sửa:** Thiết kế shutdown/settlement rõ ràng. Không cố settle bằng token đã bị canceled nếu SDK/lifecycle contract yêu cầu budget riêng; nhưng cũng không kéo dài shutdown vô hạn. Quan trọng nhất là handler phải an toàn khi message được redeliver.

### Medium — Logging thiếu message identity và delivery context

**Vấn đề:** Log chỉ có order và attempt id; không có Service Bus `MessageId`, delivery count, correlation id hoặc provider idempotency key/reference.

**Tại sao xảy ra:** Observability chưa model hóa distributed workflow.

**Ảnh hưởng production:** Khó phân biệt duplicate delivery, retry, provider timeout và application bug.

**Cách sửa:** Log structured metadata: `MessageId`, `PaymentAttemptId`, `OrderId`, delivery count, processor instance, provider request reference, final state và settlement result. Không log secret/card data.

### Low — Worker lifecycle chưa thể hiện unregister handlers nếu object tái sử dụng

**Vấn đề:** Handlers được subscribe trong `ExecuteAsync` nhưng không unsubscribe trước dispose.

**Tại sao xảy ra:** Lifecycle dựa vào processor disposal để cleanup.

**Ảnh hưởng production:** Trong lifecycle thông thường impact thấp, nhưng code khó tái sử dụng/test nếu processor bị start/stop nhiều lần.

**Cách sửa:** Giữ lifecycle đơn giản: processor sở hữu đúng một worker lifetime; nếu có restart logic trong-process thì subscribe/unsubscribe explicit.

## Phiên bản đề xuất

Một hướng an toàn hơn là tạo durable payment attempt trước external call, enforce unique key và gửi stable idempotency key cho provider. Đoạn dưới minh họa application flow; API cụ thể của provider phải được xác minh theo provider thực tế.

```csharp
public sealed class PaymentHandler
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IPaymentGateway _gateway;
    private readonly ILogger<PaymentHandler> _logger;

    public PaymentHandler(
        IDbContextFactory<AppDbContext> dbFactory,
        IPaymentGateway gateway,
        ILogger<PaymentHandler> logger)
    {
        _dbFactory = dbFactory;
        _gateway = gateway;
        _logger = logger;
    }

    public async Task<PaymentHandleResult> HandleAsync(
        PaymentRequest request,
        string messageId,
        CancellationToken cancellationToken)
    {
        var idempotencyKey = $"payment:{request.PaymentAttemptId}";

        await using var db =
            await _dbFactory.CreateDbContextAsync(cancellationToken);

        var attempt = await db.PaymentAttempts
            .SingleOrDefaultAsync(
                x => x.PaymentAttemptId == request.PaymentAttemptId,
                cancellationToken);

        if (attempt?.Status == PaymentStatus.Captured)
            return PaymentHandleResult.AlreadyCompleted;

        if (attempt is null)
        {
            attempt = new PaymentAttempt
            {
                PaymentAttemptId = request.PaymentAttemptId,
                OrderId = request.OrderId,
                Amount = request.Amount,
                Status = PaymentStatus.Pending,
                CreatedAt = DateTimeOffset.UtcNow
            };

            db.PaymentAttempts.Add(attempt);

            try
            {
                await db.SaveChangesAsync(cancellationToken);
            }
            catch (DbUpdateException ex) when (IsUniqueConflict(ex))
            {
                return PaymentHandleResult.RetryReadCanonicalState;
            }
        }

        if (attempt.Status == PaymentStatus.Unknown)
            return PaymentHandleResult.RequiresReconciliation;

        attempt.Status = PaymentStatus.Processing;
        attempt.LastMessageId = messageId;
        await db.SaveChangesAsync(cancellationToken);

        try
        {
            var result = await _gateway.CaptureAsync(
                request.OrderId,
                request.Amount,
                idempotencyKey,
                cancellationToken);

            attempt.Status = PaymentStatus.Captured;
            attempt.ProviderTransactionId = result.TransactionId;
            attempt.CapturedAt = DateTimeOffset.UtcNow;
            await db.SaveChangesAsync(cancellationToken);

            return PaymentHandleResult.Completed;
        }
        catch (PaymentOutcomeUnknownException)
        {
            attempt.Status = PaymentStatus.Unknown;
            await db.SaveChangesAsync(CancellationToken.None);
            return PaymentHandleResult.RequiresReconciliation;
        }
    }
}
```

Consumer layer sau đó quyết định settlement dựa trên result:

```csharp
private async Task HandleMessageAsync(ProcessMessageEventArgs args)
{
    PaymentRequest request;

    try
    {
        request = args.Message.Body.ToObjectFromJson<PaymentRequest>()
            ?? throw new InvalidDataException("Missing payment payload.");

        Validate(request);
    }
    catch (Exception ex) when (IsPermanentMessageError(ex))
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            "InvalidPaymentRequest",
            "Payload failed validation.",
            args.CancellationToken);
        return;
    }

    var result = await _handler.HandleAsync(
        request,
        args.Message.MessageId,
        args.CancellationToken);

    switch (result)
    {
        case PaymentHandleResult.Completed:
        case PaymentHandleResult.AlreadyCompleted:
        case PaymentHandleResult.RequiresReconciliation:
            await args.CompleteMessageAsync(
                args.Message,
                args.CancellationToken);
            break;

        case PaymentHandleResult.RetryReadCanonicalState:
            await args.AbandonMessageAsync(
                args.Message,
                cancellationToken: args.CancellationToken);
            break;
    }
}
```

Việc complete message khi state là `RequiresReconciliation` chỉ hợp lý nếu application đã persist durable `Unknown` state và có một reconciliation workflow khác chịu trách nhiệm giải quyết. Nếu không có workflow đó, không được áp dụng lựa chọn này.

Nếu payment provider không hỗ trợ idempotency key hoặc query-status theo stable reference, automatic retry cho operation capture có thể không đáp ứng requirement “at most one charge”. Khi đó cần thay đổi integration contract hoặc đưa case ambiguous vào manual review thay vì giả định queue retry có thể sửa correctness.

Azure Service Bus dùng lock/settlement để quản lý delivery ownership; duplicate delivery vẫn phải được consumer xử lý an toàn. Lock loss hoặc settlement failure không cho phép suy ra rằng side effect trước đó chưa xảy ra.

## Giải thích thiết kế sau khi sửa

`PaymentAttemptId` trở thành business idempotency key thay vì chỉ là field để query trước khi chạy. Database unique constraint giúp serialize identity của logical operation ở durable layer.

External provider nhận stable idempotency key nếu contract hỗ trợ. Đây là lớp quan trọng nhất để bảo vệ khỏi ambiguous timeout sau khi provider đã thực hiện side effect.

Trạng thái `Unknown` tránh biến “không biết outcome” thành “failed, retry lại”. Reconciliation có thể query provider theo external reference hoặc đưa manual review nếu provider không có API phù hợp.

Service Bus lock vẫn có giá trị: nó giảm concurrent handling bình thường và hỗ trợ work ownership. Nhưng correctness cuối cùng phải chịu được redelivery vì network failure, process crash và lock loss đều có thể xảy ra.

Concurrency của processor phải được tune cùng dependency. Nếu provider chỉ chịu được 20 concurrent requests ổn định thì 64 handlers chỉ làm tăng queue-to-dependency pressure.

## Trade-offs

Durable state machine phức tạp hơn một row `Captured`, nhưng payment là non-idempotent side effect có business impact cao nên complexity này có cơ sở.

Unique constraint tạo contention nếu cùng `PaymentAttemptId` bị duplicate rất nhiều, nhưng đây là contention mong muốn ở correctness boundary.

Provider idempotency key làm application phụ thuộc vào semantics của external API; contract đó phải được verify và monitor. Không được giả định mọi provider giữ idempotency key vô hạn hoặc cùng behavior.

Reconciliation workflow tăng operational cost. Tuy nhiên với ambiguous outcome, manual hoặc automated reconciliation thường an toàn hơn blind retry.

Giảm `MaxConcurrentCalls` có thể làm queue backlog tăng ngắn hạn; cần cân bằng queue age SLO với dependency capacity thay vì tối đa hóa dequeue rate.

## Cách kiểm thử

1. **Concurrency integration test:** gửi cùng logical `PaymentAttemptId` nhiều lần và chạy nhiều consumers; xác minh provider mock chỉ nhận một effective capture hoặc cùng idempotency key được deduplicate.
2. **Ambiguous-timeout test:** provider mock ghi nhận capture thành công rồi client nhận timeout; redelivery không được tạo charge thứ hai.
3. **Lock-loss test:** cố tình làm handler lâu hơn lock-renewal window; message bị redeliver nhưng final business state và provider side effect vẫn đúng một lần.
4. **Poison-message test:** payload invalid phải vào DLQ theo policy thay vì lặp transient retry.
5. **Load test:** tăng queue backlog và đo throughput với nhiều mức `MaxConcurrentCalls`; theo dõi provider 429, p95/p99, lock loss, delivery count và queue age.

## Quan sát trong production

Theo dõi:

- active message handlers;
- queue depth và oldest message age;
- message delivery count;
- lock-lost/settlement failures;
- completed, abandoned và dead-lettered count;
- payment attempts theo trạng thái `Pending`, `Processing`, `Captured`, `Unknown`, `FailedPermanent`;
- duplicate `PaymentAttemptId` conflict count;
- provider latency, timeout, 429/5xx;
- reconciliation backlog;
- correlation `MessageId` → `PaymentAttemptId` → provider request reference → database transaction;
- số operation được provider deduplicate theo idempotency key nếu provider expose metric/log tương ứng.

Alert khi `Unknown` tăng bất thường, lock-lost tăng, provider 429 tăng, queue age vượt SLO hoặc cùng logical attempt xuất hiện nhiều delivery liên tục.

# Code Review Challenge 2 — Kubernetes probes gây restart cascade khi Redis chậm và rollout làm mất nửa capacity

**Chủ đề:** Kubernetes, ASP.NET Core, liveness/readiness/startup probes, rolling deployment, resource requests/limits, Secrets, graceful shutdown, deployment safety, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core internal portal đang được thử nghiệm migrate từ Azure App Service sang Kubernetes. Team chỉ có 2 replicas ở production vì traffic chưa lớn.

Application mất khoảng 45–70 giây sau startup để load configuration, warm local caches và establish một số connection. Endpoint `/health` hiện kiểm tra:

- process còn chạy;
- SQL Server query `SELECT 1`;
- Redis `PING`;
- một third-party API health endpoint.

Production có các triệu chứng:

- khi Redis latency tăng trong 30–60 giây, cả hai pods bị restart liên tục;
- trong rollout, user thấy burst 502/503;
- một pod mới thường restart 2–3 lần trước khi startup hoàn tất;
- CPU bị throttle mạnh khi traffic tăng dù node vẫn còn capacity;
- deploy cùng tag `latest` nhưng hai pods đôi lúc chạy image digest khác nhau;
- database password nằm trực tiếp trong deployment manifest;
- khi pod terminate, một số request đang xử lý bị cắt giữa chừng;
- team cho rằng readiness và liveness nên gọi cùng endpoint để “đơn giản hóa”.

Business requirements:

- transient Redis/third-party outage không được làm application process restart hàng loạt;
- pod chưa warm xong không được nhận traffic;
- rollout phải giữ service capacity tối đa có thể với 2 replicas;
- artifact phải immutable/auditable;
- secret không được hard-code trong manifest Git;
- application cần đủ thời gian drain request khi shutdown;
- không thêm service mesh hoặc platform complexity nếu Kubernetes primitives đã đủ.

## Kết quả code review tham khảo

### Critical — Liveness probe phụ thuộc external dependencies nên transient outage gây restart cascade

**Vấn đề:** `/health` kiểm tra SQL, Redis và third-party rồi được dùng cho liveness.

**Tại sao xảy ra:** Liveness đang trả lời câu hỏi “mọi dependency có healthy không?” thay vì “process này có bị kẹt/hỏng đến mức cần restart không?”.

**Ảnh hưởng production:** Khi Redis hoặc third-party chậm, tất cả pods có thể fail liveness gần cùng lúc và bị kubelet restart, giảm capacity đúng lúc dependency đang degrade.

**Cách sửa:** Tách endpoint. `/health/live` chỉ kiểm tra process/internal liveness tối thiểu; không fail vì transient external dependency. `/health/ready` có thể kiểm tra những dependency thật sự bắt buộc để phục vụ request, với timeout/budget phù hợp.

### Critical — Không có startup probe cho application khởi động 45–70 giây

**Vấn đề:** Liveness bắt đầu sau 5 giây, fail sau hai lần với chu kỳ 5 giây.

**Tại sao xảy ra:** Probe timing không phản ánh startup profile thực tế.

**Ảnh hưởng production:** Container có thể bị kill trước khi hoàn tất warm-up và rơi vào restart loop.

**Cách sửa:** Dùng `startupProbe` với budget đủ cho startup observed worst-case. Khi startup probe được cấu hình, liveness/readiness sẽ không bắt đầu cho tới khi startup thành công. Sau đó liveness có thể dùng threshold chặt hơn.

### High — Readiness và liveness dùng cùng một health contract

**Vấn đề:** Cùng `/health` khiến dependency failure vừa ngừng traffic vừa restart process.

**Tại sao xảy ra:** Hai loại signal có semantics khác nhau nhưng bị collapse thành một endpoint.

**Ảnh hưởng production:** Temporary dependency issue biến thành pod churn, connection churn và rollout instability.

**Cách sửa:** Tách `/health/live` và `/health/ready`. Readiness có thể fail khi app không thể phục vụ traffic; liveness chỉ fail khi restart process có khả năng sửa vấn đề.

### High — Rolling update có thể giảm capacity xuống còn một pod mà không tạo pod mới trước

**Vấn đề:** Với 2 replicas, `maxUnavailable: 50%` cho phép một replica unavailable và `maxSurge: 0` không cho thêm replica vượt desired count.

**Tại sao xảy ra:** Rollout policy ưu tiên không tăng pod count hơn availability.

**Ảnh hưởng production:** Chỉ còn một pod phục vụ traffic trong rollout; nếu pod đó chậm hoặc probe fail, user có thể nhận 502/503.

**Cách sửa:** Với workload nhỏ nhưng cần availability, cân nhắc `maxUnavailable: 0` và `maxSurge: 1`, nếu cluster capacity cho phép. Đây là capacity trade-off, không phải universal default.

### High — `latest` là mutable image reference, làm deploy/rollback thiếu determinism

**Vấn đề:** Manifest không pin immutable version/digest.

**Tại sao xảy ra:** Cùng tag có thể trỏ tới image content khác theo thời điểm pull/cache.

**Ảnh hưởng production:** Hai pods có thể chạy khác digest; audit và rollback khó chứng minh chính xác artifact.

**Cách sửa:** Dùng immutable version tag gắn với build hoặc pin image digest. Release metadata nên ghi commit/build/image digest.

### High — Secret nằm plaintext trong manifest

**Vấn đề:** DB password được commit trực tiếp trong YAML.

**Tại sao xảy ra:** Configuration và secret material không được tách.

**Ảnh hưởng production:** Credential có thể leak qua Git history, review, CI logs hoặc artifact storage.

**Cách sửa:** Dùng Kubernetes Secret hoặc secret provider phù hợp với platform. Deployment chỉ reference secret key; RBAC phải hạn chế quyền đọc. Base64 trong Secret không phải encryption boundary tự thân, nên cluster secret-at-rest/RBAC vẫn cần được quản trị đúng.

### High — CPU limit quá sát request và có evidence throttling

**Vấn đề:** `requests.cpu` và `limits.cpu` đều là `250m`; application không có burst headroom.

**Tại sao xảy ra:** Resource limit được chọn cố định mà không dựa trên profiling/load evidence.

**Ảnh hưởng production:** CPU throttling kéo dài request/probe latency; probe timeout 1 giây càng dễ fail và tạo self-amplifying restart/readiness issue.

**Cách sửa:** Đo CPU usage/throttling, GC, latency và node capacity. Chọn request cho scheduling baseline và limit nếu cần theo operational policy, nhưng không đặt con số arbitrary. Nếu limit gây throttling mà node còn headroom, cần tune lại.

### Medium — `terminationGracePeriodSeconds: 5` quá ngắn so với shutdown contract

**Vấn đề:** Pod chỉ có 5 giây trước khi Kubernetes kết thúc process theo termination flow.

**Tại sao xảy ra:** Grace period không phản ánh thời gian app cần để ngừng nhận work mới và hoàn tất request đang chạy.

**Ảnh hưởng production:** In-flight request có thể bị cắt, tạo client errors hoặc partial operations.

**Cách sửa:** Đặt grace period dựa trên measured maximum reasonable request/drain time. ASP.NET Core phải handle SIGTERM/shutdown cancellation đúng. Với long-running operations cần tách khỏi request hoặc thiết kế idempotency.

### Medium — Readiness `failureThreshold: 1` + timeout 1 giây quá nhạy với jitter

**Vấn đề:** Một lần probe chậm có thể làm pod unready ngay.

**Tại sao xảy ra:** Threshold chưa dựa trên latency distribution và desired failover speed.

**Ảnh hưởng production:** Endpoint churn và capacity fluctuation khi dependency có latency spike ngắn.

**Cách sửa:** Chọn timeout/threshold dựa trên SLO và observed latency. Không che dependency outage quá lâu, nhưng cũng tránh phản ứng với một transient blip.

### Medium — Memory request/limit bằng nhau và chưa có evidence sizing

**Vấn đề:** `256Mi` vừa là request vừa là hard limit, nhưng không có evidence về working set/GC headroom.

**Tại sao xảy ra:** Resource values được chọn như template default.

**Ảnh hưởng production:** Nếu .NET vượt limit trong load spike, container có thể bị OOMKilled; nếu request quá cao, scheduler lại lãng phí capacity.

**Cách sửa:** Load test và quan sát working set, heap, GC, allocation rate. Chọn memory request/limit theo real profile và failure policy.

### Low — Deployment thiếu metadata liên kết release với source/build

**Vấn đề:** Ngoài image mutable, manifest không có annotation/version metadata phục vụ audit.

**Tại sao xảy ra:** Deployment được coi là config thuần túy thay vì release artifact.

**Ảnh hưởng production:** Incident investigation khó biết pod thuộc commit/build nào.

**Cách sửa:** Gắn annotation/label an toàn như commit SHA, build id, release id; không chứa secret.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa probe separation, immutable image, safer rollout và secret reference. Các resource numbers chỉ là placeholder cần thay bằng số đo thực tế.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-portal
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: employee-portal
  template:
    metadata:
      labels:
        app: employee-portal
        app.kubernetes.io/version: "2026.09.13.232239"
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: web
          image: registry.example.com/employee-portal@sha256:REPLACE_WITH_RELEASE_DIGEST
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_URLS
              value: http://+:8080
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: employee-portal-secrets
                  key: main-db
            - name: Redis__Endpoint
              value: redis-prod:6379
          resources:
            requests:
              cpu: "300m"
              memory: "384Mi"
            limits:
              cpu: "1"
              memory: "768Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 18
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
```

`failureThreshold: 18` với `periodSeconds: 5` tạo khoảng startup budget minh họa khoảng 90 giây. Con số thực tế phải dựa trên measured startup p95/p99 và safety margin, không copy cố định.

`/health/live` nên rất rẻ và chỉ fail khi restart process có khả năng phục hồi application. `/health/ready` có thể kiểm tra SQL/Redis nếu chúng thực sự bắt buộc cho phần lớn request. Third-party API có thể không nên nằm trong readiness nếu application vẫn phục vụ được phần còn lại hoặc đã có degradation strategy.

Không phải mọi dependency outage đều nên làm pod unready. Ví dụ nếu Redis chỉ là cache và application có DB fallback, readiness có thể vẫn healthy nhưng metric/alert phải cho thấy cache degraded.

Nếu cluster không đủ capacity cho `maxSurge: 1`, team phải chấp nhận trade-off khác: tăng replicas, dự phòng node capacity hoặc cho phép một mức unavailable. Không thể đạt zero-capacity-loss rollout nếu infrastructure không có headroom.

## Giải thích thiết kế sau khi sửa

Startup probe bảo vệ slow initialization. Chỉ sau khi startup thành công, liveness/readiness mới bắt đầu đánh giá runtime state.

Liveness tách khỏi dependency health để tránh restart cascade. Readiness dùng để quyết định có nên gửi traffic tới pod tại thời điểm đó.

`maxUnavailable: 0` + `maxSurge: 1` ưu tiên availability: pod mới phải lên ready trước khi giảm pod cũ, đổi lại cần capacity cho một replica bổ sung trong rollout.

Immutable image digest giúp rollback và audit deterministic. Version label phục vụ telemetry/deployment correlation.

Secret reference giảm nguy cơ credential nằm trong Git manifest. Tuy nhiên Secret vẫn cần RBAC và secret-at-rest controls; đổi từ plaintext sang Secret không tự động giải quyết toàn bộ secret management.

Resource values trong ví dụ chỉ là starting point. Correct sizing phải dựa trên load test, CPU throttling metrics, memory working set và latency.

## Trade-offs

Readiness kiểm tra dependency quá sâu có thể làm toàn bộ service mất endpoints khi dependency outage, dù application có thể degrade một phần. Vì vậy health semantics phải theo business capability chứ không chỉ technical reachability.

Liveness quá nông có thể không bắt được deadlock/application stuck. Endpoint cần phản ánh internal progress đủ để restart có ích nhưng không gọi dependency bên ngoài không cần thiết.

Startup budget quá dài làm pod hỏng thật mất lâu mới bị restart; quá ngắn lại kill slow-but-valid startup. Cần dùng telemetry để tune.

`maxSurge: 1` cần extra cluster capacity và có thể tăng cost ngắn hạn. Với workload resource-heavy, surge policy phải phối hợp scheduler/autoscaling.

CPU limit cao hơn cho phép burst nhưng có thể ảnh hưởng fairness giữa workloads. Có team chọn không đặt CPU limit cho latency-sensitive app nhưng vẫn đặt request; đó là cluster policy decision cần đánh giá riêng, không phải mặc định universal.

Graceful shutdown dài hơn giúp drain request nhưng rollout/scale-down cũng chậm hơn. Long-running transactions vẫn cần idempotency vì process có thể bị kill ngoài graceful path.

## Cách kiểm thử

1. **Dependency failure test:** làm Redis unavailable 60 giây; xác minh pods không restart chỉ vì Redis, và readiness behavior đúng theo degradation contract.
2. **Slow-start test:** tăng startup lên 70 giây; xác minh startup probe bảo vệ container khỏi liveness restart và pod chỉ nhận traffic sau readiness success.
3. **Rolling deployment validation:** deploy version mới với 2 replicas; xác minh luôn còn đủ ready capacity theo policy và không có burst 502/503.
4. **Resource/load test:** tạo CPU load ở nhiều mức; đo throttling, probe latency, request p95/p99, restarts và OOM events để tune requests/limits.
5. **Shutdown test:** gửi request kéo dài 20–30 giây rồi terminate pod; xác minh pod ngừng nhận traffic mới và request hiện tại hoàn tất trong grace period khi có thể.

## Quan sát trong production

Theo dõi:

- pod restart count và restart reason;
- startup duration p50/p95/p99;
- readiness/liveness probe failures;
- number of ready replicas;
- rollout duration và unavailable replicas;
- HTTP 5xx/502/503 trong deployment window;
- CPU usage và CPU throttling;
- memory working set, GC metrics và OOMKilled events;

Alert khi ready replicas dưới SLO, restart rate tăng, CPU throttling kéo dài, probe failures correlate với dependency latency hoặc rollout tạo error spike.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message lock và settlement điều phối delivery, nhưng không tạo exactly-once business semantics cho external side effect.
- Retry phải đi cùng idempotency; đặc biệt với payment, timeout có thể là **unknown outcome**, không đồng nghĩa operation thất bại.
- Durable business key + database uniqueness + provider idempotency/reconciliation là các lớp khác nhau và bổ sung cho nhau.
- Processor concurrency phải theo downstream capacity, không theo mong muốn giảm queue backlog một cách độc lập.
- Kubernetes liveness, readiness và startup probes có mục đích khác nhau; gộp tất cả dependency checks vào liveness có thể biến outage nhỏ thành restart cascade.
- Rolling deployment, resource limits và graceful shutdown đều là phần của application availability design, không chỉ là YAML syntax.

## Mẫu tư duy cần nhớ

- **Design retry together with idempotency.**
- **Unknown outcome khác với failed outcome.**
- **Temporary ownership không thay thế durable correctness.**
- **Health signal phải trả lời đúng câu hỏi: restart, route traffic hay chờ startup.**
- **Deployment safety = capacity + health checks + immutable artifact + graceful shutdown.**
