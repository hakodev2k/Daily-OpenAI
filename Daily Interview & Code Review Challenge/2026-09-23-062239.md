# Code Review Challenge 1 — Cosmos DB API ghi nhanh nhưng RU tăng vọt và một partition bị nghẽn

**Chủ đề:** C#/.NET, ASP.NET Core, Cosmos DB, partition key, concurrency, query cost, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một event-management platform dùng ASP.NET Core API và Azure Cosmos DB để lưu `AttendanceEvent`. Hệ thống chạy nhiều Azure App Service instances. Mỗi event thuộc một tenant; một số tenant lớn có hàng trăm nghìn nhân viên và tạo traffic cao vào đầu/ cuối ca.

Container hiện được partition theo `/tenantId`. Production ghi nhận RU consumption tăng mạnh vào giờ cao điểm, request bị throttling và latency p99 tăng. Team cũng thấy endpoint đọc lịch sử của một employee tốn nhiều RU hơn dự kiến. Một developer đề xuất tăng throughput ngay và thêm retry vô hạn khi gặp lỗi tạm thời.

## Đoạn code cần review

```csharp
public sealed record AttendanceEvent(
    string id,
    string tenantId,
    string employeeId,
    DateTime timestampUtc,
    string type);

[ApiController]
[Route("api/attendance")]
public sealed class AttendanceController : ControllerBase
{
    private readonly Container _container;

    public AttendanceController(CosmosClient client)
    {
        _container = client.GetContainer("hr", "attendance-events");
    }

    [HttpPost]
    public async Task<IActionResult> Add(
        [FromBody] AttendanceEvent input,
        CancellationToken cancellationToken)
    {
        var item = input with
        {
            id = Guid.NewGuid().ToString(),
            timestampUtc = DateTime.UtcNow
        };

        await _container.CreateItemAsync(
            item,
            new PartitionKey(item.tenantId));

        return Ok(item);
    }

    [HttpGet("employees/{employeeId}")]
    public async Task<IActionResult> GetHistory(
        string employeeId,
        [FromQuery] DateTime fromUtc,
        [FromQuery] DateTime toUtc,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.employeeId = @employeeId " +
            "AND c.timestampUtc >= @from AND c.timestampUtc < @to")
            .WithParameter("@employeeId", employeeId)
            .WithParameter("@from", fromUtc)
            .WithParameter("@to", toUtc);

        var iterator = _container.GetItemQueryIterator<AttendanceEvent>(query);
        var results = new List<AttendanceEvent>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync();
            results.AddRange(page);
        }

        return Ok(results.OrderByDescending(x => x.timestampUtc));
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, data-isolation và query-design problems.
2. Xác định performance/reliability risks dưới tenant skew và production load.
3. Giải thích vì sao tăng throughput hoặc retry vô hạn chưa chứng minh được root cause.
4. Ưu tiên findings theo severity và production impact.
5. Đề xuất corrected implementation/design, kể cả khi cần thay API contract hoặc data model.
6. Nêu cách test partition skew, throttling, pagination và tenant isolation.
7. Nêu telemetry cần theo dõi để chứng minh recommendation.

## Câu hỏi gợi mở

1. Endpoint đọc có biết `tenantId` không, và query hiện tại có thể target một logical partition không?
2. Một tenant cực lớn có thể tạo hot logical partition dù tổng throughput toàn container còn dư không?
3. `SELECT *` + đọc toàn bộ pages vào memory ảnh hưởng RU, latency và API response như thế nào?
4. `CancellationToken` có thực sự được truyền xuống Cosmos operations không?
5. Nếu `employeeId` chỉ unique trong tenant, query hiện tại có rủi ro gì ngoài performance?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **partition-aware access pattern, tenant isolation và unbounded result processing**.

### Gợi ý 2

Cosmos DB design nên bắt đầu từ access patterns và distribution. Retry không làm một partition key có skew trở nên cân bằng.

## Kết quả code review tham khảo

### Critical — Query lịch sử không scope theo tenant

**Vấn đề:** Endpoint chỉ nhận `employeeId` và query toàn container theo employee.  
**Tại sao xảy ra:** Tenant boundary không được đưa vào route/query và không có partition key constraint.  
**Ảnh hưởng production:** Nếu `employeeId` không globally unique, dữ liệu tenant khác có thể bị trả về; kể cả khi globally unique, query vẫn không thể tận dụng tenant partition key.  
**Cách sửa:** Tenant phải được xác định từ trusted authorization context hoặc resource mapping; query phải enforce tenant isolation và truyền đúng partition key khi data model hiện tại cho phép.

### High — `/tenantId` có nguy cơ hot partition với tenant skew

**Vấn đề:** Mọi write/read của một tenant lớn cùng tập trung vào một logical partition.  
**Tại sao xảy ra:** Partition key có cardinality theo tenant nhưng workload phân bố rất lệch.  
**Ảnh hưởng production:** Tenant lớn có thể trở thành bottleneck cục bộ, gây throttling/latency dù workload của tenant nhỏ vẫn nhẹ.  
**Cách sửa:** Đo distribution trước. Nếu tenant skew thực sự là root cause, đánh giá partition strategy mới dựa trên access patterns, ví dụ synthetic/hierarchical strategy phù hợp với khả năng nền tảng và query requirements. Migration phải được thiết kế, không đổi key tùy tiện trên container hiện tại.

### High — Cross-partition query cho employee history

**Vấn đề:** `GetItemQueryIterator` không cung cấp partition key và SQL query không filter `tenantId`.  
**Tại sao xảy ra:** Read API không mang partition context.  
**Ảnh hưởng production:** Query fan-out qua partitions, tăng RU và latency khi dữ liệu/container lớn.  
**Cách sửa:** Scope request theo tenant và truyền `QueryRequestOptions.PartitionKey` khi sử dụng `/tenantId`; nếu access pattern chủ đạo là employee history và tenant partition vẫn nóng, xem lại model/container strategy bằng measurement.

### High — Không giới hạn/paginate kết quả

**Vấn đề:** Endpoint đọc tất cả pages rồi giữ toàn bộ events trong memory.  
**Tại sao xảy ra:** API contract không có page size/continuation token.  
**Ảnh hưởng production:** Employee có lịch sử dài gây RU lớn, response lớn, allocation cao và latency xấu.  
**Cách sửa:** Thiết kế pagination có bounded page size; dùng continuation token theo contract phù hợp và projection chỉ lấy fields cần thiết.

### High — Cancellation không được truyền vào Cosmos calls

**Vấn đề:** Controller nhận `CancellationToken` nhưng `CreateItemAsync` và `ReadNextAsync` không sử dụng nó.  
**Tại sao xảy ra:** Token bị bỏ qua tại I/O boundary.  
**Ảnh hưởng production:** Client disconnect/timeout nhưng backend vẫn tiếp tục tiêu RU và tài nguyên.  
**Cách sửa:** Truyền `cancellationToken` vào các Cosmos operations hỗ trợ token và thiết kế timeout/retry policy có giới hạn.

### Medium — Server ghi đè timestamp nhưng tin `tenantId`/`employeeId` từ body

**Vấn đề:** Client có thể chọn tenant/resource identifiers nếu không có authorization validation ở layer khác.  
**Tại sao xảy ra:** Transport DTO được dùng trực tiếp như persistence model.  
**Ảnh hưởng production:** Có thể tạo dữ liệu sai tenant hoặc ghi attendance cho employee không được phép.  
**Cách sửa:** Lấy tenant từ trusted identity/context; authorize employee/resource; map request DTO sang persistence model server-side.

### Medium — `SELECT *` đọc nhiều dữ liệu hơn cần thiết

**Vấn đề:** Query materialize toàn document dù response có thể không cần mọi field.  
**Tại sao xảy ra:** Không có projection theo API contract.  
**Ảnh hưởng production:** Tăng payload, serialization và có thể tăng query/resource cost.  
**Cách sửa:** Projection fields cần thiết; đo RU/request trước/sau thay vì giả định mức tiết kiệm.

### Medium — Sort diễn ra trong application sau khi tải toàn bộ dữ liệu

**Vấn đề:** `OrderByDescending` chạy sau khi tất cả pages đã được tải.  
**Tại sao xảy ra:** Query không thể hiện ordering/pagination semantics.  
**Ảnh hưởng production:** Memory/CPU application tăng và pagination về sau khó ổn định.  
**Cách sửa:** Thiết kế query/index/API pagination cùng nhau; dùng server-side ordering phù hợp với data/index policy và continuation semantics sau khi xác minh execution/cost.

### Medium — Không có explicit throttling/backoff behavior ở application boundary

**Vấn đề:** Code không thể hiện SLA/timeout và behavior khi Cosmos throttles.  
**Tại sao xảy ra:** Team định giải quyết bằng “retry nhiều hơn” thay vì budget.  
**Ảnh hưởng production:** Retry storm có thể kéo dài latency và tăng áp lực.  
**Cách sửa:** Xác định bounded retry/time budget, quan sát retry-after/throttling telemetry và giảm request amplification; ưu tiên sửa access pattern/partition skew nếu đó là nguyên nhân.

## Phiên bản đề xuất

Ví dụ dưới đây giữ partition key `/tenantId` như một bước sửa ngắn hạn; nó không khẳng định đây là target partition strategy nếu measurement chứng minh tenant lớn tạo hot partition.

```csharp
public sealed record CreateAttendanceRequest(
    string EmployeeId,
    string Type);

public sealed record AttendanceDto(
    string Id,
    string EmployeeId,
    DateTime TimestampUtc,
    string Type);

[ApiController]
[Route("api/tenants/{tenantId}/attendance")]
public sealed class AttendanceController : ControllerBase
{
    private readonly Container _container;
    private readonly IAttendanceAuthorization _authorization;

    public AttendanceController(
        CosmosClient client,
        IAttendanceAuthorization authorization)
    {
        _container = client.GetContainer("hr", "attendance-events");
        _authorization = authorization;
    }

    [HttpPost]
    public async Task<IActionResult> Add(
        string tenantId,
        CreateAttendanceRequest request,
        CancellationToken ct)
    {
        if (!await _authorization.CanWriteAsync(User, tenantId, request.EmployeeId, ct))
            return Forbid();

        var item = new AttendanceEvent(
            Guid.NewGuid().ToString("N"),
            tenantId,
            request.EmployeeId,
            DateTime.UtcNow,
            request.Type);

        await _container.CreateItemAsync(
            item,
            new PartitionKey(tenantId),
            cancellationToken: ct);

        return CreatedAtAction(nameof(GetHistory),
            new { tenantId, employeeId = request.EmployeeId },
            new { item.id });
    }

    [HttpGet("employees/{employeeId}")]
    public async Task<IActionResult> GetHistory(
        string tenantId,
        string employeeId,
        [FromQuery] DateTime fromUtc,
        [FromQuery] DateTime toUtc,
        [FromQuery] string? continuationToken,
        CancellationToken ct)
    {
        if (!await _authorization.CanReadAsync(User, tenantId, employeeId, ct))
            return Forbid();

        var query = new QueryDefinition(
            "SELECT c.id, c.employeeId, c.timestampUtc, c.type " +
            "FROM c WHERE c.employeeId = @employeeId " +
            "AND c.timestampUtc >= @from AND c.timestampUtc < @to " +
            "ORDER BY c.timestampUtc DESC")
            .WithParameter("@employeeId", employeeId)
            .WithParameter("@from", fromUtc)
            .WithParameter("@to", toUtc);

        var options = new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(tenantId),
            MaxItemCount = 100
        };

        using var iterator = _container.GetItemQueryIterator<AttendanceDto>(
            query,
            continuationToken,
            options);

        if (!iterator.HasMoreResults)
            return Ok(new { items = Array.Empty<AttendanceDto>(), continuationToken = (string?)null });

        var page = await iterator.ReadNextAsync(ct);

        return Ok(new
        {
            items = page.Resource,
            continuationToken = page.ContinuationToken
        });
    }
}
```

Nếu telemetry xác nhận `/tenantId` tạo hot partition cho tenant lớn, bước tiếp theo là model lại partition strategy/container dựa trên write/read distribution, cardinality, query patterns và migration constraints. Không thể kết luận một synthetic key cụ thể là đúng khi chưa biết access patterns đầy đủ.

## Giải thích thiết kế sau khi sửa

Bản sửa buộc tenant boundary xuất hiện trong authorization và Cosmos request, loại cross-partition fan-out trong model hiện tại. API trả một page bounded thay vì toàn bộ history. Cancellation đi tới I/O boundary. DTO input không cho client quyết định mọi persistence field.

Quan trọng hơn, code fix không che architectural issue: nếu một tenant duy nhất tạo phần lớn traffic thì `/tenantId` vẫn có thể không phân phối workload đủ tốt. Quyết định repartition cần dựa trên RU/throttling theo partition key range và access pattern thực tế.

## Trade-offs

Partition-aware query giảm fan-out nhưng vẫn giữ tất cả workload tenant lớn trong cùng logical partition. Repartition có migration cost, thay đổi query contract và có thể khiến một số queries trở thành fan-out. Pagination bằng continuation token làm client phức tạp hơn nhưng tránh unbounded server work. Denormalize hoặc tạo read model riêng có thể tối ưu employee history nhưng thêm consistency/operational complexity.

## Cách kiểm thử

1. **Security/integration test:** user tenant A không thể đọc/ghi attendance của tenant B dù biết `employeeId`.
2. **Load test:** mô phỏng một tenant rất lớn và nhiều tenant nhỏ; ghi nhận throttling, RU/request và p95/p99 theo tenant/partition.
3. **Database/query test:** xác minh history query target đúng partition và continuation token không duplicate/miss records trong expected consistency model.
4. **Failure-path test:** inject throttling/transient failures, xác minh retry/time budget không tạo retry storm và cancellation dừng work.
5. **API test:** employee có lịch sử lớn chỉ trả bounded page; payload và memory không tăng theo toàn bộ history.

## Quan sát trong production

- RU consumption và normalized RU theo request/operation.
- 429/throttling rate, retry count và latency p95/p99.
- Distribution theo tenant/partition key range để phát hiện skew.
- Query page size, continuation usage và response payload size.
- Application Insights dependency telemetry/correlation cho Cosmos calls.
- API cancellation/timeouts và error rate theo endpoint.
- Alert khi một tenant/partition chiếm tỷ lệ RU bất thường hoặc throttling vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu 95% traffic thuộc một tenant duy nhất, bạn sẽ thu thập dữ liệu gì để chọn partition strategy mới?
2. Khi nào bạn chấp nhận một cross-partition query thay vì tạo read model/container khác?
3. Nếu Product cần employee history strong consistency ngay sau write, recommendation của bạn thay đổi thế nào?

# Code Review Challenge 2 — Kubernetes rollout báo healthy nhưng Pod mới crash và nhận traffic quá sớm

**Chủ đề:** Kubernetes, ASP.NET Core hosting, health checks, configuration, Secrets, resource management, rolling deployment  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core REST API trước đây chạy trên Azure App Service on Linux, nay team đang **đánh giá Kubernetes như một hosting alternative**. Đây chưa phải kinh nghiệm production được giả định và Kubernetes chưa được chọn làm target bắt buộc.

Trong test environment, Deployment có 3 replicas. Sau rollout, một số Pod nhận traffic khi application vẫn đang warm up; vài Pod restart liên tục lúc downstream SQL chậm; một lần khác rollout tạo Pod `Pending`/OOM-like behavior tùy node. Team cũng phát hiện connection string được commit trực tiếp trong manifest.

Developer cho rằng dùng cùng endpoint `/health` cho cả liveness và readiness là đơn giản nhất, và bỏ resource requests/limits giúp scheduler “linh hoạt hơn”.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### Critical — Secret được hard-code và commit trong manifest

**Vấn đề:** Database credential nằm plaintext trong repository/manifests.  
**Tại sao xảy ra:** Configuration và secret management không được tách khỏi deployable manifest.  
**Ảnh hưởng production:** Bất kỳ ai/process có quyền đọc repo/history/artifact có thể lấy credential; xóa dòng hiện tại không xóa secret khỏi Git history.  
**Cách sửa:** Rotate credential ngay khi exposure được xác nhận; dùng Kubernetes Secret hoặc external secret/identity mechanism phù hợp với platform, RBAC/least privilege và encryption controls. Không commit raw secret.

### High — Liveness phụ thuộc cùng health endpoint với readiness

**Vấn đề:** Nếu `/health` fail vì SQL/downstream dependency, liveness có thể fail và Kubernetes restart process vẫn đang khỏe.  
**Tại sao xảy ra:** Process health và ability-to-serve-current-traffic bị đồng nhất.  
**Ảnh hưởng production:** Dependency outage có thể tạo restart storm, mất warm state và làm recovery chậm hơn.  
**Cách sửa:** Liveness nên phản ánh process có cần restart hay không; readiness có thể phản ánh khả năng nhận traffic theo dependency policy. Thiết kế health checks theo failure semantics, không chỉ reuse một aggregate endpoint.

### High — Readiness có thể mở quá sớm trong startup/warm-up

**Vấn đề:** Probe bắt đầu sau 1 giây nhưng không có startup strategy thể hiện thời gian initialization thực tế.  
**Tại sao xảy ra:** Fixed delay được dùng thay cho explicit startup/readiness behavior.  
**Ảnh hưởng production:** Pod mới nhận traffic trước khi caches/config/model/migrations hoặc initialization cần thiết hoàn tất.  
**Cách sửa:** Application readiness chỉ success khi thực sự sẵn sàng; cân nhắc `startupProbe` nếu startup có thể dài/biến động để tránh liveness can thiệp quá sớm.

### High — Mutable `latest` làm rollout/rollback không reproducible

**Vấn đề:** Manifest không pin một immutable application version/digest.  
**Tại sao xảy ra:** Tag mutable được dùng làm deployment identity.  
**Ảnh hưởng production:** Cùng manifest có thể chạy image bytes khác nhau; khó audit, rollback và correlate incident với build.  
**Cách sửa:** Deploy immutable version tag và/hoặc digest từ CI/CD; record build/commit version trong telemetry.

### High — Không khai báo resource requests/limits

**Vấn đề:** Scheduler và runtime không có declared CPU/memory expectations/bounds cho workload.  
**Tại sao xảy ra:** Team xem resource policy là restriction thay vì scheduling/capacity signal.  
**Ảnh hưởng production:** Placement/capacity khó dự đoán; contention tăng; memory behavior và eviction/OOM risk khó quản lý.  
**Cách sửa:** Đo CPU/memory dưới representative load rồi đặt requests/limits phù hợp; theo dõi throttling/OOM/eviction và tune bằng evidence.

### Medium — Rollout strategy không thể hiện availability requirement

**Vấn đề:** Deployment dựa vào defaults mà không mô tả `maxUnavailable`/`maxSurge` theo SLO/capacity.  
**Tại sao xảy ra:** Release safety chưa được thiết kế như một requirement.  
**Ảnh hưởng production:** Với capacity sát ngưỡng hoặc startup chậm, rollout có thể giảm available capacity ngoài kỳ vọng.  
**Cách sửa:** Chọn rolling strategy dựa trên capacity/SLO và kiểm thử deployment under load; không copy giá trị cố định nếu chưa biết headroom.

### Medium — Probe thresholds/timeouts không được thiết kế theo latency distribution

**Vấn đề:** Chỉ có period/delay; failure behavior dựa nhiều vào defaults và tần suất dày.  
**Tại sao xảy ra:** Probe configuration không dựa trên startup/response measurements.  
**Ảnh hưởng production:** Transient slowdown có thể làm Pod flapping hoặc traffic churn.  
**Cách sửa:** Chọn timeout/failure threshold/period dựa trên measured behavior và desired detection time.

### Medium — Không thể hiện graceful shutdown

**Vấn đề:** Manifest không cho thấy termination budget và application behavior khi Pod bị terminate trong rollout.  
**Tại sao xảy ra:** Chỉ tập trung startup/probes.  
**Ảnh hưởng production:** In-flight requests/background work có thể bị cắt khi rollout/scale down nếu application cần thêm thời gian để drain.  
**Cách sửa:** Xác minh ASP.NET Core shutdown/cancellation behavior, termination grace phù hợp và readiness/draining strategy nếu workload yêu cầu.

### Low — Service exposure/network boundary chưa đủ thông tin

**Vấn đề:** Service selector/port hợp lệ ở mức cơ bản nhưng scenario không cho biết ingress/TLS/network policy.  
**Tại sao xảy ra:** Snippet chỉ thể hiện internal Service.  
**Ảnh hưởng production:** Không thể kết luận security boundary hoàn chỉnh.  
**Cách sửa:** Xác minh ingress/TLS/auth/network policy và service type trong architecture thực tế; không invent rằng chúng đang thiếu nếu được quản lý ở layer khác.

## Phiên bản đề xuất

Manifest dưới đây minh họa các boundary quan trọng. Giá trị resources/probe thresholds chỉ là starting point cần được tune bằng measurement, không phải production sizing mặc định.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: employee-api
  template:
    metadata:
      labels:
        app: employee-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example.com/employee-api:2026.09.23-abc123
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__MainDb
              valueFrom:
                secretKeyRef:
                  name: employee-api-db
                  key: connection-string
            - name: ASPNETCORE_ENVIRONMENT
              value: "Production"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: employee-api
spec:
  selector:
    app: employee-api
  ports:
    - port: 80
      targetPort: 8080
```

`employee-api-db` không nên được hiểu là lời khuyên commit một `Secret` chứa base64 credential vào Git. Secret source/rotation phải theo platform security model; nếu Azure identity/Managed Identity-equivalent integration phù hợp với hosting architecture, passwordless identity có thể giảm secret lifecycle burden.

## Giải thích thiết kế sau khi sửa

Startup, liveness và readiness có mục tiêu khác nhau. Startup bảo vệ application trong giai đoạn initialization; liveness chỉ nên yêu cầu restart khi process không thể tự phục hồi; readiness điều khiển việc nhận traffic. Dependency như SQL có thể ảnh hưởng readiness tùy business semantics nhưng không nên mặc định làm liveness fail.

Image version immutable giúp deployment audit/rollback deterministic. Resource requests cung cấp scheduling signal; limits phải được tune cẩn thận vì CPU/memory behavior khác nhau. Secret được đưa ra khỏi manifest và credential đã lộ phải rotate, không chỉ di chuyển.

## Trade-offs

Tách health endpoints tăng code/configuration và yêu cầu team hiểu dependency semantics. Readiness phụ thuộc SQL có thể bảo vệ request path nhưng khi toàn bộ replicas cùng mark unready trong một transient DB outage, traffic behavior cần được hiểu; đôi khi app có degraded mode tốt hơn. Memory limit quá thấp gây OOM; CPU limit không phù hợp có thể throttle. `maxUnavailable: 0` cần capacity headroom cho surge Pod. Kubernetes cũng thêm operational complexity; nếu App Service đã đáp ứng requirements, team cần chứng minh lợi ích trước khi migrate.

## Cách kiểm thử

1. **Deployment validation:** rollout image mới dưới representative load, xác minh Pod chưa nhận traffic trước readiness và rollback về immutable image cũ hoạt động.
2. **Failure-path test:** làm SQL chậm/unavailable; xác minh readiness/degraded behavior đúng nhưng healthy process không rơi vào liveness restart loop.
3. **Startup test:** kéo dài initialization có kiểm soát; `startupProbe` cho đủ budget và liveness chỉ bắt đầu sau startup success.
4. **Load/resource test:** đo CPU/memory, GC và request p95/p99; xác minh requests/limits không gây throttling/OOM bất ngờ.
5. **Security/deployment test:** rotate DB credential/secret source, xác minh rollout nhận secret mới theo expected mechanism và credential cũ không còn usable.

## Quan sát trong production

- Pod restart count/reason, OOMKilled, eviction và pending duration.
- Readiness/liveness/startup probe failures theo Pod/version.
- CPU/memory working set, CPU throttling và node pressure.
- Available replicas trong rollout, rollout duration và failed deployments.
- ASP.NET Core request rate/error/p95/p99 và Application Insights dependency telemetry.
- Build/image version trong logs/traces để correlate regression.
- SQL dependency availability/latency tách biệt với process-health signals.
- Alert cho restart loop, unavailable replicas và resource saturation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL unavailable 30 giây, readiness nên fail hay API nên tiếp tục nhận một số loại request? Bạn cần requirement nào để quyết định?
2. Khi nào Kubernetes mang lại đủ lợi ích để justify complexity so với Azure App Service cho API này?
3. Bạn sẽ chọn CPU/memory requests và limits ban đầu dựa trên dữ liệu nào thay vì copy từ manifest khác?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB partitioning phải được thiết kế từ access pattern và workload distribution; partition key có vẻ hợp lý về domain vẫn có thể tạo skew/hot partition.
- Tenant isolation là correctness/security boundary, không chỉ là query optimization.
- Pagination và cancellation là production controls quan trọng cho database-backed APIs; retry không thay thế việc sửa access pattern.
- Kubernetes readiness, liveness và startup probes có failure semantics khác nhau; dùng cùng một dependency-heavy health endpoint cho mọi probe có thể tạo restart storm.
- Immutable deployment artifacts, secret lifecycle và measured resource policy là phần của release safety.

## Mẫu tư duy cần nhớ

- Đo distribution trước khi thay partition strategy hoặc mua thêm capacity.
- Scope data access bằng trusted authorization boundary, không chỉ bằng client-supplied identifiers.
- Bound work: pagination, timeout, cancellation và retry budget phải đi cùng nhau.
- Health check phải phản ánh hành động mà platform sẽ thực hiện khi check fail.
- Deployment phải reproducible và rollback được; mutable artifacts làm incident khó điều tra.
