# Câu 1 — `ArrayPool<byte>` làm response bị corrupt và lẫn dữ liệu giữa các request

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#, .NET memory management, `ArrayPool<T>`, async/await, ASP.NET Core streaming, buffer lifetime, cancellation, production debugging, security

## Bối cảnh

Một ASP.NET Core endpoint proxy file từ một internal document service về client. Để giảm allocations và áp lực GC, team thay `new byte[]` bằng `ArrayPool<byte>.Shared`.

Code rút gọn:

```csharp
public async Task ProxyDocumentAsync(
    Stream source,
    HttpResponse response,
    CancellationToken cancellationToken)
{
    while (true)
    {
        var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

        var read = await source.ReadAsync(
            buffer.AsMemory(0, buffer.Length),
            cancellationToken);

        if (read == 0)
        {
            ArrayPool<byte>.Shared.Return(buffer);
            break;
        }

        var pendingWrite = response.Body.WriteAsync(
            buffer.AsMemory(0, read),
            cancellationToken);

        ArrayPool<byte>.Shared.Return(buffer);

        await pendingWrite;
    }
}
```

Ở local và staging, endpoint gần như luôn đúng. Khi production có nhiều concurrent downloads, team quan sát các symptom hiếm nhưng nghiêm trọng:

- một số PDF bị corrupt ở giữa file;
- checksum phía client đôi khi không khớp source;
- lỗi gần như biến mất nếu thay pooled buffer bằng `new byte[64 * 1024]`;
- tăng latency của network làm tỷ lệ lỗi tăng;
- có một security report cho rằng một response có vài bytes trông giống dữ liệu của request khác;
- memory allocation giảm rõ sau optimization nên team không muốn bỏ pooling ngay;
- một developer cho rằng `WriteAsync` đã được gọi rồi nên runtime phải “copy buffer ngay lập tức”;
- developer khác đề xuất gọi `Array.Clear` trước khi `Return` nhưng vẫn giữ thứ tự hiện tại.

## Câu hỏi chính

Hãy giải thích chính xác ownership/lifetime của buffer trong đoạn code này và vì sao lỗi chỉ dễ xuất hiện dưới concurrency hoặc slow network. `ArrayPool<T>` đảm bảo điều gì và không đảm bảo điều gì? `WriteAsync` có quyền giữ reference tới memory đến khi nào? Hãy đề xuất phiên bản đúng, đồng thời phân tích cancellation, exception path, clearing sensitive buffers, backpressure và cách kiểm thử để tái hiện bug một cách deterministic.

## Câu hỏi làm rõ nên cân nhắc

1. `response.Body` là `Stream` nào trong production, và `WriteAsync` thường complete synchronously hay asynchronously?
2. Nội dung document có được xem là sensitive data không, và threat model có yêu cầu xóa buffer trước khi trả pool không?
3. Endpoint có thể proxy file rất lớn hoặc nhiều downloads đồng thời đến mức nào?
4. Client disconnect/cancellation hiện được propagate tới source stream và response write ra sao?
5. Có middleware compression/encryption nào có thể giữ hoặc transform buffer sau `WriteAsync` không?

## Gợi ý tư duy

### Gợi ý 1

`Rent` cho code quyền sử dụng tạm thời buffer; `Return` kết thúc quyền sở hữu đó. Sau `Return`, hãy giả định code khác có thể rent và mutate cùng array ngay lập tức.

### Gợi ý 2

Một async operation nhận `Memory<byte>` không có nghĩa dữ liệu đã được copy tại thời điểm method trả về `ValueTask`/`Task`. Buffer phải còn hợp lệ cho đến khi operation hoàn tất.

### Gợi ý 3

Optimization về allocations có thể biến thành correctness/security bug nếu ownership không rõ. Đừng benchmark chỉ throughput; hãy test lifetime invariants dưới scheduling bất lợi.

## Cấu trúc trả lời đề xuất

1. Xác định lifecycle của một rented buffer.
2. Vẽ timeline `ReadAsync` → `WriteAsync` → `Return` → reuse bởi request khác → write hoàn tất.
3. Giải thích vì sao low load che giấu bug.
4. Phân biệt pooling với clearing/copying guarantees.
5. Viết lại code với `try/finally` và await đúng vị trí.
6. Xử lý EOF, exception và cancellation.
7. Quyết định khi nào dùng `clearArray: true`.
8. Phân tích throughput/backpressure và số buffer đang outstanding.
9. Thiết kế deterministic concurrency test.
10. Xác định telemetry phù hợp mà không log sensitive payload.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Sau `ArrayPool<byte>.Shared.Return(buffer)`, caller không còn quyền đọc/ghi buffer; pool có thể giao lại array đó cho renter khác.
- `response.Body.WriteAsync(buffer.AsMemory(...))` có thể hoàn tất asynchronously và tiếp tục sử dụng memory cho đến khi returned async operation hoàn tất.
- Vì code trả buffer trước `await pendingWrite`, một request khác có thể rent và overwrite array trong khi response cũ vẫn đang write.
- Bug dễ bị che ở local nếu `WriteAsync` thường complete nhanh/synchronously hoặc concurrency thấp.
- Fix cơ bản là `await WriteAsync` trước khi `Return` buffer.
- Buffer phải được `Return` trong `finally` để exception/cancellation không làm leak rental.
- Chỉ write vùng `[0, read)`; phần còn lại của rented array có thể chứa dữ liệu cũ và không được coi là initialized.

### Điểm cộng

- `ArrayPool<T>` không hứa rằng array được zero-initialized khi `Rent`; size trả về có thể lớn hơn minimum requested length.
- `Return(buffer, clearArray: true)` có thể hữu ích cho sensitive data nhưng có CPU cost; đây là security/performance trade-off, không phải fix cho use-after-return.
- Không giữ nhiều pooled buffers outstanding không cần thiết; một read → awaited write loop tự tạo backpressure hợp lý.
- Dùng `CopyToAsync` có thể là lựa chọn đơn giản hơn nếu framework implementation đáp ứng throughput/ownership requirement; custom pooling chỉ nên giữ khi đo được lợi ích.
- Cancellation từ client nên được propagate và source/response resources cần dispose theo ownership contract.

### Senior+

- Nhận ra bug là dạng ownership violation/use-after-return ở managed memory: GC safety không đồng nghĩa logical lifetime safety.
- Có thể dùng fake `Stream` whose `WriteAsync` deliberately blocks trước khi consume supplied memory để tái hiện deterministic, thay vì stress test ngẫu nhiên.
- Tách confidentiality risk khỏi corruption risk: pooled memory reuse có thể khiến bytes của operation khác xuất hiện nếu lifecycle sai; clearing chỉ giảm residual-data risk, không sửa concurrent mutation.
- Không tối ưu bằng cách queue nhiều writes cùng trỏ vào cùng buffer nếu chưa await/copy; nếu pipeline nhiều buffers, mỗi in-flight operation phải sở hữu buffer riêng đến completion.
- Benchmark cả allocations, throughput, p95/p99 latency, CPU và GC sau khi sửa.

## Hướng giải quyết tham khảo

Vấn đề không nằm ở việc `ArrayPool<T>` “không thread-safe”. Shared pool được thiết kế cho concurrent access. Vấn đề là caller vi phạm ownership contract.

Timeline có thể như sau:

```text
Request A: Rent(array #7)
Request A: Read bytes A vào array #7
Request A: gọi WriteAsync(array #7) -> write chưa hoàn tất
Request A: Return(array #7)
Request B: Rent(...) -> nhận lại array #7
Request B: ghi bytes B vào array #7
Request A: transport tiếp tục consume array #7
=> response A chứa bytes B / corrupt
```

Nếu network nhanh, `WriteAsync` có thể complete ngay hoặc transport consume dữ liệu trước khi buffer được reuse, nên bug trông như “không tồn tại”. Slow client/network làm async write kéo dài và mở rộng race window.

Phiên bản đơn giản, đúng ownership hơn:

```csharp
public async Task ProxyDocumentAsync(
    Stream source,
    HttpResponse response,
    CancellationToken cancellationToken)
{
    var buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);

    try
    {
        while (true)
        {
            var read = await source.ReadAsync(
                buffer.AsMemory(0, buffer.Length),
                cancellationToken);

            if (read == 0)
                break;

            await response.Body.WriteAsync(
                buffer.AsMemory(0, read),
                cancellationToken);
        }
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(
            buffer,
            clearArray: false);
    }
}
```

Nếu document data rất nhạy cảm và reuse residual data nằm trong threat model, có thể chọn `clearArray: true` hoặc chủ động clear relevant region trước return. Nhưng đó là decision cần benchmark; `clearArray: true` không thay thế requirement await trước return.

Một buffer cho cả loop thường đơn giản và giảm Rent/Return churn. Vì mỗi write được awaited trước read tiếp theo, buffer chỉ được mutate khi transport đã hoàn tất với nó. Đây cũng là backpressure tự nhiên: slow client làm loop chậm lại thay vì đọc cả source vào memory.

Nếu muốn tăng throughput bằng pipelining, thiết kế phải thay đổi ownership: mỗi write in-flight có buffer riêng hoặc copy dữ liệu vào memory có lifetime độc lập. Không được tái sử dụng cùng memory cho nhiều unfinished operations.

Deterministic test tốt hơn stress-only test. Tạo một custom destination stream mà `WriteAsync` báo đã bắt đầu nhưng chờ một `TaskCompletionSource` trước khi copy/inspect memory. Sau khi endpoint gọi `Return`, test rent buffer khác từ cùng pool hoặc trực tiếp orchestrate mutation, rồi mới release destination stream. Với abstraction tốt, test có thể inject `ArrayPool<byte>` fake để biết chính xác buffer đã được returned và reused. Test phải fail ở implementation cũ và pass ở implementation mới.

Production telemetry không nên log raw buffer. Theo dõi response failures, client aborts, bytes transferred, duration, checksum mismatch nếu domain có checksum, allocations/GC và concurrency. Nếu có security incident nghi ngờ cross-request bytes, preserve correlation metadata và artifact hợp lệ thay vì tạo thêm sensitive logging.

## Mẫu trả lời trong phỏng vấn

“Lỗi ở đây là lifetime, không phải thread safety của `ArrayPool`. Sau khi `Return`, code phải coi buffer không còn thuộc về mình. `WriteAsync` nhận `Memory<byte>` và có thể dùng memory đó cho tới khi async operation complete. Đoạn code trả buffer trước khi await, nên request khác có thể rent cùng array và overwrite trong lúc transport của request trước vẫn đang đọc. Slow network chỉ làm race window lớn hơn.

Tôi sẽ rent một buffer, giữ ownership suốt loop, await từng write rồi mới reuse, và return trong `finally`. Nếu dữ liệu nhạy cảm, tôi đánh giá `clearArray: true` hoặc clear vùng đã dùng, nhưng clearing không sửa use-after-return. Tôi cũng propagate cancellation và giữ one-buffer-at-a-time để có backpressure.

Để test, tôi không dựa vào load ngẫu nhiên. Tôi dùng fake destination stream cố tình block `WriteAsync`, sau đó ép buffer được reuse/mutate trước khi cho write hoàn tất. Như vậy implementation cũ fail deterministic, implementation sửa sẽ không thể return buffer khi write còn in-flight.”

## Câu hỏi đào sâu

1. Nếu muốn có 4 writes in-flight để tăng throughput, bạn sẽ thiết kế ownership của pooled buffers thế nào để vẫn đúng?
2. Khi nào `clearArray: true` đáng trả CPU cost, và tại sao nó không thể được coi là fix cho bug hiện tại?
3. Nếu benchmark cho thấy `ArrayPool<byte>` chỉ giảm allocations rất ít nhưng làm code phức tạp hơn đáng kể, bạn có giữ optimization này không?

## Lỗi trả lời thường gặp

- Cho rằng `WriteAsync` luôn copy dữ liệu ngay khi được gọi.
- Nghĩ `ArrayPool<T>` tự clear buffer khi `Rent` hoặc `Return`.
- Chỉ thêm `Array.Clear` nhưng vẫn return trước khi write hoàn tất.
- Quên return buffer khi `ReadAsync`/`WriteAsync` throw hoặc bị cancel.
- Queue nhiều writes dùng cùng buffer mà không hiểu lifetime.

## Thang điểm 0–10

- **0–2:** Không nhận ra use-after-return/lifetime violation.
- **3–4:** Biết cần đổi thứ tự nhưng không giải thích được async buffer ownership.
- **5–6:** Fix đúng với await + `finally`, hiểu pool không zero memory và có cancellation handling.
- **7–8:** Phân tích được security risk, backpressure, deterministic testing và clearing trade-off.
- **9–10:** Reasoning đầy đủ về ownership, pipelining, async completion semantics, observability và chứng minh optimization bằng benchmark production-representative.

# Câu 2 — P99 tăng vọt và `429` chỉ tập trung ở một tenant trên Azure Cosmos DB

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partitioning, RU consumption, multi-tenant design, retry, ASP.NET Core, Azure Monitor/Application Insights, performance diagnosis, incident response

## Bối cảnh

Một event platform multi-tenant dùng ASP.NET Core và Azure Cosmos DB. Container `ActivityEvents` dùng partition key `/tenantId`.

Document đơn giản:

```json
{
  "id": "evt-...",
  "tenantId": "tenant-123",
  "userId": "user-456",
  "type": "CampaignViewed",
  "occurredAt": "2026-09-14T03:00:00Z",
  "payload": { }
}
```

API có hai workload chính:

1. ghi event liên tục;
2. dashboard đọc recent events của một tenant, filter theo thời gian/type.

Hệ thống chạy ổn nhiều tháng. Sáng nay một customer lớn khởi chạy global campaign và traffic của riêng tenant đó tăng mạnh.

Symptom:

- p50 toàn API vẫn gần bình thường nhưng p99 tăng từ dưới 500 ms lên nhiều giây;
- HTTP dependency telemetry bắt đầu có nhiều request chậm và application logs ghi nhận `429` từ Cosmos SDK;
- phần lớn tenant nhỏ gần như không bị ảnh hưởng;
- tenant lớn có cả write volume và dashboard reads tăng mạnh;
- aggregate RU usage ở dashboard cấp cao nhìn chưa giống “toàn container đã cạn tuyệt đối”;
- retry count tăng và một số requests cuối cùng vẫn thành công nhưng latency rất cao;
- CPU của web app không tăng tương ứng;
- một developer muốn tăng retry count thật lớn;
- developer khác muốn scale web app từ 8 lên 20 instances;
- DBA quen SQL đề xuất tạo thêm thật nhiều indexes;
- product cần khôi phục dashboard của tenant lớn trước, nhưng không được làm các tenant còn lại xuống theo.

Bạn chưa được phép giả định hot partition là root cause cuối cùng. Nó là một hypothesis cần chứng minh cùng các khả năng khác như expensive cross-partition query, indexing/query-shape regression, SDK/network issue, throttling do capacity, hoặc một deployment regression trùng thời điểm campaign.

## Câu hỏi chính

Hãy xử lý incident này theo flow **impact → stabilize → evidence → competing hypotheses → narrow → root cause → remediation → prevention**. Bạn sẽ lấy evidence nào từ Cosmos diagnostics, Azure Monitor/Application Insights và application logs để phân biệt hot partition/capacity pressure với query/index/network/application problems? Nếu evidence xác nhận workload của một “super-tenant” tạo hotspot do partition strategy, hãy thiết kế mitigation ngắn hạn và hướng partition/data-model lâu dài, đồng thời nêu trade-offs về query fan-out, transactional boundary, migration và cost.

## Câu hỏi làm rõ nên cân nhắc

1. `429` tập trung vào operation nào: point read, query hay write, và request charge/retry-after/retry count ra sao?
2. SDK diagnostics cho thấy latency nằm ở client, network, service time hay retry/throttling?
3. Dashboard queries có luôn truyền partition key `tenantId` hay có query vô tình fan-out toàn container?
4. Provisioning mode/capacity configuration hiện tại là gì, và workload có burst theo thời gian hay duy trì lâu?
5. Một tenant lớn có thể vượt xa các tenant khác đến mức nào, và product có chấp nhận shard/bucket dữ liệu của một tenant qua nhiều logical partitions không?

## Gợi ý tư duy

### Gợi ý 1

`429` là evidence về throttling nhưng chưa nói đủ **vì sao**. Cần nhìn request charge, retries, partition-level distribution và query diagnostics.

### Gợi ý 2

Aggregate utilization có thể che mất skew. Một workload phân bố không đều có thể làm một phần của hệ thống chịu áp lực trong khi phần khác còn dư.

### Gợi ý 3

Thay partition key là data-model/operational decision lớn. Đừng chọn key mới chỉ để “chia đều writes”; phải xét query access patterns và transactional scope.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact theo tenant và endpoint.
2. Stabilize mà không làm retry storm nặng hơn.
3. Correlate request IDs với Cosmos diagnostics.
4. So sánh tenant lớn và tenant bình thường.
5. Phân tích operation type, request charge, retry count, latency và partition distribution.
6. Đặt nhiều hypotheses và loại trừ theo evidence.
7. Chọn short-term mitigation có rollback được.
8. Nếu partition hotspot được xác nhận, đánh giá data model mới.
9. Thiết kế migration/dual-read-write nếu cần.
10. Thêm load test, SLO, per-tenant guardrails và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu bằng impact và stabilization, không nhảy ngay sang redesign partition key.
- `429` thường cần xem cùng retry behavior/diagnostics; tăng retry vô hạn có thể kéo dài p99 và khuếch đại backlog.
- Scale web app không trực tiếp tăng Cosmos capacity và có thể tăng concurrency gây pressure mạnh hơn.
- Thu thập request charge, operation type, retry count, latency, query metrics/diagnostics, partition-related distribution và per-tenant throughput.
- Xác minh dashboard query có được scoped đúng partition key hay đang cross-partition/fan-out.
- So sánh before/after campaign và before/after deployment để tránh correlation bias.
- Nếu `/tenantId` làm toàn bộ super-tenant traffic dồn vào một partitioning unit không phù hợp, cần cân nhắc shard/bucket strategy dựa trên access pattern chứ không chỉ thêm RU.

### Điểm cộng

- Immediate controls: rate limit/tenant-level throttling, giảm refresh frequency, queue/buffer non-critical writes, tạm degrade expensive dashboard features, hoặc tăng capacity có kiểm soát nếu evidence cho thấy capacity là bottleneck.
- Retry phải bounded và tôn trọng service guidance/retry delay; API có latency budget nên không để SDK retry vượt quá request SLO một cách vô thức.
- Dùng point reads khi đã biết `id + partition key` thay vì query chung chung.
- Review indexing policy dựa trên query paths/write cost thay vì “index everything”.
- Có per-tenant quota/admission control để một tenant không phá SLO chung.

### Senior+

- Phân biệt symptom `429` do provisioned capacity/general pressure với skew/hotspot; không kết luận chỉ từ aggregate RU chart.
- Nếu shard một tenant bằng synthetic key như `tenantId|bucket`, hiểu rằng tenant-wide query có thể phải fan-out qua buckets và transactional scope bị giới hạn theo partition boundary.
- Chọn bucket dimension theo domain: time bucket, hash bucket hoặc entity group tùy query/retention/ordering needs; không dùng random shard count mà không có migration strategy.
- Đề xuất incremental migration với schema/version marker, dual-write hoặc backfill tùy downtime/cost tolerance.
- Thiết kế observability per tenant/per operation để phát hiện skew trước khi thành incident.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng câu “partition key sai”. Trước tiên xác định blast radius: tenant nào, endpoint nào, tỷ lệ lỗi thực, p95/p99 và business operation bị ảnh hưởng. Nếu chỉ dashboard của super-tenant xuống, có thể degrade riêng tenant/feature đó thay vì tác động toàn platform.

Immediate stabilization có thể gồm:

- giảm dashboard auto-refresh cho tenant đang burst;
- rate-limit/admission-control theo tenant;
- queue hoặc làm chậm non-critical event producers nếu business cho phép;
- tạm tắt expensive aggregate query;
- tăng capacity tạm thời nếu telemetry xác nhận service đang bị capacity pressure và cost được chấp nhận.

Tôi sẽ tránh tăng retry count vô hạn. Retry làm request “eventually succeed” nhưng có thể biến throttling thành latency/backlog amplification. Cần theo dõi retry count và latency budget end-to-end.

Evidence cần correlate theo từng request:

```text
tenantId
operation type
request charge
status/substatus
retry count
end-to-end duration
Cosmos diagnostics summary
query shape/query metrics
application version
request correlation id
```

Không log toàn payload nếu không cần.

Competing hypotheses:

1. **Hot partition / skew:** `429` và latency tập trung tenant lớn, partition-level pressure tương ứng campaign burst.
2. **Cross-partition query:** một code path mới bỏ partition key hoặc filter không phù hợp, làm RU/query tăng đột biến.
3. **Index/query regression:** query mới scan nhiều hoặc index policy thay đổi, request charge tăng trên cả tenant hoặc specific operation.
4. **SDK/network issue:** diagnostics cho thấy client/network latency, connection issue hoặc timeout hơn là service throttling.
5. **General capacity shortage:** nhiều tenants/operations cùng throttle, không chỉ một super-tenant.
6. **Deployment regression:** thời điểm trùng campaign nhưng query/serialization/retry policy mới mới là nguyên nhân.

Nếu diagnostics cho thấy request charge/query shape không đổi, 429/retries tập trung một tenant và workload của tenant đó dồn vào cùng partition key boundary, hotspot hypothesis mạnh lên.

Short-term, capacity increase có thể mua thời gian nhưng không nên được coi là permanent fix nếu một tenant tiếp tục tăng không giới hạn. Tenant-level admission control bảo vệ fair-share SLO cho các tenants khác.

Long-term, cần xem lại access patterns. `/tenantId` rất tiện vì mọi tenant query scoped rõ và transactional operations trong tenant có boundary tự nhiên. Nhưng một “super-tenant” có thể cần phân tán dữ liệu thêm. Một synthetic partition key ví dụ:

```text
tenant-123|2026-09
```

hoặc:

```text
tenant-123|bucket-03
```

có thể chia traffic, nhưng đổi lại tenant-wide dashboard phải query nhiều buckets, ordering/aggregation phức tạp hơn, và transaction chỉ nằm trong một partition boundary. Time bucket phù hợp nếu query chủ yếu theo recent time windows; hash bucket phù hợp hơn cho write distribution nhưng read fan-out có thể lớn. Phải chọn theo workload thực.

Migration cũng là một project riêng: container mới/partition model mới, backfill theo batches, dual-write hoặc change feed/event-based synchronization nếu phù hợp, compare counts/checksums, rồi gradually switch reads. Không nên “đổi partition key trực tiếp trong place” như một trivial schema migration.

Testing cần workload skew representative: hàng trăm tenants nhỏ + một super-tenant burst, concurrent reads/writes, và kiểm tra p95/p99/retry count/request charge theo tenant. Monitoring phải cảnh báo không chỉ aggregate RU mà cả throttling/retry skew theo tenant/partition/operation và dashboard latency SLO.

## Mẫu trả lời trong phỏng vấn

“429 cho tôi biết có throttling nhưng chưa chứng minh partition key là nguyên nhân. Tôi đầu tiên đo impact theo tenant/endpoint, giảm refresh hoặc rate-limit tenant đang burst để giữ SLO chung, và tránh tăng retry vô hạn.

Sau đó tôi correlate App Insights với Cosmos diagnostics: operation type, request charge, retries, latency, query metrics và partition distribution. Tôi kiểm tra dashboard có truyền partition key hay fan-out, so tenant lớn với tenant nhỏ và đối chiếu deployment timeline. Nếu chỉ super-tenant throttle với query shape bình thường và pressure tập trung đúng partition boundary, hotspot mới được xác nhận.

Ngắn hạn có thể tăng capacity hoặc throttle riêng tenant. Dài hạn, nếu `/tenantId` không scale cho super-tenant, tôi cân nhắc synthetic bucketing theo time/hash dựa trên access pattern. Nhưng tôi nêu rõ trade-off: tenant-wide reads fan-out hơn, transaction boundary hẹp hơn và cần migration container/backfill. Tôi cũng thêm per-tenant guardrails và monitoring để một customer không kéo p99 của toàn platform xuống.”

## Câu hỏi đào sâu

1. Nếu tăng capacity ngay lập tức làm incident hết, evidence nào vẫn cần thu thập trước khi kết luận không cần redesign partition model?
2. Bạn sẽ chọn time-bucket hay hash-bucket cho một tenant có write-heavy workload nhưng dashboard thường đọc 24 giờ gần nhất? Trade-off chính là gì?
3. Nếu product yêu cầu transaction atomic trên toàn bộ dữ liệu của một tenant, bạn có vẫn shard tenant đó qua nhiều partition boundaries không, hay thay đổi requirement/architecture thế nào?

## Lỗi trả lời thường gặp

- Thấy `429` là kết luận ngay “mua thêm RU”.
- Scale web app để chữa Cosmos throttling mà không xét concurrency amplification.
- Tăng retry count thật lớn và bỏ qua p99/backlog.
- Đổi partition key chỉ dựa trên write distribution mà không xem query/transaction patterns.
- Chỉ xem aggregate metrics, không xem per-tenant/per-operation skew.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất scale hoặc retry, không có evidence-driven diagnosis.
- **3–4:** Biết hot partition nhưng coi đó là root cause mặc định.
- **5–6:** Có competing hypotheses, Cosmos diagnostics, stabilization và short-term mitigation hợp lý.
- **7–8:** Phân tích được partition redesign, query fan-out, transaction boundary, migration và per-tenant guardrails.
- **9–10:** Incident reasoning hoàn chỉnh từ impact tới prevention, có SLO/cost/retry trade-offs, migration strategy và observability đủ để chứng minh/loại trừ từng hypothesis.

# Câu 3 — Thiết kế Product Detail Platform với Optimizely CMS và composable commerce

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 40–50 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, composable commerce, e-commerce, REST APIs, search, caching, frontend SSR, SEO, resilience, observability, ownership boundaries, external integrations

## Bối cảnh

Một retailer đang xây lại website thương mại điện tử toàn cầu. Hiện hệ thống là một ASP.NET application lớn, trong đó CMS, catalog, pricing, stock và reviews bị trộn logic với nhau.

Target platform có các thành phần/business ownership sau:

- **Optimizely CMS**: editorial pages, campaign content, hero blocks, buying guides, localized marketing content;
- **Product Catalog / PIM**: SKU, technical attributes, taxonomy, media references;
- **Pricing service**: giá theo market/customer segment, thay đổi thường xuyên;
- **Inventory service**: stock/availability gần real time;
- **Search**: product discovery/filter/autocomplete;
- **Reviews provider**: third-party API;
- **Frontend**: React hoặc Vue với server-side rendering cho product pages;
- 10 locales/markets;
- peak campaign traffic cao gấp nhiều lần ngày thường.

Business requirements:

- editor có thể publish campaign/product storytelling mà không cần deploy code;
- product page phải render SEO-critical content tốt cho crawler;
- catalog attributes có thể stale vài phút, nhưng price/availability cần fresh hơn;
- reviews provider outage không được làm toàn product page fail;
- nếu inventory timeout, user vẫn nên xem được product nhưng phải tránh hiển thị stock sai gây oversell;
- canonical URL, metadata và structured data phải nhất quán;
- preview trong CMS cần gần với production rendering;
- platform team nhỏ, không muốn vận hành hàng chục microservices nếu không cần;
- security không cho browser giữ credentials của pricing/reviews providers.

Một nhóm đề xuất copy toàn bộ product data vào CMS để editor có “một source duy nhất”. Nhóm khác muốn frontend gọi trực tiếp CMS, PIM, pricing, inventory và reviews từ browser. Nhóm thứ ba muốn tách mỗi integration thành một microservice riêng và dùng event-driven architecture ở mọi nơi.

## Câu hỏi chính

Hãy thiết kế architecture cho Product Detail Page và surrounding content platform. Xác định source of truth và ownership boundaries; cách CMS tham chiếu product; nơi composition xảy ra; read path synchronous/asynchronous; cache policy theo từng loại dữ liệu; search indexing; SEO/SSR; degraded behavior khi dependency lỗi; preview/editorial workflow; security; observability; deployment và migration từ monolith. Bạn phải chỉ ra trade-offs và giải thích vì sao complexity bạn chọn là đủ — không được mặc định microservices/CQRS/event-driven là đáp án tốt hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Giá có personalized theo authenticated customer hay chỉ theo market/segment?
2. Inventory cần freshness/SLO cụ thể bao nhiêu và business xử lý “unknown availability” thế nào?
3. PIM có stable immutable product identifier dùng xuyên CMS/search/pricing không?
4. Editors cần chỉnh product attributes hay chỉ editorial enrichment/storytelling quanh product?
5. Search cần phản ánh publish state của CMS và catalog update với độ trễ chấp nhận được bao lâu?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu từ **data ownership**: CMS không nên trở thành source of truth cho domain mà team khác sở hữu chỉ vì editor UI tiện hơn.

### Gợi ý 2

Không phải dữ liệu nào trên PDP cũng có cùng freshness/caching requirement. Hãy phân loại stable, semi-stable và volatile data.

### Gợi ý 3

Failure isolation là feature của architecture. Reviews outage, search lag và inventory timeout phải có degraded behavior đã thiết kế trước.

## Cấu trúc trả lời đề xuất

1. Chốt business/SLO/freshness/security assumptions.
2. Xác định source of truth cho từng data type.
3. Thiết kế CMS content model và product references.
4. Chọn composition layer/BFF/server rendering flow.
5. Phân loại synchronous vs asynchronous integration.
6. Thiết kế cache/freshness/invalidation.
7. Thiết kế search read model/indexing.
8. Xử lý SEO, localization và CMS preview.
9. Thiết kế failure/degraded modes + observability.
10. Đưa ra migration/deployment path từ monolith với complexity vừa đủ.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CMS sở hữu editorial content; PIM/catalog sở hữu product facts. CMS nên reference stable product IDs thay vì copy product domain làm source of truth mới.
- Pricing/inventory có freshness và correctness semantics khác editorial/catalog, nên cache/read policy phải khác.
- Browser không nên trực tiếp giữ provider secrets hoặc tự orchestrate nhiều backend dependencies nếu điều đó làm security/reliability khó kiểm soát.
- Có server-side/BFF/composition layer để lấy CMS + catalog + dynamic commerce data theo contract rõ.
- Third-party reviews failure không làm core PDP fail; inventory unknown phải hiển thị/degrade theo business-safe behavior.
- SEO-critical fields, canonical URL, metadata/structured data và localized content phải render server-side hoặc bằng mechanism crawler-compatible nhất quán.
- Search thường là derived read model, không phải source of truth; indexing có eventual-consistency contract rõ.

### Điểm cộng

- Cache editorial content/catalog tương đối lâu hơn; price/inventory dùng TTL ngắn hoặc bypass/cache semantics riêng theo contract.
- Không cache personalized price trong public/shared cache nếu key không bao gồm authorization/segment dimensions an toàn.
- Reviews có timeout ngắn/circuit-breaker/fallback “temporarily unavailable”.
- Inventory timeout không tự suy diễn “in stock”; fail closed cho purchase action nếu business cần tránh oversell.
- CMS block chứa `ProductId` + editorial override fields có governance rõ, không duplicate toàn PIM model.
- Search indexing pipeline combine catalog + selected publishable CMS fields asynchronously.

### Senior+

- Preview architecture tách preview/editorial draft source khỏi public published content; không để draft leak vào public cache/index.
- Cache key bao gồm market/locale/currency/segment dimensions cần thiết; tránh explosion bằng việc phân loại data thay vì nhét mọi dimension vào một mega-cache.
- Composition layer có latency budget per dependency, parallelize independent calls có kiểm soát và cancel work không còn cần.
- Có dependency-level telemetry, trace/correlation, cache hit ratio, freshness age, degraded-mode metrics và SLO cho PDP.
- Migration theo vertical slice/strangler thay vì rewrite toàn bộ monolith một lần.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng ownership, không bắt đầu bằng số lượng services.

### 1. Source of truth

- **Optimizely CMS:** campaign/editorial content, localized storytelling, placement/layout, buying guides, SEO editorial overrides khi business cho phép.
- **PIM/Catalog:** SKU/product facts, technical attributes, taxonomy, media/domain metadata.
- **Pricing:** authoritative price theo market/segment/customer semantics.
- **Inventory:** authoritative availability/stock semantics.
- **Reviews provider:** rating/reviews source, nhưng availability của provider không được trở thành availability của PDP.
- **Search:** derived index/read model phục vụ discovery; không dùng search index làm transactional source cho price/stock.

CMS product block có thể lưu stable `ProductId` và editorial fields:

```text
ProductHeroBlock
- ProductId
- EditorialHeadline
- EditorialBody
- CampaignBadge
- LayoutVariant
```

Khi render, platform resolve product facts từ catalog. Như vậy editor vẫn compose page nhưng không tạo duplicate product truth phải sync hai chiều.

### 2. Composition/read path

Tôi chọn một server-side composition/BFF trong cùng deployable ASP.NET Core application trước khi tách microservices nếu team nhỏ và scale boundaries chưa đòi hỏi khác.

PDP request có thể:

```text
SSR Frontend / Web App
      |
      v
Product Page Composition Layer
  |       |       |        |
 CMS    Catalog  Pricing  Inventory
  |
 Reviews (optional/degradable)
```

Independent calls có thể chạy song song với timeout/cancellation riêng. Nhưng composition layer không chờ mọi dependency bằng cùng budget; criticality khác nhau.

Ví dụ:

- CMS/catalog: critical để render page;
- price: critical hoặc near-critical tùy market law/business;
- inventory: critical cho CTA correctness nhưng page có thể render “availability unavailable”;
- reviews: non-critical, timeout nhanh và omit component khi lỗi.

Browser nhận một page/view model đã composition thay vì tự gọi năm providers và giữ credentials/CORS/retry logic ở client.

### 3. Cache/freshness

Không dùng một TTL cho toàn PDP object.

- editorial published content: cache tương đối lâu + purge/version theo publish;
- catalog facts: cache phút tùy update cadence;
- price: TTL rất ngắn hoặc request-time lookup tùy personalization/freshness contract;
- inventory: tương tự, ưu tiên correctness; stale stock cần explicit maximum staleness;
- reviews: cache lâu hơn nếu provider terms/UX cho phép.

Nếu price personalized, shared CDN/public cache của fully composed HTML có thể nguy hiểm. Có thể split static/anonymous shell với dynamic authenticated price fragment/API, hoặc ensure cache variance/keying chính xác. Không cache sensitive/personalized response public chỉ để đạt hit ratio.

### 4. Search

Search index là read model được build asynchronously từ catalog và selected published CMS fields. Pipeline cần idempotent updates/versioning để out-of-order events không đưa stale document trở lại. Product discovery chấp nhận eventual consistency theo explicit SLA. Price/stock không nhất thiết embed permanently vào search index nếu freshness requirement cao; có thể enrich query results hoặc index snapshot có age contract rõ.

### 5. SEO/SSR

SSR tạo canonical URL, title/meta, localized hreflang/canonical strategy và structured product data từ authoritative fields. Nếu price/availability trong structured data, freshness phải đủ đúng với policy/business contract; không render stale values chỉ vì cache tiện.

URLs nên dựa trên stable product identity + localized slug mapping; redirect strategy phải rõ khi slug đổi. Sitemap lấy published/indexable product set, không từ draft CMS content.

### 6. Preview/editorial workflow

Preview request có explicit preview context/auth, đọc draft CMS version nhưng catalog/pricing data có thể là live hoặc sandbox tùy business expectation. Preview response không đi vào public CDN/cache. UI nên cho editor thấy external dependency unavailable thay vì silently publish snapshot giả.

### 7. Failure modes

- Reviews timeout → hide reviews + emit degraded metric.
- Inventory timeout → render product content nhưng CTA disabled/“check availability later” nếu business yêu cầu tránh oversell.
- Pricing timeout → tùy jurisdiction/business, có thể hide purchase CTA thay vì dùng stale price không kiểm soát.
- CMS unavailable nhưng published cache còn valid → serve cached published content trong bounded stale policy nếu được chấp nhận.
- Catalog unavailable → cached product facts có bounded stale window hoặc return service-unavailable cho PDP nếu không thể safely render.

Timeout, retry và circuit breaking phải theo idempotency/dependency behavior, không blanket cùng một policy.

### 8. Observability

Một distributed/request trace nên cho thấy:

```text
PDP total duration
CMS duration/cache hit/content version
Catalog duration/cache hit/data age
Pricing duration/result/freshness
Inventory duration/result/freshness
Reviews duration/degraded flag
SSR duration
market/locale (không log PII không cần thiết)
```

Alert theo p95/p99 PDP, dependency error rate, degraded-mode rate, cache freshness/hit ratio và search indexing lag.

### 9. Deployment/migration

Tôi không rewrite monolith thành nhiều services ngay. Bắt đầu bằng module/boundary rõ trong existing ASP.NET solution hoặc một BFF deployable, rồi migrate vertical slices:

1. tách catalog read contract;
2. chuyển CMS product content sang stable references;
3. đưa PDP composition qua new path;
4. tách pricing/inventory adapters;
5. migrate search pipeline;
6. retire legacy path khi metrics parity đạt yêu cầu.

Chỉ tách service độc lập khi có lý do cụ thể: ownership/team autonomy, independent scaling, security boundary hoặc release cadence. Complexity phải mua được giá trị đo được.

## Mẫu trả lời trong phỏng vấn

“Tôi không copy toàn product domain vào CMS. CMS là source cho editorial content; PIM là source cho product facts; pricing và inventory giữ authority riêng. CMS block chỉ reference stable ProductId và lưu editorial enrichment.

Tôi đặt một server-side composition/BFF giữa frontend và các dependencies. Nó lấy CMS/catalog, rồi pricing/inventory theo latency budget riêng; reviews là optional. Tôi phân cache theo freshness: content/catalog có thể cache lâu hơn, price/inventory ngắn hoặc request-time. Personalized price tuyệt đối không đi vào public cache nếu key không bảo vệ đúng user/segment.

PDP dùng SSR cho canonical/meta/structured data. Search là derived read model eventual-consistent, không phải source of truth cho transactional price/stock. Khi reviews lỗi tôi degrade component; khi inventory unknown tôi không giả định in-stock.

Với team nhỏ, tôi bắt đầu modular/BFF thay vì microservices hàng loạt. Migration theo vertical slice từ monolith, đo p95/p99, dependency latency, cache age và degraded rate. Chỉ tách service khi có independent scaling/ownership/release reason thật.”

## Câu hỏi đào sâu

1. Nếu pricing personalized theo từng customer thay vì segment, bạn thay đổi SSR/CDN/cache architecture thế nào?
2. Nếu product team yêu cầu search result luôn phản ánh inventory gần real time, bạn có đưa inventory vào search index không hay compose sau search? Vì sao?
3. Nếu một architect yêu cầu tách ngay CMS adapter, Catalog, Pricing, Inventory, Reviews và Search thành sáu microservices “để future-proof”, bạn sẽ yêu cầu evidence/criteria nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- Copy toàn product domain vào CMS rồi tạo hai sources of truth.
- Để browser gọi trực tiếp mọi external provider và giữ provider credentials.
- Cache toàn PDP bằng một TTL bất kể data freshness/personalization.
- Cho reviews/inventory provider outage làm toàn page fail.
- Chọn microservices/event-driven architecture chỉ vì “scale” mà không có workload/ownership evidence.

## Thang điểm 0–10

- **0–2:** Chỉ liệt kê components, không xác định ownership/failure semantics.
- **3–4:** Có CMS/PIM separation nhưng thiếu composition/cache/freshness reasoning.
- **5–6:** Có source-of-truth rõ, BFF/SSR, per-data caching, degraded modes và search eventual consistency.
- **7–8:** Phân tích personalization/SEO/preview/security/observability và migration trade-offs đầy đủ.
- **9–10:** Architecture đơn giản nhưng có ranh giới mạnh, SLO/freshness contracts rõ, failure isolation tốt và quyết định complexity dựa trên evidence thay vì xu hướng.
