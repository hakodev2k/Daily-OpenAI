# Code Review Challenge 1 — API upload hóa đơn và ranh giới tin cậy của Blob Storage

**Chủ đề:** ASP.NET Core .NET 8, Azure Blob Storage, authorization, file streaming, security  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** khoảng 9

## Bối cảnh

Một portal quản lý chi phí cho phép nhân viên upload hóa đơn PDF/ảnh và tải lại theo mã chứng từ. API chạy trên Azure App Service, dùng Azure Blob Storage. Mỗi nhân viên thuộc một hoặc nhiều phòng ban; tài liệu chỉ được đọc bởi chủ sở hữu hoặc người có quyền duyệt đúng phòng ban. Blob container dự kiến là private. Trong giờ cao điểm có 200 request upload đồng thời; mỗi file được phép tối đa 15 MiB. Sau một bản release, bộ nhớ App Service tăng mạnh; một người dùng báo cáo có thể xem tài liệu không thuộc phòng ban của mình. Team muốn sửa mà không phá vỡ hợp đồng HTTP đang dùng.

## Đoạn code cần review

\`\`\`csharp
[ApiController]
[Route("api/expenses")]
[Authorize]
public sealed class ExpenseFilesController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly ExpenseDbContext _db;
    private readonly ILogger<ExpenseFilesController> _log;

    public ExpenseFilesController(BlobContainerClient container,
        ExpenseDbContext db, ILogger<ExpenseFilesController> log)
    {
        _container = container;
        _db = db;
        _log = log;
    }

    [HttpPost("{expenseId:guid}/attachments")]
    public async Task<IActionResult> Upload(Guid expenseId, IFormFile file)
    {
        var expense = await _db.Expenses.FindAsync(expenseId);
        if (expense is null) return NotFound();

        using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        memory.Position = 0;

        var blobName = $"{expenseId}/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);
        await blob.UploadAsync(memory, overwrite: true);

        _db.Attachments.Add(new ExpenseAttachment {
            ExpenseId = expenseId,
            BlobName = blobName,
            OriginalName = file.FileName,
            ContentType = file.ContentType
        });
        await _db.SaveChangesAsync();

        _log.LogInformation("Uploaded {File} for {Expense}",
            file.FileName, expenseId);
        return Ok(new { blobName });
    }

    [HttpGet("attachments/{attachmentId:guid}")]
    public async Task<IActionResult> Download(Guid attachmentId)
    {
        var attachment = await _db.Attachments.FindAsync(attachmentId);
        if (attachment is null) return NotFound();

        var blob = _container.GetBlobClient(attachment.BlobName);
        var result = await blob.DownloadStreamingAsync();
        return File(result.Value.Content,
            attachment.ContentType, attachment.OriginalName);
    }
}
\`\`\`

## Kết quả code review tham khảo

### Critical — Broken object-level authorization

**Vấn đề:** Chỉ có [Authorize] ở controller; Upload và Download truy xuất entity theo ID mà không kiểm tra quyền trên từng đối tượng.  
**Tại sao xảy ra:** Authentication chứng minh danh tính, không chứng minh quyền truy cập expense thuộc phòng ban khác.  
**Ảnh hưởng production:** Người có tài khoản hợp lệ và biết/đoán được ID có thể ghi hoặc đọc tài liệu trái phép. GUID không phải cơ chế authorization.  
**Cách sửa:** Áp dụng policy/authorization service theo user, department, expense và operation trước khi upload/download. Với yêu cầu không tiết lộ tồn tại tài nguyên, trả 404 thống nhất cho resource không có quyền; kiểm thử cả role và tenant boundary.

### High — Ghi đè Blob do dùng tên file của client

**Vấn đề:** BlobName ghép từ expenseId và file.FileName, kết hợp overwrite: true.  
**Tại sao xảy ra:** Tên file do client điều khiển, không bảo đảm duy nhất, có thể chứa ký tự/path segment không mong muốn.  
**Ảnh hưởng production:** Upload cùng tên ghi đè nội dung trước đó; DB có thể chứa nhiều attachment trỏ về cùng một Blob.  
**Cách sửa:** Sinh storage key ngẫu nhiên phía server, upload với overwrite: false; chỉ lưu original filename dạng metadata đã chuẩn hóa để hiển thị.

### High — Không giới hạn file size và nhân đôi dữ liệu vào RAM

**Vấn đề:** CopyToAsync vào MemoryStream không giới hạn, không streaming từ request đến storage.  
**Tại sao xảy ra:** Multipart IFormFile có thể đã được framework buffer; đoạn code lại tạo thêm bản sao trong memory.  
**Ảnh hưởng production:** Memory/GC pressure, OOM, request failures khi concurrent upload.  
**Cách sửa:** Enforce request/form/file limits ở ingress và application; dùng OpenReadStream rồi UploadAsync trực tiếp với cancellation; nếu cần upload lớn hoặc chống buffering, thiết kế streaming multipart riêng hoặc direct-to-Blob có kiểm soát. Không giả định IFormFile là zero-buffer.

### High — Thiếu xác minh nội dung và chính sách file

**Vấn đề:** Không validate file rỗng, extension, magic bytes hoặc nội dung độc hại; ContentType hoàn toàn do client cung cấp.  
**Tại sao xảy ra:** Metadata HTTP không xác nhận loại file thực tế.  
**Ảnh hưởng production:** File không được phép có thể lưu và tải về; rủi ro tăng nếu downstream render inline hoặc parser xử lý file.  
**Cách sửa:** Allowlist định dạng, kiểm tra signature, giới hạn kích thước, lưu private, quét malware khi yêu cầu; download bằng Content-Disposition attachment và content type an toàn đã xác minh. Không xem signature check là thay thế antivirus.

### High — DB và Blob không có atomic commit

**Vấn đề:** Blob upload xong mới insert DB; SaveChangesAsync thất bại để lại orphan.  
**Tại sao xảy ra:** Transaction EF Core không bao phủ Azure Blob Storage.  
**Ảnh hưởng production:** Storage leak, chi phí tăng, khó reconciliation; retry có thể tạo nhiều Blob.  
**Cách sửa:** Thiết kế trạng thái Pending/Ready, cleanup có retry, idempotency key nếu client retry; job reconcile orphan theo tuổi và trạng thái. Tránh hứa exactly-once across stores.

### Medium — Thiếu CancellationToken và kiểm soát dependency failure

**Vấn đề:** Không truyền HttpContext.RequestAborted tới DB, copy và Blob operations.  
**Tại sao xảy ra:** Các call có overload nhận cancellation nhưng không được dùng.  
**Ảnh hưởng production:** Công việc tốn tài nguyên tiếp tục sau disconnect; timeout khó phân biệt.  
**Cách sửa:** Propagate CancellationToken, phân loại timeout/transient lỗi, chỉ retry theo policy có giới hạn và không lặp side effect thiếu idempotency.

### Medium — Response trả storage key nội bộ

**Vấn đề:** API trả blobName và phụ thuộc đường dẫn vật lý.  
**Tại sao xảy ra:** Storage abstraction bị lộ qua HTTP contract.  
**Ảnh hưởng production:** Client có thể dựa vào storage layout, làm khó thay đổi; key không phải credential nhưng tiết lộ cấu trúc.  
**Cách sửa:** Ưu tiên trả attachmentId; nếu cần tương thích, giữ field cũ tạm thời và deprecate, không dùng blobName làm authorization.

### Medium — Download không xử lý Blob missing và metadata sai lệch

**Vấn đề:** Attachment có thể tồn tại trong DB nhưng Blob không còn; download không có policy cho trường hợp này.  
**Tại sao xảy ra:** Hai storage có lifecycle riêng.  
**Ảnh hưởng production:** 500/404 không nhất quán, incident khó chẩn đoán.  
**Cách sửa:** Map Blob 404 thành trạng thái phù hợp, log correlation, reconcile dữ liệu; bảo đảm stream được response pipeline dispose sau khi gửi.

### Low — Telemetry chưa đủ để điều tra

**Vấn đề:** Log filename thô, không có operation outcome, duration, size bucket, correlation hoặc storage failure category.  
**Tại sao xảy ra:** Logging chỉ tập trung happy path.  
**Ảnh hưởng production:** Khó xác định upload trùng, unauthorized attempts, orphan hoặc memory pressure.  
**Cách sửa:** Structured logs không ghi nội dung file, có attachmentId/expenseId an toàn, request trace, duration và result; hạn chế PII trong filename.

## Phiên bản đề xuất

Ví dụ sau thể hiện core path; giả định đã có \`IExpenseAccess\` xác minh quyền theo user và expense, \`IFilePolicy\` kiểm tra kích thước, extension, signature và xác định MIME an toàn. Các interface này là abstraction đề xuất, không phải API có sẵn của .NET. Giả định \`Attachment\` có \`Status\` và \`CreatedAtUtc\`, DB migration tương ứng đã triển khai. Blob container private và application dùng Managed Identity với RBAC tối thiểu.

\`\`\`csharp
[HttpPost("{expenseId:guid}/attachments")]
[RequestSizeLimit(16 * 1024 * 1024)]
public async Task<IActionResult> Upload(
    Guid expenseId, IFormFile file, CancellationToken ct)
{
    var expense = await _db.Expenses
        .AsNoTracking().SingleOrDefaultAsync(x => x.Id == expenseId, ct);
    if (expense is null || !await _access.CanUploadAsync(User, expense, ct))
        return NotFound();

    if (file.Length == 0 || file.Length > 15L * 1024 * 1024)
        return BadRequest("Invalid file size");

    var validation = await _filePolicy.ValidateAsync(file, ct);
    if (!validation.Allowed) return BadRequest("Unsupported file");

    var attachmentId = Guid.NewGuid();
    var key = $"expenses/{expenseId:N}/{attachmentId:N}";
    var record = new ExpenseAttachment {
        Id = attachmentId, ExpenseId = expenseId, BlobName = key,
        OriginalName = validation.SafeFileName,
        ContentType = validation.VerifiedContentType,
        Status = "Pending", CreatedAtUtc = DateTimeOffset.UtcNow
    };
    _db.Attachments.Add(record);
    await _db.SaveChangesAsync(ct);

    try
    {
        await using var stream = file.OpenReadStream();
        await _container.GetBlobClient(key).UploadAsync(
            stream, overwrite: false, cancellationToken: ct);
        record.Status = "Ready";
        await _db.SaveChangesAsync(ct);
        return Ok(new { attachmentId });
    }
    catch (Exception ex)
    {
        _logger.LogError(ex, "Attachment upload failed {AttachmentId}",
            attachmentId);
        // Reconciliation worker will inspect Pending records and blobs.
        throw;
    }
}

[HttpGet("attachments/{attachmentId:guid}")]
public async Task<IActionResult> Download(Guid attachmentId,
    CancellationToken ct)
{
    var item = await _db.Attachments.AsNoTracking()
        .Where(x => x.Id == attachmentId && x.Status == "Ready")
        .Join(_db.Expenses, a => a.ExpenseId, e => e.Id,
            (a, e) => new { Attachment = a, Expense = e })
        .SingleOrDefaultAsync(ct);
    if (item is null ||
        !await _access.CanDownloadAsync(User, item.Expense, ct))
        return NotFound();

    var blob = _container.GetBlobClient(item.Attachment.BlobName);
    try
    {
        var download = await blob.DownloadStreamingAsync(
            cancellationToken: ct);
        Response.Headers.CacheControl = "private, no-store";
        return File(download.Value.Content,
            item.Attachment.ContentType,
            item.Attachment.OriginalName);
    }
    catch (RequestFailedException ex) when (ex.Status == 404)
    {
        _logger.LogWarning("Missing blob for {AttachmentId}", attachmentId);
        return NotFound();
    }
}
\`\`\`

**Phạm vi chưa giải quyết trong snippet:** \`IFilePolicy\` phải đọc signature mà không làm mất byte khi upload; với \`IFormFile\` có thể mở stream riêng để kiểm tra rồi mở lại để upload. RequestSizeLimit phải phối hợp giới hạn multipart, reverse proxy và hosting. Nếu second SaveChangesAsync lỗi sau Blob success, record vẫn Pending: reconciler phải HEAD Blob, xác minh metadata/checksum trước khi chuyển Ready hoặc xóa theo policy. Nếu client retry sau timeout, cần idempotency key có unique constraint và cơ chế trả kết quả cũ; code minh họa chưa triển khai phần này. Nếu download stream gặp lỗi sau khi response bắt đầu, không thể đổi HTTP status một cách đáng tin cậy.

## Giải thích thiết kế sau khi sửa

Authorization gắn với resource chứ không chỉ endpoint. Storage key do server tạo tách khỏi filename và không bị ghi đè. Pending/Ready là workflow có thể reconcile thay vì giả định distributed transaction. Blob private; không phát SAS công khai vô hạn. File validation, quota, access audit và malware scanning cần phù hợp mức nhạy cảm nghiệp vụ. Khi có nhiều App Service instances, trạng thái DB và unique constraints là nguồn phối hợp, không dùng static memory.

## Trade-offs

- \`IFormFile\` dễ tích hợp và tương thích nhưng có buffering; direct upload SAS giảm tải App Service song yêu cầu finalize endpoint, quyền upload scoped và cleanup.
- Pending/Ready + reconciler tăng độ phức tạp vận hành nhưng giải quyết partial failure rõ ràng.
- Antivirus/quarantine tăng latency và storage; tài liệu có rủi ro cao có thể cần trạng thái Scanning trước Ready.
- Response tương thích ngược có thể buộc duy trì \`blobName\` tạm thời, nhưng client mới nên chỉ biết \`attachmentId\`.

## Cách kiểm thử

1. **Security integration:** user cùng tenant nhưng khác phòng ban, user khác tenant, owner và approver; thử cả upload/download bằng ID hợp lệ nhưng không có quyền.
2. **Concurrency:** 100–200 upload cùng original filename; mỗi attachment có Blob riêng, không overwrite, memory được giám sát.
3. **Failure-path:** Blob upload thành công rồi DB SaveChanges lỗi; reconciler xử lý Pending không làm lộ file chưa Ready.
4. **File security:** file quá lớn, empty, extension giả, signature sai, tên file bất thường, malware test fixture trong môi trường cô lập.
5. **Download:** Blob missing, client disconnect giữa streaming, Content-Disposition an toàn, no-store và quyền bị thu hồi.

## Quan sát trong production

Application Insights: upload/download p50/p95/p99, exception by dependency, Blob latency, DB SaveChanges failures, request cancellation. Azure Monitor: App Service working set, GC heap, OOM/restart, Blob request errors, Pending age, orphan count, unauthorized access denials (không ghi file content hoặc access token). Dashboard phân biệt failure ở DB và Blob; alert khi Pending vượt SLA hoặc memory tăng theo concurrency.

2. Nếu một file được dùng bởi nhiều expense, thiết kế ownership và deletion thế nào?
3. Nếu malware scanner unavailable, nên fail closed hay cho tải có điều kiện?

## Kết quả code review tham khảo

### Critical — Credentials hardcoded trong Deployment

**Vấn đề:** Connection string chứa password plaintext trong manifest.  
**Tại sao xảy ra:** Secret được đóng gói cùng cấu hình release và có thể nằm trong Git/log/artifact.  
**Ảnh hưởng production:** Rò rỉ credential, khó rotate, phạm vi ảnh hưởng rộng.  
**Cách sửa:** Dùng Secret hoặc external secret provider/Managed Identity khi được hỗ trợ; RBAC tối thiểu, không đưa secret vào log hoặc image. Kubernetes Secret mặc định không đồng nghĩa đã mã hóa end-to-end; cần kiểm soát encryption at rest và quyền truy cập.

### High — Migration chạy trong mọi Pod

**Vấn đề:** RUN_MIGRATIONS_ON_STARTUP bật cho mọi replica.  
**Tại sao xảy ra:** Startup ứng dụng kiêm nhiệm schema migration; nhiều Pod có thể tranh chấp migration/lock, và rollback schema không tự động.  
**Ảnh hưởng production:** Startup fail, database blocking, partial release, phá compatibility phiên bản cũ.  
**Cách sửa:** Chạy migration qua bước release/job được điều phối riêng, quyền DB giới hạn, kiểm tra backward compatibility và expand/contract; không để runtime app có DDL privilege nếu không cần.

### High — Probe có thể kill Pod trước khi startup xong

**Vấn đề:** Liveness bắt đầu sau 5 giây trong khi warm-up 35–50 giây.  
**Tại sao xảy ra:** Không có startupProbe; liveness failure threshold mặc định có thể khiến container bị restart trước khi phục vụ.  
**Ảnh hưởng production:** CrashLoopBackOff, release kẹt, 503 do thiếu ready endpoints.  
**Cách sửa:** Thêm startupProbe với ngân sách đủ startup worst-case, liveness chỉ kiểm tra process health, readiness chỉ phản ánh khả năng nhận traffic. Endpoint health phải có semantics đúng.

### High — Rolling update cho phép mất phần lớn capacity

**Vấn đề:** maxSurge 0 và maxUnavailable 2 với 3 replicas.  
**Tại sao xảy ra:** Controller có thể giảm available replicas xuống 1 trong rollout, không tạo Pod dư.  
**Ảnh hưởng production:** Capacity giảm mạnh, 503/latency nếu một Pod không chịu được tải.  
**Cách sửa:** Với đủ cluster capacity, maxSurge 1 và maxUnavailable 0; kết hợp readiness, PodDisruptionBudget cho voluntary disruptions và autoscaling nếu có bằng chứng tải. Không khẳng định zero downtime khi node/DB/network lỗi.

### High — Image tag mutable

**Vấn đề:** Dùng :latest.  
**Tại sao xảy ra:** Cùng manifest có thể trỏ đến bytes khác nhau, pull policy và node cache làm rollout khó tái lập.  
**Ảnh hưởng production:** Khó audit, khó rollback, các Pod có thể chạy version không mong muốn.  
**Cách sửa:** Pin digest hoặc immutable version tag do CI phát hành, kiểm tra provenance/signature theo chính sách.

### Medium — Readiness và liveness dùng chung endpoint

**Vấn đề:** /health có thể gộp kiểm tra dependency, gây restart vì lỗi DB tạm thời.  
**Tại sao xảy ra:** Liveness không nên phụ thuộc trực tiếp vào availability của mọi downstream.  
**Ảnh hưởng production:** Restart storm làm incident nặng hơn; readiness có thể loại hết endpoints nếu DB toàn hệ thống lỗi.  
**Cách sửa:** Tách /health/live, /health/ready, /health/startup với điều kiện rõ ràng; đánh giá có nên đưa dependency vào readiness theo khả năng degrade.

### Medium — Thiếu resource requests

**Vấn đề:** Chỉ khai báo limits.  
**Tại sao xảy ra:** Scheduler có thể áp dụng default requests từ limits hoặc LimitRange; thiếu cấu hình chủ động để capacity planning.  
**Ảnh hưởng production:** Pod scheduling và CPU throttling không phù hợp workload; 256Mi có thể quá thấp, nhưng phải đo trước khi tăng.  
**Cách sửa:** Đặt requests/limits theo profiling và load test; theo dõi OOMKilled, throttling, GC, p95.

### Medium — Thiếu graceful termination và rollout safeguards

**Vấn đề:** Không mô tả draining, terminationGracePeriodSeconds, progressDeadlineSeconds hoặc pre-deploy validation.  
**Tại sao xảy ra:** Pod có thể ngừng trong lúc đang xử lý request dài, và pipeline có thể báo success khi rollout chưa healthy nếu không chờ.  
**Ảnh hưởng production:** Request bị cắt, deployment stuck khó phát hiện.  
**Cách sửa:** ASP.NET Core xử lý SIGTERM/cancellation, timeout/draining phù hợp, pipeline \`kubectl rollout status\`, smoke tests và rollback gate. Kubernetes đã có grace period mặc định; điều chỉnh dựa trên đo lường.

## Phiên bản đề xuất

Manifest minh họa phần Deployment; giả định đã tạo Secret \`booking-db\` chứa key \`connectionString\`, image digest do CI phát hành, endpoint health đã triển khai đúng semantics. Giá trị requests/limits/probe phải được xác nhận bằng profiling và load test, không phải benchmark thực tế.

\`\`\`yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: booking-api
spec:
  replicas: 3
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 300
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: booking-api
  template:
    metadata:
      labels:
        app: booking-api
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: api
          image: registry.example/booking-api@sha256:REPLACE_WITH_REAL_DIGEST
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_URLS
              value: http://+:8080
            - name: ConnectionStrings__Main
              valueFrom:
                secretKeyRef:
                  name: booking-db
                  key: connectionString
            - name: RUN_MIGRATIONS_ON_STARTUP
              value: "false"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 20
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
          resources:
            requests:
              cpu: 150m
              memory: 256Mi
            limits:
              cpu: "1"
              memory: 512Mi
\`\`\`

**Release sequence đề xuất:** CI build/test → scan và pin image digest → kiểm tra migration expand/backward compatibility → chạy migration một lần qua controlled release step với DB role phù hợp → deploy rolling → chờ rollout status và smoke test → theo dõi SLO → promote/rollback image nếu cần. \`REPLACE_WITH_REAL_DIGEST\` là placeholder bắt buộc thay trước deployment. Không tự động rollback schema khi rollback image; destructive migration cần phase sau khi phiên bản cũ đã rút hoàn toàn.

## Giải thích thiết kế sau khi sửa

Readiness giữ Pod chưa sẵn sàng khỏi Service endpoints; startupProbe cho phép warm-up mà không bị liveness kill sớm; liveness phát hiện process thực sự mắc kẹt. Rolling update giữ tối thiểu 3 available replicas theo khả năng scheduler và readiness, nhưng không bảo đảm capacity khi cluster không có slot Pod thứ tư. Schema migration là một release concern riêng; database compatibility quyết định có rollback an toàn được hay không.

## Trade-offs

- maxUnavailable 0 tăng yêu cầu capacity; cluster thiếu chỗ sẽ khiến rollout chờ thay vì hy sinh capacity.
- Startup probe quá rộng che giấu startup hang; quá hẹp gây restart loop.
- Tách migration khỏi application tăng bước release nhưng giảm tranh chấp và quyền DDL runtime.
- Secret trong Kubernetes thuận tiện nhưng cần RBAC/encryption/rotation; external secret integration tăng dependency vận hành.
- Digest pinning tăng tính tái lập, đòi CI cập nhật manifest mỗi release.

## Cách kiểm thử

1. **Deployment validation:** render manifest, schema validation, thay digest thật; kiểm tra Secret refs, rollout status và image của từng Pod.
2. **Startup/health:** warm-up giả lập 50–80 giây, kiểm tra startupProbe không restart sai, readiness không nhận traffic sớm.
3. **Load/rolling update:** giữ traffic ổn định khi rollout, đo 5xx, p95, ready replicas, throttling và số Pod scheduling pending.
4. **Database compatibility:** old/new application versions cùng chạy trên schema expanded; rollback image sau migration không phá read/write.
5. **Failure-path:** kill Pod giữa request, DB outage ngắn, node thiếu capacity; xác minh graceful shutdown và alert.

## Quan sát trong production

Kubernetes: Deployment available/updated replicas, rollout conditions, restart count, probe failures, Pending/Unschedulable, OOMKilled, CPU throttling. Application Insights: request 5xx/p95/p99, dependency duration, request cancellations, startup time, version/digest dimension. PostgreSQL: migration lock waits, active connections, blocking, error rate. Jenkins: artifact digest, migration step outcome, rollout status và smoke-test result. Alert khi available replicas dưới ngưỡng, rollout vượt deadline hoặc 5xx vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cluster không thể cấp thêm Pod, bạn chấp nhận rollout chậm hay giảm capacity? Điều kiện quyết định?
2. Nếu migration cần xóa cột mà phiên bản cũ còn đọc, bạn triển khai expand/contract qua bao nhiêu release?
3. Nếu readiness kiểm tra DB và DB outage toàn vùng, bạn có nên cho toàn bộ Pods unready không?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Resource authorization phải dựa trên đối tượng và quyền nghiệp vụ, không chỉ authentication. Blob Storage và relational database có partial failure; cần idempotency và reconciliation. Với Kubernetes, health probes, immutable artifacts, rolling update capacity và schema compatibility phải được thiết kế như một chuỗi release thống nhất.

## Mẫu tư duy cần nhớ

1. Xác định trust boundary trước khi tin user-supplied identifiers và metadata.
2. Thiết kế failure recovery trước khi tuyên bố một thao tác là atomic.
3. Đo memory, latency và capacity dưới concurrency thay vì chỉ kiểm tra happy path.
4. Đánh giá release bằng khả năng chạy song song old/new versions và rollback.
5. Dùng telemetry để phân biệt triệu chứng, giả thuyết và nguyên nhân đã kiểm chứng.
