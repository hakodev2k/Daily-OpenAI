# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core
**Độ khó:** Senior+
**Thời gian review đề xuất:** 20–25 phút
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core application dùng Hangfire để gửi notification cho các event sắp diễn ra. Hệ thống chạy nhiều application instance. Một recurring job chạy mỗi phút, tìm notification chưa gửi rồi gọi external API. Khi deploy hoặc khi worker retry sau lỗi mạng, production đôi lúc gửi cùng một notification 2–3 lần. Có lúc external API đã nhận request nhưng database vẫn ghi `Sent = false`.

Business yêu cầu không gửi trùng trong điều kiện bình thường, nhưng external API không hỗ trợ transaction chung với database. Throughput hiện tại khoảng vài nghìn notification/phút và có thể tăng.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task RunAsync()
    {
        var notifications = await _db.Notifications
            .Where(x => !x.Sent && x.SendAt <= DateTime.UtcNow)
            .OrderBy(x => x.SendAt)
            .Take(500)
            .ToListAsync();

        foreach (var notification in notifications)
        {
            try
            {
                var response = await _httpClient.PostAsJsonAsync(
                    "/api/notifications",
                    new
                    {
                        notification.UserId,
                        notification.Subject,
                        notification.Body
                    });

                response.EnsureSuccessStatusCode();

                notification.Sent = true;
                notification.SentAt = DateTime.UtcNow;
                await _db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Failed to send notification {@Notification}",
                    notification);
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có atomic claim trước khi gửi

- **Problem:** nhiều worker có thể cùng đọc một notification `Sent = false`.
- **Why:** query và việc đánh dấu trạng thái xảy ra tách biệt sau HTTP call.
- **Production impact:** duplicate notification dưới concurrency.
- **Severity:** Critical.
- **Recommended fix:** claim record atomically bằng state transition có điều kiện trong database; chỉ worker claim thành công mới được xử lý.

### 2. Failure window giữa HTTP success và database commit

- **Problem:** external side effect có thể thành công nhưng local state chưa commit.
- **Why:** database và remote API không cùng một atomic transaction.
- **Production impact:** retry gửi lại notification.
- **Severity:** Critical.
- **Recommended fix:** nếu provider hỗ trợ, gửi stable idempotency key; lưu delivery attempt/state để reconcile. Nếu provider không hỗ trợ idempotency thì không thể bảo đảm exactly-once tuyệt đối chỉ từ phía client.

### 3. Retry semantics chưa được thiết kế cùng idempotency

- **Problem:** exception làm record tiếp tục eligible ở lần chạy sau.
- **Why:** mọi lỗi đều bị xử lý giống nhau và không có attempt state/backoff.
- **Production impact:** duplicate, retry storm hoặc gọi liên tục một request lỗi vĩnh viễn.
- **Severity:** High.
- **Recommended fix:** lưu attempt count, next-attempt time, error category và trạng thái terminal/dead-letter.

### 4. Một batch được xử lý tuần tự

- **Problem:** 500 HTTP calls chạy nối tiếp.
- **Why:** `foreach` await từng request.
- **Production impact:** throughput thấp, batch kéo dài và tăng khả năng overlap với recurring run tiếp theo.
- **Severity:** High.
- **Recommended fix:** bounded concurrency sau khi records đã được claim an toàn; không dùng unbounded `Task.WhenAll`.

### 5. Không truyền cancellation/timeout policy ở job boundary

- **Problem:** job khó dừng sạch khi shutdown và dependency chậm có thể kéo dài execution.
- **Why:** không có `CancellationToken` xuyên suốt code; timeout/retry policy không thể hiện ở boundary.
- **Production impact:** shutdown chậm, work bị treo lâu, overlap tăng.
- **Severity:** Medium.
- **Recommended fix:** propagate cancellation token và cấu hình timeout/resilience có giới hạn phù hợp với dependency.

### 6. Catch mọi exception rồi tiếp tục mà không phân loại lỗi

- **Problem:** 4xx permanent failure và transient 5xx/network failure bị xử lý như nhau.
- **Why:** `catch (Exception)` không có error policy.
- **Production impact:** retry vô ích, tốn tài nguyên và che lỗi dữ liệu.
- **Severity:** Medium.
- **Recommended fix:** phân loại retryable/non-retryable; terminal failure cần trạng thái riêng.

### 7. Logging toàn entity

- **Problem:** structured log `{@Notification}` có thể serialize subject/body hoặc dữ liệu người dùng.
- **Why:** log object trực tiếp.
- **Production impact:** sensitive-data exposure, tăng log volume.
- **Severity:** Medium.
- **Recommended fix:** log NotificationId, attempt, provider status, duration, correlation/idempotency key; tránh payload nhạy cảm.

### 8. `SaveChangesAsync` cho từng record

- **Problem:** nhiều database round trip.
- **Why:** commit sau từng notification.
- **Production impact:** giảm throughput và tăng DB load.
- **Severity:** Medium.
- **Recommended fix:** thiết kế state update/batching phù hợp; vẫn cần cân bằng durability và recovery, không đơn giản gom toàn bộ 500 side effects vào một transaction dài.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa workflow claim → send → finalize. Phần `TryClaimAsync` phải được implement bằng conditional update atomic ở database; production implementation có thể dùng `ExecuteUpdateAsync`, SQL thích hợp hoặc locking strategy tương ứng DB engine.

```csharp
public sealed class NotificationJob
{
    private readonly NotificationRepository _repository;
    private readonly NotificationClient _client;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        NotificationRepository repository,
        NotificationClient client,
        ILogger<NotificationJob> logger)
    {
        _repository = repository;
        _client = client;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        var ids = await _repository.GetDueIdsAsync(
            batchSize: 500,
            cancellationToken);

        await Parallel.ForEachAsync(
            ids,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 16,
                CancellationToken = cancellationToken
            },
            async (id, ct) =>
            {
                var attemptId = Guid.NewGuid();

                var notification = await _repository.TryClaimAsync(
                    id,
                    attemptId,
                    ct);

                if (notification is null)
                    return;

                try
                {
                    var idempotencyKey = notification.Id.ToString();

                    await _client.SendAsync(
                        notification,
                        idempotencyKey,
                        ct);

                    await _repository.MarkSentAsync(
                        notification.Id,
                        attemptId,
                        DateTimeOffset.UtcNow,
                        ct);
                }
                catch (OperationCanceledException) when (ct.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    await _repository.RecordFailureAsync(
                        notification.Id,
                        attemptId,
                        ex,
                        ct);

                    _logger.LogWarning(
                        ex,
                        "Notification delivery failed. NotificationId={NotificationId}, AttemptId={AttemptId}",
                        notification.Id,
                        attemptId);
                }
            });
    }
}
```

Một state machine thực tế có thể là `Pending -> Processing -> Sent`, kèm `ProcessingUntil`, `AttemptCount`, `NextAttemptAt` và `LastErrorCode`. Worker chỉ claim nếu `Pending` hoặc lease `Processing` đã hết hạn. Finalize cần kiểm tra `AttemptId` để worker cũ không ghi đè trạng thái của attempt mới.

## Trade-offs

Atomic claim làm schema và repository phức tạp hơn nhưng giải quyết concurrency giữa nhiều worker. Distributed lock quanh toàn recurring job đơn giản hơn nhưng giảm parallelism và vẫn không loại bỏ failure window sau remote side effect. Outbox rất hữu ích khi cần atomically ghi business change cùng delivery intent, nhưng consumer vẫn phải xử lý at-least-once. Nếu remote provider hỗ trợ idempotency key, đó là cơ chế quan trọng để giảm duplicate side effect; nếu không, cần chấp nhận giới hạn và có reconciliation/business deduplication phù hợp.

## Cách kiểm thử

1. **Concurrency test:** chạy nhiều worker cùng claim một record; chỉ một worker được quyền gửi.
2. **Failure-path test:** giả lập remote API success rồi process lỗi trước local finalize; retry phải dùng cùng idempotency key.
3. **Lease recovery test:** worker chết khi `Processing`; record phải được reclaim sau timeout mà worker cũ không finalize nhầm.
4. **Load test:** hàng nghìn due notifications với bounded concurrency; đo throughput, DB contention và connection usage.
5. **Permanent failure test:** provider trả lỗi không retryable; record chuyển terminal state thay vì retry vô hạn.

## Quan sát trong production

Theo dõi số record theo `Pending/Processing/Sent/Failed`, processing lease expired, attempts per notification, retry rate, duplicate/idempotency conflicts, provider latency/error rate, queue age từ `SendAt` đến `SentAt`, job duration và DB lock/deadlock. Trace nên nối job execution → claim → outbound HTTP → finalize bằng correlation/attempt ID.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `[DisableConcurrentExecution]` một mình chưa giải quyết được failure window giữa HTTP success và DB commit?
2. Nếu notification được tạo trong cùng transaction với business event, bạn sẽ áp dụng transactional outbox thế nào?
3. Nếu provider không hỗ trợ idempotency key, bạn sẽ mô tả delivery guarantee với stakeholder ra sao?

# Code Review Challenge 2 — API tra cứu người dùng có lỗ hổng authorization và SQL injection

## Bối cảnh

Một internal ASP.NET Core API cho phép support staff tìm user theo email để xử lý ticket. Application là multi-tenant. Người dùng đăng nhập bằng bearer token và tenant hiện tại có claim `tenant_id`. Sau một thay đổi gần đây, security review phát hiện một support user có thể truy vấn thông tin thuộc tenant khác nếu biết email. Production logs cũng đang chứa nhiều thông tin request hơn mong muốn.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/users")]
public sealed class UsersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<UsersController> _logger;

    public UsersController(AppDbContext db, ILogger<UsersController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string email,
        string? tenantId,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Searching user. Email={Email}, Tenant={TenantId}, Authorization={Authorization}",
            email,
            tenantId,
            Request.Headers.Authorization.ToString());

        var sql = $@"
            SELECT Id, TenantId, Email, DisplayName, PhoneNumber, IsAdmin
            FROM Users
            WHERE Email = '{email}'";

        if (!string.IsNullOrWhiteSpace(tenantId))
            sql += $" AND TenantId = '{tenantId}'";

        var users = await _db.Database
            .SqlQueryRaw<UserSearchResult>(sql)
            .ToListAsync(cancellationToken);

        if (users.Count == 0)
            return NotFound();

        return Ok(users);
    }
}
```

## Kết quả code review tham khảo

### 1. SQL injection từ `email`

- **Problem:** `email` được interpolate trực tiếp vào raw SQL.
- **Why:** input do client kiểm soát trở thành một phần của SQL command text.
- **Production impact:** query bị thay đổi ngoài ý muốn, đọc hoặc phá vỡ boundary dữ liệu tùy quyền DB account và provider.
- **Severity:** Critical.
- **Recommended fix:** dùng LINQ/EF parameterization hoặc parameterized SQL API; không tự escape chuỗi để thay thế parameterization.

### 2. Tenant authorization dựa trên client-supplied `tenantId`

- **Problem:** caller có thể bỏ `tenantId` hoặc gửi tenant khác.
- **Why:** server không bind data access vào trusted tenant claim/policy.
- **Production impact:** cross-tenant data exposure.
- **Severity:** Critical.
- **Recommended fix:** lấy tenant identity từ authenticated principal/trusted tenant context và enforce ở data-access boundary; authorization policy phải kiểm tra role/permission phù hợp.

### 3. Endpoint không thể hiện authorization requirement cho support permission

- **Problem:** code không thể hiện policy/role cần thiết cho operation nhạy cảm.
- **Why:** authentication và business authorization là hai bước khác nhau.
- **Production impact:** authenticated user không đúng quyền có thể sử dụng endpoint nếu global configuration không chặn.
- **Severity:** High.
- **Recommended fix:** `[Authorize(Policy = "SupportUserSearch")]` hoặc equivalent endpoint policy, kết hợp tenant-scoped authorization.

### 4. Log Authorization header

- **Problem:** bearer credential có thể bị ghi vào log.
- **Why:** log nguyên `Authorization` header.
- **Production impact:** credential leakage qua log access, SIEM/export hoặc support tooling.
- **Severity:** High.
- **Recommended fix:** không log token/Authorization header; nếu cần identity diagnostics chỉ log safe identifiers/correlation IDs theo policy.

### 5. Log raw email không có data-minimization policy

- **Problem:** PII được ghi ở mức Information cho mọi search.
- **Why:** raw email được dùng làm log field.
- **Production impact:** tăng phạm vi dữ liệu nhạy cảm trong logging system.
- **Severity:** Medium.
- **Recommended fix:** tránh hoặc mask/hash theo use case và policy; audit event có thể lưu identifier an toàn hơn nếu cần truy vết.

### 6. Over-fetch dữ liệu nhạy cảm

- **Problem:** trả `PhoneNumber` và `IsAdmin` dù use case chỉ nói tìm user để hỗ trợ ticket.
- **Why:** response contract không được tối thiểu hóa.
- **Production impact:** tăng blast radius khi authorization sai hoặc response bị log/cache.
- **Severity:** Medium.
- **Recommended fix:** DTO chỉ chứa field thực sự cần; endpoint khác/policy mạnh hơn cho dữ liệu nhạy cảm.

### 7. Không giới hạn/validate input theo domain

- **Problem:** email rỗng/quá dài hoặc không phù hợp domain vẫn vào query path.
- **Why:** thiếu request model validation.
- **Production impact:** request vô nghĩa, tăng load và khó observability; validation không thay thế parameterization nhưng vẫn cần.
- **Severity:** Low.
- **Recommended fix:** request model với length/domain validation phù hợp business requirement.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/users")]
[Authorize(Policy = "SupportUserSearch")]
public sealed class UsersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<UsersController> _logger;

    public UsersController(
        AppDbContext db,
        ITenantContext tenantContext,
        ILogger<UsersController> logger)
    {
        _db = db;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<UserSearchDto>>> Search(
        [FromQuery] string email,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(email) || email.Length > 254)
            return BadRequest("Invalid email.");

        var tenantId = _tenantContext.RequiredTenantId;

        var users = await _db.Users
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Email == email)
            .Select(x => new UserSearchDto(
                x.Id,
                x.Email,
                x.DisplayName))
            .Take(10)
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Support user search completed. TenantId={TenantId}, ResultCount={ResultCount}",
            tenantId,
            users.Count);

        return users.Count == 0 ? NotFound() : Ok(users);
    }
}

public sealed record UserSearchDto(
    Guid Id,
    string Email,
    string DisplayName);
```

Trong hệ thống multi-tenant lớn hơn, tenant scoping nên khó bị quên: ví dụ repository/data-access abstraction, global query filter khi phù hợp, hoặc explicit tenant predicates được kiểm thử bắt buộc. Global query filters tiện nhưng cần hiểu các đường bypass/admin scenarios; authorization vẫn không nên chỉ dựa vào filter.

## Trade-offs

LINQ giúp parameterization và composability dễ đọc hơn nhưng không tự giải quyết authorization. Global query filter giảm nguy cơ quên tenant predicate nhưng có thể gây bất ngờ cho administrative queries và phải quản lý đường `IgnoreQueryFilters` rất chặt. Hash/mask email trong log tăng privacy nhưng giảm khả năng support tìm kiếm trực tiếp; có thể dùng audit store chuyên biệt với quyền truy cập/retention riêng khi business thực sự cần PII.

## Cách kiểm thử

1. **Security test:** caller tenant A tìm email chỉ tồn tại ở tenant B phải không nhận dữ liệu B, kể cả gửi query parameter giả mạo.
2. **Injection test:** email chứa SQL metacharacters phải được xử lý như value và không thay đổi query semantics.
3. **Authorization test:** authenticated user thiếu `SupportUserSearch` policy nhận 403.
4. **Data-minimization test:** response không chứa phone/admin fields ngoài contract.
5. **Logging test:** capture test logger và xác nhận không có bearer token/raw Authorization header; kiểm tra policy đối với PII.

## Quan sát trong production

Audit số search theo tenant/caller, 401/403 rate, unusual high-volume search, cross-tenant authorization denials, query latency và database scans. Security audit log nên có caller ID, tenant ID, action, timestamp, result category và correlation ID nhưng không chứa bearer token. Alert khi một identity thực hiện lượng search bất thường hoặc liên tục bị authorization deny.

1. Khi nào EF Core global query filter là lựa chọn tốt cho tenant isolation, và khi nào nó có thể tạo false sense of security?
2. Nếu có global support admin thực sự cần tìm cross-tenant, bạn thiết kế policy và audit trail thế nào?
3. Parameterized SQL bảo vệ SQL injection nhưng tại sao vẫn không giải quyết Broken Object Level Authorization?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng distributed side effect thường có failure window: claim work, retry và idempotency phải được thiết kế cùng nhau. Một database flag sau HTTP call không tạo ra exactly-once delivery. Challenge 2 tập trung vào trust boundary: parameterization giải quyết injection, còn tenant isolation và authorization phải dựa trên trusted identity/server-side policy; logging cũng là một security boundary.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và recovery state.
