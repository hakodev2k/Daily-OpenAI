# Code Review Challenge 1 — `BackgroundService` gửi notification trùng sau khi App Service scale-out

**Chủ đề:** C#/.NET, `BackgroundService`, EF Core, multi-instance execution, idempotency, graceful shutdown, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một approval platform có bảng `PendingNotifications` trong SQL Server. ASP.NET Core application chạy trên Azure App Service và có một `BackgroundService` quét bảng mỗi 10 giây để gửi email qua third-party provider.

Khi hệ thống chỉ có một App Service instance, flow nhìn chung hoạt động. Sau khi scale-out lên 4 instances, support ghi nhận một số người nhận cùng notification 2–4 lần. Khi provider chậm hoặc deployment xảy ra giữa lúc gửi, số duplicate tăng. Team đề xuất thêm `SemaphoreSlim` static để chỉ cho một worker chạy tại một thời điểm.

Business chấp nhận delivery theo mô hình at-least-once ở infrastructure boundary, nhưng người dùng không được nhận duplicate email cho cùng một notification business event. Provider hỗ trợ timeout nhưng chưa rõ có hỗ trợ idempotency key hay query trạng thái request hay không.

## Đoạn code cần review

```csharp
public sealed class NotificationWorker : BackgroundService
{
    private static readonly SemaphoreSlim Gate = new(1, 1);
    private readonly IServiceProvider _services;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationWorker> _logger;

    public NotificationWorker(
        IServiceProvider services,
        IEmailSender emailSender,
        ILogger<NotificationWorker> logger)
    {
        _services = services;
        _emailSender = emailSender;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            await Gate.WaitAsync();

            try
            {
                using var scope = _services.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                var pending = await db.PendingNotifications
                    .Where(x => !x.Sent)
                    .OrderBy(x => x.CreatedAtUtc)
                    .Take(100)
                    .ToListAsync();

                foreach (var item in pending)
                {
                    await _emailSender.SendAsync(
                        item.Email,
                        item.Subject,
                        item.Body,
                        CancellationToken.None);

                    item.Sent = true;
                    item.SentAtUtc = DateTime.UtcNow;
                    await db.SaveChangesAsync();
                }
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Notification worker failed");
            }
            finally
            {
                Gate.Release();
            }

            await Task.Delay(TimeSpan.FromSeconds(10));
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/concurrency problems khi application chạy nhiều instances.
2. Xác định failure windows có thể gây duplicate hoặc làm worker không shutdown đúng cách.
3. Giải thích vì sao `static SemaphoreSlim` không giải quyết coordination giữa App Service instances.
4. Ưu tiên findings theo severity và business impact.
5. Đề xuất implementation/design tốt hơn với processing ownership và idempotency rõ ràng.
6. Nêu cách test concurrency, provider timeout, process termination và retry.
7. Nêu telemetry cần có để phân biệt duplicate claim, duplicate send và provider uncertainty.

## Câu hỏi gợi mở

1. Bốn App Service instances có dùng cùng một static field không?
2. Điều gì xảy ra nếu provider đã nhận email nhưng process chết trước `SaveChangesAsync`?
3. Query `!x.Sent` có atomically claim records cho một worker hay không?
4. `stoppingToken` hiện được truyền tới những asynchronous boundaries nào?
5. Nếu send timeout, bạn có chắc provider chưa gửi email không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **multi-instance ownership, crash window và idempotency**.

### Gợi ý 2

Một lock trong memory chỉ coordinate các callers trong cùng process. Hãy thiết kế dựa trên shared state hoặc một delivery mechanism có semantics rõ ràng, đồng thời coi timeout sau side effect là trạng thái không chắc chắn.

## Kết quả code review tham khảo

### Critical — Không có atomic claim nên nhiều instances có thể xử lý cùng notification

**Vấn đề:** Mọi instance đều query cùng các row `Sent = false`; không có claim/lease/locking protocol để một row thuộc về đúng một worker tại một thời điểm.  
**Tại sao xảy ra:** Read và ownership transition không phải một atomic operation. Hai workers có thể đọc cùng row trước khi bất kỳ worker nào set `Sent`.  
**Ảnh hưởng production:** Duplicate email tăng theo concurrency/scale-out; behavior phụ thuộc timing nên khó tái hiện ở local một instance.  
**Cách sửa:** Thiết kế atomic claim trong shared store hoặc chuyển delivery sang queue với consumer idempotency. Nếu dùng SQL, claim một bounded batch bằng transaction/concurrency strategy phù hợp, lưu processing state/lease và worker ownership trước khi thực hiện external side effect.

### Critical — Crash window giữa external side effect và database commit tạo duplicate không thể loại bỏ chỉ bằng transaction SQL

**Vấn đề:** Email có thể đã được provider chấp nhận, nhưng process chết trước khi `Sent = true` được commit.  
**Tại sao xảy ra:** SQL transaction không thể atomically commit cùng external email provider.  
**Ảnh hưởng production:** Row vẫn pending và lần retry gửi lại email.  
**Cách sửa:** Dùng stable business notification ID/idempotency key nếu provider hỗ trợ. Nếu provider không hỗ trợ idempotency, cần explicit delivery state (`Pending`, `Processing`, `Sent`, `Unknown`), reconciliation policy và chấp nhận rằng exactly-once side effect không thể được đảm bảo chỉ bằng local database flag.

### High — `static SemaphoreSlim` không coordinate nhiều App Service processes/instances

**Vấn đề:** Mỗi process có static memory riêng.  
**Tại sao xảy ra:** `static` chỉ chia sẻ trong process/AppDomain/runtime instance tương ứng, không phải distributed lock.  
**Ảnh hưởng production:** Team có thể tin duplicate đã được fix trong single-instance test nhưng production vẫn duplicate.  
**Cách sửa:** Không dựa vào in-process lock cho distributed ownership. Dùng database claim/lease, queue competing consumers hoặc distributed coordination khi thực sự cần; ưu tiên design giảm nhu cầu global lock.

### High — Cancellation/graceful shutdown bị bỏ qua

**Vấn đề:** Loop là `while (true)`, `Gate.WaitAsync`, EF calls, email send và `Task.Delay` không dùng `stoppingToken`.  
**Tại sao xảy ra:** `CancellationToken.None` và overload không nhận token khiến host không thể yêu cầu work dừng hợp tác.  
**Ảnh hưởng production:** Deployment/shutdown kéo dài, process có thể bị terminate giữa send/commit, làm failure window lớn hơn.  
**Cách sửa:** Dùng `while (!stoppingToken.IsCancellationRequested)`, truyền token tới wait/query/send/save/delay; phân biệt cancellation do shutdown với operational error.

### High — Timeout/failure của provider bị coi như “chưa gửi” dù outcome có thể unknown

**Vấn đề:** Exception từ `SendAsync` luôn dẫn tới retry ở lần quét sau.  
**Tại sao xảy ra:** Network timeout chỉ cho biết client không nhận được kết quả; provider có thể đã chấp nhận request.  
**Ảnh hưởng production:** Retry có thể tạo duplicate side effect.  
**Cách sửa:** Dùng provider idempotency key/status API nếu có; lưu attempt/correlation/provider message ID và có reconciliation cho outcome không chắc chắn.

### High — Một exception dừng xử lý toàn batch và không có retry/backoff policy theo item

**Vấn đề:** Exception ở một notification thoát khỏi `foreach`; batch còn lại chờ lần polling sau.  
**Tại sao xảy ra:** Catch nằm ngoài toàn bộ batch và không có per-item failure state.  
**Ảnh hưởng production:** Poison item có thể liên tục cản trở throughput; provider outage có thể tạo polling/retry pressure.  
**Cách sửa:** Track attempt count/next-attempt time/error state theo item; exponential backoff/jitter phù hợp; tách permanent failure khỏi transient failure; có dead-letter/manual review policy.

### Medium — `SaveChangesAsync` sau từng item tạo nhiều round trips

**Vấn đề:** Mỗi successful send thực hiện một database commit riêng.  
**Tại sao xảy ra:** Persistence được đặt trong loop.  
**Ảnh hưởng production:** Tăng SQL round trips và latency. Tuy nhiên không được batch commit mù vì điều đó mở rộng crash window và làm mất per-item state.  
**Cách sửa:** Tối ưu sau khi correctness model rõ; có thể persist state transitions theo batch/operation phù hợp, nhưng phải giữ recovery semantics.

### Medium — Query thiếu explicit processing/retry state và có thể gây starvation

**Vấn đề:** Chỉ có boolean `Sent`; không biểu diễn `Processing`, retry schedule, permanent failure hoặc unknown outcome.  
**Tại sao xảy ra:** Data model đơn giản hóa workflow có external side effect.  
**Ảnh hưởng production:** Khó recover, khó quan sát backlog và poison items.  
**Cách sửa:** Dùng state machine nhỏ với timestamps/attempt count/lease expiry/correlation metadata.

### Medium — Logging không đủ để điều tra duplicate

**Vấn đề:** Log chỉ ghi worker-level exception, không có notification ID, attempt, worker instance, provider correlation hoặc processing state.  
**Tại sao xảy ra:** Observability không được thiết kế theo workflow.  
**Ảnh hưởng production:** Không thể xác định duplicate phát sinh từ double claim, timeout retry hay provider behavior.  
**Cách sửa:** Structured logs/traces theo stable notification ID, claim owner, attempt, provider request ID và outcome.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa **processing lease + stable idempotency key**. Chi tiết atomic claim phụ thuộc SQL Server schema/locking strategy; `ClaimBatchAsync` phải thực sự claim rows trong database atomically, không chỉ `SELECT` rồi update ở application code.

```csharp
public sealed class NotificationWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationWorker> _logger;

    public NotificationWorker(
        IServiceScopeFactory scopeFactory,
        IEmailSender emailSender,
        ILogger<NotificationWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _emailSender = emailSender;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            await using var scope = _scopeFactory.CreateAsyncScope();
            var store = scope.ServiceProvider
                .GetRequiredService<INotificationDeliveryStore>();

            var workerId = Environment.MachineName + ":" + Guid.NewGuid();
            var batch = await store.ClaimBatchAsync(
                workerId,
                batchSize: 50,
                leaseDuration: TimeSpan.FromMinutes(2),
                stoppingToken);

            foreach (var item in batch)
            {
                try
                {
                    var result = await _emailSender.SendAsync(
                        item.Email,
                        item.Subject,
                        item.Body,
                        idempotencyKey: item.NotificationId.ToString(),
                        stoppingToken);

                    await store.MarkSentAsync(
                        item.NotificationId,
                        workerId,
                        result.ProviderMessageId,
                        stoppingToken);
                }
                catch (OperationCanceledException)
                    when (stoppingToken.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    _logger.LogWarning(
                        ex,
                        "Notification attempt failed. NotificationId={NotificationId} WorkerId={WorkerId}",
                        item.NotificationId,
                        workerId);

                    await store.ScheduleRetryAsync(
                        item.NotificationId,
                        workerId,
                        stoppingToken);
                }
            }

            await Task.Delay(TimeSpan.FromSeconds(10), stoppingToken);
        }
    }
}
```

Nếu email provider **không** hỗ trợ idempotency key hoặc status reconciliation, cần ghi rõ giới hạn: lease/claim ngăn concurrent double-processing nhưng không thể bảo đảm exactly-once external side effect khi process chết sau provider acceptance và trước local commit. Khi requirement business không chấp nhận duplicate, provider capability hoặc workflow phải thay đổi.

## Giải thích thiết kế sau khi sửa

Ownership được chuyển từ in-process lock sang shared processing state. Mỗi notification có stable identity và processing lease để worker khác có thể recover khi owner chết. External side effect dùng cùng stable idempotency key qua retry, nếu provider hỗ trợ.

Cancellation đi xuyên I/O boundaries để deployment/shutdown không kéo dài không cần thiết. Failure được ghi theo item thay vì làm poison item chặn toàn batch. Design không tuyên bố “exactly once” nếu downstream không cung cấp primitive cần thiết.

## Trade-offs

Lease/state machine làm schema và operational logic phức tạp hơn boolean `Sent`. Lease quá ngắn có thể hết hạn khi send chậm; quá dài làm recovery chậm. Queue như Azure Service Bus có thể cung cấp competing-consumer/retry/DLQ primitives tốt hơn polling SQL, nhưng vẫn cần idempotent consumer và làm tăng infrastructure/operational complexity. Nếu workload nhỏ và một instance cố định thực sự đáp ứng requirement, simpler design có thể đủ, nhưng scale-out requirement hiện tại đã bác bỏ assumption đó.

## Cách kiểm thử

1. **Concurrency test:** chạy 4 worker instances cùng claim một tập notifications; mỗi business ID chỉ được claim theo protocol cho phép.
2. **Failure-path test:** provider chấp nhận request rồi client timeout; retry dùng cùng idempotency key và không tạo duplicate khi provider hỗ trợ.
3. **Process-termination test:** kill worker sau claim và sau send ở các thời điểm khác nhau; xác minh lease expiry/reconciliation recovery đúng.
4. **Integration test:** poison notification retry theo backoff và không chặn notifications khác.
5. **Shutdown test:** gửi cancellation trong lúc idle/query/send và xác minh worker dừng trong host shutdown budget mà không corrupt processing state.

## Quan sát trong production

- Backlog size và oldest pending age.
- Claim rate, lease-expiry/reclaim count và concurrent-claim conflicts.
- Attempts per notification, retry rate và permanent/unknown outcomes.
- Provider latency/error/timeout và provider message ID correlation.
- Duplicate business notification metric nếu downstream có signal.
- Worker instance ID trong structured logs và traces.
- SQL dependency latency, query count và connection-pool health.
- Alert theo backlog age, retry storm, unknown outcome và delivery SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu chuyển workflow sang Azure Service Bus, duplicate delivery còn có thể xảy ra không và consumer phải thay đổi gì?
2. Bạn chọn lease duration dựa trên dữ liệu nào, và xử lý operation vượt lease như thế nào?
3. Nếu email provider không có idempotency key/status API nhưng business yêu cầu tuyệt đối không gửi duplicate, bạn sẽ challenge requirement hoặc architecture ra sao?

# Code Review Challenge 2 — Jenkins/Octopus deploy app trước migration làm release nửa mới nửa cũ

**Chủ đề:** CI/CD, Jenkins, Octopus Deploy, SQL Server schema migration, backward compatibility, rollback, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API được build bằng Jenkins và deploy qua Octopus Deploy lên 6 IIS servers sau load balancer. Database SQL Server dùng chung. Team đang migrate dần từ legacy schema và release thường xuyên trong giờ làm việc.

Pipeline hiện deploy application package tới từng server trước, sau đó chạy EF Core migration một lần. Một migration gần đây rename column `Customer.Name` thành `DisplayName`. Trong rolling deployment, một số servers chạy code mới trong khi schema vẫn cũ; sau migration, các servers chưa update vẫn chạy code cũ với schema mới. Production xuất hiện 500 trong vài phút. Team đề xuất “deploy nhanh hơn” hoặc tự động rollback application package nếu health check fail.

## Đoạn code cần review

```groovy
stage('Build') {
    sh 'dotnet restore'
    sh 'dotnet build -c Release'
    sh 'dotnet test -c Release'
    sh 'dotnet publish src/Web/Web.csproj -c Release -o out'
}

stage('Package') {
    sh 'octo pack --id EmployeePortal --version latest --basePath out'
    sh 'octo push --package EmployeePortal.latest.nupkg --replace-existing'
}

stage('Deploy') {
    sh 'octo create-release --project EmployeePortal --version latest --package EmployeePortal:latest'
    sh 'octo deploy-release --project EmployeePortal --version latest --deployTo Production --waitForDeployment'

stage('Migrate Database') {
    sh 'dotnet ef database update --project src/Infrastructure --startup-project src/Web'
}
```

Migration tương ứng:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "Name",
        table: "Customer",
        newName: "DisplayName");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "DisplayName",
        table: "Customer",
        newName: "Name");
}
```

## Nhiệm vụ của ứng viên

1. Xác định release-safety, artifact-integrity và schema-compatibility problems.
2. Giải thích failure window khi old/new application versions cùng dùng một database.
3. Đánh giá vì sao automatic application rollback không đủ nếu migration đã thay schema không backward-compatible.
4. Ưu tiên findings theo severity.
5. Đề xuất pipeline/migration strategy hỗ trợ rolling deployment an toàn hơn.
6. Nêu cách test deployment compatibility và rollback trước production.
7. Nêu telemetry/release evidence cần theo dõi để quyết định continue/abort rollout.

## Câu hỏi gợi mở

1. `latest` có xác định chính xác artifact nào đang chạy và có rollback reproducible không?
2. Trong rolling deployment, schema phải tương thích với những application versions nào?
3. Rename/drop column có thể tách thành nhiều releases theo expand/contract không?
4. Nếu app rollback nhưng database không rollback an toàn, hệ thống ở trạng thái nào?
5. Migration được chạy từ workspace Jenkins có chắc dùng đúng artifact/source revision vừa deploy không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **immutable artifact/versioning và database compatibility xuyên qua rolling deployment**.

### Gợi ý 2

Hãy coi schema migration là một protocol giữa nhiều application versions. Rollback application chỉ an toàn nếu schema sau migration vẫn tương thích với version được rollback.

## Kết quả code review tham khảo

### Critical — Destructive rename phá compatibility giữa old/new application versions

**Vấn đề:** Migration rename `Name` → `DisplayName` trong một bước trong khi rolling deployment cho phép old/new versions chạy đồng thời.  
**Tại sao xảy ra:** Code cũ cần `Name`; code mới có thể cần `DisplayName`. Một schema chỉ có một trong hai column không phục vụ được cả hai versions.  
**Ảnh hưởng production:** 500 trong deployment và rollback; lỗi phụ thuộc server nào nhận request.  
**Cách sửa:** Dùng expand/contract: release đầu add `DisplayName` nullable/backfilled và code transition đọc/ghi tương thích; migrate/backfill; chuyển consumers; chỉ drop `Name` ở release sau khi không còn version cũ phụ thuộc nó.

### Critical — Application được deploy trước khi schema đáp ứng code mới

**Vấn đề:** Pipeline rollout code mới rồi mới chạy migration.  
**Tại sao xảy ra:** Không có compatibility contract giữa deployment phases.  
**Ảnh hưởng production:** New instance có thể query column/table chưa tồn tại ngay khi nhận traffic.  
**Cách sửa:** Với additive backward-compatible migration, expand schema trước, verify, rồi deploy compatible app. Contract migration chạy sau khi old versions đã retired. Thứ tự phải phụ thuộc loại migration, không phải rule “migration luôn trước/sau”.

### High — `latest` và `--replace-existing` phá artifact immutability/reproducibility

**Vấn đề:** Build/package/release đều dùng mutable version `latest`.  
**Tại sao xảy ra:** Cùng identifier có thể trỏ tới bytes khác theo thời gian.  
**Ảnh hưởng production:** Không chứng minh được artifact nào đã test/deploy; rollback và audit không đáng tin cậy.  
**Cách sửa:** Dùng immutable version từ commit SHA/build number/semantic version; build một lần, promote đúng artifact qua environments; không replace cùng version.

### High — Migration chạy từ Jenkins workspace thay vì một migration artifact/version đã được kiểm soát

**Vấn đề:** `dotnet ef database update` chạy sau deploy dựa trên source/workspace hiện tại.  
**Tại sao xảy ra:** Migration execution không gắn chặt với immutable release artifact và deployment environment governance.  
**Ảnh hưởng production:** Có thể chạy migration khác với application package đã deploy hoặc phụ thuộc tool/config trên agent.  
**Cách sửa:** Tạo/version migration artifact/script trong build, review SQL khi cần, promote cùng release metadata và execute bằng controlled deployment step/identity.

### High — Automatic app rollback không phục hồi destructive schema change

**Vấn đề:** Team giả định health-check failure có thể rollback package để trở lại trạng thái cũ.  
**Tại sao xảy ra:** Database là shared persistent state và migration có thể không rollback losslessly/safely dưới concurrent writes.  
**Ảnh hưởng production:** Old app sau rollback vẫn fail với new schema hoặc rollback DB làm mất/ghi đè data.  
**Cách sửa:** Thiết kế forward/backward-compatible schema để app rollback không cần DB rollback trong normal path; backup/recovery là lớp khác, không thay thế compatibility design.

### High — Build không bảo đảm test/publish dùng đúng immutable inputs một lần

**Vấn đề:** Restore/build/test/publish được gọi riêng mà không thể hiện locked dependency/artifact provenance; package version không gắn commit.  
**Tại sao xảy ra:** Pipeline tập trung vào command sequence hơn artifact identity.  
**Ảnh hưởng production:** Audit/reproduction khó; dependency drift có thể xảy ra nếu build environment không được pin phù hợp.  
**Cách sửa:** Pin SDK/dependencies theo repository policy, dùng deterministic version metadata, tạo artifact một lần và checksum/provenance phù hợp.

### Medium — Không có pre/post deployment compatibility gates

**Vấn đề:** Pipeline deploy toàn Production mà không thể hiện schema compatibility check, smoke test, staged rollout hay abort gate.  
**Tại sao xảy ra:** `--waitForDeployment` chỉ đợi deployment tool hoàn thành, không chứng minh business/API correctness.  
**Ảnh hưởng production:** Regression có blast radius lớn trước khi phát hiện.  
**Cách sửa:** Preflight migration validation, canary/ring nếu infrastructure cho phép, health + critical smoke tests, error/SLO gate trước khi mở rộng rollout.

### Medium — `Down` rename ngược không đồng nghĩa rollback an toàn

**Vấn đề:** `Down` chỉ rename column, không giải quyết writes đã xảy ra trong transition hoặc compatibility của code đang chạy.  
**Tại sao xảy ra:** Schema reversal được nhầm với operational rollback.  
**Ảnh hưởng production:** Có thể tạo downtime hoặc data inconsistency khi chạy dưới traffic.  
**Cách sửa:** Xem rollback là release strategy; destructive migration thường được trì hoãn, còn recovery phải được rehearsal và phụ thuộc data semantics.

### Medium — Không thấy concurrency control cho migration execution

**Vấn đề:** Nếu pipeline/release bị trigger đồng thời, migration step có thể cạnh tranh hoặc chạy không theo intended release order.  
**Tại sao xảy ra:** Không có explicit deployment serialization/environment lock trong snippet.  
**Ảnh hưởng production:** Race giữa releases/migrations và khó xác định schema version.  
**Cách sửa:** Serialize production schema changes theo environment, kiểm tra expected schema/release version và audit migration execution.

## Phiên bản đề xuất

Một flow an toàn hơn cho **expand release** có thể là:

```groovy
environment {
    RELEASE_VERSION = "${GIT_COMMIT}-${BUILD_NUMBER}"
}

stage('Build and Test') {
    sh 'dotnet restore --locked-mode'
    sh 'dotnet test -c Release --no-restore'
    sh 'dotnet publish src/Web/Web.csproj -c Release --no-restore -o out'
}

stage('Create Immutable Artifacts') {
    sh "octo pack --id EmployeePortal --version ${RELEASE_VERSION} --basePath out"
    sh "dotnet ef migrations script --idempotent --project src/Infrastructure --startup-project src/Web -o migration.sql"
    // Publish application + reviewed/versioned migration artifact without replacing an existing version.
}

stage('Expand Schema') {
    // Execute the versioned, reviewed additive migration using a controlled deployment identity.
    sh './deploy-schema-expand.sh migration.sql'
    sh './verify-schema-compatibility.sh'
}

stage('Deploy Canary') {
    sh "./deploy-release.sh ${RELEASE_VERSION} canary"
    sh './run-critical-smoke-tests.sh'
    sh './verify-release-metrics.sh canary'
}

stage('Roll Out') {
    sh "./deploy-release.sh ${RELEASE_VERSION} production"
    sh './run-critical-smoke-tests.sh'
}
```

Migration được chia thành nhiều releases. Ví dụ expand phase:

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>(
        name: "DisplayName",
        table: "Customer",
        type: "nvarchar(256)",
        nullable: true);
}
```

Transition code phải hỗ trợ old/new representation theo migration plan; backfill được thực hiện có kiểm soát và quan sát được. Chỉ sau khi mọi application version đã chuyển sang `DisplayName`, dữ liệu đã backfill/validated và rollback window kết thúc, một **contract release riêng** mới loại bỏ `Name`.

Đây là pattern minh họa; exact dual-read/dual-write/backfill strategy phải dựa trên data semantics, write volume, constraints và downtime tolerance. Không nên mặc định dual-write là miễn phí hoặc luôn cần thiết.

## Giải thích thiết kế sau khi sửa

Artifact identity được cố định theo source/build, nên thứ đã test là thứ được promote. Database change được coi là phần của release protocol, không phải command hậu kỳ. Expand migration tương thích với old app; application rollout có thể dừng/rollback mà schema vẫn chấp nhận old version. Contract migration được trì hoãn tới khi dependency cũ đã biến mất.

Pipeline có staged verification để giảm blast radius. Health check chỉ là một signal; critical smoke tests và production metrics mới xác minh behavior quan trọng.

## Trade-offs

Expand/contract cần nhiều releases và có temporary schema/code complexity. Backfill có thể tốn I/O và cần throttling. Canary/ring deployment kéo dài release và đòi hỏi routing/deployment support. Immutable artifact/versioning tăng discipline nhưng cải thiện audit/rollback đáng kể. Với ứng dụng nhỏ có maintenance window thực sự chấp nhận downtime, offline migration có thể đơn giản hơn; không cần áp dụng rolling complexity nếu requirement không có zero/low downtime.

## Cách kiểm thử

1. **Database compatibility test:** chạy old application version với expanded schema và new transition version với cùng schema.
2. **Deployment validation:** deploy canary, chạy critical API/Playwright journeys và chỉ tiếp tục khi error/latency/business checks đạt gate.
3. **Rollback rehearsal:** rollback app từ new version về old version khi expanded schema vẫn tồn tại; xác minh hệ thống tiếp tục hoạt động.
4. **Migration test:** chạy migration trên production-like data volume; đo lock duration, log growth, execution time và backfill impact.
5. **Concurrent release test/process validation:** bảo đảm environment lock ngăn hai incompatible schema releases chạy đồng thời.

## Quan sát trong production

- Release version/commit SHA trên mỗi IIS instance và trong Application Insights telemetry.
- HTTP 5xx, p95/p99, dependency failures và critical business transaction success rate theo version.
- SQL blocking/deadlocks, migration duration, schema version và backfill progress.
- Number of instances trên old/new release trong rollout.
- Smoke/E2E gate results và deployment step audit.
- Alert nếu mixed-version window vượt dự kiến hoặc error budget bị vi phạm.
- Dashboard/correlation cho release marker để so sánh trước/sau deploy.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận maintenance-window migration thay vì expand/contract rolling migration?
2. Nếu backfill 200 triệu rows mất nhiều giờ, bạn thiết kế transition và throttling như thế nào để không khóa production workload?
3. Nếu một migration thay đổi business semantics chứ không chỉ schema, bạn làm thế nào để old/new versions cùng tồn tại an toàn?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- In-process synchronization không giải quyết distributed ownership khi ASP.NET Core application chạy nhiều instances.
- External side effect + local database commit luôn có failure window; idempotency và outcome reconciliation phải được thiết kế explicit.
- Rolling deployment yêu cầu schema tương thích với các application versions có thể cùng chạy trong transition window.
- Artifact immutability và release identity là nền tảng của reproducible deployment/rollback.
- Database rollback không nên được coi là bản sao đơn giản của application rollback; backward-compatible evolution thường an toàn hơn destructive change tức thời.

## Mẫu tư duy cần nhớ

- Xác định ownership boundary trước khi thêm lock.
- Thiết kế retry cùng idempotency và trạng thái “unknown outcome”.
- Với rolling deployment, hỏi “old và new version có cùng sống được với schema này không?”.
- Build once, version immutably, promote the same artifact.
- Test failure/rollback path trước khi production buộc bạn phải dùng nó.
