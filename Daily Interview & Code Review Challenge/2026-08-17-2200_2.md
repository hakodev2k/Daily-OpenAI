# Code Review Challenge 1 — EF Core Transaction và race condition khi xử lý đơn hàng

**Chủ đề:** EF Core transaction, concurrency, consistency
**Độ khó:** Senior
**Thời gian review đề xuất:** 20 phút
**Số vấn đề cần tìm:** Khoảng 6 vấn đề

## Bối cảnh

Một API ASP.NET Core xử lý việc đặt hàng. Khi người dùng submit nhiều lần hoặc có retry từ client, hệ thống đôi lúc tạo duplicate order và tồn kho âm.

## Đoạn code cần review

```csharp
public async Task<OrderResult> CreateOrder(CreateOrderRequest request)
{
    var product = await _db.Products
        .FirstAsync(x => x.Id == request.ProductId);

    if (product.Stock < request.Quantity)
        throw new Exception("Not enough stock");

    product.Stock -= request.Quantity;

    var order = new Order
    {
        UserId = request.UserId,
        ProductId = product.Id,
        Quantity = request.Quantity,
        Status = "Created"
    };

    _db.Orders.Add(order);
    await _db.SaveChangesAsync();

    await _publisher.PublishAsync(new OrderCreatedEvent
    {
        OrderId = order.Id
    });

    return new OrderResult(order.Id);
}
```

## Nhiệm vụ của ứng viên

1. Identify correctness problems.
2. Identify concurrency, reliability and performance risks.
3. Explain production impact.
4. Prioritize issues.
5. Propose corrected implementation.
6. Explain testing and observability.

## Câu hỏi gợi mở

- Điều gì xảy ra khi hai request đọc cùng một stock?
- Nếu publish event thất bại sau SaveChanges thì sao?
- Request retry có tạo dữ liệu trùng không?
- Có cần optimistic concurrency không?

## Gợi ý

### Gợi ý 1
Tập trung vào consistency và failure boundary.

### Gợi ý 2
Xem xét transaction, concurrency token và idempotency.

## Kết quả code review tham khảo

### 1. Không có transaction boundary
- Problem: Update stock và tạo order không được kiểm soát rõ ràng.
- Impact: Dữ liệu không nhất quán.
- Severity: High
- Fix: Transaction hoặc domain workflow phù hợp.

### 2. Race condition khi cập nhật stock
- Problem: Hai request có thể cùng đọc stock cũ.
- Impact: Overselling.
- Severity: Critical
- Fix: RowVersion optimistic concurrency hoặc atomic update.

### 3. Publish event sau database commit
- Problem: Event có thể mất.
- Impact: Consumer không nhận được notification.
- Severity: High
- Fix: Outbox pattern.

### Phiên bản đề xuất

```csharp
await using var tx = await _db.Database.BeginTransactionAsync();

var updated = await _db.Products
    .Where(x => x.Id == request.ProductId && x.Stock >= request.Quantity)
    .ExecuteUpdateAsync(s => s.SetProperty(
        x => x.Stock, x => x.Stock - request.Quantity));

if (updated == 0)
    throw new InvalidOperationException("Stock unavailable");

var order = new Order { ProductId = request.ProductId };
_db.Orders.Add(order);
await _db.SaveChangesAsync();

_db.OutboxMessages.Add(new OutboxMessage(order));
await _db.SaveChangesAsync();

await tx.CommitAsync();
```

## Cách kiểm thử

- Concurrent requests update same product.
- Retry duplicate request.
- Database failure during transaction.
- Event publisher unavailable.

## Quan sát production

- Order creation latency.
- Failed transaction count.
- Stock mismatch alerts.
- Outbox processing metrics.

# Code Review Challenge 2 — HttpClient và cancellation trong background worker

**Chủ đề:** HTTP client usage, async, resource lifetime
**Độ khó:** Senior
**Thời gian review đề xuất:** 20 phút
**Số vấn đề cần tìm:** Khoảng 5 vấn đề

## Bối cảnh

Một BackgroundService đồng bộ dữ liệu Microsoft Graph mỗi 5 phút. Production có dấu hiệu socket tăng, memory tăng và shutdown service chậm.

## Đoạn code cần review

```csharp
public class GraphSyncWorker : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            var client = new HttpClient();
            client.DefaultRequestHeaders.Add("Authorization", GetToken());

            var response = await client.GetAsync(
                "https://graph.microsoft.com/v1.0/users");

            var json = await response.Content.ReadAsStringAsync();
            await SaveUsers(json);

            await Task.Delay(TimeSpan.FromMinutes(5));
        }
    }
}
```

## Nhiệm vụ của ứng viên

Review correctness, runtime behavior, resource usage, failure handling và production readiness.

## Câu hỏi gợi mở

- HttpClient lifetime có vấn đề gì?
- CancellationToken được xử lý chưa?
- Điều gì xảy ra khi Graph timeout?
- Worker shutdown như thế nào?

## Gợi ý

### Gợi ý 1
Xem xét resource lifetime và graceful shutdown.

### Gợi ý 2
Kiểm tra connection pooling, cancellation và retry strategy.

## Kết quả code review tham khảo

### 1. Tạo HttpClient liên tục
- Problem: Socket exhaustion và connection không tối ưu.
- Severity: High
- Fix: IHttpClientFactory.

### 2. Bỏ qua cancellation
- Problem: Worker không dừng đúng cách.
- Severity: High
- Fix: truyền stoppingToken.

### 3. Không xử lý timeout và retry
- Problem: External API failure làm job chết.
- Severity: Medium
- Fix: timeout policy, retry có kiểm soát.

## Phiên bản đề xuất

```csharp
public class GraphSyncWorker : BackgroundService
{
    private readonly HttpClient _client;

    protected override async Task ExecuteAsync(CancellationToken token)
    {
        while (!token.IsCancellationRequested)
        {
            using var response = await _client.GetAsync(
                "users", token);

            response.EnsureSuccessStatusCode();
            await SaveUsers(await response.Content.ReadAsStringAsync(token));

            await Task.Delay(TimeSpan.FromMinutes(5), token);
        }
    }
}
```

## Cách kiểm thử

- Shutdown worker while request running.
- Graph timeout simulation.
- High frequency sync load.
- Network failure recovery.

## Quan sát production

- HTTP failure rate.
- Sync duration.
- Worker restart count.
- Memory and socket metrics.
