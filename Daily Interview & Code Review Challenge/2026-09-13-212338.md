# Code Review Challenge 1 — API export báo cáo làm LOH/GC tăng mạnh dù CPU không cao

**Chủ đề:** C#/.NET 8, ASP.NET Core, memory allocation, LOH, `MemoryStream`, buffering, streaming, `ArrayPool<T>`, cancellation, response writing, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp endpoint export báo cáo CSV cho back-office. Mỗi report có thể từ vài MB tới hơn 200 MB. Dữ liệu được đọc từ SQL Server theo từng page và sau đó trả về browser.

Production có các triệu chứng:

- memory working set tăng mạnh khi nhiều user export đồng thời;
- GC pause tăng, Gen 2 collection xuất hiện thường xuyên hơn;
- một số instance App Service bị recycle do memory pressure;
- CPU chỉ ở mức trung bình nên team ban đầu nghĩ vấn đề nằm ở SQL;
- endpoint có p95 tăng rất mạnh khi 5–10 export lớn chạy cùng lúc;
- client hủy download nhưng server vẫn tiếp tục build toàn bộ report;
- logs chỉ ghi tổng thời gian request, không có allocation/size/concurrency context;
- team đề xuất tăng memory tier và giữ nguyên implementation.

Business requirements:

- report phải bắt đầu download sớm thay vì đợi build toàn bộ file trong memory;
- không cần giữ toàn bộ CSV trong RAM;
- nếu client disconnect thì server nên ngừng work càng sớm càng tốt;
- dữ liệu phải được ghi đúng thứ tự;
- implementation phải dễ quan sát và dễ load test;
- không cần thêm distributed system nếu streaming trong cùng request đã đủ.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        AppDbContext db,
        ILogger<ReportsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("orders.csv")]
    public async Task<IActionResult> ExportOrders(
        DateTime from,
        DateTime to)
    {
        var rows = await _db.Orders
            .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
            .OrderBy(x => x.Id)
            .Select(x => new
            {
                x.Id,
                x.CustomerName,
                x.Status,
                x.Total,
                x.CreatedAt
            })
            .ToListAsync();

        using var output = new MemoryStream();
        using var writer = new StreamWriter(output, Encoding.UTF8, leaveOpen: true);

        await writer.WriteLineAsync("Id,CustomerName,Status,Total,CreatedAt");

        foreach (var row in rows)
        {
            var line = string.Join(",",
                row.Id,
                row.CustomerName,
                row.Status,
                row.Total,
                row.CreatedAt);

            await writer.WriteLineAsync(line);
        }

        await writer.FlushAsync();

        var bytes = output.ToArray();

        _logger.LogInformation(
            "Generated report with {Rows} rows and {Bytes} bytes",
            rows.Count,
            bytes.Length);

        return File(bytes, "text/csv", "orders.csv");
    }
}
```

6. Đề xuất implementation streaming dữ liệu trực tiếp ra response mà không giữ toàn bộ file trong memory.
7. Đề xuất cách đọc database theo kiểu streaming/chunking phù hợp thay vì materialize toàn bộ dataset.

## Kết quả code review tham khảo

### Critical — Toàn bộ dataset được materialize bằng `ToListAsync()`

**Vấn đề:** Query đọc tất cả rows vào memory trước khi response bắt đầu.

**Tại sao xảy ra:** Code dùng materialization toàn bộ dataset thay vì streaming hoặc pagination/chunking.

**Ảnh hưởng production:** Memory tăng theo số rows và số export concurrent; time-to-first-byte cũng tăng vì browser phải chờ query hoàn tất.

**Cách sửa:** Dùng projection + `AsNoTracking()` và stream với `AsAsyncEnumerable()` khi query/provider phù hợp, hoặc đọc theo chunk/keyset pagination để kiểm soát memory và connection lifetime.

### Critical — Buffer toàn bộ CSV trong `MemoryStream`

**Vấn đề:** Report được build hoàn toàn trong RAM trước khi gửi.

**Tại sao xảy ra:** Endpoint chọn buffered response dù requirement cho phép streaming.

**Ảnh hưởng production:** Report 200 MB gần tương đương một large managed buffer 200 MB, chưa kể object graph và temporary strings. Nhiều request đồng thời tạo memory spikes rất lớn.

**Cách sửa:** Ghi trực tiếp vào `Response.Body` hoặc `Response.BodyWriter`, set headers trước rồi stream từng row.

### Critical — `ToArray()` tạo thêm một copy lớn

**Vấn đề:** Sau khi đã có internal buffer trong `MemoryStream`, code gọi `ToArray()` để tạo thêm `byte[]` chứa toàn bộ nội dung.

**Tại sao xảy ra:** `ToArray()` trả về một copy của stream contents.

**Ảnh hưởng production:** Trong một khoảng thời gian, cả internal buffer và returned array cùng sống; memory peak cao hơn đáng kể.

**Cách sửa:** Không build report vào `MemoryStream`; stream trực tiếp. Nếu buộc phải buffer, tránh duplicate copy và cân nhắc giới hạn kích thước/concurrency.

### High — Large buffers tạo pressure lên LOH và Gen 2 GC

**Vấn đề:** Các buffer lớn vượt xa ngưỡng large-object allocation thông thường và sống đủ lâu trong request lớn.

**Tại sao xảy ra:** Mỗi report tạo large arrays/stream buffers; concurrent exports tăng số live large objects.

**Ảnh hưởng production:** Gen 2/LOH collections tốn chi phí cao hơn, memory fragmentation/working set pressure tăng và có thể kích hoạt recycle/OOM behavior tùy host limits.

**Cách sửa:** Giảm large allocations bằng streaming/chunking; đo allocations, heap size, Gen 2 collections và working set trước/sau thay đổi.

### High — Không propagate request cancellation

**Vấn đề:** `ToListAsync`, writing và generation không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Action không nhận `CancellationToken` và downstream calls không truyền token.

**Ảnh hưởng production:** Browser đóng kết nối nhưng SQL/query/CSV generation vẫn tiêu tốn CPU, memory và DB connection.

**Cách sửa:** Nhận `CancellationToken cancellationToken` hoặc dùng `HttpContext.RequestAborted`; truyền xuống EF Core và response writes.

### High — CSV escaping không đúng

**Vấn đề:** `string.Join` không escape comma, quote, newline.

**Tại sao xảy ra:** CSV được coi như text đơn giản.

**Ảnh hưởng production:** Dữ liệu lệch cột hoặc tạo file không parse được; dữ liệu bắt đầu bằng `=`, `+`, `-`, `@` còn có thể cần xem xét CSV/Spreadsheet formula injection tùy nơi mở file.

**Cách sửa:** Dùng một CSV writer/library đáng tin cậy hoặc implement escaping đúng chuẩn: quote field khi cần và duplicate quote characters. Nếu file thường được mở bằng spreadsheet, áp dụng policy cho formula injection theo threat model.

### Medium — Mỗi row tạo thêm string trung gian

**Vấn đề:** `string.Join` tạo line string rồi `StreamWriter` encode sang bytes.

**Tại sao xảy ra:** Formatting dựa trên intermediate string.

**Ảnh hưởng production:** Allocation rate tăng đáng kể với hàng trăm nghìn rows.

**Cách sửa:** Dùng CSV writer có buffering hợp lý hoặc viết field trực tiếp vào writer; tối ưu thêm chỉ sau khi đo allocation profile.

### Medium — Culture-sensitive formatting có thể làm CSV không ổn định

**Vấn đề:** `decimal` và `DateTime` được format theo culture mặc định.

**Tại sao xảy ra:** `string.Join` gọi `ToString()` implicit.

**Ảnh hưởng production:** Decimal separator/date format có thể khác theo environment, làm file khó parse nhất quán.

**Cách sửa:** Dùng `CultureInfo.InvariantCulture` và format contract rõ ràng, ví dụ ISO-8601 cho timestamp.

### Medium — Không giới hạn concurrency của expensive export

**Vấn đề:** Bất kỳ số lượng request nào cũng có thể chạy export nặng cùng lúc.

**Tại sao xảy ra:** Endpoint không có application-level capacity policy.

**Ảnh hưởng production:** Một burst export có thể gây pressure lên DB, memory và network.

**Cách sửa:** Sau khi streaming, nếu workload vẫn nặng hãy cân nhắc rate limit/concurrency limit per user/tenant hoặc chuyển sang async export job khi business cần report cực lớn. Không nên thêm queue chỉ vì implementation hiện tại buffer kém.

### Low — Observability thiếu dữ liệu để phân biệt SQL chậm với memory pressure

**Vấn đề:** Log chỉ có rows/bytes cuối request.

**Tại sao xảy ra:** Không instrument từng phase và resource pressure.

**Ảnh hưởng production:** Dễ kết luận sai root cause.

**Cách sửa:** Theo dõi query duration, time-to-first-byte, rows streamed, bytes written, request-aborted, active exports, allocation/GC/memory metrics và response duration.

## Phiên bản đề xuất

Một hướng đơn giản là stream projection ra response. Ví dụ:

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;

    public ReportsController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet("orders.csv")]
    public async Task ExportOrders(
        DateTime from,
        DateTime to,
        CancellationToken cancellationToken)
    {
        Response.ContentType = "text/csv; charset=utf-8";
        Response.Headers.ContentDisposition =
            "attachment; filename=orders.csv";

        await using var writer = new StreamWriter(
            Response.Body,
            new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
            bufferSize: 16 * 1024,
            leaveOpen: true);

        await writer.WriteLineAsync(
            "Id,CustomerName,Status,Total,CreatedAt".AsMemory(),
            cancellationToken);

        var query = _db.Orders
            .AsNoTracking()
            .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
            .OrderBy(x => x.Id)
            .Select(x => new
            {
                x.Id,
                x.CustomerName,
                x.Status,
                x.Total,
                x.CreatedAt
            })
            .AsAsyncEnumerable();

        await foreach (var row in query.WithCancellation(cancellationToken))
        {
            await WriteCsvFieldAsync(writer, row.Id.ToString(CultureInfo.InvariantCulture), cancellationToken);
            await writer.WriteAsync(",".AsMemory(), cancellationToken);
            await WriteCsvFieldAsync(writer, row.CustomerName, cancellationToken);
            await writer.WriteAsync(",".AsMemory(), cancellationToken);
            await WriteCsvFieldAsync(writer, row.Status, cancellationToken);
            await writer.WriteAsync(",".AsMemory(), cancellationToken);
            await WriteCsvFieldAsync(writer, row.Total.ToString(CultureInfo.InvariantCulture), cancellationToken);
            await writer.WriteAsync(",".AsMemory(), cancellationToken);
            await WriteCsvFieldAsync(writer, row.CreatedAt.ToString("O", CultureInfo.InvariantCulture), cancellationToken);
            await writer.WriteLineAsync(ReadOnlyMemory<char>.Empty, cancellationToken);
        }

        await writer.FlushAsync(cancellationToken);
    }

    private static async Task WriteCsvFieldAsync(
        TextWriter writer,
        string? value,
        CancellationToken cancellationToken)
    {
        value ??= string.Empty;

        var mustQuote = value.Contains(',') ||
                        value.Contains('"') ||
                        value.Contains('\n') ||
                        value.Contains('\r');

        if (!mustQuote)
        {
            await writer.WriteAsync(value.AsMemory(), cancellationToken);
            return;
        }

        await writer.WriteAsync("\"".AsMemory(), cancellationToken);
        await writer.WriteAsync(value.Replace("\"", "\"\"").AsMemory(), cancellationToken);
        await writer.WriteAsync("\"".AsMemory(), cancellationToken);
    }
}
```

Đây là minh họa. Production code nên ưu tiên CSV library đã được kiểm thử tốt thay vì tự duy trì parser/writer phức tạp. `AsAsyncEnumerable()` giữ một database reader sống trong quá trình streaming, vì vậy cần xem xét connection duration, timeout và ảnh hưởng khi client download rất chậm. Với report dài, chunked/keyset pagination có thể là lựa chọn tốt hơn để nhả connection giữa các chunks.

`ArrayPool<T>` có thể hữu ích khi code thật sự cần temporary buffers lớn/được reuse thường xuyên, nhưng không giải quyết việc materialize toàn bộ dataset hay buffer toàn bộ output. Trước tiên sửa data flow, sau đó profile allocation hotspots còn lại.

## Giải thích thiết kế sau khi sửa

Thiết kế mới bắt đầu gửi response sớm và giữ memory gần với kích thước buffer nhỏ + một số row objects hiện tại thay vì toàn bộ report.

`AsNoTracking()` phù hợp vì export là read-only. Cancellation được propagate từ HTTP request xuống query và writer.

CSV formatting được xử lý theo contract thay vì implicit culture. Nếu business mở file bằng Excel hoặc tương tự, cần thêm policy riêng cho formula injection thay vì trộn logic đó vào escaping cơ bản.

Streaming trực tiếp không mặc định là tối ưu cho mọi report. Nếu user cần download lại nhiều lần, report generation kéo dài hàng chục phút hoặc cần retry độc lập với HTTP connection, async job + Blob Storage có thể hợp lý hơn. Nhưng đó là architecture decision dựa trên requirement, không phải fix mặc định cho một endpoint đang buffer sai.

## Trade-offs

Streaming giữ HTTP connection lâu hơn và có thể giữ DB reader lâu nếu dùng `AsAsyncEnumerable()`. Client chậm có thể kéo dài connection lifetime.

Chunking giảm connection lifetime nhưng tăng số round trips và cần pagination ổn định. Keyset pagination thường phù hợp hơn `OFFSET` với deep ranges, nhưng cần sort key ổn định.

CSV library thêm dependency nhưng giảm risk correctness. Custom writer ít dependency hơn nhưng cần test kỹ edge cases.

Rate limiting/concurrency limiting có thể bảo vệ hệ thống nhưng cần cân bằng UX: một user legitimate export nhiều report không nên bị chặn tùy tiện.

## Cách kiểm thử

1. **Load test:** chạy 1, 5, 10 export lớn đồng thời; so sánh working set, GC pause, Gen 2 count, allocation rate và p95 trước/sau.
2. **Cancellation test:** đóng client connection giữa export; xác minh query/writing dừng sớm và active export count giảm.
3. **CSV correctness test:** tên chứa comma, quote, CR/LF, Unicode và empty/null values phải parse đúng.
4. **Large dataset integration test:** export hàng trăm nghìn rows; xác minh memory không tăng tuyến tính theo file size.
5. **Slow-client test:** throttle download; đo DB connection duration và quyết định streaming reader hay chunking phù hợp hơn.

## Quan sát trong production

Theo dõi:

- active export count;
- requested date range;
- rows streamed và bytes written;
- time-to-first-byte;
- total duration p50/p95/p99;

# Code Review Challenge 2 — Optimizely publish đúng nhưng Akamai vẫn phục vụ page cũ sau purge

**Chủ đề:** Optimizely CMS, CMS caching, Akamai CDN, `Cache-Control`, cache key, purge/invalidation, content publish/unpublish, stale content, third-party dependency, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một marketing website chạy ASP.NET Core + Optimizely CMS phía sau Akamai. Editors publish landing pages nhiều lần trong ngày.

Caching hiện có ba lớp:

1. Optimizely/application cache tại origin;
2. Akamai edge cache;
3. browser cache.

Production có các triệu chứng:

- editor publish xong thấy nội dung mới khi truy cập trực tiếp origin, nhưng user ngoài Internet vẫn thấy page cũ;
- purge endpoint trả `200`, nhưng một số regions vẫn phục vụ stale content trong vài phút;
- cùng URL nhưng query string tracking như `?utm_source=x` đôi lúc tạo cache entries khác nhau;
- page dành cho authenticated preview thỉnh thoảng bị cache sai tại edge;
- `Cache-Control` được set giống nhau cho mọi request;
- một developer đề xuất set `max-age=86400` cho tất cả pages rồi purge mỗi lần publish;
- một developer khác đề xuất bypass CDN hoàn toàn cho CMS pages;
- logs không ghi cache key, purge id, content version hoặc `Age`/cache status headers;
- unpublish một page đôi lúc vẫn cho user truy cập nội dung cũ ở edge.

Business requirements:

- public published content có thể cache mạnh;
- preview/authenticated content không được public-cache;
- publish/unpublish phải converge nhanh và có observability;
- tracking query parameters không nên nhân bản cache nếu chúng không thay đổi response;
- purge failure phải được phát hiện và retry có kiểm soát;
- không cần loại bỏ CDN nếu có thể thiết kế cache contract đúng.

## Đoạn configuration/code cần review

```csharp
app.Use(async (context, next) =>
{
    context.Response.Headers.CacheControl = "public,max-age=86400";
    await next();
});

app.MapGet("/akamai/purge", async (
    HttpContext context,
    IAkamaiClient akamai,
    string url) =>
{
    await akamai.PurgeAsync(url, CancellationToken.None);
    return Results.Ok();
});

public sealed class ContentPublishedHandler
{
    private readonly IAkamaiClient _akamai;
    private readonly ILogger<ContentPublishedHandler> _logger;

    public ContentPublishedHandler(
        IAkamaiClient akamai,
        ILogger<ContentPublishedHandler> logger)
    {
        _akamai = akamai;
        _logger = logger;
    }

    public async Task HandleAsync(
        string publicUrl,
        int contentId,
        CancellationToken cancellationToken)
    {
        try
        {
            await _akamai.PurgeAsync(publicUrl, CancellationToken.None);

            _logger.LogInformation(
                "Purged {Url} after publish of content {ContentId}",
                publicUrl,
                contentId);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(
                ex,
                "Purge failed for {Url}",
                publicUrl);
        }
    }
}
```

Akamai cache key hiện giữ nguyên toàn bộ query string.

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề security, cache correctness, invalidation, retry và observability.
2. Phân tích vì sao middleware set `public,max-age=86400` cho mọi response nguy hiểm với preview/authenticated pages.
3. Giải thích vì sao purge response thành công không đồng nghĩa mọi edge node đã lập tức phục vụ version mới.
4. Đánh giá cache key giữ toàn bộ query string khi `utm_*` không làm thay đổi response.
5. Phân tích unpublish flow: tại sao stale edge object có thể tiếp tục được phục vụ nếu origin đã trả 404.
6. Đề xuất cache policy khác nhau cho public published content, authenticated preview và error responses.
7. Đề xuất purge/invalidation workflow có retry, idempotency và telemetry.
8. Giải thích khi nào versioned URLs/cache-busting phù hợp và khi nào không thể áp dụng cho canonical page URLs.
9. Nêu cách verify end-to-end rằng publish/unpublish đã converge ngoài edge, không chỉ origin.
10. Đánh giá hai cực đoan: TTL 24h + purge cho mọi thứ vs bypass CDN toàn bộ CMS.

## Câu hỏi gợi mở

1. Edge cache có biết request hiện tại là preview/authenticated nếu origin vẫn trả header `public` không?
2. Nếu `utm_source=a` và `utm_source=b` tạo hai cache keys nhưng HTML giống nhau, purge canonical URL đã đủ chưa?
3. `200` từ purge API thường xác nhận điều gì: request purge đã được nhận hay mọi edge đã invalidated xong?
4. Unpublish cần invalidation khác publish như thế nào khi stale content là security/compliance concern?
5. Header `Age`, cache-status/vendor headers và content version có giúp phân biệt origin cache với edge cache không?

## Gợi ý

### Gợi ý 1

Hãy tách rõ **cache eligibility**, **cache key**, **TTL**, và **invalidation**. Đây là bốn quyết định khác nhau.

### Gợi ý 2

Purge là distributed operation có delay/failure; correctness không nên dựa trên giả định “gọi API xong là toàn thế giới đã đổi”.

## Kết quả code review tham khảo

### Critical — Tất cả responses đều bị đánh dấu `public`

**Vấn đề:** Middleware set `Cache-Control: public,max-age=86400` trước khi biết response là public page, preview, authenticated content hay error.

**Tại sao xảy ra:** Cache policy được áp dụng globally thay vì dựa trên response/request classification.

**Ảnh hưởng production:** Personalized/preview content có thể bị shared edge cache lưu và phục vụ cho user khác, tạo data disclosure/correctness incident.

**Cách sửa:** Public-cache chỉ cho anonymous published content đáp ứng policy. Authenticated/preview responses nên dùng `private` hoặc `no-store` theo requirement, đồng thời cấu hình CDN bypass tương ứng.

### High — Purge handler nuốt lỗi và không có durable retry

**Vấn đề:** Exception chỉ được log warning, event publish vẫn kết thúc như thể invalidation đã hoàn tất.

**Tại sao xảy ra:** Purge bị coi như best-effort side effect không có retry state.

**Ảnh hưởng production:** Một transient Akamai/network failure có thể để content stale cho tới TTL expiry.

**Cách sửa:** Ghi purge request vào durable work state/outbox/job table hoặc queue hiện có, retry với backoff/jitter và giới hạn. Theo dõi pending age/failure count. Không nhất thiết phải thêm messaging platform mới nếu DB-backed retry đủ.

### High — `CancellationToken.None` bỏ qua lifecycle của publish operation

**Vấn đề:** Handler nhận token nhưng không truyền xuống purge call.

**Tại sao xảy ra:** Downstream call không tôn trọng cancellation contract.

**Ảnh hưởng production:** Deploy/shutdown hoặc cancelled operation có thể để request chạy ngoài expected lifetime; khó phân biệt retry-needed với abandoned work.

**Cách sửa:** Truyền token khi phù hợp. Nếu purge phải survive process cancellation, đừng cố giữ HTTP call sống bằng `None`; hãy persist work rồi để background processor thực hiện.

### High — Query-string cache key gây fragmentation với tracking parameters

**Vấn đề:** `utm_*` thay đổi cache key dù không thay đổi HTML.

**Tại sao xảy ra:** Cache key sử dụng raw URL thay vì normalized functional parameters.

**Ảnh hưởng production:** Hit ratio giảm, purge không đầy đủ, nhiều stale variants tồn tại.

**Cách sửa:** Chuẩn hóa cache key: bỏ các tracking parameters không ảnh hưởng content, nhưng giữ các parameters thật sự thay đổi response. Quy tắc phải explicit và test được.

### High — Unpublish không có stronger invalidation semantics

**Vấn đề:** Một object cached lâu có thể vẫn được edge phục vụ dù origin đã 404 sau unpublish.

**Tại sao xảy ra:** Edge có thể đáp ứng từ cache mà không revalidate origin cho tới khi object hết fresh hoặc bị purge.

**Ảnh hưởng production:** Nội dung đã bị gỡ vì pháp lý/compliance vẫn có thể truy cập.

**Cách sửa:** Unpublish phải trigger invalidation/purge có priority và alerting mạnh hơn; nếu requirement cần near-immediate removal, cấu hình TTL/revalidation strategy phải phản ánh SLO đó. Verify từ edge locations sau purge.

### Medium — Endpoint purge công khai theo URL input là nguy hiểm

**Vấn đề:** `/akamai/purge?url=...` không thể hiện authorization, validation hoặc allow-list.

**Tại sao xảy ra:** Operational control surface được expose như application endpoint đơn giản.

**Ảnh hưởng production:** Caller không hợp lệ có thể purge arbitrary URLs, gây cache churn hoặc abuse dependency credentials.

**Cách sửa:** Không expose như public endpoint; dùng authenticated admin/internal workflow, validate host/path, least privilege và audit actor/reason.

### Medium — TTL 24h cho mọi public page phụ thuộc quá mạnh vào perfect purge

**Vấn đề:** TTL dài không sai tự thân, nhưng khi purge là correctness mechanism duy nhất thì bất kỳ failure nào có blast radius dài.

**Tại sao xảy ra:** TTL và invalidation SLO không được thiết kế cùng nhau.

**Ảnh hưởng production:** Purge failure = stale content tới 24 giờ.

**Cách sửa:** Chọn TTL dựa trên acceptable staleness và purge reliability. Có thể dùng shorter TTL + purge để giảm worst-case stale window.

### Medium — Không version/cache metadata để verify content đang được phục vụ

**Vấn đề:** Logs chỉ có URL/contentId, không có content version/publish timestamp/purge request id.

**Tại sao xảy ra:** Observability không model cache lifecycle.

**Ảnh hưởng production:** Khi user báo stale content, khó biết stale ở origin cache, edge hay browser.

**Cách sửa:** Emit safe response header như content version/build marker cho public content, log purge id, target URLs/keys, request timestamp và observe `Age`/Akamai cache status headers.

### Medium — Browser caching chưa được phân biệt với edge caching

**Vấn đề:** `max-age=86400` áp dụng cho browser cache nữa.

**Tại sao xảy ra:** Một directive đang dùng cho cả shared và private caches mà không xem xét `s-maxage`/revalidation strategy.

**Ảnh hưởng production:** Edge purge có thể thành công nhưng browser vẫn giữ copy fresh cũ.

**Cách sửa:** Tách browser freshness và shared-cache freshness theo requirement, ví dụ shorter browser `max-age`, shared `s-maxage` dài hơn nếu phù hợp.

### Low — Log purge success quá sớm và thiếu correlation

**Vấn đề:** Log “Purged” ngay sau API call có thể bị hiểu là global invalidation completed.

**Tại sao xảy ra:** Log message không phản ánh distributed semantics.

**Ảnh hưởng production:** Operator kết luận sai trạng thái.

**Cách sửa:** Log “purge request accepted/submitted” cùng purge id/status; theo dõi completion/verification nếu provider/workflow hỗ trợ.

## Phiên bản đề xuất

Một hướng thiết kế là tách cache policy khỏi business event handler và persist purge work.

```csharp
app.Use(async (context, next) =>
{
    await next();

    var isAuthenticated = context.User.Identity?.IsAuthenticated == true;
    var isPreview = context.Request.Query.ContainsKey("preview");
    var isSuccess = context.Response.StatusCode == StatusCodes.Status200OK;

    if (isAuthenticated || isPreview)
    {
        context.Response.Headers.CacheControl = "private,no-store";
        return;
    }

    if (isSuccess)
    {
        context.Response.Headers.CacheControl =
            "public,max-age=60,s-maxage=600";
    }
    else
    {
        context.Response.Headers.CacheControl = "no-store";
    }
});
```

Trong production thực tế, header phải được quyết định trước khi response headers bị gửi; middleware/output-cache integration cần được đặt đúng chỗ trong pipeline. Đoạn trên chỉ minh họa policy classification, không phải copy-paste implementation hoàn chỉnh.

Publish handler nên enqueue/persist invalidation intent:

```csharp
public sealed class ContentPublishedHandler
{
    private readonly AppDbContext _db;

    public ContentPublishedHandler(AppDbContext db)
    {
        _db = db;
    }

    public async Task HandleAsync(
        string publicUrl,
        int contentId,
        long contentVersion,
        CancellationToken cancellationToken)
    {
        _db.CdnInvalidations.Add(new CdnInvalidation
        {
            Id = Guid.NewGuid(),
            Url = publicUrl,
            ContentId = contentId,
            ContentVersion = contentVersion,
            Status = CdnInvalidationStatus.Pending,
            CreatedAt = DateTimeOffset.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Background processor sau đó gọi Akamai với retry policy, ghi `SubmittedAt`, provider request id, last error và completion/verification state nếu workflow hỗ trợ. Duplicate publish events nên coalesce/idempotent theo normalized cache key/content version khi có thể.

Cache key policy tại Akamai nên bỏ `utm_source`, `utm_campaign` và tracking parameters tương tự nếu chúng không ảnh hưởng response, nhưng phải giữ parameters có semantic thực sự như language/variant/filter khi HTML thay đổi.

Unpublish nên tạo invalidation work với priority/severity cao hơn và có alert nếu chưa converge trong SLO. Nếu legal removal cần rất nhanh, TTL và fail-safe cache behavior phải được thiết kế theo requirement đó.

## Giải thích thiết kế sau khi sửa

Public anonymous content tận dụng CDN; preview/authenticated content không đi vào shared cache. Đây là cache eligibility decision trước khi bàn TTL.

Cache key được chuẩn hóa để tránh fragmentation. Purge workflow được persist, vì một distributed side effect quan trọng không nên mất chỉ vì process restart hoặc dependency timeout.

TTL không được coi là “càng dài càng tốt”. Nó đặt upper bound cho staleness khi invalidation thất bại, vì vậy phải gắn với business SLO.

Không bypass CDN toàn bộ chỉ vì invalidation đang yếu. CDN vẫn có giá trị lớn cho marketing website; sửa cache contract thường tốt hơn loại bỏ caching.

## Trade-offs

Shorter TTL giảm worst-case staleness nhưng tăng origin load và giảm hit ratio.

Durable invalidation job tăng schema/background-processing complexity nhưng đổi lại có retry/audit/visibility. Nếu hệ thống đã có Service Bus hoặc job infrastructure, có thể reuse; nếu không, DB table + worker có thể đủ.

Normalized query-string key tăng hit ratio nhưng nếu bỏ nhầm parameter có ảnh hưởng nội dung thì có thể phục vụ sai variant. Vì vậy allow-list/deny-list cần test với Product/Marketing requirements.

Public content version header hữu ích cho debug nhưng phải tránh lộ internal sensitive metadata.

## Cách kiểm thử

1. **Cache-policy integration test:** anonymous published page có shared-cache headers; authenticated/preview page phải `private/no-store` và không cache tại edge.
2. **Query normalization test:** `?utm_source=a` và `?utm_source=b` map cùng cache object nếu response thật sự giống nhau; functional parameters vẫn tạo variant riêng.
3. **Publish failure-path test:** Akamai trả 5xx/timeout; invalidation vẫn ở durable pending/retry state, không bị mất.
4. **Unpublish E2E test:** warm edge cache, unpublish content, trigger invalidation và verify từ edge rằng canonical URL không còn trả stale body trong SLO.
5. **Browser-vs-edge test:** xác minh browser freshness không che khuất kết quả purge edge; inspect `Age`/cache-status/content-version headers.

## Quan sát trong production

Theo dõi:

- CDN cache hit ratio;
- origin request rate;
- purge requests submitted/succeeded/failed;
- pending invalidation age;
- purge retry count;

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory problem thường nằm ở **data path và live object size**, không phải CPU.
- `ToListAsync()` + `MemoryStream` + `ToArray()` có thể tạo nhiều copies/layers cùng sống và làm LOH/Gen 2 pressure tăng mạnh.
- Streaming nên được thiết kế end-to-end: database → serializer/writer → HTTP response → cancellation.
- CDN correctness gồm bốn phần độc lập: cache eligibility, cache key, TTL và invalidation.
- Purge là distributed side effect có thể chậm hoặc thất bại; cần retry, idempotency và observability.
- Preview/authenticated content không được chia sẻ chung cache policy với public anonymous content.

## Mẫu tư duy cần nhớ

- **Trace the full data path before optimizing memory.**
- **Measure allocations and concurrency, not only CPU.**
- **Stream when buffering adds no business value.**
- **Cache only what is explicitly eligible for shared caching.**
- **Design invalidation as a failure-prone distributed workflow.**
