# Câu 1 — EF Core optimistic concurrency: vì sao `SaveChangesAsync` có thể thất bại dù row vẫn tồn tại?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** EF Core, change tracking, optimistic concurrency, SQL, transaction reasoning

## Bối cảnh

Một ASP.NET Core approval API dùng EF Core và SQL Server. Hai managers có thể mở cùng một approval request. UI gửi `Id`, dữ liệu chỉnh sửa và concurrency token. Production thỉnh thoảng nhận concurrency exception khi hai người thao tác gần nhau. Một developer đề xuất catch exception rồi gọi `SaveChangesAsync` lại ngay vì “row vẫn tồn tại nên retry sẽ thành công”.

## Câu hỏi chính

Bạn giải thích internal mechanism của optimistic concurrency trong EF Core như thế nào, vì sao một update có thể dẫn tới concurrency exception dù row vẫn tồn tại, và retry đúng phải phụ thuộc vào business semantics ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. Concurrency token là SQL Server `rowversion` hay application-managed token?
2. Business cho phép last-write-wins hay cần user resolve conflict?
3. Những fields nào có thể merge độc lập và fields nào đại diện business invariant?
4. Request có giữ DbContext lâu hay mỗi HTTP request dùng một context ngắn?

## Gợi ý tư duy

### Gợi ý 1

Hãy nghĩ về SQL predicate của `UPDATE`, không chỉ entity state trong memory.

### Gợi ý 2

Concurrency token thường tham gia điều kiện update; số rows affected là tín hiệu quan trọng.

### Gợi ý 3

Retry kỹ thuật không tự giải quyết conflict business. Cần quyết định database values, client values hay merge.

## Cấu trúc trả lời đề xuất

1. Làm rõ concurrency token và business policy.
2. Giải thích original/current values trong change tracker.
3. Mô tả SQL update có predicate theo key + token.
4. Giải thích zero affected rows và concurrency exception.
5. Phân loại conflict và lựa chọn reload/reject/merge/retry.
6. Test concurrent updates và quan sát telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Optimistic concurrency không khóa row từ lúc đọc đến lúc ghi.
- EF Core dùng concurrency token để phát hiện dữ liệu đã thay đổi kể từ lúc entity được đọc.
- Row có thể vẫn tồn tại nhưng token không còn khớp, nên update ảnh hưởng 0 row.
- Blind retry có thể tiếp tục fail hoặc vô tình ghi đè dữ liệu mới.
- Conflict handling phải theo business semantics.

### Điểm cộng

- Phân biệt original values, current values và database values.
- Đề xuất trả `409 Conflict`/representation phù hợp cho API khi user cần resolve.
- Nhắc đến transaction boundary và tránh DbContext sống quá lâu.

### Senior+

- Phân biệt technical concurrency conflict với business invariant conflict.
- Thiết kế merge theo field khi an toàn thay vì generic last-write-wins.
- Telemetry phân biệt conflict bình thường với retry storm hoặc UI workflow lỗi.

## Hướng giải quyết tham khảo

Khi entity có concurrency token, EF Core giữ original token lúc query. Khi update, generated SQL thường dùng primary key và original concurrency token trong predicate. Nếu một transaction khác đã cập nhật row, token trong database thay đổi. Row vẫn tồn tại, nhưng predicate cũ không match nên affected row count bằng 0 và EF Core báo optimistic concurrency conflict.

Catch rồi gọi lại `SaveChangesAsync` mà không thay đổi state không phải chiến lược đúng. Cần đọc database values và áp dụng policy. Nếu business yêu cầu user không được ghi đè thay đổi của người khác, API nên trả conflict với dữ liệu/version hiện tại để client reload hoặc resolve. Nếu một số fields merge độc lập, có thể merge có chủ đích, refresh original token rồi thử lại. Last-write-wins chỉ hợp lệ khi business chấp nhận mất update trước đó.

Testing nên tạo hai DbContext độc lập đọc cùng version, commit context A rồi commit context B và xác minh conflict. Theo dõi concurrency-conflict rate theo endpoint/entity; spike bất thường có thể chỉ ra UI gửi stale token hoặc retry policy sai.

## Mẫu trả lời trong phỏng vấn

“Optimistic concurrency không giữ lock trong toàn bộ thời gian user chỉnh sửa. EF Core nhớ concurrency token lúc entity được đọc. Khi save, update không chỉ match theo Id mà còn theo original token. Nếu người khác đã update trước, row vẫn còn nhưng token đổi, nên update của tôi match zero rows và EF Core báo concurrency conflict.

Tôi không blind retry vì token cũ vẫn sai, và nếu reload rồi ghi đè tự động thì có thể biến conflict thành lost update. Tôi sẽ hỏi business muốn reject, last-write-wins hay merge. Với approval data quan trọng, tôi thường trả conflict và current version cho client; nếu fields merge được thì merge explicit rồi retry với token mới.

Tôi test bằng hai DbContext độc lập và theo dõi conflict rate. Nếu conflict tăng đột biến, tôi kiểm tra client token flow trước khi coi đó là lỗi database.”

## Câu hỏi đào sâu

1. Nếu entity không dùng SQL Server `rowversion`, bạn có thể quản lý token ở application như thế nào?
2. Nếu requirement nói “mọi update đều tự retry tối đa 3 lần”, bạn phản biện điều gì?
3. Concurrency conflict khác deadlock/transient database failure ở điểm nào về retry strategy?

## Lỗi trả lời thường gặp

- Cho rằng concurrency exception nghĩa là row đã bị delete.
- Blind retry mà không refresh/resolve values.
- Luôn chọn last-write-wins.
- Nhầm optimistic concurrency với database locking dài hạn.

## Thang điểm 0–10

- **0–2:** Chỉ biết catch exception.
- **3–4:** Biết token nhưng chưa giải thích SQL/affected rows.
- **5–6:** Giải thích đúng mechanism và conflict handling.
- **7–8:** Có business semantics, API behavior, tests và telemetry.
- **9–10:** Phân biệt rõ technical/business conflict và đưa strategy có điều kiện rất tốt.

# Câu 2 — Azure Function backlog tăng và DLQ đầy sau khi dependency chập chờn

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Functions, Azure Service Bus, retry, poison work, idempotency, observability, incident response

## Bối cảnh

Một Azure Function xử lý file-processing requests từ Azure Service Bus. Function đọc metadata, gọi một third-party scanning API rồi cập nhật SQL Server. Sau một giờ dependency timeout, active message count tăng nhanh, DLQ bắt đầu tăng và một số users thấy trạng thái file bị cập nhật nhiều lần. Dependency hiện đã hồi phục nhưng backlog vẫn giảm rất chậm.

Team đề xuất tăng concurrency và retry count ngay để “drain queue nhanh hơn”. Chưa rõ bottleneck hiện tại là dependency, database, Function concurrency hay poison messages.

## Câu hỏi chính

Bạn sẽ stabilize, điều tra và phục hồi incident này theo thứ tự nào, đồng thời tránh việc tăng concurrency/retry làm dependency overload hoặc khuếch đại duplicate side effects?

## Câu hỏi làm rõ nên cân nhắc

1. Delivery count, active count, DLQ reason và message age hiện tại thế nào?
2. Third-party API có rate limit và idempotency contract không?
3. SQL update có unique/business invariant nào bảo vệ duplicate processing không?
4. Function processing time, failure rate và dependency latency thay đổi theo concurrency thế nào?
5. Poison messages là permanent contract errors hay transient failures bị exhaust retries?

## Gợi ý tư duy

### Gợi ý 1

Backlog là symptom; tăng consumers chỉ đúng nếu downstream còn capacity.

### Gợi ý 2

Tách transient failure, permanent poison work và ambiguous side effect.

### Gợi ý 3

Dùng queue depth/message age cùng dependency latency/error và processing throughput để tìm bottleneck.

## Cấu trúc trả lời đề xuất

1. Đánh giá user/business impact.
2. Ngăn amplification và bảo vệ dependency.
3. Thu queue/function/dependency/database telemetry.
4. Lập nhiều hypotheses.
5. Phân loại retryable vs poison.
6. Xác minh idempotency và duplicate effects.
7. Điều chỉnh concurrency/retry có kiểm soát.
8. Drain/replay DLQ theo policy.
9. Verify recovery.
10. Prevention và failure tests.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng concurrency/retry trước khi biết downstream capacity.
- Theo dõi queue depth, oldest message age, delivery count, DLQ reason, Function duration/error và dependency latency.
- Retry phải bounded và đi cùng idempotency.
- Permanent invalid messages cần poison/DLQ handling khác transient failures.
- DLQ replay phải có kiểm soát, không bulk replay mù quáng.

### Điểm cộng

- Dùng load shedding/backoff/circuit behavior phù hợp để bảo vệ dependency.
- Reconciliation cho ambiguous timeout khi external side effect có thể đã xảy ra.
- Correlate message ID, business operation ID và dependency request ID.

### Senior+

- Tính drain rate dựa trên arrival rate vs successful service rate thay vì chỉ nhìn queue count.
- Điều chỉnh concurrency theo measured downstream saturation.
- Thiết kế runbook cho DLQ classification/replay và alerts theo message age.

## Hướng giải quyết tham khảo

Đầu tiên xác định impact và ngăn hệ thống tiếp tục làm dependency xấu hơn. Nếu third-party vừa hồi phục nhưng vẫn fragile, tăng concurrency có thể gây relapse. Quan sát active count, oldest-message age, enqueue/dequeue rate, delivery count, DLQ reasons, Function duration/error, dependency p95/p99 và SQL latency.

Các hypotheses gồm dependency vẫn chậm, Function concurrency thấp, SQL bottleneck, retry storm, hoặc một nhóm poison messages liên tục tiêu tốn capacity. Phân loại permanent contract errors để dead-letter sớm theo policy; transient failures dùng bounded retry/backoff. Với timeout có outcome không xác định, cần idempotency key hoặc reconciliation trước khi retry external side effect.

Nếu telemetry chứng minh dependency và SQL còn headroom, tăng concurrency từng bước và theo dõi successful throughput/error. Drain rate chỉ dương khi successful processing rate lớn hơn incoming rate. DLQ không replay toàn bộ ngay; sample/classify, fix cause, xác minh idempotency rồi replay theo batch có rate control.

Sau recovery, thêm alerts cho oldest message age, DLQ growth, retry/delivery count và dependency failure. Test dependency timeout, poison payload, duplicate delivery và controlled replay.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tăng concurrency ngay. Backlog có thể do downstream saturation; thêm workers có thể làm dependency vừa hồi phục lại quá tải.

Tôi bắt đầu bằng impact và telemetry: active/DLQ count, oldest message age, delivery count, Function throughput/duration, dependency p95/error và SQL latency. Tôi phân loại failures thành transient, permanent poison và ambiguous timeout. Permanent invalid messages không nên retry nhiều; transient failures cần bounded backoff; ambiguous external side effect cần idempotency hoặc reconciliation.

Sau khi biết downstream còn headroom, tôi mới tăng concurrency theo bước và quan sát successful service rate. Queue chỉ drain nếu processing thành công nhanh hơn arrival rate. Với DLQ, tôi không replay hàng loạt; tôi xác định reason, fix, kiểm tra duplicate safety rồi replay controlled batches.

Cuối cùng tôi thêm alert theo message age/DLQ growth và failure-injection tests để runbook lần sau rõ ràng hơn.”

## Câu hỏi đào sâu

1. Queue depth đang giảm nhưng oldest-message age vẫn tăng có thể gợi ý điều gì?
2. Nếu scanning API không hỗ trợ idempotency, bạn xử lý timeout có outcome không xác định ra sao?
3. Team muốn tăng concurrency gấp 10 vì CPU Function thấp; bạn cần evidence nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- Tăng concurrency/retry như phản xạ đầu tiên.
- Replay toàn bộ DLQ ngay khi dependency hồi phục.
- Không phân biệt poison và transient failure.
- Dùng CPU Function làm capacity indicator duy nhất.
- Bỏ qua duplicate side effect.

## Thang điểm 0–10

- **0–2:** Chỉ scale/retry.
- **3–4:** Có queue metrics nhưng thiếu failure classification.
- **5–6:** Có stabilization, telemetry, DLQ và retry hợp lý.
- **7–8:** Có idempotency, controlled drain/replay và downstream capacity reasoning.
- **9–10:** Incident reasoning hoàn chỉnh với service-rate analysis, failure semantics và prevention mạnh.

# Câu 3 — Thiết kế large-file upload: proxy qua ASP.NET Core hay direct-to-Blob?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, security, Managed Identity, SAS, large-file streaming, reliability, architecture trade-offs

## Bối cảnh

Một enterprise portal cần cho users upload tài liệu từ 10 MB đến vài GB. Hiện tại mọi file đi qua ASP.NET Core API rồi được copy vào storage. Khi traffic tăng, App Service memory/network pressure tăng và uploads lớn dễ fail khi request bị gián đoạn.

Team cân nhắc direct upload từ browser lên Azure Blob Storage bằng short-lived SAS. Security yêu cầu user chỉ upload vào object được cấp phép; backend phải lưu metadata trong SQL Server và file phải qua malware scanning trước khi được download. Business muốn resume/retry cho file lớn và không muốn orphan blobs tích tụ vô hạn.

## Câu hỏi chính

Bạn sẽ thiết kế upload workflow và chọn backend-proxy, direct-to-Blob hay hybrid như thế nào, bao gồm authorization, SAS/Managed Identity, metadata state, failure recovery, scanning, observability và cleanup?

## Câu hỏi làm rõ nên cân nhắc

1. Browser/mobile clients nào cần hỗ trợ và resume requirement cụ thể ra sao?
2. File types, maximum size và compliance constraints là gì?
3. File có được phép download trước khi scan hoàn tất không?
4. Storage account/network policy có cho client direct access không?
5. Consistency requirement giữa SQL metadata và Blob object mạnh đến mức nào?

## Gợi ý tư duy

### Gợi ý 1

Tách control plane khỏi data plane: backend không nhất thiết phải relay toàn bộ bytes để giữ authorization.

### Gợi ý 2

Direct upload cần capability hẹp, ngắn hạn và state machine cho incomplete/orphan uploads.

### Gợi ý 3

Không có distributed transaction tự nhiên giữa SQL metadata, client upload và scanning workflow; thiết kế reconciliation.

## Cấu trúc trả lời đề xuất

1. Clarify security/compliance/client requirements.
2. So sánh proxy vs direct upload.
3. Thiết kế authorization/control API.
4. Thiết kế blob naming/permissions/SAS scope.
5. Metadata state machine.
6. Upload completion validation.
7. Malware scan/quarantine/download gate.
8. Retry/resume và orphan cleanup.
9. Observability/security audit.
10. Test và deployment considerations.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng public container hoặc broad long-lived SAS.
- Backend authorize business action trước khi cấp upload capability.
- Direct-to-Blob giảm data-plane load trên App Service khi requirements cho phép.
- Metadata cần states như PendingUpload/Uploaded/Scanning/Ready/Rejected thay vì boolean đơn giản.
- Download chỉ cho phép theo policy sau scan.
- Có cleanup/reconciliation cho upload không hoàn tất và orphan blobs.

### Điểm cộng

- Backend dùng Managed Identity để thao tác storage thay vì embedded account keys.
- SAS giới hạn resource, permissions và lifetime; naming do server kiểm soát.
- Validate size/type/content expectations ở nhiều lớp; không tin filename/content-type từ client.
- Event/worker scanning được thiết kế idempotent.

### Senior+

- Phân biệt capability security của SAS với user identity authorization của business API.
- Thiết kế commit/finalize step để backend xác minh blob properties trước chuyển state.
- Lifecycle policy và reconciliation job bổ sung cho application cleanup.

## Hướng giải quyết tham khảo

Với file vài GB, proxy toàn bộ bytes qua ASP.NET Core làm application trở thành data relay, tăng bandwidth, connection duration và failure surface. Nếu network/compliance cho phép client kết nối Blob Storage, tôi ưu tiên hybrid: backend giữ control plane, client upload trực tiếp data plane.

Client gọi `POST /uploads` với business context. Backend authorize user, tạo upload record `PendingUpload`, chọn blob path/object identity và cấp short-lived narrowly scoped SAS chỉ cho object đó với permissions tối thiểu. Backend itself dùng Managed Identity cho privileged storage operations. Không để client tự chọn arbitrary container/path theo cách có thể overwrite object khác.

Client upload theo cơ chế phù hợp cho large files/resume. Sau đó gọi finalize hoặc backend nhận event và xác minh blob tồn tại, size/properties phù hợp trước khi chuyển `Uploaded`. Scanning worker xử lý idempotently, chuyển `Scanning` → `Ready` hoặc `Rejected`. Download API chỉ cấp read access khi state cho phép.

Không giả định SQL và Blob có atomic transaction. Nếu client lấy SAS nhưng không upload, record hết hạn và cleanup. Nếu blob tồn tại nhưng finalize thất bại, reconciliation phát hiện orphan/uncommitted object. Lifecycle policy có thể là lớp bảo vệ bổ sung nhưng không thay business reconciliation.

Proxy upload vẫn hợp lý nếu compliance bắt buộc bytes đi qua application inspection hoặc client không thể access storage. Khi đó phải stream, không buffer toàn file vào memory, áp request limits/timeouts phù hợp và xem xét resumable protocol/design. Quyết định phụ thuộc constraints, không phải direct upload luôn thắng.

Observability: upload initiation/completion rate, bytes, duration, failure reason, orphan age, scanning latency/failure, rejected files và storage errors; audit user/business ID với blob identity nhưng không log SAS token.

## Mẫu trả lời trong phỏng vấn

“Với file vài GB, tôi muốn tách control plane và data plane. Backend vẫn quyết định user có quyền upload gì, nhưng nếu compliance cho phép thì browser gửi bytes trực tiếp lên Blob thay vì giữ App Service connection rất lâu.

Flow của tôi là backend authorize, tạo `PendingUpload` record và server-controlled blob identity, rồi cấp SAS ngắn hạn chỉ có quyền cần thiết trên đúng object. Backend dùng Managed Identity cho quyền storage của service. Sau upload, có finalize/verification trước khi metadata chuyển sang `Uploaded`; scanning chạy idempotently và file chỉ download được khi state `Ready`.

Tôi không giả định SQL và Blob transactional. Vì vậy cần expiration, reconciliation và cleanup cho record/blob orphan. SAS cũng không thay business authorization; nó chỉ là capability giới hạn sau khi backend đã authorize.

Nếu policy bắt buộc traffic đi qua backend thì tôi giữ proxy nhưng stream thay vì buffer và thiết kế resume/failure handling. Tôi chọn direct hay proxy dựa trên security/network requirements và measured operational cost.”

## Câu hỏi đào sâu

1. Nếu SAS bị lộ trong thời gian còn hiệu lực, bạn giảm blast radius bằng những controls nào?
2. Nếu compliance bắt buộc malware scan trước khi bytes được lưu vào primary container, bạn thay workflow thế nào?
3. Direct-to-Blob có thực sự đơn giản hơn backend proxy trong mọi trường hợp không? Hãy nêu trường hợp bạn chọn proxy.

## Lỗi trả lời thường gặp

- Dùng long-lived account-level SAS hoặc storage key ở browser.
- Cho phép download ngay sau upload trước scan.
- Giả định SQL row và Blob upload commit atomically.
- Không có orphan cleanup/reconciliation.
- Nói direct upload luôn tốt hơn mà không hỏi compliance/network constraints.

## Thang điểm 0–10

- **0–2:** Chỉ chọn proxy/direct mà không có security/state reasoning.
- **3–4:** Có SAS nhưng scope/lifecycle mơ hồ.
- **5–6:** Có authorization, state machine, scan và cleanup.
- **7–8:** Có Managed Identity, finalize/reconciliation, observability và trade-offs.
- **9–10:** Thiết kế control/data plane rõ ràng, failure model đầy đủ và recommendation conditional theo requirements.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Optimistic concurrency cần hiểu predicate và business conflict thay vì blind retry. Queue incidents cần phân biệt backlog, downstream saturation, transient/poison work và duplicate semantics. Large-file architecture cần tách authorization/control plane khỏi data plane, đồng thời thiết kế state/reconciliation vì SQL, Blob và scanning không tạo một transaction chung.

## Mẫu tư duy cần nhớ

- Retry chỉ an toàn khi hiểu failure semantics và idempotency.
- Row tồn tại không có nghĩa concurrency token vẫn hợp lệ.
- Scale consumers dựa trên downstream capacity, không dựa riêng CPU.
- Tách control plane khỏi data plane khi nó giảm bottleneck mà vẫn giữ authorization.
- Khi nhiều systems không có atomic transaction, thiết kế state + reconciliation + observability.
