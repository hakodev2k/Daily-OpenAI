# Câu 1 — EF Core tracking, identity resolution và truy vấn tưởng là “read-only”

**Loại câu hỏi:** Internal mechanism trong tình huống production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, query execution, Change Tracker, memory/performance, diagnosis

## Bối cảnh

Một ASP.NET Core API trả về danh sách 5.000–20.000 `Employee` kèm `Department`. Endpoint chỉ đọc dữ liệu nhưng sau một đợt tăng traffic, memory tăng mạnh, GC hoạt động nhiều và latency p95 tăng. Code dùng EF Core, `Include`, projection ở một số endpoint, nhưng team cho rằng “query chỉ SELECT nên tracking không đáng kể”. Một số entity cùng `Department` xuất hiện nhiều lần trong kết quả.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong EF Core từ lúc LINQ được xây dựng đến khi materialize kết quả; tracking/identity resolution có thể ảnh hưởng thế nào; misconception nào đang tồn tại; rủi ro production là gì; và bạn sẽ chứng minh giả thuyết bằng evidence nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint trả entity hay DTO?
- `DbContext` lifetime và kích thước result thực tế là bao nhiêu?
- Có `AsNoTracking`, `AsNoTrackingWithIdentityResolution` hay split query không?
- Memory tăng theo request rồi giảm hay giữ lâu?
- SQL sinh ra, số row vật lý và số entity materialized là bao nhiêu?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng `IQueryable` với thời điểm query thực thi.
- **Gợi ý 2:** Xem Change Tracker, materialization, navigation fix-up và số object được tạo.
- **Gợi ý 3:** So sánh tracking, no-tracking, projection và identity resolution bằng measurement thực tế.

## Cấu trúc trả lời đề xuất

1. Làm rõ shape/volume của query.
2. Mô tả deferred execution và translation.
3. Mô tả materialization/tracking.
4. Xác định các nguồn allocation và query amplification.
5. Đưa ra các phương án.
6. Benchmark và đo trước/sau.
7. Kiểm thử correctness.
8. Theo dõi production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- LINQ trên `DbSet` thường tạo expression tree; database query thực thi khi enumerate/materialize như `ToListAsync`.
- Tracking query đưa entity vào Change Tracker; read-only không đồng nghĩa tự động no-tracking.
- Projection DTO và `AsNoTracking` thường phù hợp hơn cho read-only nếu không cần update entity.
- Không kết luận nguyên nhân chỉ từ symptom memory; phải đo SQL, allocations, GC và request profile.

### Điểm cộng

- Giải thích identity resolution và navigation fix-up.
- Nhận ra `Include` nhiều collection có thể làm tăng số row truyền về; cân nhắc projection hoặc split query tùy shape.
- Đề cập cancellation và pagination/bounded result.

### Nâng cao

- Phân biệt `AsNoTracking` với `AsNoTrackingWithIdentityResolution` và trade-off object duplication vs overhead identity map tạm thời.
- Đánh giá compiled query chỉ khi profiling chứng minh query compilation đáng kể, thay vì tối ưu mù.

## Hướng giải quyết tham khảo

**Giả định:** endpoint hoàn toàn read-only và client không cần toàn bộ entity graph.

Đầu tiên lấy generated SQL (`ToQueryString` trong môi trường phù hợp), query plan/database metrics, số row, response size, request allocation và GC counters. Kiểm tra Change Tracker entry count trong diagnostic test. Sau đó benchmark cùng dataset với tracking, `AsNoTracking`, projection DTO và nếu cần `AsNoTrackingWithIdentityResolution`.

Ưu tiên projection trực tiếp tới DTO và pagination vì nó giảm cả columns, entities materialized, tracking và payload. Nếu vẫn cần entity graph nhưng không update, dùng no-tracking. Nếu duplicate references trong result tạo quá nhiều object và semantics cần cùng instance trong một result, cân nhắc no-tracking có identity resolution.

Không mặc định split query tốt hơn: nó có thể tránh cartesian amplification nhưng tạo nhiều round trips/query executions và cần đánh giá consistency/latency theo workload. Kiểm thử query count, dữ liệu navigation, pagination, cancellation và response contract. Theo dõi p95/p99, allocation/request, GC pause, DB duration, rows returned và payload size.

Khuyến nghị thay đổi nếu endpoint thực sự cần modify rồi `SaveChanges`, result nhỏ, hoặc identity semantics quan trọng hơn allocation.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chưa kết luận EF tracking là root cause chỉ vì memory tăng. Trước hết tôi làm rõ result size, entity graph và generated SQL. Với EF Core, LINQ query được xây dựng trước, còn SQL thường chỉ chạy khi materialize. Tracking query không phải miễn phí dù chỉ SELECT: entity được materialize và Change Tracker giữ state/identity trong lifetime của context. Với endpoint read-only lớn, tôi ưu tiên projection DTO và pagination; nếu cần entity thì cân nhắc `AsNoTracking`. Tôi sẽ benchmark cùng dataset và xem allocation/request, GC, SQL rows, response size và latency. Nếu nhiều navigation gây row amplification, tôi so sánh projection với split query thay vì mặc định bật split query. Mục tiêu là sửa dựa trên evidence và vẫn giữ correctness của dữ liệu.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution` tốt hơn `AsNoTracking`?
2. Nếu `AsNoTracking` giảm memory nhưng latency DB vẫn cao, bạn điều tra gì tiếp?
3. Nếu team đề xuất đặt `QueryTrackingBehavior.NoTracking` toàn hệ thống, bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nói SELECT tự động không tracking.
- Chỉ thêm `AsNoTracking` mà không đo result size/SQL.
- Dùng `Include` như mặc định cho mọi navigation.
- Không phân biệt DB latency với allocation/GC phía application.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1

# Câu 2 — Incident: Hangfire job gửi thông báo trùng sau khi scale-out

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire, idempotency, database concurrency, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire gửi email/thông báo sau khi thay đổi lịch sự kiện. Sau deployment và tăng từ 1 lên nhiều worker instance, một tỷ lệ nhỏ người dùng nhận 2–3 thông báo giống nhau. Dashboard cho thấy có retry, nhưng chưa rõ duplicate đến từ enqueue nhiều lần, retry sau timeout, worker overlap hay external provider. Không được dừng toàn bộ hệ thống trong giờ làm việc.

## Câu hỏi chính

Bạn sẽ xử lý incident từ mitigation đến root cause và thiết kế lại như thế nào để việc retry/re-execution không tạo duplicate business effect?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate có cùng business event/idempotency key không?
- Job được enqueue từ request, transaction hay recurring job?
- Provider có hỗ trợ idempotency/deduplication không?
- Retry xảy ra trước hay sau khi provider đã nhận request?
- Có nhiều server cùng xử lý cùng logical event do application enqueue lặp không?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt “job chạy nhiều lần” và “business effect xảy ra nhiều lần”.
- **Gợi ý 2:** Xem transaction boundary giữa DB state, enqueue và external side effect.
- **Gợi ý 3:** Thiết kế idempotency dựa trên business operation, unique constraint/state machine và reconciliation.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius.
2. Mitigate an toàn.
3. Thu thập correlation evidence.
4. Lập nhiều hypothesis.
5. Reproduce/falsify từng hypothesis.
6. Short-term dedupe.
7. Long-term idempotent workflow.
8. Monitoring/reconciliation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định job framework đảm bảo exactly-once business effect.
- Tạo stable operation/event ID và idempotency boundary.
- Unique constraint/atomic state transition phải nằm ở durable store, không chỉ lock trong process.
- Correlate enqueue → execution attempt → provider request → provider response.

### Điểm cộng

- Transactional outbox khi cần đồng bộ DB state với việc phát sinh work.
- Reconciliation cho trạng thái “provider thành công nhưng app timeout”.
- Backoff và retry policy phân loại transient/permanent failure.

### Nâng cao

- Thiết kế inbox/deduplication nếu downstream consumer cũng at-least-once.
- Phân biệt idempotency của command với dedupe theo payload/time window.

## Hướng giải quyết tham khảo

Trước tiên xác định impact, tạm giảm retry hoặc pause riêng queue/job type nếu blast radius lớn nhưng không làm mất work. Không xóa job hàng loạt. Bổ sung/correlate `BusinessOperationId`, Hangfire job id, attempt, worker, event id và provider message/request id.

Các hypothesis gồm: application enqueue cùng event nhiều lần; retry sau timeout dù provider đã nhận; recurring execution overlap; race khi nhiều request cùng cập nhật; provider gửi duplicate. Dùng timeline và durable records để loại trừ từng nguyên nhân.

Short-term có thể tạo bảng `NotificationDelivery(OperationId, Channel, Status, ProviderId, ...)` với unique constraint phù hợp. Worker claim/transition state atomically; retry dùng cùng operation ID. Nếu provider hỗ trợ idempotency key thì truyền stable key. Không dùng Redis lock đơn thuần làm correctness boundary nếu mất lock có thể gây duplicate.

Long-term, nếu thay đổi business state và tạo notification phải gắn chặt, dùng transactional outbox: cùng DB transaction ghi domain change + outbox record; dispatcher có thể chạy lại nhưng consumer/delivery vẫn idempotent. Trạng thái ambiguous sau timeout phải được query/reconcile nếu provider hỗ trợ, hoặc đánh dấu cần reconciliation thay vì gửi lại vô điều kiện.

Theo dõi duplicate prevented count, retry rate, age of oldest pending, failure ratio, provider latency và reconciliation backlog.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là vấn đề idempotency trước, không chỉ là Hangfire duplicate. Việc đầu tiên là giới hạn blast radius và correlate một notification từ lúc enqueue đến provider. Tôi sẽ kiểm tra ít nhất bốn hướng: enqueue lặp, retry sau ambiguous timeout, overlap/race và duplicate từ provider. Fix bền vững là mỗi business operation có stable ID, lưu delivery state trong durable store với unique constraint và atomic transition. Retry phải reuse cùng ID; nếu provider hỗ trợ idempotency key thì truyền key đó. Nếu notification được sinh từ thay đổi DB, tôi cân nhắc transactional outbox để tránh khoảng trống giữa commit và enqueue. Tôi vẫn giả định execution có thể lặp, nên correctness nằm ở idempotent business effect, cộng reconciliation cho các trạng thái không chắc chắn.”

## Câu hỏi đào sâu

1. Vì sao distributed lock không thay thế idempotency?
2. Nếu provider không có API kiểm tra trạng thái sau timeout thì bạn xử lý ambiguity thế nào?
3. Outbox có loại bỏ hoàn toàn duplicate không? Vì sao?

## Lỗi trả lời thường gặp

- Tắt retry hoàn toàn.
- Cho rằng queue/job framework cung cấp exactly-once end-to-end.
- Dùng in-memory flag hoặc process lock.
- Không thiết kế cho timeout sau khi external side effect đã xảy ra.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 1.5
- Production readiness: 2
- Communication: 1

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repository và đề xuất patch

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent design, context engineering, tool security, evaluation, deterministic validation, auditability

## Bối cảnh

Team muốn một AI agent review pull request .NET: đọc diff và file liên quan, phát hiện bug/security/performance issue, có thể chạy test và đề xuất patch. Agent có thể truy cập repository qua tool integration. Team muốn giảm thời gian review nhưng không chấp nhận agent tự merge hoặc tự deploy. Repository có secrets/config nhạy cảm và test suite mất 20 phút nếu chạy toàn bộ.

## Câu hỏi chính

Hãy thiết kế workflow cho agent này: AI thực sự cần ở đâu, phần nào phải deterministic, context nào được cấp, tool/permission nào cho phép, cách validate/hallucination detection, evaluation, fallback, audit và monitoring như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được tạo commit/PR?
- Repository nào/data classification nào được phép xử lý?
- Definition của “review tốt” và acceptable false-positive rate là gì?
- CI/test infrastructure hiện có những gì?
- Có human approval ở bước nào?

## Gợi ý tư duy

- **Gợi ý 1:** Tách reasoning không chắc chắn khỏi enforcement có thể kiểm chứng.
- **Gợi ý 2:** Principle of least privilege + context minimization + structured output.
- **Gợi ý 3:** Dùng staged workflow: scope → retrieve → reason → verify → human gate → audit/evaluate.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu/metrics.
2. Threat model và permission boundary.
3. Context retrieval.
4. Agent reasoning/tool loop.
5. Deterministic validation.
6. Human approval.
7. Evaluation dataset.
8. Observability/cost/fallback.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho semantic reasoning/review; policy, authorization, schema validation, build/test và merge gate phải deterministic.
- Read-only mặc định; write scope tách riêng và cần approval.
- Context lấy theo PR diff + dependency/relevant files thay vì dump toàn repo.
- Findings cần evidence như file/line/rationale và phải được verify khi có thể.

### Điểm cộng

- Structured schema với severity, confidence, evidence, suggested validation.
- Test selection trước, full CI theo policy/risk.
- Prompt-injection threat model cho repository content/tool output.

### Nâng cao

- Offline eval trên historical PRs có labeled defects; precision/recall theo issue class và acceptance rate.
- Canary/shadow mode trước khi cho phép tạo patch.
- Audit tool call, token/cost, model/version/config và artifact hashes.

## Hướng giải quyết tham khảo

AI cần cho việc hiểu intent, liên kết thay đổi giữa file, tìm failure mode và đề xuất review. Deterministic layer chịu trách nhiệm access control, path allow/deny, secret redaction, schema validation, compiler/analyzers/tests, policy và merge protection.

Agent bắt đầu bằng PR metadata/diff, sau đó request thêm context qua bounded read tools. Không cho arbitrary shell/network mặc định. Tool chạy test nên dùng allowlisted commands trong sandbox với timeout/resource limit. Repository text là untrusted data: instruction nằm trong code/docs không được tự động nâng quyền hay thay system/tool policy.

Output dùng structured finding: location, category, severity, confidence, evidence, reasoning summary, suggested fix/test. Findings về compile/test phải được xác minh bằng deterministic tooling. Patch chỉ là proposal; human review/CI gate trước write/merge.

Quality đo bằng benchmark lịch sử và shadow production: precision, recall trên labeled categories, false-positive rate, reviewer acceptance, escaped defects, latency và cost/PR. Log audit phải tránh ghi secret nhưng lưu model/config version, context references, tool calls, validation results và approval. Khi model/tool fail, fallback là review truyền thống hoặc partial deterministic checks, không bypass gate.

## Mẫu trả lời trong phỏng vấn

“Tôi không thiết kế đây là agent có quyền repository rộng rồi hy vọng prompt giữ nó an toàn. AI chỉ xử lý phần cần semantic judgment; authorization, schema, build, tests và merge policy vẫn deterministic. Agent nhận PR diff trước, sau đó dùng read-only tool để lấy context cần thiết theo giới hạn. Repo content được coi là untrusted vì có thể chứa instruction injection. Nếu cần chạy test, agent chỉ chọn từ allowlisted command trong sandbox. Mỗi finding phải có file/line, evidence, severity và confidence; những claim có thể kiểm chứng sẽ chạy analyzer/test. Patch chỉ là proposal và cần CI cùng human approval. Tôi sẽ rollout shadow mode, đánh giá trên historical PRs bằng precision/recall, false-positive rate và reviewer acceptance, đồng thời audit model version, context và tool calls. Khi agent fail, hệ thống quay về deterministic checks và human review chứ không bỏ qua gate.”

## Câu hỏi đào sâu

1. Làm sao chống indirect prompt injection nằm trong README hoặc source code?
2. Nếu agent cần quyền write để sửa typo tự động, bạn cấp quyền thế nào mà vẫn an toàn?
3. Reviewer acceptance tăng nhưng escaped defect cũng tăng: metric nào nên ưu tiên và vì sao?

## Lỗi trả lời thường gặp

- “Cho LLM đọc toàn repo và review”.
- Trao shell/network/write permission quá rộng.
- Dùng model tự đánh giá chính output của nó làm validation duy nhất.
- Không có eval dataset, fallback hoặc human gate.
- Log toàn prompt/context làm rò rỉ secret.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 1.5
