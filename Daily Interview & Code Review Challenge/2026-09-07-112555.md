# Code Review Challenge 1 — Personalized CMS block bị cache nhầm ở origin và CDN

**Chủ đề:** C#/.NET, ASP.NET Core, Optimizely CMS, Akamai/CDN, HTTP caching, personalization, security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–13 vấn đề

## Bối cảnh

Một marketing website chạy Optimizely CMS trên ASP.NET Core. Trang sản phẩm có một content block tên `CustomerOfferBlock`.

Block này hiển thị:

- headline và body do editor quản lý trong CMS;
- offer khác nhau theo market;
- discount tier lấy từ claims của user đã đăng nhập;
- recommendation lấy từ một external API;
- anonymous user vẫn xem được default content;
- website đứng sau Akamai CDN;
- origin chạy nhiều instance trên Azure App Service;
- team muốn tăng cache hit ratio vì p95 của trang đang cao.

Sau một đợt tối ưu, production xuất hiện các hiện tượng:

- một số user đăng nhập thấy discount tier của user khác;
- anonymous user đôi khi thấy CTA dành cho customer đã đăng nhập;
- editor publish block mới nhưng CDN vẫn trả nội dung cũ trong vài phút;
- khi external recommendation API chậm, nhiều request cùng lúc gọi API đó;
- restart một App Service instance làm cache behavior thay đổi không đồng đều giữa các instance;
- log hiện tại chỉ ghi URL, không có cache status, content version hay personalization key.

Implementation hiện tại:

## Đoạn code cần review

```csharp
public sealed class CustomerOfferBlockComponent
    : BlockComponent<CustomerOfferBlock>
{
    private static readonly MemoryCache Cache = new(
        new MemoryCacheOptions());

    private readonly IHttpContextAccessor _httpContextAccessor;
    private readonly IRecommendationClient _recommendationClient;
    private readonly ILogger<CustomerOfferBlockComponent> _logger;

    public CustomerOfferBlockComponent(
        IHttpContextAccessor httpContextAccessor,
        IRecommendationClient recommendationClient,
        ILogger<CustomerOfferBlockComponent> logger)
    {
        _httpContextAccessor = httpContextAccessor;
        _recommendationClient = recommendationClient;
        _logger = logger;
    }

    protected override async Task<IViewComponentResult> InvokeComponentAsync(
        CustomerOfferBlock currentBlock)
    {
        var http = _httpContextAccessor.HttpContext!;
        var market = http.Request.Query["market"].ToString();
        var tier = http.User.FindFirst("discount_tier")?.Value ?? "anonymous";

        var cacheKey = $"offer:{currentBlock.ContentGuid}";

        if (Cache.TryGetValue(cacheKey, out CustomerOfferViewModel? cached))
        {
            return View(cached);
        }

        var recommendation = await _recommendationClient.GetAsync(
            market,
            tier);

        var model = new CustomerOfferViewModel
        {
            Heading = currentBlock.Heading,
            Body = currentBlock.Body,
            Market = market,
            DiscountTier = tier,
            Recommendation = recommendation
        };

        Cache.Set(
            cacheKey,
            model,
            TimeSpan.FromMinutes(10));

        http.Response.Headers.CacheControl = "public,max-age=600";

        _logger.LogInformation(
            "Rendered offer block {ContentGuid} for {Market}",
            currentBlock.ContentGuid,
            market);

        return View(model);
    }
}
```

Controller/page middleware ở origin còn cấu hình:

```csharp
app.Use(async (context, next) =>

```

## Kết quả code review tham khảo

### Critical — Personalized response bị đánh dấu `public`

**Vấn đề:**  
Response HTML có nội dung theo `discount_tier`, nhưng cả component và middleware đều có thể đặt `Cache-Control: public,max-age=600`.

**Tại sao xảy ra:**  
HTTP cache policy không phân biệt anonymous/public content với authenticated/personalized content.

**Ảnh hưởng production:**  
CDN có thể cache một response đã personalize rồi phục vụ lại cho request khác nếu cache key ở edge không include identity/personalization dimensions. Đây không chỉ là stale-content problem mà còn có thể trở thành data exposure hoặc authorization-related incident.

**Cách sửa:**  
Không public-cache personalized HTML. Với authenticated/personalized page, dùng `private`, `no-store`, hoặc thiết kế page shell public + personalized fragment được lấy riêng qua API có policy phù hợp. Nếu business dùng cohort-level caching, phải chứng minh cache key và privacy boundary an toàn; không dùng user-specific claim với public shared cache.

---

### Critical — Application cache key bỏ qua `market` và `discount_tier`

**Vấn đề:**  
Cache key chỉ là `offer:{ContentGuid}` trong khi output phụ thuộc ít nhất vào `market`, `discount_tier`, content version và recommendation result.

**Tại sao xảy ra:**  
Cache key mô tả content identity nhưng không mô tả rendering context.

**Ảnh hưởng production:**  
Request đầu tiên populate cache sẽ quyết định model mà các request sau nhận được trên cùng instance. User ở market/tier khác có thể nhận sai CTA, giá trị discount hoặc recommendation.

**Cách sửa:**  
Nếu cache output này thật sự hợp lý, cache key phải include toàn bộ dimensions làm output thay đổi, ví dụ content version + normalized market + safe cohort key. Với dữ liệu user-specific, tốt hơn là không cache shared view model này.

---

### High — Middleware ghi đè cache policy của endpoint/component

**Vấn đề:**  
Global middleware đặt `public,max-age=600` cho mọi response 200 sau khi downstream đã chạy.

**Tại sao xảy ra:**  
Cache policy được áp dụng theo status code thay vì route/content semantics.

**Ảnh hưởng production:**  
Ngay cả endpoint cố đặt `private` hoặc `no-store` cũng có thể bị policy chung ghi đè. Điều này làm security policy khó kiểm soát và dễ tạo regression ngoài page hiện tại.

**Cách sửa:**  
Cache policy phải được xác định ở layer có đủ context, ví dụ response caching policy/endpoint metadata hoặc middleware có explicit allow-list. Không dùng `200 => public cache` làm default.

---

### High — `MemoryCache` chỉ có phạm vi từng process/instance

**Vấn đề:**  
Static `MemoryCache` không đồng bộ giữa nhiều App Service instances.

**Tại sao xảy ra:**  
Mỗi process giữ heap riêng.

**Ảnh hưởng production:**  
Instance A có thể serve model cũ trong khi instance B vừa populate model mới. Restart/scale-out tạo cache cold start và behavior không đồng đều. Điều này cũng làm troubleshooting khó vì cùng URL có thể trả khác nhau theo instance.

**Cách sửa:**  
Trước hết xác định có cần distributed cache hay không. Nếu cache là optimization và stale ngắn hạn chấp nhận được, per-instance cache vẫn có thể hợp lý nhưng phải hiểu trade-off. Nếu consistency giữa instances là requirement, dùng distributed cache hoặc content-versioned keys/invalidation event. Không mặc định “dùng Redis” nếu chưa cần.

---

### High — Không có protection chống cache stampede

**Vấn đề:**  
Nhiều request miss cùng key sẽ đồng thời gọi recommendation API.

**Tại sao xảy ra:**  
`TryGetValue` và populate không có single-flight/coalescing.

**Ảnh hưởng production:**  
Khi key hết hạn hoặc instance mới start, burst traffic có thể khuếch đại thành burst downstream. Nếu external API đang chậm, request latency và connection usage ở origin còn tăng hơn.

**Cách sửa:**  
Dùng per-key async coordination/single-flight, hoặc stale-while-revalidate pattern nếu business chấp nhận. Phải có timeout, cancellation và fallback rõ ràng cho recommendation dependency.

---

### High — TTL không gắn với CMS publish lifecycle

**Vấn đề:**  
Cache sống 10 phút bất kể content đã được publish version mới.

**Tại sao xảy ra:**  
Invalidation chỉ dựa vào thời gian.

**Ảnh hưởng production:**  
Editor publish nội dung mới nhưng origin/cache edge vẫn có thể serve content cũ tới khi TTL hết. Purge CDN và invalidation origin không đồng bộ có thể làm stale window dài hơn.

**Cách sửa:**  
Dùng content version trong cache key hoặc subscribe vào content publish/change event để evict key liên quan. Với CDN, có cache purge/versioned URL strategy tương ứng. TTL vẫn hữu ích như safety bound nhưng không phải invalidation mechanism duy nhất.

---

### Medium — `market` được tin trực tiếp từ query string

**Vấn đề:**  
Client tự gửi `market` và value này đi thẳng vào recommendation API/cache context.

**Tại sao xảy ra:**  
Không có normalization hoặc authorization/business validation.

**Ảnh hưởng production:**  
User có thể request market không hợp lệ, làm tăng cache cardinality nếu market được thêm vào key sau này, hoặc lấy recommendation không phù hợp với session/account context.

**Cách sửa:**  
Xác định market từ trusted application context hoặc validate against allow-list/business rules. Normalize casing/format trước khi dùng làm cache dimension.

---

### Medium — Không có timeout/cancellation rõ ràng cho external API

**Vấn đề:**  
Call `GetAsync(market, tier)` không cho thấy request cancellation hoặc timeout behavior.

**Tại sao xảy ra:**  
Dependency call không được coi là failure-prone component.

**Ảnh hưởng production:**  
Khi downstream chậm, request có thể giữ resource lâu, tăng tail latency và tạo cascading failure.

**Cách sửa:**  
Truyền `CancellationToken`, cấu hình timeout phù hợp, circuit-breaking/fallback nếu cần và đo dependency duration/failure rate.

---

### Medium — Telemetry không đủ để chứng minh cache behavior

**Vấn đề:**  
Log chỉ có `ContentGuid` và market.

**Tại sao xảy ra:**  
Không log cache hit/miss, content version, tier/cohort, origin instance, dependency duration hoặc edge cache headers.

**Ảnh hưởng production:**  
Không thể trả lời nhanh câu hỏi: response này đến từ CDN, origin cache hay fresh render; model dựa trên content version nào; dependency call có chậm không.

**Cách sửa:**  
Thêm structured telemetry cho content identity/version, cache status, normalized market, safe cohort, dependency duration, correlation/trace ID và response cache headers. Không log sensitive claim values nếu không cần.

## Phiên bản đề xuất

Ví dụ dưới đây giả định:

- anonymous content có thể cache ở origin theo content version + market;
- authenticated personalized content không dùng shared public cache;
- recommendation được xem là optional dependency;
- `GetContentVersionKey` là application abstraction lấy stable version identifier của published content;
- CDN policy được xử lý ngoài component dựa trên endpoint/authentication state.

```csharp
public sealed class CustomerOfferBlockComponent
    : BlockComponent<CustomerOfferBlock>
{
    private readonly IMemoryCache _cache;
    private readonly IRecommendationClient _recommendationClient;
    private readonly IMarketResolver _marketResolver;
    private readonly IContentVersionKeyProvider _versionProvider;
    private readonly ILogger<CustomerOfferBlockComponent> _logger;

    public CustomerOfferBlockComponent(
        IMemoryCache cache,
        IRecommendationClient recommendationClient,
        IMarketResolver marketResolver,
        IContentVersionKeyProvider versionProvider,
        ILogger<CustomerOfferBlockComponent> logger)
    {
        _cache = cache;
        _recommendationClient = recommendationClient;
        _marketResolver = marketResolver;
        _versionProvider = versionProvider;
        _logger = logger;
    }

    protected override async Task<IViewComponentResult> InvokeComponentAsync(
        CustomerOfferBlock currentBlock)
    {
        var http = HttpContext;
        var market = _marketResolver.Resolve(http);
        var isAuthenticated = http.User.Identity?.IsAuthenticated == true;
        var tier = http.User.FindFirst("discount_tier")?.Value;
        var contentVersion = _versionProvider.GetContentVersionKey(currentBlock);

        CustomerOfferViewModel model;

        if (!isAuthenticated)
        {
            var cacheKey =
                $"offer:{currentBlock.ContentGuid}:{contentVersion}:{market}:anonymous";

            model = await _cache.GetOrCreateAsync(cacheKey, async entry =>
            {
                entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);

                var recommendation = await _recommendationClient.GetAsync(
                    market,
                    "anonymous",
                    http.RequestAborted);

                return new CustomerOfferViewModel
                {
                    Heading = currentBlock.Heading,
                    Body = currentBlock.Body,
                    Market = market,
                    DiscountTier = "anonymous",
                    Recommendation = recommendation
                };
            }) ?? throw new InvalidOperationException("Offer model was not created.");

            http.Response.Headers.CacheControl = "public,max-age=120";
        }
        else
        {
            var recommendation = await _recommendationClient.GetAsync(
                market,
                tier ?? "default",
                http.RequestAborted);

            model = new CustomerOfferViewModel
            {
                Heading = currentBlock.Heading,
                Body = currentBlock.Body,
                Market = market,
                DiscountTier = tier ?? "default",
                Recommendation = recommendation
            };

            http.Response.Headers.CacheControl = "private,no-store";
        }

        _logger.LogInformation(
            "Rendered offer block {ContentGuid} version {ContentVersion} market {Market} authenticated={Authenticated}",
            currentBlock.ContentGuid,
            contentVersion,
            market,
            isAuthenticated);

        return View(model);
    }
}
```

Lưu ý: `IMemoryCache.GetOrCreateAsync` một mình không nên được mặc định coi là distributed single-flight guarantee giữa nhiều process. Nếu stampede protection là requirement, implement explicit per-key coordination trong process và cân nhắc distributed coordination chỉ khi measured load chứng minh cần thiết.

## Giải thích thiết kế sau khi sửa

### 1. Cache policy đi theo personalization boundary

Anonymous response có thể shared-cache nếu output thực sự public. Authenticated response được tách khỏi public CDN caching.

### 2. Content version nằm trong key

Khi publish version mới, key tự đổi. Điều này giảm phụ thuộc vào TTL thuần túy và làm stale behavior dễ reason hơn.

### 3. Market được resolve qua abstraction

Application có một nơi duy nhất để normalize/validate market thay vì tin raw query string.

### 4. External API được coi là failure-prone

Call nhận cancellation và cần timeout/fallback/telemetry ở `IRecommendationClient` implementation.

### 5. Không tự động nâng complexity

Nếu anonymous traffic thấp hoặc recommendation đủ nhanh, có thể bỏ cache hoàn toàn. Cache chỉ nên tồn tại khi measurement chứng minh lợi ích.

## Trade-offs

- Không public-cache personalized HTML làm giảm CDN hit ratio cho authenticated users nhưng bảo vệ isolation.
- Versioned cache key làm số key tăng trong một khoảng thời gian; cần expiration hợp lý.
- Distributed cache giúp consistency tốt hơn nhưng tăng network dependency, serialization cost và operational complexity.
- Edge-side includes hoặc client-side personalized fragment có thể tăng kiến trúc phức tạp và ảnh hưởng SEO/rendering; chỉ dùng khi requirement xứng đáng.
- Purge CDN nhanh hơn giảm stale content nhưng tạo coupling giữa CMS publish pipeline và CDN provider.

## Cách kiểm thử

1. **Security/integration test:** hai authenticated users có tier khác nhau không bao giờ nhận personalized HTML của nhau.
2. **Cache-key test:** anonymous requests khác market tạo output/cache entry đúng theo market.
3. **Publish invalidation test:** publish version mới của block và xác minh origin + CDN không tiếp tục serve version cũ vượt policy cho phép.
4. **Concurrency/load test:** nhiều request cùng cache miss không làm downstream recommendation call tăng tuyến tính ngoài design expectation.
5. **Failure-path test:** recommendation API timeout/fail; page vẫn degrade theo policy đã định và telemetry ghi rõ dependency failure.

## Quan sát trong production

Theo dõi:

- CDN cache hit/miss/pass;
- `Age`, cache-status headers hoặc provider-specific cache diagnostics;
- origin cache hit ratio;
- content version đang render;
- request p50/p95/p99;
- recommendation dependency duration/failure rate;
- số concurrent downstream calls trong cache-miss burst;
- instance identifier khi troubleshoot inconsistency;
- authenticated vs anonymous cache policy distribution;
- purge/invalidation success rate;
- stale-content incident count.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business muốn cache theo customer segment thay vì từng user, bạn cần chứng minh điều gì trước khi cho phép shared caching?
2. Khi nào per-instance `MemoryCache` là lựa chọn đủ tốt hơn Redis?
3. Nếu Akamai vẫn cần cache page shell nhưng offer phải personalize, bạn sẽ tách rendering boundary như thế nào?

# Code Review Challenge 2 — Release pipeline chạy migration trước, rollback sau nhưng schema không quay lại

## Bối cảnh

Một enterprise ASP.NET Core application đang được hiện đại hóa từ IIS/Windows Server sang Azure App Service.

Pipeline hiện tại:

- TeamCity build artifact;
- artifact được push sang Octopus Deploy;
- Octopus chạy database migration;

- new version chỉ đọc `CustomerCode` và `CodeType`;

Team hiện dùng script sau như Octopus deployment step.

## Đoạn code cần review

```powershell
$ErrorActionPreference = "Stop"

$connectionString = $OctopusParameters["MainDb.ConnectionString"]
$packagePath = $OctopusParameters["App.PackagePath"]
$appServiceName = $OctopusParameters["Azure.AppServiceName"]
$resourceGroup = $OctopusParameters["Azure.ResourceGroup"]

Write-Host "Starting database migration"

dotnet tool install --global dotnet-ef
$env:PATH += ";$env:USERPROFILE\.dotnet\tools"

dotnet ef database update `
  --project $packagePath `
  --connection $connectionString

Write-Host "Database migration completed"

az webapp deployment source config-zip `
  --resource-group $resourceGroup `
  --name $appServiceName `
  --src $packagePath

Write-Host "Deployment completed"

Start-Sleep -Seconds 10

$response = Invoke-WebRequest `
  -Uri "https://$appServiceName.azurewebsites.net/health" `
  -UseBasicParsing

if ($response.StatusCode -ne 200) {
    throw "Health check failed"
}

Write-Host "Release successful"
```

Rollback runbook hiện tại:

```text
1. Chọn release trước trong Octopus.
2. Redeploy application package cũ.
3. Không chạy database rollback vì migration rollback được xem là nguy hiểm.
4. Nếu /health trả 200 thì đóng incident.
```

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **schema compatibility window** giữa old app, new app và migration.

### Gợi ý 2

Hãy nghĩ theo hướng **expand → deploy compatible code → migrate/backfill → switch reads/writes → contract later**, thay vì một migration phá vỡ schema ngay trước deployment.

## Kết quả code review tham khảo

### Critical — Migration phá backward compatibility trước khi application rollout hoàn tất

**Vấn đề:**  
Nếu migration rename/drop `LegacyCode` trước khi old application instances biến mất, old version không còn schema mà nó cần.

**Tại sao xảy ra:**  
Database được migrate như một atomic prerequisite nhưng application rollout là quá trình có overlap giữa versions.

**Ảnh hưởng production:**  
Trong rolling/multi-instance deployment, một phần traffic vẫn có thể đi vào old instances và fail query/runtime. Nếu new deployment fail giữa chừng, old version cũng có thể không còn đường rollback an toàn.

**Cách sửa:**  
Dùng backward-compatible migration. Phase 1 expand schema bằng cách thêm `CustomerCode` và `CodeType` nhưng giữ `LegacyCode`. Deploy code có thể hoạt động với schema mở rộng. Backfill dữ liệu. Chuyển read/write dần. Chỉ drop `LegacyCode` trong release sau khi chứng minh không còn consumer phụ thuộc.

---

### Critical — Rollback application không đảm bảo rollback khả năng tương thích

**Vấn đề:**  
Runbook chỉ redeploy package cũ và không đánh giá old app có chạy trên schema mới không.

**Tại sao xảy ra:**  
Rollback được xem như artifact rollback, trong khi production state gồm cả code + database + configuration + external dependencies.

**Ảnh hưởng production:**  
Old app có thể start nhưng fail ở runtime khi truy cập schema đã thay đổi. `/health` vẫn có thể 200 nếu health endpoint không exercise database path liên quan.

**Cách sửa:**  
Thiết kế database changes để rollback code không yêu cầu reverse migration khẩn cấp. Mỗi release phải xác định explicit rollback compatibility window và test old-version-on-new-schema trước production.

---

### High — Cài `dotnet-ef` global trong deployment làm toolchain không reproducible

**Vấn đề:**  
Script install tool tại runtime mà không pin rõ version.

**Tại sao xảy ra:**  
Deployment host tự resolve tool version từ external package source.

**Ảnh hưởng production:**  
Hai release giống nhau chạy ở thời điểm khác nhau có thể dùng tool version khác. Network/package-source failure cũng có thể chặn deployment trước khi app deploy.

**Cách sửa:**  
Pin tool version trong repository/tool manifest hoặc build migration artifact riêng trong CI. Production deployment nên consume immutable prebuilt artifact thay vì assemble toolchain động.

---

### High — Migration execution gắn vào app package path mơ hồ

**Vấn đề:**  
`--project $packagePath` giả định deployment package cũng là migration project hợp lệ.

**Tại sao xảy ra:**  
Build artifact boundary và migration artifact boundary không rõ ràng.

**Ảnh hưởng production:**  
Release có thể phụ thuộc layout local của package, source files hoặc SDK state không được đảm bảo trên worker.

**Cách sửa:**  
Build migration bundle/artifact rõ ràng trong CI, version cùng release và checksum/metadata với application artifact.

---

### High — Secrets được truyền trực tiếp qua command line

**Vấn đề:**  
Connection string được đưa vào argument của `dotnet ef`.

**Tại sao xảy ra:**  
Deployment script không có abstraction cho secret injection.

**Ảnh hưởng production:**  
Tùy runner/tool logging/process inspection, secret có thể xuất hiện trong logs hoặc process command line.

**Cách sửa:**  
Dùng secret variable handling của deployment platform, environment-based secure injection hoặc Managed Identity/service identity khi khả thi. Đảm bảo logs redact secret và không echo command chứa credential.

---

### High — Health check quá nông cho release validation

**Vấn đề:**  
Pipeline chỉ check một endpoint `/health` sau sleep 10 giây.

**Tại sao xảy ra:**  
Process liveness bị dùng thay cho functional release validation.

**Ảnh hưởng production:**  
App có thể return 200 nhưng login, database read/write, critical API, background integration hoặc CMS route đang fail.

**Cách sửa:**  
Giữ health endpoint cho readiness/liveness, nhưng thêm post-deploy smoke tests theo risk: authenticated API call, read path, safe write/read-back ở synthetic data, dependency connectivity và critical business route. Dùng timeout/retry bounded thay vì fixed sleep.

---

### High — Không có stop/go criteria dựa trên production telemetry

**Vấn đề:**  
Script coi deployment thành công ngay khi health trả 200.

**Tại sao xảy ra:**  
Không có observation window hoặc SLO guardrail.

**Ảnh hưởng production:**  
Release có regression về p95, 5xx, SQL error hoặc authentication nhưng vẫn được đánh dấu successful.

**Cách sửa:**  
Định nghĩa release gate: error rate, p95/p99, dependency failure, DB errors, auth failure và business smoke test. Có observation window phù hợp và manual/automatic abort rule tùy criticality.

---

### Medium — Deployment trực tiếp production slot làm rollback/verification khó hơn

**Vấn đề:**  
Script deploy zip trực tiếp vào app đang serve traffic.

**Tại sao xảy ra:**  
Không dùng staging slot hoặc equivalent pre-traffic validation.

**Ảnh hưởng production:**  
Regression được phát hiện sau khi package đã tác động traffic. Configuration warm-up và startup issue xảy ra ngay trên production path.

**Cách sửa:**  
Nếu App Service plan/workload hỗ trợ và complexity xứng đáng, deploy vào staging slot, warm-up + validate rồi swap. Cần hiểu slot-specific settings, connection strings và migration ordering; slot không tự giải quyết database compatibility.

---

### Medium — Không chứng minh artifact immutability

**Vấn đề:**  
Script chỉ nhận `$packagePath`, không log/version/check checksum của artifact.

**Tại sao xảy ra:**  
Release identity và artifact identity không được liên kết rõ.

**Ảnh hưởng production:**  
Khó chứng minh production đang chạy đúng binary nào, đặc biệt khi redeploy/rollback.

**Cách sửa:**  
Dùng immutable artifact version, commit SHA/build number, checksum hoặc package ID; ghi chúng vào deployment metadata và telemetry của app.

---

### Medium — Fixed sleep 10 giây không phản ánh startup behavior

**Vấn đề:**  
Pipeline chờ cố định 10 giây rồi check một lần.

**Tại sao xảy ra:**  
Không có readiness polling/backoff.

**Ảnh hưởng production:**  
App startup 15 giây sẽ bị false failure; app startup 3 giây nhưng dependency fail sau 20 giây thì pipeline có thể false success.

**Cách sửa:**  
Poll readiness với timeout tổng, exponential/bounded backoff và sau đó chạy smoke test + observation gate.

## Phiên bản đề xuất

Ví dụ release strategy:

```text
Release N — Expand
1. Build immutable application artifact + migration artifact in TeamCity.
2. Migration adds CustomerCode and CodeType; LegacyCode remains intact.
3. Run migration once through a dedicated Octopus step with pinned artifact.
4. Deploy app version that can read old/new schema safely.
5. App writes both old and new representation if needed during transition.
6. Run smoke tests and observe telemetry.

Release N+1 — Backfill / Switch
1. Backfill CustomerCode/CodeType in controlled batches.
2. Validate row counts, null rate and business invariants.
3. Switch reads to new columns behind configuration/feature flag if appropriate.
4. Stop writing LegacyCode only after all active consumers support new schema.
5. Observe production and verify rollback to previous app version still works.

Release N+2 — Contract
1. Confirm no code/report/job reads LegacyCode.
2. Remove compatibility code.
3. Drop LegacyCode in a later migration.
4. Update rollback documentation: pre-contract version is no longer supported after this point.
```

Một deployment script an toàn hơn về mặt flow có thể ở mức:

```powershell
$ErrorActionPreference = "Stop"

$migrationArtifact = $OctopusParameters["Migration.ArtifactPath"]
$appArtifact = $OctopusParameters["App.ArtifactPath"]
$releaseVersion = $OctopusParameters["Release.Version"]

Write-Host "Release $releaseVersion"
Write-Host "Applying pinned migration artifact"

& $migrationArtifact apply
if ($LASTEXITCODE -ne 0) {
    throw "Migration failed"
}

Write-Host "Deploying immutable application artifact"

# Deploy to staging slot or controlled target.
# Exact command depends on hosting strategy.
Deploy-ApplicationArtifact -Path $appArtifact -Version $releaseVersion

Wait-ApplicationReadiness -TimeoutSeconds 180

Invoke-SmokeTest -Name "Authentication"
Invoke-SmokeTest -Name "CustomerRead"
Invoke-SmokeTest -Name "CustomerWriteReadBack"

Assert-ReleaseTelemetry `
    -WindowMinutes 5 `
    -MaxErrorRate 0.01 `
    -MaxP95RegressionPercent 20

Write-Host "Release $releaseVersion passed validation"
```

Các function trên là abstractions minh họa release contract, không giả định Octopus có built-in command tương ứng.

## Giải thích thiết kế sau khi sửa

### 1. Expand/contract thay thế destructive migration trước rollout

Schema được mở rộng trước để old/new versions có thể cùng tồn tại. Breaking cleanup được trì hoãn tới khi không còn consumer cũ.

### 2. Migration artifact được build trong CI

CI tạo artifact xác định, deployment chỉ chạy artifact đã được review/test/pin version.

### 3. Rollback được thiết kế trước release

Mỗi schema change phải trả lời: old app có chạy trên new schema không? Nếu câu trả lời là không, release chưa có rollback story an toàn.

### 4. Health và smoke test có mục đích khác nhau

Health xác định instance có thể phục vụ. Smoke test xác minh critical workflows của release.

### 5. Release success dựa trên telemetry

Process start không đồng nghĩa business success. Cần observation window và metrics phù hợp với rủi ro thay đổi.

## Trade-offs

- Expand/contract cần nhiều release hơn và giữ temporary schema duplication.
- Dual-write tăng code complexity và có thể tạo inconsistency nếu không có verification/backfill strategy.
- Staging slot tăng release safety nhưng thêm hosting/configuration complexity.
- Observation gate kéo dài deployment duration nhưng giảm xác suất phát hiện regression quá muộn.
- Không phải migration nào cũng cần multi-release flow; additive nullable column đơn giản có thể deploy gọn hơn nếu compatibility rõ ràng.

## Cách kiểm thử

1. **Compatibility test:** old app version chạy integration tests trên schema sau bước Expand.
2. **Migration test:** apply migration trên production-like dataset, đo duration, locks và failure/rollback behavior.
3. **Rollback rehearsal:** deploy new app rồi redeploy old app trên schema hiện tại; critical flows vẫn hoạt động.
4. **Smoke/E2E test:** authentication, customer read, safe write/read-back và critical API sau deployment.
5. **Failure-path test:** migration thành công nhưng app deployment fail; runbook phải đưa hệ thống về serving state mà không yêu cầu reverse destructive migration.

## Quan sát trong production

Theo dõi:

- application version/build SHA trên từng instance;
- deployment start/end và artifact checksum;
- 5xx/error rate;
- p50/p95/p99 latency;
- SQL errors, deadlocks, blocking và migration duration;
- authentication failures;
- critical business smoke-test results;
- instance startup/readiness failures;
- dependency telemetry trong Application Insights;
- feature-flag/config version nếu rollout theo phase;
- row-count/backfill progress và data-quality invariants;
- rollback/redeploy success metrics.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận chạy migration ngay trong application startup, và điều kiện nào khiến cách đó trở nên không an toàn?
2. Nếu backfill mất 6 giờ trên bảng rất lớn, bạn sẽ kiểm soát lock, throttling và observability như thế nào?
3. Nếu business yêu cầu rollback trong 5 phút nhưng schema change không backward compatible, bạn sẽ thay đổi release design ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache key phải mô tả **rendering context**, không chỉ content identity.
- Personalized HTML và shared public CDN cache là một security boundary, không chỉ là performance decision.
- Per-instance memory cache, distributed cache và CDN cache có consistency/failure model khác nhau.
- Cache invalidation nên gắn với content lifecycle/version khi stale content có business impact.
- Production deployment phải reason về **code + schema + configuration + artifact identity**, không chỉ application package.
- Database migration an toàn trong multi-instance rollout thường cần backward compatibility window.
- Rollback phải được thiết kế và test trước release; redeploy binary cũ không tự động khôi phục compatibility.
- Health check, smoke test và telemetry gate phục vụ các mục đích khác nhau.

## Mẫu tư duy cần nhớ

1. **Match cache scope to personalization scope.**
2. **Treat shared caches as data-isolation boundaries.**
3. **Expand before contract when schema and code versions overlap.**
4. **Design rollback before deployment, not during the incident.**
5. **Validate business behavior, not only process liveness.**
