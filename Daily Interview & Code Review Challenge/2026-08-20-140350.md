# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, Change Tracker, performance diagnosis, observability

## Bối cảnh

Một ASP.NET Core API đọc danh sách nhân viên và trạng thái mailbox từ PostgreSQL bằng EF Core. Sau một đợt refactor, endpoint vẫn trả dữ liệu đúng nhưng p95 latency tăng mạnh khi tenant có vài nghìn nhân viên. Database monitoring cho thấy số SELECT trên mỗi request cao hơn trước. Đoạn application service tạo một `IQueryable<Employee>`, truyền qua vài method để thêm filter, sau đó vừa gọi `CountAsync()`, vừa enumerate để map DTO. Một số helper còn truy cập navigation property. Team nói rằng “LINQ chỉ chạy query một lần vì biến query đã được tạo rồi” và đề xuất thêm `AsNoTracking()` là đủ.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc tạo `IQueryable` đến khi endpoint hoàn tất: query được thực thi khi nào, vì sao có thể phát sinh nhiều SQL statement, Change Tracker ảnh hưởng thế nào, misconception của team là gì, rủi ro production ra sao và bạn sẽ chứng minh giả thuyết bằng evidence nào?

## Câu hỏi làm rõ nên cân nhắc

- Navigation properties có lazy loading được bật hay không?
- `CountAsync()` và materialization có cùng filter/projection không?
- Endpoint chỉ đọc hay còn sửa entity trong cùng `DbContext`?
- Số SQL statement/request tăng ở tất cả tenant hay chỉ tenant lớn?
- Có pagination, projection và index phù hợp với filter/order hiện tại không?

## Gợi ý tư duy

**Gợi ý 1:** Phân biệt xây expression tree với thực thi query.  
**Gợi ý 2:** Xem từng terminal operation/materialization, navigation loading và tracking.  
**Gợi ý 3:** Đừng tối ưu theo cảm giác; capture SQL, query count, execution plan, allocation và latency theo từng phase.

## Cấu trúc trả lời đề xuất

1. Làm rõ lifecycle của `DbContext` và query.
2. Mô tả deferred execution.
3. Liệt kê từng điểm có thể round-trip database.
4. Phân tích tracking/no-tracking và navigation loading.
5. Xác minh bằng logging/tracing/profiling.
6. Đề xuất projection/pagination/query-shape phù hợp.
7. Kiểm thử correctness và performance.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chủ yếu biểu diễn query; tạo biến không đồng nghĩa SQL đã chạy hoặc kết quả đã được cache.
- Các terminal operation như `CountAsync()`, `ToListAsync()`, `FirstAsync()` có thể tạo các database query riêng.
- Enumerate lại một query chưa materialize có thể thực thi lại.
- Tracking có overhead khi không cần update, nhưng `AsNoTracking()` không tự sửa N+1, duplicate execution hay query shape xấu.

### Điểm cộng

- Nhận ra lazy loading, nếu được cấu hình và sử dụng, có thể tạo N+1 khi truy cập navigation.
- Dùng projection trực tiếp sang DTO để giảm column/entity materialization.
- Tách requirement “total count” khỏi “page data” và đánh giá xem UI có thật sự cần exact count không.

### Nâng cao

- Phân biệt split query/single query khi include collection; đánh giá cartesian explosion so với extra round-trips.
- Dùng OpenTelemetry/EF Core command logging, database execution plan và benchmark/load test để lượng hóa.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, không cần entity tracking và dữ liệu lớn cần pagination.

Đầu tiên tôi xác định tất cả điểm materialization. `Where`, `Select`, `OrderBy` thường chỉ tiếp tục xây expression tree; `CountAsync()` gửi một query count, còn `ToListAsync()` gửi query lấy data. Nếu code enumerate lại query, database có thể bị gọi lại. Nếu navigation được lazy-load, việc map từng entity có thể phát sinh thêm query theo từng row.

Tôi sẽ bật structured EF Core command telemetry trong môi trường phù hợp, gắn correlation/request ID, đếm database commands/request, xem SQL và execution plan. Sau đó sửa query thành projection server-side, `AsNoTracking()` cho read-only, pagination rõ ràng, tránh lazy loading trong đường nóng và chỉ load dữ liệu cần thiết. Exact total count chỉ giữ nếu business cần.

`AsNoTracking()` giảm tracking overhead nhưng không phải universal performance fix. Nếu endpoint sau đó sửa entity thì tracking có thể hữu ích; nếu cần identity resolution trong read query có graph lặp, lựa chọn no-tracking cũng cần cân nhắc theo query cụ thể.

Test gồm integration test kiểm tra kết quả, assertion/telemetry về query count ở scenario quan trọng, load test với tenant lớn và so sánh p50/p95/p99, CPU, allocations, DB time trước/sau.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng `AsNoTracking()` mà trước hết xác định query thực thi bao nhiêu lần. Với EF Core, việc giữ một `IQueryable` chỉ giữ query definition; `CountAsync()` và `ToListAsync()` là hai terminal operations nên bình thường sẽ tạo hai database calls. Nếu query bị enumerate lại hoặc navigation lazy-load trong mapper thì số round-trip còn tăng thêm. Tracking có thể làm tăng allocation và Change Tracker work ở endpoint read-only, nhưng nó không giải quyết duplicate query hay N+1.

Em sẽ xác minh bằng EF Core command logs hoặc tracing có correlation ID, đếm SQL/request, xem duration và execution plan. Nếu endpoint chỉ đọc, em ưu tiên projection trực tiếp sang DTO, no-tracking, pagination và explicit query shape. Nếu UI không thật sự cần exact total count, em cũng xem lại requirement đó. Sau thay đổi em chạy integration và load test trên dataset gần production, theo dõi p95, DB duration, query count và allocations. Nếu endpoint cần update entity trong cùng unit of work thì recommendation về tracking sẽ thay đổi.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution()` có ích so với `AsNoTracking()`?
2. Nếu `Include` nhiều collection làm một query rất lớn, bạn cân nhắc split query thế nào?
3. Nếu team phản biện rằng giảm từ 3 query xuống 2 không đáng kể, bạn chứng minh ROI ra sao?

## Lỗi trả lời thường gặp

- Nói mọi LINQ operation đều thực thi SQL ngay.
- Cho rằng `IQueryable` tự cache kết quả.
- Dùng `AsNoTracking()` như câu trả lời duy nhất.
- Không kiểm tra lazy loading/N+1.
- Không đề xuất cách đo trước và sau tối ưu.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1.0

# Câu 2 — Incident: Hangfire xử lý thanh toán nghiệp vụ hai lần sau deployment

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, database concurrency, reliability, observability

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để xử lý workflow hậu kỳ sau khi một giao dịch được xác nhận: cập nhật trạng thái DB, gọi external API và gửi notification. Sau deployment, support phát hiện một số khách hàng nhận notification hai lần và external provider ghi nhận một số request nghiệp vụ lặp. Dashboard cho thấy một vài job đã retry; đồng thời hệ thống đang chạy nhiều app instances. Chưa rõ duplicate bắt nguồn từ enqueue, retry, timeout, deployment hay business logic.

## Câu hỏi chính

Bạn là senior engineer on-call. Hãy trình bày cách xử lý incident từ impact assessment và mitigation đến evidence collection, hypothesis, root-cause investigation, short-term fix, long-term prevention, verification và monitoring — không giả định trước rằng Hangfire là nguyên nhân duy nhất.

## Câu hỏi làm rõ nên cân nhắc

- External API có hỗ trợ idempotency key hay operation lookup không?
- “Duplicate” nghĩa là job chạy hai lần hay business side effect xảy ra hai lần?
- Job có transaction boundary và trạng thái processing/completed như thế nào?
- Retry policy, timeout và worker count hiện tại là gì?
- Có unique business identifier/correlation ID xuyên suốt enqueue → job → external call không?

## Gợi ý tư duy

**Gợi ý 1:** Stabilize trước, root-cause sau.  
**Gợi ý 2:** Delivery/execution semantics không thay thế business idempotency.  
**Gợi ý 3:** Theo dõi một business operation xuyên DB, job storage và external provider để tìm điểm side effect bị lặp.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius và side effect nguy hiểm.
2. Giảm thiểu tác động mới.
3. Thu evidence theo correlation/business ID.
4. Lập nhiều hypothesis.
5. Reconstruct timeline.
6. Fix ngắn hạn.
7. Thiết kế idempotency và recovery dài hạn.
8. Verify bằng failure injection và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không đồng nhất “job executed twice” với “bug của scheduler”.
- Side effect quan trọng phải chịu được retry/redelivery.
- Có idempotency/business operation key và atomic guard ở persistence layer.
- Không retry mù các external side effects không idempotent.

### Điểm cộng

- Reconcile các operation nghi duplicate thay vì chỉ restart worker.
- Phân biệt transient failure trước/sau khi provider đã nhận request.
- Dùng unique constraint/conditional update để biến concurrency race thành deterministic outcome.

### Nâng cao

- Outbox/inbox hoặc state machine cho workflow nhiều side effect.
- Idempotency key xuyên external API nếu provider hỗ trợ.
- Failure injection ở các điểm “external success nhưng local persistence fail”.

## Hướng giải quyết tham khảo

Đầu tiên xác định blast radius: số operation bị ảnh hưởng, side effect có liên quan tiền/dữ liệu hay chỉ notification, thời gian bắt đầu và deployment correlation. Nếu duplicate side effect còn tiếp diễn, giảm worker/concurrency hoặc tạm dừng riêng queue/job type nguy hiểm; không tắt toàn hệ thống nếu không cần.

Evidence cần gồm job ID, business operation ID, retry history, timestamps, worker instance, DB state transitions, external request/response identifiers và deployment logs. Hypothesis gồm enqueue hai lần, retry sau timeout, process termination sau external success nhưng trước local commit, concurrent producers, missing unique constraint, manual replay hoặc provider behavior.

Long-term, workflow phải idempotent theo business operation. Một DB constraint hoặc atomic state transition đảm bảo chỉ một logical operation được nhận xử lý; external request dùng stable idempotency key nếu provider hỗ trợ. Với nhiều side effects, có thể lưu durable state/outbox và xử lý từng step có retry semantics rõ ràng. Notification cũng nên có dedup key riêng nếu business yêu cầu exactly-once-visible behavior.

Verification phải tái hiện retry, worker crash, timeout và concurrent execution. Theo dõi duplicate-prevented count, retry rate, job age, external error rate và reconciliation mismatch.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách hai câu hỏi: job có chạy nhiều lần không, và business side effect có bị áp dụng nhiều lần không. Trước hết em xác định blast radius và nếu side effect còn nguy hiểm thì pause riêng queue hoặc giảm concurrency để ngăn phát sinh mới. Sau đó em trace theo business operation ID qua enqueue log, Hangfire retry history, DB transition và external provider.

Em sẽ giữ nhiều giả thuyết: duplicate enqueue, retry sau timeout, app chết sau khi provider thành công nhưng trước khi lưu local state, concurrent producer hoặc thiếu unique constraint. Dù root cause cụ thể là gì, workflow có side effect phải được thiết kế idempotent vì retry/failure luôn có thể xảy ra. Em dùng stable operation key, atomic database guard/unique constraint, và nếu provider hỗ trợ thì gửi cùng idempotency key cho mọi retry. Với workflow nhiều bước, em cân nhắc durable state và outbox thay vì cố bao external call trong DB transaction.

Sau fix em chạy concurrency/failure tests, đặc biệt crash ở ranh giới external success/local commit, rồi monitor retry rate, duplicate prevented, queue latency và reconciliation với provider. Nếu provider không hỗ trợ idempotency thì thiết kế recovery sẽ thận trọng hơn và có thể cần lookup/reconciliation trước retry.”

## Câu hỏi đào sâu

1. Vì sao distributed lock một mình chưa đủ đảm bảo business idempotency?
2. Bạn xử lý thế nào nếu external API thành công nhưng response timeout và provider không hỗ trợ idempotency key?
3. Nếu unique constraint làm nhiều worker fail bằng exception, bạn cải thiện flow thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng retry hoặc tắt retry mà không xử lý semantics.
- Tin rằng scheduler đảm bảo side effect đúng một lần.
- Dùng distributed lock như bảo đảm duy nhất.
- Không có reconciliation plan.
- Không phân biệt mitigation và permanent fix.

## Thang điểm 0–10

- Requirement clarification: 1.0
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.5
- Communication: 1.0

# Câu 3 — Thiết kế AI agent review pull request có quyền dùng MCP tools

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, MCP/tool security, deterministic validation, evaluation, human approval, auditability

## Bối cảnh

Team muốn xây một AI review agent cho repository .NET. Agent đọc diff, repository rules và test results; có thể dùng tools để tìm code, chạy test và đọc issue liên quan. Product owner muốn sau này cho agent tự sửa code và mở PR để giảm thời gian review. Repository có source code nội bộ và secrets không được phép đưa vào context. Một số tool có thể đọc rộng hơn phạm vi PR. Team hiện đánh giá chất lượng chủ yếu bằng việc “review có vẻ hợp lý”.

## Câu hỏi chính

Hãy thiết kế agent này từ MVP đến production: vì sao cần AI, phần nào phải deterministic, context nào được cấp, tool/permission boundary ra sao, output được validate thế nào, hallucination được phát hiện ra sao, chất lượng được đo thế nào, fallback/human approval ở đâu và hệ thống được audit/monitor như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được phép thay đổi repository?
- Repository/data classification và secret-handling policy là gì?
- Những ngôn ngữ/framework và loại PR nào nằm trong scope MVP?
- False positive hay missed critical issue gây hại hơn?
- Có historical review data/test corpus để tạo evaluation set không?

## Gợi ý tư duy

**Gợi ý 1:** Tách reasoning không xác định khỏi enforcement xác định.  
**Gợi ý 2:** Tool access phải theo least privilege và task scope, không theo “agent cần tiện”.  
**Gợi ý 3:** Chỉ promote từ read-only reviewer sang write-capable agent khi có eval, policy gates, sandbox và approval boundary rõ ràng.

## Cấu trúc trả lời đề xuất

1. Xác định value proposition và failure cost.
2. Chốt scope MVP.
3. Thiết kế context pipeline.
4. Thiết kế tool/permission model.
5. Structured output và deterministic validation.
6. Evaluation/offline benchmark.
7. Human approval và fallback.
8. Audit, monitoring, cost/latency controls.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho semantic reasoning/review; authz, secret filtering, schema validation, command allowlist và merge policy phải deterministic.
- MVP read-only, least privilege.
- Context được chọn theo PR/task, không dump toàn repository.
- Output có schema/evidence reference và validation trước khi publish.
- Có human review cho high-impact action.

### Điểm cộng

- Eval set từ historical PRs + seeded defects, đo precision/recall hoặc acceptance theo severity/category.
- Tool outputs được xem là untrusted input; tránh để nội dung repository tự mở rộng quyền.
- Budget cho token, latency và tool calls.

### Nâng cao

- Policy engine riêng với capability-scoped credentials.
- Sandbox ephemeral cho test/code modification.
- Shadow mode/canary trước khi bật write action.
- Audit trail gồm prompt/context manifest, model/config version, tool calls, outputs và approval.

## Hướng giải quyết tham khảo

**MVP:** agent chỉ đọc diff, selected surrounding code, repository instructions và CI results; không có write permission. Một deterministic preprocessor loại secret/sensitive paths theo policy và xây context manifest. Agent trả structured findings gồm file/line, severity, reasoning, evidence và suggested action. Validator kiểm tra schema, referenced file/line tồn tại và policy trước khi comment.

Tool gateway áp dụng allowlist, scope theo repo/PR và read-only credential. Nội dung source, issue hay tool response đều không được phép thay đổi policy hoặc cấp thêm capability. Tool calls có timeout, size limit, rate/cost budget và audit log.

Quality không đo bằng cảm giác. Tạo eval corpus gồm historical defects, accepted/rejected review comments và seeded cases. Theo dõi precision theo severity, useful-comment acceptance, critical miss rate, latency và cost. Với security finding, có thể kết hợp deterministic scanners thay vì giao toàn bộ cho LLM.

Khi mở rộng sang sửa code, chạy trong ephemeral sandbox, branch riêng, không push/merge trực tiếp bằng credential rộng. Test/lint/security checks là deterministic gates; human approval trước write hoặc merge tùy risk policy. Fallback là trả về “insufficient evidence” hoặc chuyển người review, không ép model đoán.

## Mẫu trả lời trong phỏng vấn

“Em sẽ bắt đầu bằng read-only reviewer vì giá trị của LLM nằm ở semantic reasoning trên diff, còn permission, secret filtering, schema validation và merge policy phải deterministic. Context chỉ gồm diff, code lân cận cần thiết, repo rules và CI evidence; em không dump cả repo. Trước model có policy layer lọc sensitive paths, sau model có validator kiểm tra structured finding và evidence.

MCP/tool gateway dùng least-privilege credential, allowlist tool và scope theo đúng repo/PR. Quan trọng là source code hoặc tool output được coi là untrusted data, không được tự thay đổi policy hay xin thêm quyền. Em log model/config version, context manifest, tool calls, result và approval để audit.

Về quality, em xây eval set từ PR lịch sử và seeded defects, đo critical miss rate, precision/acceptance theo severity, latency và cost. Chỉ khi read-only mode đạt ngưỡng ổn định em mới cho sửa code trong sandbox/branch riêng. Test, lint và security checks là deterministic gates; action có impact cao cần human approval. Nếu evidence không đủ thì agent abstain hoặc chuyển người, thay vì hallucinate.”

## Câu hỏi đào sâu

1. Prompt injection nằm trong source code hoặc issue có thể tác động tool-using agent thế nào?
2. Nếu human acceptance rate cao nhưng agent thường bỏ sót security bug nghiêm trọng, metric tổng thể có còn đủ không?
3. Product owner yêu cầu agent tự merge để tối đa tốc độ; bạn thiết kế điều kiện nào trước khi chấp nhận?

## Lỗi trả lời thường gặp

- “Cho agent access repo và để model quyết định tool nào cần dùng.”
- Không tách deterministic controls khỏi model reasoning.
- Chỉ đánh giá bằng demo hoặc subjective feedback.
- Cấp write permission ngay từ MVP.
- Không có abstention/fallback/audit trail.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5

# Tổng kết hôm nay

## Kiến thức trọng tâm

EF Core cần được hiểu theo query execution thực tế thay vì chỉ syntax LINQ; performance phải được chứng minh bằng SQL/query count và telemetry. Background jobs phải thiết kế retry cùng idempotency vì execution retry và partial failure là điều bình thường cần chịu được. AI agent production cần tách probabilistic reasoning khỏi deterministic policy, validation và authorization; tool access phải least privilege và chất lượng phải được đo bằng eval có failure-oriented metrics.

## Mẫu tư duy cần nhớ

- Clarify execution semantics trước khi tối ưu.
- Measure before optimizing: query count, latency, DB time và allocation phải có evidence.
- Stabilize incident trước rồi mới điều tra root cause.
- Design retries together with idempotency và reconciliation.
- Với AI: deterministic controls bao quanh probabilistic reasoning; least privilege + validation + evaluation + human approval.
