# Chế độ hôm nay: Interview Question Mode

# Câu 1 — EF Core Tracking và truy vấn phát sinh ngoài dự kiến

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 20 phút
**Kỹ năng được đánh giá:** EF Core internals, performance debugging, production analysis

## Bối cảnh
Một API ASP.NET Core dùng EF Core để trả danh sách đơn hàng. Sau khi dữ liệu tăng lên vài triệu bản ghi, một endpoint bắt đầu tăng latency. Log SQL cho thấy nhiều query nhỏ phát sinh thay vì một query chính.

## Câu hỏi chính
Hãy giải thích điều gì xảy ra bên trong EF Core khi tracking, lazy loading hoặc deferred execution được sử dụng sai. Vì sao hiện tượng này xảy ra? Rủi ro production là gì? Bạn xác minh giả thuyết như thế nào?

## Câu hỏi làm rõ nên cân nhắc
- Endpoint có yêu cầu cập nhật entity sau khi đọc không?
- Có bật lazy loading không?
- Query projection hay entity loading?

## Gợi ý tư duy
- Gợi ý 1: Xem cách ORM chuyển LINQ thành SQL.
- Gợi ý 2: Kiểm tra tracking, navigation property và số lượng SQL command.
- Gợi ý 3: Dùng projection, logging SQL và đo query plan.

## Cấu trúc trả lời đề xuất
1. Làm rõ workload.
2. Phân tích execution pipeline.
3. Xác định nguyên nhân.
4. Đề xuất giải pháp và trade-off.
5. Đưa ra cách đo lường.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Hiểu LINQ expression không phải lúc nào cũng execute ngay.
- Hiểu tracking ảnh hưởng memory/change detection.
- Biết kiểm tra SQL thực tế.

### Điểm cộng
- Nhắc tới AsNoTracking, projection, compiled query.

### Nâng cao
- Phân tích query plan và index.

## Hướng giải quyết tham khảo
Giả định endpoint chỉ đọc dữ liệu. Giải pháp ưu tiên dùng projection DTO, AsNoTracking, giới hạn dữ liệu bằng pagination. Nếu cần cập nhật entity mới dùng tracking có chủ đích.

## Mẫu trả lời trong phỏng vấn
"Em sẽ không kết luận ngay là EF Core chậm. Em sẽ kiểm tra SQL generated, số lượng query, execution plan và memory usage. Nếu nguyên nhân là tracking hoặc N+1 query, em sẽ chuyển sang projection và kiểm soát navigation loading..."

## Câu hỏi đào sâu
- Khi nào không nên dùng AsNoTracking?
- Split query và single query khác nhau thế nào?
- Làm sao xử lý transaction khi đọc và ghi?

## Lỗi trả lời thường gặp
- Chỉ nói tối ưu index.
- Đổ lỗi cho ORM.
- Không đề cập đo lường.

## Thang điểm 0–10
- Requirement clarification: 2
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 2
- Production readiness: 2

# Câu 2 — Thiết kế hệ thống xử lý background job đáng tin cậy

**Loại câu hỏi:** System design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 30 phút
**Kỹ năng được đánh giá:** Architecture, reliability, concurrency

## Bối cảnh
Công ty cần xây dựng hệ thống xử lý document processing. Người dùng upload file, hệ thống chạy OCR, gọi external API và cập nhật trạng thái. Có thể có hàng trăm nghìn job mỗi ngày.

## Câu hỏi chính
Thiết kế hệ thống này với ASP.NET Core, Hangfire hoặc queue. Bạn sẽ thiết kế flow, database model, retry, idempotency, monitoring và recovery như thế nào?

## Câu hỏi làm rõ nên cân nhắc
- SLA xử lý là bao lâu?
- Có cần ordering không?
- External API có giới hạn rate không?

## Gợi ý tư duy
- Gợi ý 1: Bắt đầu từ business flow.
- Gợi ý 2: Nghĩ về failure và retry.
- Gợi ý 3: Retry phải đi cùng idempotency.

## Hướng giải quyết tham khảo
Dùng modular monolith cho MVP. Có bảng Job, trạng thái, retry count, correlation id. Worker xử lý bất đồng bộ. Mỗi bước cần idempotent. Dùng logs, metrics, tracing để theo dõi.

## Câu hỏi đào sâu
- Khi worker chết giữa transaction thì sao?
- Khi external API timeout nhiều lần?
- Khi cần scale lên nhiều worker?

# Câu 3 — AI Engineering: Xây dựng Code Review Agent

**Loại câu hỏi:** AI engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** AI architecture, evaluation, security

## Bối cảnh
Team muốn xây AI agent hỗ trợ review pull request C#/.NET. Agent có quyền đọc repository, issue, test result và tạo nhận xét.

## Câu hỏi chính
Thiết kế agent như thế nào để đảm bảo chất lượng, tránh hallucination, kiểm soát quyền truy cập và đo hiệu quả?

## Gợi ý tư duy
- Gợi ý 1: Không để LLM tự quyết mọi thứ.
- Gợi ý 2: Cần context engineering và validation.
- Gợi ý 3: Kết hợp deterministic tools với model.

## Hướng giải quyết tham khảo
Agent nên có giới hạn permission, structured output, rule-based checks, test execution tools, evaluation dataset và human approval trước action quan trọng.

# Tổng kết hôm nay

## Kiến thức trọng tâm
- ORM cần hiểu execution behavior.
- Reliability cần thiết kế từ failure mode.
- AI agent cần tool boundary và evaluation.

## Mẫu tư duy cần nhớ
- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Validate AI output deterministically.
- Observability là một phần của architecture.
