# Code Review Challenge 1 — Cosmos DB: tiến độ học bị ghi đè và hot partition

## Bối cảnh

Một nền tảng học trực tuyến phục vụ 200.000 người dùng. ASP.NET Core API lưu tiến độ vào Cosmos DB, container partition theo /tenantId. Tenant lớn chiếm 70% request; khi người dùng học đồng thời trên hai thiết bị, tiến độ đôi lúc bị lùi. Dashboard ghi nhận HTTP 429 và p99 tăng cao. API cần hỗ trợ retry khi mạng không ổn định. Các giá trị throughput là giả định của bài tập, cần đo thực tế trước khi quyết định thiết kế.

## Đoạn code cần review

~~~csharp
public sealed record SaveProgress(
    string TenantId, string UserId, string LessonId,
    int Score, DateTime UpdatedAt);

public sealed class ProgressService
{
    private readonly Container _container;
    private readonly ILogger<ProgressService> _logger;

    public ProgressService(CosmosClient client,
        ILogger<ProgressService> logger)
    {
        _container = client.GetContainer("learning", "progress");
        _logger = logger;
    }

    public async Task SaveAsync(SaveProgress command)
    {
        var id = $"{command.UserId}:{command.LessonId}";
        var key = new PartitionKey(command.TenantId);
        Progress progress;
        try
        {
            progress = (await _container.ReadItemAsync<Progress>(
                id, key)).Resource;
        }
        catch (CosmosException ex)
            when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            progress = new Progress {
                id = id, tenantId = command.TenantId
            };
        }

        progress.score = command.Score;
        progress.updatedAt = command.UpdatedAt;
        await _container.UpsertItemAsync(progress, key);
        _logger.LogInformation("Saved {Progress}",
            JsonSerializer.Serialize(progress));
    }
}

public sealed class Progress
{
    public string id { get; set; } = "";
    public string tenantId { get; set; } = "";
    public int score { get; set; }
    public DateTime updatedAt { get; set; }
}
~~~

## Kết quả code review tham khảo

### [Critical] — Lost update

**Vấn đề:** Read-modify-write rồi Upsert không kiểm tra version.  
**Tại sao xảy ra:** Concurrent requests đọc cùng state và writer đến sau ghi đè writer trước.  
**Ảnh hưởng production:** Score bị lùi, dữ liệu xác nhận bị mất.  
**Cách sửa:** Dùng ETag conditional Replace và merge theo business invariant; xử lý 412 bằng bounded retry.

### [High] — Hot logical partition

**Vấn đề:** Tenant lớn tập trung workload vào cùng logical partition.  
**Tại sao xảy ra:** Partition key có cardinality thấp tương đối với workload.  
**Ảnh hưởng production:** Throttling 429 và p99 tăng.  
**Cách sửa:** Đo RU và partition distribution; cân nhắc synthetic key tenant/user. Chuyển container bằng backfill và controlled cutover, không giả định có thể đổi partition key tại chỗ.

### [High] — Retry thiếu idempotency và thứ tự nghiệp vụ

**Vấn đề:** Client retry với score cũ có thể ghi đè score mới.  
**Tại sao xảy ra:** Không có operation ID hoặc version/order rule.  
**Ảnh hưởng production:** Sai kết quả học tập.  
**Cách sửa:** Định nghĩa score là latest-version hay maximum-score; dùng version server-side và idempotency key khi có side effects.

### [High] — Không xác minh authorization

**Vấn đề:** Service nhận tenant/user từ payload mà không thể hiện security boundary.  
**Tại sao xảy ra:** Thiếu đối chiếu authenticated principal.  
**Ảnh hưởng production:** Cross-tenant modification nếu controller cũng thiếu kiểm tra.  
**Cách sửa:** Enforce authorization tại API và application layer.

### [Medium] — Thiếu CancellationToken

**Vấn đề:** Cosmos calls không nhận cancellation.  
**Tại sao xảy ra:** Không propagate request cancellation.  
**Ảnh hưởng production:** Lãng phí tài nguyên khi client disconnect.  
**Cách sửa:** Truyền CancellationToken và giới hạn tổng thời gian xử lý.

### [Medium] — Thừa read và tăng RU

**Vấn đề:** Mỗi update đọc toàn bộ document trước khi ghi.  
**Tại sao xảy ra:** Thiết kế generic read-modify-write.  
**Ảnh hưởng production:** Tăng RU, thêm network round-trip.  
**Cách sửa:** Đánh giá Patch hoặc conditional writes theo invariant; benchmark trước khi thay.

### [Medium] — Client clock quyết định updatedAt

**Vấn đề:** Timestamp thiết bị không đáng tin.  
**Tại sao xảy ra:** Không phân biệt event time và server commit time.  
**Ảnh hưởng production:** Audit và ordering sai.  
**Cách sửa:** Lưu serverRecordedAt riêng, validate clientOccurredAt.

### [Medium] — Sensitive logging

**Vấn đề:** Log nguyên progress document.  
**Tại sao xảy ra:** Serialize object vào structured logs.  
**Ảnh hưởng production:** Lộ định danh học viên, tăng log cost.  
**Cách sửa:** Log operation ID, latency, RU, status và hashed identifiers khi cần.

## Phiên bản đề xuất

Giả định business rule: score cao nhất đã được xác nhận không được giảm; container mới partition theo /userPartition. Ví dụ này minh họa concurrency control, chưa thay thế authorization, validation và migration production.

~~~csharp
public sealed class Progress
{
    public string id { get; set; } = "";
    public string userPartition { get; set; } = "";
    public int score { get; set; }
    public DateTimeOffset serverRecordedAt { get; set; }
}

public sealed class ProgressWriter(Container container)
{
    public async Task SaveAsync(
        string tenant, string user, string lesson,
        int score, CancellationToken ct)
    {
        var pk = $"{tenant}|{user}";
        var key = new PartitionKey(pk);

        for (int attempt = 0; attempt < 3; attempt++)
        {
            try
            {
                var current = await container.ReadItemAsync<Progress>(
                    lesson, key, cancellationToken: ct);
                if (current.Resource.score >= score) return;

                var updated = current.Resource;
                updated.score = score;
                updated.serverRecordedAt = DateTimeOffset.UtcNow;
                await container.ReplaceItemAsync(
                    updated, lesson, key,
                    new ItemRequestOptions {
                        IfMatchEtag = current.ETag
                    }, ct);
                return;
            }
            catch (CosmosException ex)
                when (ex.StatusCode == HttpStatusCode.NotFound)
            {
                try
                {
                    await container.CreateItemAsync(
                        new Progress {
                            id = lesson, userPartition = pk,
                            score = score,
                            serverRecordedAt = DateTimeOffset.UtcNow
                        }, key, cancellationToken: ct);
                    return;
                }
                catch (CosmosException ex)
                    when (ex.StatusCode == HttpStatusCode.Conflict)
                {
                    continue;
                }
            }
            catch (CosmosException ex)
                when (ex.StatusCode == HttpStatusCode.PreconditionFailed)
            {
                continue;
            }
        }
        throw new InvalidOperationException(
            "Concurrent update exceeded retry budget");
    }
}
~~~

## Giải thích thiết kế sau khi sửa

ETag giúp phát hiện thay đổi giữa read và write. CreateItem đảm bảo một ID duy nhất trong logical partition; 409 được xử lý bằng đọc lại. Invariant maximum score làm retry an toàn với bài toán giả định. Partition theo user giúp phân phối workload tenant lớn, nhưng phải xác minh query patterns và uniqueness trước rollout. Production cần chuyển lỗi concurrency thành response/retry policy thích hợp.

## Trade-offs

Cross-partition tenant reporting có thể tốn RU hơn; có thể dùng read model riêng. Conditional writes phát sinh retries khi contention cao. Nếu score được phép giảm do chấm lại, maximum-score rule không hợp lệ: cần business version hoặc event ordering thay thế. Migration đòi hỏi backfill, reconciliation và rollback.

## Cách kiểm thử

1. Concurrency integration: 50 requests cùng lesson, score cuối bằng maximum theo invariant.
2. Failure-path: Inject 409, 412, 429, timeout, cancellation và xác minh retry budget.
3. Load test: Tenant lớn với nhiều user, đo RU, 429 và p99 trước/sau.
4. Security test: Không ghi được tiến độ user/tenant khác.
5. Migration validation: Backfill, dual-read, reconciliation khi dữ liệu tiếp tục thay đổi.

## Quan sát trong production

Application Insights: request/dependency traces, latency, correlation ID. Cosmos diagnostics: RU/request, 429, 409, 412, partition distribution, retries. Alert theo error budget, p99 và số write thất bại; không log nội dung nhạy cảm.

1. Nếu cần audit từng attempt, document hiện tại có đủ không?
2. Khi nào dùng transactional batch thay vì optimistic concurrency?
3. Làm sao rollout partition key mới không mất update?

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Item = { id: string; title: string; excerpt: string }
const query = ref('')
const department = ref('all')
const page = ref(1)
const items = ref<Item[]>([])
const loading = ref(false)
const error = ref('')
const cache = new Map<string, Item[]>()

async function load() {
  loading.value = true
  error.value = ''
  const key = query.value + department.value + page.value

  if (cache.has(key)) {
    items.value = cache.get(key)!
    loading.value = false
    return
  }

  try {
    const url = '/api/search?q=' + query.value
      + '&department=' + department.value + '&page=' + page.value
    const response = await fetch(url, { credentials: 'include' })
    const data = await response.json()
    items.value = data.items
    cache.set(key, data.items)
  } catch {
    error.value = 'Không thể tải dữ liệu'
  } finally {
    loading.value = false
  }
}

watch([query, department, page], load)
onMounted(load)
</script>

<template>
  <input v-model="query" />
  <select v-model="department">
    <option value="all">Tất cả</option>
    <option value="hr">HR</option>
  </select>
  <button @click="page++">Trang tiếp</button>
  <p v-if="loading">Đang tải...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="item in items" :key="item.id">
      <strong>{{ item.title }}</strong>
      <div v-html="item.excerpt"></div>
    </li>
  </ul>
</template>

## Kết quả code review tham khảo

### [Critical] — XSS qua v-html

**Vấn đề:** Untrusted excerpt được chèn như HTML.  
**Tại sao xảy ra:** v-html không tự biến nội dung thành safe plain text.  
**Ảnh hưởng production:** Script injection và thao tác trái phép trong browser session.  
**Cách sửa:** API trả plain text và render bằng interpolation; nếu cần highlight, trả tokenized text hoặc sanitize theo policy đã review.

### [High] — Stale response overwrite

**Vấn đề:** Request cũ có thể cập nhật UI sau request mới.  
**Tại sao xảy ra:** Không abort hoặc generation guard.  
**Ảnh hưởng production:** Search hiển thị sai query/filter.  
**Cách sửa:** AbortController kết hợp request generation ID.

### [High] — HTTP errors không được kiểm tra

**Vấn đề:** Fetch resolve cho 4xx/5xx; code parse body như success.  
**Tại sao xảy ra:** Thiếu response.ok và payload validation.  
**Ảnh hưởng production:** Empty state sai, crash hoặc dữ liệu không đúng.  
**Cách sửa:** Kiểm tra HTTP status, schema và error policy.

### [Medium] — Cache key collision

**Vấn đề:** Nối chuỗi ba biến không delimiter.  
**Tại sao xảy ra:** Key không biểu diễn tuple duy nhất.  
**Ảnh hưởng production:** Cache trả nhầm filter/page.  
**Cách sửa:** Serialize tuple hoặc URLSearchParams.

### [Medium] — Cache không có TTL hoặc user scope

**Vấn đề:** Cache tồn tại lâu và không invalidation.  
**Tại sao xảy ra:** Không xác định freshness/authorization policy.  
**Ảnh hưởng production:** Stale results và nguy cơ dữ liệu cũ còn hiện khi đổi account.  
**Cách sửa:** Bỏ cache cho dữ liệu nhạy cảm hoặc thêm scope, TTL và clear on logout.

### [Medium] — Loading state race

**Vấn đề:** Finally của request cũ tắt loading request mới.  
**Tại sao xảy ra:** Shared boolean không gắn với request identity.  
**Ảnh hưởng production:** Spinner sai và thao tác trùng.  
**Cách sửa:** Chỉ request mới nhất được cập nhật loading.

### [Medium] — URL chưa encode

**Vấn đề:** Query có ký tự đặc biệt làm hỏng tham số.  
**Tại sao xảy ra:** String concatenation.  
**Ảnh hưởng production:** Filter sai, request khó debug.  
**Cách sửa:** URLSearchParams.

### [Low] — Không debounce, không reset page

**Vấn đề:** Mỗi ký tự tạo request, đổi filter giữ page cũ.  
**Tại sao xảy ra:** Watch trực tiếp mọi input.  
**Ảnh hưởng production:** API QPS tăng, empty results gây nhầm.  
**Cách sửa:** Debounce query và reset page khi query/filter đổi.

## Phiên bản đề xuất

API cần trả excerpt plain text; frontend không sử dụng v-html.

~~~vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

type Item = { id: string; title: string; excerpt: string }
const query = ref('')
const department = ref('all')
const page = ref(1)
const items = ref<Item[]>([])
const loading = ref(false)
const error = ref('')
let generation = 0
let controller: AbortController | undefined
let timer: ReturnType<typeof setTimeout> | undefined

function schedule() {
  if (timer) clearTimeout(timer)
  controller?.abort()
  const id = ++generation
  loading.value = true
  error.value = ''
  timer = setTimeout(() => { void load(id) }, 250)
}

function valid(value: unknown): value is { items: Item[] } {
  if (!value || typeof value !== 'object' || !('items' in value))
    return false
  const a = (value as { items: unknown }).items
  return Array.isArray(a) && a.every(x =>
    x && typeof x.id === 'string'
      && typeof x.title === 'string'
      && typeof x.excerpt === 'string')
}

async function load(id: number) {
  const active = new AbortController()
  controller = active
  const params = new URLSearchParams({
    q: query.value, department: department.value,
    page: String(page.value)
  })
  try {
    const response = await fetch('/api/search?' + params, {
      credentials: 'same-origin', signal: active.signal
    })
    if (!response.ok) throw new Error('HTTP ' + response.status)
    const payload: unknown = await response.json()
    if (!valid(payload)) throw new Error('Invalid payload')
    if (id === generation) items.value = payload.items
  } catch {
    if (id === generation && !active.signal.aborted) {
      error.value = 'Không thể tải dữ liệu'
      items.value = []
    }
  } finally {
    if (id === generation) loading.value = false
  }
}

watch([query, department], () => {
  page.value = 1
  schedule()
})
watch(page, schedule)
schedule()
onBeforeUnmount(() => {
  if (timer) clearTimeout(timer)
  controller?.abort()
  generation++
})
</script>

<template>
  <input v-model="query" />
  <select v-model="department">
    <option value="all">Tất cả</option>
    <option value="hr">HR</option>
  </select>
  <button @click="page++" :disabled="loading">Trang tiếp</button>
  <p v-if="loading">Đang tải...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <ul>
    <li v-for="item in items" :key="item.id">
      <strong>{{ item.title }}</strong>
      <div>{{ item.excerpt }}</div>
    </li>
  </ul>
</template>
~~~

## Giải thích thiết kế sau khi sửa

AbortController giảm request không cần thiết, generation ID ngăn response cũ ghi đè kể cả khi abort không kịp. URLSearchParams encode tham số. Interpolation escape HTML. Runtime payload validation giúp UI không tin mù quáng vào API. Backend vẫn phải enforce authorization, rate limiting và query limits.

## Trade-offs

Debounce giảm tải nhưng tăng một chút độ trễ. Không cache làm tăng số request; cache chỉ hợp lý khi có TTL và authorization scope. Abort phía client không bảo đảm server ngừng xử lý; backend cần cancellation và telemetry riêng. Có thể dùng query library nếu nhiều màn hình cần cache/retry, không bắt buộc thêm dependency cho màn hình đơn giản.

## Cách kiểm thử

1. Playwright E2E: delay A, trả B trước, kết quả cuối phải thuộc B.
2. Security test: excerpt chứa HTML/script, phải hiển thị text không thực thi.
3. API failure test: 401, 403, 429, 500, malformed payload, network failure.
4. E2E: query chứa &, đổi filter ở page 5, kiểm tra encoding và reset page.
5. Load test: so sánh QPS và p95 khi gõ nhanh trước/sau debounce.

## Quan sát trong production

Theo dõi search interaction latency, abort count, stale-response guard hits, HTTP error rates, invalid payload và frontend error logs. Backend đo endpoint QPS, p95/p99, database query duration, correlation ID và rate limiting; không log search query chứa thông tin nhạy cảm.
