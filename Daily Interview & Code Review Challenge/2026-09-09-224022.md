# Code Review Challenge 1 — Redis cache key thiếu tenant scope làm rò dữ liệu cross-tenant và cache outage kéo sập API

**Chủ đề:** C#, .NET 8, ASP.NET Core, Redis, multi-tenancy, authorization, cache-aside, cache stampede, reliability, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một SaaS B2B chạy ASP.NET Core .NET 8. Mỗi tenant có catalog và pricing riêng. Cùng một `productId` có thể tồn tại ở nhiều tenant nhưng giá, discount và khả năng truy cập khác nhau.

Endpoint dưới đây trả product detail cho frontend. Hệ thống dùng Redis qua `IDistributedCache` để giảm tải SQL Server. Application chạy nhiều instances trên Azure App Service.

Business yêu cầu:

- user tenant A tuyệt đối không được thấy pricing hoặc metadata của tenant B;
- tenant context phải được server xác minh;
- Redis chỉ là optimization, không phải source-of-truth;
- Redis outage không được tự động làm product API outage nếu SQL Server vẫn khỏe;
- hot products có thể nhận hàng nghìn requests/phút;
- stale pricing phải có giới hạn;
- production cần phân biệt Redis latency, cache miss, cache error, SQL fallback và authorization failure.

Production xuất hiện:

- một khách hàng đôi lúc thấy giá không thuộc tenant của họ;
- lỗi biến mất sau khi flush Redis;
- Redis incident làm p99 tăng mạnh và một số request trả 500;
- khi một hot key hết TTL, SQL CPU spike;
- team đề xuất TTL 24 giờ để giảm misses.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/products")]
public sealed class ProductsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public ProductsController(
        AppDbContext db,
        IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    [HttpGet("{productId:guid}")]
    public async Task<IActionResult> Get(
        Guid productId,
        [FromHeader(Name = "X-Tenant-Id")] Guid tenantId,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"product:{productId}";

        var cachedJson = await _cache.GetStringAsync(
            cacheKey,
            cancellationToken);

        if (cachedJson is not null)
        {
            var cached =
                JsonSerializer.Deserialize<ProductResponse>(cachedJson)!;

            return Ok(cached);
        }

        var product = await _db.Products
            .AsNoTracking()
            .Where(x => x.Id == productId &&
                        x.TenantId == tenantId)
            .Select(x => new ProductResponse
            {
                Id = x.Id,
                Name = x.Name,
                Price = x.Price,
                DiscountPercent = x.DiscountPercent
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (product is null)
            return NotFound();

        await _cache.SetStringAsync(
            cacheKey,
            JsonSerializer.Serialize(product),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow =
                    TimeSpan.FromHours(24)
            },
            cancellationToken);

        return Ok(product);
    }
}
```

## Kết quả code review tham khảo

### Critical — Cache key không chứa tenant scope

**Vấn đề:** Key chỉ là `product:{productId}`.

**Tại sao xảy ra:** SQL đúng tenant nhưng cache được đọc trước SQL. Tenant A có thể populate key mà tenant B sau đó đọc lại.

**Ảnh hưởng production:** Cross-tenant pricing/data disclosure.

**Cách sửa:** Cache key tối thiểu phải scope theo verified tenant: `tenant:{tenantId}:product:{productId}`. Nếu response phụ thuộc user/contract/role thì cache identity phải phản ánh thêm dimension đó hoặc cache ở layer khác.

### Critical — Tenant ID do client gửi được dùng như security boundary

**Vấn đề:** Header từ client được dùng trực tiếp để query dữ liệu.

**Tại sao xảy ra:** Tenant selector bị nhầm với authorized tenant context.

**Ảnh hưởng production:** Nếu không có membership check khác, user có thể đổi header để probe tenant khác.

**Cách sửa:** Resolve effective tenant từ authenticated principal + server-side membership/grant. Client có thể chọn tenant, nhưng server phải authorize lựa chọn đó.

### High — Cache hit bypass data-access authorization path

**Vấn đề:** Cache hit trả response ngay.

**Tại sao xảy ra:** Team tin object cache đã được scope đúng.

**Ảnh hưởng production:** Sai key, stale entitlement hoặc corrupted cache đi thẳng ra API.

**Cách sửa:** Authorize tenant/user context trước cache lookup và thiết kế key theo resource scope.

### High — Redis outage biến optimization thành hard dependency

**Vấn đề:** Cache get/set exception làm request fail.

**Tại sao xảy ra:** Cache nằm trên critical path mà không có degraded behavior.

**Ảnh hưởng production:** Redis incident làm 500 dù SQL vẫn khỏe.

**Cách sửa:** Catch đúng cache-provider timeout/connection exceptions, dùng bounded timeout, fallback SQL cho read path nếu business cho phép; cache write failure thường không nên làm source-of-truth read fail.

### High — Pricing update không invalidation cache

**Vấn đề:** SQL thay đổi nhưng key cũ giữ tới TTL.

**Tại sao xảy ra:** Read cache và write path tách rời.

**Ảnh hưởng production:** Giá cũ tồn tại tới 24 giờ.

**Cách sửa:** Sau successful DB commit, invalidate đúng tenant-scoped key. Nếu nhiều write paths hoặc cần durable invalidation, đánh giá outbox/versioning; không mặc định thêm messaging nếu simple invalidation đủ.

### High — Hot-key cache stampede

**Vấn đề:** Nhiều instances cùng miss và cùng query SQL.

**Tại sao xảy ra:** Cache-aside không có jitter/coalescing.

**Ảnh hưởng production:** SQL CPU, connections và latency spike khi cache cold/expire.

**Cách sửa:** Bắt đầu bằng TTL jitter và đo. Nếu vẫn cần, local single-flight/coalescing; distributed coordination chỉ khi evidence chứng minh cần.

### High — TTL 24 giờ không dựa trên freshness requirement

**Vấn đề:** TTL được chọn để giảm load.

**Tại sao xảy ra:** Hit ratio được ưu tiên hơn correctness.

**Ảnh hưởng production:** Stale pricing kéo dài.

**Cách sửa:** TTL phải xuất phát từ stale tolerance và invalidation reliability.

### Medium — Không version cache schema

**Vấn đề:** Rolling deployment có thể đọc DTO cache cũ.

**Tại sao xảy ra:** Key namespace không version.

**Ảnh hưởng production:** Deserialize lỗi hoặc semantic mismatch giữa app versions.

**Cách sửa:** Backward-compatible DTO hoặc cache namespace version.

### Medium — Telemetry không phân biệt hit/miss/error/fallback

**Vấn đề:** Không đủ metrics để biết bottleneck nằm ở Redis hay SQL.

**Tại sao xảy ra:** Cache bị coi như implementation detail.

**Ảnh hưởng production:** Điều tra p99 dựa vào đoán.

**Cách sửa:** Track hit/miss/error ratio, Redis latency, SQL fallback count, SQL dependency latency, invalidation failures.

### Medium — Cached JSON invalid có thể tạo lỗi lặp

**Vấn đề:** Deserialize dùng null-forgiving.

**Tại sao xảy ra:** Cache được tin như source-of-truth.

**Ảnh hưởng production:** Một bad entry làm một key fail liên tục.

**Cách sửa:** Evict bad entry và fallback SQL; ghi metric để phát hiện schema/deployment issue.

## Phiên bản đề xuất

```csharp
public sealed class ProductReader
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;
    private readonly ICurrentTenant _tenant;
    private readonly ILogger<ProductReader> _logger;

    public ProductReader(
        AppDbContext db,
        IDistributedCache cache,
        ICurrentTenant tenant,
        ILogger<ProductReader> logger)
    {
        _db = db;
        _cache = cache;
        _tenant = tenant;
        _logger = logger;
    }

    public async Task<ProductResponse?> GetAsync(
        Guid productId,
        CancellationToken ct)
    {
        var tenantId = _tenant.RequireAuthorizedTenantId();
        var key = $"v2:tenant:{tenantId:N}:product:{productId:N}";

        try
        {
            var json = await _cache.GetStringAsync(key, ct);

            if (json is not null)
            {
                try
                {
                    return JsonSerializer
                        .Deserialize<ProductResponse>(json);
                }
                catch (JsonException)
                {
                    await _cache.RemoveAsync(key, ct);
                }
            }
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(
                ex,
                "Redis unavailable; fallback SQL for {ProductId}",
                productId);
        }

        var product = await _db.Products
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId &&
                        x.Id == productId)
            .Select(x => new ProductResponse
            {
                Id = x.Id,
                Name = x.Name,
                Price = x.Price,
                DiscountPercent = x.DiscountPercent
            })
            .SingleOrDefaultAsync(ct);

        if (product is null)
            return null;

        try
        {
            await _cache.SetStringAsync(
                key,
                JsonSerializer.Serialize(product),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow =
                        TimeSpan.FromMinutes(5)
                },
                ct);
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(
                ex,
                "Cache populate failed for {ProductId}",
                productId);
        }

        return product;
    }

    private static bool IsCacheFailure(Exception ex) =>
        ex is TimeoutException ||
        ex.GetType().Name.Contains(
            "Redis",
            StringComparison.Ordinal);
}
```

Write path nên invalidate đúng tenant-scoped key sau DB commit. Nếu invalidation failure không chấp nhận được, cần thêm durable strategy; nếu SQL đủ nhanh và complexity vượt benefit, bỏ cache là một lựa chọn hợp lệ.

## Giải thích thiết kế sau khi sửa

Tenant identity được authorize trước cache. Cache key phản ánh isolation boundary. Redis failure degrade về SQL thay vì mặc định kéo API xuống.

TTL không còn là cơ chế freshness duy nhất; write invalidation mới là đường chính. Stampede protection được thêm theo measurement thay vì mặc định dùng distributed lock.

## Trade-offs

- Tenant-scoped keys tăng key count nhưng bảo toàn isolation.
- SQL fallback tăng availability nhưng có thể overload DB khi Redis outage.
- Explicit invalidation tăng write-path complexity.
- Short TTL tăng misses.
- Distributed coalescing/lock có failure modes riêng.
- Không cache có thể là lựa chọn đơn giản và tốt hơn.

## Cách kiểm thử

1. Integration test hai tenants cùng `productId`; không có cross-tenant cache hit.
2. Authorization test tenant selector không hợp lệ.
3. Redis outage test: endpoint fallback SQL theo contract.
4. Load test concurrent misses: đo SQL query count, CPU, pool pressure và p95/p99.
5. Consistency test update price rồi read lại; stale window không vượt requirement.

## Quan sát trong production

- cache hit/miss/error;
- Redis p95/p99 và timeout rate;
- SQL dependency latency/CPU/pool pressure;
- fallback-to-SQL count;
- invalidation failure;
- request p95/p99;
- trace request → Redis → SQL.

## Câu hỏi phỏng vấn mở rộng

1. Nếu pricing phụ thuộc từng user contract trong cùng tenant, cache key thay đổi thế nào?
2. Nếu Redis outage kéo dài và SQL không đủ capacity, bạn degrade/load-shed ra sao?
3. Evidence nào khiến bạn bỏ Redis cache hoàn toàn?

# Code Review Challenge 2 — Playwright E2E suite pass ở local nhưng flaky trên CI vì shared state, fixed sleeps và parallel workers

**Chủ đề:** Playwright, TypeScript, E2E testing, test isolation, asynchronous UI, parallelism, CI/CD, flaky tests, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một ASP.NET Core + React portal dùng Playwright cho critical E2E flow: đăng nhập, tạo project, thêm task, tìm task và xóa project.

Suite pass gần như 100% khi developer chạy một mình trên laptop. Trên CI, team chạy 6 workers song song để rút ngắn pipeline và bắt đầu gặp:

- test đôi khi thấy project của test khác;
- search test thỉnh thoảng không thấy task vừa tạo;
- có failure chỉ xảy ra khi CI load cao;
- retry lần 2 thường pass;
- screenshot failure đôi lúc chụp trạng thái đã thay đổi sau lỗi;
- team tăng `waitForTimeout` từ 1 giây lên 5 giây rồi 10 giây;
- toàn bộ tests đăng nhập bằng cùng một account và dùng cùng project name.

Backend có eventual UI refresh sau API mutation khoảng vài trăm ms đến vài giây tùy tải. Search index có thể update chậm hơn database một chút.

## Kết quả code review tham khảo

### Critical — Tests dùng cùng shared project name và có destructive operations

**Vấn đề:** Create/search/delete cùng thao tác `E2E Project` khi `fullyParallel: true`.

**Tại sao xảy ra:** Test data không unique và tests không có ownership boundary.

**Ảnh hưởng production/CI:** Worker A xóa project worker B đang dùng; test order/timing quyết định kết quả.

**Cách sửa:** Mỗi test tạo unique project/task ID/name, ví dụ suffix bằng test run ID + worker index + random/UUID. Cleanup chỉ xóa resource do chính test tạo.

### High — Fixed sleeps tạo race với thực tế asynchronous

**Vấn đề:** `waitForTimeout` giả định latency cố định.

**Tại sao xảy ra:** Test đồng bộ theo thời gian thay vì state.

**Ảnh hưởng:** CI load thay đổi là test fail; sleep quá dài làm pipeline chậm nhưng vẫn không đảm bảo.

**Cách sửa:** Dựa vào Playwright auto-wait/assertions, response/locator state, hoặc bounded polling cho eventual consistency.

### High — Search eventual consistency bị đối xử như immediate UI state

**Vấn đề:** Sau create task, test chờ 3 giây rồi search.

**Tại sao xảy ra:** Search projection timing không được model như một contract riêng.

**Ảnh hưởng:** Test flaky khi index lag dù DB/API mutation đã thành công.

**Cách sửa:** Nếu product requirement là “search cập nhật trong <= X giây”, dùng bounded polling tới X và fail với diagnostics nếu vượt. Nếu UI có direct local state, test create flow riêng khỏi search consistency flow.

### High — Shared account tạo cross-test interference

**Vấn đề:** Tất cả workers dùng cùng account.

**Tại sao xảy ra:** Login setup tối giản nhưng account state/session/data scope dùng chung.

**Ảnh hưởng:** Tests thay đổi cùng user-owned resources, preferences hoặc session-related state.

**Cách sửa:** Dùng account pool per worker hoặc tenant/test namespace. Nếu shared account bắt buộc, resources vẫn phải unique và cleanup/idempotency rõ.

### High — Retry có thể che race condition

**Vấn đề:** `retries: 2` biến nhiều intermittent failures thành green build.

**Tại sao xảy ra:** Retry được dùng như stabilization mechanism.

**Ảnh hưởng:** Flakiness kéo dài; CI pass nhưng suite không đáng tin.

**Cách sửa:** Retry có thể giữ ở CI để thu diagnostics, nhưng flaky-pass phải được track như signal. Test fail lần đầu/pass retry cần metric/report riêng và có threshold/quarantine policy.

### Medium — Login qua UI trong mọi test tăng latency và thêm failure surface

**Vấn đề:** Mỗi test lặp full login.

**Tại sao xảy ra:** Setup chưa tách mục tiêu authentication test khỏi authenticated feature tests.

**Ảnh hưởng:** Pipeline chậm, auth outage/animation/network noise làm nhiều tests không liên quan fail.

**Cách sửa:** Giữ một số dedicated login E2E tests; feature tests có thể dùng authenticated storage state hoặc trusted API setup nếu phù hợp, miễn không bypass chính behavior đang được test.

### Medium — Selector dựa trên text dễ ambiguous

**Vấn đề:** `text=E2E Project` có thể match nhiều vị trí.

**Tại sao xảy ra:** Selector không dựa trên accessible role/test contract.

**Ảnh hưởng:** Test click/assert nhầm element khi UI thay đổi.

**Cách sửa:** Ưu tiên role/name, label, hoặc stable test id khi semantics không đủ rõ.

### Medium — Setup/cleanup không có API-level lifecycle rõ

**Vấn đề:** Test giả định project tồn tại ở test sau.

**Tại sao xảy ra:** Tests phụ thuộc implicit suite ordering/state.

**Ảnh hưởng:** Chạy riêng một test hoặc shard suite sẽ fail.

**Cách sửa:** Mỗi test hoặc fixture tạo prerequisites rõ ràng và cleanup bằng API/database test fixture theo environment policy.

### Medium — Failure diagnostics chưa đủ cho async race

**Vấn đề:** Chỉ screenshot on failure.

**Tại sao xảy ra:** Không thu trace/network/console diagnostics.

**Ảnh hưởng:** Screenshot sau timeout không cho biết request nào chậm/fail.

**Cách sửa:** Bật trace/video/network logs có chọn lọc on-first-retry/on-failure; lưu request/response timing, console errors, current URL và relevant correlation ID.

## Phiên bản đề xuất

```ts

test.describe('projects', () => {
  test('create and search task', async ({ page, request }) => {

    const projectName = `E2E-${id}`;
    const taskName = `Task-${id}`;

    const project = await request.post('/api/test/projects', {

    await page.getByRole('button', { name: 'Add Task' }).click();
    await page.getByLabel('Task title').fill(taskName);

    const saveResponse = page.waitForResponse(response =>
      response.url().includes('/api/tasks') &&
      response.request().method() === 'POST' &&
      response.ok()

    await page.getByRole('button', { name: 'Save' }).click();
    await saveResponse;

    await expect(
      page.getByText(taskName, { exact: true })
    ).toBeVisible();

      async () => {
        await page.getByLabel('Search').fill(taskName);
        return page.getByText(taskName, { exact: true }).count();

        intervals: [250, 500, 1000]
```

Nếu test setup endpoint riêng không được phép trong production-like environment, fixture có thể dùng public API authenticated bằng test identity. Điểm quan trọng là prerequisites phải deterministic, unique và owned bởi test.

## Giải thích thiết kế sau khi sửa

Test không còn dựa trên resource dùng chung. Unique identity loại cross-worker race.

Synchronization dựa trên observable response/state. Search được test bằng bounded polling vì requirement cho phép eventual consistency; đây không phải blanket sleep.

Feature test không cần lặp UI login nếu login không phải subject của test. Authentication itself vẫn có dedicated E2E coverage.

Retry chỉ hỗ trợ diagnostics chứ không được dùng để biến flaky suite thành “green”.

## Trade-offs

- Unique data tăng cleanup volume.
- API/fixture setup nhanh và deterministic hơn UI setup nhưng ít cover UI path hơn.
- Polling eventual consistency làm test lâu hơn immediate assertion nhưng phản ánh đúng contract.
- Trace/video tăng artifact size.
- Account-per-worker tăng test-environment management.
- Dedicated test endpoints cần bảo vệ nghiêm ngặt hoặc chỉ tồn tại trong test environment.

## Cách kiểm thử

1. Chạy suite với 1, 6 và 12 workers; kết quả không đổi theo parallelism.
2. Chạy mỗi test riêng lẻ/shuffled; không phụ thuộc test order.
3. Inject search-index delay 8 giây; bounded polling pass nếu trong SLO và fail rõ nếu vượt timeout.
4. Inject API 500/slow response; trace phải cho thấy root cause thay vì chỉ screenshot.
5. Re-run cùng suite nhiều lần; track first-attempt pass rate và flaky-retry rate.

## Quan sát trong production

Trong CI/testing observability:

- first-attempt pass rate;
- retry-pass rate theo test;
- duration distribution p50/p95;
- trace/video on failure hoặc first retry;
- browser console errors;
- network request timing/status;
- unique test run ID/worker ID;
- backend correlation ID để nối Playwright failure với ASP.NET Core/Application Insights logs;
- cleanup failures/orphan test resources.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn API setup thay vì UI setup cho E2E test?
2. Nếu search SLO là 5 giây nhưng polling test thường mất 4.8 giây, test đang “pass” nhưng bạn có coi đó là regression signal không?
3. Bạn xử lý flaky test trong release gate thế nào để không vừa block team vô ích vừa không che defect?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache key là một phần của security/data-isolation design.
- Redis cần failure strategy cho outage, invalidation và stampede.
- Tenant identity phải được authorize server-side trước cache/query.
- E2E tests phải có isolated test data và deterministic synchronization.
- Retry không thay thế root-cause analysis của flaky tests.
- Eventual consistency nên được test bằng bounded observable contract, không bằng arbitrary sleep.

## Mẫu tư duy cần nhớ

- Security boundary phải xuất hiện trong cache identity.
- Treat cache as failure-prone optimization unless requirements say otherwise.
- Replace time-based waits with state-based synchronization.
- Make tests independent under parallel execution.
- Track flaky retries as failures of test reliability, không coi chúng như pass bình thường.
