# Câu 1 — ASP.NET Core: vì sao request bị hủy nhưng truy vấn SQL vẫn chạy?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, CancellationToken, EF Core, SQL Server, connection pooling, async I/O.

## Bối cảnh

Một API .NET 8 cung cấp endpoint `GET /api/reports/orders`. Khi người dùng chuyển trang trong Vue.js, browser hủy HTTP request. Backend sử dụng `await db.Orders.Where(...).ToListAsync()` nhưng không truyền `CancellationToken`. Dashboard cho thấy số truy vấn SQL đang thực thi tăng khi người dùng liên tục thay đổi filter; một số request bị gateway timeout. Tải giả định 150 requests/giây ở giờ cao điểm, SQL Server dùng chung với API thanh toán. Nhóm đề xuất tăng connection pool và thêm `Task.Run`.

## Câu hỏi chính

Giải thích từ HTTP disconnect đến `HttpContext.RequestAborted`, `CancellationToken`, EF Core provider và SQL Server: điều gì được bảo đảm, điều gì chỉ là best-effort, và bạn sẽ kiểm chứng cũng như sửa thế nào để giảm công việc vô ích mà không làm hỏng tính đúng đắn?

## Câu hỏi làm rõ nên cân nhắc

1. Client thực sự abort TCP/HTTP request hay chỉ bỏ qua kết quả ở Vue?
2. Cancellation được truyền đến những tầng nào, có truy vấn blocking hay synchronous I/O không?
3. SQL duration, waits, active sessions và pool utilization thay đổi thế nào khi cancel?
4. Endpoint chỉ đọc hay có side effects, transaction và yêu cầu hoàn tất độc lập với client?
5. Provider/version, command timeout, reverse proxy và các giới hạn tải hiện tại là gì?

## Gợi ý tư duy

### Gợi ý 1
Hủy việc chờ ở client không đồng nghĩa hủy công việc tại database.

### Gợi ý 2
Theo dấu token từ ASP.NET Core endpoint qua service đến `ToListAsync(token)`.

### Gợi ý 3
Phân biệt cooperative cancellation, provider gửi yêu cầu cancel, và SQL Server thực sự dừng command; đo bằng trace và SQL observations.

## Cấu trúc trả lời đề xuất

1. Làm rõ loại request và semantics hủy.
2. Vẽ chuỗi request → token → EF Core → provider → SQL.
3. Xác định bằng chứng ở client, API và database.
4. Đề xuất thay đổi nhỏ nhất; xử lý timeout, exception và side effects.
5. Kiểm thử abort/load, đo kết quả, đánh giá trade-offs.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `RequestAborted` báo request bị abort; cancellation có tính cooperative, không phải cơ chế kill SQL tức thời.
- Truyền token vào các async API hỗ trợ token; không coi `Task.Run` là cách giải quyết I/O.
- Đo lường SQL work, pool wait, request cancellation và số query còn chạy trước/sau.

### Điểm cộng
- Phân biệt `OperationCanceledException` với lỗi database thật; không log mọi cancel như HTTP 500.
- Thảo luận query timeout, pagination, index, giới hạn concurrency và server-side query cost.
- Nêu khả năng command vẫn hoàn thành do timing/provider behavior.

### Senior+
- Xử lý riêng tác vụ đã commit hoặc cần hoàn tất dù client ngắt; không buộc mọi nghiệp vụ vào `RequestAborted`.
- Cân nhắc cancellation race với connection reuse, transaction cleanup và backpressure.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, provider EF Core SQL Server hỗ trợ cancellation, không có công việc bắt buộc hoàn thành sau khi client disconnect. ASP.NET Core cung cấp `HttpContext.RequestAborted`; minimal API/controller có thể bind `CancellationToken`. Nếu không truyền token, truy vấn có thể tiếp tục dù client đã rời trang. Khi truyền, EF Core chuyển tín hiệu cho provider; provider có thể cố gắng hủy command, nhưng không được giả định mọi thao tác SQL dừng tức thì. Hủy trong lúc query đã hoàn thành cũng không thể thu hồi kết quả.

Ví dụ:

```csharp
[HttpGet("orders")]
public async Task<ActionResult<IReadOnlyList<OrderRow>>> GetOrders(
    [FromQuery] DateTime from,
    [FromQuery] DateTime to,
    CancellationToken cancellationToken)
{
    if (from >= to) return BadRequest("Invalid range");

    var rows = await db.Orders.AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
        .OrderBy(x => x.Id)
        .Select(x => new OrderRow(x.Id, x.Total))
        .Take(200)
        .ToListAsync(cancellationToken);

    return Ok(rows);
}
```

`OrderRow` là DTO giả định. Service/repository phải tiếp tục nhận token và truyền đến các operation thực sự hỗ trợ. Không dùng `CancellationToken.None` ở tầng sâu. Đặt server-side pagination/limits và kiểm tra execution plan để tránh query đắt ngay cả khi không bị cancel. Với transaction ghi dữ liệu, xác định rõ commit boundary: không tự động gắn mọi bước sau commit với request token nếu cần bảo đảm durable completion; dùng outbox/background processing khi có requirement.

**Kiểm chứng:** dùng browser network tab xác nhận abort; Application Insights ghi `requestAborted`, `db.command.duration`, cancellation count và dependency telemetry; SQL Server Query Store/DMV hoặc Extended Events xác nhận command duration, waits, active requests. Chạy load có nhiều cancel, so sánh tổng CPU SQL, active commands, p95 latency, timeout và tỷ lệ lỗi. Kiểm tra provider behavior trong đúng môi trường trước khi khẳng định cancel hiệu quả.

**Trade-offs:** cancellation cải thiện resource usage nhưng tăng nhánh xử lý lỗi và không thay thế query optimization. Tăng connection pool có thể làm database quá tải hơn; `Task.Run` chỉ đẩy I/O sang ThreadPool, không giải quyết nguồn lực SQL. Nếu API cần xuất báo cáo lâu, cân nhắc job + polling/download thay vì giữ HTTP request.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi muốn xác nhận browser có thực sự abort request hay chỉ bỏ kết quả, và endpoint có side effect hay không. Nếu đây là read-only report, tôi sẽ truyền `RequestAborted` xuyên suốt controller, service đến `ToListAsync`. Cancellation trong .NET là cooperative: EF Core chuyển tín hiệu cho provider, nhưng không có bảo đảm SQL dừng ngay. Tôi sẽ đo trên Application Insights và SQL Server để xác định bao nhiêu command vẫn chạy sau abort, cũng như execution plan và pool utilization. Nếu query vốn chậm, tôi vẫn phải giới hạn dữ liệu và tối ưu truy vấn. Tôi không chọn `Task.Run` vì đây là I/O-bound, và không tăng pool trước khi biết bottleneck. Với tác vụ cần hoàn tất sau commit, tôi sẽ tách lifecycle khỏi HTTP cancellation. Cuối cùng kiểm thử nhiều request bị hủy dưới tải và xác nhận không phát sinh lỗi 500 giả hoặc mất tính nhất quán.”

## Câu hỏi đào sâu

1. Nếu provider bỏ qua cancellation, bạn sẽ giới hạn tổn thất tài nguyên bằng cách nào?
2. Nếu request đã ghi payment và client disconnect trước response, có nên rollback không?
3. Nếu cancellation gây ra nhiều exception trong logs, làm sao phân biệt expected cancellation với timeout nghiêm trọng?

## Lỗi trả lời thường gặp

- Khẳng định đóng tab luôn kill SQL query.
- Thêm `Task.Run` quanh EF Core async call.
- Tăng `Max Pool Size` mà không xem waits và database capacity.
- Nuốt mọi `OperationCanceledException` kể cả khi server shutdown hoặc timeout cần điều tra.

## Thang điểm 0–10

- 0–2: Làm rõ semantics, loại workload và side effects.
- 0–3: Giải thích đúng propagation và best-effort cancellation.
- 0–2: Có kế hoạch đo API/SQL và xác minh giả thuyết.
- 0–2: Giải pháp, failure paths, testing và trade-offs.
- 0–1: Trình bày có thứ tự, nêu điều chưa chắc chắn.

# Câu 2 — IIS: sau deployment, ứng dụng .NET Framework 4.5 thỉnh thoảng mất session

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET session, deployment, incident response, observability.

## Bối cảnh

Portal nội bộ ASP.NET MVC chạy .NET Framework 4.5 trên hai Windows Server sau load balancer. Sau một đợt cập nhật bằng Octopus Deploy, một số người dùng bị chuyển về trang đăng nhập khi đang thao tác form; các request khác trả HTTP 500. Sự cố xảy ra không đồng đều, tăng trong 10 phút sau release. Giả định có 800 concurrent users và yêu cầu không mất dữ liệu form. Nhóm chưa xác nhận session mode, machine keys, load-balancer affinity, application pool recycling hay thứ tự triển khai.

## Câu hỏi chính

Trong vai trò incident owner, hãy xây dựng quy trình giảm impact, thu thập evidence, so sánh nhiều giả thuyết, xác minh root cause và rollout bản sửa an toàn mà không vội kết luận lỗi do application pool recycle.

## Câu hỏi làm rõ nên cân nhắc

1. Session mode là InProc, StateServer, SQLServer hay custom? Authentication dùng Forms Authentication hay identity provider?
2. Hai node dùng cùng `machineKey`, cấu hình cookie, clock và deployment artifact không?
3. Load balancer có affinity, health check và drain connections không?
4. HTTP 500 xuất hiện ở action nào, có correlation ID và Event Viewer exceptions không?
5. Deployment có thay `web.config`, bin files, App Pool settings hoặc recycle từng node không?

## Gợi ý tư duy

### Gợi ý 1
Tách “mất session state” khỏi “authentication cookie không được chấp nhận”.

### Gợi ý 2
Quan sát request theo node và thời điểm AppDomain restart.

### Gợi ý 3
Kiểm tra InProc + affinity, machineKey và deployment draining trước khi quy lỗi cho code mới.

## Cấu trúc trả lời đề xuất

1. Định lượng người dùng và giao dịch bị ảnh hưởng.
2. Stabilize bằng rollback/traffic routing có kiểm soát.
3. Thu thập request/node/recycle/session/cookie evidence.
4. Liệt kê và phân biệt các giả thuyết.
5. Xác minh bằng tái hiện có kiểm soát.
6. Sửa theo root cause, test rollout và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không coi session và authentication là một.
- Có mitigation không phá form data; ghi nhận thời điểm và node.
- So sánh ít nhất ba giả thuyết và bằng chứng phân biệt.

### Điểm cộng
- Nhắc `machineKey` consistency cho các cơ chế bảo vệ cookie/ticket phù hợp với cấu hình ASP.NET.
- Hiểu InProc session bị mất khi worker/AppDomain restart và không chia sẻ giữa nodes.
- Phân tích health check, graceful drain, sticky session và deployment artifacts.

### Senior+
- Thiết kế canary/rolling release, rollback compatibility, distributed session khi cần, và giảm dependency vào session.
- Không đề xuất sticky session như giải pháp duy nhất; đánh giá failure khi node chết.

## Hướng giải quyết tham khảo

**Impact → stabilize:** xác định tỷ lệ logout/500 theo node, user flow và thời gian. Tạm dừng rollout; nếu bằng chứng cho thấy bản mới gây lỗi, rollback từng node theo playbook, đảm bảo artifact/config cũ còn tương thích với dữ liệu đang dùng. Cảnh báo người dùng lưu form trước khi retry; nếu có autosave/draft, kiểm tra trạng thái để tránh mất dữ liệu. Không recycle cả hai nodes cùng lúc.

**Evidence:** IIS logs với `sc-status`, `sc-substatus`, `time-taken`, node ID; Windows Event Viewer và ASP.NET exceptions; App Pool recycle events; Octopus Deploy timeline; `web.config` diff, session mode, cookie attributes, `machineKey`, load-balancer logs. Correlate login redirect, request failures, instance changes, AppDomain starts. Không log raw authentication cookies hoặc secrets.

**Giả thuyết A:** InProc session + chuyển node không có affinity, hoặc node recycle làm mất session; xác minh bằng node-affinity test và AppDomain start timeline. **B:** cookie auth/ticket không giải mã hoặc validate đồng nhất giữa nodes do `machineKey` khác nhau; xác minh cấu hình và lỗi crypto, tránh đưa key vào logs. **C:** deployment cập nhật `web.config`/bin khiến AppDomain restart, session mất; so khớp timestamp. **D:** code mới gây exception hoặc thay đổi session serialization; đối chiếu stack traces và diff. **E:** auth provider timeout/cookie expiration/clock skew; kiểm tra auth events.

**Fix có điều kiện:** nếu InProc là nguyên nhân, cân nhắc out-of-process session store hoặc thiết kế lại form draft persistence, đồng thời áp dụng draining/rolling deployment; nếu key khác nhau, đồng bộ key qua secret management an toàn; nếu regression code, rollback và hotfix kèm integration tests. Out-of-process session cũng cần kiểm tra serialization, capacity, availability và security; không mặc định là giải pháp tối ưu.

**Verify:** tái hiện với 2 nodes, route đổi node giữa các bước form, deploy/recycle một node, thử cookie từ node A sang B, và chạy E2E Playwright kiểm tra form không mất dữ liệu. Theo dõi login redirects, 500 rate, App Pool restarts, session errors, p95 latency và successful form submissions sau release. Kết thúc bằng postmortem có timeline và owner.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác định ngay tỷ lệ người dùng bị logout hoặc mất form, tạm dừng rollout và kiểm tra có nên rollback từng node. Tôi không mặc định App Pool recycle là root cause vì mất session và mất authentication có thể giống nhau ở UI. Tôi sẽ đối chiếu IIS logs, Event Viewer, thời điểm Octopus Deploy, node ID và cấu hình session/machineKey. Nếu InProc session đang dùng trên hai node, request chuyển node hoặc recycle có thể mất state; nếu key khác nhau, auth ticket có thể không được xác thực giữa nodes. Tôi sẽ tái hiện bằng cách ép request đổi node và recycle từng instance trong staging. Fix tùy bằng chứng: rolling deployment có draining, shared session hoặc lưu form draft bền vững, đồng bộ cấu hình bảo mật, hay rollback regression. Tôi xác nhận bằng E2E đa node và dashboard 500/logout/form completion, rồi ghi postmortem.”

## Câu hỏi đào sâu

1. Nếu business không cho phép shared session store, bạn thiết kế form nhiều bước thế nào để chịu được node failure?
2. Nếu rolling deployment không thể tránh AppDomain restart, phương án giảm mất dữ liệu là gì?
3. Khi auth cookie hợp lệ nhưng session rỗng, làm sao UI phản hồi mà không buộc logout?

## Lỗi trả lời thường gặp

- Đồng nhất authentication và session.
- Recycle toàn bộ IIS servers như bước đầu.
- Chỉ bật sticky session mà không xử lý node failure.
- Đưa `machineKey` hoặc cookie thật vào log để debug.
- Rollback mà không xem compatibility dữ liệu và config.

## Thang điểm 0–10

- 0–2: Impact, stabilization và rollback an toàn.
- 0–3: Giả thuyết có bằng chứng phân biệt.
- 0–2: Hiểu IIS/session/auth internals.
- 0–2: Test đa node, deployment và monitoring.
- 0–1: Trình bày rõ, phân biệt fact và hypothesis.

# Câu 3 — Thiết kế kiến trúc CMS + product catalog với Akamai và Optimizely

**Loại câu hỏi:** Architecture / system design / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai CDN, REST APIs, caching, SEO, e-commerce integration, security, reliability.

## Bối cảnh

Một website marketing/e-commerce dùng Optimizely CMS để quản lý landing pages, content blocks và nội dung biên tập; product price/availability do một external commerce API quản lý. Vue.js render phần lọc sản phẩm, Akamai đứng trước origin. Giả định 1 triệu page views/ngày, peak 20 lần baseline trong campaign, editorial publish khoảng 100 lần/ngày. Marketing muốn cập nhật banner trong 2 phút; giá và tồn kho không được hiển thị sai quá lâu, nhưng chưa có SLA cụ thể. Checkout thực hiện tại commerce system. Đội vận hành nhỏ, ưu tiên đơn giản và rollback nhanh.

## Câu hỏi chính

Thiết kế ownership, content delivery, caching/invalidation, API boundaries và deployment cho hệ thống này; so sánh ít nhất hai phương án và nêu điều kiện khiến bạn đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. Giá/tồn kho có phải dữ liệu pháp lý hoặc cần strong consistency tại checkout không?
2. Tần suất cập nhật giá, tồn kho và campaign, tỷ lệ traffic anonymous vs authenticated?
3. Có localization, personalization, preview/unpublished content và yêu cầu SEO gì?
4. Akamai có hỗ trợ purge/tagging trong cấu hình hiện hữu không, và origin chịu được peak bao nhiêu?
5. Commerce API có rate limits, outage policy, cache contract và cơ chế xác thực nào?

## Gợi ý tư duy

### Gợi ý 1
Phân loại dữ liệu theo owner và mức độ freshness, không cache mọi thứ giống nhau.

### Gợi ý 2
Tách HTML/content ổn định khỏi price/availability có biến động.

### Gợi ý 3
Đặt ra failure matrix: CMS down, commerce down, CDN stale, publish race, preview leakage.

## Cấu trúc trả lời đề xuất

1. Chốt SLO freshness và critical business invariants.
2. Vẽ owner/boundary và API/data flow.
3. So sánh render/cache strategies.
4. Chọn invalidation, preview, security và degradation.
5. Thiết kế deployment, testing và telemetry.
6. Trình bày chi phí vận hành và ngưỡng thay đổi kiến trúc.

## Ý chính của câu trả lời tốt

### Bắt buộc
- CMS sở hữu content; commerce sở hữu giá/tồn kho và xác nhận cuối cùng tại checkout.
- Phân biệt public cacheable pages, authenticated/personalized content và sensitive preview.
- Có invalidation strategy, outage fallback và monitoring freshness.

### Điểm cộng
- Cân nhắc SEO/canonical, server-rendered metadata và Vue hydration.
- Đưa ra trade-off giữa CDN HTML caching, edge/origin composition và client fetch.
- Thiết kế cache keys tránh cross-user/cross-locale leakage.

### Senior+
- Có cơ chế publish version, purge verification, rate limiting/bulkhead cho commerce API và rollout compatibility.
- Không tự động dùng Microservices hay event streaming khi modular monolith + external APIs đủ đáp ứng.

## Hướng giải quyết tham khảo

**Assumptions:** đa số page views anonymous; CMS publish event có thể dùng để kích hoạt purge; checkout commerce API luôn xác nhận giá và tồn kho. Nếu yêu cầu hiển thị giá chính xác tuyệt đối theo thời gian thực, cần điều chỉnh chiến lược cache và contract API.

**Option A — server-rendered HTML + Akamai cache:** origin Optimizely tạo page/SEO metadata, Akamai cache public HTML theo host/path/locale và các biến thể được kiểm soát; banner publish kích hoạt purge có xác nhận, thêm TTL giới hạn để giảm rủi ro purge thất bại. Price/availability không nhúng vào HTML cache dài hạn; Vue gọi backend-for-frontend API với TTL ngắn hoặc no-store tùy requirement. Ưu điểm SEO và origin offload, nhược điểm invalidation và dynamic composition phức tạp.

**Option B — headless CMS + Vue frontend:** CMS cung cấp content API, frontend SSR/SSG hoặc server rendering cho SEO; backend-for-frontend hợp nhất content/product APIs. Ưu điểm tách presentation, dễ tái sử dụng; nhược điểm thêm deployment surfaces, preview/auth/invalidation phức tạp. Không chọn headless chỉ vì “modern”.

**Data flow:** editor publish → CMS versioned content → invalidation event → purge Akamai → synthetic fetch xác nhận version hiển thị. Event có thể duplicate, cần idempotency. Nếu purge lỗi, retry/backoff, alert và bounded TTL; không khẳng định purge hoàn tất ngay. Commerce API qua BFF dùng Managed Identity nếu service hỗ trợ hoặc credential trong Key Vault; client không được thấy secret. BFF áp timeout, circuit breaker có cân nhắc, bounded concurrency, cache keys theo market/currency/product; không cache personalized price bằng shared CDN. Checkout server-side xác nhận lại giá và tồn kho.

**Security:** preview/unpublished content phải bypass shared cache và yêu cầu authorization; response chứa user-specific data dùng `private`/`no-store` phù hợp. Validate redirects, sanitize rich text, CSP phù hợp, kiểm soát cache key theo locale và currency. Không để query parameters tùy ý làm tăng cache cardinality hoặc tạo poisoning.

**Reliability:** nếu CMS origin down nhưng CDN có bản public hợp lệ, có thể serve stale trong giới hạn business; nếu commerce API down, hiển thị “availability unavailable” thay vì số lượng giả, có thể giữ product description tĩnh. Giới hạn request fan-out từ Vue. Đo publish-to-visible latency, Akamai hit/miss, origin RPS, commerce dependency p95/errors, stale-price complaints và preview cache incidents. Chạy Playwright E2E cho publish, locale, anonymous/authenticated, SEO metadata và outage injection.

**Deployment:** tách release content khỏi release code; schema evolution backward-compatible; canary origin/BFF và rollback artifact, kiểm tra CDN purge sau rollback. Chọn Option A nếu hiện tại Optimizely traditional rendering ổn định và đội nhỏ; chọn Option B nếu nhiều channels cần cùng content API và có nguồn lực vận hành SSR/BFF. Không có lý do mặc định phải triển khai Kubernetes hoặc Microservices.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chốt trước freshness của banner, giá và tồn kho, đồng thời phân định owner: Optimizely sở hữu editorial content, commerce system sở hữu giá và checkout. Với đội nhỏ và website chủ yếu anonymous, tôi nghiêng về server-rendered public pages kết hợp Akamai caching, vì SEO và chi phí vận hành. Tôi sẽ cache HTML theo locale/market có kiểm soát, publish thì purge và kiểm tra version, còn giá/tồn kho lấy qua BFF với cache policy riêng và xác nhận lại tại checkout. Preview và personalized response không được đi vào shared cache. Khi commerce API lỗi, UI phải degrade rõ ràng thay vì hiển thị thông tin sai; khi purge lỗi, cần retry và bounded TTL. Tôi sẽ đo publish-to-visible, CDN hit ratio và dependency latency. Nếu sau này nhiều frontend channels dùng chung content hoặc có nhu cầu trải nghiệm độc lập, headless/SSR có thể đáng giá, nhưng không phải lựa chọn mặc định.”

## Câu hỏi đào sâu

1. Nếu marketing yêu cầu banner xuất hiện trong 10 giây toàn cầu, bạn thay đổi architecture và verification thế nào?
2. Nếu giá khác nhau theo user loyalty tier, làm sao tránh shared-cache data leakage?
3. Nếu Akamai purge thành công nhưng một POP vẫn trả version cũ, bạn phân biệt cache, browser và origin thế nào?

## Lỗi trả lời thường gặp

- Cache giá/tồn kho như banner tĩnh mà không hỏi consistency.
- Để client gọi trực tiếp external commerce API kèm secret.
- Bỏ qua preview authorization và cache key variation.
- Chọn Microservices/headless mà không định lượng lợi ích và operational cost.
- Chỉ đo hit ratio, không đo content freshness và business correctness.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cancellation trong HTTP/EF Core là tín hiệu hợp tác, không bảo đảm SQL dừng tức thì.
- IIS multi-node cần phân biệt session loss, authentication failure và deployment restart bằng evidence.
- CMS/CDN/commerce phải có ownership, freshness và cache boundaries riêng; checkout là điểm xác nhận cuối cùng.

## Mẫu tư duy cần nhớ

3. Phân biệt dữ liệu authoritative với bản cache/read model.
4. Thiết kế failure behavior và security cùng với happy path.
5. Chọn kiến trúc đơn giản nhất đáp ứng SLO đã xác minh.
