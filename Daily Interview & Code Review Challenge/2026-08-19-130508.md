# Code Review Challenge 1 — Xử lý đơn hàng trùng dưới tải cao

**Chủ đề:** Concurrency, EF Core, idempotency, transaction, background processing  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API nhận callback thanh toán từ payment provider. Provider có cơ chế retry nếu không nhận HTTP 2xx đủ nhanh, nên cùng một `PaymentId` có thể đến nhiều lần hoặc đồng thời. Sau khi xác nhận thanh toán, hệ thống cập nhật đơn hàng và enqueue Hangfire job gửi email/notification.

Production đôi lúc ghi nhận một đơn hàng được xử lý hai lần, hai email được gửi, và ở một số thời điểm trạng thái đơn hàng không nhất quán với log. Lưu lượng bình thường khoảng vài chục callback/giây nhưng có burst lớn sau khi provider phục hồi từ outage. Database dùng EF Core với SQL Server hoặc PostgreSQL. Yêu cầu quan trọng: callback hợp lệ phải có thể retry an toàn.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/payments")]
public sealed class PaymentController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IBackgroundJobClient _jobs;
    private readonly ILogger<PaymentController> _logger;

    public PaymentController(
        AppDbContext db,
        IBackgroundJobClient jobs,
        ILogger<PaymentController> logger)
    {
        _db = db;
        _jobs = jobs;
        _logger = logger;
    }

    [HttpPost("callback")]
    public async Task<IActionResult> Callback(PaymentCallback request)
    {
        _logger.LogInformation(
            "Payment callback {@Request}", request);

        var alreadyProcessed = await _db.PaymentEvents
            .AnyAsync(x => x.PaymentId == request.PaymentId);

        if (alreadyProcessed)
            return Ok();

        var order = await _db.Orders
            .FirstOrDefaultAsync(x => x.Id == request.OrderId);

        if (order == null)
            return NotFound();

        order.Status = OrderStatus.Paid;
        order.PaidAt = DateTime.UtcNow;

        _db.PaymentEvents.Add(new PaymentEvent
        {
            PaymentId = request.PaymentId,
            OrderId = request.OrderId,
            Amount = request.Amount,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _jobs.Enqueue<PaymentNotificationJob>(
            x => x.SendAsync(order.Id, request.Email));

        return Ok();
    }
}
```

2. Tìm rủi ro concurrency, idempotency, security và reliability.
3. Giải thích tác động production của từng vấn đề.
4. Ưu tiên vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation đã sửa.
6. Giải thích cách kiểm thử dưới concurrent requests và failure.
7. Đề xuất logs, traces và metrics cần quan sát.

## Câu hỏi gợi mở

- `AnyAsync()` rồi `INSERT` có tạo thành một thao tác atomic không?
- Điều gì xảy ra nếu hai callback cùng `PaymentId` đi vào hai request khác nhau gần như đồng thời?
- Điều gì xảy ra nếu database commit thành công nhưng enqueue Hangfire thất bại?

## Gợi ý

### Gợi ý 2

Xem database constraint, transaction boundary và khoảng trống giữa database commit với side effect bên ngoài transaction.

## Kết quả code review tham khảo

### 1. Check-then-insert không atomic

**Problem:** `AnyAsync()` và `SaveChangesAsync()` là hai thao tác riêng.  
**Why:** Hai request đồng thời có thể cùng thấy `alreadyProcessed == false` trước khi request nào insert.  
**Production impact:** xử lý thanh toán trùng, duplicate side effects.  
**Severity:** Critical.  
**Recommended fix:** enforce uniqueness của `PaymentId` tại database bằng unique index/constraint và xử lý duplicate-key như một kết quả idempotent.

### 2. Không có transaction/business invariant đủ mạnh

**Problem:** cập nhật `Order` và ghi `PaymentEvent` dựa trên trạng thái đọc trước đó nhưng không có concurrency strategy rõ ràng.  
**Why:** các request khác có thể đồng thời thay đổi order hoặc xử lý các payment khác cho cùng order.  
**Production impact:** trạng thái cuối không phản ánh đúng business rule.  
**Severity:** High.  
**Recommended fix:** xác định invariant trước: một order có được nhiều payment không, trạng thái nào cho phép transition sang `Paid`; dùng optimistic concurrency token hoặc conditional update/transaction phù hợp.

### 3. Dual-write giữa database và Hangfire

**Problem:** DB commit xảy ra trước `_jobs.Enqueue`.  
**Why:** process có thể crash hoặc Hangfire storage có thể lỗi sau commit.  
**Production impact:** order đã Paid nhưng notification không bao giờ được tạo. Nếu callback retry thì `PaymentEvent` khiến code trả `Ok()` và không enqueue lại.  
**Severity:** High.  
**Recommended fix:** dùng transactional outbox trong cùng database transaction với business change; một dispatcher riêng publish/enqueue outbox message, có retry và idempotency.

### 4. Chưa thấy xác thực authenticity/integrity của callback

**Problem:** code tin `PaymentId`, `OrderId`, `Amount`, `Email` từ request.  
**Why:** endpoint callback thường là public integration boundary.  
**Production impact:** nếu không có authentication/signature validation ở middleware hoặc lớp khác, attacker có thể giả callback và đánh dấu order Paid.  
**Severity:** Critical nếu thật sự chưa có validation; nếu đã validate upstream thì không phải lỗi.  
**Recommended fix:** verify signature/token theo protocol của provider, chống replay theo quy tắc provider, validate amount/currency/order mapping từ dữ liệu server-side.

### 5. Tin `Amount` và `Email` từ callback cho business/side effect

**Problem:** payload bên ngoài được lưu và dùng trực tiếp.  
**Why:** dữ liệu callback có thể sai, bị giả mạo hoặc không phải canonical customer data.  
**Production impact:** sai số tiền hoặc gửi thông tin tới email không đúng.  
**Severity:** High.  
**Recommended fix:** đối chiếu payment với expected amount/currency/order; lấy recipient từ dữ liệu nội bộ nếu đó là business requirement.

### 6. Log toàn bộ request có thể lộ dữ liệu nhạy cảm

**Problem:** structured logging `{@Request}` serialize toàn bộ callback.  
**Why:** payload có thể chứa email, token hoặc payment metadata.  
**Production impact:** PII/secrets tồn tại lâu trong centralized logs.  
**Severity:** Medium–High tùy payload.  
**Recommended fix:** allowlist trường cần log như PaymentId, OrderId, provider correlation ID; redact dữ liệu nhạy cảm.

### 7. Không truyền cancellation token

**Problem:** EF operations không nhận `HttpContext.RequestAborted`.  
**Why:** khi client disconnect/request bị hủy, DB work vẫn có thể tiếp tục.  
**Production impact:** lãng phí tài nguyên dưới tải/outage; semantics cần được thiết kế cẩn thận vì callback có thể đã bắt đầu commit.  
**Severity:** Medium.  
**Recommended fix:** truyền cancellation token cho read/write trước commit; sau khi bắt đầu critical commit cần hiểu rõ semantics thay vì giả định cancellation rollback mọi thứ.

### 8. `NotFound()` có thể kích hoạt retry storm

**Problem:** behavior đối với unknown order chưa được thiết kế theo contract provider.  
**Why:** nhiều provider retry non-2xx.  
**Production impact:** callback lỗi vĩnh viễn có thể bị retry liên tục.  
**Severity:** Medium.  
**Recommended fix:** phân loại transient/permanent failure theo contract; lưu/audit callback không hợp lệ và trả status phù hợp.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng **database uniqueness + transactional outbox**. Chi tiết exception duplicate-key nên được chuẩn hóa theo database provider thay vì bắt `DbUpdateException` một cách mù quáng.

```csharp
[HttpPost("callback")]
public async Task<IActionResult> Callback(
    PaymentCallback request,
    CancellationToken cancellationToken)
{
    if (!await _signatureVerifier.IsValidAsync(
            Request, request, cancellationToken))
        return Unauthorized();

    var order = await _db.Orders
        .SingleOrDefaultAsync(x => x.Id == request.OrderId, cancellationToken);

    if (order is null)
        return BadRequest();

    if (order.ExpectedAmount != request.Amount)
        return BadRequest();

    await using var tx = await _db.Database
        .BeginTransactionAsync(cancellationToken);

    try
    {
        _db.PaymentEvents.Add(new PaymentEvent
        {
            PaymentId = request.PaymentId,
            OrderId = order.Id,
            Amount = request.Amount,
            CreatedAt = DateTime.UtcNow
        });

        order.MarkPaid(DateTime.UtcNow);

        _db.OutboxMessages.Add(OutboxMessage.Create(
            "PaymentConfirmed",
            new PaymentConfirmed(order.Id)));

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Payment {PaymentId} confirmed for order {OrderId}",
            request.PaymentId,
            order.Id);

        return Ok();
    }
    catch (DbUpdateException ex) when (
        _duplicateKeyDetector.IsPaymentIdDuplicate(ex))
    {
        await tx.RollbackAsync(CancellationToken.None);
        return Ok();
    }
}
```

Database cần unique constraint/index trên `PaymentEvents.PaymentId`. Outbox dispatcher đọc message chưa publish, enqueue notification với một stable message ID/idempotency key, rồi đánh dấu processed. Consumer/job cũng nên idempotent vì outbox delivery thực tế thường được thiết kế theo at-least-once.

## Trade-offs

Unique constraint đơn giản và đáng tin cậy hơn distributed lock cho invariant nằm trong database. Optimistic concurrency hữu ích khi cần bảo vệ transition của `Order`, nhưng tạo retry/conflict handling. Transactional outbox thêm bảng, dispatcher và operational complexity, đổi lại loại bỏ khoảng trống dual-write giữa business transaction và message enqueue. Nếu Hangfire dùng cùng database và có một cơ chế transaction tích hợp được chứng minh phù hợp với requirement, thiết kế có thể khác; không nên giả định atomicity giữa hai storage chỉ vì chúng cùng nằm trên một server.

## Cách kiểm thử

1. **Concurrency test:** gửi 50–100 callback đồng thời với cùng `PaymentId`; chỉ một `PaymentEvent` và một logical notification được ghi nhận.
2. **Failure-path:** DB commit thành công nhưng dispatcher tạm dừng/crash; sau restart outbox vẫn được xử lý.
3. **Duplicate delivery:** dispatcher gửi cùng outbox message hai lần; consumer không tạo duplicate side effect.
4. **Security test:** signature sai, amount sai, order/payment mapping sai phải bị từ chối và không thay đổi DB.
5. **Load test:** burst callback sau outage; theo dõi connection pool, DB latency, duplicate conflict rate và outbox backlog.

## Quan sát trong production

- Structured logs: `PaymentId`, `OrderId`, provider correlation ID, kết quả validation, duplicate detected; không log secrets/PII không cần thiết.
- Metrics: callback rate, duplicate rate, validation failure, DB conflict, processing latency, outbox backlog/age, notification retry/failure.
- Traces: HTTP callback → DB transaction → outbox dispatch → notification job.
- Alerts: outbox oldest-message age tăng, callback error rate tăng, signature failures bất thường.
- Database: unique-constraint violations, lock waits/deadlocks, slow queries và connection saturation.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao distributed lock không phải lựa chọn đầu tiên cho idempotency trong trường hợp này?
2. Nếu payment provider gửi hai `PaymentId` khác nhau cho cùng một order, unique `PaymentId` đã đủ bảo vệ business invariant chưa?
3. Bạn thiết kế outbox consumer thế nào để crash sau khi gửi email nhưng trước khi đánh dấu message processed không tạo hậu quả nghiêm trọng?

# Code Review Challenge 2 — Proxy Microsoft Graph dễ rò token và cạn connection

**Chủ đề:** HTTP client usage, async/cancellation, authentication boundary, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service gọi Microsoft Graph để đọc thông tin calendar cho người dùng. Team viết wrapper dưới đây và đăng ký nó là scoped service. Production có lúc latency tăng mạnh, nhiều request timeout sau khi traffic tăng. Log cũng đang được gửi tới hệ thống tập trung mà nhiều nhóm support có quyền truy cập.

Giả định access token được truyền từ lớp caller. Chưa biết token đó là delegated token hay application token; ứng viên cần làm rõ permission model trước khi kết luận authorization có đúng hay không.

## Đoạn code cần review

```csharp
public sealed class GraphCalendarClient
{
    private readonly ILogger<GraphCalendarClient> _logger;

    public GraphCalendarClient(ILogger<GraphCalendarClient> logger)
    {
        _logger = logger;
    }

    public async Task<string> GetEventsAsync(
        string userId,
        string accessToken,
        DateTime from,
        DateTime to)
    {
        using var client = new HttpClient();
        client.Timeout = TimeSpan.FromSeconds(100);
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        var url =
            $"https://graph.microsoft.com/v1.0/users/{userId}/calendarView" +
            $"?startDateTime={from:o}&endDateTime={to:o}";

        _logger.LogInformation(
            "Calling Graph {Url} with token {Token}", url, accessToken);

        var response = await client.GetAsync(url);
        var body = await response.Content.ReadAsStringAsync();

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogError(
                "Graph failed: {Status} {Body}",
                response.StatusCode,
                body);

            throw new Exception(body);
        }

        return body;
    }
}
```

## Kết quả code review tham khảo

### 1. Access token bị ghi trực tiếp vào log

**Problem:** bearer token xuất hiện trong `LogInformation`.  
**Why:** token là credential; centralized logs thường có retention và audience rộng hơn runtime secret store.  
**Production impact:** credential disclosure có thể cho phép truy cập API trong phạm vi quyền của token cho tới khi token hết hiệu lực/revoked theo cơ chế tương ứng.  
**Severity:** Critical.  
**Recommended fix:** tuyệt đối không log raw bearer token; scrub/redact authorization headers và secrets.

### 2. Tạo/dispose `HttpClient` mỗi request

**Problem:** mỗi call tạo một client/handler mới.  
**Why:** mất lợi ích connection pooling/reuse và có thể gây áp lực socket/connection dưới tải.  
**Production impact:** latency tăng, connection churn và khả năng resource exhaustion.  
**Severity:** High.  
**Recommended fix:** dùng `IHttpClientFactory` hoặc long-lived client/handler được quản lý đúng cách; cấu hình base address và policies tập trung.

### 3. Không propagate `CancellationToken`

**Problem:** method không nhận cancellation token.  
**Why:** request phía client bị hủy nhưng Graph call vẫn tiếp tục cho tới timeout/completion.  
**Production impact:** wasted outbound connections/work trong traffic spike hoặc downstream outage.  
**Severity:** High.  
**Recommended fix:** nhận token và truyền vào `SendAsync`/content read; kết hợp timeout policy có giới hạn.

### 4. Error body được log và ném nguyên văn

**Problem:** response body của external service bị log và đưa vào generic exception.  
**Why:** body có thể chứa identifiers hoặc thông tin không nên expose upstream.  
**Production impact:** data leakage, noisy logs, caller nhận lỗi không ổn định theo Graph payload.  
**Severity:** High.  
**Recommended fix:** parse/classify lỗi; log metadata allowlisted và correlation/request ID; trả typed exception/result nội bộ.

### 5. URI được nối chuỗi từ input

**Problem:** `userId` và query values được interpolation trực tiếp.  
**Why:** path/query components có escaping rules; `DateTime` cũng cần semantics timezone rõ ràng.  
**Production impact:** malformed request, truy cập resource ngoài dự kiến nếu validation boundary yếu, hoặc sai khoảng thời gian.  
**Severity:** Medium.  
**Recommended fix:** validate identifier theo domain, URI-escape path segment, dùng query builder/URI builder và chuẩn hóa timestamp theo contract.

### 6. Timeout 100 giây cố định và không có resilience strategy rõ ràng

**Problem:** một request có thể giữ resource rất lâu; không có bounded retry/backoff/throttling strategy.  
**Why:** downstream degradation cần được phân loại theo status và operation semantics.  
**Production impact:** latency amplification, queueing và cascading failure.  
**Severity:** High.  
**Recommended fix:** chọn timeout theo SLO; retry có giới hạn chỉ cho failure phù hợp, tôn trọng server guidance như `Retry-After` khi áp dụng, thêm jitter/backoff và circuit/bulkhead strategy nếu workload cần.

### 7. Không phân biệt 401, 403, 404, 429 và 5xx

**Problem:** mọi non-success trở thành `Exception(body)`.  
**Why:** các lỗi có semantics và remediation khác nhau.  
**Production impact:** retry sai lỗi permanent, khó monitor, khó refresh token hoặc báo permission issue đúng cách.  
**Severity:** Medium–High.  
**Recommended fix:** map status code thành typed outcomes; retry chỉ transient/throttle theo policy; không retry mù 401/403.

### 8. Permission model chưa được xác minh

**Problem:** endpoint `/users/{userId}/...` không tự chứng minh caller được phép đọc calendar đó.  
**Why:** authorization phụ thuộc token type, scopes/roles, tenant policy và business authorization của ứng dụng.  
**Production impact:** over-privileged access hoặc 403 production.  
**Severity:** High nếu application layer không enforce đúng boundary.  
**Recommended fix:** làm rõ delegated vs app-only, least privilege, tenant/user authorization và không để user-controlled `userId` tự quyết định resource được truy cập.

## Phiên bản code đề xuất

```csharp
public sealed class GraphCalendarClient
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<GraphCalendarClient> _logger;

    public GraphCalendarClient(
        HttpClient httpClient,
        ILogger<GraphCalendarClient> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<string> GetEventsAsync(
        string userId,
        string accessToken,
        DateTimeOffset from,
        DateTimeOffset to,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(userId))
            throw new ArgumentException("User is required.", nameof(userId));

        if (to <= from)
            throw new ArgumentException("Invalid time range.");

        var escapedUser = Uri.EscapeDataString(userId);
        var start = Uri.EscapeDataString(from.UtcDateTime.ToString("O"));
        var end = Uri.EscapeDataString(to.UtcDateTime.ToString("O"));

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"users/{escapedUser}/calendarView" +
            $"?startDateTime={start}&endDateTime={end}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogWarning(
                "Graph calendar request failed for user {UserId}. Status={Status}",
                userId,
                (int)response.StatusCode);

            throw GraphExceptionFactory.From(response.StatusCode);
        }

        return await response.Content.ReadAsStringAsync(cancellationToken);
    }
}
```

## Trade-offs

`IHttpClientFactory` đơn giản hóa handler lifetime và cấu hình client nhưng vẫn cần hiểu DNS/connection lifetime và resilience configuration. Timeout ngắn bảo vệ capacity nhưng có thể cắt request hợp lệ nếu SLO/Graph latency thực tế cao hơn; cần chọn bằng telemetry. Retry tăng xác suất thành công cho transient failure nhưng cũng tăng load và latency, đặc biệt nguy hiểm nếu không bounded hoặc operation không idempotent. Với GET calendar view, retry hợp lý hơn write operation, nhưng vẫn phải kiểm soát throttle.

## Cách kiểm thử

1. **Cancellation test:** fake handler trì hoãn response; cancel token và xác nhận outbound operation dừng nhanh.
2. **429 test:** mô phỏng throttle và xác nhận policy bounded, tôn trọng retry guidance được cấu hình, không tạo retry storm.
3. **401/403 test:** không retry mù; trả typed authentication/authorization failure.
4. **Security test:** capture logs và xác nhận không có access token/Authorization header hay raw sensitive body.
5. **Load test:** nhiều concurrent calls; theo dõi active connections, request latency, timeout rate và socket/handler behavior.

## Quan sát trong production

- Logs: operation name, status code, duration, tenant/user identifier đã xử lý theo privacy policy, correlation ID; không log token.
- Metrics: outbound request count, latency percentiles, 401/403/429/5xx, timeout/cancellation, retry count.
- Traces: inbound API span → Graph outbound span; giữ correlation nhưng scrub headers nhạy cảm.
- Alerts: 429 tăng đột biến, 5xx/timeout vượt threshold, latency p95/p99 tăng kéo dài.
- Capacity: active outbound requests/connections, thread-pool starvation signals nếu có triệu chứng, application queueing.

## Câu hỏi phỏng vấn mở rộng

1. `IHttpClientFactory` giải quyết vấn đề gì và không giải quyết vấn đề gì?
2. Nếu đây là delegated token, bạn sẽ ngăn một user sửa `userId` để đọc calendar của người khác ở lớp nào?
3. Nếu Graph outage kéo dài 15 phút, retry policy nào có thể khiến hệ thống của bạn tệ hơn thay vì tốt hơn?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Idempotency cần được bảo vệ tại nơi có thể enforce invariant atomic; check-then-act trong application không đủ dưới concurrency.
- Database commit và side effect/message publish là bài toán dual-write; transactional outbox là một lựa chọn thực dụng khi cần reliable delivery.
- External HTTP integration phải thiết kế cả connection reuse, cancellation, timeout, throttling, error classification và observability.
- Credentials như bearer token không thuộc về application logs.
- Authorization không chỉ là “token hợp lệ”; còn phải kiểm tra resource mà principal thực sự được phép truy cập.

## Mẫu tư duy cần nhớ

- Xác định invariant trước khi chọn lock hoặc transaction.
- Thiết kế retry cùng idempotency, không tách rời hai vấn đề.
- Không tin dữ liệu từ integration boundary chỉ vì request đã parse thành DTO.
- Timeout, cancellation và backpressure là một phần của reliability design.
- Observability phải hữu ích nhưng không được biến log thành kho secrets/PII.
