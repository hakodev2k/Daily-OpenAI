# Câu 1 — Cosmos DB RU tăng mạnh dù tổng số document không đổi

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, logical/physical partition, RU, query fan-out, indexing, data modeling, observability

## Bối cảnh

Một ASP.NET Core API phục vụ hệ thống event-management lưu `Registration` documents trong Azure Cosmos DB. Container có vài triệu documents. Team chọn `/eventId` làm partition key vì phần lớn màn hình ban đầu truy vấn registrations theo event.

Sau khi Product thêm màn hình “My registrations”, API bắt đầu chạy query theo `userId` trên toàn bộ dữ liệu. Tổng số documents không tăng đột biến, response vẫn chỉ trả khoảng 20–50 records/user, nhưng RU consumption tăng mạnh trong giờ cao điểm và một số request bắt đầu bị throttling. Một developer cho rằng “response nhỏ thì query chắc chắn rẻ”; developer khác muốn tăng provisioned throughput ngay; người thứ ba đề xuất thêm Redis mà chưa có profiling.

Chưa rõ distribution của registrations giữa các events, số physical partitions, index policy, query diagnostics hay tỷ lệ traffic giữa hai access patterns.

## Câu hỏi chính

Giải thích ở mức Cosmos DB vì sao một query trả rất ít records vẫn có thể tiêu tốn nhiều RU khi partition key không phù hợp với access pattern. Bạn sẽ xác minh cơ chế nào đang gây chi phí, và quyết định giữa giữ model hiện tại, thay partitioning/model, tạo read model hay chỉ tăng throughput như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Query “My registrations” có cung cấp partition key trong request hay phải fan-out qua nhiều logical/physical partitions?
2. Distribution theo `eventId` có skew không; có event nào cực lớn tạo hot partition không?
3. RU/query, throttled requests, diagnostics và partition-level metrics hiện cho thấy điều gì?
4. Tỷ lệ read/write và tần suất hai access patterns `eventId` vs `userId` là bao nhiêu?
5. Requirement consistency/freshness của “My registrations” có cho phép read model được cập nhật bất đồng bộ không?

## Gợi ý tư duy

### Gợi ý 1

Đừng suy RU từ số records trả về. Hãy nghĩ tới phạm vi mà query engine phải tìm kiếm trước khi tạo response.

### Gợi ý 2

Partition key quyết định data distribution và khả năng route request. Một access pattern không có partition key có thể buộc query đi rộng hơn nhiều so với payload cuối cùng.

### Gợi ý 3

Tách hai câu hỏi: “query hiện tại có thể tối ưu thêm không?” và “data model có còn phù hợp với các access patterns mới không?”. Không có một partition key hoàn hảo cho mọi query.

## Cấu trúc trả lời đề xuất

1. Làm rõ access patterns và traffic distribution.
2. Giải thích partition routing/fan-out.
3. Xác định assumptions sai về response size và RU.
4. Thu thập query diagnostics và partition metrics.
5. Kiểm tra indexing/query shape.
6. Đánh giá skew/hot partition.
7. So sánh model alternatives.
8. Chọn migration/compatibility strategy.
9. Load-test bằng production-like distribution.
10. Theo dõi RU, throttling và freshness sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Số records trả về không trực tiếp quyết định RU.
- Query không route được bằng partition key có thể trở thành cross-partition query.
- Partition key phải được đánh giá theo distribution và access patterns, không chỉ theo schema.
- Phải dùng diagnostics/metrics để chứng minh bottleneck trước khi tăng throughput hoặc thêm cache.
- Thay partition strategy là data-model/migration decision, không phải chỉ đổi một property.

### Điểm cộng

- Phân biệt logical partition, physical partition và hot partition ở mức cần thiết cho application developer.
- Đánh giá composite/index policy chỉ khi query shape cho thấy phù hợp.
- Cân nhắc duplicate/read model theo `userId` nếu access pattern quan trọng và freshness cho phép.
- Nhận ra cache không sửa partition/query cost ở source và có invalidation/failure cost riêng.

### Senior+

- Đánh giá trade-off giữa write amplification, consistency, migration complexity và read cost.
- Đề xuất benchmark bằng realistic cardinality/skew thay vì dataset nhỏ đồng đều.
- Thiết kế telemetry theo operation/access pattern và partition để phát hiện regression sớm.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng việc không đồng nhất payload nhỏ với query rẻ. Nếu container partition theo `/eventId` nhưng “My registrations” chỉ có `userId`, Cosmos DB không có đủ thông tin để route request tới một logical partition cụ thể. Query có thể phải chạy cross-partition và tổng work có thể lớn hơn nhiều số documents cuối cùng được trả về. Chi phí còn phụ thuộc query shape, indexing, document size và distribution thực tế.

Tôi sẽ lấy query diagnostics cho các request đắt, RU charge theo operation, throttling/429, latency và partition-level observations. Đồng thời kiểm tra distribution: một vài `eventId` cực lớn có thể tạo hot logical partition hoặc concentrated workload dù tổng dataset nhìn cân bằng. Cần tách vấn đề fan-out của `userId` query khỏi hot partition của event traffic vì remediation khác nhau.

Indexing cần được kiểm tra dựa trên query thực tế. Không nên mặc định “thêm index” như SQL Server; Cosmos DB indexing và RU trade-offs khác. Nếu query đang dùng sort/filter combination đặc thù, cần xem diagnostics và index policy hiện tại rồi thử thay đổi trong môi trường benchmark.

Nếu “My registrations” là access pattern quan trọng, thường xuyên và latency/RU mục tiêu không đạt với model hiện tại, tôi sẽ đánh giá một read model/container được partition theo user, chứa projection tối thiểu cho màn hình này. Điều đó đổi read efficiency lấy write amplification, eventual consistency và operational complexity. Nếu strong immediate consistency giữa hai views là business requirement, thiết kế này phải được xem lại; có thể cần chọn source/read flow khác hoặc chấp nhận chi phí khác.

Thay partition key/container là migration chứ không phải refactor nhỏ. Cần backfill, dual-write hoặc change propagation có kiểm soát, versioning/cutover và reconciliation. Nếu traffic “My registrations” rất thấp, tăng throughput hoặc chấp nhận cross-partition query có thể rẻ và đơn giản hơn việc thêm read model. Quyết định phải dựa trên cost/SLO/traffic chứ không dựa trên việc một kiến trúc nghe tối ưu hơn.

Redis chỉ hợp lý nếu workload có reuse cao và stale/invalidation semantics chấp nhận được. Nó không thay thế việc hiểu RU source. Nếu cache miss vẫn tạo query đắt và burst cùng lúc, hệ thống còn có thể gặp stampede.

Cuối cùng tôi load-test với distribution giống production, bao gồm event rất lớn, nhiều users và concurrency thực. Metrics cần tách RU/request, 429 rate, retry latency, query latency và traffic theo access pattern; nếu có read model thì thêm replication lag/reconciliation drift.

## Mẫu trả lời trong phỏng vấn

“Em không suy query rẻ từ việc nó trả 20 records. Container đang partition theo `eventId`, nên query chỉ có `userId` có thể không route được tới một logical partition và phải fan-out. Em sẽ lấy RU charge và query diagnostics, kiểm tra partition distribution, 429 và xem có hot partition hay index/query-shape issue không.

Nếu `userId` trở thành access pattern chính, em sẽ so ba lựa chọn: giữ cross-partition query nếu traffic thấp; tăng throughput nếu economics chấp nhận được; hoặc tạo projection/read model partition theo user nếu read volume đủ lớn. Read model làm read rẻ hơn nhưng tăng write amplification, eventual consistency và migration/reconciliation complexity.

Em sẽ không thêm Redis trước khi có evidence vì cache có invalidation và failure behavior riêng. Bất kỳ thay đổi partitioning nào cũng cần backfill/cutover/test với data skew giống production, rồi theo dõi RU/request, throttling và freshness.”

## Câu hỏi đào sâu

1. Nếu 90% traffic vẫn query theo `eventId` và chỉ 10% theo `userId`, điều gì có thể khiến bạn không tạo read model mới?
2. Nếu một event có hàng triệu registrations, `/eventId` có thể tạo rủi ro gì ngoài cross-partition query của `userId`?
3. Nếu Product yêu cầu “My registrations” phản ánh write ngay lập tức, recommendation của bạn thay đổi thế nào?

## Lỗi trả lời thường gặp

- Dùng response size làm proxy duy nhất cho RU.
- Chỉ nói “tăng RU” mà không tìm operation đắt.
- Đề xuất Redis trước khi hiểu access pattern.
- Cho rằng một partition key tối ưu mọi query.
- Đề xuất repartition mà bỏ qua migration, consistency và write amplification.

## Thang điểm 0–10

- **0–2:** Chỉ tăng throughput/cache, không hiểu partition routing.
- **3–4:** Biết cross-partition nhưng thiếu evidence và trade-off.
- **5–6:** Có diagnostics, distribution, indexing và model reasoning.
- **7–8:** So sánh read model/migration/consistency bằng workload thực tế.
- **9–10:** Kết nối partition mechanics với economics, SLO, migration safety và telemetry.

# Câu 2 — Optimizely đã publish đúng nhưng Akamai vẫn phục vụ nội dung cũ

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai/CDN, HTTP caching, cache invalidation, ASP.NET Core, SEO/web delivery, observability, incident response

## Bối cảnh

Một marketing website dùng Optimizely CMS làm content source và ASP.NET Core render pages. Akamai đứng trước origin để cache public pages và static assets. Editors publish một campaign page lúc 09:00. Trong CMS preview và khi gọi trực tiếp origin, nội dung mới xuất hiện ngay. Tuy nhiên một phần users vẫn thấy nội dung cũ hơn 40 phút.

Một số POP/region có vẻ cập nhật sớm hơn nơi khác. Browser hard refresh không luôn giải quyết. Team vừa thay đổi cache rules để tăng hit ratio. Search engine crawler cũng có thể gặp version cũ trong khoảng này, nên Product lo ngại campaign correctness và SEO.

Dashboard hiện có origin latency và 5xx nhưng chưa có cache-hit status, object age, purge telemetry hay correlation giữa CMS publish và CDN invalidation. Một engineer muốn giảm toàn bộ TTL xuống 30 giây; người khác muốn bypass CDN cho HTML.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào để phân biệt browser cache, CDN edge cache, origin/application cache và CMS publishing/synchronization; ổn định campaign hiện tại ra sao, xác minh root cause bằng HTTP evidence nào, và thiết kế cache invalidation lâu dài thế nào mà không phá performance?

## Câu hỏi làm rõ nên cân nhắc

1. HTML response hiện có `Cache-Control`, `Age`, `ETag`, `Vary` hoặc CDN-specific cache headers/status nào?
2. Publish workflow có trigger purge/invalidation không, và purge scope/key có map đúng URL variants không?
3. URL có nhiều hostname, locale, query-string hoặc device variants khiến purge chỉ xóa một cache key không?
4. Origin/application có thêm output/content cache ngoài Akamai không?
5. Business yêu cầu freshness sau publish là vài giây, vài phút hay eventual trong TTL?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng việc tắt cache. Trước tiên xác định layer nào đang trả object cũ.

### Gợi ý 2

Dùng response headers và request path/variant để trace cùng một URL qua browser → edge → origin. “Hard refresh” không nhất thiết buộc shared CDN cache phải miss.

### Gợi ý 3

Nếu publish và purge là hai operations độc lập, hãy reason về failure, retry, observability và reconciliation của invalidation workflow.

## Cấu trúc trả lời đề xuất

1. Xác định affected pages/regions và campaign impact.
2. Stabilize bằng targeted purge/bypass nếu cần.
3. Capture headers từ affected và healthy paths.
4. So sánh edge vs origin representation.
5. Kiểm tra cache key/TTL/purge event.
6. Form competing hypotheses.
7. Xác minh root cause.
8. Fix invalidation/configuration.
9. Test URL variants/failure path.
10. Add freshness/cache telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Phân biệt browser, CDN, application/origin cache và CMS state.
- Dùng headers/object age/cache status thay vì đoán.
- Targeted purge có thể là stabilization tốt hơn disable toàn CDN.
- Cache invalidation phải xét URL/key variants.
- Publish success không đồng nghĩa purge success.

### Điểm cộng

- Đánh giá TTL theo content class thay vì một global value.
- Cân nhắc versioned static assets và purge HTML riêng.
- Đề xuất correlation ID/event giữa CMS publish và invalidation.
- Có synthetic freshness check sau publish.

### Senior+

- Thiết kế failure-tolerant invalidation: retry/idempotency/reconciliation.
- Xét stale behavior, origin protection và thundering herd khi purge lớn.
- Đưa SEO/canonical/locale variants vào validation thay vì chỉ homepage.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định campaign pages, regions/hostnames/locales bị ảnh hưởng và freshness requirement. Nếu content sai có business impact lớn, stabilization có thể là targeted purge cho đúng cache keys hoặc tạm bypass cache cho một scope nhỏ; không tắt CDN toàn site vì điều đó có thể dồn traffic vào origin và tạo incident mới.

Tôi lấy cùng một URL từ affected client/region và từ origin, ghi lại status, `Age`, `Cache-Control`, validators và các CDN cache-status headers có sẵn. Nếu origin mới nhưng edge trả object cũ với age tăng, failure domain nghiêng về CDN/config/invalidation. Nếu edge miss vẫn lấy nội dung cũ, phải kiểm tra application/output cache hoặc origin routing. Nếu chỉ browser cũ nhưng edge/origin mới, xem browser caching/service worker nếu có.

Tiếp theo kiểm tra cache key: hostname, path normalization, locale, query-string policy, headers trong `Vary`, redirects và trailing slash. Purge `/campaign` nhưng traffic thật dùng `/en/campaign/`, alternate hostname hoặc query variant có thể để lại objects cũ. Tôi cũng kiểm tra rule vừa deploy: TTL, cacheability, stale behavior và precedence của rules.

Nếu CMS publish có workflow gọi purge, publish và purge là hai side effects khác nhau. Purge failure phải observable, retry được và idempotent. Không nên báo workflow hoàn toàn “done” nếu business contract yêu cầu edge freshness mà invalidation chưa được xác nhận. Có thể dùng event/outbox-like durable work tùy architecture, nhưng không cần messaging phức tạp nếu volume thấp và một reliable retry worker đơn giản đủ đáp ứng.

TTL 30 giây toàn site giảm stale window nhưng làm hit ratio/origin load xấu đi và vẫn không giải quyết invalidation correctness. Bypass HTML cũng bỏ lợi ích edge caching. Tốt hơn là phân loại: immutable/versioned assets có TTL dài; HTML campaign có TTL phù hợp business freshness cộng targeted purge khi publish; content ít nhạy cảm có thể TTL dài hơn.

Testing gồm publish → purge → verify nhiều POP/hostname/locale variants; purge API timeout/retry; origin unavailable trong purge; burst sau invalidation để xem origin capacity; và Playwright/synthetic check cho critical pages. Production telemetry cần cache hit/miss, age distribution, purge success/failure/latency, origin request surge, publish-to-edge-fresh duration và synthetic content-version checks.

SEO cần kiểm tra crawler-visible representation, redirects/canonical và locale URLs sau publish. Vấn đề ở đây là delivery correctness, không phải chỉ cache performance.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không tắt CDN ngay. Em xác định affected URLs/regions và dùng targeted purge nếu campaign đang sai. Sau đó em lấy cùng URL qua edge và origin, so `Age`, `Cache-Control`, validators và CDN cache status để biết layer nào stale.

Nếu origin mới nhưng edge cũ, em kiểm tra cache key và purge coverage: hostname, locale, query, trailing slash, `Vary`. Em cũng review rule vừa đổi. Nếu CMS publish gọi purge riêng, em coi đó là distributed workflow: purge phải có success/failure telemetry, retry và reconciliation; publish success không tự chứng minh edge đã fresh.

Về dài hạn em không đặt TTL 30 giây toàn site. Em phân loại content: versioned assets TTL dài, HTML có TTL theo freshness SLO và targeted invalidation. Em thêm publish-to-edge freshness metric và synthetic checks qua các URL variants để bắt regression.”

## Câu hỏi đào sâu

1. Nếu targeted purge làm hàng nghìn edge objects miss cùng lúc, bạn bảo vệ origin thế nào?
2. Nếu purge API trả success nhưng một số region vẫn stale, bạn cần evidence/reconciliation gì tiếp theo?
3. Khi nào bạn chấp nhận TTL-only thay vì event-driven invalidation?

## Lỗi trả lời thường gặp

- Tắt CDN hoặc giảm TTL toàn site ngay.
- Chỉ hard-refresh browser rồi kết luận.
- Không kiểm tra cache key variants.
- Coi CMS publish success là bằng chứng CDN fresh.
- Bỏ qua origin load sau purge.

## Thang điểm 0–10

- **0–2:** Disable cache không điều tra.
- **3–4:** Biết CDN cache nhưng thiếu layered evidence.
- **5–6:** Có headers, purge/key analysis và stabilization hợp lý.
- **7–8:** Có retry/reconciliation, content-class TTL và failure tests.
- **9–10:** Kết nối freshness SLO, origin protection, SEO và end-to-end observability.

# Câu 3 — Thiết kế AI-assisted code review cho repository enterprise mà không trao quyền sửa code vô kiểm soát

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** AI-assisted engineering, Git/CI/CD, security, repository grounding, testing, human review, architecture, observability, engineering process

## Bối cảnh

Một engineering organization có nhiều repositories C#/.NET, Vue.js và infrastructure configuration. Team muốn dùng AI để hỗ trợ pull-request review: đọc diff và repository context, tìm bug/risk, đề xuất tests và có thể tạo patch suggestion. Mục tiêu là giảm thời gian review nhưng không được tự merge code.

Repositories có business logic nội bộ, configuration và đôi lúc developer vô tình đưa secrets vào diff. CI hiện có unit/integration tests, SonarQube và security scanning ở mức cơ bản. Một số repositories lớn; gửi toàn bộ source vào mỗi review là tốn kém và không cần thiết. AI output có thể hallucinate APIs, hiểu sai architecture hoặc đề xuất refactor quá rộng.

Có ba proposal:

1. Cho agent clone repo, có write token và tự push fix branch.
2. Chỉ gửi PR diff vào model và post comment.
3. Xây workflow retrieval có read-only repository access, lấy diff + targeted context, tạo structured findings và optional patch artifact nhưng mọi thay đổi phải qua CI + human approval.

Chưa có quyết định về permission boundary, context selection, confidence/evidence, evaluation metrics hay cách xử lý prompt injection trong repository content.

## Câu hỏi chính

Bạn sẽ thiết kế một AI-assisted PR review workflow như thế nào để hữu ích nhưng có thể kiểm chứng, giới hạn quyền, grounded vào repository source và không biến probabilistic model thành authority của merge pipeline? Hãy so sánh ba proposal và nêu điều kiện khiến bạn chọn giải pháp đơn giản hơn hoặc phức tạp hơn.

## Câu hỏi làm rõ nên cân nhắc

1. AI chỉ review hay còn được tạo patch/branch; action nào thực sự cần write permission?
2. Repositories/data có policy nào về việc gửi source ra external service hoặc cần self-hosted/private boundary không?
3. Loại findings nào cần deterministic scanner thay vì LLM reasoning?
4. Review latency/cost budget và repository size/context constraints là bao nhiêu?
5. Success được đo bằng reviewer time saved, true-positive rate, escaped defects hay metric nào khác?

## Gợi ý tư duy

### Gợi ý 1

Tách **reasoning capability** khỏi **authority**. Một model có thể đề xuất thay đổi mà không cần quyền merge hoặc write vào protected branch.

### Gợi ý 2

Context nên grounded và tối thiểu cần thiết: diff, changed symbols, callers/tests/config liên quan; deterministic tools vẫn giữ vai trò cho compile/test/static analysis.

### Gợi ý 3

Repository content là untrusted input đối với agent. Hãy reason về prompt injection, secrets, permissions, tool allowlist và audit trail giống một security boundary.

## Cấu trúc trả lời đề xuất

1. Clarify scope và threat model.
2. Xác định deterministic vs probabilistic responsibilities.
3. Thiết kế least-privilege tool boundary.
4. Chọn repository retrieval/context strategy.
5. Định nghĩa structured evidence/findings.
6. Thiết kế patch workflow nếu cần.
7. Bắt buộc CI/tests/static analysis.
8. Human approval/merge policy.
9. Evaluate quality/cost/latency.
10. Monitor và continuously calibrate.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI không nên có merge authority chỉ vì nó có thể generate patch.
- Read-only access là default tốt cho review; write permission phải có use case và scope rõ.
- Compile/tests/static analysis là deterministic gates, không giao hoàn toàn cho model.
- Findings cần source grounding/evidence để reviewer kiểm tra.
- Repository text có thể chứa malicious/untrusted instructions.

### Điểm cộng

- Context retrieval theo changed symbols/dependencies/tests thay vì dump toàn repo.
- Secret redaction/detection trước model context khi phù hợp.
- Structured output: severity, file/line, evidence, hypothesis, suggested verification.
- Measure precision/acceptance/escaped defects thay vì số comments.

### Senior+

- Thiết kế evaluation dataset từ historical PRs/incidents mà tránh leakage.
- Có policy/tool sandbox cho agent và audit trail mọi read/action.
- Progressive rollout: advisory-only → patch suggestion → scoped automation khi evidence đủ mạnh.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng threat model và authority boundary. Mục tiêu là hỗ trợ reviewer, nên default workflow chỉ cần read repository/PR data và quyền post suggestion nếu platform cho phép. Không có lý do để cấp token có quyền push vào protected branch hoặc merge. Nếu sau này cần tạo patch branch, dùng credential/service identity scope tối thiểu, branch riêng, explicit policy và vẫn bắt buộc CI + human approval.

Proposal chỉ gửi diff là đơn giản và an toàn hơn nhưng dễ thiếu context: một thay đổi DI lifetime, authorization policy hoặc public contract có thể chỉ hiểu được khi xem callers, tests, configuration và related types. Proposal clone toàn repo + write token lại mở authority/risk quá rộng. Tôi ưu tiên targeted retrieval: bắt đầu từ diff, resolve changed symbols, đọc surrounding code, interfaces, relevant callers/tests/config theo nhu cầu; mọi evidence nên trỏ về exact repository revision để tránh context drift.

Tôi tách deterministic tasks khỏi LLM reasoning. Build, unit/integration tests, format/lint, SonarQube, dependency/security scanners và secret scanning tiếp tục là pipeline gates. AI phù hợp hơn cho semantic review: missing failure path, race condition hypothesis, unclear boundary, test gaps, architecture inconsistency. Nó có thể đề xuất test/patch nhưng không được tự tuyên bố “verified” nếu chưa chạy tool tương ứng.

Output nên structured: finding, severity, file/line/symbol, repository evidence, reasoning ngắn, confidence nếu dùng, verification step và suggested fix. Reviewer phải phân biệt observed fact với inference. Nếu model nói API tồn tại, workflow có thể ground bằng source/package docs hoặc compile patch; không tin tên API do model tự sinh.

Repository content là untrusted. Comment, Markdown, source string hoặc fixture có thể chứa instruction nhằm điều khiển agent. System/tool policy phải quy định repository text là data, không được tự thay đổi permission hoặc gọi arbitrary network/tool vì nội dung repo yêu cầu. Tool allowlist, network restrictions, secret handling, max scope và audit logs là quan trọng. Secret scanner nên chạy trước/độc lập; không dựa vào LLM để quyết định secret có an toàn gửi đi không.

Patch generation nếu bật nên tạo artifact/suggestion hoặc branch riêng, không push thẳng protected branch. CI chạy compile/tests/scanners; reviewer xem diff cuối cùng. Nếu patch quá rộng so với finding, policy có thể reject hoặc yêu cầu explicit approval.

Evaluation không dùng “số comments” vì spam comments làm review tệ hơn. Tôi đo precision/false-positive rate, acceptance rate có phân loại, reviewer time, defects caught trước merge, regressions từ accepted suggestions, cost/latency. Tạo benchmark từ historical bugs/PRs đã anonymize/curate, đồng thời test adversarial prompt injection và hallucinated API cases.

Rollout nên progressive. Bắt đầu advisory-only trên subset repositories, thu feedback, điều chỉnh context/retrieval và threshold. Chỉ thêm patch capability khi review quality đủ tốt. Với repo nhỏ/risk thấp, diff-only workflow có thể đủ và rẻ hơn; không cần agentic retrieval nếu marginal value thấp.

## Mẫu trả lời trong phỏng vấn

“Em tách khả năng reasoning khỏi quyền hành động. Với PR review, default agent chỉ cần read-only repo access và quyền tạo review suggestion; không cần merge token. Diff-only khá an toàn nhưng thiếu context, còn clone toàn repo kèm write token là quá rộng. Em chọn retrieval theo diff: lấy changed symbols, related callers, tests và config ở đúng commit SHA.

Build, tests, SonarQube, secret/security scanning vẫn là deterministic gates. AI tập trung semantic findings và phải đưa evidence file/line cùng verification step. Repository content được coi là untrusted data để chống prompt injection; tool calls bị allowlist, credentials least-privilege và có audit trail.

Nếu bật patch generation, patch đi qua branch/artifact riêng, CI chạy đầy đủ và human vẫn approve merge. Em đo precision, false positives, reviewer time và escaped defects chứ không đo số comments. Rollout từ advisory-only rồi mới tăng quyền khi evidence chứng minh value.”

## Câu hỏi đào sâu

1. Nếu reviewer phàn nàn retrieval bỏ sót context quan trọng, bạn tăng recall mà không gửi toàn repository bằng cách nào?
2. Nếu AI patch pass toàn bộ tests nhưng thay đổi business behavior sai, workflow của bạn còn thiếu control nào?
3. Khi nào diff-only reviewer đơn giản lại tốt hơn một agent có repository tools?

## Lỗi trả lời thường gặp

- Cấp write/merge permission chỉ vì agent có khả năng sửa code.
- Dùng LLM thay compiler/tests/static scanners.
- Gửi toàn repo mặc định mà không xét privacy/cost/context relevance.
- Không coi repository text là untrusted input.
- Đánh giá success bằng số comments thay vì quality/outcome.

## Thang điểm 0–10

- **0–2:** “Cho AI review và merge nếu tests pass”, thiếu security/verification.
- **3–4:** Có human approval nhưng context/permissions còn mơ hồ.
- **5–6:** Có read-only grounding, deterministic gates và structured findings.
- **7–8:** Có prompt-injection threat model, scoped patch workflow, evaluation metrics.
- **9–10:** Thiết kế progressive, measurable, least-privilege và biết khi nào giải pháp đơn giản hơn là đủ.
