# Code Review Challenge 1 — Approval workflow: mất cập nhật khi hai approver thao tác đồng thời

**Chủ đề:** C#/.NET 8, ASP.NET Core, EF Core, PostgreSQL, optimistic concurrency, authorization  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 9

## Bối cảnh

Ứng dụng Hiring Requisition có quy trình Line Manager → Superior Manager → HR. Một request có thể bị mở ở nhiều browser tab, hệ thống chạy 3 instances. Khi approver A nhấn Approve và approver B nhấn Reject gần như đồng thời, audit history đôi khi ghi cả hai quyết định nhưng trạng thái cuối chỉ phản ánh một. Có trường hợp approver không thuộc stage hiện tại vẫn thao tác được khi gọi API trực tiếp. Yêu cầu: một stage chỉ được quyết định một lần, lưu được lịch sử đáng tin cậy, không mất quyết định do retry, và trả lỗi rõ ràng cho client.

## Đoạn code cần review

```csharp
public sealed record DecideRequest(Guid RequestId, string Action, string? Comment);

[ApiController]
[Route("api/requests")]
public sealed class ApprovalsController(AppDbContext db) : ControllerBase
{
    [HttpPost("{id:guid}/decision")]
    [Authorize]
    public async Task<IActionResult> Decide(
        Guid id, [FromBody] DecideRequest input)
    {
        var request = await db.Requisitions
            .FirstOrDefaultAsync(x => x.Id == id);

        if (request is null) return NotFound();

        var actor = User.FindFirst("email")?.Value ?? "unknown";
        if (request.Status == "Rejected" || request.Status == "Approved")
            return Conflict("Already completed");

        if (input.Action == "Approve")
        {
            request.Stage = request.Stage switch
            {
                "LineManager" => "SuperiorManager",
                "SuperiorManager" => "HR",
                _ => "Completed"
            };
            request.Status = request.Stage == "Completed"
                ? "Approved" : "Pending";
        }
        else
        {
            request.Status = "Rejected";
        }

        db.ApprovalHistories.Add(new ApprovalHistory
        {
            Id = Guid.NewGuid(),
            RequisitionId = request.Id,
            Actor = actor,
            Action = input.Action,
            Comment = input.Comment,
            CreatedAt = DateTime.UtcNow
        });

        await db.SaveChangesAsync();
        return Ok(new { request.Status, request.Stage });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Broken object-level và stage-level authorization

**Vấn đề:** Chỉ có `[Authorize]`, không xác minh actor thuộc tenant/request và được phân quyền ở stage hiện tại.  
**Tại sao xảy ra:** Authentication không phải resource authorization. Email claim không phải bằng chứng actor là approver hợp lệ.  
**Ảnh hưởng production:** User đăng nhập có thể duyệt/từ chối request không thuộc quyền.  
**Cách sửa:** Lấy subject ổn định từ validated identity, kiểm tra tenant, stage và assignment từ DB hoặc policy/service đáng tin cậy ngay trong transaction; deny mặc định.

### [High] — Lost update khi hai quyết định đồng thời

**Vấn đề:** Read-modify-write không có concurrency guard.  
**Tại sao xảy ra:** Hai transaction có thể cùng đọc trạng thái cũ, rồi lần lượt ghi; mặc định không đảm bảo chỉ một transition thắng.  
**Ảnh hưởng production:** Trạng thái cuối và audit history bất nhất.  
**Cách sửa:** Optimistic concurrency bằng version token có kiểm soát trên PostgreSQL (ví dụ cột bigint Version tăng khi transition) hoặc atomic conditional UPDATE; conflict trả 409 và không ghi history cho lần thua.

### [High] — Không kiểm soát retry/idempotency

**Vấn đề:** Client gửi lại cùng decision có thể tạo history trùng hoặc áp dụng decision vào stage mới.  
**Tại sao xảy ra:** Không có request/operation identifier và unique constraint.  
**Ảnh hưởng production:** Một click tạo nhiều quyết định, thậm chí duyệt stage kế tiếp khi actor có nhiều role.  
**Cách sửa:** Idempotency key có scope theo request + actor + operation, unique constraint; lưu fingerprint payload và kết quả trong cùng transaction.

### [High] — Stage transition thiếu state machine validation

**Vấn đề:** Stage lạ vẫn có thể được Approve thành Completed; mọi action khác `Approve` bị hiểu là Reject.  
**Tại sao xảy ra:** Dùng chuỗi tự do, default branch không fail closed.  
**Ảnh hưởng production:** Transition bất hợp lệ, request bị từ chối ngoài ý muốn.  
**Cách sửa:** Enum/typed command, whitelist transition rõ ràng, validate trạng thái Pending và stage hợp lệ.

### [High] — Thiếu expected stage/version từ client

**Vấn đề:** Request không gắn với stage mà người dùng đã xem.  
**Tại sao xảy ra:** API áp dụng decision vào trạng thái mới nhất mà không biết ý định ban đầu.  
**Ảnh hưởng production:** Một action trên màn hình cũ có thể duyệt nhầm stage tiếp theo.  
**Cách sửa:** Bắt buộc expected stage và expected version/ETag; mismatch trả 409 với trạng thái hiện tại đã được lọc theo quyền.

### [Medium] — Route ID và body ID không được đối chiếu

**Vấn đề:** `input.RequestId` bị bỏ qua.  
**Tại sao xảy ra:** Hai nguồn định danh không có invariant.  
**Ảnh hưởng production:** Client gửi nhầm request mà không được phát hiện.  
**Cách sửa:** Bỏ body ID hoặc validate bằng route ID.

### [Medium] — Actor identity và audit metadata yếu

**Vấn đề:** Fallback `unknown`, lưu email có thể thay đổi và không lưu from/to stage hay correlation.  
**Tại sao xảy ra:** Audit dựa trên claim tùy chọn, không mô hình hóa transition.  
**Ảnh hưởng production:** Khó truy vết trách nhiệm, khó điều tra incident.  
**Cách sửa:** Subject ID bắt buộc, tenant ID, from/to state, operation ID, timestamp và trace ID; tránh log PII không cần thiết.

### [Medium] — Thiếu cancellation và phân loại lỗi

**Vấn đề:** Query và SaveChanges không nhận RequestAborted; lỗi concurrency/database chưa có response contract.  
**Tại sao xảy ra:** Controller chỉ xử lý not-found và completed.  
**Ảnh hưởng production:** Request hủy vẫn tiêu tốn tài nguyên; lỗi transient trả 500 khó hiểu.  
**Cách sửa:** Truyền CancellationToken, map validation 400/422, forbidden 403, conflict 409, transient 503 khi thích hợp; không retry decision mù quáng.

### [Low] — Không có telemetry cho quyết định thất bại

**Vấn đề:** Không đo rejected authorization, conflict và transition latency.  
**Tại sao xảy ra:** Chỉ dựa vào HTTP response.  
**Ảnh hưởng production:** Không phân biệt race hợp lệ với lỗi thiết kế.  
**Cách sửa:** Structured logs không chứa comment nhạy cảm, counters theo outcome, trace cho DB transaction.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa lõi transition. Giả định schema có `Version bigint`, `DecisionOperations` với unique index `(RequisitionId, ActorId, OperationId)`; `ApprovalHistories` và operation record được lưu cùng transaction. `IAuthorizationService` ở đây là service nghiệp vụ tự triển khai, không phải interface framework cùng tên. Các helper được nêu rõ là contract cần triển khai, không phải API EF Core dựng sẵn.

```csharp
public sealed record DecisionCommand(
    string Action, string ExpectedStage, long ExpectedVersion,
    Guid OperationId, string? Comment);

public async Task<DecisionResult> DecideAsync(
    Guid id, DecisionCommand cmd, Actor actor, CancellationToken ct)
{
    if (cmd.OperationId == Guid.Empty ||
        cmd.Action is not ("Approve" or "Reject"))
        return DecisionResult.Invalid();

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var existing = await db.DecisionOperations
        .AsNoTracking()
        .SingleOrDefaultAsync(x => x.RequisitionId == id &&
            x.ActorId == actor.Id && x.OperationId == cmd.OperationId, ct);

    if (existing is not null)
        return existing.PayloadHash == Hash(cmd)
            ? DecisionResult.FromStored(existing)
            : DecisionResult.Conflict();

    var item = await db.Requisitions.SingleOrDefaultAsync(
        x => x.Id == id && x.TenantId == actor.TenantId, ct);
    if (item is null) return DecisionResult.NotFound();

    if (!await authorization.CanDecideAsync(actor, item, ct))
        return DecisionResult.Forbidden();

    if (item.Status != "Pending" ||
        item.Stage != cmd.ExpectedStage ||
        item.Version != cmd.ExpectedVersion)
        return DecisionResult.Conflict();

    var from = item.Stage;
    var to = transitions.Apply(item.Stage, cmd.Action);
    if (to is null) return DecisionResult.Invalid();

    item.Stage = to.Stage;
    item.Status = to.Status;
    item.Version++;

    db.ApprovalHistories.Add(History.For(
        item, actor.Id, from, cmd.Action, cmd.OperationId, cmd.Comment));
    db.DecisionOperations.Add(DecisionOperation.For(
        item.Id, actor.Id, cmd.OperationId, Hash(cmd), to));

    try
    {
        await db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
        return DecisionResult.Success(to);
    }
    catch (DbUpdateConcurrencyException)
    {
        await tx.RollbackAsync(CancellationToken.None);
        return DecisionResult.Conflict();
    }
    catch (DbUpdateException ex) when (IsUniqueOperationConflict(ex))
    {
        await tx.RollbackAsync(CancellationToken.None);
        return await LoadRecordedResultAsync(id, actor.Id, cmd, ct);
    }
}
```

**Điều kiện bắt buộc để ví dụ đúng:** Map `Version` bằng `IsConcurrencyToken()`, cấu hình DB constraint và transition table; khi retry trùng operation, helper phải so sánh payload fingerprint trước khi trả kết quả đã lưu. Sau exception do commit outcome không rõ, cần đọc lại operation record trên connection/transaction mới; không tự động thực hiện transition lần nữa. Kiểm tra authorization cần dựa trên assignment được bảo vệ khỏi thay đổi đồng thời (nếu assignment có thể bị revoke trong lúc transaction, cần chính sách consistency và lock/version phù hợp). Không gọi external notification trong transaction; nếu cần, dùng transactional outbox.

## Giải thích thiết kế sau khi sửa

Concurrency token đảm bảo một phiên bản state không bị ghi đè âm thầm. Unique operation key đảm bảo cùng một lệnh retry không tạo side effect mới. State machine chặn transition không hợp lệ; resource authorization bảo vệ quyền quyết định. Audit được commit cùng business state. Với EF Core + PostgreSQL, `Version` phải thực sự là concurrency token được tăng ở mọi update liên quan; unique constraint và exception mapping phải được kiểm chứng bằng integration test thực tế.

## Trade-offs

Optimistic concurrency phù hợp khi conflict hiếm, nhưng client phải xử lý 409 và refresh state. Row locking/serializable transaction có thể phù hợp nếu nhiều writer cùng tranh một request, đổi lại tăng blocking và nguy cơ deadlock. Idempotency table thêm storage và lifecycle cleanup; chỉ cần nếu retry có thể xảy ra và quyết định là nghiệp vụ quan trọng. Transactional outbox tăng độ phức tạp nhưng cần khi publish sự kiện phải đáng tin cậy.

## Cách kiểm thử

1. **Concurrency integration:** 20 requests đồng thời với cùng version, hai action đối nghịch; đúng một transition/history được commit, phần còn lại conflict hoặc replay hợp lệ.
2. **Security:** user khác tenant, actor không được assign và actor thuộc stage cũ đều bị từ chối.
3. **Retry/failure-path:** gửi lại cùng operation sau khi server commit nhưng response bị mất; trả lại kết quả cũ, không tạo history mới.
4. **Validation:** action lạ, stage lạ, body ID sai và expected version cũ không thay đổi DB.
5. **Database test:** verify unique constraint và concurrency token trên PostgreSQL thật, không chỉ EF InMemory.

## Quan sát trong production

Theo dõi `approval_decision_total{outcome}`, tỷ lệ 403/409, p95 decision latency, DB deadlocks, serialization/concurrency exceptions và số history records trên mỗi transition. Structured log gồm request ID dạng opaque, actor ID, stage, operation ID và trace ID; không ghi comment/PII. Alert nếu phát hiện nhiều quyết định committed cho cùng stage/version hoặc lịch sử không khớp state.

# Code Review Challenge 2 — Vue.js search: kết quả cũ ghi đè bộ lọc mới và cache sai tenant

## Bối cảnh

Bộ phận QA cũng báo rằng kết quả search bị nhảy ngược về query cũ. Search endpoint yêu cầu access token và phân quyền theo tenant ở server. ## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Candidate = { id: string; name: string; summary: string };
const props = defineProps<{ tenantId: string; accessToken: string }>();

const keyword = ref('');
const candidates = ref<Candidate[]>([]);
const loading = ref(false);
const error = ref('');
const selected = ref<Candidate | null>(null);
const cache = new Map<string, Candidate[]>();

async function search() {
  const q = keyword.value.trim();
  const key = q.toLowerCase();

  if (cache.has(key)) {
    candidates.value = cache.get(key)!;
    return;
  }

  loading.value = true;
  error.value = '';
  try {
    const response = await fetch(
      `/api/candidates?tenant=${props.tenantId}&q=${encodeURIComponent(q)}`,
      { headers: { Authorization: `Bearer ${props.accessToken}` } }
    );
    const body = await response.json();
    candidates.value = body.items;
    cache.set(key, body.items);
  } catch (e) {
    error.value = 'Không thể tải dữ liệu';
  } finally {
    loading.value = false;
  }
}

watch(keyword, search);
watch(() => props.tenantId, search);
onMounted(search);
</script>

<template>
  <input v-model="keyword" placeholder="Search candidates" />
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="item in candidates" :key="item.id">
      <button @click="selected = item">{{ item.name }}</button>
      <div v-html="item.summary"></div>
    </li>
  </ul>
  <aside v-if="selected">{{ selected.name }}</aside>
</template>
```

## Kết quả code review tham khảo

**Tại sao xảy ra:** Cache bỏ qua security scope.

**Tại sao xảy ra:** Token đổi/logout không invalidate state.  
**Ảnh hưởng production:** Kết quả và selected candidate của session trước vẫn hiển thị.

**Cách sửa:** Chỉ generation hiện hành được cập nhật loading/error.

### [Medium] — Không reset selected khi query/tenant thay đổi

**Vấn đề:** Panel bên phải vẫn giữ candidate cũ.  
**Tại sao xảy ra:** `selected` độc lập với search context.  
**Ảnh hưởng production:** Xem thông tin ngoài scope hiện tại.  
**Cách sửa:** Clear selected ngay khi search scope đổi, verify authorization khi mở detail.

### [Medium] — Không debounce và không giới hạn query

**Vấn đề:** Mỗi ký tự phát request, kể cả chuỗi trống/dài.  
**Tại sao xảy ra:** Watch trực tiếp gọi search.  
**Ảnh hưởng production:** Tăng tải API, DB/search service và chi phí.  
**Cách sửa:** Debounce hợp lý, validate length, server-side rate limit/pagination; đo trước khi chọn TTL/cache.

## Phiên bản đề xuất

Ví dụ không cache dữ liệu nhạy cảm ở client. `sessionId` là identifier phiên không chứa secret, do tầng authentication quản lý và thay đổi khi login/logout/switch account. Backend vẫn phải authorize tenant từ identity, không tin tenant query string.

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue';

type Candidate = { id: string; name: string; summary: string };
const props = defineProps<{
  tenantId: string; accessToken: string; sessionId: string
}>();

const keyword = ref('');
const candidates = ref<Candidate[]>([]);
const selected = ref<Candidate | null>(null);
const loading = ref(false);
const error = ref('');
let generation = 0;
let controller: AbortController | undefined;
let timer: ReturnType<typeof setTimeout> | undefined;

function reset() {
  candidates.value = [];
  selected.value = null;
  error.value = '';
}

watch(
  () => [keyword.value, props.tenantId, props.sessionId, props.accessToken],
  () => {
    const current = ++generation;
    controller?.abort();
    if (timer) clearTimeout(timer);
    reset();
    loading.value = false;

    const q = keyword.value.trim();
    const tenant = props.tenantId;
    const token = props.accessToken;
    if (!token || !props.sessionId || !tenant || q.length > 100) return;

    timer = setTimeout(async () => {
      const active = new AbortController();
      controller = active;
      if (current === generation) loading.value = true;
      try {
        const params = new URLSearchParams({ tenant, q });
        const response = await fetch(`/api/candidates?${params}`, {
          headers: { Authorization: `Bearer ${token}` },
          signal: active.signal,
          cache: 'no-store'
        });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const body: unknown = await response.json();
        if (!isCandidateResponse(body)) throw new Error('Invalid response');
        if (current === generation) candidates.value = body.items;
      } catch (e) {
        if (current === generation && !active.signal.aborted)
          error.value = 'Không thể tải dữ liệu';
      } finally {
        if (current === generation) loading.value = false;
      }
    }, 250);
  },
  { immediate: true }
);

onBeforeUnmount(() => {
  generation++;
  controller?.abort();
  if (timer) clearTimeout(timer);
});

function isCandidateResponse(value: unknown): value is { items: Candidate[] } {
  if (!value || typeof value !== 'object' || !('items' in value)) return false;
  const items = (value as { items: unknown }).items;
  return Array.isArray(items) && items.every(x =>
    x && typeof x === 'object' &&
    typeof x.id === 'string' &&
    typeof x.name === 'string' &&
    typeof x.summary === 'string');
}
</script>

<template>
  <input v-model="keyword" placeholder="Search candidates" />
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="item in candidates" :key="item.id">
      <button @click="selected = item">{{ item.name }}</button>
      <div>{{ item.summary }}</div>
    </li>
  </ul>
  <aside v-if="selected">{{ selected.name }}</aside>
</template>
```

## Giải thích thiết kế sau khi sửa

Generation guard đảm bảo request cũ không thể ghi state ngay cả khi abort đến muộn. Reset đồng bộ khi scope đổi tránh giữ kết quả cũ trong lúc debounce. `no-store` chỉ là yêu cầu đối với HTTP cache; server phải cấu hình response cache headers phù hợp và kiểm soát tenant. Không nên truyền access token qua URL. Ví dụ giả định component được unmount hoặc `sessionId` đổi ngay khi logout; auth layer phải thực thi invariant đó. Với ứng dụng thực tế, có thể thay watcher thủ công bằng query library hỗ trợ cancellation, key scoping và invalidation nếu complexity xứng đáng.

## Trade-offs

Không cache làm tăng request nhưng giảm nguy cơ giữ dữ liệu nhạy cảm. Debounce tăng độ trễ nhỏ khi nhập liệu, đổi lại giảm tải. Abort không đảm bảo server đã dừng query, nên cần server cancellation/rate limiting. Runtime response validation thêm CPU nhỏ nhưng ngăn payload lỗi làm hỏng state; nếu API contract được sinh tự động vẫn cần phân biệt static types và dữ liệu network.

## Cách kiểm thử

1. **Race/E2E:** Mock response query A chậm hơn B; kết quả cuối chỉ là B.
2. **Tenant/session security:** Chuyển tenant/logout khi request đang chạy; không còn candidate cũ trong list hoặc selected.
3. **XSS:** Summary chứa HTML độc hại phải được hiển thị như text, không thực thi.
4. **Failure-path:** 401/403/500, invalid JSON, network abort; không render dữ liệu cũ và loading kết thúc đúng.
5. **Load test:** Gõ 30 ký tự nhanh, xác minh debounce giảm request và backend vẫn giới hạn tài nguyên.

## Quan sát trong production

Theo dõi browser network waterfall, số request search/keystroke, canceled requests, tỷ lệ 401/403/5xx, client-side error counts và p95 API search latency. Dùng correlation ID nối frontend telemetry với backend traces. Không log access token, tên ứng viên hay search query nhạy cảm. Alert nếu phát hiện cross-tenant authorization denial tăng đột biến; kiểm thử định kỳ invariant server-side tenant isolation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu muốn cache search 30 giây, cache key và invalidation phải phụ thuộc vào những gì?
2. Nếu dùng TanStack Query cho Vue, cơ chế nào thay thế generation guard và reset thủ công?
3. Nếu search endpoint nhận tenantId từ client nhưng token có tenant claim khác, backend nên xử lý ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Approval workflow là state machine có authorization theo resource và stage, không chỉ authentication.
- Optimistic concurrency, unique operation key và transaction bảo vệ các invariant khác nhau; retry phải được thiết kế cùng idempotency.
- Frontend async responses không có bảo đảm hoàn thành theo thứ tự; cancellation và generation guard bổ sung cho nhau.
- Tenant isolation phải được enforce tại server; cache, selected state và DOM rendering đều có thể tạo data exposure.

## Mẫu tư duy cần nhớ

1. Xác định invariant và trust boundary trước khi sửa code.
2. Thiết kế retry cùng idempotency, không xem retry là thao tác vô hại.
3. Kiểm tra hành vi khi hai writer hoặc hai network requests chạy đồng thời.
4. Phân biệt client-side UX protection với server-side authorization.
5. Test failure paths và đo telemetry để chứng minh giải pháp.
