# Code Review Challenge 1 — `.Result` trong ASP.NET Core làm throughput sụt mạnh và tạo ThreadPool starvation dưới tải

**Chủ đề:** async/await, ThreadPool, HTTP client usage, cancellation, performance, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API tổng hợp thông tin người dùng từ database và một external profile service. Endpoint bình thường phản hồi khoảng 150–300 ms. Sau khi traffic tăng, production ghi nhận:

- p50 vẫn chấp nhận được nhưng p95/p99 tăng lên nhiều giây,
- CPU không luôn đạt 100% nhưng số request đang chờ tăng nhanh,
- ThreadPool thread count tăng mạnh trong giờ cao điểm,
- một số request timeout dù external API chỉ mất khoảng 200–500 ms,
- scale-out thêm instance giúp tạm thời nhưng khi traffic tăng tiếp thì triệu chứng quay lại,
- request bị client cancel vẫn tiếp tục gọi external service,
- log không phân biệt được thời gian chờ ThreadPool, thời gian HTTP và thời gian database.

Team cho rằng vì `GetUserProfileAsync()` đã là async nên gọi `.Result` ở service “không khác nhiều” so với `await`.

## Đoạn code cần review

```csharp
public sealed class UserSummaryService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<UserSummaryService> _logger;

    public UserSummaryService(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<UserSummaryService> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<UserSummaryDto?> GetAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var user = await _db.Users
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == userId,
                cancellationToken);

        if (user is null)
            return null;

        var profile = GetUserProfileAsync(user.ExternalProfileId).Result;

        _logger.LogInformation(
            "Loaded summary for user {UserId}",
            userId);

        return new UserSummaryDto(
            user.Id,
            user.DisplayName,
            profile.Department,
            profile.Office);
    }

    private async Task<ExternalProfile> GetUserProfileAsync(string profileId)
    {
        var response = await _httpClient.GetAsync(
            $"profiles/{profileId}");

        response.EnsureSuccessStatusCode();

        return (await response.Content
            .ReadFromJsonAsync<ExternalProfile>())!;
    }
}
```

## Kết quả code review tham khảo

### 1. Dùng `.Result` trên Task async trong request path

**Problem:** Request thread bị block trong khi external I/O đang chờ.  
**Why it happens:** `.Result` chuyển một operation async thành synchronous wait.  
**Production impact:** Dưới tải cao, nhiều worker thread cùng bị giữ; ThreadPool phải bổ sung thread, queue request tăng và tail latency có thể tăng rất mạnh.  
**Severity:** Critical  
**Recommended fix:** Dùng `await GetUserProfileAsync(...)` và giữ async end-to-end.

### 2. Không truyền request cancellation tới external HTTP call

**Problem:** Client disconnect hoặc request timeout không hủy downstream request.  
**Why it happens:** `GetUserProfileAsync` không nhận `CancellationToken`.  
**Production impact:** Công việc vô ích tiếp tục tiêu thụ connection, memory và downstream capacity sau khi caller không còn chờ kết quả.  
**Severity:** High  
**Recommended fix:** Truyền `cancellationToken` qua toàn bộ call chain và tới `HttpClient.SendAsync/GetAsync` cũng như deserialization.

### 3. Không dispose `HttpResponseMessage`

**Problem:** Response object không được dispose có chủ đích sau khi đọc xong.  
**Why it happens:** `response` chỉ là local variable không nằm trong `using`/`await using` pattern phù hợp.  
**Production impact:** Resource gắn với response có thể được giữ lâu hơn cần thiết; dưới tải cao làm pressure tăng và khó dự đoán lifetime.  
**Severity:** High  
**Recommended fix:** Dùng `using var response = await ...` sau khi nhận response.

### 4. Không có timeout budget rõ ràng cho downstream

**Problem:** Endpoint phụ thuộc external service nhưng code không biểu diễn timeout budget theo request hoặc operation.  
**Why it happens:** Chỉ dựa vào cấu hình mặc định của HttpClient/pipeline.  
**Production impact:** Khi downstream chậm, request có thể chiếm tài nguyên lâu, làm queue tăng và gây cascading latency.  
**Severity:** High  
**Recommended fix:** Thiết kế timeout hợp lý theo SLA, phân biệt request cancellation và downstream timeout; dùng policy/handler tập trung khi phù hợp.

### 5. `EnsureSuccessStatusCode()` không có error classification

**Problem:** Mọi non-success status đều biến thành exception chung ở layer này.  
**Why it happens:** Không phân biệt 404, 429, 5xx hoặc domain-specific failure.  
**Production impact:** Caller có thể nhận 500 không cần thiết; retry và alerting khó phân loại.  
**Severity:** Medium  
**Recommended fix:** Map status theo semantics: not found, throttling, transient downstream failure, permanent validation error.

### 6. Không có observability đủ để chứng minh root cause

**Problem:** Log chỉ báo đã load summary, không có timing theo DB/HTTP, queued request, downstream outcome.  
**Why it happens:** Không instrument critical dependencies riêng biệt.  
**Production impact:** Dễ nhầm ThreadPool starvation với CPU, database hoặc downstream slowness.  
**Severity:** Medium  
**Recommended fix:** Trace dependency spans, metric request duration, active requests, downstream latency/error rate, ThreadPool queue length/thread count và timeout/cancellation rate.

### 7. Có thể tạo retry amplification ở tầng trên

**Problem:** Khi endpoint timeout vì starvation, client/gateway có thể retry trong khi request cũ hoặc downstream call vẫn đang chạy.  
**Why it happens:** Cancellation không lan truyền và hệ thống không kiểm soát retry budget.  
**Production impact:** Load tăng đúng lúc hệ thống đang yếu, khiến tail latency xấu hơn.  
**Severity:** Medium  
**Recommended fix:** Propagate cancellation, giới hạn retry, chỉ retry lỗi transient và dùng backoff/jitter ở đúng layer.

### 8. Null-forgiving sau deserialization che khuất contract failure

**Problem:** `ReadFromJsonAsync<ExternalProfile>()!` giả định body luôn deserialize thành object hợp lệ.  
**Why it happens:** Null result hoặc schema mismatch bị bỏ qua ở compile time.  
**Production impact:** Có thể ném `NullReferenceException` ở đoạn sau, làm lỗi khó phân loại.  
**Severity:** Medium  
**Recommended fix:** Validate result và trả lỗi downstream contract rõ ràng.

```csharp
public sealed class UserSummaryService
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<UserSummaryService> _logger;

    public UserSummaryService(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<UserSummaryService> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<UserSummaryDto?> GetAsync(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var user = await _db.Users
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == userId,
                cancellationToken);

        if (user is null)
            return null;

        var profile = await GetUserProfileAsync(
            user.ExternalProfileId,
            cancellationToken);

        _logger.LogInformation(
            "Loaded summary for user {UserId}",
            userId);

        return new UserSummaryDto(
            user.Id,
            user.DisplayName,
            profile.Department,
            profile.Office);
    }

    private async Task<ExternalProfile> GetUserProfileAsync(
        string profileId,
        CancellationToken cancellationToken)
    {
        using var response = await _httpClient.GetAsync(
            $"profiles/{Uri.EscapeDataString(profileId)}",
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            throw new ExternalProfileNotFoundException(profileId);

        response.EnsureSuccessStatusCode();

        var profile = await response.Content
            .ReadFromJsonAsync<ExternalProfile>(
                cancellationToken: cancellationToken);

        return profile
            ?? throw new InvalidDataException(
                "Profile service returned an empty or invalid response.");
    }
}
```

## Trade-offs

- Async end-to-end không làm external API nhanh hơn, nhưng tránh giữ worker thread trong lúc chờ I/O và giúp server phục vụ concurrency hiệu quả hơn.
- Cancellation làm giảm wasted work nhưng cần xác định rõ operation nào an toàn để hủy và cách map `OperationCanceledException`.
- Timeout quá ngắn có thể tạo false failure; timeout quá dài làm giữ capacity. Nên đặt dựa trên end-to-end latency budget và downstream SLA.
- Retry có thể hữu ích cho lỗi transient, nhưng retry phải có giới hạn và không được biến downstream outage thành retry storm.

## Cách kiểm thử

1. **Load test:** So sánh throughput/p95/p99 giữa bản dùng `.Result` và bản `await` khi downstream latency cố định 300–500 ms.
2. **Cancellation test:** Client abort request; verify downstream call nhận cancellation và activity kết thúc sớm.
3. **Failure-path test:** Downstream trả 404, 429, 500 và body invalid; verify mapping đúng semantics.
4. **Resource test:** Chạy concurrency cao lâu đủ để quan sát connection usage, ThreadPool queue và memory không tăng bất thường.
5. **Timeout test:** Downstream treo/chậm; verify timeout budget và retry policy không khuếch đại tải.

## Quan sát trong production

- Metrics: request duration p50/p95/p99, active requests, ThreadPool thread count, queue length, completed work item rate, downstream latency/error rate, cancellation/timeout count.
- Traces: span riêng cho DB query và HTTP dependency, correlation xuyên suốt request.
- Logs: user id nội bộ phù hợp policy, downstream status class, elapsed time, cancellation reason; không log token hoặc full sensitive payload.
- Alert: tăng đồng thời ở request queue, ThreadPool queue và p99 trong khi CPU không tương ứng là tín hiệu đáng điều tra.

# Code Review Challenge 2 — Global exception middleware biến cancellation, validation và concurrency conflict thành `500` rồi trả stack trace ra client

## Bối cảnh

Một ASP.NET Core API dùng middleware chung để “đảm bảo mọi exception đều trả JSON”. Sau vài tháng, production xuất hiện các triệu chứng:

- dashboard báo tỷ lệ `500` cao hơn nhiều so với số incident thực tế,
- user bấm cancel download nhưng hệ thống vẫn ghi một error log cấp `Error`,
- stale update từ optimistic concurrency bị báo thành internal server error,
- validation exception do request sai cũng thành `500`,
- response lỗi đôi lúc chứa connection string fragment, SQL text hoặc internal class name,
- alerting bị nhiễu vì cancellation và lỗi client được tính như server failure,
- một số response đã bắt đầu gửi body trước khi exception xảy ra.

Security yêu cầu không được trả stack trace hoặc internal exception details cho client production. SRE muốn error metrics phản ánh đúng loại lỗi để không đánh đồng 4xx, cancellation và 5xx.

## Đoạn code cần review

```csharp
public sealed class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionMiddleware> _logger;

    public GlobalExceptionMiddleware(
        RequestDelegate next,
        ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Unhandled exception for {Method} {Path}",
                context.Request.Method,
                context.Request.Path);

            context.Response.StatusCode = 500;
            context.Response.ContentType = "application/json";

            await context.Response.WriteAsJsonAsync(new
            {
                error = ex.Message,
                type = ex.GetType().FullName,
                stackTrace = ex.StackTrace,
                inner = ex.InnerException?.Message,
                traceId = context.TraceIdentifier
            });
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Trả stack trace và exception details cho client

**Problem:** Response chứa `Message`, type đầy đủ, stack trace và inner exception.  
**Why it happens:** Internal diagnostic data bị dùng trực tiếp làm public error payload.  
**Production impact:** Có thể lộ implementation details, SQL/provider messages, đường dẫn file, host/service name hoặc dữ liệu nhạy cảm khác.  
**Severity:** Critical  
**Recommended fix:** Trả error contract công khai tối thiểu như code/title/traceId; chi tiết exception chỉ lưu server-side theo quyền truy cập phù hợp.

### 2. Mọi exception đều bị map thành `500`

**Problem:** Validation, not-found, conflict, cancellation và server bug đều thành cùng status code.  
**Why it happens:** Middleware không classification exception.  
**Production impact:** Client khó xử lý đúng; retry sai; SRE metrics/alerts phóng đại server failure; API semantics trở nên không đáng tin cậy.  
**Severity:** High  
**Recommended fix:** Có mapping rõ cho expected exception hoặc ưu tiên xử lý expected failure bằng result/typed outcome ở application layer.

### 3. Cancellation bị log như lỗi server

**Problem:** Request aborted hoặc operation canceled vẫn `LogError`.  
**Why it happens:** `OperationCanceledException` bị catch bởi `Exception`.  
**Production impact:** Alert noise, error rate sai và che khuất incident thật.  
**Severity:** High  
**Recommended fix:** Phân biệt cancellation do `RequestAborted` với unexpected timeout/failure; không xem client cancellation là internal error.

### 4. Không xử lý trường hợp response đã bắt đầu

**Problem:** Middleware cố đổi status/header và ghi JSON dù downstream có thể đã flush response.  
**Why it happens:** Không kiểm tra `Response.HasStarted`.  
**Production impact:** Có thể phát sinh exception thứ hai, response bị trộn/corrupt hoặc client nhận partial payload không đúng format.  
**Severity:** High  
**Recommended fix:** Nếu response đã bắt đầu, log có context rồi rethrow/abort theo pipeline strategy; không cố rewrite response.

### 5. `DbUpdateConcurrencyException` bị biến thành generic 500

**Problem:** Optimistic concurrency conflict thường là một state conflict có thể xử lý, không nhất thiết là server bug.  
**Why it happens:** Không có mapping cho concurrency semantics.  
**Production impact:** Client có thể retry mù hoặc hiển thị “server lỗi” thay vì yêu cầu reload/merge.  
**Severity:** Medium  
**Recommended fix:** Map theo contract đã thống nhất, ví dụ conflict/conditional request semantics tùy API design.

### 6. Validation exception cũng bị biến thành 500

**Problem:** Request không hợp lệ có thể bị tính như lỗi server.  
**Why it happens:** Validation được throw nhưng middleware không phân loại.  
**Production impact:** Client nhận sai status, monitoring sai và retry không cần thiết.  
**Severity:** Medium  
**Recommended fix:** Trả problem response dạng 4xx phù hợp, ưu tiên validate ở boundary trước khi vào domain flow.

### 7. Logging mọi lỗi cùng severity

**Problem:** Expected business/HTTP failures và unexpected exception đều `LogError`.  
**Why it happens:** Không có severity policy theo classification.  
**Production impact:** Log volume lớn, alert fatigue và khó tìm lỗi thật sự quan trọng.  
**Severity:** Medium  
**Recommended fix:** Dùng severity theo loại failure; unexpected 5xx ở Error, expected 4xx thường thấp hơn hoặc chỉ metric/structured event tùy nhu cầu.

### 8. Error contract phụ thuộc trực tiếp exception type

**Problem:** Client có thể vô tình phụ thuộc tên CLR exception/class nội bộ.  
**Why it happens:** `ex.GetType().FullName` được expose.  
**Production impact:** Refactor server có thể làm thay đổi public contract; coupling nội bộ bị rò ra ngoài.  
**Severity:** Medium  
**Recommended fix:** Dùng stable application error codes độc lập với exception class.

### 9. Không có correlation chuẩn giữa public error và telemetry

**Problem:** Có `TraceIdentifier` nhưng không chắc gắn với distributed trace/span hoặc structured error event.  
**Why it happens:** Correlation chỉ nằm trong response mà không có error classification telemetry rõ.  
**Production impact:** User gửi trace id nhưng team vẫn khó tìm đúng dependency/span/root cause.  
**Severity:** Medium  
**Recommended fix:** Trả correlation id/trace id ổn định và log cùng id, error code, endpoint, status, exception type server-side.

## Phiên bản code đề xuất

```csharp
public sealed class GlobalExceptionMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<GlobalExceptionMiddleware> _logger;

    public GlobalExceptionMiddleware(
        RequestDelegate next,
        ILogger<GlobalExceptionMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        try
        {
            await _next(context);
        }
        catch (OperationCanceledException)
            when (context.RequestAborted.IsCancellationRequested)
        {
            _logger.LogInformation(
                "Request canceled by client for {Method} {Path}",
                context.Request.Method,
                context.Request.Path);
        }
        catch (ValidationException ex)
        {
            await WriteProblemAsync(
                context,
                StatusCodes.Status400BadRequest,
                "validation_failed",
                "Request validation failed.",
                ex);
        }
        catch (DbUpdateConcurrencyException ex)
        {
            await WriteProblemAsync(
                context,
                StatusCodes.Status409Conflict,
                "concurrency_conflict",
                "The resource was modified by another operation.",
                ex);
        }
        catch (Exception ex)
        {
            if (context.Response.HasStarted)
            {
                _logger.LogError(
                    ex,
                    "Unhandled exception after response started for {Method} {Path}",
                    context.Request.Method,
                    context.Request.Path);
                throw;
            }

            await WriteProblemAsync(
                context,
                StatusCodes.Status500InternalServerError,
                "internal_error",
                "An unexpected error occurred.",
                ex);
        }
    }

    private async Task WriteProblemAsync(
        HttpContext context,
        int statusCode,
        string errorCode,
        string publicMessage,
        Exception exception)
    {
        if (context.Response.HasStarted)
            throw exception;

        var level = statusCode >= 500 ? LogLevel.Error : LogLevel.Warning;

        _logger.Log(
            level,
            exception,
            "Request failed with {ErrorCode} and status {StatusCode} for {Method} {Path}",
            errorCode,
            statusCode,
            context.Request.Method,
            context.Request.Path);

        context.Response.StatusCode = statusCode;
        context.Response.ContentType = "application/problem+json";

        await context.Response.WriteAsJsonAsync(new
        {
            status = statusCode,
            code = errorCode,
            title = publicMessage,
            traceId = Activity.Current?.TraceId.ToString()
                      ?? context.TraceIdentifier
        });
    }
}
```

> Đây là một reference design. Trong production, expected business failures có thể được biểu diễn bằng typed result thay vì exception; middleware nên chủ yếu là safety net cho lỗi không được xử lý ở layer thấp hơn.

## Trade-offs

- Centralized middleware giúp response nhất quán nhưng nếu classification quá nhiều trong một nơi sẽ biến middleware thành dependency vào toàn bộ domain.
- Typed result làm flow expected errors rõ hơn, nhưng tăng boilerplate và cần convention thống nhất trong team.
- Logging 4xx ở Warning có thể vẫn quá noisy với endpoint public; severity nên dựa vào security/operational policy thay vì áp dụng một rule tuyệt đối.
- `409 Conflict` cho optimistic concurrency là lựa chọn phổ biến, nhưng nếu API dùng conditional requests/ETag thì `412 Precondition Failed` có thể phù hợp hơn.

## Cách kiểm thử

1. **Security test:** Exception có chứa connection string/SQL/internal path; verify response không lộ chi tiết đó.
2. **Cancellation test:** Client abort request; verify không tăng server-error metric và không ghi error log không cần thiết.
3. **Concurrency integration test:** Trigger stale update; verify response conflict contract đúng và không thành 500.
4. **Response-started test:** Downstream đã flush partial response rồi ném exception; verify middleware không cố rewrite JSON response.
5. **Classification test:** Validation, unauthorized/not-found theo layer tương ứng và unexpected exception tạo đúng status/error code/log severity.

## Quan sát trong production

- Metrics: request count theo status class, unexpected 5xx rate, validation failure, concurrency conflict, cancellation và timeout tách biệt.
- Logs: stable error code, trace id, endpoint, actor/tenant metadata khi phù hợp; exception detail chỉ server-side.
- Traces: mark span status/error chỉ cho failure phù hợp; gắn dependency exceptions với cùng trace.
- Alert: ưu tiên unexpected 5xx và error budget, không alert trực tiếp theo tổng exception count chưa phân loại.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn dùng exception, khi nào dùng `Result<T>` hoặc discriminated outcome cho expected business failure?
2. Nếu API đã dùng `ProblemDetails`, bạn sẽ tổ chức mapping lỗi và extension fields như thế nào để contract ổn định?
3. Nếu security team muốn ẩn cả việc resource có tồn tại hay không trong một số authorization case, error mapping sẽ thay đổi ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async I/O chỉ phát huy lợi ích khi call chain không block bằng `.Result`/`.Wait()` trong request path.
- ThreadPool starvation có thể làm tail latency tăng mạnh ngay cả khi CPU chưa đạt 100%.
- Cancellation, timeout và retry phải được thiết kế xuyên suốt dependency chain để tránh wasted work và load amplification.
- Error handling tốt phải phân loại expected failures, cancellation và unexpected server bugs thay vì biến tất cả thành `500`.
- Public error response không nên chứa stack trace, internal exception type hoặc dữ liệu nhạy cảm; chi tiết kỹ thuật thuộc server-side telemetry.

## Mẫu tư duy cần nhớ

- Giữ async end-to-end; đừng block thread để chờ I/O.
- Khi latency tăng, đo queueing và ThreadPool chứ đừng chỉ nhìn CPU.
- Propagate cancellation và đặt timeout theo end-to-end budget.
- Phân loại lỗi trước khi quyết định status code, retry và log severity.
- Tách public error contract khỏi internal diagnostic details.
