# Code Review Challenge 1 — EF Core optimistic concurrency bị biến thành “last write wins” âm thầm

**Chủ đề:** C#/.NET, EF Core, optimistic concurrency, HTTP API, correctness, auditability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một approval API cho phép nhiều managers chỉnh sửa cùng một `ApprovalRequest`. UI gửi toàn bộ form khi Save. Entity có SQL Server `rowversion` để phát hiện concurrent update, nhưng team gần đây thêm retry logic sau khi users phàn nàn về lỗi conflict.

Sau rollout, conflict errors giảm gần về 0 nhưng audit cho thấy đôi khi comment hoặc status của manager A biến mất sau khi manager B lưu. API trả `200 OK` cho cả hai. Team cho rằng “retry đã giải quyết concurrency”.

Business yêu cầu không được âm thầm mất thay đổi. Với một số field có thể merge, nhưng `Status` cần user/business rule quyết định khi có conflict.

## Đoạn code cần review

```csharp
public sealed record UpdateApprovalRequest(
    string Status,
    string Comment,
    byte[] RowVersion);

[ApiController]
[Route("api/approvals")]
public sealed class ApprovalsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ApprovalsController> _logger;

    public ApprovalsController(
        AppDbContext db,
        ILogger<ApprovalsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id,
        UpdateApprovalRequest request,
        CancellationToken cancellationToken)
    {
        for (var attempt = 1; attempt <= 3; attempt++)
        {
            var entity = await _db.ApprovalRequests
                .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

            if (entity is null)
                return NotFound();

            entity.Status = request.Status;
            entity.Comment = request.Comment;
            entity.RowVersion = request.RowVersion;

            try
            {
                await _db.SaveChangesAsync(cancellationToken);
                return Ok(entity);
            }
            catch (DbUpdateConcurrencyException ex)
            {
                _logger.LogWarning(
                    ex,
                    "Concurrency conflict for approval {ApprovalId}, attempt {Attempt}",
                    id,
                    attempt);

                foreach (var entry in ex.Entries)
                {
                    await entry.ReloadAsync(cancellationToken);
                    entry.CurrentValues.SetValues(request);
                }
            }
        }

        return StatusCode(500, "Could not save approval");
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong concurrency handling.
2. Giải thích vì sao retry hiện tại có thể biến conflict thành lost update.
3. Phân tích HTTP/API semantics và business impact.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất conflict contract và corrected implementation/design.
6. Giải thích cách test deterministic concurrent updates.
7. Nêu telemetry production cần có.

## Câu hỏi gợi mở

1. `rowversion` đại diện version của client hay version hiện tại của database tại thời điểm retry?
2. Sau `ReloadAsync`, việc apply lại toàn bộ request có còn bảo toàn ý nghĩa optimistic concurrency không?
3. `Status` và `Comment` có cùng merge semantics không?
4. Conflict có nên trở thành 500 sau ba lần thử không?
5. API response có nên expose EF entity trực tiếp không?

### Gợi ý 2

Optimistic concurrency không tự quyết định merge policy. Detection và conflict resolution là hai bước khác nhau.

## Kết quả code review tham khảo

### Critical — Retry tự động có thể ghi đè thay đổi hợp lệ của user khác

**Vấn đề:** sau conflict, code reload database state rồi apply lại toàn bộ request và Save lại.  
**Tại sao xảy ra:** concurrency token mới sau reload làm lần Save kế tiếp có thể thành công dù request được tạo từ state cũ.  
**Ảnh hưởng production:** lost update bị biến thành `200 OK`; thay đổi của manager khác có thể biến mất mà không ai được báo.  
**Cách sửa:** coi conflict là business/API outcome. Trả current server state + current version hoặc `409 Conflict`/`412 Precondition Failed` theo contract đã chọn; chỉ merge tự động những field có merge rule rõ ràng.

### High — Gán `RowVersion` như một property thông thường làm semantics khó kiểm soát

**Vấn đề:** request token được copy vào entity thay vì cấu hình original concurrency value rõ ràng.  
**Tại sao xảy ra:** optimistic concurrency cần so sánh version client đã đọc với version database khi update.  
**Ảnh hưởng production:** code review khó chứng minh generated UPDATE predicate đúng ý định; refactor/mapping có thể phá concurrency contract.  
**Cách sửa:** cấu hình `RowVersion` là concurrency token và set `OriginalValue` từ client token khi dùng detached/update pattern; hoặc load entity rồi xác minh token trước khi mutate.

### High — Không có field-specific merge policy

**Vấn đề:** `Status` và `Comment` đều được overwrite cùng cách.  
**Tại sao xảy ra:** transport DTO được coi như authoritative aggregate state.  
**Ảnh hưởng production:** transition quan trọng có thể bị đảo/ngầm mất; audit không phản ánh user intent.  
**Cách sửa:** định nghĩa invariant/transition rules. Có thể merge comment theo business semantics nếu phù hợp, nhưng status conflict cần explicit resolution.

### Medium — Retry concurrency không có giá trị nếu input không được refresh

**Vấn đề:** cùng một stale user intent được replay tối đa ba lần.  
**Tại sao xảy ra:** retry phù hợp hơn với transient infrastructure failures; logical concurrency conflict cần quyết định dựa trên new state.  
**Ảnh hưởng production:** tăng DB work và che conflict rate.  
**Cách sửa:** không blind-retry logical conflict; return conflict payload để caller refresh/reconcile hoặc thực hiện server-side merge có rule deterministic.

### Medium — Conflict cuối cùng trả 500 không mô tả đúng lỗi

**Vấn đề:** API coi unresolved concurrency như server malfunction.  
**Tại sao xảy ra:** transport semantics không phân biệt conflict với unexpected failure.  
**Ảnh hưởng production:** client retry sai, monitoring báo lỗi hệ thống, UX không hướng dẫn refresh/reconcile.  
**Cách sửa:** dùng documented conflict response, ví dụ ProblemDetails kèm current version/state cần thiết.

### Medium — Trả EF entity trực tiếp

**Vấn đề:** persistence model trở thành response contract.  
**Tại sao xảy ra:** controller trả `entity`.  
**Ảnh hưởng production:** coupling, accidental field exposure và khó kiểm soát concurrency token representation.  
**Cách sửa:** map sang response DTO chứa fields cần thiết và version token theo contract.

### Low — Telemetry chỉ đếm retry, không đo conflict semantics

**Vấn đề:** log không cho biết client version/current version, outcome hay field conflict.  
**Tại sao xảy ra:** observability tập trung exception thay vì business concurrency.  
**Ảnh hưởng production:** “conflict errors giảm” có thể chỉ vì conflict bị overwrite.  
**Cách sửa:** metric conflict count/rate, resolved-vs-returned conflict, endpoint, aggregate type và correlation; tránh log sensitive comment content.

## Phiên bản đề xuất

Ví dụ dưới đây dùng explicit token comparison và trả conflict thay vì blind retry. Cấu hình entity vẫn phải đánh dấu `RowVersion` là concurrency token/rowversion.

```csharp
public sealed record UpdateApprovalRequest(
    string Status,
    string Comment,
    byte[] RowVersion);

public sealed record ApprovalResponse(
    Guid Id,
    string Status,
    string Comment,
    byte[] RowVersion);

[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(
    Guid id,
    UpdateApprovalRequest request,
    CancellationToken ct)
{
    var entity = await _db.ApprovalRequests
        .SingleOrDefaultAsync(x => x.Id == id, ct);

    if (entity is null)
        return NotFound();

    if (!entity.RowVersion.AsSpan().SequenceEqual(request.RowVersion))
    {
        return Conflict(new ProblemDetails
        {
            Title = "Approval was modified by another user",
            Detail = "Refresh the current state and reconcile your changes.",
            Status = StatusCodes.Status409Conflict
        });
    }

    entity.Status = request.Status;
    entity.Comment = request.Comment;

    try
    {
        await _db.SaveChangesAsync(ct);
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict(new ProblemDetails
        {
            Title = "Approval was modified concurrently",
            Detail = "Refresh the current state and reconcile your changes.",
            Status = StatusCodes.Status409Conflict
        });
    }

    return Ok(new ApprovalResponse(
        entity.Id,
        entity.Status,
        entity.Comment,
        entity.RowVersion));
}
```

## Giải thích thiết kế sau khi sửa

Pre-check cải thiện UX cho token đã stale trước khi mutation, nhưng không thay thế database concurrency predicate vì race vẫn có thể xảy ra giữa check và SaveChanges. Database token vẫn là correctness boundary cuối cùng.

Nếu business muốn merge comments, merge phải là explicit domain rule dựa trên current state và user intent; không được dùng generic `SetValues(request)` như conflict resolver. Nếu HTTP contract sử dụng ETag/`If-Match`, cùng nguyên tắc có thể được biểu diễn bằng conditional request thay vì token trong body.

## Trade-offs

Trả conflict chuyển reconciliation về client/user và tăng UX complexity, nhưng bảo vệ dữ liệu khỏi silent overwrite. Server-side merge có UX tốt hơn cho field độc lập nhưng tăng domain complexity và cần deterministic rules. ETag phù hợp HTTP semantics nhưng yêu cầu client contract và gateway/cache behavior được test đầy đủ.

## Cách kiểm thử

1. **Concurrency integration test:** hai DbContexts đọc cùng version; A save trước, B save sau; B phải nhận conflict và không overwrite A.
2. **API test:** stale token trả documented conflict response, không phải 500/200.
3. **Domain test:** status transition conflict không auto-merge; field được phép merge phải theo rule rõ ràng.
4. **Race test:** concurrent saves qua barrier để ép interleaving và xác minh database token là final guard.
5. **Telemetry test:** conflict metric tăng đúng nhưng không log comment/sensitive content.

## Quan sát trong production

Theo dõi concurrency-conflict rate theo endpoint/aggregate, tỷ lệ user retry sau refresh, latency và failed-save count. Correlate request trace với aggregate ID ở mức phù hợp privacy. Alert khi conflict tăng đột biến sau UI/API release vì có thể báo hiệu stale client state hoặc workflow contention.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào `412 Precondition Failed` với `If-Match` hợp lý hơn `409 Conflict`?
2. Nếu comment có thể merge nhưng status không thể, bạn thiết kế command/API thế nào để tránh full-resource overwrite?
3. Nếu application chạy nhiều instances, optimistic concurrency behavior có thay đổi không?

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì shared account và shared test data

**Chủ đề:** Playwright, E2E testing, CI parallelism, test isolation, retries, diagnostics  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một team chạy Playwright tests cho approval portal trên CI. Local gần như luôn pass. CI dùng nhiều workers để giảm runtime và bật retries. Gần đây suite có 8–15% flaky runs: test đôi khi thấy status từ test khác, user bị logout bất ngờ hoặc retry lần hai lại pass.

Pipeline dùng cùng staging environment cho nhiều branches. Tất cả tests đăng nhập bằng một manager account và thao tác một approval record cố định. Team đề xuất tăng retries từ 2 lên 5 để pipeline xanh hơn.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const managerEmail = 'manager@test.local';
const approvalId = '00000000-0000-0000-0000-000000000123';

let token: string;

test.beforeAll(async ({ request }) => {
  const response = await request.post('/api/test/login', {
    data: {
      email: managerEmail,
      password: 'Password123!'
    }
  });

  const body = await response.json();
  token = body.accessToken;
});

test('manager can approve request', async ({ page }) => {
  await page.goto(`/approvals/${approvalId}?token=${token}`);

  await page.getByRole('button', { name: 'Approve' }).click();

  await page.waitForTimeout(1000);
  await expect(page.getByText('Approved')).toBeVisible();
});

test('manager can reject request', async ({ page }) => {
  await page.goto(`/approvals/${approvalId}?token=${token}`);

  await page.getByRole('button', { name: 'Reject' }).click();

  await page.waitForTimeout(1000);
  await expect(page.getByText('Rejected')).toBeVisible();
});

test.afterAll(async ({ request }) => {
  await request.post(`/api/test/approvals/${approvalId}/reset`);
});
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và isolation problems.
2. Giải thích vì sao parallel workers/retries làm flakiness khó hiểu hơn.
3. Xác định security/test-environment concerns.
4. Ưu tiên root causes trước việc tăng retry.
5. Đề xuất test-data/authentication design ổn định hơn.
6. Giải thích E2E/integration tests cần có và cách tái hiện race.
7. Nêu artifacts/telemetry cần thu khi CI fail.

## Câu hỏi gợi mở

1. Hai tests có thể mutate cùng approval cùng lúc không?
2. Retry của một test chạy trong state nào nếu attempt trước đã mutate server?
3. `afterAll` có đảm bảo cleanup nếu worker/process bị kill không?
4. Token trong URL có thể xuất hiện ở đâu ngoài browser memory?
5. Một staging environment dùng chung nhiều branches ảnh hưởng determinism thế nào?

### Gợi ý 1

### Gợi ý 2

Retry chỉ hữu ích sau khi test được thiết kế replay-safe; nếu attempt trước để lại state, retry có thể che lỗi hoặc tạo lỗi mới.

## Kết quả code review tham khảo

### Critical — Hai tests mutate cùng một approval record

**Vấn đề:** approve và reject dùng cùng `approvalId`.  
**Tại sao xảy ra:** suite phụ thuộc shared mutable fixture trong khi CI cho phép parallel execution.  
**Ảnh hưởng production/CI:** outcome phụ thuộc scheduling; test có thể quan sát state do test khác tạo.  
**Cách sửa:** tạo unique data per test/worker hoặc provision isolated namespace/tenant; mỗi test phải sở hữu lifecycle dữ liệu của nó.

### High — Shared authentication identity tạo cross-test coupling

**Vấn đề:** tất cả tests dùng một manager account/token.  
**Tại sao xảy ra:** session/revocation/rate limits/account state có thể được chia sẻ giữa tests/pipelines.  
**Ảnh hưởng production/CI:** logout/session changes hoặc account-level state làm tests ảnh hưởng lẫn nhau.  
**Cách sửa:** dùng worker-scoped hoặc test-scoped accounts/context theo requirement; storage state có thể tái sử dụng có kiểm soát nếu identity không mutate.

### High — Retry không replay-safe

**Vấn đề:** attempt đầu có thể đã approve/reject server nhưng fail trước assertion; retry bắt đầu trên mutated state.  
**Tại sao xảy ra:** test không tạo/reset fixture riêng cho mỗi attempt.  
**Ảnh hưởng production/CI:** retry pass che lỗi timing hoặc retry fail vì state đã thay đổi.  
**Cách sửa:** setup fixture deterministic cho từng test attempt; cleanup là defense, không phải prerequisite để test khác chạy đúng.

### High — Token trong query string

**Vấn đề:** access token được đặt vào URL.  
**Tại sao xảy ra:** test shortcut bypass authentication flow/storage.  
**Ảnh hưởng production/CI:** URL có thể xuất hiện trong logs, traces, screenshots, history hoặc referrer behavior; test cũng không đại diện auth contract thật.  
**Cách sửa:** authenticate qua supported API/session mechanism và inject storage state/cookie/header theo application design; tránh secrets trong URL/artifacts.

### Medium — Fixed timeout thay cho observable condition

**Vấn đề:** `waitForTimeout(1000)` giả định timing.  
**Tại sao xảy ra:** CI latency biến động.  
**Ảnh hưởng production/CI:** test vừa chậm vừa flaky; 1 giây có lúc quá dài, có lúc chưa đủ.  
**Cách sửa:** chờ UI/network/state condition có ý nghĩa; Playwright assertions có auto-waiting nên tận dụng locator/assertion semantics.

### Medium — `afterAll` cleanup không đủ để tạo isolation

**Vấn đề:** toàn suite chỉ reset một record sau cùng.  
**Tại sao xảy ra:** cleanup được dùng để bù cho shared fixture.  
**Ảnh hưởng production/CI:** crash/timeout/cancel có thể bỏ cleanup; pipeline khác có thể đọc dirty state trước cleanup.  
**Cách sửa:** provision unique fixture trước mỗi test/attempt; teardown chỉ dọn resource của chính fixture đó.

### Medium — Shared staging giữa branches làm environment nondeterministic

**Vấn đề:** application version/config/data có thể thay đổi trong lúc suite chạy.  
**Tại sao xảy ra:** nhiều deployments/tests cùng target một environment.  
**Ảnh hưởng production/CI:** failure không còn map rõ vào commit under test.  
**Cách sửa:** nếu khả thi dùng ephemeral environment/namespace; nếu không, serialize deployments, tag environment ownership hoặc ít nhất isolate test tenant/data và record deployed commit SHA.

### Low — Failure artifacts chưa đủ để phân tích flaky behavior

**Vấn đề:** chỉ retain trace khi failure, chưa đảm bảo screenshot/video/network/server correlation phù hợp.  
**Tại sao xảy ra:** diagnostics chưa được thiết kế như test feature.  
**Ảnh hưởng production/CI:** retry pass làm mất context của attempt lỗi hoặc khó correlate backend.  
**Cách sửa:** retain trace theo retry policy, capture screenshot/video khi cần, log test/fixture IDs và propagate correlation ID sang backend.

## Phiên bản đề xuất

Ví dụ này minh họa fixture riêng cho từng test và tránh fixed sleep. Endpoint `/api/test/approvals` chỉ nên tồn tại trong controlled test environment với authorization phù hợp.

import { test, expect, request as playwrightRequest } from '@playwright/test';

async function createApproval(api: any) {
  const response = await api.post('/api/test/approvals', {
    data: { status: 'Pending' }
  });
  expect(response.ok()).toBeTruthy();
  return await response.json() as { id: string };

test.beforeEach(async ({ page }) => {

Một production-like suite tốt hơn có thể provision identity qua worker fixture và dùng Playwright `storageState`, nhưng exact implementation phụ thuộc authentication architecture. Test-only login/provisioning endpoints phải bị khóa khỏi production và không dùng hard-coded credentials trong source.

## Giải thích thiết kế sau khi sửa

Mỗi test tạo approval riêng nên parallel scheduling không thay đổi correctness. Assertion chờ observable UI state thay vì ngủ cố định. Authentication setup phải mô phỏng trust boundary đủ gần production nhưng vẫn deterministic; worker-scoped storage state là lựa chọn thường hữu ích khi account state không bị mutate.

Retries có thể giữ ở mức nhỏ để chống infrastructure noise, nhưng retry không được dùng làm acceptance criterion cho race trong chính test design. Flaky test cần được triage bằng artifacts của failed attempt.

## Trade-offs

Unique fixture provisioning tăng runtime và cần test-data APIs/factories. Ephemeral environment tăng infrastructure cost. Worker-scoped accounts giảm provisioning nhưng vẫn có coupling nếu tests mutate account-level state. E2E suite nên giữ các flows high-value; nhiều business rules có thể kiểm tra nhanh và deterministic hơn bằng integration/API tests.

## Cách kiểm thử

1. **Parallel stress:** chạy suite nhiều lần với 6+ workers; unique fixture IDs không được cross-contaminate.
2. **Retry validation:** inject failure sau server mutation; retry phải tạo fresh fixture và không phụ thuộc attempt trước.
3. **CI isolation:** chạy hai pipeline/branches đồng thời và xác minh tenant/data namespace tách biệt.
4. **Security validation:** artifacts/logs không chứa access token/password; test-only endpoints unavailable trong production configuration.
5. **Failure diagnostics:** ép một backend 500 và xác minh trace/screenshot/correlation đủ để nối browser failure với server request.

## Quan sát trong production/CI

Lưu test name, retry index, worker ID, fixture/tenant ID, application commit SHA, environment version và correlation ID. Theo dõi flaky rate riêng với genuine product failures; không chỉ nhìn final pipeline pass rate. # Tổng kết hôm nay

## Kiến thức trọng tâm

Optimistic concurrency chỉ phát hiện competing writes; business/application vẫn phải quyết định conflict resolution. Blind retry có thể phá chính guarantee mà concurrency token cung cấp. Ở testing, parallelism và retry cũng chỉ an toàn khi mỗi execution có state ownership rõ ràng và replay-safe setup.

## Mẫu tư duy cần nhớ

- Detection không đồng nghĩa resolution: conflict cần explicit business policy.
- Retry chỉ an toàn khi operation/test attempt có thể replay mà không làm sai state.
- Shared mutable state + parallel execution là nguồn race cần loại bằng ownership/isolation.
- Correctness guard cuối cùng phải nằm ở boundary có thể chịu race, không chỉ ở pre-check.
- Diagnostics và test artifacts phải đủ để tái dựng failed execution, không chỉ báo pass/fail.
