# Code Review Challenge 1 — Checkout giữ transaction qua payment call và vẫn tạo booking trùng dưới concurrency

**Chủ đề:** C#, ASP.NET Core, EF Core, SQL Server, transactions, concurrency, external payment, idempotency, reliability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một ASP.NET Core API trên .NET 8 xử lý đặt chỗ cho một hệ thống event booking. SQL Server là source of truth. Mỗi seat chỉ được bán cho một booking thành công. Payment được xử lý qua một external provider.

Business yêu cầu:

- không được có hai booking thành công cho cùng một seat;
- client có thể retry request khi mất mạng mà không bị charge hai lần;
- payment provider đôi khi mất 2–8 giây hoặc timeout;
- application chạy nhiều instances sau load balancer;
- khi payment fail, seat không được giữ vô thời hạn;
- user cancellation phải dừng các bước còn có thể hủy;
- production cần truy vết được một booking từ HTTP request → SQL → payment provider.

Production bắt đầu xuất hiện:

- thỉnh thoảng hai user cùng nhận HTTP 200 cho cùng một seat trong peak traffic;
- SQL blocking tăng mạnh khi payment provider chậm;
- có trường hợp client retry sau timeout và provider ghi nhận hai payment attempts;
- request p99 tăng lên hàng chục giây dù SQL query riêng lẻ vẫn nhanh;
- team đề xuất tăng transaction timeout và dùng `Serializable` cho toàn bộ method.

Code hiện tại:

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/bookings")]
public sealed class BookingController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IPaymentClient _paymentClient;
    private readonly ILogger<BookingController> _logger;

    public BookingController(
        AppDbContext db,
        IPaymentClient paymentClient,
        ILogger<BookingController> logger)
    {
        _db = db;
        _paymentClient = paymentClient;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Create(CreateBookingRequest request)
    {
        await using var tx = await _db.Database.BeginTransactionAsync();

        var seat = await _db.Seats
            .SingleOrDefaultAsync(x => x.EventId == request.EventId
                                    && x.SeatNumber == request.SeatNumber);

        if (seat is null)
        {
            return NotFound();
        }

        var exists = await _db.Bookings.AnyAsync(x =>
            x.EventId == request.EventId &&
            x.SeatNumber == request.SeatNumber &&
            x.Status == BookingStatus.Confirmed);

        if (exists)
        {
            return Conflict("Seat already booked");
        }

        var payment = await _paymentClient.ChargeAsync(
            request.CardToken,
            request.Amount);

        if (!payment.Succeeded)
        {
            await tx.RollbackAsync();
            return BadRequest("Payment failed");
        }

        var booking = new Booking
        {
            Id = Guid.NewGuid(),
            EventId = request.EventId,
            SeatNumber = request.SeatNumber,
            UserId = User.GetUserId(),
            PaymentId = payment.PaymentId,
            Amount = request.Amount,
            Status = BookingStatus.Confirmed,
            CreatedAtUtc = DateTime.UtcNow
        };

        _db.Bookings.Add(booking);
        await _db.SaveChangesAsync();
        await tx.CommitAsync();

        _logger.LogInformation(
            "Booking {BookingId} confirmed with payment {PaymentId}",
            booking.Id,
            payment.PaymentId);

        return Ok(new { booking.Id });
    }
}
```

## Kết quả code review tham khảo

### Critical — Check-then-insert không enforce được seat uniqueness dưới concurrency

**Vấn đề:** `AnyAsync` kiểm tra booking hiện tại, sau đó insert ở một statement khác. Hai requests có thể cùng thấy `exists == false`.

**Tại sao xảy ra:** Application-level check không phải atomic với insert và không có database constraint thể hiện invariant “một active/confirmed booking cho một seat”.

**Ảnh hưởng production:** Hai requests có thể cùng charge payment và cùng tạo booking thành công cho một seat.

**Cách sửa:** Enforce invariant tại database boundary. Tùy model, dùng unique constraint/index phù hợp hoặc một atomic seat state transition/conditional update. Application vẫn có pre-check để UX tốt hơn, nhưng database constraint phải là authority cuối cùng.

### Critical — External payment nằm bên trong SQL transaction

**Vấn đề:** Transaction được mở trước khi gọi payment provider, một network call có thể mất nhiều giây.

**Tại sao xảy ra:** Code cố gắng tạo cảm giác “atomic” giữa SQL và HTTP bằng cách giữ DB transaction mở.

**Ảnh hưởng production:** Locks/transaction resources bị giữ lâu, blocking tăng, connection pool bị pressure, p99 tăng và deadlock probability có thể tăng. SQL transaction vẫn không rollback được side effect đã xảy ra ở payment provider.

**Cách sửa:** Không giữ SQL transaction qua external HTTP call. Thiết kế một workflow có state machine/idempotency/compensation, ví dụ `PendingPayment` → payment → `Confirmed` hoặc `PaymentFailed`, với transaction SQL ngắn ở từng state transition.

### Critical — Không có idempotency key cho logical booking/payment operation

**Vấn đề:** Client retry có thể gọi `ChargeAsync` lần nữa với cùng card token/amount nhưng không có stable operation key.

**Tại sao xảy ra:** Request identity và business-operation identity không được lưu/persist xuyên retries.

**Ảnh hưởng production:** Double charge hoặc nhiều payment attempts khi client timeout, reverse proxy retry hoặc process crash sau provider success.

**Cách sửa:** Client hoặc server tạo một stable idempotency key cho logical booking operation. Persist key với booking attempt và gửi cùng key tới provider nếu provider hỗ trợ idempotency. Unique constraint trên key giúp cùng retry trả lại kết quả của operation cũ.

### High — Có failure window “payment succeeded, database chưa commit”

**Vấn đề:** Provider có thể charge thành công rồi process crash, SQL fail hoặc commit fail.

**Tại sao xảy ra:** External HTTP side effect không thuộc SQL transaction.

**Ảnh hưởng production:** Tiền đã charge nhưng booking không tồn tại hoặc vẫn pending; client retry có thể charge tiếp.

**Cách sửa:** Modeling explicit states và reconciliation. Persist booking/payment attempt trước khi gọi provider; sau provider response chuyển trạng thái bằng optimistic/conditional update. Với timeout không biết outcome, query provider theo idempotency/reference trước khi retry. Có background reconciliation cho trạng thái ambiguous.

### High — `request.Amount` được client cung cấp và dùng trực tiếp để charge

**Vấn đề:** Amount là security/business-sensitive value nhưng code tin dữ liệu từ client.

**Tại sao xảy ra:** Price không được lấy lại từ authoritative event/seat/pricing data.

**Ảnh hưởng production:** Client có thể sửa request để charge sai số tiền nếu upstream validation không tồn tại ở nơi khác.

**Cách sửa:** Tính amount server-side từ authoritative pricing model; request chỉ gửi seat/product identity và optional quote/version token nếu business cần.

### High — Transaction early returns không có boundary/error mapping rõ

**Vấn đề:** Một số return xảy ra khi transaction đang mở; disposal có thể rollback nhưng behavior/telemetry không thể hiện rõ business outcome, và exception từ DB/payment chưa được map thành consistent API contract.

**Tại sao xảy ra:** Controller đang điều phối quá nhiều concerns và transaction lifecycle.

**Ảnh hưởng production:** Khó quan sát failure mode, dễ để exception biến thành generic 500, khó retry có chọn lọc.

**Cách sửa:** Di chuyển orchestration sang application service, dùng transaction scope ngắn và explicit state/result types; map các conflict/failure sang ProblemDetails hoặc API error contract ổn định.

### Medium — Không propagate `CancellationToken`

**Vấn đề:** EF Core và payment calls không nhận request cancellation token.

**Tại sao xảy ra:** Action không khai báo `CancellationToken` và dependencies không được truyền token.

**Ảnh hưởng production:** Client bỏ request nhưng SQL/HTTP work có thể tiếp tục, làm lãng phí capacity. Tuy nhiên cancellation sau khi side effect bắt đầu không được dùng như “rollback payment”.

**Cách sửa:** Propagate cancellation cho I/O còn có thể hủy; thiết kế payment operation idempotent/recoverable vì cancellation không đảm bảo provider chưa thực hiện side effect.

### Medium — Không có optimistic concurrency/state transition guard

**Vấn đề:** `seat` được load nhưng không dùng version/state condition để giành quyền đặt seat.

**Tại sao xảy ra:** Workflow dựa trên đọc trạng thái rồi hành động thay vì atomic transition.

**Ảnh hưởng production:** Race conditions khó kiểm soát khi nhiều instances xử lý cùng seat.

**Cách sửa:** Dùng rowversion/concurrency token hoặc conditional SQL update như “reserve nếu seat vẫn Available”, kiểm tra affected rows. Kết hợp unique constraint tùy model.

### Medium — Logging thiếu correlation/business operation identity

**Vấn đề:** Log chỉ có BookingId/PaymentId sau thành công; không có stable idempotency/attempt/correlation identity xuyên toàn flow.

**Tại sao xảy ra:** Observability được thêm ở cuối thay vì thiết kế cùng workflow.

**Ảnh hưởng production:** Khó điều tra double charge và phân biệt retry của cùng operation với booking mới.

**Cách sửa:** Structured logs/traces với BookingAttemptId, idempotency key hash/reference, EventId, SeatId, payment provider request ID, attempt count và distributed trace correlation. Không log card token.

## Phiên bản đề xuất

Một thiết kế an toàn hơn là tách **seat reservation**, **payment**, và **confirmation** thành các state transitions ngắn. Ví dụ dưới đây minh họa orchestration; database cần có unique/index/concurrency constraints phù hợp.

```csharp
public sealed class BookingService
{
    private readonly AppDbContext _db;
    private readonly IPaymentClient _payments;
    private readonly IPriceService _prices;

    public async Task<BookingResult> CreateAsync(
        Guid eventId,
        string seatNumber,
        Guid userId,
        string idempotencyKey,
        CancellationToken cancellationToken)
    {
        var existing = await _db.BookingAttempts
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.IdempotencyKey == idempotencyKey,
                cancellationToken);

        if (existing is not null)
        {
            return BookingResult.From(existing);
        }

        var amount = await _prices.GetAuthoritativePriceAsync(
            eventId,
            seatNumber,
            cancellationToken);

        BookingAttempt attempt;

        await using (var tx = await _db.Database.BeginTransactionAsync(cancellationToken))
        {
            var reserved = await _db.Seats
                .Where(x => x.EventId == eventId
                         && x.SeatNumber == seatNumber
                         && x.Status == SeatStatus.Available)
                .ExecuteUpdateAsync(
                    setters => setters
                        .SetProperty(x => x.Status, SeatStatus.PaymentPending)
                        .SetProperty(x => x.ReservedByUserId, userId),
                    cancellationToken);

            if (reserved != 1)
            {
                return BookingResult.Conflict();
            }

            attempt = new BookingAttempt
            {
                Id = Guid.NewGuid(),
                EventId = eventId,
                SeatNumber = seatNumber,
                UserId = userId,
                Amount = amount,
                IdempotencyKey = idempotencyKey,
                Status = BookingAttemptStatus.PaymentPending,
                CreatedAtUtc = DateTime.UtcNow
            };

            _db.BookingAttempts.Add(attempt);
            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }

        PaymentResult payment;
        try
        {
            payment = await _payments.ChargeAsync(
                attempt.Id.ToString("N"),
                amount,
                cancellationToken);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            return BookingResult.PaymentStateUnknown(attempt.Id, ex);
        }

        await using (var tx = await _db.Database.BeginTransactionAsync(cancellationToken))
        {
            var tracked = await _db.BookingAttempts
                .SingleAsync(x => x.Id == attempt.Id, cancellationToken);

            tracked.PaymentId = payment.PaymentId;
            tracked.Status = payment.Succeeded
                ? BookingAttemptStatus.Confirmed
                : BookingAttemptStatus.PaymentFailed;

            var seat = await _db.Seats.SingleAsync(
                x => x.EventId == eventId && x.SeatNumber == seatNumber,
                cancellationToken);

            seat.Status = payment.Succeeded
                ? SeatStatus.Booked
                : SeatStatus.Available;

            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }

        return BookingResult.From(attempt.Id, payment);
    }
}
```

Database-level protections vẫn cần, ví dụ:

- unique constraint cho `BookingAttempts.IdempotencyKey`;
- invariant/constraint phù hợp để một seat không thể có hai confirmed bookings;
- rowversion hoặc conditional state transition cho seat;
- index cho `(EventId, SeatNumber)` và lookup idempotency key.

Production design còn cần reconciliation worker cho `PaymentStateUnknown`/stale `PaymentPending`, thay vì giả định mọi HTTP timeout nghĩa là payment thất bại.

## Giải thích thiết kế sau khi sửa

- SQL transaction chỉ bao phủ state changes cần atomicity trong SQL, không bao external HTTP.
- Seat được giành bằng atomic conditional update thay vì `check → later insert`.
- Stable idempotency identity được persist trước external side effect.
- Amount được tính server-side.
- Workflow chấp nhận distributed failure: payment có thể thành công trong khi response/DB update fail, nên có state để reconcile.
- Cancellation được propagate cho I/O, nhưng correctness không dựa vào cancellation như compensation.
- Database constraints là lớp cuối enforce invariant khi nhiều app instances cạnh tranh.

## Trade-offs

- State machine/reconciliation phức tạp hơn một transaction tuyến tính.
- Tạm giữ seat trong `PaymentPending` cần TTL/expiry policy và background cleanup.
- Provider idempotency chỉ hữu ích nếu contract thật sự hỗ trợ và key được giữ ổn định.
- Conditional update/unique constraint có thể tạo contention trên hot seats, nhưng đó là contention đúng boundary của business invariant.
- Nếu business cần queue-based checkout ở scale rất lớn, messaging có thể hợp lý; nhưng không nên thêm messaging chỉ để che một transaction design chưa đúng.

## Cách kiểm thử

1. **Concurrency integration test:** bắn hàng chục requests đồng thời vào cùng seat; verify tối đa một logical booking được confirmed và database invariant không bị phá.
2. **Idempotency test:** gửi cùng idempotency key nhiều lần, kể cả song song; verify chỉ một logical payment operation và responses hội tụ về cùng booking attempt.
3. **Failure-path test:** payment success rồi process fail trước final DB update; verify reconciliation chuyển trạng thái đúng mà không charge lại.
4. **Load test:** provider latency 5–10 giây trong peak traffic; đo SQL transaction duration, blocking, connection pool, request p95/p99 và throughput.
5. **Security/business test:** client gửi amount giả; verify server bỏ qua/từ chối và dùng authoritative price.

## Quan sát trong production

- booking attempts theo state: `PaymentPending`, `Confirmed`, `PaymentFailed`, `PaymentStateUnknown`;
- duplicate/idempotency conflict count;
- payment provider attempts, latency, timeout và provider request IDs;

## Đoạn code cần review

```vue
<script setup lang="ts">
import { onMounted, ref, watch } from 'vue';

type SearchItem = {
  id: string;
  name: string;
  highlightHtml: string;
};

const query = ref('');
const items = ref<SearchItem[]>([]);
const loading = ref(false);
const error = ref('');

async function search() {
  if (query.value.length < 2) {
    items.value = [];
    return;
  }

  loading.value = true;
  error.value = '';

  try {
    const response = await fetch('/api/search?q=' + query.value);
    const body = await response.json();
    items.value = body.items;
  } catch (e) {
    items.value = [];
    error.value = 'Search failed';
  } finally {
    loading.value = false;
  }
}

watch(query, () => {
  search();
});

onMounted(() => {
  search();
});
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-else-if="error">{{ error }}</p>
    <p v-else-if="items.length === 0">No results</p>

    <ul v-else>
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <div v-html="item.highlightHtml"></div>
      </li>
    </ul>
  </section>
</template>
```

### Critical — `v-html` render backend-provided markup tạo XSS trust boundary

**Vấn đề:** `highlightHtml` được inject trực tiếp vào DOM bằng `v-html`.

**Tại sao xảy ra:** Vue escaping không áp dụng cho nội dung render qua `v-html`; nếu backend/search index chứa markup độc hại hoặc sanitizer sai, browser có thể interpret HTML ngoài ý muốn.

**Ảnh hưởng production:** Stored/reflected XSS có thể chạy trong origin của application, lấy dữ liệu user hoặc thực hiện hành động với quyền của user tùy security controls.

**Cách sửa:** Tốt nhất backend trả structured highlight segments/text và frontend render bằng interpolation. Nếu business bắt buộc HTML, sanitize bằng một well-maintained sanitizer với allowlist phù hợp và defense-in-depth CSP; không tự viết regex sanitizer.

### High — Stale response có thể overwrite query mới hơn

**Vấn đề:** Mỗi `search()` ghi trực tiếp `items.value` khi response hoàn tất, không kiểm tra request đó còn là request mới nhất.

**Tại sao xảy ra:** Network completion order không bảo đảm giống request start order.

**Ảnh hưởng production:** User thấy kết quả không khớp text hiện tại, gây click nhầm và khó tái hiện trong local testing.

**Cách sửa:** Hủy request cũ bằng `AbortController` và/hoặc dùng request sequence token để bỏ qua stale completion.

### High — Không debounce input, dễ tạo request storm

**Vấn đề:** Mỗi thay đổi ký tự gọi API ngay.

**Tại sao xảy ra:** `watch(query)` gọi `search()` trực tiếp.

**Ảnh hưởng production:** Một user gõ nhanh tạo nhiều requests; ở scale lớn gây API/QPS burst, cache churn và tăng khả năng rate-limit/latency.

**Cách sửa:** Debounce 200–400 ms tùy UX/SLO, đồng thời cancel request cũ.

### High — HTTP 4xx/5xx không được xử lý như failure

**Vấn đề:** `fetch()` resolve bình thường cho HTTP error responses; code vẫn gọi `response.json()` và có thể gán `body.items` hoặc rơi vào lỗi parsing không rõ semantic.

**Tại sao xảy ra:** Code chỉ dựa vào exception path của network/parse failure.

**Ảnh hưởng production:** 500/401/429 có thể bị hiển thị như empty/no-results hoặc lỗi khó phân biệt; retry/alerting sai.

**Cách sửa:** Kiểm tra `response.ok`, map status classes sang error contract phù hợp, và chỉ parse body theo content contract mong đợi.

### Medium — `loading` sai khi requests overlap

**Vấn đề:** Request cũ hoàn tất có thể chạy `finally` và set `loading=false` trong khi request mới vẫn còn pending.

**Tại sao xảy ra:** Một boolean global không gắn với active request identity.

**Ảnh hưởng production:** Spinner biến mất quá sớm và state UI mâu thuẫn.

**Cách sửa:** Chỉ request hiện tại được quyền mutate loading/result state; sequence ID hoặc active controller giúp enforce.

### Medium — Query string concat thủ công

**Vấn đề:** `'/api/search?q=' + query.value` không encode query.

**Tại sao xảy ra:** Query chứa `&`, `?`, `#`, unicode hoặc ký tự đặc biệt có thể thay đổi URL semantics.

**Ảnh hưởng production:** Search sai, log/analytics khó hiểu và có thể làm input bị cắt thành query parameters ngoài ý muốn.

**Cách sửa:** Dùng `URLSearchParams` hoặc URL API.

### Medium — Không cleanup/cancel khi component unmount

**Vấn đề:** Request có thể tiếp tục sau route change; completion vẫn cố mutate component state/resource lifecycle không còn cần thiết.

**Tại sao xảy ra:** Không có `onBeforeUnmount`/`onUnmounted` để abort active request/timer.

**Ảnh hưởng production:** Lãng phí network/server capacity và tạo noise trong telemetry; với flow phức tạp hơn có thể gây side effects khó đoán.

**Cách sửa:** Abort active controller và clear debounce timer khi component unmount.

### Medium — Empty-query UX conflates initial state với “No results”

**Vấn đề:** Khi query dưới 2 ký tự, items rỗng; template có thể hiển thị `No results` dù user chưa thực hiện valid search.

**Tại sao xảy ra:** UI state chỉ dùng `items.length`, không model “idle/loaded/error”.

**Ảnh hưởng production:** UX gây hiểu nhầm; analytics nếu dựa trên empty state cũng sai.

**Cách sửa:** Model explicit state hoặc `hasSearched`/status enum.

## Phiên bản đề xuất

Ví dụ dưới đây tránh raw HTML bằng cách giả định backend trả highlight text/segments an toàn. Nếu API hiện chưa làm vậy, cần đổi contract thay vì giữ `v-html` vô điều kiện.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue';

type SearchItem = {
  id: string;
  name: string;
  highlightText: string;
};

type SearchResponse = {
  items: SearchItem[];
};

const query = ref('');
const items = ref<SearchItem[]>([]);
const status = ref<'idle' | 'loading' | 'loaded' | 'error'>('idle');
const error = ref('');

let debounceTimer: ReturnType<typeof setTimeout> | undefined;
let activeController: AbortController | undefined;
let requestSequence = 0;

async function executeSearch(input: string) {
  activeController?.abort();

  if (input.length < 2) {
    items.value = [];
    status.value = 'idle';
    return;
  }

  const sequence = ++requestSequence;
  const controller = new AbortController();
  activeController = controller;

  status.value = 'loading';
  error.value = '';

  try {
    const params = new URLSearchParams({ q: input });
    const response = await fetch(`/api/search?${params.toString()}`, {
      signal: controller.signal
    });

    if (!response.ok) {
      throw new Error(`Search HTTP ${response.status}`);
    }

    const body = (await response.json()) as SearchResponse;

    if (sequence !== requestSequence) {
      return;
    }

    items.value = body.items;
    status.value = 'loaded';
  } catch (e) {
    if (controller.signal.aborted || sequence !== requestSequence) {
      return;
    }

    items.value = [];
    error.value = 'Search failed. Please try again.';
    status.value = 'error';
  }
}

watch(query, (value) => {
  if (debounceTimer) {
    clearTimeout(debounceTimer);
  }

  debounceTimer = setTimeout(() => {
    void executeSearch(value.trim());
  }, 300);
});

onBeforeUnmount(() => {
  if (debounceTimer) {
    clearTimeout(debounceTimer);
  }

  activeController?.abort();
});
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="status === 'loading'">Loading...</p>
    <p v-else-if="status === 'error'">{{ error }}</p>
    <p v-else-if="status === 'loaded' && items.length === 0">No results</p>

    <ul v-if="status === 'loaded' && items.length > 0">
      <li v-for="item in items" :key="item.id">
        <strong>{{ item.name }}</strong>
        <div>{{ item.highlightText }}</div>
      </li>
    </ul>
  </section>
</template>
```

Trong production code, có thể đóng gói debounce/cancellation vào composable hoặc data-fetching abstraction nếu nhiều components dùng cùng pattern. Không cần thêm một state-management framework chỉ để sửa race condition cục bộ.

## Giải thích thiết kế sau khi sửa

- Debounce giảm request amplification nhưng không thay cancellation; hai cơ chế giải quyết hai vấn đề khác nhau.
- `AbortController` giảm work không còn cần thiết; sequence ID là guard bổ sung để stale completion không mutate state.
- Explicit status tránh `loading/error/empty` chồng chéo.
- URL query được encode bằng `URLSearchParams`.
- `response.ok` được kiểm tra để HTTP failures không bị coi như success.
- Highlight chuyển sang text/structured contract để tránh raw HTML trust boundary.
- Lifecycle cleanup abort request và timer khi component unmount.

## Trade-offs

- Debounce thêm 300 ms trước request; cần chọn giá trị dựa trên UX và backend capacity, không mặc định càng lớn càng tốt.
- Abort request ở browser không bảo đảm server đã dừng toàn bộ processing; backend vẫn cần cancellation/resource limits phù hợp.
- Sequence token + abort hơi nhiều code hơn, nhưng làm state correctness rõ ràng khi race xảy ra.
- Structured highlight contract có thể giảm flexibility so với arbitrary HTML nhưng an toàn và dễ test hơn.
- Nếu sanitizer bắt buộc, dependency/security maintenance cost tăng và vẫn cần CSP/encoding defense-in-depth.

## Cách kiểm thử

1. **Component async-race test:** mock `ip` và `iphone` với completion order đảo ngược; verify chỉ query mới nhất được render.
2. **Network/cancellation test:** gõ nhanh 10 ký tự; verify debounce giới hạn request count và prior active request bị abort.
3. **HTTP failure test:** backend trả 401/429/500/invalid JSON; verify error state đúng, không hiện “No results” giả.
4. **Security test:** backend trả payload chứa `<img onerror=...>` hoặc script-like markup; verify UI render như text/structured safe content, không execute HTML.
5. **Lifecycle test:** unmount component khi request đang pending; verify timer/request được cleanup và không còn state mutation không cần thiết.

## Quan sát trong production

- search request count trên mỗi active user/session;
- debounce-to-request rate và canceled request count;
- frontend perceived latency từ input settled → results rendered;
- API latency p50/p95/p99 và status 4xx/5xx/429;
- stale-response discarded count nếu instrumented;
- zero-result rate tách khỏi error rate;
- browser `PerformanceResourceTiming`/RUM hoặc Application Insights frontend telemetry phù hợp;
- correlation/trace ID giữa browser search request và backend dependency trace;
- CSP violation reports nếu hệ thống có CSP reporting.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search rất nhanh nhưng user ở mobile network chậm, bạn chọn debounce/cancellation strategy thế nào?
2. Nếu Product bắt buộc highlight chứa `<em>` markup, bạn thiết kế API/rendering để vẫn giữ XSS boundary an toàn ra sao?
3. Nếu nhiều components cần server-state caching, khi nào bạn dùng một query library thay vì tự viết composable?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Business invariant dưới concurrency phải được enforce ở transaction/database boundary; `check rồi insert` trong application không đủ khi nhiều requests/instances cạnh tranh.
- Không thể làm SQL transaction và arbitrary external HTTP side effect trở thành một ACID transaction chỉ bằng cách giữ database transaction mở lâu hơn.
- Retry-safe workflow cần stable idempotency identity, explicit state transitions và reconciliation cho failure window có kết quả không chắc chắn.
- Frontend async correctness phụ thuộc request ordering, cancellation và stale-response handling; network completion order không tuân theo thứ tự user gõ.
- `v-html`/raw HTML làm thay đổi trust boundary. Structured text/segments thường an toàn hơn sanitizer tự viết.

## Mẫu tư duy cần nhớ

1. **Enforce invariants at the authoritative boundary.**
2. **Model distributed failure windows explicitly.**
3. **Design retry together with idempotency.**
4. **Treat async completion order as nondeterministic.**
5. **Reduce trust boundaries instead of sanitizing everything after the fact.**
