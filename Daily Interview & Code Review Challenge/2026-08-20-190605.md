# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi dưới tải

**Loại câu hỏi:** Internal mechanism trong tình huống production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, Change Tracker, SQL diagnostics, performance reasoning

## Bối cảnh

Một ASP.NET Core API lấy danh sách nhân viên rồi tính thêm trạng thái mailbox. Sau một thay đổi refactor, p95 tăng từ khoảng 180 ms lên hơn 1 giây khi traffic cao. Database CPU tăng đáng kể. Developer nói rằng `IQueryable` đã được tạo một lần nên SQL cũng chỉ chạy một lần. Endpoint dùng cùng một `DbContext` trong request, dữ liệu chỉ đọc nhưng không dùng `AsNoTracking()`. Một helper kiểm tra `AnyAsync()`, sau đó code lại gọi `ToListAsync()` trên cùng query.

Chưa biết chính xác SQL được phát ra bao nhiêu lần, số entity được track, execution plan hay kích thước result set.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong từ lúc tạo `IQueryable` đến lúc `AnyAsync()` và `ToListAsync()` chạy; tại sao latency và DB CPU có thể tăng; misconception nào đang tồn tại; rủi ro production là gì; và bạn sẽ chứng minh từng giả thuyết như thế nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Query có `Include`, projection hoặc navigation nào không?
- Mỗi request trả về bao nhiêu row và entity có được cập nhật sau đó không?
- SQL thực tế của hai terminal operation có giống nhau không?
- Có query compilation/client evaluation hoặc N+1 ở phần enrichment không?
- Latency nằm ở database, materialization hay downstream mailbox call?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng expression tree với thực thi query.
- **Gợi ý 2:** Xem terminal operators, tracking, materialization và số round-trip tới DB.
- **Gợi ý 3:** Đừng tối ưu từ source code alone; thu SQL, traces, timings và execution plan rồi mới quyết định projection/no-tracking/query restructuring.

## Cấu trúc trả lời đề xuất

1. Làm rõ semantics và mục đích của query.
2. Giải thích deferred execution.
3. Xác định các điểm thực thi SQL.
4. Phân tích tracking/materialization.
5. Liệt kê nhiều giả thuyết performance.
6. Thu evidence.
7. Đề xuất thay đổi nhỏ nhất có thể đo được.
8. Kiểm thử và theo dõi regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` mô tả query; tạo biến không đồng nghĩa query đã chạy.
- `AnyAsync()` và `ToListAsync()` là hai lần execution độc lập nếu gọi trên query như mô tả.
- Query chỉ đọc thường có thể giảm tracking overhead bằng `AsNoTracking()` hoặc projection phù hợp.
- Không kết luận root cause chỉ từ một pattern; phải kiểm chứng SQL/timing/query plan.

### Điểm cộng

- Giải thích `AnyAsync()` thường được dịch thành phép kiểm tra tồn tại thay vì materialize toàn bộ collection.
- Đề xuất projection chỉ lấy cột cần thiết.
- Nhắc đến cardinality, index, `Include`, cartesian explosion và N+1 như các giả thuyết độc lập.

### Nâng cao

- Dùng OpenTelemetry/APM, EF Core command logging/interceptors và DB query statistics để correlate request → SQL.
- Phân biệt tracking overhead trong process với database execution cost.
- Đặt performance budget và regression test thay vì chỉ “query nhanh hơn trên máy dev”.

## Hướng giải quyết tham khảo

**Giả định:** endpoint chỉ đọc dữ liệu và không cần entity tracking sau khi materialize.

Expression LINQ được tích lũy thành `IQueryable`. SQL chưa cần được gửi đi cho đến khi terminal operation yêu cầu kết quả. Vì vậy việc gọi `AnyAsync()` rồi `ToListAsync()` tạo hai database operations; lần thứ hai không tái sử dụng result của lần đầu. Với query trả nhiều entity, tracking còn tạo entries/snapshot cần thiết cho Change Tracker, tăng CPU và allocation trong ứng dụng.

Tuy nhiên hai execution chưa chắc là nguyên nhân duy nhất. Cần capture generated SQL, số command/request, duration, rows, execution plan và tracing. Nếu query có `Include` lớn hoặc enrichment per-row thì phải điều tra riêng.

Nếu business logic chỉ cần danh sách, thường có thể bỏ pre-check `AnyAsync()` và materialize một lần; empty list tự biểu diễn “không có dữ liệu”. Dùng projection DTO và `AsNoTracking()` khi semantics cho phép. Index phải được quyết định từ predicate/order/join và execution plan, không phải thêm theo cảm tính.

Failure case cần xem gồm DB timeout, cancellation, result set tăng bất thường và downstream enrichment chậm. Load test với dữ liệu production-like, so sánh command count, p50/p95/p99, DB CPU, allocations và error rate trước/sau.

Nếu entity cần được sửa rồi `SaveChanges`, recommendation về no-tracking thay đổi. Nếu query rất lớn, cần pagination/keyset hoặc thiết kế lại endpoint thay vì chỉ tối ưu tracking.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ không giả định `IQueryable` chạy khi được khai báo. Nó chủ yếu giữ expression để provider dịch khi query được enumerate hoặc gặp terminal operator. Trong case này `AnyAsync()` là một execution và `ToListAsync()` là execution thứ hai, nên nhận định ‘tạo query một lần thì SQL chạy một lần’ là sai. Tôi sẽ xác nhận bằng EF command logs hoặc tracing thay vì chỉ đọc code.

Nếu endpoint read-only, tracking toàn bộ entity có thể tạo overhead không cần thiết. Tôi sẽ kiểm tra generated SQL, rows returned, execution plan, số command mỗi request và thời gian materialization. Tôi cũng kiểm tra `Include`, N+1 và downstream calls vì DB CPU tăng không chứng minh tracking là root cause.

Nếu requirement chỉ cần list, tôi có xu hướng bỏ `AnyAsync()`, materialize một lần, dùng projection DTO và no-tracking nếu phù hợp. Sau đó load test với dữ liệu tương đương production và theo dõi p95, DB CPU, query count, allocations. Nếu dữ liệu cần update trong cùng unit of work thì tôi sẽ giữ tracking ở phần thực sự cần nó.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTracking()` lại là lựa chọn sai hoặc gây code phức tạp hơn?
2. Nếu bỏ `AnyAsync()` nhưng query chính rất đắt và chỉ cần biết tồn tại trong một business branch thì sao?
3. Nếu SQL chỉ chạy một lần nhưng API vẫn chậm, bạn sẽ điều tra layer nào tiếp theo?

## Lỗi trả lời thường gặp

- Nói mọi LINQ đều chạy ngay khi khai báo.
- Khẳng định `AsNoTracking()` luôn phải dùng cho mọi query.
- Đổ lỗi cho EF Core mà không xem SQL/execution plan.
- Tối ưu bằng cache trước khi xác định bottleneck.
- Không đề cập cách đo trước/sau.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **1.5**
- Communication: đánh giá xuyên suốt; câu trả lời thiếu cấu trúc có thể bị trừ trong các mục trên.

# Câu 2 — Incident: Hangfire gửi cùng một tác vụ offboarding nhiều lần

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, database concurrency, external side effects, observability

## Bối cảnh

Một hệ thống .NET chạy background job để reset forwarding/delegation khi cấu hình offboarding hết hạn. Sau deployment, một số mailbox nhận thao tác reset nhiều lần và một số record lịch sử bị duplicate. Dashboard cho thấy có retry nhưng chưa rõ retry do timeout, exception sau external call, nhiều worker cùng lấy công việc hay scheduler enqueue trùng. Business muốn giảm tác động ngay nhưng không được bỏ sót các cấu hình thực sự cần reset.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ lúc nhận cảnh báo đến khi xác nhận hệ thống ổn định như thế nào, đồng thời thiết kế lại job để retry hoặc chạy đồng thời không tạo side effect sai?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate là duplicate enqueue, duplicate execution hay duplicate side effect?
- External operation có idempotent không và có request/correlation identifier không?
- Job retry policy hiện tại thế nào; có nhiều server/worker không?
- Database có unique constraint/state transition/concurrency token nào bảo vệ không?
- Có thể tạm dừng riêng loại job này mà không ảnh hưởng job khác không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “stabilize incident” khỏi “tìm root cause”.
- **Gợi ý 2:** At-least-once execution phải được thiết kế cùng idempotency và durable state.
- **Gợi ý 3:** Bảo vệ business invariant tại durable boundary; lock/job filter chỉ là một lớp, không nên là guarantee duy nhất cho external side effects.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius.
2. Giảm side effects mới.
3. Thu evidence theo job ID/business key.
4. Lập các giả thuyết độc lập.
5. Reproduce và xác định failure window.
6. Hotfix an toàn.
7. Thiết kế idempotency dài hạn.
8. Backfill/reconcile và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không xóa retry một cách mù quáng.
- Xác định business idempotency key, ví dụ config/action/version.
- Phân biệt enqueue-once với execute-once và side-effect-once.
- Có reconciliation cho trạng thái DB và external system.

### Điểm cộng

- State machine như Pending → Processing → Completed/Failed với optimistic concurrency hoặc atomic conditional update.
- Unique constraint cho operation key/history nếu business invariant yêu cầu duy nhất.
- Ghi external request outcome đủ để retry có quyết định.

### Nâng cao

- Phân tích “external succeeded, DB commit failed” là distributed consistency problem.
- Thiết kế inbox/outbox hoặc operation ledger tùy mức criticality.
- Metrics theo attempts, duplicate prevented, age, failure reason và reconciliation drift.

## Hướng giải quyết tham khảo

Trước tiên xác định số mailbox bị ảnh hưởng, loại side effect và thời điểm bắt đầu. Nếu duplicate có thể gây hại, giảm concurrency hoặc tạm ngừng riêng queue/job liên quan trong khi giữ dữ liệu pending; không xóa công việc chưa xử lý.

Thu job ID, retry count, worker, timestamps, exception, DB transaction logs/application logs và external request correlation. Các giả thuyết gồm scheduler enqueue hai lần, automatic retry sau exception, worker overlap, timeout khiến client nghĩ call thất bại dù remote đã thành công, hoặc transaction/save history thất bại sau external side effect.

Fix bền vững phải bắt đầu từ business operation identity. Ví dụ tạo `OperationKey = ConfigId + Action + ExpiryVersion`; persist operation ledger có unique constraint. Worker atomically claim operation bằng conditional state transition. Nếu đã Completed thì return success. Nếu đang Processing quá lâu, recovery policy quyết định retry sau khi kiểm tra trạng thái external.

Một distributed lock có thể giảm overlap nhưng không giải quyết crash ở khoảng giữa external success và local commit. Nếu external API hỗ trợ idempotency key thì truyền operation key. Nếu không, cần API-specific reconciliation/read-before-retry khi có thể và thiết kế thao tác theo hướng convergent/idempotent.

Sau hotfix, chạy reconciliation giữa DB và mailbox state, sửa duplicate history theo business rule, replay các pending operation an toàn. Monitor duplicate-prevented count, retries, job age, failures, external latency và drift.

Recommendation thay đổi nếu external action vốn idempotent hoàn toàn và duplicate chỉ tạo log noise; khi đó giải pháp có thể đơn giản hơn, nhưng history uniqueness và observability vẫn cần xử lý.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách incident thành stabilization và root-cause investigation. Trước tiên xác định blast radius và nếu duplicate side effect gây hại, tôi giảm hoặc pause riêng queue liên quan thay vì xóa retry/pending jobs. Sau đó correlate business config với Hangfire job ID, attempt, worker, exception và external request để biết duplicate xảy ra ở enqueue, execution hay external side effect.

Về thiết kế, tôi không dựa vào giả định job chỉ chạy một lần. Tôi tạo một durable operation key và enforce uniqueness trong DB. Worker claim operation bằng atomic state transition; Completed thì no-op. Nếu external system hỗ trợ idempotency key tôi truyền cùng key đó. Tôi cũng đặc biệt kiểm tra failure window nơi external call thành công nhưng DB update thất bại, vì distributed lock không giải quyết được case này.

Cuối cùng tôi reconcile DB với external state, replay phần pending an toàn và theo dõi retry rate, duplicate prevented, queue age, external failures và drift. Tôi chỉ giảm retry nếu evidence cho thấy retry policy không phù hợp; retry vẫn cần cho transient failures nhưng phải đi cùng idempotency.”

## Câu hỏi đào sâu

1. Unique constraint giúp gì và không giúp gì nếu external call xảy ra trước khi transaction commit?
2. Bạn sẽ xử lý một operation bị `Processing` 30 phút do worker crash như thế nào?
3. Nếu Microsoft Graph/Exchange operation không cung cấp idempotency key, bạn thiết kế recovery ra sao?

## Lỗi trả lời thường gặp

- Chỉ thêm distributed lock rồi coi vấn đề đã giải quyết.
- Tắt toàn bộ retry để tránh duplicate.
- Không phân biệt local DB state và external side effect.
- Không có reconciliation sau incident.
- Không thiết kế metric để phát hiện tái diễn.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repo nhưng không được tự ý thay đổi production

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, deterministic validation, evaluation, security, auditability

## Bối cảnh

Team muốn một AI agent review pull request cho repository .NET. Agent cần đọc diff và các file liên quan, nhận diện lỗi correctness/security/performance, chạy một số test và đưa comment có evidence. Team đang cân nhắc cho agent quyền GitHub, shell/test runner và MCP tools. Không được để agent merge PR, đọc secret production hoặc thực thi command tùy ý trên hạ tầng production. Chi phí và latency cũng phải kiểm soát.

Chưa có quyết định về model, context retrieval, approval boundary, benchmark hay cách đo false-positive rate.

## Câu hỏi chính

Hãy thiết kế workflow cho AI code-review agent này: vì sao phần nào cần AI, phần nào phải deterministic, context nào được cung cấp, tools/permissions nào được phép, output được validate thế nào, hallucination được phát hiện ra sao, quality được đo bằng gì, fallback là gì và hệ thống được audit/monitor như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay có thể tạo patch?
- Repository có dữ liệu nhạy cảm hoặc generated/vendor code cần loại trừ không?
- Review target là correctness, security, architecture hay tất cả?
- Test suite mất bao lâu và runner có network access không?
- Team chấp nhận false-positive/latency/cost ở mức nào?

## Gợi ý tư duy

- **Gợi ý 1:** AI nên xử lý phần cần semantic reasoning; policy enforcement không nên giao hoàn toàn cho model.
- **Gợi ý 2:** Context và tool permission là security boundary, không chỉ là prompt design.
- **Gợi ý 3:** Thiết kế pipeline evidence-first: diff → targeted context → analysis → deterministic verification → gated publication → evaluation telemetry.

## Cấu trúc trả lời đề xuất

1. Làm rõ mục tiêu và threat model.
2. Chia deterministic/AI responsibilities.
3. Thiết kế context acquisition.
4. Thiết kế tool capability và sandbox.
5. Structured review output.
6. Verification/gating.
7. Evaluation và feedback loop.
8. Audit, cost, fallback và incident handling.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI không được tự quyết permission hoặc bypass policy.
- Least privilege cho GitHub/tool access; read-only mặc định.
- Review claim phải gắn file/line/evidence và được validate trước khi publish.
- Có benchmark/evaluation thay vì đánh giá bằng cảm giác.

### Điểm cộng

- Context selection dựa trên diff, symbol/dependency references và repository rules thay vì nhét toàn repo.
- Structured schema cho severity, claim, evidence, confidence, suggested validation.
- Sandbox test runner với command allowlist, timeout, resource/network restrictions.

### Nâng cao

- Prompt-injection defense cho repository content được xem là untrusted data.
- Evaluation set từ historical bugs/reviews với precision, recall/usefulness và false-positive burden.
- Version model/prompt/tool policy để audit regression.

## Hướng giải quyết tham khảo

AI có giá trị ở việc suy luận semantic qua diff, business logic và cross-file interaction; deterministic tools tốt hơn cho compilation, tests, formatters, static analyzers, secret scanning, permission policy và schema validation.

Pipeline đề xuất: webhook/CI nhận PR → deterministic diff metadata → context selector lấy changed files cùng symbol/call-site/test/rules liên quan → model tạo structured findings → verifier kiểm tra file/line tồn tại, evidence khớp diff và chạy allowlisted analyzers/tests → confidence/policy gate → publish comment. Finding không đủ evidence bị suppress hoặc chuyển thành câu hỏi thay vì assertion.

GitHub token chỉ có quyền tối thiểu cần thiết, mặc định read repository metadata/content và quyền comment nếu cần. Shell chạy trong ephemeral sandbox không có production secrets; network bị deny mặc định hoặc allowlist. MCP server cũng được coi là capability boundary: chỉ expose tool cần thiết với input validation và audit log. Repository text, issue, README và code comments là untrusted context; không cho chúng tự thay đổi system policy/tool permissions.

Quality nên đo trên curated evaluation set và shadow runs: precision của actionable findings, recall trên known defects, false-positive burden, acceptance/dismissal rate, latency và cost/PR. Không dùng acceptance rate một mình vì reviewer behavior có bias.

Fallback: nếu model/tool timeout thì CI deterministic vẫn chạy; agent trả trạng thái inconclusive thay vì approve. High-risk finding cần human review. Audit log gồm model/prompt version, context IDs/hashes, tool calls, result schema, validation outcome và publication decision nhưng phải tránh log secrets.

Nếu mục tiêu sau này chuyển từ comment-only sang auto-fix, quyền write nên là workflow riêng với branch isolation, tests bắt buộc và human approval trước merge.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế agent như một reviewer có quyền tự do. Tôi chia pipeline thành deterministic controls và AI reasoning. Compiler, tests, analyzers, permission checks và output schema là deterministic; model dùng cho semantic review như race condition, business invariant hoặc cross-file behavior.

Context bắt đầu từ diff rồi mở rộng có mục tiêu tới symbol, call sites, tests và repository rules. Tôi coi mọi nội dung repo là untrusted data để tránh prompt injection. GitHub token dùng least privilege; shell chạy trong ephemeral sandbox không có production secret và network deny-by-default. MCP cũng chỉ expose capability cụ thể chứ không cho model quyền tùy ý.

Model trả structured findings gồm file, line, claim, severity, evidence và cách verify. Trước khi comment, hệ thống kiểm tra location/evidence và chạy test hoặc analyzer phù hợp. Finding yếu có thể bị suppress hoặc chuyển thành câu hỏi. Tôi đánh giá bằng historical defect set và shadow mode, theo dõi precision, recall, false-positive burden, latency và cost. Nếu model fail, deterministic CI vẫn hoạt động và agent không được tự approve. Mọi model version, context và tool call quan trọng đều có audit trail.”

## Câu hỏi đào sâu

1. Nếu agent cần đọc dependency source ngoài repository để xác minh finding thì bạn mở network như thế nào?
2. Làm sao phát hiện một comment trong source đang cố prompt-inject agent?
3. Nếu team yêu cầu agent tự sửa và push code để tiết kiệm thời gian, bạn thay đổi trust boundary ra sao?

## Lỗi trả lời thường gặp

- “Cho LLM đọc repo rồi review” mà không có retrieval/validation design.
- Cho shell/GitHub token quyền rộng để tiện triển khai.
- Dùng prompt như security control duy nhất.
- Không có evaluation dataset hoặc metric false positives.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution phải được hiểu theo execution boundary thực tế; performance tuning cần evidence từ SQL, tracing và measurements.
- Background jobs phải giả định retry/duplicate có thể xảy ra; correctness nằm ở business idempotency và durable state, không chỉ scheduler configuration.
- External side effects tạo failure window mà local lock/transaction không thể tự giải quyết; reconciliation là một phần của thiết kế.
- AI agent nên bị giới hạn bởi deterministic policies, least privilege, sandbox và evidence-based validation.
- Observability và evaluation phải được thiết kế cùng hệ thống, không thêm vào sau khi có incident.

## Mẫu tư duy cần nhớ

- Clarify execution boundaries before optimizing.
- Stabilize first, investigate with evidence second.
- Design retries together with idempotency and reconciliation.
- Keep policy deterministic; use AI for bounded semantic reasoning.
- Treat context, tools and observability as part of the security/design boundary.
