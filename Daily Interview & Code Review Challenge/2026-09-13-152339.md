# Code Review Challenge 1 — Cosmos DB booking API bị oversell khi nhiều request cập nhật cùng inventory

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Cosmos DB, optimistic concurrency, ETag, transactional boundary, retry, partition key, idempotency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một booking API dùng Azure Cosmos DB để quản lý số lượng vé còn lại cho từng event. Container `booking` dùng partition key `/eventId`.

Trong cùng partition của một event có hai loại document:

- `InventoryDocument`: giữ `remainingSeats`;
- `ReservationDocument`: đại diện cho một booking đã được tạo.

Business rule:

- không được oversell;
- cùng một `clientRequestId` retry nhiều lần không được tạo nhiều reservation;
- nếu request thành công thì việc trừ inventory và tạo reservation phải có outcome nhất quán;
- API chạy trên nhiều App Service instances;
- client mobile có thể retry khi timeout;
- peak traffic tập trung mạnh ngay khi mở bán.

Production xuất hiện triệu chứng:

- đôi lúc `remainingSeats` trở thành số âm;
- có hai reservation khác nhau được tạo từ cùng một thao tác user khi client retry;
- cùng một event có nhiều request đọc cùng giá trị `remainingSeats` rồi đều ghi lại thành công;
- một số request timeout ở client nhưng backend thực tế đã tạo reservation;
- khi traffic tăng, số lần update conflict và request latency tăng mạnh;
- logs chỉ ghi `eventId`, không có `clientRequestId`, ETag hoặc operation id;
- team đề xuất thêm `lock` static trong API để “serialize” booking;
- một developer khác đề xuất retry toàn bộ method 5 lần nếu gặp exception.

## Đoạn code cần review

```csharp
public sealed class BookingService
{
    private readonly Container _container;
    private readonly ILogger<BookingService> _logger;

    public BookingService(
        CosmosClient cosmosClient,
        ILogger<BookingService> logger)
    {
        _container = cosmosClient.GetContainer("booking-db", "booking");
        _logger = logger;
    }

    public async Task<ReservationDocument> ReserveAsync(
        string eventId,
        string userId,
        int quantity,
        string clientRequestId,
        CancellationToken cancellationToken)
    {
        var partitionKey = new PartitionKey(eventId);

        var inventoryResponse = await _container.ReadItemAsync<InventoryDocument>(
            id: $"inventory:{eventId}",
            partitionKey: partitionKey,
            cancellationToken: cancellationToken);

        var inventory = inventoryResponse.Resource;

        if (inventory.RemainingSeats < quantity)
            throw new InvalidOperationException("Not enough seats");

        inventory.RemainingSeats -= quantity;
        inventory.UpdatedAt = DateTimeOffset.UtcNow;

        await _container.ReplaceItemAsync(
            inventory,
            inventory.Id,
            partitionKey,
            cancellationToken: cancellationToken);

        var reservation = new ReservationDocument
        {
            Id = Guid.NewGuid().ToString("N"),
            EventId = eventId,
            UserId = userId,
            Quantity = quantity,
            ClientRequestId = clientRequestId,
            CreatedAt = DateTimeOffset.UtcNow
        };

        await _container.CreateItemAsync(
            reservation,
            partitionKey,
            cancellationToken: cancellationToken);

        _logger.LogInformation(
            "Reserved {Quantity} seats for event {EventId} user {UserId}",
            quantity,
            eventId,
            userId);

        return reservation;
    }
}
```

## Kết quả code review tham khảo

### Critical — Inventory update không có optimistic concurrency guard

**Vấn đề:** Code đọc document rồi `ReplaceItemAsync` mà không ràng buộc write vào version/ETag đã đọc.

**Tại sao xảy ra:** Đây là read-modify-write nhưng không có cơ chế phát hiện document đã thay đổi giữa read và replace.

**Ảnh hưởng production:** Hai requests có thể cùng đọc cùng `RemainingSeats`, cùng pass validation và lần lượt ghi kết quả dựa trên stale state. Last write có thể che mất update trước và reservations vẫn được tạo, dẫn tới oversell hoặc inventory không phản ánh số bookings thực tế.

**Cách sửa:** Dùng optimistic concurrency với ETag bằng request options `IfMatchEtag`, hoặc tốt hơn trong scenario này là đưa inventory update và reservation create vào cùng transactional batch trong một partition, kết hợp conditional replace.

### Critical — Trừ inventory và tạo reservation không atomic

**Vấn đề:** Hai writes là hai requests độc lập.

**Tại sao xảy ra:** Code giả định cùng partition key đồng nghĩa với atomicity, nhưng các calls tách rời không tự động là một transaction chung.

**Ảnh hưởng production:** Nếu inventory giảm thành công nhưng tạo reservation thất bại, seats bị mất. Nếu reservation tạo thành công nhưng response thất bại ở client, retry có thể tạo thêm reservation.

**Cách sửa:** Vì hai documents cùng partition key `/eventId`, có thể dùng Cosmos DB transactional batch để thực hiện conditional inventory replace + reservation create như một atomic unit, miễn là business state cần commit trong cùng logical partition.

### Critical — `clientRequestId` không enforce idempotency

**Vấn đề:** `clientRequestId` chỉ là một field trong document, còn `Id` được tạo mới bằng `Guid.NewGuid()` mỗi lần gọi.

**Tại sao xảy ra:** Không có unique identity hoặc lookup/constraint dựa trên idempotency key.

**Ảnh hưởng production:** Client retry cùng logical action có thể tạo nhiều reservations với các document ids khác nhau.

**Cách sửa:** Thiết kế reservation id deterministic theo operation, ví dụ `reservation:{clientRequestId}` trong partition event, hoặc tạo một idempotency document cùng transaction. Nếu cùng request lặp lại và document đã tồn tại, trả outcome trước đó thay vì thực hiện business side effect lần nữa.

### Critical — Retry toàn method có thể duplicate business effect

**Vấn đề:** Retry mù không phân biệt operation đã commit hay chưa.

**Tại sao xảy ra:** Distributed request có trạng thái “unknown outcome” khi backend commit nhưng client không nhận response.

**Ảnh hưởng production:** Mỗi retry có thể tạo reservation mới, trừ inventory thêm hoặc đẩy hệ thống vào inconsistency.

**Cách sửa:** Chỉ retry transient failures khi operation đã được thiết kế idempotent. Dùng stable `clientRequestId` qua mọi attempt và đọc lại committed reservation nếu create báo conflict/existence hoặc response trước bị mất.

### High — `static lock` không giải quyết multi-instance concurrency

**Vấn đề:** In-memory lock chỉ serialize threads trong một process.

**Tại sao xảy ra:** Mỗi App Service instance/process có memory riêng.

**Ảnh hưởng production:** Scale-out vẫn cho phép requests trên các instances khác nhau race cùng inventory.

**Cách sửa:** Dùng concurrency control tại datastore nơi state được sở hữu. Không thêm distributed lock nếu Cosmos transactional batch + ETag đã đủ giải quyết invariant.

### High — Validation quantity chưa bảo vệ input bất hợp lệ

**Vấn đề:** Code chỉ kiểm tra `remainingSeats < quantity` nhưng không reject `quantity <= 0`.

**Tại sao xảy ra:** Business validation chưa đầy đủ.

**Ảnh hưởng production:** Quantity âm có thể làm tăng inventory; quantity 0 có thể tạo reservation vô nghĩa.

**Cách sửa:** Validate `quantity > 0` và upper bound/business rules trước khi chạm database.

### High — Không có durable representation của operation outcome

**Vấn đề:** Khi timeout xảy ra, client không có cách chắc chắn query theo `clientRequestId` để biết reservation đã commit chưa.

**Tại sao xảy ra:** API contract tập trung vào request-response thay vì operation identity.

**Ảnh hưởng production:** Client retries dựa trên phỏng đoán, tạo duplicate hoặc UX mơ hồ.

**Cách sửa:** Cho phép lookup theo stable idempotency key hoặc trả resource id deterministic. Retry cùng key phải trả cùng logical result.

### Medium — Error handling không phân biệt concurrency conflict, insufficient inventory và transient dependency failure

**Vấn đề:** Method để exceptions đi thẳng lên mà không có domain-specific mapping.

**Tại sao xảy ra:** Technical failure và business conflict bị trộn chung.

**Ảnh hưởng production:** Client có thể retry sai loại lỗi; observability khó phân biệt sold-out với service degradation.

**Cách sửa:** Map rõ business outcome, concurrency conflict, duplicate idempotent request và transient infrastructure failure. Retry policy chỉ áp dụng cho nhóm lỗi phù hợp.

### Medium — Logging thiếu operation identity và concurrency evidence

**Vấn đề:** Log chỉ có event/user/quantity.

**Tại sao xảy ra:** Không log `clientRequestId`, reservation id, attempt, ETag/version hay outcome category.

**Ảnh hưởng production:** Khó điều tra duplicate và timeline race.

**Cách sửa:** Log structured metadata tối thiểu: `eventId`, `clientRequestId`, reservation id, old/new inventory, attempt number, conflict/duplicate/committed outcome, correlation id. Không log token hoặc dữ liệu nhạy cảm không cần thiết.

### Medium — Hai round trips trước commit làm race window rộng hơn

**Vấn đề:** Business flow read inventory rồi replace rồi create qua các network calls tách biệt.

**Tại sao xảy ra:** Application orchestration thay cho transactional primitive phù hợp datastore.

**Ảnh hưởng production:** Tăng latency và tăng cửa sổ race/failure giữa các bước.

**Cách sửa:** Dùng transactional batch khi tất cả state cùng partition. Nếu future model đặt data qua nhiều partitions thì phải thiết kế workflow khác; không thể giả định batch cross-partition.

## Phiên bản đề xuất

Một hướng phù hợp là dùng stable reservation id từ `clientRequestId`, đọc inventory cùng ETag và commit inventory + reservation trong transactional batch của cùng `eventId` partition.

```csharp
public sealed class BookingService
{
    private readonly Container _container;
    private readonly ILogger<BookingService> _logger;

    public BookingService(
        CosmosClient cosmosClient,
        ILogger<BookingService> logger)
    {
        _container = cosmosClient.GetContainer("booking-db", "booking");
        _logger = logger;
    }

    public async Task<ReservationDocument> ReserveAsync(
        string eventId,
        string userId,
        int quantity,
        string clientRequestId,
        CancellationToken cancellationToken)
    {
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        if (string.IsNullOrWhiteSpace(clientRequestId))
            throw new ArgumentException("clientRequestId is required", nameof(clientRequestId));

        var partitionKey = new PartitionKey(eventId);
        var reservationId = $"reservation:{clientRequestId}";

        try
        {
            var existing = await _container.ReadItemAsync<ReservationDocument>(
                reservationId,
                partitionKey,
                cancellationToken: cancellationToken);

            return existing.Resource;
        }
        catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
        {
        }

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            var inventoryResponse = await _container.ReadItemAsync<InventoryDocument>(
                $"inventory:{eventId}",
                partitionKey,
                cancellationToken: cancellationToken);

            var inventory = inventoryResponse.Resource;

            if (inventory.RemainingSeats < quantity)
                throw new InvalidOperationException("Not enough seats");

            var updatedInventory = inventory with
            {
                RemainingSeats = inventory.RemainingSeats - quantity,
                UpdatedAt = DateTimeOffset.UtcNow
            };

            var reservation = new ReservationDocument
            {
                Id = reservationId,
                EventId = eventId,
                UserId = userId,
                Quantity = quantity,
                ClientRequestId = clientRequestId,
                CreatedAt = DateTimeOffset.UtcNow
            };

            var batch = _container.CreateTransactionalBatch(partitionKey)
                .ReplaceItem(
                    updatedInventory.Id,
                    updatedInventory,
                    new TransactionalBatchItemRequestOptions
                    {
                        IfMatchEtag = inventoryResponse.ETag
                    })
                .CreateItem(reservation);

            var result = await batch.ExecuteAsync(cancellationToken);

            if (result.IsSuccessStatusCode)
            {
                _logger.LogInformation(
                    "Booking committed for event {EventId}, request {ClientRequestId}, reservation {ReservationId}, attempt {Attempt}",
                    eventId,
                    clientRequestId,
                    reservationId,
                    attempt);

                return reservation;
            }

            if (result.StatusCode == HttpStatusCode.Conflict)
            {
                try
                {
                    var existing = await _container.ReadItemAsync<ReservationDocument>(
                        reservationId,
                        partitionKey,
                        cancellationToken: cancellationToken);

                    return existing.Resource;
                }
                catch (CosmosException ex) when (ex.StatusCode == HttpStatusCode.NotFound)
                {
                    continue;
                }
            }

            if (result.StatusCode == HttpStatusCode.PreconditionFailed)
                continue;

            throw new InvalidOperationException(
                $"Booking batch failed with status {result.StatusCode}");
        }

        throw new InvalidOperationException(
            "Booking could not be committed due to concurrent updates");
    }
}
```

Đoạn trên minh họa design, không áp đặt retry count `3` như một production constant. Số attempt, backoff và timeout cần dựa trên expected contention, latency budget và behavior của SDK/service. Nếu conflict cao kéo dài trong ticket-release spike, chỉ tăng retry count có thể làm contention nặng hơn.

Stable reservation id làm cho cùng `clientRequestId` map về cùng logical reservation. Nếu request đã commit nhưng response bị mất, retry có thể đọc lại document cũ thay vì tạo effect mới.

Transactional batch chỉ phù hợp vì inventory và reservation cùng logical partition `eventId`. Nếu future architecture phân tán inventory và booking state qua các partition keys khác nhau, phải thay transaction model; không nên giả định Cosmos có cross-partition ACID batch cho scenario này.

## Giải thích thiết kế sau khi sửa

ETag biến stale read thành detectable conflict. Khi một request khác đã cập nhật inventory, conditional replace không được phép silently overwrite version mới.

Transactional batch làm inventory decrement và reservation create commit hoặc fail cùng nhau trong một partition. Nhờ đó không có intermediate state “đã trừ ghế nhưng chưa có reservation”.

Idempotency key được đưa vào document identity, nên client retry cùng `clientRequestId` không tạo một document mới. Đây là business-level idempotency, không chỉ HTTP retry policy.

Retry chỉ xảy ra khi failure category có thể hợp lý để thử lại, ví dụ optimistic concurrency conflict. Retry vẫn phải bounded và quan sát được; contention cao có thể yêu cầu queueing, admission control hoặc business design khác thay vì infinite retries.

## Trade-offs

Optimistic concurrency hoạt động tốt khi conflict rate thấp đến vừa. Khi hàng nghìn users tranh cùng inventory rất nhỏ, repeated read-conflict-retry có thể tăng RU và latency. Khi đó cần đo contention và cân nhắc queue/serialization theo event, nhưng complexity chỉ đáng thêm khi evidence cho thấy cần.

Dùng `eventId` làm partition key giúp transaction boundary tự nhiên cho event booking, nhưng hot event có thể tập trung workload vào cùng logical partition. Partition design phải cân bằng transactional locality với scalability; không có partition key “đúng tuyệt đối” cho mọi access pattern.

Deterministic reservation id dựa trên `clientRequestId` yêu cầu contract client tạo key unique theo logical action và reuse đúng key khi retry. Nếu client generate key mới mỗi retry thì idempotency mất tác dụng.

Lookup idempotency trước batch thêm một read. Có thể tối ưu flow bằng create-first/batch semantics khác nếu profiling chứng minh read overhead đáng kể, nhưng correctness nên được giữ rõ ràng trước khi tối ưu.

## Cách kiểm thử

1. **Concurrency test:** khởi tạo `RemainingSeats = 10`, chạy đồng thời 100 requests quantity 1 với `clientRequestId` khác nhau; xác minh đúng 10 reservations commit và inventory bằng 0, không âm.
2. **Idempotency integration test:** gửi cùng `clientRequestId` 20 lần song song; xác minh chỉ có một reservation và inventory chỉ bị trừ một lần.
3. **Failure-path test:** mô phỏng request commit thành công nhưng client không nhận response; retry cùng idempotency key phải trả reservation cũ mà không trừ inventory lần hai.
4. **Conflict/load test:** tăng concurrency trên một hot event, đo conflict rate, RU consumption, p95/p99 latency và số retry/attempt trước khi quyết định tuning.
5. **Cancellation test:** hủy request trước commit và sau khi service có thể đã commit; xác minh API contract cho phép client resolve outcome bằng `clientRequestId`.

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì dùng shared state và timing cố định

**Chủ đề:** Playwright, TypeScript, E2E testing, parallel execution, test isolation, deterministic waits, shared test data, selectors, CI reliability, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core + React/Vue back-office portal có Playwright E2E suite chạy trong CI trước khi deploy.

Các tests dùng chung một staging environment và một test account. CI cấu hình nhiều workers để giảm thời gian chạy.

Production pipeline chưa bị block hoàn toàn bởi flaky tests vì team thường rerun job cho đến khi pass.

Triệu chứng:

- suite pass gần như 100% trên laptop nhưng fail ngẫu nhiên 5–15% trên CI;
- lỗi thường là “element not found”, “expected 1 row, received 2”, hoặc timeout sau 3 giây;
- rerun thường pass mà không có code change;
- hai tests đôi lúc tạo cùng customer `qa@example.com`;
- test delete có thể xóa record mà test khác đang dùng;
- CI screenshots cho thấy trang vẫn loading khi assertion bắt đầu;
- team tăng `waitForTimeout(3000)` lên `10000` và thấy fail ít hơn nhưng pipeline chậm hơn;
- một developer đề xuất chạy toàn bộ suite với `workers: 1` để hết flaky.

Mục tiêu là giữ được parallelism hợp lý nhưng làm tests deterministic và cô lập.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test'

const email = 'qa@example.com'

test('create customer', async ({ page }) => {
  await page.goto('/customers')

  await page.click('text=New Customer')
  await page.fill('#name', 'QA Customer')
  await page.fill('#email', email)
  await page.click('text=Save')

  await page.waitForTimeout(3000)

  await page.goto('/customers')
  await page.fill('#search', email)
  await page.waitForTimeout(3000)

  const rows = page.locator('table tbody tr')
  await expect(rows).toHaveCount(1)
})

test('edit customer', async ({ page }) => {
  await page.goto('/customers')
  await page.fill('#search', email)
  await page.waitForTimeout(3000)

  await page.locator('table tbody tr').first().click()
  await page.fill('#name', 'QA Customer Updated')
  await page.click('text=Save')

  await page.waitForTimeout(3000)

  await expect(page.locator('#name')).toHaveValue('QA Customer Updated')
})

test('delete customer', async ({ page }) => {
  await page.goto('/customers')
  await page.fill('#search', email)
  await page.waitForTimeout(3000)

  await page.locator('table tbody tr').first().click()
  await page.click('text=Delete')
  await page.click('text=Confirm')

  await page.waitForTimeout(3000)

  await page.goto('/customers')
  await page.fill('#search', email)
  await page.waitForTimeout(3000)

  await expect(page.locator('table tbody tr')).toHaveCount(0)
})
```

## Nhiệm vụ của ứng viên

1. Xác định các nguyên nhân làm suite flaky khi chạy parallel trên CI.
2. Phân tích vì sao ba tests có hidden dependency về execution order dù không khai báo dependency.
3. Chỉ ra rủi ro của shared email và shared staging data.
4. Đánh giá `waitForTimeout` và giải thích vì sao tăng từ 3 giây lên 10 giây không giải quyết root cause.
5. Review cách selector `text=...`, `#name`, `table tbody tr`.first() ảnh hưởng reliability/maintainability.
6. Đề xuất cách tạo test data unique và cleanup an toàn.
7. Đề xuất cách chờ theo observable UI/network state thay vì fixed sleep.
8. Đánh giá trade-off của `workers: 1`: trường hợp nào hữu ích để chẩn đoán và vì sao không nên coi là fix mặc định.
9. Đề xuất cấu trúc tests độc lập để mỗi test tự setup đúng precondition.
10. Nêu CI artifacts/telemetry cần lưu để điều tra flaky tests nhanh hơn.

## Câu hỏi gợi mở

1. Playwright có bảo đảm `create customer` chạy trước `edit customer` không khi tests có thể chạy parallel?
2. Nếu hai workers cùng dùng `qa@example.com`, test nào sở hữu record đó?
3. Fixed timeout đang chờ một event cụ thể hay chỉ đang hy vọng hệ thống hoàn tất trước khi đồng hồ hết?
4. `first()` có đang xác nhận đúng business entity hay chỉ chọn row đầu tiên tình cờ match?
5. Khi API save trả chậm 8 giây nhưng UI có loading indicator, cách chờ nào phản ánh intent tốt hơn `waitForTimeout(10000)`?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **test isolation** và **synchronization theo tín hiệu thật**, không phải đơn thuần timeout quá ngắn.

### Gợi ý 2

Một E2E test ổn định cần sở hữu data của chính nó, biết rõ khi nào precondition đã sẵn sàng, và assert theo stable contract thay vì phụ thuộc timing/order ngẫu nhiên.

## Kết quả code review tham khảo

### High — Ba tests phụ thuộc shared state nhưng runner có thể chạy độc lập/parallel

**Vấn đề:** `edit customer` và `delete customer` giả định record từ `create customer` đã tồn tại.

**Tại sao xảy ra:** Test suite encode workflow qua side effect của test khác thay vì setup precondition riêng.

**Ảnh hưởng production/CI:** Thứ tự chạy thay đổi hoặc worker khác nhau khiến test fail ngẫu nhiên. Rerun có thể pass vì data cũ vẫn tồn tại, làm false confidence cao hơn.

**Cách sửa:** Mỗi test phải tự tạo dữ liệu nó cần qua API fixture/setup hoặc UI nếu chính create flow là behavior cần test. Không dùng một test làm setup cho test khác trừ khi deliberately dùng serial workflow và chấp nhận trade-off đó.

### High — Dùng chung `qa@example.com` gây collision giữa workers và runs

**Vấn đề:** Tất cả tests/runs dùng cùng business key.

**Tại sao xảy ra:** Test data không có namespace theo run/worker/test.

**Ảnh hưởng production/CI:** Duplicate rows, unique-constraint failures, test này sửa/xóa record của test khác, stale data từ run trước làm assertion sai.

**Cách sửa:** Generate unique identifier, ví dụ `qa+${runId}-${workerIndex}-${random}@example.test`, và cleanup theo entity id do test sở hữu.

### High — `waitForTimeout` là synchronization dựa trên thời gian chứ không dựa trên state

**Vấn đề:** Test ngủ 3 giây rồi giả định backend/UI đã hoàn tất.

**Tại sao xảy ra:** Fixed sleep không biết request nhanh hay chậm, render đã xong hay chưa.

**Ảnh hưởng production/CI:** Máy nhanh thì lãng phí thời gian; máy chậm thì vẫn flaky. Tăng lên 10 giây chỉ đổi xác suất fail và kéo dài pipeline.

**Cách sửa:** Chờ deterministic signal: `expect(locator).toBeVisible()`, URL transition, toast success, response phù hợp, loading indicator biến mất, hoặc row với exact test id xuất hiện.

### High — `.first()` che giấu ambiguity thay vì verify đúng entity

**Vấn đề:** Test chọn row đầu tiên dù có thể có nhiều matches.

**Tại sao xảy ra:** Selector không gắn với unique data của test.

**Ảnh hưởng production/CI:** Test có thể sửa/xóa nhầm record và vẫn pass một phần, gây cascading failures.

**Cách sửa:** Locate theo unique email/id và assert exactly one matching row trước khi click.

### Medium — Selector theo text generic dễ drift hoặc match nhầm

**Vấn đề:** `text=Save`, `text=Delete`, `text=Confirm` có thể match nhiều button/link hoặc thay đổi theo localization/UI wording.

**Tại sao xảy ra:** Selector chưa dựa trên semantic role/test contract.

**Ảnh hưởng production/CI:** UI refactor nhỏ làm test fail không liên quan business behavior.

**Cách sửa:** Ưu tiên `getByRole('button', { name: 'Save' })`, accessible labels, hoặc `data-testid` khi không có semantic selector ổn định.

### Medium — Cleanup không ownership-aware

**Vấn đề:** Delete test xóa theo email shared, không theo resource id mà chính test tạo.

**Tại sao xảy ra:** Data lifecycle không gắn với fixture/test context.

**Ảnh hưởng production/CI:** Một test có thể xóa fixture của test khác hoặc data staging dùng bởi manual QA.

**Cách sửa:** Tạo data qua test API với unique id, lưu id trong fixture và cleanup chính resource đó trong teardown/finally.

### Medium — Assertions không verify đúng transition sau save/delete

**Vấn đề:** Sau save, code chỉ sleep rồi navigate/assert; không xác nhận save request thành công hay UI đã nhận persisted state.

**Tại sao xảy ra:** Workflow thiếu observable completion contract.

**Ảnh hưởng production/CI:** Test failure location xa root cause, làm triage chậm.

**Cách sửa:** Assert success toast/state hoặc wait for specific response rồi mới bước tiếp. Sau delete, chờ row biến mất hoặc API confirmation thay vì fixed sleep.

### Medium — Rerun-until-pass che giấu defect signal

**Vấn đề:** Pipeline coi rerun pass như quality gate đủ tốt.

**Tại sao xảy ra:** Flakiness được operationally tolerated thay vì quantified/fixed.

**Ảnh hưởng production/CI:** Regression thật có thể được “healed” bởi retry, team mất niềm tin vào suite và bỏ qua failures.

**Cách sửa:** Track flaky rate theo test, quarantine có expiry/owner nếu bắt buộc, lưu trace/artifacts và ưu tiên root-cause. Retry có thể là diagnostic/temporary mitigation, không phải definition of success duy nhất.

### Medium — `workers: 1` chỉ che concurrency problem

**Vấn đề:** Serializing suite giảm collision nhưng không sửa data ownership hoặc fixed waits.

**Tại sao xảy ra:** Giảm concurrency làm race ít xuất hiện hơn.

**Ảnh hưởng production/CI:** Pipeline chậm đáng kể và bug có thể quay lại khi parallelism tăng.

**Cách sửa:** Dùng single worker tạm thời để isolate diagnosis nếu cần; production suite nên giữ parallelism sau khi data isolation/synchronization được sửa.

### Low — Thiếu artifacts đủ để điều tra race

**Vấn đề:** Chỉ screenshot cuối failure không cho biết request sequence, DOM state hay timing.

**Tại sao xảy ra:** CI diagnostics chưa capture trace/network/video/log context phù hợp.

**Ảnh hưởng production/CI:** Mất nhiều thời gian rerun local để reproduce.

**Cách sửa:** Lưu Playwright trace on first retry/failure, screenshot, video khi cần, console errors, request/response timing, test data id và CI run metadata.

## Phiên bản đề xuất

Ví dụ dưới đây dùng API setup để mỗi test sở hữu một customer riêng. Endpoint/helper cụ thể là scenario abstraction; trong project thật nên dùng test fixture/service đã có thay vì duplicate HTTP setup logic ở mọi file.

```ts
import { test, expect, APIRequestContext } from '@playwright/test'

async function createCustomer(
  request: APIRequestContext,
  suffix: string
) {
  const email = `qa+${suffix}@example.test`

  const response = await request.post('/api/test/customers', {
    data: {
      name: `QA Customer ${suffix}`,
      email
    }
  })

  expect(response.ok()).toBeTruthy()

  const customer = await response.json() as {
    id: string
    email: string
  }

  return customer
}

async function deleteCustomer(
  request: APIRequestContext,
  id: string
) {
  const response = await request.delete(`/api/test/customers/${id}`)

  if (!response.ok() && response.status() !== 404) {
    throw new Error(`Cleanup failed: ${response.status()}`)
  }
}

test('edit customer', async ({ page, request }, testInfo) => {
  const suffix = `${testInfo.workerIndex}-${Date.now()}-${Math.random()
    .toString(36)
    .slice(2)}`

  const customer = await createCustomer(request, suffix)

  try {
    await page.goto('/customers')

    await page.getByLabel('Search').fill(customer.email)

    const row = page.getByRole('row', { name: new RegExp(customer.email) })
    await expect(row).toHaveCount(1)
    await row.click()

    await page.getByLabel('Name').fill(`QA Updated ${suffix}`)

    const saveResponse = page.waitForResponse(response =>
      response.url().includes(`/api/customers/${customer.id}`) &&
      response.request().method() === 'PUT' &&
      response.ok()
    )

    await page.getByRole('button', { name: 'Save' }).click()
    await saveResponse

    await expect(page.getByText('Customer saved')).toBeVisible()
    await expect(page.getByLabel('Name')).toHaveValue(`QA Updated ${suffix}`)
  } finally {
    await deleteCustomer(request, customer.id)
  }
})
```

Nếu system không có test-only API, có thể seed qua database fixture hoặc public API thật tùy architecture. Mục tiêu là setup nhanh, deterministic và sở hữu rõ resource. Test create flow vẫn nên dùng UI để verify create feature; các tests khác không cần lặp UI create chỉ để setup.

`waitForResponse` cũng không phải universal answer. Nếu implementation chuyển từ REST sang background save hoặc GraphQL, selector này có thể coupling quá chặt. Tín hiệu ưu tiên nên là user-observable completion contract; network wait chỉ dùng khi nó phản ánh đúng behavior cần test.

## Giải thích thiết kế sau khi sửa

Mỗi test tạo unique data nên parallel workers không tranh một record. Resource id được giữ để cleanup đúng ownership.

Selectors dựa trên accessible role/label giúp test gần với user interaction hơn và thường ổn định hơn CSS implementation details.

Test chờ một observable completion signal thay vì chờ số milliseconds cố định. Điều này làm test nhanh khi app nhanh và vẫn đúng khi CI chậm nhưng nằm trong configured expect timeout.

Setup qua API giảm thời gian và tránh biến tests unrelated thành một chuỗi workflow dài. UI create có thể được test riêng như một behavior độc lập.

## Trade-offs

API fixture nhanh và deterministic nhưng có thể bypass một số UI integration path. Vì vậy cần cân bằng: setup bằng API cho tests không quan tâm create UI, còn create feature có test E2E riêng.

Unique data làm staging tích lũy records nếu cleanup fail. Cần TTL/test-data janitor hoặc cleanup robust theo run namespace, đặc biệt khi CI bị terminate giữa chừng.

Selectors theo role phụ thuộc accessibility semantics đúng. Đây thường là lợi ích kép, nhưng legacy UI có thể cần `data-testid` cho các control chưa có accessible role/name tốt.

Giữ parallelism làm test environment chịu load cao hơn. Nếu staging backend không đủ capacity, phải phân biệt test flakiness do shared state với environment saturation dựa trên metrics, thay vì hạ workers một cách mù quáng.

## Cách kiểm thử

1. **Parallel-repeat test:** chạy file/suite nhiều lần với nhiều workers; xác minh không collision dữ liệu và flaky rate về mức chấp nhận được.
2. **Slow-backend test:** inject delay 5–8 giây cho save/search; test vẫn chờ đúng state thay vì fail vì hard-coded 3 giây.
3. **Isolation test:** hai workers cùng chạy edit/delete trên unique customers; mỗi worker chỉ tác động resource do chính nó tạo.
4. **Failure diagnostics validation:** cố tình làm API trả 500 và xác minh CI lưu trace, screenshot, console/network evidence đủ để tìm root cause.
5. **Cleanup test:** force assertion fail giữa test rồi xác minh `finally`/fixture teardown vẫn cleanup resource hoặc resource được janitor xử lý.

## Quan sát trong production/CI

Theo dõi:

- pass/fail/flaky retry rate theo test name;
- duration p50/p95 theo test và suite;
- worker count và queue time;
- trace/screenshot/video path gắn với CI run id;
- API latency/error rate của staging trong lúc suite chạy;
- số test data tạo/xóa theo run namespace;
- duplicate-key/conflict rate trong staging;
- browser console errors;
- request timeline cho failed tests;
- top tests theo số lần retry trong 7/30 ngày.

Đặt threshold để test có flaky rate vượt mức cho phép phải có owner và action, thay vì vô thời hạn rerun-until-green.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Read-modify-write trên distributed datastore cần concurrency control; không được giả định write sau cùng vẫn đúng business invariant.
- ETag/optimistic concurrency giúp phát hiện stale state, còn transactional batch giải quyết atomicity khi các operations nằm cùng Cosmos DB logical partition.
- Retry chỉ an toàn khi operation được thiết kế idempotent; timeout có thể tạo trạng thái “không biết đã commit hay chưa”.
- In-memory lock không phải distributed coordination primitive khi application chạy nhiều instances.
- Playwright flakiness thường đến từ shared state, hidden ordering và synchronization theo thời gian thay vì theo state thực.
- Parallel E2E tests cần ownership rõ ràng cho test data và diagnostics đủ để phân biệt race condition với environment saturation.

## Mẫu tư duy cần nhớ

- **Concurrency invariant phải được enforce ở nơi state được sở hữu.**
- **Thiết kế retry cùng idempotency, không thêm retry sau cùng.**
- **Atomicity, concurrency control và idempotency là ba vấn đề khác nhau.**
- **Test phải sở hữu data của chính nó.**
- **Chờ observable state, không chờ bằng hy vọng + sleep.**
