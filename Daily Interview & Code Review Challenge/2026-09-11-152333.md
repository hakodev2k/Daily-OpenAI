# Code Review Challenge 1 — Cosmos DB chạy ổn lúc nhỏ nhưng RU tăng mạnh và p95 vọt khi tenant lớn dần

**Chủ đề:** C#/.NET 8, Azure Cosmos DB for NoSQL, partition key, cross-partition query, continuation token, pagination, RU consumption, multi-tenant data access, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một multi-tenant SaaS lưu activity history trong Azure Cosmos DB for NoSQL. Mỗi document có dạng rút gọn:

```json
{
  "id": "8d6f...",
  "tenantId": "tenant-42",
  "userId": "user-901",
  "status": "Completed",
  "createdAtUtc": "2026-09-11T07:30:00Z",
  "type": "ApprovalCompleted",
  "payload": { }
}
```

Container hiện được tạo với partition key `/status` vì team cho rằng UI thường filter theo trạng thái.

Yêu cầu:

- mọi request phải được scope theo `tenantId`;
- UI chủ yếu xem activity mới nhất của một tenant;
- một tenant lớn có thể có hàng chục triệu documents;
- write rate phân bố không đều theo thời gian nhưng `Completed` chiếm phần lớn;
- API trả 100 records mỗi page;
- người dùng chủ yếu Next/Previous, không cần nhảy tới page số 10.000;
- production cần theo dõi RU/request, throttling, p95/p99 và hot-partition symptoms;
- không muốn redesign storage nếu chưa có evidence, nhưng hiện production đã bắt đầu throttling.

Triệu chứng:

- khi dữ liệu còn nhỏ, endpoint thường dưới 200 ms;
- sau vài tháng, p95 tăng lên vài giây;
- RU/request tăng mạnh theo kích thước container;
- `429 Too Many Requests` xuất hiện dù tổng provisioned throughput vẫn còn headroom ở một số thời điểm;
- tenant lớn bị ảnh hưởng nặng hơn tenant nhỏ;
- page sâu chậm rõ rệt;
- team đề xuất tăng RU/s toàn container và thêm retry nhiều hơn.

## Đoạn code cần review

```csharp
public sealed class ActivityRepository
{
    private readonly Container _container;

    public ActivityRepository(CosmosClient client)
    {
        _container = client.GetContainer("app", "activities");
    }

    public async Task<IReadOnlyList<ActivityDto>> SearchAsync(
        string tenantId,
        string? status,
        int pageNumber,
        int pageSize,
        CancellationToken cancellationToken)
    {
        var queryText = $"""
            SELECT *
            FROM c
            WHERE c.tenantId = '{tenantId}'
              AND ('{status}' = '' OR c.status = '{status}')
            ORDER BY c.createdAtUtc DESC
            OFFSET {(pageNumber - 1) * pageSize}
            LIMIT {pageSize}
            """;

        var iterator = _container.GetItemQueryIterator<ActivityDto>(
            queryText,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = pageSize
            });

        var results = new List<ActivityDto>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            results.AddRange(page.Resource);
        }

        return results;
    }
}
```

## Câu hỏi gợi mở

1. Query có equality filter trên `tenantId`, nhưng partition key thật sự là `/status`; request được route tới đâu?
2. Low-cardinality partition key như `status` ảnh hưởng phân phối write/load như thế nào khi một status chiếm đa số?
3. `OFFSET` page sâu yêu cầu query engine bỏ qua bao nhiêu dữ liệu trước khi trả page hiện tại?
4. String interpolation trong query ảnh hưởng correctness/security/query-plan reuse ra sao?
5. `while (iterator.HasMoreResults)` có đang trả đúng “một page UI” hay đang đọc hết toàn bộ feed của query?

## Gợi ý

### Gợi ý 1

Primary risk là **partition key không align với tenant-centric access pattern**, khiến query thường fan-out và write load tập trung vào một số logical partitions.

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Partition key `/status` là low-cardinality và không align với tenant-centric workload

**Vấn đề:**  
Container partitioned theo `status`, trong khi hầu hết reads được scope theo `tenantId`, còn writes lại dồn mạnh vào giá trị phổ biến như `Completed`.

**Tại sao xảy ra:**  
Partition key quyết định logical partition và routing. Một key có ít distinct values làm dữ liệu/load dễ tập trung. Query không filter equality đúng partition key phải thực hiện cross-partition work thay vì route trực tiếp theo tenant.

**Ảnh hưởng production:**  
RU tăng theo số partitions phải tham gia, latency tăng, một logical partition có thể trở thành hot spot dù tổng throughput toàn container nhìn vẫn chưa dùng hết đều.

**Cách sửa:**  
Thiết kế partition key theo dominant access pattern và cardinality. Với workload chủ yếu “activity của một tenant”, `/tenantId` là baseline hợp lý nếu kích thước/throughput mỗi tenant nằm trong giới hạn phù hợp. Nếu một tenant đơn lẻ có thể quá lớn hoặc quá nóng, đánh giá hierarchical partition key như `TenantId -> UserId` hoặc một synthetic strategy dựa trên query patterns thực tế. Không đổi partition key chỉ bằng cảm tính; đo workload và migration cost trước.

### High — Query không được target tới partition cụ thể

**Vấn đề:**  
`QueryRequestOptions` không truyền `PartitionKey`, và container hiện partition theo `status`.

**Tại sao xảy ra:**  
Filter `tenantId` không giúp single-partition routing khi partition key là `status`.

**Ảnh hưởng production:**  
Query phải fan-out qua nhiều physical partitions. Khi container lớn hơn, chi phí và tail latency tăng rõ rệt.

**Cách sửa:**  
Sau khi schema/partitioning align với tenant, truyền partition key tương ứng trong request options khi query thuộc một tenant. Với hierarchical partition key, dùng prefix/full key phù hợp với query pattern.

### High — `while (iterator.HasMoreResults)` đọc hết kết quả thay vì một UI page

**Vấn đề:**  
Code tạo iterator rồi tiếp tục đọc đến khi query hết kết quả.

**Tại sao xảy ra:**  
`MaxItemCount` chỉ điều khiển page size của feed, không có nghĩa loop chỉ chạy một lần.

**Ảnh hưởng production:**  
Một request UI có thể vô tình materialize rất nhiều records, tăng RU, latency và memory. Với query rộng, đây có thể là root cause lớn hơn cả serialization.

**Cách sửa:**  
Đọc đúng một feed page cho mỗi API page, trả `ContinuationToken` cho client và dùng token đó cho request kế tiếp.

### High — `OFFSET/LIMIT` không phù hợp deep pagination

**Vấn đề:**  
API dùng page number và `OFFSET` cho workload mà người dùng chủ yếu Next/Previous.

**Tại sao xảy ra:**  
Deep offset buộc query engine xử lý/bỏ qua ngày càng nhiều kết quả trước page đích.

**Ảnh hưởng production:**  
Page 1 nhanh nhưng page 5.000 có thể rất tốn RU và latency.

**Cách sửa:**  
Dùng continuation-token pagination của Cosmos DB. API trả opaque token cho next page; client không cần hiểu token. Nếu business thật sự bắt buộc arbitrary page jumps, cần thiết kế riêng và chấp nhận cost/trade-off rõ ràng.

### High — Query được build bằng string interpolation

**Vấn đề:**  
`tenantId` và `status` được chèn trực tiếp vào Cosmos SQL text.

**Tại sao xảy ra:**  
Input có thể phá query syntax hoặc tạo injection-like behavior; query text cũng thay đổi theo từng request thay vì parameterized shape ổn định.

**Ảnh hưởng production:**  
Security/correctness risk, khó logging và khó reasoning về query shape.

**Cách sửa:**  
Dùng `QueryDefinition` với parameters.

### Medium — Optional-filter expression tạo query shape không tối ưu

**Vấn đề:**  
`('{status}' = '' OR c.status = '{status}')` nhét optional logic vào query string.

**Tại sao xảy ra:**  
Khi status không có, predicate trở thành rộng; khi có, query vẫn phụ thuộc partition/data model hiện tại. Nó cũng làm code khó đọc và khó kiểm thử.

**Ảnh hưởng production:**  
Query behavior khó dự đoán, đặc biệt khi status distribution lệch.

**Cách sửa:**  
Xây query có điều kiện với parameter rõ ràng; quan trọng hơn, giải quyết partitioning trước khi micro-optimize predicate.

### Medium — Không validate page parameters

**Vấn đề:**  
`pageNumber <= 0`, `pageSize <= 0` hoặc page size rất lớn chưa bị chặn.

**Tại sao xảy ra:**  
Boundary validation thiếu.

**Ảnh hưởng production:**  
Có thể tạo invalid query, integer overflow ở offset hoặc request cực đắt.

**Cách sửa:**  
Nếu chuyển sang continuation token, bỏ `pageNumber`; giới hạn `pageSize` theo contract hợp lý.

### Medium — Không expose RU và continuation metadata

**Vấn đề:**  
Repository bỏ qua `RequestCharge`, continuation token và diagnostics.

**Tại sao xảy ra:**  
Telemetry quan trọng của Cosmos request không được đưa vào result/metrics.

**Ảnh hưởng production:**  
Team chỉ thấy API chậm nhưng không biết request nào đắt, partition nào bị nóng hoặc query nào fan-out.

**Cách sửa:**  
Capture `RequestCharge`, latency, diagnostics/traces phù hợp và continuation token; aggregate metrics theo endpoint/query shape/tenant class thay vì log raw sensitive IDs khi không cần.

### Medium — Retry không sửa được partitioning issue

**Vấn đề:**  
Team muốn tăng retry khi gặp throttling.

**Tại sao xảy ra:**  
SDK có retry behavior cho throttling theo policy/configuration, nhưng retry chỉ delay/re-attempt; nó không làm query rẻ hơn hay phân phối load lại.

**Ảnh hưởng production:**  
Retry quá aggressive có thể tăng tail latency và tạo thêm pressure trong incident.

**Cách sửa:**  
Đầu tiên đo RU/query, hot partition và routing. Sau đó mới điều chỉnh throughput/retry budget theo SLO và workload.

## Phiên bản đề xuất

Ví dụ sau giả định container mới được thiết kế với partition key `/tenantId`. Nếu một tenant đơn lẻ có thể quá lớn/hot, cần đánh giá hierarchical partition key thay vì copy nguyên mẫu này.

```csharp
public sealed record ActivityPage(
    IReadOnlyList<ActivityDto> Items,
    string? ContinuationToken,
    double RequestCharge);

public sealed class ActivityRepository
{
    private readonly Container _container;

    public ActivityRepository(CosmosClient client)
    {
        _container = client.GetContainer("app", "activities-v2");
    }

    public async Task<ActivityPage> SearchAsync(
        string tenantId,
        string? status,
        int pageSize,
        string? continuationToken,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(tenantId))
            throw new ArgumentException("Tenant is required.", nameof(tenantId));

        pageSize = Math.Clamp(pageSize, 1, 100);

        var sql = """
            SELECT c.id,
                   c.tenantId,
                   c.userId,
                   c.status,
                   c.createdAtUtc,
                   c.type
            FROM c
            WHERE c.tenantId = @tenantId
            """;

        if (!string.IsNullOrWhiteSpace(status))
            sql += " AND c.status = @status";

        sql += " ORDER BY c.createdAtUtc DESC";

        var query = new QueryDefinition(sql)
            .WithParameter("@tenantId", tenantId);

        if (!string.IsNullOrWhiteSpace(status))
            query.WithParameter("@status", status);

        using var iterator = _container.GetItemQueryIterator<ActivityDto>(
            query,
            continuationToken,
            new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(tenantId),
                MaxItemCount = pageSize
            });

        if (!iterator.HasMoreResults)
            return new ActivityPage([], null, 0);

        var response = await iterator.ReadNextAsync(cancellationToken);

        return new ActivityPage(
            response.Resource.ToList(),
            response.ContinuationToken,
            response.RequestCharge);
    }
}
```

## Giải thích thiết kế sau khi sửa

Microsoft documentation hiện tại mô tả rằng query có equality filter phù hợp partition key có thể được route tới partition liên quan, còn query không có partition-key filter phải fan-out qua physical partitions. Documentation cũng cảnh báo low-cardinality keys có thể tạo phân phối workload/storage không đều. Vì vậy sửa quan trọng nhất là align partitioning với access pattern, không phải chỉ tối ưu câu SQL.

Continuation token phù hợp với Next/Previous-style navigation hơn page number. API nên coi token là opaque. Nếu product yêu cầu back navigation, frontend có thể giữ stack các token đã đi qua thay vì biến token thành page index toàn cục.

Nếu một tenant có thể vượt scale envelope của một logical partition, `/tenantId` đơn thuần có thể chưa đủ. Khi đó cần đánh giá hierarchical partition key hoặc synthetic strategy dựa trên query patterns; tránh random suffix nếu nó làm mất khả năng route các query chính.

## Trade-offs

- `/tenantId` giúp tenant-scoped reads rẻ hơn nhưng một “whale tenant” có thể trở thành hotspot riêng.
- Hierarchical partition key cải thiện scale cho tenant lớn nhưng data model/query routing phức tạp hơn.
- Continuation token hiệu quả hơn deep OFFSET nhưng không hỗ trợ arbitrary page-number jump tự nhiên.
- Repartition/migrate container có operational cost và cần dual-write/backfill/cutover strategy nếu production không thể downtime.
- Tăng RU/s có thể vẫn cần sau khi sửa data model, nhưng khi đó capacity increase dựa trên measured workload thay vì che architectural inefficiency.

## Cách kiểm thử

1. **Integration test theo partitioning:** seed nhiều tenants, xác minh tenant-scoped query chỉ trả đúng dữ liệu tenant và sử dụng partition key đúng.
2. **Load test skewed distribution:** một tenant lớn, nhiều tenant nhỏ, status `Completed` chiếm đa số; đo RU/request, p95/p99 và throttling trước/sau redesign.
3. **Pagination test:** đọc hàng nghìn pages bằng continuation token, xác minh không duplicate/missing record trong điều kiện dataset snapshot phù hợp với consistency assumptions.
4. **Failure-path test:** inject throttling/transient errors; xác minh retry budget không tạo request latency vô hạn và cancellation được propagate.
5. **Security test:** tenant A không thể query tenant B bằng cách thay route/query parameter.

## Quan sát trong production

Theo dõi:

- RU/request theo endpoint và query shape;
- `429` rate, retry count và retry delay;
- p50/p95/p99 latency;
- request charge distribution theo tenant size bucket;
- cross-partition/query diagnostics khi cần điều tra;
- hot-partition indicators và normalized RU consumption;
- continuation-token usage/page depth;
- request cancellation;
- alerts khi RU/request hoặc throttling tăng sau deployment.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một tenant chiếm 60% traffic toàn hệ thống, `/tenantId` còn là partition key đủ tốt không?
2. Nếu business cần query cross-tenant theo `userId`, bạn sẽ xử lý access pattern thứ hai như thế nào mà không phá primary workload?
3. Khi nào bạn chấp nhận cross-partition query thay vì redesign data model?

# Code Review Challenge 2 — Vue search hiển thị kết quả cũ sau khi user gõ nhanh và vô tình mở đường cho XSS

**Chủ đề:** Vue 3, TypeScript, Composition API, `watch`, async race condition, `AbortController`, stale responses, API load, XSS, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một Vue 3 admin portal có ô search customer. Khi user gõ, frontend gọi `/api/customers/search?q=...` và hiển thị kết quả được backend trả về.

Yêu cầu:

- kết quả phải luôn tương ứng với query mới nhất;
- user có thể gõ nhanh hoặc xóa/chuyển query liên tục;
- API có rate limit và production traffic cao;
- component có thể unmount khi user chuyển route;
- backend trả `displayName` dạng plain text, không phải trusted HTML;
- nếu request cũ hoàn thành sau request mới, nó không được overwrite state mới;
- loading/error state phải phản ánh request hiện tại;
- production cần biết request count per search, cancellation rate, frontend errors và API p95.

Triệu chứng:

- user gõ `alice`, đôi lúc UI lại hiển thị kết quả của `ali`;
- API nhận nhiều request hơn số thao tác tìm kiếm mà product team mong đợi;
- khi network chậm, spinner đôi lúc biến mất dù request mới vẫn đang chạy;
- chuyển route nhanh có thể tạo console errors;
- security review phát hiện frontend render `displayName` bằng `v-html` vì team muốn highlight keyword.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type Customer = {
  id: string
  displayName: string
}

const query = ref('')
const customers = ref<Customer[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch(query, async (value) => {
  if (!value.trim()) {
    customers.value = []
    return
  }

  loading.value = true
  error.value = null

  try {
    const response = await fetch(
      `/api/customers/search?q=${value}`
    )

    if (!response.ok)
      throw new Error(`HTTP ${response.status}`)

    customers.value = await response.json()
  } catch (e) {
    error.value = (e as Error).message
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <input v-model="query" placeholder="Search customers" />

  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>

  <ul>
    <li v-for="customer in customers" :key="customer.id">
      <span v-html="customer.displayName"></span>
    </li>
  </ul>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong async state management.
2. Xác định performance, security, reliability và maintainability concerns.
3. Giải thích production impact khi user gõ nhanh, network reorder response hoặc component unmount.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected implementation/design.
6. Giải thích testing cho stale-response race, cancellation, XSS và high typing rate.
7. Đề xuất production telemetry để chứng minh frontend behavior đã đúng.

## Câu hỏi gợi mở

1. Nếu request cho `ali` bắt đầu trước nhưng hoàn thành sau request `alice`, state cuối cùng là gì?
2. `finally { loading = false }` của request cũ có thể ảnh hưởng request mới như thế nào?
3. `fetch` cũ có được cancel khi watcher chạy lại hoặc component unmount không?
4. Query parameter đã được encode chưa?
5. `v-html` có phù hợp khi backend contract nói `displayName` là plain text không?

## Gợi ý

### Gợi ý 1

Primary risk là **nhiều async requests cùng ghi vào một reactive state mà không có ownership/cancellation semantics**.

### Gợi ý 2

Vue cung cấp cleanup semantics cho watcher; kết hợp cleanup với `AbortController` hoặc request-sequence guard để stale request không được commit state.

## Kết quả code review tham khảo

### Critical — `v-html` render dữ liệu plain text tạo XSS surface

**Vấn đề:**  
`customer.displayName` được đưa trực tiếp vào `v-html`.

**Tại sao xảy ra:**  
`v-html` yêu cầu nội dung HTML đáng tin cậy/sanitized. Contract hiện tại nói `displayName` là plain text, nên render như HTML là vượt trust boundary cần thiết.

**Ảnh hưởng production:**  
Nếu dữ liệu chứa markup/script payload hoặc backend/source data bị compromise, browser có thể render HTML nguy hiểm trong context của ứng dụng.

**Cách sửa:**  
Render text bằng interpolation `{{ customer.displayName }}`. Nếu highlight keyword là requirement, split text thành text nodes/segments và render bằng template bindings; chỉ dùng sanitizer nếu thật sự cần render rich HTML từ nguồn được kiểm soát.

### High — Stale response có thể overwrite kết quả mới

**Vấn đề:**  
Mỗi lần query đổi tạo request mới, nhưng request cũ vẫn có quyền set `customers.value`.

**Tại sao xảy ra:**  
Network responses không bảo đảm hoàn thành theo thứ tự request bắt đầu.

**Ảnh hưởng production:**  
User thấy kết quả không khớp input hiện tại, có thể thao tác nhầm customer.

**Cách sửa:**  
Cancel stale request bằng `AbortController` khi watcher invalidates, và/hoặc dùng monotonically increasing request ID để chỉ request mới nhất được commit state.

### High — Request cũ có thể tắt `loading` của request mới

**Vấn đề:**  
Mọi invocation đều chạy `finally { loading.value = false }`.

**Tại sao xảy ra:**  
`loading` là shared state nhưng không gắn với request identity.

**Ảnh hưởng production:**  
Spinner biến mất trong khi request mới vẫn chạy, tạo UI state sai và khó debug.

**Cách sửa:**  
Chỉ request hiện tại được update loading/error/result, hoặc track active request token/id.

### High — Không cancel side effect khi watcher invalidates

**Vấn đề:**  
Watcher không đăng ký cleanup cho request đang chạy.

**Tại sao xảy ra:**  
`fetch` tiếp tục dù query đã đổi. Vue watcher có cleanup semantics; request cần chủ động nối vào đó.

**Ảnh hưởng production:**  
API nhận request thừa, rate limit dễ bị hit, browser giữ network work không còn giá trị.

**Cách sửa:**  
Trong `watch`, tạo `AbortController`; dùng `onCleanup(() => controller.abort())` và truyền `signal` vào `fetch`. Official Vue documentation mô tả cleanup cho async side effects chính xác cho stale-request scenario này.

### High — Không debounce input

**Vấn đề:**  
Mỗi keystroke tạo một request ngay lập tức.

**Tại sao xảy ra:**  
Reactive update rate của input cao hơn mức API call product cần.

**Ảnh hưởng production:**  
Request amplification, tăng server load, rate-limit pressure và làm race window rộng hơn.

**Cách sửa:**  
Debounce query theo UX requirement, ví dụ 200–300 ms như một scenario assumption cần đo/test. Không hard-code delay chỉ vì “best practice”; chọn theo perceived latency và API capacity.

### Medium — Query parameter không được encode

**Vấn đề:**  
`value` được nối trực tiếp vào URL.

**Tại sao xảy ra:**  
Các ký tự như `&`, `?`, `#`, Unicode đặc biệt có thể thay đổi URL semantics.

**Ảnh hưởng production:**  
Search sai hoặc request malformed.

**Cách sửa:**  
Dùng `URLSearchParams` hoặc `encodeURIComponent`.

### Medium — Abort bị coi như application error

**Vấn đề:**  
Nếu thêm cancellation mà catch tất cả error như nhau, `AbortError` sẽ hiện thành error UI.

**Tại sao xảy ra:**  
User typing/navigation cancellation là expected control flow, không phải dependency failure.

**Ảnh hưởng production:**  
UI nháy lỗi và telemetry bị noise.

**Cách sửa:**  
Phân biệt abort/cancellation với network/server error.

### Medium — Empty query không reset toàn bộ state

**Vấn đề:**  
Nhánh empty chỉ clear `customers`, nhưng có thể để lại `error` hoặc loading từ invocation trước nếu request không được cleanup đúng.

**Tại sao xảy ra:**  
State transition không được thiết kế theo request lifecycle.

**Ảnh hưởng production:**  
UI có thể hiển thị stale error/spinner khi input đã trống.

**Cách sửa:**  
Cleanup request cũ và set state nhất quán cho empty query.

### Medium — Không có response schema validation

**Vấn đề:**  
`await response.json()` được cast ngầm sang expected structure mà không validate.

**Tại sao xảy ra:**  
TypeScript type không validate runtime JSON.

**Ảnh hưởng production:**  
Backend contract regression có thể tạo render errors hoặc invalid state khó chẩn đoán.

**Cách sửa:**  
Với boundary quan trọng, validate minimal response shape hoặc dùng generated/schema-driven client. Không cần thêm runtime schema library nếu risk thấp và contract đã được kiểm soát bằng typed client/testing.

### Low — Error message hiển thị trực tiếp technical detail

**Vấn đề:**  
UI hiển thị raw `Error.message`.

**Tại sao xảy ra:**  
Technical detail và user-facing message bị trộn.

**Ảnh hưởng production:**  
UX kém và có thể expose thông tin không cần thiết nếu error message về sau chứa detail nhạy cảm.

**Cách sửa:**  
Map error thành user-safe message; giữ technical detail trong telemetry.

## Phiên bản đề xuất

Ví dụ sau dùng `watch` cleanup + `AbortController`, request identity và debounce tối thiểu. Nếu project đã có query/data-fetching library chuẩn hóa, có thể centralize behavior ở đó thay vì lặp trong component.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type Customer = {
  id: string
  displayName: string
}

const query = ref('')
const customers = ref<Customer[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let requestVersion = 0

watch(query, (rawValue, _oldValue, onCleanup) => {
  const value = rawValue.trim()
  const version = ++requestVersion
  const controller = new AbortController()

  let timer: ReturnType<typeof setTimeout> | undefined

  onCleanup(() => {
    if (timer)
      clearTimeout(timer)

    controller.abort()
  })

  if (!value) {
    customers.value = []
    error.value = null
    loading.value = false
    return
  }

  timer = setTimeout(async () => {
    if (version !== requestVersion)
      return

    loading.value = true
    error.value = null

    try {
      const params = new URLSearchParams({ q: value })
      const response = await fetch(
        `/api/customers/search?${params.toString()}`,
        { signal: controller.signal }
      )

      if (!response.ok)
        throw new Error(`HTTP ${response.status}`)

      const data = await response.json() as Customer[]

      if (version === requestVersion)
        customers.value = data
    } catch (e) {
      if (controller.signal.aborted)
        return

      if (version === requestVersion)
        error.value = 'Unable to load customers.'
    } finally {
      if (version === requestVersion)
        loading.value = false
    }
  }, 250)
})
</script>

<template>
  <input v-model="query" placeholder="Search customers" />

  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>

  <ul>
    <li v-for="customer in customers" :key="customer.id">
      <span>{{ customer.displayName }}</span>
    </li>
  </ul>
</template>
```

Nếu cần highlight keyword, có thể build an array of safe text segments và render từng segment bằng interpolation, ví dụ normal text + `<mark>{{ segment }}</mark>`, thay vì nhét backend string vào `v-html`.

## Giải thích thiết kế sau khi sửa

Vue official documentation mô tả watcher cleanup như cơ chế để hủy stale async side effect khi watched source thay đổi. `AbortController` giúp browser ngừng request cũ; request version đóng vai trò guard bổ sung để stale completion không ghi state trong trường hợp cancellation không đủ để suy luận business ownership.

Debounce giảm request amplification nhưng là UX/performance trade-off. Nếu search API rất nhanh và product muốn instant search, delay có thể ngắn hơn; nếu mobile latency cao/rate limit chặt, delay có thể dài hơn hoặc search chỉ chạy sau số ký tự tối thiểu.

Security fix quan trọng nhất là giữ plain text ở dạng text. Highlighting requirement không biện minh cho mở HTML trust boundary.

## Trade-offs

- Abort + request-version guard làm code nhiều state hơn nhưng semantics rõ hơn.
- Debounce giảm API load nhưng thêm perceived latency.
- Centralized composable/query library giảm duplication nhưng có thể quá mức nếu chỉ một màn hình cần behavior này.
- Runtime response validation tăng safety nhưng thêm code/runtime cost.
- Sanitization cho `v-html` có maintenance/security cost; nếu data chỉ là text thì không render HTML là giải pháp đơn giản và an toàn hơn.

## Cách kiểm thử

1. **Race-condition test:** mock `ali` trả sau `alice`; xác minh UI cuối cùng luôn hiển thị `alice`.
2. **Cancellation test:** đổi query liên tục/chuyển route; xác minh stale requests bị abort và không tạo error UI.
3. **Load/browser test:** mô phỏng typing nhanh 10–20 ký tự; xác minh số API requests nằm trong debounce contract thay vì một request cho mỗi keystroke.
4. **Security test:** backend trả `displayName` chứa `<img onerror=...>` hoặc markup; xác minh browser render text, không execute HTML/script.
5. **Error-state test:** request cũ fail sau request mới success; xác minh error/loading của request cũ không overwrite state hiện tại.

## Quan sát trong production

Theo dõi:

- API calls per search session / per keystroke;
- cancellation/abort rate;
- frontend search latency từ input đến stable result;
- API p50/p95/p99 và rate-limit responses;
- stale-response guard count nếu instrumented;
- frontend unhandled promise/runtime errors;
- user-safe error rate;
- correlation ID/request ID giữa browser telemetry và backend traces;
- alert nếu request amplification hoặc API throttling tăng sau frontend release.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search được chuyển sang server-side rendering hoặc route-driven search, lifecycle/cancellation design sẽ thay đổi thế nào?
2. Nếu backend trả highlighted HTML hợp lệ theo requirement, bạn sẽ thiết kế trust boundary và sanitization ở đâu?
3. Khi nào bạn dùng một data-fetching library thay vì tự quản lý watcher/request state trong component?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB partitioning phải align với workload: high cardinality chưa đủ, query routing và hot-partition risk mới là trọng tâm.
- Cross-partition query và deep pagination có thể khiến RU/latency tăng theo scale; tăng throughput không tự sửa access pattern kém.
- Continuation-token pagination phù hợp hơn page-number pagination cho feed lớn và Next/Previous workflow.
- Frontend async request cũng có distributed-ordering problem ở quy mô nhỏ: response cũ có thể đến sau response mới và ghi đè state.
- Vue watcher cleanup + `AbortController` giúp quản lý stale side effects; request ownership vẫn cần được thể hiện rõ.
- `v-html` là trust-boundary decision, không phải chỉ là convenience API để format text.

## Mẫu tư duy cần nhớ

- Align data partitioning với dominant access pattern trước khi tăng capacity.
- Đo RU/latency theo query shape trước khi tối ưu.
- Treat pagination như một scalability decision, không chỉ UI concern.
- Mỗi async side effect cần lifecycle và ownership rõ ràng.
- Không mở rộng trust boundary chỉ để giải quyết presentation requirement.
