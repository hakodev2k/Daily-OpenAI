# Code Review Challenge 1 — Refresh token bị dùng chéo giữa các phiên

**Chủ đề:** ASP.NET Core 8, Microsoft Entra ID/OIDC, distributed session, authorization  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một BFF ASP.NET Core phục vụ React SPA. Người dùng đăng nhập qua OIDC; access token dành cho downstream API và refresh token được lưu trong distributed Redis session. BFF chạy 4 instances sau Azure App Service load balancer. Khi người dùng mở nhiều tabs hoặc logout đồng thời với API request, một số request trả 401, một số phiên vẫn gọi API sau logout. Security yêu cầu không gửi access/refresh token xuống browser, mọi request phải được phân quyền theo user hiện tại; token refresh có thể rotation và token endpoint có thể timeout. Đoạn code sau được rút gọn; giả định cookie authentication và Redis session đã cấu hình.

## Đoạn code cần review

```csharp
public sealed class TokenForwarder
{
    private readonly IHttpContextAccessor _accessor;
    private readonly IHttpClientFactory _factory;
    private readonly IDistributedCache _cache;

    public TokenForwarder(IHttpContextAccessor accessor,
        IHttpClientFactory factory, IDistributedCache cache)
    {
        _accessor = accessor;
        _factory = factory;
        _cache = cache;
    }

    public async Task<string> GetProfileAsync(string userId)
    {
        var context = _accessor.HttpContext!;
        var cacheKey = $"token:{userId}";
        var accessToken = await _cache.GetStringAsync(cacheKey);
        if (accessToken == null)
        {
            var refreshToken = await _cache.GetStringAsync($"refresh:{userId}");
            var client = _factory.CreateClient("identity");
            var response = await client.PostAsync("/oauth/token",
                new FormUrlEncodedContent(new Dictionary<string, string>
                {
                    ["grant_type"] = "refresh_token",
                    ["refresh_token"] = refreshToken ?? ""
                }));
            response.EnsureSuccessStatusCode();
            var tokens = await response.Content
                .ReadFromJsonAsync<TokenResponse>();
            accessToken = tokens!.AccessToken;
            await _cache.SetStringAsync(cacheKey, accessToken,
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
                });
            await _cache.SetStringAsync($"refresh:{userId}",
                tokens.RefreshToken);
        }

        var api = _factory.CreateClient("profile");
        api.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);
        var result = await api.GetAsync($"/users/{userId}/profile");
        result.EnsureSuccessStatusCode();
        return await result.Content.ReadAsStringAsync();
    }
}

public record TokenResponse(string AccessToken, string RefreshToken);
```

## Kết quả code review tham khảo

### [Critical] — Broken object-level authorization

**Vấn đề:** Method nhận `userId` tùy ý rồi dùng nó để truy cập token và profile.  
**Tại sao xảy ra:** Không ràng buộc path parameter với authenticated principal và quyền đọc profile.  
**Ảnh hưởng production:** IDOR, có thể đọc profile người khác nếu caller điều khiển userId.  
**Cách sửa:** Derive identity từ validated principal; đối với truy cập hộ người khác phải kiểm tra policy và resource authorization ở BFF lẫn downstream.

### [Critical] — Token store không phân tách session

**Vấn đề:** Key chỉ theo user, không theo phiên/client/tenant.  
**Tại sao xảy ra:** Nhiều login cùng user dùng chung refresh token; logout một phiên ảnh hưởng hoặc không thu hồi đúng phiên khác.  
**Ảnh hưởng production:** Session confusion, sai phạm vi revoke, khó audit.  
**Cách sửa:** Dùng opaque server-side session ID, partition theo tenant và session; liên kết với principal, issuer, audience và token family.

### [High] — Concurrent refresh phá token rotation

**Vấn đề:** Cache miss làm nhiều requests refresh cùng lúc.  
**Tại sao xảy ra:** Read–refresh–write không atomic; provider có thể invalidated refresh token cũ sau rotation.  
**Ảnh hưởng production:** Invalid grant, logout hàng loạt, token family bị thu hồi tùy provider.  
**Cách sửa:** Per-session single-flight phối hợp liên instance bằng lease/fencing hoặc atomic CAS; reread sau lock, ghi token pair atomically.

### [High] — TTL không dựa vào token expiry

**Vấn đề:** Cache access token cố định một giờ.  
**Tại sao xảy ra:** Bỏ qua `expires_in`, clock skew, revoked/short-lived token.  
**Ảnh hưởng production:** 401 kéo dài, retry storm.  
**Cách sửa:** Persist expiry chính xác và refresh sớm có jitter; không mặc định JWT luôn có cùng lifetime.

### [High] — Logout không được kiểm tra trong luồng refresh

**Vấn đề:** Request đang chạy có thể ghi token mới sau khi session bị xóa.  
**Tại sao xảy ra:** Không có session version/revocation check trước commit.  
**Ảnh hưởng production:** Phiên đã logout có thể sống lại.  
**Cách sửa:** Session generation/fencing; verify active state trong atomic write, revoke upstream nếu được hỗ trợ.

### [High] — Token lưu thô trong Redis

**Vấn đề:** Token nhạy cảm không được bảo vệ theo threat model.  
**Tại sao xảy ra:** Thiếu encryption at rest/application envelope, ACL, TLS và retention policy được xác nhận.  
**Ảnh hưởng production:** Redis compromise có thể làm lộ bearer credentials.  
**Cách sửa:** Harden Redis; mã hóa token ở application layer khi phù hợp; tuyệt đối không log token.

### [Medium] — Không truyền cancellation/timeout budget

**Vấn đề:** Network call không dùng `RequestAborted` và deadline tổng.  
**Tại sao xảy ra:** API handler không kiểm soát vòng đời outbound request.  
**Ảnh hưởng production:** Resource consumption và request treo sau client disconnect.  
**Cách sửa:** Truyền CancellationToken, cấu hình per-dependency timeout và bounded retry cho lỗi transient phù hợp.

### [Medium] — Xử lý lỗi refresh thiếu phân loại

**Vấn đề:** `EnsureSuccessStatusCode` biến mọi lỗi thành exception chung.  
**Tại sao xảy ra:** Không phân biệt invalid_grant, 429, 5xx và ambiguous timeout.  
**Ảnh hưởng production:** Xóa session sai hoặc retry quá mức.  
**Cách sửa:** Phân loại; invalid_grant yêu cầu reauthentication, transient retry có backoff có giới hạn; kiểm tra trạng thái token family khi outcome không rõ.

### [Medium] — Thiếu validation token response và downstream scope

**Vấn đề:** Tin payload không kiểm tra null, expiry, scope/audience; trả raw JSON.  
**Tại sao xảy ra:** Thiếu contract validation và response shaping.  
**Ảnh hưởng production:** Null failure, overexposure dữ liệu và sai quyền.  
**Cách sửa:** Validate OAuth response; downstream API xác minh issuer/audience/scope; trả DTO tối thiểu.

### [Low] — Thiếu correlation và audit

**Vấn đề:** Không ghi outcome refresh và session lifecycle.  
**Tại sao xảy ra:** Không instrument dependency/span hoặc outcome metrics.  
**Ảnh hưởng production:** Khó phân biệt lỗi IdP, race và user logout.  
**Cách sửa:** Log session hash, correlation ID, outcome code; không log token/PII.

## Phiên bản đề xuất

Thiết kế dưới đây là pseudocode C# có interface theo contract; không giả định Redis hỗ trợ transaction/CAS trực tiếp qua `IDistributedCache`. `ITokenSessionStore` phải triển khai atomicity bằng backend có conditional update và fencing.

```csharp
public sealed class ProfileService(
    ITokenSessionStore sessions,
    ITokenRefresher refresher,
    IHttpClientFactory clients)
{
    public async Task<ProfileDto> GetMineAsync(
        ClaimsPrincipal principal, string sessionId,
        CancellationToken ct)
    {
        var subject = principal.FindFirst("sub")?.Value
            ?? throw new UnauthorizedAccessException();
        var issuer = principal.FindFirst("iss")?.Value
            ?? throw new UnauthorizedAccessException();

        var session = await sessions.RequireActiveAsync(
            sessionId, issuer, subject, ct);

        if (session.ExpiresAt <= DateTimeOffset.UtcNow.AddMinutes(2))
        {
            await using var lease =
                await sessions.AcquireRefreshLeaseAsync(sessionId, ct);
            session = await sessions.RequireActiveAsync(
                sessionId, issuer, subject, ct);

            if (session.ExpiresAt <= DateTimeOffset.UtcNow.AddMinutes(2))
            {
                var next = await refresher.RefreshAsync(
                    session.RefreshToken, ct);
                await sessions.CompareAndSwapActiveAsync(
                    sessionId, session.Version, lease.FencingToken,
                    next, ct);
                session = await sessions.RequireActiveAsync(
                    sessionId, issuer, subject, ct);
            }
        }

        using var request = new HttpRequestMessage(
            HttpMethod.Get, "/me/profile");
        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", session.AccessToken);
        using var response = await clients.CreateClient("profile")
            .SendAsync(request, ct);
        response.EnsureSuccessStatusCode();
        return (await response.Content.ReadFromJsonAsync<ProfileDto>(
            cancellationToken: ct))!;
    }
}
```

Contract quan trọng: `CompareAndSwapActiveAsync` chỉ commit khi session vẫn active, version khớp và lease còn hợp lệ; token pair được ghi cùng nhau. Cần xử lý kết quả CAS thất bại bằng reread/re-auth, không retry refresh mù quáng. `ProfileDto`, session types và IdP integration là application-specific.

## Giải thích thiết kế sau khi sửa

Authentication principal được xác minh trước; session binding và authorization là hai lớp riêng. Token rotation chỉ có một writer hợp lệ cho mỗi session, refresh expiry được quản lý theo dữ liệu IdP. BFF giữ token server-side và downstream API vẫn tự enforce scopes.

## Trade-offs

Distributed lease/CAS tăng chi phí và độ phức tạp; với ít concurrency có thể dùng managed authentication/token-management library đã chứng minh hỗ trợ rotation thay vì tự xây. Lease không bảo đảm exactly-once đối với IdP; cần quyết định khi timeout và xác minh provider behavior. Không nên dùng distributed lock như bằng chứng authorization.

## Cách kiểm thử

1. **Security test:** Caller A yêu cầu profile B, tenant khác và session khác; tất cả bị từ chối.
2. **Concurrency test:** 100 requests trên 4 instances với một token sắp hết hạn; không có stale overwrite.
3. **Failure-path test:** IdP timeout sau refresh, 429, invalid_grant; kết quả phân loại và bounded.
4. **Race test:** Logout trong lúc refresh; không có token mới commit sau revoke.
5. **Integration test:** Token expiry, scope và downstream 401 với clock skew.

## Quan sát trong production

Application Insights dependency traces theo IdP/downstream; metrics `refresh_attempts`, `refresh_conflicts`, `invalid_grant`, `session_revoked`, p95 latency và 401 ratio; alert khi refresh conflict/401 tăng đột biến. Log correlation và session fingerprint không đảo ngược, tuyệt đối không lưu token.

## Câu hỏi phỏng vấn mở rộng

1. Khi Redis outage, fail closed hay cho phép grace period? Phân tích security và availability.
2. Khi IdP không hỗ trợ refresh rotation hoặc revocation, thay đổi thiết kế ra sao?
3. BFF session cookie cần bảo vệ CSRF như thế nào nếu dùng cookie authentication?

```csharp
[ApiController]
[Route("content")]
public class PageController : ControllerBase
{
    private readonly IPageStore _store;
    private readonly IMemoryCache _cache;

    public PageController(IPageStore store, IMemoryCache cache)
    {
        _store = store;
        _cache = cache;
    }

    [HttpGet("{slug}")]
    public async Task<IActionResult> Get(
        string slug, string? language, bool preview = false)
    {
        var key = $"page:{slug}";
        if (!_cache.TryGetValue(key, out PageModel? page))
        {
            page = await _store.LoadAsync(slug, language, preview);
            if (page == null) return NotFound();

            _cache.Set(key, page, TimeSpan.FromHours(12));
        }

        Response.Headers.CacheControl = "public,max-age=86400";
        Response.Headers["Surrogate-Control"] = "max-age=86400";
        Response.Headers["X-Page-Id"] = page.Id.ToString();

        return Ok(new
        {
            page.Title,
            page.BodyHtml,
            page.CanonicalUrl,
            page.Robots,
            page.PublishedAt
        });
    }
}

public sealed record PageModel(
    Guid Id, string Title, string BodyHtml,
    string CanonicalUrl, string Robots,
    DateTimeOffset PublishedAt);
```

## Kết quả code review tham khảo

### [Critical] — Preview content có thể bị cache public

**Vấn đề:** Preview request đi qua cùng endpoint và trả `public` headers.  
**Tại sao xảy ra:** Không tách authenticated preview và published delivery.  
**Ảnh hưởng production:** Draft hoặc embargoed content có thể bị lộ qua shared cache.  
**Cách sửa:** Preview phải được authorize, no-store tại browser/shared CDN và không dùng shared origin cache.

### [High] — Cache key bỏ qua locale và preview

**Vấn đề:** Key chỉ gồm slug.  
**Tại sao xảy ra:** Content variant và publication state không có trong identity của cache.  
**Ảnh hưởng production:** Sai ngôn ngữ, draft lẫn live, metadata/canonical sai.  
**Cách sửa:** Key gồm site/tenant, content identity, language, publication version và variant; preview bypass shared cache.

### [High] — Unpublish không invalidate cache

**Vấn đề:** Entry sống 12 giờ tại origin, 24 giờ tại edge.  
**Tại sao xảy ra:** TTL không liên kết lifecycle publish/unpublish.  
**Ảnh hưởng production:** Content hết quyền xuất bản vẫn truy cập được.  
**Cách sửa:** Invalidate on publish/unpublish, purge theo surrogate key; với nội dung nhạy cảm cần origin authorization và fail-safe, không chỉ purge best effort.

### [High] — Cache-Control public cho mọi response

**Vấn đề:** Không phân biệt personalized/authenticated và public.  
**Tại sao xảy ra:** Header unconditional; CDN policy chưa được xác minh.  
**Ảnh hưởng production:** Cache poisoning/leak nếu response phụ thuộc cookie/identity.  
**Cách sửa:** Chỉ cache representation hoàn toàn public; enforce edge bypass cho authorization/cookies và preview.

### [High] — Không kiểm tra published window

**Vấn đề:** Trust `LoadAsync` mà không có explicit contract đảm bảo published state và access.  
**Tại sao xảy ra:** Repository có thể trả scheduled, expired hoặc restricted content.  
**Ảnh hưởng production:** Sai lịch hiển thị và disclosure.  
**Cách sửa:** Public query contract bắt buộc filter publish status, time window, access rights; test tại boundary.

### [Medium] — Cache incoherence giữa instances

**Vấn đề:** IMemoryCache riêng từng replica.  
**Tại sao xảy ra:** Purge một instance không invalidate replicas khác.  
**Ảnh hưởng production:** User thấy nội dung khác nhau giữa requests.  
**Cách sửa:** Pub/sub invalidation hoặc versioned keys; cân nhắc bỏ origin cache nếu CDN đã đủ.

### [Medium] — Cache stampede sau purge

**Vấn đề:** Concurrent cache misses cùng gọi CMS store.  
**Tại sao xảy ra:** Không có request coalescing hoặc bounded concurrency.  
**Ảnh hưởng production:** Origin/database spike, p99 tăng.  
**Cách sửa:** Per-key single-flight tại origin, jitter và backpressure; đo trước khi thêm distributed cache.

### [Medium] — SEO metadata không được validate

**Vấn đề:** Canonical/robots từ model có thể stale hoặc không đúng locale.  
**Tại sao xảy ra:** Không kiểm tra URL normalization, canonical ownership và publish state.  
**Ảnh hưởng production:** Duplicate indexing hoặc index nhầm trang.

### [Medium] — Thiếu failure strategy cho purge

**Tại sao xảy ra:** Publishing và CDN invalidation là hai hệ thống độc lập.  
**Ảnh hưởng production:** Stale content kéo dài khi purge API lỗi.

### [Low] — Thiếu observability

**Vấn đề:** Không biết response đến từ cache nào hay version nào.

**Ảnh hưởng production:** Không phân biệt stale origin và stale edge.

## Phiên bản đề xuất

Thiết kế mẫu sau chỉ dùng public published query, bypass preview và cache theo immutable version. `IPublishedPageStore` có trách nhiệm enforce publish window, ACL và locale. `IContentVersionIndex` cập nhật khi publish/unpublish, `IPreviewPageStore` phải authorize riêng.

```csharp
[ApiController]
[Route("content")]
public sealed class PublishedPagesController(
    IPublishedPageStore pages,
    IContentVersionIndex versions,
    IMemoryCache cache) : ControllerBase
{
    [HttpGet("{site}/{language}/{slug}")]
    public async Task<IActionResult> Get(
        string site, string language, string slug,
        CancellationToken ct)
    {
        var current = await versions.GetCurrentAsync(
            site, language, slug, ct);
        if (current is null)
        {
            Response.Headers.CacheControl = "no-store";
            return NotFound();
        }

        var key = $"public:{site}:{language}:{slug}:{current.Version}";
        var page = await cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow =
                TimeSpan.FromMinutes(2);
            return await pages.LoadPublishedAsync(
                site, language, slug, current.Version, ct);
        });

        if (page is null)
        {
            Response.Headers.CacheControl = "no-store";
            return NotFound();
        }

        Response.Headers.CacheControl = "public,max-age=60";
        Response.Headers["Surrogate-Key"] = $"content-{page.Id:N}";
        Response.Headers["X-Content-Version"] = current.Version;
        return Ok(new PublicPageDto(
            page.Title, page.BodyHtml,
            page.CanonicalUrl, page.Robots));
    }
}
```

Đây là sketch, không phải drop-in compile: `IPublishedPageStore`, `IContentVersionIndex`, `PublicPageDto` và `Version` là domain contracts. `GetOrCreateAsync` không đảm bảo single-flight; production cần bổ sung nếu đo thấy stampede. Nếu edge purge không có guarantee, TTL ngắn giới hạn stale exposure nhưng **không** đủ cho yêu cầu xóa ngay lập tức; khi đó cần edge bypass/authorization hoặc cơ chế delivery khác. `BodyHtml` phải được sanitize theo trust boundary và CMS editor policy trước khi render vào browser.

## Giải thích thiết kế sau khi sửa

Tách published và preview endpoints; content version làm cache key ổn định, site/language là dimensions bắt buộc. CMS publish event tạo invalidation durable; Akamai purge là bước asynchronous có monitoring. Origin không dựa vào CDN để enforce authorization.

## Trade-offs

TTL 60 giây tăng origin requests so với 24 giờ; purge và version index tăng complexity. Nếu site public chịu stale tối đa vài phút, CDN TTL ngắn có thể đủ mà không cần event pipeline. Với embargoed content cần kiểm soát mạnh hơn. Không mặc định Redis hoặc microservices.

## Cách kiểm thử

1. **Security test:** Draft/preview không xuất hiện qua public endpoint hay shared cache.
2. **Integration test:** Hai locales cùng slug luôn trả đúng content và canonical.
3. **Lifecycle test:** Publish, schedule, unpublish và rollback không để lộ stale sensitive content.
4. **Failure-path test:** Akamai purge timeout/429, retry và reconciliation không mất event.
5. **Load test:** 1000 concurrent misses sau purge, đo CMS query count và p99.

## Quan sát trong production

Akamai cache hit/miss và purge completion lag; origin metrics hit ratio, cache key cardinality, CMS query count, p95/p99; structured logs gồm content ID/version, site, locale, publish state (không log draft body); alert khi edge version khác expected version quá freshness SLO. Dùng Lighthouse và crawler checks cho canonical/robots, không xem Lighthouse là bằng chứng cache correctness.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business yêu cầu unpublish có hiệu lực dưới 5 giây trên toàn cầu, bạn xác minh những guarantee nào?
2. Khi chuyển từ traditional Optimizely rendering sang headless React, cache ownership và SEO rendering thay đổi thế nào?
3. Nếu CDN purge API outage 30 phút, chọn biện pháp giảm rủi ro nào trước?
