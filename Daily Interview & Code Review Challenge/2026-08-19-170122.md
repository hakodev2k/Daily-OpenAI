# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý các cấu hình offboarding đã hết hạn. Job chạy định kỳ, tìm các bản ghi `EmployeeOffboardingMailConfig` đã đến `EndTime`, gọi Exchange/Microsoft 365 qua một abstraction `IExchangeService`, sau đó đánh dấu cấu hình đã reset.

Production có nhiều Hangfire worker. Thỉnh thoảng cùng một mailbox bị reset hai lần, audit history có bản ghi trùng, một số config vẫn ở trạng thái `Pending` dù thao tác Exchange đã thành công. Khi Microsoft 365 chậm hoặc timeout, số retry tăng mạnh.

## Đoạn code cần review

```csharp
public sealed class ResetExpiredOffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<ResetExpiredOffboardingJob> _logger;

    public ResetExpiredOffboardingJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<ResetExpiredOffboardingJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteAsync()
    {
        var now = DateTime.UtcNow;

        var configs = await _db.EmployeeOffboardingMailConfigs
            .Where(x => x.Status == "Pending" && x.EndTime <= now)
            .Take(100)
            .ToListAsync();

        foreach (var config in configs)
        {
            try
            {
                await _exchange.ResetMailboxAsync(config.UserEmail);

                config.Status = "Completed";
                config.CompletedAt = DateTime.UtcNow;

                _db.EmployeeOffboardingMailConfigHistories.Add(new()
                {
                    ConfigId = config.Id,
                    Action = "Reset",
                    CreatedAt = DateTime.UtcNow
                });

                await _db.SaveChangesAsync();
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Failed resetting mailbox {Email}", config.UserEmail);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Hai worker có thể xử lý cùng một config

- **Problem:** Query `Pending` rồi xử lý không có cơ chế claim/lock.
- **Why:** Read và transition trạng thái là hai bước tách rời; nhiều worker có thể cùng đọc một row.
- **Impact:** Reset mailbox và ghi history nhiều lần.
- **Severity:** Critical.
- **Fix:** Claim row atomically ở database hoặc dùng optimistic concurrency/conditional update; chỉ worker claim thành công mới tiếp tục.

### 2. External side effect và database commit không atomic

- **Problem:** Exchange có thể thành công nhưng `SaveChangesAsync` thất bại.
- **Why:** DB transaction không thể rollback một API call đã hoàn tất ở external system.
- **Impact:** DB vẫn `Pending`, Hangfire retry và gọi Exchange lần nữa.
- **Severity:** Critical.
- **Fix:** Thiết kế operation idempotent, lưu operation/idempotency key và reconcile trạng thái thay vì giả định distributed transaction.

### 3. Không có idempotency contract

- **Problem:** `ResetMailboxAsync(email)` không thể hiện identity của business operation.
- **Why:** Retry không phân biệt được thao tác đã hoàn thành hay chưa.
- **Impact:** Duplicate side effect hoặc dữ liệu audit sai.
- **Severity:** High.
- **Fix:** Dùng stable operation ID/config ID; external adapter nên kiểm tra desired state hoặc hỗ trợ idempotent semantics nếu có thể.

### 4. Re-throw làm dừng toàn bộ batch

- **Problem:** Một config lỗi khiến các config phía sau không được xử lý trong run hiện tại.
- **Why:** `throw` thoát khỏi vòng lặp.
- **Impact:** Head-of-line blocking và backlog tăng.
- **Severity:** High.
- **Fix:** Tốt hơn là enqueue một job cho từng config hoặc xử lý failure riêng với retry policy có giới hạn.

### 5. Không có cancellation/timeout boundary rõ ràng

- **Problem:** Job không nhận `CancellationToken` và external call không thể hiện timeout/cancellation.
- **Impact:** Shutdown/deploy có thể kéo dài; worker bị giữ lâu khi dependency chậm.
- **Severity:** Medium.
- **Fix:** Propagate cancellation nơi framework/integration hỗ trợ và cấu hình timeout ở HTTP/client layer.

### 6. Batch selection không có ordering

- **Problem:** `Take(100)` không `OrderBy`.
- **Impact:** Không đảm bảo fairness; record cũ có thể bị trì hoãn tùy execution plan/data churn.
- **Severity:** Medium.
- **Fix:** Order theo `EndTime`, rồi `Id` để có deterministic pagination/claiming.

### 7. String status dễ tạo invalid state

- **Problem:** Trạng thái dùng magic string.
- **Impact:** Typo/refactor khó kiểm soát, state transition không rõ.
- **Severity:** Low.
- **Fix:** Enum/value mapping hoặc constants cùng state-transition methods.

### 8. Log thiếu operation identity

- **Problem:** Chỉ log email.
- **Impact:** Khó correlate retry, config và external request.
- **Severity:** Medium.
- **Fix:** Structured logging với `ConfigId`, `OperationId`, attempt, duration, external correlation ID; tránh log dữ liệu nhạy cảm quá mức.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng optimistic claim. Chi tiết SQL/provider cần điều chỉnh cho SQL Server hoặc PostgreSQL.

```csharp
public sealed class ResetExpiredOffboardingJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IExchangeService _exchange;
    private readonly ILogger<ResetExpiredOffboardingJob> _logger;

    public ResetExpiredOffboardingJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IExchangeService exchange,
        ILogger<ResetExpiredOffboardingJob> logger)
    {
        _dbFactory = dbFactory;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ProcessAsync(long configId, CancellationToken ct)
    {
        var operationId = $"offboarding-reset:{configId}";

        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.EmployeeOffboardingMailConfigs
            .Where(x => x.Id == configId && x.Status == "Pending")
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.OperationId, operationId), ct);

        if (claimed == 0)
        {
            _logger.LogInformation(
                "Skipping config {ConfigId}; it is not claimable", configId);
            return;
        }

        try
        {
            var config = await db.EmployeeOffboardingMailConfigs
                .SingleAsync(x => x.Id == configId, ct);

            await _exchange.EnsureMailboxResetAsync(
                config.UserEmail, operationId, ct);

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;

            db.EmployeeOffboardingMailConfigHistories.Add(new()
            {
                ConfigId = config.Id,
                Action = "Reset",
                OperationId = operationId,
                CreatedAt = DateTime.UtcNow
            });

            await db.SaveChangesAsync(ct);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Reset failed for config {ConfigId}, operation {OperationId}",
                configId, operationId);
            throw;
        }
    }
}
```

Database nên có unique constraint phù hợp cho history/operation identity nếu business rule yêu cầu một logical reset duy nhất. `EnsureMailboxResetAsync` nên hướng tới desired-state/idempotent behavior: kiểm tra hoặc thiết lập mailbox về trạng thái mong muốn thay vì giả định mỗi invocation là một command chỉ được gọi đúng một lần.

## Trade-offs

Atomic claim giảm duplicate execution nhưng tạo bài toán recovery nếu worker chết sau khi chuyển sang `Processing`; cần lease/heartbeat hoặc cơ chế reclaim stale operations. Distributed lock có thể đơn giản trong một số deployment nhưng không thay thế idempotency vì process vẫn có thể chết sau external side effect. Outbox hữu ích cho reliable publication từ DB, nhưng không tự biến một arbitrary external API thành transactional participant.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 20 task cùng claim một config và xác nhận chỉ một task thắng.
2. **Failure-window test:** external operation thành công nhưng DB save bị giả lập failure; retry phải không gây duplicate business effect.
3. **Crash recovery test:** worker chết sau `Processing`; stale operation phải có đường recovery/reconciliation.
4. **Batch/load test:** hàng nghìn expired configs, xác nhận throughput, fairness và connection-pool behavior.
5. **Database constraint test:** hai attempts ghi cùng logical history phải bị deduplicate hoặc xử lý có chủ đích.

## Quan sát trong production

Theo dõi số `Pending`, `Processing`, `Completed`, tuổi của oldest pending item, processing duration, retry count, external API latency/error rate, số operation bị reclaim, duplicate-prevention count và DB lock/deadlock metrics. Trace nên correlate Hangfire job → config ID → external operation/correlation ID → DB transition.

1. Nếu external API không hỗ trợ idempotency key hoặc endpoint đọc trạng thái, bạn sẽ giảm duplicate side effect thế nào?
2. Khi nào bạn chọn database claim thay vì distributed lock?
3. Nếu job phải xử lý 1 triệu record/ngày, kiến trúc hiện tại cần thay đổi ở đâu trước?

# Code Review Challenge 2 — Endpoint tra cứu audit log có lỗ hổng authorization và query nguy hiểm

**Chủ đề:** Authorization, SQL injection, sensitive-data exposure, performance, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** Khoảng 8–9 vấn đề

## Bối cảnh

Một internal ASP.NET Core API cho phép portal tìm audit log của nhiều tenant. Endpoint nhận tenant ID, từ khóa và sort column. Hệ thống dùng PostgreSQL qua Npgsql. Support team báo đôi khi query rất chậm; security review cũng nghi ngờ user của tenant A có thể truy cập dữ liệu tenant B nếu biết tenant ID.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly NpgsqlConnection _connection;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        NpgsqlConnection connection,
        ILogger<AuditController> logger)
    {
        _connection = connection;
        _logger = logger;
    }

    [HttpGet]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string? search,
        string sort = "created_at")
    {
        var sql = $@"
            SELECT id, tenant_id, user_email, action, payload, created_at
            FROM audit_logs
            WHERE tenant_id = '{tenantId}'
              AND ('{search}' IS NULL OR payload ILIKE '%{search}%')
            ORDER BY {sort} DESC";

        _logger.LogInformation("Audit SQL: {Sql}", sql);

        await _connection.OpenAsync();
        await using var command = new NpgsqlCommand(sql, _connection);
        await using var reader = await command.ExecuteReaderAsync();

        var rows = new List<object>();
        while (await reader.ReadAsync())
        {
            rows.Add(new
            {
                Id = reader.GetInt64(0),
                TenantId = reader.GetString(1),
                UserEmail = reader.GetString(2),
                Action = reader.GetString(3),
                Payload = reader.GetString(4),
                CreatedAt = reader.GetDateTime(5)
            });
        }

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization

- **Problem:** Caller tự truyền `tenantId`; code không chứng minh caller có quyền trên tenant đó.
- **Why:** `[Authorize]` chỉ yêu cầu authenticated principal theo policy mặc định, không tự thực hiện resource authorization cho arbitrary tenant ID.
- **Impact:** Cross-tenant data exposure.
- **Severity:** Critical.
- **Fix:** Derive tenant từ trusted claims/context khi phù hợp, hoặc kiểm tra membership/permission bằng authorization policy/service trước query.

### 2. SQL injection qua `tenantId` và `search`

- **Problem:** Values được interpolate trực tiếp vào SQL.
- **Impact:** Query manipulation, data disclosure hoặc tác động khác tùy DB permissions.
- **Severity:** Critical.
- **Fix:** Dùng Npgsql parameters cho mọi data value.

### 3. SQL injection qua `sort`

- **Problem:** Identifier được nối trực tiếp vào `ORDER BY`.
- **Why:** SQL parameter không dùng để parameterize identifier theo cách dùng cho scalar value.
- **Impact:** Injection/query manipulation.
- **Severity:** Critical.
- **Fix:** Map một enum/allowlist (`createdAt`, `action`) sang hard-coded SQL identifiers.

### 4. Response trả raw `payload`

- **Problem:** Audit payload có thể chứa PII, tokens hoặc internal fields.
- **Impact:** Sensitive-data exposure ngay cả với caller hợp lệ.
- **Severity:** High.
- **Fix:** DTO tối thiểu, redaction, field-level authorization; không lưu secrets vào audit payload ngay từ đầu.

### 5. Log toàn bộ SQL đã chứa input và dữ liệu tìm kiếm

- **Problem:** Query string được ghi nguyên văn.
- **Impact:** Log injection, PII leakage, secrets/search terms xuất hiện trong log aggregation.
- **Severity:** High.
- **Fix:** Log query name/template, tenant-safe identifier, duration và row count; không log raw SQL chứa user input.

### 6. Không pagination/limit

- **Problem:** Endpoint có thể materialize toàn bộ matching rows vào memory.
- **Impact:** High memory, latency, DB load, response quá lớn.
- **Severity:** High.
- **Fix:** Bounded page size, cursor/keyset pagination cho audit timeline lớn.

### 7. Search `%term%` trên payload có thể rất đắt

- **Problem:** Leading wildcard thường không tận dụng B-tree index thông thường cho substring search.
- **Impact:** Sequential scans/high CPU-I/O trên bảng audit lớn.
- **Severity:** Medium.
- **Fix:** Xác định search requirement; dùng searchable structured columns, PostgreSQL full-text/trigram strategy khi thực sự cần, và kiểm tra execution plan.

### 8. Cancellation không được propagate

- **Problem:** Không nhận `CancellationToken` từ request.
- **Impact:** Client disconnect nhưng DB work có thể tiếp tục.
- **Severity:** Medium.
- **Fix:** Pass `HttpContext.RequestAborted`/action token vào open, execute và read operations.

### 9. Connection lifetime cần rõ ràng

- **Problem:** Inject trực tiếp một mutable `NpgsqlConnection`; độ an toàn phụ thuộc registration/lifetime bên ngoài.
- **Impact:** Nếu lifetime sai, concurrent use/state leakage có thể xảy ra.
- **Severity:** Medium.
- **Fix:** Ưu tiên `NpgsqlDataSource`/factory-style creation hoặc bảo đảm connection scoped/transient đúng thiết kế và dispose đúng chỗ.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private static readonly IReadOnlyDictionary<string, string> SortColumns =
        new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase)
        {
            ["createdAt"] = "created_at",
            ["action"] = "action"
        };

    private readonly NpgsqlDataSource _dataSource;
    private readonly ITenantAccessService _tenantAccess;

    public AuditController(
        NpgsqlDataSource dataSource,
        ITenantAccessService tenantAccess)
    {
        _dataSource = dataSource;
        _tenantAccess = tenantAccess;
    }

    [HttpGet]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string? search,
        string sort = "createdAt",
        int pageSize = 50,
        CancellationToken ct = default)
    {
        if (!await _tenantAccess.CanReadAuditAsync(User, tenantId, ct))
            return Forbid();

        pageSize = Math.Clamp(pageSize, 1, 100);

        if (!SortColumns.TryGetValue(sort, out var sortColumn))
            return BadRequest("Unsupported sort column.");

        var sql = $"""
            SELECT id, user_email, action, created_at
            FROM audit_logs
            WHERE tenant_id = @tenantId
              AND (@search IS NULL OR payload ILIKE '%' || @search || '%')
            ORDER BY {sortColumn} DESC, id DESC
            LIMIT @pageSize
            """;

        await using var connection = await _dataSource.OpenConnectionAsync(ct);
        await using var command = new NpgsqlCommand(sql, connection);
        command.Parameters.AddWithValue("tenantId", tenantId);
        command.Parameters.AddWithValue(
            "search",
            string.IsNullOrWhiteSpace(search) ? DBNull.Value : search);
        command.Parameters.AddWithValue("pageSize", pageSize);

        await using var reader = await command.ExecuteReaderAsync(ct);
        var rows = new List<AuditRowDto>();

        while (await reader.ReadAsync(ct))
        {
            rows.Add(new AuditRowDto(
                reader.GetInt64(0),
                reader.GetString(1),
                reader.GetString(2),
                reader.GetDateTime(3)));
        }

        return Ok(rows);
    }
}

public sealed record AuditRowDto(
    long Id,
    string UserEmail,
    string Action,
    DateTime CreatedAt);
```

Trong production, nếu email cũng không cần thiết cho mọi role thì tiếp tục redact/omit. Với pagination thực tế, nên dùng cursor dựa trên `(created_at, id)` thay vì chỉ `LIMIT`, nếu UX cần load tiếp ổn định trên dataset lớn.

## Trade-offs

Resource authorization thêm một lookup hoặc policy evaluation nhưng là boundary bắt buộc cho multi-tenant security. Deriving tenant hoàn toàn từ claim đơn giản hơn nếu mỗi identity chỉ thuộc một tenant; nếu user có quyền trên nhiều tenant, explicit resource authorization phù hợp hơn. Trigram/full-text index tăng storage và write cost, nên chỉ thêm sau khi đo query pattern thực tế.

## Cách kiểm thử

1. **Security integration test:** user tenant A request tenant B phải nhận `403` và không query/return data tenant B.
2. **Injection test:** payload như `' OR 1=1 --` ở `tenantId/search` không thay đổi query semantics; invalid sort bị reject.
3. **Sensitive-data test:** response không chứa `payload`, token hoặc fields không được phép.
4. **Load/database test:** bảng lớn với search phổ biến; kiểm tra latency, execution plan, rows scanned và bounded response size.
5. **Cancellation test:** hủy request khi DB query đang chạy và xác nhận operation được cancel/connection được trả về pool.

## Quan sát trong production

Ghi structured logs gồm route, authorized tenant context, result count, duration và status nhưng không raw search payload. Theo dõi p50/p95/p99 latency, DB command duration, rows returned, timeout/cancellation count, forbidden cross-tenant attempts và slow-query plans. Trace authorization check và DB span để phân biệt latency ở policy lookup với database query.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một support admin hợp lệ cần truy cập nhiều tenant, bạn thiết kế authorization model và audit trail thế nào?
2. Keyset pagination cho `(created_at, id)` sẽ hoạt động ra sao khi nhiều rows có cùng timestamp?
3. Nếu product yêu cầu full-text search trên JSON audit payload hàng trăm triệu rows, bạn sẽ giữ PostgreSQL hay tách search workload? Điều kiện nào quyết định?

- Thiết kế retries cùng idempotency, không thêm retry sau cùng như một patch.
- Với distributed side effects, luôn hỏi: “Nếu process chết chính xác giữa hai bước này thì sao?”
- Authentication không thay thế resource-level authorization.
- Parameterize data values; allowlist identifiers không thể parameterize trực tiếp.
- Treat observability as part of correctness: operation identity, state transition và failure window phải truy vết được.
