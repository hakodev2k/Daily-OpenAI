# Code Review Challenge 1 — Hangfire job xử lý thanh toán bị chạy trùng

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction
**Độ khó:** Senior+
**Thời gian review đề xuất:** 25–30 phút
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service nhận yêu cầu hoàn tiền và enqueue Hangfire job. Mỗi job đọc `RefundRequest`, gọi payment provider rồi cập nhật trạng thái. Production chạy 3 Hangfire workers. Gần đây một số khách hàng nhận hai lần hoàn tiền khi worker timeout hoặc bị restart. Dashboard cho thấy cùng business request đôi khi được thực thi lại. Payment provider hỗ trợ idempotency key nhưng code hiện tại chưa dùng. Không được giả định rằng Hangfire đảm bảo exactly-once execution.

## Đoạn code cần review

```csharp
public sealed class RefundJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<RefundJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task Execute(Guid refundId)
    {
        var refund = await _db.RefundRequests
            .FirstOrDefaultAsync(x => x.Id == refundId);

        if (refund == null || refund.Status == "Completed")
            return;

        refund.Status = "Processing";
        await _db.SaveChangesAsync();

        var response = await _httpClient.PostAsJsonAsync(
            "/refunds",
            new { refund.PaymentId, refund.Amount });

        var body = await response.Content.ReadAsStringAsync();
        _logger.LogInformation("Refund response: {Body}", body);

        response.EnsureSuccessStatusCode();

        refund.Status = "Completed";
        refund.ProviderResponse = body;
        refund.CompletedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();
    }
}
```

## Kết quả code review tham khảo

### 1. Không có idempotency key cho thao tác hoàn tiền

**Problem:** Retry có thể tạo side effect lần hai.
**Why:** HTTP request mới không có business key ổn định để provider deduplicate.
**Production impact:** Khách hàng có thể được hoàn tiền nhiều lần.
**Severity:** Critical.
**Recommended fix:** Gửi một idempotency key ổn định, ví dụ `refund.Id`, nếu provider hỗ trợ và lưu provider operation/reference để reconcile.

### 2. Check-then-act race condition

**Problem:** `Status != Completed` không khóa hoặc atomically claim job.
**Why:** Hai worker có thể cùng đọc `Pending`, cùng chuyển `Processing`, rồi cùng gọi provider.
**Impact:** Duplicate external calls.
**Severity:** Critical.
**Fix:** Atomic claim bằng optimistic concurrency token hoặc conditional update; chỉ worker claim thành công mới tiếp tục.

### 3. Failure window sau external side effect

**Problem:** Provider có thể thành công nhưng process chết trước khi DB thành `Completed`.
**Why:** Database transaction không thể atomically commit cùng external HTTP side effect.
**Impact:** Retry không biết lần trước đã thành công hay chưa.
**Severity:** Critical.
**Fix:** Idempotency key + persisted attempt state + reconciliation/query provider khi outcome không chắc chắn.

### 4. Không truyền CancellationToken

**Problem:** DB và HTTP operation không nhận cancellation.
**Impact:** Shutdown hoặc cancellation kéo dài resource usage và làm failure recovery khó dự đoán.
**Severity:** Medium.
**Fix:** Truyền token nếu execution model cho phép và thiết kế cancellation boundary cẩn thận quanh external side effect.

### 5. Không kiểm soát timeout/retry policy của external call ở mức business

**Problem:** Timeout không có nghĩa provider thất bại.
**Impact:** Blind retry có thể duplicate side effect.
**Severity:** High.
**Fix:** Phân biệt transport retry với business retry; chỉ retry an toàn khi idempotency được bảo đảm.

### 6. Logging toàn bộ provider response

**Problem:** Body có thể chứa payment/customer data.
**Impact:** Sensitive-data exposure và log volume cao.
**Severity:** High.
**Fix:** Structured logging với allow-list field, correlation ID, provider reference; redact dữ liệu nhạy cảm.

### 7. String status không bảo vệ state transition

**Problem:** State transition dễ sai và khó enforce.
**Impact:** Invalid states khi retry/concurrency.
**Severity:** Medium.
**Fix:** Enum/state model kết hợp database constraint hoặc transition method.

### 8. Thiếu observability cho attempt và reconciliation

**Problem:** Không có attempt count, duration, outcome category hay correlation.
**Impact:** Khó xác định duplicate và unknown outcome.
**Severity:** Medium.
**Fix:** Metrics và structured logs theo refund ID, attempt ID, provider operation ID.

## Phiên bản code đề xuất

```csharp
public sealed class RefundJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly HttpClient _client;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(
        IDbContextFactory<AppDbContext> dbFactory,
        HttpClient client,
        ILogger<RefundJob> logger)
    {
        _dbFactory = dbFactory;
        _client = client;
        _logger = logger;
    }

    public async Task Execute(Guid refundId, CancellationToken ct = default)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var affected = await db.RefundRequests
            .Where(x => x.Id == refundId && x.Status == RefundStatus.Pending)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, RefundStatus.Processing)
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (affected == 0)
            return;

        var refund = await db.RefundRequests
            .AsNoTracking()
            .SingleAsync(x => x.Id == refundId, ct);

        using var request = new HttpRequestMessage(HttpMethod.Post, "/refunds")
        {
            Content = JsonContent.Create(new { refund.PaymentId, refund.Amount })
        };
        request.Headers.TryAddWithoutValidation("Idempotency-Key", refund.Id.ToString("N"));

        try
        {
            using var response = await _client.SendAsync(request, ct);
            response.EnsureSuccessStatusCode();
            var result = await response.Content.ReadFromJsonAsync<RefundResult>(cancellationToken: ct);

            await db.RefundRequests
                .Where(x => x.Id == refundId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, RefundStatus.Completed)
                    .SetProperty(x => x.ProviderReference, result!.Reference)
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow), ct);

            _logger.LogInformation(
                "Refund {RefundId} completed with provider reference {ProviderReference}",
                refundId, result!.Reference);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(ex, "Refund {RefundId} has an uncertain or failed outcome", refundId);
            throw;
        }
    }
}
```

Điểm quan trọng: code trên minh họa atomic claim và provider idempotency, nhưng production vẫn cần state như `UnknownOutcome`/reconciliation thay vì mặc định coi mọi exception là thất bại. Nếu provider không hỗ trợ idempotency, cần thiết kế workflow bù/reconcile dựa trên provider transaction reference; không thể tạo exactly-once side effect chỉ bằng database lock.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi một database là source of truth. Distributed lock có thể hữu ích cho một số workload nhưng không loại bỏ failure window với external provider. Giữ DB transaction mở trong lúc HTTP call làm tăng lock duration mà vẫn không tạo atomicity xuyên hệ thống. Outbox phù hợp để đảm bảo phát hành command/event sau DB commit, nhưng consumer vẫn phải idempotent.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 execution cùng `refundId`; xác nhận provider chỉ ghi nhận một business refund.
2. **Failure-path:** provider thành công nhưng giả lập process crash trước DB completion; retry phải dùng cùng idempotency key và không hoàn tiền lần hai.
3. **Timeout test:** provider xử lý thành công nhưng client timeout; workflow chuyển sang trạng thái cần reconcile thay vì blind duplicate.
4. **Database test:** kiểm tra conditional claim chỉ cho đúng một worker thắng.
5. **Logging test:** đảm bảo không ghi payment/customer secret vào log.

## Quan sát trong production

Theo dõi `refund_attempt_total`, `refund_duplicate_prevented_total`, `refund_unknown_outcome_total`, provider latency/error rate và số request mắc lâu ở `Processing`. Trace nên nối Hangfire execution → DB claim → outbound HTTP. Alert khi `UnknownOutcome` tăng hoặc request `Processing` vượt SLA.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không hỗ trợ idempotency key thì bạn thiết kế recovery thế nào?
2. Outbox pattern giải quyết phần nào và không giải quyết phần nào của bài toán này?
3. Tại sao distributed lock vẫn không đủ để đảm bảo exactly-once external side effect?

# Code Review Challenge 2 — Endpoint tìm kiếm người dùng vừa chậm vừa vượt boundary authorization

**Chủ đề:** EF Core query execution, authorization, input validation, sensitive-data exposure
**Độ khó:** Senior
**Thời gian review đề xuất:** 20–25 phút
**Số vấn đề cần tìm:** Khoảng 6–8 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép manager tìm nhân viên trong tenant của mình. Production có vài trăm nghìn employee records. Endpoint bắt đầu gây memory spike và đôi khi trả dữ liệu của tenant khác khi người dùng biết một phần email. API sử dụng JWT authentication; authorization policy ở endpoint chỉ kiểm tra role `Manager`.

## Đoạn code cần review

```csharp
[Authorize(Roles = "Manager")]
[HttpGet("employees/search")]
public async Task<IActionResult> Search(
    string tenantId,
    string? keyword,
    int page = 1,
    int pageSize = 100)
{
    var employees = await _db.Employees
        .Include(x => x.Manager)
        .ToListAsync();

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        employees = employees
            .Where(x => x.Email.Contains(keyword) ||
                        x.DisplayName.Contains(keyword))
            .ToList();
    }

    employees = employees
        .Where(x => x.TenantId == tenantId)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToList();

    _logger.LogInformation(
        "Employee search tenant={TenantId}, keyword={Keyword}, count={Count}",
        tenantId, keyword, employees.Count);

    return Ok(employees.Select(x => new
    {
        x.Id,
        x.DisplayName,
        x.Email,
        ManagerEmail = x.Manager!.Email,
        x.InternalNotes
    }));
}
```

## Kết quả code review tham khảo

### 1. Tenant authorization dựa trên user-controlled `tenantId`

**Problem:** Role `Manager` không chứng minh caller được truy cập tenant truyền trong query.
**Why:** Endpoint tin tenant ID do client cung cấp.
**Impact:** Cross-tenant data exposure.
**Severity:** Critical.
**Fix:** Resolve tenant từ authenticated principal/server-side membership và enforce tenant predicate trong query; không dùng caller-provided tenant ID như authorization proof.

### 2. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync()` chạy trước tenant, keyword và paging.
**Why:** Các operation sau chạy bằng LINQ-to-Objects.
**Impact:** Memory spike, GC pressure, DB/network I/O lớn, latency tăng theo table size.
**Severity:** High.
**Fix:** Giữ query ở `IQueryable`, filter/paging/projection trước `ToListAsync`.

### 3. Sensitive-data exposure

**Problem:** Trả `InternalNotes` và manager email mà chưa chứng minh business requirement.
**Impact:** Data leakage và tăng blast radius khi authorization sai.
**Severity:** High.
**Fix:** DTO allow-list tối thiểu; field nhạy cảm cần policy riêng nếu thực sự cần.

### 4. Không giới hạn page/pageSize

**Problem:** Giá trị âm hoặc cực lớn không được validate.
**Impact:** Expensive query, abuse/DoS và behavior paging bất thường.
**Severity:** Medium.
**Fix:** Validate `page >= 1`, giới hạn `pageSize`, ví dụ theo policy của hệ thống.

### 5. Logging raw keyword

**Problem:** Keyword có thể là email/PII.
**Impact:** PII lan vào log storage.
**Severity:** Medium.
**Fix:** Không log raw search term; log normalized metadata như term length, tenant scope, result count.

### 6. `Include` dư thừa nếu projection đúng cách

**Problem:** Load entity graph rồi mới map.
**Impact:** Extra data transfer/tracking/allocation.
**Severity:** Medium.
**Fix:** Project trực tiếp thành DTO trong SQL; không cần `Include` cho navigation được dùng trong projection.

### 7. Tracking không cần thiết cho read-only endpoint

**Problem:** Entity materialization hiện tại bị tracking mặc định.
**Impact:** Tăng memory/change-tracker overhead.
**Severity:** Low/Medium.
**Fix:** Projection DTO hoặc `AsNoTracking()`.

## Phiên bản code đề xuất

```csharp
[Authorize(Roles = "Manager")]
[HttpGet("employees/search")]
public async Task<ActionResult<IReadOnlyList<EmployeeSearchDto>>> Search(
    string? keyword,
    int page = 1,
    int pageSize = 50,
    CancellationToken ct = default)
{
    if (page < 1 || pageSize is < 1 or > 100)
        return BadRequest("Invalid paging parameters.");

    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var query = _db.Employees
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x =>
            x.Email.Contains(term) || x.DisplayName.Contains(term));
    }

    var results = await query
        .OrderBy(x => x.Id)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(x => new EmployeeSearchDto(
            x.Id,
            x.DisplayName,
            x.Email,
            x.Manager == null ? null : x.Manager.DisplayName))
        .ToListAsync(ct);

    _logger.LogInformation(
        "Employee search completed for tenant {TenantId}; page={Page}, pageSize={PageSize}, count={Count}",
        tenantId, page, pageSize, results.Count);

    return Ok(results);
}
```

`tenant_id` chỉ là ví dụ về server-trusted tenant context. Trong hệ thống thực, cần xác nhận cách claim được phát hành và liệu một user có thể thuộc nhiều tenant; khi đó tenant selection phải được validate against server-side membership. Cũng cần kiểm tra execution plan/index theo workload thực tế thay vì mặc định rằng `Contains` sẽ scale tốt.

## Trade-offs

Offset pagination đơn giản nhưng có thể kém hiệu quả ở page sâu và dễ thay đổi kết quả khi dữ liệu mutate; keyset pagination phù hợp hơn cho feed lớn có ordering ổn định. Search bằng SQL `Contains` đủ cho nhu cầu nhỏ nhưng full-text/search engine có thể phù hợp khi cần ranking, fuzzy search hoặc dataset rất lớn. Denormalizing manager display name có thể giảm join nhưng làm tăng consistency cost.

## Cách kiểm thử

1. **Security integration test:** manager tenant A cố truy cập employee tenant B và không nhận được dữ liệu.
2. **Database test:** xác nhận generated SQL chứa tenant predicate, filtering, ordering và paging trước materialization.
3. **Load test:** dataset lớn, kiểm tra latency, allocation và DB reads khi keyword có/không có kết quả.
4. **Validation test:** `page=0`, negative page, `pageSize` quá lớn đều bị reject.
5. **Sensitive-data test:** response và logs không chứa `InternalNotes` hay raw keyword ngoài policy.

## Quan sát trong production

Theo dõi endpoint p50/p95/p99 latency, DB query duration, rows scanned/returned, allocation/GC pressure, response size và rejected paging requests. Trace phải cho thấy SQL span và tenant scope nhưng không chứa raw PII. Kiểm tra execution plan/index khi query latency hoặc logical reads tăng.
