# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân lên trong production

**Loại câu hỏi:** Internal mechanism trong tình huống thực tế  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, change tracking, SQL diagnosis, performance, observability

## Bối cảnh

Một ASP.NET Core API trả danh sách 200 nhân viên cùng trạng thái offboarding. Sau một thay đổi nhỏ, p95 tăng từ khoảng 180 ms lên hơn 2 giây và memory allocation tăng đáng kể. Code tạo `IQueryable<Employee>`, áp dụng filter theo nhiều bước, sau đó enumerate để build DTO. Trong quá trình mapping, một số navigation property được truy cập. Developer nói: “`IQueryable` đã lấy dữ liệu từ database từ lúc gọi `Where`, và tracking giúp query nhanh hơn vì EF đã cache entity.”

Không rõ lazy loading có được bật hay không, query có `Include` hay không, và endpoint là read-only hay còn cập nhật entity sau đó.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc tạo `IQueryable` đến lúc enumerate; vì sao latency/allocation có thể tăng; misconception nào nằm trong nhận định trên; rủi ro production là gì; và bạn sẽ chứng minh từng giả thuyết bằng evidence nào?

## Câu hỏi làm rõ nên cân nhắc

- Lazy-loading proxies có được bật không?
- Endpoint có cần update entity sau query không?
- SQL thực tế EF Core sinh ra là gì và có bao nhiêu round trip?
- DTO projection được thực hiện trước hay sau `ToListAsync`?
- Query có pagination, `Include`, split query hoặc client-side processing nào không?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng expression tree với thời điểm query thực sự được thực thi.
- **Gợi ý 2:** Xem xét tracking, materialization, navigation loading, projection và số round trip.
- **Gợi ý 3:** So sánh `AsNoTracking()` + server-side projection với materialize toàn entity graph; đo SQL, duration và allocations thay vì suy đoán.

## Cấu trúc trả lời đề xuất

1. Làm rõ behavior và requirement.
2. Mô tả lifecycle của `IQueryable`.
3. Phân tích tracking/materialization/navigation loading.
4. Liệt kê nhiều giả thuyết latency.
5. Thu thập SQL, traces, metrics và allocation profile.
6. Đề xuất tối ưu theo evidence.
7. Kiểm thử correctness và performance.
8. Nêu trường hợp recommendation thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Where` trên `IQueryable` thường chỉ xây dựng query; execution xảy ra khi enumerate/materialize bằng các terminal operation như `ToListAsync`.
- Change tracking có chi phí CPU/memory và hữu ích khi entity cần được cập nhật; không nên coi nó là query cache.
- Read-only query thường nên cân nhắc `AsNoTracking()` và projection chỉ lấy cột cần thiết.
- Phải kiểm tra SQL thực tế và số database round trip.

### Điểm cộng

- Nhận diện nguy cơ N+1 nếu navigation loading gây query bổ sung.
- Phân biệt eager loading, explicit loading và lazy loading.
- Nhắc đến pagination, indexes và query plan thay vì chỉ tối ưu C#.

### Nâng cao

- Đo allocation bằng runtime profiling/counters và correlate DB spans trong distributed tracing.
- Hiểu rằng `AsNoTracking` không tự động chữa SQL xấu; projection/index/query shape vẫn quan trọng.

## Hướng giải quyết tham khảo

**Giả định:** endpoint chỉ đọc dữ liệu và không cần cập nhật các entity vừa load.

Trước hết xác nhận SQL và round trip. `IQueryable` giữ expression cho đến khi được enumerate. Nếu code materialize entity sớm rồi mới map/filter, database có thể trả nhiều dữ liệu hơn cần thiết. Tracking khiến `DbContext` duy trì state cho các entity được materialize; với read-heavy endpoint đây có thể là overhead không cần thiết.

Tối ưu ưu tiên là giữ filter/projection trong query càng lâu càng tốt, ví dụ `Where(...).Select(...).AsNoTracking().ToListAsync(ct)`, chỉ lấy các cột cần cho DTO. Nếu navigation cần thiết, chọn projection hoặc eager loading có chủ đích. Nếu phát hiện N+1, sửa query shape thay vì tăng timeout.

Đồng thời kiểm tra execution plan, index phù hợp, row count và pagination. So sánh trước/sau bằng p50/p95/p99, DB duration, query count, rows returned và allocation/request.

Nếu endpoint thực sự cần sửa các entity trong cùng unit of work thì tracking có thể hợp lý; recommendation khi đó thay đổi.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ không kết luận tracking hay EF Core là nguyên nhân trước khi xem SQL và traces. `Where` trên `IQueryable` chủ yếu xây expression tree; database thường chưa được gọi cho tới khi query được enumerate, ví dụ `ToListAsync`. Tracking cũng không phải query cache. Nó lưu state của entity trong `DbContext` để identity resolution/change detection và có cost về memory/CPU.

Tôi sẽ kiểm tra endpoint có read-only không, lazy loading có bật không, SQL thực tế, số round trip và execution plan. Nếu mapping truy cập navigation và lazy loading hoạt động thì N+1 là một giả thuyết mạnh. Nếu query load toàn entity rồi mới map thì cũng có thể đang lấy quá nhiều columns/rows.

Với read-only path, tôi ưu tiên server-side projection và `AsNoTracking`, cộng pagination và index phù hợp. Sau đó tôi benchmark cùng workload và theo dõi query count, DB duration, p95 và allocation. Nếu endpoint cần update entity ngay sau đó, tôi có thể giữ tracking và tối ưu query shape thay vì áp dụng `AsNoTracking` máy móc.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution()` có thể hữu ích?
2. Nếu query chỉ chạy đúng một SQL statement nhưng vẫn chậm, bạn điều tra tiếp thế nào?
3. Nếu bỏ tracking giảm memory nhưng latency gần như không đổi, điều đó nói gì về giả thuyết ban đầu?

## Lỗi trả lời thường gặp

- Nói `Where` luôn query database ngay lập tức.
- Xem change tracker như cache truy vấn.
- Áp dụng `AsNoTracking` cho mọi query mà không xét write workflow.
- Chỉ nhìn C# mà bỏ qua SQL plan/index/row count.
- Khẳng định N+1 khi chưa xác nhận loading strategy và query count.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 2 — Incident: Hangfire gửi email offboarding trùng sau khi scale-out

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire, idempotency, concurrency, database consistency, observability

## Bối cảnh

Một backend dùng Hangfire để xử lý tác vụ offboarding và gọi Exchange Online/Microsoft Graph cho các thao tác liên quan. Sau khi deployment tăng từ một lên ba application instances, một số nhân viên nhận notification hai lần và vài external operation được thực hiện lặp lại. Dashboard cho thấy job có retry nhưng chưa rõ duplicate đến từ enqueue, retry, worker concurrency hay timeout sau khi external system đã nhận request.

Business yêu cầu giảm duplicate ngay nhưng không được bỏ sót tác vụ quan trọng.

## Câu hỏi chính

Bạn sẽ xử lý incident từ mitigation đến root cause như thế nào, và thiết kế lại processing ra sao để retry an toàn mà không dựa vào giả định “job chỉ chạy đúng một lần”? 

## Câu hỏi làm rõ nên cân nhắc

- Duplicate là cùng Hangfire job ID hay nhiều job ID khác nhau?
- External operation nào có side effect và có hỗ trợ idempotency/concurrency control không?
- Job được enqueue từ đâu và có thể enqueue đồng thời không?
- Timeout xảy ra trước hay sau khi external service thực hiện side effect?
- Database có business key/status/audit record đủ để xác định một operation đã hoàn tất không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “delivery/execution có thể lặp lại” khỏi “business side effect chỉ nên xảy ra một lần”.
- **Gợi ý 2:** Điều tra enqueue path, retry history, worker logs, DB state và external request correlation.
- **Gợi ý 3:** Thiết kế idempotency dựa trên durable business key/state transition; dùng transaction/unique constraint khi phù hợp và coi external call là failure boundary riêng.

## Cấu trúc trả lời đề xuất

1. Xác định impact và phạm vi.
2. Mitigate duplicate nhưng giữ khả năng xử lý backlog.
3. Correlate job ID, operation ID, employee ID và external request.
4. Xây nhiều giả thuyết.
5. Reproduce/verify từng giả thuyết.
6. Sửa ngắn hạn.
7. Thiết kế idempotency/recovery dài hạn.
8. Thêm monitoring và runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định background job là exactly-once.
- Side effect phải idempotent hoặc có durable deduplication/state machine.
- Retry phải được thiết kế cùng idempotency.
- Điều tra bằng correlation/evidence trước khi quy lỗi cho scale-out.

### Điểm cộng

- Unique constraint trên operation/business key để chống race ở DB.
- Phân biệt transaction nội bộ với external side effect; không giả vờ một DB transaction có thể atomically bao phủ Graph/Exchange.
- Có reconciliation job cho trạng thái “không biết external call đã thành công hay chưa”.

### Nâng cao

- Outbox pattern nếu enqueue/message publication cần atomic với database state.
- State transition rõ ràng: Pending → Processing → Completed/Failed/NeedsReconciliation.
- Metrics duplicate suppression, retries, poison operations và external latency/error rate.

## Hướng giải quyết tham khảo

Mitigation đầu tiên có thể giới hạn concurrency hoặc tạm dừng nguồn enqueue gây duplicate nếu evidence chỉ ra nó, nhưng không xóa backlog tùy tiện. Thu thập Hangfire job ID, retry count, worker/server, employee/business operation ID, timestamps và external correlation IDs.

Thiết kế dài hạn dùng một `OperationId`/business key bền vững cho side effect. Database enforce uniqueness nơi có thể. Worker phải kiểm tra durable state và thực hiện transition có concurrency control. External call cần timeout/retry có kiểm soát. Trường hợp timeout sau khi server bên ngoài đã xử lý là “ambiguous outcome”; nếu API không cung cấp idempotency key, cần query/reconcile trạng thái trước khi lặp side effect nguy hiểm.

Nếu việc ghi business state và enqueue phải đi cùng nhau, outbox giúp tránh trạng thái DB commit nhưng job không được phát hoặc ngược lại. Không cần đưa microservices vào chỉ để giải quyết vấn đề này.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi duplicate execution là điều có thể xảy ra và tập trung bảo đảm business side effect an toàn. Trong incident, trước tiên tôi xác định duplicate là cùng job retry hay nhiều lần enqueue bằng Hangfire job IDs và correlation IDs. Tôi cũng kiểm tra thời điểm timeout vì có trường hợp external service đã thành công nhưng client không nhận response.

Mitigation có thể giảm concurrency hoặc chặn enqueue path bị lỗi, nhưng phải bảo toàn backlog. Về fix, tôi tạo business operation ID bền vững, lưu state trong DB và enforce uniqueness. Worker chỉ được transition operation hợp lệ; retry cùng operation ID không được tạo side effect mới nếu trạng thái đã Completed.

External API là failure boundary riêng. Nếu outcome không xác định, tôi ưu tiên reconciliation/query state thay vì gọi lại mù quáng. Nếu DB change và việc tạo job cần atomic, tôi cân nhắc outbox. Cuối cùng tôi thêm metrics cho retry, duplicate suppression, ambiguous outcomes và alert theo tỷ lệ lỗi thay vì chỉ theo job failed.”

## Câu hỏi đào sâu

1. `DisableConcurrentExecution` có đủ để bảo đảm không gửi duplicate không? Vì sao?
2. Nếu external API không có idempotency key và cũng không cho query trạng thái, bạn xử lý ambiguous outcome thế nào?
3. Unique constraint có thể ngăn duplicate ở bước nào và không giải quyết được bước nào?

## Lỗi trả lời thường gặp

- Chỉ tắt retry.
- Cho rằng distributed lock đồng nghĩa exactly-once business effect.
- Bao external HTTP call trong DB transaction dài và coi đó là atomic.
- Không có correlation ID/audit trail.
- Chỉ sửa worker mà bỏ qua nguồn duplicate enqueue.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **1.5**
- Trade-off analysis: **1.5**
- Production readiness: **2.5**
- Communication: **1.0**

# Câu 3 — Thiết kế AI agent review pull request có quyền dùng GitHub tools

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, structured output, evaluation, security, human approval

## Bối cảnh

Team muốn xây một AI agent hỗ trợ review pull request cho repository .NET. Agent được phép đọc diff, repository guidance và test results; tương lai có thể comment trực tiếp lên PR. Mục tiêu là phát hiện correctness/security/performance issues có giá trị, giảm noise và không để model tự ý sửa code hoặc tiết lộ secrets.

Chưa xác định model, token budget, mức quyền GitHub, tiêu chí quality hay quy trình human approval.

## Câu hỏi chính

Hãy thiết kế workflow cho agent này từ context collection đến validation, tool permissions, evaluation và production monitoring. Phần nào nên dùng AI, phần nào phải deterministic, và khi nào cần human approval?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ review hay được comment/write?
- Repository có dữ liệu nhạy cảm hoặc generated files nào không được gửi model?
- False positive và false negative loại nào gây thiệt hại lớn hơn?
- Có historical PR/review dataset để làm evaluation không?
- Latency/cost budget trên mỗi PR là bao nhiêu?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng bắt đầu từ model; bắt đầu từ trust boundary và desired outcome.
- **Gợi ý 2:** Tách deterministic retrieval/filtering/schema validation khỏi reasoning của model.
- **Gợi ý 3:** Least privilege + structured findings + evidence grounding + offline eval + staged rollout trước khi cho write permission.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và risk tolerance.
2. Xác định deterministic pipeline.
3. Thiết kế context package.
4. Giới hạn tools/permissions.
5. Định nghĩa output schema và validators.
6. Human approval/fallback.
7. Offline + online evaluation.
8. Audit, cost, latency và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho semantic reasoning/review; auth, permission, file allow/deny rules, schema validation và policy enforcement phải deterministic.
- Tool access theo least privilege; read-only mặc định.
- Finding phải gắn với file/range/evidence và qua validation trước khi publish.
- Có eval dataset và metrics thay vì đánh giá bằng cảm giác.

### Điểm cộng

- Context chỉ gồm diff + relevant surrounding code + repository instructions + test/static-analysis evidence thay vì dump toàn repo.
- Human approval trước write/comment ở giai đoạn đầu.
- Prompt injection từ repository content được xem là untrusted data, không phải instruction có quyền cao.

### Nâng cao

- Severity calibration, deduplication và confidence threshold.
- Shadow mode/canary rollout.
- Audit log cho prompt version, model/config version, tool calls và final decision mà không ghi secrets.

## Hướng giải quyết tham khảo

Pipeline có thể bắt đầu deterministic: nhận PR → xác thực repo/ref → lấy changed files/diff → áp file policy → chạy compiler/tests/static analyzers nếu phù hợp → retrieve repository guidance và surrounding code có liên quan → đóng gói context có provenance.

Model chỉ tạo candidate findings theo schema như `{path, line/range, category, severity, explanation, evidence, recommendation, confidence}`. Validator kiểm tra path/range tồn tại, schema hợp lệ, finding thực sự liên quan changed code và không chứa secret/policy-violating output. Findings trùng được deduplicate.

Giai đoạn đầu agent chỉ read và tạo draft review cho người duyệt. Chỉ sau khi eval đạt threshold mới cân nhắc quyền comment; không cấp merge/push nếu use case không cần. Repository text được coi là dữ liệu không đáng tin cậy, tránh để nội dung trong code thay đổi system/tool policy.

Evaluation nên dùng tập PR lịch sử có review label hoặc curated benchmark: precision của actionable findings, recall trên bug classes quan trọng, false-positive rate, acceptance rate, latency và cost. Production cần audit trail, tool-call traces, error rate, token/cost metrics và sampling để human QA.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế đây như một chatbot có token GitHub rộng. Trước hết tôi xác định agent chỉ cần review, nên mặc định GitHub access là read-only. Pipeline deterministic lấy diff, validate ref, lọc file, chạy test/static analysis và retrieve đúng repository guidance. Model nhận context có provenance và dùng reasoning để tạo candidate findings theo structured schema.

Những việc như authorization, secret filtering, schema validation, path/line verification và quyết định có được publish hay không phải deterministic. Repository content là untrusted data, vì vậy một comment trong source không được phép nâng quyền hoặc thay đổi tool policy.

Ban đầu tôi chạy shadow mode hoặc tạo draft để human approve. Tôi đánh giá bằng PR lịch sử/curated cases, theo precision, recall cho lỗi quan trọng, false-positive rate, acceptance rate, latency và cost. Chỉ khi quality ổn định mới cân nhắc quyền comment. Tôi vẫn không cấp push/merge vì không cần cho mục tiêu review. Mọi run cần audit model/config version, context sources và tool calls nhưng phải redact secrets.”

## Câu hỏi đào sâu

1. Làm sao đánh giá recall khi bạn không biết toàn bộ bug thật trong PR production?
2. Nếu tăng context giúp recall nhưng cost và noise cũng tăng, bạn tối ưu thế nào?
3. Nếu business yêu cầu agent tự comment ngay để tiết kiệm thời gian, bạn sẽ đặt guardrail nào trước khi chấp nhận?

## Lỗi trả lời thường gặp

- “Cho LLM đọc cả repo rồi review”.
- Cấp write permission ngay từ MVP.
- Không phân biệt repository content với trusted instruction.
- Không có deterministic validation/evidence grounding.
- Chỉ đo số comment thay vì actionable quality và false positives.
