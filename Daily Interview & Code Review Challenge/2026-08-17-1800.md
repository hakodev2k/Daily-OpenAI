# Code Review Challenge 1 — Transaction giữ lock quá lâu vì gọi Microsoft Graph bên trong transaction

**Chủ đề:** EF Core transaction handling, concurrency, external side effects, error handling, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API nội bộ xử lý thay đổi trạng thái nhân viên từ `Active` sang `Inactive`. Khi thao tác thành công, hệ thống cần:

- cập nhật trạng thái nhân viên trong SQL Server,
- tạo bản ghi offboarding,
- gọi Microsoft Graph để cập nhật một calendar event liên quan,
- gọi một service khác để gửi notification.

API chạy trên 4 instance. Khoảng 20–50 request/phút bình thường, nhưng cuối tháng có burst 300–500 request/phút. Production ghi nhận:

- một số request mất 20–40 giây,
- deadlock/lock timeout xuất hiện ở bảng `Employees`,
- Graph thỉnh thoảng timeout hoặc trả lỗi transient,
- có trường hợp notification đã gửi nhưng DB rollback,
- có trường hợp DB commit nhưng calendar chưa được cập nhật.

Business yêu cầu trạng thái nhân viên trong database phải chính xác. Với calendar/notification, chấp nhận eventual consistency trong vài phút nhưng không được gửi trùng không kiểm soát.

## Đoạn code cần review

```csharp
public sealed class EmployeeOffboardingService
{
    private readonly AppDbContext _db;
    private readonly GraphServiceClient _graph;
    private readonly HttpClient _notificationClient;
    private readonly ILogger<EmployeeOffboardingService> _logger;

    public EmployeeOffboardingService(
        AppDbContext db,
        GraphServiceClient graph,
        HttpClient notificationClient,
        ILogger<EmployeeOffboardingService> logger)
    {
        _db = db;
        _graph = graph;
        _notificationClient = notificationClient;
        _logger = logger;
    }

    public async Task OffboardAsync(
        Guid employeeId,
        string calendarEventId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var employee = await _db.Employees
            .SingleAsync(x => x.Id == employeeId, cancellationToken);

        employee.Status = EmployeeStatus.Inactive;
        employee.UpdatedAt = DateTime.UtcNow;

        _db.EmployeeOffboardings.Add(new EmployeeOffboarding
        {
            EmployeeId = employeeId,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await _graph.Me.Events[calendarEventId]
            .PatchAsync(
                new Microsoft.Graph.Models.Event
                {
                    Subject = $"[Inactive] {employee.DisplayName}"
                },
                cancellationToken: cancellationToken);

        var response = await _notificationClient.PostAsJsonAsync(
            "/api/notifications/offboarding",
            new { employeeId, employee.Email },
            cancellationToken);

        response.EnsureSuccessStatusCode();

        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Employee {EmployeeId} offboarded",
            employeeId);
    }
}
```

## Kết quả code review tham khảo

### 1. Giữ database transaction mở trong lúc gọi external network

**Problem:** Transaction được mở trước khi query/update DB và chỉ commit sau hai network call.  
**Why it happens:** Code cố tạo cảm giác “all-or-nothing” giữa DB và external systems dù chúng không cùng một transaction manager.  
**Production impact:** Lock bị giữ lâu theo latency của Graph/notification; dưới burst traffic làm tăng lock wait, deadlock và timeout.  
**Severity:** Critical  
**Recommended fix:** Giới hạn transaction chỉ cho thay đổi database. Commit nhanh, sau đó xử lý side effect ngoài transaction.

### 2. Không thể rollback external side effect bằng rollback SQL

**Problem:** Graph hoặc notification có thể thành công trước khi DB commit.  
**Why it happens:** External API không tham gia transaction SQL hiện tại.  
**Production impact:** Notification đã gửi nhưng trạng thái DB rollback; hoặc calendar đổi rồi DB fail, gây inconsistency.  
**Severity:** Critical  
**Recommended fix:** Dùng outbox/work-item được ghi cùng transaction với business state. Worker xử lý external side effects sau commit.

### 3. Retry toàn bộ method có thể lặp side effect

**Problem:** Nếu caller/job retry sau lỗi ở cuối flow, Graph/notification có thể đã thành công trước đó.  
**Why it happens:** Method không có operation id/idempotency state.  
**Production impact:** Gửi notification trùng, patch lặp, khó phân biệt attempt cũ/mới.  
**Severity:** High  
**Recommended fix:** Có operation/outbox id ổn định; consumer đánh dấu từng side effect `Pending/Processing/Succeeded/Failed` và thiết kế idempotent theo business key.

### 4. Hai request đồng thời có thể cùng offboard một employee

**Problem:** Không có concurrency guard hoặc business invariant rõ ràng.  
**Why it happens:** Cả hai request có thể đọc `Active` rồi cùng tạo offboarding record.  
**Production impact:** Duplicate history, duplicate notification/outbox item, trạng thái khó audit.  
**Severity:** High  
**Recommended fix:** Enforce invariant bằng unique constraint phù hợp hoặc optimistic concurrency token; kiểm tra state transition hợp lệ và xử lý conflict rõ ràng.

### 5. `SingleAsync` không kiểm tra trạng thái hiện tại trước khi transition

**Problem:** Code chỉ tìm theo `Id`, không xác nhận employee đang `Active`.  
**Why it happens:** Business transition bị encode ngầm thay vì kiểm tra invariant.  
**Production impact:** Có thể offboard lại employee đã inactive hoặc trạng thái trung gian.  
**Severity:** High  
**Recommended fix:** Query/validate current status hoặc update có điều kiện; trả conflict nếu transition không hợp lệ.

### 6. Cancellation từ request có thể làm mất việc sau khi business state đã commit nếu side effect chạy inline

**Problem:** Toàn flow gắn với request cancellation token.  
**Why it happens:** External delivery chưa được tách khỏi request lifecycle.  
**Production impact:** Client disconnect có thể huỷ Graph/notification dù business state đáng lẽ vẫn phải hoàn tất eventual processing.  
**Severity:** Medium  
**Recommended fix:** Request token dùng cho transaction chính; sau commit, worker riêng xử lý outbox với lifecycle/cancellation riêng.

### 7. Không có trạng thái retry/failure bền vững cho external operations

**Problem:** Nếu Graph lỗi, chỉ exception bubble ra.  
**Why it happens:** Không lưu attempt count, next retry time, last error hoặc poison state.  
**Production impact:** Khó recovery, dễ mất công việc hoặc retry mù.  
**Severity:** Medium  
**Recommended fix:** Outbox/work queue có trạng thái, retry policy, dead-letter/manual review sau ngưỡng phù hợp.

### 8. Thiếu correlation/operation id trong log

**Problem:** Log cuối chỉ có `EmployeeId`.  
**Why it happens:** Observability không theo workflow nhiều bước.  
**Production impact:** Khó nối DB update với từng Graph/notification attempt.  
**Severity:** Medium  
**Recommended fix:** Log structured với `OperationId`, `EmployeeId`, `OutboxId`, attempt, duration, dependency status.

### 9. `HttpResponseMessage` không được dispose rõ ràng

**Problem:** `response` không được dispose.  
**Why it happens:** Lifetime của response bị bỏ qua vì payload không được đọc.  
**Production impact:** Có thể giữ resource/network response lâu hơn cần thiết.  
**Severity:** Low  
**Recommended fix:** `using var response = ...` hoặc wrapper client xử lý response đầy đủ.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng transactional outbox đơn giản. `Employee` nên có concurrency token hoặc invariant được enforce ở database theo thiết kế thực tế.

```csharp
public sealed class EmployeeOffboardingService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public EmployeeOffboardingService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task<Guid> OffboardAsync(
        Guid employeeId,
        string calendarEventId,
        CancellationToken cancellationToken)
    {
        var now = _timeProvider.GetUtcNow();
        var operationId = Guid.NewGuid();

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var employee = await _db.Employees
            .SingleOrDefaultAsync(
                x => x.Id == employeeId,
                cancellationToken)
            ?? throw new InvalidOperationException("Employee not found.");

        if (employee.Status != EmployeeStatus.Active)
        {
            throw new InvalidOperationException(
                $"Invalid transition from {employee.Status} to Inactive.");
        }

        employee.Status = EmployeeStatus.Inactive;
        employee.UpdatedAt = now.UtcDateTime;

        _db.EmployeeOffboardings.Add(new EmployeeOffboarding
        {
            Id = operationId,
            EmployeeId = employeeId,
            CreatedAt = now.UtcDateTime
        });

        _db.OutboxMessages.AddRange(
            OutboxMessage.Create(
                operationId,
                "CalendarEventUpdateRequested",
                new { employeeId, calendarEventId, employee.DisplayName },
                now.UtcDateTime),
            OutboxMessage.Create(
                operationId,
                "OffboardingNotificationRequested",
                new { employeeId, employee.Email },
                now.UtcDateTime));

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        return operationId;
    }
}
```

Worker riêng đọc outbox, thực hiện Graph/notification, retry transient failures và đánh dấu trạng thái xử lý. Cơ chế claim message phải an toàn khi có nhiều worker, ví dụ dùng atomic update/locking strategy phù hợp với database đang dùng.

## Trade-offs

- Outbox tăng thêm table, worker và trạng thái vận hành nhưng đổi lại giảm lock duration và làm recovery rõ ràng.
- Eventual consistency nghĩa là UI phải chấp nhận trạng thái “business change đã commit, integrations đang xử lý”.
- Nếu external system hỗ trợ idempotency key thì nên dùng; nếu không, cần deduplication ở phía mình theo operation/business key.
- Nếu business thực sự yêu cầu synchronous confirmation từ Graph trước khi đổi trạng thái DB, flow cần thiết kế compensation rõ ràng; không nên giả định SQL rollback sẽ hoàn tác external side effect.

## Cách kiểm thử

1. **Concurrency test:** gửi hai request offboard cùng employee, chỉ một transition hợp lệ và không tạo duplicate workflow.
2. **Failure-path test:** DB commit thành công nhưng Graph fail; xác nhận outbox còn pending và retry được.
3. **Idempotency test:** cùng outbox message được deliver hai lần, notification/calendar không tạo kết quả business trùng không kiểm soát.
4. **Load test:** dependency giả lập latency 20–30 giây, xác nhận transaction DB không bị giữ trong khoảng đó.
5. **Recovery test:** worker crash sau khi gọi external API nhưng trước khi đánh dấu success; hệ thống xử lý retry an toàn.

## Quan sát trong production

Theo dõi:

- transaction duration và DB lock wait,
- deadlock count / timeout count,
- outbox backlog và oldest message age,
- delivery attempts, success/failure rate theo dependency,
- Graph/notification latency và status code,
- số message vượt retry threshold,
- correlation theo `OperationId` từ request tới worker và dependency call.

# Code Review Challenge 2 — `.Result` trong ASP.NET Core làm latency tăng mạnh và Thread Pool bị nghẽn khi dependency chậm

**Chủ đề:** async/await, Thread Pool starvation, cancellation, HTTP client usage, error handling, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một endpoint tổng hợp thông tin user từ database và hai external APIs: profile service và permission service. Endpoint trung bình 80 request/giây, peak 600 request/giây.

Bình thường external APIs trả về trong 100–300 ms. Khi permission service chậm lên 3–5 giây, production ghi nhận:

- request queue tăng nhanh,
- latency toàn API tăng dù CPU chưa luôn ở 100%,
- số Thread Pool thread tăng,
- một số request timeout dây chuyền,
- khi client huỷ request, server vẫn tiếp tục gọi dependency,
- lỗi từ dependency thường bị trả thành HTTP 500 chung chung.

Team từng nghĩ rằng dùng `Task.Run` và `.Result` sẽ giúp “chạy song song” hai API call.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/users")]
public sealed class UserSummaryController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ProfileClient _profileClient;
    private readonly PermissionClient _permissionClient;

    public UserSummaryController(
        AppDbContext db,
        ProfileClient profileClient,
        PermissionClient permissionClient)
    {
        _db = db;
        _profileClient = profileClient;
        _permissionClient = permissionClient;
    }

    [HttpGet("{userId:guid}/summary")]
    public IActionResult GetSummary(Guid userId)
    {
        var user = _db.Users
            .AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == userId)
            .Result;

        if (user == null)
        {
            return NotFound();
        }

        var profileTask = Task.Run(() =>
            _profileClient.GetProfileAsync(user.ExternalId));

        var permissionTask = Task.Run(() =>
            _permissionClient.GetPermissionsAsync(user.ExternalId));

        Task.WaitAll(profileTask, permissionTask);

        return Ok(new
        {
            user.Id,
            user.DisplayName,
            Profile = profileTask.Result,
            Permissions = permissionTask.Result
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Sync-over-async bằng `.Result` trên EF Core query

**Problem:** Request thread block chờ `SingleOrDefaultAsync`.  
**Why it happens:** Async API bị chuyển về synchronous wait.  
**Production impact:** Khi concurrency cao, nhiều thread bị giữ trong lúc I/O chờ database; throughput giảm và có thể góp phần Thread Pool starvation.  
**Severity:** High  
**Recommended fix:** Action trả `Task<IActionResult>` và `await` query.

### 2. `Task.Run` bọc I/O async là thừa và làm tăng pressure lên Thread Pool

**Problem:** Hai async dependency call bị bọc trong `Task.Run`.  
**Why it happens:** Nhầm rằng mọi parallelism cần thêm thread.  
**Production impact:** Scheduler phải cấp worker thread chỉ để bắt đầu một I/O operation vốn đã async, tạo overhead và cạnh tranh thread dưới tải.  
**Severity:** High  
**Recommended fix:** Gọi trực tiếp hai method async rồi await chúng.

### 3. `Task.WaitAll` block request thread

**Problem:** Thread xử lý request đứng chờ cả hai task hoàn tất.  
**Why it happens:** Dùng synchronous blocking API trong async-capable request pipeline.  
**Production impact:** Khi dependency chậm, hàng trăm request cùng giữ thread, queue tăng và latency lan sang endpoint khác.  
**Severity:** High  
**Recommended fix:** `await Task.WhenAll(profileTask, permissionTask)`.

### 4. Không propagate cancellation token

**Problem:** Database và hai dependency không nhận `HttpContext.RequestAborted`.  
**Why it happens:** Action synchronous không expose cancellation flow.  
**Production impact:** Client disconnect nhưng server vẫn giữ DB/network work, làm lãng phí connection/thread/resource dưới tải.  
**Severity:** High  
**Recommended fix:** Nhận `CancellationToken cancellationToken` trong action và truyền xuyên suốt các dependency.

### 5. Không có timeout budget cho dependency

**Problem:** Endpoint phụ thuộc hoàn toàn vào timeout mặc định/cấu hình bên dưới.  
**Why it happens:** Không có latency budget theo request.  
**Production impact:** Một dependency chậm có thể giữ request rất lâu, tạo cascading failure.  
**Severity:** High  
**Recommended fix:** Đặt timeout policy/budget phù hợp ở typed client hoặc resilience layer; không retry mù mọi lỗi.

### 6. Failure handling không phân biệt dependency nào lỗi

**Problem:** Exception từ `WaitAll`/`.Result` sẽ bubble thành lỗi chung.  
**Why it happens:** Không có mapping failure semantics.  
**Production impact:** Client nhận 500 không rõ nguyên nhân; observability kém; không tận dụng được partial response nếu business cho phép.  
**Severity:** Medium  
**Recommended fix:** Làm rõ requirement: fail toàn endpoint, fallback, hay partial response. Map lỗi dependency thành status/result có ý nghĩa và log dependency name.

### 7. Không có trace/metric theo từng dependency

**Problem:** Không đo duration hoặc failure rate riêng cho profile/permission.  
**Why it happens:** Endpoint chỉ tập trung happy path.  
**Production impact:** Khó xác định dependency gây saturation hoặc regression.  
**Severity:** Medium  
**Recommended fix:** Distributed trace/span cho DB + mỗi HTTP dependency, metric duration/error/timeout/cancelled.

### 8. Không giới hạn fan-out/capacity khi dependency bị suy giảm

**Problem:** Mọi request tiếp tục bắn hai dependency call ngay cả khi downstream đang quá tải.  
**Why it happens:** Không có backpressure/resilience strategy.  
**Production impact:** Có thể khuếch đại outage của downstream và làm hệ thống mình cạn connection/request slots.  
**Severity:** Medium  
**Recommended fix:** Tùy requirement, dùng timeout, circuit breaker/bulkhead/concurrency limit ở resilience layer và rate/capacity planning phù hợp.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/users")]
public sealed class UserSummaryController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ProfileClient _profileClient;
    private readonly PermissionClient _permissionClient;

    public UserSummaryController(
        AppDbContext db,
        ProfileClient profileClient,
        PermissionClient permissionClient)
    {
        _db = db;
        _profileClient = profileClient;
        _permissionClient = permissionClient;
    }

    [HttpGet("{userId:guid}/summary")]
    public async Task<IActionResult> GetSummary(
        Guid userId,
        CancellationToken cancellationToken)
    {
        var user = await _db.Users
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == userId,
                cancellationToken);

        if (user == null)
        {
            return NotFound();
        }

        var profileTask = _profileClient.GetProfileAsync(
            user.ExternalId,
            cancellationToken);

        var permissionTask = _permissionClient.GetPermissionsAsync(
            user.ExternalId,
            cancellationToken);

        try
        {
            await Task.WhenAll(profileTask, permissionTask);
        }
        catch (OperationCanceledException)
            when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            return StatusCode(
                StatusCodes.Status503ServiceUnavailable,
                new { message = "A required dependency is unavailable." });
        }

        return Ok(new
        {
            user.Id,
            user.DisplayName,
            Profile = await profileTask,
            Permissions = await permissionTask
        });
    }
}
```

Trong production, timeout/retry/circuit breaker nên đặt ở typed client/resilience layer thay vì viết ad-hoc trong controller. Nếu business cho phép partial response, implementation nên biểu diễn rõ field nào degraded thay vì luôn trả 503.

## Trade-offs

- `Task.WhenAll` giảm tổng latency so với gọi tuần tự nhưng tăng concurrent pressure lên dependencies; cần capacity planning.
- Timeout ngắn bảo vệ hệ thống nhưng có thể tăng lỗi giả khi dependency chỉ chậm tạm thời.
- Retry chỉ phù hợp với lỗi transient và phải xét idempotency; retry ngay trong peak outage có thể làm tình hình tệ hơn.
- Partial response tăng availability nhưng làm API contract và client logic phức tạp hơn.

## Cách kiểm thử

1. **Load test:** 600 concurrent RPS với dependency latency tăng từ 200 ms lên 5 giây; theo dõi queue, Thread Pool và latency.
2. **Cancellation test:** client disconnect giữa request; xác nhận DB/HTTP calls được cancel sớm khi dependency hỗ trợ cancellation.
3. **Failure-path test:** profile thành công, permission timeout; xác nhận response đúng theo policy và trace chỉ rõ dependency lỗi.
4. **Timeout test:** dependency treo lâu hơn budget; xác nhận endpoint không giữ request vô hạn.
5. **Regression test:** xác nhận hai external calls thực sự chạy concurrent nhưng không dùng `Task.Run`.

## Quan sát trong production

Theo dõi:

- request rate, p50/p95/p99 latency và in-flight requests,
- Thread Pool thread count/queue length,
- dependency duration, timeout, cancellation và error rate,
- outbound connection pool observations,
- DB query duration,
- distributed traces với span cho profile/permission,
- alert khi downstream latency hoặc timeout rate vượt ngưỡng vận hành.

## Câu hỏi phỏng vấn mở rộng

1. Nếu hai dependency đều chịu tải kém khi fan-out concurrent, bạn bảo vệ chúng bằng cơ chế nào?
2. Khi nào gọi tuần tự lại hợp lý hơn `Task.WhenAll`?
3. Nếu permission là critical nhưng profile chỉ là optional, bạn thay đổi contract và failure handling ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Không giữ database transaction mở trong lúc chờ external network nếu business không yêu cầu synchronous atomicity bất khả thi.
- External side effects cần được thiết kế cùng retry, idempotency và recovery state; transactional outbox là một pattern hữu ích khi phù hợp.
- Async I/O không đồng nghĩa với `Task.Run`; sync-over-async có thể làm giảm throughput nghiêm trọng dưới tải.
- Cancellation, timeout và dependency failure semantics phải là một phần của API design chứ không chỉ là chi tiết implementation.

## Mẫu tư duy cần nhớ

- Thu hẹp transaction boundary trước khi tối ưu lock.
- Thiết kế retry cùng idempotency và recovery state.
- Async end-to-end; tránh block thread khi đang chờ I/O.
- Một dependency chậm có thể trở thành cascading failure nếu không có timeout/backpressure.
- Observability phải theo workflow và dependency, không chỉ log request cuối cùng.
