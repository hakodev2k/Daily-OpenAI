# Câu 1 — `Span<T>` giúp giảm allocation, nhưng tại sao không thể giữ nó trong field hoặc qua `await`?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET 8, `Span<T>`, `ReadOnlySpan<T>`, `Memory<T>`, stack vs heap, `ref struct`, async state machine, allocation, parsing, performance, benchmarking

## Bối cảnh

Một ASP.NET Core .NET 8 API nhận các dòng dữ liệu telemetry dạng text. Mỗi request có thể chứa vài nghìn records. Team đang tối ưu parser vì profiler cho thấy nhiều allocation từ `Substring`, `Split` và temporary strings.

Một developer refactor parser sang `ReadOnlySpan<char>`:

```csharp
public static DeviceRecord Parse(ReadOnlySpan<char> line)
{
    var first = line.IndexOf('|');
    var second = line[(first + 1)..].IndexOf('|') + first + 1;

    var deviceId = line[..first];
    var timestamp = line[(first + 1)..second];
    var value = line[(second + 1)..];

    return new DeviceRecord(
        deviceId.ToString(),
        DateTimeOffset.Parse(timestamp),
        decimal.Parse(value));
}
```

Sau đó team muốn dùng cùng technique cho một pipeline async:

```csharp
public sealed class TelemetryProcessor
{
    private ReadOnlySpan<char> _lastDeviceId;

    public async Task ProcessAsync(
        string line,
        CancellationToken cancellationToken)
    {
        ReadOnlySpan<char> span = line.AsSpan();
        var separator = span.IndexOf('|');
        var deviceId = span[..separator];

        await SaveAsync(deviceId.ToString(), cancellationToken);

        _lastDeviceId = deviceId;
    }
}
```

Code trên gặp hạn chế từ compiler. Một engineer cho rằng “`Span<T>` chỉ là một array slice nên compiler quá bảo thủ”. Một engineer khác đề xuất thay toàn bộ thành `Memory<char>` vì “Memory giống Span nhưng dùng được ở mọi nơi”.

Trong production, parser hiện tiêu thụ CPU đáng kể nhưng chưa có benchmark xác định allocation nào thực sự là bottleneck. Payload có cả valid và invalid input. API cần giữ throughput cao mà vẫn dễ maintain.

## Câu hỏi chính

Hãy giải thích **`Span<T>`/`ReadOnlySpan<T>` thực chất đại diện cho điều gì, vì sao chúng là `ref struct`, vì sao không thể được lưu tùy ý trên heap hoặc sống qua một `await`, và `Memory<T>` giải quyết bài toán lifetime khác như thế nào**. Sau đó đánh giá parser hiện tại: allocation nào đã giảm, allocation nào vẫn còn, khi nào dùng Span có lợi thực sự, và bạn sẽ verify performance/correctness trước khi rollout ra sao.

## Câu hỏi làm rõ nên cân nhắc

1. Parser đang xử lý `string`, UTF-8 bytes hay stream dữ liệu lớn từ network/file?
2. Profiler cho thấy allocation/GC pressure nằm ở `Split`/`Substring`, parsing primitives hay object creation của `DeviceRecord`?
3. Có requirement giữ slice sau khi method return hoặc sau `await` hay chỉ cần xử lý đồng bộ trong một scope ngắn?
4. Input invalid thường xuyên tới mức exception từ `DateTimeOffset.Parse`/`decimal.Parse` trở thành performance concern không?
5. Throughput target, latency p95/p99 và allocation budget hiện tại là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Đừng nghĩ Span như một collection độc lập. Hãy nghĩ nó là một **view có giới hạn lifetime** trỏ vào vùng memory do nơi khác sở hữu.

### Gợi ý 2

Một `async` method có thể bị transform thành state machine sống trên heap. Hãy hỏi điều gì xảy ra nếu state machine giữ một reference tới stack memory sau khi stack frame gốc không còn hợp lệ.

### Gợi ý 3

Tối ưu parser không đồng nghĩa loại bỏ mọi allocation. Hãy đo xem conversion nào vẫn tạo object/string và primitive parsing có overload nhận Span hay không.

## Cấu trúc trả lời đề xuất

1. Làm rõ workload và evidence hiện tại.
2. Giải thích representation/lifetime của Span.
3. Giải thích lý do `ref struct` restrictions.
4. Giải thích async state machine interaction.
5. So sánh `Span<T>` và `Memory<T>` theo ownership/lifetime/use case.
6. Audit allocation của parser hiện tại.
7. Đề xuất parsing approach an toàn hơn.
8. Benchmark allocation/CPU.
9. Test invalid input và edge cases.
10. Monitor production sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Span<T>`/`ReadOnlySpan<T>` là view liên tục trên một vùng memory; chúng không sở hữu dữ liệu.
- `Span<T>` là `ref struct`, bị giới hạn để không thoát sang heap theo cách có thể làm reference tới stack memory sống lâu hơn lifetime hợp lệ.
- Async methods có thể được compiler transform thành state machine; locals cần sống qua `await` có thể trở thành fields của state machine, do đó Span không thể tùy ý sống qua suspension point.
- Span không thể là field của một normal class như `TelemetryProcessor`.
- `Memory<T>`/`ReadOnlyMemory<T>` phù hợp hơn khi cần representation có thể được lưu trên heap hoặc đi qua async boundary; tại điểm xử lý synchronous có thể lấy `.Span`.
- `deviceId.ToString()` vẫn tạo string allocation; `DeviceRecord` nếu là class cũng vẫn là object allocation.
- `DateTimeOffset.Parse(ReadOnlySpan<char>)` và numeric parsing overloads có thể giúp tránh intermediate string allocations khi dùng đúng API.
- Span optimization phải được chứng minh bằng profiler/benchmark; không nên tăng complexity nếu allocation không phải bottleneck thực tế.

### Điểm cộng

- Phân biệt Span lifetime safety với GC pinning: Span không mặc định pin managed objects.
- Nhận ra slicing Span rất rẻ vì chủ yếu tạo view mới, không copy underlying data.
- Dùng `TryParse` thay vì exception-driven control flow nếu invalid input là expected path.
- Cân nhắc parse trực tiếp từ UTF-8 bytes nếu input gốc đã là bytes và conversion sang string đang là cost lớn.
- Dùng BenchmarkDotNet hoặc benchmark harness đáng tin cậy với realistic payload distribution, không chỉ stopwatch một lần.

### Senior+

- Giải thích được vì sao compiler restriction là memory-safety guarantee chứ không chỉ API limitation.
- Phân biệt ownership với view: `Memory<T>` cho phép lifetime dài hơn nhưng vẫn không tự giải quyết ownership/race nếu backing buffer bị pool/reuse.
- Nếu dùng pooled buffers (`ArrayPool<T>`), nhận ra `Memory<T>` không làm buffer an toàn sau khi đã trả pool.
- Đưa ra optimization boundary rõ: parse synchronously bằng Span, materialize chỉ những values thực sự phải sống lâu hơn.

## Hướng giải quyết tham khảo

`Span<T>` là một stack-only abstraction đại diện cho một contiguous region of memory. Region đó có thể nằm trên managed array, string, stack memory hoặc unmanaged memory tùy cách tạo. Bản thân Span không sở hữu vùng nhớ; nó giữ đủ thông tin để tham chiếu tới region và độ dài.

Slicing như:

```csharp
var deviceId = span[..separator];
```

không copy các characters. Nó chỉ tạo một view mới trên cùng backing memory. Đây là lý do Span có thể loại bỏ rất nhiều temporary allocations vốn xuất hiện khi dùng `Substring` hoặc `Split`.

Tuy nhiên, vì Span có thể tham chiếu tới stack memory, runtime/compiler phải bảo đảm Span không sống lâu hơn backing memory. Vì vậy nó là `ref struct` với escape rules nghiêm ngặt. Một normal class field sống trên heap có thể tồn tại lâu hơn stack frame, nên:

```csharp
private ReadOnlySpan<char> _lastDeviceId;
```

không hợp lệ.

Tương tự, `await` có thể suspend method. Compiler transform async method thành state machine. Những locals cần dùng sau `await` có thể phải trở thành state-machine fields. Nếu một Span được giữ qua suspension point, lifetime của nó có thể không còn phù hợp với backing storage. Vì vậy compiler hạn chế pattern này.

Khi cần dữ liệu đi qua async boundary, `ReadOnlyMemory<char>` có thể là abstraction phù hợp hơn:

```csharp
public async Task ProcessAsync(
    ReadOnlyMemory<char> line,
    CancellationToken cancellationToken)
{
    var separator = line.Span.IndexOf('|');

    var deviceIdMemory = line[..separator];

    await SaveAsync(
        deviceIdMemory.ToString(),
        cancellationToken);

    // Memory can survive the await, assuming its backing owner is still valid.
}
```

Nhưng `Memory<T>` không phải “Span tốt hơn”. Nó có trade-off khác: có thể sống trên heap/qua async boundary, nhưng không thể cover mọi loại stack memory như Span. Quan trọng hơn, nếu backing memory đến từ pooled buffer rồi buffer bị trả về pool, việc giữ Memory lại vẫn là bug về ownership/lifetime logic.

Parser có thể tiếp tục giảm allocations:

```csharp
public static bool TryParse(
    ReadOnlySpan<char> line,
    out DeviceRecord? record)
{
    record = null;

    var first = line.IndexOf('|');
    if (first <= 0)
        return false;

    var remainder = line[(first + 1)..];
    var relativeSecond = remainder.IndexOf('|');
    if (relativeSecond <= 0)
        return false;

    var second = first + 1 + relativeSecond;

    var deviceId = line[..first];
    var timestampText = line[(first + 1)..second];
    var valueText = line[(second + 1)..];

    if (!DateTimeOffset.TryParse(timestampText, out var timestamp))
        return false;

    if (!decimal.TryParse(valueText, out var value))
        return false;

    record = new DeviceRecord(
        deviceId.ToString(),
        timestamp,
        value);

    return true;
}
```

Ở đây vẫn có allocation cho `deviceId.ToString()` và `DeviceRecord` nếu đó là reference type. Điều này có thể hoàn toàn chấp nhận được nếu device ID cần được lưu sau parser và domain object cần tồn tại lâu hơn input buffer. Mục tiêu không phải “zero allocation bằng mọi giá”, mà là loại bỏ allocations trung gian không cần thiết.

Kế hoạch verify:

- benchmark implementation cũ và mới trên payload thực tế;
- đo throughput, CPU, allocated bytes/op, Gen0/Gen1 collections;
- test invalid input distribution;
- profile production-like load để xác nhận parser nằm trên hot path;
- test Unicode, empty fields, malformed timestamps/numbers, very large lines;
- nếu dùng pooled buffers, test ownership/lifetime dưới concurrency;
- rollout canary và theo dõi request latency, CPU, GC allocation rate.

Nếu profiler cho thấy database/network latency áp đảo parser cost, thêm Span complexity có thể không đáng. Nếu parser là CPU/allocation hotspot thật, Span có thể mang lại lợi ích đáng kể mà không cần unsafe code.

## Mẫu trả lời trong phỏng vấn

“Em xem Span như một view lên memory chứ không phải collection sở hữu data. Slicing Span không copy dữ liệu, nên nó giúp bỏ các allocation kiểu Substring/Split. Nhưng vì Span có thể trỏ vào stack memory, nó là ref struct và compiler phải ngăn nó escape sang heap hoặc sống qua async suspension point. Async method có thể thành state machine trên heap, nên một Span local cần tồn tại sau await là vấn đề về lifetime safety.

Nếu cần dữ liệu sống qua await, em dùng Memory hoặc materialize value cần thiết. Nhưng Memory cũng không giải quyết ownership nếu backing buffer bị trả về pool.

Trong parser hiện tại, `deviceId.ToString()` và domain object vẫn allocate; em có thể dùng TryParse overload nhận Span để tránh intermediate strings và tránh exceptions trên expected invalid input. Em sẽ benchmark CPU + allocated bytes/op và profile dưới realistic load trước khi rollout. Nếu parser không phải bottleneck thì em giữ code đơn giản hơn.”

## Câu hỏi đào sâu

1. Nếu input nằm trong buffer thuê từ `ArrayPool<byte>` và bạn trả buffer về pool ngay sau khi enqueue một `ReadOnlyMemory<byte>` sang worker khác, điều gì có thể xảy ra?
2. Một teammate đề xuất dùng Span ở mọi method để “code nhanh hơn”. Bạn sẽ đặt tiêu chí nào để phản biện?
3. Nếu parser từ UTF-8 request body hiện phải tạo một `string` lớn trước khi dùng `ReadOnlySpan<char>`, bạn sẽ tìm optimization boundary ở đâu tiếp theo?

## Lỗi trả lời thường gặp

- Nói Span luôn nằm trên stack và backing data cũng luôn nằm trên stack.
- Nghĩ `Span<T>` là một copied sub-array.
- Chỉ nói “compiler không cho” mà không giải thích lifetime/async state machine.
- Đổi sang `Memory<T>` rồi giả định mọi lifetime/ownership problem biến mất.
- Tối ưu zero-allocation mà không benchmark hoặc làm code khó maintain hơn nhiều.

## Thang điểm 0–10

- **0–2:** chỉ biết Span “nhanh hơn array/string”.
- **3–4:** biết Span tránh allocation nhưng không giải thích `ref struct`/async restrictions.
- **5–6:** hiểu lifetime, slicing, Memory và remaining allocations.
- **7–8:** có parser design, benchmark/test strategy và ownership reasoning.
- **9–10:** giải thích memory safety/state-machine interaction sâu, pooled-buffer hazards và biết khi nào không nên dùng Span.

# Câu 2 — Upload file lớn lên Azure Blob Storage lúc được lúc lỗi: API đang trở thành bottleneck hay Blob Storage có vấn đề?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, large file upload, streaming, buffering, SAS, Managed Identity, request timeout, memory, reverse proxy, App Service, retry, security, observability, failure recovery

## Bối cảnh

Một document-management platform cho phép user upload PDF, ZIP và media files. Hệ thống chạy ASP.NET Core .NET 8 trên Azure App Service. Backend xác thực user, kiểm tra quyền rồi upload file lên Azure Blob Storage.

Flow hiện tại:

```text
Browser
  → ASP.NET Core API
      → read multipart form
      → copy file vào MemoryStream
      → upload MemoryStream lên Azure Blob Storage
      → lưu metadata vào SQL Server
```

Production symptoms:

- file dưới 20 MB gần như luôn thành công;
- file 300 MB–1.5 GB thỉnh thoảng trả 502/504 hoặc client thấy connection reset;
- khi nhiều user upload đồng thời, App Service memory tăng mạnh và response của các API không liên quan cũng chậm;
- Blob Storage server-side latency dashboard không cho thấy spike rõ rệt tương ứng;
- một số request fail sau khi client đã upload gần hết file vào backend;
- đôi lúc blob đã tồn tại nhưng SQL metadata record chưa được tạo;
- team retry toàn bộ HTTP request từ browser khi thất bại;
- một developer đề xuất tăng App Service memory tier;
- một developer khác muốn cấp public write access trực tiếp cho container để browser upload thẳng;
- security requirement: user chỉ được upload vào logical folder/object scope mà họ được phép; container không được public-write;
- application hiện có Managed Identity truy cập Storage;
- chưa xác minh reverse proxy/request limits, upload buffering behavior, App Service timeout path, exact memory allocations, SDK transfer settings hoặc network throughput.

Không giả định trước Blob Storage là root cause.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo **impact → stabilize → evidence → competing hypotheses → root cause → remediation → prevention**. Phân tích vì sao backend proxying + buffering file lớn có thể làm application trở thành bottleneck, cách phân biệt lỗi ở browser/proxy/App Service/API/Blob Storage, và khi nào nên chuyển sang **direct-to-Blob upload bằng scoped SAS** thay vì proxy toàn bộ file qua backend. Đồng thời giải thích security, consistency và failure-recovery implications của thiết kế mới.

## Câu hỏi làm rõ nên cân nhắc

1. Upload hiện tại buffer toàn file trong memory, temp disk hay stream trực tiếp từ request body?
2. 502/504 được phát ra bởi browser-facing proxy/App Service front end, application hay downstream Blob SDK call?
3. User cần upload tối đa bao nhiêu GB và business cần progress/resume/chunking không?
4. Có antivirus/content validation nào bắt buộc phải chạy trước khi object được coi là usable không?
5. Blob name/container permissions được authorize thế nào và backend có thể phát SAS ngắn hạn chỉ cho một object cụ thể không?

## Gợi ý tư duy

### Gợi ý 1

Một request path có **hai network transfers**: client → API và API → Blob. Hãy xem backend đang làm gì với bytes trong khoảng giữa.

### Gợi ý 2

Nếu Blob đã tồn tại nhưng SQL chưa có record, đây là consistency/failure-ordering problem, không chỉ là timeout problem.

### Gợi ý 3

Direct upload không có nghĩa public container. Authorization có thể xảy ra ở backend, còn data path đi trực tiếp từ browser tới Blob qua credential tạm thời có scope hẹp.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và error scope.
2. Giảm pressure trong incident.
3. Xây timeline request từ browser tới Blob.
4. Thu memory/GC/network/request/dependency telemetry.
5. Liệt kê hypotheses theo từng network/application layer.
6. Xác minh buffering và timeout limits.
7. Sửa immediate backend flow nếu cần.
8. Đánh giá proxy streaming vs direct-to-Blob.
9. Thiết kế upload state/metadata consistency.
10. Thiết kế security và file validation.
11. Test large-file/concurrency/failure paths.
12. Monitor sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `MemoryStream` với hàng trăm MB/GB cho nhiều concurrent uploads có thể gây memory pressure rất lớn; tăng tier chỉ tăng trần, không sửa amplification pattern.
- Proxy upload khiến application nhận toàn bộ data từ client rồi truyền tiếp sang Blob; application chịu bandwidth, connection lifetime, memory/buffering và timeout pressure.
- Phải xác minh source của 502/504 thay vì gọi chung là “Blob timeout”.
- Direct-to-Blob upload có thể dùng short-lived, least-privilege SAS thay vì public write access.
- Backend vẫn chịu trách nhiệm authorize user và xác định object key/scope trước khi phát upload capability.
- SAS cần scope hẹp, thời hạn ngắn và quyền tối thiểu; không phát credential cho cả container nếu chỉ cần một blob.
- Blob upload và SQL metadata update không nằm trong một atomic transaction; cần explicit upload state/reconciliation/cleanup strategy.
- Retry toàn bộ 1.5 GB upload từ đầu có thể rất tốn kém; chunk/block upload/resume strategy cần được đánh giá.
- Security không kết thúc ở authorization: file type/size/content validation, malware scanning/quarantine, overwrite policy và filename handling cũng quan trọng.

### Điểm cộng

- Nếu vẫn proxy qua API, stream thay vì buffer toàn file và giới hạn concurrency/request size hợp lý.
- Dùng block blob semantics/chunk upload cho large files, với retry ở block granularity khi phù hợp.
- Thiết kế trạng thái `PendingUpload → Uploaded → Validating → Ready/Rejected` thay vì coi blob xuất hiện là business record hoàn tất.
- Dùng backend-generated opaque blob key thay vì tin client filename làm storage path.
- Có cleanup job cho orphan blobs và stale pending-upload records.
- Sử dụng Managed Identity ở backend để tạo user delegation SAS khi architecture/security policy phù hợp.

### Senior+

- Phân biệt control plane và data plane: backend authorize/orchestrate, browser đi data path trực tiếp tới Storage.
- Nhận ra direct upload thay đổi observability: backend không còn thấy transfer bytes trực tiếp, cần Storage telemetry/client correlation/upload session IDs.
- Thiết kế finalize endpoint idempotent, verify blob properties trước khi chuyển trạng thái Ready.
- Nếu malware scan là mandatory trước availability, dùng quarantine container/prefix và asynchronous validation workflow.
- Cân nhắc CORS trên Storage cho browser upload nhưng không nhầm CORS với authorization.

## Hướng giải quyết tham khảo

### 1. Stabilize

Trong incident, tôi sẽ xác định file-size threshold và concurrency gây pressure. Nếu large uploads đang làm chậm toàn App Service, có thể tạm giới hạn concurrent large uploads hoặc size theo business-approved guardrail thay vì để toàn hệ thống degrade.

Không tăng memory tier ngay như root-cause fix. Scale-up có thể mua thời gian, nhưng nếu mỗi upload 1 GB được buffer trong memory thì vài uploads đồng thời vẫn có thể bão hòa bất kỳ finite memory tier nào.

### 2. Evidence

Tôi cần correlation ID/upload session ID đi xuyên:

```text
Browser request
→ App Service/front-end
→ ASP.NET Core request
→ Blob SDK dependency
→ SQL metadata write
```

Thu:

- process working set, managed heap size, allocation rate, GC pauses;
- concurrent request count;
- upload duration và request sizes;
- inbound/outbound network throughput;
- App Service HTTP/frontend logs;
- application exceptions/status codes;
- Blob dependency duration/status/error codes;
- Blob Storage server request latency/availability;
- SQL write timing;
- timestamp khi blob xuất hiện so với metadata commit.

Nếu 504 xảy ra trước khi Blob SDK call bắt đầu, Blob không thể là root cause cho request đó.

### 3. Proxy implementation

Anti-pattern:

```csharp
await using var memory = new MemoryStream();
await file.CopyToAsync(memory, cancellationToken);

memory.Position = 0;
await blobClient.UploadAsync(memory, overwrite: false, cancellationToken);
```

Backend đã giữ full payload trước khi bắt đầu upstream upload. Với nhiều users, memory amplification rất lớn.

Nếu requirement buộc proxy, tốt hơn là stream:

```csharp
await using var input = file.OpenReadStream();

await blobClient.UploadAsync(
    input,
    overwrite: false,
    cancellationToken);
```

Nhưng implementation thực tế còn phụ thuộc ASP.NET Core multipart handling, server limits, buffering configuration và Blob SDK transfer behavior. “Có Stream” trong code không tự chứng minh end-to-end không buffer; phải đo.

### 4. Direct-to-Blob design

Một architecture phù hợp large files:

```text
1. Browser → POST /uploads
2. Backend:
   - authenticate + authorize
   - validate requested type/size policy
   - create UploadSession(Pending)
   - generate opaque blob key
   - return short-lived SAS scoped to that blob
3. Browser → Blob Storage directly
4. Browser → POST /uploads/{id}/complete
5. Backend verifies blob properties
6. Validation/scanning
7. Mark metadata Ready
```

Container không cần public write. SAS có thể chỉ cho phép create/write tới đúng object và hết hạn nhanh.

Pseudocode concept:

```csharp
[Authorize]
[HttpPost("uploads")]
public async Task<UploadTicket> CreateUploadAsync(
    CreateUploadRequest request,
    CancellationToken ct)
{
    await _authorization.EnsureCanUploadAsync(
        User,
        request.DocumentScopeId,
        ct);

    _policy.ValidateSizeAndDeclaredType(
        request.Size,
        request.ContentType);

    var session = UploadSession.CreatePending(
        request.DocumentScopeId,
        opaqueBlobName: Guid.NewGuid().ToString("N"));

    await _repository.AddAsync(session, ct);

    var sas = await _sasFactory.CreateWriteOnlyBlobSasAsync(
        session.BlobName,
        expiresIn: TimeSpan.FromMinutes(15),
        ct);

    return new UploadTicket(session.Id, sas);
}
```

### 5. Finalization và consistency

Blob + SQL không atomic. `complete` phải idempotent:

```text
PendingUpload
   ↓ blob verified
Uploaded
   ↓ scan/validation
Ready
```

Nếu browser upload xong nhưng không gọi complete, reconciliation job có thể kiểm tra stale sessions. Nếu blob có nhưng session expired, cleanup policy quyết định delete/quarantine.

Nếu SQL update fail sau upload, retry finalize chứ không upload lại bytes từ đầu.

### 6. Security

- SAS least privilege, short-lived, scope một object khi có thể;
- HTTPS only;
- server-generated object names;
- enforce expected size/content constraints ở finalize;
- không tin `Content-Type` hoặc filename do client khai báo;
- malware scanning/quarantine nếu requirement có;
- không overwrite arbitrary existing blob;
- Storage account/container không public-write;
- audit upload ticket issue/finalization;
- CORS chỉ cho trusted frontend origins nếu browser upload cần cross-origin access, nhưng authorization vẫn nằm ở SAS.

### 7. Testing

- upload 20 MB, 500 MB, 1.5 GB;
- concurrent large uploads;
- network interruption giữa chunks;
- SAS expiry giữa upload;
- browser upload thành công nhưng finalize request fail;
- duplicate finalize calls;
- malicious filename/content-type mismatch;
- orphan cleanup;
- Blob 429/5xx transient failure;
- App Service restart trong control-plane call.

### 8. Monitoring

Theo dõi:

- upload success/failure by stage;
- file-size distribution;
- session duration;
- orphan/pending count;
- finalize retry rate;
- Storage 4xx/5xx/throttling;
- client upload latency nếu collect được;
- App Service memory/GC/network pressure;
- scan latency/rejection rate;
- SAS issue failures.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách incident theo từng hop thay vì gọi chung là Blob timeout. Flow hiện tại client gửi file vào API, API buffer MemoryStream rồi gửi lại Blob, nên backend đang chịu hai data transfers và full memory amplification. Dưới concurrency, đó là candidate rất mạnh cho memory/GC/network pressure.

Em sẽ correlate 502/504 với App Service frontend logs, ASP.NET Core request, Blob dependency telemetry và memory metrics. Nếu business cần large files thường xuyên, em ưu tiên direct-to-Blob: backend authenticate/authorize, tạo upload session và phát short-lived SAS chỉ cho đúng blob; browser upload trực tiếp; sau đó gọi finalize. Container không public-write.

Vì Blob và SQL không atomic, em dùng state machine Pending → Uploaded → Validating → Ready, finalize idempotent và reconciliation cho orphan blob. Nếu cần malware scan thì blob ở quarantine cho tới khi validation pass. Em test concurrent GB uploads, network interruption, SAS expiry và finalize failure. Mục tiêu là backend giữ control-plane/security, còn bulk bytes không cần đi vòng qua application.”

## Câu hỏi đào sâu

1. Nếu security team không cho phép SAS xuất hiện ở browser, bạn có thể cải thiện proxy architecture thế nào mà vẫn chịu được file nhiều GB?
2. Nếu browser upload thành công nhưng user đóng tab trước khi gọi finalize, bạn làm sao phân biệt orphan hợp lệ với upload đang chậm?
3. Nếu business yêu cầu antivirus scan trước khi bất kỳ internal service nào đọc file, bạn thiết kế container/state/permissions thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng App Service memory tier.
- Khẳng định Blob Storage chậm chỉ vì request upload timeout.
- Đề xuất public write container cho direct upload.
- Dùng SAS rộng, thời hạn dài hoặc scope cả container không cần thiết.
- Bỏ qua consistency giữa blob và SQL metadata.

## Thang điểm 0–10

- **0–2:** chỉ tăng timeout/memory hoặc blame Storage.
- **3–4:** nhận ra buffering nhưng chưa có end-to-end failure/security reasoning.
- **5–6:** có streaming/direct-upload concept, scoped SAS và telemetry plan.
- **7–8:** có idempotent finalize, upload state, scanning, cleanup và failure-path tests.
- **9–10:** phân tích control-plane/data-plane, ownership, observability shift, partial failure và chọn proxy/direct architecture theo explicit security/business constraints.

# Câu 3 — Modernize .NET Framework 4.5 trên IIS: rewrite toàn bộ hay migration từng bước sang .NET 8/App Service Linux?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, .NET 8, ASP.NET MVC/Web API, IIS, Windows Server, Azure App Service on Linux, modernization, dependency compatibility, incremental migration, API boundaries, data migration, CI/CD, testing, observability, rollout, rollback, architecture trade-offs

## Bối cảnh

Một internal enterprise platform được xây khoảng 8 năm trước:

- ASP.NET MVC + ASP.NET Web API trên .NET Framework 4.5;
- host trên IIS/Windows Server;
- SQL Server dùng chung cho nhiều modules;
- authentication dựa trên legacy corporate identity integration;
- server-side session được dùng ở một số flows;
- có scheduled jobs chạy trong web application;
- một số modules dùng static helpers/service locator và tight coupling;
- frontend gồm Razor + jQuery, vài màn hình Angular legacy;
- CI dùng Jenkins và deployment qua Octopus Deploy;
- production support phụ thuộc khá nhiều vào IIS logs, Windows Event Log và manual server access;
- test coverage thấp, có một số integration tests nhưng gần như không có E2E automation;
- hệ thống vẫn tạo business value và user không chấp nhận downtime dài.

Mục tiêu được đề xuất:

- đưa backend lên modern .NET;
- có thể host phần mới trên Azure App Service on Linux;
- giảm phụ thuộc Windows Server/IIS nếu hợp lý;
- cải thiện deployment, observability và testability;
- giữ SQL Server trong giai đoạn đầu;
- Product muốn tiếp tục ship features trong quá trình migration;
- team 6–8 developers, không có bandwidth cho dự án rewrite kéo dài 18 tháng mà không ra feature;
- một architect đề xuất rewrite toàn bộ thành microservices + Kubernetes;
- một engineer khác đề xuất chỉ in-place upgrade từng target framework cho tới .NET 8;
- chưa có inventory đầy đủ về NuGet dependencies, System.Web usage, third-party components, Windows-specific APIs, authentication library compatibility hoặc batch jobs.

## Câu hỏi chính

Hãy đề xuất **modernization strategy có thể triển khai dần** cho hệ thống này. Bạn phải quyết định cách inventory dependencies, xác định migration seams, xử lý shared database và authentication, tách background jobs khỏi web lifecycle, chọn hosting cho từng phase, duy trì backward compatibility, test/regression strategy, CI/CD, observability, rollout và rollback. Đồng thời so sánh các lựa chọn:

- rewrite toàn bộ;
- in-place/framework-by-framework upgrade;
- incremental strangler/modular migration;
- microservices/Kubernetes ngay từ đầu;

và giải thích khi nào recommendation của bạn sẽ thay đổi.

## Câu hỏi làm rõ nên cân nhắc

1. Những modules nào tạo thay đổi business thường xuyên, modules nào ổn định nhưng khó migrate?
2. Dependency nào khóa hệ thống vào `System.Web`, Windows-only API, native library hoặc unsupported vendor component?
3. Authentication/SSO hiện tại có contract nào cho phép old và new applications cùng xác thực user trong transition không?
4. Shared SQL schema có mức coupling nào giữa modules: foreign keys, stored procedures, cross-module transactions, direct table access?
5. RTO/RPO, rollback tolerance và thời gian chấp nhận coexistence old/new system là bao lâu?

## Gợi ý tư duy

### Gợi ý 1

Bước đầu tiên không phải chọn .NET 8 hay Kubernetes. Hãy xây dependency/runtime inventory và tìm **seams có thể migration độc lập**.

### Gợi ý 2

Modernization thành công khi old và new versions có thể coexist trong một khoảng thời gian mà user vẫn dùng hệ thống bình thường.

### Gợi ý 3

Tách “runtime modernization” khỏi “architecture rewrite”. Bạn không nhất thiết phải đổi framework, database ownership, frontend và deployment topology trong cùng một release.

## Cấu trúc trả lời đề xuất

1. Clarify business constraints và migration success criteria.
2. Inventory runtime/dependencies/Windows coupling.
3. Establish observability + regression safety trước thay đổi lớn.
4. Xác định module boundaries/seams.
5. Chọn migration sequence theo risk/value.
6. Thiết kế old/new routing và authentication coexistence.
7. Quản lý shared database transition.
8. Tách background processing khỏi web process lifecycle.
9. Chọn hosting per phase.
10. CI/CD và compatibility gates.
11. Rollout/canary/rollback.
12. Đánh giá khi nào microservices/Kubernetes đáng giá.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nên rewrite toàn bộ chỉ vì code cũ; rewrite có feature freeze risk, regression risk và business delay rất lớn.
- Không thể giả định .NET Framework 4.5 → .NET 8 là simple target-framework change; `System.Web`, APIs, packages và hosting model khác nhau cần được inventory.
- Migration nên bắt đầu bằng dependency/compatibility inventory và characterization tests.
- Tách runtime migration khỏi unnecessary architecture changes giúp giảm blast radius.
- Old/new systems cần coexistence strategy: routing, auth/session, API contracts và shared data behavior.
- Shared database có thể được giữ tạm thời nhưng cần guardrails; direct cross-module table access làm boundary extraction khó hơn.
- Background jobs không nên tiếp tục phụ thuộc web application/IIS lifecycle trong architecture mới nếu reliability yêu cầu execution độc lập.
- App Service Linux có thể phù hợp phần modern .NET nếu dependencies không còn Windows-specific; không bắt buộc chuyển mọi component sang Linux ngay.
- Microservices/Kubernetes không phải requirement mặc định của modernization.
- Rollback phải tính cả schema/data compatibility, không chỉ application binary.

### Điểm cộng

- Dùng migration assessment tooling/dependency graph và classify blockers: source-compatible, package replacement, rewrite adapter, Windows-only, unknown.
- Tạo anti-corruption/adaptor layer quanh legacy integrations thay vì spread compatibility code vào domain mới.
- Xây facade/API boundary trước khi tách module nếu old code truy cập trực tiếp internals.
- Dùng reverse proxy/routing để chuyển từng route/module từ old sang new application.
- Authentication bridge có thể dùng common identity provider/token/cookie strategy tùy legacy constraints, nhưng phải design secure coexistence thay vì copy session state mù quáng.
- Tạo observability baseline trước migration để biết regression có thật hay không.
- Dùng Playwright cho critical user journeys trong coexistence period.

### Senior+

- Chọn migration order bằng risk-adjusted value: module đủ độc lập, có testable behavior, tạo operational benefit cao và không nằm ở core transaction coupling quá lớn.
- Phân biệt logical modularization với physical service split; có thể modernize sang modular monolith trước rồi tách service sau nếu evidence cần.
- Đề xuất database ownership tiến hóa: ban đầu shared DB có compatibility contract, sau đó từng module own tables/schema trước khi cân nhắc separate database.
- Thiết kế strangler seam sao cho rollback route về legacy system vẫn khả thi khi data semantics cho phép.
- Nêu trigger cụ thể để chọn Kubernetes/microservices: independent scaling, ownership, deployment cadence, isolation hoặc platform requirement thực sự.

## Hướng giải quyết tham khảo

### 1. Phase 0 — Inventory và safety baseline

Trước khi migrate, lập inventory:

```text
Application
├─ ASP.NET MVC / Web API areas
├─ System.Web dependencies
├─ Authentication/session
├─ NuGet/vendor packages
├─ Windows-only APIs
├─ file system/native dependencies
├─ scheduled jobs
├─ SQL tables/SPs/functions
├─ cross-module transactions
├─ external integrations
└─ deployment/runtime assumptions
```

Classify mỗi dependency:

- works on modern .NET;
- has supported replacement;
- needs adapter;
- requires Windows;
- unclear → spike/POC.

Đồng thời capture baseline:

- critical user journeys;
- p95/p99 endpoints;
- error rates;
- CPU/memory;
- DB query behavior;
- current scheduled-job reliability;
- deployment duration/failure rate.

Thêm characterization/integration tests cho critical behavior trước khi refactor lớn.

### 2. Không trộn tất cả transformations

Một anti-pattern là cùng lúc:

```text
.NET Framework → .NET 8
Monolith → Microservices
IIS → Kubernetes
SQL Server → new datastore
jQuery → React
legacy auth → new auth
```

Khi production regression xảy ra, blast radius và investigation space quá lớn.

Tốt hơn là chia axes:

- runtime modernization;
- hosting modernization;
- architecture modularization;
- UI modernization;
- data ownership;
- identity modernization.

Mỗi phase có measurable exit criteria.

### 3. Chọn seam đầu tiên

Chọn một module tương đối độc lập, ví dụ Reporting hoặc Notifications nếu domain thực tế phù hợp. Không chọn module chỉ vì “nhỏ” nếu nó có cross-database coupling sâu.

Tạo new ASP.NET Core .NET 8 application/module với clean API contract. Routing layer có thể chuyển một subset URLs:

```text
User
  → Reverse Proxy / Gateway
      → /legacy/*    → IIS .NET Framework app
      → /reports/*   → ASP.NET Core .NET 8 app
```

Nếu migration route gặp regression và data contracts vẫn compatible, traffic có thể route về legacy.

### 4. Authentication/session coexistence

Không giả định cookies từ legacy `System.Web` tự tương thích với ASP.NET Core. Cần xác minh actual authentication stack.

Mục tiêu là user không login hai lần. Có thể:

- dùng shared external identity provider/token issuance;
- tạo compatibility bridge có thời hạn;
- hoặc chuyển auth boundary trước khi module migration.

Server-side session nên được inventory theo use case. Nếu session chứa business state quan trọng, phải refactor ownership rõ thay vì đơn giản copy toàn bộ session giữa old/new apps.

### 5. Shared SQL transition

Giai đoạn đầu có thể giữ cùng SQL Server để giảm scope. Nhưng đặt guardrails:

```text
Legacy module A owns tables A*
Modern module B owns tables B*
No new cross-module direct writes without explicit contract
```

Nếu new module vẫn query legacy tables, dùng read adapter/repository có boundary rõ. Tránh new code tiếp tục tăng coupling.

Schema migrations phải backward-compatible trong coexistence period. Destructive changes dùng staged migration khi cần.

Tách database vật lý chỉ khi ownership đã rõ và distributed consistency cost được chấp nhận.

### 6. Background jobs

Scheduled jobs chạy trong IIS web app dễ phụ thuộc recycle/process lifecycle. Trong modernization, tách chúng thành Worker Service, Azure Functions hoặc một hosted worker deployment riêng tùy workload.

Decision criteria:

- execution duration;
- scheduling precision;
- retry/idempotency;
- scale;
- operational model;
- access to dependencies.

Không chọn Functions chỉ vì “cloud-native”; BackgroundService/Worker Service có thể đơn giản hơn cho continuous processing.

### 7. Hosting

New .NET 8 components không dùng Windows-specific dependencies có thể chạy Azure App Service on Linux. Legacy app tiếp tục IIS/Windows cho tới khi migrated.

```text
Phase 1:
IIS legacy + App Service Linux modern module

Phase 2:
majority ASP.NET Core modules on App Service

Phase 3:
retire legacy IIS when last dependency removed
```

Kubernetes chỉ thêm khi workload/platform requirement justify orchestration overhead.

### 8. CI/CD

Jenkins/Octopus có thể tiếp tục nếu đang ổn; modernization không bắt buộc đổi CI tool ngay.

Pipeline cần thêm:

- compile/test matrix;
- package artifact immutability;
- dependency/security scanning;
- migration compatibility check;
- integration tests;
- Playwright smoke tests;
- canary/slot deployment cho new app;
- post-deploy health gate;
- rollback routing.

Tooling có thể được đổi sau nếu business value rõ.

### 9. Observability

Legacy system nên được instrument đủ để so sánh trước/sau. New app dùng structured logs, correlation IDs, traces và Application Insights/Azure Monitor.

Trong coexistence, correlation ID phải đi xuyên proxy → legacy/new app → database/external calls để debug user journey chạy qua cả hai worlds.

### 10. Migration order

Một example roadmap:

**Phase A — Stabilize**  
Inventory, tests, telemetry, dependency spikes.

**Phase B — Extract low-risk boundary**  
Một module sang ASP.NET Core .NET 8, shared SQL nhưng ownership rõ.

**Phase C — Identity/session cleanup**  
Giảm coupling user/session giữa old/new.

**Phase D — Extract background jobs**  
Đưa scheduled work ra khỏi IIS lifecycle.

**Phase E — Migrate remaining modules**  
Theo risk/value, không theo arbitrary folder order.

**Phase F — Retire legacy hosting**  
Chỉ khi Windows/System.Web/vendor blockers được xử lý.

### 11. Khi nào rewrite toàn bộ có thể hợp lý?

Rewrite có thể đáng cân nhắc nếu:

- business requirements đã thay đổi căn bản;
- legacy code không còn phản ánh domain hiện tại;
- không thể tạo reliable seams;
- total cost incremental migration cao hơn đáng kể;
- có budget/time và transition strategy thực tế.

Nhưng ngay cả khi rewrite, vẫn cần coexistence/data migration/cutover plan; “rewrite” không xóa production transition problem.

### 12. Khi nào microservices/Kubernetes đáng giá?

Chỉ khi có evidence như:

- domains có independent ownership;
- scaling profiles rất khác;
- independent deployment cadence đem lại giá trị;
- failure isolation cần process boundary;
- platform team có năng lực vận hành;
- workload cần orchestration capabilities mà App Service không đáp ứng tốt.

Nếu team 6–8 developers và system vẫn là một cohesive business application, modular monolith trên modern .NET có thể là target hợp lý hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng rewrite hay Kubernetes. Bước đầu là inventory System.Web, NuGet/vendor dependencies, Windows APIs, auth/session, jobs và SQL coupling; sau đó dựng characterization tests và observability baseline.

Em tách runtime modernization khỏi architecture rewrite. Em chọn một module có seam rõ, đưa sang ASP.NET Core .NET 8, route traffic theo path giữa legacy IIS và new App Service. Giai đoạn đầu vẫn có thể dùng chung SQL Server nhưng đặt ownership rules và migration backward-compatible để old/new coexist. Auth phải có bridge hoặc common identity contract; em không giả định legacy cookie tự dùng được ở ASP.NET Core.

Scheduled jobs em tách khỏi IIS lifecycle sang worker riêng khi migration phù hợp. Jenkins/Octopus có thể giữ nếu ổn; em thêm test, migration compatibility, canary, health gate và rollback routing. Playwright cover critical cross-system flows.

Em chỉ tách microservices hoặc dùng Kubernetes khi có independent scaling, ownership, deployment hoặc isolation requirement đủ mạnh. Với team 6–8 người, modular modern .NET trên App Service có thể giảm operational risk hơn rất nhiều mà vẫn để mở đường tách service sau.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên cần transaction atomic qua cả tables legacy và tables mới, bạn vẫn tách nó trước không? Bạn sẽ quyết định thế nào?
2. Nếu một vendor library critical chỉ hỗ trợ .NET Framework/Windows trong ít nhất 2 năm nữa, bạn thay đổi roadmap và hosting target ra sao?
3. Product nói rewrite toàn bộ giúp “xóa sạch technical debt”. Bạn sẽ chứng minh hoặc bác bỏ claim đó bằng những loại cost/risk nào?

## Lỗi trả lời thường gặp

- Chọn rewrite toàn bộ chỉ vì code cũ khó đọc.
- Coi migration .NET Framework → .NET 8 là đổi target framework rồi fix compile errors.
- Thêm microservices/Kubernetes vào scope mà không có operational/business trigger.
- Không thiết kế old/new coexistence, authentication và shared-data compatibility.
- Đổi đồng thời runtime, database, frontend, CI/CD và hosting khiến rollback gần như không thể kiểm soát.

## Thang điểm 0–10

- **0–2:** chỉ chọn rewrite hoặc upgrade framework mà không có migration plan.
- **3–4:** có phase migration nhưng thiếu coexistence/data/auth reasoning.
- **5–6:** có inventory, seams, backward compatibility, testing và staged hosting.
- **7–8:** có risk-based sequence, observability, rollback, job extraction và architecture trade-offs.
- **9–10:** thiết kế modernization như evolutionary system transition, phân tách axes of change, đưa recommendation conditional theo dependency/business evidence và tránh complexity không có ROI.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Span<T>` là memory view có lifetime constraints; performance benefit đến từ giảm copy/allocation chứ không phải vì “stack luôn nhanh hơn heap”.
- Async state machine và heap lifetime giải thích tại sao `ref struct` không thể tùy ý sống qua `await`.
- Large-file upload qua backend có thể biến application thành memory/network bottleneck dù Blob Storage vẫn khỏe.
- Direct-to-Blob upload nên tách authorization/control plane khỏi bulk data path, dùng scoped short-lived SAS thay vì public container.
- Blob + SQL là distributed consistency boundary; cần state machine, idempotent finalize và reconciliation.
- Modernization nên giảm số axes thay đổi cùng lúc và ưu tiên coexistence/rollback thay vì rewrite vì cảm tính.
- Microservices/Kubernetes không phải thước đo độ hiện đại; operational complexity chỉ đáng trả khi requirement thực sự cần.

## Mẫu tư duy cần nhớ

- **Understand lifetime before optimizing memory.**
- **Measure allocation and throughput before adding low-level complexity.**
- **Trace failures hop-by-hop before blaming a dependency.**
- **Separate control plane from high-volume data plane when it simplifies scale and security.**
- **Modernize incrementally; preserve coexistence and rollback paths.**
