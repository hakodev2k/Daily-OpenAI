# Câu 1 — Tại sao React hiển thị dữ liệu của nhân viên khác sau khi đổi bộ lọc?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** React hooks, JavaScript event loop, Promise, HTTP cancellation, state consistency, ASP.NET Core API

## Bối cảnh

Một portal nhân sự dùng React + TypeScript và ASP.NET Core .NET 8. Khi quản trị viên chọn nhân viên A rồi nhanh chóng chọn B, trang chi tiết đôi lúc hiển thị thông tin A trong khi tiêu đề đang là B. Mỗi lần thay đổi `employeeId`, một `useEffect` gọi `fetch('/api/employees/' + employeeId)`, sau đó `setEmployee(data)`. API trả dữ liệu đúng theo ID và các request có thể hoàn tất không theo thứ tự gửi. Portal có thể được dùng bởi nhiều tenant; chưa xác định cơ chế cache, authentication và kiểm tra tenant ở backend.

## Câu hỏi chính

Giải thích cơ chế React effect, closure, Promise resolution và network ordering gây lỗi; thiết kế cách ngăn stale response cập nhật UI, đồng thời chỉ ra ranh giới giữa frontend correctness và backend authorization.

## Câu hỏi làm rõ nên cân nhắc

1. Effect phụ thuộc `employeeId` như thế nào, có cleanup không?
2. React Strict Mode trong development có bật không; lỗi xảy ra ở production chứ?
3. Có request deduplication, caching library hoặc retry interceptor không?
4. Response chứa tenant/employee identity để kiểm tra tính nhất quán không?
5. Khi chuyển A → B → A, có cần cache kết quả cũ hay bắt buộc làm mới?

## Gợi ý tư duy

### Gợi ý 1

Thứ tự khởi tạo Promise không đảm bảo thứ tự hoàn tất.

### Gợi ý 2

Cleanup của effect có thể vô hiệu hóa kết quả cũ; hủy network request là một lớp tối ưu khác.

### Gợi ý 3

UI không phải là security boundary: dữ liệu của tenant khác không được phép trả về ngay từ API.

## Cấu trúc trả lời đề xuất

1. Tái hiện timeline A/B và định nghĩa invariant của UI.
2. Phân tích closure, effect lifecycle và Promise scheduling.
3. Chọn chiến lược ignore stale result, abort request và cache key.
4. Kiểm tra authorization, test race và quan sát production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Chỉ rõ race là **completion order**, không phải lỗi `setState` tự thân.
- Cleanup bảo vệ việc cập nhật state từ effect đã lỗi thời.
- Backend phải xác thực quyền truy cập employee/tenant cho từng request.

### Điểm cộng

- Phân biệt `AbortController` với bảo đảm dữ liệu không stale.
- Nêu cách xử lý loading/error khi đổi ID nhanh và khi component unmount.
- Kiểm tra caching key theo tenant và employee.

### Senior+

- Phân tích deduplication, revalidation, optimistic UI và observability không log PII.
- Giải thích vì sao Strict Mode development có thể giúp lộ side-effect nhưng không phải root cause duy nhất.

## Hướng giải quyết tham khảo

**Giả định:** dữ liệu employee phụ thuộc vào `employeeId` và tenant của phiên hiện tại. Khi ID đổi, React chạy cleanup của effect cũ trước khi chạy setup effect mới cho cùng component. Mỗi callback `then`/continuation giữ giá trị `employeeId` trong closure của render đã tạo ra nó. Request A có thể hoàn tất sau request B, và nếu không kiểm soát, callback A ghi đè state của B.

Một cách triển khai đơn giản:

```tsx
type Employee = { id: string; name: string };

function EmployeeDetail({ employeeId }: { employeeId: string }) {
  const [employee, setEmployee] = React.useState<Employee | null>(null);
  const [error, setError] = React.useState<string | null>(null);
  const [loading, setLoading] = React.useState(false);

  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;

    setEmployee(null);
    setError(null);
    setLoading(true);

    async function load() {
      try {
        const response = await fetch(
          `/api/employees/${encodeURIComponent(employeeId)}`,
          { signal: controller.signal, credentials: "same-origin" }
        );
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const data: Employee = await response.json();
        if (active && data.id === employeeId) setEmployee(data);
      } catch (error) {
        if (active && !controller.signal.aborted) {
          setError("Không tải được thông tin nhân viên");
        }
      } finally {
        if (active) setLoading(false);
      }
    }

    void load();
    return () => {
      active = false;
      controller.abort();
    };
  }, [employeeId]);

  if (loading) return <p>Đang tải...</p>;
  if (error) return <p role="alert">{error}</p>;
  return <div>{employee?.name ?? "Không có dữ liệu"}</div>;
}
```

`active` ngăn continuation cũ cập nhật state, kể cả khi abort đến quá muộn hoặc tầng abstraction không hỗ trợ cancellation. `AbortController` giảm công việc không cần thiết nhưng không bảo đảm server dừng xử lý. Nếu tenant thay đổi mà component không remount, tenant phải có trong dependency và cache key; ví dụ này giả định tenant được quản lý riêng và effect được khởi tạo lại khi tenant đổi. API cần policy/resource-based authorization và tenant filtering ở server; kiểm tra `data.id` ở client chỉ là kiểm tra consistency, không thay thế authorization.

Nếu dùng TanStack Query hoặc tương tự, dùng query key gồm tenant + employee ID, cấu hình stale time theo yêu cầu và xử lý signal; không thêm library chỉ vì một màn hình đơn giản. Dùng Playwright để điều khiển response A/B đảo thứ tự, test unmount, HTTP 403, retry và đổi tenant. Theo dõi request correlation, error rate, cancellation rate và mismatch giữa selected ID với response ID (không ghi tên nhân viên).

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận effect có cleanup và API có tenant authorization. Hai request A và B không có bảo đảm hoàn thành theo thứ tự. Callback của A vẫn giữ closure cũ nên có thể ghi đè state sau khi B được chọn. Tôi sẽ reset trạng thái khi ID đổi, abort request cũ và dùng cờ active hoặc request identity để bỏ kết quả stale. Sau đó test A/B với network delay đảo chiều, unmount và lỗi HTTP. Quan trọng hơn, đây chỉ là vấn đề hiển thị nếu backend đã kiểm tra quyền đúng; nếu API trả dữ liệu tenant khác thì đó là security incident riêng, không thể giải quyết bằng frontend.”

## Câu hỏi đào sâu

1. Nếu A → B → A rất nhanh, làm thế nào tránh hiển thị kết quả A cũ quá hạn mà vẫn tận dụng cache?
2. Nếu `fetch` đã hoàn tất nhưng JSON parsing đang diễn ra khi abort, điều gì bảo vệ state?
3. Khi nào nên dùng query library thay vì effect thủ công, và chi phí là gì?

## Lỗi trả lời thường gặp

- Cho rằng request gửi trước luôn hoàn thành trước.
- Chỉ thêm `setTimeout` hoặc debounce mà không xử lý response stale.
- Coi `AbortController` là cơ chế server-side authorization.
- Bỏ qua error/loading và tenant identity trong cache key.

## Thang điểm 0–10

- 0–2: Nhận diện đúng timeline, đặt câu hỏi làm rõ.
- 0–3: Giải thích closure/effect/Promise chính xác.
- 0–2: Đề xuất giải pháp và phân tích trade-off.
- 0–2: Testing, security và production telemetry.
- 0–1: Trình bày rõ ràng, có điều kiện.  
**Tổng:** 10 điểm.

# Câu 2 — Azure Service Bus backlog tăng sau khi nâng cấp consumer dù CPU vẫn thấp

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, .NET worker, message lock, retry, idempotency, SQL, observability, incident response

## Bối cảnh

Một Worker Service .NET 8 xử lý sự kiện `InvoiceIssued` từ Azure Service Bus queue, lưu kết quả vào SQL Server và gọi API kế toán bên thứ ba. Sau khi deploy phiên bản mới, queue active message count tăng, dead-letter count tăng, một số hóa đơn bị gọi đối tác hai lần. CPU worker chỉ 20%; log có `MessageLockLost` và HTTP 429. Deployment tăng số replica từ 2 lên 6; chưa biết `MaxConcurrentCalls`, `PrefetchCount`, lock duration, auto lock renewal, retry policy, transaction boundary hay idempotency hiện tại. Business ưu tiên không phát sinh ghi nhận kế toán trùng, cho phép xử lý trễ tối đa 15 phút.

## Câu hỏi chính

Bạn là on-call engineer. Hãy trình bày kế hoạch từ giảm thiểu tác động đến tìm nguyên nhân, khôi phục backlog an toàn và thiết kế phòng ngừa duplicate side effect.

## Câu hỏi làm rõ nên cân nhắc

1. Tốc độ enqueue/dequeue, age of oldest message và DLQ reason biến động thế nào?
2. `MaxConcurrentCalls`, prefetch, lock renewal và timeout dependency có thay đổi?
3. Đối tác có idempotency key và rate limit theo account hay IP?
4. SQL commit diễn ra trước hay sau external API; có outbox/inbox không?
5. Có thể tạm dừng publisher, giảm replica hoặc giới hạn concurrency mà không vi phạm SLA không?

## Gợi ý tư duy

### Gợi ý 1

CPU thấp không có nghĩa hệ thống thiếu throughput do CPU.

### Gợi ý 2

Message lock và external HTTP latency có thể tương tác với prefetch và concurrency.

### Gợi ý 3

Một message có thể được giao lại sau khi side effect đã thành công nhưng settlement thất bại.

## Cấu trúc trả lời đề xuất

1. Định lượng tác động business, đặt ngưỡng khẩn cấp.
2. Ổn định tốc độ xử lý và ngăn duplicate side effect.
3. Đối chiếu telemetry theo message ID, business ID và deployment version.
4. Kiểm chứng các giả thuyết cạnh tranh.
5. Remediation, replay, test và prevention.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định Service Bus bảo đảm exactly-once processing.
- Không replay DLQ hàng loạt khi chưa sửa nguyên nhân.
- Đưa ra ít nhất hai giả thuyết kiểm chứng được.
- Phân biệt lock expiration, retry HTTP và redelivery.

### Điểm cộng

- Tính arrival rate, processing rate, backlog drain time có điều kiện.
- Thiết kế idempotency dựa trên business operation, không chỉ transport message ID.
- Chỉ rõ external API và SQL không nằm trong một distributed transaction thông thường.

### Senior+

- Đề xuất state machine/operation ledger, reconciliation và operational runbook.
- Nhận diện giới hạn của auto lock renewal, duplicate detection và retry policy.

## Hướng giải quyết tham khảo

**Impact:** kiểm tra số invoice có khả năng ghi nhận trùng, số invoice chưa xử lý, SLA delay và financial reconciliation. Phân loại sự kiện chưa settlement nhưng side effect đã thành công. Cảnh báo finance/operations trước khi replay.

**Stabilize:** nếu rate limit của đối tác bị vượt, giảm tổng concurrency bằng cấu hình processor và replica count; có thể tạm dừng một phần consumer hoặc publisher nếu được business phê duyệt. Không tăng replica khi chưa chứng minh bottleneck. Giữ DLQ để điều tra, không xóa message. Nếu có nguy cơ duplicate side effect, chặn outbound call không idempotent cho đến khi có guard hoặc phương án đối soát.

**Hypotheses:**
- Tăng `replicas × MaxConcurrentCalls` vượt rate limit → HTTP 429, retry kéo dài, lock hết hạn.
- Prefetch quá lớn làm message nằm chờ trong local buffer và lock tuổi cao trước khi xử lý.
- SQL blocking/connection pool hoặc external API latency tăng làm message xử lý lâu.
- Settlement failure sau khi gọi đối tác thành công gây redelivery.
- Bug mới bỏ qua idempotency hoặc thay đổi retry semantics.

**Evidence:** phân tích deployment diff; Service Bus active/dead-letter counts, oldest age, delivery count, DLQ reason; worker throughput, processing duration p95/p99, lock-lost, HTTP 429, retry count, SQL waits, connection pool; correlation bằng `MessageId`, `InvoiceId`, `OperationId`. Không log payload tài chính nhạy cảm. Truy vết theo deployment version.

**Fix có điều kiện:** nếu rate limit là nguyên nhân, áp dụng bounded concurrency và backoff tôn trọng `Retry-After` khi có; giới hạn tổng tải trên toàn replica. Dùng `ServiceBusProcessor` với `AutoCompleteMessages = false`, settle message sau khi xác nhận business operation đã hoàn tất hoặc đã được ghi nhận là hoàn tất. Cấu hình lock renewal theo latency thực tế, nhưng không coi renewal là thay thế idempotency.

Tạo bảng `InvoiceDispatch` với unique constraint trên `(TenantId, InvoiceId, OperationType)`, trạng thái `Pending/InFlight/Completed/NeedsReconciliation`, attempt count, partner reference và timestamps. Acquire/claim bằng thao tác atomic có lease/timeout, không dùng `SELECT` rồi `INSERT` không bảo vệ concurrency. Nếu đối tác hỗ trợ idempotency key, gửi key ổn định cho cùng business operation. Nếu đối tác không hỗ trợ, khi timeout sau gửi phải coi kết quả là **unknown**, query trạng thái đối tác hoặc đưa vào reconciliation thay vì tự động gọi lại. Transaction SQL không thể rollback external API đã thành công. Có thể dùng Outbox để phát lệnh đáng tin cậy từ DB, Inbox để chống duplicate, nhưng phải cân nhắc vận hành và độ phức tạp.

**Recovery:** phân loại DLQ theo reason, đối soát side effect, replay có kiểm soát theo batch và giới hạn tốc độ; đo backlog drain time theo `backlog / (sustainable completion rate - arrival rate)` khi mẫu số dương. Nếu không dương, không thể drain ở trạng thái ổn định. Chạy load/failure injection trước rollout đầy đủ.

**Prevention:** dashboard arrival/completion rates, queue age, DLQ, lock lost, partner 429, duplicate prevention hits, unknown outcomes, reconciliation age; alerts theo SLA và error budget. Canary deployment, rollback cấu hình, game day kiểm tra timeout và redelivery.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ ưu tiên ngăn ghi nhận kế toán trùng và xác định số hóa đơn đang chậm. CPU 20% không chứng minh thiếu worker; 429 và lock lost khiến tôi nghi ngờ concurrency tăng vượt rate limit, nhưng cũng cần kiểm tra prefetch, SQL waits và thay đổi release. Tôi sẽ giảm tổng concurrency, đối chiếu message ID với invoice ID và partner reference, không replay DLQ ngay. Về lâu dài cần operation ledger có unique constraint, idempotency key phía đối tác nếu hỗ trợ, và reconciliation cho các kết quả timeout không rõ. Sau khi ổn định mới replay theo batch, theo dõi oldest message age và tốc độ drain để xác nhận SLA.”

## Câu hỏi đào sâu

1. Nếu đối tác không có idempotency API hoặc API tra cứu trạng thái, có thể bảo đảm không duplicate tuyệt đối không?
2. Nếu tăng `MaxAutoLockRenewalDuration` mà backlog vẫn tăng, bạn kiểm tra gì tiếp?
3. Khi nào Outbox/Inbox đáng chi phí hơn một unique constraint và job reconciliation đơn giản?

## Lỗi trả lời thường gặp

- Tăng replica vì thấy backlog mà không kiểm tra rate limit.
- Nhầm auto lock renewal với exactly-once delivery.
- Retry HTTP timeout mù quáng, tạo side effect trùng.
- Replay toàn bộ DLQ trước khi sửa nguyên nhân.
- Chỉ nhìn CPU mà bỏ qua queue age và dependency telemetry.

## Thang điểm 0–10

- 0–2: Impact và stabilization.
- 0–2: Competing hypotheses và evidence.
- 0–2: Service Bus/lock/retry mechanism.
- 0–2: Idempotency, consistency và recovery.
- 0–1: Testing/observability.
- 0–1: Communication và trade-off.  
**Tổng:** 10 điểm.

# Câu 3 — Chọn chiến lược nâng cấp ứng dụng .NET Framework 4.5 và jQuery đang vận hành

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35 phút  
**Kỹ năng được đánh giá:** .NET modernization, IIS, SQL Server, deployment, API contracts, React/Vue integration, testing, migration strategy, cost of complexity

## Bối cảnh

Một hệ thống quản lý timesheet nội bộ chạy ASP.NET MVC trên .NET Framework 4.5, jQuery, IIS/Windows Server và SQL Server. Hệ thống tích hợp Windows authentication, một thư viện xuất Excel cũ và các scheduled jobs chạy trong web application. Product yêu cầu thêm mobile-friendly UI và REST API cho một hệ thống khác. Nhóm có 4 developer, QA bán thời gian; downtime cho phép tối đa 15 phút mỗi release. Một số thư viện chưa rõ có hỗ trợ .NET 8/10 không. Business không yêu cầu microservices; quy mô giả định 2.000 nhân viên, giờ cao điểm đầu tháng.

## Câu hỏi chính

Đề xuất lộ trình modernization trong 6 tháng, so sánh in-place migration, strangler/incremental replacement và rewrite; quyết định boundaries, data ownership, authentication, hosting, release/rollback và tiêu chí dừng hoặc thay đổi hướng.

## Câu hỏi làm rõ nên cân nhắc

1. Có bao nhiêu module, dependencies và stored procedures; có automated tests không?
2. Windows authentication phục vụ intranet hay còn identity integration nào khác?
3. Scheduled jobs có được phép chạy lại, cần exactly-once business effect hay chỉ at-least-once?
4. Có API contract cho client hiện tại và yêu cầu backward compatibility nào?
5. Năng lực vận hành App Service/Linux so với IIS/Windows hiện có thế nào?

## Gợi ý tư duy

### Gợi ý 1

Đừng đồng nhất modernize UI với migrate toàn bộ runtime.

### Gợi ý 2

Một ứng dụng mới có thể cùng tồn tại với legacy qua boundaries rõ ràng, nhưng shared database tạo coupling.

### Gợi ý 3

Rollback không chỉ là rollback binary; schema và background jobs có thể đã thay đổi dữ liệu.

## Cấu trúc trả lời đề xuất

1. Chốt business outcomes, risk budget và inventory.
2. Xác định seams theo business capability.
3. So sánh ba phương án theo effort, risk, rollback và vận hành.
4. Chọn hosting, auth, API/data contracts và deployment strategy.
5. Xây test/telemetry gates và milestone 6 tháng.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định thư viện .NET Framework 4.5 chạy trên modern .NET.
- Nêu chiến lược incremental và rollback.
- Xử lý scheduled jobs độc lập khỏi IIS lifecycle.
- Nêu phương án bảo vệ data consistency khi legacy và modern cùng tồn tại.

### Điểm cộng

- Dùng contract tests, characterization tests và strangler proxy/routing.

### Senior+

- Quyết định dựa trên measurable gates thay vì timeline cứng.
- Cân nhắc tránh shared DB writes lâu dài và chi phí vận hành dual-stack.

## Hướng giải quyết tham khảo

**Giả định:** không có yêu cầu bắt buộc phải thay IIS ngay; SQL Server vẫn đáp ứng tải nếu được đo kiểm. Với team nhỏ và downtime ngắn, ưu tiên incremental modernization, không chọn rewrite mặc định.

**Tháng 1 — Inventory & baseline:** lập dependency map của .NET Framework assemblies, Excel library, Windows auth, SQL schema, scheduled jobs, IIS config; đo p95, failure rate, release time, DB waits, số regression; characterization tests quanh timesheet approval, payroll export và quyền truy cập. Phân loại module dễ tách, module phụ thuộc session/static state, module khó migrate. Tạo API contract và acceptance criteria cùng Product/QA.

**Tháng 2 — Stabilize legacy:** tách scheduled jobs khỏi web process sang worker/job runner có durable state, concurrency guard và idempotency theo business key; không giả định IIS app pool sống liên tục. Thêm structured logging, correlation IDs, health checks phù hợp và backup/restore drill. Tạo CI pipeline build/test/deploy artifact bất biến; giữ rollback artifact.

**Tháng 3 — First seam:** triển khai một ASP.NET Core service/module cho read-only timesheet summary hoặc reporting có ranh giới rõ. Có thể dùng cùng SQL Server ban đầu, nhưng quản lý migration tập trung, giới hạn write ownership và không để hai hệ thống cùng tự ý thay schema. Dùng gateway/reverse proxy định tuyến đường dẫn, bảo vệ authorization ở cả hai phía. Cân nhắc BFF nếu frontend mới cần aggregate nhiều API.

**Tháng 4 — UI/API:** dùng React hoặc Vue cho một màn hình có giá trị cao, tích hợp qua API có versioning/contract tests; không bắt buộc thay toàn bộ jQuery. Đánh giá authentication: giữ Windows auth cho intranet khi phù hợp, hoặc pilot Entra ID/OIDC cho frontend mới; kiểm tra cookie, CSRF, CORS, token audience, logout và user mapping. Không đặt secrets trong frontend.

**Tháng 5 — Move bounded capability:** chuyển một write workflow nhỏ theo ownership rõ, có audit, optimistic concurrency/transaction ở DB, feature flag và reconciliation nếu dual-run. Schema migration theo expand/contract, bảo đảm old binary tương thích trong rollback window. Không dual-write không kiểm soát. Dùng shadow reads nếu phù hợp nhưng không shadow write side effects.

**Tháng 6 — Prove & decide:** load test giờ cao điểm, Playwright E2E cho workflows quan trọng, kiểm tra export Excel và quyền truy cập, diễn tập rollback/recovery. Quyết định tiếp tục migrate hay giữ phần legacy ổn định dựa trên defect rate, latency, lead time và chi phí vận hành. Hosting: giữ IIS/Windows nếu rủi ro chuyển hosting cao; chọn App Service hoặc container chỉ khi vận hành và dependency hỗ trợ. Kubernetes không tự động đem lại lợi ích cho quy mô này.

**Trade-offs:** incremental kéo dài dual-stack và routing complexity nhưng giảm blast radius; in-place migration nhanh hơn nếu dependency compatibility tốt và test coverage đủ; rewrite có thể phù hợp khi domain cực nhỏ hoặc legacy không thể cứu vãn, nhưng thường rủi ro parity và regression lớn. Không cam kết deadline nếu inventory chứng minh dependency blocker. Quy trình rollback cần kiểm tra schema, queue/job side effects, config và session behavior, không chỉ đổi binary.

**Testing & monitoring:** unit tests cho domain rules; integration tests SQL/auth; contract tests cho API; Playwright E2E cho submit/approve/export; load test đầu tháng; security tests tenant/role; deployment smoke/canary; metrics release failure, error rate, p95, job duplication, SQL waits, auth failures và rollback duration.

## Mẫu trả lời trong phỏng vấn

“Với bốn developer và hệ thống đang chạy, tôi không chọn rewrite toàn bộ ngay. Tôi sẽ inventory dependencies, đo baseline, tạo characterization tests và tách scheduled jobs khỏi IIS trước. Sau đó chọn một module read-only làm seam để thử ASP.NET Core và React/Vue, giữ contract và quyền truy cập rõ ràng. Với write flows, mỗi capability phải có owner, schema expand/contract và rollback được diễn tập. Tôi chỉ chuyển hosting hoặc authentication khi có bằng chứng lợi ích và khả năng vận hành. Sau sáu tháng, quyết định tiếp dựa trên defect rate, deployment risk và business outcomes chứ không phải số phần trăm code đã viết lại.”

## Kiến thức trọng tâm

Ba lớp rủi ro khác nhau: **frontend state consistency** dưới network race; **distributed side-effect correctness** dưới retry/redelivery; và **incremental modernization** dưới dependency/operational constraints. 1. Xác định invariant trước khi sửa race condition.

3. Thiết kế retry cùng idempotency và reconciliation.
4. Chọn migration boundary theo ownership và rollback, không theo framework hype.
5. Dùng telemetry để bác bỏ giả thuyết, không chỉ xác nhận trực giác.
