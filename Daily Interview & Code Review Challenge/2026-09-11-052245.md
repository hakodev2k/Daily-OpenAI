# Code Review Challenge 1 — Service Bus consumer “xử lý đúng một lần” nhưng production vẫn gửi cùng notification nhiều lần

**Chủ đề:** C#/.NET, Azure Service Bus, PeekLock, message settlement, idempotency, SQL Server, EF Core, Outbox/Inbox Pattern, external side effects, retries, failure recovery, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một notification service nhận message từ Azure Service Bus queue sau khi user hoàn tất một approval workflow.

Mỗi message yêu cầu:

- ghi một audit record vào SQL Server;
- cập nhật trạng thái notification trong database;
- gọi external email provider;
- không được gửi cùng business notification nhiều lần chỉ vì message bị redeliver;
- transient failure phải có khả năng retry;
- process có thể restart bất kỳ lúc nào;
- application chạy nhiều worker instances;
- một message có thể mất 20–90 giây để xử lý nếu external provider chậm;
- dead-letter chỉ nên dùng khi message không còn khả năng xử lý hợp lệ theo policy;
- Application Insights được dùng cho production telemetry.

Sau khi scale-out từ 1 lên 6 worker instances, support ghi nhận một số user nhận cùng email 2–3 lần. SQL audit đôi khi chỉ có một row, đôi khi có hai rows. Service Bus metrics cho thấy một phần messages có `DeliveryCount > 1`.

Team kết luận rằng “Service Bus duplicate delivery là bug của broker” và thêm một bảng `ProcessedMessages` để check `MessageId` trước khi xử lý.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ApprovalCompletedConsumer
{
    private readonly AppDbContext _db;
    private readonly IEmailGateway _emailGateway;
    private readonly ILogger<ApprovalCompletedConsumer> _logger;

    public ApprovalCompletedConsumer(
        AppDbContext db,
        IEmailGateway emailGateway,
        ILogger<ApprovalCompletedConsumer> logger)
    {
        _db = db;
        _emailGateway = emailGateway;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var message = args.Message;
        var messageId = message.MessageId;

        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == messageId);

        if (alreadyProcessed)
        {
            await args.CompleteMessageAsync(message);
            return;
        }

        var payload = JsonSerializer.Deserialize<ApprovalCompleted>(
            message.Body.ToString())!;

        try
        {
            await _emailGateway.SendApprovalCompletedAsync(
                payload.UserEmail,
                payload.ApprovalId,
                CancellationToken.None);

            _db.NotificationAudits.Add(new NotificationAudit
            {
                ApprovalId = payload.ApprovalId,
                UserEmail = payload.UserEmail,
                SentAtUtc = DateTime.UtcNow
            });

            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = messageId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync();
            await args.CompleteMessageAsync(message);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Failed to process Service Bus message {MessageId} for {Email}",
                messageId,
                payload.UserEmail);

            await args.DeadLetterMessageAsync(
                message,
                "ProcessingFailed",
                ex.Message);
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code theo góc nhìn distributed systems và production reliability. Bạn cần:

1. xác định các correctness, concurrency, reliability, security và observability issues;
2. giải thích vì sao `AnyAsync` rồi mới `Insert` không tạo ra idempotency an toàn dưới concurrency;
3. phân tích failure window nếu email gửi thành công nhưng process crash trước `SaveChangesAsync` hoặc trước `CompleteMessageAsync`;
4. giải thích vì sao PeekLock/redelivery không đồng nghĩa broker “gửi sai”;
5. đánh giá việc dead-letter mọi exception ngay lần đầu;
6. phân tích message lock lifetime và việc xử lý 20–90 giây;
7. đề xuất một design có idempotency boundary rõ, tránh distributed transaction giả giữa SQL Server, Service Bus và external email provider;
8. mô tả testing cho crash/retry/duplicate delivery/concurrent consumers;
9. đề xuất telemetry để phân biệt duplicate delivery, duplicate side effect và poison message.

## Câu hỏi gợi mở

1. Nếu hai worker nhận hai bản delivery của cùng business event gần nhau, cả hai có thể cùng thấy `AnyAsync == false` không?
2. Nếu email provider đã gửi mail nhưng process chết trước khi `ProcessedMessages` được commit, lần delivery tiếp theo sẽ làm gì?
3. Nếu SQL commit thành công nhưng `CompleteMessageAsync` thất bại vì mất connection/lock, message có thể xuất hiện lại không?
4. Có nên coi `MessageId` là idempotency key duy nhất, hay business key như `ApprovalId + NotificationType` mới là invariant cần bảo vệ?
5. Exception do timeout tạm thời và exception do payload invalid có nên cùng đi thẳng vào DLQ không?

## Kết quả code review tham khảo

### Critical — External email side effect xảy ra trước durable idempotency state

**Vấn đề:**  
Email được gửi trước khi database ghi nhận message/business event đã được xử lý.

**Tại sao xảy ra:**  
Nếu provider nhận request và gửi email thành công nhưng process crash, network disconnect hoặc worker bị terminate trước `SaveChangesAsync`, database không có durable marker. Khi lock hết hạn hoặc message được redeliver, consumer lại gửi email.

**Ảnh hưởng production:**  
User nhận duplicate notifications dù database có thể không phản ánh duplicate. Đây là failure window điển hình khi cố phối hợp external side effect và broker settlement mà không có distributed transaction thực sự.

**Cách sửa:**  
Đưa durable state transition vào một local database transaction trước. Ví dụ ghi Inbox marker + Notification intent/Outbox row atomically trong SQL Server. Sau đó complete Service Bus message. Một dispatcher riêng gửi email từ Outbox và dùng idempotency key/business key với provider nếu provider hỗ trợ, hoặc duy trì state machine để retry safely.

---

### Critical — Check-then-insert bằng `AnyAsync` có race condition

**Vấn đề:**  
Consumer kiểm tra existence rồi mới insert ở hai database round trips khác nhau.

**Tại sao xảy ra:**  
Hai workers có thể đồng thời quan sát “chưa có”, cả hai tiếp tục xử lý và cùng tạo side effect trước khi một trong hai insert marker.

**Ảnh hưởng production:**  
Duplicate email, duplicate audit hoặc database exception muộn sau khi side effect đã xảy ra.

**Cách sửa:**  
Enforce idempotency bằng database constraint/unique key và atomic insert/upsert semantics. Business invariant phải được bảo vệ tại source of truth, không chỉ bằng pre-check trong application memory/ORM flow.

Ví dụ:

```sql
CREATE UNIQUE INDEX UX_ProcessedMessages_MessageId
ON ProcessedMessages(MessageId);
```

Nếu business invariant thực sự là “một approval chỉ gửi một loại notification một lần”, unique key nên phản ánh business key tương ứng thay vì chỉ transport `MessageId`.

---

### High — `CompleteMessageAsync` sau DB commit có ambiguous completion window

**Vấn đề:**  
Database có thể commit thành công nhưng message settlement có thể fail hoặc acknowledgment không tới client.

**Tại sao xảy ra:**  
SQL transaction và Service Bus settlement không phải một atomic distributed transaction trong code này. Nếu message xuất hiện lại, consumer phải coi đó là normal recoverable condition.

**Ảnh hưởng production:**  
Redelivery sau successful local commit. Nếu handler không idempotent, side effect bị lặp.

**Cách sửa:**  
Thiết kế redelivery-safe. Khi delivery lặp, durable Inbox/business marker cho phép consumer biết local transition đã hoàn tất và chỉ cần settle message mà không tái tạo side effects.

---

### High — Dead-letter mọi exception ngay lần đầu làm mất khả năng recover transient failures

**Vấn đề:**  
`catch (Exception)` đưa message thẳng vào DLQ bất kể nguyên nhân.

**Tại sao xảy ra:**  
Timeout, SQL transient error, temporary Service Bus/network failure, payload contract violation và permanent business rejection có semantics khác nhau.

**Ảnh hưởng production:**  
Transient incidents biến thành manual recovery backlog; message có khả năng xử lý được lại bị loại khỏi normal retry path.

**Cách sửa:**  
Classify failures. Permanent malformed/unsupported payload có thể dead-letter sớm với reason an toàn. Transient infrastructure errors nên cho redelivery/retry theo bounded policy. Theo dõi `DeliveryCount` và policy của queue trước khi quyết định DLQ.

---

### High — Processing time có thể vượt message lock nếu lock renewal không phù hợp

**Vấn đề:**  
Scenario cho phép 20–90 giây processing nhưng code không thể hiện strategy cho lock duration/renewal.

**Tại sao xảy ra:**  
Với PeekLock, message chỉ được giữ độc quyền trong lock window. Nếu processing vượt lock hoặc connection bị mất, settlement có thể fail và message được redeliver.

**Ảnh hưởng production:**  
Hai workers có thể thực hiện overlapping work cho cùng logical message; `Complete` có thể fail sau khi side effect đã chạy.

**Cách sửa:**  
Giữ message handler ngắn bằng cách chỉ commit Inbox/Outbox rồi complete, thay vì giữ broker lock trong suốt external email call. Nếu có workload thực sự cần xử lý dài trong handler, configure auto-renewal/lock strategy dựa trên measured processing time và vẫn phải giữ idempotency.

---

### High — Không propagate cancellation token

**Vấn đề:**  
External call dùng `CancellationToken.None`; EF Core calls cũng không nhận processor cancellation token.

**Tại sao xảy ra:**  
Khi host shutdown, processor stop hoặc lock không còn hữu ích, work vẫn chạy.

**Ảnh hưởng production:**  
Shutdown kéo dài, external calls tiếp tục dù message có thể được worker khác xử lý lại, tăng duplicate side-effect risk.

**Cách sửa:**  
Propagate cancellation token phù hợp từ message processing context/host. Tuy nhiên cancellation không thay idempotency: provider có thể đã nhận request trước khi cancellation được quan sát.

---

### Medium — `MessageId` chưa chắc đại diện đúng business idempotency invariant

**Vấn đề:**  
Code mặc định transport-level `MessageId` chính là business identity.

**Tại sao xảy ra:**  
Producer có thể vô tình phát lại cùng business event với một `MessageId` mới; hoặc một business action có nhiều notification types hợp lệ.

**Ảnh hưởng production:**  
Dedupe sai scope: vẫn duplicate nếu producer tạo ID mới, hoặc vô tình suppress event hợp lệ nếu key quá rộng.

**Cách sửa:**  
Xác định invariant rõ. Ví dụ unique key `(ApprovalId, NotificationType, RecipientId)` nếu business yêu cầu mỗi combination chỉ gửi một lần. `MessageId` vẫn hữu ích cho transport tracing/deduplication nhưng không nhất thiết là business key cuối cùng.

---

### Medium — Logging có thể chứa PII và exception details không phù hợp

**Vấn đề:**  
Log raw email address và đưa `ex.Message` vào dead-letter description.

**Tại sao xảy ra:**  
Exception text có thể chứa provider URL, payload fragments hoặc dữ liệu nhạy cảm. Email address là PII.

**Ảnh hưởng production:**  
Tăng exposure trong Application Insights/DLQ và làm data-governance phức tạp.

**Cách sửa:**  
Log stable identifiers/pseudonymized recipient ID, message/business key, failure category và correlation ID. Dead-letter reason nên ngắn, structured và không chứa raw secret/PII.

---

### Medium — Audit record hiện phản ánh “email đã gửi” nhưng không có state machine đáng tin cậy

**Vấn đề:**  
`SentAtUtc` được ghi sau email call nhưng không phân biệt queued, sending, sent, failed, retrying.

**Tại sao xảy ra:**  
Một external operation không thể được đại diện an toàn bằng một boolean/timestamp duy nhất nếu có retry và ambiguous completion.

**Ảnh hưởng production:**  
Khó reconciliation khi provider timeout nhưng thực tế đã nhận request; khó biết mail nào cần retry.

**Cách sửa:**  
Model explicit notification delivery state và attempt history tối thiểu cần thiết. Nếu provider hỗ trợ idempotency key/provider message ID, lưu chúng để reconciliation.

## Phiên bản đề xuất

Một hướng an toàn hơn là tách **message acceptance** khỏi **external delivery**.

### 1. Service Bus handler: atomic Inbox + Outbox transaction

```csharp
public sealed class ApprovalCompletedConsumer
{
    private readonly AppDbContext _db;
    private readonly ILogger<ApprovalCompletedConsumer> _logger;

    public ApprovalCompletedConsumer(
        AppDbContext db,
        ILogger<ApprovalCompletedConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = args.Message;
        var payload = JsonSerializer.Deserialize<ApprovalCompleted>(
            message.Body.ToString());

        if (payload is null)
        {
            await args.DeadLetterMessageAsync(
                message,
                "InvalidPayload",
                "Payload could not be deserialized",
                cancellationToken);
            return;
        }

        var businessKey =
            $"approval-completed:{payload.ApprovalId}:{payload.UserId}";

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var alreadyAccepted = await _db.ProcessedMessages
            .AnyAsync(x => x.BusinessKey == businessKey, cancellationToken);

        if (!alreadyAccepted)
        {
            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                BusinessKey = businessKey,
                MessageId = message.MessageId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            _db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                BusinessKey = businessKey,
                Type = "SendApprovalCompletedEmail",
                PayloadJson = JsonSerializer.Serialize(new
                {
                    payload.UserId,
                    payload.ApprovalId
                }),
                CreatedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
        }

        await tx.CommitAsync(cancellationToken);

        await args.CompleteMessageAsync(message, cancellationToken);
    }
}
```

Điểm bắt buộc của design này là database phải có unique constraint trên `BusinessKey`. `AnyAsync` ở đây chỉ là optimization/readability; correctness vẫn đến từ unique constraint. Trong implementation production, duplicate-key exception cần được phân loại thành “already accepted” thay vì generic failure.

Ví dụ:

```sql
CREATE UNIQUE INDEX UX_ProcessedMessages_BusinessKey
ON ProcessedMessages(BusinessKey);

CREATE UNIQUE INDEX UX_OutboxMessages_BusinessKey
ON OutboxMessages(BusinessKey);
```

Nếu hai consumers race, database constraint quyết định winner. Một consumer có thể nhận duplicate-key, rollback transaction đó, xác minh business key đã tồn tại rồi settle message.

### 2. Outbox dispatcher: retry external email independently

```csharp
public sealed class EmailOutboxDispatcher
{
    private readonly AppDbContext _db;
    private readonly IEmailGateway _emailGateway;

    public async Task DispatchAsync(
        OutboxMessage item,
        CancellationToken cancellationToken)
    {
        if (item.SentAtUtc is not null)
            return;

        var command = JsonSerializer.Deserialize<SendApprovalEmail>(
            item.PayloadJson)!;

        var providerResult = await _emailGateway
            .SendApprovalCompletedAsync(
                command.UserId,
                command.ApprovalId,
                idempotencyKey: item.BusinessKey,
                cancellationToken);

        item.ProviderMessageId = providerResult.MessageId;
        item.SentAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Nếu provider **không** hỗ trợ idempotency key, exactly-once external side effect không thể được giả định chỉ bằng local transaction. Khi timeout xảy ra sau khi request có thể đã tới provider, system cần reconciliation contract hoặc chấp nhận/giảm thiểu duplicate theo business requirement. Đây là chỗ ứng viên Senior+ phải nói rõ giới hạn của hệ thống thay vì hứa “exactly once” tuyệt đối.

Azure Service Bus PeekLock được thiết kế để message có thể redeliver nếu processing/settlement không hoàn tất. Vì vậy handler phải idempotent. Duplicate detection phía sender, nếu được bật và cấu hình phù hợp, không thay thế idempotent consumer ở phía receive.

Tài liệu tham khảo:

- Microsoft Learn — Message transfers, locks, and settlement: `https://learn.microsoft.com/azure/service-bus-messaging/message-transfers-locks-settlement`
- Microsoft Learn — Prevent message loss and duplicate processing: `https://learn.microsoft.com/azure/service-bus-messaging/service-bus-message-loss-and-duplicates`

## Giải thích thiết kế sau khi sửa

Design mới tạo hai boundaries rõ:

1. **Broker message → SQL durable intent**: Inbox/Outbox được ghi atomically trong một database transaction.
2. **SQL Outbox → external email provider**: retry độc lập, có idempotency/reconciliation strategy riêng.

Điều này tránh giữ Service Bus lock trong lúc external dependency có thể chậm 90 giây. Nó cũng biến redelivery thành behavior bình thường: nếu DB đã ghi intent nhưng broker settlement thất bại, lần delivery sau chỉ xác nhận state đã có rồi complete.

Không cần Microservices hay một transaction coordinator chỉ để giải bài toán này. Một SQL-backed Inbox/Outbox trong cùng service có thể đủ nếu throughput và operational requirements cho phép.

## Trade-offs

- Thêm Outbox table, dispatcher và cleanup policy làm tăng code/operational complexity.
- Notification trở thành asynchronous sau khi business event được accepted; cần xác định SLA từ accepted đến sent.
- Nếu provider không hỗ trợ idempotency, vẫn tồn tại ambiguous completion khi network timeout sau provider acceptance; cần reconciliation hoặc business tolerance.
- Unique business key phải được thiết kế đúng. Key sai có thể suppress event hợp lệ hoặc cho phép duplicate.
- Polling Outbox đơn giản dễ vận hành nhưng cần tuning batch size/concurrency; dùng thêm messaging chỉ khi scale/latency requirement thực sự cần.

## Cách kiểm thử

1. **Concurrency test:** chạy nhiều consumers đồng thời với cùng business event; chỉ một Inbox/Outbox intent được commit.
2. **Failure-path test:** kill process sau DB commit nhưng trước `CompleteMessageAsync`; message redeliver nhưng không tạo Outbox/email intent thứ hai.
3. **External ambiguity test:** provider nhận request rồi client timeout; xác minh idempotency key/reconciliation không gửi mail lặp ngoài policy.
4. **Transient retry test:** SQL/provider lỗi tạm thời; message/outbox được retry đúng policy, không dead-letter ngay lần đầu.
5. **Long-processing/load test:** chạy nhiều messages với provider latency cao; đo lock loss, queue depth, processing concurrency và shutdown behavior.

## Quan sát trong production

Nên có structured telemetry cho:

- `message_id`;
- `business_key`;
- `delivery_count`;
- processor instance;
- Inbox insert outcome: `accepted / duplicate`;
- Outbox state: `pending / sending / sent / failed`;
- provider idempotency key/provider message ID;
- processing duration;
- lock-lost/settlement failures;
- retry count;
- DLQ count + reason category;
- queue active message count và age of oldest message;
- duplicate deliveries observed;
- duplicate external side effects confirmed.

Alert quan trọng nên dựa trên backlog age, repeated delivery, DLQ growth và send-failure ratio, không chỉ tổng exception count.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL transaction commit thành công nhưng `CompleteMessageAsync` timeout và bạn không biết broker đã nhận settlement hay chưa, design trên phục hồi thế nào?
2. Nếu email provider không hỗ trợ idempotency key và timeout có thể xảy ra sau khi mail đã được gửi, bạn sẽ thiết kế reconciliation/business contract ra sao thay vì hứa exactly-once?
3. Một teammate đề xuất giữ transaction SQL mở trong suốt lúc gọi email provider để “đồng bộ mọi thứ”. Bạn phản biện recommendation đó thế nào?

# Code Review Challenge 2 — Elasticsearch search “đúng ở dev” nhưng production vừa chậm, vừa stale, vừa không thể đổi mapping an toàn

**Chủ đề:** Elasticsearch, SQL Server, search indexing, text vs keyword, analyzers, wildcard query, filtering, sorting, eventual consistency, reindexing, aliases, dual-write failure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một product catalog dùng SQL Server làm source of truth và Elasticsearch để phục vụ search cho website e-commerce.

Production có khoảng 8 triệu products. Search API cần hỗ trợ:

- full-text search theo `name` và `description`;
- exact lookup theo `sku`;
- filter theo `categoryId` và `isActive`;
- sort theo `price`;
- cập nhật product trong SQL rồi search index phản ánh trong thời gian chấp nhận được;
- deploy mapping mới mà không làm search downtime kéo dài;
- Elasticsearch outage không được làm mất product update trong SQL;
- search có thể eventual consistent nhưng business phải biết freshness expectation;
- indexing throughput có burst lớn khi import catalog.

Team tạo index như sau:

## Đoạn code cần review

```json
PUT products
{
  "mappings": {
    "properties": {
      "sku":        { "type": "text" },
      "name":       { "type": "keyword" },
      "description":{ "type": "keyword" },
      "categoryId": { "type": "text" },
      "price":      { "type": "keyword" },
      "isActive":   { "type": "boolean" }
    }
  }
}
```

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;
    private readonly IElasticClient _search;
    private readonly ILogger<ProductService> _logger;

    public async Task UpdateProductAsync(
        ProductDto input,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products.SingleAsync(
            x => x.Id == input.Id,
            cancellationToken);

        product.Sku = input.Sku;
        product.Name = input.Name;
        product.Description = input.Description;
        product.CategoryId = input.CategoryId;
        product.Price = input.Price;
        product.IsActive = input.IsActive;

        await _db.SaveChangesAsync(cancellationToken);

        try
        {
            await _search.IndexAsync("products", product, cancellationToken);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Elasticsearch indexing failed");
        }
    }

    public Task<SearchResult> SearchAsync(
        string query,
        string categoryId,
        CancellationToken cancellationToken)
    {
        return _search.SearchAsync(
            index: "products",
            rawQuery: $"""
            {
              "query": {
                "bool": {
                  "must": [
                    { "wildcard": { "name": "*{query}*" } },
                    { "term": { "categoryId": "{categoryId}" } },
                    { "term": { "isActive": true } }
                  ]
                }
              },
              "sort": [
                { "price": "asc" }
              ]
            }
            """,
            cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review mapping, update flow và search query dưới góc nhìn correctness, performance và operability. Bạn cần:

1. xác định mapping nào không phù hợp với intended query semantics;
2. giải thích vì sao full-text search bằng leading/trailing wildcard trên production catalog có thể rất đắt và relevance kém;
3. phân tích `text` vs `keyword` cho `sku`, `name`, `description`, `categoryId`;
4. giải thích vấn đề khi sort numeric `price` được index thành `keyword`;
5. phân tích dual-write `SQL SaveChanges → Elasticsearch Index` và failure window hiện tại;
6. giải thích tại sao API không nên hứa read-after-write search consistency nếu chưa có contract phù hợp;
7. đề xuất reindex/mapping migration strategy không hard-code application vào một physical index duy nhất;
8. mô tả bulk indexing, retry/reconciliation và backpressure khi import lớn;
9. đề xuất tests + telemetry để phát hiện index drift, expensive queries và stale data.

## Câu hỏi gợi mở

1. Exact SKU lookup có thực sự nên chạy trên analyzed `text` field không?
2. `name` và `description` là full-text content nhưng lại map `keyword`; điều đó tác động tokenization/relevance thế nào?
3. Giá trị `"100"`, `"20"`, `"9"` khi sort như string có cùng thứ tự với decimal numeric không?
4. Nếu SQL commit xong nhưng Elasticsearch đang outage và exception chỉ được log, data sẽ được đồng bộ lại bằng cơ chế nào?
5. Khi cần thay analyzer/mapping không compatible, application có thể reindex sang index mới rồi đổi traffic mà không downtime bằng cách nào?

## Gợi ý

### Gợi ý 1

Primary risk là **schema/query semantics không khớp và search index đang được cập nhật bằng best-effort dual write không có recovery path**.

### Gợi ý 2

Tách ba bài toán:

`source-of-truth consistency` → `indexing pipeline` → `search query/mapping`

Đừng cố giải cả ba chỉ bằng một HTTP call `IndexAsync` ngay sau `SaveChangesAsync`.

## Kết quả code review tham khảo

### Critical — SQL và Elasticsearch dual-write có thể drift vĩnh viễn

**Vấn đề:**  
SQL commit trước, sau đó index Elasticsearch best-effort. Nếu Elasticsearch call fail, code chỉ log và trả control cho caller.

**Tại sao xảy ra:**  
Không có atomic transaction giữa SQL Server và Elasticsearch trong flow này. Một failure sau SQL commit để lại source of truth mới nhưng search index cũ.

**Ảnh hưởng production:**  
Search trả product stale hoặc thiếu product không giới hạn thời gian nếu không có reconciliation/retry pipeline. User có thể update product thành inactive nhưng search vẫn hiển thị nó.

**Cách sửa:**  
Ghi một durable indexing intent cùng transaction SQL, ví dụ Outbox/change table. Background indexer đọc intent, retry với backoff và đánh dấu processed. Thêm periodic reconciliation theo version/updated timestamp để sửa drift.

---

### High — Full-text fields được map thành `keyword`

**Vấn đề:**  
`name` và `description` dùng `keyword` dù requirement là full-text search.

**Tại sao xảy ra:**  
`keyword` phù hợp exact values, filtering, aggregations và sorting; nó không được analyzed thành terms theo cách full-text search thường cần.

**Ảnh hưởng production:**  
Relevance kém, query buộc dùng wildcard/substrings, khó tận dụng inverted index theo intent của search engine.

**Cách sửa:**  
Map full-text fields là `text`, chọn analyzer theo language/content requirement. Có thể thêm multi-field `keyword` cho exact sort/filter nếu thực sự cần.

---

### High — `sku` và `categoryId` dùng `text` cho exact-match semantics

**Vấn đề:**  
Hai identifiers được map analyzed text.

**Tại sao xảy ra:**  
SKU/category ID thường là exact identifiers, không phải natural language.

**Ảnh hưởng production:**  
Exact `term` queries có thể không match như expected tùy analyzer/tokenization, và mapping thể hiện sai domain semantics.

**Cách sửa:**  
Dùng `keyword` cho exact identifiers. Nếu SKU cần cả normalized lookup và partial UI search, tạo explicit secondary field/search strategy thay vì biến primary identifier thành free text.

---

### High — `price` là `keyword` nhưng được sort như numeric

**Vấn đề:**  
Price được index dưới dạng string.

**Tại sao xảy ra:**  
Lexicographic ordering khác numeric ordering.

**Ảnh hưởng production:**  
Sort price sai và range query/aggregation numeric không đúng semantics.

**Cách sửa:**  
Map theo numeric type phù hợp precision requirement của product domain. Với money, cần thống nhất representation/scale thay vì tùy tiện dùng floating point nếu business yêu cầu exact minor-unit semantics.

---

### High — Leading wildcard query trên catalog lớn có thể rất đắt

**Vấn đề:**  
Query `*{query}*` tìm substring tùy ý trên `name`.

**Tại sao xảy ra:**  
Leading wildcard không tận dụng search structure hiệu quả như normal analyzed term query và có thể mở rộng rất nhiều candidate terms, đặc biệt với high-cardinality vocabulary.

**Ảnh hưởng production:**  
CPU/query latency tăng mạnh dưới load; một query ngắn có thể trở thành expensive query.

**Cách sửa:**  
Dùng analyzed `match`/`multi_match` cho full-text. Nếu business thực sự cần prefix/autocomplete/substring, thiết kế dedicated field/analyzer/query type theo use case và benchmark với realistic corpus. Không dùng wildcard làm default full-text engine.

---

### High — Raw JSON query interpolation tạo correctness/injection-like query construction risk

**Vấn đề:**  
`query` và `categoryId` được nhúng trực tiếp vào raw JSON string.

**Tại sao xảy ra:**  
Quotes/escape characters có thể làm invalid JSON hoặc thay đổi query structure nếu abstraction không escape hộ.

**Ảnh hưởng production:**  
Search failures, unexpected queries và logging/debugging khó kiểm soát.

**Cách sửa:**  
Dùng typed query DSL/request object hoặc serialize structured request bằng JSON serializer. Validate length/allowed shape cho user-facing search input.

---

### Medium — Filter clauses nằm trong `must` thay vì filter context

**Vấn đề:**  
`categoryId` và `isActive` là exact filters nhưng nằm trong query scoring path.

**Tại sao xảy ra:**  
Business không cần chúng đóng góp relevance score.

**Ảnh hưởng production:**  
Query intent kém rõ, bỏ lỡ filter-context optimization/caching behavior phù hợp.

**Cách sửa:**  
Đưa exact constraints vào `bool.filter`; chỉ full-text clauses tham gia score.

---

### Medium — Hard-code physical index name làm mapping migration khó

**Vấn đề:**  
Application đọc/ghi trực tiếp `products` và schema được mutate theo tên cố định.

**Tại sao xảy ra:**  
Nhiều mapping changes không thể áp dụng in-place theo cách mong muốn cho dữ liệu đã index. Reindex thường cần index version mới.

**Ảnh hưởng production:**  
Upgrade mapping/analyzer có thể yêu cầu downtime hoặc deploy coupling phức tạp.

**Cách sửa:**  
Dùng versioned physical indices như `products-v001`, `products-v002` và alias ổn định như `products-read`. Reindex/backfill index mới, verify, rồi switch alias atomically theo supported alias API.

---

### Medium — Không có explicit freshness/version contract

**Vấn đề:**  
Sau `UpdateProductAsync`, caller có thể giả định search thấy dữ liệu ngay nhưng design không cam kết điều đó.

**Tại sao xảy ra:**  
Elasticsearch indexing/search visibility có refresh semantics riêng, và pipeline asynchronous càng làm consistency eventual hơn.

**Ảnh hưởng production:**  
UI/tests flaky, team cố “fix” bằng forced refresh trên mọi write làm throughput giảm.

**Cách sửa:**  
Định nghĩa freshness SLO, ví dụ “95% updates searchable trong X giây” theo business requirement. Nếu UI cần read-your-own-write cho edit confirmation, đọc SQL/source-of-truth trực tiếp thay vì ép toàn search system thành strongly consistent.

---

### Medium — Import lớn chưa có bulk/backpressure strategy

**Vấn đề:**  
Một product một `IndexAsync` call không scale tốt cho catalog import lớn.

**Tại sao xảy ra:**  
Per-document network overhead và uncontrolled concurrency có thể overload Elasticsearch cluster hoặc application.

**Ảnh hưởng production:**  
Indexing queue lag, high CPU, rejected requests và search latency bị ảnh hưởng.

**Cách sửa:**  
Batch bằng Bulk API ở kích thước đo được, bounded concurrency, retry item-level transient failures và backpressure theo cluster health/rejection metrics. Không tăng batch/concurrency mù quáng.

## Phiên bản đề xuất

### 1. Mapping phù hợp hơn với query semantics

Ví dụ conceptual mapping:

```json
PUT products-v002
{
  "mappings": {
    "properties": {
      "productId":  { "type": "keyword" },
      "sku":        { "type": "keyword" },
      "name": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword" }
        }
      },
      "description": { "type": "text" },
      "categoryId":  { "type": "keyword" },
      "priceMinor":  { "type": "long" },
      "currency":    { "type": "keyword" },
      "isActive":    { "type": "boolean" },
      "sourceVersion": { "type": "long" },
      "updatedAtUtc": { "type": "date" }
    }
  }
}
```

`priceMinor` chỉ là một ví dụ nếu domain lưu money theo minor unit. Nếu hệ thống có multi-currency/decimal scale khác, mapping phải theo contract thực tế.

### 2. Query dùng full-text + filter rõ ràng

```json
POST products-read/_search
{
  "query": {
    "bool": {
      "must": [
        {
          "multi_match": {
            "query": "wireless keyboard",
            "fields": ["name^3", "description"]
          }
        }
      ],
      "filter": [
        { "term": { "categoryId": "electronics" } },
        { "term": { "isActive": true } }
      ]
    }
  },
  "sort": [
    { "priceMinor": "asc" }
  ]
}
```

Exact SKU lookup nên dùng:

```json
{ "term": { "sku": "KB-1042-US" } }
```

Không bắt buộc mọi search use case dùng cùng query. Autocomplete, typo tolerance, exact lookup và free-text search nên có explicit semantics riêng.

### 3. Durable indexing pipeline từ SQL source of truth

Trong SQL transaction khi update product:

```csharp
public async Task UpdateProductAsync(
    ProductDto input,
    CancellationToken cancellationToken)
{
    var product = await _db.Products.SingleAsync(
        x => x.Id == input.Id,
        cancellationToken);

    product.Apply(input);
    product.Version++;

    _db.SearchIndexOutbox.Add(new SearchIndexOutbox
    {
        Id = Guid.NewGuid(),
        AggregateId = product.Id,
        Version = product.Version,
        Operation = "UpsertProduct",
        CreatedAtUtc = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(cancellationToken);
}
```

Indexer đọc Outbox theo batch. Với mỗi item, nó load projection cần thiết từ SQL hoặc dùng payload đã versioned, rồi index document với `sourceVersion`.

Pseudo-code:

```csharp
foreach (var batch in pending.BatchesOf(500))
{
    var documents = await LoadProductProjectionsAsync(batch, ct);

    var result = await _search.BulkIndexAsync(
        aliasOrWriteIndex: "products-write",
        documents,
        ct);

    MarkSucceededItems(result.SucceededIds);
    ScheduleRetryForTransientFailures(result.TransientFailures);
    QuarantinePermanentFailures(result.PermanentFailures);

    await _db.SaveChangesAsync(ct);
}
```

Kích thước batch 500 ở đây chỉ minh họa; production phải benchmark theo document size, heap/CPU, network và Elasticsearch rejection behavior.

Nếu events có thể out-of-order, indexer phải dùng `sourceVersion` để ngăn event cũ overwrite document mới.

### 4. Mapping migration bằng versioned index + alias

Flow:

```text
products-read -> products-v001

create products-v002 with new mapping
        |
        v
reindex/backfill from SQL source of truth
        |
        v
validate count + sample queries + version/freshness
        |
        v
switch products-read alias -> products-v002
        |
        v
monitor
        |
        v
delete v001 only after rollback window
```

Alias giúp application không cần hard-code physical index version và hỗ trợ reindex không downtime theo architecture phù hợp.

Tài liệu tham khảo:

- Elastic Docs — Aliases: `https://www.elastic.co/docs/manage-data/data-store/aliases`

## Giải thích thiết kế sau khi sửa

SQL Server vẫn là source of truth. Elasticsearch được coi là rebuildable read model/search projection.

Điều này dẫn đến các quyết định:

- product update thành công khi SQL transaction commit;
- indexing là asynchronous, durable và retryable;
- search freshness được đo bằng version/lag chứ không giả định immediate consistency;
- mapping migration tạo index mới thay vì biến production index thành mutable schema không kiểm soát;
- application query qua alias ổn định;
- search failure không được phép làm mất transactional product update;
- nếu Elasticsearch mất toàn bộ index, system có thể rebuild từ SQL + durable version state.

## Trade-offs

- Eventual consistency trở thành explicit product behavior; UI cần xử lý edit-confirmation/read-your-own-write phù hợp.
- Outbox/indexer tăng operational components và cần cleanup/retry policy.
- Multi-field mapping tăng index size; chỉ thêm fields phục vụ real query/use case.
- Rich analyzers/autocomplete/ngram có thể cải thiện UX nhưng làm index lớn hơn và indexing/query cost tăng; cần benchmark.
- Alias migration giúp giảm downtime nhưng vẫn cần rollback plan và kiểm tra compatibility giữa application query và cả old/new mappings trong deployment window.
- Bulk throughput cao hơn nhưng batch quá lớn/concurrency quá cao có thể làm search cluster mất ổn định.

## Cách kiểm thử

1. **Mapping/query integration test:** exact SKU, full-text name/description, category/isActive filter và numeric price sort cho kết quả đúng semantics.
2. **Failure-path test:** SQL commit thành công trong lúc Elasticsearch unavailable; Outbox còn pending và indexer đồng bộ lại sau recovery.
3. **Ordering test:** version N+1 index trước version N; document cuối cùng vẫn giữ N+1.
4. **Reindex deployment test:** build `v002`, backfill, switch alias, chạy representative queries rồi rollback alias nếu error rate/latency tăng.
5. **Load test:** 8M-like dataset distribution, realistic query mix và bulk import burst; đo p95/p99 search latency, CPU/heap, rejected requests và indexing lag.

## Quan sát trong production

Nên theo dõi:

- search request p50/p95/p99;
- query type/fingerprint và slow-query samples;
- Elasticsearch CPU/heap/GC;
- rejected search/bulk operations;
- indexing throughput;
- Outbox pending count;
- age of oldest indexing item;
- source SQL version vs indexed `sourceVersion` lag;
- reconciliation mismatch count;
- alias → physical index version;
- search error ratio;
- zero-result rate theo query class;
- cache hit nếu có search/application cache;
- deployment/reindex progress và rollback marker.

Đừng chỉ alert “Elasticsearch health red”. Business-facing alert nên bao gồm search availability, latency, freshness lag và indexing backlog.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product Manager yêu cầu “sửa product xong phải search thấy ngay lập tức”, bạn sẽ hỏi gì để phân biệt UX requirement thực sự với strong-consistency requirement toàn hệ thống?
2. Nếu index `v002` cần analyzer mới và application query mới chỉ tương thích với `v002`, bạn sẽ sequence application deployment và alias switch thế nào để giữ rollback an toàn?
3. Một teammate đề xuất bỏ SQL và dùng Elasticsearch làm source of truth để hết dual-write. Bạn đánh giá recommendation đó dựa trên transactional/business requirements nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus PeekLock/redelivery phải được xem như normal distributed-system behavior. Consumer cần idempotent thay vì giả định “một message chỉ xuất hiện một lần”.
- `check-then-insert` ở application không bảo vệ invariant dưới concurrency; unique constraint/atomic state transition tại source of truth mới là correctness boundary.
- Không thể giả định exactly-once transaction xuyên SQL Server, Service Bus và external provider chỉ bằng thứ tự `await`. Inbox/Outbox giúp tách durable local commit khỏi retryable external side effect.
- Elasticsearch nên được coi là search projection/read model khi SQL là source of truth; dual-write best effort không có recovery path sẽ tạo drift.
- Mapping phải phản ánh query semantics: `text` cho analyzed full-text, `keyword` cho exact identifiers/filter/sort, numeric field cho numeric sort/range.
- Search freshness, reindexing và deployment là operational contracts. Alias + versioned index + durable indexing pipeline giúp mapping evolution và rollback rõ hơn.

## Mẫu tư duy cần nhớ

- **Vẽ failure windows:** đặt crash/network failure giữa từng bước để kiểm tra flow có phục hồi được không.
- **Invariant phải được enforce tại source of truth:** pre-check trong application không đủ dưới concurrency.
- **Tách transactional state khỏi external side effect:** durable intent trước, side effect retry sau.
- **Schema phải đi cùng query semantics:** chọn data type/analyzer theo cách dữ liệu được search/filter/sort.
- **Eventual consistency phải được đo:** định nghĩa freshness SLO và version/lag telemetry thay vì nói chung chung “eventually consistent”.
