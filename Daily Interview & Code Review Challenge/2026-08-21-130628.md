# Code Review Challenge 1 — Hangfire job cấp quyền bị chạy lặp

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core application dùng Hangfire để xử lý yêu cầu cấp quyền truy cập mailbox. API tạo `PermissionRequest`, sau đó enqueue job gọi Microsoft Graph/Exchange integration. Production đôi khi ghi nhận cùng một user được xử lý hai lần khi worker restart hoặc job retry. Một số request trong database có trạng thái `Completed` dù thao tác bên ngoài thất bại, trong khi một số request khác vẫn `Processing` rất lâu.

Hệ thống chạy nhiều Hangfire workers trên hai application instances. Thao tác bên ngoài có thể timeout sau khi remote system đã thực sự nhận request. Không giả định remote API hỗ trợ transaction chung với SQL Server.

## Đoạn code cần review

```csharp
public sealed class PermissionJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeClient _exchange;
    private readonly ILogger<PermissionJob> _logger;

    public PermissionJob(
        AppDbContext db,
        IExchangeClient exchange,
        ILogger<PermissionJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync(Guid requestId)
    {
        var request = await _db.PermissionRequests
            .FirstOrDefaultAsync(x => x.Id == requestId);

        if (request == null)
            return;

        if (request.Status == "Completed")
            return;

        request.Status = "Processing";
        request.AttemptCount++;
        await _db.SaveChangesAsync();

        try
        {
            await _exchange.GrantMailboxPermissionAsync(
                request.UserEmail,
                request.TargetEmail);

            request.Status = "Completed";
            request.CompletedAtUtc = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Permission request failed: {@Request}", request);

            request.Status = "Failed";
            request.LastError = ex.ToString();
            await _db.SaveChangesAsync();
            throw;
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-update tạo race condition

- **Problem:** Hai worker có thể cùng đọc request chưa `Completed` rồi cùng xử lý.
- **Why:** `SELECT` và cập nhật `Processing` là các thao tác riêng; không có atomic compare-and-set hay concurrency token.
- **Production impact:** Side effect bên ngoài có thể chạy nhiều lần.
- **Severity:** Critical
- **Recommended fix:** Claim request bằng conditional update/optimistic concurrency và chỉ worker thắng mới tiếp tục.

### 2. Retry không được kết hợp với idempotency

- **Problem:** Hangfire có thể retry sau exception, nhưng remote call có thể đã thành công trước khi client nhận response.
- **Why:** Timeout/network failure không chứng minh server chưa thực hiện side effect.
- **Production impact:** Cấp quyền lặp, notification lặp hoặc trạng thái remote/local lệch nhau.
- **Severity:** Critical
- **Recommended fix:** Dùng idempotency key nếu dependency hỗ trợ; nếu operation tự nhiên idempotent thì xác minh điều đó; nếu không, lưu operation identity và reconciliation state.

### 3. `Failed` mô tả sai trạng thái khi outcome chưa xác định

- **Problem:** Mọi exception đều chuyển request sang `Failed`.
- **Why:** Có exception mang nghĩa definitive failure, nhưng timeout có thể là unknown outcome.
- **Production impact:** Retry hoặc operator có thể thực hiện lại một side effect đã thành công.
- **Severity:** High
- **Recommended fix:** Phân biệt `Retryable`, `Failed`, `UnknownOutcome`/`NeedsReconciliation`.

### 4. Không truyền cancellation/timeout policy rõ ràng

- **Problem:** Job không thể hiện cancellation token hoặc deadline cho external call.
- **Why:** Dependency chậm có thể giữ worker lâu hơn cần thiết.
- **Production impact:** Worker saturation, backlog tăng và shutdown khó kiểm soát.
- **Severity:** High
- **Recommended fix:** Thiết lập timeout tại HTTP/client policy và hỗ trợ cancellation phù hợp với execution model.

### 5. Retry tất cả exception cùng một cách

- **Problem:** Validation/authentication/permanent errors cũng bị retry.
- **Why:** `AutomaticRetry` không phân loại lỗi business/permanent tại đoạn code này.
- **Production impact:** Tốn worker, tăng tải dependency và che mất lỗi cấu hình.
- **Severity:** Medium
- **Recommended fix:** Phân loại lỗi; chỉ throw để retry transient failures, còn permanent failures kết thúc có chủ đích.

### 6. Logging quá nhiều dữ liệu

- **Problem:** Structured logging toàn bộ entity và `ex.ToString()` được lưu DB.
- **Why:** Entity/error có thể chứa email, identifiers hoặc response nhạy cảm.
- **Production impact:** PII/secrets xuất hiện trong log/database và tăng kích thước record.
- **Severity:** Medium
- **Recommended fix:** Log request ID, error category, correlation ID; sanitize/truncate remote error.

### 7. Không có recovery rõ ràng cho request kẹt ở `Processing`

- **Problem:** Process crash sau khi ghi `Processing` nhưng trước completion có thể để record treo.
- **Why:** Không có lease/claimed timestamp/reconciliation policy.
- **Production impact:** Request không được hoàn tất hoặc phải sửa thủ công.
- **Severity:** Medium
- **Recommended fix:** Lưu `ClaimedAtUtc`, lease/attempt metadata và có reconciliation job cho stale work.

### 8. Magic strings cho state machine

- **Problem:** State là chuỗi tự do.
- **Why:** Không enforce transition hợp lệ.
- **Production impact:** Dễ sinh trạng thái typo hoặc transition sai khi code mở rộng.
- **Severity:** Low
- **Recommended fix:** Enum/value object cùng transition rules rõ ràng.

## Phiên bản code đề xuất

```csharp
public sealed class PermissionJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeClient _exchange;
    private readonly TimeProvider _time;
    private readonly ILogger<PermissionJob> _logger;

    public PermissionJob(
        AppDbContext db,
        IExchangeClient exchange,
        TimeProvider time,
        ILogger<PermissionJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _time = time;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync(Guid requestId, CancellationToken ct)
    {
        var now = _time.GetUtcNow();

        var claimed = await _db.PermissionRequests
            .Where(x => x.Id == requestId &&
                        (x.Status == "Pending" || x.Status == "Retryable"))
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.ClaimedAtUtc, now)
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1), ct);

        if (claimed == 0)
            return;

        var request = await _db.PermissionRequests
            .AsNoTracking()
            .SingleAsync(x => x.Id == requestId, ct);

        try
        {
            await _exchange.EnsureMailboxPermissionAsync(
                request.OperationId,
                request.UserEmail,
                request.TargetEmail,
                ct);

            await _db.PermissionRequests
                .Where(x => x.Id == requestId && x.Status == "Processing")
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, "Completed")
                    .SetProperty(x => x.CompletedAtUtc, _time.GetUtcNow())
                    .SetProperty(x => x.LastError, (string?)null), ct);
        }
        catch (RemoteOutcomeUnknownException ex)
        {
            await MarkAsync(requestId, "NeedsReconciliation", ex.Code, ct);
            throw;
        }
        catch (TransientRemoteException ex)
        {
            await MarkAsync(requestId, "Retryable", ex.Code, ct);
            throw;
        }
        catch (Exception ex)
        {
            await MarkAsync(requestId, "Failed", "permanent_failure", ct);
            _logger.LogError(ex,
                "Permission operation {OperationId} failed for request {RequestId}",
                request.OperationId, requestId);
        }
    }

    private Task MarkAsync(Guid id, string status, string errorCode,
        CancellationToken ct) =>
        _db.PermissionRequests
            .Where(x => x.Id == id)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, status)
                .SetProperty(x => x.LastError, errorCode), ct);
}
```

`EnsureMailboxPermissionAsync` ở đây là abstraction được thiết kế để đạt semantics idempotent phù hợp với dependency thực tế; không giả định mọi Exchange/Microsoft API đều cung cấp idempotency key. Nếu remote API không hỗ trợ, implementation phải query/reconcile trạng thái hoặc dùng business operation vốn có tính idempotent.

## Trade-offs

Conditional update đơn giản và phù hợp khi SQL database là nguồn coordination chính. Lease phức tạp hơn nhưng cần thiết nếu operation dài và worker có thể chết giữa chừng. Distributed lock có thể giảm duplicate execution nhưng không tự giải quyết “remote succeeded, response lost”; vì vậy lock không thay thế idempotency. Outbox hữu ích khi cần đảm bảo database state và việc phát message nhất quán, nhưng vẫn không tạo distributed transaction với remote service.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời nhiều `ExecuteAsync` cho cùng `requestId`; chỉ một worker được claim.
2. **Unknown-outcome test:** fake remote side effect thành công rồi throw timeout; record phải chuyển sang reconciliation thay vì blindly replay.
3. **Retry test:** transient failure rồi success; kiểm tra attempt count và chỉ một logical side effect.
4. **Crash/recovery test:** giả lập worker chết sau claim; stale processing record phải được recovery theo lease/reconciliation policy.
5. **Security/logging test:** bảo đảm log không chứa mailbox payload/token hoặc raw sensitive response.

## Quan sát trong production

Theo dõi `job_attempt_total`, `permission_duplicate_prevented_total`, số request theo state, tuổi của request `Processing`, reconciliation backlog và external-call latency/error category. Trace nên liên kết Hangfire job ID, request ID và operation ID. Alert khi `Processing` vượt lease, `NeedsReconciliation` tăng hoặc retry rate tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Nếu không dùng `ExecuteUpdateAsync`, bạn có thể implement optimistic concurrency bằng `rowversion` như thế nào?
2. Tại sao distributed lock vẫn không giải quyết hoàn toàn duplicate side effect khi network timeout?
3. Nếu phải gửi thêm email notification sau khi DB chuyển `Completed`, bạn sẽ dùng outbox ở đâu?

# Code Review Challenge 2 — Endpoint tìm kiếm outlet kéo toàn bộ dữ liệu về memory

**Chủ đề:** EF Core query execution, SQL/spatial performance, cancellation, input validation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một API tìm outlet trong viewport bản đồ. Bảng có hàng triệu outlet và traffic tăng mạnh khi người dùng pan/zoom bản đồ. Production ghi nhận request đôi lúc mất nhiều giây, application memory tăng và SQL Server CPU không tương ứng với lượng filtering mà API thực hiện.

Mỗi outlet có latitude/longitude và một spatial `Point` đã được lưu trong database. Một số client gửi viewport rất lớn. Endpoint chỉ cần trả tối đa 200 outlet gần viewport hiện tại.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/outlets")]
public sealed class OutletsController : ControllerBase
{
    private readonly AppDbContext _db;

    public OutletsController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet("search")]
    public async Task<ActionResult<List<OutletDto>>> Search(
        double minLat,
        double minLng,
        double maxLat,
        double maxLng,
        string? keyword)
    {
        var outlets = await _db.Outlets
            .Include(x => x.Address)
            .Include(x => x.Categories)
            .ToListAsync();

        var result = outlets
            .Where(x => x.Latitude >= minLat &&
                        x.Latitude <= maxLat &&
                        x.Longitude >= minLng &&
                        x.Longitude <= maxLng)
            .Where(x => string.IsNullOrWhiteSpace(keyword) ||
                        x.Name.ToLower().Contains(keyword.ToLower()))
            .OrderBy(x => x.Name)
            .Select(x => new OutletDto
            {
                Id = x.Id,
                Name = x.Name,
                Latitude = x.Latitude,
                Longitude = x.Longitude,
                Address = x.Address.FullAddress,
                Categories = x.Categories.Select(c => c.Name).ToList()
            })
            .Take(200)
            .ToList();

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ bảng trước khi filter

- **Problem:** `ToListAsync()` chạy ngay sau `Include`.
- **Why:** Sau materialization, các `Where`, `OrderBy` và `Take` là LINQ-to-Objects.
- **Production impact:** Đọc hàng triệu rows, memory pressure, latency và network/database I/O lớn.
- **Severity:** Critical
- **Recommended fix:** Giữ query dưới dạng `IQueryable` đến projection/`Take` cuối cùng rồi mới `ToListAsync`.

### 2. `Include` toàn bộ navigation trước khi biết row nào cần

- **Problem:** Address/Categories được eager-load cho toàn bộ outlet.
- **Why:** Include xảy ra trước filtering.
- **Production impact:** Data explosion, nhiều allocation và có thể tạo lượng dữ liệu join rất lớn.
- **Severity:** High
- **Recommended fix:** Filter trước và project trực tiếp DTO; chỉ lấy columns/navigation cần thiết.

### 3. Không tận dụng spatial predicate/index đã có

- **Problem:** Viewport filter bằng scalar values sau khi dữ liệu đã ở memory.
- **Why:** Database không được giao nhiệm vụ spatial filtering.
- **Production impact:** Mất khả năng giảm candidate rows sớm bằng database index strategy.
- **Severity:** High
- **Recommended fix:** Tạo polygon/envelope phù hợp SRID và dùng spatial predicate được EF/provider dịch sang SQL, sau đó xác minh execution plan thực tế.

### 4. Không validate bounding box

- **Problem:** Không kiểm tra range/order của lat/lng hoặc viewport bất thường.
- **Why:** Client input được dùng trực tiếp.
- **Production impact:** Kết quả sai, query quá rộng hoặc khó xử lý trường hợp crossing antimeridian.
- **Severity:** High
- **Recommended fix:** Validate latitude/longitude, min/max và xác định rõ policy cho antimeridian/viewport quá lớn.

### 5. Keyword normalization gây allocation và semantics không rõ

- **Problem:** `ToLower()` chạy cho từng entity trong memory và culture/collation semantics không được xác định.
- **Why:** Filtering không nằm ở database.
- **Production impact:** CPU/allocation tăng; search semantics có thể khác DB.
- **Severity:** Medium
- **Recommended fix:** Để DB xử lý với collation/search strategy phù hợp; escape wildcard nếu dùng LIKE semantics theo yêu cầu.

### 6. Không truyền request cancellation

- **Problem:** Client disconnect không hủy database work.
- **Why:** Không nhận `CancellationToken` từ request.
- **Production impact:** Work vô ích tiếp tục chiếm connection/resources.
- **Severity:** Medium
- **Recommended fix:** Nhận token và truyền tới EF async operation.

### 7. Tracking không cần thiết cho read-only endpoint

- **Problem:** Query entity mặc định có tracking.
- **Why:** Endpoint chỉ đọc DTO.
- **Production impact:** Thêm change-tracking overhead, đặc biệt nghiêm trọng với result lớn hiện tại.
- **Severity:** Medium
- **Recommended fix:** Projection trực tiếp thường đã tránh tracking entity output; có thể dùng `AsNoTracking` rõ ràng cho read query.

### 8. Không có deterministic tie-breaker

- **Problem:** `OrderBy(Name)` không bảo đảm ổn định khi nhiều outlet trùng tên.
- **Why:** Không có secondary unique key.
- **Production impact:** Kết quả top 200 có thể thay đổi giữa các lần chạy.
- **Severity:** Low
- **Recommended fix:** Thêm `ThenBy(Id)` nếu deterministic ordering là yêu cầu.

## Phiên bản code đề xuất

```csharp
[HttpGet("search")]
public async Task<ActionResult<List<OutletDto>>> Search(
    double minLat,
    double minLng,
    double maxLat,
    double maxLng,
    string? keyword,
    CancellationToken ct)
{
    if (minLat is < -90 or > 90 || maxLat is < -90 or > 90 ||
        minLng is < -180 or > 180 || maxLng is < -180 or > 180 ||
        minLat >= maxLat || minLng >= maxLng)
    {
        return BadRequest("Invalid viewport.");
    }

    var bbox = GeometryFactoryProvider.Wgs84.CreatePolygon(new[]
    {
        new Coordinate(minLng, minLat),
        new Coordinate(maxLng, minLat),
        new Coordinate(maxLng, maxLat),
        new Coordinate(minLng, maxLat),
        new Coordinate(minLng, minLat)
    });

    IQueryable<Outlet> query = _db.Outlets
        .AsNoTracking()
        .Where(x => x.Location.Intersects(bbox));

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x => x.Name.Contains(term));
    }

    var result = await query
        .OrderBy(x => x.Name)
        .ThenBy(x => x.Id)
        .Take(200)
        .Select(x => new OutletDto
        {
            Id = x.Id,
            Name = x.Name,
            Latitude = x.Latitude,
            Longitude = x.Longitude,
            Address = x.Address.FullAddress,
            Categories = x.Categories.Select(c => c.Name).ToList()
        })
        .ToListAsync(ct);

    return Ok(result);
}
```

Ví dụ trên giả định `Location` và `bbox` dùng cùng SRID và EF Core spatial provider có thể dịch predicate thành SQL cho database đang dùng. Cần kiểm tra SQL được sinh và actual execution plan thay vì mặc định kết luận index chắc chắn được dùng. Với SQL Server, spatial-index effectiveness phụ thuộc schema, predicate và query plan thực tế. Nếu business phải hỗ trợ viewport qua antimeridian, validation/query cần được thiết kế khác thay vì đơn giản từ chối `minLng >= maxLng`.

## Trade-offs

Spatial search phù hợp khi dữ liệu/query thực sự là địa lý và đã có spatial column/index. Scalar lat/lng với composite/filtered indexes có thể đủ cho dataset nhỏ hoặc query đơn giản, nhưng cần benchmark trên distribution thật. Projection với collection navigation có thể tạo SQL phức tạp; nếu category cardinality cao, có thể cân nhắc query hai phase cho tối đa 200 IDs. Keyword `Contains` không tự động trở thành full-text search hiệu quả; nếu search text trở thành bottleneck riêng, cần chọn full-text/trigram/search engine theo database và yêu cầu.

## Cách kiểm thử

1. **Integration test:** xác minh outlets trong/ngoài bbox và boundary behavior.
2. **SQL translation test:** capture generated SQL, bảo đảm filter và `Take` nằm ở database trước materialization.
3. **Load test:** viewport nhỏ/lớn, nhiều concurrent map requests; đo p50/p95/p99, allocations và DB reads.
4. **Database test:** so actual execution plan và logical reads trước/sau index/query change trên data volume gần production.
5. **Cancellation/input test:** client cancel, invalid coordinates và viewport vượt policy phải được xử lý có kiểm soát.

## Quan sát trong production

Ghi duration, result count, viewport size bucket và query fingerprint; không log raw user data không cần thiết. Theo dõi API p95/p99, EF query duration, DB logical reads/CPU, connection-pool pressure, GC allocation rate và cancellation count. Dùng distributed trace để tách thời gian API, EF và database. Alert theo latency/error SLO thay vì chỉ CPU.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng **retry và idempotency phải được thiết kế cùng nhau**. Database transaction không thể tự biến remote side effect thành atomic operation; timeout còn tạo trạng thái unknown outcome cần reconciliation. Atomic claim giúp giảm concurrent execution nhưng không thay thế idempotency.

Challenge 2 nhấn mạnh **query execution boundary** trong EF Core. Một `ToListAsync()` đặt quá sớm có thể biến database filtering thành in-memory filtering và làm mọi index phía database trở nên vô nghĩa cho phần predicate đó. Tối ưu phải được xác minh bằng generated SQL, execution plan và benchmark trên dữ liệu thực.

## Mẫu tư duy cần nhớ

- Xác định execution boundary trước khi tối ưu query.
- Thiết kế retries cùng idempotency và unknown-outcome recovery.
- Atomic claim giải quyết concurrency nhưng không giải quyết mọi distributed failure.
- Measure before optimizing: kiểm tra SQL, execution plan, p95/p99 và resource usage.
- Treat observability and recovery as part of the design, không phải phần bổ sung sau cùng.
