# Code Review Challenge 1 — Cache-aside dưới tải cao: stale overwrite và cache stampede

**Chủ đề:** Caching, concurrency, EF Core, async/await  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp thông tin outlet cho ứng dụng mobile. Dữ liệu thay đổi không thường xuyên nên team dùng Redis cache TTL 10 phút. API chạy nhiều instance sau load balancer và đạt khoảng 1.500 request/giây vào giờ cao điểm.

Sau một đợt tăng traffic, team quan sát thấy database CPU tăng đột biến mỗi khi một nhóm key hết hạn. Một số người dùng cũng báo vừa cập nhật outlet xong nhưng GET đôi lúc trả dữ liệu cũ trong vài phút. Không phải request nào cũng tái hiện được lỗi.

Redis và database là shared infrastructure cho tất cả application instances. Yêu cầu business chưa nói rõ mức consistency cần thiết ngay sau update.

## Đoạn code cần review

```csharp
public sealed class OutletService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public OutletService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<OutletDto?> GetAsync(Guid id)
    {
        var key = $"outlet:{id}";
        var cached = await _cache.GetStringAsync(key);

        if (cached != null)
            return JsonSerializer.Deserialize<OutletDto>(cached);

        var outlet = await _db.Outlets
            .FirstOrDefaultAsync(x => x.Id == id);

        if (outlet == null)
            return null;

        var dto = new OutletDto(outlet.Id, outlet.Name, outlet.Address);

        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            });

        return dto;
    }

    public async Task UpdateAsync(Guid id, string name, string address)
    {
        var outlet = await _db.Outlets.SingleAsync(x => x.Id == id);
        outlet.Name = name;
        outlet.Address = address;

        await _db.SaveChangesAsync();
        await _cache.RemoveAsync($"outlet:{id}");
    }
}
```

## Kết quả code review tham khảo

### 1. GET cũ có thể ghi dữ liệu stale trở lại cache sau Update

- **Problem:** Một GET có thể đọc bản cũ từ DB, sau đó Update commit và xóa cache, rồi GET mới ghi bản cũ vào cache.
- **Why it happens:** Database operation và cache operation không thuộc cùng một atomic boundary.
- **Production impact:** Client có thể nhận dữ liệu cũ cho tới khi TTL hết hạn.
- **Severity:** High
- **Recommended fix:** Xác định consistency requirement. Với dữ liệu cần read-after-write tốt hơn, dùng versioned cache key/value, kiểm tra version trước khi populate, hoặc cơ chế invalidation/version phù hợp. Không coi delete-after-commit đơn thuần là bằng chứng rằng stale repopulation không thể xảy ra.

### 2. Cache stampede khi key hết hạn

- **Problem:** Tất cả concurrent cache misses đều query database.
- **Why it happens:** Không có request coalescing/single-flight hoặc distributed coordination.
- **Production impact:** DB CPU, connection usage và latency tăng mạnh đúng lúc hot key hết hạn.
- **Severity:** High
- **Recommended fix:** Dùng per-key request coalescing; nếu cần coordination giữa nhiều instances thì cân nhắc distributed locking có timeout/failure semantics rõ ràng, hoặc cache design có soft expiration/background refresh. Thêm TTL jitter để giảm synchronized expiration.

### 3. Không truyền `CancellationToken`

- **Problem:** Redis và EF Core vẫn có thể tiếp tục công việc sau khi client disconnect hoặc request timeout.
- **Why it happens:** Methods không nhận token và không truyền token xuống async I/O.
- **Production impact:** Waste I/O và database capacity trong failure/load spike.
- **Severity:** Medium
- **Recommended fix:** Nhận `CancellationToken` từ caller và truyền tới cache/EF Core APIs hỗ trợ token.

### 4. Read query đang tracking entity không cần thiết

- **Problem:** `FirstOrDefaultAsync` mặc định tracking entity trong DbContext.
- **Why it happens:** Không dùng projection/`AsNoTracking()` cho read-only query.
- **Production impact:** Allocation/change-tracker overhead không cần thiết.
- **Severity:** Medium
- **Recommended fix:** Project trực tiếp sang DTO hoặc dùng `AsNoTracking()`.

### 5. Không cache negative result

- **Problem:** Một ID không tồn tại luôn hit database.
- **Why it happens:** `null` không được cache.
- **Production impact:** Invalid/missing hot IDs có thể gây repeated DB load.
- **Severity:** Medium
- **Recommended fix:** Nếu phù hợp business, cache negative result với TTL ngắn và phân biệt rõ “missing” với cache miss.

### 6. Fixed TTL có thể đồng bộ expiration

- **Problem:** Nhiều entries được tạo cùng thời điểm có thể cùng hết hạn.
- **Why it happens:** Mọi entry dùng đúng 10 phút.
- **Production impact:** Periodic DB load spikes.
- **Severity:** Medium
- **Recommended fix:** Thêm random jitter quanh TTL hoặc soft-expiration strategy.

### 7. Update không có concurrency policy rõ ràng

- **Problem:** Hai writers có thể ghi đè nhau theo last-write-wins mà không phát hiện conflict.
- **Why it happens:** Không có concurrency token/version và business semantics chưa được định nghĩa.
- **Production impact:** Lost update nếu nhiều nguồn cùng sửa outlet.
- **Severity:** Medium
- **Recommended fix:** Nếu lost update không chấp nhận được, dùng optimistic concurrency token và xử lý conflict rõ ràng.

## Phiên bản code đề xuất

Ví dụ dưới đây cải thiện cancellation, read query, TTL jitter và single-flight trong một process. Với nhiều application instances, single-flight local chỉ giảm duplicate work trong từng instance; nếu hot-key stampede xuyên instance vẫn đáng kể thì cần thêm distributed strategy.

```csharp
public sealed class OutletService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;
    private readonly ConcurrentDictionary<Guid, SemaphoreSlim> _locks = new();

    public OutletService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<OutletDto?> GetAsync(Guid id, CancellationToken ct)
    {
        var key = $"outlet:{id}";
        var cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<OutletDto>(cached);

        var gate = _locks.GetOrAdd(id, _ => new SemaphoreSlim(1, 1));
        await gate.WaitAsync(ct);

        try
        {
            cached = await _cache.GetStringAsync(key, ct);
            if (cached is not null)
                return JsonSerializer.Deserialize<OutletDto>(cached);

            var dto = await _db.Outlets
                .AsNoTracking()
                .Where(x => x.Id == id)
                .Select(x => new OutletDto(x.Id, x.Name, x.Address))
                .SingleOrDefaultAsync(ct);

            if (dto is null)
                return null;

            var ttl = TimeSpan.FromMinutes(9)
                      + TimeSpan.FromSeconds(Random.Shared.Next(0, 120));

            await _cache.SetStringAsync(
                key,
                JsonSerializer.Serialize(dto),
                new DistributedCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = ttl
                },
                ct);

            return dto;
        }
        finally
        {
            gate.Release();
        }
    }

    public async Task UpdateAsync(
        Guid id,
        string name,
        string address,
        CancellationToken ct)
    {
        var outlet = await _db.Outlets.SingleAsync(x => x.Id == id, ct);
        outlet.Name = name;
        outlet.Address = address;

        await _db.SaveChangesAsync(ct);
        await _cache.RemoveAsync($"outlet:{id}", ct);
    }
}
```

Phiên bản này chưa tuyên bố giải quyết hoàn toàn stale repopulation giữa nhiều instances. Nếu requirement yêu cầu mạnh hơn, có thể thêm monotonically increasing version vào database/cache và chỉ publish value tương ứng version hợp lệ, hoặc thiết kế write-through/versioned keys tùy consistency và chi phí mong muốn.

## Trade-offs

Single-flight local đơn giản và không tạo distributed-lock dependency nhưng chỉ phối hợp request trong cùng process. Distributed lock giảm cross-instance stampede nhưng thêm latency, availability concerns, lock timeout và failure modes. Soft TTL/background refresh có thể giữ latency ổn định hơn nhưng chấp nhận bounded staleness. Versioning tăng correctness nhưng làm invalidation và key lifecycle phức tạp hơn.

## Cách kiểm thử

1. **Concurrency test:** bắn hàng trăm GET vào một cold key và đo số DB queries; kỳ vọng request coalescing giảm mạnh duplicate queries trong cùng instance.
2. **Race test:** điều khiển timeline GET đọc DB cũ → Update commit/delete → GET tiếp tục; xác minh consistency strategy đã chọn xử lý đúng stale repopulation.
3. **Load test:** cho nhiều key hết hạn gần nhau, so sánh DB CPU/query rate trước và sau TTL jitter/coalescing.
4. **Cancellation test:** cancel request trong lúc chờ DB/Redis và xác minh downstream operation nhận cancellation phù hợp.
5. **Concurrent update test:** nếu dùng optimistic concurrency, hai writers trên cùng version phải tạo conflict có kiểm soát thay vì silent lost update.

## Quan sát trong production

Theo dõi cache hit/miss ratio, cache-fill duration, DB query count theo cache key class, Redis latency/error rate, request latency p95/p99, số concurrent cache fills, lock wait duration và database connection-pool utilization. Trace nên nối HTTP request → Redis → SQL để thấy miss path. Alert khi cache miss rate hoặc DB queries tăng bất thường sau expiration waves.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao distributed lock không tự động giải quyết stale cache correctness?
2. Nếu chấp nhận stale tối đa 30 giây, bạn có thay đổi design như thế nào?
3. Nếu Redis outage hoàn toàn, API nên fail closed, bypass cache hay degrade theo cách nào?

# Code Review Challenge 2 — Hangfire gửi email: retry biến side effect thành gửi trùng

**Chủ đề:** Background jobs, idempotency, transaction boundaries, failure recovery  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 7 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core tạo email thông báo khi lịch sự kiện thay đổi. API lưu notification record rồi enqueue Hangfire job. Job gọi một external mail provider và đánh dấu notification đã gửi.

Production thỉnh thoảng gửi cùng email hai lần. Log cho thấy một số lần provider trả thành công nhưng worker bị restart ngay sau đó. Team muốn giữ retry vì external provider đôi lúc timeout. Business yêu cầu không được silently mất notification; duplicate cũng cần giảm tối đa.

Chưa rõ provider có hỗ trợ idempotency key hay query trạng thái theo client-generated ID hay không.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IMailClient _mailClient;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IMailClient mailClient,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task SendAsync(long notificationId)
    {
        var notification = await _db.Notifications
            .SingleAsync(x => x.Id == notificationId);

        if (notification.Status == "Sent")
            return;

        var response = await _mailClient.SendAsync(
            notification.To,
            notification.Subject,
            notification.Body);

        if (!response.Success)
            throw new InvalidOperationException(response.Error);

        notification.Status = "Sent";
        notification.SentAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Sent notification {NotificationId} to {Recipient}",
            notification.Id,
            notification.To);
    }
}
```

## Nhiệm vụ của ứng viên

2. Phân tích retry, concurrency và side-effect risks.
3. Giải thích vì sao duplicate chỉ xuất hiện trong một số failure windows.
4. Ưu tiên các vấn đề.
5. Đề xuất corrected implementation/design.
6. Giải thích test strategy.
7. Đề xuất observability để phân biệt retry bình thường với duplicate delivery.

## Câu hỏi gợi mở

- Điều gì xảy ra nếu mail provider đã nhận email nhưng process chết trước `SaveChangesAsync()`?

## Kết quả code review tham khảo

### 1. Crash sau external success nhưng trước DB commit gây duplicate

- **Problem:** Provider có thể đã gửi mail nhưng database vẫn là Pending.
- **Why it happens:** External side effect và DB update không atomic.
- **Production impact:** Hangfire retry gọi provider lần nữa và gửi duplicate.
- **Severity:** Critical
- **Recommended fix:** Ưu tiên provider-supported idempotency key/client message ID nếu có. Dùng stable key gắn với logical notification và reuse key trên mọi retry. Nếu provider không hỗ trợ, phải chấp nhận semantics gần at-least-once và dùng reconciliation/deduplication strategy khả thi thay vì tuyên bố exactly-once.

### 2. Check-then-act không chống concurrent executions

- **Problem:** Hai workers có thể cùng đọc `Pending`, cùng gửi.
- **Why it happens:** `Status` check và state transition không có atomic claim/concurrency control.
- **Production impact:** Duplicate ngay cả khi không crash.
- **Severity:** High
- **Recommended fix:** Atomic claim bằng conditional update/concurrency token hoặc một cơ chế coordination phù hợp. Trạng thái nên thể hiện Pending/Processing/Sent/Failed cùng attempt metadata.

### 3. Timeout của provider có kết quả mơ hồ

- **Problem:** Timeout không chứng minh provider chưa xử lý request.
- **Why it happens:** Failure xảy ra sau khi request rời process nhưng trước khi response được nhận.
- **Production impact:** Blind retry có thể duplicate.
- **Severity:** High
- **Recommended fix:** Nếu provider hỗ trợ idempotency/query-by-client-ID, dùng nó để retry/reconcile. Nếu không, ghi nhận ambiguous outcome và thiết kế retry policy theo business risk.

### 4. Không có cancellation/timeout policy thể hiện rõ

- **Problem:** Job không truyền cancellation và code không cho thấy bounded timeout cho external call.
- **Why it happens:** Dependency call được thực hiện không có execution policy rõ ràng trong method contract.
- **Production impact:** Worker slot có thể bị giữ lâu, shutdown kém sạch và backlog tăng.
- **Severity:** Medium
- **Recommended fix:** Dùng cancellation mechanism phù hợp với background job/runtime và HTTP timeout policy; phân biệt timeout, transient và permanent errors.

### 5. Throw mọi provider failure như nhau

- **Problem:** Permanent failure và transient failure đều đi cùng retry path.
- **Why it happens:** Error classification không tồn tại.
- **Production impact:** Retry vô ích, backlog/noise và có thể tăng duplicate risk.
- **Severity:** Medium
- **Recommended fix:** Classify retryable vs permanent failures; dead-letter/manual review cho permanent/exhausted attempts.

### 6. Logging recipient có thể làm lộ PII không cần thiết

- **Problem:** Email address được log ở information level.
- **Why it happens:** Structured logging đưa recipient trực tiếp vào log store.
- **Production impact:** Tăng phạm vi dữ liệu cá nhân trong observability system.
- **Severity:** Medium
- **Recommended fix:** Log notification ID/provider message ID; mask/hash recipient nếu thực sự cần correlation và phù hợp policy.

### 7. String status dễ tạo invalid state

- **Problem:** Domain state dựa vào magic string và thiếu attempt/version metadata.
- **Why it happens:** State machine chưa được mô hình hóa rõ.
- **Production impact:** Khó kiểm soát transitions và recovery.
- **Severity:** Low
- **Recommended fix:** Dùng enum/value mapping cùng explicit transition rules, attempt count, timestamps và concurrency token nếu cần.

## Phiên bản code đề xuất

Giả sử mail provider hỗ trợ stable idempotency key. Atomic claim bên dưới là ý tưởng thiết kế; implementation cụ thể có thể dùng `ExecuteUpdateAsync`, concurrency token hoặc provider-specific SQL tùy database.

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IMailClient _mailClient;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IMailClient mailClient,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _mailClient = mailClient;
        _logger = logger;
    }

    public async Task SendAsync(long notificationId, CancellationToken ct)
    {
        var notification = await _db.Notifications
            .SingleAsync(x => x.Id == notificationId, ct);

        if (notification.Status == NotificationStatus.Sent)
            return;

        var idempotencyKey = $"notification:{notification.Id}";

        var result = await _mailClient.SendAsync(
            notification.To,
            notification.Subject,
            notification.Body,
            idempotencyKey,
            ct);

        if (!result.Success)
        {
            if (result.IsTransient)
                throw new TransientMailException(result.Error);

            notification.Status = NotificationStatus.Failed;
            notification.LastErrorCode = result.ErrorCode;
            await _db.SaveChangesAsync(ct);
            return;
        }

        notification.Status = NotificationStatus.Sent;
        notification.ProviderMessageId = result.MessageId;
        notification.SentAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(ct);

        _logger.LogInformation(
            "Notification {NotificationId} accepted by provider as {ProviderMessageId}",
            notification.Id,
            result.MessageId);
    }
}
```

Trong production, còn cần một atomic claim trước send để ngăn hai workers đồng thời xử lý cùng logical notification. Ví dụ state transition có điều kiện `Pending -> Processing` chỉ thành công cho một worker. Cần recovery cho `Processing` bị bỏ lại khi worker chết. Quan trọng nhất: claim chống concurrent execution nhưng không xóa crash window sau external side effect; provider idempotency hoặc reconciliation vẫn cần cho trường hợp đó.

Nếu enqueue bản thân nó xảy ra sau một business transaction quan trọng, có thể dùng transactional outbox để bảo đảm intent gửi notification không bị mất giữa DB commit và enqueue. Outbox giải quyết reliability của việc phát sinh công việc; nó không tự làm external email side effect exactly-once.

## Trade-offs

Provider idempotency là giải pháp mạnh nếu provider thực sự cam kết semantics và retention phù hợp. Atomic claim giảm duplicate concurrent workers nhưng tạo state-recovery requirement. Transactional outbox tăng reliability giữa database và queue nhưng thêm table, dispatcher và cleanup. Giữ DB transaction mở trong lúc gọi HTTP thường không biến hai hệ thống thành một atomic transaction và còn kéo dài lock/connection lifetime.

Nếu provider không hỗ trợ idempotency hoặc lookup bằng client ID, hệ thống thường phải thiết kế theo at-least-once processing và giảm duplicate bằng local dedupe, reconciliation, business identifiers và retry policy; không nên hứa “exactly once” khi không có primitive hỗ trợ từ external side effect.

## Cách kiểm thử

1. **Crash-window integration test:** provider fake ghi nhận success rồi worker throw trước DB save; retry phải reuse cùng idempotency key và provider fake chỉ tạo một logical delivery.
2. **Concurrency test:** chạy hai job cùng notification; chỉ một execution được atomic claim/send.
3. **Ambiguous-timeout test:** provider xử lý request nhưng client nhận timeout; retry cùng key không tạo duplicate.
4. **Permanent failure test:** invalid recipient không bị retry vô hạn và chuyển đúng trạng thái Failed/dead-letter policy.
5. **Recovery test:** worker chết khi trạng thái Processing; watchdog/retry có thể reclaim sau timeout mà vẫn giữ idempotency semantics.

## Quan sát trong production

Theo dõi job attempts, retry count, queue latency, Pending/Processing age, ambiguous provider outcomes, provider latency/error rate, duplicate/idempotency-hit count nếu provider cung cấp, failed/dead-letter count và reconciliation mismatches. Log correlation nên gồm notification ID, attempt number và provider message ID nhưng tránh raw sensitive content/recipient khi không cần thiết. Alert khi Processing age vượt ngưỡng hoặc retry rate tăng mạnh.

## Câu hỏi phỏng vấn mở rộng

1. Transactional outbox giải quyết phần nào của bài toán và phần nào nó không giải quyết?
2. Nếu provider không hỗ trợ idempotency key nhưng hỗ trợ query theo custom message ID, bạn thiết kế retry thế nào?
3. Vì sao một distributed lock quanh toàn bộ job vẫn không đảm bảo exactly-once external delivery?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge hôm nay cùng nhấn mạnh một nguyên tắc quan trọng: khi một workflow đi qua nhiều consistency/failure boundaries, code tuần tự nhìn có vẻ đúng vẫn có thể sai dưới concurrency hoặc partial failure. Cache-aside cần xem xét stampede và stale repopulation; background side effects cần xem xét retry cùng idempotency và ambiguous outcomes.

## Mẫu tư duy cần nhớ

- Vẽ timeline các thao tác concurrent thay vì chỉ review từng method độc lập.
- Thiết kế retry cùng idempotency; retry không phải là reliability nếu side effect không an toàn khi lặp lại.
- Phân biệt database transaction với atomicity xuyên external systems.
- Measure cache miss, retry và failure windows thay vì chỉ nhìn average latency.
- Xem observability và recovery state như một phần của design, không phải phần bổ sung sau cùng.
