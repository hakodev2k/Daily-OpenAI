# Câu 1 — EF Core Tracking và hành vi bất ngờ trong production

**Loại câu hỏi:** Internal mechanism
**Độ khó:** Senior
**Thời gian trả lời đề xuất:** 15 phút
**Kỹ năng được đánh giá:** EF Core, ORM internals, performance diagnosis

## Bối cảnh
Một API ASP.NET Core dùng EF Core để lấy danh sách Employee và cập nhật trạng thái. Sau khi tăng traffic, memory tăng và một số request trả dữ liệu cũ dù database đã thay đổi.

## Câu hỏi chính
Giải thích EF Core tracking hoạt động nội bộ như thế nào, vì sao có thể xảy ra hiện tượng trên, cách kiểm chứng và thiết kế lại.

## Câu hỏi làm rõ nên cân nhắc
- Query này có dùng AsNoTracking không?
- DbContext lifetime đang cấu hình thế nào?
- Entity có được giữ qua nhiều request không?
- Kích thước result và tần suất gọi API là bao nhiêu?

## Gợi ý tư duy
1. Xem xét Change Tracker và identity resolution.
2. Kiểm tra lifetime, query execution và memory.
3. Chọn tracking strategy dựa trên use case.

## Cấu trúc trả lời đề xuất
1. Clarify context.
2. Explain internal mechanism.
3. Analyze risks.
4. Compare solutions.
5. Explain testing and monitoring.

## Ý chính câu trả lời tốt
- Bắt buộc: hiểu DbContext, tracking, query lifecycle.
- Điểm cộng: phân tích memory, concurrency.
- Nâng cao: profiling và architecture decision.

## Hướng giải quyết tham khảo
Dùng tracking cho workflow cần update entity; dùng AsNoTracking cho read-only; tránh giữ DbContext quá lâu; đo bằng profiling, logs và metrics.

# Câu 2 — Thiết kế hệ thống xử lý background jobs cho SaaS

**Loại câu hỏi:** System Design
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 30 phút
**Kỹ năng được đánh giá:** Architecture, reliability, distributed processing

## Bối cảnh
Một hệ thống SaaS cần xử lý email notification, đồng bộ Microsoft Graph, tạo báo cáo và chạy các tác vụ định kỳ bằng Hangfire.

## Câu hỏi chính
Thiết kế kiến trúc xử lý background job có retry, idempotency, monitoring và failure recovery.

## Câu hỏi làm rõ nên cân nhắc
- Số lượng tenant và job mỗi ngày?
- Có yêu cầu ordering không?
- External API timeout thế nào?
- Có cần audit history không?

## Gợi ý tư duy
1. Bắt đầu từ yêu cầu reliability.
2. Phân biệt scheduling và execution.
3. Thiết kế retry cùng idempotency.

## Hướng giải quyết tham khảo
Có thể bắt đầu bằng modular monolith + Hangfire. Dùng job state, distributed lock, retry policy, audit table, metrics và structured logging. Chỉ tách service khi scale hoặc ownership yêu cầu.

# Câu 3 — Xây dựng AI Coding Review Agent an toàn

**Loại câu hỏi:** AI Engineering
**Độ khó:** Senior+
**Thời gian trả lời đề xuất:** 25 phút
**Kỹ năng được đánh giá:** Agent architecture, context engineering, evaluation

## Bối cảnh
Team muốn tạo AI agent review pull request C#/.NET, phát hiện bug, security issue và đề xuất cải thiện.

## Câu hỏi chính
Thiết kế agent workflow, context, tool permission, validation và evaluation strategy.

## Hướng giải quyết tham khảo
Agent không thay thế deterministic checks. Kết hợp static analysis, test execution, repository context, MCP tools, structured output, human approval và quality evaluation.

# Tổng kết hôm nay

## Kiến thức trọng tâm
- ORM behavior cần hiểu runtime không chỉ API.
- Background processing cần reliability trước scalability.
- AI agent cần workflow, validation và permission boundary.

## Mẫu tư duy cần nhớ
- Clarify before designing.
- Measure before optimizing.
- Design retries with idempotency.
- Validate AI output deterministically.
- Observability is part of design.
