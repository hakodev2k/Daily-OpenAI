# Câu 1 — Memory tăng liên tục dù object “đã hết scope”: LOH, Gen 2 GC và buffer lifetime thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** C#, .NET GC, LOH, allocations, `ArrayPool<T>`, ASP.NET Core, memory diagnostics, file/image processing, production performance

## Bối cảnh

Một ASP.NET Core API xử lý ảnh và PDF trước khi upload lên Azure Blob Storage.

Mỗi request thường đọc file 5–20 MB, transform dữ liệu rồi upload kết quả:

```csharp
public async Task UploadDocumentAsync(
    Stream input,
    BlobClient blob,
    CancellationToken cancellationToken)
{
    using var source = new MemoryStream();
    await input.CopyToAsync(source, cancellationToken);

    var bytes = source.ToArray();

    var transformed = await _processor.TransformAsync(
        bytes,
        cancellationToken);

    await using var output = new MemoryStream(transformed);

    await blob.UploadAsync(
        output,
        overwrite: true,
        cancellationToken);
}
```

Production chạy trên container có memory limit 1.5 GB. Bình thường traffic khoảng 10 requests/second, nhưng giờ cao điểm có thể có 80–120 requests đang xử lý đồng thời.

Telemetry cho thấy:

- working set tăng nhanh lên hơn 1 GB trong giờ cao điểm;
- managed heap cũng tăng nhưng không hoàn toàn bằng working set;
- Gen 2 GC tăng mạnh;
- latency p99 tăng đáng kể khi memory pressure cao;
- CPU không luôn đạt 100%;
- sau khi traffic giảm, memory không quay ngay về mức ban đầu;
- thỉnh thoảng container bị OOMKilled;
- code review không thấy static collection giữ references lâu dài;
- một developer cho rằng “method return rồi nên byte array phải được free ngay”;
- người khác đề xuất gọi `GC.Collect()` sau mỗi upload;
- một người khác muốn chuyển toàn bộ sang `ArrayPool<byte>` nhưng chưa xác định ownership/lifetime của buffer.

## Câu hỏi chính

Hãy giải thích vì sao application có thể giữ mức memory cao và chịu Gen 2/LOH pressure dù các local variables đã ra khỏi scope. Phân biệt object reachability, garbage collection, heap compaction, large-object allocation, `MemoryStream.ToArray()`, concurrent request amplification và process working set. Sau đó đề xuất cách xác minh nguyên nhân và redesign pipeline để giảm peak memory mà không dùng `GC.Collect()` như một “fix”.

## Câu hỏi làm rõ nên cân nhắc

1. `_processor.TransformAsync` trả về buffer mới hay transform in-place/streaming được?
2. File-size distribution thực tế là bao nhiêu ở p50/p95/p99, không chỉ average?
3. Có bao nhiêu copies của cùng payload tồn tại đồng thời qua `MemoryStream`, `ToArray()`, processor và upload?
4. Blob upload có thể stream trực tiếp từ transform pipeline hay bắt buộc cần toàn bộ output trong memory?
5. Container OOM dựa trên cgroup memory limit nào, và native memory/TLS/compression/library allocations chiếm bao nhiêu ngoài managed heap?

## Gợi ý tư duy

### Gợi ý 1

Một local variable hết scope chỉ có nghĩa reference có thể không còn được dùng; nó không đồng nghĩa runtime lập tức trả memory cho OS.

### Gợi ý 2

Đếm số **copies của payload × số requests concurrent** trước khi tìm một “memory leak”.

### Gợi ý 3

Nếu business flow bản chất là stream → transform → stream, giữ toàn bộ input và output thành nhiều `byte[]` lớn là một architectural choice, không chỉ là GC tuning problem.

## Cấu trúc trả lời đề xuất

1. Vẽ lifetime của từng allocation trong một request.
2. Giải thích reachability và thời điểm GC reclaim object.
3. Giải thích Gen 0/1/2 và large-object behavior ở mức cần thiết.
4. Tính peak memory theo concurrency.
5. Phân biệt managed heap với process working set.
6. Thu thập dump/counters/profile để xác minh.
7. Xác định các copies không cần thiết.
8. Thiết kế streaming/bounded-concurrency pipeline.
9. Đánh giá khi nào pooling có ích và ownership rules cần gì.
10. Load test với file-size distribution thật và memory limit production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Object chỉ có thể được reclaim khi không còn reachable và GC chạy; scope kết thúc không phải lệnh `free()`.
- `MemoryStream.ToArray()` tạo một array mới chứa copy dữ liệu; nếu processor lại tạo output mới thì cùng một logical payload có thể tồn tại thành nhiều buffers lớn.
- Các allocations lớn gây pressure lên Large Object Heap/Gen 2 collection behavior; high allocation rate và nhiều buffers sống đồng thời có thể làm full/Gen 2 collections tăng.
- Concurrent requests nhân peak memory. Ví dụ một request giữ input stream buffer + `byte[]` input + output buffer thì 100 requests có thể giữ nhiều lần tổng file size cùng lúc.
- Managed objects được reclaim không đồng nghĩa process working set lập tức giảm tương ứng; runtime có thể giữ segments/committed memory để tái sử dụng và OS accounting còn gồm native memory.
- `GC.Collect()` trong request path không phải fix mặc định; nó có thể tăng pause/CPU và chỉ che thiết kế allocation kém.
- Ưu tiên giảm copies, streaming và bounded concurrency trước khi GC tuning.

### Điểm cộng

- Dùng `dotnet-counters`, `dotnet-gcdump`, `dotnet-dump`, allocation profiler hoặc Application Insights/custom runtime metrics để phân biệt leak với allocation pressure.
- So sánh GC heap size, allocation rate, Gen 2 collections, LOH size, working set và request concurrency theo cùng timeline.
- Nếu `MemoryStream` phải dùng, cân nhắc tránh `ToArray()` bằng cách dùng underlying buffer an toàn khi contract cho phép, nhưng không assume mọi `MemoryStream` expose buffer.
- Với `ArrayPool<byte>`, buffer phải được `Return` đúng ownership, không return trước khi asynchronous consumer hoàn tất, và cần xử lý dữ liệu nhạy cảm nếu buffer có thể được reuse.
- Bounded concurrency có thể tốt hơn scale-out mù quáng khi mỗi request là memory-heavy.

### Senior+

- Phân biệt true leak (object graph vẫn reachable ngoài expected lifetime) với high retained heap/fragmentation/pooling/native allocations.
- Nhận ra pooling có thể **giữ memory lâu hơn** theo process lifetime dù giảm allocation/GC churn; pooling không đồng nghĩa working set thấp.
- Xem pinned buffers/native interop nếu library xử lý ảnh/PDF pin memory hoặc dùng unmanaged allocations.
- Thiết kế admission control theo payload size thay vì chỉ request count nếu 2 MB và 200 MB requests có cost rất khác nhau.
- Tách resource budget: request body limit, transform concurrency, temporary disk option, Blob streaming/chunking và cancellation.

## Hướng giải quyết tham khảo

Điểm đầu tiên là bỏ assumption “method return = memory được trả ngay”. .NET GC quản lý object theo reachability. Khi references biến mất, object trở thành eligible để collect, nhưng GC chỉ reclaim khi collection phù hợp xảy ra. Sau đó runtime có thể giữ heap segments để phục vụ allocations tương lai thay vì lập tức trả toàn bộ pages cho OS.

Ở code hiện tại, một request có thể giữ nhiều copies:

```text
input stream buffering
    ↓
MemoryStream internal buffer
    ↓ ToArray()
byte[] bytes        ← copy mới
    ↓ TransformAsync
byte[] transformed  ← có thể là copy mới khác
    ↓
MemoryStream wrapper cho upload
```

Nếu file trung bình 10 MB nhưng mỗi request có 20–30 MB payload-related managed memory sống cùng lúc, 100 concurrent requests đã tạo hàng GB theoretical pressure trước khi tính object overhead, framework buffers, TLS, compression, native image/PDF library memory và database/HTTP clients.

Tôi sẽ xác minh bằng telemetry thay vì đoán. Trong load reproduction, thu:

```text
GC heap size
allocation rate
Gen 0/1/2 collection count
LOH size
working set / private bytes
active requests
payload size histogram
transform duration
```

Nếu memory tăng cùng concurrency và sau GC object types chủ yếu là `System.Byte[]` với call stacks từ upload/transform pipeline, đây có thể là allocation-pressure design hơn là static-reference leak. Nếu dump cho thấy các arrays vẫn được giữ bởi cache/singleton/channel/task graph sau khi request kết thúc, khi đó mới đi theo leak path.

Thiết kế tốt hơn phụ thuộc processor. Nếu transform hỗ trợ stream:

```text
request stream
→ bounded transform stream/pipeline
→ Blob upload stream
```

thì tránh materialize toàn file. Nếu transform cần random access/toàn bộ file, có thể dùng temporary file hoặc pooled/rented buffers với kích thước giới hạn, nhưng cần cân bằng disk I/O và latency.

Tôi cũng giới hạn số transforms đồng thời:

```csharp
private readonly SemaphoreSlim _transformGate = new(initialCount: 8);

public async Task ProcessAsync(...)
{
    await _transformGate.WaitAsync(cancellationToken);
    try
    {
        await TransformAndUploadAsync(...);
    }
    finally
    {
        _transformGate.Release();
    }
}
```

Con số 8 phải lấy từ load test/memory budget, không phải magic number. Nếu workload có file size rất lệch, admission control theo estimated bytes tốt hơn một semaphore count cố định.

`ArrayPool<byte>` phù hợp khi algorithm thực sự cần reusable buffers. Nhưng tôi chỉ dùng nếu ownership rõ:

```csharp
var buffer = ArrayPool<byte>.Shared.Rent(requiredSize);
try
{
    await UseBufferAsync(buffer, cancellationToken);
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: containsSensitiveData);
}
```

Không được return buffer trong khi Blob SDK/processor vẫn giữ reference asynchronous. Pooling giảm allocations và GC churn nhưng có thể giữ large arrays trong pool, vì vậy success metric không phải “working set xuống bằng zero” mà là peak memory, GC pause, throughput và OOM risk giảm.

`GC.Collect()` sau mỗi request có thể ép full collections đúng lúc traffic cao, làm latency tệ hơn và không giải quyết việc 100 requests vẫn đồng thời giữ nhiều copies. Chỉ cân nhắc explicit collection trong các workload rất đặc biệt, có evidence và lifecycle rõ — không phải request-level web processing mặc định.

## Mẫu trả lời trong phỏng vấn

“Local variable hết scope không đồng nghĩa memory được free ngay. Object chỉ eligible khi không còn reachable, và GC quyết định khi nào collect. Với code này, `MemoryStream.ToArray()` tạo thêm một copy lớn, processor có thể tạo thêm output buffer; dưới 100 concurrent requests, peak memory tăng theo số copies × payload size.

Tôi sẽ đo GC heap, LOH, allocation rate, Gen 2 count, working set và lấy dump để xem `byte[]` đang được giữ bởi ai. Nếu chúng biến mất sau full GC nhưng peak vẫn rất cao, đó là allocation/concurrency pressure hơn là classic leak.

Fix chính là giảm materialization: stream input/transform/output nếu thư viện hỗ trợ, nếu không thì bounded concurrency và có thể dùng pooled buffers với ownership rõ. Tôi không gọi `GC.Collect()` sau mỗi upload vì nó chỉ ép pause mà không giảm số bytes đang live. Thành công phải được chứng minh bằng load test với file-size distribution thật dưới đúng container memory limit.”

## Câu hỏi đào sâu

1. Nếu `ArrayPool<byte>` giảm Gen 2 GC nhưng working set lại cao hơn trước, bạn có coi đó là regression không? Vì sao?
2. Nếu transform library bắt buộc cần toàn bộ 200 MB file trong memory, bạn thay đổi architecture/resource controls thế nào?
3. Làm sao phân biệt managed leak với native memory leak khi working set tăng nhưng GC heap gần như ổn định?

## Lỗi trả lời thường gặp

- Cho rằng object được free ngay khi method return.
- Gọi `GC.Collect()` như primary remediation.
- Dùng `ArrayPool` nhưng không xác định ownership/async lifetime.
- Chỉ nhìn working set và kết luận managed-memory leak.
- Không nhân memory cost theo concurrency và payload distribution.

## Thang điểm 0–10

- **0–2:** Chỉ nói “GC sẽ tự dọn” hoặc “tăng RAM”.
- **3–4:** Biết LOH/Gen 2 nhưng không liên hệ copies và concurrency.
- **5–6:** Giải thích đúng reachability, allocation pressure, diagnostics và giảm copies.
- **7–8:** Có streaming, bounded concurrency, pooling trade-offs và managed-vs-native diagnostics.
- **9–10:** Xây được memory budget, phân biệt leak/retention/pooling/native pressure và thiết kế pipeline theo resource economics thực tế.

# Câu 2 — Service Bus message bị xử lý hai lần dù handler chỉ chạy “một consumer”: lock expiry, settlement và idempotency

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, background processing, at-least-once delivery, message locks, retries, idempotency, external APIs, observability, failure recovery

## Bối cảnh

Một ASP.NET Core background worker nhận message từ Azure Service Bus queue để đồng bộ order sang một legacy ERP.

Message:

```json
{
  "messageId": "order-sync-7d7c...",
  "orderId": "7d7c...",
  "tenantId": "t-42",
  "operation": "CreateOrder"
}
```

Handler đơn giản hóa:

```csharp
public async Task HandleAsync(
    ServiceBusReceivedMessage message,
    ServiceBusReceiver receiver,
    CancellationToken cancellationToken)
{
    var command = message.Body.ToObjectFromJson<SyncOrderCommand>();

    var order = await _db.Orders
        .AsNoTracking()
        .SingleAsync(x => x.Id == command.OrderId, cancellationToken);

    var erpResult = await _erpClient.CreateOrderAsync(
        order,
        cancellationToken);

    await _db.OrderSyncLogs.AddAsync(
        new OrderSyncLog
        {
            OrderId = order.Id,
            ExternalReference = erpResult.Reference,
            CompletedAt = DateTime.UtcNow
        },
        cancellationToken);

    await _db.SaveChangesAsync(cancellationToken);

    await receiver.CompleteMessageAsync(
        message,
        cancellationToken);
}
```

Incident production:

- đa số messages xử lý 5–15 giây;
- một số orders lớn khiến ERP call mất 6–12 phút;
- trong incident window có network latency cao giữa worker và Azure;
- ERP đã tạo order thành công cho một số message;
- ngay sau đó worker log `ServiceBusLockLostException` khi settle message;
- vài phút sau cùng logical order được nhận lại với `DeliveryCount` tăng;
- ERP không hỗ trợ transaction với SQL Server;
- một số duplicate ERP orders đã được tạo;
- team đang dùng nhiều worker instances sau scale-out;
- một developer đề xuất “tăng lock duration thật lớn là xong”;
- người khác muốn đặt `MaxConcurrentCalls = 1` để bảo đảm một message chỉ chạy một lần;
- operations thấy backlog tăng mạnh nếu ERP chậm;
- hiện chưa có unique constraint/idempotency record theo logical operation.

Không được assume lock expiry là nguyên nhân duy nhất. Có thể còn retry, process crash, transient settlement failure, prefetch hoặc deployment overlap. Bạn phải điều tra bằng evidence.

## Câu hỏi chính

Hãy xử lý incident này theo flow **impact → stabilize → evidence → competing hypotheses → root cause → remediation → prevention**. Giải thích semantics của peek-lock/settlement và vì sao message có thể được redeliver sau khi external side effect đã thành công. Sau đó thiết kế consumer idempotent, lock-renewal/processing strategy, concurrency/backpressure và recovery path để duplicate delivery không tạo duplicate business effect.

## Câu hỏi làm rõ nên cân nhắc

1. Processor/receiver hiện cấu hình lock renewal, prefetch và concurrency thế nào?
2. ERP có hỗ trợ một stable client request ID/idempotency key hoặc lookup theo external order identity không?
3. `MessageId` có stable qua producer retries hay producer tạo ID mới mỗi attempt?
4. Worker có crash/redeploy trong incident window không, và settle failure xảy ra trước hay sau SQL commit?
5. Queue DLQ/retry policy và max delivery behavior hiện tại là gì?

## Gợi ý tư duy

### Gợi ý 1

Message lock bảo vệ quyền xử lý tạm thời; nó không biến handler thành exactly-once transaction.

### Gợi ý 2

Timeline quan trọng hơn exception name: external ERP success, local DB commit và Service Bus settlement là ba commit points khác nhau.

### Gợi ý 3

Thiết kế đúng phải vẫn an toàn nếu cùng logical message được giao lại nhiều lần.

## Cấu trúc trả lời đề xuất

1. Xác định business blast radius và duplicate side effects.
2. Stabilize concurrency/retry nếu đang khuếch đại incident.
3. Correlate message ID, delivery count, lock expiry, processor instance và ERP request.
4. Dựng timeline của các commit points.
5. Kiểm tra lock-renewal/prefetch/process-restart hypotheses.
6. Định nghĩa logical idempotency key.
7. Enforce idempotency bằng database/external API contract.
8. Thiết kế long-running processing và settlement.
9. Xử lý poison/unknown/ambiguous outcome.
10. Load/failure test và production telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Peek-lock delivery là at-least-once style processing; nếu message không được settle thành công trước khi lock không còn hợp lệ, message có thể được delivered lại.
- `MaxConcurrentCalls = 1` không tạo exactly-once. Process crash, lock expiry hoặc retry vẫn có thể redeliver.
- Tăng lock duration/renewal có thể giảm lock-loss probability nhưng không thay business idempotency requirement.
- External ERP side effect và Service Bus settlement không cùng transaction; ERP có thể success nhưng message completion fail.
- Consumer cần stable logical operation identity, ví dụ `(OrderId, Operation)` hoặc producer-generated operation ID, được persist/enforce unique.
- Duplicate delivery phải trở thành no-op hoặc return existing result, không tạo side effect thứ hai.
- Long-running work phải có cancellation, bounded concurrency và strategy khi processing time vượt expected message-lock window.

### Điểm cộng

- Nếu ERP hỗ trợ idempotency key, gửi cùng stable operation ID trên mọi retry/redelivery.
- Dùng unique constraint trên inbox/idempotency table để claim operation atomically.
- Phân biệt states như `Started`, `ExternalSucceeded`, `Completed`, `Unknown` để recovery có cơ sở.
- Nếu outcome của ERP call ambiguous do timeout, query ERP bằng operation ID trước khi gửi lại create request.
- Không prefetch quá nhiều long-running messages nếu lock timer/processing delay khiến message chờ lâu trước khi handler bắt đầu.

### Senior+

- Không tuyên bố distributed exactly-once nếu ERP không tham gia protocol/transaction chung.
- Nếu handler mất lock sau external success nhưng trước local durable state, cần external idempotency/lookup hoặc reconciliation; SQL inbox một mình chưa đủ.
- Có thể tách “receive message → persist work intent → settle nhanh” khỏi long-running ERP worker nếu durability model phù hợp, nhưng phải tránh mất/duplicate work giữa queue và local store bằng transaction/outbox-like design phù hợp.
- Backpressure dựa trên ERP capacity, không dựa chỉ trên Service Bus throughput.
- Theo dõi lock lost, delivery count distribution, processing duration vs lock budget, active concurrency, backlog age và ERP latency cùng dashboard.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng impact. Duplicate ERP order là data-correctness incident, nên trước hết xác định số orders có thể bị duplicate, ngăn consumer tạo thêm side effects nếu incident đang tiếp diễn, và phối hợp ERP/business để freeze hoặc reconcile affected records.

Sau đó dựng timeline cho từng message:

```text
T0  message received / lock acquired
T1  ERP create request sent
T2  ERP create success
T3  local SQL sync log committed
T4  CompleteMessage attempted
T5  settlement success OR lock lost/failure
T6  redelivery
```

Nếu T2 thành công nhưng T5 thất bại, redelivery là expected possibility trong at-least-once processing. Một lock không phải transaction across ERP + SQL + broker.

Tôi thu evidence:

- `MessageId`, correlation ID, `DeliveryCount`;
- enqueued time và processing start/end;
- locked-until timestamp nếu available trong telemetry;
- worker instance/process/version;
- Service Bus processor errors/lock-lost events;
- ERP request/response id và latency;
- SQL idempotency/sync-log records;
- deployment/restart/autoscale events.

Đồng thời kiểm tra processor configuration: auto-lock renewal, prefetch, concurrency và cancellation. Nếu message nằm trong prefetch buffer lâu hoặc processing duration vượt lock-renew capacity, lock loss dễ xảy ra. Nhưng đây là operational reliability layer, không phải correctness guarantee.

Correctness phải bắt đầu từ stable logical operation:

```text
OperationId = order-sync:{tenantId}:{orderId}:CreateOrder
```

Database có inbox/idempotency table:

```sql
CREATE UNIQUE INDEX UX_OrderSyncOperation_OperationId
ON OrderSyncOperations(OperationId);
```

Handler atomically tạo operation record. Nếu record `Completed`, redelivery trả no-op. Nếu `Started/Unknown`, logic recovery quyết định query ERP hay retry dựa trên external semantics.

Nếu ERP hỗ trợ client idempotency key:

```csharp
await _erpClient.CreateOrderAsync(
    order,
    idempotencyKey: operationId,
    cancellationToken);
```

thì retry/redelivery luôn dùng cùng key. Đây là bridge tốt nhất qua failure window “ERP success nhưng local/broker commit chưa xong”.

Nếu ERP **không** hỗ trợ idempotency nhưng có lookup theo merchant/external order ID, trước create cần kiểm tra/reconcile theo stable business identity. Nếu ERP không có cả idempotency lẫn reliable lookup, hệ thống không thể tự hứa exactly-once; những outcome ambiguous phải chuyển sang `Unknown/NeedsReconciliation` thay vì blind retry create.

Về lock, tôi cấu hình renewal phù hợp với **expected bounded processing time**, nhưng không để handler chạy vô hạn. ERP call cần timeout/request budget. Nếu có orders thật sự cần hàng chục phút, cân nhắc split workflow:

1. Service Bus consumer validate + persist durable work intent;
2. settle message sau khi intent đã durable;
3. worker riêng xử lý ERP với state machine/retries;
4. publish completion/failure qua outbox nếu cần.

Cách này giảm phụ thuộc vào một message lock kéo dài, nhưng thêm local durability/state-machine complexity. Chỉ làm khi long-running workload biện minh được.

`MaxConcurrentCalls = 1` chỉ giảm song song trong **một processor instance** và làm throughput/backlog tệ; nhiều instances vẫn tồn tại, và redelivery vẫn xảy ra. Concurrency nên được giới hạn theo ERP capacity, có backpressure và circuit breaker/timeout phù hợp.

Tests quan trọng:

- cùng message delivery 20 lần song song;
- process crash sau ERP success trước SQL commit;
- SQL commit success nhưng `CompleteMessage` fail;
- ERP timeout nhưng ERP thực sự đã create;
- lock lost/restart/deployment;
- backlog burst với slow ERP.

Success criterion là đúng **một logical ERP order**, dù physical message deliveries > 1.

## Mẫu trả lời trong phỏng vấn

“Service Bus lock không cho exactly-once; nó chỉ cấp quyền xử lý tạm thời. Nếu ERP đã tạo order nhưng `CompleteMessage` fail hoặc lock hết hạn, broker có thể redeliver. Vì vậy correctness phải giả định duplicate delivery.

Tôi sẽ correlate `MessageId`, `DeliveryCount`, locked-until, worker instance, ERP request và SQL commit để xác định lock loss, crash hay settlement failure. Immediate stabilization là giảm concurrency/retry nếu ERP đang overload và khoanh vùng duplicate records.

Permanent fix là stable `OperationId`, unique inbox/idempotency record và dùng cùng idempotency key với ERP nếu provider hỗ trợ. Nếu ERP outcome ambiguous, query/reconcile thay vì blind create lại. Lock renewal và processor tuning chỉ giảm xác suất redelivery; chúng không thay idempotency. Nếu processing thường xuyên kéo dài nhiều phút, tôi cân nhắc persist durable work rồi settle message sớm và xử lý bằng stateful worker riêng.”

## Câu hỏi đào sâu

1. Nếu ERP không hỗ trợ idempotency key và cũng không có lookup theo external ID, bạn sẽ thiết kế recovery cho timeout ambiguous như thế nào?
2. Nếu team đề xuất tăng auto-lock renewal lên hàng giờ để tránh duplicate, bạn phản biện những failure modes nào?
3. Nếu inbox row đã là `Started` nhưng worker trước có thể đã chết giữa ERP success và local update, consumer mới nên quyết định retry hay reconcile bằng evidence nào?

## Lỗi trả lời thường gặp

- Giảm `MaxConcurrentCalls` xuống 1 rồi coi duplicate đã được giải quyết.
- Tăng lock duration nhưng không có idempotency.
- Assume message handler và ERP call cùng transaction.
- Treat mọi timeout là “external call failed” rồi retry create.
- Không theo dõi `DeliveryCount`, lock-loss và worker-instance timeline.

## Thang điểm 0–10

- **0–2:** Nghĩ Service Bus queue tự bảo đảm exactly-once processing.
- **3–4:** Biết lock có thể expire nhưng chỉ tăng lock/concurrency setting.
- **5–6:** Có idempotency key/inbox và hiểu external side-effect boundary.
- **7–8:** Có recovery cho ambiguous outcome, lock telemetry, backpressure và failure tests.
- **9–10:** Thiết kế đầy đủ state machine, distributed failure windows, operational stabilization và end-to-end idempotent business invariant.

# Câu 3 — Thiết kế product page cho Optimizely CMS + commerce + search + CDN: composition ở đâu và cache đến mức nào?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 40–50 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, e-commerce integrations, Elasticsearch, Akamai/CDN, Redis/cache, ASP.NET Core, SEO, observability, failure isolation, composable architecture

## Bối cảnh

Một e-commerce website đang được tái kiến trúc theo hướng composable nhưng chưa muốn chuyển ngay sang microservices toàn diện.

Product Detail Page (PDP) hiện cần dữ liệu từ nhiều nguồn:

- **Optimizely CMS**: marketing copy, hero content, editorial blocks, SEO metadata;
- **Commerce/PIM API**: product attributes, price, variants, inventory summary;
- **Review provider**: rating/review summary;
- **Elasticsearch**: related products và search-derived recommendations;
- **Akamai CDN**: edge caching cho public website;
- **ASP.NET Core web application**: render server-side HTML vì SEO quan trọng.

Hiện tại mỗi PDP request thực hiện fan-out synchronously:

```text
Browser
  → ASP.NET Core origin
       → Optimizely
       → Commerce API
       → Review API
       → Elasticsearch
```

Symptoms trong production:

- p95 PDP khoảng 1.8–2.5 giây;
- review provider thỉnh thoảng timeout 3–5 giây;
- commerce API có burst latency khi promotion bắt đầu;
- Akamai hit ratio thấp vì response headers hiện gần như `no-cache`;
- editors muốn publish CMS content và preview gần real-time;
- price/inventory phải “khá tươi”, nhưng Product chưa định nghĩa chính xác freshness budget;
- review count có thể stale vài phút;
- related products có thể stale lâu hơn;
- security team không muốn private/account-specific data lọt vào CDN cache;
- SEO yêu cầu canonical URL, metadata và server-rendered product content ổn định;
- team chỉ có 6 backend/full-stack developers và operations khá nhỏ;
- một architect đề xuất tách ngay thành 8 microservices + event streaming;
- developer khác đề xuất cache toàn bộ HTML 24 giờ ở Akamai và purge mỗi lần bất kỳ dependency thay đổi.

## Câu hỏi chính

Hãy thiết kế kiến trúc PDP production-ready và giải thích **composition boundary**, ownership của từng loại dữ liệu, cache strategy theo freshness requirement, failure/degradation behavior và invalidation/event strategy. Bạn phải cân bằng SEO, editorial preview, giá/inventory freshness, third-party failures, CDN efficiency và complexity cost. Không được mặc định microservices, Redis hay event-driven architecture là bắt buộc.

## Câu hỏi làm rõ nên cân nhắc

1. Price/inventory freshness SLO thực sự là bao nhiêu: seconds, tens of seconds hay minutes?
2. PDP có personalized content, account price hoặc geo-specific pricing không?
3. CMS publish volume và campaign launch pattern có tạo purge storm không?
4. Commerce/PIM có webhook/event/change-feed đáng tin cậy hay chỉ có pull API?
5. Preview traffic có thể bypass CDN/cache hoàn toàn và route riêng cho editors không?

## Gợi ý tư duy

### Gợi ý 1

Không phải mọi field trên một page cần cùng TTL hoặc cùng consistency model.

### Gợi ý 2

“Cache whole page” và “không cache gì” đều là hai cực. Hãy tách stable content khỏi volatile commerce data.

### Gợi ý 3

Architecture tốt phải mô tả behavior khi **Review API**, **Elasticsearch** hoặc **Commerce API** chậm/không available — không chỉ happy path.

## Cấu trúc trả lời đề xuất

1. Làm rõ ownership và freshness/SLO từng field.
2. Xác định public vs personalized/security-sensitive content.
3. Chọn server-side composition boundary.
4. Thiết kế origin data access/read model.
5. Thiết kế CDN/browser/application cache theo lớp.
6. Xác định invalidation/purge/events.
7. Thiết kế degraded behavior per dependency.
8. Giữ CMS preview/editor experience riêng.
9. Thiết kế observability và deployment simplicity.
10. Nêu trigger nào mới biện minh cho service extraction phức tạp hơn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Xác định rõ source of truth: CMS owns editorial content; commerce/PIM owns commercial product data; review provider owns reviews; search index là derived read model, không phải authoritative price/inventory source.
- Không áp dụng một TTL duy nhất cho toàn PDP nếu các fields có freshness requirements khác nhau.
- Public cacheable HTML có thể tận dụng CDN, nhưng personalized/account-specific data phải tách hoặc đánh dấu private/no-store phù hợp.
- Third-party review/recommendation failure không nên kéo sập toàn PDP nếu business có thể degrade gracefully.
- Commerce/price/inventory failure cần behavior rõ theo business risk: stale-last-known, hide purchase action, hoặc fail closed — tùy requirement.
- Preview/editor path nên bypass hoặc use separate cache policy để editor thấy unpublished/new content chính xác.
- Invalidation phải có scope/versioning rõ; purge toàn site cho mỗi update có thể tốn kém và tạo origin stampede.

### Điểm cộng

- Dùng fragment/data-level cache khác TTL thay vì chỉ full-page cache.
- Có stale-while-revalidate hoặc last-known-good strategy nơi business cho phép.
- Cache key include locale/currency/market/device variant nếu content thực sự khác theo dimensions đó.
- Dùng CMS publish events/webhooks để invalidate editorial fragments; commerce events để invalidate product cache nếu upstream hỗ trợ đáng tin cậy.
- Có circuit breaker/timeout cho review/search, nhưng không retry fan-out vô hạn trên request path.

### Senior+

- Nhận ra full HTML edge caching khó khi price/inventory thay đổi nhanh; có thể cache shell/editorial HTML lâu hơn và hydrate volatile commerce fragment server-side/edge-side/client-side tùy SEO/UX/security trade-off.
- Với SEO-critical primary product info, server-side render core content; optional reviews/recommendations có thể defer nếu không ảnh hưởng crawl/content requirement.
- Dùng versioned cache keys/content version thay vì phụ thuộc hoàn toàn vào distributed purge cho mọi thay đổi.
- Cân nhắc stampede protection/single-flight cho hot product sau purge/campaign launch.
- Không tách thành nhiều deployable services nếu ownership/team scale/operational need chưa biện minh; modular composition trong một ASP.NET Core application có thể đủ.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng data ownership và freshness matrix, vì không thể chọn cache architecture trước khi biết field nào cần tươi đến mức nào.

Ví dụ giả định ban đầu:

| Data | Source of truth | Freshness giả định | Failure behavior |
|---|---|---:|---|
| Marketing blocks | Optimizely CMS | seconds–minutes after publish | last known content acceptable |
| SEO metadata | Optimizely CMS | seconds–minutes | last known acceptable |
| Product attributes | Commerce/PIM | minutes | stale briefly acceptable |
| Price | Commerce | tens of seconds hoặc stricter | business-dependent |
| Inventory | Commerce | seconds–tens of seconds | fail closed/hide buy if uncertain |
| Reviews | Review provider | minutes | hide/degrade section |
| Related products | Elasticsearch | minutes+ | omit section |

Nếu Product nói price phải real-time tuyệt đối, architecture khác rất nhiều so với “stale 30 giây chấp nhận được”. Vì vậy freshness budget là requirement, không phải implementation detail.

### 1. Composition boundary

Với team 6 người và chưa có independent ownership mạnh, tôi không tách 8 microservices chỉ vì có 8 dependencies. Một ASP.NET Core web/BFF layer có thể là page-composition boundary:

```text
Akamai
  → ASP.NET Core PDP composer
      → CMS adapter
      → Commerce adapter
      → Review adapter
      → Search adapter
```

Các adapters/modules có ownership contract rõ nhưng vẫn deploy trong một application nếu operational simplicity quan trọng. Sau này mới extract service khi có independent scale/deploy/team boundary thực sự.

### 2. Cache theo data volatility

Tôi tránh một cache policy duy nhất. Có thể dùng:

- CMS/editorial fragment cache: TTL dài hơn + invalidate khi publish;
- product attributes: medium TTL;
- price/inventory: rất ngắn hoặc no shared cache tùy SLO;
- reviews/search recommendations: vài phút hoặc longer;
- request-level coalescing/single-flight cho hot keys.

Redis chỉ cần khi multiple instances cần shared cache semantics hoặc memory/cost/eviction requirement biện minh. Nếu application nhỏ và data source đã đủ nhanh, in-memory cache + CDN có thể đơn giản hơn.

### 3. CDN strategy

Nếu PDP hoàn toàn public và price giống nhau cho mọi user/market key, Akamai có thể cache HTML với TTL ngắn và serve stale-while-revalidate nếu acceptable.

Nếu price/inventory thay đổi theo user/account, không được cache personalized HTML dưới public key. Khi đó tách:

```text
cacheable public/editorial shell
+ volatile commerce data
```

Volatile fragment có thể được composed server-side per request, fetched client-side sau server render, hoặc handled bằng edge capability nếu platform/team thực sự có expertise. Quyết định dựa SEO, Core Web Vitals, security và complexity.

SEO-critical fields như title, canonical URL, main description, structured data nên có server-rendered consistent source. Không nên để core crawled content phụ thuộc một client-only API nếu SEO requirement không cho phép.

### 4. Failure isolation

Mỗi dependency có timeout budget riêng. Ví dụ:

```text
Review API timeout → render PDP without reviews
Elasticsearch timeout → omit recommendations
CMS temporary failure → use cached last-known content if valid
Commerce timeout → decision theo business: show stale price with timestamp, disable purchase, hoặc fail request
```

Không được chọn stale commerce behavior nếu business chưa chấp nhận risk. Với inventory, thường an toàn hơn là disable checkout action khi không chắc, nhưng exact policy phải do requirement quyết định.

### 5. Publish/invalidation

CMS publish event nên invalidate đúng content/product/locale key, không purge toàn site. Commerce event cũng invalidate product-specific keys. Nếu event delivery có thể duplicate, invalidation phải idempotent.

Có thể dùng versioned key:

```text
pdp-content:{productId}:{locale}:cmsVersion
```

để publish tạo version mới thay vì phải purge mọi intermediate cache đồng bộ tuyệt đối.

Sau purge của một sản phẩm hot, dùng single-flight/distributed request coalescing để tránh hàng trăm origin requests cùng rebuild cache.

### 6. Preview

Editor preview đi path riêng:

```text
/preview/... → auth required → bypass CDN/public cache
```

Preview phải đọc draft/unpublished content từ CMS nhưng không được contaminate public cache. Cache key/path/header phải tránh việc draft content bị edge-cache public.

### 7. Observability

Tôi instrument:

- total PDP p50/p95/p99;
- dependency latency/error per CMS/commerce/review/search;
- CDN hit ratio và cache status;
- application cache hit/miss/eviction;
- stale-response count/age nếu dùng stale fallback;
- purge/invalidation latency;
- origin request rate sau campaign publish;
- Core Web Vitals/Lighthouse trend;
- SEO crawl/render smoke tests cho canonical/structured data.

Distributed trace phải cho thấy critical path, để team biết 2.5 giây đến từ commerce, review hay cache miss fan-out.

### 8. Khi nào mới tăng complexity

Tôi chỉ tách service/streaming infrastructure nếu có evidence:

- một domain cần scale/deploy độc lập;
- team ownership tách rõ;
- event-driven freshness thật sự cần;
- shared read model được nhiều channels dùng;
- current module boundaries gây release coupling đáng kể.

Không nên đưa Kafka/event mesh/microservices chỉ để sửa một PDP chậm.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn TTL trước khi làm rõ freshness từng field. CMS content, price, inventory, reviews và recommendations có volatility khác nhau, nên một full-page TTL 24 giờ hoặc no-cache toàn bộ đều không hợp lý.

Với team nhỏ, tôi giữ ASP.NET Core PDP composer làm boundary và tách adapters theo source of truth. Core SEO/editorial content render server-side. CMS fragments có thể cache lâu hơn và invalidate theo publish; reviews/search có thể stale vài phút và degrade nếu timeout; price/inventory có policy ngắn hơn hoặc fail closed tùy business SLO.

Akamai chỉ cache public variants. Personalized/account pricing không được rơi vào public key. Editor preview đi path authenticated riêng và bypass public cache. Tôi dùng scoped invalidation/versioned keys và stampede protection thay vì purge toàn site.

Tôi chỉ tách microservices khi có independent ownership, scale hoặc deployment need. Trước mắt success được đo bằng PDP p95/p99, CDN hit ratio, dependency latency, stale age, purge propagation và Core Web Vitals.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu price thay đổi phải hiển thị toàn cầu trong dưới 5 giây nhưng vẫn muốn CDN hit ratio >90%, bạn thay đổi composition/cache design thế nào?
2. Nếu architect insist mỗi dependency phải thành một microservice độc lập để “đúng composable”, bạn sẽ phản biện bằng những operational costs nào?
3. Nếu CMS publish event bị mất nhưng edge cache TTL là 30 phút, bạn thiết kế reconciliation/version checking thế nào để stale content không kéo dài ngoài SLO?

## Lỗi trả lời thường gặp

- Gắn một TTL cho toàn page mà không phân loại data volatility.
- Cache personalized price/account data ở public CDN.
- Tách microservices chỉ vì có nhiều external dependencies.
- Retry mọi dependency trong request path làm tail latency tệ hơn.
- Purge toàn bộ CDN mỗi khi một product/content block thay đổi.

## Thang điểm 0–10

- **0–2:** Chỉ nói “dùng Redis/CDN” mà không định nghĩa ownership/freshness.
- **3–4:** Có caching nhưng không phân biệt public/private, preview và failure behavior.
- **5–6:** Có composition boundary, per-data TTL, degradation và scoped invalidation.
- **7–8:** Cân bằng SEO, CDN, volatile commerce data, preview, stampede và observability.
- **9–10:** Đưa ra architecture có conditional reasoning rõ theo freshness/security/team scale, tránh complexity không cần thiết và có failure/reconciliation strategy production-ready.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Scope của local variable không quyết định lúc memory được reclaim; cần phân biệt object reachability, GC lifecycle, LOH/Gen 2 pressure và process working set.
- Với workload xử lý file lớn, peak memory thường đến từ **copies × concurrency × payload distribution**, không nhất thiết từ classic memory leak.
- `ArrayPool<T>` giảm allocation churn nhưng có ownership/security trade-offs và không bảo đảm working set luôn thấp.
- Azure Service Bus message lock/settlement không tạo exactly-once business processing; duplicate delivery phải được coi là expected failure mode.
- Idempotency phải bao phủ cả external side effect và ambiguous outcome, không chỉ database row local.
- CMS/e-commerce page architecture nên tách data ownership, freshness budget và failure policy thay vì áp một cache strategy cho toàn page.
- CDN, application cache và source-of-truth APIs là các consistency layers khác nhau; cache policy phải phản ánh security và business semantics.

## Mẫu tư duy cần nhớ

- **Tính resource cost theo concurrency, không chỉ theo một request.**
- **Phân biệt delivery guarantee với business-side-effect guarantee.**
- **Dựng timeline commit points trước khi thiết kế retry/idempotency.**
- **Xác định freshness và ownership trước khi chọn cache architecture.**
- **Chỉ tăng architecture complexity khi có requirement hoặc operational evidence biện minh.**
