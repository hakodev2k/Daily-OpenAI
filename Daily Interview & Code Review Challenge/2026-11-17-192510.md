# Code Review Challenge 1 — Authorization bị lệch giữa API và cache

**Chủ đề:** ASP.NET Core .NET 8, authorization, multi-tenant, HTTP caching  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Một API trả về cấu hình dashboard theo tenant, có cả các widget giới hạn theo role. Frontend React dùng JWT do Microsoft Entra ID cấp; gateway xác thực token và ASP.NET Core cũng có JWT authentication. Hệ thống chạy 4 App Service instances, dùng Redis shared cache. Một số người dùng báo nhìn thấy widget của phòng ban khác sau khi đổi tài khoản trong cùng trình duyệt. Quyền có thể bị thu hồi giữa hai lần request; yêu cầu hiện tại chưa xác định độ trễ thu hồi quyền chấp nhận được.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/dashboard")]
[Authorize]
public sealed class DashboardController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;
    private readonly ILogger<DashboardController> _logger;

    public DashboardController(
        AppDbContext db,
        IDistributedCache cache,
        ILogger<DashboardController> logger)
    {
        _db = db;
        _cache = cache;
        _logger = logger;
    }

    [HttpGet("{tenantId:guid}")]
    public async Task<IActionResult> Get(Guid tenantId)
    {
        var userId = User.FindFirst("oid")?.Value ?? "unknown";
        var role = Request.Headers["X-Role"].ToString();
        var key = $"dashboard:{tenantId}";
        var cached = await _cache.GetStringAsync(key);

        if (cached != null)
        {
            Response.Headers.CacheControl = "public,max-age=300";
            return Content(cached, "application/json");
        }

        var widgets = await _db.Widgets
            .Where(w => w.TenantId == tenantId &&
                        (w.RequiredRole == null || w.RequiredRole == role))
            .Select(w => new
            {
                w.Id,
                w.Title,
                w.DataEndpoint,
                w.RequiredRole
            })
            .ToListAsync();

        var json = JsonSerializer.Serialize(widgets);
        await _cache.SetStringAsync(
            key, json,
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            });

        _logger.LogInformation(
            "Dashboard loaded for {UserId} and {TenantId}", userId, tenantId);

        Response.Headers.CacheControl = "public,max-age=300";
        return Content(json, "application/json");
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Thiếu kiểm tra tenant membership

**Vấn đề:** Bất kỳ principal đã authentication có thể yêu cầu tenantId tùy ý.

**Tại sao xảy ra:** `[Authorize]` chỉ yêu cầu principal được xác thực; truy vấn dùng trực tiếp route parameter.

**Ảnh hưởng production:** Cross-tenant data exposure, kể cả qua cache.

**Cách sửa:** Kiểm tra quyền truy cập tenant từ authoritative membership store hoặc authorization handler trước khi đọc cache và truy vấn.

### [Critical] — Tin tưởng role từ header do client điều khiển

**Vấn đề:** `X-Role` có thể bị giả mạo.

**Tại sao xảy ra:** Header không phải nguồn role đáng tin nếu không có boundary xác thực riêng được thiết kế rõ.

**Ảnh hưởng production:** Escalation quyền truy cập widget.

**Cách sửa:** Dùng role/permission được xác minh từ identity và membership store; nếu gateway cung cấp header thì phải chứng minh trusted proxy boundary, loại bỏ header do client gửi và bảo vệ đường kết nối.

### [Critical] — Cache key không phân biệt authorization scope

**Vấn đề:** `dashboard:{tenantId}` dùng chung cho các role/user có kết quả khác nhau.

**Tại sao xảy ra:** Cache không phản ánh inputs của phép lọc.

**Ảnh hưởng production:** Người có quyền thấp nhận payload đã cache của người có quyền cao.

**Cách sửa:** Ưu tiên cache dữ liệu không nhạy theo tenant rồi lọc theo permission sau khi authorize; hoặc dùng key theo tenant + effective permission fingerprint + version và có invalidation rõ ràng.

### [High] — Public HTTP caching cho dữ liệu có phân quyền

**Vấn đề:** Response được đánh dấu `public,max-age=300`.

**Tại sao xảy ra:** Shared caches có thể lưu response; URL không phân biệt người dùng.

**Ảnh hưởng production:** Leakage qua proxy/CDN và dữ liệu cũ sau logout hoặc đổi tài khoản.

**Cách sửa:** `Cache-Control: private, no-store` cho response nhạy cảm; kiểm tra cả gateway/CDN configuration.

### [High] — Không có cơ chế thu hồi quyền và invalidation

**Vấn đề:** Cache có TTL 10 phút, không gắn version của membership/permission.

**Tại sao xảy ra:** Authorization và cache lifecycle độc lập.

**Ảnh hưởng production:** Quyền cũ tồn tại sau thay đổi policy.

**Cách sửa:** Xác định SLA revocation, luôn authorize trên nguồn đủ mới; dùng version/event invalidation nếu caching permission.

### [Medium] — Không truyền CancellationToken

**Vấn đề:** Cache và EF operations tiếp tục sau client disconnect.

**Tại sao xảy ra:** Không dùng `HttpContext.RequestAborted`.

**Ảnh hưởng production:** Tốn tài nguyên khi request bị hủy, tăng latency dưới load.

**Cách sửa:** Truyền token cho cache/EF calls.

### [Medium] — Cache stampede và dependency degradation chưa được xử lý

**Vấn đề:** Concurrent cache misses đều query DB; Redis outage có thể biến thành HTTP 500.

**Tại sao xảy ra:** Thiếu bounded fallback và điều tiết miss.

**Ảnh hưởng production:** DB load spike hoặc dashboard unavailable.

**Cách sửa:** Theo dõi miss rate, dùng short-lived request coalescing khi cần, fallback DB có giới hạn và timeout; không fail-open authorization.

### [Low] — Telemetry thiếu phân biệt kết quả và nguyên nhân

**Vấn đề:** Chỉ log request thành công, không có authorization-denied/cache-source metrics.

**Tại sao xảy ra:** Thiếu instrumentation cho boundary.

**Ảnh hưởng production:** Khó chứng minh lỗi đã hết.

**Cách sửa:** Structured metrics với outcome, cache hit/miss và tenant pseudonymous ID; tránh log token/payload.

## Phiên bản đề xuất

Giả định `ITenantAccessService` đọc membership và effective permissions từ nguồn tin cậy, có freshness đáp ứng SLA thu hồi quyền; `IWidgetCatalog` chỉ trả về widget của tenant, không cache response đã cá nhân hóa.

```csharp
public sealed record WidgetDto(Guid Id, string Title, string DataEndpoint);

public interface ITenantAccessService
{
    Task<IReadOnlySet<string>?> GetPermissionsAsync(
        ClaimsPrincipal principal, Guid tenantId, CancellationToken ct);
}

public interface IWidgetCatalog
{
    Task<IReadOnlyList<WidgetRecord>> GetTenantWidgetsAsync(
        Guid tenantId, CancellationToken ct);
}

public sealed record WidgetRecord(
    Guid Id, string Title, string DataEndpoint, string? RequiredPermission);

[ApiController]
[Route("api/dashboard")]
[Authorize]
public sealed class DashboardController : ControllerBase
{
    private readonly ITenantAccessService _access;
    private readonly IWidgetCatalog _catalog;

    public DashboardController(
        ITenantAccessService access, IWidgetCatalog catalog)
    {
        _access = access;
        _catalog = catalog;
    }

    [HttpGet("{tenantId:guid}")]
    public async Task<ActionResult<IReadOnlyList<WidgetDto>>> Get(
        Guid tenantId, CancellationToken ct)
    {
        Response.Headers.CacheControl = "private, no-store";
        var permissions = await _access.GetPermissionsAsync(
            User, tenantId, ct);

        if (permissions is null)
            return Forbid();

        var widgets = await _catalog.GetTenantWidgetsAsync(tenantId, ct);
        var result = widgets
            .Where(w => w.RequiredPermission is null ||
                        permissions.Contains(w.RequiredPermission))
            .Select(w => new WidgetDto(w.Id, w.Title, w.DataEndpoint))
            .ToArray();

        return Ok(result);
    }
}
```

`IWidgetCatalog` có thể dùng EF Core `AsNoTracking`, projection và tenant-scoped cache cho catalog **không chứa dữ liệu user-specific**; nếu `DataEndpoint` chứa secret hoặc privileged URL thì phải lọc thêm ở backend và authorize khi endpoint đó được gọi. Cấu hình JWT phải validate issuer, audience, signature và lifetime; tenant permission không được suy ra chỉ từ token nếu requirement yêu cầu revocation gần real-time.

## Giải thích thiết kế sau khi sửa

Authorization chạy trước retrieval; cache của catalog không quyết định quyền. Mỗi request có effective permissions từ trusted source. Endpoint dữ liệu phía sau widget vẫn phải authorize độc lập. Không dùng `Vary: Authorization` như giải pháp duy nhất cho shared cache.

## Trade-offs

Đọc membership mỗi request tăng database/identity load; có thể dùng short-lived permission cache gắn version nhưng phải chấp nhận và đo revocation lag. `no-store` làm giảm cache efficiency ở browser/CDN nhưng đơn giản hóa confidentiality. Nếu widget catalog lớn, nên lọc ở database sau authorization với permission predicate có kiểm soát, thay vì materialize toàn bộ.

## Cách kiểm thử

1. **Security integration:** User tenant A gọi tenant B nhận 403, kể cả khi B đã warm cache.
2. **Role matrix:** Hai user cùng tenant khác permission nhận đúng tập widget bất kể request order.
3. **Revocation:** Thu hồi permission rồi kiểm tra response theo SLA đã thống nhất.
4. **Cache/proxy:** Xác nhận `no-store`, không rò payload sau đổi tài khoản hoặc qua CDN.
5. **Failure-path/load:** Redis outage và concurrent misses không bypass authorization, đo p95 và DB load.

## Quan sát trong production

Application Insights traces cho authentication/authorization latency, catalog latency, cache hit/miss và 403 rate; Azure Monitor alert khi 403 bất thường hoặc dependency failure tăng. Gắn correlation ID xuyên gateway và API, không ghi JWT, raw claims hoặc dashboard payload. Kiểm tra CDN response headers và audit membership changes để đối chiếu incident.

## Câu hỏi phỏng vấn mở rộng

1. Nếu requirement là thu hồi quyền trong 5 giây, bạn thiết kế cache/version như thế nào?
2. Nếu widget catalog chứa hàng triệu records, thay đổi query và index ra sao?
3. Khi dùng service-to-service identity thay vì end-user JWT, boundary tenant authorization chuyển dịch thế nào?

# Code Review Challenge 2 — Rolling deployment làm mất tính tương thích của database schema

## Kết quả code review tham khảo

### [Critical] — Drop cột trước khi v1 ngừng chạy

**Vấn đề:** v1 vẫn đọc/ghi `customer_name` khi cột bị xóa.

**Tại sao xảy ra:** Migration destructive chạy trước rolling deployment.

**Ảnh hưởng production:** SQL errors và order failures trong lúc rollout hoặc rollback.

**Cách sửa:** Expand schema trước, giữ cột cũ đến khi tất cả consumers đã chuyển và rollback window kết thúc.

### [Critical] — Phép tách tên làm mất dữ liệu

**Vấn đề:** `split_part(..., 2)` bỏ qua các token sau token thứ hai; C# indexing cũng có thể ném exception.

**Tại sao xảy ra:** Mô hình first/last không đủ thông tin để biểu diễn mọi tên.

**Ảnh hưởng production:** Sai tên khách hàng, mất dữ liệu và request 500.

**Cách sửa:** Giữ `customer_name` canonical cho đến khi business xác nhận semantics; nếu cần cấu trúc tên, dùng optional fields và explicit validation, không tự suy đoán.

### [High] — Backfill toàn bảng trong một transaction

**Vấn đề:** Một UPDATE lớn cùng DDL tạo thời gian lock/transaction dài.

**Tại sao xảy ra:** Không giới hạn batch và không đánh giá lock profile.

**Ảnh hưởng production:** Blocking, WAL growth, replication lag, latency spike.

**Cách sửa:** Backfill theo batch có checkpoint, throttle và quan sát locks; tách DDL ngắn khỏi data migration.

### [High] — Rollback ứng dụng không rollback schema/data

**Vấn đề:** `kubectl rollout undo` chỉ đổi image.

**Tại sao xảy ra:** Pipeline giả định app rollback tương đương DB rollback.

**Ảnh hưởng production:** v1 vẫn lỗi, dữ liệu đã mất không phục hồi bằng rollout.

**Cách sửa:** Duy trì schema tương thích hai chiều trong rollback window; destructive cleanup sau khi hết khả năng rollback.

### [High] — Race giữa backfill và writes

**Vấn đề:** Old/new writers có thể tạo các cột lệch nhau.

**Tại sao xảy ra:** Không có write strategy và reconciliation.

**Ảnh hưởng production:** Tên không nhất quán tùy thời điểm ghi.

**Cách sửa:** Thiết kế dual-write hoặc DB synchronization có kiểm chứng, ưu tiên một source of truth, kiểm tra drift trước cutover.

### [Medium] — Default rỗng che giấu dữ liệu chưa migrate

**Vấn đề:** `NOT NULL DEFAULT ''` khiến record mới trông hợp lệ dù chưa có tên cấu trúc.

**Tại sao xảy ra:** Schema constraint không phản ánh business invariants.

**Ảnh hưởng production:** Silent data-quality failures.

**Cách sửa:** Bắt đầu nullable, đo completeness, thêm constraints sau khi đã xác nhận dữ liệu và write paths.

### [Medium] — Pipeline thiếu canary và data validation

**Vấn đề:** `rollout status` chỉ xác nhận deployment rollout, không chứng minh dữ liệu đúng.

**Tại sao xảy ra:** Thiếu readiness về nghiệp vụ và migration checks.

**Ảnh hưởng production:** Phát hiện lỗi muộn khi đã phục vụ traffic lớn.

**Cách sửa:** Canary/feature flag, data-quality gates, application metrics và manual stop criteria.

## Phiên bản đề xuất

Không thể sửa lossless bằng cách tách tên tùy tiện. Dưới đây là **expand phase** minh họa, giữ nguyên cột canonical; production cần bổ sung schema naming theo convention, migration ownership và kiểm thử compatibility.

```sql
-- Phase 1: additive migration; retain customer_name.
ALTER TABLE orders
    ADD COLUMN customer_first_name text NULL,
    ADD COLUMN customer_last_name text NULL;

-- Optional index only if justified by measured query patterns.
-- No destructive changes in this release.
```

```csharp
public sealed class Order
{
    public long Id { get; set; }
    public string CustomerName { get; set; } = "";
    public string? CustomerFirstName { get; set; }
    public string? CustomerLastName { get; set; }
}

public async Task<long> PlaceOrderAsync(
    CreateOrderRequest request, CancellationToken ct)
{
    if (string.IsNullOrWhiteSpace(request.CustomerName))
        throw new ArgumentException("CustomerName is required");

    var order = new Order
    {
        CustomerName = request.CustomerName.Trim(),
        CustomerFirstName = request.FirstName,
        CustomerLastName = request.LastName
    };

    _db.Orders.Add(order);
    await _db.SaveChangesAsync(ct);
    return order.Id;
}
```

Nếu request contract chưa có `FirstName`/`LastName`, thêm optional properties trong phiên bản API tương thích trước khi dùng đoạn code trên. Chỉ nhận structured names khi client thực sự cung cấp; không tự suy ra từ `CustomerName`.

**Deployment sequence đề xuất:**

1. Deploy additive schema và kiểm tra v1 hoạt động bình thường.
2. Deploy v2 ghi `CustomerName` canonical và optional structured fields; giữ đọc được dữ liệu v1.
3. Nếu business có nguồn structured names đáng tin, backfill theo batches có checkpoint, đo drift; không suy đoán dữ liệu còn thiếu.
4. Canary v2, theo dõi write errors và data invariants; rollback image khi cần mà không đụng schema.
5. Chỉ contract/drop cột sau khi tất cả writers/readers và rollback dependencies đã được chuyển, có backup/restore rehearsal và quyết định rõ ràng về dữ liệu.

## Giải thích thiết kế sau khi sửa

Schema mở rộng trước để cả v1 và v2 cùng chạy. Dữ liệu canonical không bị xóa; optional structured fields phản ánh đúng tính chưa đầy đủ của nguồn. Chuyển đổi dữ liệu và triển khai ứng dụng là hai hoạt động khác nhau, cần gates và observability riêng.

## Trade-offs

Giữ cột cũ và dual-write làm tăng chi phí lưu trữ, logic consistency và thời gian migration. Bù lại, rollback không yêu cầu khôi phục database. Nếu không có business requirement thật sự cho structured names, giữ một trường full name có thể là thiết kế đơn giản và an toàn hơn. Batch size và throttling cần đo thực tế, không mặc định một con số.

## Cách kiểm thử

1. **Compatibility integration:** v1 và v2 đồng thời đọc/ghi trên expanded schema.
2. **Data-quality:** Tên một từ, nhiều từ, Unicode, khoảng trắng, null/empty và tên quốc tế.
3. **Load/database:** Chạy batch backfill dưới traffic giả lập, đo locks, WAL, p95 và replication lag.
4. **Deployment:** Canary v2 rồi rollback image khi v1 còn hoạt động, xác nhận không có SQL error.
5. **Failure-path:** Kill backfill giữa chừng, resume không ghi đè dữ liệu mới và không mất records.

## Quan sát trong production

Theo dõi PostgreSQL `pg_stat_activity`, lock waits, deadlocks, WAL/replication lag, transaction duration; Application Insights cho order-write failure rate, p95/p99, DB dependency errors; Kubernetes rollout/restarts/readiness. Dashboard data-quality gồm tỷ lệ structured names có nguồn hợp lệ và số records mismatch. Alert và pause rollout khi write errors hoặc lock waits vượt ngưỡng SLO đã xác định.

## Câu hỏi phỏng vấn mở rộng

1. Nếu phải loại bỏ `customer_name` sau 30 ngày, bạn chứng minh mọi consumer đã migrate như thế nào?
2. Nếu backfill chạy nhiều giờ trong khi writes liên tục, thiết kế reconciliation và checkpoint ra sao?
3. Khi PostgreSQL schema migration cần tạo index lớn, bạn chọn migration strategy nào để hạn chế downtime?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Authorization phải gắn với resource và nguồn quyền đáng tin; cache không được làm mất isolation. Database migration khi rolling deployment là bài toán tương thích giữa nhiều phiên bản, không chỉ là chạy SQL thành công. Cả hai trường hợp cần kiểm thử failure path và telemetry chứng minh invariants.

## Mẫu tư duy cần nhớ

1. Xác định trust boundary trước khi dùng claims, headers và route parameters.
2. Kiểm tra mọi cache key theo inputs ảnh hưởng đến kết quả và quyền.
3. Thiết kế rollback trước khi thực hiện destructive migration.
4. Giữ dữ liệu canonical khi phép chuyển đổi không thể đảo ngược.
5. Đo lỗi và tính nhất quán dưới concurrency, không chỉ happy path.
