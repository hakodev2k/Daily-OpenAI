# Câu 1 — API export tăng memory dù mọi object “cuối cùng cũng được GC”

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C# runtime, Garbage Collector, LOH, allocation, ASP.NET Core, serialization, streaming, performance diagnostics

## Bối cảnh

Một ASP.NET Core API trên .NET 8 cung cấp endpoint export dữ liệu giao dịch. Mỗi request thường trả 5–20 MB JSON, nhưng đôi lúc lên tới 150 MB. Sau khi feature được mở cho nhiều khách hàng, memory của process tăng theo từng đợt export. Sau một thời gian memory có giảm nhưng RSS không luôn trở về mức ban đầu; p99 latency cũng tăng trong các đợt export đồng thời.

Implementation hiện tại query toàn bộ rows vào `List<TransactionDto>`, serialize thành một `string`, chuyển tiếp sang UTF-8 `byte[]`, rồi trả `File(...)`. Team kết luận “không leak vì GC sẽ thu hồi” và đề xuất gọi `GC.Collect()` sau mỗi export.

Chưa có allocation profile, GC pause metrics, heap dump, số request export đồng thời, kích thước object thực tế hoặc evidence về memory leak.

## Câu hỏi chính

Hãy giải thích những allocation/lifetime transitions có thể xảy ra trong flow này, tại sao large temporary objects vẫn có thể gây production pressure dù cuối cùng collectible, vì sao RSS không giảm ngay không chứng minh memory leak, và bạn sẽ xác minh nguyên nhân trước khi thiết kế lại endpoint như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrency của export là bao nhiêu và request có bị giới hạn kích thước/số rows không?
2. DTO graph có chứa strings/arrays lớn hoặc duplicated data không?
3. Response có bắt buộc phải biết toàn bộ content trước khi gửi hay có thể stream/chunk?
4. GC metrics cho Gen 2, LOH, allocation rate và pause time thay đổi thế nào trong incident?
5. Memory có tiếp tục tăng qua nhiều chu kỳ workload-idle hay đạt plateau và được runtime giữ lại để tái sử dụng?

## Gợi ý tư duy

### Gợi ý 1

Đếm số representation đồng thời của cùng dữ liệu: entity/DTO collection, JSON text, UTF-8 buffer và response buffering nếu có.

### Gợi ý 2

Phân biệt **managed heap live size**, **committed memory**, **process RSS** và một leak thực sự. Chúng liên quan nhưng không đồng nghĩa.

### Gợi ý 3

`GC.Collect()` thay đổi thời điểm collection; nó không loại bỏ nguyên nhân allocation amplification và có thể làm latency tệ hơn.

## Cấu trúc trả lời đề xuất

1. Clarify workload và response semantics.
2. Vẽ allocation/lifetime path của một request.
3. Giải thích generational GC/large-object pressure ở mức thực dụng.
4. Phân biệt leak với transient/retained heap capacity.
5. Thu thập allocation/GC/process evidence.
6. Xác định bottleneck trước khi tối ưu.
7. Đề xuất streaming/batching hoặc giới hạn phù hợp.
8. Test concurrency/load và failure path.
9. Monitor memory, GC và latency sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận leak chỉ từ RSS; phải xem live managed objects, allocation rate, GC behavior và retention roots.
- Flow hiện tại có thể giữ nhiều representation lớn của cùng payload cùng lúc.
- Large temporary allocations có thể tăng GC pressure, peak memory và latency dù sau đó collectible.
- `GC.Collect()` per request không phải default fix; forced full collections có thể tăng pause/CPU và che thiết kế allocation kém.
- Cần profile trước: allocation flame/call stacks, heap snapshots/dumps khi phù hợp, GC counters, request size/concurrency và p95/p99.
- Nếu response semantics cho phép, streaming JSON/file output hoặc paging/batching có thể giảm peak live set vì không cần materialize toàn bộ payload.

### Điểm cộng

- Nhận ra một `string` JSON lớn và UTF-8 `byte[]` tạo các buffers khác nhau; serialization pipeline cần được kiểm tra cụ thể thay vì suy đoán.
- Phân biệt memory pressure với memory leak: leak cần evidence rằng objects không còn cần thiết vẫn bị giữ reachable.
- Backpressure/concurrency limit cho export có thể cần thiết ngay cả khi mỗi request được tối ưu.
- Cancellation khi client disconnect phải propagate để tránh tiếp tục query/serialize dữ liệu không còn người nhận.
- Nếu export rất lớn, asynchronous export-to-Blob + download có thể phù hợp hơn synchronous HTTP, nhưng chỉ khi UX/business requirement chấp nhận.

### Senior+

- Đánh giá trade-off streaming: response đã bắt đầu thì khả năng đổi status/error semantics bị hạn chế; transaction consistency và partial response cần thiết kế.
- Không tối ưu chỉ một tầng: EF Core materialization, serialization, buffering, compression và network đều có thể góp phần vào allocation/latency.
- Thiết kế capacity guard theo concurrent bytes/work units thay vì chỉ request count nếu payload variance rất lớn.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng `GC.Collect()`. Trước tiên tôi dựng allocation path thực tế. Nếu query materialize 100 MB DTO, serializer tạo thêm JSON `string`, sau đó encoding tạo `byte[]`, peak live memory của một request có thể lớn hơn payload cuối nhiều lần. Với nhiều request đồng thời, peak memory tăng nhanh dù từng object cuối cùng collectible.

Tôi thu thập `dotnet-counters`/runtime metrics hoặc telemetry tương đương cho allocation rate, GC heap size, Gen 2 collections, LOH size nếu metric/tool hỗ trợ, GC pause/time-in-GC và process working set. Khi cần, allocation profile/heap dump cho biết loại object nào chiếm memory và retention path nào giữ chúng. Tôi correlate với export size, concurrency và p99.

Nếu live heap giảm sau workload nhưng RSS không giảm tương ứng, điều đó chưa đủ để gọi là leak: runtime/process có thể giữ committed/reserved memory để tái sử dụng. Ngược lại, nếu heap snapshots qua nhiều chu kỳ cho thấy cùng object graph tăng và vẫn reachable từ cache/static/event handler hoặc long-lived scope, lúc đó mới có evidence retention leak.

Nếu requirement cho phép stream, tôi sẽ tránh `List -> string -> byte[]` toàn bộ. Có thể query theo bounded batches hoặc async enumeration phù hợp, serialize trực tiếp ra response stream bằng API hỗ trợ streaming. Nhưng phải kiểm tra database reader lifetime, cancellation, partial-response semantics và không giữ một transaction dài vô lý. Với export hàng trăm MB, một background export tạo file vào Azure Blob Storage rồi trả trạng thái/download URL có thể cho operational isolation tốt hơn nếu business chấp nhận asynchronous UX.

Tôi cũng đặt giới hạn hợp lý: max rows/date range, bounded concurrent exports hoặc queue. Load test phải dùng distribution thật của payload, không chỉ 1 MB happy path. Theo dõi peak working set, managed heap, allocation bytes/sec, GC pauses, export duration, aborted exports và p95/p99 trước/sau.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là leak và cũng không gọi `GC.Collect()`. Flow hiện tại có thể đồng thời giữ list DTO, JSON string và UTF-8 byte array, nên một response 150 MB có thể tạo peak live set lớn hơn nhiều; concurrency sẽ nhân áp lực đó lên.

Tôi sẽ đo allocation rate, managed heap, Gen 2/GC pause, process working set và profile object types/retention roots, rồi correlate với payload size và concurrency. RSS không giảm ngay sau GC chưa chứng minh leak; leak cần evidence object không còn cần nhưng vẫn reachable.

Nếu bottleneck đúng là materialization/buffering, tôi ưu tiên streaming hoặc bounded batching để tránh giữ toàn payload, propagate cancellation và giới hạn concurrent exports. Với export cực lớn có thể chuyển sang background export + Blob nếu UX cho phép. Sau đó load test theo payload distribution thật và theo dõi memory, GC và p99 thay vì chỉ kiểm tra endpoint còn trả 200.”

## Câu hỏi đào sâu

1. Nếu streaming làm peak memory giảm mạnh nhưng request giữ DB connection trong 8 phút, bạn thay đổi thiết kế thế nào?
2. Nếu heap dump cho thấy phần lớn memory là collectible nhưng RSS vẫn cao ổn định, bạn có restart process định kỳ không? Vì sao?
3. Nếu Product yêu cầu export phải synchronous và không giới hạn rows, bạn sẽ bảo vệ capacity thế nào?

## Lỗi trả lời thường gặp

- Gọi mọi RSS growth là memory leak.
- Ép `GC.Collect()` sau mỗi request mà không profile.
- Chỉ tối ưu serializer nhưng vẫn materialize toàn bộ dataset.
- Streaming nhưng bỏ qua cancellation, partial response và DB connection lifetime.
- Load test payload nhỏ, không mô phỏng concurrency và size distribution production.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng RAM hoặc `GC.Collect()`.
- **3–4:** Biết GC/LOH nhưng không có evidence plan.
- **5–6:** Phân tích allocation pipeline, profile đúng và đề xuất giảm buffering.
- **7–8:** Có streaming/backpressure/cancellation/load-test/telemetry trade-offs.
- **9–10:** Phân biệt chính xác retention leak, managed heap và process memory; thiết kế capacity-safe export theo requirements.

# Câu 2 — Kubernetes Pods restart liên tục sau release nhưng health checks đều “đúng”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, liveness/readiness, resources, deployment, Azure dependencies, observability, incident investigation

## Bối cảnh

Một ASP.NET Core API trước đây chạy ổn trên Azure App Service vừa được chuyển thử nghiệm sang Kubernetes. Deployment có 8 replicas. Sau release mới, một số Pods chuyển `Ready -> NotReady`, rồi restart. Trong khoảng 20 phút error rate tăng, rollout không hoàn thành và một số requests timeout.

Thông tin ban đầu:

- liveness và readiness đều gọi `/health` mỗi 10 giây;
- `/health` kiểm tra SQL Server, Redis và một external identity endpoint;
- container có memory limit;
- application log có khoảng trống ở vài Pods trước restart;
- SQL và Redis có latency tăng nhẹ nhưng không outage;
- release thêm một in-memory cache warm-up khi startup.

Team đề xuất tăng `failureThreshold`, memory limit và restart toàn Deployment. Chưa có `kubectl describe`/termination reason, container memory working set, probe latency, OOM evidence, startup duration hoặc dependency trace đầy đủ.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào để phân biệt OOM kill, failed liveness, failed readiness, startup/warm-up regression và dependency degradation? Sau khi ổn định, bạn sẽ thiết kế health probes và resource behavior ra sao để một dependency chậm không tạo restart cascade?

## Câu hỏi làm rõ nên cân nhắc

1. Container termination reason/exit code và Pod events nói gì ở từng restart?
2. Liveness failure hay process termination xảy ra trước; readiness bắt đầu fail ở thời điểm nào?
3. `/health` có timeout bao lâu và mỗi dependency check thực hiện network call thật ở mọi probe không?
4. Memory request/limit, working set và warm-up allocation peak là bao nhiêu?
5. Có startup probe hoặc readiness gate nào ngăn traffic trước khi warm-up hoàn tất không?

## Gợi ý tư duy

### Gợi ý 1

`NotReady` và `Restarted` là hai hiện tượng khác nhau. Xây timeline để biết cái nào gây cái nào.

### Gợi ý 2

Liveness trả lời câu hỏi “process này cần restart không?”; external dependency tạm chậm không nhất thiết đồng nghĩa process hỏng không thể tự hồi phục.

### Gợi ý 3

Resource limit, startup allocation và probes có thể tương tác: một warm-up chậm hoặc tốn memory có thể bị probe/restart loop làm tệ hơn.

## Cấu trúc trả lời đề xuất

1. Xác định impact/blast radius và pause rollout.
2. Stabilize bằng rollback/canary/drain có kiểm soát.
3. Dựng timeline per Pod.
4. Thu thập Pod events, termination reason, probe failures và resource metrics.
5. So sánh OOM/probe/startup/dependency hypotheses.
6. Verify bằng reproduction/canary.
7. Sửa probe semantics và startup behavior.
8. Right-size resources dựa trên measurement.
9. Test failure injection/rolling deployment.
10. Monitor restart/readiness/resource/dependency signals.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Pause rollout và tránh restart toàn bộ Deployment trước khi capture evidence.
- Kiểm tra Pod/container termination reason, previous logs, events và probe failures; không suy ra OOM chỉ vì có memory limit.
- Readiness failure nên loại Pod khỏi traffic; liveness failure có thể khiến container restart, vì vậy hai probe không nên mặc định có cùng dependency semantics.
- External SQL/Redis/identity degradation không nhất thiết là lý do restart process; liveness quá phụ thuộc external services có thể tạo restart cascade.
- Startup warm-up phải được đo; nếu application cần thời gian khởi động, startup/readiness semantics cần phản ánh điều đó.
- Tăng memory limit chỉ hợp lý sau khi biết working set/peak và nguyên nhân; nó không sửa leak hoặc unbounded cache.

### Điểm cộng

- Health endpoint cho liveness thường chỉ kiểm tra khả năng process tự phục vụ/recover ở mức nội bộ; readiness có thể xét critical dependencies nhưng cần cân nhắc fail-open/fail-closed theo capacity và dependency semantics.
- Nếu mọi replicas cùng fail readiness vì shared dependency chậm, toàn service có thể mất endpoints; cần thiết kế degradation/circuit/bounded dependency behavior.
- Warm-up có thể lazy/bounded/background tùy requirement thay vì bắt startup load toàn dataset.
- Resource requests ảnh hưởng scheduling/capacity; limits ảnh hưởng runtime behavior, nên right-sizing phải dùng production/load evidence.
- Rolling deployment cần `maxUnavailable`/capacity strategy phù hợp và health gates có ý nghĩa.

### Senior+

- Phân biệt “restart giúp hồi phục process-corrupt state” với “restart khuếch đại shared dependency outage”.
- Thiết kế probe endpoints rẻ, bounded và observable; không biến probes thành high-frequency synthetic load lên dependencies.
- Có canary/failure-injection tests cho dependency latency, OOM pressure và slow startup.

## Hướng giải quyết tham khảo

Tôi pause rollout trước. Nếu phiên bản cũ còn healthy và rollback an toàn, giữ capacity bằng rollback/canary thay vì restart đồng loạt. Sau đó dựng timeline từng Pod: readiness transitions, liveness failures, restart timestamp, termination reason/exit code, Kubernetes events, previous container logs, memory/CPU và dependency latency.

Nếu termination reason cho thấy OOM, tôi kiểm tra peak working set quanh warm-up và cache growth. Tăng limit có thể là mitigation ngắn hạn nếu workload hợp lệ và node capacity đủ, nhưng root fix phải xử lý allocation/cache bound. Nếu events cho thấy liveness timeout/failure trước restart, tôi xem `/health` implementation: việc gọi SQL, Redis và external identity ở liveness khiến shared dependency latency có thể yêu cầu Kubernetes giết một process vốn vẫn có thể hồi phục.

Tôi thường tách semantics: liveness là cheap internal signal cho process deadlock/unrecoverable state; readiness xác định Pod có nên nhận traffic. Dependency checks chỉ đưa vào readiness khi dependency thực sự cần để phục vụ request và failure policy đã được cân nhắc. Nếu identity provider chậm nhưng cached token validation vẫn hoạt động, fail readiness toàn Pod có thể sai. Nếu SQL là bắt buộc cho mọi request, readiness fail có thể đúng, nhưng phải xem cluster-level capacity và tránh probe storm.

Nếu startup warm-up cần 90 giây, dùng startup/readiness behavior phù hợp để Pod không bị liveness kill trước khi khởi động xong. Tốt hơn nữa, đánh giá liệu warm-up có cần synchronous/unbounded hay có thể bounded/lazy.

Sau fix, tôi chạy canary và inject dependency latency, test slow startup, memory pressure và rolling deployment. Dashboard theo restart count/reason, readiness transitions, probe latency, container working set vs limit, startup duration, request p95/p99 và dependency telemetry. Alert trên restart loop và unavailable replicas thay vì chỉ CPU.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ pause rollout và không restart toàn bộ trước khi lấy evidence. Tôi cần termination reason, Pod events, previous logs, probe failures và memory timeline để biết restart do OOM, liveness hay process exit. `NotReady` không tự đồng nghĩa restart.

Điểm đáng nghi là liveness và readiness cùng gọi endpoint kiểm tra ba external dependencies. Nếu identity hoặc SQL chậm, liveness có thể fail và Kubernetes restart một process vẫn có khả năng hồi phục, tạo cascade. Tôi sẽ tách liveness thành cheap internal health, readiness theo khả năng nhận traffic và dùng startup semantics cho warm-up nếu cần.

Memory limit cũng phải đo: nếu warm-up tạo peak hợp lệ thì right-size hoặc redesign warm-up; nếu cache unbounded thì tăng limit chỉ trì hoãn lỗi. Tôi verify bằng canary với dependency latency/memory/slow-start tests và monitor restart reasons, readiness, working set, startup duration và request/dependency latency.”

## Câu hỏi đào sâu

1. Nếu SQL outage làm mọi request business đều vô dụng, bạn có đưa SQL vào readiness không? Điều gì có thể khiến quyết định đó vẫn nguy hiểm?
2. Nếu container thực sự OOM nhưng chỉ trong warm-up 30 giây, tăng memory limit có phải giải pháp hợp lệ không?
3. Team muốn liveness gọi tất cả dependencies để “phát hiện lỗi sớm hơn”. Bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Restart Deployment ngay và mất evidence.
- Coi `NotReady` là bằng chứng process crash.
- Tăng `failureThreshold` mà không biết probe nào đang fail và vì sao.
- Dùng cùng một deep dependency check cho liveness/readiness mà không xét semantics.
- Tăng memory limit nhưng không đo warm-up/cache/allocation behavior.

## Thang điểm 0–10

- **0–2:** Chỉ restart hoặc tăng limits.
- **3–4:** Biết xem Pod logs/events nhưng không tách probe/resource hypotheses.
- **5–6:** Điều tra evidence-driven và sửa probe semantics hợp lý.
- **7–8:** Có stabilization, canary, resource sizing, failure tests và telemetry.
- **9–10:** Phân tích cascade behavior, capacity, startup/dependency semantics và operational trade-offs sâu.

# Câu 3 — Hiện đại hóa .NET Framework 4.5 mà không biến migration thành rewrite nhiều năm

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, ASP.NET, architecture, SQL Server, IIS, CI/CD, compatibility, testing, rollout, rollback, technical debt, engineering process

## Bối cảnh

Một internal approval platform đã chạy hơn 8 năm trên .NET Framework 4.5, ASP.NET MVC, IIS và SQL Server. Hệ thống có khoảng 35 modules, nhiều stored procedures, jQuery UI, một số scheduled jobs chạy trong web application và integrations với HR/CRM qua HTTP/file exchange.

Business muốn chuyển sang modern .NET để giảm security/maintenance risk và dễ tuyển người hơn, nhưng không chấp nhận freeze feature development 12 tháng. Team 7 developers vẫn phải release hàng tháng. Test automation hiện ít; một số business rules chỉ tồn tại trong code cũ/stored procedures. Database được dùng chung bởi nhiều modules.

Có ba đề xuất:

1. rewrite toàn bộ sang .NET 10 + React + microservices;
2. nâng từng phần lên modern .NET nhưng giữ modular monolith/database trong giai đoạn đầu;
3. giữ nguyên application, chỉ containerize lên Kubernetes để “modernize infrastructure”.

Chưa có inventory dependency compatibility, module coupling, traffic, deployment pain points hoặc test coverage đáng tin cậy.

## Câu hỏi chính

Bạn sẽ xây modernization strategy như thế nào để giảm risk mà vẫn tiếp tục delivery? Hãy trình bày cách inventory dependencies/boundaries, chọn migration seams, xử lý shared database và scheduled jobs, xây safety net testing, rollout/rollback, và tiêu chí quyết định phần nào nên refactor, replace hay giữ nguyên. Hãy đánh giá cả ba đề xuất thay vì mặc định chọn công nghệ mới nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Những business capabilities nào thay đổi thường xuyên và module nào ổn định nhưng khó hiểu/rủi ro cao?
2. Dependency/package nào khóa hệ thống vào .NET Framework/Windows/IIS?
3. Database coupling giữa modules ở mức tables, stored procedures, cross-module transactions hay reporting reads?
4. Current deployment incidents, downtime/SLO và rollback process ra sao?
5. Có thể route một subset endpoints/users sang implementation mới để strangler/canary không?

## Gợi ý tư duy

### Gợi ý 1

Modernization là bài toán risk/feedback loop, không phải bài toán đổi framework version một lần.

### Gợi ý 2

Trước khi tách service, hãy tìm dependency direction, data ownership và transaction boundaries. Shared database có thể làm “microservices” chỉ trở thành distributed code với coupling cũ.

### Gợi ý 3

Test safety net không nhất thiết bắt đầu bằng unit-test toàn bộ legacy code; characterization/integration/E2E ở critical flows có thể cho feedback nhanh hơn.

## Cấu trúc trả lời đề xuất

1. Inventory architecture/dependencies/business criticality.
2. Baseline production behavior và migration goals/SLO.
3. Xác định seams/bounded migration slices.
4. Tạo test/observability safety net.
5. Chọn target hosting/runtime theo constraint thực.
6. Migrate incrementally với compatibility boundary.
7. Xử lý database/jobs/integrations riêng.
8. Rollout/canary/rollback và data compatibility.
9. Đo kết quả từng slice.
10. Quyết định có/không tách services dựa trên evidence.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không rewrite toàn bộ chỉ vì target stack hiện đại; big-bang rewrite làm mất feedback và tăng business-rule discovery risk.
- Không coi container/Kubernetes là modernization của application semantics; legacy/runtime/dependency risk vẫn còn.
- Bắt đầu bằng inventory: dependencies, unsupported libraries, module coupling, data ownership, critical flows, deployment/runtime constraints.
- Xây characterization/integration/E2E tests cho critical behavior trước hoặc song song migration.
- Chọn vertical slices/seams để old/new cùng tồn tại trong transition, với routing/integration contract rõ.
- Database migration phải backward-compatible trong transition; shared schema/cross-module transactions cần được hiểu trước khi tách ownership.
- Scheduled jobs không nên tiếp tục dựa mơ hồ vào web process lifetime; khi migrate cần explicit execution/idempotency/multi-instance semantics.
- Rollback phải xét code + schema + data compatibility.

### Điểm cộng

- Ưu tiên modules có business value/maintenance pain cao nhưng boundary đủ rõ để học migration process.
- Dùng contract tests/observability để so sánh old/new behavior khi có thể.
- Có thể giữ jQuery UI tạm thời trong một số flows nếu frontend rewrite không mang đủ value; backend/runtime và frontend modernization không bắt buộc big-bang cùng lúc.
- Stored procedures không cần xóa chỉ để “modern”; đánh giá ownership, correctness, performance và migration value.
- CI/CD cần build/test/deploy old và new artifacts nhất quán trong transition.

### Senior+

- Thiết kế coexistence architecture để tránh distributed monolith: explicit ownership, anti-corruption/integration boundary và hạn chế dual writes.
- Dùng migration metrics: escaped defects, lead time, rollback rate, unsupported dependency count, runtime/hosting incidents, critical-flow test coverage.
- Có stop criteria: nếu một module ổn định, low-risk và migration cost vượt benefit, có thể trì hoãn thay vì ép timeline đồng đều.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng discovery ngắn nhưng có output cụ thể: dependency/package/runtime inventory; module map; database tables/SPs và cross-module transactions; external integrations; scheduled jobs; critical user journeys; production incidents; deployment/rollback flow. Mục tiêu là tìm coupling và risk, không viết tài liệu kiến trúc hoàn hảo.

Sau đó tạo safety net ở behavior boundary. Với legacy khó unit-test, tôi ưu tiên characterization tests cho business rules quan trọng, API/integration tests, database tests cho stored procedures critical và Playwright E2E cho vài approval journeys có giá trị cao. Đồng thời bổ sung structured logging/correlation và baseline latency/error để biết migration có đổi behavior không.

Tôi thường chọn một slice có boundary tương đối rõ, không phải module dễ nhất cũng không phải core phức tạp nhất. Implementation mới chạy modern .NET và được route có kiểm soát. Old/new coexist qua explicit contract. Nếu có thể, giữ database changes additive/backward-compatible để rollback binary/routing không yêu cầu reverse destructive migration.

Với shared database, tôi chưa vội tách DB per service. Trước tiên xác định table ownership và loại bỏ cross-module writes dần. Nếu một module mới vẫn trực tiếp sửa tables của module khác thì gọi nó là microservice không tạo isolation thật. Khi ownership rõ và independent deployment/scale thực sự có value, mới cân nhắc tách storage/service.

Scheduled jobs được đưa ra khỏi implicit web lifecycle sang một execution model rõ như Worker Service, Functions hoặc scheduler phù hợp sau khi đánh giá duration, trigger, hosting và operational requirements. Dù chọn gì, job phải có cancellation, idempotency, retry và multi-instance semantics rõ.

Tôi không bắt buộc React rewrite cùng backend migration. Nếu jQuery screens ổn và ít thay đổi, giữ chúng tạm thời có thể giảm scope. Frontend có thể migrate theo route/feature sau. Tương tự, stored procedures hiệu quả và well-owned có thể tiếp tục tồn tại; mục tiêu là giảm risk/coupling chứ không đạt “zero stored procedure”.

Đề xuất 1 — full rewrite — chỉ hợp lý khi current model fundamentally không thể evolve và business chấp nhận parallel product rebuild risk; trong bối cảnh này thiếu tests/rules undocumented khiến nó rất nguy hiểm. Đề xuất 2 là baseline tôi ưu tiên vì tạo feedback sớm và giữ monthly delivery. Đề xuất 3 có thể cải thiện packaging/operations trong vài trường hợp nhưng Kubernetes không nâng runtime hoặc tháo coupling; nó còn thêm operational complexity nếu team chưa cần.

Mỗi slice có canary/feature routing nếu phù hợp, compatibility tests, rollback plan và metrics. Sau vài slices, tôi đánh giá lại target architecture. Nếu modular monolith trên App Service/IIS/Linux phù hợp SLO và team size, không có nghĩa migration thất bại vì chưa có microservices/Kubernetes.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng rewrite hay Kubernetes. Đầu tiên tôi inventory dependencies, module/data coupling, scheduled jobs, integrations và critical business flows. Vì test automation yếu, tôi tạo characterization/integration/E2E safety net ở các approval flows quan trọng để bảo vệ behavior trước khi thay code.

Tôi chọn một vertical slice có boundary đủ rõ, migrate sang modern .NET và cho old/new coexist qua contract/routing có kiểm soát. Database changes ưu tiên additive/backward-compatible để rollback được. Shared DB chưa cần tách ngay; trước hết phải xác định ownership và giảm cross-module writes. Scheduled jobs được tách khỏi implicit web lifecycle với idempotency/retry/multi-instance semantics rõ.

Tôi cũng không buộc React rewrite đồng thời nếu jQuery screen vẫn ổn. Sau từng slice tôi đo defects, deployment/rollback, lead time và production telemetry. Chỉ tách microservices hoặc chọn Kubernetes khi independent scaling/deployment/ownership thực sự tạo value. Mục tiêu là giảm risk từng bước trong khi business vẫn release hàng tháng.”

## Câu hỏi đào sâu

1. Nếu một critical module dùng transaction xuyên 12 tables thuộc 4 modules, bạn có tách nó trước không? Bạn cần thay đổi gì trước?
2. Nếu CTO yêu cầu “mọi thứ phải lên .NET 10 trong 6 tháng”, bạn sẽ chia migration waves và risk acceptance như thế nào?
3. Nếu characterization tests cho thấy implementation cũ có behavior kỳ lạ nhưng business không biết đó là bug hay requirement, bạn xử lý migration ra sao?

## Lỗi trả lời thường gặp

- Đồng nhất modernization với rewrite/microservices/Kubernetes.
- Tách services nhưng vẫn share-write cùng database tables.
- Migrate framework trước khi có safety net cho undocumented business rules.
- Đổi backend, frontend, database và hosting cùng một lúc khiến rollback gần như không thể.
- Xóa stored procedures hoặc legacy UI chỉ vì “không modern” mà không có value/risk analysis.

## Thang điểm 0–10

- **0–2:** Chọn stack mới và đề xuất rewrite toàn bộ.
- **3–4:** Biết incremental migration nhưng chưa có data/testing/rollback strategy.
- **5–6:** Có inventory, safety net, slices và compatibility plan thực tế.
- **7–8:** Xử lý shared DB/jobs/coexistence/CI-CD/observability và migration metrics tốt.
- **9–10:** Cân bằng delivery với technical risk, có explicit ownership/evolution criteria và tránh complexity không có business justification.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- GC có thể thu hồi object nhưng allocation amplification và peak live set vẫn gây memory/latency pressure; RSS growth một mình không chứng minh leak.
- Kubernetes readiness, liveness và startup giải quyết các câu hỏi khác nhau; external dependency degradation không nên mặc định kích hoạt process restart.
- Resource limits phải được right-size bằng evidence, không dùng để che cache/allocation không giới hạn.
- Modernization an toàn cần inventory, behavioral safety net, incremental seams, backward-compatible data changes và rollback thực tế.
- Microservices/Kubernetes là lựa chọn kiến trúc/vận hành có chi phí, không phải thước đo mức độ “modern”.

## Mẫu tư duy cần nhớ

- **Measure allocation and retention before calling something a leak.**
- **Separate readiness from liveness and restart from traffic routing.**
- **Stabilize first, then prove competing hypotheses with evidence.**
- **Modernize through bounded, reversible slices rather than synchronized rewrites.**
- **Preserve rollback by designing code and schema compatibility together.**
