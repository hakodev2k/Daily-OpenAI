# Code Review Challenge 1 — Hai admin xử lý cùng một approval request làm trạng thái cuối bị ghi đè

**Chủ đề:** Concurrency và race conditions, EF Core transaction handling, optimistic concurrency, correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API quản lý approval request cho thay đổi quyền truy cập hệ thống. Mỗi request ban đầu ở trạng thái `Pending`; admin có thể chọn `Approve` hoặc `Reject`.

Hệ thống chạy trên 4 instance. Trong giờ cao điểm, cùng một request đôi lúc được hai admin mở trên hai browser khác nhau. Production đã ghi nhận các trường hợp:

- Admin A approve, vài trăm mili giây sau Admin B reject, trạng thái cuối thành `Rejected`.
- Audit log chứa cả `Approved` và `Rejected` cho cùng một request.
- Notification đã gửi “Approved” nhưng API sau đó lại trả trạng thái `Rejected`.
- Khi client retry do timeout, action đôi lúc được ghi lại nhiều lần.

Business rule là một request chỉ được chuyển khỏi `Pending` đúng một lần. Sau khi đã `Approved` hoặc `Rejected`, mọi action tiếp theo phải trả về kết quả xác định, không được ghi đè trạng thái trước đó.

## Đoạn code cần review

```csharp
public sealed class ApprovalService
{
    private readonly AppDbContext _db;
    private readonly INotificationSender _notificationSender;
    private readonly ILogger<ApprovalService> _logger;

    public ApprovalService(
        AppDbContext db,
        INotificationSender notificationSender,
        ILogger<ApprovalService> logger)
    {
        _db = db;
        _notificationSender = notificationSender;
        _logger = logger;
    }

    public async Task<ApprovalRequestDto> DecideAsync(
        Guid requestId,
        bool approve,
        Guid adminId,
        CancellationToken cancellationToken)
    {
        var request = await _db.ApprovalRequests
            .SingleAsync(x => x.Id == requestId, cancellationToken);

        if (request.Status != ApprovalStatus.Pending)
            return ApprovalRequestDto.From(request);

        request.Status = approve
            ? ApprovalStatus.Approved
            : ApprovalStatus.Rejected;

        request.DecidedBy = adminId;
        request.DecidedAt = DateTime.UtcNow;

        _db.ApprovalAuditLogs.Add(new ApprovalAuditLog
        {
            RequestId = requestId,
            Action = request.Status.ToString(),
            AdminId = adminId,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await _notificationSender.SendDecisionAsync(
            request.Id,
            request.Status.ToString(),
            cancellationToken);

        _logger.LogInformation(
            "Approval request {RequestId} decided as {Status} by {AdminId}",
            request.Id,
            request.Status,
            adminId);

        return ApprovalRequestDto.From(request);
    }
}
```

4. Ưu tiên các vấn đề cần sửa trước.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### 1. Check-then-update tạo lost update dưới concurrency

**Problem:** Hai request có thể cùng đọc trạng thái `Pending` rồi cùng cập nhật kết quả khác nhau.  
**Why it happens:** Điều kiện `Pending` chỉ được kiểm tra trên snapshot đã đọc ở application layer.  
**Production impact:** Quyết định của admin xử lý sau có thể ghi đè quyết định hợp lệ trước đó.  
**Severity:** Critical  
**Recommended fix:** Bảo vệ transition bằng optimistic concurrency token hoặc conditional `UPDATE ... WHERE Id = ... AND Status = Pending`; chỉ request update được đúng một row mới thắng.

### 2. Không xử lý conflict như một business outcome rõ ràng

**Problem:** Code không phân biệt “request đã được quyết định bởi người khác” với lỗi kỹ thuật.  
**Why it happens:** Không có concurrency exception handling hoặc row-count check.  
**Production impact:** Client có thể hiểu sai là action của mình thành công.  
**Severity:** High  
**Recommended fix:** Sau conflict, reload current state và trả response xác định như `409 Conflict` hoặc domain result phù hợp.

### 3. Audit log có thể ghi action của cả hai request

**Problem:** Mỗi request thêm audit record trước khi biết mình có thực sự thắng transition hay không.  
**Why it happens:** Audit và state transition dựa trên entity state local, không dựa trên atomic outcome.  
**Production impact:** Audit trail mâu thuẫn, khó dùng cho security/compliance.  
**Severity:** High  
**Recommended fix:** Chỉ tạo audit cho transition thực sự thành công, trong cùng transaction với state update.

### 4. Notification nằm sau DB commit nhưng không có delivery state bền vững

**Problem:** Nếu notification lỗi sau commit, DB đã final nhưng side effect bị mất.  
**Why it happens:** External call không có outbox/work item durable.  
**Production impact:** Người dùng không nhận thông báo hoặc retry thủ công có thể tạo hành vi lặp.  
**Severity:** High  
**Recommended fix:** Ghi notification outbox trong cùng transaction với transition, xử lý asynchronously với retry/idempotency.

### 5. Retry từ client không có idempotency semantics rõ ràng

**Problem:** Retry sau timeout có thể chạy lại code hoặc gửi notification lần nữa trong một số thiết kế mở rộng.  
**Why it happens:** API không định nghĩa idempotency key hoặc outcome replay.  
**Production impact:** Duplicate side effect và UX không xác định.  
**Severity:** High  
**Recommended fix:** Quy định rõ retry semantics; với transition final, trả current final state mà không tạo thêm side effect. Nếu request có operation id, lưu và reuse kết quả.

### 6. `SingleAsync` biến not-found thành exception không mang nghĩa domain

**Problem:** Không có handling rõ cho request không tồn tại.  
**Why it happens:** Dùng `SingleAsync` trực tiếp.  
**Production impact:** Có thể tạo 500 thay vì 404/domain error.  
**Severity:** Medium  
**Recommended fix:** Dùng `SingleOrDefaultAsync` và mapping domain result rõ ràng.

### 7. Dùng nhiều `DateTime.UtcNow` tạo timestamp không đồng nhất

**Problem:** Decision và audit có thể lệch vài mili giây dù là cùng operation.  
**Why it happens:** Lấy clock nhiều lần trong flow.  
**Production impact:** Nhỏ nhưng gây khó correlation và test deterministic.  
**Severity:** Low  
**Recommended fix:** Lấy một timestamp cho operation, tốt hơn qua `TimeProvider` nếu cần test.

### 8. Thiếu correlation/decision operation id

**Problem:** Log chỉ có request/admin/status.  
**Why it happens:** Không có operation id hoặc concurrency outcome.  
**Production impact:** Khó điều tra race và retry giữa nhiều instance.  
**Severity:** Medium  
**Recommended fix:** Log structured với request id, operation id, expected state, resulting state, conflict outcome và duration.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng optimistic concurrency với `RowVersion` và transactional outbox. Entity `ApprovalRequest` giả định đã cấu hình `RowVersion` làm concurrency token.

```csharp
public sealed class ApprovalService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public ApprovalService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task<ApprovalDecisionResult> DecideAsync(
        Guid requestId,
        ApprovalStatus decision,
        Guid adminId,
        CancellationToken cancellationToken)
    {
        if (decision is not ApprovalStatus.Approved and not ApprovalStatus.Rejected)
            throw new ArgumentOutOfRangeException(nameof(decision));

        var request = await _db.ApprovalRequests
            .SingleOrDefaultAsync(x => x.Id == requestId, cancellationToken);

        if (request is null)
            return ApprovalDecisionResult.NotFound();

        if (request.Status != ApprovalStatus.Pending)
            return ApprovalDecisionResult.AlreadyDecided(request.Status);

        var now = _timeProvider.GetUtcNow().UtcDateTime;

        request.Status = decision;
        request.DecidedBy = adminId;
        request.DecidedAt = now;

        _db.ApprovalAuditLogs.Add(new ApprovalAuditLog
        {
            RequestId = requestId,
            Action = decision.ToString(),
            AdminId = adminId,
            CreatedAt = now
        });

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "ApprovalDecisionNotification",
            AggregateId = requestId,
            Payload = JsonSerializer.Serialize(new
            {
                RequestId = requestId,
                Status = decision,
                AdminId = adminId
            }),
            CreatedAt = now
        });

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
            return ApprovalDecisionResult.Success(decision);
        }
        catch (DbUpdateConcurrencyException)
        {
            await _db.Entry(request).ReloadAsync(cancellationToken);
            return ApprovalDecisionResult.AlreadyDecided(request.Status);
        }
    }
}
```

Một lựa chọn khác là dùng conditional update trực tiếp tại database và kiểm tra affected rows. Cách đó có thể phù hợp hơn nếu muốn thao tác compare-and-set rõ ràng và giảm tracking.

## Trade-offs

- Optimistic concurrency đơn giản và phù hợp khi conflict hiếm, nhưng cần xử lý `DbUpdateConcurrencyException` có chủ đích.
- Conditional update cho semantics rõ và hiệu quả, nhưng code persistence có thể ít “entity-centric” hơn.
- Pessimistic locking có thể hợp lý trong vài domain đặc biệt nhưng tăng lock contention và complexity.
- Transactional outbox tăng độ tin cậy của side effect nhưng cần worker, cleanup và monitoring.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 20 request song song cho cùng request với cả approve/reject; xác nhận chỉ một transition thành công.
2. **Database invariant test:** xác nhận chỉ một audit record quyết định được tạo cho transition final.
3. **Retry test:** gửi lại cùng action sau khi request đã final; không tạo audit/outbox mới.
4. **Failure-path test:** mô phỏng notification worker lỗi sau commit; outbox vẫn tồn tại và retry được.
5. **Load test:** nhiều approval request khác nhau chạy song song để kiểm tra conflict handling không tạo bottleneck toàn hệ thống.

## Quan sát trong production

Nên theo dõi:

- số concurrency conflict theo phút,
- số duplicate/replayed decision request,
- decision latency,
- outbox pending/failed/retry count,
- notification delivery latency,
- structured log gồm `RequestId`, `AdminId`, `OperationId`, `Decision`, `Outcome`,
- alert khi conflict rate tăng bất thường hoặc outbox backlog vượt SLA.

# Code Review Challenge 2 — Background worker polling queue làm poison message chặn cả luồng và shutdown mất công việc

**Chủ đề:** Background jobs, async/cancellation, error handling, resource lifetime, retry, performance, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một `BackgroundService` xử lý các work item lưu trong bảng `PendingJobs`. Worker chạy trên mỗi application instance. Mỗi job gọi một external API rồi đánh dấu `Completed`.

Khi dependency ổn định, hệ thống xử lý khoảng 30–50 job/giây. Production gần đây xuất hiện:

- một job lỗi dữ liệu bị retry liên tục và chiếm CPU/log volume,
- khi có 3 instance, đôi lúc cùng một job được xử lý nhiều lần,
- khi deploy rolling restart, một số job đang chạy dở không được hoàn thành nhưng cũng không quay lại queue sớm,
- dependency timeout làm backlog tăng nhanh,
- worker gần như không có metric để biết throughput, retry hay oldest pending age.

Business chấp nhận at-least-once processing, nhưng external side effect phải có idempotency strategy và poison job không được làm starvation các job khác.

## Đoạn code cần review

```csharp
public sealed class PendingJobWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly HttpClient _httpClient;
    private readonly ILogger<PendingJobWorker> _logger;

    public PendingJobWorker(
        IServiceScopeFactory scopeFactory,
        HttpClient httpClient,
        ILogger<PendingJobWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var jobs = await db.PendingJobs
                .Where(x => x.Status == JobStatus.Pending)
                .OrderBy(x => x.CreatedAt)
                .Take(100)
                .ToListAsync(stoppingToken);

            foreach (var job in jobs)
            {
                try
                {
                    var response = await _httpClient.PostAsJsonAsync(
                        "/api/process",
                        new { job.Id, job.Payload });

                    response.EnsureSuccessStatusCode();

                    job.Status = JobStatus.Completed;
                    job.CompletedAt = DateTime.UtcNow;
                    await db.SaveChangesAsync(stoppingToken);
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "Job {JobId} failed", job.Id);
                }
            }

            await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có atomic claim nên nhiều instance có thể xử lý cùng job

**Problem:** Tất cả worker query `Pending` mà không claim row.  
**Why it happens:** Query và processing không có ownership/lease.  
**Production impact:** Duplicate external calls và duplicate business side effects.  
**Severity:** Critical  
**Recommended fix:** Claim job atomically bằng trạng thái `Processing` + lease/worker id hoặc database-specific locking/skip-locked pattern phù hợp.

### 2. External side effect không có idempotency strategy

**Problem:** Nếu external call thành công nhưng DB update thất bại, job vẫn `Pending` và sẽ gọi lại.  
**Why it happens:** DB và external service không thể commit trong một local transaction.  
**Production impact:** Duplicate processing ở downstream.  
**Severity:** Critical  
**Recommended fix:** Gửi idempotency key ổn định như `job.Id`; downstream phải deduplicate hoặc workflow phải có reconciliation.

### 3. Poison job retry vô hạn mà không có backoff/dead-letter

**Problem:** Job lỗi vẫn giữ `Pending`.  
**Why it happens:** Catch chỉ log exception.  
**Production impact:** Retry storm, log flood, chiếm slot của job khác và tăng dependency load.  
**Severity:** High  
**Recommended fix:** Lưu `AttemptCount`, `NextAttemptAt`, `LastError`, phân loại transient/permanent và chuyển dead-letter sau policy phù hợp.

### 4. Không có lease recovery khi worker chết giữa chừng

**Problem:** Khi thêm trạng thái `Processing` đơn giản mà không có lease, job có thể mắc kẹt vĩnh viễn nếu process chết.  
**Why it happens:** Ownership không có expiration.  
**Production impact:** Lost progress dù dữ liệu vẫn còn.  
**Severity:** High  
**Recommended fix:** Lưu `LeaseUntil`; worker khác được reclaim sau timeout an toàn.

### 5. Không truyền `stoppingToken` vào HTTP call

**Problem:** HTTP request có thể tiếp tục khi host đang shutdown.  
**Why it happens:** `PostAsJsonAsync` overload đang dùng không nhận token.  
**Production impact:** Shutdown kéo dài, work bị cắt giữa chừng khó kiểm soát.  
**Severity:** High  
**Recommended fix:** Truyền cancellation token và thiết kế lease để job có thể retry sau restart.

### 6. `HttpResponseMessage` không được dispose rõ ràng

**Problem:** Response object không được dispose.  
**Why it happens:** Chỉ gọi `EnsureSuccessStatusCode`.  
**Production impact:** Resource được giữ lâu hơn cần thiết dưới tải cao.  
**Severity:** Medium  
**Recommended fix:** `using var response = await ...`.

### 7. Một job chậm giữ cả batch tuần tự

**Problem:** 100 job được xử lý sequentially.  
**Why it happens:** Không có bounded concurrency.  
**Production impact:** Một dependency call chậm kéo throughput toàn worker xuống mạnh.  
**Severity:** Medium  
**Recommended fix:** Dùng bounded parallelism có giới hạn dựa trên capacity của downstream; tránh `Task.WhenAll` không giới hạn.

### 8. Scope/DbContext sống qua toàn batch và external I/O

**Problem:** DbContext tồn tại trong suốt lúc gọi external API cho nhiều job.  
**Why it happens:** Một scope cho cả polling cycle.  
**Production impact:** Change Tracker/lifetime dài hơn cần thiết, khó tách transaction/claim boundaries.  
**Severity:** Medium  
**Recommended fix:** Tách claim và process thành context/scope ngắn, rõ ownership.

### 9. Không có metric/backlog age

**Problem:** Chỉ log từng lỗi.  
**Why it happens:** Observability chưa được thiết kế cho queue semantics.  
**Production impact:** Không biết worker đang chậm, retry storm hay backlog tăng tới mức nào.  
**Severity:** Medium  
**Recommended fix:** Theo dõi queue depth, oldest pending age, attempts, throughput, success/failure, processing duration, lease recovery.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa flow claim/lease ở mức application. Phần atomic claim thực tế nên được triển khai bằng câu lệnh database phù hợp để tránh hai worker cùng claim.

```csharp
public sealed class PendingJobWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly HttpClient _httpClient;
    private readonly ILogger<PendingJobWorker> _logger;
    private readonly string _workerId = Guid.NewGuid().ToString("N");

    public PendingJobWorker(
        IServiceScopeFactory scopeFactory,
        HttpClient httpClient,
        ILogger<PendingJobWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            var job = await ClaimNextJobAsync(stoppingToken);

            if (job is null)
            {
                await Task.Delay(TimeSpan.FromSeconds(1), stoppingToken);
                continue;
            }

            try
            {
                using var request = new HttpRequestMessage(HttpMethod.Post, "/api/process")
                {
                    Content = JsonContent.Create(new { job.Id, job.Payload })
                };
                request.Headers.Add("Idempotency-Key", job.Id.ToString());

                using var response = await _httpClient.SendAsync(
                    request,
                    HttpCompletionOption.ResponseHeadersRead,
                    stoppingToken);

                response.EnsureSuccessStatusCode();
                await MarkCompletedAsync(job.Id, stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                throw;
            }
            catch (Exception ex)
            {
```

Điểm trọng tâm không phải API cụ thể của database mà là semantics: **claim atomic, lease có timeout, at-least-once có idempotency, retry có backoff và poison isolation**.

## Trade-offs

- Database-backed queue đơn giản cho volume vừa phải và ít infrastructure, nhưng cần thiết kế claim/index/polling cẩn thận.
- Message broker có thể cung cấp delivery/visibility semantics tốt hơn nhưng tăng operational complexity.
- Bounded concurrency tăng throughput nhưng phải dựa trên rate limit và capacity của downstream.
- Lease ngắn recovery nhanh nhưng tăng nguy cơ job dài bị reclaim; lease dài giảm duplicate nhưng recovery chậm hơn. Có thể cần heartbeat/lease renewal.

## Cách kiểm thử

1. **Concurrency test:** chạy nhiều worker cùng lúc, xác nhận một job chỉ được claim bởi một worker tại một thời điểm.
2. **Crash recovery test:** kill worker sau claim nhưng trước complete; job được reclaim sau lease expiry.
3. **Failure-path test:** downstream trả 500/timeout; attempt count tăng, backoff đúng và poison job chuyển dead-letter.
4. **Idempotency test:** downstream thành công nhưng DB complete update fail; retry không tạo side effect duplicate.
5. **Shutdown test:** gửi cancellation khi worker đang call dependency; host dừng có kiểm soát và job vẫn recoverable.

## Quan sát trong production

Nên theo dõi:

- `pending_jobs_count`,
- `oldest_pending_job_age_seconds`,
- `jobs_processed_total`, `jobs_failed_total`, `jobs_dead_letter_total`,
- processing duration và downstream latency,
- retry count theo reason,
- active leases và expired lease recovery,
- dependency timeout/error rate,
- alert khi backlog age vượt SLA hoặc dead-letter tăng bất thường.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- State transition có cạnh tranh phải được bảo vệ bằng database invariant hoặc concurrency mechanism, không chỉ bằng `if` trong application.
- External side effect sau DB commit cần delivery state bền vững nếu không muốn mất công việc.
- Background processing theo kiểu at-least-once đòi hỏi idempotency, retry policy, poison isolation và recovery semantics.
- Multi-instance worker cần atomic claim/lease; polling đơn thuần không tạo ownership.
- Observability cho workflow phải đo conflict, backlog, retries, oldest age và failure outcome chứ không chỉ log exception.

## Mẫu tư duy cần nhớ

- Bảo vệ invariant tại nơi có thể enforce atomicity.
- Thiết kế retry cùng idempotency, không tách rời.
- Tách business commit khỏi external delivery bằng durable handoff khi cần.
- Poison work phải bị cô lập để không gây starvation.
- Failure recovery và observability là một phần của thiết kế, không phải phần thêm sau.
