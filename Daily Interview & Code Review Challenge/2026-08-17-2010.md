# Code Review Challenge 1 — Observability middleware làm telemetry nổ cardinality và lộ dữ liệu nhạy cảm

**Chủ đề:** Logging và observability, sensitive-data exposure, performance, memory/allocation, error handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API chạy trên nhiều instance đã thêm middleware để gắn thông tin request vào logging scope và OpenTelemetry tags. Mục tiêu là giúp điều tra production nhanh hơn.

Traffic bình thường khoảng 150–300 request/giây, nhưng có thời điểm burst trên 1.500 request/giây. Sau khi middleware được deploy, team ghi nhận:

- số lượng time series và unique attribute values trong telemetry backend tăng rất nhanh,
- chi phí observability tăng mạnh,
- memory allocation và CPU của API tăng nhẹ nhưng rõ rệt dưới tải cao,
- dashboard truy vấn chậm,
- log đôi lúc chứa access token hoặc query parameter có email/user identifier,
- một số route có GUID/id khác nhau nên metric gần như tạo một series riêng cho từng request.

Business vẫn cần correlation theo request, tenant và endpoint, nhưng không được dùng dữ liệu có cardinality không giới hạn làm metric dimension và không được log secrets.

## Đoạn code cần review

```csharp
public sealed class RequestObservabilityMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestObservabilityMiddleware> _logger;

    public RequestObservabilityMiddleware(
        RequestDelegate next,
        ILogger<RequestObservabilityMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var requestId = context.TraceIdentifier;
        var fullPath = context.Request.Path + context.Request.QueryString;
        var authorization = context.Request.Headers.Authorization.ToString();
        var userId = context.User.FindFirst("sub")?.Value ?? "anonymous";
        var tenantId = context.User.FindFirst("tenant_id")?.Value ?? "unknown";

        using (_logger.BeginScope(new Dictionary<string, object>
        {
            ["RequestId"] = requestId,
            ["Path"] = fullPath,
            ["Authorization"] = authorization,
            ["UserId"] = userId,
            ["TenantId"] = tenantId
        }))
        {
            var activity = Activity.Current;
            activity?.SetTag("http.request_id", requestId);
            activity?.SetTag("http.path", fullPath);
            activity?.SetTag("user.id", userId);
            activity?.SetTag("tenant.id", tenantId);

            var started = Stopwatch.GetTimestamp();

            try
            {
                await _next(context);
            }
            finally
            {
                var elapsedMs = Stopwatch.GetElapsedTime(started).TotalMilliseconds;

                RequestMetrics.Duration.Record(
                    elapsedMs,
                    new KeyValuePair<string, object?>("path", fullPath),
                    new KeyValuePair<string, object?>("user", userId),
                    new KeyValuePair<string, object?>("tenant", tenantId),
                    new KeyValuePair<string, object?>("request_id", requestId),
                    new KeyValuePair<string, object?>("status", context.Response.StatusCode));

                _logger.LogInformation(
                    "Handled {Method} {Path} for {UserId} in {ElapsedMs}ms",
                    context.Request.Method,
                    fullPath,
                    userId,
                    elapsedMs);
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Gắn `request_id` vào metric attributes

**Problem:** Mỗi request gần như tạo một giá trị `request_id` khác nhau.  
**Why it happens:** Code dùng identifier duy nhất làm metric dimension.  
**Production impact:** Cardinality tăng theo số request, làm telemetry backend tốn memory/storage, query chậm và chi phí tăng mạnh.  
**Severity:** Critical  
**Recommended fix:** Không dùng request id trong metric dimensions. Dùng trace/span id để correlation ở trace/log.

### 2. Gắn `userId` vào metric dimensions

**Problem:** Số lượng user có thể rất lớn và tăng theo thời gian.  
**Why it happens:** Per-user metadata bị đưa vào time-series dimensions.  
**Production impact:** Nổ số lượng series và làm dashboard/aggregation kém hiệu quả.  
**Severity:** High  
**Recommended fix:** Không gắn user id vào metrics; nếu cần điều tra theo user, dùng logs/traces có kiểm soát và retention phù hợp.

### 3. Dùng full path + query string làm metric dimension

**Problem:** URL động hoặc query string tạo vô số giá trị khác nhau.  
**Why it happens:** Code dùng URL thực tế thay vì route template ổn định.  
**Production impact:** High cardinality và metric aggregation không còn ý nghĩa.  
**Severity:** High  
**Recommended fix:** Tag theo route pattern ổn định, ví dụ endpoint/route template, không dùng raw URL có ids/query string.

### 4. Logging `Authorization` header

**Problem:** Access token có thể bị ghi vào log scope.  
**Why it happens:** Middleware thu thập header mà không có redaction policy.  
**Production impact:** Secret/token có thể bị lộ cho người có quyền đọc log hoặc qua export pipeline.  
**Severity:** Critical  
**Recommended fix:** Không log Authorization, cookies, API keys hoặc secret headers; áp dụng centralized redaction policy.

### 5. Log raw query string

**Problem:** Query string có thể chứa email, search terms, ids hoặc thậm chí token.  
**Why it happens:** `fullPath` bao gồm nguyên `QueryString`.  
**Production impact:** Rò rỉ PII/sensitive metadata và làm log volume tăng.  
**Severity:** High  
**Recommended fix:** Log route/path chuẩn hóa; chỉ allowlist một số query parameter an toàn nếu thật sự cần.

### 6. Gắn `user.id`/`tenant.id` không có policy rõ ràng vào trace

**Problem:** Trace có thể lưu định danh cá nhân hoặc tenant nhạy cảm.  
**Why it happens:** Mọi claim được coi như observability metadata mặc định.  
**Production impact:** Tăng rủi ro privacy/compliance và làm trace attributes phình to.  
**Severity:** Medium  
**Recommended fix:** Xác định rõ dữ liệu nào được phép xuất ra telemetry; nếu cần tenant dimension, dùng mã ổn định không chứa bí mật và kiểm soát cardinality.

### 7. Duplicated telemetry cho cùng một thông tin

**Problem:** Cùng full path/user/tenant bị ghi ở scope, span và metric.  
**Why it happens:** Không có telemetry schema chung.  
**Production impact:** Tăng payload, allocation, ingestion cost và khó thống nhất dashboard.  
**Severity:** Medium  
**Recommended fix:** Thiết kế semantic convention nội bộ: metric attributes tối thiểu; trace chi tiết hơn; logs chỉ khi có giá trị điều tra.

### 8. Log mỗi request ở `Information`

**Problem:** Mỗi request sinh ít nhất một log entry.  
**Why it happens:** Request logging không có sampling/aggregation phù hợp traffic lớn.  
**Production impact:** I/O và ingestion volume tăng đáng kể dưới tải cao.  
**Severity:** Medium  
**Recommended fix:** Dựa vào access logging đã chuẩn hóa, sampling, hoặc chỉ log request bất thường/slow/error ở mức phù hợp.

### 9. Không có phân loại lỗi trong log cuối request

**Problem:** Middleware chỉ log “Handled” dù request có thể 5xx hoặc exception upstream.  
**Why it happens:** Logging strategy không phân biệt outcome.  
**Production impact:** Incident investigation khó hơn và alerting dễ nhiễu.  
**Severity:** Medium  
**Recommended fix:** Log outcome theo status/exception; dùng structured fields ổn định và không lộ payload nhạy cảm.

## Phiên bản code đề xuất

```csharp
public sealed class RequestObservabilityMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestObservabilityMiddleware> _logger;

    public RequestObservabilityMiddleware(
        RequestDelegate next,
        ILogger<RequestObservabilityMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        var tenantId = context.User.FindFirst("tenant_id")?.Value;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Unhandled request failure. TraceId={TraceId}",
                Activity.Current?.TraceId.ToString());
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);
            var route = context.GetEndpoint() is RouteEndpoint endpoint
                ? endpoint.RoutePattern.RawText ?? "unknown"
                : "unknown";

            RequestMetrics.Duration.Record(
                elapsed.TotalMilliseconds,
                new KeyValuePair<string, object?>("http.method", context.Request.Method),
                new KeyValuePair<string, object?>("http.route", route),
                new KeyValuePair<string, object?>("http.status_code", context.Response.StatusCode));

            if (elapsed > TimeSpan.FromSeconds(2))
            {
                _logger.LogWarning(
                    "Slow request {Method} {Route}. Status={Status} DurationMs={DurationMs} TraceId={TraceId} Tenant={Tenant}",
                    context.Request.Method,
                    route,
                    context.Response.StatusCode,
                    elapsed.TotalMilliseconds,
                    Activity.Current?.TraceId.ToString(),
                    tenantId);
            }
        }
    }
}
```

## Trade-offs

- Bỏ user/request id khỏi metrics làm mất khả năng drill-down trực tiếp từ metric, nhưng đổi lại time-series ổn định và rẻ hơn.
- Tenant id chỉ nên dùng nếu số tenant được kiểm soát và policy cho phép; nếu tenant count rất lớn, cũng không nên là metric dimension.
- Sampling logs/traces giảm chi phí nhưng có thể bỏ sót event hiếm; error traces và security events thường cần sampling policy khác.
- Redaction làm giảm raw diagnostic detail nhưng là yêu cầu bắt buộc để tránh biến telemetry thành kho secrets.

## Cách kiểm thử

1. Load test với hàng trăm nghìn request có request id/user id khác nhau và xác nhận số metric series không tăng theo số request.

# Code Review Challenge 2 — Multi-tenant API có `[Authorize]` nhưng vẫn cho đọc hồ sơ của tenant khác

**Chủ đề:** Authentication và authorization, multi-tenant isolation, EF Core query correctness, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ hệ thống HR multi-tenant. Mỗi tenant có employee riêng. Người dùng đã đăng nhập và có role `HRAdmin` được phép đọc employee trong tenant của mình.

Một pentest phát hiện rằng HR admin của tenant A có thể thay đổi `employeeId` trên URL và đôi lúc đọc được employee thuộc tenant B. Team ban đầu phản hồi rằng endpoint đã có `[Authorize(Roles = "HRAdmin")]` nên đáng lẽ an toàn.

Ngoài ra production ghi nhận audit log không luôn chỉ ra tenant nào sở hữu dữ liệu được truy cập, và response trả nhiều field nội bộ hơn UI thực sự cần.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/employees")]
[Authorize(Roles = "HRAdmin")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeesController> _logger;

    public EmployeesController(
        AppDbContext db,
        ILogger<EmployeesController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{employeeId:guid}")]
    public async Task<IActionResult> Get(
        Guid tenantId,
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        var employee = await _db.Employees
            .SingleOrDefaultAsync(
                x => x.Id == employeeId,
                cancellationToken);

        if (employee == null)
            return NotFound();

        _logger.LogInformation(
            "HR admin {User} read employee {EmployeeId} in tenant {TenantId}",
            User.Identity!.Name,
            employeeId,
            tenantId);

        return Ok(new
        {
            employee.Id,
            employee.TenantId,
            employee.DisplayName,
            employee.Email,
            employee.PersonalEmail,
            employee.HomeAddress,
            employee.InternalNotes,
            employee.Salary
        });
    }
}
```

## Câu hỏi gợi mở

2. `tenantId` trong route có được so với tenant trong identity/token không?
3. Query hiện tại có enforce `employee.TenantId == tenant hiện tại` không?

### Gợi ý 1

### Gợi ý 2

## Kết quả code review tham khảo

### 1. Query không filter theo tenant

**Problem:** Employee được tìm chỉ bằng `employeeId`.  
**Why it happens:** Endpoint coi role `HRAdmin` là đủ để truy cập mọi employee.  
**Production impact:** IDOR/cross-tenant data leak nếu biết hoặc đoán được employee id.  
**Severity:** Critical  
**Recommended fix:** Enforce tenant predicate trong query bằng tenant id lấy từ trusted identity/context.

### 2. Tin `tenantId` trong route như authorization boundary

**Problem:** Caller tự cung cấp `tenantId`.  
**Why it happens:** Route parameter được dùng trong log nhưng không được đối chiếu với tenant claim hoặc membership thực tế.  
**Production impact:** Attacker có thể gửi tenant id tùy ý và khiến audit log gây hiểu nhầm.  
**Severity:** Critical  
**Recommended fix:** Tenant hiện tại phải được resolve từ identity/session đáng tin; nếu route có tenant id thì phải validate nó khớp tenant được phép truy cập.

### 3. Role-based authorization quá rộng

**Problem:** `HRAdmin` chỉ cho biết role, không chứng minh quyền với resource cụ thể.  
**Why it happens:** Authorization model dừng ở role-level.  
**Production impact:** Một HR admin hợp lệ vẫn có thể truy cập resource ngoài scope.  
**Severity:** High  
**Recommended fix:** Dùng policy/resource authorization hoặc tenant-scoped role/membership check ngoài việc xác thực role.

### 4. Response overexposes sensitive fields

**Problem:** API trả salary, home address, personal email, internal notes dù UI có thể không cần.  
**Why it happens:** Return trực tiếp nhiều field từ entity thay vì DTO tối thiểu.  
**Production impact:** Data breach impact lớn hơn và tăng rủi ro privacy/compliance.  
**Severity:** High  
**Recommended fix:** Dùng DTO/projection theo principle of least data; field nhạy cảm cần quyền riêng nếu business yêu cầu.

### 5. Audit log dùng tenant từ request thay vì tenant của resource/authorized context

**Problem:** Log có thể nói request thuộc tenant A dù employee thực tế thuộc tenant B.  
**Why it happens:** Log trusted route input thay vì authorization context và resource ownership.  
**Production impact:** Incident forensics sai lệch và khó phát hiện cross-tenant access.  
**Severity:** High  
**Recommended fix:** Audit tenant từ trusted tenant context và resource; log denied attempts riêng.

### 6. Không thấy defense-in-depth ở data access layer

**Problem:** Tenant isolation phụ thuộc hoàn toàn vào controller nếu những query khác cũng tương tự.  
**Why it happens:** Multi-tenancy chưa được chuẩn hóa thành application/data-access invariant.  
**Production impact:** Dễ tái xuất hiện lỗi ở endpoint khác.  
**Severity:** Medium  
**Recommended fix:** Chuẩn hóa tenant-aware repository/query specification hoặc global query filtering khi phù hợp, nhưng vẫn cần hiểu bypass behavior cho admin/system flows.

### 7. Entity tracking không cần thiết cho endpoint read-only

**Problem:** Query mặc định có thể tracking entity dù chỉ đọc.  
**Why it happens:** Query trả entity đầy đủ.  
**Production impact:** Allocation/Change Tracker overhead không cần thiết.  
**Severity:** Low  
**Recommended fix:** Projection trực tiếp DTO hoặc `AsNoTracking()` nếu cần materialize entity.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/employees")]
[Authorize(Roles = "HRAdmin")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<EmployeesController> _logger;

    public EmployeesController(
        AppDbContext db,
        ITenantContext tenantContext,
        ILogger<EmployeesController> logger)
    {
        _db = db;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [HttpGet("{employeeId:guid}")]
    public async Task<IActionResult> Get(
        Guid tenantId,
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        var authorizedTenantId = _tenantContext.TenantId;

        if (tenantId != authorizedTenantId)
            return Forbid();

        var employee = await _db.Employees
            .AsNoTracking()
            .Where(x =>
                x.Id == employeeId &&
                x.TenantId == authorizedTenantId)
            .Select(x => new EmployeeDetailsDto(
                x.Id,
                x.DisplayName,
                x.Email))
            .SingleOrDefaultAsync(cancellationToken);

        if (employee == null)
            return NotFound();

        _logger.LogInformation(
            "HR admin read employee {EmployeeId} for tenant {TenantId}. TraceId={TraceId}",
            employeeId,
            authorizedTenantId,
            Activity.Current?.TraceId.ToString());

        return Ok(employee);
    }
}

public sealed record EmployeeDetailsDto(
    Guid Id,
    string DisplayName,
    string Email);
```

## Trade-offs

- Route có tenant id giúp URL rõ ràng nhưng tạo thêm giá trị phải validate; nếu user chỉ luôn thuộc một tenant, có thể bỏ tenant id khỏi route và resolve hoàn toàn từ identity.
- Global query filters giúp giảm lỗi lặp lại nhưng cần thiết kế cẩn thận cho system/admin jobs và tránh false sense of security.
- Trả ít field hơn tăng an toàn nhưng có thể cần endpoint/policy riêng cho use case xem salary hoặc dữ liệu nhạy cảm.
- Trả `Forbid` hay `NotFound` cho cross-tenant resource phụ thuộc threat model và API semantics; nhiều hệ thống chọn không tiết lộ resource tồn tại ngoài tenant.

## Cách kiểm thử

1. Integration test HR admin tenant A đọc employee tenant A: thành công.
2. Security test HR admin tenant A dùng employee id của tenant B: không trả dữ liệu.
3. Test route tenant id khác tenant claim dù employee id hợp lệ: bị từ chối.
4. Test user không có `HRAdmin`: bị chặn trước controller/action.
5. Response contract test xác nhận các field nhạy cảm như salary/home address/internal notes không bị serialize.

## Quan sát trong production

- Audit denied cross-tenant attempts với actor id, authorized tenant, requested tenant và trace id; không log dữ liệu nhân sự nhạy cảm.
- Metric số lần authorization denied theo endpoint/reason có cardinality hữu hạn.
- Trace gắn tenant context ở mức phù hợp policy, không gắn employee PII.
- Alert khi một actor liên tục thử nhiều employee id hoặc tenant id khác nhau.
- Security review định kỳ trên tất cả query multi-tenant để tìm predicate thiếu tenant scope.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào global query filter là phù hợp, và khi nào nó có thể gây rủi ro?
2. Bạn thiết kế authorization thế nào nếu một user hợp lệ với nhiều tenant?
3. Nếu một số HR admin được xem salary nhưng số khác không được xem, bạn tách policy và DTO ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Metrics cần attributes có cardinality hữu hạn; request id, user id và raw URL thường phù hợp hơn với logs/traces thay vì metric dimensions.
- Telemetry phải có redaction policy; Authorization, cookies, API keys, token và sensitive query parameters không được log tùy tiện.
- Authentication và role authorization không thay thế resource-level authorization.
- Multi-tenant isolation phải được enforce bằng trusted tenant context và data-access predicate, không dựa vào route parameter do client gửi.
- Principle of least privilege cũng áp dụng cho dữ liệu trả về: chỉ expose đúng field cần thiết.

## Mẫu tư duy cần nhớ

- Chọn telemetry attributes theo **cardinality, sensitivity và mục đích sử dụng**.
- Correlate bằng trace/span id thay vì biến identifier duy nhất thành metric dimension.
- Xem mọi tenant/resource id từ request là untrusted cho đến khi đối chiếu với identity.
- Enforce security invariant càng gần data access càng tốt.
- Giảm blast radius bằng cách không trả hoặc log dữ liệu vượt quá nhu cầu business.
