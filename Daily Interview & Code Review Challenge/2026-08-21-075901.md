# Code Review Challenge 1 — Hangfire job gửi email bị chạy trùng dưới tải cao

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để gửi email nhắc lịch. API tạo bản ghi `EmailJob`, sau đó enqueue Hangfire job. Production chạy nhiều Hangfire workers trên nhiều instance. Gần đây một số khách hàng nhận 2–3 email giống nhau, đặc biệt khi worker restart hoặc external mail API timeout. Business yêu cầu không được bỏ sót email, nhưng duplicate cũng phải được giảm xuống mức có thể kiểm soát.

## Đoạn code cần review

```csharp
public sealed class ReminderJob
{
    private readonly AppDbContext _db;
    private readonly IEmailClient _emailClient;
    private readonly ILogger<ReminderJob> _logger;

    public ReminderJob(
        AppDbContext db,
        IEmailClient emailClient,
        ILogger<ReminderJob> logger)
    {
        _db = db;
        _emailClient = emailClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid jobId)
    {
        var job = await _db.EmailJobs
            .FirstOrDefaultAsync(x => x.Id == jobId);

        if (job == null || job.Status == "Sent")
            return;

        job.Status = "Processing";
        await _db.SaveChangesAsync();

        try
        {
            await _emailClient.SendAsync(
                job.To,
                job.Subject,
                job.Body,
                CancellationToken.None);

            job.Status = "Sent";
            job.SentAtUtc = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            job.Status = "Pending";
            job.LastError = ex.ToString();
            await _db.SaveChangesAsync();
            _logger.LogError(ex, "Failed email job {JobId}", jobId);
            throw;
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Tìm rủi ro concurrency, retry và idempotency.
3. Giải thích tác động production.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation tốt hơn.
6. Mô tả cách kiểm thử dưới concurrency/failure.
7. Đề xuất logs, traces và metrics.

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc `Pending` không?
- Điều gì xảy ra nếu mail provider đã nhận request nhưng client timeout trước khi nhận response?
- `Processing` có thực sự là một lock không?
- Retry của background job tương tác thế nào với trạng thái DB?
- Có thể đạt exactly-once delivery qua một external mail API thông thường không?

## Gợi ý

### Gợi ý 1

Tách hai vấn đề: độc quyền xử lý job và duplicate side effect khi retry.

### Gợi ý 2

Một transaction trong database không thể rollback một email đã được external provider chấp nhận. Hãy nghĩ đến optimistic concurrency/atomic claim và idempotency key ở boundary bên ngoài.

## Kết quả code review tham khảo

### 1. Check-then-update không atomic — High

**Problem:** Nhiều worker có thể cùng đọc trạng thái khác `Sent`.  
**Why:** Query và update `Processing` là hai bước riêng; không có concurrency token hay atomic conditional update.  
**Impact:** Nhiều worker cùng gửi một email.  
**Fix:** Claim job bằng conditional update (`WHERE Status = Pending`) và chỉ worker update thành công mới tiếp tục; hoặc dùng concurrency token/locking phù hợp với DB.

### 2. Không có end-to-end idempotency — Critical

**Problem:** Timeout sau khi provider đã nhận email tạo trạng thái không xác định.  
**Why:** Local DB transaction không bao phủ side effect ở external provider.  
**Impact:** Retry có thể gửi lại email đã gửi thành công.  
**Fix:** Nếu provider hỗ trợ, truyền stable idempotency key theo `jobId`; nếu không, thiết kế semantics rõ ràng là at-least-once và có deduplication/operation ledger ở boundary phù hợp.

### 3. Đặt lại `Pending` cho mọi exception — High

Retry tiếp theo có thể resend ngay cả khi lỗi là ambiguous outcome. Cần phân loại transient, permanent và unknown-outcome; không coi mọi exception giống nhau.

### 4. `Processing` có thể bị kẹt — High

Worker có thể crash sau khi claim. Cần lease/claim timestamp, recovery policy và cơ chế reclaim job quá hạn.

### 5. `CancellationToken.None` — Medium

Không cho phép cooperative cancellation khi shutdown. Nên nhận cancellation token nếu execution framework cho phép và truyền xuống dependency, nhưng phải phân biệt cancellation trước và sau khi side effect có thể đã xảy ra.

### 6. Lưu toàn bộ `ex.ToString()` — Medium

Có thể làm phình dữ liệu hoặc ghi thông tin nhạy cảm. Nên lưu error code/message đã sanitize và giữ stack trace trong logging/telemetry thích hợp.

### 7. String status — Low

Dễ tạo trạng thái không hợp lệ. Dùng enum/value mapping và state-transition rules rõ ràng.

## Phiên bản code đề xuất

```csharp
public sealed class ReminderJob
{
    private readonly AppDbContext _db;
    private readonly IEmailClient _emailClient;
    private readonly ILogger<ReminderJob> _logger;

    public ReminderJob(AppDbContext db, IEmailClient emailClient,
        ILogger<ReminderJob> logger)
    {
        _db = db;
        _emailClient = emailClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid jobId, CancellationToken ct)
    {
        var now = DateTime.UtcNow;

        var claimed = await _db.EmailJobs
            .Where(x => x.Id == jobId && x.Status == EmailJobStatus.Pending)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, EmailJobStatus.Processing)
                .SetProperty(x => x.ProcessingStartedAtUtc, now), ct);

        if (claimed == 0)
            return;

        var job = await _db.EmailJobs
            .AsNoTracking()
            .SingleAsync(x => x.Id == jobId, ct);

        try
        {
            await _emailClient.SendAsync(
                job.To,
                job.Subject,
                job.Body,
                idempotencyKey: job.Id.ToString("N"),
                cancellationToken: ct);

            await _db.EmailJobs
                .Where(x => x.Id == jobId && x.Status == EmailJobStatus.Processing)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, EmailJobStatus.Sent)
                    .SetProperty(x => x.SentAtUtc, DateTime.UtcNow), ct);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Email delivery failed for {JobId}", jobId);
            throw;
        }
    }
}
```

Đoạn code trên minh họa atomic claim và stable idempotency key; production vẫn cần recovery cho `Processing` quá hạn và policy xử lý trạng thái ambiguous. Khả năng dùng idempotency key phụ thuộc contract thực tế của email provider.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi DB là source of truth, nhưng contention cao có thể cần queue architecture tốt hơn. Distributed lock có thể hữu ích trong một số hệ thống nhưng không tự giải quyết duplicate side effect sau timeout. Outbox giúp đảm bảo intent được ghi cùng transaction nghiệp vụ, nhưng consumer vẫn phải idempotent.

## Cách kiểm thử

1. Chạy 20 executions đồng thời cùng `jobId`; chỉ một execution được claim.
2. Mô phỏng provider nhận request rồi client timeout; retry phải dùng cùng idempotency key.
3. Kill worker sau khi claim và kiểm tra recovery của stale `Processing`.
4. Provider trả permanent 4xx và transient 5xx; xác nhận retry policy khác nhau.
5. Load test nhiều job độc lập để đo contention, throughput và duplicate rate.

## Quan sát trong production

Theo dõi `email_job_claim_conflict_total`, retry count, stale-processing count, ambiguous-delivery count, provider latency/error rate và duplicate reports. Correlate trace bằng `jobId`/provider request ID nhưng không log body hoặc recipient nhạy cảm không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu email provider không hỗ trợ idempotency key, bạn thiết kế guarantee nào và communicate ra sao?
2. Outbox pattern giải quyết phần nào của bài toán và phần nào vẫn chưa giải quyết?
3. Bạn có dùng distributed lock để thay atomic DB claim không? Khi nào lựa chọn đó hợp lý?

# Code Review Challenge 2 — Endpoint export user có lỗ hổng authorization và rò rỉ dữ liệu

**Chủ đề:** Authentication/authorization, sensitive-data exposure, EF Core query, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép support staff export thông tin user để xử lý ticket. Endpoint được bảo vệ bằng JWT authentication. Sau một đợt security review, team phát hiện một support user của tenant A có thể lấy dữ liệu user tenant B nếu biết `userId`. Logs production cũng chứa nhiều thông tin cá nhân hơn dự kiến.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/users")]
[Authorize]
public sealed class UsersController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<UsersController> _logger;

    public UsersController(AppDbContext db, ILogger<UsersController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{userId}/export")]
    public async Task<IActionResult> Export(Guid userId)
    {
        var user = await _db.Users
            .Include(x => x.RefreshTokens)
            .Include(x => x.ApiKeys)
            .FirstOrDefaultAsync(x => x.Id == userId);

        if (user == null)
            return NotFound();

        _logger.LogInformation(
            "Exporting user {UserId}: {@User}", userId, user);

        return Ok(new
        {
            user.Id,
            user.TenantId,
            user.Email,
            user.FullName,
            user.PasswordHash,
            RefreshTokens = user.RefreshTokens,
            ApiKeys = user.ApiKeys,
            user.LastLoginIp
        });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/security problems.
2. Phân tích authorization và data exposure.
3. Giải thích impact production.
4. Ưu tiên issues.
5. Viết implementation an toàn hơn.
6. Đề xuất security/integration tests.
7. Đề xuất audit logs và metrics phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` chứng minh điều gì và không chứng minh điều gì?
- Tenant boundary được enforce ở đâu?
- Endpoint thực sự cần những field nào?
- Structured logging object graph có thể ghi gì?
- Tracking entity có cần thiết cho read-only export không?

## Gợi ý

### Gợi ý 1

Authentication không thay thế resource-level authorization.

### Gợi ý 2

Enforce tenant/permission trong query hoặc authorization policy và project trực tiếp sang DTO chỉ chứa dữ liệu được phép trả về.

## Kết quả code review tham khảo

### 1. Broken object-level authorization — Critical

Query chỉ filter `Id`, không kiểm tra tenant/resource permission. Authenticated user biết GUID có thể truy cập resource ngoài phạm vi. Fix bằng policy/permission và tenant boundary được enforce server-side; không tin tenant ID từ request body/query.

### 2. Trả credential material — Critical

`PasswordHash`, refresh tokens và API keys không thuộc support export thông thường. Credential/secrets phải bị loại khỏi response; nếu có use case đặc biệt cần quy trình riêng với least privilege và audit.

### 3. Log toàn entity — High

Destructuring `{@User}` có thể đưa PII hoặc credential-related data vào log sink. Chỉ log identifiers và metadata cần thiết; áp dụng redaction/data classification.

### 4. Chỉ `[Authorize]`, thiếu permission/role policy — High

Authenticated principal chưa chắc được phép export. Endpoint cần authorization policy phù hợp, ví dụ support permission cộng resource/tenant check.

### 5. Load navigation nhạy cảm không cần thiết — Medium

`Include` refresh tokens/API keys vừa tăng query/data materialization vừa mở rộng blast radius nếu logging/serialization sai. Không load dữ liệu không cần dùng.

### 6. Query tracking không cần thiết — Low

Read-only endpoint nên projection trực tiếp hoặc `AsNoTracking()` khi phù hợp để giảm tracking overhead.

## Phiên bản code đề xuất

```csharp
[HttpGet("{userId:guid}/export")]
[Authorize(Policy = "SupportUserExport")]
public async Task<IActionResult> Export(Guid userId, CancellationToken ct)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (!Guid.TryParse(tenantId, out var currentTenantId))
        return Forbid();

    var dto = await _db.Users
        .AsNoTracking()
        .Where(x => x.Id == userId && x.TenantId == currentTenantId)
        .Select(x => new UserExportDto(
            x.Id,
            x.Email,
            x.FullName))
        .SingleOrDefaultAsync(ct);

    if (dto is null)
        return NotFound();

    _logger.LogInformation(
        "User export performed. UserId={UserId}, TenantId={TenantId}",
        userId, currentTenantId);

    return Ok(dto);
}

public sealed record UserExportDto(Guid Id, string Email, string FullName);
```

Trong hệ thống phức tạp hơn, tenant claim phải được thiết lập từ trusted identity context và authorization có thể cần resource-based handler thay vì chỉ policy tĩnh. Có thể cố ý trả `NotFound` cho cross-tenant resource để tránh resource enumeration, tùy security contract.

## Trade-offs

Filter tenant trực tiếp trong query giảm nguy cơ fetch nhầm dữ liệu và hiệu quả hơn fetch-then-check. Global query filter có thể tăng tính nhất quán nhưng cần quản trị cẩn thận các code path được phép bypass. Resource-based authorization linh hoạt hơn nhưng phức tạp hơn. DTO projection giảm accidental exposure nhưng cần maintenance khi contract thay đổi.

## Cách kiểm thử

1. User tenant A export user tenant A với đúng permission → thành công.
2. User tenant A dùng `userId` tenant B → không nhận dữ liệu.
3. Authenticated user không có `SupportUserExport` → 403.
4. Kiểm tra response không chứa password hash/token/API key/IP ngoài contract.
5. Security test log sink để bảo đảm secrets/PII bị loại hoặc redacted theo policy.

## Quan sát trong production

Audit actor ID, tenant ID, target user ID, authorization outcome và correlation ID. Theo dõi số lần denied/cross-tenant access, export rate bất thường và alert khi một actor export số lượng resource vượt baseline. Không ghi credentials hoặc payload nhạy cảm vào logs.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn global query filter cho tenant isolation, và rủi ro của `IgnoreQueryFilters()` là gì?
2. Nếu một central support team được phép truy cập nhiều tenant, authorization model nên thay đổi thế nào?
3. Bạn thiết kế audit trail thế nào để vừa điều tra được incident vừa giảm PII trong logs?
