# Câu 1 — Vì sao API dùng nhiều `byte[]` lớn bắt đầu GC dày, latency nhảy vọt dù CPU chưa cao?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET runtime, Garbage Collector, LOH, allocation, streaming, memory profiling, performance reasoning

## Bối cảnh

Một ASP.NET Core .NET 8 API nhận file từ Blob Storage, transform nội dung rồi trả file mới cho client. File thường 5–30 MB, nhưng có thời điểm 100–250 MB. API chạy 4 instances.

Team đã refactor để dùng `async/await` đầy đủ và CPU trung bình vẫn chỉ khoảng 35–45%, nhưng khi traffic tăng production có các triệu chứng:

- p50 gần như bình thường nhưng p95/p99 tăng mạnh;
- working set dao động rất lớn;
- GC time tăng;
- nhiều request cùng lúc làm process memory tăng nhanh;
- không có memory leak rõ ràng sau khi traffic giảm;
- code hiện đọc file thành nhiều `byte[]` lớn, gọi `ToArray()` nhiều lần rồi mới ghi response;
- một developer đề xuất gọi `GC.Collect()` sau mỗi request lớn;
- người khác đề xuất đổi toàn bộ sang `ArrayPool<byte>` mà chưa đo allocation profile.

Một đoạn simplified code:

```csharp
public async Task<IActionResult> DownloadTransformed(
    Guid fileId,
    CancellationToken cancellationToken)
{
    var source = await _blobClient.DownloadContentAsync(
        fileId,
        cancellationToken);

    var original = source.Value.Content.ToArray();

    var transformed = await _transformer.TransformAsync(
        original,
        cancellationToken);

    var output = transformed.ToArray();

    return File(
        output,
        "application/octet-stream",
        $"{fileId}.bin");
}
```

Bạn chưa được cung cấp GC dump, allocation flame graph hay exact heap size.

## Câu hỏi chính

Hãy giải thích cơ chế runtime có thể khiến workload này có tail latency xấu và memory pressure dù CPU trung bình chưa cao. Sau đó trình bày cách bạn sẽ xác minh giả thuyết, phân biệt allocation pressure với memory leak, và lựa chọn giữa streaming, pooled buffers, batching/concurrency limits hoặc các tối ưu khác.

## Câu hỏi làm rõ nên cân nhắc

1. `TransformAsync` có thật sự cần toàn bộ input trong memory hay có thể xử lý theo stream/chunk?
2. Có bao nhiêu request file lớn chạy đồng thời trên mỗi instance và kích thước phân phối p95/p99 của file là bao nhiêu?
3. `DownloadContentAsync` và `ToArray()` hiện materialize bao nhiêu bản sao của dữ liệu trong memory?
4. GC metrics cho thấy Gen 2 collections, LOH size, allocation rate và pause time thay đổi như thế nào khi incident xảy ra?
5. File response có thể stream trực tiếp hay business requirement yêu cầu biết toàn bộ output trước khi trả?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng `GC.Collect()`. Hãy dựng lại vòng đời của bytes: storage → SDK buffer → `ToArray()` → transformer → output copy → response.

### Gợi ý 2

Đặc biệt chú ý allocations lớn, object lifetime, concurrent live set và việc một request có thể giữ nhiều buffers lớn cùng lúc.

### Gợi ý 3

Tail latency thường đến từ pause, allocation/GC pressure hoặc queueing dưới concurrency; average CPU không đủ để loại trừ runtime pressure.

## Cấu trúc trả lời đề xuất

1. Làm rõ file size/concurrency/transform semantics.
2. Vẽ allocation path và object lifetime.
3. Giải thích LOH/Gen 2 pressure ở mức khái niệm.
4. Nêu các competing hypotheses: leak, allocation burst, buffering, downstream latency, response backpressure.
5. Chọn telemetry/profiling để chứng minh.
6. Đề xuất solution đơn giản nhất trước.
7. Nêu trade-offs của streaming và pooling.
8. Kiểm thử dưới load với file-size distribution thực tế.
9. Theo dõi regression bằng metrics production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra `ToArray()` có thể tạo thêm full-size copies và làm peak live memory tăng theo concurrency.
- Hiểu allocations lớn thường đi vào Large Object Heap và có tác động khác allocations nhỏ; không cần nhớ trivia threshold chính xác để lập luận tốt.
- Phân biệt **memory leak** với **high allocation rate / high live set**: memory có thể giảm sau traffic nhưng GC vẫn gây tail latency.
- Không dùng `GC.Collect()` như default production fix.
- Đề xuất đo allocation rate, heap/LOH, Gen 2 GC, pause time, working set và request concurrency.
- Ưu tiên tránh materialization nếu transform có thể stream/chunk.

### Điểm cộng

- Nhận ra `ArrayPool<byte>` chỉ tốt khi buffer lifecycle rõ, bounded và không giữ buffer quá lâu; pooling không sửa architecture vẫn materialize nhiều copies.
- Đề cập response backpressure và việc client chậm có thể kéo dài lifetime buffer.
- Đề xuất concurrency limit cho large-file transforms để bound live set.
- Phân biệt CPU-bound transform với I/O-bound storage/download.

### Senior+

- Đưa ra kế hoạch benchmark/load test với distribution thực tế thay vì chỉ microbenchmark.
- Thiết kế transform contract dạng stream/pipeline nếu thuật toán cho phép.
- Nêu rõ khi nào temporary file/disk staging có thể là trade-off hợp lý nếu transform bắt buộc random access/full materialization.
- Giải thích rằng pooling có thể làm retained memory tăng và phải tránh trả buffer khi vẫn còn use-after-return risk.

## Hướng giải quyết tham khảo

Giả thuyết đầu tiên là **allocation amplification** chứ chưa phải memory leak. Trong snippet, dữ liệu từ Blob Storage được materialize thành content, sau đó `ToArray()` tạo một buffer mới. Transformer có thể tạo thêm output buffer nội bộ; `transformed.ToArray()` lại tạo thêm copy. Tại một thời điểm, một request 200 MB có thể giữ nhiều buffers lớn đồng thời. Nếu nhiều requests chạy song song, peak live set tăng gần theo `concurrency × bytes-per-request × number-of-live-copies`.

Các allocations lớn tạo pressure lên managed heap, đặc biệt vùng Large Object Heap. LOH được thu gom cùng Gen 2 collection; khi nhiều large objects sinh ra và chết theo burst, Gen 2/LOH collections và pause có thể tăng. Điều này có thể làm p95/p99 xấu dù average CPU không gần 100%. Không cần có leak để GC trở thành bottleneck.

Tôi sẽ không kết luận từ working set một mình. Tôi sẽ thu:

- allocation rate;
- GC pause/time percentage;
- Gen 0/1/2 collection counts;
- LOH size;
- managed heap size;
- process working set;
- request concurrency;
- file-size histogram;
- request duration theo file size;
- dependency duration tới Blob Storage;
- transformer CPU duration.

Sau đó dùng .NET diagnostics/profiler phù hợp để xem allocation hotspots và object retention. Nếu memory giảm lại sau load nhưng allocation/GC tăng mạnh theo burst, đây nghiêng về allocation pressure hơn leak. Nếu retained object graph tiếp tục tăng qua nhiều GC cycles và sau traffic giảm vẫn không release, mới điều tra leak sâu hơn.

Thiết kế tốt nhất nếu transform hỗ trợ là **streaming/chunked processing**: đọc stream từ storage, transform theo stream/chunk và ghi trực tiếp ra response hoặc một output stream. Mục tiêu là bound memory theo buffer size chứ không theo file size.

Nếu thuật toán cần buffers nhưng không cần toàn bộ file, `ArrayPool<byte>` có thể giảm allocation churn cho fixed-size chunks. Nhưng pooling không phải magic: buffer phải được trả đúng lifecycle, không được giữ reference sau return, và pooled arrays có thể làm process giữ memory lâu hơn.

Nếu transform bắt buộc full materialization, tôi sẽ bound concurrency cho large files. Ví dụ chỉ cho một số lượng transforms lớn chạy song song trên một instance; queue phần còn lại. Khi đó tail latency có thể tăng theo queue nhưng process tránh OOM/GC storm. Có thể cân nhắc temp-file staging nếu memory safety quan trọng hơn disk I/O.

Tôi sẽ tránh `GC.Collect()` theo request vì nó biến GC thành synchronous global cost và thường làm throughput/tail latency tệ hơn. Manual collection chỉ nên dùng trong những trường hợp rất đặc biệt và có evidence rõ ràng.

Tài liệu tham khảo để xác minh runtime behavior: Microsoft Learn — .NET garbage collection fundamentals và Large Object Heap documentation.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak. Code đang tạo nhiều full-size copies của cùng file, nên với file 200 MB và nhiều requests đồng thời, live set có thể lên rất nhanh. Large allocations làm LOH/Gen 2 pressure tăng, dẫn tới GC pause và p99 xấu dù average CPU chưa cao. Tôi sẽ đo allocation rate, LOH size, Gen 2 count/pause, working set và correlate với file size + concurrency trước khi sửa. Nếu transformer stream được, tôi sẽ đổi contract sang stream/chunk để memory bounded theo buffer size. Nếu cần buffer, có thể cân nhắc ArrayPool nhưng chỉ sau profiling và với lifecycle rõ. Nếu transform bắt buộc full file, tôi sẽ giới hạn concurrency cho large jobs. Tôi sẽ không gọi GC.Collect sau mỗi request vì đó thường chỉ chuyển pressure thành synchronous pause.”

## Câu hỏi đào sâu

1. Nếu transformer bắt buộc random access toàn bộ 500 MB file, bạn sẽ thiết kế memory/disk/concurrency trade-off thế nào?
2. Nếu chuyển sang `ArrayPool<byte>` nhưng working set tăng và không giảm nhanh, điều đó có nhất thiết chứng minh leak không?
3. Nếu benchmark cho thấy GC chỉ chiếm 2% thời gian nhưng p99 vẫn cao, giả thuyết tiếp theo của bạn là gì?

## Lỗi trả lời thường gặp

- Kết luận “memory leak” chỉ từ working set tăng.
- Đề xuất `GC.Collect()` như fix đầu tiên.
- Nói “dùng Span<T> là nhanh hơn” mà không liên hệ tới allocation path thực tế.
- Đề xuất `ArrayPool<byte>` mà không bàn buffer lifetime/concurrency.
- Không đo tail latency theo file size và concurrency.

## Thang điểm 0–10

- **0–2:** Chỉ nói “GC chậm” hoặc “thêm RAM”.
- **3–4:** Nhận ra allocations lớn nhưng không giải thích concurrency/live set hoặc cách đo.
- **5–6:** Giải thích tốt allocation pressure, LOH/Gen 2, profiling và streaming.
- **7–8:** Có trade-offs cho pooling, backpressure, concurrency limit và failure behavior.
- **9–10:** Lập luận conditional, phân biệt leak vs pressure bằng evidence, thiết kế benchmark/telemetry và chọn architecture memory-bounded phù hợp.

# Câu 2 — Publish trong Optimizely thành công nhưng người dùng vẫn thấy nội dung cũ qua CDN

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CDN/Akamai, HTTP caching, cache invalidation, production troubleshooting, observability, SEO/web reliability

## Bối cảnh

Một marketing website dùng Optimizely CMS, ASP.NET Core và Akamai CDN. Editors publish campaign content qua CMS. Origin chạy nhiều instances trên Azure App Service.

Một incident xảy ra lúc campaign launch:

- editor publish hero banner và pricing text mới;
- CMS UI báo publish thành công;
- một số user thấy nội dung mới ngay;
- một số region/user tiếp tục thấy content cũ 20–40 phút;
- bypass CDN và gọi origin trực tiếp cho thấy content mới;
- hard refresh không phải lúc nào cũng sửa;
- API health, database và CMS authoring đều bình thường;
- team đã từng cấu hình `Cache-Control: public, max-age=1800` cho HTML để giảm origin load;
- Akamai có purge workflow nhưng không rõ publish event có trigger purge cho mọi URL variant không;
- site có canonical URLs, locale variants, query-string campaign parameters và một số pages được render theo culture;
- team đề xuất tắt toàn bộ CDN ngay lập tức.

Bạn đang on-call và chưa biết root cause chính xác.

## Câu hỏi chính

Hãy xử lý incident theo hướng production troubleshooting: đánh giá impact, stabilize, thu evidence, xây competing hypotheses, khoanh vùng cache layer gây stale content, phục hồi service an toàn, rồi đề xuất prevention dài hạn. Không được giả định ngay rằng Akamai purge bị lỗi.

## Câu hỏi làm rõ nên cân nhắc

1. Stale content chỉ xuất hiện ở HTML document hay cả API/JSON/assets?
2. Response headers ở user bị stale có `Age`, `Cache-Control`, `ETag`, `Last-Modified`, CDN cache-status hoặc surrogate headers gì?
3. Các URL bị stale có khác nhau theo hostname, locale path, query string hoặc trailing slash không?
4. Publish event hiện invalidate theo content ID, canonical URL hay danh sách URL variants?
5. Có browser cache/service worker hoặc application-level output cache ở origin ngoài CDN không?

## Gợi ý tư duy

### Gợi ý 1

Đừng nhảy từ “origin đúng, user stale” sang “CDN bug”. Hãy map toàn bộ cache chain: browser → service worker (nếu có) → CDN edge → origin output/cache → CMS/content cache.

### Gợi ý 2

So sánh response headers giữa một request stale và một request fresh. Headers thường cho biết response được cache ở đâu và bao lâu.

### Gợi ý 3

Invalidation phải xử lý **cache key variants**. Một canonical page có thể tương ứng nhiều URL keys theo host/path/query/culture.

## Cấu trúc trả lời đề xuất

1. Xác định business/user impact và phạm vi region/page.
2. Stabilize campaign content delivery.
3. Thu sample stale/fresh responses và headers.
4. Xây hypothesis theo từng cache layer.
5. Verify từng hypothesis bằng targeted request/bypass/purge.
6. Chọn remediation ít blast radius nhất.
7. Xác minh recovery từ nhiều regions.
8. Thiết kế publish → invalidation contract dài hạn.
9. Thêm tests, telemetry và runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tắt CDN ngay nếu chưa cần; ưu tiên scoped purge/bypass cho affected pages nếu khả thi.
- Kiểm tra `Age`, `Cache-Control`, CDN cache status, URL variants và origin response.
- Phân biệt browser cache, CDN cache, output cache và CMS content cache.
- Nhận ra `max-age=1800` cho HTML có nghĩa stale content có thể hợp lệ theo policy nếu purge không xảy ra.
- Phân tích purge key mismatch, locale/query variants và publish invalidation coverage.
- Xác minh recovery từ nhiều edge locations.

### Điểm cộng

- Đề xuất versioned/static assets thay vì purge assets mutable.
- Phân biệt cache policy cho HTML, APIs và immutable assets.
- Đề xuất `s-maxage`/shared-cache policy khi phù hợp thay vì dùng một `max-age` chung cho browser và CDN.
- Đề cập stale-while-revalidate/stale-if-error như deliberate policy, không dùng mặc định.

### Senior+

- Thiết kế content-publish invalidation như observable workflow có event ID, affected URLs, purge result và retry.
- Nêu risk của purge-all: origin thundering herd và global cache cold.
- Đưa SEO/canonical consistency vào verification cho locale/redirect variants.
- Có plan synthetic monitoring theo regions và content version marker.

## Hướng giải quyết tham khảo

Đầu tiên tôi sẽ đánh giá impact: pages nào, locales nào, regions nào, tỷ lệ stale/fresh và campaign criticality. Nếu chỉ vài campaign URLs bị ảnh hưởng, tôi ưu tiên scoped mitigation thay vì tắt CDN toàn site.

Tôi sẽ lấy hai response mẫu cùng URL: một stale từ affected path/region và một fresh từ origin hoặc region không bị ảnh hưởng. So sánh:

- status code;
- `Age`;
- `Cache-Control`;
- `ETag`/`Last-Modified`;
- CDN-specific cache status headers nếu có;
- `Vary`;
- redirect chain;
- exact hostname/path/query/culture.

Các hypothesis chính:

1. **CDN object chưa purge:** edge đang phục vụ object hợp lệ theo TTL 1800 giây.
2. **Purge không cover URL variant:** purge canonical path nhưng cache key khác bởi locale/query/host/trailing slash.
3. **Browser cache:** CDN đã fresh nhưng browser còn response cacheable.
4. **Origin output cache:** bypass edge nhưng vẫn có intermediate output cache cho một số instances.
5. **Service worker/client cache:** nếu site có PWA/service worker.
6. **Mixed origin instances/config:** một subset origin còn render version cũ, dù sample bypass hiện tại fresh.

Nếu header `Age` tăng và CDN cache status cho thấy hit trên response stale trong khi origin fresh, hypothesis CDN stale mạnh. Tôi sẽ thực hiện scoped purge cho affected URL variants và verify từ nhiều locations. Nếu purge API báo success nhưng một variant vẫn stale, kiểm tra cache key composition và exact URL normalization.

Tắt toàn CDN chỉ là last-resort nếu stale content gây harm lớn và scoped invalidation không thể restore nhanh. Purge-all/tắt CDN có thể tạo origin load spike và làm vấn đề khác xuất hiện.

Dài hạn, tôi sẽ tách cache policy:

- HTML/content: TTL phù hợp với editorial freshness requirement, có publish-triggered invalidation;
- static fingerprinted assets: long immutable caching;
- APIs: policy theo sensitivity/freshness, không reuse HTML rule.

Publish pipeline cần có durable/observable invalidation step. Ví dụ CMS publish tạo event với content version + affected URL set. Purge worker gọi CDN API, retry transient failures, ghi outcome, và alert khi purge latency vượt SLO. Mapping URL phải tính locale, aliases, canonical/redirect variants và cache key normalization.

Tôi cũng sẽ thêm synthetic check từ nhiều regions: sau publish một test page/version marker, expected content version phải xuất hiện trong SLO. Dashboard theo purge success rate, purge latency, CDN hit ratio, origin request rate và stale-content incidents.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tắt CDN ngay. Origin fresh chỉ cho biết source hiện đúng, chưa chỉ ra stale nằm ở layer nào. Tôi sẽ lấy stale và fresh response cùng URL, so `Age`, `Cache-Control`, cache-status, ETag, Vary và exact URL variants. Với `max-age=1800`, nếu publish không purge đúng key thì edge phục vụ content cũ 30 phút là đúng policy. Tôi sẽ kiểm tra purge event có cover host, locale, query/trailing-slash variants không, rồi scoped purge affected pages và verify từ nhiều regions. Sau incident, tôi sẽ biến publish→purge thành observable workflow có retry/metrics, tách TTL HTML khỏi immutable assets và thêm synthetic version check sau publish. Purge-all chỉ dùng nếu scoped recovery không đủ vì nó có thể tạo origin thundering herd.”

## Câu hỏi đào sâu

1. Nếu purge thành công nhưng stale chỉ còn trên một browser cohort, bạn điều tra gì tiếp theo?
2. Nếu business yêu cầu content update visible toàn cầu trong dưới 30 giây, bạn thay đổi cache strategy và SLO thế nào?
3. Nếu tắt CDN giúp hết stale nhưng origin CPU tăng lên 95%, bạn ổn định hệ thống ra sao mà không quay lại policy cũ mù quáng?

## Lỗi trả lời thường gặp

- Kết luận “CDN lỗi” chỉ vì origin fresh.
- Purge toàn bộ cache ngay mà không đánh giá origin capacity.
- Chỉ nói giảm TTL mà không thiết kế publish invalidation.
- Không kiểm tra URL/cache-key variants.
- Không dùng response headers để chứng minh cache layer.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất clear cache/tắt CDN.
- **3–4:** Biết kiểm tra cache headers nhưng thiếu incident structure và competing hypotheses.
- **5–6:** Có impact→evidence→hypothesis→verify→fix, hiểu TTL/purge/variants.
- **7–8:** Có scoped mitigation, multi-region verification, cache policy separation và monitoring.
- **9–10:** Thiết kế publish invalidation observable/retriable, cân nhắc origin thundering herd, SEO/locale variants và SLO end-to-end.

# Câu 3 — Activity feed cho CRM: giữ SQL Server hay chuyển sang MongoDB?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** SQL Server, MongoDB, data modeling, indexing, transactions, scale assumptions, architecture trade-offs, observability, migration design

## Bối cảnh

Một CRM hiện lưu customer, contact, deal và audit data trong SQL Server. Team muốn xây Activity Feed cho mỗi customer để hiển thị theo thời gian:

- note được tạo;
- deal đổi stage;
- email metadata được đồng bộ;
- support ticket update;
- marketing event;
- attachment metadata;
- custom integration events.

Mỗi activity có một số fields chung:

- `ActivityId`;
- `TenantId`;
- `CustomerId`;
- `OccurredAtUtc`;
- `ActivityType`;
- `ActorId`;
- metadata riêng theo type.

Business hiện có khoảng 2 triệu customers, vài trăm triệu activity records tổng cộng, tăng liên tục. Dominant reads:

1. lấy 50 activity mới nhất theo `CustomerId`;
2. filter theo `ActivityType` + time range;
3. export lịch sử của một customer;
4. retention theo tenant;
5. một số compliance report cần join activity với customer/account metadata.

Writes đến từ nhiều modules nhưng hiện tất cả vẫn nằm trong cùng modular monolith và SQL transaction boundaries khá rõ.

Một architect đề xuất MongoDB vì “activity payload là JSON và schema thay đổi nhiều”. Một developer khác muốn giữ SQL Server vì team đã vận hành SQL tốt. Chưa có evidence rằng SQL hiện tại không đáp ứng latency SLO.

## Câu hỏi chính

Bạn sẽ quyết định giữa giữ Activity Feed trong SQL Server, chuyển sang MongoDB, hoặc dùng hybrid architecture như thế nào? Hãy đưa ra assumptions, data model, indexes, transaction/consistency semantics, APIs, retention, scale strategy, observability, migration path và các điều kiện khiến recommendation của bạn thay đổi.

## Câu hỏi làm rõ nên cân nhắc

1. SLO cho “latest 50 activities” là bao nhiêu và current SQL execution plan/latency hiện tại ra sao?
2. Activity có cần commit atomically với domain change, ví dụ deal stage update + activity event, hay eventual consistency chấp nhận được?
3. Compliance reports cần strong consistency tới mức nào và join pattern cụ thể ra sao?
4. Có tenant/customer nào cực lớn tạo skew đáng kể không?
5. Metadata riêng theo activity type có được query/filter thường xuyên hay chủ yếu chỉ render lại?

## Gợi ý tư duy

### Gợi ý 1

“JSON payload” không tự động đồng nghĩa “MongoDB”. Bắt đầu từ access patterns, invariants và transaction boundaries.

### Gợi ý 2

Hỏi xem schema variability nằm ở fields cần query hay chỉ ở payload display-only.

### Gợi ý 3

Nếu SQL hiện đáp ứng SLO, cost of introducing một datastore mới phải được tính như một phần của architecture decision.

## Cấu trúc trả lời đề xuất

1. Clarify SLO, growth, consistency và reporting requirements.
2. Đánh giá current SQL evidence.
3. Đề xuất SQL model baseline.
4. Đề xuất MongoDB model alternative.
5. So sánh indexing/query/transaction/operational costs.
6. Chọn recommendation conditional.
7. Thiết kế migration nếu cần thay đổi.
8. Xác định tests, load benchmark và telemetry.
9. Nêu threshold/condition để revisit decision.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn MongoDB chỉ vì document JSON.
- Nhận ra current domain writes đang có SQL transaction boundary; chuyển activity sang datastore khác sẽ thay consistency semantics.
- Đề xuất SQL table/index khả thi cho `TenantId/CustomerId/OccurredAtUtc` access pattern trước khi kết luận SQL không scale.
- Nếu dùng MongoDB, thiết kế document/index theo dominant query thay vì nhúng vô hạn activities vào customer document.
- Có migration/dual-write strategy tránh unsafe distributed dual write.

### Điểm cộng

- Dùng payload JSON column/document field cho variable metadata trong SQL nếu DB/version/use case hỗ trợ, trong khi giữ common query fields normalized/indexed.
- Đề xuất keyset pagination thay offset cho deep customer history.
- Phân tách OLTP feed path khỏi heavy compliance/export workloads khi cần.
- Cân nhắc archival/partitioning/retention theo time/tenant.

### Senior+

- Nếu hybrid projection, dùng Outbox Pattern từ SQL source-of-truth thay vì request path dual-write SQL + MongoDB.
- Có benchmark plan với realistic skew và hot customers.
- Đánh giá operational cost: backup, monitoring, security, migrations, on-call skill, consistency model.
- Nhận ra một datastore mới chỉ đáng giá khi nó giải quyết measured constraint hoặc rõ ràng giảm complexity tổng thể.

## Hướng giải quyết tham khảo

Recommendation ban đầu của tôi sẽ là **giữ SQL Server** nếu benchmark hiện tại cho thấy nó đáp ứng SLO, vì workload có access pattern khá rõ và domain transaction đang ở SQL. Tôi sẽ không thêm MongoDB chỉ vì metadata variable.

Một SQL baseline có thể là:

```text
Activities
- ActivityId
- TenantId
- CustomerId
- OccurredAtUtc
- ActivityType
- ActorId
- PayloadJson
- CreatedAtUtc
```

Common fields dùng columns typed. Variable metadata nằm trong `PayloadJson` nếu phần lớn chỉ cần render. Index chính phục vụ feed có thể bắt đầu theo access pattern như `(TenantId, CustomerId, OccurredAtUtc DESC, ActivityId)` với include fields phù hợp sau khi xem execution plan. Filter `ActivityType` có thể cần index khác nếu query volume đủ lớn; không thêm mọi index trước khi đo write amplification/storage cost.

Pagination cho history dài nên dùng keyset/cursor dựa trên `(OccurredAtUtc, ActivityId)` thay vì offset sâu.

Nếu activity phải được tạo atomically cùng deal update, SQL có lợi thế rõ vì cùng transaction. Nếu chuyển activity primary store sang MongoDB, request path có nguy cơ dual write: SQL commit thành công nhưng MongoDB fail hoặc ngược lại. Nếu eventual feed projection chấp nhận được, tốt hơn là commit domain change + outbox trong SQL rồi asynchronous projector ghi MongoDB idempotently.

MongoDB trở nên hấp dẫn hơn nếu evidence cho thấy:

- workload chủ yếu document-centric;
- metadata rất đa dạng và nhiều fields dynamic thực sự cần query/index;
- query/read scale hoặc sharding requirement vượt khả năng/cost của SQL design thực tế;
- transaction coupling với SQL domain thấp hoặc eventual consistency được chấp nhận;
- team có operational maturity để vận hành thêm datastore.

Trong MongoDB, tôi sẽ không embed toàn bộ activities vào một customer document vì document sẽ tăng vô hạn và tạo contention/size problem. Mỗi activity nên là document riêng, với fields `tenantId`, `customerId`, `occurredAtUtc`, `activityType` và payload. Index phải phục vụ latest-by-customer và type/time filters. Shard key nếu cần phải dựa trên real distribution/query routing; không chọn chỉ vì field “có vẻ unique”.

Hybrid architecture có thể hợp lý nếu SQL vẫn là source-of-truth/compliance record còn MongoDB là read projection cho feed. Nhưng hybrid thêm lag, replay/reconciliation, monitoring và cost. Tôi chỉ chọn nếu benchmark chứng minh projection giải quyết constraint đáng kể.

Migration nếu cần:

1. tạo new store/indexes;
2. backfill historical activities có checkpoint;
3. dùng SQL outbox/projector cho new writes;
4. validate count/hash/sample parity;
5. shadow-read hoặc compare result sets;
6. chuyển read traffic dần;
7. giữ rollback path;
8. chỉ decommission old path sau stability window.

Observability gồm feed query p50/p95/p99, rows/docs scanned, index usage, DB CPU/IO, write latency, storage growth, hot customer skew, projection lag, failed/retried events và reconciliation mismatches.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa thấy lý do đủ mạnh để thêm MongoDB. Activity payload variable không có nghĩa phải dùng document database; common query fields vẫn rất ổn với SQL và payload riêng có thể để JSON nếu phần lớn chỉ render. Tôi sẽ benchmark latest-50 và filter-by-type với index theo tenant/customer/time trước. Quan trọng hơn, domain updates hiện commit trong SQL; chuyển activity sang MongoDB sẽ đổi từ local transaction sang distributed consistency problem. Nếu sau này MongoDB thật sự cần cho read scale/schema-query flexibility, tôi sẽ dùng SQL outbox để project activity sang MongoDB idempotently thay vì dual-write trong request. MongoDB lúc đó là read model/projection hoặc primary store chỉ khi consistency requirements cho phép. Quyết định thay đổi nếu SQL không đạt SLO/cost sau tuning hoặc dynamic query workload thực sự phù hợp document indexing hơn.”

## Câu hỏi đào sâu

1. Nếu một customer enterprise tạo 20 triệu activities trong khi hầu hết customer chỉ có vài trăm, SQL và MongoDB design của bạn thay đổi thế nào?
2. Nếu product yêu cầu activity xuất hiện trong feed dưới 500 ms sau deal update, hybrid asynchronous projection còn phù hợp không?
3. Nếu compliance yêu cầu export consistent snapshot trong khi writes vẫn tiếp tục, bạn sẽ thiết kế đọc/export như thế nào?

## Lỗi trả lời thường gặp

- “JSON thì dùng MongoDB” mà không phân tích query/invariant.
- “SQL scale không được” nhưng không có execution plan/load evidence.
- Dual-write SQL + MongoDB trực tiếp trong request mà không xử lý partial failure.
- Embed toàn bộ activity history vào một MongoDB customer document.
- Không tính operational cost của datastore thứ hai.

## Thang điểm 0–10

- **0–2:** Chọn datastore theo sở thích/cliché.
- **3–4:** So sánh SQL vs MongoDB ở mức feature list nhưng thiếu transaction/access pattern.
- **5–6:** Có data model/index/consistency reasoning và conditional recommendation.
- **7–8:** Có migration, outbox/hybrid trade-off, load evidence và observability.
- **9–10:** Cân bằng correctness, scale, operational complexity, migration safety và chỉ thêm datastore khi có measured justification.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Allocation pressure và high live set có thể gây GC/tail-latency problem mà không cần memory leak.
- Với workload file lớn, giảm số lần materialize/copy và bound concurrency thường quan trọng hơn micro-optimization.
- Stale content qua CDN phải được điều tra theo cache chain và evidence từ response headers, không đoán theo cảm giác.
- Publish-to-purge là một production workflow cần retry, telemetry và cache-key coverage rõ ràng.
- Chọn SQL Server hay MongoDB phải bắt đầu từ access pattern, consistency boundary và measured constraints, không từ data-format stereotype.
- Datastore thứ hai mang theo operational và distributed-consistency cost thật.

## Mẫu tư duy cần nhớ

- Measure allocation/live set before forcing GC or pooling everything.
- Trace bytes and object lifetime before optimizing memory.
- For cache incidents: **impact → sample stale/fresh → inspect headers → locate layer → scoped recovery → verify**.
- Design invalidation together with cache policy.
- Choose storage from **access patterns + invariants + consistency + operations**, not buzzwords.
