# Code Review Challenge 1 — Hangfire job gửi email bị chạy trùng và trạng thái sai

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một Hangfire job xử lý các yêu cầu offboarding. Job cập nhật mailbox qua dịch vụ bên ngoài rồi đánh dấu bản ghi hoàn tất. Production có nhiều Hangfire workers. Gần đây một số mailbox bị thao tác hai lần, lịch sử có bản ghi trùng, và đôi lúc hệ thống ghi `Completed` dù bước bên ngoài chưa hoàn tất đầy đủ. Dịch vụ ngoài có thể timeout sau khi đã thực hiện thành công thao tác.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 3)]
    public async Task ProcessAsync(int requestId)
    {
        var request = await _db.OffboardingRequests
            .FirstOrDefaultAsync(x => x.Id == requestId);

        if (request == null || request.Status == "Completed")
            return;

        request.Status = "Processing";
        await _db.SaveChangesAsync();

        if (request.Action == "Forward")
            await _exchange.SetForwardingAsync(request.Email, request.TargetEmail!);
        else if (request.Action == "Delegate")
            await _exchange.AddDelegateAsync(request.Email, request.TargetEmail!);

        _db.OffboardingHistories.Add(new OffboardingHistory
        {
            RequestId = request.Id,
            Message = "Mailbox updated",
            CreatedAt = DateTime.Now
        });

        request.Status = "Completed";
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Offboarding completed for {Email} -> {Target}",
            request.Email,
            request.TargetEmail);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Tìm rủi ro concurrency, retry và idempotency.
3. Giải thích impact khi timeout/failure xảy ra ở các thời điểm khác nhau.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai workers có thể cùng đọc `Pending` không?
- Retry có biết external side effect trước đó đã thành công hay chưa?
- `SaveChangesAsync` đầu tiên có tạo lock kéo dài đến external call không?
- Điều gì xảy ra nếu process chết sau external call nhưng trước lần `SaveChangesAsync` cuối?
- `Completed` có đủ để biểu diễn trạng thái từng bước không?

## Gợi ý

### Gợi ý 1

Hãy phân biệt **exactly-once execution** với **effectively-once business effect**.

### Gợi ý 2

Một `if (Status == Completed)` không phải cơ chế mutual exclusion; hãy nghĩ đến atomic claim, optimistic concurrency, unique constraints và reconciliation.

## Kết quả code review tham khảo

### 1. Check-then-update không atomic

- **Problem:** nhiều workers có thể cùng đọc cùng một request chưa `Completed`.
- **Why:** đọc trạng thái và chuyển sang `Processing` là các thao tác tách rời, không có conditional atomic update/concurrency token.
- **Impact:** external side effect và history có thể chạy trùng.
- **Severity:** Critical.
- **Fix:** claim công việc atomically, ví dụ conditional update `Pending -> Processing`, hoặc optimistic concurrency token; chỉ worker claim thành công được tiếp tục.

### 2. Retry không đi cùng idempotency

- **Problem:** Hangfire retry toàn method sau exception.
- **Why:** external service có thể đã commit nhưng client nhận timeout.
- **Impact:** forwarding/delegation có thể được áp dụng lặp lại hoặc tạo trạng thái khó dự đoán.
- **Severity:** Critical.
- **Fix:** thiết kế operation idempotent theo desired state; lưu operation key/state và kiểm tra trạng thái thực tế trước retry khi API ngoài không hỗ trợ idempotency key.

### 3. Crash window sau external side effect

- **Problem:** process có thể chết sau `_exchange...` nhưng trước khi DB ghi `Completed`.
- **Impact:** lần retry không biết side effect đã xảy ra.
- **Severity:** High.
- **Fix:** state machine theo từng bước (`Pending`, `Processing`, `ExternalApplied`, `Completed`, `Failed`) và reconciliation. Không thể tạo distributed transaction thực sự với Exchange; phải thiết kế recovery.

### 4. `Processing` có thể bị mắc kẹt

- **Problem:** exception sau lần save đầu để request ở `Processing`.
- **Impact:** dashboard sai hoặc cơ chế khác có thể bỏ qua request mãi mãi.
- **Severity:** High.
- **Fix:** lưu attempt/lease timestamp, error, next retry; có recovery cho lease quá hạn.

### 5. Không validate business input trước side effect

- **Problem:** `TargetEmail!` chỉ suppress nullable warning.
- **Impact:** invalid request có thể fail muộn hoặc gọi external API với dữ liệu sai.
- **Severity:** High.
- **Fix:** validate action, target, end-time/business rules trước khi claim hoặc trước external call.

### 6. History có thể trùng

- **Problem:** không có uniqueness/idempotency key cho history.
- **Impact:** audit trail sai lệch khi retry/concurrency.
- **Severity:** Medium.
- **Fix:** history gắn `OperationId`/step và unique constraint phù hợp.

### 7. Không truyền cancellation token

- **Problem:** DB/external calls không nhận cancellation.
- **Impact:** shutdown/deployment có thể kéo dài và làm recovery khó hơn.
- **Severity:** Medium.
- **Fix:** truyền cancellation token nếu job framework và dependency hỗ trợ; external timeout vẫn phải cấu hình độc lập.

### 8. `DateTime.Now` làm audit phụ thuộc timezone máy chạy

- **Problem:** timestamp local không ổn định giữa môi trường.
- **Impact:** audit/correlation khó chính xác.
- **Severity:** Low.
- **Fix:** dùng UTC, ví dụ `DateTimeOffset.UtcNow`.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(AppDbContext db, IExchangeService exchange,
        ILogger<OffboardingJob> logger)
        => (_db, _exchange, _logger) = (db, exchange, logger);

    [AutomaticRetry(Attempts = 3)]
    public async Task ProcessAsync(int requestId, CancellationToken ct)
    {
        var operationId = Guid.NewGuid();

        var claimed = await _db.OffboardingRequests
            .Where(x => x.Id == requestId && x.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.ProcessingStartedAt, DateTimeOffset.UtcNow)
                .SetProperty(x => x.OperationId, operationId), ct);

        if (claimed == 0)
            return;

        var request = await _db.OffboardingRequests
            .AsNoTracking()
            .SingleAsync(x => x.Id == requestId, ct);

        try
        {
            Validate(request);

            switch (request.Action)
            {
                case "Forward":
                    await _exchange.EnsureForwardingAsync(
                        request.Email, request.TargetEmail!, ct);
                    break;
                case "Delegate":
                    await _exchange.EnsureDelegateAsync(
                        request.Email, request.TargetEmail!, ct);
                    break;
                default:
                    throw new InvalidOperationException("Unsupported action");
            }

            await _db.OffboardingRequests
                .Where(x => x.Id == requestId && x.OperationId == operationId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "ExternalApplied"), ct);

            _db.OffboardingHistories.Add(new OffboardingHistory
            {
                RequestId = requestId,
                OperationId = operationId,
                Message = "Mailbox desired state verified",
                CreatedAt = DateTimeOffset.UtcNow
            });

            await _db.OffboardingRequests
                .Where(x => x.Id == requestId && x.OperationId == operationId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Completed"), ct);

            await _db.SaveChangesAsync(ct);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Offboarding attempt failed. RequestId={RequestId} OperationId={OperationId}",
                requestId, operationId);
            throw;
        }
    }

    private static void Validate(OffboardingRequest request)
    {
        if (request.Action is "Forward" or "Delegate" &&
            string.IsNullOrWhiteSpace(request.TargetEmail))
            throw new InvalidOperationException("Target email is required");
    }
}
```

`EnsureForwardingAsync`/`EnsureDelegateAsync` ở đây là **recommended design**: đặt hệ thống ngoài về desired state hoặc verify trước/sau thao tác. Nếu external API không hỗ trợ semantics này, cần reconciliation riêng. Ngoài ra nên có unique constraint cho `(RequestId, OperationId)` hoặc business operation key phù hợp.

## Trade-offs

Atomic claim đơn giản và phù hợp workload vừa phải nhưng cần recovery cho worker chết sau claim. Distributed lock có thể giảm cạnh tranh nhưng không giải quyết crash window hay unknown outcome của external API. Một workflow/state machine bền vững phức tạp hơn nhưng phù hợp khi offboarding là quy trình quan trọng gồm nhiều side effects.

## Cách kiểm thử

1. **Concurrency test:** 20 workers cùng gọi một `requestId`; chỉ một worker claim thành công.
2. **Unknown-outcome test:** external service thực hiện side effect rồi throw timeout; retry không tạo business effect sai.
3. **Crash recovery:** mô phỏng process chết sau external call và chạy reconciliation.
4. **Database test:** unique constraint ngăn duplicate audit operation.
5. **Failure-path test:** invalid target/action không gọi external service và trạng thái lỗi quan sát được.

## Quan sát trong production

Theo dõi số request theo state/age, retry count, external latency/error/timeout, số request `Processing` quá lease, reconciliation corrections và duplicate-operation attempts. Log phải có `RequestId`, `OperationId`, action và external correlation ID; không log token/credential hoặc dữ liệu nhạy cảm không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu external API không có idempotency key và cũng không có endpoint đọc trạng thái hiện tại, bạn xử lý unknown outcome thế nào?
2. Tại sao distributed lock không tự động giải quyết bài toán exactly-once?
3. Khi nào bạn sẽ chuyển workflow này sang durable workflow/orchestrator thay vì Hangfire job đơn?

# Code Review Challenge 2 — API tìm kiếm tải toàn bộ dữ liệu rồi lọc và làm lộ thông tin

**Chủ đề:** EF Core query execution, authorization, sensitive-data exposure, performance, cancellation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một API nội bộ tìm nhân viên theo keyword và office. Bảng `Employees` có hàng trăm nghìn bản ghi. Sau một đợt tăng traffic, API có latency cao, memory tăng và database CPU cũng tăng. Một QA đồng thời phát hiện người dùng thông thường đôi khi nhận được trường salary/email cá nhân của nhân viên ở office khác.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/employees")]
public sealed class EmployeesController : ControllerBase
{
    private readonly AppDbContext _db;

    public EmployeesController(AppDbContext db) => _db = db;

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string? keyword,
        string? officeCode,
        int page = 1,
        int pageSize = 100)
    {
        var employees = await _db.Employees
            .Include(x => x.Office)
            .Include(x => x.Manager)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            employees = employees
                .Where(x => x.FullName.Contains(keyword,
                    StringComparison.OrdinalIgnoreCase) ||
                    x.Email.Contains(keyword,
                    StringComparison.OrdinalIgnoreCase))
                .ToList();
        }

        if (!string.IsNullOrWhiteSpace(officeCode))
            employees = employees.Where(x => x.Office.Code == officeCode).ToList();

        var result = employees
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.FullName,
                x.Email,
                x.PersonalEmail,
                x.Salary,
                Office = x.Office.Name,
                Manager = x.Manager == null ? null : x.Manager.FullName
            });

        return Ok(result);
    }
}
```

### Gợi ý 2

Authentication chỉ trả lời “ai đang gọi”; authorization/data scoping còn phải trả lời “người đó được xem hàng và cột nào”.

## Kết quả code review tham khảo

### 1. Broken data authorization / sensitive-data exposure

- **Problem:** mọi authenticated user có thể nhận `PersonalEmail` và `Salary`; office filter do client tự chọn.
- **Why:** `[Authorize]` chỉ yêu cầu authenticated principal, không áp policy/row scope/field scope.
- **Impact:** data leak nghiêm trọng.
- **Severity:** Critical.
- **Fix:** authorization policy + server-derived data scope; DTO theo quyền, không để client tự mở rộng scope.

### 2. Materialize toàn bảng trước filtering

- **Problem:** `ToListAsync()` chạy trước `Where`.
- **Why:** từ đó các filter là LINQ-to-Objects.
- **Impact:** DB/network/memory/GC/latency tăng mạnh theo kích thước bảng.
- **Severity:** High.
- **Fix:** giữ `IQueryable` đến cuối và materialize sau filter/projection/paging.

### 3. Paging chạy trong memory

- **Problem:** `Skip/Take` sau materialization.
- **Impact:** mỗi request vẫn tải toàn bộ matching universe.
- **Severity:** High.
- **Fix:** paging trong SQL và có deterministic `OrderBy`.

### 4. Không giới hạn `pageSize` và validate `page`

- **Problem:** client có thể yêu cầu page size rất lớn hoặc page không hợp lệ.
- **Impact:** resource exhaustion/behavior khó đoán.
- **Severity:** High.
- **Fix:** validate `page >= 1`, clamp/reject `pageSize` theo giới hạn hợp lý.

### 5. Over-fetch bằng `Include`

- **Problem:** load entity graph rồi mới tạo DTO.
- **Impact:** nhiều cột/data/tracking hơn cần thiết.
- **Severity:** Medium.
- **Fix:** projection trực tiếp từ query; EF tạo join/subquery cần thiết cho projected fields.

### 6. Read query tracking không cần thiết

- **Problem:** entity được tracking dù chỉ đọc.
- **Impact:** thêm memory/change-tracker overhead.
- **Severity:** Medium.
- **Fix:** `AsNoTracking()` khi materialize entity; projection DTO thường tránh nhu cầu tracking entity output.

### 7. Không truyền request cancellation

- **Problem:** client disconnect nhưng query vẫn có thể tiếp tục.
- **Impact:** lãng phí DB/application capacity khi tải cao.
- **Severity:** Medium.
- **Fix:** nhận `CancellationToken` và truyền vào `ToListAsync`.

### 8. Search semantics/index strategy chưa được thiết kế

- **Problem:** substring search `%keyword%` thường khó tận dụng B-tree index hiệu quả; case sensitivity phụ thuộc DB/collation/operator.
- **Impact:** query có thể vẫn chậm sau khi push xuống DB.
- **Severity:** Medium.
- **Fix:** xác định semantics theo SQL Server/PostgreSQL; dùng predicate translatable phù hợp, đo execution plan; nếu cần search quy mô lớn cân nhắc full-text/trigram/index strategy phù hợp thay vì giả định `Contains` luôn nhanh.

## Phiên bản code đề xuất

```csharp
[HttpGet("search")]
[Authorize(Policy = "EmployeeDirectory.Read")]
public async Task<ActionResult<IReadOnlyList<EmployeeSearchDto>>> Search(
    string? keyword,
    string? officeCode,
    int page = 1,
    int pageSize = 50,
    CancellationToken ct = default)
{
    if (page < 1 || pageSize is < 1 or > 100)
        return BadRequest("Invalid paging parameters.");

    var scope = await GetEmployeeReadScopeAsync(User, ct);

    IQueryable<Employee> query = _db.Employees.AsNoTracking();

    query = query.Where(x => scope.AllowedOfficeCodes.Contains(x.Office.Code));

    if (!string.IsNullOrWhiteSpace(officeCode))
    {
        if (!scope.AllowedOfficeCodes.Contains(officeCode))
            return Forbid();

        query = query.Where(x => x.Office.Code == officeCode);
    }

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x =>
            x.FullName.Contains(term) || x.Email.Contains(term));
    }

    var result = await query
        .OrderBy(x => x.Id)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(x => new EmployeeSearchDto(
            x.Id,
            x.FullName,
            x.Email,
            x.Office.Name,
            x.Manager == null ? null : x.Manager.FullName))
        .ToListAsync(ct);

    return Ok(result);
}
```

**Confirmed principle:** EF Core query operators trên `IQueryable` được dịch sang provider query khi có thể; materialization như `ToListAsync` khiến phần xử lý sau đó chạy trên dữ liệu đã lấy về. **Assumption:** salary/personal email không thuộc directory DTO thông thường. **Recommended approach:** nếu role đặc quyền cần hai field này, dùng explicit privileged DTO/policy thay vì luôn trả rồi kỳ vọng UI ẩn đi.

## Trade-offs

Offset pagination đơn giản nhưng page sâu có thể tốn chi phí và dữ liệu thay đổi giữa các page; keyset pagination phù hợp hơn khi duyệt tuần tự dataset lớn. Projection giảm over-fetch nhưng cần DTO/query riêng. Search behavior phải được benchmark theo DB thực tế: SQL Server collation và PostgreSQL operator/index strategy khác nhau.

## Cách kiểm thử

1. **Authorization test:** user office A không đọc được employee chỉ thuộc office B; field nhạy cảm không xuất hiện trong response thường.
2. **Integration/query test:** xác nhận filtering, ordering và paging được thực hiện trong generated SQL.
3. **Load test:** dataset lớn, đo p95/p99 latency, allocations và DB reads trước/sau fix.
4. **Boundary test:** `page=0`, `pageSize=0`, `pageSize>100`, keyword rỗng/dài.
5. **Cancellation test:** abort request và xác nhận operation được cancel theo khả năng của provider.

## Quan sát trong production

Theo dõi endpoint latency p50/p95/p99, DB command duration, rows returned, request cancellation, allocation/GC, timeout rate và authorization denials. Với slow queries, thu execution plan/query statistics phù hợp DB. Không log salary, personal email hay raw authorization token.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào keyset pagination tốt hơn offset pagination và API contract sẽ thay đổi thế nào?
2. Với PostgreSQL, bạn sẽ thiết kế case-insensitive substring search và index strategy ra sao sau khi đo plan?
3. Nếu HR được xem salary nhưng manager chỉ xem salary của direct reports, bạn đặt authorization ở đâu để tránh data leak?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry chỉ an toàn khi được thiết kế cùng **idempotency** và recovery cho unknown outcome.
- Check-then-act trên shared state không đảm bảo mutual exclusion; claim công việc phải atomic hoặc có concurrency control.
- Không thể dựa vào local DB transaction để rollback side effect đã xảy ra ở external system.
- Với EF Core, giữ query dưới dạng `IQueryable` đến khi filter, projection và paging đã được biểu diễn cho database.
- Authentication không thay thế authorization; data access phải kiểm soát cả **row scope** và **field scope**.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và reconciliation.
- Xác định crash window trước khi gọi một workflow “reliable”.
- Push filtering/projection/paging về nơi dữ liệu nằm, rồi đo execution plan.
- Authorization phải xuất phát từ server-side policy, không tin scope do client cung cấp.
- Observability và failure recovery là một phần của thiết kế, không phải phần bổ sung sau cùng.
