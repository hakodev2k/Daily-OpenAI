# Code Review Challenge 1 — Message đã xử lý xong nhưng vẫn bị giao lại: duplicate delivery làm gọi partner API hai lần

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, idempotency, Inbox/Outbox, message settlement, partial failure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40–50 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một background worker chạy trên .NET 8 nhận `OrderConfirmed` events từ Azure Service Bus.

Mỗi message cần:

- cập nhật `Order` trong SQL Server;
- ghi nhận message đã xử lý để tránh duplicate;
- gọi một external Loyalty API để cộng điểm;
- chỉ complete message khi operation được xem là thành công.

Production chạy 6 instances. Bình thường xử lý ổn, nhưng khi Loyalty API chậm hoặc application restart, team thấy:

- cùng một `MessageId` đôi lúc xuất hiện lại;
- một số order chỉ có một record trong SQL nhưng customer được cộng loyalty points hai lần;
- vài messages bị delivery nhiều lần dù database đã có dấu vết `ProcessedMessage`;
- queue age tăng mạnh khi partner API latency tăng;
- có log chứa toàn bộ raw message body;
- team cho rằng nếu đã check `ProcessedMessages` trước khi xử lý thì duplicate delivery sẽ không còn gây side effect.

Service Bus processor đang được cấu hình với manual settlement.

## Đoạn code cần review

```csharp
public sealed class OrderConfirmedHandler
{
    private readonly AppDbContext _db;
    private readonly LoyaltyClient _loyalty;
    private readonly ILogger<OrderConfirmedHandler> _logger;

    public OrderConfirmedHandler(
        AppDbContext db,
        LoyaltyClient loyalty,
        ILogger<OrderConfirmedHandler> logger)
    {
        _db = db;
        _loyalty = loyalty;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var messageId = args.Message.MessageId;
        var payload = args.Message.Body.ToString();

        _logger.LogInformation(
            "Processing Service Bus message {MessageId}: {Payload}",
            messageId,
            payload);

        if (await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == messageId, cancellationToken))
        {
            _logger.LogInformation("Message {MessageId} already processed", messageId);
            return;
        }

        var message = JsonSerializer.Deserialize<OrderConfirmed>(payload)
            ?? throw new InvalidOperationException("Invalid message");

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        order.Status = OrderStatus.Confirmed;
        order.ConfirmedAt = message.ConfirmedAt;

        await _loyalty.AddPointsAsync(
            message.CustomerId,
            message.LoyaltyPoints,
            cancellationToken);

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = messageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await args.CompleteMessageAsync(
            args.Message,
            cancellationToken);
    }
}
```

Database hiện có bảng:

```sql
CREATE TABLE ProcessedMessages
(
    Id bigint IDENTITY PRIMARY KEY,
    MessageId nvarchar(200) NOT NULL,
    ProcessedAt datetime2 NOT NULL
);
```

Không có unique constraint trên `MessageId`.

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### Critical — External Loyalty API có thể bị gọi nhiều lần cho cùng một business event

**Vấn đề:**  
`AddPointsAsync` được gọi trước khi message được ghi nhận durable là đã xử lý và trước khi Service Bus message được complete.

**Tại sao xảy ra:**  
Nếu Loyalty API trả thành công nhưng process crash, host restart, message lock mất hiệu lực, hoặc `SaveChangesAsync` thất bại sau đó, Service Bus có thể giao lại message. Lần xử lý sau không có bằng chứng durable rằng loyalty side effect đã hoàn tất.

**Ảnh hưởng production:**  
Customer có thể được cộng điểm nhiều lần cho cùng một order dù SQL business state chỉ ghi một lần. Đây là lỗi business correctness, không chỉ là “retry noise”.

**Cách sửa:**  
Không để một non-idempotent remote side effect nằm trong failure window giữa receive và durable state. Một lựa chọn mạnh là transactionally ghi business state + Inbox record + Outbox command/event trong cùng SQL transaction. Một worker riêng dispatch Outbox đến Loyalty API với idempotency key ổn định như `OrderConfirmed:{MessageId}` hoặc business operation ID. Nếu Loyalty API hỗ trợ idempotency key, tận dụng contract đó; nếu không, cần thiết kế một local state machine/reconciliation strategy phù hợp với business risk.

### Critical — `AnyAsync` rồi mới insert là check-then-act race

**Vấn đề:**  
Hai processor instances có thể cùng chạy `AnyAsync` khi chưa có row nào, cả hai đều nhận `false`, rồi cùng tiếp tục xử lý.

**Tại sao xảy ra:**  
Check và insert không phải một atomic operation. Application-level read-before-write không tạo mutual exclusion trên distributed consumers.

**Ảnh hưởng production:**  
Duplicate deliveries gần nhau có thể tạo duplicate DB work và duplicate partner side effect.

**Cách sửa:**  
Enforce uniqueness ở database bằng unique index/constraint trên `MessageId` và xử lý insert như idempotency gate trong transaction. Database constraint mới là race arbiter đáng tin cậy giữa nhiều process. Không chỉ dựa vào `AnyAsync`.

Ví dụ:

```sql
CREATE UNIQUE INDEX UX_ProcessedMessages_MessageId
ON ProcessedMessages(MessageId);
```

### High — Duplicate path `return` nhưng không settle message

**Vấn đề:**  
Processor dùng manual settlement. Khi message đã tồn tại trong `ProcessedMessages`, handler chỉ `return` mà không gọi `CompleteMessageAsync`.

**Tại sao xảy ra:**  
Code giả định “không làm gì” đồng nghĩa message đã xử lý xong, nhưng manual settlement yêu cầu explicit completion nếu muốn loại message khỏi active delivery flow.

**Ảnh hưởng production:**  
Một duplicate đã được xác nhận là an toàn để bỏ qua có thể tiếp tục được giao lại cho đến khi lock hết hạn/processor xử lý lại, làm tăng delivery count, queue churn, cost và noise.

**Cách sửa:**  
Nếu durable Inbox record chứng minh message đã được xử lý hoàn chỉnh, complete duplicate message rõ ràng. Chỉ làm vậy khi idempotency state thực sự đại diện cho business operation đã commit thành công.

### High — Business update và idempotency record chưa được thiết kế thành một atomic boundary rõ ràng

**Vấn đề:**  
Hiện tại `Order` update và `ProcessedMessage` insert cùng `SaveChangesAsync`, thường có thể được commit cùng một database transaction khi dùng cùng `DbContext`, nhưng code không biến đó thành một explicit processing contract và external side effect lại nằm bên ngoài boundary.

**Tại sao xảy ra:**  
Team đang coi ba hệ thống — SQL Server, Service Bus và Loyalty API — như thể có một transaction chung, trong khi thực tế mỗi dependency có failure semantics riêng.

**Ảnh hưởng production:**  
Có nhiều trạng thái trung gian: partner thành công nhưng DB chưa commit; DB commit nhưng message chưa complete; message được redeliver sau DB commit.

**Cách sửa:**  
Định nghĩa transaction boundary rõ: trong một SQL transaction, ghi business state + Inbox + Outbox. Sau commit, complete Service Bus message. Nếu crash sau SQL commit nhưng trước complete, redelivery sẽ gặp Inbox unique record và được complete an toàn mà không lặp business operation.

### High — Không có database uniqueness nên “ProcessedMessages” không phải idempotency barrier

**Vấn đề:**  
Schema cho phép nhiều rows cùng `MessageId`.

**Tại sao xảy ra:**  
Idempotency rule chỉ tồn tại ở application code, không tồn tại ở persistence invariant.

**Ảnh hưởng production:**  
Concurrent consumers hoặc bug retry có thể chèn duplicate rows; sau đó audit/diagnostics trở nên khó tin cậy.

**Cách sửa:**  
Thêm unique constraint/index trên idempotency key. Chọn key theo semantic identity thực sự của event, không mặc định tin mọi producer luôn cung cấp `MessageId` đúng business uniqueness nếu contract không bảo đảm điều đó.

### Medium — Logging toàn bộ raw payload có thể rò rỉ dữ liệu nhạy cảm và tăng log volume

**Vấn đề:**  
`Payload` được ghi nguyên văn ở Information level.

**Tại sao xảy ra:**  
Message body có thể chứa customer identifiers, dữ liệu business hoặc fields nhạy cảm; payload lớn còn làm tăng ingestion/storage cost.

**Ảnh hưởng production:**  
Rủi ro privacy/security, log retention vượt policy, tăng chi phí và khó search do payload noise.

**Cách sửa:**  
Log structured identifiers cần thiết như `MessageId`, `OrderId`, event type, delivery count, processing result và correlation ID. Chỉ log payload đã redacted ở debug/troubleshooting path có kiểm soát nếu thật sự cần.

### Medium — Error classification và dead-letter policy không xuất hiện trong design

**Vấn đề:**  
Deserialize lỗi, missing order, permanent partner rejection và transient timeout hiện đều có thể đi qua một failure path giống nhau tùy processor host configuration.

**Tại sao xảy ra:**  
Không phân biệt transient failure với poison/permanent failure.

**Ảnh hưởng production:**  
Poison messages có thể retry nhiều lần vô ích; ngược lại transient dependency issue có thể bị xử lý quá sớm như permanent failure nếu policy ở host không phù hợp.

**Cách sửa:**  
Phân loại failure theo contract: invalid schema/business invariant → dead-letter hoặc quarantine có reason rõ; transient network/dependency failure → retry/backoff theo policy; unexpected exception → telemetry đầy đủ rồi để processor retry theo bounded policy. Quyết định retry phải đi cùng idempotency.

### Medium — Cancellation và processing deadline chưa gắn với toàn bộ operation budget

**Vấn đề:**  
Handler nhận cancellation token nhưng chưa có explicit processing timeout/deadline cho external API và DB path, cũng chưa thể hiện cách xử lý khi host shutdown hoặc message lock sắp hết thời gian.

**Tại sao xảy ra:**  
Một partner call kéo dài có thể giữ message processing rất lâu, tăng queue age và lock-loss risk nếu runtime/config không renew đủ cho workload thực tế.

**Ảnh hưởng production:**  
Throughput giảm, redelivery tăng, shutdown kéo dài và khó phân biệt dependency slowness với consumer starvation.

**Cách sửa:**  
Đặt timeout budget rõ cho external dependencies, propagate cancellation, cấu hình message processing/lock renewal phù hợp với measured p99, và ưu tiên chuyển remote side effect sang Outbox dispatcher để Service Bus receive handler có critical section ngắn hơn.

### Low — `DateTime.UtcNow` trong persistence làm testability/audit semantics kém rõ ràng

**Vấn đề:**  
Processing timestamp lấy trực tiếp từ static clock.

**Tại sao xảy ra:**  
Code không có abstraction cho clock và chưa phân biệt event time (`ConfirmedAt`) với processing time.

**Ảnh hưởng production:**  
Không phải incident chính nhưng làm deterministic testing và audit reasoning khó hơn.

**Cách sửa:**  
Dùng `TimeProvider` hoặc abstraction tương đương khi cần test deterministic, đồng thời đặt tên field rõ event time vs processed time.

## Phiên bản đề xuất

Một hướng an toàn hơn là giữ receive handler ngắn và transactionally tạo Inbox + business update + Outbox.

```csharp
public sealed class OrderConfirmedHandler
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<OrderConfirmedHandler> _logger;

    public OrderConfirmedHandler(
        AppDbContext db,
        TimeProvider timeProvider,
        ILogger<OrderConfirmedHandler> logger)
    {
        _db = db;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var messageId = args.Message.MessageId;

        OrderConfirmed message;
        try
        {
            message = JsonSerializer.Deserialize<OrderConfirmed>(
                args.Message.Body.ToString())
                ?? throw new JsonException("Message body is empty");
        }
        catch (JsonException ex)
        {
            _logger.LogWarning(
                ex,
                "Invalid OrderConfirmed payload. MessageId={MessageId}",
                messageId);

            await args.DeadLetterMessageAsync(
                args.Message,
                deadLetterReason: "InvalidPayload",
                cancellationToken: cancellationToken);
            return;
        }

        await using var transaction = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        try
        {
            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = messageId,
                ProcessedAt = _timeProvider.GetUtcNow().UtcDateTime
            });

            var order = await _db.Orders
                .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

            order.Status = OrderStatus.Confirmed;
            order.ConfirmedAt = message.ConfirmedAt;

            _db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                Type = "AddLoyaltyPoints",
                IdempotencyKey = $"order-confirmed:{messageId}",
                Payload = JsonSerializer.Serialize(new AddLoyaltyPointsCommand(
                    message.CustomerId,
                    message.LoyaltyPoints)),
                CreatedAt = _timeProvider.GetUtcNow().UtcDateTime
            });

            await _db.SaveChangesAsync(cancellationToken);
            await transaction.CommitAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsDuplicateMessage(ex))
        {
            await transaction.RollbackAsync(cancellationToken);

            _logger.LogInformation(
                "Message already processed. MessageId={MessageId}",
                messageId);

            await args.CompleteMessageAsync(
                args.Message,
                cancellationToken);
            return;
        }

        await args.CompleteMessageAsync(
            args.Message,
            cancellationToken);
    }

    private static bool IsDuplicateMessage(DbUpdateException exception)
    {
        // Implement using the actual SQL provider error/constraint metadata.
        // Do not classify every DbUpdateException as a duplicate.
        return DuplicateConstraintDetector.IsMatch(
            exception,
            "UX_ProcessedMessages_MessageId");
    }
}
```

Schema cần có persistence invariant:

```sql
CREATE UNIQUE INDEX UX_ProcessedMessages_MessageId
ON ProcessedMessages(MessageId);

CREATE UNIQUE INDEX UX_OutboxMessages_IdempotencyKey
ON OutboxMessages(IdempotencyKey);
```

Outbox dispatcher xử lý remote side effect độc lập:

```csharp
public sealed class LoyaltyOutboxDispatcher
{
    private readonly AppDbContext _db;
    private readonly LoyaltyClient _loyalty;

    public LoyaltyOutboxDispatcher(
        AppDbContext db,
        LoyaltyClient loyalty)
    {
        _db = db;
        _loyalty = loyalty;
    }

    public async Task DispatchAsync(
        OutboxMessage item,
        CancellationToken cancellationToken)
    {
        var command = JsonSerializer.Deserialize<AddLoyaltyPointsCommand>(
            item.Payload)!;

        await _loyalty.AddPointsAsync(
            command.CustomerId,
            command.Points,
            item.IdempotencyKey,
            cancellationToken);

        item.ProcessedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

Đoạn dispatcher trên vẫn cần retry, concurrency control, claim/lease hoặc row-lock strategy phù hợp để nhiều workers không cùng dispatch một Outbox row. Quan trọng hơn, partner API nên hỗ trợ idempotency key nếu operation có thể được retry sau timeout không rõ outcome.

Nếu Loyalty API không hỗ trợ idempotency key, không thể chỉ gọi HTTP rồi tuyên bố exactly-once. Một timeout có thể xảy ra sau khi partner đã commit nhưng trước khi client nhận response. Khi đó cần business-level reconciliation hoặc endpoint contract mới cho phép query trạng thái/idempotent command.

## Giải thích thiết kế sau khi sửa

Flow an toàn hơn:

```text
Service Bus delivery
        |
        v
SQL transaction
  - Inbox/ProcessedMessage unique insert
  - Order state update
  - Outbox insert
        |
        v
Commit SQL
        |
        v
Complete Service Bus message

Outbox dispatcher
        |
        v
Loyalty API with stable idempotency key
        |
        v
Mark Outbox processed
```

Nếu process crash sau SQL commit nhưng trước `CompleteMessageAsync`, message được giao lại. Unique Inbox constraint chặn business processing lần hai; duplicate path chỉ complete message.

Nếu Outbox dispatcher crash sau partner success nhưng trước mark-processed, nó có thể retry. Vì vậy external API idempotency contract mới đóng vòng cuối của duplicate protection.

Mục tiêu thực tế là **effectively-once business effect** bằng durable idempotency, không phải giả định transport có exactly-once execution.

## Trade-offs

- Inbox + Outbox tăng schema, storage và operational code, nhưng đổi lấy failure semantics rõ ràng cho workflow quan trọng.
- Direct HTTP call trong receive handler đơn giản hơn và có thể đủ nếu partner operation tự idempotent và duplicate effect không nghiêm trọng.
- Unique constraint có thêm write/index cost nhưng là chi phí nhỏ so với việc không có distributed idempotency barrier cho business-critical event.
- Outbox dispatcher thêm eventual consistency: SQL order có thể confirmed trước vài giây/phút so với loyalty update. Business cần chấp nhận hoặc hiển thị trạng thái pending.
- Dead-letter policy giúp dừng poison messages nhưng cần operational ownership để theo dõi, sửa và replay có kiểm soát.

## Cách kiểm thử

1. **Concurrency integration test:** publish hoặc trực tiếp invoke hai deliveries cùng `MessageId` đồng thời trên hai scopes; xác minh chỉ một Inbox row, một business transition và một Outbox record tồn tại.
2. **Crash-window test:** inject failure sau SQL commit nhưng trước Service Bus completion; delivery lại phải được complete mà không tạo thêm business effect.
3. **Partner ambiguous-timeout test:** Loyalty API giả lập commit thành công nhưng client timeout; retry với cùng idempotency key không được cộng điểm lần hai.
4. **Poison-message test:** invalid JSON/schema phải đi vào dead-letter/quarantine path với reason rõ và không retry vô hạn.
5. **Load/failure test:** tăng partner latency/error rate; xác minh receive throughput, Outbox backlog và SQL health vẫn trong budget đã định.

## Quan sát trong production

Theo dõi ít nhất:

- Service Bus active message count, queue age và delivery count distribution;
- processing duration p50/p95/p99;
- duplicate Inbox conflicts theo event type;
- completed/abandoned/dead-lettered count;
- Outbox backlog, oldest item age, retry count và dispatch latency;
- Loyalty API p95/p99, timeout, 429/5xx và idempotency-conflict metrics nếu partner cung cấp;
- SQL transaction duration, deadlocks, connection pool pressure;
- correlation fields: `MessageId`, `OrderId`, Outbox ID, external idempotency key;
- alert khi duplicate rate hoặc oldest Outbox age vượt baseline.

Một dashboard tốt phải trả lời được: event đã nhận chưa, SQL đã commit chưa, message đã settle chưa, external side effect đã xác nhận chưa, và có duplicate/retry ở bước nào.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Loyalty API không hỗ trợ idempotency key và không có endpoint tra cứu transaction đã áp dụng, bạn thiết kế reconciliation thế nào?
2. Khi nào Inbox/Outbox là over-engineering và một handler đơn giản vẫn đủ an toàn?
3. Nếu SQL commit thành công nhưng `CompleteMessageAsync` liên tục fail do network partition, vì sao duplicate delivery vẫn an toàn trong design mới?

# Code Review Challenge 2 — Pagination chạy nhanh ở page 1 nhưng chậm dần và trả duplicate/missing rows khi dữ liệu thay đổi

**Chủ đề:** SQL Server, query design, pagination, ordering correctness, indexes, execution plans, concurrent writes, API performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp danh sách `AuditEvents` cho enterprise portal.

Bảng có khoảng 80 triệu rows và tăng khoảng 3–5 triệu rows mỗi tháng. Users thường:

- xem events mới nhất trước;
- filter theo `TenantId`;
- có thể filter `EventType`;
- search theo `ActorName` hoặc một phần `Description`;
- di chuyển qua nhiều pages;
- exports dùng endpoint khác, không phụ thuộc vào pagination này.

API hiện trả `page`, `pageSize`, `totalCount` và rows.

Production có các symptom:

- page 1 thường dưới 150 ms nhưng page 5000 có thể mất vài giây;
- khi events mới liên tục được insert, user đôi lúc thấy một row xuất hiện ở hai pages hoặc bị “mất” khi bấm Next;
- SQL CPU tăng mạnh khi nhiều users search cùng lúc;
- execution plan có large sort và nhiều logical reads;
- `COUNT(*) OVER()` khiến query vẫn đọc lượng dữ liệu rất lớn dù client chỉ cần 50 rows;
- team đề xuất “thêm thêm vài index” nhưng chưa xác định query shape nào phải tối ưu.

Query hiện tại:

## Đoạn code cần review

```sql
CREATE OR ALTER PROCEDURE dbo.GetAuditEvents
    @TenantId uniqueidentifier,
    @EventType nvarchar(100) = NULL,
    @Search nvarchar(200) = NULL,
    @Page int = 1,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Offset int = (@Page - 1) * @PageSize;

    SELECT
        e.Id,
        e.TenantId,
        e.EventType,
        e.ActorName,
        e.Description,
        e.CreatedAt,
        COUNT(*) OVER() AS TotalCount
    FROM dbo.AuditEvents e
    WHERE e.TenantId = @TenantId
      AND (@EventType IS NULL OR e.EventType = @EventType)
      AND (
            @Search IS NULL
            OR e.ActorName LIKE N'%' + @Search + N'%'
            OR e.Description LIKE N'%' + @Search + N'%'
          )
    ORDER BY e.CreatedAt DESC
    OFFSET @Offset ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
GO

CREATE INDEX IX_AuditEvents_TenantId
ON dbo.AuditEvents(TenantId);
```

Assume `Id` là `bigint` tăng dần và `CreatedAt` không unique.

## Nhiệm vụ của ứng viên

Hãy review query và API pagination strategy này ở góc độ correctness lẫn production performance.

Bạn cần:

1. xác định nguyên nhân gây duplicate/missing rows khi users chuyển page;
2. giải thích vì sao deep `OFFSET` trở nên đắt khi dataset lớn;
3. đánh giá tác động của `COUNT(*) OVER()`;
4. đánh giá search pattern hiện tại và giới hạn của B-tree index với leading wildcard;
5. đề xuất indexing/query strategy dựa trên access pattern;
6. đưa ra một phiên bản pagination ổn định hơn;
7. nêu cách đo execution plan/IO/latency trước và sau thay đổi.

## Câu hỏi gợi mở

1. Nếu nhiều rows có cùng `CreatedAt`, `ORDER BY CreatedAt DESC` có tạo total ordering ổn định không?
2. Khi một event mới được insert giữa lúc user xem page 1 và page 2, `OFFSET 50` đang “đếm” trên cùng một snapshot hay một tập dữ liệu đã thay đổi?
3. SQL Server phải làm gì để bỏ qua hàng trăm nghìn rows trước khi trả page sâu?
4. `LIKE '%text%'` có tận dụng index thông thường giống equality/prefix seek không?
5. Client có thật sự cần exact `totalCount` ở mọi request hay đó là một product requirement có thể thay đổi?

## Gợi ý

### Gợi ý 1

Primary risk có hai phần độc lập: **pagination correctness dưới concurrent writes** và **work amplification của deep OFFSET + count/search**.

### Gợi ý 2

Hãy nghĩ về một stable cursor gồm các cột tạo deterministic order, ví dụ `(CreatedAt, Id)`, thay vì “page number tuyệt đối” trên một dataset liên tục thay đổi.

## Kết quả code review tham khảo

### High — `ORDER BY CreatedAt DESC` không tạo deterministic total order

**Vấn đề:**  
`CreatedAt` không unique. Nhiều rows có thể có cùng timestamp nhưng query không có tie-breaker.

**Tại sao xảy ra:**  
SQL chỉ cần thỏa ordering theo `CreatedAt`; thứ tự tương đối giữa rows cùng timestamp không được business query định nghĩa.

**Ảnh hưởng production:**  
Giữa hai executions, rows có cùng `CreatedAt` có thể xuất hiện ở thứ tự khác, dẫn đến duplicate/missing rows giữa pages ngay cả khi dataset không thay đổi nhiều.

**Cách sửa:**  
Dùng deterministic composite order, ví dụ:

```sql
ORDER BY e.CreatedAt DESC, e.Id DESC
```

Và index hỗ trợ cùng prefix/order nếu access pattern phù hợp.

### High — OFFSET pagination không ổn định trên dataset có concurrent inserts

**Vấn đề:**  
User lấy page 1, sau đó nhiều rows mới được insert trước khi lấy page 2. `OFFSET 50` ở lần sau áp dụng trên một ordered set mới.

**Tại sao xảy ra:**  
Page-number pagination dựa trên vị trí tương đối, nhưng vị trí rows dịch chuyển khi records mới được thêm/xóa hoặc sorting values thay đổi.

**Ảnh hưởng production:**  
Rows có thể bị lặp hoặc bị bỏ qua khi user bấm Next/Previous trong một feed thay đổi liên tục.

**Cách sửa:**  
Dùng keyset/cursor pagination cho navigation tuần tự. Cursor giữ last `(CreatedAt, Id)` của page trước; query page tiếp theo lấy rows nhỏ hơn cursor theo cùng sort order.

### High — Deep `OFFSET` tạo work tăng theo độ sâu trang

**Vấn đề:**  
Để trả page 5000 với 50 rows, engine vẫn phải xác định và bỏ qua một lượng lớn rows đứng trước page đó.

**Tại sao xảy ra:**  
`OFFSET` không biến page sâu thành constant-time lookup. Tùy plan/index, SQL có thể scan/read/sort lượng dữ liệu lớn rồi discard phần đầu.

**Ảnh hưởng production:**  
Latency, logical reads, CPU và memory grant tăng mạnh theo page depth; nhiều concurrent users có thể tạo noisy-neighbor effect lên database.

**Cách sửa:**  
Keyset pagination tránh skip work bằng seek predicate theo stable cursor. Nếu product bắt buộc random access đến page 5000, cần thảo luận rõ trade-off và có thể giữ OFFSET cho use case đó nhưng không giả định nó scale như cursor navigation.

### High — `COUNT(*) OVER()` buộc page query mang theo cost tính total trên toàn result set phù hợp

**Vấn đề:**  
Client chỉ cần 50 rows nhưng query đồng thời yêu cầu exact total count của mọi matching rows.

**Tại sao xảy ra:**  
Window count phải tính trên tập kết quả phù hợp trước pagination semantics; với filter/search rộng, lượng work có thể rất lớn.

**Ảnh hưởng production:**  
Request page nhẹ bị gắn với expensive count. Search phổ biến có thể làm CPU/reads tăng đáng kể dù page size nhỏ.

**Cách sửa:**  
Xác minh requirement. Có thể:

- không trả exact total cho cursor navigation;
- trả `hasMore` bằng cách fetch `PageSize + 1`;
- tính count bằng endpoint/query riêng chỉ khi UI cần;
- cache/approximate count chỉ nếu business cho phép và measurement chứng minh có lợi.

Không có một lựa chọn đúng cho mọi UX.

### High — Leading wildcard search không phù hợp với B-tree index thông thường

**Vấn đề:**  
`LIKE '%term%'` trên `ActorName` và đặc biệt `Description` có thể buộc scan lượng lớn text trong tenant result set.

**Tại sao xảy ra:**  
Pattern bắt đầu bằng wildcard không có anchored prefix để B-tree index thông thường seek trực tiếp theo chuỗi tìm kiếm.

**Ảnh hưởng production:**  
SQL CPU và logical reads tăng mạnh khi nhiều users search đồng thời; thêm index ngây thơ trên `Description` không bảo đảm giải quyết.

**Cách sửa:**  
Làm rõ search semantics. Nếu `ActorName` chỉ cần prefix search, đổi UX/query thành `term%` có thể tận dụng index phù hợp. Nếu cần contains/full-text trên description, đánh giá SQL Server Full-Text Search hoặc search engine đã có trong architecture, nhưng chỉ sau khi đo workload và chấp nhận sync/operational cost.

### Medium — Index hiện tại quá hẹp so với access pattern chính

**Vấn đề:**  
`IX_AuditEvents_TenantId(TenantId)` chỉ hỗ trợ tenant predicate, nhưng query còn order theo `CreatedAt, Id` và có optional `EventType`.

**Tại sao xảy ra:**  
Index chưa phản ánh read pattern “một tenant, newest first”.

**Ảnh hưởng production:**  
Engine có thể đọc nhiều rows trong tenant rồi sort; page càng sâu càng tệ.

**Cách sửa:**  
Đo execution plan và cân nhắc index theo hot path, ví dụ baseline:

```sql
CREATE INDEX IX_AuditEvents_Tenant_CreatedAt_Id
ON dbo.AuditEvents(TenantId, CreatedAt DESC, Id DESC)
INCLUDE (EventType, ActorName);
```

Không mặc định INCLUDE `Description` nếu field lớn. Nếu filter `EventType` đủ selective và phổ biến, có thể cần index variant khác như `(TenantId, EventType, CreatedAt DESC, Id DESC)`. Quyết định dựa trên actual query mix, write cost và plan evidence.

### Medium — Optional predicates có thể tạo plan khó tối ưu ổn định cho các shape rất khác nhau

**Vấn đề:**  
Query phải phục vụ cả no-filter, EventType-filtered và text-search shapes bằng cùng statement.

**Tại sao xảy ra:**  
Cardinality và selective behavior giữa các parameter combinations có thể khác rất lớn. Một plan phù hợp một shape có thể không tốt cho shape khác.

**Ảnh hưởng production:**  
Latency có thể dao động theo parameters và cached plan, đặc biệt khi tenant sizes chênh lệch lớn.

**Cách sửa:**  
Không áp một “hint thần kỳ”. Trước hết quan sát Query Store/execution plans theo representative parameters. Nếu cần, tách query shapes hoặc dùng dynamic SQL có parameterization an toàn cho optional filters. `OPTION (RECOMPILE)` chỉ là một trade-off cần benchmark vì đổi runtime CPU compilation lấy plan specialization.

### Medium — Input validation cho pagination chưa được thể hiện

**Vấn đề:**  
`@Page <= 0`, `@PageSize <= 0` hoặc `@PageSize` quá lớn không được giới hạn trong procedure.

**Tại sao xảy ra:**  
Query giả định caller luôn gửi hợp lệ.

**Ảnh hưởng production:**  
Bad requests hoặc abuse có thể tạo invalid offset, excessive memory/network work hoặc làm API behavior khó đoán.

**Cách sửa:**  
Validate ở API boundary và defensive-check ở database contract nếu procedure được nhiều callers dùng. Đặt maximum page size theo product/SLO.

### Low — Trả `Description` đầy đủ trên list endpoint có thể tăng I/O/network không cần thiết

**Vấn đề:**  
List UI có thể chỉ hiển thị summary nhưng query luôn lấy full description.

**Tại sao xảy ra:**  
Projection chưa được tối ưu theo response contract.

**Ảnh hưởng production:**  
Tăng row width, memory/network và làm index covering kém thực tế hơn.

**Cách sửa:**  
Chỉ select fields list view cần. Nếu user mở detail, gọi detail endpoint riêng.

## Phiên bản đề xuất

Nếu UX chủ yếu là “Next” qua events mới nhất, keyset pagination là default tốt hơn.

Ví dụ page đầu:

```sql
CREATE OR ALTER PROCEDURE dbo.GetAuditEventsPage
    @TenantId uniqueidentifier,
    @EventType nvarchar(100) = NULL,
    @BeforeCreatedAt datetime2 = NULL,
    @BeforeId bigint = NULL,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 200
        THROW 50001, 'Invalid PageSize', 1;

    SELECT TOP (@PageSize + 1)
        e.Id,
        e.EventType,
        e.ActorName,
        e.CreatedAt
    FROM dbo.AuditEvents e
    WHERE e.TenantId = @TenantId
      AND (@EventType IS NULL OR e.EventType = @EventType)
      AND (
            @BeforeCreatedAt IS NULL
            OR e.CreatedAt < @BeforeCreatedAt
            OR (e.CreatedAt = @BeforeCreatedAt AND e.Id < @BeforeId)
          )
    ORDER BY e.CreatedAt DESC, e.Id DESC;
END
```

API lấy tối đa `PageSize + 1` rows:

```text
rows[0..PageSize-1] -> data trả client
row PageSize         -> chỉ dùng để xác định hasMore
nextCursor           -> CreatedAt + Id của row cuối được trả
```

Cursor không nên là raw query fragment. Có thể encode một payload nhỏ và ký/validate nếu client không được phép sửa cursor semantics.

Index baseline cho newest-first tenant feed:

```sql
CREATE INDEX IX_AuditEvents_Tenant_CreatedAt_Id
ON dbo.AuditEvents(TenantId, CreatedAt DESC, Id DESC)
INCLUDE (EventType, ActorName);
```

Nếu EventType filter chiếm phần lớn traffic và đủ selective, benchmark thêm:

```sql
CREATE INDEX IX_AuditEvents_Tenant_EventType_CreatedAt_Id
ON dbo.AuditEvents(TenantId, EventType, CreatedAt DESC, Id DESC)
INCLUDE (ActorName);
```

Không tạo cả hai chỉ vì “có vẻ đúng”. Mỗi index làm tăng storage và write/update cost. Dùng actual workload, Query Store và execution plan để quyết định.

Search nên tách theo semantics:

```text
ActorName prefix search needed?
    -> có thể dùng normalized/prefix-searchable field + suitable index

Description contains/full-text needed?
    -> đánh giá Full-Text Search hoặc external search projection

Arbitrary substring everywhere?
    -> chấp nhận cost hoặc đổi requirement; B-tree index không biến '%term%' thành seek
```

Nếu product vẫn cần exact `totalCount`, tôi tách count khỏi every-page query. Ví dụ UI chỉ lấy count khi filter thay đổi, hoặc gọi count endpoint riêng có cancellation/timeout. Nếu business chấp nhận `hasMore`, bỏ exact count sẽ giúp pagination path nhẹ và ổn định hơn.

## Giải thích thiết kế sau khi sửa

Keyset pagination dùng **value boundary**, không dùng **row position**.

Ví dụ page trước kết thúc ở:

```text
CreatedAt = 2026-09-15T06:00:00Z
Id        = 91234567
```

Page tiếp theo yêu cầu:

```text
CreatedAt < cursor.CreatedAt
OR (CreatedAt = cursor.CreatedAt AND Id < cursor.Id)
```

Nếu events mới được insert với timestamp mới hơn cursor, chúng không đẩy vị trí của các rows cũ theo kiểu OFFSET. User có một navigation sequence ổn định hơn.

Trade-off là keyset không phù hợp với UX “nhảy trực tiếp đến page 5000” theo page number. Nếu random page access là hard requirement, OFFSET hoặc một navigation model khác vẫn có thể cần, nhưng cost phải được thừa nhận và benchmark.

`CreatedAt + Id` là một cursor hợp lý trong scenario này vì `Id` unique và monotonic; tuy nhiên cần xác minh business có cho phép `CreatedAt` bị update sau insert hay không. Nếu sort key có thể mutate, pagination stability lại cần xem xét.

## Trade-offs

- Keyset pagination có hiệu năng và stability tốt cho next/previous feed nhưng không tự nhiên cho arbitrary page number.
- Bỏ exact total count giúp query nhẹ hơn nhưng UI mất “Trang 1/134.218”. Có thể thay bằng `hasMore` hoặc count-on-demand.
- Composite index tăng read performance nhưng làm tăng storage và write amplification trên bảng audit có tốc độ insert cao.
- Full-text/search projection cải thiện contains search nhưng thêm indexing delay, failure modes và operational complexity.
- Tách list/detail projection giảm I/O nhưng thêm một API call khi user mở event chi tiết.

## Cách kiểm thử

1. **Pagination correctness test:** đọc liên tiếp nhiều pages trong khi concurrently insert events mới; không được duplicate rows trong navigation sequence và tie timestamps phải xử lý đúng bằng `Id`.
2. **Deep-pagination benchmark:** so OFFSET page 1/1000/5000 với keyset ở dataset production-like; đo duration, logical reads, CPU và memory grant.
3. **Search workload test:** benchmark no-search, EventType filter, ActorName prefix và Description contains bằng representative tenant sizes; capture actual execution plans.
4. **Index write-cost test:** đo insert throughput/log usage trước và sau composite index để tránh tối ưu reads bằng cách làm ingest vượt SLO.
5. **API contract test:** invalid/expired/tampered cursor, maximum page size và cancellation phải cho response deterministic.

## Quan sát trong production

Theo dõi:

- API p50/p95/p99 theo query shape;
- database duration và logical reads theo stored procedure/query hash;
- execution plan regressions qua Query Store;
- sort spills, memory grants và tempdb pressure nếu xuất hiện;
- rows scanned vs rows returned;
- count-query frequency và duration nếu vẫn giữ total count;
- search usage distribution;
- database CPU và IO khi traffic tăng;
- request cancellation/timeout rate;
- cursor decode/validation errors;
- index usage và write overhead sau rollout.

Một rollout tốt nên so trước/sau bằng cùng representative workload thay vì chỉ nhìn một query chạy nhanh trong SSMS.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc user phải nhập page number bất kỳ và nhảy trực tiếp tới page đó, bạn giữ correctness/performance thế nào và chấp nhận trade-off gì?
2. Nếu audit table bị partition theo thời gian, partitioning có tự động giải quyết pagination/search cost không? Bạn cần điều kiện gì để partition elimination thực sự xảy ra?
3. Nếu `CreatedAt` có thể bị sửa sau khi event được insert, bạn còn dùng `(CreatedAt, Id)` làm cursor không? Bạn sẽ thay đổi data model hoặc sort key thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker có thể giao lại message; business idempotency phải được thiết kế ở persistence/business boundary chứ không dựa vào một `AnyAsync` check.
- External side effect trước durable commit tạo failure window rất nguy hiểm. Inbox + Outbox và partner idempotency key là một cách phổ biến để làm retry an toàn hơn.
- Manual message settlement cần explicit handling cho cả normal path và duplicate path.
- Page-number pagination trên dataset thay đổi liên tục vừa có correctness problem vừa có performance problem ở deep pages.
- Deterministic ordering cần tie-breaker unique; `CreatedAt` một mình không đủ nếu nhiều rows trùng timestamp.
- `OFFSET`, exact total count và leading-wildcard search đều có thể khuếch đại database work; cần đo execution plan, logical reads và workload thật trước khi thêm index.

## Mẫu tư duy cần nhớ

1. **Thiết kế retry cùng idempotency; không coi duplicate delivery là ngoại lệ hiếm.**
2. **Tìm failure window giữa các hệ thống không có cùng transaction boundary.**
3. **Đặt invariant quan trọng ở database/contract, không chỉ ở application `if` check.**
4. **Với pagination, phân biệt row position với stable value cursor.**
5. **Đo query shape và access pattern trước khi thêm index hoặc cache.**
