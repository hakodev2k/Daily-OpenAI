## Bối cảnh

Một worker nhận `InventoryReserved` từ queue. Hệ thống có 6 replicas; một message có thể được gửi lại khi lock hết hạn hoặc process chết. Mỗi event có `EventId` duy nhất; `Sku`, `Quantity` hợp lệ về schema nhưng không bảo đảm hợp lệ về nghiệp vụ. Yêu cầu không bán quá số lượng hiện có.

## Đoạn code cần review

```csharp
public sealed record InventoryReserved(Guid EventId, string Sku, int Quantity);

public sealed class InventoryConsumer(
    ServiceBusClient bus,
    InventoryDbContext db,
    ILogger<InventoryConsumer> logger)
{
    public async Task RunAsync(CancellationToken stoppingToken)
    {
        var processor = bus.CreateProcessor("inventory-reservations",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 16
            });

        processor.ProcessMessageAsync += async args =>
        {
            var evt = args.Message.Body.ToObjectFromJson<InventoryReserved>();
            if (evt is null) return;

            var alreadyHandled = await db.ProcessedEvents
                .AnyAsync(x => x.EventId == evt.EventId);

            if (alreadyHandled)
            {
                await args.CompleteMessageAsync(args.Message);
                return;
            }

            var stock = await db.Stocks.SingleAsync(x => x.Sku == evt.Sku);
            stock.Available -= evt.Quantity;
            db.ProcessedEvents.Add(new ProcessedEvent { EventId = evt.EventId });
            await db.SaveChangesAsync();

            logger.LogInformation("Reserved {Sku} {Quantity}", evt.Sku, evt.Quantity);
            await args.CompleteMessageAsync(args.Message);
        };

        processor.ProcessErrorAsync += args =>
        {
            logger.LogError(args.Exception, "Inventory processor error");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(stoppingToken);
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Lost update / oversell

**Vấn đề:** Đọc stock rồi trừ trong bộ nhớ mà không có điều kiện atomic.  
**Tại sao xảy ra:** Hai consumer có thể đọc cùng giá trị; update cuối ghi đè update trước, hoặc đưa stock xuống âm.  
**Ảnh hưởng production:** Số lượng bán vượt tồn hoặc sai lệch reservation.  
**Cách sửa:** Dùng conditional SQL update `WHERE available >= quantity`, kiểm tra affected rows; đặt trong cùng transaction với inbox insert.

### [Critical] — Shared DbContext giữa callbacks

**Vấn đề:** Một `DbContext` bị sử dụng đồng thời bởi `MaxConcurrentCalls=16`.  
**Tại sao xảy ra:** EF Core DbContext không thread-safe.  
**Ảnh hưởng production:** Exception, tracking conflict, state corruption hoặc xử lý thất bại.  
**Cách sửa:** Tạo DI scope và DbContext riêng cho mỗi message.

### [High] — Check-then-insert không bảo đảm idempotency

**Vấn đề:** `AnyAsync` và `Add` là hai thao tác không atomic.  
**Tại sao xảy ra:** Hai worker cùng nhìn thấy chưa xử lý.  
**Ảnh hưởng production:** Double processing hoặc unique violation.  
**Cách sửa:** Unique constraint trên `EventId`; insert inbox trong transaction và xử lý duplicate constraint riêng.

### [High] — Thiếu validation nghiệp vụ

**Vấn đề:** Quantity có thể bằng 0/âm; SKU không tồn tại.  
**Tại sao xảy ra:** Deserialization không đồng nghĩa validation.  
**Ảnh hưởng production:** Tăng tồn ngoài ý muốn hoặc poison-message loop.  
**Cách sửa:** Validate và dead-letter dữ liệu không hợp lệ theo policy.

### [High] — Settlement và cancellation chưa đầy đủ

**Vấn đề:** Complete không truyền cancellation, thiếu explicit abandon/dead-letter, shutdown không dispose processor.  
**Tại sao xảy ra:** Worker chưa quản lý lifecycle và failure policy.  
**Ảnh hưởng production:** Redelivery không rõ nguyên nhân, shutdown thiếu graceful.  
**Cách sửa:** `await using` processor, stop trong finally; phân loại transient/permanent, propagate cancellation.

### [Medium] — Lock duration và thời gian xử lý

**Vấn đề:** Chưa cấu hình/quan sát auto lock renewal và handler latency.  
**Tại sao xảy ra:** Message lock có thời hạn, đặc biệt khi DB chậm.  
**Ảnh hưởng production:** Duplicate delivery tăng.  
**Cách sửa:** Cấu hình lock renewal phù hợp, đo thời gian và giảm thời gian transaction.

### [Medium] — Thiếu correlation và outcome telemetry

**Vấn đề:** Log không có EventId, MessageId, delivery count, transaction outcome.  
**Tại sao xảy ra:** Chỉ log khi thành công.  
**Ảnh hưởng production:** Không xác định được duplicate và nguyên nhân DLQ.  
**Cách sửa:** Structured logs, traces và counters theo outcome, tránh log payload nhạy cảm.

## Phiên bản đề xuất

Phần cốt lõi xử lý mỗi message (host đăng ký handler với scoped DbContext riêng, processor được quản lý bởi BackgroundService). Ví dụ giả định PostgreSQL, bảng `processed_events(event_id uuid primary key)`, `stocks(sku text primary key, available int)`; production cần migration, exception mapping và monitoring đầy đủ.

```csharp
public sealed class ReservationHandler(
    IDbContextFactory<InventoryDbContext> factory)
{
    public async Task<HandleResult> HandleAsync(
        InventoryReserved evt, CancellationToken ct)
    {
        if (evt.EventId == Guid.Empty ||
            string.IsNullOrWhiteSpace(evt.Sku) || evt.Quantity <= 0)
            return HandleResult.Invalid;

        await using var db = await factory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        // PostgreSQL: unique EventId makes duplicate detection atomic.
        var inserted = await db.Database.ExecuteSqlInterpolatedAsync(
            $"""INSERT INTO processed_events(event_id)
                VALUES ({evt.EventId})
                ON CONFLICT (event_id) DO NOTHING""", ct);
        if (inserted == 0)
        {
            await tx.RollbackAsync(ct);
            return HandleResult.Duplicate;
        }

        var updated = await db.Database.ExecuteSqlInterpolatedAsync(
            $"""UPDATE stocks SET available = available - {evt.Quantity}
                WHERE sku = {evt.Sku} AND available >= {evt.Quantity}""", ct);

        if (updated != 1)
        {
            await tx.RollbackAsync(ct);
            return HandleResult.InsufficientOrMissing;
        }

        await tx.CommitAsync(ct);
        return HandleResult.Applied;
    }
}
public enum HandleResult
{
    Applied, Duplicate, Invalid, InsufficientOrMissing
}
```

Tầng Service Bus: `Applied`/`Duplicate` thì Complete; `Invalid` thì DeadLetter với reason không chứa PII; `InsufficientOrMissing` cần contract nghiệp vụ rõ ràng (ví dụ phát rejection qua transactional outbox, rồi Complete), không tự retry vô hạn. Lỗi DB transient để message được redeliver theo retry policy; khi transaction commit thành công nhưng Complete thất bại, inbox bảo đảm redelivery không trừ lần hai. Khi commit outcome không rõ, kiểm tra inbox bằng event ID thay vì giả định rollback. Nếu cần phát sự kiện kết quả, ghi outbox trong cùng transaction và publish bất đồng bộ.

## Giải thích thiết kế sau khi sửa

Unique inbox bảo vệ trùng event; conditional update bảo vệ tồn kho dưới concurrent writers; transaction gắn cả hai vào một atomic unit. Handler độc lập transport giúp test dễ hơn. Scope riêng ngăn cross-message DbContext sharing.

## Trade-offs

Unique index và transaction tạo thêm I/O; inbox cần retention policy phù hợp với duplicate horizon. SQL trực tiếp gắn với PostgreSQL nhưng rõ atomic semantics. Outbox tăng vận hành và độ trễ eventual consistency, chỉ nên dùng nếu thực sự cần thông báo đáng tin cậy.

## Cách kiểm thử

1. **Concurrency:** 100 event khác nhau cùng SKU, stock ban đầu 10; đúng 10 applied, không âm.
2. **Duplicate:** Gửi đồng thời cùng EventId trên hai instances; chỉ một lần trừ.
3. **Failure-path:** Commit xong nhưng Complete lỗi; redelivery không trừ lại.
4. **Database:** Kill connection giữa transaction; kiểm tra rollback hoặc unknown-outcome reconciliation.
5. **Integration:** Invalid payload vào DLQ; graceful shutdown không làm mất message.

## Quan sát trong production

Theo dõi `reservation_applied_total`, `duplicate_total`, `insufficient_total`, `deadletter_total`, handler duration p95/p99, DB lock waits, transaction retries, Service Bus active messages, delivery count và DLQ depth. Correlate `EventId`, `MessageId`, trace ID trong Application Insights, không dùng SKU làm high-cardinality metric label.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cùng một SKU được cập nhật bởi hệ thống warehouse ngoài queue, invariant phải được bảo vệ ở đâu?
2. Nếu cần giữ reservation 15 phút rồi hoàn trả, bạn thiết kế state transition và idempotency thế nào?
3. Khi nào Azure Service Bus Sessions có ích, và tại sao không thay thế database constraint?

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from "vue";

type Product = { id: string; name: string; descriptionHtml: string };
const props = defineProps<{ tenantId: string; token: string }>();
const query = ref("");
const products = ref<Product[]>([]);
const selected = ref<Product | null>(null);
const loading = ref(false);
const error = ref("");

async function search() {
  loading.value = true;
  error.value = "";
  try {
    const url = "/api/catalog?tenant=" + props.tenantId +
      "&q=" + encodeURIComponent(query.value);
    const response = await fetch(url, {
      headers: { Authorization: "Bearer " + props.token }
    });
    products.value = await response.json();
  } catch (e) {
    error.value = String(e);
  } finally {
    loading.value = false;
  }
}
watch(query, search);
onMounted(search);

function openProduct(product: Product) {
  selected.value = product;
}
</script>

<template>
  <input v-model="query" placeholder="Tìm sản phẩm" />
  <p v-if="loading">Đang tải...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="p in products" :key="p.id">
      <button @click="openProduct(p)">{{ p.name }}</button>
    </li>
  </ul>
  <section v-if="selected">
    <h3>{{ selected.name }}</h3>
    <div v-html="selected.descriptionHtml"></div>
  </section>
</template>
```

## Kết quả code review tham khảo

### [Critical] — HTML injection / stored XSS

**Vấn đề:** Client gửi `tenant` do UI quyết định, nhưng không thấy backend authorize.

## Phiên bản đề xuất

Ví dụ chọn render mô tả dưới dạng text để loại bỏ HTML injection. Nếu business yêu cầu rich text, thiết kế sanitizer riêng và test policy. Backend vẫn phải enforce tenant authorization.

```vue
<script setup lang="ts">
import { ref, watch } from "vue";

type Product = { id: string; name: string; descriptionHtml: string };
const props = defineProps<{ tenantId: string; token: string }>();
const query = ref("");
const products = ref<Product[]>([]);
const selected = ref<Product | null>(null);
const loading = ref(false);
const error = ref("");

watch(
  [query, () => props.tenantId, () => props.token],
  ([q, tenant, token], _old, onCleanup) => {
    const controller = new AbortController();
    let active = true;
    const timer = setTimeout(async () => {
      if (!active) return;
      loading.value = true;
      try {
        const params = new URLSearchParams({ q, tenant });
        const response = await fetch("/api/catalog?" + params, {
          headers: { Authorization: "Bearer " + token },
          signal: controller.signal
        });
        if (!response.ok) throw new Error("HTTP " + response.status);
        const data: unknown = await response.json();
        if (!Array.isArray(data) ||
            !data.every(x => x && typeof x.id === "string" &&
              typeof x.name === "string" &&
              typeof x.descriptionHtml === "string"))
          throw new Error("Invalid catalog response");
        if (active) products.value = data as Product[];
      } catch (e) {
        if (active && !controller.signal.aborted)
          error.value = e instanceof Error ? e.message : "Request failed";
      } finally {
        if (active) loading.value = false;
      }
    }, 250);
    products.value = [];
    selected.value = null;
    error.value = "";
    loading.value = false;
    onCleanup(() => {
      active = false;
      clearTimeout(timer);
      controller.abort();
    });
  },
  { immediate: true }
);
</script>

<template>
  <input v-model="query" placeholder="Tìm sản phẩm" />
  <p v-if="loading">Đang tải...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="p in products" :key="p.id">
      <button @click="selected = p">{{ p.name }}</button>
    </li>
  </ul>
  <section v-if="selected">
    <h3>{{ selected.name }}</h3>
    <div>{{ selected.descriptionHtml }}</div>
  </section>
</template>
```

## Giải thích thiết kế sau khi sửa

Watch phụ thuộc đủ query, tenant và token. Cleanup chạy trước lần watch kế tiếp và khi component unmount; `active` guard ngăn late update ngay cả khi abort không thể hủy response đã hoàn thành. Reset dữ liệu cũ trước khi gọi lại; server phải kiểm tra membership tenant và policy của từng endpoint.

## Trade-offs

Debounce tăng độ trễ cảm nhận khoảng 250 ms nhưng giảm request; tùy traffic có thể dùng server-side rate limit hoặc query caching. Plain text làm mất formatting; sanitizer allowlist tăng complexity và phải được bảo trì. Token ở props có thể cần đánh giá lại theo mô hình auth của ứng dụng, tránh persistence không an toàn.

## Cách kiểm thử

1. **Component:** Gõ nhanh và resolve responses ngược thứ tự; chỉ kết quả mới được hiển thị.
2. **Security:** Dữ liệu chứa `<img onerror=...>` phải hiển thị như text, không thực thi.
3. **Integration:** Đổi tenant khi request đang chạy; không xuất hiện dữ liệu tenant cũ.
4. **API authorization:** Token tenant A truy vấn tenant B phải nhận 403 dù client sửa query parameter.
5. **E2E Playwright:** Giả lập 401/500, network timeout và unmount; UI không crash hoặc stale state.

## Quan sát trong production

Đo search request per user/session, HTTP 401/403/429/5xx, p95 latency, abort rate, payload validation failures, browser network waterfall và correlation ID từ frontend tới ASP.NET Core. Không log bearer token hoặc HTML chứa dữ liệu nhạy cảm. Alert trên cross-tenant authorization denial spikes.

# Tổng kết hôm nay

## Kiến thức trọng tâm
