# Code Review Challenge 1 — Cosmos DB đọc order bằng query fan-out, RU tăng mạnh và retry làm traffic tệ hơn

**Chủ đề:** C#/.NET 8, Azure Cosmos DB for NoSQL, partition key, point read, cross-partition query, RU consumption, retry, consistency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API dùng Azure Cosmos DB for NoSQL để lưu order documents cho hệ thống multi-tenant.

Container `orders` được partition theo `/tenantId`. Mỗi document có dạng rút gọn:

```json
{
  "id": "ORD-2026-900184",
  "tenantId": "TENANT-42",
  "status": "Paid",
  "customerId": "CUS-991",
  "createdAt": "2026-09-13T08:20:00Z",
  "total": 1250.50
}
```

Business requirement:

- endpoint tenant-local luôn biết `tenantId` từ authenticated server context;
- lookup một order theo `id` + tenant phải có latency ổn định;
- user không được đọc order tenant khác;
- production cần đo được RU charge và latency theo operation;
- application chạy nhiều instances;
- khi Cosmos DB bị throttling hoặc dependency latency tăng, API không được tạo retry storm;
- không được redesign toàn hệ thống chỉ để xử lý một read path đơn giản.

Production gần đây có các triệu chứng:

- request rate gần như không đổi nhưng RU consumption tăng mạnh khi số tenant và dữ liệu tăng;
- cùng endpoint lúc nhỏ container chạy nhanh, sau vài tháng p95/p99 tăng đáng kể;
- Azure Monitor cho thấy nhiều query operations dù endpoint chỉ cần đúng một document;
- team thấy HTTP `429` tăng vào giờ cao điểm;
- developer thêm retry vòng `for` 3 lần không backoff để “chống transient error”;
- một số request user tenant A có thể truyền `tenantId` khác qua query string;
- logs không ghi request charge nên team chỉ đo latency;
- một developer đề xuất tăng provisioned throughput ngay mà chưa biết operation nào đang tiêu RU.

## Đoạn code cần review

```csharp
public sealed class OrderReader
{
    private readonly Container _container;
    private readonly ILogger<OrderReader> _logger;

    public OrderReader(Container container, ILogger<OrderReader> logger)
    {
        _container = container;
        _logger = logger;
    }

    public async Task<OrderDocument?> GetAsync(
        string orderId,
        string tenantId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.id = @id")
            .WithParameter("@id", orderId);

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                using var iterator = _container.GetItemQueryIterator<OrderDocument>(
                    query,
                    requestOptions: new QueryRequestOptions
                    {
                        MaxItemCount = 100
                    });

                while (iterator.HasMoreResults)
                {
                    var page = await iterator.ReadNextAsync(cancellationToken);

                    var order = page.Resource.FirstOrDefault();
                    if (order is not null)
                    {
                        _logger.LogInformation(
                            "Found order {OrderId} for tenant {TenantId}",
                            orderId,
                            tenantId);

                        return order;
                    }
                }

                return null;
            }
            catch (CosmosException ex) when ((int)ex.StatusCode == 429)
            {
                _logger.LogWarning(
                    "Cosmos throttled order {OrderId}, retry attempt {Attempt}",
                    orderId,
                    attempt);
            }
        }

        return null;
    }
}
```

Controller gọi service như sau:

```csharp
[Authorize]
[HttpGet("orders/{orderId}")]
public async Task<IActionResult> GetOrder(
    string orderId,
    [FromQuery] string tenantId,
    CancellationToken cancellationToken)
{
    var order = await _reader.GetAsync(
        orderId,
        tenantId,
        cancellationToken);

    return order is null ? NotFound() : Ok(order);
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness, tenant isolation, RU efficiency, retry behavior và observability.
2. Giải thích vì sao query chỉ filter `id` có thể trở thành cross-partition/fan-out query khi container partition theo `/tenantId`.
3. So sánh query hiện tại với point read khi application đã có cả `id` và partition key.
4. Chỉ ra vì sao `tenantId` parameter hiện tại gần như không tham gia vào data lookup hoặc authorization.
5. Phân tích rủi ro khi client được phép tự truyền `tenantId` thay vì derive từ authenticated identity.
6. Đánh giá vòng retry 3 lần ngay lập tức khi gặp `429`.
7. Đề xuất cách đo RU charge theo request để chứng minh optimization thay vì đoán.
8. Nêu cách xử lý `404`, `429`, cancellation và dependency failure rõ ràng hơn.
9. Đề xuất implementation đơn giản hơn, ưu tiên point read cho exact lookup.
10. Nêu tests và production telemetry để xác minh latency/RU ổn định khi số partition tăng.

## Câu hỏi gợi mở

1. Với partition key `/tenantId`, Cosmos DB có đủ thông tin để route query `WHERE c.id = @id` tới đúng logical partition không?
2. Nếu đã biết `id` và `tenantId`, tại sao cần chạy query iterator?
3. `MaxItemCount = 100` có biến query này thành point read không?
4. Nếu user tenant A truyền `tenantId=TENANT-B`, code nào hiện tại ngăn đọc dữ liệu tenant B?
5. Khi gặp `429`, retry ngay lập tức có giảm hay tăng pressure lên dependency?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **data access pattern không khớp partition model**. Hãy xác định dữ liệu nào application đã biết trước khi gọi Cosmos DB.

Với một exact item lookup, hãy phân biệt rõ **point read bằng `id` + partition key** với một SQL-style query. Sau đó mới đánh giá retry và RU.

## Kết quả code review tham khảo

### Critical — Tenant isolation không được enforce trong query

**Vấn đề:** `tenantId` được truyền vào method nhưng query chỉ filter `c.id = @id`.

**Tại sao xảy ra:** Security context và data-access predicate bị tách rời. Method signature tạo cảm giác tenant-aware nhưng implementation không dùng partition key để giới hạn lookup.

**Ảnh hưởng production:** Nếu `id` không globally unique theo business contract hoặc code path khác có bug, cross-tenant data exposure có thể xảy ra. Ngay cả khi `id` hiện globally unique, authorization invariant vẫn không được enforce rõ ràng.

**Cách sửa:** Derive tenant từ trusted authenticated context và dùng nó làm partition key trong read operation. Không nhận tenant authority từ client cho tenant-local endpoint.

### Critical — Exact lookup đang dùng query thay vì point read

**Vấn đề:** Endpoint cần một document cụ thể nhưng dùng `GetItemQueryIterator` với `SELECT * WHERE c.id = @id`.

**Tại sao xảy ra:** Code áp dụng relational-query mental model cho access pattern đã biết đầy đủ item identity.

**Ảnh hưởng production:** Query có overhead và có thể phải kiểm tra nhiều partitions khi partition key không được chỉ ra trong routing predicate. Khi container lớn dần, RU và latency có thể tăng rõ rệt.

**Cách sửa:** Nếu biết `id` và full partition key, dùng point read API với hai giá trị đó. Microsoft documentation xác định point read bằng item `id` + partition key là read pattern hiệu quả nhất cho exact lookup.

### High — Query không cung cấp partition key nên có thể fan-out

**Vấn đề:** `QueryRequestOptions` không chỉ ra partition key và SQL query cũng không filter `tenantId`.

**Tại sao xảy ra:** Cosmos DB không có information để target đúng logical partition từ query hiện tại.

**Ảnh hưởng production:** Query engine có thể cần fan-out/cross-partition work; RU cost tăng theo footprint của container thay vì giữ gần với một exact lookup.

**Cách sửa:** Với exact item lookup, tránh query hoàn toàn. Với query thật sự cần thiết, constrain bằng partition-key-aware access pattern khi business query cho phép.

### High — Client-controlled `tenantId` là security authority sai chỗ

**Vấn đề:** Controller nhận `tenantId` từ query string và truyền xuống repository.

**Tại sao xảy ra:** Caller-controlled input được dùng như thể nó là identity context.

**Ảnh hưởng production:** Một user có thể thử arbitrary tenant identifiers; future refactor rất dễ biến điều này thành direct cross-tenant read.

**Cách sửa:** Resolve current tenant từ validated claims/application identity mapping. Chỉ privileged support/system flow mới được chọn target tenant, qua explicit authorization policy.

### High — Retry `429` ngay lập tức tạo thêm pressure

**Vấn đề:** Khi dependency báo throttling, code lập tức chạy lại query trong vòng lặp mà không có delay/backoff/jitter hoặc sử dụng retry guidance từ SDK/runtime configuration.

**Tại sao xảy ra:** Retry được xem như “thử lại càng nhanh càng tốt”.

**Ảnh hưởng production:** Nhiều application instances đồng thời retry có thể làm throttling kéo dài, tăng latency và request volume.

**Cách sửa:** Không tự thêm blind retry loop nếu SDK retry policy đã xử lý phù hợp. Nếu application cần policy riêng, phải honor dependency retry signal/backoff, đặt retry budget và theo dõi end-to-end latency. Không retry vô hạn sau client cancellation hoặc request deadline.

### High — Nuốt `429` cuối cùng và trả `null`

**Vấn đề:** Sau 3 attempts, method trả `null`, khiến controller trả `404`.

**Tại sao xảy ra:** Dependency failure bị map nhầm thành business absence.

**Ảnh hưởng production:** User thấy “order không tồn tại” khi thực tế storage đang throttled. Monitoring và incident diagnosis cũng bị sai.

**Cách sửa:** Phân biệt not-found với dependency unavailable/throttled. Trả error contract phù hợp như `503` khi application không thể hoàn thành read do dependency failure; policy cụ thể phụ thuộc API contract.

### Medium — Không quan sát RU charge

**Vấn đề:** Log chỉ ghi `OrderId`, tenant và attempt.

**Tại sao xảy ra:** Team chỉ đo HTTP latency mà không instrument storage-cost signal.

**Ảnh hưởng production:** Khó chứng minh query fan-out đang gây RU spike hoặc optimization có hiệu quả.

**Cách sửa:** Ghi/aggregate request charge từ Cosmos response, operation type, status code, latency và partition context ở mức metadata phù hợp. Tránh high-cardinality uncontrolled logging nếu traffic lớn.

### Medium — `MaxItemCount = 100` không phù hợp access intent

**Vấn đề:** Code cấu hình page size cho operation vốn chỉ cần một item.

**Tại sao xảy ra:** Query abstraction che mất business semantics.

**Ảnh hưởng production:** Không giải quyết fan-out và làm review khó nhận ra rằng operation nên là point read.

**Cách sửa:** Dùng exact read API. Chỉ tune page size khi thật sự có paginated query workload.

### Medium — `SELECT *` materialize toàn document dù endpoint có thể chỉ cần DTO

**Vấn đề:** Nếu document lớn nhưng endpoint chỉ cần vài fields, code luôn deserialize toàn document.

**Tại sao xảy ra:** Storage model và API model bị dùng chung.

**Ảnh hưởng production:** Tăng payload/deserialization cost. Với point read, RU chủ yếu vẫn phụ thuộc item size; projection không biến point read thành “rẻ hơn item size”, nên cần đánh giá data model nếu document quá lớn.

**Cách sửa:** Trước hết sửa access pattern. Nếu item quá lớn so với read use case, cân nhắc document modeling dựa trên measured workload, không tối ưu mù.

### Low — Log chưa phân biệt operation path và failure semantics

**Vấn đề:** Không có structured fields như operation=`point-read/query`, request charge, status/substatus, retry count, elapsed time.

**Tại sao xảy ra:** Storage telemetry chưa được coi là part of design.

**Ảnh hưởng production:** Khi RU/latency tăng, team khó xác định call pattern nào thay đổi.

**Cách sửa:** Chuẩn hóa telemetry cho Cosmos dependency calls và correlation với API request.

## Phiên bản đề xuất

Giả sử application đã validate identity và có trusted `CurrentTenantId`, exact lookup có thể đơn giản như sau:

```csharp
public sealed class OrderReader
{
    private readonly Container _container;
    private readonly ILogger<OrderReader> _logger;

    public OrderReader(Container container, ILogger<OrderReader> logger)
    {
        _container = container;
        _logger = logger;
    }

    public async Task<OrderDocument?> GetAsync(
        string orderId,
        string tenantId,
        CancellationToken cancellationToken)
    {
        try
        {
            var response = await _container.ReadItemAsync<OrderDocument>(
                id: orderId,
                partitionKey: new PartitionKey(tenantId),
                cancellationToken: cancellationToken);

            _logger.LogInformation(
                "Cosmos point read order {OrderId} tenant {TenantId} RU {RequestCharge}",
                orderId,
                tenantId,
                response.RequestCharge);

            return response.Resource;
        }
        catch (CosmosException ex)
            when (ex.StatusCode == HttpStatusCode.NotFound)
        {
            return null;
        }
    }
}
```

Controller tenant-local không cần nhận `tenantId` từ client:

```csharp
[Authorize]
[HttpGet("orders/{orderId}")]
public async Task<IActionResult> GetOrder(
    string orderId,
    CancellationToken cancellationToken)
{
    var tenantId = _currentUser.TenantId;

    try
    {
        var order = await _reader.GetAsync(
            orderId,
            tenantId,
            cancellationToken);

        return order is null ? NotFound() : Ok(order);
    }
    catch (CosmosException ex) when ((int)ex.StatusCode == 429)
    {
        _logger.LogWarning(
            "Cosmos throttled order read for tenant {TenantId}",
            tenantId);

        return Problem(
            statusCode: StatusCodes.Status503ServiceUnavailable,
            title: "Order storage is temporarily unavailable");
    }
}
```

Đoạn trên minh họa semantics chính, không khẳng định application phải catch `429` tại controller. Trong production, retry/resilience policy thường nên tập trung ở dependency layer và phải kiểm tra behavior của SDK version/configuration đang dùng trước khi thêm custom retry.

Nếu `tenantId` là partition key và `id` đã biết, point read là lựa chọn tự nhiên. Nếu business query là “tìm orders theo customer/date/status”, đó là workload khác và cần đánh giá partition strategy/index/query design riêng thay vì cố ép mọi query thành point read.

## Giải thích thiết kế sau khi sửa

Data access bây giờ khớp với container partitioning: application đưa cả item id và partition key cho SDK. Điều này giúp routing chính xác và tránh query fan-out cho exact lookup.

Tenant security context đến từ authenticated server-side abstraction, không từ query parameter. Nhờ vậy authorization invariant rõ hơn và data access tự nhiên gắn với đúng logical partition.

`404` chỉ dùng cho item thật sự không tồn tại trong partition đã xác định. Dependency throttling/failure giữ semantics riêng để client và monitoring không nhầm “storage failure” với “business absence”.

Request charge được instrument để team có thể so sánh trước/sau optimization. Đây là evidence tốt hơn việc chỉ nhìn tổng RU toàn account.

## Trade-offs

Point read yêu cầu caller biết full partition key. Nếu API chỉ có `orderId` nhưng không biết tenant, bạn phải thay đổi lookup contract, duy trì mapping/index khác, hoặc chấp nhận query cost; lựa chọn phụ thuộc business identity model.

Partition key `/tenantId` phù hợp khi phần lớn workload tenant-local và distribution đủ tốt. Nếu một tenant cực lớn/hot gây partition pressure, đó là partition-design problem khác; không nên kết luận chỉ từ endpoint này.

Tăng throughput có thể vẫn cần nếu workload thật sự tăng. Nhưng scaling throughput trước khi sửa một fan-out read pattern có thể che inefficiency và tăng cost lâu dài.

Custom retry có thể hữu ích trong một số case, nhưng thêm retry ở nhiều tầng dễ nhân số attempts. Cần biết SDK behavior và thiết kế một retry budget thống nhất.

## Cách kiểm thử

1. **Integration test:** tạo hai tenants có order ids khác nhau; xác minh tenant A không thể đọc order tenant B khi endpoint không nhận tenant id từ client.
2. **RU comparison test:** cùng một known item, đo request charge của query cũ và point read mới trên representative dataset; lưu evidence thay vì dùng giả định chung chung.
3. **Scale test:** tăng số logical partitions/data volume và xác minh latency/RU của point read giữ ổn định hơn query fan-out.
4. **Failure-path test:** mô phỏng throttling/dependency error; xác minh API không trả `404` và không tạo tight retry loop.
5. **Cancellation test:** hủy request giữa dependency call; xác minh cancellation được propagate và không tiếp tục retry không cần thiết.

## Quan sát trong production

Theo dõi:

- Cosmos operation type (`ReadItem`, query);
- request charge theo operation;
- p50/p95/p99 dependency latency;
- status code và `429` rate;
- retry count/end-to-end attempt count;
- request volume theo tenant ở mức aggregate phù hợp;
- API `404` vs dependency `503` rate;
- total RU consumption và normalized RU utilization;
- correlation từ API request → Cosmos dependency call;
- hot partition/tenant signal nếu workload phân bố lệch.

Alert khi request charge của exact lookup tăng bất thường, `429` tăng kéo dài hoặc retry amplification xuất hiện sau dependency degradation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu API chỉ biết `orderId` nhưng không biết partition key, bạn sẽ thay đổi data model hoặc lookup flow thế nào mà không tạo một global cross-partition scan?
2. Nếu một tenant chiếm 70% traffic và tạo hot partition, bạn đánh giá lại partition strategy dựa trên evidence nào?
3. Khi nào tăng provisioned throughput là đúng quyết định dù code đã dùng point reads tối ưu?

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì dùng chung account và phụ thuộc test order

## Bối cảnh

Một ASP.NET Core + React back-office application có Playwright E2E suite chạy trong CI trước production deployment.

Suite hiện có khoảng 180 tests và được chạy parallel để giảm thời gian pipeline. Team dùng một shared test account `qa-admin@example.test` và một shared project tên `E2E Project` trong test environment.

Production pipeline gần đây thường phải rerun E2E stage vì:

- test pass gần như 100% khi developer chạy một file riêng trên local;
- chạy full suite trên CI có 5–15 tests flaky;
- lỗi thay đổi theo lần chạy: khi thì project không tồn tại, khi thì status sai, khi thì login state mất;
- một test delete project trong khi test khác đang edit cùng project;
- một số tests chỉ pass nếu test tạo dữ liệu chạy trước;
- team cấu hình retries=2 và thấy pipeline “xanh hơn”, nhưng không biết root cause;
- file chứa authenticated storage state đang được commit vào repository để CI dùng cho nhanh;
- trace/video chỉ bật khi chạy local vì team sợ artifact CI quá lớn;
- test thường dùng `waitForTimeout(2000)` để đợi UI cập nhật.

Requirement:

- suite phải chạy độc lập với test order;
- parallel execution không được làm tests phá state của nhau;
- CI failure phải có đủ evidence để debug;
- authentication setup không được làm lộ reusable credentials/session artifacts;
- retries có thể dùng như diagnostic/safety net nhưng không được che flaky test design;
- không cần xây custom testing framework nếu Playwright primitives đã đủ.

1. Xác định các nguyên nhân flakiness, shared-state coupling, authentication risk và CI observability gap.
2. Giải thích vì sao ba tests không thực sự độc lập dù Playwright tạo isolated browser context cho từng test.
3. Phân biệt browser/session isolation với backend data isolation.
4. Chỉ ra vì sao shared `projectName` làm parallel execution trở nên nondeterministic.
5. Đánh giá `waitForTimeout(2000)` và đề xuất web-first synchronization tốt hơn.
6. Phân tích việc commit authenticated `storageState` vào repository.
7. Đánh giá retries=2: khi nào hữu ích và khi nào đang che root cause.
8. Đề xuất strategy cho per-test test data hoặc API fixture để mỗi test tự sở hữu dữ liệu.
9. Đề xuất authentication setup nhanh nhưng không share mutable user/session state theo cách nguy hiểm.
10. Nêu artifacts/telemetry cần capture trên CI để debug failed first attempt.

## Câu hỏi gợi mở

1. BrowserContext mới có làm database record `E2E Project` trở thành riêng cho từng test không?
2. Nếu `delete project` chạy trước `edit project`, điều gì xảy ra?
3. Nếu hai CI workers cùng tạo `E2E Project`, test nào “sở hữu” record đó?
4. Fixed sleep 2 giây đang chờ một condition cụ thể hay chỉ hy vọng UI đã xong?
5. `storageState` có thể chứa cookies/headers đủ để impersonate account không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **test isolation không chỉ là browser isolation**. Hãy kiểm tra mọi mutable dependency mà tests đang dùng chung: account, database row, server state và environment.

### Gợi ý 2

Một E2E test ổn định nên tự arrange dữ liệu cần thiết, chờ observable condition và để lại đủ trace để điều tra failure. Đừng dùng test order như fixture system.

## Kết quả code review tham khảo

### Critical — Tests phụ thuộc thứ tự create → edit → delete

**Vấn đề:** `edit project` giả định project đã tồn tại; `delete project` cũng giả định state được tạo bởi test khác.

**Tại sao xảy ra:** Test suite dùng previous test output như setup fixture thay vì mỗi test tự arrange state.

**Ảnh hưởng production:** Khi chạy parallel, shard, retry hoặc chạy riêng một test, ordering assumption bị phá vỡ và suite flaky.

**Cách sửa:** Mỗi test tạo project riêng trước action chính, hoặc dùng API/database test fixture được kiểm soát. Cleanup phải gắn với test-owned data và không ảnh hưởng test khác.

### Critical — Shared backend record gây race giữa parallel tests

**Vấn đề:** Tất cả tests dùng cùng `projectName = 'E2E Project'`.

**Tại sao xảy ra:** Browser contexts isolate cookies/local storage, nhưng không isolate shared backend database.

**Ảnh hưởng production:** Test A có thể rename/delete record trong khi test B đang đọc hoặc edit. Kết quả phụ thuộc timing.

**Cách sửa:** Tạo unique test data per test, ví dụ `E2E-${testInfo.workerIndex}-${uuid}` hoặc server-generated ID. Prefer resource ID sau create thay vì tìm bằng display name không unique.

### High — Commit authenticated `storageState` vào repository

**Vấn đề:** File auth state được version-control để CI tái sử dụng.

**Tại sao xảy ra:** Optimization tốc độ login được ưu tiên hơn credential/session hygiene.

**Ảnh hưởng production:** Auth state có thể chứa cookies/headers có khả năng impersonate test account. Repo access mở rộng blast radius và state có thể hết hạn bất ngờ.

**Cách sửa:** Generate auth state trong CI/setup step từ secret store hoặc test identity flow; thêm auth directory vào `.gitignore`. Playwright documentation cũng cảnh báo storage state có thể chứa sensitive cookies/headers và không nên commit.

### High — Retry đang che deterministic race

**Vấn đề:** `retries: 2` làm pipeline xanh hơn nhưng không loại bỏ shared-state bug.

**Tại sao xảy ra:** Race timing thay đổi giữa attempts nên retry có thể pass.

**Ảnh hưởng production:** Team mất niềm tin vào suite; release gate “green” không phản ánh deterministic quality.

**Cách sửa:** Giữ retry có giới hạn nếu cần thu thập diagnostic signal, nhưng track flaky-on-first-attempt rate và fail/triage recurring flakes. Sửa isolation trước khi dùng retries như stability strategy.

### High — `waitForTimeout(2000)` là timing guess

**Vấn đề:** Test sleep cố định thay vì chờ observable application state.

**Tại sao xảy ra:** Code giả định 2 giây đủ cho mọi CI load/network/backend latency.

**Ảnh hưởng production:** CI chậm hơn local có thể fail; nếu UI xong sau 100 ms thì test vẫn lãng phí gần 2 giây.

**Cách sửa:** Dùng locator assertions/web-first waiting, chờ URL/state/response phù hợp hoặc element semantics cụ thể. Chỉ dùng fixed sleep cho intentional timing scenarios rất hiếm.

### High — Shared account có thể tạo state collision ngoài browser

**Vấn đề:** Nhiều tests dùng cùng user account.

**Tại sao xảy ra:** Test identity có thể sở hữu mutable server-side preferences, permissions, recently-used data hoặc concurrency-sensitive session state.

**Ảnh hưởng production:** Tests gây ảnh hưởng qua backend dù browser context riêng.

**Cách sửa:** Nếu tests chỉ read hoặc account không có mutable state, shared auth có thể chấp nhận. Nếu tests mutate user-owned state, dùng account pool/per-worker identity hoặc data ownership model rõ ràng. Không tự động tạo hàng trăm accounts nếu không cần.

### Medium — Selector theo text/name dễ ambiguity

**Vấn đề:** `page.click('text=...')` tìm resource qua display name shared.

**Tại sao xảy ra:** Test không giữ stable resource identifier.

**Ảnh hưởng production:** Duplicate names hoặc localization/UI changes làm test click sai element.

**Cách sửa:** Sau arrange, giữ resource id/URL và dùng accessible role/test id hợp lý. Test user behavior nhưng tránh selector mơ hồ.

### Medium — Không capture trace/video trên CI failure

**Vấn đề:** `trace: 'off'`, `video: 'off'` cho môi trường flaky nhất.

**Tại sao xảy ra:** Team tránh artifact size bằng cách tắt hoàn toàn diagnostics.

**Ảnh hưởng production:** Rerun mất evidence của first failure, làm race khó điều tra.

**Cách sửa:** Bật artifact có chọn lọc, ví dụ trace on-first-retry/retain-on-failure tùy policy phù hợp; video/screenshot chỉ khi failure nếu cần. Chọn retention phù hợp thay vì tắt toàn bộ.

### Medium — UI login duplicated trong test nhưng config lại dùng `storageState`

**Vấn đề:** `create project` tự login trong khi suite config đã load auth state; các tests khác lại dựa ngầm vào storage state.

**Tại sao xảy ra:** Authentication strategy không thống nhất.

**Ảnh hưởng production:** Một test kiểm tra login side effect, tests khác phụ thuộc stale auth file; debug behavior không nhất quán.

**Cách sửa:** Tách authentication setup project/fixture khỏi business tests. Chỉ tests chuyên auth mới đi qua login UI; business E2E dùng state được tạo an toàn cho run hiện tại.

### Low — Cleanup không có ownership semantics

**Vấn đề:** Delete test vừa là business test vừa vô tình cleanup shared fixture.

**Tại sao xảy ra:** Test lifecycle và business behavior bị trộn.

**Ảnh hưởng production:** Một failure giữa suite để lại dirty data hoặc xóa dữ liệu test khác.

**Cách sửa:** Cleanup test-owned resources trong fixture/teardown có best-effort semantics. Test “delete project” vẫn test delete behavior trên resource riêng của nó.

## Phiên bản đề xuất

Một cách đơn giản là dùng API fixture để arrange project riêng cho từng test, sau đó test UI behavior trên resource đó.

```ts
import { test, expect } from '@playwright/test'
import crypto from 'node:crypto'

async function createProject(request: any, name: string) {
  const response = await request.post('/api/projects', {
    data: { name }
  })

  expect(response.ok()).toBeTruthy()
  return await response.json() as { id: string; name: string }
}

async function deleteProjectBestEffort(request: any, id: string) {
  await request.delete(`/api/projects/${id}`)
}

test('edit project', async ({ page, request }, testInfo) => {
  const name = `E2E-${testInfo.workerIndex}-${crypto.randomUUID()}`
  const project = await createProject(request, name)

  try {
    await page.goto(`/projects/${project.id}`)

    const updatedName = `${name}-updated`
    await page.getByLabel('Name').fill(updatedName)
    await page.getByRole('button', { name: 'Save' }).click()

    await expect(page.getByText(updatedName)).toBeVisible()
  } finally {
    await deleteProjectBestEffort(request, project.id)
  }
})

test('delete project', async ({ page, request }, testInfo) => {
  const name = `E2E-${testInfo.workerIndex}-${crypto.randomUUID()}`
  const project = await createProject(request, name)

  await page.goto(`/projects/${project.id}`)
  await page.getByRole('button', { name: 'Delete' }).click()
  await page.getByRole('button', { name: 'Confirm' }).click()

  await expect(page).toHaveURL(/\/projects$/)

  const response = await request.get(`/api/projects/${project.id}`)
  expect(response.status()).toBe(404)
})
```

Authentication state nên được tạo trong setup cho từng CI run từ secret-managed test identity, không commit session artifact:

```ts
export default defineConfig({
  fullyParallel: true,
  retries: process.env.CI ? 1 : 0,
  use: {
    storageState: 'playwright/.auth/admin.json',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
    video: 'retain-on-failure'
  }
})
```

File `playwright/.auth/admin.json` trong ví dụ phải được generate runtime và ignored khỏi source control. Exact artifact policy có thể điều chỉnh theo storage cost và debugging need.

Nếu test environment không cho phép API test setup, có thể tạo resource qua UI trong `beforeEach`; test sẽ chậm hơn nhưng vẫn phải dùng unique data per test và không phụ thuộc test khác.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu resource riêng nên parallel workers không tranh cùng row. Test có thể chạy riêng, chạy đảo thứ tự hoặc shard mà vẫn giữ semantics.

BrowserContext isolation vẫn hữu ích cho cookies/local storage/session, nhưng backend data isolation được giải quyết riêng bằng unique test-owned resources.

Authentication setup được tách khỏi business test. Điều này giảm login overhead mà không cần commit reusable session state vào Git.

Web-first assertions thay fixed sleep. Test chờ condition thực tế thay vì thời gian giả định, nên vừa nhanh hơn vừa ít flaky hơn.

CI giữ trace/screenshot/video theo failure policy để first failure có evidence. Retry trở thành diagnostic fallback, không phải cơ chế làm test “ổn định giả”.

## Trade-offs

Per-test resource creation tăng số API/database operations và có thể kéo dài suite. Có thể tối ưu bằng per-worker fixtures nếu resource thật sự không mutable hoặc ownership vẫn tách biệt, nhưng phải chứng minh không tạo coupling.

Shared account không luôn sai. Nếu account chỉ cung cấp authentication và mọi mutable business data là per-test, shared auth có thể đủ đơn giản. Nếu account có mutable server-side settings, cần per-worker/per-role accounts.

UI-only setup gần hơn với end-user path nhưng chậm và làm nhiều tests kiểm tra cùng login/create flow. API setup nhanh hơn và giúp test tập trung vào behavior chính, nhưng phải có một số E2E riêng cover create/login flows.

Artifacts tăng CI storage. Nên retain theo failure/retry thay vì record mọi test vô thời hạn.

## Cách kiểm thử

1. **Parallel stress:** chạy cùng suite nhiều lần với `fullyParallel` và nhiều workers; xác minh không còn collision trên project name/id.
2. **Order independence:** chạy từng test riêng, shuffle/shard files; mỗi test vẫn pass mà không cần test khác chạy trước.
3. **Failure diagnostics:** cố tình làm một assertion fail; xác minh CI lưu trace/screenshot/video theo policy và đủ để xem request/UI state.
4. **Auth hygiene test:** rotate/remove generated storage state giữa runs; setup phải tạo state mới và repo không chứa auth artifact.
5. **Slow-backend test:** inject network delay; web-first assertions vẫn chờ đúng condition trong timeout budget thay vì phụ thuộc 2-second sleep.

## Quan sát trong production

Với test pipeline, theo dõi:

- first-attempt pass rate;
- retry pass rate/flaky rate;
- top failing tests theo tuần;
- failure category: assertion, timeout, environment, shared data, auth;
- test duration p50/p95;
- artifact availability cho first failure;
- worker count và collision/error rate;
- test-data cleanup backlog;
- environment API latency/error rate trong thời gian suite chạy.

Một suite “xanh sau retry” nhưng first-attempt flaky rate tăng vẫn phải được coi là quality signal xấu.

## Câu hỏi phỏng vấn mở rộng

2. Nếu API fixture để tạo test data bypass một business validation quan trọng, bạn sẽ phân chia test coverage như thế nào?
3. Nếu E2E suite tăng từ 180 lên 2.000 tests, bạn tối ưu runtime thế nào mà không hy sinh isolation và diagnostic quality?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB access pattern phải phù hợp partition model; exact lookup đã biết `id` + partition key nên ưu tiên point read thay vì generic query.
- RU phải được đo theo operation trước khi quyết định tăng throughput hoặc thêm cache.
- Dependency throttling không nên được xử lý bằng tight retry loop; retry cần budget, backoff và failure semantics rõ ràng.
- Test isolation có hai lớp khác nhau: browser/session isolation và backend data isolation.
- Playwright BrowserContext không tự cô lập database state; parallel E2E cần test-owned mutable resources.
- Retry không sửa deterministic race; first-attempt flakiness vẫn là engineering signal cần xử lý.

## Mẫu tư duy cần nhớ

- **Match data access pattern to partition design.**
- **Measure RU/latency before scaling cost.**
- **Do not confuse dependency failure with business not-found.**
- **Isolate all mutable test state, not only browser state.**
- **Wait for observable conditions, not arbitrary time.**
