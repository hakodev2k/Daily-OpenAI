# Code Review Challenge 1 — Redis cache-aside làm rò dữ liệu tenant và trả dữ liệu cũ dưới concurrency

**Chủ đề:** ASP.NET Core, EF Core, Redis, multi-tenancy, cache consistency, concurrency, security  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–12 vấn đề

## Bối cảnh

Một ASP.NET Core API trên .NET 8 phục vụ product catalog cho một nền tảng multi-tenant. SQL Server là source of truth. Redis được thêm vào để giảm latency cho endpoint đọc product detail.

Mỗi product có `Id`, `TenantId`, `Name`, `Price`, `Status` và `Version`. `Version` tăng mỗi lần product được cập nhật.

Application chạy nhiều instances sau load balancer. Traffic production có burst lớn khi campaign bắt đầu. Redis đôi khi timeout hoặc bị failover. Business yêu cầu:

- user của tenant A tuyệt đối không được đọc dữ liệu tenant B;
- product update phải phản ánh “gần như ngay lập tức” trong API;
- nếu Redis lỗi, core read API nên ưu tiên tiếp tục phục vụ từ SQL nếu SQL vẫn khỏe;
- không được tạo retry/caching pattern khiến SQL hoặc Redis bị stampede khi cache miss hàng loạt.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public ProductService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<ProductDto?> GetAsync(Guid tenantId, Guid productId)
    {
        var cacheKey = $"product:{productId}";
        var cached = await _cache.GetStringAsync(cacheKey);

        if (cached != null)
        {
            return JsonSerializer.Deserialize<ProductDto>(cached);
        }

        var product = await _db.Products
            .AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == productId);

        if (product == null)
        {
            return null;
        }

        var dto = new ProductDto(
            product.Id,
            product.TenantId,
            product.Name,
            product.Price,
            product.Status,
            product.Version);

        await _cache.SetStringAsync(
            cacheKey,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(1)
            });

        return dto;
    }

    public async Task UpdatePriceAsync(
        Guid tenantId,
        Guid productId,
        decimal newPrice)
    {
        var product = await _db.Products
            .SingleAsync(x => x.Id == productId);

        product.Price = newPrice;
        product.Version++;

        await _db.SaveChangesAsync();
        await _cache.RemoveAsync($"product:{productId}");
    }
}
```

## Kết quả code review tham khảo

### Critical — Tenant isolation không được enforce ở database query

**Vấn đề:** `tenantId` được truyền vào method nhưng query chỉ dùng `x.Id == productId`.

**Tại sao xảy ra:** Code giả định `productId` đủ để xác định resource và bỏ qua tenant boundary. Nếu caller có thể cung cấp một `productId` thuộc tenant khác, query vẫn trả entity đó.

**Ảnh hưởng production:** Đây là lỗi authorization/data-isolation nghiêm trọng. User tenant A có thể đọc hoặc update dữ liệu tenant B nếu biết/đoán được ID hoặc ID bị lộ qua nơi khác.

**Cách sửa:** Tenant phải được lấy từ trusted authenticated context hoặc được validate rõ với claims/policy, sau đó mọi resource query phải bao gồm `TenantId == currentTenantId`. Defense-in-depth có thể thêm global query filter hoặc repository/query abstraction tenant-aware, nhưng không được dùng abstraction để che mất authorization semantics.

### Critical — Cache key không chứa tenant identity

**Vấn đề:** Key là `product:{productId}`.

**Tại sao xảy ra:** Cache namespace không phản ánh security partition của dữ liệu.

**Ảnh hưởng production:** Nếu ID có thể trùng theo tenant hoặc dữ liệu bị cache sai do query bug, tenant khác có thể nhận trực tiếp serialized DTO của tenant trước mà không chạm database. Cache biến lỗi authorization thành data leak nhanh và khó quan sát hơn.

**Cách sửa:** Cache key phải chứa tenant scope, ví dụ `product:{tenantId}:{productId}`. Quan trọng hơn, tenant ID phải là trusted/authorized identity, không chỉ là parameter do client tự khai báo.

### High — Update path cũng không enforce tenant boundary

**Vấn đề:** `UpdatePriceAsync` dùng `SingleAsync(x => x.Id == productId)`.

**Tại sao xảy ra:** Write path lặp lại cùng assumption sai như read path.

**Ảnh hưởng production:** Cross-tenant modification có thể xảy ra, nghiêm trọng hơn stale read vì làm hỏng source of truth.

**Cách sửa:** Query update bằng cả tenant + product ID, kết hợp authorization policy và xử lý `not found`/`forbidden` theo contract đã chọn để tránh resource enumeration không cần thiết.

### High — Race “stale fill after invalidation” có thể đưa dữ liệu cũ trở lại Redis

**Vấn đề:** Reader cache miss → đọc SQL version 10. Trước khi reader ghi Redis, writer commit version 11 và `RemoveAsync`. Reader sau đó ghi version 10 vào cache với TTL 1 giờ.

**Tại sao xảy ra:** Delete-after-write không serialize với concurrent cache fills. Invalidation hoàn tất trước không ngăn một reader đang giữ snapshot cũ ghi cache sau đó.

**Ảnh hưởng production:** API có thể trả giá/status cũ trong thời gian dài dù DB đã đúng. Với campaign/price updates, đây là lỗi correctness/business-visible.

**Cách sửa:** Chọn consistency strategy rõ ràng. Một phương án là cache value mang `Version` và dùng conditional update trong Redis để version cũ không overwrite version mới. Writer sau DB commit ghi cache version mới; reader chỉ được fill nếu version của nó không thấp hơn version hiện tại. Nếu platform không cần cache cho endpoint này, bỏ cache cũng là lựa chọn hợp lệ và đơn giản hơn. Distributed lock chỉ nên dùng khi hiểu failure/ownership semantics; lock không tự động giải quyết mọi consistency problem.

### High — Redis đang nằm trên critical path mà không có graceful fallback

**Vấn đề:** `GetStringAsync`, `SetStringAsync` và `RemoveAsync` đều có thể throw/timeout và làm request fail.

**Tại sao xảy ra:** Cache được xử lý như dependency bắt buộc thay vì optimization layer.

**Ảnh hưởng production:** Redis failover hoặc network degradation có thể biến thành API outage dù SQL vẫn khỏe.

**Cách sửa:** Với read path, bounded cache timeout và fallback về SQL nếu cache lỗi. Cache write sau khi lấy DB result có thể best-effort, được log/metric rõ. Write business transaction không nên bị rollback về mặt business chỉ vì cache invalidation/update lỗi; thay vào đó cần repair/freshness strategy an toàn.

### High — Cache stampede khi hot key expire/miss

**Vấn đề:** Mọi request miss đều query SQL và cùng serialize/write cùng key.

**Tại sao xảy ra:** Không có request coalescing/single-flight hoặc coordination cho hot misses.

**Ảnh hưởng production:** Khi nhiều keys expire cùng lúc hoặc Redis flush/failover, database load có thể spike mạnh và gây cascading latency.

**Cách sửa:** Có thể dùng per-key single-flight ở từng instance, distributed coordination cho hot keys nếu thật sự cần, TTL jitter, proactive refresh hoặc bỏ cache cho workload không đáng cache. Correctness phải độc lập với anti-stampede optimization.

### Medium — TTL cố định một giờ quá dài so với freshness requirement

**Vấn đề:** TTL dài và đồng đều, trong khi system dựa chủ yếu vào invalidation.

**Tại sao xảy ra:** Nếu invalidation thất bại/race, stale data tồn tại lâu; đồng thời nhiều keys có thể expire gần nhau nếu được tạo cùng đợt.

**Ảnh hưởng production:** Tăng stale window và có thể tạo synchronized expiry burst.

**Cách sửa:** TTL là safety net, chọn theo SLO và thêm jitter. Không dùng TTL để thay thế correctness/invalidation strategy.

### Medium — Không propagate `CancellationToken`

**Vấn đề:** Redis/EF calls không nhận cancellation từ request.

**Tại sao xảy ra:** Method signatures không nhận token.

**Ảnh hưởng production:** Client disconnect/timeout nhưng DB/cache work vẫn tiếp tục, làm lãng phí connection/thread/IO budget dưới load.

**Cách sửa:** Nhận `CancellationToken` và truyền xuống EF/cache APIs nơi implementation hỗ trợ.

### Medium — `Version++` là concurrency strategy yếu nếu có concurrent writers

**Vấn đề:** Hai writers có thể đọc cùng version rồi cùng tăng cục bộ nếu entity không dùng concurrency token/conditional update phù hợp.

**Tại sao xảy ra:** Application counter không tự tạo optimistic concurrency guarantee.

**Ảnh hưởng production:** Lost update hoặc version semantics không đáng tin, làm cache-version strategy sai theo.

**Cách sửa:** Dùng database-backed concurrency token phù hợp, ví dụ SQL Server `rowversion` hoặc một numeric version được cập nhật bằng conditional statement/EF concurrency token. Xử lý `DbUpdateConcurrencyException` theo business semantics.

### Low — Serialization contract/cache schema chưa có versioning strategy

**Vấn đề:** Cache lưu DTO JSON trực tiếp mà không nói rõ schema compatibility khi deploy nhiều app versions.

**Tại sao xảy ra:** Rolling deployment có thể khiến old/new instances cùng đọc một key nhưng DTO thay đổi.

**Ảnh hưởng production:** Deserialize lỗi hoặc semantic mismatch trong rollout.

**Cách sửa:** Giữ DTO backward-compatible hoặc version cache namespace/schema khi breaking change.

## Phiên bản đề xuất

Ví dụ dưới đây tập trung vào tenant isolation, graceful cache fallback và version-aware cache writes. `IVersionedProductCache` là abstraction có implementation Redis thực hiện compare-and-set theo `Version`; version thấp hơn không được overwrite version cao hơn.

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;
    private readonly IVersionedProductCache _cache;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<ProductService> _logger;

    public ProductService(
        AppDbContext db,
        IVersionedProductCache cache,
        ITenantContext tenantContext,
        ILogger<ProductService> logger)
    {
        _db = db;
        _cache = cache;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    public async Task<ProductDto?> GetAsync(
        Guid productId,
        CancellationToken cancellationToken)
    {
        var tenantId = _tenantContext.RequiredTenantId;
        var key = ProductCacheKey.For(tenantId, productId);

        try
        {
            var cached = await _cache.GetAsync(key, cancellationToken);
            if (cached is not null)
                return cached;
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(ex,
                "Product cache read failed for tenant {TenantId}, product {ProductId}",
                tenantId, productId);
        }

        var dto = await _db.Products
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Id == productId)
            .Select(x => new ProductDto(
                x.Id,
                x.TenantId,
                x.Name,
                x.Price,
                x.Status,
                x.Version))
            .SingleOrDefaultAsync(cancellationToken);

        if (dto is null)
            return null;

        try
        {
            await _cache.SetIfNewerAsync(
                key,
                dto,
                ttl: CacheTtl.WithJitter(TimeSpan.FromMinutes(10)),
                cancellationToken);
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(ex,
                "Product cache write failed for tenant {TenantId}, product {ProductId}",
                tenantId, productId);
        }

        return dto;
    }

    public async Task UpdatePriceAsync(
        Guid productId,
        decimal newPrice,
        CancellationToken cancellationToken)
    {
        var tenantId = _tenantContext.RequiredTenantId;

        var product = await _db.Products
            .SingleOrDefaultAsync(
                x => x.TenantId == tenantId && x.Id == productId,
                cancellationToken)
            ?? throw new ProductNotFoundException(productId);

        product.Price = newPrice;

        await _db.SaveChangesAsync(cancellationToken);

        var dto = new ProductDto(
            product.Id,
            product.TenantId,
            product.Name,
            product.Price,
            product.Status,
            product.Version);

        try
        {
            await _cache.SetIfNewerAsync(
                ProductCacheKey.For(tenantId, productId),
                dto,
                ttl: CacheTtl.WithJitter(TimeSpan.FromMinutes(10)),
                cancellationToken);
        }
        catch (Exception ex) when (IsCacheFailure(ex))
        {
            _logger.LogWarning(ex,
                "Product cache refresh failed after DB commit for tenant {TenantId}, product {ProductId}",
                tenantId, productId);
        }
    }

    private static bool IsCacheFailure(Exception exception) =>
        exception is TimeoutException or RedisConnectionException;
}
```

`SetIfNewerAsync` có thể được triển khai bằng một atomic Redis script/transaction phù hợp: đọc current cached version và chỉ ghi khi incoming version mới hơn hoặc bằng. Implementation cụ thể phải được integration-test với client Redis đang sử dụng; không nên tự giả định multi-command sequence là atomic.

Nếu profiling cho thấy Redis không tạo lợi ích đủ lớn, phương án đơn giản hơn là bỏ cache khỏi endpoint này. Cache là optimization, không phải requirement mặc định.

## Giải thích thiết kế sau khi sửa

- Tenant identity đến từ authenticated context và được enforce trong SQL predicate.
- Cache key chứa tenant scope.
- SQL vẫn là source of truth; cache failure không làm core read fail nếu SQL còn phục vụ được.
- Version-aware conditional write ngăn reader cũ overwrite cache entry mới hơn.
- Writer refresh cache sau commit thay vì chỉ delete; nếu refresh fail, TTL/future read repair đóng vai trò recovery.
- TTL ngắn hơn có jitter chỉ là safety net.
- `CancellationToken` được propagate.
- Anti-stampede có thể thêm sau dựa trên metrics; không trộn nó với authorization/correctness.

## Trade-offs

- Version-aware cache tăng complexity và cần atomic compare-and-set implementation/test.
- Fallback về SQL giúp availability nhưng khi Redis outage có thể đẩy tải lớn xuống SQL; cần circuit/bulkhead/admission strategy dựa trên capacity.
- Per-key single-flight giảm stampede nhưng chỉ coalesce trong boundary mà primitive đó bao phủ; local lock không giải quyết nhiều instances.
- Distributed coordination tăng network dependency và failure modes. Không nên thêm nếu TTL/jitter/capacity đủ.
- Bỏ cache đơn giản và an toàn hơn, nhưng có thể tăng DB latency/cost nếu workload thực sự read-heavy với hot keys.

## Cách kiểm thử

1. **Security integration test:** cùng `productId` hoặc các IDs biết trước ở tenant khác không bao giờ đọc/update được qua API, kể cả khi Redis đã có entry.
2. **Concurrency test:** điều phối reader lấy version N, writer commit N+1, rồi reader cố fill cache; assert cache cuối cùng không thể lùi về N.
3. **Failure-path test:** Redis timeout/failover trong get/set; API vẫn trả dữ liệu từ SQL trong SLO phù hợp và không làm write business transaction thất bại sau DB commit.
4. **Load test:** cho hàng nghìn requests cùng miss/expire một hot key; đo DB QPS, cache miss amplification và effectiveness của single-flight/jitter nếu dùng.
5. **Optimistic-concurrency test:** hai writers update cùng product; verify invariant/version và response semantics khi conflict.

## Quan sát trong production

Theo dõi:

- cache hit/miss/error/timeout rate;
- cache fallback-to-SQL rate;
- DB QPS và latency khi cache degraded;
- version-regression/prevented-stale-write counter;

- p50/p95/p99 endpoint latency;

# Code Review Challenge 2 — Vue autocomplete hiển thị kết quả sai vì request race và mở cửa XSS

## Bối cảnh

Một Vue 3 component cung cấp autocomplete cho trang tìm kiếm sản phẩm. Backend trả tối đa 20 suggestions. Response có `title` và `highlightedTitle`; backend hiện dùng search engine để chèn `<em>` quanh phần text match.

Production symptoms:

- backend QPS tăng mạnh theo số keystrokes;
- loading spinner đôi khi tắt trong khi request mới vẫn đang chạy;
- khi API trả 500, UI thỉnh thoảng giữ kết quả cũ mà không báo trạng thái rõ;
- security review phát hiện API response có thể chứa content do seller nhập;

Code hiện tại:

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue';

type Suggestion = {
  id: string;
  title: string;
  highlightedTitle: string;
};

const searchText = ref('');
const suggestions = ref<Suggestion[]>([]);
const loading = ref(false);
const error = ref<string | null>(null);

watch(searchText, async (value) => {
  const query = value.trim();

  if (!query) {
    suggestions.value = [];
    return;
  }

  loading.value = true;
  error.value = null;

  try {
    const response = await fetch('/api/search/suggestions?q=' + query);
    const data = await response.json();
    suggestions.value = data.items;
  } catch (e) {
    error.value = 'Search failed';
  } finally {
    loading.value = false;
  }
});
</script>

<template>
  <div class="search-box">
    <input v-model="searchText" type="search" autocomplete="off" />

    <span v-if="loading">Loading...</span>
    <span v-if="error">{{ error }}</span>

    <ul v-if="suggestions.length">
      <li v-for="item in suggestions" :key="item.id">
        <a :href="'/products/' + item.id" v-html="item.highlightedTitle"></a>
      </li>
    </ul>
  </div>
</template>
```

## Gợi ý

## Kết quả code review tham khảo

### Critical — `v-html` render seller-controlled/untrusted HTML

**Vấn đề:** `highlightedTitle` được đưa thẳng vào `v-html`.

**Tại sao xảy ra:** Vue escaping bị bypass khi dùng `v-html`. Nếu search backend/index trả markup chứa payload không được sanitize đúng, browser sẽ parse nó như HTML.

**Ảnh hưởng production:** Stored/reflected XSS có thể chạy trong origin của ứng dụng, ảnh hưởng session/actions/data mà browser có quyền truy cập.

**Cách sửa:** Tốt nhất API trả plain text + match ranges/token metadata và frontend render text bằng interpolation, không render raw HTML. Nếu product requirement bắt buộc HTML highlighting, dùng sanitizer đã được review/cấu hình allowlist chặt tại boundary phù hợp; không tự viết regex sanitizer.

### High — Out-of-order response ghi đè query mới

**Vấn đề:** Mỗi thay đổi `searchText` tạo request mới; response nào hoàn thành sau cùng sẽ ghi `suggestions`, không quan tâm query hiện tại.

**Tại sao xảy ra:** Promise completion order không đảm bảo giống request creation order.

**Ảnh hưởng production:** User gõ `cars`, nhưng request cũ cho `car` hoàn tất sau và UI hiển thị dữ liệu sai/stale.

**Cách sửa:** Abort request trước bằng `AbortController` và/hoặc dùng monotonically increasing request sequence, chỉ commit state nếu response thuộc latest request.

### High — Không debounce gây request amplification

**Vấn đề:** Mỗi keystroke phát HTTP request ngay.

**Tại sao xảy ra:** Watcher không có debounce/minimum query threshold phù hợp.

**Ảnh hưởng production:** Backend/search cluster QPS tăng mạnh, đặc biệt với fast typists/mobile input; có thể tạo rate limit/latency feedback loop.

**Cách sửa:** Debounce 150–300 ms tùy UX evidence, optionally minimum query length. Cancellation vẫn cần vì debounce không loại bỏ mọi overlap.

### High — `loading` bị race giữa request cũ và mới

**Vấn đề:** `finally` của bất kỳ request nào cũng set `loading = false`.

**Tại sao xảy ra:** Loading state không gắn với latest request identity.

**Ảnh hưởng production:** Request mới còn in-flight nhưng request cũ vừa hoàn tất → spinner tắt sai.

**Cách sửa:** Chỉ update loading/error/results nếu sequence/request vẫn là latest, hoặc quản lý active request count/state machine rõ ràng.

### Medium — Query parameter được nối chuỗi trực tiếp

**Vấn đề:** `'?q=' + query` không encode đúng reserved characters.

**Tại sao xảy ra:** URL được build thủ công.

**Ảnh hưởng production:** Query như `A&B`, `#tag`, unicode hoặc dấu `?` có thể bị parse sai và tạo bug khó tái hiện.

**Cách sửa:** Dùng `URLSearchParams` hoặc URL API.

### Medium — Không kiểm tra `response.ok`

**Vấn đề:** `fetch` không reject chỉ vì HTTP 4xx/5xx; code vẫn gọi `response.json()` và có thể gán payload lỗi như success data.

**Tại sao xảy ra:** Nhầm network rejection với HTTP failure semantics.

**Ảnh hưởng production:** Error state không nhất quán; malformed error payload có thể throw ở chỗ khác; stale UI khó hiểu.

**Cách sửa:** Kiểm tra `response.ok`, map lỗi theo contract trước khi deserialize/use data.

### Medium — Error path giữ suggestions cũ

**Vấn đề:** Khi latest query fail, `suggestions` không được clear hoặc đánh dấu stale.

**Tại sao xảy ra:** Error handling chỉ set message.

**Ảnh hưởng production:** UI có thể hiển thị suggestions từ query cũ bên dưới error của query mới, khiến user click sai item.

**Cách sửa:** Với latest failed request, clear results hoặc giữ previous results nhưng phải có explicit stale/degraded UX contract. Mặc định autocomplete nên clear để tránh ambiguity.

### Medium — In-flight request không được abort khi component unmount

**Vấn đề:** Component lifecycle không cleanup controller/timer.

**Tại sao xảy ra:** Không dùng `onBeforeUnmount` hoặc `onWatcherCleanup`/cleanup mechanism phù hợp.

**Ảnh hưởng production:** Network work tiếp tục không cần thiết; callbacks có thể chạy sau navigation; telemetry và resource usage bị nhiễu.

**Cách sửa:** Abort request và clear debounce timer khi watcher invalidates/unmount.

### Low — Link path ghép raw `id`

**Vấn đề:** Route được ghép string trực tiếp.

**Tại sao xảy ra:** Không dùng router route-object/encoding.

**Ảnh hưởng production:** Nếu `id` contract thay đổi hoặc có reserved characters, URL có thể sai; ngoài ra navigation policy bị phân tán.

**Cách sửa:** Dùng router named route/encoded params hoặc validate strict ID contract.

## Phiên bản đề xuất

Phiên bản dưới đây bỏ raw HTML highlight để ưu tiên security. Backend trả `title` plain text; nếu cần highlight, frontend có thể render các text segments an toàn dựa trên match ranges.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue';

type Suggestion = {
  id: string;
  title: string;
};

type SuggestionResponse = {
  items: Suggestion[];
};

const searchText = ref('');
const suggestions = ref<Suggestion[]>([]);
const loading = ref(false);
const error = ref<string | null>(null);

let timer: ReturnType<typeof setTimeout> | undefined;
let controller: AbortController | undefined;
let requestSequence = 0;

watch(searchText, (value) => {
  const query = value.trim();
  const sequence = ++requestSequence;

  if (timer) clearTimeout(timer);
  controller?.abort();

  if (query.length < 2) {
    suggestions.value = [];
    loading.value = false;
    error.value = null;
    return;
  }

  loading.value = true;
  error.value = null;

  timer = setTimeout(async () => {
    controller = new AbortController();

    try {
      const params = new URLSearchParams({ q: query });
      const response = await fetch(
        `/api/search/suggestions?${params.toString()}`,
        { signal: controller.signal }
      );

      if (!response.ok) {
        throw new Error(`Suggestion request failed: ${response.status}`);
      }

      const data = await response.json() as SuggestionResponse;

      if (sequence === requestSequence) {
        suggestions.value = data.items;
      }
    } catch (e) {
      if (e instanceof DOMException && e.name === 'AbortError') {
        return;
      }

      if (sequence === requestSequence) {
        suggestions.value = [];
        error.value = 'Search failed';
      }
    } finally {
      if (sequence === requestSequence) {
        loading.value = false;
      }
    }
  }, 200);
});

onBeforeUnmount(() => {
  if (timer) clearTimeout(timer);
  controller?.abort();
});
</script>

<template>
  <div class="search-box">
    <label for="product-search" class="sr-only">Search products</label>
    <input
      id="product-search"
      v-model="searchText"
      type="search"
      autocomplete="off"
    />

    <span v-if="loading" aria-live="polite">Loading...</span>
    <span v-else-if="error" role="status">{{ error }}</span>

    <ul v-if="suggestions.length">
      <li v-for="item in suggestions" :key="item.id">
        <a :href="`/products/${encodeURIComponent(item.id)}`">
          {{ item.title }}
        </a>
      </li>
    </ul>
  </div>
</template>
```

Một production implementation có thể dùng composable đã chuẩn hóa debounce/cancellation thay vì tự quản lý timer trong từng component. Nếu dùng Vue watcher cleanup APIs, chọn API phù hợp với Vue version thực tế của repository và verify qua official docs trước khi nâng cấp.

## Giải thích thiết kế sau khi sửa

- Debounce giảm request amplification.
- AbortController giảm work không còn cần thiết ở browser/network path.
- Sequence check bảo đảm state chỉ được commit bởi latest logical query, kể cả khi abort không thể ngăn server xử lý request đã gửi.
- `response.ok` tách HTTP errors khỏi success payload.
- `URLSearchParams` encode query đúng.
- Results/error/loading đều gắn với latest request.
- Plain text interpolation để Vue escape content; không dùng `v-html` cho seller-controlled content.
- Cleanup khi unmount giảm dangling work.

## Trade-offs

- Debounce tăng một lượng nhỏ perceived latency; giá trị nên chọn dựa trên UX/backend QPS evidence.
- Abort ở client không đảm bảo backend ngừng xử lý nếu request đã tới server; backend vẫn cần cancellation/rate limiting/capacity controls phù hợp.
- Sequence token có vẻ thừa khi đã abort, nhưng tăng correctness khi abort đến muộn hoặc implementation/network không dừng được response race.
- Bỏ HTML highlight đơn giản và an toàn nhất nhưng mất markup-based highlighting. Nếu highlight là requirement, trả match ranges và render từng text segment thường an toàn hơn sanitizer HTML.
- Tự viết debounce logic ở nhiều component làm tăng duplication; composable/library chuẩn hóa có thể tốt hơn nếu team đã có dependency phù hợp.

## Cách kiểm thử

1. **Concurrency/race test:** mock request `car` chậm hơn `cars`; assert UI cuối cùng chỉ hiển thị `cars` và loading phản ánh request mới nhất.
2. **Security test:** backend trả title chứa `<img onerror=...>`/`<script>` dạng text; assert DOM hiển thị text và không tạo executable element/event handler.
3. **Failure-path test:** latest request trả 500 hoặc network error; assert error state đúng, stale suggestions không còn hiển thị và spinner tắt đúng.
4. **Debounce/load test:** simulate 10 keystrokes nhanh; verify số HTTP requests nằm trong expectation và backend QPS giảm so với implementation cũ.
5. **Lifecycle test:** unmount component khi request đang chạy; verify request bị abort/cleanup và không có unexpected state/error noise.

## Quan sát trong production

Frontend/browser telemetry:

- suggestion request count per search session;
- debounce-to-request ratio;
- aborted request count;
- success/error/HTTP status distribution;
- p50/p95/p99 suggestion latency;
- query length distribution ở dạng aggregate, tránh log raw sensitive search text nếu không cần;
- JavaScript errors và route/unmount correlation.

Backend/search telemetry:

- QPS theo endpoint;
- canceled/disconnected requests nếu platform quan sát được;
- search dependency latency;
- 429/5xx rate;
- request concurrency;
- cache/search-cluster saturation metrics;
- trace sampling đủ để phân biệt browser amplification với backend slowdown.

Security monitoring không thay thế prevention: XSS sink phải được loại bỏ/sanitize đúng từ thiết kế, không dựa vào CSP/logging như primary fix.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache key, cache contents và database predicates đều có thể nằm trong security boundary của một hệ thống multi-tenant; performance optimization không được làm yếu authorization.
- Cache-aside có race condition thực tế. “Update DB rồi delete cache” không tự động bảo đảm reader cũ không ghi stale value trở lại sau invalidation.
- Cache nên có degradation strategy. Nếu Redis chỉ là optimization, dependency failure không nên mặc định biến thành full API outage.
- Frontend async requests có thể hoàn thành sai thứ tự. Cancellation, latest-request identity và state-machine discipline là các công cụ khác nhau nhưng bổ trợ nhau.
- `v-html` là một security-sensitive sink. Dữ liệu từ backend/search/CMS vẫn phải được coi là untrusted nếu nguồn gốc có user-controlled content.
- Debounce giảm load nhưng không thay thế cancellation, backend capacity protection hoặc correctness guards.

## Mẫu tư duy cần nhớ

1. **Security scope phải xuất hiện ở mọi data boundary:** authorization context, query predicate, cache key và response.
2. **Vẽ timeline khi review concurrency:** xác định chính xác operation nào có thể xen kẽ và state cuối cùng là gì.
3. **Treat caches and networks as failure-prone:** design fallback, timeout và observability trước khi production outage xảy ra.
4. **Latest intent wins trong interactive UI:** response cũ không được phép overwrite state của user intent mới.
5. **Loại bỏ unsafe sink tốt hơn cố sanitize muộn:** ưu tiên structured/plain-text contract thay vì raw HTML khi có thể.
