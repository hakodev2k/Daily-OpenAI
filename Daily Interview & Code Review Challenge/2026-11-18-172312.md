# Câu 1 — Cosmos DB: partition key đúng cho query nhưng hot khi ghi

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partitioning, RU, C#/.NET, query performance

## Bối cảnh

API ASP.NET Core .NET 8 lưu audit events vào Azure Cosmos DB (API for NoSQL), với các trường `id`, `tenantId`, `userId`, `createdAt`, `eventType`, `payload`. Partition key là `/tenantId` vì dashboard chủ yếu đọc theo tenant. Trong 800 tenants, một tenant tạo 55% writes giờ cao điểm. P95 ghi tăng từ 45 ms lên 1.8 s và xuất hiện HTTP 429. Dashboard cũng chậm. Team muốn tăng RU/s hoặc chuyển sang SQL Server. Chưa có diagnostics theo partition key range, query charge hay indexing policy.

## Câu hỏi chính

Giải thích nội bộ vì sao partition key hợp lý theo query vẫn gây hot partition; xác định bằng chứng, cách giảm thiểu, phương án thiết kế lại và trade-offs mà không vội đổi database.

## Câu hỏi làm rõ nên cân nhắc

1. 429 đến từ writes, reads hay cả hai; phân bố theo tenant?
2. Query có luôn cung cấp partition key và id, hay fan-out?
3. Throughput đang provisioned/autoscale; RU và physical partitions ra sao?
4. Retention, document size, consistency và SLO của dashboard?
5. SDK retries, diagnostics và deadline được cấu hình thế nào?

## Gợi ý tư duy

### Gợi ý 1

Xem phân phối traffic theo partition-key values, không chỉ tổng RU.

### Gợi ý 2

Phân biệt logical partition, physical partition và request charge.

### Gợi ý 3

Một logical partition nóng không tự tách chỉ nhờ tăng số physical partitions; cân nhắc key có bucket và chi phí đọc.

## Cấu trúc trả lời đề xuất

1. Chốt SLO và assumptions; 2. Mô tả cơ chế logical/physical partition; 3. Đo RU/429 theo operation và tenant; 4. Kiểm tra hypotheses; 5. So sánh mitigations; 6. Thiết kế migration; 7. Test và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

Giải thích cùng partition-key value định tuyến tới một logical partition; logical partition có giới hạn riêng, trong khi tổng RU container có thể chưa phải bottleneck. 429 cần đọc cùng retry-after, request charge và metrics; không suy ra nguyên nhân duy nhất.

### Điểm cộng

Phân biệt point read `id + partition key` với cross-partition queries; đánh giá index updates, payload size, TTL, SDK retries và query diagnostics.

### Senior+

Đề xuất synthetic partition key khi write skew được chứng minh, kèm chi phí fan-out reads, migration, rollback và consistency verification.

## Hướng giải quyết tham khảo

**Giả định cần xác minh:** tenant lớn thực sự là hot key; 429 không nhất thiết chỉ do một nguyên nhân. Cosmos DB ánh xạ logical partitions sang physical partitions; tất cả items có cùng logical partition key thuộc cùng logical partition. Throughput và storage có ràng buộc ở cấp partition, vì vậy phân phối không đều có thể làm một key bị throttling dù aggregate capacity còn. RU phản ánh chi phí đọc/ghi/query; kích thước item, index paths, consistency và query pattern có thể ảnh hưởng. Thu Azure Monitor metrics, SDK diagnostics (request charge, status/substatus, retry count, latency), phân nhóm theo tenant, operation và partition-key range. Kiểm tra bốn giả thuyết: hot writes, dashboard fan-out, index overhead và retry amplification. Ngắn hạn áp dụng bounded concurrency/backpressure theo tenant, tối ưu query có partition key, projection và indexing policy theo đo lường; điều chỉnh throughput chỉ khi chứng minh hữu ích. Nếu key thực sự hot, cân nhắc `tenantId#bucket` dựa trên hash của `userId` hoặc event id: phân tán ghi nhưng query toàn tenant phải đọc nhiều buckets, tăng RU và complexity. Partition-key migration cần container mới, backfill, đối chiếu counts và read/write cutover có feature flag; dual-write cần xử lý thất bại từng bên, không mặc định atomic. Có thể tạo pre-aggregated dashboard nếu yêu cầu. Chỉ đánh giá SQL Server/PostgreSQL khi transaction/query requirements và TCO phù hợp hơn. Load test skewed traffic, throttling, retry budget, p95/p99 và dữ liệu sau cutover. Không khẳng định một ngưỡng RU cố định khi chưa xác minh cấu hình.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tăng RU ngay. Tôi muốn biết 429 tập trung vào tenant nào, operation nào và mức RU thực tế. Với `/tenantId`, tenant có lượng ghi quá lớn có thể thành hot logical partition. Tôi sẽ thu SDK diagnostics và Azure Monitor, phân biệt write skew, cross-partition queries và index overhead. Sau mitigation bằng concurrency limit và query tuning, nếu bottleneck vẫn do một key, tôi đánh giá synthetic partition key để phân tán ghi; đổi lại đọc phải fan-out và migration phức tạp. Tôi chỉ chuyển database nếu workload thực sự yêu cầu. Quyết định cuối dựa trên load test và cost/latency metrics.”

## Câu hỏi đào sâu

1. Synthetic key ảnh hưởng dashboard theo tenant như thế nào?
2. Nếu 429 xảy ra đồng đều ở mọi tenant, bạn đổi hướng điều tra ra sao?
3. Làm thế nào chuyển container mà vẫn bảo đảm đọc đúng và rollback?

## Lỗi trả lời thường gặp

- Đồng nhất 429 với thiếu tổng RU/s.
- Đổi partition key mà bỏ qua query fan-out.
- Retry vô hạn không có deadline.
- Chuyển database mà không đo workload.
- Không kiểm thử migration và data consistency.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Clarification/SLO | 1 |
| Internal mechanism | 2 |
| Evidence & hypotheses | 2 |
| Reliability/mitigation | 1.5 |
| Trade-offs/migration | 2 |
| Testing/observability/communication | 1.5 |

# Câu 2 — Octopus Deploy báo thành công nhưng IIS trả 503

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, .NET Framework 4.5, TeamCity, Octopus Deploy, SQL Server, incident response

## Bối cảnh

ASP.NET MVC trên .NET Framework 4.5 chạy ở hai IIS nodes sau load balancer. TeamCity build, Octopus Deploy phát hành. Sau release 12 phút, 18% request trả 503, chủ yếu ở một node; App Pool có dấu hiệu recycle, session mất, một số request kéo dài 40 giây. Release đổi connection string, thêm assembly và chạy migration. Chưa rõ 503 substatus, App Pool settings, SQL waits, health probes hay session storage. Product cần phục hồi trong 15 phút mà không mất giao dịch đã commit.

## Câu hỏi chính

Bạn sẽ điều phối incident từ impact, stabilization, evidence, competing hypotheses, root-cause verification, rollback/hotfix đến phòng ngừa như thế nào? Nêu điều kiện khiến bạn đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. 503 xuất phát từ IIS node hay load balancer; có substatus?
2. App Pool recycle vì schedule, rapid-fail, memory, crash hay config change?
3. Migration có backward-compatible với artifact cũ không?
4. Session dùng InProc hay distributed store?
5. Node còn lại có đủ capacity nếu drain node lỗi không?

## Gợi ý tư duy

### Gợi ý 1

Cô lập ảnh hưởng trước khi sửa nhiều biến cùng lúc.

### Gợi ý 2

Đối chiếu IIS/WAS, Windows Event Viewer, deployment diff và SQL telemetry.

### Gợi ý 3

Rollback application và rollback database không tương đương; cần kiểm tra schema compatibility.

## Cấu trúc trả lời đề xuất

1. Định lượng ảnh hưởng; 2. Freeze release và giảm traffic lỗi; 3. Thu timeline; 4. Xây hypothesis/evidence matrix; 5. Điều tra node và SQL; 6. Chọn rollback/fix-forward; 7. Bảo vệ data; 8. Verify; 9. RCA và release safeguards.

## Ý chính của câu trả lời tốt

### Bắt buộc

Đánh giá khả năng drain node, kiểm tra IIS logs, WAS/W3SVC, Event Viewer, w3wp crashes, Octopus variables, SQL blocking, connection pools và health probe. Không rollback DB phá dữ liệu.

### Điểm cộng

Phân biệt session loss do InProc recycle, application startup failure, connection string lỗi, assembly binding, schema locks và health check sai.

### Senior+

Expand-contract schema migration, immutable artifacts, staged/canary deployment, readiness gates, incident communication và idempotency cho retry writes.

## Hướng giải quyết tham khảo

**Impact → stabilize:** freeze deploy, xác định node/endpoint, tỉ lệ 5xx, ảnh hưởng đến giao dịch và session. Nếu node thứ hai đủ capacity, drain node lỗi; nếu không, giảm noncritical traffic và chuẩn bị phương án mở rộng. Giữ logs/dumps trước restart. **Evidence:** IIS status/substatus và Failed Request Tracing; WAS/W3SVC events, worker process exit reason, recycle settings, memory; Octopus deployment log, artifact hash, environment variable/config transforms, assembly load/binding errors; SQL Server waits, locks, long-running migration, connections/pool exhaustion; load balancer health probes. **Hypotheses:** (A) worker crash hoặc rapid-fail; (B) assembly/config/credentials mismatch; (C) SQL migration blocking hoặc pool exhaustion; (D) node readiness sai khiến LB tiếp tục gửi traffic. Không chọn root cause chỉ vì release gần thời điểm lỗi. **Decision:** nếu binary/config mới là nguyên nhân và schema backward-compatible, rollback artifact/config trên một node, smoke test, mở traffic dần. Nếu migration phá compatibility, rollback binary cũ có thể làm lỗi nặng hơn; chọn fix-forward nhỏ với DBA review và đối chiếu data. Không reverse migration xóa dữ liệu đã ghi. **Verify:** 503, p95/p99, App Pool uptime, SQL waits, login/session, checkout/write paths, duplicate writes sau retries. **Prevent:** expand-contract, preflight configuration, canary/blue-green phù hợp, readiness probe, alert theo node, runbook, RCA timeline và owners. Không coi “Octopus success” là production health.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác định node nào phát 503, freeze release và drain node lỗi nếu capacity cho phép. Tôi thu IIS/WAS events, w3wp crashes, config diff, SQL waits và health probe để phân biệt App Pool, assembly/config, database và load balancer. Nếu schema vẫn tương thích và binary mới lỗi, rollback artifact/config; nếu migration đã phá compatibility, không rollback mù quáng mà cân nhắc fix-forward an toàn. Sau phục hồi, kiểm chứng request errors, session và integrity của writes, rồi bổ sung canary, readiness và expand-contract migrations.”

## Câu hỏi đào sâu

1. Nếu node còn lại đã 85% CPU, bạn còn drain node lỗi không?
2. Nếu migration xóa cột mà binary cũ dùng, rollback thế nào?
3. Nếu App Pool recycle theo lịch bình thường, vì sao 503 vẫn tăng?

## Lỗi trả lời thường gặp

- Restart toàn bộ servers trước khi thu evidence.
- Coi 503 luôn là lỗi SQL.
- Rollback schema phá hủy dữ liệu.
- Bỏ qua session storage và health probes.
- Không định nghĩa tiêu chí xác nhận phục hồi.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact/stabilization | 2 |
| IIS/SQL/deployment correctness | 2 |
| Hypotheses/evidence | 2 |
| Rollback/data safety/trade-offs | 2 |
| Testing/monitoring/communication | 2 |

# Câu 3 — Optimizely CMS + React: kiến trúc tích hợp commerce không làm sai giá

**Loại câu hỏi:** Architecture / system design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, ASP.NET Core BFF, React, CDN, e-commerce, security, resilience

## Bối cảnh

Website e-commerce dùng Optimizely CMS cho landing pages/content blocks; PIM cung cấp catalog, commerce API cung cấp price/stock, provider thứ ba cung cấp reviews. Frontend mới là React. Marketing cần preview, SEO và cập nhật nội dung nhanh; checkout không được chốt giá cũ. Campaign giả định 20.000 concurrent visitors, chưa biết request profile. Ba lựa chọn: (A) React gọi trực tiếp providers; (B) ASP.NET Core Backend-for-Frontend tổng hợp; (C) microservices riêng, Azure Service Bus và Redis. Deadline 12 tuần, đội 6 engineers.

## Câu hỏi chính

Thiết kế boundaries, data ownership, read/write APIs, rendering, caching, consistency, security, failure recovery, observability và rollout; so sánh ba lựa chọn, giải thích khi nào kiến trúc đơn giản thắng.

## Câu hỏi làm rõ nên cân nhắc

1. Price/stock cần strong consistency ở listing hay chỉ lúc checkout?
2. Preview, publish, localization và personalization có yêu cầu gì?
3. Providers có SLA, quotas, webhooks và bulk sync không?
4. SEO cần SSR/SSG hay CSR có thể đáp ứng sau kiểm chứng?
5. Team sở hữu checkout/payment và dữ liệu cá nhân nào?

## Gợi ý tư duy

### Gợi ý 1

Tách content freshness khỏi transactional correctness.

### Gợi ý 2

Xác định trust boundaries và fallback khi provider hỏng.

### Gợi ý 3

BFF với adapters có thể đủ; chỉ tách services khi ownership và scale chứng minh cần.

## Cấu trúc trả lời đề xuất

1. Requirements/SLO; 2. Ownership; 3. API và data flows; 4. Rendering/SEO; 5. Cache/consistency; 6. Security; 7. Failure isolation; 8. Deployment/testing/telemetry; 9. Compare options.

## Ý chính của câu trả lời tốt

### Bắt buộc

CMS là authority cho content, PIM cho catalog, commerce cho price/stock và order, review provider cho reviews. Revalidate giá/tồn kho tại checkout; browser không giữ provider secrets.

### Điểm cộng

CDN/Akamai cache public content theo publish/invalidation, preview không cache chung, timeout/circuit breaker cho reviews, SSR/SSG/hybrid nếu SEO cần.

### Senior+

Giải thích BFF/Modular Monolith vs microservices theo team ownership, latency, deployment complexity, consistency và TCO; đưa ra phased rollout và rollback.

## Hướng giải quyết tham khảo

**Giả định:** checkout phải xác nhận authoritative price/stock với commerce; published CMS content và reviews cho phép eventual consistency. Với đội 6 người và 12 tuần, ưu tiên **ASP.NET Core BFF + adapters** trong một Modular Monolith: `ContentAdapter`, `CatalogAdapter`, `PricingInventoryAdapter`, `ReviewsAdapter`. React dùng SSR/SSG/hybrid rendering khi SEO/crawlability yêu cầu; kiểm tra canonical URLs, structured data, sitemap và Lighthouse thay vì mặc định CSR đủ. **Data flows:** CMS published pages có thể cache ở CDN/Akamai theo version/purge; preview được authorization và bypass public cache. Catalog attributes có TTL hoặc webhook invalidation; reviews timeout ngắn và graceful degradation. Price trên listing có thể cache ngắn tùy business tolerance, nhưng checkout bắt buộc revalidate và xử lý stock reservation/order idempotency. Không public-cache personalized prices hoặc cart. **Resilience:** per-provider timeout budget, bounded retry chỉ với operation idempotent, circuit breaker, bulkhead, rate limits, structured logging và correlation ID; fallback reviews nhưng không giả lập checkout success. Background sync/queue chỉ nếu cần durable async integration; outbox/inbox khi có yêu cầu đồng bộ đáng tin cậy, không mặc định mọi request đi qua Service Bus. **Security:** BFF giữ credentials ở server, dùng Managed Identity/Key Vault khi phù hợp, validate external payload, least privilege, authz cho preview và user-specific APIs, tránh SSRF/PII logging. **Deploy:** strangler rollout từng route với feature flags, contract tests cho adapters, Playwright E2E cho preview/SEO/cart, load/failure injection với provider timeout, canary trên Azure App Service; đo BFF p95, provider errors, cache hit, checkout mismatches, publish-to-visible lag. **Trade-offs:** (A) nhanh prototype nhưng browser coupling, secrets/CORS và provider failures; (B) thêm hop và phải scale BFF nhưng tập trung contracts/security; (C) services tăng autonomy khi domain teams đủ độc lập nhưng thêm network, observability, consistency và release burden. Nếu có ba teams độc lập, scaling và change cadence khác nhau rõ, có thể tách sau. Nếu traffic thấp, thậm chí một layered BFF không cache có thể đủ.

## Mẫu trả lời trong phỏng vấn

“Tôi làm rõ nơi cần consistency: CMS và reviews có thể trễ, nhưng checkout phải xác nhận giá và tồn kho với commerce authority. Với sáu engineers và deadline 12 tuần, tôi chọn ASP.NET Core BFF với adapters trước microservices. React cần rendering strategy được kiểm chứng cho SEO; CMS preview phải tách khỏi public CDN cache. Reviews có thể degrade, còn checkout phải fail rõ ràng và dùng idempotency. Tôi sẽ test contracts, Playwright, provider failures và rollout theo route với feature flags. Chỉ tách services khi scale và ownership chứng minh cần.”

## Câu hỏi đào sâu

1. Nếu commerce API không chịu nổi campaign, bạn giảm tải mà không bán sai giá thế nào?
2. Preview và personalization làm thay đổi cache key/authorization ra sao?
3. Khi nào tách adapters thành services độc lập là quyết định tốt?

## Lỗi trả lời thường gặp

- Dùng microservices/queues cho mọi request dù chưa cần.
- Expose provider API keys ra browser.
- Dùng TTL cache làm authority cho checkout.
- Không kiểm chứng SEO với rendering thực tế.
- Bỏ qua preview security, partial failures và rollback.
