# Câu 1 — Cosmos DB query tăng RU đột biến dù số document trả về không đổi

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, query execution, RU, indexing, data modeling, observability

## Bối cảnh

Một ASP.NET Core API lưu `Activity` documents trong Cosmos DB. Container có khoảng vài chục triệu documents và tiếp tục tăng. API sau phục vụ màn hình lịch sử hoạt động:

```csharp
var query = container.GetItemLinqQueryable<Activity>()
    .Where(x => x.UserId == userId && x.CreatedAtUtc >= fromUtc)
    .OrderByDescending(x => x.CreatedAtUtc)
    .Take(50)
    .ToFeedIterator();

var result = new List<Activity>();
while (query.HasMoreResults)
{
    var page = await query.ReadNextAsync(ct);
    result.AddRange(page);
}
```

Ba tháng đầu endpoint ổn định. Sau khi dữ liệu tăng mạnh, p95 latency và RU/request tăng nhiều lần dù endpoint vẫn chỉ trả tối đa 50 records. CPU của API thấp. Team đề xuất tăng RU/s vì “response chỉ 50 records nên query chắc đã tối ưu”.

Chưa biết partition key hiện tại là gì, distribution giữa users ra sao, indexing policy đã bị thay đổi hay chưa, và query có thực sự được route vào một logical partition hay fan-out nhiều partitions.

## Câu hỏi chính

Giải thích vì sao số records trả về không quyết định trực tiếp query cost trong Cosmos DB. Bạn sẽ xác minh query đang được thực thi và route như thế nào, những yếu tố nào có thể khiến RU tăng theo data growth, và khi nào nên sửa query/indexing/partition strategy thay vì chỉ tăng provisioned throughput?

## Câu hỏi làm rõ nên cân nhắc

1. Partition key của container là gì và request có cung cấp đúng partition-key value không?
2. Một user có thể tạo bao nhiêu documents và distribution có skew/hot partition không?
3. Indexing policy có index `UserId` và `CreatedAtUtc` theo cách phù hợp với query hiện tại không?
4. Query metrics cho thấy bao nhiêu partitions/ranges được chạm và bao nhiêu documents được examined?
5. Freshness/ordering requirement có bắt buộc global ordering hay chỉ ordering trong một user stream?

## Gợi ý tư duy

### Gợi ý 1

`Take(50)` giới hạn output, không nhất thiết giới hạn lượng dữ liệu engine phải xét để tìm đúng 50 records.

### Gợi ý 2

Hãy phân biệt logical partition targeting với cross-partition fan-out.

### Gợi ý 3

RU là tín hiệu của work thực hiện bởi database; muốn tối ưu cần xem query metrics, partitioning và index usage thay vì suy luận từ response size.

## Cấu trúc trả lời đề xuất

1. Làm rõ partition key và access pattern.
2. Giải thích logical/physical partition và query routing.
3. Đọc request charge/query metrics.
4. Kiểm tra indexing và sort/filter behavior.
5. Kiểm tra skew/hot partition.
6. So sánh query/index/model alternatives.
7. Test trên representative data volume.
8. Theo dõi RU/latency/throttling sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không suy luận query cost từ số documents cuối cùng trả về.
- Xác minh partition key và liệu query có target một logical partition hay fan-out.
- Dùng request charge, diagnostics/query metrics và latency để đo thay vì đoán.
- Data growth có thể làm cross-partition query, sort/filter hoặc index mismatch đắt hơn.
- Partition-key design phải bắt đầu từ access patterns, cardinality/distribution và scale; không đổi partition key chỉ vì một query chậm.
- Tăng throughput có thể giảm throttling nhưng không sửa một query pattern lãng phí RU.

### Điểm cộng

- Nhận ra `UserId` có thể là candidate partition key nếu workload chủ yếu query theo user, nhưng phải kiểm tra per-user volume, distribution và các access patterns khác.
- Nếu query target partition được, truyền partition-key context rõ ràng khi API/SDK path phù hợp để tránh ambiguity.
- Kiểm tra continuation/pagination thay vì offset-like approaches cho lịch sử dài.
- Phân biệt total RU efficiency với hot-partition throughput constraint.

### Senior+

- Đánh giá data model dựa trên workload portfolio, không tối ưu một endpoint làm hỏng ingestion hoặc queries khác.
- Thiết kế migration/repartition strategy nếu partition model thật sự sai, thay vì coi đó là schema edit đơn giản.
- Xác định SLO và cost budget để đánh giá optimization có thực sự cần thiết.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng diagnostics của request thực tế: request charge, latency, retries/throttling và query metrics. Sau đó xác minh partition key của container. Nếu partition key không phải `UserId` hoặc request không thể route theo một key cụ thể, query có thể phải fan-out qua nhiều partition ranges. Khi dataset tăng, work để filter/order có thể tăng dù cuối cùng chỉ trả 50 records.

`Take(50)` là output limit, không phải guarantee rằng engine chỉ đọc 50 documents. Cost phụ thuộc query plan, index, partition routing và distribution. Tôi kiểm tra indexing policy, đặc biệt fields tham gia filter/order, nhưng không mặc định “thêm index” luôn là đáp án vì indexing cũng có write/storage cost.

Nếu access pattern chính là `UserId + CreatedAtUtc` và `UserId` có cardinality/distribution tốt, partitioning theo user hoặc một strategy dẫn xuất phù hợp có thể giúp query được scoped. Nhưng nếu một số users có volume cực lớn hoặc hệ thống còn nhiều query theo tenant/event type, cần đánh giá toàn bộ workload. Nếu partition key hiện tại sai căn bản, migration sang container/model mới cần dual-write/backfill/cutover hoặc strategy tương đương với verification và rollback plan.

Tôi chỉ tăng provisioned throughput khi workload hợp lệ thực sự cần capacity hoặc để stabilize trong lúc điều tra. Nếu RU/request tăng vì query inefficiency, tăng RU/s chủ yếu mua thêm capacity cho cùng lượng work lãng phí.

## Mẫu trả lời trong phỏng vấn

“50 records trả về không có nghĩa Cosmos DB chỉ xử lý 50 records. Tôi sẽ kiểm tra request charge và diagnostics trước, rồi xác minh partition key và query có target đúng một logical partition hay fan-out. Khi dữ liệu tăng, cross-partition filtering/order hoặc index không phù hợp có thể làm RU tăng dù output giữ nguyên.

Tôi sẽ xem query metrics, indexing policy, distribution và hot partitions. Nếu workload chủ yếu truy cập theo `UserId`, đó có thể là partition-key candidate, nhưng tôi không đổi model chỉ vì một endpoint; phải xét cardinality, per-user volume và các query khác. Tăng RU/s có thể stabilize throttling, nhưng nếu RU/request đang tăng do query pattern thì đó không phải root fix. Tôi sẽ benchmark trên data volume đại diện và theo dõi RU/request, p95/p99 và throttling sau thay đổi.”

## Câu hỏi đào sâu

1. Nếu `UserId` tạo một vài logical partitions cực lớn/hot, bạn thay đổi partition strategy thế nào?
2. Nếu business thêm requirement query activity toàn tenant theo thời gian, model tối ưu cho per-user query còn đủ không?
3. Team muốn tăng RU/s ngay để giải quyết incident; khi nào bạn đồng ý dù biết query chưa tối ưu?

## Lỗi trả lời thường gặp

- Cho rằng `Take(50)` đồng nghĩa database chỉ đọc 50 documents.
- Đề xuất tăng RU/s trước khi đo RU/request và partition routing.
- Chọn partition key chỉ theo field xuất hiện trong `WHERE` mà không xét distribution/access patterns.
- Nói “thêm index” mà không xem indexing policy/query metrics.
- Bỏ qua migration cost khi muốn đổi partition model.

## Thang điểm 0–10

- **0–2:** Chỉ tăng RU hoặc cache endpoint.
- **3–4:** Biết partition key quan trọng nhưng chưa giải thích routing/cost.
- **5–6:** Điều tra request charge, partitioning, indexing và data growth hợp lý.
- **7–8:** Có workload-driven model, hot-partition reasoning, test/telemetry rõ.
- **9–10:** Phân tích cả efficiency, capacity, migration và multi-query trade-offs với evidence.

# Câu 2 — Azure Service Bus backlog tăng nhưng scale consumer không làm throughput tốt hơn

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, distributed systems, message processing, idempotency, lock/retry, SQL, dependency failure, observability, incident response

## Bối cảnh

Một order integration service nhận messages từ Azure Service Bus queue và ghi kết quả xuống SQL Server rồi gọi một third-party fulfillment API. Bình thường queue depth thấp. Sau một campaign, active message count tăng liên tục từ vài nghìn lên hàng trăm nghìn.

Operations scale consumer từ 4 lên 20 instances nhưng completed messages/second gần như không tăng. Application Insights cho thấy dependency latency tăng, SQL có lúc chậm, third-party API thỉnh thoảng trả `429`, và một số message được xử lý lại. DLQ cũng bắt đầu tăng nhưng chưa rõ lý do chính.

Team có ba đề xuất ngay lập tức: tăng concurrency tối đa, retry mọi exception ngay lập tức, hoặc tăng lock duration rất lớn. Chưa có đủ evidence để kết luận bottleneck.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ stabilization đến root-cause analysis? Hãy chỉ ra telemetry cần thu thập để phân biệt bottleneck ở Service Bus receiver, message lock/settlement, SQL, third-party API, application concurrency hay poison messages; sau đó thiết kế remediation để backlog được drain mà không tạo duplicate side effects hoặc làm dependency downstream sập nặng hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Processing time distribution và lock-lost/abandon/dead-letter reasons hiện là gì?
2. Handler hoàn thành SQL write và third-party side effect theo thứ tự nào, có idempotency key không?
3. `MaxConcurrentCalls`, prefetch và auto/manual settlement đang cấu hình ra sao?
4. Third-party `429` có `Retry-After`/rate limit contract nào và giới hạn theo account/IP/tenant không?
5. SQL waits, connection pool, transaction duration và query latency thay đổi thế nào khi scale từ 4 lên 20 instances?

## Gợi ý tư duy

### Gợi ý 1

Nếu downstream capacity cố định, tăng consumer concurrency có thể chỉ chuyển backlog từ queue sang SQL/API và làm retry storm nặng hơn.

### Gợi ý 2

At-least-once delivery nghĩa handler phải chịu được duplicate; settlement/retry policy không thay thế idempotency.

### Gợi ý 3

Hãy đo flow theo từng stage: receive → processing → dependencies → settlement → retry/DLQ.

## Cấu trúc trả lời đề xuất

1. Định lượng business impact và backlog growth rate.
2. Stabilize để không overload downstream.
3. Thu telemetry theo processing stage.
4. Lập competing hypotheses.
5. Xác minh bottleneck và duplicate path.
6. Sửa retry/backpressure/concurrency.
7. Bảo vệ idempotency và settlement.
8. Drain backlog có kiểm soát.
9. Test failure paths/load.
10. Thiết lập alerts/capacity plan.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng concurrency mù khi downstream đang `429` hoặc SQL chậm.
- Đo queue depth/age, incoming/completed rate, processing duration, retry count, lock-lost, DLQ reason và dependency latency/error.
- Duplicate delivery phải được coi là expected failure mode; side effects cần idempotency hoặc deduplication boundary phù hợp.
- Retry cần bounded exponential backoff/jitter và tôn trọng downstream rate limits khi có contract phù hợp; immediate retry có thể khuếch đại outage.
- DLQ cần classify theo reason, không chỉ replay toàn bộ.
- Lock duration/renewal phải phù hợp processing model nhưng kéo lock rất dài không sửa downstream bottleneck.

### Điểm cộng

- Kiểm tra SQL connection pool/waits/locks khi scale consumers.
- Phân biệt throughput bottleneck với message-level poison failures.
- Dùng controlled concurrency/backpressure để match downstream capacity.
- Có replay tooling cho DLQ với audit/idempotency safeguards.
- Theo dõi oldest-message age chứ không chỉ queue count.

### Senior+

- Nhận ra distributed transaction giữa SQL và third-party API không tự nhiên tồn tại; thiết kế state machine/outbox/inbox hoặc reconciliation theo invariant thực tế.
- Có capacity model: arrival rate, service rate, drain target và dependency quotas.
- Thiết kế degraded mode/circuit behavior để queue hấp thụ burst thay vì phá downstream.

## Hướng giải quyết tham khảo

Tôi đầu tiên xác định arrival rate, completion rate và oldest-message age để biết backlog đang tăng nhanh đến đâu và SLA nào bị vi phạm. Nếu third-party đang trả `429`, tôi không scale thêm ngay; có thể giảm concurrency hoặc pause một subset nếu cần để tránh self-amplifying retry storm.

Tôi xây dashboard theo pipeline: receive rate, active/dead-letter counts, message age, handler p50/p95/p99, success/abandon/dead-letter, lock-lost, delivery count; rồi dependency telemetry cho SQL và fulfillment API. SQL cần xem query duration, waits/blocking, connection-pool pressure. External API cần status distribution, latency và rate-limit signals.

Nếu message được SQL commit rồi external API thành công nhưng process chết trước settlement, message có thể được redeliver. Vì vậy handler không được dựa vào “message chỉ đến một lần”. Tôi dùng stable business/message idempotency key và persist processing state/inbox semantics phù hợp. Với external API, nếu provider hỗ trợ idempotency key thì tận dụng; nếu không, cần reconciliation/state design để duplicate side effects không bị coi nhẹ.

Retry transient failures bằng bounded backoff/jitter; `429` phải tuân theo provider contract nếu có. Permanent validation errors đi DLQ sớm hơn thay vì retry vô hạn. DLQ được phân nhóm theo reason trước khi replay.

Sau khi bottleneck được sửa, drain backlog theo controlled concurrency và theo dõi downstream saturation. Nếu SQL là bottleneck, optimize query/index/transaction hoặc capacity theo evidence. Nếu external quota là bottleneck, queue chính là buffer; throughput không thể vượt sustainable provider rate chỉ bằng thêm pods.

## Mẫu trả lời trong phỏng vấn

“Tôi không tăng consumer concurrency trước vì evidence đã cho thấy SQL chậm và external API trả 429. Tôi sẽ đo arrival/completion rate, oldest message age, processing p95/p99, delivery count, lock-lost, DLQ reasons và dependency telemetry để tìm stage giới hạn throughput.

Tôi coi duplicate là bình thường với at-least-once delivery. Nếu handler commit SQL hoặc gọi fulfillment rồi crash trước settlement, message có thể quay lại, nên side effect cần idempotency key hoặc persisted processing state. Retry phải bounded/backoff và tôn trọng rate limit; retry ngay lập tức chỉ tạo storm.

Sau khi xác định bottleneck, tôi đặt concurrency theo sustainable downstream capacity và drain backlog có kiểm soát. DLQ được classify trước khi replay. Tôi theo dõi queue age, completed/sec, dependency saturation và duplicate/idempotency conflict để chứng minh hệ thống thực sự hồi phục.”

## Câu hỏi đào sâu

1. Nếu third-party API không hỗ trợ idempotency key, bạn bảo vệ duplicate fulfillment như thế nào?
2. Nếu SQL write phải xảy ra trước external call nhưng process crash giữa hai bước, bạn thiết kế recovery state machine ra sao?
3. Nếu tăng concurrency thực sự làm throughput giảm vì SQL contention, bạn chứng minh điều đó bằng metrics nào?

## Lỗi trả lời thường gặp

- Scale consumers vô hạn vì queue depth cao.
- Retry mọi exception ngay lập tức.
- Tin rằng message settlement đảm bảo exactly-once business side effect.
- Replay toàn bộ DLQ mà không classify nguyên nhân.
- Chỉ nhìn queue count mà không xem oldest-message age và rates.

## Thang điểm 0–10

- **0–2:** Chỉ scale hoặc tăng lock duration.
- **3–4:** Biết retry/DLQ nhưng chưa có evidence-driven investigation.
- **5–6:** Điều tra pipeline tốt, có backoff/idempotency/concurrency controls.
- **7–8:** Phân tích SQL/external bottleneck, duplicate paths và controlled backlog drain.
- **9–10:** Có state/transaction-boundary reasoning, capacity model, recovery/reconciliation và operational safeguards hoàn chỉnh.

# Câu 3 — Modernize .NET Framework 4.5 + jQuery system mà không rewrite toàn bộ

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, ASP.NET, legacy architecture, incremental migration, IIS/App Service, frontend modernization, database compatibility, CI/CD, testing, rollout, rollback

## Bối cảnh

Một internal approval platform đã chạy hơn 9 năm trên .NET Framework 4.5, ASP.NET MVC, jQuery, IIS và SQL Server. Hệ thống có khoảng 120 màn hình, nhiều stored procedures, Windows authentication ở một số luồng nội bộ, scheduled jobs chạy trong web application và vài integrations SOAP/REST với hệ thống cũ.

Business muốn chuyển dần sang modern .NET, cải thiện deployment và cho phép các màn hình mới dùng React hoặc Vue.js. Tuy nhiên platform vẫn phải phục vụ người dùng trong suốt quá trình migration. Team chỉ có 6 developers và không thể freeze feature development 12 tháng.

Một proposal yêu cầu rewrite toàn bộ sang .NET 10 + React + microservices trong một lần. Proposal khác muốn giữ nguyên hệ thống thêm 3 năm vì migration “quá rủi ro”. Chưa có inventory dependency, test coverage thấp và một số business rules chỉ tồn tại trong stored procedures/code cũ.

## Câu hỏi chính

Bạn sẽ thiết kế modernization roadmap như thế nào để giảm rủi ro nhưng vẫn tạo tiến bộ đo được? Hãy trình bày cách inventory dependencies/business behavior, xác định migration boundaries, xử lý authentication/integrations/database, đưa modern .NET và frontend mới vào dần, thiết kế CI/CD/testing/observability, và quyết định khi nào strangler/incremental migration tốt hơn rewrite hoặc giữ nguyên.

## Câu hỏi làm rõ nên cân nhắc

1. Những modules nào thay đổi thường xuyên, có business value cao hoặc đang gây production incidents nhiều nhất?
2. Có dependencies/packages nào khóa runtime/Windows/IIS hoặc không có replacement trên modern .NET không?
3. Database ownership giữa modules rõ đến đâu và stored procedures có cross-module coupling không?
4. Authentication requirement có thể chuyển sang modern identity provider hay phải duy trì Windows-integrated flows trong giai đoạn chuyển tiếp?
5. Release frequency, downtime allowance và rollback expectations hiện tại là gì?

## Gợi ý tư duy

### Gợi ý 1

Modernization trước hết là bài toán dependency, behavior và rollout; target framework chỉ là một phần.

### Gợi ý 2

Một migration boundary tốt thường đi theo business capability/dependency seam, không nhất thiết theo controller hoặc database table.

### Gợi ý 3

Đừng thay runtime, architecture, database model, frontend framework và deployment platform đồng thời nếu không có lý do bắt buộc.

## Cấu trúc trả lời đề xuất

1. Inventory runtime/dependencies/business behavior.
2. Baseline production metrics và tests.
3. Phân loại modules theo risk/value/coupling.
4. Chọn migration seams và coexistence strategy.
5. Thiết kế auth/data/integration compatibility.
6. Xây modern deployment path.
7. Migrate theo vertical slices.
8. Canary/rollback/observability.
9. Retire legacy incrementally.
10. Xác định tiêu chí cho rewrite hoặc platform change lớn hơn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite toàn bộ là tốt nhất.
- Bắt đầu bằng dependency/runtime/business-rule inventory và production baseline.
- Bổ sung characterization/integration/E2E tests quanh critical behavior trước khi thay đổi sâu.
- Chọn incremental boundaries cho phép old/new coexist và rollback.
- Database/schema changes cần backward compatibility trong giai đoạn nhiều versions cùng tồn tại.
- Authentication/integration compatibility phải được thiết kế, không giả định đổi framework sẽ tự giải quyết.
- Scheduled jobs trong web app cần được inventory và cân nhắc tách lifecycle khỏi request-host nếu reliability yêu cầu.
- Frontend mới có thể được đưa vào theo route/module thay vì big-bang rewrite toàn UI.

### Điểm cộng

- Dùng traffic routing/reverse proxy hoặc route-level strangler khi phù hợp với hạ tầng.
- Có anti-corruption/adaptation boundary cho SOAP/legacy integrations thay vì lan legacy contract vào code mới.
- Không ép microservices nếu modular monolith/ít deployables giảm operational cost cho team 6 người.
- Tách infrastructure modernization khỏi domain rewrite thành các bước có thể verify độc lập.
- Dùng Git bisect/release metadata/feature flags khi phù hợp để giảm blast radius.

### Senior+

- Có migration fitness metrics: % traffic/modules trên modern stack, incident rate, deployment lead time, rollback success, legacy dependency count.
- Xử lý shared database/cross-module stored procedure coupling như một migration constraint thực tế.
- Có sunset criteria rõ cho legacy paths và tránh “temporary bridge” tồn tại vô hạn.
- Chọn App Service/container/Kubernetes dựa trên workload và operational needs, không dùng Kubernetes như mục tiêu modernization mặc định.

## Hướng giải quyết tham khảo

Tôi sẽ không chấp nhận cả hai cực: big-bang rewrite hoặc đứng yên ba năm. Bước đầu là discovery có timebox: inventory projects/packages, .NET Framework APIs, IIS dependencies, authentication, scheduled jobs, file system assumptions, SOAP/REST clients, stored procedures và các business flows quan trọng. Đồng thời lấy production baseline về traffic, latency, errors và deployment pain.

Vì test coverage thấp, tôi ưu tiên characterization tests quanh business-critical flows và integration/E2E tests ở boundaries. Mục tiêu không phải đạt coverage cao mà tạo safety net cho behavior cần giữ.

Sau đó phân loại modules theo business value, change frequency, coupling và migration difficulty. Chọn một vertical slice có giá trị nhưng dependency manageable để tạo “paved road” cho modern .NET: build pipeline, configuration/secrets, logging/tracing, deployment, auth integration và rollback. Tôi tránh chọn module khó nhất đầu tiên chỉ để chứng minh kỹ thuật.

Old/new có thể coexist theo route hoặc capability. Một reverse proxy/gateway/routing layer có thể chuyển một subset routes sang modern ASP.NET Core app trong khi phần còn lại vẫn vào legacy IIS app, nếu hạ tầng phù hợp. Database có thể tạm shared nhưng ownership phải rõ; schema changes trong transition cần backward-compatible. Shared DB không phải trạng thái lý tưởng lâu dài nhưng cũng không cần tách database ngay nếu điều đó làm migration bùng nổ phạm vi.

Authentication cần migration plan riêng. Nếu Windows-integrated auth vẫn bắt buộc cho một số users, có thể giữ legacy path hoặc bridge identity ở boundary trong giai đoạn chuyển tiếp; không giả định thay bằng JWT/Entra chỉ vì stack mới hỗ trợ. Các SOAP integrations được bọc sau adapter trong code mới để domain/application layer không phụ thuộc contract legacy trực tiếp.

Frontend có thể modernize theo route/page/feature: shell/navigation và API contracts được chuẩn hóa, các màn hình mới dùng Vue/React, rồi thay dần jQuery pages có value cao. Không rewrite 120 screens chỉ để đồng nhất framework nếu business không thu được giá trị tương ứng.

Scheduled jobs chạy trong web app cần xem semantics. Nếu job critical và IIS recycle/deployment có thể làm gián đoạn/duplicate execution, tách thành Worker Service, Functions hoặc scheduler phù hợp sau khi hiểu idempotency/multi-instance behavior. Không tách chỉ để “microservice hóa”.

Mỗi slice có canary/feature flag hoặc routing switch khi khả thi, telemetry so sánh old/new, rollback path và acceptance tests. Sau vài slices, dùng dữ liệu để quyết định tiếp tục strangler hay có subsystem nào đủ isolated để rewrite hoàn toàn.

Kubernetes không phải modernization requirement. Với team nhỏ và workload phù hợp, App Service hoặc đơn giản hơn có thể giảm operational burden. Chỉ chọn Kubernetes nếu deployment/isolation/scaling/platform requirements thực sự cần.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tránh big-bang rewrite vì hệ thống có 9 năm behavior, test coverage thấp và nhiều rules nằm trong stored procedures. Tôi bắt đầu bằng inventory dependencies, auth, jobs, integrations và critical business flows, rồi tạo characterization/integration tests quanh những behavior cần giữ.

Sau đó tôi chọn một vertical slice có business value và coupling vừa phải để xây paved road cho modern .NET: CI/CD, configuration, observability, auth và rollback. Old/new coexist theo route hoặc capability; database changes phải backward-compatible trong giai đoạn transition. Frontend mới có thể đưa vào từng route thay vì rewrite 120 screens.

Tôi cũng inventory scheduled jobs vì chạy trong web app có lifecycle/recycle risk; chỉ tách khi reliability semantics yêu cầu. Tôi không chọn microservices/Kubernetes mặc định cho team 6 người. Thành công được đo bằng modules/traffic migrated, deployment lead time, incident rate và số legacy dependencies giảm dần. Mỗi slice phải rollback được và có telemetry so sánh trước/sau.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên bạn chọn phụ thuộc 40 stored procedures dùng chung với legacy modules, bạn thay đổi migration boundary thế nào?
2. CTO vẫn yêu cầu microservices vì muốn teams deploy độc lập trong tương lai, nhưng hiện chỉ có một team 6 người. Bạn phản biện hoặc đồng ý theo tiêu chí nào?
3. Nếu old và new applications phải cùng ghi một database trong 18 tháng, bạn quản lý schema evolution và compatibility ra sao?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ chỉ vì stack cũ đã hết thời.
- Bắt đầu bằng nâng framework mà chưa inventory unsupported dependencies/business behavior.
- Thay backend, frontend, database và hosting cùng lúc.
- Đặt mục tiêu “100% test coverage” thay vì risk-based safety net.
- Chọn Kubernetes/microservices như dấu hiệu của modernization thay vì một trade-off vận hành.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất rewrite hoặc upgrade framework.
- **3–4:** Có migration phases nhưng thiếu coexistence/rollback/testing.
- **5–6:** Có inventory, vertical slices, compatibility và test strategy tốt.
- **7–8:** Xử lý auth/data/jobs/frontend/CI-CD/observability và rollback thực tế.
- **9–10:** Có evidence-driven roadmap, migration economics, explicit seams/sunset criteria và kiểm soát complexity phù hợp team.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB query cost phụ thuộc work thực tế, partition routing và indexing; output size không đại diện trực tiếp cho RU cost.
- Queue backlog là flow/capacity problem; scale consumers chỉ hữu ích khi downstream còn sustainable capacity.
- At-least-once messaging phải được thiết kế cùng idempotency, retry, settlement và reconciliation.
- Legacy modernization cần bảo toàn behavior và khả năng rollback trước khi tối ưu độ “hiện đại” của architecture.
- Architecture complexity phải được chứng minh bằng requirements, scale, ownership và operational evidence.

## Mẫu tư duy cần nhớ

- **Measure database work, not response size.**
- **Find the bottleneck before adding concurrency.**
- **Design retry together with idempotency.**
- **Modernize by verified slices, not simultaneous rewrites.**
- **Preserve rollback and compatibility across every migration boundary.**
