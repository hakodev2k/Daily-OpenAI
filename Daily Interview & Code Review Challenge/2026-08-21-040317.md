# Code Review Challenge 1 — Trừ tồn kho đồng thời và xử lý message lặp

**Chủ đề:** Concurrency, EF Core, idempotency, transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một service .NET nhận message `OrderPaid` từ RabbitMQ và trừ tồn kho. Hệ thống chạy 4 replicas, khoảng 200–500 message/giây lúc cao điểm. Broker có thể redeliver khi consumer mất kết nối hoặc process chết trước khi ACK. Production thỉnh thoảng xuất hiện tồn kho âm, cùng một order bị ghi nhận hai lần và một số message retry liên tục. Database dùng PostgreSQL với EF Core.

## Đoạn code cần review

```csharp
public sealed class OrderPaidConsumer
{
    private readonly AppDbContext _db;
    private readonly ILogger<OrderPaidConsumer> _logger;

    public OrderPaidConsumer(AppDbContext db, ILogger<OrderPaidConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(OrderPaid message)
    {
        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId);

        if (alreadyProcessed)
            return;

        foreach (var item in message.Items)
        {
            var product = await _db.Products
                .FirstAsync(x => x.Id == item.ProductId);

            if (product.Stock < item.Quantity)
                throw new InvalidOperationException("Out of stock");

            product.Stock -= item.Quantity;
        }

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Processed order {OrderId}, payload: {@Message}",
            message.OrderId,
            message);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Tìm rủi ro concurrency, database và idempotency.
3. Giải thích tác động production.
4. Ưu tiên vấn đề theo severity.
5. Đề xuất implementation tốt hơn.
6. Giải thích cách kiểm thử dưới concurrent delivery và failure.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

- Hai consumer có thể cùng vượt qua `AnyAsync` không?
- Hai transaction cùng đọc một giá trị `Stock` sẽ tạo kết quả gì?
- Điều gì xảy ra nếu cùng một message được redeliver?
- Việc kiểm tra tồn kho và cập nhật có thực sự atomic theo business invariant không?
- Payload log có thể chứa dữ liệu không nên ghi log không?

## Gợi ý

### Gợi ý 1

Hãy tách hai invariant: “mỗi message chỉ gây side effect một lần” và “stock không được nhỏ hơn 0”. Cả hai cần được bảo vệ tại boundary có khả năng cạnh tranh.

### Gợi ý 2

Một lần `SaveChangesAsync` tạo transaction cho các thay đổi trong lần save đó, nhưng transaction không tự biến pattern read-check-write thành cơ chế chống lost update. Hãy nghĩ đến unique constraint, concurrency control hoặc atomic conditional update.

## Kết quả code review tham khảo

### 1. Check-then-insert idempotency bị race

- **Problem:** `AnyAsync` rồi mới insert `ProcessedMessage` là hai bước logic tách biệt.
- **Why:** Hai consumer có thể cùng thấy chưa tồn tại.
- **Impact:** Cùng message có thể trừ stock nhiều lần.
- **Severity:** Critical.
- **Fix:** Unique constraint/index trên `MessageId`; coi database constraint là hàng rào cuối cùng. Thiết kế transaction để marker và business mutation commit cùng nhau.

### 2. Read-check-write stock có race/lost update

- **Problem:** `product.Stock < quantity` rồi `product.Stock -= quantity` dựa trên snapshot đã đọc.
- **Why:** Concurrent consumers có thể đọc cùng stock trước khi bất kỳ transaction nào commit.
- **Impact:** Overselling hoặc lost update tùy concurrency strategy/schema.
- **Severity:** Critical.
- **Fix:** Dùng atomic conditional update kiểu `UPDATE ... SET Stock = Stock - @qty WHERE Id=@id AND Stock >= @qty`, kiểm tra affected rows; hoặc optimistic concurrency token/retry; pessimistic locking chỉ khi thật sự phù hợp.

### 3. Không có business idempotency theo Order nếu producer tạo MessageId mới khi retry

- **Problem:** Chỉ deduplicate theo `MessageId`.
- **Why:** Retry ở upstream có thể tạo event ID khác nhưng cùng business operation.
- **Impact:** Order vẫn bị apply hai lần.
- **Severity:** High.
- **Fix:** Làm rõ event contract. Nếu invariant là một lần/order, thêm business key phù hợp như `(OrderId, EventType/Version)` với unique constraint.

### 4. Xử lý nhiều sản phẩm tuần tự tạo nhiều round-trip

- **Problem:** Một query cho mỗi item.
- **Why:** N+1 database calls.
- **Impact:** Latency và DB load tăng mạnh với order lớn.
- **Severity:** Medium.
- **Fix:** Batch read/update hoặc sử dụng các conditional update có kiểm soát; cân nhắc stored procedure khi invariant đa-row cần hiệu năng/atomicity cao.

### 5. Failure “out of stock” có thể trở thành poison-message loop

- **Problem:** Business rejection bị throw như lỗi transient.
- **Why:** Broker/job retry policy có thể retry vô hạn.
- **Impact:** Tốn tài nguyên, backlog tăng.
- **Severity:** High.
- **Fix:** Phân loại transient/permanent failure; reject/DLQ hoặc phát event nghiệp vụ phù hợp cho permanent failure.

### 6. Không truyền cancellation token

- **Problem:** Query và save không nhận cancellation.
- **Why:** Consumer shutdown không propagate cancellation xuống DB operations.
- **Impact:** Shutdown chậm, work kéo dài không cần thiết.
- **Severity:** Medium.
- **Fix:** Nhận `CancellationToken` và truyền xuống EF Core.

### 7. Log toàn bộ payload

- **Problem:** Structured log toàn message.
- **Why:** Payload có thể chứa PII hoặc dữ liệu nhạy cảm; log volume lớn.
- **Impact:** Data exposure và chi phí observability.
- **Severity:** Medium.
- **Fix:** Log identifiers/metadata cần thiết, redact dữ liệu nhạy cảm.

### 8. Thiếu telemetry cho duplicate/conflict/retry

- **Problem:** Chỉ có success log.
- **Why:** Không quan sát được contention và duplicate rate.
- **Impact:** Khó điều tra incident.
- **Severity:** Medium.
- **Fix:** Metrics cho processed/duplicate/rejected/retry/db-conflict/duration và trace correlation.

## Phiên bản code đề xuất

```csharp
public sealed class OrderPaidConsumer
{
    private readonly AppDbContext _db;
    private readonly ILogger<OrderPaidConsumer> _logger;

    public OrderPaidConsumer(AppDbContext db, ILogger<OrderPaidConsumer> logger)
        => (_db, _logger) = (db, logger);

    public async Task HandleAsync(OrderPaid message, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        // ProcessedMessages.MessageId MUST have a unique constraint.
        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAt = DateTime.UtcNow
        });

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateException ex) when (IsUniqueViolation(ex))
        {
            await tx.RollbackAsync(ct);
            _logger.LogInformation("Duplicate message {MessageId}", message.MessageId);
            return;
        }

        foreach (var item in message.Items)
        {
            var affected = await _db.Products
                .Where(p => p.Id == item.ProductId && p.Stock >= item.Quantity)
                .ExecuteUpdateAsync(
                    setters => setters.SetProperty(
                        p => p.Stock,
                        p => p.Stock - item.Quantity),
                    ct);

            if (affected != 1)
            {
                await tx.RollbackAsync(ct);
                throw new InsufficientStockException(item.ProductId);
            }
        }

        await tx.CommitAsync(ct);

        _logger.LogInformation(
            "Processed order {OrderId} message {MessageId} with {ItemCount} items",
            message.OrderId,
            message.MessageId,
            message.Items.Count);
    }

    private static bool IsUniqueViolation(DbUpdateException ex)
    {
        // Implement using the PostgreSQL provider's exception details/error code.
        return false;
    }
}
```

**Lưu ý:** Đây là hướng thiết kế tham khảo. Cách nhận diện unique violation phải dùng thông tin exception thực tế của provider thay vì `return false`. Nếu nhiều item của cùng product có thể xuất hiện trong một message, nên normalize/gộp quantity trước khi update.

## Trade-offs

Atomic conditional update bảo vệ invariant ngay tại database và phù hợp contention vừa phải, nhưng nhiều item vẫn tạo nhiều statement. Optimistic concurrency giúp domain model tự nhiên hơn nhưng cần retry policy và xử lý conflict. Pessimistic locking đơn giản hóa một số invariant nhưng làm tăng lock contention/deadlock risk. Nếu throughput rất lớn, có thể partition processing theo product/order key, nhưng complexity vận hành tăng đáng kể.

## Cách kiểm thử

1. Gửi đồng thời 20 bản sao cùng `MessageId`: stock chỉ giảm một lần.
2. Hai order khác nhau cùng mua lượng hàng vượt tổng stock: không bao giờ commit stock âm.
3. Crash/failure giữa các update: transaction rollback toàn bộ mutation và idempotency marker.
4. Simulate unique violation và transient DB failure để xác nhận retry/DLQ semantics.
5. Load test với nhiều replicas, đo conflict rate, DB latency và throughput.

## Quan sát trong production

Theo dõi `consumer_duration`, duplicate count, insufficient-stock count, retry/DLQ count, DB conflict/deadlock/timeout, queue lag và throughput. Trace nên mang `MessageId`, `OrderId` và correlation ID xuyên consumer → database. Alert khi queue lag/retry/DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu transaction commit thành công nhưng consumer chết trước ACK thì thiết kế này phản ứng thế nào?
2. Khi nào optimistic concurrency tốt hơn atomic conditional update?
3. Nếu cần publish `InventoryReserved` sau commit, bạn tránh dual-write database/broker như thế nào?

# Code Review Challenge 2 — API proxy Microsoft Graph với token và HttpClient không an toàn

**Chủ đề:** Authentication/authorization, sensitive-data exposure, HTTP client, cancellation, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép frontend gọi endpoint để đọc lịch của user qua Microsoft Graph. Endpoint chạy khoảng 50–100 request/giây. Gần đây production có socket/connection errors, latency tăng khi Graph chậm và security review phát hiện access token có thể xuất hiện trong log. API dùng delegated access token của request hiện tại.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/calendar")]
public class CalendarController : ControllerBase
{
    private readonly ILogger<CalendarController> _logger;

    public CalendarController(ILogger<CalendarController> logger)
        => _logger = logger;

    [HttpGet("events")]
    public async Task<IActionResult> GetEvents(
        string userId,
        DateTime from,
        DateTime to)
    {
        var token = Request.Headers.Authorization
            .ToString()
            .Replace("Bearer ", "");

        _logger.LogInformation(
            "Loading calendar for {UserId} using token {Token}",
            userId,
            token);

        using var client = new HttpClient();
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        var url = $"https://graph.microsoft.com/v1.0/users/{userId}/calendarView" +
                  $"?startDateTime={from:o}&endDateTime={to:o}";

        var response = await client.GetAsync(url);
        var body = await response.Content.ReadAsStringAsync();

        if (!response.IsSuccessStatusCode)
        {
            _logger.LogError(
                "Graph failed: {Status}; response: {Body}",
                response.StatusCode,
                body);

            return StatusCode(500, body);
        }

        return Content(body, "application/json");
    }
}
```

### Gợi ý 2

Review ba trust boundary độc lập: inbound identity/token, outbound Graph request, và dữ liệu được đưa vào logs/response.

## Dừng lại và tự review

## Kết quả code review tham khảo

### 1. Broken object-level authorization qua `userId`

- **Problem:** Authenticated caller tự chọn `userId`.
- **Why:** `[Authorize]` không tự enforce quyền truy cập resource cụ thể.
- **Impact:** Có thể tạo IDOR/BOLA nếu token/quyền upstream cho phép truy cập user khác.
- **Severity:** Critical.
- **Fix:** Với delegated self-calendar, derive identity từ validated claims và dùng resource tương ứng như `/me/...`; nếu business cho phép đọc user khác, enforce explicit authorization policy/business relationship.

### 2. Access token bị ghi log

- **Problem:** Raw bearer token được log.
- **Why:** Token là credential có thể được replay trong thời gian còn hiệu lực.
- **Impact:** Credential exposure qua log pipeline.
- **Severity:** Critical.
- **Fix:** Không log token; cấu hình redaction và kiểm tra log sinks.

### 3. Tự parse Authorization header thiếu an toàn/robustness

- **Problem:** `Replace("Bearer ", "")` không phải token acquisition strategy tốt.
- **Why:** Authentication middleware đã validate identity; outbound token handling cần flow rõ ràng.
- **Impact:** Fragile parsing và dễ lẫn trust boundary.
- **Severity:** High.
- **Fix:** Dùng authentication/token acquisition abstraction phù hợp với kiến trúc; không coi raw header là identity proof bổ sung.

### 4. `new HttpClient()` mỗi request

- **Problem:** Client được tạo/dispose liên tục.
- **Why:** Không tận dụng handler/connection pooling lifecycle được quản lý.
- **Impact:** Connection churn, latency và nguy cơ resource pressure dưới tải.
- **Severity:** High.
- **Fix:** Dùng `IHttpClientFactory`/typed client hoặc Graph SDK với lifecycle đúng.

### 5. Không propagate cancellation

- **Problem:** `GetAsync`/read body không nhận `HttpContext.RequestAborted`.
- **Why:** Outbound call tiếp tục dù caller đã disconnect/cancel.
- **Impact:** Lãng phí connection/thread/resource khi upstream chậm.
- **Severity:** Medium.
- **Fix:** Truyền cancellation token.

### 6. Trả nguyên upstream error body

- **Problem:** Graph error body bị proxy nguyên cho client.
- **Why:** Không có error boundary/sanitization.
- **Impact:** Có thể lộ upstream details/correlation/internal information và tạo coupling.
- **Severity:** High.
- **Fix:** Map lỗi thành contract nội bộ; log metadata đã sanitize.

### 7. Log toàn upstream error body

- **Problem:** Body có thể chứa dữ liệu không phù hợp cho log.
- **Why:** Logging không có data classification/redaction.
- **Impact:** PII/sensitive metadata exposure.
- **Severity:** High.
- **Fix:** Log status, request/correlation ID và error code đã parse/sanitize.

### 8. Input thời gian chưa được validate

- **Problem:** Không kiểm tra `from < to`, range hợp lý hoặc semantics timezone.
- **Why:** Model binding thành công không đồng nghĩa input hợp lệ về nghiệp vụ.
- **Impact:** Request lỗi, query quá rộng, tăng chi phí/latency.
- **Severity:** Medium.
- **Fix:** Validate range và dùng `DateTimeOffset`/UTC semantics rõ ràng.

### 9. Không có timeout/resilience policy rõ ràng

- **Problem:** Endpoint phụ thuộc upstream nhưng không thể hiện timeout/retry strategy.
- **Why:** Upstream latency/failure có thể kéo dài request.
- **Impact:** Cascading latency/resource exhaustion.
- **Severity:** Medium.
- **Fix:** Timeout budget; retry chỉ với lỗi transient và operation an toàn, có backoff/jitter; tôn trọng throttling guidance/headers của upstream.

### 10. Mọi upstream failure đều thành 500

- **Problem:** Không phân biệt 401/403/429/timeout/5xx.
- **Why:** Error mapping quá thô.
- **Impact:** Client không biết hành động đúng; observability kém.
- **Severity:** Medium.
- **Fix:** Map có chủ đích, tránh leak chi tiết, đồng thời giữ correlation cho investigation.

## Phiên bản code đề xuất

```csharp
[Authorize]
[ApiController]
[Route("api/calendar")]
public sealed class CalendarController : ControllerBase
{
    private readonly GraphCalendarClient _graph;
    private readonly ILogger<CalendarController> _logger;

    public CalendarController(
        GraphCalendarClient graph,
        ILogger<CalendarController> logger)
        => (_graph, _logger) = (graph, logger);

    [HttpGet("events")]
    public async Task<IActionResult> GetEvents(
        DateTimeOffset from,
        DateTimeOffset to,
        CancellationToken ct)
    {
        if (from >= to || to - from > TimeSpan.FromDays(31))
            return BadRequest(new { error = "Invalid time range" });

        try
        {
            var result = await _graph.GetMyCalendarViewAsync(from, to, ct);
            return Ok(result);
        }
        catch (GraphThrottledException ex)
        {
            _logger.LogWarning(
                "Graph throttled calendar request. CorrelationId={CorrelationId}",
                ex.CorrelationId);

            return StatusCode(StatusCodes.Status503ServiceUnavailable,
                new { error = "Calendar service temporarily unavailable" });
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            throw;
        }
        catch (GraphAccessDeniedException ex)
        {
            _logger.LogWarning(
                "Graph access denied. CorrelationId={CorrelationId}",
                ex.CorrelationId);

            return Forbid();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Calendar upstream request failed");
            return StatusCode(502, new { error = "Calendar service failed" });
        }
    }
}

public sealed class GraphCalendarClient
{
    private readonly HttpClient _http;
    private readonly IDelegatedTokenProvider _tokens;

    public GraphCalendarClient(HttpClient http, IDelegatedTokenProvider tokens)
        => (_http, _tokens) = (http, tokens);

    public async Task<JsonDocument> GetMyCalendarViewAsync(
        DateTimeOffset from,
        DateTimeOffset to,
        CancellationToken ct)
    {
        var token = await _tokens.GetTokenAsync(ct);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"me/calendarView?startDateTime={Uri.EscapeDataString(from.ToString("O"))}" +
            $"&endDateTime={Uri.EscapeDataString(to.ToString("O"))}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        using var response = await _http.SendAsync(request, ct);

        if (!response.IsSuccessStatusCode)
            throw MapGraphFailure(response);

        await using var stream = await response.Content.ReadAsStreamAsync(ct);
        return await JsonDocument.ParseAsync(stream, cancellationToken: ct);
    }

    private static Exception MapGraphFailure(HttpResponseMessage response)
        => new HttpRequestException($"Graph returned {(int)response.StatusCode}");
}
```

`GraphCalendarClient` nên được đăng ký qua `IHttpClientFactory` với `BaseAddress` hợp lệ, timeout/resilience policy phù hợp. `IDelegatedTokenProvider` là abstraction minh họa; implementation phải phù hợp authentication flow thực tế. Không log access token.

## Trade-offs

Dùng `/me` đơn giản và giảm BOLA risk khi requirement chỉ là calendar của chính caller. Nếu ứng dụng thực sự cần admin/delegate đọc calendar người khác thì `userId` có thể tồn tại, nhưng authorization phải explicit và permission model cần được review. Typed `HttpClient` thêm cấu hình/DI nhưng đổi lại connection lifecycle, timeout và telemetry nhất quán. Graph SDK có thể giảm code HTTP thủ công, nhưng vẫn phải thiết kế authorization, token acquisition, retry và observability đúng.

## Cách kiểm thử

1. Security test: user A không thể yêu cầu calendar user B bằng cách sửa identifier.
2. Kiểm tra log capture bảo đảm bearer token và dữ liệu nhạy cảm không xuất hiện.
3. Failure-path test cho 401/403/429/5xx/timeout và xác nhận mapping không leak upstream body.
4. Cancellation test: hủy inbound request và xác nhận outbound request dừng.
5. Load test nhiều request đồng thời, quan sát connection reuse, latency và error rate.

## Quan sát trong production

Theo dõi outbound request duration, status-class, timeout, throttling, retry count và active connections. Distributed trace nên nối inbound API span với outbound Graph span nhưng không chứa token. Log correlation/request IDs, authenticated subject ở dạng phù hợp chính sách dữ liệu, operation và sanitized error category. Alert trên sustained 429/5xx/timeout và p95/p99 latency.

## Câu hỏi phỏng vấn mở rộng

1. Nếu requirement là admin được đọc calendar nhân viên, bạn thiết kế authorization model thế nào?
2. Khi nào retry 429/5xx là an toàn, và retry budget nên đặt ở layer nào?
3. Vì sao `IHttpClientFactory` giải quyết connection lifecycle tốt hơn việc tạo/dispose `HttpClient` cho từng request?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Idempotency cần database-enforced invariant, không chỉ check trong application code.
- Read-check-write dưới concurrency phải được bảo vệ bằng atomic update, optimistic/pessimistic concurrency hoặc serialization strategy phù hợp.
- Authentication không thay thế resource-level authorization.
- Access token là secret; không được đưa vào logs.
- Outbound HTTP cần connection lifecycle, cancellation, timeout, failure mapping và telemetry được thiết kế như một phần của production architecture.

## Mẫu tư duy cần nhớ

- Đặt invariant ở boundary có thể enforce atomically.
- Thiết kế retry cùng idempotency và failure classification.
- Phân biệt authentication với authorization trên resource.
- Không log credentials; sanitize ở mọi trust boundary.
- Treat cancellation, timeout và observability as part of the design.
