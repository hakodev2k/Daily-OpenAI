# Code Review Challenge 1 — Import dữ liệu sau khi IIS recycle

**Chủ đề:** ASP.NET Core 8, IIS, BackgroundService, SQL Server, deployment reliability

## Bối cảnh

Một ứng dụng quản trị trên IIS/Windows Server cho phép upload CSV giao dịch. Endpoint phải phản hồi nhanh; import chạy nền và cập nhật SQL Server. Có hai IIS nodes sau load balancer; App Pool có thể recycle khi triển khai. Một file 60 MB có thể chứa 250.000 dòng. Production xuất hiện import biến mất sau deploy, đôi lúc dữ liệu bị nhập hai lần và memory tăng đột biến. Mỗi dòng có mã giao dịch duy nhất theo tenant. Yêu cầu: không mất job đã nhận, có thể retry an toàn, không tạo duplicate; không được làm hỏng API hiện hữu.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/imports")]
public sealed class ImportController : ControllerBase
{
    private static readonly ConcurrentQueue<ImportJob> Queue = new();
    private readonly IServiceProvider _services;

    public ImportController(IServiceProvider services)
        => _services = services;

    [HttpPost]
    public async Task<IActionResult> Upload(IFormFile file, Guid tenantId)
    {
        using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        Queue.Enqueue(new ImportJob(
            Guid.NewGuid(), tenantId, buffer.ToArray()));
        return Accepted();
    }

    public static bool TryDequeue(out ImportJob? job)
        => Queue.TryDequeue(out job);
}

public record ImportJob(Guid Id, Guid TenantId, byte[] Data);

public sealed class ImportWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    public ImportWorker(IServiceProvider services)
        => _services = services;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            if (!ImportController.TryDequeue(out var job))
            {
                await Task.Delay(500, stoppingToken);
                continue;
            }

            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var text = Encoding.UTF8.GetString(job!.Data);
            foreach (var line in text.Split('\n').Skip(1))
            {
                var cells = line.Split(',');
                if (cells.Length < 2) continue;
                db.Transactions.Add(new TransactionRow
                {
                    TenantId = job.TenantId,
                    ExternalId = cells[0],
                    Amount = decimal.Parse(cells[1])
                });
            }
            await db.SaveChangesAsync(stoppingToken);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Queue chỉ tồn tại trong RAM

**Vấn đề:** `static ConcurrentQueue` nằm trong từng process; restart/recycle làm mất dữ liệu đã accepted.  
**Tại sao xảy ra:** IIS worker processes và các nodes không dùng chung heap.  
**Ảnh hưởng production:** Mất import không thể phục hồi sau 202.  
**Cách sửa:** Persist file vào Blob Storage hoặc storage bền vững và ghi job record vào SQL trước khi trả 202; worker riêng hoặc hosted worker có cơ chế claim/recovery.

### [High] — Không có idempotency và uniqueness

**Vấn đề:** Retry file tạo thêm các transaction trùng.  
**Tại sao xảy ra:** Không có unique constraint theo `(TenantId, ExternalId)` và chính sách duplicate.  
**Ảnh hưởng production:** Sai báo cáo tài chính.  
**Cách sửa:** Unique index và upsert/insert có xử lý conflict; job idempotency key và kiểm soát retry theo nghiệp vụ.

### [High] — Không có trạng thái job hoặc cơ chế recovery

**Vấn đề:** Dequeue trước khi ghi DB; exception có thể kết thúc worker, job mất.  
**Tại sao xảy ra:** Không có durable lease, retry/backoff, poison handling.  
**Ảnh hưởng production:** Import treo hoặc mất dấu.  
**Cách sửa:** State machine Pending/Processing/Completed/Failed; lease có expiry, attempt count, backoff, dead-letter/manual remediation.

### [High] — Thiếu tenant authorization

**Vấn đề:** `tenantId` từ request không được đối chiếu với principal.  
**Tại sao xảy ra:** Endpoint không có authorization policy hoặc tenant membership validation.  
**Ảnh hưởng production:** Người dùng có thể import sang tenant khác.  
**Cách sửa:** Authenticate, authorize theo tenant và ghi actor audit; validate lại trong worker nếu policy yêu cầu.

### [High] — Bộ nhớ và tracking tăng theo file

**Vấn đề:** MemoryStream + ToArray + UTF8 string + Split + hàng trăm nghìn tracked entities.  
**Tại sao xảy ra:** Nhiều bản sao của dữ liệu và một DbContext cho toàn bộ batch.  
**Ảnh hưởng production:** LOH pressure, GC pauses, OOM và API latency.  
**Cách sửa:** Stream upload với giới hạn dung lượng, parse theo luồng, batch bounded, DbContext per batch.

### [Medium] — CSV parsing không đúng chuẩn và thiếu validation

**Vấn đề:** `Split(',')` không hỗ trợ quoted fields/newlines; `decimal.Parse` phụ thuộc culture; dòng lỗi bị bỏ qua âm thầm.  
**Tại sao xảy ra:** Không dùng CSV parser, không xác định schema/culture.  
**Ảnh hưởng production:** Dữ liệu sai hoặc import fail không rõ nguyên nhân.  
**Cách sửa:** CSV parser chuẩn, invariant culture hoặc culture contract, row-level error report.

### [Medium] — Thiếu CancellationToken khi upload

**Vấn đề:** Copy không nhận `RequestAborted`; không giới hạn kích thước, MIME/content validation.  
**Tại sao xảy ra:** Endpoint thiếu input constraints.  
**Ảnh hưởng production:** Tốn tài nguyên và nguy cơ DoS.  
**Cách sửa:** Bounded streaming, upload limits, content inspection và cancellation.

### [Medium] — Một transaction quá lớn

**Vấn đề:** Một `SaveChangesAsync` cho toàn bộ file.  
**Tại sao xảy ra:** Không có batching hoặc checkpoint.  
**Ảnh hưởng production:** Transaction log/locks lớn, rollback tốn kém.  
**Cách sửa:** Batch có checkpoint và idempotency; chọn atomicity theo yêu cầu nghiệp vụ.

### [Medium] — Thiếu observability

**Vấn đề:** Không log job lifecycle, progress, row errors hay metrics.  
**Tại sao xảy ra:** Thiết kế thiếu correlation và trạng thái bền vững.  
**Ảnh hưởng production:** Không thể điều tra import mất.  
**Cách sửa:** Structured logs và metrics theo JobId/TenantId (không log nội dung file).

## Phiên bản đề xuất

Ví dụ dưới đây minh họa **ingress bền vững và claim**; các thao tác `IImportStore` phải triển khai transaction/lease ở DB, `IFileStore` phải cung cấp storage bền vững. Đây là contract thiết kế, không phải implementation hoàn chỉnh của adapter.

```csharp
public interface IFileStore
{
    Task<string> SaveAsync(Stream stream, CancellationToken ct);
    IAsyncEnumerable<ImportRow> ReadRowsAsync(string key, CancellationToken ct);
}
public record ImportRow(string ExternalId, decimal Amount);
public record ClaimedJob(Guid Id, Guid TenantId, string FileKey);

public interface IImportStore
{
    Task<Guid> CreatePendingAsync(Guid tenantId, string key,
        string requestKey, CancellationToken ct);
    Task<ClaimedJob?> ClaimNextAsync(TimeSpan lease, CancellationToken ct);
    Task UpsertBatchAsync(ClaimedJob job,
        IReadOnlyList<ImportRow> rows, CancellationToken ct);
    Task CompleteAsync(Guid id, CancellationToken ct);
    Task RecordFailureAsync(Guid id, Exception ex, CancellationToken ct);
}

[Authorize]
[ApiController]
[Route("api/tenants/{tenantId:guid}/imports")]
public sealed class ImportController(
    IFileStore files, IImportStore jobs,
    ITenantAccess access) : ControllerBase
{
    [HttpPost]
    [RequestSizeLimit(70_000_000)]
    public async Task<IActionResult> Upload(
        Guid tenantId, IFormFile file,
        [FromHeader(Name = "Idempotency-Key")] string requestKey,
        CancellationToken ct)
    {
        if (!await access.CanImportAsync(User, tenantId, ct))
            return Forbid();
        if (file.Length is <= 0 or > 70_000_000 ||
            string.IsNullOrWhiteSpace(requestKey))
            return BadRequest();

        await using var stream = file.OpenReadStream();
        var key = await files.SaveAsync(stream, ct);
        var id = await jobs.CreatePendingAsync(
            tenantId, key, requestKey, ct);
        return Accepted($"/api/imports/{id}", new { id });
    }
}

public sealed class ImportWorker(
    IServiceScopeFactory scopes,
    ILogger<ImportWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();
            var jobs = scope.ServiceProvider.GetRequiredService<IImportStore>();
            var files = scope.ServiceProvider.GetRequiredService<IFileStore>();
            var job = await jobs.ClaimNextAsync(TimeSpan.FromMinutes(5), ct);
            if (job is null)
            {
                await Task.Delay(TimeSpan.FromSeconds(2), ct);
                continue;
            }

            try
            {
                var batch = new List<ImportRow>(500);
                await foreach (var row in files.ReadRowsAsync(job.FileKey, ct))
                {
                    batch.Add(row);
                    if (batch.Count < 500) continue;
                    await jobs.UpsertBatchAsync(job, batch, ct);
                    batch.Clear();
                }
                if (batch.Count > 0)
                    await jobs.UpsertBatchAsync(job, batch, ct);
                await jobs.CompleteAsync(job.Id, ct);
            }
            catch (OperationCanceledException) when (ct.IsCancellationRequested)
            {
                throw;
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Import failed {JobId}", job.Id);
                await jobs.RecordFailureAsync(job.Id, ex, ct);
            }
        }
    }
}
```

**Điều kiện bắt buộc của adapters:** `CreatePendingAsync` phải unique theo tenant + request key và xử lý file orphan nếu DB ghi thất bại; `ClaimNextAsync` phải claim atomically giữa nhiều nodes, có lease renewal khi xử lý lâu; `UpsertBatchAsync` dùng unique constraint và checkpoint trong cùng DB transaction. `CompleteAsync` chỉ thành công khi toàn bộ batches đã xác nhận. `RecordFailureAsync` phân loại transient/permanent và không được ghi nhận thành công khi job chưa hoàn tất. Cần endpoint status và cleanup storage. Nếu IIS App Pool bị dừng lâu, worker trong IIS không bảo đảm tiến độ; nên chạy worker độc lập hoặc dùng durable queue service.

## Giải thích thiết kế sau khi sửa

HTTP 202 chỉ được trả sau khi payload đã lưu bền vững và job record được tạo. DB là nguồn trạng thái; file store là nguồn nội dung. Lease và unique constraint giúp nhiều workers chạy an toàn; checkpoint xử lý retry sau crash. Các batch có thể commit riêng, vì vậy tính atomic toàn file cần được quyết định rõ: nếu yêu cầu all-or-nothing, cân nhắc staging table rồi publish atomically.

## Trade-offs

Durable store và worker riêng tăng chi phí vận hành, storage cleanup và complexity. Batch giúp memory ổn định nhưng có thể tạo trạng thái partially imported; staging + publish tránh partial visibility nhưng tốn dung lượng và thêm bước. Nếu tải thấp và không cần chạy liên tục, một worker đơn giản với SQL job table vẫn đủ; không mặc định cần Kubernetes hay Service Bus.

## Cách kiểm thử

1. **Integration:** Upload xong recycle IIS trước khi worker chạy; job vẫn Pending và xử lý được.
2. **Concurrency:** Hai workers claim cùng lúc; chỉ một lease hợp lệ, không trùng transaction.
3. **Failure-path:** DB commit batch rồi worker chết trước checkpoint; retry không tạo duplicate.
4. **Load:** Nhiều file 60 MB đồng thời; kiểm tra peak memory, GC và thời gian xử lý.
5. **Security/data:** Tenant khác bị từ chối; CSV quoted field, invalid decimal và oversized file được xử lý đúng.

## Quan sát trong production

Structured logs theo JobId, TenantId, attempt, batch count và error category; metrics queue age, pending/failed jobs, processing duration, retry count, memory/GC, SQL deadlocks và duplicate conflicts. Alert khi oldest pending age vượt SLA hoặc lease timeout tăng. Đối chiếu tổng rows accepted/processed/rejected và số records thực tế.

2. Làm sao đạt atomic visibility của cả file nếu từng batch đã commit?
3. Nếu storage upload thành công nhưng DB create job thất bại, cơ chế reconciliation nào phù hợp?

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Ticket = { id: string; title: string; tenantId: string };
const props = defineProps<{ tenantId: string }>();

const query = ref('');
const tickets = ref<Ticket[]>([]);
const loading = ref(false);
const error = ref('');
const page = ref(1);

async function loadTickets() {
  loading.value = true;
  error.value = '';
  try {
    const url = '/api/tenants/' + props.tenantId +
      '/tickets?q=' + query.value + '&page=' + page.value;
    const response = await fetch(url, { credentials: 'include' });
    const body = await response.json();
    tickets.value = body.items;
    localStorage.setItem('lastTickets', JSON.stringify(body.items));
  } catch (e) {
    error.value = 'Không thể tải dữ liệu';
  } finally {
    loading.value = false;
  }
}

watch(query, loadTickets);
watch(page, loadTickets);
watch(() => props.tenantId, loadTickets);
onMounted(() => {
  const previous = localStorage.getItem('lastTickets');
  if (previous) tickets.value = JSON.parse(previous);
  loadTickets();
});
</script>

<template>
  <input v-model="query" aria-label="Search tickets" />
  <p v-if="error">{{ error }}</p>
  <p v-if="loading">Đang tải...</p>
  <ul><li v-for="ticket in tickets" :key="ticket.id">
    {{ ticket.title }}
  </li></ul>
</template>
```

## Kết quả code review tham khảo

### [High] — Response cũ ghi đè state mới

**Vấn đề:** Request hoàn thành out-of-order nhưng luôn gán `tickets.value`.  
**Tại sao xảy ra:** Async responses không có sequence guard/cancellation.  
**Ảnh hưởng production:** Hiển thị kết quả sai tenant hoặc sai từ khóa.  
**Cách sửa:** AbortController kết hợp monotonically increasing request ID; chỉ request hiện hành được update.

### [High] — Cache không phân vùng theo tenant và lưu dữ liệu nhạy cảm

**Vấn đề:** `lastTickets` dùng chung cho mọi tenant/session và tồn tại sau logout.  
**Tại sao xảy ra:** Cache key toàn cục, không có chính sách retention.  
**Ảnh hưởng production:** Lộ thông tin ticket cũ cho người dùng khác trên cùng browser.  
**Cách sửa:** Không persist tickets vào localStorage; nếu cần cache, dùng in-memory theo tenant + identity + query và clear khi đổi session.

### [Medium] — Không kiểm tra HTTP status

**Vấn đề:** HTTP 429/500 vẫn được parse và coi là thành công.  
**Tại sao xảy ra:** `fetch` chỉ reject với network/abort failures, không tự reject non-2xx.  
**Ảnh hưởng production:** `body.items` undefined, UI sai và không hiện lỗi phù hợp.  
**Cách sửa:** Kiểm tra `response.ok`, phân loại 401/403/429/5xx, không tự động retry vô hạn.

### [Medium] — Quá nhiều requests

**Vấn đề:** Mỗi ký tự và thay đổi page kích hoạt fetch.  
**Tại sao xảy ra:** Watchers gọi trực tiếp, không debounce hoặc coalesce.  
**Ảnh hưởng production:** API load tăng và rate limit.  
**Cách sửa:** Debounce query, reset page khi query/tenant đổi, cancel obsolete requests.

### [Medium] — Loading race

**Vấn đề:** Request cũ có thể tắt loading của request mới.  
**Tại sao xảy ra:** Mọi `finally` đều gán false.  
**Ảnh hưởng production:** Spinner không phản ánh trạng thái thật.  
**Cách sửa:** Chỉ request hiện hành cập nhật loading/error.

### [Medium] — Không clear dữ liệu khi đổi context

**Vấn đề:** Kết quả tenant cũ vẫn render khi tenant mới đang tải.  
**Tại sao xảy ra:** Không reset tickets khi context thay đổi.  
**Ảnh hưởng production:** Người dùng đọc nhầm hoặc nhìn thấy dữ liệu không phù hợp.  
**Cách sửa:** Clear ngay khi context đổi, hoặc chỉ hiển thị cache hợp lệ theo context.

### [Low] — Không validate response shape

**Vấn đề:** Giả định `body.items` luôn là array.  
**Tại sao xảy ra:** TypeScript type không kiểm chứng JSON runtime.  
**Ảnh hưởng production:** Rendering error khi API thay đổi.  
**Cách sửa:** Runtime schema validation hoặc kiểm tra tối thiểu trước khi gán.

  try {
    const params = new URLSearchParams({
      q, page: String(currentPage)
    });
    const response = await fetch(
      `/api/tenants/${encodeURIComponent(tenant)}/tickets?${params}`,
      { credentials: 'include', signal: controller.signal }
    );
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    const body: unknown = await response.json();
    if (!body || typeof body !== 'object' ||
        !('items' in body) || !Array.isArray(body.items))
      throw new Error('Invalid response');
    if (current === sequence && !controller.signal.aborted)
      tickets.value = body.items.filter(
        (x: unknown): x is Ticket =>
          !!x && typeof x === 'object' &&
          'tenantId' in x && x.tenantId === tenant &&
          'id' in x && typeof x.id === 'string' &&
          'title' in x && typeof x.title === 'string'
      );
  } catch (e) {
    if (current === sequence && !controller.signal.aborted)
      error.value = 'Không thể tải tickets. Vui lòng thử lại.';
  } finally {
    if (current === sequence) loading.value = false;
  }
}

watch([() => props.tenantId, query], () => {
  page.value = 1;
  clearTimeout(debounce);
  active?.abort();
  ++sequence;
  tickets.value = [];
  loading.value = true;
  debounce = setTimeout(load, 300);
}, { immediate: true });

watch(page, () => {
  clearTimeout(debounce);
  load();
});

onBeforeUnmount(() => {
  clearTimeout(debounce);
  active?.abort();
  ++sequence;
});
</script>

<template>
  <input v-model="query" aria-label="Search tickets" />
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="loading">Đang tải...</p>
  <ul><li v-for="ticket in tickets" :key="ticket.id">
    {{ ticket.title }}
  </li></ul>
</template>
```

**Lưu ý triển khai:** Khi query/tenant đổi, `page.value = 1` có thể kích hoạt thêm watcher `page` nếu trước đó page khác 1. Nên hợp nhất thành một watcher của normalized search parameters hoặc điều phối qua một scheduler duy nhất trong production. Client-side tenant filtering chỉ là defensive rendering, **không thay thế backend authorization**. Với nội dung nhạy cảm, API phải authorize từng tenant và trả `Cache-Control` phù hợp.

## Giải thích thiết kế sau khi sửa

Sequence guard bảo đảm response lỗi/thành công từ request cũ không ghi đè state mới; AbortController giảm network work nhưng không được coi là đủ để chống race. Query params được encode đúng. Không lưu tickets vào persistent browser storage. Backend vẫn là enforcement point của quyền truy cập.

## Trade-offs

Debounce tăng độ trễ nhỏ trước khi tìm kiếm nhưng giảm requests. Clear list tránh dữ liệu cũ song có thể gây flicker; có thể giữ stale data chỉ khi cùng tenant/query và hiển thị rõ stale state. Cancellation không bảo đảm backend dừng xử lý, vì vậy rate limiting và server cancellation vẫn cần thiết. Runtime schema validation tăng code và có thể dùng thư viện nếu API lớn.

## Cách kiểm thử

1. **Playwright E2E:** Intercept hai requests và trả response đảo thứ tự; chỉ kết quả mới được hiển thị.
2. **Security/E2E:** Chuyển tenant và logout/login tài khoản khác; không thấy tickets cũ trong UI hoặc storage.
3. **Failure-path:** Mock 429/500, malformed JSON và network disconnect; UI hiện lỗi, không crash.
4. **Load/browser:** Gõ 20 ký tự nhanh; đo số request và thời gian render.
5. **Component:** Đổi page khi debounce đang chờ; xác nhận không có duplicate fetch và loading đúng.

## Quan sát trong production

Đo request count theo search interaction, client abort count, API 429 rate, p95 latency, frontend error category, stale-response ignored count và backend 403 theo tenant. Dùng correlation/request ID không chứa ticket payload; network waterfall và Application Insights dependency traces để phân biệt server slow với race trên client.

2. Nếu search là server-side pagination, làm sao tránh page cũ hiển thị sau filter đổi?
3. Tại sao frontend tenant filtering không phải security boundary?

## Kiến thức trọng tâm

Durable acknowledgement khác với in-memory enqueue; multi-instance và recycle buộc phải thiết kế recovery/idempotency. Trong frontend, thứ tự Promise completion không nhất thiết trùng thứ tự request; authorization thuộc backend, còn UI phải tránh hiển thị stale context.

1. Xác định ranh giới durability trước khi trả success/accepted.

3. Kiểm thử crash/restart, out-of-order responses và dependency failures.
4. Đo memory, queue age, request rate và latency trước khi tối ưu.
