# Code Review Challenge 1 — Thanh toán trùng sau khi Azure Service Bus redeliver

**Chủ đề:** .NET 8, Azure Service Bus, PostgreSQL, idempotency, distributed failure  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một booking platform xử lý lệnh thu tiền từ Azure Service Bus queue. API tạo booking đã ghi dữ liệu vào PostgreSQL và gửi message `PaymentRequested`. Có 5 worker replicas; payment gateway đôi khi timeout hoặc trả 502. Khách hàng báo bị thu tiền hai lần, trong khi dashboard báo một số booking chưa thanh toán. Yêu cầu nghiệp vụ: không tạo hai giao dịch thu tiền cho cùng một payment intent; vẫn phải xử lý lại lỗi tạm thời. Không giả định gateway hỗ trợ idempotency nếu chưa kiểm tra hợp đồng API.

## Đoạn code cần review

```csharp
public sealed record PaymentRequested(Guid BookingId, decimal Amount, string Currency);

public sealed class PaymentWorker(
    ServiceBusClient bus,
    IServiceScopeFactory scopeFactory,
    HttpClient gateway,
    ILogger<PaymentWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        var processor = bus.CreateProcessor("payments", new ServiceBusProcessorOptions
        {
            AutoCompleteMessages = true,
            MaxConcurrentCalls = 16
        });

        processor.ProcessMessageAsync += async args =>
        {
            var request = args.Message.Body.ToObjectFromJson<PaymentRequested>();
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var booking = await db.Bookings.FindAsync(
                new object[] { request.BookingId }, args.CancellationToken);

            if (booking is null || booking.Status == "Paid") return;

            var response = await gateway.PostAsJsonAsync("/charge", new
            {
                bookingId = booking.Id,
                amount = request.Amount,
                currency = request.Currency
            }, args.CancellationToken);
            response.EnsureSuccessStatusCode();

            booking.Status = "Paid";
            booking.PaidAt = DateTimeOffset.UtcNow;
            await db.SaveChangesAsync(args.CancellationToken);
            logger.LogInformation("Payment succeeded for {BookingId}", booking.Id);
        };

        processor.ProcessErrorAsync += args =>
        {
            logger.LogError(args.Exception, "Bus processor failure");
            return Task.CompletedTask;
        };

        await processor.StartProcessingAsync(ct);
        try { await Task.Delay(Timeout.Infinite, ct); }
        catch (OperationCanceledException) when (ct.IsCancellationRequested) { }
        await processor.StopProcessingAsync(CancellationToken.None);
        await processor.DisposeAsync();
    }
}
```

## Kết quả code review tham khảo

### [Critical] — External charge không có idempotency contract
**Vấn đề:** POST charge không có stable payment intent/idempotency key.  
**Tại sao xảy ra:** Worker có thể crash sau charge nhưng trước SaveChanges; message được giao lại.  
**Ảnh hưởng production:** Double charge, hoàn tiền thủ công, mất niềm tin.  
**Cách sửa:** Tạo PaymentIntentId bền vững, truyền cùng key qua mọi retry nếu gateway hỗ trợ; nếu không, dùng query/reconciliation theo merchant reference, không blind retry khi kết quả chưa rõ.

### [Critical] — Check-then-act không atomic giữa replicas
**Vấn đề:** Hai consumer đọc `Status != Paid` đồng thời.  
**Tại sao xảy ra:** EF tracking không phải distributed lock; không có atomic claim/unique constraint.  
**Ảnh hưởng production:** Cả hai gửi charge.  
**Cách sửa:** Unique index cho PaymentIntentId; claim bằng atomic conditional update/transaction hoặc state transition có concurrency token; chỉ một owner được thực hiện side effect. Lease hết hạn cần recovery có kiểm tra trạng thái gateway.

### [High] — Database và payment gateway không có atomic transaction
**Vấn đề:** Gateway thành công nhưng database commit thất bại.  
**Tại sao xảy ra:** Không thể bao trùm HTTP external side effect bằng local SQL transaction.  
**Ảnh hưởng production:** Trạng thái lệch, retry nguy hiểm.  
**Cách sửa:** State machine `Pending/Processing/Succeeded/Unknown/Failed`, persist intent trước khi gọi, reconcile qua gateway reference; outbox/inbox cho event nội bộ nếu cần.

### [High] — Không xác thực amount/currency với dữ liệu authoritative
**Vấn đề:** Dùng Amount/Currency từ message trực tiếp.  
**Tại sao xảy ra:** Message có thể cũ, bị duplicate hoặc không đồng bộ với booking.  
**Ảnh hưởng production:** Thu sai số tiền.  
**Cách sửa:** Lookup immutable payment intent server-side; validate message schema/version, amount, currency, booking ownership và trạng thái.

### [High] — AutoComplete và exception không đủ chiến lược xử lý
**Vấn đề:** Không chủ động phân biệt transient/permanent/unknown outcome.  
**Tại sao xảy ra:** SDK settlement mặc định có thể complete khi handler thành công, abandon khi lỗi; delivery count tăng, cuối cùng có thể DLQ.  
**Ảnh hưởng production:** Poison messages, retry không kiểm soát, side effect lặp.  
**Cách sửa:** `AutoCompleteMessages=false`; complete sau durable outcome; dead-letter invalid payload; retry bounded với backoff ở orchestration phù hợp; giám sát DLQ.

### [High] — Gateway timeout không đồng nghĩa charge thất bại
**Vấn đề:** `EnsureSuccessStatusCode` và timeout được coi như kết quả thất bại an toàn để retry.  
**Tại sao xảy ra:** HTTP response mất sau khi server xử lý.  
**Ảnh hưởng production:** Double charge.  
**Cách sửa:** Đánh dấu `Unknown`, query status bằng reference/idempotency key trước khi gửi lại.

### [Medium] — Lock duration, concurrency và graceful shutdown chưa được kiểm chứng
**Vấn đề:** 16 concurrent calls/replica có thể quá tải gateway; processing lâu có thể mất lock.  
**Tại sao xảy ra:** Chưa có limit theo toàn hệ thống, renewal policy và shutdown drain rõ ràng.  
**Ảnh hưởng production:** Redelivery, throttling, duplicate attempts.  
**Cách sửa:** Giới hạn concurrency theo capacity, xem xét MaxAutoLockRenewalDuration, cancellation/drain và gateway rate limits; không coi lock là bảo đảm exactly-once.

### [Medium] — Thiếu correlation và reconciliation telemetry
**Vấn đề:** Log chỉ có BookingId khi thành công.  
**Tại sao xảy ra:** Không ghi intent ID, delivery count, gateway reference, state transitions.  
**Ảnh hưởng production:** Khó phân biệt duplicate delivery với duplicate charge.  
**Cách sửa:** Structured logs/traces không chứa payment secrets, metrics unknown intents, retry, DLQ, mismatch.

## Phiên bản đề xuất

Mẫu sau minh họa **application contract**; `IPaymentIntentStore` phải được triển khai bằng PostgreSQL với unique constraint, atomic claim và optimistic concurrency. `IPaymentGateway` phải hỗ trợ stable idempotency key và lookup theo reference để đạt tính chất mong muốn. Không coi đoạn code là drop-in production implementation.

```csharp
public enum ChargeState { Pending, Processing, Unknown, Succeeded, Failed }
public record ChargeIntent(Guid Id, Guid BookingId, long AmountMinor,
    string Currency, ChargeState State, string? GatewayReference);

public interface IPaymentIntentStore
{
    Task<ChargeIntent?> GetAsync(Guid id, CancellationToken ct);
    Task<bool> TryClaimAsync(Guid id, CancellationToken ct);
    Task MarkUnknownAsync(Guid id, CancellationToken ct);
    Task MarkSucceededAsync(Guid id, string reference, CancellationToken ct);
}
public interface IPaymentGateway
{
    Task<GatewayResult?> FindAsync(string merchantReference, CancellationToken ct);
    Task<GatewayResult> ChargeAsync(
        string merchantReference, long amountMinor, string currency,
        string idempotencyKey, CancellationToken ct);
}
public record GatewayResult(bool Succeeded, string Reference);

public sealed class PaymentHandler(
    IPaymentIntentStore store, IPaymentGateway gateway)
{
    public async Task HandleAsync(Guid intentId, CancellationToken ct)
    {
        var intent = await store.GetAsync(intentId, ct)
            ?? throw new InvalidDataException("Unknown payment intent");
        if (intent.State == ChargeState.Succeeded) return;
        if (!await store.TryClaimAsync(intentId, ct)) return;

        var key = intent.Id.ToString("N");
        try
        {
            var result = await gateway.FindAsync(key, ct)
                ?? await gateway.ChargeAsync(
                    key, intent.AmountMinor, intent.Currency, key, ct);

            if (result.Succeeded)
                await store.MarkSucceededAsync(intentId, result.Reference, ct);
            else
                await store.MarkUnknownAsync(intentId, ct);
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            await store.MarkUnknownAsync(intentId, CancellationToken.None);
            throw;
        }
        catch (HttpRequestException)
        {
            await store.MarkUnknownAsync(intentId, CancellationToken.None);
            throw;
        }
    }
}
```

**Điều kiện quan trọng:** `TryClaimAsync` cần lease/expiry và fencing hoặc cơ chế tương đương; một claim không được phép chặn recovery vĩnh viễn. Nếu gateway không hỗ trợ lookup/idempotency, cần đưa Unknown vào manual reconciliation thay vì tự động charge lần nữa. Trong thực tế, settlement message phải được triển khai riêng với `AutoCompleteMessages=false`, explicit Complete/DeadLetter, handling cho mất lock và durable state; `MarkUnknownAsync` cũng có thể thất bại nên cần recovery scan.

## Giải thích thiết kế sau khi sửa

Database giữ payment intent làm source of truth; message chỉ mang intent ID. Claim atomic ngăn xử lý đồng thời ở mức local; stable gateway key ngăn duplicate external side effect nếu gateway bảo đảm đúng contract. Recovery worker truy vấn các intent `Unknown` hoặc lease expired và đối soát với gateway trước khi retry. Outbox được cân nhắc khi phát event sau commit, không giải quyết trực tiếp atomicity giữa SQL và gateway.

## Trade-offs

Thêm bảng intent, state machine, reconciliation và gateway contract làm tăng độ phức tạp vận hành nhưng phù hợp rủi ro tiền thật. Với hệ thống không xử lý tiền hoặc side effect có thể lặp, mức bảo vệ có thể nhẹ hơn. Exactly-once end-to-end không thể suy ra từ Azure Service Bus duplicate detection hay database transaction đơn lẻ.

## Cách kiểm thử

1. **Concurrency integration:** 100 deliveries cùng intent tới nhiều worker; chỉ một logical charge được ghi nhận.
2. **Failure injection:** Gateway thành công nhưng HTTP timeout; redelivery không phát sinh charge mới.
3. **Database fault:** Commit state thất bại sau charge; reconciliation chuyển về Succeeded.
4. **Contract/security:** Message amount/currency bị sửa; gateway vẫn dùng immutable intent data.
5. **Shutdown/lock:** Restart worker khi đang xử lý; không mất message, không double charge, DLQ được giám sát.

## Quan sát trong production

Theo dõi `payment_intent_state_total`, `payment_unknown_age_seconds`, gateway attempts per intent, duplicate delivery, Service Bus active/dead-letter count, delivery count, lock lost, charge-to-booking mismatch. Trace xuyên BookingId → IntentId → MessageId → gateway reference; log structured, không ghi thông tin thẻ/token. Alert khi Unknown tồn đọng vượt SLO hoặc duplicate charge được xác nhận.

## Câu hỏi phỏng vấn mở rộng

1. Khi gateway không hỗ trợ idempotency key và không có lookup API, bạn đặt ranh giới tự động hóa ở đâu?
2. Outbox giải quyết failure nào và không giải quyết failure nào?
3. Khi cần refund/compensation, bạn thiết kế audit trail và quyền thao tác thế nào?

# Code Review Challenge 2 — React search hiển thị sai kết quả và rò rỉ dữ liệu cache

## Bối cảnh

Internal portal cho nhân viên tìm customer records theo từ khóa. Người dùng có thể chuyển tenant khi đang mở tab, đăng nhập lại và gõ nhanh. API `/api/customers` áp dụng authorization theo tenant ở backend. Khi mạng chậm, UI đôi khi hiển thị kết quả của từ khóa trước hoặc tenant trước. Browser và CDN configuration chưa được xác nhận. React 18+ và TypeScript là giả định của bài.

## Đoạn code cần review

```tsx
type Customer = { id: string; name: string; email: string };
type Props = { tenantId: string; accessToken: string };

const cache = new Map<string, Customer[]>();

export function CustomerSearch({ tenantId, accessToken }: Props) {
  const [query, setQuery] = React.useState("");
  const [items, setItems] = React.useState<Customer[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  React.useEffect(() => {
    if (!query.trim()) {
      setItems([]);
      return;
    }
    const key = query.trim().toLowerCase();
    const cached = cache.get(key);
    if (cached) {
      setItems(cached);
      return;
    }

    setLoading(true);
    fetch("/api/customers?tenant=" + tenantId + "&q=" + query, {
      headers: { Authorization: "Bearer " + accessToken }
    })
      .then(r => r.json())
      .then((data: Customer[]) => {
        cache.set(key, data);
        setItems(data);
      })
      .catch(e => setError(String(e)))
      .finally(() => setLoading(false));
  }, [query]);

  return (
    <section>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>{items.map(c => <li key={c.id}>{c.name} — {c.email}</li>)}</ul>
    </section>
  );
}
```

## Kết quả code review tham khảo

### [Critical] — Cache key không phân biệt tenant và session

## Phiên bản đề xuất

Bản này **cố ý không cache dữ liệu customer**. Backend vẫn phải xác thực token, xác định tenant được phép truy cập từ claims/authorization policy, kiểm tra scope của tenantId và trả response không cache công khai.

```tsx
type Customer = { id: string; name: string; email: string };
type Props = { tenantId: string; accessToken: string };

function isCustomerList(value: unknown): value is Customer[] {
  return Array.isArray(value) && value.every(x =>
    typeof x === "object" && x !== null &&
    typeof x.id === "string" &&
    typeof x.name === "string" &&
    typeof x.email === "string");
}

export function CustomerSearch({ tenantId, accessToken }: Props) {
  const [query, setQuery] = React.useState("");
  const [items, setItems] = React.useState<Customer[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;
    setItems([]);
    setError("");
    setLoading(false);

    if (!query.trim()) return () => { active = false; controller.abort(); };

    const timer = window.setTimeout(async () => {
      if (!active) return;
      setLoading(true);
      try {
        const params = new URLSearchParams({
          tenant: tenantId, q: query.trim()
        });
        const response = await fetch("/api/customers?" + params, {
          signal: controller.signal,
          cache: "no-store",
          headers: { Authorization: "Bearer " + accessToken }
        });
        if (!response.ok) throw new Error("HTTP " + response.status);
        const data: unknown = await response.json();
        if (!isCustomerList(data)) throw new Error("Invalid response");
        if (active) setItems(data);
      } catch (err) {
        if (active && !controller.signal.aborted)
          setError("Không thể tải dữ liệu. Vui lòng thử lại.");
      } finally {
        if (active) setLoading(false);
      }
    }, 250);

    return () => {
      active = false;
      window.clearTimeout(timer);
      controller.abort();
    };
  }, [query, tenantId, accessToken]);

  return (
    <section>
      <input aria-label="Search customers" value={query}
        onChange={e => setQuery(e.target.value)} />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>{items.map(c => <li key={c.id}>{c.name} — {c.email}</li>)}</ul>
    </section>
  );
}
```

**Giới hạn:** Effect cleanup chạy sau render/commit; trong khoảng chuyển context, UI cũ có thể tồn tại rất ngắn. Với ranh giới bảo mật nghiêm ngặt, parent nên key/remount component theo authenticated context hoặc render boundary chỉ khi context khớp, clear dữ liệu đồng bộ với logout/tenant switch. Không truyền access token xuống component rộng hơn mức cần thiết nếu kiến trúc auth có thể tránh được.

## Giải thích thiết kế sau khi sửa

`AbortController` giảm request không cần thiết; `active` guard đảm bảo callback cũ không ghi state. Dependencies đảm bảo đổi tenant/token sẽ invalidation. Không cache customer PII ở module scope. Schema validation ngăn dữ liệu lỗi bị coi là array. Server phải luôn kiểm tra authorization, bất kể tenant query param.

## Trade-offs

Bỏ cache làm tăng request và latency khi gõ lại; có thể dùng query cache với partition theo principal/tenant và policy TTL/invalidation khi có yêu cầu rõ. Debounce giảm QPS nhưng tăng độ trễ nhỏ. Strict schema validation tăng code nhưng phát hiện API contract drift sớm. Request cancellation không phải cơ chế bảo mật.

## Cách kiểm thử

1. **Playwright E2E:** Mock response query A chậm hơn B; UI cuối cùng chỉ hiển thị B.
2. **Security E2E:** Đổi tenant và logout/login cùng query; không thấy customer của session trước, kể cả cache/browser back.
3. **API integration:** Tenant query bị giả mạo; server trả 403 hoặc filtered result theo authorization policy.
4. **Failure path:** 401, 500, invalid JSON/schema, abort và network timeout; không render sai, không lộ raw error.
5. **Load/browser:** Gõ nhanh 20 ký tự; đo số requests, latency, abort count và UI consistency.

## Quan sát trong production

Browser telemetry: request count per search, aborted/stale response count (không log query chứa PII), response status, perceived latency và UI errors. Backend: p95/p99 search duration, 401/403 rate, tenant authorization failures, query cost, correlation ID. CDN: kiểm tra cache headers và không cache private responses giữa users.

# Tổng kết hôm nay

## Kiến thức trọng tâm

External payment side effect cần durable intent, idempotency contract và reconciliation; database transaction không bao trùm gateway. UI asynchronous requests cần kiểm soát response ownership và cache partition theo security context. Cả hai bài nhấn mạnh rằng **đúng trong single request không có nghĩa đúng khi retry hoặc context thay đổi**.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi thiết kế retry.
2. Khi kết quả external call không xác định, đối soát trước khi thực hiện lại.
3. Tách concurrency control nội bộ khỏi idempotency tại hệ thống bên ngoài.
4. Kiểm tra cache key có chứa đầy đủ security context, không chỉ business query.
5. Test failure paths, races và production telemetry thay vì chỉ happy path.
