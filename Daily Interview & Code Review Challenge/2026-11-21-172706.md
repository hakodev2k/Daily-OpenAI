# Code Review Challenge 1 — Azure Blob upload làm lộ hồ sơ và tăng memory

**Chủ đề:** C#, ASP.NET Core, Azure Blob Storage, authorization, failure recovery  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

API quản lý hồ sơ nhân viên chạy .NET 8 trên nhiều Azure App Service instances, SQL Server lưu metadata, Azure Blob Storage lưu file. Tải đỉnh 100 uploads đồng thời, mỗi file có thể 200 MB. Người dùng báo file của người khác đọc được qua URL, RAM tăng và một số blob không có record SQL. Yêu cầu: file private, chỉ nhân viên được cấp quyền đọc/ghi.

## Đoạn code cần review

~~~csharp
[ApiController]
[Route("api/employees/{employeeId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobServiceClient _storage;
    private readonly AppDbContext _db;
    public DocumentsController(BlobServiceClient storage, AppDbContext db)
        => (_storage, _db) = (storage, db);

    [HttpPost]
    public async Task<IActionResult> Upload(Guid employeeId, IFormFile file)
    {
        if (file is null || file.Length == 0) return BadRequest();
        var bytes = new byte[file.Length];
        using (var stream = file.OpenReadStream())
            await stream.ReadAsync(bytes);

        var container = _storage.GetBlobContainerClient("employee-docs");
        await container.CreateIfNotExistsAsync(PublicAccessType.Blob);
        var key = employeeId + "/" + file.FileName;
        var blob = container.GetBlobClient(key);
        await blob.UploadAsync(new BinaryData(bytes), overwrite: true);

        _db.EmployeeDocuments.Add(new EmployeeDocument
        {
            EmployeeId = employeeId,
            BlobName = key,
            FileName = file.FileName,
            UploadedBy = User.Identity?.Name ?? "unknown"
        });
        await _db.SaveChangesAsync();
        return Ok(new { url = blob.Uri.ToString() });
    }
}
~~~

## Kết quả code review tham khảo

### [Critical] — Thiếu object-level authorization

**Vấn đề:** Không có [Authorize] và không kiểm tra quyền của caller đối với employeeId.  
**Tại sao xảy ra:** Tin route parameter do client cung cấp.  
**Ảnh hưởng production:** User ghi file vào hồ sơ người khác; có thể anonymous nếu không có global policy.  
**Cách sửa:** Authentication + resource authorization trên employeeId cho upload và download.

### [Critical] — Container có thể public

**Vấn đề:** PublicAccessType.Blob yêu cầu public blob access khi tạo container.  
**Tại sao xảy ra:** Storage access policy không phù hợp dữ liệu nhạy cảm. Nếu account chặn anonymous access, lệnh có thể thất bại; nếu cho phép, blob có thể bị đọc công khai.  
**Ảnh hưởng production:** Data exposure hoặc upload failure.  
**Cách sửa:** Provision private container qua IaC, disable anonymous access ở storage account, trả document ID và authorized download endpoint.

### [High] — Memory allocation và partial read

**Vấn đề:** Buffer theo file.Length, ReadAsync một lần không bảo đảm đọc đủ bytes.  
**Tại sao xảy ra:** Stream có thể trả partial read; nhiều concurrent uploads gây LOH/GC pressure, IFormFile có thể đã buffer.  
**Ảnh hưởng production:** Corrupted content, OOM, 5xx.  
**Cách sửa:** Giới hạn size ở ingress/API, stream dữ liệu, dùng streaming multipart hoặc direct-to-Blob cho file lớn.

### [High] — Overwrite và filename không đáng tin

**Vấn đề:** file.FileName đi vào key, overwrite:true.  
**Tại sao xảy ra:** Client kiểm soát filename; trùng tên ghi đè blob.  
**Ảnh hưởng production:** Mất dữ liệu, DB records trỏ cùng object.  
**Cách sửa:** Server-generated opaque GUID key, no overwrite, sanitize display filename.

### [High] — Không validate nội dung

**Vấn đề:** Thiếu size cap, signature validation, quarantine/scan.  
**Tại sao xảy ra:** Input được coi là hợp lệ.  
**Ảnh hưởng production:** Lưu file độc hại hoặc giả mạo content type.  
**Cách sửa:** Allowlist định dạng, verify magic bytes, malware scanning theo threat model; download attachment/nosniff.

### [High] — Không có cross-resource recovery

**Vấn đề:** Blob upload thành công, SaveChanges thất bại tạo orphan; retry có thể duplicate.  
**Tại sao xảy ra:** SQL và Blob không có atomic transaction chung.  
**Ảnh hưởng production:** Storage leak, inconsistency.  
**Cách sửa:** Pending/Ready state, idempotency key, durable reconciliation, cleanup orphan.

### [Medium] — Thiếu cancellation và error handling

**Vấn đề:** Không truyền RequestAborted, không giới hạn dependency retries.  
**Tại sao xảy ra:** Không quản lý request lifecycle.  
**Ảnh hưởng production:** Tải tiếp tục sau disconnect, 5xx khó chẩn đoán.  
**Cách sửa:** Propagate CancellationToken, bounded retries, ProblemDetails, dependency metrics.

### [Medium] — Provision và audit trong request

**Vấn đề:** CreateIfNotExists mỗi request; Identity.Name không ổn định để audit.  
**Tại sao xảy ra:** Trộn infrastructure provisioning và business logic.  
**Ảnh hưởng production:** Latency, excessive permissions, audit yếu.  
**Cách sửa:** IaC, least-privilege Managed Identity, immutable user subject ID, structured trace IDs.

## Phiên bản đề xuất

Ví dụ đường đi chính với container private provision sẵn, IEmployeeAccess/IFilePolicy là services do ứng dụng triển khai. Giới hạn file 20 MiB; nếu cần 200 MB, dùng streaming multipart hoặc direct upload. Đoạn này cần phối hợp với durable reconciliation workflow trước khi production.

~~~csharp
[Authorize]
[ApiController]
[Route("api/employees/{employeeId:guid}/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxBytes = 20L * 1024 * 1024;
    private readonly BlobContainerClient _blobs;
    private readonly AppDbContext _db;
    private readonly IEmployeeAccess _access;
    private readonly IFilePolicy _policy;

    public DocumentsController(BlobContainerClient blobs, AppDbContext db,
        IEmployeeAccess access, IFilePolicy policy)
        => (_blobs, _db, _access, _policy) = (blobs, db, access, policy);

    [HttpPost]
    [RequestSizeLimit(MaxBytes + 1024 * 1024)]
    public async Task<IActionResult> Upload(
        Guid employeeId, IFormFile file, CancellationToken ct)
    {
        if (!await _access.CanUploadAsync(User, employeeId, ct))
            return Forbid();
        if (file is null || file.Length is <= 0 or > MaxBytes)
            return BadRequest("Invalid size");

        await using var input = file.OpenReadStream();
        if (!input.CanSeek ||
            !await _policy.IsAllowedAsync(input, file.FileName, ct))
            return BadRequest("Invalid content");
        input.Position = 0;

        var documentId = Guid.NewGuid();
        var key = "employees/" + employeeId.ToString("N") + "/" +
                  documentId.ToString("N");
        var blob = _blobs.GetBlobClient(key);
        await blob.UploadAsync(input,
            new BlobUploadOptions {
                HttpHeaders = new BlobHttpHeaders {
                    ContentType = "application/octet-stream"
                }
            }, ct);

        _db.EmployeeDocuments.Add(new EmployeeDocument {
            Id = documentId, EmployeeId = employeeId,
            BlobName = key,
            FileName = Path.GetFileName(file.FileName),
            UploadedBy = User.FindFirst("sub")?.Value
                ?? throw new UnauthorizedAccessException()
        });
        await _db.SaveChangesAsync(ct);
        return Created("/api/documents/" + documentId,
            new { id = documentId });
    }
}
~~~

**Điều kiện production:** Ví dụ chưa atomic giữa Blob và SQL. Phải thêm Pending/Ready records, idempotency key và reconciliation job có checkpoint để xử lý upload thành công nhưng DB commit thất bại hoặc response bị mất. Không xóa blob nếu DB đã commit mà chỉ HTTP response lỗi. IFilePolicy cần giới hạn bytes đọc và verify signature. IFormFile vẫn có buffering; upload cực lớn cần unbuffered streaming. Blob download luôn re-authorize.

## Giải thích thiết kế sau khi sửa

Authorization tại resource boundary, opaque blob keys, private container và bounded upload giảm rủi ro. Resource ID tách public API khỏi physical storage. Reconciliation xử lý failure xuyên hai storage systems, thay vì giả định transaction chung.

## Trade-offs

Proxy upload dễ audit nhưng tốn bandwidth/compute; direct-to-Blob SAS giảm tải nhưng cần finalize API, expiration, scan và orphan cleanup. Pending state tăng complexity nhưng giúp retry an toàn. Chỉ dùng distributed processing nếu scale và failure evidence yêu cầu.

## Cách kiểm thử

1. **Security:** User A không upload/download employee B; anonymous và raw blob URL không truy cập.
2. **Concurrency:** 100 files cùng original name không overwrite.
3. **Load:** đo peak memory, GC, p95 và error rate với near-limit files.
4. **Failure injection:** Blob timeout, SQL failure, client disconnect, retry; xác minh reconciliation.
5. **Validation:** fake MIME, sai signature, oversized file và filename độc hại.

## Quan sát trong production

Application Insights traces HTTP → Blob → SQL; structured logs documentId, traceId, storage request ID; không log file bytes. Theo dõi upload p95/p99, GC, 429/5xx, dependency latency, orphan/pending count và scan backlog; alert theo SLA.

## Câu hỏi phỏng vấn mở rộng

1. Với file 5 GB từ mobile, thiết kế upload thế nào?
2. Nếu user bị revoke quyền sau khi cấp SAS, điều gì xảy ra?
3. Xử lý deletion SLA khi bật Blob versioning ra sao?

# Code Review Challenge 2 — Octopus rolling deployment làm SQL schema không tương thích

## Bối cảnh

E-commerce chạy trên WEB01/WEB02 (IIS), dùng chung SQL Server. TeamCity build, Octopus Deploy rolling. Release đổi Customers.FullName thành DisplayName. Khi WEB01 đang deploy, WEB02 vẫn phục vụ checkout và bắt đầu lỗi SQL; rollback binary vẫn lỗi. Downtime tối đa 30 giây; bảng Customers lớn và background jobs có thể dùng schema cũ.

## Đoạn code cần review

~~~yaml
# Simplified internal deployment manifest
release:
  artifact: "Store.Web-latest.zip"
  nodes: [WEB01, WEB02]
  strategy: rolling
  steps:
    - name: stop-web01
      run: "appcmd stop apppool /apppool.name:Store"
    - name: schema
      run: "sqlcmd -S DB01 -d Store -U deploy -P $(DB_PASSWORD) -b -i release.sql"
    - name: deploy-web01
      artifact: "Store.Web-104.zip"
    - name: start-web01
      run: "appcmd start apppool /apppool.name:Store"
    - name: deploy-web02
      artifact: "Store.Web-latest.zip"
    - name: rollback
      when: deployment_failed
      artifact: "Store.Web-previous.zip"
~~~

## Kết quả code review tham khảo

### [Critical] — Breaking schema change trong rolling rollout

**Vấn đề:** Rename FullName trước khi old binary và jobs ngừng dùng column.  
**Tại sao xảy ra:** Shared schema thay đổi trong khi nhiều versions đang chạy.  
**Ảnh hưởng production:** WEB02 checkout lỗi, binary rollback không cứu được.  
**Cách sửa:** Expand DisplayName, deploy dual-compatible code, backfill/reconcile, contract sau rollback window.

### [High] — Rollback chỉ có binary

**Vấn đề:** Không có schema/data rollback plan.  
**Tại sao xảy ra:** Coi migration là tự động reversible.  
**Ảnh hưởng production:** Downtime và data inconsistency.  
**Cách sửa:** Roll-forward compatible schema, feature flag, explicit restore runbook; destructive changes ở release riêng.

### [High] — Artifact drift

**Vấn đề:** WEB01 dùng version 104, WEB02 dùng latest.  
**Tại sao xảy ra:** Không pin digest/package.  
**Ảnh hưởng production:** Different code versions không kiểm soát.  
**Cách sửa:** Build once, promote immutable package SHA qua environments.

### [High] — Không drain traffic và health gate

**Vấn đề:** App pool stop/start không bảo đảm node không nhận traffic hay app đã ready.  
**Tại sao xảy ra:** Thiếu load balancer coordination và smoke tests.  
**Ảnh hưởng production:** 502/503, in-flight requests bị cắt.  
**Cách sửa:** Drain, wait, deploy, warm-up, business smoke test, restore traffic; halt nếu gate fail.

### [High] — Long transaction gây blocking

**Vấn đề:** DDL và UPDATE toàn bảng trong một transaction.  
**Tại sao xảy ra:** Không đo row count, locks, log growth.  
**Ảnh hưởng production:** Checkout timeout và log pressure.  
**Cách sửa:** Additive migration, batch backfill có checkpoint và throttle; đo SQL waits trước.

### [High] — Password trong process args

**Vấn đề:** -P nhận DB_PASSWORD qua shell.  
**Tại sao xảy ra:** Credential interpolation có thể lộ trong process diagnostics/logs.  
**Ảnh hưởng production:** Credential exposure.  
**Cách sửa:** Integrated authentication/secure credential mechanism, least privilege, rotation.

### [Medium] — Migration không idempotent

**Vấn đề:** Rerun rename/ADD có thể fail; concurrent deploy race.  
**Tại sao xảy ra:** Thiếu schema version ledger và migration lock.  
**Ảnh hưởng production:** Partial rollout và retries lỗi.  
**Cách sửa:** Serialized migration, version preconditions, idempotent additive steps.

### [Medium] — Không test tất cả consumers

**Vấn đề:** Background jobs và external integrations có thể còn dùng FullName.  
**Tại sao xảy ra:** Chỉ test web binary mới.  
**Ảnh hưởng production:** Hidden production failures.  
**Cách sửa:** Consumer inventory, contract tests, mixed-version matrix.

## Phiên bản đề xuất

Đây là pseudo-manifest thể hiện orchestration, không phải Octopus Deploy import syntax.

~~~yaml
release_B_backfill:
  steps:
    - resumable-batch-backfill
    - reconcile-data-and-consumers

release_C_contract:
  prerequisites:
    - rollback-window-closed
    - no-old-consumers
    - data-validated

    - remove-legacy-code
    - drop-old-column-in-separate-release
~~~

~~~sql
-- Release A; verify actual FullName type and length first.
IF COL_LENGTH('dbo.Customers', 'DisplayName') IS NULL
    ALTER TABLE dbo.Customers ADD DisplayName nvarchar(256) NULL;
GO
-- Release B: run as a bounded, resumable job, not one giant transaction.
UPDATE TOP (500) dbo.Customers
SET DisplayName = FullName

GO
~~~

**Điều kiện:** Nếu concurrent writes thay đổi FullName, phải dual-write hoặc đồng bộ có kiểm chứng; kiểm tra consistency trước contract. Type nvarchar(256) chỉ là giả định cần đối chiếu schema. Batch cần checkpoint, timeout và giới hạn retry; TOP không bảo đảm thứ tự.

## Giải thích thiết kế sau khi sửa

Mỗi release state tương thích old/new binaries. Schema mở rộng trước, backfill và reconcile dữ liệu, cuối cùng mới drop old contract. Pin artifact và health gates giúp reproducible rollout. Migration runner tách quyền khỏi web runtime.

## Trade-offs

Expand–contract tăng số releases và duplicate fields tạm thời nhưng cho rollback an toàn. Batch migration chậm hơn một transaction lớn song giảm blocking. Nếu bảng nhỏ và maintenance window được chấp thuận, migration trực tiếp có thể hợp lý sau khi đo và test.

## Cách kiểm thử

1. **Compatibility:** old binary/expanded schema; new binary/expanded schema; rollback sau new writes.
2. **Deployment:** WEB01 smoke fail phải halt WEB02; verify artifact hash.
3. **Database load:** lock waits, transaction log, checkout p95 trên realistic dataset.
4. **Failure injection:** interrupted migration, retry và concurrent deploy.
5. **Security:** process args/logs không lộ secrets, runner least privilege.

## Quan sát trong production

Structured releaseId, artifact SHA, schema version, node, migration stage. Theo dõi checkout success, HTTP 5xx, p95/p99, IIS app pool recycle, SQL blocking/deadlocks, log usage, backfill progress và column mismatch count. Dùng baseline/error budget làm go/no-go gate.

## Câu hỏi phỏng vấn mở rộng

1. Nếu đối tác chưa thể nâng cấp ba tháng, contract phase thay đổi thế nào?
2. Khi nào maintenance window tốt hơn blue/green database migration?
3. Xác minh không còn writer cũ trước khi drop column ra sao?
