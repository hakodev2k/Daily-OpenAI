# Code Review Challenge 1 — Service Bus consumer xử lý thanh toán hai lần khi lock hết hạn

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, EF Core, distributed systems, retries, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core Worker xử lý message `PaymentCaptured` từ Azure Service Bus. Mỗi message cập nhật trạng thái order trong SQL Server rồi gọi CRM bên ngoài để cộng loyalty points. Hệ thống chạy 4 replicas. Bình thường mỗi message xử lý dưới 2 giây, nhưng CRM đôi lúc mất 40–90 giây hoặc timeout.

Production ghi nhận một số khách hàng được cộng loyalty points hai lần dù Service Bus message chỉ đại diện cho một payment. Log cũng có các lần message được xử lý lại sau transient failure. Team cho rằng `CompleteMessageAsync` ở cuối handler đảm bảo exactly-once và đề xuất tăng retry count để giảm DLQ.

## Đoạn code cần review

```csharp
public sealed class PaymentConsumer
{
    private readonly OrdersDbContext _db;
    private readonly HttpClient _crm;
    private readonly ILogger<PaymentConsumer> _logger;

    public PaymentConsumer(
        OrdersDbContext db,
        IHttpClientFactory factory,
        ILogger<PaymentConsumer> logger)
    {
        _db = db;
        _crm = factory.CreateClient("crm");
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = args.Message.Body
            .ToObjectFromJson<PaymentCaptured>();

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        if (order.PaymentStatus == "Captured")
        {
            await args.CompleteMessageAsync(args.Message, cancellationToken);
            return;
        }

        order.PaymentStatus = "Captured";
        order.PaymentReference = message.PaymentReference;
        order.PaidAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        var response = await _crm.PostAsJsonAsync(
            "/api/loyalty/credit",
            new
            {
                message.CustomerId,
                message.OrderId,
                Points = message.Amount / 10
            },
            cancellationToken);

        response.EnsureSuccessStatusCode();

        _logger.LogInformation(
            "Payment {PaymentReference} processed for order {OrderId}",
            message.PaymentReference,
            message.OrderId);

        await args.CompleteMessageAsync(args.Message, cancellationToken);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và data consistency.
2. Xác định reliability risks khi CRM chậm, timeout hoặc Service Bus redeliver message.
3. Giải thích production impact và vì sao lỗi có thể chỉ xuất hiện không thường xuyên.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design an toàn hơn.
6. Nêu cách test duplicate delivery, retry và dependency failure.
7. Nêu telemetry cần có trong production.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu SQL commit thành công nhưng process chết trước khi gọi CRM?
2. Điều gì xảy ra nếu CRM đã cộng điểm nhưng response bị mất và message được xử lý lại?
3. `PaymentStatus == "Captured"` có thực sự chứng minh loyalty side effect đã hoàn tất không?
4. Nhiều replicas xử lý duplicate delivery gần đồng thời thì check-then-update hiện tại có atomic không?
5. Message settlement và business transaction có cùng một transaction boundary không?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **duplicate delivery + non-idempotent external side effect + transaction boundaries không đồng nhất**.

### Gợi ý 2

Hãy tách trạng thái “payment đã ghi nhận” khỏi trạng thái “loyalty side effect đã được phát/hoàn tất”, và giả định network có thể fail ở mọi điểm giữa request và response.

## Kết quả code review tham khảo

### Critical — External loyalty side effect không idempotent

**Vấn đề:** CRM credit request không mang idempotency key/business operation ID được CRM enforce.  
**Tại sao xảy ra:** Network timeout không cho consumer biết CRM đã thực hiện side effect hay chưa. Redelivery/retry có thể gửi lại credit.  
**Ảnh hưởng production:** Khách hàng có thể được cộng điểm nhiều lần.  
**Cách sửa:** Dùng stable idempotency key như `PaymentReference`/event ID và yêu cầu CRM lưu/enforce uniqueness; nếu CRM không hỗ trợ, cần một integration design khác không giả định retry an toàn.

### Critical — SQL commit và external call không có atomic business workflow

**Vấn đề:** Order được đánh `Captured` trước khi CRM call hoàn tất.  
**Tại sao xảy ra:** SQL transaction, HTTP side effect và Service Bus settlement là ba boundaries riêng.  
**Ảnh hưởng production:** Process crash sau `SaveChangesAsync` nhưng trước CRM khiến redelivery đi vào nhánh `Captured` và complete message mà không cộng điểm.  
**Cách sửa:** Persist business state và durable outbound work atomically trong SQL, ví dụ Outbox Pattern; xử lý CRM từ outbox với retry/idempotency riêng.

### High — `PaymentStatus` được dùng sai làm deduplication marker

**Vấn đề:** Payment state và integration completion bị trộn thành một flag.  
**Tại sao xảy ra:** `Captured` chỉ nói order state đã thay đổi, không chứng minh CRM side effect hoàn tất.  
**Ảnh hưởng production:** Có thể mất loyalty credit hoặc complete duplicate message quá sớm.  
**Cách sửa:** Có event/inbox/outbox identifiers và trạng thái riêng cho từng durable operation.

### High — Check-then-update có race condition giữa consumers

**Vấn đề:** Hai deliveries cùng order có thể cùng đọc trạng thái chưa `Captured`.  
**Tại sao xảy ra:** Read và update không có concurrency guard/idempotency uniqueness phù hợp.  
**Ảnh hưởng production:** Cả hai handler có thể gọi CRM.  
**Cách sửa:** Dùng unique processed-message/event constraint hoặc optimistic concurrency/atomic insert để một consumer giành quyền xử lý business event; thiết kế theo business key phù hợp.

### High — Không có durable Inbox/deduplication theo message/event ID

**Vấn đề:** Handler không ghi nhận message nào đã được xử lý.  
**Tại sao xảy ra:** Code dựa vào current order state để suy ra duplicate.  
**Ảnh hưởng production:** Duplicate delivery với side effects khác nhau không được phân biệt chính xác.  
**Cách sửa:** Persist processed event ID với unique constraint trong cùng transaction với domain change khi phù hợp.

### High — Long-running dependency làm tăng rủi ro settlement/lock failure

**Vấn đề:** Handler giữ message trong khi chờ CRM 40–90 giây.  
**Tại sao xảy ra:** Processing duration phụ thuộc external service; lock renewal/configuration chưa được xác minh.  
**Ảnh hưởng production:** Message có thể trở lại delivery path trong lúc hoặc sau side effect; throughput giảm và backlog tăng.  
**Cách sửa:** Giữ message handler ngắn bằng durable local transaction/outbox; đồng thời cấu hình processor lock renewal/timeout dựa trên measured processing nếu vẫn cần long processing.

### Medium — `EnsureSuccessStatusCode` không có retry classification

**Vấn đề:** Mọi failure đều thoát handler giống nhau.  
**Tại sao xảy ra:** Không phân biệt transient 429/5xx/timeout với permanent 4xx/business rejection.  
**Ảnh hưởng production:** Retry vô ích, queue churn hoặc DLQ chậm; ngược lại transient failure có thể không có controlled backoff.  
**Cách sửa:** Retry có giới hạn cho transient errors, exponential backoff/jitter và tôn trọng server hints khi có; permanent failure cần explicit handling.

### Medium — Cancellation semantics chưa tách shutdown khỏi business failure

**Vấn đề:** Một cancellation token đi xuyên SQL, HTTP và settlement nhưng code không phân biệt host shutdown/lock loss với dependency error.  
**Tại sao xảy ra:** Cancellation có thể dừng operation ở boundary bất kỳ.  
**Ảnh hưởng production:** Trạng thái partial dễ xảy ra nếu design không idempotent.  
**Cách sửa:** Thiết kế mọi step có thể resume/retry; log cancellation reason/context và không dựa vào in-memory sequence để đảm bảo consistency.

### Medium — Logging thiếu event/message identity và attempt context

**Vấn đề:** Log chỉ có payment reference/order ID.  
**Tại sao xảy ra:** Không log Service Bus message ID, delivery count, correlation ID, outbox operation ID.  
**Ảnh hưởng production:** Khó chứng minh duplicate path và timeline.  
**Cách sửa:** Structured logging với identifiers, delivery count, dependency outcome và processing duration.

### Low — String status làm state transition khó kiểm soát

**Vấn đề:** `"Captured"` là magic string.  
**Tại sao xảy ra:** State model không encode valid transitions.  
**Ảnh hưởng production:** Dễ typo hoặc tạo invalid state trong code lớn.  
**Cách sửa:** Dùng enum/value/domain transition phù hợp; đây không phải fix chính cho duplicate processing.

## Phiên bản đề xuất

Một hướng an toàn là consumer chỉ thực hiện durable local transaction: deduplicate event, cập nhật order và ghi outbox. External CRM side effect được worker riêng xử lý idempotently.

```csharp
public sealed class PaymentConsumer
{
    private readonly OrdersDbContext _db;

    public PaymentConsumer(OrdersDbContext db) => _db = db;

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = args.Message.Body
            .ToObjectFromJson<PaymentCaptured>()
            ?? throw new InvalidOperationException("Invalid payment message");

        var eventId = args.Message.MessageId;

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var alreadyProcessed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == eventId, cancellationToken);

        if (!alreadyProcessed)
        {
            var order = await _db.Orders
                .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

            order.MarkPaymentCaptured(
                message.PaymentReference,
                DateTime.UtcNow);

            _db.OutboxMessages.Add(OutboxMessage.Create(
                type: "CreditLoyaltyPoints",
                idempotencyKey: message.PaymentReference,
                payload: new
                {
                    message.CustomerId,
                    message.OrderId,
                    Points = message.Amount / 10
                }));

            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = eventId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
            await tx.CommitAsync(cancellationToken);
        }

        await args.CompleteMessageAsync(args.Message, cancellationToken);
    }
}
```

Database cần unique constraint trên `ProcessedMessages.MessageId`; code cũng phải xử lý unique-constraint race như một duplicate hợp lệ. Outbox dispatcher gửi CRM request với stable idempotency key và chỉ mark outbox completed sau confirmed success. Nếu CRM không hỗ trợ idempotency, cần làm rõ contract trước khi hứa exactly-once business effect.

## Giải thích thiết kế sau khi sửa

Consumer không cố tạo distributed transaction giữa SQL, Service Bus và HTTP. Nó thu nhỏ atomic boundary về SQL: domain state + deduplication marker + outbound intent cùng commit. Sau commit, redelivery có thể xảy ra nhưng unique inbox marker khiến domain mutation không lặp lại. Outbox dispatcher có thể retry độc lập.

Exactly-once delivery không được giả định. Mục tiêu thực tế là **at-least-once delivery + idempotent processing/effects**. Stable business idempotency key phải tồn tại đến CRM; nếu downstream không enforce uniqueness, retry sau ambiguous timeout vẫn có thể duplicate side effect.

## Trade-offs

Outbox/Inbox thêm tables, cleanup, dispatcher, monitoring và eventual consistency: loyalty points không nhất thiết xuất hiện ngay cùng lúc order được đánh paid. Đổi lại, failure recovery rõ ràng hơn và request/message handler không bị external latency giữ lâu. Với hệ thống nhỏ và CRM có native idempotency mạnh, có thể dùng thiết kế đơn giản hơn, nhưng vẫn cần durable deduplication và explicit failure semantics.

## Cách kiểm thử

1. **Integration/concurrency test:** gửi cùng `MessageId` đồng thời qua nhiều handler; chỉ một domain mutation/outbox record được tạo.
2. **Failure-path test:** crash sau SQL commit nhưng trước Service Bus complete; redelivery không tạo outbox thứ hai.
3. **Dependency test:** CRM thực hiện credit nhưng response bị timeout; retry cùng idempotency key không cộng điểm lần hai.
4. **Database test:** verify unique constraint và race handling trên processed message ID.
5. **Load test:** CRM chậm/429 trong thời gian dài; queue consumer vẫn ổn định và outbox backlog/latency được quan sát.

## Quan sát trong production

Theo dõi Service Bus active message count, delivery count, DLQ count, processing duration và settlement failures. Với outbox, theo dõi pending age, retry count, permanent failures và throughput. Log structured fields gồm `MessageId`, `PaymentReference`, `OrderId`, `DeliveryCount`, `OutboxId`, correlation ID. Application Insights dependency telemetry cần thể hiện CRM latency/status. Alert khi oldest outbox age, DLQ hoặc duplicate-conflict rate vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu CRM không hỗ trợ idempotency key và API `GET` cũng không cho kiểm tra transaction đã tồn tại, bạn thiết kế recovery như thế nào?
2. Khi nào Outbox Pattern là complexity không đáng có cho một consumer?
3. Bạn sẽ xử lý ordering nếu cùng một order có `PaymentCaptured` và `PaymentRefunded` gần nhau như thế nào?

# Code Review Challenge 2 — Kubernetes rollout xanh nhưng Pod mới nhận traffic trước khi ASP.NET Core thực sự sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core, readiness/liveness, rolling deployment, resource management, configuration, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API được chuyển từ Azure App Service sang Kubernetes. Deployment có 4 replicas và rolling update. API cần khoảng 20–45 giây để warm up một số metadata và establish dependency connectivity. Gần đây mỗi lần deploy, error rate tăng trong 30–60 giây; đôi lúc Pods restart liên tục khi SQL Server chậm. Team nói rollout vẫn báo thành công nên muốn tăng `initialDelaySeconds` cho cả hai probes lên 120 giây.

Cluster cũng có lúc CPU contention. Chưa có evidence rằng ứng dụng memory leak. Configuration chứa connection string và API key.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 2
      maxSurge: 0
  selector:
    matchLabels:
      app: catalog-api
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      containers:
        - name: api
          image: registry.example/catalog-api:latest
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Catalog
              value: "Server=sql-prod;Database=Catalog;User Id=app;Password=ProdPassword123"
            - name: PartnerApi__Key
              value: "partner-prod-key"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 1
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 10
            failureThreshold: 1
          resources:
            limits:
              cpu: "250m"
              memory: "256Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
spec:
  selector:
    app: catalog-api
  ports:
    - port: 80
      targetPort: 8080
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/deployment/security problems trong manifest.
2. Giải thích vì sao rollout có thể gây 5xx dù Kubernetes objects trông healthy.
3. Phân tích failure mode khi dependency chậm hoặc CPU bị contention.
4. Ưu tiên vấn đề theo production impact.
5. Đề xuất manifest/design tốt hơn mà không over-engineer.
6. Nêu deployment validation tests.
7. Nêu metrics/logs/events cần quan sát.

## Câu hỏi gợi mở

1. Readiness và liveness có cùng mục đích không?
2. `/health` hiện đang kiểm tra điều gì, và điều gì xảy ra nếu SQL transiently unavailable?
3. `maxUnavailable: 2` + `maxSurge: 0` ảnh hưởng capacity thế nào khi rollout?
4. Scheduler quyết định placement dựa trên field nào nếu chỉ có `limits`?
5. Image tag `latest` giúp hay làm khó rollback/audit?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **probe semantics + rollout capacity + resource/configuration safety**, không chỉ ở thời gian delay.

### Gợi ý 2

Liveness trả lời “process có cần restart không?”, readiness trả lời “Pod có nên nhận traffic không?”. Một transient dependency failure không nhất thiết đồng nghĩa process bị hỏng.

## Kết quả code review tham khảo

### Critical — Secrets được hard-code trực tiếp trong Deployment

**Vấn đề:** SQL password và partner API key nằm plaintext trong manifest.  
**Tại sao xảy ra:** Configuration và secrets không được tách khỏi workload manifest.  
**Ảnh hưởng production:** Secret có thể rò qua Git, CI artifacts, deployment history hoặc người có quyền đọc manifest.  
**Cách sửa:** Dùng Kubernetes Secret hoặc external secret integration phù hợp; giới hạn RBAC và rotate credentials đã lộ. Secret object không tự động giải quyết toàn bộ security nếu access control kém.

### High — Readiness và liveness dùng cùng endpoint/semantics

**Vấn đề:** Cả hai probes gọi `/health`.  
**Tại sao xảy ra:** Không phân biệt khả năng nhận traffic với process health.  
**Ảnh hưởng production:** Nếu `/health` fail khi SQL transiently chậm, liveness có thể restart một process hoàn toàn recoverable, làm outage nặng hơn. Nếu endpoint trả healthy quá sớm, readiness đưa Pod vào Service trước warm-up.  
**Cách sửa:** Tách `/health/live` và `/health/ready`; liveness chỉ kiểm tra process-level health, readiness kiểm tra điều kiện cần để serve traffic theo requirement.

### High — Probe thresholds quá nhạy với transient failure

**Vấn đề:** `failureThreshold: 1` cho cả readiness và liveness.  
**Tại sao xảy ra:** Một probe failure duy nhất đổi trạng thái/restart.  
**Ảnh hưởng production:** Dependency jitter hoặc CPU scheduling delay gây flapping/restart storm.  
**Cách sửa:** Chọn thresholds/timeouts theo measured startup/runtime behavior; không dùng delay 120 giây như một con số che symptom.

### High — Rolling update làm giảm capacity đáng kể

**Vấn đề:** 4 replicas nhưng `maxUnavailable: 2`, `maxSurge: 0`.  
**Tại sao xảy ra:** Controller có thể giảm available capacity trong khi Pod mới còn warm-up.  
**Ảnh hưởng production:** Traffic dồn vào ít Pods hơn, tăng latency/CPU và có thể tạo cascading errors.  
**Cách sửa:** Chọn `maxUnavailable`/`maxSurge` theo capacity headroom và cluster resources; ví dụ giữ `maxUnavailable: 0` và cho phép surge nếu cluster có headroom.

### High — Không có startup probe cho startup chậm/biến thiên

**Vấn đề:** Liveness bắt đầu sớm trong khi startup có thể 20–45 giây.  
**Tại sao xảy ra:** Startup phase và steady-state health dùng cùng cơ chế.  
**Ảnh hưởng production:** Pod có thể bị restart trước khi startup hoàn tất.  
**Cách sửa:** Dùng `startupProbe` khi startup cần window riêng; sau khi startup probe thành công mới để liveness kiểm soát steady state.

### High — Chỉ khai báo limits, thiếu requests

**Vấn đề:** Không có CPU/memory requests.  
**Tại sao xảy ra:** Scheduler/resource guarantees không phản ánh nhu cầu workload.  
**Ảnh hưởng production:** Placement và QoS không có baseline phù hợp; contention có thể làm latency/probes thất thường. CPU limit thấp cũng có thể throttle workload nếu demand vượt limit.  
**Cách sửa:** Đo usage rồi đặt requests/limits phù hợp; quan sát CPU throttling và memory working set trước khi chọn số.

### Medium — Mutable image tag làm deployment/rollback không deterministic

**Vấn đề:** `image: ...:latest`.  
**Tại sao xảy ra:** Tag có thể trỏ tới artifact khác theo thời gian.  
**Ảnh hưởng production:** Khó audit version, reproduce incident và rollback chính xác.  
**Cách sửa:** Dùng immutable version tag hoặc digest do CI/CD phát hành.

### Medium — Readiness không chứng minh warm-up hoàn tất

**Vấn đề:** Scenario nói app cần warm metadata nhưng manifest chỉ gọi generic `/health`.  
**Tại sao xảy ra:** Health endpoint contract chưa gắn với khả năng serve request đúng.  
**Ảnh hưởng production:** Pod nhận traffic trước khi internal initialization hoàn tất.  
**Cách sửa:** Readiness chỉ success khi initialization cần thiết đã hoàn tất; tránh biến readiness thành deep dependency test quá đắt.

### Medium — Không thể hiện graceful termination/draining strategy

**Vấn đề:** Manifest không cho thấy app/rollout có đủ thời gian ngừng nhận request và hoàn tất in-flight work.  
**Tại sao xảy ra:** Rolling update chỉ được nhìn từ startup side.  
**Ảnh hưởng production:** Requests có thể fail khi old Pod terminate.  
**Cách sửa:** Xác minh ASP.NET Core graceful shutdown, termination grace period và endpoint removal behavior; thêm lifecycle handling nếu evidence cho thấy cần.

### Low — Resource numbers không có evidence

**Vấn đề:** `250m/256Mi` có vẻ được chọn cố định nhưng không có workload measurement.  
**Tại sao xảy ra:** Capacity planning dựa trên guess.  
**Ảnh hưởng production:** CPU throttling hoặc OOMKill nếu thấp; lãng phí nếu quá cao.  
**Cách sửa:** Dựa trên load test và production percentiles, rồi đặt alert trước saturation.

## Phiên bản đề xuất

Các con số dưới đây là ví dụ cấu trúc, không phải production sizing mặc định; requests/limits và probe thresholds phải được hiệu chỉnh bằng measurement.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: catalog-api
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example/catalog-api:2026.09.23.1
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Catalog
              valueFrom:
                secretKeyRef:
                  name: catalog-api-secrets
                  key: catalog-connection-string
            - name: PartnerApi__Key
              valueFrom:
                secretKeyRef:
                  name: catalog-api-secrets
                  key: partner-api-key
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
spec:
  selector:
    app: catalog-api
  ports:
    - port: 80
      targetPort: 8080
```

ASP.NET Core health checks cần map semantics tương ứng: `/health/live` không nên fail chỉ vì SQL có transient outage; `/health/ready` có thể phản ánh initialization và dependencies thực sự bắt buộc để serve traffic. Các values về resources/probes phải được benchmark/load-test và điều chỉnh theo môi trường.

## Giải thích thiết kế sau khi sửa

Startup probe cho app một startup window riêng mà không làm liveness restart sớm. Readiness quyết định Service routing; liveness chỉ quyết định process có cần restart. Rolling strategy giữ old capacity trong lúc Pod mới chưa ready nếu cluster có đủ surge headroom.

Secrets được reference thay vì embedded. Image version immutable giúp audit/rollback. Resource requests cho scheduler một baseline; limits kiểm soát upper bound nhưng phải tránh CPU throttling/OOM do sizing mù.

## Trade-offs

`maxUnavailable: 0` + surge cần thêm cluster capacity trong rollout. Readiness quá phụ thuộc vào downstream có thể loại toàn bộ Pods khi dependency chung lỗi; readiness quá nông lại đưa traffic vào Pod chưa usable. Startup probe dài quá mức có thể trì hoãn phát hiện startup thật sự bị treo. Secret objects vẫn cần RBAC/encryption/rotation; chỉ chuyển plaintext từ `env.value` sang Secret không tự động tạo security hoàn chỉnh.

## Cách kiểm thử

1. **Deployment validation:** deploy version mới với warm-up 45 giây; xác minh không nhận production traffic trước readiness success và rollout không tạo 5xx spike.
2. **Failure-path test:** làm SQL transiently unavailable; readiness phản ánh serving policy nhưng liveness không tạo restart storm.
3. **Load test:** rollout dưới peak-like traffic; đo p95/p99, CPU throttling, available replicas và error rate.
4. **Resource test:** chạy workload vượt CPU baseline và gần memory limit; xác minh alerts và behavior trước saturation/OOM.
5. **Rollback test:** rollback về immutable image version trước và xác minh configuration/schema compatibility.

## Quan sát trong production

Theo dõi Kubernetes Pod restarts, readiness transitions, rollout duration, unavailable replicas, events, OOMKilled và CPU throttling. Ở application layer theo dõi ASP.NET Core request rate/error/p95/p99, startup duration và dependency telemetry trong Application Insights. Correlate deployment version/digest với error-rate change. Alert khi available replicas giảm dưới capacity target, restart rate tăng hoặc rollout vượt expected duration.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL outage kéo dài 10 phút, readiness có nên fail trên mọi Pod không? Quyết định phụ thuộc requirement nào?
2. Khi nào CPU limit nên được bỏ hoặc đặt khác với request cho ASP.NET Core workload?
3. Nếu database migration không backward-compatible, probe/rolling update tốt có đủ làm deployment an toàn không?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Azure Service Bus redelivery phải được xem là behavior bình thường cần thiết kế cho; message settlement không biến external side effect thành exactly-once.
- Idempotency phải đi đến boundary thực hiện side effect; một flag domain như `PaymentStatus` không thay thế durable Inbox/Outbox semantics.
- Kubernetes readiness, liveness và startup probes giải quyết ba vấn đề khác nhau; dùng cùng endpoint/threshold có thể biến transient dependency issue thành restart storm.
- Rolling deployment safety phụ thuộc capacity, immutable artifacts, health semantics, resources, backward compatibility và observability chứ không chỉ việc Deployment báo `Available`.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; luôn xét ambiguous failure sau side effect.
- Thu nhỏ atomic transaction boundary rồi persist intent cho phần việc nằm ngoài boundary đó.
- Phân biệt “có thể nhận traffic” với “process cần restart”.
- Measure resource/probe behavior trước khi tăng timeout hoặc capacity bằng phỏng đoán.
- Test deployment và dependency failure path, không chỉ happy path.
