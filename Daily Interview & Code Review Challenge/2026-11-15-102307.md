# Code Review Challenge 1 — PostgreSQL keyset pagination bỏ sót đơn hàng khi đồng bộ

## Bối cảnh

Một API cung cấp incremental export đơn hàng cho đối tác ERP. Mỗi tenant có hàng triệu đơn, nhiều đơn được cập nhật cùng một millisecond. Worker ERP gọi nhiều trang liên tục; đôi khi bỏ sót đơn, đôi khi thấy đơn của tenant khác khi đổi tài khoản, và p99 tăng mạnh. Đối tác cần một feed có thể resume; cần làm rõ liệu yêu cầu là snapshot bất biến hay feed thay đổi liên tục. Giả định `UpdatedAt` được lưu theo UTC và có thể thay đổi khi sửa đơn.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/orders/export")]
public sealed class ExportController(AppDbContext db) : ControllerBase
{
    [HttpGet]
    public async Task<IActionResult> Get(
        [FromQuery] DateTime? after,
        [FromQuery] int page = 1,
        [FromQuery] int size = 500,
        CancellationToken ct = default)
    {
        var tenant = Request.Headers["X-Tenant-Id"].ToString();
        var query = db.Orders.AsNoTracking()
            .Where(o => after == null || o.UpdatedAt >= after)
            .OrderBy(o => o.UpdatedAt);

        var total = await query.CountAsync(ct);
        var rows = await query.Skip((page - 1) * size)
            .Take(size)
            .Select(o => new
            {
                o.Id, o.TenantId, o.UpdatedAt, o.Total,
                CustomerEmail = o.Customer.Email
            })
            .ToListAsync(ct);

        Response.Headers["X-Total-Count"] = total.ToString();
        Response.Headers["X-Next-Cursor"] =
            rows.Count == 0 ? "" : rows[^1].UpdatedAt.ToString("O");

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Tenant ID do client tự khai báo và không được lọc

**Vấn đề:** Đọc `X-Tenant-Id` nhưng không áp dụng filter; mọi tenant có thể xuất dữ liệu của nhau.  
**Tại sao xảy ra:** Không gắn identity được xác thực với data-access policy.  
**Ảnh hưởng production:** Rò rỉ dữ liệu đơn hàng và email khách hàng.  
**Cách sửa:** Bắt buộc authentication, resolve tenant từ claims đã xác thực và kiểm tra membership; filter `TenantId` ở truy vấn; kiểm tra quyền export.

### [High] — Thứ tự không ổn định khi timestamp trùng

**Vấn đề:** Chỉ `OrderBy(UpdatedAt)`, cursor chỉ chứa timestamp.  
**Tại sao xảy ra:** Nhiều hàng cùng khóa sắp xếp; `>=` khiến trùng lặp, còn đổi thành `>` có thể bỏ sót.  
**Ảnh hưởng production:** Feed mất hoặc lặp đơn.  
**Cách sửa:** Sort theo `UpdatedAt, Id`, cursor gồm cả hai và dùng seek predicate lexicographic.

### [High] — Offset pagination không ổn định dưới concurrent writes

**Vấn đề:** `Skip(page * size)` phụ thuộc vị trí thay đổi theo thời gian.  
**Tại sao xảy ra:** Insert/update giữa các request làm hàng dịch chuyển.  
**Ảnh hưởng production:** Trùng/bỏ sót và chi phí scan tăng.  
**Cách sửa:** Keyset pagination, xác định consistency contract; với feed không được mất thay đổi, dùng append-only change log/CDC có sequence.

### [High] — Không có ranh giới snapshot hoặc high-water mark

**Vấn đề:** `UpdatedAt` của order có thể thay đổi sau khi đã đọc.  
**Tại sao xảy ra:** Keyset trên bảng mutable không bảo đảm nhìn thấy mọi phiên bản thay đổi.  
**Ảnh hưởng production:** Incremental synchronization có thể mất sự kiện cập nhật.  
**Cách sửa:** Nếu cần reliable change feed, ghi change records trong cùng transaction và paginate theo sequence; nếu chỉ cần export snapshot, tạo snapshot/version có vòng đời rõ ràng.

### [Medium] — Không giới hạn page và size

**Vấn đề:** Client gửi số âm, zero hoặc kích thước cực lớn.  
**Tại sao xảy ra:** Thiếu validation và upper bound.  
**Ảnh hưởng production:** Tải DB, memory, overflow hoặc truy vấn vô nghĩa.  
**Cách sửa:** Giới hạn page size, xác thực cursor và trả ProblemDetails cho input không hợp lệ.

### [Medium] — CountAsync gây thêm truy vấn đắt

**Vấn đề:** Đếm toàn bộ tập dữ liệu ở mọi trang.  
**Tại sao xảy ra:** Contract dùng total count dù cursor feed không cần.  
**Ảnh hưởng production:** Tăng latency, I/O và contention.  
**Cách sửa:** Bỏ count khỏi hot path; nếu cần tổng số, tính riêng hoặc làm rõ tính gần đúng.

### [Medium] — Thiếu index phù hợp

**Vấn đề:** Không có bằng chứng index hỗ trợ tenant filter và thứ tự.  
**Tại sao xảy ra:** Query shape không được thiết kế theo access pattern.  
**Ảnh hưởng production:** Sort/scan lớn, p99 tăng.  
**Cách sửa:** Đánh giá `(TenantId, UpdatedAt, Id)` bằng EXPLAIN ANALYZE trên dữ liệu đại diện; xem xét covering index theo nhu cầu thực tế.

### [Medium] — Cursor không ràng buộc tenant, filter và phiên bản

**Vấn đề:** Cursor timestamp dạng string không có contract bảo vệ.  
**Tại sao xảy ra:** Thiếu versioning và validation.  
**Ảnh hưởng production:** Dùng lại cursor sai ngữ cảnh, kết quả không nhất quán.  
**Cách sửa:** Cursor opaque có version, tenant, filter hash và expiry; ký HMAC nếu cần chống sửa đổi.

### [Low] — Trả dữ liệu PII và count không có kiểm soát

**Vấn đề:** Email được export mặc định; count có thể tạo leakage khi authorization sai.  
**Tại sao xảy ra:** Projection không dựa trên data-minimization contract.  
**Ảnh hưởng production:** Tăng phạm vi lộ dữ liệu.  
**Cách sửa:** Xác nhận quyền truy cập field và nhu cầu tích hợp.

## Phiên bản đề xuất

Đây là giải pháp cho **bounded listing** với thứ tự ổn định; không tuyên bố bảo đảm CDC hoặc snapshot tuyệt đối. `ITenantContext` phải được xây từ authentication/authorization đã xác minh. Cursor được decode/validate bởi service riêng, bao gồm tenant và filter; ví dụ dưới đây dùng tuple đã được validate.

```csharp
public sealed record OrderCursor(DateTime UpdatedAt, Guid Id);

public sealed class OrderExportService(
    AppDbContext db, ITenantContext tenantContext)
{
    public async Task<(List<OrderRow> Rows, OrderCursor? Next)> ReadAsync(
        OrderCursor? cursor, int requestedSize, CancellationToken ct)
    {
        var tenantId = tenantContext.RequireAuthorizedTenant();
        if (requestedSize is < 1 or > 500)
            throw new ArgumentOutOfRangeException(nameof(requestedSize));

        var query = db.Orders.AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (cursor is not null)
        {
            query = query.Where(x =>
                x.UpdatedAt > cursor.UpdatedAt ||
                (x.UpdatedAt == cursor.UpdatedAt && x.Id.CompareTo(cursor.Id) > 0));
        }

        var rows = await query
            .OrderBy(x => x.UpdatedAt).ThenBy(x => x.Id)
            .Select(x => new OrderRow(x.Id, x.UpdatedAt, x.Total))
            .Take(requestedSize + 1)
            .ToListAsync(ct);

        var hasMore = rows.Count > requestedSize;
        if (hasMore) rows.RemoveAt(rows.Count - 1);
        var next = hasMore && rows.Count > 0
            ? new OrderCursor(rows[^1].UpdatedAt, rows[^1].Id)
            : null;
        return (rows, next);
    }
}

public sealed record OrderRow(Guid Id, DateTime UpdatedAt, decimal Total);
```

**Lưu ý implementation:** Translation của `Guid.CompareTo` phải được kiểm chứng với EF Core/Npgsql version đang dùng; nếu không được dịch thành SQL phù hợp, chọn khóa thứ tự database-native (ví dụ bigint sequence) hoặc raw SQL có tham số. Không dùng client-side evaluation để che lỗi translation. Với yêu cầu đồng bộ mọi thay đổi, thiết kế một bảng `OrderChange(Sequence, TenantId, OrderId, Payload, ...)` ghi cùng transaction và phân trang bằng `Sequence` thay vì `UpdatedAt`.

## Giải thích thiết kế sau khi sửa

Authorization được áp trước query; composite ordering tạo thứ tự toàn phần; `Take(size + 1)` cho biết còn trang tiếp theo mà không cần `COUNT`. Hợp đồng API phải nói rõ cursor biểu diễn listing hay change feed. Để tránh mất thay đổi khi cập nhật đồng thời, change log transactional là lựa chọn đúng khi business yêu cầu at-least-once delivery.

## Trade-offs

Keyset không hỗ trợ nhảy trực tiếp đến page N; opaque cursor tăng độ phức tạp client. Change log cần retention, cleanup, consumer checkpoint và monitoring. Snapshot export có thể cần storage và TTL. Index cải thiện đọc nhưng làm tăng write amplification; cần đo trước khi áp dụng.

## Cách kiểm thử

1. Security integration: tenant A không thể đọc đơn của tenant B, kể cả khi tự gửi header hoặc cursor khác tenant.
2. Database integration: nhiều hàng trùng timestamp vẫn được duyệt đúng một lần với cursor và thứ tự cố định.
3. Concurrency: insert/update trong khi đọc, đối chiếu kết quả với consistency contract đã chọn.
4. Load test: so sánh p95/p99 và query plan giữa offset sâu với seek pagination.
5. Failure-path: cursor sai chữ ký, sai filter, hết hạn và request bị cancel.

## Quan sát trong production

Structured logs có `tenantHash`, `requestId`, `cursorVersion`, `pageSize` nhưng không log PII/cursor nhạy cảm. Application Insights ghi latency, rows/page, DB dependency duration và error rate; PostgreSQL quan sát `pg_stat_statements`, execution plan, buffers và index usage. Alert khi export failures hoặc sync lag tăng; đối chiếu sequence/checkpoint nếu dùng change log.

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Product = { id: string; name: string; descriptionHtml: string }
const props = defineProps<{ tenantId: string; token: string }>()
const term = ref('')
const products = ref<Product[]>([])
const loading = ref(false)
const error = ref('')
const selected = ref<Product | null>(null)

async function search() {
  loading.value = true
  error.value = ''
  const url = '/api/products?tenant=' + props.tenantId +
    '&q=' + term.value
  console.debug('Search', url, props.token)
  try {
    const response = await fetch(url, {
      headers: { Authorization: 'Bearer ' + props.token }
    })
    const data = await response.json()
    products.value = data.items
  } catch (e) {
    error.value = String(e)
  }
  loading.value = false
}

watch(term, search)
onMounted(search)

function choose(product: Product) {
  selected.value = product
}
</script>

<template>
  <input v-model="term" aria-label="Search products" />
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="p in products" :key="p.id" @click="choose(p)">
      <strong>{{ p.name }}</strong>
      <div v-html="p.descriptionHtml"></div>
    </li>
  </ul>
  <section v-if="selected">{{ selected.name }}</section>
</template>
```

### [Critical] — Render HTML không đáng tin cậy

**Vấn đề:** `v-html` đưa nội dung đối tác trực tiếp vào DOM.  
**Tại sao xảy ra:** Vue không tự sanitize nội dung của `v-html`.

**Vấn đề:** `console.debug` in access token.  
**Tại sao xảy ra:** Debug logging không loại bỏ credential.  
**Ảnh hưởng production:** Token lộ qua console, công cụ ghi log hoặc bản chụp debug.

## Phiên bản đề xuất

Giải pháp tối giản ưu tiên plain text, debounce và request sequencing. Backend vẫn phải kiểm tra token, tenant membership và quyền xem sản phẩm; frontend không thể thay thế authorization.

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue'

type Product = { id: string; name: string; descriptionHtml: string }
const props = defineProps<{ tenantId: string; token: string }>()
const term = ref('')
const products = ref<Product[]>([])
const selected = ref<Product | null>(null)
const loading = ref(false)
const error = ref('')
let controller: AbortController | undefined
let timer: ReturnType<typeof setTimeout> | undefined
let generation = 0

watch([term, () => props.tenantId, () => props.token], () => {
  const current = ++generation
  controller?.abort()
  if (timer) clearTimeout(timer)
  products.value = []
  selected.value = null
  error.value = ''
  loading.value = false

  timer = setTimeout(async () => {
    const active = new AbortController()
    controller = active
    loading.value = true
    try {
      const params = new URLSearchParams({
        tenant: props.tenantId,
        q: term.value.trim()
      })
      const response = await fetch('/api/products?' + params, {
        headers: { Authorization: 'Bearer ' + props.token },
        signal: active.signal
      })
      if (!response.ok) throw new Error('Search unavailable')
      const data: { items: Product[] } = await response.json()
      if (current === generation && !active.signal.aborted)
        products.value = data.items
    } catch (e) {
      if (current === generation && !active.signal.aborted)
        error.value = 'Không thể tải kết quả. Vui lòng thử lại.'
    } finally {
      if (current === generation) loading.value = false
    }
  }, 250)
}, { immediate: true })

onBeforeUnmount(() => {
  generation++
  if (timer) clearTimeout(timer)
  controller?.abort()
})
</script>

<template>
  <input v-model="term" aria-label="Search products" />
  <p v-if="loading" role="status">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <ul>
    <li v-for="p in products" :key="p.id">
      <button type="button" @click="selected = p">
        {{ p.name }}
      </button>
      <div>{{ p.descriptionHtml }}</div>
    </li>
  </ul>
  <section v-if="selected">{{ selected.name }}</section>
</template>
```

## Giải thích thiết kế sau khi sửa

`generation` ngăn response stale commit state ngay cả khi abort không đủ nhanh; `AbortController` giảm công việc không cần thiết ở client/network, không bảo đảm server đã dừng xử lý. `watch` bao phủ tenant và credential rotation. Interpolation tránh thực thi HTML. Error message được chuẩn hóa; authorization vẫn thuộc backend.

## Trade-offs

Debounce tăng độ trễ cảm nhận khoảng 250 ms; cần đo và điều chỉnh. Clear results ngay khi tìm kiếm có thể gây flicker; nếu giữ stale results, phải phân biệt trạng thái và tuyệt đối không giữ dữ liệu tenant cũ. Plain text mất rich formatting; sanitizer cần quy tắc và bảo trì. Token trong props vẫn có rủi ro nếu kiến trúc ứng dụng cho phép script không đáng tin cậy; cân nhắc BFF/HttpOnly cookie và CSRF protection theo threat model.

## Cách kiểm thử

1. Component test với deferred promises: request cũ hoàn thành sau request mới, UI chỉ hiển thị dữ liệu mới.
2. Integration test: đổi tenant và token khi request đang chạy; kết quả và selection tenant cũ bị xóa.
3. Security test: HTML chứa payload sự kiện/script được hiển thị như text, không chạy.
4. API test: 401/403/500, network error và aborted request cho UI state nhất quán.
5. Playwright E2E: gõ nhanh với network throttling; xác nhận số request, trạng thái loading và khả năng keyboard navigation.

## Quan sát trong production

Theo dõi client search latency, aborted request count, error rate, stale-response suppression và request volume trên mỗi phiên ở dạng aggregate. Backend log `traceId`, tenant đã xác thực (dạng an toàn), status và dependency latency; không log token, query chứa PII hoặc response nhạy cảm. Cảnh báo khi 403 tăng, p95 search tăng hoặc tỷ lệ lỗi vượt SLO; kiểm tra browser network waterfall cùng server traces.

## Câu hỏi phỏng vấn mở rộng

1. Khi cần render rich HTML từ CMS, bạn định nghĩa allowlist và CSP như thế nào?
2. Nếu nhiều component dùng chung search cache, cache key cần chứa những dimensions nào?
3. Khi chuyển sang BFF authentication, bạn xử lý CSRF và session expiration thế nào?

## Kiến thức trọng tâm

- Data isolation phải được enforce tại server; cursor và UI không phải authorization boundary.
