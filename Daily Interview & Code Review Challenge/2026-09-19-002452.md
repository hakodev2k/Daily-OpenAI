# Code Review Challenge 1 — File upload API tin `Content-Type` và đọc toàn bộ file vào memory

**Chủ đề:** ASP.NET Core, Azure Blob Storage, file upload security, streaming, Managed Identity, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một enterprise portal cho phép nhân viên upload tài liệu PDF lên ASP.NET Core API. API chạy nhiều instances trên Azure App Service và lưu file vào Azure Blob Storage. Production gần đây xuất hiện memory spikes khi nhiều người upload đồng thời; một security review cũng phát hiện backend đang tin metadata do browser gửi lên.

Business yêu cầu file tối đa 50 MB, chỉ chấp nhận PDF, file phải private và chỉ người có quyền mới được truy cập. Team muốn tránh lưu temporary file trên local filesystem. Blob Storage account đã có thể được truy cập bằng Managed Identity, nhưng code hiện tại vẫn dùng connection string.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly IConfiguration _configuration;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        IConfiguration configuration,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _configuration = configuration;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file");

        if (file.ContentType != "application/pdf")
            return BadRequest("PDF only");

        using var ms = new MemoryStream();
        await file.CopyToAsync(ms);

        var connectionString = _configuration["Storage:ConnectionString"];
        var service = new BlobServiceClient(connectionString);
        var container = service.GetBlobContainerClient("documents");

        await container.CreateIfNotExistsAsync(PublicAccessType.Blob);

        var blobName = $"{Guid.NewGuid()}-{file.FileName}";
        var blob = container.GetBlobClient(blobName);

        ms.Position = 0;
        await blob.UploadAsync(ms, overwrite: true);

        var document = new Document
        {
            FileName = file.FileName,
            BlobName = blobName,
            ContentType = file.ContentType,
            Size = file.Length,
            UploadedBy = User.Identity?.Name,
            UploadedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} to {BlobUri}",
            file.FileName,
            blob.Uri);

        return Ok(new { document.Id, Url = blob.Uri.ToString() });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và security problems trong upload flow.
2. Xác định performance/reliability concerns khi nhiều uploads chạy đồng thời.
3. Giải thích production impact của public blob, memory buffering và partial failure giữa Blob Storage/SQL.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected implementation/design phù hợp private document storage.
6. Giải thích security, integration, load và failure-path tests.
7. Nêu telemetry production để phát hiện abuse, upload failure và memory pressure.

## Câu hỏi gợi mở

1. Browser-controlled `Content-Type` có chứng minh bytes thực sự là PDF không?
2. Điều gì xảy ra nếu 100 requests cùng upload file 50 MB và mỗi request tạo một `MemoryStream`?
3. `PublicAccessType.Blob` có phù hợp requirement private document không?
4. Nếu Blob upload thành công nhưng SQL `SaveChangesAsync` thất bại thì hệ thống còn state gì?
5. `file.FileName` có nên được dùng trực tiếp như một phần storage key hoặc log field không?

### Gợi ý 2

Xem thêm identity/secrets, authorization, private access, cancellation và transaction boundary giữa Blob Storage với SQL.

## Kết quả code review tham khảo

### Critical — Container được tạo với public blob access

**Vấn đề:** `CreateIfNotExistsAsync(PublicAccessType.Blob)` cho phép anonymous access ở mức blob nếu storage account policy cho phép.  
**Tại sao xảy ra:** code biến storage privacy thành implementation default trái requirement.  
**Ảnh hưởng production:** tài liệu nội bộ có thể bị truy cập ngoài authorization path của application.  
**Cách sửa:** container phải private; authorization được enforce trước upload/download. Khi cần client access trực tiếp, cấp quyền ngắn hạn theo policy phù hợp thay vì public container.

### Critical — Không có authorization policy cho upload

**Vấn đề:** endpoint không thể hiện yêu cầu quyền upload ngoài việc có thể có một `User.Identity`.  
**Tại sao xảy ra:** authentication identity bị nhầm với authorization decision.  
**Ảnh hưởng production:** user không đủ quyền có thể upload content hoặc tiêu thụ storage.  
**Cách sửa:** áp dụng policy-based authorization phù hợp business role/ownership và kiểm tra authorization riêng cho download/delete.

### High — Tin `Content-Type` do client cung cấp

**Vấn đề:** `file.ContentType == "application/pdf"` không xác minh nội dung.  
**Tại sao xảy ra:** multipart metadata do client kiểm soát.  
**Ảnh hưởng production:** file không phải PDF có thể được lưu dưới nhãn PDF; downstream processing có thể gặp security/correctness risk.  
**Cách sửa:** validate allow-list extension chỉ như UX signal, kiểm tra signature/content bằng parser/validation strategy phù hợp, giới hạn processing và coi file là untrusted input. Nếu domain yêu cầu malware scanning, thêm quarantine/scanning workflow thay vì tuyên bố MIME check là đủ.

### High — Không enforce 50 MB application limit

**Vấn đề:** code chỉ kiểm tra `Length == 0`.  
**Tại sao xảy ra:** business size constraint chưa được enforce ở endpoint/hosting boundary.  
**Ảnh hưởng production:** oversized uploads tiêu thụ bandwidth/memory/storage và tăng DoS risk.  
**Cách sửa:** enforce request/form/file size limits ở layers phù hợp và kiểm tra lại `file.Length` trong application.

### High — Buffer toàn bộ file vào `MemoryStream`

**Vấn đề:** mỗi upload copy toàn bộ file vào managed memory trước khi gửi Blob Storage.  
**Tại sao xảy ra:** implementation biến file size thành per-request memory footprint lớn.  
**Ảnh hưởng production:** concurrent uploads gây allocation/GC pressure, memory spikes và có thể dẫn tới process recycle/OOM.  
**Cách sửa:** stream từ upload source tới Blob Storage khi framework/validation pipeline cho phép; nếu cần inspect prefix/signature, chỉ buffer phần cần thiết hoặc dùng controlled temporary/quarantine strategy. Đo memory và concurrency trước khi chọn buffering model.

### High — Secret-based connection string được đọc trong request path dù Managed Identity khả dụng

**Vấn đề:** application phụ thuộc storage account credential trong configuration.  
**Tại sao xảy ra:** identity capability hiện có chưa được dùng.  
**Ảnh hưởng production:** secret rotation/exposure surface lớn hơn và quyền có thể rộng hơn cần thiết.  
**Cách sửa:** cấu hình `BlobServiceClient` qua DI với Azure identity/Managed Identity và least-privilege RBAC phù hợp; không tạo client thủ công cho mỗi request.

### High — Partial failure tạo orphan blob

**Vấn đề:** Blob upload hoàn tất trước SQL insert; SQL failure để lại blob không có metadata row.  
**Tại sao xảy ra:** Blob Storage và SQL không có atomic local transaction chung.  
**Ảnh hưởng production:** orphaned data, storage leak và khó audit.  
**Cách sửa:** thiết kế explicit state/reconciliation: tạo metadata `Pending`, upload bằng stable ID rồi mark `Ready`, hoặc compensating delete khi safe; có sweeper cho stale pending/orphan objects. Không giả định distributed transaction.

### Medium — File name từ client được dùng trong blob key và log

**Vấn đề:** original filename là untrusted metadata và có thể chứa ký tự bất thường hoặc dữ liệu nhạy cảm.  
**Tại sao xảy ra:** storage identity và display metadata bị trộn.  
**Ảnh hưởng production:** log pollution, privacy exposure, khó canonicalize và storage naming không ổn định.  
**Cách sửa:** storage key dùng server-generated identifier; original filename được normalize/validate và lưu riêng cho display nếu business cần.

### Medium — Cancellation không được propagate

**Vấn đề:** upload, Blob operations và EF call không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** request lifecycle chưa được truyền xuống I/O.  
**Ảnh hưởng production:** client disconnect vẫn có thể để expensive work tiếp tục không cần thiết.  
**Cách sửa:** truyền cancellation token qua async I/O, nhưng thiết kế cleanup/reconciliation để cancellation giữa các resource boundaries không tạo inconsistent state.

### Medium — Client được tạo lại và container initialization nằm trong hot path

**Vấn đề:** `BlobServiceClient` và container initialization được thực hiện mỗi upload.  
**Tại sao xảy ra:** infrastructure configuration nằm trong controller action.  
**Ảnh hưởng production:** thêm overhead và làm lifecycle/configuration khó quản lý.  
**Cách sửa:** register client/service qua DI; provision container bằng deployment/infrastructure setup hoặc idempotent startup process phù hợp.

### Low — Log/response tiết lộ storage URI không cần thiết

**Vấn đề:** API trả raw blob URI và log URI dù access phải đi qua authorization model.  
**Tại sao xảy ra:** physical storage location bị coi như public resource identity.  
**Ảnh hưởng production:** tăng information exposure và coupling client với storage layout.  
**Cách sửa:** trả application document ID/download endpoint; log stable document/blob IDs với structured fields và tránh sensitive metadata.

## Phiên bản đề xuất

Ví dụ rút gọn dưới đây giả định container private đã được provision, `BlobContainerClient` dùng Managed Identity qua DI và application có một validator phù hợp domain:

```csharp
[Authorize(Policy = "CanUploadDocuments")]
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxFileSize = 50L * 1024 * 1024;
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly IPdfValidator _pdfValidator;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        IPdfValidator pdfValidator)
    {
        _container = container;
        _db = db;
        _pdfValidator = pdfValidator;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(
        IFormFile file,
        CancellationToken ct)
    {
        if (file is null || file.Length is <= 0 or > MaxFileSize)
            return BadRequest("Invalid file size.");

        await using var source = file.OpenReadStream(MaxFileSize);

        if (!await _pdfValidator.IsValidAsync(source, ct))
            return BadRequest("Invalid PDF.");

        source.Position = 0;

        var documentId = Guid.NewGuid();
        var blobName = $"documents/{documentId:N}";

        var document = new Document
        {
            Id = documentId,
            FileName = NormalizeDisplayName(file.FileName),
            BlobName = blobName,
            ContentType = "application/pdf",
            Size = file.Length,
            Status = DocumentStatus.Pending,
            UploadedBy = User.FindFirstValue(ClaimTypes.NameIdentifier),
            UploadedUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(ct);

        try
        {
            var blob = _container.GetBlobClient(blobName);
            await blob.UploadAsync(source, overwrite: false, ct);

            document.Status = DocumentStatus.Ready;
            await _db.SaveChangesAsync(ct);
        }
        catch
        {
            document.Status = DocumentStatus.Failed;
            await _db.SaveChangesAsync(CancellationToken.None);
            throw;
        }

        return CreatedAtAction(
            nameof(GetDocument),
            new { id = document.Id },
            new { document.Id, document.FileName, document.Size });
    }

    [HttpGet("{id:guid}")]
    public IActionResult GetDocument(Guid id) => throw new NotImplementedException();
}
```

`IPdfValidator` phải có contract rõ về stream seekability và mức validation. Nếu scanning nặng hoặc malware scanning là requirement, upload nên vào private quarantine location rồi xử lý asynchronously trước khi document chuyển sang `Ready`. Download path phải authorize ownership/role và có thể stream qua backend hoặc phát hành time-limited access phù hợp requirement.

## Giải thích thiết kế sau khi sửa

Storage identity được tách khỏi original filename. Blob luôn private, identity dùng Managed Identity, và application giữ durable processing state để nhận biết partial failure. Streaming tránh copy toàn bộ payload sang một `MemoryStream`; validation chỉ nên buffer lượng dữ liệu thật sự cần. Authorization là một phần của API contract chứ không phụ thuộc việc blob URL khó đoán.

## Trade-offs

State machine `Pending/Ready/Failed` và reconciliation tăng code/schema nhưng làm failure visible. Backend-proxied download cho authorization tập trung nhưng tiêu tốn application bandwidth; short-lived delegated access giảm tải backend nhưng tăng complexity và phải kiểm soát expiry/permissions. Malware scanning asynchronous tăng latency trước khi file khả dụng nhưng thường an toàn hơn việc cho untrusted content đi thẳng vào downstream workflows.

## Cách kiểm thử

1. **Security test:** upload file giả PDF với `Content-Type: application/pdf`; validator phải reject theo policy.
2. **Authorization test:** unauthenticated hoặc user không có policy không thể upload/download document.
3. **Load test:** concurrent 50 MB uploads không làm memory tăng tuyến tính theo toàn bộ payload buffering.
4. **Failure-path integration test:** Blob thành công nhưng metadata transition thất bại; reconciliation xác định và recover/cleanup được state.
5. **Cancellation test:** client disconnect giữa upload; workflow kết thúc ở state có thể quan sát/reconcile, không để silent orphan.

## Quan sát trong production

Theo dõi upload count/size/duration, rejection reason, authorization failures, `Pending/Failed` age, orphan reconciliation count, Blob dependency latency/errors, process memory/GC, request aborts và storage growth. Application Insights traces nên correlate `DocumentId`, user subject identifier và blob operation ID nhưng không log file contents hoặc sensitive filenames nếu không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn direct-to-Blob upload bằng delegated access thay vì proxy toàn bộ bytes qua ASP.NET Core?
2. Nếu PDF scanning mất 30 giây, bạn thay đổi API/workflow thế nào?
3. Managed Identity giảm loại rủi ro nào nhưng không thay thế authorization ở application ra sao?

# Code Review Challenge 2 — SQL pagination càng về cuối càng chậm và trả item lặp khi dữ liệu thay đổi

**Chủ đề:** SQL Server, pagination, composite index, deterministic ordering, keyset pagination, query performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một order-management portal hiển thị lịch sử đơn hàng theo `CreatedUtc` mới nhất trước. API nhận `page` và `pageSize`, chạy SQL bên dưới. Bảng `Orders` có khoảng 80 triệu rows và tiếp tục tăng. Page đầu nhanh, nhưng page sâu có thể mất vài giây. Trong lúc traffic cao, user đôi khi thấy cùng một order xuất hiện ở hai pages hoặc một order bị bỏ qua khi có order mới được insert giữa hai requests.

Business chủ yếu dùng “Next”/“Previous”; họ hiếm khi nhảy trực tiếp tới page 5000. UI cần sort ổn định. Team đề xuất thêm một index chỉ trên `CreatedUtc` và giữ nguyên offset pagination.

## Đoạn code cần review

```sql
CREATE PROCEDURE dbo.GetOrders
    @CustomerId uniqueidentifier,
    @Page int,
    @PageSize int
AS
BEGIN
    SELECT
        o.Id,
        o.CustomerId,
        o.CreatedUtc,
        o.Status,
        o.TotalAmount
    FROM dbo.Orders o
    WHERE o.CustomerId = @CustomerId
    ORDER BY o.CreatedUtc DESC
    OFFSET (@Page - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
GO

CREATE INDEX IX_Orders_CreatedUtc
ON dbo.Orders (CreatedUtc DESC);
```

## Nhiệm vụ của ứng viên

1. Xác định correctness issues trong ordering/pagination.
2. Xác định performance concerns khi page offset lớn.
3. Giải thích vì sao index hiện tại có thể không phù hợp access pattern.
4. Ưu tiên findings theo user impact và scale.
5. Đề xuất query/index/API contract tốt hơn cho Next/Previous navigation.
6. Giải thích database/load/concurrency tests.
7. Nêu execution-plan và production metrics cần quan sát.

## Câu hỏi gợi mở

1. `CreatedUtc` có guaranteed unique không?
2. Khi nhiều rows có cùng timestamp, database có nghĩa vụ giữ cùng thứ tự giữa requests không?
3. Offset 5 triệu rows có nghĩa database chỉ cần đọc 20 rows cuối cùng không?
4. Filter bắt đầu bằng `CustomerId`, vậy index chỉ trên `CreatedUtc` phục vụ query shape này thế nào?
5. Nếu có insert mới giữa page 1 và page 2, offset của các rows cũ thay đổi ra sao?

## Gợi ý

### Gợi ý 1

Có hai vấn đề độc lập: work tăng theo offset và page boundary không ổn định khi ordering/data thay đổi.

### Gợi ý 2

Hãy nghĩ theo access path `(CustomerId, CreatedUtc, Id)` và cursor đại diện cho row cuối cùng của page trước.

## Kết quả code review tham khảo

### High — `ORDER BY CreatedUtc` không deterministic khi timestamp trùng

**Vấn đề:** nhiều orders có thể có cùng `CreatedUtc`, nhưng query không có tie-breaker.  
**Tại sao xảy ra:** SQL chỉ đảm bảo ordering theo keys được yêu cầu; các rows bằng nhau trên sort key không có stable relative order contract.  
**Ảnh hưởng production:** item có thể đổi vị trí giữa executions, gây duplicate/missing page entries ngay cả khi data ít thay đổi.  
**Cách sửa:** dùng total ordering, ví dụ `ORDER BY CreatedUtc DESC, Id DESC` nếu `Id` là tie-breaker phù hợp.

### High — Deep offset pagination phải bỏ qua lượng rows ngày càng lớn

**Vấn đề:** `OFFSET` tăng theo page number.  
**Tại sao xảy ra:** engine vẫn phải xác định/order/skip các rows trước page cần trả; cost không chỉ bằng `PageSize`.  
**Ảnh hưởng production:** latency và reads tăng ở page sâu, gây database pressure.  
**Cách sửa:** với Next/Previous-heavy UX, dùng keyset/seek pagination theo stable sort keys; giữ offset chỉ nếu random page access là requirement đủ quan trọng.

### High — Offset boundary dịch chuyển khi concurrent inserts xảy ra

**Vấn đề:** page 2 được tính lại bằng vị trí hiện tại, không phải snapshot của page 1.  
**Tại sao xảy ra:** new rows ở đầu result set đẩy offsets.  
**Ảnh hưởng production:** duplicate hoặc missing orders giữa navigation requests.  
**Cách sửa:** keyset cursor dựa trên last seen `(CreatedUtc, Id)` giữ boundary logic ổn định hơn trước inserts ở phía trước. Nếu requirement là snapshot consistency tuyệt đối qua nhiều requests, cần contract/state khác; keyset không tự tạo multi-request transaction snapshot.

### High — Index không bắt đầu bằng equality filter chính

**Vấn đề:** `IX_Orders_CreatedUtc` không align tốt với access pattern `CustomerId = ?` rồi order theo time.  
**Tại sao xảy ra:** key order của index quyết định khả năng seek/range scan hữu ích.  
**Ảnh hưởng production:** nhiều reads/sort/work hơn cần thiết tùy data distribution và plan.  
**Cách sửa:** đánh giá composite index như `(CustomerId, CreatedUtc DESC, Id DESC)` và include projected columns khi evidence cho thấy lookup cost đáng kể. Xác minh bằng actual execution plan và workload, không tạo index chỉ theo intuition.

### Medium — Arithmetic/page validation chưa rõ

**Vấn đề:** procedure không validate `@Page >= 1`, `@PageSize` hợp lệ hoặc multiplication range.  
**Tại sao xảy ra:** API contract assumptions không được enforce ở database boundary.  
**Ảnh hưởng production:** invalid requests có thể fail hoặc tạo query behavior không mong muốn.  
**Cách sửa:** validate ở API và defensive validation ở procedure nếu đây là public/shared DB contract; giới hạn maximum page size.

### Medium — API contract buộc client nghĩ theo page number dù UX chủ yếu là sequential

**Vấn đề:** page-number abstraction khuyến khích random offset dù product behavior là Next/Previous.  
**Tại sao xảy ra:** storage/query model và UX chưa được align.  
**Ảnh hưởng production:** khó chuyển sang efficient seek semantics và client có thể phụ thuộc page count không cần thiết.  
**Cách sửa:** trả opaque continuation cursor/token cho sequential navigation; không expose internal tuple nếu muốn giữ khả năng thay đổi implementation.

### Medium — Index proposal chưa xét write/storage cost

**Vấn đề:** thêm composite/covering index có chi phí.  
**Tại sao xảy ra:** read optimization dễ bỏ qua write amplification và storage.  
**Ảnh hưởng production:** inserts/updates tốn thêm I/O và maintenance.  
**Cách sửa:** chọn included columns dựa trên execution plan, lookup frequency, read/write ratio và index size; không mặc định cover mọi selected column.

### Low — Không có strategy rõ cho backward navigation

**Vấn đề:** keyset “Next” dễ hơn “Previous”, nhưng product yêu cầu cả hai.  
**Tại sao xảy ra:** cursor contract chưa được thiết kế hai chiều.  
**Ảnh hưởng production:** implementation có thể quay lại offset cho Previous hoặc tạo ordering bug.  
**Cách sửa:** thiết kế before/after cursor semantics hoặc reverse comparison/order rồi normalize output; test boundaries kỹ.

## Phiên bản đề xuất

Một hướng keyset pagination cho trang tiếp theo:

```sql
CREATE INDEX IX_Orders_Customer_Created_Id
ON dbo.Orders (CustomerId, CreatedUtc DESC, Id DESC)
INCLUDE (Status, TotalAmount);
GO

CREATE PROCEDURE dbo.GetOrdersNext
    @CustomerId uniqueidentifier,
    @PageSize int,
    @AfterCreatedUtc datetime2 = NULL,
    @AfterId uniqueidentifier = NULL
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 100
        THROW 50001, 'Invalid page size', 1;

    SELECT TOP (@PageSize)
        o.Id,
        o.CustomerId,
        o.CreatedUtc,
        o.Status,
        o.TotalAmount
    FROM dbo.Orders o
    WHERE o.CustomerId = @CustomerId
      AND (
          @AfterCreatedUtc IS NULL
          OR o.CreatedUtc < @AfterCreatedUtc
          OR (o.CreatedUtc = @AfterCreatedUtc AND o.Id < @AfterId)
      )
    ORDER BY o.CreatedUtc DESC, o.Id DESC;
END
```

API có thể trả opaque cursor encode/sign tuple của row cuối thay vì bắt client hiểu SQL keys. Với `Previous`, dùng inverse predicate/order hoặc cursor semantics riêng rồi trả result theo display order mong muốn. Nếu `uniqueidentifier` không có ordering semantics phù hợp business/performance goals, chọn stable unique tie-breaker khác theo schema thực tế; điểm bắt buộc là ordering phải total và cursor phải dùng cùng keys.

## Giải thích thiết kế sau khi sửa

Composite key bắt đầu bằng `CustomerId` phù hợp equality partition của query, sau đó giữ rows theo display order. Seek predicate bắt đầu sau row cuối đã thấy thay vì đếm lại hàng triệu rows. Cursor boundary ít bị ảnh hưởng bởi inserts mới ở đầu danh sách. Tuy nhiên keyset không cung cấp snapshot consistency tuyệt đối nếu rows cũ bị update làm thay đổi sort key; nếu business yêu cầu immutable browsing snapshot, cần thêm snapshot/version semantics.

## Trade-offs

Keyset pagination không hỗ trợ jump-to-page-N tự nhiên và total page count có thể đắt. Cursor contract phức tạp hơn page number nhưng phù hợp UX sequential. Composite covering index tăng storage/write cost. Nếu dataset nhỏ hoặc random page navigation là requirement cốt lõi, offset có thể vẫn hợp lý; quyết định phải dựa trên workload và latency target.

## Cách kiểm thử

1. **Database test:** nhiều rows có cùng `CreatedUtc`; pagination không duplicate/miss do tie ordering.
2. **Concurrency test:** insert orders mới giữa hai page requests; cursor navigation không lặp row từ page trước.
3. **Performance test:** so logical reads/duration của offset page sâu với keyset trên production-like cardinality.
4. **Execution-plan validation:** xác minh access path sử dụng index hợp lý và không tạo unexpected sort/scan.
5. **API/E2E test:** Next/Previous cursors giữ đúng order và reject malformed/expired cursor theo contract.

## Quan sát trong production

Theo dõi query duration p95/p99, logical reads, rows examined/returned, execution plan regressions, database CPU/waits, index usage/size và page-depth/cursor usage distribution. Correlate slow API requests với SQL dependency telemetry trong Application Insights để tránh tối ưu database khi latency nằm ở layer khác.

## Câu hỏi phỏng vấn mở rộng

1. Keyset pagination xử lý concurrent inserts tốt hơn offset nhưng có còn anomaly nào khi `CreatedUtc` của row cũ bị update không?
2. Nếu Product bắt buộc jump trực tiếp tới page 5000, bạn cân bằng UX requirement và query cost thế nào?
3. Khi nào `INCLUDE (Status, TotalAmount)` đáng giá và khi nào nó làm index quá nặng?

# Tổng kết hôm nay

## Kiến thức trọng tâm

File upload là trust boundary và resource-management problem, không chỉ là thao tác copy bytes. Private storage, authorization, validation, streaming, identity và partial-failure recovery phải được thiết kế cùng nhau. Với pagination, correctness của ordering và access pattern của index quan trọng ngang performance; offset phù hợp một số UX nhưng không phải mặc định cho dataset lớn và sequential navigation.

## Mẫu tư duy cần nhớ

* Không tin metadata từ client như bằng chứng security.
* Resource cost phải được nhân với concurrency, không đánh giá trên một request đơn lẻ.
* External resources không có atomic transaction chung thì phải thiết kế state/reconciliation.
* Stable pagination cần total ordering và boundary semantics rõ ràng.
* Index phải phục vụ query access pattern và được xác minh bằng execution plan/measurements.
