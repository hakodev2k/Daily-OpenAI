# Code Review Challenge 1 — Background job dùng `Skip/Take` trên dữ liệu đang thay đổi làm bỏ sót và xử lý trùng record

**Chủ đề:** Background jobs, SQL correctness, pagination, concurrency, idempotency, failure recovery, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 9–11 vấn đề

## Bối cảnh

Một Hangfire job chạy mỗi 10 phút để tìm các `NotificationDelivery` đang ở trạng thái `Pending`, gửi chúng tới external notification provider rồi đánh dấu `Sent`.

Bảng hiện có vài triệu record. Mỗi lần chạy job xử lý theo batch 500 record để tránh load toàn bộ dữ liệu vào memory. Trong lúc job chạy, các API khác vẫn liên tục insert delivery mới và một số worker khác có thể retry delivery lỗi.

Production ghi nhận:

- một số delivery nằm `Pending` nhiều giờ dù job vẫn chạy thành công,
- một số delivery được gửi hai lần,
- số record xử lý theo từng page không ổn định,
- khi provider timeout giữa batch, lần chạy sau đôi lúc gửi lại các delivery đã gửi thành công trước đó,
- tăng số Hangfire worker khiến duplicate tăng nhiều hơn,
- log chỉ ghi `Processed 500 items` mà không có cursor, delivery id range hoặc retry reason.

Business yêu cầu delivery có thể được xử lý lại khi chưa xác định được kết quả, nhưng không được dựa vào offset pagination nếu điều đó làm bỏ sót dữ liệu. Provider hỗ trợ một `Idempotency-Key` do client truyền vào.

## Đoạn code cần review

```csharp
public sealed class NotificationDeliveryJob
{
    private readonly AppDbContext _db;
    private readonly NotificationClient _client;
    private readonly ILogger<NotificationDeliveryJob> _logger;

    public NotificationDeliveryJob(
        AppDbContext db,
        NotificationClient client,
        ILogger<NotificationDeliveryJob> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        const int pageSize = 500;
        var page = 0;

        while (true)
        {
            var deliveries = await _db.NotificationDeliveries
                .Where(x => x.Status == DeliveryStatus.Pending)
                .OrderBy(x => x.CreatedAt)
                .Skip(page * pageSize)
                .Take(pageSize)
                .ToListAsync(cancellationToken);

            if (deliveries.Count == 0)
                break;

            foreach (var delivery in deliveries)
            {
                await _client.SendAsync(
                    delivery.Destination,
                    delivery.Payload,
                    cancellationToken);

                delivery.Status = DeliveryStatus.Sent;
                delivery.SentAt = DateTime.UtcNow;
            }

            await _db.SaveChangesAsync(cancellationToken);

            _logger.LogInformation(
                "Processed {Count} notification deliveries on page {Page}",
                deliveries.Count,
                page);

            page++;
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Offset pagination trên tập `Pending` đang co lại làm bỏ sót record

**Problem:** Sau khi page 0 được xử lý và đổi trạng thái sang `Sent`, tập `Pending` ngắn đi nhưng page tiếp theo vẫn `Skip(500)`.  
**Why it happens:** Offset được tính dựa trên vị trí trong tập kết quả hiện tại, trong khi chính job làm thay đổi tập đó.  
**Production impact:** Có thể bỏ qua một nhóm delivery và để chúng `Pending` cho đến run khác, thậm chí lâu hơn nếu pattern lặp lại.  
**Severity:** Critical  
**Recommended fix:** Không tăng offset trên tập đang mutate. Dùng keyset/cursor ổn định hoặc luôn lấy batch đầu tiên sau khi đã atomically claim các item.

### 2. Không có cơ chế claim/lease giữa nhiều worker

**Problem:** Hai worker có thể query cùng các record `Pending` trước khi bất kỳ worker nào cập nhật trạng thái.  
**Why it happens:** Query và việc đánh dấu ownership không atomic.  
**Production impact:** Cùng delivery có thể được gửi nhiều lần.  
**Severity:** Critical  
**Recommended fix:** Atomically claim batch bằng trạng thái như `Processing`, lease owner + lease expiry, hoặc database locking/update phù hợp provider; bảo đảm hai worker không cùng claim một item.

### 3. External side effect và DB state không cùng transaction

**Problem:** Provider có thể nhận message thành công nhưng process chết trước khi DB ghi `Sent`.  
**Why it happens:** Không thể dùng một local DB transaction để atomically commit cả database và external provider.  
**Production impact:** Retry sẽ gửi lại cùng message.  
**Severity:** Critical  
**Recommended fix:** Dùng idempotency key ổn định theo `DeliveryId` ở provider; lưu attempt/result state; thiết kế theo at-least-once thay vì giả định exactly-once.

### 4. Không truyền idempotency key cho provider

**Problem:** Business cho biết provider hỗ trợ idempotency nhưng code không sử dụng.  
**Why it happens:** Retry semantics không được thiết kế cùng side effect.  
**Production impact:** Network timeout hoặc crash có thể biến retry hợp lệ thành duplicate notification.  
**Severity:** High  
**Recommended fix:** Gửi `DeliveryId` hoặc một business operation id ổn định làm `Idempotency-Key`.

### 5. Batch chỉ `SaveChanges` sau khi gửi toàn bộ 500 item

**Problem:** Tiến độ của các item đã gửi thành công chưa được persist cho đến cuối batch.  
**Why it happens:** Một unit of work quá lớn bao quanh nhiều external side effect.  
**Production impact:** Failure ở item 499 có thể làm lần chạy sau coi 498 item trước là chưa xử lý.  
**Severity:** High  
**Recommended fix:** Persist trạng thái attempt theo từng item hoặc theo chunk nhỏ; kết hợp idempotency để retry an toàn.

### 6. Không có trạng thái `Processing`/attempt metadata

**Problem:** Chỉ có `Pending` và `Sent`, không thể phân biệt chưa xử lý, đang xử lý, retry hay stuck.  
**Why it happens:** State machine quá đơn giản cho background processing có failure.  
**Production impact:** Khó recovery và khó phát hiện lease bị bỏ quên sau crash.  
**Severity:** High  
**Recommended fix:** Có `Processing`, `Sent`, `Failed/DeadLetter`, `AttemptCount`, `NextAttemptAt`, `LeaseUntil`, `LastErrorCode` theo nhu cầu.

### 7. Ordering chưa deterministic hoàn toàn

**Problem:** Chỉ `OrderBy(CreatedAt)`; nhiều row có thể cùng timestamp.  
**Why it happens:** Không có tie-breaker duy nhất.  
**Production impact:** Cursor/keyset nếu xây trên ordering này có thể skip hoặc lặp item.  
**Severity:** Medium  
**Recommended fix:** Order theo `(CreatedAt, Id)` hoặc một khóa đơn điệu phù hợp.

### 8. Retry không có backoff/classification

**Problem:** Mọi failure từ provider sẽ ném ra và để Hangfire retry cả job/batch theo cơ chế chung.  
**Why it happens:** Không phân biệt transient, permanent và ambiguous outcomes.  
**Production impact:** Retry storm, duplicate nhiều hơn, poison item chặn tiến độ.  
**Severity:** Medium  
**Recommended fix:** Retry theo từng delivery với backoff/jitter, giới hạn attempt và dead-letter/manual review cho lỗi permanent.

### 9. Query tracking không được kiểm soát theo lifecycle dài

**Problem:** Job lặp nhiều batch trên cùng `DbContext`, các entity đã load có thể tiếp tục nằm trong change tracker.  
**Why it happens:** Scoped context sống xuyên toàn run và không clear tracker.  
**Production impact:** Memory tăng dần ở run lớn và SaveChanges/change detection tốn hơn.  
**Severity:** Medium  
**Recommended fix:** Dùng scope/context theo batch hoặc clear tracker có chủ đích sau khi persist.

### 10. Observability không đủ để điều tra stuck/duplicate

**Problem:** Log chỉ có count và page number.  
**Why it happens:** Không có delivery/attempt/cursor/worker metadata.  
**Production impact:** Không xác định được item nào bị bỏ sót hoặc xử lý hai lần.  
**Severity:** Medium  
**Recommended fix:** Log structured theo `DeliveryId`, attempt, worker/lease, outcome, provider request id; metric pending age, retry rate và duplicate/idempotent-hit nếu có.

## Phiên bản code đề xuất

```csharp
public sealed class NotificationDeliveryWorker
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly NotificationClient _client;
    private readonly ILogger<NotificationDeliveryWorker> _logger;

    public NotificationDeliveryWorker(
        IDbContextFactory<AppDbContext> dbFactory,
        NotificationClient client,
        ILogger<NotificationDeliveryWorker> logger)
    {
        _dbFactory = dbFactory;
        _client = client;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        while (!cancellationToken.IsCancellationRequested)
        {
            var claimed = await ClaimBatchAsync(100, cancellationToken);
            if (claimed.Count == 0)
                break;

            foreach (var item in claimed)
            {
                try
                {
                    var result = await _client.SendAsync(
                        item.Destination,
                        item.Payload,
                        idempotencyKey: item.Id.ToString("N"),
                        cancellationToken);

                    await MarkSentAsync(
                        item.Id,
                        result.ProviderRequestId,
                        cancellationToken);
                }
                catch (OperationCanceledException)
                    when (cancellationToken.IsCancellationRequested)
                {
                    throw;
                }
                catch (Exception ex)
                {
                    await ScheduleRetryAsync(item.Id, ex, cancellationToken);

                    _logger.LogWarning(
                        ex,
                        "Notification delivery {DeliveryId} failed on attempt {Attempt}",
                        item.Id,
                        item.AttemptCount + 1);
                }
            }
        }
    }

    private async Task<List<ClaimedDelivery>> ClaimBatchAsync(
        int batchSize,
        CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

        var now = DateTime.UtcNow;
        var leaseUntil = now.AddMinutes(2);
        var workerId = Environment.MachineName + ":" + Guid.NewGuid().ToString("N");

        // Ý tưởng: claim phải atomic ở database.
        // Implementation cụ thể có thể dùng UPDATE ... OUTPUT/RETURNING,
        // locking hints phù hợp DB, hoặc transaction với row locking.
        var candidates = await db.NotificationDeliveries
            .Where(x => x.Status == DeliveryStatus.Pending &&
                        x.NextAttemptAt <= now)
            .OrderBy(x => x.CreatedAt)
            .ThenBy(x => x.Id)
            .Take(batchSize)
            .ToListAsync(cancellationToken);

        foreach (var item in candidates)
        {
            item.Status = DeliveryStatus.Processing;
            item.LeaseOwner = workerId;
            item.LeaseUntil = leaseUntil;
            item.AttemptCount++;
        }

        await db.SaveChangesAsync(cancellationToken);

        return candidates.Select(x => new ClaimedDelivery(
            x.Id,
            x.Destination,
            x.Payload,
            x.AttemptCount)).ToList();
    }

    private async Task MarkSentAsync(
        Guid id,
        string? providerRequestId,
        CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

        var delivery = await db.NotificationDeliveries
            .SingleAsync(x => x.Id == id, cancellationToken);

        delivery.Status = DeliveryStatus.Sent;
        delivery.SentAt = DateTime.UtcNow;
        delivery.ProviderRequestId = providerRequestId;
        delivery.LeaseOwner = null;
        delivery.LeaseUntil = null;

        await db.SaveChangesAsync(cancellationToken);
    }

    private async Task ScheduleRetryAsync(
        Guid id,
        Exception error,
        CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

        var delivery = await db.NotificationDeliveries
            .SingleAsync(x => x.Id == id, cancellationToken);

        delivery.Status = DeliveryStatus.Pending;
        delivery.NextAttemptAt = DateTime.UtcNow.AddMinutes(1);
        delivery.LastErrorCode = error.GetType().Name;
        delivery.LeaseOwner = null;
        delivery.LeaseUntil = null;

        await db.SaveChangesAsync(cancellationToken);
    }
}
```

> Phần `ClaimBatchAsync` trên minh họa state machine; trong production, claim nhiều worker phải được bảo đảm atomic bởi database. SQL cụ thể khác giữa SQL Server và PostgreSQL, nên cần dùng primitive locking/update phù hợp hệ quản trị đang chạy.

## Trade-offs

- Claim/lease làm state machine phức tạp hơn, nhưng cho phép scale nhiều worker an toàn hơn.
- Persist per-item tăng số DB round-trip; có thể batch status update theo chunk nếu throughput yêu cầu, miễn retry semantics vẫn rõ ràng.
- Outbox/inbox có thể hữu ích nếu nguồn tạo delivery và việc publish sang queue cần atomic, nhưng không tự giải quyết external provider exactly-once.
- Nếu provider không hỗ trợ idempotency, cần business deduplication hoặc chấp nhận duplicate có kiểm soát; không nên tuyên bố exactly-once chỉ dựa vào transaction local.

## Cách kiểm thử

1. **Concurrency test:** Chạy 5–10 worker đồng thời, verify mỗi delivery chỉ được claim bởi một worker tại một thời điểm.
2. **Failure-path test:** Provider trả success rồi process bị kill trước DB update; run sau phải gửi cùng idempotency key và không tạo business side effect trùng.
3. **Mutation test:** Insert thêm `Pending` trong lúc job chạy; không item cũ nào bị skip vì offset dịch chuyển.
4. **Lease recovery test:** Worker crash sau claim; sau `LeaseUntil`, item phải quay lại trạng thái có thể retry.
5. **Load test:** Hàng trăm nghìn pending item; theo dõi throughput, DB CPU, tracker memory, pending-age p95/p99.

## Quan sát trong production

- Metric: `pending_count`, oldest pending age, processing count, retry count, dead-letter count, send latency, provider errors.
- Log structured: `DeliveryId`, attempt, lease owner, provider request id, result, error class.
- Trace: span claim DB → provider call → state update, correlation bằng `DeliveryId`.
- Alert khi oldest pending age vượt SLO hoặc retry/dead-letter tăng bất thường.
- Database observation: lock waits, query plan của claim query, index trên status/next-attempt/order keys.

# Code Review Challenge 2 — Download link ký số kiểm tra sai boundary khiến link hết hạn vẫn dùng được và có thể truy cập file ngoài tenant

**Chủ đề:** Authentication & authorization, input validation, sensitive-data exposure, cryptographic verification, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API tạo link download tạm thời cho tài liệu nội bộ. Link chứa `documentId`, `tenantId`, `expires` và `signature`. Client có thể gửi link cho trình duyệt hoặc mobile app để download mà không cần gửi access token lần nữa.

Production/security review phát hiện:

- link đã hết hạn đôi lúc vẫn download được,
- một số tenant có thể thay `documentId` trên URL và nhận file khác nếu signature vẫn vượt qua check,
- signature được so sánh bằng string thông thường,
- lỗi trả về chứa đường dẫn storage nội bộ,
- log ghi nguyên URL gồm signature,
- team không chắc timestamp đang là UTC seconds, milliseconds hay local ticks.

Business yêu cầu signed link chỉ hợp lệ cho đúng resource, đúng tenant, trong thời gian ngắn và không để signature trở thành credential bị lộ qua logs.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IConfiguration _configuration;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        AppDbContext db,
        IConfiguration configuration,
        ILogger<DocumentsController> logger)
    {
        _db = db;
        _configuration = configuration;
        _logger = logger;
    }

    [AllowAnonymous]
    [HttpGet("{documentId:guid}/download")]
    public async Task<IActionResult> Download(
        Guid documentId,
        Guid tenantId,
        long expires,
        string signature,
        CancellationToken cancellationToken)
    {
        var secret = _configuration["DownloadSigningKey"]!;
        var payload = $"{tenantId}:{expires}";

        using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secret));
        var expected = Convert.ToHexString(
            hmac.ComputeHash(Encoding.UTF8.GetBytes(payload)));

        if (expected != signature.ToUpperInvariant())
            return Unauthorized();

        if (DateTime.Now.Ticks > expires)
            return Unauthorized();

        var document = await _db.Documents
            .SingleOrDefaultAsync(
                x => x.Id == documentId,
                cancellationToken);

        if (document is null)
            return NotFound();

        _logger.LogInformation(
            "Signed download {Url} resolved to {StoragePath}",
            Request.GetDisplayUrl(),
            document.StoragePath);

        var bytes = await System.IO.File.ReadAllBytesAsync(
            document.StoragePath,
            cancellationToken);

        return File(bytes, document.ContentType, document.FileName);
    }
}
```

## Kết quả code review tham khảo

### 1. Signature không bind với `documentId`

**Problem:** HMAC chỉ ký `tenantId:expires`.  
**Why it happens:** Resource identifier không nằm trong canonical payload.  
**Production impact:** Nếu cùng tenant có một signed link hợp lệ, attacker có thể đổi `documentId` sang tài liệu khác và chữ ký vẫn hợp lệ.  
**Severity:** Critical  
**Recommended fix:** Bind `documentId`, tenant, expiry và các field security-relevant khác vào payload ký.

### 2. Query document không enforce tenant ownership

**Problem:** Document được query chỉ bằng `Id`.  
**Why it happens:** `tenantId` từ signed link không được dùng để ràng buộc resource.  
**Production impact:** Cross-tenant data exposure nếu attacker có valid signature không scoped đúng resource.  
**Severity:** Critical  
**Recommended fix:** Query bằng `Id + TenantId`; tenant trong token/link phải là phần của payload đã ký.

### 3. Expiry dùng đơn vị và timezone không rõ ràng

**Problem:** Code so `DateTime.Now.Ticks` với `expires`, nhưng không có contract cho `expires`.  
**Why it happens:** Timestamp serialization không được chuẩn hóa.  
**Production impact:** Link có thể hết hạn quá sớm, quá muộn hoặc gần như không hết hạn nếu producer dùng Unix seconds/milliseconds.  
**Severity:** High  
**Recommended fix:** Chuẩn hóa thành Unix time seconds UTC hoặc một format rõ ràng; dùng `DateTimeOffset.UtcNow` và validate range.

### 4. So sánh signature bằng string comparison

**Problem:** `expected != signature.ToUpperInvariant()` dùng comparison thông thường.  
**Why it happens:** HMAC được convert sang text rồi so sánh như dữ liệu thường.  
**Production impact:** Không phải primitive verification lý tưởng cho secret-derived values và còn tạo thêm canonicalization ambiguity.  
**Severity:** High  
**Recommended fix:** Decode signature về bytes và dùng `CryptographicOperations.FixedTimeEquals` sau khi validate đúng độ dài/encoding.

### 5. Signing key được dùng trực tiếp từ config string

**Problem:** Không thấy key versioning/rotation, key length policy hoặc secret provider.  
**Why it happens:** Configuration value được coi như secret management hoàn chỉnh.  
**Production impact:** Rotation khó, rollback khó, key có thể bị lưu trong config không phù hợp.  
**Severity:** High  
**Recommended fix:** Dùng secret store phù hợp, có key id/version và rotation window nếu business cần link vẫn sống qua rotation.

### 6. Log nguyên URL chứa signature

**Problem:** `Request.GetDisplayUrl()` có thể chứa signature query parameter.  
**Why it happens:** Signed URL bị coi như request metadata bình thường.  
**Production impact:** Người có quyền đọc log có thể reuse credential nếu link còn hạn.  
**Severity:** High  
**Recommended fix:** Không log signature; log resource id, tenant id, expiry bucket, verification outcome và correlation id.

### 7. Log `StoragePath` nội bộ

**Problem:** Log chứa đường dẫn filesystem/storage.  
**Why it happens:** Debug data được đưa vào production log.  
**Production impact:** Lộ topology/path naming và có thể chứa thông tin nhạy cảm.  
**Severity:** Medium  
**Recommended fix:** Log storage object id/key đã redacted hoặc document id, không log internal path không cần thiết.

### 8. `ReadAllBytesAsync` load toàn bộ file vào memory

**Problem:** File được đọc toàn bộ trước khi trả response.  
**Why it happens:** Endpoint dùng byte array cho mọi kích thước file.  
**Production impact:** File lớn hoặc nhiều download đồng thời gây memory pressure/LOH/GC và giảm stability.  
**Severity:** Medium  
**Recommended fix:** Stream file/remote object; giới hạn size hoặc dùng storage-native download redirect nếu phù hợp.

### 9. Không validate expiry window bất thường

**Problem:** Một link có thể được ký với expiry rất xa tương lai nếu issuer bug hoặc bị cấu hình sai.  
**Why it happens:** Verifier chỉ check “chưa hết hạn”.  
**Production impact:** Bearer link tồn tại lâu hơn security policy dự kiến.  
**Severity:** Medium  
**Recommended fix:** Có maximum TTL/policy, ví dụ reject expiry vượt quá `issuedAt + maxLifetime` nếu protocol có `issuedAt`.

### 10. Error semantics và abuse controls chưa rõ

**Problem:** Endpoint anonymous có thể bị probe với nhiều id/signature.  
**Why it happens:** Không có mention rate limiting, uniform error hoặc telemetry abuse.  
**Production impact:** Enumeration/probing và log noise.  
**Severity:** Low  
**Recommended fix:** Cân nhắc uniform invalid-link response, rate limit phù hợp và metric verification failures.

## Phiên bản code đề xuất

```csharp
public sealed record SignedDownloadToken(
    Guid DocumentId,
    Guid TenantId,
    long ExpiresUnixSeconds,
    string KeyId,
    string Signature);

[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IDownloadSigningKeyProvider _keys;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        AppDbContext db,
        IDownloadSigningKeyProvider keys,
        ILogger<DocumentsController> logger)
    {
        _db = db;
        _keys = keys;
        _logger = logger;
    }

    [AllowAnonymous]
    [HttpGet("{documentId:guid}/download")]
    public async Task<IActionResult> Download(
        Guid documentId,
        Guid tenantId,
        long expires,
        string kid,
        string sig,
        CancellationToken cancellationToken)
    {
        if (expires <= DateTimeOffset.UtcNow.ToUnixTimeSeconds())
            return Unauthorized();

        if (expires > DateTimeOffset.UtcNow.AddMinutes(15).ToUnixTimeSeconds())
            return Unauthorized();

        var key = await _keys.GetKeyAsync(kid, cancellationToken);
        if (key is null)
            return Unauthorized();

        var canonical = $"v1\n{documentId:N}\n{tenantId:N}\n{expires}\n{kid}";
        var data = Encoding.UTF8.GetBytes(canonical);

        byte[] provided;
        try
        {
            provided = Convert.FromBase64String(sig);
        }
        catch (FormatException)
        {
            return Unauthorized();
        }

        using var hmac = new HMACSHA256(key);
        var expected = hmac.ComputeHash(data);

        if (provided.Length != expected.Length ||
            !CryptographicOperations.FixedTimeEquals(expected, provided))
        {
            return Unauthorized();
        }

        var document = await _db.Documents
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.Id == documentId && x.TenantId == tenantId,
                cancellationToken);

        if (document is null)
            return NotFound();

        _logger.LogInformation(
            "Signed document download allowed for DocumentId {DocumentId}, TenantId {TenantId}, KeyId {KeyId}",
            documentId,
            tenantId,
            kid);

        var stream = new FileStream(
            document.StoragePath,
            FileMode.Open,
            FileAccess.Read,
            FileShare.Read,
            bufferSize: 64 * 1024,
            useAsync: true);

        return File(
            stream,
            document.ContentType,
            document.FileName,
            enableRangeProcessing: true);
    }
}
```

> Đây là reference design. Nếu file nằm trên Azure Blob Storage hoặc object storage khác, thường nên dùng storage-native streaming hoặc signed URL của storage thay vì đọc file qua app server, tùy yêu cầu authorization/audit và kiến trúc hiện tại.

## Trade-offs

- Tự triển khai signed URL cho phép kiểm soát business scope nhưng tăng trách nhiệm về canonicalization, key rotation và crypto correctness.
- Dùng signed URL/SAS của object storage giảm data path qua API nhưng cần kiểm soát TTL, permission scope và audit ở storage layer.
- TTL ngắn giảm blast radius khi link lộ nhưng làm UX kém hơn nếu download lâu hoặc mobile offline.
- Key rotation với `kid` phức tạp hơn một key duy nhất nhưng hỗ trợ rollover có kiểm soát.

## Cách kiểm thử

1. **Tampering test:** Đổi `documentId`, `tenantId`, `expires` hoặc `kid` sau khi ký; request phải fail.
2. **Expiry boundary test:** Kiểm tra trước hạn, đúng boundary và sau hạn bằng clock abstraction thay vì test phụ thuộc thời gian thực.
3. **Cross-tenant test:** Valid token tenant A không được tải document tenant B dù biết id.
4. **Key rotation test:** Key cũ còn hợp lệ trong grace period theo policy, sau đó bị reject.
5. **Load/file-size test:** Nhiều file lớn đồng thời; memory không tăng tuyến tính theo tổng kích thước file.

## Quan sát trong production

- Metric: signed-download success, invalid-signature, expired-token, not-found, bytes streamed, active downloads.
- Log: document id, tenant id, key id, verification outcome, correlation id; không log signature hoặc raw signed URL.
- Trace: verify token → DB lookup → storage read.
- Alert nếu invalid-signature rate hoặc cross-tenant lookup failures tăng bất thường.
- Audit access theo document/actor context nếu link issuance có gắn người dùng hoặc business event.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ thiết kế endpoint tạo signed link thế nào để chỉ user có quyền mới issue được link?
2. Khi nào nên dùng application-signed URL và khi nào nên dùng Azure Blob SAS/presigned URL từ storage?
3. Nếu link cần revoke ngay trước khi hết hạn, bạn sẽ thêm cơ chế gì và trade-off ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Offset pagination không an toàn khi chính worker làm thay đổi tập dữ liệu đang phân trang.
- Background processing nhiều worker cần claim/lease hoặc primitive concurrency tương đương ở database.
- Retry và external side effect phải được thiết kế cùng idempotency; local transaction không tạo ra exactly-once với external provider.
- Signed URL là bearer credential: chữ ký phải bind đúng resource, tenant, expiry và được verify bằng canonical contract rõ ràng.
- Security credential không nên xuất hiện trong logs; streaming phù hợp hơn `ReadAllBytesAsync` cho file lớn.

## Mẫu tư duy cần nhớ

- Đừng paginate bằng offset trên một tập dữ liệu đang mutate bởi chính workflow.
- Design retries together with idempotency.
- Claim work atomically before scaling worker count.
- Bind every security-relevant field into signed credentials.
- Treat observability as part of the design, nhưng không biến logs thành nơi lưu secrets.
