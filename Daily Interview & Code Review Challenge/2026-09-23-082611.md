# Code Review Challenge 1 — Dual-write SQL + Elasticsearch làm search mất đồng bộ sau lỗi mạng

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, Elasticsearch, eventual consistency, distributed failure, idempotency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một automotive marketplace lưu dữ liệu xe trong SQL Server bằng EF Core và dùng Elasticsearch làm read model cho search. Khi dealer cập nhật giá hoặc trạng thái xe, API phải ghi SQL và sau đó cập nhật search index.

Production chạy nhiều Azure App Service instances. Support gần đây ghi nhận một số xe đã chuyển sang `Sold` trong SQL nhưng vẫn xuất hiện là `Available` trên search trong nhiều giờ. Một số request trả `500` dù SQL đã commit thành công. Khi Elasticsearch chậm, latency p99 của update API tăng mạnh. Team đề xuất retry `IndexAsync` nhiều lần ngay trong HTTP request để “đảm bảo đồng bộ”.

SQL là source of truth. Search có thể eventual consistent trong một khoảng ngắn, nhưng không được mất update vĩnh viễn. Chưa có durable event/outbox hoặc reconciliation job.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/vehicles")]
public sealed class VehiclesController : ControllerBase
{
    private readonly MarketplaceDbContext _db;
    private readonly IElasticClient _elastic;
    private readonly ILogger<VehiclesController> _logger;

    public VehiclesController(
        MarketplaceDbContext db,
        IElasticClient elastic,
        ILogger<VehiclesController> logger)
    {
        _db = db;
        _elastic = elastic;
        _logger = logger;
    }

    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id,
        UpdateVehicleRequest request,
        CancellationToken cancellationToken)
    {
        var vehicle = await _db.Vehicles
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        if (vehicle is null)
            return NotFound();

        vehicle.Price = request.Price;
        vehicle.Status = request.Status;
        vehicle.UpdatedAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        var document = new VehicleSearchDocument
        {
            Id = vehicle.Id,
            Make = vehicle.Make,
            Model = vehicle.Model,
            Price = vehicle.Price,
            Status = vehicle.Status,
            UpdatedAtUtc = vehicle.UpdatedAtUtc
        };

        var result = await _elastic.IndexDocumentAsync(document, cancellationToken);

        if (!result.IsValid)
        {
            _logger.LogError(
                "Failed to index vehicle {VehicleId}: {Debug}",
                id,
                result.DebugInformation);

            return StatusCode(500, "Search indexing failed");
        }

        return Ok(vehicle);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và consistency.
2. Xác định các rủi ro performance, reliability và security/observability liên quan.
3. Giải thích impact khi SQL thành công nhưng Elasticsearch thất bại hoặc timeout.
4. Ưu tiên các vấn đề theo severity và blast radius.
5. Đề xuất implementation/design để không mất search update vĩnh viễn.
6. Mô tả testing cho failure, retry, concurrency và recovery.
7. Mô tả telemetry cần có để phát hiện search drift trong production.

## Câu hỏi gợi mở

1. HTTP `500` ở đây có đồng nghĩa business update đã rollback không?
2. Điều gì xảy ra nếu client retry request sau khi nhận `500`?
3. Có transaction nào có thể atomic cả SQL Server và Elasticsearch không, và có nên cố tạo distributed transaction cho flow này không?
4. Nếu hai update của cùng một vehicle được xử lý gần nhau, search document nào có thể thắng?
5. Làm sao chứng minh rằng mọi committed SQL change cuối cùng đều được phản ánh vào search?

## Kết quả code review tham khảo

### Critical — SQL commit và Elasticsearch index không có atomic boundary

**Vấn đề:** `SaveChangesAsync` commit SQL trước, sau đó mới gọi Elasticsearch. Nếu call thứ hai thất bại, không có durable record nào bảo đảm index sẽ được sửa sau đó.  
**Tại sao xảy ra:** Hai storage systems độc lập; code đang thực hiện dual-write tuần tự nhưng xử lý chúng như một transaction logic duy nhất.  
**Ảnh hưởng production:** SQL đã đúng nhưng search có thể stale vô thời hạn; vehicle `Sold` vẫn có thể được tìm thấy như `Available`.  
**Cách sửa:** Ghi business change và một Outbox record trong cùng SQL transaction/`SaveChanges` unit of work. Background processor publish/index từ Outbox theo at-least-once semantics; chỉ mark processed sau khi Elasticsearch operation thành công.

### High — Trả `500` sau khi business update đã commit tạo ambiguous outcome

**Vấn đề:** Client nhận failure nhưng SQL state đã thay đổi.  
**Tại sao xảy ra:** API response đang phản ánh search side effect thay vì authoritative write outcome.  
**Ảnh hưởng production:** Client có thể retry, user không biết update đã thành công, audit/business side effects có thể lặp.  
**Cách sửa:** Xác định contract rõ: khi SQL + Outbox commit thành công, authoritative update đã được accepted/succeeded; indexing diễn ra asynchronous. Nếu product cần expose trạng thái search propagation, trả/version một trạng thái riêng thay vì giả vờ transaction đã rollback.

### High — Không có protection cho out-of-order updates

**Vấn đề:** Hai updates gần nhau có thể được index không đúng thứ tự nếu sau này thêm retry/parallel worker.  
**Tại sao xảy ra:** Document không có concurrency/version rule dùng để reject stale update.  
**Ảnh hưởng production:** Một retry cũ có thể ghi đè trạng thái mới hơn.  
**Cách sửa:** Mang aggregate/search version hoặc monotonic sequence từ source of truth vào Outbox/document và thiết kế consumer/index operation để stale event không thắng newer state; hoặc consumer đọc current authoritative projection trước khi index khi phù hợp.

### High — Search dependency làm tăng latency và availability coupling của write API

**Vấn đề:** HTTP request chờ Elasticsearch sau SQL commit.  
**Tại sao xảy ra:** Search indexing nằm trên synchronous critical path.  
**Ảnh hưởng production:** Elasticsearch chậm làm update API p95/p99 tăng và có thể gây request/thread/resource pressure dù SQL khỏe.  
**Cách sửa:** Đưa indexing ra asynchronous durable processing nếu freshness requirement cho phép eventual consistency.

### Medium — Retry trong request có thể khuếch đại sự cố

**Vấn đề:** Đề xuất retry nhiều lần synchronous không giải quyết lost intent.  
**Tại sao xảy ra:** Retry kéo dài request và tăng load lên dependency đang degraded.  
**Ảnh hưởng production:** Retry storm, timeout chain và giảm throughput.  
**Cách sửa:** Retry bounded với backoff ở worker khi lỗi transient; durable Outbox giữ work để retry sau. Phân loại permanent failure và đưa vào failed/dead-letter state để operator xử lý.

### Medium — Logging `DebugInformation` có thể quá lớn hoặc chứa dữ liệu không phù hợp

**Vấn đề:** Raw client debug payload được log trực tiếp.  
**Tại sao xảy ra:** Debug information thường dành cho diagnostics và có thể chứa request/response details.  
**Ảnh hưởng production:** Log volume tăng và có nguy cơ lộ dữ liệu nhạy cảm tùy client/configuration.  
**Cách sửa:** Log structured fields cần thiết như vehicle ID, operation, status/error type, attempt, latency, correlation ID; kiểm soát diagnostic payload theo policy.

### Medium — Không có reconciliation để phát hiện drift đã tồn tại

**Vấn đề:** Ngay cả sau khi thêm Outbox, các documents stale từ trước hoặc lỗi permanent vẫn có thể tồn tại.  
**Tại sao xảy ra:** Hệ thống không có invariant check giữa source of truth và search projection.  
**Ảnh hưởng production:** Silent data-quality issue kéo dài.  
**Cách sửa:** Có reconciliation process theo batch/version/checkpoint và metric drift/oldest-unprocessed age.

### Medium — Validation/business concurrency chưa rõ

**Vấn đề:** Request update trực tiếp mutable fields mà không thể hiện validation hoặc optimistic concurrency semantics.  
**Tại sao xảy ra:** Scenario chưa cho biết row version/business conflict requirement.  
**Ảnh hưởng production:** Concurrent dealer updates có thể last-write-wins ngoài ý muốn.  
**Cách sửa:** Xác minh requirement; nếu lost update không chấp nhận được, dùng optimistic concurrency token/version và trả conflict phù hợp.

### Low — Trả trực tiếp entity làm API contract phụ thuộc persistence model

**Vấn đề:** `Ok(vehicle)` expose persistence entity.  
**Tại sao xảy ra:** API model và EF model bị coupling.  
**Ảnh hưởng production:** Khó version contract và có thể expose field ngoài ý muốn khi entity thay đổi.  
**Cách sửa:** Trả response DTO explicit.

## Phiên bản đề xuất

```csharp
public sealed class Vehicle
{
    public Guid Id { get; set; }
    public decimal Price { get; set; }
    public string Status { get; set; } = default!;
    public long SearchVersion { get; set; }
    public DateTime UpdatedAtUtc { get; set; }
}

public sealed class SearchOutbox
{
    public Guid Id { get; set; }
    public Guid VehicleId { get; set; }
    public long Version { get; set; }
    public DateTime CreatedAtUtc { get; set; }
    public DateTime? ProcessedAtUtc { get; set; }
}

[HttpPut("{id:guid}")]
public async Task<ActionResult<VehicleResponse>> Update(
    Guid id,
    UpdateVehicleRequest request,
    CancellationToken cancellationToken)
{
    var vehicle = await _db.Vehicles
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (vehicle is null)
        return NotFound();

    // Business validation omitted here only because requirements are scenario-specific.
    vehicle.Price = request.Price;
    vehicle.Status = request.Status;
    vehicle.UpdatedAtUtc = DateTime.UtcNow;
    vehicle.SearchVersion++;

    _db.SearchOutbox.Add(new SearchOutbox
    {
        Id = Guid.NewGuid(),
        VehicleId = vehicle.Id,
        Version = vehicle.SearchVersion,
        CreatedAtUtc = DateTime.UtcNow
    });

    await _db.SaveChangesAsync(cancellationToken);

    return Ok(new VehicleResponse(
        vehicle.Id,
        vehicle.Price,
        vehicle.Status,
        vehicle.SearchVersion,
        vehicle.UpdatedAtUtc));
}

public async Task ProcessAsync(SearchOutbox item, CancellationToken token)
{
    var vehicle = await _db.Vehicles
        .AsNoTracking()
        .SingleAsync(x => x.Id == item.VehicleId, token);

    if (vehicle.SearchVersion < item.Version)
        throw new InvalidOperationException("Source version is behind outbox version.");

    await _searchIndexer.UpsertAsync(
        VehicleSearchDocument.From(vehicle),
        vehicle.SearchVersion,
        token);

    item.ProcessedAtUtc = DateTime.UtcNow;
    await _db.SaveChangesAsync(token);
}
```

`UpsertAsync` phải có semantics được xác định rõ để retry cùng version là idempotent và stale version không ghi đè version mới. Cách implement cụ thể phụ thuộc Elasticsearch client/version và indexing strategy đang dùng; không nên giả định API/version behavior khi chưa xác minh client hiện tại.

## Giải thích thiết kế sau khi sửa

SQL vẫn là source of truth. Business state và Outbox intent được commit cùng một database transaction do cùng `DbContext`/`SaveChanges` quản lý. Sau commit, HTTP request không còn phụ thuộc availability của Elasticsearch. Worker có thể retry vì intent tồn tại durable.

At-least-once delivery đồng nghĩa consumer phải chịu được duplicate. Version giúp xử lý retry/out-of-order thay vì giả định queue/worker luôn xử lý đúng thứ tự. Reconciliation là safety net, không thay Outbox.

## Trade-offs

Outbox thêm table, worker, cleanup, retry policy và operational telemetry. Search không còn read-after-write immediate consistency. Nếu business thực sự yêu cầu search phải phản ánh write trước khi API success, cần làm rõ SLA và cân nhắc kiến trúc khác; không thể đạt atomic commit đơn giản giữa SQL và Elasticsearch chỉ bằng đặt hai calls trong một C# `try` block.

## Cách kiểm thử

1. **Integration/failure-path test:** SQL commit thành công, Elasticsearch unavailable; xác minh API outcome theo contract và Outbox vẫn pending.
2. **Retry/idempotency test:** xử lý cùng Outbox item nhiều lần; search cuối cùng chỉ phản ánh một logical version.
3. **Concurrency test:** hai updates cùng vehicle gần nhau và worker xử lý đảo thứ tự; version mới không bị stale update ghi đè.
4. **Recovery test:** Elasticsearch down một khoảng thời gian rồi hồi phục; backlog drain và không mất committed update.
5. **Reconciliation test:** cố tình tạo search drift rồi xác minh job phát hiện/sửa đúng scope.

## Quan sát trong production

Theo dõi Outbox backlog count, oldest pending age, retry count, permanent failures, indexing latency/error rate và search-version lag. Correlate HTTP update với Outbox ID/vehicle ID nhưng không log payload nhạy cảm. Application Insights có thể theo dõi request/dependency latency; Kibana/Elasticsearch operational dashboards cần tách application search data khỏi diagnostic assumptions. Alert khi oldest pending vượt freshness SLO hoặc failed items tăng. Có periodic drift metric/reconciliation report.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search freshness phải dưới 2 giây ở p99, bạn thiết kế capacity/backpressure cho Outbox worker thế nào?
2. Khi nào bạn chọn CDC/event stream thay cho application Outbox?
3. Nếu Elasticsearch đã nhận index request nhưng client timeout trước khi nhận response, idempotency/versioning giúp gì?

# Code Review Challenge 2 — Kubernetes rollout “xanh” nhưng Pod nhận traffic trước khi ASP.NET Core sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core health checks, rolling deployment, configuration, Secrets, resource management, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core REST API được deploy lên Kubernetes. Mỗi Pod cần khoảng 15–30 giây để warm up configuration, initialize local caches và kiểm tra một số required startup dependencies. Sau release gần đây, deployment báo thành công nhưng người dùng nhận intermittent `502/503` trong vài chục giây. Một số Pod cũng restart khi SQL Server chậm tạm thời.

Team dùng cùng endpoint `/health` cho cả liveness và readiness. Endpoint hiện kiểm tra SQL, Redis và một third-party API. Deployment manifest cũng chứa connection string trực tiếp trong environment variable. CPU/memory behavior chưa được baseline dưới load.

## Đoạn code cần review

## Kết quả code review tham khảo

### Critical — Production credential được hard-code trong Deployment manifest

**Vấn đề:** SQL username/password nằm trực tiếp trong YAML.  
**Tại sao xảy ra:** Configuration và secret management bị trộn vào deployment definition.  
**Ảnh hưởng production:** Credential có thể xuất hiện trong Git history, CI logs, manifests, review artifacts và người có quyền đọc Deployment.  
**Cách sửa:** Dùng Kubernetes Secret hoặc external secret/identity mechanism phù hợp với platform; ưu tiên workload identity/Managed Identity khi hạ tầng và dependency hỗ trợ. Rotate credential đã bị expose và áp dụng least privilege.

### High — Dùng dependency-heavy `/health` làm liveness có thể tạo restart storm

**Vấn đề:** Liveness phụ thuộc SQL, Redis và third-party API.  
**Tại sao xảy ra:** External dependency degradation bị hiểu nhầm thành process deadlock/unhealthy cần restart.  
**Ảnh hưởng production:** Khi SQL chậm/down, nhiều Pods cùng fail liveness và bị restart, làm availability tệ hơn và tăng load lúc recovery.  
**Cách sửa:** Liveness nên phản ánh process có còn hoạt động/khả năng tự phục hồi hay không; không đưa mọi external dependency vào liveness. Readiness có thể phản ánh dependencies cần thiết để phục vụ request, tùy degraded-mode requirement.

### High — Không có startup probe dù startup/warm-up có thể mất 15–30 giây

**Vấn đề:** Liveness bắt đầu sau 5 giây và có thể kill process trong lúc startup hợp lệ.  
**Tại sao xảy ra:** Manifest giả định startup nhanh hơn behavior thực tế.  
**Ảnh hưởng production:** Restart loop hoặc rollout kéo dài/thất bại.  
**Cách sửa:** Dùng `startupProbe` với budget dựa trên measured startup time; trong khi startup probe chưa success, liveness/readiness semantics được bảo vệ theo Kubernetes probe behavior.

### High — Image tag `latest` phá artifact determinism và rollback confidence

**Vấn đề:** Deployment không pin image version/digest.  
**Tại sao xảy ra:** Mutable tag không định danh immutable artifact.  
**Ảnh hưởng production:** Pods của cùng release có thể chạy artifact khác nhau tùy pull/cache timing; audit và rollback khó tin cậy.  
**Cách sửa:** Deploy immutable version tag hoặc digest được tạo từ CI artifact và promote cùng artifact qua environments.

### High — RollingUpdate không định nghĩa availability policy theo requirement

**Vấn đề:** Không có explicit `maxUnavailable`/`maxSurge` và chưa chứng minh default behavior phù hợp capacity/SLO.  
**Tại sao xảy ra:** Rollout strategy chưa gắn với minimum serving capacity.  
**Ảnh hưởng production:** Trong combination với readiness/startup issues, serving capacity có thể giảm trong rollout.  
**Cách sửa:** Chọn `maxUnavailable`/`maxSurge` dựa trên replica count, headroom và SLO; ví dụ `maxUnavailable: 0` chỉ phù hợp nếu cluster có capacity cho surge và application semantics cho phép.

### Medium — Readiness quá nhạy và dependency model chưa rõ

**Vấn đề:** `failureThreshold: 1` với endpoint kiểm tra nhiều dependencies có thể loại Pod khỏi Service vì một transient failure nhỏ.  
**Tại sao xảy ra:** Probe policy không dựa trên failure tolerance hoặc degraded-mode design.  
**Ảnh hưởng production:** Endpoint churn, reduced capacity và cascading failure.  
**Cách sửa:** Xác định dependency nào bắt buộc để serve traffic, dùng timeout/threshold phù hợp với measured behavior, và tránh readiness call tạo tải đáng kể lên dependencies.

### Medium — Chỉ có resource limits, không có requests

**Vấn đề:** Scheduler không có explicit expected CPU/memory request cho workload.  
**Tại sao xảy ra:** Capacity model chưa được baseline.  
**Ảnh hưởng production:** Scheduling/QoS behavior khó dự đoán; CPU limit quá thấp có thể throttle và memory limit quá thấp có thể dẫn tới OOM kill.  
**Cách sửa:** Đo CPU, working set, GC và load; đặt requests/limits theo evidence, rồi quan sát throttling/OOM/restart metrics.

### Medium — Probe timing dùng magic numbers chưa được đo

**Vấn đề:** `initialDelaySeconds`, period và thresholds không gắn với startup/latency distribution.  
**Tại sao xảy ra:** Configuration theo guess.  
**Ảnh hưởng production:** False unhealthy hoặc phát hiện failure quá chậm.  
**Cách sửa:** Baseline startup p95/p99 và health endpoint latency; đặt budget có margin hợp lý, sau đó load/failure test.

### Medium — Không thể hiện graceful termination behavior

**Vấn đề:** Manifest/application design chưa cho thấy Pod ngừng nhận traffic và hoàn tất in-flight requests trước termination như thế nào.  
**Tại sao xảy ra:** Rollout chỉ tập trung startup.  
**Ảnh hưởng production:** Request có thể bị cắt giữa chừng trong rollout/scale-down.  
**Cách sửa:** Xác minh ASP.NET Core shutdown behavior, termination grace period, readiness transition và load balancer/service endpoint propagation; test thực tế thay vì chỉ thêm sleep tùy ý.

## Phiên bản đề xuất

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: employee-api
  template:
    metadata:
      labels:
        app: employee-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example.com/employee-api:2026.09.23.1
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__Sql
              valueFrom:
                secretKeyRef:
                  name: employee-api-secrets
                  key: sql-connection
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1000m"
              memory: "512Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: employee-api
spec:
  selector:
    app: employee-api
  ports:

      targetPort: 8080
```

Các resource values và probe thresholds ở trên chỉ là **scenario example**, không phải production recommendation mặc định. Phải thay bằng values dựa trên measurement. `employee-api-secrets` cũng không nên chứa một credential đã từng commit/expose mà chưa rotate.

## Giải thích thiết kế sau khi sửa

Health endpoints có trách nhiệm khác nhau. `/health/live` kiểm tra process có đang hoạt động theo nghĩa restart có thể giúp hay không. `/health/ready` quyết định Pod có nên nhận traffic; dependency checks chỉ nên xuất hiện nếu dependency đó thực sự cần để phục vụ traffic và không có degraded mode hợp lệ. `/health/startup` dành thời gian cho initialization trước khi liveness can thiệp.

Artifact được pin bằng immutable version. Rollout policy giữ serving capacity nhưng cần cluster headroom. Secret được tách khỏi manifest; nếu platform cho phép identity-based access thì còn có thể giảm credential lifecycle risk.

## Trade-offs

`maxUnavailable: 0` cần extra capacity trong rollout. Readiness check dependency quá chặt có thể loại toàn bộ Pods khi shared dependency down; quá lỏng có thể gửi traffic vào Pod không thể phục vụ. Startup budget quá dài làm phát hiện startup failure chậm. Resource requests cao làm giảm packing density; quá thấp làm scheduling không phản ánh nhu cầu. External secret/identity solution thêm platform complexity nhưng giảm secret exposure.

## Cách kiểm thử

1. **Deployment validation:** deploy version mới khi old version đang nhận load; xác minh không có spike `5xx` và minimum ready replicas được giữ.
2. **Failure-path test:** làm SQL/Redis/third-party dependency chậm hoặc unavailable; xác minh readiness/liveness phản ứng đúng theo degraded-mode requirement và không tạo restart storm.
3. **Startup test:** kéo dài warm-up lên gần upper bound; Pod không bị liveness kill trước khi startup hoàn tất.
4. **Load/resource test:** đo CPU throttling, memory/GC, OOM/restart và request p95/p99 để hiệu chỉnh requests/limits.
5. **Security/deployment test:** CI policy chặn plaintext production secrets và mutable image tags; rotate credential đã expose.

## Quan sát trong production

Theo dõi ready replica count, Pod restart reason/count, probe failures, rollout duration, CPU throttling, working set, OOMKilled events, request `5xx`, p95/p99 và dependency telemetry trong Application Insights. Correlate release version/image digest với request errors. Alert nếu ready replicas xuống dưới SLO threshold hoặc restart rate tăng. Kubernetes events giúp giải thích scheduling/probe/OOM behavior; application logs phải có structured startup/shutdown events nhưng không log secret values.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Redis down nhưng API vẫn có thể đọc trực tiếp SQL với latency cao hơn, readiness nên fail hay Pod vẫn nên nhận traffic?
2. `maxUnavailable: 0` có luôn là lựa chọn tốt nhất cho mọi service ba replicas không?
3. Nếu readiness endpoint tự gọi SQL mỗi 5 giây trên hàng trăm Pods, health-check design có thể tạo failure mode mới như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Dual-write giữa SQL và Elasticsearch không trở thành atomic chỉ vì hai calls nằm trong cùng request; durable intent và idempotent projection processing mới giải quyết lost update theo eventual-consistency model.
- Search/read model cần versioning/reconciliation nếu duplicate, retry và out-of-order processing có thể xảy ra.
- Kubernetes liveness, readiness và startup probes giải quyết ba câu hỏi khác nhau; external dependency failure không mặc định đồng nghĩa process phải restart.
- Deployment safety gồm immutable artifacts, secret handling, capacity-aware rollout, graceful termination, resource measurement và observability.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency và durable state.
- Khi hai systems không share transaction, phân tích failure ở mọi điểm giữa các writes.
- Tách “alive”, “ready” và “started” trước khi thiết kế health checks.
- Đặt resource/probe values bằng measurement, không bằng cảm giác.
- Rollout và rollback phải dùng artifact xác định được và telemetry chứng minh được trạng thái.
