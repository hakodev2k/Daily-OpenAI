# Code Review Challenge 1 — API phê duyệt ghi đè thay đổi do optimistic concurrency bị bỏ qua

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core optimistic concurrency, HTTP semantics, authorization, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một internal approval platform cho phép manager duyệt hoặc từ chối expense request. ASP.NET Core API chạy nhiều instances trên Azure App Service và dùng EF Core với SQL Server. Người dùng có thể mở cùng một request ở nhiều browser tab; đồng thời background integration cũng có thể cập nhật trạng thái request sau khi đồng bộ với finance system.

Production ghi nhận một số request đã được finance integration chuyển sang `Cancelled`, nhưng vài giây sau lại trở thành `Approved`. Audit log chỉ cho thấy request cuối cùng thành công, khiến team khó xác định ai đã ghi đè ai. Business rule yêu cầu không được silently overwrite một quyết định dựa trên dữ liệu cũ; client phải biết khi resource đã thay đổi và reload trước khi quyết định lại.

Entity hiện có `RowVersion` trong database nhưng API không dùng version do client gửi để kiểm tra concurrency.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/expenses")]
public sealed class ExpensesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ExpensesController> _logger;

    public ExpensesController(
        AppDbContext db,
        ILogger<ExpensesController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpPut("{id:long}/decision")]
    public async Task<IActionResult> Decide(
        long id,
        [FromBody] ExpenseDecisionRequest request)
    {
        var expense = await _db.Expenses
            .SingleOrDefaultAsync(x => x.Id == id);

        if (expense is null)
            return NotFound();

        if (expense.Status == "Approved")
            return Ok(expense);

        expense.Status = request.Approve ? "Approved" : "Rejected";
        expense.Comment = request.Comment;
        expense.DecidedBy = User.Identity?.Name;
        expense.DecidedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Expense {ExpenseId} changed to {Status} by {User}",
            expense.Id,
            expense.Status,
            expense.DecidedBy);

        return Ok(expense);
    }
}

public sealed record ExpenseDecisionRequest(
    bool Approve,
    string? Comment,
    string RowVersion);

public sealed class Expense
{
    public long Id { get; set; }
    public string Status { get; set; } = "Pending";
    public string? Comment { get; set; }
    public string? DecidedBy { get; set; }
    public DateTime? DecidedUtc { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = Array.Empty<byte>();
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong concurrent update flow.
2. Xác định authorization, API contract và auditability concerns.
3. Giải thích vì sao có `[Timestamp]` chưa đủ để ngăn lost update trong flow hiện tại.
4. Ưu tiên findings theo severity và production impact.
5. Đề xuất corrected implementation/design sử dụng optimistic concurrency đúng boundary.
6. Giải thích cách test race giữa browser, integration worker và nhiều API instances.
7. Đề xuất telemetry để phát hiện conflict, forbidden transition và unexpected overwrite.

## Câu hỏi gợi mở

1. EF Core sẽ so sánh `RowVersion` nào trong `UPDATE`: version được đọc bởi request hiện tại hay version mà browser đã nhìn thấy trước đó?
2. Nếu browser đọc request lúc `Pending`, finance integration đổi thành `Cancelled`, rồi browser gọi endpoint này thì chuyện gì xảy ra?
3. `if (expense.Status == "Approved")` có bảo vệ đầy đủ state machine không?
4. Endpoint đang chứng minh caller có quyền approve expense này ở đâu?
5. Concurrency conflict nên được biểu diễn thế nào trong HTTP contract để client có thể xử lý có chủ đích?

## Gợi ý

### Gợi ý 1

Primary risk là **stale client decision bị áp dụng lên state mới** dù entity đã có concurrency token.

### Gợi ý 2

Hãy phân biệt version mà API vừa query từ database với version mà client đã dùng khi đưa ra quyết định. Optimistic concurrency chỉ bảo vệ đúng intent nếu original concurrency value đại diện cho state mà decision dựa trên.

## Kết quả code review tham khảo

### Critical — Client `RowVersion` bị bỏ qua nên stale decision vẫn có thể overwrite state mới

**Vấn đề:** Request chứa `RowVersion` nhưng endpoint không dùng nó. API query entity mới nhất rồi sửa entity đó, nên EF Core dùng version vừa đọc làm original concurrency token.

**Tại sao xảy ra:** `[Timestamp]` giúp phát hiện thay đổi xảy ra sau thời điểm `DbContext` load row, nhưng không tự biết browser đã đưa ra quyết định dựa trên version cũ hơn.

**Ảnh hưởng production:** Browser nhìn thấy `Pending`; integration chuyển row sang `Cancelled`; sau đó endpoint load `Cancelled` mới nhất và vẫn đổi thành `Approved`. Không có `DbUpdateConcurrencyException` vì version original của EF chính là version sau update của integration.

**Cách sửa:** Parse/validate client version và đặt nó làm original value của concurrency property trước `SaveChangesAsync`, hoặc thiết kế conditional update có predicate gồm `Id`, expected state/version. Khi zero rows affected/concurrency exception, trả conflict/precondition response và buộc client reload. HTTP `ETag`/`If-Match` cũng là contract phù hợp để đánh giá nếu API muốn dùng HTTP preconditions.

### Critical — Không enforce authorization/policy cho quyết định

**Vấn đề:** Endpoint sử dụng `User.Identity?.Name` nhưng không chứng minh caller có role/policy hoặc quyền trên expense cụ thể.

**Tại sao xảy ra:** Authentication identity bị nhầm với authorization.

**Ảnh hưởng production:** Authenticated user không đúng thẩm quyền có thể approve/reject request nếu route có thể gọi được.

**Cách sửa:** Dùng policy/resource-based authorization phù hợp business rule; xác minh manager ownership/scope và separation-of-duties nếu requirement có. Không tin client-supplied identity.

### High — State transition không được validate

**Vấn đề:** Mọi trạng thái khác `Approved` đều có thể chuyển sang `Approved` hoặc `Rejected`.

**Tại sao xảy ra:** Status được xử lý như string mutable thay vì business state transition.

**Ảnh hưởng production:** `Cancelled`, `Paid`, `Archived` hoặc trạng thái terminal khác có thể bị thay đổi trái rule.

**Cách sửa:** Mô hình hóa allowed transitions ở domain/application layer và reject invalid transition. Concurrency check và transition validation đều cần thiết: transition hợp lệ tại thời điểm đọc có thể không còn hợp lệ lúc commit.

### High — Không xử lý `DbUpdateConcurrencyException`

**Vấn đề:** Nếu một update thực sự xảy ra giữa query và save, exception có thể thành generic 500.

**Tại sao xảy ra:** API chưa có explicit concurrency response contract.

**Ảnh hưởng production:** Client không phân biệt conflict có thể retry sai hoặc hiển thị lỗi chung.

**Cách sửa:** Catch concurrency exception tại boundary thích hợp, không tự động retry business decision. Reload current representation nếu policy cho phép và trả `409 Conflict` hoặc `412 Precondition Failed` tùy contract. Không silently reapply decision lên state mới.

### High — Audit log chỉ được ghi sau thành công và thiếu version/transition context

**Vấn đề:** Log không ghi old status, expected version, resulting version, conflict hay correlation ID.

**Tại sao xảy ra:** Logging tập trung vào final success thay vì decision attempt.

**Ảnh hưởng production:** Khó reconstruct concurrent actions và security-sensitive decisions.

**Cách sửa:** Dùng durable audit record cho business decision nếu audit là requirement; structured operational log thêm actor ID ổn định, expense ID, old/new state, expected/current version, result và correlation ID. Tránh log comment nếu có sensitive data.

### Medium — Trả EF entity trực tiếp làm API representation

**Vấn đề:** Controller trả `expense` trực tiếp.

**Tại sao xảy ra:** Persistence model và API contract bị coupling.

**Ảnh hưởng production:** Có thể expose fields ngoài ý muốn và làm versioning khó hơn.

**Cách sửa:** Trả response DTO rõ ràng, bao gồm concurrency token/ETag cần thiết nhưng không expose persistence details khác.

### Medium — `RowVersion` chưa được validate

**Vấn đề:** Contract dùng `string` nhưng không quy định encoding hoặc malformed behavior.

**Tại sao xảy ra:** Serialization format của `byte[]` concurrency token không được định nghĩa ở API boundary.

**Ảnh hưởng production:** Invalid input có thể thành exception hoặc inconsistent client behavior.

**Cách sửa:** Chọn Base64/ETag contract rõ ràng, validate input và trả `400` khi malformed.

### Medium — String status làm invalid state dễ lọt qua

**Vấn đề:** Magic strings xuất hiện trong controller.

**Tại sao xảy ra:** Domain invariant không được encapsulate.

**Ảnh hưởng production:** Typo hoặc transition mới dễ tạo logic phân tán.

**Cách sửa:** Dùng enum/value object/state transition method phù hợp complexity; không cần DDD phức tạp nếu một service/domain method đơn giản đủ.

## Phiên bản đề xuất

Ví dụ dưới đây giữ thiết kế đơn giản, dùng client `RowVersion` làm expected version. Policy name chỉ là scenario contract và phải được cấu hình thực tế.

```csharp
[Authorize(Policy = "CanDecideExpense")]
[HttpPut("{id:long}/decision")]
public async Task<IActionResult> Decide(
    long id,
    ExpenseDecisionRequest request,
    CancellationToken cancellationToken)
{
    byte[] expectedVersion;
    try
    {
        expectedVersion = Convert.FromBase64String(request.RowVersion);
    }
    catch (FormatException)
    {
        return BadRequest(new ProblemDetails
        {
            Title = "Invalid row version"
        });
    }

    var expense = await _db.Expenses
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (expense is null)
        return NotFound();

    var authorization = await _authorizationService.AuthorizeAsync(
        User, expense, "CanDecideExpenseResource");

    if (!authorization.Succeeded)
        return Forbid();

    if (!ExpenseTransitions.CanDecide(expense.Status))
        return Conflict(new ProblemDetails
        {
            Title = "Expense can no longer be decided",
            Detail = $"Current status is {expense.Status}."
        });

    _db.Entry(expense)
        .Property(x => x.RowVersion)
        .OriginalValue = expectedVersion;

    var oldStatus = expense.Status;
    expense.Status = request.Approve ? "Approved" : "Rejected";
    expense.Comment = request.Comment;
    expense.DecidedBy = User.FindFirst("sub")?.Value;
    expense.DecidedUtc = DateTime.UtcNow;

    try
    {
        await _db.SaveChangesAsync(cancellationToken);
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict(new ProblemDetails
        {
            Title = "Expense changed since it was loaded",
            Detail = "Reload the expense before making another decision."
        });
    }

    _logger.LogInformation(
        "Expense {ExpenseId} decision {OldStatus}->{NewStatus} by {ActorId}",
        expense.Id, oldStatus, expense.Status, expense.DecidedBy);

    return Ok(new ExpenseDecisionResponse(
        expense.Id,
        expense.Status,
        Convert.ToBase64String(expense.RowVersion)));
}
```

Nếu chọn `ETag`/`If-Match`, server có thể trả version trong `ETag` khi GET và yêu cầu `If-Match` khi mutation. Khi precondition không còn đúng, `412 Precondition Failed` là một contract có thể phù hợp hơn `409`; team cần chọn nhất quán và document bằng OpenAPI.

## Giải thích thiết kế sau khi sửa

Concurrency token giờ đại diện cho state mà client thực sự nhìn thấy, thay vì state API vừa query. Business transition được validate riêng; authorization cũng là một concern riêng. Optimistic concurrency không biến business operation thành distributed lock và không nên bị “sửa” bằng blind retry: nếu người dùng đưa ra quyết định trên stale state, hệ thống cần surface conflict.

Nếu finance integration và user decision có priority rule đặc biệt, rule đó phải được business xác nhận. Reference solution không tự giả định `Cancelled` luôn thắng; nó chỉ ngăn silent overwrite và tạo nơi rõ ràng để enforce transition policy.

## Trade-offs

Optimistic concurrency làm client phải giữ version và xử lý conflict UX. Pessimistic locking có thể giảm một số conflict nhưng giữ lock lâu quanh human workflow là không phù hợp. Conditional SQL update có thể hiệu quả hơn load-and-save cho command đơn giản, nhưng cần giữ authorization, audit và domain transition rõ ràng. ETag chuẩn hóa HTTP precondition nhưng tăng contract work cho frontend.

## Cách kiểm thử

1. **Concurrency integration test:** hai clients đọc cùng version; client A save trước, client B phải nhận conflict thay vì overwrite.
2. **Integration race test:** finance worker đổi `Pending -> Cancelled` trước browser decision; browser dùng version cũ phải bị reject.
3. **Authorization test:** authenticated user ngoài approval scope nhận `403` và database không thay đổi.
4. **State-machine test:** các terminal states không được chuyển bằng endpoint nếu business rule không cho phép.
5. **API contract test:** malformed version trả `400`; conflict response có schema ổn định để frontend xử lý.

## Quan sát trong production

Theo dõi concurrency conflict rate theo endpoint/version, invalid transition count, forbidden decision count và decision latency. Structured log/audit cần correlation ID, actor ID, expense ID, expected/current version khi conflict và transition result. Application Insights có thể theo dõi request failures nhưng business audit nên có durable store nếu compliance yêu cầu; không phụ thuộc chỉ vào application log retention.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn `ETag`/`If-Match` thay vì gửi `RowVersion` trong JSON body?
2. Nếu business muốn finance cancellation luôn thắng user approval, bạn đặt invariant đó ở đâu để cả API và background integration cùng tuân thủ?
3. Tại sao automatic retry `DbUpdateConcurrencyException` rồi apply lại cùng decision có thể phá semantics của optimistic concurrency?

# Code Review Challenge 2 — Playwright E2E suite flaky vì shared state và chờ theo thời gian cố định

**Chủ đề:** Playwright, TypeScript, E2E testing, test isolation, parallel execution, CI reliability, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một e-commerce portal có Playwright E2E suite chạy trong CI sau deployment vào test environment. Suite chạy ổn khi developer chạy từng test local nhưng flaky khi CI bật nhiều workers. Hai test dưới đây cùng dùng một account và cùng thao tác giỏ hàng. Backend test environment có latency biến động; deployment đôi lúc làm API response chậm hơn bình thường nhưng vẫn trong SLO.

Team đang xử lý flake bằng cách tăng `waitForTimeout` và retry toàn suite. CI pass rate cải thiện tạm thời nhưng thời gian chạy tăng, và một số failure chỉ xuất hiện khi test chạy parallel. Mục tiêu là test phải độc lập, chẩn đoán được khi fail và không che regression thật bằng retry tùy tiện.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const email = 'e2e-shopper@example.test';
const password = process.env.E2E_PASSWORD!;

test.describe('shopping cart', () => {
  test.beforeEach(async ({ page }) => {
    await page.goto('/login');
    await page.fill('#email', email);
    await page.fill('#password', password);
    await page.click('button[type=submit]');
    await page.waitForTimeout(3000);
  });

  test('adds a product to cart', async ({ page }) => {
    await page.goto('/products/42');
    await page.click('[data-testid=add-to-cart]');
    await page.waitForTimeout(2000);

    await page.goto('/cart');
    const rows = await page.locator('.cart-row').count();
    expect(rows).toBe(1);
  });

  test('removes a product from cart', async ({ page }) => {
    await page.goto('/cart');

    if (await page.locator('.cart-row').count() === 0) {
      await page.goto('/products/42');
      await page.click('[data-testid=add-to-cart]');
      await page.waitForTimeout(1500);
      await page.goto('/cart');
    }

    await page.click('.remove-item');
    await page.waitForTimeout(2000);

    expect(await page.locator('.cart-row').count()).toBe(0);
  });
});
```

## Nhiệm vụ của ứng viên

1. Xác định nguyên nhân correctness/flakiness trong test design.
2. Phân tích shared account, parallel workers và backend state ảnh hưởng lẫn nhau như thế nào.
3. Xác định các assertion/waiting pattern có thể tạo false pass hoặc false failure.
4. Ưu tiên findings theo ảnh hưởng đến độ tin cậy của CI.
5. Đề xuất corrected test architecture mà không biến mọi test thành serial.
6. Giải thích test nào nên setup qua API/fixture và test nào cần giữ UI path.
7. Đề xuất artifacts/telemetry để debug flake mà không chỉ tăng retry.

## Câu hỏi gợi mở

1. Hai workers dùng cùng `email` có thật sự có isolated browser state nếu backend cart gắn với user không?
2. `waitForTimeout(3000)` chứng minh điều kiện nào đã sẵn sàng?
3. Test `removes a product` đang test một behavior hay đang phụ thuộc state từ test khác?
4. `locator.count()` rồi `expect(number)` khác gì web-first assertion của Playwright về auto-waiting?
5. Retry có thể làm mất tín hiệu regression nào nếu test không deterministic?

## Gợi ý

### Gợi ý 1

Primary risk là **test isolation**: browser context riêng không đồng nghĩa backend data riêng.

### Gợi ý 2

Thay time-based waiting bằng condition-based/web-first assertions và tạo deterministic test data per worker/test. Dùng UI cho behavior cần kiểm tra qua UI; dùng API/fixture cho setup nếu setup đó không phải mục tiêu của test.

## Kết quả code review tham khảo

### High — Shared backend account làm tests race khi chạy parallel

**Vấn đề:** Mọi worker dùng cùng account nên cùng cart state ở server.

**Tại sao xảy ra:** Playwright tạo browser contexts isolated, nhưng server-side identity/data vẫn chung.

**Ảnh hưởng production/CI:** Test A add item trong lúc test B remove; kết quả phụ thuộc scheduling. Local single-worker có thể pass còn CI parallel flaky.

**Cách sửa:** Provision unique user/cart per test hoặc per worker, hoặc cung cấp deterministic test-data API/fixture. Cleanup phải scoped theo data identity, không xóa global state của test khác.

### High — Fixed sleeps không đồng bộ với application state

**Vấn đề:** `waitForTimeout` giả định login/add/remove hoàn tất sau một số milliseconds cố định.

**Tại sao xảy ra:** CI latency biến động; sleep không quan sát condition thực tế.

**Ảnh hưởng production/CI:** Chậm hơn vẫn fail dù app hợp lệ; nhanh hơn thì test lãng phí thời gian. Tăng timeout chỉ dịch ngưỡng flake.

**Cách sửa:** Chờ navigation/URL hoặc UI state có ý nghĩa; dùng Playwright web-first assertions như `await expect(locator).toBeVisible()` / `toHaveCount()` và event/network synchronization khi thực sự cần.

### High — `removes a product` tự sửa precondition qua UI một cách không deterministic

**Vấn đề:** Test inspect cart rồi có thể add item, nhưng concurrent test có thể thay đổi cart giữa check và action.

**Tại sao xảy ra:** Check-then-act trên shared mutable backend state.

**Ảnh hưởng production/CI:** `.remove-item` có thể biến mất hoặc target item không phải item test tạo.

**Cách sửa:** Tạo known cart state trước test bằng isolated fixture/API. Test remove chỉ kiểm tra remove behavior từ deterministic precondition.

### Medium — Assertion dùng snapshot count thay vì web-first retrying assertion

**Vấn đề:** `const rows = await locator.count(); expect(rows).toBe(1)` lấy giá trị tại một thời điểm.

**Tại sao xảy ra:** Generic assertion không retry theo DOM state như locator assertion.

**Ảnh hưởng production/CI:** UI đang cập nhật hợp lệ vẫn có thể bị đọc quá sớm.

**Cách sửa:** `await expect(page.locator('.cart-row')).toHaveCount(1)` với timeout phù hợp SLO/test environment.

### Medium — Login lặp qua UI cho mọi test dù login không phải subject

**Vấn đề:** Mỗi test phụ thuộc login page và fixed wait.

**Tại sao xảy ra:** Setup và behavior under test bị trộn.

**Ảnh hưởng production/CI:** Suite chậm, failure surface lớn và auth UI flake làm cart tests fail dù cart đúng.

**Cách sửa:** Dùng authenticated `storageState` hoặc API-based auth fixture nếu phù hợp security architecture. Giữ một nhóm test riêng để kiểm tra login UI end-to-end.

### Medium — Selectors không nhất quán về stability

**Vấn đề:** Một số selector dựa CSS/class như `.cart-row`, `.remove-item`.

**Tại sao xảy ra:** Styling selector bị dùng như test contract.

**Ảnh hưởng production/CI:** Refactor CSS có thể làm E2E fail dù behavior không đổi.

**Cách sửa:** Ưu tiên role/accessible name hoặc explicit test IDs cho elements cần stable automation contract.

### Medium — Retry toàn suite có thể che nondeterminism

**Vấn đề:** Retry được dùng như primary flake mitigation.

**Tại sao xảy ra:** Không phân loại infra transient failure và deterministic product regression.

**Ảnh hưởng production/CI:** Build xanh sau retry có thể che race hoặc regression; thời gian feedback tăng.

**Cách sửa:** Retry có thể là safety net có giới hạn, nhưng cần theo dõi first-attempt failure rate, quarantine có owner/expiry nếu cần và sửa root cause. Retried pass vẫn phải tạo signal.

### Low — Thiếu diagnostic artifacts có hệ thống

**Vấn đề:** Snippet không cho thấy trace/screenshot/video/network artifacts khi failure.

**Tại sao xảy ra:** Debugging dựa vào rerun thay vì evidence.

**Ảnh hưởng production/CI:** Khó phân biệt frontend timing, API failure, test-data collision và deployment issue.

**Cách sửa:** Thu Playwright trace on first retry/failure, screenshot khi fail và attach server correlation ID/test run ID khi có thể; giữ artifacts theo retention phù hợp.

## Phiên bản đề xuất

Ví dụ này giả định team có test-support API chỉ tồn tại trong controlled test environment để tạo isolated user/cart. Nếu không có API đó, fixture có thể seed database qua một supported test-data service; không nên để test truy cập production database trực tiếp.

```ts
import { test as base, expect, request } from '@playwright/test';

const test = base.extend<{ shopper: { email: string; password: string } }>({
  shopper: async ({}, use, testInfo) => {
    const api = await request.newContext({ baseURL: process.env.BASE_URL });
    const unique = `${testInfo.workerIndex}-${testInfo.testId}`
      .replace(/[^a-zA-Z0-9-]/g, '')
      .slice(0, 40);

    const response = await api.post('/test-support/shoppers', {
      data: { key: unique, cart: [] }
    });
    expect(response.ok()).toBeTruthy();

    const shopper = await response.json();
    await use(shopper);

    await api.delete(`/test-support/shoppers/${shopper.id}`);
    await api.dispose();
  }
});

test.describe('shopping cart', () => {
  test.beforeEach(async ({ page, shopper }) => {
    await page.goto('/login');
    await page.getByLabel('Email').fill(shopper.email);
    await page.getByLabel('Password').fill(shopper.password);
    await page.getByRole('button', { name: 'Sign in' }).click();
    await expect(page).toHaveURL(/\/products|\/account/);
  });

  test('adds a product to cart', async ({ page }) => {
    await page.goto('/products/42');
    await page.getByTestId('add-to-cart').click();

    await page.goto('/cart');
    await expect(page.getByTestId('cart-row')).toHaveCount(1);
  });

  test('removes a product from cart', async ({ page, shopper, request }) => {
    const setup = await request.post(`/test-support/shoppers/${shopper.id}/cart`, {
      data: { productId: 42, quantity: 1 }
    });
    expect(setup.ok()).toBeTruthy();

    await page.goto('/cart');
    const row = page.getByTestId('cart-row').filter({ hasText: 'Product 42' });
    await expect(row).toHaveCount(1);

    await row.getByRole('button', { name: 'Remove' }).click();
    await expect(row).toHaveCount(0);
  });
});
```

Trong project thực tế, test-support endpoints phải được bảo vệ để không tồn tại hoặc không truy cập được trong production. Một alternative là worker-scoped account pool được provision trước và reset bằng authenticated test fixture. Không nên chọn serial mode chỉ để né shared-state race nếu suite có thể thiết kế isolation tốt hơn.

## Giải thích thiết kế sau khi sửa

Mỗi test có backend identity riêng nên parallel workers không chia sẻ cart. Precondition của remove test được tạo deterministic qua setup API vì mục tiêu test là remove UI, không phải add flow. Add flow vẫn được test riêng qua UI. Assertions dựa trên locator condition thay vì sleep.

Việc tách setup khỏi behavior giúp failure dễ phân loại: nếu test-support fixture fail, đó là environment/setup issue; nếu UI action fail, trace và network evidence có thể tập trung vào behavior thực sự.

## Trade-offs

Test-data API/fixture là infrastructure cần bảo trì và phải được cô lập khỏi production. Tạo user per test có thể làm suite chậm nếu provisioning đắt; worker-scoped identities là compromise nhưng cleanup cần chặt. `storageState` tăng tốc login nhưng có thể che auth regression nếu không giữ dedicated authentication E2E tests. Parallelism cao hơn rút ngắn runtime nhưng tăng load lên test environment, vì vậy worker count phải phù hợp capacity.

## Cách kiểm thử

1. **Parallel stress:** chạy cart spec nhiều lần với nhiều workers; first-attempt pass rate phải ổn định và không có cross-test data collision.
2. **Latency injection:** tăng API latency trong test environment; condition-based waits vẫn pass trong SLO thay vì phụ thuộc fixed sleep.
3. **Isolation validation:** log/test-run ID chứng minh mỗi test dùng shopper/cart riêng và cleanup không xóa data của worker khác.
4. **Failure diagnostics:** cố ý tạo một API 500 và xác minh trace/screenshot/network evidence đủ để xác định failure path.
5. **Deployment validation:** chạy smoke subset sau deploy trước full suite; phân biệt environment-unready failure với product regression.

## Quan sát trong production/CI

Theo dõi first-attempt pass rate, retry-pass rate, flake rate theo test, duration p50/p95, failure category và worker count. Lưu Playwright trace/screenshot cho failure theo retention hợp lý. Gắn `testRunId`/`testId` vào test-data identity và, nếu application hỗ trợ an toàn, correlation header để đối chiếu Application Insights/server logs. Alert hoặc quality gate nên dựa trên persistent flake/regression trend, không chỉ final pass sau retry.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn worker-scoped user thay vì test-scoped user, và trade-off isolation/performance là gì?
2. Test login qua `storageState` có làm giảm E2E confidence không? Bạn sẽ chia test portfolio thế nào?
3. Nếu test chỉ flaky trên CI sau khi tăng workers từ 4 lên 20, bạn sẽ phân biệt test race với test-environment capacity saturation bằng evidence nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Optimistic concurrency chỉ bảo vệ đúng business intent khi concurrency token đại diện cho state mà caller thực sự dựa vào. Việc entity có `[Timestamp]` không tự ngăn stale browser action nếu endpoint load version mới rồi bỏ qua expected version từ client. Với E2E testing, browser isolation không đồng nghĩa data isolation: shared server-side account vẫn tạo race giữa parallel workers.

Cả hai challenge đều yêu cầu xác định đúng **boundary của state**. Ở API, boundary là expected resource version và allowed transition. Ở test automation, boundary là test-owned backend data và condition mà test thực sự chờ đợi.

## Mẫu tư duy cần nhớ

* Với concurrent update, hỏi: **decision này dựa trên version nào của dữ liệu?**
* Không automatic retry một business conflict nếu retry có thể thay đổi ý nghĩa quyết định.
* Test chạy parallel phải cô lập **backend state**, không chỉ browser/process state.
* Chờ **condition**, không chờ một số milliseconds tùy ý.
* Retry trong CI là safety net, không phải bằng chứng test deterministic.
