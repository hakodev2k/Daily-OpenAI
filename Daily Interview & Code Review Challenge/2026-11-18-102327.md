# Câu 1 — Vì sao PostgreSQL keyset pagination vẫn trả bản ghi trùng?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** SQL, PostgreSQL, EF Core, LINQ translation, transaction isolation, HTTP pagination.

## Bối cảnh

Một API ASP.NET Core .NET 8 trả lịch sử thay đổi đơn hàng từ PostgreSQL. Bảng `order_events` có 12 triệu hàng, cột `id bigint` duy nhất, `created_at timestamptz`, `tenant_id uuid`, `event_type text`. API lấy 50 hàng/trang, sắp xếp `created_at DESC`; nhiều sự kiện cùng timestamp. Team thay `OFFSET` bằng keyset nhưng QA vẫn thấy trùng/bỏ sót khi người dùng chuyển trang, nhất là khi có insert liên tục. Đoạn truy vấn hiện tại:

```sql
SELECT id, created_at, event_type
FROM order_events
WHERE tenant_id = @tenant
  AND created_at < @cursor_created_at
ORDER BY created_at DESC
LIMIT 50;
```

Một developer khẳng định “keyset luôn không trùng, không bỏ sót và nhanh O(1)”. Hệ thống có nhiều tenant; chưa biết index hiện có, timestamp precision, cursor encoding và isolation level.

## Câu hỏi chính

Hãy giải thích từ cơ chế sắp xếp, predicate, index scan và MVCC vì sao hành vi này xảy ra; thiết kế lại pagination có tính xác định, nêu rõ giới hạn consistency khi dữ liệu thay đổi, và cách kiểm chứng trong production.

## Câu hỏi làm rõ nên cân nhắc

1. `created_at` có bất biến không, được tạo ở DB hay application, và có thể trùng đến mức nào?
2. Client truyền cursor thế nào; có giữ nguyên `tenant_id`, filter và sort giữa các trang không?
3. Yêu cầu là duyệt feed “mới nhất” hay xuất snapshot đầy đủ không bỏ sót?
4. Execution plan, index và số hàng mỗi tenant phân bố thế nào?
5. Có update/delete hàng đã phân trang và cần đảm bảo quyền tenant tại mọi request không?

## Gợi ý tư duy

### Gợi ý 1
Xem thứ tự sắp xếp có phải total order không.

### Gợi ý 2
Phân biệt cursor predicate với `ORDER BY`, đặc biệt khi nhiều hàng có cùng `created_at`.

### Gợi ý 3
Xem snapshot MVCC giữa các HTTP requests; một index tốt không tự tạo ra snapshot xuyên request.

## Cấu trúc trả lời đề xuất

1. Xác nhận semantics của feed và consistency.
2. Mô phỏng hai hàng cùng timestamp nằm ở ranh giới trang.
3. Phân tích execution plan, composite index và selectivity.
4. Đề xuất stable ordering và cursor.
5. Giải thích insert/update/delete trong các snapshot khác nhau.
6. Đưa ra test concurrency, telemetry và trade-offs.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `created_at` không duy nhất nên `created_at < cursor` loại bỏ các hàng cùng timestamp chưa đọc; chỉ thêm `id` vào ORDER BY mà không sửa predicate vẫn sai.
- Total order `ORDER BY created_at DESC, id DESC` và điều kiện lexicographic `(created_at, id) < (@ts, @id)`.
- Composite index phù hợp filter và order; đánh giá bằng `EXPLAIN (ANALYZE, BUFFERS)`, không hứa O(1).
- Các request ở `READ COMMITTED` có snapshot khác nhau; không thể hứa snapshot-consistent pagination khi dữ liệu đổi.

### Điểm cộng
- Cursor opaque, signed hoặc authenticated, gắn tenant/filter/order và version; giới hạn page size.
- Xử lý timezone, timestamp precision, nullable, duplicate client retry, và `id` tie-breaker.
- Distinguish immutable event feed với mutable `created_at`/sort key.

### Senior+
- Thiết kế snapshot export bằng transaction/snapshot hoặc materialized export session phù hợp thời gian sống; giải thích chi phí long-running transactions và vacuum.
- Chứng minh correctness qua invariant về total order, index behavior và các interleaving insert/delete.

## Hướng giải quyết tham khảo

**Giả định:** `created_at` và `id` bất biến, `id` unique; mỗi trang dùng filter tenant giống nhau. Nếu không thỏa, cần đổi schema hoặc semantics.

Với hai hàng `(10:00:00, 102)` và `(10:00:00, 101)`, nếu trang trước kết thúc tại `(10:00:00, 102)`, predicate chỉ dùng timestamp sẽ bỏ qua hàng 101. Ngược lại, nếu dùng `<=` có thể lặp hàng 102. Sửa cả order lẫn predicate:

```sql
SELECT id, created_at, event_type
FROM order_events
WHERE tenant_id = @tenant
  AND (created_at, id) < (@cursor_created_at, @cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT @page_size;
```

Trang đầu bỏ predicate cursor. Cursor lấy đúng hai giá trị từ hàng cuối, không lấy timestamp từ đồng hồ client. Index ứng viên:

```sql
CREATE INDEX CONCURRENTLY ix_events_tenant_created_id
ON order_events (tenant_id, created_at DESC, id DESC);
```

Việc tạo index cần kiểm tra chi phí storage, write amplification và tình trạng vận hành. `CONCURRENTLY` có giới hạn transaction và cần theo dõi trạng thái build. Không giả định index-only scan vì query còn đọc `event_type`, visibility map và các điều kiện khác. `EXPLAIN (ANALYZE, BUFFERS)` cùng `pg_stat_statements` giúp xác định scans, buffers, latency và index usage. Với EF Core, kiểm tra SQL thực tế từ `ToQueryString()`; biểu thức tương đương là `e.CreatedAt < ts || (e.CreatedAt == ts && e.Id < id)`. Không dựa vào giả định LINQ provider tự dịch tuple comparison.

**Consistency:** Keyset giảm tác động của chèn hàng mới ở phía trước cursor và tránh chi phí skip lớn, nhưng không đóng băng dữ liệu. Hàng mới có sort key nằm phía sau cursor vẫn có thể xuất hiện; update sort key hoặc delete có thể thay đổi tập kết quả. Nếu business yêu cầu export đúng một tập dữ liệu tại một thời điểm, cần snapshot strategy riêng, ví dụ tạo danh sách ID cố định cho export job, hoặc transaction với snapshot phù hợp và giới hạn lifetime. Không giữ transaction dài xuyên nhiều HTTP requests mà không cân nhắc connection, vacuum và resource pressure.

**Security:** luôn lấy tenant từ authorization context đã xác thực; không tin tenant trong cursor. Cursor chứa thông tin có thể bị sửa phải được bảo vệ integrity, đồng thời áp dụng authorization trên DB query.

**Kiểm thử:** seed nhiều hàng cùng timestamp ở ranh giới 50; duyệt toàn bộ so với tập chuẩn bất biến; chạy insert/update/delete giữa các trang; kiểm tra retry cursor, invalid cursor, cross-tenant, timezone/precision. **Monitoring:** p95 latency theo tenant và page depth, rows scanned/returned, DB buffers, query plan regressions, cursor validation failures.

**Khi nào thay đổi quyết định:** nếu user cần nhảy trực tiếp trang 200, keyset không đáp ứng random access dễ dàng; có thể chọn hybrid pagination hoặc thiết kế UX khác. Nếu tập dữ liệu nhỏ, OFFSET với index tốt có thể đủ.

## Mẫu trả lời trong phỏng vấn

“Trước hết tôi cần xác nhận API đang cung cấp live feed hay snapshot export. Query hiện tại không có thứ tự duy nhất: nhiều event cùng `created_at` nên cursor chỉ dựa timestamp sẽ bỏ sót các event nằm sau ranh giới trang. Tôi sẽ sắp xếp `created_at DESC, id DESC` và dùng điều kiện lexicographic tương ứng. Sau đó kiểm tra SQL do EF Core sinh ra và execution plan của PostgreSQL; index có thể bắt đầu bằng tenant rồi đến hai cột sort, nhưng phải đo trước khi quyết định. Keyset không đảm bảo O(1) hay snapshot consistency: mỗi request có thể thấy snapshot khác, và update/delete vẫn ảnh hưởng. Nếu requirement đòi export đầy đủ đúng một thời điểm, tôi sẽ dùng export snapshot riêng. Cuối cùng tôi kiểm thử dữ liệu trùng timestamp, concurrent writes và cross-tenant authorization, đồng thời đo p95 và buffers.”

## Câu hỏi đào sâu

1. Nếu `created_at` có thể được chỉnh sửa sau insert, bạn giữ semantics ổn định bằng cách nào?
2. Tại sao index `(created_at, id, tenant_id)` có thể kém hơn index tenant-first, và khi nào điều ngược lại có thể xảy ra?
3. Nếu Product yêu cầu “đến trang N” và tổng số kết quả chính xác, bạn chọn giải pháp nào thay vì keyset thuần?

## Lỗi trả lời thường gặp

- Chỉ thêm `id` vào `ORDER BY` nhưng giữ predicate cũ.
- Khẳng định keyset luôn O(1) và không bao giờ bỏ sót trong dữ liệu động.
- Dùng timestamp client làm cursor.
- Đề xuất Redis mà chưa xem query plan.
- Tin `tenant_id` do client cung cấp mà không xác thực quyền.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ consistency và filter | 1.5 |
| Giải thích total order/cursor chính xác | 2.5 |
| Phân tích PostgreSQL/index/EF Core | 2 |
| Concurrency và giới hạn MVCC | 1.5 |
| Testing, security, telemetry | 1.5 |
| Trade-off và diễn đạt | 1 |

# Câu 2 — IIS recycle sau deployment khiến checkout thất bại ngẫu nhiên

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC legacy, dependency troubleshooting, SQL Server, observability, release management.

## Bối cảnh

Một website e-commerce ASP.NET MVC chạy trên .NET Framework 4.5, IIS/Windows Server, SQL Server và API thanh toán bên thứ ba. Sau khi deploy bằng TeamCity + Octopus Deploy, tỷ lệ checkout lỗi tăng từ mức thông thường dưới 0,5% lên khoảng 6% trong 30 phút; một số khách thấy timeout hoặc HTTP 503, vài người retry và báo bị giữ tiền hai lần. App Pool có sự kiện recycle; CPU trung bình thấp, p95 checkout tăng từ 0,8 giây lên 11 giây. Log không có correlation ID xuyên web và payment API. Team muốn tăng timeout lên 120 giây và restart toàn bộ servers. Chưa rõ số node, sticky session, payment provider idempotency, database blocking hay thay đổi cấu hình.

## Câu hỏi chính

Bạn là người phụ trách incident: hãy đưa ra kế hoạch 0–15 phút, 15–60 phút và sau khi ổn định; phân biệt nhiều giả thuyết, xác minh nguyên nhân và triển khai remediation an toàn, đặc biệt tránh charge trùng.

## Câu hỏi làm rõ nên cân nhắc

1. Có bao nhiêu IIS nodes, load balancer, sticky session và overlapping recycle?
2. Release đổi binary, web.config, secrets, TLS, payment client hay schema SQL?
3. Provider trả transaction ID/idempotency key hoặc có API tra cứu trạng thái không?
4. HTTP 503 phát sinh ở proxy, IIS queue hay application; các thời điểm có trùng recycle?
5. Tỷ lệ thanh toán thực sự thành công so với UI báo lỗi, có audit trail và reconciliation không?

## Gợi ý tư duy

### Gợi ý 1
Ưu tiên an toàn giao dịch và ngăn thiệt hại trước khi tìm root cause.

### Gợi ý 2
HTTP timeout không chứng minh payment thất bại; phân biệt client, IIS, app, SQL và provider.

### Gợi ý 3
Dùng timeline deployment/recycle, request tracing, IIS logs, Windows Event Viewer, SQL waits và provider transaction records để loại trừ giả thuyết.

## Cấu trúc trả lời đề xuất

1. Định lượng impact và dừng tác động.
2. Chọn rollback hoặc giảm traffic dựa trên tính tương thích dữ liệu.
3. Chặn retry không an toàn và đối soát giao dịch không rõ trạng thái.
4. Lập timeline và thu bằng chứng theo từng tầng.
5. Xếp hạng giả thuyết, kiểm chứng và xác nhận root cause.
6. Hotfix, rollout theo từng node, test failure paths.
7. Dashboard, alert, postmortem và preventive controls.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Incident commander, freeze rollout, thông báo stakeholder, đánh dấu đơn hàng trạng thái unknown để đối soát.
- Không retry charge mù quáng; sử dụng idempotency nếu provider hỗ trợ, hoặc reconciliation/manual resolution nếu không.
- So sánh trước/sau deploy; tách 503 từ IIS/proxy với timeout ứng dụng và provider.
- Kiểm tra rollback compatibility trước khi rollback binary hoặc DB.

### Điểm cộng
- Theo dõi App Pool recycle reasons, startup/warmup, health, request queue, overlapped recycling và session state.
- Correlate payment attempt bằng internal order ID và provider transaction ID; không log PAN, tokens hay secrets.
- Canary/rolling release, smoke tests và synthetic checkout sandbox.

### Senior+
- State machine checkout rõ ràng, outbox/reconciliation job và audit bất biến.
- SLO/error budget, detection-to-mitigation time, runbook, deployment gates và chaos/failure-path tests.

## Hướng giải quyết tham khảo

**0–15 phút:** công bố incident severity theo doanh thu/ảnh hưởng; dừng deploy, giữ artifact và config hiện tại để so sánh. Nếu checkout có nguy cơ charge trùng, tạm hạn chế retry tự động và hiển thị trạng thái “đang xác minh” thay vì cho khách bấm thanh toán lại không kiểm soát. Cân nhắc giảm traffic sang healthy node, rollback **chỉ nếu** schema/config backward compatible. Thu thập danh sách orders/payment attempts cần reconciliation, liên hệ payment provider. Không restart đồng loạt vì mất bằng chứng và tăng outage.

**15–60 phút:** dựng timeline deployment, recycle, 503, p95, provider errors. Kiểm tra IIS access logs (`sc-status`, `sc-substatus`, `time-taken`), HTTPERR, Event Viewer/WAS, App Pool startup duration, request queue và recycle reasons. Với SQL Server, xem blocking, waits, connection pool timeouts và query regression. Với payment API, đo DNS/TLS/connect timeout, HTTP status, response times, provider incident, thay đổi certificate hoặc proxy. Chạy truy vấn audit: `order_id` → `attempt_id` → provider transaction ID → confirmed/unknown/failed. Dùng request ID mới xuyên gateway, web, SQL dependency và provider call; không lộ thông tin nhạy cảm.

**Các giả thuyết cạnh tranh:** (A) web.config change gây recycle và cold-start kéo dài; (B) App Pool crash hoặc memory pressure; (C) payment API latency/timeout; (D) SQL blocking/schema migration; (E) session state in-process mất sau recycle, khiến checkout replay. Mỗi giả thuyết cần dấu hiệu độc lập; ví dụ nếu 503 đồng thời với WAS recycle và queue length tăng, ưu tiên IIS, nhưng điều đó chưa chứng minh double charge. Đối chiếu provider ledger mới xác định charge thật.

**Remediation:** rollback config hoặc hotfix đúng thành phần, rollout một node và theo dõi p95, 5xx, successful checkouts, unknown payment states trước khi mở rộng. Với provider có idempotency key, tạo key ổn định cho một logical payment attempt, lưu durable trước call; nếu không hỗ trợ, phải tra cứu provider trước khi retry và đưa trường hợp không chắc chắn vào reconciliation/manual review. DB transaction không bao trùm network call; không giả định atomic commit xuyên SQL và payment provider.

**Prevention:** checkout state machine (`Pending`, `Processing`, `Succeeded`, `Failed`, `Unknown`) có unique constraints cho logical attempts, idempotent callbacks, audit log, background reconciliation và policy chống duplicate submit. Cải thiện deployment bằng warmup, rolling deployment, health validation, immutable artifacts, config diff, rollback rehearsal. Tránh kéo timeout lên 120 giây khi chưa có evidence vì có thể làm tăng resource occupancy và user retries.

**Kiểm thử:** staging recycle khi có in-flight checkout; inject payment timeout sau provider đã charge; duplicate callback; rollback binary với schema mới; load test cold start; đối soát unknown attempts. **Monitoring:** payment success/unknown rate, duplicate-attempt alerts, IIS 503 substatus, App Pool recycle count, checkout p95/p99, SQL waits, provider latency, reconciliation backlog.

**Điều kiện thay đổi quyết định:** nếu payment provider không có API tra cứu hoặc idempotency, cần quy trình thủ công chặt chẽ và giới hạn tự động retry; nếu deployment schema không backward compatible, ưu tiên roll-forward/hotfix thay vì rollback.

## Mẫu trả lời trong phỏng vấn

“Tôi ưu tiên hai rủi ro: mất khả năng checkout và khả năng charge trùng. Trong 15 phút đầu tôi freeze release, định lượng impact, ngăn retry thanh toán không an toàn và chuẩn bị rollback nếu tương thích schema. Tôi không coi HTTP timeout là payment failure; phải đối soát với provider. Sau đó tôi dựng timeline giữa deploy, IIS recycle, 503, SQL waits và payment dependency latency. Các giả thuyết gồm cold start, App Pool crash, SQL blocking, payment provider chậm hoặc session bị mất; tôi cần bằng chứng loại trừ từng nhánh. Khi có fix, tôi rollout một node, đo p95/5xx và trạng thái giao dịch unknown trước khi mở rộng. Về dài hạn tôi thiết kế payment attempts durable, idempotency và reconciliation, cộng thêm health gates, warmup và observability. Tôi sẽ không chỉ tăng timeout hoặc restart tất cả server vì có thể che root cause và làm lỗi nghiêm trọng hơn.”

## Câu hỏi đào sâu

1. Provider charge thành công nhưng response mất: nếu provider không hỗ trợ idempotency, bạn làm gì?
2. Nếu rollback binary sẽ phá schema mới, bạn quyết định roll-forward ra sao?
3. Nếu 503 vẫn tăng dù App Pool không recycle, bạn sẽ điều tra tầng nào tiếp theo?

## Lỗi trả lời thường gặp

- Retry payment khi gặp timeout mà không tra cứu trạng thái.
- Khẳng định recycle là root cause chỉ vì trùng thời gian.
- Restart toàn bộ servers trước khi thu bằng chứng.
- Log raw payment payload chứa secrets hoặc PII.
- Rollback mà không kiểm tra schema compatibility.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact, containment và incident communication | 2 |
| Payment safety/idempotency/reconciliation | 2 |
| Competing hypotheses và evidence | 2 |
| IIS/SQL/dependency technical depth | 1.5 |
| Safe remediation và rollout | 1 |
| Testing/monitoring/trade-offs/communication | 1.5 |

# Câu 3 — Thiết kế tìm kiếm nội dung CMS đa ngôn ngữ với Elasticsearch

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS concepts, Elasticsearch, Azure App Service, Azure Service Bus alternatives, CDN, SEO, data ownership, distributed consistency.

## Bối cảnh

Một website marketing/e-commerce dùng Optimizely CMS để quản lý trang, blocks, bản dịch và lịch publish. Team muốn thêm search cho 200.000 content items bằng tiếng Việt/Anh; cần lọc theo category, locale, publish window và quyền xem. Mục tiêu ban đầu p95 dưới 500ms (giả định SLO), traffic cao vào giờ chạy campaign, có Akamai trước origin. Content publish/unpublish thường xuyên; marketing yêu cầu kết quả tìm kiếm cập nhật “nhanh” nhưng chưa định nghĩa. Team cân nhắc: truy vấn CMS DB trực tiếp, Elasticsearch index, hoặc managed search service. Chưa có đội vận hành search chuyên trách.

## Câu hỏi chính

Bạn sẽ chọn kiến trúc search và đồng bộ CMS như thế nào, với yêu cầu correctness, authorization, SEO, performance và vận hành? Hãy so sánh giải pháp đơn giản với search index và nêu điều kiện khiến bạn đổi lựa chọn.

## Câu hỏi làm rõ nên cân nhắc

1. Search cần full-text ranking, typo tolerance, autocomplete hay chỉ lọc category/title?
2. “Cập nhật nhanh” là vài giây, vài phút hay strong consistency sau publish/unpublish?

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không chọn Elasticsearch mặc định nếu nhu cầu chỉ là filter đơn giản và SQL đáp ứng SLO.
- CMS là source of truth; search index là derived read model có thể rebuild.
- Publish/unpublish, locale, visibility và access rules phải được xử lý nhất quán.
- Thiết kế reindex/reconciliation, eventual consistency và failure mode.

### Điểm cộng
- Analyzer phù hợp ngôn ngữ được benchmark bằng corpus thật; `text` cho full-text, `keyword` cho exact filter.
- Index alias/version và zero-downtime reindex; idempotent upsert theo content version.
- CDN cache key, TTL/purge và tránh cache public cho private queries.

### Senior+
- Quy định rõ freshness SLO, safety-first unpublish behavior, authorization ở nguồn đáng tin cậy và strategy khi index lag.
- Trade-offs về cost, ops, observability, multi-tenant isolation và rollback.

## Hướng giải quyết tham khảo

**Giả định:** cần full-text ranking và filtering đa ngôn ngữ, freshness chấp nhận eventual consistency vài chục giây; content public là chủ yếu. Đây là assumption cần Product xác nhận, không phải guarantee của Elasticsearch hay CMS.

**Architecture:** Optimizely CMS lưu nội dung và trạng thái publish; projection worker lấy content đã publish và tạo search documents với `contentId`, `language`, `version`, `title`, `summary`, `categoryIds`, `publishedFrom/Until`, `visibility`, `canonicalUrl`. API search chạy ở ASP.NET Core, query search backend theo text + locale + filters, trả IDs/snippets và URLs. Đừng index raw draft hoặc secret. Với nội dung private, áp dụng authorization server-side trên tập kết quả và cân nhắc không đưa vào public index; không tin client-supplied role filter. Các quyền phức tạp cần kiểm tra lại ở nguồn đáng tin cậy trước khi hiển thị nội dung.

**Sync:** publish/unpublish event được đưa qua durable integration boundary nếu platform hỗ trợ; nếu event source không durable, bổ sung polling reconciliation. Worker idempotent theo content/version, tránh event cũ ghi đè bản mới bằng version ordering; delete/tombstone khi unpublish, xóa quyền truy cập ngay theo yêu cầu bảo mật. Nếu có nguy cơ stale private content, dùng denylist/revalidation tại read path hoặc không index private content. Queue không bắt buộc nếu nhu cầu nhỏ và webhook + retry đủ tin cậy; Service Bus hữu ích khi cần buffer/retry/decouple nhưng làm tăng complexity.

**Index/query:** dùng fields `text` với analyzer được test cho tiếng Việt/Anh, `keyword` cho locale/category/status; không giả định analyzer mặc định xử lý tiếng Việt tốt. Query cần deterministic sort tie-breaker, bounded page size, escaping input, query timeouts và rate limits. Benchmark relevance bằng tập query đại diện, p50/p95/p99, indexing lag, shard/memory usage. Nếu chỉ cần title/category exact filters, thử PostgreSQL full-text hoặc SQL trước khi vận hành cluster mới.

**CDN/SEO:** Akamai chỉ cache public GET có key đầy đủ locale/query/filter; TTL ngắn theo freshness SLO, purge/invalidation khi campaign thay đổi. Không cache response có thông tin phân quyền trong shared cache. Canonical URL, redirects, sitemap và robots được sinh từ published CMS content, không lấy search index eventual-consistent làm authority. Search results pages có thể cần noindex tùy SEO strategy; quyết định với Product/SEO, không mặc định mọi search URL phải index.

**Failure:** search cluster down → trả degraded experience (ví dụ category navigation, thông báo search tạm không khả dụng) thay vì tự động query CMS DB với traffic không giới hạn. Reindex bằng versioned index + alias switch sau validation, có rollback alias và reconcile drift. CMS vẫn hoạt động khi search unavailable.

**Testing:** contract tests CMS event → document, out-of-order updates, unpublish security, locale ranking, search outage, reindex with concurrent writes, cache leakage, load tests và Playwright E2E cho search UX. **Telemetry:** indexing lag p95/max, DLQ/retry count nếu có queue, index document mismatch, search p95, timeout/error rate, cache hit/miss, unauthorized exposure tests, reindex duration.

**Khi nào thay đổi:** nếu strong consistency ngay sau unpublish là bắt buộc, search index eventual consistency một mình không đủ; cần read-time authorization/visibility gate hoặc mô hình khác. Nếu traffic thấp và query đơn giản, SQL-backed search ít operational overhead hơn. Nếu không có search ops team, cân nhắc managed search dựa trên chi phí và yêu cầu thực tế, không mặc định rẻ hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi bắt đầu bằng việc làm rõ search có cần full-text ranking hay chỉ lọc nội dung, và thời gian cho phép sau publish/unpublish. Nếu chỉ lọc đơn giản, tôi benchmark database trước. Nếu cần full-text đa ngôn ngữ, tôi dùng CMS làm source of truth và Elasticsearch như derived read model, đồng bộ bằng sự kiện có retry và reconciliation. Document có content ID, locale, version và visibility; event cũ không được ghi đè version mới. Tôi sẽ đặc biệt bảo vệ unpublish và private content bằng authorization ở backend, không tin cache hay index là nguồn quyền. Tôi benchmark analyzer tiếng Việt/Anh, query latency và indexing lag. Khi search lỗi, website vẫn phục vụ CMS pages, search degraded có kiểm soát. Reindex bằng index version/alias, test concurrent updates, cache leakage và rollback. Chọn managed search hay self-hosted phụ thuộc đội vận hành và chi phí, không phải vì kiến trúc càng phức tạp càng tốt.”
