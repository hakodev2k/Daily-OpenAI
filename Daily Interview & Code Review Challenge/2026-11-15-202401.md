## Bối cảnh

Nhân viên merchandising có thể sửa giá thủ công khi campaign đang chạy; một sản phẩm có thể thuộc nhiều campaign nhưng chỉ campaign có priority cao nhất được áp dụng. Production xuất hiện giá quay về mức cũ sau khi nhân viên cập nhật, và một số campaign kết thúc sớm. Mỗi lần thay đổi giá phải có audit trail; không được khóa toàn bộ catalog. Giả định thời điểm hiệu lực là UTC, giá tiền dùng decimal.

## Đoạn code cần review

```csharp
public sealed class PromotionWorker(
    IServiceScopeFactory scopes,
    ILogger<PromotionWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<CatalogDb>();
            var now = DateTime.UtcNow;

            var campaigns = await db.Campaigns
                .Include(x => x.Products)
                .Where(x => x.StartsAt <= now && x.EndsAt >= now)
                .ToListAsync(stoppingToken);

            foreach (var campaign in campaigns)
            {
                foreach (var item in campaign.Products)
                {
                    var product = await db.Products
                        .SingleAsync(x => x.Id == item.ProductId, stoppingToken);
                    if (item.OriginalPrice == null)
                        item.OriginalPrice = product.Price;
                    product.Price = item.PromotionalPrice;
                }
                campaign.IsActive = true;
            }

            var expired = await db.Campaigns
                .Include(x => x.Products)
                .Where(x => x.IsActive && x.EndsAt < now)
                .ToListAsync(stoppingToken);

            foreach (var campaign in expired)
            {
                foreach (var item in campaign.Products)
                {
                    var product = await db.Products
                        .SingleAsync(x => x.Id == item.ProductId, stoppingToken);
                    product.Price = item.OriginalPrice ?? product.Price;
                }
                campaign.IsActive = false;
            }

            await db.SaveChangesAsync(stoppingToken);
            logger.LogInformation("Promotion cycle completed at {Time}", now);
            await Task.Delay(TimeSpan.FromMinutes(1), stoppingToken);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Khôi phục giá cũ làm mất cập nhật hợp lệ

**Vấn đề:** `OriginalPrice` lưu snapshot rồi dùng ghi đè `Product.Price` khi hết hạn.

**Tại sao xảy ra:** Snapshot không đại diện cho base price hiện tại sau chỉnh sửa thủ công.

**Ảnh hưởng production:** Sai giá bán, thiệt hại tài chính và tranh chấp đơn hàng.

**Cách sửa:** Tách `BasePrice` khỏi `EffectivePrice`; tính effective price từ base price và campaign còn hiệu lực theo rule xác định.

### [High] — Không xác định precedence của các campaign chồng lấn

**Vấn đề:** Vòng lặp ghi giá theo thứ tự trả về của query, không theo priority.

**Tại sao xảy ra:** Không có policy giải quyết conflict hoặc tie-breaker ổn định.

**Ảnh hưởng production:** Giá thay đổi không dự đoán được giữa các lần chạy.

**Cách sửa:** Chọn campaign hợp lệ có `Priority` cao nhất, tie-break bằng `CampaignId` hoặc rule nghiệp vụ đã thống nhất.

### [High] — Lost update giữa replicas và chỉnh sửa thủ công

**Vấn đề:** Nhiều DbContext đọc giá rồi cùng ghi mà không kiểm tra version.

**Tại sao xảy ra:** Transaction của `SaveChanges` không tự phát hiện lost update nếu thiếu concurrency token/conditional update.

**Ảnh hưởng production:** Giá bị ghi đè, audit thiếu tính liên tục.

**Cách sửa:** Dùng concurrency token (PostgreSQL `xmin` nếu mapping/version phù hợp, hoặc application-managed version), retry bounded khi conflict, recompute từ state mới.

### [High] — Không có audit trail của thay đổi giá

**Vấn đề:** Worker cập nhật giá nhưng không lưu lý do, campaign, giá trước/sau và actor.

**Tại sao xảy ra:** Audit không nằm trong cùng transaction với giá.

**Ảnh hưởng production:** Không thể truy nguyên quyết định giá.

**Cách sửa:** Ghi audit event cùng transaction; outbox nếu phải phát sự kiện ra hệ thống khác.

### [High] — Trạng thái active dựa trên worker có thể lệch với thời gian hiệu lực

**Vấn đề:** `IsActive` chỉ được đổi khi worker chạy; query active dùng `EndsAt >= now` trong khi expired dùng `EndsAt < now`.

**Tại sao xảy ra:** Trạng thái lưu trữ phụ thuộc tick và có thể lệch khi worker down; boundary tại `EndsAt` chưa thống nhất.

**Ảnh hưởng production:** Giá stale, báo cáo trạng thái sai.

**Cách sửa:** Định nghĩa interval nửa mở `[StartsAt, EndsAt)`; dùng thời gian hiệu lực làm source of truth, không dùng cờ worker làm quyết định giá.

### [Medium] — N+1 queries và tracking graph lớn

**Vấn đề:** Mỗi item phát sinh `SingleAsync`; `Include` tải toàn bộ campaign products.

**Tại sao xảy ra:** Truy vấn theo item thay vì batch theo SKU bị ảnh hưởng.

**Ảnh hưởng production:** DB load cao, cycle kéo dài và memory tăng.

**Cách sửa:** Truy vấn theo batch, projection, giới hạn batch size và kiểm tra execution plan.

### [Medium] — Tick mỗi phút không bảo đảm chạy đúng boundary

**Vấn đề:** `Task.Delay` sau khi xử lý khiến chu kỳ trôi theo duration.

**Tại sao xảy ra:** Worker không phải scheduler chính xác theo thời gian.

**Ảnh hưởng production:** Promotion có thể kích hoạt trễ, đặc biệt sau deploy.

**Cách sửa:** Dùng reconciliation theo UTC và `PeriodicTimer` cho polling; nếu cần độ chính xác cao, thiết kế event-driven scheduling kèm reconciliation.

### [Medium] — Logging không cho biết sản phẩm nào bị ảnh hưởng

**Vấn đề:** Chỉ có log hoàn thành vòng chạy.

**Tại sao xảy ra:** Không có metrics conflicts, số SKU, duration và failed batches.

**Ảnh hưởng production:** Khó phát hiện giá stale hoặc lỗi âm thầm.

**Cách sửa:** Structured logs và metrics theo batch, campaign, số conflict, giá lệch và thời gian xử lý.

## Phiên bản đề xuất

Thiết kế dưới đây minh họa phần lõi tính giá; giả định `CatalogDb` có `ProductPrices`, `CampaignItems`, `PriceAudits`, trường `Version` được cấu hình concurrency token, và `CampaignItems` chứa `StartsAt`, `EndsAt`, `Priority`, `CampaignId`. Bản production cần batching, lease/queue và transaction boundaries theo batch.

```csharp
public async Task ReconcilePriceAsync(
    Guid productId, DateTime nowUtc, CancellationToken ct)
{
    for (var attempt = 0; attempt < 3; attempt++)
    {
        await using var db = await dbFactory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var price = await db.ProductPrices
            .SingleAsync(x => x.ProductId == productId, ct);

        var winner = await db.CampaignItems.AsNoTracking()
            .Where(x => x.ProductId == productId
                && x.StartsAt <= nowUtc && nowUtc < x.EndsAt)
            .OrderByDescending(x => x.Priority)
            .ThenBy(x => x.CampaignId)
            .Select(x => new { x.CampaignId, x.PromotionalPrice })
            .FirstOrDefaultAsync(ct);

        var next = winner?.PromotionalPrice ?? price.BasePrice;
        if (next == price.EffectivePrice)
            return;

        var before = price.EffectivePrice;
        price.EffectivePrice = next;
        price.Version++;

        db.PriceAudits.Add(new PriceAudit
        {
            ProductId = productId,
            OldPrice = before,
            NewPrice = next,
            CampaignId = winner?.CampaignId,
            ChangedAt = nowUtc
        });

        try
        {
            await db.SaveChangesAsync(ct);
            await tx.CommitAsync(ct);
            return;
        }
        catch (DbUpdateConcurrencyException) when (attempt < 2)
        {
            await tx.RollbackAsync(ct);
        }
    }
}
```

**Lưu ý:** Ví dụ chỉ xử lý optimistic conflict, chưa xử lý retry cho lỗi mạng/DB transient. Không tái sử dụng `DbContext` đã conflict. Trước khi dùng thực tế, bảo đảm mapping `Version` đúng và mọi writer của `BasePrice`/effective price cùng tuân thủ versioning. Tính lại theo timestamp mới khi retry nếu yêu cầu độ chính xác boundary nghiêm ngặt. Nếu read path cần chính xác tuyệt đối tại boundary, có thể tính effective price lúc đọc hoặc dùng cơ chế invalidation nhất quán thay vì chờ reconciliation.

## Giải thích thiết kế sau khi sửa

Base price là dữ liệu nghiệp vụ độc lập; effective price là projection có thể tái tính. Chọn winner có thứ tự ổn định, dùng concurrency token để tránh lost update, audit trong cùng transaction với giá. Một scheduler chỉ chọn các SKU cần reconcile; multiple replicas có thể xử lý cùng SKU nhưng conflict sẽ được phát hiện.

## Trade-offs

Reconciliation tạo write amplification và độ trễ theo tick; tính giá khi đọc tăng query cost. Versioning tăng retry và contention trên SKU nóng. Audit tăng dung lượng. Distributed lease có thể giảm duplicate work nhưng không thay thế optimistic concurrency; cần cân bằng freshness và chi phí.

## Cách kiểm thử

1. **Integration:** Hai campaign overlap và priority bằng nhau cho kết quả deterministic.
2. **Concurrency:** 4 workers cùng cập nhật SKU trong khi merchandising sửa base price; không mất cập nhật.
3. **Boundary:** Test `StartsAt`, `EndsAt` chính xác với interval nửa mở.
4. **Failure-path:** Kill worker sau DB commit, chạy reconciliation lại; không tạo audit thay đổi giả.
5. **Load:** 100.000 SKU hết hạn cùng phút; đo p95 cycle, DB CPU, lock waits và query count.

## Quan sát trong production

Theo dõi `promotion_reconcile_duration_ms`, `affected_sku_count`, `concurrency_conflict_count`, `price_mismatch_count`; trace theo batch ID, campaign ID; alert nếu reconciliation lag vượt SLO. Không đưa thông tin nhạy cảm vào log.

## Câu hỏi phỏng vấn mở rộng

1. Nếu checkout đã chốt giá, giá order line cần được snapshot và xác thực ở bước nào?
2. Khi cache/CDN giữ giá cũ, thiết kế invalidation như thế nào để tránh sai giá?
3. Có nên tính giá ở read path thay vì persist projection nếu catalog nhỏ?

import { ref, watch, onMounted } from 'vue'

type Customer = { id: string; name: string; tenantId: string }
const props = defineProps<{ tenantId: string }>()
const keyword = ref('')
const customers = ref<Customer[]>([])
const loading = ref(false)
const error = ref('')
const selected = ref<Customer | null>(null)

async function load() {
  loading.value = true
  error.value = ''
  const response = await fetch(

onMounted(load)

  selected.value = customer
}

    <p v-if="error">{{ error }}</p>
    <ul>

### [Critical] — Render HTML không tin cậy

**Vấn đề:** `v-html` đưa `customer.name` vào DOM như HTML.

**Tại sao xảy ra:** Vue không escape nội dung truyền vào `v-html`.

**Cách sửa:** Dùng text interpolation; không render HTML khi chỉ cần hiển thị tên.

### [High] — Race condition ghi đè kết quả mới

**Vấn đề:** Request cũ hoàn thành sau request mới vẫn ghi `customers`.

**Tại sao xảy ra:** Không cancel và không xác thực request identity.

**Ảnh hưởng production:** Hiển thị kết quả tenant/từ khóa cũ, người dùng thao tác nhầm. Đây là lỗi UI, không được xem là ranh giới authorization; backend vẫn phải enforce tenant.

**Tại sao xảy ra:** State lựa chọn không phụ thuộc tenant.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type Customer = { id: string; name: string; tenantId: string }
const props = defineProps<{ tenantId: string }>()
const keyword = ref('')
const customers = ref<Customer[]>([])
const selected = ref<Customer | null>(null)
const loading = ref(false)
const error = ref('')

watch(
  [keyword, () => props.tenantId],
  (_values, _old, onCleanup) => {
    const controller = new AbortController()
    let current = true
    let timer: ReturnType<typeof setTimeout> | undefined

    onCleanup(() => {
      current = false
      controller.abort()
      if (timer !== undefined) clearTimeout(timer)
    })

    customers.value = []
    selected.value = null
    error.value = ''
    loading.value = true

    timer = setTimeout(async () => {
      try {
        const params = new URLSearchParams({
          tenantId: props.tenantId, q: keyword.value
        })
        const response = await fetch(
          '/api/customers?' + params.toString(),
          { signal: controller.signal }
        )
        if (!response.ok) throw new Error('HTTP ' + response.status)
        const data = (await response.json()) as Customer[]
        if (current) customers.value = data
      } catch (e) {
        if (current && !controller.signal.aborted)
          error.value = 'Không thể tải danh sách khách hàng'
      } finally {
        if (current) loading.value = false
      }
    }, 250)
  },
  { immediate: true }
)

function choose(customer: Customer) {
  if (customer.tenantId === props.tenantId)
    selected.value = customer
}
</script>

<template>
  <section>
    <label for="customer-query">Tìm khách hàng</label>
    <input id="customer-query" v-model="keyword" />
    <p v-if="loading">Đang tải...</p>
    <p v-if="error" role="alert">{{ error }}</p>
    <p v-if="!loading && !error && !customers.length">Không có kết quả</p>
    <ul>
      <li v-for="customer in customers" :key="customer.id">
        <button type="button" @click="choose(customer)">
          {{ customer.name }}
        </button>
      </li>
    </ul>
    <p v-if="selected">Đã chọn: {{ selected.name }}</p>
  </section>
</template>
```

Giả định endpoint trả về `Customer[]` đã validate và có `tenantId`; cần schema validation nếu response không tin cậy. Việc hủy `fetch` chỉ giảm lãng phí phía client, không bảo đảm server đã dừng xử lý. Backend phải thực thi authorization theo tenant dựa trên identity được xác thực, không tin query parameter.

## Giải thích thiết kế sau khi sửa

`watch` có cleanup cho mỗi lần dependency đổi và khi component dừng; flag `current` bảo vệ commit state ngay cả nếu cancellation không ngăn được completion. Reset state đồng bộ khi context đổi. Dùng text interpolation để Vue escape HTML. `URLSearchParams` bảo đảm encoding; debounce giảm request nhưng không phải giải pháp race condition.

## Trade-offs

Debounce làm tăng độ trễ cảm nhận 250 ms; cancel có thể không tiết kiệm tài nguyên server nếu request đã đến. Xóa kết quả ngay khi tìm lại tránh stale state nhưng có thể gây flicker; nếu muốn giữ dữ liệu cũ, phải gắn nhãn rõ context và khóa hành động. Có thể dùng query library nhưng thêm dependency và quy tắc cache key cần kiểm soát.

## Cách kiểm thử

1. **Component test:** Mock A trả về sau B; chỉ hiển thị kết quả B.
2. **Security:** Tên khách hàng chứa HTML/script payload; DOM chỉ hiện text, không chạy handler.
3. **E2E Playwright:** Chuyển tenant trong khi request pending; không còn selection hoặc kết quả cũ.
4. **Failure-path:** Network timeout, HTTP 500 và abort; loading/error kết thúc đúng.
5. **Load/network:** Gõ 20 ký tự liên tục; kiểm tra số request thực tế và cancellation.

## Quan sát trong production

Đo frontend search latency, aborted request count, error rate theo HTTP status, số request/keystroke, client-side exception và backend dependency traces qua correlation ID. Không log keyword chứa PII; giám sát cảnh báo XSS/CSP violation nếu triển khai CSP reporting.

2. Khi người dùng đổi tenant, có nên hủy cả mutation đang chạy không?
3. Làm sao xác nhận backend không có IDOR dù frontend đã reset state?
