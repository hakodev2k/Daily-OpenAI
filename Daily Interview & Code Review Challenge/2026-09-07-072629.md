# Code Review Challenge 1 — CMS cache trả sai nội dung giữa site, culture và preview

**Chủ đề:** C#/.NET, ASP.NET Core, Optimizely CMS, caching, Akamai/CDN, multi-site content delivery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một marketing platform dùng Optimizely CMS để phục vụ nhiều website trên cùng application. Hệ thống chạy nhiều instance trên Azure App Service, hỗ trợ `en-US`, `en-GB`, `vi-VN`, có editor preview mode và Akamai cache HTML ở edge. Application dùng `IMemoryCache` để giảm content load.

Production ghi nhận:

- user ở UK đôi khi nhận title của US site;
- sau publish, một số node vẫn trả content cũ;
- editor preview đôi khi thấy published content;
- purge Akamai xong nhưng một số App Service instance vẫn trả stale content;
- một lần authenticated user nhận banner chứa tên user khác.

## Đoạn code cần review

```csharp
public sealed class CmsPageRenderer
{
    private readonly IMemoryCache _cache;
    private readonly IContentLoader _contentLoader;
    private readonly IHttpContextAccessor _httpContextAccessor;

    public CmsPageRenderer(
        IMemoryCache cache,
        IContentLoader contentLoader,
        IHttpContextAccessor httpContextAccessor)
    {
        _cache = cache;
        _contentLoader = contentLoader;
        _httpContextAccessor = httpContextAccessor;
    }

    public PageViewModel GetPage(
        ContentReference contentLink,
        CultureInfo culture,
        bool preview)
    {
        var cacheKey = $"page:{contentLink.ID}";

        return _cache.GetOrCreate(cacheKey, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);

            var page = _contentLoader.Get<PageData>(contentLink);
            var user = _httpContextAccessor.HttpContext?.User;

            return new PageViewModel
            {
                Id = contentLink.ID,
                Title = page.Name,
                MainHtml = page["MainBody"]?.ToString(),
                IsPreview = preview,
                BannerText = user?.Identity?.IsAuthenticated == true
                    ? $"Welcome {user.Identity.Name}"
                    : "Welcome guest"
            };
        })!;
    }
}

[HttpGet("/{**path}")]
public IActionResult RenderPage(
    ContentReference contentLink,
    string culture,
    bool preview = false)
{
    var model = _renderer.GetPage(
        contentLink,
        CultureInfo.GetCultureInfo(culture),
        preview);

    Response.Headers.CacheControl = "public,max-age=300";
    return View("Page", model);
}
```

## Kết quả code review tham khảo

### Critical — Personalized data bị lưu trong shared cache

**Vấn đề:** `BannerText` lấy từ current user rồi nằm trong object cache dùng lại cho request sau.  
**Tại sao xảy ra:** cache key không có user scope.  
**Ảnh hưởng production:** user B có thể nhận data của user A.  
**Cách sửa:** chỉ cache public deterministic CMS projection; personalized fragment render ngoài shared cache.

### Critical — Shared HTTP cache áp dụng cho authenticated và preview response

**Vấn đề:** controller luôn trả `public,max-age=300`.  
**Tại sao xảy ra:** không phân biệt public anonymous traffic với private/preview traffic.  
**Ảnh hưởng production:** intermediary cache có thể chia sẻ response không nên được chia sẻ.  
**Cách sửa:** chỉ public-cache anonymous deterministic pages; preview/authenticated response dùng private/no-store policy phù hợp requirement.

### High — Cache key chỉ dựa trên content ID

**Vấn đề:** key bỏ qua site, culture và delivery mode.  
**Tại sao xảy ra:** content ID bị coi như toàn bộ rendered-output identity.  
**Ảnh hưởng production:** `en-US` có thể contaminate `en-GB`; preview và public path có thể va chạm.  
**Cách sửa:** cache key phải chứa mọi dimension thực sự thay đổi output: site/host identity, content identity, culture và published/preview mode.

### High — `culture` không được dùng khi load content

**Vấn đề:** method nhận `CultureInfo` nhưng content load path không thể hiện language-specific resolution.  
**Tại sao xảy ra:** culture chỉ tồn tại trong signature.  
**Ảnh hưởng production:** result có thể phụ thuộc ambient/default context.  
**Cách sửa:** resolve content bằng explicit CMS language/content-delivery context phù hợp integration.

### High — Preview flag không điều khiển version resolution

**Vấn đề:** `preview` chỉ được ghi vào view model.  
**Tại sao xảy ra:** public và preview dùng cùng loader/cache path.  
**Ảnh hưởng production:** editor có thể thấy published content; preview state có nguy cơ contaminate public cache.  
**Cách sửa:** tách preview delivery path, authorization, version resolution và caching semantics.

### High — `IMemoryCache` là per-process

**Vấn đề:** mỗi application instance giữ cache riêng.  
**Tại sao xảy ra:** in-memory cache không phải distributed cache.  
**Ảnh hưởng production:** publish/invalidation trên một instance không tự động làm instance khác fresh.  
**Cách sửa:** dùng CMS-native invalidation/event mechanism hoặc cross-instance invalidation strategy; TTL chỉ là safety net.

### High — CDN purge không invalidation origin cache

**Vấn đề:** team coi Akamai purge như toàn bộ cache reset.  
**Tại sao xảy ra:** CDN và origin memory cache độc lập.  
**Ảnh hưởng production:** edge purge xong nhưng origin vẫn trả stale HTML rồi edge cache lại stale response.  
**Cách sửa:** define publish choreography rõ ràng cho origin invalidation và CDN invalidation/versioning.

### Medium — TTL cố định không phản ánh publish semantics

**Vấn đề:** stale content chỉ biến mất theo thời gian.  
**Tại sao xảy ra:** không có publish event/dependency invalidation.  
**Ảnh hưởng production:** freshness không deterministic.  
**Cách sửa:** event-driven/dependency invalidation; TTL là fallback.

### Medium — Thiếu observability theo cache dimension

**Vấn đề:** không có hit/miss và invalidation telemetry theo site/culture/delivery mode.  
**Tại sao xảy ra:** cache bị xem như local optimization.  
**Ảnh hưởng production:** khó xác định stale response đến từ CMS, origin hay CDN.  
**Cách sửa:** metrics/logs theo cache layer, site, culture, content identity và publish correlation ID.

## Phiên bản đề xuất

```csharp
public sealed record PublicPageCacheKey(
    string SiteId,
    int ContentId,
    string Culture,
    string DeliveryMode);

public sealed class CmsPageRenderer
{
    private readonly IMemoryCache _cache;
    private readonly ICmsContentResolver _resolver;

    public CmsPageRenderer(
        IMemoryCache cache,
        ICmsContentResolver resolver)
    {
        _cache = cache;
        _resolver = resolver;
    }

    public async Task<PublicPageViewModel> GetPublicPageAsync(
        string siteId,
        ContentReference contentLink,
        CultureInfo culture,
        CancellationToken cancellationToken)
    {
        var key = new PublicPageCacheKey(
            siteId,
            contentLink.ID,
            culture.Name,
            "published");

        return await _cache.GetOrCreateAsync(key, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(30);

            return await _resolver.GetPublishedPageAsync(
                siteId,
                contentLink,
                culture,
                cancellationToken);
        }) ?? throw new InvalidOperationException("Page not found.");
    }
}
```

Controller nên tách public anonymous rendering khỏi authenticated/preview rendering. Public path mới được phép shared-cache; private/preview path dùng cache policy riêng. Publish flow phải invalidate origin/application content trước hoặc đồng thời với CDN invalidation theo architecture đã chọn.

## Giải thích thiết kế sau khi sửa

- Cache key mô tả rendered output, không chỉ raw content ID.
- Personalized state không nằm trong public cache.
- Preview là delivery path riêng, không phải boolean trang trí.
- Origin cache và CDN có lifecycle độc lập.

## Trade-offs

- Cache key chi tiết hơn làm tăng số entry và có thể giảm hit ratio.
- Event-driven invalidation phức tạp hơn TTL-only nhưng phù hợp publish semantics hơn.
- Tách public/private render paths tăng code nhưng làm security boundary rõ ràng.
- Không nên thêm distributed cache chỉ vì có nhiều instances nếu CMS-native invalidation đã đủ.

## Cách kiểm thử

1. **Integration test:** cùng content ID với `en-US` và `en-GB` không được cross-hit sai model.
2. **Multi-site test:** hai host/site không reuse sai cache entry.
3. **Preview test:** preview không làm thay đổi public result và không shared-cache.
4. **Cross-instance test:** publish rồi route qua nhiều instances; freshness phải đúng design.
5. **Personalization test:** hai authenticated users liên tiếp không nhận private content của nhau.

## Quan sát trong production

- cache hit/miss theo site + culture + delivery mode;
- invalidation count;
- publish-to-fresh latency;
- Akamai cache status;
- origin response version marker;
- authenticated/preview response cache headers;
- p95/p99 origin latency khi cache miss tăng.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào distributed cache thực sự cần thiết thay vì stateless origin + CDN?
2. Nếu page có 90% public content và 10% personalized widget, bạn tách cache boundary thế nào?
3. Nếu CDN purge tạm thời fail sau origin invalidation, bạn xử lý eventual freshness ra sao?

# Code Review Challenge 2 — Vue search hiển thị stale result và tạo request thừa

**Chủ đề:** Vue.js, TypeScript, frontend/backend integration, async race condition, request cancellation, error handling  
**Độ khó:** Senior

## Bối cảnh

Một Vue.js search component gọi ASP.NET Core API `/api/products/search?q=...`. User thường gõ nhanh 5–10 ký tự; API latency dao động 80–900 ms.

Production ghi nhận:

- user gõ `iphone` nhưng đôi khi UI cuối cùng hiển thị result của `iph`;
- request count cao hơn dự kiến;
- loading spinner chớp;
- navigate khỏi page nhưng một số request vẫn tiếp tục;
- API trả 401 nhưng component đôi khi hiển thị `No results`.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

watch(query, async (value) => {
  loading.value = true
  error.value = ''

  setTimeout(async () => {
    try {
      const response = await fetch(
        `/api/products/search?q=${value}`

      const data = await response.json()
      results.value = data.items
    } catch {
      results.value = []
      error.value = 'No results'
    } finally {
      loading.value = false
    }
  }, 300)
})
</script>

<template>
  <div>
    <input v-model="query" placeholder="Search products" />
    <div v-if="loading">Loading...</div>
    <div v-if="error">{{ error }}</div>
    <ul>
      <li v-for="item in results" :key="item.id">
        {{ item.name }}
      </li>
    </ul>
  </div>
</template>
```

## Kết quả code review tham khảo

### High — `setTimeout` không phải debounce

**Vấn đề:** mỗi query change tạo timer mới.  
**Tại sao xảy ra:** timer cũ không được clear.  
**Ảnh hưởng production:** gõ nhiều ký tự tạo nhiều request và tăng race.  
**Cách sửa:** lưu timer handle và `clearTimeout` trước khi schedule request mới.

### High — Out-of-order response overwrite latest state

**Vấn đề:** mọi response đều gán `results.value`.  
**Tại sao xảy ra:** completion order không đảm bảo giống request-start order.  
**Ảnh hưởng production:** request cũ có thể overwrite query mới.  
**Cách sửa:** abort request cũ và/hoặc dùng monotonically increasing request generation để chỉ latest request commit state.

### High — Không cancel request khi query thay đổi hoặc component unmount

**Vấn đề:** `fetch` không dùng `AbortController`.  
**Tại sao xảy ra:** component không model lifecycle của in-flight request.  
**Ảnh hưởng production:** browser tiếp tục network work thừa; stale callback có thể mutate state muộn.  
**Cách sửa:** abort active request khi query mới đến và trong `onBeforeUnmount`.

### High — HTTP 401/500 không được xử lý rõ

**Vấn đề:** code parse body ngay mà không kiểm tra `response.ok`.  
**Tại sao xảy ra:** `fetch` không coi mọi HTTP error là rejected promise.  
**Ảnh hưởng production:** authentication/system failure có thể bị hiển thị như empty search.  
**Cách sửa:** kiểm tra status và model riêng unauthorized, forbidden, server error, empty result.

### Medium — Query không được encode đúng

**Vấn đề:** URL được nối chuỗi trực tiếp.  
**Tại sao xảy ra:** không dùng URL encoding helper.  
**Ảnh hưởng production:** ký tự đặc biệt có thể làm sai query semantics.  
**Cách sửa:** dùng `URLSearchParams`.

### Medium — Loading state không thuộc về latest request

**Vấn đề:** request cũ có thể set `loading=false` khi request mới còn chạy.  
**Tại sao xảy ra:** không có request ownership.  
**Ảnh hưởng production:** spinner chớp hoặc biến mất sớm.  
**Cách sửa:** chỉ latest request generation được finalize loading state.

### Medium — Empty query vẫn tạo request

**Vấn đề:** watcher xử lý mọi string.  
**Tại sao xảy ra:** không trim/minimum-length guard.  
**Ảnh hưởng production:** tạo broad hoặc meaningless search.  
**Cách sửa:** trim input và skip request dưới threshold phù hợp requirement.

### Medium — Error state conflates empty result với technical failure

**Vấn đề:** mọi exception thành `No results`.  
**Tại sao xảy ra:** business state và failure state bị trộn.  
**Ảnh hưởng production:** user/support không biết API down hay thật sự không có dữ liệu.  
**Cách sửa:** model `idle/loading/success/empty/error/unauthorized` hoặc state machine tương đương.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

let timer: number | undefined
let activeController: AbortController | null = null
let generation = 0

watch(query, (rawValue) => {
  window.clearTimeout(timer)
  activeController?.abort()

  const value = rawValue.trim()
  if (value.length < 2) {
    results.value = []
    loading.value = false
    error.value = ''
    return
  }

  timer = window.setTimeout(async () => {
    const current = ++generation
    const controller = new AbortController()
    activeController = controller

    loading.value = true
    error.value = ''

    try {
      const params = new URLSearchParams({ q: value })
      const response = await fetch(
        `/api/products/search?${params.toString()}`,
        { signal: controller.signal }
      )

      if (!response.ok) {
        throw new Error(`HTTP_${response.status}`)
      }

      const data = await response.json() as { items: SearchItem[] }

      if (current === generation) {
        results.value = data.items
      }
    } catch {
      if (!controller.signal.aborted && current === generation) {
        results.value = []
        error.value = 'Search is temporarily unavailable.'
      }
    } finally {
      if (current === generation) {
        loading.value = false
      }
    }
  }, 300)
})

onBeforeUnmount(() => {
  window.clearTimeout(timer)
  activeController?.abort()
})
</script>
```

## Giải thích thiết kế sau khi sửa

- Debounce cũ bị hủy nên chỉ latest stable query tạo request.
- Abort giảm work thừa.
- Generation guard đảm bảo chỉ latest request được commit state.
- HTTP error được xử lý rõ thay vì giả làm empty result.
- URL query được encode đúng.

## Trade-offs

- Debounce giảm request count nhưng thêm perceived latency.
- Abort request không đảm bảo backend luôn ngừng xử lý; server phải propagate cancellation nếu muốn tiết kiệm compute thực sự.
- Generation guard thêm một chút complexity nhưng làm state correctness rõ ràng.
- Minimum query length phải phù hợp search UX và backend query cost.

## Cách kiểm thử

1. **Race test:** `iph` latency 800 ms, `iphone` latency 100 ms; UI cuối phải là `iphone`.
2. **Debounce test:** gõ nhanh nhiều ký tự; request count phải đúng policy.
3. **Cancellation test:** đổi query hoặc unmount; stale request không được mutate state.
4. **HTTP-state test:** 200 empty, 401, 403, 500 và network failure phải được phân biệt hợp lý.
5. **E2E test:** dùng Playwright mô phỏng typing nhanh và network latency khác nhau.

## Quan sát trong production

- request count trên mỗi search session;
- aborted request count;
- p50/p95/p99 search latency;
- 4xx/5xx rate;
- frontend error rate;
- query-length distribution;
- empty-result rate;
- browser network timing;
- backend cancellation telemetry nếu có.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend dùng Elasticsearch và prefix query ngắn rất đắt, frontend và backend nên phối hợp protection thế nào?
2. Nếu product yêu cầu instant-search perceived latency rất thấp, bạn tune debounce ra sao?
3. Nếu nhiều component cùng gọi search API, bạn có centralize request/cache layer không? Khi nào việc đó đáng complexity?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache correctness phụ thuộc vào đầy đủ output identity, không chỉ raw hit ratio.
- Multi-site, multi-language, preview và personalization là các cache boundary khác nhau.
- `IMemoryCache`, CMS cache và Akamai là các layer độc lập; invalidation một layer không tự động lan sang layer khác.
- Shared caching phải đặc biệt cẩn thận với authenticated và preview responses.
- Frontend async race xảy ra khi nhiều request cùng có quyền ghi state nhưng completion order không deterministic.
- Debounce, cancellation và latest-request guard giải quyết các lớp vấn đề khác nhau.
- Empty business result và HTTP/network failure không nên bị trộn thành một trạng thái.

## Mẫu tư duy cần nhớ

1. **Cache key must describe the output, not merely the input ID.**
2. **Separate public shared state from private/personalized state.**
3. **Invalidate every cache layer that can independently serve stale data.**
4. **Only the latest async request should own the latest UI state.**
5. **Model technical failure separately from valid empty business state.**
