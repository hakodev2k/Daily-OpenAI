# Code Review Challenge 1 — Checkout ghi nhận thanh toán hai lần khi gateway timeout

**Chủ đề:** C#/.NET 8, ASP.NET Core, PostgreSQL, payment integration, idempotency, distributed failure  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 50 phút  
**Số vấn đề cần tìm:** khoảng 10

## Bối cảnh

API checkout của một modular monolith nhận yêu cầu thanh toán cho đơn hàng. Gateway hỗ trợ idempotency key, nhưng đôi khi HTTP request timeout dù gateway đã xử lý thành công. Mobile client tự retry khi gặp 5xx. API chạy trên ba instance Azure App Service. Mỗi ngày có khoảng 40.000 lượt checkout; báo cáo tài chính xuất hiện các khoản charge trùng và đơn hàng có trạng thái không nhất quán. Không được thay đổi contract của gateway trong đợt hotfix.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/orders")]
public sealed class CheckoutController(
    ShopDbContext db,
    HttpClient gateway,
    ILogger<CheckoutController> logger) : ControllerBase
{
    [HttpPost("{orderId:guid}/pay")]
    public async Task<IActionResult> Pay(Guid orderId, CancellationToken ct)
    {
        var order = await db.Orders.SingleOrDefaultAsync(x => x.Id == orderId, ct);
        if (order is null) return NotFound();
        if (order.Status == "Paid") return Ok(new { order.Id, order.Status });

        var payload = new
        {
            orderId = order.Id,
            amount = order.Total,
            currency = order.Currency,
            cardToken = Request.Headers["X-Card-Token"].ToString()
        };

        var response = await gateway.PostAsJsonAsync(
            "https://payments.example/charges", payload, ct);

        var body = await response.Content.ReadAsStringAsync(ct);
        logger.LogInformation("Gateway response: {Body}", body);

        if (!response.IsSuccessStatusCode)
            return StatusCode(502, "Payment failed");

        var charge = JsonSerializer.Deserialize<ChargeResult>(
            body, new JsonSerializerOptions(JsonSerializerDefaults.Web))!;

        db.Payments.Add(new Payment
        {
            Id = Guid.NewGuid(),
            OrderId = order.Id,
            GatewayChargeId = charge.Id,
            Amount = order.Total
        });
        order.Status = "Paid";
        await db.SaveChangesAsync(ct);

        return Ok(new { order.Id, order.Status });
    }
}

public sealed record ChargeResult(string Id);
```

## Kết quả code review tham khảo

### [Critical] — Double charge do race condition và retry

**Vấn đề:** Nhiều request cùng đọc `Status != Paid` rồi cùng gửi charge.

**Tại sao xảy ra:** Check-then-act không atomic, không có unique business key, và gateway không nhận idempotency key.

**Ảnh hưởng production:** Khách hàng bị trừ tiền nhiều lần; refund và reconciliation tốn chi phí.

**Cách sửa:** Tạo payment attempt có unique constraint theo business operation, dùng gateway idempotency key cố định cho cùng attempt; kiểm soát ownership của worker và retry an toàn.

### [Critical] — Timeout bị hiểu thành thất bại chắc chắn

**Vấn đề:** API trả lỗi khi chưa biết gateway đã thực hiện charge hay chưa.

**Tại sao xảy ra:** Network timeout không xác định kết quả của remote side effect.

**Ảnh hưởng production:** Retry tạo charge mới; trạng thái DB sai.

**Cách sửa:** Lưu `Unknown/PendingReconciliation`, tra cứu bằng idempotency key hoặc gateway transaction reference, trả trạng thái pending để client polling.

### [High] — Thiếu authorization và xác thực order ownership

**Vấn đề:** Route chỉ nhận `orderId`, không kiểm tra user/tenant được phép thanh toán order.

**Tại sao xảy ra:** Controller không ràng buộc resource authorization.

**Ảnh hưởng production:** Cross-tenant payment attempts và truy cập trạng thái đơn của người khác.

**Cách sửa:** Yêu cầu authentication, tenant scoping và resource-based authorization trước mọi side effect.

### [High] — Dữ liệu giá trị thanh toán có thể stale hoặc bị thay đổi

**Vấn đề:** Tổng tiền lấy từ order chưa khóa và không đảm bảo trạng thái giá/phiên bản tại thời điểm charge.

**Tại sao xảy ra:** Không có immutable checkout snapshot hay concurrency token.

**Ảnh hưởng production:** Số tiền gateway và sổ cái lệch nhau.

**Cách sửa:** Chốt amount/currency vào attempt, kiểm tra state transition và concurrency trong DB.

### [High] — DB commit thất bại sau remote charge

**Vấn đề:** Side effect ngoài DB xảy ra trước `SaveChangesAsync`.

**Tại sao xảy ra:** Không có distributed atomic transaction với gateway.

**Ảnh hưởng production:** Charge thành công nhưng đơn vẫn unpaid.

**Cách sửa:** Persist attempt trước khi gọi gateway; finalize idempotently; reconciliation worker xử lý trạng thái chưa rõ.

### [High] — Thiếu unique constraint cho gateway charge

**Vấn đề:** `Payments` có thể ghi trùng `GatewayChargeId`.

**Tại sao xảy ra:** Không thấy invariant ở database.

**Ảnh hưởng production:** Báo cáo kế toán ghi nhận trùng.

**Cách sửa:** Unique index trên `GatewayChargeId` khi không null; unique constraint theo `PaymentAttemptId` và xử lý conflict.

### [Medium] — Log toàn bộ gateway response

**Vấn đề:** Response có thể chứa dữ liệu nhạy cảm hoặc thông tin vận hành không nên lưu.

**Tại sao xảy ra:** Structured log dùng nguyên body không lọc.

**Ảnh hưởng production:** Rò rỉ dữ liệu, tăng rủi ro compliance.

**Cách sửa:** Log allowlist: attempt ID, gateway status, correlation ID, duration; redaction dữ liệu nhạy cảm.

### [Medium] — Card token lấy trực tiếp từ header và thiếu validation

**Vấn đề:** Header rỗng, sai định dạng hoặc không phù hợp luồng PCI có thể được chuyển tiếp.

**Tại sao xảy ra:** Không có DTO validation, không phân biệt token hóa từ trusted payment provider.

**Ảnh hưởng production:** Payment failure và mở rộng phạm vi xử lý dữ liệu nhạy cảm.

**Cách sửa:** Validate token, chỉ nhận tokenized reference theo integration contract; không log token.

### [Medium] — Thiếu bounded timeout, error mapping và resilience policy

**Vấn đề:** HTTP lỗi transport, gateway 429/503 và lỗi nghiệp vụ bị gộp hoặc phát sinh 500.

**Tại sao xảy ra:** Không có typed client, phân loại transient/permanent và retry contract.

**Ảnh hưởng production:** Client retry không kiểm soát, tăng tải gateway.

**Cách sửa:** Typed `HttpClient`, timeout budget, retry chỉ với stable idempotency key và theo contract gateway.

### [Medium] — Không có reconciliation/telemetry cho payment lifecycle

**Vấn đề:** Không theo dõi pending quá hạn và sai lệch gateway-DB.

**Tại sao xảy ra:** Chỉ log body, không có attempt lifecycle metrics.

**Ảnh hưởng production:** Lỗi âm thầm kéo dài.

**Cách sửa:** Trace attempt, metrics pending age, unknown outcome, reconciliation lag, duplicate suppression và alert.

## Phiên bản đề xuất

Thiết kế dưới đây là **pseudocode C# có chủ đích**, thể hiện ranh giới giao dịch; các helper là application services cần hiện thực bằng transaction, unique constraint và gateway contract. Không giả định gateway hỗ trợ API tra cứu nếu chưa xác minh.

```csharp
public async Task<PaymentView> PayAsync(
    Guid orderId, ClaimsPrincipal user, CancellationToken ct)
{
    var order = await orders.GetAuthorizedOrderAsync(orderId, user, ct);
    if (order.Status == OrderStatus.Paid)
        return PaymentView.Paid(orderId);

    // Atomic DB operation: insert-or-get attempt by (OrderId, CheckoutVersion).
    // Persist immutable Amount, Currency and stable GatewayKey.
    var attempt = await attempts.GetOrCreateAsync(
        order.Id, order.CheckoutVersion, order.Total, order.Currency, ct);

    if (attempt.Status == AttemptStatus.Succeeded)
        return PaymentView.Paid(orderId);

    // Acquire a lease with fencing/version check. Only the lease owner
    // may dispatch; concurrent callers receive Pending.
    var lease = await attempts.TryAcquireLeaseAsync(attempt.Id, ct);
    if (lease is null)
        return PaymentView.Pending(attempt.Id);

    try
    {
        var result = await gateway.ChargeAsync(
            attempt.Amount, attempt.Currency,
            attempt.GatewayKey, ct);

        if (result.IsDefinitiveSuccess)
            await attempts.MarkSucceededAndPayOrderAsync(
                attempt.Id, lease.Version, result.ChargeId, ct);
        else if (result.IsDefinitiveFailure)
            await attempts.MarkFailedAsync(attempt.Id, lease.Version, ct);
        else
            await attempts.MarkUnknownAsync(attempt.Id, lease.Version, ct);
    }
    catch (Exception ex) when (IsAmbiguousTransportFailure(ex))
    {
        await attempts.MarkUnknownBestEffortAsync(
            attempt.Id, lease.Version, CancellationToken.None);
    }

    return await attempts.GetPaymentViewAsync(attempt.Id, ct);
}
```

**Điều kiện triển khai:** `GetOrCreateAsync` phải dựa trên DB unique constraint; `TryAcquireLeaseAsync` là compare-and-swap có expiry và fencing token; việc giữ lease không đảm bảo exactly-once remote call, nên idempotency ở gateway vẫn bắt buộc. `CancellationToken.None` trong best-effort persistence cần timeout nội bộ ngắn, không chạy vô hạn. Nếu gateway không hỗ trợ truy vấn, dùng reconciliation theo settlement reports và quy trình xử lý thủ công; không tự động charge lại khi outcome chưa rõ.

## Giải thích thiết kế sau khi sửa

Payment attempt là nguồn dữ liệu về intent, immutable amount và gateway key. DB transaction bảo vệ local invariant; gateway idempotency bảo vệ remote side effect; reconciliation khôi phục trạng thái sau partial failure. API trả `202 Accepted` với attempt ID cho trạng thái chưa xác định, không khẳng định thất bại. Authorization nằm trước attempt creation.

## Trade-offs

Persist attempt và reconciliation làm tăng số trạng thái, storage và độ phức tạp vận hành. Lease giảm request đồng thời nhưng có thể hết hạn khi gateway xử lý chậm. Không nên thêm Service Bus chỉ để giải quyết một flow ít tải nếu synchronous + reconciliation đáp ứng SLO; queue phù hợp khi cần durable dispatch và chịu spike. Gateway idempotency retention cần được xác minh trước khi chọn retry horizon.

## Cách kiểm thử

1. **Concurrency integration:** 100 request cùng order; xác nhận một business attempt và tối đa một charge thực tế theo gateway mock idempotent.
2. **Failure-path:** Gateway charge thành công rồi timeout; retry cùng key, không double charge.
3. **Database fault injection:** Gateway thành công, DB finalize lỗi; reconciliation cuối cùng chuyển sang Paid đúng một lần.
4. **Security:** User khác tenant không tạo attempt hoặc xem payment status.
5. **Load test:** Đo p95, gateway call amplification và số attempt Unknown khi gateway chậm.

## Quan sát trong production

Application Insights trace theo `orderId` (định danh nội bộ phù hợp policy), `attemptId`, `correlationId`; không log card token. Dashboard cho `payment_attempts_unknown`, `reconciliation_age_seconds`, `duplicate_request_suppressed`, `gateway_timeout_rate`, `gateway_charge_to_db_mismatch`. Alert theo tỷ lệ Unknown và tuổi pending; đối soát với gateway settlement độc lập.

# Code Review Challenge 2 — PostgreSQL báo cáo phân trang chậm và sai thứ tự khi dữ liệu thay đổi

## Bối cảnh

Trang quản trị hiển thị lịch sử giao dịch cho từng tenant. Bảng `transactions` có 28 triệu dòng; mỗi tenant có 10.000 đến 3 triệu dòng. Bộ lọc theo ngày, trạng thái và tìm kiếm email. ## Đoạn code cần review

```sql
-- Inputs: :tenant_id, :from_date, :to_date, :status,
-- :email, :page, :page_size
SELECT
    t.id,
    t.tenant_id,
    t.created_at,
    t.status,
    t.amount,
    u.email
FROM transactions t
JOIN users u ON u.id = t.user_id
WHERE
    (:tenant_id IS NULL OR t.tenant_id = :tenant_id)
    AND DATE(t.created_at) >= :from_date
    AND DATE(t.created_at) <= :to_date
    AND (:status IS NULL OR LOWER(t.status) = LOWER(:status))
    AND (:email IS NULL OR u.email ILIKE '%' || :email || '%')
ORDER BY t.created_at DESC
LIMIT :page_size
OFFSET (:page - 1) * :page_size;
```

## Kết quả code review tham khảo

### [Critical] — Tenant filter có thể bị bỏ qua

**Vấn đề:** `:tenant_id IS NULL` trả dữ liệu tất cả tenant.

**Tại sao xảy ra:** Query tin giá trị nullable từ request, không gắn tenant với authenticated principal.

**Ảnh hưởng production:** Cross-tenant data exposure, đặc biệt trong export.

**Cách sửa:** Resolve tenant từ authorization context, bắt buộc `t.tenant_id = @tenantId`; kiểm tra `users` cũng thuộc cùng tenant và cân nhắc PostgreSQL RLS defense-in-depth.

### [High] — Public HTTP caching trên dữ liệu riêng tư

**Vấn đề:** `Cache-Control: public` cho transaction response.

**Tại sao xảy ra:** Shared caches có thể lưu response theo URL và policy.

**Ảnh hưởng production:** Rò rỉ dữ liệu giữa người dùng/tenant tùy cấu hình cache.

**Cách sửa:** `Cache-Control: private, no-store` cho endpoint nhạy cảm; kiểm tra CDN/proxy hiện hành và invalidation.

### [High] — OFFSET gây thiếu/trùng bản ghi giữa các request

**Vấn đề:** Pagination theo vị trí không ổn định khi dữ liệu mới chèn.

**Tại sao xảy ra:** Mỗi HTTP request thấy snapshot khác; OFFSET dịch theo số dòng mới.

**Ảnh hưởng production:** Báo cáo thiếu hoặc lặp giao dịch.

**Cách sửa:** Keyset pagination với `(created_at, id)` và cursor; nếu cần snapshot hoàn toàn ổn định cho export, tạo job snapshot/watermark và xác định semantics riêng.

### [High] — ORDER BY không có tie-breaker

**Vấn đề:** Nhiều giao dịch cùng `created_at` không có thứ tự xác định.

**Tại sao xảy ra:** Sort key không unique.

**Ảnh hưởng production:** Kết quả nhảy vị trí ngay cả khi không có insert.

**Cách sửa:** `ORDER BY t.created_at DESC, t.id DESC`, index tương ứng.

### [Medium] — DATE() làm range filter kém sargable

**Vấn đề:** Cast `created_at` trong predicate.

**Tại sao xảy ra:** Expression trên cột cản trở sử dụng range index thông thường một cách trực tiếp.

**Ảnh hưởng production:** Quét nhiều row, tăng CPU và I/O.

**Cách sửa:** Dùng `created_at >= @fromUtc AND created_at < @toExclusiveUtc` sau khi quy đổi timezone đúng business rule.

### [Medium] — Deep OFFSET tốn tài nguyên

**Vấn đề:** Database phải xử lý các row trước trang yêu cầu.

**Tại sao xảy ra:** OFFSET không nhảy trực tiếp tới logical row thứ N.

**Ảnh hưởng production:** p95 tăng theo page number.

**Cách sửa:** Keyset seek; nếu UI bắt buộc random page, cần giới hạn page depth hoặc thiết kế khác và đo trade-off.

### [Medium] — Optional predicates và tìm kiếm substring khó tối ưu

**Vấn đề:** OR nullable filters và `ILIKE '%...%'` có thể dẫn đến plan kém.

**Tại sao xảy ra:** Selectivity biến đổi mạnh, B-tree thường không hiệu quả với leading wildcard.

**Ảnh hưởng production:** Sequential scan hoặc join cost cao.

**Cách sửa:** Build parameterized query theo filter thực tế; cân nhắc `pg_trgm` GIN cho email khi có bằng chứng query workload phù hợp, hoặc exact/prefix search theo requirement.

### [Medium] — Join thiếu tenant invariant

**Vấn đề:** `JOIN users u ON u.id = t.user_id` không kiểm tra tenant của user.

**Tại sao xảy ra:** Quan hệ có thể chứa dữ liệu sai hoặc ID không globally scoped theo schema.

**Ảnh hưởng production:** Sai dữ liệu email, tiềm ẩn rò rỉ khi integrity không được bảo đảm.

**Cách sửa:** `u.tenant_id = t.tenant_id` và composite FK/index khi mô hình dữ liệu yêu cầu.

WHERE t.tenant_id = @tenantId
  AND t.created_at >= @fromUtc
  AND t.created_at < @toExclusiveUtc
  AND (@status IS NULL OR t.status = @status)
  AND (@lastCreatedAt IS NULL
       OR (t.created_at, t.id) < (@lastCreatedAt, @lastId))
ORDER BY t.created_at DESC, t.id DESC
LIMIT @pageSize;
```

    ix_transactions_tenant_created_id

[Authorize]
[HttpGet("transactions")]
public async Task<IActionResult> Get(
    [FromQuery] ReportFilter filter, CancellationToken ct)
{
    var tenantId = tenantContext.RequireAuthorizedTenant(User);
    var pageSize = Math.Clamp(filter.PageSize, 1, 100);
    var cursor = cursorCodec.DecodeAndValidate(
        filter.Cursor, tenantId, filter.FromUtc,
        filter.ToExclusiveUtc, filter.Status);

    var rows = await reports.FetchPageAsync(
        tenantId, filter, cursor, pageSize, ct);

    Response.Headers.CacheControl = "private, no-store";
    return Ok(new
    {
        items = rows,
        nextCursor = cursorCodec.EncodeNext(rows, tenantId, filter)
    });
}
```

**Lưu ý:** `cursorCodec`, `tenantContext`, `reports` là application abstractions, không phải .NET built-in API. Nếu `created_at` có thể cập nhật, keyset không tự bảo đảm snapshot tuyệt đối; với export cần cơ chế nhất quán riêng. Index phải được kiểm chứng bằng `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu đại diện. Email filter cần query riêng và đánh giá selectivity; không lặng lẽ bỏ requirement tìm kiếm.

## Giải thích thiết kế sau khi sửa

Tenant scope lấy từ authenticated identity, không từ nullable query parameter. Keyset dựa trên total order, giảm công việc bỏ qua row và hạn chế drift do insert mới trước cursor. Half-open timestamp range rõ timezone và tương thích index. Index tạo `CONCURRENTLY` để giảm blocking write, nhưng vẫn cần kiểm tra thời gian build, disk và operational impact.

## Trade-offs

Keyset không hỗ trợ nhảy trực tiếp tới page 500; cursor phải được version hóa, bảo vệ khỏi sửa đổi và gắn filter. Index mới tăng write amplification và storage. `pg_trgm` tăng overhead index, chỉ nên thêm nếu workload substring search đủ lớn. Với báo cáo export yêu cầu snapshot point-in-time, cần thiết kế snapshot hoặc bounded watermark thay vì coi pagination là transaction snapshot.

## Cách kiểm thử

1. **Security integration:** Tenant A thử bỏ tenant ID, sửa cursor và truy vấn transaction tenant B; không nhận dữ liệu.
2. **Pagination concurrency:** Insert nhiều row cùng timestamp giữa hai lần fetch; không duplicate/missing trong tập ổn định theo cursor semantics.
3. **Database plan:** `EXPLAIN (ANALYZE, BUFFERS)` với tenant nhỏ/lớn, status phổ biến/hiếm; so sánh rows scanned và buffer reads.
4. **Load:** Đo p50/p95/p99 trên trang đầu và trang sâu trước/sau thay đổi.
5. **Time-boundary:** Kiểm tra DST/timezone conversion, inclusive/exclusive end và timestamp trùng nhau.

## Quan sát trong production

Application Insights: duration, tenant-safe correlation ID, query fingerprint, page size, cursor presence. PostgreSQL: `pg_stat_statements` (nếu bật), `EXPLAIN` sampling an toàn, buffer hits/reads, temp files, lock waits. Alert khi p95 tăng, row scan/returned ratio bất thường, và bất kỳ security audit event cross-tenant nào. Không log email nguyên văn hoặc SQL parameter nhạy cảm.

## Kiến thức trọng tâm

Payment correctness cần idempotency xuyên qua retry và reconciliation sau partial failure; DB transaction không bảo đảm atomicity với gateway.
