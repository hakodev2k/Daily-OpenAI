# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core query pipeline, LINQ deferred execution, Change Tracker, SQL diagnosis, performance

## Bối cảnh

Một ASP.NET Core API lấy danh sách nhân viên và trạng thái mailbox. Sau một thay đổi refactor, endpoint vẫn trả đúng dữ liệu nhưng số SQL command tăng mạnh, latency P95 tăng từ khoảng 180 ms lên hơn 1 giây khi tenant có vài nghìn nhân viên. Code tạo một `IQueryable<Employee>`, áp dụng filter theo nhiều bước, gọi `CountAsync()`, sau đó enumerate để map DTO; trong mapper lại truy cập navigation property. DbContext dùng scoped lifetime. Một developer nói: “`IQueryable` đã chứa dữ liệu rồi nên gọi lại không query database; EF Core tracking cũng giúp cache kết quả.”

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc tạo `IQueryable` đến lúc materialize; vì sao endpoint có thể phát nhiều SQL command; misconception nào đang tồn tại; tracking ảnh hưởng thế nào; production risk là gì; và bạn sẽ chứng minh từng giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Navigation properties có được eager-load, explicit-load hay lazy-loading không?
- Query có `AsNoTracking`, projection hay `Include` không?
- `CountAsync()` và danh sách có cần cùng snapshot dữ liệu không?
- SQL command count tăng ở tất cả tenant hay chỉ tenant lớn?
- Mapper có gọi query/database-dependent code hay chỉ xử lý object đã materialize?

## Gợi ý tư duy

**Gợi ý 1:** Phân biệt “xây expression tree” và “thực thi query”.  
**Gợi ý 2:** Tìm mọi terminal operation/materialization và mọi đường dẫn có thể kích hoạt query phụ.  
**Gợi ý 3:** Quan sát generated SQL + command spans; sau đó cân nhắc projection server-side thay vì load entity graph rồi map.

## Cấu trúc trả lời đề xuất

1. Làm rõ query shape và loading strategy.
2. Mô tả `IQueryable`/expression tree và thời điểm execution.
3. Liệt kê các điểm có thể phát SQL.
4. Phân biệt tracking/identity resolution với result caching.
5. Đưa giả thuyết và bằng chứng cần thu thập.
6. Đề xuất query shape mới.
7. Phân tích consistency/trade-off của count + page.
8. Kiểm thử và quan sát production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chưa phải tập dữ liệu đã tải; terminal operation như `CountAsync`, `ToListAsync`, `FirstAsync` kích hoạt execution riêng.
- Change Tracker không biến một LINQ query lặp lại thành query-result cache.
- Navigation loading không kiểm soát có thể tạo N+1.
- Dùng generated SQL, EF Core command logging/tracing và database statistics để xác minh.

### Điểm cộng

- Projection bằng `Select` chỉ lấy cột cần thiết; `AsNoTracking` cho read-only query khi phù hợp.
- Không dùng `Include` như phản xạ mặc định; kiểm tra cartesian explosion/query shape.
- Cancellation token và pagination phải đi xuyên query.

### Nâng cao

- Nhận ra `Count` và page là hai query độc lập, dữ liệu có thể thay đổi giữa hai lần nếu yêu cầu consistency nghiêm ngặt.
- Phân biệt tracking, identity resolution và caching.
- Benchmark bằng dữ liệu có cardinality gần production thay vì chỉ stopwatch local.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, không cần snapshot transaction tuyệt đối và navigation đang bị truy cập trong mapper.

`IQueryable` giữ representation của query. Mỗi terminal operation có thể dịch expression hiện tại thành SQL và thực thi. `CountAsync()` không materialize danh sách cho lần `ToListAsync()` tiếp theo. Tracking giữ entity instance/state trong DbContext để change detection và identity resolution; không phải general query-result cache. Nếu lazy loading được bật hoặc mapper explicit-load navigation theo từng entity, số round trip có thể tăng theo số record.

Tôi sẽ bật/thu thập EF Core command telemetry có correlation với request, xem generated SQL bằng `ToQueryString()` trong diagnostic/test, kiểm tra số command/request, query duration, rows read và execution plan cho query nóng. Sau đó chuyển read model sang projection server-side, ví dụ `Select(e => new EmployeeDto { ... })`, dùng `AsNoTracking()` nếu không update entity, giữ pagination ở database và chỉ load field cần thiết.

Nếu total count không thật sự cần trên mọi request, có thể bỏ hoặc tách nó. Nếu cần count + page nhưng business yêu cầu cùng snapshot, phải thảo luận isolation/transaction và chi phí lock/versioning thay vì giả định hai query luôn nhất quán.

Failure cases cần kiểm tra gồm cancellation, tenant lớn, navigation thiếu, concurrent update và database timeout. Security vẫn phải bảo đảm tenant filter/authorization được áp dụng trong query, không filter sau khi materialize.

Recommendation thay đổi nếu endpoint cần update tracked entities trong cùng unit of work, hoặc consistency requirement bắt buộc snapshot mạnh.

## Mẫu trả lời trong phỏng vấn

“Trước hết tôi sẽ xác nhận loading strategy và chính xác có bao nhiêu terminal operation. `IQueryable` chủ yếu mô tả query; nó chưa chứa result. Vì vậy `CountAsync()` là một database operation và `ToListAsync()` sau đó thường là operation khác. Tracking không phải query cache; nó theo dõi entity và có thể identity-resolve entity đã được track, nhưng không có nghĩa EF bỏ qua việc chạy LINQ query tiếp theo. Nếu mapper chạm navigation có lazy/explicit loading, tôi đặc biệt nghi N+1.

Tôi sẽ không sửa bằng cách thêm `Include` ngay. Tôi sẽ đo command count/request, generated SQL, duration, rows và execution plan. Với endpoint read-only, hướng mặc định của tôi là projection trực tiếp sang DTO, `AsNoTracking`, pagination tại DB và chỉ lấy field cần thiết. Nếu total count không bắt buộc, tôi cân nhắc loại bỏ vì nó là query riêng. Nếu count và page phải nhất quán tuyệt đối, tôi sẽ làm rõ isolation requirement vì transaction mạnh hơn có trade-off. Cuối cùng tôi sẽ regression-test SQL command count và load-test với tenant lớn để chứng minh fix thay vì chỉ thấy local nhanh hơn.”

## Câu hỏi đào sâu

1. `AsNoTrackingWithIdentityResolution()` khác gì `AsNoTracking()` trong trường hợp result lặp entity?
2. Nếu projection vẫn chậm, bạn điều tra database/index/query plan theo thứ tự nào?
3. Nếu team đề xuất cache toàn bộ employee list trong Redis để né query, bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nói `IQueryable` đã query database ngay khi khai báo.
- Cho rằng Change Tracker là result cache.
- Chữa N+1 bằng `Include` mọi navigation mà không xem query shape.
- Chỉ đo tổng latency, không đo SQL command count/rows/plan.
- Bỏ qua tenant isolation và consistency của count/page.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **1.5**
- Communication: đánh giá xuyên suốt; câu trả lời 8+ phải có cấu trúc rõ, phân biệt fact/hypothesis và nêu cách verify.

# Câu 2 — Incident: Hangfire job gửi thông báo trùng sau deployment

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, concurrency, database consistency, observability

## Bối cảnh

Một hệ thống .NET chạy nhiều instance. Sau deployment, một số khách hàng nhận email/thông báo hai lần. Dashboard cho thấy job có retry và có thời điểm worker bị restart. Business yêu cầu giảm duplicate ngay nhưng không được làm mất notification hợp lệ. Chưa rõ duplicate được enqueue hai lần, execute hai lần hay external provider nhận request hai lần.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ impact assessment đến mitigation, evidence, hypotheses, root cause, short-term fix, long-term prevention và monitoring như thế nào mà không giả định trước chỉ có một nguyên nhân?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate có cùng business event/idempotency key không?
- Job được enqueue từ request, recurring scheduler hay database event?
- Retry policy và timeout hiện tại là gì?
- Provider có hỗ trợ idempotency/deduplication key không?
- Transaction nào tạo business state và transaction nào enqueue job?

## Gợi ý tư duy

**Gợi ý 1:** Tách “delivery semantics” khỏi “business effect”.  
**Gợi ý 2:** Theo dấu một notification qua event → enqueue → execution → provider call.  
**Gợi ý 3:** Thiết kế consumer/job idempotent; nếu DB state và enqueue cần gắn kết, cân nhắc transactional outbox.

## Cấu trúc trả lời đề xuất

1. Định lượng impact và khoanh vùng.
2. Mitigate mà không phá delivery.
3. Correlate evidence bằng business ID/job ID/provider ID.
4. Xây nhiều hypotheses.
5. Reproduce/falsify từng hypothesis.
6. Áp dụng idempotency ở business boundary.
7. Cải thiện enqueue consistency/outbox nếu cần.
8. Monitor duplicate rate, retries, failures và delivery latency.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi retry là bug tự thân; background processing phải chịu được re-execution.
- Có stable idempotency key theo business operation.
- Phân biệt duplicate enqueue, duplicate execution và ambiguous external call outcome.
- Không đánh dấu “sent” trước khi hiểu failure semantics.

### Điểm cộng

- Unique constraint/atomic claim trong database thay vì check-then-act trong memory.
- Outbox để giảm dual-write gap giữa business transaction và enqueue/publish.
- Correlation ID xuyên job và external provider.

### Nâng cao

- Thảo luận provider timeout sau khi provider đã nhận request: retry có thể duplicate nếu không có provider-side idempotency.
- Reconciliation process cho trạng thái “unknown”.
- Deployment/restart là trigger làm lộ thiết kế thiếu idempotency chứ chưa chắc là root cause.

## Hướng giải quyết tham khảo

Đầu tiên xác định phạm vi: loại notification, tenant, version, thời điểm, duplicate rate và user impact. Mitigation có thể giảm concurrency/retry cho luồng bị ảnh hưởng hoặc tạm chặn loại event cụ thể nếu business chấp nhận, nhưng không tắt toàn bộ retry một cách mù quáng.

Tôi cần một timeline có `BusinessEventId`, Hangfire JobId, attempt, worker, deployment version và provider request/message ID. Các hypothesis gồm enqueue hai lần; job được execute lại sau worker failure; retry sau timeout dù provider đã xử lý; recurring schedule overlap; hoặc check-then-send race giữa worker.

Long-term, notification operation phải idempotent theo business key. Database nên enforce uniqueness/atomic state transition. Nếu việc cập nhật domain state và tạo công việc là dual-write, transactional outbox là lựa chọn mạnh: cùng transaction lưu domain change + outbox record, worker riêng dispatch. Tuy nhiên outbox vẫn cần idempotent consumer vì dispatcher có thể retry.

Với external provider, nếu họ hỗ trợ idempotency key thì truyền stable key; nếu không, giữ delivery ledger và thiết kế reconciliation cho trạng thái ambiguous. Không hứa “exactly once” end-to-end nếu các boundary không hỗ trợ nó.

Tests gồm concurrent execution cùng key, crash trước/sau provider call, retry sau timeout, deployment restart và replay outbox. Metrics: duplicate prevented, attempts/job, retry rate, outbox age, provider error/timeout và end-to-end delivery latency.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi đây là incident về business side effect chứ không chỉ Hangfire. Trước tiên tôi định lượng duplicate và giảm blast radius. Sau đó tôi trace một notification bằng business event ID qua enqueue, từng attempt và provider request để biết duplicate sinh ở đâu. Tôi giữ nhiều giả thuyết: enqueue hai lần, retry sau crash, overlap scheduler hoặc provider đã nhận request nhưng client timeout.

Về thiết kế, tôi giả định job có thể chạy lại. Tôi tạo stable idempotency key cho business notification và enforce bằng database/atomic transition, không dùng `if (!sent) send` đơn giản vì có race. Nếu domain update và enqueue đang là hai write độc lập, tôi cân nhắc transactional outbox. Outbox không loại bỏ retry, nên consumer vẫn idempotent. Nếu provider hỗ trợ idempotency key, tôi truyền cùng key qua boundary; nếu không, cần ledger và reconciliation cho trạng thái không chắc chắn.

Tôi verify bằng concurrency/failure tests, đặc biệt crash ở các điểm trước và sau external call. Production sẽ có metrics cho duplicate prevented, retries, provider timeout và outbox lag. Mục tiêu là retry an toàn, không phải cố ép worker chỉ chạy đúng một lần.”

## Câu hỏi đào sâu

1. Unique constraint nên đặt trên những field nào nếu một event có thể gửi qua nhiều channel?
2. Outbox giải quyết vấn đề gì và không giải quyết vấn đề gì?
3. Nếu provider không hỗ trợ idempotency và timeout xảy ra sau khi request đã tới provider, bạn xử lý trạng thái ambiguous thế nào?

## Lỗi trả lời thường gặp

- Chỉ thêm distributed lock rồi tuyên bố hết duplicate.
- Tắt retry để “fix”.
- Check trạng thái rồi send mà không có atomicity.
- Gọi outbox là exactly-once delivery.
- Không phân biệt job execution với external side effect.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repository và tạo review

**Loại câu hỏi:** AI Engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool security, structured output, evaluation, human approval, auditability

## Bối cảnh

Team muốn xây một AI agent review pull request cho repository .NET. Agent có thể đọc diff, mở file liên quan, đọc coding rules và chạy một số kiểm tra. Team muốn giảm thời gian review nhưng không muốn agent tự ý sửa production code hoặc làm lộ secret. Kết quả phải đủ đáng tin để developer dùng hằng ngày. Chưa quyết định agent được comment trực tiếp lên PR hay chỉ tạo draft review.

## Câu hỏi chính

Hãy thiết kế workflow cho agent này: vì sao cần AI, phần nào phải deterministic, context nào được cung cấp, tool/permission nào được phép, cách validate output và phát hiện hallucination, cách đánh giá quality, fallback/human approval, audit và monitoring. Bạn sẽ chọn boundary an toàn nào cho MVP?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ review code hay còn security/performance/architecture?
- Repository có secret/config nhạy cảm hoặc code của khách hàng không?
- False positive và false negative loại nào tốn kém hơn?
- Agent được phép chạy test/build hay chỉ đọc artifact có sẵn?
- Ai chịu trách nhiệm cuối cùng khi review được publish?

## Gợi ý tư duy

**Gợi ý 1:** Đừng bắt LLM làm việc mà compiler, analyzer hoặc policy engine làm chắc chắn hơn.  
**Gợi ý 2:** Context và tool access đều là trust boundary.  
**Gợi ý 3:** MVP nên read-mostly, evidence-backed, structured và có human approval trước write action.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và failure cost.
2. Chia deterministic pipeline và model reasoning.
3. Thiết kế minimal context retrieval.
4. Áp dụng least privilege cho tools.
5. Yêu cầu structured finding + evidence.
6. Validate finding bằng deterministic checks khi có thể.
7. Human approval cho side effect.
8. Offline/online evaluation, audit và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho semantic reasoning/trade-offs, không thay compiler/tests/static analyzer.
- Không cấp write permission nếu MVP chỉ cần review.
- Mỗi finding phải gắn file/line/evidence và confidence/category.
- Output schema được validate trước khi hiển thị/publish.
- Human vẫn là decision maker cho merge và action có side effect.

### Điểm cộng

- Context budget theo changed files + dependency neighborhood thay vì gửi cả repo.
- Treat repository text/tool output as untrusted data để giảm indirect prompt injection.
- Redaction/secret scanning trước khi gửi context ra model boundary phù hợp.
- Eval dataset từ historical PRs + seeded defects.

### Nâng cao

- Permission broker tách reasoning khỏi execution.
- Audit log lưu model/config/prompt version, tool calls, evidence và reviewer disposition.
- Theo dõi precision/acceptance theo category thay vì một “AI accuracy” chung chung.

## Hướng giải quyết tham khảo

**Assumption:** MVP chỉ hỗ trợ reviewer, không tự merge/sửa code.

AI có giá trị ở việc reasoning trên intent, cross-file semantics và trade-off mà rule-based analyzer khó bao phủ. Compiler, unit tests, formatters, secret scanners, dependency/security scanners và schema validation vẫn deterministic.

Pipeline: ingest PR metadata/diff → deterministic checks → context selector lấy changed files, symbol/dependency liên quan và repository rules → model tạo structured findings → validator kiểm tra schema, file/line tồn tại, evidence có trong retrieved context → deduplicate/rank → human review → publish.

Tool permissions cho MVP là read repository, đọc approved CI artifacts và có thể request deterministic checks trong sandbox. Không cấp shell/network tùy ý, secret access, merge, push hoặc production credential. Nội dung repository và tool result phải được coi là untrusted; instruction trong source code không được phép thay system/tool policy.

Finding nên có `category`, `severity`, `file`, `line/range`, `claim`, `evidence`, `recommendation`, `confidence`. Claim về API/runtime có thể cần documentation/evidence retrieval; nếu không đủ bằng chứng thì agent phải downgrade confidence hoặc abstain.

Evaluation: bộ PR lịch sử được human-label, seeded bugs và regression set. Đo precision/recall theo category, false-positive rate, reviewer acceptance, escaped defects, latency và cost/PR. Online rollout shadow mode trước, rồi draft review; chỉ sau khi có evidence mới cân nhắc comment tự động cho nhóm finding có precision cao.

Fallback: model/tool timeout → trả deterministic checks hoặc “review incomplete”, không giả vờ complete. Audit log lưu model/config version, context references, tool calls, validation result và human disposition. Recommendation thay đổi nếu repository cực nhạy cảm: có thể cần model deployment/data boundary khác hoặc không gửi source ra external model.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng một agent có quyền sửa code. Với MVP, AI chỉ nên bổ sung semantic review cho những việc compiler, tests và static analyzers chưa làm tốt. Pipeline của tôi chạy deterministic checks trước, sau đó chọn context tối thiểu quanh diff và symbol liên quan. Model trả structured findings có file, line, claim, evidence, severity và confidence. Một validator kiểm tra schema và bảo đảm evidence thực sự tồn tại trong context trước khi finding được đưa cho người review.

Về security, repository content là untrusted input vì comment hoặc source text có thể chứa instruction độc hại. Tool policy nằm ngoài model: read-only repo, approved CI artifacts, sandboxed checks; không push, merge, đọc secret hay có arbitrary network. Với side effect như publish comment, MVP dùng human approval.

Tôi đánh giá bằng historical PRs và seeded defects, đo precision/recall theo từng category, false positives, reviewer acceptance, latency và cost. Rollout từ shadow mode sang draft review. Nếu model timeout hoặc thiếu evidence, hệ thống abstain hoặc chỉ trả deterministic results. Tôi cũng lưu model/config version, context, tool calls và reviewer disposition để audit và regression-test khi prompt/model thay đổi.”

## Câu hỏi đào sâu

1. Bạn chống indirect prompt injection từ README/source code mà không chỉ dựa vào prompt “ignore malicious instructions” như thế nào?
2. Nếu agent có precision cao nhưng recall thấp, bạn có cho phép auto-comment không? Vì sao?
3. Nếu developer muốn agent tự chạy shell command để kiểm chứng finding, permission model của bạn thay đổi thế nào?

## Lỗi trả lời thường gặp

- “Gửi toàn repo cho LLM rồi bảo nó review.”
- Cho model quyền write/execute rộng chỉ để giảm một bước thao tác.
- Không yêu cầu evidence cho finding.
- Dùng reviewer thumbs-up làm metric duy nhất.
- Không có abstention/fallback khi thiếu context hoặc tool failure.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` mô tả query; materialization/terminal operations mới là các execution boundary quan trọng cần quan sát.
- EF Core tracking không phải general-purpose query result cache; query shape và navigation loading quyết định rất lớn đến số round trip và dữ liệu được tải.
- Background job/retry phải được thiết kế cùng idempotency; distributed execution không nên dựa trên giả định “job chỉ chạy một lần”.
- AI agent cần tách model reasoning khỏi deterministic validation và permission enforcement.
- Evidence, observability và failure recovery là một phần của thiết kế, không phải phần bổ sung sau cùng.

## Mẫu tư duy cần nhớ

1. **Clarify execution boundaries before optimizing.**
2. **Measure commands, rows and traces before blaming the ORM.**
3. **Design retries together with idempotency.**
4. **Treat external side effects as failure/ambiguity boundaries.**
5. **Let AI reason; let deterministic controls validate and authorize.**
