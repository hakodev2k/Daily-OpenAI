# Code Review Challenge 1 — Upload tài liệu: tenant isolation và Blob Storage

**Chủ đề:** ASP.NET Core authorization, Azure Blob Storage, upload security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một enterprise portal chạy ASP.NET Core 8 trên Azure App Service, dùng Microsoft Entra ID để đăng nhập. API cho phép nhân viên tải hợp đồng PDF vào Azure Blob Storage. Có nhiều tổ chức (tenant), mỗi tổ chức có hàng nghìn người dùng; file được mở lại bằng một API download riêng. Đợt kiểm thử bảo mật phát hiện người dùng có thể truy cập tài liệu không thuộc tổ chức của mình. Một số lần upload thất bại khiến blob rác tồn tại. Product yêu cầu không lưu toàn bộ file vào RAM và phải giới hạn PDF tối đa 20 MiB. Chưa rõ có yêu cầu quét malware, retention hoặc public sharing hay không.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
[Authorize]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost("{tenantId}/upload")]
    [RequestSizeLimit(100_000_000)]
    public async Task<IActionResult> Upload(
        string tenantId, IFormFile file)
    {
        if (!file.FileName.EndsWith(".pdf"))
            return BadRequest("Only PDF");

        var blobName = tenantId + "/" + file.FileName;
        var blob = _container.GetBlobClient(blobName);

        using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        buffer.Position = 0;

        await blob.UploadAsync(buffer, overwrite: true);

        var record = new DocumentRecord
        {
            TenantId = tenantId,
            FileName = file.FileName,
            BlobName = blobName,
            UploadedBy = User.Identity!.Name!
        };
        _db.Documents.Add(record);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} for {TenantId} by {User}",
            file.FileName, tenantId, User.Identity.Name);

        return Ok(new { record.Id, record.BlobName });
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> Download(Guid id)
    {
        var doc = await _db.Documents.FindAsync(id);
        if (doc == null) return NotFound();

        var blob = _container.GetBlobClient(doc.BlobName);
        var stream = await blob.OpenReadAsync();
        return File(stream, "application/pdf", doc.FileName);
    }
}
```

## Kết quả code review tham khảo

### Critical — Broken object-level authorization ở download

**Vấn đề:** Chỉ có `[Authorize]`, nhưng `FindAsync(id)` không lọc tenant hoặc kiểm tra quyền tài liệu.  
**Tại sao xảy ra:** Authentication chứng minh danh tính, không chứng minh quyền truy cập một object.  
**Ảnh hưởng production:** Lộ hợp đồng xuyên tenant nếu biết/đoán/thu thập được ID.  
**Cách sửa:** Lấy tenant được phép từ trusted identity/membership service; query theo cả `Id` và `TenantId`; kiểm tra policy theo quyền tài liệu trước khi stream. Không tin route tenant.

### Critical — Tenant ID do client tự chọn khi upload

**Vấn đề:** Route `tenantId` được dùng trực tiếp để ghi blob và metadata.  
**Tại sao xảy ra:** Không có bước xác thực membership và authorization với tenant đích.  
**Ảnh hưởng production:** Ghi dữ liệu vào namespace tenant khác, tạo record giả, gây lẫn dữ liệu.  
**Cách sửa:** Xác minh tenant membership từ server-side authorization; nếu cho phép nhiều tenant thì yêu cầu quyền rõ ràng cho tenant được chọn.

### High — Blob name có thể ghi đè và không bảo đảm namespace

**Vấn đề:** Dùng `tenantId + "/" + file.FileName` và `overwrite: true`.  
**Tại sao xảy ra:** Tên do client điều khiển, không unique; có thể chứa ký tự phân tách hoặc tên không chuẩn. Blob Storage không có directory isolation tự động theo slash.  
**Ảnh hưởng production:** Ghi đè tài liệu, làm record cũ trỏ tới nội dung mới; tên file có thể tạo key ngoài cấu trúc dự kiến.  
**Cách sửa:** Sinh random opaque blob key trên server, prefix từ tenant đã xác thực; lưu tên gốc chỉ để hiển thị sau khi sanitize.

### High — Chỉ kiểm tra đuôi tên file và thiếu giới hạn thực tế

**Vấn đề:** `EndsWith(".pdf")` không xác minh content; request limit 100 MB không khớp 20 MiB; thiếu null/empty checks.  
**Tại sao xảy ra:** Extension là metadata không đáng tin; limit request không thay thế validation của file.  
**Ảnh hưởng production:** Upload sai loại file, tiêu thụ storage và tăng rủi ro xử lý nội dung độc hại.  
**Cách sửa:** Kiểm tra `Length`, content signature và file parser khi cần; malware scan/quarantine theo policy; không coi magic bytes là đủ để bảo đảm file an toàn.

### High — Memory amplification dưới concurrency

**Vấn đề:** Copy toàn bộ `IFormFile` sang `MemoryStream`.  
**Tại sao xảy ra:** `IFormFile` đã có thể được ASP.NET Core buffer ở memory/disk; copy thêm làm tăng allocation/LOH và áp lực GC.  
**Ảnh hưởng production:** Memory spike, GC pause, instance restart dưới tải.  
**Cách sửa:** Stream từ `OpenReadStream()` sang Blob; với yêu cầu không buffer toàn bộ request, xem xét streaming multipart reader thay vì `IFormFile` (vẫn có buffering theo cấu hình).

### High — Blob và SQL không atomic

**Vấn đề:** Upload thành công nhưng `SaveChangesAsync` thất bại để lại orphan blob.  
**Tại sao xảy ra:** Hai resource không chia sẻ transaction.  
**Ảnh hưởng production:** Storage rác, khó reconcile, metadata sai lệch.  
**Cách sửa:** Compensation delete best-effort, log failure; thiết kế trạng thái Pending/Ready và cleanup/reconciliation job khi cần. Không hứa rollback tuyệt đối.

### Medium — Không truyền cancellation token

**Vấn đề:** I/O Blob, copy và SQL không dùng `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Request cancellation không tự động truyền qua mọi API.  
**Ảnh hưởng production:** Tiếp tục làm việc sau khi client rời đi, tăng tải và thời gian giữ connection.  
**Cách sửa:** Truyền token, phân biệt cancel trước/sau commit; vẫn cần cleanup vì cancellation có thể xảy ra giữa các bước.

### Medium — Identity/logging và lỗi response chưa chuẩn hóa

**Vấn đề:** `User.Identity.Name!` có thể null; log tên file chứa dữ liệu nhạy cảm; exception mặc định thiếu contract ổn định.  
**Tại sao xảy ra:** Claim mapping và log retention phụ thuộc cấu hình.  
**Ảnh hưởng production:** 500 không cần thiết, lộ metadata qua logs, khó điều tra.  
**Cách sửa:** Dùng stable subject claim sau validation, structured log với document ID/tenant pseudonymous; centralized ProblemDetails, correlation ID, không trả nội dung nhạy cảm.

## Phiên bản đề xuất

Đoạn sau là **core flow** minh họa; `ITenantAccess` phải kiểm tra membership/permission trên server, và `IDocumentStore` quản lý record cùng cleanup. Với upload lớn hoặc yêu cầu strict no-buffer, thay `IFormFile` bằng streaming multipart endpoint.

```csharp
[ApiController]
[Authorize]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private const long MaxPdfBytes = 20L * 1024 * 1024;
    private readonly ITenantAccess _access;
    private readonly IDocumentStore _store;
    private readonly BlobContainerClient _blobs;

    public DocumentsController(
        ITenantAccess access,
        IDocumentStore store,
        BlobContainerClient blobs)
    {
        _access = access;
        _store = store;
        _blobs = blobs;
    }

    [HttpPost("{tenantId}/upload")]
    [RequestSizeLimit(22L * 1024 * 1024)]
    public async Task<IActionResult> Upload(
        string tenantId, IFormFile? file,
        CancellationToken ct)
    {
        if (!await _access.CanWriteAsync(User, tenantId, ct))
            return Forbid();

        if (file is null || file.Length == 0 ||
            file.Length > MaxPdfBytes)
            return BadRequest("Invalid file size");

        await using var input = file.OpenReadStream();
        var header = new byte[5];
        if (await input.ReadAtLeastAsync(
                header, header.Length, throwOnEndOfStream: false, ct) != 5 ||
            !header.AsSpan().SequenceEqual("%PDF-"u8))
            return BadRequest("Invalid PDF signature");

        if (!input.CanSeek)
            return StatusCode(500, "Streaming validation unavailable");
        input.Position = 0;

        var id = Guid.NewGuid();
        var key = $"{tenantId}/{id:N}";
        var blob = _blobs.GetBlobClient(key);

        try
        {
            await blob.UploadAsync(input,
                new Azure.Storage.Blobs.Models.BlobUploadOptions
                {
                    HttpHeaders = new Azure.Storage.Blobs.Models.BlobHttpHeaders
                    {
                        ContentType = "application/pdf"
                    }
                }, ct);

            await _store.CreateReadyAsync(
                id, tenantId, key, file.FileName, User, ct);
            return CreatedAtAction(nameof(Download), new { id },
                new { id });
        }
        catch
        {
            try { await blob.DeleteIfExistsAsync(
                cancellationToken: CancellationToken.None); }
            catch { /* record cleanup failure in centralized telemetry */ }
            throw;
        }
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> Download(Guid id, CancellationToken ct)
    {
        var tenantId = await _access.GetAuthorizedReadTenantAsync(
            User, id, ct);
        if (tenantId is null) return NotFound();

        var doc = await _store.FindReadyAsync(id, tenantId, ct);
        if (doc is null) return NotFound();

        var stream = await _blobs.GetBlobClient(doc.BlobName)
            .OpenReadAsync(cancellationToken: ct);
        return File(stream, "application/pdf", doc.SafeDownloadName);
    }
}
```

**Giới hạn của ví dụ:** `ReadAtLeastAsync` chỉ kiểm tra signature; validation sâu, antivirus, quota, request streaming, stable identity và reconciliation là các thành phần cần triển khai theo policy. `ITenantAccess` không được suy ra tenant chỉ từ request body hoặc header tùy ý. Trong production, lưu trạng thái Pending/Ready trước và sau upload sẽ giúp recovery tốt hơn; cleanup sau lỗi cần durable job, không chỉ catch. Với stream không seekable, dùng buffered prefix wrapper thay vì trả 500. Nếu SDK overload hoặc framework version khác, kiểm tra lại chữ ký API trước khi tích hợp.

## Giải thích thiết kế sau khi sửa

Authorization đặt trước I/O; opaque blob key không cho phép user chọn tên storage; metadata được tìm theo tenant; giới hạn kích thước kiểm tra trước upload. Cancellation giảm wasted work nhưng không bảo đảm atomicity. Blob container nên private, ứng dụng dùng Managed Identity với quyền tối thiểu. Không tạo SAS public nếu nghiệp vụ không cần.

## Trade-offs

API proxy giúp kiểm soát nội dung nhưng tốn bandwidth App Service; direct-to-Blob upload bằng SAS ngắn hạn giảm tải nhưng phải có quy trình finalize/scan/authorize và ràng buộc blob key. Quarantine + malware scanning tăng latency và vận hành. Metadata Pending/Ready tăng trạng thái cần reconcile nhưng đáng giá nếu tài liệu có giá trị cao.

## Cách kiểm thử

1. **Security integration:** User tenant A không upload/download được tài liệu tenant B; kiểm tra cả ID đã biết.
2. **Concurrency:** Hai upload cùng tên không ghi đè, ID và blob key khác nhau.
3. **Failure-path:** SQL fail sau Blob upload; verify cleanup hoặc Pending reconciliation.
4. **Load:** 50 upload song song sát 20 MiB; đo memory/GC/latency, xác minh không giữ 20 MiB trong `MemoryStream` ứng dụng.
5. **Content security:** extension giả, file rỗng, oversized, signature giả và payload cần scan bị từ chối theo policy.

## Quan sát trong production

Structured logs: `documentId`, tenant identifier đã kiểm soát, correlation ID, stage và error category (không log nội dung file). Metrics: upload success/failure, duration p95/p99, bytes, memory/GC, orphan count, scan backlog. Trace Blob dependency và SQL dependency trong Application Insights; alert khi orphan tăng hoặc authorization denial bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cần direct upload qua SAS, làm sao ngăn upload nhầm tenant và finalize file chưa scan?
2. Nếu database commit thành công nhưng HTTP response mất, client retry thế nào để không tạo hai tài liệu?
3. Khi tenant yêu cầu xóa toàn bộ tài liệu, thiết kế reconciliation và audit như thế nào?

# Code Review Challenge 2 — CI/CD rollback khi database schema thay đổi

**Chủ đề:** TeamCity, Octopus Deploy, SQL Server, IIS, release engineering  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–8

## Bối cảnh

Một ứng dụng ASP.NET MVC legacy chạy trên hai IIS nodes sau load balancer. TeamCity build artifact, Octopus Deploy triển khai. Phiên bản mới đổi cột `Customer.DisplayName` thành `FullName`. Deploy có rolling rollout, các nodes có thể chạy hai version trong vài phút. Lần trước rollout lỗi khiến requests trả 500; thao tác rollback app không khôi phục dịch vụ. SQL Server là shared database. Chưa rõ dữ liệu có thể chấp nhận downtime hay không, và thời gian rollback tối đa là bao nhiêu.

## Đoạn code cần review

```yaml
# release-plan.yml — pseudo configuration for review
build:
  tool: TeamCity
  steps:
    - run: dotnet restore
    - run: dotnet build -c Release
    - run: dotnet publish Web.csproj -c Release -o ./publish
    - run: package ./publish --name customer-portal --version latest

deploy:
  tool: Octopus
  environment: Production
  steps:
    - name: Apply database change
      runSql: |
        EXEC sp_rename 'dbo.Customer.DisplayName',
                       'FullName', 'COLUMN';
        ALTER TABLE dbo.Customer
          ALTER COLUMN FullName nvarchar(80) NOT NULL;
    - name: Deploy node A
      package: customer-portal:latest
      target: IIS-A
      action: replace-files
    - name: Deploy node B
      package: customer-portal:latest
      target: IIS-B
      action: replace-files
    - name: Health check
      request: GET https://portal.example.com/
      expectedStatus: 200
    - name: Rollback on failure
      condition: previous-step-failed
      deployPreviousPackage: true

application:
  startup:
    runSql: |
      UPDATE dbo.Customer
      SET FullName = LTRIM(RTRIM(FullName));
  connection:
    string: "Server=sql-prod;Database=Portal;User Id=deploy;Password=change-me"
  diagnostics:
    logRequestBody: true
    logSqlParameters: true
```

## Kết quả code review tham khảo

### Critical — Breaking schema change trước khi deploy

**Vấn đề:** Rename `DisplayName` ngay khi các IIS nodes vẫn chạy code cũ.  
**Tại sao xảy ra:** Shared DB được thay đổi độc lập với thời điểm mỗi node nhận binary mới.  
**Ảnh hưởng production:** Old nodes lỗi SQL, requests 500 trong rollout; rollback binary vẫn lỗi.  
**Cách sửa:** Expand/contract: thêm `FullName` nullable, backfill, dual-write hoặc compatibility adapter, deploy readers tương thích, sau khi toàn bộ old consumers biến mất mới enforce constraint/drop old column.

### High — Rollback chỉ khôi phục binary

**Vấn đề:** `deployPreviousPackage` không đảo ngược schema/data changes.  
**Tại sao xảy ra:** Database migration có thể không reversible, nhất là khi dữ liệu đã đổi.  
**Ảnh hưởng production:** Rollback tạo tổ hợp binary/schema không tương thích.  
**Cách sửa:** Định nghĩa compatibility window, roll-forward remediation, backup/restore runbook có RPO/RTO; tránh dựa vào destructive rollback.

### High — Migration ALTER và startup UPDATE có thể gây blocking

**Vấn đề:** ALTER `NOT NULL` và update toàn bảng trên production không đánh giá locks/size; startup update chạy ở nhiều nodes.  
**Tại sao xảy ra:** DDL và mass update có thể giữ locks, tăng transaction log và blocking; mỗi process có thể chạy lại.  
**Ảnh hưởng production:** SQL latency spike, timeouts, App Pool startup delay.  
**Cách sửa:** Backfill theo batch có checkpoint và monitoring; migrate qua release step độc lập; chỉ enforce constraint khi dữ liệu và app đã sẵn sàng, kiểm tra execution/locking thực tế.

### High — Secret lộ trong config

**Vấn đề:** Connection string có password plaintext, deploy account có thể có quyền quá rộng.  
**Tại sao xảy ra:** Secret được nhúng trong release config.  
**Ảnh hưởng production:** Credential leakage qua repository/log/artifact; lateral access.  
**Cách sửa:** Octopus sensitive variables/secret manager, credential rotation, least privilege, tách schema migration identity khỏi runtime identity; ưu tiên integrated identity khi khả thi.

### High — Log request body và SQL parameters không kiểm soát

**Vấn đề:** `logRequestBody: true`, `logSqlParameters: true` toàn cục.  
**Tại sao xảy ra:** Diagnostic config không phân loại PII và secret.  
**Ảnh hưởng production:** Lộ customer data, credentials, retention risk.  
**Cách sửa:** Structured redacted logs, allowlist fields, sampling và access control.

### Medium — Artifact không immutable và thiếu test gate

**Vấn đề:** Package version `latest`, không có automated test, artifact promotion không pin SHA.  
**Tại sao xảy ra:** Build và deploy thiếu provenance/version pinning.  
**Ảnh hưởng production:** Deploy sai binary, khó tái hiện hoặc rollback chính xác.  
**Cách sửa:** Build once, test, package bằng immutable build number/commit SHA, promote đúng artifact qua environments, verify checksum.

### Medium — Health check không kiểm tra từng node và dependency

**Vấn đề:** GET homepage qua load balancer trả 200 có thể chỉ hit node tốt hoặc cached response.  
**Tại sao xảy ra:** Kiểm tra route chung không chứng minh readiness của node mới hoặc SQL path.  
**Ảnh hưởng production:** Rollout tiếp tục dù node A/B lỗi.  
**Cách sửa:** Drain node, deploy, kiểm tra readiness + critical synthetic transaction trên node đó, đưa vào pool sau khi pass; canary metrics trước khi tăng traffic.

### Medium — Thiếu concurrency guard cho migration

**Vấn đề:** Không có cơ chế bảo đảm migration chạy một lần, idempotent, có version ledger.  
**Tại sao xảy ra:** Startup/retry có thể chạy lại step.  
**Ảnh hưởng production:** Schema drift, repeated expensive operations, race condition.  
**Cách sửa:** Versioned migrations với deployment lock và preconditions; không chạy DDL trong mỗi app startup.

## Phiên bản đề xuất

Đây là release plan **mang tính thiết kế**, không phải cú pháp chạy trực tiếp của TeamCity/Octopus.

```yaml
release:
  artifact:
    buildOnce: true
    version: "<immutable-build-number-and-commit-sha>"
    requiredChecks:
      - unit-tests
      - integration-tests
      - migration-compatibility-tests
  secrets:
    source: "Octopus sensitive variables / approved secret store"
    runtimeIdentity: "least-privilege application account"
    migrationIdentity: "separate restricted deployment account"
  phases:
    - name: Expand schema
      runOnce: true
      migration: "Add nullable FullName; preserve DisplayName"
      verify: "Both old and new readers still work"
    - name: Backfill
      runOnce: true
      mode: "bounded batches with checkpoint and lock monitoring"
      verify: "No missing FullName values; monitor blocking"
    - name: Compatible application rollout
      strategy: "drain -> deploy pinned package -> per-node health -> restore"
      compatibility: "old and new columns supported during transition"
      canaryGate: "error rate, SQL errors, latency, business transaction"
    - name: Verify
      checks:
        - "All nodes use pinned artifact"
        - "Mixed-version compatibility confirmed"
        - "Data parity and application telemetry healthy"
    - name: Contract in later release
      preconditions:
        - "All readers/writers migrated"
        - "Rollback window closed"
        - "No legacy consumer dependency"
      migration: "Enforce constraints and remove DisplayName"
  recovery:
    app: "Redeploy previous pinned compatible artifact"
    database: "Prefer forward-fix; use documented recovery plan"
```

Ví dụ SQL expand/backfill (cần xác minh schema, collation, index và dữ liệu trước khi chạy):

```sql
IF COL_LENGTH('dbo.Customer', 'FullName') IS NULL
    ALTER TABLE dbo.Customer ADD FullName nvarchar(80) NULL;
GO

-- Thực thi theo batch từ migration runner; đo lock và log growth.
UPDATE TOP (500) dbo.Customer
SET FullName = LEFT(LTRIM(RTRIM(DisplayName)), 80)
WHERE FullName IS NULL;
-- Lặp có checkpoint đến khi hết rows; không tự chạy tại app startup.
```

**Lưu ý:** Nếu `DisplayName` dài hơn 80 ký tự, `LEFT` có thể làm mất dữ liệu. Chỉ dùng sau khi Product chấp thuận truncation; phương án an toàn hơn là giữ đủ độ dài và xử lý records vượt giới hạn trước contract. Dual-write cần xử lý cạnh tranh, lựa chọn nguồn dữ liệu chuẩn và kiểm chứng parity. Migration runner phải bảo đảm chỉ một executor và có bounded retries.

## Giải thích thiết kế sau khi sửa

Tách database compatibility khỏi binary deployment; giữ old/new app cùng hoạt động trong transition. Mỗi release dùng artifact đã test với identity và checksum xác định. Per-node readiness và canary giúp giảm blast radius. Không để startup của từng IIS worker chịu trách nhiệm migrate shared schema.

## Trade-offs

Expand/contract cần nhiều release, dual-write phức tạp và storage tạm thời; đổi lại hỗ trợ zero/low downtime và rollback app. Nếu được phép maintenance window với downtime rõ ràng, có thể dùng cutover đơn giản hơn nhưng phải chứng minh RTO và phương án recovery. Batch migration giảm lock duration nhưng tăng thời gian hoàn tất và yêu cầu theo dõi consistency.

## Cách kiểm thử

1. **Compatibility integration:** Old binary + expanded schema, new binary + expanded schema, và mixed-version writes.
2. **Migration test:** Database copy với dữ liệu lớn, Unicode, null, tên dài; đo lock/log growth và kiểm tra không mất dữ liệu.
3. **Deployment validation:** Rolling deploy từng node; synthetic transaction và per-node health; rollback binary trên expanded schema.
4. **Failure injection:** Dừng migration giữa batch, retry; đảm bảo resume không tạo sai dữ liệu hoặc chạy đồng thời.
5. **Security test:** Scan artifact/config/log để bảo đảm không có password, PII hoặc SQL parameter nhạy cảm.

## Quan sát trong production

Application Insights/Kibana: request 5xx, SQL exceptions, p95/p99 theo node và release version. SQL Server: blocking sessions, wait stats, transaction log growth, deadlocks, query duration, batch progress, parity counts. Octopus: deployment ID, artifact hash, migration version, gate results. Alert khi error budget bị vượt, data parity giảm hoặc một node health fail.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product chỉ cho phép một lần deploy, điều kiện nào khiến bạn chọn maintenance window thay vì rolling rollout?
2. Khi dual-write thành công ở cột cũ nhưng thất bại ở cột mới, làm sao bảo đảm consistency?
3. Nếu migration chạy 4 giờ và cần hotfix ứng dụng, bạn quyết định rollback hay roll-forward dựa trên tiêu chí nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authorization phải kiểm tra quyền trên từng resource, không chỉ authentication và route parameter.
- Blob Storage và SQL không có transaction chung; thiết kế compensation/reconciliation và idempotency.
- Release với shared database phải tương thích trong khoảng mixed-version; rollback binary không tự đảo schema.
- Observability cần chứng minh failure mode qua telemetry, không chỉ log một thông báo thành công.

## Mẫu tư duy cần nhớ

1. Xác định trust boundary trước khi viết logic.
2. Thiết kế failure path và recovery trước khi tăng concurrency.
3. Đo memory, lock, latency và error rate trước khi tối ưu.
4. Triển khai expand → migrate → contract khi cần zero/low downtime.
5. Kiểm tra từng node và dữ liệu thực, không chỉ HTTP 200.
