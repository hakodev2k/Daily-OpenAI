# Code Review Challenge 1 — Consumer xử lý thanh toán bị trừ quota hai lần

**Chủ đề:** Concurrency, idempotency, EF Core transaction, message retry  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core worker nhận message từ RabbitMQ sau khi người dùng đặt vé sự kiện. Mỗi message yêu cầu giữ một suất và ghi lịch sử xử lý. RabbitMQ có thể redeliver message khi consumer chết trước khi ACK. Hệ thống chạy nhiều replica và cùng một `EventBookingId` có thể nhận nhiều request đồng thời. Production thỉnh thoảng ghi nhận `RemainingSlots` giảm hai lần cho cùng một message, một số booking vượt quá giới hạn, và có message được đánh dấu processed dù thay đổi business chưa hoàn tất.

## Đoạn code cần review

```csharp
public sealed class BookingConsumer
{
    private readonly BookingDbContext _db;
    private readonly ILogger<BookingConsumer> _logger;

    public BookingConsumer(
        BookingDbContext db,
        ILogger<BookingConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        BookingMessage message,
        CancellationToken cancellationToken)
    {
        var processed = await _db.ProcessedMessages
            .AnyAsync(x => x.MessageId == message.MessageId, cancellationToken);

        if (processed)
            return;

        var booking = await _db.EventBookings
            .SingleAsync(x => x.Id == message.EventBookingId, cancellationToken);

        if (booking.RemainingSlots <= 0)
            throw new InvalidOperationException("No slots available");

        _db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = message.MessageId,
            ProcessedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        booking.RemainingSlots--;

        _db.UserBookings.Add(new UserBooking
        {
            EventBookingId = message.EventBookingId,
            UserId = message.UserId,
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Processed booking {MessageId} for {UserId}",
            message.MessageId,
            message.UserId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Xác định rủi ro concurrency, reliability và performance.
3. Giải thích impact khi chạy nhiều consumer hoặc khi message bị redelivery.
4. Ưu tiên các vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử race condition và failure path.
7. Đề xuất logs, traces và metrics cần theo dõi.

## Câu hỏi gợi mở

- `AnyAsync()` rồi `INSERT` có thực sự tạo thành một thao tác atomic không?
- Điều gì xảy ra nếu process chết giữa hai lần `SaveChangesAsync()`?
- Hai consumer cùng đọc `RemainingSlots = 1` thì chuyện gì có thể xảy ra?

- ACK/retry của broker nên xảy ra ở thời điểm nào?

## Kết quả code review tham khảo

### 1. Idempotency check có race condition

**Problem:** `AnyAsync()` và việc thêm `ProcessedMessage` là hai thao tác riêng biệt.  
**Why:** Hai consumer có thể cùng quan sát rằng message chưa tồn tại trước khi một consumer commit.  
**Impact:** Cùng message có thể được xử lý hai lần.  
**Severity:** Critical  
**Recommended fix:** Tạo unique constraint/index cho `MessageId`; coi database constraint là hàng phòng thủ cuối cùng và xử lý conflict theo semantics idempotent.

### 2. Business transaction bị chia thành hai commit

**Problem:** `ProcessedMessage` được commit trước khi giảm slot và tạo `UserBooking`.  
**Why:** Process có thể crash sau lần save đầu tiên.  
**Impact:** Khi broker redeliver, consumer thấy message đã processed và bỏ qua, trong khi booking chưa được tạo.  
**Severity:** Critical  
**Recommended fix:** Ghi idempotency record và toàn bộ thay đổi database trong cùng transaction/atomic unit phù hợp.

### 3. Lost update trên `RemainingSlots`

**Problem:** Read-modify-write `RemainingSlots--` không bảo vệ concurrent writers.  
**Why:** Nhiều consumer có thể đọc cùng giá trị rồi ghi kết quả dựa trên snapshot cũ.  
**Impact:** Overselling hoặc số slot không phản ánh số booking thực tế.  
**Severity:** Critical  
**Recommended fix:** Dùng concurrency token và retry có kiểm soát, hoặc conditional atomic update kiểu `UPDATE ... SET RemainingSlots = RemainingSlots - 1 WHERE Id = ... AND RemainingSlots > 0`, sau đó kiểm tra affected rows.

### 4. Không có database invariant cho booking trùng

**Problem:** Không thấy constraint ngăn cùng user/event được tạo nhiều lần nếu business rule yêu cầu một booking duy nhất.  
**Why:** Application check không đủ dưới concurrency.  
**Impact:** Duplicate booking dù message ID khác nhau hoặc retry flow có lỗi.  
**Severity:** High  
**Recommended fix:** Nếu business rule yêu cầu, thêm unique constraint phù hợp, ví dụ `(EventBookingId, UserId)` hoặc key thể hiện đúng invariant.

### 5. Failure semantics phụ thuộc broker nhưng không được thể hiện

**Problem:** Code không cho thấy ACK chỉ diễn ra sau durable commit.  
**Why:** ACK quá sớm có thể mất công việc; ACK muộn dẫn tới redelivery nên consumer bắt buộc idempotent.  
**Impact:** Lost hoặc duplicate processing.  
**Severity:** High  
**Recommended fix:** ACK chỉ sau khi durable transaction thành công; retry transient failures và dead-letter poison messages theo policy rõ ràng.

### 6. `InvalidOperationException` cho hết slot có thể bị retry vô ích

**Problem:** Business rejection và transient infrastructure failure chưa được phân loại.  
**Why:** Broker/job framework có thể retry mọi exception.  
**Impact:** Retry storm, log noise và tăng latency cho queue.  
**Severity:** Medium  
**Recommended fix:** Phân biệt permanent business outcome với transient failure; persist/reply trạng thái hết slot theo workflow nghiệp vụ.

### 7. Logging thiếu correlation và outcome

**Problem:** Chỉ log success cuối flow.  
**Why:** Không có structured fields cho event, attempt, duplicate, concurrency conflict hoặc duration.  
**Impact:** Khó điều tra redelivery và race condition.  
**Severity:** Medium  
**Recommended fix:** Trace theo message/correlation ID và metrics cho duplicate, conflict, retry, processing latency, failures.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng transaction, unique constraint cho `ProcessedMessages.MessageId`, và optimistic concurrency cho booking. `RowVersion` cần được cấu hình làm concurrency token; database migration phải tạo unique index cho `MessageId` và invariant booking tương ứng.

```csharp
public sealed class BookingConsumer
{
    private readonly BookingDbContext _db;
    private readonly ILogger<BookingConsumer> _logger;

    public BookingConsumer(BookingDbContext db, ILogger<BookingConsumer> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task HandleAsync(
        BookingMessage message,
        CancellationToken cancellationToken)
    {
        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        try
        {
            var booking = await _db.EventBookings
                .SingleAsync(x => x.Id == message.EventBookingId, cancellationToken);

            if (booking.RemainingSlots <= 0)
                throw new BookingRejectedException("No slots available");

            _db.ProcessedMessages.Add(new ProcessedMessage
            {
                MessageId = message.MessageId,
                ProcessedAtUtc = DateTime.UtcNow
            });

            booking.RemainingSlots--;

            _db.UserBookings.Add(new UserBooking
            {
                EventBookingId = message.EventBookingId,
                UserId = message.UserId,
                CreatedAtUtc = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
            await transaction.CommitAsync(cancellationToken);

            _logger.LogInformation(
                "Booking message {MessageId} committed for event {EventBookingId} and user {UserId}",
                message.MessageId,
                message.EventBookingId,
                message.UserId);
        }
        catch (DbUpdateConcurrencyException)
        {
            await transaction.RollbackAsync(CancellationToken.None);
            throw;
        }
        catch (DbUpdateException ex) when (IsUniqueConstraintViolation(ex))
        {
            await transaction.RollbackAsync(CancellationToken.None);

            _logger.LogInformation(
                "Duplicate booking message {MessageId} ignored",
                message.MessageId);
        }
    }

    private static bool IsUniqueConstraintViolation(DbUpdateException ex)
    {
        return DatabaseErrorClassifier.IsUniqueViolation(ex);
    }
}
```

Trong production, classifier phải dựa trên provider-specific error code thay vì parse chuỗi exception. Nếu contention trên slot cao, một conditional database update có thể phù hợp hơn optimistic retry vì nó giảm round trip và biểu diễn `RemainingSlots > 0` trực tiếp trong thao tác update.

## Trade-offs

Optimistic concurrency đơn giản và phù hợp khi conflict hiếm, nhưng khi nhiều người tranh suất cuối cùng, retry có thể tăng mạnh. Conditional update atomic thường hiệu quả hơn cho counter nóng nhưng implementation phụ thuộc database nhiều hơn. Transaction bảo vệ các thay đổi trong cùng database; nếu workflow còn publish event ra broker, cần cân nhắc transactional outbox thay vì cố tạo distributed transaction.

## Cách kiểm thử

1. Chạy 20 consumer đồng thời với cùng `MessageId`; chỉ một business effect được commit.
2. Chạy nhiều message khác nhau khi chỉ còn một slot; không được tạo nhiều hơn một booking hợp lệ.
3. Inject crash/failure ngay trước commit và xác nhận redelivery vẫn hoàn tất đúng một lần về business effect.
4. Test unique constraint và concurrency conflict bằng database thật trong integration test.
5. Load test queue backlog lớn, theo dõi retry rate, lock/concurrency conflict và processing latency.

## Quan sát trong production

Log structured `MessageId`, `CorrelationId`, `EventBookingId`, `UserId`, attempt và outcome. Theo dõi processing duration, redelivery count, duplicate-detected count, concurrency conflicts, dead-letter count và queue depth. Trace consumer → database → outbound integration. Alert khi conflict/retry hoặc DLQ tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu sau commit cần gửi push notification, bạn tránh mất notification hoặc gửi trùng bằng cách nào?
2. Khi nào bạn chọn optimistic concurrency thay vì atomic SQL update?
3. Unique constraint có đủ để gọi toàn bộ consumer là idempotent không? Vì sao?

# Code Review Challenge 2 — Endpoint proxy Microsoft Graph làm lộ quyền và cạn connection

**Chủ đề:** Authorization, input validation, HTTP client lifetime, cancellation, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một internal ASP.NET Core API cho phép helpdesk tra cứu thông tin mailbox từ Microsoft Graph. API dùng application credential ở backend. Sau khi thêm tính năng “generic Graph lookup”, production xuất hiện latency tăng khi traffic cao và security review phát hiện người dùng helpdesk có thể truy vấn resource ngoài phạm vi mailbox dự kiến. Log cũng có khả năng chứa dữ liệu nhạy cảm. Endpoint chạy sau authentication middleware nhưng requirement authorization chi tiết chưa được thể hiện trong code.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/graph")]
public sealed class GraphProxyController : ControllerBase
{
    private readonly ITokenService _tokenService;
    private readonly ILogger<GraphProxyController> _logger;

    public GraphProxyController(
        ITokenService tokenService,
        ILogger<GraphProxyController> logger)
    {
        _tokenService = tokenService;
        _logger = logger;
    }

    [HttpGet("lookup")]
    public async Task<IActionResult> Lookup(
        [FromQuery] string path,
        CancellationToken cancellationToken)
    {
        var token = await _tokenService.GetApplicationTokenAsync();

        using var client = new HttpClient();
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        var url = "https://graph.microsoft.com/v1.0/" + path;

        _logger.LogInformation(
            "Graph request by {User}: {Url} Token={Token}",
            User.Identity?.Name,
            url,
            token);

        var response = await client.GetAsync(url);
        var body = await response.Content.ReadAsStringAsync();

        return StatusCode(
            (int)response.StatusCode,
            body);
    }
}
```

## Kết quả code review tham khảo

### 1. Caller điều khiển Graph path dùng application privilege

**Problem:** `path` từ request được nối trực tiếp vào Graph base URL.  
**Why:** Backend application token có quyền độc lập với quyền của end user; endpoint biến credential đó thành generic proxy.  
**Impact:** Caller có thể truy cập Graph resources ngoài business scope nếu application permission cho phép.  
**Severity:** Critical  
**Recommended fix:** Không nhận raw Graph path. Expose business-specific operations, validate identifiers và allowlist resource/query options cần thiết.

### 2. Thiếu authorization policy cụ thể

**Problem:** Code không yêu cầu role/policy cho chức năng nhạy cảm.  
**Why:** Authentication chỉ xác định identity, không chứng minh caller được phép thực hiện mailbox lookup.  
**Impact:** Authenticated user ngoài nhóm helpdesk có thể gọi endpoint nếu pipeline/routing cho phép.  
**Severity:** Critical  
**Recommended fix:** Dùng `[Authorize(Policy = "MailboxHelpdesk")]` hoặc policy/resource-based authorization phù hợp và least privilege ở identity/app registration.

### 3. Access token bị ghi vào log

**Problem:** Bearer token được log nguyên văn.  
**Why:** Structured logging có thể đưa token tới Application Insights/SIEM hoặc nhiều operator.  
**Impact:** Credential leakage; người có log access có thể lợi dụng token khi còn hiệu lực.  
**Severity:** Critical  
**Recommended fix:** Không log secret/token; redaction ở logging pipeline và review retention/access control.

### 4. Tạo `HttpClient` mỗi request

**Problem:** `new HttpClient()` làm mất lợi ích quản lý handler/connection lifetime tập trung.  
**Why:** Repeated handler creation/disposal có thể làm connection reuse kém và gây resource pressure dưới tải.  
**Impact:** Latency tăng và nguy cơ socket/connection pressure.  
**Severity:** High  
**Recommended fix:** Dùng `IHttpClientFactory` hoặc typed client; với Microsoft Graph SDK thì dùng client/lifetime theo hướng dẫn của SDK và DI.

### 5. Cancellation không truyền xuống outbound request

**Problem:** `GetAsync(url)` không nhận `cancellationToken`.  
**Why:** Client disconnect hoặc request timeout không hủy outbound operation.  
**Impact:** Wasted connections/work và tăng pressure khi downstream chậm.  
**Severity:** Medium  
**Recommended fix:** Truyền cancellation token cho token acquisition nếu API hỗ trợ và cho outbound send/read.

### 6. Response được buffer toàn bộ thành string

**Problem:** `ReadAsStringAsync()` buffer body rồi trả lại.  
**Why:** Response lớn tạo allocation và memory pressure.  
**Impact:** GC/memory tăng dưới tải hoặc response bất thường.  
**Severity:** Medium  
**Recommended fix:** Chỉ deserialize schema cần thiết; đặt giới hạn response và tránh generic pass-through.

### 7. Trả raw downstream response cho caller

**Problem:** Status/body từ Graph được chuyển thẳng ra ngoài.  
**Why:** Downstream error có thể chứa metadata không phù hợp cho caller; contract API phụ thuộc trực tiếp Graph.  
**Impact:** Information disclosure và coupling mạnh.  
**Severity:** Medium  
**Recommended fix:** Map sang domain DTO/error contract ổn định; log correlation ID thay vì raw sensitive payload.

### 8. Không thấy timeout/resilience policy rõ ràng

**Problem:** Outbound dependency chưa có timeout/bounded retry policy ở code/config được thể hiện.  
**Why:** Downstream degradation có thể giữ request lâu hoặc retry không kiểm soát nếu bổ sung sai.  
**Impact:** Tail latency và cascading failure.  
**Severity:** Medium  
**Recommended fix:** Cấu hình timeout và resilience phù hợp; retry chỉ transient/idempotent calls, có backoff và observability.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/mailboxes")]
[Authorize(Policy = "MailboxHelpdesk")]
public sealed class MailboxController : ControllerBase
{
    private readonly GraphMailboxClient _graph;
    private readonly ILogger<MailboxController> _logger;

    public MailboxController(
        GraphMailboxClient graph,
        ILogger<MailboxController> logger)
    {
        _graph = graph;
        _logger = logger;
    }

    [HttpGet("{userId}")]
    public async Task<ActionResult<MailboxDto>> GetMailbox(
        string userId,
        CancellationToken cancellationToken)
    {
        if (!MailboxIdentifier.TryParse(userId, out var identifier))
            return BadRequest(new { error = "Invalid mailbox identifier" });

        var mailbox = await _graph.GetMailboxAsync(
            identifier,
            cancellationToken);

        if (mailbox is null)
            return NotFound();

        _logger.LogInformation(
            "Mailbox lookup completed for {MailboxId} by {Actor}",
            identifier.SafeLogValue,
            User.Identity?.Name);

        return Ok(mailbox);
    }
}

public sealed class GraphMailboxClient
{
    private readonly HttpClient _httpClient;
    private readonly ITokenService _tokenService;

    public GraphMailboxClient(
        HttpClient httpClient,
        ITokenService tokenService)
    {
        _httpClient = httpClient;
        _tokenService = tokenService;
    }

    public async Task<MailboxDto?> GetMailboxAsync(
        MailboxIdentifier id,
        CancellationToken cancellationToken)
    {
        var token = await _tokenService
            .GetApplicationTokenAsync(cancellationToken);

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"users/{Uri.EscapeDataString(id.Value)}?$select=id,displayName,mail");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        using var response = await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return null;

        response.EnsureSuccessStatusCode();

        return await response.Content.ReadFromJsonAsync<MailboxDto>(
            cancellationToken: cancellationToken);
    }
}
```

`GraphMailboxClient` nên được đăng ký bằng typed `HttpClient` với base address cố định, timeout/resilience policy phù hợp. Permission của application identity phải được thu hẹp tối đa theo use case; API authorization và Graph application permission là hai lớp kiểm soát khác nhau, không thay thế cho nhau.

## Trade-offs

Business-specific endpoint làm giảm flexibility so với generic proxy nhưng tạo security boundary, validation và contract rõ ràng. Typed `HttpClient` thêm configuration nhưng cải thiện connection management và testability. Nếu có nhiều Graph operations hợp lệ, có thể xây service abstraction với một tập operation được allowlist thay vì mở raw URL. Cache có thể giảm Graph traffic cho dữ liệu ít thay đổi, nhưng phải cân nhắc freshness và dữ liệu nhạy cảm.

## Cách kiểm thử

1. Security integration test: user authenticated nhưng không có policy phải nhận 403; helpdesk hợp lệ mới được truy cập.
2. Fuzz/path test: identifier chứa path/query manipulation không được biến thành Graph endpoint ngoài operation cho phép.
3. Failure test: Graph timeout/429/5xx được map theo policy, không leak token/body nhạy cảm.
4. Cancellation test: hủy request và xác nhận outbound operation nhận cancellation.
5. Load test: nhiều request đồng thời, theo dõi connection reuse, latency, memory và downstream request count.

## Quan sát trong production

Không log token hoặc raw response chứa PII. Ghi actor, operation, sanitized resource identifier, correlation ID, downstream status category và duration. Theo dõi Graph dependency latency, timeout rate, 401/403/429/5xx, active outbound requests và retry count. Trace request qua API tới Graph; alert khi authorization failures hoặc throttling tăng đột biến.

1. Nếu helpdesk chỉ được phép quản lý mailbox của một số tenant/office, bạn thiết kế resource-based authorization thế nào?
2. `IHttpClientFactory` giải quyết vấn đề connection management ra sao và có trade-off gì với handler lifetime/DNS changes?
3. Nếu Graph trả 429, bạn quyết định retry ở đâu và làm sao tránh retry storm?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào việc biến idempotency và inventory invariant thành guarantee ở tầng durable storage thay vì dựa vào check trong memory/application flow. Retry của message broker chỉ an toàn khi business effect có semantics idempotent và transaction boundary đúng.

Challenge 2 nhấn mạnh sự khác biệt giữa authentication và authorization, đặc biệt khi backend giữ application credential có quyền mạnh. External API integration phải giới hạn capability, quản lý connection đúng lifetime, truyền cancellation và tránh đưa secret/PII vào observability pipeline.

## Mẫu tư duy cần nhớ

- Với concurrency: tìm mọi pattern **read/check → write** và hỏi liệu thao tác có atomic không.
- Thiết kế retry cùng idempotency; đừng xử lý hai vấn đề này độc lập.
- Business invariant quan trọng nên được enforce ở database khi có thể.
- Credential mạnh phải đi cùng least privilege và business-specific authorization boundary.
- Observability là một phần của thiết kế nhưng secret không bao giờ là telemetry.
