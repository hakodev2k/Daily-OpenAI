# Code Review Challenge 1 — `BackgroundService` chạy duplicate sau scale-out và Redis lock tạo cảm giác “đã an toàn”

**Chủ đề:** C#/.NET, `BackgroundService`, horizontal scaling, Redis, distributed coordination, idempotency, SQL Server, graceful shutdown, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core application trên Azure App Service có background job tổng hợp invoice mỗi 5 phút. Khi chỉ có một instance, hệ thống chạy ổn. Sau khi scale lên 4 instances, cùng một batch đôi lúc được tạo nhiều lần. Team thêm Redis distributed lock và kết luận vấn đề đã được giải quyết.

Sau vài tuần, production vẫn có duplicate invoice trong các thời điểm deployment/restart hoặc khi Redis latency tăng. Application Insights cho thấy một số job mất hơn 2 phút, đôi khi process bị shutdown giữa batch. SQL table hiện không có unique constraint cho business key của invoice batch.

Bạn được giao review implementation dưới đây. Không giả định rằng distributed lock cung cấp exactly-once execution.

## Đoạn code cần review

```csharp
public sealed class InvoiceAggregationWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly IDatabase _redis;
    private readonly ILogger<InvoiceAggregationWorker> _logger;

    public InvoiceAggregationWorker(
        IServiceProvider services,
        IConnectionMultiplexer redis,
        ILogger<InvoiceAggregationWorker> logger)
    {
        _services = services;
        _redis = redis.GetDatabase();
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (true)
        {
            await Task.Delay(TimeSpan.FromMinutes(5));
            await RunBatch();
        }
    }

    private async Task RunBatch()
    {
        var lockKey = "invoice-aggregation-lock";
        var lockValue = Environment.MachineName;

        if (!await _redis.StringSetAsync(
                lockKey,
                lockValue,
                TimeSpan.FromMinutes(1),
                When.NotExists))
        {
            _logger.LogInformation("Another instance is running");
            return;
        }

        try
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<BillingDbContext>();

            var orders = await db.Orders
                .Where(x => !x.Invoiced)
                .OrderBy(x => x.CreatedAt)
                .Take(500)
                .ToListAsync();

            foreach (var order in orders)
            {
                db.Invoices.Add(new Invoice
                {
                    OrderId = order.Id,
                    Number = $"INV-{DateTime.UtcNow:yyyyMMdd}-{order.Id}",
                    CreatedAt = DateTime.UtcNow
                });

                order.Invoiced = true;
                await db.SaveChangesAsync();
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Invoice batch failed");
        }
        finally
        {
            await _redis.KeyDeleteAsync(lockKey);
        }
    }
}
```

## Nhiệm vụ review

1. Xác định các correctness/reliability issues quan trọng và failure windows có thể tạo duplicate hoặc bỏ sót work.
2. Giải thích vì sao Redis lock hiện tại không đảm bảo chỉ một logical batch tạo side effect một lần.
3. Đề xuất thiết kế lại theo hướng chịu được multi-instance, restart, cancellation và partial failure.
4. Nêu rõ nơi cần idempotency/data constraint thay vì chỉ coordination.
5. Đề xuất tests và telemetry để chứng minh behavior khi có concurrency và failure.

## Gợi ý

### Gợi ý 1

Lock TTL là 1 phút nhưng job có thể chạy hơn 2 phút. Điều gì xảy ra khi lease hết hạn trong lúc instance cũ vẫn tiếp tục xử lý?

### Gợi ý 2

Ngay cả một distributed lock hoàn hảo cũng không tự biến side effect thành exactly-once nếu process chết sau khi commit nhưng trước khi hoàn thành coordination protocol.

### Gợi ý 3

Hãy phân biệt **coordination** với **business idempotency**.

## Các finding quan trọng cần nhận ra

### Bắt buộc

- `while (true)` và `Task.Delay` không dùng `stoppingToken`, nên worker không graceful shutdown đúng cách.
- `RunBatch()` không nhận/propagate cancellation tới EF Core operations.
- Lock TTL ngắn hơn worst-case processing time; instance khác có thể lấy lock trong khi owner cũ vẫn chạy.
- `lockValue = Environment.MachineName` không phải ownership token đủ an toàn; nhiều process/container có thể không tạo identity phù hợp cho compare-and-delete.
- `finally` xóa lock mà không kiểm tra ownership. Nếu lease cũ hết hạn và instance khác đã lấy lock, instance cũ có thể xóa lock của owner mới.
- Redis outage/latency là một failure mode riêng; lock không phải nguồn correctness duy nhất nên business invariant không được phụ thuộc hoàn toàn vào cache availability.
- Query `!Invoiced` rồi insert invoice/update order không tự bảo vệ trước concurrent processors nếu hai workers cùng quan sát state trước commit.
- Database không có unique business constraint cho invoice/order relationship, nên duplicate side effect vẫn có thể commit.
- `SaveChangesAsync()` trong từng iteration tạo nhiều round trips và tạo partial-completion boundary: một số orders đã commit trước khi batch lỗi.
- Catch-all exception chỉ log rồi vòng sau tiếp tục; không có explicit retry classification/backoff hoặc state cho failed work.

### Điểm cộng

- Timer cadence hiện là “delay sau khi job hoàn tất”, không phải lịch tuyệt đối 5 phút; cần xác nhận semantics business mong muốn.
- Có thể dùng `PeriodicTimer` với cancellation cho in-process cadence, nhưng nó vẫn không giải quyết distributed ownership.
- Nếu giữ lease-based coordination, cần unique token, renewal strategy và atomic compare-and-delete; vẫn phải giữ idempotency ở persistence boundary.
- Unique constraint như một invoice cho mỗi `OrderId` hoặc business operation key có thể biến race thành conflict có thể xử lý rõ ràng, nếu đó thực sự là invariant của domain.
- Transaction boundary phải được chọn theo business semantics; transaction cho toàn bộ 500 rows có lock/log-growth/failure trade-offs.
- Cần cân nhắc claim/lease work ở database, queue-based processing hoặc scheduler có distributed semantics tùy requirement; không mặc định Redis lock là giải pháp duy nhất.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng business invariant: nếu mỗi order chỉ được tạo một invoice cho operation này, database cần enforce invariant đó bằng unique key/constraint phù hợp. Coordination giúp giảm duplicate work, nhưng correctness không nên chỉ dựa vào việc một Redis key tồn tại.

Worker phải honor `stoppingToken`, ví dụ dùng `PeriodicTimer`, truyền cancellation xuống từng operation và xác định behavior khi shutdown giữa batch. Nếu deployment dừng process sau một số commits, lần chạy sau phải có khả năng resume/retry mà không tạo invoice thứ hai.

Nếu vẫn dùng Redis lease, lease phải có owner token ngẫu nhiên duy nhất, TTL đủ/renewable theo processing time, và release phải atomically kiểm tra token trước khi delete. Tuy nhiên lease có thể mất do pause/network/Redis failure, nên persistence operation vẫn phải idempotent.

Ở database layer, có thể xử lý theo từng logical unit với unique constraint và transaction phù hợp. Một lựa chọn khác là atomically claim work bằng state/lease trong database hoặc publish work sang queue và thiết kế consumer idempotent. Lựa chọn phụ thuộc throughput, operational complexity và requirement về latency; không tự động chuyển sang một distributed architecture phức tạp hơn.

`SaveChanges` per row có thể chấp nhận nếu mỗi order là transaction boundary độc lập và throughput đủ, nhưng cần chủ động. Nếu batch commit nhiều orders cùng lúc, failure/retry semantics thay đổi. Không nên gom tất cả vào một transaction lớn chỉ để giảm round trips mà bỏ qua lock duration và rollback cost.

## Tests nên có

- Concurrency integration test chạy nhiều worker instances cùng đọc một tập orders và xác nhận invariant không tạo duplicate invoice.
- Test lock TTL hết hạn giữa batch và owner thứ hai bắt đầu.
- Test owner cũ release sau khi owner mới đã lấy lease; owner cũ không được xóa lease mới.
- Test process/cancellation xảy ra sau invoice commit nhưng trước bước tiếp theo, rồi rerun.
- Test Redis unavailable/timeout và xác nhận hệ thống fail theo policy thay vì silently vi phạm invariant.
- Test database unique constraint/conflict handling.
- Test graceful shutdown với `stoppingToken`.

## Production observability

Theo dõi batch duration p50/p95/p99, số orders claimed/completed/failed, duplicate-constraint conflicts, lock acquire/renew/release failures, Redis latency, job overlap, cancellation/shutdown count và backlog age. Mỗi batch cần correlation identifier; log business key nhưng tránh sensitive data. Alert nên dựa trên backlog/age và failure rate, không chỉ “job đã chạy”.

## Trade-offs

- Redis coordination có latency thấp nhưng thêm failure mode và không thay thế database invariant.
- Database claiming đơn giản hóa correctness boundary nhưng có thể tăng contention tùy workload.
- Queue-based work có thể scale tốt và cô lập retries nhưng thêm operational complexity và vẫn cần idempotent consumer.
- Transaction lớn giảm một số round trips nhưng tăng lock duration, rollback cost và blast radius.

## Câu hỏi đào sâu

1. Nếu Redis lease được renew hoàn hảo, vì sao bạn vẫn muốn unique constraint/idempotency ở database?
2. Nếu mỗi order có thể hợp lệ tạo nhiều invoice theo nhiều billing cycle, bạn sẽ thiết kế idempotency key/business constraint thế nào thay vì `UNIQUE(OrderId)`?
3. Khi deployment gửi cancellation giữa batch, bạn chọn hoàn tất current item hay dừng ngay? Evidence và business semantics nào quyết định lựa chọn đó?

## Thang điểm 0–10

- **0–2:** Chỉ tăng TTL hoặc pool size.
- **3–4:** Nhận ra multi-instance/TTL nhưng vẫn coi lock là guarantee exactly-once.
- **5–6:** Sửa cancellation, lease ownership và thêm database invariant.
- **7–8:** Reasoning được partial failure, transaction/idempotency boundary, concurrency tests và observability.
- **9–10:** Thiết kế rõ coordination vs correctness, recovery semantics, rollout/failure testing và cost of complexity.

# Code Review Challenge 2 — Optimizely content cache làm rò personalization qua CDN và purge đang gây tải origin

**Chủ đề:** Optimizely CMS, ASP.NET Core, Akamai/CDN, HTTP caching, personalization, cache key design, invalidation, web performance, SEO, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một marketing/e-commerce site dùng Optimizely CMS. Trang product landing lấy content block từ CMS và thêm một banner phụ thuộc trạng thái đăng nhập/member tier. Team muốn tăng Lighthouse performance nên bật cache ở application và CDN. Sau rollout, QA thỉnh thoảng thấy banner member của user khác khi test qua shared edge location. Editorial team cũng phàn nàn content publish xong phải chờ lâu hoặc phải purge toàn site. Mỗi lần purge lớn, origin CPU và request rate tăng mạnh.

Chưa có bằng chứng lỗi nằm riêng ở Optimizely, CDN hay application cache. Hãy review implementation và HTTP policy thay vì chỉ giảm TTL.

## Đoạn code cần review

```csharp
public sealed class LandingPageService
{
    private readonly IContentLoader _contentLoader;
    private readonly IMemoryCache _cache;
    private readonly IHttpContextAccessor _httpContextAccessor;

    public LandingPageService(
        IContentLoader contentLoader,
        IMemoryCache cache,
        IHttpContextAccessor httpContextAccessor)
    {
        _contentLoader = contentLoader;
        _cache = cache;
        _httpContextAccessor = httpContextAccessor;
    }

    public LandingPageVm Get(ContentReference pageLink)
    {
        var cacheKey = $"landing:{pageLink.ID}";

        return _cache.GetOrCreate(cacheKey, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(6);

            var page = _contentLoader.Get<ProductLandingPage>(pageLink);
            var user = _httpContextAccessor.HttpContext!.User;

            return new LandingPageVm
            {
                Title = page.Title,
                HeroText = page.HeroText,
                CanonicalUrl = page.CanonicalUrl,
                MemberBanner = user.Identity?.IsAuthenticated == true
                    ? $"Special offer for {user.FindFirst("member_tier")?.Value}"
                    : null
            };
        })!;
    }
}

[HttpGet("/products/{slug}")]
public IActionResult ProductLanding(string slug)
{
    var model = _landingPages.Get(ResolveContent(slug));

    Response.Headers.CacheControl = "public, max-age=3600, s-maxage=21600";
    Response.Headers.Vary = "Accept-Encoding";

    return View("ProductLanding", model);
}
```

## Nhiệm vụ review

1. Tìm correctness/privacy/cache invalidation issues ở application cache và HTTP/CDN cache.
2. Giải thích cách personalized output có thể bị chia sẻ giữa users dù authentication backend vẫn đúng.
3. Đề xuất cách tách public CMS content và personalized data để cache hiệu quả hơn.
4. Thiết kế invalidation/purge strategy khi editor publish content mà không tạo thundering herd lên origin.
5. Nêu test và telemetry cho application cache, CDN và editorial publish flow.

## Gợi ý

### Gợi ý 1

Cache key chỉ dựa trên content ID, nhưng cached object chứa dữ liệu lấy từ `HttpContext.User`.

### Gợi ý 2

`public, s-maxage=...` nói gì với shared cache khi response chứa personalized HTML?

### Gợi ý 3

Purge toàn site giải quyết freshness bằng cách đánh đổi origin stability. Hãy tìm boundary nhỏ hơn.

## Các finding quan trọng cần nhận ra

### Bắt buộc

- `IMemoryCache` key không chứa identity/tier nhưng value chứa `MemberBanner`; request đầu tiên có thể quyết định personalized value cho các request sau trên cùng application instance.
- Với nhiều application instances, `IMemoryCache` còn tạo freshness khác nhau giữa instances.
- Response được đánh dấu `public` và có `s-maxage`, nên shared CDN có thể cache toàn bộ personalized HTML nếu không có policy khác ở edge.
- `Vary: Accept-Encoding` không phân tách authenticated/member variants.
- Không nên đơn giản thêm `Vary: Authorization` rồi coi vấn đề đã xong; điều đó có thể tạo cardinality/security/cache behavior khó kiểm soát và phụ thuộc auth transport/CDN configuration.
- Fixed 6-hour application TTL không gắn với Optimizely publish/content change, nên editor publish không đảm bảo invalidation ngay.
- Purge toàn site làm mất cache hàng loạt và có thể tạo cache stampede/thundering herd lên origin.
- `pageLink.ID` có thể chưa đủ cho mọi dimension như language/site/version nếu hệ thống phục vụ nhiều variants; cần xác nhận content model/routing thực tế.

### Điểm cộng

- Tách cacheable public content model khỏi request-specific personalization.
- Render personalized overlay bằng endpoint/client-side request riêng hoặc server composition có response cache policy private/no-store phù hợp, tùy SEO/UX requirement.
- Public landing HTML có thể dùng surrogate/cache tags theo content dependency để purge chọn lọc nếu CDN hỗ trợ cơ chế tương ứng.
- Application cache nên invalidation theo content events/dependency/version thay vì chỉ TTL dài.
- Có thể dùng stale-while-revalidate/stale-if-error nếu CDN/platform hỗ trợ và freshness requirement cho phép, nhưng phải xác minh behavior cụ thể trước khi dựa vào nó.
- Cần tránh cache stampede bằng request coalescing/single-flight hoặc controlled warm-up cho hot pages nếu workload chứng minh cần thiết.
- Canonical URL/SEO metadata phải nhất quán giữa variants và không nên phụ thuộc member personalization ngoài ý muốn.

## Hướng giải quyết tham khảo

Đầu tiên tôi sẽ phân loại response thành phần nào public và phần nào personalized. `Title`, `HeroText`, canonical metadata và phần lớn CMS content có thể là public cacheable content. `MemberBanner` phụ thuộc principal nên không được nhét vào cùng cache entry chỉ keyed bằng content ID.

Ở application layer, cache public content snapshot với key chứa các dimension thực sự ảnh hưởng nội dung, ví dụ site/language/content identity theo content model. Invalidation nên hook vào content publish/change mechanism phù hợp của CMS hoặc dùng version/dependency token thay vì chờ 6 giờ. Không cache `HttpContext.User`-derived state trong shared application entry.

Ở HTTP/CDN layer, chỉ đánh dấu `public` cho response thực sự an toàn để shared cache. Nếu toàn bộ HTML phải chứa personalization server-side, response cần policy phù hợp như private/no-store hoặc edge design có explicit safe variants; nhưng điều đó giảm CDN hit ratio. Một architecture thường đáng đánh giá là cache public page shell/content ở CDN và lấy personalized overlay qua endpoint riêng có authorization và cache policy riêng. Đây là trade-off, không phải rule bắt buộc nếu SEO/latency/rendering requirement khác.

Với publish, thay vì purge toàn site, map content dependencies sang targeted purge/cache tags hoặc purge URL affected. Nếu một block được reuse trên nhiều pages, dependency graph/cache tag giúp xác định impacted surfaces. Đối với hot pages, controlled pre-warm hoặc stale serving có thể giảm origin spike nếu infrastructure hỗ trợ và business freshness cho phép.

## Tests nên có

- Integration test: anonymous request rồi member request và ngược lại trên cùng application instance; không được leak `MemberBanner`.
- Test hai member tiers liên tiếp và xác nhận shared cache không reuse personalized value.
- Test multi-instance behavior nếu application cache vẫn local.
- CDN/E2E test với hai authenticated sessions qua cùng edge POP và xác nhận personalized HTML không bị shared.
- Test content publish invalidates đúng page/block dependencies mà không cần chờ TTL.
- Test reused content block publish làm invalidation tất cả affected pages nhưng không purge unrelated pages.
- Load test sau targeted purge/warm-up để đo origin request burst.
- SEO regression test cho canonical URL, status code và public metadata sau cache changes.

## Production observability

Theo dõi CDN hit ratio, origin request rate, application cache hit/miss, purge count/scope, cache fill latency, content publish-to-visible latency, p50/p95/p99 page latency và origin CPU. Correlate purge events với origin spikes. Với personalization, có privacy-safe telemetry để phát hiện variant mismatch nhưng không log member data hoặc credentials.

## Trade-offs

- Full-page CDN caching tối đa performance nhưng chỉ an toàn khi response shared được hoặc variant strategy được thiết kế rõ.
- Tách personalized overlay tăng request/composition complexity nhưng làm public cache boundary sạch hơn.
- TTL ngắn giảm stale window nhưng tăng origin load; event-driven invalidation phức tạp hơn nhưng freshness chính xác hơn.
- Targeted purge cần dependency metadata; purge toàn site đơn giản nhưng blast radius lớn.
- Local `IMemoryCache` đơn giản nhưng multi-instance invalidation/freshness cần được thiết kế; distributed cache không tự giải quyết sai cache key hoặc personalization boundary.

## Câu hỏi đào sâu

1. Nếu Product yêu cầu member banner phải xuất hiện trong initial HTML vì UX, bạn sẽ thiết kế shared-cache policy thế nào mà không leak giữa users?
2. Nếu một Optimizely block xuất hiện trên 5.000 pages, targeted invalidation nên được thiết kế thế nào để không biến một publish thành 5.000 synchronous purge calls?
3. Nếu CDN hit ratio giảm sau khi tách personalization nhưng origin vẫn trong capacity, bạn ưu tiên correctness hay cố khôi phục hit ratio bằng variant caching? Bạn cần evidence gì để quyết định?

## Thang điểm 0–10

- **0–2:** Chỉ giảm TTL hoặc purge thường xuyên hơn.
- **3–4:** Nhận ra cache key sai nhưng bỏ qua CDN/shared-cache boundary.
- **5–6:** Tách public/personalized data và sửa HTTP cache policy cơ bản.
- **7–8:** Có event-driven/targeted invalidation, stampede mitigation, E2E cache tests và observability.
- **9–10:** Reasoning được CMS dependency graph, privacy boundary, CDN/origin economics, SEO/UX và operational trade-offs.
