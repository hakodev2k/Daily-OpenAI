# Code Review Challenge 1 — Batch approval gây deadlock, giữ transaction quá lâu và trả kết quả không nhất quán

**Chủ đề:** EF Core transaction handling, SQL locking, concurrency, performance, error handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống timesheet có chức năng manager duyệt nhiều entry cùng lúc. API nhận danh sách `entryIds`, cập nhật trạng thái và ghi audit log. Một request thường có 20–100 entry, nhưng cuối tháng có thể lên tới vài trăm entry.

Production gần đây xuất hiện:

- Một số request mất 8–20 giây mới hoàn tất.
- SQL Server thỉnh thoảng báo deadlock victim.
- Có request trả lỗi nhưng một phần entry đã được cập nhật ở lần retry sau.
- Khi hai manager cùng duyệt các tập entry giao nhau theo thứ tự khác nhau, lỗi xảy ra nhiều hơn.
- Log hiện tại chỉ ghi một exception chung, khó biết entry nào gây lỗi.

Team muốn giữ tính nguyên tử ở mức business hợp lý, nhưng không muốn transaction dài và lock contention cao.

## Đoạn code cần review

```csharp
public sealed class TimesheetApprovalService
{
    private readonly AppDbContext _db;
    private readonly ILogger<TimesheetApprovalService> _logger;

    public TimesheetApprovalService(
        AppDbContext db,
        ILogger<TimesheetApprovalService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task ApproveAsync(
        IReadOnlyList<Guid> entryIds,
        Guid managerId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        foreach (var entryId in entryIds)
        {
            var entry = await _db.TimesheetEntries
                .SingleAsync(x => x.Id == entryId, cancellationToken);

            if (entry.Status == TimesheetStatus.Approved)
                continue;

            entry.Status = TimesheetStatus.Approved;
            entry.ApprovedBy = managerId;
            entry.ApprovedAt = DateTime.UtcNow;

            _db.TimesheetApprovalHistories.Add(new TimesheetApprovalHistory
            {
                TimesheetEntryId = entry.Id,
                ManagerId = managerId,
                ApprovedAt = DateTime.UtcNow
            });

            await _db.SaveChangesAsync(cancellationToken);
        }

        await _externalNotifier.SendApprovedAsync(
            entryIds,
            managerId,
            cancellationToken);

        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Approved {Count} timesheet entries by {ManagerId}",
            entryIds.Count,
            managerId);
    }
}
```

## Kết quả code review tham khảo

### 1. Gọi external notifier bên trong database transaction tạo dual-write inconsistency

**Problem:** `_externalNotifier.SendApprovedAsync()` chạy trước `CommitAsync()`.

**Why it happens:** Database transaction chỉ kiểm soát thay đổi trong database; external service không tham gia transaction đó.

**Production impact:** Notifier có thể thành công nhưng database commit thất bại, khiến người dùng nhận thông báo về trạng thái chưa tồn tại. Ngược lại notifier lỗi có thể làm rollback database dù business update hợp lệ.

**Severity:** Critical

**Recommended fix:** Commit database trước và ghi một outbox record trong cùng transaction. Một worker riêng đọc outbox và gửi notification với retry/idempotency.

### 2. `SaveChangesAsync()` cho từng entry làm tăng round-trip và kéo dài transaction

**Problem:** Mỗi entry tạo ít nhất một database flush riêng.

**Why it happens:** EF Core gửi thay đổi xuống database nhiều lần trong cùng transaction.

**Production impact:** Batch lớn giữ transaction lâu hơn, tăng lock duration, connection usage, latency và khả năng deadlock.

**Severity:** High

**Recommended fix:** Load batch cần xử lý, cập nhật trong memory và gọi `SaveChangesAsync()` một lần nếu business semantics cho phép.

### 3. Lock order không ổn định giữa các request

**Problem:** `entryIds` được xử lý theo thứ tự client gửi lên.

**Why it happens:** Hai request có thể khóa cùng tập row theo thứ tự khác nhau, ví dụ A→B và B→A.

**Production impact:** Khi concurrent, circular wait có thể hình thành và database chọn một transaction làm deadlock victim.

**Severity:** High

**Recommended fix:** Chuẩn hóa thứ tự xử lý, ví dụ sort theo primary key trước khi query/update. Đồng thời giảm thời gian transaction và kiểm tra deadlock graph để xác nhận nguyên nhân thực tế.

### 4. N+1 query cho batch approval

**Problem:** Mỗi `entryId` chạy một `SingleAsync()` riêng.

**Why it happens:** Service truy vấn từng row thay vì tải tập dữ liệu trong một query.

**Production impact:** Tăng round-trip, latency, database CPU và thời gian giữ transaction.

**Severity:** High

**Recommended fix:** Query toàn bộ entry bằng `Where(x => ids.Contains(x.Id))`, sau đó kiểm tra missing IDs và cập nhật theo thứ tự ổn định.

### 5. Không có concurrency protection cho business transition

**Problem:** Code chỉ kiểm tra `Status` sau khi load entity nhưng không có optimistic concurrency token hoặc điều kiện update thể hiện transition hợp lệ.

**Why it happens:** Hai manager có thể đọc cùng trạng thái cũ rồi cùng cập nhật.

**Production impact:** Audit có thể ghi nhiều lần, `ApprovedBy` có thể bị ghi đè và business rule “ai duyệt trước” trở nên không rõ ràng.

**Severity:** High

**Recommended fix:** Xác định rule business. Nếu chỉ một actor được thắng, dùng optimistic concurrency token/rowversion hoặc conditional update dựa trên trạng thái hiện tại và xử lý conflict rõ ràng.

### 6. Batch có ID không tồn tại sẽ fail giữa chừng

**Problem:** `SingleAsync()` ném exception ngay khi gặp ID sai.

**Why it happens:** Validation input và existence check không được thực hiện trước khi mutate.

**Production impact:** Transaction rollback nhưng thời gian đã giữ lock vẫn bị tiêu tốn; log không chỉ ra đầy đủ input nào invalid.

**Severity:** Medium

**Recommended fix:** Tải toàn bộ batch trước, so sánh số lượng/ID, validate authorization và trạng thái trước khi bắt đầu phần mutate quan trọng.

### 7. Hai lần gọi `DateTime.UtcNow` tạo timestamp không đồng nhất trong cùng logical action

**Problem:** `ApprovedAt` của entity và history được lấy ở hai thời điểm khác nhau.

**Why it happens:** Timestamp được tạo lặp lại trong loop.

**Production impact:** Không nghiêm trọng nhưng làm audit khó đối chiếu và test kém deterministic.

**Severity:** Low

**Recommended fix:** Dùng một `now` cho toàn bộ batch hoặc một `now` cho từng entry tùy semantics, tốt hơn nữa dùng abstraction như `TimeProvider` để test.

### 8. Logging thiếu context điều tra deadlock/failure

**Problem:** Chỉ log khi thành công, không có batch id, ordered ids summary, transaction duration hay số conflict.

**Why it happens:** Observability không được thiết kế cùng transaction workflow.

**Production impact:** Khó nối application trace với deadlock graph hoặc xác định batch nào gây contention.

**Severity:** Medium

**Recommended fix:** Log structured fields như batch id, manager id, item count, duration, conflict count; correlate database command/trace và deadlock event.

## Phiên bản code đề xuất

```csharp
public sealed class TimesheetApprovalService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public TimesheetApprovalService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task ApproveAsync(
        IReadOnlyCollection<Guid> entryIds,
        Guid managerId,
        CancellationToken cancellationToken)
    {
        var ids = entryIds
            .Distinct()
            .OrderBy(x => x)
            .ToArray();

        var entries = await _db.TimesheetEntries
            .Where(x => ids.Contains(x.Id))
            .OrderBy(x => x.Id)
            .ToListAsync(cancellationToken);

        if (entries.Count != ids.Length)
            throw new InvalidOperationException("One or more timesheet entries do not exist.");

        var now = _timeProvider.GetUtcNow().UtcDateTime;

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        foreach (var entry in entries)
        {
            if (entry.Status == TimesheetStatus.Approved)
                continue;

            entry.Status = TimesheetStatus.Approved;
            entry.ApprovedBy = managerId;
            entry.ApprovedAt = now;

            _db.TimesheetApprovalHistories.Add(new TimesheetApprovalHistory
            {
                TimesheetEntryId = entry.Id,
                ManagerId = managerId,
                ApprovedAt = now
            });
        }

        _db.OutboxMessages.Add(OutboxMessage.Create(
            "TimesheetEntriesApproved",
            new { EntryIds = ids, ManagerId = managerId, ApprovedAt = now }));

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
}
```

**Lưu ý:** Nếu business yêu cầu concurrency nghiêm ngặt, entity cần concurrency token hoặc update có điều kiện để phát hiện trường hợp trạng thái đã đổi kể từ lúc đọc.

## Trade-offs

- Một `SaveChangesAsync()` giảm round-trip nhưng batch rất lớn có thể tạo transaction lớn; khi đó cần chunking có chủ đích và định nghĩa rõ atomicity.
- Outbox tăng thêm bảng, worker và cleanup logic, nhưng đổi lại giải quyết dual-write đáng tin cậy hơn.
- Optimistic concurrency phù hợp khi conflict hiếm; với contention rất cao có thể cần thiết kế khác hoặc serialize theo business key.
- Sort theo ID giúp lock order nhất quán hơn nhưng không tự động loại bỏ mọi deadlock; vẫn cần quan sát deadlock graph thực tế.

## Cách kiểm thử

1. **Concurrency test:** chạy hai request với tập ID giao nhau và thứ tự đầu vào khác nhau; xác nhận không tạo duplicate history ngoài rule cho phép.
2. **Failure-path test:** giả lập database commit fail; xác nhận không có external notification được gửi trực tiếp.
3. **Outbox integration test:** commit thành công tạo đúng một outbox event cho batch và retry worker không gửi trùng nếu consumer hỗ trợ idempotency.
4. **Large batch test:** 500–1.000 ID, đo số SQL round-trip, transaction duration và latency.
5. **Concurrency-token test:** mô phỏng entry bị thay đổi bởi request khác trước `SaveChangesAsync()` và xác nhận conflict được xử lý rõ ràng.

## Quan sát trong production

- Log: `ApprovalBatchId`, `ManagerId`, `EntryCount`, `ChangedCount`, `ConflictCount`, elapsed time.
- Metric: batch latency p95/p99, deadlock count, transaction duration, outbox backlog, notification retry count.
- Trace: span cho load batch, save, commit, outbox processing.
- Database: deadlock graph, blocked process report, top waits, lock duration, query count/plan.
- Alert: deadlock rate tăng, outbox backlog vượt ngưỡng, approval latency vượt SLO.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/webhooks")]
public sealed class WebhookController : ControllerBase
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<WebhookController> _logger;

    public WebhookController(
        HttpClient httpClient,
        ILogger<WebhookController> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    [HttpPost("test")]
    [Authorize]
    public async Task<IActionResult> TestAsync(
        TestWebhookRequest request,
        CancellationToken cancellationToken)
    {
        if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri))
            return BadRequest("Invalid URL");

        var payload = JsonSerializer.Serialize(new
        {
            type = "webhook.test",
            tenantId = request.TenantId,
            requestedBy = User.Identity?.Name,
            secret = request.Secret
        });

        _logger.LogInformation(
            "Testing webhook {Url} for tenant {TenantId}",
            request.Url,
            request.TenantId);

        using var message = new HttpRequestMessage(HttpMethod.Post, uri)
        {
            Content = new StringContent(payload, Encoding.UTF8, "application/json")
        };

        message.Headers.Add("X-Webhook-Secret", request.Secret);

        var response = await _httpClient.SendAsync(
            message,
            HttpCompletionOption.ResponseContentRead,
            cancellationToken);

        var body = await response.Content.ReadAsStringAsync(cancellationToken);

        return Ok(new
        {
            status = (int)response.StatusCode,
            responseBody = body
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Endpoint có SSRF risk nghiêm trọng

**Problem:** Bất kỳ absolute URI nào cũng được gửi request từ server.

**Why it happens:** `Uri.TryCreate()` chỉ xác nhận parse được URI, không đảm bảo target là destination an toàn.

**Production impact:** Attacker có thể khiến application truy cập loopback, private network, link-local hoặc dịch vụ nội bộ mà họ không thể truy cập trực tiếp.

**Severity:** Critical

**Recommended fix:** Chỉ cho phép `https`, áp outbound destination policy, resolve DNS và từ chối IP loopback/private/link-local/reserved theo policy của môi trường. Cân nhắc egress proxy/firewall allow-list nếu threat model cao.

### 2. Chỉ `[Authorize]` nhưng không enforce tenant admin authorization

**Problem:** Caller có thể truyền `request.TenantId` tùy ý.

**Why it happens:** Identity authentication bị nhầm với resource authorization.

**Production impact:** User tenant A có thể test webhook dưới tenant B, tạo audit sai hoặc lợi dụng secret/config thuộc tenant khác nếu service sau này mở rộng.

**Severity:** Critical

**Recommended fix:** Lấy tenant từ authenticated context hoặc kiểm tra policy/resource authorization; không tin `TenantId` do client tự khai báo nếu không có validation server-side.

### 3. Secret bị đưa vào payload và header

**Problem:** `request.Secret` xuất hiện hai nơi trong outbound request.

**Why it happens:** Test payload trộn diagnostics data với credential.

**Production impact:** Secret dễ bị target lưu lại, echo lại hoặc xuất hiện trong response/log downstream.

**Severity:** High

**Recommended fix:** Không gửi secret trong body. Nếu cần signature test, dùng credential đã lưu server-side hoặc một test secret ngắn hạn, và ký payload thay vì gửi raw secret.

### 4. Log full URL có thể lộ token/query string

**Problem:** `request.Url` được log nguyên văn.

**Why it happens:** URL được coi là metadata an toàn.

**Production impact:** Query string có thể chứa token, signature hoặc tenant-specific credential và bị lưu trong log system.

**Severity:** High

**Recommended fix:** Log scheme + sanitized host + route template hoặc redacted URL; không log query string chứa secret.

### 5. Redirect có thể bypass destination validation

**Problem:** Nếu `HttpClientHandler` tự follow redirect, destination sau redirect có thể khác host ban đầu.

**Why it happens:** Validation thường chỉ áp dụng cho URI đầu tiên.

**Production impact:** Public URL hợp lệ có thể redirect sang internal endpoint.

**Severity:** High

**Recommended fix:** Disable auto-redirect cho client này hoặc validate từng redirect hop trước khi follow.

### 6. Không có timeout riêng phù hợp cho thao tác test

**Problem:** Request phụ thuộc timeout chung của client hoặc cancellation từ caller.

**Why it happens:** Endpoint chưa định nghĩa budget riêng cho outbound dependency.

**Production impact:** Nhiều target chậm có thể giữ request, socket và worker resources lâu, tạo self-inflicted DoS.

**Severity:** High

**Recommended fix:** Dùng timeout ngắn, rõ ràng, thông qua linked cancellation token hoặc resilience pipeline phù hợp; phân biệt timeout với user cancellation trong observability.

### 7. Đọc toàn bộ response body vào memory

**Problem:** `ResponseContentRead` và `ReadAsStringAsync()` materialize toàn bộ body.

**Why it happens:** Endpoint trả raw response để tiện debug.

**Production impact:** Target độc hại có thể trả payload rất lớn, gây memory pressure và tăng latency.

**Severity:** High

**Recommended fix:** Dùng `ResponseHeadersRead`, stream có giới hạn và chỉ capture preview tối đa N byte.

### 8. Trả raw response body của third party về caller

**Problem:** Endpoint phản chiếu nội dung target gần như nguyên vẹn.

**Why it happens:** Thiết kế test chú trọng convenience hơn security boundary.

**Production impact:** Có thể làm lộ dữ liệu nội bộ nếu SSRF xảy ra; body cũng có thể chứa secret hoặc content không phù hợp để hiển thị trực tiếp.

**Severity:** High

**Recommended fix:** Chỉ trả status, elapsed time, sanitized headers và preview giới hạn nếu cần.

### 9. Không giới hạn payload/config đầu vào

**Problem:** URL và secret không có length limit hay policy validation rõ ràng.

**Why it happens:** Chỉ dựa vào model binding và URI parser.

**Production impact:** Input quá lớn làm tăng allocation/logging cost và mở rộng attack surface.

**Severity:** Medium

**Recommended fix:** Áp model validation: length, allowed scheme, host requirements và secret policy.

### 10. Error handling thiếu phân loại

**Problem:** DNS failure, TLS error, timeout, refused connection và cancellation đều có thể trở thành lỗi 500 nếu không được xử lý phù hợp.

**Why it happens:** Không có mapping lỗi dependency thành domain/result rõ ràng.

**Production impact:** UX kém, alert noise và khó điều tra incident.

**Severity:** Medium

**Recommended fix:** Map timeout/DNS/TLS/network errors thành kết quả test có cấu trúc, log exception category nhưng không lộ secret.

## Phiên bản code đề xuất

```csharp
[HttpPost("test")]
[Authorize(Policy = "TenantAdmin")]
public async Task<IActionResult> TestAsync(
    TestWebhookRequest request,
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri) ||
        uri.Scheme != Uri.UriSchemeHttps)
    {
        return BadRequest("Only HTTPS webhook URLs are allowed.");
    }

    var validation = await _destinationValidator.ValidateAsync(
        uri,
        cancellationToken);

    if (!validation.IsAllowed)
        return BadRequest("Webhook destination is not allowed.");

    using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(
        cancellationToken);
    timeoutCts.CancelAfter(TimeSpan.FromSeconds(5));

    var payload = JsonSerializer.Serialize(new
    {
        type = "webhook.test",
        tenantId,
        requestedBy = User.FindFirst("sub")?.Value
    });

    using var message = new HttpRequestMessage(HttpMethod.Post, uri)
    {
        Content = new StringContent(payload, Encoding.UTF8, "application/json")
    };

    var started = Stopwatch.GetTimestamp();

    try
    {
        using var response = await _webhookHttpClient.SendAsync(
            message,
            HttpCompletionOption.ResponseHeadersRead,
            timeoutCts.Token);

        var preview = await ReadLimitedPreviewAsync(
            response.Content,
            maxBytes: 4096,
            timeoutCts.Token);

        return Ok(new
        {
            status = (int)response.StatusCode,
            elapsedMs = Stopwatch.GetElapsedTime(started).TotalMilliseconds,
            responsePreview = preview
        });
    }
    catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)
    {
        return StatusCode(StatusCodes.Status504GatewayTimeout, new
        {
            error = "Webhook target timed out."
        });
    }
    catch (HttpRequestException)
    {
        return BadRequest(new
        {
            error = "Webhook target could not be reached."
        });
    }
}
```

**Quan trọng:** `_destinationValidator` phải kiểm tra destination theo policy thực tế của môi trường, bao gồm DNS resolution/IP range và redirect strategy. Với hệ thống rủi ro cao, network-level egress control đáng tin cậy hơn việc chỉ kiểm tra trong application code.

## Trade-offs

- Allow-list domain cho security mạnh hơn nhưng giảm tính linh hoạt cho SaaS có nhiều customer endpoint.
- DNS/IP validation trong application phức tạp và có TOCTOU/DNS rebinding concerns; egress proxy/firewall là defense-in-depth tốt hơn.
- Disable redirect đơn giản và an toàn hơn, nhưng một số webhook provider hợp lệ có thể cần redirect; nếu hỗ trợ thì phải validate từng hop.
- Trả response preview hỗ trợ troubleshooting nhưng phải giới hạn kích thước và sanitize nội dung.

## Cách kiểm thử

1. **Security test:** thử `localhost`, `127.0.0.1`, `::1`, private CIDR, link-local và hostname resolve về private IP; tất cả phải bị chặn theo policy.
2. **Authorization test:** user tenant A gửi `TenantId` của tenant B hoặc không có quyền admin; phải bị từ chối.
3. **Redirect test:** public endpoint redirect sang private destination; client không được tự follow tới target bị cấm.
4. **Failure-path test:** DNS failure, TLS failure, connection refused, timeout và caller cancellation phải được phân loại đúng.
5. **Large-response test:** target trả response rất lớn; application chỉ đọc preview giới hạn và memory không tăng tuyến tính theo payload.

## Quan sát trong production

- Log sanitized: tenant id, destination host, result category, status code, elapsed time, trace id; không log query token/raw secret.
- Metric: webhook test count, timeout rate, blocked-destination count, DNS/TLS failure rate, latency p95/p99.
- Trace: outbound HTTP span với sanitized host và response status.
- Alert: blocked SSRF attempts tăng đột biến, timeout rate cao, outbound latency bất thường.
- Network observations: egress destination distribution và denied egress events nếu có firewall/proxy.

## Câu hỏi phỏng vấn mở rộng

1. Nếu customer bắt buộc dùng webhook trong private network qua VPN, bạn sẽ thay đổi architecture thế nào thay vì nới lỏng SSRF policy toàn cục?
2. Làm sao xử lý DNS rebinding khi application validate hostname trước rồi `HttpClient` resolve lại khi kết nối?
3. Nếu webhook secret phải được dùng để ký payload, bạn sẽ thiết kế key storage, rotation và audit như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Transaction boundary cần bám theo business atomicity, không nên kéo external side effect vào database transaction.
- Giảm round-trip và transaction duration thường giúp giảm lock contention, nhưng concurrency rule vẫn phải được thể hiện rõ bằng optimistic concurrency hoặc conditional update.
- Deadlock không chỉ là “database chậm”; lock order và transaction duration là hai yếu tố cần kiểm tra có hệ thống.
- Authentication không thay thế resource authorization, đặc biệt trong multi-tenant systems.
- Outbound HTTP với URL do user cung cấp phải được xem là một security boundary, không chỉ là một integration detail.
- SSRF defense cần kết hợp application validation và network-level egress control khi threat model yêu cầu.

## Mẫu tư duy cần nhớ

- Xác định transaction boundary trước khi tối ưu code.
- Tách database consistency khỏi external side effects bằng outbox khi cần reliability.
- Khi có deadlock, xem lock order + transaction duration + deadlock graph thay vì đoán.
- Treat every user-controlled URL as an outbound security boundary.
- Authentication answers “who are you”; authorization answers “are you allowed to act on this resource?”.
