# Code Review Challenge 1 — EF Core check-then-update làm oversell inventory khi checkout đồng thời

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, optimistic concurrency, transaction boundaries, inventory correctness  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một e-commerce API giữ số lượng tồn kho trong SQL Server. Mỗi checkout có thể chứa nhiều sản phẩm. Team muốn tránh bán vượt tồn kho nên trước khi tạo `Order`, service load từng `Product`, kiểm tra `Stock >= Quantity`, rồi trừ `Stock` và gọi `SaveChangesAsync`.

Production chạy nhiều application instances. Trong campaign, nhiều customer có thể checkout cùng SKU trong cùng vài milliseconds. Monitoring cho thấy thỉnh thoảng database còn `Stock = 0` nhưng tổng số lượng order thành công lớn hơn số stock ban đầu. Team đề xuất thêm một `lock` C# quanh method.

Bạn cần review implementation và xác định correctness boundary thực sự. Không giả định rằng một request chạy trong một `DbContext` hoặc một process-local `lock` sẽ serialize tất cả application instances.

## Đoạn code cần review

```csharp
public sealed class CheckoutService
{
    private readonly AppDbContext _db;
    private readonly ILogger<CheckoutService> _logger;

    public CheckoutService(
        AppDbContext db,
        ILogger<CheckoutService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<Guid> CheckoutAsync(
        Guid customerId,
        IReadOnlyList<CheckoutItem> items,
        CancellationToken cancellationToken)
    {
        var order = new Order
        {
            Id = Guid.NewGuid(),
            CustomerId = customerId,
            CreatedAtUtc = DateTime.UtcNow
        };

        foreach (var item in items)
        {
            var product = await _db.Products
                .SingleAsync(x => x.Id == item.ProductId, cancellationToken);

            if (product.Stock < item.Quantity)
                throw new InvalidOperationException("Insufficient stock");

            product.Stock -= item.Quantity;

            order.Items.Add(new OrderItem
            {
                ProductId = product.Id,
                Quantity = item.Quantity,
                UnitPrice = product.Price
            });
        }

        _db.Orders.Add(order);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Order {OrderId} created for {CustomerId}",
            order.Id,
            customerId);

        return order.Id;
    }
}
```

## Kết quả code review tham khảo

### Critical — Lost update có thể oversell inventory

**Vấn đề:** Hai request có thể cùng đọc một giá trị `Stock`, cùng vượt qua validation rồi cùng ghi state dựa trên snapshot đã đọc.

**Tại sao xảy ra:** Validation `product.Stock < item.Quantity` và mutation `product.Stock -= item.Quantity` không phải một atomic conditional operation ở database. Không có concurrency token hoặc predicate trên update chứng minh stock vẫn đủ tại thời điểm write.

**Ảnh hưởng production:** Nhiều order có thể được chấp nhận cho cùng lượng inventory. Giá trị cuối cùng trong row không phản ánh tổng số stock đã hứa cho customers.

**Cách sửa:** Bảo vệ invariant tại database boundary, ví dụ atomic conditional update `UPDATE ... SET Stock = Stock - @qty WHERE Id = @id AND Stock >= @qty`, kiểm tra affected rows, hoặc optimistic concurrency với token và retry/re-evaluate business condition. Chọn strategy dựa trên contention và transaction requirements.

### High — `lock` C# không giải quyết multi-instance concurrency

**Vấn đề:** Process-local synchronization chỉ serialize threads trong một process.

**Tại sao xảy ra:** Mỗi replica có memory và lock riêng.

**Ảnh hưởng production:** Fix có thể pass local tests nhưng vẫn oversell sau horizontal scaling.

**Cách sửa:** Đặt correctness control ở shared authoritative store. Distributed lock chỉ nên được cân nhắc khi thực sự cần và vẫn phải thiết kế failure/lease semantics; database invariant thường đơn giản hơn cho case này.

### High — Không có explicit business transaction design cho nhiều SKU

**Vấn đề:** Requirement chưa nói rõ checkout nhiều SKU phải all-or-nothing hay có thể reserve từng phần.

**Tại sao xảy ra:** Code dựa vào một `SaveChangesAsync`, nhưng design không mô tả reservation semantics, transaction duration hoặc failure handling khi một SKU hết hàng.

**Ảnh hưởng production:** Một bản sửa bằng nhiều conditional updates riêng lẻ có thể trừ một số SKU rồi fail ở SKU sau nếu không nằm trong transaction phù hợp.

**Cách sửa:** Nếu requirement là atomic order, thực hiện các inventory mutations và order persistence trong một database transaction có boundary rõ; rollback toàn bộ khi bất kỳ conditional update nào thất bại.

### High — Duplicate product IDs trong request có thể làm validation sai

**Vấn đề:** `items` có thể chứa cùng `ProductId` nhiều lần.

**Tại sao xảy ra:** Mỗi iteration kiểm tra/mutate tracked entity theo thứ tự, nhưng business validation không normalize input hoặc giới hạn quantity tổng cho SKU.

**Ảnh hưởng production:** Semantics phụ thuộc request shape; validation, pricing và limits dễ bị bypass hoặc khó reasoning.

**Cách sửa:** Validate positive quantities và group theo `ProductId` trước khi reservation; áp business limits trên tổng quantity.

### High — Không có idempotency boundary cho checkout retry

**Vấn đề:** Nếu client timeout sau commit rồi retry request, method tạo `Order.Id` mới.

**Tại sao xảy ra:** Không có stable checkout/idempotency key từ logical operation.

**Ảnh hưởng production:** Duplicate order và duplicate inventory decrement có thể xảy ra dù concurrency control trên từng row hoàn hảo.

**Cách sửa:** Nếu API contract cần safe retry, dùng stable operation identity/idempotency record với unique constraint và return/reconcile outcome của operation cũ.

### Medium — N+1 database round trips cho products

**Vấn đề:** Mỗi item gọi `SingleAsync` riêng.

**Tại sao xảy ra:** Query nằm trong loop.

**Ảnh hưởng production:** Checkout lớn tăng latency và DB round trips; dưới load làm contention/resource usage xấu hơn.

**Cách sửa:** Normalize IDs và load dữ liệu cần thiết theo batch, hoặc dùng set-based conditional updates phù hợp design. Không tối ưu theo cách làm mất concurrency correctness.

### Medium — Input quantity không được validate

**Vấn đề:** `Quantity <= 0` không bị chặn.

**Tại sao xảy ra:** Code chỉ kiểm tra stock nhỏ hơn quantity.

**Ảnh hưởng production:** Quantity âm có thể làm tăng stock và tạo order data sai nếu validation không tồn tại ở layer khác.

**Cách sửa:** Validate request ở API/application boundary và bổ sung database constraints phù hợp cho invariant quan trọng.

### Medium — Exception type không biểu diễn business conflict tốt

**Vấn đề:** `InvalidOperationException` cho insufficient stock không tạo contract HTTP rõ ràng.

**Tại sao xảy ra:** Infrastructure exception và business outcome bị trộn.

**Ảnh hưởng production:** Có thể bị map thành `500`, gây retry sai và telemetry nhiễu.

**Cách sửa:** Dùng domain/application result hoặc exception có mapping rõ sang response phù hợp, ví dụ conflict/business validation tùy API contract.

### Medium — Pricing snapshot chưa có requirement rõ

**Vấn đề:** `UnitPrice = product.Price` lấy giá tại checkout nhưng không có version/currency/promotion semantics.

**Tại sao xảy ra:** Inventory và pricing được coi như một concern dù lifecycle có thể khác.

**Ảnh hưởng production:** Khi giá thay đổi đồng thời hoặc price đến từ external system, order có thể không phản ánh price mà customer đã xác nhận.

**Cách sửa:** Làm rõ pricing contract; persist immutable price snapshot đã được authoritative validation tại checkout.

## Phiên bản đề xuất

Ví dụ dưới đây giả định SQL Server, toàn bộ order phải atomic, quantity đã normalize theo SKU, và application chấp nhận conditional SQL update để giữ invariant tại database. Production code cần mapping/table naming phù hợp model thực tế.

```csharp
public async Task<Guid> CheckoutAsync(
    Guid customerId,
    IReadOnlyList<CheckoutItem> items,
    CancellationToken cancellationToken)
{
    var normalized = items
        .GroupBy(x => x.ProductId)
        .Select(g => new
        {
            ProductId = g.Key,
            Quantity = g.Sum(x => x.Quantity)
        })
        .ToArray();

    if (normalized.Length == 0 || normalized.Any(x => x.Quantity <= 0))
        throw new CheckoutValidationException("Invalid items");

    await using var tx = await _db.Database
        .BeginTransactionAsync(cancellationToken);

    var ids = normalized.Select(x => x.ProductId).ToArray();
    var products = await _db.Products
        .AsNoTracking()
        .Where(x => ids.Contains(x.Id))
        .ToDictionaryAsync(x => x.Id, cancellationToken);

    if (products.Count != ids.Length)
        throw new CheckoutValidationException("Unknown product");

    foreach (var item in normalized.OrderBy(x => x.ProductId))
    {
        var affected = await _db.Database.ExecuteSqlInterpolatedAsync($@
            UPDATE Products
            SET Stock = Stock - {item.Quantity}
            WHERE Id = {item.ProductId}
              AND Stock >= {item.Quantity};",
            cancellationToken);

        if (affected != 1)
            throw new InsufficientStockException(item.ProductId);
    }

    var order = new Order
    {
        Id = Guid.NewGuid(),
        CustomerId = customerId,
        CreatedAtUtc = DateTime.UtcNow,
        Items = normalized.Select(x => new OrderItem
        {
            ProductId = x.ProductId,
            Quantity = x.Quantity,
            UnitPrice = products[x.ProductId].Price
        }).ToList()
    };

    _db.Orders.Add(order);
    await _db.SaveChangesAsync(cancellationToken);
    await tx.CommitAsync(cancellationToken);

    return order.Id;
}
```

Nếu retry-safe checkout là requirement, cần thêm stable idempotency key và unique persistence boundary; đoạn code trên chỉ minh họa inventory concurrency invariant, không tự giải quyết duplicate logical checkout.

## Giải thích thiết kế sau khi sửa

Điểm quan trọng nhất là chuyển từ “đọc rồi tin rằng giá trị chưa đổi” sang conditional mutation tại authoritative database. `Stock >= quantity` được kiểm tra cùng statement làm decrement, nên affected-row count trở thành evidence rằng reservation thành công.

Transaction bao toàn bộ SKU mutations và order insert nếu business yêu cầu all-or-nothing. Việc sort SKU IDs có thể giúp tạo lock acquisition order ổn định hơn, nhưng không được coi là bảo đảm tuyệt đối rằng deadlock không thể xảy ra; deadlock vẫn cần telemetry và retry policy phù hợp.

Một lựa chọn khác là EF Core optimistic concurrency token (`rowversion`) rồi bắt `DbUpdateConcurrencyException`, reload và re-evaluate stock. Cách đó giữ abstraction EF tốt hơn nhưng dưới hot-SKU contention có thể tạo nhiều retries. Pessimistic locking cũng có thể hợp lệ trong một số workload nhưng làm tăng blocking. Cần đo contention trước khi chọn.

## Trade-offs

Atomic conditional update giảm race window nhưng đưa một phần persistence logic gần SQL hơn. Optimistic concurrency giữ model EF tự nhiên hơn nhưng có retry cost. Transaction nhiều SKU tăng correctness nhưng giữ locks lâu hơn. Reservation workflow tách riêng có thể phù hợp khi checkout kéo dài qua payment/external services, nhưng làm state machine và expiration/reconciliation phức tạp hơn.

Không nên giữ database transaction mở qua network call tới payment provider. Nếu inventory cần được giữ trong lúc payment diễn ra, nên thiết kế reservation có expiry/confirmation thay vì kéo dài SQL transaction qua external dependency.

## Cách kiểm thử

1. **Concurrency database test:** khởi tạo `Stock = 10`, chạy đồng thời 50 checkout mỗi request mua 1; tổng order success phải đúng 10 và stock không âm.
2. **Integration test:** order có nhiều SKU, một SKU thiếu stock; nếu contract all-or-nothing thì không SKU nào bị decrement và không order nào được commit.
3. **Failure-path test:** inject failure sau một conditional decrement nhưng trước `SaveChanges`; transaction rollback phải phục hồi inventory.
4. **API/idempotency test:** nếu contract hỗ trợ retry-safe checkout, gửi cùng operation key đồng thời/nhiều lần và chứng minh chỉ một logical order/decrement tồn tại.
5. **Load test:** hot SKU contention để đo latency, deadlocks, lock waits và retry rate trước khi chọn optimistic/pessimistic strategy.

## Quan sát trong production

Theo dõi checkout success/conflict rate, insufficient-stock rate, conditional-update affected-row failures, SQL deadlocks, lock waits, transaction duration, DB latency, hot SKU distribution và invariant audit `available/reserved/sold`. Correlate order ID, checkout operation ID và SKU IDs trong structured logs nhưng tránh customer-sensitive data. Alert khi inventory reconciliation phát hiện sold quantity vượt authoritative stock/reservation history.

## Câu hỏi phỏng vấn mở rộng

1. Nếu payment mất 30 giây, bạn có giữ SQL transaction/reservation lock trong 30 giây không? Thiết kế nào tốt hơn?
2. `rowversion` optimistic concurrency và atomic conditional update khác nhau thế nào dưới một hot SKU có hàng nghìn concurrent buyers?
3. Nếu checkout request timeout sau database commit, idempotency design nào ngăn retry tạo order thứ hai?

# Code Review Challenge 2 — Kubernetes probes biến downstream outage thành restart storm

## Bối cảnh

Một ASP.NET Core API được deploy lên Kubernetes với 12 replicas. API phụ thuộc SQL Server và một third-party pricing API. Team tạo endpoint `/health` kiểm tra cả hai dependencies rồi dùng cùng endpoint cho `livenessProbe` và `readinessProbe`.

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc pricing API nên dependency outage gây restart storm

**Vấn đề:** `/health` fail khi pricing provider fail, và endpoint đó được dùng cho `livenessProbe`.

**Tại sao xảy ra:** Liveness đang trả lời sức khỏe của dependency thay vì khả năng sống của process.

**Ảnh hưởng production:** Kubernetes restart pods dù restart không chữa được external outage. 12 replicas có thể cùng churn, làm mất warm state, tăng startup traffic, logs, CPU và áp lực lên SQL/dependencies.

**Cách sửa:** Tạo liveness check tối thiểu, không phụ thuộc remote services, chỉ fail khi process ở trạng thái restart có khả năng khắc phục. Tách readiness/dependency checks bằng tags/endpoints hoặc predicate phù hợp.

### High — Cùng một endpoint cho liveness và readiness làm mất semantics

**Vấn đề:** Hai probes có mục tiêu khác nhau nhưng nhận cùng aggregate status.

**Tại sao xảy ra:** Health checks không được phân loại theo purpose.

**Ảnh hưởng production:** Một dependency issue có thể vừa remove pod khỏi traffic vừa restart nó; troubleshooting khó vì signal không nói failure category.

**Cách sửa:** Map `/health/live` và `/health/ready` riêng. Tag checks theo dependency/criticality và dùng predicate để chọn checks cho từng endpoint.

### High — Readiness của pricing dependency chưa dựa trên business degradation contract

**Vấn đề:** Code mặc định pricing unavailable nghĩa là toàn API không nên nhận traffic.

**Tại sao xảy ra:** Technical dependency được coi là critical mà chưa xác minh endpoint behavior.

**Ảnh hưởng production:** Nếu API có thể phục vụ catalog với stale price/partial response, tất cả pods bị unready sẽ gây total outage không cần thiết. Ngược lại, nếu pricing là bắt buộc để bảo đảm correctness, giữ pod ready có thể trả dữ liệu sai.

**Cách sửa:** Làm rõ service contract. Chỉ đưa dependency vào readiness nếu pod thực sự không thể phục vụ traffic hợp lệ khi dependency đó fail; nếu có degradation/fallback, expose dependency metric/status riêng thay vì làm toàn pod unready.

### High — Giảm `failureThreshold` xuống 1 sẽ tăng sensitivity và churn

**Vấn đề:** Một transient timeout đủ trigger probe failure ngay.

**Tại sao xảy ra:** Probe cadence/timeout/failure threshold không được chọn theo startup/network characteristics.

**Ảnh hưởng production:** False-positive restarts/removal tăng trong network jitter hoặc GC/CPU pressure.

**Cách sửa:** Chọn thresholds từ measured behavior và desired detection window; không dùng “fail fast” như mục tiêu độc lập.

### High — Không có `startupProbe` cho startup có thể biến chậm khởi động thành liveness failure

**Vấn đề:** Liveness bắt đầu sau 5 giây bất kể startup thực tế.

**Tại sao xảy ra:** `initialDelaySeconds` là fixed delay và không tách startup semantics.

**Ảnh hưởng production:** Pod có startup lâu hơn dự kiến có thể bị kill trước khi hoàn tất, tạo crash/restart loop.

**Cách sửa:** Nếu startup có thể đáng kể/biến thiên, dùng `startupProbe` với budget phù hợp; sau khi startup probe success mới để liveness/readiness đảm nhiệm lifecycle tương ứng.

### Medium — Probe tới remote dependencies có thể tự tạo synchronized load

**Vấn đề:** 12 pods gọi dependency mỗi 5 giây qua health endpoint.

**Tại sao xảy ra:** Mỗi readiness/liveness invocation có thể thực hiện network check, và hai probes cùng endpoint làm số lần kiểm tra tăng.

**Ảnh hưởng production:** Trong degradation, health checks góp thêm traffic/timeout work và có thể khuếch đại incident.

**Cách sửa:** Chỉ check dependency nơi có giá trị; chọn cadence/timeout hợp lý, cân nhắc cached/internal readiness state nếu cần nhưng tránh che giấu stale health quá lâu.

### Medium — Resource requests/limits không có evidence

**Vấn đề:** `100m/128Mi` requests và `200m/256Mi` limits xuất hiện như magic numbers.

**Tại sao xảy ra:** Không có profiling/working-set/CPU percentile evidence trong scenario.

**Ảnh hưởng production:** CPU throttling hoặc OOMKill có thể bị nhầm với application bug; requests quá thấp cũng ảnh hưởng scheduling/capacity planning.

**Cách sửa:** Chọn từ measured steady-state/burst behavior, GC memory, load tests và production telemetry; monitor throttling/OOM/restarts.

### Medium — Không có graceful termination context

**Vấn đề:** Manifest không thể hiện `terminationGracePeriodSeconds`, `preStop` hoặc application shutdown behavior.

**Tại sao xảy ra:** Deployment review chỉ tập trung probes.

**Ảnh hưởng production:** Rolling update/restart có thể cắt request hoặc background work nếu application cần drain.

**Cách sửa:** Xác minh ASP.NET Core shutdown behavior, request duration/background work và thiết lập termination budget phù hợp. Không thêm hook máy móc nếu application không cần.

### Medium — Health endpoint không cung cấp đủ operational classification

**Vấn đề:** Aggregate health response không giúp phân biệt SQL failure, pricing failure hay process issue trong telemetry.

**Tại sao xảy ra:** Probe result được dùng như binary signal duy nhất.

**Ảnh hưởng production:** Incident responders thấy pod unhealthy nhưng khó xác định blast radius/root cause.

**Cách sửa:** Structured telemetry/metrics cho từng dependency và probe outcome; bảo vệ health detail khỏi lộ sensitive infrastructure information ra public network.

## Phiên bản đề xuất

Một cách tách health checks trong ASP.NET Core:

```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(
        builder.Configuration.GetConnectionString("Default")!,
        name: "sql",
        tags: new[] { "ready", "critical" })
    .AddUrlGroup(
        new Uri(builder.Configuration["PricingApi:HealthUrl"]!),
        name: "pricing",
        tags: new[] { "dependency" });

var app = builder.Build();

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = _ => false
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

app.MapControllers();
app.Run();
```

Ví dụ manifest, với các giá trị threshold chỉ là starting assumptions cần được validate bằng startup/load/production measurements:

```yaml
containers:
  - name: catalog-api
    image: registry.example/catalog-api:2026.09.21
    ports:
      - containerPort: 8080

    startupProbe:
      httpGet:
        path: /health/live
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 12

    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3

    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 3
```

Trong ví dụ này SQL được giả định là dependency critical cho request contract, còn pricing được giả định có degradation path và vì vậy không gate readiness. Nếu requirement thực tế nói không request nào có thể được phục vụ đúng khi pricing unavailable, quyết định readiness phải thay đổi. Reference design không được dùng để che requirement đó.

## Giải thích thiết kế sau khi sửa

`/health/live` không gọi remote dependency. Nó chứng minh HTTP process có thể phản hồi; nếu application có một internal fatal-state signal đáng tin cậy, có thể bổ sung nhưng chỉ khi restart có ý nghĩa.

`/health/ready` kiểm tra dependencies cần thiết để instance nhận traffic hợp lệ. “Critical” phải đến từ business/service contract chứ không phải vì dependency tồn tại trong architecture.

`startupProbe` tạo startup budget riêng. Điều này đặc biệt hữu ích khi startup có thể vượt liveness window do cold start, migrations không nên chạy đồng thời, cache warm-up hoặc infrastructure variability. Tuy nhiên startup probe không phải lý do để cho phép startup vô hạn; cần đo và alert startup regression.

Pricing dependency vẫn phải observable dù không gate readiness. Application có thể dùng timeout/circuit breaker/fallback phù hợp contract; health probes không thay thế resilience design trong request path.

## Trade-offs

Tách probes tăng configuration nhưng giảm coupling giữa failure domains. Readiness phụ thuộc SQL giúp tránh gửi request vào pod không thể phục vụ dữ liệu, nhưng nếu toàn cluster mất SQL thì tất cả pods có thể unready; điều đó có thể đúng với contract nhưng cần hiểu ingress behavior và incident UX.

Không gate readiness theo pricing giữ API online khi provider fail, nhưng chỉ hợp lệ nếu application có safe degradation. Caching stale prices có thể là unacceptable trong checkout dù chấp nhận được ở browse page; readiness/degradation có thể cần phân biệt endpoint/use case thay vì một policy đơn giản cho toàn service.

## Cách kiểm thử

1. **Failure-injection test:** làm pricing endpoint timeout 90 giây; pod không được liveness restart nếu process vẫn khỏe, và user behavior phải đúng degradation contract.
2. **Integration/deployment test:** làm SQL unavailable; xác nhận readiness chuyển trạng thái theo requirement nhưng liveness không restart-loop.
3. **Startup test:** artificial slow startup vượt 5 giây nhưng nằm trong startup budget; container không bị kill trước khi ready.
4. **Rolling deployment validation:** deploy khi traffic đang chạy; theo dõi unavailable replicas, failed requests, termination/drain behavior và rollback criteria.
5. **Load/resource test:** đo CPU throttling, working set/GC, OOM events và latency để hiệu chỉnh requests/limits/probe timeout thay vì dùng magic numbers.

## Quan sát trong production

Theo dõi pod restart count/reason, readiness transitions, startup duration, probe latency/failures, SQL dependency latency/error, pricing dependency latency/error, request p95/p99, 5xx, CPU throttling, memory working set/OOMKill và replica availability. Correlate incident timeline giữa external dependency degradation và pod lifecycle. Alert riêng cho dependency outage và restart storm để tránh coi restart là root cause khi nó chỉ là amplifier.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL outage làm toàn bộ pods unready, khi nào đó là hành vi đúng và khi nào bạn muốn service vẫn ready với degraded endpoints?
2. Một liveness endpoint chỉ trả `200` từ ASP.NET Core pipeline có phát hiện được mọi deadlock/starvation không? Bạn cân bằng false positive và detection thế nào?
3. Nếu pricing API recovery nhưng 12 pods đồng thời reconnect/warm cache, bạn giảm recovery stampede ở layer nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Correctness dưới concurrency phải được bảo vệ tại shared authoritative boundary; process-local synchronization không đủ cho multi-instance systems.
- Database transaction không tự động ngăn check-then-act race; cần hiểu statement/concurrency semantics thực tế bảo vệ invariant nào.
- Retry-safe business operation cần stable identity riêng với row-level concurrency correctness.
- Kubernetes liveness, readiness và startup là ba signal khác nhau; dependency outage không mặc định là lý do restart process.
- Health checks phải phản ánh service contract và failure domains, không chỉ “ping mọi dependency”.

## Mẫu tư duy cần nhớ

- Đưa invariant về nơi mọi concurrent actors cùng nhìn thấy và enforce được.
- Phân biệt logical-operation idempotency với database concurrency control.
- Failure của dependency không đồng nghĩa failure của process.
- Đo contention, startup và resource behavior trước khi chọn threshold/locking strategy.
- Test failure path và multi-instance behavior, không chỉ happy path trên local.
