# Code Review Challenge 1 — Cosmos DB hot partition trong dịch vụ audit đa tenant

## Bối cảnh

Một SaaS audit portal chạy trên Azure App Service, lưu sự kiện vào Cosmos DB for NoSQL. Container `audit` có partition key `/tenantId`; document có `id`, `tenantId`, `actorId`, `eventType`, `occurredAt`, `payload`. Một tenant lớn phát sinh 2 triệu events/ngày, còn tenant nhỏ vài trăm. API hiển thị lịch sử gần nhất theo actor; người dùng chỉ được đọc tenant mình được cấp quyền. Production xuất hiện 429, p95 tăng, vài trang trả sự kiện lặp. UI cần phân trang ổn định, tối đa 100 records/lần; giữ dữ liệu 90 ngày. Đoạn code dưới đây đã chạy được và dùng SDK Cosmos DB.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly Container _container;
    public AuditController(CosmosClient client)
        => _container = client.GetContainer("operations", "audit");

    [HttpGet]
    public async Task<IActionResult> List(
        [FromQuery] string tenantId,
        [FromQuery] string actorId,
        [FromQuery] int page = 1,
        [FromQuery] int size = 100)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.tenantId = @tenant " +
            "AND c.actorId = @actor ORDER BY c.occurredAt DESC")
            .WithParameter("@tenant", tenantId)
            .WithParameter("@actor", actorId);

        var options = new QueryRequestOptions
        {
            MaxItemCount = 100
        };
        var iterator = _container.GetItemQueryIterator<AuditEvent>(
            query, requestOptions: options);

        var all = new List<AuditEvent>();
        while (iterator.HasMoreResults)
        {
            var response = await iterator.ReadNextAsync();
            all.AddRange(response);
        }

        return Ok(new
        {
            items = all.Skip((page - 1) * size).Take(size),
            total = all.Count
        });
    }

    [HttpPost]
    public async Task<IActionResult> Write(AuditEvent entry)
    {
        entry.Id = Guid.NewGuid().ToString("N");
        entry.OccurredAt = DateTimeOffset.UtcNow;
        await _container.CreateItemAsync(
            entry, new PartitionKey(entry.TenantId));
        return Accepted(new { entry.Id });
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Broken tenant-level authorization

**Vấn đề:** `[Authorize]` chỉ xác thực, không chứng minh user được đọc `tenantId` trong query hoặc ghi vào tenant của payload.  
**Tại sao xảy ra:** Tin dữ liệu client thay vì tenant membership đã xác minh server-side.  
**Ảnh hưởng production:** Cross-tenant data exposure hoặc ghi audit giả.  
**Cách sửa:** Policy/tenant access service kiểm tra cả read/write, tenant ID từ authenticated context hoặc explicit membership validation; audit hành vi từ chối.

### [High] — Unbounded query materialization

**Vấn đề:** `while (HasMoreResults)` đọc toàn bộ matching documents.  
**Tại sao xảy ra:** `MaxItemCount` chỉ giới hạn số items mong muốn mỗi SDK page, không giới hạn tổng số pages.  
**Ảnh hưởng production:** RU và allocation tăng theo lịch sử, request timeout, memory pressure.  
**Cách sửa:** Trả một trang từ iterator với continuation token, giới hạn page size và không tính total bằng cách load tất cả.

### [High] — Hot logical partition và throughput concentration

**Vấn đề:** `/tenantId` gom tenant lớn vào một logical partition.  
**Tại sao xảy ra:** Workload ghi của tenant có thể vượt khả năng phục vụ của logical partition; nguyên nhân 429 cụ thể phải xác minh từ diagnostics.  
**Ảnh hưởng production:** Throttling, tail latency, bất cân xứng tenant.  
**Cách sửa:** Đo RU, 429 và key distribution; nếu cần, đánh giá synthetic bucket `tenantId|bucket` cho dữ liệu mới, với fan-out read, backfill và migration cost. Không đổi key mù quáng.

### [High] — Pagination không ổn định

**Vấn đề:** Offset `Skip` sau khi tải tất cả, thiếu tie-breaker; events cùng timestamp hoặc writes mới gây duplicate/missing giữa requests.  
**Tại sao xảy ra:** Order key không unique và mỗi request chạy trên tập dữ liệu thay đổi.  
**Ảnh hưởng production:** UI bỏ sót hoặc lặp audit events.  
**Cách sửa:** Continuation token cho query cùng filter/order; document rõ rằng không cung cấp snapshot xuyên nhiều requests; khi yêu cầu snapshot mạnh cần thiết kế riêng.

### [Medium] — Thiếu validation và bounded inputs

**Vấn đề:** `page`, `size`, `tenantId`, `actorId` chưa validate; `Skip((page-1)*size)` có thể overflow.  
**Tại sao xảy ra:** Không enforce API limits.  
**Ảnh hưởng production:** 500, truy vấn vô ích, resource abuse.  
**Cách sửa:** Validate actor, size 1–100, token length, tenant access và return 400.

### [Medium] — Không propagate cancellation

**Vấn đề:** Cosmos calls không nhận `HttpContext.RequestAborted`.  
**Tại sao xảy ra:** Request đã hủy vẫn có thể tiêu thụ tài nguyên.  
**Ảnh hưởng production:** Work thừa khi client disconnect.  
**Cách sửa:** Truyền `CancellationToken` đến SDK.

### [Medium] — Query payload quá rộng

**Vấn đề:** `SELECT *` trả `payload` có thể lớn.  
**Tại sao xảy ra:** UI list không cần toàn bộ dữ liệu.  
**Ảnh hưởng production:** RU/network/serialization tăng, nguy cơ lộ fields không cần thiết.  
**Cách sửa:** Projection DTO với fields tối thiểu; detail endpoint riêng có authorization.

### [Medium] — Retention và index strategy chưa xác định

**Vấn đề:** Không có evidence cho TTL 90 ngày và composite index cho `actorId` + `occurredAt`.  
**Tại sao xảy ra:** Cấu hình container/index không thể suy ra từ controller.  
**Ảnh hưởng production:** Dữ liệu tồn lâu hơn chính sách, truy vấn có thể tốn RU hoặc bị từ chối tùy indexing policy.  
**Cách sửa:** Kiểm tra TTL và index policy thực tế, benchmark bằng query metrics trước khi thêm index.

## Phiên bản đề xuất

Giả định partition key hiện tại vẫn là `/tenantId`; `ITenantAccess` xác minh membership từ dữ liệu tin cậy. DTO không chứa payload. Dưới đây là phần read path minh họa; write path phải áp dụng cùng authorization, server-owned fields và validation.

```csharp
public sealed record AuditListItem(
    string Id, string ActorId, string EventType,
    DateTimeOffset OccurredAt);
public sealed record AuditPage(
    IReadOnlyList<AuditListItem> Items, string? NextToken);

[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController(
    Container container, ITenantAccess access) : ControllerBase
{
    [HttpGet]
    public async Task<ActionResult<AuditPage>> List(
        [FromQuery] string tenantId,
        [FromQuery] string actorId,
        [FromQuery] string? continuation,
        [FromQuery] int size = 50,
        CancellationToken ct = default)
    {
        if (string.IsNullOrWhiteSpace(tenantId) ||
            string.IsNullOrWhiteSpace(actorId) ||
            size is < 1 or > 100 ||
            continuation?.Length > 8192)
            return BadRequest();

        if (!await access.CanReadAsync(User, tenantId, ct))
            return Forbid();

        var q = new QueryDefinition(
            "SELECT c.id AS Id, c.actorId AS ActorId, " +
            "c.eventType AS EventType, c.occurredAt AS OccurredAt " +
            "FROM c WHERE c.tenantId = @t AND c.actorId = @a " +
            "ORDER BY c.occurredAt DESC, c.id DESC")
            .WithParameter("@t", tenantId)
            .WithParameter("@a", actorId);

        var iterator = container.GetItemQueryIterator<AuditListItem>(
            q, continuation,
            new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(tenantId),
                MaxItemCount = size
            });

        var response = await iterator.ReadNextAsync(ct);
        return Ok(new AuditPage(
            response.ToList(), response.ContinuationToken));
    }
}
```

**Điều kiện triển khai:** Query cần index hỗ trợ ORDER BY nhiều thuộc tính; xác minh indexing policy và dữ liệu serialized đúng tên field. Continuation token là opaque: trong hệ thống thật cần ràng buộc token với user/tenant/filter và có thể ký/encrypt envelope ở API boundary; không tin token do client tự chỉnh. Cosmos SDK có thể trả trang ít hơn size (kể cả rỗng) và còn token; UI phải dựa vào `NextToken`, không dựa vào `Items.Count`. Tránh dùng `total` trừ khi có use case và phương án count được đo chi phí. Write endpoint cần `CreateItemAsync` với tenant đã được xác thực, server-generated ID/time, giới hạn payload và chiến lược duplicate/idempotency riêng.

## Giải thích thiết kế sau khi sửa

Server kiểm tra tenant authorization trước khi query; query chỉ đọc partition tương ứng và projection nhỏ. Cursor giảm việc quét lặp lại toàn bộ lịch sử, nhưng không cam kết snapshot consistency giữa các request. Phân tách read optimization khỏi quyết định repartition — quyết định sau cần dữ liệu telemetry và migration plan.

## Trade-offs

- Continuation token làm API/UI phức tạp hơn offset, không hỗ trợ nhảy tới page 500 trực tiếp.
- Composite index và nhiều buckets có storage/index write cost; fan-out query khó hơn và cần merge order.
- Không trả `total` giảm RU nhưng UI mất số trang chính xác.
- TTL hỗ trợ retention nhưng cần xác minh chính sách lưu trữ, legal hold và thời điểm xóa thực tế.

## Cách kiểm thử

1. **Security integration:** User tenant A thử read/write tenant B; phải bị từ chối, không phát sinh Cosmos query/write không được phép.
2. **Database integration:** 250 documents, page size 40, duyệt hết continuation; kiểm tra không bỏ sót trong tập dữ liệu tĩnh, kể cả timestamp trùng.
3. **Concurrency:** Ghi events mới giữa các page; xác nhận semantics đã công bố, không giả định snapshot.
4. **Load:** Benchmark RU/request, p95, memory với tenant lớn; kiểm tra hot partition và retry/429.
5. **Failure-path:** Client cancel, Cosmos 429/timeout; API trả lỗi phù hợp, không lặp work vô hạn.

## Quan sát trong production

Application Insights dependency traces: duration, status, Cosmos diagnostics và correlation ID; metric RU per request, 429, retry count, p95/p99, query page size, request cancellation. Dashboard theo tenant ở mức aggregated/hashed, tránh log payload audit hoặc token. Kiểm tra hot partition và indexing metrics trong Azure Monitor; alert theo throttling và error budget.

```tsx
type Order = {
  id: string;
  tenantId: string;
  total: number;
  status: string;
};
type Result = { items: Order[]; total: number };

export function OrdersPanel({
  tenantId,
  token
}: { tenantId: string; token: string }) {
  const [status, setStatus] = React.useState("all");
  const [rows, setRows] = React.useState<Order[]>([]);
  const [total, setTotal] = React.useState(0);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  async function loadOrders() {
    setLoading(true);
    const url = "/api/orders?tenantId=" + tenantId +
      "&status=" + status;
    try {
      const response = await fetch(url, {
        headers: { Authorization: "Bearer " + token }
      });
      const result: Result = await response.json();
      setRows(result.items);
      setTotal(result.total);
      setError("");
    } catch (e) {
      setError("Không thể tải đơn hàng");
    } finally {
      setLoading(false);
    }
  }

  React.useEffect(() => {
    loadOrders();
  }, [tenantId, status]);

  return <section>
    <select value={status}
      onChange={e => setStatus(e.target.value)}>
      <option value="all">Tất cả</option>
      <option value="paid">Đã thanh toán</option>
      <option value="pending">Chờ xử lý</option>
    </select>
    {loading && <p>Đang tải...</p>}
    {error && <p role="alert">{error}</p>}
    <strong>Tổng: {total}</strong>
    <ul>{rows.map(x => <li key={x.id}>
      {x.id}: {x.status} — {x.total}
    </li>)}</ul>
  </section>;
}
```

## Kết quả code review tham khảo

### [High] — Stale response ghi đè filter mới

**Vấn đề:** Request cũ có thể hoàn tất sau request mới và gọi `setRows`/`setTotal`.  
**Tại sao xảy ra:** Không có cleanup, cancellation hoặc guard theo request identity.  
**Ảnh hưởng production:** Admin nhìn thấy đơn hàng tenant/status không khớp filter hiện tại.  
**Cách sửa:** `AbortController` trong effect và ignore stale completion; clear stale rows khi context đổi.

### [High] — Không kiểm tra HTTP status

**Vấn đề:** `fetch` resolve cả 401/403/500; `response.json()` có thể parse error payload như `Result`.  
**Tại sao xảy ra:** Nhầm HTTP error với network exception.  
**Ảnh hưởng production:** UI lỗi runtime hoặc dữ liệu không hợp lệ.  
**Cách sửa:** Kiểm tra `response.ok`, xử lý 401/403 riêng, validate response shape ở trust boundary.

### [High] — Authentication context không nằm trong effect dependencies

**Vấn đề:** Token đổi nhưng effect không chạy lại.  
**Tại sao xảy ra:** Closure dùng `token` nhưng dependency thiếu.  
**Ảnh hưởng production:** Hiển thị dữ liệu user cũ sau switch account/session.  
**Cách sửa:** Dependency bao gồm token/auth context; clear dữ liệu khi thay account; server luôn enforce tenant authorization.

### [Medium] — Loading state có race

**Vấn đề:** `finally` của request cũ có thể đặt loading=false khi request mới còn chạy.  
**Tại sao xảy ra:** Nhiều asynchronous calls điều khiển cùng state.  
**Ảnh hưởng production:** Spinner biến mất sớm, UX gây hiểu lầm.  
**Cách sửa:** Chỉ request active mới được cập nhật state.

### [Medium] — Error state có race

**Vấn đề:** Request cũ thất bại sau request mới thành công, ghi lỗi không còn phù hợp.  
**Tại sao xảy ra:** Không gắn error với request identity.  
**Ảnh hưởng production:** False alarm, hỗ trợ vận hành khó chẩn đoán.  
**Cách sửa:** Bỏ qua lỗi từ aborted/stale requests; phân biệt lỗi HTTP với network.

### [Medium] — Query parameters chưa encode

**Vấn đề:** Ghép chuỗi trực tiếp cho `tenantId` và `status`.  
**Tại sao xảy ra:** Không dùng `URLSearchParams`.  
**Ảnh hưởng production:** Filter có ký tự đặc biệt có thể bị parse sai.  
**Cách sửa:** Encode parameters bằng URLSearchParams.

### [Medium] — Thiếu runtime response validation và stale-data policy

**Vấn đề:** TypeScript annotation không kiểm chứng JSON; rows cũ còn hiển thị khi tenant đổi.  
**Tại sao xảy ra:** Không có schema check hoặc chính sách loading state.  
**Ảnh hưởng production:** Crash hoặc data context confusion.

```tsx
type Order = {
  id: string; tenantId: string; total: number; status: string
};
type Result = { items: Order[]; total: number };

function isResult(value: unknown): value is Result {
  if (!value || typeof value !== "object") return false;
  const x = value as Record<string, unknown>;
  return typeof x.total === "number" &&
    Array.isArray(x.items) &&
    x.items.every(item => {
      if (!item || typeof item !== "object") return false;
      const o = item as Record<string, unknown>;
      return typeof o.id === "string" &&
        typeof o.tenantId === "string" &&
        typeof o.status === "string" &&
        typeof o.total === "number";
    });
}

        });
        if (!response.ok)
          throw new Error("HTTP " + response.status);
        const json: unknown = await response.json();
        if (!isResult(json)) throw new Error("Invalid response");
        if (active) setView({
          key, rows: json.items, total: json.total, error: ""
        });
      } catch (err) {
        if (active && !controller.signal.aborted)
          setView({
            key, rows: [], total: 0,
            error: err instanceof Error ? err.message : "Network error"
          });
      } finally {
        if (active) setPendingKey("");
      }
    }
    void run();
    return () => {
      active = false;
      controller.abort();
    };
  }, [tenantId, status, token, key]);

  const current = view?.key === key ? view : null;
  const loading = pendingKey === key || !current;
  return <section>
    <select value={status}
      onChange={e => setStatus(e.target.value)}>
      <option value="all">Tất cả</option>
      <option value="paid">Đã thanh toán</option>
      <option value="pending">Chờ xử lý</option>
    </select>
    {loading && <p>Đang tải...</p>}
    {current?.error && <p role="alert">
      Không thể tải đơn hàng ({current.error})
    </p>}
    {!loading && !current?.error && current && <>
      <strong>Tổng: {current.total}</strong>
      <ul>{current.rows.map(x =>
        <li key={x.id}>{x.id}: {x.status} — {x.total}</li>
      )}</ul>
    </>}
  </section>;
}
```

**Lưu ý:** Ví dụ dùng token trong `key` để làm rõ invalidation; production không nên đưa token vào log, analytics, DOM hoặc cache key được lưu bền. Thực tế nên dùng auth session identity/version không nhạy cảm. Khi API trả 401/403, hiển thị thông báo thân thiện thay vì raw status; không lộ server error body. Có thể dùng TanStack Query nếu ứng dụng đã có, nhưng không bắt buộc thêm dependency chỉ cho component này.

## Giải thích thiết kế sau khi sửa

Cleanup abort request cũ và cờ `active` ngăn stale callbacks ghi state; `view.key` đảm bảo không render dữ liệu của context trước khi effect mới chạy. `response.ok` xử lý HTTP errors đúng, runtime validation tránh tin JSON theo kiểu TypeScript compile-time. Backend phải kiểm tra tenant membership trên mọi request; frontend filtering không phải security boundary.

## Trade-offs

- Abort giảm traffic thừa nhưng không đảm bảo server đã dừng xử lý; backend cần cancellation và authorization.
- Reset dữ liệu tránh cross-context confusion nhưng có thể gây flicker; stale-while-revalidate chỉ an toàn nếu key gắn đúng identity/tenant.
- Runtime schema validation thêm code/dependency; với API lớn có thể sinh types/schema từ OpenAPI và kiểm tra ở boundary.
- Nếu token đổi liên tục, refetch có chi phí; auth session version giúp ổn định hơn.

## Cách kiểm thử

1. **Component race test:** Mock request A chậm hơn B; đổi tenant A→B, chỉ dữ liệu B được render.
2. **HTTP test:** Mock 401, 403, 500 trả JSON và body không hợp lệ; không render rows giả, có error phù hợp.
3. **Auth switch test:** Token/user đổi cùng tenant, dữ liệu user trước không còn hiển thị.
4. **Unmount test:** Unmount khi pending, không cập nhật state sau cleanup; abort được gọi.
5. **Playwright E2E:** Throttle network, đổi status nhanh; đối chiếu UI với request cuối, test backend từ chối tenant không được cấp quyền.

## Quan sát trong production

Theo dõi frontend request duration, abort count, HTTP status, filter transition latency và stale-response guard metrics (không gửi token hoặc PII). Correlation ID giữa browser và ASP.NET Core Application Insights; server log tenant access denied, request cancellation, p95/p99. Dùng browser network waterfall để phân biệt race ở UI với response sai từ backend.

## Câu hỏi phỏng vấn mở rộng

1. Nếu muốn stale-while-revalidate mà vẫn bảo đảm tenant isolation, bạn thiết kế query cache key và cache invalidation thế nào?
2. Nếu user chuyển account trong lúc mutation đang gửi, backend và frontend cần bảo vệ dữ liệu ra sao?
3. Khi nào nên đưa logic fetch vào custom hook hoặc data-fetching library thay vì tự viết effect?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB pagination phải giới hạn work thực tế, không chỉ đặt `MaxItemCount`; partition key ảnh hưởng routing và hot-tenant behavior.
- Authentication không thay thế tenant-level authorization; multi-tenant boundary phải được kiểm tra ở backend.
- React asynchronous requests có thể hoàn thành không theo thứ tự khởi tạo; state phải gắn với request/filter/auth identity.
- TypeScript type assertion không validate JSON; `fetch` không tự throw với HTTP 4xx/5xx.
- Telemetry phải chứng minh hypothesis bằng RU, 429, latency, cancellation, status và correlation.

## Mẫu tư duy cần nhớ

1. **Verify authorization at every trust boundary**, không tin tenant ID từ client.
2. **Bound work before scaling**, đo RU/memory/latency trước khi đổi kiến trúc.
3. **Treat asynchronous completion as unordered**, ràng buộc kết quả với request identity.
4. **Test failure paths and context switching**, không chỉ happy path.
5. **Separate measured bottlenecks from speculative fixes**, nhất là partition redesign.
