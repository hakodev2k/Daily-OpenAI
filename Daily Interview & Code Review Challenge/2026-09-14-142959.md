# Câu 1 — Webhook đã verify HMAC nhưng attacker vẫn replay cùng payment event nhiều lần

**Loại câu hỏi:** Security + API Correctness + Production Design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, REST APIs, HMAC, request-body integrity, replay protection, idempotency, distributed systems, secret rotation, observability

## Bối cảnh

Một ASP.NET Core service nhận webhook từ payment provider:

```http
POST /webhooks/payment
X-Webhook-Timestamp: 1789378130
X-Webhook-Signature: sha256=...
X-Webhook-Event-Id: evt_9f2...
```

Code hiện tại:

```csharp
[HttpPost("/webhooks/payment")]
public async Task<IActionResult> ReceiveAsync(
    PaymentWebhook payload,
    CancellationToken cancellationToken)
{
    var signature = Request.Headers["X-Webhook-Signature"].ToString();

    var json = JsonSerializer.Serialize(payload);

    using var hmac = new HMACSHA256(
        Encoding.UTF8.GetBytes(_options.WebhookSecret));

    var computed = Convert.ToHexString(
        hmac.ComputeHash(Encoding.UTF8.GetBytes(json)));

    if (!string.Equals(signature, computed, StringComparison.OrdinalIgnoreCase))
        return Unauthorized();

    await _paymentService.ApplyAsync(payload, cancellationToken);

    return Ok();
}
```

Sau một security review, team sửa format signature và HMAC verification cho đúng theo provider docs. Tuy nhiên production vẫn xuất hiện incident:

- cùng một `eventId` được nhận 4–20 lần trong vài phút;
- provider xác nhận họ retry webhook khi endpoint timeout hoặc trả non-2xx;
- một captured request hợp lệ nếu gửi lại nguyên xi trong 30 phút vẫn được accepted;
- một số duplicate events làm business workflow chạy lại, gửi email lại và tạo duplicate ledger side effects ở downstream cũ;
- timestamp header hiện chỉ được log, không validate;
- application deserialize JSON trước rồi serialize object lại để verify signature;
- provider ký trên **raw request bytes + timestamp**, không ký trên normalized DTO;
- provider đang chuẩn bị rotate webhook secret và trong 24 giờ sẽ có hai secrets cùng valid;
- một developer nói “HMAC đã chứng minh request chính chủ nên replay không còn là security problem”; người khác đề xuất lưu mọi raw request mãi mãi để deduplicate.

## Câu hỏi chính

Hãy phân biệt **authenticity/integrity** với **freshness/replay protection**. Giải thích vì sao HMAC đúng vẫn không ngăn một request hợp lệ bị replay; tại sao verify signature trên object đã deserialize rồi re-serialize là nguy hiểm; và thiết kế webhook receiver production-safe gồm raw-body verification, constant-time comparison, timestamp tolerance, event-id deduplication/idempotency, secret rotation, transaction boundary và retry semantics.

## Câu hỏi làm rõ nên cân nhắc

1. Provider định nghĩa signed payload chính xác là gì: `timestamp.rawBody`, canonical string hay format khác?
2. `eventId` có unique toàn account hay chỉ unique theo event type/resource?
3. Provider retry trong bao lâu và retention window cho dedup cần dài đến mức nào?
4. Business handler có side effects nào nằm ngoài local SQL transaction?
5. Nếu event đến out-of-order, domain dùng event sequence/version hay re-read canonical state?

## Gợi ý tư duy

### Gợi ý 1

Một chữ ký hợp lệ trả lời câu hỏi “message này có được tạo bởi bên biết secret và bị sửa không?”, không trả lời “message này có mới không?”.

### Gợi ý 2

Cryptographic verification phải chạy trên đúng byte sequence mà sender đã ký. Deserialize rồi serialize lại có thể thay whitespace, property order, escaping hoặc numeric representation.

### Gợi ý 3

Webhook delivery thường là **at-least-once**. Receiver phải giả định duplicate delivery là bình thường, không phải exception hiếm.

## Cấu trúc trả lời đề xuất

1. Xác định signed-data contract từ provider.
2. Đọc raw body an toàn và verify trước khi trust payload.
3. Parse/validate timestamp và freshness window.
4. Dùng constant-time signature comparison.
5. Thiết kế event identity/dedup store.
6. Đặt transaction boundary giữa inbox record và local state mutation.
7. Xử lý external side effects bằng outbox/idempotency phù hợp.
8. Thiết kế secret rotation với active/previous key.
9. Xử lý duplicate/out-of-order events.
10. Thiết kế telemetry, alert và security tests.

## Ý chính của câu trả lời tốt

### Bắt buộc

- HMAC cung cấp authenticity/integrity nếu secret còn an toàn, nhưng **không tự cung cấp replay protection**.
- Receiver phải verify đúng raw bytes/canonical input theo provider specification; re-serialize DTO có thể làm signature verification sai hoặc tạo canonicalization assumptions nguy hiểm.
- Timestamp phải được validate với tolerance hợp lý và reject quá cũ/quá xa trong tương lai, sau khi hiểu clock-skew requirement.
- Signature comparison nên dùng constant-time primitive như `CryptographicOperations.FixedTimeEquals` sau khi decode đúng format.
- `eventId` phải được persist với unique constraint hoặc equivalent dedup invariant; duplicate delivery phải trả success phù hợp mà không chạy business side effect lần nữa.
- Idempotency không chỉ nằm ở controller; downstream side effects cũng cần outbox/idempotency hoặc operation identity ổn định.
- Secret rotation phải hỗ trợ overlap có kiểm soát mà không làm receiver chấp nhận secret cũ vô thời hạn.

### Điểm cộng

- Limit request size trước buffering raw body để tránh memory abuse.
- Verify signature trước expensive parsing/business work.
- Không log full raw webhook nếu chứa PII/payment metadata; log event id, timestamp, verification outcome và hash/correlation metadata đủ dùng.
- Có unique index kiểu `(Provider, AccountId, EventId)` nếu event id scope không global.
- Dedup retention dựa trên provider retry/replay window + business/audit requirement, không mặc định giữ raw payload mãi mãi.

### Senior+

- Inbox pattern: transactionally insert received-event identity + apply local state hoặc mark processing state sao cho crash/retry không tạo double application.
- Nếu handler cần publish downstream event, dùng transactional outbox để local commit và message publication không tạo failure window mới.
- Timestamp freshness chỉ giảm replay window; event-id dedup vẫn cần vì legitimate provider retries trong window phải an toàn.
- Out-of-order events cần aggregate version/state transition checks hoặc canonical re-fetch; dedup không giải quyết ordering.
- Rotation có key identifier/version nếu provider hỗ trợ; nếu không, thử bounded set active secrets và telemetry secret-version match mà không lộ secret.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng contract của provider. Nếu họ ký `timestamp + "." + rawBody`, receiver phải giữ nguyên raw bytes của request trước model binding làm thay đổi representation. ASP.NET Core có thể enable buffering có giới hạn hoặc dùng middleware/endpoint đọc body thành bounded buffer, verify rồi mới deserialize.

Pseudocode:

```csharp
var timestamp = ParseTimestamp(headers);
RejectIfOutsideTolerance(timestamp, now);

var rawBody = await ReadBoundedBodyAsync(Request.Body, maxBytes, ct);
var signedPayload = BuildSignedPayload(timestamp, rawBody);

var expected = ComputeHmac(activeSecret, signedPayload);
var supplied = DecodeSignature(headers);

if (!CryptographicOperations.FixedTimeEquals(expected, supplied))
    return Unauthorized();
```

Khi rotate secret, receiver có thể thử `current` rồi `previous` trong một overlap window được cấu hình; sau deadline phải loại previous secret. Secrets lấy từ secret store/config provider phù hợp, không commit vào source.

Sau verification mới parse JSON và validate schema. Timestamp chỉ bảo vệ freshness một phần. Một attacker ghi lại request hợp lệ và replay trong tolerance vẫn có HMAC đúng. Vì vậy event identity phải được deduplicate.

Một inbox table tối thiểu:

```text
WebhookInbox
------------
Provider
AccountId
EventId
ReceivedAt
PayloadHash
Status
ProcessedAt
```

Có unique constraint trên identity scope. Khi duplicate insert conflict hoặc row đã `Processed`, endpoint trả 2xx theo provider contract nhưng không chạy lại handler. Nếu first attempt crash giữa receive và apply, state machine/inbox transaction phải cho phép retry đúng chỗ.

Nếu `ApplyAsync` vừa update SQL vừa gửi email/message trực tiếp, local dedup chưa đủ. Tôi sẽ commit domain change + outbox record trong cùng DB transaction, rồi worker phát message với downstream idempotency key là event/operation id. Như vậy retry webhook không gửi side effect mới.

Tôi không lưu raw body vô hạn chỉ để dedup. Event identity + minimal audit metadata thường đủ; raw payload retention phải theo security/compliance need và được encrypt/access-controlled nếu giữ.

Testing phải gồm: valid signature, modified byte, changed whitespace, old timestamp, future timestamp, duplicate same event, duplicate concurrent requests, secret overlap, crash after inbox insert, crash after domain commit, out-of-order events và large-body rejection.

## Mẫu trả lời trong phỏng vấn

“HMAC đúng chỉ chứng minh message hợp lệ theo secret và chưa bị sửa; nó không chứng minh message chưa từng được gửi. Webhook là at-least-once nên tôi thiết kế duplicate như normal case.

Tôi verify đúng raw bytes + timestamp theo provider contract, không deserialize rồi serialize lại. Tôi reject timestamp ngoài tolerance, dùng `FixedTimeEquals`, rồi persist `eventId` với unique constraint trong inbox. Duplicate trả 2xx nhưng không apply business logic lần hai.

Nếu business handler phát external side effect, tôi dùng outbox hoặc stable idempotency key để crash/retry không tạo duplicate ở downstream. Secret rotation hỗ trợ current + previous chỉ trong overlap window. Timestamp giảm replay window; event-id dedup mới bảo vệ duplicate trong window.”

## Câu hỏi đào sâu

1. Nếu provider không có event id đáng tin cậy, bạn xây dedup identity từ dữ liệu nào và trade-off ra sao?
2. Nếu hai events hợp lệ đến ngược thứ tự, inbox unique key có giải quyết correctness không?
3. Nếu webhook handler mất 40 giây nhưng provider timeout sau 10 giây, bạn thiết kế acknowledgement/async processing thế nào?

## Lỗi trả lời thường gặp

- Nói HMAC hợp lệ nghĩa là request không thể replay.
- Verify trên DTO re-serialized thay vì signed raw bytes.
- Chỉ check timestamp mà không dedup event id.
- Dedup bằng `SELECT` rồi `INSERT` không có unique constraint, tạo race dưới concurrency.
- Trả 500 cho duplicate đã xử lý, khiến provider retry thêm.
- Giữ mọi raw payload vô hạn mà không xét PII/compliance.

## Thang điểm 0–10

- **0–2:** Chỉ nói “check signature”.
- **3–4:** Biết timestamp/replay nhưng thiếu raw-body và durable dedup reasoning.
- **5–6:** Có correct signature verification, freshness, unique event dedup và idempotent handler.
- **7–8:** Có inbox/outbox, secret rotation, concurrency và failure-window analysis.
- **9–10:** Thiết kế đầy đủ cryptographic boundary, at-least-once semantics, ordering, retention và crash-safe operational model.

# Câu 2 — Pagination theo `OFFSET` làm API vừa bỏ sót vừa trả trùng record khi dữ liệu thay đổi liên tục

**Loại câu hỏi:** REST/API Design + Database Correctness + Performance  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, EF Core, SQL Server, REST APIs, pagination, ordering, indexing, consistency, cursor/keyset pagination, API contracts

## Bối cảnh

Một order API cho mobile app:

```http
GET /api/orders?page=4&pageSize=50&sort=createdAtDesc
```

Implementation:

```csharp
public async Task<IReadOnlyList<OrderDto>> GetOrdersAsync(
    Guid tenantId,
    int page,
    int pageSize,
    CancellationToken cancellationToken)
{
    return await _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId)
        .OrderByDescending(x => x.CreatedAt)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(x => new OrderDto(
            x.Id,
            x.CreatedAt,
            x.Status,
            x.Total))
        .ToListAsync(cancellationToken);
}
```

Production symptoms:

- user scroll trang 1 → 2 → 3 thì đôi khi thấy cùng order xuất hiện lại;
- một số order không bao giờ xuất hiện trong session scroll đó;
- issue tăng mạnh vào giờ có nhiều order mới được tạo;
- `CreatedAt` chỉ có precision tới millisecond ở một integration path nên nhiều rows có cùng timestamp;
- khi page lớn, SQL latency/reads tăng;
- Product muốn infinite scroll ổn định hơn, nhưng không yêu cầu một snapshot transaction kéo dài qua nhiều HTTP requests;
- client có thể pause vài phút giữa hai page;
- một developer đề xuất thêm `Distinct()`; người khác muốn giữ `OFFSET` nhưng cache page 1 trong Redis;
- API cũng hỗ trợ filter theo `Status` và khoảng thời gian.

## Câu hỏi chính

Hãy giải thích hai nhóm vấn đề độc lập: **correctness dưới mutable dataset** và **performance của deep OFFSET**. Chỉ ra vì sao ordering chỉ theo `CreatedAt` chưa deterministic; mô tả concrete timeline dẫn tới duplicate/missing record giữa page 1 và page 2; rồi thiết kế cursor/keyset pagination có stable tie-breaker, opaque continuation token, filter binding và indexing phù hợp.

## Câu hỏi làm rõ nên cân nhắc

1. `Order.Id` có monotonic không hay là random GUID?
2. API cần “mọi record đúng một lần trong một scrolling session” hay chỉ cần stable forward traversal best-effort?
3. `CreatedAt` có immutable không? Có backfill/import record với timestamp cũ không?
4. Filter có thể thay đổi giữa các page không?
5. Có requirement jump trực tiếp tới page 500 hay chủ yếu next/previous infinite scroll?

## Gợi ý tư duy

### Gợi ý 1

`ORDER BY CreatedAt DESC` không phải total order nếu nhiều rows có cùng `CreatedAt`.

### Gợi ý 2

`OFFSET 50` được tính lại trên dataset **tại thời điểm request thứ hai**, không trên snapshot của request đầu tiên.

### Gợi ý 3

Cursor tốt không chỉ encode vị trí; nó phải gắn với sort/filter semantics để client không dùng cursor của query A cho query B.

## Cấu trúc trả lời đề xuất

1. Chứng minh non-deterministic ordering khi timestamp trùng.
2. Vẽ timeline insert giữa hai page requests.
3. Phân tích OFFSET/deep-page cost.
4. Chọn stable total ordering.
5. Viết keyset predicate đúng với descending sort.
6. Thiết kế opaque cursor/token.
7. Bind cursor với tenant/filter/sort.
8. Thiết kế composite index.
9. Nêu consistency semantics rõ trong API contract.
10. Test mutations, ties và concurrent inserts.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `OrderByDescending(CreatedAt)` không deterministic khi nhiều rows cùng timestamp; cần tie-breaker unique/stable như `Id` hoặc sequence.
- Với OFFSET, insert/delete trước boundary giữa hai requests dịch vị trí rows, gây duplicate hoặc skip dù SQL của từng request hoàn toàn đúng.
- `Distinct()` không khôi phục record đã bị skip và không sửa unstable page boundary.
- Deep OFFSET thường khiến DB phải locate/sort/skip ngày càng nhiều rows; keyset seek theo last-seen key thường scale tốt hơn cho next-page traversal.
- Cursor phải đại diện sort key của last item, ví dụ `(CreatedAt, Id)` và predicate phải match sort direction.
- Cursor không được tin như authorization input; tenant vẫn lấy từ authenticated context/authorized scope.
- Filters/sort version phải được gắn hoặc validated với cursor để tránh continuation sai query.

### Điểm cộng

- Opaque cursor được signed/MAC hoặc server-validated để client không tùy ý sửa fields ảnh hưởng query semantics.
- Dùng API response dạng `{ items, nextCursor, hasMore }` thay vì expose raw DB values nếu contract muốn linh hoạt.
- Composite index bắt đầu bằng tenant + filter phù hợp rồi sort keys, ví dụ `(TenantId, CreatedAt DESC, Id DESC)` cho query cơ bản.
- Limit `pageSize` để bảo vệ DB/network.
- Nếu `Status` filter phổ biến, đánh giá index strategy dựa trên selectivity/workload thay vì tạo mọi tổ hợp index.

### Senior+

- Keyset pagination ổn định trước inserts **mới hơn cursor**: chúng không đẩy boundary của traversal đã bắt đầu; nhưng nó không tự tạo full snapshot semantics cho updates/deletes/backfills.
- Nếu requirement thật sự cần immutable snapshot across minutes, cần snapshot token/materialized result/version boundary riêng; không giả vờ cursor cung cấp serializable snapshot.
- Với random GUID tie-breaker, lexical ordering vẫn dùng được nếu DB/app thống nhất comparison, nhưng clustered/index economics cần xem riêng; monotonic sequence có thể phù hợp hơn.
- Cursor nên có schema/version để API có thể evolve format.
- Date/time normalization, precision và serialization phải deterministic giữa client/server.

## Hướng giải quyết tham khảo

Giả sử page size = 2 và order theo newest first.

Tại request 1:

```text
A 10:00:04
B 10:00:03
C 10:00:02
D 10:00:01
```

Page 1 trả `A, B`. Trước request page 2, order `X 10:00:05` được insert:

```text
X, A, B, C, D
```

`OFFSET 2` lúc này bỏ `X, A` rồi trả `B, C`. `B` bị duplicate. Với delete hoặc mutation khác, một row có thể bị skip. Đây không phải bug của EF Core; đó là semantics của positional paging trên mutable set.

Trước hết cần total order:

```csharp
.OrderByDescending(x => x.CreatedAt)
.ThenByDescending(x => x.Id)
```

Giả sử cursor cuối page chứa `(lastCreatedAt, lastId)`. Page kế tiếp với descending order dùng:

```csharp
.Where(x =>
    x.CreatedAt < lastCreatedAt ||
    (x.CreatedAt == lastCreatedAt && x.Id.CompareTo(lastId) < 0))
.OrderByDescending(x => x.CreatedAt)
.ThenByDescending(x => x.Id)
.Take(pageSize + 1)
```

Tùy kiểu `Id`/provider, expression thực tế phải translate được sang SQL; nếu GUID comparison không phù hợp/provider không support mong muốn, dùng một stable sortable unique key khác như sequence.

Cursor không nên chỉ là base64 của timestamp rồi tin hoàn toàn. Payload có thể gồm:

```json
{
  "v": 1,
  "createdAt": "2026-09-14T07:20:11.123Z",
  "id": "...",
  "filterHash": "..."
}
```

Server encode opaque và ký/MAC hoặc validate strict. `filterHash`/query fingerprint bảo đảm cursor của `Status=Paid` không được reuse với `Status=Cancelled`. Tenant không lấy từ token mà lấy từ auth context; nếu token có tenant id thì chỉ dùng để cross-check.

Index cho query cơ bản có thể là:

```sql
CREATE INDEX IX_Orders_Tenant_CreatedAt_Id
ON dbo.Orders (TenantId, CreatedAt DESC, Id DESC)
INCLUDE (Status, Total);
```

Nhưng nếu status là predicate chính, cần xem actual plans và workload trước khi thêm variant index.

API contract phải nói rõ consistency: keyset cho traversal ổn định hơn và tránh rows mới hơn cursor chen vào các page sau, nhưng update/delete/backfill vẫn có thể làm dataset thay đổi. Nếu Product cần exact snapshot, có thể thêm `asOf`/version boundary hoặc materialized search session, với cost storage/state/complexity rõ ràng.

Testing gồm hàng nghìn rows có timestamp ties, concurrent inserts giữa page calls, deletes/updates, cursor tampering, filter mismatch, page-size abuse và benchmark page 1 vs equivalent deep traversal.

## Mẫu trả lời trong phỏng vấn

“Có hai vấn đề. Thứ nhất, `CreatedAt` một mình không tạo total order khi timestamps trùng. Thứ hai, OFFSET là vị trí trên dataset tại từng request; nếu một row mới chèn trước boundary, page 2 có thể lặp item từ page 1 hoặc skip item khác.

Tôi chuyển infinite scroll sang keyset pagination với order ổn định `(CreatedAt DESC, Id DESC)`. Cursor mang last-seen sort tuple và query/filter fingerprint; server validate token và authorization độc lập. Page sau query bằng `< lastCreatedAt` hoặc equality + tie-breaker, thay vì `Skip(n)`.

Tôi tạo composite index khớp tenant + sort keys và nói rõ cursor không phải snapshot transaction. Nếu business cần exact immutable snapshot qua nhiều phút, đó là requirement khác và cần version/as-of/materialized session.”

## Câu hỏi đào sâu

1. Nếu user đổi `Status` filter giữa hai calls nhưng vẫn gửi cursor cũ, server nên làm gì?
2. Nếu order có thể được backfill với `CreatedAt` cũ sau khi cursor đã đi qua vị trí đó, keyset semantics xử lý ra sao?
3. Bạn hỗ trợ “jump to page 1000” thế nào nếu product thực sự cần random access?

## Lỗi trả lời thường gặp

- Chỉ thêm `ThenBy(Id)` nhưng vẫn nghĩ OFFSET đã ổn định dưới inserts/deletes.
- Dùng `Distinct()` để chữa duplicate mà không hiểu missing rows.
- Base64 cursor rồi coi là tamper-proof.
- Nhét tenant id từ cursor vào query mà không authorize.
- Tuyên bố keyset cung cấp full snapshot consistency.
- Thêm composite indexes cho mọi filter permutation mà không đo workload.

## Thang điểm 0–10

- **0–2:** Chỉ chỉnh page size hoặc `Distinct()`.
- **3–4:** Biết stable ordering nhưng chưa hiểu mutation/offset semantics.
- **5–6:** Thiết kế keyset đúng với tie-breaker, cursor và index.
- **7–8:** Có filter binding, tamper handling, explicit consistency contract và mutation tests.
- **9–10:** Phân biệt rõ traversal vs snapshot semantics, API evolution, index economics và security boundary của cursor.

# Câu 3 — Key Vault secret đã rotate nhưng một số App Service instances vẫn dùng credential cũ

**Loại câu hỏi:** Azure / Configuration / Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Azure App Service, Azure Key Vault, Managed Identity, ASP.NET Core configuration, secret rotation, caching, rollout, observability, incident response

## Bối cảnh

Một ASP.NET Core application chạy trên Azure App Service, 8 instances. Ứng dụng cần credential để gọi một legacy partner API. Secret được lưu trong Azure Key Vault.

Startup code hiện tại:

```csharp
var secretClient = new SecretClient(
    new Uri(builder.Configuration["KeyVaultUri"]!),
    new DefaultAzureCredential());

var partnerSecret = await secretClient.GetSecretAsync("PartnerApiSecret");

builder.Services.Configure<PartnerOptions>(o =>
{
    o.BaseUrl = builder.Configuration["Partner:BaseUrl"]!;
    o.Secret = partnerSecret.Value.Value;
});
```

`PartnerClient` được đăng ký singleton và nhận `IOptions<PartnerOptions>`.

Rotation runbook hiện tại:

1. partner tạo credential mới;
2. operations tạo version mới của `PartnerApiSecret` trong Key Vault;
3. partner giữ credential cũ valid thêm 30 phút;
4. sau 30 phút credential cũ bị revoke.

Incident:

- sau rotation, khoảng 60% requests thành công và 40% nhận `401` từ partner;
- restart toàn App Service làm 100% requests thành công ngay;
- Key Vault portal cho thấy secret version mới đúng;
- Managed Identity access không lỗi;
- các instances được restart lệch thời gian do autoscale/deployment trước đó;
- application không pin secret version, nhưng chỉ gọi `GetSecretAsync` ở startup;
- một developer cho rằng “Key Vault đã rotate thì app tự nhận version mới”; người khác muốn fetch Key Vault secret trước **mỗi** outbound request;
- security team không muốn restart toàn fleet mỗi lần rotate;
- partner đôi khi cần emergency revoke credential cũ sớm hơn 30 phút.

## Câu hỏi chính

Hãy xác định vì sao các instances có thể dùng secret versions khác nhau dù cùng trỏ tới một Key Vault secret name. Phân biệt Key Vault secret versioning với application-side caching/configuration lifetime; thiết kế rotation strategy không cần full restart, có bounded staleness và safe overlap; đồng thời xử lý failure mode khi new secret sai, Key Vault tạm unavailable hoặc partner revoke old secret sớm.

## Câu hỏi làm rõ nên cân nhắc

1. Partner có hỗ trợ đồng thời hai credentials trong overlap window thật sự không?
2. Secret cần refresh tối đa trong bao lâu theo rotation SLO?
3. Application có thể retry `401` bằng credential refresh một lần an toàn không?
4. `PartnerClient` có copy secret vào field tại construction hay đọc options mỗi request?
5. Key Vault throttling/availability budget cho 8 instances và request volume là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

“Không pin version” chỉ nghĩa lần `GetSecretAsync(name)` đó lấy current version; nó không tạo subscription tự động cho future versions.

### Gợi ý 2

Secret lifecycle có ít nhất ba lớp: Key Vault version, application refresh/cache lifetime và downstream credential validity window.

### Gợi ý 3

Fetch secret mỗi HTTP request thường đổi một stale-cache problem thành latency/availability/throttling dependency trên Key Vault.

## Cấu trúc trả lời đề xuất

1. Dựng timeline per instance startup/secret version.
2. Phân biệt Key Vault current version với in-memory value.
3. Xác định max acceptable staleness.
4. Thiết kế central refresh/cache mechanism.
5. Đảm bảo clients consume refreshed value thật sự.
6. Thiết kế overlap/activation/revoke runbook.
7. Xử lý refresh failure và bad new secret.
8. Cân nhắc forced refresh on 401 có guardrails.
9. Telemetry secret version/refresh age không lộ secret.
10. Test rotation trên multi-instance deployment.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `GetSecretAsync("name")` không pin version nếu không chỉ định version, nhưng giá trị trả về là snapshot tại thời điểm fetch; application không tự cập nhật nếu code chỉ gọi lúc startup.
- Different app instances có thể giữ in-memory secret khác nhau tùy startup/refresh time.
- `IOptions<T>` thường là fixed configuration instance; chỉ đổi Key Vault không làm object đã configure thủ công refresh.
- Fetch Key Vault trước mọi outbound request không phải default tốt vì tăng latency, Key Vault dependency, cost/throttling và blast radius.
- Cần explicit refresh policy với bounded TTL/periodic refresh hoặc provider mechanism phù hợp, cộng với overlap giữa old/new credential.
- Consumer (`PartnerClient`) phải đọc refreshed credential source, không copy một lần vào singleton field rồi giữ vĩnh viễn.
- Không log secret; telemetry có thể log secret version identifier/last refresh time.

### Điểm cộng

- Refresh có jitter giữa instances để tránh thundering herd lên Key Vault.
- Cache last-known-good secret và tiếp tục dùng trong bounded failure window nếu Key Vault tạm unavailable, tùy security policy.
- Nếu partner trả 401, trigger single-flight forced refresh rồi retry **một lần** nếu request replay-safe hoặc auth retry không tạo duplicate side effect.
- Validate new credential trước khi revoke old nếu partner supports validation/dual activation.
- Phân biệt secret rotation failure với Managed Identity/token failure.

### Senior+

- Thiết kế two-phase rotation: publish new → app fleet observes/validates → switch/prefer new → revoke old, với observability cho adoption percentage.
- Nếu emergency revoke yêu cầu convergence nhanh, periodic TTL phải match SLO hoặc có push/control-plane invalidation; không giả định 30-minute polling đáp ứng 2-minute revoke SLO.
- Single-flight refresh per instance để nhiều concurrent 401 không tạo Key Vault stampede.
- Secret value nên được encapsulate trong provider abstraction có atomic swap/thread-safe snapshot; callers không giữ raw secret lâu hơn cần thiết.
- Runbook có rollback khi new credential sai: giữ old active, restore previous Key Vault current version hoặc republish known-good version theo policy.

## Hướng giải quyết tham khảo

Root cause là application-side lifetime. Mỗi instance gọi Key Vault đúng một lần khi process start, rồi copy value vào `PartnerOptions`. Key Vault có version mới không đẩy value vào process đang chạy. Vì instances có tuổi khác nhau, một số process khởi động sau rotation hoặc restart đã lấy secret mới, còn process cũ vẫn giữ version cũ.

Tôi sẽ tạo abstraction kiểu:

```csharp
public interface IPartnerCredentialProvider
{
    ValueTask<CredentialSnapshot> GetAsync(CancellationToken ct);
    ValueTask ForceRefreshAsync(CancellationToken ct);
}

public sealed record CredentialSnapshot(
    string Secret,
    string Version,
    DateTimeOffset RefreshedAt);
```

Provider giữ snapshot thread-safe trong memory, refresh theo TTL ví dụ vài phút + jitter dựa trên rotation SLO. Refresh dùng single-flight để một instance chỉ có một fetch in progress. Nếu refresh thành công, atomic swap snapshot. Nếu Key Vault tạm lỗi, giữ last-known-good trong policy window và emit alert thay vì làm toàn bộ traffic fail ngay — trừ khi security requirement nói fail closed.

`PartnerClient` singleton không được copy secret ở constructor. Mỗi operation lấy current snapshot từ provider hoặc provider trả lightweight current value. Việc này vẫn là in-memory read trên normal path; Key Vault chỉ được gọi khi TTL/forced refresh cần thiết.

Rotation runbook tốt hơn:

1. Partner tạo credential mới nhưng giữ old valid.
2. Publish new Key Vault version.
3. Fleet refresh dần; dashboard theo `secretVersion` adoption.
4. Validate success/auth error rate với new version.
5. Khi adoption đạt 100% hoặc policy threshold an toàn, revoke old.
6. Nếu new credential lỗi, rollback trước revoke bằng known-good version và forced refresh.

Nếu emergency revoke yêu cầu convergence trong 2 phút, TTL phải nhỏ hơn SLO hoặc operations cần một push/invalidation mechanism để fleet forced refresh; không thể dùng TTL 15 phút rồi kỳ vọng 2 phút.

Fetch-per-request là không cần thiết và làm Key Vault thành dependency trực tiếp cho mọi partner call. Tám instances với high RPS có thể tạo throttle/latency và outage coupling.

Có thể xử lý partner `401` bằng một forced refresh + retry một lần, nhưng phải tránh retry storm và xem operation có replay-safe không. Nếu `POST` đã được partner process nhưng response auth semantics ambiguous, cần partner-level idempotency key.

Telemetry: instance id, secret version, age since refresh, refresh success/failure, forced refresh count, partner 401 rate và adoption distribution. Tuyệt đối không log secret value.

Testing cần multi-instance simulation: version A → publish B → staggered refresh; Key Vault unavailable; B invalid; concurrent 401 burst; old revoked sớm; rollback B→A. Success criterion là convergence trong rotation SLO mà không restart fleet và không thundering herd.

## Mẫu trả lời trong phỏng vấn

“Key Vault version mới không push vào object trong memory. Mỗi instance của code này gọi `GetSecretAsync` lúc startup rồi giữ secret trong `IOptions`, nên fleet có thể split giữa version cũ và mới. Restart chỉ tình cờ buộc fetch lại.

Tôi không fetch Key Vault mỗi request. Tôi dùng credential provider có cached snapshot, TTL + jitter và single-flight refresh. `PartnerClient` đọc snapshot hiện tại thay vì copy secret ở constructor. Rotation là publish new → observe fleet adoption → validate → revoke old. Nếu requirement là emergency revoke trong 2 phút, refresh/invalidation SLO phải ngắn hơn 2 phút.

Trên 401 có thể forced-refresh rồi retry một lần có kiểm soát. Tôi log version id và refresh age, không log secret. Khi Key Vault lỗi, policy quyết định dùng last-known-good bao lâu hoặc fail closed.”

## Câu hỏi đào sâu

1. Nếu security yêu cầu revoke old credential trong 60 giây, polling Key Vault còn phù hợp không?
2. Bạn xử lý concurrent 401 từ 500 requests trên cùng instance thế nào để không gọi Key Vault 500 lần?
3. Nếu partner API operation là non-idempotent POST, retry sau forced refresh cần thêm cơ chế gì?

## Lỗi trả lời thường gặp

- Nghĩ Key Vault tự push version mới vào application đang chạy.
- Restart fleet là rotation strategy duy nhất.
- Fetch secret cho mọi request mà không xét latency/throttling.
- Dùng `IOptions<T>` rồi kỳ vọng nó tự đổi vì external secret store đổi.
- Log secret value để debug adoption.
- Revoke old trước khi biết fleet đã dùng new credential.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart hoặc fetch-per-request.
- **3–4:** Biết application cache stale nhưng chưa có safe rotation strategy.
- **5–6:** Có periodic refresh, overlap, refreshed consumer và version telemetry.
- **7–8:** Có jitter, single-flight, forced refresh, failure/rollback handling và SLO reasoning.
- **9–10:** Thiết kế được fleet-wide two-phase rotation, emergency convergence, availability/security trade-offs và deterministic multi-instance tests.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- HMAC xác thực authenticity/integrity nhưng không tự cung cấp freshness hay replay protection.
- Webhook receiver phải verify đúng raw signed bytes, rồi dùng timestamp + durable event identity để xử lý at-least-once delivery an toàn.
- Pagination bằng OFFSET trên mutable dataset có thể duplicate/skip records; stable ordering một mình chưa giải quyết boundary shift.
- Keyset pagination dùng last-seen sort tuple, deterministic tie-breaker và index phù hợp để traversal ổn định/scalable hơn.
- Key Vault secret version mới không tự cập nhật giá trị đã cache trong process; application phải có refresh lifecycle rõ ràng.
- Secret rotation production-safe cần overlap, fleet adoption telemetry, bounded staleness, rollback và thundering-herd protection.

## Mẫu tư duy cần nhớ

- **Authentication của message không đồng nghĩa message là mới.**
- **At-least-once delivery đòi hỏi idempotent receiver, không phải optimistic assumption.**
- **Pagination là consistency contract, không chỉ là `Skip/Take`.**
- **Total order + keyset boundary tốt hơn positional offset cho infinite scroll.**
- **Secret lifecycle phải được thiết kế xuyên qua secret store → app cache → client consumer → downstream revoke window.**
