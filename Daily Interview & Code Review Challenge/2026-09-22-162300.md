# Câu 1 — `Task.WhenAll` nhanh hơn nhưng vì sao API lại làm cạn connection pool?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C#, async/await, `Task.WhenAll`, EF Core, SQL connection pooling, concurrency, ASP.NET Core, performance diagnostics

## Bối cảnh

Một ASP.NET Core API trả dashboard cho manager. Mỗi request nhận khoảng 20 employee IDs và cần đọc summary từ SQL Server. Team vừa tối ưu code tuần tự thành chạy song song:

```csharp
public async Task<IReadOnlyList<EmployeeSummary>> GetDashboardAsync(
    IReadOnlyList<Guid> employeeIds,
    CancellationToken ct)
{
    var tasks = employeeIds.Select(async id =>
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);
        return await db.Employees
            .Where(x => x.Id == id)
            .Select(x => new EmployeeSummary(x.Id, x.Name, x.Status))
            .SingleAsync(ct);
    });

    return await Task.WhenAll(tasks);
}
```

Ở load test nhỏ, latency của một request giảm. Sau khi production traffic tăng, p95/p99 tăng mạnh, một số request timeout và SQL dependency telemetry xuất hiện nhiều thời gian chờ. CPU web và database chưa chạm 100%. Team kết luận `async` “tạo quá nhiều threads” và đề xuất bọc từng query bằng `Task.Run` để ThreadPool xử lý tốt hơn.

Chưa biết connection-string pool size, request concurrency thực tế, SQL execution plan hay liệu 20 queries có thể gom thành một query hay không.

## Câu hỏi chính

Hãy giải thích cơ chế thực tế của đoạn code khi `Task.WhenAll` chạy nhiều I/O đồng thời, vì sao latency của một request có thể giảm nhưng throughput toàn hệ thống lại xấu đi, assumption nào về `async`/threads là sai, và bạn sẽ chứng minh bottleneck nằm ở ThreadPool, SQL, connection pool hay query shape trước khi sửa như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Concurrent HTTP requests ở peak là bao nhiêu và mỗi request có bao nhiêu employee IDs?
2. Các query có cùng database/connection string và pool configuration không?
3. Một query đơn lẻ mất bao lâu, execution plan và logical reads thế nào?
4. Requirement có thực sự cần 20 independent round trips hay có thể lấy toàn bộ summaries bằng một set-based query?
5. Timeout quan sát được là command timeout, request timeout hay thời gian chờ lấy connection?

## Gợi ý tư duy

### Gợi ý 1

`async` I/O không đồng nghĩa giữ một ThreadPool thread trong suốt thời gian chờ network/database.

### Gợi ý 2

Hãy nhân concurrency: số request đồng thời × số database operations được fan-out trong mỗi request.

### Gợi ý 3

Tối ưu local latency có thể làm tăng contention ở shared downstream resource. Đừng chỉ profile web CPU; đo connection acquisition, SQL waits, query count và dependency latency.

## Cấu trúc trả lời đề xuất

1. Giải thích async I/O và `Task.WhenAll`.
2. Tính concurrency amplification theo traffic.
3. Liệt kê các resource có thể bão hòa.
4. Thu thập telemetry để phân biệt hypotheses.
5. Đánh giá query shape/set-based alternative.
6. Nếu vẫn cần fan-out, chọn bounded concurrency.
7. Kiểm thử dưới realistic load.
8. Theo dõi p50/p95/p99 và downstream saturation sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Task.WhenAll` không tự tạo một thread cho mỗi asynchronous database operation.
- `Task.Run` không chữa I/O-bound database contention và còn có thể thêm scheduling overhead/ThreadPool pressure.
- 20 operations/request có thể khuếch đại concurrency rất lớn khi nhiều requests chạy đồng thời.
- Connection pool là bounded shared resource; nếu demand vượt capacity, operations có thể phải chờ connection dù CPU chưa cao.
- Phải đo query count, SQL duration/waits, pool/connection symptoms, request concurrency và ThreadPool metrics trước khi kết luận.
- Nếu dữ liệu có thể lấy bằng một set-based query, giảm round trips thường đáng xem xét trước việc tăng pool size.

### Điểm cộng

- Một query `WHERE Id IN (...)` + projection có thể giảm round trips nhưng phải đánh giá plan/cardinality và giới hạn thực tế của input.
- Bounded concurrency bằng `SemaphoreSlim` hoặc thiết kế batching có thể phù hợp khi operations thật sự độc lập nhưng downstream cần bảo vệ.
- Tăng connection pool size có thể chỉ chuyển bottleneck sang SQL Server; cần capacity evidence.
- Cancellation cần propagate để request bị hủy không tiếp tục giữ downstream work vô ích.

### Senior+

- Phân biệt per-request latency optimization với system throughput/queueing.
- Đưa ra load model, ví dụ 100 concurrent requests × 20 queries có thể tạo tối đa khoảng 2.000 in-flight attempts nếu không có các giới hạn khác.
- Kiểm tra cả database lock/wait, query plan và connection acquisition thay vì mặc định pool exhaustion.
- Thiết kế backpressure/admission/bounded parallelism theo downstream capacity.

## Hướng giải quyết tham khảo

Khi query EF Core bắt đầu I/O bất đồng bộ, thread thực thi không cần ngồi chờ database trả kết quả. Completion sẽ tiếp tục execution khi I/O hoàn tất. Vì vậy `Task.WhenAll` ở đây chủ yếu tăng số I/O operations có thể outstanding đồng thời; nó không có semantics “20 queries = 20 dedicated threads”.

Điểm nguy hiểm là concurrency amplification. Nếu một request fan-out 20 query và có nhiều request đồng thời, database/connection pool có thể nhận burst lớn. Một request riêng lẻ nhanh hơn khi downstream còn dư capacity, nhưng ở tải cao, queueing bắt đầu xuất hiện: connection acquisition, SQL worker/resource waits, locks hoặc network đều có thể kéo p95/p99 lên.

Tôi sẽ không thêm `Task.Run`. Tôi dựng evidence chain:

- request concurrency, request duration và p50/p95/p99;
- số SQL dependencies/request;
- dependency duration/error/timeout;
- SQL execution plans, waits, blocking, reads;
- connection pool-related counters/diagnostics phù hợp runtime/provider;
- ThreadPool queue length/thread count/starvation evidence;
- GC/CPU để loại trừ resource khác.

Nếu 20 employee summaries chỉ là cùng một projection, tôi ưu tiên thử một query set-based:

```csharp
var summaries = await db.Employees
    .Where(x => employeeIds.Contains(x.Id))
    .Select(x => new EmployeeSummary(x.Id, x.Name, x.Status))
    .ToListAsync(ct);
```

Cần xác nhận semantics: thứ tự output, missing IDs, duplicates và kích thước input. Nếu operations thực sự phải độc lập, tôi giới hạn parallelism theo measured capacity thay vì fan-out không giới hạn.

Không tăng pool size trước khi biết SQL có chịu được nhiều concurrent sessions/queries hơn hay không. Pool lớn hơn có thể giảm queue ở application nhưng làm database contention tệ hơn. Fix phải được xác nhận bằng load test có concurrency gần production và quan sát cả application lẫn SQL.

## Mẫu trả lời trong phỏng vấn

“`Task.WhenAll` không tạo một thread cho mỗi query. Với async database I/O, thread được trả lại trong thời gian chờ; vấn đề ở đây có khả năng là tăng số I/O outstanding. Nếu 100 requests cùng vào và mỗi request fan-out 20 queries, downstream có thể nhận lượng concurrency lớn hơn rất nhiều so với code tuần tự.

Tôi sẽ không dùng `Task.Run` vì đây là I/O-bound work. Tôi đo request concurrency, SQL dependencies/request, dependency p95/p99, SQL waits/execution plans, connection acquisition symptoms và ThreadPool metrics để phân biệt bottleneck. Nếu 20 query cùng lấy một projection, tôi ưu tiên thử một set-based query để giảm round trips. Nếu vẫn phải fan-out, tôi dùng bounded concurrency dựa trên capacity.

Tôi cũng không tăng pool size mù vì có thể chỉ chuyển bottleneck sang SQL. Bản sửa phải được load-test và theo dõi cả web p99, SQL latency/waits, connection pressure và timeout rate.”

## Câu hỏi đào sâu

1. Nếu set-based query có execution plan tệ hơn 20 point lookups ở một số input sizes, bạn chọn strategy thế nào?
2. Nếu connection pool không bão hòa nhưng SQL lock waits tăng mạnh, recommendation của bạn thay đổi ra sao?
3. Nếu product yêu cầu latency thấp nhất cho từng request, tại sao bạn vẫn có thể từ chối unbounded parallelism?

## Lỗi trả lời thường gặp

- Nói mỗi `async` operation cần một dedicated thread.
- Dùng `Task.Run` quanh EF Core async queries.
- Chỉ tăng connection pool size mà không đo database capacity.
- Giới hạn concurrency bằng một con số tùy ý không dựa trên load/capacity.
- Chỉ nhìn average latency thay vì p95/p99 và downstream telemetry.

## Thang điểm 0–10

- **0–2:** Quy lỗi cho ThreadPool chỉ vì thấy `Task.WhenAll`.
- **3–4:** Hiểu async I/O nhưng không phân tích concurrency amplification.
- **5–6:** Đo được pool/SQL/ThreadPool và đề xuất giảm round trips hoặc bounded concurrency.
- **7–8:** Có system-level load reasoning, testing và observability tốt.
- **9–10:** Phân tích queueing/backpressure, query alternatives và capacity trade-offs có điều kiện, không tối ưu một tầng làm hỏng toàn hệ thống.

# Câu 2 — Azure Service Bus backlog tăng sau release nhưng consumer vẫn “healthy”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, distributed systems, idempotency, retries, message lock, downstream dependencies, Application Insights, incident investigation, deployment safety

## Bối cảnh

Một order-processing backend nhận message từ Azure Service Bus queue. Consumer chạy nhiều instances trên Azure App Service. Mỗi message thực hiện validation, ghi SQL Server và gọi một inventory API. Sau release mới, queue depth tăng đều trong 40 phút, order processing chậm từ vài giây thành hơn 10 phút. Health endpoint của tất cả instances vẫn trả 200 và CPU chỉ khoảng mức trung bình.

Application Insights cho thấy inventory dependency latency tăng nhưng chưa rõ đó là nguyên nhân chính. Logs có cả message processing retries và một số duplicate business operations. Team đề xuất tăng số App Service instances ngay lập tức và tăng message concurrency để “drain queue nhanh”.

Release vừa thay đổi retry policy cho inventory API và tăng batch/concurrency configuration của consumer. Chưa biết lock duration, processing duration distribution, retry backoff, dead-letter count, SQL contention hay inventory rate limits.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ business impact và stabilization đến root-cause verification? Hãy giải thích cách phân biệt insufficient consumer capacity, retry amplification, message lock loss/redelivery, SQL contention và inventory degradation; đồng thời quyết định khi nào scale-out/concurrency increase giúp và khi nào nó làm incident tệ hơn.

## Câu hỏi làm rõ nên cân nhắc

1. Queue incoming rate, completion rate, active message count và oldest-message age thay đổi thế nào trước/sau release?
2. Processing duration p50/p95/p99 so với message lock/renewal behavior là bao nhiêu?
3. Inventory API có rate limit/SLO nào và retry policy mới có thể tạo bao nhiêu attempts cho một logical message?
4. Duplicate business operation xảy ra do redelivery, application retry hay thiếu idempotency ở side effect nào?
5. SQL waits/locks/connection usage và dead-letter count có thay đổi cùng thời điểm không?

## Gợi ý tư duy

### Gợi ý 1

Queue backlog là kết quả của **arrival rate > sustainable completion rate**. Scale chỉ giúp nếu bottleneck có thể scale cùng consumer.

### Gợi ý 2

Retry làm tăng work. Khi dependency đang chậm/rate-limited, nhiều consumers × nhiều retries có thể tạo positive feedback loop.

### Gợi ý 3

“At-least-once” processing semantics nghĩa là duplicate delivery phải được xem như normal failure mode; hãy tìm idempotency boundary quanh business side effects.

## Cấu trúc trả lời đề xuất

1. Xác định order/business impact và backlog age.
2. Stabilize: pause/revert risky config hoặc giảm pressure nếu cần.
3. Dựng timeline release → dependency latency → processing duration → queue metrics.
4. So sánh arrival/completion/retry/redelivery rates.
5. Kiểm tra lock, DLQ, SQL và inventory evidence.
6. Xác định bottleneck và feedback loops.
7. Áp dụng short-term remediation có giới hạn.
8. Thiết kế idempotency/retry/concurrency dài hạn.
9. Test failure path và load.
10. Alert theo backlog age, completion rate và dependency health.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng concurrency/instances trước khi biết downstream bottleneck.
- Đo incoming rate, successful completion rate, active/dead-letter counts và message age.
- Retry policy phải được tính vào effective load lên inventory API.
- Processing kéo dài có thể tương tác với message lock/renewal và dẫn tới redelivery; cần kiểm tra evidence thay vì giả định.
- Duplicate delivery/processing phải được xử lý bằng idempotency ở business boundary, không chỉ dựa vào “queue sẽ không gửi trùng”.
- Health 200 chỉ chứng minh endpoint hiện trả 200; không chứng minh consumer throughput đáp ứng SLO.

### Điểm cộng

- Nếu inventory là bottleneck/rate-limited, giảm concurrency hoặc retry aggressiveness có thể phục hồi nhanh hơn scale-out.
- Nếu consumer CPU/SQL/downstream đều còn capacity và completion scales tuyến tính, scale-out có thể hữu ích.
- Có thể temporarily stop/pause intake hoặc degrade non-critical work nếu business architecture cho phép.
- Tách retryable transient failure khỏi permanent/business failure; tránh retry mọi exception giống nhau.
- Theo dõi lock lost/redelivery/delivery count và DLQ reasons.

### Senior+

- Dùng Little's-law-style reasoning định tính/định lượng về arrival, service time và concurrency thay vì nhìn CPU.
- Thiết kế bounded retry + exponential backoff/jitter phù hợp, idempotent side effects và poison-message handling.
- Xem concurrency setting như một control loop với downstream capacity, không phải throughput knob độc lập.
- Phân biệt application health, dependency health và workload health/readiness.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định backlog có đang gây mất order hay chỉ delay, oldest-message age, arrival rate và completion rate. Nếu backlog tăng nhanh ngay sau release, tôi freeze rollout và so sánh configuration diff, đặc biệt retry/concurrency.

Tôi sẽ không scale ngay. Nếu inventory API đang degraded hoặc rate-limited, thêm consumers có thể tạo thêm calls và retries, làm dependency chậm hơn. Nếu retry policy cho mỗi logical message tạo nhiều attempts, effective request rate lên inventory có thể lớn hơn queue message rate nhiều lần.

Evidence cần correlate theo thời gian:

- Service Bus active messages, incoming/completed, DLQ, delivery count/redelivery;
- handler duration p50/p95/p99;
- lock-lost/settlement errors và renewal behavior;
- inventory request rate/latency/status/timeout/retry count;
- SQL dependency latency, waits/blocking/connection pressure;
- instance/concurrency configuration;
- business duplicate-operation metrics.

Nếu inventory degradation + retry amplification là hypothesis mạnh, short-term có thể revert retry/concurrency config, giảm pressure, dùng bounded backoff và phối hợp dependency owner. Nếu SQL là bottleneck, tăng consumers có thể tăng blocking. Nếu consumer compute là bottleneck còn downstream khỏe, scale-out có thể đúng.

Về correctness, mỗi message cần idempotency boundary. Ví dụ dùng stable business/message operation key và transactional record/inbox semantics phù hợp để side effect không được thực hiện lại vô điều kiện khi message redeliver. Nếu workflow gồm SQL commit rồi inventory call hoặc ngược lại, phải phân tích partial failure; không giả định distributed transaction tự tồn tại.

Sau fix, tôi load/failure-test với inventory latency/429/5xx, forced handler delay, redelivery và duplicate messages. Alerts nên dựa trên oldest-message age/backlog growth, completion-to-arrival ratio, retry rate, dependency p99, DLQ và duplicate suppression, không chỉ CPU/health endpoint.

## Mẫu trả lời trong phỏng vấn

“Tôi coi backlog là throughput problem: arrival rate đang lớn hơn sustainable completion rate. Tôi sẽ đo incoming/completed rate và oldest-message age trước, freeze release nếu correlation rõ, rồi correlate handler duration, delivery count/lock errors, inventory retries/latency và SQL waits.

Tôi chưa scale-out vì release vừa tăng concurrency và retry. Nếu inventory đang chậm hoặc rate-limited, thêm instances nhân số calls/retries và có thể làm feedback loop tệ hơn. Nếu evidence cho thấy downstream khỏe nhưng consumer compute thiếu capacity thì scale mới hợp lý.

Tôi cũng coi duplicate delivery là failure mode bình thường và đặt idempotency ở business side-effect boundary. Sau stabilization tôi sửa retry thành bounded/backoff phù hợp, tune concurrency theo downstream capacity, test inventory failure/lock delay/redelivery và alert theo backlog age, completion rate, retries, DLQ và dependency p99.”

## Câu hỏi đào sâu

1. Nếu inventory API trả 429 và có `Retry-After`, concurrency/retry policy của bạn nên phản ứng thế nào?
2. Nếu SQL commit thành công nhưng process crash trước khi message complete, bạn ngăn duplicate business effect khi redelivery bằng cách nào?
3. Nếu tăng instances thực sự làm backlog giảm trong 5 phút đầu nhưng inventory p99 tăng gấp ba, bạn giữ scale hay giảm lại? Vì sao?

## Lỗi trả lời thường gặp

- Scale consumer ngay chỉ vì queue depth tăng.
- Retry mọi lỗi ngay lập tức mà không phân loại failure.
- Dùng health endpoint 200 làm bằng chứng workload khỏe.
- Tin queue đảm bảo exactly-once business processing.
- Chỉ theo dõi message count mà bỏ qua oldest-message age và completion rate.

## Thang điểm 0–10

- **0–2:** Chỉ tăng instance/concurrency.
- **3–4:** Biết xem queue metrics nhưng không phân tích retry/downstream/idempotency.
- **5–6:** Điều tra đúng arrival/completion, dependency, lock/redelivery và SQL.
- **7–8:** Có stabilization, idempotency, failure tests và operational telemetry tốt.
- **9–10:** Reasoning đầy đủ về feedback loop, partial failure, capacity control và trade-off giữa throughput với downstream protection.

# Câu 3 — Modernize `.NET Framework 4.5` portal: rewrite hay incremental migration?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, ASP.NET MVC, ASP.NET Core, IIS, Azure App Service, legacy Angular/jQuery, migration strategy, CI/CD, testing, architecture trade-offs

## Bối cảnh

Một internal enterprise portal đã chạy nhiều năm trên `.NET Framework 4.5`, ASP.NET MVC, IIS/Windows Server, SQL Server và một frontend pha trộn server-rendered views với jQuery và Angular legacy. Portal có khoảng 25 business modules, một số scheduled jobs trong cùng application, nhiều integrations SOAP/REST cũ và deployment qua Jenkins + Octopus Deploy.

Business muốn chuyển dần sang modern .NET, cải thiện release frequency và giảm rủi ro Windows Server lifecycle. Một nhóm đề xuất rewrite toàn bộ sang .NET 10 + React + microservices + Kubernetes trong 12 tháng. Nhóm khác muốn giữ nguyên hệ thống vì “nó vẫn chạy”.

Constraints hiện biết:

- chỉ có một team chính khoảng 8 engineers cùng QA;
- business vẫn yêu cầu feature delivery trong thời gian migration;
- automated test coverage của legacy code thấp;
- database được chia sẻ bởi nhiều modules;
- một số third-party libraries chưa rõ khả năng chạy trên modern .NET;
- downtime production chỉ được phép rất ngắn;
- chưa có requirement bắt buộc Kubernetes hoặc microservices.

## Câu hỏi chính

Bạn sẽ xây modernization strategy như thế nào để chuyển hệ thống sang modern .NET với rủi ro có kiểm soát? Hãy so sánh rewrite-from-scratch với incremental modernization, xác định cách chọn migration boundaries, xử lý shared database/integrations/frontend, testing, rollout/rollback và hosting; đồng thời nêu điều kiện nào mới khiến microservices/Kubernetes trở thành lựa chọn hợp lý.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào thay đổi thường xuyên, module nào có business criticality/risk cao và dependency graph giữa chúng ra sao?
2. Third-party packages, authentication/session và SOAP integrations nào chặn modern .NET?
3. Có thể chạy old/new applications song song sau cùng domain/reverse proxy hay không?
4. Database schema ownership có thể tách theo module dần không, hay stored procedures/shared tables tạo coupling lớn?
5. Mục tiêu business ưu tiên là supportability, cloud hosting, deployment speed, performance hay feature velocity?

## Gợi ý tư duy

### Gợi ý 1

Đừng biến modernization thành một technology wishlist. Hãy map business risk, dependency và deployability trước.

### Gợi ý 2

Low test coverage làm big-bang rewrite và big-bang migration đều khó chứng minh behavioral equivalence. Characterization/integration/E2E tests có thể tạo safety net trước khi thay đổi sâu.

### Gợi ý 3

Bạn có thể modernize runtime/hosting và architecture theo nhiều bước khác nhau. Không nhất thiết đồng thời đổi backend framework, frontend framework, database boundaries và orchestration platform.

## Cấu trúc trả lời đề xuất

1. Xác định modernization goals và success metrics.
2. Inventory dependencies và blockers.
3. Lập module/dependency/risk map.
4. Tạo testing/observability baseline.
5. Chọn migration seams và sequence.
6. Thiết kế coexistence old/new và data boundaries.
7. Chọn hosting/deployment đơn giản nhất đáp ứng requirement.
8. Rollout/canary/rollback từng slice.
9. Theo dõi progress bằng operational/business metrics.
10. Định nghĩa triggers cho architecture complexity bổ sung.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite toàn bộ là tối ưu.
- Không mặc định giữ legacy vô thời hạn chỉ vì đang chạy.
- Inventory compatibility của libraries/integrations/auth/session/build/deployment trước khi cam kết roadmap.
- Tạo safety net bằng characterization, integration và critical Playwright E2E flows trước/đồng thời migration.
- Chọn vertical/module slices có boundary đủ rõ và business risk kiểm soát được.
- Có coexistence/traffic routing strategy và rollback per slice.
- Shared database là migration constraint quan trọng; tránh để old/new writers phá invariants.
- App Service/Linux/container hoặc IIS mới có thể là bước hosting hợp lý; Kubernetes không phải requirement mặc định.

### Điểm cộng

- Tách scheduled/background jobs khỏi web process khi lifecycle/scaling/reliability justify, nhưng không cần biến thành microservice ngay.
- Dùng strangler-style routing ở reverse proxy/gateway khi phù hợp để chuyển endpoint/module dần.
- Expand/contract schema changes giúp old/new versions coexist trong rollout.
- Frontend có thể modernize theo route/feature thay vì rewrite đồng thời toàn bộ UI.
- Establish telemetry baseline trước migration để biết version mới có thực sự tốt hơn.

### Senior+

- Xây dependency graph và chọn migration order giảm coupling thay vì chọn module theo sở thích.
- Phân biệt technical migration với domain decomposition; không dùng migration làm cớ tạo service boundaries chưa hiểu.
- Định nghĩa rollback compatibility window giữa code/schema/contracts.
- Có explicit exit criteria cho legacy module và decommission plan.
- Đưa ra measurable triggers cho microservices/Kubernetes: independent ownership/deployment/scaling, isolation/SLO khác biệt, workload/platform needs và operational maturity.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng mục tiêu, không phải target stack. Ví dụ mục tiêu có thể là đưa runtime về supported modern .NET, giảm lead time deployment, loại bỏ unsupported dependencies và giảm incident rate. Sau đó inventory toàn hệ thống: projects, packages, APIs, authentication/session, IIS assumptions, filesystem usage, SOAP clients, scheduled jobs, SQL dependencies, frontend coupling và CI/CD.

Với 25 modules, một team 8 người và business vẫn cần features, big-bang rewrite 12 tháng có rủi ro cao: requirements drift, behavioral gaps, delayed feedback và hai hệ thống phải được duy trì. Nhưng “không làm gì” cũng tích lũy platform/security/support risk. Tôi ưu tiên incremental modernization.

### Phase 1 — Safety net và observability

Chọn critical user journeys và tạo integration/API tests + Playwright E2E ở mức đủ bảo vệ behavior quan trọng. Không cần đợi 100% coverage. Ghi baseline latency/error/deployment metrics. Inventory package compatibility và spike các blockers khó nhất trước.

### Phase 2 — Tạo migration seam

Nếu routing cho phép, đặt reverse proxy/gateway hoặc routing layer để old/new applications có thể coexist. Chọn một module có boundary tương đối rõ, business value thực và blast radius vừa phải. Implement module đó trên modern ASP.NET Core, giữ contract tương thích khi cần, rồi route một phần traffic sang mới.

Không nhất thiết chọn microservice. New application có thể là một modular ASP.NET Core deployment. Mục tiêu là tạo đường di chuyển lặp lại được.

### Phase 3 — Data compatibility

Shared SQL database là rủi ro lớn. Tôi map table/stored-procedure ownership và writers. Trong giai đoạn coexistence, schema changes cần backward-compatible nếu old/new chạy song song. Dùng expand/contract khi phù hợp: thêm cấu trúc mới trước, migrate/backfill, chuyển readers/writers, rồi cleanup sau khi old version không còn dùng. Không cho hai implementations cập nhật cùng invariant theo semantics khác nhau mà không có coordination.

### Phase 4 — Frontend

Không rewrite toàn UI chỉ để đổi framework. Có thể migrate theo route/module: legacy jQuery/Angular tiếp tục ở phần chưa chuyển; module mới dùng React/Vue nếu team đã chọn và business benefit đủ. Shared design/auth/navigation contract cần rõ. E2E tests bảo vệ cross-boundary flows.

### Phase 5 — Jobs và integrations

Scheduled jobs đang sống trong web application cần review riêng. Nếu multi-instance hosting làm duplicate execution hoặc lifecycle web không phù hợp, chuyển chúng sang Worker Service/Azure Functions tùy execution semantics. Đây là operational boundary, không tự động là microservice/domain boundary.

External SOAP/REST integrations được bọc sau adapters để migration application code không lan vendor-specific coupling. Với unsupported library, đánh giá replace, isolate behind old process/API, hoặc rewrite phần nhỏ đó thay vì block toàn chương trình.

### Hosting

Nếu modern ASP.NET Core chạy tốt trên Azure App Service/Linux và đáp ứng networking/scale/SLO, đó có thể là target đơn giản hơn Kubernetes. Kubernetes chỉ đáng cân nhắc khi có nhiều workloads/services cần orchestration, independent scaling/deployment, platform controls hoặc organization standard và team đủ năng lực vận hành.

### Rollout

Mỗi slice có compatibility contract, feature flag/traffic routing khi phù hợp, canary, telemetry và rollback plan. Rollback phải xét schema: old binary chỉ rollback được nếu database vẫn tương thích. Migration progress được đo bằng số critical flows/modules chuyển, legacy dependency removed, deployment lead time, failure rate và operational outcomes chứ không chỉ lines of code rewritten.

## Mẫu trả lời trong phỏng vấn

“Với một team 8 người, 25 modules, low test coverage và business vẫn cần features, tôi không chọn big-bang rewrite. Tôi cũng không giữ nguyên legacy vô thời hạn. Tôi sẽ inventory dependency/package/auth/SQL/integration blockers, tạo characterization + integration + Playwright tests cho critical journeys và baseline telemetry trước.

Sau đó tôi chọn module có boundary rõ để migrate theo vertical slice sang ASP.NET Core, cho old/new coexist qua routing. Shared database cần ownership map và backward-compatible expand/contract changes để rollback được. Frontend cũng migrate theo route/feature thay vì đổi backend, UI, database và hosting cùng lúc.

Tôi ưu tiên App Service hoặc hosting đơn giản nếu đáp ứng SLO. Kubernetes/microservices chỉ vào khi có evidence về independent scaling, ownership, isolation hoặc orchestration needs. Mỗi slice phải có canary, telemetry và rollback compatibility. Mục tiêu là giảm risk từng bước và vẫn tiếp tục feature delivery.”

## Câu hỏi đào sâu

1. Nếu module đầu tiên bạn chọn có 70% tables dùng chung với legacy modules, bạn vẫn migrate nó hay chọn boundary khác?
2. Nếu CTO bắt buộc “microservices để future-proof”, bạn đưa ra criteria và experiment nào để kiểm chứng trước khi tăng complexity?
3. Nếu một authentication library quan trọng không hỗ trợ modern .NET nhưng business không thể thay provider trong 12 tháng, bạn thiết kế transitional architecture thế nào?

## Lỗi trả lời thường gặp

- Rewrite toàn bộ chỉ vì target stack mới hơn.
- Đổi backend, frontend, database decomposition và Kubernetes trong một cutover.
- Chờ đạt 100% unit-test coverage mới bắt đầu migration.
- Bỏ qua shared-database writers và rollback compatibility.
- Coi container/Kubernetes là mục tiêu modernization thay vì một hosting decision.

## Thang điểm 0–10

- **0–2:** Chỉ chọn rewrite hoặc “để nguyên” mà không phân tích risk.
- **3–4:** Có phased migration nhưng thiếu data/rollback/testing strategy.
- **5–6:** Có inventory, safety net, coexistence, vertical slices và hosting trade-offs.
- **7–8:** Xử lý tốt shared DB, frontend/jobs/integrations, rollout và metrics.
- **9–10:** Strategy evolvable dựa trên dependency/risk map, có compatibility windows và criteria rõ cho service/platform complexity.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Async I/O và parallel fan-out phải được đánh giá ở mức toàn hệ thống; giảm latency của một request có thể làm downstream contention tăng mạnh.
- `Task.Run` không phải cách sửa mặc định cho I/O-bound database work.
- Queue backlog cần phân tích arrival rate, sustainable completion rate, retry amplification và downstream capacity; CPU/health 200 không đủ để đánh giá workload health.
- At-least-once messaging yêu cầu idempotency ở business side-effect boundary và thiết kế cho partial failure.
- Modernization nên tách mục tiêu business/platform khỏi technology wishlist; incremental migration thường cần testing, compatibility và rollback seams rõ ràng.

## Mẫu tư duy cần nhớ

- **Measure system throughput, not only local latency.**
- **Scale only when the bottleneck can scale with you.**
- **Design retry together with idempotency and downstream protection.**
- **Create a safety net before changing legacy behavior.**
- **Add architectural complexity only when requirements justify it.**
