# Code Review Challenge 1 — EF Core bulk update bỏ qua optimistic concurrency làm ghi đè trạng thái Order

**Chủ đề:** C#/.NET, EF Core, SQL Server, optimistic concurrency, `ExecuteUpdateAsync`, transactions, background jobs, idempotency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một commerce backend có API cho customer cancel order và một background worker tự động chuyển các order `Pending` quá 30 phút sang `Expired`. Entity `Order` dùng SQL Server `rowversion` để tránh lost update ở các flow thông thường qua tracked entities.

Sau khi traffic tăng, team tối ưu worker bằng `ExecuteUpdateAsync` để không load hàng nghìn rows vào memory. Từ đó production xuất hiện một số order mà customer vừa thanh toán hoặc support vừa chuyển sang `Processing`, nhưng worker vẫn ghi thành `Expired`. Team cho rằng `rowversion` đã bảo vệ mọi update nên đây có thể chỉ là logging delay.

Bạn được giao review implementation dưới đây. Không giả định rằng concurrency token trên entity tự động áp dụng cùng semantics cho mọi bulk DML operation.

## Code cần review

```csharp
public sealed class Order
{
    public Guid Id { get; set; }
    public string Status { get; set; } = null!;
    public DateTime CreatedAtUtc { get; set; }
    public DateTime? PaidAtUtc { get; set; }

    [Timestamp]
    public byte[] Version { get; set; } = null!;
}

public sealed class ExpireOrdersWorker
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<ExpireOrdersWorker> _logger;

    public ExpireOrdersWorker(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<ExpireOrdersWorker> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task<int> RunAsync(CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);
        var cutoff = DateTime.UtcNow.AddMinutes(-30);

        var candidates = await db.Orders
            .AsNoTracking()
            .Where(x => x.Status == "Pending" && x.CreatedAtUtc < cutoff)
            .Select(x => new { x.Id, x.Version })
            .ToListAsync(cancellationToken);

        var ids = candidates.Select(x => x.Id).ToArray();

        var affected = await db.Orders
            .Where(x => ids.Contains(x.Id))
            .ExecuteUpdateAsync(
                setters => setters
                    .SetProperty(x => x.Status, "Expired"),
                cancellationToken);

        _logger.LogInformation(
            "Expired {Affected} orders from {CandidateCount} candidates",
            affected,
            candidates.Count);

        return affected;
    }
}
```

Một payment callback khác chạy đồng thời:

```csharp
public async Task MarkPaidAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders.SingleAsync(x => x.Id == orderId, ct);
    order.Status = "Paid";
    order.PaidAtUtc = DateTime.UtcNow;
    await _db.SaveChangesAsync(ct);
}
```

## Nhiệm vụ review

1. Xác định correctness/concurrency risks và dựng interleaving làm order `Paid` bị ghi thành `Expired`.
2. Giải thích chính xác `rowversion` bảo vệ tracked `SaveChanges` như thế nào và vì sao code bulk update hiện tại không dùng snapshot `Version` đã đọc.
3. Thiết kế một atomic predicate/update boundary phù hợp để chỉ expire order vẫn còn eligible tại thời điểm write.
4. Phân tích trade-off giữa set-based update, per-row optimistic concurrency và transaction/isolation.
5. Đề xuất tests, telemetry và rollout strategy để chứng minh bản sửa không tạo lost state transition.

## Gợi ý

### Gợi ý 1

Hãy tách thời điểm **đọc candidates** và thời điểm **thực hiện UPDATE**. Điều gì có thể thay đổi ở giữa?

### Gợi ý 2

Concurrency token chỉ hữu ích khi giá trị token được đưa vào điều kiện write hoặc framework tạo predicate tương đương.

### Gợi ý 3

Nếu business rule chỉ cần “expire nếu hiện tại vẫn Pending và quá cutoff”, có thể bạn không cần pre-read IDs để quyết định eligibility.

## Các vấn đề cần tìm

### Bắt buộc

- Có TOCTOU window giữa query candidates và `ExecuteUpdateAsync`; trạng thái order có thể đổi sau lần đọc đầu tiên.
- Bulk update thứ hai chỉ filter theo `Id`, không còn predicate `Status == "Pending"` và cutoff, nên eligibility không được re-check atomically tại write time.
- `Version` được select nhưng hoàn toàn không được dùng trong UPDATE predicate.
- `[Timestamp]`/`rowversion` không tự biến `ExecuteUpdateAsync` thành tracked optimistic-concurrency workflow giống `SaveChanges`.
- Interleaving hợp lệ: worker đọc Pending → payment callback update Paid → worker bulk update theo Id → status trở thành Expired.
- `affected == candidates.Count` không chứng minh correctness; nó có thể cho biết mọi row đã bị update, kể cả row không còn eligible.
- String status dễ cho phép invalid transition nếu state-machine invariants không được enforce tập trung.
- `ids.Contains` với candidate set lớn có thể tạo parameter/query-size/performance issues; preloading toàn bộ IDs cũng tăng memory và latency window.
- Không có telemetry cho attempted transition từ current status, conflict/skipped count hoặc evidence để reconstruct race.

### Điểm cộng

- Nếu rule đơn giản, dùng một set-based atomic UPDATE với đầy đủ predicate hiện tại: `Status == Pending`, cutoff và các business guards như `PaidAtUtc == null`.
- Nếu phải dựa trên snapshot riêng từng row, include `(Id, Version)` semantics trong write boundary và kiểm tra affected rows/conflicts.
- Không dùng transaction dài chỉ để giữ locks qua business processing nếu không có capacity analysis; isolation mạnh hơn có blocking/deadlock trade-off.
- Có thể dùng enum/value object/state-transition service để giảm invalid transition trong application, nhưng database predicate vẫn cần bảo vệ race.
- Payment callback cũng cần idempotency và transition rules; callback duplicate/out-of-order không được tùy ý ghi state.
- Index phù hợp cho eligibility predicate giúp set-based update tránh scan/lock footprint quá lớn.

## Hướng giải quyết tham khảo

Nếu business rule thực sự là “mọi order vẫn `Pending`, chưa paid và quá cutoff tại thời điểm update đều được expire”, thiết kế sạch nhất thường là một atomic set-based update trực tiếp trên predicate đó, thay vì query IDs trước rồi update sau:

```csharp
var cutoff = DateTime.UtcNow.AddMinutes(-30);

var affected = await db.Orders
    .Where(x => x.Status == "Pending"
             && x.PaidAtUtc == null
             && x.CreatedAtUtc < cutoff)
    .ExecuteUpdateAsync(
        s => s.SetProperty(x => x.Status, "Expired"),
        cancellationToken);
```

Điểm quan trọng là eligibility được đánh giá trong cùng SQL statement với write. Nếu workflow cần quyết định dựa trên snapshot phức tạp đã đọc trước đó, optimistic concurrency phải đưa expected version vào write condition và coi zero affected rows là conflict cần classify/retry/re-evaluate, không phải success im lặng.

Không nên mặc định dùng `Serializable` hoặc lock dài để chữa race. Isolation/locking có thể đúng cho một số invariant nhưng phải đánh giá contention, deadlocks, transaction duration và throughput. Atomic conditional DML thường đơn giản hơn khi invariant có thể biểu diễn trực tiếp trong predicate.

## Test nên có

- Deterministic concurrency test: pause worker sau candidate read, chạy `MarkPaidAsync`, sau đó resume worker; order không được thành `Expired`.
- Test support chuyển `Pending → Processing` trong cùng window.
- Test order vẫn Pending nhưng chưa qua cutoff tại write time không bị update.
- Test bulk update trên hàng nghìn rows với execution plan/index thực tế.
- Test duplicate/out-of-order payment callbacks và state transition idempotency.
- Test affected-row/conflict metrics khi có concurrent writers.
- Stress test nhiều worker replicas chạy expiration cùng lúc.

## Production observability

Theo dõi candidate/eligible count, affected count, skipped/conflict count, transition source, previous/current status khi có conflict, worker duration, SQL latency, lock waits/deadlocks và số payment callbacks concurrent với expiration window. Correlate bằng `OrderId` khi điều tra nhưng tránh high-cardinality labels trong metrics backend không phù hợp.

## Trade-offs

- Set-based conditional update có throughput tốt và thu hẹp race window nhưng ít linh hoạt hơn nếu mỗi row cần business computation riêng.
- Per-row optimistic concurrency cho conflict semantics rõ nhưng tăng round trips và overhead.
- Isolation mạnh có thể bảo vệ invariant rộng hơn nhưng đổi lấy blocking/deadlock/throughput cost.
- Database constraint/predicate bảo vệ write boundary tốt hơn việc chỉ kiểm tra state ở application trước đó.

## Câu hỏi đào sâu

1. Nếu expiration còn phụ thuộc inventory reservation ở bảng khác, một single-table predicate còn đủ không? Bạn bảo vệ invariant xuyên bảng thế nào?
2. Nếu hai worker cùng chạy atomic expiration statement, outcome và lock behavior bạn kỳ vọng là gì?
3. Khi `ExecuteUpdateAsync` trả `0`, trong trường hợp nào đó là conflict, trong trường hợp nào chỉ đơn giản là không còn row eligible?

## Thang điểm 0–10

- **0–2:** Chỉ thêm retry hoặc tăng transaction timeout.
- **3–4:** Nhận ra race nhưng tin `rowversion` tự bảo vệ bulk update.
- **5–6:** Re-check eligibility trong atomic UPDATE và hiểu tracked-vs-bulk concurrency semantics.
- **7–8:** Thiết kế transition invariant, conflict handling, indexes và deterministic concurrency tests.
- **9–10:** Reasoning đầy đủ về write boundary, isolation/locking trade-offs, multi-worker behavior, observability và rollout.

# Code Review Challenge 2 — JWT signing-key rotation làm API ngẫu nhiên trả 401 giữa nhiều replicas

**Chủ đề:** ASP.NET Core authentication, JWT, JWKS, key rotation, caching, distributed systems, security, availability, deployment, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core API chạy 8 replicas và validate JWT access token do internal Identity Service phát hành. Identity Service rotate signing key định kỳ và publish public keys tại endpoint JWKS. Để giảm latency, team tự viết `IssuerSigningKeyResolver`: mỗi process fetch JWKS một lần khi startup rồi giữ dictionary trong memory.

Trong lần key rotation gần đây, token mới hợp lệ trên một số pods nhưng bị `401` trên pods khác cho đến khi restart. Team đề xuất nếu không tìm thấy `kid` thì tạm bỏ signature validation để tránh outage trong lúc JWKS chưa cập nhật.

Bạn được giao review implementation sau. Availability không được đạt bằng cách chấp nhận token chưa được xác thực chữ ký.

## Code cần review

```csharp
var builder = WebApplication.CreateBuilder(args);

var http = new HttpClient();
var jwksJson = await http.GetStringAsync(
    builder.Configuration["Auth:JwksUrl"]!);

var jwks = new JsonWebKeySet(jwksJson);
var keys = jwks.Keys.ToDictionary(x => x.Kid);

builder.Services
    .AddAuthentication("Bearer")
    .AddJwtBearer("Bearer", options =>
    {
        options.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,
            ValidIssuer = builder.Configuration["Auth:Issuer"],
            ValidateAudience = true,
            ValidAudience = builder.Configuration["Auth:Audience"],
            ValidateLifetime = true,
            ValidateIssuerSigningKey = true,
            IssuerSigningKeyResolver = (_, _, kid, _) =>
            {
                if (kid is null)
                    return Array.Empty<SecurityKey>();

                return keys.TryGetValue(kid, out var key)
                    ? new[] { key }
                    : Array.Empty<SecurityKey>();
            }
        };
    });

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();
app.Run();
```

## Nhiệm vụ review

1. Xác định correctness, availability và security risks của key-loading/rotation strategy hiện tại.
2. Dựng timeline rotation giải thích vì sao token mới có thể pass/fail tùy replica.
3. Thiết kế refresh/cache behavior an toàn khi gặp unknown `kid`, JWKS outage và overlapping old/new keys.
4. Phân biệt fail-closed authentication với operational resilience; tuyệt đối không biến unknown key thành bypass signature validation.
5. Đề xuất tests, telemetry và rollout/key-rotation procedure cho production.

## Gợi ý

### Gợi ý 1

Key rotation thường cần một overlap window: verifier phải có thể validate token ký bằng key cũ còn sống và key mới vừa được phát hành.

### Gợi ý 2

Unknown `kid` có thể là legitimate rotation, stale cache hoặc attacker input. Refresh không được trở thành unbounded outbound request primitive.

### Gợi ý 3

Hãy xem startup fetch, steady-state refresh, cache expiry và IdP/JWKS outage là bốn failure modes khác nhau.

## Các vấn đề cần tìm

### Bắt buộc

- JWKS chỉ được fetch một lần tại startup; process sống lâu không thấy signing keys mới.
- Các replicas restart/deploy ở thời điểm khác nhau có thể giữ key snapshots khác nhau, tạo non-deterministic `401` theo pod routing.
- Startup phụ thuộc synchronous availability của JWKS endpoint; outage/network issue có thể ngăn application khởi động.
- Unknown `kid` chỉ trả empty keys; không có controlled refresh/retry path để xử lý legitimate rotation.
- Đề xuất bỏ signature validation khi unknown `kid` là critical security flaw: attacker có thể forge token/claims nếu validation bị bypass.
- Không có refresh throttling/single-flight; nếu bổ sung naive refresh-per-unknown-kid, attacker có thể gây request amplification tới Identity Service.
- Không định nghĩa cache TTL, stale-key retention hoặc overlap window tương thích với token lifetime/key-rotation policy.
- `new HttpClient()` ở startup bỏ qua managed client/resilience/telemetry configuration của application.
- Không có explicit clock-skew/token-lifetime/key-retirement reasoning; xóa old key quá sớm có thể invalidate token vẫn còn hợp lệ.

### Điểm cộng

- Ưu tiên metadata/JWKS management chuẩn của JWT/OIDC middleware khi architecture cho phép, thay vì tự xây cache nếu không cần thiết.
- Unknown `kid` có thể trigger bounded, rate-limited refresh với single-flight/coalescing; sau refresh vẫn không có key thì authentication phải fail closed.
- Cache last-known-good key set để chịu được JWKS outage ngắn hạn, nhưng không dùng stale key vô hạn mà không có policy.
- Identity Service nên publish new public key trước khi bắt đầu ký token bằng private key tương ứng; giữ old public key đủ lâu cho token cũ hết hạn cộng clock skew hợp lý.
- Validate algorithm/key type/issuer/audience/lifetime theo security contract; `kid` chỉ là selector, không phải bằng chứng trust.
- Refresh telemetry không được log raw JWT/secrets.

## Hướng giải quyết tham khảo

Nếu issuer hỗ trợ OIDC discovery/JWKS theo chuẩn, dùng configuration management của authentication stack để có refresh semantics đã được thiết kế cho signing-key rollover, thay vì snapshot thủ công. Dù dùng framework hay custom implementation, verifier phải luôn fail closed khi không thể xác minh signature.

Rotation procedure nên theo thứ tự: publish key mới trong JWKS → cho verifiers có thời gian refresh → bắt đầu ký token mới bằng key mới → tiếp tục publish key cũ cho tới khi mọi token hợp lệ ký bằng key cũ đã hết lifetime (cộng clock skew/propagation margin) → mới retire key cũ.

Với unknown `kid`, refresh phải bounded. Nhiều requests cùng gặp key mới chỉ nên tạo một refresh in-flight thay vì N outbound calls. Nếu JWKS tạm unavailable, last-known-good keys vẫn có thể validate token dùng key đã biết; token với unknown key tiếp tục bị reject cho tới khi verifier có trusted key material.

Cache policy phải cân bằng freshness và dependency availability. Không fetch JWKS trên mọi request, nhưng cũng không giữ snapshot bất biến suốt process lifetime.

## Test nên có

- Rotation integration test: publish new key, sau đó issuer bắt đầu ký bằng key mới; tất cả replicas cuối cùng validate mà không restart.
- Overlap test: token cũ vẫn hợp lệ sau khi key mới active cho tới hết intended lifetime.
- Unknown random `kid` flood: refresh rate phải bounded và Identity Service không bị amplification.
- JWKS outage trong khi token dùng known key: behavior theo last-known-good policy.
- JWKS outage với genuinely new key: request phải fail closed, không bypass signature.
- Malformed JWKS/duplicate `kid`/unsupported algorithm handling.
- Multi-replica test với cache age khác nhau.
- Clock skew/lifetime boundary test khi retire old key.

## Production observability

Theo dõi JWT validation failures theo reason class (`unknown_kid`, expired, issuer, audience, signature), JWKS refresh success/failure/latency, configuration age, last-successful-refresh time, refresh throttling/coalescing count và distribution của active `kid` values ở mức aggregate. Alert khi `unknown_kid` tăng đột biến hoặc last-successful-refresh vượt rotation safety window. Không log raw access token.

## Trade-offs

- Refresh thường xuyên giảm stale-key window nhưng tăng dependency traffic và exposure với JWKS outages.
- Last-known-good cache tăng availability cho known keys nhưng cần bounded staleness policy.
- Key overlap làm rotation an toàn hơn nhưng kéo dài thời gian old public key còn trusted; private old key phải được quản lý/revoke theo incident policy riêng.
- Fail closed có thể tạo temporary `401` khi trust material chưa cập nhật, nhưng fail open phá authentication boundary và không phải availability strategy chấp nhận được.

## Câu hỏi đào sâu

1. Nếu private signing key cũ bị compromise, rotation procedure khác gì so với routine rotation có overlap dài?
2. Nếu attacker gửi hàng nghìn token với random `kid`, bạn ngăn refresh storm nhưng vẫn refresh nhanh cho một legitimate new key thế nào?
3. Nếu Identity Service publish JWKS qua CDN cache 10 phút, TTL đó tương tác với key activation sequence và token lifetime ra sao?

## Thang điểm 0–10

- **0–2:** Restart pods sau mỗi rotation hoặc tắt signature validation khi lỗi.
- **3–4:** Biết cần refresh nhưng fetch lại JWKS trên mọi unknown `kid`.
- **5–6:** Có bounded refresh, fail-closed validation và overlap policy.
- **7–8:** Thiết kế multi-replica cache, last-known-good, single-flight, rotation procedure và integration tests.
- **9–10:** Reasoning đầy đủ về trust lifecycle, compromise-vs-routine rotation, amplification resistance, observability và operational trade-offs.
