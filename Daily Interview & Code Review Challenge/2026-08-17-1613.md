# Code Review Challenge 1 — Export dữ liệu lớn làm API tăng memory, GC pressure và timeout

**Chủ đề:** Memory & allocation, async/cancellation, EF Core query execution, resource lifetime, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API có endpoint export lịch sử giao dịch ra CSV cho người dùng doanh nghiệp. Dữ liệu mỗi lần export thường từ 20.000 đến 300.000 bản ghi, nhưng một số tenant có thể vượt 1 triệu bản ghi. Endpoint chạy trực tiếp trong web API vì ban đầu volume nhỏ và người dùng muốn bấm nút rồi tải file ngay.

Sau vài tháng, production xuất hiện các triệu chứng:

- Memory của process tăng mạnh khi nhiều người export cùng lúc.
- Gen 2 GC tăng và latency của các API không liên quan cũng tăng.
- Một số request bị timeout sau 60–90 giây.
- Khi client đóng browser giữa chừng, server vẫn tiếp tục query và tạo file.
- Một vài container bị restart do memory limit.
- SQL Server/PostgreSQL đều cho thấy query export đọc lượng dữ liệu rất lớn.

Team chưa muốn chuyển ngay sang một kiến trúc phức tạp, nhưng chấp nhận background processing nếu có lý do rõ ràng.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ReportController> _logger;

    public ReportController(
        AppDbContext db,
        ILogger<ReportController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("transactions/export")]
    public async Task<IActionResult> ExportTransactions(
        DateTime from,
        DateTime to)
    {
        var rows = await _db.Transactions
            .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
            .OrderBy(x => x.CreatedAt)
            .ToListAsync();

        var csv = new StringBuilder();
        csv.AppendLine("Id,CreatedAt,UserEmail,Amount,Description");

        foreach (var row in rows)
        {
            csv.AppendLine(
                $"{row.Id},{row.CreatedAt:O},{row.UserEmail},{row.Amount},{row.Description}");
        }

        var bytes = Encoding.UTF8.GetBytes(csv.ToString());
        var stream = new MemoryStream();
        await stream.WriteAsync(bytes);
        stream.Position = 0;

        _logger.LogInformation(
            "Generated transaction export from {From} to {To}, rows={Rows}, bytes={Bytes}",
            from,
            to,
            rows.Count,
            bytes.Length);

        return File(stream, "text/csv", "transactions.csv");
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ dataset bằng `ToListAsync()`

**Problem:** Query tải toàn bộ entity phù hợp vào memory trước khi bắt đầu tạo response.

**Why it happens:** `ToListAsync()` materialize toàn bộ kết quả; số lượng row có thể rất lớn.

**Production impact:** Memory tăng theo kích thước dataset. Nhiều export đồng thời có thể tạo memory amplification, tăng GC pressure và làm chậm cả process.

**Severity:** High

**Recommended fix:** Với direct export, stream dữ liệu theo từng row/chunk bằng `AsAsyncEnumerable()` hoặc pagination/keyset phù hợp. Chỉ projection các cột cần thiết.

### 2. Query read-only nhưng vẫn giữ tracking

**Problem:** EF Core mặc định có thể track entity trả về từ query thông thường.

**Why it happens:** Code dùng entity query trực tiếp mà không bật `AsNoTracking()`.

**Production impact:** Change tracker giữ thêm metadata/reference, làm tăng memory và CPU không cần thiết cho workload chỉ đọc.

**Severity:** High

**Recommended fix:** Dùng `AsNoTracking()` và projection sang DTO/anonymous type chỉ chứa các field cần export.

### 3. Nhiều bản sao lớn của cùng dữ liệu tồn tại đồng thời

**Problem:** Dữ liệu tồn tại lần lượt và có thể chồng lấp dưới dạng entity list, internal buffer của `StringBuilder`, chuỗi từ `ToString()`, `byte[]`, rồi `MemoryStream`.

**Why it happens:** Implementation xây toàn bộ file trong RAM rồi lại copy qua nhiều representation.

**Production impact:** Với file lớn, tổng memory thực tế có thể lớn hơn đáng kể kích thước CSV cuối cùng. Dưới tải, process dễ chạm memory limit.

**Severity:** High

**Recommended fix:** Ghi từng row trực tiếp vào response stream hoặc một stream đích, tránh `StringBuilder` + `ToString()` + `byte[]` toàn bộ.

### 4. Không propagate cancellation từ request

**Problem:** `ToListAsync()` và `WriteAsync()` không nhận `HttpContext.RequestAborted`.

**Why it happens:** Cancellation token không được truyền xuyên suốt pipeline.

**Production impact:** Client disconnect nhưng server vẫn query DB, allocate memory và build file, gây lãng phí CPU/DB connection/memory.

**Severity:** High

**Recommended fix:** Truyền `RequestAborted` vào mọi async operation hỗ trợ cancellation; trong streaming loop cũng kiểm tra token.

### 5. CSV escaping không đúng

**Problem:** Code nối string trực tiếp với dấu phẩy. `UserEmail` hoặc đặc biệt `Description` có thể chứa comma, quote hoặc newline.

**Why it happens:** CSV được coi như plain string concatenation.

**Production impact:** File bị lệch cột, dữ liệu sai hoặc khó import. Ngoài ra cần cân nhắc CSV formula injection nếu file được mở bằng spreadsheet và dữ liệu user-controlled bắt đầu bằng ký tự công thức.

**Severity:** High

**Recommended fix:** Dùng CSV writer đáng tin cậy hoặc implement escaping đúng chuẩn: quote field khi cần và double quote nội bộ. Với dữ liệu untrusted mở bằng spreadsheet, áp policy chống formula injection phù hợp.

### 6. Không giới hạn khoảng thời gian hoặc kích thước export

**Problem:** Client có thể yêu cầu khoảng thời gian rất lớn.

**Why it happens:** Endpoint không có guardrails theo date range, estimated rows hoặc business policy.

**Production impact:** Một request đơn lẻ có thể trở thành truy vấn rất nặng, ảnh hưởng DB và application.

**Severity:** Medium

**Recommended fix:** Xác định giới hạn nghiệp vụ; validate `from <= to`; giới hạn direct-export theo range hoặc row estimate. Với dataset lớn, chuyển sang background export.

### 7. Direct HTTP request không phù hợp cho export rất lớn

**Problem:** Request phải sống đủ lâu để query, serialize và truyền toàn bộ file.

**Why it happens:** Thiết kế ban đầu tối ưu cho dữ liệu nhỏ được giữ nguyên khi scale tăng.

**Production impact:** Timeout, connection bị giữ lâu, khó retry, trải nghiệm kém khi export mất nhiều phút.

**Severity:** Medium

**Recommended fix:** Dùng hai chế độ: export nhỏ có thể stream trực tiếp; export lớn tạo job nền, ghi file vào object storage/blob, lưu trạng thái và cho client tải khi hoàn tất.

### 8. Query có thể đọc nhiều cột hơn cần thiết

**Problem:** Query lấy full `Transaction` entity nhưng CSV chỉ cần vài field.

**Why it happens:** Không projection trước khi materialize/stream.

**Production impact:** Tăng network từ DB, allocation và materialization cost.

**Severity:** Medium

**Recommended fix:** `Select` đúng cột cần dùng trước khi enumeration.

### 9. Ordering chưa chắc deterministic nếu nhiều row có cùng `CreatedAt`

**Problem:** Chỉ `OrderBy(CreatedAt)`; nhiều row có thể cùng timestamp.

**Why it happens:** Không có tie-breaker ổn định.

**Production impact:** Nếu sau này chuyển sang chunk/keyset pagination, có thể skip/duplicate row nếu ordering không deterministic.

**Severity:** Medium

**Recommended fix:** Thêm `ThenBy(x => x.Id)` hoặc dùng keyset cursor dựa trên `(CreatedAt, Id)`.

### 10. `MemoryStream` do action sở hữu nhưng lifetime phụ thuộc FileResult

**Problem:** Code trả stream ra ngoài method và để framework đọc sau khi action kết thúc; hiện tại không dispose trong method là cần thiết để response còn đọc được, nhưng cách này làm ownership khó hiểu và gắn với thiết kế buffering không tối ưu.

**Why it happens:** `MemoryStream` được dùng như intermediate storage.

**Production impact:** Không phải lỗi chính, nhưng làm thiết kế phức tạp hơn và giữ buffer lớn lâu hơn cần thiết.

**Severity:** Low

**Recommended fix:** Với file nhỏ có thể dùng `File(byte[])` có giới hạn rõ ràng; với file lớn ưu tiên stream trực tiếp hoặc background file generation.

## Phiên bản code đề xuất

Ví dụ dưới đây minh hoạ direct export cho dataset có giới hạn. Nó projection, `AsNoTracking`, stream trực tiếp ra response, truyền cancellation và escape CSV. Với dataset rất lớn nên chuyển sang background job thay vì giữ request lâu.

```csharp
[HttpGet("transactions/export")]
public async Task ExportTransactions(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    if (from > to)
    {
        Response.StatusCode = StatusCodes.Status400BadRequest;
        return;
    }

    if (to - from > TimeSpan.FromDays(31))
    {
        Response.StatusCode = StatusCodes.Status422UnprocessableEntity;
        await Response.WriteAsync(
            "Direct export supports at most 31 days. Use background export for larger ranges.",
            cancellationToken);
        return;
    }

    Response.ContentType = "text/csv; charset=utf-8";
    Response.Headers.ContentDisposition =
        "attachment; filename=transactions.csv";

    await using var writer = new StreamWriter(
        Response.Body,
        new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
        bufferSize: 16 * 1024,
        leaveOpen: true);

    await writer.WriteLineAsync(
        "Id,CreatedAt,UserEmail,Amount,Description".AsMemory(),
        cancellationToken);

    var query = _db.Transactions
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
        .OrderBy(x => x.CreatedAt)
        .ThenBy(x => x.Id)
        .Select(x => new
        {
            x.Id,
            x.CreatedAt,
            x.UserEmail,
            x.Amount,
            x.Description
        })
        .AsAsyncEnumerable();

    await foreach (var row in query.WithCancellation(cancellationToken))
    {
        var line = string.Join(',',
            EscapeCsv(row.Id.ToString()),
            EscapeCsv(row.CreatedAt.ToString("O")),
            EscapeCsv(row.UserEmail),
            EscapeCsv(row.Amount.ToString(CultureInfo.InvariantCulture)),
            EscapeCsv(row.Description));

        await writer.WriteLineAsync(line.AsMemory(), cancellationToken);
    }

    await writer.FlushAsync(cancellationToken);
}

private static string EscapeCsv(string? value)
{
    value ??= string.Empty;

    var needsQuotes = value.Contains(',') ||
                      value.Contains('"') ||
                      value.Contains('\n') ||
                      value.Contains('\r');

    var escaped = value.Replace("\"", "\"\"");
    return needsQuotes ? $"\"{escaped}\"" : escaped;
}
```

Trong hệ thống production thực tế, nếu CSV mở bằng Excel và có field do user kiểm soát, nên bổ sung policy chống formula injection theo yêu cầu bảo mật của tổ chức. Với export rất lớn, luồng đề xuất là: tạo `ExportJob` → worker tạo file theo chunk/stream → lưu vào blob/object storage → cập nhật trạng thái → client poll hoặc nhận notification → tải file qua URL có thời hạn/quyền truy cập phù hợp.

## Trade-offs

- **Streaming trực tiếp** giảm memory đáng kể và cho client nhận dữ liệu sớm, nhưng request vẫn tồn tại lâu và nếu connection đứt giữa chừng thì client phải chạy lại.
- **Background export** phù hợp với dữ liệu rất lớn, có retry và audit tốt hơn, nhưng cần trạng thái job, storage, cleanup file và UX bất đồng bộ.
- **Chunk pagination** giúp kiểm soát memory nhưng phải dùng ordering deterministic; offset lớn có thể kém hiệu quả, keyset thường phù hợp hơn cho scan dài.
- **AsAsyncEnumerable** vẫn giữ database reader/connection trong thời gian enumeration; cần kiểm soát concurrency export để không chiếm quá nhiều connection.

## Cách kiểm thử

1. **Integration test — CSV correctness:** dữ liệu có comma, quote, newline và Unicode; verify file parse lại đúng số cột và giá trị.
2. **Cancellation test:** huỷ request khi đang export và xác nhận query/streaming dừng sớm, không tiếp tục chạy lâu ở server.
3. **Load test:** chạy nhiều export đồng thời với dataset lớn; đo working set, GC pause, request latency và DB connection pool.
4. **Large dataset test:** vài trăm nghìn row; verify memory không tăng tuyến tính theo toàn bộ file như implementation cũ.
5. **Security test:** field bắt đầu bằng `=`, `+`, `-`, `@` hoặc chứa dữ liệu nhạy cảm; kiểm tra policy sanitization/audit theo yêu cầu tổ chức.

## Quan sát trong production

- **Logs:** export id, tenant/user, range, mode direct/background, rows exported, elapsed time, cancellation reason, failure category; tránh log nội dung dữ liệu nhạy cảm.
- **Metrics:** active exports, rows/sec, export duration p95/p99, cancelled exports, failed exports, process working set, allocation rate, GC collections, DB pool usage.
- **Traces:** span cho query, serialization/streaming, storage upload nếu dùng background.
- **Alerts:** memory cao kéo dài, export failure rate tăng, DB pool saturation, background queue age tăng.
- **Database observations:** query duration, rows read, execution plan, index usage, lock/wait nếu có.

# Code Review Challenge 2 — Cache quyền truy cập sai scope gây cross-tenant authorization leak

**Chủ đề:** Authentication & authorization, caching, concurrency, sensitive-data exposure, error handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API dùng JWT để xác thực. Mỗi user có thể thuộc nhiều tenant và quyền truy cập được lưu trong database. Để giảm số lần query DB, team thêm một service cache quyền trong memory.

Production có 6 instance sau load balancer. Sau deployment mới, support nhận một incident nghiêm trọng: một user chuyển từ Tenant A sang Tenant B trong cùng phiên đăng nhập và đôi khi thấy API cho phép truy cập resource thuộc tenant mà user không còn quyền. Một số thay đổi role mất vài phút mới có hiệu lực. Log thỉnh thoảng chỉ ghi `Authorization lookup failed` nhưng request vẫn trả 200.

Team muốn giữ caching vì authorization DB lookup có tần suất cao, nhưng correctness và tenant isolation phải ưu tiên tuyệt đối.

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private static readonly Dictionary<string, HashSet<string>> Cache = new();

    private readonly AppDbContext _db;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        AppDbContext db,
        ILogger<PermissionService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<bool> HasPermissionAsync(
        ClaimsPrincipal user,
        string tenantId,
        string permission)
    {
        var userId = user.FindFirstValue(ClaimTypes.NameIdentifier)!;

        if (Cache.TryGetValue(userId, out var cachedPermissions))
        {
            return cachedPermissions.Contains(permission);
        }

        try
        {
            var permissions = await _db.UserRoles
                .Where(x => x.UserId == userId)
                .SelectMany(x => x.Role.Permissions)
                .Select(x => x.Name)
                .ToListAsync();

            Cache[userId] = permissions.ToHashSet();
            return Cache[userId].Contains(permission);
        }
        catch (Exception ex)
        {
            _logger.LogWarning(
                ex,
                "Authorization lookup failed for user {UserId} tenant {TenantId}",
                userId,
                tenantId);

            return true;
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Fail-open khi authorization lookup lỗi

**Problem:** Catch mọi exception và `return true`.

**Why it happens:** Code ưu tiên availability hơn security mà không phân loại failure.

**Production impact:** Khi DB timeout, exception hoặc bug query xảy ra, user được cấp quyền mặc dù hệ thống không xác minh được. Đây là authorization bypass.

**Severity:** Critical

**Recommended fix:** Authorization failure phải fail closed theo mặc định: trả false/forbid hoặc surface dependency failure theo policy. Không biến exception thành allow.

### 2. Query không lọc theo tenant

**Problem:** `_db.UserRoles.Where(x => x.UserId == userId)` bỏ qua `tenantId`.

**Why it happens:** Tenant context có trong method signature nhưng không được dùng trong data access.

**Production impact:** Permission của user ở Tenant A có thể được dùng khi kiểm tra Tenant B. Đây là cross-tenant authorization leak.

**Severity:** Critical

**Recommended fix:** Data model/query phải scope rõ theo tenant, ví dụ `Where(x => x.UserId == userId && x.TenantId == tenantId)` hoặc enforce tenant filter nhất quán ở repository/query layer.

### 3. Cache key chỉ theo `userId`

**Problem:** Cache không phân biệt tenant.

**Why it happens:** Permission set được coi như global cho user.

**Production impact:** Khi một user thuộc nhiều tenant, permission được tính lần đầu ở một tenant có thể tái sử dụng cho tenant khác.

**Severity:** Critical

**Recommended fix:** Cache key tối thiểu phải gồm `(userId, tenantId)` và nếu authorization phụ thuộc thêm dimension khác thì key cần phản ánh đúng security context đó.

### 4. `Dictionary` static không thread-safe cho concurrent writes

**Problem:** Nhiều request đồng thời đọc/ghi `Dictionary` dùng chung.

**Why it happens:** Shared mutable state không có synchronization.

**Production impact:** Race condition, exception hoặc state không nhất quán có thể xuất hiện dưới load.

**Severity:** High

**Recommended fix:** Dùng `IMemoryCache`, `ConcurrentDictionary` với design hợp lý hoặc cache abstraction chuẩn. Tuy nhiên thread-safety chỉ giải quyết concurrency, không tự giải quyết tenant isolation/invalidation.

### 5. Cache không có expiration

**Problem:** Entry sống vô thời hạn trong process.

**Why it happens:** Không TTL, không version và không event invalidation.

**Production impact:** User bị revoke quyền nhưng instance vẫn cho phép đến khi process restart. Security change không có bounded staleness.

**Severity:** High

**Recommended fix:** Đặt TTL ngắn theo risk profile và có invalidation/versioning khi role/permission membership thay đổi.

### 6. Multi-instance cache không đồng bộ

**Problem:** Static in-memory cache chỉ tồn tại trong từng process.

**Why it happens:** Không có cơ chế invalidate cross-instance.

**Production impact:** Sau khi quyền thay đổi, một instance có entry mới còn instance khác vẫn giữ quyền cũ, tạo behavior không nhất quán.

**Severity:** High

**Recommended fix:** Có thể dùng distributed cache hoặc publish invalidation event/version; hoặc giữ memory cache nhưng dùng permission version từ nguồn chia sẻ để phát hiện stale entry. Lựa chọn phụ thuộc latency, scale và security requirement.

### 7. Không truyền cancellation token vào query

**Problem:** `ToListAsync()` không nhận request cancellation.

**Why it happens:** Method không nhận `CancellationToken`.

**Production impact:** Request bị huỷ nhưng authorization DB query vẫn tiếp tục; dưới sự cố downstream có thể làm tăng pressure.

**Severity:** Medium

**Recommended fix:** Nhận token và truyền vào data access.

### 8. Cache stampede khi entry miss

**Problem:** Nhiều request đầu tiên cho cùng `(user, tenant)` có thể cùng query DB.

**Why it happens:** Không có single-flight/per-key synchronization.

**Production impact:** Khi cache expire hàng loạt hoặc instance mới start, authorization store có thể nhận spike lớn.

**Severity:** Medium

**Recommended fix:** Dùng cache abstraction có chiến lược chống stampede hoặc per-key async lock/single-flight nếu load thực tế cần. Không dùng global lock làm nghẽn toàn bộ user.

### 9. Null-forgiving cho user id che giấu identity validation

**Problem:** `FindFirstValue(...)!` giả định claim luôn tồn tại.

**Why it happens:** Authentication và authorization contract không được validate rõ.

**Production impact:** Principal không hợp lệ có thể gây exception thay vì explicit deny; exception lại nguy hiểm hơn trong code hiện tại vì catch phía dưới có thể dẫn đến allow ở một số refactor tương lai.

**Severity:** Medium

**Recommended fix:** Nếu user id thiếu/invalid thì deny rõ ràng; validate tenant claim/context tương ứng nếu kiến trúc yêu cầu.

### 10. Logging chưa đủ để audit quyết định authorization

**Problem:** Chỉ log khi DB lookup fail; không có structured reason cho allow/deny/cache hit/version.

**Why it happens:** Observability được thêm sau thay vì là một phần của security design.

**Production impact:** Khó điều tra vì sao một request được allow ở tenant cụ thể và entry cache nào được dùng.

**Severity:** Low

**Recommended fix:** Ghi audit/diagnostic metadata có kiểm soát: user internal id, tenant id, permission name, decision, source cache/db, permission version, trace id; không log token hoặc sensitive claims.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng `IMemoryCache`, key theo user + tenant, TTL ngắn, fail closed và query đúng tenant. Đây là baseline; với nhiều instance và yêu cầu revoke gần real-time cần bổ sung distributed invalidation hoặc permission version.

```csharp
public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IMemoryCache _cache;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        AppDbContext db,
        IMemoryCache cache,
        ILogger<PermissionService> logger)
    {
        _db = db;
        _cache = cache;
        _logger = logger;
    }

    public async Task<bool> HasPermissionAsync(
        ClaimsPrincipal user,
        string tenantId,
        string permission,
        CancellationToken cancellationToken)
    {
        var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);
        if (string.IsNullOrWhiteSpace(userId) ||
            string.IsNullOrWhiteSpace(tenantId) ||
            string.IsNullOrWhiteSpace(permission))
        {
            return false;
        }

        var cacheKey = $"permissions:{tenantId}:{userId}";

        if (!_cache.TryGetValue<HashSet<string>>(
                cacheKey,
                out var permissions))
        {
            try
            {
                var names = await _db.UserRoles
                    .AsNoTracking()
                    .Where(x => x.UserId == userId && x.TenantId == tenantId)
                    .SelectMany(x => x.Role.Permissions)
                    .Select(x => x.Name)
                    .Distinct()
                    .ToListAsync(cancellationToken);

                permissions = names.ToHashSet(StringComparer.Ordinal);

                _cache.Set(
                    cacheKey,
                    permissions,
                    new MemoryCacheEntryOptions
                    {
                        AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(2),
                        Size = 1
                    });
            }
            catch (OperationCanceledException)
                when (cancellationToken.IsCancellationRequested)
            {
                throw;
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Permission lookup failed. User={UserId} Tenant={TenantId} Permission={Permission}",
                    userId,
                    tenantId,
                    permission);

                return false;
            }
        }

        var allowed = permissions!.Contains(permission);

        _logger.LogDebug(
            "Authorization decision User={UserId} Tenant={TenantId} Permission={Permission} Allowed={Allowed}",
            userId,
            tenantId,
            permission,
            allowed);

        return allowed;
    }
}
```

Một production design mạnh hơn có thể lưu `PermissionVersion` theo `(tenantId, userId)` hoặc theo tenant. Khi admin thay đổi role/permission, transaction update quyền đồng thời tăng version và publish invalidation event. Mỗi cache entry mang version; instance phát hiện mismatch thì reload. Nếu yêu cầu revoke gần như tức thời, chỉ TTL 2 phút là chưa đủ và cần cơ chế invalidation đáng tin cậy hơn.

## Trade-offs

- **Memory cache** rất nhanh và đơn giản nhưng invalidation cross-instance khó hơn.
- **Distributed cache** cho state chia sẻ hơn nhưng thêm network dependency; khi cache lỗi vẫn phải giữ nguyên nguyên tắc fail closed đối với authorization decision.
- **TTL ngắn** giảm stale window nhưng tăng DB/cache load.
- **Event-driven invalidation** giảm stale permission nhanh hơn nhưng phải xử lý lost event, replay/recovery và consistency.
- **Permission versioning** giúp xác minh freshness rõ ràng nhưng thêm read/version management.

## Cách kiểm thử

1. **Security integration test:** cùng một user có quyền `Report.Read` ở Tenant A nhưng không có ở Tenant B; verify Tenant B luôn bị deny kể cả sau khi Tenant A đã populate cache.
2. **Revocation test:** populate cache, revoke role, trigger invalidation/version update và verify access bị deny trong SLA đã định.
3. **Failure-path test:** database/cache dependency timeout hoặc throw exception; verify request không bao giờ được allow chỉ vì dependency failure.
4. **Concurrency/load test:** hàng trăm request cùng miss một cache key; đo DB query count và kiểm tra không có race/corrupt state.
5. **Multi-instance test:** populate cache trên hai instance, thay đổi permission, verify invalidation propagate và decisions hội tụ đúng trong thời gian yêu cầu.

## Quan sát trong production

- **Logs:** authorization decision metadata ở level phù hợp; đặc biệt deny reason, cache/db source, version mismatch, lookup failures. Không log JWT/token raw.
- **Metrics:** authorization allow/deny count, cache hit ratio, permission lookup latency, lookup failure count, stale-version detection, invalidation propagation lag.
- **Traces:** span cho policy evaluation và DB/cache lookup; gắn tenant id dạng internal-safe tag nếu policy cho phép.
- **Alerts:** authorization dependency failure tăng, invalidation lag vượt SLA, deny/allow ratio thay đổi bất thường.
- **Audit:** admin role changes, permission grants/revokes, actor, tenant, timestamp và version mới.

## Câu hỏi phỏng vấn mở rộng

1. Nếu permission revocation phải có hiệu lực dưới 5 giây trên 50 instance, bạn thiết kế invalidation thế nào để vẫn chịu được message loss?
2. Nếu authorization store tạm thời unavailable, API nên trả 403, 503 hay behavior khác? Bạn quyết định dựa trên contract và security requirement nào?
3. Bạn sẽ tách Authentication, Tenant Resolution và Authorization responsibilities trong middleware/policy layer như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Dữ liệu lớn không chỉ gây chậm query; cách materialize và serialize có thể tạo nhiều bản sao trong memory và làm GC trở thành bottleneck toàn process.
- Read-only EF Core workload nên projection đúng cột và tránh tracking khi không cần.
- Cancellation phải được truyền xuyên suốt từ HTTP request xuống database và stream I/O.
- Authorization là security boundary: tenant scope, cache key và failure behavior đều phải đúng; dependency failure không được biến thành quyền truy cập.
- Cache authorization cần chiến lược freshness/invalidation rõ ràng, đặc biệt trong hệ thống multi-instance.

## Mẫu tư duy cần nhớ

1. **Theo dấu dữ liệu qua toàn pipeline** — DB → objects → serialization → buffers → network để tìm memory amplification.
2. **Security checks phải fail closed** — không xác minh được thì không tự động allow.
3. **Cache key phải chứa đầy đủ security context** — user id một mình thường không đủ trong multi-tenant system.
4. **Đặt guardrails trước khi scale** — range limit, concurrency limit, size threshold và background fallback.
5. **Observability là một phần của design** — đo memory, cancellation, authorization decisions và invalidation lag trước khi incident xảy ra.
