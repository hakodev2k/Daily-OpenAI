# Code Review Challenge 1 — API tìm kiếm đơn hàng chậm dần và trả kết quả không ổn định

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, LINQ, pagination, query/index optimization, API security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–40 phút  
**Số vấn đề cần tìm:** khoảng 10–13

## Bối cảnh

Một enterprise order portal có endpoint cho support tìm kiếm đơn hàng. Bảng `Orders` hiện có khoảng 18 triệu rows và tăng liên tục. Người dùng có thể lọc theo customer, status, khoảng thời gian và sort theo một số cột. UI dùng page number truyền thống.

Ở production, page đầu thường phản hồi dưới 300 ms nhưng page 2.000 có thể mất 8–15 giây. Support đôi lúc thấy một order xuất hiện ở hai page liên tiếp hoặc bị bỏ qua khi dữ liệu mới được tạo trong lúc họ chuyển page. Database CPU tăng mạnh khi nhiều người cùng export/search. Application Insights cho thấy dependency SQL chiếm phần lớn latency.

Endpoint chỉ dành cho support của một tenant. `tenantId` lấy từ authenticated user context; client không được phép đọc order của tenant khác. Team đề xuất tăng command timeout và thêm Redis cache cho toàn bộ kết quả search.

## Đoạn code cần review

```csharp
[HttpGet("orders")]
public async Task<IActionResult> Search(
    [FromQuery] OrderSearchRequest request,
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")!.Value;

    IQueryable<Order> query = _db.Orders;

    query = query.Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(request.Customer))
        query = query.Where(x => x.CustomerName.Contains(request.Customer));

    if (!string.IsNullOrWhiteSpace(request.Status))
        query = query.Where(x => x.Status == request.Status);

    if (request.FromUtc.HasValue)
        query = query.Where(x => x.CreatedAtUtc >= request.FromUtc.Value);

    if (request.ToUtc.HasValue)
        query = query.Where(x => x.CreatedAtUtc <= request.ToUtc.Value);

    query = request.SortBy switch
    {
        "customer" => request.Desc
            ? query.OrderByDescending(x => x.CustomerName)
            : query.OrderBy(x => x.CustomerName),
        "total" => request.Desc
            ? query.OrderByDescending(x => x.Total)
            : query.OrderBy(x => x.Total),
        _ => request.Desc
            ? query.OrderByDescending(x => x.CreatedAtUtc)
            : query.OrderBy(x => x.CreatedAtUtc)
    };

    var pageSize = request.PageSize ?? 100;
    var page = request.Page ?? 1;

    var total = await query.CountAsync(cancellationToken);

    var orders = await query
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync(cancellationToken);

    return Ok(new
    {
        total,
        page,
        pageSize,
        items = orders
    });
}
```

Giả sử model có nhiều navigation properties và một số text/blob metadata không cần hiển thị trong search result. Index hiện tại chưa được cung cấp; ứng viên phải yêu cầu execution plan/index metadata trước khi kết luận.

## Kết quả code review tham khảo

### High — Pagination không có deterministic tie-breaker

**Vấn đề:** Sort chỉ dùng một cột có thể không unique.  
**Tại sao xảy ra:** Nhiều orders có thể cùng `CreatedAtUtc`, `CustomerName` hoặc `Total`; SQL không đảm bảo thứ tự giữa các rows có sort key bằng nhau nếu không có ordering bổ sung.  
**Ảnh hưởng production:** Row có thể đổi vị trí giữa requests, gây duplicate/missing items giữa các page ngay cả khi dataset không đổi hoàn toàn.  
**Cách sửa:** Luôn thêm unique stable tie-breaker, ví dụ `ThenByDescending(x => x.Id)` theo cùng pagination contract.

### High — Deep offset pagination làm database thực hiện ngày càng nhiều công việc

**Vấn đề:** `Skip((page - 1) * pageSize)` tăng tuyến tính theo page number.  
**Tại sao xảy ra:** Database vẫn phải tìm/order và bỏ qua các rows trước offset trước khi trả page cần thiết; execution plan thực tế cần được xác minh.  
**Ảnh hưởng production:** Deep pages có latency/CPU/I/O cao, đặc biệt trên tập 18 triệu rows và sort/filter không được index phù hợp.  
**Cách sửa:** Với UX cho phép next/previous hoặc infinite scroll, dùng keyset/seek pagination với stable composite cursor. Nếu business bắt buộc random page number, phải chấp nhận trade-off hoặc dùng strategy khác dựa trên measured workload.

### High — Page size/page number không được validate

**Vấn đề:** Client có thể gửi page size rất lớn, zero/negative page hoặc giá trị gây overflow trong phép nhân.  
**Tại sao xảy ra:** Giá trị query string được dùng trực tiếp.  
**Ảnh hưởng production:** Query tốn tài nguyên, exception hoặc abuse làm tăng database load.  
**Cách sửa:** Validate `page >= 1`, giới hạn `pageSize` bằng server-side maximum và dùng arithmetic an toàn nếu vẫn dùng offset.

### High — Tracking full entities cho read-only search

**Vấn đề:** Query materialize toàn bộ `Order` entity và mặc định tracking.  
**Tại sao xảy ra:** Không dùng projection/`AsNoTracking`.  
**Ảnh hưởng production:** Đọc các cột không cần thiết, tăng network payload DB→app, allocations và change-tracker overhead.  
**Cách sửa:** Project trực tiếp sang DTO với đúng fields UI cần; dùng no-tracking semantics cho read-only query.

### Medium — `CountAsync` tạo thêm expensive query cho mỗi request

**Vấn đề:** Mỗi search luôn chạy một aggregate count trước data query.  
**Tại sao xảy ra:** API contract yêu cầu `total` dù UI có thể không cần exact count ở mọi bước.  
**Ảnh hưởng production:** Thêm round trip và database work; với filter ít selective, count có thể đáng kể.  
**Cách sửa:** Xác minh requirement. Có thể bỏ exact total cho cursor pagination, dùng `Take(pageSize + 1)` để trả `hasMore`, hoặc tính count riêng khi user thực sự cần.

### Medium — Search `Contains` cần được đánh giá bằng execution plan và search requirement

**Vấn đề:** Substring search trên `CustomerName` có thể không sử dụng index B-tree hiệu quả theo query shape/collation và dữ liệu.  
**Tại sao xảy ra:** Requirement là contains search nhưng data access được thiết kế như exact/prefix indexed lookup.  
**Ảnh hưởng production:** Scan lớn khi customer filter phổ biến.  
**Cách sửa:** Xác minh generated SQL + actual execution plan. Nếu requirement thực sự là substring/full-text, đánh giá SQL Server Full-Text Search hoặc search index; nếu prefix đủ, thay contract/query phù hợp. Không thêm Elasticsearch chỉ vì một query chậm mà chưa có evidence.

### Medium — Date boundary semantics chưa rõ

**Vấn đề:** `ToUtc <= value` dễ sai nếu UI truyền ngày thay vì timestamp cuối ngày.  
**Tại sao xảy ra:** API chưa định nghĩa inclusive/exclusive range và timezone conversion contract.  
**Ảnh hưởng production:** User có thể thiếu orders ở cuối khoảng thời gian.  
**Cách sửa:** Chuẩn hóa input UTC và ưu tiên half-open interval `[from, toExclusive)` khi UI làm việc theo date ranges.

### Medium — Claim access dùng null-forgiving operator mà không có explicit authorization contract

**Vấn đề:** `FindFirst(...)!.Value` giả định claim luôn tồn tại.  
**Tại sao xảy ra:** Authentication và tenant authorization invariant không được enforce/validate ở boundary.  
**Ảnh hưởng production:** Misconfigured token/policy có thể gây 500 thay vì 401/403; tenant isolation phụ thuộc vào một string claim không được thể hiện rõ trong authorization policy.  
**Cách sửa:** Enforce required tenant claim bằng authorization policy và resolve tenant qua typed service; mọi query vẫn phải include tenant boundary.

### Medium — Index strategy chưa được chứng minh

**Vấn đề:** Có nguy cơ thêm index theo cảm tính.  
**Tại sao xảy ra:** Filter/sort combinations rất đa dạng. Một index không thể tối ưu mọi permutation.  
**Ảnh hưởng production:** Over-indexing tăng storage/write cost nhưng query vẫn có thể chậm.  
**Cách sửa:** Thu thập Query Store/actual execution plans, frequency, logical reads, waits và top filter/sort patterns; thiết kế composite/covering indexes theo workload thực tế.

### Low — Response shape có thể expose domain fields ngoài contract

**Vấn đề:** Serialize entity trực tiếp trong `items`.  
**Tại sao xảy ra:** Persistence model được dùng làm API model.  
**Ảnh hưởng production:** Field mới thêm vào entity có thể vô tình xuất hiện trong API; payload lớn và coupling cao.  
**Cách sửa:** Explicit DTO projection.

## Phiên bản đề xuất

Ví dụ dưới đây chọn cursor pagination cho sort mặc định `CreatedAtUtc DESC, Id DESC`. Các sort khác cần cursor contract riêng hoặc bị giới hạn theo requirement; không nên giả vờ một cursor áp dụng đúng cho mọi sort.

```csharp
public sealed record OrderCursor(DateTime CreatedAtUtc, long Id);

[HttpGet("orders")]
public async Task<IActionResult> Search(
    [FromQuery] OrderSearchRequest request,
    CancellationToken cancellationToken)
{
    var tenantId = _tenantContext.RequiredTenantId;
    var pageSize = Math.Clamp(request.PageSize ?? 50, 1, 200);

    var query = _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(request.Status))
        query = query.Where(x => x.Status == request.Status);

    if (request.FromUtc is { } from)
        query = query.Where(x => x.CreatedAtUtc >= from);

    if (request.ToExclusiveUtc is { } to)
        query = query.Where(x => x.CreatedAtUtc < to);

    if (request.Cursor is { } cursor)
    {
        query = query.Where(x =>
            x.CreatedAtUtc < cursor.CreatedAtUtc ||
            (x.CreatedAtUtc == cursor.CreatedAtUtc && x.Id < cursor.Id));
    }

    var rows = await query
        .OrderByDescending(x => x.CreatedAtUtc)
        .ThenByDescending(x => x.Id)
        .Select(x => new OrderListItemDto
        {
            Id = x.Id,
            CustomerName = x.CustomerName,
            Status = x.Status,
            Total = x.Total,
            CreatedAtUtc = x.CreatedAtUtc
        })
        .Take(pageSize + 1)
        .ToListAsync(cancellationToken);

    var hasMore = rows.Count > pageSize;
    if (hasMore)
        rows.RemoveAt(rows.Count - 1);

    var nextCursor = hasMore && rows.Count > 0
        ? new OrderCursor(rows[^1].CreatedAtUtc, rows[^1].Id)
        : null;

    return Ok(new { items = rows, hasMore, nextCursor });
}
```

Một index ứng viên cho query mặc định có thể bắt đầu từ tenant + ordering key, nhưng cấu trúc chính xác phải được kiểm chứng bằng workload và execution plan. Status/date selectivity, included columns, write rate và các sort khác đều có thể thay đổi quyết định.

## Giải thích thiết kế sau khi sửa

Cursor chứa toàn bộ stable ordering key. Điều kiện seek và `ORDER BY` phải đồng nhất. Projection làm API contract explicit và giảm data materialization. Exact count được loại khỏi hot path nếu product chấp nhận `hasMore`; nếu UI bắt buộc hiển thị tổng chính xác, count là requirement riêng cần đo và tối ưu riêng.

## Trade-offs

Keyset pagination rất tốt cho sequential navigation nhưng không hỗ trợ nhảy trực tiếp tới page 2.000 như offset. Cursor phức tạp hơn khi hỗ trợ nhiều sort modes và phải encode/version an toàn. Composite indexes cải thiện read nhưng tăng write/storage cost. Full-text/search engine chỉ đáng dùng nếu search semantics và workload biện minh cho complexity đồng bộ dữ liệu.

## Cách kiểm thử

1. **Database integration test:** nhiều rows có cùng `CreatedAtUtc`; đi qua toàn bộ cursor pages và assert không duplicate/missing trên snapshot dữ liệu ổn định.
2. **Concurrency test:** insert order mới giữa hai page requests; xác minh cursor semantics được định nghĩa rõ và không làm đảo các rows đã đi qua.
3. **Load test:** so sánh p50/p95/p99, logical reads và DB CPU của offset sâu với seek pagination trên dataset gần production scale.
4. **Security test:** token thiếu/sai tenant claim và cross-tenant data; assert không có dữ liệu tenant khác.
5. **Query-plan test/benchmark:** capture generated SQL + actual execution plan cho các filter phổ biến trước khi quyết định index.

## Quan sát trong production

Theo dõi endpoint latency p50/p95/p99, SQL dependency duration, rows returned, logical reads/CPU qua database tooling, query timeout rate, top sort/filter patterns, query count và payload size. Correlate Application Insights request trace với SQL dependency. Alert dựa trên latency/error/SLO, không dựa đơn thuần vào một execution plan thay đổi.

# Code Review Challenge 2 — React search hiển thị dữ liệu của request cũ và tạo request storm

**Chủ đề:** React, TypeScript, browser networking, async race condition, request cancellation, state correctness, API integration, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một React admin portal có màn hình customer search. Khi support gõ nhanh vào ô search, browser gửi nhiều request liên tiếp. Production ghi nhận UI đôi lúc hiển thị kết quả của keyword trước đó dù textbox đang chứa keyword mới. Backend cũng thấy request rate tăng mạnh từ màn hình này và một số response lớn tiếp tục được xử lý sau khi user chuyển sang màn khác.

API yêu cầu tối thiểu 2 ký tự. UI phải phản hồi nhanh nhưng không được để response cũ overwrite state mới. Backend đã có rate limiting ở mức bảo vệ hệ thống, nhưng frontend vẫn phải tránh tạo traffic vô ích.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Customer = {
  id: string;
  name: string;
  email: string;
};

export function CustomerSearch() {
  const [query, setQuery] = useState("");
  const [customers, setCustomers] = useState<Customer[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (query.length < 2) {
      setCustomers([]);
      return;
    }

    setLoading(true);
    setError(null);

    fetch(`/api/customers?query=${query}`)
      .then(response => {
        if (!response.ok) {
          throw new Error(`HTTP ${response.status}`);
        }
        return response.json();
      })
      .then(data => {
        setCustomers(data);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [query]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search customers"
      />

      {loading && <div>Loading...</div>}
      {error && <div>{error}</div>}

      <ul>
        {customers.map(customer => (
          <li key={customer.id}>
            {customer.name} — {customer.email}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems liên quan async state.
2. Xác định performance/reliability/security concerns trong request construction và lifecycle.
3. Giải thích chính xác race condition theo timeline của hai request.
4. Ưu tiên vấn đề theo user impact và backend impact.
5. Đề xuất implementation tốt hơn mà không over-engineer.
6. Thiết kế tests tái hiện race deterministically.
7. Nêu browser/frontend/backend telemetry hữu ích.

## Câu hỏi gợi mở

1. Nếu request cho `ab` mất 900 ms nhưng request cho `abc` mất 100 ms, state cuối cùng là gì?
2. Cleanup function của `useEffect` có thể kiểm soát lifecycle request như thế nào?
3. Cancellation có thay thế debounce không, hay hai kỹ thuật giải quyết hai vấn đề khác nhau?
4. Query string hiện tại được tạo an toàn/chính xác với ký tự `&`, `+`, `?`, Unicode như thế nào?

## Kết quả code review tham khảo

### High — Response cũ có thể overwrite kết quả mới

**Vấn đề:** Mọi `fetch` completion đều gọi `setCustomers`.  
**Tại sao xảy ra:** Network completion order không được đảm bảo theo thứ tự effect chạy.  
**Ảnh hưởng production:** User gõ `abc`, thấy kết quả đúng, sau đó response chậm của `ab` quay về và thay bằng dữ liệu cũ.  
**Cách sửa:** Abort request cũ trong effect cleanup và/hoặc guard response bằng request generation/token để chỉ request hiện hành được cập nhật state.

### High — Mỗi keystroke sau ký tự thứ hai tạo request

**Vấn đề:** Không có debounce.  
**Tại sao xảy ra:** `query` đổi là effect chạy ngay.  
**Ảnh hưởng production:** Fast typing tạo request storm, tăng backend load và network waste; cancellation sau đó vẫn không hoàn toàn thay thế việc tránh tạo request.  
**Cách sửa:** Debounce input/search term với khoảng thời gian được đo theo UX; không hard-code như một universal optimum.

### High — Request cũ không bị hủy khi query đổi/unmount

**Vấn đề:** Không dùng `AbortController`.  
**Tại sao xảy ra:** Effect không trả cleanup function.  
**Ảnh hưởng production:** Browser/backend có thể tiếp tục công việc không còn giá trị; completion cũ còn có thể mutate state logic.  
**Cách sửa:** Tạo `AbortController` cho mỗi active effect, truyền `signal` vào `fetch`, abort trong cleanup và coi `AbortError` là expected control flow.

### Medium — Query parameter không được encode đúng

**Vấn đề:** Interpolation trực tiếp vào URL.  
**Tại sao xảy ra:** Ký tự đặc biệt có semantics trong URL query string.  
**Ảnh hưởng production:** Search sai hoặc tạo thêm query parameters ngoài ý muốn. Đây không tự động đồng nghĩa backend bị injection; backend vẫn phải validate input độc lập.  
**Cách sửa:** Dùng `URLSearchParams`.

### Medium — Loading state có race riêng

**Vấn đề:** Request cũ có thể `setLoading(false)` trong khi request mới vẫn chạy.  
**Tại sao xảy ra:** Boolean loading dùng chung cho nhiều concurrent operations.  
**Ảnh hưởng production:** Spinner biến mất sớm hoặc trạng thái UI không phản ánh active request.  
**Cách sửa:** Sau khi đảm bảo chỉ một active request bằng cleanup/cancellation, cập nhật loading theo request hiện hành; nếu có concurrency hợp lệ, dùng request identity/count thay boolean đơn giản.

### Medium — Nhánh query ngắn không reset đầy đủ state

**Vấn đề:** Khi query xuống dưới 2 ký tự, code clear customers nhưng không clear loading/error và không trực tiếp hủy request trước đó.  
**Tại sao xảy ra:** Early return chỉ xử lý data list.  
**Ảnh hưởng production:** UI có thể hiển thị spinner/error cũ; request cũ có thể hoàn thành sau đó.  
**Cách sửa:** Cleanup effect trước sẽ abort request cũ; nhánh invalid query reset state phù hợp với UX contract.

### Medium — Response shape được tin tưởng ở runtime

**Vấn đề:** TypeScript type không validate JSON từ network.  
**Tại sao xảy ra:** `response.json()` trả dữ liệu runtime không được đảm bảo bởi compile-time type.  
**Ảnh hưởng production:** API regression hoặc unexpected payload có thể gây UI lỗi khó chẩn đoán.  
**Cách sửa:** Với boundary quan trọng, validate response schema hoặc ít nhất có typed API client + contract/integration tests. Mức validation phụ thuộc risk; không cần thêm schema library cho mọi endpoint nhỏ.

### Low — Error UX expose raw transport message

**Vấn đề:** UI hiển thị `err.message` trực tiếp.  
**Tại sao xảy ra:** Technical error được dùng làm user-facing message.  
**Ảnh hưởng production:** UX kém và có thể lộ chi tiết không cần thiết nếu error source thay đổi.  
**Cách sửa:** Map lỗi sang user-safe message; gửi diagnostic detail vào telemetry.

## Phiên bản đề xuất

Ví dụ dưới đây debounce query và abort request cũ. Delay chỉ là scenario choice; production nên điều chỉnh theo UX/telemetry.

```tsx
import { useEffect, useState } from "react";

type Customer = {
  id: string;
  name: string;
  email: string;
};

export function CustomerSearch() {
  const [query, setQuery] = useState("");
  const [debouncedQuery, setDebouncedQuery] = useState("");
  const [customers, setCustomers] = useState<Customer[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const timer = window.setTimeout(() => {
      setDebouncedQuery(query.trim());
    }, 300);

    return () => window.clearTimeout(timer);
  }, [query]);

  useEffect(() => {
    if (debouncedQuery.length < 2) {
      setCustomers([]);
      setLoading(false);
      setError(null);
      return;
    }

    const controller = new AbortController();

    async function search() {
      setLoading(true);
      setError(null);

      try {
        const parameters = new URLSearchParams({ query: debouncedQuery });
        const response = await fetch(`/api/customers?${parameters}`, {
          signal: controller.signal
        });

        if (!response.ok)
          throw new Error(`HTTP ${response.status}`);

        const data: Customer[] = await response.json();

        if (!controller.signal.aborted)
          setCustomers(data);
      } catch (error) {
        if (error instanceof DOMException && error.name === "AbortError")
          return;

        if (!controller.signal.aborted)
          setError("Không thể tải danh sách customer.");
      } finally {
        if (!controller.signal.aborted)
          setLoading(false);
      }
    }

    void search();

    return () => controller.abort();
  }, [debouncedQuery]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search customers"
      />

      {loading && <div>Loading...</div>}
      {error && <div role="alert">{error}</div>}

      <ul>
        {customers.map(customer => (
          <li key={customer.id}>
            {customer.name} — {customer.email}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Trong codebase lớn, data-fetching library có thể cung cấp cancellation/dedup/cache semantics tốt hơn, nhưng không nên thêm dependency chỉ để che việc chưa hiểu request lifecycle. Backend vẫn phải enforce validation, authorization và rate limits; frontend optimization không phải security boundary.

## Giải thích thiết kế sau khi sửa

Debounce giảm request creation. Abort cleanup giảm wasted work và ngăn request cũ tiếp tục là active operation của component. `URLSearchParams` tạo query string đúng semantics. Error/loading chỉ được cập nhật bởi request còn relevant.

Nếu environment/library có trường hợp transport không thực sự dừng ngay sau abort, request-generation guard vẫn là một lớp correctness hữu ích. Mục tiêu là state transition phải gắn với search generation hiện hành.

## Trade-offs

Debounce quá dài làm UI cảm giác chậm; quá ngắn không giảm được nhiều traffic. Abort giúp client lifecycle nhưng backend có thể đã bắt đầu xử lý request trước khi cancellation tới hoặc có operation không propagate cancellation. Data-fetching library giảm boilerplate nhưng thêm abstraction/dependency. Runtime schema validation tăng robustness nhưng có cost về code/bundle/runtime.

## Cách kiểm thử

1. **Component test:** dùng controllable promises; request `ab` resolve sau `abc`, assert UI cuối cùng vẫn là kết quả `abc`.
2. **Fake-timer test:** gõ 5 ký tự nhanh, advance timer và assert chỉ request phù hợp được tạo sau debounce.
3. **Unmount/query-change test:** assert `AbortController.abort()` được gọi và aborted request không set error/data.
4. **E2E Playwright:** route API với latency khác nhau, gõ nhanh và xác minh UI không regress về stale result.
5. **Integration/security test:** query chứa `&`, `+`, Unicode và ký tự đặc biệt; xác minh request parameter đúng và backend vẫn enforce authorization.

## Quan sát trong production

Theo dõi requests-per-search-session, aborted request count nếu telemetry hỗ trợ, frontend search latency, error rate, backend request rate, API p95/p99, response size và rate-limit responses. Browser performance/network trace giúp xác minh request overlap. Correlation ID/trace context giữa frontend và API giúp phân biệt perceived latency với backend latency.

## Câu hỏi phỏng vấn mở rộng

1. Nếu không muốn debounce vì requirement yêu cầu search-as-you-type cực nhanh, bạn bảo vệ correctness và backend như thế nào?
2. Abort ở browser có đảm bảo SQL query phía backend dừng ngay không? Điều gì phải có trong ASP.NET Core/EF Core path?
3. Khi nào bạn chọn React Query/TanStack Query hoặc abstraction tương tự thay vì tự quản lý effect này?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Pagination là correctness contract và performance contract; stable ordering quan trọng không kém `Skip`/`Take`.
- Deep offset cần được đánh giá bằng execution plan và workload; keyset pagination là một trade-off, không phải universal replacement.
- Projection/no-tracking và API DTO giúp giảm work đồng thời làm contract rõ ràng hơn.
- Async UI phải giả định network responses có thể hoàn thành khác thứ tự khởi tạo.
- Debounce và cancellation giải quyết hai vấn đề khác nhau: request creation và request lifecycle.

## Mẫu tư duy cần nhớ

- Đo execution plan và production workload trước khi thêm index/cache.
- Stable ordering trước, pagination optimization sau.
- Không để asynchronous completion order quyết định state correctness.
- Hủy work không còn giá trị và vẫn thiết kế guard cho stale result.
- Frontend optimization không thay thế backend validation/authorization.
