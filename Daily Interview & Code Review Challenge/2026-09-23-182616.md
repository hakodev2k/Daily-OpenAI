# Code Review Challenge 1 — Typed HttpClient bị race condition khi refresh access token

**Chủ đề:** C#/.NET, ASP.NET Core, HttpClientFactory, async/concurrency, OAuth access token, retry, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một ASP.NET Core API tích hợp với hệ thống CRM bên thứ ba. API chạy trên nhiều Azure App Service instances và có thể xử lý vài trăm request đồng thời. CRM dùng OAuth access token có thời hạn ngắn. Team tạo một typed client để tự lấy token và retry khi nhận `401`.

Production xuất hiện các triệu chứng không ổn định: khi token gần hết hạn, số request tới token endpoint tăng đột biến; một số CRM request gửi token cũ dù một request khác vừa refresh thành công; latency p99 tăng mạnh; khi CRM chậm, request từ client đã bị hủy nhưng backend vẫn tiếp tục gọi CRM. Log đôi lúc chứa token endpoint response body để “debug nhanh”.

Không có yêu cầu exactly-once từ CRM. Một số endpoint CRM là `GET`, nhưng typed client cũng sẽ được tái sử dụng cho các thao tác `POST` tạo dữ liệu.

## Đoạn code cần review

```csharp
public sealed class CrmClient
{
    private readonly HttpClient _httpClient;
    private readonly IConfiguration _configuration;
    private readonly ILogger<CrmClient> _logger;

    private string? _accessToken;
    private DateTime _expiresAtUtc;

    public CrmClient(
        HttpClient httpClient,
        IConfiguration configuration,
        ILogger<CrmClient> logger)
    {
        _httpClient = httpClient;
        _configuration = configuration;
        _logger = logger;
    }

    public async Task<CustomerDto?> GetCustomerAsync(
        Guid customerId,
        CancellationToken cancellationToken)
    {
        if (_accessToken is null || DateTime.UtcNow >= _expiresAtUtc)
            await RefreshTokenAsync();

        _httpClient.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", _accessToken);

        var response = await _httpClient.GetAsync(
            $"customers/{customerId}");

        if (response.StatusCode == HttpStatusCode.Unauthorized)
        {
            await RefreshTokenAsync();

            _httpClient.DefaultRequestHeaders.Authorization =
                new AuthenticationHeaderValue("Bearer", _accessToken);

            response = await _httpClient.GetAsync(
                $"customers/{customerId}");
        }

        if (!response.IsSuccessStatusCode)
        {
            var body = await response.Content.ReadAsStringAsync();
            _logger.LogError(
                "CRM failed with {StatusCode}: {Body}",
                response.StatusCode,
                body);

            return null;
        }

        return await response.Content
            .ReadFromJsonAsync<CustomerDto>();
    }

    private async Task RefreshTokenAsync()
    {
        var clientId = _configuration["Crm:ClientId"];
        var clientSecret = _configuration["Crm:ClientSecret"];

        var response = await _httpClient.PostAsJsonAsync(
            "/oauth/token",
            new { clientId, clientSecret });

        var body = await response.Content.ReadAsStringAsync();
        _logger.LogInformation("CRM token response: {Body}", body);

        var token = JsonSerializer.Deserialize<TokenResponse>(body)!;

        _accessToken = token.AccessToken;
        _expiresAtUtc = DateTime.UtcNow.AddSeconds(token.ExpiresIn);
    }
}
```

## Kết quả code review tham khảo

### Critical — Log toàn bộ token response

**Vấn đề:** Token endpoint response body được ghi ở `Information` level.  
**Tại sao xảy ra:** Debugging dựa trên raw payload thay vì structured metadata an toàn.  
**Ảnh hưởng production:** Access token hoặc dữ liệu nhạy cảm có thể đi vào Application Insights/log aggregation và được đọc bởi nhiều principal hơn hệ thống secret store.  
**Cách sửa:** Không log token, client secret hoặc raw authentication payload. Chỉ log outcome, duration, status code, token refresh reason và correlation metadata không nhạy cảm.

### High — Token refresh stampede

**Vấn đề:** Mọi request đều có thể đồng thời gọi `RefreshTokenAsync`.  
**Tại sao xảy ra:** Check `_accessToken`/`_expiresAtUtc` và refresh không được phối hợp.  
**Ảnh hưởng production:** Khi token hết hạn, token endpoint nhận burst lớn, làm tăng latency, throttling và có thể tạo cascading failure.  
**Cách sửa:** Tách token acquisition thành service riêng có single-flight/`SemaphoreSlim` trong mỗi process, kiểm tra lại expiration sau khi lấy lock. Với nhiều App Service instances, mỗi instance vẫn có token cache riêng; điều đó thường chấp nhận được nếu identity provider cho phép, nhưng phải quan sát refresh volume và rate limits.

### High — Shared mutable `DefaultRequestHeaders.Authorization`

**Vấn đề:** Header authorization được mutate trên shared `HttpClient`.  
**Tại sao xảy ra:** Token được coi như global mutable request state.  
**Ảnh hưởng production:** Concurrent operations có thể quan sát header thay đổi giữa các request; thiết kế khó reason và dễ gửi credential sai khi client mở rộng cho nhiều authentication context.  
**Cách sửa:** Tạo `HttpRequestMessage` cho từng operation và đặt `request.Headers.Authorization` trên request đó; hoặc dùng `DelegatingHandler` chuyên trách authentication.

### High — Refresh failure vẫn có thể cập nhật state không hợp lệ

**Vấn đề:** `RefreshTokenAsync` không kiểm tra `IsSuccessStatusCode`, không validate payload và dùng null-forgiving operator.  
**Tại sao xảy ra:** Code giả định token endpoint luôn trả success JSON đúng schema.  
**Ảnh hưởng production:** `500`, HTML error page, malformed JSON hoặc authentication failure có thể gây exception không rõ nguyên nhân hoặc state token sai.  
**Cách sửa:** Validate status, deserialize có kiểm tra, reject token rỗng/expiration bất hợp lệ và map lỗi authentication/dependency rõ ràng.

### High — Không propagate `CancellationToken`

**Vấn đề:** `GetAsync`, `PostAsJsonAsync`, `ReadAsStringAsync` và JSON read không nhận request cancellation.  
**Tại sao xảy ra:** Parameter tồn tại nhưng không được truyền xuống dependency calls.  
**Ảnh hưởng production:** Client disconnect/timeout nhưng App Service vẫn giữ socket, memory và dependency work. Dưới load, lượng orphaned work có thể làm tail latency tệ hơn.  
**Cách sửa:** Propagate cancellation tới toàn bộ async I/O; nếu cần dependency timeout riêng, kết hợp policy timeout với request cancellation thay vì bỏ qua caller cancellation.

### High — Retry `401` không có semantics rõ cho future write operations

**Vấn đề:** Pattern “refresh rồi gửi lại” dễ được copy sang `POST` mà không xét idempotency.  
**Tại sao xảy ra:** Code coi mọi retry là tương đương.  
**Ảnh hưởng production:** Nếu server đã xử lý write nhưng response/auth path không rõ ràng, retry có thể tạo duplicate side effect.  
**Cách sửa:** Chỉ auto-retry operation được chứng minh safe/idempotent; với write cần idempotency key hoặc contract rõ từ CRM. Phân biệt authentication retry với transient retry.

### Medium — Refresh đúng lúc expiry, không có safety window

**Vấn đề:** Token chỉ refresh khi local clock đã đạt expiration.  
**Tại sao xảy ra:** Không có skew/network safety margin.  
**Ảnh hưởng production:** Token có thể hết hạn trong lúc request đang transit hoặc server/identity provider có clock skew.  
**Cách sửa:** Coi token hết hạn sớm hơn một khoảng nhỏ có cấu hình/được chọn theo measured latency và token lifetime; không hard-code margin lớn hơn lifetime thực tế.

### Medium — Error contract bị mất

**Vấn đề:** Mọi CRM non-success đều biến thành `null`.  
**Tại sao xảy ra:** Client không phân biệt `404`, `429`, `5xx`, auth failure và invalid response.  
**Ảnh hưởng production:** Caller không thể quyết định retry, map `404`, degrade hay trả `503`; observability cũng mất semantics.  
**Cách sửa:** Dùng typed result/exception hierarchy phù hợp hoặc return type thể hiện not-found, transient dependency failure và permanent failure.

### Medium — Response disposal không rõ ràng

**Vấn đề:** `HttpResponseMessage` bị thay thế khi retry và không được dispose rõ.  
**Tại sao xảy ra:** Method xử lý response như DTO thay vì disposable transport resource.  
**Ảnh hưởng production:** Resource cleanup trở nên phụ thuộc implementation/GC; đặc biệt nhánh retry làm ownership khó theo dõi.  
**Cách sửa:** Dùng `using` cho từng response và tách send attempt thành method có ownership rõ ràng.

### Medium — Secret retrieval/configuration boundary yếu

**Vấn đề:** Client secret được đọc trực tiếp từ generic configuration mỗi refresh.  
**Tại sao xảy ra:** Authentication concern bị trộn vào CRM API client.  
**Ảnh hưởng production:** Khó enforce secret source/rotation/least privilege và khó test.  
**Cách sửa:** Bind/validate options và ưu tiên secret source phù hợp như Key Vault; nếu CRM hỗ trợ workload identity/federated credential phù hợp thì đánh giá để giảm static secret, nhưng không giả định provider hỗ trợ.

### Low — `DateTime.UtcNow` làm token policy khó test

**Vấn đề:** Time source hard-coded.  
**Tại sao xảy ra:** Token cache phụ thuộc trực tiếp system clock.  
**Ảnh hưởng production:** Không phải lỗi runtime chính, nhưng expiration/concurrency tests khó deterministic.  
**Cách sửa:** Dùng `TimeProvider` trong modern .NET hoặc abstraction clock phù hợp codebase.

## Phiên bản đề xuất

Một cách tách responsibility:

```csharp
public sealed class CrmTokenProvider
{
    private readonly HttpClient _authClient;
    private readonly CrmOptions _options;
    private readonly TimeProvider _timeProvider;
    private readonly SemaphoreSlim _refreshLock = new(1, 1);

    private TokenState? _current;

    public CrmTokenProvider(
        HttpClient authClient,
        IOptions<CrmOptions> options,
        TimeProvider timeProvider)
    {
        _authClient = authClient;
        _options = options.Value;
        _timeProvider = timeProvider;
    }

    public async Task<string> GetTokenAsync(CancellationToken cancellationToken)
    {
        if (IsUsable(_current))
            return _current!.AccessToken;

        await _refreshLock.WaitAsync(cancellationToken);
        try
        {
            if (IsUsable(_current))
                return _current!.AccessToken;

            using var response = await _authClient.PostAsJsonAsync(
                "oauth/token",
                new
                {
                    clientId = _options.ClientId,
                    clientSecret = _options.ClientSecret
                },
                cancellationToken);

            if (!response.IsSuccessStatusCode)
                throw new CrmAuthenticationException(response.StatusCode);

            var token = await response.Content
                .ReadFromJsonAsync<TokenResponse>(cancellationToken)
                ?? throw new CrmAuthenticationException("Empty token response");

            if (string.IsNullOrWhiteSpace(token.AccessToken) || token.ExpiresIn <= 0)
                throw new CrmAuthenticationException("Invalid token response");

            _current = new TokenState(
                token.AccessToken,
                _timeProvider.GetUtcNow().AddSeconds(token.ExpiresIn));

            return _current.AccessToken;
        }
        finally
        {
            _refreshLock.Release();
        }
    }

    public void Invalidate(string token)
    {
        if (_current?.AccessToken == token)
            _current = null;
    }

    private bool IsUsable(TokenState? token)
    {
        if (token is null)
            return false;

        var refreshBefore = TimeSpan.FromSeconds(30);
        return _timeProvider.GetUtcNow() < token.ExpiresAt - refreshBefore;
    }

    private sealed record TokenState(
        string AccessToken,
        DateTimeOffset ExpiresAt);
}
```

CRM client đặt auth header trên từng request:

```csharp
public sealed class CrmClient
{
    private readonly HttpClient _httpClient;
    private readonly CrmTokenProvider _tokens;

    public CrmClient(HttpClient httpClient, CrmTokenProvider tokens)
    {
        _httpClient = httpClient;
        _tokens = tokens;
    }

    public async Task<CustomerDto?> GetCustomerAsync(
        Guid customerId,
        CancellationToken cancellationToken)
    {
        var token = await _tokens.GetTokenAsync(cancellationToken);
        using var first = await SendGetAsync(customerId, token, cancellationToken);

        if (first.StatusCode == HttpStatusCode.NotFound)
            return null;

        if (first.StatusCode != HttpStatusCode.Unauthorized)
            return await ReadSuccessAsync(first, cancellationToken);

        _tokens.Invalidate(token);
        var refreshed = await _tokens.GetTokenAsync(cancellationToken);

        using var second = await SendGetAsync(
            customerId,
            refreshed,
            cancellationToken);

        return await ReadSuccessAsync(second, cancellationToken);
    }

    private async Task<HttpResponseMessage> SendGetAsync(
        Guid id,
        string token,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"customers/{id}");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", token);

        return await _httpClient.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);
    }

    private static async Task<CustomerDto> ReadSuccessAsync(
        HttpResponseMessage response,
        CancellationToken cancellationToken)
    {
        if (!response.IsSuccessStatusCode)
            throw new CrmDependencyException(response.StatusCode);

        return await response.Content
            .ReadFromJsonAsync<CustomerDto>(cancellationToken)
            ?? throw new CrmDependencyException("Invalid CRM payload");
    }
}
```

Đây là skeleton để thể hiện boundary, không phải universal library. Nếu authentication flow phức tạp, một `DelegatingHandler` có thể phù hợp hơn. Retry/backoff cho `429`/`5xx` phải có bounded policy, jitter và chỉ áp dụng khi operation semantics cho phép.

## Giải thích thiết kế sau khi sửa

Token acquisition trở thành một responsibility riêng và có single-flight refresh trong process. Request-specific authorization không mutate shared defaults. `401` làm invalidation token rồi thử lại đúng một lần cho `GET`; transient retry là policy khác. Caller cancellation được truyền xuyên suốt. Error type giữ đủ semantics để tầng API quyết định mapping.

## Trade-offs

`SemaphoreSlim` chỉ phối hợp trong một process; nhiều App Service instances vẫn refresh độc lập. Distributed lock thường không đáng thêm chỉ để chia sẻ access token nếu identity provider chịu được số instance và token endpoint quota phù hợp. Caching token tập trung bằng Redis lại tạo thêm dependency và secret-bearing data path. Một authentication handler giảm duplicate code nhưng có thể che retry behavior nếu abstraction quá “magic”.

## Cách kiểm thử

1. **Concurrency test:** 100 concurrent calls với token expired; fake token endpoint phải được gọi một lần trong một process và tất cả request dùng token mới.
2. **Failure-path test:** token endpoint trả `500`, malformed JSON, token rỗng và cancellation; state cũ không được ghi đè thành token invalid.
3. **Integration test:** CRM trả `401` lần đầu rồi success; xác minh chỉ một auth retry và request thứ hai dùng token mới.
4. **Cancellation test:** hủy request trong lúc CRM chậm; outbound operation phải dừng trong budget dự kiến.
5. **Write semantics test:** nếu sau này thêm `POST`, xác minh không auto-retry trừ khi contract/idempotency key cho phép.

## Quan sát trong production

Theo dõi CRM dependency duration/error theo status code, token refresh count/success/failure/duration, số refresh concurrent, `401` rate, `429` rate, request cancellation, p50/p95/p99 và retry count. Trace phải correlate inbound request với outbound CRM dependency nhưng không chứa access token/client secret. Alert khi token refresh failure tăng hoặc refresh rate lệch mạnh so với expected token lifetime × instance count.

3. Khi nào bạn dùng `DelegatingHandler` thay vì gọi `CrmTokenProvider` trực tiếp trong typed client?

# Code Review Challenge 2 — Optimizely page cache và Akamai làm nội dung đã publish vẫn stale

**Chủ đề:** Optimizely CMS, ASP.NET Core, Akamai/CDN, HTTP caching, cache invalidation, SEO, deployment/operations  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút

## Bối cảnh

Một marketing website dùng Optimizely CMS và được phân phối qua Akamai. Editors publish campaign pages nhiều lần trong ngày. Team muốn giảm origin load nên thêm một middleware tự cache HTML trong memory và cấu hình `Cache-Control` dài cho mọi response.

Sau release, production có các triệu chứng:

- editor publish nội dung mới nhưng một số người dùng vẫn thấy bản cũ hàng giờ;
- hai App Service instances đôi lúc trả hai phiên bản page khác nhau;
- authenticated preview/editor traffic có lúc nhận HTML public đã cache;
- redirect và `404` thỉnh thoảng bị giữ ở edge lâu hơn mong muốn;
- query string dùng cho preview/campaign tracking tạo behavior cache khó dự đoán;
- team thường “fix” bằng purge toàn site trên Akamai.

Origin chạy nhiều instances. Requirement: public published pages có thể cache mạnh, nhưng preview/authenticated/editor responses không được chia sẻ như public content. Khi publish, freshness cần đạt SLA rõ ràng thay vì dựa vào restart application.

## Đoạn code cần review

```csharp
public sealed class PageCacheMiddleware
{
    private readonly RequestDelegate _next;
    private static readonly Dictionary<string, CachedPage> Cache = new();

    public PageCacheMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var key = context.Request.Path.Value ?? "/";

        if (Cache.TryGetValue(key, out var cached) &&
            cached.ExpiresAtUtc > DateTime.UtcNow)
        {
            context.Response.StatusCode = cached.StatusCode;
            context.Response.ContentType = cached.ContentType;
            await context.Response.WriteAsync(cached.Html);
            return;
        }

        var originalBody = context.Response.Body;
        await using var buffer = new MemoryStream();
        context.Response.Body = buffer;

        await _next(context);

        buffer.Position = 0;
        var html = await new StreamReader(buffer).ReadToEndAsync();

        Cache[key] = new CachedPage(
            html,
            context.Response.StatusCode,
            context.Response.ContentType ?? "text/html",
            DateTime.UtcNow.AddHours(6));

        context.Response.Headers.CacheControl =
            "public,max-age=21600,s-maxage=21600";

        context.Response.Body = originalBody;
        await context.Response.WriteAsync(html);
    }

    private sealed record CachedPage(
        string Html,
        int StatusCode,
        string ContentType,
        DateTime ExpiresAtUtc);
}
```

## Kết quả code review tham khảo

### Critical — Authenticated/preview response có thể bị lưu như public HTML

**Vấn đề:** Middleware cache mọi response theo path và sau đó gắn `public`.  
**Tại sao xảy ra:** Không có cache eligibility dựa trên authentication, preview/edit mode, cookies, authorization hay response metadata.  
**Ảnh hưởng production:** Nội dung dành cho editor/preview hoặc personalized response có thể bị phục vụ cho request khác; đây là security/data-isolation issue chứ không chỉ stale content.  
**Cách sửa:** Bypass shared caching cho authenticated, preview/edit và personalized responses. Chỉ public-cache route/content đã được xác định explicit là shareable.

### High — Cache key chỉ dùng path

**Vấn đề:** Query string, host/site, language/culture và các response-varying dimensions khác không nằm trong key.  
**Tại sao xảy ra:** Key quá đơn giản so với routing/content model thực tế.  
**Ảnh hưởng production:** Request khác nhau có thể nhận cùng HTML; multilingual/multisite/preview/query-dependent content có thể bị trộn.  
**Cách sửa:** Trước hết giảm phạm vi cache về public canonical content; sau đó định nghĩa key từ đúng dimensions. Không đưa mọi query parameter vào key một cách mù quáng vì sẽ tạo cache fragmentation/cardinality explosion.

### High — `Dictionary` static không thread-safe

**Vấn đề:** Concurrent read/write trên `Dictionary` không được đồng bộ.  
**Tại sao xảy ra:** Static collection được dùng như concurrent cache.  
**Ảnh hưởng production:** Race condition, undefined application behavior và cache corruption risk dưới load.  
**Cách sửa:** Không tự xây cache bằng `Dictionary`; dùng caching primitive/framework phù hợp với eviction/concurrency hoặc bỏ origin HTML cache nếu CDN đã giải quyết use case tốt hơn.

### High — Cache per-process không nhất quán giữa nhiều instances

**Vấn đề:** Mỗi App Service instance có static cache riêng.  
**Tại sao xảy ra:** Process memory không shared.  
**Ảnh hưởng production:** Sau publish/invalidation, instance A có thể trả page mới còn B vẫn trả page cũ; CDN có thể tiếp tục cache response tùy request routing.  
**Cách sửa:** Xác định một source of cache truth. Với public HTML, thường ưu tiên CDN cache + origin render/cache có invalidation rõ. Nếu application cache thực sự cần, invalidation phải tới mọi instance hoặc dùng distributed strategy có lý do rõ ràng.

### High — Không có publish-driven invalidation

**Vấn đề:** Cache chỉ hết hạn sau 6 giờ.  
**Tại sao xảy ra:** CMS content lifecycle không được nối với caching lifecycle.  
**Ảnh hưởng production:** Published content không đạt freshness SLA. Restart/purge thủ công trở thành operational dependency.  
**Cách sửa:** Khi content publish làm thay đổi public representation, phát invalidation/purge cho affected URLs/cache tags hoặc dùng versioned cache key. Scope invalidation phải đủ hẹp và có retry/telemetry.

### High — Cache mọi status code

**Vấn đề:** `404`, redirect, `500` hoặc response tạm thời đều có thể bị lưu 6 giờ và đánh dấu public.  
**Tại sao xảy ra:** Không có response cache policy theo status/content type.  
**Ảnh hưởng production:** Transient origin failure có thể biến thành edge-visible failure kéo dài; redirect migration có thể khó rollback; newly published URL có thể tiếp tục bị cached `404`.  
**Cách sửa:** Explicit allow-list status/content types cacheable; đặt TTL riêng cho redirects/not-found nếu business muốn negative caching; không public-cache server errors.

### High — Buffer toàn bộ response và cache không giới hạn

**Vấn đề:** Mọi response được copy vào `MemoryStream`, convert thành string và giữ trong static dictionary không có eviction/size limit.  
**Tại sao xảy ra:** Middleware tự triển khai full-response cache.  
**Ảnh hưởng production:** Allocation lớn, LOH/GC pressure tùy page size, memory growth theo số URL và nguy cơ instance recycle.  
**Cách sửa:** Dùng output caching/caching mechanism phù hợp có limits hoặc tận dụng CDN; đo page cardinality/size/hit ratio trước khi thêm origin HTML cache.

### Medium — Ghi `Cache-Control` sau `_next` nhưng cache decision không tôn trọng downstream policy

**Vấn đề:** Middleware override policy của endpoint/CMS.  
**Tại sao xảy ra:** Một global policy được áp lên mọi response.  
**Ảnh hưởng production:** Endpoint muốn `private`, `no-store` hoặc TTL ngắn có thể bị biến thành public cacheable.  
**Cách sửa:** Cache policy phải explicit theo route/content type và không override stronger privacy directives.

### Medium — Không đảm bảo restore response body khi downstream throw

**Vấn đề:** `context.Response.Body` chỉ được restore ở happy path.  
**Tại sao xảy ra:** Không dùng `try/finally`.  
**Ảnh hưởng production:** Exception path làm response pipeline khó dự đoán và có thể cản error middleware.  
**Cách sửa:** Nếu vẫn buffer, restore stream trong `finally`; tốt hơn là dùng framework-supported output caching thay vì hand-written middleware.

### Medium — Không có cache stampede protection

**Vấn đề:** Khi key miss/expire, nhiều request cùng render cùng page.  
**Tại sao xảy ra:** Không có request coalescing/single-flight.  
**Ảnh hưởng production:** Campaign traffic có thể dồn về CMS/origin đúng lúc TTL hết hạn.  
**Cách sửa:** CDN stale-while-revalidate/request collapsing nếu platform/policy hỗ trợ hoặc origin cache có coalescing; chọn dựa trên measured load, không thêm distributed lock mặc định.

### Medium — Purge toàn site là invalidation quá rộng

**Vấn đề:** Operational workaround xóa toàn bộ edge cache.  
**Tại sao xảy ra:** Không có mapping content → affected URLs/tags.  
**Ảnh hưởng production:** Cache hit ratio tụt đột ngột, origin load spike và có thể gây cascading latency sau publish.  
**Cách sửa:** Purge theo URL/cache tag/surrogate grouping phù hợp khả năng CDN và content graph; rate-limit/batch và retry purge operation có telemetry.

## Phiên bản đề xuất

Thay vì tự cache HTML bằng static dictionary, định nghĩa policy rõ ở application và để CDN/shared cache làm nhiệm vụ chính cho public content. Ví dụ middleware chỉ thiết lập policy cho request đủ điều kiện:

```csharp
public sealed class PublicPageCachePolicyMiddleware
{
    private readonly RequestDelegate _next;

    public PublicPageCachePolicyMiddleware(RequestDelegate next)
        => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        await _next(context);

        if (!IsPublicCacheCandidate(context))
        {
            context.Response.Headers.CacheControl = "private,no-store";
            return;
        }

        if (context.Response.StatusCode == StatusCodes.Status200OK &&
            context.Response.ContentType?.StartsWith("text/html",
                StringComparison.OrdinalIgnoreCase) == true)
        {
            context.Response.Headers.CacheControl =
                "public,max-age=60,s-maxage=600";
        }
    }

    private static bool IsPublicCacheCandidate(HttpContext context)
    {
        if (context.User.Identity?.IsAuthenticated == true)
            return false;

        if (!HttpMethods.IsGet(context.Request.Method) &&
            !HttpMethods.IsHead(context.Request.Method))
            return false;

        if (IsPreviewOrEditRequest(context))
            return false;

        return IsKnownPublicContentRoute(context.Request.Path);
    }

    private static bool IsPreviewOrEditRequest(HttpContext context)
    {
        // Implement bằng integration chính thức của CMS/application.
        // Không suy đoán preview chỉ từ một query parameter nếu hệ thống
        // có authenticated edit/preview context riêng.
        return context.Items.ContainsKey("CmsPreviewMode");
    }

    private static bool IsKnownPublicContentRoute(PathString path)
        => path.StartsWithSegments("/campaigns") || path == "/";
}
```

Publish invalidation được tách thành workflow riêng:

```csharp
public sealed class PublishedContentInvalidator
{
    private readonly ICdnPurgeClient _cdn;
    private readonly IContentUrlResolver _urls;
    private readonly ILogger<PublishedContentInvalidator> _logger;

    public async Task HandleAsync(
        ContentPublishedEvent published,
        CancellationToken cancellationToken)
    {
        var affectedUrls = await _urls.ResolveAffectedPublicUrlsAsync(
            published.ContentId,
            cancellationToken);

        if (affectedUrls.Count == 0)
            return;

        await _cdn.PurgeAsync(affectedUrls, cancellationToken);

        _logger.LogInformation(
            "Purged CDN for content {ContentId}; UrlCount={UrlCount}",
            published.ContentId,
            affectedUrls.Count);
    }
}
```

Đoạn trên chỉ thể hiện boundary. Cách subscribe publish event và API purge cụ thể phải theo version/configuration Optimizely và Akamai đang dùng; không nên tự giả định API. Nếu purge có thể fail, cần durable retry/outbox/job phù hợp freshness SLA thay vì fire-and-forget trong publish request.

## Giải thích thiết kế sau khi sửa

Thiết kế tách **cache eligibility** khỏi **cache storage**. Public anonymous HTML mới được shared-cache; preview/editor/personalized traffic bị bypass. Browser TTL ngắn hơn shared CDN TTL để giảm stale phía client. Publish event tạo invalidation có scope theo affected content URLs. Origin HTML cache chỉ được thêm nếu đo cho thấy render cost đáng kể sau khi CDN đã hoạt động tốt.

Một hệ thống thật cần quyết định rõ query parameters nào thay đổi representation. Tracking parameters như `utm_*` thường không nên tạo biến thể HTML nếu application không dùng chúng để render; preview/language/search parameters lại có semantics khác. Chính sách này phải đồng bộ với Akamai cache key configuration.

## Trade-offs

TTL ngắn tăng origin/CDN revalidation traffic nhưng giảm stale window. Purge theo URL chính xác hơn purge toàn site nhưng cần content dependency graph: một block dùng trên 50 pages có thể làm 50 URL bị ảnh hưởng. Versioned URL giải quyết tốt static assets nhưng không trực tiếp giải quyết canonical page URL. Distributed origin cache có thể tăng consistency giữa instances nhưng cũng thêm dependency, serialization và invalidation complexity; không nên thêm Redis chỉ vì hiện tại có nhiều instances.

## Cách kiểm thử

1. **E2E publish test:** request public page để warm cache, publish revision, thực hiện invalidation và assert public URL trả revision mới trong freshness SLA.
2. **Security test:** authenticated editor/preview request không được tạo shared-cache entry; anonymous request sau đó không bao giờ nhận preview HTML.
3. **Multi-instance test:** route request qua ít nhất hai origin instances; sau publish, cả hai không phục vụ stale origin cache ngoài policy cho phép.
4. **HTTP/CDN test:** kiểm tra `200`, `302/301`, `404`, `500`, query parameters, language/site variants và `Cache-Control`/CDN cache status tương ứng.
5. **Load/failure-path test:** purge thất bại hoặc CDN API timeout; workflow retry có bounded behavior và không làm publish request treo vô hạn.

## Quan sát trong production

Theo dõi CDN cache HIT/MISS/BYPASS, Age/cache-status headers nếu cấu hình expose an toàn, origin request rate, page render duration, purge request count/failure/duration, publish-to-visible latency, cache hit ratio và App Service CPU/memory. Correlate `ContentId`/revision với purge operation nhưng không log editor secrets/cookies. Dashboard nên cho phép phân biệt stale ở browser, Akamai edge hay origin bằng response headers và request trace. Alert nếu publish-to-visible vượt SLA hoặc purge failures tăng.

## Câu hỏi phỏng vấn mở rộng

1. Một shared content block xuất hiện trên 10.000 pages; bạn invalidation thế nào để tránh purge storm?
2. Nếu business yêu cầu campaign publish hiển thị toàn cầu trong 10 giây, TTL/purge architecture cần thay đổi ra sao?
3. Khi nào origin output cache vẫn có giá trị nếu Akamai đã có hit ratio rất cao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Mutable authentication state trong concurrent HTTP client cần boundary và refresh coordination rõ ràng; retry phải đi cùng operation semantics và idempotency.
- Cancellation, secret handling và dependency error classification là một phần của production correctness, không phải chi tiết phụ.
- CMS caching cần phân biệt browser, CDN/shared cache và origin cache; mỗi lớp phải có cache key, eligibility, TTL và invalidation ownership rõ ràng.
- Publish-driven freshness không thể dựa vào TTL dài hoặc restart application; purge/invalidation phải được thiết kế như một workflow có failure handling và observability.

## Mẫu tư duy cần nhớ

- Shared mutable state + concurrency → xác định ownership và coordination trước khi thêm retry.
- Retry luôn phải được đánh giá cùng idempotency và failure ambiguity.
- Cache key đúng chưa đủ; phải xác định response nào được phép shared-cache.
- Invalidation là một phần của write/publish workflow, không phải thao tác vận hành thủ công sau sự cố.
- Dùng telemetry để xác định failure nằm ở caller, application, dependency, origin hay edge trước khi sửa.
