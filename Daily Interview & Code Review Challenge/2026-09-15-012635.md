# Code Review Challenge 1 — API đọc Cosmos DB chạy ổn ở dev nhưng RU và latency tăng vọt khi dữ liệu lớn

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Cosmos DB, partitioning, pagination, query cost, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp lịch sử đơn hàng cho hệ thống CRM nội bộ. Dữ liệu được lưu trong Azure Cosmos DB.

Container `orders` hiện có:

- partition key: `/tenantId`;
- khoảng 120 triệu documents;
- một tenant lớn có thể có vài triệu orders;
- `customerId` là duy nhất trong phạm vi một tenant, không phải toàn hệ thống;
- API thường được gọi với `tenantId` và `customerId` đã biết;
- UI chỉ hiển thị 50 orders mỗi trang;
- production bắt đầu xuất hiện 429, RU consumption tăng mạnh và p99 của endpoint vượt 5 giây khi traffic tăng;
- team muốn giữ API responsive mà không tăng provisioned throughput một cách mù quáng.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed record OrderDto(
    string Id,
    string CustomerId,
    string Status,
    decimal Total,
    DateTimeOffset CreatedAt);

[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly Container _orders;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        CosmosClient cosmosClient,
        ILogger<OrdersController> logger)
    {
        _orders = cosmosClient.GetContainer("commerce", "orders");
        _logger = logger;
    }

    [HttpGet("{tenantId}/customers/{customerId}")]
    public async Task<ActionResult<IReadOnlyList<OrderDto>>> GetCustomerOrders(
        string tenantId,
        string customerId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.customerId = @customerId " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@customerId", customerId);

        using var iterator = _orders.GetItemQueryIterator<OrderDocument>(
            query,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = 1000
            });

        var result = new List<OrderDto>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);

            foreach (var order in page)
            {
                result.Add(new OrderDto(
                    order.Id,
                    order.CustomerId,
                    order.Status,
                    order.Total,
                    order.CreatedAt));
            }
        }

        _logger.LogInformation(
            "Loaded {Count} orders for tenant {TenantId}, customer {CustomerId}",
            result.Count,
            tenantId,
            customerId);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### Critical — `tenantId` không được dùng để scope query theo logical partition

**Vấn đề:**  
Container partition theo `/tenantId`, nhưng query chỉ filter `customerId`. Method đã có `tenantId` nhưng không đưa nó vào query và cũng không truyền `PartitionKey` trong `QueryRequestOptions`.

**Tại sao xảy ra:**  
Cosmos DB phải tìm kết quả ngoài một logical partition cụ thể. Với container lớn, query có thể phải fan out qua nhiều physical partitions thay vì route trực tiếp tới partition của tenant.

**Ảnh hưởng production:**  
RU tăng, latency tăng, throughput bị cạnh tranh bởi các request khác và 429 xuất hiện sớm hơn. Ngoài ra, vì `customerId` chỉ unique trong tenant, query có thể trả orders của customer có cùng ID ở tenant khác — đây là lỗi correctness nghiêm trọng ngay cả khi endpoint chỉ dùng nội bộ.

**Cách sửa:**  
Filter cả `tenantId` trong query và scope request bằng `PartitionKey = new PartitionKey(tenantId)` khi access pattern đã biết exact partition key.

---

### High — Endpoint đọc toàn bộ lịch sử thay vì một page

**Vấn đề:**  
`while (iterator.HasMoreResults)` đọc đến hết result set và gom toàn bộ vào `List<OrderDto>`.

**Tại sao xảy ra:**  
`MaxItemCount = 1000` chỉ liên quan kích thước một page request; vòng lặp vẫn tiếp tục cho đến khi không còn page nào.

**Ảnh hưởng production:**  
Một customer lâu năm có hàng chục nghìn orders sẽ tạo nhiều database requests, RU lớn, allocation lớn, GC pressure và response rất nặng. p99 có thể xấu dù đa số customer chỉ có vài orders.

**Cách sửa:**  
Expose server-side pagination. Mỗi API call chỉ đọc một page phù hợp với UI, ví dụ 20–100 records, và trả continuation token opaque cho client.

---

### High — `SELECT *` tạo read/deserialization cost không cần thiết

**Vấn đề:**  
Query tải toàn bộ document dù response chỉ cần một số field.

**Tại sao xảy ra:**  
Documents thực tế có thể chứa shipping metadata, audit information, product snapshot hoặc payload khác mà endpoint không sử dụng.

**Ảnh hưởng production:**  
Tăng payload từ Cosmos DB tới application, tăng serialization/deserialization work và memory allocation. Mức ảnh hưởng cần đo bằng document size thực tế, nhưng đây là chi phí dễ tránh.

**Cách sửa:**  
Projection đúng các field cần thiết trong Cosmos SQL query và deserialize trực tiếp vào read model phù hợp.

---

### High — Không có API contract cho continuation token/page size

**Vấn đề:**  
Response trả một `IReadOnlyList<OrderDto>` duy nhất, không có `continuationToken`, không có giới hạn page size từ server và không có contract cho lần đọc tiếp theo.

**Tại sao xảy ra:**  
Implementation đang coi lịch sử order như một collection nhỏ có thể materialize toàn bộ.

**Ảnh hưởng production:**  
Team khó sửa performance mà không thay API behavior; frontend cũng không thể incremental-load dữ liệu hiệu quả.

**Cách sửa:**  
Thiết kế response dạng page:

```text
items
continuationToken
```

Giới hạn page size bằng server-side cap thay vì để client yêu cầu tùy ý.

**Vấn đề:**  
`FeedResponse<T>` có thông tin request charge nhưng code bỏ qua hoàn toàn.

**Tại sao xảy ra:**

### Medium — `MaxItemCount = 1000` không phù hợp với UI chỉ cần 50 items

**Vấn đề:**  
Ngay page đầu tiên cũng có thể request nhiều items hơn business cần.

**Tại sao xảy ra:**

**Ảnh hưởng production:**

**Cách sửa:**  
Dùng page size gần UI need và clamp trong một range an toàn, ví dụ default 50 và max 100 tùy measurement.

### Medium — Không có guardrail cho tenant/customer input và access pattern

**Vấn đề:**

**Tại sao xảy ra:**  
Không có boundary rõ giữa API input và query contract.

**Ảnh hưởng production:**

## Phiên bản đề xuất

```csharp
public sealed record OrderRow(
    string Id,
    string CustomerId,
    string Status,
    decimal Total,
    DateTimeOffset CreatedAt);

public sealed record OrderPage(
    IReadOnlyList<OrderRow> Items,
    string? ContinuationToken);

[ApiController]
[Route("api/orders")]
public sealed class OrdersController : ControllerBase
{
    private readonly Container _orders;
    private readonly ILogger<OrdersController> _logger;

    public OrdersController(
        CosmosClient cosmosClient,
        ILogger<OrdersController> logger)
    {
        _orders = cosmosClient.GetContainer("commerce", "orders");
        _logger = logger;
    }

    [HttpGet("{tenantId}/customers/{customerId}")]
    public async Task<ActionResult<OrderPage>> GetCustomerOrders(
        string tenantId,
        string customerId,
        [FromQuery] string? continuationToken,
        [FromQuery] int pageSize = 50,
        CancellationToken cancellationToken = default)
    {
        pageSize = Math.Clamp(pageSize, 1, 100);

        var query = new QueryDefinition(
            "SELECT c.id, c.customerId, c.status, c.total, c.createdAt " +
            "FROM c " +
            "WHERE c.tenantId = @tenantId " +
            "AND c.customerId = @customerId " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@customerId", customerId);

        using var iterator = _orders.GetItemQueryIterator<OrderRow>(
            query,
            continuationToken,
            new QueryRequestOptions
            {
                PartitionKey = new PartitionKey(tenantId),
                MaxItemCount = pageSize
            });

        if (!iterator.HasMoreResults)
        {
            return Ok(new OrderPage(Array.Empty<OrderRow>(), null));
        }

        var response = await iterator.ReadNextAsync(cancellationToken);

        _logger.LogInformation(
            "Cosmos order query completed. Tenant={TenantId} Customer={CustomerId} " +
            "Items={ItemCount} RU={RequestCharge} Continuation={HasContinuation}",
            tenantId,
            customerId,
            response.Count,
            response.RequestCharge,
            response.ContinuationToken is not null);

        return Ok(new OrderPage(
            response.Resource.ToArray(),
            response.ContinuationToken));
    }
}
```

## Giải thích thiết kế sau khi sửa

Điểm quan trọng nhất không phải syntax của SDK mà là **route query theo partition key mà business đã biết**.

Container được partition theo `/tenantId`; endpoint nhận đúng tenant cần đọc. Vì vậy access pattern này nên trở thành single-logical-partition query thay vì fan-out toàn container.

Query vẫn filter `tenantId` để semantics rõ ràng, đồng thời `QueryRequestOptions.PartitionKey` giúp SDK/request được scope đúng logical partition. Điều này giảm phạm vi query và làm cost predictable hơn khi container tăng kích thước.

Thứ hai, endpoint chỉ đọc **một page**. Continuation token của Cosmos DB được giữ opaque và trả lại cho caller. API không tự biến token thành offset/page-number giả, vì continuation token đại diện trạng thái tiếp tục query chứ không phải một index tuyệt đối.

Projection chỉ lấy fields cần cho UI. Nếu sau này UI cần thêm data, hãy mở rộng projection có chủ đích thay vì quay lại `SELECT *` mặc định.

Logging RU là cần thiết nhưng không nên biến logs thành high-cardinality dump. Trong hệ thống thực tế, RU/request, latency, 429 rate và page count phù hợp hơn với metrics/traces; tenant/customer identifiers cần tuân theo privacy/logging policy.

Nếu workload thường xuyên cần query theo một dimension khác không liên quan partition key — ví dụ global lookup theo `customerId` trên toàn tenant — vấn đề không còn là “sửa query” đơn thuần. Khi đó cần đánh giá data model, partition key và read model phụ theo access pattern thực tế thay vì tăng RU vô hạn.

## Trade-offs

- Single-partition query rất hiệu quả cho access pattern theo tenant, nhưng một tenant cực lớn có thể trở thành hot partition nếu workload tập trung bất cân xứng. Cần đo distribution trước khi kết luận partition key hiện tại hoàn hảo.
- Continuation-token pagination đơn giản và scale tốt, nhưng client không thể nhảy trực tiếp đến “page 42” như offset pagination. Với infinite scroll/lịch sử timeline, đây thường là trade-off hợp lý.
- Projection giảm payload nhưng tạo coupling giữa query và response model; thay đổi response cần cập nhật query projection.
- Log RU theo request giúp điều tra, nhưng không nên log mọi dimension với cardinality cực cao ở mức Information nếu traffic lớn.
- Nếu requirement cần global customer history across tenants, có thể cần read model/index phụ; không nên ép một partitioning strategy phục vụ mọi query pattern.

## Cách kiểm thử

1. **Integration test — partition correctness:** tạo hai tenant có cùng `customerId`, xác minh endpoint của tenant A không bao giờ trả data tenant B.
2. **Pagination test:** tạo hơn 120 orders cho một customer, request page size 50 và xác minh lần đầu trả tối đa 50 items cùng continuation token hợp lệ; đọc tiếp tới hết không trùng/mất item.
3. **Load test:** chạy realistic concurrency với tenant lớn, đo p95/p99, RU/request, 429 rate, CPU/memory trước và sau fix.
4. **Cancellation/failure-path test:** cancel request giữa lúc query, xác minh application dừng work sớm và không tiếp tục enumerate các page không cần thiết.
5. **Query/index validation:** dùng production-like data distribution để xác minh `ORDER BY createdAt` và indexing policy đáp ứng query; không tự động thêm composite index nếu telemetry/query diagnostics chưa chứng minh cần.

Theo dõi ít nhất:

# Code Review Challenge 2 — Playwright pass ở local nhưng flaky trên CI khi chạy parallel và retry

**Chủ đề:** TypeScript, Playwright, E2E testing, test isolation, parallelism, network synchronization, CI reliability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một approval web application dùng ASP.NET Core backend và React frontend. Team có bộ Playwright E2E để kiểm tra các workflow quan trọng trước release.

Local chạy `--workers=1` gần như luôn pass. Trên CI, suite chạy 6 workers và bật retry 2 lần. Sau khi tăng parallelism để giảm pipeline time:

- test thỉnh thoảng fail vì setup API trả `409 Conflict`;
- test `Approve` đôi lúc timeout ở `waitForResponse` dù UI đã đổi trạng thái;
- test khác nhìn thấy dữ liệu do test trước để lại;
- retry đôi khi pass, khiến pipeline green nhưng flake rate tăng;
- cùng một file được cấu hình `mode: 'parallel'`;
- backend test environment là shared environment cho toàn job.

Code hiện tại:

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

test.describe.configure({ mode: 'parallel' });

test.describe('approval workflow', () => {
  let orderId: string;

  test.beforeAll(async ({ request }) => {
    const response = await request.post('/test-api/orders', {
      data: {
        externalId: 'e2e-order',
        customerName: 'Automation User',
        amount: 250
      }
    });

    const body = await response.json();
    orderId = body.id;
  });

  test('manager can approve an order', async ({ page }) => {
    await page.goto(`/orders/${orderId}`);

    await page.getByRole('button', { name: 'Approve' }).click();

    const response = await page.waitForResponse(r =>
      r.url().includes(`/api/orders/${orderId}/approve`) &&
      r.request().method() === 'POST'
    );

    await page.waitForTimeout(1000);

    expect(response.ok()).toBeTruthy();
    await expect(page.getByText('Approved')).toBeVisible();
  });

  test('manager can cancel an order', async ({ page }) => {
    await page.goto(`/orders/${orderId}`);

    await page.getByRole('button', { name: 'Cancel' }).click();
    await page.waitForTimeout(1500);

    await expect(page.getByText('Cancelled')).toBeVisible();
  });
});
```

## Câu hỏi gợi mở

1. Trong fully/explicit parallel execution, bạn có thể giả định hai tests dùng cùng một in-memory variable hoặc cùng setup instance không?
2. `externalId: 'e2e-order'` có điều gì xảy ra khi nhiều workers hoặc retries cùng tạo record?
3. Network response có thể hoàn tất trước khi `waitForResponse` bắt đầu lắng nghe không?
4. `waitForTimeout(1000)` đang chờ điều kiện business nào, hay chỉ chờ thời gian trôi qua?
5. Nếu test approve và cancel cùng mutate một order, chúng có còn độc lập và rerunnable không?

## Gợi ý

### Gợi ý 1

Synchronization tốt nên chờ một **observable condition** — response, DOM state, backend state — chứ không chờ một khoảng thời gian cố định.

### High — Hai test mutate cùng logical test data

**Vấn đề:**  
Cả `approve` và `cancel` phụ thuộc vào `orderId` được setup ở scope chung và đều thay đổi state của order.

**Tại sao xảy ra:**  
Test design giả định execution tuần tự, nhưng file được cấu hình parallel. Parallel workers cần test independence ở cả browser state lẫn backend data.

**Ảnh hưởng production pipeline:**  
Một test có thể approve order trong lúc test khác cố cancel cùng order, tạo failure nondeterministic. Retry có thể pass chỉ vì timing thay đổi, che mất defect của test suite.

**Cách sửa:**  
Mỗi test tạo data riêng hoặc dùng fixture tạo unique backend state theo test/worker. Không chia sẻ mutable business entity giữa independent tests.

---

### High — Fixed `externalId` gây collision giữa parallel workers và retries

**Vấn đề:**  
Mọi setup request dùng `externalId: 'e2e-order'`.

**Tại sao xảy ra:**  
Backend shared environment có thể enforce unique external ID hoặc reuse record ngoài dự kiến. Parallel workers và retry làm cùng setup gần như đồng thời.

**Ảnh hưởng production pipeline:**  
`409 Conflict`, test data contamination và flaky behavior. Một retry có thể gặp record từ attempt trước và tạo kết quả khác attempt đầu.

**Cách sửa:**  
Sinh identifier unique theo test attempt/test ID hoặc UUID. Cleanup nên idempotent hoặc test environment cần TTL/reaper phù hợp.

---

### High — `waitForResponse` được đăng ký sau khi click

**Vấn đề:**  
Code `click()` trước rồi mới gọi `page.waitForResponse(...)`.

**Tại sao xảy ra:**  
Nếu API nhanh, response có thể hoàn tất trước khi listener được đăng ký.

**Ảnh hưởng production pipeline:**  
UI có thể đã đổi state đúng nhưng test vẫn timeout vì bỏ lỡ event network. Flake xuất hiện rõ hơn khi machine/network timing khác local.

**Cách sửa:**  
Đăng ký wait trước action, thường bằng `Promise.all` hoặc tạo response promise trước khi click.

---

### Medium — `waitForTimeout` là synchronization theo thời gian, không theo trạng thái

**Vấn đề:**  
Test ngủ 1–1.5 giây rồi giả định UI/backend đã hoàn thành.

**Tại sao xảy ra:**  
Fixed delay không mô tả điều kiện hoàn thành thật sự. Máy nhanh thì lãng phí; máy chậm thì vẫn fail.

**Ảnh hưởng production pipeline:**  
Tăng test duration và flakiness, đặc biệt khi CI contention hoặc backend latency thay đổi.

**Cách sửa:**  
Dùng auto-waiting/assertions của Playwright, chờ response cụ thể hoặc poll observable backend/UI state với timeout có ý nghĩa.

---

### Medium — Setup không kiểm tra HTTP status trước khi parse JSON

**Vấn đề:**  
`beforeAll` parse body và lấy `id` ngay cả khi setup trả 409/500.

**Tại sao xảy ra:**  
Test không fail tại nguyên nhân đầu tiên.

**Ảnh hưởng production pipeline:**  
Failure sau đó có thể là `undefined` order ID hoặc navigation error, làm log đánh lạc hướng khỏi setup failure.

**Cách sửa:**  
Assert setup response `ok()` hoặc status expected trước khi đọc/use body, và attach diagnostic response khi fail.

---

### Medium — Test chỉ xác minh presentation state, chưa bảo vệ business persistence

**Vấn đề:**  
`Cancelled` hoặc `Approved` trên UI có thể xuất hiện từ optimistic state update dù backend commit thất bại sau đó.

**Tại sao xảy ra:**  
Assertion chỉ nhìn DOM sau thao tác.

**Ảnh hưởng production pipeline:**  
Một regression ở persistence/error recovery có thể lọt qua E2E nếu UI hiển thị trạng thái trước khi server xác nhận.

**Cách sửa:**  
Tùy architecture, xác minh network response thành công và/hoặc reload page để chứng minh state persisted. Không cần gọi database trực tiếp nếu public API/UI có thể xác nhận behavior.

---

### Low — Không có cleanup/idempotent lifecycle rõ ràng cho test data

**Vấn đề:**  
Orders tạo bởi suite tồn tại trong shared test environment.

**Tại sao xảy ra:**  
Suite chỉ nghĩ đến setup, không nghĩ đến lifecycle dữ liệu sau fail/retry.

**Ảnh hưởng production pipeline:**  
Environment tích tụ dữ liệu, unique constraints va chạm và debugging trở nên khó khăn.

**Cách sửa:**  
Dùng unique data + cleanup idempotent trong fixture/teardown khi phù hợp, hoặc có environment-level TTL/reaper dành cho test records. Cleanup không được làm test chính phụ thuộc vào teardown thành công.

## Phiên bản đề xuất

```ts
import { test as base, expect } from '@playwright/test';
import { randomUUID } from 'node:crypto';

type Fixtures = {
  orderId: string;
};

const test = base.extend<Fixtures>({
  orderId: async ({ request }, use, testInfo) => {
    const externalId = `e2e-${testInfo.testId}-${randomUUID()}`;

    const createResponse = await request.post('/test-api/orders', {
      data: {
        externalId,
        customerName: 'Automation User',
        amount: 250
      }
    });

    expect(createResponse.ok()).toBeTruthy();

    const created = await createResponse.json();
    await use(created.id);

    const deleteResponse = await request.delete(
      `/test-api/orders/${created.id}`
    );

    if (!deleteResponse.ok() && deleteResponse.status() !== 404) {
      await testInfo.attach('cleanup-failure.txt', {
        body: `Cleanup failed with ${deleteResponse.status()}`,
        contentType: 'text/plain'
      });
    }
  }
});

test.describe('approval workflow', () => {
  test('manager can approve an order', async ({ page, orderId }) => {
    await page.goto(`/orders/${orderId}`);

    const [response] = await Promise.all([
      page.waitForResponse(r =>
        r.url().includes(`/api/orders/${orderId}/approve`) &&
        r.request().method() === 'POST'
      ),
      page.getByRole('button', { name: 'Approve' }).click()
    ]);

    expect(response.ok()).toBeTruthy();
    await expect(page.getByText('Approved')).toBeVisible();

    await page.reload();
    await expect(page.getByText('Approved')).toBeVisible();
  });

  test('manager can cancel an order', async ({ page, orderId }) => {
    await page.goto(`/orders/${orderId}`);

    const [response] = await Promise.all([
      page.waitForResponse(r =>
        r.url().includes(`/api/orders/${orderId}/cancel`) &&
        r.request().method() === 'POST'
      ),
      page.getByRole('button', { name: 'Cancel' }).click()
    ]);

    expect(response.ok()).toBeTruthy();
    await expect(page.getByText('Cancelled')).toBeVisible();

    await page.reload();
    await expect(page.getByText('Cancelled')).toBeVisible();
  });
});
```

## Giải thích thiết kế sau khi sửa

Mỗi test có một fixture `orderId` riêng. BrowserContext isolation của Playwright bảo vệ cookies/storage/browser state, nhưng không tự cô lập dữ liệu trong shared backend. Vì vậy data isolation phải được thiết kế ở fixture/backend level.

Identifier chứa test-specific component + UUID để giảm collision giữa workers, retries và concurrent CI jobs. Trong hệ thống thật, có thể dùng `testInfo.parallelIndex`, worker-scoped accounts hoặc namespace theo build ID nếu backend có constraints riêng.

`Promise.all` đăng ký response wait trước khi action được thực thi, loại race “response đến trước listener”.

Fixed sleeps được bỏ. Assertions chờ observable state và Playwright tự retry assertions trong timeout. Reload sau mutation tăng confidence rằng state đã persist thay vì chỉ là optimistic UI state.

Cleanup chạy sau `use()`, nhưng được thiết kế theo hướng best-effort/idempotent để cleanup failure không che mất assertion chính. Với môi trường có nhiều job song song, một backend TTL/reaper cho test data vẫn rất hữu ích.

Nếu authentication state được reuse, cần đánh giá riêng: một account dùng cho parallel tests chỉ an toàn khi tests không mutate shared server-side state liên quan account đó. Nếu tests thay đổi profile/settings/permissions, nên có account/namespace per worker hoặc per test tùy cost.

## Trade-offs

- Tạo data riêng cho mỗi test tăng số API calls và thời gian setup, nhưng đổi lại test độc lập và có thể chạy parallel đáng tin cậy.
- Per-test cleanup tăng complexity; environment TTL/reaper đơn giản hơn trong một số hệ thống nhưng cleanup không tức thời.
- Reload để xác minh persistence làm test chậm hơn, nhưng hợp lý cho critical workflow; không cần áp cho mọi UI micro-interaction.
- `Promise.all` giúp đồng bộ network event, nhưng test vẫn nên ưu tiên user-visible state khi exact endpoint không phải part of behavior contract.
- Worker-scoped fixtures có thể nhanh hơn per-test fixtures, nhưng chỉ dùng khi data thật sự có thể share an toàn giữa các tests trong worker.

## Cách kiểm thử

1. **Parallel stress:** chạy file 50–100 lần với 6–10 workers, xác minh không có 409/data collision và flake rate về gần zero.
2. **Retry validation:** cố ý inject một transient failure ở attempt đầu, xác minh retry tạo/isolate test data đúng và không reuse state bẩn.
3. **Network timing test:** chạy backend response cực nhanh và cực chậm để chứng minh `waitForResponse` không bỏ lỡ event và không cần fixed sleep.
4. **Persistence test:** làm UI optimistic nhưng backend trả failure trong test environment, xác minh E2E không false-positive.
5. **CI isolation test:** chạy hai pipeline jobs song song trên cùng environment, xác minh namespace/unique IDs không va chạm.

## Quan sát trong production

Đây là test infrastructure nên telemetry cần tập trung vào CI/test environment:

- test duration p50/p95 theo test name;
- retry count và first-attempt failure rate;
- flake rate theo rolling window;
- setup API status distribution, đặc biệt 409/429/5xx;
- Playwright trace, screenshot, video khi retry/failure theo policy;
- network HAR/trace cho failed attempts khi cần;
- test ID / build ID / worker index được log trong test data metadata;
- backend correlation ID để nối failed E2E với server logs;
- số test records tồn đọng và cleanup failure rate.

Pipeline không nên chỉ theo dõi “final pass after retry”. Một test thường xuyên fail attempt đầu nhưng pass attempt hai vẫn là reliability regression cần xử lý.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn worker-scoped authentication/data thay vì per-test data, và điều kiện nào khiến sharing đó trở nên nguy hiểm?
2. Nếu test suite mất quá nhiều thời gian vì mỗi test tự setup data, bạn tối ưu thế nào mà không quay lại shared mutable state?
3. Retry nên được dùng để tăng resilience của CI ở mức nào trước khi nó biến thành cơ chế che giấu flaky tests?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Với Cosmos DB, partition key không chỉ là chi tiết lưu trữ; nó quyết định routing, query scope, RU predictability và khả năng scale của access pattern.
- `MaxItemCount` không phải pagination nếu code vẫn enumerate toàn bộ iterator.
- API pagination tốt cần bounded work cho mỗi request và contract continuation rõ ràng.
- Performance investigation cần telemetry gắn với cost thật: RU, page count, p95/p99, 429 và dependency latency.
- Playwright BrowserContext isolation không tự cô lập shared database/backend state.
- Parallel tests phải độc lập về data, account state và external side effects.
- Fixed sleeps tạo timing assumptions; synchronization nên dựa trên observable condition.
- Retry là safety net, không phải tiêu chuẩn để chấp nhận flaky tests.

## Mẫu tư duy cần nhớ

1. **Scope work theo partition/boundary đã biết trước khi scale throughput.**
2. **Bound mỗi request/test bằng dữ liệu và side effect hữu hạn.**
3. **Test parallelism chỉ an toàn khi state bên ngoài process cũng được isolate.**
4. **Chờ condition, không chờ thời gian.**
5. **Đo cost và failure signal trước khi tăng capacity hoặc thêm retry.**
