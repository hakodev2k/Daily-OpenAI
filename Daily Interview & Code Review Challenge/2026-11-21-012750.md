# Code Review Challenge 1 — Cache trang Optimizely làm lộ giá hợp đồng

**Chủ đề:** ASP.NET Core .NET 8, Optimizely CMS, Akamai CDN, HTTP caching, authorization  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút

## Bối cảnh

Một website B2B dùng Optimizely CMS để quản lý landing page và content blocks, ASP.NET Core để render HTML, Akamai làm CDN. Giá hiển thị phụ thuộc hợp đồng của tenant và quyền người xem; nội dung marketing công khai được cache ở edge 10 phút. Trong một đợt campaign, khách tenant A báo thấy giá của tenant B. Một số trang sau khi biên tập vẫn hiển thị phiên bản cũ. Hệ thống chạy 3 App Service instances; CDN có thể phục vụ response mà không gọi origin. Nhóm muốn giữ CDN cho tài nguyên công khai và không làm tăng p95 quá mức.

## Đoạn code cần review

```csharp
public sealed class ProductLandingController : Controller
{
    private readonly IContentLoader _content;
    private readonly IContractPriceService _prices;
    private readonly IMemoryCache _cache;
    private readonly ILogger<ProductLandingController> _logger;

    public ProductLandingController(
        IContentLoader content,
        IContractPriceService prices,
        IMemoryCache cache,
        ILogger<ProductLandingController> logger)
    {
        _content = content;
        _prices = prices;
        _cache = cache;
        _logger = logger;
    }

    [HttpGet("/products/{slug}")]
    public async Task<IActionResult> Detail(
        string slug, CancellationToken cancellationToken)
    {
        var tenant = Request.Headers["X-Tenant-Id"].ToString();
        var userId = User.FindFirst("sub")?.Value ?? "anonymous";
        var key = $"landing:{slug}";

        if (!_cache.TryGetValue(key, out string? html))
        {
            var page = _content.GetChildren<ProductPage>(
                ContentReference.StartPage)
                .FirstOrDefault(p => p.URLSegment == slug);

            if (page is null) return NotFound();

            var price = await _prices.GetPriceAsync(
                tenant, page.ProductSku, cancellationToken);

            html = $"<h1>{page.Name}</h1>" +
                   $"<div>{page.MainBody}</div>" +
                   $"<strong>{price}</strong>";

            _cache.Set(key, html, TimeSpan.FromMinutes(10));
        }

        _logger.LogInformation(
            "Rendered product {Slug} tenant {Tenant} user {User}",
            slug, tenant, userId);

        Response.Headers.CacheControl = "public, max-age=600";
        return Content(html!, "text/html");
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Shared cache chứa giá riêng của tenant

**Vấn đề:** Cache key chỉ có slug, nhưng HTML chứa contract price.  
**Tại sao xảy ra:** Request đầu tiên đi qua một instance quyết định nội dung được cache 10 phút; request tenant khác nhận lại HTML đó.  
**Ảnh hưởng production:** Lộ thông tin thương mại và trả giá sai.  
**Cách sửa:** Không đưa personalized HTML vào shared cache; tách public page shell khỏi API giá được authorize, response giá `private, no-store`.

### [Critical] — Public HTTP caching cho response nhạy cảm

**Vấn đề:** `public, max-age=600` cho toàn bộ HTML.  
**Tại sao xảy ra:** Shared intermediary có thể lưu response theo URL; không thể dựa vào cache key nội bộ của ứng dụng để bảo vệ edge.  
**Ảnh hưởng production:** Rò rỉ cross-tenant kể cả khi origin đã được sửa.  
**Cách sửa:** Ngay lập tức disable shared caching cho personalized route; purge những URL đã bị cache, xác minh cấu hình Akamai và browser behavior.

### [High] — Tin tưởng X-Tenant-Id từ request

**Vấn đề:** Header do client kiểm soát được sử dụng để lấy giá.  
**Tại sao xảy ra:** Không ràng buộc tenant với principal đã được xác thực và quyền truy cập hợp đồng.  
**Ảnh hưởng production:** Có thể truy xuất giá tenant khác ngay cả khi không có cache.  
**Cách sửa:** Lấy tenant từ trusted identity/tenant membership sau authorization; pricing service tự enforce tenant boundary.

### [High] — Không có authorization bắt buộc

**Vấn đề:** Endpoint không yêu cầu xác thực, không kiểm tra quyền xem giá.  
**Tại sao xảy ra:** Controller coi việc lấy giá là đủ điều kiện hiển thị.  
**Ảnh hưởng production:** Anonymous hoặc user sai vai trò có thể xem dữ liệu hợp đồng nếu service chấp nhận.  
**Cách sửa:** `[Authorize]` cho pricing endpoint và policy theo tenant; landing page public chỉ chứa thông tin công khai.

### [High] — HTML interpolation không có encoding rõ ràng

**Vấn đề:** `page.Name` và giá được nối chuỗi trực tiếp; `MainBody` cũng được đưa thẳng vào HTML.  
**Tại sao xảy ra:** Không phân biệt plain text với CMS rich HTML đã được sanitization/trust-policy xử lý.  
**Ảnh hưởng production:** Stored XSS nếu dữ liệu đầu vào không được kiểm soát phù hợp.  
**Cách sửa:** Razor auto-encoding cho plain text; xử lý rich text bằng CMS rendering pipeline và chính sách sanitize phù hợp, không tự nối HTML.

### [Medium] — Cache invalidation không theo publish event

**Vấn đề:** TTL cố định không gắn với version/content publish.  
**Tại sao xảy ra:** Cập nhật CMS không invalidates IMemoryCache hoặc CDN tự động.  
**Ảnh hưởng production:** Trang stale, marketing campaign hiển thị sai.  
**Cách sửa:** Public content cache có version/purge strategy; publish event kích hoạt invalidation phù hợp và CDN purge có kiểm chứng.

### [Medium] — In-process cache không nhất quán giữa instances

**Vấn đề:** IMemoryCache tồn tại riêng trên từng App Service instance.  
**Tại sao xảy ra:** Không có cơ chế đồng bộ entry.  
**Ảnh hưởng production:** Nội dung khác nhau tùy origin được chọn.  
**Cách sửa:** Với public page, dùng HTTP caching có key/version rõ ràng; không giả định memory cache là distributed cache.

### [Medium] — Tìm page bằng quét children

**Vấn đề:** `GetChildren` rồi `FirstOrDefault` theo slug không thể hiện routing/locale/publication context chuẩn.  
**Tại sao xảy ra:** Dùng một collection traversal làm lookup; chưa xử lý duplicate slug, language và published state.  
**Ảnh hưởng production:** Sai trang hoặc tăng latency khi content tree lớn.  
**Cách sửa:** Sử dụng CMS routing/content resolution phù hợp phiên bản triển khai; đo số lượng content và dependency calls trước tối ưu.

### [Medium] — Telemetry thiếu cache provenance

**Vấn đề:** Log chỉ ghi slug/tenant/user, không phân biệt cache hit, content version, edge status.  
**Tại sao xảy ra:** Thiếu correlation và cache diagnostics.  
**Ảnh hưởng production:** Khó chứng minh nguồn gây lộ dữ liệu.  
**Cách sửa:** Log structured fields an toàn (không log giá hoặc token), cache layer/hit, page version, trace ID; thu thập CDN cache-status và purge audit.

## Phiên bản đề xuất

Phương án tối thiểu tách public landing page và giá riêng. Ví dụ dưới đây giả định CMS page đã được route tới action bằng một resolver phù hợp với phiên bản Optimizely; `IProductPageResolver` là abstraction ứng dụng, không phải API có sẵn của Optimizely.

```csharp
[ApiController]
[Route("api/products")]
[Authorize]
public sealed class ContractPricesController : ControllerBase
{
    private readonly IContractPriceService _prices;
    private readonly ITenantAccessService _access;

    public ContractPricesController(
        IContractPriceService prices, ITenantAccessService access)
    {
        _prices = prices;
        _access = access;
    }

    [HttpGet("{sku}/contract-price")]
    public async Task<IActionResult> Get(
        string sku, CancellationToken ct)
    {
        Response.Headers.CacheControl = "private, no-store";
        var tenantId = await _access.GetAuthorizedTenantAsync(User, ct);
        if (tenantId is null) return Forbid();

        var price = await _prices.GetPriceAsync(tenantId, sku, ct);
        return Ok(new { sku, price });
    }
}

[AllowAnonymous]
public sealed class PublicLandingController : Controller
{
    private readonly IProductPageResolver _pages;

    public PublicLandingController(IProductPageResolver pages)
        => _pages = pages;

    [HttpGet("/products/{slug}")]
    public async Task<IActionResult> Detail(
        string slug, CancellationToken ct)
    {
        var page = await _pages.ResolvePublishedAsync(
            slug, HttpContext.Request.Headers.AcceptLanguage.ToString(), ct);
        if (page is null) return NotFound();

        Response.Headers.CacheControl = "public, max-age=60";
        return View("PublicProduct", page);
    }
}
```

View `PublicProduct` chỉ render nội dung công khai bằng Razor/CMS rendering đã kiểm soát rich text; client gọi API giá sau khi xác thực và không lưu response giá ở shared cache. Cache policy cho public page chỉ được bật khi xác nhận không có cookie, personalization hay fragment riêng. Quy tắc tenant authorization phải được thực thi ở data-access/service boundary, không chỉ controller. TTL 60 giây là lựa chọn minh họa, không phải yêu cầu của CDN; triển khai thực tế cần purge/versioning.

## Giải thích thiết kế sau khi sửa

Tách data classification trước khi chọn cache. HTML công khai có thể cache theo URL, locale và content version; contract price được tính theo authenticated principal và tenant membership. Mọi truy vấn giá phải được authorization ở server. Khi publish CMS, purge/invalidate public content độc lập với dữ liệu giá. Nếu yêu cầu SEO cho giá theo user, phải thảo luận lại vì personalized price không phù hợp với public indexing.

## Trade-offs

Tách API tạo thêm round trip và loading state trên frontend; có thể tối ưu bằng BFF render riêng nhưng response vẫn `private, no-store`. TTL ngắn giảm stale window nhưng tăng origin traffic; purge nhanh hơn nhưng phụ thuộc propagation/operational correctness. Không cần mặc định đưa Redis vào hệ thống nếu CDN và CMS resolution đáp ứng p95.

## Cách kiểm thử

1. **Security integration:** Hai tenants dùng cùng slug; không request nào được nhận giá tenant khác, kể cả giả mạo `X-Tenant-Id`.
2. **Cache integration:** Request anonymous/public và authenticated/pricing kiểm tra `Cache-Control`, CDN cache key và `Age`/cache-status khi có.
3. **Content publish:** Publish phiên bản mới, kích hoạt purge và đo thời gian đến khi mọi POP trả đúng nội dung.
4. **XSS:** Tạo title/rich text chứa payload thử nghiệm; xác nhận escaping và sanitization theo trust policy.
5. **Load test:** Đo origin QPS, p95, cache hit ratio và error rate khi campaign tăng traffic.

## Quan sát trong production

Application Insights: request/dependency latency, exception, trace ID; logs: page ID, content version, tenant authorization outcome (không log giá), origin cache hit; Akamai: cache key/config, hit/miss, Age, purge status; alerts: bất thường tỷ lệ 403, pricing requests anonymous, CDN serving private endpoints, stale-content SLO. Sau hotfix cần chủ động đánh giá phạm vi dữ liệu đã lộ qua CDN/access logs và quy trình incident response.

2. Nếu CMS publish event bị mất, cơ chế reconciliation nào ngăn stale content kéo dài?
3. Khi nào nên dùng output caching tại origin thay vì chỉ CDN?

# Code Review Challenge 2 — Rolling deployment làm mất đơn hàng khi schema thay đổi

**Chủ đề:** .NET 8, SQL Server, EF Core, Kubernetes, Jenkins/Octopus Deploy, backward-compatible migration  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút

## Bối cảnh

Một e-commerce order API chạy 6 replicas trên Kubernetes, dùng SQL Server. Team chuyển từ cột `Orders.CustomerName` sang `Orders.CustomerFirstName` và `Orders.CustomerLastName`. Pipeline deploy version mới trong rolling update; phiên bản cũ và mới có thể cùng xử lý request vài phút. Khi triển khai ở staging (1 replica) thành công, nhưng production có 500 và một số order không lưu được. DB khoảng 40 triệu rows, traffic 150 writes/s. Có thể tạm dừng rollout, nhưng không được mất order và rollback application phải khả thi.

```csharp
public sealed class OrderDbContext : DbContext
{
    public DbSet<Order> Orders => Set<Order>();

    public OrderDbContext(DbContextOptions<OrderDbContext> options)
        : base(options) { }
}

public sealed class Order
{
    public long Id { get; set; }
    public string CustomerFirstName { get; set; } = "";
    public string CustomerLastName { get; set; } = "";
    public decimal Total { get; set; }
}

public sealed class OrderService
{
    private readonly OrderDbContext _db;

    public OrderService(OrderDbContext db) => _db = db;

    public async Task<long> CreateAsync(
        string fullName, decimal total, CancellationToken ct)
    {
        var parts = fullName.Split(' ', 2);
        var order = new Order
        {
            CustomerFirstName = parts[0],
            CustomerLastName = parts.Length > 1 ? parts[1] : "",
            Total = total
        };
        _db.Orders.Add(order);
        await _db.SaveChangesAsync(ct);
        return order.Id;
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Drop column trước khi old pods ngừng hoạt động

**Vấn đề:** Migration phá contract của binary cũ ngay lập tức.  
**Tại sao xảy ra:** Rolling deployment không cập nhật tất cả pods cùng lúc; old EF model vẫn tham chiếu `CustomerName`.  
**Ảnh hưởng production:** SQL errors, 500, write failures; rollback app không khôi phục cột đã drop.  
**Cách sửa:** Expand schema trước, giữ cột cũ đến khi toàn bộ readers/writers tương thích và rollback window kết thúc.

### [High] — Existing rows bị thay tên bằng chuỗi rỗng

**Vấn đề:** Thêm cột NOT NULL với default rỗng nhưng không backfill từ `CustomerName`.  
**Tại sao xảy ra:** Migration không bảo tồn semantic dữ liệu lịch sử.  
**Ảnh hưởng production:** Dữ liệu khách hàng mất ý nghĩa; downstream reporting/search sai.  
**Cách sửa:** Backfill theo batches có checkpoint, validate counts/sample và giữ original column đến khi reconcile.

### [High] — Mixed-version writes không được đồng bộ

**Vấn đề:** Old code ghi `CustomerName`, new code chỉ ghi hai cột mới.  
**Tại sao xảy ra:** Hai model khác nhau cùng tồn tại trong rollout.  
**Ảnh hưởng production:** Divergent fields, reads không nhất quán; backfill có thể ghi đè dữ liệu mới.  
**Cách sửa:** Giai đoạn compatibility dùng dual-write hoặc database synchronization được kiểm soát; thiết kế read precedence và reconciliation rõ ràng.

### [High] — Migration có nguy cơ lock và gây nghẽn traffic

**Vấn đề:** DDL trên bảng 40 triệu rows và backfill nếu làm một transaction lớn có thể gây blocking, log growth.  
**Tại sao xảy ra:** Chưa đánh giá execution/locking, DB edition, constraints và maintenance window.  
**Ảnh hưởng production:** p95 tăng, timeouts, deadlocks, storage/log pressure.  
**Cách sửa:** Test migration trên bản sao production-like; batch update theo key ranges, giới hạn batch, theo dõi locks/log, có pause/resume.

### [High] — Rollback không an toàn

**Vấn đề:** Deployment có thể quay về image cũ nhưng schema không còn cột cũ.  
**Tại sao xảy ra:** App rollback và schema rollback bị xem như một thao tác.  
**Ảnh hưởng production:** Incident kéo dài, không thể phục hồi chỉ bằng rollback image.  
**Cách sửa:** Contract phase tách biệt sau rollback window; có kế hoạch restore dữ liệu đã xác minh, không tự động chạy destructive down migration.

### [Medium] — latest tag không bảo đảm artifact identity

**Vấn đề:** Image tag `latest` mutable.  
**Tại sao xảy ra:** Các pods có thể pull image khác nhau ở các thời điểm khác nhau; khó audit/rollback.  
**Ảnh hưởng production:** Non-reproducible deployments và điều tra incident khó.  
**Cách sửa:** Pin immutable digest hoặc version tag được bảo vệ, ghi build SHA vào release telemetry.

### [Medium] — Readiness chưa thể hiện trạng thái phục vụ

**Vấn đề:** `/health` có thể trả 200 dù dependency/schema không tương thích.  
**Tại sao xảy ra:** Không có phân tách liveness/readiness và contract check thích hợp.  
**Ảnh hưởng production:** Pod nhận traffic rồi trả 500; shutdown có thể làm rớt in-flight requests.  
**Cách sửa:** Readiness kiểm tra các dependency tối thiểu và version compatibility không tốn kém; graceful termination, rollout gates theo error rate.

### [Medium] — Name parsing làm mất cấu trúc tên

**Vấn đề:** `Split(' ', 2)` không xử lý null/whitespace, nhiều thành phần, Unicode normalization hoặc business meaning của first/last name.  
**Tại sao xảy ra:** Tự suy ra semantic từ free-text field.  
**Ảnh hưởng production:** Dữ liệu không đúng và downstream integration sai.  
**Cách sửa:** Xác nhận requirement; ưu tiên giữ `FullName` nguyên vẹn nếu không thể phân tách đáng tin cậy; validation và user input có cấu trúc khi cần.

## Phiên bản đề xuất

Kế hoạch an toàn minh họa; phải xác minh DB schema, index và compatibility của mọi consumer trước khi chạy.

**Phase A — Expand (không phá old app):**

```sql
ALTER TABLE dbo.Orders
    ADD CustomerFirstName nvarchar(100) NULL,
        CustomerLastName nvarchar(100) NULL;
```

**Phase B — Compatibility app:** Deploy image immutable; app vẫn ghi `CustomerName` đồng thời ghi các trường mới nếu schema đã expand. Với dữ liệu không thể tách chính xác, giữ nguyên full name và đánh dấu trạng thái migration cần xử lý. Dưới đây là ví dụ phần write-path, giả định model có đủ cả ba cột và dữ liệu đầu vào đã được validate:

```csharp
public async Task<long> CreateAsync(
    string fullName, string? firstName, string? lastName,
    decimal total, CancellationToken ct)
{
    if (string.IsNullOrWhiteSpace(fullName))
        throw new ArgumentException("Full name required", nameof(fullName));

    var order = new Order
    {
        CustomerName = fullName.Trim(),
        CustomerFirstName = firstName?.Trim(),
        CustomerLastName = lastName?.Trim(),
        Total = total
    };
    _db.Orders.Add(order);
    await _db.SaveChangesAsync(ct);
    return order.Id;
}
```

**Phase C — Backfill:** Sau khi tất cả writers hỗ trợ compatibility contract, chạy batch job idempotent với checkpoint. Chỉ điền các trường mới khi thiếu, không ghi đè dữ liệu mới hơn. Ví dụ dưới đây chỉ minh họa checkpoint theo `Id`, không cố tách tên tự động:

```sql
SELECT TOP (500) Id, CustomerName
FROM dbo.Orders
WHERE Id > @LastProcessedId
ORDER BY Id;
```

Persist checkpoint **sau** khi mỗi batch đã được cập nhật thành công; reconciliation cuối phải quét cả rows được tạo/đổi trong migration window, không chỉ dựa vào một lượt tăng `Id`. Nếu cần tách tên, xác định mapping với Product/QA và xử lý ngoại lệ. Cần có migration-state/validation metrics.

**Phase D — Contract:** Chỉ sau khi không còn old readers/writers, xác nhận backfill hoàn tất, audit downstream consumers, hoàn thành rollback window và có backup/restore rehearsal mới cân nhắc NOT NULL constraints và drop cột cũ trong release riêng. Không mặc định chạy schema migration khi mỗi pod khởi động.

```yaml
containers:
  - name: api
    image: registry.example/order-api@sha256:REPLACE_WITH_VERIFIED_DIGEST
    ports:
      - containerPort: 8080
    readinessProbe:
      httpGet:
        path: /health/ready
        port: 8080
      periodSeconds: 5
    livenessProbe:
      httpGet:
        path: /health/live
        port: 8080
      periodSeconds: 10
    terminationMessagePolicy: FallbackToLogsOnError
```

Đoạn YAML là fragment của container spec; digest placeholder phải thay bằng digest thực trước deploy. Cần cấu hình termination grace period và graceful shutdown phù hợp workload; probe phải thực sự được triển khai. Pipeline Jenkins/Octopus Deploy nên có phase gates riêng cho expand, app rollout, backfill, contract, với manual approval cho bước destructive.

## Giải thích thiết kế sau khi sửa

Đơn vị release không chỉ là binary: schema, jobs, consumers và deployment strategy tạo thành compatibility contract. Expand trước cho phép old app sống tiếp. Compatibility release bảo đảm mọi writer duy trì cả hai biểu diễn trong migration window. Backfill/reconciliation đo được và có thể tiếp tục sau failure. Contract chỉ được thực hiện sau khi không còn dependency cũ.

## Trade-offs

Dual-write tăng code và có thể tạo divergence nếu hai update không cùng transaction; cùng một row trong một SQL transaction giúp giảm rủi ro nhưng không giải quyết các consumer ngoài DB. Nullable columns tồn tại lâu hơn làm tăng technical debt, đổi lại rollback an toàn. Batch nhỏ giảm lock pressure nhưng kéo dài migration; cần chọn bằng số liệu. Không cần microservices, messaging hay Kubernetes operator mới để giải quyết vấn đề này.

## Cách kiểm thử

1. **Mixed-version integration:** Old và compatibility binaries cùng chạy trên expanded schema; create/read/update đều thành công.
2. **Database migration:** Backfill dữ liệu lịch sử có tên đặc biệt, null/empty, non-Latin, dữ liệu mới phát sinh giữa chừng; đối soát số lượng.
3. **Failure injection:** Kill batch job giữa transaction, resume checkpoint, kiểm tra không overwrite newer values.
4. **Load/locking:** Production-like table và write rate; đo blocking, transaction log, p95/p99, deadlocks.
5. **Deployment rollback:** Rollout 20–50%, tăng lỗi giả lập, rollback image cũ mà không cần rollback schema; xác minh không mất đơn hàng.

## Quan sát trong production

Application Insights: error rate, SQL dependency failures, p95/p99 theo app version và trace ID; SQL Server: waits, blocking, deadlocks, log usage, batch throughput, migration mismatch count; Kubernetes: pod image digest, ready replicas, restarts, rollout events; CI/CD: migration phase, checksum, approvals và audit trail. Đặt alert cho 5xx tăng, failed order writes, reconciliation mismatch và lock wait vượt baseline. Khi incident: chặn rollout/destructive migration, ổn định traffic, thu thập evidence rồi mới sửa.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một hệ thống báo cáo ngoài team vẫn query `CustomerName`, làm sao chứng minh đủ điều kiện contract?
2. Nếu dual-write không thể bảo đảm vì dữ liệu có hai nguồn cập nhật, bạn chọn cơ chế reconcile nào?
3. Nếu Product yêu cầu deploy không downtime nhưng schema change có lock lâu, bạn sẽ đề xuất rollout/maintenance trade-off ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Shared cache không được chứa dữ liệu phụ thuộc tenant/identity nếu cache key và authorization không bảo đảm isolation. CMS publish, origin cache và CDN là các vòng đời invalidation khác nhau. Database migration trong rolling deployment là bài toán tương thích đa phiên bản và bảo toàn dữ liệu, không chỉ là câu lệnh ALTER TABLE.

## Mẫu tư duy cần nhớ

1. Phân loại public/private data trước khi thiết kế cache.
2. Xác minh trust boundary và authorization ở server, không tin client header.
3. Khi incident, ổn định hệ thống rồi kiểm tra logs, traces, cache provenance và SQL evidence.
4. Với schema change, dùng expand → compatibility → backfill/reconcile → contract.
5. Kiểm thử mixed versions, failure paths và rollback trước khi triển khai production.
