# Câu 1 — Keyset pagination có thực sự không bỏ sót bản ghi?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** SQL Server, PostgreSQL, EF Core, isolation, composite indexes, query plans, HTTP API pagination.

## Bối cảnh

Một API .NET 8 liệt kê lịch sử thay đổi của 8 triệu đơn hàng. Giao diện React yêu cầu tải thêm 50 dòng mỗi lần, sắp xếp theo \`CreatedAt DESC\`. Với \`OFFSET 500000 FETCH NEXT 50\`, p95 tăng đáng kể. Nhóm chuyển sang cursor \`CreatedAt < lastCreatedAt\`; sau đó QA báo một số dòng có cùng timestamp không xuất hiện, và khi có đơn hàng mới thì người dùng thấy kết quả không ổn định. Chưa biết index, transaction isolation, yêu cầu snapshot, hay việc dữ liệu được cập nhật trong lúc phân trang.

## Câu hỏi chính

Giải thích cơ chế SQL ordering, index seek/scan và tính nhất quán giữa các request; thiết kế pagination vừa hiệu quả vừa có semantics rõ ràng khi dữ liệu được insert/update đồng thời, đồng thời chỉ ra cách kiểm chứng.

## Câu hỏi làm rõ nên cân nhắc

1. \`CreatedAt\` có immutable và độ phân giải bao nhiêu? Có nhiều hàng trùng timestamp không?
2. Có bắt buộc xem snapshot cố định qua nhiều request hay chấp nhận feed cập nhật liên tục?
3. Filter có tenant, status, khoảng ngày không? Index hiện tại và execution plan là gì?
4. Client có thể nhảy tới trang N hoặc chỉ infinite scroll?
5. Có thể xóa/cập nhật bản ghi trong khi người dùng đang đọc không?

## Gợi ý tư duy

### Gợi ý 1

Một sort key không duy nhất chưa xác định thứ tự tổng.

### Gợi ý 2

Hãy kết hợp sort key với unique ID và giữ nguyên predicate ở trang kế tiếp.

### Gợi ý 3

Keyset không tự cung cấp snapshot xuyên nhiều HTTP requests; phân biệt duplicate/skip do ordering với thay đổi dữ liệu.

## Cấu trúc trả lời đề xuất

1. Xác định semantics của feed và yêu cầu nhất quán.
2. Giải thích OFFSET, keyset, stable ordering và SQL plan.
3. Thiết kế cursor, filter, index, validation.
4. Phân tích concurrent inserts/updates, isolation và các phương án snapshot.
5. Benchmark, test, observability và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

- \`ORDER BY CreatedAt DESC, Id DESC\` tạo thứ tự xác định nếu Id duy nhất.
- Predicate kế tiếp: \`CreatedAt < @lastTime OR (CreatedAt = @lastTime AND Id < @lastId)\`; \`CreatedAt < @lastTime\` đơn độc bỏ qua các dòng cùng timestamp.
- OFFSET phải đi qua nhiều vị trí trước khi lấy trang sâu; keyset có thể tận dụng composite index nhưng cần kiểm tra plan thực tế.
- Mỗi request đọc một trạng thái dữ liệu khác nhau; keyset không đồng nghĩa snapshot consistency.

### Điểm cộng

- Cursor opaque chứa last tuple, filter fingerprint, sort version; ký HMAC nếu cần chống sửa.
- Composite index xét tenant/filter và sort; bao gồm cột projection có chọn lọc, cân nhắc write overhead.
- Giới hạn page size, dùng projection và \`AsNoTracking\` khi phù hợp.

### Senior+

- Nêu trade-off giữa live feed, high-water mark và snapshot/materialized result.
- Với updates thay đổi sort key, cần semantics immutable event sequence hoặc snapshot token, không hứa keyset giải quyết mọi anomaly.
- Phân biệt index seek, residual predicate, key lookup, statistics và isolation tùy SQL Server/PostgreSQL.

## Hướng giải quyết tham khảo

**Giả định:** \`CreatedAt\` và \`Id\` không thay đổi, \`Id\` là unique, API chỉ hỗ trợ next-page, feed có thể xuất hiện bản ghi mới nhưng không yêu cầu snapshot tuyệt đối. Khi đó keyset là lựa chọn hợp lý.

Ví dụ EF Core:

\`\`\`csharp
public async Task<IReadOnlyList<OrderRow>> GetNextAsync(
    Guid tenantId, DateTime? lastCreatedAt, Guid? lastId,
    int requestedSize, CancellationToken ct)
{
    var size = Math.Clamp(requestedSize, 1, 100);
    var query = db.Orders.AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (lastCreatedAt.HasValue && lastId.HasValue)
    {
        var time = lastCreatedAt.Value;
        var id = lastId.Value;
        query = query.Where(x => x.CreatedAt < time ||
            (x.CreatedAt == time && x.Id.CompareTo(id) < 0));
    }

    return await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Select(x => new OrderRow(x.Id, x.CreatedAt, x.Status))
        .Take(size)
        .ToListAsync(ct);
}
\`\`\`

Đây là **pseudocode minh họa predicate**, không phải bảo đảm LINQ provider nào cũng dịch \`Guid.CompareTo\` như mong muốn. Trong production, xác minh translation cho SQL Server/PostgreSQL, hoặc chọn khóa \`bigint\` tăng đơn điệu và SQL predicate đã kiểm thử. Ví dụ SQL khi \`Id\` là \`bigint\`:

\`\`\`sql
SELECT TOP (@pageSize) Id, CreatedAt, Status
FROM dbo.Orders
WHERE TenantId = @tenantId
  AND (
    @lastCreatedAt IS NULL
    OR CreatedAt < @lastCreatedAt
    OR (CreatedAt = @lastCreatedAt AND Id < @lastId)
  )
ORDER BY CreatedAt DESC, Id DESC;
\`\`\`

Trong thực tế có thể tách query trang đầu và trang sau để optimizer tránh optional predicate. Index ứng viên: \`(TenantId, CreatedAt DESC, Id DESC) INCLUDE (Status)\` trên SQL Server; phải đo write cost, storage, actual execution plan và logical reads. Không đưa tất cả cột vào covering index theo phản xạ.

Nếu cần **consistent export** trên nhiều request, snapshot isolation trong từng request chưa đủ: cần snapshot server-side, immutable event cutoff kèm định nghĩa rõ, hoặc materialized result/token với TTL; transaction kéo dài qua nhiều HTTP requests thường gây operational cost. High-water mark hạn chế inserts mới nhưng không giải quyết updates/deletes tùy nghiệp vụ. Cursor cần gắn filter, sort, tenant; không tin tenant ID từ client nếu authorization dựa trên identity.

Test với hàng nghìn record trùng timestamp, insert trước/sau cursor, xóa record, thay filter, nhiều tenant và tải sâu. So sánh p50/p95, logical reads, actual plan, lock waits và độ ổn định kết quả. Rollout canary với feature flag, rollback sang phương thức cũ nếu correctness regression.

## Mẫu trả lời trong phỏng vấn

“Trước hết tôi hỏi feed cần live hay snapshot. OFFSET sâu chậm vì database vẫn phải xử lý các hàng trước trang mong muốn, nhưng chuyển sang cursor chỉ dùng CreatedAt là sai khi timestamp trùng. Tôi sẽ dùng thứ tự tổng \`CreatedAt DESC, Id DESC\`, predicate lexicographic tương ứng và composite index theo tenant cùng thứ tự sort. Tôi không kết luận nhanh hơn cho mọi workload: cần actual plan và logical reads. Keyset ổn định vị trí tương đối nếu sort keys immutable, nhưng không tự khóa snapshot xuyên các request; nếu Product yêu cầu export đúng một tập dữ liệu, tôi chọn snapshot/materialization hoặc event cutoff được định nghĩa rõ. Tôi sẽ kiểm thử concurrent writes, isolation, tenant authorization và benchmark trước khi rollout.”

## Câu hỏi đào sâu

1. Nếu business yêu cầu nhảy trực tiếp tới trang 10.000, bạn sẽ thay đổi API hoặc UX như thế nào?
2. Nếu \`CreatedAt\` có thể bị sửa, tại sao cursor đôi vẫn có thể duplicate/skip?
3. Composite index giúp đọc nhưng làm write latency tăng: quyết định dựa trên dữ liệu nào?

## Lỗi trả lời thường gặp

- Dùng \`CreatedAt < cursor\` và quên tie-breaker.
- Khẳng định keyset luôn cho snapshot nhất quán.
- Đề xuất index mà không xem filter, actual plan và write cost.
- Dùng cursor từ client làm nguồn tin cậy cho tenant authorization.
- Chỉ đo average latency, không kiểm thử dữ liệu bị thiếu/trùng.

# Câu 2 — IIS App Pool recycle và lỗi đăng nhập sau deployment

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC/.NET Framework 4.5, authentication cookies, machineKey, deployment, observability, incident management.

## Bối cảnh

Một cổng nội bộ ASP.NET MVC chạy trên .NET Framework 4.5, hai Windows Server sau load balancer. Sau đợt Octopus Deploy, người dùng bị đăng xuất ngẫu nhiên và có lúc nhận HTTP 500. Sự cố xảy ra nhiều hơn khi traffic cao; log IIS có các lần worker process restart nhưng chưa rõ nguyên nhân. Team định tăng memory limit và bật sticky sessions vĩnh viễn. Không có dữ liệu về authentication mode, cấu hình \`machineKey\`, web garden, session mode, recycle schedule, application errors hay health probes.

## Câu hỏi chính

Bạn sẽ chỉ huy điều tra và ổn định sự cố thế nào, từ ảnh hưởng người dùng đến root cause, rollback, kiểm thử và phòng ngừa, mà không kết luận sớm rằng recycle là nguyên nhân duy nhất?

## Câu hỏi làm rõ nên cân nhắc

1. Authentication dùng Forms Authentication, OWIN cookies hay external IdP? Có mã hóa/sign cookies bằng key cục bộ không?
2. Deployment có thay \`web.config\`, \`machineKey\`, binary, certificate hoặc session storage không?
3. Recycle là scheduled, memory threshold, config change, crash hay health-check-triggered?
4. 500 xảy ra trên server nào, trước/sau recycle, có exception và event ID nào?
5. Load balancer affinity, session mode, warm-up và rollback artifact có sẵn không?

## Gợi ý tư duy

### Gợi ý 1

Tách mất session, không giải mã được auth cookie và HTTP 500 thành các triệu chứng có thể có nguyên nhân khác nhau.

### Gợi ý 2

Một cookie được bảo vệ trên node A có thể không được node B chấp nhận nếu cryptographic configuration không đồng bộ.

### Gợi ý 3

Đối chiếu deploy timeline, IIS/WAS events, ASP.NET exceptions, config diffs và request correlation trước khi thay đổi topology.

## Cấu trúc trả lời đề xuất

1. Đo ảnh hưởng và phân loại mức độ.
2. Ổn định: rollback/traffic drain theo điều kiện.
3. Thu thập timeline và chứng cứ từng node.
4. Lập nhiều giả thuyết, xác minh riêng.
5. Fix ngắn hạn và kiến trúc vận hành dài hạn.
6. Test deployment, failover, telemetry, postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Xác định số user/session bị ảnh hưởng, tỷ lệ 401/302 login và 500 theo node/version.
- Không coi recycle luôn là bug; recycle có thể là hành vi bình thường hoặc hậu quả của crash.
- Xác minh cấu hình bảo vệ cookie tương thích giữa nodes (với Forms Authentication trên .NET Framework thường liên quan \`machineKey\`).
- Phân biệt InProc session mất khi process restart với auth cookie validity.
- Có rollback, drain, warm-up và bảo toàn logs trước khi thay đổi.

### Điểm cộng

- Kiểm tra Event Viewer Application/System, WAS/W3SVC, IIS logs, Failed Request Tracing, crash dumps theo chính sách.
- So sánh package hash, config transforms và Octopus variable sets.
- Không dùng sticky sessions làm giải pháp cho key mismatch hoặc state loss khi node chết.

### Senior+

- Đề xuất release gates, deployment smoke test trên từng node, canary và synthetic login.
- Bảo vệ secret/key bằng quản trị cấu hình an toàn; rotate có kế hoạch tương thích cookie.
- Chia incident command, communication cadence và postmortem không đổ lỗi.

## Hướng giải quyết tham khảo

**Impact:** đo số lần redirect về login, số phiên bị mất, 500 theo \`server\`, \`appVersion\`, thời gian và route; thông báo Product/Support với workaround thực tế. Không log cookie/token thô.

**Stabilize:** nếu tương quan mạnh với deployment và có artifact ổn định, cân nhắc rollback theo node, drain connections, warm-up, kiểm tra login/health trước khi đưa lại traffic. Nếu nghi cấu hình key khác nhau, ngừng chuyển traffic đến node sai cấu hình trong khi xác minh, không thay đổi key tùy tiện vì có thể invalidate cookies. Lưu lại logs/config diff có kiểm soát.

**Giả thuyết cạnh tranh:**
- \`machineKey\` không đồng nhất khiến protected auth cookie không được xác thực trên node còn lại; xác minh bằng cross-node login/failover, config fingerprints và cookie validation events.
- \`InProc\` session mất sau recycle; xác minh session mode, recycle timeline và dữ liệu nào thực sự nằm trong session.
- Process crash do unhandled exception, native dependency hoặc memory pressure; xác minh WAS events, dump, counters, 500 substatus.
- Deployment config transforms/binary mismatch hoặc startup failure; so sánh artifacts, binding redirects, event logs, health.
- Load balancer health probe đưa node chưa warm-up vào phục vụ; kiểm tra probe và startup latency.

**Fix có điều kiện:** đồng bộ key bảo vệ cookie qua các node với secret management và rotation policy phù hợp; chuyển state nghiệp vụ quan trọng ra khỏi InProc session nếu yêu cầu chịu được recycle/failover; sửa crash theo dump thay vì tăng memory limit mù quáng; cấu hình health/readiness và deployment rollout từng node. Không giả định ASP.NET Core Data Protection áp dụng nguyên xi cho Forms Authentication .NET Framework.

**Verification:** kiểm thử login trên node A rồi request node B; recycle từng node; rollout/rollback package; soak/load test; xác nhận 401/302/500 trở lại baseline. Theo dõi \`w3wp\` process uptime, private bytes, request queue, recycle reasons, failed requests và authentication failure rate. Đặt alert theo SLO và regression threshold thay vì số lần recycle đơn lẻ.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ tách hai triệu chứng: bị đăng xuất và HTTP 500. Đầu tiên đo tỷ lệ lỗi theo node, version và timeline deploy, sau đó giảm tác động bằng rollback hoặc drain node nếu bằng chứng ủng hộ. Với ASP.NET MVC trên .NET Framework, tôi kiểm tra cookie protection giữa hai node, machineKey, session mode và recycle reasons. Một recycle bình thường có thể làm mất InProc session nhưng không nhất thiết làm auth cookie mất hiệu lực; key mismatch có thể khiến cookie không hợp lệ khi request chuyển node. Song song tôi xem WAS events, exception logs và config diff để không bỏ qua crash hoặc startup failure. Tôi sẽ fix theo nguyên nhân đã xác minh, kiểm thử failover và triển khai từng node với synthetic login, telemetry và rollback rõ ràng. Sticky sessions chỉ là biện pháp giảm triệu chứng trong vài trường hợp, không phải sửa tận gốc.”

## Câu hỏi đào sâu

1. Nếu không thể rollback vì database schema đã thay đổi, bạn ổn định thế nào?
2. Nếu machineKey đã giống nhau nhưng 500 vẫn xảy ra, bước điều tra tiếp theo là gì?
3. Bạn sẽ thay đổi thiết kế session thế nào khi chuyển ứng dụng lên Azure App Service?

## Lỗi trả lời thường gặp

- Gán tất cả lỗi cho recycle khi chưa có evidence.
- Bật sticky sessions rồi coi hệ thống đã chịu được node failure.
- Thay machineKey production mà không đánh giá ảnh hưởng cookie hiện có.
- Không phân biệt auth cookie và InProc session.
- Không có rollback, per-node telemetry hoặc incident communication.

# Câu 3 — Chọn SQL Server hay Cosmos DB cho audit timeline đa tenant?

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35 phút  
**Kỹ năng được đánh giá:** data modeling, SQL Server, Cosmos DB, partition keys, consistency, authorization, API, Azure architecture, cost and failure modes.

## Bối cảnh

Một hệ thống approval workflow .NET 8 đang lưu transaction trong SQL Server. Product muốn thêm audit timeline cho từng hồ sơ: ai sửa gì, khi nào, trạng thái trước/sau, có thể tìm theo tenant và export. Quy mô giả định: 300 tenant, 15 triệu audit events/năm, 95% request đọc timeline theo một hồ sơ, 5% là truy vấn compliance theo tenant trong khoảng thời gian. Có đề xuất chuyển toàn bộ audit sang Cosmos DB “để scale”, đề xuất khác thêm bảng SQL, và đề xuất thứ ba đẩy events qua Azure Service Bus rồi index vào Elasticsearch. Chưa biết retention, legal hold, độ trễ chấp nhận, RU budget hay quy định về PII.

## Câu hỏi chính

Thiết kế audit timeline và chọn storage/ingestion/deployment phù hợp, làm rõ điều kiện khiến bạn thay đổi quyết định; giải thích consistency, security, query cost, operational complexity và failure recovery.

## Câu hỏi làm rõ nên cân nhắc

1. Audit phải commit atomically cùng nghiệp vụ hay chấp nhận eventual consistency? Mức độ mất event chấp nhận được?
2. Có yêu cầu bất biến, tamper evidence, retention/legal hold, xóa PII theo quy định không?
3. Truy vấn chủ đạo theo \`CaseId\`, \`TenantId\` hay cross-tenant? Cần full-text search không?
4. Tenant lớn nhất chiếm bao nhiêu traffic/storage? Export tối đa bao nhiêu bản ghi?
5. Độ trễ timeline, RPO/RTO, chi phí vận hành và quyền truy cập audit ra sao?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu từ transaction boundary và query patterns, không bắt đầu từ tên database.

### Gợi ý 2

Partition key có thể tối ưu một kiểu truy vấn và làm kiểu khác đắt hơn.

### Gợi ý 3

Nếu đưa message broker vào giữa, phải thiết kế durable publish, duplicate handling và replay.

## Cấu trúc trả lời đề xuất

1. Định nghĩa invariants và compliance.
2. Thiết kế event schema, API, authorization.
3. So sánh SQL, Cosmos DB và asynchronous read model.
4. Chọn consistency/partitioning/index/retention.
5. Phân tích failure, recovery, deployment, migration.
6. Benchmark, observability, security và cost.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Audit event có \`EventId\`, \`TenantId\`, \`CaseId\`, \`ActorId\`, \`OccurredAt\`, \`EventType\`, \`SchemaVersion\`, payload được kiểm soát PII.
- Nếu audit là bắt buộc cùng business write, SQL transaction với audit row hoặc transactional outbox trong cùng database là baseline đáng cân nhắc.
- Cosmos DB partition key phải dựa trên access pattern, tenant skew, RU và giới hạn thực tế; không mặc định partition theo tenant là đủ.
- Cross-partition queries, secondary index/search projection và export có chi phí.
- Authorization theo tenant và vai trò compliance; immutable append semantics, audit access logging.

### Điểm cộng

- Keyset pagination, partitioned retention, cold archive, event schema evolution, idempotent consumers.
- Service Bus là transport, không phải audit source of truth; Elasticsearch là search projection, không mặc nhiên là ledger.
- Đo storage/index cost, read/write latency, RU consumption, hot partitions, replay lag.

### Senior+

- Tách event creation consistency khỏi search freshness SLO.
- Phân tích tenant+case partitioning, hierarchical partition keys hoặc bucketing khi phù hợp, nhưng phải kiểm chứng khả năng và giới hạn theo cấu hình Cosmos DB thực tế.
- Có phương án integrity/tamper-evidence và quy trình legal hold mà không khẳng định append-only table tự động đáp ứng compliance.

## Hướng giải quyết tham khảo

**Giả định quyết định:** audit phải ghi bền vững cùng thay đổi approval; phần lớn truy vấn theo case; hiện SQL Server đã được vận hành tốt và chưa có evidence quá tải. Tôi ưu tiên **SQL Server audit table + transactional outbox nếu cần fan-out**, chưa chuyển ngay sang Cosmos DB.

Schema gợi ý:

\`\`\`sql
CREATE TABLE dbo.CaseAudit (
    EventId uniqueidentifier NOT NULL PRIMARY KEY,
    TenantId uniqueidentifier NOT NULL,
    CaseId bigint NOT NULL,
    OccurredAt datetime2(7) NOT NULL,
    ActorId nvarchar(128) NOT NULL,
    EventType nvarchar(80) NOT NULL,
    SchemaVersion int NOT NULL,
    Payload nvarchar(max) NOT NULL
);
CREATE INDEX IX_CaseAudit_Tenant_Case_Time
ON dbo.CaseAudit (TenantId, CaseId, OccurredAt DESC, EventId DESC);
\`\`\`

Trong transaction của approval, ghi thay đổi trạng thái + audit event (và outbox nếu có integration). \`EventId\` bảo đảm uniqueness, consumer dùng inbox/idempotency khi retry. API \`GET /cases/{id}/audit?cursor=...\` enforce tenant authorization ở server; export compliance chạy background với job status, giới hạn, audit access và storage encryption. Dùng server-side projection/field redaction; không đưa secrets hoặc toàn bộ object tùy ý vào payload.

**Khi Cosmos DB hợp lý:** nếu workload document, throughput/geo-distribution, access pattern và vận hành chứng minh lợi ích vượt chi phí; cần prototype với partition key phù hợp, đo RU theo query, hot partitions, consistency và khả năng export. Nếu audit được ghi SQL rồi async replicate sang Cosmos, Cosmos là read model eventual-consistent; cần outbox, retries, DLQ, replay, checkpoint, lag alert. Không thể dùng distributed transaction xuyên SQL/Cosmos như mặc định.

**Khi Elasticsearch hợp lý:** full-text search hoặc faceted analytics cần thiết; dùng index projection từ durable events, xử lý duplicate/reindex và degraded search. Không dùng search index làm nơi duy nhất lưu audit bắt buộc.

**Trade-offs:** SQL đơn giản và atomic nhưng index/write amplification, retention và growth cần quản lý; Cosmos linh hoạt scale nhưng partition/cost/consistency phức tạp; async pipeline cách ly search nhưng thêm lag, reconciliation và on-call burden. Nếu compliance yêu cầu tamper-evident records, bổ sung hash chain/signing, immutable archival hoặc dịch vụ phù hợp sau khi thẩm định threat model và quy định.

**Testing/operations:** integration test business rollback không để audit orphan; concurrency test hai approval; replay/duplicate test; tenant isolation security test; load test 95/5 query mix; fail Service Bus/search và xác minh SQL source of truth vẫn chính xác. Theo dõi write p95, audit row count, index fragmentation, outbox age, DLQ depth, consumer lag, export failures, unauthorized attempts. Deploy expand/contract schema và backfill có checkpoint; rollback không xóa events đã ghi.

## Mẫu trả lời trong phỏng vấn

“Tôi không chọn Cosmos DB chỉ vì dữ liệu tăng. Tôi hỏi trước audit có bắt buộc atomic cùng approval không và query chủ đạo là gì. Với giả định audit phải tồn tại cùng business transaction, SQL Server hiện có là baseline tốt: ghi audit row trong cùng transaction, index theo tenant/case/time và paginate bằng cursor. Nếu cần search hoặc analytics, tôi phát event từ transactional outbox sang projection; Service Bus chỉ là kênh truyền, Elasticsearch không phải ledger chính. Tôi sẽ cân nhắc Cosmos DB khi workload và benchmark RU/partition chứng minh lợi ích, nhưng phải tính hot tenant, cross-partition export và eventual consistency. Tôi còn thiết kế authorization, PII minimization, retention, replay, observability và rollback. Mục tiêu là đáp ứng invariant với ít operational complexity nhất.”

## Câu hỏi đào sâu

1. Nếu 1 tenant chiếm 80% traffic, partition strategy của bạn sẽ thay đổi ra sao?
2. Nếu compliance yêu cầu timeline xuất hiện ngay sau approval nhưng search index cập nhật trễ 30 giây, bạn xử lý UX/SLO thế nào?
3. Nếu SQL audit table tăng đến hàng tỷ dòng, vì sao bạn vẫn có thể chọn giữ SQL hoặc quyết định chuyển một phần?

## Lỗi trả lời thường gặp

- Coi NoSQL luôn nhanh hơn SQL mà không đo query pattern.
- Dùng Service Bus/Elasticsearch làm nguồn dữ liệu audit duy nhất.
- Không bảo đảm atomicity hoặc có recovery cho event publication.
- Chọn partition key theo cảm tính, bỏ qua hot partitions và export.
- Không thiết kế tenant isolation, PII, retention và audit integrity.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Stable ordering và cursor semantics là bài toán correctness trước khi là bài toán performance.
- IIS recycle, session state, cookie protection và HTTP 500 là các cơ chế khác nhau, phải xác minh từng giả thuyết.
- Audit design bắt đầu từ business invariants và transaction boundaries; storage, broker và search là các quyết định phụ thuộc workload.

## Mẫu tư duy cần nhớ

1. **Clarify before designing:** xác định semantics và invariants trước khi chọn công nghệ.
2. **Measure before optimizing:** xem actual query plan, per-node errors và workload telemetry.
3. **Stabilize before deep investigation:** giảm impact nhưng giữ evidence và rollback.
4. **Design retry together with idempotency:** message delivery và projections phải chịu được duplicate.
5. **Simpler architecture is often safer:** chỉ thêm distributed components khi có nhu cầu đo được.
