## Đoạn code cần review

```csharp
[ApiController]
[Route("api/tenants/{tenantId}/events")]
public sealed class DeviceEventsController : ControllerBase
{
    private readonly Container _container;
    private readonly ILogger<DeviceEventsController> _logger;

    public DeviceEventsController(Container container,
        ILogger<DeviceEventsController> logger)
    {
        _container = container;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> Ingest(
        string tenantId, [FromBody] List<DeviceEventInput> events)
    {
        foreach (var item in events)
        {
            var document = new
            {
                id = Guid.NewGuid().ToString("N"),
                tenantId,
                deviceId = item.DeviceId,
                eventId = item.EventId,
                timestamp = item.Timestamp,
                payload = item.Payload
            };

            try
            {
                await _container.CreateItemAsync(
                    document, new PartitionKey(tenantId));
            }
            catch (CosmosException ex)
            {
                _logger.LogWarning(ex,
                    "Cosmos write failed: {Tenant} {Event}",
                    tenantId, item.EventId);
            }
        }

        return Ok(new { accepted = events.Count });
    }

    [HttpGet("{deviceId}")]
    public async Task<IActionResult> Recent(
        string tenantId, string deviceId)
    {
        var sql = "SELECT TOP 100 * FROM c WHERE " +
                  $"c.deviceId = '{deviceId}' ORDER BY c.timestamp DESC";
        var query = _container.GetItemQueryIterator<dynamic>(sql);
        var items = new List<dynamic>();

        while (query.HasMoreResults)
        {
            var page = await query.ReadNextAsync();
            items.AddRange(page);
        }

        return Ok(items);
    }
}

public sealed record DeviceEventInput(
    string DeviceId, string EventId,
    DateTimeOffset Timestamp, object Payload);
```

## Kết quả code review tham khảo

### [Critical] — Không có idempotency, retry tạo document mới

**Vấn đề:** `Guid.NewGuid()` làm mỗi lần retry có một `id` khác nhau.

**Tại sao xảy ra:** Cosmos DB không thể nhận diện hai request là cùng một business event. `eventId` chỉ là property thường, không tự tạo uniqueness.

**Ảnh hưởng production:** Duplicate event, sai thống kê, downstream processing lặp.

**Cách sửa:** Xác định contract `eventId` duy nhất theo device; dùng deterministic `id` từ device/event trong partition tương ứng, `CreateItemAsync` và xử lý 409 Conflict như duplicate đã biết sau khi kiểm tra contract. Nếu payload có thể khác cho cùng event ID, cần chính sách conflict rõ ràng.

### [High] — Trả success dù write thất bại

**Vấn đề:** Catch mọi `CosmosException` và trả `accepted = events.Count`.

**Tại sao xảy ra:** Kết quả batch không phản ánh kết quả ghi; 400, 403, 429 và 5xx bị coi như nhau.

**Ảnh hưởng production:** Silent data loss và client không retry đúng.

**Cách sửa:** Phân loại retryable/permanent errors, trả kết quả theo item hoặc chỉ ACK khi tất cả đã bền vững; dùng queue nếu cần durable acceptance và asynchronous persistence.

### [High] — Tenant partition key dễ thành hot partition

**Vấn đề:** Mọi write của một tenant dùng cùng partition key.

**Tại sao xảy ra:** Phân bố traffic không đồng đều khiến một logical partition chịu tải cao; tăng tổng RU không nhất thiết chữa được hotspot.

**Ảnh hưởng production:** 429, latency tăng, ingestion backlog.

**Cách sửa:** Đo RU và distribution trước; nếu xác nhận hotspot, tạo container mới với partition strategy phù hợp access pattern, ví dụ hierarchical partition key `/tenantId`, `/deviceId` khi được hỗ trợ bởi cấu hình container, rồi migrate và cutover. Không thể thay partition key của container hiện tại in-place.

### [High] — Truy vấn thiếu tenant filter và partition routing

**Vấn đề:** Query chỉ lọc `deviceId`, không truyền `PartitionKey` vào `QueryRequestOptions`.

**Tại sao xảy ra:** Query có thể chạy cross-partition; nếu deviceId không globally unique, dữ liệu tenant khác có thể xuất hiện.

**Ảnh hưởng production:** Data exposure và RU cao.

**Cách sửa:** Xác thực tenant membership, lọc tenant + device, truyền partition key tương ứng với schema thực tế, kiểm tra query plan/charge.

### [High] — Thiếu authorization theo tenant

**Vấn đề:** Route tenantId được tin tưởng mà không kiểm tra quyền.

**Tại sao xảy ra:** Authentication không đồng nghĩa với authorization; tenantId là untrusted input.

**Ảnh hưởng production:** Cross-tenant write/read.

**Cách sửa:** Áp policy và resource-based authorization, lấy tenant entitlement từ trusted identity/store, không tin client-supplied claim đơn lẻ.

### [High] — Query string interpolation

**Vấn đề:** `deviceId` ghép trực tiếp vào SQL query text.

**Tại sao xảy ra:** Dữ liệu client có thể thay đổi cấu trúc query.

**Ảnh hưởng production:** Query manipulation, dữ liệu ngoài phạm vi, lỗi truy vấn.

**Cách sửa:** `QueryDefinition(...).WithParameter("@deviceId", deviceId)` cùng tenant filter và partition option.

### [Medium] — Batch không giới hạn và xử lý tuần tự

**Vấn đề:** Không validate count, payload size, timestamp và eventId; mỗi item chờ write trước khi xử lý item tiếp theo.

**Tại sao xảy ra:** Endpoint thiếu request contract và concurrency control.

**Ảnh hưởng production:** Slow request, dễ timeout, request lớn gây áp lực memory; throughput thấp.

**Cách sửa:** Giới hạn batch, validate schema, cân nhắc bounded concurrency hoặc queue, không mở `Task.WhenAll` vô hạn.

### [Medium] — Cancellation và partial failure không được mô hình hóa

**Vấn đề:** Không truyền `HttpContext.RequestAborted`; nếu kết nối mất giữa batch, client không biết phần nào đã ghi.

**Tại sao xảy ra:** Không có per-item status và idempotent replay.

**Ảnh hưởng production:** Trùng lặp, retry không kiểm soát, kéo dài shutdown.

**Cách sửa:** Truyền `CancellationToken`, cho phép replay an toàn và trả per-item outcome khi còn kết nối.

### [Medium] — Thiếu telemetry có thể hành động

**Vấn đề:** Chỉ log warning; không ghi status, activity ID, request charge, tenant bucket, batch outcome.

**Tại sao xảy ra:** Không đo được throttling hay cost per access pattern.

**Ảnh hưởng production:** Không xác định được nguyên nhân hotspot và data loss.

**Cách sửa:** Metrics cho RU, 429, latency, batch success/failure, retry, duplicate; traces theo correlation ID; tránh log raw payload hoặc PII.

## Phiên bản đề xuất

Đoạn sau là phần lõi minh họa cho **container mới có partition key `/tenantId`** và deterministic document ID; chưa giải quyết hotspot của tenant lớn. Việc đổi partition strategy phải là migration riêng, không được giả định chỉ đổi tham số ở code.

```csharp
public sealed record EventDocument(
    string id, string tenantId, string deviceId,
    string eventId, DateTimeOffset timestamp, object payload);

public sealed record ItemOutcome(string EventId, string Status);

[HttpPost]
[Authorize]
public async Task<IActionResult> Ingest(
    string tenantId, [FromBody] List<DeviceEventInput> events,
    CancellationToken ct)
{
    if (!await _tenantAccess.CanWriteAsync(User, tenantId, ct))
        return Forbid();

    if (events is null || events.Count is < 1 or > 100 ||
        events.Any(x => string.IsNullOrWhiteSpace(x.DeviceId) ||
                        string.IsNullOrWhiteSpace(x.EventId)))
        return BadRequest();

    var outcomes = new List<ItemOutcome>(events.Count);
    foreach (var item in events)
    {
        var id = StableId(item.DeviceId, item.EventId);
        var doc = new EventDocument(
            id, tenantId, item.DeviceId, item.EventId,
            item.Timestamp, item.Payload);

        try
        {
            using var response = await _container.CreateItemAsync(
                doc, new PartitionKey(tenantId),
                cancellationToken: ct);
            outcomes.Add(new(item.EventId, "created"));
        }
        catch (CosmosException ex) when (
            ex.StatusCode == HttpStatusCode.Conflict)
        {
            outcomes.Add(new(item.EventId, "duplicate"));
        }
        catch (CosmosException ex)
        {
            _logger.LogError(ex,
                "Ingest failed: status={Status} tenant={Tenant}",
                (int)ex.StatusCode, tenantId);
            outcomes.Add(new(item.EventId, "failed"));
        }
    }

    return Ok(new { outcomes });
}

private static string StableId(string deviceId, string eventId)
{
    var bytes = SHA256.HashData(
        Encoding.UTF8.GetBytes(
            $"{deviceId.Length}:{deviceId}{eventId.Length}:{eventId}"));
    return Convert.ToHexString(bytes);
}
```

**Điều kiện bổ sung:** `_tenantAccess` là service authorization được đăng ký qua DI; `HttpStatusCode`, `SHA256`, `Encoding` cần namespace tương ứng. Validate payload size, semantic timestamps, tenant-specific quotas và error contract ở API boundary. Nếu 409 có thể do payload xung đột, đọc document hiện có và so sánh fingerprint trước khi đánh dấu duplicate. SDK retry behavior phải được kiểm chứng theo version và policy thực tế. Với dashboard:

```csharp
var query = new QueryDefinition(
    "SELECT TOP 100 * FROM c " +
    "WHERE c.tenantId = @tenant AND c.deviceId = @device " +
    "ORDER BY c.timestamp DESC")
    .WithParameter("@tenant", tenantId)
    .WithParameter("@device", deviceId);

var options = new QueryRequestOptions
{
    PartitionKey = new PartitionKey(tenantId),
    MaxItemCount = 100
};
```

Truy vấn cần chạy iterator, kiểm soát continuation và đo RU; `TOP 100` không bảo đảm một response page duy nhất. Authorization cho read phải thực hiện trước query. Kiểm tra indexing policy hỗ trợ filter/sort; không mặc định rằng composite index luôn cần thiết.

## Giải thích thiết kế sau khi sửa

Deterministic identity giúp client replay sau network failure. Authorization tenant được thực thi trước data access. Batch outcome tách thành công, duplicate và lỗi để caller xử lý. Query có tenant boundary và partition routing; thay đổi partition strategy được quản lý bằng migration có dual-write/verification hoặc backfill và cutover phù hợp consistency requirement.

## Trade-offs

- Deterministic ID đơn giản nhưng cần contract event uniqueness và xử lý conflict payload.
- Trả per-item result làm client phức tạp hơn; queue + 202 Accepted có thể phù hợp khi cần durable asynchronous ingestion, nhưng bổ sung vận hành và idempotent consumer.
- Hierarchical partition key hoặc bucketing giúp phân tán tải nhưng ảnh hưởng query pattern, migration và transaction scope; cần benchmark RU/latency theo tenant/device.
- Bounded concurrency tăng throughput nhưng cũng có thể làm 429 tăng; đo trước khi tuning.

## Cách kiểm thử

1. **Integration:** Gửi cùng tenant/device/eventId hai lần, chỉ một document tồn tại; khác eventId vẫn được ghi.
2. **Security:** User tenant A truy cập route tenant B bị chặn trước mọi query/write.
3. **Failure-path:** Giả lập 429, timeout sau successful write và 403; kết quả không được báo toàn bộ thành công.
4. **Load:** Tái hiện traffic skew giữa tenant lớn/nhỏ, đo RU, 429, p95 và throughput theo partition strategy.
5. **Database:** Kiểm chứng query chỉ trả đúng tenant/device, đúng thứ tự, đủ tối đa 100 item qua pagination.

## Quan sát trong production

Theo dõi Cosmos DB normalized RU consumption, 429 rate, request charge, partition-key distribution, latency và query metrics; Application Insights dependency spans, per-item ingestion outcomes, duplicate ratio và correlation ID. Cảnh báo khi throttling hoặc failed-item ratio vượt baseline; không ghi payload nhạy cảm vào logs.

## Kết quả code review tham khảo

### [Critical] — Credential nằm trong manifest

**Vấn đề:** Connection string chứa username/password plaintext.

**Tại sao xảy ra:** Secret được nhúng trực tiếp vào versioned deployment config.

**Ảnh hưởng production:** Lộ credential qua repo, artifact, logs hoặc quyền đọc Deployment; cần xem credential là đã bị phơi lộ trong tình huống thực tế.

**Cách sửa:** Rotate credential, chuyển sang workload identity/Managed Identity nếu driver và môi trường hỗ trợ; hoặc external secret provider/Key Vault integration. Kubernetes Secret riêng vẫn cần RBAC, encryption at rest và quản lý quyền.

### [High] — Liveness probe có thể kill app đang warm up

**Vấn đề:** Liveness bắt đầu sớm và dùng cùng endpoint với readiness.

**Tại sao xảy ra:** Startup có thể kéo dài 55 giây; probe timeout/failure threshold thấp làm container restart trước khi startup hoàn tất.

**Ảnh hưởng production:** CrashLoopBackOff, thiếu capacity, 5xx.

**Cách sửa:** Dùng startupProbe với failure budget phù hợp worst-case startup đã đo; chỉ bắt đầu liveness/readiness sau startup success. Liveness kiểm tra process health, không phụ thuộc transient SQL availability.

### [High] — Readiness không thể hiện khả năng phục vụ

**Vấn đề:** `/health` chưa rõ kiểm tra gì; readiness bắt đầu rất sớm.

**Tại sao xảy ra:** Endpoint có thể chỉ trả HTTP 200 dù dependencies hoặc warmup chưa hoàn thành.

**Ảnh hưởng production:** Service đưa request vào pod chưa sẵn sàng, gây 502/503 hoặc order failure.

**Cách sửa:** Tách `/health/live` và `/health/ready`; readiness kiểm tra trạng thái warmup và các dependency thiết yếu với timeout hợp lý, tránh quá tải dependency khi probe.

### [High] — Không khai báo rolling update availability budget

**Vấn đề:** Manifest dựa vào default strategy mà không diễn đạt SLO mong muốn.

**Tại sao xảy ra:** Với replicas thấp, mặc định có thể không đáp ứng availability objective khi pod warmup lâu.

**Ảnh hưởng production:** Giảm capacity trong rollout và khó dự đoán.

**Cách sửa:** Đặt `maxUnavailable: 0`, `maxSurge: 1` nếu cluster đủ capacity, `minReadySeconds`, `progressDeadlineSeconds`; theo dõi rollout và rollback khi SLO vi phạm.

### [High] — Mutable image tag

**Vấn đề:** Dùng `:latest` cho release.

**Tại sao xảy ra:** Tag có thể trỏ tới artifact khác ở các thời điểm, pull policy và cache có thể khiến pod chạy build không đồng nhất.

**Ảnh hưởng production:** Khó reproduce, audit và rollback.

**Cách sửa:** Pin immutable image digest hoặc unique build SHA, lưu release manifest và artifact provenance.

### [Medium] — Không có resource requests

**Vấn đề:** Chỉ khai báo limits.

**Tại sao xảy ra:** Scheduler không có request explicit để lập kế hoạch capacity theo nhu cầu đo được; defaulting tùy cấu hình cluster.

**Ảnh hưởng production:** Placement không phù hợp, throttling hoặc OOM khi memory thấp.

**Cách sửa:** Đặt requests dựa trên telemetry; điều chỉnh limits sau load test và xem CPU throttling/GC.

### [Medium] — Không xử lý graceful shutdown

**Vấn đề:** Không có chiến lược drain và termination window được xác nhận.

**Tại sao xảy ra:** In-flight order request có thể bị cắt khi pod terminate; readiness propagation và ingress behavior khác nhau.

**Ảnh hưởng production:** Timeout, retry, duplicate order nếu thiếu idempotency.

**Cách sửa:** ASP.NET Core shutdown cancellation, idempotent order API, terminationGracePeriodSeconds phù hợp và kiểm chứng drain thực tế; cân nhắc preStop nếu chứng minh cần thiết.

### [Medium] — Feature flag bật đồng loạt khi deploy

**Vấn đề:** `Features__NewCheckout=true` gắn trực tiếp với rollout image.

**Tại sao xảy ra:** Không tách release code và activation của chức năng.

**Ảnh hưởng production:** Regression ảnh hưởng toàn bộ traffic, rollback khó.

**Cách sửa:** Controlled rollout theo tenant/percentage nếu có hạ tầng hỗ trợ, default-safe config, kiểm chứng backward-compatible DB schema.

## Phiên bản đề xuất

Ví dụ manifest dưới đây dùng Secret đã được provision qua cơ chế bảo mật riêng; không đưa secret value vào repo. Endpoint health phải được triển khai đúng semantics trong ASP.NET Core.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  minReadySeconds: 10
  progressDeadlineSeconds: 300
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      terminationGracePeriodSeconds: 60
      containers:
        - name: api
          image: registry.example.com/orders-api@sha256:REPLACE_WITH_REAL_DIGEST
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__Orders
              valueFrom:
                secretKeyRef:
                  name: orders-api-credentials
                  key: connection-string
            - name: Features__NewCheckout
              value: "false"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 18
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: "150m"
              memory: 256Mi
            limits:
              cpu: "500m"
              memory: 512Mi
```

**Lưu ý:** Image digest là placeholder và phải được pipeline thay bằng digest thật; values resource/probe là điểm bắt đầu để kiểm chứng, không phải sizing đã xác nhận. Giữ Service từ manifest ban đầu. Secret phải tồn tại trước rollout; lựa chọn identity/external secret store cần đánh giá cụ thể theo cluster.

## Giải thích thiết kế sau khi sửa

StartupProbe bảo vệ quá trình khởi động dài; readiness quyết định pod có nhận traffic hay không; liveness chỉ phát hiện process thực sự không hồi phục. Immutable digest cho phép rollback đúng binary. Rolling update cố gắng giữ replica cũ khi replica mới chưa ready, với điều kiện cluster có đủ capacity và dependencies vẫn hoạt động.

## Trade-offs

- `maxUnavailable: 0` cải thiện availability nhưng cần capacity cho surge và có thể làm rollout bị treo khi cluster đầy.
- Readiness phụ thuộc database có thể ngắt toàn bộ traffic trong outage chung; nên kiểm tra dependency thiết yếu có kiểm soát và cân nhắc degraded mode.
- Secret store bên ngoài giảm credential sprawl nhưng thêm dependency, quyền truy cập và operational complexity.
- App Service có thể đơn giản hơn Kubernetes nếu không cần khả năng orchestration đặc thù; quyết định dựa trên SLO, skill đội ngũ, chi phí và môi trường.

## Cách kiểm thử

1. **Deployment validation:** `kubectl apply --dry-run=server` và policy scan không cho plaintext credentials/mutable tags vào production.
2. **Startup test:** Cố ý kéo dài warmup 60 giây, xác nhận không restart và không nhận traffic sớm.
3. **Failure injection:** SQL unavailable trong vài chục giây; quan sát readiness/liveness và recovery, không tạo restart storm.
4. **Rolling deployment:** Deploy phiên bản mới lỗi readiness, kiểm tra old replicas vẫn phục vụ và rollback được bằng digest cũ.
5. **Load/E2E:** Giữ in-flight order trong pod termination, xác nhận request semantics, idempotency và error budget.

## Quan sát trong production

Theo dõi `kubectl describe pod` events, restart count, probe failures, readiness transitions, rollout status, CPU throttling, OOMKilled, node pressure và ingress 502/503. Kết hợp Application Insights request/dependency p95, structured logs, trace correlation và deployment annotations (build SHA). Cảnh báo khi available replicas thấp hơn SLO hoặc rollout không tiến triển.

## Câu hỏi phỏng vấn mở rộng

1. Nếu mọi pod cùng mất SQL connectivity, readiness nên phản ứng thế nào để tránh outage kéo dài sau khi SQL hồi phục?
2. Khi database migration không backward-compatible, bạn tổ chức expand-migrate-contract và rollback thế nào?
3. Nếu cluster không đủ chỗ cho surge pod, bạn chọn thay đổi rollout policy hay scale cluster, dựa trên bằng chứng nào?

## Kiến thức trọng tâm

Cosmos DB cần thiết kế identity và partition key cùng với retry semantics, query pattern, authorization và RU observability. Kubernetes cần phân biệt startup/readiness/liveness, quản lý artifact bất biến, secrets, resource sizing và rollout an toàn. Cả hai bài yêu cầu đo lường trước khi thay đổi kiến trúc.

## Mẫu tư duy cần nhớ

1. Thiết kế retry cùng idempotency; mất response không có nghĩa write thất bại.
2. Kiểm tra tenant boundary ở cả authorization và data access.
3. Đo workload distribution trước khi quyết định partition strategy.
4. Phân biệt sống, đã khởi động và sẵn sàng phục vụ.
5. Release safety gồm artifact identity, rollback, telemetry và failure-path tests.
