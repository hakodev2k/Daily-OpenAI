# Code Review Challenge 1 — JWT authorization tin `tenantId` từ request và biến authenticated user thành cross-tenant reader

**Chủ đề:** C#/.NET, ASP.NET Core, JWT, policy-based authorization, multi-tenancy, EF Core, security, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một enterprise management portal dùng Microsoft Entra ID để authenticate users. Mỗi user thuộc một hoặc nhiều tenant; API lưu business data trong SQL Server và mọi `Invoice` có `TenantId`. Frontend gửi `tenantId` trong query string để user chuyển workspace.

Sau một penetration test, security team phát hiện một authenticated user có thể thay `tenantId` trong URL và đọc invoice metadata của tenant khác nếu đoán được GUID. Team cho rằng `[Authorize]` đã đủ vì JWT hợp lệ và endpoint chỉ trả dữ liệu read-only.

Business yêu cầu tenant isolation nghiêm ngặt. Một số support users có quyền cross-tenant nhưng quyền này phải explicit và auditable. Không được giả định claim names hoặc token issuer configuration cụ thể ngoài những gì cần xác minh từ authentication setup hiện tại.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/invoices")]
[Authorize]
public sealed class InvoicesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<InvoicesController> _logger;

    public InvoicesController(
        AppDbContext db,
        ILogger<InvoicesController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> GetInvoices(
        [FromQuery] Guid tenantId,
        [FromQuery] int page = 1,
        CancellationToken cancellationToken = default)
    {
        var userId = User.FindFirst("sub")?.Value;

        _logger.LogInformation(
            "User {UserId} requested invoices for tenant {TenantId}",
            userId,
            tenantId);

        var invoices = await _db.Invoices
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedUtc)
            .Skip((page - 1) * 50)
            .Take(50)
            .Select(x => new
            {
                x.Id,
                x.Number,
                x.CustomerName,
                x.Total,
                x.CreatedUtc
            })
            .ToListAsync(cancellationToken);

        return Ok(invoices);
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> GetInvoice(
        Guid id,
        CancellationToken cancellationToken)
    {
        var invoice = await _db.Invoices
            .AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

        return invoice is null ? NotFound() : Ok(invoice);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và authorization problems.
2. Xác định security, data-isolation, API và observability concerns.
3. Giải thích production impact dù attacker vẫn phải có JWT hợp lệ.
4. Ưu tiên findings theo severity.
5. Đề xuất authorization model và corrected implementation/design.
6. Giải thích security/integration tests cần có.
7. Nêu telemetry production cần thiết mà không log sensitive token/data.

## Câu hỏi gợi mở

1. Authentication chứng minh điều gì, và chưa chứng minh điều gì về quyền truy cập một tenant cụ thể?
2. `tenantId` từ query string thuộc trust boundary nào?
3. Endpoint theo `id` đang enforce tenant isolation ở đâu?
4. Support user cross-tenant nên được biểu diễn và audit thế nào?
5. Nếu authorization logic được copy thủ công vào hàng chục controllers, failure mode dài hạn là gì?

## Gợi ý

### Gợi ý 1

Primary risk là broken object/tenant-level authorization, không phải JWT validation syntax.

### Gợi ý 2

Một authenticated principal vẫn có thể yêu cầu resource không thuộc scope của mình. Hãy thiết kế resource/tenant authorization từ server-side trusted identity context thay vì coi client-supplied tenant identifier là quyền truy cập.

## Kết quả code review tham khảo

### Critical — Client-controlled `tenantId` được dùng làm authorization scope mà không kiểm tra membership

**Vấn đề:** endpoint list filter trực tiếp bằng `tenantId` từ request nhưng không chứng minh principal có quyền trên tenant đó.  
**Tại sao xảy ra:** `[Authorize]` chỉ yêu cầu authenticated principal theo configured authentication scheme; authorization tới business resource cần rule riêng.  
**Ảnh hưởng production:** authenticated user có thể đọc dữ liệu cross-tenant bằng cách thay identifier, phá tenant isolation và tạo data breach.  
**Cách sửa:** resolve allowed tenant scope từ trusted server-side authorization context/claims + authoritative membership source theo thiết kế hệ thống; enforce policy/resource authorization trước query. Client có thể chọn tenant, nhưng selection phải được validate against allowed scope.

### Critical — Endpoint theo invoice `id` không scope theo tenant/resource authorization

**Vấn đề:** `GetInvoice` query chỉ bằng `Id`.  
**Tại sao xảy ra:** object lookup và authorization bị tách rời, nhưng không có bước authorization sau lookup hoặc tenant-scoped query.  
**Ảnh hưởng production:** nếu GUID bị lộ/đoán/thu được qua log hoặc link, user authenticated có thể đọc invoice tenant khác.  
**Cách sửa:** query trong authorized tenant scope hoặc load resource rồi dùng resource-based authorization. Tránh trả entity trực tiếp.

### High — Authentication claim được đọc trực tiếp nhưng semantics chưa được xác minh

**Vấn đề:** code hard-code `"sub"` như application user identity.  
**Tại sao xảy ra:** claim mapping/issuer/token type có thể khác theo authentication configuration.  
**Ảnh hưởng production:** audit attribution có thể thiếu hoặc sai nếu assumption không khớp token configuration.  
**Cách sửa:** định nghĩa một current-user abstraction dựa trên validated authentication configuration; xác minh issuer/audience/claim semantics và fail closed khi identity cần thiết không có.

### High — Support cross-tenant access chưa có explicit privileged policy

**Vấn đề:** requirement support user có quyền đặc biệt nhưng endpoint không phân biệt normal membership và privileged access.  
**Tại sao xảy ra:** authorization chỉ ở mức authenticated/not-authenticated.  
**Ảnh hưởng production:** team dễ mở rộng bằng bypass ad-hoc, khó audit và dễ privilege creep.  
**Cách sửa:** policy/resource handler explicit cho support capability, least privilege, audit reason/context nếu business yêu cầu, và tests riêng cho privileged path.

### High — Trả EF entity trực tiếp ở detail endpoint

**Vấn đề:** `Ok(invoice)` expose persistence entity shape.  
**Tại sao xảy ra:** API contract phụ thuộc trực tiếp database entity.  
**Ảnh hưởng production:** có thể vô tình lộ fields mới/sensitive khi entity thay đổi; coupling API-storage tăng.  
**Cách sửa:** projection sang explicit response DTO chỉ gồm fields được phép công khai.

### Medium — Pagination validation thiếu

**Vấn đề:** `page <= 0` làm `Skip` nhận offset không hợp lệ/không có semantics API rõ ràng; page size hard-coded không có response metadata.  
**Tại sao xảy ra:** input contract chưa validate.  
**Ảnh hưởng production:** error behavior không nhất quán và UX pagination khó quản lý.  
**Cách sửa:** validate page, định nghĩa bounded page size/cursor strategy phù hợp workload và response metadata cần thiết.

### Medium — Offset pagination có thể xuống cấp ở dataset lớn

**Vấn đề:** `Skip` ngày càng lớn khi page sâu.  
**Tại sao xảy ra:** offset pagination yêu cầu database đi qua preceding rows tùy plan/index.  
**Ảnh hưởng production:** deep pages có thể tăng latency/read cost.  
**Cách sửa:** đo execution plan và workload; nếu deep navigation thực sự cần, cân nhắc keyset pagination trên stable ordering key + tie-breaker. Không đổi chỉ vì lý thuyết nếu dataset nhỏ.

### Medium — Audit log chưa đủ để chứng minh authorization decision

**Vấn đề:** log request user/tenant nhưng không ghi policy outcome/access mode/correlation context.  
**Tại sao xảy ra:** telemetry mô tả intent của client, không mô tả server authorization decision.  
**Ảnh hưởng production:** incident investigation khó phân biệt normal tenant access và privileged support access.  
**Cách sửa:** structured security audit event với stable actor ID, tenant/resource ID, authorization mode/policy outcome, correlation ID; không log JWT hoặc unnecessary invoice data.

### Low — List query thiếu `AsNoTracking()` cho read-only projection

**Vấn đề:** query read-only không cần entity tracking; với projection tracking impact có thể đã thấp tùy shape, nên đây không phải primary issue.  
**Tại sao xảy ra:** read model intent chưa explicit.  
**Ảnh hưởng production:** nhỏ so với authorization flaws.  
**Cách sửa:** dùng read-only query conventions phù hợp và đo trước khi coi đây là performance fix.

## Phiên bản đề xuất

Ví dụ dưới đây dùng một abstraction `ITenantAccessService` để minh họa server-side authorization. Implementation thực tế phải dựa trên token/membership model đã được xác minh; không giả định một claim cụ thể là đủ.

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/invoices")]
[Authorize]
public sealed class InvoicesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<InvoicesController> _logger;

    public InvoicesController(
        AppDbContext db,
        ITenantAccessService tenantAccess,
        ILogger<InvoicesController> logger)
    {
        _db = db;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<InvoiceSummaryResponse>>> GetInvoices(
        Guid tenantId,
        [FromQuery] int page = 1,
        CancellationToken cancellationToken = default)
    {
        if (page < 1)
            return ValidationProblem("page must be greater than or equal to 1.");

        var access = await _tenantAccess.AuthorizeAsync(
            User,
            tenantId,
            TenantPermission.ReadInvoices,
            cancellationToken);

        if (!access.Succeeded)
            return Forbid();

        var invoices = await _db.Invoices
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedUtc)
            .ThenByDescending(x => x.Id)
            .Skip((page - 1) * 50)
            .Take(50)
            .Select(x => new InvoiceSummaryResponse(
                x.Id,
                x.Number,
                x.CustomerName,
                x.Total,
                x.CreatedUtc))
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Invoice list authorized for tenant {TenantId}; access mode {AccessMode}",
            tenantId,
            access.Mode);

        return Ok(invoices);
    }

    [HttpGet("{id:guid}")]
    public async Task<ActionResult<InvoiceDetailResponse>> GetInvoice(
        Guid tenantId,
        Guid id,
        CancellationToken cancellationToken)
    {
        var access = await _tenantAccess.AuthorizeAsync(
            User,
            tenantId,
            TenantPermission.ReadInvoices,
            cancellationToken);

        if (!access.Succeeded)
            return Forbid();

        var invoice = await _db.Invoices
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Id == id)
            .Select(x => new InvoiceDetailResponse(
                x.Id,
                x.Number,
                x.CustomerName,
                x.Total,
                x.CreatedUtc))
            .SingleOrDefaultAsync(cancellationToken);

        return invoice is null ? NotFound() : Ok(invoice);
    }
}
```

## Giải thích thiết kế sau khi sửa

Authentication và business authorization được tách rõ. `tenantId` vẫn có thể đến từ route để biểu diễn resource hierarchy, nhưng server xác minh principal có `ReadInvoices` trên tenant trước khi đọc data. Detail query đồng thời scope `TenantId + Id`, giảm nguy cơ object lookup vượt tenant boundary.

`ITenantAccessService` không có nghĩa phải tạo một remote authorization microservice. Trong một Modular Monolith hoặc simple application, nó có thể chỉ là application service/authorization handler đọc trusted membership store. Complexity phải tương xứng hệ thống.

Support access cần một explicit mode/policy để audit. Nếu policy yêu cầu justification hoặc approval, đó là business/security requirement cần làm rõ, không tự invent.

## Trade-offs

Centralized tenant authorization thêm dependency và có thể thêm database/cache lookup. Cache membership có thể giảm latency nhưng tạo revocation/staleness trade-off, vì vậy không nên thêm Redis mặc định. Resource-based authorization sau khi load entity có thể linh hoạt hơn nhưng phải tránh data exposure trước authorization và cần consistent pattern toàn codebase.

## Cách kiểm thử

1. **Security integration test:** user thuộc tenant A gọi list/detail của tenant B phải bị deny, kể cả khi biết invoice ID.
2. **Authorization test:** normal user tenant A được phép tenant A; support principal chỉ được cross-tenant khi explicit privileged policy thỏa mãn.
3. **Negative token/identity test:** thiếu required identity/membership information phải fail closed.
4. **API test:** response DTO không expose internal/sensitive entity fields khi schema thay đổi.
5. **Database/performance test:** tenant-scoped query dùng representative indexes/data volume; đo deep pagination trước khi chọn keyset migration.

## Quan sát trong production

Theo dõi authorization deny rate theo endpoint/tenant (không log token), privileged support access events, correlation ID, actor identity đã chuẩn hóa, request p95/p99 và database dependency duration. Alert với unusual cross-tenant denial spikes hoặc privileged access pattern bất thường theo security policy. Audit logs phải có retention/access control phù hợp vì chính chúng cũng là sensitive security data.

## Câu hỏi phỏng vấn mở rộng

1. Nếu user membership thay đổi giữa lúc JWT còn hạn, bạn thiết kế revocation/freshness trade-off thế nào?
2. Khi nào resource-based authorization handler tốt hơn tenant filter ở query layer?
3. Global query filter cho `TenantId` có đủ để coi tenant isolation đã được giải quyết không? Vì sao?

# Code Review Challenge 2 — Kubernetes Deployment chứa secret trong ConfigMap và rollout làm pod nhận traffic trước khi application sẵn sàng

**Chủ đề:** Kubernetes, deployment safety, ConfigMap/Secret, probes, resource management, ASP.NET Core hosting  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core product API được chuyển từ Azure App Service sang Kubernetes. Manifest dưới đây deploy thành công ở staging. Production có ba replicas. Sau một rollout, users thấy 503 trong khoảng 20–30 giây; một pod đôi khi restart khi traffic tăng. Security review phát hiện database credential xuất hiện trong deployment repository.

Application cần khoảng 15 giây để warm local metadata/cache trước khi có thể phục vụ request đúng. `/health/live` chỉ kiểm tra process; `/health/ready` kiểm tra trạng thái application readiness đã được team implement. Workload memory thường 250–400 MiB nhưng có spike cao hơn khi xử lý large responses. Team chưa có evidence rằng Kubernetes là nguyên nhân duy nhất của restart; ứng viên phải phân biệt configuration risks với hypothesis cần telemetry xác minh.

## Kết quả code review tham khảo

### Critical — Production database credential được commit trong ConfigMap

**Vấn đề:** connection string chứa username/password plaintext trong repository và ConfigMap.  
**Tại sao xảy ra:** non-secret configuration và credential bị trộn chung. ConfigMap không phải secret boundary.  
**Ảnh hưởng production:** credential có thể lộ qua Git history, repository access, manifests và cluster read permissions.  
**Cách sửa:** rotate exposed credential; đưa secret ra khỏi repository. Dùng Kubernetes Secret hoặc external secret/identity mechanism phù hợp platform. Nếu Azure workload hỗ trợ passwordless identity là option, đánh giá Managed Identity/workload identity theo environment thay vì hard-code như universal solution.

### High — Readiness probe dùng liveness endpoint

**Vấn đề:** pod được coi ready khi process sống dù application cần 15 giây warmup.  
**Tại sao xảy ra:** `/health/live` không biểu diễn service readiness.  
**Ảnh hưởng production:** Service có thể route traffic vào pod chưa sẵn sàng, tạo 503/error trong rollout.  
**Cách sửa:** readiness dùng `/health/ready` với thresholds/timing dựa trên measured startup behavior.

### High — Liveness probe dùng readiness endpoint

**Vấn đề:** temporary not-ready state có thể bị coi là process failure.  
**Tại sao xảy ra:** liveness phụ thuộc application readiness/dependencies.  
**Ảnh hưởng production:** pod có thể restart khi dependency/warmup tạm thời fail, tạo restart loop/cascading capacity loss.  
**Cách sửa:** liveness dùng `/health/live`; nếu startup hợp lệ nhưng chậm, cân nhắc `startupProbe` để bảo vệ startup window trước liveness evaluation.

### High — Memory limit thấp hơn workload bình thường được mô tả

**Vấn đề:** limit `256Mi` trong khi scenario cho biết workload thường có thể tới 400 MiB và spike cao hơn.  
**Tại sao xảy ra:** resource configuration không grounded bằng measured working set/load profile.  
**Ảnh hưởng production:** có khả năng container bị OOM kill khi vượt cgroup memory limit; tuy nhiên phải xác minh pod termination reason trước khi kết luận đây là root cause observed restart.  
**Cách sửa:** thu memory working set, peak, GC/container metrics và pod status; set requests/limits theo capacity testing và node economics. Đồng thời giảm avoidable allocation nếu application có issue.

### High — Mutable `latest` image làm rollout/rollback không reproducible

**Vấn đề:** manifest không pin immutable version/digest.  
**Tại sao xảy ra:** cùng tag có thể trỏ tới artifact khác theo thời gian.  
**Ảnh hưởng production:** khó chứng minh artifact nào đang chạy và rollback chính xác; cache/pull behavior có thể gây fleet không đồng nhất tùy policy/state.  
**Cách sửa:** deploy immutable version tag và tốt hơn pin digest trong release pipeline khi phù hợp; record artifact provenance.

### Medium — Không có startup probe dù application có warmup phase đáng kể

**Vấn đề:** liveness bắt đầu sớm và hiện lại trỏ nhầm readiness.  
**Tại sao xảy ra:** startup lifecycle chưa được model riêng.  
**Ảnh hưởng production:** legitimate startup có thể bị restart nếu thresholds không đủ.  
**Cách sửa:** dùng `startupProbe` khi startup cần window riêng; configure từ measured startup p95/p99, không copy magic numbers.

### Medium — Resource requests không phản ánh workload đã biết

**Vấn đề:** memory request 128Mi thấp đáng kể so với normal usage mô tả. CPU request/limit cũng chưa có evidence.  
**Tại sao xảy ra:** values có vẻ được chọn tùy ý.  
**Ảnh hưởng production:** scheduling/capacity planning không phản ánh thực tế; CPU limit có thể tạo throttling nếu workload cần burst, nhưng phải đo.  
**Cách sửa:** derive requests/limits từ profiling/load tests và production metrics; monitor CPU throttling, memory working set và OOM events.

### Medium — Rollout strategy không explicit theo service SLO

**Vấn đề:** Deployment dùng defaults mà không chứng minh chúng phù hợp capacity/error budget.  
**Tại sao xảy ra:** deployment availability chưa được thiết kế như một requirement.  
**Ảnh hưởng production:** kết hợp readiness sai với rolling update có thể giảm effective healthy capacity.  
**Cách sửa:** sau khi probes đúng, chọn `maxUnavailable`/`maxSurge` theo capacity/SLO; không coi `maxUnavailable: 0` là guarantee zero errors.

### Medium — Secret access scope chưa thể hiện least privilege

**Vấn đề:** manifest đơn giản không cho thấy secret source/RBAC/service account boundary.  
**Tại sao xảy ra:** credential lifecycle chưa được thiết kế.  
**Ảnh hưởng production:** secret có thể được đọc rộng hơn cần thiết.  
**Cách sửa:** giới hạn service account/RBAC và secret access theo platform; rotate/audit access. Chi tiết phụ thuộc cluster security model.

### Low — Thiếu deployment metadata hỗ trợ observability

**Vấn đề:** pod không có version/revision labels hữu ích ngoài `app`.  
**Tại sao xảy ra:** artifact identity không được đưa vào telemetry/deployment metadata.  
**Ảnh hưởng production:** khó correlate 503/restart với release version.  
**Cách sửa:** thêm immutable version labels/annotations và expose version trong application telemetry nếu phù hợp.

## Phiên bản đề xuất

Manifest dưới đây minh họa separation giữa non-secret config và Secret reference. Secret value không được đặt trong file này; cách provision Secret phải phù hợp platform và security process.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: product-api-config
data:
  ASPNETCORE_ENVIRONMENT: Production
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: product-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: product-api
  template:
    metadata:
      labels:
        app: product-api
        version: "2026.09.17.1"
    spec:
      containers:
        - name: product-api
          image: registry.example/product-api@sha256:RELEASE_DIGEST
          ports:
            - containerPort: 8080
          envFrom:
            - configMapRef:
                name: product-api-config
          env:
            - name: ConnectionStrings__Main
              valueFrom:
                secretKeyRef:
                  name: product-api-secrets
                  key: main-connection-string
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            failureThreshold: 6
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            failureThreshold: 3
          resources:
            requests:
              cpu: "250m"
              memory: "384Mi"
            limits:
              cpu: "1"
              memory: "768Mi"
---
apiVersion: v1
kind: Service
metadata:
  name: product-api
spec:
  selector:
    app: product-api
  ports:
    - port: 80
      targetPort: 8080
```

Các resource/probe values trong ví dụ là candidate values để minh họa cấu trúc, không phải production recommendation. Chúng phải được thay bằng số liệu từ startup/load profiling và cluster capacity.

## Giải thích thiết kế sau khi sửa

Probe semantics được tách theo lifecycle: startup cho phép application có startup window; readiness điều khiển traffic admission; liveness chỉ phản ánh trạng thái cần restart. Secret không còn nằm trong ConfigMap/repository. Image được pin bằng digest để release reproducible.

`maxUnavailable: 0` giúp giữ desired ready capacity trong một số rollout scenarios nhưng không đảm bảo zero-error deployment; ingress propagation, graceful termination, long-lived connections và application correctness vẫn cần kiểm tra. Resource values phải dựa trên telemetry thay vì copy từ manifest mẫu.

## Trade-offs

Memory limit cao hơn giảm OOM risk nhưng tăng reserved/allocatable capacity pressure và có thể giảm pod density. Startup/readiness thresholds quá rộng làm rollout phát hiện lỗi chậm; quá hẹp gây false failure. External secret manager/passwordless identity cải thiện credential lifecycle nhưng thêm platform integration complexity; Kubernetes Secret đơn thuần vẫn cần RBAC, encryption-at-rest/cluster controls và rotation process phù hợp.

## Cách kiểm thử

1. **Deployment validation:** deploy pod cold-start 15+ giây; verify Service không route traffic trước readiness success.
2. **Failure-path test:** readiness dependency tạm fail nhưng process healthy; verify pod removed khỏi traffic mà không bị liveness restart vô ích.
3. **Load test:** representative large responses; record container memory/GC/CPU throttling và verify configured limits có headroom phù hợp.
4. **Security validation:** repository/manifests không chứa credential; service account chỉ đọc secret cần thiết theo cluster policy.
5. **Rollout E2E:** continuous traffic qua rolling update; correlate 5xx với pod version/lifecycle và verify rollback tới exact artifact digest.

## Quan sát trong production

Theo dõi pod restart count và `lastState/termination reason`, OOMKilled events, memory working set, CPU throttling, readiness transitions, startup duration, per-revision 5xx/p95/p99 và ingress/service telemetry. Application Insights hoặc OpenTelemetry traces nên mang pod/revision identity để nối user error với lifecycle event. Kubernetes events cần được giữ/ship đủ lâu để incident investigation không mất evidence.

## Câu hỏi phỏng vấn mở rộng

1. Nếu readiness check phụ thuộc trực tiếp database và database outage xảy ra, toàn bộ fleet có thể phản ứng thế nào?
2. Khi nào không nên đặt CPU limit cho một latency-sensitive .NET API, và cần evidence gì để quyết định?
3. Nếu cluster chạy trên Azure, Managed Identity/workload identity có thể thay password connection string trong những điều kiện nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge hôm nay tập trung vào hai boundary thường bị đánh đồng với “đã cấu hình là an toàn”: authenticated không đồng nghĩa authorized tới mọi resource, và container `Running`/manifest apply thành công không đồng nghĩa application sẵn sàng phục vụ traffic. Tenant isolation phải được enforce server-side theo trusted authorization context; Kubernetes lifecycle phải phân biệt startup, readiness và liveness. Secret/artifact identity cũng là một phần của release correctness chứ không chỉ DevOps hygiene.

## Mẫu tư duy cần nhớ

- Authentication xác định principal; authorization phải kiểm tra quyền trên resource cụ thể.
- Không dùng client-supplied identifier như bằng chứng authorization.
- Tách process health khỏi traffic readiness và startup lifecycle.
- Không kết luận OOM/restart root cause nếu chưa xem termination reason và resource telemetry.
- Secret handling và immutable artifact identity là một phần của production design và incident traceability.
