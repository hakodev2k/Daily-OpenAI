# Câu 1 — Singleton giữ scoped service: vì sao lỗi chỉ xuất hiện sau khi chạy production?

**Loại câu hỏi:** Internal mechanism + practical runtime behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core dependency injection, service lifetime, EF Core DbContext, thread safety, configuration validation

## Bối cảnh

Một ASP.NET Core .NET 8 API dùng EF Core và một bộ xử lý cập nhật giá. `PriceRefreshCoordinator` được đăng ký `AddSingleton`; constructor nhận `IProductRepository` được đăng ký `AddScoped`, bên trong sử dụng `AppDbContext` scoped. Coordinator được cả API và một `BackgroundService` gọi. Staging chạy một instance, ít request nên chưa có lỗi rõ ràng; sau scale-out, log xuất hiện `InvalidOperationException` liên quan đến sử dụng `DbContext` đồng thời và đôi lúc dữ liệu đọc không đúng trạng thái mong đợi. Một số môi trường khởi động thất bại khi bật validation DI.

## Câu hỏi chính

Giải thích chính xác cách container tạo và giữ object graph, vì sao cấu hình lifetime này có thể lỗi lúc startup hoặc runtime, và cách sửa bảo toàn transaction boundary và khả năng xử lý song song.

## Câu hỏi làm rõ nên cân nhắc

1. Coordinator được resolve từ root provider hay scope nào; `ValidateScopes` có bật không?
2. BackgroundService chạy bao nhiêu operation đồng thời và có dùng cùng repository instance?
3. Repository có giữ state mutable hay transaction giữa các lần gọi không?
4. Mỗi operation có cần một transaction/DbContext độc lập không?
5. Triệu chứng xuất hiện trong cùng process hay chỉ sau scale-out nhiều process?

## Gợi ý tư duy

### Gợi ý 1
Xem lifetime của dependency ngắn hơn lifetime của object đang giữ nó.

### Gợi ý 2
Phân biệt scoped resolution từ root với tạo scope cho từng logical operation; `DbContext` không hỗ trợ truy cập đồng thời trên cùng instance.

### Gợi ý 3
Kiểm tra `IServiceScopeFactory`, `IDbContextFactory<T>`, scope ownership và DI validation trong integration tests.

## Cấu trúc trả lời đề xuất

1. Làm rõ graph và nơi resolve.
2. Diễn giải lifetime, root scope và disposal.
3. Phân biệt lỗi validation, race và vấn đề đa instance.
4. Đề xuất ownership của scope theo operation.
5. Kiểm chứng concurrency, transaction và cancellation.
6. Xác định telemetry và release gate.

## Ý chính của câu trả lời tốt

### Bắt buộc
Nhận diện captive dependency; singleton có thể giữ scoped object quá lâu nếu scope validation không chặn; `DbContext` không thread-safe; không dùng cùng context cho các operation song song.

### Điểm cộng
Tách coordinator singleton stateless khỏi worker scoped; dùng `IServiceScopeFactory.CreateAsyncScope()` cho từng operation; giữ transaction và repository cùng scope; bật `ValidateScopes` và `ValidateOnBuild` phù hợp.

### Senior+
Không nhầm lỗi đa instance với shared in-memory `DbContext` (mỗi process có container riêng); xem xét distributed coordination riêng nếu job không được chạy trùng trên nhiều instance.

## Hướng giải quyết tham khảo

**Cơ chế:** Với Microsoft DI, singleton thường được tạo một lần trên root container và giữ reference đến các dependency constructor. Scoped service được thiết kế cho một scope, thường là HTTP request. Nếu scoped dependency được resolve từ root khi validation tắt, nó có thể bị giữ đến khi root provider dispose, biến thành một captive dependency. Nếu validation bật, container có thể từ chối resolve graph singleton → scoped; thời điểm lỗi phụ thuộc cách service được đăng ký và resolve. Một `DbContext` được dùng song song có thể ném exception hoặc dẫn đến hành vi không được hỗ trợ; không giả định tất cả concurrency bugs đều được runtime phát hiện.

**Phân tích bằng chứng:** Xem startup logs và environment flags; ghi scope/operation correlation, DbContext identity trong môi trường thử nghiệm (không log dữ liệu nhạy cảm), trace request/background operation, so sánh số concurrent operations. Tái hiện với `Task.WhenAll` trên cùng coordinator, rồi với scope riêng. Phân biệt dữ liệu stale do tracking với transaction isolation hoặc cache; không quy mọi sai lệch dữ liệu cho DI.

**Thiết kế:** Giữ singleton coordinator chỉ chứa stateless orchestration và `IServiceScopeFactory`. Mỗi operation tạo `await using var scope = scopeFactory.CreateAsyncScope();`, resolve scoped `IPriceRefreshHandler`, `await handler.RunAsync(id, cancellationToken)`. Handler và repository cùng scope; DbContext sống đến hết operation. Với công việc đơn giản, có thể đăng ký coordinator scoped và resolve nó trong request scope; BackgroundService vẫn phải tạo scope cho từng iteration. `IDbContextFactory<AppDbContext>` là lựa chọn khi cần tạo context độc lập ngoài request scope; phải dispose context và giữ transaction ownership rõ ràng. Không inject trực tiếp scoped handler vào singleton hosted service.

**Scale-out:** Scope riêng chỉ giải quyết chia sẻ object trong process. Nếu nhiều App Service instances cùng kích hoạt job, cần cơ chế single scheduler, claim/lease trong durable store hoặc idempotent operation với unique constraint và concurrency control. Không dùng `lock` trong process làm distributed lock. Kiểm tra cancellation khi shutdown và rollback khi operation lỗi.

**Validation:** Bật scope/build validation trong môi trường kiểm thử, integration test resolve graph, concurrency test với nhiều operation, fault injection khi database timeout, kiểm tra mỗi operation tạo và dispose scope, đo DbContext-related errors, duration, retry count, duplicate business effects. Tránh log connection string.

## Mẫu trả lời trong phỏng vấn

“Tôi kiểm tra DI graph trước vì singleton đang giữ scoped repository. Nếu resolve từ root và scope validation không chặn, repository và DbContext có thể tồn tại quá lâu, bị nhiều operation dùng chung; DbContext không hỗ trợ concurrent use. Tôi sẽ xác minh bằng DI validation và một concurrency test, đồng thời tách các giả thuyết như stale tracking hoặc job chạy trùng. Cách sửa là để coordinator singleton chỉ orchestration, tạo async scope riêng cho mỗi logical operation rồi resolve handler scoped. Transaction và context nằm trong scope đó. Nếu hệ thống chạy nhiều instance, đây là bài toán khác: cần durable claim/idempotency để tránh duplicate effects. Tôi sẽ triển khai kèm test và metrics trước khi rollout.”

## Câu hỏi đào sâu

1. Nếu dùng `IDbContextFactory` thay vì `IServiceScopeFactory`, ai sở hữu transaction và disposal?
2. Nếu API và worker cùng cập nhật một product, scope riêng có ngăn lost update không?
3. Nếu chỉ có một request tại một thời điểm, bạn có cần thay đổi kiến trúc hay chỉ bật validation?

## Lỗi trả lời thường gặp

- Cho rằng scoped đồng nghĩa với một instance cho toàn ứng dụng.
- Sửa bằng cách chuyển `DbContext` thành singleton.
- Cho rằng `lock` cục bộ xử lý duplicate execution trên nhiều instance.
- Không phân biệt concurrency trong process và optimistic concurrency ở database.
- Quên dispose scope và propagation của `CancellationToken`.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ graph và workload | 1 |
| Giải thích lifetime và container validation | 2 |
| Phân tích concurrency, state, transaction | 2 |
| Thiết kế scope ownership đúng | 2 |
| Phân biệt scale-out và trade-offs | 1.5 |
| Tests, telemetry và trình bày | 1.5 |

# Câu 2 — Cosmos DB RU tăng đột biến nhưng CPU ứng dụng vẫn bình thường

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU, HTTP 429, indexing, Application Insights, incident response

## Bối cảnh

Một hệ thống lưu activity feed của 120.000 người dùng trong Azure Cosmos DB for NoSQL. Sau khi ra mắt tính năng dashboard quản trị “hoạt động gần nhất”, p95 tăng từ 300 ms lên 4 giây, một số request bị HTTP 429 từ dependency và chi phí RU tăng. CPU API bình thường. Dashboard truy vấn toàn tenant theo thời gian, còn truy vấn mobile thường đọc feed theo user. Container hiện partition theo `/userId`; chưa rõ indexing policy, throughput mode, query shapes hoặc mức phân phối traffic. Team đề xuất tăng RU ngay và chuyển toàn bộ dữ liệu sang SQL Server.

## Câu hỏi chính

Bạn xử lý incident từ ổn định dịch vụ đến xác định root cause và quyết định mô hình truy vấn/lưu trữ thế nào, không làm mất dữ liệu và không suy diễn chỉ từ HTTP 429?

## Câu hỏi làm rõ nên cân nhắc

1. 429 tập trung vào logical/physical partitions nào, hay phân bố toàn container?
2. Query mới có partition key filter không; `ORDER BY`, `TOP`, pagination và continuation token thế nào?
3. RU charge, request rate, latency và retry-after theo từng query là bao nhiêu?
4. Throughput provisioned/autoscale hay serverless; workload giờ cao điểm và retention?
5. Dashboard cần near-real-time, exact global order hay chấp nhận vài phút trễ?

## Gợi ý tư duy

### Gợi ý 1
CPU API thấp không loại trừ bottleneck tại dependency.

### Gợi ý 2
Partition key tối ưu cho truy vấn theo user có thể không phù hợp cho truy vấn toàn tenant.

### Gợi ý 3
So sánh query diagnostics, RU/request, partition-level throttling, index utilization và tác động của retry.

## Cấu trúc trả lời đề xuất

1. Định lượng impact và cô lập dashboard.
2. Thu request diagnostics, metrics và traces.
3. Đưa ra ít nhất ba giả thuyết.
4. Kiểm chứng query/index/partition.
5. Stabilize có kiểm soát.
6. Chọn mô hình read path.
7. Kế hoạch rollout, backfill, rollback.
8. Đo kết quả và ngăn tái diễn.

## Ý chính của câu trả lời tốt

### Bắt buộc
Phân biệt 429 do throughput/partition pressure với application CPU; kiểm tra cross-partition fan-out, query RU và retry behavior; không mặc định thêm RU hay đổi database.

### Điểm cộng
Throttling dashboard, pagination/continuation token, query/index tuning, separate read model, change feed, cache theo SLA và retry có jitter.

### Senior+
Đánh giá chi phí write amplification, eventual consistency, backfill correctness, partition skew, security isolation và dual-read migration.

## Hướng giải quyết tham khảo

**Impact/stabilize:** Tách traffic mobile và dashboard bằng telemetry; nếu dashboard là nguồn tăng tải, feature flag giảm tần suất refresh, giới hạn concurrent dashboard queries, giảm time range hoặc tạm tắt tính năng quản trị theo thỏa thuận với Product. Ưu tiên mobile core flows. Không retry vô hạn: SDK thường xử lý một số 429 theo retry policy; kiểm tra tổng latency và retry diagnostics trước khi thêm application retry. Có thể điều chỉnh throughput tạm thời nếu metrics xác nhận thiếu capacity và chi phí được chấp thuận, nhưng đó chưa phải root-cause fix.

**Giả thuyết:** (A) dashboard query thiếu partition key nên quét nhiều partitions, tiêu thụ RU lớn; (B) `ORDER BY`/filter không có indexing phù hợp; (C) hot partition do traffic tập trung vào nhóm user; (D) autoscale/throughput không đáp ứng burst; (E) UI polling hoặc retry nhân số request. Thu query text đã loại dữ liệu nhạy cảm, diagnostics `RequestCharge`, status/substatus, 429 counts, partition metrics, query plan/index metrics nếu có, Application Insights dependency traces và frontend request waterfall. Đối chiếu thời điểm rollout, p95, RU/s và number of queries.

**Quyết định:** Giữ `/userId` cho mobile nếu đó là truy vấn cốt lõi và partition distribution hợp lý. Đối với dashboard cần global recency, xem xét projection/read model riêng theo tenant/time bucket, cập nhật bằng change feed processor hoặc pipeline đáng tin cậy. Thiết kế partition key mới dựa trên truy vấn và tránh một tenant hot; dùng continuation tokens, giới hạn time range, tối ưu composite indexes theo filter + sort thực tế. Nếu dashboard ít sử dụng và latency chấp nhận được, scheduled aggregation sang SQL/reporting store có thể đơn giản hơn một Cosmos container thứ hai. Không khẳng định change feed tạo exactly-once projection; consumer phải idempotent, có checkpoint và replay/backfill. Nếu yêu cầu thứ tự toàn cục mạnh và tức thời, cần làm rõ consistency/transaction limits và cân nhắc database phù hợp thay vì hứa eventual projection đáp ứng.

**Rollout:** Xây read model song song, backfill theo watermark và kiểm tra missing/duplicate records, đối chiếu số lượng và recency, shadow read dashboard, canary, feature flag chuyển traffic, giữ đường rollback. Phân quyền tenant-scoped, giới hạn truy vấn quản trị và kiểm tra PII. Theo dõi RU per operation, throttled requests, SDK retry duration, p95/p99, partition skew, change feed lag, dashboard freshness và cost.

## Mẫu trả lời trong phỏng vấn

“Tôi không kết luận CPU bình thường nghĩa là hệ thống khỏe, vì 429 từ Cosmos có thể tạo latency qua retry. Tôi xác định tác động mobile và dashboard, tạm giảm dashboard polling để bảo vệ core flow, rồi xem RU charge và diagnostics theo query, partition và thời điểm rollout. Partition `/userId` có thể rất tốt cho feed từng người nhưng đắt cho global dashboard. Nếu cross-partition query là nguyên nhân, tôi tối ưu truy vấn và index trước; với dashboard truy cập thường xuyên, cân nhắc read model riêng cập nhật bất đồng bộ, có backfill và idempotency. Tôi đánh giá freshness requirement, chi phí write amplification và rollback trước khi quyết định, không tự động tăng RU hay chuyển toàn bộ database.”

## Câu hỏi đào sâu

1. Nếu 429 chỉ tập trung ở một physical partition dù tổng RU/s còn dư, bạn thay đổi chẩn đoán ra sao?
2. Nếu Product yêu cầu dashboard chính xác trong vòng một giây và không chấp nhận dữ liệu trễ, bạn còn chọn change feed projection không?
3. Nếu chuyển sang SQL reporting store, bạn kiểm tra backfill và tính đúng đắn khi có delete/update như thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất 429 với downtime hoàn toàn.
- Tăng throughput mà không đo query RU và partition skew.
- Chuyển partition key của container hiện tại như một thao tác config đơn giản.
- Xem cross-partition query luôn sai hoặc luôn phải tránh.
- Quên frontend polling và retry amplification.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|

| Evidence, metrics và competing hypotheses | 2 |
| Cosmos partition/query reasoning | 2 |
| Remediation và kiến trúc có điều kiện | 2 |

| Testing và monitoring | 1 |

# Câu 3 — Có nên di chuyển cổng phê duyệt từ IIS/.NET Framework sang App Service?

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** .NET Framework modernization, IIS, Windows Server, ASP.NET Core, Azure App Service, SQL Server, authentication, CI/CD, release safety

## Bối cảnh

Một cổng phê duyệt nội bộ chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server, SQL Server. Có 18.000 nhân viên, khoảng 1.500 người dùng đồng thời vào giờ cao điểm. Hệ thống tích hợp Windows Authentication trong intranet, một thư viện PDF chỉ hỗ trợ Windows, file upload lưu trên ổ đĩa server và batch job chạy bằng Windows Task Scheduler. Team muốn hiện đại hóa để giảm rủi ro bảo trì và deploy an toàn hơn; Product không chấp nhận gián đoạn quá 15 phút, cần giữ API contract cho ứng dụng mobile cũ. Có đề xuất rewrite toàn bộ sang .NET 10 + Kubernetes + Microservices trong một quý.

## Câu hỏi chính

Hãy đề xuất roadmap modernization có các quyết định kiến trúc, hosting và migration boundaries cụ thể; so sánh incremental modernization với rewrite, giải thích cách rollout và rollback mà không mất dữ liệu hay phá vỡ authentication.

## Câu hỏi làm rõ nên cân nhắc

1. Những dependency nào phụ thuộc `System.Web`, COM, GAC, Windows APIs hoặc 32-bit?
2. Windows Authentication có bắt buộc giữ nguyên trải nghiệm intranet hay được phép chuyển sang Microsoft Entra ID?
3. PDF library có thể thay thế, cô lập thành Windows service hay cần giữ nguyên?
4. Database schema, shared transactions và mobile API compatibility bị ràng buộc thế nào?
5. RPO/RTO, ngân sách cloud, compliance và khả năng chạy song song là gì?

## Gợi ý tư duy

### Gợi ý 1
Tách mục tiêu kinh doanh khỏi lựa chọn framework/hosting.

### Gợi ý 2
Đánh giá dependency compatibility và stateful assumptions trước khi chọn Linux/container.

### Gợi ý 3
Thiết kế từng lát cắt migration với contract tests, routing và rollback; xem xét database expand/contract.

## Cấu trúc trả lời đề xuất

1. Inventory và risk map.
2. Non-functional requirements và success criteria.
3. So sánh các phương án hosting/architecture.
4. Chọn boundary chuyển đổi.
5. Data/auth/files/jobs migration.
6. CI/CD, rollout, rollback.
7. Testing và production telemetry.
8. Định nghĩa tiêu chí dừng hoặc đổi hướng.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không khẳng định ASP.NET MVC .NET Framework 4.5 chạy trực tiếp trên Linux App Service; đánh giá compatibility; ưu tiên incremental migration, contract preservation và rollback.

### Điểm cộng
Strangler routing, anti-corruption layer, externalize file storage, migrate jobs có idempotency, versioned API, database expand/contract, blue-green/canary, feature flags.

### Senior+
Phân tích identity trust boundary, Windows-only workload isolation, transaction ownership, dual-write hazards, security lifecycle và migration economics.

## Hướng giải quyết tham khảo

**Discovery:** Kiểm kê routes, traffic, background tasks, Windows Authentication, PDF, upload paths, SQL dependencies, session state, IIS modules, config transforms, third-party binaries và pipeline TeamCity/Octopus Deploy (nếu đang dùng). Lập contract tests cho mobile API và business-critical approval transitions. Xác minh khả năng nâng framework legacy lên bản được hỗ trợ trong giai đoạn chuyển tiếp; .NET Framework 4.5 đã hết hỗ trợ, nên cần kế hoạch giảm rủi ro bảo mật ngay, không đợi rewrite.

**Phương án:** (A) Hardening legacy IIS/Windows và thay đổi từng phần: ít rủi ro ngắn hạn nhưng kéo dài nợ kỹ thuật. (B) Strangler: đặt reverse proxy/gateway định tuyến một số endpoints sang ASP.NET Core trên App Service; giữ phần Windows-only trên IIS/Windows trong thời gian chuyển đổi. (C) Big-bang rewrite sang Kubernetes/Microservices: rủi ro timeline, auth, transaction và rollback cao; chỉ hợp lý khi có bằng chứng yêu cầu scale/ownership và nguồn lực vận hành tương xứng. App Service Windows hoặc Linux được chọn theo compatibility thực tế; không ép mọi workload lên Linux.

**Data và boundary:** Ưu tiên một vertical slice ít coupling, ví dụ read-only approval history, chuyển dần sang API mới; định nghĩa ownership của database tables và transaction. Tránh dual-write giữa legacy và new service; nếu cần đồng bộ bất đồng bộ, dùng Outbox/inbox hoặc CDC với reconciliation, nêu rõ eventual consistency. Với upload, thiết kế Blob Storage migration theo checksum, access control, malware scanning, SAS ngắn hạn hoặc backend proxy tùy trust model; không coi local disk App Service là durable shared storage. PDF Windows-only có thể chạy trong worker Windows cô lập với API rõ ràng, hoặc thay thư viện sau khi xác minh output parity. Batch jobs phải có idempotency và durable state trước khi chuyển sang Functions/Worker.

**Identity:** Windows Authentication intranet và Entra ID/OIDC không tương đương tự động. Thiết kế authentication boundary, claims mapping, authorization parity, token validation, session migration và audit; chạy pilot với nhóm người dùng và mobile compatibility tests. Không thay đổi authorization chỉ vì login thành công.

**Delivery:** Dùng expand/contract DB migrations tương thích cả hai versions, test rollback với dữ liệu mới, deployment slot/canary nơi phù hợp, smoke tests và Playwright E2E. Ràng buộc 15 phút downtime yêu cầu dry-run, cutover checklist và fallback route; backup/restore không phải rollback tức thời cho mọi schema migration. Theo dõi p95, error rates, approval state transitions, duplicate approvals, auth failures, job lag, file integrity, SQL waits và user-impact metrics. Đặt gates: error budget, contract parity, rollback rehearsal, security review. Tách quyết định target .NET version khỏi quyết định architecture; kiểm tra support lifecycle và library compatibility tại thời điểm triển khai.

**Trade-offs:** Strangler làm tăng vận hành hai stacks và routing complexity nhưng giảm blast radius; rewrite có thể đơn giản hóa code cuối cùng nhưng tăng migration risk. Chỉ chuyển Kubernetes khi có nhu cầu orchestration thực sự và năng lực SRE; App Service thường đủ cho web workload thông thường.

# Tổng kết hôm nay

## Kiến thức trọng tâm

DI lifetime là ownership boundary; `DbContext` cần scope riêng cho mỗi logical operation và không được dùng đồng thời. Cosmos DB cần tối ưu theo access pattern, RU charge và partition distribution; global dashboard có thể cần read model khác mobile feed. ## Mẫu tư duy cần nhớ

1. Kiểm tra object lifetime và ownership trước khi sửa concurrency symptom.

3. Thiết kế partition key theo workload thực tế, không theo tên entity.
4. Chọn migration boundary có thể kiểm chứng và rollback.
5. Test failure path và đo p95/p99, correctness, cost sau mỗi thay đổi.
