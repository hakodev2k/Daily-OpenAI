# Câu 1 — `HttpClient` vẫn gọi endpoint cũ sau khi DNS failover

**Loại câu hỏi:** Internal Mechanism + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** C#, ASP.NET Core, `HttpClient`, `IHttpClientFactory`, `SocketsHttpHandler`, DNS, connection pooling, resilience, networking, observability

## Bối cảnh

Một ASP.NET Core API gọi service `pricing.internal.company` qua HTTPS. Service downstream chạy nhiều instances phía sau internal load balancer. DNS record được thay đổi khi failover giữa hai clusters.

Team đã chuyển từ việc tạo `new HttpClient()` cho mỗi request sang dùng một singleton `HttpClient` vì trước đây từng gặp socket exhaustion.

```csharp
public sealed class PricingClient
{
    private static readonly HttpClient Client = new()
    {
        BaseAddress = new Uri("https://pricing.internal.company/")
    };

    public async Task<PriceDto> GetPriceAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        using var response = await Client.GetAsync(
            $"api/prices/{Uri.EscapeDataString(sku)}",
            cancellationToken);

        response.EnsureSuccessStatusCode();

        return (await response.Content
            .ReadFromJsonAsync<PriceDto>(cancellationToken))!;
    }
}
```

Trong một production incident:

- DNS của `pricing.internal.company` được đổi từ cluster A sang cluster B lúc 10:00;
- `nslookup` trên host application sau đó trả IP của B;
- một số application instances chuyển sang B nhanh, nhưng một số vẫn tiếp tục gửi traffic tới A hơn 20 phút;
- restart application làm symptom biến mất ngay;
- cluster A vẫn còn accept TCP connection nhưng trả nhiều `503` do đang drain;
- team kết luận rằng singleton `HttpClient` “cache DNS vĩnh viễn”;
- một developer đề xuất quay lại `new HttpClient()` cho mỗi request;
- developer khác muốn gọi DNS manually trước mọi HTTP request;
- platform team nói DNS TTL chỉ là 60 giây nên application đáng lẽ phải chuyển sau khoảng một phút.

## Câu hỏi chính

Hãy giải thích chính xác mối quan hệ giữa `HttpClient`, `SocketsHttpHandler`, DNS resolution và connection pooling; tại sao DNS TTL không đồng nghĩa mọi HTTP request sẽ resolve DNS lại; vì sao restart application làm incident biến mất; và thiết kế một cấu hình production-safe bằng `IHttpClientFactory` hoặc handler lifetime/connection lifetime phù hợp mà không quay lại socket exhaustion.

## Câu hỏi làm rõ nên cân nhắc

1. Protocol đang dùng là HTTP/1.1 hay HTTP/2, và một connection có thể sống bao lâu?
2. Downstream/load balancer có chủ động đóng connection khi drain cluster A không?
3. Application chạy .NET version nào và đang dùng default `SocketsHttpHandler` settings nào?
4. DNS failover là emergency mechanism hiếm hay deployment mechanism thường xuyên?
5. Có proxy/service mesh nào nằm giữa application và downstream làm thay đổi connection behavior không?

## Gợi ý tư duy

### Gợi ý 1

DNS thường được resolve khi cần tạo connection mới, không phải trước mỗi logical HTTP request.

### Gợi ý 2

Một connection đang còn usable có thể tiếp tục phục vụ nhiều requests ngay cả khi DNS record đã thay đổi.

### Gợi ý 3

Mục tiêu không phải “tạo `HttpClient` thật nhiều” mà là quản lý **handler/connection lifetime** đúng với DNS/failover characteristics.

## Cấu trúc trả lời đề xuất

1. Phân biệt `HttpClient` với handler và connection pool.
2. Giải thích lúc DNS được resolve.
3. Liên hệ persistent connections với stale endpoint.
4. Giải thích restart behavior.
5. Phân tích anti-pattern `new HttpClient()` per request.
6. Đề xuất `IHttpClientFactory` hoặc `PooledConnectionLifetime`.
7. Xác định timeout/retry/circuit-breaker boundary.
8. Xử lý downstream draining và connection failures.
9. Thiết kế telemetry để chứng minh endpoint thật sự được gọi.
10. Nêu test/failover exercise.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `HttpClient` là façade; connection pooling chủ yếu nằm trong underlying handler (`SocketsHttpHandler`).
- DNS resolution thường xảy ra khi thiết lập connection mới; một pooled persistent connection có thể tiếp tục được reuse mà không resolve DNS lại.
- DNS TTL không tự ép một connection TCP/HTTP hiện có phải đóng sau TTL.
- Singleton `HttpClient` không mặc định “xấu”; vấn đề là connection lifetime phải phù hợp nếu endpoint IP thay đổi.
- `new HttpClient()` mỗi request có thể tạo quá nhiều handlers/connections và dẫn đến port/socket exhaustion, latency và mất pooling benefits.
- `PooledConnectionLifetime` có thể giới hạn tuổi connection để định kỳ buộc tạo connection mới và re-resolve DNS.
- `IHttpClientFactory` quản lý handler lifetime/pooling và là lựa chọn phù hợp trong ASP.NET Core cho nhiều client scenarios.

### Điểm cộng

- Phân biệt `PooledConnectionLifetime` với idle timeout: một connection bận/liên tục reused có thể không bao giờ trở thành idle.
- Không đặt lifetime ngắn cực đoan nếu không có requirement, vì sẽ tăng TLS handshakes và connection churn.
- Retry chỉ áp dụng cho transient/replay-safe operations; không retry POST có side effect một cách mù quáng.
- Có connect timeout/request timeout hợp lý và cancellation propagation.
- Có named/typed client thay vì một global client với config phân tán.

### Senior+

- Nhận ra HTTP/2 multiplexing có thể khiến một connection duy nhất phục vụ rất nhiều requests lâu dài, làm connection lifetime càng quan trọng trong DNS-based failover.
- Phân biệt DNS caching ở OS/resolver với stale **connection reuse**; không kết luận dựa chỉ trên `nslookup`.
- Cân nhắc downstream connection draining: failover tốt hơn nếu old endpoint chủ động đóng/drain connection hợp lý.
- Đề xuất telemetry ghi remote peer/connection diagnostics hoặc correlate với downstream cluster identity thay vì chỉ log hostname.
- Thiết kế failover test đo time-to-converge thay vì chỉ unit test client.

## Hướng giải quyết tham khảo

Điểm đầu tiên là singleton `HttpClient` không đơn giản “cache một IP mãi mãi”. `HttpClient` gửi request qua handler. Với `SocketsHttpHandler`, handler giữ connection pool theo destination. DNS cần thiết khi handler mở một connection mới. Sau đó HTTP keep-alive cho phép reuse connection đó cho nhiều requests.

Nếu DNS record đổi nhưng application vẫn có một connection khỏe tới cluster A, logical requests tiếp theo có thể tiếp tục chạy trên connection A. DNS TTL 60 giây không có nghĩa connection TCP đang mở sẽ bị đóng ở giây 60. `nslookup` chỉ chứng minh resolver hiện trả IP mới; nó không chứng minh HTTP client đã cần tạo connection mới.

Restart application dispose handler/pool cũ, nên connection cũ bị mất. Khi process tạo connection mới, DNS được resolve lại và traffic sang B. Điều đó phù hợp với symptom.

Một cấu hình typed client có thể là:

```csharp
services.AddHttpClient<PricingClient>(client =>
{
    client.BaseAddress = new Uri("https://pricing.internal.company/");
    client.Timeout = TimeSpan.FromSeconds(10);
})
.ConfigurePrimaryHttpMessageHandler(() =>
    new SocketsHttpHandler
    {
        PooledConnectionLifetime = TimeSpan.FromMinutes(2),
        PooledConnectionIdleTimeout = TimeSpan.FromMinutes(1),
        ConnectTimeout = TimeSpan.FromSeconds(3)
    });
```

Con số 2 phút không phải magic number. Nó phải dựa trên failover SLO, DNS topology, connection cost và downstream behavior. Nếu business yêu cầu converge trong 30 giây, lifetime phải phản ánh requirement đó; nếu DNS hiếm đổi và TLS handshake đắt, lifetime dài hơn có thể hợp lý.

Một lựa chọn khác là dựa vào handler rotation do `IHttpClientFactory` quản lý. Tuy nhiên cần hiểu handler lifetime và connection lifetime là các knobs khác nhau. Tôi ưu tiên typed client để ownership/configuration rõ, rồi đo failover behavior thực tế.

Tôi sẽ không resolve DNS manually trước mỗi request vì application cuối cùng vẫn phải kết nối bằng networking stack/handler; manual resolution dễ phá TLS/SNI, load-balancing semantics và tạo thêm caching layer khó kiểm soát.

Retry policy cũng không giải quyết stale connection root cause. Nếu A trả 503, retry có thể giúp tạm thời nếu attempt mới mở connection khác, nhưng cũng có thể tiếp tục dùng pool cũ. Retry phải bounded, có jitter và chỉ cho operation replay-safe.

Observability nên có request duration, result, timeout/cancellation, retry count, downstream cluster/version marker và nếu phù hợp diagnostic event cho connection establishment. Failover exercise nên đổi DNS/load balancer trong staging và đo từ thời điểm change tới lúc toàn bộ app instances ngừng gửi request tới old cluster.

## Mẫu trả lời trong phỏng vấn

“DNS TTL không ép connection hiện có hết hạn. `HttpClient` dùng handler có connection pool; DNS thường được resolve khi cần mở connection mới. Nếu một keep-alive hoặc HTTP/2 connection tới cluster A vẫn usable, nhiều request có thể tiếp tục đi qua nó dù resolver hiện đã trả B. Restart xóa pool nên application tạo connection mới và resolve DNS lại.

Tôi không quay lại `new HttpClient()` mỗi request vì mất pooling và có thể gây socket/port pressure. Tôi dùng typed `HttpClient` qua `IHttpClientFactory`, đặt `PooledConnectionLifetime` dựa trên failover SLO để connection định kỳ được thay mới. Đồng thời tôi cấu hình timeout, bounded retry cho operation an toàn và đo time-to-converge trong failover test.

Điểm quan trọng là phân biệt DNS cache với connection reuse; `nslookup` mới không chứng minh request mới đã đi qua connection mới.”

## Câu hỏi đào sâu

1. Với HTTP/2, tại sao vấn đề stale endpoint có thể kéo dài hơn HTTP/1.1 trong một số workload?
2. `HandlerLifetime` của `IHttpClientFactory` và `PooledConnectionLifetime` giải quyết hai lớp lifecycle khác nhau thế nào?
3. Nếu service discovery thay IP mỗi 30 giây, liệu HTTP DNS-based discovery còn phù hợp hay nên thay đổi platform architecture?

## Lỗi trả lời thường gặp

- Nói `HttpClient` luôn resolve DNS trước mỗi request.
- Nói DNS TTL tự đóng TCP connection.
- Quay lại tạo/dispose `HttpClient` cho từng request mà không hiểu handler pooling.
- Cấu hình lifetime cực ngắn mà không xét TLS/connection overhead.
- Dùng retry như fix chính cho stale routing.
- Dựa vào `nslookup` nhưng không xác minh remote endpoint thật của traffic.

## Thang điểm 0–10

- **0–2:** Chỉ biết “singleton tốt/per-request xấu” nhưng không giải thích networking mechanism.
- **3–4:** Biết connection pooling nhưng nhầm DNS TTL với connection expiry.
- **5–6:** Giải thích đúng DNS-on-new-connection và đề xuất `IHttpClientFactory`/connection lifetime hợp lý.
- **7–8:** Phân tích HTTP/2, handler vs connection lifetime, retry và failover observability.
- **9–10:** Thiết kế được failover SLO, lifecycle tuning, downstream draining và evidence-driven production diagnostics đầy đủ.

# Câu 2 — Chỉ một số tenant bị SQL timeout vì parameter-sensitive execution plan

**Loại câu hỏi:** Production Incident + SQL Performance  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** SQL Server, EF Core, query plans, parameter sniffing/parameter sensitivity, Query Store, indexing, cardinality estimation, production diagnostics, performance engineering

## Bối cảnh

Một multi-tenant reporting API dùng EF Core và SQL Server. Endpoint sau lấy orders theo tenant và khoảng thời gian:

```csharp
public async Task<IReadOnlyList<OrderSummary>> SearchAsync(
    int tenantId,
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    return await _db.Orders
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId)
        .Where(x => x.CreatedAt >= from && x.CreatedAt < to)
        .OrderByDescending(x => x.CreatedAt)
        .Take(500)
        .Select(x => new OrderSummary(
            x.Id,
            x.ReferenceNo,
            x.Total,
            x.Status,
            x.CreatedAt))
        .ToListAsync(cancellationToken);
}
```

Database có khoảng 300 tenants:

- phần lớn tenant có dưới 20.000 orders;
- 5 tenant lớn có hàng chục triệu orders;
- data distribution theo `Status`, `CreatedAt` và tenant rất lệch;
- index hiện tại gồm `(CreatedAt)` và một index riêng `(TenantId)`;
- endpoint thường chạy 50–150 ms;
- sau một deployment không thay đổi query này, một số request của tenant lớn bắt đầu mất 8–15 giây và timeout;
- tenant nhỏ vẫn nhanh;
- restart application không giúp;
- DBA chạy cùng query trong SSMS với một tenant nhỏ thì rất nhanh;
- `UPDATE STATISTICS` làm symptom thay đổi tạm thời;
- một developer muốn tăng command timeout lên 60 giây;
- developer khác muốn thêm `AsEnumerable()` rồi filter trong application để SQL “đỡ phức tạp”;
- team nghi ngờ EF Core vì SQL generated có parameters thay vì literal values.

## Câu hỏi chính

Bạn sẽ điều tra incident này thế nào để phân biệt thiếu index, blocking, parameter-sensitive plan/parameter sniffing, stale statistics và query-shape problem? Hãy nêu evidence cụ thể cần lấy từ SQL Server, giải thích vì sao cùng SQL text có thể nhanh với tenant này nhưng chậm với tenant khác, rồi đề xuất remediation ngắn hạn và thiết kế query/index lâu dài mà không chữa symptom bằng command timeout.

## Câu hỏi làm rõ nên cân nhắc

1. Actual execution plan của slow tenant khác estimated plan ở đâu?
2. Query Store có thấy nhiều plans hoặc plan regression theo thời gian không?
3. SQL Server version/database compatibility level có hỗ trợ Parameter Sensitive Plan optimization không?
4. Slow request đang CPU-bound, IO-bound hay chờ lock/blocking?
5. Date range của tenant lớn có selectivity khác tenant nhỏ đến mức nào?

## Gợi ý tư duy

### Gợi ý 1

Đừng gọi mọi performance problem là “parameter sniffing”. Bắt đầu bằng waits, duration, reads và actual plan.

### Gợi ý 2

Một plan tối ưu cho tenant nhỏ có thể rất tệ cho tenant cực lớn nếu data distribution skew mạnh.

### Gợi ý 3

Index phù hợp phải phục vụ cả equality predicate, range/order và projection — nhưng không phải lúc nào “thêm index” cũng là đáp án duy nhất.

## Cấu trúc trả lời đề xuất

1. Xác định scope và mẫu request chậm/nhanh.
2. Capture generated SQL + parameter values an toàn.
3. Kiểm tra blocking/waits trước.
4. Dùng Query Store/actual plan để xem plan history.
5. So sánh estimated vs actual row counts.
6. Phân tích statistics/data skew.
7. Đánh giá index hiện tại.
8. Chọn mitigation ít rủi ro.
9. Thiết kế permanent fix theo SQL Server version/workload.
10. Regression/load test theo nhiều tenant cardinalities.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận parameter sniffing chỉ từ việc parameters tồn tại.
- Thu thập execution plan, logical reads, CPU/duration, waits/blocking và Query Store evidence.
- So sánh estimated rows với actual rows để phát hiện cardinality misestimate.
- Data skew theo tenant có thể khiến một cached plan tốt cho tenant nhỏ nhưng tệ cho tenant lớn, hoặc ngược lại.
- Index đơn `(TenantId)` và `(CreatedAt)` không nhất thiết tốt cho predicate kết hợp; composite index có thể phù hợp hơn.
- `AsEnumerable()` trước filter sẽ đẩy work ra client và thường làm performance/network/memory tệ hơn.
- Tăng command timeout chỉ kéo dài thời gian thất bại nếu root cause không được xử lý.

### Điểm cộng

- Xem plan compilation parameter và runtime parameter trong Query Store/plan properties.
- Xem statistics histogram và auto-update statistics behavior trên bảng lớn.
- Cân nhắc index dạng `(TenantId, CreatedAt DESC)` với `INCLUDE` cho projection tùy workload/write cost.
- Cân nhắc query splitting theo use case hoặc bounded date window nếu business cho phép.
- Phân biệt compile/recompile strategy với plan forcing.

### Senior+

- Biết SQL Server mới có Parameter Sensitive Plan optimization trong điều kiện phù hợp; không giả định feature hoạt động nếu compatibility/settings không đáp ứng.
- Hiểu `OPTION (RECOMPILE)` có thể giúp parameter-sensitive query nhưng đổi CPU compilation cost lấy plan specialization, nên không dùng blanket.
- `OPTIMIZE FOR`, plan forcing hoặc hints có thể là tactical mitigation nhưng cần evidence và monitoring.
- Xem memory grant/spill, key lookup, scan/seek choice, sort và row-goal do `TOP`/`Take`.
- Tách emergency mitigation khỏi schema/query redesign lâu dài.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng việc tăng timeout. Trước hết cần chứng minh slow request đang chờ gì.

Với một request chậm cụ thể, tôi correlate trace/request id với SQL dependency, lấy query text/query hash, duration, CPU, logical reads và wait/blocking evidence. Nếu request bị `LCK_*` wait, hướng điều tra là blocking/transaction. Nếu CPU/reads tăng lớn nhưng không bị block, query plan đáng nghi hơn.

Query Store đặc biệt hữu ích để xem cùng query có plan nào trước/sau incident, runtime distribution và plan regression. Tôi sẽ lấy actual plan cho representative tenant nhỏ và tenant lớn, rồi so estimated rows với actual rows ở các operators.

Ví dụ optimizer compile plan khi parameter đại diện chỉ trả vài trăm rows, chọn nested loops + key lookup. Với tenant cực lớn/date range rộng, actual rows có thể lên hàng trăm nghìn hoặc triệu, khiến cùng plan thực hiện quá nhiều lookups. Một plan scan/hash khác có thể tốt hơn cho tenant lớn. Ngược lại, plan compile từ giant tenant có thể scan quá nhiều cho tenant nhỏ.

Index hiện tại tách `(TenantId)` và `(CreatedAt)` buộc optimizer lựa chọn/intersect tùy plan. Với query equality theo tenant, range + sort theo CreatedAt và projection nhỏ, candidate index có thể là:

```sql
CREATE INDEX IX_Orders_TenantId_CreatedAt
ON dbo.Orders (TenantId, CreatedAt DESC)
INCLUDE (Id, ReferenceNo, Total, Status);
```

Nhưng tôi chỉ deploy sau khi xem write overhead, table width, existing indexes và actual plan. `Take(500)` có thể hưởng lợi lớn nếu index cho phép seek tenant/date range rồi đọc theo đúng order và dừng sớm.

Statistics phải được kiểm tra chứ không chỉ update theo thói quen. Nếu histogram/cardinality model không phản ánh skew đủ tốt, stats update có thể đổi compiled plan tạm thời nhưng không đảm bảo ổn định lâu dài.

Tùy SQL Server version, có thể tận dụng Parameter Sensitive Plan optimization nếu environment hỗ trợ. Với version cũ hoặc query đặc biệt, tactical options gồm `OPTION (RECOMPILE)` cho query có tần suất vừa phải nhưng độ skew cao, hoặc query/hint strategy được DBA kiểm chứng. Recompile mỗi execution có CPU cost nên không phải blanket fix.

Plan forcing qua Query Store có thể giúp rollback regression nhanh nếu đã biết một plan an toàn, nhưng nếu workload thật sự có hai cardinality regimes rất khác nhau thì ép một plan duy nhất có thể chỉ chuyển nạn nhân từ nhóm tenant này sang nhóm khác.

`AsEnumerable()` trước filter là sai hướng: nó có thể kéo data lớn qua network rồi filter trong process, mất server-side optimizer/index và tăng memory. Command timeout 60 giây chỉ làm thread/request giữ tài nguyên lâu hơn.

Regression test phải có dữ liệu skew representative: tiny tenant, medium tenant, giant tenant; date range 1 ngày, 30 ngày, 1 năm; cold/warm cache. Theo dõi p50/p95/p99, reads và plan stability chứ không chỉ một timing trong SSMS.

## Mẫu trả lời trong phỏng vấn

“Tôi không gọi đây là parameter sniffing ngay. Tôi lấy Query Store/actual plan, waits, reads, CPU và so estimated với actual rows cho cùng query ở tenant nhỏ và lớn. Nếu không có blocking và plan compile cho cardinality nhỏ nhưng chạy với cardinality rất lớn, parameter-sensitive plan là hypothesis mạnh.

Hai index riêng `TenantId` và `CreatedAt` có thể không phục vụ tốt query equality + range/order này. Tôi sẽ kiểm chứng một composite index `(TenantId, CreatedAt DESC)` với includes cần thiết để seek và stop sau 500 rows. Song song tôi xem stats/data skew và SQL Server version để biết PSP có áp dụng được không.

Tôi không tăng timeout hay chuyển filter về memory. Nếu cần mitigation, Query Store plan forcing hoặc recompile/hint có thể dùng có kiểm soát. Permanent fix phải dựa trên representative cardinalities và benchmark logical reads/plan stability.”

## Câu hỏi đào sâu

1. Khi nào `OPTION (RECOMPILE)` là lựa chọn hợp lý hơn một cached plan ổn định?
2. Tại sao `Take(500)` có thể tạo row-goal làm optimizer chọn plan bất ngờ?
3. Nếu composite covering index tăng write latency 20%, bạn sẽ quyết định giữ/bỏ nó dựa trên workload SLO nào?

## Lỗi trả lời thường gặp

- Thấy parameters là kết luận ngay parameter sniffing.
- Chỉ chạy query bằng một tenant nhỏ trong SSMS rồi nói database bình thường.
- Thêm index không dựa trên actual plan/workload.
- Dùng `AsEnumerable()` để né SQL performance issue.
- Tăng timeout mà không hiểu waits/reads.
- Force một plan duy nhất mà không xét tenant skew.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất timeout/index chung chung.
- **3–4:** Biết parameter sniffing nhưng thiếu evidence/plan reasoning.
- **5–6:** Có Query Store, actual plan, cardinality, composite index và stats analysis.
- **7–8:** Phân biệt waits, skew, PSP/recompile/forcing trade-offs và benchmark representative data.
- **9–10:** Có incident mitigation, deep optimizer reasoning, index economics và plan-stability strategy phù hợp production multi-tenant workload.

# Câu 3 — Zero-downtime deployment thất bại vì EF Core migration không tương thích với phiên bản app cũ

**Loại câu hỏi:** Architecture / Deployment / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, EF Core, SQL Server, Azure App Service deployment slots, schema migration, backward compatibility, feature flags, release engineering, rollback, observability

## Bối cảnh

Một ASP.NET Core application chạy trên Azure App Service với nhiều instances. Team dùng staging slot để deploy version mới rồi swap sang production.

Version hiện tại `v42` có bảng:

```sql
Customers
---------
Id
Name
LegacyCode NULL
```

Version `v43` refactor domain và muốn thay `LegacyCode` bằng `ExternalCustomerCode`, bắt buộc `NOT NULL`.

EF Core migration được tạo như sau:

```csharp
migrationBuilder.DropColumn(
    name: "LegacyCode",
    table: "Customers");

migrationBuilder.AddColumn<string>(
    name: "ExternalCustomerCode",
    table: "Customers",
    type: "nvarchar(64)",
    nullable: false,
    defaultValue: "");
```

Pipeline hiện làm:

1. deploy `v43` vào staging slot;
2. chạy `dotnet ef database update` trên production database;
3. health check staging;
4. swap staging → production;
5. nếu lỗi, swap back về `v42`.

Trong deployment gần nhất, migration chạy thành công nhưng trước khi swap hoàn tất, production slot vẫn có `v42` instances nhận traffic. Các instance này bắt đầu lỗi vì query vẫn đọc `LegacyCode`, column đã bị drop.

Team rollback bằng slot swap, nhưng `v42` vẫn không chạy được vì database schema đã thay đổi. Incident kéo dài cho tới khi DBA manually restore column.

Một developer đề xuất luôn chạy migration sau slot swap để app mới lên trước. Người khác muốn mỗi app instance tự gọi `Database.Migrate()` khi startup. Project manager yêu cầu “zero downtime và rollback trong vài phút”.

## Câu hỏi chính

Hãy thiết kế lại release/migration strategy để application version cũ và mới có thể coexist trong rolling/slot deployment. Giải thích nguyên tắc expand-contract, backward/forward compatibility, thứ tự deploy schema/code, data backfill, feature activation và destructive cleanup. Chỉ ra vì sao slot rollback không đồng nghĩa database rollback, và đưa ra một runbook đủ an toàn cho production.

## Câu hỏi làm rõ nên cân nhắc

1. Staging và production slot có dùng chung production database hay database riêng?
2. Có bao nhiêu app instances và swap/drain mất bao lâu?
3. `LegacyCode` có null/duplicate values cần transformation không?
4. Có background workers hoặc external integrations vẫn đọc schema cũ không?
5. Business chấp nhận bao lâu giữa expand release và contract cleanup?

## Gợi ý tư duy

### Gợi ý 1

Trong zero-downtime rollout, luôn giả định **old code và new code chạy đồng thời** trong một khoảng thời gian.

### Gợi ý 2

Schema migration destructive thường không nên nằm cùng release với code bắt đầu dùng schema mới.

### Gợi ý 3

Rollback application binary dễ hơn rollback data/schema đã mutated. Hãy thiết kế database change theo hướng additive trước.

## Cấu trúc trả lời đề xuất

1. Xác định compatibility window.
2. Phân loại additive vs destructive schema changes.
3. Thiết kế expand migration.
4. Deploy code bridge đọc/ghi hai representations nếu cần.
5. Backfill dữ liệu idempotent/batched.
6. Verify completeness và constraints.
7. Activate new behavior qua feature flag/config.
8. Retire old code path.
9. Contract/drop old schema ở release sau.
10. Thiết kế rollback/runbook/metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không drop/rename column đang được version cũ sử dụng trước khi version cũ biến mất hoàn toàn.
- Slot swap/rollback chỉ đổi application routing/version; nó không tự rollback production database migration.
- Dùng expand-contract: thêm schema mới trước, duy trì compatibility, migrate data/code, rồi destructive cleanup sau.
- Migration phải có ownership rõ trong pipeline; không để mọi app instance tự chạy destructive migration cạnh tranh ở startup.
- Backfill dữ liệu lớn cần batch/idempotency/monitoring, không nhất thiết chạy trong blocking migration transaction.
- `NOT NULL` constraint thường chỉ thêm sau khi dữ liệu đã backfill và application đã đảm bảo write invariant.
- Rollback plan phải giữ old app tương thích với expanded schema.

### Điểm cộng

- Thêm `ExternalCustomerCode NULL` ban đầu thay vì `NOT NULL default ''` ngay lập tức.
- Có bridge release dual-write hoặc write-new/read-fallback tùy consistency requirement.
- Có data validation trước khi chuyển read path.
- Destructive `DropColumn` chỉ thực hiện sau telemetry chứng minh không còn reader/writer cũ.
- Tách schema migration job khỏi app startup và serialize execution trong deployment pipeline.

### Senior+

- Phân biệt application rollback, schema rollback và data rollback; data transformation có thể irreversible.
- Thiết kế feature flag activation sau compatibility deployment để giảm blast radius.
- Xem cả background workers, reporting jobs, ETL, stored procedures và external consumers như schema clients.
- Cân nhắc lock duration/online behavior của DDL trên bảng lớn.
- Có migration version telemetry và startup compatibility check nhưng không để startup tự mutate schema nguy hiểm.

## Hướng giải quyết tham khảo

Root cause không nằm ở Azure slot swap riêng lẻ mà ở giả định database migration có thể phá backward compatibility trước khi old code ngừng chạy. Trong một rolling/slot deployment, luôn có compatibility window nơi cả `v42` và `v43` có thể truy cập cùng database.

Tôi sẽ chia thay đổi thành nhiều release.

### Phase 1 — Expand

Chỉ thêm schema mới, không drop cũ:

```csharp
migrationBuilder.AddColumn<string>(
    name: "ExternalCustomerCode",
    table: "Customers",
    type: "nvarchar(64)",
    nullable: true);
```

`v42` vẫn đọc `LegacyCode` bình thường. Database expanded phải backward-compatible.

### Phase 2 — Bridge application

Deploy một version trung gian, ví dụ `v43a`, hiểu cả hai columns. Tùy requirement, write path có thể dual-write:

```text
LegacyCode = value
ExternalCustomerCode = value
```

Read path có thể ưu tiên new column và fallback old trong giai đoạn chuyển tiếp. Nếu dual-write có risk divergence, logic phải centralized và có reconciliation metric.

### Phase 3 — Backfill

Backfill dữ liệu cũ theo batch, idempotent:

```sql
UPDATE TOP (5000) dbo.Customers
SET ExternalCustomerCode = LegacyCode
WHERE ExternalCustomerCode IS NULL;
```

Job tiếp tục theo batches, có progress, retry và throttling. Với bảng lớn, không nhét toàn bộ backfill vào một migration transaction dài chỉ vì tiện.

Trước khi chuyển read path, validate:

- số rows còn `NULL`;
- duplicate/invalid values;
- mismatch giữa old/new;
- downstream reports/integrations;
- error rate và write consistency.

### Phase 4 — Activate new path

Sau khi tất cả application instances hỗ trợ schema mới và backfill hoàn tất, bật feature flag để read/write chính thức dùng `ExternalCustomerCode`. Vẫn giữ old column trong compatibility window để rollback binary nếu cần.

### Phase 5 — Enforce

Khi dữ liệu đã sạch và write path mới ổn định, thêm constraint `NOT NULL` ở release riêng nếu cần. Cần đánh giá DDL locking trên bảng production lớn.

### Phase 6 — Contract

Chỉ sau khi chứng minh không còn `v42`, worker cũ, ETL, stored procedure hay integration nào đọc `LegacyCode`, deploy migration drop old column. Đây là destructive contract release và rollback semantics phải được đánh giá riêng.

Tôi không chọn “migration sau swap” như quy tắc tổng quát. Nếu app mới cần schema chưa tồn tại, app mới có thể lỗi ngay khi nhận traffic. Thứ tự đúng không phải luôn schema trước hoặc code trước; đúng là **mỗi bước phải tương thích với versions cùng tồn tại**.

Tôi cũng không để mỗi instance tự `Database.Migrate()` trong production multi-instance. Hai process có thể startup đồng thời, migration có thể lock lâu, failure ownership không rõ và application startup trở thành schema-control plane. Tôi muốn một migration stage/job duy nhất trong pipeline, có audit log, timeout và approval/rollback runbook phù hợp.

Rollback binary phải được test: trong phases expand/bridge, swap back về version cũ vẫn chạy vì old column còn đó. Sau contract phase, rollback về binary rất cũ có thể không còn supported; runbook phải nói rõ minimum compatible app version.

Observability gồm app version per instance, database migration version, rows pending backfill, dual-write mismatch count, feature flag state, SQL lock/wait duration và health checks từ cả old/new compatible clients.

## Mẫu trả lời trong phỏng vấn

“Zero downtime nghĩa là tôi phải thiết kế cho thời gian old và new code chạy cùng nhau. Migration hiện tại drop `LegacyCode` trước swap nên phá `v42`; swap back chỉ rollback binary, database vẫn ở schema mới nên rollback không có tác dụng.

Tôi dùng expand-contract. Release đầu chỉ add `ExternalCustomerCode` nullable. Sau đó deploy bridge code hiểu cả old/new, dual-write hoặc read-fallback tùy requirement. Backfill theo batch và verify. Khi toàn fleet đã hỗ trợ schema mới, bật new read path. Sau khi ổn định mới thêm `NOT NULL`, rồi ở release sau nữa drop `LegacyCode`.

Migration được chạy bởi một pipeline job có ownership rõ, không phải mỗi instance tự `Database.Migrate()`. Tôi giữ old schema trong rollback window và chỉ contract khi telemetry chứng minh không còn consumer cũ. Như vậy application rollback thực sự khả thi trong giai đoạn migration.”

## Câu hỏi đào sâu

1. Nếu dual-write old/new thành công một bên nhưng fail bên kia, bạn đảm bảo consistency thế nào?
2. Nếu bảng có 500 triệu rows, backfill và thêm `NOT NULL` cần thay đổi runbook ra sao để tránh lock/outage?
3. Nếu hai services độc lập dùng chung bảng và release cadence khác nhau, contract migration ownership nên được quản lý thế nào?

## Lỗi trả lời thường gặp

- Tin rằng deployment slot rollback sẽ rollback database.
- Rename/drop column trong cùng release với code mới và gọi đó là zero downtime.
- Bắt mọi instance tự chạy migration production khi startup.
- Add `NOT NULL default ''` để “cho migration chạy” mà không xử lý domain validity.
- Backfill hàng triệu rows trong một transaction dài không có throttling.
- Chỉ kiểm tra web app mà quên workers/ETL/integrations.

## Thang điểm 0–10

- **0–2:** Chỉ đổi thứ tự migrate/swap mà không hiểu compatibility window.
- **3–4:** Biết giữ column cũ nhưng chưa có data/backfill/rollback strategy.
- **5–6:** Thiết kế đúng expand-contract, bridge, backfill và delayed cleanup.
- **7–8:** Có feature activation, pipeline ownership, constraint strategy, observability và rollback compatibility.
- **9–10:** Reasoning đầy đủ về schema/data irreversibility, multi-consumer compatibility, large-table operations và production runbook nhiều phase.
