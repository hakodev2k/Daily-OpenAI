# Code Review Challenge 1 — CMS page cache làm rò rỉ nội dung personalized giữa người dùng

**Chủ đề:** C#/.NET, ASP.NET Core, Optimizely CMS architecture, caching, authorization, CDN, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một marketing website dùng ASP.NET Core và Optimizely CMS. Một số landing page có block chung cho mọi visitor, nhưng một block `AccountSummary` hiển thị dữ liệu theo user đã đăng nhập. Website chạy nhiều instances và đứng sau CDN. Team vừa thêm in-memory page cache để giảm latency origin vì một số content query và API call khá chậm.

Sau release, p95 latency giảm rõ rệt nhưng production xuất hiện incident nghiêm trọng: một số user thấy tên và membership tier của user khác trong HTML. Đồng thời editor phản ánh nội dung vừa publish đôi khi phải chờ vài phút mới xuất hiện. Business yêu cầu public content có thể cache mạnh, nhưng personalized content tuyệt đối không được chia sẻ giữa users. Chưa có requirement rằng toàn bộ page phải personalized; vì vậy không nên mặc định tắt toàn bộ caching là giải pháp tốt nhất.

## Đoạn code cần review

```csharp
public sealed class LandingPageService
{
    private readonly IMemoryCache _cache;
    private readonly IContentRepository _content;
    private readonly IAccountClient _accounts;
    private readonly IHttpContextAccessor _httpContextAccessor;

    public LandingPageService(
        IMemoryCache cache,
        IContentRepository content,
        IAccountClient accounts,
        IHttpContextAccessor httpContextAccessor)
    {
        _cache = cache;
        _content = content;
        _accounts = accounts;
        _httpContextAccessor = httpContextAccessor;
    }

    public Task<LandingPageVm> GetAsync(
        ContentReference pageLink,
        string language,
        CancellationToken cancellationToken)
    {
        var cacheKey = $"landing:{pageLink.ID}:{language}";

        return _cache.GetOrCreateAsync(cacheKey, async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);

            var page = _content.Get<LandingPage>(pageLink);
            var user = _httpContextAccessor.HttpContext?.User;

            AccountSummaryVm? account = null;
            if (user?.Identity?.IsAuthenticated == true)
            {
                var userId = user.FindFirst("sub")?.Value;
                if (userId is not null)
                {
                    account = await _accounts.GetSummaryAsync(
                        userId,
                        cancellationToken);
                }
            }

            return new LandingPageVm
            {
                Heading = page.Heading,
                HeroText = page.HeroText,
                Account = account
            };
        })!;
    }
}

[ApiController]
public sealed class LandingController : ControllerBase
{
    private readonly LandingPageService _service;

    public LandingController(LandingPageService service)
    {
        _service = service;
    }

    [HttpGet("/landing/{id:int}")]
    public async Task<IActionResult> Get(
        int id,
        CancellationToken cancellationToken)
    {
        var vm = await _service.GetAsync(
            new ContentReference(id),
            Request.Headers.AcceptLanguage.ToString(),
            cancellationToken);

        Response.Headers.CacheControl = "public,max-age=300";
        return Ok(vm);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và security problems trong cache key, cached value và HTTP cache policy.
2. Giải thích vì sao lỗi có thể xuất hiện khác nhau giữa application instances và CDN.
3. Phân tích publication/invalidation behavior thay vì chỉ đề xuất giảm TTL.
4. Ưu tiên findings theo severity và business impact.
5. Đề xuất design tách cacheable public content khỏi user-specific data.
6. Giải thích cách test cross-user leakage, publish invalidation, load và dependency failure.
7. Đề xuất telemetry để phát hiện cache leak/staleness mà không log dữ liệu cá nhân nhạy cảm.

## Câu hỏi gợi mở

1. Cache key hiện tại có dimension nào liên quan đến authenticated user không?
2. Nếu response chứa personalized data nhưng `Cache-Control` là `public`, intermediary cache được phép hiểu response như thế nào?
3. TTL 10 phút có phải là content publication strategy không?
4. Khi 1.000 requests cùng miss một hot page sau expiration, dependency behavior có gì đáng xem xét?
5. Có nhất thiết phải cache nguyên `LandingPageVm`, hay có thể tách public fragment và personalized fragment?

### Gợi ý 1

Primary risk là **cache boundary không trùng với data ownership boundary**: dữ liệu per-user đang được đặt vào cache dùng chung.

### Gợi ý 2

Review riêng ba lớp: application cache, HTTP/CDN cache và CMS publication invalidation. Mỗi lớp cần key/visibility/invalidation semantics phù hợp.

## Kết quả code review tham khảo

### Critical — Personalized account data được lưu trong shared application cache

**Vấn đề:** `AccountSummaryVm` được cache bằng key chỉ gồm page ID và language.

**Tại sao xảy ra:** Cache entry không phân biệt user. User đầu tiên tạo entry có thể đưa account data của mình vào object được trả cho các request sau.

**Ảnh hưởng production:** Cross-user data disclosure; đây là security/privacy incident, không chỉ là stale-cache bug.

**Cách sửa:** Không đưa user-specific data vào shared page cache. Cache riêng phần CMS/public content; account summary phải được resolve per request hoặc dùng private per-user caching có threat model và key/authorization rõ ràng. Với dữ liệu nhạy cảm, mặc định đơn giản hơn là không shared-cache nó.

### Critical — Response personalized được đánh dấu `public`

**Vấn đề:** Controller đặt `Cache-Control: public,max-age=300` cho response kể cả khi response chứa account data.

**Tại sao xảy ra:** HTTP caching policy không phân biệt public và authenticated/personalized representation.

**Ảnh hưởng production:** CDN/proxy có thể cache representation và phục vụ cho request khác tùy cache key/configuration, mở rộng blast radius ra ngoài một application instance.

**Cách sửa:** Personalized response không được public-cache. Có thể trả public CMS shell/data riêng với cache policy phù hợp và gọi endpoint account riêng với `private`/`no-store` theo sensitivity. Nếu server-side composition bắt buộc, cache policy phải phản ánh representation thực tế.

### High — CMS publication không có explicit invalidation

**Vấn đề:** Content được giữ tối đa 10 phút bất kể publish event.

**Tại sao xảy ra:** TTL đang thay thế invalidation strategy.

**Ảnh hưởng production:** Editor publish thành công nhưng visitor tiếp tục thấy content cũ; nhiều instances có local caches độc lập nên staleness không đồng nhất.

**Cách sửa:** Tận dụng CMS/content change notification phù hợp với architecture để invalidate cache entries liên quan, hoặc dùng cache dependency/versioning. Nếu dùng CDN, publication workflow cũng cần purge/version strategy ở edge. TTL vẫn có thể là safety bound, không phải cơ chế correctness duy nhất.

### High — Local `IMemoryCache` tạo consistency khác nhau giữa instances

**Vấn đề:** Mỗi instance có cache riêng.

**Tại sao xảy ra:** Scale-out không chia sẻ in-memory state.

**Ảnh hưởng production:** User có thể thấy phiên bản content khác nhau theo instance; publish invalidation nếu chỉ local càng dễ sai.

**Cách sửa:** Không nhất thiết phải chuyển mọi thứ sang Redis. Nếu CMS event có thể fan-out invalidation đến từng instance thì local cache vẫn có lợi và đơn giản. Nếu requirement cần shared cache, đánh giá distributed cache dựa trên latency, consistency và operational cost.

### High — Cache miss đồng thời có thể tạo stampede vào CMS/account dependency

**Vấn đề:** Nhiều request cho cùng hot key có thể cùng chạy expensive factory tùy cache implementation/pattern; code không có explicit single-flight/backpressure contract.

**Tại sao xảy ra:** Expiration đồng thời tập trung work vào dependency.

**Ảnh hưởng production:** CPU/origin/API load spike sau expiration hoặc restart; account API có thể bị khuếch đại tải.

**Cách sửa:** Sau khi loại personalized data khỏi shared cache, cân nhắc single-flight/keyed coordination cho expensive public-content load nếu telemetry chứng minh cần. Dùng jitter/pre-warming khi phù hợp; tránh global lock.

### Medium — `Accept-Language` raw header là cache dimension không được chuẩn hóa

**Vấn đề:** Header raw được đưa vào key và CMS language resolution không được xác định rõ.

**Tại sao xảy ra:** Một header có thể chứa nhiều language/ranking forms; các representation tương đương có thể tạo nhiều keys.

**Ảnh hưởng production:** Cache fragmentation, memory growth và content-language behavior khó dự đoán.

**Cách sửa:** Resolve culture/language theo supported languages trước, rồi dùng normalized culture key. Validate page availability/fallback theo CMS policy.

### Medium — Request cancellation bị gắn vào shared cache population

**Vấn đề:** Factory dùng request `CancellationToken`. Nếu request tạo cache entry bị disconnect/cancel, population có thể fail dù các request khác vẫn cần cùng public content.

**Tại sao xảy ra:** Lifetime của shared cache population bị buộc vào một caller.

**Ảnh hưởng production:** Hot-key misses có thể lặp lại và tăng load trong network churn.

**Cách sửa:** Sau khi tách cache layers, xác định explicit cancellation semantics cho shared refresh; không vô điều kiện dùng một request token làm lifecycle của work dùng chung. Đồng thời vẫn phải có bounded timeout để tránh orphan work.

### Medium — Không mô hình hóa dependency degradation cho account API

**Vấn đề:** Account API failure có thể làm toàn bộ landing request fail.

**Tại sao xảy ra:** Public content và personalized enrichment bị coupling trong cùng cache factory.

**Ảnh hưởng production:** Một dependency cá nhân hóa làm mất availability của marketing page.

**Cách sửa:** Xác định business requirement: nếu account summary optional, render public page và degrade block; nếu bắt buộc, trả failure rõ ràng. Timeout/retry phải bounded và dựa trên idempotency/cost.

### Low — Thiếu cache telemetry có thể chứng minh representation source

**Vấn đề:** Không có hit/miss, content version hay cache-layer metadata.

**Tại sao xảy ra:** Cache được xem như implementation detail thay vì production subsystem.

**Ảnh hưởng production:** Khó phân biệt stale data từ CMS, app cache hay CDN.

**Cách sửa:** Emit metrics/logs cho normalized key dimensions không nhạy cảm, hit/miss, content version/publish timestamp, refresh duration và CDN cache status khi có; không log account payload.

## Phiên bản đề xuất

Một hướng đơn giản là chỉ cache public CMS projection và resolve account per request. Ví dụ:

```csharp
public sealed record PublicLandingContent(
    string Heading,
    string HeroText,
    long ContentVersion);

public sealed class LandingContentService
{
    private readonly IMemoryCache _cache;
    private readonly IContentRepository _content;

    public LandingContentService(
        IMemoryCache cache,
        IContentRepository content)
    {
        _cache = cache;
        _content = content;
    }

    public Task<PublicLandingContent> GetPublicAsync(
        ContentReference pageLink,
        string resolvedLanguage)
    {
        var key = $"landing-public:{pageLink.ID}:{resolvedLanguage}";

        return _cache.GetOrCreateAsync(key, entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10);

            var page = _content.Get<LandingPage>(pageLink);
            return Task.FromResult(new PublicLandingContent(
                page.Heading,
                page.HeroText,
                page.ContentLink.WorkID));
        })!;
    }

    public void Invalidate(ContentReference pageLink, string resolvedLanguage)
        => _cache.Remove($"landing-public:{pageLink.ID}:{resolvedLanguage}");
}

[ApiController]
public sealed class LandingController : ControllerBase
{
    private readonly LandingContentService _content;
    private readonly IAccountClient _accounts;

    public LandingController(
        LandingContentService content,
        IAccountClient accounts)
    {
        _content = content;
        _accounts = accounts;
    }

    [HttpGet("/landing/{id:int}")]
    public async Task<IActionResult> Get(
        int id,
        CancellationToken cancellationToken)
    {
        var language = ResolveSupportedLanguage(Request);
        var page = await _content.GetPublicAsync(
            new ContentReference(id), language);

        AccountSummaryVm? account = null;
        if (User.Identity?.IsAuthenticated == true)
        {
            var userId = User.FindFirst("sub")?.Value;
            if (userId is not null)
                account = await _accounts.GetSummaryAsync(userId, cancellationToken);
        }

        Response.Headers.CacheControl = account is null
            ? "public,max-age=60"
            : "private,no-store";

        return Ok(new LandingPageVm
        {
            Heading = page.Heading,
            HeroText = page.HeroText,
            Account = account
        });
    }
}
```

`Invalidate` ở đây chỉ minh họa boundary; production phải wire nó vào content publication/change mechanism phù hợp và xử lý tất cả instances/edge cache. Nếu muốn CDN cache mạnh ngay cả với authenticated visitors, tốt hơn có thể tách public page/content endpoint khỏi account endpoint để personalized data không làm toàn representation trở thành private.

## Giải thích thiết kế sau khi sửa

Shared cache chỉ chứa dữ liệu có cùng visibility cho mọi user trong cùng content/language representation. Personalized data được tính sau cache boundary. HTTP cache policy phụ thuộc representation thực tế. Publication invalidation là một explicit flow thay vì chờ TTL.

Tách public/personalized endpoints còn cho phép CDN cache public content mà không phải cache account data. Đây thường là boundary dễ audit hơn so với tạo cache key per-user cho cả page.

## Trade-offs

Tách endpoint có thể thêm một browser request và cần xử lý loading/error state ở frontend. Server-side composition đơn giản cho client nhưng làm response private và giảm CDN hit ratio. Distributed cache có thể đồng bộ data tốt hơn giữa instances nhưng thêm network hop, serialization và failure mode. Event-driven invalidation nhanh hơn TTL-only nhưng cần đảm bảo event propagation và fallback khi event bị mất.

## Cách kiểm thử

1. **Security integration test:** user A và B gọi cùng page qua cùng/different instances; không representation nào được chứa account data của user khác.
2. **Publication test:** warm cache, publish content mới, xác minh app instances và CDN converge theo invalidation SLO.
3. **Load test:** expire một hot public key rồi tạo burst concurrency; đo origin/content-query rate và p95/p99 latency.
4. **Failure-path test:** account API timeout; xác minh behavior đúng policy và public content không bị cache cùng error/personalized state.
5. **HTTP/CDN test:** kiểm tra `Cache-Control`, `Age`/cache status và cache key behavior cho anonymous vs authenticated requests.

## Quan sát trong production

Theo dõi app cache hit ratio, refresh duration/error, CMS query duration, content version lag, CDN hit ratio/cache status và account dependency p95/error rate. Structured logs có correlation ID, page/content ID, normalized language, cache layer và content version nhưng không log account payload. Alert khi publication-to-visible lag vượt SLO hoặc khi authenticated responses xuất hiện với public-cache policy.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business muốn CDN cache HTML cho cả logged-in users nhưng vẫn có account widget, bạn sẽ thay đổi composition boundary thế nào?
2. Khi nào Redis/distributed cache đáng dùng hơn local cache + distributed invalidation trong scenario này?
3. Nếu publication event bị mất, cơ chế reconciliation/fallback nào ngăn stale content tồn tại vô hạn?

# Code Review Challenge 2 — Vue search hiển thị kết quả cũ do race condition và render HTML không tin cậy

**Chủ đề:** Vue.js, TypeScript, async race condition, request cancellation, XSS, API integration, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một enterprise product portal dùng Vue.js + TypeScript gọi ASP.NET Core search API. Khi user gõ nhanh, frontend gửi request theo từng thay đổi query. API có latency dao động 80 ms–2 s vì một số query đi qua search backend. Production nhận phản ánh rằng đôi khi user gõ `laptop`, nhưng UI cuối cùng lại hiển thị kết quả của query cũ `lap`.

Search result có field `highlight` do backend/search engine trả về để đánh dấu từ khóa. Team đang render field này như HTML. Chưa có contract nói rằng `highlight` đã được sanitize theo allowlist. Requirement là UI phải không hiển thị stale result, phải xử lý network failure rõ ràng và không tạo XSS boundary dựa trên assumption không được chứng minh.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  title: string
  highlight: string
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch(query, async (value) => {
  if (!value.trim()) {
    items.value = []
    return
  }

  loading.value = true
  error.value = null

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(value)}`
    )

    if (!response.ok) {
      throw new Error(await response.text())
    }

    const data = await response.json() as SearchItem[]
    items.value = data
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <input v-model="query" placeholder="Search products" />

  <div v-if="loading">Loading...</div>
  <div v-if="error" class="error">{{ error }}</div>

  <ul>
    <li v-for="item in items" :key="item.id">
      <strong>{{ item.title }}</strong>
      <div v-html="item.highlight"></div>
    </li>
  </ul>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định race conditions và state correctness problems khi nhiều requests overlap.
2. Xác định security risk của rendering search highlight.
3. Phân tích UX/network impact khi user gõ nhanh hoặc request bị abort/fail.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation giữ latest-query-wins một cách rõ ràng.
6. Giải thích unit/integration/Playwright tests cho out-of-order response và XSS payload.
7. Đề xuất browser/network telemetry để phát hiện stale result và request amplification.

## Câu hỏi gợi mở

1. Request cho `lap` và `laptop` có bắt buộc hoàn thành theo thứ tự gửi không?
2. `loading` của request cũ có thể chuyển thành `false` trong lúc request mới vẫn chạy không?
3. `AbortController` giải quyết được phần nào, và phần nào vẫn cần sequence/identity guard?
4. `v-html` có trust boundary gì khác với interpolation `{{ ... }}`?
5. Có cần gọi API cho mọi keystroke hay nên có debounce/minimum query policy?

## Gợi ý

### Gợi ý 1

Primary risks là **out-of-order async completion** và **rendering untrusted HTML**.

### Gợi ý 2

Đừng chỉ thêm debounce. Hãy xác định request identity/latest-result rule, cancellation behavior và HTML trust contract độc lập với request-rate optimization.

## Kết quả code review tham khảo

### Critical — `v-html` render `highlight` khi chưa có trusted sanitization contract

**Vấn đề:** `item.highlight` được đưa trực tiếp vào DOM như HTML.

**Tại sao xảy ra:** HTML từ API/search index được coi là trusted presentation markup. Nếu source content hoặc highlight pipeline có attacker-controlled text, markup nguy hiểm có thể tới browser.

**Ảnh hưởng production:** DOM-based/rendered XSS có thể chạy trong origin của application, dẫn tới account/session actions hoặc data exposure tùy authentication model và browser protections.

**Cách sửa:** Ưu tiên API trả structured highlight segments hoặc plain text và render bằng Vue interpolation. Nếu business bắt buộc HTML highlight, sanitize bằng well-maintained allowlist sanitizer tại trust boundary và giới hạn tags/attributes nghiêm ngặt; không tự viết regex sanitizer.

### High — Out-of-order responses có thể overwrite latest query

**Vấn đề:** Mọi watcher callback đều ghi `items.value` khi request của nó hoàn thành.

**Tại sao xảy ra:** Network completion order không được bảo đảm. Request cũ chậm hơn có thể hoàn thành sau request mới.

**Ảnh hưởng production:** UI hiển thị dữ liệu không tương ứng với input hiện tại; user có thể chọn nhầm product.

**Cách sửa:** Mỗi search có request identity/sequence; chỉ latest request được phép commit state. Abort previous request để giảm wasted work, nhưng vẫn giữ identity guard vì cancellation không nên là correctness assumption duy nhất.

### High — `loading` cũng bị race giữa requests

**Vấn đề:** `finally` của request cũ luôn set `loading=false`.

**Tại sao xảy ra:** Loading state không gắn với active request identity.

**Ảnh hưởng production:** Spinner biến mất trong khi latest request vẫn pending, tạo misleading UX.

**Cách sửa:** Chỉ latest request được cập nhật shared loading/error state hoặc dùng active request counter/state machine phù hợp.

### Medium — Abort được coi như error nếu thêm cancellation ngây thơ

**Vấn đề:** Code hiện chưa cancel; nếu chỉ thêm `AbortController` mà giữ catch hiện tại, `AbortError` có thể hiện như user-facing failure.

**Tại sao xảy ra:** Expected cancellation và real network/server failure không được phân loại.

**Ảnh hưởng production:** UI nhấp nháy error khi user gõ bình thường.

**Cách sửa:** Nhận diện expected abort và không set error cho request bị supersede; real failure của latest request mới cập nhật error state.

### Medium — Không debounce làm tăng request amplification

**Vấn đề:** Mỗi thay đổi query tạo network request ngay.

**Tại sao xảy ra:** Watcher không có debounce/minimum-length policy.

**Ảnh hưởng production:** Tăng QPS, browser work và search-backend load; dưới peak traffic có thể làm latency xấu hơn và tăng overlap.

**Cách sửa:** Debounce theo UX requirement và cân nhắc minimum query length. Đây là optimization/backpressure, không thay thế latest-result correctness guard.

### Medium — Error body từ server bị biến thành user-facing string

**Vấn đề:** `await response.text()` được đưa vào `Error`, rồi render cho user.

**Tại sao xảy ra:** Internal/server error contract không được tách khỏi presentation message.

**Ảnh hưởng production:** Có thể lộ implementation detail hoặc tạo UX không nhất quán; interpolation giúp tránh HTML execution nhưng không giải quyết information disclosure.

**Cách sửa:** API dùng stable `ProblemDetails`/error code contract; UI map sang safe user message và log correlation ID/details ở telemetry phù hợp.

### Medium — Empty query không reset toàn bộ request state

**Vấn đề:** Khi query trở thành empty, code clear items nhưng request cũ vẫn có thể hoàn thành và repopulate items; loading/error cũng có thể giữ state cũ.

**Tại sao xảy ra:** Empty-query transition không cancel/invalidate active request.

**Ảnh hưởng production:** Search result xuất hiện dù input trống.

**Cách sửa:** Invalidate sequence và abort active request khi query empty; reset relevant state.

### Low — Response parsing tin shape runtime hoàn toàn

**Vấn đề:** Type assertion `as SearchItem[]` chỉ có tác dụng compile-time.

**Tại sao xảy ra:** Không có runtime validation nếu API contract drift hoặc malformed payload.

**Ảnh hưởng production:** Rendering/runtime behavior khó chẩn đoán khi contract sai.

**Cách sửa:** Với boundary quan trọng, validate required shape hoặc dùng generated typed client/schema validation phù hợp; ít nhất handle JSON parse/contract errors riêng trong telemetry.

## Phiên bản đề xuất

Ví dụ dưới đây dùng sequence guard + `AbortController`; debounce có thể được bọc ngoài theo UX requirement.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  title: string
  highlightText: string
}

const query = ref('')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let sequence = 0
let controller: AbortController | null = null

watch(query, async (rawValue) => {
  const value = rawValue.trim()
  const requestSequence = ++sequence

  controller?.abort()
  controller = null

  if (!value) {
    items.value = []
    loading.value = false
    error.value = null
    return
  }

  const currentController = new AbortController()
  controller = currentController

  loading.value = true
  error.value = null

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(value)}`,
      { signal: currentController.signal }
    )

    if (!response.ok) {
      throw new Error(`Search failed with status ${response.status}`)
    }

    const data = await response.json() as SearchItem[]

    if (requestSequence === sequence) {
      items.value = data
    }
  } catch (e) {
    if (currentController.signal.aborted) {
      return
    }

    if (requestSequence === sequence) {
      error.value = 'Search is temporarily unavailable.'
    }
  } finally {
    if (requestSequence === sequence) {
      loading.value = false
    }
  }
})
</script>

<template>
  <input v-model="query" placeholder="Search products" />

  <div v-if="loading">Loading...</div>
  <div v-if="error" class="error">{{ error }}</div>

  <ul>
    <li v-for="item in items" :key="item.id">
      <strong>{{ item.title }}</strong>
      <div>{{ item.highlightText }}</div>
    </li>
  </ul>
</template>
```

Nếu highlight cần giữ formatting, API có thể trả segments như `{ text, highlighted }[]` để frontend tạo DOM bằng template thay vì nhận arbitrary HTML. Debounce nên được thêm với cleanup rõ ràng; giá trị delay cần dựa trên UX/QPS measurements chứ không phải con số “chuẩn” giả định.

## Giải thích thiết kế sau khi sửa

Sequence number định nghĩa correctness rule: chỉ request đại diện cho query mới nhất được commit shared state. `AbortController` giảm wasted browser/network work nhưng không phải nền tảng duy nhất của correctness. Loading/error cũng tuân theo cùng request identity.

Plain-text/structured highlighting loại bỏ HTML khỏi API trust boundary. Điều này dễ audit hơn việc cố chứng minh mọi source và search analyzer luôn tạo safe HTML.

## Trade-offs

Debounce giảm QPS nhưng thêm perceived latency; delay quá dài làm search cảm giác chậm. Cancellation không đảm bảo backend luôn dừng work ngay lập tức nếu cancellation không propagate end-to-end. Sequence guard giữ correctness dù backend vẫn hoàn thành request cũ. Structured highlight làm payload/template phức tạp hơn một chút nhưng giảm đáng kể XSS surface.

## Cách kiểm thử

1. **Unit/component test:** mock request `lap` chậm hơn `laptop`; resolve `laptop` trước rồi `lap`; UI cuối cùng chỉ hiển thị `laptop`.
2. **Playwright E2E:** route/intercept search API với delayed responses và xác minh latest-query-wins cùng loading state.
3. **Security test:** backend trả highlight chứa HTML/event-handler payload; UI phải render text/allowed structure, không execute script/event.
4. **Failure-path test:** latest request trả 500/network failure trong khi previous request bị abort; chỉ real latest failure tạo user-facing error.
5. **Load/browser test:** mô phỏng typing pattern thực tế, đo requests per search session, aborted ratio, API QPS và p95 latency trước/sau debounce.

## Quan sát trong production

Frontend telemetry nên có search request duration, status category, abort/superseded count, query-length bucket và correlation/request ID; tránh gửi raw search query nếu nó có thể chứa dữ liệu nhạy cảm. Backend/Application Insights theo dõi search QPS, cancellation, dependency latency và p95/p99. Browser performance/network telemetry giúp xác định request amplification. Có thể đo stale-commit prevention count ở client để biết race xảy ra thường xuyên đến mức nào mà không ghi query content.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao debounce một mình không giải quyết out-of-order response?
2. Nếu ASP.NET Core API nhận `RequestAborted`, bạn sẽ propagate cancellation xuống search client như thế nào và khi nào không nên retry?
3. Nếu product team bắt buộc backend trả `<em>` trong highlight, bạn thiết kế allowlist/sanitization contract và tests ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cache và async UI đều là bài toán về **identity của representation/work**. Shared cache chỉ an toàn khi mọi request dùng cùng key thực sự được phép nhìn cùng dữ liệu. Async search chỉ đúng khi UI biết response nào còn quyền cập nhật state. CDN, application cache, CMS publication, browser requests và backend dependencies đều tạo thêm failure/ordering boundaries cần được mô hình hóa rõ.

Security cũng không nên dựa trên implicit trust: authenticated response không mặc nhiên được public-cache, và HTML từ API không mặc nhiên an toàn để render. Correctness boundary nên được thể hiện trong cache key/policy, request identity và data contract.

## Mẫu tư duy cần nhớ

* Cache key phải phản ánh **representation identity và visibility**, không chỉ technical lookup key.
* Tách **public cacheable data** khỏi **personalized/private data** trước khi tối ưu cache hit ratio.
* Với async UI, định nghĩa rõ **request nào còn quyền commit state**; cancellation chỉ là optimization bổ sung.
* Không render HTML từ external/API boundary nếu chưa có explicit sanitization contract.
* Test ordering, failure và invalidation paths — không chỉ happy path.
