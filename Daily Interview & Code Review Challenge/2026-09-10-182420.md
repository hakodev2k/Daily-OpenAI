# Câu 1 — Vì sao UI hiển thị dữ liệu “cũ” dù request mới trả về sau: JavaScript event loop, Promise microtask và race condition thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** JavaScript, TypeScript, Vue.js/React.js, event loop, Promise, microtask, task queue, async/await, API integration, race condition, request cancellation, frontend observability

## Bối cảnh

Một product-search page viết bằng Vue.js gọi ASP.NET Core API mỗi khi user thay đổi filter. Logic rút gọn:

```ts
const products = ref<Product[]>([])
const loading = ref(false)

async function loadProducts(query: SearchQuery) {
  loading.value = true

  const response = await fetch('/api/products?' + toQueryString(query))
  const result = await response.json()

  products.value = result.items
  loading.value = false
}

watch(searchState, async (value) => {
  await loadProducts(value)
}, { deep: true })
```

Trong production:

- user thay đổi filter rất nhanh;
- Network tab cho thấy request B được gửi sau request A nhưng trả về trước;
- đôi khi UI cuối cùng lại hiển thị kết quả của A;
- backend logs xác nhận cả hai API responses đều đúng theo request tương ứng;
- CPU browser thấp;
- team cho rằng “JavaScript single-threaded nên không thể có race condition”;
- một developer thêm `setTimeout(..., 0)` để “đảm bảo request mới chạy sau”;
- một developer khác thêm `await Promise.resolve()` nhưng behavior vẫn không ổn định;
- chưa có request cancellation hoặc request sequence/version guard;
- application có loading spinner dùng chung một boolean.

Không giả định Vue.js là nguyên nhân duy nhất; hãy reasoning từ JavaScript runtime trước.

## Câu hỏi chính

Hãy giải thích **call stack, task queue, Promise microtask queue và `async/await` continuation** liên quan thế nào đến scenario này. Vì sao JavaScript vẫn có race condition dù code JavaScript trên main thread thường chạy theo run-to-completion? Tại sao `setTimeout(..., 0)` hoặc `await Promise.resolve()` không giải quyết bản chất stale-response race? Sau đó đề xuất cách sửa phù hợp và cách verify behavior trong browser/production telemetry.

## Câu hỏi làm rõ nên cân nhắc

1. Search API có idempotent GET hoàn toàn hay mỗi request còn tạo side effect khác?
2. UX mong muốn là cancel request cũ, bỏ qua response cũ, hay cho phép song song nhưng chỉ apply response mới nhất?
3. Filter state có debounce requirement hay mọi thay đổi phải gọi API ngay?
4. `fetch` failure/abort đang được xử lý thế nào, và loading state có thể bị request cũ set về false khi request mới vẫn chạy không?
5. Có SSR, client-side cache hoặc shared store nào khác cũng có thể mutate `products` không?

## Gợi ý tư duy

### Gợi ý 1

Tách **execution order của JavaScript callbacks** khỏi **completion order của asynchronous I/O**.

### Gợi ý 2

Promise continuation được queue khi asynchronous operation hoàn tất. Request bắt đầu trước không có nghĩa continuation của nó sẽ chạy trước.

### Gợi ý 3

Fix cần định nghĩa ownership của kết quả: response nào còn quyền cập nhật state khi nó quay về?

## Cấu trúc trả lời đề xuất

1. Clarify desired UX semantics.
2. Giải thích run-to-completion của từng job/callback.
3. Giải thích task và microtask scheduling ở mức cần thiết.
4. Giải thích async I/O completion order và stale response race.
5. Phân tích loading-state race riêng.
6. So sánh cancellation, sequence guard và debounce.
7. Đề xuất implementation.
8. Test rapid interaction + network latency inversion.
9. Instrument browser/API correlation.

## Ý chính của câu trả lời tốt

### Bắt buộc

- JavaScript main-thread execution thường xử lý từng job/callback theo run-to-completion, nhưng asynchronous operations có thể hoàn tất theo thứ tự khác với thứ tự bắt đầu.
- `async/await` không serialize mọi invocation của cùng function. Mỗi invocation có continuation riêng sau awaited Promise.
- Promise callbacks/`await` continuations chạy qua microtask processing; điều đó không đảm bảo request A hoàn tất trước B chỉ vì A được gọi trước.
- Nếu B trả về trước rồi A trả về sau, assignment từ A có thể overwrite state mới bằng stale data.
- `setTimeout(..., 0)` chỉ schedule một task ở tương lai; nó không tạo ordering guarantee với network completion.
- `await Promise.resolve()` chỉ yield qua Promise/microtask semantics; nó không giải quyết quyền cập nhật shared UI state.
- Cần explicit strategy như AbortController, monotonically increasing request ID/version, hoặc cả hai.
- Shared boolean `loading` cũng có race: request cũ hoàn tất có thể set `loading=false` trong khi request mới vẫn pending.

### Điểm cộng

- Dùng debounce khi product requirement cho phép để giảm request volume, nhưng không coi debounce là correctness guarantee duy nhất.
- Tách `isLatestRequest`/request generation khỏi UI framework specifics.
- Handle `AbortError` như expected control flow, không log thành production error nếu user tạo cancellation hợp lệ.
- Có correlation giữa frontend request ID và backend trace ID để verify which response updated UI.
- Test bằng controlled delays để đảo completion order A/B một cách deterministic.

### Senior+

- Nhận ra cancellation không luôn đồng nghĩa server-side work đã dừng; frontend vẫn cần state guard và backend cần propagate cancellation nếu phù hợp.
- Phân biệt “drop stale response” với “cancel underlying request”; hai chiến lược giải quyết overlap nhưng có operational consequences khác nhau.
- Thiết kế loading state theo active request token/counter thay vì boolean toàn cục đơn giản khi nhiều requests hợp lệ chạy song song.
- Nếu search results được cache, version guard vẫn cần nếu cache hit/miss làm completion order khác nhau.

## Hướng giải quyết tham khảo

JavaScript không cần nhiều threads để có race condition ở mức application state. Race ở đây là **thứ tự hoàn tất của hai asynchronous operations**.

Một simplified timeline:

```text
T0  call loadProducts(A)
T1  fetch(A) pending → function yields
T2  call loadProducts(B)
T3  fetch(B) pending → function yields
T4  network B completes
T5  continuation B runs → products = B
T6  network A completes
T7  continuation A runs → products = A  // stale overwrite
```

Mỗi continuation chạy run-to-completion khi được execute. Vấn đề không phải hai callbacks chạy đồng thời trên cùng main thread; vấn đề là chúng **arrive in an order business logic không mong muốn**.

MDN mô tả JavaScript execution model với call stack/job queue và event loop; Promise callbacks sử dụng microtask semantics, và microtasks được xử lý trước khi event loop chuyển sang task tiếp theo khi stack rỗng. Tuy nhiên queueing priority này không biến network I/O thành FIFO theo request-start order.

Một fix bằng `AbortController`:

```ts
let activeController: AbortController | null = null
let requestVersion = 0

async function loadProducts(query: SearchQuery) {
  const version = ++requestVersion

  activeController?.abort()
  const controller = new AbortController()
  activeController = controller

  try {
    loading.value = true

    const response = await fetch(
      '/api/products?' + toQueryString(query),
      { signal: controller.signal })

    if (!response.ok) {
      throw new Error(`Search failed: ${response.status}`)
    }

    const result = await response.json()

    if (version !== requestVersion) {
      return
    }

    products.value = result.items
  }
  catch (error) {
    if (error instanceof DOMException && error.name === 'AbortError') {
      return
    }

    if (version === requestVersion) {
      reportSearchError(error)
    }
  }
  finally {
    if (version === requestVersion) {
      loading.value = false
    }
  }
}
```

Tại sao vừa abort vừa version guard? Abort giảm unnecessary work và network transfer khi browser/runtime/provider thực sự dừng được request. Version guard bảo vệ state correctness ngay cả khi một operation đã tiến xa, cancellation đến muộn, hoặc abstraction khác không abort hoàn hảo.

Nếu UX cho phép debounce:

```ts
const debouncedLoad = useDebounceFn((query: SearchQuery) => {
  void loadProducts(query)
}, 250)
```

Debounce giảm churn nhưng correctness vẫn nên dựa trên cancellation/version semantics.

Testing quan trọng:

- A delayed 800 ms, B delayed 100 ms → UI cuối phải là B;
- A response hoàn tất đúng lúc B được start;
- B fails nhưng A stale response quay về sau → không được restore A ngoài ý muốn;
- rapid 20 filter changes → chỉ latest result apply;
- aborted requests không tạo noisy error telemetry;
- loading không flicker sai do stale `finally`.

Production telemetry có thể record:

- frontend request version/client request ID;
- filter hash không nhạy cảm;
- start/end/abort/stale-drop events;
- browser duration;
- backend trace/correlation ID;
- count stale responses dropped;
- abort ratio và search error ratio.

Tài liệu tham khảo:

- MDN — JavaScript execution model: `https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model`
- MDN — Using microtasks in JavaScript: `https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide`

## Mẫu trả lời trong phỏng vấn

“Single-threaded không có nghĩa không có race condition. Mỗi JavaScript job chạy run-to-completion, nhưng hai `fetch` có thể complete ngược thứ tự. `loadProducts(A)` await rồi yield, `loadProducts(B)` cũng yield; nếu B hoàn tất trước thì B update state trước, sau đó A quay về có thể overwrite bằng dữ liệu cũ.

Promise continuation được schedule theo microtask semantics khi Promise settle, nhưng điều đó không đảm bảo network request nào bắt đầu trước sẽ settle trước. Vì thế `setTimeout(0)` hoặc `await Promise.resolve()` chỉ thay đổi scheduling cục bộ, không định nghĩa response nào được quyền update state.

Em sẽ định nghĩa latest-request ownership bằng sequence/version ID và thường abort request cũ bằng AbortController. `finally` cũng chỉ được update loading nếu request đó vẫn là latest. Nếu UX cho phép, em debounce input để giảm load nhưng không dùng debounce làm correctness mechanism duy nhất.

Em test bằng cách cố tình cho A chậm hơn B và instrument request ID từ browser tới backend để chứng minh response nào được apply, abort hay drop.”

## Câu hỏi đào sâu

1. Nếu AbortController đã gọi `abort()` nhưng backend vẫn tiếp tục chạy query SQL, bạn giải thích điều đó thế nào và cần sửa ở layers nào?
2. Nếu product yêu cầu hiển thị cached result ngay rồi refresh result mới sau, versioning/cancellation design cần thay đổi ra sao?
3. Một teammate đề xuất serialize mọi search request bằng queue để tránh race. Khi nào bạn chấp nhận và khi nào cách đó làm UX/performance tệ hơn?

## Lỗi trả lời thường gặp

- Nói JavaScript single-threaded nên race condition không tồn tại.
- Cho rằng `await` làm tất cả invocations chạy tuần tự.
- Dùng `setTimeout(0)` để “ép thứ tự network”.
- Chỉ fix `products` nhưng bỏ qua race ở loading/error state.
- Dùng debounce nhưng không có stale-response correctness guard.

## Thang điểm 0–10

- **0–2:** chỉ nói “API trả về sai thứ tự”.
- **3–4:** nhận ra stale response nhưng giải thích event loop/microtask còn mơ hồ.
- **5–6:** giải thích đúng async completion race, `await`, microtask và sequence guard/cancellation.
- **7–8:** xử lý loading/error/cancellation, có deterministic tests và telemetry.
- **9–10:** phân tích browser + server cancellation semantics, cache/UX variants và lựa chọn coordination mechanism dựa trên business behavior.

# Câu 2 — Kubernetes pods restart liên tục sau release: liveness probe, readiness probe, startup probe hay memory limit đang giết application?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, liveness/readiness/startup probes, container lifecycle, OOMKilled, resource requests/limits, rollout, health checks, Application Insights, structured logs, incident response, load/performance

## Bối cảnh

Một ASP.NET Core .NET 8 API trước đây chạy trên Azure App Service, gần đây được một platform team đưa lên Kubernetes. Sau một release có thêm in-memory product metadata preload, production xuất hiện:

- một số Pods restart nhiều lần;
- rollout kéo dài hơn bình thường;
- user thấy burst 502/503 trong khoảng 10 phút;
- `kubectl get pods` có Pods từng ở `CrashLoopBackOff`;
- event history của một số Pods có `OOMKilled`, một số khác có probe failures;
- application startup có thể mất 45–90 giây khi preload metadata;
- cùng endpoint `/health` hiện được dùng cho liveness và readiness;
- endpoint đó kiểm tra cả SQL Server, Redis và một third-party product API;
- liveness probe bắt đầu sau 10 giây;
- readiness failure khiến Pod tạm không nhận traffic;
- container memory limit hiện là 512 MiB nhưng team chưa có allocation/working-set baseline;
- memory request thấp hơn limit khá nhiều;
- deployment có 8 replicas;
- một engineer muốn tăng liveness timeout và restart threshold thật cao;
- một engineer khác muốn tăng memory limit lên 2 GiB ngay;
- chưa có heap dump/profile hoặc timeline correlate giữa GC, preload, probe failures và restarts.

Không giả định chỉ có một root cause. Có thể tồn tại đồng thời probe misconfiguration và memory pressure.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo thứ tự **impact → stabilize → evidence → competing hypotheses → verification → remediation → prevention**. Giải thích đúng vai trò của liveness, readiness và startup probes; vì sao cùng một `/health` kiểm tra external dependencies có thể gây restart cascade; `OOMKilled` khác probe-triggered restart ra sao; và cách bạn quyết định điều chỉnh probes/resources/application behavior dựa trên evidence thay vì chỉ tăng timeout hoặc memory.

## Câu hỏi làm rõ nên cân nhắc

1. Pod restart reason/last state cụ thể của từng Pod là `OOMKilled`, failed liveness, application exit hay deployment replacement?
2. Peak RSS/working set, GC heap size và allocation rate khi preload là bao nhiêu so với 512 MiB limit?
3. `/health` mất bao lâu khi SQL/Redis/third-party chậm, và dependency nào thực sự cần thiết để process còn “alive”?
4. Pod có startup probe hay chỉ liveness/readiness với `initialDelaySeconds=10`?
5. Rollout strategy (`maxUnavailable`, `maxSurge`) và traffic drain/termination behavior hiện tại có làm giảm capacity quá nhanh không?

## Gợi ý tư duy

### Gợi ý 1

Trước hết phân loại **restart cause**. `CrashLoopBackOff` là symptom/backoff state, không phải root cause.

### Gợi ý 2

Liveness trả lời “process/app có cần restart không?”; readiness trả lời “instance này có nên nhận traffic lúc này không?”. Hai câu hỏi không giống nhau.

### Gợi ý 3

External dependency outage không nên tự động biến thành mass restart nếu restart application không thể chữa dependency đó.

## Cấu trúc trả lời đề xuất

1. Xác định user impact và remaining healthy capacity.
2. Pause/slow rollout nếu release đang tiếp tục gây churn.
3. Group Pods theo restart reason.
4. Thu Kubernetes events, previous container logs và application metrics.
5. Correlate memory/probe/startup timeline.
6. Verify health endpoint semantics.
7. Stabilize probe/resource configuration có kiểm soát.
8. Fix application preload/memory behavior nếu có evidence.
9. Revisit rollout/readiness/drain strategy.
10. Test startup, dependency failure và load.
11. Add dashboards/alerts/runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `CrashLoopBackOff` mô tả repeated container failures với backoff; cần xem `lastState`, exit reason, events và previous logs để biết nguyên nhân.
- Liveness failure repeated đủ threshold có thể dẫn đến container restart.
- Readiness failure chủ yếu khiến Pod bị loại khỏi matching Service endpoints; không nên dùng readiness như restart mechanism.
- Startup probe phù hợp khi application startup có thể lâu; khi được cấu hình, nó bảo vệ startup khỏi liveness/readiness can thiệp trước khi startup thành công theo semantics của Kubernetes.
- Một liveness endpoint phụ thuộc SQL/Redis/third-party có thể làm Pods restart khi dependency ngoài app bị outage, tạo thundering herd/restart cascade mà không chữa root cause.
- `OOMKilled` là tín hiệu process/container bị kill vì memory limit/cgroup memory pressure context; tăng probe timeout không chữa OOM.
- Tăng memory limit không mặc định đúng nếu release tạo unbounded/preload allocation bug.
- Resource tuning phải dựa trên working set/heap/allocation/load measurements.
- Có thể tồn tại multiple failure modes đồng thời và phải phân loại theo Pod/restart attempt.

### Điểm cộng

- Tách `/health/live` và `/health/ready` với checks phù hợp thay vì một endpoint cho mọi mục đích.
- Liveness nên kiểm tra process-internal condition mà restart có khả năng chữa; tránh deep dependency check không cần thiết.
- Readiness có thể phản ánh dependency cần thiết để instance phục vụ traffic, nhưng cần cân nhắc nếu dependency outage toàn cục khiến toàn fleet unready.
- Startup probe budget dựa trên measured cold-start distribution chứ không giá trị ngẫu nhiên.
- Inspect `kubectl describe pod`, events, previous logs, container termination reason, metrics và application traces.
- Có memory profile/heap dump/dotnet-counters hoặc equivalent observability trong staging/load test.

### Senior+

- Phân tích resource requests ảnh hưởng scheduling/capacity planning còn limits ảnh hưởng enforcement; không chỉ nhìn một số duy nhất.
- Xem preload design: eager load toàn catalog có thể đổi memory scaling theo dataset size; cân nhắc bounded cache, lazy loading, external/distributed cache hoặc compact representation nếu evidence justify.
- Xem rollout availability math: probes quá nghiêm + long startup + maxUnavailable có thể giảm serving capacity trong rollout.
- Có graceful termination/readiness drain để tránh nhận request mới khi Pod sắp dừng.
- Không biến health checks thành synthetic end-to-end dependency tests quá nặng chạy vài giây một lần.

## Hướng giải quyết tham khảo

### 1. Stabilize

Nếu rollout vẫn đang tiếp tục và healthy capacity giảm, tôi sẽ pause rollout. Mục tiêu đầu tiên là giữ đủ serving Pods, không tiếp tục thay replicas khi chưa hiểu failure.

Nếu previous version ổn và rollback application **không** gặp schema/data incompatibility, rollback có thể là stabilization option. Nếu release thay shared DB/schema thì phải kiểm tra compatibility trước.

### 2. Phân loại restart

Cho mỗi Pod:

```text
Pod
deployment revision
node
restart count
last termination reason / exit code
OOMKilled?
liveness failure events?
startup duration
memory peak
request load
```

Các lệnh investigation điển hình:

```bash
kubectl get pods -o wide
kubectl describe pod <pod>
kubectl logs <pod> --previous
kubectl get events --sort-by=.lastTimestamp
```

Không kết luận từ `CrashLoopBackOff` một mình.

### 3. Probe semantics

Kubernetes documentation phân biệt:

- **liveness probe**: xác định khi nào container cần restart;
- **readiness probe**: xác định Pod có sẵn sàng nhận traffic qua Service hay không;
- **startup probe**: dành cho application cần thời gian startup dài và trì hoãn liveness/readiness semantics cho tới khi startup probe thành công.

Với startup 45–90 giây mà liveness bắt đầu sau 10 giây, application có thể bị kill trước khi preload xong nếu probe endpoint chưa thành công.

Ví dụ cấu hình tốt hơn về mặt structure:

```yaml
startupProbe:
  httpGet:
    path: /health/startup
    port: 8080
  periodSeconds: 5
  failureThreshold: 24

livenessProbe:
  httpGet:
    path: /health/live
    port: 8080
  periodSeconds: 10
  failureThreshold: 3

readinessProbe:
  httpGet:
    path: /health/ready
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
```

Các numbers trên chỉ là ví dụ; production values phải dựa trên measured startup/request behavior.

### 4. Health endpoint design

`/health/live` không nên fail chỉ vì third-party product API đang down nếu restart app không thể chữa dependency. Có thể chỉ check critical internal progress/deadlock-like conditions hoặc process state tối thiểu.

`/health/ready` có thể check những prerequisites cần để serve traffic. Nhưng nếu Redis optional với fallback SQL, Redis failure không nhất thiết làm unready. Health semantics phải theo actual capability.

Ví dụ ASP.NET Core conceptual mapping:

```csharp
builder.Services.AddHealthChecks()
    .AddCheck<SelfHealthCheck>("self", tags: ["live"])
    .AddCheck<SqlHealthCheck>("sql", tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = r => r.Tags.Contains("ready")
});
```

Không thêm external third-party health check nếu failure của nó không nên remove/restart toàn instance.

### 5. OOM investigation

Nếu `lastState.terminated.reason == OOMKilled`, thu memory telemetry:

- working set/RSS theo thời gian;
- managed heap size;
- Gen 2/LOH size;
- allocation rate;
- dataset size preload;
- concurrent preload count;
- native allocations nếu nghi ngờ;
- memory before/after GC.

Nếu 512 MiB limit nhỏ hơn legitimate working set, tăng limit có thể đúng. Nhưng nếu preload build duplicate graphs hoặc load unbounded metadata, tăng limit chỉ trì hoãn failure.

Một design tốt hơn có thể:

- stream/load theo batches;
- compact DTO/index thay vì full entity graph;
- lazy/bounded cache;
- enforce max cache size;
- avoid duplicate copy trong serialization/deserialization;
- move rarely-used metadata ra external store nếu latency/SLA cho phép.

### 6. Requests/limits

Requests nên phản ánh scheduling needs, limits phản ánh bounded maximum phù hợp workload. Nếu request quá thấp, scheduler có thể pack nhiều Pods lên node hơn resource profile thực tế mong muốn. Nếu limit quá thấp, legitimate spikes có thể bị kill. Nhưng “set request=limit=2GiB” cũng cần capacity/cost evidence.

### 7. Rollout

Long startup + strict probes + aggressive `maxUnavailable` có thể giảm capacity. Rollout cần:

- readiness trước khi nhận traffic;
- sensible startup budget;
- enough surge capacity;
- termination grace/drain;
- deployment health gate;
- rollback trigger theo error/restart rate.

### 8. Tests

- cold startup với production-like metadata size;
- third-party API down → liveness phải vẫn đúng semantics;
- SQL unavailable → readiness behavior theo designed capability;
- memory load test tới expected peak;
- rolling deployment under traffic;
- kill dependency/introduce latency và verify no restart storm;
- graceful termination test.

### 9. Observability

Dashboard:

- Pod restart count by reason;
- OOMKilled count;
- readiness/liveness/startup failure count;
- memory working set vs limit;
- managed heap/allocation/GC pause;
- startup duration p50/p95/p99;
- deployment revision;
- 5xx/latency;
- ready replicas / desired replicas;
- node memory pressure if relevant.

Tài liệu tham khảo:

- Kubernetes — Configure Liveness, Readiness and Startup Probes: `https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/`

## Mẫu trả lời trong phỏng vấn

“Em sẽ pause rollout và phân loại từng restart trước. `CrashLoopBackOff` chỉ nói container đang fail lặp lại; em xem `describe`, events, `logs --previous` và last termination reason để tách OOMKilled khỏi liveness kill hoặc app exit.

Liveness và readiness có semantics khác nhau. Liveness trả lời có nên restart container; readiness trả lời có nên nhận traffic. Nếu liveness gọi deep health check gồm SQL, Redis và third-party, dependency outage có thể restart cả fleet dù restart không chữa được dependency. Với startup 45–90 giây, em dùng startup probe với budget dựa trên p99 startup thay vì cho liveness bắn từ giây thứ 10.

OOMKilled em xử lý riêng: đo RSS, managed heap, allocation và preload size so với 512 MiB. Nếu working set hợp lệ vượt limit thì tăng limit có thể đúng; nếu preload unbounded/duplicate thì phải sửa memory behavior. Em cũng review requests/limits và rollout capacity.

Sau fix em tách live/ready endpoints, test dependency outage + cold startup + load, và monitor restart reason, probe failures, memory versus limit, ready replicas và 5xx theo deployment revision.”

## Câu hỏi đào sâu

1. Nếu Redis outage làm tất cả Pods readiness-fail và Service không còn endpoint nào, bạn có giữ Redis trong readiness check không? Bạn quyết định dựa trên fallback/business semantics nào?
2. Nếu memory working set ổn dưới 512 MiB ở staging nhưng production vẫn OOMKilled, bạn điều tra dataset, concurrency, node/container metrics và native memory theo hướng nào?
3. Một platform engineer đề xuất liveness probe gọi luôn SQL + Redis + three external APIs để “đảm bảo end-to-end healthy”. Bạn phản biện recommendation đó thế nào?

## Lỗi trả lời thường gặp

- Coi CrashLoopBackOff là root cause.
- Dùng cùng deep dependency health check cho liveness và readiness.
- Tăng memory limit trước khi đo memory profile.
- Tăng liveness timeout để chữa OOMKilled.
- Không xét rollout capacity, startup time và mixed failure modes.

## Thang điểm 0–10

- **0–2:** chỉ tăng timeout/memory hoặc restart deployment.
- **3–4:** biết probes và OOM nhưng chưa có incident evidence flow.
- **5–6:** phân loại restart đúng, hiểu live/ready/startup semantics và đo memory.
- **7–8:** có rollout/resource/probe redesign, tests và production telemetry rõ.
- **9–10:** phân tích capability-based readiness, resource scheduling/enforcement, failure amplification và đưa remediation conditional theo measured workload.

# Câu 3 — Thiết kế test strategy cho e-commerce/CMS platform: bao nhiêu Playwright E2E là đủ, và phần nào phải test ở API/integration level?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Playwright, unit testing, integration testing, API testing, E2E testing, ASP.NET Core, Optimizely CMS, SQL Server, Redis, third-party integrations, CI/CD, test data, flaky tests, observability, release safety, AI-assisted test generation

## Bối cảnh

Một e-commerce/CMS platform gồm:

- ASP.NET Core backend;
- Optimizely CMS cho editorial content;
- SQL Server cho transactional data;
- Redis cache;
- search service;
- third-party payment, review và identity providers;
- Vue.js frontend;
- CI bằng Jenkins;
- CD qua Octopus Deploy;
- production có nhiều deployment environments/slots.

Hiện tại team có khoảng 1.500 unit tests nhưng production vẫn gặp regression ở integration boundaries. Product đề xuất “viết Playwright cho mọi user flow” để tăng confidence.

Tình hình hiện tại:

- critical journeys gồm login, product search, PDP, add-to-cart, checkout, CMS publish và campaign landing page;
- Playwright suite prototype mới có 40 tests nhưng mất khoảng 18 phút và một số tests flaky;
- third-party sandbox đôi khi chậm hoặc unavailable;
- test data bị dùng chung nên tests ảnh hưởng nhau;
- database migration đôi lúc làm staging data không tương thích;
- frontend và backend deploy có thể lệch version trong vài phút;
- team chưa có contract/integration test rõ cho payment/review/search adapters;
- QA muốn giữ manual exploratory testing cho high-risk releases;
- leadership hỏi có nên đầu tư một “central automated testing platform” riêng, service hóa mọi test execution và dùng AI generate test cases tự động.

Mục tiêu là tăng release confidence mà không biến test suite thành bottleneck 60 phút và không phụ thuộc hoàn toàn vào flaky external systems.

## Câu hỏi chính

Hãy thiết kế **risk-based test architecture** cho hệ thống này: phân bố unit/integration/API/Playwright E2E tests ra sao, test data và third-party dependencies xử lý thế nào, suite nào chạy ở PR/merge/deploy/post-deploy, cách giảm flaky tests, cách validate database/configuration/mixed-version deployment, và khi nào một dedicated testing platform đáng đầu tư. Đồng thời giải thích cách dùng AI để hỗ trợ test generation mà không biến generated tests thành false confidence.

## Câu hỏi làm rõ nên cân nhắc

1. Những regression production gần đây tập trung ở business logic, database, frontend/backend contract hay third-party integration?
2. Release frequency và acceptable feedback time cho PR, pre-production và production smoke test là bao nhiêu?
3. Third-party providers có sandbox ổn định, mock server contract hoặc recorded fixtures chính thức không?
4. Team có khả năng tạo isolated test tenant/user/cart/order data theo test run không?
5. CMS publish/search indexing có eventual consistency SLA nào cần test thay vì dùng fixed sleep?

## Gợi ý tư duy

### Gợi ý 1

Đừng tối ưu theo số lượng tests. Tối ưu theo **risk coverage × feedback speed × determinism**.

### Gợi ý 2

E2E là valuable nhưng expensive và fragile. Boundary failures nên được đẩy xuống integration/contract level khi có thể.

### Gợi ý 3

Một test platform chỉ đáng có khi orchestration/environment/data scale tạo pain thực; không phải vì “automation = microservice”.

## Cấu trúc trả lời đề xuất

1. Inventory production failure modes.
2. Map risks sang test layer rẻ nhất có thể bắt lỗi.
3. Define PR fast suite.
4. Define integration/API suite.
5. Define small critical Playwright journeys.
6. Design test data isolation.
7. Design third-party strategy.
8. Design deployment/migration compatibility tests.
9. Tackle flakiness bằng evidence.
10. Define observability/artifacts của test runs.
11. Evaluate build-vs-buy/dedicated platform.
12. Define AI-assisted generation verification.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nên chuyển mọi behavior thành Playwright E2E. E2E nên tập trung critical cross-system journeys mà lower-level tests không cover đủ.
- Unit tests phù hợp pure business rules/algorithms; integration/API tests phù hợp DB mapping, EF Core queries, HTTP contracts, auth policies và adapters.
- Playwright phù hợp login/navigation/browser behavior/critical conversion journeys và a few failure-paths có giá trị cao.
- Third-party instability không nên làm toàn CI ngẫu nhiên đỏ; cần adapter-level contract tests, controlled mocks/stubs và một bounded real-sandbox suite.
- Shared mutable test data là nguồn flakiness; cần per-run/per-test isolation hoặc deterministic reset strategy.
- Không dùng arbitrary fixed sleeps cho eventual consistency nếu có thể poll condition với timeout/bounded retry.
- Database migrations phải được test trên realistic schema/data snapshot và mixed-version compatibility khi deployment strategy cần.
- Flaky tests phải có ownership/root-cause tracking; retry chỉ che noise nếu dùng vô tội vạ.
- Release gates phải cân bằng speed và risk; không chạy 60 phút tests cho mọi tiny PR nếu phần lớn không relevant.
- AI-generated tests phải được review, run, mutation/failure-validated hoặc ít nhất chứng minh test fail khi code behavior bị cố ý phá; generated tests không mặc định có giá trị.

### Điểm cộng

- Test pyramid/trophy không dùng như dogma; chọn layer dựa trên failure mode.
- Có “critical path E2E” nhỏ chạy mỗi merge/deploy và “broader regression E2E” chạy scheduled/pre-release.
- Parallelize Playwright với isolated data/context thay vì chỉ tăng worker count trên shared state.
- Thu trace/video/screenshot/network logs chỉ khi cần hoặc on-failure để debug mà không làm artifact bloat quá mức.
- Contract tests cho frontend-backend OpenAPI/API schema và third-party adapter normalization.
- Synthetic post-deploy smoke test qua actual ingress/CDN path cho vài journeys không destructive.

### Senior+

- Thiết kế test portfolio theo historical incident classes: mỗi production escape phải trigger question “layer nào rẻ nhất nên bắt lỗi này lần sau?”.
- Có deterministic environment/config manifest để biết test đang chạy artifact/config/schema version nào.
- Tách provider contract correctness khỏi provider live availability; một flaky sandbox không được trở thành single source of truth cho code correctness.
- Dedicated testing platform chỉ khi cần shared environment orchestration, ephemeral environments, test-data provisioning, cross-service observability hoặc large-scale execution; nếu không Jenkins + Playwright + test containers/scripts có thể đủ.
- AI usage có source grounding vào requirements/code diff và verification bằng test execution, code review, coverage of failure assertions—not test count.

## Hướng giải quyết tham khảo

### 1. Bắt đầu từ production escapes

Tôi sẽ phân loại các regression gần đây:

```text
Business rule bug
EF/SQL mapping/query bug
Auth policy bug
Frontend/backend contract mismatch
Migration/config mismatch
Third-party adapter bug
Browser UX bug
CMS publish/cache/search propagation bug
Deployment ordering bug
```

Sau đó mỗi failure class được map sang layer thấp nhất có confidence tốt.

### 2. Unit tests

Giữ unit tests cho logic không cần infrastructure:

- pricing calculation;
- validation;
- state transitions;
- mapping pure functions;
- retry decision logic;
- authorization helper khi tách được pure policy logic.

Không mock EF Core quá sâu để “test query” bằng LINQ-to-Objects rồi cho rằng SQL translation đã được test.

### 3. Integration/API tests

Dùng real relational engine/container/test database phù hợp cho:

- EF Core mappings;
- LINQ translation;
- constraints/transactions;
- migrations;
- authorization middleware/policies;
- HTTP status/ProblemDetails;
- serialization/versioning;
- Redis adapter fallback nếu test environment hỗ trợ Redis thật;
- search adapter contract ở layer phù hợp.

Ví dụ WebApplicationFactory-based API test với disposable database có thể rẻ và deterministic hơn browser E2E cho hàng trăm API rules.

### 4. Third-party dependencies

Tách ba tầng:

```text
A. Adapter unit tests
   - mapping/error classification

B. Contract/integration tests against controlled stub/mock server
   - exact HTTP request/response behavior

C. Small live-sandbox tests
   - credentials/network/provider compatibility
   - not necessarily blocking every PR if provider sandbox unstable
```

Nếu provider cung cấp official sandbox/contract, dùng nó. Nếu không, capture contract từ docs/approved fixtures, không invent behavior.

### 5. Playwright E2E portfolio

PR/merge suite chỉ nên có vài critical, deterministic journeys:

- login;
- search → PDP;
- add cart;
- checkout happy path với controlled payment stub/sandbox strategy;
- one authorization failure;
- CMS publish → public render nếu environment support deterministic propagation.

Broader suite có thể chạy pre-release/scheduled:

- multiple browsers nếu requirement;
- locale variants;
- campaign landing pages;
- failure journeys;
- accessibility checks phù hợp;
- cache/CDN behavior ở deployment environment.

Không viết 20 browser tests cho 20 validation rules nếu API/unit integration test bắt nhanh hơn.

### 6. Data isolation

Mỗi test run nhận namespace/run ID:

```text
run-20260910-abc123
  user
  cart
  order
  content item
```

Dữ liệu created by run phải cleanup idempotently hoặc environment reset bằng snapshot/container strategy. Parallel tests không reuse cùng mutable cart/order/user nếu tránh được.

### 7. Eventual consistency

Không:

```ts
await page.waitForTimeout(5000)
```

Nếu search indexing/CMS propagation eventual:

```ts
await expect.poll(async () => {
  const response = await request.get(`/api/search?q=${slug}`)
  return response.ok()
}, {
  timeout: 30_000
}).toBe(true)
```

Timeout phải dựa trên expected SLA/test environment, không arbitrary infinite polling.

### 8. Flakiness process

Mỗi flaky failure phải có classification:

- product bug;
- test bug;
- environment capacity;
- external dependency;
- timing assumption;
- shared data;
- selector instability.

Retry có thể dùng một lần để collect signal/artifacts nhưng build không nên xanh chỉ vì lần 2 pass mà issue bị bỏ qua. Track flaky rate per test và quarantine có owner/expiry nếu thật sự cần.

### 9. Pipeline design

Một baseline:

```text
PR:
  build + static analysis + unit + fast integration/API

merge/main:
  above + critical Playwright + migration validation

pre-deploy/staging:
  broader integration + compatibility + critical E2E

post-deploy:
  non-destructive smoke/synthetic checks

scheduled/pre-release:
  broader browser/provider/live-sandbox/load/failure-path suites
```

Thresholds phụ thuộc release frequency và risk.

### 10. Migration/deployment tests

Test database upgrade từ current production-like schema, không chỉ fresh database create.

Nếu rolling deployment:

- old app against expanded schema;
- new app against expanded schema;
- data written by new worker/app có old-reader compatibility trong transition;
- rollback package behavior sau migration.

Configuration manifest cần record:

- build SHA/version;
- frontend version;
- backend version;
- schema version;
- environment config version;
- test suite version.

### 11. Dedicated testing platform?

Không cần ngay nếu Jenkins + scripts + Playwright workers + disposable test infrastructure giải quyết được.

Platform đáng đầu tư khi team có recurring pain:

- nhiều services cần ephemeral environments;
- test data provisioning phức tạp;
- hàng trăm parallel runs;
- environment booking/contention;
- cross-service trace collection;
- centralized flaky analytics;
- multiple teams share testing capabilities.

Ngay cả khi build platform, hãy bắt đầu như internal tooling/modular service đơn giản; không mặc định microservices/Kubernetes.

### 12. AI-assisted testing

AI có thể:

- đọc code diff và suggest missing cases;
- tạo fixture builders;
- draft Playwright/API tests;
- identify boundary conditions;
- summarize flaky traces.

Nhưng verification bắt buộc:

- generated test compile/run;
- assertions match requirement;
- test fails khi target behavior bị intentionally broken;
- no hallucinated endpoints/selectors/APIs;
- no real secrets/PII copied vào prompts/fixtures;
- human review cho high-risk flows.

Một useful discipline là “red test proof”: trước khi chấp nhận generated regression test, cố chứng minh nó fail trên buggy version hoặc injected fault.

### 13. Observability của test system

Theo dõi:

- duration p50/p95 per suite;
- flaky rate per test;
- retry rate;
- queue time;
- environment failures;
- third-party sandbox failure rate;
- test failures by category;
- production escapes mapped to missing test layer;
- deployment rollback triggered by validation.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không biến toàn bộ regression thành Playwright. Em bắt đầu từ các production escapes rồi map mỗi risk xuống layer rẻ nhất bắt được. Business rules ở unit; EF/SQL/auth/API contracts ở integration/API; Playwright giữ cho critical browser journeys và vài cross-system failure paths.

Third-party em tách adapter tests, controlled contract/stub tests và một small live-sandbox suite. Sandbox không ổn định thì không nên làm mọi PR đỏ ngẫu nhiên. Test data phải isolated theo run; eventual consistency dùng polling theo condition/SLA, không fixed sleep.

Pipeline em chia fast PR suite, critical E2E ở merge/deploy, broader regression theo pre-release/scheduled. Database migration phải test từ production-like schema và nếu rolling deploy thì test old/new compatibility.

Flaky test có owner và root-cause classification; retry không phải giải pháp cuối. AI có thể draft tests từ diff/requirements nhưng em chỉ tin sau khi test chạy, assertions được review và chứng minh test fail trên buggy behavior.

Em chỉ xây testing platform riêng khi environment orchestration, data provisioning hoặc scale thực sự tạo pain. Nếu Jenkins + Playwright + integration infrastructure hiện tại đủ thì kiến trúc đơn giản hơn sẽ rẻ và đáng tin hơn.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu checkout Playwright test phải gọi payment sandbox thật trên mọi PR nhưng sandbox fail 3% ngẫu nhiên, bạn thiết kế release confidence thế nào mà không che integration risk?
2. Nếu critical E2E suite tăng từ 8 lên 80 tests và mất 45 phút, bạn quyết định test nào giữ ở E2E, test nào hạ xuống API/integration bằng tiêu chí gì?
3. Một AI agent tạo 300 tests và coverage tăng mạnh nhưng tất cả tests vẫn pass khi bạn cố ý remove một authorization check. Bạn đánh giá chất lượng workflow đó ra sao và sửa verification thế nào?

## Lỗi trả lời thường gặp

- Coi nhiều E2E tests hơn luôn đồng nghĩa confidence cao hơn.
- Dùng retry để che flaky tests mà không điều tra root cause.
- Shared test account/cart/order cho toàn suite parallel.
- Dùng fixed sleeps dài cho eventual consistency.
- Tin AI-generated tests dựa trên test count/coverage mà không chứng minh assertions bắt đúng failure.

## Thang điểm 0–10

- **0–2:** đề xuất “test mọi thứ bằng Playwright”.
- **3–4:** biết test pyramid nhưng áp dụng máy móc, chưa gắn với failure modes.
- **5–6:** phân tầng unit/integration/API/E2E hợp lý, xử lý data/third-party/flakiness.
- **7–8:** có pipeline gates, migration compatibility, observability và AI verification strategy.
- **9–10:** thiết kế test portfolio theo production risk, feedback economics và operational complexity; biết khi nào không nên xây platform riêng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- JavaScript single-threaded vẫn có asynchronous race condition khi I/O hoàn tất ngoài thứ tự business mong muốn; correctness cần explicit ownership/cancellation/versioning.
- Promise microtask semantics giải thích callback ordering nhưng không tạo FIFO guarantee cho network requests.
- Kubernetes liveness, readiness và startup probes có mục đích khác nhau; health-check design sai có thể khuếch đại dependency outage thành restart storm.
- `OOMKilled` cần memory evidence riêng; tăng timeout probe không giải quyết memory limit, và tăng limit không thay thế việc tìm allocation/preload bug.
- Test architecture phải tối ưu risk coverage, feedback speed và determinism; Playwright E2E là một layer quan trọng nhưng không nên gánh mọi regression.
- AI-assisted test generation chỉ tạo giá trị khi output được grounded, reviewed và chứng minh có khả năng fail trên behavior sai.

## Mẫu tư duy cần nhớ

- **Separate callback execution order from asynchronous completion order.**
- **Classify the failure before changing infrastructure knobs.**
- **Health checks should reflect the action Kubernetes can safely take.**
- **Put each risk in the cheapest deterministic test layer that can catch it.**
- **Validate generated tests by proving they fail when the target behavior is broken.**
