# Câu 1 — React search box trả kết quả “lùi thời gian”: request mới xong trước nhưng UI lại hiển thị response cũ

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** JavaScript event loop, Promise, React hooks, `useEffect`, closure, request cancellation, race condition, TypeScript, browser networking, frontend observability

## Bối cảnh

Một internal employee portal có màn hình tìm kiếm nhân viên bằng React + TypeScript. Khi user gõ vào ô search, frontend gọi ASP.NET Core API:

```http
GET /api/employees/search?q={text}
```

API thường trả trong 100–300 ms, nhưng đôi lúc một query mất 1–2 giây do SQL Server hoặc network chậm.

Component hiện tại:

```tsx
function EmployeeSearch() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState<Employee[]>([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!query.trim()) {
      setResults([]);
      return;
    }

    setLoading(true);

    fetch(`/api/employees/search?q=${encodeURIComponent(query)}`)
      .then(r => r.json())
      .then(data => {
        setResults(data);
        setLoading(false);
      })
      .catch(() => {
        setLoading(false);
      });
  }, [query]);

  return (
    <>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
      />
      {loading && <span>Loading...</span>}
      <EmployeeList items={results} />
    </>
  );
}
```

Production symptom:

- user gõ nhanh `a` → `an` → `anna`;
- request `anna` có thể trả trước request `an`;
- UI hiển thị đúng kết quả `anna` trong chốc lát rồi bị thay bằng kết quả cũ của `an`;
- đôi lúc spinner biến mất dù request mới nhất vẫn đang chạy;
- QA không reproduce ổn định trên local vì local API rất nhanh;
- một developer đề xuất “thêm `await` vào fetch là hết race condition”.

Giả sử backend trả đúng dữ liệu cho từng query và không có cache sai ở server.

## Câu hỏi chính

Hãy giải thích chính xác cơ chế nào khiến UI có thể hiển thị response cũ dù React state update và `fetch` đều dùng asynchronous APIs, vai trò của JavaScript event loop/Promise completion order/closure trong trường hợp này, tại sao chỉ đổi `.then(...)` thành `await` không giải quyết race, và bạn sẽ thiết kế implementation + verification như thế nào để UI luôn phản ánh request hợp lệ mới nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Product muốn gửi request ở mỗi keystroke hay có debounce requirement, ví dụ 200–300 ms?
2. Khi query thay đổi, response cũ có được phép populate cache nội bộ nhưng không update UI không?
3. Browser/support matrix có cho phép dùng `AbortController` ổn định không?
4. Nếu request bị abort, telemetry/backend có phân biệt client cancellation với server/network failure không?
5. Có library quản lý server state như React Query/TanStack Query đang dùng ở project hay đây là plain React state?

## Gợi ý tư duy

### Gợi ý 1

Thứ tự **request được tạo** không đảm bảo giống thứ tự **Promise được resolve**.

### Gợi ý 2

Mỗi execution của `useEffect` giữ closure riêng với giá trị `query` tại thời điểm effect chạy. Response cũ vẫn có thể gọi `setResults` sau response mới nếu không có guard/cancellation.

### Gợi ý 3

Hãy tách hai mục tiêu: giảm số request bằng debounce và đảm bảo correctness bằng cancellation hoặc request identity. Debounce một mình không chứng minh hết race.

## Cấu trúc trả lời đề xuất

1. Mô tả timeline của ba requests `a`, `an`, `anna`.
2. Giải thích event loop/Promise callbacks và completion order.
3. Giải thích closure của từng `useEffect` invocation.
4. Chỉ ra vì sao `await` chỉ đổi syntax/control flow trong cùng async function chứ không serialize các effect executions khác nhau.
5. Đưa ra ít nhất hai cách đảm bảo latest-request-wins.
6. Chọn một implementation phù hợp với project constraints.
7. Xử lý `loading`, abort và error state đúng semantics.
8. Test bằng artificial latency/reordered responses.
9. Quan sát production bằng request correlation/cancellation metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra đây là race giữa nhiều network operations độc lập.
- Biết thứ tự resolve của Promise phụ thuộc completion của I/O, không phụ thuộc thứ tự request được tạo.
- Biết mỗi effect giữ closure riêng với query tương ứng.
- Giải thích `await` không tự cancel/serialize các effect cũ.
- Đề xuất `AbortController` hoặc request sequence/token guard để stale response không update state.
- Nhận ra `loading` dạng boolean đơn giản cũng có race: request cũ hoàn tất có thể set `false` trong khi request mới đang chạy.
- Có test deterministic bằng mocked delayed/reordered responses.

### Điểm cộng

- Dùng cleanup function của `useEffect` để abort request trước.
- Phân biệt abort với genuine failure và tránh hiển thị error cho intentional cancellation.
- Đề xuất debounce để giảm backend load nhưng không coi debounce là correctness mechanism duy nhất.
- Dùng stable request ID hoặc compare query hiện tại trước khi commit response.
- Nhận ra React development behaviors như Strict Mode có thể làm side effects dễ lộ hơn trong development nhưng không phải root cause của production race này.

### Senior+

- Đề xuất mô hình server-state library nếu project đã dùng và library giải quyết cancellation/dedup/stale data semantics; không thêm dependency chỉ vì một component nhỏ.
- Định nghĩa rõ UX khi query rỗng, error, cancellation và stale results.
- Correlate frontend request ID với backend trace để phân biệt latency/reordering.
- Thảo luận failure nếu API không honor cancellation: client vẫn phải có stale-response guard dù abort đã được gửi.

## Hướng giải quyết tham khảo

Root cause không nằm ở việc code dùng `.then()` thay vì `await`. Có ba effects khác nhau chạy gần nhau:

```text
Effect 1: query = "a"     → request A
Effect 2: query = "an"    → request B
Effect 3: query = "anna"  → request C
```

Network/database latency có thể khiến completion order là:

```text
C → A → B
```

Mỗi `fetch()` trả một Promise riêng. Khi response tới, Promise continuation tương ứng được đưa vào microtask processing theo lúc Promise được settle. JavaScript không có rule “request tạo trước phải resolve trước”. Vì vậy `setResults` từ request B vẫn có thể chạy sau C và ghi đè state mới bằng dữ liệu cũ.

Closure cũng quan trọng: mỗi invocation của effect capture giá trị `query` riêng. Điều đó giúp biết request nào được tạo cho query nào, nhưng React không tự biết response nào “cũ về mặt product semantics”. `setResults(data)` đơn giản luôn commit dữ liệu.

Viết lại:

```tsx
useEffect(() => {
  async function load() {
    const response = await fetch(...);
    const data = await response.json();
    setResults(data);
  }

  load();
}, [query]);
```

không thay đổi fundamental concurrency. Mỗi effect vẫn gọi `load()` riêng; các async functions vẫn overlap.

Một implementation phù hợp là dùng `AbortController` trong cleanup và chỉ update loading/error cho request còn active:

```tsx
function EmployeeSearch() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState<Employee[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const normalized = query.trim();

    if (!normalized) {
      setResults([]);
      setLoading(false);
      setError(null);
      return;
    }

    const controller = new AbortController();
    let active = true;

    async function load() {
      setLoading(true);
      setError(null);

      try {
        const response = await fetch(
          `/api/employees/search?q=${encodeURIComponent(normalized)}`,
          { signal: controller.signal });

        if (!response.ok) {
          throw new Error(`HTTP ${response.status}`);
        }

        const data: Employee[] = await response.json();

        if (active) {
          setResults(data);
        }
      }
      catch (error) {
        if (!active) {
          return;
        }

        if (error instanceof DOMException && error.name === "AbortError") {
          return;
        }

        setError("Không thể tải kết quả tìm kiếm.");
      }
      finally {
        if (active) {
          setLoading(false);
        }
      }
    }

    void load();

    return () => {
      active = false;
      controller.abort();
    };
  }, [query]);

  // render...
}
```

`AbortController` giúp giảm work/network không cần thiết nếu request thực sự được cancel xuyên suốt stack. `active` guard vẫn hữu ích để stale continuation không commit state sau cleanup, kể cả khi cancellation không ngăn server hoàn tất work ngay lập tức.

Một alternative là sequence number:

```tsx
const requestId = useRef(0);

useEffect(() => {
  const id = ++requestId.current;

  async function load() {
    const response = await fetch(...);
    const data = await response.json();

    if (id === requestId.current) {
      setResults(data);
    }
  }

  void load();
}, [query]);
```

Cách này đảm bảo latest-request-wins ngay cả khi không abort được request cũ. Có thể kết hợp sequence guard + abort nếu cost của request đáng kể.

Debounce cũng hữu ích để tránh gửi request cho từng keystroke, nhưng debounce không phải toàn bộ correctness solution. Ví dụ user gõ query mới sau khi một debounced request cũ đã được gửi; hai requests vẫn có thể overlap.

Với `loading`, state nên phản ánh request hiện active chứ không để bất kỳ request cũ nào set `false`. Sequence/active guard giải quyết phần này.

Để verify, tôi không test bằng cách “gõ nhanh trên local”. Tôi dùng mocked network với response order deterministic:

```text
A("an")    delay 1000 ms
B("anna")  delay 100 ms
```

Sau khi cả hai hoàn tất, UI phải hiển thị `anna`, không bao giờ quay lại `an`. Test thêm unmount, query rỗng, HTTP 500, abort và rapid typing. Playwright có thể intercept routes và delay từng request để reproduce race ổn định.

Production telemetry có thể ghi search request duration, cancellation count và frontend error rate. Nếu có correlation ID từ browser → ASP.NET Core → SQL, team sẽ biết user input nào bị chậm và cancellation có thực sự propagate đến backend hay không.

## Mẫu trả lời trong phỏng vấn

“Đây là race giữa nhiều requests, không phải vấn đề `.then` hay `await`. Khi user gõ `an` rồi `anna`, hai `fetch` độc lập chạy đồng thời. Request `anna` có thể hoàn tất trước và update UI đúng, nhưng request `an` chậm hơn sau đó vẫn resolve và gọi `setResults`, nên state bị ghi đè bằng dữ liệu cũ. Mỗi `useEffect` giữ closure riêng với query của nó, nhưng React không tự biết response nào mới nhất theo business semantics.

Đổi code sang `await` chỉ làm code dễ đọc hơn; nó không serialize các effect executions. Tôi sẽ dùng cleanup của `useEffect` với `AbortController` và thêm stale-response guard hoặc request sequence ID. Chỉ request hiện active mới được update `results`, `loading` và `error`. Nếu project đã có TanStack Query thì có thể tận dụng cancellation/query-key behavior thay vì tự viết.

Tôi cũng cân nhắc debounce để giảm request rate, nhưng debounce không thay thế cancellation/latest-wins correctness. Để test, tôi mock hai requests sao cho query mới trả sau 100 ms còn query cũ trả sau 1 giây, rồi assert UI không bị quay lại kết quả cũ. Production thì theo dõi request latency, cancellation và correlation ID để phân biệt frontend race với backend latency.”

## Câu hỏi đào sâu

1. Nếu backend không dừng SQL query ngay cả khi browser abort request, `AbortController` còn giá trị gì và bạn cần thêm cơ chế nào ở frontend/backend?
2. Nếu product muốn giữ kết quả cũ trên màn hình trong lúc query mới đang loading để giảm flicker, bạn sẽ mô hình hóa `results`, `query`, `loading` và stale state thế nào?
3. Tôi phản đối mọi request sequence logic và muốn chỉ debounce 500 ms; bạn đồng ý hay phản đối dựa trên failure scenario nào?

## Lỗi trả lời thường gặp

- Nói “JavaScript single-threaded nên không có race condition”.
- Nghĩ `await` tự đảm bảo request chạy đúng thứ tự giữa nhiều effects.
- Chỉ thêm debounce rồi kết luận stale-response race đã hết.
- Abort request nhưng vẫn để `finally` của request cũ set `loading=false` cho request mới.
- Không có deterministic test cho reordered responses.

## Thang điểm 0–10

- **0–2:** Chỉ nói chung chung về async hoặc debounce, không giải thích completion-order race.
- **3–4:** Nhận ra stale response nhưng chưa giải thích closure/loading race hoặc cách test.
- **5–6:** Giải thích đúng Promise ordering, dùng abort/sequence guard và có test cơ bản.
- **7–8:** Xử lý đầy đủ results/loading/error/cancellation, phân biệt correctness với request reduction và có Playwright/network verification.
- **9–10:** Kết nối browser runtime → React lifecycle → network cancellation → backend telemetry; biết trade-off giữa tự quản lý state và server-state library, đồng thời thiết kế failure semantics rõ ràng.

# Câu 2 — Search index “xanh” nhưng sản phẩm mới publish không xuất hiện trong 20 phút

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, indexing pipeline, eventual consistency, background processing, retries, observability, Application Insights/Kibana, incident investigation, deployment safety

## Bối cảnh

Một e-commerce platform dùng:

- SQL Server làm source of truth cho product/catalog data;
- ASP.NET Core cho admin/product APIs;
- Elasticsearch cho customer-facing search;
- một background indexing worker đọc product changes rồi update Elasticsearch;
- Kibana để quan sát Elasticsearch/logs;
- Application Insights cho API/background dependencies.

Business expectation: product sau khi publish phải searchable trong vòng **2 phút**.

Production incident lúc 10:05:

- merchandisers publish khoảng 8,000 product updates cho campaign mới;
- admin UI xác nhận publish thành công và SQL rows đúng;
- customer search chỉ thấy khoảng 60–70% products mới sau 5 phút;
- một số products xuất hiện sau 20 phút, số khác không xuất hiện cho đến khi support chạy manual reindex;
- Elasticsearch cluster health vẫn `green`;
- CPU cluster không vượt 65%;
- search query latency vẫn bình thường;
- background worker logs có cả `200`, `429`, timeout và một số retry messages;
- queue/backlog metric hiện chưa có;
- một developer cho rằng vì cluster `green` nên Elasticsearch không thể là vấn đề;
- developer khác muốn “giảm `refresh_interval` xuống 1s” để fix ngay.

Bạn vào incident lúc 10:12. Chưa có bằng chứng root cause duy nhất.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào theo flow **impact → stabilize → evidence → competing hypotheses → investigation → root cause → remediation → prevention**, và làm sao phân biệt các khả năng như indexing backlog, retry/throttling, lost change event, refresh visibility, mapping/rejection, worker deployment regression hoặc query/filter mismatch mà không mặc định blame Elasticsearch?

## Câu hỏi làm rõ nên cân nhắc

1. Product change được đưa từ SQL sang worker bằng cơ chế nào: polling, queue, CDC hay outbox-like table?
2. Worker có persisted checkpoint/offset và idempotent indexing theo product/version không?
3. `429` đến từ Elasticsearch bulk indexing hay từ dependency khác, và retry policy có backoff/jitter/bounded attempts không?
4. Elasticsearch bulk response có được inspect từng item hay code chỉ nhìn HTTP status của toàn request?
5. Search index có aliases/versioned indices, ingest pipeline hoặc filter theo `published`, `market`, `language`, `availability` không?

## Gợi ý tư duy

### Gợi ý 1

`green` chủ yếu nói cluster allocation/health ở mức shard, không chứng minh mọi product change đã được index đúng hoặc đã đi qua pipeline.

### Gợi ý 2

Tách **ingestion lag** khỏi **visibility lag**. Nếu document chưa tới Elasticsearch thì đổi refresh interval không giúp gì.

### Gợi ý 3

Với bulk indexing, một request có thể thành công ở transport level nhưng chứa item-level failures. Hãy kiểm tra evidence ở từng stage của pipeline.

## Cấu trúc trả lời đề xuất

1. Xác định scope và freshness SLO violation.
2. Stabilize campaign/search impact với biện pháp có blast radius nhỏ.
3. Chọn một số product IDs đại diện: found, delayed, missing.
4. Trace từng ID từ SQL publish → change record/queue → worker → Elasticsearch document → search query.
5. Xây competing hypotheses và cách falsify từng cái.
6. Kiểm tra backlog, retry, bulk item failures, refresh/index visibility và query filters.
7. Xác định root cause/failure window.
8. Remediate backlog/missing events an toàn, idempotently.
9. Bổ sung durable pipeline, DLQ/reconciliation và observability nếu thiếu.
10. Test burst/retry/deployment/failure paths và theo dõi freshness SLO.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu từ business impact và freshness SLO, không nhảy ngay vào config.
- Không coi cluster `green` là bằng chứng indexing pipeline khỏe.
- Phân biệt document chưa được index với document đã index nhưng chưa visible/searchable.
- Trace product ID end-to-end qua từng stage.
- Kiểm tra bulk item-level errors/rejections thay vì chỉ HTTP status.
- Đề cập backlog/lag metric, retry semantics và idempotency.
- Có reconciliation mechanism để phát hiện lost changes.
- Không giảm refresh interval một cách reflexive nếu chưa xác định visibility lag là bottleneck.

### Điểm cộng

- Phân biệt `429` throttling/rejection với timeout/network errors và áp retry phù hợp.
- Nếu dùng queue, kiểm tra age of oldest message, delivery count, DLQ và processing rate.
- Nếu dùng polling/outbox, kiểm tra checkpoint gaps, transaction boundaries và lease/ownership khi nhiều workers.
- Dùng product version/timestamp để tránh old retry ghi đè document mới hơn.
- Dùng bulk API hiệu quả nhưng limit batch size/concurrency dựa trên measurement.
- Tận dụng alias/versioned index cho reindex lớn thay vì mutate live index mù quáng nếu scenario phù hợp.

### Senior+

- Mô hình hóa search indexing là eventual-consistency projection, không phải source of truth.
- Thiết kế reconciliation job so sánh SQL version/change sequence với Elasticsearch indexed version.
- Có circuit/backpressure để không retry storm khi Elasticsearch đang throttle.
- Có SLO metric `publish_to_searchable_latency` p50/p95/p99 và alert theo oldest lag.
- Phân biệt recovery cho backlog với full reindex; full reindex không phải first response cho mọi incident.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng `refresh_interval`. Symptom “một số product xuất hiện sau 20 phút, một số không xuất hiện cho tới manual reindex” gợi ý có thể có nhiều failure modes. `refresh_interval` chỉ ảnh hưởng thời điểm document đã index trở nên visible cho search; nó không đưa missing product từ SQL vào Elasticsearch.

### 1. Impact và stabilization

Tôi xác định campaign nào bị ảnh hưởng, bao nhiêu products, market/language nào, và business có thể tạm chấp nhận browse/category fallback hay không. Nếu manual reindex nhỏ theo affected IDs có thể chạy idempotently và không gây overload, đó có thể là mitigation nhanh hơn full reindex. Tôi tránh chạy global rebuild ngay khi chưa biết cluster/headroom vì có thể làm incident nặng hơn.

Nếu worker đang retry storm do `429`, tôi có thể giảm indexing concurrency/batch pressure theo evidence để Elasticsearch recover, đồng thời giữ backlog durable. Goal lúc đầu là ngăn mất thêm changes và giảm lag, không phải tối ưu throughput bằng cảm tính.

### 2. Trace representative IDs

Chọn ba nhóm:

- product searchable đúng trong <2 phút;
- product delayed 10–20 phút;
- product missing hoàn toàn.

Với mỗi product ID, trace:

```text
SQL published version/time
→ change event/outbox/queue entry
→ worker receive/start/complete
→ bulk request item result
→ Elasticsearch document _source/version/index
→ search query/filter result
```

Nếu SQL có version `v42` nhưng change record không tồn tại, lỗi nằm trước worker. Nếu change tồn tại nhưng chưa được consume, có backlog/worker throughput issue. Nếu worker log “success” nhưng document absent, cần xem bulk item result/exception handling. Nếu document tồn tại đúng version nhưng query không trả, mới tập trung refresh, alias, mapping, routing hoặc search filters.

### 3. Competing hypotheses

Ví dụ:

**H1 — backlog:** burst 8,000 changes vượt processing throughput. Evidence: oldest pending age tăng, processing rate thấp hơn incoming rate, documents dần xuất hiện theo thời gian.

**H2 — throttle/retry bug:** Elasticsearch trả `429`; retry chạy immediate hoặc capped sai, một số items bị drop sau max attempts. Evidence: rejection rate, repeated IDs, gaps giữa accepted changes và indexed docs.

**H3 — bulk partial failure bị bỏ qua:** HTTP request trả `200`, nhưng `errors: true` và một số items fail do mapping/version/rejection. Nếu code log cả batch là success thì lost products rất plausible.

**H4 — refresh visibility:** document có mặt trong index gần ngay sau publish nhưng chưa searchable cho tới refresh. Evidence: direct GET by document ID thấy document mới trước khi search thấy. Nếu delay 20 phút trong khi refresh interval vài giây/phút, hypothesis yếu đi.

**H5 — query/filter mismatch:** document đã index nhưng field `published`, `market`, `language` hoặc analyzer/mapping làm query loại ra. Evidence: `_source` có doc nhưng filtered search không match.

**H6 — deployment regression/checkpoint:** worker release mới đổi checkpoint/lease hoặc starts from wrong offset; logs/versions correlate với deploy time.

### 4. Đọc bulk response đúng cách

Với Elasticsearch bulk API, transport-level success không đủ. Worker phải inspect từng item. Một simplified pattern:

```csharp
var response = await client.BulkAsync(bulkRequest, ct);

if (!response.IsValidResponse)
{
    // transport/request level failure
}

foreach (var item in response.Items)
{
    if (item.Status is >= 200 and < 300)
        continue;

    // classify retryable vs permanent
    // persist failure / retry / dead-letter appropriately
}
```

API exact shape phụ thuộc Elasticsearch .NET client/version, nên implementation phải theo version docs hiện dùng. Điều quan trọng là semantics: **per-item result**.

Retry cho `429`/transient failure nên exponential backoff + jitter, bounded concurrency, và item vẫn phải nằm trong durable retry path. Permanent mapping/data error nên đi DLQ/failure store với alert, không retry vô hạn.

### 5. Idempotency và ordering

Nếu cùng product có nhiều updates `v40`, `v41`, `v42`, retry cũ không được ghi đè version mới. Có thể persist `productVersion` trong projection và dùng external/version-aware semantics hoặc application guard phù hợp. Ít nhất worker phải idempotent theo product ID + source version.

### 6. Recovery

Sau khi root cause rõ, replay từ durable source cho affected range/IDs. Nếu pipeline không có durable log, chạy reconciliation từ SQL dựa trên `UpdatedAt`/rowversion hoặc campaign scope để tìm records mà Elasticsearch version thiếu/cũ. Full reindex chỉ dùng khi phạm vi/consistency uncertainty đủ lớn và cluster capacity cho phép.

### 7. Long-term prevention

Tôi muốn indexing pipeline có:

- durable change capture/outbox/queue;
- persisted checkpoint hoặc ack semantics;
- idempotent consumer;
- retry classification + backoff;
- DLQ/failure store;
- periodic reconciliation;
- controlled bulk size/concurrency;
- product/source version trong indexed document;
- index alias/versioning cho migrations/reindex nếu cần.

Về observability, metric quan trọng nhất không chỉ là cluster health mà là:

```text
publish_to_searchable_latency
oldest_unindexed_change_age
pending/backlog count
indexing throughput
bulk item failure rate
429/rejection rate
retry count
DLQ count
reconciliation mismatch count
```

Dashboard correlate theo application/index version. Alert khi p95/p99 freshness vượt 2 phút hoặc oldest lag tăng liên tục.

### 8. Testing

- Burst test 10k+ updates với realistic document sizes.
- Failure injection: Elasticsearch trả `429`, timeout, partial bulk failures.
- Restart worker giữa batch và verify không mất/duplicate-corrupt data.
- Out-of-order update test: `v42` xử lý trước rồi `v41` retry sau.
- End-to-end publish → searchable SLO test trên representative environment.

## Mẫu trả lời trong phỏng vấn

“Tôi xem đây là incident của indexing pipeline, không phải mặc định Elasticsearch. `green` chỉ nói cluster/shard health; nó không chứng minh 8,000 product changes đã đi qua worker và searchable trong SLO 2 phút.

Tôi sẽ chọn vài product IDs thuộc nhóm đúng, delayed và missing rồi trace từ SQL publish version → change record/queue → worker → bulk item result → Elasticsearch document → search query. Như vậy tôi tách được ingestion lag, lost event, bulk partial failure và visibility/query issue.

`429` khiến tôi kiểm tra backlog và retry policy. Với Bulk API tôi phải inspect item-level errors; HTTP 200 không có nghĩa mọi document thành công. Nếu document đã có trong index nhưng search chưa thấy thì mới xem refresh interval, alias, mapping hoặc filters. Tôi không giảm refresh xuống 1 giây trước khi chứng minh refresh lag là bottleneck vì nó có thể tăng indexing cost mà không sửa lost changes.

Ngắn hạn tôi replay/reindex đúng affected IDs từ durable source và giảm retry pressure nếu cluster đang throttle. Dài hạn tôi muốn durable change capture, idempotent/version-aware indexing, retry + DLQ, reconciliation và metric `publish_to_searchable_latency` cùng oldest backlog age. Tôi sẽ load/failure test burst, 429, partial bulk failure và worker restart trước release tiếp theo.”

## Câu hỏi đào sâu

1. Nếu pipeline hiện dùng polling theo `UpdatedAt` và hai rows có cùng timestamp ở checkpoint boundary, bạn thiết kế checkpoint thế nào để tránh skip/duplicate?
2. Nếu manual full reindex là cách duy nhất đảm bảo consistency hiện tại nhưng cluster không đủ capacity để reindex trong giờ cao điểm, bạn sẽ phục hồi service thế nào?
3. Tôi phản đối thêm queue/outbox vì system hiện chỉ có 50 product updates/phút bình thường; bạn sẽ quyết định durable pipeline nào là đủ đơn giản dựa trên requirement và failure history ra sao?

## Lỗi trả lời thường gặp

- Thấy cluster `green` rồi loại Elasticsearch/indexing khỏi investigation.
- Giảm `refresh_interval` ngay mà không biết document đã vào index chưa.
- Chỉ xem HTTP status của bulk request, bỏ qua item-level failures.
- Full reindex toàn catalog như phản xạ đầu tiên.
- Không có metric freshness/backlog nên chỉ nhìn CPU và search latency.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất restart/reindex/giảm refresh interval.
- **3–4:** Nhận ra eventual consistency nhưng chưa trace pipeline hoặc phân loại hypotheses.
- **5–6:** Có end-to-end ID tracing, backlog/retry/bulk error investigation và recovery hợp lý.
- **7–8:** Thiết kế idempotency/versioning, DLQ/reconciliation, failure tests và freshness observability.
- **9–10:** Xử lý incident theo evidence, phân biệt ingestion/visibility/query failure chính xác, kiểm soát recovery load và đưa ra pipeline lâu dài vừa đủ phức tạp cho SLO.

# Câu 3 — SQL Server hay Cosmos DB cho activity timeline đa tenant: chọn theo access pattern, không theo “NoSQL scale tốt hơn”

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–45 phút  
**Kỹ năng được đánh giá:** SQL Server, Cosmos DB, data modeling, partition key, consistency, multi-tenancy, query patterns, cost/performance reasoning, ASP.NET Core API design, Azure architecture, observability, migration strategy

## Bối cảnh

Một enterprise employee platform muốn xây **Activity Timeline** mới. Timeline ghi lại các sự kiện người dùng có thể xem trong UI, ví dụ:

- leave request submitted/approved;
- profile updated;
- document uploaded;
- manager comment added;
- timesheet submitted;
- workflow state changed.

Dữ liệu hiện nằm rải trong nhiều SQL Server tables của modular monolith. Team muốn một read model riêng để UI gọi nhanh hơn.

Requirement ban đầu:

- khoảng 250 tenants;
- tenant nhỏ có vài nghìn users, tenant lớn nhất khoảng 80,000 users;
- tổng 15–25 triệu timeline events/tháng;
- retention online 18 tháng;
- API phổ biến nhất:

```http
GET /api/activity?tenantId=42&userId=123&before=...&limit=50
```

- UI chủ yếu đọc newest-first theo user;
- đôi lúc admin cần query theo tenant + event type + khoảng thời gian;
- một số event chứa metadata khác nhau theo type;
- timeline có thể chậm vài giây so với transaction gốc, nhưng không được hiển thị event của tenant khác;
- chưa có requirement join timeline trực tiếp với transactional tables trong cùng request;
- team đang dùng Azure và đã có SQL Server expertise;
- chưa có production experience sâu với Cosmos DB, nhưng nó là công nghệ đang được xem xét;
- team tranh luận:
  - “SQL đã có sẵn, thêm table là đủ”;
  - “25 triệu events/tháng thì phải Cosmos DB mới scale được”;
  - “Dùng cả SQL và Cosmos để an toàn”.

Bạn được yêu cầu đưa ra quyết định kiến trúc có thể defend được, không chỉ chọn công nghệ theo sở thích.

## Câu hỏi chính

Bạn sẽ đánh giá **SQL Server vs Cosmos DB vs một thiết kế hybrid** như thế nào cho Activity Timeline này? Hãy làm rõ access patterns, partitioning, data model, consistency, ingestion, retention, query cost, failure recovery, security, observability và migration/rollout; sau đó chọn một hướng mặc định với các điều kiện rõ ràng có thể khiến bạn đổi quyết định.

## Câu hỏi làm rõ nên cân nhắc

1. Tỷ lệ read/write và p95/p99 latency SLO thực tế là gì?
2. Admin query tenant-wide có tần suất cao đến mức nào và có cần interactive latency không?
3. Tenant/user distribution có skew mạnh hơn số liệu hiện tại không, đặc biệt một user/service account có thể tạo volume cực lớn không?
4. Timeline event có immutable sau khi ghi không, hay cần update/delete theo compliance/user request?
5. Có yêu cầu geo-distribution/multi-region writes hoặc regional data residency trong roadmap 12–24 tháng không?

## Gợi ý tư duy

### Gợi ý 1

25 triệu events/tháng là một volume đáng chú ý, nhưng bản thân con số đó chưa đủ để kết luận SQL hay Cosmos. Hãy tính query shape, retention, index/storage/write rate và operational constraints.

### Gợi ý 2

Với Cosmos DB, partition key là decision trung tâm. Một key tốt phải phân phối writes nhưng vẫn cho dominant reads đi vào ít partitions nhất có thể.

### Gợi ý 3

“Dùng cả hai” chỉ hợp lý nếu mỗi store có ownership/use case rõ. Dual-write trực tiếp từ request path thường tạo consistency/recovery problem nếu không có durable propagation design.

## Cấu trúc trả lời đề xuất

1. Chốt dominant access patterns và SLO.
2. Ước lượng write rate, retained volume và data-size order of magnitude.
3. Mô hình data/event immutability và tenant isolation.
4. Đánh giá SQL design cụ thể, không chỉ nói “relational”.
5. Đánh giá Cosmos partition-key/query/RU/consistency implications.
6. Đánh giá hybrid only-if-needed và propagation semantics.
7. So sánh operational complexity/cost/team expertise.
8. Chọn default và nêu trigger làm thay đổi quyết định.
9. Thiết kế rollout/migration/rebuild của read model.
10. Nêu tests và telemetry chứng minh lựa chọn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận Cosmos chỉ vì data volume lớn.
- Lấy dominant query `tenantId + userId + newest-first` làm trung tâm thiết kế.
- Với SQL, đề xuất schema/index phù hợp, ví dụ composite key/index cho tenant/user/time.
- Với Cosmos, thảo luận partition key thực tế, không chỉ nói “partition theo tenant”.
- Nhận ra tenant lớn có thể tạo hot partition nếu key quá coarse.
- Cân nhắc cross-partition cost cho admin queries.
- Không dual-write trực tiếp vào hai stores mà không có recovery/idempotency.
- Có retention/TTL/archive strategy và tenant isolation/security.
- Có benchmark/load test trước quyết định cuối nếu uncertainty còn lớn.

### Điểm cộng

- Dùng seek/keyset pagination thay vì deep offset.
- Cân nhắc event ID + timestamp tie-breaker để order ổn định.
- SQL có table partitioning/archive chỉ khi evidence cần, không phải mặc định.
- Cosmos có hierarchical/synthetic partitioning strategy phù hợp query pattern nếu SDK/service version hỗ trợ; phải verify current platform behavior trước implementation.
- Đề xuất asynchronous projection từ source transactions qua outbox/change feed-like mechanism phù hợp stack.
- Có rebuild strategy cho read model từ source-of-truth events/data.

### Senior+

- Phân biệt source of truth với disposable/rebuildable read projection.
- Đưa team expertise và operational maturity vào decision, không chỉ benchmark raw throughput.
- Định nghĩa measurable triggers: RU/cost, hot partitions, SQL write/index pressure, geo requirements, tenant growth.
- Thiết kế failure mode khi projection lag mà transaction gốc vẫn thành công.
- Có cost model đủ thực dụng: storage, indexes, read/write volume, backup/restore/rebuild, operational toil.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng việc phản biện hai câu cực đoan: “đã có SQL thì cứ SQL” và “25 triệu events/tháng thì phải NoSQL”. Technology choice phải bám access pattern và operational constraints.

### 1. Ước lượng workload

25 triệu events/tháng trung bình khoảng 9–10 events/giây nếu phân bổ đều, nhưng average gần như vô nghĩa nếu peak campaign/batch tạo burst 20×–100×. Tôi cần peak write rate, event size distribution, read QPS và retention.

18 tháng retention nghĩa là khoảng 270–450 triệu events nếu growth ổn định. Nếu mỗi event sau indexes/storage overhead là vài KB, đây là hàng trăm GB tới hơn TB tùy payload/index. SQL Server hoàn toàn có thể xử lý dataset lớn nếu query/indexing đúng và hardware/tier phù hợp; Cosmos cũng có thể phù hợp nếu partition/access pattern tốt. Cần benchmark bằng representative data.

### 2. Data model chung

Timeline event nên gần immutable:

```text
ActivityEvent
- EventId
- TenantId
- UserId
- EventType
- OccurredAtUtc
- SourceEntityType
- SourceEntityId
- Payload/Metadata
- SourceVersion
```

Dominant query:

```text
TenantId = T
UserId = U
ORDER BY OccurredAtUtc DESC, EventId DESC
LIMIT 50
```

Dùng cursor `(OccurredAtUtc, EventId)` cho next page.

### 3. Nếu dùng SQL Server

Một schema có thể là:

```sql
CREATE TABLE ActivityEvent
(
    EventId UNIQUEIDENTIFIER NOT NULL,
    TenantId INT NOT NULL,
    UserId BIGINT NOT NULL,
    EventType VARCHAR(64) NOT NULL,
    OccurredAtUtc DATETIME2(3) NOT NULL,
    SourceEntityType VARCHAR(64) NULL,
    SourceEntityId VARCHAR(128) NULL,
    Payload NVARCHAR(MAX) NULL,
    SourceVersion BIGINT NULL,
    CONSTRAINT PK_ActivityEvent
        PRIMARY KEY (TenantId, UserId, OccurredAtUtc, EventId)
);
```

Exact clustered/nonclustered arrangement cần benchmark theo insert pattern và storage. Query index có thể xoay quanh:

```sql
(TenantId, UserId, OccurredAtUtc DESC, EventId DESC)
```

Admin query `TenantId + EventType + time` có thể cần secondary index nếu đủ frequent/value. Tôi không tạo tất cả indexes trước vì mỗi index tăng write amplification và storage.

Ưu điểm SQL:

- team expertise cao;
- operational tooling/backup/monitoring sẵn;
- query admin linh hoạt;
- transactionally strong nếu cần;
- dễ bắt đầu với một read-model table riêng.

Rủi ro:

- hundreds of millions rows + multiple indexes có thể tăng storage/maintenance;
- retention/delete lớn cần strategy;
- burst ingestion và hot index pages cần load test;
- nếu workload sau này cần multi-region active-active hoặc massive horizontal write scale, SQL topology có thể phức tạp hơn.

Có thể partition/archive theo time nếu maintenance/retention evidence cần; không nên thêm partitioning chỉ vì row count nghe lớn.

### 4. Nếu dùng Cosmos DB

Cosmos hợp khi access pattern document-centric, scale-out/high write, low-latency partition-local reads và/hoặc multi-region requirements quan trọng. Nhưng partition key là critical.

Chỉ dùng `/tenantId` có vấn đề: tenant 80k users có thể trở thành logical partition nóng/lớn theo thời gian. Dominant read luôn có tenant + user, nên partition strategy nên cân nhắc user dimension.

Một synthetic logical key kiểu:

```text
partitionKey = tenantId:userId
```

làm user timeline reads rất hiệu quả vì single partition. Nhưng admin query toàn tenant theo event type/time sẽ fan out qua nhiều user partitions và tốn RU hơn. Nếu admin query hiếm/chấp nhận async/reporting, đây có thể là trade-off tốt.

Nếu platform hiện tại hỗ trợ hierarchical partition keys phù hợp, có thể đánh giá `(tenantId, userId)` semantics, nhưng phải verify official current Cosmos DB behavior/limits trước implementation. Không nên dựa trên memory về service feature.

Document:

```json
{
  "id": "event-id",
  "tenantId": "42",
  "userId": "123",
  "pk": "42:123",
  "eventType": "LeaveApproved",
  "occurredAt": "2026-09-12T10:20:00Z",
  "sourceEntityId": "leave-987",
  "sourceVersion": 12,
  "payload": { }
}
```

TTL có thể giúp retention 18 tháng nếu compliance semantics phù hợp; nhưng archive/audit requirement phải làm rõ trước khi auto-delete.

Ưu điểm Cosmos:

- horizontal partitioning built-in;
- predictable partition-local access nếu key tốt;
- schema-flexible payload;
- TTL/multi-region capabilities có thể hữu ích.

Rủi ro:

- RU cost phụ thuộc query/index/document size;
- bad partition key tạo hot partitions;
- tenant-wide cross-partition admin queries có thể đắt;
- team chưa có deep ops experience;
- index policy/default indexing có thể tăng write RU nếu payload lớn;
- consistency setting cần align product requirement.

### 5. Ingestion và consistency

Timeline là read projection, nên transaction gốc không nhất thiết phải block chờ timeline write. Tôi không làm:

```text
SQL business transaction
→ commit
→ synchronous Cosmos/SQL timeline write
```

rồi giả định cả hai atomic.

Tốt hơn, business transaction persist một durable change/outbox record cùng transaction. Background projector tạo timeline event idempotently. Nếu projector lag vài giây, product requirement cho phép. Nếu projector fail, business transaction vẫn đúng; timeline có lag metric và replay/reconciliation.

Nếu monolith hiện không cần messaging platform, SQL outbox + `BackgroundService` polling có thể đủ. Nếu throughput/decoupling/reliability requirements sau này cần Service Bus, có thể thêm sau. Không thêm broker chỉ để làm architecture đẹp.

### 6. Hybrid

“Dùng cả SQL và Cosmos để an toàn” không phải design. Hybrid chỉ có ý nghĩa nếu roles khác nhau, ví dụ:

- SQL giữ source-of-truth business data;
- Cosmos giữ disposable timeline projection;

hoặc:

- SQL timeline phục vụ admin/compliance reporting;
- Cosmos user timeline phục vụ high-scale read path.

Nhưng nếu cùng một timeline phải write vào cả hai stores chỉ để dự phòng, complexity reconciliation/consistency tăng mạnh. Tôi cần business reason trước khi trả chi phí đó.

### 7. Recommendation mặc định

Với dữ liệu hiện có, tôi có xu hướng **bắt đầu bằng SQL Server read-model table riêng** vì:

- dominant query đơn giản và indexable;
- team expertise/operations mạnh SQL;
- chưa có geo/multi-region requirement;
- throughput trung bình chưa chứng minh cần distributed database;
- admin tenant-wide queries linh hoạt hơn;
- incremental delivery nhanh hơn.

Nhưng đây không phải kết luận cố định. Trước production, tôi load test với 300–500 triệu representative rows hoặc scale model tương đương, peak ingestion, concurrent reads và retention operations.

Tôi sẽ đổi sang/đánh giá Cosmos nghiêm túc nếu evidence cho thấy:

- SQL write/index maintenance hoặc storage economics không đạt SLO/cost;
- tenant/user access pattern rất partition-friendly;
- growth/peak write tăng lớn;
- multi-region low-latency/availability trở thành requirement;
- organization có đủ Cosmos expertise/observability/cost controls.

Ngược lại, nếu Cosmos benchmark cho RU/cross-partition admin query cost cao hoặc hot-key risk, SQL tiếp tục là lựa chọn hợp lý.

### 8. Security và tenant isolation

API không nhận `tenantId` rồi tin client. Tenant phải derive/authorize từ authenticated identity/context. Repository/query bắt buộc tenant predicate. Với Cosmos, partition key construction cũng phải server-controlled. Telemetry không log sensitive payload.

### 9. Observability

Nếu SQL:

- write/read latency;
- rows/sec;
- index usage/size;
- logical reads;
- waits/blocking;
- deadlocks;
- storage growth;
- projector lag.

Nếu Cosmos:

- RU/request;
- throttled `429` rate;
- normalized RU by operation;
- hot partition indicators;
- latency by partition/query;
- cross-partition query cost;
- projector lag.

Cả hai cần `publish_to_timeline_latency`, failed projection count, replay count và tenant-isolation tests.

### 10. Testing và rollout

- Generate representative event distribution including largest tenant/user skew.
- Load test peak writes + concurrent timeline reads.
- Verify cursor pagination correctness với equal timestamps/concurrent inserts.
- Failure test projector restart/duplicate delivery/out-of-order replay.
- Security test cross-tenant access.
- Run shadow projection hoặc small tenant canary trước migration toàn bộ.
- Giữ read model rebuildable để rollback hoặc chuyển store dễ hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn Cosmos chỉ vì 25 triệu events/tháng. Tôi bắt đầu từ access pattern: gần như mọi user request là `tenantId + userId`, newest-first, 50 items; admin tenant-wide query ít hơn. Tôi cần peak write/read QPS, event size, skew và SLO rồi benchmark với retention khoảng vài trăm triệu rows.

Nếu SQL, tôi có thể tạo read-model table riêng với composite index theo `TenantId, UserId, OccurredAtUtc, EventId` và dùng keyset pagination. Team đã có SQL expertise nên đây là baseline có operational risk thấp. Tôi chỉ thêm secondary index cho admin query nếu telemetry chứng minh cần.

Nếu Cosmos, partition key là decision chính. `/tenantId` có thể tạo hot partition cho tenant lớn; key kiểu `tenantId:userId` phù hợp dominant user timeline nhưng khiến tenant-wide admin query thành cross-partition. Tôi phải đo RU và query cost, không chỉ nói NoSQL scale tốt.

Timeline nên là asynchronous projection từ source transactions qua durable outbox/change mechanism và idempotent projector; không dual-write trực tiếp SQL + Cosmos trong request path. Nếu projector lag, transaction gốc vẫn đúng và chúng ta đo `publish_to_timeline_latency`.

Với requirement hiện tại tôi nghiêng SQL trước vì đơn giản, team hiểu sâu và chưa có multi-region driver. Tôi sẽ đổi quyết định nếu benchmark cho thấy SQL không đạt SLO/cost hoặc roadmap có multi-region/horizontal-scale requirement đủ mạnh. Decision phải có measurable triggers, không phải preference.”

## Câu hỏi đào sâu

1. Nếu một service account của tenant lớn tạo 20% toàn bộ events và partition key là `tenantId:userId`, bạn xử lý hot partition risk thế nào mà vẫn giữ user-timeline reads hiệu quả?
2. Nếu Product yêu cầu admin query “mọi security events của tenant trong 90 ngày” dưới 2 giây, recommendation SQL/Cosmos/indexing của bạn thay đổi ra sao?
3. Tôi phản đối SQL vì “đã biết sau 18 tháng sẽ có hơn 400 triệu rows, thiết kế dùng SQL bây giờ chỉ tạo migration debt”; bạn sẽ bảo vệ hay thay đổi quyết định dựa trên evidence nào?

## Lỗi trả lời thường gặp

- “Data lớn → Cosmos” mà không tính access pattern/partition key.
- “Đã có SQL → cứ dùng SQL” mà không load test retained volume/peak write.
- Partition Cosmos chỉ theo tenant dù có tenant cực lớn, không phân tích hot partition/cross-partition trade-off.
- Dual-write hai stores trong request path mà không có recovery strategy.
- Bỏ qua retention, tenant isolation, projector lag và cost telemetry.

## Thang điểm 0–10

- **0–2:** Chọn công nghệ theo khẩu hiệu, không làm rõ workload/access pattern.
- **3–4:** So sánh SQL/Cosmos ở mức feature nhưng thiếu partition/index/consistency details.
- **5–6:** Có data model, SQL index, Cosmos partition trade-off, ingestion và tests hợp lý.
- **7–8:** Có benchmark/cost/operations reasoning, asynchronous projection, failure recovery và measurable decision triggers.
- **9–10:** Thể hiện architecture judgment đầy đủ: dominant access pattern → partition/index design → consistency/failure model → operational complexity → evidence-based choice, đồng thời tránh complexity không cần thiết.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `async`/Promise không đảm bảo completion order; correctness khi nhiều requests overlap cần cancellation hoặc request identity rõ ràng.
- Production search incident phải trace từng entity qua toàn bộ indexing pipeline; cluster health không thay thế freshness/ingestion evidence.
- Elasticsearch search projection là eventually consistent read model, nên retry, idempotency, per-item failure handling và reconciliation quan trọng ngang với query performance.
- Database choice phải bắt đầu từ access pattern, partition/index design, consistency và operational constraints; data volume một mình không quyết định SQL hay NoSQL.
- Read models nên có khả năng rebuild/replay và có telemetry cho projection lag thay vì trở thành hidden source of truth.

## Mẫu tư duy cần nhớ

- **Order of start ≠ order of completion** — mọi asynchronous workflow cần xác định stale/duplicate result semantics.
- **Trace one entity end-to-end** — khi pipeline phân tán lỗi, theo một ID xuyên từng stage để thu hẹp hypothesis.
- **Separate ingestion from visibility** — dữ liệu chưa được ghi và dữ liệu đã ghi nhưng chưa visible là hai failure class khác nhau.
- **Access pattern before storage technology** — chọn index/partition/store dựa trên query shape và failure model.
- **Measure before adding complexity** — benchmark workload thực tế trước khi thêm distributed database, queue hoặc architecture layer mới.
