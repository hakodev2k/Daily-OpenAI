# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để gửi thông báo cho nhân viên. Nhiều Hangfire worker có thể chạy song song. Khi production bị timeout hoặc worker restart, một số người dùng nhận cùng thông báo 2–3 lần. Bảng `Notifications` lưu trạng thái gửi; provider bên ngoài không hỗ trợ transaction chung với database.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly INotificationClient _client;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        INotificationClient client,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
    }

    public async Task SendAsync(Guid notificationId)
    {
        var notification = await _db.Notifications
            .FirstOrDefaultAsync(x => x.Id == notificationId);

        if (notification == null || notification.Status == "Sent")
            return;

        notification.Status = "Processing";
        await _db.SaveChangesAsync();

        try
        {
            await _client.SendAsync(
                notification.Recipient,
                notification.Subject,
                notification.Body);

            notification.Status = "Sent";
            notification.SentAt = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Failed to send notification {NotificationId} to {Recipient}",
                notification.Id,
                notification.Recipient);

            notification.Status = "Pending";
            await _db.SaveChangesAsync();
            throw;
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các lỗi correctness.
2. Phân tích concurrency, retry và idempotency.
3. Giải thích vì sao duplicate có thể xuất hiện dù đã kiểm tra `Status == "Sent"`.
4. Ưu tiên vấn đề theo mức độ ảnh hưởng.
5. Đề xuất implementation tốt hơn.
6. Mô tả cách kiểm thử dưới concurrent execution và failure.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai worker đọc cùng bản ghi `Pending` gần như đồng thời thì điều gì xảy ra?
- Nếu provider đã nhận request nhưng process chết trước `SaveChangesAsync`, retry sẽ làm gì?
- `Processing` có thực sự là một distributed lock không?
- Cancellation và timeout của outbound request nên được xử lý thế nào?
- Có thể đạt exactly-once end-to-end khi database và provider là hai hệ thống độc lập không?

## Gợi ý

### Gợi ý 1

Hãy tách bài toán thành hai cửa sổ race: trước khi gọi provider và sau khi provider đã nhận request.

### Gợi ý 2

Một state flag chỉ hữu ích khi việc claim được thực hiện atomically; side effect bên ngoài còn cần idempotency key hoặc cơ chế reconciliation.

## Kết quả code review tham khảo

### 1. Check-then-update không atomic

**Problem:** Nhiều worker có thể cùng đọc `Pending`, sau đó đều đổi thành `Processing`.  
**Why:** Query và update là các operation riêng biệt, không có conditional atomic claim.  
**Impact:** Cùng notification có thể được gửi nhiều lần.  
**Severity:** Critical  
**Fix:** Claim bằng conditional update, concurrency token hoặc transaction/locking phù hợp; chỉ worker thắng claim mới tiếp tục.

### 2. Crash window sau side effect

**Problem:** Provider có thể gửi thành công nhưng process chết trước khi DB được đánh dấu `Sent`.  
**Why:** DB và external provider không cùng transaction.  
**Impact:** Hangfire retry và gửi lại cùng notification.  
**Severity:** Critical  
**Fix:** Nếu provider hỗ trợ idempotency key, truyền stable key như `notificationId`; nếu không, thiết kế at-least-once + deduplication/reconciliation theo khả năng của hệ thống.

### 3. `Processing` có thể bị kẹt

**Problem:** Worker chết sau khi set `Processing`.  
**Impact:** Notification có thể không bao giờ được xử lý lại nếu không có lease/recovery policy.  
**Severity:** High  
**Fix:** Lưu `ProcessingUntil`, attempt/version hoặc lease expiration; job khác reclaim các lease hết hạn.

### 4. Catch mọi exception rồi chuyển về `Pending`

**Problem:** Permanent errors cũng được retry như transient errors.  
**Impact:** Retry storm, tốn tài nguyên và có thể spam provider.  
**Severity:** High  
**Fix:** Phân loại transient/permanent; permanent failure chuyển `Failed`/dead-letter, transient để retry có backoff.

### 5. Không truyền cancellation token

**Problem:** DB và outbound I/O không nhận cancellation token.  
**Impact:** Shutdown kéo dài, request tiếp tục chạy khi job đã bị hủy; failure semantics khó kiểm soát.  
**Severity:** Medium  
**Fix:** Truyền cancellation token khi API/framework integration cho phép và xác định rõ behavior khi cancellation xảy ra quanh side effect.

### 6. Log có dữ liệu người nhận

**Problem:** `Recipient` có thể là PII.  
**Impact:** Sensitive data tồn tại trong centralized logs.  
**Severity:** Medium  
**Fix:** Log identifier không nhạy cảm hoặc mask/hash theo policy.

### 7. String state dễ sai và thiếu state-machine invariant

**Problem:** `"Sent"`, `"Processing"`, `"Pending"` là magic strings và transition không được bảo vệ.  
**Impact:** Invalid transition, typo và maintenance risk.  
**Severity:** Low/Medium  
**Fix:** Enum/value mapping cùng conditional transitions và database constraints khi phù hợp.

## Phiên bản code đề xuất

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly INotificationClient _client;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        INotificationClient client,
        TimeProvider timeProvider,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _client = client;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task SendAsync(Guid id, CancellationToken ct)
    {
        var now = _timeProvider.GetUtcNow();
        var leaseUntil = now.AddMinutes(5);

        var claimed = await _db.Notifications
            .Where(x => x.Id == id &&
                        (x.Status == NotificationStatus.Pending ||
                         (x.Status == NotificationStatus.Processing &&
                          x.ProcessingUntil < now)))
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, NotificationStatus.Processing)
                .SetProperty(x => x.ProcessingUntil, leaseUntil)
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1), ct);

        if (claimed != 1)
            return;

        var item = await _db.Notifications
            .AsNoTracking()
            .SingleAsync(x => x.Id == id, ct);

        try
        {
            await _client.SendAsync(
                item.Recipient,
                item.Subject,
                item.Body,
                idempotencyKey: id.ToString("N"),
                cancellationToken: ct);

            await _db.Notifications
                .Where(x => x.Id == id && x.Status == NotificationStatus.Processing)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, NotificationStatus.Sent)
                    .SetProperty(x => x.SentAt, _timeProvider.GetUtcNow())
                    .SetProperty(x => x.ProcessingUntil, (DateTimeOffset?)null), ct);
        }
        catch (PermanentNotificationException ex)
        {
            await MarkFailedAsync(id, ex.Message, ct);
            throw;
        }
    }

    private Task MarkFailedAsync(Guid id, string reason, CancellationToken ct) =>
        _db.Notifications
            .Where(x => x.Id == id)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, NotificationStatus.Failed)
                .SetProperty(x => x.LastError, reason), ct);
}
```

Giải pháp trên giả định provider hỗ trợ idempotency key. Nếu provider không hỗ trợ, không nên tuyên bố exactly-once; cần chấp nhận delivery semantics thực tế và thêm reconciliation/deduplication nếu business cho phép.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi database là coordination point. Lease giúp recovery nhưng cần chọn timeout đủ lớn và xử lý job chạy lâu. Distributed lock có thể giảm concurrent execution nhưng không tự giải quyết crash window sau external side effect. Outbox hữu ích khi cần atomically lưu intent cùng business transaction, nhưng vẫn không tự biến external provider thành exactly-once nếu consumer/provider không deduplicate.

## Cách kiểm thử

1. Chạy 20 invocation đồng thời cho cùng ID và xác minh chỉ một worker claim được record.
2. Mô phỏng provider thành công rồi process exception trước DB completion; xác minh retry dùng cùng idempotency key.
3. Tạo `Processing` lease hết hạn và xác minh job có thể reclaim.
4. Provider trả transient timeout nhiều lần: xác minh retry/backoff và không chuyển permanent failure sai trạng thái.
5. Provider trả permanent validation error: xác minh chuyển `Failed`, không retry vô hạn.

## Quan sát trong production

Theo dõi `notification_attempt_total`, duplicate/idempotency-hit count nếu provider cung cấp, thời gian ở trạng thái `Processing`, số lease hết hạn, retry count, failure theo provider/error class và latency outbound. Trace nên nối Hangfire job → DB claim → provider call bằng notification ID/correlation ID, tránh ghi PII thô.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giải quyết phần nào của bài toán này và phần nào không?
2. Nếu provider không hỗ trợ idempotency key, bạn thiết kế business semantics ra sao?
3. Nếu một notification mất 10 phút để gửi nhưng lease chỉ 5 phút, thiết kế trên có thể thất bại thế nào?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log: authorization và SQL injection

**Chủ đề:** Authorization, input validation, SQL correctness, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một internal ASP.NET Core API cho phép support team tìm audit log theo tenant và từ khóa. API chạy trong multi-tenant SaaS. Sau một đợt pentest, đội security nghi ngờ người dùng có thể truy cập log của tenant khác và có khả năng thao túng SQL. Production cũng gặp query chậm khi từ khóa rộng.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        int page = 1,
        int pageSize = 100)
    {
        var sql = $@"
            SELECT Id, TenantId, UserEmail, Action, Payload, CreatedAt
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'";

        if (!string.IsNullOrWhiteSpace(keyword))
            sql += $" AND (Action LIKE '%{keyword}%' OR Payload LIKE '%{keyword}%')";

        sql += $" ORDER BY CreatedAt DESC OFFSET {(page - 1) * pageSize} ROWS FETCH NEXT {pageSize} ROWS ONLY";

        _logger.LogInformation("Audit search SQL: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .AsNoTracking()
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Nhiệm vụ của ứng viên

1. Tìm correctness và security issues.
2. Xác định authorization, injection và data-exposure risks.
3. Giải thích production impact.
4. Ưu tiên remediation.
5. Đề xuất implementation an toàn hơn.
6. Mô tả security/integration/performance tests.
7. Đề xuất logs, traces và metrics phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` chứng minh được điều gì và chưa chứng minh điều gì?
- `tenantId` lấy từ query string có phải trusted tenant context không?
- Những phần nào của SQL chịu ảnh hưởng bởi input của người dùng?
- `Payload` và `UserEmail` có nên luôn được trả về không?
- `pageSize` không giới hạn ảnh hưởng gì đến hệ thống?

## Kết quả code review tham khảo

### 1. SQL injection

**Problem:** `tenantId`, `keyword`, pagination values được nối trực tiếp vào SQL.  
**Why:** `FromSqlRaw` nhận chuỗi SQL đã được interpolation thủ công.  
**Impact:** Query manipulation, data disclosure hoặc phá vỡ tính toàn vẹn tùy quyền DB account.  
**Severity:** Critical  
**Fix:** Dùng LINQ/parameterized SQL; không concatenate user input.

### 2. Broken tenant authorization

**Problem:** Caller tự truyền `tenantId`; `[Authorize]` chỉ yêu cầu principal đã authenticated theo policy mặc định, không chứng minh quyền với tenant được yêu cầu.  
**Impact:** Cross-tenant data exposure.  
**Severity:** Critical  
**Fix:** Resolve tenant từ trusted claims/context hoặc resource-based authorization; không tin query parameter làm authorization source.

### 3. Trả dữ liệu nhạy cảm quá rộng

**Problem:** `UserEmail` và toàn bộ `Payload` được trả mặc định.  
**Impact:** PII/secrets có thể bị lộ cho support role không cần chúng.  
**Severity:** High  
**Fix:** DTO tối thiểu, field-level policy/redaction; endpoint chi tiết riêng nếu cần.

### 4. Ghi toàn bộ SQL vào log

**Problem:** SQL chứa tenant ID và keyword; keyword có thể chứa dữ liệu nhạy cảm.  
**Impact:** Sensitive data lan sang log store và tăng injection/log-forging concerns ở downstream tooling.  
**Severity:** High  
**Fix:** Structured log chỉ metadata cần thiết, không log raw query/user payload.

### 5. Pagination không validate

**Problem:** `page <= 0`, `pageSize <= 0` hoặc cực lớn.  
**Impact:** lỗi query, excessive memory/DB load, abuse.  
**Severity:** Medium  
**Fix:** Validate và clamp page size; dùng cursor/keyset pagination nếu dataset lớn và navigation phù hợp.

### 6. `%keyword%` trên cột lớn có thể rất đắt

**Problem:** Leading wildcard và tìm trong `Payload` có thể buộc scan lớn.  
**Impact:** DB CPU/I/O cao, latency tăng.  
**Severity:** Medium  
**Fix:** Giới hạn searchable fields, index/search strategy phù hợp, full-text/search engine khi requirements cần; đo execution plan trước khi chọn.

### 7. Thiếu cancellation token

**Problem:** Request bị client hủy nhưng DB query có thể tiếp tục.  
**Impact:** Lãng phí DB resources khi query đắt.  
**Severity:** Low/Medium  
**Fix:** Nhận `CancellationToken` và truyền vào async query.

## Phiên bản code đề xuất

```csharp
[HttpGet("search")]
[Authorize(Policy = "AuditReader")]
public async Task<ActionResult<IReadOnlyList<AuditRowDto>>> Search(
    string? keyword,
    int page = 1,
    int pageSize = 50,
    CancellationToken ct = default)
{
    if (page < 1)
        return BadRequest("page must be >= 1");

    pageSize = Math.Clamp(pageSize, 1, 100);

    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x => x.Action.Contains(term));
    }

    var rows = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .Select(x => new AuditRowDto(
            x.Id,
            x.Action,
            x.CreatedAt))
        .ToListAsync(ct);

    _logger.LogInformation(
        "Audit search completed for tenant {TenantId}; page={Page}; pageSize={PageSize}; hasKeyword={HasKeyword}",
        tenantId,
        page,
        pageSize,
        !string.IsNullOrWhiteSpace(keyword));

    return Ok(rows);
}
```

Giải pháp giả định claim `tenant_id` được phát hành từ identity/trusted application context và policy `AuditReader` được cấu hình đúng. Nếu người dùng có thể thuộc nhiều tenant, cần explicit tenant selection cộng resource-based authorization thay vì chỉ lấy một claim.

## Trade-offs

LINQ giúp parameterization và maintainability nhưng không tự giải quyết query design hoặc authorization. Offset pagination đơn giản nhưng chi phí tăng ở page sâu; keyset pagination tốt hơn cho feed lớn nhưng không thuận tiện khi người dùng cần nhảy trực tiếp đến page N. Tìm kiếm substring đơn giản có thể đủ cho volume nhỏ; volume lớn hoặc search phức tạp có thể cần database full-text capability hay search subsystem riêng.

## Cách kiểm thử

1. Security test: authenticated user tenant A yêu cầu dữ liệu tenant B và phải không thể lấy được dữ liệu B.
2. Injection payload trong keyword/tenant-related inputs không được thay đổi query semantics.
3. `pageSize` âm, zero, cực lớn và page không hợp lệ được xử lý có kiểm soát.
4. Integration test xác minh response không chứa `Payload`/email khi role chỉ cần summary.
5. Load/database test với dataset lớn, kiểm tra latency và execution plan cho search phổ biến.

## Quan sát trong production

Theo dõi audit-search latency, rows scanned/returned nếu có telemetry DB, timeout count, authorization denial count, query failure rate và page-size distribution. Alert khi latency/DB CPU tăng bất thường. Security audit log nên ghi actor ID, tenant/resource, action và outcome nhưng không ghi raw payload hoặc search SQL.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một support engineer hợp lệ cần truy cập nhiều tenant, bạn thiết kế authorization thế nào?
2. Khi nào bạn chọn keyset pagination thay vì offset pagination?
3. Nếu business bắt buộc search toàn bộ JSON payload, bạn sẽ đánh giá những phương án storage/search nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào trust boundaries ở hai dạng khác nhau: concurrency boundary giữa nhiều worker và security boundary giữa caller, tenant, database. Một status flag không tạo ra atomicity; authentication không tạo ra resource authorization. Với side effect bên ngoài, retry phải được thiết kế cùng idempotency và failure recovery. Với dữ liệu multi-tenant, tenant context phải đến từ nguồn đáng tin và query phải parameterized.

## Mẫu tư duy cần nhớ

- Check-then-act dưới concurrency cần được thay bằng atomic state transition khi correctness phụ thuộc vào exclusivity.
- Design retries together with idempotency; đừng tuyên bố exactly-once nếu các hệ thống không hỗ trợ semantics đó.
- Authentication trả lời “ai”, authorization phải trả lời “được làm gì trên resource nào”.
- Treat user input, logs và outbound data như các trust boundary riêng biệt.
- Observability là một phần của correctness: phải đo retry, lease, authorization denial, query latency và failure class.
