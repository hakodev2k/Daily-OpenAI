# Câu 1 — CancellationToken đã “cancel” nhưng SQL vẫn chạy và connection pool vẫn nghẽn

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C# async/await, CancellationToken, ASP.NET Core request lifecycle, EF Core, SQL Server, connection pooling, HTTP cancellation, observability

## Bối cảnh

Một ASP.NET Core .NET 8 API phục vụ trang tìm kiếm đơn hàng. UI React huỷ request cũ khi người dùng đổi filter nhanh. Controller nhận `CancellationToken` và gọi service:

```csharp
[HttpGet]
public async Task<IReadOnlyList<OrderDto>> Search(
    [FromQuery] SearchRequest request,
    CancellationToken cancellationToken)
{
    return await _service.SearchAsync(request, cancellationToken);
}

public async Task<IReadOnlyList<OrderDto>> SearchAsync(
    SearchRequest request,
    CancellationToken cancellationToken)
{
    var query = _db.Orders
        .AsNoTracking()
        .Where(x => x.CreatedAt >= request.From &&
                    x.CreatedAt < request.To);

    var rows = await query.ToListAsync();

    return rows.Select(Map).ToList();
}
```

Production cho thấy browser thường báo request bị cancelled, nhưng SQL dependency trong Application Insights đôi lúc vẫn chạy 20–30 giây. Khi nhiều người đổi filter liên tục, DB CPU tăng, số query đồng thời tăng và một số API khác bắt đầu timeout. Team cho rằng “ASP.NET Core đã có cancellation token nên query phải tự dừng”. Một đề xuất khác là bọc `ToListAsync()` trong `Task.Run` để cancellation hoạt động tốt hơn.

Chưa rõ token có được truyền xuyên suốt call chain hay không, SQL query có đang bị blocking hay không, provider xử lý cancellation ở mức nào, và query shape/index hiện tại có phù hợp không.

## Câu hỏi chính

Hãy giải thích từ lúc client ngắt request đến lúc database command kết thúc: cancellation được biểu diễn và truyền như thế nào, vì sao có `CancellationToken` ở controller không đồng nghĩa mọi downstream operation tự bị huỷ, assumption nào về `Task.Run` là sai, production impact là gì, và bạn sẽ chứng minh từng phần của call chain ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. Token từ action có thực sự là request-abort token và service/repository có truyền nó tới mọi async I/O không?
2. Query 20–30 giây là do execution cost, lock/blocking, connection acquisition hay dependency khác?
3. Business có chấp nhận partial result không, hay cancellation phải dừng toàn bộ operation?
4. Có timeout riêng ở HTTP, EF/database command và reverse proxy không?
5. Search endpoint có giới hạn date range, pagination và query concurrency không?

## Gợi ý tư duy

### Gợi ý 1

Cancellation trong .NET là cooperative. Việc một token chuyển sang trạng thái cancelled không tự “kill” mọi công việc đang chạy.

### Gợi ý 2

Theo dõi token từ request boundary đến API thực sự hỗ trợ cancellation. Trong đoạn code, hãy nhìn kỹ overload của operation I/O.

### Gợi ý 3

Cancellation không thay thế query optimization, timeout hay capacity control. Một query được cancel muộn vẫn có thể tiêu tốn tài nguyên đáng kể.

## Cấu trúc trả lời đề xuất

1. Làm rõ semantics của client abort và SLA.
2. Trace token xuyên call chain.
3. Giải thích cooperative cancellation và async I/O.
4. Phân biệt cancellation với timeout.
5. Kiểm tra SQL execution/blocking/index/query shape.
6. Sửa propagation và đặt guardrails.
7. Test client-abort/failure path.
8. Correlate request, dependency và DB evidence sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Nhận ra `ToListAsync()` hiện không nhận `cancellationToken`.
- Hiểu cancellation là cooperative, downstream API phải nhận/quan sát token.
- Không dùng `Task.Run` để biến database I/O thành “cancellable”.
- Phân biệt request cancellation, command timeout và query performance.
- Điều tra query/DB evidence thay vì coi cancellation là giải pháp performance.
- Propagate token qua service/repository tới EF Core async operation phù hợp.

### Điểm cộng

- Không catch `OperationCanceledException` rồi log như server error thông thường.
- Xem xét bounded input: date range, pagination, request rate/concurrency.
- Correlate Application Insights dependency duration với SQL execution plan, waits/blocking và cancellation events.
- Nhận ra client đã bỏ response không có nghĩa server-side work đã kết thúc ngay tức thì.

### Senior+

- Giải thích rằng cancellation request tới provider/database vẫn có race và phụ thuộc operation/provider; không xây correctness dựa trên giả định “cancel luôn thành công tức thì”.
- Tách ba control plane: user/request cancellation, deadline/timeout và resource/capacity protection.
- Nếu operation có side effects, xác định transaction semantics thay vì giả định cancellation rollback mọi thứ.

## Hướng giải quyết tham khảo

Đầu tiên, token ở action chỉ có giá trị nếu được truyền xuống các operation hỗ trợ cancellation. Trong code hiện tại, service nhận token nhưng `ToListAsync()` không dùng overload nhận token, nên database operation không được yêu cầu huỷ qua call đó. Sửa tối thiểu là `await query.ToListAsync(cancellationToken)`, đồng thời audit toàn bộ call chain để tránh “token parameter chỉ để trang trí”.

`async/await` và cancellation là hai cơ chế khác nhau. `async` giúp không block thread trong khi chờ I/O; cancellation là tín hiệu cooperative. `Task.Run` quanh EF query không làm SQL command có semantics cancellation tốt hơn và còn có thể tiêu thụ ThreadPool không cần thiết.

Tuy nhiên, propagation đúng chưa đủ. Cần xác định vì sao query mất 20–30 giây: execution plan xấu, scan lớn, blocking, parameter/data distribution, thiếu pagination, connection pool wait hay resource saturation. Dùng request/dependency correlation trong Application Insights, SQL telemetry/execution plan và waits phù hợp. Nếu người dùng có thể query khoảng thời gian rất lớn, đặt validation/pagination dựa trên requirement.

Timeout là guardrail riêng: request deadline và database command timeout phải được chọn có chủ đích. Cancellation do client abort giúp giải phóng work không còn giá trị, nhưng không phải performance strategy. Nếu query thường xuyên vượt SLA ngay cả khi không cancel, phải sửa query/index/data access hoặc workload design.

Test bằng integration test tạo request dài rồi abort, xác minh service quan sát cancellation và dependency kết thúc hợp lý; thêm test cho token đã cancelled; load test với rapid filter changes; đồng thời kiểm tra không biến cancellation thành hàng loạt error alerts. Nếu DB command vẫn kéo dài, trace xuống provider/SQL để phân biệt cancellation propagation failure với DB-side behavior.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không giả định token ở controller tự huỷ mọi thứ. Cancellation trong .NET là cooperative: token phải được truyền tới operation hỗ trợ nó. Ở đây `ToListAsync()` không nhận token, nên trước hết em sửa propagation tới EF Core và audit toàn call chain. Em cũng không dùng `Task.Run` vì đây là database I/O; nó không giải quyết command cancellation và có thể làm ThreadPool tệ hơn. Sau đó em tách cancellation khỏi timeout và performance: em correlate request abort với Application Insights dependency, kiểm tra SQL execution plan, waits/blocking, query range và pagination. Nếu query bản thân mất 30 giây thì cancellation chỉ giảm wasted work, không chữa root cause. Em sẽ test abort dưới load, theo dõi DB concurrency/p95/p99 và chỉ coi fix thành công khi cả wasted dependencies lẫn latency/capacity trở về mức chấp nhận được.”

## Câu hỏi đào sâu

1. Nếu đã truyền token vào `ToListAsync(ct)` nhưng SQL vẫn đôi lúc chạy thêm một khoảng thời gian, bạn sẽ điều tra gì trước khi kết luận provider có bug?
2. Nếu business yêu cầu export lớn không được huỷ khi browser đóng tab, bạn có còn dùng request-abort token làm lifetime của operation không?
3. Team muốn đặt command timeout xuống 2 giây cho mọi query để bảo vệ DB; bạn phản biện và thiết kế timeout policy thế nào?

## Lỗi trả lời thường gặp

- Cho rằng có `CancellationToken` parameter là downstream tự cancel.
- Dùng `Task.Run` cho EF Core I/O.
- Dùng cancellation để che query/index kém.
- Catch mọi cancellation rồi trả/log 500.
- Không phân biệt timeout, cancellation và capacity protection.

## Thang điểm 0–10

- **0–2:** Không phát hiện token bị bỏ qua hoặc đề xuất `Task.Run` như fix chính.
- **3–4:** Biết truyền token nhưng không giải thích cooperative cancellation hay production impact.
- **5–6:** Propagation đúng, phân biệt timeout, có SQL investigation cơ bản.
- **7–8:** Evidence-driven, có load/failure testing, query/capacity guardrails và observability.
- **9–10:** Phân tách rõ cancellation/deadline/resource protection, hiểu race/failure semantics và đưa ra verification plan end-to-end.

# Câu 2 — Service Bus retry biến một đơn hàng thành ba lần gửi email và hai lần trừ tồn kho

**Loại câu hỏi:** Production Incident / Troubleshooting  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, at-least-once delivery, idempotency, retries, message settlement, SQL transactions, distributed systems, observability, incident response

## Bối cảnh

Một e-commerce backend nhận đơn hàng trong ASP.NET Core API. Sau khi order được ghi vào SQL Server, hệ thống publish `OrderPlaced` lên Azure Service Bus. Một worker xử lý message để reserve inventory, gọi email provider và cập nhật trạng thái order.

Sau một sự cố network ngắn, support phát hiện một số khách nhận 2–3 email xác nhận; nghiêm trọng hơn, vài SKU bị reserve hai lần. Queue depth tăng trong khoảng 15 phút rồi giảm. Logs có cùng `OrderId` xuất hiện nhiều lần nhưng `MessageId` không phải lúc nào cũng giống nhau. Team đề xuất tăng lock duration và bật duplicate detection rồi coi sự cố đã được xử lý.

Chưa rõ producer có retry publish sau timeout hay không, consumer complete message ở thời điểm nào, inventory API có idempotency hay không, email provider có idempotency key không, lock có bị mất do processing lâu, và database update với external side effects có transaction boundary thế nào.

## Câu hỏi chính

Bạn đang on-call. Hãy trình bày cách stabilize incident, dựng evidence để phân biệt producer duplicate, redelivery do settlement/lock, consumer retry và downstream duplicate side effect; sau đó thiết kế remediation để correctness không phụ thuộc vào giả định “message chỉ đến một lần”.

## Câu hỏi làm rõ nên cân nhắc

1. Producer tạo `MessageId` mới cho mỗi retry hay giữ stable ID theo business event?
2. Worker complete message trước hay sau inventory/email, và processing duration so với lock behavior thế nào?
3. Inventory reservation có business key/idempotency constraint nào không?
4. Email provider có hỗ trợ idempotency key hoặc truy vấn trạng thái request trước đó không?
5. Order write và event publication hiện dùng transaction/outbox hay hai bước độc lập?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng config queue. Hãy xác định side effect nào có thể lặp và side effect nào phải “exactly once” theo business semantics.

### Gợi ý 2

Một broker có thể redeliver; producer cũng có thể publish lại khi không biết request trước thành công hay thất bại.

### Gợi ý 3

Stable business identity, idempotent consumer và durable state thường quan trọng hơn việc cố biến transport thành exactly-once end-to-end.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và ngăn duplicate side effects tiếp tục.
2. Bảo toàn evidence, không purge mù quáng.
3. Correlate OrderId, MessageId, delivery attempt và downstream call.
4. Phân loại nguồn duplicate.
5. Xác định business idempotency boundary.
6. Sửa producer/consumer/side-effect handling.
7. Thiết kế retry/DLQ/recovery.
8. Test duplicate, lock loss và network ambiguity.
9. Rollout và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định Azure Service Bus đảm bảo exactly-once end-to-end.
- Xem duplicate delivery/retry là failure mode cần thiết kế.
- Dùng business idempotency cho inventory và các side effects quan trọng.
- Không coi tăng lock duration là root-cause fix.
- Phân biệt duplicate transport message với hai message khác ID nhưng cùng business event.
- Có incident stabilization và evidence collection trước remediation.

### Điểm cộng

- Stable event/message identity khi producer retry.
- Inbox/idempotency record hoặc unique constraint được ghi atomically với local business update.
- Outbox Pattern cho atomicity giữa order DB state và event intent nếu failure window hiện hữu.
- DLQ/retry policy có phân loại transient/permanent failure.
- Correlation ID và attempt/delivery metadata trong structured logs.

### Senior+

- Nhận ra external email side effect không thể nằm trong SQL transaction theo cách tạo exactly-once đơn giản; cần provider idempotency hoặc business-level dedupe/state machine.
- Giải thích failure window “side effect thành công nhưng consumer crash trước settlement”.
- Không biến Outbox/Inbox thành cargo cult: dùng ở boundary có dual-write/duplicate risk thực tế.

## Hướng giải quyết tham khảo

Trong incident, trước tiên xác định duplicate inventory có đang tiếp diễn không. Nếu worker tiếp tục gây thiệt hại, có thể tạm giảm/stop consumer hoặc cô lập side effect theo runbook, nhưng không purge queue vì sẽ mất evidence/work hợp lệ. Inventory correctness cần được đối soát theo order/reservation business key.

Dựng timeline theo `OrderId`, event ID, `MessageId`, delivery count/attempt, worker instance, timestamps, settlement outcome và downstream request IDs. Nếu cùng `MessageId` được xử lý lại, xem xét redelivery, lock loss, crash hoặc settlement failure. Nếu khác `MessageId` nhưng cùng business event, producer retry/re-publish là giả thuyết mạnh. Cả hai có thể đồng thời xảy ra.

Thiết kế consumer theo at-least-once reality. Với inventory, reservation nên có idempotency key như `OrderId + LineId` và DB constraint/state transition để retry không reserve thêm. Consumer có thể lưu Inbox/process marker cùng transaction với local state nếu phù hợp. Nhưng đừng mark “processed” trước external side effect nếu như vậy tạo failure window mất side effect.

Email cần semantics riêng. Nếu provider hỗ trợ idempotency key, dùng stable key. Nếu không, cần durable notification state và workflow cho phép xác định đã gửi/đang gửi; vẫn phải thừa nhận network ambiguity nếu provider không cho idempotent operation/status lookup. Business có thể chấp nhận duplicate email hơn duplicate charge/inventory, nên severity và design khác nhau.

Ở producer, nếu order commit và publish là dual write có failure window, Outbox Pattern có thể ghi event intent trong cùng DB transaction với order rồi publisher riêng gửi/retry. Stable event identity giúp downstream dedupe. Duplicate detection của broker có thể là defense-in-depth khi cấu hình phù hợp, nhưng không thay thế business idempotency, đặc biệt nếu producer tạo ID mới hoặc duplicate xuất hiện ngoài dedupe assumptions.

Tăng lock duration chỉ có thể giảm một số redelivery do processing vượt lock; nó không xử lý crash sau side effect, ambiguous publish hay duplicate business event. Cần đo processing duration, lock/settlement failures, queue depth, active/dead-letter counts và downstream error rate.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xử lý đây như correctness incident. Trước hết em ngăn duplicate inventory tiếp tục và giữ queue/evidence để đối soát. Sau đó correlate theo OrderId, MessageId, delivery attempt, worker instance và downstream request ID. Cùng MessageId lặp lại gợi ý redelivery/settlement; khác MessageId nhưng cùng OrderId có thể là producer retry. Em không dựa vào exactly-once transport. Inventory phải idempotent theo business key, ví dụ unique reservation cho OrderId/LineId. Nếu order write và publish đang dual-write, em đánh giá Outbox để lưu event intent atomically. Consumer có Inbox/state transition khi phù hợp. Với email, em ưu tiên provider idempotency key; nếu không có thì cần durable notification state và chấp nhận/giảm network ambiguity. Duplicate detection và lock tuning chỉ là defense-in-depth. Em sẽ test crash sau side effect nhưng trước complete, duplicate publish và network timeout, rồi monitor duplicate rate, settlement failure, DLQ và inventory reconciliation.”

## Câu hỏi đào sâu

1. Nếu inventory DB update thành công nhưng process chết ngay trước khi complete message, thiết kế của bạn đảm bảo retry không trừ tiếp như thế nào?
2. Nếu email provider không hỗ trợ idempotency key và timeout khiến bạn không biết email đã được gửi chưa, bạn chọn trade-off nào?
3. Một teammate nói “Outbox + Inbox ở mọi service sẽ giải quyết exactly-once”; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng lock duration.
- Tin rằng duplicate detection loại bỏ mọi duplicate end-to-end.
- Dedupe chỉ theo random `MessageId` dù producer retry tạo ID mới.
- Mark processed quá sớm mà không xét failure window.
- Purge queue trong incident mà chưa phân loại work hợp lệ.

## Thang điểm 0–10

- **0–2:** Coi duplicate là broker bug và chỉ sửa config.
- **3–4:** Biết idempotency nhưng chưa xác định business boundary/failure windows.
- **5–6:** Có dedupe/idempotency, retry/DLQ và incident investigation hợp lý.
- **7–8:** Phân biệt producer/redelivery/downstream ambiguity, có Outbox/Inbox khi justified và test failure windows.
- **9–10:** Reason end-to-end về business correctness, external side effects, recovery/reconciliation, operational complexity và trade-offs.

# Câu 3 — Optimizely + Akamai: làm sao cache mạnh mà editor vẫn publish đúng và không tạo “kiến trúc phân tán quá mức”

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, Akamai/CDN, caching, content modeling, ASP.NET Core, SEO, performance, failure isolation, observability, architecture trade-offs

## Bối cảnh

Một marketing website toàn cầu chạy Optimizely CMS trên ASP.NET Core. Site có khoảng 90% anonymous traffic, nhiều content blocks dùng lại giữa các page, có 12 locale và peak traffic tăng mạnh khi chạy campaign. Akamai đứng trước origin.

Product muốn:

- p95 page load tốt hơn trong campaign;
- editor publish content và thấy thay đổi “gần như ngay”;
- personalized banner cho một nhóm người dùng đăng nhập;
- canonical URL/redirect/metadata không bị stale sai;
- nếu CRM/review API chậm thì trang chính vẫn usable.

Hiện team đang tranh luận ba hướng:

1. Cache toàn bộ HTML 30 phút ở CDN.
2. Không cache HTML, chỉ cache static assets để tránh stale content.
3. Tách website thành nhiều microservices và dùng Redis cho mọi block.

Chưa có freshness SLA chính xác theo content type, cache hit ratio, origin bottleneck breakdown, purge latency, personalization ratio hay dependency latency distribution.

## Câu hỏi chính

Hãy thiết kế caching/content-delivery strategy và service boundaries cho hệ thống này. Bạn cần giải thích dữ liệu nào cache ở browser/CDN/application, cách invalidation/purge gắn với publish, cách tránh leak personalized content, cách degrade khi third-party dependency lỗi, và evidence nào quyết định liệu có cần Redis/microservices hay không.

## Câu hỏi làm rõ nên cân nhắc

1. “Gần như ngay” nghĩa là 2 giây, 30 giây hay 2 phút, và content nào có SLA khác nhau?
2. Anonymous/personalized traffic chiếm tỷ lệ bao nhiêu và personalization dựa trên cookie/identity nào?
3. Page/block nào thay đổi thường xuyên, block nào được reuse rộng và publish một block ảnh hưởng bao nhiêu URL?
4. Origin latency đến từ CMS rendering, SQL/content query, external APIs hay asset delivery?
5. Akamai purge/invalidation workflow hiện tại có được tích hợp vào publish event và có quan sát được failure không?

## Gợi ý tư duy

### Gợi ý 1

Không có một TTL phù hợp cho mọi representation. Hãy phân loại theo tính public/private, volatility và correctness impact.

### Gợi ý 2

Cache key và invalidation là một phần của correctness, đặc biệt khi có locale, query variation và authenticated personalization.

### Gợi ý 3

Đừng chọn Redis hay microservices trước khi chứng minh bottleneck/boundary. CDN có thể hấp thụ anonymous read traffic với operational cost thấp hơn.

## Cấu trúc trả lời đề xuất

1. Làm rõ freshness, personalization, SEO và availability SLA.
2. Phân loại content/representation.
3. Đo origin/dependency/CDN hiện tại.
4. Thiết kế cache layers và keys.
5. Thiết kế publish invalidation/purge.
6. Tách personalized path khỏi public cache.
7. Thiết kế dependency degradation.
8. Chọn boundaries đơn giản nhất đáp ứng requirement.
9. Test publish/cache/security/SEO/failure.
10. Rollout và quan sát.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cache personalized HTML như public content.
- Không chọn một TTL toàn site mà không phân loại content.
- Có cache key strategy gồm các dimensions thực sự thay đổi representation, ví dụ locale.
- Có invalidation/purge strategy gắn với publish và fallback khi purge thất bại.
- Third-party dependency có timeout/fallback; không để một review/CRM call kéo sập page.
- Không tự động chọn microservices/Redis.

### Điểm cộng

- Immutable/fingerprinted static assets có long-lived cache.
- Public anonymous pages có thể tận dụng CDN mạnh nếu correctness/purge model cho phép.
- Dependency-derived fragments có TTL/fallback riêng và tránh gọi third party synchronously trên mọi request.
- Theo dõi cache hit ratio, origin p95/p99, purge success/latency, stale-content incidents.
- SEO regression test cho canonical, redirects, status code, metadata sau publish.

### Senior+

- Xử lý shared content block invalidation theo dependency graph/tag/surrogate-key concept ở mức thiết kế thay vì purge toàn site nếu nền tảng hỗ trợ cơ chế phù hợp.
- Nhận ra cache variation quá nhiều có thể phá hit ratio và tăng complexity.
- Thiết kế stale-if-error/graceful degradation có điều kiện, nhưng không dùng stale cho dữ liệu có correctness/security requirement không cho phép.
- Cân nhắc origin protection/backpressure trong campaign thay vì chỉ “scale thêm”.

## Hướng giải quyết tham khảo

Trước hết đo. Tách page latency thành CDN hit/miss, origin rendering, CMS/data access và external dependencies. Nếu phần lớn traffic anonymous và representation ổn định theo locale, CDN full-page caching có thể đem lại lợi ích lớn, nhưng chỉ cho public representation và với invalidation model đúng.

Static assets fingerprinted nên cache dài ở browser/CDN. Public HTML có TTL theo content class, không nhất thiết 30 phút cố định. Publish workflow cần phát invalidation cho các URL/representations bị ảnh hưởng; shared block có thể ảnh hưởng nhiều pages nên cần dependency mapping hoặc tagging strategy nếu khả năng của stack/CDN hỗ trợ. Nếu purge thất bại, phải retry/alert và có operational path; không giả định publish đồng nghĩa edge đã cập nhật tức thì.

Personalized content phải được tách khỏi public cache boundary. Có thể render personalized fragment client-side/API riêng, hoặc dùng cơ chế variation/private caching phù hợp, nhưng cache key phải tránh cross-user data leakage. Không thêm user ID vào full-page CDN cache một cách máy móc vì cardinality và security/operational cost có thể rất lớn.

CRM/review APIs là failure-prone dependencies. Đặt timeout ngắn phù hợp, circuit/fallback khi justified, cache dữ liệu không nhạy cảm theo freshness requirement, và render trang với degraded fragment nếu business cho phép. Không giữ request chính chờ dependency quá lâu. Correlation/tracing phải cho biết latency đến từ origin hay dependency.

Redis chỉ nên thêm nếu có server-side shared state/cache workload mà CDN/application cache không đáp ứng và measurement chứng minh lợi ích. Microservices chỉ hợp lý khi có boundary ownership/deployment/scaling rõ; marketing site không nên bị phân tán chỉ để “scale cache”. Một modular/layered ASP.NET Core + Optimizely origin sau CDN có thể đơn giản và đáng tin cậy hơn.

Rollout theo nhóm page/campaign nhỏ, đo cache hit ratio, origin RPS, p95/p99, purge latency/failure, external dependency error và stale incidents. Test publish shared block, locale variation, authenticated/anonymous transition, canonical/redirect/status code, dependency outage và cache poisoning/leak scenarios.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn TTL 30 phút cho toàn site và cũng không tắt HTML caching ngay. Trước hết em làm rõ freshness SLA theo content type và đo CDN hit/miss, origin render time, CMS query và third-party latency. Với 90% anonymous traffic, public HTML là ứng viên tốt cho Akamai cache theo locale và các variation thực sự cần thiết; static fingerprinted assets cache dài hơn. Publish phải kích hoạt invalidation cho affected representations, đặc biệt shared blocks, và purge failure cần retry/alert. Personalized banner em tách khỏi public page cache hoặc dùng private/variation boundary an toàn để không leak user data. CRM/review failure phải degrade fragment thay vì kéo sập page. Em chỉ thêm Redis khi có measured server-side shared-cache need, và chỉ tách microservice khi có ownership/scaling boundary thật. Thành công được đo bằng hit ratio, origin RPS, p95/p99, purge latency, stale incidents và SEO regression, không phải số lượng cache layer.”

## Câu hỏi đào sâu

1. Một shared content block xuất hiện trên 20.000 URLs; purge từng URL sau publish quá chậm. Bạn thay đổi invalidation model thế nào mà vẫn kiểm soát stale content?
2. Nếu Product yêu cầu personalized banner nằm trong server-rendered HTML nhưng security cấm bất kỳ khả năng cross-user caching nào, bạn thiết kế cache boundary ra sao?
3. Nếu CDN hit ratio đã 95% nhưng origin miss vẫn chậm do một review provider, bạn có thêm Redis không? Evidence nào quyết định?

## Lỗi trả lời thường gặp

- Cache toàn bộ authenticated/personalized HTML ở public CDN.
- Dùng một TTL cho mọi content và coi TTL là invalidation strategy.
- Purge toàn site cho mọi publish mà không xét blast radius/cost.
- Thêm Redis/microservices mà chưa đo bottleneck.
- Không test canonical/redirect/locale và stale behavior sau publish.

## Thang điểm 0–10

- **0–2:** Chọn cache/no-cache cực đoan, bỏ qua personalization/security.
- **3–4:** Có CDN/cache cơ bản nhưng invalidation và dependency failure mơ hồ.
- **5–6:** Phân lớp cache hợp lý, có publish purge, personalization isolation và measurement.
- **7–8:** Có shared-content invalidation, failure degradation, SEO/security tests và observability.
- **9–10:** Tối ưu theo evidence, kiểm soát correctness/blast radius, cân bằng performance với operational complexity và biết khi không cần Redis/microservices.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `CancellationToken` là cooperative signal; cancellation chỉ có tác dụng khi được propagate và operation downstream thực sự quan sát/hỗ trợ nó. Cancellation, timeout và performance optimization là ba vấn đề khác nhau.
- Hệ thống messaging phải thiết kế cho duplicate/retry/failure windows. Business idempotency quan trọng hơn giả định transport “exactly once”.
- Với CMS/web delivery, caching là bài toán correctness: cache key, invalidation, personalization boundary và failure behavior quan trọng ngang TTL.
- Architecture tốt không đồng nghĩa thêm nhiều infrastructure. CDN, application boundary đơn giản và targeted resilience thường tốt hơn Redis/microservices nếu requirement chưa chứng minh complexity đó.

## Mẫu tư duy cần nhớ

- Trace signal và ownership end-to-end trước khi kết luận framework “không hoạt động”.
- Design retry together with idempotency.
- Measure before optimizing; phân biệt symptom với root cause.
- Treat cache invalidation and cache keys as correctness concerns.
- Chọn kiến trúc đơn giản nhất đáp ứng SLA, security và failure model.
