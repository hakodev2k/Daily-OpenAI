# Câu 1 — EF Core `IQueryable`, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core query pipeline, LINQ deferred execution, tracking, SQL profiling, performance diagnosis

## Bối cảnh

Một ASP.NET Core API trả về danh sách nhân viên. Sau một lần refactor, endpoint vẫn đúng dữ liệu nhưng số SQL query tăng mạnh và p95 latency tăng từ khoảng 180 ms lên hơn 1 giây khi có tải. Service tạo một `IQueryable<Employee>`, sau đó gọi `CountAsync()`, `ToListAsync()`, và một helper khác cũng enumerate query để tạo audit metadata. Một developer nói: “`IQueryable` đã chứa kết quả rồi nên reuse query sẽ không gọi database thêm.”

Database có vài triệu bản ghi, endpoint hỗ trợ filter và paging. Chưa rõ query có `Include`, projection hay tracking hay không.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra bên trong EF Core/LINQ khi `IQueryable` bị enumerate nhiều lần, vì sao latency và số SQL query tăng, misconception nằm ở đâu, production risk là gì và bạn sẽ chứng minh giả thuyết bằng cách nào trước khi sửa?

## Câu hỏi làm rõ nên cân nhắc

- Query được enumerate ở những vị trí nào và mỗi lần dùng terminal operator nào?
- Có cần tổng số record chính xác hay chỉ cần biết còn trang tiếp theo?
- Query có `Include`, projection, lazy loading hoặc tracking không?
- SQL thực tế và execution plan của từng lần execution là gì?
- Endpoint có yêu cầu consistency giữa `Count` và page data không?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt “query definition” với “query result”.
- **Gợi ý 2:** Xem các terminal operations như `CountAsync`, `FirstAsync`, `ToListAsync` và enumeration là các execution boundary.
- **Gợi ý 3:** Đo SQL command count/duration, kiểm tra generated SQL, projection, indexes và quyết định liệu có thật sự cần `COUNT(*)` riêng.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement paging và consistency.
2. Giải thích expression tree và deferred execution.
3. Liệt kê execution boundaries.
4. Xác minh bằng logs/traces/profiler.
5. Kiểm tra generated SQL và execution plan.
6. Tối ưu số round-trip, projection và tracking.
7. So sánh các lựa chọn paging/count.
8. Đo lại p50/p95/p99 và database load.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable<T>` không phải collection đã materialize; nó mô tả query.
- Mỗi terminal operation có thể tạo một database command riêng.
- Re-enumeration có thể thực thi lại query.
- `CountAsync()` và `ToListAsync()` thường là hai query khác nhau.
- Cần quan sát generated SQL thay vì đoán.

### Điểm cộng

- Dùng projection chỉ lấy cột cần thiết.
- `AsNoTracking()` phù hợp cho read-only query khi không cần change tracking.
- Đánh giá keyset pagination nếu offset lớn và use case phù hợp.
- Có thể lấy `pageSize + 1` nếu business chỉ cần `hasNextPage` thay vì exact total.

### Nâng cao

- Nhận ra `Count` và page query chạy tách biệt có thể nhìn thấy hai snapshot khác nhau tùy transaction/isolation.
- Phân tích query shape, cardinality, indexes và parameter sensitivity thay vì chỉ “thêm cache”.
- Đề xuất tracing theo database command để phát hiện query multiplication.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, cần paging và hiện tại không yêu cầu snapshot-consistent exact count.

EF Core xây dựng query từ LINQ expression. Việc giữ một biến `IQueryable<Employee>` không materialize dữ liệu. Khi gọi `CountAsync`, EF Core dịch expression tương ứng thành SQL và gửi command xuống database. Sau đó `ToListAsync` tạo một execution khác. Nếu helper enumerate query thêm lần nữa thì lại có thêm execution. Vì vậy reuse `IQueryable` không đồng nghĩa reuse result.

Trước tiên bật structured logging/tracing cho database commands ở môi trường kiểm soát, gắn correlation/trace ID, đo command count và duration cho một request. Dùng `ToQueryString()` trong diagnostic/test để xem SQL shape; kiểm tra execution plan và indexes tại database. Không log parameter nhạy cảm.

Nếu cần exact total, chấp nhận count query riêng nhưng tối ưu predicate/index và page query. Nếu UI chỉ cần biết có trang tiếp theo, lấy tối đa `pageSize + 1` có thể loại bỏ count. Query trả DTO nên `Select` trước khi materialize và dùng no-tracking khi entity không cần update.

Không nên materialize toàn bộ dataset chỉ để tránh re-query: việc đó chuyển chi phí sang memory/network và có thể tệ hơn rất nhiều. Cache total chỉ hợp lý nếu semantics cho phép stale data và invalidation được thiết kế rõ.

Testing gồm integration test xác nhận query semantics, performance/load test với dữ liệu gần production, và regression instrumentation về số database commands/request. Monitoring gồm DB duration, endpoint latency, rows returned, connection-pool pressure và slow-query metrics.

Khuyến nghị sẽ thay đổi nếu business bắt buộc exact count cùng snapshot với page data, query rất nhỏ, hoặc dữ liệu có mô hình truy cập phù hợp với precomputed count.

## Mẫu trả lời trong phỏng vấn

“Em sẽ chưa kết luận chỉ từ việc thấy `IQueryable` được reuse. `IQueryable` chủ yếu giữ expression của query chứ không giữ result. Mỗi lần gặp execution boundary như `CountAsync` hoặc `ToListAsync`, EF Core có thể dịch và gửi một SQL command mới. Vì vậy ở scenario này em kỳ vọng ít nhất count và page data là hai round-trip, cộng thêm helper nếu nó enumerate lại.

Em sẽ xác minh bằng trace/database command logging theo request, xem generated SQL và execution plan. Sau đó em hỏi business có thực sự cần exact total không. Nếu chỉ cần `hasNext`, em có thể query `pageSize + 1`; nếu cần total thì giữ count riêng nhưng tối ưu predicate/index. Với read-only endpoint em sẽ projection thẳng DTO và cân nhắc `AsNoTracking`.

Em không materialize toàn bộ query để ‘fix’ deferred execution vì có thể làm memory và network tệ hơn. Cuối cùng em load test lại và theo dõi p95, số SQL commands/request, DB duration và connection-pool pressure. Nếu cần count và page nhất quán tuyệt đối thì em sẽ bàn thêm về transaction/isolation vì hai query riêng không tự động tạo cùng một snapshot.”

## Câu hỏi đào sâu

1. `AsNoTracking()` giải quyết vấn đề gì và không giải quyết vấn đề gì trong scenario này?
2. Nếu product yêu cầu exact total nhưng bảng thay đổi liên tục, bạn đảm bảo semantics của total và page như thế nào?
3. Nếu reviewer đề xuất gọi `ToListAsync()` ngay đầu rồi filter/paging trong memory để chỉ query DB một lần, bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Nói `IQueryable` “cache kết quả”.
- Chỉ đề xuất `AsNoTracking` nhưng bỏ qua multiple executions.
- Materialize toàn bộ dataset trước filter/paging.
- Tối ưu trước khi xem generated SQL/execution plan.
- Không phân biệt exact total với `hasNextPage`.

## Thang điểm 0–10

- Requirement clarification: **1.5 điểm**
- Technical correctness: **2.5 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **1.5 điểm**
- Communication: **1 điểm**

# Câu 2 — Incident: Hangfire job gửi email bị thực thi trùng sau timeout

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, distributed failure, database consistency, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire để xử lý workflow offboarding. Job đọc cấu hình từ SQL Server, gọi Exchange Online/Microsoft Graph để cập nhật mailbox/calendar, rồi ghi trạng thái hoàn tất. Sau một đợt external API latency cao, support báo một số người nhận nhận email/notification hai lần. Dashboard cho thấy một số job retry; database lại chỉ có một record business operation.

Không rõ duplicate xảy ra ở bước nào, timeout là client-side hay upstream, và external operation có idempotency support hay không.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ lúc nhận alert đến khi xác định nguyên nhân, giảm duplicate ngay lập tức và thiết kế workflow lâu dài để retry an toàn như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Side effect nào bị duplicate: email, calendar update hay mailbox operation?
- Job retry policy và timeout hiện tại là gì?
- External API trả timeout trước hay sau khi server có thể đã commit side effect?
- Có business operation ID/idempotency key hoặc unique constraint nào không?
- Nhiều Hangfire workers/server có thể xử lý cùng logical operation không?

## Gợi ý tư duy

- **Gợi ý 1:** Timeout không chứng minh operation thất bại.
- **Gợi ý 2:** Phân biệt delivery semantics của job framework với idempotency của business side effect.
- **Gợi ý 3:** Thiết kế state machine/idempotency record và reconcile trạng thái khi kết quả external call không xác định.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và side effect bị ảnh hưởng.
2. Giảm tác động mà không phá recovery.
3. Thu thập job history, trace, DB và external request evidence.
4. Xây dựng nhiều hypothesis.
5. Reproduce failure window.
6. Thêm idempotency guard/state transition.
7. Thiết kế retry/reconciliation.
8. Thêm metrics, alert và chaos/failure tests.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Retry phải được thiết kế cùng idempotency.
- Timeout tạo trạng thái “unknown outcome”, không đồng nghĩa external side effect chưa xảy ra.
- Không dựa vào in-memory lock cho correctness giữa nhiều worker/process.
- Cần correlation giữa logical operation, Hangfire job attempt và external request.
- Immediate mitigation phải cân bằng duplicate với nguy cơ bỏ sót operation.

### Điểm cộng

- Unique business key/constraint để chống duplicate logical operation.
- Explicit state như `Pending`, `InProgress`, `Succeeded`, `Unknown`, `Failed` cùng attempt metadata.
- Reconciliation/query-back nếu external system cho phép kiểm tra trạng thái.
- Retry có backoff/jitter và phân loại transient/permanent failures.

### Nâng cao

- Phân biệt exactly-once processing với exactly-once observable side effect; không hứa điều framework không bảo đảm.
- Outbox hữu ích cho DB-to-message boundary nhưng không tự biến một arbitrary external API thành idempotent.
- Với non-idempotent API và không query-back được, có thể cần human review cho ambiguous outcomes.

## Hướng giải quyết tham khảo

**Impact:** xác định số logical operations, users bị ảnh hưởng và loại side effect. Nếu duplicate email gây tác động lớn, có thể tạm giảm concurrency hoặc tạm dừng riêng loại job đó trong lúc điều tra; không tắt toàn bộ background processing nếu không cần.

**Evidence:** lấy Hangfire attempt history, exception/timeout timestamps, trace IDs, DB state transitions và external request IDs nếu có. Correlate theo immutable `OperationId` thay vì job ID vì retry có thể tạo nhiều attempt cho cùng business operation.

**Hypotheses:** external server đã thực hiện side effect nhưng response bị mất; job bị retry sau worker/process failure; hai workers nhận hai logical jobs tương đương; DB commit thất bại sau external success; application enqueue duplicate.

**Short-term fix:** thêm guard ở persistent store bằng business key và state transition có concurrency protection. Không chỉ check-then-act bằng hai câu lệnh rời rạc. Nếu external provider hỗ trợ idempotency key, gửi stable key dựa trên logical operation. Nếu operation có thể query lại trạng thái, reconcile trước khi retry ambiguous attempt.

**Long-term:** model workflow thành explicit state machine. Retry chỉ cho lỗi được phân loại transient; ambiguous outcome đi qua reconciliation. Với DB event cần publish, dùng transactional outbox có thể bảo vệ DB/message boundary. Với external non-idempotent side effect không có status lookup, chấp nhận rằng automation không thể đảm bảo exactly-once tuyệt đối; route trường hợp không xác định sang human approval hoặc business compensation.

**Verification:** fault-injection test ở các điểm “external success nhưng client timeout”, “process chết trước DB update”, concurrent duplicate enqueue, và DB transient failure. Theo dõi duplicate-prevented count, retry attempts, ambiguous operations, job age, external latency/error rate và end-to-end success.

## Mẫu trả lời trong phỏng vấn

“Em coi đây trước hết là incident về side-effect safety, không chỉ là lỗi Hangfire. Em sẽ xác định blast radius và side effect nào duplicate, sau đó correlate một logical `OperationId` với tất cả job attempts và external requests. Điểm quan trọng là timeout không chứng minh request chưa được xử lý; external system có thể đã commit nhưng response không về được client.

Vì vậy em không giải quyết bằng cách tắt retry. Em thiết kế retry cùng idempotency: persistent business key/unique constraint, state transition có concurrency protection và nếu provider hỗ trợ thì dùng stable idempotency key. Với outcome không xác định, nếu API cho query trạng thái thì reconcile trước khi retry. Nếu không thể query và operation không idempotent, em sẽ cân nhắc human review thay vì tự động gọi lại mù quáng.

Em cũng kiểm tra duplicate enqueue và worker failure. Outbox có thể giúp boundary giữa DB và message, nhưng không tự giải quyết duplicate của một external API không idempotent. Cuối cùng em fault-test các cửa sổ failure và monitor retry rate, ambiguous operations, prevented duplicates, job age và external latency.”

## Câu hỏi đào sâu

1. Vì sao distributed lock một mình chưa đủ để đảm bảo external side effect chỉ xảy ra một lần?
2. Outbox pattern giải quyết boundary nào và không giải quyết boundary nào ở đây?
3. Nếu external API không có idempotency key cũng không có API kiểm tra trạng thái, bạn xử lý timeout sau request như thế nào?

## Lỗi trả lời thường gặp

- Tắt retry hoàn toàn để “hết duplicate”.
- Cho rằng timeout nghĩa là external call chắc chắn thất bại.
- Dùng static/in-memory flag làm distributed deduplication.
- Hứa “exactly once” mà không mô tả failure boundary.
- Không có correlation ID và attempt-level telemetry.

## Thang điểm 0–10

- Requirement clarification: **1 điểm**
- Technical correctness: **2 điểm**
- Depth: **2 điểm**
- Trade-off analysis: **1.5 điểm**
- Production readiness: **2.5 điểm**
- Communication: **1 điểm**

# Câu 3 — Thiết kế AI Code Review Agent có quyền đọc repository và đề xuất patch

**Loại câu hỏi:** AI engineering / system decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, deterministic validation, evaluation, security, auditability, cost/latency trade-offs

## Bối cảnh

Team muốn xây một AI agent hỗ trợ review pull request cho các dự án .NET. Agent có thể đọc diff, một phần repository, coding rules và CI results; sau đó phát hiện correctness/security/performance issues và đề xuất patch. Team muốn sau này agent có thể chạy test hoặc tạo commit, nhưng security không chấp nhận cấp repository write permission rộng ngay từ MVP.

PR có thể chứa nội dung không đáng tin cậy, bao gồm comments, README, test fixtures hoặc text có thể cố hướng dẫn agent bỏ qua policy. Repository có thể chứa secrets hoặc dữ liệu nội bộ. Budget inference và latency đều có giới hạn nhưng chưa được định lượng.

## Câu hỏi chính

Hãy thiết kế MVP AI code-review agent: phần nào cần AI, phần nào phải deterministic, context nào được cấp, tool/permission model ra sao, cách chống prompt injection và hallucination, cách validate output, đánh giá chất lượng, fallback, audit và monitoring như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được phép tạo patch/commit?
- Repository nào được phép gửi code/context tới model và có data-classification requirement gì?
- Success metric là recall issue, precision, reviewer acceptance hay thời gian review?
- PR size/language mix và latency/cost budget là bao nhiêu?
- Agent được chạy command nào, trong môi trường cách ly nào và network access ra sao?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng biến mọi bước thành LLM call.
- **Gợi ý 2:** Tách trusted instructions khỏi untrusted repository content và áp dụng least privilege cho tools.
- **Gợi ý 3:** Dùng staged pipeline: deterministic collection/filtering → model analysis với structured output → deterministic validation/test → human approval cho side effect.

## Cấu trúc trả lời đề xuất

1. Làm rõ threat model và success criteria.
2. Chọn nhiệm vụ thực sự cần semantic reasoning.
3. Thiết kế trusted/untrusted context boundaries.
4. Thiết kế tool permissions và sandbox.
5. Định nghĩa structured output/evidence requirements.
6. Validate bằng compiler/tests/static analyzers/policy checks.
7. Human approval trước write side effect.
8. Offline eval + production monitoring + cost controls.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI phù hợp cho semantic review/triage; authz, policy enforcement và side-effect permission phải deterministic.
- Repository content là untrusted input, không phải instruction có cùng authority với system/developer policy.
- MVP nên read-only hoặc comment-only; write cần explicit approval và scoped token.
- Findings phải có evidence/location và structured schema để validate.
- Chất lượng phải được đo trên eval set, không chỉ demo vài PR.

### Điểm cộng

- Context selection theo diff/symbol/dependency thay vì gửi toàn repo.
- Secret scanning/redaction trước model context.
- Tool allowlist, argument validation, command sandbox, network restrictions và time/resource limits.
- Deduplicate findings với static analyzers để giảm noise.
- Track precision/acceptance, false positives, latency, token/cost và tool failures.

### Nâng cao

- Adversarial eval cho indirect prompt injection trong source/docs/comments.
- Separate planner/reviewer không tự động tạo security boundary; enforcement phải ở tool gateway/policy layer.
- Patch validation bằng build/test/analyzer và change-scope checks trước khi cho human approve.
- Version prompt/rules/model/eval dataset để audit regressions.

## Hướng giải quyết tham khảo

**Vì sao cần AI:** static analyzers rất tốt với rules deterministic nhưng khó bao phủ semantic intent, cross-file reasoning, requirement mismatch và một số design smells. LLM dùng cho hypothesis generation và explanation; compiler, analyzers, tests, permission checks và policy enforcement vẫn deterministic.

**Context:** pipeline lấy PR diff, metadata, relevant symbols/files, coding rules và CI failures. Context retrieval phải có budget và provenance. Repository text được đánh dấu là untrusted data; không cho nội dung file tự thay đổi tool policy. Secret scanner/data classification chạy trước khi context được gửi ra model.

**Permissions:** MVP chỉ read repository metadata/content cần thiết và post suggestion qua một narrowly scoped integration nếu business chấp nhận. Không cấp shell/network/write mặc định. Nếu cần chạy test, chạy trong ephemeral sandbox với allowlisted command, resource/time limits, sanitized environment và network disabled hoặc allowlisted. Tạo commit/merge là side effect cần human approval và scoped credential chỉ được cấp tại execution boundary.

**Output validation:** model trả schema như `category`, `severity`, `file`, `line/range`, `claim`, `evidence`, `suggested_fix`, `confidence`. Validator kiểm tra file/range tồn tại, evidence thuộc context, severity hợp lệ và finding không duplicate. Patch phải build/test/static-analyze trước khi được đề xuất như verified patch. Không coi confidence tự khai báo của model là bằng chứng correctness.

**Hallucination/injection:** require evidence, reject references tới symbol/file không tồn tại, adversarially test instructions nằm trong code/comments/docs, và enforce permissions ngoài model. Model không thể tự nâng quyền bằng text.

**Evaluation:** xây golden set từ historical PR bugs/review comments cộng synthetic/adversarial cases. Đo precision, useful-findings/PR, reviewer acceptance, false-positive rate, missed critical issues, latency và cost. Có shadow mode trước khi comment tự động.

**Fallback:** model timeout/schema failure → không tạo side effect; có thể retry có giới hạn hoặc bỏ qua AI review và giữ CI/static analysis. Audit lưu model/prompt/rules version, context references/hashes, tool calls, validation results và human decision, nhưng tránh lưu secrets/raw sensitive context không cần thiết.

Khuyến nghị thay đổi nếu code không được phép rời private boundary, latency budget rất thấp, hoặc agent được trao write/production permissions; khi đó threat model và isolation phải mạnh hơn đáng kể.

## Mẫu trả lời trong phỏng vấn

“Em sẽ bắt đầu bằng comment-only MVP, vì giá trị cần chứng minh trước khi cấp write permission. AI chỉ làm phần semantic reasoning: đọc diff và relevant context để tạo findings. Những thứ như authorization, secret policy, command allowlist, schema validation, build và test vẫn deterministic.

Em coi toàn bộ repository content là untrusted data. Một comment trong source nói ‘ignore previous rules’ không được quyền thay đổi policy. Tool gateway mới là nơi enforce quyền. Context sẽ gồm diff, symbols/files liên quan, team rules và CI result, có provenance và budget; trước đó chạy secret scanning/data classification.

Model phải trả structured findings có file/range, claim và evidence. Validator reject file hoặc symbol không tồn tại; patch phải build, test và qua analyzers. Nếu sau này cho chạy command, em dùng ephemeral sandbox với allowlist, resource limits và network restriction. Commit hoặc merge cần human approval và credential scope nhỏ.

Về quality, em không đánh giá bằng vài demo PR. Em tạo golden set từ historical bugs/reviews và adversarial prompt-injection cases, đo precision, reviewer acceptance, missed critical findings, latency và cost. Production audit lưu version của model/prompt/rules, tool calls và validation outcome. Nếu model fail thì CI/static analysis vẫn chạy; AI không trở thành single point of failure.”

## Câu hỏi đào sâu

1. Nếu agent cần đọc thêm file ngoài diff để hiểu behavior, bạn giới hạn context expansion thế nào?
2. Tại sao tách thành nhiều subagent không tự động giải quyết prompt injection hoặc permission escalation?
3. Product yêu cầu agent tự commit patch để tiết kiệm thời gian; bạn sẽ thêm những control nào trước khi đồng ý?

## Lỗi trả lời thường gặp

- “Cho LLM đọc toàn repo rồi review” mà không có context/security boundary.
- Dùng prompt “không được hallucinate” thay cho deterministic validation.
- Cấp token write rộng ngay từ MVP.
- Cho model tự quyết định shell command/network target mà không có policy gateway.
- Không có eval dataset và chỉ đo cảm nhận người dùng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` biểu diễn query; materialization/execution boundary quyết định khi database thực sự được gọi.
- Background-job retry và business idempotency là hai vấn đề khác nhau; timeout có thể tạo outcome không xác định.
- AI agent cần được thiết kế như một untrusted reasoning component nằm sau deterministic permission/policy boundaries.
- Observability phải theo logical operation/request xuyên qua database, background job và external dependencies.

## Mẫu tư duy cần nhớ

- Clarify semantics trước khi tối ưu implementation.
- Measure generated behavior trước khi kết luận từ source code.
- Design retries together with idempotency và reconciliation.
- Treat external timeout as potentially ambiguous outcome.
- Validate AI output deterministically và enforce least privilege ngoài model.
