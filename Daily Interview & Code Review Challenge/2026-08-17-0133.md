# Code Review Challenge 1 — Fire-and-forget, scoped `DbContext` và cancellation bị bỏ qua

**Chủ đề:** async/await, cancellation, resource lifetime, background work, logging/observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép admin yêu cầu reset cấu hình mailbox hết hạn. Endpoint cần trả về nhanh vì thao tác Exchange Online có thể mất vài giây cho mỗi mailbox. Team quyết định dùng fire-and-forget để không giữ request mở lâu.

Production có thể nhận 20–50 request gần như đồng thời, mỗi request chứa 10–100 mailbox. Gần đây log xuất hiện các lỗi không ổn định như `ObjectDisposedException`, `A second operation was started on this context`, một số mailbox không được xử lý nhưng API vẫn trả `200`, và đôi lúc application shutdown nhưng tác vụ vẫn đang chạy.

Ràng buộc: không được mất thao tác đã chấp nhận; cần biết mailbox nào thành công/thất bại; external API có thể timeout; request cancellation không đồng nghĩa business operation phải bị hủy.

## Đoạn code cần review

```csharp
[ApiController]
[Route("mail/configurations")]
public sealed class MailConfigurationController : ControllerBase
{
    private readonly AppDbContext _dbContext;
    private readonly IExchangeOnlineService _exchange;
    private readonly ILogger<MailConfigurationController> _logger;

    public MailConfigurationController(
        AppDbContext dbContext,
        IExchangeOnlineService exchange,
        ILogger<MailConfigurationController> logger)
    {
        _dbContext = dbContext;
        _exchange = exchange;
        _logger = logger;
    }

    [HttpPost("reset-expired")]
    public IActionResult ResetExpired(
        [FromBody] List<ResetExpiredMailConfigurationsRequest> requests,
        CancellationToken cancellationToken)
    {
        Task.Run(async () =>
        {
            foreach (var request in requests)
            {
                var config = await _dbContext.EmployeeOffboardingMailConfigs
                    .FirstOrDefaultAsync(
                        x => x.Employee.Email == request.UserEmail,
                        cancellationToken);

                if (config is null)
                    continue;

                await _exchange.RemoveMailboxForwardingAsync(
                    request.UserEmail,
                    cancellationToken);

                config.IsExpired = true;
                config.UpdatedAt = DateTime.UtcNow;

                await _dbContext.SaveChangesAsync(cancellationToken);

                _logger.LogInformation(
                    "Reset expired mail config for {UserEmail}",
                    request.UserEmail);
            }
        }, cancellationToken);

        return Ok(new { accepted = requests.Count });
    }
}
```

## Kết quả code review tham khảo

### 1. Capture scoped `DbContext` rồi dùng sau khi request kết thúc

- **Problem:** `AppDbContext` thường là scoped theo request nhưng task chạy độc lập sau khi endpoint trả về.
- **Why it happens:** request scope có thể bị dispose trong khi lambda vẫn đang chạy.
- **Production impact:** `ObjectDisposedException`, mất một phần xử lý, lỗi ngẫu nhiên khó tái hiện.
- **Severity:** Critical
- **Recommended fix:** không capture scoped service vào fire-and-forget task. Dùng durable background job/queue; worker tạo scope riêng cho từng unit of work.

### 2. `Task.Run` không đảm bảo work được hoàn tất hoặc khôi phục

- **Problem:** công việc chỉ nằm trong memory/process hiện tại.
- **Why it happens:** process restart, recycle, deployment hoặc crash sẽ làm task biến mất.
- **Production impact:** API đã báo accepted nhưng mailbox có thể không bao giờ được xử lý.
- **Severity:** Critical
- **Recommended fix:** persist work item trước khi trả accepted; dùng Hangfire, queue + BackgroundService, hoặc một job store đáng tin cậy.

### 3. Dùng request `CancellationToken` cho business operation chạy sau response

- **Problem:** token gắn với request có thể bị cancel khi client disconnect hoặc request lifecycle kết thúc.
- **Why it happens:** cancellation của HTTP request không nhất thiết là cancellation của business operation đã accepted.
- **Production impact:** xử lý bị dừng giữa chừng, trạng thái external và DB không đồng bộ.
- **Severity:** High
- **Recommended fix:** xác định cancellation semantics riêng cho background operation; worker dùng token của host/job execution, không dùng request token làm lifetime của durable task.

### 4. Không await hoặc quan sát task

- **Problem:** endpoint bỏ qua exception của task.
- **Why it happens:** fire-and-forget task không được await, không có structured job state.
- **Production impact:** failure chỉ xuất hiện ngẫu nhiên trong process logs hoặc bị bỏ sót; caller vẫn thấy `200`.
- **Severity:** High
- **Recommended fix:** enqueue và trả operation/job ID; worker ghi status `Pending/Processing/Completed/Failed` cùng error details phù hợp.

### 5. Một `DbContext` được dùng xuyên suốt batch dài

- **Problem:** cùng context xử lý nhiều mailbox và có thể giữ tracking state lâu hơn cần thiết.
- **Why it happens:** một scope/context cho batch lớn.
- **Production impact:** memory tăng, state phức tạp hơn; nếu code sau này parallelize thì dễ gặp lỗi concurrent use.
- **Severity:** Medium
- **Recommended fix:** xác định transaction boundary rõ ràng; có thể tạo scope/context theo item hoặc batch nhỏ tùy throughput và consistency requirement.

### 6. Không có idempotency/status model

- **Problem:** retry request hoặc enqueue lại có thể chạy cùng business operation nhiều lần.
- **Why it happens:** code chỉ lookup config theo email rồi gọi external side effect.
- **Production impact:** duplicate side effects, trạng thái khó reconcile.
- **Severity:** High
- **Recommended fix:** persist operation ID/idempotency key; kiểm tra desired state trước side effect; dùng atomic status transition khi claim job.

### 7. External side effect và DB update không có failure strategy

- **Problem:** Exchange call có thể thành công nhưng `SaveChangesAsync` fail, hoặc ngược lại ở các flow khác.
- **Why it happens:** không thể có một transaction ACID bao trùm SQL + external system.
- **Production impact:** remote state và local state lệch nhau.
- **Severity:** High
- **Recommended fix:** thiết kế saga/reconciliation semantics: read-back remote state, retry idempotently, lưu attempt/history, đánh dấu cần reconcile khi outcome không chắc chắn.

### 8. Response `200 OK` không phản ánh semantics “accepted for background processing”

- **Problem:** endpoint báo thành công dù chỉ mới bắt đầu fire-and-forget.
- **Why it happens:** response không phân biệt accepted và completed.
- **Production impact:** caller hiểu nhầm operation đã hoàn tất.
- **Severity:** Medium
- **Recommended fix:** trả `202 Accepted` cùng operation/job ID và endpoint/status mechanism khi phù hợp.

### 9. Không giới hạn batch/concurrency

- **Problem:** mỗi request tạo thêm một `Task.Run`; nhiều request có thể bùng số task/outbound calls.
- **Why it happens:** không có centralized queue/backpressure.
- **Production impact:** Thread Pool pressure, dependency throttling, database/external API overload.
- **Severity:** High
- **Recommended fix:** bounded queue hoặc background job workers với concurrency limit, rate limit và retry/backoff phù hợp.

### 10. Observability chưa đủ

- **Problem:** log chỉ ghi success theo email.
- **Why it happens:** không có operation correlation/status/attempt.
- **Production impact:** khó điều tra partial failure và retry.
- **Severity:** Medium
- **Recommended fix:** log `OperationId`, item ID, attempt, worker, dependency request ID, duration, final status; thêm metrics/traces.

## Phiên bản code đề xuất

Một hướng phù hợp là persist operation rồi enqueue một durable job. Ví dụ controller chỉ nhận request và tạo work item:

```csharp
[ApiController]
[Route("mail/configurations")]
public sealed class MailConfigurationController : ControllerBase
{
    private readonly IResetExpiredOperationService _operations;
    private readonly IBackgroundJobClient _jobs;

    public MailConfigurationController(
        IResetExpiredOperationService operations,
        IBackgroundJobClient jobs)
    {
        _operations = operations;
        _jobs = jobs;
    }

    [HttpPost("reset-expired")]
    public async Task<IActionResult> ResetExpired(
        [FromBody] IReadOnlyList<ResetExpiredMailConfigurationsRequest> requests,
        CancellationToken cancellationToken)
    {
        if (requests.Count is 0 or > 100)
            return BadRequest("Request must contain between 1 and 100 items.");

        var operationId = await _operations.CreateAsync(
            requests,
            cancellationToken);

        _jobs.Enqueue<ResetExpiredMailJob>(
            job => job.ExecuteAsync(operationId, CancellationToken.None));

        return Accepted(new
        {
            operationId,
            status = "Pending"
        });
    }
}
```

Worker tạo scope/job lifetime riêng và xử lý có idempotency:

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly AppDbContext _dbContext;
    private readonly IExchangeOnlineService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        AppDbContext dbContext,
        IExchangeOnlineService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _dbContext = dbContext;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteAsync(
        Guid operationId,
        CancellationToken cancellationToken)
    {
        var operation = await _dbContext.ResetExpiredOperations
            .Include(x => x.Items)
            .SingleAsync(x => x.Id == operationId, cancellationToken);

        foreach (var item in operation.Items.Where(x => x.Status != "Completed"))
        {
            try
            {
                var remoteState = await _exchange.GetMailboxStateAsync(
                    item.UserEmail,
                    cancellationToken);

                if (remoteState.HasForwarding)
                {
                    await _exchange.RemoveMailboxForwardingAsync(
                        item.UserEmail,
                        cancellationToken);
                }

                item.Status = "Completed";
                item.CompletedAt = DateTime.UtcNow;
                await _dbContext.SaveChangesAsync(cancellationToken);
            }
            catch (Exception ex)
            {
                item.AttemptCount++;
                item.LastError = ex.Message;
                await _dbContext.SaveChangesAsync(CancellationToken.None);

                _logger.LogError(
                    ex,
                    "Failed reset mail item {ItemId} in operation {OperationId}",
                    item.Id,
                    operationId);

                throw;
            }
        }
    }
}
```

Đây vẫn chỉ là skeleton. Production design cần unique operation/idempotency constraints, retry policy, timeout classification, poison-job handling và reconciliation strategy.

## Trade-offs

- **Hangfire/durable queue:** reliability và visibility tốt hơn nhưng thêm operational dependency và job semantics cần quản lý.
- **In-process `BackgroundService`:** đơn giản hơn nhưng muốn chống mất work thì queue/work item vẫn phải persistent.
- **Scope mỗi item:** isolation tốt hơn nhưng tăng overhead; scope theo batch nhỏ có thể hiệu quả hơn nếu consistency cho phép.
- **Retry:** cần cho transient failure nhưng phải đi cùng idempotency và backoff; không retry mọi exception giống nhau.

## Cách kiểm thử

1. **Concurrency test:** nhiều request enqueue cùng một business operation; xác nhận duplicate được suppress.
2. **Failure-path test:** Exchange thành công nhưng DB save fail; lần retry phải reconcile thay vì tạo side effect sai.
3. **Restart test:** restart worker sau khi API trả `202`; operation vẫn được tiếp tục từ persistent state.
4. **Cancellation test:** client disconnect sau `202`; background operation vẫn tuân theo business semantics đã định.
5. **Load test:** batch 100 items × nhiều concurrent requests; kiểm tra queue depth, dependency throttling, memory và processing latency.

## Quan sát trong production

- **Logs:** `OperationId`, item ID, email đã mask khi cần, attempt, worker, status transition, dependency request ID.
- **Metrics:** queue depth, processing duration, success/failure/retry count, duplicate suppression, operations stuck in `Processing`.
- **Traces:** API accept → enqueue → worker → DB → Exchange dependency.
- **Alerts:** failure rate tăng, queue age cao, retry storm, stuck operations.
- **Database observations:** số `Pending/Processing/Failed`, optimistic-concurrency conflicts, duplicate-key violations.

2. Bạn thiết kế idempotency thế nào nếu Exchange call timeout nhưng không biết request đã thành công hay chưa?
3. Nếu Hangfire storage bị outage, endpoint nên trả gì và business semantics ra sao?

# Code Review Challenge 2 — Authorization dựa trên request body và log lộ access token

**Chủ đề:** authentication/authorization, input validation, sensitive-data exposure, API security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một API nội bộ cho phép manager xem dữ liệu timesheet của nhân viên. API dùng JWT authentication. Frontend gửi `managerId`, `employeeId` và `accessToken` trong body để backend kiểm tra quyền và gọi tiếp một internal API.

Production ghi nhận một trường hợp user bình thường xem được timesheet của nhân viên ngoài team khi thay đổi request bằng DevTools. Security review cũng phát hiện bearer token xuất hiện trong application logs.

Ràng buộc: ứng dụng multi-tenant; employee IDs là GUID; manager có thể xem dữ liệu trong team của mình; admin có quyền rộng hơn; token của user không được ghi log hoặc tin tưởng từ request payload.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/timesheets")]
public sealed class TimesheetController : ControllerBase
{
    private readonly AppDbContext _dbContext;
    private readonly HttpClient _httpClient;
    private readonly ILogger<TimesheetController> _logger;

    public TimesheetController(
        AppDbContext dbContext,
        HttpClient httpClient,
        ILogger<TimesheetController> logger)
    {
        _dbContext = dbContext;
        _httpClient = httpClient;
        _logger = logger;
    }

    [HttpPost("employee")]
    public async Task<IActionResult> GetEmployeeTimesheet(
        TimesheetRequest request,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Timesheet request Manager={ManagerId} Employee={EmployeeId} Token={Token}",
            request.ManagerId,
            request.EmployeeId,
            request.AccessToken);

        var manager = await _dbContext.Employees
            .FirstOrDefaultAsync(
                x => x.Id == request.ManagerId,
                cancellationToken);

        if (manager == null)
            return Unauthorized();

        var employee = await _dbContext.Employees
            .FirstOrDefaultAsync(
                x => x.Id == request.EmployeeId,
                cancellationToken);

        if (employee == null)
            return NotFound();

        if (employee.ManagerId != request.ManagerId && !request.IsAdmin)
            return Forbid();

        _httpClient.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", request.AccessToken);

        var result = await _httpClient.GetStringAsync(
            $"https://internal-api/employees/{request.EmployeeId}/timesheet",
            cancellationToken);

        return Ok(result);
    }
}

public sealed record TimesheetRequest(
    Guid ManagerId,
    Guid EmployeeId,
    string AccessToken,
    bool IsAdmin);
```

## Gợi ý

### Gợi ý 1

## Dừng lại và tự review

## Kết quả code review tham khảo

### 1. Tin `ManagerId` từ request body để xác định caller

- **Problem:** user có thể gửi bất kỳ `ManagerId` nào.
- **Why it happens:** authorization dùng client-supplied identity thay vì authenticated principal.
- **Production impact:** Broken Object Level Authorization; user có thể impersonate manager khác.
- **Severity:** Critical
- **Recommended fix:** lấy caller identity từ `User` claims sau JWT validation; map claim sang employee/user record phía server.

### 2. Tin `IsAdmin` từ request body

- **Problem:** user chỉ cần đổi `IsAdmin=true`.
- **Why it happens:** role/privilege được nhận từ untrusted input.
- **Production impact:** privilege escalation trực tiếp.
- **Severity:** Critical
- **Recommended fix:** dùng policy/role/permission claims đã được xác thực và server-side authorization handler.

### 3. Không enforce tenant boundary

- **Problem:** lookup chỉ theo `Id`; không có `TenantId` constraint.
- **Why it happens:** object ID được coi như đủ để xác định authorization scope.
- **Production impact:** cross-tenant data exposure nếu user đoán/lấy được GUID của tenant khác.
- **Severity:** Critical
- **Recommended fix:** mọi query và authorization check cần tenant context đáng tin cậy; cân nhắc global query filter chỉ như lớp hỗ trợ, không thay thế policy review.

### 4. Ghi bearer token vào logs

- **Problem:** access token được log dạng plaintext.
- **Why it happens:** diagnostic logging ghi toàn bộ request field.
- **Production impact:** credential leakage qua log aggregation, support tooling, SIEM hoặc người có quyền đọc log.
- **Severity:** Critical
- **Recommended fix:** tuyệt đối không log bearer token; thêm redaction và logging policy cho credentials/secrets.

### 5. Nhận access token từ request body

- **Problem:** backend tin token do client gửi như một data field riêng.
- **Why it happens:** authentication credential bị trộn vào business payload.
- **Production impact:** token substitution/confusion; khó kiểm soát intended audience/scope; tăng rủi ro leak.
- **Severity:** High
- **Recommended fix:** dùng authenticated request token khi architecture thực sự cần delegated downstream call, hoặc dùng token acquisition/on-behalf-of flow phù hợp; không nhận arbitrary token field từ body.

### 6. Mutate `DefaultRequestHeaders.Authorization` trên shared `HttpClient`

- **Problem:** header global của client bị thay đổi theo từng request.
- **Why it happens:** `HttpClient` thường được reuse; nhiều inbound requests có thể chạy concurrent.
- **Production impact:** token của user A có thể bị dùng cho request của user B trong race condition.
- **Severity:** High
- **Recommended fix:** tạo `HttpRequestMessage` và set `requestMessage.Headers.Authorization` cho từng outbound call; hoặc delegating handler/token handler có scope rõ ràng.

### 7. Authorization chỉ kiểm tra direct manager relation

- **Problem:** business rules có thể phức tạp hơn nhưng bị hard-code tại controller.
- **Why it happens:** authorization logic phân tán và gắn chặt data access.
- **Production impact:** khó maintain, dễ lệch rule giữa endpoints.
- **Severity:** Medium
- **Recommended fix:** centralize vào authorization service/policy handler có test riêng; support admin, delegated approver, tenant scope theo rule thật.

### 8. Downstream URL/data scope phụ thuộc employee ID nhưng không bind với tenant/caller authorization artifact

- **Problem:** downstream call chỉ dùng employee ID.
- **Why it happens:** authorization hoàn thành “ngầm” ở upstream nhưng downstream không có context/contract rõ ràng.
- **Production impact:** nếu upstream check bị bypass, downstream có thể trả dữ liệu nhạy cảm.
- **Severity:** High
- **Recommended fix:** defense in depth: downstream cũng enforce service/user authorization hoặc nhận scoped identity/tenant context phù hợp.

### 9. Trả raw downstream string mà không kiểm soát content/error semantics

- **Problem:** response được pass-through thiếu validation/shape/error handling.
- **Why it happens:** controller làm proxy thô.
- **Production impact:** có thể leak field không cần thiết hoặc biến dependency error thành hành vi API khó kiểm soát.
- **Severity:** Medium
- **Recommended fix:** deserialize vào DTO được allowlist fields; map dependency errors; validate payload và content type.

## Phiên bản code đề xuất

Ví dụ đơn giản hóa với server-side authorization service và token per outbound request:

```csharp
[Authorize]
[ApiController]
[Route("api/timesheets")]
public sealed class TimesheetController : ControllerBase
{
    private readonly ITimesheetAuthorizationService _authorization;
    private readonly IHttpClientFactory _httpClientFactory;
    private readonly IUserTokenProvider _tokenProvider;

    public TimesheetController(
        ITimesheetAuthorizationService authorization,
        IHttpClientFactory httpClientFactory,
        IUserTokenProvider tokenProvider)
    {
        _authorization = authorization;
        _httpClientFactory = httpClientFactory;
        _tokenProvider = tokenProvider;
    }

    [HttpGet("employees/{employeeId:guid}")]
    public async Task<IActionResult> GetEmployeeTimesheet(
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);
        var tenantId = User.FindFirstValue("tenant_id");

        if (string.IsNullOrWhiteSpace(userId) ||
            string.IsNullOrWhiteSpace(tenantId))
        {
            return Forbid();
        }

        var allowed = await _authorization.CanViewEmployeeTimesheetAsync(
            userId,
            tenantId,
            employeeId,
            cancellationToken);

        if (!allowed)
            return Forbid();

        var accessToken = await _tokenProvider.GetForInternalApiAsync(
            User,
            cancellationToken);

        var client = _httpClientFactory.CreateClient("InternalApi");

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"employees/{employeeId:D}/timesheet");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        using var response = await client.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        if (response.StatusCode == HttpStatusCode.NotFound)
            return NotFound();

        response.EnsureSuccessStatusCode();

        var dto = await response.Content.ReadFromJsonAsync<TimesheetDto>(
            cancellationToken: cancellationToken);

        return Ok(dto);
    }
}
```

Authorization service phải enforce tenant + role/policy + employee relationship từ dữ liệu server-side:

```csharp
public async Task<bool> CanViewEmployeeTimesheetAsync(
    string userId,
    string tenantId,
    Guid employeeId,
    CancellationToken cancellationToken)
{
    var caller = await _dbContext.Employees
        .AsNoTracking()
        .SingleOrDefaultAsync(
            x => x.UserId == userId && x.TenantId == tenantId,
            cancellationToken);

    if (caller is null)
        return false;

    if (caller.IsTenantAdmin)
        return true;

    return await _dbContext.Employees
        .AsNoTracking()
        .AnyAsync(
            x => x.Id == employeeId &&
                 x.TenantId == tenantId &&
                 x.ManagerId == caller.Id,
            cancellationToken);
}
```

Trong hệ thống thực tế, admin privilege nên đến từ authorization policy/permission model đáng tin cậy thay vì field mutable đơn giản nếu business model yêu cầu kiểm soát chặt hơn.

## Trade-offs

- **Policy handler/authorization service:** thêm abstraction nhưng giảm duplicated security logic và test dễ hơn.
- **Delegated token/OBO:** giữ user context tốt nhưng phức tạp hơn service-to-service credentials; chỉ dùng khi downstream thực sự cần delegated identity.
- **Defense in depth ở downstream:** tốn thêm authorization work nhưng giảm blast radius nếu upstream có bug.
- **Global tenant query filters:** hữu ích để giảm accidental cross-tenant query nhưng không nên là cơ chế authorization duy nhất.

## Cách kiểm thử

1. **BOLA test:** user sửa `employeeId` sang nhân viên ngoài team; phải nhận `403` hoặc response phù hợp mà không leak dữ liệu.
2. **Privilege escalation test:** gửi `IsAdmin=true` hoặc giả `managerId`; các field này không còn ảnh hưởng authorization.
3. **Cross-tenant test:** employee ID hợp lệ của tenant B được gọi từ user tenant A; luôn bị từ chối.
4. **Concurrency test:** 100 concurrent users với token khác nhau; outbound request không được trộn Authorization header.
5. **Sensitive-data test:** scan logs/traces/errors; không có bearer token, cookie, secret hoặc raw credential.

## Quan sát trong production

- **Logs:** caller subject/user ID đã chuẩn hóa, tenant ID, target employee ID, authorization result, policy name; không log token.
- **Metrics:** denied authorization count, cross-tenant attempts, downstream 401/403, unusual access patterns.
- **Traces:** inbound authenticated request → authorization decision → downstream call, nhưng redact credentials.
- **Alerts:** tăng đột biến `403`, repeated attempts truy cập nhiều employee IDs, token-related downstream failures.
- **Security audit:** định kỳ kiểm tra logging pipeline, claim mappings, tenant-isolation tests và authorization-policy coverage.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên dùng resource-based authorization trong ASP.NET Core thay vì chỉ `[Authorize(Roles = ...)]`?
2. Nếu JWT có role claim `Admin`, bạn còn cần query database để authorize không?
3. Làm sao thiết kế integration test để phát hiện cross-tenant leakage trên hàng chục endpoints?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Task.Run` không biến request code thành durable background processing.
- Scoped dependencies như `DbContext` không nên bị capture rồi dùng sau request lifetime.
- Cancellation phải gắn với đúng semantic boundary; client disconnect không mặc định đồng nghĩa hủy business operation đã accepted.
- Background work đáng tin cậy cần persistence, idempotency, retry strategy, failure recovery và observability.
- Authorization phải dựa trên authenticated principal và server-side state, không tin identity/role do client tự khai báo.
- Multi-tenant API phải enforce tenant boundary ở mọi object-level access path.
- Bearer tokens và credentials không được ghi log.
- Shared `HttpClient` không nên mutate per-user `DefaultRequestHeaders.Authorization`; dùng header trên từng request.

## Mẫu tư duy cần nhớ

1. **Lifetime first:** trước khi dùng async/background code, xác định lifetime của request, DI scope và process.
2. **Accepted ≠ completed:** nếu API trả trước khi xử lý xong, cần operation state và recovery path.
3. **Trust only authenticated context:** mọi client-supplied identity/role đều là untrusted input.
4. **Authorize the resource, not just the endpoint:** kiểm tra caller có quyền trên đúng employee/tenant/object hay không.
5. **Treat observability as part of security and reliability:** correlation, status, metrics và redaction phải được thiết kế ngay từ đầu.
