# Code Review Challenge 1 — Trừ số lượng vé dưới tải đồng thời

**Chủ đề:** Concurrency, EF Core, transaction, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7

## Bối cảnh

Một ASP.NET Core API cho phép người dùng đặt vé sự kiện. `RemainingSlots` nằm trong SQL Server/PostgreSQL qua EF Core. Khi mở bán, cùng một event có thể nhận hàng trăm request trong vài giây. Production thỉnh thoảng ghi nhận số booking vượt capacity; client retry sau timeout đôi khi tạo hai booking. Yêu cầu không được oversell và một request nghiệp vụ chỉ được tạo booking một lần.

## Đoạn code cần review

```csharp
public sealed class BookingService(AppDbContext db)
{
    public async Task<Guid> BookAsync(
        Guid eventId,
        Guid userId,
        string requestId,
        CancellationToken ct)
    {
        var ev = await db.Events
            .FirstOrDefaultAsync(x => x.Id == eventId, ct);

        if (ev is null)
            throw new KeyNotFoundException();

        if (ev.RemainingSlots <= 0)
            throw new InvalidOperationException("Sold out");

        var existing = await db.Bookings
            .FirstOrDefaultAsync(x => x.RequestId == requestId, ct);

        if (existing is not null)
            return existing.Id;

        ev.RemainingSlots--;

        var booking = new Booking
        {
            Id = Guid.NewGuid(),
            EventId = eventId,
            UserId = userId,
            RequestId = requestId,
            CreatedAtUtc = DateTime.UtcNow
        };

        db.Bookings.Add(booking);
        await db.SaveChangesAsync(ct);

        return booking.Id;
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-update `RemainingSlots` không nguyên tử

- **Problem:** Nhiều request có thể đọc cùng một giá trị rồi cùng vượt qua check.
- **Why:** Read và write là các thao tác tách biệt; isolation mặc định không biến logic này thành atomic reservation.
- **Impact:** Oversell hoặc lost update tùy concurrency strategy/provider.
- **Severity:** Critical
- **Fix:** Dùng conditional atomic update (`RemainingSlots > 0`) hoặc optimistic concurrency token và retry có kiểm soát; xác nhận đúng một row được cập nhật.

### 2. Idempotency check cũng là check-then-insert

- **Problem:** Hai request cùng `requestId` có thể đều thấy chưa tồn tại.
- **Why:** Application query không phải uniqueness guarantee.
- **Impact:** Duplicate booking và trừ capacity nhiều lần.
- **Severity:** Critical
- **Fix:** Unique index/constraint trên idempotency key phù hợp scope, ví dụ `(UserId, RequestId)` hoặc contract đã định nghĩa; xử lý unique violation bằng cách đọc kết quả đã tồn tại.

### 3. Capacity và booking phải nằm trong cùng transaction nghiệp vụ

- **Problem:** Nếu chuyển sang raw/ExecuteUpdate nhưng không gom đúng transaction, capacity và booking có thể lệch.
- **Impact:** Slot bị giữ nhưng booking không tồn tại hoặc ngược lại.
- **Severity:** High
- **Fix:** Atomic capacity claim + insert booking trong transaction DB.

### 4. Không xác định scope của `requestId`

- **Problem:** Global uniqueness có thể sai business rule; không unique lại nguy hiểm.
- **Impact:** Collision giữa user/operation hoặc idempotency không hiệu lực.
- **Severity:** High
- **Fix:** Định nghĩa contract và constraint tương ứng.

### 5. Cancellation sau khi commit có thể gây retry từ client

- **Problem:** Client có thể không nhận response dù transaction đã thành công.
- **Impact:** At-least-once request behavior tạo duplicate nếu thiếu idempotency bền vững.
- **Severity:** High
- **Fix:** Idempotency key lưu trong DB và trả lại kết quả cũ khi retry.

### 6. Exception nghiệp vụ quá chung

- **Problem:** `InvalidOperationException`/`KeyNotFoundException` không thể hiện API contract.
- **Impact:** Mapping HTTP/status và observability kém rõ ràng.
- **Severity:** Medium
- **Fix:** Domain result/typed exception và mapping nhất quán.

### 7. Thiếu telemetry theo event/request

- **Problem:** Khó phân biệt sold-out thật, concurrency conflict và duplicate retry.
- **Severity:** Medium
- **Fix:** Structured logs và metrics theo outcome, không log dữ liệu nhạy cảm không cần thiết.

## Phiên bản code đề xuất

Ví dụ sau minh họa SQL Server bằng conditional update. Với PostgreSQL dùng cú pháp/provider tương ứng; nguyên tắc là update capacity có điều kiện và kiểm tra affected rows.

```csharp
public sealed class BookingService(AppDbContext db)
{
    public async Task<Guid> BookAsync(
        Guid eventId,
        Guid userId,
        string requestId,
        CancellationToken ct)
    {
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var existing = await db.Bookings
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.UserId == userId && x.RequestId == requestId, ct);

        if (existing is not null)
            return existing.Id;

        var affected = await db.Database.ExecuteSqlInterpolatedAsync($@"
            UPDATE Events
            SET RemainingSlots = RemainingSlots - 1
            WHERE Id = {eventId} AND RemainingSlots > 0", ct);

        if (affected != 1)
            throw new InvalidOperationException("Event not found or sold out");

        var booking = new Booking
        {
            Id = Guid.NewGuid(),
            EventId = eventId,
            UserId = userId,
            RequestId = requestId,
            CreatedAtUtc = DateTime.UtcNow
        };

        db.Bookings.Add(booking);

        try
        {
            await db.SaveChangesAsync(ct);
            await tx.CommitAsync(ct);
            return booking.Id;
        }
        catch (DbUpdateException)
        {
            await tx.RollbackAsync(CancellationToken.None);

            var duplicate = await db.Bookings.AsNoTracking()
                .SingleOrDefaultAsync(
                    x => x.UserId == userId && x.RequestId == requestId,
                    CancellationToken.None);

            if (duplicate is not null)
                return duplicate.Id;

            throw;
        }
    }
}
```

Database vẫn phải có unique constraint phù hợp cho idempotency key. Trong production nên phân biệt “event không tồn tại” với “sold out” nếu API contract yêu cầu. Có thể dùng optimistic concurrency token thay conditional SQL nếu muốn giữ abstraction EF Core, nhưng phải xử lý conflict/retry đúng cách.

## Trade-offs

Conditional update thường đơn giản và hiệu quả cho một counter nóng, nhưng gắn logic với SQL/provider hơn. Optimistic concurrency giữ code gần EF Core nhưng dưới contention cao có thể tạo nhiều conflict/retry. Pessimistic locking có thể phù hợp cho một số workload nhưng tăng blocking/deadlock risk. Distributed lock thường không cần nếu invariant có thể được bảo vệ trực tiếp trong database là source of truth.

## Cách kiểm thử

- Chạy 100 request đồng thời khi chỉ còn 1 slot: đúng một booking thành công và capacity không âm.
- Gửi nhiều request đồng thời với cùng idempotency key: chỉ một row booking tồn tại và mọi retry nhận cùng booking ID.
- Mô phỏng failure giữa capacity update và insert: transaction rollback giữ dữ liệu nhất quán.
- Mô phỏng client timeout sau commit rồi retry: không tạo booking mới.
- Chạy integration test trên đúng DB provider production để kiểm tra transaction/constraint behavior.

## Quan sát trong production

Theo dõi `booking_success`, `sold_out`, `idempotent_replay`, `concurrency_conflict`, DB duration và transaction failures. Trace request → DB transaction bằng correlation/idempotency ID đã được xử lý an toàn. Alert khi capacity âm, unique-violation tăng bất thường hoặc conflict/retry rate tăng mạnh.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một event cực nóng tạo contention trên một row, bạn scale thiết kế thế nào?
2. Optimistic concurrency token khác conditional update ở failure mode và throughput ra sao?
3. Nếu booking còn phải publish RabbitMQ message sau commit, bạn bảo đảm không mất message thế nào?

# Code Review Challenge 2 — Proxy tải tài liệu từ URL do người dùng cung cấp

**Chủ đề:** SSRF, HTTP client, cancellation, sensitive-data exposure, resource limits  
**Độ khó:** Senior

## Bối cảnh

Một ASP.NET Core API nhận URL của tài liệu để tải về rồi gửi nội dung sang một pipeline xử lý. Endpoint chỉ dành cho user đã đăng nhập nhưng URL do user nhập. Production thỉnh thoảng latency tăng mạnh, memory spike và có request treo lâu. Hệ thống chạy trong cloud network có các internal services không public.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    [HttpPost("import")]
    public async Task<IActionResult> Import([FromBody] ImportRequest request)
    {
        using var client = new HttpClient();
        client.DefaultRequestHeaders.Authorization =
            new AuthenticationHeaderValue("Bearer", request.AccessToken);

        var response = await client.GetAsync(request.Url);
        var bytes = await response.Content.ReadAsByteArrayAsync();

        Console.WriteLine(
            $"Imported {request.Url}, token={request.AccessToken}, size={bytes.Length}");

        if (!response.IsSuccessStatusCode)
            return BadRequest(await response.Content.ReadAsStringAsync());

        var fileName = request.FileName ?? "document.bin";
        await System.IO.File.WriteAllBytesAsync(
            Path.Combine("/tmp/imports", fileName), bytes);

        return Ok(new { fileName, size = bytes.Length });
    }
}

public sealed record ImportRequest(
    string Url,
    string? FileName,
    string AccessToken);
```

## Kết quả code review tham khảo

### 1. SSRF qua URL do user kiểm soát

- **Problem:** Server fetch URL tùy ý.
- **Why:** Authentication không làm URL trở nên trusted.
- **Impact:** Có thể truy cập internal/private endpoints từ network của application.
- **Severity:** Critical
- **Fix:** Tốt nhất dùng allowlist destination/business connector. Nếu phải hỗ trợ URL rộng hơn, áp dụng outbound proxy/egress policy và validation chống private/link-local/loopback; kiểm tra redirect và DNS/rebinding threat model, không chỉ regex hostname.

### 2. Forward bearer token tới destination tùy ý

- **Problem:** Credential do request cung cấp được gửi tới bất kỳ host nào.
- **Impact:** Credential disclosure.
- **Severity:** Critical
- **Fix:** Không nhận/forward arbitrary bearer token; dùng server-side credential scoped cho connector/host cụ thể hoặc cơ chế delegated token được kiểm soát.

### 3. Path traversal qua `FileName`

- **Problem:** `Path.Combine` không biến input thành safe filename.
- **Impact:** Ghi file ngoài thư mục dự kiến tùy input/platform.
- **Severity:** Critical
- **Fix:** Không dùng user path trực tiếp; generate server-side ID/name, hoặc lấy `Path.GetFileName` rồi enforce policy và canonical path check.

### 4. Buffer toàn bộ response vào memory, không giới hạn kích thước

- **Impact:** Memory pressure/DoS khi file lớn hoặc nhiều request đồng thời.
- **Severity:** High
- **Fix:** `ResponseHeadersRead`, kiểm tra giới hạn và stream với byte cap.

### 5. Tạo `HttpClient` mỗi request

- **Impact:** Mất lợi ích handler/connection pooling; dưới tải có thể tăng connection overhead và resource pressure.
- **Severity:** High
- **Fix:** Dùng `IHttpClientFactory` hoặc long-lived client/handler với cấu hình phù hợp.

### 6. Không truyền request cancellation và không có policy timeout rõ ràng

- **Impact:** Work tiếp tục sau client disconnect; slow upstream giữ resource lâu.
- **Severity:** High
- **Fix:** Propagate `HttpContext.RequestAborted`, đặt timeout/budget rõ ràng và phân biệt timeout với cancellation.

### 7. Log access token

- **Impact:** Secret xuất hiện trong log pipeline.
- **Severity:** High
- **Fix:** Không log credential; structured logging với redaction.

### 8. Trả raw upstream error body cho client

- **Impact:** Có thể leak chi tiết upstream/internal data và tạo API contract không ổn định.
- **Severity:** Medium
- **Fix:** Map sang controlled error response; log metadata cần thiết một cách an toàn.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định business chỉ cho phép các host đã cấu hình. Defense-in-depth ở network/egress vẫn cần thiết cho SSRF; code allowlist không thay thế network policy.

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController(
    IHttpClientFactory clients,
    ILogger<DocumentsController> logger,
    IOptions<ImportOptions> options) : ControllerBase
{
    [HttpPost("import")]
    public async Task<IActionResult> Import(
        [FromBody] ImportRequest request,
        CancellationToken ct)
    {
        if (!Uri.TryCreate(request.Url, UriKind.Absolute, out var uri) ||
            uri.Scheme != Uri.UriSchemeHttps ||
            !options.Value.AllowedHosts.Contains(uri.Host,
                StringComparer.OrdinalIgnoreCase))
        {
            return BadRequest("Unsupported source URL.");
        }

        var client = clients.CreateClient("document-import");

        using var response = await client.GetAsync(
            uri,
            HttpCompletionOption.ResponseHeadersRead,
            ct);

        if (!response.IsSuccessStatusCode)
            return StatusCode(StatusCodes.Status502BadGateway,
                "Document source returned an error.");

        const long maxBytes = 20 * 1024 * 1024;
        if (response.Content.Headers.ContentLength is > maxBytes)
            return StatusCode(StatusCodes.Status413PayloadTooLarge);

        Directory.CreateDirectory("/tmp/imports");
        var fileName = $"{Guid.NewGuid():N}.bin";
        var path = Path.Combine("/tmp/imports", fileName);

        await using var input = await response.Content.ReadAsStreamAsync(ct);
        await using var output = System.IO.File.Create(path);

        var buffer = new byte[81920];
        long total = 0;
        int read;

        while ((read = await input.ReadAsync(buffer, ct)) > 0)
        {
            total += read;
            if (total > maxBytes)
            {
                output.Close();
                System.IO.File.Delete(path);
                return StatusCode(StatusCodes.Status413PayloadTooLarge);
            }

            await output.WriteAsync(buffer.AsMemory(0, read), ct);
        }

        logger.LogInformation(
            "Imported document from host {Host}, bytes {Bytes}",
            uri.Host, total);

        return Ok(new { fileName, size = total });
    }
}

public sealed record ImportRequest(string Url);
public sealed class ImportOptions
{
    public HashSet<string> AllowedHosts { get; init; } = [];
}
```

Named client nên cấu hình timeout/handler và redirect policy phù hợp với threat model. Nếu redirects được phép, destination sau redirect cũng phải tuân thủ policy. Với yêu cầu tải arbitrary internet URLs, nên đặt fetcher trong network boundary riêng với egress controls thay vì tin vào application validation đơn lẻ.

## Trade-offs

Allowlist an toàn và dễ audit nhưng hạn chế tính linh hoạt. Một isolated fetch service/outbound proxy phức tạp hơn nhưng phù hợp nếu sản phẩm thực sự cần tải URL internet tùy ý. Streaming giảm memory nhưng cần xử lý cleanup khi cancellation/failure. Server-generated filename làm mất tên gốc, vì vậy có thể lưu display name đã sanitize trong metadata thay vì dùng nó làm filesystem path.

## Cách kiểm thử

- Security test với loopback/private/link-local URL, hostname không allowlist và redirect sang destination bị cấm.
- File vượt giới hạn dù không có `Content-Length`: stream phải dừng và cleanup partial file.
- Client disconnect/upstream timeout: operation bị cancel và không để file rác.
- Load test nhiều download song song: memory không tăng tỷ lệ với tổng kích thước file.
- Kiểm tra log không chứa token, query secret hoặc raw sensitive upstream body.

## Quan sát trong production

Theo dõi outbound request duration, timeout/cancellation rate, response-size distribution, rejected-host count, active imports và process memory. Trace outbound HTTP nhưng sanitize URL/query. Alert khi rejected SSRF-like destinations tăng, upstream latency tăng hoặc import memory/disk usage vượt baseline.
