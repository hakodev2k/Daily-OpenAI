# Code Review Challenge 1 — Hangfire thanh toán: retry biến một lần xử lý thành nhiều lần

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để hoàn tất đơn hàng sau khi cổng thanh toán xác nhận. Job có thể được retry khi process chết, database timeout hoặc HTTP call lỗi. Hệ thống chạy nhiều Hangfire workers trên hai application instances. Production thỉnh thoảng ghi nhận khách hàng nhận hai email xác nhận, tồn kho bị trừ hai lần và một số order ở trạng thái `Paid` dù bước downstream chưa hoàn tất.

Yêu cầu nghiệp vụ chưa nói rõ payment provider có hỗ trợ idempotency key hay không và thao tác inventory có thể rollback xuyên service hay không.

## Đoạn code cần review

```csharp
public sealed class CompleteOrderJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly IEmailSender _email;

    public CompleteOrderJob(
        AppDbContext db,
        HttpClient http,
        IEmailSender email)
    {
        _db = db;
        _http = http;
        _email = email;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync(Guid orderId)
    {
        var order = await _db.Orders
            .Include(x => x.Items)
            .SingleAsync(x => x.Id == orderId);

        if (order.Status == OrderStatus.Paid)
            return;

        var response = await _http.PostAsJsonAsync(
            "/api/inventory/reserve",
            new { order.Id, order.Items });

        response.EnsureSuccessStatusCode();

        order.Status = OrderStatus.Paid;
        order.PaidAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        await _email.SendAsync(
            order.CustomerEmail,
            "Payment completed",
            $"Order {order.Id} was completed.");
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không chống concurrent execution

- **Problem:** Hai workers có thể cùng thấy `Status != Paid` rồi cùng reserve inventory.
- **Why:** Read và update không tạo một atomic ownership claim.
- **Impact:** Duplicate reservation và duplicate downstream side effects.
- **Severity:** Critical
- **Fix:** Dùng atomic state transition/optimistic concurrency hoặc một inbox/job-execution record có unique constraint để một execution giành quyền xử lý.

### 2. Retry không đi cùng idempotency

- **Problem:** HTTP inventory có thể được gọi lại sau timeout hoặc worker crash.
- **Why:** Caller không biết request trước đã được server xử lý hay chưa.
- **Impact:** Double reservation.
- **Severity:** Critical
- **Fix:** Gửi stable idempotency key như `ReserveInventory:{orderId}` và yêu cầu inventory service lưu/deduplicate key. Nếu dependency không hỗ trợ, thiết kế reconciliation/compensation phù hợp.

### 3. Dual-write giữa database và HTTP service

- **Problem:** Inventory reserve và cập nhật order không atomic.
- **Why:** Local EF transaction không bao phủ remote HTTP side effect.
- **Impact:** Inventory đã giữ nhưng order vẫn Pending khi crash trước `SaveChangesAsync`.
- **Severity:** High
- **Fix:** Dùng durable workflow/state machine; lưu intent/outbox trong transaction local rồi worker thực hiện side effect idempotently và cập nhật trạng thái từng bước.

### 4. Email nằm sau commit nhưng không có durable delivery state

- **Problem:** Email lỗi khiến Hangfire retry toàn job; lần retry thấy `Paid` và return nên email có thể mất. Ngược lại nếu email đã gửi nhưng acknowledgment thất bại, có thể gửi lặp tùy implementation.
- **Impact:** Missing/duplicate email.
- **Severity:** High
- **Fix:** Ghi `OrderCompleted` vào transactional outbox; email consumer xử lý riêng và idempotently.

### 5. `Paid` đang gộp nhiều trạng thái nghiệp vụ

- **Problem:** Một flag được dùng như dấu hiệu hoàn thành cả workflow.
- **Impact:** Không thể biết inventory/email đang pending, failed hay completed.
- **Severity:** High
- **Fix:** Mô hình hóa trạng thái cần thiết (`PaymentConfirmed`, `InventoryReserved`, `CompletionStatus`) hoặc workflow step records.

### 6. Không truyền `CancellationToken`

- **Problem:** DB/HTTP operations không nhận cancellation.
- **Impact:** Shutdown kéo dài, work tiếp tục khi host đang dừng; recovery khó dự đoán.
- **Severity:** Medium
- **Fix:** Cho method nhận token nếu execution framework/integration hỗ trợ cancellation phù hợp và truyền xuống EF/HTTP.

### 7. Payload inventory chứa entity graph

- **Problem:** Gửi trực tiếp `order.Items` tạo coupling với persistence model và có thể serialize dữ liệu dư thừa.
- **Impact:** Contract mong manh, payload lớn, nguy cơ lộ field nội bộ.
- **Severity:** Medium
- **Fix:** Map sang explicit DTO chỉ gồm product/SKU, quantity và idempotency metadata.

### 8. Thiếu observability theo workflow attempt

- **Problem:** Không correlation/idempotency identifiers hoặc structured step logs.
- **Impact:** Khó phân biệt retry hợp lệ với duplicate business operation.
- **Severity:** Medium
- **Fix:** Structured logs + trace spans + metrics theo order, job attempt, downstream operation và outcome; tránh log PII không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng **transactional outbox + idempotent consumer**. Đây là recommended approach; schema cụ thể phụ thuộc hệ thống.

```csharp
public sealed class CompleteOrderJob
{
    private readonly AppDbContext _db;

    public CompleteOrderJob(AppDbContext db) => _db = db;

    public async Task ExecuteAsync(Guid orderId, CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        var order = await _db.Orders
            .SingleAsync(x => x.Id == orderId, ct);

        if (order.CompletionStatus != CompletionStatus.Pending)
            return;

        order.CompletionStatus = CompletionStatus.Processing;

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "ReserveInventory",
            AggregateId = orderId,
            IdempotencyKey = $"inventory-reserve:{orderId}",
            Payload = JsonSerializer.Serialize(new ReserveInventoryCommand(orderId))
        });

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}

public sealed class ReserveInventoryHandler
{
    private readonly InventoryClient _inventory;
    private readonly AppDbContext _db;

    public async Task HandleAsync(OutboxMessage message, CancellationToken ct)
    {
        var result = await _inventory.ReserveAsync(
            message.AggregateId,
            message.IdempotencyKey,
            ct);

        if (!result.IsSuccess)
            throw new InvalidOperationException("Inventory reservation failed.");

        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        var order = await _db.Orders.SingleAsync(
            x => x.Id == message.AggregateId, ct);

        if (order.CompletionStatus != CompletionStatus.Completed)
        {
            order.CompletionStatus = CompletionStatus.Completed;
            order.PaidAt = DateTime.UtcNow;

            _db.OutboxMessages.Add(OutboxMessage.ForOrderCompleted(order.Id));
        }

        message.ProcessedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

Production implementation còn cần unique constraint cho idempotency/inbox key, atomic claiming của outbox rows, retry policy có backoff, poison-message handling và reconciliation. Nếu payment/inventory provider cung cấp idempotency semantics riêng, tận dụng contract đó thay vì giả định exactly-once delivery.

## Trade-offs

Outbox tăng schema, worker logic và operational complexity nhưng làm intent bền vững và tách transaction local khỏi side effect. Với hệ thống nhỏ và dependency có idempotency API mạnh, một state machine đơn giản + unique operation key có thể đủ. Distributed transaction thường không phải lựa chọn thực tế cho HTTP service độc lập.

## Cách kiểm thử

1. Chạy 20 executions đồng thời cho cùng `orderId`; xác nhận chỉ một logical reservation được ghi nhận.
2. Mô phỏng inventory thành công rồi process crash trước DB update; retry không được reserve lần hai.
3. Mô phỏng timeout sau khi inventory server đã xử lý request; cùng idempotency key phải trả cùng logical result.
4. Làm email consumer fail nhiều lần; order vẫn giữ trạng thái đúng và email có thể retry độc lập.
5. Kill worker ở từng boundary rồi chạy reconciliation để xác nhận workflow hội tụ về trạng thái hợp lệ.

## Quan sát trong production

Theo dõi `job_attempt_count`, `duplicate_operation_detected`, outbox backlog/age, downstream latency/error rate, workflow step duration và số order stuck theo trạng thái. Trace nên liên kết Hangfire job → outbox dispatch → inventory call → completion event bằng correlation identifiers. Alert khi backlog hoặc stuck workflow vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Unique constraint trong database khác distributed lock ở điểm nào cho bài toán này?
2. Nếu inventory API không hỗ trợ idempotency key thì bạn thiết kế compensation/reconciliation ra sao?
3. Tại sao “exactly once” thường nên được chuyển thành at-least-once delivery + idempotent effect?

# Code Review Challenge 2 — Export endpoint: authorization đúng route nhưng sai dữ liệu

**Chủ đề:** Authorization, sensitive-data exposure, EF Core query, input validation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép manager export employee records sang CSV. JWT authentication đã bật toàn hệ thống. Endpoint được dùng khoảng vài nghìn lần/ngày. Security team phát hiện một manager có thể lấy dữ liệu thuộc tenant khác khi biết `tenantId`; logs cũng chứa các chuỗi filter do người dùng nhập. Dataset của tenant lớn có thể trên 500.000 employees.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/tenants/{tenantId:guid}/employees")]
public sealed class EmployeeExportController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeeExportController> _logger;

    public EmployeeExportController(
        AppDbContext db,
        ILogger<EmployeeExportController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [Authorize(Roles = "Manager")]
    [HttpGet("export")]
    public async Task<IActionResult> Export(
        Guid tenantId,
        string? search,
        CancellationToken ct)
    {
        _logger.LogInformation(
            $"Employee export tenant={tenantId}, search={search}, user={User.Identity?.Name}");

        var employees = await _db.Employees
            .Where(x => x.TenantId == tenantId)
            .Where(x => search == null ||
                        x.Email.Contains(search) ||
                        x.FullName.Contains(search))
            .ToListAsync(ct);

        var csv = new StringBuilder();
        csv.AppendLine("Id,Name,Email,Salary");

        foreach (var e in employees)
            csv.AppendLine($"{e.Id},{e.FullName},{e.Email},{e.Salary}");

        return File(
            Encoding.UTF8.GetBytes(csv.ToString()),
            "text/csv",
            "employees.csv");
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object-level/tenant authorization

- **Problem:** Bất kỳ authenticated Manager nào cũng có thể truyền một `tenantId` khác.
- **Why:** `[Authorize(Roles = "Manager")]` kiểm tra role nhưng không kiểm tra quyền trên resource tenant cụ thể.
- **Impact:** Cross-tenant sensitive-data disclosure.
- **Severity:** Critical
- **Fix:** Derive allowed tenant from trusted claims/server-side membership hoặc resource-based authorization; query phải luôn scope theo authorized tenant.

### 2. Export salary mà không chứng minh field-level permission

- **Problem:** Manager role mặc định được xuất `Salary`.
- **Impact:** Exposure dữ liệu nhạy cảm nếu business policy phân quyền salary riêng.
- **Severity:** High
- **Fix:** Xác nhận requirement; dùng explicit export DTO và policy/permission riêng cho sensitive fields.

### 3. CSV injection/formula injection

- **Problem:** Cell bắt đầu bằng `=`, `+`, `-`, `@` có thể được spreadsheet app diễn giải như formula tùy consumer.
- **Impact:** File export chứa user-controlled data có thể trở thành active spreadsheet content khi mở.
- **Severity:** High
- **Fix:** Dùng CSV writer đúng chuẩn và neutralize formula-leading cells theo threat model/client compatibility; không chỉ escape comma/quote.

### 4. Load toàn bộ entity set vào memory

- **Problem:** `ToListAsync` materialize toàn bộ rows, sau đó tạo thêm StringBuilder và byte array.
- **Impact:** Large allocations, GC pressure, request latency và có thể OOM dưới concurrent exports.
- **Severity:** High
- **Fix:** Project chỉ fields cần thiết, `AsNoTracking`, giới hạn export hoặc chuyển large export sang background job/object storage; streaming khi phù hợp.

### 5. CSV serialization không escape đúng

- **Problem:** Name/email chứa comma, quote hoặc newline làm hỏng cấu trúc file.
- **Impact:** Corrupt/misleading exports.
- **Severity:** Medium
- **Fix:** Dùng thư viện CSV đáng tin cậy hoặc implementation RFC-compatible có quoting/escaping đầy đủ.

### 6. Logging dùng string interpolation với raw search

- **Problem:** User-controlled text được đưa thẳng vào log message; mất structured properties và có thể tạo log pollution/PII leakage.
- **Impact:** Khó query logs, tăng exposure và có thể gây confusion nếu input chứa control characters.
- **Severity:** Medium
- **Fix:** Structured logging; không log raw search nếu không cần, hoặc sanitize/redact/hash theo mục đích quan sát.

### 7. Query/search chưa có guardrails

- **Problem:** Search tùy ý trên large tenant với contains predicates có thể đắt tùy provider/index/collation/query plan.
- **Impact:** DB CPU/latency tăng, đặc biệt với concurrent exports.
- **Severity:** Medium
- **Fix:** Validate length, xem generated SQL/query plan, thiết kế search/index theo access pattern; không tuyên bố một index thông thường chắc chắn giải quyết mọi `Contains`.

## Phiên bản code đề xuất

```csharp
[Authorize]
[HttpGet("export")]
public async Task<IActionResult> Export(
    Guid tenantId,
    string? search,
    CancellationToken ct)
{
    var authorization = await _authorization.AuthorizeAsync(
        User,
        tenantId,
        "CanExportEmployees");

    if (!authorization.Succeeded)
        return Forbid();

    search = string.IsNullOrWhiteSpace(search) ? null : search.Trim();
    if (search is { Length: > 100 })
        return BadRequest("Search is too long.");

    _logger.LogInformation(
        "Employee export requested for tenant {TenantId} by subject {Subject}",
        tenantId,
        User.FindFirst("sub")?.Value);

    var query = _db.Employees
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (search is not null)
    {
        query = query.Where(x =>
            x.Email.Contains(search) || x.FullName.Contains(search));
    }

    var rows = query
        .Select(x => new EmployeeExportRow(
            x.Id,
            x.FullName,
            x.Email));

    var stream = new MemoryStream();
    await using (var writer = new StreamWriter(
        stream, Encoding.UTF8, leaveOpen: true))
    {
        await _csvWriter.WriteAsync(writer, rows, ct);
    }

    stream.Position = 0;
    return File(stream, "text/csv", "employees.csv");
}
```

Ví dụ trên cố ý loại `Salary` trừ khi policy xác nhận quyền riêng cho field đó. Với export rất lớn, ngay cả `MemoryStream` vẫn chưa đủ tốt; recommended approach là background export có bounded query batches/streaming, lưu artifact ở storage có TTL và authorization khi download. `_csvWriter` phải xử lý CSV escaping và spreadsheet-formula safety theo threat model.

## Trade-offs

Resource-based authorization thêm policy code nhưng ngăn route parameter trở thành trust boundary. Synchronous streaming đơn giản cho export vừa/nhỏ; background export tốt hơn cho dataset lớn nhưng thêm queue, storage lifecycle, progress/status API và cleanup. Search optimization phải dựa trên provider và query plan thực tế thay vì áp dụng index theo thói quen.

## Cách kiểm thử

1. Manager tenant A gọi export tenant B phải nhận `403` và không query dữ liệu B.
2. User có role Manager nhưng thiếu export/salary permission không được nhận field nhạy cảm.
3. Rows chứa comma, quote, newline và formula-leading values phải tạo CSV an toàn, đúng cấu trúc.
4. Load test concurrent exports trên dataset lớn; theo dõi memory, GC, DB duration và cancellation.
5. Client cancel request/background export fail giữa chừng; resource phải được dispose và artifact dở dang không được public.

## Quan sát trong production

Ghi structured audit event gồm subject identifier, authorized tenant, export outcome, row count và duration nhưng tránh raw PII/search text không cần thiết. Theo dõi export request rate, authorization denials, DB query duration, rows exported, allocation/GC pressure, failures và canceled exports. Alert khi cross-tenant authorization anomalies hoặc export latency/error rate vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ enforce tenant isolation chỉ ở application layer hay thêm defense-in-depth ở database? Trade-off là gì?
2. Khi nào synchronous streaming tốt hơn background export?
3. Nếu PostgreSQL và SQL Server cùng được hỗ trợ, bạn sẽ đánh giá chiến lược search/index như thế nào mà không phụ thuộc giả định provider-specific?
