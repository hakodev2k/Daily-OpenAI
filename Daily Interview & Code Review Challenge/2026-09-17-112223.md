# Code Review Challenge 1 — Middleware audit đọc request body làm hỏng model binding và biến log thành data leak

**Chủ đề:** C#/.NET, ASP.NET Core middleware, request buffering, security, memory, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core API xử lý profile, checkout và file-import requests. Team thêm middleware để lưu request body phục vụ audit/debugging. Sau rollout, một số POST endpoint nhận model rỗng hoặc trả 400, memory tăng khi có request body lớn, và security review phát hiện access token cùng dữ liệu cá nhân xuất hiện trong log aggregation.

Production chạy nhiều instances trên Azure App Service Linux. Một số endpoint nhận JSON vài KB, nhưng import endpoint có thể nhận payload hàng chục MB. Request có thể bị client cancel. Business muốn giữ correlation và audit metadata, nhưng không có requirement phải lưu nguyên toàn bộ body của mọi request.

## Đoạn code cần review

```csharp
public sealed class RequestAuditMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestAuditMiddleware> _logger;

    public RequestAuditMiddleware(
        RequestDelegate next,
        ILogger<RequestAuditMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        string body;

        using (var reader = new StreamReader(context.Request.Body))
        {
            body = await reader.ReadToEndAsync();
        }

        _logger.LogInformation(
            "Request {Method} {Path} headers={Headers} body={Body}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers,
            body);

        var started = DateTime.UtcNow;

        await _next(context);

        _logger.LogInformation(
            "Request completed {Method} {Path} status={StatusCode} elapsedMs={ElapsedMs}",
            context.Request.Method,
            context.Request.Path,
            context.Response.StatusCode,
            (DateTime.UtcNow - started).TotalMilliseconds);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems ảnh hưởng request pipeline/model binding.
2. Xác định security, memory, performance và reliability concerns.
3. Giải thích production impact với body lớn, client cancellation và exception downstream.
4. Ưu tiên data exposure/correctness trước style issues.
5. Đề xuất thiết kế audit/logging an toàn hơn thay vì chỉ sửa stream position.
6. Giải thích testing cho JSON, large body, cancellation và sensitive data.
7. Nêu telemetry cần có để chứng minh middleware không gây regression.

## Câu hỏi gợi mở

1. Request body stream có mặc định cho phép đọc lại sau khi middleware consume không?
2. Điều gì xảy ra với Authorization, cookies, passwords hoặc payment/profile fields khi log toàn headers/body?
3. Một request 50 MB tạo allocation/lifetime gì khi `ReadToEndAsync()` biến toàn bộ body thành `string`?
4. Nếu `_next` throw exception, completion log hiện tại có được ghi không?
5. Middleware thực sự cần raw body hay chỉ cần route, identity, correlation, size và một số audit fields đã được allow-list?

## Gợi ý

### Gợi ý 1

Primary risks nằm ở request-stream semantics và việc biến untrusted/sensitive request data thành log data.

### Gợi ý 2

“Enable buffering rồi rewind” chỉ sửa một phần correctness. Bạn vẫn phải thiết kế giới hạn kích thước, redaction/allow-list, cancellation và failure-path logging.

## Kết quả code review tham khảo

### Critical — Log toàn bộ headers/body có thể làm lộ secrets và PII

**Vấn đề:** middleware ghi mọi header và raw request body vào log.  
**Tại sao xảy ra:** logging được xem như debug dump thay vì một data boundary có retention/access riêng. Authorization headers, cookies, credentials và business fields có thể chứa dữ liệu nhạy cảm.  
**Ảnh hưởng production:** secrets/PII bị nhân bản vào Application Insights/Elasticsearch/Kibana hoặc hệ thống log khác; phạm vi truy cập và retention thường rộng hơn transactional store.  
**Cách sửa:** mặc định không log raw body/headers. Dùng allow-list metadata/fields, explicit redaction, classification và environment-specific policy. Không cố sanitize secrets bằng blacklist không đầy đủ.

### High — Consume request body làm downstream không còn dữ liệu để đọc

**Vấn đề:** middleware đọc `Request.Body` đến cuối nhưng không chuẩn bị buffering và rewind.  
**Tại sao xảy ra:** request body là stream; đọc xong position ở cuối và không phải mọi stream đều seekable.  
**Ảnh hưởng production:** model binding/controller/minimal API downstream có thể thấy body rỗng hoặc request fail.  
**Cách sửa:** nếu thật sự cần inspect body, gọi buffering mechanism phù hợp trước khi đọc, giới hạn lượng đọc và reset position trước `_next`. Tốt hơn là tránh body capture toàn cục nếu audit requirement không cần nó.

### High — Unbounded `ReadToEndAsync()` tạo memory amplification

**Vấn đề:** toàn bộ payload được materialize thành `string`.  
**Tại sao xảy ra:** middleware không kiểm tra content type/length hoặc capture limit.  
**Ảnh hưởng production:** concurrent large requests tạo allocation pressure, GC/LOH pressure và có thể gây memory exhaustion; log payload còn tạo thêm serialization/network/storage cost.  
**Cách sửa:** không capture large/file/streaming bodies; nếu capture một phần JSON cho diagnostics, áp hard byte limit và content-type allow-list, đồng thời đánh dấu truncated.

### High — Dispose `StreamReader` có thể ảnh hưởng underlying request stream lifetime

**Vấn đề:** reader được dispose mà không chủ động giữ stream mở.  
**Tại sao xảy ra:** middleware không sở hữu lifetime của `Request.Body`.  
**Ảnh hưởng production:** downstream có thể gặp stream-disposal behavior ngoài ý muốn tùy wrapper/usage.  
**Cách sửa:** middleware không được coi request stream là resource của mình; nếu tạo reader cho shared stream, dùng ownership/lifetime semantics phù hợp và giữ stream usable cho downstream.

### Medium — Cancellation không được propagate vào body read

**Vấn đề:** read không gắn với `context.RequestAborted`.  
**Tại sao xảy ra:** middleware tiếp tục làm work dù client đã disconnect.  
**Ảnh hưởng production:** wasted CPU/memory/I/O dưới aborted uploads hoặc slow clients.  
**Cách sửa:** dùng cancellable read API/path và propagate `RequestAborted` nơi hỗ trợ; tránh expensive capture trước khi biết nó cần thiết.

### Medium — Completion telemetry biến mất khi downstream throw

**Vấn đề:** log completion chỉ chạy sau `_next` thành công.  
**Tại sao xảy ra:** không có `try/finally`.  
**Ảnh hưởng production:** failed requests thiếu duration/outcome telemetry chính lúc cần điều tra nhất.  
**Cách sửa:** đo duration bằng monotonic timer và emit completion/failure metadata trong `finally`, để exception middleware vẫn xử lý exception theo pipeline design.

### Medium — `DateTime.UtcNow` không phải lựa chọn tốt nhất để đo elapsed time

**Vấn đề:** wall-clock timestamp được trừ để đo duration.  
**Tại sao xảy ra:** wall clock phục vụ thời điểm, không tối ưu cho monotonic duration measurement.  
**Ảnh hưởng production:** telemetry duration có thể kém robust khi system clock điều chỉnh.  
**Cách sửa:** dùng `Stopwatch.GetTimestamp()`/`Stopwatch.GetElapsedTime()` cho duration.

### Medium — Logging cardinality/volume không được kiểm soát

**Vấn đề:** mỗi request tạo large structured log với arbitrary header/body values.  
**Tại sao xảy ra:** không có sampling/size policy/data classification.  
**Ảnh hưởng production:** ingestion/storage cost tăng, queries chậm và log signal bị chìm trong noise.  
**Cách sửa:** log stable low-cardinality metadata, metrics/traces cho latency; audit event chỉ chứa fields business đã định nghĩa.

### Low — Không phân biệt audit event với diagnostic log

**Vấn đề:** cùng logger event đang cố phục vụ security audit lẫn debugging.  
**Tại sao xảy ra:** hai use cases có retention, immutability, access và schema khác nhau.  
**Ảnh hưởng production:** khó đáp ứng cả operational troubleshooting và audit governance.  
**Cách sửa:** định nghĩa audit schema/sink/policy riêng nếu business thực sự yêu cầu audit trail.

## Phiên bản đề xuất

Thiết kế dưới đây mặc định chỉ log metadata an toàn. Một số endpoint có audit requirement cụ thể nên emit domain audit event ở application layer thay vì dump raw HTTP body.

```csharp
public sealed class RequestTelemetryMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? failure = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            failure = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.LogInformation(
                "HTTP {Method} {Path} status={StatusCode} elapsedMs={ElapsedMs} " +
                "contentLength={ContentLength} traceId={TraceId} outcome={Outcome}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.Request.ContentLength,
                context.TraceIdentifier,
                failure is null ? "completed" : "failed");
        }
    }
}

public sealed record ProfileAuditEvent(
    string Action,
    string SubjectId,
    string ActorId,
    DateTimeOffset OccurredAt,
    string CorrelationId);
```

Nếu một endpoint JSON đặc biệt cần diagnostic body capture tạm thời, implementation riêng phải có content-type allow-list, strict byte limit, redaction/allow-list fields, buffering + rewind đúng semantics và phải bỏ qua file/streaming endpoints. Không nên biến capability đó thành default toàn API.

## Giải thích thiết kế sau khi sửa

Request telemetry và business audit được tách trách nhiệm. Middleware quan sát method/path/status/duration/content length/correlation mà không copy payload. Audit event được tạo tại nơi application hiểu semantic fields nào cần lưu và fields nào nhạy cảm.

Điều này cũng làm observability tốt hơn: latency nên đi qua request telemetry/tracing/metrics thay vì parse raw body logs. Khi cần temporary deep diagnostics, capture phải là opt-in có giới hạn và governance rõ ràng.

## Trade-offs

Không log raw body làm giảm khả năng “mở log xem nguyên request”, nhưng đổi lại giảm security exposure, ingestion cost và memory risk. Domain audit yêu cầu thêm schema/code ở application layer, nhưng có semantics rõ và dễ kiểm soát retention/access. Limited diagnostic capture phức tạp hơn một `ReadToEndAsync`, vì correctness/security thực sự phức tạp hơn.

## Cách kiểm thử

1. **Integration test:** POST JSON qua middleware phải vẫn bind đầy đủ ở controller.
2. **Security test:** Authorization, Cookie, password/token/profile sensitive fields không xuất hiện trong captured logs.
3. **Load test:** concurrent large/file requests không làm memory tăng theo tổng raw body size do middleware.
4. **Cancellation test:** client abort large request; middleware không tiếp tục expensive body work và telemetry phản ánh aborted/failure path phù hợp.
5. **Failure-path test:** downstream throw; exception vẫn propagate tới error handler và completion/failure telemetry vẫn có duration/correlation.

## Quan sát trong production

Theo dõi request p95/p99, allocation/GC/memory, log ingestion bytes, average event size, aborted requests và error rate trước/sau rollout. Application Insights trace/dependency correlation nên dùng trace ID thay cho raw payload. Thiết lập security review cho audit sink, retention và access permissions.

## Câu hỏi phỏng vấn mở rộng

1. Nếu compliance bắt buộc lưu một phần request payload, bạn thiết kế encryption, retention và access boundary thế nào?
2. `EnableBuffering()` có những operational costs nào khi body vượt memory threshold và vì sao vẫn cần hard capture limit?
3. Nếu API dùng streaming upload, bạn đặt audit hook ở đâu để không phá streaming semantics?

# Code Review Challenge 2 — Playwright suite pass local nhưng flaky trên CI vì shared account và retry đang che data race

**Chủ đề:** Playwright, E2E testing, CI parallelism, test isolation, shared data, retries, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một enterprise portal có Playwright E2E suite chạy trong Jenkins. Local developer thường chạy một worker nên suite ổn. CI dùng 6 workers để giảm thời gian. Gần đây suite pass rate dao động; rerun thường pass nên team đặt `retries: 3`. Hai tests dưới đây dùng cùng một test account và cùng một timesheet record seed. Test đầu approve timesheet, test sau edit rồi submit lại. CI đôi khi báo expected `Draft` nhưng thấy `Approved`, hoặc login bị invalidate khi test khác chạy đồng thời.

QA muốn tăng retry lên 5 để pipeline “xanh ổn định hơn”. Team chưa lưu Playwright trace/video cho first failure và chưa gắn test-run ID vào test data.

## Đoạn code cần review

```ts
import { defineConfig, test, expect } from "@playwright/test";

export default defineConfig({
  workers: 6,
  retries: 3,
  use: {
    baseURL: process.env.BASE_URL,
    storageState: "playwright/.auth/user.json",
    screenshot: "only-on-failure"
  }
});

const employeeEmail = "e2e.employee@example.test";
const timesheetId = "TS-E2E-001";

test.beforeEach(async ({ page }) => {
  await page.goto(`/timesheets/${timesheetId}`);
});

test("manager can approve timesheet", async ({ page }) => {
  await page.getByRole("button", { name: "Approve" }).click();
  await expect(page.getByTestId("status")).toHaveText("Approved");
});

test("employee can edit draft timesheet", async ({ page, request }) => {
  await request.post(`/api/test-data/timesheets/${timesheetId}/reset`, {
    data: { employeeEmail }
  });

  await page.reload();
  await expect(page.getByTestId("status")).toHaveText("Draft");

  await page.getByLabel("Hours").fill("8");
  await page.getByRole("button", { name: "Save" }).click();

  await expect(page.getByText("Saved")).toBeVisible();
});
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/isolation problems trong test design.
2. Xác định reliability và CI parallelism concerns.
3. Giải thích vì sao retries có thể làm pipeline xanh nhưng giảm khả năng phát hiện defect.
4. Ưu tiên shared mutable state và authentication isolation.
5. Đề xuất test-data lifecycle/design có thể chạy song song an toàn.
6. Giải thích cách kiểm thử chính test infrastructure.
7. Nêu artifacts/telemetry cần giữ để điều tra first failure.

## Câu hỏi gợi mở

1. Hai workers có thể mutate cùng `TS-E2E-001` cùng lúc không?
2. `storageState` dùng chung có đảm bảo server-side session/token state độc lập giữa tests không?
3. Reset endpoint chạy trong test thứ hai có thể thay đổi dữ liệu mà test thứ nhất đang dùng không?
4. Retry test với cùng mutable data có thực sự tái hiện cùng initial state không?
5. Khi chỉ giữ screenshot của lần fail cuối, evidence nào của first failure đã bị mất?

### Gợi ý 1

Primary problem là test isolation, không phải assertion timeout.

### Gợi ý 2

Parallel workers biến shared account/shared record thành concurrent production-like actors. Retry có thể đổi scheduling/interleaving và làm race biến mất thay vì sửa nó.

## Kết quả code review tham khảo

### High — Shared mutable timesheet làm tests không độc lập

**Vấn đề:** mọi worker dùng cùng `TS-E2E-001`; approve/reset/edit cùng một record.  
**Tại sao xảy ra:** test data được coi là global fixture thay vì resource scoped theo test/run/worker.  
**Ảnh hưởng production CI:** interleaving làm state phụ thuộc execution order; test có thể fail hoặc pass vì test khác, không phải behavior đang kiểm chứng.  
**Cách sửa:** tạo unique timesheet per test hoặc per worker bằng API/fixture; ID gắn run/test identity; cleanup riêng và idempotent.

### High — Shared authentication state có thể tạo cross-test coupling

**Vấn đề:** toàn suite dùng cùng `storageState` và account, trong khi scenario cần manager và employee roles khác nhau.  
**Tại sao xảy ra:** browser state file được reuse nhưng server-side identity/session constraints chưa được xác minh.  
**Ảnh hưởng production CI:** logout/token rotation/session invalidation hoặc role mismatch ở một test ảnh hưởng test khác.  
**Cách sửa:** tạo role-specific authenticated fixtures/accounts; nếu backend giới hạn concurrent sessions, cấp identity per worker hoặc dùng deterministic test identity provisioning.

### High — Reset endpoint chạy sau navigation và có thể race với test khác

**Vấn đề:** `beforeEach` load shared record trước khi test reset nó; reset còn có thể phá state của approval test.  
**Tại sao xảy ra:** setup không atomic/scoped và thứ tự setup/UI navigation sai.  
**Ảnh hưởng production CI:** UI thấy state cũ/mới không deterministic; network/cache/state transitions tạo flakes khó tái hiện.  
**Cách sửa:** provision state trước navigation; resource phải unique cho test.

### Medium — Retries che nondeterministic test infrastructure

**Vấn đề:** `retries: 3` được dùng như reliability fix.  
**Tại sao xảy ra:** retry thay đổi scheduling và có thể gặp state đã khác.  
**Ảnh hưởng production CI:** pipeline xanh dù test architecture có race; defect thực có thể bị giảm signal.  
**Cách sửa:** giữ retry policy nhỏ/chủ đích nếu cần cho environment transients, nhưng đo retry rate và coi “passed on retry” là quality signal cần điều tra.

### Medium — Retry không đảm bảo clean initial state

**Vấn đề:** retry cùng test có thể dùng record đã bị mutation từ attempt trước.  
**Tại sao xảy ra:** setup/reset không tạo resource mới cho từng attempt.  
**Ảnh hưởng production CI:** attempt 2 không kiểm chứng cùng precondition với attempt 1.  
**Cách sửa:** fixture provisioning phải idempotent hoặc tạo unique data per attempt/test; teardown không được là điều kiện duy nhất để test sau đúng.

### Medium — Thiếu first-failure trace/video/network evidence

**Vấn đề:** chỉ screenshot khi failure.  
**Tại sao xảy ra:** config không giữ trace/video hữu ích cho race/navigation/network issue.  
**Ảnh hưởng production CI:** rerun pass làm mất interleaving/evidence của failure gốc.  
**Cách sửa:** giữ trace trên first retry/failure theo policy phù hợp, attach server correlation/test-run ID và retain artifacts cho flaky failures.

### Medium — Test data endpoint có thể trở thành unsafe production surface

**Vấn đề:** `/api/test-data/.../reset` được gọi như một normal endpoint; snippet không thể hiện environment/auth guard.  
**Tại sao xảy ra:** test-support API có khả năng mutate business data mạnh.  
**Ảnh hưởng production:** nếu deploy/authorize sai, endpoint có thể trở thành security/integrity risk.  
**Cách sửa:** test-only deployment capability hoặc strongly gated internal fixture service; verify endpoint không tồn tại/không accessible trong production.

### Low — Hard-coded data làm parallel scaling khó

**Vấn đề:** email/ID global constants.  
**Tại sao xảy ra:** fixture design không expose resource factory.  
**Ảnh hưởng production CI:** tăng workers/sharding làm flakes tăng.  
**Cách sửa:** worker/test-scoped fixture sinh deterministic unique identifiers.

## Phiên bản đề xuất

Ví dụ dưới dùng fixtures để tạo identity/data riêng cho từng test. Chi tiết provisioning endpoint là scenario assumption và phải được bảo vệ ngoài production.

```ts
import { test as base, expect, type APIRequestContext } from "@playwright/test";

interface TimesheetFixture {
  id: string;
  employeeEmail: string;
}

type Fixtures = {
  draftTimesheet: TimesheetFixture;
};

async function createDraftTimesheet(
  request: APIRequestContext,
  testKey: string
): Promise<TimesheetFixture> {
  const response = await request.post("/api/test-support/timesheets", {
    data: { testKey, state: "Draft" }
  });

  expect(response.ok()).toBeTruthy();
  return await response.json();
}

const test = base.extend<Fixtures>({
  draftTimesheet: async ({ request }, use, testInfo) => {
    const testKey = `${testInfo.workerIndex}-${testInfo.retry}-${testInfo.testId}`;
    const timesheet = await createDraftTimesheet(request, testKey);

    await use(timesheet);

    await request.delete(`/api/test-support/timesheets/${timesheet.id}`);
  }
});

test("employee can edit draft timesheet", async ({
  page,
  draftTimesheet
}) => {
  await page.goto(`/timesheets/${draftTimesheet.id}`);
  await expect(page.getByTestId("status")).toHaveText("Draft");

  await page.getByLabel("Hours").fill("8");
  await page.getByRole("button", { name: "Save" }).click();

  await expect(page.getByText("Saved")).toBeVisible();
});
```

Role-specific tests nên dùng manager/employee fixtures riêng thay vì một shared `storageState`. Playwright config có thể retain trace cho first retry/failure và CI artifact pipeline phải giữ nó cùng test-run correlation.

## Giải thích thiết kế sau khi sửa

Mỗi test sở hữu data riêng nên execution order và worker scheduling không ảnh hưởng correctness. Retry cũng tạo key/resource riêng theo attempt, tránh việc attempt trước làm thay đổi precondition. Authentication được coi là một fixture/resource cần isolation tương tự business data.

Test-support capability cần được thiết kế như infrastructure: deterministic, observable, cleanup được và không exposed ở production. E2E suite không nên phụ thuộc vào một global record mà con người hoặc worker khác có thể mutate.

## Trade-offs

Per-test provisioning tăng setup time và số API/database operations, nhưng đổi lại suite có thể parallelize đáng tin cậy. Có thể provision per worker nếu data creation quá đắt, nhưng khi đó tests trong worker vẫn phải tránh shared mutation. Retry có thể giữ cho network/environment transient đã hiểu rõ, nhưng retry count cao làm chậm CI và che quality signal.

## Cách kiểm thử

1. **Parallel stress:** chạy suite nhiều lần với 6–12 workers; không test nào dùng cùng business record/account nếu isolation yêu cầu riêng.
2. **Order randomization:** đổi test order/sharding; kết quả không thay đổi.
3. **Retry validation:** cố ý fail attempt đầu sau mutation; retry phải bắt đầu từ independent clean fixture.
4. **Playwright E2E artifact test:** tạo controlled failure và verify trace/screenshot/correlation được publish vào Jenkins artifacts.
5. **Security/deployment validation:** production environment không expose test-support mutation endpoints/credentials.

## Quan sát trong production

Ở CI, theo dõi first-attempt pass rate, retry rate, flaky test frequency, test duration p95, fixture provisioning failures và worker/shard identity. Lưu trace cho failure/retry theo retention policy. Backend test environment nên log `testRunId/testId` để correlate API/database operations với Playwright artifact mà không dựa vào shared account name.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận serial test thay vì đầu tư vào isolated fixtures?
2. Nếu provisioning mỗi test làm CI chậm gấp đôi, bạn tối ưu ở đâu mà không quay lại shared mutable data?
3. Làm sao phân biệt product flake thật với test-infrastructure flake bằng evidence thay vì rerun thủ công?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Middleware là một phần của runtime pipeline nên phải tôn trọng stream ownership, request lifecycle, cancellation và data-security boundary. Logging nhiều hơn không đồng nghĩa observability tốt hơn; raw payload có thể vừa phá pipeline vừa tạo security/memory risk.

E2E reliability phụ thuộc mạnh vào test isolation. Parallel workers và retries làm shared mutable state trở thành race condition. Một suite “xanh sau retry” không chứng minh hệ thống ổn nếu attempt đầu thất bại vì infrastructure nondeterminism.

## Mẫu tư duy cần nhớ

- Không consume hoặc sở hữu shared runtime resource nếu chưa hiểu lifecycle của nó.
- Log metadata có mục đích; đừng biến logs thành bản sao không kiểm soát của sensitive payload.
- Đặt hard bounds cho work phụ thuộc input size.
- Parallel tests cần data và identity ownership rõ ràng.
- Retry là resilience mechanism, không phải cách sửa nondeterminism.
