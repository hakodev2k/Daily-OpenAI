# Câu 1 — Configuration đã đổi nhưng service vẫn dùng giá trị cũ: IOptions, IOptionsSnapshot và IOptionsMonitor thực sự khác nhau ở đâu?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET 8, ASP.NET Core, dependency injection, configuration, Options Pattern, service lifetime, configuration reload, singleton/scoped services, production diagnostics

## Bối cảnh

Một ASP.NET Core .NET 8 API đọc cấu hình pricing và feature switches từ configuration providers. Team bọc cấu hình bằng Options Pattern:

~~~csharp
public sealed class PricingOptions
{
    public decimal MaxDiscountPercent { get; set; }
    public bool UseNewPricingEngine { get; set; }
}

builder.Services.Configure<PricingOptions>(
    builder.Configuration.GetSection("Pricing"));

builder.Services.AddSingleton<PricingGateway>();
builder.Services.AddScoped<CheckoutService>();

public sealed class PricingGateway
{
    private readonly PricingOptions _options;

    public PricingGateway(IOptions<PricingOptions> options)
    {
        _options = options.Value;
    }

    public decimal ClampDiscount(decimal requested)
        => Math.Min(requested, _options.MaxDiscountPercent);
}

public sealed class CheckoutService
{
    private readonly IOptionsSnapshot<PricingOptions> _options;

    public CheckoutService(IOptionsSnapshot<PricingOptions> options)
    {
        _options = options;
    }

    public bool ShouldUseNewEngine()
        => _options.Value.UseNewPricingEngine;
}
~~~

Trong production, team thay đổi configuration source mà application đang dùng. Sau đó họ quan sát:

- một số request mới phản ánh giá trị feature switch mới;
- PricingGateway vẫn hành xử như trước;
- restart application khiến tất cả hành vi đồng nhất;
- một developer cho rằng mọi IOptions<T> đều tự động đọc IConfiguration mỗi lần truy cập Value;
- một developer khác muốn inject IOptionsSnapshot<T> vào singleton để “luôn lấy config mới”;
- application chạy nhiều instances nên thời điểm từng process nhận configuration change có thể khác nhau;
- chưa xác minh configuration provider hiện tại có hỗ trợ change notifications/reload hay không.

## Câu hỏi chính

Hãy giải thích cơ chế và lifetime semantics của IOptions<T>, IOptionsSnapshot<T> và IOptionsMonitor<T> trong ASP.NET Core. Vì sao cùng một configuration change có thể được quan sát khác nhau giữa PricingGateway và CheckoutService? Khi nào configuration thực sự có thể reload mà không restart? Bạn sẽ chọn pattern nào cho singleton, scoped request service và configuration có yêu cầu thay đổi runtime, đồng thời xác minh behavior trong production bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

1. Configuration provider cụ thể là gì và provider đó có hỗ trợ reload/change token hay chỉ đọc lúc startup?
2. Giá trị có cần thay đổi ngay trong runtime hay business chấp nhận restart/deployment để áp dụng?
3. PricingGateway có phải singleton vì lý do kỹ thuật thực sự hay chỉ vì đăng ký mặc định?
4. Có yêu cầu một request phải dùng một configuration snapshot nhất quán từ đầu tới cuối không?
5. Application chạy bao nhiêu instances và có yêu cầu tất cả instances chuyển configuration gần như đồng thời không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu từ tên interface. Hãy nối Options abstraction với DI lifetime và thời điểm một options value được tạo/cache.

### Gợi ý 2

Configuration reload chỉ có ý nghĩa khi provider phát hiện thay đổi. Options abstraction không tự tạo khả năng reload cho một provider vốn không hỗ trợ nó.

### Gợi ý 3

Phân biệt hai yêu cầu: “giá trị mới cho request mới” và “singleton cần quan sát thay đổi trong suốt lifetime của process”.

## Cấu trúc trả lời đề xuất

1. Làm rõ provider và reload requirement.
2. Giải thích IOptions<T> và lifetime/cache behavior.
3. Giải thích IOptionsSnapshot<T> theo scope/request.
4. Giải thích IOptionsMonitor<T> và change notifications/current value.
5. Nối từng interface với singleton/scoped/transient usage.
6. Phân tích consistency trong một request và giữa nhiều instances.
7. Đề xuất implementation phù hợp với business semantics.
8. Xác minh bằng integration test và production telemetry.
9. Xác định rollback/failure behavior cho invalid configuration.

## Ý chính của câu trả lời tốt

### Bắt buộc

- IOptions<T> phù hợp với configuration được dùng như một value ổn định trong lifetime của application; không nên giả định Value đọc lại IConfiguration mỗi lần.
- IOptionsSnapshot<T> tạo snapshot theo scope và thường phù hợp với scoped dependencies như ASP.NET Core request scope; request mới có thể lấy value mới nếu underlying configuration/options pipeline đã thay đổi.
- IOptionsMonitor<T> được thiết kế để quan sát current options qua lifetime dài hơn và hỗ trợ change notifications khi underlying configuration source/options pipeline phát change.
- Không nên inject scoped IOptionsSnapshot<T> trực tiếp vào singleton vì lifetime mismatch.
- Configuration provider phải hỗ trợ reload/change notifications thì runtime update mới có thể propagate; Options Pattern không tự biến static configuration thành dynamic.
- Với multi-instance deployment, runtime reload không tự đảm bảo distributed atomic switch giữa tất cả processes.
- Dynamic configuration cần validation và failure semantics rõ; “config mới” không mặc định là “config hợp lệ”.

### Điểm cộng

- Nhận ra việc constructor của PricingGateway copy options.Value vào field làm behavior cố định theo value được resolve tại construction time.
- Đề xuất IOptionsMonitor<PricingOptions> cho singleton nếu business thật sự cần dynamic value, hoặc chuyển gateway sang scoped nếu per-request snapshot semantics phù hợp hơn.
- Với logic nhạy cảm như pricing, cân nhắc snapshot một immutable configuration/version cho cả operation thay vì đọc CurrentValue nhiều lần giữa transaction để tránh cùng một operation thấy hai versions.
- Sử dụng Validate, ValidateOnStart hoặc custom validation phù hợp để reject cấu hình sai.
- Ghi config version/hash không nhạy cảm vào telemetry để xác định instance nào đang dùng version nào.

### Senior+

- Phân biệt application configuration với feature-management/control-plane requirements: nếu cần coordinated rollout, percentage rollout, audit và instant rollback, chỉ dựa vào generic config reload có thể không đủ.
- Nhận ra OnChange callback không nên làm expensive/blocking work hoặc tạo unsafe mutation mà không có synchronization strategy.
- Thiết kế fail-safe behavior nếu new configuration parse/validation thất bại.
- Nêu được vấn đề distributed consistency: mỗi process có cache/lifetime riêng, nên coordinated business change cần versioning hoặc deployment/control-plane semantics rõ ràng.

## Hướng giải quyết tham khảo

IOptions<T>, IOptionsSnapshot<T> và IOptionsMonitor<T> giải quyết các lifetime semantics khác nhau.

IOptions<T> thường được dùng khi options về cơ bản ổn định. Nếu singleton PricingGateway được tạo một lần và constructor lưu options.Value vào _options, object đó sẽ tiếp tục dùng value đã lấy ở thời điểm construction. Việc configuration source thay đổi về sau không tự mutate object đã copy vào field.

IOptionsSnapshot<T> phù hợp với scope. Trong ASP.NET Core, request thường tạo một DI scope, nên CheckoutService mới ở request mới có thể nhận snapshot mới. Một request đang chạy sẽ giữ semantics snapshot của scope đó, điều này thường hữu ích khi muốn business operation không thay configuration giữa chừng.

IOptionsMonitor<T> phù hợp với singleton hoặc component có lifetime dài cần quan sát current value. Ví dụ:

~~~csharp
public sealed class PricingGateway
{
    private readonly IOptionsMonitor<PricingOptions> _options;

    public PricingGateway(IOptionsMonitor<PricingOptions> options)
    {
        _options = options;
    }

    public decimal ClampDiscount(decimal requested)
    {
        var current = _options.CurrentValue;
        return Math.Min(requested, current.MaxDiscountPercent);
    }
}
~~~

Nhưng lựa chọn trên chỉ đúng nếu pricing rule có thể thay đổi giữa operations và provider thực sự phát change. Nếu một checkout có nhiều bước, đọc CurrentValue ở từng bước có thể khiến cùng checkout dùng hai config versions khi change xảy ra giữa chừng. Khi đó tốt hơn là lấy một snapshot/version ở operation boundary:

~~~csharp
public sealed class CheckoutService
{
    private readonly PricingOptions _optionsForRequest;

    public CheckoutService(IOptionsSnapshot<PricingOptions> options)
    {
        _optionsForRequest = options.Value;
    }

    public CheckoutResult Execute(CheckoutCommand command)
    {
        // All calculations in this scoped operation use one snapshot.
        return Calculate(command, _optionsForRequest);
    }
}
~~~

Điểm phải xác minh đầu tiên trong incident là configuration provider. JSON provider có thể được cấu hình reload-on-change; provider khác có thể có semantics khác. Nếu provider không phát change token, đổi sang IOptionsMonitor cũng không làm dữ liệu tự cập nhật.

Kế hoạch xác minh:

- log một config version/hash không chứa secret ở startup và OnChange;
- xác định instance ID trong telemetry;
- test provider change trong integration environment;
- kiểm tra request trước/sau change trên nhiều instances;
- xác minh invalid value bị reject hoặc xử lý theo policy;
- kiểm tra singleton/scoped behavior bằng tests thay vì chỉ nhìn UI;
- nếu cần distributed coordinated switch, dùng explicit version/feature management mechanism thay vì giả định mọi instance reload cùng thời điểm.

Ví dụ validation:

~~~csharp
builder.Services
    .AddOptions<PricingOptions>()
    .Bind(builder.Configuration.GetSection("Pricing"))
    .Validate(
        x => x.MaxDiscountPercent >= 0 &&
             x.MaxDiscountPercent <= 100,
        "MaxDiscountPercent must be between 0 and 100.")
    .ValidateOnStart();
~~~

Nếu business cho phép config chỉ thay qua deployment, solution đơn giản nhất có thể là IOptions<T> + immutable deployment configuration, thay vì thêm runtime reload complexity.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xác minh provider trước vì Options không tự tạo runtime reload. IOptions thường phù hợp với value ổn định; trong ví dụ singleton PricingGateway lấy options.Value lúc được tạo rồi giữ object đó nên thay config về sau không có nghĩa gateway tự đổi. IOptionsSnapshot có scope semantics, nên request mới có thể lấy snapshot mới và một request giữ một version nhất quán. IOptionsMonitor phù hợp hơn cho singleton cần CurrentValue hoặc OnChange.

Em không inject IOptionsSnapshot vào singleton vì lifetime mismatch. Nếu pricing rule thật sự cần thay runtime, em cân nhắc IOptionsMonitor nhưng vẫn quyết định snapshot ở operation boundary nếu một checkout phải dùng cùng config version từ đầu đến cuối.

Em cũng kiểm tra provider có reload/change token không, validate config mới, và instrument config version + instance ID. Vì app chạy nhiều instances, reload không phải distributed atomic switch. Nếu business yêu cầu coordinated rollout/audit/rollback thì em dùng một control mechanism có version rõ hơn thay vì giả định mọi process đổi cùng lúc.”

## Câu hỏi đào sâu

1. Nếu IOptionsMonitor.OnChange chạy nhưng một callback ném exception hoặc thực hiện work rất chậm, bạn thiết kế callback và observability thế nào?
2. Nếu business yêu cầu mọi checkout bắt đầu sau 10:00:00 phải dùng pricing version V42 trên tất cả instances, generic runtime config reload có đủ không?
3. Nếu team muốn “đơn giản hóa” bằng cách biến tất cả services thành scoped và dùng IOptionsSnapshot ở mọi nơi, bạn sẽ đồng ý hay phản biện dựa trên tiêu chí nào?

## Lỗi trả lời thường gặp

- Nói mọi IOptions interface đều đọc IConfiguration trực tiếp mỗi lần Value được access.
- Inject IOptionsSnapshot vào singleton mà bỏ qua lifetime mismatch.
- Chọn IOptionsMonitor nhưng không kiểm tra provider có hỗ trợ reload hay không.
- Không xét consistency của cùng một business operation khi config đổi giữa chừng.
- Coi runtime configuration change trên nhiều instances là atomic distributed update.

## Thang điểm 0–10

- **0–2:** chỉ nhớ tên ba interfaces, không giải thích lifetime/mechanism.
- **3–4:** biết Snapshot và Monitor có thể cập nhật nhưng không nối với scope/provider.
- **5–6:** giải thích đúng lifetime, provider reload requirement và singleton/scoped use.
- **7–8:** có validation, per-operation consistency, multi-instance telemetry và test strategy.
- **9–10:** phân tích distributed rollout semantics, config versioning, invalid-change failure mode và biết khi nào runtime reload complexity không đáng có.

# Câu 2 — Release qua TeamCity + Octopus làm 500 tăng mạnh: database migration, mixed-version deployment hay configuration mới là thủ phạm?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET 8, TeamCity, Octopus Deploy, SQL Server, EF Core migrations, CI/CD, backward-compatible deployment, rollout, rollback, configuration, observability, incident response, production support

## Bối cảnh

Một enterprise ASP.NET Core API được build bằng TeamCity và deploy bằng Octopus Deploy lên 6 application instances sau load balancer. Database SQL Server dùng chung.

Release mới gồm:

- application binary mới;
- một EF Core migration đổi cấu trúc bảng Orders;
- một configuration key mới;
- một background worker mới đọc cùng bảng Orders;
- deployment rolling theo từng instance, không downtime có chủ đích.

Khoảng 4 phút sau khi release bắt đầu:

- HTTP 500 tăng từ gần 0 lên khoảng 18%;
- một số instances vẫn trả 200;
- lỗi tập trung ở endpoint update order;
- database CPU không tăng đáng kể;
- logs của một số instances báo “invalid column”, một số lại báo validation/conversion error;
- deployment dashboard cho thấy application version cũ và mới cùng chạy trong vài phút;
- migration step đã chạy trước khi tất cả old instances được drain;
- team chưa xác minh migration là additive hay destructive;
- configuration variable có scope theo environment/role trong Octopus;
- background worker mới bắt đầu chạy ngay sau instance đầu tiên được nâng cấp;
- release manager muốn rollback application package ngay lập tức;
- chưa biết database schema sau migration có backward-compatible với old binary hay không.

## Câu hỏi chính

Bạn đang xử lý incident production này. Hãy trình bày cách bạn **ổn định hệ thống, thu evidence, phân biệt competing hypotheses và quyết định rollback/roll-forward an toàn**. Sau đó đề xuất release strategy cho các thay đổi application + database + configuration để mixed-version deployment không gây lỗi tương tự. Không được mặc định migration là root cause trước khi xác minh.

## Câu hỏi làm rõ nên cân nhắc

1. Migration đã thực hiện chính xác DDL nào: thêm column nullable, rename/drop column, đổi type hay backfill dữ liệu?
2. Error rate có correlate với application instance/version nào hay với tất cả instances?
3. Configuration key mới có giá trị khác nhau theo Octopus scope hoặc missing ở một subset instances không?
4. Background worker mới có write data theo format mà old application không hiểu không?
5. Có health/drain mechanism để ngăn traffic tới instance đang deploy và có capability tạm dừng worker hay không?

## Gợi ý tư duy

### Gợi ý 1

Trước tiên tạo timeline: migration, instance rollout, worker start, error spike và configuration resolution.

### Gợi ý 2

Trong rolling deployment, database schema và shared data phải chịu được **old + new binaries cùng tồn tại** trong một khoảng thời gian.

### Gợi ý 3

Rollback application chỉ an toàn nếu database/data changes vẫn tương thích với old version. Nếu migration destructive, “rollback binary” có thể làm incident nặng hơn.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact.
2. Tạm dừng rollout hoặc worker để giảm biến số.
3. Thu timeline theo deployment/version/instance.
4. Correlate 500 với instance, exception và database schema.
5. Liệt kê hypotheses: schema compatibility, config scope, worker write format, deployment artifact.
6. Xác minh từng hypothesis bằng evidence.
7. Chọn rollback hoặc roll-forward dựa trên compatibility.
8. Sửa dữ liệu/schema nếu cần với recovery plan.
9. Thiết kế expand/migrate/contract cho release sau.
10. Add deployment validation, tests và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không deploy tiếp một release đang gây 18% 500 chỉ để “xem có tự hết không”; cân nhắc pause rollout và stabilize.
- Phải correlate error với application version/instance và exact migration/config timeline.
- Rolling deployment tạo mixed-version window; shared database schema phải tương thích với cả old và new applications trong window đó.
- Destructive migration như rename/drop/change incompatible type trước khi old instances rời traffic có thể phá old binary.
- Application rollback không tự rollback database schema/data.
- Configuration scope lỗi có thể tạo subset instances fail dù artifact giống nhau.
- Background worker mới có thể thay đổi shared data state và cần được xem như một participant trong deployment.
- Rollback/roll-forward phải dựa trên schema/data compatibility, không dựa vào phản xạ.
- Cần deployment health checks và post-deploy verification trước khi tiếp tục wave.

### Điểm cộng

- Dùng additive expand/contract migration: add new schema first, deploy backward-compatible app, migrate/backfill, switch reads/writes, rồi drop old schema ở release sau.
- Tách schema migration khỏi application rollout khi cần kiểm soát rõ ordering.
- Gắn build version, deployment ID và instance ID vào logs/traces.
- Có automated smoke test/canary gate sau mỗi wave.
- Validate required configuration trước khi instance được coi healthy.
- Worker có feature flag/activation gate để không chạy trước khi schema/data prerequisites sẵn sàng.

### Senior+

- Nhận ra dual-read/dual-write có complexity và chỉ dùng nếu transition thực sự cần; không biến mọi migration thành framework phức tạp.
- Phân tích data backfill load và lock impact thay vì chỉ DDL compatibility.
- Đề xuất migration idempotency/ownership để nhiều app instances không tự chạy migration cạnh tranh.
- Xem deployment là state machine với preconditions, health gates và irreversible steps.
- Có runbook cho “database already changed, application rollback requested”.

## Hướng giải quyết tham khảo

### 1. Stabilize

Với error rate 18%, tôi sẽ pause rollout nếu platform/process cho phép, tránh đưa thêm instances vào unknown state. Nếu background worker mới có thể tạo writes làm tăng inconsistency, cân nhắc tạm disable worker bằng cơ chế đã được thiết kế an toàn.

Không nên rollback package ngay trước khi biết database schema/data hiện tại có tương thích với old version hay không.

### 2. Evidence

Tạo timeline:

- T0: migration start/end;
- T1..T6: từng instance đổi version;
- thời điểm worker mới start;
- thời điểm config variable resolution;
- thời điểm first 500.

Mỗi request trace/log cần có applicationVersion và instanceId. Sau đó group errors:

~~~text
version old → invalid column?
version new → validation/conversion error?
specific role → missing config?
worker active → malformed/new-format rows?
~~~

Kiểm tra schema trực tiếp và migration history. Lấy exact exception/SQL, không suy luận từ message rút gọn.

### 3. Competing hypotheses

**Hypothesis A — destructive/incompatible migration.**  
Nếu migration rename/drop một column mà old app vẫn query, old instances sẽ fail trong mixed-version window.

**Hypothesis B — config scope mismatch.**  
Nếu new key chỉ được set cho một Octopus role, subset new instances có thể fail.

**Hypothesis C — worker writes incompatible data.**  
Worker mới có thể ghi enum/state/format mà old app không parse được.

**Hypothesis D — application defect độc lập.**  
New binary có thể có logic bug không liên quan migration.

Có thể nhiều nguyên nhân cùng tồn tại. “Invalid column” và “conversion error” gợi ý ít nhất hai failure paths cần tách.

### 4. Rollback vs roll-forward

Nếu schema change additive và old app vẫn tương thích, rollback binaries có thể là cách stabilize nhanh.

Nếu migration đã drop/rename schema mà old binary cần, rollback binary trước khi restore compatibility sẽ làm nhiều failures hơn. Khi đó có thể phải roll forward nhanh bằng compatibility patch hoặc restore compatibility column/view trước, tùy exact schema/data.

Database rollback bằng down migration cũng không mặc định an toàn: migration có thể mất data hoặc không reverse được backfill. Phải đọc exact migration.

### 5. Future deployment strategy

Ví dụ đổi Orders.CustomerCode thành AccountCode:

**Release A — Expand**

~~~sql
ALTER TABLE Orders
ADD AccountCode nvarchar(50) NULL;
~~~

Deploy application có thể đọc AccountCode nếu có nhưng vẫn tương thích CustomerCode. Nếu write transition cần thiết, có thể dual-write trong bounded period.

**Migration/backfill**

Backfill theo batches, theo dõi locks/log growth/latency.

**Release B — Switch**

New version dùng AccountCode làm authoritative sau khi validation cho thấy backfill hoàn tất.

**Release C — Contract**

Chỉ sau khi không còn old binary/consumer nào dùng CustomerCode mới drop old column.

Không phải migration nào cũng cần ba releases. Add-only schema có thể đơn giản hơn. Nguyên tắc là destructive step phải xảy ra sau khi consumers cũ không còn phụ thuộc.

### 6. Configuration

Required configuration nên được validate ở startup/readiness:

~~~csharp
builder.Services
    .AddOptions<OrderWorkerOptions>()
    .BindConfiguration("OrderWorker")
    .ValidateDataAnnotations()
    .ValidateOnStart();
~~~

Octopus variable scope phải được review như code/configuration, tránh một role nhận value khác ngoài ý muốn.

### 7. Worker activation

Worker mới có thể được deploy disabled, rồi enable sau schema/data validation. Nếu worker có side effects, activation phải có explicit release step và rollback semantics.

### 8. Verification

- smoke tests cho create/update/read order;
- mixed-version compatibility tests trong staging;
- migration test trên realistic data volume;
- config validation;
- canary/wave rollout;
- error-rate gate trước khi tiếp tục;
- rollback rehearsal với schema đã migrate.

## Mẫu trả lời trong phỏng vấn

“Em sẽ pause rollout trước để giảm biến số, nhưng chưa rollback binary ngay vì database đã migrate. Em tạo timeline migration → từng instance rollout → worker start → first errors, rồi group 500 theo application version và instance. Invalid-column có thể là schema incompatibility, nhưng conversion errors cũng có thể đến từ worker/data hoặc config, nên em giữ nhiều hypotheses.

Điểm quan trọng là rolling deployment luôn có mixed-version window. Shared schema phải tương thích old và new versions. Nếu migration destructive chạy trước khi old nodes drain thì old binary có thể fail. Nhưng nếu database đã thay đổi không backward-compatible, rollback application package lại có thể làm lỗi nặng hơn.

Sau incident em chuyển migrations sang expand/migrate/contract khi thay đổi destructive: add schema trước, deploy code tương thích cả hai, backfill có kiểm soát, chuyển reads/writes, rồi contract ở release sau. Em validate config at startup, gate worker activation, log version/instance/deployment ID, và có canary/smoke/error-rate gate từng wave. Rollback chỉ được thực hiện khi đã biết schema/data compatibility.”

## Câu hỏi đào sâu

1. Nếu migration chỉ add nullable column nhưng new worker ghi enum value mà old app không hiểu, expand/contract schema có đủ để giải quyết không?
2. Nếu Product yêu cầu zero-downtime nhưng database change là đổi một column từ string sang integer trên 500 triệu rows, bạn thiết kế transition thế nào?
3. Một teammate đề xuất luôn chạy EF Core migrations tự động ở startup trên tất cả 6 instances để “đỡ bước Octopus”; bạn đánh giá recommendation đó ra sao?

## Lỗi trả lời thường gặp

- Rollback application ngay mà không kiểm tra database compatibility.
- Thấy “invalid column” rồi kết luận toàn bộ incident chỉ có một root cause.
- Deploy destructive migration trước application trong rolling deployment.
- Không include background workers và configuration scopes trong release reasoning.
- Đề xuất expand/contract như công thức bắt buộc cho mọi migration mà không xét complexity/cost.

## Thang điểm 0–10

- **0–2:** chỉ nói rollback/redeploy.
- **3–4:** nhận ra migration ordering nhưng chưa có evidence plan.
- **5–6:** có mixed-version reasoning, correlation, rollback compatibility và deployment gates.
- **7–8:** có expand/contract, config/worker handling, realistic migration tests và observability.
- **9–10:** xử lý deployment như distributed state transition, phân tích irreversible data changes, rollout safety và chọn strategy conditional theo exact migration/business constraints.

# Câu 3 — Audit trail và activity history nên dùng SQL Server hay MongoDB, và có cần tách thành service riêng ngay từ đầu không?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** SQL Server, MongoDB, document modeling, indexing, consistency, audit trail, data retention, security, architecture boundaries, Modular Monolith, microservices, background processing, observability, scalability, trade-offs

## Bối cảnh

Một enterprise management platform hiện là ASP.NET Core modular application dùng SQL Server. Product muốn thêm hai capability:

1. **Audit Trail** — lưu thay đổi quan trọng như ai đổi trạng thái Project, sửa quyền truy cập, cập nhật Finance record. Audit phải đủ tin cậy cho điều tra và không được sửa/xóa tùy tiện bởi application user.
2. **Activity History** — timeline thân thiện với user, ví dụ “Ha updated Task A”, “Project X completed”, có filtering theo user/module/time.

Requirements ban đầu:

- khoảng 50.000 active users;
- mỗi user có thể tạo từ vài chục tới vài trăm domain changes/ngày;
- phần lớn query là “lấy 50–100 events mới nhất theo user/module/time”;
- một số compliance export có thể quét vài tháng;
- retention dự kiến vài năm nhưng chưa chốt;
- platform hiện dùng SQL Server và team vận hành SQL tốt;
- MongoDB có trong skill set/team nhưng chưa phải hạ tầng bắt buộc của product;
- Product hỏi có nên lưu toàn bộ audit/activity vào MongoDB vì “event JSON thay đổi schema dễ hơn”;
- Architect khác đề xuất tạo Audit Microservice + Kafka-style event pipeline ngay để future-proof;
- một domain operation có thể commit business state thành công nhưng việc ghi audit không được phép âm thầm mất;
- Activity History có thể eventual consistent vài giây;
- Audit Trail có yêu cầu mạnh hơn về durability, authorization và tamper resistance;
- chưa có con số thực tế cho write throughput peak, export frequency, legal retention hoặc nhu cầu cross-region.

## Câu hỏi chính

Hãy thiết kế solution cho Audit Trail và Activity History, bao gồm **data ownership, write path, consistency, schema/model, indexing, retention, security, failure recovery và deployment**. So sánh SQL Server và MongoDB dựa trên workload thực tế thay vì slogan “relational vs document”. Đồng thời quyết định có cần tách microservice/event infrastructure ngay hay một modular architecture đơn giản hơn đủ tốt trong Release đầu.

## Câu hỏi làm rõ nên cân nhắc

1. Audit Trail có phải legal/compliance evidence với immutability/WORM requirement hay chỉ là application audit history?
2. Audit record phải được commit atomically với domain change hay chấp nhận delayed durable capture?
3. Các query chính là per-entity/per-user timeline, cross-module analytics hay full-text search?
4. Retention, purge, archive và legal hold cụ thể là gì?
5. Peak write rate, payload size, multi-region requirement và recovery objectives là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Tách **Audit Trail** khỏi **Activity History** về semantics, dù chúng có thể dùng chung một nguồn event ban đầu.

### Gợi ý 2

Chọn storage từ access patterns, consistency, operational maturity và retention; schema flexibility một mình không đủ để justify MongoDB.

### Gợi ý 3

Nếu audit không được mất khi business transaction commit, hãy xem kỹ transaction boundary trước khi đề xuất asynchronous service.

## Cấu trúc trả lời đề xuất

1. Clarify audit/compliance semantics.
2. Xác định authoritative event ownership.
3. Thiết kế atomic/durable write path.
4. Tách audit source và activity projection nếu cần.
5. Model/index cho query patterns.
6. So sánh SQL và MongoDB.
7. Thiết kế retention/archive.
8. Thiết kế tamper resistance/authorization.
9. Phân tích failure/retry/idempotency.
10. Chọn modular monolith vs separate service.
11. Định nghĩa observability/SLO.
12. Xác định trigger để scale/evolve architecture.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Audit Trail và Activity History có requirements khác: audit ưu tiên durability/integrity; activity ưu tiên UX/read model và có thể eventual consistent.
- Nếu audit record phải atomically đi cùng domain transaction trong cùng SQL database, lưu audit/outbox cùng transaction là giải pháp đơn giản và mạnh.
- Gửi HTTP tới Audit Microservice sau khi commit không bảo đảm audit không mất; gọi trước commit cũng tạo failure window khác.
- MongoDB không tự làm audit “tốt hơn” chỉ vì event payload là JSON.
- SQL Server có thể phục vụ append-heavy audit workload rất tốt nếu schema/index/partition/retention phù hợp; cần đo trước khi đổi storage.
- MongoDB có lợi nếu document shape đa dạng, access patterns/document locality và scale/operational constraints phù hợp; vẫn cần indexes, schema/version discipline và durability settings.
- Activity projection có thể được build asynchronously từ durable outbox/audit event.
- Audit records cần authorization, append-only application contract và tamper-evidence/immutability strategy phù hợp compliance requirement.
- Không nên mặc định tạo microservice chỉ để “future-proof”.

### Điểm cộng

- Dùng immutable event envelope với EventId, TenantId, ActorId, EntityType, EntityId, EventType, OccurredAtUtc, SchemaVersion, CorrelationId và payload.
- Có unique EventId/idempotent consumer để projection retry an toàn.
- Index theo actual query paths, ví dụ (TenantId, EntityType, EntityId, OccurredAtUtc DESC) hoặc (TenantId, ActorId, OccurredAtUtc DESC), tránh index mọi JSON property.
- Tách hot retention khỏi cold archive nếu compliance export hiếm.
- Có redaction/classification policy: audit không nên vô tình lưu password/token/full sensitive payload.
- Nếu cần tamper evidence, cân nhắc cryptographic chaining/signing hoặc immutable external archive theo exact compliance threat model.

### Senior+

- Nhận ra application-level “no UPDATE/DELETE” không tương đương WORM/compliance immutability nếu DB administrator vẫn có quyền sửa.
- Đề xuất storage evolution trigger bằng measured write volume, index size, maintenance window, export SLA và team operational capacity.
- Có backfill/rebuild strategy cho Activity projection.
- Phân biệt event schema evolution với database schema evolution và dùng SchemaVersion/upcaster/read compatibility khi cần.
- Nếu tách service sau này, dùng durable contract/outbox làm seam thay vì thiết kế distributed architecture từ ngày đầu.

## Hướng giải quyết tham khảo

### 1. Tách semantics

Audit Trail là security/compliance-oriented record:

~~~text
Who did what
To which resource
When
From which operation/request
What changed
Was the action allowed/successful
~~~

Activity History là user-facing projection:

~~~text
Ha completed Project X
09:41
~~~

Không nên để UX requirement của activity làm giảm integrity của audit source.

### 2. Baseline architecture đơn giản

Nếu domain data hiện ở SQL Server và audit phải không mất khi business transaction commit, baseline mạnh là ghi domain state + audit event/outbox trong cùng local transaction:

~~~text
ASP.NET Core module
  ├─ Domain tables
  ├─ AuditEvents        ← durable append record
  └─ OutboxMessages     ← optional projection/integration delivery

Background projector
  └─ ActivityHistory read model
~~~

Ví dụ transaction:

~~~csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

project.Complete(actorId);

db.AuditEvents.Add(AuditEvent.Create(
    eventId: Guid.NewGuid(),
    tenantId: tenantId,
    actorId: actorId,
    entityType: "Project",
    entityId: project.Id,
    eventType: "ProjectCompleted",
    occurredAtUtc: clock.UtcNow,
    schemaVersion: 1));

db.OutboxMessages.Add(OutboxMessage.ForActivityProjection(
    project.Id,
    actorId,
    clock.UtcNow));

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
~~~

Nếu AuditEvents chính là durable source cho projector thì outbox riêng có thể không cần; worker có thể đọc audit rows theo durable checkpoint. Nếu có nhiều independent consumers/integration boundaries, outbox có thể làm delivery seam rõ hơn. Không thêm cả audit table + outbox + broker chỉ vì pattern phổ biến; chọn minimum components đáp ứng failure semantics.

### 3. SQL model

Ví dụ relational envelope:

~~~sql
CREATE TABLE AuditEvents
(
    EventId uniqueidentifier NOT NULL PRIMARY KEY,
    TenantId uniqueidentifier NOT NULL,
    ActorId uniqueidentifier NULL,
    EntityType nvarchar(100) NOT NULL,
    EntityId nvarchar(100) NOT NULL,
    EventType nvarchar(100) NOT NULL,
    OccurredAtUtc datetime2 NOT NULL,
    SchemaVersion int NOT NULL,
    CorrelationId nvarchar(100) NULL,
    PayloadJson nvarchar(max) NULL
);
~~~

Indexes phải theo query:

~~~sql
CREATE INDEX IX_Audit_Tenant_Entity_Time
ON AuditEvents(TenantId, EntityType, EntityId, OccurredAtUtc DESC);

CREATE INDEX IX_Audit_Tenant_Actor_Time
ON AuditEvents(TenantId, ActorId, OccurredAtUtc DESC);
~~~

Nếu write volume lớn, mỗi additional index làm tăng write/storage cost. Chỉ add index từ measured query need.

### 4. MongoDB option

MongoDB có thể model một event thành document tự chứa:

~~~json
{
  "_id": "event-id",
  "tenantId": "tenant-id",
  "actorId": "actor-id",
  "entity": {
    "type": "Project",
    "id": "project-id"
  },
  "type": "ProjectCompleted",
  "occurredAtUtc": "2026-09-10T02:28:00Z",
  "schemaVersion": 1,
  "payload": {
    "previousStatus": "InProgress",
    "newStatus": "Completed"
  }
}
~~~

Điều này thuận tiện cho heterogeneous payload. Nhưng MongoDB không loại bỏ các câu hỏi:

- durability/write concern;
- index selection;
- tenant isolation;
- retention;
- schema versioning;
- backup/restore;
- operational monitoring;
- cross-system transaction boundary.

Nếu domain transaction vẫn ở SQL Server, chuyển audit write sang MongoDB làm mất local atomic transaction. Khi đó cần durable outbox trong SQL rồi asynchronous delivery sang MongoDB. Nếu audit phải hiện ngay nhưng có thể delayed vài giây, điều này có thể hợp lý. Nếu requirement đòi audit committed atomically với domain mutation, SQL local write là đơn giản hơn.

### 5. Activity projection

Projector đọc durable events và upsert activity rows/documents idempotently theo EventId:

~~~text
Audit Event / Outbox
        ↓
 Projector
        ↓
ActivityHistory
  - optimized for timeline
  - display text/template key
  - actor display snapshot if needed
  - module/entity links
~~~

Nếu projector fail, audit source vẫn còn. Worker retry. Nếu projection bị corrupt, rebuild từ audit source trong retention window.

### 6. Retention

Retention cần business/compliance quyết định:

- hot online window;
- cold archive;
- legal hold;
- purge ownership;
- tenant deletion semantics;
- encryption/key retention;
- export SLA.

Không hard-code “giữ 7 năm” nếu requirement chưa có.

Nếu hàng tỷ rows trở thành vấn đề, SQL partitioning/archive hoặc move cold data sang cheaper immutable storage có thể tốt hơn đổi toàn bộ operational database ngay.

### 7. Security/integrity

Audit write API không expose generic update/delete.

Không log/store secrets như password, bearer tokens, recovery codes hoặc full payment details trong payload.

Nếu compliance yêu cầu tamper resistance trước privileged DB admin, application-only permission không đủ. Có thể cần immutable storage, append-only external sink, cryptographic chain/hash/signature hoặc platform retention controls phù hợp threat model. Cần security/compliance xác nhận exact requirement trước chọn technology.

### 8. Khi nào tách service?

Giữ trong modular monolith khi:

- cùng team sở hữu;
- throughput SQL còn tốt;
- local transaction là lợi thế;
- release cadence chung;
- operational simplicity quan trọng.

Tách audit/activity service khi có evidence:

- independent scale/storage lifecycle;
- independent security/compliance ownership;
- nhiều systems cần publish chung audit contract;
- retention/query workload gây pressure đáng kể lên primary SQL;
- team có năng lực vận hành distributed failure modes.

Service boundary không tự giải quyết durability. Nếu domain commit ở service A và audit ở service B, vẫn cần reliable event delivery.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách semantics trước. Audit Trail là durable security record; Activity History là user-facing read model có thể eventual consistent. Vì domain hiện dùng SQL Server và requirement nói business commit không được âm thầm mất audit, baseline đơn giản nhất là ghi audit event cùng local SQL transaction. Sau đó projector async tạo Activity History.

Em chưa chọn MongoDB chỉ vì payload là JSON. SQL có thể lưu envelope relational cộng payload JSON và index đúng access patterns. MongoDB đáng cân nhắc nếu document model, scale hoặc operational requirements thực sự phù hợp, nhưng nếu write sang Mongo sau SQL commit thì em phải có outbox vì mất atomicity.

Em cũng không tách microservice ngay với team đã vận hành SQL tốt nếu chưa có scale/ownership reason. Em thiết kế EventId, SchemaVersion và durable seam để sau này tách được. Audit records append-only ở application layer, payload có data-classification policy; nếu compliance yêu cầu chống cả privileged DBA sửa dữ liệu thì phải dùng stronger immutable/tamper-evident mechanism.

Em đo write rate, index/storage growth, query/export SLA và retention. Khi những số đó hoặc ownership/release cadence justify service riêng, lúc đó mới tách.”

## Câu hỏi đào sâu

1. Nếu compliance yêu cầu audit vẫn tồn tại và không thể sửa ngay cả khi production database administrator bị compromise, solution SQL append-only hiện tại còn đủ không?
2. Nếu Activity History cần full-text search trên hàng tỷ events nhưng Audit Trail chỉ cần entity/time lookup, bạn có dùng cùng một datastore cho cả hai không?
3. Một architect nói “microservice ngay từ đầu sẽ giúp scale sau này miễn phí”; bạn sẽ dùng tiêu chí và số liệu nào để phản biện hoặc đồng ý?

## Lỗi trả lời thường gặp

- Chọn MongoDB chỉ vì event là JSON.
- Chọn SQL chỉ vì team đang dùng SQL mà không phân tích access pattern/retention.
- Gửi audit bằng HTTP sau transaction rồi gọi đó là “guaranteed”.
- Đồng nhất Audit Trail với Activity History.
- Tạo microservice/message broker từ đầu mà không giải thích ownership, scale hay failure semantics.

## Thang điểm 0–10

- **0–2:** technology preference không có requirement reasoning.
- **3–4:** biết SQL/Mongo trade-offs nhưng bỏ qua transaction/durability.
- **5–6:** có local durable audit, activity projection, indexes và retention thinking.
- **7–8:** có idempotency/schema evolution/security/rebuild/operational trade-offs.
- **9–10:** phân biệt compliance threat models, local vs distributed transaction boundary, evolutionary architecture và đưa storage/service decision dựa trên measured scale + organizational constraints.
