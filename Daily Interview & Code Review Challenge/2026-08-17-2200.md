# Code Review Challenge 1 — `Parallel.ForEachAsync` dùng chung `DbContext` làm job lỗi ngẫu nhiên và ghi dữ liệu không nhất quán

**Chủ đề:** Concurrency và race conditions, EF Core resource lifetime, async/await và cancellation, background jobs, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một Hangfire job đồng bộ thông tin nhân viên từ hệ thống ngoài về database nội bộ. Mỗi lần chạy có thể nhận 20.000–50.000 employee records. Team muốn tăng tốc nên đổi từ vòng lặp tuần tự sang `Parallel.ForEachAsync`.

Sau khi deploy, production ghi nhận:

- thỉnh thoảng xuất hiện lỗi kiểu `A second operation was started on this context instance before a previous operation completed`,
- một số employee được update nhưng history tương ứng lại thiếu,
- retry job có thể xử lý lại cùng employee,
- khi tăng `MaxDegreeOfParallelism`, error rate tăng mạnh,
- memory và connection usage tăng không ổn định,
- cancellation của Hangfire đôi lúc dừng giữa chừng nhưng log chỉ ghi tổng số item bắt đầu xử lý,
- job có lúc chạy nhanh hơn đáng kể nhưng p99 của các API khác cùng database tăng rõ rệt.

Business yêu cầu có thể xử lý song song có kiểm soát, mỗi employee phải được cập nhật nhất quán cùng audit history, và job phải chịu được retry/failure giữa chừng.

## Đoạn code cần review

```csharp
public sealed class EmployeeSyncJob
{
    private readonly AppDbContext _db;
    private readonly IEmployeeDirectoryClient _directory;
    private readonly ILogger<EmployeeSyncJob> _logger;

    public EmployeeSyncJob(
        AppDbContext db,
        IEmployeeDirectoryClient directory,
        ILogger<EmployeeSyncJob> logger)
    {
        _db = db;
        _directory = directory;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        var employees = await _directory.GetEmployeesAsync(cancellationToken);

        await Parallel.ForEachAsync(
            employees,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 20,
                CancellationToken = cancellationToken
            },
            async (source, ct) =>
            {
                var employee = await _db.Employees
                    .SingleOrDefaultAsync(
                        x => x.ExternalId == source.Id,
                        ct);

                if (employee is null)
                {
                    employee = new Employee
                    {
                        ExternalId = source.Id,
                        CreatedAt = DateTime.UtcNow
                    };

                    _db.Employees.Add(employee);
                }

                employee.DisplayName = source.DisplayName;
                employee.Department = source.Department;
                employee.JobTitle = source.JobTitle;
                employee.UpdatedAt = DateTime.UtcNow;

                _db.EmployeeSyncHistories.Add(new EmployeeSyncHistory
                {
                    ExternalId = source.Id,
                    SyncedAt = DateTime.UtcNow
                });

                await _db.SaveChangesAsync(ct);
            });

        _logger.LogInformation(
            "Employee sync completed for {Count} employees",
            employees.Count);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong cách dùng `DbContext` và change tracker.
2. Xác định rủi ro concurrency, connection pressure, duplicate processing và cancellation.
3. Giải thích production impact khi chạy 20 luồng logic song song trên cùng job.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation an toàn hơn nhưng vẫn tận dụng được concurrency khi phù hợp.
6. Giải thích cách test race condition, retry, cancellation và database pressure.
7. Đề xuất logs, traces và metrics phù hợp.

## Câu hỏi gợi mở

1. Một instance `DbContext` có được thiết kế để dùng đồng thời bởi nhiều task không?
2. `SaveChangesAsync` trong mỗi iteration đang commit những entity nào đang có trong change tracker chung?
3. Nếu hai record cùng `ExternalId` xuất hiện hoặc hai job overlap, điều gì ngăn duplicate insert?
4. `MaxDegreeOfParallelism = 20` có nghĩa database thực sự chịu tối đa bao nhiêu concurrent operations?
5. Khi cancellation xảy ra sau một số employee đã commit, retry run tiếp theo sẽ xử lý thế nào?

## Kết quả code review tham khảo

### 1. Dùng chung một `DbContext` cho nhiều iteration chạy đồng thời

**Problem:** Tất cả iteration của `Parallel.ForEachAsync` cùng truy cập `_db`.  
**Why it happens:** `DbContext` có mutable state và không hỗ trợ nhiều operation song song trên cùng instance.  
**Production impact:** Có thể ném exception ngẫu nhiên, change tracker bị truy cập cạnh tranh và job fail dưới tải.  
**Severity:** Critical  
**Recommended fix:** Không chia sẻ cùng `DbContext` giữa các iteration. Tạo scope/context riêng cho mỗi item hoặc mỗi batch bằng `IDbContextFactory<AppDbContext>`/scope factory.

### 2. `SaveChangesAsync` trên shared change tracker có thể commit thay đổi từ iteration khác

**Problem:** Mỗi task nghĩ rằng nó đang save employee của riêng mình, nhưng cùng dùng một change tracker.  
**Why it happens:** Entity từ nhiều iteration đều được attach vào cùng context.  
**Production impact:** Biên transaction/unit-of-work không còn rõ ràng; failure và commit khó dự đoán, audit có thể lệch với employee update.  
**Severity:** Critical  
**Recommended fix:** Mỗi unit of work phải có context riêng hoặc batch được xử lý tuần tự trong một context riêng có boundary rõ ràng.

### 3. Không có database-level uniqueness bảo vệ `ExternalId`

**Problem:** Hai worker/job overlap có thể cùng thấy `employee is null` rồi cùng insert.  
**Why it happens:** Check-then-insert ở application layer không atomic.  
**Production impact:** Duplicate employee hoặc lỗi unique constraint muộn, tùy schema hiện tại.  
**Severity:** High  
**Recommended fix:** Có unique constraint/index trên `ExternalId` và xử lý conflict theo chiến lược retry/upsert phù hợp.

### 4. Audit history không idempotent

**Problem:** Mỗi lần retry đều thêm một `EmployeeSyncHistory` mới dù dữ liệu thực tế không thay đổi.  
**Why it happens:** Không có operation id/run id hoặc business idempotency rule cho history.  
**Production impact:** Audit phình to, khó phân biệt retry với sync thực sự, có thể tạo duplicate business event downstream.  
**Severity:** High  
**Recommended fix:** Xác định rõ semantic của history; nếu cần một record cho mỗi source version/run, dùng unique key như `(ExternalId, SourceVersion)` hoặc `(RunId, ExternalId)`.

### 5. Concurrency cố định 20 không dựa trên capacity downstream

**Problem:** `MaxDegreeOfParallelism = 20` được hard-code.  
**Why it happens:** Tối ưu theo CPU-style concurrency trong khi bottleneck chính có thể là database/network I/O.  
**Production impact:** Tăng contention, connection-pool pressure, lock wait và p99 của API khác.  
**Severity:** High  
**Recommended fix:** Benchmark và cấu hình concurrency; có thể batch write, rate-limit/admission control, hoặc tách worker pool riêng.

### 6. Một `SaveChangesAsync` cho từng employee tạo quá nhiều round-trip

**Problem:** Với 50.000 employee có thể phát sinh hàng chục nghìn transaction/round-trip riêng lẻ.  
**Why it happens:** Unit of work quá nhỏ.  
**Production impact:** Throughput kém, overhead transaction và network cao dù có parallelism.  
**Severity:** Medium  
**Recommended fix:** Cân nhắc batch hợp lý, ví dụ 100–500 item tùy payload và database; mỗi batch dùng context riêng và commit một cách có kiểm soát.

### 7. Không phân biệt item failure với toàn-job failure

**Problem:** Một exception trong iteration có thể làm toàn operation thất bại, nhưng không có trạng thái item-level rõ ràng.  
**Why it happens:** Job chỉ log completion tổng thể.  
**Production impact:** Không biết employee nào đã xử lý thành công trước failure và employee nào cần retry.  
**Severity:** Medium  
**Recommended fix:** Theo dõi run id, item outcome, failed external ids và checkpoint/attempt metadata theo nhu cầu.

### 8. Cancellation semantics chưa có recovery design

**Problem:** Cancellation có thể đến sau khi một số item đã commit.  
**Why it happens:** Job xử lý nhiều unit độc lập nhưng không có checkpoint/idempotency rõ ràng.  
**Production impact:** Run tiếp theo bắt đầu lại từ đầu và tạo audit trùng hoặc extra work.  
**Severity:** Medium  
**Recommended fix:** Thiết kế retry idempotent và checkpoint; cancellation chỉ dừng việc nhận thêm work, các unit đang commit cần có boundary rõ ràng.

### 9. Không có observability cho concurrency pressure

**Problem:** Chỉ log tổng số item sau khi hoàn tất.  
**Why it happens:** Không đo active workers, DB latency, retry, failure hoặc queue depth.  
**Production impact:** Khó chứng minh concurrency 20 có cải thiện throughput hay chỉ chuyển bottleneck sang database.  
**Severity:** Medium  
**Recommended fix:** Metric active sync operations, item throughput, DB duration, connection-pool wait nếu có telemetry, error rate, retries và run duration.

## Phiên bản code đề xuất

```csharp
public sealed class EmployeeSyncJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IEmployeeDirectoryClient _directory;
    private readonly ILogger<EmployeeSyncJob> _logger;

    public EmployeeSyncJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IEmployeeDirectoryClient directory,
        ILogger<EmployeeSyncJob> logger)
    {
        _dbFactory = dbFactory;
        _directory = directory;
        _logger = logger;
    }

    public async Task RunAsync(CancellationToken cancellationToken)
    {
        var employees = await _directory.GetEmployeesAsync(cancellationToken);
        var runId = Guid.NewGuid();

        await Parallel.ForEachAsync(
            employees,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = 6,
                CancellationToken = cancellationToken
            },
            async (source, ct) =>
            {
                await using var db = await _dbFactory.CreateDbContextAsync(ct);

                var employee = await db.Employees
                    .SingleOrDefaultAsync(x => x.ExternalId == source.Id, ct);

                if (employee is null)
                {
                    employee = new Employee
                    {
                        ExternalId = source.Id,
                        CreatedAt = DateTime.UtcNow
                    };
                    db.Employees.Add(employee);
                }

                var changed =
                    employee.DisplayName != source.DisplayName ||
                    employee.Department != source.Department ||
                    employee.JobTitle != source.JobTitle;

                employee.DisplayName = source.DisplayName;
                employee.Department = source.Department;
                employee.JobTitle = source.JobTitle;
                employee.UpdatedAt = DateTime.UtcNow;

                if (changed)
                {
                    db.EmployeeSyncHistories.Add(new EmployeeSyncHistory
                    {
                        ExternalId = source.Id,
                        RunId = runId,
                        SyncedAt = DateTime.UtcNow
                    });
                }

                await db.SaveChangesAsync(ct);
            });

        _logger.LogInformation(
            "Employee sync {RunId} completed for {Count} employees",
            runId,
            employees.Count);
    }
}
```

> Giả định database có unique constraint trên `ExternalId`. Concurrency `6` chỉ là ví dụ cấu hình; giá trị thật phải được đo theo database capacity, connection pool, latency và workload của hệ thống.

## Trade-offs

- Context riêng cho mỗi item tăng số lần tạo context nhưng loại bỏ shared-state race. Với volume rất lớn, context theo batch thường hiệu quả hơn.
- Parallelism giúp che latency I/O nhưng quá cao sẽ làm database chậm hơn. Throughput tối ưu không đồng nghĩa concurrency tối đa.
- Batch write giảm round-trip nhưng làm failure boundary lớn hơn; cần cân bằng batch size và khả năng retry.
- Upsert/database-native bulk approach có thể phù hợp hơn nếu sync chủ yếu là data ingestion khối lượng lớn, nhưng cần giữ audit/business invariant rõ ràng.

## Cách kiểm thử

1. **Concurrency test:** Chạy hàng nghìn employee với parallelism cao, xác nhận không còn lỗi concurrent `DbContext` và không duplicate `ExternalId`.
2. **Overlap test:** Khởi chạy hai job cùng lúc với cùng source data; verify unique constraint và history/idempotency đúng.
3. **Cancellation test:** Cancel giữa run; xác định item đã commit vẫn nhất quán và rerun không tạo duplicate business effect.
4. **Load test:** So sánh throughput, DB latency, connection usage và p95/p99 API ở các mức concurrency khác nhau.
5. **Failure-path test:** Inject DB timeout/deadlock cho một số item và verify retry strategy không làm toàn dataset mất khả năng phục hồi.

## Quan sát trong production

- Log structured theo `RunId`, `ExternalId`, outcome, elapsed time và retry count.
- Metric: items/sec, active item workers, failed items, retry count, job duration.
- Trace: span cho directory fetch và DB read/write theo batch/item ở mức sampling hợp lý.
- Alert khi sync error rate, DB latency hoặc job duration tăng bất thường.
- Theo dõi connection-pool pressure, lock waits và top SQL trong thời gian job chạy.

# Code Review Challenge 2 — Reset token dùng được hai lần vì validate và consume không atomic

**Chủ đề:** Authentication và authorization, sensitive-data exposure, concurrency/race conditions, input validation, transaction handling, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API triển khai luồng reset password cho portal nội bộ. Khi user yêu cầu reset, hệ thống tạo một token ngẫu nhiên, lưu xuống database và gửi link qua email.

Production/security review ghi nhận:

- cùng một reset link đôi lúc được submit gần đồng thời từ hai tab và cả hai request đều trả thành công,
- token hiện được lưu plaintext trong database,
- log có thể chứa token khi reset thất bại,
- token hết hạn sau 30 phút nhưng không có thông tin rõ ràng về lần sử dụng,
- team lo nếu database hoặc log bị lộ thì attacker có thể dùng token còn hạn,
- endpoint không giới hạn số lần thử token sai.

Business yêu cầu reset token phải one-time-use, không được lưu secret thô nếu không cần thiết, và hai request đồng thời không được cùng consume một token thành công.

## Đoạn code cần review

```csharp
public sealed record ResetPasswordRequest(
    string Email,
    string Token,
    string NewPassword);

[ApiController]
[Route("api/auth")]
public sealed class PasswordResetController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<PasswordResetController> _logger;
    private readonly IPasswordHasher<User> _hasher;

    public PasswordResetController(
        AppDbContext db,
        ILogger<PasswordResetController> logger,
        IPasswordHasher<User> hasher)
    {
        _db = db;
        _logger = logger;
        _hasher = hasher;
    }

    [AllowAnonymous]
    [HttpPost("reset-password")]
    public async Task<IActionResult> ResetPassword(
        ResetPasswordRequest request,
        CancellationToken cancellationToken)
    {
        var reset = await _db.PasswordResetRequests
            .SingleOrDefaultAsync(
                x => x.Email == request.Email &&
                     x.Token == request.Token,
                cancellationToken);

        if (reset is null || reset.ExpiresAt <= DateTime.UtcNow)
        {
            _logger.LogWarning(
                "Invalid password reset token {Token} for {Email}",
                request.Token,
                request.Email);

            return BadRequest(new { error = "invalid_token" });
        }

        var user = await _db.Users
            .SingleAsync(x => x.Email == request.Email, cancellationToken);

        user.PasswordHash = _hasher.HashPassword(user, request.NewPassword);
        reset.UsedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        return NoContent();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong one-time token flow.
2. Xác định rủi ro concurrency, secret exposure, brute-force và user enumeration side-channel nếu có.
3. Giải thích production impact của từng vấn đề.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation bảo đảm một token chỉ consume thành công một lần.
6. Giải thích cách test race condition, expired token, replay và log redaction.
7. Đề xuất logs, traces và metrics phù hợp mà không lộ secret.

## Câu hỏi gợi mở

1. Code hiện tại có kiểm tra `UsedAt` trước khi cho reset không?
2. Hai request cùng đọc token khi `UsedAt == null` có thể cùng đi tiếp không?
3. Có cần lưu token plaintext để so sánh không?
4. Token có nên xuất hiện trong structured log không?
5. Nếu attacker thử hàng nghìn token cho cùng email, endpoint hiện tại có cơ chế kiểm soát nào?

## Gợi ý

### Gợi ý 1

### Gợi ý 2

## Kết quả code review tham khảo

### 1. Không kiểm tra `UsedAt`

**Problem:** Token đã dùng vẫn có thể match query và được dùng lại nếu chưa hết hạn.  
**Why it happens:** Query chỉ kiểm tra email + token; điều kiện validity không bao gồm trạng thái consumed.  
**Production impact:** Reset link có thể replay nhiều lần trong cửa sổ 30 phút.  
**Severity:** Critical  
**Recommended fix:** Token hợp lệ phải yêu cầu `UsedAt == null` và việc consume phải atomic.

### 2. Check rồi update không atomic giữa hai request đồng thời

**Problem:** Hai request có thể cùng đọc record chưa dùng rồi cùng đổi password.  
**Why it happens:** Validity check và `UsedAt` update diễn ra qua nhiều bước, không có concurrency token/conditional update bảo vệ.  
**Production impact:** Cùng token có thể reset password hai lần; request đến sau quyết định password cuối cùng.  
**Severity:** Critical  
**Recommended fix:** Dùng conditional update/optimistic concurrency hoặc transaction phù hợp để chỉ một request chuyển state từ unused → used thành công.

### 3. Lưu reset token plaintext trong database

**Problem:** Database chứa credential tạm thời dùng trực tiếp được.  
**Why it happens:** Token được lưu nguyên giá trị để lookup.  
**Production impact:** Nếu DB snapshot/read access bị lộ, attacker có thể dùng token còn hạn.  
**Severity:** High  
**Recommended fix:** Sinh token đủ entropy, gửi raw token cho user nhưng lưu hash/digest của token; khi request tới thì hash input và lookup/compare digest.

### 4. Log raw reset token

**Problem:** Secret bị ghi vào logs.  
**Why it happens:** Error logging dùng trực tiếp `request.Token`.  
**Production impact:** Người có quyền đọc logs hoặc hệ thống log downstream có thể lấy token còn hạn.  
**Severity:** Critical  
**Recommended fix:** Không log raw token. Nếu cần correlation, log token fingerprint ngắn không đảo ngược hoặc reset request id.

### 5. Thiếu brute-force/rate control

**Problem:** Endpoint anonymous có thể bị thử token/email lặp lại.  
**Why it happens:** Không thấy rate limiting, attempt policy hoặc abuse monitoring.  
**Production impact:** Tăng nguy cơ brute-force/credential abuse và resource exhaustion.  
**Severity:** High  
**Recommended fix:** Rate-limit theo identity signals phù hợp, generic response, abuse detection và lockout/throttling ở mức hợp lý.

### 6. Password policy không được thể hiện

**Problem:** `NewPassword` được hash ngay mà không thấy validation policy.  
**Why it happens:** Endpoint bỏ qua boundary/business validation.  
**Production impact:** Có thể cho phép password không đạt policy hoặc tạo UX không nhất quán.  
**Severity:** Medium  
**Recommended fix:** Validate password theo policy tập trung trước khi consume token.

### 7. Lookup theo email + secret plaintext làm contract phụ thuộc PII

**Problem:** Client phải gửi cả email và token, và system lookup trực tiếp email.  
**Why it happens:** Reset request không có public opaque request id riêng.  
**Production impact:** Tăng surface xử lý PII và có thể tạo khác biệt response/timing theo email tồn tại hay không.  
**Severity:** Medium  
**Recommended fix:** Có thể dùng opaque reset request id + token; giữ response generic và tránh tiết lộ account existence.

### 8. Không invalidate các reset token cũ khác của cùng user

**Problem:** Sau khi reset thành công, token khác còn hạn có thể vẫn dùng được.  
**Why it happens:** Chỉ mark một record hiện tại.  
**Production impact:** Link reset cũ bị lộ vẫn còn giá trị sau khi password đã đổi.  
**Severity:** High  
**Recommended fix:** Theo policy, invalidate toàn bộ outstanding reset requests của user sau reset thành công.

### 9. Observability thiếu security signals nhưng lại log secret

**Problem:** Không có metric attempt/replay/rate-limit nhưng lại lưu dữ liệu nguy hiểm nhất.  
**Why it happens:** Logging chưa phân biệt security telemetry với raw request data.  
**Production impact:** Khó phát hiện abuse mà tăng rủi ro credential leakage.  
**Severity:** Medium  
**Recommended fix:** Log reset request id, outcome, expiry/replay flag, source metadata phù hợp; tuyệt đối không log token/password.

## Phiên bản code đề xuất

```csharp
public sealed record ResetPasswordRequest(
    Guid ResetRequestId,
    string Token,
    string NewPassword);

[ApiController]
[Route("api/auth")]
public sealed class PasswordResetController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IPasswordHasher<User> _hasher;
    private readonly ITokenHasher _tokenHasher;

    public PasswordResetController(
        AppDbContext db,
        IPasswordHasher<User> hasher,
        ITokenHasher tokenHasher)
    {
        _db = db;
        _hasher = hasher;
        _tokenHasher = tokenHasher;
    }

    [AllowAnonymous]
    [HttpPost("reset-password")]
    public async Task<IActionResult> ResetPassword(
        ResetPasswordRequest request,
        CancellationToken cancellationToken)
    {
        if (!PasswordPolicy.IsValid(request.NewPassword))
            return BadRequest(new { error = "invalid_request" });

        var tokenHash = _tokenHasher.Hash(request.Token);
        var now = DateTime.UtcNow;

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var reset = await _db.PasswordResetRequests
            .SingleOrDefaultAsync(
                x => x.Id == request.ResetRequestId &&
                     x.TokenHash == tokenHash &&
                     x.UsedAt == null &&
                     x.ExpiresAt > now,
                cancellationToken);

        if (reset is null)
            return BadRequest(new { error = "invalid_token" });

        var affected = await _db.PasswordResetRequests
            .Where(x => x.Id == reset.Id && x.UsedAt == null)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(x => x.UsedAt, now),
                cancellationToken);

        if (affected != 1)
            return BadRequest(new { error = "invalid_token" });

        var user = await _db.Users
            .SingleAsync(x => x.Id == reset.UserId, cancellationToken);

        user.PasswordHash = _hasher.HashPassword(user, request.NewPassword);

        await _db.PasswordResetRequests
            .Where(x => x.UserId == user.Id && x.UsedAt == null)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(x => x.UsedAt, now),
                cancellationToken);

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        return NoContent();
    }
}
```

> Đây là hướng tham khảo. Điều quan trọng là conditional state transition phải được database enforce để chỉ một consumer thành công. Nếu dự án không dùng API bulk update tương ứng, có thể dùng concurrency token hoặc câu SQL parameterized conditional update với cùng nguyên tắc.

## Trade-offs

- Lưu token hash tăng an toàn khi DB bị đọc trái phép, nhưng raw token mất thì không thể khôi phục; đây thường là behavior mong muốn.
- Conditional update + transaction làm implementation phức tạp hơn một query đơn giản nhưng cần thiết để enforce one-time-use dưới concurrency.
- Invalidate toàn bộ reset token sau password change tăng security nhưng có thể làm hỏng một link hợp lệ khác user vừa request; thường đây là trade-off chấp nhận được cho credential reset.
- Rate limiting cần tránh chặn nhầm user hợp lệ; nên kết hợp nhiều tín hiệu thay vì chỉ IP nếu môi trường có NAT/proxy lớn.

## Cách kiểm thử

1. **Concurrency test:** Gửi 20 request đồng thời với cùng token; đúng một request được phép consume thành công.
2. **Replay test:** Dùng lại token sau reset; luôn bị từ chối.
3. **Expiry test:** Token ở đúng boundary expiry và token quá hạn phải fail theo UTC semantics thống nhất.
4. **Security test:** Xác nhận DB/log không chứa raw token hoặc password; verify token hash không thể dùng trực tiếp như credential.
5. **Abuse test:** Gửi nhiều token sai liên tục và verify throttling/alert hoạt động mà response không tiết lộ account existence.

## Quan sát trong production

- Metric: reset attempts, success, invalid/expired/replayed token, throttled requests.
- Log structured: `ResetRequestId`, outcome, user/account surrogate id nếu policy cho phép; không log token/password.
- Alert khi replay rate hoặc invalid-attempt rate tăng bất thường.
- Trace chỉ cần operation-level timing; tránh đưa token/email raw vào span attributes.
- Theo dõi số outstanding reset requests và tuổi của chúng để phát hiện cleanup/policy lỗi.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao hash password và hash reset token có thể cần chiến lược khác nhau?
2. Nếu password reset còn cần revoke refresh token/session hiện tại, bạn sẽ đặt bước đó ở đâu để giữ consistency hợp lý?
3. Nếu hệ thống chạy nhiều region, bạn đảm bảo one-time token consumption thế nào khi database replication không phải strong-consistent ở mọi nơi?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `DbContext` là một unit of work có mutable state; không nên chia sẻ một instance cho nhiều operation đồng thời.
- Parallelism với workload I/O phải được giới hạn theo capacity downstream, không tối ưu bằng cách tăng concurrency vô hạn.
- Check-then-act trong application layer không đủ để bảo vệ invariant khi có nhiều request/job chạy đồng thời; database constraint hoặc conditional state transition là lớp bảo vệ cuối cùng.
- Credential tạm thời như reset token phải có expiry, one-time-use, secrecy, replay protection và abuse monitoring.
- Retry/cancellation chỉ an toàn khi business operation có idempotency và recovery semantics rõ ràng.

## Mẫu tư duy cần nhớ

- Không chia sẻ mutable unit of work giữa các task song song.
- Enforce invariant quan trọng ở database boundary, không chỉ bằng `if` trong code.
- Tăng concurrency phải đi kèm đo database/downstream pressure.
- Secret không nên xuất hiện trong logs hoặc storage plaintext nếu có thể dùng hash.
- Thiết kế retry cùng idempotency và state transition atomic.
