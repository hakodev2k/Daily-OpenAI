# Code Review Challenge 1 — Job phát hành vé có thể phát hành hai lần

**Chủ đề:** Background jobs, concurrency, EF Core, idempotency, transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một hệ thống event booking chạy ASP.NET Core, EF Core và Hangfire. Khi payment provider xác nhận thanh toán, ứng dụng enqueue `IssueTicketJob`. Job kiểm tra booking, tạo ticket, lưu trạng thái và gửi push notification.

Thông thường lưu lượng thấp, nhưng khi một sự kiện mở bán có thể có hàng trăm job chạy đồng thời. Hangfire có thể retry job khi execution thất bại. Production thỉnh thoảng xuất hiện hai ticket cho cùng một booking; đôi khi người dùng nhận hai notification. Một số trường hợp database đã có ticket nhưng booking vẫn ở trạng thái `Paid` sau khi job lỗi.

Giả định business rule là mỗi booking chỉ được có tối đa một ticket. Chưa biết database hiện có unique constraint tương ứng hay không.

## Đoạn code cần review

```csharp
public sealed class IssueTicketJob
{
    private readonly BookingDbContext _db;
    private readonly IPushNotificationService _push;
    private readonly ILogger<IssueTicketJob> _logger;

    public IssueTicketJob(
        BookingDbContext db,
        IPushNotificationService push,
        ILogger<IssueTicketJob> logger)
    {
        _db = db;
        _push = push;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid bookingId)
    {
        var booking = await _db.Bookings
            .FirstOrDefaultAsync(x => x.Id == bookingId);

        if (booking == null)
            return;

        if (booking.Status != BookingStatus.Paid)
            return;

        var alreadyIssued = await _db.Tickets
            .AnyAsync(x => x.BookingId == bookingId);

        if (alreadyIssued)
            return;

        var ticket = new Ticket
        {
            Id = Guid.NewGuid(),
            BookingId = booking.Id,
            UserId = booking.UserId,
            IssuedAtUtc = DateTime.UtcNow
        };

        _db.Tickets.Add(ticket);
        await _db.SaveChangesAsync();

        await _push.SendAsync(
            booking.UserId,
            $"Ticket {ticket.Id} has been issued");

        booking.Status = BookingStatus.Issued;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Ticket {TicketId} issued for booking {BookingId}",
            ticket.Id,
            booking.Id);
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-insert không bảo vệ khỏi race condition

**Problem:** `AnyAsync()` và insert ticket là hai thao tác riêng biệt.  
**Why:** Hai worker có thể cùng đọc `false` trước khi worker nào commit insert.  
**Production impact:** Hai ticket cho cùng booking.  
**Severity:** Critical  
**Recommended fix:** Enforce invariant bằng unique constraint/index trên `Ticket.BookingId`; code phải xử lý conflict như một kết quả idempotent. Có thể bổ sung optimistic concurrency/atomic state transition tùy workflow, nhưng application check không thay thế database constraint.

### 2. Ticket và booking status được commit ở hai lần SaveChanges

**Problem:** Ticket được commit trước khi booking chuyển sang `Issued`.  
**Why:** Failure giữa hai lần save tạo partial state.  
**Production impact:** Ticket tồn tại trong khi booking vẫn `Paid`; downstream logic có thể hiểu sai trạng thái.  
**Severity:** High  
**Recommended fix:** Thay đổi ticket và booking trong cùng một database transaction/`SaveChangesAsync` khi chúng thuộc cùng database và cùng consistency boundary.

### 3. External notification nằm giữa hai database state changes

**Problem:** Push notification là side effect không transactional với database.  
**Why:** Nếu push thành công rồi job crash trước update cuối, retry có thể gửi lại. Nếu push lỗi, database đã có ticket.  
**Production impact:** Duplicate notification hoặc state khó phục hồi.  
**Severity:** High  
**Recommended fix:** Commit business state cùng một outbox record trong database transaction; worker riêng publish notification và đánh dấu outbox processed. Consumer/publisher vẫn nên idempotent vì delivery có thể lặp.

### 4. Không có chiến lược idempotency rõ ràng cho retry

**Problem:** Code dựa vào query `AnyAsync` như cơ chế chống retry.  
**Why:** Retry và concurrent execution có thể xen kẽ; failure có thể xảy ra tại nhiều điểm.  
**Production impact:** Duplicate side effects và kết quả phụ thuộc timing.  
**Severity:** High  
**Recommended fix:** Xác định idempotency key ổn định, ví dụ `bookingId`, enforce uniqueness ở DB và thiết kế mỗi bước có thể chạy lại an toàn.

### 5. Không truyền cancellation token cho database/external I/O

**Problem:** Async calls không nhận cancellation token.  
**Why:** Khi host/job bị shutdown hoặc operation bị hủy, I/O có thể tiếp tục lâu hơn cần thiết nếu framework/job integration cung cấp cancellation.  
**Production impact:** Shutdown chậm, tài nguyên giữ lâu, khó kiểm soát failure path.  
**Severity:** Medium  
**Recommended fix:** Nhận cancellation token phù hợp với execution model và truyền xuyên suốt tới EF/external call khi API hỗ trợ.

### 6. Booking không tồn tại hoặc trạng thái không phù hợp bị bỏ qua mà thiếu telemetry

**Problem:** Early return hoàn toàn im lặng.  
**Why:** Không phân biệt duplicate hợp lệ, dữ liệu bất thường và job enqueue sai.  
**Production impact:** Điều tra incident khó; mất tín hiệu về workflow lỗi.  
**Severity:** Medium  
**Recommended fix:** Structured log/metric theo outcome, tránh log noise và không đưa dữ liệu nhạy cảm không cần thiết.

### 7. Dùng thời gian trực tiếp làm giảm testability

**Problem:** `DateTime.UtcNow` nằm trực tiếp trong business code.  
**Why:** Test phụ thuộc clock thực.  
**Production impact:** Không phải lỗi correctness chính nhưng làm test boundary/time behavior khó hơn.  
**Severity:** Low  
**Recommended fix:** Dùng `TimeProvider` hoặc abstraction clock nếu logic thời gian cần kiểm thử deterministically.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng database làm source of truth, unique index để giữ invariant và transactional outbox để tách external side effect. Chi tiết mapping/entity được rút gọn.

```csharp
public sealed class IssueTicketJob
{
    private readonly BookingDbContext _db;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<IssueTicketJob> _logger;

    public IssueTicketJob(
        BookingDbContext db,
        TimeProvider timeProvider,
        ILogger<IssueTicketJob> logger)
    {
        _db = db;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    public async Task ExecuteAsync(
        Guid bookingId,
        CancellationToken cancellationToken = default)
    {
        var booking = await _db.Bookings
            .SingleOrDefaultAsync(x => x.Id == bookingId, cancellationToken);

        if (booking is null)
        {
            _logger.LogWarning("Booking {BookingId} was not found", bookingId);
            return;
        }

        if (booking.Status == BookingStatus.Issued)
        {
            _logger.LogInformation(
                "Booking {BookingId} was already issued",
                bookingId);
            return;
        }

        if (booking.Status != BookingStatus.Paid)
        {
            _logger.LogWarning(
                "Booking {BookingId} cannot be issued from status {Status}",
                bookingId,
                booking.Status);
            return;
        }

        var now = _timeProvider.GetUtcNow();
        var ticketId = Guid.NewGuid();

        _db.Tickets.Add(new Ticket
        {
            Id = ticketId,
            BookingId = booking.Id,
            UserId = booking.UserId,
            IssuedAtUtc = now.UtcDateTime
        });

        booking.Status = BookingStatus.Issued;

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "TicketIssued",
            AggregateId = booking.Id,
            Payload = JsonSerializer.Serialize(new
            {
                BookingId = booking.Id,
                TicketId = ticketId,
                booking.UserId
            }),
            CreatedAtUtc = now.UtcDateTime
        });

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateException ex) when (IsTicketBookingUniqueViolation(ex))
        {
            _logger.LogInformation(
                "Booking {BookingId} was concurrently issued",
                bookingId);
            return;
        }

        _logger.LogInformation(
            "Ticket {TicketId} committed for booking {BookingId}",
            ticketId,
            bookingId);
    }

    private static bool IsTicketBookingUniqueViolation(DbUpdateException ex)
    {
        return DatabaseErrorClassifier.IsUniqueViolation(
            ex,
            "UX_Tickets_BookingId");
    }
}
```

EF Core model cần một invariant ở database, ví dụ:

```csharp
modelBuilder.Entity<Ticket>()
    .HasIndex(x => x.BookingId)
    .IsUnique()
    .HasDatabaseName("UX_Tickets_BookingId");
```

Outbox dispatcher sau đó gửi notification và đánh dấu message processed. Cách detect unique violation phải dùng provider-specific error information đáng tin cậy thay vì parse message text tùy tiện.

## Trade-offs

Unique constraint là lớp bảo vệ cuối cùng đơn giản và mạnh cho invariant “một ticket/booking”, nhưng application vẫn cần xử lý conflict đúng nghĩa. Outbox thêm table, dispatcher, cleanup và operational complexity, đổi lại loại bỏ khoảng trống consistency giữa database commit và external notification. Nếu notification chỉ mang tính best-effort và duplicate hoàn toàn chấp nhận được, kiến trúc có thể đơn giản hơn; nhưng nếu user-facing side effect cần retry đáng tin cậy, outbox thường hợp lý hơn distributed transaction.

Pessimistic locking hoặc isolation mạnh hơn có thể phù hợp với một số contention pattern, nhưng không nên dùng mặc định khi unique constraint đã diễn đạt chính xác invariant.

## Cách kiểm thử

1. **Concurrency integration test:** khởi chạy nhiều execution đồng thời cùng `bookingId`; cuối cùng database chỉ có một ticket và một trạng thái `Issued`.
2. **Database invariant test:** cố insert hai ticket cho cùng booking và xác nhận unique constraint từ chối bản ghi thứ hai.
3. **Failure-path test:** mô phỏng failure sau business transaction; outbox vẫn tồn tại và dispatcher có thể gửi lại sau recovery.
4. **Duplicate delivery test:** dispatcher xử lý cùng outbox/message nhiều lần; notification layer hoặc downstream dedupe theo message/idempotency key nếu business yêu cầu.
5. **Load test:** chạy nhiều booking và một nhóm hot booking đồng thời để quan sát lock waits, conflict rate, latency và throughput.

## Quan sát trong production

Theo dõi structured logs với `BookingId`, `TicketId`, job/trace correlation; metric `ticket_issue_success`, `ticket_issue_duplicate`, `ticket_issue_conflict`, `ticket_issue_failure`; outbox backlog age/count và retry count; Hangfire retries/failures; database unique-violation rate, deadlocks/lock waits và query latency. Trace nên nối job execution → database commit → outbox dispatch → notification provider.

## Câu hỏi phỏng vấn mở rộng

1. Nếu `Ticket` và `Booking` nằm ở hai database khác nhau, bạn thay đổi consistency strategy thế nào?
2. Unique constraint đã đủ rồi thì tại sao còn cần idempotency ở notification consumer?
3. Nếu contention trên một booking rất cao, bạn cân nhắc optimistic concurrency, pessimistic locking hay queue partitioning theo tiêu chí nào?

# Code Review Challenge 2 — Endpoint admin nhưng tenant isolation chỉ nằm trong request

**Chủ đề:** Authentication/authorization, multi-tenant isolation, input validation, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một SaaS nội bộ có nhiều tenant. Endpoint dưới đây cho phép tenant administrator tìm user và reset API key của integration account. JWT authentication đã được cấu hình ở ASP.NET Core. Mỗi user có claim `tenant_id`; role `Admin` chỉ có ý nghĩa bên trong tenant của user.

Sau một security review, team phát hiện một admin có thể thay đổi request body để tác động tới account thuộc tenant khác. Log production cũng đang chứa API key mới ở một số request. API key phải chỉ hiển thị đúng một lần cho caller được phép.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/admin/integrations")]
public sealed class IntegrationAdminController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<IntegrationAdminController> _logger;

    public IntegrationAdminController(
        AppDbContext db,
        ILogger<IntegrationAdminController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpPost("reset-key")]
    [Authorize]
    public async Task<IActionResult> ResetKey(ResetKeyRequest request)
    {
        if (!User.Identity!.IsAuthenticated)
            return Unauthorized();

        var isAdmin = User.Claims
            .Any(x => x.Type == ClaimTypes.Role && x.Value == "Admin");

        if (!isAdmin)
            return Forbid();

        var account = await _db.IntegrationAccounts
            .FirstOrDefaultAsync(x =>
                x.Id == request.AccountId &&
                x.TenantId == request.TenantId);

        if (account == null)
            return NotFound();

        var apiKey = Convert.ToBase64String(Guid.NewGuid().ToByteArray());

        account.ApiKey = apiKey;
        account.UpdatedAtUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Admin {User} reset key {ApiKey} for account {AccountId} in tenant {TenantId}",
            User.Identity.Name,
            apiKey,
            account.Id,
            request.TenantId);

        return Ok(new
        {
            account.Id,
            request.TenantId,
            ApiKey = apiKey
        });
    }
}

public sealed record ResetKeyRequest(Guid AccountId, Guid TenantId);
```

## Gợi ý

### Gợi ý 1

Authentication trả lời “caller là ai”; bài toán này còn cần trả lời “caller được làm gì với resource cụ thể nào”.

### Gợi ý 2

Đừng để client tự chọn authorization boundary. Tenant scope phải xuất phát từ identity/policy đáng tin cậy và được áp dụng vào resource query/update.

## Kết quả code review tham khảo

### 1. Tenant ID do client kiểm soát được dùng làm authorization scope

**Problem:** Query dùng `request.TenantId`, không ràng buộc nó với authenticated tenant claim.  
**Why:** Caller có thể sửa body sang tenant khác.  
**Production impact:** Cross-tenant access/reset secret — vi phạm isolation nghiêm trọng.  
**Severity:** Critical  
**Recommended fix:** Lấy tenant scope từ trusted identity/context; query resource bằng authenticated tenant ID. Nếu có platform admin cross-tenant, đó phải là policy/permission riêng và được audit rõ ràng.

### 2. Authorization chỉ kiểm tra role bằng code ad-hoc

**Problem:** `[Authorize]` chỉ yêu cầu authenticated user; code sau đó tự scan role claim và không mô hình hóa tenant/resource authorization.  
**Why:** Authorization logic dễ phân tán và sai khác giữa endpoint.  
**Production impact:** Privilege boundary khó kiểm chứng, dễ tái diễn IDOR/BOLA.  
**Severity:** High  
**Recommended fix:** Dùng authorization policy/requirement phù hợp, và resource/tenant scope phải được enforce trong query/service boundary.

### 3. API key được ghi plaintext vào log

**Problem:** Secret xuất hiện trực tiếp trong structured log.  
**Why:** Log thường được replicate, lưu lâu và nhiều operator có quyền đọc.  
**Production impact:** Credential leakage có thể dẫn tới account compromise.  
**Severity:** High  
**Recommended fix:** Không log secret. Audit event chỉ chứa actor ID, tenant, account, timestamp, result/correlation ID.

### 4. API key được lưu plaintext trong database

**Problem:** Nếu API key chỉ cần được kiểm tra khi client sử dụng, plaintext storage làm tăng blast radius khi database bị đọc.  
**Why:** Server không nhất thiết cần phục hồi raw key sau lần hiển thị đầu tiên.  
**Production impact:** Database compromise làm lộ toàn bộ active credentials.  
**Severity:** High  
**Recommended fix:** Sinh secret bằng CSPRNG, trả raw secret một lần, lưu verifier/hash phù hợp cùng key ID/prefix. Nếu business thực sự cần retrieve secret, dùng secret store/encryption strategy thích hợp thay vì hash; yêu cầu này sẽ thay đổi thiết kế.

### 5. Cách sinh key không biểu đạt rõ yêu cầu cryptographic secret

**Problem:** `Guid.NewGuid()` được biến thành Base64 và dùng trực tiếp như API key.  
**Why:** API key nên được tạo bằng API CSPRNG với entropy/length được lựa chọn rõ ràng cho credential.  
**Production impact:** Thiết kế credential khó review và evolve.  
**Severity:** Medium  
**Recommended fix:** Dùng `RandomNumberGenerator.GetBytes(...)`, encode bằng Base64Url/hex phù hợp; không hard-code claim rằng một độ dài cụ thể là bắt buộc nếu threat model chưa xác định.

### 6. Không có concurrency/version strategy cho key rotation

**Problem:** Hai admin có thể reset gần đồng thời; response đầu tiên có thể chứa key đã lập tức bị request thứ hai vô hiệu hóa.  
**Why:** Last-write-wins mặc định.  
**Production impact:** Integration fail khó hiểu và audit khó xác định key version nào active.  
**Severity:** Medium  
**Recommended fix:** Cân nhắc concurrency token/key version, rotation semantics hoặc explicit confirmation tùy business requirement.

### 7. Không truyền cancellation token

**Problem:** Database operations không nhận request cancellation.  
**Why:** Request abort không được propagate tới EF operation.  
**Production impact:** Waste tài nguyên khi request đã bị hủy, nhất là dưới tải.  
**Severity:** Low  
**Recommended fix:** Nhận `CancellationToken` action parameter và truyền cho EF calls.

### 8. Audit identity dựa vào `User.Identity.Name` có thể không phải stable actor ID

**Problem:** Display/name claim có thể thiếu hoặc thay đổi.  
**Why:** Audit cần identifier ổn định từ trusted identity.  
**Production impact:** Khó điều tra ai thực hiện rotation.  
**Severity:** Low  
**Recommended fix:** Audit stable subject/object identifier phù hợp với identity provider, đồng thời có correlation ID.

## Phiên bản code đề xuất

Ví dụ giả định tenant admin không được phép cross-tenant và API key chỉ cần verify, không cần retrieve lại sau lần reset.

```csharp
[ApiController]
[Route("api/admin/integrations")]
[Authorize(Policy = "TenantIntegrationAdmin")]
public sealed class IntegrationAdminController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;
    private readonly ILogger<IntegrationAdminController> _logger;

    public IntegrationAdminController(
        AppDbContext db,
        TimeProvider timeProvider,
        ILogger<IntegrationAdminController> logger)
    {
        _db = db;
        _timeProvider = timeProvider;
        _logger = logger;
    }

    [HttpPost("{accountId:guid}/reset-key")]
    public async Task<IActionResult> ResetKey(
        Guid accountId,
        CancellationToken cancellationToken)
    {
        var tenantValue = User.FindFirstValue("tenant_id");
        var actorId = User.FindFirstValue(ClaimTypes.NameIdentifier)
            ?? User.FindFirstValue("sub");

        if (!Guid.TryParse(tenantValue, out var tenantId) ||
            string.IsNullOrWhiteSpace(actorId))
        {
            return Forbid();
        }

        var account = await _db.IntegrationAccounts
            .SingleOrDefaultAsync(
                x => x.Id == accountId && x.TenantId == tenantId,
                cancellationToken);

        if (account is null)
            return NotFound();

        var secretBytes = RandomNumberGenerator.GetBytes(32);
        var rawKey = WebEncoders.Base64UrlEncode(secretBytes);
        var keyHash = SHA256.HashData(Encoding.UTF8.GetBytes(rawKey));

        account.ApiKeyHash = Convert.ToHexString(keyHash);
        account.KeyVersion += 1;
        account.UpdatedAtUtc = _timeProvider.GetUtcNow().UtcDateTime;

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Actor {ActorId} rotated integration key for account {AccountId} " +
            "in tenant {TenantId}; version {KeyVersion}",
            actorId,
            account.Id,
            tenantId,
            account.KeyVersion);

        return Ok(new
        {
            account.Id,
            KeyVersion = account.KeyVersion,
            ApiKey = rawKey
        });
    }
}
```

Trong production, verifier nên được thiết kế phù hợp với API-key authentication scheme. Hashing ở ví dụ nhằm minh họa “không cần lưu raw credential”; format, key identifier, rotation/grace period và comparison strategy phải được thiết kế cùng authentication path. Policy `TenantIntegrationAdmin` cũng phải được cấu hình để xác nhận đúng permission/role semantics của hệ thống; policy không tự động thay thế resource query có tenant scope.

## Trade-offs

Lấy tenant từ authenticated context làm API đơn giản và an toàn hơn cho tenant admin, nhưng platform/support admin có nhu cầu cross-tenant sẽ cần một flow riêng với explicit permission và audit mạnh hơn. Hash-only storage giảm impact khi database lộ nhưng không cho phép xem lại raw key; nếu requirement cần retrieval, cần encryption/key-management thay vì hashing. Immediate rotation đơn giản nhưng có thể gây downtime cho integration; dual-key/grace-period rotation tăng availability nhưng làm state machine và revoke logic phức tạp hơn.

Trả `404` cho resource ngoài tenant có thể giảm resource enumeration so với phân biệt `403`, nhưng lựa chọn status code phải nhất quán với API security contract.

## Cách kiểm thử

1. **Cross-tenant security test:** admin tenant A gọi endpoint với account tenant B; không được thay đổi dữ liệu dù biết chính xác account ID.
2. **Authorization test:** authenticated non-admin và token thiếu tenant claim đều bị từ chối.
3. **Secret leakage test:** capture logs/traces/error response và xác nhận raw API key không xuất hiện ngoài successful one-time response.
4. **Rotation integration test:** key cũ bị xử lý theo đúng rotation policy; key mới verify thành công; stored value không chứa raw key nếu dùng verifier/hash design.
5. **Concurrency test:** hai reset đồng thời cho cùng account; xác minh behavior/key version đúng với business rule đã chọn.

## Quan sát trong production

Audit log nên có stable actor ID, tenant ID, account ID, key version, timestamp, outcome và correlation/trace ID nhưng tuyệt đối không chứa raw key. Theo dõi số lần rotation theo tenant/account, authorization-denied rate, cross-tenant lookup attempts nếu có thể phân biệt an toàn, authentication failure tăng đột biến sau rotation, request latency/error rate và security alerts cho rotation bất thường. Cần rà soát telemetry pipeline để bảo đảm request/response body capture không vô tình thu secret.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support engineer cần reset key cho bất kỳ tenant nào, bạn thiết kế authorization và audit flow ra sao mà không mở lại lỗ hổng cross-tenant?
2. Khi nào hash-only API key storage không phù hợp và bạn sẽ dùng encryption/secret vault thay thế?
3. Nếu muốn zero-downtime key rotation, data model và authentication flow cần thay đổi thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge cùng kiểm tra một nguyên tắc kiến trúc quan trọng: invariant và trust boundary phải được enforce ở nơi đáng tin cậy nhất, không chỉ bằng một `if` trong application code. Với concurrency, database constraint/transaction bảo vệ business state còn idempotency/outbox xử lý retry và external side effect. Với security, authenticated identity phải quyết định tenant scope; input của client không được trở thành authorization boundary. Secret phải được sinh, lưu, trả về và audit theo threat model rõ ràng.

## Mẫu tư duy cần nhớ

1. Với mọi workflow có retry, hỏi: “Nếu chạy lại từ đầu sau từng điểm crash thì chuyện gì xảy ra?”
2. Enforce business invariant ở database khi database là source of truth; application pre-check chỉ hỗ trợ UX/flow, không phải concurrency guarantee.
3. Thiết kế retry cùng idempotency; external side effect cần strategy riêng như outbox/deduplication.
4. Authentication không thay thế authorization; authorization phải gắn với resource và tenant boundary.
5. Secret không thuộc về logs; observability phải hữu ích mà không mở rộng blast radius.
