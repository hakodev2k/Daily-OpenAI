# Câu 1 — `IQueryable` chạy lúc nào và vì sao cùng một LINQ query có thể tạo SQL rất khác?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, `IQueryable`, expression tree, deferred execution, query translation, SQL, materialization, performance verification

## Bối cảnh

Một ASP.NET Core API dùng EF Core để lấy danh sách orders. Repository trả về `IQueryable<Order>`, sau đó application layer tiếp tục thêm `Where`, `OrderBy`, `Select` và cuối cùng gọi `ToListAsync()`.

Trong một refactor, developer chèn `AsEnumerable()` trước một số filter vì một helper method không translate được sang SQL. API vẫn trả đúng dữ liệu ở môi trường test nhỏ, nhưng production bắt đầu tăng memory, SQL rows transferred và request latency. Một thành viên khác cho rằng `Where` luôn chạy ngay tại dòng code được viết, còn `IQueryable` chỉ là `IEnumerable` có thêm async.

Chưa biết dataset production lớn đến đâu, execution plan hiện tại thế nào, hay projection có đang lấy nhiều cột không cần thiết hay không.

## Câu hỏi chính

Hãy giải thích internal mechanism từ lúc xây dựng LINQ trên `IQueryable` đến lúc EF Core thực thi SQL và materialize kết quả. Vì sao `AsEnumerable()` có thể thay đổi nơi filter được thực hiện, assumption nào của team là sai, và bạn sẽ chứng minh query thực tế đang làm gì trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

1. `IQueryable` được materialize ở đâu và có operation nào gọi `ToList`, `First`, `Count` hoặc enumerate sớm không?
2. Helper method nào không translate được và business logic đó có thể biểu diễn thành expression/query khác không?
3. Production cardinality trước và sau filter là bao nhiêu?
4. Query cần những columns/navigation nào thực sự?
5. SQL generated và execution plan hiện tại cho thấy bottleneck ở database hay application?

## Gợi ý tư duy

### Gợi ý 1

Phân biệt việc xây expression/query representation với việc enumerate kết quả.

### Gợi ý 2

Hỏi provider nào đang xử lý các operators trước và sau `AsEnumerable()`.

### Gợi ý 3

Tối ưu phải dựa trên generated SQL, rows read/returned, execution plan và application allocations chứ không chỉ nhìn LINQ syntax.

## Cấu trúc trả lời đề xuất

1. Xác định query boundary và materialization point.
2. Giải thích `IQueryable`, expression tree và provider.
3. Giải thích deferred execution.
4. Phân tích tác động của `AsEnumerable()`.
5. Xem generated SQL và parameters.
6. Đo rows, plan, duration, allocations.
7. Đề xuất server-side filtering/projection nếu phù hợp.
8. Kiểm thử correctness và performance regression.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Các LINQ operators trên EF Core `IQueryable` thường xây query representation; database query chưa nhất thiết chạy tại từng `Where`.
- Execution xảy ra khi query được enumerated/materialized bởi operation tương ứng như `ToListAsync`.
- EF Core query provider dịch phần expression được hỗ trợ sang SQL.
- Sau `AsEnumerable()`, các LINQ-to-Objects operators tiếp theo chạy phía application khi sequence được enumerate; vì vậy filter phía sau có thể không còn được push xuống SQL.
- Việc kéo nhiều rows/columns về application có thể tăng network transfer, allocations, GC và latency.
- Cần kiểm tra generated SQL, query plan và telemetry thay vì đoán từ code.

### Điểm cộng

- Dùng projection để chỉ lấy dữ liệu cần thiết thay vì materialize full entity graph khi không cần tracking/update.
- Phân biệt `AsNoTracking()` với việc query chạy client-side; `AsNoTracking` không biến `IQueryable` thành `IEnumerable`.
- Nhận ra việc expose `IQueryable` xuyên layer có trade-off về abstraction/leak query semantics; không mặc định luôn sai hoặc luôn đúng.
- Xem xét pagination và deterministic ordering nếu endpoint trả danh sách lớn.

### Senior+

- Giải thích expression composition, provider translation boundary và materialization như một execution boundary.
- Nhận ra query shape, parameterization, cardinality và indexes đều ảnh hưởng plan; “LINQ trông gọn” không đồng nghĩa SQL tối ưu.
- Thiết kế API/repository boundary để caller có đủ flexibility nhưng vẫn kiểm soát query behavior và testing.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng xác định materialization point. Khi code tiếp tục compose trên `IQueryable`, các operators tạo expression/query shape mà provider có thể dịch. Query thực sự được gửi khi sequence được enumerated, ví dụ `ToListAsync`. Vì vậy assumption “mỗi `Where` chạy ngay” là sai.

`AsEnumerable()` là boundary quan trọng: nó cho phép các operators tiếp theo dùng LINQ-to-Objects semantics. Nếu trước đó SQL mới chỉ giới hạn một phần dữ liệu, filter phía sau có thể chạy trong process sau khi database đã trả nhiều rows. Điều này đặc biệt nguy hiểm khi test data nhỏ che mất network/memory cost.

Tôi sẽ lấy generated SQL bằng tooling/logging phù hợp, xem parameters, số rows database đọc/trả, execution plan, dependency duration trong Application Insights và allocation/GC ở application. Nếu helper không translate, ưu tiên viết lại phần có thể filter server-side hoặc chia logic thành hai giai đoạn nhưng đặt một server-side narrowing boundary đủ mạnh trước khi chuyển sang client evaluation. Projection chỉ lấy columns cần thiết và pagination nếu requirement cho phép.

Nếu query cần business calculation không thể dịch và dataset sau server-side filter rất nhỏ, client-side phase có thể là trade-off hợp lý; nhưng cần explicit và có test/telemetry bảo vệ cardinality assumption.

## Mẫu trả lời trong phỏng vấn

“`IQueryable` không phải chỉ là `IEnumerable` có async. Với EF Core, các LINQ operators thường compose expression cho query provider; SQL được thực thi khi query được enumerate như `ToListAsync`. Nếu tôi gọi `AsEnumerable()`, các operators sau đó chuyển sang LINQ-to-Objects, nên một `Where` phía sau có thể chạy trong application thay vì database. Với production data lớn, điều đó có thể kéo nhiều rows qua network rồi mới lọc, làm tăng allocation và latency. Tôi sẽ không sửa bằng cảm giác: tôi xem generated SQL, execution plan, rows read/returned, dependency duration và allocations. Nếu helper không translate, tôi cố đẩy phần filter/select có thể dịch xuống database trước, rồi chỉ xử lý client-side trên tập nhỏ có cardinality được kiểm soát.”

## Câu hỏi đào sâu

1. Nếu repository trả `IQueryable` ra application layer, lợi ích và coupling/risk của thiết kế này là gì?
2. Nếu generated SQL đã filter đúng nhưng query vẫn chậm, bạn điều tra tiếp theo hướng nào?
3. Nếu business rule bắt buộc dùng một C# library không thể translate, bạn sẽ thiết kế boundary thế nào để không kéo hàng triệu rows về memory?

## Lỗi trả lời thường gặp

- Cho rằng `Where` luôn thực thi ngay khi được gọi.
- Đồng nhất `AsNoTracking()` với server-side/client-side execution.
- Chỉ đề xuất “thêm index” mà không xem generated SQL và execution plan.
- Dùng `AsEnumerable()` để làm query compile rồi bỏ qua cardinality.
- Không đo network rows, allocations hoặc dependency latency.

## Thang điểm 0–10

- **0–2:** Không phân biệt `IQueryable`/enumeration hoặc hiểu sai execution boundary.
- **3–4:** Biết deferred execution nhưng chưa giải thích provider/translation và production impact.
- **5–6:** Giải thích đúng `AsEnumerable`, SQL translation và cách kiểm tra generated query.
- **7–8:** Có reasoning về cardinality, projection, plan, telemetry và abstraction trade-offs.
- **9–10:** Kết nối query mechanism với database/application cost, thiết kế boundary và regression protection production-ready.

# Câu 2 — Azure Service Bus backlog tăng nhanh nhưng tăng consumer lại không giải quyết được

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, distributed systems, message lock, retries, idempotency, dependency degradation, SQL, observability, incident response

## Bối cảnh

Một order-processing service nhận messages từ Azure Service Bus và gọi SQL Server cùng một third-party fulfillment API. Bình thường queue gần như rỗng. Trong một campaign, queue depth tăng liên tục, processing latency từ vài giây lên hàng chục phút. Team scale App Service consumers từ 4 lên 16 instances nhưng throughput không tăng đáng kể; SQL dependency latency và external API timeout cùng tăng.

Một số messages xuất hiện lại sau khi đã được xử lý một phần. Support thấy một số orders có fulfillment request lặp, nhưng chưa xác định duplicate đến từ redelivery, publisher hay application retry. Team đề xuất tăng concurrency và retry count thêm nữa.

Chưa biết message processing duration so với lock behavior, prefetch/concurrency configuration, external API rate limits, SQL connection pool state, DLQ growth hay consumer idempotency strategy.

## Câu hỏi chính

Bạn sẽ điều tra và stabilize incident này như thế nào? Hãy đưa ra nhiều competing hypotheses cho việc backlog không giảm dù đã scale consumers, cách chứng minh từng hypothesis, xử lý duplicate/redelivery an toàn, và thiết kế prevention dài hạn mà không mặc định “scale thêm” là đáp án.

## Câu hỏi làm rõ nên cân nhắc

1. Arrival rate và completed processing rate thay đổi thế nào trước/sau campaign và sau scale-out?
2. Processing time phân bổ giữa SQL, external API và application CPU là bao nhiêu?
3. Message có idempotency/business key nào, và fulfillment API hỗ trợ idempotency semantics gì?
4. Delivery count, lock-lost/retry/DLQ metrics có tăng không?
5. SQL connection pool, database waits và external dependency throttling/rate-limit evidence cho thấy gì?

## Gợi ý tư duy

### Gợi ý 1

Backlog là chênh lệch giữa arrival rate và sustainable completion rate; consumer count chỉ là một biến.

### Gợi ý 2

Nếu bottleneck là downstream dependency, tăng parallelism có thể làm dependency tệ hơn và tăng retry amplification.

### Gợi ý 3

At-least-once style delivery/retry behavior phải được thiết kế cùng idempotent side effects và settlement strategy.

## Cấu trúc trả lời đề xuất

1. Đánh giá business impact và queue age/depth.
2. Giảm amplification/risk cho downstream systems.
3. Đo arrival/completion/failure/retry rates.
4. Tách processing timeline theo dependencies.
5. Lập hypotheses: external throttling, SQL bottleneck, lock/retry, poison messages, concurrency config.
6. Xác minh bằng telemetry.
7. Stabilize concurrency/retry và isolate failures.
8. Bảo vệ side effects bằng idempotency.
9. Drain backlog có kiểm soát.
10. Thêm capacity model, alerts và failure tests.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tăng concurrency/retry mù khi downstream latency đã tăng.
- So sánh message arrival rate, successful completion rate, failure/retry rate và oldest-message age.
- Phân rã latency qua SQL/external API bằng traces/dependency telemetry.
- Xem delivery count, settlement failures, lock-related errors và DLQ để hiểu redelivery.
- Duplicate delivery phải được coi là tình huống có thể xảy ra; side effect như fulfillment cần idempotency/business deduplication phù hợp.
- Retry phải bounded, có backoff/jitter phù hợp và phân biệt transient với permanent failure; poison work cần đường xử lý/DLQ.

### Điểm cộng

- Nếu external API throttles, giảm consumer concurrency có thể tăng successful throughput bằng cách giảm timeout/retry storm.
- Kiểm tra SQL connection pool, blocking/waits và query latency trước khi scale application tiếp.
- Dùng correlation/message/business IDs trong structured logs để reconstruct một order qua deliveries.
- Không complete message trước khi required durable side effects đã đạt trạng thái mong muốn; đồng thời tránh thực hiện side effect không idempotent lặp lại khi redelivery.

### Senior+

- Phân biệt broker throughput với end-to-end sustainable throughput.
- Thiết kế inbox/idempotency record hoặc business-state transition có unique constraint/atomicity phù hợp khi cần deduplication.
- Nếu publish/update local DB cần atomic relationship, cân nhắc Outbox ở boundary thích hợp nhưng không thêm pattern nếu scenario không cần.
- Capacity planning dựa trên service time và dependency quotas thay vì instance count đơn thuần.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng impact: backlog depth, oldest-message age, orders delayed và duplicate fulfillment risk. Immediate stabilization ưu tiên ngăn amplification. Nếu traces cho thấy external API timeout/rate limiting hoặc SQL saturation, tôi có thể giảm concurrency/retry pressure thay vì scale thêm, đồng thời bảo vệ critical traffic và phối hợp với dependency owner.

Evidence cần gồm arrival rate, completion rate, abandon/retry/dead-letter counts, delivery count distribution, handler duration, SQL dependency latency/waits/pool signals, external API status/latency/throttling và per-instance CPU/ThreadPool. Nếu application CPU thấp nhưng dependency time cao, scale consumer có thể chỉ tạo thêm concurrent waits và retries.

Với duplicate, dùng message ID và business order ID để phân biệt duplicate publish với redelivery. Handler phải thiết kế side effect idempotent. Nếu fulfillment provider hỗ trợ idempotency key, dùng stable business operation key. Nếu không, cần local durable state/deduplication và transaction boundary được thiết kế cẩn thận; chỉ check-then-act không atomic có thể race dưới concurrency.

Retry chỉ dành cho transient failure và phải bounded. Permanent validation error đi DLQ/repair flow thay vì retry vô hạn. Sau khi bottleneck ổn định, drain backlog với concurrency tăng dần và theo dõi success throughput chứ không chỉ queue depth.

Dài hạn, alert trên oldest-message age, completion/arrival ratio, retry/DLQ rate, dependency p95/p99 và duplicate/idempotency conflicts. Load/failure tests phải mô phỏng downstream slowdown và redelivery để chứng minh hệ thống degrade có kiểm soát.

## Mẫu trả lời trong phỏng vấn

“Tôi xem backlog như bài toán arrival rate lớn hơn sustainable completion rate. Việc scale từ 4 lên 16 mà throughput không tăng, trong khi SQL và external API latency tăng, làm tôi nghi bottleneck nằm downstream hoặc retry amplification. Tôi sẽ stabilize bằng cách giới hạn concurrency/retry nếu cần, rồi đo arrival/completion/failure rates, handler traces, SQL waits/pool, external throttling, delivery count và DLQ. Duplicate fulfillment là rủi ro correctness nên handler phải idempotent theo business operation; tôi không giả định broker chỉ giao một lần. Sau khi xác định bottleneck, tôi drain backlog có kiểm soát và theo dõi successful throughput. Dài hạn tôi thêm bounded retry, poison-message handling, idempotency state và alerts trên queue age, retry rate và dependency latency.”

## Câu hỏi đào sâu

1. Nếu giảm concurrency làm queue depth tăng nhanh hơn trong 10 phút đầu nhưng success rate tăng, bạn quyết định thế nào?
2. Một bảng `ProcessedMessageIds` đơn giản có luôn đủ để ngăn duplicate fulfillment không? Những race/transaction boundaries nào cần xem xét?
3. Nếu third-party API không hỗ trợ idempotency và timeout xảy ra sau khi họ đã nhận request nhưng trước khi bạn nhận response, bạn xử lý trạng thái “unknown outcome” thế nào?

## Lỗi trả lời thường gặp

- Chỉ scale thêm consumers mà không đo dependency capacity.
- Tăng retry count khi đang có retry storm.
- Cho rằng duplicate message là broker bug và không thiết kế idempotency.
- Complete/abandon message mà không reasoning về side-effect state.
- Chỉ monitor queue depth, bỏ qua oldest age, retry/DLQ và dependency telemetry.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất scale/retry thêm.
- **3–4:** Nhận ra downstream bottleneck nhưng thiếu evidence và duplicate handling.
- **5–6:** Có incident flow, telemetry, bounded retry và idempotency reasoning.
- **7–8:** Phân tích lock/redelivery, SQL/external capacity, atomic deduplication và failure tests.
- **9–10:** Điều khiển amplification tốt, xử lý unknown outcomes, capacity model và operational prevention đầy đủ.

# Câu 3 — Thiết kế file-ingestion platform: direct upload, Blob Storage và background processing đến đâu là đủ?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity/SAS concepts, background processing, Service Bus, SQL, security, reliability, observability, architecture trade-offs

## Bối cảnh

Một enterprise portal cần cho users upload CSV/JSON files từ vài MB đến vài GB. Sau upload, hệ thống validate format, parse records, cập nhật SQL Server và hiển thị trạng thái processing. Hiện prototype gửi toàn bộ file qua ASP.NET Core API rồi lưu tạm trên local filesystem trước khi một background task xử lý.

Production dự kiến nhiều App Service instances, không đảm bảo request và background processing nằm trên cùng instance. Product yêu cầu upload có thể retry, user xem progress, file lỗi có diagnostic, và không để một file lớn làm API mất ổn định. Security yêu cầu user chỉ được upload/read files họ được phép truy cập.

Team đang tranh luận giữa:

- proxy toàn bộ bytes qua API;
- client upload trực tiếp vào Azure Blob Storage bằng quyền hạn chế;
- xử lý synchronous ngay sau upload;
- dùng queue/background workers;
- đưa tất cả lên Kubernetes để “scale dễ hơn”.

Chưa có con số chính xác về peak concurrency, SLA processing hay retention.

## Câu hỏi chính

Hãy thiết kế một solution vừa đủ cho hệ thống này. Nêu rõ upload flow, authorization, storage/data model, processing boundary, retry/idempotency, progress, failure recovery, observability và deployment. Giải thích khi nào direct-to-Blob + asynchronous processing đáng complexity, khi nào API proxy đơn giản hơn, và vì sao Kubernetes không tự động là lựa chọn tốt hơn App Service/worker hosting.

## Câu hỏi làm rõ nên cân nhắc

1. Peak concurrent uploads, file-size distribution và processing SLA là bao nhiêu?
2. Client là browser hay trusted internal application, và network constraints ra sao?
3. Processing một file có thể được retry toàn bộ hay cần checkpoint/chunk-level progress?
4. SQL updates yêu cầu atomic toàn file hay chấp nhận partial/batch processing?
5. Retention, malware/content validation, audit và data residency requirements là gì?

## Gợi ý tư duy

### Gợi ý 1

Tách upload data plane khỏi application control plane nếu file size/concurrency khiến proxying trở thành bottleneck.

### Gợi ý 2

Direct upload không có nghĩa client được quyền rộng trên storage; capability phải scoped và authorization vẫn bắt đầu từ application.

### Gợi ý 3

Async processing cần durable state, idempotency và recovery; queue không tự giải quyết correctness.

## Cấu trúc trả lời đề xuất

1. Làm rõ scale/SLA/security/transaction requirements.
2. Chọn upload path theo evidence.
3. Thiết kế upload session/job metadata.
4. Thiết kế Blob permissions và object naming.
5. Tạo durable processing trigger/state transition.
6. Thiết kế worker, retry, idempotency và checkpoint.
7. Xử lý SQL transaction/batch semantics.
8. Expose status/progress API.
9. Thiết kế observability và operations.
10. Chọn hosting đơn giản nhất đáp ứng requirements.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng local filesystem như shared durable handoff giữa nhiều App Service instances.
- Với file lớn/concurrency đáng kể, direct upload vào Blob có thể tránh giữ request/API resources cho data transfer; nhưng quyết định cần dựa trên scale.
- Application vẫn authorize user và cấp quyền upload giới hạn về object/scope/thời gian thay vì storage credential rộng.
- Có durable metadata cho upload/processing status và ownership.
- Background processing phải idempotent/recoverable; queue delivery/retry không được giả định exactly-once.
- Progress/status phải đến từ durable state, không từ in-memory state của một instance.
- Kubernetes chỉ nên chọn nếu operational/orchestration requirements justify; App Service + worker/Functions có thể đơn giản hơn.

### Điểm cộng

- Upload session tạo blob key không đoán được hoặc được map bằng server-side ownership record; validate final object metadata trước khi enqueue.
- Worker stream file thay vì load toàn bộ file vào memory.
- Large processing dùng bounded batches/checkpoints nếu SLA/retry cost justify.
- SQL update strategy xác định rõ atomicity: staging + validation + commit, hoặc batch semantics có trạng thái rõ.
- Poison files đi failed state/DLQ với diagnostic an toàn, không log raw sensitive content.

### Senior+

- Tách control plane (`create upload`, authorize, status) khỏi data plane (Blob transfer) nhưng không over-service architecture.
- Có idempotency key/state machine cho transition `Created → Uploaded → Queued → Processing → Completed/Failed` và bảo vệ duplicate triggers.
- Xử lý orphaned uploads/jobs bằng reconciliation/retention job.
- Security bao gồm content-type không đáng tin, size limits, scanning policy nếu requirement, least privilege và audit.

## Hướng giải quyết tham khảo

Nếu files chủ yếu nhỏ và traffic thấp, proxy qua ASP.NET Core có thể đơn giản và đủ, miễn stream thay vì buffer toàn file và không dựa vào local disk cho durable workflow. Nhưng với vài GB và nhiều concurrent uploads, direct-to-Blob thường giảm API bandwidth/resource pressure. API tạo một upload record sau authorization và cấp một capability giới hạn cho đúng blob/path và thời gian cần thiết. Không đưa account key cho client.

Sau upload, cần một bước xác nhận durable rằng object đã tồn tại và metadata hợp lệ trước khi tạo processing work. SQL giữ job metadata/owner/status; Blob giữ raw file. Queue có thể decouple processing nếu processing lâu hoặc cần scale độc lập. Worker nhận job, kiểm tra current state/idempotency, stream file, validate và xử lý theo batch. Nếu duplicate message đến, state transition/business key ngăn cùng file tạo side effects lặp không kiểm soát.

Transaction strategy phụ thuộc requirement. Nếu toàn file phải atomic và dataset cho phép, có thể parse/validate vào staging rồi commit business changes trong transaction phù hợp. Nếu file rất lớn và partial processing được phép, dùng batches/checkpoints nhưng status phải diễn tả partial outcome rõ ràng. Không giữ transaction SQL dài hàng giờ.

Status API đọc durable metadata; progress có thể cập nhật theo batches với tần suất hợp lý. Failure đi trạng thái `Failed` có error category/correlation ID; poison work có DLQ/repair flow. Reconciliation tìm jobs mắc kẹt và orphan blobs.

Observability gồm upload success/duration, file sizes, queue age/depth, processing duration, rows/sec, failure categories, retries, DLQ, SQL dependency latency và Blob dependency telemetry. Với hosting, bắt đầu App Service + worker/Functions nếu đáp ứng scale và operational model; Kubernetes chỉ khi có requirements mà platform đơn giản không đáp ứng và team chấp nhận operational cost.

## Mẫu trả lời trong phỏng vấn

“Tôi tách control plane và file transfer khi file size/concurrency đủ lớn. API authorize user, tạo upload job và cấp quyền giới hạn cho đúng Blob; client upload trực tiếp, sau đó hệ thống xác nhận object và enqueue processing. SQL giữ durable ownership/status, Blob giữ file, worker stream dữ liệu và cập nhật progress theo batch. Tôi thiết kế handler idempotent vì processing trigger có thể lặp, và không dùng local filesystem hay in-memory progress vì App Service chạy nhiều instances. Nếu requirement cần atomic toàn file, tôi cân nhắc staging rồi commit; nếu file rất lớn và partial được phép thì checkpoint theo batch. Tôi bắt đầu bằng App Service/worker đơn giản; Kubernetes chỉ khi orchestration requirements thực sự justify complexity. Tôi monitor upload latency, queue age, processing duration, retries, DLQ và SQL/Blob dependencies.”

## Câu hỏi đào sâu

1. Nếu security không cho phép browser nhận bất kỳ SAS-style capability nào, bạn thay đổi upload design thế nào và chấp nhận cost gì?
2. Nếu một 4 GB file xử lý được 95% rồi worker crash, bạn chọn restart toàn file hay checkpoint? Evidence nào quyết định?
3. Nếu Product yêu cầu “không bao giờ process cùng file hai lần”, bạn sẽ challenge requirement đó và chuyển nó thành guarantees kỹ thuật nào?

## Lỗi trả lời thường gặp

- Dùng local disk như durable shared storage trên multi-instance hosting.
- Đưa storage credential rộng cho client để direct upload.
- Cho rằng queue bảo đảm processing exactly once.
- Load toàn bộ file lớn vào memory.
- Chọn Kubernetes chỉ vì file processing cần scale.

## Thang điểm 0–10

- **0–2:** Thiết kế dựa trên local disk/in-memory state hoặc bỏ qua authorization.
- **3–4:** Có Blob/queue nhưng thiếu idempotency, durable status hoặc failure recovery.
- **5–6:** Upload/processing boundary hợp lý, security và state rõ.
- **7–8:** Có transaction/checkpoint trade-offs, reconciliation, telemetry và hosting judgment.
- **9–10:** Thiết kế conditional theo scale/SLA, least privilege, recovery semantics và cost of complexity đầy đủ.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` là query composition/execution boundary; phải nhìn generated SQL và cardinality thay vì suy luận performance từ LINQ syntax.
- Queue backlog cần được phân tích bằng arrival rate, successful completion rate và downstream capacity; scale-out có thể làm retry/dependency saturation tệ hơn.
- Message retries/redelivery phải đi cùng idempotent side effects và observable failure handling.
- File ingestion lớn cần durable storage/state và explicit processing semantics; local instance state không phải workflow store.
- Chọn architecture/hosting theo requirement và evidence, không theo độ phức tạp hay xu hướng.

## Mẫu tư duy cần nhớ

- Xác định execution boundary trước khi tối ưu.
- Measure throughput của toàn dependency chain, không chỉ application instances.
- Design retry cùng idempotency và unknown-outcome handling.
- Tách durable state khỏi process lifetime.
- Chọn solution đơn giản nhất vẫn đáp ứng scale, security và recovery requirements.
