# Code Review Challenge 1 — EF Core retry ghi đè thay đổi của người dùng khi xử lý optimistic concurrency

**Chủ đề:** C#/.NET, EF Core, optimistic concurrency, transactions, API correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một ASP.NET Core API quản lý approval request. Hai người có thể mở cùng một request: requester sửa mô tả trong khi approver thay đổi trạng thái. Entity có `rowversion` để phát hiện concurrent update. Team muốn “giảm lỗi 409” nên thêm retry khi `SaveChangesAsync` ném `DbUpdateConcurrencyException`.

Production xuất hiện khiếu nại rằng một số nội dung vừa sửa bị quay về giá trị cũ, dù API trả `200`. Tỷ lệ lỗi thấp và khó tái hiện bằng test tuần tự.

## Đoạn code cần review

```csharp
public sealed class ApprovalService
{
    private readonly AppDbContext _db;
    private readonly ILogger<ApprovalService> _logger;

    public ApprovalService(AppDbContext db, ILogger<ApprovalService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<ApprovalDto> UpdateAsync(
        Guid id,
        UpdateApprovalRequest request,
        CancellationToken cancellationToken)
    {
        var entity = await _db.Approvals
            .SingleAsync(x => x.Id == id, cancellationToken);

        entity.Description = request.Description;
        entity.Status = request.Status;

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                await _db.SaveChangesAsync(cancellationToken);
                break;
            }
            catch (DbUpdateConcurrencyException ex) when (attempt < 3)
            {
                _logger.LogWarning(ex,
                    "Concurrency conflict for approval {ApprovalId}; retry {Attempt}",
                    id, attempt);

                foreach (var entry in ex.Entries)
                {
                    await entry.ReloadAsync(cancellationToken);
                    entry.CurrentValues.SetValues(request);
                }
            }
        }

        return new ApprovalDto(
            entity.Id,
            entity.Description,
            entity.Status,
            entity.RowVersion);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong concurrency handling.
2. Giải thích state của EF Core `OriginalValues`, `CurrentValues` và database values sau conflict/reload.
3. Phân tích vì sao blind retry có thể làm mất concurrent changes.
4. Ưu tiên findings theo severity và business impact.
5. Đề xuất API/concurrency contract tốt hơn, bao gồm cách client gửi version.
6. Nêu tests cho simultaneous edits và conflicting/non-conflicting fields.
7. Đề xuất telemetry để phân biệt expected concurrency conflict với database/transient failure.

## Câu hỏi gợi mở

1. `ReloadAsync` làm gì với values đang tracked trước conflict?
2. Nếu approver vừa đổi `Status`, requester retry với snapshot cũ thì điều gì xảy ra?
3. Retry có hợp lệ khi application chưa định nghĩa merge policy không?
4. `rowversion` nên đi từ server tới client và quay lại update request như thế nào?
5. HTTP response nào phù hợp nếu server không thể tự merge an toàn?

## Gợi ý

### Gợi ý 1

Rủi ro chính không phải “retry chưa đủ nhiều”, mà là **application đang tự quyết định merge semantics mà business chưa hề định nghĩa**.

### Gợi ý 2

Phân biệt ba bộ giá trị: client intent, database hiện tại và snapshot mà EF dùng để phát hiện conflict. Sau đó quyết định field nào được phép merge.

## Kết quả code review tham khảo

### Critical — Blind retry có thể ghi đè concurrent update hợp lệ

**Vấn đề:** Sau conflict, code reload database rồi áp lại toàn bộ request và save lại.

**Tại sao xảy ra:** Retry biến conflict thành last-writer-wins mà không có business merge policy. Client có thể đang gửi cả fields mà nó không thực sự sở hữu.

**Ảnh hưởng production:** Thay đổi hợp lệ của user khác có thể bị mất trong khi caller nhận `200`, tạo silent data corruption ở mức nghiệp vụ.

**Cách sửa:** Không tự động retry optimistic concurrency conflict như transient infrastructure error. Nếu không có deterministic merge rule, trả conflict cho client kèm version/current representation phù hợp để user/application quyết định.

### High — Update contract không thể hiện concurrency token của client

**Vấn đề:** Method load entity mới rồi áp request; không thấy expected `RowVersion` từ client.

**Tại sao xảy ra:** Server chỉ biết version tại thời điểm chính nó query, không biết version mà user đã nhìn thấy khi chỉnh sửa.

**Ảnh hưởng production:** Lost-update protection không phản ánh user editing session; stale UI có thể overwrite data mới nếu request bắt đầu sau thay đổi kia.

**Cách sửa:** Round-trip concurrency token qua DTO/ETag hoặc field version; attach/compare expected version khi update.

### High — `ReloadAsync` làm mất tracked client intent trước khi merge được đánh giá

**Vấn đề:** Reload thay tracked state bằng database state rồi `SetValues(request)` áp object request lên entity.

**Tại sao xảy ra:** Code không lưu rõ client-original/server-current/client-proposed values và không xác định field ownership.

**Ảnh hưởng production:** Merge behavior khó kiểm soát, đặc biệt khi DTO/entity shape khác nhau hoặc fields mới được thêm.

**Cách sửa:** Lấy database values riêng (`GetDatabaseValuesAsync`) khi cần phân tích conflict; xây merge có chủ đích theo domain thay vì generic `SetValues`.

### High — Final-attempt failure semantics không rõ

**Vấn đề:** Catch chỉ chạy khi `attempt < 3`; attempt cuối ném exception ra ngoài nhưng method không map conflict thành API contract có ý nghĩa.

**Tại sao xảy ra:** Infrastructure exception bị để leak qua service boundary.

**Ảnh hưởng production:** Caller có thể nhận generic 500 cho expected concurrency condition.

**Cách sửa:** Chuyển domain concurrency outcome thành explicit result và map thành `409 Conflict` hoặc precondition response phù hợp contract.

### Medium — Request có thể mass-update fields không thuộc command

**Vấn đề:** `SetValues(request)` dễ làm merge policy phụ thuộc shape của request.

**Tại sao xảy ra:** Generic property copying thay cho explicit command semantics.

**Ảnh hưởng production:** Khi DTO phát triển, fields ngoài ý định có thể bị overwrite.

**Cách sửa:** Gán explicit fields mà operation sở hữu; tách commands nếu requester và approver có quyền thay đổi khác nhau.

### Medium — Observability chỉ đếm retry, không ghi nhận conflict semantics

**Vấn đề:** Log warning không cho biết expected version/current version hoặc operation type.

**Tại sao xảy ra:** Concurrency conflict bị coi như exception chung.

**Ảnh hưởng production:** Khó biết conflict tập trung ở workflow/field nào và liệu UX/API contract có vấn đề.

**Cách sửa:** Structured metric/log cho conflict count theo operation/entity type, không log sensitive payload; correlation ID và result (`resolved`, `returned-conflict`) rõ ràng.

## Phiên bản đề xuất

Ví dụ dưới đây giả định client round-trip `RowVersion` và business chưa cho phép auto-merge:

```csharp
public async Task<UpdateApprovalResult> UpdateAsync(
    Guid id,
    UpdateApprovalRequest request,
    CancellationToken cancellationToken)
{
    var entity = await _db.Approvals
        .SingleOrDefaultAsync(x => x.Id == id, cancellationToken);

    if (entity is null)
        return UpdateApprovalResult.NotFound();

    _db.Entry(entity)
        .Property(x => x.RowVersion)
        .OriginalValue = request.RowVersion;

    entity.Description = request.Description;
    entity.Status = request.Status;

    try
    {
        await _db.SaveChangesAsync(cancellationToken);

        return UpdateApprovalResult.Success(new ApprovalDto(
            entity.Id,
            entity.Description,
            entity.Status,
            entity.RowVersion));
    }
    catch (DbUpdateConcurrencyException ex)
    {
        var entry = ex.Entries.Single();
        var databaseValues = await entry.GetDatabaseValuesAsync(cancellationToken);

        if (databaseValues is null)
            return UpdateApprovalResult.NotFound();

        var current = (Approval)databaseValues.ToObject();

        return UpdateApprovalResult.Conflict(new ApprovalDto(
            current.Id,
            current.Description,
            current.Status,
            current.RowVersion));
    }
}
```

Controller có thể map conflict thành `409 Conflict` cùng representation/version hiện tại. Nếu API dùng HTTP preconditions, ETag/`If-Match` là một alternative tốt; contract cụ thể cần thống nhất với client.

Nếu domain cho phép merge non-overlapping fields, merge phải explicit. Ví dụ requester chỉ sở hữu `Description`, approver chỉ sở hữu `Status`; server có thể re-read current row, xác minh field mà caller thay đổi không conflict với versioned baseline rồi áp command. Đây là domain rule, không phải generic EF retry policy.

## Giải thích thiết kế sau khi sửa

Optimistic concurrency không nhằm loại bỏ conflict; nó làm conflict **visible trước khi lost update xảy ra**. Server cần biết version mà client đã đọc, không chỉ version server vừa query khi request bắt đầu.

`DbUpdateConcurrencyException` khác transient connection error. Retry transient database operation có thể hợp lý theo provider strategy, nhưng concurrency conflict cần business decision: reject, merge hoặc overwrite có chủ đích.

Explicit command fields giảm nguy cơ accidental overwrite và làm authorization/ownership rõ hơn.

## Trade-offs

- Trả `409` yêu cầu frontend có UX refresh/merge/retry.
- ETag chuẩn HTTP nhưng thêm contract handling ở client; version field đơn giản hơn trong một số internal APIs.
- Fine-grained merge giảm conflict UX nhưng tăng domain complexity và cần baseline values.
- Pessimistic locking có thể tránh một số conflict nhưng tăng blocking/deadlock/capacity cost và thường không phù hợp user edit session dài.

## Cách kiểm thử

1. **Concurrency integration test:** hai clients đọc cùng version, client A save trước; client B save stale version phải nhận conflict và không overwrite A.
2. **Non-conflicting command test:** nếu domain hỗ trợ field-level merge, requester sửa description và approver đổi status đồng thời; xác nhận policy giữ cả hai.
3. **Deletion race:** entity bị xóa giữa read và save; map đúng thành domain outcome.
4. **Authorization test:** requester không thể dùng generic update để thay status nếu field ownership tách biệt.
5. **API test:** conflict response trả current version/representation theo contract và frontend có thể refresh/retry có chủ đích.

## Quan sát trong production

Theo dõi concurrency-conflict rate theo endpoint/operation, success-after-user-retry, 409 rate và latency. Correlate bằng request/correlation ID nhưng không log toàn bộ approval payload. Nếu conflict tăng sau UX/workflow change, kiểm tra thời gian edit, polling/refresh behavior và command granularity trước khi “tăng retry”.

Application Insights dependency telemetry nên tách concurrency outcome khỏi SQL transient failures/deadlocks/timeouts để team không áp cùng một retry policy cho hai loại lỗi khác bản chất.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào auto-merge hai concurrent changes là an toàn, và bạn cần dữ liệu gì để chứng minh chúng không conflict?
2. Bạn chọn ETag/`If-Match` hay version field trong JSON cho internal SPA API dựa trên tiêu chí nào?
3. Nếu Product yêu cầu “không bao giờ hiện 409 cho user”, bạn sẽ thách thức requirement và đề xuất UX/workflow nào thay vì blind overwrite?

# Code Review Challenge 2 — Playwright E2E pass local nhưng flaky khi CI chạy parallel workers

**Chủ đề:** Playwright, TypeScript, E2E testing, test isolation, shared test data, CI reliability, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một web portal có Playwright E2E suite chạy trong CI. Local chạy một worker gần như luôn pass. CI chạy 6 workers để giảm thời gian pipeline, nhưng suite fail ngẫu nhiên 5–12% ở các tests profile/settings. Team đã tăng retries lên 3 và thêm `waitForTimeout`, khiến pipeline chậm nhưng vẫn flaky.

Các tests dùng chung một seeded account `qa-user@example.test`. Mỗi test có thể thay đổi display name và notification settings. Backend là ASP.NET Core API với SQL Server; CI environment được dùng riêng cho pipeline nhưng tests trong cùng run chạy parallel.

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const email = 'qa-user@example.test';
const password = 'Password123!';

test.describe.configure({ mode: 'parallel' });

test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.fill('#email', email);
  await page.fill('#password', password);
  await page.click('button[type=submit]');
  await page.waitForTimeout(1000);
});

test('updates display name', async ({ page }) => {
  await page.goto('/profile');
  await page.fill('#displayName', 'Automation User');
  await page.click('button:has-text("Save")');
  await page.waitForTimeout(2000);

  await page.reload();
  await expect(page.locator('#displayName'))
    .toHaveValue('Automation User');
});

test('enables weekly notifications', async ({ page }) => {
  await page.goto('/settings');
  await page.check('#weeklyNotifications');
  await page.click('button:has-text("Save")');
  await page.waitForTimeout(2000);

  await page.reload();
  await expect(page.locator('#weeklyNotifications')).toBeChecked();
});

test('can restore default profile', async ({ page }) => {
  await page.goto('/profile');
  await page.fill('#displayName', 'QA User');
  await page.click('button:has-text("Save")');
  await page.waitForTimeout(2000);

  await expect(page.locator('.toast-success')).toBeVisible();
});
```

## Nhiệm vụ của ứng viên

1. Xác định nguyên nhân correctness/flakiness trong test design.
2. Phân tích behavior khi nhiều workers mutate cùng account.
3. Xác định vì sao fixed sleeps và retries có thể che lỗi thay vì sửa lỗi.
4. Ưu tiên findings theo ảnh hưởng tới độ tin cậy của CI.
5. Đề xuất test-data/isolation design tốt hơn mà vẫn giữ pipeline nhanh.
6. Nêu cách test/debug race giữa workers và backend persistence.
7. Đề xuất artifacts/telemetry cần lưu khi test fail.

## Câu hỏi gợi mở

1. Ba tests có thật sự independent khi chạy cùng lúc không?
2. `waitForTimeout(2000)` đang chờ điều kiện nào?
3. Nếu test A reload đúng lúc test C vừa đổi display name, assertion của A có nghĩa gì?
4. Retry pass ở lần hai chứng minh product đúng hay chỉ chứng minh race không lặp lại?
5. CI cần capture gì để phân biệt UI timing issue, API failure và shared-data race?

## Kết quả code review tham khảo

### Critical — Parallel tests mutate cùng một user

**Vấn đề:** Tất cả tests đăng nhập cùng account và thay đổi shared profile/settings.

**Tại sao xảy ra:** `mode: 'parallel'` cho phép tests chạy đồng thời nhưng server-side test data không được partition.

**Ảnh hưởng production/CI:** Assertion phụ thuộc scheduling giữa workers; test có thể fail dù feature đúng hoặc pass dù test khác vừa sửa state. Suite mất tính diagnostic.

**Cách sửa:** Cấp unique account/data namespace cho mỗi worker/test hoặc reset deterministic state bằng API/fixture có ownership rõ. Nếu không thể isolate, serialize đúng nhóm tests như biện pháp có chủ đích, nhưng chấp nhận runtime cost.

### High — Fixed sleeps không đồng bộ với application state

**Vấn đề:** `waitForTimeout(1000/2000)` giả định operation hoàn thành trong thời gian cố định.

**Tại sao xảy ra:** CI load/network/database latency thay đổi; sleep không quan sát condition cần thiết.

**Ảnh hưởng production/CI:** Test vừa chậm vừa flaky: ngủ quá lâu khi nhanh và chưa đủ khi chậm.

**Cách sửa:** Chờ navigation/URL, response có ý nghĩa, enabled/visible state hoặc assertion auto-waiting của Playwright. Chỉ dùng timeout cố định cho mục đích đặc biệt, không làm synchronization primitive.

### High — Retry che shared-state race

**Vấn đề:** Retry có thể làm test pass sau khi worker khác kết thúc.

**Tại sao xảy ra:** Root cause phụ thuộc timing; rerun thay timing thay vì sửa isolation.

**Ảnh hưởng production/CI:** False confidence, pipeline lâu hơn và flaky-rate thật bị che.

**Cách sửa:** Theo dõi first-attempt failure riêng; dùng retries có giới hạn cho known infrastructure noise nếu cần, nhưng không coi retry là fix. Quarantine/fix deterministic root cause.

### High — Login setup không chờ condition xác nhận authentication

**Vấn đề:** Sau click login chỉ sleep 1 giây rồi test tiếp tục.

**Tại sao xảy ra:** Không xác minh navigation/session/auth state đã sẵn sàng.

**Ảnh hưởng production/CI:** Tests có thể đi `/profile` khi login request vẫn pending hoặc failed.

**Cách sửa:** Chờ URL/dashboard marker hoặc API response/state chứng minh login thành công. Tốt hơn có thể dùng authenticated storage state fixture nếu mục tiêu test không phải login flow.

### Medium — Test không thiết lập precondition riêng

**Vấn đề:** Notification test chỉ `check` checkbox; profile tests giả định initial value nhưng không tạo baseline trước assertion.

**Tại sao xảy ra:** Test dựa vào seed/shared previous state.

**Ảnh hưởng production/CI:** Order dependence và false pass nếu state đã đúng từ run trước.

**Cách sửa:** Arrange deterministic precondition qua API/fixture/database-supported test setup, sau đó Act/Assert UI behavior.

### Medium — Selectors gắn chặt implementation/text

**Vấn đề:** CSS IDs và text selector có thể brittle khi UI refactor/localization.

**Tại sao xảy ra:** Selector strategy không ưu tiên user-facing semantics/stable test contracts.

**Ảnh hưởng production/CI:** Maintenance noise không liên quan business regression.

**Cách sửa:** Ưu tiên role/label/test-id có chủ đích tùy UI accessibility contract, ví dụ `getByRole`, `getByLabel`.

### Medium — Failure artifacts chưa được thiết kế

**Vấn đề:** Snippet không cho thấy trace/screenshot/video/network evidence khi fail.

**Tại sao xảy ra:** Pipeline chỉ báo assertion cuối.

**Ảnh hưởng production/CI:** Team rerun để “xem có pass không” thay vì điều tra root cause.

**Cách sửa:** Retain Playwright trace on first retry/failure, screenshot và CI metadata; correlate API request/correlation ID khi có thể.

## Phiên bản đề xuất

Một hướng là fixture cấp account riêng theo worker và dùng observable waits. Ví dụ rút gọn:

```ts
import { test as base, expect } from '@playwright/test';

type Fixtures = {
  account: { email: string; password: string };
};

const test = base.extend<Fixtures>({
  account: async ({ request }, use, testInfo) => {
    const suffix = `${testInfo.workerIndex}-${testInfo.retry}-${Date.now()}`;
    const email = `e2e-${suffix}@example.test`;
    const password = 'GeneratedForTestOnly!';

    await request.post('/test-support/users', {
      data: { email, password, displayName: 'QA User' }
    });

    await use({ email, password });

    await request.delete(`/test-support/users/${encodeURIComponent(email)}`);
  }
});

test.beforeEach(async ({ page, account }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill(account.email);
  await page.getByLabel('Password').fill(account.password);

  await Promise.all([
    page.waitForURL('**/dashboard'),
    page.getByRole('button', { name: 'Sign in' }).click()
  ]);
});

test('updates display name', async ({ page }) => {
  await page.goto('/profile');
  await page.getByLabel('Display name').fill('Automation User');

  const saveResponse = page.waitForResponse(r =>
    r.url().includes('/api/profile') &&
    r.request().method() === 'PUT');

  await page.getByRole('button', { name: 'Save' }).click();
  expect((await saveResponse).ok()).toBeTruthy();

  await page.reload();
  await expect(page.getByLabel('Display name'))
    .toHaveValue('Automation User');
});
```

`/test-support/users` chỉ nên tồn tại trong isolated test environment, được authentication/network-policy bảo vệ và tuyệt đối không expose ở production. Alternative tốt hơn có thể là provisioning trực tiếp qua test harness/backend fixture nếu platform hỗ trợ.

Nếu tạo account mỗi test quá chậm, có thể cấp một account cho mỗi worker và bảo đảm tests trong worker không mutate cùng field đồng thời; hoặc tạo data bằng worker-scoped fixture rồi reset deterministic state trước mỗi test. Lựa chọn dựa trên runtime và isolation requirement.

## Giải thích thiết kế sau khi sửa

Parallelism chỉ an toàn khi tests không cạnh tranh cùng mutable state hoặc state được partition rõ. Unique data làm failure reproducible hơn và loại order dependence.

Playwright auto-waiting/observable conditions giúp synchronization gắn với behavior thực thay vì wall-clock guess. API setup có thể làm Arrange nhanh hơn UI setup, miễn là test vẫn validate user-visible flow cần thiết.

Retries là signal, không phải correctness mechanism. Nếu first-attempt flaky rate tăng, pipeline nên surface trend ngay cả khi retry cuối pass.

## Trade-offs

- Unique account per test tăng setup/cleanup cost và có thể làm database lớn nếu cleanup fail.
- Worker-scoped data nhanh hơn nhưng isolation yếu hơn test-scoped data.
- Serializing tests đơn giản nhưng kéo dài CI và có thể che architectural coupling của test data.
- Trace/video tăng artifact storage; nên retention có policy.
- Test-support API tăng attack surface nếu deploy nhầm, vì vậy phải tách environment/build/configuration chặt.

## Cách kiểm thử

1. **Parallel stress:** chạy nhóm test 50–100 lần với 6 workers; first-attempt failure phải về mức kỳ vọng và không phụ thuộc ordering.
2. **Isolation test:** cố ý chạy hai profile updates song song trên hai fixture accounts; state không cross-contaminate.
3. **Slow-backend test:** inject API latency; observable waits vẫn pass trong timeout hợp lý mà không thêm sleep.
4. **Failure artifact test:** force API 500; trace/network evidence phải đủ chỉ ra request/response gây fail.
5. **Cleanup test:** kill test giữa chừng và xác minh lifecycle job/fixture không để test data tăng vô hạn.

## Quan sát trong production

Đây chủ yếu là CI/test-environment observability: theo dõi first-attempt pass rate, retry pass rate, duration theo test, worker count và failure signature. Lưu Playwright trace/screenshot cho failure, cùng build SHA, browser version và test-data identifier.

Ở backend test environment, structured logs nên cho phép correlate request với test run/worker identifier mà không đưa production-only instrumentation vào business logic. Dashboard flaky tests nên phân biệt assertion regression, infrastructure failure và retry-only pass.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận chạy một nhóm E2E tests serial thay vì đầu tư isolation?
2. Nếu suite có 2.000 tests, bạn cân bằng test-scoped data với pipeline duration như thế nào?
3. Retry policy nào giúp phân loại infrastructure noise mà không biến flaky product behavior thành green build giả?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Optimistic concurrency có giá trị vì nó làm lost-update risk trở nên visible; không nên biến `DbUpdateConcurrencyException` thành blind retry. Cần round-trip client version, định nghĩa merge semantics theo domain và trả conflict khi server không thể merge an toàn.

E2E parallelism chỉ đáng giá khi test data có isolation. Shared mutable account làm scheduling của workers trở thành một phần của expected result. Fixed sleeps và retries thường làm triệu chứng ít xuất hiện hơn chứ không sửa root cause.

## Mẫu tư duy cần nhớ

- Phân biệt **transient failure** với **business concurrency conflict** trước khi retry.
- Không auto-merge khi chưa có explicit ownership/merge rule.
- Parallel test cần **isolated mutable state** hoặc serialization có chủ đích.
- Chờ **observable condition**, không dùng wall-clock sleep làm synchronization.
- Flaky retry là telemetry cần điều tra, không phải bằng chứng correctness.
