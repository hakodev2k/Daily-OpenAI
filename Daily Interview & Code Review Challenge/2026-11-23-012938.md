# Code Review Challenge 1 — Azure Service Bus: thanh toán trùng khi consumer bị retry

**Chủ đề:** C#/.NET 8, Azure Service Bus, SQL Server, idempotency, distributed systems  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một hệ thống e-commerce nhận thông báo `PaymentCaptured` từ Azure Service Bus queue. Consumer ghi trạng thái đơn hàng vào SQL Server, gọi API đối tác cấp quyền sử dụng sản phẩm số, rồi hoàn tất message. Hệ thống chạy bốn Azure App Service instances, mỗi instance có một consumer. Trong một đợt tăng tải, khách hàng nhận hai license cho một đơn; một số đơn ở trạng thái Paid nhưng chưa có license. API đối tác có timeout ngẫu nhiên; chưa xác định timeout có nghĩa thao tác đã thất bại hay chỉ response bị mất. Đối tác hỗ trợ `Idempotency-Key` nhưng hiện chưa được sử dụng. Message có `EventId`, `OrderId`, `PaymentId`, `Amount`.

Giả định `AppDbContext` được tạo từ `IDbContextFactory<AppDbContext>`; `LicenseApi` là typed HTTP client; queue sử dụng PeekLock và auto-complete được tắt. Không giả định exactly-once delivery.

## Đoạn code cần review

```csharp
public sealed record PaymentCaptured(
    Guid EventId, Guid OrderId, string PaymentId, decimal Amount);

public sealed class PaymentConsumer
{
    private readonly IDbContextFactory<AppDbContext> _factory;
    private readonly LicenseApi _licenseApi;
    private readonly ILogger<PaymentConsumer> _log;

    public PaymentConsumer(
        IDbContextFactory<AppDbContext> factory,
        LicenseApi licenseApi,
        ILogger<PaymentConsumer> log)
    {
        _factory = factory;
        _licenseApi = licenseApi;
        _log = log;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var message = args.Message.Body.ToObjectFromJson<PaymentCaptured>();
        if (message is null)
        {
            await args.CompleteMessageAsync(args.Message);
            return;
        }

        await using var db = await _factory.CreateDbContextAsync();
        var order = await db.Orders.SingleAsync(x => x.Id == message.OrderId);

        if (order.Status == "Paid")
        {
            await args.CompleteMessageAsync(args.Message);
            return;
        }

        order.Status = "Paid";
        order.PaymentId = message.PaymentId;
        order.PaidAmount = message.Amount;
        await db.SaveChangesAsync();

        var license = await _licenseApi.IssueAsync(order.Id.ToString());
        order.LicenseId = license.Id;
        await db.SaveChangesAsync();

        _log.LogInformation("Issued license {LicenseId} for {OrderId}",
            license.Id, order.Id);
        await args.CompleteMessageAsync(args.Message);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Đánh dấu Paid trước khi cấp license rồi bỏ qua retry

**Vấn đề:** Nhánh `Status == "Paid"` coi nghiệp vụ hoàn tất mặc dù `LicenseId` có thể chưa tồn tại.  
**Tại sao xảy ra:** Database commit và HTTP call là hai side effects không atomic; crash/timeout sau commit đầu tạo trạng thái trung gian.  
**Ảnh hưởng production:** Đơn hàng bị kẹt vĩnh viễn mà message được complete.  
**Cách sửa:** Tách `PaymentRecorded` khỏi `LicenseIssued`, lưu durable fulfillment intent/outbox trong cùng transaction với payment state; chỉ đánh dấu hoàn tất khi đã ghi nhận license.

### [Critical] — External side effect không idempotent

**Vấn đề:** `IssueAsync` không gửi stable idempotency key.  
**Tại sao xảy ra:** Redelivery hoặc timeout khiến cùng một yêu cầu được thực hiện lại; timeout không khẳng định đối tác rollback.  
**Ảnh hưởng production:** Cấp nhiều license, phát sinh chi phí hoặc khiếu nại.  
**Cách sửa:** Dùng khóa nghiệp vụ ổn định (ví dụ `license:{OrderId}` nếu mỗi order chỉ có một license), yêu cầu đối tác deduplicate; có reconciliation bằng key khi response mất.

### [High] — Race giữa consumers

**Vấn đề:** Hai consumer cùng đọc trạng thái chưa Paid rồi cùng cập nhật và gọi đối tác.  
**Tại sao xảy ra:** Read-then-write không có uniqueness/optimistic concurrency hoặc claim atomic.  
**Ảnh hưởng production:** Duplicate fulfillment và ghi đè `LicenseId`.  
**Cách sửa:** Unique constraint cho `PaymentId` và fulfillment business key; claim bằng transaction/conditional update hoặc concurrency token, xử lý conflict bằng re-read.

### [High] — Thiếu kiểm tra payment invariants

**Vấn đề:** Message `Amount`, `PaymentId`, `OrderId` được chấp nhận mà không đối chiếu expected amount, currency, payment provider identity và trạng thái.  
**Tại sao xảy ra:** Event payload bị coi là nguồn chân lý đầy đủ.  
**Ảnh hưởng production:** Ghi nhận sai đơn hoặc thanh toán không hợp lệ.  
**Cách sửa:** Xác thực event từ trusted producer, kiểm tra payment identity và các invariants theo hợp đồng nghiệp vụ; không log thông tin thanh toán nhạy cảm.

### [High] — Message settlement và lock lifetime không được xử lý có chủ đích

**Vấn đề:** Không phân loại lỗi retryable/permanent; không thấy cấu hình auto lock renewal, cancellation, dead-letter và max delivery.  
**Tại sao xảy ra:** Handler giả định có đủ thời gian và mọi exception sẽ được xử lý giống nhau.  
**Ảnh hưởng production:** Redelivery khi handler cũ còn chạy, poison-message loop, backlog.  
**Cách sửa:** Đặt timeout, auto-renew phù hợp với SLA, cancellation, retry/backoff và DLQ; coi settlement failure là trạng thái không chắc chắn và dựa vào idempotency.

### [Medium] — Không có durable event deduplication và reconciliation

**Vấn đề:** Không ghi `EventId` đã xử lý, cũng không có job sửa trạng thái pending.  
**Tại sao xảy ra:** Dựa hoàn toàn vào `Order.Status`.  
**Ảnh hưởng production:** Khó audit, không tự phục hồi sau mất response.  
**Cách sửa:** Inbox/processed-event uniqueness khi cần, fulfillment record có trạng thái và số lần thử; job reconciliation quét pending quá SLA.

### [Medium] — Thiếu cancellation và telemetry liên kết

**Vấn đề:** EF/HTTP calls không nhận cancellation token; logs thiếu `EventId`, attempt, correlation và latency.  
**Tại sao xảy ra:** Luồng xử lý không coi shutdown và chẩn đoán production là một phần thiết kế.  
**Ảnh hưởng production:** Shutdown kéo dài, khó xác định duplicate thực hay retry hợp lệ.  
**Cách sửa:** Propagate cancellation phù hợp; structured logs và tracing qua message, DB, HTTP; không log payload chứa PII.

## Phiên bản đề xuất

Thiết kế hai bước: consumer chỉ ghi payment và tạo fulfillment intent **trong một SQL transaction**; worker riêng thực hiện external side effect bằng idempotency key. Các unique constraints là bắt buộc. Mã minh họa dưới đây giả định `PaymentEvent.EventId` và `Fulfillment.OrderId` có unique indexes; `PaymentEvent`, `Fulfillment`, `Order` là EF entities. `Order` có `ExpectedAmount`, `Currency` và `PaymentId`. Validation về nguồn event và currency được thực hiện trước khi gọi handler; các chi tiết auth phụ thuộc hợp đồng producer.

```csharp
public async Task RecordPaymentAsync(
    PaymentCaptured evt, CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    if (await db.PaymentEvents.AnyAsync(x => x.EventId == evt.EventId, ct))
        return;

    var order = await db.Orders.SingleAsync(x => x.Id == evt.OrderId, ct);
    if (order.ExpectedAmount != evt.Amount ||
        (order.PaymentId != null && order.PaymentId != evt.PaymentId))
        throw new InvalidPaymentEventException(evt.EventId);

    db.PaymentEvents.Add(new PaymentEvent { EventId = evt.EventId });
    order.Status = "PaymentRecorded";
    order.PaymentId = evt.PaymentId;

    if (!await db.Fulfillments.AnyAsync(x => x.OrderId == order.Id, ct))
        db.Fulfillments.Add(new Fulfillment {
            OrderId = order.Id, Status = "Pending",
            IdempotencyKey = $"license:{order.Id:N}"
        });

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
```

Đoạn trên **không** tự giải quyết concurrent insert: unique constraints phải là nguồn bảo vệ cuối cùng; khi `DbUpdateException` do unique conflict, rollback, re-read và chỉ coi là duplicate nếu dữ liệu đã ghi tương thích. Đừng bắt mọi `DbUpdateException` rồi bỏ qua.

Worker fulfillment (pseudocode có chủ đích, vì API claim phụ thuộc SQL provider):

```text
claim atomically one Pending/Due fulfillment with lease and fencing/version
call LicenseApi.Issue(orderId, Idempotency-Key = fulfillment.IdempotencyKey)
on success: persist LicenseId, Status=Completed if claim version still valid
on timeout: query partner by idempotency key if supported;
            otherwise retry same key with bounded backoff
on permanent rejection: mark Failed, alert or route for manual resolution
on worker crash: lease expires; another worker resumes using same key
reconciliation: inspect stale Pending/InProgress and partner state
```

Message chỉ được complete sau khi payment + intent transaction commit thành công. Nếu complete thất bại, redelivery là an toàn nhờ uniqueness; nếu DB commit thất bại, message phải được retry theo policy. Khi `EventId` trùng nhưng payload khác, ghi security/audit signal thay vì coi là hợp lệ. Không dùng SQL transaction bao quanh HTTP call.

## Giải thích thiết kế sau khi sửa

Đảm bảo **atomicity nội bộ** giữa ghi nhận thanh toán và intent; không hứa atomicity xuyên SQL–HTTP–Service Bus. Stable idempotency key bảo vệ side effect ở đối tác; lease/claim bảo vệ công việc nội bộ; reconciliation khắc phục uncertain outcomes. Nếu nhà cung cấp không hỗ trợ idempotency hoặc lookup, cần thay đổi hợp đồng tích hợp hoặc quy trình xử lý thủ công vì không thể bảo đảm exactly-once external effect chỉ bằng database local.

## Trade-offs

Thêm bảng, worker và vận hành retry/DLQ tăng độ phức tạp, độ trễ eventual consistency và chi phí monitoring. Với throughput nhỏ vẫn có thể dùng một worker, nhưng durable intent + idempotency vẫn cần nếu cấp license có chi phí. Service Bus duplicate detection (nếu bật và cấu hình đúng) không thay thế idempotent consumer. Nếu order có nhiều line items/licenses, business key phải chuyển thành `OrderId + LineItemId`, không dùng khóa toàn order.

## Cách kiểm thử

1. **Concurrency integration:** phát cùng event 100 lần trên nhiều consumer; assert một fulfillment business key và một license.
2. **Failure-path:** crash sau SQL commit trước complete; redelivery không mất intent.
3. **Network failure:** đối tác cấp license rồi timeout; retry cùng idempotency key không cấp thêm.
4. **Database test:** hai transactions insert cùng key; unique constraint chặn duplicate, logic conflict re-read chính xác.
5. **Poison-message:** payment mismatch hoặc event hỏng được phân loại, DLQ/audit theo policy; không retry vô hạn.

## Quan sát trong production

Structured logs với `EventId`, `OrderId`, `FulfillmentId`, attempt và trace ID; Application Insights dependency spans cho SQL/HTTP; metrics `pending_age_seconds`, `duplicate_event_count`, `license_issue_attempts`, `reconciliation_count`, `DLQ_depth`, `lock_lost_count`; alert cho pending vượt SLA và duplicate license phía đối tác. Không ghi secrets hoặc payment payload nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu đối tác không hỗ trợ idempotency và không có lookup API, bạn cam kết mức consistency nào?
2. Nếu một đơn có nhiều item được refund một phần, mô hình state và business key thay đổi thế nào?
3. Bạn phân biệt Service Bus duplicate detection với consumer inbox và outbox như thế nào?

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from "vue";

type Product = {
  id: string;
  name: string;
  highlightHtml: string;
  price: number;
};
type SearchResponse = {
  items: Product[];
  total: number;
  page: number;
};

const query = ref("");
const category = ref("all");
const page = ref(1);
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");
const token = localStorage.getItem("access_token") ?? "";

async function loadProducts() {
  loading.value = true;
  error.value = "";
  const url = "/api/products/search?q=" + query.value +
    "&category=" + category.value + "&page=" + page.value;

  try {
    const response = await fetch(url, {
      headers: { Authorization: "Bearer " + token }
    });
    const data = await response.json() as SearchResponse;
    products.value = data.items;
    total.value = data.total;
  } catch (e) {
    error.value = "Không tải được sản phẩm";
  }
  loading.value = false;
}

watch([query, category, page], loadProducts);
onMounted(loadProducts);
</script>

<template>
  <input v-model="query" placeholder="Tìm sản phẩm" />
  <select v-model="category">
    <option value="all">Tất cả</option>
    <option value="electronics">Electronics</option>
  </select>
  <p v-if="loading">Đang tải...</p>
  <p v-if="error">{{ error }}</p>
  <div v-for="product in products" :key="product.id">
    <h3>{{ product.name }}</h3>
    <div v-html="product.highlightHtml"></div>
    <span>{{ product.price }}</span>
  </div>
  <button @click="page++">Trang tiếp</button>
  <small>{{ total }} kết quả</small>
</template>
```

## Kết quả code review tham khảo

### [Critical] — XSS qua `v-html`

**Vấn đề:** Render HTML chưa được xác thực/sanitize từ search service chứa user-controlled content.  
**Tại sao xảy ra:** `v-html` bypass HTML escaping mặc định của interpolation.  
**Ảnh hưởng production:** Script/event-handler injection hoặc DOM-based attack, có thể dẫn tới chiếm phiên tùy mô hình token.  
**Cách sửa:** Ưu tiên trả plain-text highlights hoặc structured spans và render bằng Vue escaping; nếu bắt buộc HTML, sanitize theo allowlist bằng thư viện được duy trì, áp CSP defense-in-depth.

### [High] — Race condition ghi đè kết quả mới

**Vấn đề:** Response cũ có thể đến sau response mới rồi ghi vào `products`.  
**Tại sao xảy ra:** Watcher tạo nhiều Promise đồng thời, không kiểm tra request identity.  
**Ảnh hưởng production:** Kết quả sai filter; người dùng có thể thao tác trên sản phẩm không mong đợi.  
**Cách sửa:** Abort request trước và thêm sequence ID guard cho stale response; cancellation không thay thế guard khi response đã hoàn tất.

### [High] — HTTP error bị xử lý như thành công

**Vấn đề:** `fetch` không reject cho 4xx/5xx; code parse JSON rồi gán fields mà không kiểm tra schema.  
**Tại sao xảy ra:** Nhầm network failure với HTTP failure.  
**Ảnh hưởng production:** UI rỗng, lỗi runtime hoặc che giấu 401/403.  
**Cách sửa:** Check `response.ok`, phân loại auth, timeout, server error; validate response schema tại trust boundary nếu cần.

### [High] — Token tồn tại trong localStorage và được chụp một lần

**Vấn đề:** Token JS-readable tăng tác động XSS; snapshot token lúc mount có thể hết hạn hoặc không phản ánh refresh.  
**Tại sao xảy ra:** Component tự quản lý token thay vì dùng auth-aware API client.  
**Ảnh hưởng production:** 401 ngẫu nhiên và token exposure nếu có XSS.  
**Cách sửa:** Dùng auth client tập trung với token acquisition/refresh; cân nhắc BFF + HttpOnly Secure SameSite cookies khi phù hợp, kèm CSRF controls. Không coi storage choice đơn lẻ là đủ bảo mật.

### [Medium] — Không encode query params và không debounce

**Vấn đề:** Ghép URL bằng string, mỗi phím gõ gọi API.  
**Tại sao xảy ra:** Không dùng `URLSearchParams` và delay/throttle hợp lý.  
**Ảnh hưởng production:** Query bị diễn giải sai khi có `&`, `#`; tải tăng, search latency xấu.  
**Cách sửa:** URLSearchParams và debounce 250–400ms tùy UX; server vẫn phải validate input và rate limit phù hợp.

### [Medium] — Pagination và filter state không nhất quán

**Vấn đề:** Đổi query/category không reset page; `page++` không chặn vượt tổng trang.  
**Tại sao xảy ra:** Không định nghĩa state transition của search.  
**Ảnh hưởng production:** Trả trang trống dù có kết quả; khó debug.  
**Cách sửa:** Reset page về 1 khi filter đổi, disable Next khi không còn trang; dùng `pageSize` từ hợp đồng API.

### [Medium] — Loading/error và unmount lifecycle sai

**Vấn đề:** Request cũ có thể đặt `loading=false` khi request mới đang chạy; unmount không hủy công việc.  
**Tại sao xảy ra:** Không quản lý owner của request.  
**Ảnh hưởng production:** Spinner nhấp nháy, update state không còn cần thiết.  
**Cách sửa:** Cleanup watcher, abort, chỉ owner mới nhất được cập nhật state.

## Phiên bản đề xuất

Bản dưới giả định API trả `highlightText` plain text thay cho HTML; backend và client cùng triển khai contract mới. `apiFetch` là client đã được kiểm thử, lấy token hợp lệ tại thời điểm gọi và xử lý 401 theo auth flow; không đặt access token vào URL. `pageSize=20` là giả định của ví dụ. Nếu API chưa thể thay đổi, cần sanitizer allowlist đã kiểm thử trước khi render HTML, không dùng regex tự viết.

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from "vue";
import { apiFetch } from "@/services/apiFetch";

type Product = { id: string; name: string; highlightText: string; price: number };
type Result = { items: Product[]; total: number; page: number };

const query = ref("");
const category = ref("all");
const page = ref(1);
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref("");
const pageSize = 20;
let seq = 0;
let controller: AbortController | undefined;
let debounce: ReturnType<typeof setTimeout> | undefined;

watch([query, category], () => { page.value = 1; }, { flush: "sync" });

watch([query, category, page], ([q, c, p], _old, onCleanup) => {
  const id = ++seq;
  controller?.abort();
  controller = new AbortController();
  const signal = controller.signal;
  if (debounce) clearTimeout(debounce);
  loading.value = true;
  error.value = "";

  debounce = setTimeout(async () => {
    const params = new URLSearchParams({
      q: q.trim(), category: c, page: String(p)
    });
    try {
      const response = await apiFetch("/api/products/search?" + params, { signal });
      if (!response.ok) throw new Error("HTTP " + response.status);
      const data = await response.json() as Result;
      if (id !== seq || signal.aborted) return;
      products.value = data.items;
      total.value = data.total;
    } catch (e) {
      if (id !== seq || signal.aborted) return;
      error.value = "Không tải được sản phẩm";
    } finally {
      if (id === seq) loading.value = false;
    }
  }, 300);

  onCleanup(() => {
    clearTimeout(debounce);
    controller?.abort();
  });
}, { immediate: true });

onUnmounted(() => {
  ++seq;
  clearTimeout(debounce);
  controller?.abort();
});
</script>

<template>
  <input v-model="query" placeholder="Tìm sản phẩm" />
  <select v-model="category">
    <option value="all">Tất cả</option>
    <option value="electronics">Electronics</option>
  </select>
  <p v-if="loading">Đang tải...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <div v-for="product in products" :key="product.id">
    <h3>{{ product.name }}</h3>
    <div>{{ product.highlightText }}</div>
    <span>{{ product.price }}</span>
  </div>
  <button :disabled="loading || page * pageSize >= total"
          @click="page++">Trang tiếp</button>
  <small>{{ total }} kết quả</small>
</template>
```

Trong ứng dụng thực, nên giữ `AbortController` và timer theo từng watcher invocation thay vì biến shared nếu có nhiều nguồn gọi độc lập; cleanup phải chỉ hủy request thuộc invocation đó. `apiFetch` cần thực sự hỗ trợ `AbortSignal` và bảo đảm không retry non-idempotent request vô điều kiện. Cần xác minh contract `pageSize`/schema, authorization và caching phía backend.

## Giải thích thiết kế sau khi sửa

Sequence guard đảm bảo latest-request-wins kể cả khi abort không kịp; debounce giảm requests không cần thiết; URLSearchParams encode input; plain-text interpolation bảo vệ khỏi HTML injection. Client không tự định nghĩa auth policy: backend vẫn enforce authorization trên mọi endpoint. Loading state thuộc request mới nhất. Với ứng dụng lớn, có thể cân nhắc query library đã được team chấp nhận nhưng không bắt buộc.

## Trade-offs

Debounce tăng latency cảm nhận khi người dùng dừng gõ; abort không bảo đảm server dừng truy vấn đã bắt đầu; sequence guard vẫn cần. Plain text mất formatting highlight; structured highlight segments cho UX tốt hơn nhưng cần API contract phức tạp hơn. BFF/cookie giảm khả năng JS đọc token nhưng phát sinh CSRF và vận hành session. Caching search có thể hữu ích cho query phổ biến, song phải xét personalization và quyền truy cập trước khi cache shared.

## Cách kiểm thử

1. **Component test:** giả lập response A chậm hơn B; UI chỉ hiển thị B.
2. **Security test:** `highlightText` chứa HTML độc hại; DOM chỉ có text, không thực thi.
3. **API test:** query có `&`, Unicode, ký tự đặc biệt; server nhận đúng params.
4. **Playwright E2E:** đổi filter khi page sâu, Next disabled đúng, loading/error khi 401/500.
5. **Load/network test:** gõ liên tục trên mạng chậm; đếm request và quan sát cancellation/latency.

## Quan sát trong production

Browser network waterfall, count request theo search session, abort rate, HTTP 401/429/5xx, `search_latency_ms`, stale-response-discard count (không chứa keyword nhạy cảm); backend Application Insights correlation, p95 search dependency latency, SQL/search service query cost; CSP violation reports và frontend error tracking. Không log access token hoặc raw search input có PII.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search API dùng Elasticsearch eventual consistency, UI cần thông báo gì sau khi cập nhật sản phẩm?
2. Khi kết quả phụ thuộc quyền truy cập người dùng, cache key và CDN policy phải thay đổi thế nào?
3. Khi chuyển từ client-side fetch sang SSR, bạn xử lý auth và hydration mismatch ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Distributed workflow không thể dùng một status flag thay cho durable business state, idempotency và reconciliation.
- Message delivery, database transaction và external HTTP side effect có failure boundaries khác nhau.
- Vue reactive watcher không tự bảo đảm request ordering; cancellation và sequence guard giải quyết các lớp rủi ro khác nhau.
- Browser API response là untrusted input; render text mặc định an toàn hơn raw HTML.
- Observability phải liên kết được hành vi người dùng, request, database, message và external dependency.

## Mẫu tư duy cần nhớ

1. Liệt kê từng điểm crash giữa các side effects trước khi quyết định retry.
2. Thiết kế idempotency theo business operation, không theo lần delivery.
3. Xác định owner của async state trước khi cập nhật UI.
4. Xác minh trust boundary và authorization ở cả API lẫn presentation layer.
5. Kiểm thử đường lỗi, đo production telemetry rồi mới tối ưu.
