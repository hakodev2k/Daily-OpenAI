# Câu 1 — Cosmos DB: RU còn dư nhưng một tenant vẫn bị throttling

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partition key, RU, indexing, .NET API.

## Bối cảnh

ASP.NET Core .NET 8 API lưu activity events trong Cosmos DB với `id`, `tenantId`, `userId`, `createdAt`. Partition key là `/tenantId`. Tenant lớn gặp 429 và p99 tăng giờ cao điểm, trong khi dashboard tổng RU còn dư. API lọc tenant, user, khoảng thời gian và sắp xếp mới nhất. Chưa biết throughput mode, indexing policy, retry và phân phối request.

## Câu hỏi chính

Giải thích cơ chế logical/physical partition, RU và truy vấn dẫn tới hiện tượng này; cần chứng cứ nào để phân biệt hot partition với expensive query và nên thay đổi thiết kế như thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Provisioned throughput hay autoscale, region và RU/s?
2. Request/size phân phối theo tenant và time window thế nào?
3. SDK diagnostics: request charge, retry, latency, partition range?
4. Query có filter partition key, projection, pagination và composite index không?
5. SLA freshness, retention và query xuyên tenant là gì?

## Gợi ý tư duy

### Gợi ý 1
Capacity tổng không phản ánh mọi bottleneck cục bộ.

### Gợi ý 2
Đo 429, normalized RU, request charge và query metrics theo partition range.

### Gợi ý 3
Synthetic/hierarchical partition keys thay đổi cả write distribution lẫn read fan-out; migration cần container mới.

## Cấu trúc trả lời đề xuất

1. Xác định access patterns và SLA.
2. Giải thích routing, RU và throttling.
3. Đối chiếu các giả thuyết với diagnostics.
4. Mitigation và phương án dài hạn.
5. Migration, security, tests, monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc
Phân biệt logical/physical partition; 429 không chứng minh tổng RU cạn; đo query charge trước khi tối ưu; retry phải bounded.

### Điểm cộng
Point read với id + partition key, indexing, continuation token, skew theo tenant, cost của cross-partition query.

### Senior+
Thiết kế cutover/backfill, reconciliation, versioning, rollback và đánh giá chi phí phân mảnh tenant.

## Hướng giải quyết tham khảo

**Cơ chế:** Cosmos DB tính RU cho các thao tác; partition key quyết định cách dữ liệu và request được phân phối. Một key nóng hoặc query tốn RU có thể bị throttling dù biểu đồ tổng có dư. Logical partition và physical partition không đồng nhất; không suy ra bottleneck từ tổng request count. Query có filter tenant nhưng đọc nhiều document vẫn có thể tốn RU.

**Evidence:** Azure Monitor normalized RU consumption và throttled requests theo partition-key range; SDK diagnostics gồm request charge, activity ID, retry count, duration; query metrics, item count, page count, phân phối key. Replay query đại diện với dữ liệu và index tương ứng. Kiểm tra ORDER BY, composite index theo query pattern; index mới tăng write/storage cost. So sánh point read và query.

**Mitigation:** giảm concurrency theo tenant, backpressure, SDK retry/backoff với deadline, pagination bằng continuation token, projection và cache chỉ nếu stale data được chấp nhận. Không retry vô hạn. Tăng RU chỉ khi số liệu hỗ trợ.

**Long-term:** nếu skew bền vững, đánh giá bucket theo tenant/user/time hoặc hierarchical partition keys tùy access pattern và tính năng account; query toàn tenant có thể fan-out nhiều hơn. Đổi partition key thường cần container mới: backfill có checkpoint, verify counts/checksums, đồng bộ delta idempotent, canary read, reconciliation và rollback. Bảo vệ tenant isolation bằng authorization server-side; không tin tenantId từ client.

**Điều kiện thay đổi:** nếu query/index mới là nguyên nhân chính, tối ưu query trước; nếu tất cả key đều bão hòa, throughput adjustment có thể đủ. Theo dõi p95/p99, 429/key, RU/operation, retry, cost và correctness sau cutover.

## Mẫu trả lời trong phỏng vấn

“Tôi không kết luận thiếu RU chỉ vì có 429, cũng không kết luận hệ thống ổn vì tổng RU còn dư. Tôi kiểm tra request charge, normalized RU theo partition range, query metrics và phân phối tenant. Nếu vấn đề là expensive query, tôi tối ưu filter, projection, index và pagination. Nếu tenant lớn là hot key, tôi đánh giá bucket hoặc hierarchical partition key nhưng phải tính chi phí truy vấn xuyên bucket. Trước mắt tôi giới hạn concurrency và retry có deadline. Thay partition key cần migration có backfill, đồng bộ delta, kiểm đếm và rollback; bảo mật tenant vẫn được thực thi ở API. Tôi quyết định dựa trên tải thực và SLA, không theo công thức chung.”

## Câu hỏi đào sâu

1. Nếu cần 100 events mới nhất toàn tenant, bucket theo user gây trade-off gì?
2. Làm sao chứng minh composite index giúp giảm RU mà không tăng write cost quá mức?
3. Nếu không được downtime, bạn làm cutover và reconciliation ra sao?

## Lỗi trả lời thường gặp

- Cho rằng RU tổng còn dư thì không thể bị 429.
- Chọn partition key chỉ theo cardinality.
- Retry vô hạn hoặc tăng RU mà không đo.
- Giả định đổi partition key bằng một thao tác cấu hình.
- Quên cross-partition read cost và tenant authorization.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Clarification | 1.5 |
| Internal mechanism | 2.5 |
| Evidence và diagnosis | 2 |
| Trade-offs, design | 2 |
| Migration, monitoring, communication | 2 |

# Câu 2 — Search trả HTTP 200 nhưng catalog sai sau reindex

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 22 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, Azure App Service, Vue.js, observability, incident response.

## Bối cảnh

E-commerce site lưu catalog trong SQL Server, search/filter bằng Elasticsearch, frontend Vue.js. Sau full reindex, sản phẩm ngừng bán vẫn xuất hiện, sản phẩm mới biến mất. API trả 200 và cluster health xanh. Indexer dùng batch, alias và incremental updates nhưng checkpoint, retry, cache TTL và thứ tự alias switch chưa rõ. Không được xóa index giữa giờ bán hàng.

## Câu hỏi chính

Bạn sẽ ổn định hệ thống, phân biệt lỗi ingest/alias/refresh/cache/query và khôi phục search correctness ra sao, rồi ngăn tái diễn thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. Tỷ lệ sai, phạm vi tenant/region và business impact?
2. Product IDs sai và versions tương ứng trong SQL/index?
3. Full reindex và incremental updates chạy đồng thời không?
4. Alias mapping, bulk failures, tombstones, checkpoint?
5. CDN/API/browser cache và freshness SLA?

## Gợi ý tư duy

### Gợi ý 1
Cluster health không xác nhận business correctness.

### Gợi ý 2
Theo dấu product ID từ SQL → job/event → index → alias → API → browser.

### Gợi ý 3
Tìm race giữa snapshot và delta, bulk partial failure, missing delete event, cache và refresh visibility.

## Cấu trúc trả lời đề xuất

1. Impact và stabilization.
2. Thu thập timeline, sample IDs và telemetry.
3. Đặt giả thuyết cạnh tranh.
4. Kiểm chứng theo từng lớp.
5. Fix có rollback, verify và prevention.
6. Truyền thông incident, theo dõi freshness.

## Ý chính của câu trả lời tốt

### Bắt buộc
Đối chiếu source of truth; bảo vệ unpublish/checkout; kiểm tra alias, ingestion, cache; không rebuild mù quáng.

### Điểm cộng
Bulk item errors, event ordering/versioning, refresh, alias cutover, drift detection.

### Senior+
Snapshot + delta replay với cutover barrier, validation gate, rollback và freshness SLO.

## Hướng giải quyết tham khảo

**Impact:** đo số product sai, mức ảnh hưởng người mua và checkout; nếu cần, guard trạng thái bán ở authoritative API/checkout. Đánh giá rollback alias chỉ khi index cũ được chứng minh tốt hơn, không switch tùy tiện.

**Evidence:** đối chiếu SQL row/version, outbox/change log, job checkpoint, bulk response item-level failures, Elasticsearch document, alias targets, API response và browser network. Dùng correlation IDs. Query trực tiếp Elasticsearch và request bypass cache để tách các lớp.

**Giả thuyết:** (1) full snapshot cũ được switch sau delta mới; (2) delete/unpublish event bị mất; (3) bulk job đánh dấu thành công dù một số items fail; (4) refresh chưa làm document visible; (5) CDN/browser/API cache stale; (6) alias sai. Với mỗi giả thuyết xác định phép thử: compare versions, lag, alias state, bulk logs, direct query và cache headers. HTTP 200 không bác bỏ giả thuyết nào.

**Remediation:** nếu race được chứng minh, xây index mới từ snapshot có checkpoint, replay delta có ordering/version guard, verify counts + sampled IDs + deletes, sau đó atomic alias switch và tiếp tục stream. Stable IDs, idempotent updates và tombstones. Không ép refresh mỗi write vì cost. Nếu cache sai, invalidate/purge theo scope. Không mặc định lỗi Elasticsearch khi dữ liệu nguồn hoặc frontend sai.

**Prevention:** test concurrent reindex/update/delete, retries, bulk partial failure, alias rollback, cache stale; alert source-to-index lag, mismatch samples, failed bulk items, freshness p95, business correctness. Hạn chế quyền đổi alias, bảo vệ dữ liệu chưa publish. Nếu unpublish phải tức thì, enforce tại serving layer; nếu SLA cho phép eventual consistency thì kiến trúc có thể đơn giản hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi xem đây là incident correctness dù search API vẫn 200. Tôi xác định phạm vi và trước hết bảo vệ sản phẩm đã ngừng bán ở API/checkout. Sau đó lấy vài product ID làm trace từ SQL qua event/job, index, alias, API đến cache/browser. Tôi kiểm tra race giữa full reindex và incremental update, delete events, bulk partial errors và stale cache. Chỉ khi chứng minh nguyên nhân tôi mới rollback alias hay rebuild. Dài hạn cần version guard, replay delta, validation gate và freshness monitoring. Mức phức tạp phụ thuộc SLA: nếu eventual consistency được chấp nhận thì không cần distributed transaction, nhưng trạng thái không được bán phải được enforce rõ.”

## Câu hỏi đào sâu

1. Reindex mất sáu giờ; bảo đảm không mất updates lúc alias switch thế nào?
2. Vì sao refresh không giải quyết missing events hoặc CDN stale?
3. Khi index cũ cũng sai, tiêu chí rollback hay forward-fix là gì?

## Lỗi trả lời thường gặp

- Coi cluster xanh là dữ liệu đúng.
- Xóa/rebuild index ngay trong production.
- Không xem bulk item errors và delete events.
- Không kiểm tra cache, API và browser.
- Không có SLO freshness hoặc verification gate.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact, clarification | 1.5 |
| Stabilization | 1.5 |
| Competing hypotheses và evidence | 2.5 |
| Indexing/consistency depth | 2 |
| Prevention/observability | 1.5 |
| Trade-offs và communication | 1 |

# Câu 3 — Modernize approval portal từ IIS sang Azure App Service

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** .NET Framework modernization, ASP.NET Core, SQL Server, TeamCity, Octopus Deploy, SSO, architecture, audit.

## Bối cảnh

Một approval portal viết ASP.NET MVC .NET Framework 4.5, chạy IIS/Windows Server, dùng jQuery, SQL Server, SSO và email notification. Hệ thống có multi-level approvals và audit trail. Đội muốn modernize sang .NET 8/10, cân nhắc Azure App Service. TeamCity build và Octopus Deploy release; rollback target 15 phút. Chưa rõ dependency Windows-only, RTO/RPO, throughput và yêu cầu audit compliance.

## Câu hỏi chính

Bạn chọn giữ monolith, Modular Monolith hay Microservices, xác định boundaries, transactions và triển khai migration tăng dần thế nào để bảo vệ audit/approval correctness, SSO, API compatibility và rollback?

## Câu hỏi làm rõ nên cân nhắc

1. Có COM, Windows authentication, IIS modules hay third-party assemblies không tương thích?
2. SLA, peak concurrency, RTO/RPO và audit retention?
3. Ai có quyền duyệt/sửa/đọc audit, yêu cầu tamper-evidence?
4. Có thể chuyển routing theo module và chạy song song hệ cũ-mới?
5. Schema consumers, API contracts và downtime window?

## Gợi ý tư duy

### Gợi ý 1
Modernization không bắt buộc rewrite.

### Gợi ý 2
Approval state, audit record và notification có transaction boundaries khác nhau.

### Gợi ý 3
Strangler routing, expand-contract migration, outbox và rollback window cần thiết kế cùng nhau.

## Cấu trúc trả lời đề xuất

1. Inventory dependencies và business invariants.
2. Chốt constraints và SLA.
3. So sánh architecture/hosting options.
4. Define ownership, API và data model.
5. Transaction, security và reliability.
6. Migration, rollout, rollback, testing.
7. Cost, observability và decision criteria.

## Ý chính của câu trả lời tốt

### Bắt buộc
Architecture dựa trên constraints; approval/audit nhất quán; incremental migration; DB rollback compatibility; authorization server-side.

### Điểm cộng
Optimistic concurrency, outbox, idempotency, contract tests, SSO migration và canary.

### Senior+
Tách service chỉ khi có lý do operational/domain, định nghĩa reconciliation và diễn tập rollback thực tế.

## Hướng giải quyết tham khảo

**Khuyến nghị có điều kiện:** nếu domain gắn kết và đội vận hành nhỏ, ưu tiên Modular Monolith ASP.NET Core với modules Requests, Approvals, Audit, IdentityIntegration, Notifications, Reporting; giữ SQL Server ban đầu. Module là ownership và dependency boundary, không chỉ folder. Nếu scale/ownership/deployment độc lập thực sự cần, mới tách notification/reporting. Microservices thêm network failure, tracing và eventual consistency; không mặc định tốt hơn.

**Correctness:** state machine cho approval transitions; policy authorization server-side; transaction ghi approval state + audit + outbox trong cùng DB. Rowversion/optimistic concurrency ngăn hai approvers ghi đè; idempotency key chống double-submit. Audit append-only, quyền DB hạn chế; nếu cần chống sửa bởi admin thì bổ sung tamper-evidence/external immutable storage theo compliance. Worker gửi email sau commit, retry idempotent; không giữ transaction mở chờ email.

**Migration:** inventory .NET Framework libraries, Windows-specific APIs, auth, config, SQL dependencies và jQuery screens. Characterization tests giữ business rules; chuyển từng endpoint qua proxy/route switch, giữ API contracts và xác minh SSO/cookie/claims compatibility. Frontend migrate từng phần; không bắt buộc rewrite. Expand-contract schema: thêm schema tương thích, backfill, deploy code đọc/ghi compatible, chỉ remove cột cũ sau rollback window. Không coi rollback binary là đủ khi DB schema/data đã đổi.

**Hosting/DevOps:** App Service Linux nếu dependencies tương thích; nếu còn Windows-only, cân nhắc Windows App Service hoặc IIS tạm thời. TeamCity build immutable artifact, Octopus Deploy deploy với approvals, environment config, canary, smoke tests và feature flags. Secrets qua Key Vault/Managed Identity nếu áp dụng được; least privilege, CSRF cho cookie forms, XSS guard ở legacy UI. Diễn tập rollback 15 phút với routing, schema, auth và dữ liệu; đo thực tế thay vì cam kết suông.

**Observability:** approval transition errors, concurrency conflicts, audit/outbox mismatch, queue lag, authentication failures, p95 latency, deployment version và correlation IDs. Test integration transactions, concurrent approvals, SSO, Playwright E2E, contract compatibility, schema rollback và failure injection.

**Khi đổi quyết định:** nếu Windows-only dependencies sâu, giữ coexistence lâu hơn; nếu nhiều nhóm cần deploy độc lập và ranh giới nghiệp vụ rõ, tách service có thể đáng giá. Không chọn Kubernetes nếu App Service đáp ứng yêu cầu và đội thiếu năng lực vận hành cluster.

## Mẫu trả lời trong phỏng vấn

“Tôi bắt đầu từ inventory IIS/.NET Framework dependencies, SSO, database và audit invariants. Nếu domain còn liên kết chặt và đội vận hành nhỏ, tôi chọn Modular Monolith trên ASP.NET Core thay vì mặc định Microservices. Approval, audit và outbox ghi cùng transaction; email xử lý sau commit với idempotency. Tôi dùng strangler routing chuyển từng endpoint, characterization tests và expand-contract schema để giữ backward compatibility. TeamCity tạo artifact cố định, Octopus deploy canary với smoke tests; rollback 15 phút phải được diễn tập cả ở DB, auth và routing. App Service là lựa chọn ưu tiên nếu dependency hỗ trợ; phần Windows-only có thể ở IIS hoặc Windows hosting tạm thời. Tôi chỉ tách service khi có bằng chứng về scale hoặc ownership.”

## Câu hỏi đào sâu

1. Audit phải chống chỉnh sửa kể cả bởi DBA thì bổ sung gì?
2. Approval và notification ở hai database: consistency và failure recovery ra sao?
3. Product yêu cầu Kubernetes trong một sprint: phản biện bằng dữ liệu gì?

## Lỗi trả lời thường gặp

- Mặc định Microservices/Kubernetes tốt hơn.
- Gửi email trước commit hoặc không bảo vệ audit.
- Rollback code mà bỏ qua schema/data compatibility.
- Giả định mọi .NET Framework dependency chạy trên .NET mới.
- Không kiểm thử SSO, concurrency và recovery.
