# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi dưới tải

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, Change Tracker, performance diagnosis, observability

## Bối cảnh

Một ASP.NET Core API trả về danh sách nhân viên và trạng thái offboarding. Sau một thay đổi refactor, p95 latency tăng từ khoảng 180 ms lên hơn 1 giây khi traffic cao. Database CPU tăng rõ rệt nhưng CPU của API không tăng tương ứng. Code tạo một `IQueryable<Employee>`, áp dụng nhiều điều kiện tùy request, sau đó vừa gọi `CountAsync()` vừa materialize bằng `ToListAsync()`. Một helper khác enumerate lại cùng query để tạo audit metadata. Một số developer cho rằng “LINQ chỉ chạy một lần vì biến query đã được tạo rồi”, và đề xuất thêm `AsNoTracking()` như giải pháp chính.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc tạo `IQueryable` đến khi các terminal operations chạy, vì sao latency/database load có thể tăng, misconception nào đang tồn tại, `AsNoTracking()` giải quyết phần nào và không giải quyết phần nào, rủi ro production là gì, và bạn sẽ chứng minh giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint có cần cả total count và page data không?
- Helper audit enumerate query hay chỉ inspect expression tree?
- Query có `Include`, projection, pagination hoặc navigation collection nào không?
- Query có được thực thi song song trên cùng `DbContext` không?
- SQL thực tế và execution plan thay đổi thế nào sau refactor?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng expression tree với thực thi query.
- **Gợi ý 2:** Xem từng terminal operation như một ứng viên tạo database round-trip riêng; sau đó tách chi phí tracking khỏi chi phí SQL.
- **Gợi ý 3:** Đo số command, duration, rows và SQL shape thay vì suy luận chỉ từ code C#.

## Cấu trúc trả lời đề xuất

1. Làm rõ mục tiêu endpoint và số lần enumerate.
2. Mô tả deferred execution và translation.
3. Liệt kê database round-trips.
4. Phân biệt tracking overhead với query execution overhead.
5. Kiểm tra SQL, plan, row count và indexes.
6. Đề xuất giảm execution dư thừa và projection phù hợp.
7. Test bằng integration/load test.
8. Theo dõi command count, p95/p99 và DB metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chủ yếu biểu diễn query; tạo biến không đồng nghĩa query đã chạy.
- `CountAsync()`, `ToListAsync()` và enumeration khác có thể tạo các lần thực thi riêng.
- `AsNoTracking()` giảm Change Tracker overhead cho read-only query nhưng không hợp nhất nhiều database round-trip.
- Không được chạy nhiều operation đồng thời trên cùng một `DbContext` instance.

### Điểm cộng

- Projection chỉ lấy cột cần thiết, pagination đúng chỗ, tránh materialize sớm.
- Kiểm tra generated SQL bằng logging/`ToQueryString()` trong môi trường phù hợp.
- Phân tích execution plan, logical reads, row estimates và index usage.

### Nâng cao

- Nhận ra `Count` + page query đôi khi là yêu cầu UX có thể thay đổi, ví dụ cursor pagination hoặc bỏ exact total.
- Phân biệt cartesian explosion do collection includes với tracking overhead.
- Đề xuất query tagging/tracing để liên hệ request với SQL commands.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only, cần page data và hiện tại UI yêu cầu exact total. Query được xây dựng một lần nhưng bị execute ba lần.

EF Core giữ query dưới dạng expression cho tới terminal operation. Vì vậy `CountAsync()` tạo một SQL command, `ToListAsync()` tạo command khác, và helper enumerate lại query có thể tạo command thứ ba. Nếu query chứa joins/includes/filter phức tạp, ba lần execution có thể khuếch đại database CPU và I/O. `AsNoTracking()` hữu ích khi entities không cần update vì giảm tracking/identity bookkeeping, nhưng không loại bỏ những SQL command dư thừa.

Tôi sẽ bật structured command logging/tracing ở mức an toàn, gắn correlation/query tag, kiểm tra generated SQL và execution plan. Sau đó xác nhận số round-trip/request và row count. Fix ưu tiên là không enumerate query trong audit helper, dùng projection DTO, giữ filter/pagination server-side và chỉ thực hiện những query business thực sự cần. Nếu exact total không bắt buộc, có thể thay đổi API contract để tránh `COUNT` đắt tiền. Nếu cần cả hai, chấp nhận hai queries nhưng tối ưu riêng và đo trade-off.

Failure case cần kiểm tra gồm cancellation giữa count và page query, dữ liệu thay đổi giữa hai statement khiến total/page không hoàn toàn cùng snapshot, timeout và query plan regression. Không nên mở transaction chỉ để ép consistency nếu business không yêu cầu vì sẽ tăng locking/versioning cost tùy database/isolation.

Testing gồm integration test kiểm tra kết quả/filter/paging, command interceptor để đếm số SQL command, load test và so sánh DB CPU/logical reads. Monitoring gồm request latency, EF/database command duration, command count/request, timeout rate và slow-query telemetry.

Khuyến nghị sẽ thay đổi nếu business cần snapshot-consistent count + rows, dataset rất nhỏ, hoặc endpoint thực sự cần tracked entities để update trong cùng unit of work.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng `AsNoTracking()` vì symptom cho thấy database load tăng và trước tiên cần xác định query chạy bao nhiêu lần. Với EF Core, việc tạo `IQueryable` chỉ xây expression; mỗi terminal operation như `CountAsync` hay `ToListAsync` có thể translate và gửi SQL riêng. Nếu helper enumerate lại query thì một request có thể tạo thêm round-trip. `AsNoTracking` giảm overhead của Change Tracker cho read-only data nhưng không ngăn query bị execute ba lần.

Tôi sẽ xác nhận bằng EF command logs/traces, generated SQL, execution plan và command count trên mỗi request. Sau đó tôi loại enumeration trong audit helper, project đúng DTO, giữ filter/paging ở database và xem exact total có thật sự cần không. Nếu vẫn cần count và page thì hai query có thể hợp lý, nhưng phải đo plan, reads và latency. Tôi cũng kiểm tra consistency requirement giữa count và rows thay vì tự động thêm transaction. Cuối cùng tôi chạy integration/load test và theo dõi p95/p99, DB CPU, command duration và timeout rate.”

## Câu hỏi đào sâu

1. Nếu `CountAsync()` và `ToListAsync()` được gọi đồng thời bằng `Task.WhenAll` trên cùng `DbContext`, chuyện gì có thể xảy ra?
2. Nếu bỏ exact count giúp giảm tải nhưng product yêu cầu “Page 1 of N”, bạn thương lượng API/UX thế nào?
3. `AsSplitQuery()` có luôn cải thiện performance khi có nhiều `Include` không? Vì sao không?

## Lỗi trả lời thường gặp

- Cho rằng `IQueryable` cache kết quả sau lần execution đầu tiên.
- Xem `AsNoTracking()` là giải pháp cho mọi vấn đề EF Core performance.
- Chỉ nhìn C# mà không kiểm tra generated SQL/plan.
- Materialize sớm rồi filter/paginate trong memory.
- Đề xuất chạy song song nhiều query trên cùng `DbContext`.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1.0

# Câu 2 — Incident: Hangfire xử lý offboarding hai lần và trạng thái Exchange không nhất quán

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire, idempotency, distributed side effects, database consistency, Exchange integration, observability

## Bối cảnh

Một background job xử lý employee offboarding: đọc cấu hình từ SQL, gọi dịch vụ tích hợp Exchange Online để đổi mailbox/forwarding/auto-reply, rồi cập nhật trạng thái trong database. Sau deployment, support báo một số nhân viên nhận side effect lặp lại, vài record trong DB báo `Completed` nhưng trạng thái mailbox không đúng như mong đợi, và một số job xuất hiện nhiều lần trong dashboard. Hệ thống chạy nhiều worker instance. External API có thể timeout sau khi server đã nhận request. Không có distributed transaction giữa SQL và Exchange.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ phút đầu tiên đến khi có long-term fix như thế nào, bao gồm impact assessment, mitigation, evidence, hypotheses, root cause, idempotency, retry/failure recovery và monitoring?

## Câu hỏi làm rõ nên cân nhắc

- “Duplicate job” nghĩa là cùng Hangfire job ID hay nhiều enqueue cho cùng business operation?
- External operation nào idempotent và operation nào có side effect không an toàn khi lặp?
- DB `Completed` được ghi trước hay sau external calls?
- Có business key/idempotency key cho một lần offboarding không?
- Retry policy hiện tại nằm ở Hangfire, HTTP client hay cả hai?

## Gợi ý tư duy

- **Gợi ý 1:** Tách delivery semantics của job khỏi business idempotency.
- **Gợi ý 2:** Timeout không chứng minh external operation thất bại; trạng thái có thể “unknown”.
- **Gợi ý 3:** Thiết kế state machine/reconciliation thay vì cố tạo distributed transaction với external SaaS.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius và business impact.
2. Giảm side effect ngay lập tức.
3. Bảo toàn evidence.
4. Lập nhiều hypotheses.
5. Trace theo business operation ID.
6. Xây idempotency + state transitions.
7. Thiết kế retry/reconciliation.
8. Test failure windows và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định queue/background job là exactly-once.
- Retry phải đi cùng idempotency.
- Phân biệt duplicate enqueue, retry và concurrent execution.
- Không đánh dấu completed nếu chưa có bằng chứng phù hợp về external state.
- Có reconciliation cho trạng thái “unknown”.

### Điểm cộng

- Unique business operation key/DB constraint.
- Atomic claim/optimistic concurrency cho state transition.
- Per-step status cho workflow nhiều side effects.
- Backoff/jitter và phân loại transient/permanent errors.

### Nâng cao

- Inbox/outbox khi có message boundary.
- Compensating/reconciliation action thay vì rollback giả tạo.
- Audit trail không chứa secret/token/PII quá mức cần thiết.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định phạm vi: số employee bị ảnh hưởng, operation nào nguy hiểm khi lặp, tenant nào bị ảnh hưởng và liệu cần tạm dừng worker/job cụ thể. Mitigation có thể là pause enqueue mới hoặc chặn execution theo business operation key, nhưng tránh xóa evidence.

Tôi thu thập Hangfire job IDs, retry history, timestamps, worker instance, business key, DB state transitions và external request correlation nếu có. Các hypothesis gồm duplicate enqueue từ application, automatic retry sau exception, worker crash sau external success nhưng trước DB commit, timeout tạo trạng thái không xác định, hoặc race giữa nhiều worker.

Long-term, mỗi offboarding operation có stable business ID và state machine như Pending → InProgress → ExternalApplied/NeedsReconciliation → Completed/Failed. Việc claim operation cần concurrency protection. Mỗi side effect nên được thiết kế idempotent khi có thể; trước khi retry operation có trạng thái không chắc chắn, đọc trạng thái hiện tại từ external system nếu API cho phép. DB unique constraint ngăn tạo trùng logical operation. Retry chỉ dành cho lỗi transient và có giới hạn/backoff.

Không cố dùng distributed transaction giữa SQL và Exchange. Thay vào đó lưu durable intent/progress và có reconciliation job. Nếu có message broker, transactional outbox có thể đảm bảo DB change và message intent được commit cùng nhau, nhưng consumer vẫn cần idempotency.

Test quan trọng nhất là fault injection tại từng boundary: external call thành công rồi process chết trước DB update; timeout sau server acceptance; hai worker claim cùng operation; retry nhiều lần. Monitoring theo operation ID, retry count, duplicate suppression, reconciliation backlog, external latency/error và age của state chưa hoàn tất.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là bài toán at-least-once và partial failure, không phải chỉ là ‘Hangfire chạy duplicate’. Trước tiên tôi đo blast radius và nếu side effect nguy hiểm thì tạm hạn chế execution mới. Tôi giữ nguyên evidence và correlate Hangfire job, employee/business operation, worker, DB transition và external call.

Tôi sẽ kiểm tra ít nhất bốn hướng: enqueue trùng, automatic retry, concurrent workers, và crash/timeout tại khoảng giữa external success với DB commit. Timeout đặc biệt nguy hiểm vì client không biết operation đã được áp dụng hay chưa.

Fix dài hạn của tôi là business-level idempotency: một stable operation key có unique constraint, state machine durable và atomic claim. External steps được retry chỉ khi an toàn; trạng thái unknown phải reconcile bằng cách đọc external state nếu có thể. Tôi không cố distributed transaction với Exchange. Nếu có message boundary tôi cân nhắc outbox, nhưng consumer vẫn idempotent. Tôi test bằng fault injection ở từng failure window và monitor retry, duplicate suppression, reconciliation backlog và operation age.”

## Câu hỏi đào sâu

1. Distributed lock có đủ để đảm bảo không bao giờ có duplicate side effect không?
2. Nếu external API không hỗ trợ idempotency key và cũng không có endpoint đọc trạng thái đáng tin cậy, bạn xử lý thế nào?
3. Khi nào bạn chọn outbox thay vì enqueue Hangfire trực tiếp sau `SaveChanges`?

## Lỗi trả lời thường gặp

- Chỉ thêm distributed lock rồi coi bài toán đã xong.
- Tắt toàn bộ retry mà không thiết kế failure recovery.
- Giả định timeout nghĩa là external request chưa thực thi.
- Không có business operation ID xuyên suốt logs.
- Cố rollback external SaaS bằng SQL transaction.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0

# Câu 3 — Thiết kế AI code-review agent có quyền đọc repository và đề xuất patch

**Loại câu hỏi:** AI engineering / system decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, deterministic validation, evaluation, security, auditability

## Bối cảnh

Team muốn xây một AI code-review agent cho repository .NET. Agent nhận PR diff, đọc thêm file liên quan, chạy build/test và tạo review findings hoặc patch đề xuất. Mục tiêu là bắt lỗi correctness/security/performance mà static analyzers bỏ sót, nhưng không được tự merge. Repository có source code, CI config và đôi khi có test fixtures chứa dữ liệu nhạy cảm. Agent có thể dùng LLM và tool interface/MCP-like integrations. Team lo prompt injection từ code/comment, chi phí context lớn, hallucinated findings và tool permission quá rộng.

## Câu hỏi chính

Bạn sẽ thiết kế agent này như thế nào để chứng minh AI thực sự cần thiết, giữ phần nào deterministic, kiểm soát context/tools/permissions, validate findings, đo chất lượng, xử lý hallucination/fallback và tạo audit trail đủ cho production?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ review internal repositories hay cả fork/untrusted PR?
- Patch có được push branch hay chỉ trả diff cho human?
- Ngôn ngữ/framework ngoài .NET có nằm trong scope không?
- Budget latency/token và false-positive tolerance là bao nhiêu?
- Dữ liệu nào tuyệt đối không được gửi tới model provider?

## Gợi ý tư duy

- **Gợi ý 1:** AI nên xử lý phần cần semantic reasoning; policy, permission và validation không nên giao hoàn toàn cho model.
- **Gợi ý 2:** Xem repository content là untrusted input, kể cả comments/instructions trong code.
- **Gợi ý 3:** Tách planner/reviewer khỏi execution gateway; dùng schema, allowlist, sandbox và evaluation dataset.

## Cấu trúc trả lời đề xuất

1. Làm rõ mục tiêu và threat model.
2. Xác định baseline không-AI.
3. Phân chia deterministic vs probabilistic responsibilities.
4. Thiết kế context retrieval.
5. Thiết kế tool gateway/permissions.
6. Validate output và patch.
7. Evaluation + rollout.
8. Audit, monitoring, fallback và cost control.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Có lý do dùng LLM ngoài static analysis.
- Code/PR text được coi là untrusted data, không phải instruction authority.
- Least privilege: read-only mặc định; build/test sandbox; không cấp secret tùy tiện.
- Structured findings được validate bằng schema và evidence location.
- Patch phải qua build/test/static checks và human approval trước merge.
- Có offline eval và production metrics.

### Điểm cộng

- Context theo diff + dependency/relevance retrieval thay vì dump toàn repo.
- Separate trusted policy/system instructions khỏi repository content.
- Tool-call authorization nằm ngoài model.
- Deduplicate findings với analyzers và suppressions có audit.

### Nâng cao

- Adversarial evaluation cho indirect prompt injection.
- Canary rollout, shadow mode, confidence/calibration analysis.
- Cost attribution theo PR/repository và cache deterministic artifacts an toàn.

## Hướng giải quyết tham khảo

Trước tiên tôi benchmark baseline gồm compiler warnings, analyzers, tests, SAST và human review. AI chỉ đáng dùng cho semantic cross-file reasoning, business invariant, suspicious interactions hoặc giải thích trade-off mà deterministic tooling khó bao phủ.

Pipeline có thể gồm: ingest PR metadata/diff → deterministic preprocessing → relevance retrieval → model review → structured findings → deterministic validation → optional patch generation trong sandbox → build/test/analyzers → human review. Repository text, comments và tool output đều là untrusted context; chúng không được quyền thay đổi system policy hay cấp thêm capability.

Agent không trực tiếp sở hữu broad GitHub/cloud credentials. Tool gateway enforce allowlist, repository scope, read/write policy, argument validation, timeout và audit. Review phase read-only. Nếu patch generation được phép, agent chỉ tạo ephemeral diff/worktree; push/write là capability riêng và trong yêu cầu hiện tại có thể không cần cấp.

Mỗi finding cần schema như category, severity, file/range, claim, evidence và suggested verification. Validator kiểm tra path/range tồn tại, patch apply được, build/tests chạy, và security rules deterministic. “Hallucination detection” không chỉ dựa vào model tự chấm confidence; cần evidence grounding, tool verification và human rejection signal.

Evaluation dùng bộ PR đã gán nhãn gồm real bugs, clean changes và adversarial samples. Theo dõi precision/recall trên tập phù hợp, false-positive rate, acceptance rate, escaped issues, latency và cost/PR. Rollout shadow/canary trước khi blocking bất kỳ workflow nào. Fallback là deterministic CI + human review; model failure không được chặn merge trừ khi policy đã định nghĩa rõ fail-closed cho một check deterministic.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng việc cho LLM toàn quyền đọc repo rồi gọi tools. Trước hết tôi đo baseline của compiler, analyzers, tests và SAST để xác định AI mang thêm giá trị ở semantic reasoning nào. Tôi coi mọi nội dung trong PR là untrusted data vì comment hoặc fixture có thể chứa instruction injection.

Kiến trúc tôi chọn là deterministic preprocessing và retrieval, sau đó LLM tạo structured findings có file/range/evidence. Tool access đi qua gateway enforce permission; review mặc định read-only, build/test chạy trong sandbox không có production secrets. Nếu model đề xuất patch thì patch phải apply, compile, qua tests/analyzers và human approval; model không tự merge.

Context chỉ gồm diff và các file liên quan được retrieval theo rule/dependency thay vì dump toàn repo. Tôi đánh giá bằng dataset PR có nhãn, gồm clean PR và adversarial injection cases, theo dõi precision, false-positive rate, acceptance, latency và cost. Fallback luôn là deterministic CI và human review. Audit log lưu model/version, policy version, context references, tool calls và validation result nhưng tránh lưu secret không cần thiết.”

## Câu hỏi đào sâu

1. Nếu agent cần chạy test nhưng test script trong PR độc hại, sandbox của bạn phải bảo vệ những gì?
2. Một reviewer đề xuất cho model quyền push branch để tiết kiệm thời gian. Bạn đồng ý trong điều kiện nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution: xây query không đồng nghĩa đã chạy query; phải đo actual database commands.
- Read performance của EF Core cần tách query shape/round-trips khỏi Change Tracker overhead.
- Background processing phải được thiết kế với partial failure, retry và business-level idempotency; không giả định exactly-once.
- External side effects cần durable state và reconciliation thay vì giả lập distributed transaction.
- AI agent production cần tách probabilistic reasoning khỏi deterministic policy, authorization, validation và CI gates.
- Untrusted code/context có thể là nguồn indirect prompt injection; least privilege và sandbox là phần của architecture.

## Mẫu tư duy cần nhớ

- Clarify requirement trước khi tối ưu hoặc thiết kế.
- Measure actual execution thay vì suy luận từ abstraction.
- Stabilize incident trước, sau đó bảo toàn evidence và điều tra nhiều hypothesis.
- Thiết kế retry cùng idempotency và reconciliation.
- Để AI suy luận, nhưng để deterministic systems enforce permissions và validate kết quả.
