# Code Review Challenge 1 — Cache-aside dưới tải cao: stale data, cache stampede và lost update

**Chủ đề:** Caching, concurrency, EF Core, correctness, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một ASP.NET Core API trả về hồ sơ nhân viên. Redis được dùng để giảm tải PostgreSQL. Endpoint đọc khoảng 800–1.500 request/giây vào giờ cao điểm; cập nhật ít hơn nhiều. Sau deployment, team thấy DB CPU tăng đột biến khi cache hết hạn, đôi lúc client đọc dữ liệu cũ ngay sau update, và thỉnh thoảng hai update gần đồng thời làm mất thay đổi của nhau.

## Đoạn code cần review

```csharp
public sealed class EmployeeService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;

    public EmployeeService(AppDbContext db, IDistributedCache cache)
    {
        _db = db;
        _cache = cache;
    }

    public async Task<EmployeeDto?> GetAsync(int id)
    {
        var key = $"employee:{id}";
        var cached = await _cache.GetStringAsync(key);
        if (cached != null)
            return JsonSerializer.Deserialize<EmployeeDto>(cached);

        var employee = await _db.Employees
            .FirstOrDefaultAsync(x => x.Id == id);

        if (employee == null)
            return null;

        var dto = new EmployeeDto(employee.Id, employee.Name, employee.Email);

        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            });

        return dto;
    }

    public async Task<bool> UpdateEmailAsync(int id, string email)
    {
        var employee = await _db.Employees.FirstOrDefaultAsync(x => x.Id == id);
        if (employee == null)
            return false;

        employee.Email = email;
        await _db.SaveChangesAsync();

        await _cache.RemoveAsync($"employee:{id}");
        return true;
    }
}
```

## Kết quả code review tham khảo

### 1. Lost update khi hai writer cập nhật cùng record

- **Problem:** read-modify-write không có concurrency control.
- **Why:** writer sau có thể SaveChanges dựa trên state đã cũ.
- **Impact:** mất thay đổi hợp lệ mà không báo lỗi.
- **Severity:** Critical.
- **Fix:** dùng optimistic concurrency token phù hợp DB/model, xử lý `DbUpdateConcurrencyException`, hoặc atomic conditional update khi phù hợp.

### 2. DB commit thành công nhưng cache invalidation thất bại

- **Problem:** DB và Redis không cùng transaction.
- **Why:** process crash/network failure sau commit nhưng trước `RemoveAsync`.
- **Impact:** cache cũ có thể sống tới TTL.
- **Severity:** High.
- **Fix:** coi invalidation là operation có thể thất bại; retry có kiểm soát, TTL hợp lý, observability; với yêu cầu consistency cao hơn cân nhắc transactional outbox/event-driven invalidation.

### 3. Cache stampede

- **Problem:** mọi cache miss đều query DB.
- **Why:** không có request coalescing/single-flight/distributed coordination.
- **Impact:** DB spike đúng lúc key nóng hết hạn.
- **Severity:** High.
- **Fix:** per-key request coalescing trong instance; nếu nhiều instance và key cực nóng cân nhắc distributed locking cẩn thận hoặc refresh-ahead/stale-while-revalidate.

### 4. Race giữa read-populate và update-invalidate

- **Problem:** reader có thể đọc DB cũ, writer commit+invalidate, sau đó reader ghi giá trị cũ trở lại cache.
- **Impact:** stale cache dù invalidation đã chạy.
- **Severity:** High.
- **Fix:** versioned cache/value, generation token, hoặc chiến lược write-through/refresh phù hợp consistency requirement.

### 5. Không truyền CancellationToken

- **Impact:** request đã disconnect vẫn tiếp tục dùng DB/Redis resource.
- **Severity:** Medium.
- **Fix:** nhận và propagate token tới EF Core và cache APIs hỗ trợ token.

### 6. Query read-only vẫn tracking entity

- **Impact:** allocation/change-tracker overhead không cần thiết.
- **Severity:** Medium.
- **Fix:** project trực tiếp DTO + `AsNoTracking()` khi phù hợp.

### 7. TTL đồng nhất

- **Impact:** nhiều key tạo cùng lúc có thể hết hạn cùng lúc và gây synchronized miss.
- **Severity:** Medium.
- **Fix:** thêm TTL jitter hoặc refresh-ahead.

### 8. Thiếu failure policy và telemetry cho Redis

- **Impact:** khó phân biệt Redis outage, DB overload và application latency.
- **Severity:** Medium.
- **Fix:** đo cache hit/miss, Redis latency/error, DB query latency, stampede/coalesced waits; không retry vô hạn.

## Phiên bản code đề xuất

```csharp
public sealed class EmployeeService
{
    private readonly AppDbContext _db;
    private readonly IDistributedCache _cache;
    private readonly KeyedLocker<int> _locker;

    public EmployeeService(
        AppDbContext db,
        IDistributedCache cache,
        KeyedLocker<int> locker)
    {
        _db = db;
        _cache = cache;
        _locker = locker;
    }

    public async Task<EmployeeDto?> GetAsync(int id, CancellationToken ct)
    {
        var key = $"employee:{id}";
        var cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<EmployeeDto>(cached);

        await using var lease = await _locker.AcquireAsync(id, ct);

        cached = await _cache.GetStringAsync(key, ct);
        if (cached is not null)
            return JsonSerializer.Deserialize<EmployeeDto>(cached);

        var dto = await _db.Employees
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new EmployeeDto(x.Id, x.Name, x.Email))
            .SingleOrDefaultAsync(ct);

        if (dto is null) return null;

        var ttl = TimeSpan.FromMinutes(8) +
                  TimeSpan.FromSeconds(Random.Shared.Next(0, 120));

        await _cache.SetStringAsync(
            key,
            JsonSerializer.Serialize(dto),
            new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = ttl
            }, ct);

        return dto;
    }

    public async Task<bool> UpdateEmailAsync(
        int id,
        string email,
        CancellationToken ct)
    {
        var employee = await _db.Employees.SingleOrDefaultAsync(x => x.Id == id, ct);
        if (employee is null) return false;

        employee.Email = email;

        try
        {
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateConcurrencyException)
        {
            throw new ConflictException("Employee was modified concurrently.");
        }

        await _cache.RemoveAsync($"employee:{id}", ct);
        return true;
    }
}
```

`KeyedLocker<T>` ở đây là abstraction minh họa cho single-flight trong một process; nó không tự giải quyết coordination giữa nhiều application instances. Concurrency token trên entity/schema cũng được giả định đã cấu hình.

## Trade-offs

Single-flight giảm DB burst nhưng tạo điểm chờ cho key nóng. Distributed lock có thể mở rộng coordination nhưng thêm latency và failure modes. Outbox tăng reliability của invalidation nhưng tăng độ phức tạp và thường chỉ đáng dùng khi stale-data window thực sự quan trọng. Cache-aside vẫn phù hợp nếu business chấp nhận eventual consistency ngắn.

## Cách kiểm thử

1. 500 concurrent GET cùng miss một key: xác nhận số DB query được coalesce đáng kể.
2. Hai concurrent update cùng version: một update phải conflict thay vì silently overwrite.
3. Inject Redis failure ngay sau DB commit: xác nhận metric/error/retry policy và giới hạn stale-data đã thiết kế.
4. Race reader-populate với writer-invalidate: kiểm tra chiến lược versioning nếu consistency requirement yêu cầu.
5. Cancel request trong lúc chờ DB/Redis: xác nhận operation dừng và không giữ resource bất thường.

## Quan sát trong production

Theo dõi cache hit ratio theo key group, Redis p95/p99 latency/error, DB query count/latency, concurrent single-flight waiters, optimistic-concurrency conflicts, stale-cache incidents và correlation trace từ HTTP → Redis → EF Core. Alert khi cache hit giảm mạnh đồng thời DB load tăng.

## Câu hỏi phỏng vấn mở rộng

1. Single-flight trong memory còn hiệu quả thế nào khi chạy 20 replicas?
2. Khi nào bạn chấp nhận stale-while-revalidate thay vì strong consistency?
3. Nếu invalidation event có thể duplicate hoặc out-of-order, consumer nên thiết kế thế nào?

# Code Review Challenge 2 — Authorization bị đặt nhầm chỗ và lộ dữ liệu nhạy cảm

**Chủ đề:** Authentication/authorization, IDOR/BOLA, sensitive-data exposure, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một internal ASP.NET Core API cho phép nhân viên xem offboarding mail configuration. Admin có thể xem mọi employee; user thường chỉ được xem record của chính mình. Security review phát hiện một số user có thể thử ID khác và nhận dữ liệu chứa forwarding address. Log aggregator cũng chứa token/PII nhiều hơn dự kiến.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/mail-config")]
public sealed class MailConfigController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<MailConfigController> _logger;

    public MailConfigController(AppDbContext db, ILogger<MailConfigController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{employeeId:int}")]
    [Authorize]
    public async Task<IActionResult> Get(int employeeId)
    {
        _logger.LogInformation(
            "Request {EmployeeId}, auth={Authorization}",
            employeeId,
            Request.Headers.Authorization.ToString());

        var config = await _db.EmployeeOffboardingMailConfigs
            .Include(x => x.Employee)
            .FirstOrDefaultAsync(x => x.EmployeeId == employeeId);

        if (config == null)
            return NotFound();

        return Ok(new
        {
            config.EmployeeId,
            config.TargetEmail,
            config.AutoReplyMessage,
            config.Employee.DisplayName,
            config.Employee.PersonalEmail,
            config.LastError
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object-level authorization / IDOR

- **Problem:** authenticated user có thể cung cấp bất kỳ `employeeId` nào.
- **Why:** code không kiểm tra ownership hoặc admin permission.
- **Impact:** đọc dữ liệu employee khác.
- **Severity:** Critical.
- **Fix:** enforce resource-based/policy authorization hoặc derive employee identity từ trusted claim cho self-service; admin path phải có explicit permission.

### 2. Ghi Authorization header vào log

- **Problem:** bearer credential có thể bị lưu trong log.
- **Impact:** credential exposure và lateral access nếu log bị truy cập trái phép.
- **Severity:** Critical.
- **Fix:** tuyệt đối không log raw Authorization header/token; log correlation ID, subject identifier đã phù hợp chính sách và authorization outcome.

### 3. Overexposure của response

- **Problem:** trả `PersonalEmail`, `LastError`, `AutoReplyMessage` dù use case chưa chứng minh cần chúng.
- **Impact:** PII/internal diagnostic leakage.
- **Severity:** High.
- **Fix:** explicit DTO theo use case và least-data principle.

### 4. Authorization diễn ra sau khi developer đã tin input resource ID

- **Impact:** dễ tái diễn BOLA ở endpoint khác.
- **Severity:** High.
- **Fix:** policy/resource authorization rõ ràng, centralize reusable rules, integration-test authorization matrix.

### 5. Load toàn entity graph trước khi projection

- **Impact:** lấy dữ liệu nhiều hơn cần thiết vào memory và tăng nguy cơ accidental exposure.
- **Severity:** Medium.
- **Fix:** authorize scope trước, sau đó project đúng fields bằng `Select` + `AsNoTracking`.

### 6. Không propagate cancellation

- **Impact:** wasted DB work khi request bị hủy.
- **Severity:** Low/Medium.
- **Fix:** nhận `CancellationToken` và truyền vào EF Core.

### 7. Thiếu security telemetry

- **Impact:** khó phát hiện enumeration/forbidden-access pattern.
- **Severity:** Medium.
- **Fix:** structured security event không chứa secret, metric 403/denied-resource attempts, rate/anomaly monitoring phù hợp.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/mail-config")]
[Authorize]
public sealed class MailConfigController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IAuthorizationService _authorization;
    private readonly ILogger<MailConfigController> _logger;

    public MailConfigController(
        AppDbContext db,
        IAuthorizationService authorization,
        ILogger<MailConfigController> logger)
    {
        _db = db;
        _authorization = authorization;
        _logger = logger;
    }

    [HttpGet("{employeeId:int}")]
    public async Task<IActionResult> Get(int employeeId, CancellationToken ct)
    {
        var resource = new EmployeeMailConfigResource(employeeId);
        var auth = await _authorization.AuthorizeAsync(
            User, resource, "ReadEmployeeMailConfig");

        if (!auth.Succeeded)
        {
            _logger.LogWarning(
                "Mail config access denied for employee {EmployeeId}",
                employeeId);
            return Forbid();
        }

        var dto = await _db.EmployeeOffboardingMailConfigs
            .AsNoTracking()
            .Where(x => x.EmployeeId == employeeId)
            .Select(x => new MailConfigDto(
                x.EmployeeId,
                x.TargetEmail,
                x.AutoReplyMessage))
            .SingleOrDefaultAsync(ct);

        return dto is null ? NotFound() : Ok(dto);
    }
}
```

Policy `ReadEmployeeMailConfig` được giả định kiểm tra explicit admin permission hoặc mapping đáng tin cậy giữa authenticated subject và employee resource. Nếu API chỉ phục vụ self-service, thiết kế tốt hơn có thể là `/api/me/mail-config`, tránh nhận `employeeId` từ caller.

## Trade-offs

Resource-based authorization rõ ràng và tái sử dụng tốt nhưng cần policy/handler/test matrix. `/me` đơn giản và giảm attack surface cho self-service, nhưng admin use case cần endpoint/policy riêng. Trả 403 hay 404 cho unauthorized resource phụ thuộc threat model và API semantics; tránh dựa vào status code như biện pháp bảo mật duy nhất.

## Cách kiểm thử

1. User A request employee A → success; User A request employee B → denied.
2. Admin có đúng permission → access allowed; authenticated user không có permission → denied.
3. Verify response JSON không chứa `PersonalEmail`, `LastError` hoặc field ngoài contract.
4. Capture test logs và xác nhận bearer token/secret không xuất hiện.
5. Enumeration test nhiều employee IDs: authorization luôn được enforce và telemetry phát hiện pattern bất thường.

## Quan sát trong production

Theo dõi 401/403 rates, denied access theo endpoint/subject đã pseudonymize phù hợp, unusual resource enumeration, authorization-handler latency và audit event cho privileged admin access. Không ghi token, raw credentials hoặc PII không cần thiết vào logs/traces.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào resource-based authorization tốt hơn role check trực tiếp trong controller?
2. Bạn chọn 403 hay 404 cho unauthorized resource như thế nào?
3. Nếu employee identity nằm trong DB thay vì token claim, bạn thiết kế mapping/cache ra sao để không tạo authorization bypass?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cache-aside không chỉ là `GET → DB → SET`: dưới tải cao phải nghĩ tới stampede, race giữa populate/invalidate, concurrency control và failure window giữa DB/Redis. Với security, authentication chỉ xác định caller; authorization phải quyết định caller có quyền trên resource cụ thể hay không. DTO projection, least-data exposure và secret-safe logging là một phần của security boundary.

## Mẫu tư duy cần nhớ

- Tìm race bằng cách liệt kê các interleaving giữa concurrent operations.
- Thiết kế retry cùng idempotency/concurrency semantics, không thêm retry một cách độc lập.
- Xem cache là bản sao có thể stale; xác định consistency requirement trước khi chọn strategy.
- Authentication ≠ authorization; luôn kiểm tra quyền trên resource/action.
- Observability phải giúp điều tra sự cố mà không biến logs thành kho secret/PII.
