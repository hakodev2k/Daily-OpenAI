# Code Review Challenge 1 — Cosmos DB chạy ổn ở test nhưng RU và latency tăng vọt với tenant lớn

**Chủ đề:** C#/.NET, ASP.NET Core, Cosmos DB, partition key, query patterns, RU consumption, pagination, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một enterprise activity platform lưu audit/activity events vào Azure Cosmos DB. API được viết bằng ASP.NET Core và chạy nhiều instance trên Azure App Service.

Container `activities` hiện có partition key path là `/tenantId`.

Dữ liệu thực tế:

- phần lớn tenant có 5.000–50.000 activity records;
- một số tenant enterprise có hàng chục triệu records;
- activity được append liên tục;
- màn hình quản trị thường xem activity của **một tenant cụ thể** theo thời gian mới nhất trước;
- support đôi khi cần tìm theo `userId` trên nhiều tenant, nhưng đây là flow hiếm;
- API list mặc định trả 100 records;
- production gần đây ghi nhận:
  - p95 latency của endpoint list tăng mạnh ở tenant lớn;
  - Cosmos DB RU consumption tăng đột biến khi support search theo `userId`;
  - có request trả hàng chục MB dữ liệu dù client chỉ hiển thị trang đầu;
  - một tenant lớn tạo phần lớn write traffic trong giờ cao điểm;
  - telemetry cho thấy nhiều query có `RequestCharge` cao nhưng log không chứa partition key hoặc continuation token;
  - team đề xuất “tăng RU thật cao” để xử lý dứt điểm.

Developer hiện tại viết service như sau:

## Đoạn code cần review

```csharp
public sealed class ActivityService
{
    private readonly Container _container;
    private readonly ILogger<ActivityService> _logger;

    public ActivityService(
        CosmosClient cosmosClient,
        IConfiguration configuration,
        ILogger<ActivityService> logger)
    {
        var database = configuration["Cosmos:Database"]!;
        var container = configuration["Cosmos:ActivitiesContainer"]!;

        _container = cosmosClient.GetContainer(database, container);
        _logger = logger;
    }

    public async Task AddAsync(
        ActivityRecord activity,
        CancellationToken cancellationToken)
    {
        await _container.CreateItemAsync(
            activity,
            new PartitionKey(activity.TenantId),
            cancellationToken: cancellationToken);
    }

    public async Task<IReadOnlyList<ActivityRecord>> GetRecentAsync(
        string tenantId,
        DateTime fromUtc,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.tenantId = @tenantId " +
            "AND c.createdUtc >= @fromUtc " +
            "ORDER BY c.createdUtc DESC")
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@fromUtc", fromUtc);

        var iterator = _container.GetItemQueryIterator<ActivityRecord>(query);
        var result = new List<ActivityRecord>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            result.AddRange(page);
        }

        _logger.LogInformation(
            "Loaded {Count} activities since {FromUtc}",
            result.Count,
            fromUtc);

        return result;
    }

    public async Task<IReadOnlyList<ActivityRecord>> SearchByUserAsync(
        string userId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.userId = @userId ORDER BY c.createdUtc DESC")
            .WithParameter("@userId", userId);

        var iterator = _container.GetItemQueryIterator<ActivityRecord>(query);
        var result = new List<ActivityRecord>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            result.AddRange(page);
        }

        return result;
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review implementation này như một Senior .NET Developer chịu trách nhiệm cả API design và Cosmos DB cost/performance.

Bạn cần:

1. xác định correctness/performance/reliability concerns;
2. phân tích query nào có thể được route tới một logical partition và query nào có thể fan-out;
3. đánh giá việc load toàn bộ result set vào memory;
4. đánh giá pagination và continuation token;
5. đánh giá partition key `/tenantId` với tenant có dữ liệu/traffic rất lớn;
6. phân tích vì sao “tăng RU” chưa chắc giải quyết được data model/query problem;
7. chỉ ra telemetry còn thiếu để chứng minh bottleneck;
8. đề xuất API/query implementation tốt hơn;
9. giải thích khi nào nên giữ `/tenantId` và khi nào cần xem xét partitioning strategy khác;
10. giải thích testing và production monitoring.

## Câu hỏi gợi mở

1. `WHERE c.tenantId = @tenantId` có tự động đồng nghĩa SDK luôn route query tối ưu nếu code không truyền `QueryRequestOptions.PartitionKey` không?
2. Nếu tenant có 20 triệu records và API đọc tất cả records của 90 ngày rồi mới trả response, chuyện gì xảy ra với RU, memory và latency?
3. Query `WHERE c.userId = @userId` sẽ được thực thi thế nào khi partition key của container là `/tenantId` và request không biết tenant?
4. Một tenant tạo phần lớn write traffic có thể ảnh hưởng gì tới lựa chọn partition key?
5. Bạn cần log/metric gì để phân biệt “Cosmos chậm” với “query pattern đắt”?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **query shape + partition routing + unbounded result materialization**, không chỉ ở số RU được provision.

### Gợi ý 2

Hãy nghĩ theo hướng **bounded page size + continuation token + explicit partition key khi đã biết + projection + measured RequestCharge + data model phù hợp với dominant access patterns**.

## Kết quả code review tham khảo

### High — Endpoint materialize toàn bộ result set trước khi trả response

**Vấn đề:**  
`GetRecentAsync` đọc tất cả pages cho tới khi `HasMoreResults == false`, cộng toàn bộ item vào `List<ActivityRecord>` rồi mới trả về controller.

**Tại sao xảy ra:**  
Code đang coi pagination nội bộ của Cosmos SDK như implementation detail thay vì expose pagination semantics cho API consumer.

**Ảnh hưởng production:**  
Với tenant lớn, một request có thể đọc hàng nghìn hoặc hàng triệu items, tiêu thụ RU lớn, tăng latency, allocation và process memory. Client chỉ cần trang đầu nhưng backend vẫn trả toàn bộ lịch sử phù hợp filter.

**Cách sửa:**  
Thiết kế API phân trang. Đọc một bounded page mỗi request, trả `continuationToken` opaque cho client và chỉ đọc tiếp khi client yêu cầu. Đặt page-size limit ở server.

---

### High — Query theo tenant không truyền explicit partition key vào request options

**Vấn đề:**  
Code biết chính xác `tenantId`, nhưng `GetItemQueryIterator` không truyền `QueryRequestOptions.PartitionKey`.

**Tại sao xảy ra:**  
Query text có predicate trên partition key nhưng application không biểu đạt routing intent một cách explicit ở SDK call.

**Ảnh hưởng production:**  
Application mất một cơ hội quan trọng để đảm bảo query được scoped rõ ràng tới partition đã biết và để code review/telemetry thể hiện đúng access pattern. Tùy query/SDK/service behavior, việc chỉ dựa vào query text làm intent kém rõ và khó kiểm soát hơn.

**Cách sửa:**  
Khi tenant đã biết, truyền `QueryRequestOptions { PartitionKey = new PartitionKey(tenantId), MaxItemCount = ... }`. Đồng thời vẫn giữ predicate nếu cần correctness/readability.

---

### High — Cross-partition search theo `userId` là access pattern đắt

**Vấn đề:**  
`SearchByUserAsync` chỉ filter theo `userId`, trong khi container partition theo `/tenantId`.

**Tại sao xảy ra:**  
Không có partition key value để route tới một logical partition cụ thể.

**Ảnh hưởng production:**  
Query có thể phải fan-out qua nhiều physical/logical partition liên quan, làm RU và latency tăng theo quy mô dữ liệu. Support flow hiếm có thể tạo load lớn ngoài dự đoán.

**Cách sửa:**  
Trước tiên xác minh requirement: nếu support thường có thể chọn tenant trước, bắt buộc `tenantId + userId`. Nếu cross-tenant search thật sự cần thiết nhưng hiếm, có thể tách thành operational/search workflow riêng, maintain read model/index khác phù hợp, hoặc chấp nhận cost với guardrails. Không nên phá dominant tenant-scoped model chỉ để tối ưu một query hiếm mà chưa đo.

---

### High — `/tenantId` có nguy cơ tạo hot logical partition cho tenant rất lớn

**Vấn đề:**  
Mọi activity của một tenant dùng cùng partition-key value.

**Tại sao xảy ra:**  
Partition key được chọn đúng theo tenant boundary nhưng workload thực tế có tenant cực lớn và write-heavy.

**Ảnh hưởng production:**  
Một tenant có thể tạo concentration về data và throughput trên một logical partition. Tăng throughput tổng của container không tự động biến một logical partition cực nóng thành workload phân tán đều.

**Cách sửa:**  
Đo distribution trước khi redesign. Nếu tenant-scoped partition vẫn phù hợp với size/throughput thực tế thì giữ lại vì query đơn giản và isolation tốt. Nếu tenant lớn vượt khả năng practical của một logical partition/workload pattern, cân nhắc hierarchical/synthetic partitioning phù hợp với access pattern, ví dụ tenant + time bucket hoặc tenant + shard, nhưng phải tính cost query fan-out và migration. Không đổi partition key chỉ vì một metric spike ngắn hạn.

---

### High — Default 90 ngày không có upper bound về số item

**Vấn đề:**  
Controller mặc định query 90 ngày bất kể activity volume.

**Tại sao xảy ra:**  
Time range được dùng như một surrogate cho pagination.

**Ảnh hưởng production:**  
90 ngày với tenant nhỏ có thể chỉ vài trăm rows, nhưng với tenant lớn có thể là hàng triệu events. API contract không bảo đảm response bounded.

**Cách sửa:**  
Dùng page size + continuation token làm primary pagination. Time range là filter, không phải giới hạn cardinality. Có thể enforce maximum time window cho một số endpoints nếu business phù hợp.

### Medium — `SELECT *` đọc nhiều dữ liệu hơn UI cần

**Vấn đề:**  
Query trả toàn bộ document dù list view có thể chỉ cần vài fields.

**Tại sao xảy ra:**  
Persistence model được trả trực tiếp như API/read model.

**Ảnh hưởng production:**

**Cách sửa:**

### Medium — Logging không ghi RequestCharge, partition key, page count hoặc continuation behavior

**Vấn đề:**  
Log chỉ ghi tổng count và `fromUtc`.

**Tại sao xảy ra:**  
Service bỏ qua diagnostics quan trọng từ `FeedResponse`.

**Ảnh hưởng production:**  
Khi latency/RU tăng, support không biết request nào đắt, tenant nào gây load, một request đọc bao nhiêu pages hay RU/page ra sao.

**Cách sửa:**  
Ghi structured telemetry cho endpoint/query name, tenant hash/ID theo policy, page size, item count, RequestCharge, duration, continuation-present flag và status. Không log raw continuation token nếu security/size policy không cho phép.

### Medium — Không có API-level guardrail cho page size và search scope

**Vấn đề:**  
Implementation hiện không có `pageSize` bounded và cross-tenant search có thể chạy không giới hạn.

**Tại sao xảy ra:**

**Ảnh hưởng production:**

**Cách sửa:**

## Phiên bản đề xuất

Ví dụ dưới đây giữ `/tenantId` vì dominant access pattern vẫn tenant-scoped, nhưng API chỉ đọc một page và đo RU.

```csharp
public sealed record ActivityListItem(
    string Id,
    string UserId,
    string Action,
    DateTime CreatedUtc);

public sealed record ActivityPage(
    IReadOnlyList<ActivityListItem> Items,
    string? ContinuationToken,
    double RequestCharge);

public async Task<ActivityPage> GetRecentPageAsync(
    string tenantId,
    DateTime fromUtc,
    int pageSize,
    string? continuationToken,
    CancellationToken cancellationToken)
{
    var safePageSize = Math.Clamp(pageSize, 1, 100);

    var query = new QueryDefinition(
        "SELECT c.id, c.userId, c.action, c.createdUtc " +
        "FROM c " +
        "WHERE c.tenantId = @tenantId " +
        "AND c.createdUtc >= @fromUtc " +
        "ORDER BY c.createdUtc DESC")
        .WithParameter("@tenantId", tenantId)
        .WithParameter("@fromUtc", fromUtc);

    var options = new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(tenantId),
        MaxItemCount = safePageSize
    };

    using var iterator = _container.GetItemQueryIterator<ActivityListItem>(
        query,
        continuationToken,
        options);

    if (!iterator.HasMoreResults)
    {
        return new ActivityPage(
            Array.Empty<ActivityListItem>(),
            null,
            0);
    }

    var started = Stopwatch.GetTimestamp();
    var response = await iterator.ReadNextAsync(cancellationToken);
    var elapsed = Stopwatch.GetElapsedTime(started);

    _logger.LogInformation(
        "Cosmos activity page. Tenant={TenantId} Count={Count} RU={RequestCharge} DurationMs={DurationMs} HasContinuation={HasContinuation}",
        tenantId,
        response.Count,
        response.RequestCharge,
        elapsed.TotalMilliseconds,
        !string.IsNullOrEmpty(response.ContinuationToken));

    return new ActivityPage(
        response.ToList(),
        response.ContinuationToken,
        response.RequestCharge);
}
```

Với `SearchByUserAsync`, design ưu tiên nên yêu cầu `tenantId` nếu operational workflow cho phép:

```csharp
public async Task<ActivityPage> SearchByUserAsync(
    string tenantId,
    string userId,
    int pageSize,
    string? continuationToken,
    CancellationToken cancellationToken)
{
    var query = new QueryDefinition(
        "SELECT c.id, c.userId, c.action, c.createdUtc " +
        "FROM c WHERE c.tenantId = @tenantId AND c.userId = @userId " +
        "ORDER BY c.createdUtc DESC")
        .WithParameter("@tenantId", tenantId)
        .WithParameter("@userId", userId);

    var options = new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(tenantId),
        MaxItemCount = Math.Clamp(pageSize, 1, 100)
    };

    using var iterator = _container.GetItemQueryIterator<ActivityListItem>(
        query,
        continuationToken,
        options);

    var response = await iterator.ReadNextAsync(cancellationToken);

    return new ActivityPage(
        response.ToList(),
        response.ContinuationToken,
        response.RequestCharge);
}
```

Nếu cross-tenant `userId` search là requirement thật sự và có tần suất/cost đáng kể, cần đánh giá read model/index chuyên biệt thay vì biến mọi tenant-scoped read thành cross-partition query.

## Giải thích thiết kế sau khi sửa

### 1. API pagination map trực tiếp vào database pagination

Mỗi request đọc một bounded page. Backend không đọc trước dữ liệu client chưa yêu cầu.

### 2. Partition routing được thể hiện explicit

Khi `tenantId` đã biết, request options mang đúng partition key. Điều này làm access pattern rõ cả trong code lẫn review.

### 3. Projection giảm payload

List endpoint chỉ đọc fields cần hiển thị. Document detail có thể được đọc riêng khi cần.

### 4. RU trở thành observable engineering signal

Không đánh giá Cosmos chỉ bằng latency. `RequestCharge`, page size, query scope và duration phải được đo cùng nhau.

### 5. Partition-key redesign là architecture decision, không phải reflex

`/tenantId` có ưu điểm lớn khi dominant queries đều theo tenant. Chỉ nên đổi khi data/traffic distribution thực tế chứng minh logical partition đó không còn phù hợp. Synthetic/hierarchical key có thể phân tán tenant lớn nhưng đổi lại query routing và operational complexity tăng.

## Trade-offs

- Continuation token làm API contract phức tạp hơn page-number pagination, nhưng phù hợp với continuation semantics và tránh offset scan pattern.
- Giữ `/tenantId` đơn giản cho đa số requests nhưng tenant cực lớn có thể cần strategy riêng.
- Synthetic partitioning phân tán write tốt hơn nhưng tenant-wide query có thể phải đọc nhiều buckets/shards.
- Read model riêng cho support search tăng storage/sync complexity; chỉ đáng làm nếu query cross-tenant thực sự quan trọng.
- Projection giảm payload nhưng tạo DTO/read model riêng cần maintain.

## Cách kiểm thử

1. **Integration test — pagination:** tenant có >500 records, page size 50; mỗi call trả tối đa 50 records và continuation token không skip/duplicate records trong sequence ổn định.
2. **Load test — large tenant:** mô phỏng tenant có volume lớn; đo RU/request, p95/p99, memory và response size trước/sau pagination.
3. **Query-scope test:** so sánh tenant-scoped query với cross-tenant `userId` query bằng RequestCharge/diagnostics để định lượng cost.
4. **Hot-tenant workload test:** tạo phần lớn writes trên một tenant và quan sát throughput/throttling distribution thay vì chỉ total container RU.
5. **Cancellation/failure test:** cancel request giữa page read; API dừng đúng và không cố materialize phần còn lại.

## Quan sát trong production

Theo dõi:

- RequestCharge theo endpoint/query name;
- RU/s và throttled requests;
- p50/p95/p99 latency;
- item count/page và response bytes;
- continuation-token usage rate;
- cross-partition support-query rate;
- request volume và RU theo tenant bucket;
- SDK dependency duration/diagnostics;
- App Service memory/allocation nếu response vẫn lớn;
- error/cancellation rate;
- trend của top tenants theo storage và throughput.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một tenant vượt xa tất cả tenant khác cả data size lẫn write rate, bạn sẽ đánh giá synthetic partition key nào và query tenant-wide sẽ thay đổi ra sao?
2. Khi nào bạn chọn một search/read model riêng cho cross-tenant support lookup thay vì query trực tiếp Cosmos DB?
3. Nếu Product yêu cầu page number kiểu `page=5000`, bạn sẽ giải thích trade-off và đề xuất API semantics nào?

# Code Review Challenge 2 — React search hiển thị kết quả cũ, tạo request storm và render HTML không tin cậy

**Chủ đề:** React.js, TypeScript, browser networking, async race conditions, request cancellation, XSS, API integration, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một admin portal dùng React + TypeScript để tìm customer theo tên/email.

Behavior mong muốn:

- user gõ từ khóa;
- sau một khoảng debounce ngắn, UI gọi `GET /api/customers/search?q=...`;
- request mới phải supersede request cũ;
- kết quả hiển thị tối đa 20 items;
- API trả object gồm `id`, `displayName`, `email`, `highlightedName`;
- `highlightedName` được backend tạo để highlight đoạn match;
- network có thể chậm hoặc request hoàn tất không theo thứ tự gửi;
- component được mở/đóng thường xuyên trong modal;
- production ghi nhận:
  - khi gõ nhanh “anna”, đôi lúc UI cuối cùng hiển thị kết quả cho “an”;
  - backend nhận nhiều request cho từng ký tự;
  - console thỉnh thoảng có warning về state update sau navigation/modal close;
  - một security review phát hiện backend `highlightedName` có thể chứa dữ liệu customer do user nhập;

## Kết quả code review tham khảo

### Critical — Render `highlightedName` bằng `dangerouslySetInnerHTML` tạo XSS boundary nguy hiểm

**Vấn đề:**  
Component render raw HTML nhận từ API.

**Tại sao xảy ra:**  
React escaping mặc định bị bypass khi dùng `dangerouslySetInnerHTML`. Backend field chứa dữ liệu có nguồn gốc từ user/customer input nên không thể mặc định xem là trusted HTML.

**Ảnh hưởng production:**  
Nếu attacker-controlled content đi vào `highlightedName` mà không được sanitize đúng theo context, script/HTML payload có thể chạy trong origin của admin portal, dẫn tới session/data compromise tùy security model.

**Cách sửa:**  
Ưu tiên không truyền HTML. Backend nên trả plain text + match ranges/tokens, rồi frontend render bằng React elements để React escape text mặc định. Nếu business bắt buộc HTML, phải dùng sanitizer được duy trì tốt với explicit allowlist và defense-in-depth CSP; nhưng tránh HTML là design đơn giản hơn.

---

### High — Stale response có thể ghi đè kết quả mới

**Vấn đề:**  
Mọi request khi hoàn tất đều gọi `setCustomers(data)`.

**Tại sao xảy ra:**  
Network responses không đảm bảo hoàn tất theo thứ tự request được gửi.

**Ảnh hưởng production:**  
User gõ `anna`; request `anna` có thể trả trước request `an`. Sau đó response `an` đến muộn và ghi đè state, khiến UI hiển thị kết quả không khớp input hiện tại.

**Cách sửa:**  
Abort request cũ bằng `AbortController` khi effect cleanup chạy. Có thể thêm sequence/request ID guard để stale response không được commit state ngay cả khi cancellation không ngăn được mọi timing edge case.

---

### High — Debounce timer cũ không được clear

**Vấn đề:**  
`setTimeout` được tạo cho mỗi query change nhưng effect không return cleanup để `clearTimeout`.

**Tại sao xảy ra:**  
Debounce được implement như delay chứ không phải cancellation-based debounce.

**Ảnh hưởng production:**  
Gõ `a` → `an` → `ann` → `anna` có thể tạo bốn request sau 300 ms thay vì chỉ request cuối. Backend load tăng và race condition trở nên thường xuyên hơn.

**Cách sửa:**  
Lưu timer handle trong effect scope và `clearTimeout` trong cleanup. Chỉ timer của query mới nhất được phép fire.

---

### High — Không abort in-flight fetch khi query đổi hoặc component unmount

**Vấn đề:**  
Request cũ tiếp tục chạy khi input thay đổi hoặc component biến mất.

**Tại sao xảy ra:**  
Không dùng `AbortController` và cleanup.

**Ảnh hưởng production:**  
Lãng phí browser/server work, tăng stale-response race, và có thể dẫn tới state updates không còn phù hợp với UI lifecycle.

**Cách sửa:**  
Tạo `AbortController` cho effect, truyền `signal` vào `fetch`, gọi `controller.abort()` trong cleanup. Ignore `AbortError` như expected cancellation.

---

### High — HTTP 4xx/5xx không tự động đi vào `catch`

**Vấn đề:**  
Code gọi `response.json()` mà không kiểm tra `response.ok`.

**Tại sao xảy ra:**  
`fetch` thường reject ở network-level failure/abort, không phải chỉ vì HTTP status là 500.

**Ảnh hưởng production:**  
UI có thể parse error payload như customer array hoặc throw ở chỗ khó hiểu. Error state không rõ và kết quả cũ có thể vẫn hiển thị.

**Cách sửa:**  
Kiểm tra `response.ok`, map error response rõ ràng, set UI error state và quyết định có clear stale results hay giữ chúng kèm warning theo UX requirement.

---

### Medium — Query string được nối trực tiếp không encode

**Vấn đề:**  
`/api/customers/search?q=${query}` dùng raw user input.

**Tại sao xảy ra:**  
Không dùng `URLSearchParams` hoặc encoding API.

**Ảnh hưởng production:**  
Query chứa `&`, `+`, `?`, Unicode hoặc ký tự đặc biệt có thể bị interpret sai và tạo request không đúng ý định.

**Cách sửa:**  
Dùng `URLSearchParams` hoặc `encodeURIComponent` phù hợp.

---

### Medium — Loading state có thể sai khi nhiều request overlap

**Vấn đề:**  
Mỗi request tự đặt `loading=true` và `finally` đặt `false`.

**Tại sao xảy ra:**  
Không có ownership của loading state theo request hiện hành.

**Ảnh hưởng production:**  
Request cũ có thể kết thúc và set `loading=false` trong khi request mới vẫn đang chạy.

**Cách sửa:**  
Sau khi cancel/serialize request bằng effect cleanup, chỉ request hiện hành được quyền cập nhật loading/error state; sequence guard giúp enforce điều này.

---

### Medium — Error handling chỉ `console.log` và giữ stale UI im lặng

**Vấn đề:**  
Không có user-facing error state hoặc telemetry có cấu trúc.

**Tại sao xảy ra:**  
Exception được coi như developer debugging concern.

**Ảnh hưởng production:**  
User nhìn thấy kết quả cũ và có thể tưởng đó là kết quả cho query mới. Support không biết tỷ lệ failure hay query nào gây lỗi.

**Cách sửa:**  
Có `error` state, render trạng thái phù hợp, và emit telemetry có request/correlation ID, duration, status, abort reason. Không log PII query text nguyên văn nếu policy không cho phép.

---

### Medium — Không có minimum query length/normalization policy

**Vấn đề:**  
Một ký tự cũng kích hoạt search.

**Tại sao xảy ra:**  
Frontend không thể hiện contract search threshold.

**Ảnh hưởng production:**  
Search rộng và tốn tài nguyên, đặc biệt với backend catalog/customer table lớn.

**Cách sửa:**  
Thống nhất với API contract, ví dụ trim input và chỉ search từ 2–3 ký tự nếu product requirement cho phép. Backend vẫn phải tự enforce guardrail; frontend không phải security/performance boundary duy nhất.

## Phiên bản đề xuất

Ví dụ sau tránh raw HTML bằng cách backend trả match ranges. Để tập trung vào lifecycle, ví dụ giả định API response là plain text customer data.

```tsx
import { useEffect, useRef, useState } from "react";

type Customer = {
  id: string;
  displayName: string;
  email: string;
};

type SearchState = {
  customers: Customer[];
  loading: boolean;
  error: string | null;
};

export function CustomerSearch() {
  const [query, setQuery] = useState("");
  const [state, setState] = useState<SearchState>({
    customers: [],
    loading: false,
    error: null,
  });

  const requestSequence = useRef(0);

  useEffect(() => {
    const normalized = query.trim();

    if (normalized.length < 2) {
      setState({
        customers: [],
        loading: false,
        error: null,
      });
      return;
    }

    const controller = new AbortController();
    const sequence = ++requestSequence.current;

    const timer = window.setTimeout(async () => {
      setState((current) => ({
        ...current,
        loading: true,
        error: null,
      }));

      try {
        const params = new URLSearchParams({ q: normalized });

        const response = await fetch(
          `/api/customers/search?${params.toString()}`,
          {
            signal: controller.signal,
            headers: {
              Accept: "application/json",
            },
          }
        );

        if (!response.ok) {
          throw new Error(`Search failed with HTTP ${response.status}`);
        }

        const data = (await response.json()) as Customer[];

        if (sequence !== requestSequence.current) {
          return;
        }

        setState({
          customers: data,
          loading: false,
          error: null,
        });
      } catch (error) {
        if (controller.signal.aborted) {
          return;
        }

        if (sequence !== requestSequence.current) {
          return;
        }

        setState({
          customers: [],
          loading: false,
          error: "Không thể tải kết quả tìm kiếm.",
        });
      }
    }, 300);

    return () => {
      window.clearTimeout(timer);
      controller.abort();
    };
  }, [query]);

  return (
    <section>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Search customers"
      />

      {state.loading && <span>Loading...</span>}
      {state.error && <p role="alert">{state.error}</p>}

      <ul>
        {state.customers.map((customer) => (
          <li key={customer.id}>
            <strong>{customer.displayName}</strong>
            <span>{customer.email}</span>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Nếu cần highlight match mà không dùng raw HTML, API có thể trả text + ranges:

```ts
type HighlightedText = {
  text: string;
  ranges: Array<{ start: number; length: number }>;
};
```

Frontend sau đó chia plain text thành React text nodes và `<mark>` elements. Text vẫn đi qua React escaping thay vì được interpret như HTML.

## Giải thích thiết kế sau khi sửa

### 1. Debounce phải cancel timer trước

Chỉ query cuối cùng sau 300 ms im lặng mới tạo request.

### 2. In-flight request cũ bị abort

Khi query đổi hoặc component unmount, browser không cần tiếp tục giữ request không còn giá trị cho UI.

### 3. Sequence guard bảo vệ state ownership

Ngay cả khi timing edge case khiến một operation hoàn tất gần thời điểm cleanup, chỉ request sequence hiện tại được commit state.

### 4. HTTP error được xử lý khác network cancellation

Abort là expected lifecycle event; HTTP 500 là application/dependency failure cần UI state và telemetry khác.

### 5. Plain text giữ trust boundary đơn giản

Không cần biến customer-controlled string thành trusted HTML chỉ để highlight vài ký tự.

## Trade-offs

- Abort request cũ giảm work nhưng không bảo đảm backend đã dừng ngay mọi downstream operation; backend vẫn cần cancellation support và cost guardrails.
- Debounce 300 ms là UX/performance parameter cần đo, không phải hằng số đúng cho mọi use case.
- Sequence guard thêm một chút state machinery nhưng làm ownership của async response rõ ràng.
- Không giữ stale results khi error giúp tránh user hiểu nhầm, nhưng một UX khác có thể giữ kết quả cũ kèm explicit “stale/error” indicator.
- Highlight bằng ranges phức tạp hơn raw HTML nhưng trust model an toàn và dễ audit hơn.

## Cách kiểm thử

1. **Race-condition test:** mock request `an` trả chậm hơn `anna`; UI cuối cùng chỉ được hiển thị kết quả của query hiện tại.
2. **Debounce test:** nhập nhanh nhiều ký tự trong <300 ms; chỉ một request cuối được phát sau debounce window.
3. **Unmount/cancellation test:** đóng modal khi request đang chạy; request bị abort và không cập nhật state sau lifecycle kết thúc.
4. **Security test:** customer display name chứa `<img onerror=...>` hoặc HTML-like input; UI phải render như text, không execute markup.
5. **Failure-path test:** API trả 500/429/network error; UI hiển thị error state đúng, loading kết thúc và không giữ kết quả cũ như thể thành công.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cosmos DB performance cần được phân tích từ **access pattern, partition key, RequestCharge, cardinality và pagination**, không chỉ từ provisioned RU.
- Query đã biết partition key nên thể hiện partition scope rõ ràng trong SDK request; cross-partition query cần được coi là một cost/latency decision có chủ đích.
- Time range không thay thế pagination. Một endpoint production phải có bounded response behavior.
- Tenant-based partitioning có thể rất hợp lý cho multi-tenant systems, nhưng tenant cực lớn/hot cần được đo riêng trước khi quyết định synthetic/hierarchical partitioning.
- Frontend async code cũng có distributed-timing problems: request được gửi theo thứ tự không có nghĩa response hoàn tất theo thứ tự.
- Debounce đúng cần cleanup timer; superseded network request cần cancellation hoặc stale-response guard.
- `dangerouslySetInnerHTML` làm mất React escaping boundary và không nên dùng cho dữ liệu không tin cậy nếu plain-text/range-based rendering giải quyết được bài toán.
- HTTP 500 và network rejection là hai semantics khác nhau; frontend phải xử lý rõ thay vì dựa vào `catch` cho mọi failure.

## Mẫu tư duy cần nhớ

1. **Bound the query before scaling the database.**
2. **Choose partitioning from dominant access patterns and measured distribution.**
3. **Measure RequestCharge before blaming Cosmos DB capacity.**
4. **Cancel superseded async work and reject stale responses.**
5. **Keep untrusted data as data; do not turn it into executable markup.**
