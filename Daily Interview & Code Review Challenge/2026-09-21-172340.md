# Code Review Challenge 1 — Cosmos DB partition key biến một API lookup thành cross-partition scan đắt đỏ

**Chủ đề:** C#/.NET, ASP.NET Core, Azure Cosmos DB, partition key, RU, query design, pagination, cancellation, observability
**Độ khó:** Senior
**Thời gian review đề xuất:** 30–35 phút
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core API phục vụ trang lịch sử booking. Container `bookings` có khoảng 40 triệu documents và được partition theo `/tenantId`. UI cho phép support agent tìm booking bằng `bookingReference`, sau đó hiển thị 50 booking gần nhất của customer.

Trong production, endpoint chạy ổn với tenant nhỏ nhưng p95 tăng lên 4–8 giây ở giờ cao điểm. Azure Monitor cho thấy RU consumption tăng mạnh và xuất hiện `429`. Team đề xuất tăng throughput vì query vẫn trả đúng dữ liệu.

## Đoạn code cần review

```csharp
public sealed class BookingRepository
{
    private readonly Container _container;

    public BookingRepository(Container container)
        => _container = container;

    public async Task<IReadOnlyList<BookingDocument>> FindAsync(
        string bookingReference,
        string customerId,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(@"
            SELECT * FROM c
            WHERE c.bookingReference = @bookingReference
               OR c.customerId = @customerId
            ORDER BY c.createdAt DESC")
            .WithParameter("@bookingReference", bookingReference)
            .WithParameter("@customerId", customerId);

        var iterator = _container.GetItemQueryIterator<BookingDocument>(query);
        var results = new List<BookingDocument>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            results.AddRange(page);
        }

        return results.Take(50).ToList();
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, performance, cost và reliability concerns.
2. Giải thích production impact và ưu tiên findings.
3. Phân tích partitioning/query shape trước khi đề xuất tăng RU.
4. Đề xuất implementation/data-access design tốt hơn dựa trên requirement thực tế.
5. Giải thích testing và production telemetry cần thiết.

## Kết quả code review tham khảo

### Critical — Query không scope theo partition dù container partition theo `tenantId`

**Vấn đề:** `GetItemQueryIterator` không cung cấp `PartitionKey` và SQL cũng không giới hạn `tenantId`.
**Tại sao xảy ra:** Query phải tìm trên nhiều physical/logical partitions nếu không thể route tới partition cụ thể.
**Ảnh hưởng production:** RU và latency tăng theo dữ liệu/partition fan-out; concurrent traffic có thể gây throttling.
**Cách sửa:** Nếu business context biết tenant, bắt buộc truyền `tenantId` và `QueryRequestOptions.PartitionKey`; nếu lookup thực sự global thì cần thiết kế access path riêng thay vì giả định scan là rẻ.

### High — Giới hạn 50 records diễn ra sau khi đọc toàn bộ result set

**Vấn đề:** Code đọc mọi page rồi mới `Take(50)` trong memory.
**Tại sao xảy ra:** Query không có `TOP`/bounded pagination và loop consume iterator đến hết.
**Ảnh hưởng production:** Tốn RU, network, allocations và latency không cần thiết.
**Cách sửa:** Đưa giới hạn vào query hoặc triển khai pagination/continuation token theo UX requirement.

### High — `OR` trộn hai access patterns khác nhau

**Vấn đề:** Lookup một booking reference và list booking của customer có semantics/cardinality khác nhau.
**Tại sao xảy ra:** Repository gom hai use case vào một query tiện lợi.
**Ảnh hưởng production:** Query khó tối ưu, khó index/partition reasoning và có thể trả tập dữ liệu không đúng intent của caller.
**Cách sửa:** Tách `GetByReference` và `GetRecentByCustomer`; xác định partition key cho từng use case.

### High — Không có pagination contract

**Vấn đề:** API luôn materialize rồi cắt 50, không expose continuation token.
**Tại sao xảy ra:** Data access đang che mất native paging semantics.
**Ảnh hưởng production:** UX không thể tải trang tiếp theo ổn định; server lặp lại công việc lớn.
**Cách sửa:** Thiết kế response với bounded page size và continuation token nếu requirement cần browse history.

### Medium — Materialize full document bằng `SELECT *`

**Vấn đề:** Endpoint có thể chỉ cần subset fields cho list view.
**Tại sao xảy ra:** Document model được dùng trực tiếp làm read model.
**Ảnh hưởng production:** Tăng payload, deserialization và network cost.
**Cách sửa:** Projection đúng fields cần thiết nếu đo đạc cho thấy có lợi.

### Medium — Không quan sát request charge và throttling ở boundary này

**Vấn đề:** Repository bỏ qua diagnostics/request charge của từng page.
**Tại sao xảy ra:** Chỉ quan tâm result data.
**Ảnh hưởng production:** Khó chứng minh query nào gây RU spike/429.
**Cách sửa:** Thu thập telemetry có kiểm soát: operation name, latency, RU, status/substatus, retry/throttling và partition-aware dimensions; không log sensitive payload.

### Medium — Không xác định consistency requirement

**Vấn đề:** Design không nói support agent cần đọc dữ liệu mới đến mức nào.
**Tại sao xảy ra:** Consistency bị coi như implementation detail.
**Ảnh hưởng production:** Có thể trả stale result hoặc trả giá cao hơn cần thiết nếu chọn consistency không phù hợp.
**Cách sửa:** Xác minh business requirement trước khi thay đổi consistency setting.

### Medium — Không có input/tenant authorization boundary thể hiện trong repository contract

**Vấn đề:** API shape không cho thấy tenant scope được ràng buộc với caller.
**Tại sao xảy ra:** `bookingReference`/`customerId` được truyền độc lập.
**Ảnh hưởng production:** Nếu upper layer sai, có nguy cơ cross-tenant lookup ngoài ý muốn.
**Cách sửa:** Carry trusted tenant context xuyên suốt authorization và query boundary.

## Phiên bản đề xuất

```csharp
public sealed record BookingSummary(
    string Id,
    string BookingReference,
    string CustomerId,
    DateTimeOffset CreatedAt,
    string Status);

public sealed class BookingRepository
{
    private readonly Container _container;

    public BookingRepository(Container container)
        => _container = container;

    public async Task<IReadOnlyList<BookingSummary>> GetRecentByCustomerAsync(
        string tenantId,
        string customerId,
        int pageSize,
        CancellationToken cancellationToken)
    {
        var take = Math.Clamp(pageSize, 1, 50);

        var query = new QueryDefinition(@"
            SELECT TOP @take
                c.id,
                c.bookingReference,
                c.customerId,
                c.createdAt,
                c.status
            FROM c
            WHERE c.tenantId = @tenantId
              AND c.customerId = @customerId
            ORDER BY c.createdAt DESC")
            .WithParameter("@take", take)
            .WithParameter("@tenantId", tenantId)
            .WithParameter("@customerId", customerId);

        var options = new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(tenantId),
            MaxItemCount = take
        };

        using var iterator = _container
            .GetItemQueryIterator<BookingSummary>(query, requestOptions: options);

        var results = new List<BookingSummary>(take);

        while (iterator.HasMoreResults && results.Count < take)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            results.AddRange(page);
        }

        return results;
    }
}
```

Lookup theo `bookingReference` nên là operation riêng. Nếu reference chỉ unique trong tenant, query cùng partition là đủ. Nếu requirement bắt buộc global lookup mà không biết tenant, cần đánh giá read model/index mapping riêng hoặc thay đổi key strategy dựa trên volume và consistency requirement; không tự động thêm một datastore mới nếu traffic chưa biện minh.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đưa tenant vào contract, route query tới một logical partition và giới hạn work tại database thay vì sau materialization. Hai use case được tách để mỗi query có semantics rõ. Nếu UI cần paging đầy đủ, phiên bản production nên trả continuation token thay vì chỉ list đầu tiên.

## Trade-offs

Partition theo tenant tối ưu tenant-scoped access nhưng tenant cực lớn có thể tạo hot partition và cần đánh giá lại model. Projection giảm payload nhưng tạo read DTO cần duy trì. Read model riêng cho global lookup tăng write complexity/eventual consistency, vì vậy chỉ đáng dùng khi requirement và measurements chứng minh cần thiết.

## Cách kiểm thử

1. Integration test xác nhận tenant A không thể nhận booking tenant B.
2. Load test trên dataset lớn, so sánh p95/RU trước và sau khi scope partition.
3. Test customer có hàng chục nghìn bookings nhưng endpoint chỉ đọc bounded page.
4. Test throttling/failure path và cancellation propagation.
5. Database test cho query/index policy bằng workload đại diện, không chỉ dataset nhỏ.

## Quan sát trong production

Theo dõi request latency p50/p95/p99, RU/request, `429`, retry count, request volume, partition-level hot spots khi có telemetry phù hợp, result count và Cosmos dependency diagnostics. Correlate với endpoint/tenant dạng an toàn; tránh high-cardinality telemetry không kiểm soát.

## Câu hỏi phỏng vấn mở rộng

1. Nếu một tenant chiếm 60% traffic và trở thành hot partition, bạn sẽ thu thập evidence gì trước khi đổi partition strategy?
2. Nếu `bookingReference` phải lookup global với strong correctness nhưng traffic rất thấp, bạn có tạo read model riêng không? Vì sao?
3. Khi nào tăng provisioned throughput là remediation đúng thay vì che giấu query inefficiency?

# Code Review Challenge 2 — React search UI bị race condition và hiển thị kết quả của request cũ

**Chủ đề:** React.js, TypeScript, async race condition, request cancellation, API integration, state correctness, browser behavior, observability
**Độ khó:** Senior
**Thời gian review đề xuất:** 25–30 phút
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề quan trọng

## Bối cảnh

Một product-search page dùng React và TypeScript. Khi user gõ, UI gọi backend search API. Production analytics cho thấy user gõ nhanh đôi khi nhìn thấy kết quả không khớp text hiện tại. Backend cũng ghi nhận nhiều request gần như đồng thời từ cùng browser. Mobile network chậm làm lỗi xuất hiện thường xuyên hơn.

Team đã thêm debounce bằng `setTimeout`, nhưng bug vẫn xảy ra sau khi component unmount/remount hoặc khi response cũ về sau response mới.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (!query.trim()) {
      setProducts([]);
      return;
    }

    setTimeout(async () => {
      setLoading(true);

      try {
        const response = await fetch(`/api/products?q=${query}`);
        const data = await response.json();
        setProducts(data);
        setError(null);
      } catch (e) {
        setError("Search failed");
      } finally {
        setLoading(false);
      }
    }, 300);
  }, [query]);

  return (
    <section>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Search products"
      />

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {products.map((product) => (
          <li key={product.id}>{product.name}</li>
        ))}
      </ul>
    </section>
  );
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, performance, reliability và UX concerns.
2. Giải thích chính xác race condition giữa nhiều timer/request/response.
3. Ưu tiên vấn đề nào gây stale results và request amplification.
4. Đề xuất implementation an toàn hơn mà không over-engineer.
5. Nêu tests và browser/production telemetry để chứng minh bản sửa.

## Câu hỏi gợi mở

1. Cleanup function của `useEffect` đang ở đâu?
2. Điều gì xảy ra nếu request cho `abc` hoàn thành trước request cho `ab`?
3. `fetch` có tự coi HTTP `500` là rejected promise không?
4. Query string có được encode đúng không?

### Gợi ý 1

### Gợi ý 2

Cancellation giúp giảm wasted work, nhưng correctness vẫn cần bảo đảm response cũ không được phép thắng state mới.

## Kết quả code review tham khảo

### High — Debounce timer cũ không được cleanup

**Vấn đề:** Mỗi thay đổi `query` tạo timer mới và timer trước vẫn chạy.
**Tại sao xảy ra:** `useEffect` không return cleanup gọi `clearTimeout`.
**Ảnh hưởng production:** Gõ `a` → `ab` → `abc` có thể gửi cả ba requests, tăng backend load và mở nhiều race windows.
**Cách sửa:** Lưu timer trong effect scope và clear khi dependency đổi/unmount.

### High — Response cũ có thể overwrite state của query mới

**Vấn đề:** Mọi response đều gọi `setProducts` khi hoàn thành.
**Tại sao xảy ra:** Network completion order không đảm bảo giống request start order.
**Ảnh hưởng production:** UI có thể hiển thị kết quả `ab` trong khi input đang là `abc`.
**Cách sửa:** Abort request cũ và/hoặc dùng generation/request identity để chỉ latest request được commit state.

### High — Không abort in-flight request khi query đổi hoặc component unmount

**Vấn đề:** Request không gắn với `AbortController` lifecycle.
**Tại sao xảy ra:** Effect chỉ khởi tạo asynchronous work mà không cleanup network operation.
**Ảnh hưởng production:** Wasted browser/backend work, stale callbacks và khó reasoning loading/error state.
**Cách sửa:** Tạo `AbortController` theo effect và `abort()` trong cleanup.

### Medium — HTTP error response bị parse như success

**Vấn đề:** `fetch` resolve promise cho nhiều HTTP error statuses; code không kiểm tra `response.ok`.
**Tại sao xảy ra:** Nhầm transport rejection với HTTP failure.
**Ảnh hưởng production:** Error payload có thể bị gán vào `products`, hoặc JSON parsing tạo misleading error.
**Cách sửa:** Check `response.ok` và map error contract rõ ràng.

### Medium — Query parameter không được encode

**Vấn đề:** Interpolation trực tiếp vào URL.
**Tại sao xảy ra:** Không dùng `URLSearchParams`/encoding.
**Ảnh hưởng production:** Query chứa `&`, `#`, Unicode hoặc ký tự đặc biệt có thể tạo request semantics sai.
**Cách sửa:** Dùng `URLSearchParams`.

### Medium — `loading` có thể bị request cũ đặt `false` khi request mới vẫn chạy

**Vấn đề:** `finally` của mọi request đều mutate shared loading state.
**Tại sao xảy ra:** State không gắn với latest operation.
**Ảnh hưởng production:** Spinner biến mất sớm và UI biểu diễn sai trạng thái.
**Cách sửa:** Chỉ latest non-aborted request được commit state, hoặc model state theo request identity.

### Medium — Abort bị hiển thị như lỗi người dùng

**Vấn đề:** Nếu thêm cancellation nhưng catch mọi exception thành `Search failed`, normal supersession sẽ thành error.
**Tại sao xảy ra:** Không phân loại `AbortError`.
**Ảnh hưởng production:** Error flicker khi user gõ nhanh.
**Cách sửa:** Ignore expected abort; chỉ surface genuine failures.

### Low — Empty query không reset toàn bộ transient state

**Vấn đề:** Clear input có thể để error/loading từ operation trước nếu lifecycle không được xử lý đúng.
**Tại sao xảy ra:** State transitions phân tán.
**Ảnh hưởng production:** UX không nhất quán.
**Cách sửa:** Khi query rỗng, cleanup previous operation và reset relevant state có chủ đích.

## Phiên bản đề xuất

```tsx
import { useEffect, useRef, useState } from "react";

type Product = {
  id: string;
  name: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const generation = useRef(0);

  useEffect(() => {
    const normalized = query.trim();
    const currentGeneration = ++generation.current;
    const controller = new AbortController();

    if (!normalized) {
      setProducts([]);
      setLoading(false);
      setError(null);
      return () => controller.abort();
    }

    const timer = window.setTimeout(async () => {
      setLoading(true);
      setError(null);

      try {
        const parameters = new URLSearchParams({ q: normalized });
        const response = await fetch(`/api/products?${parameters}`, {
          signal: controller.signal,
        });

        if (!response.ok) {
          throw new Error(`Search returned ${response.status}`);
        }

        const data: Product[] = await response.json();

        if (generation.current === currentGeneration) {
          setProducts(data);
        }
      } catch (error) {
        if (
          !controller.signal.aborted &&
          generation.current === currentGeneration
        ) {
          setError("Search failed");
        }
      } finally {
        if (generation.current === currentGeneration) {
          setLoading(false);
        }
      }
    }, 300);

    return () => {
      window.clearTimeout(timer);
      controller.abort();
    };
  }, [query]);

  return (
    <section>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Search products"
        aria-label="Search products"
      />

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {products.map((product) => (
          <li key={product.id}>{product.name}</li>
        ))}
      </ul>
    </section>
  );
}
```

## Giải thích thiết kế sau khi sửa

Timer cleanup tạo debounce thực sự. `AbortController` dừng request đã obsolete khi có thể, còn generation check bảo vệ correctness ở state-commit boundary. Hai cơ chế bổ sung nhau: cancellation giảm wasted work; generation bảo đảm chỉ latest logical search được cập nhật UI.

Không cần thêm state-management framework chỉ để giải quyết lifecycle này. Nếu product đã dùng query library có cancellation/cache/deduplication semantics phù hợp, có thể tận dụng library nhưng vẫn phải hiểu stale-result policy.

## Trade-offs

Debounce 300 ms giảm request volume nhưng thêm perceived latency; con số nên dựa trên UX/traffic measurement. Abort không đảm bảo server luôn dừng work ngay lập tức vì request có thể đã tới backend. Generation tracking thêm chút state complexity nhưng làm latest-wins semantics rõ ràng.

## Cách kiểm thử

1. Component test với fake timers: gõ nhanh ba lần chỉ request query cuối sau debounce.
2. Test response cũ hoàn thành sau response mới; UI vẫn hiển thị latest query results.
3. Test unmount/query change abort request và không hiển thị `Search failed` cho expected abort.
4. Test HTTP `500` và malformed payload đi vào error state.
5. Playwright E2E với network delay/reordering để tái hiện mobile/slow-network race.

## Quan sát trong production

Theo dõi frontend request count/search interaction, cancellation rate nếu instrumentation hỗ trợ, API latency/error rate, backend request volume, query-to-result latency và stale-result bug telemetry có correlation an toàn. Browser network traces trong reproduction nên xác nhận số request và completion order. Không log raw search terms nếu chúng có thể chứa dữ liệu nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search rất rẻ nhưng UX yêu cầu phản hồi gần như tức thì, bạn điều chỉnh debounce thế nào?
2. `AbortController` đã đủ để bảo đảm latest-wins correctness chưa? Vì sao?
3. Nếu muốn cache kết quả theo query ở client, bạn sẽ tránh stale data và uncontrolled memory growth như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Cosmos DB performance phải bắt đầu từ access pattern, partition routing và lượng work thực tế thay vì mặc định tăng throughput. Ở frontend asynchronous UI, thứ tự response không được đảm bảo; cancellation và state-commit guard phải được thiết kế theo logical operation.
