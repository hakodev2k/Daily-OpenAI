# Câu 1 — API xuất báo cáo: bộ nhớ tăng dù request đã kết thúc

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 18 phút  
**Kỹ năng được đánh giá:** C# allocation, GC, LOH, streaming, profiling, ASP.NET Core

## Bối cảnh

Một ASP.NET Core API xuất CSV từ PostgreSQL. Một số request tạo file 40–150 MB bằng `MemoryStream`, sau đó gọi `ToArray()` và trả `File(byte[], "text/csv")`. Trên Azure App Service, traffic tăng từ 5 lên 60 request đồng thời; memory working set tăng, GC pause xuất hiện và một số instance bị restart. Sau khi traffic giảm, working set không giảm ngay. Chưa có heap dump hoặc phân tích container limit.

## Câu hỏi chính

Giải thích cơ chế allocation/GC nào có thể gây ra hiện tượng này, những suy luận nào chưa đủ căn cứ, và bạn sẽ kiểm chứng rồi thiết kế lại đường xuất file như thế nào để bảo đảm đúng dữ liệu, kiểm soát bộ nhớ và xử lý client disconnect?

## Câu hỏi làm rõ nên cân nhắc

1. Dữ liệu được buffer ở ứng dụng, driver DB hay reverse proxy; số request đồng thời thực tế?
2. Có giới hạn kích thước export, memory limit và timeout nào?
3. Working set, managed heap, LOH size, GC pause và allocation rate biến động ra sao?
4. Có yêu cầu download lại, resume, audit hay snapshot dữ liệu nhất quán?
5. Có thể xuất bất đồng bộ vào Blob Storage thay vì giữ HTTP request không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt memory được cấp phát với memory đã được trả về hệ điều hành.

### Gợi ý 2
Xem kích thước buffer, hành vi mở rộng của `MemoryStream`, và bản sao từ `ToArray()`.

### Gợi ý 3
Kiểm tra LOH, Gen 2 GC, peak concurrency và cơ chế backpressure khi streaming từ database tới response.

## Cấu trúc trả lời đề xuất

1. Xác nhận triệu chứng và phạm vi ảnh hưởng.
2. Mô tả allocation path và giả thuyết.
3. Chỉ ra điều chưa thể kết luận từ working set.
4. Thiết kế thí nghiệm/telemetry.
5. So sánh streaming trực tiếp, temp file, Blob async.
6. Nêu cancellation, error handling, test và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc
Hiểu `ToArray()` tạo bản sao; buffer lớn gây áp lực lên managed heap/LOH; working set không đồng nghĩa leak; phải đo allocation/GC và peak concurrency trước khi kết luận.

### Điểm cộng
Đề xuất `DbDataReader` sequential access, `StreamWriter` trên `Response.Body`, giới hạn concurrent exports, timeout và cancellation; CSV escaping và authorization.

### Senior+
Giải thích trade-off giữa streaming response (không thể đổi status sau khi headers đã gửi) và export job tạo Blob với TTL, idempotency, quota, observability.

## Hướng giải quyết tham khảo

**Giả định cần xác minh:** Mỗi request materialize CSV hoàn chỉnh trong `MemoryStream`. Với 60 request và payload 100 MB, riêng các buffer có thể tiêu thụ nhiều GB, chưa kể capacity growth, `ToArray()`, query objects và HTTP buffering. Không thể suy ra mức dùng bộ nhớ chính xác bằng phép nhân vì lifetime, capacity và concurrency thực tế chưa biết.

`MemoryStream` thường dùng mảng byte có thể tăng capacity khi ghi; `ToArray()` cấp phát mảng mới và copy nội dung. Các object lớn (thường từ khoảng 85,000 bytes) vào Large Object Heap; thu gom LOH gắn với Gen 2 GC. Bộ nhớ managed đã được GC thu hồi có thể vẫn được runtime giữ để tái sử dụng; working set cao không tự chứng minh memory leak. Không nên khẳng định LOH fragmentation là nguyên nhân khi chưa có heap evidence.

**Xác minh:** Dùng `dotnet-counters` hoặc Azure Application Insights/diagnostics để quan sát allocation rate, GC heap size, Gen 2 collections, time-in-GC, request concurrency, response bytes, OOM/restart events. Lấy memory dump có kiểm soát trong môi trường phù hợp, phân tích retained roots và kích thước `byte[]`; load test với 1/10/60 exports để đối chiếu peak memory và p95.

**Cải tiến:** Đọc database theo luồng, ghi CSV incremental vào response, escape dấu phẩy, quote và newline đúng chuẩn; propagate `HttpContext.RequestAborted` xuống DB và I/O. Không `ToList()` toàn bộ trước khi ghi. Throttle các export tốn tài nguyên, giới hạn kích thước/duration, đặt headers phù hợp trước khi stream. Khi lỗi sau khi response bắt đầu, kết nối có thể bị ngắt và file không hoàn chỉnh; client cần phát hiện lỗi. Nếu export kéo dài hoặc cần retry/download lại, dùng background job tạo file vào Azure Blob Storage, lưu trạng thái job và cấp quyền tải có thời hạn; thiết kế cleanup và phân quyền theo tenant. Không tự động chọn Blob nếu file nhỏ và lưu lượng thấp.

**Kiểm thử:** CSV chứa quote/newline/Unicode; client cancel giữa chừng; DB timeout; nhiều request đồng thời; dữ liệu lớn; authorization cross-tenant. **Giám sát:** p95/p99 duration, active exports, bytes streamed, allocation rate, Gen 2 GC, memory limit, failed/incomplete downloads.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là memory leak vì working set không giảm ngay không chứng minh object còn được giữ. Tôi sẽ xác minh đường allocation: nếu tạo toàn bộ CSV trong MemoryStream rồi ToArray thì có ít nhất một bản copy lớn và có thể gây LOH/Gen 2 pressure. Tôi so sánh GC metrics, heap dump và request concurrency với traffic. Nếu requirement cho phép, tôi sẽ stream từng dòng từ DB ra response, propagate cancellation và giới hạn concurrent exports. Với file lớn, chạy lâu hoặc cần retry, tôi cân nhắc job xuất ra Blob. Đổi lại, streaming khó báo lỗi sau khi gửi headers, còn job tăng độ phức tạp và cần quản lý lifecycle. Tôi sẽ load test và triển khai canary trước khi khẳng định cải thiện.”

## Câu hỏi đào sâu

1. Vì sao GC đã chạy mà working set vẫn cao?
2. Nếu client ngắt kết nối sau khi nhận 80% CSV, bạn đảm bảo UX và dữ liệu thế nào?
3. Nếu phải bảo đảm snapshot nhất quán trong lúc bảng đang thay đổi, thiết kế streaming của bạn thay đổi ra sao?

## Lỗi trả lời thường gặp

- Kết luận memory leak chỉ từ working set.
- Đề xuất gọi `GC.Collect()` trong mỗi request.
- Thay `ToArray()` bằng một buffer lớn khác mà không kiểm tra peak memory.
- Bỏ qua cancellation, CSV escaping và download không hoàn chỉnh.
- Không phân biệt direct streaming và asynchronous export.

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ requirement và giới hạn | 1 |
| Giải thích allocation, LOH, GC đúng | 2 |
| Giả thuyết và bằng chứng | 2 |
| Thiết kế, trade-offs | 2 |
| Production readiness, testing, telemetry | 2 |
| Trình bày mạch lạc | 1 |

# Câu 2 — Service Bus backlog tăng sau release, xử lý chậm và có tác vụ trùng

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 22 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, message processing, idempotency, dependency diagnostics, incident response

## Bối cảnh

Một worker .NET 8 nhận message từ Azure Service Bus queue để đồng bộ trạng thái đơn hàng tới CRM. Sau release, queue depth tăng liên tục; người dùng thấy trạng thái cập nhật chậm 20–40 phút. Một số đơn có log “processed” hai lần. Worker chạy nhiều instance; CRM có rate limit và đôi khi trả HTTP 429. Dashboard mới chỉ hiển thị tổng số message đã nhận, chưa có end-to-end correlation. Không biết lock duration, max concurrent calls, retry policy, DB commit ordering hay version deploy.

## Câu hỏi chính

Trong 30 phút đầu của incident, bạn sẽ giảm tác động, phân biệt ít nhất ba nguyên nhân có thể, tìm bằng chứng và đưa ra biện pháp khắc phục ngắn hạn/dài hạn như thế nào mà không làm mất hoặc xử lý trùng nghiệp vụ?

## Câu hỏi làm rõ nên cân nhắc

1. Active, scheduled, deferred và dead-letter messages thay đổi thế nào; tuổi message cũ nhất?
2. Tốc độ enqueue/dequeue, processing duration, lock lost, delivery count, exception và 429 là bao nhiêu?
3. “Processed” nghĩa là CRM thành công, DB commit hay chỉ nhận message?
4. Có `MessageId`, business idempotency key và retry/backoff phía CRM không?
5. Có thể pause producer/consumer, rollback release, giảm concurrency và ưu tiên loại message nào?

## Gợi ý tư duy

### Gợi ý 1
Bắt đầu từ tác động kinh doanh và an toàn dữ liệu, không chỉ tăng số instance.

### Gợi ý 2
Phân biệt backlog do ingress tăng, throughput giảm, poison messages hoặc dependency throttling.

### Gợi ý 3
Xem at-least-once delivery, lock renewal, complete/settlement, retry và tính idempotent của side effect CRM.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius, SLA và ưu tiên.
2. Stabilize: rollback/throttle có kiểm soát.
3. Thu thập queue, worker, CRM, DB telemetry.
4. So sánh giả thuyết với evidence.
5. Xác định điểm side effect/settlement.
6. Sửa retry và idempotency.
7. Backfill/replay, kiểm thử và alert.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không coi duplicate delivery là lỗi bất thường của queue; xử lý at-least-once, message settlement và idempotency. Điều tra 429, latency, concurrency, retry và lock.

### Điểm cộng
Phân biệt queue depth và oldest-message age, có kế hoạch rollback, DLQ triage, correlation theo business operation, giới hạn throughput theo quota CRM.

### Senior+
Phân tích atomicity gap giữa CRM side effect, local state và `CompleteMessageAsync`; đề xuất reconciliation, inbox/dedupe hoặc remote idempotency contract theo khả năng CRM.

## Hướng giải quyết tham khảo

**Impact và stabilize:** Xác nhận bao nhiêu đơn bị trễ, có cập nhật trùng gây hại không, thông báo trạng thái degradation. Giữ queue để không mất message. Nếu release liên quan, cân nhắc rollback worker; giảm concurrency khi CRM 429 tăng, thay vì scale out mù quáng. Chỉ pause consumer khi có nguy cơ side effect sai; đánh giá producer/backlog growth.

**Giả thuyết cạnh tranh:** (A) release tăng `MaxConcurrentCalls` làm CRM throttling; (B) xử lý lâu hơn lock duration hoặc auto-renew không đủ khiến redelivery; (C) exception xảy ra sau CRM success nhưng trước settlement; (D) DB connection pool hoặc query chậm; (E) ingress đột biến. Cần đối chiếu deploy timeline, CRM 429, worker dependency duration, delivery count, lock-lost exceptions, queue age, CPU, connection pool và traces theo `MessageId`.

**Cơ chế:** Azure Service Bus PeekLock có thể giao lại message nếu lock hết hạn hoặc settlement thất bại. Complete thành công sau side effect không phải giao dịch atomic xuyên Service Bus–CRM. Hai log “processed” chưa đủ chứng minh CRM side effect thực hiện hai lần. Duplicate detection ở broker (nếu cấu hình) không thay thế idempotent consumer.

**Remediation:** Đặt bounded concurrency và retry cho lỗi transient có exponential backoff/jitter, tôn trọng `Retry-After` khi phù hợp; tránh retry đồng thời nhiều tầng làm tăng tải. Thiết kế idempotency key ổn định theo operation, ghi trạng thái dedupe bằng unique constraint và state machine; không đánh dấu thành công trước side effect nếu không có cơ chế recovery. Nếu CRM hỗ trợ idempotency key, dùng ở API phía CRM; nếu không, cần read-before-write/reconciliation theo contract, nhận thức rằng không thể bảo đảm exactly-once cross-system chỉ bằng local DB. Chỉ complete sau khi xử lý đạt trạng thái nghiệp vụ an toàn; poison message đưa DLQ theo policy và xử lý thủ công/có audit. Reconcile những message đã xử lý không chắc chắn trước replay.

**Xác minh:** Tạo fault injection CRM 429, timeout sau side effect, crash trước settlement, lock expiry, duplicate delivery; đo recovery và bảo đảm trạng thái cuối đúng. Alert theo oldest active message age, DLQ growth, 429 ratio, processing latency, lock lost, redelivery, error budget. Phân tách correlation ID, message ID, business operation ID; không log token hoặc dữ liệu khách hàng nhạy cảm.

## Mẫu trả lời trong phỏng vấn

“Tôi ưu tiên xác định đơn hàng nào bị trễ hoặc cập nhật sai và ngăn tăng tác động. Tôi không tăng worker ngay vì CRM đang có 429; tăng concurrency có thể khiến throughput tệ hơn. Tôi kiểm tra queue age, ingress/egress, delivery count, lock lost, dependency duration và timeline release. Các giả thuyết gồm throttling, lock expiry, lỗi giữa CRM success và Complete, hoặc DB bottleneck. Vì Service Bus có thể redeliver, tôi yêu cầu consumer idempotent ở mức business operation; broker duplicate detection không đủ. Tôi điều chỉnh concurrency/retry, có DLQ và reconciliation cho trạng thái chưa chắc chắn, rồi test crash/retry trước khi mở lại throughput. Tôi theo dõi thời gian trễ end-to-end chứ không chỉ số message đã nhận.”

## Câu hỏi đào sâu

1. CRM trả 200 nhưng worker crash trước `CompleteMessageAsync`: xử lý thế nào?
2. Nếu CRM không có idempotency API và cập nhật không thể đọc lại, bạn cam kết điều gì với Product?
3. Khi tăng worker instance làm backlog tăng nhanh hơn, bạn dùng số liệu nào để giải thích?

## Lỗi trả lời thường gặp

- Tăng concurrency/instance ngay khi thấy queue depth tăng.
- Khẳng định queue đảm bảo exactly-once business execution.
- Retry mọi HTTP status không giới hạn.
- Xóa hoặc replay DLQ hàng loạt mà không đánh giá side effects.
- Chỉ đo throughput, bỏ qua tuổi message và trạng thái cuối.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ impact và stabilize | 2 |
| Cơ chế Service Bus, lock, delivery | 2 |
| Hypotheses, evidence, investigation | 2 |
| Idempotency, retry, trade-offs | 2 |
| Testing, monitoring, communication | 1 |
| Trình bày có ưu tiên | 1 |

# Câu 3 — Modernize cổng quản trị ASP.NET MVC và jQuery mà không ngừng vận hành

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** .NET modernization, IIS, ASP.NET Core, Vue.js, auth, deployment, incremental architecture

## Bối cảnh

Một portal quản trị chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server, jQuery và SQL Server. Hệ thống quản lý phê duyệt hồ sơ; mỗi ngày vài nghìn người dùng, có file attachment và audit trail. Business muốn giao diện mới bằng Vue.js và chuẩn hóa API, nhưng không cho phép downtime dài; đội ngũ chỉ có 4 developer. Có thư viện third-party chưa rõ hỗ trợ modern .NET; session-based authentication đang dùng. Không có yêu cầu bắt buộc Kubernetes hoặc Microservices.

## Câu hỏi chính

Bạn sẽ chọn chiến lược modernization, chia boundary và migration sequence ra sao để triển khai dần Vue.js/ASP.NET Core mà vẫn bảo toàn authentication, authorization, dữ liệu, audit và khả năng rollback? Khi nào bạn giữ nguyên monolith?

## Câu hỏi làm rõ nên cân nhắc

1. Thư viện third-party, Windows-only APIs và integration nào cản trở chuyển runtime?
2. Có SSO/Entra ID, cookie/session store, cross-origin, CSRF và quyền theo vai trò hiện tại thế nào?
3. Những flow nào có rủi ro cao nhất: approval, upload, audit hay báo cáo?
4. Có automated tests, CI/CD, staging, feature flags, reverse proxy và khả năng rollback không?
5. Có thể giữ cùng domain, schema và deploy độc lập theo route không?

## Gợi ý tư duy

### Gợi ý 1
Không mặc định rewrite toàn bộ hay chia Microservices.

### Gợi ý 2
Xác định seam theo route, feature và ownership của dữ liệu.

### Gợi ý 3
Chú ý authentication boundary, database schema evolution, session, rollback và audit consistency trong giai đoạn hai runtime cùng hoạt động.

## Cấu trúc trả lời đề xuất

1. Inventory và baseline behavior.
2. Xác định rủi ro, non-functional requirements.
3. So sánh big-bang rewrite và incremental migration.
4. Thiết kế routing, identity, data ownership.
5. Kế hoạch từng wave, release/rollback.
6. Testing, telemetry và tiêu chí dừng.

## Ý chính của câu trả lời tốt

### Bắt buộc
Ưu tiên incremental strangler-style migration có đo lường; giữ chức năng cũ ổn định; phân quyền phía server; tránh dual-write không kiểm soát; nêu rõ rollback.

### Điểm cộng
Đề xuất reverse proxy route-based migration, shared identity contract, expand-contract schema, feature flags, contract tests và Playwright E2E.

### Senior+
Biết rằng cookie/session giữa ASP.NET Framework và ASP.NET Core không tự tương thích; cân nhắc SSO/OIDC hoặc bridge được thiết kế rõ; xử lý dữ liệu phiên, distributed transaction và backward compatibility theo từng wave.

## Hướng giải quyết tham khảo

**Quyết định ban đầu:** Với 4 developer, traffic vừa phải và yêu cầu downtime thấp, tôi nghiêng về migration theo tính năng thay vì rewrite hay Microservices. Trước hết inventory packages, Windows-specific dependencies, route map, SQL schema, background jobs, authentication, authorization, file handling, audit và dependency graph. Chạy baseline E2E cho approval, upload và rollback; thiết lập metrics latency/error rate.

**Kiến trúc chuyển tiếp:** Giữ IIS portal cũ làm legacy app; đưa ASP.NET Core API/Vue.js theo các route hoặc subpaths có thể chuyển hướng bằng reverse proxy. Ưu tiên feature ít critical trước. Với API mới, phân quyền ở backend theo claims/policy và object ownership, không dựa vào Vue route guard. Tránh giả định session/cookie cũ dùng trực tiếp được trên runtime mới: nếu có identity provider phù hợp, chuẩn hóa OIDC login và token/cookie handling; nếu chưa có, thiết kế transition/bridge riêng, đánh giá CSRF, SameSite, logout và shared session requirements. Dùng same-origin nếu khả thi để giảm phức tạp CORS.

**Dữ liệu:** Trong giai đoạn chuyển tiếp có thể cùng SQL Server nhưng phải định nghĩa rõ module nào được ghi bảng nào. Ưu tiên một write owner cho mỗi workflow; schema migration kiểu expand-contract: thêm cột/bảng tương thích trước, deploy code đọc/ghi mới, backfill, sau đó mới bỏ schema cũ khi rollback window đóng. Với approval và audit, bảo đảm transaction boundary, concurrency tokens và immutable audit events theo yêu cầu. Nếu hai hệ thống cần giao tiếp, dùng API nội bộ rõ contract; không tự động đưa message broker vào mọi thao tác.

**Triển khai:** Chia wave: (1) inventory và test baseline, (2) CI/CD + telemetry + identity plan, (3) một feature read-only trên Vue/API mới, (4) feature ghi ít rủi ro, (5) approval với dual-run comparison hoặc shadow read không gây side effect, (6) cleanup legacy. Mỗi wave có feature flag, smoke tests, Playwright E2E, schema compatibility và rollback route về legacy. Rollback application không có nghĩa rollback schema dễ dàng; tránh destructive migrations trong release.

**Các lựa chọn:** Big-bang có thể phù hợp nếu ứng dụng rất nhỏ, test đầy đủ và downtime chấp nhận được; ở đây rủi ro cao. Modular Monolith/Layered Architecture đủ nếu transaction và team boundaries đơn giản. Microservices chỉ cân nhắc khi có nhu cầu scaling/deploy/ownership độc lập thực sự. Azure App Service hoặc IIS đều có thể dùng; hosting choice dựa vào dependencies và operations chứ không chạy theo công nghệ.

**Production:** So sánh error rate, auth failures, p95, SQL waits, audit gaps, approval completion rate giữa legacy và new. Dùng correlation ID xuyên proxy và API; cảnh báo 401/403 tăng đột ngột, inconsistent approval state, failed uploads. Có kế hoạch support và runbook cho từng wave.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không rewrite toàn bộ vì hệ thống có approval và audit đang chạy production, trong khi team chỉ có bốn người. Tôi inventory dependencies và tạo baseline test trước. Sau đó triển khai từng route bằng reverse proxy: feature đọc đơn giản trước, workflow ghi sau. Điểm khó nhất là identity/session giữa ASP.NET Framework và ASP.NET Core, cùng ownership của SQL writes. Tôi chuẩn hóa identity contract, enforce authorization ở API và dùng expand-contract schema để cả hai version tương thích trong rollback window. Mỗi wave có feature flag, E2E test và telemetry. Tôi giữ Modular Monolith nếu chưa có lý do vận hành rõ ràng để tách Microservices; kiến trúc đơn giản hơn sẽ giảm rủi ro migration.”

## Câu hỏi đào sâu

1. Nếu legacy và ASP.NET Core cần cùng phiên đăng nhập nhưng không thể thay identity provider ngay, bạn đánh giá những phương án nào?
2. Nếu Product yêu cầu rollback ngay sau khi schema mới đã ghi dữ liệu, bạn chuẩn bị thế nào?
3. Khi nào việc giữ một database chung trở thành vấn đề và bạn sẽ tách ownership ra sao?

## Lỗi trả lời thường gặp

- Chọn Microservices/Kubernetes chỉ vì hiện đại.
- Giả định cookie và session tự chia sẻ giữa hai runtime.
- Deploy destructive migration trước khi rollback window kết thúc.
- Dùng frontend route guard thay server authorization.
- Không đo parity nghiệp vụ, audit và tác động sau release.
