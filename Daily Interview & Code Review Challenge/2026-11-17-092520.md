# Code Review Challenge 1 — Service Bus consumer gửi hóa đơn hai lần sau lock expiry

**Chủ đề:** C#/.NET 8, Azure Service Bus, idempotent consumer, SQL Server, external payment API  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một hệ thống subscription nhận message `InvoiceRequested` qua Azure Service Bus queue. Mỗi message chứa `InvoiceId`, `CustomerId`, `Amount`. Worker chạy trên bốn instances; nhà cung cấp thanh toán có thể timeout sau khi đã chấp nhận yêu cầu. SLA cho phép xử lý bất đồng bộ, nhưng không cho phép charge hai lần. Gần đây có invoice bị charge hai lần khi provider chậm; một số message biến mất khỏi hàng đợi dù database chưa cập nhật. Chưa biết provider hỗ trợ idempotency key hay API tra cứu transaction.

## Đoạn code cần review

```csharp
public sealed class InvoiceWorker : BackgroundService
{
    private readonly ServiceBusClient _bus;
    private readonly IServiceProvider _services;
    private readonly HttpClient _http;
    private readonly ILogger<InvoiceWorker> _logger;

    public InvoiceWorker(ServiceBusClient bus, IServiceProvider services,
        HttpClient http, ILogger<InvoiceWorker> logger)
        => (_bus, _services, _http, _logger) = (bus, services, http, logger);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await using var receiver = _bus.CreateReceiver("invoice-requests");
        while (!stoppingToken.IsCancellationRequested)
        {
            var message = await receiver.ReceiveMessageAsync(
                TimeSpan.FromSeconds(5), stoppingToken);
            if (message is null) continue;
            var invoice = message.Body.ToObjectFromJson<InvoiceRequested>();
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<BillingDbContext>();

            if (await db.Invoices.AnyAsync(x => x.Id == invoice.InvoiceId))
            {
                await receiver.CompleteMessageAsync(message, stoppingToken);
                continue;
            }

            var response = await _http.PostAsJsonAsync(
                "/charges", new { invoice.CustomerId, invoice.Amount });
            response.EnsureSuccessStatusCode();

            await receiver.CompleteMessageAsync(message, stoppingToken);
            db.Invoices.Add(new Invoice {
                Id = invoice.InvoiceId, Status = "Paid",
                Amount = invoice.Amount
            });
            await db.SaveChangesAsync(stoppingToken);
            _logger.LogInformation("Charged {InvoiceId}", invoice.InvoiceId);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — External charge không idempotent

**Vấn đề:** Mỗi lần xử lý gọi `/charges` mới, không có operation key ổn định.  
**Tại sao xảy ra:** Broker có thể redeliver; provider có thể charge thành công trước khi client timeout.  
**Ảnh hưởng production:** Charge trùng, cần hoàn tiền, mất lòng tin.  
**Cách sửa:** Dùng provider-supported idempotency key gắn với `InvoiceId`; nếu không hỗ trợ, cần API tra cứu/reconciliation và không retry mù khi outcome unknown.

### [Critical] — Complete trước khi commit

**Vấn đề:** `CompleteMessageAsync` chạy trước `SaveChangesAsync`.  
**Tại sao xảy ra:** Ack và SQL commit là hai hệ thống không có atomic transaction chung.  
**Ảnh hưởng production:** Crash giữa hai bước gây mất message và thiếu invoice.  
**Cách sửa:** Persist trạng thái trước ack; thiết kế retry idempotent, reconcile outcome chưa rõ.

### [High] — Check-then-act race

**Vấn đề:** `AnyAsync` không khóa logical invoice.  
**Tại sao xảy ra:** Hai workers cùng thấy chưa có record rồi đều charge.  
**Ảnh hưởng production:** Duplicate charge ngay cả khi database có unique constraint; constraint chỉ ngăn insert trùng sau side effect.  
**Cách sửa:** Unique key và atomic claim trong database trước side effect; đảm bảo chỉ một worker sở hữu operation tại một thời điểm.

### [High] — Không xử lý unknown outcome

**Vấn đề:** Timeout được xem là thất bại chắc chắn.  
**Tại sao xảy ra:** HTTP response bị mất không đồng nghĩa request chưa được provider thực hiện.  
**Ảnh hưởng production:** Retry dẫn tới duplicate hoặc invoice mắc kẹt.  
**Cách sửa:** Trạng thái `Unknown`, tra cứu bằng operation key, reconciliation và cảnh báo.

### [High] — Lock và shutdown không được điều phối

**Vấn đề:** Receiver dùng receive/complete thủ công nhưng không renew lock; HTTP không nhận cancellation token.  
**Tại sao xảy ra:** Xử lý lâu hơn lock duration hoặc shutdown giữa chừng.  
**Ảnh hưởng production:** Concurrent delivery, worker treo khi shutdown, xử lý lại.  
**Cách sửa:** Dùng `ServiceBusProcessor` với auto lock renewal cấu hình phù hợp hoặc chủ động renew; truyền token và thiết kế restart-safe.

### [Medium] — Poison message và lỗi transient không có chính sách

**Vấn đề:** Exception thoát khỏi vòng lặp, không có phân loại retry.  
**Tại sao xảy ra:** `EnsureSuccessStatusCode`, deserialize, SQL và broker operations có thể throw.  
**Ảnh hưởng production:** Worker dừng, backlog tăng; invalid payload được thử lại vô ích.  
**Cách sửa:** Per-message exception handling, abandon/dead-letter theo loại lỗi, backoff, bounded attempts và alert DLQ.

### [Medium] — Thiếu kiểm tra business invariants

**Vấn đề:** Không xác minh amount/currency và invoice source-of-truth trước charge.  
**Tại sao xảy ra:** Tin trực tiếp vào payload.  
**Ảnh hưởng production:** Charge sai amount hoặc duplicate business request.  
**Cách sửa:** Tra cứu immutable invoice từ database, kiểm tra trạng thái và currency, không lấy amount tùy ý từ message.

### [Medium] — Thiếu correlation và dependency telemetry

**Vấn đề:** Chỉ log sau success, không có operation/provider ID, attempt hoặc duration.  
**Tại sao xảy ra:** Không thiết kế observability cho distributed operation.  
**Ảnh hưởng production:** Không xác định được nguyên nhân và phạm vi charge trùng.  
**Cách sửa:** Structured logs và traces có `InvoiceId`, `MessageId`, `DeliveryCount`, provider reference; tuyệt đối không log payment secrets.

## Phiên bản đề xuất

Đoạn sau minh họa *phần claim và transition*, không giả định có distributed transaction. Cần triển khai `TryClaimAsync` bằng atomic conditional update + unique index trên `InvoiceId`, có lease owner/expiry và fencing token; `ResolveAsync` phải kiểm tra kết quả provider theo idempotency key trước khi thử lại.

```csharp
public async Task ProcessAsync(
    ServiceBusReceivedMessage message,
    CancellationToken ct)
{
    var request = message.Body.ToObjectFromJson<InvoiceRequested>()
        ?? throw new InvalidDataException("Invalid invoice payload");

    var invoice = await _db.Invoices.SingleAsync(
        x => x.Id == request.InvoiceId, ct);
    if (invoice.Status == InvoiceStatus.Paid) return;

    var claim = await _operations.TryClaimAsync(
        invoice.Id, _workerId, ct);
    if (claim is null)
        throw new OperationInProgressException(invoice.Id);

    try
    {
        var result = await _payments.ResolveOrChargeAsync(
            invoice.Id.ToString("N"),
            invoice.CustomerId,
            invoice.Amount,
            invoice.Currency,
            ct);

        await _operations.CommitOutcomeAsync(
            invoice.Id, claim.FencingToken,
            result.ProviderReference, result.Status, ct);
    }
    catch (OperationCanceledException) when (ct.IsCancellationRequested)
    {
        throw;
    }
    catch (PaymentOutcomeUnknownException)
    {
        await _operations.MarkUnknownAsync(
            invoice.Id, claim.FencingToken, CancellationToken.None);
        throw;
    }
}
```

Receiver chỉ complete sau khi trạng thái durable được commit; lỗi retryable thì abandon hoặc để lock expire theo retry policy, invalid permanent payload thì dead-letter. `MarkUnknownAsync` cần bounded shutdown token riêng và reconciliation để xử lý cả khi persistence thất bại. `ResolveOrChargeAsync` chỉ an toàn khi provider có idempotency key được bảo đảm hoặc tra cứu outcome đáng tin cậy; nếu không, phải dừng auto-charge lại ở trạng thái unknown và can thiệp nghiệp vụ.

## Giải thích thiết kế sau khi sửa

Database là nguồn sự thật của invoice và operation state; broker chỉ kích hoạt xử lý. Atomic claim giảm concurrency nhưng không thay thế provider idempotency. Fencing token ngăn worker có lease cũ ghi đè outcome mới. Khi DB commit thành công nhưng ack thất bại, redelivery thấy `Paid` và complete an toàn.

## Trade-offs

Operation table, reconciliation worker và DLQ tăng complexity và chi phí vận hành. Nếu provider không có idempotency/lookup, không thể bảo đảm exactly-once external side effect bằng SQL + Service Bus đơn thuần; phải chấp nhận manual resolution hoặc thay provider/contract. Lock renewal không thay thế idempotency.

## Cách kiểm thử

1. **Concurrency test:** Hai consumers nhận hai messages cùng `InvoiceId`, provider mock chỉ ghi một charge.
2. **Failure-path test:** Provider charge thành công nhưng HTTP timeout; retry dùng cùng key và không charge thêm.
3. **Crash test:** DB commit thành công, process chết trước ack; redelivery complete mà không charge lại.
4. **Integration test:** Invalid payload vào DLQ; transient SQL failure retry, không mất message.
5. **Load test:** Nhiều invoice khác nhau, đo throughput, lock lost, backlog và connection saturation.

## Quan sát trong production

Application Insights traces nối `InvoiceId` và `MessageId`; metrics: `charge_attempts`, `provider_duplicate_prevented`, `unknown_outcomes`, `lock_lost`, `queue_depth`, `DLQ_depth`, `reconciliation_age`. Alert khi unknown tăng, DLQ có message hoặc chênh lệch paid invoice với provider settlement. Không log PII/payment token.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không có idempotency key lẫn lookup, đề xuất operational contract nào để tránh charge lại?
2. Khi nào cần Outbox Pattern ở phía producer và nó giải quyết/không giải quyết điều gì ở consumer?
3. Nếu cùng invoice nhận yêu cầu đổi amount, operation key và invariant phải thiết kế thế nào?

```tsx
type Product = {
  id: string;
  title: string;
  price: number;
  descriptionHtml: string;
};

export function ProductSearch({ market }: { market: "VN" | "US" }) {
  const [query, setQuery] = React.useState("");
  const [sort, setSort] = React.useState("relevance");
  const [products, setProducts] = React.useState<Product[]>([]);
  const [loading, setLoading] = React.useState(false);
  const cache = React.useRef<Record<string, Product[]>>({});

  React.useEffect(() => {
    const key = query.trim().toLowerCase();
    if (cache.current[key]) {
      setProducts(cache.current[key]);
      return;
    }
    setLoading(true);
    fetch(
      `/api/products?market=${market}&q=${query}&sort=${sort}`
    )
      .then(r => r.json())
      .then(data => {
        cache.current[key] = data.items;
        setProducts(data.items);
      })
      .catch(() => setProducts([]))
      .finally(() => setLoading(false));
  }, [query, market, sort]);

  return (
    <section>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <select value={sort} onChange={e => setSort(e.target.value)}>
        <option value="relevance">Relevance</option>
        <option value="price">Price</option>
      </select>
      {loading && <p>Loading...</p>}
      {products.map(p => (
        <article key={p.id}>
          <h3>{p.title}</h3>
          <strong>{market === "VN" ? "₫" : "$"}{p.price}</strong>
          <div dangerouslySetInnerHTML={{ __html: p.descriptionHtml }} />
        </article>
      ))}
    </section>
  );
}
```

## Phiên bản đề xuất

Giả định API trả `{ items: [{ id, title, price, currency }] }`, trong đó `price` là major unit chính xác theo contract (production có thể dùng integer minor units để tránh floating-point). Mẫu dưới đây cố ý không cache để ưu tiên correctness; cache có thể bổ sung khi đã xác định scope và TTL.

```tsx
type Market = "VN" | "US";
type Product = {
  id: string;
  title: string;
  price: number;
  currency: "VND" | "USD";
};

export function ProductSearch({ market }: { market: Market }) {
  const [input, setInput] = React.useState("");
  const [query, setQuery] = React.useState("");
  const [sort, setSort] = React.useState("relevance");
  const [items, setItems] = React.useState<Product[]>([]);
  const [status, setStatus] = React.useState<
    "loading" | "success" | "error"
  >("loading");

  React.useEffect(() => {
    const timer = window.setTimeout(() => setQuery(input.trim()), 300);
    return () => window.clearTimeout(timer);
  }, [input]);

  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;
    setStatus("loading");
    setItems([]);

    const params = new URLSearchParams({ market, q: query, sort });
    async function load() {
      try {
        const response = await fetch(`/api/products?${params}`, {
          signal: controller.signal
        });
        if (!response.ok) throw new Error(`HTTP ${response.status}`);
        const data: { items: Product[] } = await response.json();
        if (!Array.isArray(data.items)) throw new Error("Invalid payload");
        if (active) {
          setItems(data.items);
          setStatus("success");
        }
      } catch (error) {
        if (active && !controller.signal.aborted) {
          setStatus("error");
        }
      }
    }
    void load();
    return () => {
      active = false;
      controller.abort();
    };
  }, [market, query, sort]);

  return (
    <section>
      <label htmlFor="product-query">Tìm sản phẩm</label>
      <input id="product-query" value={input}
        onChange={e => setInput(e.target.value)} />
      <label htmlFor="product-sort">Sắp xếp</label>
      <select id="product-sort" value={sort}
        onChange={e => setSort(e.target.value)}>
        <option value="relevance">Relevance</option>
        <option value="price">Price</option>
      </select>
      <p role="status" aria-live="polite">
        {status === "loading" ? "Đang tải..." :
         status === "error" ? "Không tải được sản phẩm." :
         `${items.length} sản phẩm`}
      </p>
      {status === "success" && items.map(p => (
        <article key={p.id}>
          <h3>{p.title}</h3>
          <strong>{new Intl.NumberFormat(
            market === "VN" ? "vi-VN" : "en-US",
            { style: "currency", currency: p.currency }
          ).format(p.price)}</strong>
        </article>
      ))}
    </section>
  );
}
```

API cần validate `market`, `sort`, access scope và đảm bảo price/currency đúng market; frontend không thể tự bảo đảm điều này. Khi cần rich text, render qua component sanitize riêng đã kiểm thử. Production cần runtime schema validation, error classification và retry UI theo contract, không chỉ TypeScript type assertion.

## Giải thích thiết kế sau khi sửa

Effect cleanup ngăn stale response cập nhật UI; debounce giảm request bursts. `URLSearchParams` encode query đúng. Không cache cross-market khi chưa xác định ownership. Explicit status phân biệt empty với error. `Intl.NumberFormat` xử lý format, không thực hiện currency conversion.

## Trade-offs

Clear items khi loading tránh hiển thị sai market nhưng gây flicker; có thể giữ previous data kèm market badge và loading overlay nếu Product chấp thuận. Abort không bảo đảm server ngừng xử lý; server vẫn cần rate limiting. Query library giúp caching/deduplication nhưng thêm dependency và phải cấu hình query key đúng. Debounce tăng latency cảm nhận nhỏ.

## Cách kiểm thử

1. **Race test:** Trả response market VN sau US; UI vẫn chỉ hiển thị US.
2. **Component test:** Đổi sort cùng query không dùng nhầm dữ liệu cũ.
3. **Security test:** HTML chứa event handler từ API không được render thành executable markup.
4. **Failure-path test:** HTTP 429/500/401 hiển thị error state, không crash hay giả vờ empty.
5. **Playwright E2E:** Gõ nhanh, chuyển market, kiểm tra currency, keyboard label và network request count.

## Quan sát trong production

Đo request count per search session, 429 rate, API p95, cancellation count, client errors, market/currency mismatch (không log query chứa PII), browser network waterfall và Web Vitals. Correlate request ID từ frontend với API traces. Alert khi mismatch hoặc 429 tăng sau release.

## Câu hỏi phỏng vấn mở rộng

1. Khi chuyển sang TanStack Query, query key và staleTime cần định nghĩa thế nào cho giá theo market và user?
2. Nếu SEO yêu cầu crawler đọc product list, SSR/SSG và hydration ảnh hưởng consistency ra sao?
3. Khi API trả tiền ở minor units, thiết kế TypeScript model và format VND/USD thế nào để tránh sai số?

## Kiến thức trọng tâm

Service Bus có thể redeliver, vì vậy consumer phải thiết kế idempotency cùng với database state và external side effect. Không thể dựa vào thứ tự ack/commit để có atomicity giữa broker, SQL và payment provider. Ở frontend, state correctness phụ thuộc identity của request, cache scope, response order và contract về giá; TypeScript không thay thế runtime validation.

3. Xác định transaction boundary và các crash window trước khi viết code.
4. Chứng minh UI state tương ứng với đúng request parameters.
5. Test failure path và race trước khi tối ưu caching.
