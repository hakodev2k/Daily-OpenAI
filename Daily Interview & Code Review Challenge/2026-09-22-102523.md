# Câu 1 — API xuất file tăng memory theo bậc thang dù request đã hoàn tất

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** C# runtime, GC, LOH, allocation, ASP.NET Core, file streaming, memory diagnostics, performance

## Bối cảnh

Một ASP.NET Core API trên .NET 8 tạo file JSON export cho khách hàng. Mỗi request thường tạo payload 20–80 MB. Sau khi thêm feature này, memory của process tăng theo bậc thang trong giờ cao điểm. Request vẫn hoàn tất, không thấy object leak rõ ràng trong code review, và memory đôi khi giảm sau một thời gian nhưng không trở lại ngay mức ban đầu.

Implementation hiện tại serialize toàn bộ dữ liệu vào `MemoryStream`, gọi `ToArray()`, sau đó trả `File(bytes, "application/json")`. Team thấy `GC.GetTotalMemory(false)` thấp hơn đáng kể so với working set của process và kết luận rằng “GC đang leak native memory”. Một đề xuất khác là gọi `GC.Collect()` sau mỗi export.

Chưa biết allocation profile thực tế, tỷ lệ concurrent exports, response buffering ở các layer khác hay container/process memory limit.

## Câu hỏi chính

Hãy giải thích các cơ chế runtime có thể khiến memory tăng như vậy dù object cuối cùng không còn reachable. Phân tích vai trò của large allocations, LOH, copying do `MemoryStream.ToArray()`, GC generations, committed memory/working set và concurrency. Sau đó trình bày cách bạn xác minh giả thuyết và thiết kế lại export path trước khi quyết định đây là memory leak.

## Câu hỏi làm rõ nên cân nhắc

1. Có bao nhiêu export lớn chạy đồng thời và kích thước phân phối p50/p95/p99 là bao nhiêu?
2. Response có bị buffering thêm bởi middleware, reverse proxy hoặc hosting layer không?
3. Working set, GC heap size, committed bytes và allocation rate thay đổi tương quan thế nào?
4. Export có bắt buộc phải biết `Content-Length` trước hay có thể stream/chunk response?
5. Dữ liệu được đọc từ database theo streaming/projection hay materialize toàn bộ trước khi serialize?

## Gợi ý tư duy

### Gợi ý 1

“Object đã được collect” và “OS working set lập tức giảm” không phải cùng một khái niệm.

### Gợi ý 2

Hãy đếm số bản sao của payload trong memory tại peak: source objects, `MemoryStream` buffer, `ToArray()` result và các buffer khác.

### Gợi ý 3

Trước khi gọi `GC.Collect()`, hãy chứng minh vấn đề là GC scheduling chứ không phải allocation architecture hoặc concurrency amplification.

## Cấu trúc trả lời đề xuất

1. Làm rõ memory metric đang quan sát.
2. Mô tả allocation path của request hiện tại.
3. Giải thích GC generations/large-object behavior ở mức cần thiết.
4. Phân biệt leak, retained managed memory, committed heap và working set.
5. Thu thập allocation/GC evidence.
6. Tính peak-memory envelope theo payload × concurrency × copies.
7. Đề xuất streaming/bounded-concurrency design.
8. Test dưới load và monitor production.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `MemoryStream.ToArray()` tạo một array mới chứa bản sao dữ liệu; với payload lớn, request có thể giữ nhiều large buffers cùng lúc.
- Large managed arrays thuộc nhóm large-object allocations và có GC/compaction behavior khác small objects; không nên suy luận leak chỉ từ working set.
- Managed objects không còn reachable có thể được collect nhưng runtime/OS không nhất thiết trả toàn bộ committed pages về OS ngay lập tức.
- `GC.GetTotalMemory` và process working set đo các phạm vi khác nhau.
- Concurrent exports nhân peak memory; phải tính concurrency chứ không chỉ kích thước một request.
- `GC.Collect()` trên mỗi request thường là phản ứng sai nếu chưa có evidence; có thể tăng pause/CPU và phá heuristics của GC.
- Cần đo allocation rate, GC heap/collections, object types/sizes, working set và request concurrency trước khi tối ưu.

### Điểm cộng

- Streaming trực tiếp JSON ra response có thể loại bỏ full-payload buffering nếu semantics cho phép.
- Database materialization cũng có thể chiếm phần lớn memory; chỉ sửa response buffer chưa chắc đủ.
- Bounded concurrency/backpressure cho export lớn có thể quan trọng hơn micro-optimization allocation.
- Có thể cân nhắc asynchronous job + Blob Storage/direct download cho export rất lớn nếu UX/requirements phù hợp.
- Nếu dùng pooled buffers phải quản lý ownership/lifetime cẩn thận; pooling không tự động giảm peak live data.

### Senior+

- Phân biệt GC heap size, committed memory, working set, native allocations và fragmentation thay vì dùng một metric làm bằng chứng.
- Đưa ra memory budget theo worst-case concurrency và container/App Service limits.
- Xem xét cancellation khi client disconnect để tránh tiếp tục tạo file lớn không còn người nhận.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng `GC.Collect()`. Trước tiên dựng allocation path. Với code serialize vào `MemoryStream` rồi `ToArray()`, ít nhất có buffer nội bộ của stream và array kết quả cùng tồn tại ở một thời điểm; buffer stream còn có thể đã grow qua nhiều lần allocation. Nếu trước đó dữ liệu database đã được materialize thành object graph lớn, live set còn cao hơn.

Các array lớn đi vào large-object allocation regime. Khi request kết thúc và references biến mất, GC có thể reclaim chúng theo collection behavior của runtime, nhưng process working set không phải phép đo trực tiếp số managed objects đang live. Runtime có thể giữ committed memory để tái sử dụng; working set còn bao gồm code, native/runtime state và những vùng khác. Vì vậy `GC.GetTotalMemory(false)` thấp hơn working set không chứng minh native leak.

Tôi sẽ thu evidence bằng runtime counters/traces phù hợp: GC heap size, allocation rate, Gen 2/GC frequency, LOH size, pause time, process working set/private bytes, request concurrency và payload sizes. Khi cần, capture dump/GC dump ở nhiều thời điểm và so sánh retained object graph; leak thực sự cần evidence rằng objects không mong muốn vẫn bị root/retained qua thời gian.

Nếu endpoint không cần full buffer, ưu tiên stream serialization ra `HttpResponse.Body`/response stream. Dữ liệu từ DB cũng nên projection và xử lý theo batch/stream khi phù hợp thay vì load toàn bộ. Cần propagate request cancellation để dừng DB/serialization khi client disconnect.

Ví dụ về direction, không phải implementation duy nhất:

```csharp
[HttpGet("exports/{customerId:guid}")]
public async Task Export(Guid customerId, CancellationToken ct)
{
    Response.ContentType = "application/json";

    await using var writer = new Utf8JsonWriter(Response.BodyWriter);
    writer.WriteStartArray();

    await foreach (var item in _service.StreamExportRows(customerId, ct))
    {
        JsonSerializer.Serialize(writer, item);
        await writer.FlushAsync(ct);
    }

    writer.WriteEndArray();
    await writer.FlushAsync(ct);
}
```

Implementation thực tế cần verify API semantics/version và error behavior: nếu response đã bắt đầu rồi mới lỗi, không thể đơn giản đổi status code như trước. Có thể cần export background job ghi vào Azure Blob Storage nếu file rất lớn, cần retry/resume hoặc download nhiều lần.

Cuối cùng chạy load test với realistic payload distribution và concurrency. So sánh peak working set, GC heap, allocation rate, throughput và p95/p99 trước/sau. Nếu memory vẫn tăng vô hạn qua nhiều GC cycles và dump cho thấy retained graph, lúc đó mới điều tra leak cụ thể.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa gọi đây là leak chỉ từ working set. Với `MemoryStream` rồi `ToArray()`, một export 80 MB có thể có ít nhất hai large buffers đồng thời, chưa kể object graph từ DB và buffering khác. Khi nhiều request chạy song song, peak memory tăng rất nhanh. Các large objects có GC behavior khác small allocations, và memory đã được GC reclaim không đồng nghĩa OS working set giảm ngay.

Tôi sẽ correlate payload/concurrency với GC heap, LOH, allocation rate, Gen 2 collections, pause time và process memory; nếu cần lấy dump ở nhiều thời điểm để xem retained roots. Nếu requirement cho phép, tôi stream JSON trực tiếp ra response và stream/batch dữ liệu từ DB, đồng thời giới hạn concurrency và propagate cancellation. Với export rất lớn tôi cân nhắc background job + Blob Storage. Tôi chỉ dùng forced GC nếu có một lý do runtime rất đặc thù và đã đo được, không như cách chữa mặc định.”

## Câu hỏi đào sâu

1. Nếu streaming giảm allocation nhưng client rất chậm, backpressure và lifetime của DB resources cần xử lý thế nào?
2. Nếu product yêu cầu file phải retry/download lại nhiều lần và có checksum trước khi trả, bạn còn stream trực tiếp từ request không?
3. Sau khi tối ưu, GC heap ổn định nhưng working set vẫn tăng; bạn sẽ thu evidence nào để phân biệt runtime/native memory với OS caching hoặc managed committed memory?

## Lỗi trả lời thường gặp

- Kết luận memory leak chỉ từ Task Manager/working set.
- Gọi `GC.Collect()` sau mỗi request mà không đo tác động.
- Chỉ nói “LOH” nhưng không phân tích copies và concurrency.
- Stream response nhưng vẫn `ToListAsync()` toàn bộ dữ liệu lớn trước đó.
- Bỏ qua cancellation, client disconnect và failure sau khi response đã bắt đầu.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng RAM hoặc forced GC.
- **3–4:** Nhận ra large allocations nhưng chưa phân biệt metrics/lifetime.
- **5–6:** Phân tích đúng copies, GC/working set và đề xuất streaming có kiểm chứng.
- **7–8:** Có concurrency budget, diagnostics, cancellation và load testing.
- **9–10:** Phân tích toàn bộ memory envelope, failure semantics, operational limits và lựa chọn sync streaming vs background export theo requirements.

# Câu 2 — Azure Service Bus backlog tăng sau khi scale-out consumer

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Service Bus, distributed systems, at-least-once delivery, message lock, idempotency, retries, DLQ, SQL, observability, production troubleshooting

## Bối cảnh

Một order-processing backend nhận message từ Azure Service Bus queue. Consumer là .NET Worker Service chạy 2 instances. Bình thường queue gần như rỗng. Sau một campaign, team scale lên 8 instances để tăng throughput nhưng backlog lại tăng nhanh hơn. Dashboard cho thấy một số order được xử lý hai lần, số delivery tăng, SQL latency tăng mạnh và có message vào dead-letter queue.

Mỗi message thực hiện các bước: đọc order từ SQL Server, gọi inventory API, cập nhật database, rồi gọi email API. Processing time bình thường 2–5 giây nhưng khi inventory API chậm có thể lên tới hơn một phút. Code có retry ở HTTP client và Service Bus handler cũng có failure retry. Chưa biết lock duration, auto-lock renewal, prefetch/concurrency settings, SQL connection pool hay exact reason của DLQ.

Business yêu cầu không tạo duplicate inventory reservation và không gửi email xác nhận sai, nhưng có thể chấp nhận email trễ vài phút.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào? Hãy đưa ra competing hypotheses giải thích vì sao thêm consumers lại làm throughput xấu đi, cách thu evidence để xác minh, cách stabilize hệ thống, và thiết kế processing/idempotency/retry boundary để scale an toàn.

## Câu hỏi làm rõ nên cân nhắc

1. DLQ reason và delivery count distribution là gì; message lock có bị lost/expired không?
2. `MaxConcurrentCalls`, prefetch, lock duration/renewal và processing-time distribution hiện tại ra sao?
3. Inventory API có idempotency key hoặc query trạng thái reservation theo business key không?
4. SQL Server đang bottleneck ở connection pool, blocking/locks, CPU, I/O hay query plan?
5. Email send có nằm trong cùng retryable handler với database/inventory work không?

## Gợi ý tư duy

### Gợi ý 1

Scale consumer chỉ tăng throughput nếu downstream dependencies còn capacity. Nếu không, nó có thể tăng contention và kéo processing time vượt lock assumptions.

### Gợi ý 2

At-least-once processing nghĩa là duplicate delivery phải được coi là expected failure mode, không phải anomaly hiếm.

### Gợi ý 3

Hãy vẽ timeline một message: receive → lock → DB → inventory → DB → email → settlement. Xác định bước nào có thể thành công trước khi handler bị retry.

## Cấu trúc trả lời đề xuất

1. Xác định impact và invariants cần bảo vệ.
2. Stabilize concurrency/traffic.
3. Thu queue, lock, DLQ, dependency và DB evidence.
4. Lập competing hypotheses.
5. Reconstruct message lifecycle và duplicate timeline.
6. Thiết kế idempotency/transaction boundaries.
7. Tách retry policy theo failure class.
8. Kiểm thử failure paths/concurrency.
9. Scale lại có kiểm soát.
10. Thiết kế alerts/SLO.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định scale-out luôn tăng throughput; downstream saturation có thể làm latency/lock failures/retries tăng.
- Kiểm tra active message count, incoming/completion rate, delivery count, lock-lost behavior, DLQ reason, handler duration và dependency latency.
- Duplicate delivery phải được xử lý bằng idempotency/business invariant, không chỉ hy vọng queue không redeliver.
- Retry HTTP + retry message có thể nhân số attempts; phải xác định retry budget và operation nào an toàn để retry.
- Inventory reservation cần idempotency boundary; duplicate message không được tạo reservation mới.
- Email không nên khiến toàn bộ business transaction bị replay nếu email send fail sau khi order đã commit.
- SQL contention/connection saturation cần evidence trước khi tăng pool hoặc instances.

### Điểm cộng

- Giảm consumer concurrency tạm thời có thể cải thiện throughput tổng nếu downstream đang quá tải.
- Phân biệt transient failure, permanent/business failure và poison message; DLQ cần operational workflow.
- Inbox/idempotency record với unique business/message key có thể bảo vệ consumer-side duplicate processing, nhưng transaction boundary với side effects bên ngoài phải được thiết kế rõ.
- Outbox có thể tách durable business state change khỏi email notification publish/send.
- Auto-lock renewal giúp long processing nhưng không thay thế idempotency; process crash vẫn có thể gây redelivery.
- Đo SQL waits/blocking/query duration/connection pool trước khi tune.

### Senior+

- Phân tích “exactly once business effect” như invariant được xây từ idempotency + durable state, không dựa vào transport guarantee đơn thuần.
- Thiết kế backpressure/concurrency theo capacity downstream.
- Xử lý ambiguity khi external inventory call timeout: request có thể đã thành công ở remote side dù caller không nhận response.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng invariants: một order không được reserve inventory hai lần; state transition phải idempotent; email có thể trễ nên không cần giữ critical order path chỉ để retry email.

Để stabilize, nếu campaign vẫn đang diễn ra và SQL/inventory đang saturated, tôi có thể giảm `MaxConcurrentCalls` hoặc số replicas về mức downstream chịu được thay vì scale tiếp. Đồng thời tránh thay đổi nhiều knobs cùng lúc.

Evidence cần correlate theo thời gian: queue active/incoming/completed rate, delivery count, lock-lost/abandon/dead-letter, DLQ reason, handler p95/p99, inventory latency/error/timeout, SQL dependency latency, waits/blocking, connection usage và CPU. Nếu handler p99 vượt lock/renewal behavior hoặc process bị starved, redelivery là một hypothesis. Nếu SQL latency tăng ngay theo concurrency, contention/downstream saturation là hypothesis khác. Nếu inventory 429/5xx tăng, scale consumer đang đẩy quá tải downstream.

Với duplicate semantics, handler phải có durable idempotency. Ví dụ một inbox/processed-message record hoặc order-operation key có unique constraint có thể ngăn cùng logical command commit hai lần. Nhưng điều này chưa tự giải quyết external inventory side effect. Inventory API nên hỗ trợ idempotency key theo `OrderId`/reservation operation nếu contract cho phép. Nếu timeout xảy ra, consumer cần khả năng reconcile/query reservation state trước khi tạo lại, vì timeout không chứng minh remote side thất bại.

Tôi không để email API nằm như side effect cuối cùng khiến toàn message replay sau khi order/inventory đã thành công. Một design phù hợp là commit order state và durable outbox event trong cùng local DB transaction; publisher/worker gửi notification sau. Email consumer cũng idempotent theo notification key. Outbox không tạo distributed transaction với inventory API, nên workflow vẫn cần state machine/reconciliation cho external reservation.

Retry cần phân lớp. Network transient có bounded exponential backoff/jitter; validation/business failure không retry vô hạn; throttling phải tôn trọng capacity; poison messages đi DLQ với reason/context phù hợp. HTTP retry × message retry phải có total retry budget để tránh retry storm.

Sau fix, chạy integration/failure tests: duplicate delivery cùng lúc trên nhiều consumers; inventory timeout-after-success; DB commit success rồi process crash trước message settlement; email outage; lock expiration/renewal; SQL slowdown; poison payload. Sau đó tăng concurrency từng bước và quan sát completed/sec thay vì chỉ CPU.

Production alerts nên có queue age/backlog, completion rate, delivery-count distribution, DLQ rate/reason, lock-lost count, handler p95/p99, idempotency conflicts, inventory timeout/throttle, SQL waits/latency và notification outbox age.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không scale tiếp chỉ vì backlog tăng. Tám consumers có thể đang saturate SQL hoặc inventory, làm handler chậm, lock/retry tăng và throughput thực tế giảm. Tôi sẽ stabilize bằng cách đưa concurrency về mức đã biết an toàn, rồi correlate queue completion rate, delivery count, lock failures, DLQ reason, handler p99, inventory latency và SQL waits.

Tôi coi duplicate delivery là bình thường với at-least-once semantics. Consumer cần durable idempotency; inventory reservation cần business/idempotency key hoặc reconciliation vì timeout có thể xảy ra sau khi remote side đã reserve thành công. Tôi cũng tách email khỏi critical handler bằng durable outbox nếu architecture phù hợp, để email outage không replay order processing.

Cuối cùng tôi rationalize retry budget vì HTTP retry nhân với message retry có thể tạo retry storm. Tôi test duplicate concurrent delivery, timeout-after-success, crash-before-settlement và dependency slowdown, rồi scale concurrency từng bước dựa trên completed/sec và downstream saturation.”

## Câu hỏi đào sâu

1. Nếu inventory API không hỗ trợ idempotency key và cũng không có endpoint query reservation theo order, bạn thay đổi integration contract hoặc workflow thế nào?
2. Nếu auto-lock renewal loại bỏ phần lớn lock expiry nhưng duplicate vẫn xảy ra khi process crash sau DB commit, bạn còn cần inbox/idempotency không?
3. Nếu SQL là bottleneck nhưng business yêu cầu xử lý campaign nhanh gấp 5 lần, bạn sẽ chứng minh bottleneck và chọn tối ưu query/index, partition workload hay thay đổi architecture dựa trên tiêu chí nào?

## Lỗi trả lời thường gặp

- Scale từ 8 lên 20 consumers mà không đo downstream capacity.
- Tăng lock duration rồi coi duplicate đã được giải quyết.
- Retry mọi exception giống nhau.
- Dùng distributed lock như câu trả lời mặc định nhưng không có durable business idempotency.
- Để email failure replay inventory/order side effects.

## Thang điểm 0–10

- **0–2:** Chỉ scale thêm hoặc tăng timeout.
- **3–4:** Nhận ra lock/retry nhưng chưa bảo vệ business side effects.
- **5–6:** Có evidence-driven incident flow, idempotency và retry classification.
- **7–8:** Xử lý timeout ambiguity, outbox/inbox boundaries, DB capacity và failure tests.
- **9–10:** Thiết kế end-to-end business-effect correctness, backpressure và operational scaling dựa trên measured bottlenecks/trade-offs.

# Câu 3 — Hiện đại hóa .NET Framework 4.5 mà không biến migration thành rewrite nhiều năm

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, ASP.NET, architecture boundaries, migration strategy, compatibility, IIS/App Service, database, CI/CD, testing, rollout, rollback, technical debt

## Bối cảnh

Một internal enterprise platform đã chạy khoảng 8 năm trên .NET Framework 4.5, ASP.NET MVC, IIS và SQL Server. Hệ thống có khoảng 60 modules trong một solution, dùng một số NuGet packages cũ, Windows authentication cho intranet, scheduled jobs chạy trong web application và nhiều stored procedures. Frontend có jQuery và một phần Angular cũ.

Business vẫn phát triển feature mới mỗi sprint. Downtime cho migration bị giới hạn; team 7 developers không thể dừng roadmap 12 tháng để rewrite. Một số modules thay đổi thường xuyên, một số gần như ổn định. Production incidents hiện khó điều tra vì logging không đồng nhất và integration tests rất ít.

Có ba đề xuất:

1. rewrite toàn bộ sang .NET 10 + React + microservices;
2. nâng trực tiếp toàn solution trong một big-bang release;
3. tiếp tục .NET Framework thêm vài năm vì “hệ thống vẫn chạy”.

Chưa có dependency inventory, compatibility matrix hay baseline test coverage đủ tin cậy.

## Câu hỏi chính

Hãy đề xuất modernization strategy thực tế. Bạn sẽ khám phá dependency/risk, chọn migration boundaries, xử lý authentication/jobs/database/frontend, xây compatibility và rollout/rollback như thế nào để vừa giảm rủi ro vừa tiếp tục delivery? Trong trường hợp nào bạn sẽ giữ một phần legacy lâu hơn thay vì ép migrate ngay?

## Câu hỏi làm rõ nên cân nhắc

1. Những packages/framework APIs nào không có đường nâng cấp hoặc replacement tương thích trên modern .NET?
2. Modules nào có business value/change frequency cao, coupling thấp và production pain lớn nhất?
3. Windows authentication là requirement bắt buộc hay có roadmap sang Microsoft Entra ID/identity khác?
4. Database schema/stored procedures được share chặt giữa modules đến mức nào?
5. Deployment topology, downtime budget và rollback SLA cụ thể là gì?

## Gợi ý tư duy

### Gợi ý 1

Migration plan tốt bắt đầu bằng inventory và seams, không bắt đầu bằng target framework version.

### Gợi ý 2

Tách **runtime modernization**, **architecture decomposition** và **frontend rewrite** thành các quyết định có thể độc lập.

### Gợi ý 3

Một strangler/incremental path chỉ an toàn nếu old/new versions có contract, data ownership, routing và observability đủ rõ.

## Cấu trúc trả lời đề xuất

1. Inventory và baseline hiện trạng.
2. Phân loại dependencies/coupling/risk.
3. Chọn target architecture tối thiểu cần thiết.
4. Xác định migration slices và compatibility seams.
5. Thiết kế auth, jobs, DB và frontend transition.
6. Xây characterization/integration tests.
7. Thiết kế CI/CD, canary/parallel/rollback.
8. Thêm observability trước và trong migration.
9. Định nghĩa exit criteria cho từng slice.
10. Nêu điều kiện để giữ legacy hoặc tách service.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn rewrite toàn bộ chỉ vì target stack hiện đại hơn.
- Trước migration cần inventory packages, framework APIs, IIS/Windows dependencies, configuration, background jobs, DB coupling và external integrations.
- Characterization/integration tests bảo vệ behavior hiện tại trước refactor lớn.
- Tách runtime upgrade khỏi microservices/frontend rewrite để giảm simultaneous variables.
- Chọn vertical/module slices dựa trên value, change frequency, coupling và migration risk.
- Old/new phải có compatibility strategy cho API/data/schema/authentication.
- Database changes cần backward-compatible rollout khi old/new versions cùng tồn tại.
- Rollback phải được thiết kế trước release, không chỉ “redeploy bản cũ”.

### Điểm cộng

- Có thể tạo modern .NET boundary/API cho module phù hợp trong khi legacy vẫn chạy, nhưng không tách service nếu boundary/data ownership không rõ.
- Scheduled jobs không nên tiếp tục phụ thuộc vô thức vào web-process lifecycle; có thể chuyển dần sang Worker Service/Functions nếu operational requirements phù hợp.
- Frontend jQuery/Angular có thể modernize theo route/component thay vì bắt buộc rewrite đồng thời backend.
- Authentication migration cần coexistence/token/session strategy rõ nếu old/new apps chạy song song.
- Observability baseline trước migration giúp phân biệt regression do migration với vấn đề cũ.

### Senior+

- Dùng risk-based sequencing: observability/test seams trước, low-risk representative slice tiếp theo, rồi mới modules khó.
- Định nghĩa ownership boundary trước khi microservice extraction; shared database có thể là transitional state nhưng cần kế hoạch giảm coupling nếu tách deployables.
- Đưa ra stop/go criteria dựa trên defect rate, latency, operational burden và delivery velocity.
- Chấp nhận để stable low-change legacy module tồn tại tạm thời nếu cost/risk migrate cao hơn value, nhưng phải quản lý security/support risk có thời hạn.

## Hướng giải quyết tham khảo

Tôi coi đây là chương trình risk reduction, không phải một project rewrite. Bước đầu là discovery có thời hạn: dependency inventory, target-framework compatibility, custom IIS/Windows APIs, authentication, scheduled jobs, package support, config/secrets, external integrations, DB/stored procedures và deployment pipeline. Đồng thời đo production baseline và bổ sung structured logging/correlation ở những đường critical.

Tiếp theo tạo characterization tests cho business flows quan trọng và integration tests quanh DB/external boundaries. Không cần đạt 100% coverage trước khi bắt đầu; cần coverage đủ để phát hiện regression ở slice sắp migrate.

Tôi phân modules theo change frequency, business criticality, coupling và technical pain. Slice đầu nên đủ representative nhưng không phải module nguy hiểm nhất. Nếu một module có boundary rõ và ít shared-state coupling, có thể đưa nó sang modern .NET trước. Nếu toàn hệ thống quá coupled, có thể cần modularize/seam creation trong legacy trước khi extraction.

Tôi không gắn ba cuộc migration thành một: runtime/backend, frontend và microservices. Có thể giữ UI cũ gọi endpoint mới, hoặc modernize frontend theo route trong khi backend vẫn tương thích. Microservices chỉ xuất hiện khi independent deployment/scaling/team ownership/failure isolation thực sự có lợi; Modular Monolith hoặc vài deployables có thể đủ.

Database là điểm khó. Khi old/new cùng chạy, schema migration nên ưu tiên expand/contract: thêm schema mới tương thích, deploy code đọc/ghi theo transition plan, backfill có quan sát, chuyển traffic, rồi chỉ cleanup khi old version không còn cần. Stored procedures được inventory như contracts; không rewrite tất cả chỉ để đạt “pure EF Core”.

Authentication cần proof-of-concept sớm nếu Windows auth là dependency sâu. Nếu business vẫn cần intranet Windows authentication, target hosting phải hỗ trợ requirement đó hoặc có bridge phù hợp. Nếu chuyển sang Entra ID, cần thiết kế coexistence và authorization mapping thay vì đổi identity cùng lúc với mọi module.

Jobs đang chạy trong web app cần inventory về schedule, idempotency, overlap và recovery. Những job critical có thể được chuyển sang Worker Service/Functions khi semantics phù hợp, nhưng đây là migration riêng với monitoring/retry/duplicate-execution design.

Release theo slice: route một phần traffic/use case sang modern component, health/smoke/integration checks, metrics so sánh old/new và rollback path. Nếu data migration destructive, rollback binary có thể không đủ; vì vậy schema compatibility là điều kiện release.

Tôi sẽ giữ một legacy module ổn định lâu hơn nếu nó ít thay đổi, boundary khó, migration risk cao và runtime/support/security risk vẫn được kiểm soát trong thời gian xác định. Ngược lại, dependency hết support hoặc security exposure có thể nâng priority dù business change thấp.

Cuối cùng, modernization success không chỉ là % code trên .NET mới. Tôi đo lead time, deployment failure rate, incident rate, p95/p99, test confidence, supportability và số legacy dependencies đã loại bỏ. Nếu decomposition làm velocity giảm mà không mang operational value, tôi điều chỉnh thay vì tiếp tục theo architecture target cứng nhắc.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn rewrite hay big-bang trước khi có dependency inventory. Tôi tách runtime modernization, frontend modernization và service decomposition thành ba quyết định. Đầu tiên tôi inventory packages, Windows/IIS dependencies, auth, jobs, DB/stored procedures và integrations; thêm characterization tests và observability cho critical flows.

Sau đó tôi chọn migration slices theo value, change frequency, coupling và risk. Old/new cần coexist, nên schema/API/auth phải backward-compatible; database thường dùng expand/contract thay vì destructive migration sớm. Jobs trong web process được đánh giá riêng và chuyển sang Worker/Functions nếu semantics phù hợp. Frontend có thể migrate theo route thay vì rewrite cùng backend.

Tôi chỉ tách microservice khi boundary/data ownership và independent deployment thực sự có giá trị. Một stable module ít thay đổi có thể ở legacy lâu hơn nếu migration risk cao, miễn support/security risk được quản lý. Mỗi slice phải có tests, telemetry, rollout và rollback rõ. Tôi đo success bằng reliability và delivery velocity, không chỉ số project đã target modern .NET.”

## Câu hỏi đào sâu

1. Nếu một module boundary rõ nhưng vẫn ghi trực tiếp vào 20 bảng dùng chung với legacy, bạn có tách nó thành microservice ngay không? Vì sao?
2. Nếu security policy buộc phải rời .NET Framework trong 6 tháng nhưng test coverage gần như bằng 0, bạn thay đổi sequencing và risk controls thế nào?
3. Nếu team đã migrate 40% nhưng delivery velocity giảm mạnh vì dual-running complexity, bạn dùng tiêu chí nào để tiếp tục, hợp nhất lại hoặc thay đổi chiến lược?

## Lỗi trả lời thường gặp

- Đồng nhất modernization với rewrite sang microservices.
- Upgrade runtime, auth, database, frontend và hosting trong cùng một big-bang release.
- Bỏ qua characterization tests vì “legacy code không test được”.
- Tách service nhưng vẫn share database không có ownership/contract, chỉ chuyển distributed coupling sang network.
- Không thiết kế rollback khi schema/data đã thay đổi.

## Thang điểm 0–10

- **0–2:** Chọn rewrite/big-bang mà không có risk analysis.
- **3–4:** Có phased migration nhưng thiếu compatibility/testing/rollback.
- **5–6:** Có inventory, slicing, characterization tests và coexistence strategy.
- **7–8:** Xử lý auth/jobs/DB/frontend độc lập, observability và release safety tốt.
- **9–10:** Đưa ra risk-based modernization portfolio, explicit stop/go criteria, cost-of-complexity reasoning và chấp nhận giữ legacy có kiểm soát khi đó là quyết định tốt hơn.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory performance phải được phân tích bằng allocation path, live-set/concurrency và đúng metric; working set tăng không tự động đồng nghĩa managed memory leak.
- Large payload buffering tạo amplification qua nhiều copies; streaming và bounded concurrency thường quan trọng hơn forced GC.
- Message transport at-least-once yêu cầu business idempotency; lock/renewal không tạo exactly-once business effect.
- Scale-out consumer có thể giảm throughput nếu downstream dependencies bị saturated và retries khuếch đại tải.
- Modernization nên tách runtime, architecture và frontend decisions; incremental compatibility/rollback thường quan trọng hơn target architecture “đẹp”.

## Mẫu tư duy cần nhớ

- **Measure allocation and retention before calling something a leak.**
- **Scale against downstream capacity, not queue depth alone.**
- **Design retry together with idempotency and ambiguous outcomes.**
- **Separate modernization concerns to reduce simultaneous risk.**
- **Prefer reversible migration steps and explicit compatibility windows.**
