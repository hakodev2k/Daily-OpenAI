# Code Review Challenge 1 — Job đồng bộ lịch bị chạy lặp và ghi đè trạng thái

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để đồng bộ thay đổi thời gian sự kiện sang hệ thống lịch bên ngoài. Khi admin cập nhật một sự kiện, API enqueue job. Trong production có nhiều web instance và nhiều Hangfire worker. Nhà cung cấp bên ngoài đôi lúc timeout sau khi đã nhận request.

Gần đây xuất hiện các triệu chứng: một số sự kiện được gửi nhiều lần; một số bản ghi được đánh dấu `Synced` dù lần chạy khác vừa thất bại; khi provider chậm, số job retry tăng mạnh; support khó xác định một thay đổi đã được gửi bao nhiêu lần.

Yêu cầu nghiệp vụ chưa nói rõ provider có hỗ trợ idempotency key hay version/ETag hay không.

## Đoạn code cần review

```csharp
public sealed class CalendarSyncJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _httpClient;
    private readonly ILogger<CalendarSyncJob> _logger;

    public CalendarSyncJob(
        AppDbContext db,
        HttpClient httpClient,
        ILogger<CalendarSyncJob> logger)
    {
        _db = db;
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid eventId)
    {
        var item = await _db.Events.SingleAsync(x => x.Id == eventId);

        if (item.SyncStatus == "Synced")
            return;

        try
        {
            var response = await _httpClient.PutAsJsonAsync(
                $"/calendar/events/{item.ExternalId}",
                new
                {
                    item.Title,
                    item.StartTime,
                    item.EndTime
                });

            response.EnsureSuccessStatusCode();

            item.SyncStatus = "Synced";
            item.LastSyncedAt = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            item.SyncStatus = "Failed";
            item.LastError = ex.ToString();
            await _db.SaveChangesAsync();

            _logger.LogError(ex,
                "Calendar sync failed for event {@Event}", item);

            throw;
        }
    }
}
```

## Câu hỏi gợi mở

- Hai worker có thể cùng đọc `SyncStatus != Synced` không?
- Timeout có chứng minh provider chưa xử lý request không?
- `Failed` và `Synced` có phản ánh đúng trạng thái khi nhiều execution cùng tồn tại không?
- Job đang đồng bộ “event hiện tại” hay một version cụ thể của thay đổi?

## Kết quả code review tham khảo

### 1. Check-then-act không bảo vệ khỏi concurrent workers

**Problem:** Hai worker có thể cùng đọc trạng thái chưa sync rồi cùng gọi provider.  
**Why:** Việc đọc và quyết định không có optimistic/pessimistic concurrency protocol.  
**Production impact:** Duplicate side effect; trạng thái cuối phụ thuộc thứ tự completion.  
**Severity:** Critical  
**Recommended fix:** Thiết kế idempotency theo operation/version và dùng database constraint/concurrency token để claim operation an toàn.

### 2. Retry sau timeout có thể lặp side effect

**Problem:** Timeout không cho biết request có được provider commit hay chưa.  
**Why:** Failure xảy ra tại client boundary nhưng remote side effect có thể đã thành công.  
**Production impact:** Retry tạo duplicate update/notification nếu remote operation không idempotent.  
**Severity:** Critical  
**Recommended fix:** Nếu provider hỗ trợ, gửi stable idempotency key hoặc conditional/versioned update. Nếu không, thiết kế reconciliation/read-after-failure phù hợp với API của provider.

### 3. Chỉ dùng `eventId` làm input khiến job mất version semantics

**Problem:** Job enqueue cho version A nhưng lúc chạy lại đọc dữ liệu version B.  
**Why:** Payload của operation không được snapshot/version hóa.  
**Production impact:** Khó audit; retry của thay đổi cũ có thể gửi trạng thái mới ngoài ý định.  
**Severity:** High  
**Recommended fix:** Tạo `SyncOperation` có operation ID, event ID, version và payload/version reference rõ ràng.

### 4. Race giữa `Synced` và `Failed`

**Problem:** Execution thất bại có thể ghi `Failed` sau khi execution khác đã thành công.  
**Why:** Các execution cập nhật cùng entity mà không kiểm tra version/state transition.  
**Production impact:** Database báo failed dù remote state đã đúng, dẫn đến retry không cần thiết.  
**Severity:** High  
**Recommended fix:** State transition có điều kiện và optimistic concurrency; tốt hơn là trạng thái theo từng sync operation.

### 5. Catch mọi exception rồi retry như nhau

**Problem:** Permanent failure như validation/4xx có thể bị retry giống transient failure.  
**Why:** Không phân loại lỗi.  
**Production impact:** Retry storm, tăng tải provider và queue backlog.  
**Severity:** High  
**Recommended fix:** Phân loại transient/permanent; policy retry có backoff/jitter và giới hạn phù hợp.

### 6. Không truyền cancellation token

**Problem:** Database và HTTP operation không nhận cancellation.  
**Why:** Method không expose token.  
**Production impact:** Shutdown hoặc cancellation không dừng I/O kịp thời.  
**Severity:** Medium  
**Recommended fix:** Truyền `CancellationToken` xuyên suốt khi execution environment hỗ trợ.

### 7. Lưu `ex.ToString()` trực tiếp vào entity

**Problem:** Stack trace có thể quá dài hoặc chứa chi tiết không nên lưu lâu dài.  
**Why:** Persistence model bị dùng như log store.  
**Production impact:** Database phình, rủi ro lộ thông tin nội bộ.  
**Severity:** Medium  
**Recommended fix:** Lưu error code/category và correlation ID; chi tiết exception ở hệ thống logging có retention/access control phù hợp.

### 8. Structured logging toàn bộ entity

**Problem:** `{@Event}` serialize object có thể chứa dữ liệu không cần thiết hoặc nhạy cảm.  
**Why:** Destructuring toàn entity.  
**Production impact:** Log volume lớn, dữ liệu nghiệp vụ xuất hiện trong log.  
**Severity:** Medium  
**Recommended fix:** Log identifiers, operation/version, attempt và provider status có chủ đích.

### 9. Không có explicit timeout/resilience semantics trong đoạn code

**Problem:** Không thấy timeout budget và policy theo loại failure.  
**Why:** Chỉ dựa vào cấu hình HttpClient bên ngoài hoặc mặc định.  
**Production impact:** Worker bị giữ lâu, throughput giảm khi dependency suy yếu.  
**Severity:** Medium  
**Recommended fix:** Định nghĩa timeout budget, retry policy phù hợp và telemetry; không retry mù các unsafe side effects.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định provider hỗ trợ idempotency key. Operation được tạo trước khi enqueue và có `Version` làm concurrency token.

```csharp
public sealed class CalendarSyncJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _client;
    private readonly ILogger<CalendarSyncJob> _logger;

    public CalendarSyncJob(
        AppDbContext db,
        HttpClient client,
        ILogger<CalendarSyncJob> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid operationId, CancellationToken ct)
    {
        var op = await _db.CalendarSyncOperations
            .SingleAsync(x => x.Id == operationId, ct);

        if (op.Status == SyncOperationStatus.Completed)
            return;

        var request = new HttpRequestMessage(
            HttpMethod.Put,
            $"/calendar/events/{Uri.EscapeDataString(op.ExternalId)}")
        {
            Content = JsonContent.Create(new
            {
                op.Title,
                op.StartTime,
                op.EndTime
            })
        };

        request.Headers.TryAddWithoutValidation(
            "Idempotency-Key", op.Id.ToString("N"));

        try
        {
            using var response = await _client.SendAsync(request, ct);

            if ((int)response.StatusCode >= 500)
                throw new HttpRequestException(
                    $"Provider returned {(int)response.StatusCode}");

            if (!response.IsSuccessStatusCode)
            {
                op.Status = SyncOperationStatus.PermanentFailure;
                op.ErrorCode = $"HTTP_{(int)response.StatusCode}";
                await _db.SaveChangesAsync(ct);
                return;
            }

            op.Status = SyncOperationStatus.Completed;
            op.CompletedAtUtc = DateTime.UtcNow;
            op.ErrorCode = null;
            await _db.SaveChangesAsync(ct);
        }
        catch (DbUpdateConcurrencyException)
        {
            _logger.LogInformation(
                "Sync operation {OperationId} was updated concurrently",
                operationId);
            throw;
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogWarning(ex,
                "Transient calendar sync failure. OperationId={OperationId}",
                operationId);
            throw;
        }
    }
}
```

Điểm quan trọng không phải tên header cụ thể; capability này phải được xác nhận từ provider. Nếu provider không hỗ trợ idempotency key, cần reconciliation hoặc conditional update dựa trên capability thực tế thay vì giả định.

## Trade-offs

Operation table tăng storage và complexity nhưng tạo audit trail, version semantics và retry safety tốt hơn. Distributed lock có thể giảm concurrent execution nhưng không giải quyết được ambiguous HTTP failure sau khi remote side effect đã xảy ra. Vì vậy lock không thay thế idempotency.

Snapshot payload giúp retry đúng operation ban đầu nhưng cần chính sách dữ liệu và migration. Reference tới version hiện tại tiết kiệm storage hơn nhưng semantics khác.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời nhiều execution cùng `operationId`; remote fake phải quan sát cùng idempotency key và logical side effect chỉ xảy ra một lần.
2. **Ambiguous timeout test:** fake provider commit rồi client nhận timeout; retry phải không tạo logical duplicate.
3. **Permanent failure test:** provider trả 400; operation chuyển permanent failure và không bị retry vô hạn.
4. **Version race test:** cập nhật event nhiều lần nhanh; từng operation phải có semantics rõ ràng và không ghi đè trạng thái sai.
5. **Cancellation/failure test:** cancel giữa HTTP/database I/O; trạng thái phải có thể retry/reconcile mà không giả định remote chưa commit.

## Quan sát trong production

Theo dõi `sync_attempt_total`, `sync_completed_total`, `sync_retry_total`, `sync_permanent_failure_total`, queue age, duration và provider status code. Log `OperationId`, `EventId`, version, attempt và correlation/trace ID. Distributed trace nên tách span database và outbound HTTP. Alert khi retry ratio, queue age hoặc permanent failure vượt baseline. Có dashboard/reconciliation cho operation bị treo ở trạng thái chưa xác định.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider hoàn toàn không hỗ trợ idempotency hoặc conditional update, bạn thiết kế recovery thế nào?
2. Distributed lock có giải quyết duplicate side effect không? Hãy nêu một failure sequence chứng minh câu trả lời.
3. Nếu có 100.000 event update/phút, operation table và cleanup strategy cần thay đổi thế nào?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa có nguy cơ lộ dữ liệu

**Chủ đề:** SQL/EF Core performance, authorization, input handling, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 8–9 vấn đề

## Bối cảnh

Portal nội bộ có endpoint cho support tìm audit log theo tenant và từ khóa. Bảng `AuditLogs` đã tăng lên hàng chục triệu dòng. Người dùng support thuộc nhiều tenant khác nhau; một số role chỉ được xem metadata, không được xem payload chứa dữ liệu chi tiết.

Production ghi nhận memory spike khi search từ khóa phổ biến, latency tăng theo kích thước bảng, và security review nghi ngờ endpoint có thể trả dữ liệu vượt phạm vi tenant. Chưa rõ database hiện có index nào ngoài primary key.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        int page = 1,
        int pageSize = 1000)
    {
        _logger.LogInformation(
            "Searching audit logs tenant={TenantId}, keyword={Keyword}",
            tenantId, keyword);

        var logs = await _db.AuditLogs
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        var result = logs
            .Where(x => x.TenantId == tenantId)
            .Where(x => string.IsNullOrEmpty(keyword) ||
                        x.Message.Contains(keyword,
                            StringComparison.OrdinalIgnoreCase))
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.CreatedAt,
                x.UserEmail,
                x.Message,
                x.RequestPayload,
                x.ResponsePayload
            })
            .ToList();

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Tenant scope lấy trực tiếp từ user input mà không chứng minh authorization

**Problem:** Caller có thể truyền tenant khác nếu authorization layer không kiểm tra tương ứng.  
**Why:** Data filter dựa vào request parameter, không dựa trên trusted tenant context/authorization decision.  
**Production impact:** Cross-tenant data exposure.  
**Severity:** Critical  
**Recommended fix:** Resolve allowed tenant từ authenticated principal/policy hoặc kiểm tra quyền explicit trước khi query.

### 2. Trả payload nhạy cảm cho mọi caller

**Problem:** Projection luôn chứa request/response payload và email.  
**Why:** Không có field-level authorization/data minimization.  
**Production impact:** Lộ PII, token hoặc business data nếu payload chứa chúng.  
**Severity:** Critical  
**Recommended fix:** DTO theo quyền; mặc định metadata-only, endpoint/detail permission riêng cho payload; redact dữ liệu nhạy cảm từ lúc ghi log nếu có thể.

### 3. Materialize toàn bộ bảng trước khi filter

**Problem:** `ToListAsync()` tải tất cả audit rows vào application memory.  
**Why:** Filter/paging sau đó là LINQ-to-Objects.  
**Production impact:** Memory spike, GC pressure, database/network I/O cực lớn, latency tăng theo bảng.  
**Severity:** High  
**Recommended fix:** Giữ query ở `IQueryable`, filter/projection/paging trước `ToListAsync`.

### 4. `pageSize` không giới hạn

**Problem:** Caller có thể yêu cầu kích thước rất lớn hoặc giá trị không hợp lệ.  
**Why:** Không validate bounds.  
**Production impact:** Response lớn, memory/network pressure, abuse/DoS amplification.  
**Severity:** High  
**Recommended fix:** Validate `page >= 1`, clamp/reject `pageSize` theo giới hạn có chủ đích.

### 5. Pagination không có deterministic tie-breaker

**Problem:** Chỉ sort `CreatedAt`; nhiều row cùng timestamp có thể đổi thứ tự giữa requests.  
**Why:** Order không total/deterministic.  
**Production impact:** Duplicate/missing rows giữa các page.  
**Severity:** Medium  
**Recommended fix:** Sort thêm unique key, ví dụ `CreatedAt DESC, Id DESC`; với deep paging cân nhắc keyset pagination.

### 6. Offset pagination xuống cấp khi page sâu

**Problem:** `Skip` lớn có thể tốn chi phí database đáng kể.  
**Why:** Database vẫn phải định vị/bỏ qua nhiều rows theo execution plan.  
**Production impact:** Latency tăng cho deep page.  
**Severity:** Medium  
**Recommended fix:** Keyset/cursor pagination nếu UX không cần random page jumps.

### 7. Substring/case-insensitive search chưa có database search strategy

**Problem:** Implementation hiện tại search in-memory; chuyển thẳng sang SQL cũng chưa đảm bảo scalable.  
**Why:** `%keyword%`/case-insensitive semantics phụ thuộc provider/collation và thường không tận dụng B-tree index như prefix/equality search.  
**Production impact:** Scan lớn trên bảng audit.  
**Severity:** Medium  
**Recommended fix:** Xác định requirement tìm kiếm; dùng capability phù hợp của SQL Server/PostgreSQL như full-text/search index chuyên dụng khi cần, và đo execution plan thực tế.

### 8. Logging raw keyword có thể ghi dữ liệu nhạy cảm

**Problem:** Search term được ghi nguyên văn.  
**Why:** User có thể tìm email/token/nội dung nhạy cảm.  
**Production impact:** Sensitive data bị nhân bản sang log platform.  
**Severity:** Medium  
**Recommended fix:** Log metadata như keyword-present/length/hash khi cần, không log raw search term mặc định.

### 9. Read-only query không dùng `AsNoTracking`

**Problem:** Nếu query trả entity trước projection hoặc thay đổi projection sau này, tracking không cần thiết tạo overhead.  
**Why:** Default EF Core tracking cho entity query.  
**Production impact:** Memory/CPU overhead.  
**Severity:** Low  
**Recommended fix:** Dùng `AsNoTracking()` cho read-only query; projection trực tiếp cũng giúp giảm dữ liệu materialize.

## Phiên bản code đề xuất

Ví dụ giả định service đã resolve tenant từ identity và caller này chỉ được xem metadata. Chiến lược search cụ thể phải chọn theo database và requirement thực tế.

```csharp
[Authorize(Policy = "Audit.Read")]
[HttpGet("search")]
public async Task<ActionResult<IReadOnlyList<AuditLogListItem>>> Search(
    string? keyword,
    DateTime? beforeCreatedAt,
    long? beforeId,
    int pageSize = 100,
    CancellationToken ct = default)
{
    if (pageSize is < 1 or > 200)
        return BadRequest("pageSize must be between 1 and 200.");

    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    IQueryable<AuditLog> query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(keyword))
    {
        var term = keyword.Trim();
        query = query.Where(x => x.Message.Contains(term));
    }

    if (beforeCreatedAt.HasValue && beforeId.HasValue)
    {
        query = query.Where(x =>
            x.CreatedAt < beforeCreatedAt.Value ||
            (x.CreatedAt == beforeCreatedAt.Value && x.Id < beforeId.Value));
    }

    var result = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Select(x => new AuditLogListItem(
            x.Id,
            x.CreatedAt,
            x.Message))
        .Take(pageSize)
        .ToListAsync(ct);

    return Ok(result);
}

public sealed record AuditLogListItem(
    long Id,
    DateTime CreatedAt,
    string Message);
```

`Contains` ở ví dụ chỉ minh họa việc giữ filter trong database; không phải khẳng định đây là search strategy tối ưu. Với bảng hàng chục triệu dòng cần benchmark bằng dữ liệu thật, xem generated SQL/execution plan và chọn full-text/trigram/search service tùy SQL Server/PostgreSQL cùng yêu cầu matching.

## Trade-offs

Keyset pagination nhanh và ổn định cho “next page” nhưng không tiện nhảy trực tiếp tới page 500. Full-text hoặc search engine tăng operational complexity nhưng phù hợp hơn nếu requirement là substring/fuzzy search quy mô lớn. Projection metadata-only tăng an toàn; nếu support thực sự cần payload, nên có permission riêng, audit việc truy cập và redaction thay vì mở mặc định.

Composite index thường bắt đầu từ tenant/filter/order columns, nhưng index chính xác phải dựa trên workload và execution plan; không nên đưa một index “chuẩn” mà chưa biết schema, selectivity và database provider.

## Cách kiểm thử

1. **Security test:** user tenant A yêu cầu hoặc cố truy cập dữ liệu tenant B; không row nào được trả.
2. **Authorization test:** role metadata-only không thể lấy payload; role đặc quyền được kiểm tra qua policy riêng nếu feature đó tồn tại.
3. **Database integration test:** xác nhận filter/paging được translate thành SQL và số row materialize bị giới hạn.
4. **Pagination concurrency test:** insert thêm audit rows giữa hai page; cursor không gây duplicate/missing trong semantics đã định nghĩa.
5. **Load test:** dữ liệu production-like với từ khóa phổ biến; đo p95/p99, DB CPU, logical reads/execution plan và allocation phía API.

## Quan sát trong production

Theo dõi request duration theo endpoint, result count, page size, timeout/error rate và DB command duration. Trace outbound không cần thiết ở endpoint này nhưng database span/query timing rất quan trọng. Theo dõi slow query, execution plan, rows examined/returned và index usage bằng công cụ phù hợp của database. Security audit nên ghi user ID, tenant đã được authorize, action và số record trả về nhưng tránh raw keyword/payload.

## Câu hỏi phỏng vấn mở rộng

1. Với PostgreSQL và SQL Server, bạn sẽ đánh giá các lựa chọn search khác nhau thế nào mà không khóa architecture vào một provider?
2. Nếu product bắt buộc hỗ trợ “jump to page N”, bạn cân bằng UX và database cost ra sao?
3. Bạn sẽ thiết kế quyền xem audit payload và redaction thế nào nếu payload đôi lúc chứa access token?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào một nguyên tắc Senior quan trọng: correctness không dừng ở code chạy đúng trong happy path. Background job phải được thiết kế với delivery semantics, retry, idempotency và ambiguous failure; database state không thể tự động làm transaction với remote HTTP side effect. Với data API, authorization phải được đặt trước data access, còn filter/projection/pagination phải được đẩy xuống database thay vì materialize rồi xử lý trong memory.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; timeout không đồng nghĩa remote side effect chưa xảy ra.
- Tách rõ database boundary, queue boundary và external side-effect boundary.
- Authorization phải dựa trên trusted identity/context, không dựa đơn thuần vào tenant ID do client gửi.
- Filter → project → order → paginate → materialize; luôn biết LINQ đang chạy ở database hay memory.
- Đo execution plan, latency, allocation và failure metrics trước khi kết luận optimization.
