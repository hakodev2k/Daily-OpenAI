# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý các cấu hình offboarding đã đến hạn. Mỗi job tìm các bản ghi `Pending`, gọi Exchange Online thông qua `IMailboxService`, sau đó cập nhật trạng thái DB. Hệ thống chạy nhiều Hangfire worker trên hai instance ứng dụng. Production thỉnh thoảng ghi nhận cùng mailbox bị xử lý hai lần, một số bản ghi vẫn `Pending` dù thao tác bên ngoài đã thành công, và khi Exchange Online chậm thì backlog tăng nhanh.

Yêu cầu nghiệp vụ là thao tác phải có khả năng retry nhưng không được gây tác dụng phụ nguy hiểm nếu cùng job hoặc cùng record được xử lý nhiều lần.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IMailboxService _mailboxService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IMailboxService mailboxService,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _mailboxService = mailboxService;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task RunAsync()
    {
        var configs = await _db.MailConfigs
            .Where(x => x.Status == "Pending" && x.EndTime <= DateTime.UtcNow)
            .ToListAsync();

        foreach (var config in configs)
        {
            try
            {
                await _mailboxService.ResetMailboxAsync(config.UserEmail);

                config.Status = "Completed";
                config.CompletedAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Reset mailbox completed for {Email}", config.UserEmail);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Reset mailbox failed for {Email}", config.UserEmail);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có cơ chế claim record atomically

- **Problem:** nhiều worker có thể cùng đọc một record `Pending`.
- **Why:** query và cập nhật trạng thái là hai bước tách biệt, không có optimistic concurrency, conditional update hoặc locking/claim protocol.
- **Impact:** cùng mailbox có thể bị gọi reset nhiều lần.
- **Severity:** Critical.
- **Fix:** claim record bằng atomic conditional update (`Pending -> Processing`) và chỉ worker claim thành công mới xử lý; có thể dùng concurrency token hoặc database-specific locking khi phù hợp.

### 2. External side effect và DB state không atomic

- **Problem:** external call có thể thành công nhưng DB update thất bại.
- **Why:** không thể dùng transaction ACID thông thường bao phủ Exchange Online và relational DB.
- **Impact:** retry nhìn thấy `Pending` và lặp lại side effect.
- **Severity:** Critical.
- **Fix:** thiết kế operation idempotent, lưu operation/idempotency key và reconciliation state; external action phải có precondition/check-current-state nếu API không hỗ trợ idempotency key.

### 3. Retry toàn batch

- **Problem:** exception của một item được rethrow khiến Hangfire retry toàn method.
- **Why:** batch không có checkpoint độc lập cho từng item.
- **Impact:** các item đã hoàn tất có thể bị quét/xử lý lại; một poison item gây repeated work.
- **Severity:** High.
- **Fix:** enqueue một job riêng cho từng record hoặc persist per-item state và retry từng operation.

### 4. Không có trạng thái Processing/lease/recovery

- **Problem:** không biểu diễn ownership và thời gian claim.
- **Why:** chỉ có `Pending`/`Completed`.
- **Impact:** khó phân biệt đang chạy, crash hay chưa chạy; không có cơ chế reclaim worker chết.
- **Severity:** High.
- **Fix:** thêm `Processing`, `ClaimedAt`, `AttemptCount`, `LastError`; reclaim lease quá hạn theo policy.

### 5. Cancellation không được truyền xuống

- **Problem:** query, external call và SaveChanges không nhận cancellation token.
- **Impact:** shutdown/deployment có thể kéo dài và công việc khó dừng có kiểm soát.
- **Severity:** Medium.
- **Fix:** nhận `CancellationToken` nếu execution model hỗ trợ và truyền xuyên suốt dependency.

### 6. Batch không giới hạn

- **Problem:** `ToListAsync()` tải toàn bộ record đến hạn.
- **Impact:** memory/latency tăng khi backlog lớn và job giữ scope lâu.
- **Severity:** Medium.
- **Fix:** claim theo batch giới hạn hoặc enqueue IDs theo page/keyset.

### 7. DbContext giữ tracking lâu

- **Problem:** một DbContext track toàn batch và sống xuyên nhiều external calls.
- **Impact:** change tracker lớn, state khó kiểm soát sau failure.
- **Severity:** Medium.
- **Fix:** xử lý từng operation bằng scope/DbContext ngắn hoặc bulk claim IDs trước rồi xử lý riêng.

### 8. Observability chưa đủ để điều tra retry

- **Problem:** log thiếu record ID, attempt, operation ID, duration và external correlation.
- **Impact:** khó phân biệt duplicate execution với duplicate side effect.
- **Severity:** Medium.
- **Fix:** structured logging + tracing + metrics theo operation.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IMailboxService _mailboxService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IMailboxService mailboxService,
        ILogger<OffboardingJob> logger)
    {
        _dbFactory = dbFactory;
        _mailboxService = mailboxService;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ProcessAsync(long configId, CancellationToken ct)
    {
        var operationId = $"offboarding:{configId}";

        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.MailConfigs
            .Where(x => x.Id == configId && x.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.ClaimedAt, DateTime.UtcNow), ct);

        if (claimed == 0)
        {
            _logger.LogInformation(
                "Skipping operation {OperationId}; record is not pending",
                operationId);
            return;
        }

        try
        {
            var config = await db.MailConfigs
                .SingleAsync(x => x.Id == configId, ct);

            await _mailboxService.EnsureMailboxResetAsync(
                config.UserEmail, operationId, ct);

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;
            config.LastError = null;
            await db.SaveChangesAsync(ct);
        }
        catch (Exception ex)
        {
            await db.MailConfigs
                .Where(x => x.Id == configId && x.Status == "Processing")
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, "Pending")
                    .SetProperty(x => x.LastError, ex.Message),
                    CancellationToken.None);

            _logger.LogError(ex,
                "Operation {OperationId} failed", operationId);
            throw;
        }
    }
}
```

`EnsureMailboxResetAsync` ở đây là contract được thiết kế theo hướng idempotent: trước khi tạo side effect, implementation cần xác định trạng thái mong muốn đã tồn tại hay chưa hoặc dùng idempotency primitive của downstream nếu có. Atomic claim chỉ ngăn concurrent workers trong DB; nó không tự giải quyết crash sau external success nhưng trước DB commit.

## Trade-offs

Atomic claim đơn giản và phù hợp với modular monolith, nhưng cần recovery cho record bị kẹt `Processing`. Distributed lock có thể giảm concurrent execution nhưng không thay thế idempotency. Transaction bao quanh network call thường là lựa chọn xấu vì giữ lock lâu và vẫn không tạo distributed atomicity. Nếu throughput lớn, có thể tách scheduler và per-record jobs hoặc dùng transactional outbox để phát work item đáng tin cậy.

## Cách kiểm thử

1. **Concurrency test:** 20 worker cùng `ProcessAsync(id)`; chỉ một worker claim thành công.
2. **Failure-path:** external call thành công nhưng DB save bị inject failure; retry không tạo side effect sai lần hai.
3. **Crash recovery:** record `Processing` quá lease timeout được reclaim an toàn.
4. **Poison record:** một mailbox lỗi liên tục không ngăn các mailbox khác hoàn thành.
5. **Load test:** backlog lớn vẫn giữ memory, DB connections và external concurrency trong giới hạn.

## Quan sát trong production

Log `OperationId`, config ID, attempt, previous/new status và downstream correlation ID. Theo dõi `pending_count`, `processing_count`, `oldest_pending_age`, success/failure/retry rate, duplicate-prevented count và external-call latency. Trace từ Hangfire execution qua DB claim đến Exchange operation; alert khi backlog age hoặc số record `Processing` quá lease tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `[DisableConcurrentExecution]` không đủ để bảo đảm business operation exactly-once?
2. Nếu downstream không có idempotency key và cũng không có API đọc trạng thái hiện tại, bạn thiết kế recovery thế nào?
3. Khi nào transactional outbox giúp ích, và nó không giải quyết phần nào của bài toán external side effect?

# Code Review Challenge 2 — API tìm kiếm audit log có lỗ hổng authorization và SQL injection

**Chủ đề:** Authorization, input validation, SQL correctness, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–25 phút  
**Số vấn đề cần tìm:** khoảng 7 vấn đề

## Bối cảnh

Một API nội bộ cho phép quản trị viên tenant tìm audit log. Ứng dụng là multi-tenant ASP.NET Core, dùng PostgreSQL. Endpoint được bảo vệ bằng JWT authentication. Sau một đợt security review, team phát hiện có request trả về log của tenant khác và database CPU tăng mạnh khi người dùng nhập chuỗi tìm kiếm dài. Audit log có thể chứa email, IP và metadata nghiệp vụ nhạy cảm.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
[Authorize]
public sealed class AuditController : ControllerBase
{
    private readonly NpgsqlDataSource _dataSource;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        NpgsqlDataSource dataSource,
        ILogger<AuditController> logger)
    {
        _dataSource = dataSource;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? tenantId,
        string? text,
        int page = 1,
        int pageSize = 100)
    {
        var sql = $"""
            SELECT id, tenant_id, user_email, ip_address, action, metadata, created_at
            FROM audit_logs
            WHERE tenant_id = '{tenantId}'
              AND (user_email ILIKE '%{text}%' OR metadata::text ILIKE '%{text}%')
            ORDER BY created_at DESC
            OFFSET {(page - 1) * pageSize}
            LIMIT {pageSize};
            """;

        _logger.LogInformation(
            "Audit search tenant={TenantId}, text={Text}, sql={Sql}",
            tenantId, text, sql);

        await using var command = _dataSource.CreateCommand(sql);
        await using var reader = await command.ExecuteReaderAsync();

        var rows = new List<object>();
        while (await reader.ReadAsync())
        {
            rows.Add(new
            {
                Id = reader.GetInt64(0),
                TenantId = reader.GetString(1),
                Email = reader.GetString(2),
                Ip = reader.GetString(3),
                Action = reader.GetString(4),
                Metadata = reader.GetString(5),
                CreatedAt = reader.GetDateTime(6)
            });
        }

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. SQL injection

- **Problem:** `tenantId`, `text`, pagination được interpolate trực tiếp vào SQL.
- **Why:** input trở thành SQL syntax thay vì parameter values.
- **Impact:** có thể đọc/sửa dữ liệu ngoài ý muốn tùy quyền DB account; ít nhất có thể phá query hoặc vượt filter.
- **Severity:** Critical.
- **Fix:** parameterized command cho mọi giá trị; validate pagination.

### 2. Tenant boundary dựa trên input của client

- **Problem:** caller tự truyền `tenantId`.
- **Why:** authenticated user có thể thay ID tenant nếu endpoint không kiểm tra ownership.
- **Impact:** cross-tenant data disclosure.
- **Severity:** Critical.
- **Fix:** derive tenant ID từ trusted claim/context; nếu super-admin được cross-tenant thì dùng policy riêng và audit rõ ràng.

### 3. Authentication nhưng thiếu authorization phù hợp

- **Problem:** `[Authorize]` chỉ yêu cầu authenticated principal.
- **Impact:** user thường có thể truy cập audit endpoint nếu route không bị policy khác chặn.
- **Severity:** High.
- **Fix:** policy/permission như `Audit.Read`, cộng tenant authorization.

### 4. Sensitive data bị log

- **Problem:** log search text và full SQL chứa tenant/email/search terms.
- **Impact:** PII hoặc dữ liệu nghiệp vụ đi vào log store và mở rộng blast radius.
- **Severity:** High.
- **Fix:** log normalized metadata như tenant hash/id được phép, page, duration, result count; không log raw SQL/input nhạy cảm.

### 5. Query có thể rất đắt

- **Problem:** wildcard leading `%text%`, đặc biệt `metadata::text`, có thể buộc scan lớn nếu không có indexing strategy phù hợp.
- **Impact:** DB CPU/latency tăng dưới abuse hoặc legitimate broad searches.
- **Severity:** High.
- **Fix:** giới hạn search length, pagination, timeout; thiết kế searchable fields/index phù hợp; cân nhắc full-text/trigram tùy yêu cầu thay vì cast toàn metadata.

### 6. Pagination không được giới hạn

- **Problem:** page/pageSize có thể âm hoặc cực lớn.
- **Impact:** expensive queries, lỗi SQL, resource abuse; OFFSET lớn cũng kém hiệu quả.
- **Severity:** Medium.
- **Fix:** clamp/validate; với dataset lớn dùng keyset pagination theo `(created_at, id)`.

### 7. Không truyền cancellation/command timeout rõ ràng

- **Problem:** request abort không được propagate.
- **Impact:** query đắt có thể tiếp tục chạy sau khi client bỏ request.
- **Severity:** Medium.
- **Fix:** dùng `HttpContext.RequestAborted`, cấu hình command timeout phù hợp.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
[Authorize(Policy = "Audit.Read")]
public sealed class AuditController : ControllerBase
{
    private readonly NpgsqlDataSource _dataSource;
    private readonly ITenantContext _tenantContext;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        NpgsqlDataSource dataSource,
        ITenantContext tenantContext,
        ILogger<AuditController> logger)
    {
        _dataSource = dataSource;
        _tenantContext = tenantContext;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        [FromQuery] string? text,
        [FromQuery] int pageSize = 50,
        CancellationToken ct = default)
    {
        pageSize = Math.Clamp(pageSize, 1, 100);
        text = text?.Trim();

        if (text is { Length: > 100 })
            return BadRequest("Search text is too long.");

        var tenantId = _tenantContext.RequiredTenantId;

        const string sql = """
            SELECT id, user_email, ip_address, action, metadata, created_at
            FROM audit_logs
            WHERE tenant_id = @tenantId
              AND (@text IS NULL
                   OR user_email ILIKE @pattern
                   OR metadata::text ILIKE @pattern)
            ORDER BY created_at DESC, id DESC
            LIMIT @pageSize;
            """;

        var started = Stopwatch.GetTimestamp();

        await using var command = _dataSource.CreateCommand(sql);
        command.Parameters.AddWithValue("tenantId", tenantId);
        command.Parameters.AddWithValue(
            "text", (object?)text ?? DBNull.Value);
        command.Parameters.AddWithValue(
            "pattern", text is null ? DBNull.Value : $"%{text}%");
        command.Parameters.AddWithValue("pageSize", pageSize);

        await using var reader = await command.ExecuteReaderAsync(ct);
        var rows = new List<object>();

        while (await reader.ReadAsync(ct))
        {
            rows.Add(new
            {
                Id = reader.GetInt64(0),
                Email = reader.GetString(1),
                Ip = reader.GetString(2),
                Action = reader.GetString(3),
                Metadata = reader.GetString(4),
                CreatedAt = reader.GetDateTime(5)
            });
        }

        _logger.LogInformation(
            "Audit search completed for tenant {TenantId}; Count={Count}; ElapsedMs={ElapsedMs}",
            tenantId, rows.Count, Stopwatch.GetElapsedTime(started).TotalMilliseconds);

        return Ok(rows);
    }
}
```

Đoạn sửa tập trung vào security boundary và parameterization. Với production table lớn, `metadata::text ILIKE` vẫn cần được thay bằng search design phù hợp; parameterization giải quyết injection chứ không tự giải quyết query cost.

## Trade-offs

Lấy tenant từ identity context làm API an toàn và đơn giản hơn nhưng cần flow riêng cho legitimate cross-tenant admin. Keyset pagination hiệu quả hơn OFFSET lớn nhưng API phức tạp hơn vì phải trả cursor. Trigram/full-text index có thể cải thiện substring search nhưng tăng storage/write cost; nếu audit search ít dùng, có thể ưu tiên structured filters trước khi thêm index chuyên biệt.

## Cách kiểm thử

1. **Security test:** user tenant A cố truyền/giả tenant B vẫn không thể nhận dữ liệu tenant B.
2. **Injection test:** payload chứa quote/comment/operator chỉ được xử lý như text parameter.
3. **Authorization test:** authenticated user thiếu `Audit.Read` nhận 403.
4. **Load/database test:** search phổ biến trên production-like dataset đạt latency budget và không gây sequential scan ngoài dự kiến.
5. **Cancellation test:** client abort làm database command được cancel và connection trở về pool.

## Quan sát trong production

Theo dõi request latency, DB command duration, timeout/cancellation count, rows scanned/returned, authorization-denied count và slow-query plans. Audit riêng các privileged cross-tenant accesses nếu có. Không ghi raw search terms, tokens, full SQL có input hoặc toàn bộ audit payload vào application logs.

## Câu hỏi phỏng vấn mở rộng

1. Parameterized SQL ngăn SQL injection nhưng vì sao không giải quyết authorization?
2. Nếu product bắt buộc tìm substring trong JSON metadata trên hàng trăm triệu records, bạn thay đổi data/search architecture thế nào?
3. Bạn thiết kế quyền super-admin cross-tenant thế nào để vừa usable vừa audit được?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai bài hôm nay tập trung vào hai boundary thường gây sự cố production: **reliability boundary** giữa database và external side effect, và **security boundary** giữa authenticated identity với tenant-scoped data. Retry không tạo exactly-once semantics; idempotency phải được thiết kế ở business operation.
