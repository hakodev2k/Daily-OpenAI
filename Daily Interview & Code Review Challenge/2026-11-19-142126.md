# Code Review Challenge 1 — Webhook thanh toán: xác thực chữ ký, replay và trạng thái đơn hàng

**Chủ đề:** ASP.NET Core 8, C#, HMAC, SQL Server, EF Core, distributed retries  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** khoảng 10

## Bối cảnh

Một nền tảng bán vé nhận webhook từ payment provider. Provider gửi header `X-Payment-Signature` là chuỗi hex của HMAC-SHA256 trên **raw request body**, dùng shared secret. Khi không nhận HTTP 2xx, provider retry; cùng event có thể đến đồng thời và không bảo đảm thứ tự. Một event có `eventId`, `orderId`, `type`, `amount`, `currency`. Trong đợt bán vé, API chạy trên 5 Azure App Service instances. Có trường hợp vé được phát hành hai lần, trạng thái thanh toán bị đảo và một số webhook giả mạo lọt qua. Giả định `Order` có `Id`, `Amount`, `Currency`, `Status`; `TicketIssuer.IssueAsync` gọi hệ thống ngoài, không tham gia SQL transaction. Mã dưới đây rút gọn nhưng là một đường xử lý thực tế.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/payments/webhook")]
public sealed class PaymentWebhookController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly TicketIssuer _tickets;
    private readonly IConfiguration _config;
    private readonly ILogger<PaymentWebhookController> _log;

    public PaymentWebhookController(AppDbContext db, TicketIssuer tickets,
        IConfiguration config, ILogger<PaymentWebhookController> log)
        => (_db, _tickets, _config, _log) = (db, tickets, config, log);

    [HttpPost]
    public async Task<IActionResult> Receive(CancellationToken ct)
    {
        using var reader = new StreamReader(Request.Body);
        var body = await reader.ReadToEndAsync(ct);
        var evt = JsonSerializer.Deserialize<PaymentEvent>(body)!;
        var supplied = Request.Headers["X-Payment-Signature"].ToString();
        var secret = _config["Payment:WebhookSecret"] ?? "";

        using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secret));
        var expected = Convert.ToHexString(
            hmac.ComputeHash(Encoding.UTF8.GetBytes(
                JsonSerializer.Serialize(evt))));
        if (supplied.ToLowerInvariant() != expected.ToLowerInvariant())
            return Unauthorized();

        var order = await _db.Orders.FindAsync([evt.OrderId], ct);
        if (order is null) return Ok();

        if (evt.Type == "payment.succeeded")
        {
            order.Status = "Paid";
            await _tickets.IssueAsync(order.Id, ct);
        }
        else if (evt.Type == "payment.failed")
        {
            order.Status = "Failed";
        }

        _log.LogInformation("Payment event: {Body}", body);
        await _db.SaveChangesAsync(ct);
        return Ok();
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Xác thực HMAC trên dữ liệu đã serialize lại

**Vấn đề:** `JsonSerializer.Serialize(evt)` thay đổi representation so với raw body; tính đúng/sai của signature không được bảo đảm.  
**Tại sao xảy ra:** Whitespace, property ordering, escaping, number formatting và options có thể khác.  
**Ảnh hưởng production:** Webhook hợp lệ bị từ chối; logic tin cậy sai nếu contract thay đổi.  
**Cách sửa:** Tính HMAC trên **raw body bytes** đúng theo contract provider; dùng comparison constant-time sau khi validate encoding/length.

### [Critical] — Không kiểm tra event có thực sự thuộc đơn hàng và số tiền hợp lệ

**Vấn đề:** Chỉ dựa vào `orderId` và `type`; thiếu kiểm tra `amount`, `currency`, merchant/account và các định danh giao dịch liên quan.  
**Tại sao xảy ra:** Signature chứng minh thông điệp từ provider, không tự chứng minh event được gắn đúng với order nội bộ.  
**Ảnh hưởng production:** Sai đơn hàng hoặc số tiền có thể phát vé không tương ứng với thanh toán.  
**Cách sửa:** Validate schema và đối chiếu payment intent/transaction reference, amount/currency, tenant và provider account theo contract; xử lý mismatch như sự kiện bất thường.

### [Critical] — Side effect phát vé trước khi commit, không idempotent

**Vấn đề:** `IssueAsync` có thể thành công trước `SaveChangesAsync`, và bị gọi lại khi retry.  
**Tại sao xảy ra:** Không có atomic transaction xuyên SQL và hệ thống phát vé.  
**Ảnh hưởng production:** Phát vé trùng, hoàn tiền/thất thoát, khó đối soát.  
**Cách sửa:** Trong SQL transaction lưu event duy nhất, cập nhật trạng thái có điều kiện và ghi outbox; worker phát vé bằng idempotency key ổn định; ghi nhận kết quả và retry có giới hạn.

### [High] — Thiếu chống duplicate delivery xuyên instances

**Vấn đề:** Không lưu `eventId` với unique index; đọc trạng thái đơn hàng rồi ghi không có concurrency protection.  
**Tại sao xảy ra:** Các replicas có thể xử lý cùng lúc, một instance không nhìn thấy thay đổi chưa commit của instance khác.  
**Ảnh hưởng production:** Duplicate fulfillment, race và lost update.  
**Cách sửa:** Unique constraint `(provider, eventId)`; transaction và optimistic concurrency/conditional update; duplicate trả 2xx khi đã xử lý an toàn.

### [High] — Trạng thái bị ghi đè bởi event đến sai thứ tự

**Vấn đề:** `payment.failed` có thể ghi đè `Paid` dù không còn hợp lệ.  
**Tại sao xảy ra:** Không có state machine hoặc kiểm tra phiên bản/nguồn sự thật.  
**Ảnh hưởng production:** Vé đã phát nhưng UI hiển thị thất bại; đối soát sai.  
**Cách sửa:** Định nghĩa allowed transitions, tham chiếu transaction/payment attempt và khi cần truy vấn provider để hòa giải; không suy luận thứ tự từ thời điểm nhận.

### [High] — Không kiểm soát replay và chính sách timestamp

**Vấn đề:** Một payload đã ký có thể gửi lại vô hạn.  
**Tại sao xảy ra:** Thiếu event deduplication và timestamp/tolerance nếu provider có hỗ trợ.  
**Ảnh hưởng production:** Tăng tải, kích hoạt lại side effect.  
**Cách sửa:** Unique event inbox; kiểm tra timestamp theo hợp đồng và đồng bộ clock; timestamp không thay thế idempotency.

### [High] — Log toàn bộ payload nhạy cảm

**Vấn đề:** `{Body}` có thể chứa thông tin cá nhân, payment metadata.  
**Tại sao xảy ra:** Logging không có data classification và redaction.  
**Ảnh hưởng production:** Rủi ro lộ dữ liệu, retention và access control không phù hợp.  
**Cách sửa:** Log `eventId`, `orderId`, provider, outcome, trace ID; che dữ liệu nhạy cảm và phân quyền logs.

### [Medium] — Thiếu input validation và giới hạn body

**Vấn đề:** Null-forgiving deserialize, body không giới hạn và signature hex không kiểm tra định dạng.  
**Tại sao xảy ra:** Tin payload trước khi xác thực.  
**Ảnh hưởng production:** 500, memory pressure, DoS.  
**Cách sửa:** Giới hạn request size, validate header và parse an toàn sau khi xác thực; trả mã lỗi nhất quán.

### [Medium] — Không phân biệt lỗi tạm thời với lỗi vĩnh viễn

**Vấn đề:** DB hoặc issuer failure biến thành 500 nhưng chưa có bounded retry/DLQ/reconciliation; order không tồn tại lại `Ok()`.  
**Tại sao xảy ra:** Chưa có delivery contract và operational recovery.  
**Ảnh hưởng production:** Mất sự kiện hoặc retry storm.  
**Cách sửa:** Quy định response theo provider, lưu inbox bền vững, retry/backoff, quarantine và đối soát định kỳ.

### [Medium] — Secret và rotation chưa được thiết kế

**Vấn đề:** Secret rỗng được chấp nhận ở config; chưa có quy trình rotation.  
**Tại sao xảy ra:** Không fail-fast và không định nghĩa key versions.  
**Ảnh hưởng production:** Sai cấu hình gây lỗi xác thực diện rộng hoặc suy giảm bảo mật.  
**Cách sửa:** Validate startup config, lưu Key Vault/Managed Identity, hỗ trợ overlapping secrets có giới hạn khi rotation.

## Phiên bản đề xuất

Minh họa đường nhận webhook; các abstraction dưới đây là **hợp đồng ứng dụng cần triển khai**, không phải API sẵn có của framework. `PersistOnceAsync` phải thực thi trong **một SQL transaction**, có unique index trên `(Provider, EventId)`, kiểm tra trạng thái/amount và thêm outbox trong cùng commit. `IWebhookVerifier` chịu trách nhiệm raw-body HMAC, key rotation và timestamp theo contract provider.

```csharp
[ApiController]
[Route("api/payments/webhook")]
public sealed class PaymentWebhookController : ControllerBase
{
    private const int MaxBodyBytes = 64 * 1024;
    private readonly IWebhookVerifier _verifier;
    private readonly IPaymentInbox _inbox;
    private readonly ILogger<PaymentWebhookController> _logger;

    public PaymentWebhookController(IWebhookVerifier verifier,
        IPaymentInbox inbox, ILogger<PaymentWebhookController> logger)
        => (_verifier, _inbox, _logger) = (verifier, inbox, logger);

    [HttpPost]
    [RequestSizeLimit(MaxBodyBytes)]
    public async Task<IActionResult> Receive(CancellationToken ct)
    {
        await using var buffer = new MemoryStream();
        await Request.Body.CopyToAsync(buffer, ct);
        if (buffer.Length > MaxBodyBytes)
            return StatusCode(StatusCodes.Status413PayloadTooLarge);

        var raw = buffer.ToArray();
        var signature = Request.Headers["X-Payment-Signature"].ToString();
        if (!_verifier.Verify(raw, signature, Request.Headers))
            return Unauthorized();

        PaymentEvent? evt;
        try { evt = JsonSerializer.Deserialize<PaymentEvent>(raw); }
        catch (JsonException) { return BadRequest(); }
        if (evt is null || string.IsNullOrWhiteSpace(evt.EventId)
            || string.IsNullOrWhiteSpace(evt.OrderId))
            return BadRequest();

        var outcome = await _inbox.PersistOnceAsync(evt, ct);
        _logger.LogInformation(
            "Webhook {EventId} {OrderId} {Outcome}",
            evt.EventId, evt.OrderId, outcome);
        return outcome switch
        {
            InboxOutcome.Accepted or InboxOutcome.Duplicate => Ok(),
            InboxOutcome.InvalidBusinessData => BadRequest(),
            _ => StatusCode(StatusCodes.Status503ServiceUnavailable)
        };
    }
}
```

Phác thảo invariant ở persistence/worker:

```text
SQL transaction:
  INSERT PaymentInbox(provider,eventId,...)  -- UNIQUE(provider,eventId)
  verify order ownership + amount/currency + payment attempt
  apply allowed state transition using concurrency control
  INSERT Outbox(messageId = "issue-ticket:" + orderId + ":" + paymentId)
  COMMIT

Outbox worker:
  claim pending item with lease / concurrency-safe update
  call issuer using stable idempotency key
  record completion, retry with backoff and alert on exhausted attempts
  reconcile ambiguous timeout with issuer before retrying non-idempotent calls
```

Lưu ý: Nếu provider không hỗ trợ idempotency key, phải xây dựng deduplication ở hệ thống phát vé hoặc reconciliation; outbox một mình **không** tạo exactly-once side effects.

## Giải thích thiết kế sau khi sửa

HTTP handler chỉ xác thực và ghi nhận sự kiện bền vững; external fulfillment không nằm trong transaction SQL. Unique constraint bảo vệ concurrency xuyên replicas, state machine bảo vệ ordering, outbox nối transaction nội bộ với side effect bất đồng bộ. Khi đã lưu inbox thành công có thể trả 2xx, còn DB unavailable cần response để provider retry theo contract.

## Trade-offs

Thêm inbox/outbox, worker và reconciliation làm tăng vận hành và độ trễ phát vé; đổi lại giảm duplicate và cho phép recovery. Với lưu lượng nhỏ, một SQL-backed background worker có thể đủ, không bắt buộc microservices hay Service Bus. Nếu business đòi phát vé tức thì, cần xác định SLA và cơ chế thông báo pending.

## Cách kiểm thử

1. **Security test:** Raw body đúng signature được nhận; body thay một byte, signature malformed, secret rotation và timestamp ngoài tolerance bị từ chối theo contract.
2. **Concurrency integration:** Gửi 100 request cùng `eventId` qua nhiều instances; một inbox/outbox duy nhất, không phát vé trùng.
3. **Failure-path:** SQL commit thất bại, issuer timeout sau khi thực sự phát vé, worker crash trước ack; retry và reconciliation giữ invariant.
4. **State-machine test:** `failed`/ `succeeded` đến đảo thứ tự và payment attempts khác nhau; không ghi đè trạng thái sai.
5. **Load test:** Burst webhook lớn, giới hạn body, connection pool, p95 và outbox backlog.

## Quan sát trong production

Structured logs không chứa payload thô; trace/correlation theo `eventId` và `orderId`. Metrics: signature rejection rate, duplicates, inbox persistence failures, outbox age/p95, issuance latency, issuer retries, reconciliation mismatches, SQL deadlocks/unique conflicts, HTTP 5xx. Alert trên backlog vượt SLA và duplicate fulfillment (mục tiêu 0); dùng Application Insights và Azure Monitor, kết hợp đối soát với provider.

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Product = {
  id: string; name: string; descriptionHtml: string; price: number;
};
const query = ref('');
const category = ref('all');
const page = ref(1);
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref('');
const cache = new Map<string, Product[]>();

async function load() {
  loading.value = true;
  error.value = '';
  const key = query.value + category.value;
  if (cache.has(key)) {
    products.value = cache.get(key)!;
    loading.value = false;
    return;
  }
  try {
    const url = '/api/products?q=' + query.value +
      '&category=' + category.value + '&page=' + page.value;
    const response = await fetch(url);
    const data = await response.json();
    products.value = data.items;
    total.value = data.total;
    cache.set(key, data.items);
  } catch {
    error.value = 'Không tải được sản phẩm';
  } finally {
    loading.value = false;
  }
}
watch([query, category, page], load);
onMounted(load);
</script>

<template>
  <input v-model="query" placeholder="Tìm sản phẩm" />
  <select v-model="category">
    <option value="all">Tất cả</option>
    <option value="books">Sách</option>
    <option value="tools">Dụng cụ</option>
  </select>
  <p v-if="loading">Đang tải...</p>
  <p v-if="error">{{ error }}</p>
  <p>{{ total }} sản phẩm</p>
  <article v-for="product in products" :key="product.id">
    <h3>{{ product.name }}</h3>
    <div v-html="product.descriptionHtml"></div>
    <span>{{ product.price }}</span>
  </article>
  <button @click="page++">Trang tiếp</button>
</template>
```

## Kết quả code review tham khảo

### [Critical] — XSS qua `v-html` với seller-controlled HTML

**Vấn đề:** Render HTML từ nguồn không đáng tin mà không có bảo đảm sanitize.  
**Tại sao xảy ra:** `v-html` chèn HTML trực tiếp, không áp dụng escaping như interpolation.  
**Ảnh hưởng production:** Stored XSS có thể chiếm phiên làm việc hoặc thao tác thay người dùng, tùy các biện pháp bảo vệ hiện có.  
**Cách sửa:** Ưu tiên render text/plain hoặc structured rich text với allowlist; nếu cần HTML, sanitize ở trust boundary bằng thư viện được duy trì, kiểm tra cả server và client; CSP là defense-in-depth, không thay sanitize.

### [High] — Race condition trả về dữ liệu query cũ

**Vấn đề:** Request cũ có thể hoàn tất sau request mới và ghi đè state.  
**Tại sao xảy ra:** Không cancel request trước hoặc kiểm tra request identity.  
**Ảnh hưởng production:** Hiển thị sai sản phẩm/category, gây nhầm lẫn quyết định mua.  
**Cách sửa:** Dùng watcher cleanup + `AbortController` và sequence guard; chỉ request mới nhất được phép cập nhật state.

### [High] — Cache key thiếu phân cách và page, cache không đồng bộ total

**Vấn đề:** `query + category` có thể collision, không chứa page; cache hit chỉ cập nhật items.  
**Tại sao xảy ra:** Key không biểu diễn toàn bộ query parameters và response shape.  
**Ảnh hưởng production:** Pagination sai, total cũ, dữ liệu không tương ứng filter.  
**Cách sửa:** Key có cấu trúc gồm query/category/page/pageSize/sort; cache cả `items` và `total`, TTL/invalidation theo yêu cầu freshness.

### [High] — HTML error response bị xử lý như thành công

**Vấn đề:** `fetch` resolve khi HTTP 4xx/5xx; code không kiểm tra `response.ok` hoặc schema.  
**Tại sao xảy ra:** Nhầm network failure với HTTP error.  
**Ảnh hưởng production:** UI hiển thị dữ liệu undefined, lỗi khó chẩn đoán.  
**Cách sửa:** Check status và validate shape; thông báo retry phù hợp, log status mà không lộ dữ liệu nhạy cảm.

### [Medium] — Mỗi ký tự gây một request

**Vấn đề:** Watch `query` gọi API liên tục khi gõ.  
**Tại sao xảy ra:** Không debounce hoặc giới hạn request.  
**Ảnh hưởng production:** Tăng QPS và API cost, gây cạnh tranh tài nguyên.  
**Cách sửa:** Debounce 250–350 ms theo UX, kết hợp cancellation; không coi debounce là giải pháp race duy nhất.

### [Medium] — Pagination không reset và không có boundary

**Vấn đề:** Chuyển category giữ page cũ; nút next không kiểm tra total.  
**Tại sao xảy ra:** Page độc lập filter và thiếu page count.  
**Ảnh hưởng production:** Trang rỗng không giải thích, API call thừa.  
**Cách sửa:** Reset page=1 khi filter thay đổi; disable next khi hết trang; backend cũng validate page/pageSize.

### [Medium] — Loading/error state không gắn request hiện hành

**Vấn đề:** `finally` của request cũ có thể tắt loading của request mới; products cũ còn hiển thị khi lỗi.  
**Tại sao xảy ra:** Shared mutable state thiếu request identity.  
**Ảnh hưởng production:** UX mâu thuẫn và dữ liệu stale.  
**Cách sửa:** Chỉ request active cập nhật loading/error; quy định rõ stale-while-revalidate hoặc clear results.

### [Low] — Accessibility và lifecycle chưa đầy đủ

**Vấn đề:** Input/select thiếu label rõ, chưa có status announcement; không abort khi unmount.  
**Tại sao xảy ra:** Chỉ tối ưu happy path.  
**Ảnh hưởng production:** Người dùng assistive technology khó thao tác; request lãng phí.  
**Cách sửa:** Label liên kết, `role="status"`/`aria-live`, abort trong watcher cleanup/unmount, disabled button hợp lý.

## Phiên bản đề xuất

Ví dụ ưu tiên text-only description để loại bỏ HTML injection. Nếu sản phẩm bắt buộc có rich text, cần pipeline sanitize được kiểm chứng riêng. `watch` mặc định chạy sau khi các refs khởi tạo; `immediate: true` thay `onMounted`.

```vue
<script setup lang="ts">
import { computed, ref, watch } from 'vue';

type Product = { id: string; name: string; descriptionHtml: string; price: number };
type Result = { items: Product[]; total: number };
const query = ref('');
const category = ref('all');
const page = ref(1);
const pageSize = 20;
const products = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref('');
const searchTerm = ref('');
let sequence = 0;

watch([query, category], () => { page.value = 1; });
watch(query, (value, _old, onCleanup) => {
  const timer = setTimeout(() => { searchTerm.value = value.trim(); }, 300);
  onCleanup(() => clearTimeout(timer));
}, { immediate: true });

watch([searchTerm, category, page], (_value, _old, onCleanup) => {
  const controller = new AbortController();
  const current = ++sequence;
  onCleanup(() => controller.abort());
  loading.value = true;
  error.value = '';

  const params = new URLSearchParams({
    q: searchTerm.value, category: category.value,
    page: String(page.value), pageSize: String(pageSize)
  });
  (async () => {
    try {
      const response = await fetch('/api/products?' + params, {
        signal: controller.signal
      });
      if (!response.ok) throw new Error('HTTP ' + response.status);
      const data: Result = await response.json();
      if (!Array.isArray(data.items) || !Number.isFinite(data.total))
        throw new Error('Invalid response');
      if (current !== sequence) return;
      products.value = data.items;
      total.value = data.total;
    } catch (e) {
      if (current !== sequence || controller.signal.aborted) return;
      error.value = 'Không tải được sản phẩm. Vui lòng thử lại.';
      products.value = [];
      total.value = 0;
    } finally {
      if (current === sequence) loading.value = false;
    }
  })();
}, { immediate: true });

const canNext = computed(() => page.value * pageSize < total.value);
</script>

<template>
  <label for="product-search">Tìm sản phẩm</label>
  <input id="product-search" v-model="query" type="search" />
  <label for="product-category">Danh mục</label>
  <select id="product-category" v-model="category">
    <option value="all">Tất cả</option>
    <option value="books">Sách</option>
    <option value="tools">Dụng cụ</option>
  </select>
  <p role="status" aria-live="polite">
    {{ loading ? 'Đang tải...' : error || total + ' sản phẩm' }}
  </p>
  <article v-for="product in products" :key="product.id">
    <h3>{{ product.name }}</h3>
    <p>{{ product.descriptionHtml }}</p>
    <span>{{ product.price }}</span>
  </article>
  <button :disabled="loading || !canNext" @click="page++">
    Trang tiếp
  </button>
</template>
```

**Giới hạn của ví dụ:** Khi filter đổi, `page` và `searchTerm` có thể tạo thêm request trung gian tùy batching; sequence guard bảo đảm correctness nhưng không loại bỏ mọi call. Trong production có thể gộp filters thành một query-state object, dùng `watch` một nguồn chuẩn hoặc thư viện query cache có cancellation và key ổn định. `descriptionHtml` hiện hiển thị như text, không phải rich text.

## Giải thích thiết kế sau khi sửa

Cancellation giảm request không cần thiết; sequence guard đảm bảo request cũ không ghi đè dù cancellation không chặn được mọi response. URLSearchParams encode input. Kiểm tra HTTP status và response shape giúp phân biệt failure modes. Không dùng cache tự chế khi chưa có freshness contract; nếu cache cần thiết, thêm key đầy đủ, TTL và invalidation rõ ràng.

## Trade-offs

Debounce giảm QPS nhưng tăng thời gian phản hồi khi gõ; 300 ms chỉ là giả định cần đo. Cancellation không đảm bảo backend đã ngừng xử lý. Text-only an toàn hơn nhưng mất rich formatting; rich text cần sanitize policy, CSP và kiểm thử. Giải pháp dùng TanStack Query/Vue Query có thể giảm boilerplate nếu dự án đã dùng; không bắt buộc thêm dependency cho một màn hình nhỏ.

## Cách kiểm thử

1. **Component race test:** Mock request A chậm, B nhanh; chỉ B cập nhật kết quả, loading đúng.
2. **Playwright E2E:** Gõ nhanh, đổi category ở trang cuối, quay lại trang trước; không hiện kết quả sai, next disabled đúng.
3. **Security test:** Seller HTML chứa `<img onerror=...>` hiển thị như text, không thực thi; nếu bật rich text, test sanitizer.
4. **API failure test:** HTTP 429/500, invalid JSON, offline và abort; error state hợp lệ, không unhandled rejection.
5. **Performance test:** Đếm request/keystroke, latency p95 và network waterfall trên mạng chậm; xác minh debounce/cancellation.

## Quan sát trong production

Browser Real User Monitoring: search-to-results latency, API error rate/status, aborted request count, stale-result prevention events (không log raw search nếu có dữ liệu nhạy cảm), p95 input-to-render, requests per search session. Backend theo dõi QPS, 429/5xx, SQL dependency latency và correlation IDs. Dùng Lighthouse/accessibility checks và Playwright trong CI.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product prices thay đổi mỗi phút, bạn quyết định cache TTL/invalidation ở browser như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Webhook an toàn phải kết hợp raw-body signature verification, business validation, idempotent inbox, transactional outbox và reconciliation; không có exactly-once xuyên hệ thống chỉ nhờ SQL transaction. UI tìm kiếm bất đồng bộ phải bảo vệ request ordering, query-state consistency và trust boundary khi render CMS content. Cả hai tình huống đều đòi hỏi kiểm chứng dưới concurrency/failure, không chỉ happy-path unit tests.

## Mẫu tư duy cần nhớ

1. **Xác thực nguồn không đồng nghĩa xác thực nghiệp vụ:** kiểm tra identity, payload, amount và state transition.
2. **Thiết kế retry cùng idempotency:** giả định duplicate, out-of-order và ambiguous timeout.
3. **Bảo vệ state khỏi kết quả cũ:** cancellation để tiết kiệm tài nguyên, sequence guard để bảo vệ correctness.
4. **Không render dữ liệu không tin cậy như HTML:** đặt trust boundary rõ ràng.
5. **Đo trước khi tối ưu:** quan sát backlog, p95, QPS, duplicate và error rate trước/sau sửa.
