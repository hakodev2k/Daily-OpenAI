# Code Review Challenge 1 — Cache stampede và dữ liệu ghi đè dưới tải cao

**Chủ đề:** Caching, concurrency, EF Core, consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API trả về cấu hình outlet. Dữ liệu được cache trong Redis 5 phút để giảm tải PostgreSQL. Endpoint update được gọi bởi Portal; endpoint read được Mobile gọi với lưu lượng cao. Production thỉnh thoảng xuất hiện spike DB khi cache hết hạn, client nhận dữ liệu cũ ngay sau update, và hai admin cập nhật gần nhau có thể ghi đè thay đổi của nhau.

## Đoạn code cần review

```csharp
public sealed class OutletService
{
    private readonly AppDbContext _db;
    private readonly IDatabase _redis;

    public OutletService(AppDbContext db, IConnectionMultiplexer redis)
    {
        _db = db;
        _redis = redis.GetDatabase();
    }

    public async Task<OutletDto?> GetAsync(Guid id)
    {
        var key = $"outlet:{id}";
        var cached = await _redis.StringGetAsync(key);

        if (cached.HasValue)
            return JsonSerializer.Deserialize<OutletDto>(cached!);

        var outlet = await _db.Outlets
            .FirstOrDefaultAsync(x => x.Id == id);

        if (outlet == null)
            return null;

        var dto = new OutletDto(outlet.Id, outlet.Name, outlet.Status);
        await _redis.StringSetAsync(key, JsonSerializer.Serialize(dto), TimeSpan.FromMinutes(5));
        return dto;
    }

    public async Task UpdateAsync(Guid id, UpdateOutletRequest request)
    {
        var outlet = await _db.Outlets.FirstAsync(x => x.Id == id);
        outlet.Name = request.Name;
        outlet.Status = request.Status;

        await _redis.KeyDeleteAsync($"outlet:{id}");
        await _db.SaveChangesAsync();
    }
}
```

## Kết quả code review tham khảo

### 1. Invalidate cache trước khi transaction DB commit

- **Problem:** Cache bị xóa trước `SaveChangesAsync`.
- **Why:** Một request read có thể cache miss, đọc giá trị DB cũ rồi ghi lại vào Redis trước khi update commit.
- **Impact:** Cache có thể giữ dữ liệu cũ thêm 5 phút dù update đã thành công.
- **Severity:** High.
- **Fix:** Commit DB trước, sau đó invalidate cache; nếu yêu cầu consistency cao hơn, dùng outbox/versioned cache hoặc chiến lược invalidation có retry.

### 2. Lost update giữa các admin

- **Problem:** Không có optimistic concurrency.
- **Why:** Hai request có thể đọc cùng version rồi lần lượt ghi; request sau silently overwrite request trước.
- **Impact:** Mất thay đổi nghiệp vụ.
- **Severity:** High.
- **Fix:** Dùng concurrency token phù hợp provider/model, bắt `DbUpdateConcurrencyException`, trả conflict và yêu cầu client refresh/retry có kiểm soát.

### 3. Cache stampede

- **Problem:** Mọi request cache miss đều query DB.
- **Why:** Không có request coalescing/single-flight/distributed coordination.
- **Impact:** Khi hot key hết TTL, DB có thể nhận burst lớn.
- **Severity:** High.
- **Fix:** Có thể dùng per-key locking/single-flight trong instance; nhiều instance thì cân nhắc distributed lock hoặc stale-while-revalidate. Lock phải có timeout và failure strategy.

### 4. Cache invalidation failure sau DB commit chưa được xử lý

- **Problem:** Nếu DB update thành công nhưng Redis delete lỗi, dữ liệu stale vẫn tồn tại.
- **Impact:** Client tiếp tục đọc dữ liệu cũ.
- **Severity:** Medium.
- **Fix:** Retry có giới hạn, metrics/alert; nếu consistency quan trọng, publish invalidation qua outbox sau transaction DB.

### 5. Read query tracking không cần thiết

- **Problem:** `GetAsync` materialize entity dưới tracking dù chỉ đọc.
- **Impact:** Overhead CPU/memory trên hot path.
- **Severity:** Medium.
- **Fix:** Projection trực tiếp sang DTO và `AsNoTracking()` khi phù hợp.

### 6. Không truyền CancellationToken

- **Problem:** DB/Redis operations tiếp tục dù request đã bị hủy.
- **Impact:** Lãng phí tài nguyên khi timeout/disconnect, đặc biệt dưới tải cao.
- **Severity:** Medium.
- **Fix:** Nhận `CancellationToken` và truyền tới API hỗ trợ cancellation.

### 7. Cache miss cho record không tồn tại không được negative-cache

- **Problem:** ID không tồn tại luôn hit DB.
- **Impact:** Repeated invalid IDs có thể tạo tải DB không cần thiết.
- **Severity:** Low/Medium tùy traffic.
- **Fix:** Cân nhắc negative caching TTL ngắn nếu workload phù hợp; phải xử lý khi record được tạo sau đó.

### 8. TTL đồng loạt có thể tạo burst định kỳ

- **Problem:** Nhiều key có cùng TTL cố định.
- **Impact:** Nếu được warm cùng lúc, nhiều key có thể expire gần nhau.
- **Severity:** Low.
- **Fix:** Thêm jitter hợp lý vào TTL.

## Phiên bản code đề xuất

```csharp
public sealed class OutletService
{
    private readonly AppDbContext _db;
    private readonly IDatabase _redis;
    private readonly ILogger<OutletService> _logger;

    public OutletService(
        AppDbContext db,
        IConnectionMultiplexer redis,
        ILogger<OutletService> logger)
    {
        _db = db;
        _redis = redis.GetDatabase();
        _logger = logger;
    }

    public async Task<OutletDto?> GetAsync(Guid id, CancellationToken ct)
    {
        var key = $"outlet:{id}";
        var cached = await _redis.StringGetAsync(key);
        if (cached.HasValue)
            return JsonSerializer.Deserialize<OutletDto>(cached!);

        var dto = await _db.Outlets
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new OutletDto(x.Id, x.Name, x.Status))
            .SingleOrDefaultAsync(ct);

        if (dto is null)
            return null;

        var ttl = TimeSpan.FromSeconds(270 + Random.Shared.Next(0, 60));
        await _redis.StringSetAsync(key, JsonSerializer.Serialize(dto), ttl);
        return dto;
    }

    public async Task UpdateAsync(
        Guid id,
        UpdateOutletRequest request,
        CancellationToken ct)
    {
        var outlet = await _db.Outlets.SingleAsync(x => x.Id == id, ct);
        outlet.Name = request.Name;
        outlet.Status = request.Status;

        await _db.SaveChangesAsync(ct);

        try
        {
            await _redis.KeyDeleteAsync($"outlet:{id}");
        }
        catch (RedisException ex)
        {
            _logger.LogError(ex, "Failed to invalidate outlet cache {OutletId}", id);
            throw;
        }
    }
}
```

Đoạn trên sửa thứ tự commit/invalidate, giảm tracking và hỗ trợ cancellation, nhưng chưa tự giải quyết hoàn toàn cache stampede hoặc invalidation durability. Với yêu cầu consistency cao, nên bổ sung concurrency token và transactional outbox cho cache invalidation/event propagation.

## Trade-offs

Commit DB rồi xóa cache giảm race nghiêm trọng của code cũ nhưng vẫn có failure window nếu Redis lỗi sau commit. Outbox làm recovery đáng tin cậy hơn nhưng tăng complexity và có eventual consistency. Distributed lock giảm stampede đa instance nhưng thêm dependency, latency và failure modes; stale-while-revalidate thường phù hợp hơn nếu business chấp nhận dữ liệu hơi cũ.

## Cách kiểm thử

1. **Concurrency test:** 100–500 concurrent reads ngay khi cache expire; đo số DB queries cho một hot key.
2. **Lost-update test:** hai transaction cùng update cùng version; xác nhận một request nhận conflict khi optimistic concurrency được bật.
3. **Failure-path test:** Redis delete lỗi sau DB commit; xác nhận log/metric/retry hoặc outbox hoạt động.
4. **Consistency integration test:** tạo read đúng giữa update và invalidation; đảm bảo không tái-cache giá trị cũ theo strategy đã chọn.
5. **Load test:** theo dõi p95/p99, DB connections, Redis latency và cache-hit ratio.

## Quan sát trong production

Theo dõi `cache_hit_ratio`, cache miss theo key/category, DB query count và latency, Redis latency/errors, số `DbUpdateConcurrencyException`, p95/p99 endpoint, connection-pool saturation. Trace nên nối API → Redis → EF Core/DB. Alert khi cache miss hoặc DB QPS tăng đột biến cùng lúc.

## Câu hỏi phỏng vấn mở rộng

1. Nếu hệ thống chạy 20 replicas, in-memory lock còn giải quyết cache stampede không?
2. Nếu business yêu cầu read-after-write gần như tức thời, bạn thay đổi thiết kế thế nào?
3. Distributed lock có thể làm hệ thống tệ hơn trong failure mode nào?

# Code Review Challenge 2 — Authorization sai ranh giới và lộ dữ liệu nhạy cảm

**Chủ đề:** Authentication, authorization, sensitive-data exposure, logging  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Portal nội bộ có endpoint cho admin xem cấu hình mailbox offboarding của nhân viên. Người dùng đăng nhập bằng bearer token. Mỗi admin chỉ được quản lý một số business unit, nhưng production security review phát hiện khả năng truy cập record ngoài phạm vi và log chứa dữ liệu nhạy cảm.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/mail-configs")]
public sealed class MailConfigsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<MailConfigsController> _logger;

    public MailConfigsController(AppDbContext db, ILogger<MailConfigsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("{employeeId}")]
    public async Task<IActionResult> Get(string employeeId)
    {
        var userEmail = User.FindFirst("preferred_username")?.Value;
        _logger.LogInformation(
            "User {UserEmail} requested employee {EmployeeId}. Claims: {Claims}",
            userEmail,
            employeeId,
            string.Join(",", User.Claims.Select(x => $"{x.Type}={x.Value}")));

        var config = await _db.EmployeeOffboardingMailConfigs
            .Include(x => x.Employee)
            .FirstOrDefaultAsync(x => x.Employee.EmployeeCode == employeeId);

        if (config == null)
            return NotFound();

        return Ok(new
        {
            config.Employee.EmployeeCode,
            config.Employee.Email,
            config.TargetEmail,
            config.AutoReplyMessage,
            config.ForwardingEnabled,
            config.DelegateEnabled
        });
    }
}
```

## Kết quả code review tham khảo

### 1. Không có authorization requirement rõ ràng

- **Problem:** Endpoint không thể hiện policy/role requirement.
- **Why:** Có identity không đồng nghĩa caller được phép xem mail configuration.
- **Impact:** Nếu global/fallback policy không bảo vệ route, anonymous hoặc user không đủ quyền có thể truy cập; ngay cả khi authenticated, quyền vẫn quá rộng.
- **Severity:** Critical.
- **Fix:** Áp dụng authorization policy phù hợp và cấu hình fallback policy nếu đó là convention của ứng dụng.

### 2. Thiếu resource-level authorization theo business unit

- **Problem:** Query chỉ filter bằng `EmployeeCode`.
- **Why:** Caller có thể thay employee ID để đọc record ngoài scope.
- **Impact:** IDOR/BOLA-style data exposure.
- **Severity:** Critical.
- **Fix:** Enforce tenant/business-unit scope từ trusted claims/authorization service trong query hoặc resource authorization handler; không dựa vào ID caller gửi lên.

### 3. Log toàn bộ claims

- **Problem:** Serialize tất cả claim values vào application log.
- **Why:** Token-derived claims có thể chứa email, object IDs, group/role information hoặc dữ liệu không cần thiết.
- **Impact:** Tăng blast radius nếu log store bị truy cập, vi phạm data minimization.
- **Severity:** High.
- **Fix:** Chỉ log identifiers cần cho audit, dùng structured logging, classification/redaction theo chính sách hệ thống; tuyệt đối không log token.

### 4. Response trả dữ liệu nhạy cảm quá mức

- **Problem:** Trả email, target email và auto-reply content mà chưa chứng minh caller cần toàn bộ.
- **Impact:** Tăng exposure và ảnh hưởng khi authorization bug xảy ra.
- **Severity:** High.
- **Fix:** DTO tối thiểu theo use case; field-level authorization nếu cần.

### 5. Dùng `preferred_username` như audit identity chính

- **Problem:** Email/username có thể thay đổi và không phải lúc nào cũng là immutable identifier.
- **Impact:** Audit correlation yếu.
- **Severity:** Medium.
- **Fix:** Dùng stable subject/object identifier theo identity-provider contract của hệ thống, kèm display/email chỉ khi cần.

### 6. Query read-only vẫn tracking và load entity rộng

- **Problem:** `Include` load entity rồi map sau.
- **Impact:** Thừa allocation/tracking và có thể lấy nhiều column hơn cần thiết.
- **Severity:** Low/Medium.
- **Fix:** Filter authorization trong DB, `AsNoTracking`, projection trực tiếp sang DTO.

### 7. Không truyền CancellationToken

- **Problem:** DB query tiếp tục khi request bị hủy.
- **Severity:** Low/Medium.
- **Fix:** Nhận và truyền `CancellationToken`.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Authorize(Policy = "MailConfig.Read")]
[Route("api/mail-configs")]
public sealed class MailConfigsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ICurrentUserScope _scope;
    private readonly ILogger<MailConfigsController> _logger;

    public MailConfigsController(
        AppDbContext db,
        ICurrentUserScope scope,
        ILogger<MailConfigsController> logger)
    {
        _db = db;
        _scope = scope;
        _logger = logger;
    }

    [HttpGet("{employeeId}")]
    public async Task<ActionResult<MailConfigDto>> Get(
        string employeeId,
        CancellationToken ct)
    {
        var allowedBusinessUnits = await _scope.GetAllowedBusinessUnitsAsync(User, ct);
        var actorId = _scope.GetStableUserId(User);

        var result = await _db.EmployeeOffboardingMailConfigs
            .AsNoTracking()
            .Where(x => x.Employee.EmployeeCode == employeeId)
            .Where(x => allowedBusinessUnits.Contains(x.Employee.BusinessUnitId))
            .Select(x => new MailConfigDto(
                x.Employee.EmployeeCode,
                x.ForwardingEnabled,
                x.DelegateEnabled))
            .SingleOrDefaultAsync(ct);

        _logger.LogInformation(
            "Mail config read by {ActorId} for employee {EmployeeId}; found={Found}",
            actorId,
            employeeId,
            result is not null);

        return result is null ? NotFound() : Ok(result);
    }
}
```

`ICurrentUserScope` ở đây là abstraction minh họa: implementation phải lấy scope từ nguồn tin cậy và được kiểm thử. Nếu việc phân biệt “không tồn tại” và “không có quyền” làm lộ resource existence, response semantics cần được thiết kế thống nhất theo threat model.

## Trade-offs

Filter scope ngay trong query giúp tránh load resource trái phép nhưng logic authorization phức tạp có thể khó tái sử dụng; authorization handler/service tập trung dễ audit hơn. Trả DTO tối thiểu giảm exposure nhưng có thể cần endpoint riêng hoặc permission riêng cho màn hình quản trị nâng cao. Claims-based scope đơn giản nhưng nếu scope rất lớn hoặc thay đổi thường xuyên, cần cân nhắc server-side entitlement lookup và cache có invalidation phù hợp.

## Cách kiểm thử

1. **Authorization integration test:** user không có `MailConfig.Read` bị từ chối.
2. **Horizontal access test:** admin BU-A không đọc được employee BU-B dù biết chính xác employee ID.
3. **Positive test:** admin đúng scope nhận đúng DTO tối thiểu.
4. **Logging test:** xác nhận log không chứa bearer token, toàn bộ claims, target email hay auto-reply content.
5. **Scope-change test:** sau khi admin bị thu hồi quyền, access không tiếp tục tồn tại ngoài khoảng cache entitlement được chấp nhận.

## Quan sát trong production

Audit access theo stable actor ID, resource ID, action, decision và correlation ID; không ghi secrets/token. Theo dõi authorization-denied count, unusual cross-resource enumeration patterns, 401/403/404 rate, DB latency và policy-evaluation failures. Alert khi một actor thử nhiều employee IDs bất thường trong thời gian ngắn.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên dùng policy-based authorization và khi nào cần resource-based authorization?
2. Nếu admin quản lý hàng nghìn business units, `Contains` trong query còn là lựa chọn tốt không?
3. Trả `403` hay `404` khi caller không có quyền với một resource cụ thể? Trade-off là gì?
