# Câu 1 — API export tăng memory dù request đã kết thúc: GC, LOH và allocation thực sự đang làm gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C# runtime, allocation, GC, LOH, ASP.NET Core, streaming, diagnostics, performance

## Bối cảnh

Một ASP.NET Core API trên .NET 8 có endpoint export báo cáo. Endpoint query khoảng 50.000–300.000 rows từ SQL Server, serialize thành JSON rồi trả về client. Sau khi feature được mở cho nhiều người dùng, memory của App Service tăng mạnh vào giờ cao điểm; GC activity tăng và đôi lúc instance restart. Developer thấy request đã hoàn tất nhưng process memory không giảm ngay nên kết luận rằng “GC bị leak” và đề xuất gọi `GC.Collect()` sau mỗi export.

Code hiện tại tạo một `List<ReportRow>`, serialize toàn bộ thành một `string`, sau đó chuyển sang UTF-8 bytes trước khi trả response. Chưa có memory dump, allocation profile, GC counters hoặc bằng chứng object nào còn rooted.

## Câu hỏi chính

Hãy giải thích những allocation nào có thể xảy ra trong flow này, vì sao process memory không giảm ngay sau request không tự động chứng minh memory leak, LOH/GC có thể liên quan thế nào, cách bạn kiểm chứng nguyên nhân, và bạn sẽ sửa endpoint theo hướng nào trước khi cân nhắc `GC.Collect()`.

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước trung bình của payload và số request export chạy đồng thời là bao nhiêu?
2. App Service memory limit/restart evidence và GC mode hiện tại là gì?
3. Object nào đang chiếm heap theo memory dump/allocation profile; có object còn rooted sau nhiều GC cycle không?
4. EF Core query đang tracking hay projection/no-tracking, và dữ liệu có bắt buộc materialize toàn bộ không?
5. Client có chấp nhận streaming/chunked response hoặc file generation bất đồng bộ không?

## Gợi ý tư duy

### Gợi ý 1

Tách **managed heap live objects**, **allocated/committed memory**, và **process working set**; chúng không phải cùng một metric.

### Gợi ý 2

Một payload lớn có thể tồn tại đồng thời dưới nhiều representation: entities/DTOs, `string`, UTF-8 `byte[]` và serialization buffers.

### Gợi ý 3

Đừng chữa GC trước khi chứng minh retention hay allocation pressure bằng counters/profile/dump.

## Cấu trúc trả lời đề xuất

1. Làm rõ workload và memory symptoms.
2. Vẽ allocation lifecycle của một export request.
3. Phân biệt allocation pressure với leak/retention.
4. Giải thích GC generations và LOH ở mức cần thiết.
5. Thu thập GC counters, allocation profile và dump.
6. Xác định object types/root paths lớn nhất.
7. Giảm materialization/copy bằng projection và streaming.
8. Load test theo concurrency thực tế.
9. Theo dõi memory, GC pause, allocation rate và restart sau rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận leak chỉ từ working set không giảm ngay.
- Nhận ra nhiều large allocations/copies trong flow hiện tại.
- Không dùng `GC.Collect()` như default production fix.
- Đo allocation rate, heap size, GC collections/pause và inspect dump/root nếu nghi retention.
- Giảm materialization và streaming khi contract cho phép.
- Tính concurrency: một request ổn không có nghĩa nhiều export đồng thời ổn.

### Điểm cộng

- EF Core projection + `AsNoTracking` khi phù hợp.
- Phân biệt live heap, committed memory và OS working set.
- Nhắc đến LOH cho large objects mà không biến threshold cụ thể thành trọng tâm phỏng vấn.
- Dùng `dotnet-counters`, `dotnet-trace`, profiler hoặc dump theo môi trường cho phép.

### Senior+

- Đánh giá synchronous streaming vs background export + Blob Storage tùy SLA/payload.
- Đặt concurrency/backpressure thay vì chỉ tối ưu từng request.
- Đề xuất performance budget dựa trên p95/p99, allocation/request và peak concurrency.

## Hướng giải quyết tham khảo

Tôi sẽ không gọi đây là leak trước khi chứng minh object còn được giữ reference ngoài lifetime mong muốn. Trong flow hiện tại, dữ liệu có thể được materialize thành hàng trăm nghìn objects trong `List`, sau đó serializer tạo một `string` lớn, rồi code lại tạo `byte[]` UTF-8. Trong một khoảng thời gian, nhiều representation có thể cùng tồn tại. Nếu nhiều request chạy đồng thời, peak memory có thể tăng theo concurrency rất nhanh.

GC thu hồi managed objects khi chúng không còn reachable, nhưng việc object được collect không đồng nghĩa process working set lập tức trả toàn bộ memory cho OS. Runtime quản lý heap segments và có thể giữ committed/reserved memory để tái sử dụng. Vì vậy cần nhìn managed heap và allocation/GC evidence, không chỉ một biểu đồ working set.

Large buffers/string có thể tạo pressure ở LOH. Điều cần kiểm chứng là allocation rate, heap composition, GC frequency/pause và root paths. Tôi sẽ reproduce với representative payload/concurrency, thu counters và allocation trace; nếu heap tiếp tục tăng qua nhiều GC cycle thì capture dump và xem dominant types cùng GC roots. Nếu live heap ổn nhưng working set cao, investigation sẽ khác với trường hợp có rooted collections/cache thực sự tăng vô hạn.

Ở implementation, trước tiên giảm số representation: project đúng columns, tránh tracking nếu không cần update, tránh `ToListAsync` nếu contract có thể stream, serialize trực tiếp ra response stream thay vì tạo toàn bộ JSON string rồi UTF-8 copy. Cancellation phải propagate từ `HttpContext.RequestAborted`. Nếu export rất lớn và user không cần response ngay, background generation + private Blob Storage/download workflow có thể phù hợp hơn, nhưng chỉ khi requirement chấp nhận asynchronous UX.

`GC.Collect()` ép collection toàn cục và có thể làm latency/throughput xấu hơn; nó không sửa reference leak hay thiết kế tạo quá nhiều data. Chỉ cân nhắc manual collection trong các workload rất đặc thù sau profiling, không phải request-level cleanup mặc định.

## Mẫu trả lời trong phỏng vấn

“Em chưa gọi đây là memory leak chỉ vì App Service working set không giảm ngay. Em muốn phân biệt live managed heap, allocation rate và process working set. Flow hiện tại có khả năng giữ nhiều bản của cùng dữ liệu: EF objects/DTOs, một JSON string lớn và thêm UTF-8 byte array. Với nhiều exports đồng thời, peak memory có thể tăng rất nhanh và large buffers còn tạo GC/LOH pressure.

Em sẽ reproduce với payload và concurrency thực tế, xem GC counters, allocation profile và nếu live heap tiếp tục tăng thì lấy dump để xem object types và GC roots. Nếu object không còn reachable sau request nhưng working set vẫn cao, đó chưa phải bằng chứng leak.

Về sửa code, em ưu tiên projection, `AsNoTracking` khi phù hợp, tránh materialize toàn bộ và serialize trực tiếp ra response stream, đồng thời propagate request cancellation và giới hạn concurrency nếu endpoint quá nặng. Nếu export hàng trăm nghìn rows là workflow dài, em sẽ hỏi business có chấp nhận background export sang Blob Storage không. Em sẽ không thêm `GC.Collect()` sau mỗi request vì nó không sửa root cause và có thể làm latency xấu hơn.”

## Câu hỏi đào sâu

1. Nếu dump cho thấy live heap nhỏ nhưng working set vẫn cao, bạn sẽ điều tra tiếp theo hướng nào?
2. Streaming giảm peak memory nhưng client rất chậm; backpressure và connection lifetime thay đổi trade-off ra sao?
3. Bạn vừa đề xuất background export; nếu requirement bắt buộc download bắt đầu trong 2 giây thì thiết kế thay đổi thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất working set với managed live heap.
- Khẳng định GC “không chạy” chỉ vì memory graph không giảm.
- Gọi `GC.Collect()` sau mỗi request như cleanup pattern.
- Chỉ nói “streaming” mà không xét query materialization, slow client và cancellation.
- Tối ưu dựa trên một request mà bỏ qua peak concurrency.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất `GC.Collect()`/tăng RAM, không giải thích allocation hay đo đạc.
- **3–4:** Biết GC/LOH nhưng thiếu evidence-driven diagnosis.
- **5–6:** Phân biệt leak và pressure, đề xuất profiling + giảm copies hợp lý.
- **7–8:** Giải thích tốt lifecycle, streaming, EF behavior, concurrency và telemetry.
- **9–10:** Kết nối runtime mechanism với production capacity, backpressure, alternative workflow và conditional trade-offs rõ ràng.

# Câu 2 — Optimizely publish thành công nhưng người dùng vẫn thấy nội dung cũ qua CDN

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, Akamai/CDN, HTTP caching, cache invalidation, observability, incident response, deployment/web performance

## Bối cảnh

Một marketing website dùng Optimizely CMS phía origin và Akamai ở edge. Editor publish thay đổi campaign lúc 09:00. Một số người dùng thấy nội dung mới ngay, một số vẫn thấy nội dung cũ trong 20–40 phút. Purge thủ công đôi khi làm nội dung cập nhật, nhưng không phải lúc nào cũng tái hiện được. Origin logs không cho thấy error đáng kể và CPU/SQL bình thường.

Team vừa thay đổi cache policy cho HTML để giảm origin load. Website có nhiều hostname theo market/language, query parameters cho tracking, và một số page có personalization. Bạn chưa biết cache key thực tế, response headers, TTL, purge scope, browser cache behavior hay liệu stale response đến từ edge hay browser.

## Câu hỏi chính

Bạn là người xử lý incident. Hãy mô tả cách đánh giá impact, stabilize hệ thống, thu evidence để phân biệt CMS publish/cache, origin, Akamai edge và browser caching; cách hình thành/loại trừ nhiều giả thuyết; remediation ngắn hạn; và thiết kế lâu dài để nội dung publish có freshness contract rõ ràng mà không vô hiệu hóa lợi ích CDN.

## Câu hỏi làm rõ nên cân nhắc

1. Business freshness SLA sau publish là bao lâu và page nào được phép cache?
2. Response headers ở origin và edge (`Cache-Control`, `Age`, `ETag`, cache-status-related headers nếu có) cho URL bị lỗi là gì?
3. Cache key có gồm hostname, path, query string, language/cookie/personalization dimensions nào?
4. Purge được trigger tự động từ publish event hay thủ công; purge theo URL/tag/key nào và có failure telemetry không?
5. User thấy stale content trên hard refresh/private window/edge region khác nhau thế nào?

## Gợi ý tư duy

### Gợi ý 1

Đầu tiên phải chứng minh stale copy đang nằm ở **browser, edge hay origin**.

### Gợi ý 2

Một URL “giống nhau” về business có thể trở thành nhiều cache objects do hostname, query string, variation hoặc cache key configuration.

### Gợi ý 3

Freshness là contract giữa CMS publish, origin headers, CDN policy và invalidation—not chỉ một nút purge.

## Cấu trúc trả lời đề xuất

1. Xác định page/market/user impact và freshness SLA.
2. Stabilize các campaign-critical URLs nếu cần.
3. Capture cùng request ở origin-bypass/edge/browser với headers và body version marker.
4. So sánh cache key dimensions và TTL.
5. Kiểm tra publish event + purge request/result telemetry.
6. Giữ nhiều hypotheses cho đến khi evidence loại trừ.
7. Áp dụng remediation nhỏ nhất có rollback.
8. Thiết kế invalidation/versioning policy lâu dài.
9. Test nhiều host/language/query/personalization cases.
10. Alert theo publish-to-visible latency và purge failures.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nhảy thẳng sang “purge toàn CDN”.
- Phân biệt origin, edge và browser bằng evidence.
- Kiểm tra cache key/TTL/headers và purge scope.
- Nhận ra personalized content có cache-safety requirements riêng.
- Có stabilization, rollback và verification.
- Thiết kế telemetry cho publish → purge → visible content.

### Điểm cộng

- Dùng content/version marker hoặc correlation để so sánh responses.
- Kiểm tra query-string normalization và multi-host/multi-language variants.
- Đề xuất `Cache-Control` theo content class thay vì một TTL toàn site.
- Cân nhắc stale-while-revalidate/stale-if-error chỉ khi business semantics cho phép.

### Senior+

- Xây freshness SLO cho campaign-critical content.
- Tách purge reliability khỏi CMS publish success; purge là external distributed operation có thể partial-fail.
- Thiết kế cacheability cho personalization để tránh data leakage/cross-user content.

## Hướng giải quyết tham khảo

Đầu tiên tôi sẽ xác định blast radius: market/hostname/page nào, bao nhiêu users, campaign nào có deadline và freshness SLA thực tế. Nếu đây là campaign-critical incident, stabilization có thể là tạm giảm TTL hoặc bypass caching cho một tập URL nhỏ đã xác định, không phải disable CDN toàn site khi chưa cần.

Tôi sẽ lấy một URL stale cụ thể và so sánh ba góc nhìn: response từ origin theo đường kiểm soát phù hợp, response qua Akamai, và browser/network trace của user. Tôi cần headers, `Age`, cache-control semantics và một content version marker để biết copy nào đang được phục vụ. Nếu origin đã mới nhưng edge cũ, focus vào edge key/TTL/invalidation. Nếu edge mới nhưng browser cũ, kiểm tra browser cache directives. Nếu origin cũng cũ, quay về CMS/content delivery/cache layer ở origin.

Các hypotheses nên tồn tại song song: purge chỉ match canonical URL nhưng traffic có tracking query variants; hostname/language tạo cache keys khác; TTL mới dài hơn dự kiến; publish hook gửi purge nhưng call thất bại/timeout; personalized page bị cache như public HTML; hoặc browser nhận max-age quá dài. Tôi sẽ dùng evidence để loại trừ từng hypothesis thay vì sửa hàng loạt.

Ngắn hạn, purge chính xác các affected variants hoặc điều chỉnh policy cho affected content class, rồi verify từ nhiều edge paths/markets. Dài hạn, define cache matrix: static assets có immutable/versioned URLs; public HTML có TTL/freshness policy rõ; campaign-critical content có automated invalidation; personalized/user-specific response không được shared-cache nếu có nguy cơ cross-user leakage. Publish workflow nên emit event/operation ID, purge request/result và metric publish-to-visible latency.

Nếu purge provider partial-fail, cần retry có giới hạn, idempotent invalidation request nếu provider semantics cho phép, dashboard/alert và manual fallback. Không nên coi CMS publish thành công đồng nghĩa toàn bộ distributed delivery path đã fresh.

## Mẫu trả lời trong phỏng vấn

“Em sẽ bắt đầu bằng impact và một URL stale cụ thể, sau đó chứng minh stale copy nằm ở đâu. Em muốn so sánh origin response, Akamai response và browser network trace, kèm headers như `Cache-Control`, `Age` và một content version marker. Nếu origin mới nhưng edge cũ thì em điều tra cache key, TTL và purge; nếu edge mới nhưng browser cũ thì xem browser caching; nếu origin cũng cũ thì quay lại Optimizely/content-delivery cache.

Em sẽ giữ nhiều giả thuyết: query-string variants, hostname/language key, purge scope thiếu, publish hook thất bại, TTL policy mới hoặc personalization bị cache sai. Với campaign quan trọng, em có thể tạm bypass/giảm TTL cho đúng nhóm URL thay vì tắt CDN toàn site.

Lâu dài em muốn cache policy theo content class và freshness SLA, automated invalidation có telemetry từ publish đến purge result, cùng metric publish-to-visible latency. Personalized content phải có cache-safety rule riêng. Mục tiêu không phải ‘không cache’, mà là cache có contract và biết chính xác khi nào nội dung phải fresh.”

## Câu hỏi đào sâu

1. Nếu purge API trả success nhưng một region vẫn stale, bạn sẽ thiết kế verification/retry như thế nào mà không tạo purge storm?
2. Nếu business yêu cầu campaign page cập nhật toàn cầu trong dưới một phút, bạn đánh đổi TTL, purge, origin load và cost thế nào?
3. Bạn đề xuất cache public HTML; nếu page có personalization theo cookie thì recommendation thay đổi ra sao?

## Lỗi trả lời thường gặp

- Purge toàn bộ CDN ngay mà không xác định cache layer/root cause.
- Chỉ kiểm tra CMS publish status và bỏ qua delivery path.
- Không xét query/hostname/language cache-key variants.
- Cache personalized HTML như public response mà không đánh giá security.
- Không có telemetry cho purge request/result và freshness latency.

## Thang điểm 0–10

- **0–2:** Chỉ nói purge/restart.
- **3–4:** Biết CDN TTL nhưng investigation tuyến tính và thiếu evidence.
- **5–6:** Phân biệt browser/edge/origin, có cache-key reasoning và remediation.
- **7–8:** Incident flow đầy đủ, nhiều hypotheses, security/personalization và telemetry tốt.
- **9–10:** Thiết kế freshness SLO, distributed invalidation reliability, safe degradation và verification có hệ thống.

# Câu 3 — Modernize nền tảng nội bộ: Modular Monolith, Microservices hay chỉ nâng cấp .NET trước?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET modernization, architecture boundaries, SQL, deployment, migration, reliability, testing, CI/CD, cost of complexity

## Bối cảnh

Một internal employee platform chạy `.NET Framework 4.5` trên IIS/Windows Server, dùng một SQL Server database chung. Hệ thống gồm attendance, leave approval, timesheet, employee profile và notification. Khoảng 1.500 nhân viên dùng hệ thống; peak traffic không lớn nhưng deployment hiện tại rủi ro vì mọi module release cùng nhau. Một số thư viện cũ khó nâng cấp và automated tests rất ít.

Management muốn “modernize lên cloud” và một đề xuất là tách ngay thành 8 microservices chạy Kubernetes. Một đề xuất khác là migrate toàn bộ sang .NET 8/modern .NET trong một big-bang release. Team chỉ có vài backend developers và vẫn phải duy trì feature delivery. Requirement về independent scaling gần như chưa có; pain points rõ nhất là unsupported/legacy runtime, release risk, test coverage thấp và coupling giữa modules.

## Câu hỏi chính

Hãy đề xuất modernization strategy theo giai đoạn. Bạn sẽ quyết định thế nào giữa giữ layered monolith, chuyển sang Modular Monolith, tách một số services, App Service hay Kubernetes; làm sao quản lý database/schema, compatibility, testing, rollout/rollback và observability mà không biến modernization thành một rewrite kéo dài nhiều năm?

## Câu hỏi làm rõ nên cân nhắc

1. Module nào thay đổi thường xuyên nhất và module nào có dependency/coupling mạnh nhất?
2. Có integration nào phụ thuộc Windows/IIS/.NET Framework-only libraries hay authentication mechanism cũ không?
3. Downtime/rollback requirement và release frequency hiện tại là gì?
4. Database có cross-module joins/stored procedures/shared tables ở mức nào?
5. Team có operational capability nào cho containers/Kubernetes, và cloud migration có deadline/compliance constraint không?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu từ **risk và business pain**, không bắt đầu từ target architecture đẹp nhất.

### Gợi ý 2

Runtime modernization, module boundary modernization và hosting modernization có thể là ba trục khác nhau; không nhất thiết đổi cùng lúc.

### Gợi ý 3

Independent deployment chỉ có giá trị khi ownership/data/dependency boundaries đủ rõ; nếu không, microservices có thể chuyển coupling từ compile-time sang network/runtime.

## Cấu trúc trả lời đề xuất

1. Inventory dependencies, runtime blockers và business-critical flows.
2. Establish characterization/integration tests cho behavior hiện tại.
3. Tách configuration/secrets/observability khỏi code legacy.
4. Chọn incremental runtime migration path dựa trên compatibility evidence.
5. Xác định module boundaries và dependency rules.
6. Quyết định hosting đơn giản nhất đáp ứng requirement.
7. Xử lý database ownership/schema evolution theo từng phase.
8. Thiết kế CI/CD, migration ordering, canary/slot/rollback.
9. Chỉ extract service khi có driver rõ.
10. Đo lead time, failure rate, incident rate và modernization progress.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định Microservices/Kubernetes là đích đến.
- Không mặc định rewrite-from-scratch.
- Inventory dependency/compatibility trước migration.
- Thêm tests/observability trước các thay đổi lớn.
- Tách modernization thành phases có rollback.
- Xử lý database coupling như một vấn đề kiến trúc chính.
- Có release/migration strategy giảm blast radius.

### Điểm cộng

- Modular Monolith như một intermediate/final state hợp lý nếu scale/ownership chưa cần services.
- Strangler/incremental replacement cho phần khó migrate.
- Deployment slots/App Service hoặc simpler hosting nếu Kubernetes chưa có driver.
- Contract tests/integration tests cho boundaries được tách.

### Senior+

- Đặt exit criteria cho từng phase và tiêu chí rõ để extract service.
- Tách logical ownership trước physical database split.
- Đánh giá organizational/operational cost của distributed systems.
- Có kế hoạch rollback cho cả app và schema, tránh migration không backward-compatible.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng “8 microservices trên Kubernetes” vì pain points hiện tại chưa chứng minh cần independent scaling hoặc distributed deployment. Với team nhỏ, thêm service discovery, network failure, tracing, distributed consistency và cluster operations có thể làm release risk tăng thay vì giảm. Tôi cũng tránh big-bang rewrite vì hệ thống có business behavior tích lũy nhưng automated tests ít.

Phase đầu là discovery và safety net: inventory projects/packages, .NET Framework-only APIs, IIS dependencies, authentication, scheduled jobs, third-party integrations và database coupling. Bổ sung characterization tests cho critical workflows, integration tests quanh SQL/integrations, baseline telemetry và reproducible build/deploy. Mục tiêu là biết behavior nào phải giữ và có tín hiệu khi migration phá nó.

Sau đó tôi tách runtime modernization khỏi architecture modernization. Có thể cần một bước bridge tùy compatibility thực tế; target modern .NET phải dựa trên package/API support chứ không ép mọi module cùng ngày. Với code còn nằm chung, tôi sẽ làm rõ module boundaries—Attendance, Leave, Timesheet, Profile, Notification—và enforce dependency direction. Modular Monolith có thể giảm coupling và release/test ownership mà chưa trả distributed-system tax.

Database là phần khó: ban đầu vẫn có thể dùng một SQL Server physical database nhưng tạo logical ownership/schema/API boundaries, giảm cross-module writes và catalog các stored procedures/joins. Không nên split database chỉ để gọi là microservices. Nếu sau này một module có nhu cầu independent deployment/scale, ownership rõ và ít cross-boundary transaction, lúc đó mới đánh giá extraction. Notification/background processing có thể là candidate nếu failure/throughput/ownership thật sự độc lập, nhưng cần evidence.

Hosting cũng chọn theo requirement. Nếu App Service đáp ứng availability, deployment slots, scaling và operational model, nó có thể đơn giản hơn Kubernetes. Kubernetes chỉ nên vào khi có concrete drivers và team đủ operational maturity.

Mỗi phase cần backward-compatible schema migration khi có rolling deployment, release nhỏ, feature flags khi hữu ích, deployment slot/canary strategy, database backup/recovery và rollback plan. Một migration schema phá backward compatibility không thể “rollback app” an toàn chỉ bằng redeploy binary cũ.

Tôi sẽ đo deployment frequency, change failure rate, recovery time, automated critical-flow coverage, legacy dependency count và module coupling. Modernization thành công khi delivery an toàn hơn và legacy risk giảm, không phải khi diagram có nhiều boxes hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn microservices/Kubernetes trước khi chứng minh requirement. Pain hiện tại là legacy runtime, release risk, ít tests và coupling, nên em ưu tiên giảm những rủi ro đó trước. Em sẽ inventory dependency/IIS/.NET Framework blockers và database coupling, rồi thêm characterization/integration tests cùng baseline observability cho critical flows.

Em tách ba quyết định: nâng runtime, cải thiện module boundaries và đổi hosting. Chúng không cần xảy ra cùng lúc. Với team nhỏ và traffic vừa phải, em có thể hướng code về Modular Monolith trên modern .NET, giữ SQL Server nhưng tạo logical data ownership và giảm cross-module writes. App Service có thể đủ; Kubernetes chỉ đáng cân nhắc nếu có driver như platform standardization, scheduling/networking/scale requirements mà App Service không đáp ứng tốt.

Em sẽ migrate theo slices nhỏ, dùng backward-compatible schema changes, rollout có slot/canary/feature flag khi phù hợp và rollback được. Chỉ extract một module thành service khi nó có boundary, ownership và independent deployment/scale requirement rõ. Em đo kết quả bằng release safety, lead time, incident rate và số legacy dependencies giảm đi, chứ không đo bằng số microservices tạo ra.”

## Câu hỏi đào sâu

1. Nếu management bắt buộc Kubernetes vì platform standard của công ty, bạn sẽ giảm operational risk của migration thế nào?
2. Bạn khuyến nghị Modular Monolith; nếu Notification cần scale gấp 20 lần và release độc lập hàng ngày thì tiêu chí extraction thay đổi ra sao?
3. Nếu một stored procedure critical join dữ liệu của bốn modules và không thể bỏ ngay, bạn làm gì để tiến tới data ownership mà không big-bang rewrite?

## Lỗi trả lời thường gặp

- Coi microservices/Kubernetes là “modern” nên mặc định tốt hơn.
- Rewrite toàn bộ trước khi tạo tests/observability.
- Chỉ nói code layers mà bỏ qua database coupling và release mechanics.
- Chuyển app và schema theo breaking migration không có rollback compatibility.
- Đưa ra target architecture nhưng không có phased migration/exit criteria.

## Thang điểm 0–10

- **0–2:** Chọn buzzword architecture mà không làm rõ requirement/risk.
- **3–4:** Có migration idea nhưng big-bang hoặc thiếu database/rollback.
- **5–6:** Incremental plan hợp lý, tests và compatibility được xét.
- **7–8:** Phân tách runtime/architecture/hosting, data ownership và release safety rõ.
- **9–10:** Conditional architecture judgment xuất sắc, có exit criteria, operational cost, rollback/schema strategy và metrics chứng minh modernization tạo giá trị.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hôm nay tập trung vào ba dạng reasoning khác nhau: hiểu runtime thay vì suy đoán từ một memory graph; xử lý distributed cache incident bằng evidence thay vì purge mù; và modernization dựa trên risk/requirements thay vì chọn kiến trúc theo xu hướng. Điểm chung là phải phân biệt triệu chứng với cơ chế thực sự, xác định boundary nơi failure xảy ra, rồi chọn giải pháp nhỏ nhất đáp ứng correctness và operability.

## Mẫu tư duy cần nhớ

- **Measure before optimizing:** phân biệt live heap, allocation pressure và working set trước khi “sửa GC”.
- **Locate the stale layer before invalidating:** origin, edge và browser là ba failure domains khác nhau.
- **Modernize by risk, not by buzzword:** runtime, architecture và hosting là các quyết định có thể tách rời.
- **Prefer reversible phases:** migration tốt phải có verification và rollback path.
- **Complexity needs a driver:** Microservices, Kubernetes hay background workflow chỉ đáng thêm khi requirement/evidence biện minh cho cost.
