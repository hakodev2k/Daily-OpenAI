# Câu 1 — Cosmos DB query “đúng dữ liệu” nhưng RU tăng mạnh: partition key, point read và query routing thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, logical partition, physical partition, RU, point read, cross-partition query, query routing, indexing, .NET SDK, data modeling, production diagnostics

## Bối cảnh

Một ASP.NET Core .NET 8 API lưu hồ sơ notification preferences trong Azure Cosmos DB for NoSQL. Container hiện có khoảng 60 triệu items.

Document đơn giản hóa:

```json
{
  "id": "preference-83421",
  "tenantId": "tenant-17",
  "userId": "user-9281",
  "channel": "email",
  "enabled": true,
  "updatedAtUtc": "2026-09-10T03:15:00Z"
}
```

Container được partition theo `/tenantId`.

Hai code paths đang tồn tại:

```csharp
var response = await container.ReadItemAsync<Preference>(
    id: preferenceId,
    partitionKey: new PartitionKey(tenantId),
    cancellationToken: ct);
```

và:

```csharp
var query = new QueryDefinition(
    "SELECT * FROM c WHERE c.id = @id")
    .WithParameter("@id", preferenceId);

using var iterator = container.GetItemQueryIterator<Preference>(query);
```

Sau khi một feature mới được release:

- request count chỉ tăng khoảng 15%;
- tổng RU consumption tăng gần 4 lần;
- một số requests bị 429 khi load cao;
- latency p95 tăng rõ trong giờ cao điểm;
- database team nói “query theo id thì chắc chắn tương đương point read”;
- một developer đề xuất tăng provisioned RU/s ngay;
- chưa có breakdown RU theo operation type, partition key value, query text hoặc tenant;
- một số tenant rất lớn, một số tenant nhỏ;
- không rõ feature mới có biết `tenantId` tại thời điểm đọc hay chỉ biết `preferenceId`.

## Câu hỏi chính

Hãy giải thích **Cosmos DB dùng partition key để route request như thế nào**, vì sao `ReadItemAsync(id, partitionKey)` khác về cơ chế và cost profile so với query `WHERE c.id = @id`, và tại sao query “lọc đúng một item theo id” vẫn có thể tốn nhiều RU hơn. Sau đó trình bày cách bạn xác minh nguyên nhân RU spike, đánh giá partition key hiện tại và quyết định nên tối ưu code path, data model, partitioning hay throughput.

## Câu hỏi làm rõ nên cân nhắc

1. Feature mới có luôn biết cả `id` và `tenantId` hay chỉ biết `id`?
2. Query iterator có được truyền partition key trong `QueryRequestOptions` hay không?
3. RU spike tập trung ở một số tenants/partition keys hay phân bố đều?
4. Có thay đổi indexing policy, item size hoặc projection (`SELECT *`) cùng release không?
5. 429 xảy ra trên toàn container hay chủ yếu ở một partition key/hot workload pattern?

## Gợi ý tư duy

### Gợi ý 1

Đừng đồng nhất “query trả một row” với “point read”. Hãy xem service biết gì để route request trước khi thực thi.

### Gợi ý 2

Partition key không chỉ là field để filter. Nó quyết định logical data distribution và khả năng route tới subset phù hợp.

### Gợi ý 3

Tăng RU/s chỉ hợp lý sau khi biết request charge đến từ legitimate load hay từ access pattern kém hiệu quả.

## Cấu trúc trả lời đề xuất

1. Làm rõ request/access pattern thực tế.
2. Giải thích logical partition và request routing.
3. So sánh point read với SQL query.
4. Đo RU charge theo operation và tenant.
5. Phân tích 429, hot partition và cross-partition behavior.
6. Kiểm tra indexing/projection/item size.
7. Ưu tiên code-path fixes ít rủi ro.
8. Đánh giá lại partition key nếu workload đã thay đổi.
9. Chỉ tăng throughput khi evidence cho thấy cần capacity thật.
10. Load test và monitor sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Point read cần cả item `id` và partition key value để Cosmos DB định vị trực tiếp item trong logical partition phù hợp.
- Query `WHERE c.id = @id` không tự động trở thành point read chỉ vì predicate là `id`.
- Nếu query không có partition key restriction phù hợp, service có thể phải fan out/query qua nhiều partitions.
- Cross-partition query có thể tăng RU và latency dù final result chỉ có một item.
- RU phải được đo từ response diagnostics/request charge, không đoán từ số rows trả về.
- 429 là tín hiệu throttling và cần correlate với consumed RU, partition distribution và workload pattern.
- Partition key quality phải được đánh giá từ cardinality, distribution và dominant access patterns.
- Không nên tăng RU/s trước khi loại trừ query/access-pattern regression.

### Điểm cộng

- Nếu code biết `tenantId`, dùng point read khi semantics phù hợp thay vì query theo `id`.
- Nếu query business cần theo tenant, truyền partition key/request options để giới hạn query scope khi phù hợp.
- `SELECT *` có thể làm response payload lớn hơn cần thiết; projection có thể giảm payload/network và đôi khi ảnh hưởng query cost, nhưng không thay thế đúng partition routing.
- Theo dõi RU theo tenant để phát hiện hot tenant.
- Nhận ra một partition key như `/tenantId` có thể tốt cho tenant-scoped reads nhưng có nguy cơ hot partition với tenant cực lớn; cần đo trước khi đổi model.
- Cân nhắc hierarchical partition keys hoặc alternate container/model nếu access pattern thực sự cần scale vượt giới hạn của một logical partition hoặc nhiều dimensions, nhưng không đổi chỉ vì một spike.

### Senior+

- Tách hai vấn đề: **capacity saturation** và **inefficient request shape**.
- Nêu được rằng logical partition distribution và physical partition mapping là implementation concern mà application gián tiếp chịu ảnh hưởng qua partition key design.
- Đề xuất observability theo operation name, partition key hash/category, request charge, retries, 429 rate và latency.
- Nhận ra nếu application chỉ biết `id`, root problem có thể là data model/API contract thiếu partition-key information; giải pháp có thể là carry `tenantId` cùng identifier hoặc maintain lookup strategy có chủ đích thay vì query toàn container.
- Đưa ra migration strategy nếu partition key thực sự cần thay đổi thay vì giả định có thể sửa in-place đơn giản.

## Hướng giải quyết tham khảo

Cosmos DB phân phối items theo partition key. Trong container `/tenantId`, mỗi item thuộc logical partition được xác định từ giá trị `tenantId`. Với point read, application cung cấp cả `id` và partition key, nên request có thể được route trực tiếp tới partition phù hợp và đọc item theo key.

Ví dụ:

```csharp
var result = await container.ReadItemAsync<Preference>(
    preferenceId,
    new PartitionKey(tenantId),
    cancellationToken: ct);

logger.LogInformation(
    "Cosmos point read RU={RequestCharge}",
    result.RequestCharge);
```

Microsoft Learn mô tả point read bằng item ID + partition key là loại read hiệu quả nhất. Theo tài liệu hiện hành, point read cho item 1 KB ở default consistency thường có cost rất thấp và là baseline phù hợp để so sánh với query; exact RU còn phụ thuộc item size và consistency, vì vậy không nên hard-code assumption cho mọi workload.

Query sau:

```sql
SELECT * FROM c WHERE c.id = @id
```

không phải point read. Nếu query request không có partition key scope, SDK/service có thể phải evaluate query trên nhiều partitions để tìm item phù hợp. Final result count = 1 không có nghĩa work performed = 1 item lookup.

Nếu code biết tenant:

```csharp
var options = new QueryRequestOptions
{
    PartitionKey = new PartitionKey(tenantId)
};

using var iterator = container.GetItemQueryIterator<Preference>(
    query,
    requestOptions: options);
```

nhưng nếu objective chỉ là đọc item theo `id` + `tenantId`, point read vẫn là API rõ intent hơn.

Kế hoạch điều tra production:

1. Instrument `RequestCharge`, status code, retry count và operation type.
2. Correlate RU spike với feature flag/release timestamp.
3. So sánh point reads vs queries theo cùng business operation.
4. Group 429 theo tenant/partition-key value để phát hiện hot tenant.
5. Kiểm tra query options có partition key hay cross-partition.
6. Kiểm tra indexing policy và document growth nếu release có thay đổi schema.
7. Kiểm tra response payload và projection.
8. Test representative production-like data với diagnostics enabled.

Nếu feature mới chỉ có `preferenceId` mà không có `tenantId`, tôi sẽ hỏi tại sao API/domain contract làm mất partition-key information. Có thể sửa để identifier context luôn carry tenant. Một secondary lookup có thể tồn tại nếu business thật sự cần global lookup, nhưng cần đánh giá consistency/cost.

Nếu sau khi chuyển đúng point reads, bỏ cross-partition query không cần thiết và xác minh không có hot-partition issue mà legitimate traffic vẫn chạm capacity, tăng RU/s/autoscale có thể là bước đúng. Capacity tuning là quyết định sau measurement, không phải phản xạ đầu tiên.

Tài liệu tham khảo hiện hành:

- Microsoft Learn — Request Units in Azure Cosmos DB: `https://learn.microsoft.com/azure/cosmos-db/request-units`
- Microsoft Learn — Optimize request cost: `https://learn.microsoft.com/azure/cosmos-db/optimize-cost-reads-writes`
- Microsoft Learn — Partitioning and horizontal scaling: `https://learn.microsoft.com/azure/cosmos-db/partitioning`

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách result cardinality khỏi request routing. `ReadItemAsync` với `id` và partition key là point read vì Cosmos DB biết logical partition cần đến. `SELECT * WHERE id = ...` không tự thành point read. Nếu query không được scope theo partition key, service có thể phải query nhiều partitions dù cuối cùng chỉ trả một item, nên RU và latency tăng.

Em sẽ instrument `RequestCharge`, operation type, retry/429 và tenant, rồi so sánh trước/sau release. Nếu feature mới bỏ mất `tenantId`, em xem đó là access-pattern/API-contract issue trước khi tăng RU. Nếu biết tenant thì dùng point read hoặc partition-scoped query tùy semantics.

Em cũng kiểm tra hot tenants, indexing và item size. Chỉ khi request shape đã hợp lý mà legitimate throughput vẫn vượt capacity thì em mới tăng RU/s. Nếu `/tenantId` gây hot partition vì một tenant cực lớn, lúc đó mới đánh giá partition-key redesign hoặc hierarchical strategy với migration plan rõ ràng.”

## Câu hỏi đào sâu

1. Nếu 90% workload là tenant-scoped nhưng một tenant chiếm 45% traffic, bạn đánh giá `/tenantId` thế nào và cần evidence gì trước khi đổi partition key?
2. Nếu Product yêu cầu lookup global chỉ bằng `preferenceId`, bạn sẽ thay API contract, thêm lookup store hay chấp nhận query? Trade-offs là gì?
3. Nếu tăng RU/s giải quyết 429 ngay lập tức, bạn có dừng investigation không? Vì sao?

## Lỗi trả lời thường gặp

- Cho rằng `WHERE id = ...` luôn là point read.
- Chỉ nhìn result count thay vì request charge và query scope.
- Thấy 429 rồi tăng throughput ngay mà không tìm regression.
- Chọn partition key chỉ theo cardinality mà không xét access patterns và skew.
- Đề xuất repartition toàn bộ dữ liệu mà không có migration/cutover plan.

## Thang điểm 0–10

- **0–2:** chỉ nói tăng RU hoặc thêm index.
- **3–4:** biết partition key nhưng chưa giải thích point read vs query routing.
- **5–6:** hiểu point read, cross-partition query, RU measurement và 429 diagnostics.
- **7–8:** có hot-partition reasoning, instrumentation, access-pattern redesign và capacity decision dựa trên evidence.
- **9–10:** nối API contract, partition-key distribution, migration strategy và operational telemetry thành một recommendation conditional, không over-engineer.

# Câu 2 — Vue search page gửi request chồng nhau, UI hiển thị kết quả cũ và backend traffic tăng gấp đôi: incident nằm ở frontend, network hay API?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Vue.js, TypeScript, JavaScript promises, race conditions, fetch, AbortController, ASP.NET Core API, browser/network diagnostics, request cancellation, observability, frontend/backend integration, production incident response

## Bối cảnh

Một internal product-search portal có frontend Vue.js + TypeScript và ASP.NET Core API.

Khi user nhập từ khóa, frontend gọi `/api/products/search?q=...`.

Sau một release UI:

- backend RPS gần gấp đôi ở giờ cao điểm dù active users gần như không đổi;
- một số user thấy kết quả “nhảy ngược” về keyword cũ sau khi đã gõ keyword mới;
- browser DevTools cho thấy nhiều requests overlap;
- Application Insights cho thấy nhiều requests bị client disconnect/cancel nhưng một số database work vẫn chạy gần đủ thời gian;
- search API p95 tăng từ 300 ms lên 1.8 s dưới load;
- frontend team nghi backend chậm;
- backend team nghi Vue watcher bị gọi nhiều lần;
- CDN không cache API search;
- chưa biết component có debounce, request cancellation hay stale-response guard hay không;
- chưa biết component có bị mount hai lần trong một route transition hoặc development-only behavior có bị nhầm với production behavior hay không.

Một đoạn simplified frontend hiện tại:

```ts
watch(searchText, async (value) => {
  if (!value.trim()) {
    results.value = [];
    return;
  }

  loading.value = true;

  try {
    const response = await fetch(
      `/api/products/search?q=${encodeURIComponent(value)}`
    );

    results.value = await response.json();
  } finally {
    loading.value = false;
  }
});
```

Backend:

```csharp
[HttpGet("search")]
public async Task<ActionResult<IReadOnlyList<ProductDto>>> Search(
    [FromQuery] string q,
    CancellationToken cancellationToken)
{
    return await _searchService.SearchAsync(q, cancellationToken);
}
```

## Câu hỏi chính

Bạn đang điều tra incident. Hãy trình bày cách xác định **vì sao requests bị duplicate/overlap, vì sao stale response có thể ghi đè kết quả mới, và vì sao client cancellation không nhất thiết dừng toàn bộ backend work**. Hãy đi theo flow impact → stabilize → evidence → competing hypotheses → verification → fix → prevention, và đề xuất frontend/backend changes cùng telemetry cần thiết.

## Câu hỏi làm rõ nên cân nhắc

1. Watcher chạy trên mỗi keystroke hay có debounce/throttle layer ở chỗ khác?
2. Component có thể tạo nhiều watcher/subscription do lifecycle hoặc route reuse không?
3. Search service có propagate `CancellationToken` xuyên qua EF Core/HTTP/search dependencies không?
4. Requests overlap có cùng query hay query sequence khác nhau như `c`, `ca`, `car`?
5. API/search dependency có rate limit, connection limits hoặc expensive queries làm overlap khuếch đại latency không?

## Gợi ý tư duy

### Gợi ý 1

Tách hai bug classes: **too many requests** và **out-of-order response commits**. Chúng liên quan nhưng không giống nhau.

### Gợi ý 2

Promise hoàn thành theo network timing, không theo thứ tự user gõ.

### Gợi ý 3

Browser abort chỉ hữu ích nếu cancellation được propagate và downstream operation hỗ trợ quan sát cancellation; nó không quay ngược side effect đã xảy ra.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và RPS amplification.
2. Capture browser network timeline + frontend lifecycle telemetry.
3. Correlate request IDs với backend traces.
4. Liệt kê hypotheses: watcher frequency, duplicate subscriptions, retries, race conditions, slow backend.
5. Xác minh request generation trước khi tối ưu backend.
6. Stabilize bằng debounce/cancellation/admission controls phù hợp.
7. Fix stale-result ordering.
8. Propagate backend cancellation.
9. Load/E2E test realistic typing behavior.
10. Monitor request-per-search, cancellation rate và p95.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Watcher hiện tại có thể gửi request trên mỗi change của `searchText`.
- Nhiều requests có thể overlap; response cho query cũ có thể về sau response của query mới và ghi đè `results`.
- Debounce giảm request frequency nhưng không tự giải quyết mọi stale-response race nếu requests vẫn overlap.
- `AbortController` có thể hủy previous fetch, nhưng UI vẫn nên có latest-request guard/versioning khi cần.
- Backend `CancellationToken` chỉ có hiệu quả nếu `_searchService` và downstream operations nhận/quan sát token.
- Client disconnect không bảo đảm database/server work lập tức dừng ở mọi layer.
- Loading state cũng có race: request cũ `finally` có thể set `loading=false` trong khi request mới vẫn đang chạy.
- Cần xác minh component lifecycle để loại trừ duplicate watchers/subscriptions.

### Điểm cộng

- Dùng sequence/request version để chỉ latest response được commit.
- Cleanup previous request khi watcher re-runs hoặc component unmounts.
- Debounce 200–400 ms có thể hợp lý cho search-as-you-type tùy UX; con số phải được validate, không coi là chân lý.
- Backend validate minimum query length, bounded page size và timeout policy.
- Propagate cancellation tới EF Core `ToListAsync(ct)` hoặc outbound search dependency.
- Đo requests per user search session, canceled-before-server-complete, query duration và downstream dependency duration.

### Senior+

- Nhận ra cancellation là cooperative, không phải transaction rollback.
- Phân biệt frontend cancellation với backend timeout/bulkhead/admission control.
- Nếu search dependency expensive, có thể cần request coalescing/cache theo hot query sau khi đo, nhưng không thêm cache trước khi fix duplicate traffic.
- Thiết kế UI state machine rõ cho idle/loading/success/error/cancelled thay vì boolean loading dễ race.
- Dùng correlation fields gồm frontend search sequence, query hash, API request ID và trace ID để chứng minh stale overwrite path.

## Hướng giải quyết tham khảo

### 1. Stabilize và evidence

Tôi sẽ bắt đầu từ browser/network evidence của một session thực tế. Nếu user gõ `c` → `ca` → `car`, watcher hiện tại có thể phát 3 requests gần nhau. Nếu `car` trả trong 200 ms nhưng `ca` trả sau 1 s, code không có protection và `ca` có thể ghi đè `results` của `car`.

Timeline mẫu:

```text
T0  q=c    request A starts
T1  q=ca   request B starts
T2  q=car  request C starts
T3  C completes → UI shows car
T4  A completes → UI becomes stale
T5  B completes → UI becomes stale again
```

### 2. Frontend fix

Một design tốt hơn có debounce + cancellation + latest-result guard.

Ví dụ concept:

```ts
import { ref, watch } from 'vue';

const searchText = ref('');
const results = ref<Product[]>([]);
const state = ref<'idle' | 'loading' | 'success' | 'error'>('idle');

let sequence = 0;
let debounceTimer: number | undefined;
let controller: AbortController | undefined;

watch(searchText, (rawValue, _, onCleanup) => {
  const value = rawValue.trim();

  window.clearTimeout(debounceTimer);
  controller?.abort();

  if (!value) {
    sequence++;
    results.value = [];
    state.value = 'idle';
    return;
  }

  const currentSequence = ++sequence;
  const currentController = new AbortController();
  controller = currentController;

  debounceTimer = window.setTimeout(async () => {
    state.value = 'loading';

    try {
      const response = await fetch(
        `/api/products/search?q=${encodeURIComponent(value)}`,
        { signal: currentController.signal }
      );

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`);
      }

      const data = await response.json();

      if (currentSequence === sequence) {
        results.value = data;
        state.value = 'success';
      }
    } catch (error) {
      if (
        !currentController.signal.aborted &&
        currentSequence === sequence
      ) {
        state.value = 'error';
      }
    }
  }, 300);

  onCleanup(() => {
    window.clearTimeout(debounceTimer);
    currentController.abort();
  });
});
```

Không phải mọi app cần cả ba mechanisms, nhưng với network search autocomplete chúng giải quyết các failure modes khác nhau:

- debounce: giảm số requests;
- abort: giảm work không còn cần;
- sequence guard: ngăn stale response update UI.

### 3. Backend cancellation

Controller đã nhận token từ ASP.NET Core request lifetime. Service phải propagate:

```csharp
public async Task<IReadOnlyList<ProductDto>> SearchAsync(
    string query,
    CancellationToken cancellationToken)
{
    return await _db.Products
        .AsNoTracking()
        .Where(x => x.Name.Contains(query))
        .OrderBy(x => x.Name)
        .Select(x => new ProductDto(x.Id, x.Name))
        .Take(50)
        .ToListAsync(cancellationToken);
}
```

Nếu service gọi Elasticsearch/HTTP dependency, token cũng cần được truyền nếu API hỗ trợ.

Cancellation không bảo đảm mọi server-side work biến mất tức thì. Một downstream operation có thể đã bắt đầu, provider có semantics riêng, hoặc side effect đã commit. Vì vậy cancellation là optimization/control signal, không phải atomic undo.

### 4. Competing hypotheses

Ngoài watcher-per-keystroke, cần kiểm tra:

- component mounted/subscribed nhiều lần;
- application-level retry interceptor;
- browser retry/network behavior;
- search action bị trigger cả input handler và watcher;
- backend 30x redirects hoặc proxy retry;
- slow backend làm overlap rõ hơn nhưng không nhất thiết là nguồn duplicate request.

### 5. Testing

- Playwright test gõ nhanh 10 ký tự và assert final results thuộc query cuối.
- Mock network để response cũ về sau response mới.
- Assert previous fetch được aborted khi query mới xuất hiện.
- Load test với realistic typing rate để đo RPS amplification.
- Backend test cancellation propagation và bounded result size.

### 6. Production telemetry

Frontend có thể gửi telemetry cho `search_started`, `search_cancelled`, `search_completed`, sequence/query length và duration nhưng tránh log raw sensitive search text nếu policy không cho phép.

Backend theo dõi:

- requests/search session;
- p50/p95/p99;
- canceled request rate;
- dependency duration;
- DB/search query count;
- active concurrent searches;
- 429/5xx;
- CPU/ThreadPool/connection saturation.

Tài liệu tham khảo hiện hành:

- Vue.js Guide — Watchers: `https://vuejs.org/guide/essentials/watchers.html`
- MDN — AbortController: `https://developer.mozilla.org/docs/Web/API/AbortController`

## Mẫu trả lời trong phỏng vấn

“Em sẽ chứng minh request amplification trước. Watcher hiện tại có thể phát request mỗi keystroke, và promises không hoàn thành theo thứ tự input nên response cũ có thể về sau rồi ghi đè kết quả mới. Đây là hai vấn đề: frequency và stale commit.

Em capture network timeline, component lifecycle và trace IDs. Nếu đúng, em dùng debounce để giảm RPS, abort previous fetch để giảm work không còn cần, và sequence/latest-request guard để chỉ response mới nhất được update UI. Em cũng sửa loading state vì `finally` của request cũ có thể set false sai thời điểm.

Backend đã nhận `CancellationToken`, nhưng em kiểm tra nó có được propagate tới EF Core hoặc external search client không. Client abort là cooperative cancellation, không phải guarantee rằng mọi downstream work dừng tức thì.

Cuối cùng em Playwright test với typing nhanh và network response reorder, load test realistic keystrokes, rồi monitor requests/search session, cancellation rate, concurrent searches và backend p95. Em sẽ không thêm Redis hay scale backend trước khi loại duplicate traffic do client.”

## Câu hỏi đào sâu

1. Nếu debounce giảm RPS 60% nhưng stale-result bug vẫn còn, vì sao và bạn cần guard nào thêm?
2. Nếu backend query không thể cancel giữa chừng, bạn sẽ làm gì để ngăn abandoned searches chiếm hết capacity dưới load?
3. Một teammate đề xuất cache mọi search query trong Redis thay vì sửa frontend. Khi nào recommendation đó hợp lý hoặc không hợp lý?

## Lỗi trả lời thường gặp

- Chỉ thêm debounce và cho rằng race condition đã biến mất.
- Chỉ dùng AbortController nhưng không có latest-response guard khi lifecycle phức tạp.
- Nghĩ client abort chắc chắn rollback backend work.
- Tối ưu SQL/search engine trước khi chứng minh source của duplicate traffic.
- Không test out-of-order responses.

## Thang điểm 0–10

- **0–2:** chỉ nói “backend chậm” hoặc “thêm debounce”.
- **3–4:** nhận ra overlap nhưng chưa xử lý stale response/cancellation propagation.
- **5–6:** có debounce, abort, latest-result guard và backend token propagation.
- **7–8:** có incident evidence flow, lifecycle hypotheses, race-safe loading/state và realistic E2E/load tests.
- **9–10:** phân tích capacity/backpressure, cooperative cancellation, observability xuyên browser→API→dependency và tránh premature caching/scaling.

# Câu 3 — Modernize .NET Framework 4.5 trên IIS lên .NET 8/App Service: rewrite, strangler hay nâng cấp từng bước?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, .NET 8, ASP.NET Core, IIS, Windows Server, Azure App Service, modernization, backward compatibility, migration strategy, testing, CI/CD, rollout, rollback, observability, architecture trade-offs

## Bối cảnh

Một enterprise management portal được xây nhiều năm trước bằng ASP.NET MVC trên .NET Framework 4.5 và chạy trên IIS/Windows Server.

Hệ thống hiện có:

- khoảng 180 controllers;
- Entity Framework 6 + SQL Server;
- jQuery và một số legacy Angular modules;
- Windows Authentication cho intranet users;
- một số scheduled jobs chạy trong web process;
- file upload lưu trên local filesystem của server;
- vài libraries nội bộ target .NET Framework và chưa rõ khả năng migrate;
- deployment qua Jenkins + Octopus Deploy;
- downtime mỗi release hiện khoảng 10–20 phút;
- production incidents thường khó trace vì logging không có correlation ID chuẩn;
- Product muốn thêm public/mobile APIs trong 12 tháng tới;
- management đề xuất “rewrite toàn bộ sang .NET 8 + React + Kubernetes trong 6 tháng”;
- team có 6 backend/full-stack developers và vẫn phải maintain feature delivery hàng tháng;
- chưa có inventory đầy đủ cho dependencies, IIS-specific behavior, Windows-only APIs, authentication constraints hoặc batch jobs.

Mục tiêu business là giảm deployment risk, cải thiện maintainability và tạo đường cho cloud hosting. Chưa có requirement bắt buộc phải dùng Kubernetes hay Linux.

## Câu hỏi chính

Hãy đề xuất **modernization strategy** từ hệ thống .NET Framework 4.5/IIS hiện tại tới modern .NET. So sánh rewrite toàn bộ, in-place/incremental migration và strangler-style extraction. Bạn cần chỉ ra cách xử lý dependency compatibility, authentication, database, background jobs, filesystem, frontend, testing, deployment, rollback và observability. Đồng thời quyết định App Service Windows, App Service Linux/container hay Kubernetes có phù hợp ở từng giai đoạn hay không.

## Câu hỏi làm rõ nên cân nhắc

1. Có libraries/COM/GAC/Windows-only APIs nào buộc workload tiếp tục chạy Windows trong một giai đoạn không?
2. Windows Authentication có còn là requirement dài hạn hay identity model sẽ chuyển sang Entra ID/OIDC cho web/mobile?
3. Database schema có thể được chia theo module hay tất cả modules phụ thuộc chặt vào cùng tables/stored procedures?
4. Scheduled jobs có yêu cầu exactly-once/idempotency gì, và hiện có bị duplicate khi App Pool recycle không?
5. Business chấp nhận migration timeline bao lâu, và release cadence hiện tại có được giảm trong migration hay không?

## Gợi ý tư duy

### Gợi ý 1

Đừng bắt đầu bằng target hosting. Bắt đầu bằng **inventory, dependency graph và migration seams**.

### Gợi ý 2

Rewrite toàn bộ loại bỏ một số technical debt nhưng tạo một khoảng thời gian dài không có production validation.

### Gợi ý 3

Modernization tốt thường tách **application modernization**, **hosting modernization** và **frontend modernization** thành các quyết định có thể tiến hóa độc lập.

## Cấu trúc trả lời đề xuất

1. Clarify business goals và constraints.
2. Inventory dependencies/runtime/hosting assumptions.
3. Phân loại modules theo migration difficulty/value.
4. Thiết kế compatibility seams và routing.
5. Quyết định database transition strategy.
6. Tách background jobs khỏi web lifecycle nếu cần.
7. Chuyển filesystem/state assumptions.
8. Modernize authentication theo target clients.
9. Xây regression/integration/E2E safety net.
10. Chọn hosting theo actual dependency requirements.
11. Thiết kế rollout/rollback wave-by-wave.
12. Thiết lập observability và success metrics.
13. Xác định trigger để tách thêm services hoặc dùng Kubernetes.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chấp nhận rewrite 6 tháng như default nếu chưa có dependency inventory và production-validation strategy.
- Migration phải bắt đầu từ assessment: frameworks/libraries, Windows-specific APIs, authentication, filesystem, background jobs, deployment, database coupling.
- .NET Framework và modern .NET có hosting/runtime differences; không assume package compatibility.
- Có thể giữ SQL Server chung trong giai đoạn đầu nếu transaction/data boundaries chưa rõ, thay vì ép microservices.
- Scheduled jobs không nên phụ thuộc mù vào IIS App Pool/web process lifecycle nếu business cần reliable execution.
- Local filesystem là hosting coupling cần xử lý trước scale-out/cloud; có thể chuyển shared/object storage như Azure Blob Storage nếu requirement phù hợp.
- Authentication migration phải tính cả current intranet behavior và future public/mobile APIs.
- App Service có thể là target hợp lý trước Kubernetes nếu application không cần orchestration complexity.
- Rollout phải incremental và rollbackable ở boundary rõ.
- Tests và observability phải được xây trước/đồng thời migration, không để cuối dự án.

### Điểm cộng

- Dùng route/module-level strangler: reverse proxy/gateway route một số paths sang ASP.NET Core service/app mới trong khi phần legacy tiếp tục chạy.
- Dùng shared database tạm thời có governance rõ, rồi tách ownership khi module boundary đủ trưởng thành.
- Chuyển Windows Authentication sang modern identity theo requirement, ví dụ Entra ID/OIDC cho new APIs, nhưng không giả định có thể thay ngay toàn bộ legacy auth.
- Tách background jobs sang Worker Service/Azure Functions chỉ khi execution pattern phù hợp; không coi Functions luôn tốt hơn.
- Xây characterization tests cho legacy behavior trước refactor.
- Dùng deployment slots/canary hoặc side-by-side release khi target platform hỗ trợ.
- Có compatibility facade/adapters cho legacy dependencies để giảm blast radius.

### Senior+

- Tách ba streams: runtime migration, hosting migration, UI migration; không bắt buộc đổi tất cả cùng lúc.
- Xác định migration scorecard theo business value, coupling, test coverage, operational pain và dependency risk.
- Thiết kế data evolution backward-compatible giữa legacy/new versions.
- Có plan cho observability parity trước traffic cutover: trace correlation, dependency telemetry, error/latency SLO.
- Nêu rõ khi nào App Service Windows là stepping stone tốt hơn Linux do Windows-specific dependencies.
- Kubernetes chỉ được chọn khi có concrete needs như orchestration, multi-service operational model, portability/sidecars/custom networking hoặc organizational platform capability; không chọn để “future-proof”.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng rewrite. Giai đoạn đầu là **assessment + safety net**.

### 1. Inventory

Tạo dependency inventory:

```text
Module
- Runtime/API dependencies
- NuGet/internal libraries
- EF6/SQL objects
- Windows-only APIs
- authentication assumptions
- filesystem/session/cache
- scheduled/background work
- external integrations
- deployment/configuration
- test coverage
- production incident frequency
```

Phân nhóm:

- easy-to-port;
- needs library upgrade/replacement;
- Windows-bound;
- highly coupled to legacy UI/database;
- business-critical/high risk.

### 2. Không trộn mọi modernization vào một big bang

Ba axes độc lập:

```text
Runtime:   .NET Framework → modern .NET
Hosting:   IIS/Windows → App Service Windows/Linux/container/Kubernetes
Frontend:  jQuery/Angular legacy → Vue/React/other modern UI
```

Một module có thể migrate backend sang ASP.NET Core trước nhưng vẫn giữ UI cũ. Hoặc có thể move legacy IIS app lên App Service Windows như hosting step trước khi runtime rewrite nếu assessment cho thấy phù hợp.

### 3. Strangler/incremental routing

Một transition architecture:

```text
Users
  ↓
Reverse proxy / gateway
  ├─ /legacy/* → existing IIS app
  └─ /api/v2/*, /new-module/* → ASP.NET Core .NET 8 app
                               ↓
                          SQL Server / shared services
```

Shared DB trong giai đoạn đầu có thể chấp nhận nếu team kiểm soát schema change và transaction boundaries. Tôi không tạo distributed database/service topology trước khi domain ownership rõ.

### 4. Database

Schema changes phải backward-compatible trong mixed-version phase. Nếu new app cần field mới, ưu tiên additive change trước; old app vẫn chạy. Destructive migration chỉ sau khi legacy consumer đã ngừng dùng.

Nếu sau này tách ownership, có thể migrate data module-by-module. Không nên tạo dual-write distributed consistency problem nếu chưa cần.

### 5. Background jobs

Jobs chạy trong web process chịu App Pool recycle/restart behavior. Với jobs quan trọng, tách lifecycle:

- Worker Service nếu long-running process semantics phù hợp;
- Azure Functions nếu trigger/execution model phù hợp;
- scheduler + durable queue nếu cần retry/idempotency.

Dù chọn gì, cần idempotency và duplicate execution handling khi multi-instance.

### 6. Filesystem

Local server disk không phù hợp nếu scale-out hoặc platform instance có ephemeral/non-shared semantics. Move uploads sang abstraction rồi implementation có thể dùng Azure Blob Storage/shared store.

Migration nên gồm:

- object naming/key strategy;
- auth/Managed Identity nếu phù hợp;
- metadata;
- migration/backfill;
- virus/file validation nếu upload public;
- rollback/read compatibility trong transition.

### 7. Authentication

Không nên đổi auth giữa migration mà không hiểu clients. Legacy intranet có thể tạm giữ Windows auth. New public/mobile APIs thường cần token-based identity như Entra ID/OIDC tùy organization requirement.

Có thể dùng identity seam để application authorization dựa trên claims/policies thay vì trải Windows-specific principal checks khắp codebase.

### 8. Hosting decision

**App Service Windows** có thể là stepping stone nếu app/dependencies còn Windows-specific.

**App Service Linux** hợp lý khi module đã chạy cross-platform modern .NET và không phụ thuộc Windows APIs.

**Container** hữu ích khi cần packaging/runtime consistency hoặc dependency isolation, nhưng không tự giải quyết architecture.

**Kubernetes** chỉ nên vào roadmap khi workload/organization cần orchestration complexity. Với 6 developers và chưa có platform team, App Service thường có operational cost thấp hơn.

Microsoft Learn hiện mô tả App Service là managed hosting cho .NET web apps và cũng có migration paths cho ASP.NET applications; một số .NET Framework applications có Windows-specific dependencies có thể cần Windows-based options hoặc containerization thay vì giả định chạy Linux trực tiếp.

### 9. Testing strategy

Trước khi thay module quan trọng:

- characterization tests cho current behavior;
- integration tests với SQL/external dependencies;
- contract tests cho legacy/new boundary;
- Playwright E2E cho critical user flows;
- migration compatibility tests;
- performance baseline;
- rollback validation.

Không cần 100% coverage. Cần coverage đúng risk.

### 10. Observability

Trước traffic migration, chuẩn hóa:

- correlation ID/trace ID;
- structured logs;
- request/dependency telemetry;
- p50/p95/p99;
- error rate;
- per-route old/new backend attribution;
- job success/failure/duplicates;
- deployment version.

Điều này cho phép canary cutover 1% → 10% → 50% → 100% và rollback theo evidence.

### 11. Khi nào rewrite toàn bộ có thể hợp lý?

Rewrite có thể defensible nếu:

- legacy architecture quá coupled và không có usable seams;
- requirements thay đổi sâu đến mức behavior cũ không còn giá trị;
- system tương đối nhỏ;
- business chấp nhận dual-run và migration cost;
- test/validation plan đủ mạnh.

Nhưng với 180 controllers, monthly feature delivery và nhiều unknown dependencies, big-bang rewrite có delivery risk rất cao.

Tài liệu tham khảo hiện hành:

- Microsoft Learn — Migrate .NET apps to Azure App Service: `https://learn.microsoft.com/azure/app-service/app-service-asp-net-migration`
- Microsoft Learn — Migrate your .NET web app or service to Azure App Service: `https://learn.microsoft.com/dotnet/azure/migration/app-service`

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chốt .NET 8 + React + Kubernetes trước khi có inventory. Mục tiêu là giảm risk và tạo đường tiến hóa, nên em tách runtime, hosting và frontend modernization thành ba streams.

Đầu tiên em inventory dependencies, Windows-only APIs, auth, filesystem, jobs, DB coupling và test coverage. Sau đó em chọn module có business value cao nhưng coupling vừa phải để migrate sang ASP.NET Core .NET 8 theo strangler route. Legacy vẫn chạy trên IIS; traffic module mới đi sang app mới. Database có thể còn shared ở giai đoạn đầu nếu schema changes backward-compatible.

Em tách reliable jobs khỏi web process, abstract local filesystem rồi move sang Blob/shared storage nếu scale-out cần, và thiết kế identity seam để future public/mobile APIs dùng token-based auth mà không buộc đổi toàn bộ legacy ngay.

Về hosting, App Service Windows có thể là stepping stone nếu còn Windows dependencies; App Service Linux khi module đã cross-platform. Em chỉ chọn Kubernetes nếu có orchestration requirement và năng lực vận hành đủ mạnh, không vì future-proof.

Mỗi wave có characterization/integration/E2E tests, telemetry old-vs-new, canary traffic và rollback. Em muốn migration luôn tạo production value theo từng bước thay vì đợi 6 tháng mới biết rewrite có đúng behavior hay không.”

## Câu hỏi đào sâu

1. Nếu một internal library quan trọng chỉ chạy .NET Framework và không có source code, bạn sẽ chọn adapter/process boundary, replacement hay trì hoãn module migration dựa trên tiêu chí nào?
2. Nếu Product yêu cầu public mobile API trong 3 tháng nhưng legacy app vẫn phụ thuộc Windows Authentication, bạn thiết kế identity boundary thế nào để không block roadmap?
3. Management nói Kubernetes sẽ tránh phải migrate hosting lần nữa sau này. Bạn cần evidence nào để đồng ý hoặc phản đối?

## Lỗi trả lời thường gặp

- Chọn rewrite vì code cũ “xấu” mà không có migration economics/validation plan.
- Buộc đổi backend, frontend, hosting và database cùng lúc.
- Chọn Kubernetes chỉ vì target architecture “hiện đại”.
- Không xử lý IIS web-process jobs và local filesystem trước scale-out.
- Không thiết kế mixed-version database compatibility và rollback.

## Thang điểm 0–10

- **0–2:** chỉ đề xuất rewrite hoặc upgrade framework trực tiếp.
- **3–4:** có migration phases nhưng thiếu dependency/rollback reasoning.
- **5–6:** có inventory, incremental route, testing, data compatibility và hosting trade-offs.
- **7–8:** tách runtime/hosting/UI streams, có auth/jobs/filesystem strategy, observability và canary rollout.
- **9–10:** architecture tiến hóa theo evidence, biết khi nào giữ Windows/App Service đơn giản hơn, khi nào mới tách services/Kubernetes, và quản lý migration như continuous risk-reduction program.
