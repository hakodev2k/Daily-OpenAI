# Code Review Challenge 1 — Service Bus consumer ghi nhận thanh toán hai lần khi retry

**Chủ đề:** C#/.NET, Azure Service Bus, idempotency, EF Core, distributed systems, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 40–50 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một backend nhận `PaymentConfirmed` từ Azure Service Bus để cập nhật order và tạo audit record. Production chạy nhiều application instances. Broker có thể redeliver message khi handler xử lý xong business logic nhưng việc settlement không hoàn tất, hoặc khi processing vượt quá lock window. Gần đây support phát hiện một số order có hai audit records và downstream notification bị gửi hai lần.

Business yêu cầu không làm mất payment confirmation. Duplicate delivery được xem là tình huống phải chịu được. Database là SQL Server qua EF Core. Không được giả định broker cung cấp exactly-once end-to-end.

## Đoạn code cần review

```csharp
public sealed class PaymentConfirmedHandler
{
    private readonly OrdersDbContext _db;
    private readonly INotificationClient _notifications;
    private readonly ILogger<PaymentConfirmedHandler> _logger;

    public PaymentConfirmedHandler(
        OrdersDbContext db,
        INotificationClient notifications,
        ILogger<PaymentConfirmedHandler> logger)
    {
        _db = db;
        _notifications = notifications;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        CancellationToken cancellationToken)
    {
        var payload = JsonSerializer.Deserialize<PaymentConfirmed>(message.Body)!;

        var order = await _db.Orders
            .SingleAsync(x => x.Id == payload.OrderId, cancellationToken);

        order.PaymentStatus = "Paid";
        order.PaidAtUtc = DateTime.UtcNow;

        _db.PaymentAudits.Add(new PaymentAudit
        {
            OrderId = payload.OrderId,
            ProviderReference = payload.ProviderReference,
            CreatedAtUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await _notifications.SendPaymentReceiptAsync(
            order.CustomerId,
            payload.OrderId,
            cancellationToken);

        _logger.LogInformation(
            "Processed payment {ProviderReference} for order {OrderId}",
            payload.ProviderReference,
            payload.OrderId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, consistency, retry và reliability problems.
2. Giải thích điều gì xảy ra nếu cùng message được deliver hai lần đồng thời trên hai instances.
3. Phân tích failure window giữa `SaveChangesAsync` và notification call.
4. Ưu tiên findings theo business impact.
5. Đề xuất corrected implementation/design chịu được duplicate delivery mà không tuyên bố exactly-once một cách sai lệch.
6. Giải thích testing cho duplicate, concurrency, crash và dependency failure.
7. Đề xuất telemetry để phát hiện redelivery, duplicate suppression và notification failure.

## Câu hỏi gợi mở

1. `MessageId` hoặc business id nào có thể đóng vai trò idempotency identity, và identity đó có thực sự ổn định không?
2. Hai consumers cùng kiểm tra “chưa xử lý” rồi cùng insert thì application-level check có đủ không?
3. Nếu database commit thành công nhưng process chết trước khi notification hoàn tất thì retry sẽ làm gì?
4. Transaction database có bao phủ được external HTTP notification không?
5. Khi deserialize lỗi hoặc order không tồn tại, retry vô hạn có hữu ích không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **at-least-once delivery gặp non-idempotent side effects**.

### Gợi ý 2

Hãy tách atomic database state transition khỏi external side effect và xem database constraint/outbox có thể đóng vai trò gì.

## Kết quả code review tham khảo

### Critical — Handler không idempotent trước duplicate delivery

**Vấn đề:** Mỗi delivery đều insert `PaymentAudit` và gửi receipt, không có durable deduplication.

**Tại sao xảy ra:** Broker delivery và application side effects không tạo thành một exactly-once transaction.

**Ảnh hưởng production:** Duplicate audit, duplicate notification và có thể duplicate các side effects nghiêm trọng hơn nếu handler được mở rộng.

**Cách sửa:** Chọn idempotency key có business semantics rõ ràng, lưu durable processing record cùng transaction với order mutation, và enforce uniqueness tại database. Không chỉ dùng in-memory set vì nhiều instances/restarts.

### Critical — Check-then-insert ở application layer sẽ không đủ dưới concurrency

**Vấn đề:** Nếu chỉ thêm `AnyAsync` trước insert, hai instances vẫn có thể cùng thấy “chưa tồn tại”.

**Tại sao xảy ra:** Race giữa read và write.

**Ảnh hưởng production:** Duplicate vẫn lọt qua đúng lúc redelivery/concurrency.

**Cách sửa:** Dùng unique constraint/index trên idempotency key như `(ConsumerName, MessageId)` hoặc business event ID phù hợp; transaction xử lý unique violation theo semantics đã định.

### High — Dual-write giữa SQL và notification có failure window

**Vấn đề:** Database commit trước external notification. Nếu notification lỗi, state đã Paid; nếu retry toàn handler, database side effects có thể lặp.

**Tại sao xảy ra:** SQL transaction không thể atomic với arbitrary external HTTP dependency.

**Ảnh hưởng production:** Missing hoặc duplicate receipt tùy failure point.

**Cách sửa:** Ghi Outbox record trong cùng DB transaction với order/idempotency record. Một dispatcher riêng gửi notification với retry + idempotency ở downstream nếu có thể.

### High — Không thể hiện policy cho poison/permanent failure

**Vấn đề:** Invalid payload, unknown order hoặc invariant violation có thể khác transient dependency failure nhưng code không phân loại.

**Tại sao xảy ra:** Handler chỉ throw theo behavior mặc định của dependency/runtime.

**Ảnh hưởng production:** Retry lãng phí, queue backlog hoặc message đi DLQ mà thiếu diagnostic context.

**Cách sửa:** Xác định retryable vs permanent errors, dead-letter policy và structured reason; không swallow lỗi khiến message bị coi là thành công.

### High — Payment transition thiếu domain invariant/concurrency policy

**Vấn đề:** Gán `PaymentStatus = "Paid"` trực tiếp không xác minh trạng thái hiện tại, provider reference hoặc conflicting payment event.

**Tại sao xảy ra:** Message handling bypass business transition semantics.

**Ảnh hưởng production:** Event sai/thứ tự khác có thể overwrite state hoặc che conflict.

**Cách sửa:** Domain transition phải validate allowed state; cân nhắc optimistic concurrency token nếu các workflows khác cùng update order.

### Medium — `DateTime.UtcNow` cho mỗi delivery làm audit semantics không ổn định

**Vấn đề:** `PaidAtUtc` trở thành processing time của lần delivery cuối, không nhất thiết event/payment time.

**Tại sao xảy ra:** Không phân biệt occurred-at với processed-at.

**Ảnh hưởng production:** Retry có thể thay đổi business timestamp.

**Cách sửa:** Nếu event có trusted occurrence timestamp, dùng nó theo contract; lưu processed timestamp riêng khi cần.

### Medium — Deserialization dùng null-forgiving operator

**Vấn đề:** Invalid/empty payload có thể dẫn đến exception thiếu ngữ cảnh.

**Tại sao xảy ra:** Contract validation không explicit.

**Ảnh hưởng production:** Khó phân loại poison message và điều tra DLQ.

**Cách sửa:** Validate payload/schema và log metadata an toàn như MessageId/CorrelationId, không log payment secrets.

### Low — Telemetry chưa thể hiện delivery attempt và dedupe outcome

**Vấn đề:** Log “Processed payment” không cho biết delivery count, duplicate suppression, outbox state hay duration.

**Tại sao xảy ra:** Observability chỉ ghi happy path.

**Ảnh hưởng production:** Khó chứng minh duplicate đến từ broker redelivery hay application retry.

**Cách sửa:** Structured telemetry cho message identity, correlation, delivery count, processing result, dedupe result, outbox enqueue/dispatch và latency.

## Phiên bản đề xuất

Một hướng rút gọn là Inbox/idempotency record + Outbox trong cùng transaction. Exact schema và exception type cần theo provider/EF Core version của project:

```csharp
public sealed class PaymentConfirmedHandler
{
    private readonly OrdersDbContext _db;
    private readonly TimeProvider _timeProvider;

    public PaymentConfirmedHandler(OrdersDbContext db, TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        CancellationToken cancellationToken)
    {
        var payload = JsonSerializer.Deserialize<PaymentConfirmed>(message.Body)
            ?? throw new InvalidDataException("Invalid PaymentConfirmed payload.");

        var messageId = message.MessageId;
        if (string.IsNullOrWhiteSpace(messageId))
            throw new InvalidDataException("MessageId is required for this consumer contract.");

        await using var tx = await _db.Database.BeginTransactionAsync(cancellationToken);

        if (await _db.ProcessedMessages.AnyAsync(
            x => x.Consumer == "PaymentConfirmed" && x.MessageId == messageId,
            cancellationToken))
        {
            await tx.CommitAsync(cancellationToken);
            return;
        }

        var order = await _db.Orders
            .SingleAsync(x => x.Id == payload.OrderId, cancellationToken);

        order.MarkPaid(payload.ProviderReference, payload.OccurredAtUtc);

        _db.PaymentAudits.Add(PaymentAudit.From(payload));
        _db.ProcessedMessages.Add(new ProcessedMessage("PaymentConfirmed", messageId));
        _db.OutboxMessages.Add(OutboxMessage.PaymentReceiptRequested(
            order.CustomerId,
            order.Id,
            _timeProvider.GetUtcNow()));

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);
    }
}
```

Database phải có unique constraint cho `(Consumer, MessageId)`; `AnyAsync` chỉ là fast-path/readability, constraint mới là arbiter khi concurrent consumers race. Production code phải xử lý unique-conflict sao cho duplicate hợp lệ được coi là already processed, nhưng không che các database failures khác.

Outbox dispatcher gửi receipt độc lập. Dispatcher cũng phải chịu duplicate dispatch; tốt nhất downstream API hỗ trợ idempotency key hoặc dispatcher lưu durable delivery state với retry policy phù hợp.

## Giải thích thiết kế sau khi sửa

Idempotency nằm ở durable boundary, không phụ thuộc một process. Order update, audit, processed-message record và outbox enqueue cùng commit hoặc cùng rollback. External notification được đưa ra khỏi transaction thay vì cố giữ SQL transaction qua network call.

Thiết kế này không biến hệ thống thành exactly-once toàn cục. Nó tạo **effectively-once business mutation** trong boundary SQL với constraint, còn external delivery vẫn cần idempotency/retry semantics riêng.

## Trade-offs

- Inbox/Outbox thêm tables, cleanup/retention và dispatcher operations.
- Unique key chỉ đúng nếu MessageId/event ID contract ổn định; nếu producer tạo ID mới cho cùng business event cần business idempotency key khác.
- Transaction tăng database work nhưng đổi lại consistency rõ ràng.
- Downstream không hỗ trợ idempotency thì không thể bảo đảm không bao giờ gửi duplicate chỉ bằng local code.

## Cách kiểm thử

1. **Integration test:** deliver cùng MessageId tuần tự hai lần; chỉ một business mutation/audit/outbox logical event.
2. **Concurrency test:** hai DbContexts xử lý cùng MessageId đồng thời; unique constraint phải chặn duplicate.
3. **Failure-path test:** crash/fail sau DB commit trước dispatch; outbox vẫn được gửi sau recovery.
4. **Retry test:** notification dependency timeout; dispatcher retry mà không tạo payment mutation mới.
5. **Poison-message test:** invalid payload được phân loại và telemetry/DLQ behavior đúng policy.

## Quan sát trong production

Theo dõi queue depth, active/dead-letter message count, processing duration, delivery count, duplicate-suppression count, DB unique conflicts, outbox pending age, dispatch retry count và notification dependency failures. Correlate `MessageId`, business event ID, OrderId và trace/correlation ID bằng structured logging nhưng không ghi payment secrets.

Alert trên DLQ growth, oldest outbox age, sustained retry rate và queue backlog thay vì chỉ alert exception count.

## Câu hỏi phỏng vấn mở rộng

1. Nếu producer gửi cùng payment hai lần với hai MessageId khác nhau, bạn thiết kế business idempotency key thế nào?
2. Khi nào Inbox table là quá phức tạp và một unique business constraint trên payment record đã đủ?
3. Nếu notification provider không hỗ trợ idempotency, bạn mô tả guarantee thực tế với Product như thế nào?

# Code Review Challenge 2 — React search hiển thị kết quả cũ sau request mới

**Chủ đề:** React.js, TypeScript, browser networking, async race condition, API integration, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một product-search page gọi ASP.NET Core API khi user thay đổi query hoặc category. Users gõ nhanh thấy kết quả đôi lúc “nhảy ngược” về keyword cũ. Production telemetry cũng cho thấy số request cao hơn dự kiến. API có p95 khoảng vài trăm milliseconds nhưng đôi lúc Elasticsearch dependency chậm vài giây.

UI phải giữ kết quả tương ứng với input mới nhất. Không yêu cầu search-as-you-type ở từng keystroke; debounce ngắn được chấp nhận. Component có thể unmount khi user chuyển route.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    setLoading(true);
    setError(null);

    fetch(`/api/products?q=${query}&category=${category}`)
      .then(r => r.json())
      .then(data => {
        setProducts(data.items);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [query, category]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      <select value={category} onChange={e => setCategory(e.target.value)}>
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="software">Software</option>
      </select>

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {products.map(p => <li key={p.id}>{p.name}</li>)}
      </ul>
    </section>
  );
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, network-efficiency và failure-handling concerns.
2. Giải thích chính xác race khi request cho query cũ hoàn tất sau request mới.
3. Phân tích behavior khi component unmount hoặc input thay đổi liên tục.
4. Ưu tiên vấn đề ảnh hưởng correctness trước micro-optimization.
5. Đề xuất implementation bảo đảm chỉ response hợp lệ cho intent mới nhất được commit vào state.
6. Giải thích tests cho out-of-order responses, cancellation, HTTP errors và debounce.
7. Đề xuất browser/API telemetry để xác minh fix.

## Câu hỏi gợi mở

1. Network responses có bắt buộc hoàn thành theo thứ tự request được tạo không?
2. `fetch()` có reject Promise cho HTTP 500 theo cách code đang giả định không?
3. Điều gì xảy ra nếu user nhập `car`, rồi `cart`, nhưng request `car` chậm hơn?
4. Có cần gọi API cho query rỗng hoặc mọi keystroke không?
5. Cleanup function của `useEffect` có thể giúp lifecycle này như thế nào?

## Gợi ý

### Gợi ý 1

Primary risk là **out-of-order async completion làm stale request thắng latest intent**.

### Gợi ý 2

Xem `AbortController`, effect cleanup, HTTP status validation và debounce; cancellation giúp giảm waste nhưng correctness vẫn nên gắn với lifecycle/request identity.

## Dừng lại và tự review

## Kết quả code review tham khảo

### High — Out-of-order response có thể overwrite kết quả mới

**Vấn đề:** Mọi response đều gọi `setProducts` khi hoàn tất.

**Tại sao xảy ra:** Network completion order không tương ứng input order.

**Ảnh hưởng production:** User nhìn thấy kết quả của query/category cũ dù input đang là giá trị mới.

**Cách sửa:** Cleanup/cancel request cũ bằng `AbortController`; chỉ effect hiện hành được phép commit state. Có thể bổ sung request sequence guard nếu abstraction/cancellation semantics phức tạp.

### High — Không kiểm tra HTTP status

**Vấn đề:** `fetch` resolve cho nhiều HTTP error responses; code gọi `r.json()` rồi có thể xử lý error payload như success shape.

**Tại sao xảy ra:** Promise rejection của fetch chủ yếu phản ánh network-level failure, không tự biến mọi non-2xx thành rejection.

**Ảnh hưởng production:** UI có thể throw ở `data.items`, hiển thị state sai hoặc mất error context.

**Cách sửa:** Kiểm tra `response.ok`, parse error contract có kiểm soát và map thành user-safe error.

### Medium — Một request cho mỗi keystroke tạo request amplification

**Vấn đề:** `query` thay đổi là effect chạy ngay.

**Tại sao xảy ra:** Không có debounce/minimum query policy.

**Ảnh hưởng production:** Browser tạo request thừa; backend/Elasticsearch chịu load không cần thiết.

**Cách sửa:** Debounce intent theo UX requirement và cân nhắc không search query rỗng. Không dùng debounce để “sửa” correctness race; vẫn cần lifecycle handling.

### Medium — Abort được xử lý như user-visible error nếu thêm cancellation ngây thơ

**Vấn đề:** Nếu chỉ thêm AbortController nhưng catch mọi exception, mỗi superseded request có thể flash error.

**Tại sao xảy ra:** Cancellation là expected control flow của search interaction.

**Ảnh hưởng production:** UI nhấp nháy lỗi khi user gõ bình thường.

**Cách sửa:** Phân biệt abort/cancellation với real network/server error.

### Medium — Loading state có thể bị request cũ tắt sai thời điểm

**Vấn đề:** Request cũ hoàn tất có thể `setLoading(false)` trong khi request mới còn chạy.

**Tại sao xảy ra:** Loading boolean không gắn với active request lifecycle.

**Ảnh hưởng production:** Loading indicator không phản ánh request mới nhất.

**Cách sửa:** Chỉ active effect/request được cập nhật loading state; cleanup/identity guard.

### Medium — Query parameters không được encode an toàn

**Vấn đề:** String interpolation trực tiếp có thể tạo URL sai với `&`, `?`, Unicode hoặc reserved characters.

**Tại sao xảy ra:** Không dùng URL encoding abstraction.

**Ảnh hưởng production:** Query bị biến dạng hoặc thêm unintended parameters.

**Cách sửa:** Dùng `URLSearchParams`.

### Low — Error message thô từ exception được render trực tiếp

**Vấn đề:** Technical message không nhất thiết phù hợp UX và có thể thiếu correlation support.

**Tại sao xảy ra:** Không có error mapping.

**Ảnh hưởng production:** UX kém và support khó correlate lỗi.

**Cách sửa:** Hiển thị user-safe message, giữ diagnostic detail trong telemetry phù hợp.

## Phiên bản đề xuất

```tsx
import { useEffect, useState } from "react";

type Product = { id: string; name: string };
type SearchResult = { items: Product[] };

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const controller = new AbortController();
    const timer = window.setTimeout(async () => {
      const trimmed = query.trim();
      if (!trimmed) {
        setProducts([]);
        setLoading(false);
        setError(null);
        return;
      }

      const parameters = new URLSearchParams({
        q: trimmed,
        category
      });

      setLoading(true);
      setError(null);

      try {
        const response = await fetch(`/api/products?${parameters}`, {
          signal: controller.signal
        });

        if (!response.ok) {
          throw new Error(`Search failed with HTTP ${response.status}`);
        }

        const data: SearchResult = await response.json();
        if (!controller.signal.aborted) {
          setProducts(data.items);
          setLoading(false);
        }
      } catch (error) {
        if (controller.signal.aborted) return;

        setError("Không thể tải kết quả tìm kiếm.");
        setLoading(false);
      }
    }, 250);

    return () => {
      window.clearTimeout(timer);
      controller.abort();
    };
  }, [query, category]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      <select value={category} onChange={e => setCategory(e.target.value)}>
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="software">Software</option>
      </select>
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>
    </section>
  );
}
```

## Giải thích thiết kế sau khi sửa

Effect cleanup hủy timer và request của intent cũ khi query/category đổi hoặc component unmount. `AbortController` giảm work không còn hữu ích và ngăn stale effect commit state. Debounce 250 ms chỉ là scenario choice; giá trị thực tế phải dựa trên UX/load measurement.

`URLSearchParams` xử lý encoding. `response.ok` phân biệt HTTP error khỏi success. Production code có thể dùng một data-fetching abstraction/library nếu application đã chuẩn hóa, nhưng không cần thêm dependency chỉ để giải quyết component nhỏ này.

## Trade-offs

- Debounce làm giảm request volume nhưng thêm một ít perceived latency.
- Cancellation không bảo đảm backend đã dừng work; ASP.NET Core API cũng cần propagate request cancellation đến dependency hỗ trợ nó.
- Client-side sequence guard có thể cần nếu request abstraction không expose cancellation tốt.
- Data-fetching library có cache/deduplication hữu ích nhưng tăng abstraction/dependency; chỉ dùng nếu phù hợp toàn application.

## Cách kiểm thử

1. **Component/integration test:** mock `car` response chậm hơn `cart`; UI cuối cùng chỉ hiển thị `cart`.
2. **Cancellation test:** đổi query/unmount trước completion; stale request không commit state và không hiện abort error.
3. **HTTP error test:** 500 response tạo user-safe error, không parse như success.
4. **Debounce test:** nhiều keystrokes trong 250 ms chỉ phát request cho intent cuối.
5. **E2E/Playwright:** dùng route interception tạo latency khác nhau và xác minh input/result consistency trong browser thật.

## Quan sát trong production

Client telemetry nên đo search intent count, requests actually sent, aborted requests, success/error rate và client-perceived duration. API/Application Insights theo dõi request rate, cancellation, p95/p99 và Elasticsearch dependency duration. Correlation/trace context giúp xác định request bị chậm ở browser, API hay search dependency.

Không alert chỉ vì abort rate tăng nếu abort là expected behavior khi user gõ; alert server error rate, sustained latency và dependency degradation.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend vẫn tiếp tục Elasticsearch query sau khi browser abort, bạn sẽ kiểm tra và propagate cancellation ở ASP.NET Core như thế nào?
2. Khi nào bạn dùng React Query/TanStack Query hoặc abstraction tương tự thay vì tự quản lý effect?
3. Nếu Product yêu cầu instant cached results khi quay lại query cũ, bạn thêm cache mà vẫn tránh stale-data bugs như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Duplicate delivery và out-of-order completion là hai biểu hiện khác nhau của cùng một nguyên tắc: distributed/async systems không bảo đảm thứ tự hoặc “chỉ xảy ra một lần” nếu contract không nói rõ. Correctness phải được thiết kế bằng durable identity, transaction boundaries, idempotency, lifecycle ownership và explicit failure handling.

Service Bus consumer cần coi retry/redelivery là behavior bình thường và tách database atomicity khỏi external side effects. Frontend async flow cần coi request cũ là stale work và không cho nó overwrite latest user intent.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency; đừng giả định exactly-once.
- Đặt correctness guarantee tại durable boundary, không chỉ trong process memory.
- External side effect sau database commit cần explicit recovery strategy.
- Latest user intent phải sở hữu quyền cập nhật UI state.
- Test concurrency, retry, cancellation và failure path thay vì chỉ happy path.
