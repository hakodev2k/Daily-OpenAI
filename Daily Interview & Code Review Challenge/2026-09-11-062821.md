# Code Review Challenge 1 — Cache `Task` trong singleton giúp giảm query nhưng một request bị cancel lại làm cả tenant lỗi mãi

**Chủ đề:** C#/.NET, ASP.NET Core, `ConcurrentDictionary`, async/await, `Task` caching, `CancellationToken`, EF Core, per-instance caching, stale data, fault propagation, memory growth, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 application có dashboard hiển thị dữ liệu order gần nhất của từng tenant. Dashboard bị gọi khá nhiều nên team tạo một singleton in-memory cache để tránh query SQL Server và gọi external pricing API lặp lại.

Yêu cầu hiện tại:

- mỗi tenant có tối đa vài trăm orders cần hiển thị;
- dữ liệu có thể stale khoảng 30–60 giây;
- application chạy 6 Azure App Service instances;
- khi user đóng browser hoặc request timeout, work không còn cần thiết nên được phép cancel;
- external pricing provider đôi lúc timeout hoặc trả `503`;
- tenant mới được tạo/xóa thường xuyên;
- dashboard response không được “hỏng vĩnh viễn” chỉ vì một request trước đó fail;
- operations muốn biết cache hit/miss, load duration và failure rate;
- không có yêu cầu strict consistency giữa tất cả application instances.

Sau một release, production xuất hiện behavior lạ:

- một user mở dashboard rồi đóng tab giữa lúc load;
- sau đó nhiều request khác của cùng tenant liên tục nhận `TaskCanceledException` gần như ngay lập tức;
- ở tenant khác, pricing provider lỗi một lần rồi dashboard tiếp tục fail trong nhiều phút dù provider đã hồi phục;
- memory của process tăng dần theo số tenant từng truy cập;
- khi support gọi endpoint invalidate cache trên một instance, một số users vẫn thấy dữ liệu cũ;
- team nói `ConcurrentDictionary` đã thread-safe nên implementation chắc chắn an toàn.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class TenantDashboardCache
{
    private readonly ConcurrentDictionary<string, Task<List<OrderDto>>> _cache = new();
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly PricingClient _pricingClient;
    private readonly ILogger<TenantDashboardCache> _logger;

    public TenantDashboardCache(
        IDbContextFactory<AppDbContext> dbFactory,
        PricingClient pricingClient,
        ILogger<TenantDashboardCache> logger)
    {
        _dbFactory = dbFactory;
        _pricingClient = pricingClient;
        _logger = logger;
    }

    public Task<List<OrderDto>> GetAsync(
        string tenantId,
        CancellationToken cancellationToken)
    {
        return _cache.GetOrAdd(
            tenantId,
            _ => LoadAsync(tenantId, cancellationToken));
    }

    public bool Invalidate(string tenantId)
        => _cache.TryRemove(tenantId, out _);

    private async Task<List<OrderDto>> LoadAsync(
        string tenantId,
        CancellationToken cancellationToken)
    {
        _logger.LogInformation(
            "Loading dashboard for tenant {TenantId}",
            tenantId);

        await using var db = await _dbFactory
            .CreateDbContextAsync(cancellationToken);

        var orders = await db.Orders
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAtUtc)
            .Take(200)
            .Select(x => new OrderDto
            {
                Id = x.Id,
                ProductId = x.ProductId,
                Quantity = x.Quantity,
                CreatedAtUtc = x.CreatedAtUtc
            })
            .ToListAsync(cancellationToken);

        foreach (var order in orders)
        {
            order.CurrentPrice = await _pricingClient.GetPriceAsync(
                order.ProductId,
                cancellationToken);
        }

        return orders;
    }
}
```

## Kết quả code review tham khảo

### High — Request cancellation của caller đầu tiên có thể “poison” shared cache entry

**Vấn đề:**  
`GetAsync` truyền `CancellationToken` của request đầu tiên vào `LoadAsync`, sau đó cache chính `Task` được tạo bởi operation đó.

**Tại sao xảy ra:**  
`GetOrAdd` biến computation đầu tiên thành shared state cho mọi caller cùng key. Nếu request đầu tiên bị cancel, EF Core hoặc pricing call có thể throw `OperationCanceledException`/`TaskCanceledException`. `Task` đã bị canceled vẫn nằm trong dictionary.

**Ảnh hưởng production:**  
Các request sau có thể nhận lại cùng canceled task và fail gần như ngay lập tức dù chúng có token riêng và dependency đã khỏe.

**Cách sửa:**  
Không gắn lifetime của shared cache fill trực tiếp với cancellation token của một caller ngẫu nhiên. Hoặc dùng cache abstraction có expiration + factory semantics phù hợp, hoặc quản lý shared fill với token có ownership độc lập rồi cho caller chỉ cancel việc **chờ** kết quả. Đồng thời remove failed/canceled entries.

---

### High — Faulted `Task` được cache vô thời hạn

**Vấn đề:**  
Nếu SQL hoặc pricing provider fail, `Task<List<OrderDto>>` chuyển sang faulted nhưng vẫn là value của dictionary.

**Tại sao xảy ra:**  
Dictionary không hiểu state của `Task`; thread-safe collection chỉ bảo vệ concurrent access vào collection chứ không tự retry/remove asynchronous work thất bại.

**Ảnh hưởng production:**  
Một transient `503` có thể biến thành persistent outage cho tenant đó cho tới khi manual invalidation hoặc process restart.

**Cách sửa:**  
Không giữ faulted/canceled result như valid cache value. Cache successful data với explicit TTL, hoặc remove entry khi fill fail. Nếu dùng single-flight task để chống stampede thì lifecycle của task phải tách khỏi lifecycle của final cached value.

---

### High — Cache không có TTL nên vi phạm freshness requirement và tăng memory không giới hạn

**Vấn đề:**  
Entry chỉ biến mất khi gọi `Invalidate`; không có absolute/sliding expiration hoặc size limit.

**Tại sao xảy ra:**  
`ConcurrentDictionary` không phải cache policy engine.

**Ảnh hưởng production:**  
Tenant đã từng truy cập có thể được giữ suốt process lifetime. Data có thể stale nhiều giờ và memory tăng theo tenant cardinality.

**Cách sửa:**  
Dùng `IMemoryCache` với expiration khoảng thời gian phù hợp requirement, cộng size limit nếu cardinality đáng kể; hoặc xây policy rõ nếu cần custom behavior.

---

### High — Invalidation chỉ tác động một process trong deployment nhiều instances

**Vấn đề:**  
`Invalidate` chỉ xóa dictionary của instance nhận request.

**Tại sao xảy ra:**  
In-memory state là local process state. Sáu App Service instances có sáu cache độc lập.

**Ảnh hưởng production:**  
User có thể hit instance khác và tiếp tục thấy stale data. Support dễ kết luận invalidation “không ổn định”.

**Cách sửa:**  
Nếu business chấp nhận stale 30–60 giây thì có thể không cần distributed invalidation: dùng bounded TTL và chấp nhận per-instance divergence. Nếu yêu cầu invalidate gần realtime thì cần explicit distributed invalidation/version signal; không tự động thêm Redis nếu requirement chưa cần.

---

### Medium — Mutable `List<OrderDto>` được chia sẻ trực tiếp cho nhiều callers

**Vấn đề:**  
Cache trả cùng reference tới mutable list và mutable DTO objects.

**Tại sao xảy ra:**  
Caller có thể vô tình sort, add/remove hoặc mutate `CurrentPrice`, làm state shared thay đổi cho caller khác.

**Ảnh hưởng production:**  
Dữ liệu cache có thể bị corrupt ở application level dù dictionary vẫn thread-safe.

**Cách sửa:**  
Cache immutable/read-only projection, ví dụ `ImmutableArray<OrderDashboardItem>` hoặc DTO bất biến; không expose collection mutable nếu không cần.

---

### Medium — Pricing API được gọi tuần tự tối đa 200 lần

**Vấn đề:**  
`foreach` await từng call nối tiếp.

**Tại sao xảy ra:**  
Latency cộng dồn theo số orders. Nếu mỗi dependency call mất 50 ms, hàng trăm calls tuần tự có thể vượt xa dashboard SLO. Ngược lại, đổi thẳng sang `Task.WhenAll` cho 200 calls cũng có thể gây burst/rate-limit.

**Ảnh hưởng production:**  
Cache miss trở nên rất chậm; shared fill dễ timeout/cancel, làm vấn đề cache poisoning nghiêm trọng hơn.

**Cách sửa:**  
Trước hết kiểm tra có thể batch product IDs tại provider hay không. Nếu không, dùng bounded concurrency theo dependency capacity/rate limit, deduplicate cùng `ProductId`, timeout hợp lý và failure/degradation policy rõ.

---

### Medium — Cache key cần normalization/ownership contract rõ

**Vấn đề:**  
Raw `tenantId` string được dùng trực tiếp làm key.

**Tại sao xảy ra:**  
Nếu upstream có nhiều textual forms hoặc case semantics không thống nhất, cùng tenant có thể tạo nhiều entries. Quan trọng hơn, code phải bảo đảm tenant identity đến từ trusted authorization context chứ không chỉ client input.

**Ảnh hưởng production:**  
Duplicate cache entries, memory tăng hoặc nguy cơ tenant-boundary bug nếu caller truyền sai identity.

**Cách sửa:**  
Dùng canonical tenant identifier từ authenticated/authorized context và comparer/normalization phù hợp domain semantics.

---

### Medium — Thiếu explicit degradation strategy khi pricing provider lỗi

**Vấn đề:**  
Một lỗi ở một product price làm toàn bộ dashboard load fault.

**Tại sao xảy ra:**  
Dependency được coi như bắt buộc cho toàn result nhưng scenario chưa chứng minh business cần behavior đó.

**Ảnh hưởng production:**  
Partial dependency outage trở thành total dashboard outage.

**Cách sửa:**  
Làm rõ requirement. Nếu chấp nhận, trả order data với `CurrentPrice = null`/last-known-good và flag degraded. Nếu price là critical invariant thì fail có chủ đích nhưng không cache failure như dữ liệu thành công.

---

### Low — Telemetry chưa phân biệt cache hit, miss, fill, fault và eviction

**Vấn đề:**  
Chỉ log khi `LoadAsync` chạy.

**Tại sao xảy ra:**  
Không có metrics/traces cho cache lifecycle.

**Ảnh hưởng production:**  
Khó chứng minh memory growth, stampede, stale behavior hay dependency amplification.

**Cách sửa:**  
Ghi metrics cho hits/misses/fill duration/fill failures/entry count, dependency calls per fill và structured traces theo tenant identifier đã xử lý phù hợp.

## Phiên bản đề xuất

Một implementation đơn giản hơn là cache **successful immutable data** với TTL, và dùng per-key single-flight riêng để tránh nhiều miss cùng lúc. Shared fill không dùng request cancellation của caller đầu tiên làm ownership token.

```csharp
public sealed record OrderDashboardItem(
    Guid Id,
    string ProductId,
    int Quantity,
    DateTime CreatedAtUtc,
    decimal? CurrentPrice);

public sealed class TenantDashboardCache
{
    private readonly IMemoryCache _cache;
    private readonly ConcurrentDictionary<string, SemaphoreSlim> _locks = new();
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly PricingClient _pricingClient;
    private readonly ILogger<TenantDashboardCache> _logger;

    public TenantDashboardCache(
        IMemoryCache cache,
        IDbContextFactory<AppDbContext> dbFactory,
        PricingClient pricingClient,
        ILogger<TenantDashboardCache> logger)
    {
        _cache = cache;
        _dbFactory = dbFactory;
        _pricingClient = pricingClient;
        _logger = logger;
    }

    public async Task<IReadOnlyList<OrderDashboardItem>> GetAsync(
        string tenantId,
        CancellationToken cancellationToken)
    {
        var key = $"dashboard:{tenantId}";

        if (_cache.TryGetValue(key, out IReadOnlyList<OrderDashboardItem>? cached))
            return cached!;

        var gate = _locks.GetOrAdd(key, _ => new SemaphoreSlim(1, 1));
        await gate.WaitAsync(cancellationToken);

        try
        {
            if (_cache.TryGetValue(key, out cached))
                return cached!;

            // Cache-fill lifetime is intentionally not owned by a random caller.
            // A production implementation should use an explicit bounded internal
            // timeout/shutdown token rather than CancellationToken.None forever.
            using var fillTimeout = new CancellationTokenSource(TimeSpan.FromSeconds(10));

            var result = await LoadAsync(tenantId, fillTimeout.Token);

            _cache.Set(
                key,
                result,
                new MemoryCacheEntryOptions
                {
                    AbsoluteExpirationRelativeToNow = TimeSpan.FromSeconds(45),
                    Size = Math.Max(1, result.Count)
                });

            return result;
        }
        finally
        {
            gate.Release();
        }
    }

    private async Task<IReadOnlyList<OrderDashboardItem>> LoadAsync(
        string tenantId,
        CancellationToken cancellationToken)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(cancellationToken);

        var rows = await db.Orders
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAtUtc)
            .Take(200)
            .Select(x => new
            {
                x.Id,
                x.ProductId,
                x.Quantity,
                x.CreatedAtUtc
            })
            .ToListAsync(cancellationToken);

        var productIds = rows
            .Select(x => x.ProductId)
            .Distinct()
            .ToArray();

        var prices = await _pricingClient.GetPricesAsync(
            productIds,
            cancellationToken);

        return rows
            .Select(x => new OrderDashboardItem(
                x.Id,
                x.ProductId,
                x.Quantity,
                x.CreatedAtUtc,
                prices.TryGetValue(x.ProductId, out var price) ? price : null))
            .ToArray();
    }
}
```

Đây chỉ là một direction. `SemaphoreSlim` dictionary ở ví dụ vẫn cần lifecycle cleanup nếu key cardinality rất lớn; có thể dùng một single-flight abstraction/library phù hợp hoặc eviction-aware strategy thay vì tự quản lý locks vô hạn. Điểm quan trọng là không chuyển từ unbounded data cache sang unbounded lock cache.

Nếu product requirement chỉ cần stale tối đa 60 giây, per-instance `IMemoryCache` có thể hoàn toàn đủ và đơn giản hơn distributed cache. Sáu instances không cần cùng value tại cùng millisecond nếu business không yêu cầu điều đó.

Nếu caller cancel khi đang chờ lock, caller có thể dừng chờ. Nếu caller cancel sau khi fill đã bắt đầu, cần quyết định rõ liệu shared fill có tiếp tục vì các callers khác vẫn cần nó hay không. Internal fill phải có timeout và host-shutdown semantics riêng; không nên dùng `CancellationToken.None` không giới hạn.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách ba khái niệm trước đây bị trộn:

- **cached data**: chỉ successful immutable result, có TTL;
- **single-flight coordination**: ngăn nhiều cache miss cùng key tạo nhiều expensive loads;
- **caller cancellation**: cho phép một caller dừng chờ mà không mặc định hủy shared computation của tất cả callers.

`IMemoryCache` được dùng vì requirement cho phép stale 30–60 giây và không yêu cầu strict cluster-wide consistency. Việc thêm distributed cache chỉ để mọi node “giống nhau” sẽ tăng network dependency, serialization, invalidation và operational complexity mà chưa chắc mang giá trị.

Pricing lookup nên batch nếu provider/API hỗ trợ. Nếu không có batch endpoint, bounded concurrency tốt hơn cả hai cực đoan: 200 calls tuần tự hoặc 200 calls đồng thời.

## Trade-offs

- Per-instance memory cache đơn giản và nhanh nhưng các instances có thể stale khác nhau trong TTL window.
- Single-flight làm giảm duplicate load nhưng tạo thêm coordination state và phải quản lý lifecycle của per-key locks.
- Cho shared fill tiếp tục sau khi một caller cancel có thể dùng tài nguyên cho request không còn tồn tại, nhưng tránh một caller phá kết quả của tất cả callers khác. Vì vậy cần internal timeout và metrics.
- Immutable data có thể tạo allocation/copy nhỏ hơn so với chia sẻ mutable list, đổi lại correctness và reasoning tốt hơn.
- Batch pricing giảm request count nhưng yêu cầu provider hỗ trợ hoặc application có aggregation layer phù hợp.

## Cách kiểm thử

1. **Concurrency test:** 100 requests cùng tenant khi cache miss; verify chỉ có một logical fill hoặc số fill đúng theo coordination design, mọi caller nhận cùng valid data.
2. **Cancellation test:** caller đầu tiên cancel trong lúc fill; các caller khác không bị permanently poisoned và request sau vẫn recover.
3. **Failure-path test:** pricing provider trả `503` một lần; failure không được cache vô thời hạn, lần sau có thể reload thành công theo policy.
4. **Expiration/load test:** tạo nhiều tenant keys, chạy qua nhiều TTL cycles và quan sát entry/memory growth; không để cache/lock state tăng vô hạn.
5. **Multi-instance validation:** chứng minh bounded stale behavior khi invalidate/expire ở các nodes khác nhau; nếu business yêu cầu stronger invalidation thì test mechanism phân tán riêng.

## Quan sát trong production

Theo dõi ít nhất:

- `dashboard_cache_hit_total` / `dashboard_cache_miss_total`;
- fill duration p50/p95/p99;
- fill success/failure/cancellation counts;
- active cache entries và estimated size;
- number of single-flight waiters;
- pricing calls per cache fill;
- SQL query duration;
- dependency `429`/`5xx`/timeout;
- process memory/GC metrics;
- Application Insights trace correlation theo instance + tenant identifier an toàn;

## Câu hỏi phỏng vấn mở rộng

1. Nếu business đổi requirement thành “sau khi user cập nhật order, mọi instance phải thấy dữ liệu mới trong dưới 2 giây”, bạn còn giữ pure per-instance cache không?

3. Nếu thêm Redis, những failure mode mới nào xuất hiện và tại sao distributed cache không tự giải quyết cache stampede/invalidation correctness?

# Code Review Challenge 2 — Akamai cache HTML đã đăng nhập: website nhanh hơn nhưng có nguy cơ trả dữ liệu user A cho user B

**Chủ đề:** ASP.NET Core, Akamai/CDN, HTTP caching, `Cache-Control`, personalized content, authentication, cache keys, cookies, security, SEO/web performance, failure behavior, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một marketing/e-commerce website render HTML bằng ASP.NET Core. Phần lớn page là public CMS content, nhưng khi user đăng nhập server sẽ render thêm:

- tên user ở header;
- loyalty tier;
- số lượng items trong cart;
- một CTA riêng cho account.

Akamai đứng trước origin để giảm load và cải thiện TTFB/Core Web Vitals. Team muốn cache HTML 10 phút ở edge vì campaign traffic có thể tăng đột biến.

Sau thay đổi gần đây:

- CDN hit ratio tăng mạnh;
- origin CPU giảm;
- support nhận vài report rằng refresh page sau login đôi khi hiển thị tên/tier không đúng;
- logout xong đôi khi header vẫn trông như đang login;
- market `en-AU` đôi khi thấy canonical/metadata của market khác;
- application không thấy request tương ứng trong origin logs vì response là CDN HIT;
- team định thêm `Vary: Authorization` và purge URL sau mỗi login/logout để “sửa cache”.

Origin code và edge policy được rút gọn như sau:

## Đoạn code cần review

```csharp
[HttpGet("/{market}/{slug}")]
public async Task<IActionResult> Page(
    string market,
    string slug,
    CancellationToken cancellationToken)
{
    var page = await _cms.GetPublishedPageAsync(
        market,
        slug,
        cancellationToken);

    if (page is null)
        return NotFound();

    var model = new PageViewModel
    {
        Title = page.Title,
        BodyHtml = page.BodyHtml,
        CanonicalUrl = page.CanonicalUrl
    };

    if (User.Identity?.IsAuthenticated == true)
    {
        var account = await _accounts.GetAsync(
            User,
            cancellationToken);

        model.UserName = account.DisplayName;
        model.LoyaltyTier = account.LoyaltyTier;
        model.CartCount = account.CartCount;
    }

    Response.Headers.CacheControl =
        "public, max-age=120, s-maxage=600";

    return View("Page", model);
}
```

  scheme + host + path

1. Xác định correctness và security problems.
2. Xác định performance/reliability concerns mà không đánh đổi privacy.
3. Giải thích production impact, đặc biệt cache HIT không chạm origin.
4. Ưu tiên findings theo severity.
5. Đề xuất rendering + caching design an toàn hơn.
6. Giải thích testing cho anonymous/authenticated, multi-market, purge và origin failure.
7. Đề xuất CDN/origin/browser telemetry để phát hiện regression.

## Câu hỏi gợi mở

1. Một shared cache object có chứa dữ liệu phụ thuộc identity của request hay không?
2. Cache key hiện tại phân biệt anonymous/authenticated users hoặc user A/user B bằng cách nào?
3. `Vary: Authorization` có thực sự là boundary tốt cho personalized HTML hay chỉ làm cache cardinality/security reasoning phức tạp hơn?
4. Khi edge trả HIT hoặc stale object, origin authorization/rendering logic có được chạy lại không?
5. Public CMS content, market-specific metadata và user-specific header có nhất thiết phải nằm trong cùng một cached HTML object không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **shared-cache data isolation**: một response personalized đang được đánh dấu `public` và cache key không chứa identity.

### Gợi ý 2

Thiết kế tốt thường tách cacheable public shell/content khỏi private user state, thay vì cố biến identity thành một edge cache dimension.

## Kết quả code review tham khảo

### Critical — Personalized response được đánh dấu `public` và có thể được shared-cache giữa users

**Vấn đề:**  
Controller render `UserName`, `LoyaltyTier`, `CartCount` vào HTML rồi đặt:

```http
Cache-Control: public, max-age=120, s-maxage=600
```

Akamai cache key không phân biệt identity.

**Tại sao xảy ra:**  
`public` cho phép shared cache lưu response. Nếu first cacheable response cho URL được render khi user A đang authenticated, edge có thể phục vụ object đó cho request khác phù hợp cùng cache key mà không gọi origin.

**Ảnh hưởng production:**  
Cross-user information disclosure, sai cart/account state và security incident. Đây không còn là bug UI đơn thuần.

**Cách sửa:**  
Không shared-cache HTML chứa private/user-specific data. Tách public page shell/content khỏi personalized state, hoặc bypass shared cache và dùng `private`/`no-store` theo sensitivity cho personalized response.

---

### High — Cache HIT bypass origin nên origin authorization/rendering không thể “sửa” object đã cache

**Vấn đề:**  
Team đang reasoning như mọi request vẫn đi qua controller.

**Tại sao xảy ra:**  
Edge HIT được trả trước origin; ASP.NET Core không chạy cho request đó.

**Ảnh hưởng production:**  
Logs ở origin thiếu evidence, logout/login behavior khó hiểu, và security checks ở origin không bảo vệ một object edge đã cache sai.

**Cách sửa:**  
Thiết kế cache boundary trước authorization-sensitive content; instrument CDN cache status/request ID và bảo đảm private paths/variants không cache shared.

---

### High — `Vary: Authorization` không phải default fix tốt cho user-personalized HTML

**Vấn đề:**  
Team muốn đưa bearer credential thành cache variation dimension.

**Tại sao xảy ra:**  
Ngoài việc CDN behavior cần được cấu hình/verify cụ thể, tạo cache objects theo credential/user làm cardinality lớn, tăng cache complexity và dễ gây privacy mistakes. Authentication trên website cũng có thể dựa vào cookies chứ không phải `Authorization` header.

**Ảnh hưởng production:**  
Cache hit ratio giảm, cache state khó kiểm soát, vẫn có thể leak nếu một identity signal khác bị bỏ qua hoặc CDN không xử lý `Vary` theo giả định.

**Cách sửa:**  
Không cache shared personalized HTML. Cache anonymous/public representation; tải user state qua private authenticated endpoint hoặc server-side fragment mechanism có isolation rõ nếu platform hỗ trợ và được security review.

---

### High — Purge sau login/logout không giải quyết identity isolation

**Vấn đề:**  
Purge URL được đề xuất như correctness mechanism.

**Tại sao xảy ra:**  
Login/logout của một user không phải global content mutation. Purging shared URL cho mọi auth transition vừa tốn kém vừa có race và không ngăn response của user tiếp theo trở thành cached shared object.

**Ảnh hưởng production:**  
Purge storm, origin load spikes và leak vẫn có thể tái diễn.

**Cách sửa:**  
Sửa cacheability/cache key boundary; purge chỉ dùng cho public content lifecycle khi phù hợp, không dùng để mô phỏng per-user cache isolation.

---

### High — Forward `Set-Cookie` cùng shared cached objects cần được kiểm soát chặt

**Vấn đề:**  
Edge policy nói `Set-Cookie` từ origin được forward, trong khi response có thể shared-cache.

**Tại sao xảy ra:**  
Nếu response chứa cookie state và CDN lưu/replay header không đúng policy, session/tracking behavior có thể sai hoặc nhạy cảm. Exact Akamai behavior phải được xác minh trong property config; không nên dựa vào assumption.

**Ảnh hưởng production:**  
Sai session state, privacy risk hoặc cache bypass không như dự kiến.

**Cách sửa:**  
Public cacheable HTML không nên chứa authentication/session-setting behavior. Strip/avoid inappropriate `Set-Cookie` trên public cached response theo reviewed CDN policy; private auth responses phải bypass shared cache.

---

### Medium — Stale-on-error 30 phút có thể kéo dài exposure hoặc dữ liệu sai

**Vấn đề:**  
Edge có thể serve stale HTML lâu hơn TTL bình thường.

**Tại sao xảy ra:**  
Stale serving là resilience feature cho public content nhưng nguy hiểm nếu object chứa personalized hoặc market-sensitive data không đúng.

**Ảnh hưởng production:**  
Một cached leak/sai header có thể tiếp tục được phục vụ khi origin lỗi, đúng lúc team khó purge/verify nhất.

**Cách sửa:**  
Chỉ dùng stale-on-error cho representation được chứng minh là public/safe. Private data không đi qua shared stale cache.

### Medium — Query strings bị ignore có thể gây correctness bug nếu query ảnh hưởng representation

**Vấn đề:**  
Akamai key bỏ toàn bộ query string.

**Tại sao xảy ra:**  
Nếu tương lai/hiện tại query như `?preview=`, campaign variant, locale override hoặc pagination thay đổi HTML, các variants có thể collapse thành một object.

**Ảnh hưởng production:**  
Sai content, preview leak hoặc analytics/campaign behavior không đúng tùy routes thực tế.

**Cách sửa:**  
Allowlist những query parameters thực sự ảnh hưởng representation vào cache key hoặc bypass caching cho preview/auth-sensitive modes. Không đưa tracking parameters vô key nếu chúng không đổi content.

### Medium — Public content và personalized state bị coupling trong cùng server-rendered model

**Vấn đề:**  
Một endpoint/render path đang cố tối ưu đồng thời hai loại state có cacheability hoàn toàn khác nhau.

**Tại sao xảy ra:**  
Editorial CMS content thay đổi theo phút/giờ; user/account state thay đổi theo giây và là private.

**Ảnh hưởng production:**  
Hoặc phải bỏ phần lớn CDN benefit, hoặc dễ tạo security bug khi cache toàn document.

**Cách sửa:**  
Render public anonymous shell ở origin/edge; hydrate user-specific header từ authenticated API với `private, no-store` hoặc policy phù hợp. Nếu SEO yêu cầu một số dynamic data trong HTML, chỉ server-render data không user-specific vào cacheable representation.

Không có unified edge/origin observability.

**Ảnh hưởng production:**

## Phiên bản đề xuất

Một architecture đơn giản và an toàn hơn là cache **anonymous public page** ở Akamai, còn user state lấy từ endpoint private sau khi page load.

```csharp
[AllowAnonymous]
[HttpGet("/{market}/{slug}")]
public async Task<IActionResult> Page(
    string market,
    string slug,
    CancellationToken cancellationToken)
{
    var page = await _cms.GetPublishedPageAsync(
        market,
        slug,
        cancellationToken);

    if (page is null)
        return NotFound();

    Response.Headers.CacheControl =
        "public, max-age=120, s-maxage=600";

    var model = new PublicPageViewModel
    {
        Title = page.Title,
        BodyHtml = page.BodyHtml,
        CanonicalUrl = page.CanonicalUrl,
        Market = market
    };

    return View("Page", model);
}

[Authorize]
[HttpGet("/api/me/header")]
public async Task<IActionResult> AccountHeader(
    CancellationToken cancellationToken)
{
    Response.Headers.CacheControl = "private, no-store";

    var account = await _accounts.GetAsync(
        User,
        cancellationToken);

    return Ok(new
    {
        account.DisplayName,
        account.LoyaltyTier,
        account.CartCount
    });
}
```

Frontend public HTML có anonymous placeholder:

```html
<header>
  <div id="account-state" data-mode="anonymous"></div>
</header>
```

Sau client authentication, JavaScript gọi `/api/me/header`. Endpoint này không shared-cache. Public page vẫn đạt CDN hit ratio cao mà không đưa user identity vào shared object.

Akamai policy nên được diễn đạt theo **cacheability classes**, ví dụ conceptually:

```text
Public CMS page:
  cache shared
  honor bounded public TTL
  cache key includes host + normalized path/market
  allowlist only representation-changing query params
  do not cache preview/authenticated variants

/api/me/*:
  bypass shared cache
  honor private/no-store

Preview/editor routes:
  bypass shared cache
  require authorization
  noindex
```

Không nên coi đoạn config trên là cú pháp Akamai cụ thể; property behavior thực tế cần được verify trong environment/tooling hiện hành.

Nếu website bắt buộc server-render personalized header, cách an toàn mặc định là bypass shared cache cho authenticated response:

```csharp
if (User.Identity?.IsAuthenticated == true)
{
    Response.Headers.CacheControl = "private, no-store";
}
else
{
    Response.Headers.CacheControl =
        "public, max-age=120, s-maxage=600";
}
```

Cách này giảm edge hit ratio cho logged-in traffic nhưng boundary dễ reasoning hơn. Chỉ dùng fragment/edge personalization khi requirement đủ lớn để trả complexity cost và security model đã được review.

## Giải thích thiết kế sau khi sửa

Thiết kế tách state theo ownership/freshness:

- **CMS public content** → shared cacheable;
- **market-specific routing/SEO metadata** → nằm trong public object nhưng cache key phải phân biệt market/path đúng;
- **user/account/cart state** → private, authenticated, không shared-cache.

Akamai lúc này tối ưu phần có cardinality thấp và reuse cao. User state không làm cache key nổ theo số users.

Logout/login không cần global purge page. Public shell vẫn giống nhau; account endpoint phản ánh auth state hiện tại theo application semantics.

Stale-on-error trở thành resilience feature hợp lý cho public CMS HTML nếu business chấp nhận, vì stale object không chứa dữ liệu private.

## Trade-offs

- Client-side hydration tạo thêm một request và có thể gây header “pop-in”; có thể giảm bằng skeleton, preconnect hoặc server render private path khi cần.
- Bypass cache cho authenticated HTML đơn giản và an toàn nhưng giảm CDN offload cho logged-in traffic.
- Edge-side fragments/personalization có thể cải thiện UX nhưng tăng cache-key, security, testing và operational complexity.
- Public stale serving tăng availability nhưng có thể kéo dài editorial stale content; TTL/stale window phải theo publishing SLA.
- Query-parameter allowlist cần governance; include quá nhiều làm fragmentation, ignore quá nhiều làm correctness bug.

## Cách kiểm thử

1. **Security test:** login user A, warm cache, sau đó request cùng URL anonymous và user B; tuyệt đối không thấy identity/cart/tier của A trong response body/headers.
2. **E2E test:** Playwright chạy login → navigate cached public pages → logout → navigate lại; public shell đúng và private header state thay đổi theo session mà không cần global purge.
3. **Multi-market test:** warm `en-AU` và market khác theo cùng slug; verify canonical/meta/content không cross-market và cache key phân biệt đúng path.
4. **Failure-path test:** origin unavailable khi edge có public stale object; public page có thể được serve theo policy nhưng `/api/me/*` không được trả stale data của user khác.
5. **Deployment/CDN validation:** kiểm tra response headers/cache status trên MISS/HIT, preview/auth routes bypass, query allowlist hoạt động đúng và không cache response chứa private markers.

## Quan sát trong production

Theo dõi:

- CDN HIT/MISS/BYPASS ratio theo route class;
- cache object age/TTL và stale-served count;
- origin request rate + p95 TTFB;
- private account API p95/error rate;
- cache-key cardinality bất thường;
- purge success/failure/latency cho public content publishing;
- market/content-version mismatch indicators;
- safe request correlation giữa edge và origin;
- synthetic probes so sánh anonymous/user-A/user-B representations;
- security alert nếu public cached HTML chứa known private-data marker pattern;
- Core Web Vitals/Lighthouse trends để bảo đảm security fix không bị “rollback” vì performance pressure.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Thread-safe collection không đồng nghĩa asynchronous computation bên trong nó có lifetime/cancellation semantics đúng. Cache một `Task` nghĩa là bạn cũng cache trạng thái success, fault hoặc cancellation của task đó.
- Cancellation token phải có ownership phù hợp. Token của một HTTP caller không nên mặc định sở hữu shared work đang phục vụ nhiều callers khác.
- Cache cần explicit freshness, eviction, failure và multi-instance semantics; `ConcurrentDictionary` đơn thuần không cung cấp các policy này.
- Shared CDN cache chỉ an toàn khi representation thực sự shareable. Personalized HTML không được biến thành `public` object chỉ để tăng hit ratio.
- Edge HIT không chạy lại origin authorization/rendering. Vì vậy cache boundary là một phần của security architecture, không chỉ là performance tuning.
- Tách public CMS content khỏi private account state thường cho design đơn giản, hiệu quả và dễ kiểm chứng hơn việc cache theo từng identity.

## Mẫu tư duy cần nhớ

- **Phân biệt thread safety với state/lifetime correctness.**
- **Xác định ownership của cancellation và shared work trước khi tối ưu async.**
- **Cache successful data theo policy; đừng vô tình cache transient failure vô thời hạn.**
- **Phân loại dữ liệu theo public/private + freshness trước khi thiết kế CDN/cache key.**
- **Tối ưu performance không được phá security boundary; đo cả hit ratio lẫn correctness/privacy.**
