# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng và ghi đè trạng thái

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, transaction handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8 vấn đề

## Bối cảnh

Một ASP.NET Core application sử dụng Hangfire để xử lý các cấu hình offboarding đã hết hạn. Job có thể chạy trên nhiều worker instance. Mỗi cấu hình hết hạn cần reset forwarding/delegation trên Exchange Online rồi cập nhật database. Production đôi khi xuất hiện cùng một mailbox bị reset hai lần, trạng thái DB không khớp với Exchange, job retry gây thêm side effect và log khó xác định lần chạy nào thực sự thành công.

Giả định `AppDbContext` là scoped, Hangfire có automatic retry mặc định của hệ thống, và thao tác Exchange là remote side effect có thể timeout sau khi server đã thực hiện thành công.

## Đoạn code cần review

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly AppDbContext _db;
    private readonly ExchangeService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        AppDbContext db,
        ExchangeService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteAsync()
    {
        var now = DateTime.UtcNow;
        var configs = await _db.MailConfigs
            .Where(x => x.EndTime <= now && x.Status == "Active")
            .ToListAsync();

        foreach (var config in configs)
        {
            try
            {
                await _exchange.DisableForwardingAsync(config.Email);
                await _exchange.RemoveDelegatesAsync(config.Email);

                config.Status = "Expired";
                config.UpdatedAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Reset completed for {Email}", config.Email);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Reset failed for {Email}", config.Email);
                throw;
            }
        }
    }
}
```

## Kết quả code review tham khảo

### 1. Không có cơ chế claim/idempotency trước remote side effect

- **Problem:** Nhiều worker có thể cùng query một `Active` record rồi cùng gọi Exchange.
- **Why:** Read và transition state không được thực hiện atomically.
- **Impact:** Duplicate remote operations, race condition, trạng thái khó dự đoán.
- **Severity:** Critical.
- **Fix:** Atomically claim work bằng conditional update/state transition hoặc cơ chế locking phù hợp; dùng operation identity/idempotency strategy cho side effect.

### 2. Retry sau ambiguous timeout có thể lặp side effect

- **Problem:** Client không biết Exchange đã thực hiện thao tác hay chưa nếu response bị mất/timeout.
- **Why:** Remote side effect và DB commit không cùng transaction boundary.
- **Impact:** Retry có thể thực hiện lại thao tác đã thành công.
- **Severity:** Critical.
- **Fix:** Thiết kế operation idempotent nếu API cho phép; nếu không, query/reconcile remote state trước retry và lưu execution state rõ ràng.

### 3. Không có durable workflow state

- **Problem:** Chỉ có `Active`/`Expired`, không thể biểu diễn processing hoặc partial completion.
- **Why:** Workflow nhiều bước bị mô hình hóa như một update đơn giản.
- **Impact:** Khó recovery khi forwarding thành công nhưng delegate removal thất bại.
- **Severity:** High.
- **Fix:** Lưu trạng thái như `Pending`, `Processing`, `Completed`, `Failed` cùng attempt count, operation ID và timestamps; nếu cần, lưu trạng thái từng step.

### 4. `throw` trong loop làm dừng toàn bộ batch

- **Problem:** Một mailbox thất bại khiến các mailbox sau không được xử lý trong run đó.
- **Impact:** Backlog tăng và retry lại batch có thể chạm các item đã có side effect.
- **Severity:** High.
- **Fix:** Tách mỗi item thành independent job hoặc quản lý failure per item.

### 5. Không có concurrency token/conditional state transition

- **Problem:** DB không phát hiện worker khác đã thay đổi cùng record.
- **Impact:** Lost update hoặc state transition sai.
- **Severity:** High.
- **Fix:** Optimistic concurrency token (`rowversion` trên SQL Server hoặc cơ chế tương ứng) hoặc atomic conditional update.

### 6. Không truyền cancellation token

- **Problem:** DB và external calls không nhận cancellation.
- **Impact:** Shutdown/deployment có thể kéo dài; work có thể tiếp tục khi execution đã bị hủy.
- **Severity:** Medium.
- **Fix:** Propagate cancellation token khi API hỗ trợ và thiết kế recovery cho cancellation giữa các step.

### 7. Query toàn bộ expired rows một lần

- **Problem:** Không batching/paging.
- **Impact:** Memory tăng, DbContext tracking phình lớn, transaction/work duration khó kiểm soát khi backlog lớn.
- **Severity:** Medium.
- **Fix:** Claim theo batch giới hạn hoặc enqueue independent jobs.

### 8. Observability thiếu operation identity và step information

- **Problem:** Log chỉ có email.
- **Impact:** Khó correlate retries và xác định bước nào đã thành công.
- **Severity:** Medium.
- **Fix:** Structured logs với config ID, operation ID, attempt, step, duration và result; tránh log dữ liệu nhạy cảm không cần thiết.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa state machine và atomic claim ở application level; production implementation cần chọn conditional update phù hợp database provider và chiến lược reconcile với Exchange.

```csharp
public sealed class ResetExpiredMailItemJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ExchangeService _exchange;
    private readonly ILogger<ResetExpiredMailItemJob> _logger;

    public ResetExpiredMailItemJob(
        IDbContextFactory<AppDbContext> dbFactory,
        ExchangeService exchange,
        ILogger<ResetExpiredMailItemJob> logger)
    {
        _dbFactory = dbFactory;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteAsync(long configId, CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.MailConfigs
            .Where(x => x.Id == configId && x.Status == "Pending")
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.UpdatedAt, DateTime.UtcNow), ct);

        if (claimed == 0)
        {
            _logger.LogInformation(
                "Mail reset skipped because item {ConfigId} was already claimed",
                configId);
            return;
        }

        var config = await db.MailConfigs
            .SingleAsync(x => x.Id == configId, ct);

        using var scope = _logger.BeginScope(new Dictionary<string, object>
        {
            ["ConfigId"] = config.Id,
            ["OperationId"] = config.OperationId
        });

        try
        {
            await _exchange.EnsureForwardingDisabledAsync(config.Email, ct);
            await _exchange.EnsureDelegatesRemovedAsync(config.Email, ct);

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;
            config.UpdatedAt = DateTime.UtcNow;
            await db.SaveChangesAsync(ct);
        }
        catch (Exception ex)
        {
            config.Status = "Failed";
            config.LastErrorCode = ex.GetType().Name;
            config.UpdatedAt = DateTime.UtcNow;
            await db.SaveChangesAsync(CancellationToken.None);

            _logger.LogError(ex, "Mail reset operation failed");
            throw;
        }
    }
}
```

Điểm quan trọng là `Ensure...` nên có semantics idempotent/reconciliation thay vì giả định mỗi remote call chỉ chạy một lần. Nếu việc kiểm tra remote state có chi phí cao, có thể lưu step state và chỉ reconcile khi outcome ambiguous.

## Trade-offs

Atomic claim đơn giản và phù hợp nhiều workload, nhưng một worker crash sau khi chuyển sang `Processing` đòi hỏi lease/timeout hoặc recovery job. Distributed lock có thể giảm concurrent execution nhưng không giải quyết ambiguous remote outcome. Tách từng mailbox thành một Hangfire job tăng số job nhưng isolation, retry và observability tốt hơn. Với workflow phức tạp hơn, durable workflow/state machine có thể đáng giá hơn một batch job tự quản lý nhiều step.

## Cách kiểm thử

1. **Concurrency test:** chạy đồng thời nhiều executions cho cùng `configId`; xác minh chỉ một execution claim được item.
2. **Ambiguous failure test:** mock Exchange thực hiện side effect rồi throw timeout; retry phải reconcile và không gây trạng thái sai.
3. **Partial failure:** disable forwarding thành công, remove delegates thất bại; retry phải tiếp tục an toàn.
4. **Worker crash:** crash sau khi claim; recovery mechanism phải đưa item quay lại trạng thái có thể xử lý.
5. **Load test:** hàng nghìn expired configs; theo dõi DB connections, job latency, backlog và memory.

## Quan sát trong production

Theo dõi structured logs theo `OperationId`/`ConfigId`, job attempt và từng external step; metrics gồm pending/processing/failed count, retry count, duration, Exchange error/timeout rate và oldest pending age. Trace nên liên kết Hangfire execution → DB claim → Exchange calls. Alert khi failed backlog hoặc processing age vượt threshold. Database dashboard nên phát hiện item kẹt ở `Processing`.

2. Distributed lock có đủ để đảm bảo exactly-once không? Vì sao?
3. Khi nào bạn chọn outbox/state machine thay vì một Hangfire job đơn giản?

# Code Review Challenge 2 — API tìm kiếm audit log có SQL injection và rò rỉ dữ liệu tenant

**Chủ đề:** Authorization, SQL injection, multi-tenancy, sensitive-data exposure, query performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép admin tìm audit logs. Endpoint được thêm nhanh để hỗ trợ điều tra incident. Production có hàng chục triệu audit records. QA phát hiện một tenant đôi lúc nhìn thấy dữ liệu không thuộc tenant của mình khi dùng filter đặc biệt. Security review cũng cảnh báo endpoint có khả năng injection và log có thể chứa token hoặc request body nhạy cảm.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string? text,
        string? userId,
        DateTime? from,
        DateTime? to)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;

        var sql = $"SELECT * FROM AuditLogs WHERE TenantId = '{tenantId}'";

        if (!string.IsNullOrWhiteSpace(text))
            sql += $" AND Message LIKE '%{text}%'";

        if (!string.IsNullOrWhiteSpace(userId))
            sql += $" OR UserId = '{userId}'";

        if (from.HasValue)
            sql += $" AND CreatedAt >= '{from.Value:O}'";

        if (to.HasValue)
            sql += $" AND CreatedAt <= '{to.Value:O}'";

        _logger.LogInformation("Audit search SQL: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Kết quả code review tham khảo

### 1. Tenant isolation bị phá bởi `OR`

- **Problem:** `... WHERE TenantId = X AND ... OR UserId = Y` có thể trả rows của tenant khác có cùng `UserId`.
- **Why:** Trong SQL, `AND` có precedence cao hơn `OR`; thiếu grouping khiến tenant predicate không áp dụng cho toàn bộ biểu thức.
- **Impact:** Cross-tenant data disclosure.
- **Severity:** Critical.
- **Fix:** Tenant predicate phải là invariant filter; xây query bằng LINQ/composable predicates và không cho user filter thay đổi tenant boundary.

### 2. SQL injection qua interpolated user input

- **Problem:** `text`, `userId` và cả dữ liệu đưa vào raw SQL được nối trực tiếp.
- **Impact:** Query manipulation, data exposure hoặc hậu quả lớn hơn tùy quyền DB account/provider.
- **Severity:** Critical.
- **Fix:** Parameterized queries; ưu tiên LINQ cho query này. Nếu raw SQL thực sự cần thiết, dùng parameter APIs đúng cách.

### 3. Thiếu explicit authorization policy

- **Problem:** Endpoint không thể hiện yêu cầu admin/audit-reader policy.
- **Impact:** Authenticated user có claim phù hợp nhưng không có business permission vẫn có thể truy cập.
- **Severity:** High.
- **Fix:** Dùng `[Authorize(Policy = "AuditReader")]` hoặc policy tương ứng và validate tenant context bắt buộc.

### 4. Trả nguyên entity có thể expose sensitive fields

- **Problem:** `SELECT *` + return entity trực tiếp.
- **Impact:** Token, payload, internal metadata hoặc PII có thể ra API response.
- **Severity:** High.
- **Fix:** Projection sang response DTO allowlist fields; redact sensitive audit content ngay từ ingestion hoặc presentation layer theo policy.

### 5. Không pagination/bounded time range

- **Problem:** `ToListAsync()` có thể materialize lượng dữ liệu rất lớn.
- **Impact:** Memory pressure, DB load, latency và DoS-like behavior.
- **Severity:** High.
- **Fix:** Pagination có upper bound, deterministic ordering và cân nhắc yêu cầu time window.

### 6. Log raw SQL chứa user-controlled/sensitive search text

- **Problem:** Search terms được ghi nguyên vào logs.
- **Impact:** Sensitive data leakage và log-forging risk tùy sink/rendering.
- **Severity:** Medium.
- **Fix:** Log normalized metadata như tenant, filter presence, range, result count, duration; không log raw sensitive values mặc định.

### 7. Query shape có thể không tận dụng index tốt

- **Problem:** Leading wildcard `%text%` thường không phù hợp B-tree index cho substring search; thiếu ordering/index strategy rõ ràng.
- **Impact:** Scan lớn trên audit table.
- **Severity:** Medium.
- **Fix:** Index theo tenant/time/use-case; nếu cần full-text/sub-string search ở scale lớn, đánh giá full-text/search engine phù hợp thay vì tùy tiện `LIKE '%...%'`.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
[Authorize(Policy = "AuditReader")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        string? text,
        string? userId,
        DateTime? from,
        DateTime? to,
        int pageSize = 50,
        CancellationToken ct = default)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;
        if (string.IsNullOrWhiteSpace(tenantId))
            return Forbid();

        pageSize = Math.Clamp(pageSize, 1, 100);

        var query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(text))
            query = query.Where(x => x.Message.Contains(text));

        if (!string.IsNullOrWhiteSpace(userId))
            query = query.Where(x => x.UserId == userId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        var rows = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(pageSize)
            .Select(x => new AuditLogDto(
                x.Id,
                x.UserId,
                x.Action,
                x.CreatedAt,
                x.SafeSummary))
            .ToListAsync(ct);

        _logger.LogInformation(
            "Audit search completed for tenant {TenantId}; Count={Count}",
            tenantId,
            rows.Count);

        return Ok(rows);
    }
}
```

Ở production, cursor/keyset pagination thường phù hợp hơn offset pagination cho audit stream lớn. `Contains` cần được kiểm tra SQL translation và execution plan trên provider thực tế; nếu search nội dung là requirement quan trọng, cần thiết kế search/index riêng. Authorization cũng nên đảm bảo tenant identity đến từ trusted authentication context và không nhận tenant ID tùy ý từ request.

## Trade-offs

LINQ giảm đáng kể nguy cơ raw SQL injection và giúp compose tenant invariant rõ hơn, nhưng không tự bảo đảm query nhanh. Full-text/search service tăng operational complexity nhưng có thể cần thiết nếu substring search là use case chính. Global query filter cho tenant giảm nguy cơ developer quên predicate, nhưng vẫn cần defense-in-depth, tests và cách xử lý rõ ràng cho privileged cross-tenant operations. DTO projection tăng code nhưng kiểm soát data exposure tốt hơn.

## Cách kiểm thử

1. **Tenant isolation test:** tạo hai tenant cùng `UserId`; mọi tổ hợp filter chỉ được trả rows thuộc tenant hiện tại.
2. **Injection test:** truyền `' OR 1=1 --` và các payload tương tự; query phải coi đó là dữ liệu, không phải SQL.
3. **Authorization test:** authenticated user thiếu `AuditReader` phải nhận 403; thiếu tenant context cũng bị từ chối.
4. **Sensitive-data test:** response không chứa token, raw request body hoặc fields ngoài DTO allowlist.
5. **Load/database test:** dataset lớn; kiểm tra execution plan, query duration, rows scanned/read và memory với page-size maximum.

## Quan sát trong production

Theo dõi request duration, result count, rejected authorization count, DB query duration/timeouts và search volume theo tenant nhưng không đưa sensitive filter text vào metrics. Trace API → EF/DB query. Alert khi query latency hoặc DB timeout tăng mạnh. Review execution plans/slow-query logs định kỳ và audit các cross-tenant access paths đặc quyền.

2. Khi audit search cần substring/full-text trên hàng trăm triệu rows, bạn thay đổi kiến trúc thế nào?
3. Nếu support team cần cross-tenant search, bạn thiết kế authorization và audit trail ra sao?
