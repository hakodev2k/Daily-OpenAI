# Code Review Challenge 1 — Service Bus consumer xử lý payment event “thành công” nhưng đôi lúc tạo receipt hai lần

**Chủ đề:** C#/.NET 8, Azure Service Bus, EF Core, at-least-once delivery, idempotency, message lock, retry, outbox/inbox, external side effects, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một order service nhận sự kiện `OrderPaid` từ Azure Service Bus. Khi nhận message, worker cần:

- xác nhận order tồn tại và chưa được xử lý;
- gọi receipt provider để tạo hóa đơn/receipt;
- cập nhật order thành `Paid` trong SQL Server;
- xử lý an toàn khi Service Bus redeliver message;
- chạy trên nhiều application instances;
- không tạo receipt trùng nếu process crash, network timeout hoặc message lock hết hạn;
- phân biệt lỗi transient với poison message;
- shutdown phải graceful;
- operations cần biết duplicate delivery, retry, lock loss, DLQ và latency của receipt provider.

Traffic thông thường thấp, nhưng giờ cao điểm có thể có hàng nghìn payment events trong vài phút. Receipt provider chỉ chịu được khoảng vài chục request đồng thời và đôi lúc timeout 20–40 giây.

Production gần đây xuất hiện:

- một số order có hai receipt khác nhau dù chỉ thanh toán một lần;
- có message được xử lý lại sau khi handler tưởng rằng đã hoàn tất;
- khi receipt provider chậm, queue backlog tăng và số delivery của một số message tăng;
- một vài malformed messages cứ bị retry nhiều lần;
- team đề xuất tăng `MaxConcurrentCalls` để “xử lý backlog nhanh hơn”.

## Đoạn code cần review

```csharp
public sealed class PaidOrderConsumer
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ReceiptClient _receiptClient;
    private readonly ILogger<PaidOrderConsumer> _logger;

    public PaidOrderConsumer(
        IDbContextFactory<AppDbContext> dbFactory,
        ReceiptClient receiptClient,
        ILogger<PaidOrderConsumer> logger)
    {
        _dbFactory = dbFactory;
        _receiptClient = receiptClient;
        _logger = logger;
    }

    public ServiceBusProcessor CreateProcessor(ServiceBusClient client)
    {
        var processor = client.CreateProcessor(
            "orders-paid",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 32,
                MaxAutoLockRenewalDuration = TimeSpan.Zero
            });

        processor.ProcessMessageAsync += HandleAsync;
        processor.ProcessErrorAsync += ErrorAsync;
        return processor;
    }

    private async Task HandleAsync(ProcessMessageEventArgs args)
    {
        try
        {
            var message = args.Message.Body.ToObjectFromJson<OrderPaid>();

            await using var db = await _dbFactory.CreateDbContextAsync();

            var order = await db.Orders
                .SingleAsync(x => x.Id == message.OrderId);

            if (order.Status == OrderStatus.Paid)
            {
                await args.CompleteMessageAsync(args.Message);
                return;
            }

            var receipt = await _receiptClient.CreateReceiptAsync(
                order.Id,
                order.TotalAmount);

            order.MarkPaid(receipt.Id, DateTime.UtcNow);
            await db.SaveChangesAsync();

            await args.CompleteMessageAsync(args.Message);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Failed to process message {MessageId}",
                args.Message.MessageId);

            await args.AbandonMessageAsync(args.Message);
        }
    }

    private Task ErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(
            args.Exception,
            "Service Bus processor error from {Source}",
            args.ErrorSource);

        return Task.CompletedTask;
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong message-processing flow.
2. Xác định các vấn đề concurrency, reliability, performance và maintainability.
3. Giải thích production impact, đặc biệt với duplicate delivery, crash window và dependency timeout.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà không giả định distributed transaction giữa SQL Server, Service Bus và receipt provider.
6. Giải thích testing cho duplicate delivery, lock loss, process crash, malformed message và dependency failure.
7. Đề xuất production telemetry để chứng minh consumer xử lý event an toàn.

## Câu hỏi gợi mở

1. Nếu receipt provider đã tạo receipt nhưng process crash trước `SaveChangesAsync`, lần delivery tiếp theo sẽ thấy trạng thái nào?
2. `order.Status == Paid` có phải idempotency guard đủ mạnh khi side effect bên ngoài xảy ra trước durable state change không?
3. Điều gì xảy ra nếu handler chạy lâu hơn message lock và auto lock renewal đã bị tắt?
4. `catch (Exception)` rồi `Abandon` mọi lỗi có phù hợp với malformed payload và permanent business error không?
5. Tăng `MaxConcurrentCalls` có giúp khi bottleneck thật sự nằm ở receipt provider hay có thể làm incident nặng hơn?

## Gợi ý

### Gợi ý 1

Primary risk là **failure window giữa external side effect và durable local state**. Một operation có thể thành công ở receipt provider nhưng application chưa ghi nhận thành công đó.

### Gợi ý 2

Reasoning theo at-least-once delivery: message có thể xuất hiện lại vì lock loss, process crash hoặc settlement failure. Hãy thiết kế sao cho retry không tạo side effect mới ngoài ý muốn.

## Kết quả code review tham khảo

### Critical — External side effect xảy ra trước durable idempotency state

**Vấn đề:**  
`CreateReceiptAsync` được gọi trước khi SQL Server lưu bất kỳ durable marker nào chứng minh event đã được xử lý.

**Tại sao xảy ra:**  
Receipt provider và SQL Server là hai transactional boundaries khác nhau. Nếu provider tạo receipt thành công nhưng process crash, network response bị mất hoặc `SaveChangesAsync` fail, retry sẽ không biết side effect đã xảy ra.

**Ảnh hưởng production:**  
Cùng một payment event có thể tạo nhiều receipt. Đây là correctness bug trực tiếp ở business workflow.

**Cách sửa:**  
Dùng stable business idempotency key như `MessageId`/payment event ID khi gọi provider nếu provider hỗ trợ idempotency. Đồng thời persist inbox/idempotency state trong SQL. Nếu external side effect không thể tham gia cùng transaction, tách flow bằng transactional outbox: consumer transaction chỉ ghi order/inbox/outbox, sau đó một dispatcher thực hiện receipt creation với stable idempotency key.

### Critical — Check `order.Status == Paid` không đóng failure window

**Vấn đề:**  
Code coi order status là duplicate guard nhưng status chỉ được set sau receipt call.

**Tại sao xảy ra:**  
Duplicate guard nằm sau side effect cần bảo vệ. Hai deliveries cạnh tranh hoặc một retry sau crash có thể cùng thấy `NotPaid`.

**Ảnh hưởng production:**  
Duplicate receipt vẫn có thể xảy ra dù code “check trước khi xử lý”.

**Cách sửa:**  
Dùng unique inbox/event key tại database boundary và transaction có concurrency guarantee phù hợp. Nếu nhiều workers có thể nhận logical duplicate events khác `MessageId` nhưng cùng payment ID, idempotency key cần dựa trên business event identity chứ không chỉ transport ID.

### High — Message lock có thể hết hạn trong handler dài

**Vấn đề:**  
`MaxAutoLockRenewalDuration = TimeSpan.Zero` trong khi receipt provider có thể timeout hàng chục giây và toàn handler còn query/save database.

**Tại sao xảy ra:**  
Peek-lock ownership có thời hạn. Handler dài hơn lock budget có thể mất quyền settle message.

**Ảnh hưởng production:**  
Message có thể được redeliver trong khi instance đầu tiên vẫn đang xử lý; `CompleteMessageAsync` có thể fail vì lock đã mất. Duplicate side effects và concurrent processing trở nên dễ xảy ra hơn.

**Cách sửa:**  
Cấu hình lock duration/auto-renewal phù hợp với measured processing time hoặc, tốt hơn, làm handler ngắn bằng cách persist work rồi tách external processing. Dù có auto-renewal, vẫn phải có idempotency vì lock renewal không loại bỏ mọi duplicate-delivery scenario.

### High — Không có explicit concurrency control ở database level

**Vấn đề:**  
Hai handlers có thể cùng load một order chưa paid, cùng gọi receipt provider rồi cùng save.

**Tại sao xảy ra:**  
`SingleAsync` + in-memory status check không serialize concurrent consumers. Không có concurrency token, unique processed-event constraint hoặc atomic claim.

**Ảnh hưởng production:**  
Concurrent duplicate deliveries có thể tạo side effect hai lần dù cả hai request đều “đúng” khi nhìn snapshot riêng.

**Cách sửa:**  
Dùng unique constraint cho inbox/event identity và transaction để chỉ một logical processing attempt được accepted. Nếu order row cần optimistic concurrency, dùng rowversion/concurrency token và xử lý conflict; nhưng concurrency token không tự giải quyết external side effect đã phát ra trước đó.

### High — Mọi exception đều bị `Abandon`, kể cả permanent poison message

**Vấn đề:**  
Malformed JSON, missing order, validation error và transient network timeout cùng đi qua một retry path.

**Tại sao xảy ra:**  
Failure classification bị collapse thành `catch (Exception)`.

**Ảnh hưởng production:**  
Poison message có thể tiêu tốn delivery attempts, tạo log noise và làm backlog chậm. Transient errors cũng không có backoff/budget rõ ràng ở application layer.

**Cách sửa:**  
Phân loại lỗi: malformed/invalid business payload → dead-letter với reason phù hợp; transient dependency failure → để retry theo policy/broker semantics; cancellation do shutdown → không biến thành permanent error. Tôn trọng max delivery/DLQ strategy thay vì retry vô hạn bằng code.

### High — Concurrency 32 có thể vượt capacity downstream

**Vấn đề:**  
`MaxConcurrentCalls = 32` được đặt cố định dù receipt provider chỉ chịu được một mức concurrency hữu hạn, và deployment còn có nhiều application instances.

**Tại sao xảy ra:**  
Effective concurrency là tổng trên tất cả processor instances, không chỉ một process.

**Ảnh hưởng production:**  
Scale-out có thể tạo dependency overload, timeout, retry amplification và backlog lớn hơn thay vì nhỏ hơn.

**Cách sửa:**  
Chọn concurrency từ capacity measurement và SLO của downstream; có thể thêm bounded concurrency/rate limiting ở integration boundary. Theo dõi queue age và dependency saturation trước khi tăng parallelism.

### Medium — Cancellation không được propagate

**Vấn đề:**  
`CreateDbContextAsync`, EF Core queries/save, receipt call và settlement không dùng cancellation token của processing context.

**Tại sao xảy ra:**  
Async method không tự nhận cancellation chỉ vì host đang shutdown.

**Ảnh hưởng production:**  
Deployment/shutdown có thể kéo dài; work tiếp tục sau khi process cần drain. Outcome trở nên khó đoán nếu host bị terminate giữa external side effect và local persistence.

**Cách sửa:**  
Propagate cancellation token được cung cấp bởi handler context tới operations hỗ trợ token. Tuy nhiên cancellation không phải rollback xuyên systems; idempotency vẫn là bắt buộc.

### Medium — Không kiểm tra schema/version và required fields của message

**Vấn đề:**  
Deserialized event được dùng ngay để query database.

**Tại sao xảy ra:**  
Transport payload được tin là luôn hợp lệ.

**Ảnh hưởng production:**  
Producer version drift hoặc malformed event có thể tạo exception/retry storm và khó phân biệt contract violation với infrastructure failure.

**Cách sửa:**  
Validate event version, identifiers và business-required fields trước processing; dead-letter unsupported/permanent invalid payload với diagnostic metadata không chứa dữ liệu nhạy cảm.

### Medium — Observability không cho biết message outcome

**Vấn đề:**  
Log chỉ có generic failure và processor error.

**Tại sao xảy ra:**  
Không có structured lifecycle telemetry cho receive → deduplicate → persist → dispatch → settle.

**Ảnh hưởng production:**  
Team khó chứng minh duplicate rate, lock-loss rate, retry reason hoặc provider saturation.

**Cách sửa:**  
Ghi metrics/traces cho delivery count, processing latency, duplicate/inbox hit, lock-lost/settlement failure, DLQ, queue age, provider latency/error và outbox age. Correlate bằng event/business ID thay vì log payload nhạy cảm.

### Low — `DateTime.UtcNow` làm business time và processing time bị trộn

**Vấn đề:**  
`Paid` timestamp được lấy tại thời điểm consumer xử lý thay vì từ event/domain contract nếu business cần thời điểm payment thực tế.

**Tại sao xảy ra:**  
Processing timestamp và event timestamp không được phân biệt.

**Ảnh hưởng production:**  
Audit/reporting có thể sai khi queue backlog hoặc retry kéo dài.

**Cách sửa:**  
Lưu riêng event occurred time và processing time nếu domain cần cả hai; không tin producer timestamp mù quáng nếu security/audit contract yêu cầu validation.

## Phiên bản đề xuất

Một thiết kế an toàn hơn là làm Service Bus handler ngắn và transactional trong SQL: ghi nhận inbox event, cập nhật order, tạo outbox command yêu cầu receipt. External receipt được thực hiện ở worker khác bằng stable idempotency key.

```csharp
public sealed class PaidOrderConsumer
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly ILogger<PaidOrderConsumer> _logger;

    public PaidOrderConsumer(
        IDbContextFactory<AppDbContext> dbFactory,
        ILogger<PaidOrderConsumer> logger)
    {
        _dbFactory = dbFactory;
        _logger = logger;
    }

    public async Task HandleAsync(ProcessMessageEventArgs args)
    {
        var ct = args.CancellationToken;
        OrderPaid message;

        try
        {
            message = args.Message.Body.ToObjectFromJson<OrderPaid>();
            Validate(message);
        }
        catch (Exception ex) when (ex is JsonException or InvalidMessageException)
        {
            await args.DeadLetterMessageAsync(
                args.Message,
                "InvalidPayload",
                ex.Message,
                ct);
            return;
        }

        await using var db = await _dbFactory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var eventId = message.EventId;

        var alreadyProcessed = await db.InboxMessages
            .AnyAsync(x => x.EventId == eventId, ct);

        if (!alreadyProcessed)
        {
            var order = await db.Orders
                .SingleAsync(x => x.Id == message.OrderId, ct);

            db.InboxMessages.Add(new InboxMessage
            {
                EventId = eventId,
                ReceivedAtUtc = DateTime.UtcNow
            });

            order.MarkPaid(message.PaidAtUtc);

            db.OutboxMessages.Add(new OutboxMessage
            {
                Id = Guid.NewGuid(),
                Type = "CreateReceipt",
                IdempotencyKey = $"receipt:{eventId}",
                Payload = JsonSerializer.Serialize(new
                {
                    message.OrderId,
                    message.Amount
                }),
                CreatedAtUtc = DateTime.UtcNow
            });

            try
            {
                await db.SaveChangesAsync(ct);
                await tx.CommitAsync(ct);
            }
            catch (DbUpdateException ex) when (IsInboxUniqueViolation(ex))
            {
                await tx.RollbackAsync(ct);
                _logger.LogInformation(
                    "Duplicate payment event {EventId} ignored",
                    eventId);
            }
        }
        else
        {
            await tx.RollbackAsync(ct);
        }

        await args.CompleteMessageAsync(args.Message, ct);
    }
}
```

`InboxMessages.EventId` phải có unique constraint. Check `AnyAsync` chỉ là fast path; unique constraint mới là correctness boundary khi hai consumers race.

Outbox dispatcher sau đó đọc `CreateReceipt` messages và gọi receipt provider bằng `IdempotencyKey`. Nếu provider hỗ trợ idempotency, cùng key phải trả lại cùng logical result thay vì tạo receipt mới. Dispatcher chỉ mark outbox completed sau khi đã có durable evidence về provider outcome.

Nếu provider không hỗ trợ idempotency, hệ thống không thể hứa exactly-once external side effect chỉ bằng retry logic. Khi đó cần xem lại integration contract, reconciliation process hoặc một business-level deduplication key phía provider.

## Giải thích thiết kế sau khi sửa

Thiết kế tách ba boundaries:

1. Service Bus delivery có thể lặp lại.
2. SQL transaction quyết định event nào đã được accept và tạo durable intent.
3. Receipt provider là external side-effect boundary riêng.

Inbox + unique constraint giúp duplicate delivery trở thành no-op ở local domain. Outbox đảm bảo order update và intent tạo receipt được commit cùng transaction. Stable idempotency key bảo vệ external side effect khi dispatcher retry sau timeout hoặc crash.

Điều này không biến toàn hệ thống thành exactly-once transport. Mục tiêu thực tế là **at-least-once delivery + idempotent processing + durable intent + reconciliation**.

## Trade-offs

- Inbox/outbox thêm tables, cleanup policy và dispatcher operational burden.
- Gọi provider trực tiếp đơn giản hơn và latency thấp hơn nhưng khó bảo vệ crash window xuyên systems.
- Auto lock renewal giảm lock-loss trong handler dài nhưng không thay thế idempotency.
- Giảm concurrency bảo vệ downstream nhưng có thể tăng queue age; phải cân bằng bằng đo đạc.
- Dead-letter sớm giúp cô lập poison work nhưng cần tooling/runbook để inspect và replay an toàn.

## Cách kiểm thử

1. **Duplicate/concurrency integration test:** gửi cùng `EventId` nhiều lần và xử lý song song; chỉ một inbox row, một logical order transition và một outbox intent được tạo.
2. **Crash-window test:** terminate dispatcher sau khi provider đã nhận request nhưng trước khi outbox được mark complete; retry phải dùng cùng idempotency key và không tạo receipt thứ hai.
3. **Lock-loss/failure-path test:** làm handler/processor vượt lock budget hoặc inject settlement failure; message có thể redeliver nhưng domain state vẫn đúng.
4. **Poison-message test:** malformed JSON/unsupported version phải đi DLQ theo policy thay vì retry nóng nhiều lần.
5. **Load test:** tăng queue depth với nhiều application instances, đo queue age, provider concurrency, timeout/retry rate và xác minh tăng `MaxConcurrentCalls` không vượt downstream capacity.

## Quan sát trong production

Theo dõi:

- active message count, oldest-message age và DLQ depth;
- delivery count distribution và duplicate/inbox-hit rate;
- handler p50/p95/p99 latency;
- lock-lost và settlement failure count;
- outbox pending age, dispatch retry và permanent-failure count;
- receipt provider concurrency, latency, timeout và error rate;
- SQL unique-conflict/concurrency metrics;
- trace correlation từ Service Bus message → SQL transaction → outbox → receipt provider;
- alert khi queue age, DLQ, duplicate side-effect evidence hoặc provider saturation vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu receipt provider không hỗ trợ idempotency key, bạn có thể đảm bảo điều gì và không thể đảm bảo điều gì?
2. Nếu ordering của nhiều events trên cùng order là bắt buộc, bạn sẽ cân nhắc Service Bus sessions hoặc domain sequencing thế nào?
3. Khi nào direct synchronous processing vẫn là lựa chọn hợp lý hơn inbox/outbox?

# Code Review Challenge 2 — Vue search hiển thị kết quả cũ sau kết quả mới và mở đường cho XSS qua highlighted HTML

**Chủ đề:** Vue 3, TypeScript, browser async behavior, API integration, request cancellation, race conditions, debounce, stale state, XSS, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một e-commerce frontend dùng Vue 3 + TypeScript để search sản phẩm khi user gõ. Backend trả về danh sách có `highlightedName` để UI tô đậm phần text khớp query.

Yêu cầu:

- search bắt đầu sau khi user gõ ít nhất 2 ký tự;
- không flood backend theo từng keystroke;
- kết quả trên màn hình phải tương ứng với query mới nhất;
- request cũ không được làm loading/error state của request mới bị sai;
- network chậm hoặc response đến không đúng thứ tự phải được xử lý an toàn;
- nội dung sản phẩm đến từ nhiều nguồn catalog bên ngoài và không được coi là trusted HTML;
- component cần hoạt động tốt khi user gõ nhanh, xóa query hoặc navigate khỏi page;
- operations muốn đo search latency, error rate và request amplification từ browser.

Production report:

- user gõ `iphone` rất nhanh nhưng đôi lúc UI cuối cùng hiển thị kết quả của `iph`;
- spinner có lúc biến mất dù request mới nhất vẫn đang chạy;
- một lỗi từ request cũ có thể hiện banner error sau khi request mới đã thành công;
- backend thấy nhiều request liên tiếp cho cùng một typing session;
- security review phát hiện catalog data có thể chứa markup từ nguồn không hoàn toàn tin cậy.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type SearchItem = {
  id: string
  url: string
  highlightedName: string
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

watch(query, async (value) => {
  if (!value) {
    results.value = []
    return
  }

  loading.value = true
  error.value = ''

  try {
    const response = await fetch(
      `/api/search?q=${encodeURIComponent(value)}`)

    const data = await response.json()
    results.value = data.items
  } catch {
    error.value = 'Search failed'
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in results" :key="item.id">
        <a :href="item.url">
          <span v-html="item.highlightedName"></span>
        </a>
      </li>
    </ul>
  </section>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong async search flow.
2. Xác định các vấn đề performance, security, reliability và maintainability.
3. Giải thích production impact khi user gõ nhanh, network response đến out-of-order hoặc backend trả nội dung không tin cậy.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa.
6. Giải thích testing cho race condition, cancellation, debounce, HTTP error và XSS.
7. Đề xuất production telemetry để chứng minh search UX hoạt động đúng.

## Câu hỏi gợi mở

1. Nếu request cho `iph` mất 800 ms nhưng request cho `iphone` chỉ mất 100 ms, response nào sẽ ghi `results` cuối cùng?
2. Một request cũ đi vào `finally` có thể thay đổi `loading` của request mới nhất như thế nào?
3. Component hiện tạo bao nhiêu request nếu user gõ 8 ký tự liên tục?
4. `fetch` có throw exception chỉ vì server trả HTTP 500 hay cần kiểm tra thêm gì?
5. `v-html` có trust boundary nào khi dữ liệu catalog đến từ nguồn bên ngoài?

## Gợi ý

### Gợi ý 1

Primary risk về correctness là **out-of-order completion**: thứ tự response về không nhất thiết giống thứ tự request được gửi.

### Gợi ý 2

Hãy tách hai vấn đề: kiểm soát lifecycle của asynchronous request và kiểm soát trust boundary khi render dữ liệu do server cung cấp.

## Kết quả code review tham khảo

### Critical — `v-html` render catalog markup không tin cậy

**Vấn đề:**  
`item.highlightedName` được inject trực tiếp vào DOM bằng `v-html`.

**Tại sao xảy ra:**  
Vue escaping bảo vệ text interpolation, nhưng `v-html` chủ động render chuỗi dưới dạng HTML. Scenario nói catalog data không phải trusted HTML.

**Ảnh hưởng production:**  
Nếu attacker hoặc compromised upstream đưa markup/script-capable payload vào field, UI có thể tạo XSS tùy browser/context/payload. XSS có thể dẫn tới account/session abuse và data exposure.

**Cách sửa:**  
Không dùng `v-html` cho untrusted content. Ưu tiên backend trả plain text + structured highlight ranges/tokens và render bằng Vue text interpolation. Nếu business bắt buộc nhận HTML, cần sanitization library/policy được review kỹ ở trust boundary; không tự viết sanitizer đơn giản bằng regex.

### High — Out-of-order responses có thể ghi đè kết quả mới bằng kết quả cũ

**Vấn đề:**  
Mỗi callback `watch` độc lập ghi `results.value` khi request của nó hoàn tất.

**Tại sao xảy ra:**  
Network latency không đảm bảo request gửi trước sẽ hoàn tất trước. Không có `AbortController`, sequence ID hoặc comparison với query hiện tại.

**Ảnh hưởng production:**  
User thấy stale/wrong search result, đặc biệt trên mobile network hoặc khi backend latency biến động.

**Cách sửa:**  
Cancel previous request khi query thay đổi và/hoặc dùng monotonically increasing request ID; chỉ latest request được phép commit state.

### High — `loading` bị race giữa nhiều requests

**Vấn đề:**  
Mọi request đều set `loading=false` trong `finally`.

**Tại sao xảy ra:**  
Một request cũ có thể hoàn tất trong lúc request mới vẫn pending.

**Ảnh hưởng production:**  
Spinner biến mất quá sớm; UX nói “đã xong” trong khi latest search chưa hoàn tất.

**Cách sửa:**  
Chỉ latest request được mutate shared loading/error/result state hoặc derive loading từ current request token/ID.

### High — Error cũ có thể overwrite success mới

**Vấn đề:**  
Một request lỗi set global `error` mà không biết nó còn là active request hay không.

**Tại sao xảy ra:**  
State ownership không gắn với request generation.

**Ảnh hưởng production:**  
UI có thể hiển thị “Search failed” dù kết quả mới nhất đã load thành công.

**Cách sửa:**  
Kiểm tra request ID trước khi update error; bỏ qua `AbortError` của request đã bị hủy; reset state chỉ từ latest interaction.

### High — Không debounce và không có minimum query length

**Vấn đề:**  
Watcher gọi API ngay trên mỗi thay đổi non-empty.

**Tại sao xảy ra:**  
Typing được map trực tiếp 1:1 thành network call.

**Ảnh hưởng production:**  
Browser tạo request amplification, backend/search dependency chịu QPS không cần thiết, tăng cost/latency và làm race condition thường xuyên hơn.

**Cách sửa:**  
Debounce khoảng thời gian được chọn theo UX measurement, yêu cầu tối thiểu 2 ký tự theo scenario và cancel request cũ. Không hard-code một con số “chuẩn” mà không đo latency/typing behavior.

### Medium — Không kiểm tra `response.ok`

**Vấn đề:**  
Code gọi `response.json()` ngay cả khi server trả 4xx/5xx.

**Tại sao xảy ra:**  
`fetch` chủ yếu reject cho network-level failures/cancellation; HTTP error status cần được kiểm tra explicit.

**Ảnh hưởng production:**  
Error response có thể bị parse như success hoặc phát sinh lỗi JSON không phản ánh đúng failure category.

**Cách sửa:**  
Kiểm tra `response.ok`; map expected statuses rõ ràng; validate shape của response trước khi gán state.

### Medium — Xóa query không hủy request đang chạy

**Vấn đề:**  
Khi query thành empty, code clear results nhưng request trước đó vẫn tồn tại.

**Tại sao xảy ra:**  
Không có lifecycle cancellation.

**Ảnh hưởng production:**  
Response cũ có thể quay về sau đó và repopulate results dù input trống; backend vẫn xử lý request user không còn cần.

**Cách sửa:**  
Abort active request ngay khi query thay đổi/xóa và invalidate request generation trước khi clear state.

### Medium — Không xử lý component unmount

**Vấn đề:**  
Active fetch/timer có thể tiếp tục sau khi user navigate khỏi component.

**Tại sao xảy ra:**  
Không cleanup debounce timer/AbortController trong lifecycle hook.

**Ảnh hưởng production:**  
Tạo network work không cần thiết và telemetry noise; trong component phức tạp còn có thể làm stale side effects.

**Cách sửa:**  
Dọn timer và abort current request trong `onBeforeUnmount`.

### Medium — `item.url` cần URL policy rõ ràng

**Vấn đề:**  
Href lấy trực tiếp từ API/catalog data.

**Tại sao xảy ra:**  
Data source bên ngoài có thể cung cấp scheme/domain không mong muốn.

**Ảnh hưởng production:**  
Có thể dẫn user tới external/malicious URL hoặc unsafe navigation nếu backend contract không constrain field.

**Cách sửa:**  
Tốt nhất API trả product identifier/route data và client xây internal route. Nếu phải nhận URL, validate allowed scheme/origin tại trusted boundary.

### Low — Không có telemetry cho search interaction lifecycle

**Vấn đề:**  
Frontend không đo query-to-result latency, aborted requests hoặc requests per typing interaction.

**Tại sao xảy ra:**  
Chỉ nhìn backend latency sẽ bỏ mất client-side race/amplification.

**Ảnh hưởng production:**  
Khó chứng minh debounce/cancellation cải thiện UX hay xác định browser/network segment nào gặp stale behavior.

**Cách sửa:**  
Thu thập privacy-safe metrics cho request count, abort count, success/error, query length bucket, latency và stale-response suppression; tránh log raw search text nếu có thể chứa dữ liệu nhạy cảm.

## Phiên bản đề xuất

Ví dụ dưới đây dùng debounce, `AbortController` và request generation. API trả plain text `name` thay vì HTML để UI render an toàn.

```vue
<script setup lang="ts">
import { onBeforeUnmount, ref, watch } from 'vue'

type SearchItem = {
  id: string
  route: string
  name: string
}

type SearchResponse = {
  items: SearchItem[]
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')

let debounceTimer: ReturnType<typeof setTimeout> | undefined
let activeController: AbortController | undefined
let generation = 0

watch(query, (rawValue) => {
  const value = rawValue.trim()
  const currentGeneration = ++generation

  if (debounceTimer)
    clearTimeout(debounceTimer)

  activeController?.abort()
  activeController = undefined

  if (value.length < 2) {
    results.value = []
    loading.value = false
    error.value = ''
    return
  }

  debounceTimer = setTimeout(async () => {
    const controller = new AbortController()
    activeController = controller

    if (currentGeneration !== generation)
      return

    loading.value = true
    error.value = ''

    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(value)}`,
        { signal: controller.signal })

      if (!response.ok)
        throw new Error(`Search returned HTTP ${response.status}`)

      const data = await response.json() as SearchResponse

      if (currentGeneration === generation)
        results.value = data.items
    } catch (err) {
      if (
        currentGeneration === generation &&
        !(err instanceof DOMException && err.name === 'AbortError')
      ) {
        error.value = 'Search failed'
      }
    } finally {
      if (currentGeneration === generation)
        loading.value = false
    }
  }, 250)
})

onBeforeUnmount(() => {
  if (debounceTimer)
    clearTimeout(debounceTimer)

  activeController?.abort()
})
</script>

<template>
  <section>
    <input
      v-model="query"
      placeholder="Search products"
      autocomplete="off"
    />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in results" :key="item.id">
        <RouterLink :to="item.route">
          <span>{{ item.name }}</span>
        </RouterLink>
      </li>
    </ul>
  </section>
</template>
```

Nếu UI thực sự cần highlight substring, API có thể trả `name` cùng danh sách highlight ranges/tokens. Component render các segment bằng text nodes/components thay vì HTML string. Điều này giữ presentation capability mà không mở trust boundary rộng như `v-html`.

## Giải thích thiết kế sau khi sửa

Thiết kế mới coi mỗi search attempt là một generation. Query mới invalidate generation cũ ngay lập tức. `AbortController` giảm work không còn cần thiết, còn generation check vẫn bảo vệ correctness kể cả khi cancellation đến muộn hoặc transport không hủy ngay được.

Debounce giảm request amplification nhưng không phải correctness mechanism; request identity/cancellation mới xử lý out-of-order response. Hai concerns cần được giữ riêng.

Plain-text rendering đưa XSS protection về default escaping behavior của Vue. Nếu backend muốn hỗ trợ highlighting, contract nên truyền structure thay vì raw executable markup.

## Trade-offs

- Debounce giảm QPS nhưng thêm một chút perceived latency trước request đầu tiên.
- Abort giảm work thừa nhưng không đảm bảo server đã dừng xử lý nếu request đã tới backend.
- Sequence/generation check thêm state nhưng làm ownership của UI state rõ ràng.
- Structured highlights phức tạp hơn `v-html` nhưng có trust boundary an toàn hơn.
- Client-side telemetry hữu ích nhưng phải tránh thu thập raw query không cần thiết.

## Cách kiểm thử

1. **Race-condition test:** mock request `iph` trả sau `iphone`; UI cuối cùng chỉ được hiển thị kết quả của query mới nhất và loading state không bị request cũ thay đổi.
2. **Debounce/request-count test:** simulate typing nhanh nhiều ký tự; xác minh số network requests giảm đúng policy và query dưới 2 ký tự không gọi API.
3. **Cancellation/navigation test:** đổi query/xóa input/unmount component khi request đang pending; old request bị abort hoặc ít nhất không thể commit state.
4. **HTTP failure test:** 500, invalid JSON và network timeout phải tạo error state đúng cho latest request; aborted request không hiển thị error giả.
5. **Security test:** product name chứa payload như `<img onerror=...>` phải hiển thị dưới dạng text hoặc structured safe output, không tạo executable DOM; URL/route contract cũng được validate.

## Quan sát trong production

Theo dõi:

- searches initiated per user interaction/session bucket;
- requests sent, aborted, succeeded và failed;
- query-to-result p50/p95 latency;
- backend search QPS và dependency latency;
- stale-response suppression count nếu instrument được;
- HTTP status categories và network-failure rate theo browser/device/network class;
- frontend error traces correlated với backend request IDs;
- alert khi request-per-search tăng bất thường hoặc search error/latency vượt baseline.

Không log raw query theo mặc định nếu không có mục đích rõ ràng và privacy policy phù hợp.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- At-least-once message delivery phải được thiết kế cùng idempotency; `check state rồi xử lý` không tự động tạo exactly-once behavior.
- External side effects cần stable idempotency key hoặc durable workflow như inbox/outbox để chịu được crash/retry windows.
- Concurrency phải được giới hạn theo capacity end-to-end, không chỉ theo khả năng tạo thêm tasks/consumers.
- Browser async requests có thể hoàn tất out-of-order; UI state cần ownership theo latest request/generation.
- Default text escaping an toàn hơn render raw HTML; `v-html` phải được coi là explicit trust boundary.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng idempotency, không thêm retry trước rồi mới nghĩ về duplicate side effects.
- Vẽ failure windows giữa các durable/external boundaries để tìm nơi state có thể lệch.
- Giới hạn concurrency theo downstream capacity và đo queue age/latency trước khi tăng parallelism.
- Với UI async, tách request cancellation khỏi quyền được commit shared state.
- Ưu tiên safe-by-default rendering thay vì truyền raw HTML qua nhiều trust boundaries.
