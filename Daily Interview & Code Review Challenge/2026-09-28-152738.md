# Câu 1 — React search hiển thị kết quả cũ dù request mới đã hoàn thành

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** React.js, TypeScript, JavaScript event loop, Promise, request cancellation, state correctness, HTTP, observability

## Bối cảnh

Một portal nội bộ dùng React + TypeScript gọi ASP.NET Core search API. Khi người dùng gõ nhanh vào ô tìm kiếm, UI đôi lúc hiển thị kết quả của từ khóa cũ. Backend trace cho thấy từng request đều trả đúng dữ liệu cho query của nó và không có HTTP error.

Code rút gọn:

```tsx
function EmployeeSearch() {
  const [query, setQuery] = useState("");
  const [items, setItems] = useState<Employee[]>([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!query.trim()) {
      setItems([]);
      return;
    }

    setLoading(true);

    fetch(`/api/employees?q=${encodeURIComponent(query)}`)
      .then(r => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then(data => setItems(data))
      .finally(() => setLoading(false));
  }, [query]);

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {loading && <span>Loading...</span>}
      <EmployeeList items={items} />
    </>
  );
}
```

Production latency thay đổi theo query và cache state: một request cũ có thể mất 800 ms trong khi request mới chỉ mất 120 ms. Chưa rõ application có React Strict Mode trong development hay không, có debounce hay không, backend có hỗ trợ cancellation đầy đủ hay không, và UX mong muốn search-on-type hay chỉ search sau khi submit.

## Câu hỏi chính

Hãy giải thích vì sao code trên có thể commit stale result dù mỗi HTTP response đều đúng; Promise continuation, effect lifecycle và completion order liên quan thế nào; assumption nào sai khi cho rằng “request được gửi trước sẽ hoàn thành trước”; và bạn sẽ sửa cũng như xác minh behavior này ra sao mà không chỉ tăng debounce delay?

## Câu hỏi làm rõ nên cân nhắc

1. UX yêu cầu mọi keystroke tạo search hay có debounce/minimum query length?
2. Có cần giữ kết quả cũ trong lúc query mới đang tải không?
3. Backend có propagate client disconnect/cancellation tới database hoặc downstream dependency không?
4. Lỗi chỉ xảy ra production hay có thể tái tạo bằng artificial latency?
5. Có request nào được tạo ngoài effect này, ví dụ prefetch hoặc state manager?

## Gợi ý tư duy

### Gợi ý 1

Thứ tự bắt đầu asynchronous operation không tạo guarantee về thứ tự hoàn thành.

### Gợi ý 2

Mỗi lần effect chạy tạo một closure riêng. Hãy xem closure nào còn quyền cập nhật shared component state sau khi dependency thay đổi.

### Gợi ý 3

Tách hai mục tiêu: ngăn stale commit ở UI và giảm work không còn cần thiết bằng cancellation. Chúng liên quan nhưng không hoàn toàn đồng nghĩa.

## Cấu trúc trả lời đề xuất

1. Xác nhận UX/search semantics.
2. Vẽ timeline cho query A và query AB.
3. Giải thích effect cleanup, Promise completion và state update.
4. Xác định invariant: chỉ request tương ứng query hiện hành được commit.
5. Chọn AbortController hoặc request identity/version guard.
6. Xử lý loading/error theo cùng identity.
7. Kiểm thử reordered responses.
8. Quan sát request duration/cancellation trong browser và backend.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hai `fetch` độc lập có thể hoàn thành khác thứ tự bắt đầu; network/backend latency không đảm bảo FIFO.
- Closure của effect cũ vẫn có thể chạy Promise continuation và gọi `setItems` sau khi query đã đổi nếu không cleanup/guard.
- Đây là race về logical ordering, không cần multi-threaded JavaScript để xảy ra.
- Debounce chỉ giảm số request; nó không chứng minh request cũ không thể hoàn thành sau request mới.
- UI phải có invariant rõ ràng để stale request không commit state.
- Cancellation nên được coi là resource optimization và lifecycle control; correctness vẫn nên không phụ thuộc vào giả định cancellation luôn ngăn được response.
- `loading` cũng có race: `finally` của request cũ có thể đặt false trong khi request mới còn chạy.

### Điểm cộng

- Dùng `AbortController` trong cleanup và bỏ qua `AbortError`.
- Hoặc dùng monotonically increasing request ID/query identity để chỉ latest request được phép commit.
- Kết hợp debounce nếu UX phù hợp, nhưng tách debounce khỏi correctness.
- Propagate cancellation ở ASP.NET Core qua `RequestAborted`/action `CancellationToken` tới I/O hỗ trợ token.
- Dùng browser Network panel và server correlation/tracing để chứng minh completion order.

### Senior+

- Nhận ra “abort” không phải distributed rollback: server/downstream có thể đã nhận hoặc hoàn thành work.
- Thiết kế state machine cho idle/loading/success/error theo request identity thay vì nhiều boolean dễ race.
- Nếu dùng data-fetching library, vẫn phải hiểu stale/cache/request-key semantics thay vì coi library là magic fix.
- Test bằng deterministic deferred promises thay vì dựa vào timing ngẫu nhiên.

## Hướng giải quyết tham khảo

Khi `query` đổi từ `a` sang `ab`, effect thứ nhất đã khởi động request A. React chạy effect mới và khởi động request B. JavaScript không block chờ A; Promise continuation của từng request được schedule khi operation tương ứng hoàn thành. Nếu B trả sau 120 ms, nó gọi `setItems(resultB)`. Nếu A trả sau 800 ms, continuation của A vẫn tồn tại và sau đó gọi `setItems(resultA)`, ghi đè state bằng dữ liệu cũ.

Cách sửa phù hợp là gắn lifetime của request với effect. Ví dụ:

```tsx
useEffect(() => {
  const normalized = query.trim();

  if (!normalized) {
    setItems([]);
    setLoading(false);
    return;
  }

  const controller = new AbortController();
  let active = true;

  setLoading(true);

  async function load() {
    try {
      const response = await fetch(
        `/api/employees?q=${encodeURIComponent(normalized)}`,
        { signal: controller.signal });

      if (!response.ok)
        throw new Error(`HTTP ${response.status}`);

      const data: Employee[] = await response.json();

      if (active)
        setItems(data);
    } catch (error) {
      if (error instanceof DOMException && error.name === "AbortError")
        return;

      if (active) {
        // map to the application's error state
      }
    } finally {
      if (active)
        setLoading(false);
    }
  }

  void load();

  return () => {
    active = false;
    controller.abort();
  };
}, [query]);
```

`active` bảo vệ state correctness; `AbortController` yêu cầu browser dừng operation khi có thể. Với flow phức tạp hơn, request sequence ID thường rõ hơn. Debounce có thể thêm để giảm traffic nhưng không thay thế guard.

Phía backend, nếu search chỉ đọc dữ liệu, action nên nhận cancellation token và truyền xuống EF Core/downstream I/O. Tuy nhiên client không được giả định abort nghĩa là server chắc chắn chưa thực thi; cancellation là cooperative.

Để verify, tôi sẽ viết test tạo hai deferred responses: A bắt đầu trước, B bắt đầu sau; resolve B trước rồi A sau và assert UI vẫn là B, loading state đúng. Sau đó kiểm tra browser waterfall và Application Insights để xem canceled request có giảm downstream work hay không.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không giả định request order bằng response order. Khi query đổi, effect cũ đã tạo một asynchronous operation có closure riêng. Request mới có thể hoàn thành trước, cập nhật đúng state, rồi request cũ hoàn thành sau và overwrite bằng stale data. Debounce chỉ giảm xác suất và traffic chứ không tạo correctness guarantee. Tôi sẽ gắn request vào effect lifecycle bằng AbortController và thêm active/request-id guard để chỉ latest request được commit; loading/error cũng phải theo cùng identity. Backend sẽ nhận cancellation token để giảm work thừa, nhưng tôi không coi cancellation là rollback guarantee. Tôi sẽ verify bằng test cố ý resolve responses ngược thứ tự, rồi xem browser network và server traces để xác nhận cả correctness lẫn resource behavior.”

## Câu hỏi đào sâu

1. Nếu `abort()` được gọi sau khi server đã chạy SQL query, điều gì có thể vẫn xảy ra?
2. Nếu product muốn giữ kết quả cũ trong lúc query mới tải, bạn sẽ model state thế nào để tránh flicker mà vẫn không stale?
3. Một teammate đề xuất chỉ debounce 500 ms và bỏ cancellation/identity guard; bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Cho rằng JavaScript single-threaded nghĩa là không có race condition.
- Chỉ thêm debounce và coi vấn đề đã được chứng minh hết.
- Chỉ abort request nhưng không nghĩ tới stale state/loading/error semantics.
- Không test reordered completion.
- Đổ lỗi backend dù response của từng query đã được xác nhận đúng.

## Thang điểm 0–10

- **0–2:** Không nhận ra stale-response race.
- **3–4:** Nhận ra race nhưng chỉ đề xuất debounce hoặc workaround timing.
- **5–6:** Giải thích đúng completion order và có cleanup/guard hợp lý.
- **7–8:** Bao quát loading/error, cancellation propagation, deterministic testing và telemetry.
- **9–10:** Phân biệt correctness với resource cancellation, trình bày state invariant rõ ràng và thảo luận trade-off UX/backend sâu.

# Câu 2 — Search index trả dữ liệu cũ sau release và queue đồng bộ tăng liên tục

**Loại câu hỏi:** Production Incident / Troubleshooting  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Elasticsearch, SQL Server, Azure Service Bus, distributed systems, eventual consistency, incident response, observability, idempotency

## Bối cảnh

Một e-commerce platform lưu product/catalog authority trong SQL Server và phục vụ product search từ Elasticsearch. Khi product được publish, application commit SQL rồi gửi message để một indexing worker cập nhật Elasticsearch.

Sau một release, khoảng 6% sản phẩm vừa chỉnh sửa vẫn hiển thị title/price cũ trong search 20–60 phút, trong khi product detail page đọc SQL và hiển thị đúng. Azure Service Bus active message count tăng nhanh, một số message vào DLQ, worker CPU chỉ khoảng 35%. Restart worker làm throughput tăng tạm thời rồi giảm lại.

Business đang chạy campaign nên stale price có tác động trực tiếp. Chưa rõ producer publish message trước hay sau DB commit, message có version hay không, retry policy thế nào, DLQ reason là gì, Elasticsearch bulk response có được kiểm tra từng item hay không, hay deployment có thay đổi mapping/index alias.

## Câu hỏi chính

Bạn là engineer on-call. Hãy trình bày cách ổn định incident, thu thập evidence và phân biệt các giả thuyết producer/message/consumer/Elasticsearch; xác định vì sao “restart worker” chưa phải root-cause fix; và đề xuất remediation giúp synchronization chịu được retry, duplicate, out-of-order message và partial indexing failure.

## Câu hỏi làm rõ nên cân nhắc

1. Stale product có correlation với một message type, partition/session, tenant hoặc release version không?
2. Active count, oldest message age, DLQ count/reason, delivery count và processing duration thay đổi thế nào?
3. Consumer complete message ở thời điểm nào so với việc kiểm tra Elasticsearch bulk item result?
4. Message mang full document, product ID hay product version/updated timestamp?
5. Mapping/alias/index target có thay đổi trong release và detail/search có đang đọc cùng product version logic không?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu bằng business impact và queue age, không bắt đầu bằng việc “tune Elasticsearch”.

### Gợi ý 2

Một HTTP/bulk request thành công ở transport level chưa nhất thiết chứng minh mọi document item đã index thành công.

### Gợi ý 3

Khi transport có at-least-once delivery, consumer phải có strategy cho duplicate và ordering; đồng bộ search cũng cần cách reconcile missed updates.

## Cấu trúc trả lời đề xuất

1. Xác định impact/SLO và phạm vi stale data.
2. Stabilize: giảm blast radius, bảo toàn message, xử lý campaign-sensitive data.
3. Thu thập Service Bus, worker và Elasticsearch telemetry.
4. Correlate product ID/version xuyên producer → message → consumer → index.
5. Kiểm tra DLQ và partial bulk failures.
6. Xác minh ordering/idempotency assumptions.
7. Remediate consumer/protocol.
8. Reconcile/reindex dữ liệu đã lệch.
9. Canary rollout và theo dõi freshness lag.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Detail page đúng nhưng search sai gợi ý synchronization/index path, nhưng chưa đủ để kết luận chính xác component lỗi.
- Queue growth cần xem arrival rate vs completion rate, oldest message age, delivery count, lock/retry/DLQ và dependency latency.
- Không xóa/purge message để “giảm queue” nếu chưa hiểu impact.
- Restart chỉ thay đổi process state/capacity tạm thời; cần evidence vì sao throughput suy giảm.
- Consumer phải xử lý duplicate vì delivery/retry có thể xảy ra nhiều lần.
- Out-of-order update có thể làm version cũ overwrite version mới nếu document update không có ordering/version guard.
- Bulk indexing phải kiểm tra item-level failures và chỉ settle message khi outcome đã được xử lý đúng.
- Cần reconciliation path để phát hiện/sửa dữ liệu SQL và search index bị drift.

### Điểm cộng

- Dùng correlation fields như product ID, event ID, source version, trace ID.
- Với message chỉ chứa ID, consumer có thể đọc current authoritative state để giảm out-of-order payload overwrite, đổi lại tăng DB load/coupling.
- Với versioned event, index/update logic có thể reject stale version.
- DLQ phải có alert, triage và controlled replay sau khi root cause được sửa.
- Theo dõi freshness lag từ source update timestamp tới searchable version.

### Senior+

- Nhận ra dual-write SQL + message có failure window; đánh giá transactional Outbox nếu business cần reliable publication.
- Tách transport retry khỏi application retry để tránh retry amplification.
- Thiết kế poison-message handling không block toàn bộ flow.
- Nếu price correctness cực nhạy, xem xét liệu search response có nên là authority cho checkout/pricing hay checkout phải revalidate từ authoritative pricing source.
- Reindex strategy phải cân nhắc alias swap, load và rollback thay vì update mù production index.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định mức ảnh hưởng: product nào stale, campaign/checkout có dùng search price như authority không, freshness SLO là bao nhiêu. Nếu checkout vẫn revalidate price từ authoritative source thì customer-facing risk khác với trường hợp search price được dùng để charge. Tôi sẽ bảo toàn queue/DLQ và tránh purge.

Sau đó tôi so arrival/completion rate và oldest message age. Application Insights/Kibana cần cho thấy processing duration theo stage: receive, source read nếu có, transform, Elasticsearch call, settle. Service Bus metrics cho active/dead-letter count và worker logs phải có message/event/product/version correlation.

Tôi lấy vài stale product và trace end-to-end. Các giả thuyết gồm: producer không publish sau commit; publish thất bại ở dual-write window; consumer retry/lock/settlement sai; poison message; bulk response có partial failures nhưng code complete message; mapping rejection; index alias trỏ sai; version cũ đến sau version mới; hoặc dependency throttling.

Nếu producer hiện commit SQL rồi gửi message trực tiếp, crash giữa hai bước có thể tạo missed event. Transactional Outbox là một lựa chọn nếu reliability requirement biện minh complexity: business change và outbox row commit cùng local DB transaction; dispatcher publish với retry; consumer vẫn idempotent vì duplicate vẫn có thể xảy ra.

Consumer nên xử lý message theo event ID/version. Nếu event chứa snapshot, chỉ apply khi source version không cũ hơn indexed version. Nếu event chỉ chứa product ID, consumer có thể load current source state và index latest state; trade-off là tăng source DB traffic. Elasticsearch bulk operation phải inspect từng item; successful items và failed items cần outcome rõ, không complete toàn batch chỉ vì HTTP request thành công.

Sau khi fix, cần reconciliation: compare source version/update timestamp với indexed metadata hoặc replay/reindex theo controlled batch. Nếu mapping migration liên quan, tạo index mới, validate, rồi alias switch có rollback plan thường an toàn hơn sửa ad-hoc.

Telemetry lâu dài gồm queue age, processing throughput, DLQ rate, retry rate, indexing error by reason, Elasticsearch latency/rejection, và product freshness lag. Alert nên dựa cả lag chứ không chỉ queue count.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là data-freshness incident, chưa kết luận Elasticsearch là root cause. Trước hết tôi xác định business impact và đảm bảo checkout/pricing authority không dựa mù vào stale search result. Tôi giữ nguyên queue/DLQ, đo arrival versus completion rate, oldest message age, delivery count và trace một số product từ SQL commit qua event tới indexed version. Tôi sẽ đặc biệt kiểm tra bulk item failures, settlement timing và out-of-order versions. Restart worker chỉ là mitigation nếu process state bị kẹt; nó không giải thích vì sao throughput lại giảm. Về thiết kế, producer có thể cần Outbox nếu dual-write window là nguyên nhân; consumer phải idempotent, có version guard hoặc đọc current source state, xử lý partial failures và DLQ có kiểm soát. Cuối cùng tôi chạy reconciliation/reindex cho drift đã tồn tại và alert trên freshness lag.”

## Câu hỏi đào sâu

1. Nếu message chứa toàn bộ product snapshot, bạn chống event cũ overwrite event mới như thế nào?
2. Nếu chuyển sang consumer đọc current SQL state cho mỗi message, trade-off và failure mode mới là gì?
3. Một architect đề xuất bỏ Service Bus và gọi Elasticsearch đồng bộ trong request publish để có “strong consistency”; bạn đánh giá thế nào?

## Lỗi trả lời thường gặp

- Restart worker rồi coi incident đã giải quyết.
- Chỉ nhìn CPU và kết luận worker còn capacity.
- Purge DLQ/queue để giảm metric.
- Giả định message chỉ được giao một lần.
- Không có reconciliation cho missed/failed indexing.

## Thang điểm 0–10

- **0–2:** Nhảy thẳng tới restart/reindex không điều tra.
- **3–4:** Có xem queue/log nhưng thiếu ordering/idempotency/partial failure.
- **5–6:** Điều tra có cấu trúc và xác định được các failure boundary chính.
- **7–8:** Bao quát versioning, DLQ, reconciliation, telemetry và rollout.
- **9–10:** Kết nối dual-write/Outbox, retry amplification, authority boundary và operational trade-offs một cách có điều kiện.

# Câu 3 — Thiết kế publishing cho Optimizely CMS, Akamai CDN và các dependency commerce

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, Akamai/CDN, caching, composable commerce, failure isolation, SEO, observability, architecture trade-offs

## Bối cảnh

Một marketing/e-commerce website dùng Optimizely CMS cho editorial content và page composition. Product name/price/availability đến từ commerce APIs; ratings từ review provider; authentication từ external identity provider. Website phục vụ nhiều quốc gia và traffic có spike lớn khi campaign bắt đầu.

Hiện page request từ browser đi qua Akamai tới ASP.NET Core origin. Team muốn cải thiện Core Web Vitals và giảm origin load bằng edge caching. Tuy nhiên editors yêu cầu publish content thấy “gần như ngay lập tức”; Product yêu cầu giá không được stale quá mức cho phép; SEO team cần canonical URL/redirect/status code chính xác. Một architect đề xuất cache toàn bộ HTML 24 giờ ở CDN và purge toàn site sau mỗi CMS publish. Người khác muốn bỏ CDN cache cho mọi dynamic page để tránh stale data.

Chưa có con số chính thức cho freshness SLA theo loại dữ liệu, tỷ lệ anonymous/authenticated traffic, personalization, purge capability/latency, hay việc price trong listing có phải transactional authority không.

## Câu hỏi chính

Hãy thiết kế cache/content-delivery strategy cho hệ thống này. Bạn sẽ phân loại dữ liệu và page theo freshness/identity thế nào; phối hợp browser/CDN/origin cache và invalidation ra sao; xử lý dependency degradation thế nào; và vì sao cả “cache 24h + purge toàn site” lẫn “không cache dynamic page” đều có thể là quyết định quá đơn giản?

## Câu hỏi làm rõ nên cân nhắc

1. Freshness SLA riêng cho editorial content, product description, price, inventory và review là bao nhiêu?
2. Tỷ lệ anonymous traffic và mức personalization thực tế là gì?
3. Publish event có biết chính xác content/page dependency nào bị ảnh hưởng không?
4. Akamai configuration hiện hỗ trợ purge/invalidation theo URL/tag/key nào và operational limits cần xác minh ra sao?
5. Checkout có revalidate price/inventory từ authoritative commerce service không?

## Gợi ý tư duy

### Gợi ý 1

“Page” không phải một consistency unit duy nhất. Các fragment/data source có authority và freshness requirement khác nhau.

### Gợi ý 2

Cache key và invalidation correctness quan trọng ngang TTL. Hãy nghĩ tới host, locale, route, query, authentication/personalization và content dependency.

### Gợi ý 3

Thiết kế failure mode trước: nếu review API hoặc commerce API chậm, toàn page có nhất thiết phải fail không?

## Cấu trúc trả lời đề xuất

1. Phân loại content/data theo authority và freshness.
2. Xác định anonymous/personalized boundaries.
3. Chọn cache layer và cache key cho từng class.
4. Thiết kế publish-driven invalidation + bounded TTL.
5. Thiết kế dependency timeout/fallback.
6. Bảo vệ transactional correctness ở checkout.
7. Bao quát SEO/status/redirect semantics.
8. Định nghĩa telemetry và freshness SLO.
9. Rollout từng bước với canary/cache metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không dùng một TTL cho mọi loại dữ liệu.
- Editorial content, ratings, product catalog, price và inventory có freshness/authority khác nhau.
- CDN cache phù hợp nhất với response có thể chia sẻ an toàn; authenticated/personalized content cần cache policy/key khác hoặc bypass.
- Purge toàn site sau mỗi publish có thể gây cache-miss storm/origin spike và xóa nhiều object không liên quan.
- Không cache gì làm mất lợi ích edge cho anonymous read-heavy traffic và tăng dependency/origin coupling.
- Checkout/order boundary phải revalidate transactional data theo business requirement; CDN-rendered price không nên mặc nhiên là charging authority.
- Cache-Control/status/redirect/canonical behavior phải được thiết kế cùng SEO, không chỉ performance.
- External dependency phải có timeout, bounded retry khi phù hợp và graceful degradation theo criticality.

### Điểm cộng

- Dùng publish event/content dependency graph để invalidate targeted URLs/keys khi khả thi, cộng TTL như safety bound.
- Có stale-while-revalidate/stale fallback chỉ khi freshness semantics cho phép và CDN behavior đã được xác minh.
- Reviews có thể degrade thành “temporarily unavailable”; identity provider failure ảnh hưởng login nhưng không nhất thiết phá anonymous content.
- Cache key phải tránh cross-locale/cross-user data leak.
- Theo dõi CDN hit ratio, origin requests, purge latency, freshness lag và dependency latency.

### Senior+

- Tách shell/content và volatile commerce data khi UX/architecture biện minh, nhưng cân nhắc SEO/rendering complexity.
- Chống cache stampede khi campaign/purge tạo simultaneous misses.
- Thiết kế origin protection/backpressure và capacity cho worst-case cold cache.
- Không phụ thuộc vào vendor-specific purge guarantee nếu chưa xác minh current contract/configuration.
- Đánh giá complexity của fragment caching/edge-side composition so với lợi ích đo được.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng data classification thay vì chọn TTL. Ví dụ editorial hero copy có thể chấp nhận freshness vài phút tùy business; ratings thường có thể stale lâu hơn; price/inventory có thể yêu cầu ngắn hơn nhiều và checkout phải revalidate. Các con số cụ thể phải được Product xác nhận.

Với anonymous pages có representation giống nhau theo host/locale/path, CDN caching có giá trị lớn. Cache key phải bao gồm các dimension thực sự thay đổi response và loại bỏ dimension không cần thiết để tránh fragmentation. Authenticated/personalized response không được chia sẻ ở edge nếu key/policy không chứng minh isolation; thường bypass hoặc tách personalized data call.

CMS publish nên tạo invalidation có mục tiêu. Nếu một block được dùng trên 20 pages, dependency graph hoặc publish handler cần biết các URLs bị ảnh hưởng. Targeted purge giảm blast radius. TTL vẫn là safety net nếu event/purge thất bại. Tôi không mặc định một feature như cache tags hay stale directives hoạt động giống nhau trên mọi Akamai configuration; team cần verify current property/configuration và contract.

Commerce data cần quyết định rendering boundary. Nếu SEO cần server-rendered product content nhưng price biến động nhanh, có thể cache page shell/catalog content ngắn và fetch/revalidate volatile fields theo policy phù hợp. Tuy nhiên split rendering tăng complexity, hydration/API calls và có thể ảnh hưởng UX/SEO; chỉ dùng khi evidence cho thấy đáng giá.

Dependency degradation phải theo criticality. Review provider timeout có thể trả page không có rating thay vì 500. Commerce catalog failure có thể dùng bounded stale snapshot nếu business cho phép; inventory/checkout phải fail safely hoặc revalidate authoritative source. Retry phải bounded với timeout/backoff và tránh nhân tải khi dependency đang lỗi.

SEO semantics không được cache sai: redirects/status codes/canonical/locale variants cần policy rõ và purge khi route thay đổi. Một cached 200 cho URL đã chuyển sang 301 có thể kéo dài crawl inconsistency nếu invalidation không đúng.

Tôi rollout bằng nhóm route/country nhỏ, đo edge hit ratio, origin RPS, p95/p99, Core Web Vitals, purge-to-visible latency, stale-content incidents và dependency error rate. Đồng thời load-test cold-cache scenario vì purge hoặc CDN issue có thể đẩy traffic đột ngột về origin.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không chọn một TTL cho cả page. Trước hết tôi phân loại editorial content, catalog, ratings, price và inventory theo authority và freshness SLA. Anonymous shared HTML có thể cache ở Akamai với key theo locale/route và invalidation có mục tiêu khi CMS publish; TTL là safety bound. Tôi tránh purge toàn site vì có thể tạo cold-cache storm. Personalized response phải bypass hoặc có isolation được chứng minh. Với commerce data biến động nhanh, tôi cân nhắc tách khỏi cacheable shell hoặc dùng TTL ngắn, nhưng checkout luôn revalidate authoritative price/inventory. External review API có thể degrade gracefully; critical commerce call cần timeout và fail-safe behavior. Tôi cũng thiết kế redirect/canonical/status cache cùng SEO. Sau đó rollout nhỏ và đo hit ratio, origin load, freshness lag, Core Web Vitals và cold-cache behavior trước khi mở rộng.”

## Câu hỏi đào sâu

1. Một shared CMS block xuất hiện trên 5.000 pages; targeted invalidation nên thiết kế thế nào để không biến publish thành bottleneck?
2. Nếu Product yêu cầu price trên listing stale tối đa 5 giây nhưng CDN purge thực tế đôi lúc lâu hơn, bạn thay đổi architecture ra sao?
3. Một architect muốn dùng Kubernetes để giải quyết origin spike sau purge; tại sao đó có thể không phải vấn đề hạ tầng cần giải đầu tiên?

## Lỗi trả lời thường gặp

- Đặt cùng TTL cho content, price và inventory.
- Cache personalized response mà không phân tích cache key/isolation.
- Purge toàn site cho mọi publish.
- Chỉ nói “dùng CDN” mà không có invalidation/failure strategy.
- Bỏ qua SEO status/redirect và checkout authority.

## Thang điểm 0–10

- **0–2:** Chọn cache/no-cache tuyệt đối mà không phân loại dữ liệu.
- **3–4:** Có TTL/CDN nhưng thiếu identity, invalidation hoặc dependency failure.
- **5–6:** Có layered cache strategy và phân biệt freshness.
- **7–8:** Bao quát targeted invalidation, transactional authority, SEO, degradation và telemetry.
- **9–10:** Cân bằng performance/freshness/complexity, thiết kế cold-cache/failure behavior và biết chỗ cần xác minh vendor-specific capability.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Asynchronous request completion không có ordering guarantee; UI correctness cần explicit latest-request invariant.
- Distributed indexing phải được thiết kế cho duplicate, out-of-order delivery, partial failure và reconciliation.
- Cache architecture bắt đầu từ data authority, freshness và identity boundary, không bắt đầu từ một TTL chung.
- Production troubleshooting cần đi từ impact và evidence tới hypothesis, verification và remediation.
- Performance optimization phải giữ correctness: edge cache tốt không được biến stale transactional data thành source of truth.

## Mẫu tư duy cần nhớ

- Tách **correctness guarantee** khỏi **performance optimization**.
- Treat asynchronous/distributed completion as unordered unless protocol proves otherwise.
- Observe before guessing; trace một entity xuyên toàn failure path.
- Phân loại data theo authority/freshness trước khi cache.
- Thiết kế retry cùng idempotency và reconciliation.
