# Câu 1 — Elasticsearch đã index thành công, tại sao API tìm kiếm vẫn chưa thấy tài liệu?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Elasticsearch refresh, indexing, near-real-time search, distributed consistency, ASP.NET Core API, observability.

## Bối cảnh

Một hệ thống quản lý tài liệu dùng ASP.NET Core .NET 8, PostgreSQL làm source of truth và Elasticsearch phục vụ tìm kiếm. Sau khi nhân viên cập nhật tiêu đề, API ghi PostgreSQL rồi gửi cập nhật sang Elasticsearch. Worker nhận phản hồi thành công từ indexing API. Người dùng mở ngay trang tìm kiếm nhưng vẫn thấy tiêu đề cũ trong vài giây. Đôi khi khi có hai lần sửa liên tiếp, kết quả tìm kiếm còn quay về phiên bản trước. Hệ thống có nhiều worker và cần duy trì throughput cao; không thể khóa toàn bộ tìm kiếm trong lúc cập nhật.

## Câu hỏi chính

Giải thích những cơ chế nội bộ nào khiến indexing thành công không đồng nghĩa với search lập tức nhìn thấy dữ liệu mới, phân biệt hiện tượng visibility delay với stale overwrite, và thiết kế cách kiểm chứng cũng như bảo đảm trải nghiệm đúng theo yêu cầu nghiệp vụ.

## Câu hỏi làm rõ nên cân nhắc

1. API indexing trả kết quả gì, có lỗi từng item trong bulk response không?
2. Người dùng đọc bằng search hay GET theo document ID? Có cache ở API hoặc CDN không?
3. Worker có bảo đảm thứ tự cập nhật theo từng document và có version trong event không?
4. SLA về độ mới của search là bao nhiêu; màn hình chi tiết có cần read-your-writes không?
5. Có alias, reindex, replica lag hoặc refresh setting tùy chỉnh không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt durability của thao tác ghi với khả năng quan sát của search.

### Gợi ý 2
Xét refresh, searcher, thứ tự xử lý event và việc retry có thể đến muộn.

### Gợi ý 3
Đặt một version đơn điệu theo document tại ranh giới giữa database và search index.

## Cấu trúc trả lời đề xuất

1. Định nghĩa tính đúng đắn của trang chi tiết và trang tìm kiếm.
2. Tách đường đi write → event → index → refresh → search.
3. Thu thập timeline và version của từng lần cập nhật.
4. Kiểm chứng visibility delay và out-of-order update riêng biệt.
5. Chọn cơ chế đồng bộ, freshness contract và cách đo.
6. Đánh giá chi phí refresh, retry và reindex.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Elasticsearch là near-real-time search; indexing acknowledgment không mặc nhiên đồng nghĩa search visibility ngay.
- Refresh mở dữ liệu mới cho search; refresh khác flush và không phải giải pháp cho event đảo thứ tự.
- PostgreSQL vẫn là nguồn dữ liệu có thẩm quyền; cần theo dõi version và trạng thái đồng bộ.

### Điểm cộng
- Phân biệt GET realtime theo ID với search; kiểm tra bulk item errors và alias.
- Dùng transactional outbox hoặc cơ chế phát event đáng tin cậy để giảm khoảng trống DB commit / event publish.
- Có phép đo indexing lag, refresh lag, stale version và reconciliation.

### Senior+
- Định nghĩa consistency contract theo từng use case; dùng version gating chống stale overwrite, kể cả khi retry.
- Cân nhắc external versioning/version conflict theo API và chính sách xử lý sự kiện trễ, thay vì giả định thứ tự queue toàn cục.

## Hướng giải quyết tham khảo

**Giả định:** PostgreSQL là source of truth, tìm kiếm chấp nhận eventual consistency trong vài giây, còn màn hình chi tiết phải hiện dữ liệu vừa lưu.

**Cơ chế:** Indexing response xác nhận thao tác được xử lý ở write path theo semantics của API, nhưng searcher có thể chưa nhìn thấy segment mới cho đến refresh. Elasticsearch có thể phục vụ GET theo ID khác với search. `refresh=wait_for` có thể chờ refresh để dữ liệu vừa index trở nên searchable, nhưng tăng độ trễ và không nên áp dụng mặc định cho mọi bản ghi ở tải lớn. `refresh=true` ép refresh và có chi phí đáng kể. Cần kiểm tra cấu hình index, trạng thái shard và thời điểm refresh thực tế trước khi quy kết nguyên nhân.

**Một lỗi độc lập:** Hai event cho cùng tài liệu, version 41 và 42, có thể đến worker theo thứ tự 42 rồi 41. Nếu worker dùng index ghi đè vô điều kiện, version 41 có thể thay thế version 42 dù mọi HTTP response đều thành công. Cần phát hành version tăng đơn điệu từ nguồn dữ liệu, chỉ chấp nhận bản cập nhật mới hơn tại nơi ghi index; khi có conflict, xác minh document mới nhất thay vì retry vô hạn event cũ. Nếu dùng versioning API của Elasticsearch, kiểm tra đúng semantics và giá trị version theo tài liệu phiên bản đang triển khai.

**Thiết kế:** PostgreSQL transaction cập nhật document và outbox record chứa document ID/version. Worker xử lý at-least-once, cập nhật search index idempotently với version gating; dead-letter hoặc quarantine lỗi không hồi phục; reconciliation định kỳ so sánh version index với database. UI sau khi save dùng response hoặc đọc chi tiết từ PostgreSQL, thông báo rằng kết quả tìm kiếm có thể cập nhật chậm. Chỉ yêu cầu synchronous wait-for-refresh tại endpoint thật sự cần read-after-write search và sau khi đo tác động.

**Kiểm chứng:** Gắn correlation ID, document ID, version, DB commit time, outbox publish time, worker receive/index acknowledgment time và thời điểm search nhìn thấy version mới. Thử index một document rồi search ngay, search sau refresh, đồng thời gửi event 42 trước 41; kiểm tra cả lỗi bulk item. Quan sát p95 freshness lag, backlog, version conflicts, worker retry và số bản ghi lệch sau reconciliation.

**Trade-off:** Refresh thường xuyên cải thiện freshness nhưng tăng chi phí indexing/search; outbox và version gating tăng độ phức tạp nhưng giải quyết hai loại lỗi khác nhau. Nếu yêu cầu strong consistency trên mọi truy vấn, cần xem xét liệu Elasticsearch có phù hợp làm nguồn đọc quyết định nghiệp vụ hay không.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không xem phản hồi index thành công là bằng chứng search đã nhìn thấy bản ghi. Trước tiên tôi xác định màn hình nào cần read-your-writes và đo thời gian từ PostgreSQL commit tới khi search trả đúng version. Elasticsearch có cơ chế refresh nên một khoảng trễ ngắn có thể bình thường. Tuy nhiên việc kết quả quay về phiên bản cũ gợi ý một vấn đề khác: worker xử lý event không đúng thứ tự hoặc retry event cũ. Tôi sẽ log document ID/version xuyên suốt pipeline, tái hiện bằng cách đảo thứ tự event, rồi bảo vệ thao tác index bằng version đơn điệu. Tôi ưu tiên outbox và reconciliation nếu pipeline phải chịu lỗi mạng. Màn hình chi tiết đọc nguồn chính, còn search có freshness SLA rõ ràng. Tôi chỉ dùng wait-for-refresh ở những luồng thật sự cần, sau khi đo ảnh hưởng tới throughput.”

## Câu hỏi đào sâu

1. Nếu bulk API trả HTTP 200 nhưng một item thất bại, worker phải xử lý thế nào?
2. Nếu Product yêu cầu search nhìn thấy dữ liệu ngay sau mỗi lần sửa, bạn thay đổi kiến trúc hay API contract thế nào?
3. Khi reindex sang alias mới, làm sao tránh mất các cập nhật xảy ra trong lúc backfill?

## Lỗi trả lời thường gặp

- Đồng nhất indexing acknowledgment với search visibility.
- Chỉ chỉnh refresh interval mà bỏ qua event đảo thứ tự.
- Cho Elasticsearch quyết định dữ liệu nghiệp vụ chính xác tuyệt đối mà không có consistency contract.
- Retry vô hạn mọi lỗi indexing mà không phân loại.
- Không có version hoặc telemetry để chứng minh stale overwrite.

## Thang điểm 0–10

- 0–2: Chỉ định nghĩa Elasticsearch hoặc đoán lỗi cache.
- 3–4: Hiểu refresh nhưng chưa phân biệt stale overwrite.
- 5–6: Giải thích đúng cơ chế, có kiểm chứng và giải pháp cơ bản.
- 7–8: Đề xuất version gating, idempotency, observability, trade-off rõ.
- 9–10: Thiết kế consistency contract, failure recovery, reindex và phép đo production thuyết phục.

# Câu 2 — Cosmos DB tăng RU và 429 sau chiến dịch, dù tổng request không tăng nhiều

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB partitioning, RU, 429 throttling, incident response, .NET SDK, query diagnostics.

## Bối cảnh

Một hệ thống loyalty trên Azure App Service dùng Cosmos DB lưu sự kiện cộng điểm. Mỗi document có `tenantId`, `campaignId`, `memberId`, `createdAt`. Partition key hiện tại là `/campaignId`. Khi một chiến dịch lớn mở lúc 09:00, p95 API tăng từ khoảng 180 ms lên hơn 4 giây, một số request trả 503 từ application; dashboard cho thấy 429 từ Cosmos DB tăng mạnh. Tổng RU provisioned vẫn còn dư theo biểu đồ tổng hợp 5 phút. Một số tenant không thuộc chiến dịch cũng bị ảnh hưởng. Team muốn tăng RU ngay và retry vô hạn cho mọi request.

## Câu hỏi chính

Bạn sẽ điều hành incident, phân biệt hot logical partition, query/index cost, client connection pressure và retry amplification thế nào, rồi chọn remediation ngắn hạn và thiết kế dài hạn có thể chứng minh bằng số liệu?

## Câu hỏi làm rõ nên cân nhắc

1. Container dùng provisioned throughput, autoscale hay serverless; throughput cấp container hay database?
2. 429 tập trung ở partition key nào; có retry-after và SDK diagnostics không?
3. Đường đọc/ghi có point read đúng partition key hay cross-partition query?
4. Application dùng singleton CosmosClient, timeout/retry mặc định nào, có circuit breaker tầng API không?
5. Campaign có bao nhiêu member, tỷ lệ write/read, tính duy nhất và yêu cầu thứ tự sự kiện ra sao?

## Gợi ý tư duy

### Gợi ý 1
Biểu đồ RU trung bình toàn container không cho thấy mọi phân vùng đều còn khả năng phục vụ.

### Gợi ý 2
Phân tích mức tiêu thụ theo partition, query plan/diagnostics và các lần retry đã thực hiện.

### Gợi ý 3
Partition key là quyết định data modeling gắn với access patterns, không chỉ là cách phân phối lưu trữ.

## Cấu trúc trả lời đề xuất

1. Xác nhận tác động theo tenant, endpoint và mức lỗi.
2. Giảm tải, bảo vệ dependency và thông báo incident.
3. Thu thập RU/429 theo partition, request diagnostics, latency, retry, CPU.
4. Đặt giả thuyết cạnh tranh và kiểm chứng từng giả thuyết.
5. Chọn mitigation an toàn theo bằng chứng.
6. Đề xuất lại partition strategy và migration nếu cần.
7. Thiết kế load/failure tests, dashboard, alert và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc
- 429 là throttling; SDK có thể tự retry theo chính sách nên phải quan sát cả retries và end-to-end latency.
- RU tổng còn dư không loại trừ giới hạn tại physical partition/hot key.
- Không retry vô hạn, không mặc định tăng RU là chữa được key skew.

### Điểm cộng
- Phân biệt logical partition key skew với cross-partition fan-out và query RU cao.
- Xem xét idempotency của cộng điểm, queue buffering và tenant fairness.
- Dùng diagnostics per operation, query metrics, partition key metrics, status/substatus.

### Senior+
- Đề xuất migration/backfill/dual-read có kiểm soát và tính đến unique constraints/transaction scope.
- Đặt giới hạn concurrency, retry budget, backpressure và SLO theo tenant.

## Hướng giải quyết tham khảo

**Impact/stabilize:** Xác định tỷ lệ request thất bại và tenant bị ảnh hưởng; ưu tiên bảo vệ tính đúng đắn cộng điểm. Tạm giới hạn concurrency của campaign lớn, áp dụng backpressure hoặc queue nếu nghiệp vụ chấp nhận xử lý bất đồng bộ; trả lỗi có thể retry một cách có kiểm soát. Không cho API tạo nhiều side effect khi client retry: dùng operation ID và idempotent write. Tăng RU tạm thời có thể là biện pháp tình thế nếu metric cho thấy tăng capacity hữu ích; không xem đó là root-cause fix.

**Giả thuyết A — hot key:** Tất cả ghi cho campaign lớn cùng `campaignId`, gây tập trung lên một logical partition. Physical partition chứa key nóng có thể đạt giới hạn trong khi RU tổng chưa sử dụng hết. Xác minh bằng normalized RU consumption, throttled requests, partition-level metrics và distribution của key. Nếu đúng, cân nhắc partition key phân tán theo member hoặc synthetic key `campaignId#bucket`, nhưng phải đánh giá query theo campaign, uniqueness và transaction scope.

**Giả thuyết B — query cost:** Một truy vấn tìm sự kiện theo `tenantId` nhưng không cung cấp `campaignId` có thể fan out. Query lọc/sort không khớp index policy hoặc quét nhiều tài liệu tiêu tốn RU. Kiểm tra query metrics, index utilization, request charge và execution pattern. Tối ưu point reads, thiết kế materialized view phù hợp hoặc thay đổi query shape trước khi scale.

**Giả thuyết C — retry amplification:** SDK retry khi 429, tầng application và gateway lại retry đồng thời làm tăng latency, số request và nguy cơ duplicate business operation. Kiểm tra SDK diagnostics, retry count, retry-after, concurrency và request timeout. Dùng bounded retries có jitter khi thích hợp, tôn trọng retry-after và request deadline; phân biệt transient throttling với lỗi validation/authorization không nên retry.

**Giả thuyết D — client/network:** CosmosClient tạo per-request, kết nối quá nhiều, SNAT/connection pressure hoặc ThreadPool saturation làm latency xấu hơn; xác minh bằng lifetime của client, connection metrics, CPU và thread pool counters. Đây là giả thuyết phải kiểm chứng, không tự nhận là nguyên nhân từ 429.

**Remediation:** Nếu partition skew được xác nhận, triển khai mô hình key mới với workload test đại diện, migration qua backfill và change feed/dual processing theo chiến lược đã kiểm chứng; kiểm soát cutover và rollback. Cosmos DB không cho đổi partition key của container hiện hữu theo cách chỉnh metadata đơn giản: thường cần container mới và chuyển dữ liệu. Chú ý transactional batch chỉ áp dụng trong cùng logical partition; nếu tách dữ liệu cộng điểm qua nhiều partition, phải thiết kế lại invariant và compensation.

**Testing/monitoring:** Load test traffic skew 80–90% vào một campaign, test 429/retry budget, idempotency, cross-partition query và migration reconciliation. Dashboard theo p50/p95/p99, RU/request, throttling theo partition, retry count, backlog, success rate, duplicate prevention, client diagnostics và chi phí.

## Mẫu trả lời trong phỏng vấn

“Trước tiên tôi xác nhận tác động tới cộng điểm và giảm tải cho campaign nóng để tránh retry amplification. Tôi không kết luận container thiếu RU chỉ từ 429, vì RU tổng trung bình có thể che một partition quá tải. Tôi sẽ lấy diagnostics và metric theo partition key, so sánh request charge giữa các truy vấn, kiểm tra client lifetime và số lần retry. Nếu một campaign chiếm phần lớn write thì `/campaignId` là ứng viên gây hot partition, nhưng vẫn phải xác minh. Trong ngắn hạn tôi dùng backpressure, retry có giới hạn và idempotency; có thể tăng RU tạm thời nếu capacity cho phép. Dài hạn tôi đánh giá partition key mới theo access pattern, tác động đến transaction boundary và chi phí migration. Tôi sẽ chạy load test skew và theo dõi p95, RU, 429 cùng tính đúng đắn điểm thưởng trước khi rollout.”

## Câu hỏi đào sâu

1. Nếu cần truy vấn toàn bộ sự kiện của một campaign theo thời gian, synthetic partition key ảnh hưởng gì tới query?
2. Nếu tăng RU không giảm 429 tại hot key, bạn chứng minh nguyên nhân và bước tiếp theo ra sao?
3. Nếu cộng điểm yêu cầu exactly-once business effect nhưng event có thể được gửi lặp, bạn thiết kế invariant ở đâu?

## Lỗi trả lời thường gặp

- Chỉ tăng throughput mà không nhìn distribution.
- Retry vô hạn hoặc nhân đôi retry ở nhiều tầng.
- Đổi partition key mà bỏ qua query patterns và transactional scope.
- Không kiểm tra 429 bị SDK retry và che khỏi HTTP response.
- Dùng load test đồng đều để kết luận chiến dịch tập trung sẽ ổn.

## Thang điểm 0–10

- 0–2: Chỉ nói tăng RU.
- 3–4: Biết 429 nhưng thiếu kiểm chứng và stabilization.
- 5–6: Có nhiều giả thuyết, biết metrics và retry.
- 7–8: Có partition analysis, mitigation, migration và tests.
- 9–10: Quản lý incident theo SLO, fairness, correctness, cost và rollout an toàn.

# Câu 3 — Hiện đại hóa cổng quản trị .NET Framework và jQuery mà không ngừng vận hành

**Loại câu hỏi:** Architecture / system design / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** .NET modernization, IIS, ASP.NET Core, Vue.js, authentication, deployment, CI/CD, migration strategy, architecture trade-offs.

## Bối cảnh

Một cổng quản trị nội bộ chạy ASP.NET MVC trên .NET Framework 4.5, jQuery, SQL Server và IIS/Windows Server. Hệ thống có khoảng 120 màn hình, nhiều stored procedures, Windows Authentication tại intranet và các thư viện bên thứ ba không rõ còn hỗ trợ hay không. Team 6 kỹ sư phải thêm workflow phê duyệt mới, đồng thời giảm rủi ro bảo mật và thời gian release. Product muốn chuyển ngay toàn bộ sang .NET 10 + Vue.js, container/Kubernetes và microservices trong sáu tháng; ngân sách vận hành có hạn, business không chấp nhận downtime dài.

## Câu hỏi chính

Hãy đưa ra các phương án hiện đại hóa khả thi, chọn kiến trúc và lộ trình migration có điều kiện, giải thích ranh giới dữ liệu/authentication/deployment, cách rollout và rollback, và khi nào nên giữ giải pháp đơn giản hơn đề xuất ban đầu.

## Câu hỏi làm rõ nên cân nhắc

1. Thư viện nào buộc phải ở .NET Framework, có COM, Windows-only API hoặc vendor SDK không?
2. Mức downtime, RTO/RPO, SLO và lịch release được chấp nhận?
3. Authentication cần giữ Windows Authentication hay có thể chuyển Microsoft Entra ID; user/session migration thế nào?
4. Mỗi module có ownership/data boundary riêng không, hay cùng transaction SQL Server?
5. Team có kinh nghiệm vận hành container/Kubernetes, test automation và observability tới đâu?

## Gợi ý tư duy

### Gợi ý 1
Modernization không đồng nghĩa viết lại toàn bộ hay phân tách microservices.

### Gợi ý 2
Tìm seam ở routing, identity, database và deployment trước khi tách module.

### Gợi ý 3
Tạo một đường chuyển đổi có thể đảo ngược, đo được regression và giới hạn blast radius.

## Cấu trúc trả lời đề xuất

1. Xác nhận mục tiêu business và risk appetite.
2. Inventory dependencies, traffic, dữ liệu và quy trình release.
3. So sánh in-place modernization, strangler và full rewrite.
4. Chọn module pilot cùng tiêu chí thành công.
5. Định nghĩa routing, identity, DB ownership, API contract.
6. Thiết kế CI/CD, migration schema, observability, rollback.
7. Phân kỳ dự án, acceptance gates và tổng chi phí sở hữu.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Đánh giá compatibility trước khi chốt target framework và thời hạn.
- Không khẳng định Kubernetes/microservices là bắt buộc.
- Có chiến lược coexistence, data consistency, authentication và rollback.

### Điểm cộng
- Dùng strangler routing, contract tests, feature flags, canary và schema expand-contract.
- Đặt security baseline cho hệ thống legacy; tránh mở rộng quyền trong migration.
- Tách frontend migration khỏi backend migration khi phù hợp.

### Senior+
- Nêu rủi ro shared database, distributed transactions, duplicated business logic và dual-write.
- Xây dựng decision record có giả định, exit criteria, cost và phương án dừng migration.

## Hướng giải quyết tham khảo

**Định hướng:** Không hứa hoàn tất 120 màn hình trong sáu tháng trước khi inventory. Đặt mục tiêu đo được: giảm thời gian release, tăng coverage các luồng quan trọng, loại bỏ dependency không hỗ trợ, cải thiện security posture và không gián đoạn workflow. Kiểm tra support lifecycle của runtime hiện hữu và target trước khi cam kết version; nâng cấp không tương thích có thể cần thay vendor SDK.

**Các lựa chọn:** (A) giữ monolith IIS, nâng dependency/test/CI/CD trước: rủi ro chuyển đổi thấp, nhưng không giải quyết mọi giới hạn runtime; (B) strangler từng module qua reverse proxy, xây ASP.NET Core modular monolith và Vue.js cho màn hình mới: thêm routing/identity complexity nhưng migration theo lát cắt; (C) full rewrite + microservices + Kubernetes: chỉ hợp lý khi có bằng chứng về domain boundaries, nhu cầu scale độc lập và năng lực vận hành, thường rủi ro cao nhất trong bối cảnh này.

**Đề xuất có điều kiện:** Chọn B nếu module mới đủ tách biệt, có khả năng định tuyến và team chấp nhận coexistence. Giữ các trang legacy trên IIS, route path mới sang ASP.NET Core trên App Service hoặc IIS hosting tùy constraints. Dùng một identity strategy rõ ràng: nếu chuyển Entra ID/OIDC, xác minh compatibility của legacy authentication và thiết kế SSO transition; không chia sẻ cookie/session tùy tiện giữa hai stack. Phân quyền ở backend theo policy và audit mọi quyết định nhạy cảm.

**Data boundary:** Bắt đầu với một SQL Server nếu đây là nguồn dữ liệu đang được chia sẻ, nhưng quy định ownership ở tầng module. Không để cả legacy lẫn new service cập nhật cùng invariant một cách không kiểm soát. Ưu tiên API boundary hoặc stored procedure contract ổn định; thay schema theo expand-contract. Nếu cần event integration, dùng outbox để tránh dual-write không nguyên tử. Không ép microservices khi transaction liên module vẫn chặt.

**Frontend:** Có thể viết workflow mới bằng Vue.js mà không cần chuyển toàn bộ jQuery. Tách bundle, routing và contract API; bảo vệ CSRF/XSS, xác thực ở server, kiểm tra browser history và deep link. Với màn hình legacy ít thay đổi, giữ nguyên cho tới khi có business case.

**Delivery:** Pipeline build/test/scan tạo immutable artifact; deploy staging có dữ liệu ẩn danh; chạy integration/Playwright E2E cho approval, permissions và rollback. Dùng feature flags/canary theo module, log/traces có correlation ID xuyên reverse proxy, so sánh p95/error rate và dữ liệu nghiệp vụ. Rollback ứng dụng dễ hơn rollback schema: schema migration phải backward-compatible và có kế hoạch dữ liệu riêng. Nếu pilot không đạt SLO hoặc chi phí tăng quá ngưỡng, dừng mở rộng và xử lý debt.

**Trade-offs:** Coexistence tăng complexity vận hành tạm thời; monolith hiện đại dễ debug/transaction hơn microservices; App Service thường ít gánh vận hành hơn Kubernetes cho workload không có yêu cầu đặc biệt. Nếu dependencies không thể tách và quy trình release đơn giản, phương án A có thể an toàn hơn trong ngắn hạn.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ bắt đầu bằng inventory dependencies, domain boundaries và SLO thay vì chốt .NET 10, Kubernetes hay microservices ngay. Với 120 màn hình và sáu người, full rewrite trong sáu tháng có rủi ro lớn. Tôi ưu tiên một pilot theo strangler: giữ module legacy trên IIS, triển khai workflow mới bằng ASP.NET Core và Vue.js qua routing rõ ràng, trước mắt giữ SQL Server nhưng định nghĩa ownership và tránh dual-write. Identity là rủi ro cần thiết kế sớm, nhất là khi legacy dùng Windows Authentication. Tôi sẽ xây contract tests, Playwright E2E, feature flag và rollout từng nhóm user; database schema theo expand-contract để rollback được application. Nếu pilot cho thấy coexistence quá đắt hoặc dependency không tách được, tôi sẵn sàng ưu tiên hardening monolith và CI/CD trước. Tôi chỉ chọn microservices hoặc Kubernetes khi có yêu cầu độc lập triển khai, scale hoặc compliance chứng minh được lợi ích vượt chi phí.”

## Câu hỏi đào sâu

1. Nếu module mới cần cập nhật ba bảng mà legacy cũng ghi, bạn xác lập ownership và rollback ra sao?
2. Nếu Product yêu cầu tất cả màn hình lên Vue.js trong sáu tháng, bạn thương lượng scope bằng dữ liệu nào?
3. Nếu team đã có Kubernetes platform dùng chung miễn phí về vận hành, lựa chọn hosting thay đổi thế nào?

## Lỗi trả lời thường gặp

- Cam kết rewrite trước khi đánh giá dependency.
- Đề xuất microservices chỉ vì muốn nâng version .NET.
- Bỏ qua authentication coexistence và data ownership.
- Giả định rollback code cũng rollback được database.
- Chỉ đo số màn hình đã migrate, không đo business correctness và release safety.

## Thang điểm 0–10

- 0–2: Chọn công nghệ theo xu hướng.
- 3–4: Có migration plan nhưng thiếu rủi ro identity/data.
- 5–6: So sánh phương án, có pilot và rollback cơ bản.
- 7–8: Có boundaries, deployment gates, tests và trade-offs.
- 9–10: Đưa ra roadmap theo điều kiện, measurable outcomes và exit strategy.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Elasticsearch indexing acknowledgment khác search visibility; refresh delay và stale overwrite là hai failure mode riêng. Cosmos DB cần phân tích RU và 429 theo phân vùng và access pattern thay vì chỉ nhìn tổng throughput. Modernization cần thiết kế seam, ownership, identity và rollback trước khi chọn framework hay infrastructure.

1. Tách hiện tượng giống nhau thành các cơ chế lỗi có thể kiểm chứng độc lập.

3. Thiết kế retry cùng idempotency và backpressure.
4. Chọn migration theo rủi ro business, không theo độ mới công nghệ.
5. Thiết kế rollback cho cả application, schema và state.
