## Đoạn code cần review

```csharp
public sealed class CatalogIndexer : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly IElasticCatalogClient _search;
    private readonly ILogger<CatalogIndexer> _logger;

    public CatalogIndexer(IServiceScopeFactory scopes,
        IElasticCatalogClient search,
        ILogger<CatalogIndexer> logger)
        => (_scopes, _search, _logger) = (scopes, search, logger);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _scopes.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<CatalogDbContext>();
            var products = await db.Products
                .Where(p => p.UpdatedAt > DateTime.UtcNow.AddMinutes(-5))
                .OrderBy(p => p.UpdatedAt)
                .Take(1000)
                .ToListAsync(stoppingToken);

            await Task.WhenAll(products.Select(async product =>
            {
                var document = new ProductSearchDocument(
                    product.Id, product.Name, product.Price, product.IsActive);
                if (product.IsActive)
                    await _search.IndexAsync(product.Id.ToString(), document);
                else
                    await _search.DeleteAsync(product.Id.ToString());
            }));

            _logger.LogInformation("Indexed {Count} products", products.Count);
            await Task.Delay(TimeSpan.FromSeconds(20), stoppingToken);
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Có thể mất thay đổi vĩnh viễn

**Vấn đề:** Quét `UpdatedAt > UtcNow - 5 phút` không lưu checkpoint bền vững.  
**Tại sao xảy ra:** Search outage, worker downtime hoặc backlog quá năm phút khiến record ra khỏi cửa sổ.  
**Ảnh hưởng production:** Search sai giá/trạng thái không tự hồi phục.  
**Cách sửa:** Transactional outbox trong cùng transaction cập nhật product; consumer có trạng thái xử lý bền vững, retry và DLQ/parking cho poison events.

### [High] — Version cũ có thể ghi đè mới

**Vấn đề:** Nhiều worker index cùng product mà không kiểm soát thứ tự.  
**Tại sao xảy ra:** Request cũ có thể hoàn tất sau request mới, kể cả trong cùng một instance.  
**Ảnh hưởng production:** Giá hoặc trạng thái cũ tái xuất hiện.  
**Cách sửa:** Dùng version tăng đơn điệu từ database, áp dụng external versioning/conditional write phù hợp với Elasticsearch client/version; hoặc serialize per product và xác minh version ở phía index. Tombstone/delete cũng cần bảo vệ khỏi stale replay.

### [High] — Mỗi instance quét và xử lý trùng

**Vấn đề:** Cả 4 instances chạy cùng một vòng quét.  
**Tại sao xảy ra:** `BackgroundService` không phải distributed scheduler.  
**Ảnh hưởng production:** Nhân tải, duplicate writes, tăng xác suất race.  
**Cách sửa:** Claim outbox rows có lease/lock hoặc dùng queue với competing consumers; bảo đảm idempotency ở sink.

### [High] — Bỏ sót record khi backlog vượt 1.000

**Vấn đề:** `Take(1000)` luôn lấy phần đầu trong cửa sổ, không có cursor hay acknowledgment.  
**Tại sao xảy ra:** Không tiến tới trang tiếp theo khi backlog lớn.  
**Ảnh hưởng production:** Starvation và lag không giới hạn.  
**Cách sửa:** Batch theo outbox ID/claim, đánh dấu hoàn tất và tiếp tục tới các batch tiếp theo.

### [High] — Không kiểm tra kết quả thao tác index

**Vấn đề:** Code không xem `IsValidResponse` hay lỗi từng item.  
**Tại sao xảy ra:** Một số client trả response thất bại mà không throw; Bulk API có thể thành công một phần.  
**Ảnh hưởng production:** Báo thành công sai, mất khả năng retry có chọn lọc.  
**Cách sửa:** Kiểm tra response, phân loại lỗi retryable/permanent và ghi trạng thái từng event.

### [Medium] — Burst không giới hạn và thiếu backpressure

**Vấn đề:** `Task.WhenAll` tạo tối đa 1.000 requests cùng lúc mỗi instance.  
**Tại sao xảy ra:** Không có concurrency limit hoặc adaptive throttling.  
**Ảnh hưởng production:** 429, connection pressure, CPU và memory tăng.  
**Cách sửa:** Bounded concurrency, bulk indexing có batch size phù hợp, exponential backoff + jitter.

### [Medium] — Cancellation không đi tới search client

**Vấn đề:** Không truyền `stoppingToken` cho network calls.  
**Tại sao xảy ra:** Chỉ query DB và delay có token.  
**Ảnh hưởng production:** Shutdown kéo dài, deploy không sạch.  
**Cách sửa:** Truyền token xuyên suốt, đồng thời thiết kế retry không làm mất event đã claim.

### [Medium] — Tải entity đầy đủ và tracking không cần thiết

**Vấn đề:** `ToListAsync` materialize tracked entities cho tác vụ read-only.  
**Tại sao xảy ra:** Mặc định EF Core tracking.  
**Ảnh hưởng production:** Tăng allocations và chi phí query.  
**Cách sửa:** Projection + `AsNoTracking`, index hỗ trợ query claim; ưu tiên outbox payload tối thiểu.

### [Medium] — Dựa vào clock và độ phân giải timestamp

**Vấn đề:** Đồng hồ app và `UpdatedAt` có thể lệch, nhiều update cùng timestamp.  
**Tại sao xảy ra:** Không có cursor thứ tự ổn định và source-of-truth version.  
**Ảnh hưởng production:** Bỏ sót hoặc xử lý sai thứ tự.  
**Cách sửa:** Database-generated sequence/version, không dùng wall-clock làm event offset.

### [Low] — Telemetry không thể phân biệt scanned và indexed

**Vấn đề:** Log số product được lấy, không phản ánh số thành công/thất bại.  
**Tại sao xảy ra:** Không thu thập response và lag.  
**Ảnh hưởng production:** Incident phát hiện muộn.  
**Cách sửa:** Metrics cho pending, oldest event age, retry, failures, version conflict và indexing latency.

## Phiên bản đề xuất

Thiết kế: transaction cập nhật `Products` đồng thời insert `CatalogOutbox` với `EventId`, `ProductId`, `ProductVersion`, `Operation`, `Payload`. Một worker claim các event chưa hoàn tất bằng database locking/lease, index với version guard và ack sau khi xác minh response. Pseudocode C# dưới đây giả định repository đã triển khai atomic claim và lease expiry, và adapter hỗ trợ conditional versioning; không phải API mặc định của EF Core/Elasticsearch.

```csharp
public sealed class CatalogOutboxWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly ILogger<CatalogOutboxWorker> _log;

    public CatalogOutboxWorker(IServiceScopeFactory scopes,
        ILogger<CatalogOutboxWorker> log)
        => (_scopes, _log) = (scopes, log);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using var scope = _scopes.CreateScope();
            var outbox = scope.ServiceProvider.GetRequiredService<ICatalogOutbox>();
            var index = scope.ServiceProvider.GetRequiredService<IVersionedCatalogIndex>();
            var events = await outbox.ClaimBatchAsync(100, TimeSpan.FromMinutes(2), ct);

            await Parallel.ForEachAsync(events,
                new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
                async (item, token) =>
                {
                    try
                    {
                        var result = await index.ApplyIfNewerAsync(
                            item.ProductId, item.ProductVersion,
                            item.Operation, item.Payload, token);
                        if (result is IndexApplyResult.Applied
                            or IndexApplyResult.AlreadyNewer)
                            await outbox.CompleteAsync(item.EventId, item.LeaseToken, token);
                        else
                            await outbox.ReleaseForRetryAsync(item.EventId,
                                item.LeaseToken, token);
                    }
                    catch (Exception ex) when (!token.IsCancellationRequested)
                    {
                        _log.LogWarning(ex, "Index retry for event {EventId}", item.EventId);
                        await outbox.ReleaseForRetryAsync(item.EventId,
                            item.LeaseToken, token);
                    }
                });

            if (events.Count == 0)
                await Task.Delay(TimeSpan.FromSeconds(2), ct);
        }
    }
}
```

**Điều kiện bắt buộc của thiết kế:** `ClaimBatchAsync` phải atomic giữa instances; `CompleteAsync` kiểm tra lease token; retry có backoff và giới hạn, poison event được chuyển trạng thái để xử lý thủ công; `ApplyIfNewerAsync` phải xử lý delete/tombstone và idempotency. Lease có thể hết hạn trong lúc request còn chạy: version guard vẫn là tuyến bảo vệ cuối. Nếu Elasticsearch không hỗ trợ semantics mong muốn cho delete/recreate trong cấu hình đang dùng, cân nhắc giữ tombstone document hoặc xây dựng snapshot reconciliation.

## Giải thích thiết kế sau khi sửa

Outbox đóng khoảng trống giữa SQL commit và index; atomic claim hạn chế trùng công việc; version guard ngăn stale replay; ack sau xác minh bảo đảm có thể retry khi worker chết. Đây là at-least-once processing, không phải exactly-once delivery. Periodic reconciliation so sánh source DB và index là tuyến phòng vệ bổ sung.

## Trade-offs

Outbox tăng schema, write amplification, vận hành worker và backlog monitoring. Conditional versioning đòi hỏi thiết kế version xuyên suốt delete/recreate. Nếu catalog rất nhỏ, periodic full reconciliation có thể đơn giản hơn; với yêu cầu một phút và 2 triệu sản phẩm, cần benchmark throughput trước khi chọn batch size.

## Cách kiểm thử

1. **Integration:** Commit product + outbox atomic; rollback không để lại event.
2. **Concurrency:** Hai worker claim cùng batch, không cùng ack một lease; replay event cũ không overwrite version mới.
3. **Failure-path:** Elasticsearch down 15 phút rồi hồi phục, mọi thay đổi vẫn có thể được xử lý.
4. **Load:** Burst 100.000 updates, đo oldest-event age, p95 indexing lag và 429.
5. **Recovery:** Crash giữa index success và ack; retry không tạo trạng thái sai, kể cả delete/recreate.

## Quan sát trong production

Dashboard: outbox pending count, oldest pending age, processing latency p95/p99, retry rate, poison count, Elasticsearch rejection/429, version conflicts, DB lock waits. Trace từ product update đến event ID và index operation; alert khi indexing lag vượt SLO hoặc pending tăng liên tục. Không log payload chứa dữ liệu nhạy cảm.

<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Product = { id: string; name: string; price: number };
type Result = { items: Product[]; total: number };

const query = ref('');
const category = ref('all');
const page = ref(1);
const items = ref<Product[]>([]);
const total = ref(0);
const loading = ref(false);
const error = ref('');

async function loadProducts() {
  loading.value = true;
  error.value = '';
  const url = '/api/products?q=' + query.value +
    '&category=' + category.value + '&page=' + page.value;
  const response = await fetch(url);
  const data = await response.json() as Result;
  items.value = data.items;
  total.value = data.total;
  loading.value = false;
}

watch([query, category, page], loadProducts);
onMounted(loadProducts);

function nextPage() {
  if (items.value.length > 0) page.value++;
}
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <select v-model="category" aria-label="Category">
    <option value="all">All</option>
    <option value="electronics">Electronics</option>
    <option value="books">Books</option>
  </select>
  <button :disabled="loading" @click="nextPage">Next</button>
  <p v-if="loading">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <p>{{ total }} products</p>
  <ul><li v-for="p in items" :key="p.id">{{ p.name }}</li></ul>
</template>
```

## Kết quả code review tham khảo

### [High] — Stale response ghi đè state mới

**Vấn đề:** Mọi response đều cập nhật `items` dù filter đã thay đổi.  
**Tại sao xảy ra:** Network completion order khác request start order.  
**Ảnh hưởng production:** Hiển thị sản phẩm không đúng bộ lọc, có thể dẫn tới quyết định mua sai.  
**Cách sửa:** Abort request cũ và kiểm tra request generation trước khi ghi state.

### [High] — Không xử lý lỗi và HTTP status

**Vấn đề:** Không `try/catch/finally`, không kiểm tra `response.ok`.  
**Tại sao xảy ra:** `fetch` không reject chỉ vì HTTP 4xx/5xx; JSON parse hoặc network có thể throw.  
**Ảnh hưởng production:** Unhandled rejection, loading bị treo, response lỗi có thể bị gán như data.  
**Cách sửa:** Kiểm tra status, validate response shape, phân biệt AbortError và lỗi thực, reset loading trong `finally` có guard.

### [High] — Pagination giữ page cũ khi filter đổi

**Vấn đề:** Thay query/category không reset page.  
**Tại sao xảy ra:** Page là state độc lập với filter.  
**Ảnh hưởng production:** Trang rỗng dù có kết quả ở trang đầu.  
**Cách sửa:** Reset page về 1 trước khi fetch cho filter mới; gom thay đổi để tránh request trung gian.

### [Medium] — Không encode query parameters

**Vấn đề:** Nối chuỗi trực tiếp.  
**Tại sao xảy ra:** Dấu `&`, `#`, `+` và Unicode làm URL có semantics khác.  
**Ảnh hưởng production:** Query sai, khó tái hiện lỗi.  
**Cách sửa:** `URLSearchParams`; server vẫn phải validate input.

### [Medium] — Request trên từng ký tự

**Vấn đề:** Watch query gọi API liên tục.  
**Tại sao xảy ra:** Không debounce hoặc min query length policy.  
**Ảnh hưởng production:** Tăng load, request thừa và UI nhấp nháy.  
**Cách sửa:** Debounce input search 250–400 ms theo UX đã đo; category/page có thể fetch ngay.

### [Medium] — Không cleanup request khi unmount

**Vấn đề:** Request còn chạy sau khi component rời trang.  
**Tại sao xảy ra:** Không có cleanup lifecycle.  
**Ảnh hưởng production:** Network lãng phí và callback khó debug.

const error = ref('');
let generation = 0;

watch(query, (value, _, onCleanup) => {
  const timer = setTimeout(() => { debouncedQuery.value = value; }, 300);
  onCleanup(() => clearTimeout(timer));
});
watch([debouncedQuery, category], () => { page.value = 1; });

watch([debouncedQuery, category, page], async ([q, c, p], _, onCleanup) => {
  const controller = new AbortController();
  const current = ++generation;
  onCleanup(() => controller.abort());
  loading.value = true;
  error.value = '';
  try {
    const params = new URLSearchParams({ q, category: c, page: String(p) });
    const response = await fetch('/api/products?' + params, {
      signal: controller.signal
    });
    if (!response.ok) throw new Error('HTTP ' + response.status);
    const result: Result = await response.json();
    if (!Array.isArray(result.items) || !Number.isFinite(result.total))
      throw new Error('Invalid API response');
    if (current !== generation || controller.signal.aborted) return;
    items.value = result.items;
    total.value = result.total;
  } catch (e) {
    if (current !== generation || controller.signal.aborted) return;
    items.value = [];
    total.value = 0;
    error.value = 'Không tải được sản phẩm. Vui lòng thử lại.';
  } finally {
    if (current === generation) loading.value = false;
  }
}, { immediate: true });

const canNext = computed(() =>
  !loading.value && page.value * PAGE_SIZE < total.value);
</script>

<template>
  <input v-model="query" aria-label="Search products" />
  <select v-model="category" aria-label="Category">
    <option value="all">All</option>
    <option value="electronics">Electronics</option>
    <option value="books">Books</option>
  </select>
  <button :disabled="!canNext" @click="page++">Next</button>
  <p v-if="loading" role="status">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="!loading && !error && !items.length">Không có kết quả.</p>
  <p aria-live="polite">{{ total }} products</p>
  <ul><li v-for="p in items" :key="p.id">{{ p.name }}</li></ul>
</template>
```

**Lưu ý:** Trong Vue, watcher được batch theo scheduler; cần kiểm thử để bảo đảm filter reset page không tạo fetch trung gian không mong muốn. Nếu có query cache/router state hoặc SSR, nên đóng gói fetch trong composable có contract rõ. Validation ở ví dụ là tối thiểu, production nên kiểm tra schema đầy đủ. Khi input đã đổi nhưng debounce chưa hoàn tất, UI có thể tạm hiển thị kết quả cũ: cần quyết định UX có hiển thị trạng thái pending hay không.

## Giải thích thiết kế sau khi sửa

Sequence guard ngăn response cũ ghi state; abort tiết kiệm tài nguyên nhưng không thay thế guard. `URLSearchParams` giữ đúng query encoding. `response.ok` và schema validation tạo ranh giới tin cậy. Pagination dựa vào metadata thay vì số phần tử ở trang hiện tại.

## Trade-offs

Debounce giảm request nhưng tăng latency cảm nhận; hủy request không bảo đảm server dừng xử lý; clear items khi lỗi tránh nhầm kết quả cũ nhưng làm mất context người dùng. Với ứng dụng lớn, query library có cache, deduplication và retry policy có thể phù hợp hơn, nhưng không bắt buộc cho một màn hình nhỏ.

## Cách kiểm thử

1. **Playwright E2E:** Mock response A chậm hơn B; UI cuối cùng chỉ hiển thị B.
2. **Component test:** Đổi category khi đang ở page 4, kết quả và page trở về 1.
3. **Failure-path:** HTTP 500, malformed JSON, offline; loading kết thúc, error hiển thị.
4. **Network test:** Nhập nhanh 10 ký tự, đo số requests sau debounce và abort khi unmount.
5. **Pagination test:** Total 41, pageSize 20; Next bị disable ở page 3.

## Quan sát trong production

Theo dõi request count/search session, latency p50/p95, HTTP error rate, abort rate (phân biệt abort chủ động với lỗi), empty-result rate và user interaction timing. Browser network waterfall và correlation ID nối frontend request với ASP.NET Core/Application Insights; không log raw query có dữ liệu cá nhân nếu không có chính sách phù hợp.

## Câu hỏi phỏng vấn mở rộng

1. Khi URL cần hỗ trợ deep-link filter/page, bạn sẽ đồng bộ Vue Router và state thế nào để tránh loop?
2. Nếu API trả cursor pagination thay vì page number, UI và cache key thay đổi ra sao?
3. Nếu sản phẩm cập nhật liên tục, bạn sẽ chọn stale-while-revalidate hay luôn fetch mới dựa trên tiêu chí nào?

## Kiến thức trọng tâm

Đồng bộ PostgreSQL → Elasticsearch cần durability, idempotency, version ordering và reconciliation; background worker chạy trên nhiều instances không tự bảo đảm single execution. Frontend async request cần quản lý lifecycle, stale responses, HTTP errors, filter pagination và backpressure. Cả hai tình huống đều yêu cầu đo telemetry trước khi kết luận.

3. Mọi asynchronous result cần điều kiện hợp lệ trước khi commit state.
4. Kiểm thử race, outage, backlog và recovery thay vì chỉ happy path.
5. Đo lag, error rate và p95 trước khi thêm complexity.
