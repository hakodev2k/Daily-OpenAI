# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, query execution, Change Tracker, SQL diagnosis, performance

## Bối cảnh

Một ASP.NET Core API trả danh sách nhân viên kèm trạng thái mailbox. Sau một refactor, endpoint vẫn đúng dữ liệu nhưng p95 tăng từ khoảng 250 ms lên hơn 2 giây khi có tải. SQL monitoring cho thấy số query/request tăng mạnh. Service dùng cùng một `DbContext` trong request, có cả `IQueryable`, `ToListAsync`, navigation properties và một số đoạn kiểm tra `AnyAsync`. Một developer nói: “LINQ chỉ là collection filtering; query đã chạy ngay khi gọi `Where`, nên thêm `ToListAsync` không thay đổi nhiều.”

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc xây dựng `IQueryable` đến lúc SQL được thực thi, Change Tracker tham gia như thế nào, vì sao cùng logic có thể phát sinh nhiều database round-trip, misconception nào đang tồn tại, rủi ro production là gì và bạn sẽ chứng minh giả thuyết bằng evidence nào?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint là read-only hay dữ liệu còn được update trong cùng request?
- Có lazy-loading proxies hay explicit loading không?
- Query được enumerate bao nhiêu lần và ở những vị trí nào?
- Có projection DTO hay load nguyên entity graph?
- Số row, cardinality của navigation và SQL thực tế thay đổi ra sao sau refactor?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt xây dựng expression tree với thời điểm enumerate query.
- **Gợi ý 2:** Kiểm tra materialization, tracking, navigation loading, repeated enumeration và query shape.
- **Gợi ý 3:** Đừng tối ưu từ source code bằng cảm giác; capture SQL/query count, execution plan và trace theo request.

## Cấu trúc trả lời đề xuất

1. Làm rõ read/write và loading strategy.
2. Giải thích `IQueryable` và deferred execution.
3. Xác định các execution boundary.
4. Phân tích Change Tracker và materialization cost.
5. Liệt kê các nguyên nhân gây query lặp/N+1.
6. Đề xuất projection, `AsNoTracking`, query consolidation khi phù hợp.
7. So sánh trade-off.
8. Xác minh bằng logs, tracing và database metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `Where` trên `IQueryable` thường xây expression chứ chưa tự thực thi SQL; các terminal/materialization operations như `ToListAsync`, `FirstAsync`, `AnyAsync` mới kích hoạt query.
- Enumerate cùng query nhiều lần có thể tạo nhiều round-trip.
- Tracking hữu ích khi update nhưng tạo overhead không cần thiết cho nhiều read-only query.
- Phải xem SQL thực tế thay vì suy luận chỉ từ LINQ.

### Điểm cộng

- Nêu projection trực tiếp sang DTO để giảm columns/entity materialization.
- Phân biệt eager, explicit và lazy loading; nhận diện N+1.
- Đề cập query splitting/single-query như một trade-off phụ thuộc shape, không phải quy tắc tuyệt đối.

### Nâng cao

- Correlate request trace với EF Core command spans, database execution plan, logical reads và query count.
- Đánh giá identity resolution/tracking khi graph lớn.
- Dùng benchmark/load test có dữ liệu gần production để tránh tối ưu sai bottleneck.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only và regression xuất hiện sau thay đổi query shape. Tôi sẽ trước tiên đo query count/request và SQL duration. `IQueryable` giữ expression tree; provider dịch expression sang SQL khi query được execute. Nếu code gọi `AnyAsync`, sau đó `ToListAsync`, rồi enumerate một query mới cho từng entity/navigation thì một request có thể tạo nhiều lệnh SQL.

Với read-only path, ưu tiên projection chỉ lấy field cần thiết và `AsNoTracking()` nếu không cần tracking. Nếu cần related data, thiết kế query rõ ràng thay vì vô tình tạo N+1. Không mặc định rằng một query SQL khổng lồ luôn tốt hơn nhiều query: join nhiều collection có thể làm tăng lượng dữ liệu lặp; split query cũng tăng round-trip và có consistency trade-off.

Tôi sẽ bật EF Core command logging có kiểm soát ở môi trường chẩn đoán, dùng distributed tracing, kiểm tra generated SQL và execution plan. Test gồm correctness, query-count regression test cho critical path và load test. Theo dõi p50/p95/p99, DB duration, rows returned và query count/request. Nếu endpoint thực sự update entity trong cùng unit of work thì việc bỏ tracking phải được đánh giá lại.

## Mẫu trả lời trong phỏng vấn

“Trước hết tôi muốn xác nhận endpoint này read-only và có lazy loading hay không. Với EF Core, `Where` trên `IQueryable` chủ yếu xây expression tree; SQL thường chỉ chạy khi materialize hoặc dùng terminal operator như `ToListAsync` hay `AnyAsync`. Vì vậy refactor có thể giữ nguyên business result nhưng vô tình execute query nhiều lần hoặc tạo N+1 qua navigation. Tôi sẽ không kết luận chỉ từ code mà correlate request trace với EF command logs để đếm round-trip và xem generated SQL. Nếu đây là read-only endpoint, tôi thường projection thẳng sang DTO và dùng no-tracking khi phù hợp. Tuy nhiên tôi cũng kiểm tra execution plan và lượng dữ liệu trả về vì gom tất cả thành một query lớn không phải lúc nào cũng tốt. Sau fix tôi thêm regression test về query count cho critical path và load test, rồi theo dõi latency cùng DB metrics.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTracking()` có thể làm thiết kế của bạn khó hơn hoặc sai kỳ vọng?
2. Nếu `Include` nhiều collection làm một query chậm hơn, bạn cân nhắc gì trước khi dùng split query?
3. Nếu generated SQL chỉ có một query nhưng latency vẫn cao, bước điều tra tiếp theo là gì?

## Lỗi trả lời thường gặp

- Nói mọi LINQ đều chạy in-memory.
- Cho rằng `Where` lập tức gọi database.
- Dùng `AsNoTracking` như thuốc chữa mọi vấn đề EF Core.
- Chỉ nhìn duration mà không đếm query/rows/logical reads.
- Đề xuất cache trước khi xác định bottleneck.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.5**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **1.5**
- Communication: **1.0**

# Câu 2 — Incident: Hangfire gửi email/notification trùng sau khi scale-out

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire/background jobs, idempotency, concurrency, database consistency, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire xử lý thay đổi lịch sự kiện và gửi notification. Sau deployment tăng từ một lên ba application instances, một tỷ lệ nhỏ người dùng nhận hai email giống nhau và một số external calendar update được gọi lặp. Job có retry khi dependency timeout. Không có bằng chứng rõ ràng rằng Hangfire “chạy cùng job hai lần”, nhưng duplicate tăng rõ khi external API chậm.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ containment đến root cause và thiết kế lâu dài để side effect an toàn trước retry/concurrency, trong khi không giả định trước rằng chỉ Hangfire là nguyên nhân?

## Câu hỏi làm rõ nên cân nhắc

- Duplicate là cùng business operation ID hay chỉ cùng nội dung?
- Side effect nào có idempotency support từ external provider?
- Job được enqueue ở đâu và transaction với business data ra sao?
- Retry xảy ra trước hay sau khi external side effect có thể đã thành công?
- Có unique constraint/deduplication key hay audit trail cho delivery không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “job được thực thi lại” khỏi “business side effect xảy ra lại”.
- **Gợi ý 2:** Xem enqueue, retry, timeout ambiguity, multi-instance concurrency và transaction boundary.
- **Gợi ý 3:** Thiết kế idempotency ở business boundary; đừng phụ thuộc vào niềm tin rằng execution sẽ exactly-once.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius và loại side effect.
2. Contain duplicate nếu có thể mà không làm mất processing.
3. Correlate job ID, operation ID, retry và provider request.
4. Xây nhiều giả thuyết.
5. Xác định transaction/failure windows.
6. Thêm idempotency/deduplication phù hợp.
7. Thiết kế retry/failure recovery.
8. Verify bằng concurrency/failure tests và production metrics.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không hứa exactly-once chỉ dựa vào background-job framework.
- Side effect cần business idempotency key hoặc durable deduplication state.
- Timeout tạo trạng thái mơ hồ: caller không biết provider đã xử lý hay chưa.
- Phải ưu tiên containment và evidence trước refactor lớn.

### Điểm cộng

- Unique constraint trên `(OperationId, EffectType, Recipient/Target)` khi semantics cho phép.
- Outbox để gắn thay đổi business data với intent phát event/job một cách bền vững.
- State machine như Pending/Processing/Succeeded/Failed với lease/version thay vì boolean đơn giản.

### Nâng cao

- Phân biệt idempotency của command nội bộ và idempotency của provider bên ngoài.
- Reconciliation job cho ambiguous outcomes.
- Chaos/failure injection tại thời điểm “provider thành công nhưng response bị mất”.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định blast radius, tạm giảm retry aggressiveness hoặc chặn riêng side effect có duplicate nguy hiểm nếu có safe mitigation. Sau đó dùng một business `OperationId` xuyên suốt API → database → Hangfire → external call. Tôi kiểm tra liệu duplicate bắt nguồn từ enqueue nhiều lần, retry sau timeout, concurrent workers hay code gọi provider hai lần.

Thiết kế lâu dài không dựa vào exactly-once execution. Với mỗi side effect, lưu durable delivery record có unique business key. Worker cố claim operation theo concurrency-safe database operation. Nếu provider hỗ trợ idempotency key thì truyền cùng key qua retry. Nếu provider không hỗ trợ, cần ledger/reconciliation và chấp nhận rằng một số failure window không thể loại bỏ tuyệt đối chỉ bằng local lock.

Nếu business transaction và enqueue có dual-write gap, cân nhắc transactional outbox. Test quan trọng nhất là kill/timeout tại nhiều boundary: trước call, provider xử lý nhưng response mất, sau ghi success, worker restart, hai workers claim đồng thời. Metrics gồm retry rate, duplicate-prevented count, ambiguous operations và age của pending records.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng kết luận Hangfire bị lỗi. Tôi muốn xác định duplicate có cùng business operation ID không, sau đó correlate enqueue, execution attempt, retry và external request. Khi external call timeout, một tình huống nguy hiểm là provider đã thành công nhưng worker chưa nhận response; retry có thể lặp side effect. Vì vậy tôi thiết kế business operation idempotent thay vì kỳ vọng job exactly-once. Tôi sẽ có durable delivery record với unique key, claim operation atomically và dùng provider idempotency key nếu có. Nếu enqueue và business update đang là dual write, tôi cân nhắc outbox. Với provider không hỗ trợ idempotency, tôi thêm reconciliation cho ambiguous outcome. Cuối cùng tôi test bằng concurrent workers và fault injection đúng các failure window, rồi theo dõi retry, duplicate suppression và pending age.”

## Câu hỏi đào sâu

1. Distributed lock có đủ để thay thế idempotency không? Vì sao?
2. Nếu provider không có API tra cứu trạng thái và không hỗ trợ idempotency key, bạn xử lý ambiguity thế nào?
3. Outbox giải quyết vấn đề gì và không giải quyết vấn đề gì?

## Lỗi trả lời thường gặp

- Chỉ thêm distributed lock rồi tuyên bố hết duplicate.
- Tắt retry hoàn toàn và tạo nguy cơ mất operation.
- Không phân biệt enqueue duplicate với side-effect duplicate.
- Không có correlation/business operation ID.
- Bỏ qua failure window sau external success nhưng trước local commit.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
- Communication: **1.0**

# Câu 3 — Thiết kế AI Code Review Agent có quyền truy cập repository và CI

**Loại câu hỏi:** AI engineering / system decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** AI agents, context engineering, tool security, deterministic validation, evaluation, auditability, cost/latency

## Bối cảnh

Team muốn một AI agent review pull request cho dự án .NET. Agent có thể đọc diff, repository instructions, test results và static-analysis output. Product owner muốn agent “tự sửa code và merge nếu confidence cao” để giảm thời gian review. Repository chứa deployment workflows và một số configuration nhạy cảm. PR có thể đến từ contributor không đáng tin cậy; nội dung source code/comment có thể chứa instruction cố tình thao túng agent.

## Câu hỏi chính

Hãy thiết kế phiên bản production-safe của agent: AI thực sự cần làm phần nào, phần nào phải deterministic, context nào được cấp, tool/permission nào được phép, cách chống prompt injection từ repository, validation/evaluation ra sao, fallback và human approval ở đâu, và hệ thống được audit/monitor thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được phép push commit/merge?
- PR đến từ internal branch hay untrusted fork?
- Những file/path nào được xem là sensitive hoặc privileged?
- Quality target đo bằng defect detection, false-positive rate hay developer acceptance?
- CI hiện có những deterministic gates nào?

## Gợi ý tư duy

- **Gợi ý 1:** Tách reasoning không xác định khỏi authorization và enforcement.
- **Gợi ý 2:** Repository content là untrusted data, không phải instruction có cùng trust level với system policy.
- **Gợi ý 3:** Bắt đầu read-only + human approval; mở quyền theo measured evidence và explicit policy, không theo model “confidence” tự khai báo.

## Cấu trúc trả lời đề xuất

1. Xác định mục tiêu và threat model.
2. Phân loại trusted/untrusted context.
3. Thiết kế minimal tool permissions.
4. Xác định deterministic gates.
5. Thiết kế structured output và validation.
6. Human approval cho privileged action.
7. Offline/online evaluation.
8. Audit, monitoring, fallback và cost controls.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cho model tự quyết authorization dựa trên natural-language confidence.
- Treat PR diff, comments và repository text như untrusted input.
- Principle of least privilege; read-only mặc định.
- Build/test/lint/security policy phải do deterministic tooling enforce.
- Structured findings cần file/line/evidence và validation trước khi publish/action.

### Điểm cộng

- Context allowlist, size/token budget, secret redaction và path-based policy.
- Separate agent identity/token với quyền tối thiểu; không expose deployment credentials.
- Human approval cho write/merge hoặc policy engine độc lập kiểm soát action.

### Nâng cao

- Evaluation dataset từ historical PRs với labeled defects; đo precision/recall theo category và false-positive burden.
- Canary rollout, shadow mode, regression eval khi prompt/model/tooling thay đổi.
- Audit log gồm model/config version, context provenance, tool calls, validation result và approver.

## Hướng giải quyết tham khảo

**Khuyến nghị:** MVP chỉ read-only và tạo review suggestion. AI phù hợp để tổng hợp context, tìm pattern phức tạp và đề xuất hypothesis; authorization, secret access, CI gates, merge policy và schema validation phải deterministic.

Context pipeline chỉ lấy diff, các file liên quan theo allowlist, repository guidance đáng tin cậy từ vị trí được quản trị, test/static-analysis output và metadata cần thiết. Nội dung PR được đánh dấu untrusted; agent không được phép biến text trong code/comment thành policy/tool instruction. Tool layer enforce path/operation permissions độc lập với model.

Output dùng schema gồm severity, file, line/range, claim, evidence, suggested test/fix. Validator loại finding không map được vào diff hoặc thiếu evidence. CI tiếp tục quyết định build/test/security gates. Write action, nếu sau này mở, đi qua approval/policy gate và token riêng có scope tối thiểu; merge không dựa vào model confidence đơn thuần.

Đánh giá bằng historical PR benchmark và shadow deployment: precision, recall trên defect classes, false-positive rate, developer acceptance, latency và token cost. Audit mọi tool call/context provenance/model version. Nếu model/tool lỗi, fallback là CI + human review hiện tại, không block delivery trừ khi deterministic gate thất bại.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không cho agent quyền merge ở phiên bản đầu. AI có giá trị ở việc đọc diff cùng context và phát hiện vấn đề khó encode thành rule, nhưng authorization, CI gates và merge policy phải deterministic. Tôi coi code, comments và PR text là untrusted input vì chúng có thể chứa prompt injection. Context được build qua allowlist, redaction và token budget; tool layer enforce quyền độc lập với lời model. Agent trả structured findings có file, line và evidence; validator kiểm tra chúng trước khi comment. Tôi chạy shadow mode trên historical/current PRs để đo precision, recall, false-positive burden, latency và cost. Chỉ khi có evidence tốt mới cân nhắc write capability, và khi đó vẫn cần policy/human approval cho privileged actions. Mọi context provenance, tool call, model/config version và approval đều phải audit được.”

## Câu hỏi đào sâu

1. Nếu agent cần chạy test để xác minh hypothesis, bạn sandbox execution như thế nào?
2. Tại sao “confidence > 95% thì auto-merge” là policy yếu?
3. Nếu read-only agent có false-positive rate thấp nhưng recall cũng thấp, bạn ưu tiên cải thiện gì và đo tác động ra sao?

## Lỗi trả lời thường gặp

- Cấp write/merge permission ngay từ đầu.
- Tin repository instructions bất kể nguồn/path/trust level.
- Dùng model để tự xác nhận output của chính nó mà không có deterministic evidence.
- Chỉ đo “developer thích hay không” mà không có defect-oriented evaluation.
- Không có fallback hoặc audit trail.

## Thang điểm 0–10

- Requirement clarification: **1.5**
- Technical correctness: **2.0**
- Depth: **2.0**
- Trade-off analysis: **1.5**
- Production readiness: **2.0**
