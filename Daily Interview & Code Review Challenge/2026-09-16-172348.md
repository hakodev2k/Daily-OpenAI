# Câu 1 — ASP.NET Core middleware đọc Request.Body rồi controller nhận body rỗng

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core request pipeline, middleware, request body streams, buffering, model binding, resource usage, security, observability

## Bối cảnh

Một ASP.NET Core Web API có middleware audit mới để ghi hash của JSON request phục vụ điều tra giao dịch. Sau rollout, một số POST endpoints bắt đầu trả validation error vì DTO bind thành `null` hoặc thiếu dữ liệu. Middleware hiện đọc toàn bộ `HttpContext.Request.Body` bằng `StreamReader` trước khi gọi `_next(context)`.

Team nhận thấy nếu bỏ middleware thì lỗi biến mất. Một developer đề xuất luôn copy body sang `MemoryStream`; developer khác muốn log raw request body để debug nhanh. API có request từ vài KB đến khoảng 20 MB, một số endpoint upload file riêng, và traffic peak khá cao.

## Câu hỏi chính

Hãy giải thích internal/practical behavior của `Request.Body`, vị trí middleware và model binding trong pipeline khiến downstream có thể thấy body rỗng. Bạn sẽ sửa middleware như thế nào để đạt mục tiêu audit mà không tạo memory pressure hoặc rủi ro lộ dữ liệu, và bạn sẽ xác minh behavior bằng test/telemetry nào?

## Câu hỏi làm rõ nên cân nhắc

1. Audit cần hash của raw bytes hay canonicalized business payload?
2. Endpoint/content type nào cần audit và endpoint nào phải loại trừ?
3. Maximum body size và concurrency thực tế là bao nhiêu?
4. Audit có được phép chứa PII/secrets hay chỉ metadata/hash?
5. Middleware chạy trước hay sau authentication, routing và exception handling?

## Gợi ý tư duy

### Gợi ý 1

Request body là stream; đọc stream làm thay đổi position/state mà downstream consumer quan sát.

### Gợi ý 2

Buffering có cost. Đừng biến mọi request thành một bản copy lớn trong memory chỉ để giải quyết stream semantics.

### Gợi ý 3

Thiết kế audit phải xét pipeline ordering, rewind/buffering, request-size bounds và data-classification cùng lúc.

## Cấu trúc trả lời đề xuất

1. Làm rõ audit semantics và data sensitivity.
2. Giải thích request stream consumption và model-binding timing.
3. Chọn buffering/streaming strategy có giới hạn cho endpoint phù hợp.
4. Khôi phục stream position khi downstream cần đọc lại.
5. Không log raw sensitive payload mặc định.
6. Xử lý cancellation, oversized body và read failure.
7. Test middleware + model binding + large-body behavior.
8. Đo allocation, latency và audit failure rate.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Middleware chạy trước controller có thể consume request stream trước model binding.
- Không được giả định request body có thể đọc lại tùy ý nếu chưa có cơ chế buffering/rewind phù hợp.
- Sau khi middleware đọc, downstream phải nhận stream ở trạng thái phù hợp nếu còn cần body.
- Copy toàn bộ request vào memory không phải default an toàn với payload lớn/concurrency cao.
- Raw body logging có security/privacy risk và cần tránh hoặc redaction/data-classification nghiêm ngặt.

### Điểm cộng

- Chỉ áp dụng audit cho route/content type cần thiết.
- Dùng request-size limits và cancellation.
- Hash theo streaming/chunk nếu requirement chỉ cần raw-byte digest, tránh giữ toàn bộ payload thêm một bản khi thiết kế cho phép.
- Phân biệt audit availability với request availability: audit sink failure không nhất thiết phải làm business request fail, tùy compliance requirement.

### Senior+

- Nhận ra canonical JSON hash và raw-byte hash có semantics khác nhau.
- Đề xuất threat model cho audit logs: access control, retention, tamper evidence và correlation ID.
- Benchmark dưới concurrency thay vì chỉ test một request 20 MB.

## Hướng giải quyết tham khảo

Tôi sẽ xác nhận trước hash cần đại diện cho raw HTTP payload hay business object. Nếu middleware cần đọc body trước model binding, phải dùng cơ chế cho phép downstream đọc lại và đưa stream về position phù hợp. Tuy nhiên tôi không mặc định materialize toàn bộ body thành `string` hoặc `MemoryStream` cho mọi request.

Nếu chỉ cần digest raw bytes, tôi ưu tiên xử lý stream theo chunk trong phạm vi buffering strategy được hỗ trợ, có giới hạn kích thước và chỉ bật cho endpoint/content type cần audit. Sau khi đọc, phải rewind khi stream hỗ trợ theo cơ chế đã thiết lập trước khi gọi `_next`. Với payload rất lớn hoặc file upload, có thể cần một design riêng thay vì audit middleware chung.

Tôi không log raw request body để debug production nếu có khả năng chứa token, PII hoặc secrets. Audit record nên chứa request ID/correlation ID, route, authenticated subject phù hợp, hash, content length, timestamp và outcome; dữ liệu nhạy cảm chỉ được ghi nếu policy thực sự yêu cầu và có bảo vệ tương ứng.

Testing gồm integration test gửi JSON qua middleware và xác nhận controller vẫn bind đúng, test body rỗng/invalid JSON, oversized payload, cancellation và concurrency/load với payload lớn. Telemetry theo dõi request latency p95/p99, allocation/memory, audit processing duration/failure, rejected body size và correlation giữa audit record với request.

## Mẫu trả lời trong phỏng vấn

“Em nghi ngờ middleware đang consume `Request.Body` trước model binding. Body là stream nên nếu đọc đến cuối rồi gọi `_next` mà không thiết lập cơ chế đọc lại và rewind đúng, controller có thể thấy EOF. Em sẽ không chữa bằng cách copy mọi body sang memory vì payload có thể 20 MB và concurrency cao.

Em sẽ làm rõ audit cần raw-byte hash hay business-level hash, giới hạn endpoint và size, dùng buffering/streaming phù hợp rồi đảm bảo downstream đọc được body. Em cũng không log raw payload mặc định vì audit có thể biến thành nơi chứa PII/secrets.

Em sẽ chứng minh bằng integration test xuyên middleware-controller và load test để đo allocation, memory, p99. Mục tiêu là đúng stream semantics, bounded resource usage và audit data tối thiểu.”

## Câu hỏi đào sâu

1. Nếu compliance yêu cầu hash chính xác raw bytes nhưng body có thể 500 MB, bạn thay đổi design thế nào?
2. Nếu middleware audit sink bị timeout, request business có nên fail không? Điều kiện nào quyết định?
3. Tôi muốn đặt middleware này đầu tiên trong pipeline để chắc chắn bắt mọi request; bạn phản biện những rủi ro nào?

## Lỗi trả lời thường gặp

- Chỉ nói “set Position = 0” mà không xét stream có hỗ trợ seek/buffering hay không.
- Materialize mọi request thành `string`.
- Log raw body để debug mà bỏ qua secrets/PII.
- Không xét middleware ordering.
- Không test concurrency và payload lớn.

## Thang điểm 0–10

- **0–2:** Chỉ nhận ra body bị đọc hai lần.
- **3–4:** Biết rewind/buffering nhưng thiếu resource/security reasoning.
- **5–6:** Giải thích pipeline đúng và có bounded implementation/test.
- **7–8:** Có streaming, data classification, failure behavior và telemetry.
- **9–10:** Kết nối stream semantics, middleware architecture, security/compliance và performance thành design có điều kiện rõ ràng.

# Câu 2 — PostgreSQL API chậm dần dù CPU database thấp: connection pool hay transaction bị giữ quá lâu?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** PostgreSQL, ASP.NET Core, EF Core, connection pooling, transactions, locking, dependency telemetry, production incident reasoning

## Bối cảnh

Một approval platform dùng ASP.NET Core, EF Core và PostgreSQL. Sau khi traffic tăng khoảng 2 lần, API `POST /approvals/{id}/submit` có p99 từ dưới 800 ms lên 12–20 giây. CPU PostgreSQL vẫn dưới 45%, query trung bình nhìn riêng không quá chậm, nhưng application instances bắt đầu có nhiều requests chờ lâu rồi timeout.

Release gần đây thêm transaction bao quanh việc cập nhật approval, ghi audit record và gọi một external compliance API. Team chưa biết external call có đang diễn ra trong lúc database transaction/connection vẫn được giữ hay không. Một số dashboards chỉ hiển thị SQL duration, chưa có pool wait hoặc transaction age.

Một developer đề xuất tăng maximum pool size; người khác muốn tăng database CPU tier.

## Câu hỏi chính

Bạn sẽ xử lý incident theo impact → stabilization → evidence → competing hypotheses → root cause → remediation như thế nào? Hãy phân tích connection-pool exhaustion, long-lived transactions, database locking và external dependency latency; nêu cách chứng minh từng giả thuyết trước khi tăng pool/database capacity.

## Câu hỏi làm rõ nên cân nhắc

1. Transaction bắt đầu/kết thúc chính xác ở đâu so với external compliance call?
2. Pool configuration, concurrent requests và số application instances hiện tại là bao nhiêu?
3. Có requests chờ lấy connection hay đang chờ lock/query/dependency?
4. Transaction age, lock waits và blocked sessions trong PostgreSQL có tăng không?
5. Compliance call có timeout, retry và latency distribution như thế nào?

## Gợi ý tư duy

### Gợi ý 1

CPU database thấp không loại trừ saturation ở một resource khác như connection pool hoặc locks.

### Gợi ý 2

Một connection bị giữ trong transaction khi chờ network có thể làm throughput giảm dù SQL statements riêng lẻ nhanh.

### Gợi ý 3

Correlate request trace thành các pha: pool acquisition → SQL/transaction → external dependency → commit. Đừng chỉ nhìn query average.

## Cấu trúc trả lời đề xuất

1. Định lượng impact và endpoint/business flow bị ảnh hưởng.
2. Stabilize bằng traffic controls/timeouts/degraded behavior phù hợp.
3. Thu pool, transaction, lock và external dependency evidence.
4. Lập hypotheses riêng cho pool exhaustion, locking, slow dependency và database capacity.
5. Correlate theo distributed trace/request ID.
6. Xác minh transaction boundary trong code và runtime.
7. Sửa transaction/external-call design dựa trên consistency requirement.
8. Chỉ tune pool sau khi hiểu database capacity và concurrency.
9. Load/failure test.
10. Thêm alerts cho pool wait, transaction age, lock wait và dependency p99.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CPU thấp không chứng minh database không phải một phần bottleneck, nhưng cũng không biện minh scale CPU ngay.
- Connection pool là bounded resource; tăng pool có thể chuyển pressure sang database thay vì sửa nguyên nhân.
- Không nên giữ database transaction qua slow external network call trừ khi requirement/architecture thực sự buộc và hiểu failure semantics.
- Phải kiểm tra lock/blocking/transaction age cùng pool acquisition wait.
- External call retry/timeout có thể khuếch đại thời gian giữ resource.

### Điểm cộng

- Phân biệt database transaction atomicity với distributed side effect; không giả vờ một local DB transaction có thể rollback external API.
- Đề xuất state machine/outbox/async workflow khi business cho phép thay vì giữ transaction mở qua network.
- Có concurrency limits/bulkhead cho compliance dependency nếu nó là bounded external resource.
- Xem pool sizing theo tổng instances × pool size, không theo một process riêng lẻ.

### Senior+

- Nhận ra tăng pool có thể tăng lock contention và overload database.
- Thiết kế recovery/reconciliation nếu external compliance call thành công nhưng local state update/commit thất bại.
- Tách stabilization ngắn hạn khỏi architecture fix dài hạn.

## Hướng giải quyết tham khảo

Đầu tiên tôi xác định user impact và giảm amplification: kiểm tra retry, timeout, có thể giới hạn concurrency cho submit nếu compliance dependency đang degrade. Tôi không tăng pool ngay vì nếu mỗi request giữ connection 15 giây, pool lớn hơn chỉ cho phép nhiều transaction dài hơn cùng lúc.

Tôi cần trace một request thành các đoạn thời gian. Ở application, đo thời gian chờ lấy connection nếu provider/telemetry cho phép, EF/SQL dependency duration và compliance dependency duration. Ở PostgreSQL, xem active sessions, transaction age, lock waits, blocked sessions và query state. Trong code, xác định transaction scope có bao quanh HTTP call không.

Nếu external call nằm trong transaction, tôi hỏi consistency requirement. Nếu business cho phép workflow nhiều bước, tôi ưu tiên commit local state/outbox rồi xử lý compliance ngoài transaction với idempotency, retry và reconciliation. Nếu phải gọi synchronously trước khi quyết định local state, vẫn nên tránh giữ DB connection/transaction trong thời gian network không cần thiết và thiết kế compensation/reconciliation cho partial failure.

Tôi chỉ tăng pool khi evidence cho thấy workload hợp lệ cần concurrency cao hơn và database có headroom về connections, memory, locks và throughput. Pool sizing phải xét tổng số instances. Scale database cũng chỉ hợp lý nếu metrics chứng minh database resource thực sự saturated.

Sau fix, tôi load-test với compliance latency injection, timeout và retry. Monitoring gồm request p99, pool acquisition/wait, active/idle connections, transaction age, lock waits, external dependency p95/p99/error rate và business submit success.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không scale CPU hoặc pool chỉ vì request chậm. CPU database thấp nhưng pool hoặc locks vẫn có thể saturated. Release vừa thêm external call trong flow transaction nên em sẽ trace request theo pha và kiểm tra transaction scope.

Nếu connection/transaction đang bị giữ khi chờ compliance API, một dependency 10 giây có thể chiếm connection 10 giây, làm pool cạn và tạo queueing. Tăng pool có thể chỉ đẩy thêm concurrent transactions xuống PostgreSQL và làm lock contention tệ hơn.

Em sẽ thu pool wait, active connections, transaction age, lock waits và dependency latency. Nếu business cho phép, em tách external side effect khỏi local transaction bằng workflow/outbox/idempotency; nếu không, em vẫn thu hẹp transaction boundary tối đa và có reconciliation cho partial failure. Sau đó load-test với dependency delay và monitor pool/locks/p99.”

## Câu hỏi đào sâu

1. Nếu compliance API bắt buộc phải thành công trước khi approval được coi là submitted, bạn thiết kế state transition thế nào mà không giả định distributed transaction?
2. Nếu tăng pool từ 100 lên 500 làm p99 giảm ngay, điều đó có chứng minh pool size 500 là fix đúng không?
3. Nếu PostgreSQL không có lock waits đáng kể nhưng pool vẫn cạn, bạn mở rộng hypotheses theo hướng nào?

## Lỗi trả lời thường gặp

- Tăng pool như giải pháp đầu tiên.
- Nhìn CPU thấp rồi loại database khỏi investigation.
- Giữ transaction qua external HTTP call mà không phân tích failure semantics.
- Không xét tổng connection count của tất cả instances.
- Không test dependency latency/retry dưới load.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất tăng pool/CPU.
- **3–4:** Nhận ra transaction dài nhưng thiếu evidence và recovery design.
- **5–6:** Có pool/lock/dependency investigation đúng và transaction-boundary fix.
- **7–8:** Có partial-failure, idempotency/reconciliation, load test và telemetry.
- **9–10:** Phân tích resource queueing, database concurrency và distributed side effects thành một incident response + architecture fix hoàn chỉnh.

# Câu 3 — Thiết kế nền tảng Playwright E2E cho CI: test nhanh nhưng không flaky và không phá dữ liệu của nhau

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** Playwright, E2E testing, CI/CD, test isolation, test data, parallel execution, observability, release quality, architecture trade-offs

## Bối cảnh

Một team phát triển ASP.NET Core + React e-commerce portal. Hiện có khoảng 25 Playwright tests chạy tuần tự trên shared QA environment và mất 35 phút. Team muốn tăng lên 250–400 E2E tests, chạy trong pull request và trước production release.

Hiện trạng:

- nhiều tests dùng chung một account và cùng catalog/order data;
- tests đôi lúc fail vì test trước thay đổi state;
- external payment/review providers không ổn định;
- QA environment cũng được manual testers sử dụng;
- team muốn bật parallel workers để giảm thời gian xuống dưới 15 phút;
- pipeline có thể dùng Jenkins hoặc Azure Repos/CI hiện có;
- chưa có strategy rõ cho seed/reset data, traces, screenshots, retries hoặc quarantine.

Một đề xuất là “retry failed test 5 lần để hết flaky”. Đề xuất khác muốn mock toàn bộ backend để E2E chạy nhanh.

## Câu hỏi chính

Bạn sẽ thiết kế test platform và pipeline như thế nào để 250–400 Playwright tests có thể chạy nhanh, deterministic đủ để làm release signal, nhưng vẫn kiểm thử được integration thật? Hãy phân tích test pyramid/scope, environment, test-data ownership, parallelism, external dependencies, retries, artifacts, flaky-test policy, security và chi phí vận hành.

## Câu hỏi làm rõ nên cân nhắc

1. Những user journeys nào thực sự cần E2E thay vì integration/API/unit tests?
2. Có thể tạo ephemeral environment/database per run hay chỉ có shared QA?
3. External providers có sandbox/stub contract chính thức không?
4. Release gate cần độ tin cậy và thời gian tối đa bao nhiêu?
5. Test data có chứa production-derived PII hay secrets không?

## Gợi ý tư duy

### Gợi ý 1

400 E2E tests không tự động đồng nghĩa chất lượng cao. Trước hết xác định đúng layer test cho từng risk.

### Gợi ý 2

Parallelism chỉ an toàn khi data và side effects được isolate hoặc partition rõ ràng.

### Gợi ý 3

Retry có thể là diagnostic aid nhưng nếu dùng để biến red thành green thì pipeline mất giá trị làm release signal.

## Cấu trúc trả lời đề xuất

1. Xác định critical journeys và release risks.
2. Chuyển logic không cần browser xuống unit/integration/API tests.
3. Chọn environment strategy: ephemeral ưu tiên khi khả thi, shared có namespace/isolation nếu bắt buộc.
4. Thiết kế per-run/per-worker test-data ownership.
5. Phân loại external dependencies: real sandbox, controlled stub, contract test.
6. Bật parallelism sau khi isolation được chứng minh.
7. Thiết kế retries/flaky quarantine có policy.
8. Thu trace/video/screenshot/network/server correlation artifacts khi fail.
9. Chia PR suite và broader pre-release/nightly suite theo risk.
10. Theo dõi runtime, flake rate và defect escape để điều chỉnh portfolio.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không biến mọi behavior thành E2E browser test.
- Shared mutable test data là nguyên nhân lớn của nondeterminism khi parallel.
- Mỗi run/worker cần data namespace hoặc lifecycle rõ ràng.
- Retry không được che flaky tests vô thời hạn.
- Mock toàn bộ backend làm mất giá trị E2E integration; cần chọn seam phù hợp.
- Failure artifacts phải đủ để debug CI mà không cần rerun thủ công ngay.

### Điểm cộng

- Dùng API/setup helpers để tạo preconditions nhanh thay vì thao tác UI cho mọi setup.
- Unique IDs/run IDs cho accounts/orders và cleanup có idempotency.
- Tách provider sandbox tests khỏi deterministic core PR suite nếu provider availability không thể kiểm soát.
- Contract/integration tests bảo vệ seam với external provider khi E2E dùng stub.
- Playwright trace/screenshot/video chỉ giữ theo policy phù hợp để cân bằng storage và debugging value.

### Senior+

- Thiết kế test portfolio theo expected signal/cost: small deterministic PR gate, broader release suite, targeted real-provider checks.
- Theo dõi flake rate theo test/root cause và cấm “retry inflation” biến flaky thành pass.
- Xem test platform như production-like system: ownership, observability, capacity, security, lifecycle và cost.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng cách bật 20 workers cho 400 tests. Trước tiên review portfolio: business logic, validation và API behavior nên được kiểm ở unit/integration/API layer; Playwright tập trung vào critical browser journeys, routing/authentication, frontend-backend integration và một số high-value failure flows.

Về environment, lựa chọn tốt nhất nếu chi phí cho phép là environment/database tách theo run hoặc namespace mạnh. Nếu bắt buộc dùng shared QA, mỗi run/worker phải tạo dữ liệu riêng bằng unique prefix/ID, không dùng chung account/order mutable state, và cleanup phải an toàn/idempotent. Manual QA traffic cần được tách khỏi automated test data càng nhiều càng tốt.

Tôi dùng API/setup fixtures để tạo account/catalog/order preconditions nhanh, rồi UI test chỉ thao tác phần cần browser verification. Parallelism được tăng dần sau khi chạy stress/repeat chứng minh tests độc lập.

Với external payment/review providers, core PR suite nên deterministic: dùng controlled test double ở boundary khi mục tiêu không phải kiểm provider thật, đồng thời có contract/integration tests và một suite nhỏ chạy với provider sandbox để phát hiện integration drift. Không mock backend application đang được kiểm thử nếu mục tiêu là E2E full-stack.

Retries chỉ ở mức nhỏ và có mục đích thu thêm signal; một test pass sau retry vẫn phải được ghi nhận là flaky, có owner và SLA sửa/quarantine. Không cho retry 5 lần rồi coi green như bình thường.

Khi fail, pipeline lưu Playwright trace, screenshot/video theo policy, console/network errors, application correlation ID và server logs liên quan. Tôi chia pipeline: PR gate dưới target thời gian với critical deterministic tests; broader suite trước release hoặc theo lịch; real-provider checks riêng nếu availability thấp.

Metrics của platform gồm duration p50/p95, queue time, pass rate first-attempt, retry-pass rate, flake rate, top flaky tests, setup failures và defect escape. Những metrics này quyết định nên thêm worker, sửa test hay chuyển coverage xuống layer rẻ hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không coi mục tiêu là chạy 400 browser tests thật nhanh; mục tiêu là release signal đáng tin trong dưới 15 phút. Em sẽ phân loại coverage trước: logic/API xuống unit và integration, Playwright giữ critical browser journeys.

Sau đó giải quyết isolation trước parallelism. Mỗi run/worker có test-data namespace riêng, setup qua API và cleanup idempotent. Nếu có thể em dùng ephemeral environment; nếu shared QA thì automation không dùng chung mutable account/order với manual QA.

External provider được tách theo mục tiêu: core PR suite dùng controlled seam để deterministic, nhưng vẫn có contract/integration và một nhóm sandbox tests để kiểm integration thật. Retry chỉ giúp diagnostic, không được biến flaky thành green; pass-after-retry vẫn được tracking.

Khi fail em cần trace, screenshot/video khi phù hợp, network/console và correlation với backend logs. Em sẽ theo dõi first-pass rate, flake rate và runtime để quyết định tăng workers hay sửa architecture test. Một suite nhanh nhưng retry liên tục không phải release gate tốt.”

## Câu hỏi đào sâu

1. Nếu organization không cho tạo ephemeral environments, bạn thiết kế isolation trên shared QA cụ thể thế nào?
2. Tôi muốn mọi PR chạy real payment sandbox để “test thật nhất”; bạn phản biện reliability/cost và đề xuất coverage nào thay thế?
3. Nếu 5% tests pass ở lần retry thứ hai nhưng không tìm được root cause trong một tuần, pipeline nên xử lý chúng thế nào?

## Lỗi trả lời thường gặp

- Bật parallel workers trước khi isolate test data.
- Retry nhiều lần để che flakiness.
- Mock toàn bộ backend rồi gọi đó là E2E.
- Dùng UI để setup mọi precondition làm suite chậm và fragile.
- Không thu artifacts/correlation nên CI failure khó điều tra.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất thêm workers/retries.
- **3–4:** Có test isolation nhưng thiếu portfolio/external dependency strategy.
- **5–6:** Có data ownership, parallelism, artifacts và flaky policy.
- **7–8:** Có layered coverage, controlled external seams, release gates và metrics.
- **9–10:** Thiết kế test platform như một engineering system cân bằng signal, determinism, integration realism, runtime và operational cost.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- ASP.NET Core request body là stream trong pipeline; middleware phải tôn trọng consumption, buffering, downstream model binding và resource/security constraints.
- API latency có thể đến từ queueing trên connection pool hoặc long-lived transaction dù database CPU không cao; cần đo resource wait thay vì chỉ query duration.
- Database transaction không biến external HTTP side effect thành atomic operation; transaction boundaries phải đi cùng partial-failure/reconciliation design.
- Playwright parallelism chỉ tạo tốc độ khi test-data ownership và dependency isolation đủ tốt; retries không được dùng để che flaky tests.

## Mẫu tư duy cần nhớ

1. **Hiểu lifecycle của resource trước khi dùng lại:** stream, connection và transaction đều có ownership/state hữu hạn.
2. **Đo thời gian chờ, không chỉ thời gian thực thi:** queue/pool/lock wait thường giải thích p99 tốt hơn average query time.
3. **Không giữ scarce resource trong lúc chờ dependency nếu không cần thiết.**
4. **Isolation trước parallelism:** concurrency phóng đại shared-state bugs.
5. **Release signal phải đáng tin:** retry, mock và test count không được thay thế deterministic engineering.
