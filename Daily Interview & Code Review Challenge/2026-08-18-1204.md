# Câu 1 — EF Core Change Tracker và memory leak giả trong batch processing

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 10 phút  
**Kỹ năng được đánh giá:** EF Core internals, memory profiling, production debugging

## Bối cảnh
Một ASP.NET Core API dùng EF Core xử lý báo cáo cuối ngày. Khi dữ liệu tăng lên vài triệu bản ghi, worker chạy lâu hơn, memory tăng dần và container bị restart.

## Câu hỏi chính
Giải thích cơ chế bên trong của EF Core tracking, materialization và DbContext lifecycle. Vì sao cùng một truy vấn đọc dữ liệu có thể tạo ra khác biệt lớn về memory? Bạn sẽ kiểm chứng giả thuyết như thế nào?

## Câu hỏi làm rõ nên cân nhắc
- Đây là read-only hay cần update entity?
- DbContext được tạo theo request hay dùng lâu dài?
- Query có Include nhiều navigation không?
- Memory tăng theo batch hay theo thời gian?

## Gợi ý tư duy
- Gợi ý 1: Xem object lifecycle và state management.
- Gợi ý 2: Phân tích Change Tracker và allocation.
- Gợi ý 3: Cân nhắc projection, AsNoTracking và batch strategy.

## Cấu trúc trả lời đề xuất
1. Làm rõ workload.
2. Giải thích cơ chế runtime.
3. Đưa ra giả thuyết.
4. Đề xuất cách đo.
5. Chọn giải pháp và trade-off.

## Hướng giải quyết tham khảo
Với read-only workload, tracking không cần thiết có thể gây tăng allocation do EntityEntry và Change Tracker giữ state. Cần dùng projection DTO hoặc AsNoTracking khi phù hợp, kiểm tra bằng memory profiler, metrics và database query analysis.

# Câu 2 — Thiết kế notification platform đa kênh

**Loại câu hỏi:** System design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Architecture, reliability, scalability

## Bối cảnh
Một hệ thống cần gửi Email, Teams message và push notification cho nhiều tenant. MVP đang chạy ASP.NET Core modular monolith với background jobs.

## Câu hỏi chính
Thiết kế hệ thống để xử lý retry, idempotency, provider failure, monitoring và mở rộng trong tương lai như thế nào?

## Câu hỏi làm rõ nên cân nhắc
- SLA delivery là gì?
- Có chấp nhận gửi trùng không?
- Có cần ordering không?
- Provider có rate limit không?

## Gợi ý tư duy
- Gợi ý 1: Bắt đầu từ business guarantee.
- Gợi ý 2: Thiết kế trạng thái delivery.
- Gợi ý 3: Failure recovery quan trọng hơn scale ban đầu.

## Hướng giải quyết tham khảo
Dùng modular monolith với domain notification, provider adapter, background worker, outbox/idempotency key, retry policy có giới hạn, logs, metrics và tracing. Chỉ tách service khi có lý do rõ ràng.

# Câu 3 — AI agent hỗ trợ code review

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** Context engineering, AI reliability

## Bối cảnh
Team muốn tạo AI agent review pull request C#/.NET. Agent có repository access, coding rules, test tools và issue context.

## Câu hỏi chính
Thiết kế workflow AI agent như thế nào để feedback hữu ích nhưng tránh hallucination và rủi ro bảo mật?

## Gợi ý tư duy
- Gợi ý 1: Không đưa toàn bộ context một cách tùy tiện.
- Gợi ý 2: Tool permission và validation rất quan trọng.
- Gợi ý 3: AI output cần được kiểm chứng bằng deterministic tools.

## Hướng giải quyết tham khảo
Cần kiểm soát context, permission boundary, structured output, compiler/test validation, human approval, audit logs và quality evaluation.

# Tổng kết hôm nay

- Hiểu runtime behavior trước khi tối ưu.

## Mẫu tư duy cần nhớ
- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of architecture.
