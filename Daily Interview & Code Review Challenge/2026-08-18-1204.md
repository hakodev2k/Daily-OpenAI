# Câu 1 — EF Core tracking gây tăng memory khi xử lý batch lớn

**Loại câu hỏi:** Internal mechanism trong production scenario  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 10 phút  
**Kỹ năng được đánh giá:** EF Core internals, memory analysis, performance tuning

## Bối cảnh
Một ASP.NET Core API chạy .NET 8 dùng EF Core xử lý báo cáo cuối ngày. Sau khi dữ liệu tăng lên vài triệu bản ghi, service bắt đầu tăng memory liên tục và đôi lúc bị restart.

Developer nhận thấy query lấy dữ liệu bằng repository thông thường thay vì projection.

## Câu hỏi chính
EF Core đang làm gì bên trong khi tracking entity? Vì sao cùng một câu query có thể gây khác biệt lớn về memory? Bạn sẽ xác minh giả thuyết như thế nào?

## Câu hỏi làm rõ nên cân nhắc
- Query này chỉ đọc hay có cập nhật dữ liệu?
- Kích thước batch và thời gian chạy là bao nhiêu?
- Có navigation property được load không?
- Memory tăng theo request hay tăng liên tục?

## Gợi ý tư duy
- Gợi ý 1: Xem lifecycle của DbContext và entity state.
- Gợi ý 2: Phân tích Change Tracker, materialization và allocation.
- Gợi ý 3: Với read-only workload cần cân nhắc projection và AsNoTracking.

## Hướng giải quyết tham khảo
EF Core tracking giữ entity trong Change Tracker để theo dõi thay đổi. Với batch lớn, số lượng object và metadata tăng mạnh. Cần xác định read/write requirement, dùng projection DTO hoặc AsNoTracking cho truy vấn chỉ đọc, kiểm tra bằng profiling, SQL logs và memory counters.

# Câu 2 — Thiết kế hệ thống xử lý notification đa kênh

**Loại câu hỏi:** System design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Architecture, scalability, reliability

## Bối cảnh
Công ty cần xây dựng hệ thống gửi Email, Teams notification và mobile push cho hàng triệu sự kiện. MVP hiện tại dùng ASP.NET Core modular monolith và background jobs.

## Câu hỏi chính
Bạn thiết kế hệ thống này như thế nào để đảm bảo retry, idempotency, monitoring và khả năng mở rộng?

## Câu hỏi làm rõ nên cân nhắc
- SLA gửi notification là bao lâu?
- Có cần đảm bảo thứ tự gửi không?
- Provider lỗi có retry thế nào?
- Người dùng có thể nhận trùng không?

## Gợi ý tư duy
- Gợi ý 1: Bắt đầu từ business requirement.
- Gợi ý 2: Xem queue, retry, trạng thái delivery.
- Gợi ý 3: Thiết kế failure recovery trước khi scale.

## Hướng giải quyết tham khảo
Bắt đầu bằng modular monolith với notification domain, persistence, worker và provider adapters. Dùng background processing, outbox/idempotency key, retry policy có kiểm soát, logging, tracing và metrics. Chỉ tách service khi có nhu cầu scale hoặc ownership rõ ràng.

# Câu 3 — AI code review agent trong workflow phát triển

**Loại câu hỏi:** AI engineering  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** Context engineering, AI safety, automation design

## Bối cảnh
Team muốn tạo agent hỗ trợ review pull request C#/.NET. Agent có thể đọc repository, issue, coding rules và chạy tool kiểm tra.

## Câu hỏi chính
Bạn thiết kế agent workflow như thế nào để tránh hallucination và đảm bảo feedback có giá trị?

## Hướng giải quyết tham khảo
Cần xác định context cần cung cấp, permission boundary, tool access, structured output, validation bằng compiler/test/linter, human approval trước merge và đánh giá chất lượng bằng feedback thực tế.

# Tổng kết hôm nay

## Kiến thức trọng tâm
- Hiểu cơ chế runtime trước khi tối ưu.
- Thiết kế failure handling cùng với business flow.
- AI system cần deterministic validation, không chỉ gọi model.

## Mẫu tư duy cần nhớ
- Clarify before designing.
- Measure before optimizing.
- Design retries together with idempotency.
- Treat observability as part of architecture.
