# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý yêu cầu offboarding nhân viên. Job cập nhật trạng thái trong PostgreSQL, gọi một external mail service để cấu hình forwarding rồi đánh dấu hoàn tất. Production chạy nhiều Hangfire workers trên nhiều instance.

Gần đây một số nhân viên nhận thao tác forwarding hai lần, một số record ở trạng thái `Processing` mãi sau khi external API timeout. Khi retry xảy ra, đôi lúc cùng một request được xử lý đồng thời. External API không đảm bảo idempotency. Không được phép mất yêu cầu offboarding.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IMailService _mailService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IMailService mailService,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _mailService = mailService;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync(Guid requestId)
    {
        var request = await _db.OffboardingRequests
            .FirstOrDefaultAsync(x => x.Id == requestId);

        if (request == null || request.Status == "Completed")
            return;

        request.Status = "Processing";
        request.AttemptCount++;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Processing offboarding {RequestId} for {Email}",
            request.Id,
            request.EmployeeEmail);

        await _mailService.ConfigureForwardingAsync(
            request.EmployeeEmail,
            request.TargetEmail);

        request.Status = "Completed";
        request.CompletedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();
    }
}
```

## Kết quả code review tham khảo

### 1. Check-then-act không atomic

- **Problem:** Nhiều worker có thể cùng đọc cùng request trước khi worker nào commit trạng thái.
- **Why:** `FirstOrDefaultAsync()` và cập nhật `Processing` không tạo quyền sở hữu độc quyền cho toàn workflow.
- **Production impact:** External side effect có thể chạy nhiều lần.
- **Severity:** Critical.
- **Recommended fix:** Claim request bằng atomic conditional update/optimistic concurrency hoặc cơ chế lock phù hợp; database phải quyết định worker nào sở hữu attempt.

### 2. Không có idempotency cho external side effect

- **Problem:** Retry có thể gọi `ConfigureForwardingAsync` lại.
- **Why:** Job chỉ kiểm tra local `Completed`; external operation không gắn idempotency key.
- **Production impact:** Duplicate side effects hoặc trạng thái external không xác định.
- **Severity:** Critical.
- **Recommended fix:** Nếu provider hỗ trợ, truyền stable idempotency key theo `requestId`. Nếu không, thiết kế reconciliation/read-before-write hoặc adapter có semantic idempotent theo desired state.

### 3. Dual-write inconsistency

- **Problem:** External call có thể thành công nhưng DB update `Completed` thất bại.
- **Why:** Database transaction không thể bao trùm arbitrary remote side effect.
- **Production impact:** Retry thực hiện lại side effect đã thành công.
- **Severity:** High.
- **Recommended fix:** Mô hình state machine có attempt/outcome, idempotent external operation và reconciliation. Không giả định transaction DB giải quyết distributed transaction.

### 4. `Processing` có thể bị kẹt

- **Problem:** Exception sau lần save đầu khiến status giữ nguyên `Processing`.
- **Why:** Không có lease expiry, `LastAttemptAt`, recovery state hoặc finally/failure transition đáng tin cậy.
- **Production impact:** Request có thể bị bỏ qua bởi logic khác hoặc khó vận hành.
- **Severity:** High.
- **Recommended fix:** Dùng lease có expiry/owner token hoặc trạng thái retryable rõ ràng; có recovery/reconciliation job.

### 5. Không truyền `CancellationToken`

- **Problem:** Database và external I/O không nhận cancellation token.
- **Why:** Signature không hỗ trợ cooperative cancellation.
- **Production impact:** Shutdown/deployment hoặc timeout có thể kéo dài work và tăng overlap.
- **Severity:** Medium.
- **Recommended fix:** Truyền cancellation token phù hợp xuống EF Core và HTTP layer; phân biệt cancellation với business failure.

### 6. Retry policy thiếu phân loại lỗi

- **Problem:** Mọi exception có thể bị retry theo cùng chiến lược.
- **Why:** Không phân biệt transient, permanent, validation hoặc authorization failures.
- **Production impact:** Retry storm, tăng tải external service và che giấu lỗi permanent.
- **Severity:** Medium.
- **Recommended fix:** Phân loại lỗi; retry transient với backoff/jitter; permanent failure chuyển trạng thái cần xử lý.

### 7. Logging chứa email người dùng

- **Problem:** Email được ghi trực tiếp vào log.
- **Why:** Log dùng raw business identifier.
- **Production impact:** Tăng phạm vi dữ liệu nhạy cảm/PII trong observability system.
- **Severity:** Medium.
- **Recommended fix:** Log request ID và tenant/correlation ID; mask/hash email khi thực sự cần.

### 8. Thiếu telemetry về attempt và outcome

- **Problem:** Chỉ có một log bắt đầu xử lý.
- **Why:** Không ghi latency, external outcome, retry reason hoặc state transition.
- **Production impact:** Khó xác định duplicate, stuck job và dependency degradation.
- **Severity:** Low.
- **Recommended fix:** Structured logs, traces và counters theo outcome/retry/status.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa hướng thiết kế. `TryClaimAsync` phải được implement bằng conditional update atomic trong database và lease phải có thời hạn.

```csharp
public sealed class OffboardingJob
{
    private readonly IOffboardingRepository _repository;
    private readonly IMailService _mailService;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        IOffboardingRepository repository,
        IMailService mailService,
        ILogger<OffboardingJob> logger)
    {
        _repository = repository;
        _mailService = mailService;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ExecuteAsync(Guid requestId, CancellationToken cancellationToken)
    {
        var leaseId = Guid.NewGuid();
        var claimed = await _repository.TryClaimAsync(
            requestId,
            leaseId,
            DateTimeOffset.UtcNow.AddMinutes(5),
            cancellationToken);

        if (!claimed)
            return;

        var request = await _repository.GetAsync(requestId, cancellationToken);
        if (request is null || request.Status == OffboardingStatus.Completed)
            return;

        try
        {
            await _mailService.SetForwardingStateAsync(
                request.EmployeeEmail,
                request.TargetEmail,
                idempotencyKey: request.Id.ToString("N"),
                cancellationToken);

            await _repository.MarkCompletedAsync(
                request.Id,
                leaseId,
                DateTimeOffset.UtcNow,
                cancellationToken);
        }
        catch (OperationCanceledException) when (cancellationToken.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            await _repository.RecordFailureAsync(
                request.Id,
                leaseId,
                ex.GetType().Name,
                CancellationToken.None);

            _logger.LogError(ex,
                "Offboarding attempt failed for request {RequestId}",
                request.Id);
            throw;
        }
    }
}
```

Repository claim có thể tương đương một conditional update như `UPDATE ... WHERE Id = @id AND (...)`, kiểm tra affected rows bằng 1. Nếu external provider không hỗ trợ idempotency key, `SetForwardingStateAsync` nên hướng tới **desired-state semantics** thay vì một command kiểu “thực hiện thêm một lần”.

## Trade-offs

Atomic claim giảm concurrent execution nhưng không tự giải quyết crash sau external success. Distributed lock cũng không tạo exactly-once side effect và có failure modes riêng. Outbox rất hữu ích khi cần đảm bảo database change và message publication, nhưng không tự biến một remote API không-idempotent thành exactly-once. Với nghiệp vụ quan trọng, state machine + idempotency + reconciliation thường thực tế hơn việc cố tạo distributed transaction.

## Cách kiểm thử

1. **Concurrency test:** chạy 20 executions cùng `requestId`; xác minh chỉ một claim thành công và desired external state không bị áp dụng sai nhiều lần.
2. **Failure-path test:** external API thành công nhưng giả lập DB failure sau đó; retry phải hội tụ về trạng thái đúng.
3. **Transient failure test:** external API timeout hai lần rồi thành công; kiểm tra retry, attempt count và final state.
4. **Permanent failure test:** external trả validation/authorization failure; không retry vô hạn và có trạng thái vận hành rõ ràng.
5. **Lease recovery test:** worker chết sau claim; request được reclaim sau lease expiry mà không mất job.

## Quan sát trong production

Theo dõi structured logs với `RequestId`, `LeaseId`, attempt và outcome; trace span cho DB claim và external call; metrics `offboarding_started`, `completed`, `failed`, `retry`, `claim_conflict`, external latency; alert cho request ở trạng thái processing quá lease hoặc retry tăng đột biến. Dashboard nên cho phép đối chiếu local desired state với external actual state mà không log PII không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Nếu external provider hoàn toàn không hỗ trợ idempotency và cũng không có API đọc trạng thái hiện tại, bạn thay đổi business workflow thế nào?
2. Outbox pattern giải quyết phần nào của bài toán này và phần nào nó không giải quyết?
3. Khi nào bạn chọn optimistic concurrency thay vì distributed lock?

# Code Review Challenge 2 — API export báo cáo có lỗ hổng authorization và query không kiểm soát

**Chủ đề:** Authentication/authorization, input validation, EF Core query execution, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–8 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cho phép người quản lý export danh sách nhân viên. Người dùng đã đăng nhập bằng bearer token. Endpoint nhận `tenantId`, từ khóa tìm kiếm và số lượng record cần export.

Production ghi nhận một tenant có thể đoán ID tenant khác và nhận dữ liệu không thuộc phạm vi của mình. Khi `take` lớn, API tăng memory và latency mạnh. Security team cũng phát hiện response chứa nhiều trường hơn UI thực sự cần.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(AppDbContext db, ILogger<ReportsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("employees")]
    public async Task<IActionResult> ExportEmployees(
        Guid tenantId,
        string? search,
        int take = 5000)
    {
        var employees = await _db.Employees
            .Include(x => x.Manager)
            .Where(x => x.TenantId == tenantId)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(search))
        {
            employees = employees
                .Where(x => x.Name.Contains(search, StringComparison.OrdinalIgnoreCase)
                         || x.Email.Contains(search, StringComparison.OrdinalIgnoreCase))
                .ToList();
        }

        var result = employees
            .Take(take)
            .Select(x => new
            {
                x.Id,
                x.Name,
                x.Email,
                x.PersonalPhone,
                x.HomeAddress,
                ManagerEmail = x.Manager == null ? null : x.Manager.Email
            });

        _logger.LogInformation(
            "Tenant {TenantId} exported {Count} employees using search {Search}",
            tenantId,
            employees.Count,
            search);

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken object/tenant-level authorization

- **Problem:** Caller tự cung cấp `tenantId` nhưng endpoint chỉ yêu cầu authenticated user.
- **Why:** Không có policy/claim/membership check ràng buộc caller với tenant được truy cập.
- **Production impact:** Cross-tenant data exposure.
- **Severity:** Critical.
- **Recommended fix:** Resolve tenant scope từ trusted identity/context hoặc kiểm tra explicit tenant membership/permission trước query; defense-in-depth tại data access layer.

### 2. Sensitive data bị overexpose

- **Problem:** Response trả `PersonalPhone` và `HomeAddress` dù use case chỉ là report nhân viên thông thường.
- **Why:** Projection được thiết kế theo entity data thay vì least-data principle.
- **Production impact:** Tăng impact khi authorization bug hoặc response bị lưu/chia sẻ.
- **Severity:** High.
- **Recommended fix:** DTO tối thiểu theo use case và permission; field nhạy cảm cần quyền riêng nếu business thực sự yêu cầu.

### 3. Materialize toàn bộ tenant trước filtering và limiting

- **Problem:** `ToListAsync()` chạy trước search và `Take`.
- **Why:** Các thao tác tiếp theo chạy trong memory.
- **Production impact:** DB/network transfer, allocation, GC và latency tăng theo tenant size.
- **Severity:** High.
- **Recommended fix:** Giữ `IQueryable` tới cuối; filter, order, limit và projection trong database trước `ToListAsync`.

### 4. `take` không được giới hạn

- **Problem:** Client có thể truyền giá trị rất lớn hoặc giá trị không hợp lệ.
- **Why:** Không có validation/server-side maximum.
- **Production impact:** Resource exhaustion và endpoint dễ bị abuse.
- **Severity:** High.
- **Recommended fix:** Clamp/validate `take`, dùng pagination hoặc async export job cho dataset lớn.

### 5. `Include` lấy nhiều dữ liệu hơn cần thiết

- **Problem:** Load full employee và manager entities rồi mới project.
- **Why:** Query không project trực tiếp DTO.
- **Production impact:** Tracking/allocation/data transfer không cần thiết.
- **Severity:** Medium.
- **Recommended fix:** Projection trực tiếp các cột cần thiết; với read-only query có thể dùng `AsNoTracking` khi phù hợp.

### 6. Search chạy client-side

- **Problem:** Search được thực hiện sau materialization.
- **Why:** LINQ lúc này là LINQ-to-Objects.
- **Production impact:** CPU/memory app tăng và DB không thể tối ưu query.
- **Severity:** Medium.
- **Recommended fix:** Xây dựng expression translatable theo provider và kiểm tra query plan/index phù hợp. Cách search case-insensitive cần cân nhắc semantics/collation của SQL Server hoặc PostgreSQL thay vì giả định một implementation giống nhau.

### 7. Log raw search term

- **Problem:** User-controlled search text được ghi nguyên văn.
- **Why:** Logging không áp dụng data minimization.
- **Production impact:** PII/secrets vô tình đi vào log; log cardinality và privacy risk tăng.
- **Severity:** Medium.
- **Recommended fix:** Không log raw search trừ khi có nhu cầu rõ ràng; ưu tiên flag/length/hash hoặc sanitized diagnostic data.

### 8. Thiếu cancellation token

- **Problem:** Request abort không hủy DB operation.
- **Why:** Không truyền `HttpContext.RequestAborted`/`CancellationToken`.
- **Production impact:** Work tiếp tục sau khi client bỏ kết nối, đặc biệt tốn kém với export lớn.
- **Severity:** Low.
- **Recommended fix:** Nhận và truyền cancellation token vào async database call.

## Phiên bản code đề xuất

```csharp
public sealed record EmployeeExportRow(
    Guid Id,
    string Name,
    string Email,
    string? ManagerEmail);

[ApiController]
[Route("api/reports")]
public sealed class ReportsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<ReportsController> _logger;

    public ReportsController(
        AppDbContext db,
        ITenantAccessService tenantAccess,
        ILogger<ReportsController> logger)
    {
        _db = db;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [Authorize]
    [HttpGet("employees")]
    public async Task<ActionResult<IReadOnlyList<EmployeeExportRow>>> ExportEmployees(
        Guid tenantId,
        string? search,
        int take = 500,
        CancellationToken cancellationToken = default)
    {
        if (!await _tenantAccess.CanReadEmployeesAsync(
                User, tenantId, cancellationToken))
            return Forbid();

        if (take is < 1 or > 1000)
            return BadRequest("take must be between 1 and 1000.");

        IQueryable<Employee> query = _db.Employees
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(search))
        {
            var term = search.Trim();
            query = query.Where(x =>
                x.Name.Contains(term) || x.Email.Contains(term));
        }

        var result = await query
            .OrderBy(x => x.Id)
            .Take(take)
            .Select(x => new EmployeeExportRow(
                x.Id,
                x.Name,
                x.Email,
                x.Manager == null ? null : x.Manager.Email))
            .ToListAsync(cancellationToken);

        _logger.LogInformation(
            "Employee export completed for tenant {TenantId}; rows={RowCount}; hasSearch={HasSearch}",
            tenantId,
            result.Count,
            !string.IsNullOrWhiteSpace(search));

        return Ok(result);
    }
}
```

Phần search ở ví dụ chỉ minh họa. Trong production cần xác nhận database provider, collation/case-sensitivity, indexing và search requirements; với PostgreSQL/SQL Server có thể cần chiến lược khác nhau. Nếu export thực sự có thể rất lớn, endpoint đồng bộ không còn là lựa chọn tốt: tạo export job có authorization snapshot phù hợp, giới hạn retention và cung cấp secure download.

## Trade-offs

Derive tenant từ identity giúp giảm nguy cơ IDOR nhưng có thể không phù hợp với admin được phép switch tenant; khi đó explicit tenant ID vẫn được chấp nhận nhưng bắt buộc policy authorization. Projection tối thiểu giảm data exposure nhưng có thể cần nhiều report DTO theo quyền. `Contains` đơn giản dễ triển khai nhưng search quy mô lớn có thể cần index/search strategy khác. Pagination phù hợp API tương tác; background export phù hợp report lớn nhưng tăng complexity, storage và lifecycle/security requirements.

## Cách kiểm thử

1. **Authorization integration test:** token tenant A gọi `tenantId` của B phải nhận 403 và không query/trả dữ liệu B.
2. **Data minimization test:** response schema không chứa phone/address khi caller không có quyền tương ứng.
3. **Query test:** kiểm tra generated SQL có tenant predicate, search predicate, projection và limit trước materialization.
4. **Load test:** tenant lớn với maximum allowed `take`; theo dõi latency, allocation và DB load.
5. **Cancellation/security test:** client abort hủy query; fuzz `search` và invalid `take` không gây data leak hoặc resource abuse.

## Quan sát trong production

Theo dõi authorization-denied count theo tenant/caller category, export latency và row count, DB query duration, request cancellation, response size và memory allocation. Trace nên liên kết request với DB span nhưng tránh ghi raw search/PII. Alert khi cross-tenant denial tăng bất thường, export latency vượt SLO hoặc response size tăng đột biến.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ enforce tenant isolation ở controller, application layer hay DbContext/query filter? Trade-off của từng cách là gì?
2. Nếu admin có quyền export nhiều tenant cùng lúc, bạn thiết kế authorization và query thế nào để không quay lại lỗ hổng IDOR?
3. Khi report có hàng triệu rows, bạn chuyển từ synchronous API sang background export như thế nào và bảo vệ file kết quả ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng retry không đồng nghĩa exactly-once; correctness của background workflow cần atomic ownership, idempotency, explicit state transitions và reconciliation khi side effect nằm ngoài database transaction. Challenge 2 nhấn mạnh separation giữa authentication và authorization, tenant isolation, data minimization và nguyên tắc giữ EF Core query ở database càng lâu càng tốt trước khi materialize.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency; đừng xử lý chúng như hai vấn đề riêng.
- Với distributed side effects, luôn hỏi: “Điều gì xảy ra nếu bước trước thành công nhưng bước ghi nhận kết quả thất bại?”
- Authentication không thay thế object-level hoặc tenant-level authorization.
- Filter, project và limit trước khi materialize dữ liệu.
- Treat observability, recovery và privacy như một phần của design chứ không phải việc bổ sung sau cùng.
