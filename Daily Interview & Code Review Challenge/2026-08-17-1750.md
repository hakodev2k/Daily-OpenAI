# Code Review Challenge 1 — API tìm kiếm audit log vừa có nguy cơ SQL Injection vừa chậm khi phân trang sâu

**Chủ đề:** SQL performance & correctness, input validation, injection risks, authorization boundary, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một API nội bộ cho phép admin tìm kiếm audit log theo tenant, từ khóa, loại hành động và khoảng thời gian. Hệ thống hiện có khoảng 80 triệu audit records và tăng thêm vài triệu record mỗi tháng.

Endpoint thường trả về 50 record/trang. Ở các trang đầu latency khoảng 100–250 ms, nhưng khi người dùng nhảy tới trang 2.000–5.000 thì latency tăng mạnh, CPU database tăng và đôi lúc query timeout. Team cũng nhận được cảnh báo security rằng endpoint có thể bị SQL Injection thông qua tham số `sortBy`, `search` hoặc `action`.

Hệ thống chạy multi-tenant. Một số admin chỉ được xem audit log trong tenant của mình, còn global admin mới được xem nhiều tenant. Code hiện tại được viết nhanh để hỗ trợ filter linh hoạt.

## Đoạn code cần review

```csharp
public sealed class AuditLogRepository
{
    private readonly AppDbContext _db;

    public AuditLogRepository(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IReadOnlyList<AuditLogDto>> SearchAsync(
        Guid tenantId,
        string? search,
        string? action,
        string sortBy,
        bool descending,
        int page,
        int pageSize,
        CancellationToken cancellationToken)
    {
        var direction = descending ? "DESC" : "ASC";
        var offset = (page - 1) * pageSize;

        var sql = $@"
            SELECT Id, TenantId, UserId, Action, CreatedAt, Detail
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND ('{search}' = '' OR Detail LIKE '%{search}%')
              AND ('{action}' = '' OR Action = '{action}')
            ORDER BY {sortBy} {direction}
            OFFSET {offset} ROWS
            FETCH NEXT {pageSize} ROWS ONLY";

        return await _db.Database
            .SqlQueryRaw<AuditLogDto>(sql)
            .ToListAsync(cancellationToken);
    }
}
```

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### 1. SQL Injection thông qua `search` và `action`

**Problem:** Hai tham số được chèn trực tiếp vào SQL string.  
**Why it happens:** String interpolation được dùng thay cho parameterized query.  
**Production impact:** Kẻ tấn công hoặc user có quyền truy cập endpoint có thể làm thay đổi điều kiện query, đọc dữ liệu ngoài phạm vi dự kiến hoặc phá vỡ câu SQL.  
**Severity:** Critical  
**Recommended fix:** Dùng LINQ/EF Core parameterization hoặc `FromSqlInterpolated`/database parameters cho toàn bộ giá trị dữ liệu.

### 2. `sortBy` cho phép chèn SQL vào cấu trúc `ORDER BY`

**Problem:** `sortBy` được chèn nguyên văn vào câu SQL.  
**Why it happens:** Tên column không phải là một scalar value có thể parameterize theo cách thông thường.  
**Production impact:** Đây là injection surface nghiêm trọng dù các filter khác đã được parameterize.  
**Severity:** Critical  
**Recommended fix:** Mapping `sortBy` từ input sang tập field được allow-list cứng trong code; tuyệt đối không nối tên cột user gửi trực tiếp.

### 3. Tenant isolation phụ thuộc hoàn toàn vào `tenantId` do caller truyền

**Problem:** Repository nhận `tenantId` như dữ liệu thông thường nhưng không thể hiện authorization context.  
**Why it happens:** Data filtering và authorization boundary bị trộn lẫn.  
**Production impact:** Nếu controller/service truyền nhầm tenant hoặc cho user kiểm soát tenant id, dữ liệu tenant khác có thể bị lộ.  
**Severity:** High  
**Recommended fix:** Lấy allowed tenant scope từ authenticated authorization context; validate explicit tenant request với quyền của caller trước khi query. Có thể thêm global query filter khi phù hợp nhưng vẫn cần hiểu rõ bypass/admin scenario.

### 4. `OFFSET` lớn gây chi phí tăng khi phân trang sâu

**Problem:** Query phải bỏ qua ngày càng nhiều rows trước khi trả trang hiện tại.  
**Why it happens:** Offset pagination phù hợp cho navigation nông nhưng kém hiệu quả khi nhảy sâu trên dataset lớn.  
**Production impact:** CPU/I/O tăng, latency tăng và query có thể timeout khi page number lớn.  
**Severity:** High  
**Recommended fix:** Nếu UX cho phép, dùng keyset/cursor pagination dựa trên deterministic ordering như `(CreatedAt, Id)`.

### 5. Ordering không đảm bảo deterministic nếu sort column có duplicate

**Problem:** Query chỉ order theo một field user chọn.  
**Why it happens:** Không có stable tie-breaker.  
**Production impact:** Record có thể bị lặp hoặc bị bỏ qua giữa các page khi dữ liệu thay đổi hoặc nhiều rows có cùng sort value.  
**Severity:** High  
**Recommended fix:** Thêm `Id` hoặc khóa ổn định làm secondary sort key.

### 6. `LIKE '%search%'` có thể rất tốn tài nguyên

**Problem:** Search substring trên `Detail` lớn có thể buộc database scan nhiều dữ liệu.  
**Why it happens:** Leading wildcard thường làm B-tree index thông thường khó được tận dụng hiệu quả cho predicate này.  
**Production impact:** Database CPU/I/O tăng mạnh với bảng hàng chục triệu record.  
**Severity:** High  
**Recommended fix:** Xác định requirement search thật sự; cân nhắc search trên field được cấu trúc, full-text search/provider feature hoặc hệ thống search riêng nếu workload yêu cầu. Benchmark bằng execution plan thực tế trước khi chọn giải pháp.

### 7. Không validate `page` và `pageSize`

**Problem:** Giá trị âm, 0 hoặc `pageSize` cực lớn có thể đi vào query.  
**Why it happens:** Repository giả định input đã hợp lệ.  
**Production impact:** Overflow ở phép tính offset, query lỗi hoặc resource consumption bất thường.  
**Severity:** Medium  
**Recommended fix:** Validate page >= 1, giới hạn `pageSize` theo policy, và tránh arithmetic overflow.

### 8. Không thể hiện giới hạn time range

**Problem:** Query có thể search toàn bộ lịch sử chỉ bằng keyword.  
**Why it happens:** API chưa bắt buộc hoặc khuyến khích thời gian tìm kiếm.  
**Production impact:** Query rất rộng gây tải lớn và ảnh hưởng workload khác.  
**Severity:** Medium  
**Recommended fix:** Với dataset lớn, yêu cầu time range hợp lý hoặc áp default window; cho phép mở rộng chỉ khi thật sự cần.

### 9. Thiếu observability cho query shape

**Problem:** Không log normalized filter shape, elapsed time, page depth hoặc timeout.  
**Why it happens:** Query được coi là repository implementation detail.  
**Production impact:** Khó biết loại search nào gây database pressure.  
**Severity:** Medium  
**Recommended fix:** Ghi duration, result count, filter presence, page depth/cursor use, tenant scope, timeout và trace id nhưng không log raw sensitive search content nếu policy không cho phép.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng LINQ để parameterize các filter values và allow-list sort field. Với các page đầu vẫn có thể dùng offset pagination; nếu sản phẩm cần browse rất sâu, nên chuyển API sang cursor/keyset.

```csharp
public sealed class AuditLogRepository
{
    private const int MaxPageSize = 100;
    private readonly AppDbContext _db;

    public AuditLogRepository(AppDbContext db)
    {
        _db = db;
    }

    public async Task<IReadOnlyList<AuditLogDto>> SearchAsync(
        Guid tenantId,
        string? search,
        string? action,
        string sortBy,
        bool descending,
        int page,
        int pageSize,
        CancellationToken cancellationToken)
    {
        if (page < 1)
            throw new ArgumentOutOfRangeException(nameof(page));

        pageSize = Math.Clamp(pageSize, 1, MaxPageSize);

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(action))
        {
            var normalizedAction = action.Trim();
            query = query.Where(x => x.Action == normalizedAction);
        }

        if (!string.IsNullOrWhiteSpace(search))
        {
            var normalizedSearch = search.Trim();
            query = query.Where(x => x.Detail.Contains(normalizedSearch));
        }

        query = (sortBy.Trim().ToLowerInvariant(), descending) switch
        {
            ("createdat", false) => query.OrderBy(x => x.CreatedAt).ThenBy(x => x.Id),
            ("createdat", true)  => query.OrderByDescending(x => x.CreatedAt).ThenByDescending(x => x.Id),
            ("action", false)    => query.OrderBy(x => x.Action).ThenBy(x => x.Id),
            ("action", true)     => query.OrderByDescending(x => x.Action).ThenByDescending(x => x.Id),
            _ => query.OrderByDescending(x => x.CreatedAt).ThenByDescending(x => x.Id)
        };

        var skip = checked((page - 1) * pageSize);

        return await query
            .Skip(skip)
            .Take(pageSize)
            .Select(x => new AuditLogDto
            {
                Id = x.Id,
                TenantId = x.TenantId,
                UserId = x.UserId,
                Action = x.Action,
                CreatedAt = x.CreatedAt,
                Detail = x.Detail
            })
            .ToListAsync(cancellationToken);
    }
}
```

Nếu requirement thực sự cần deep pagination, nên đổi contract sang cursor, ví dụ lấy `lastCreatedAt` + `lastId`, rồi dùng predicate theo ordering hiện tại thay vì tăng `OFFSET` vô hạn.

## Trade-offs

- Offset pagination dễ dùng và phù hợp UI có số trang, nhưng chi phí tăng khi page sâu.
- Cursor/keyset nhanh và ổn định hơn cho feed lớn nhưng không hỗ trợ nhảy trực tiếp tới page 5.000 một cách tự nhiên.
- Search substring đơn giản dễ triển khai nhưng khó scale; full-text/search engine tăng complexity vận hành.
- Global query filter giảm nguy cơ quên tenant predicate nhưng có thể gây bất ngờ ở admin/reporting code; cần quy ước rõ về bypass.

## Cách kiểm thử

1. **Security test:** truyền payload chứa quote, SQL fragment và sort field lạ; xác nhận không thay đổi query semantics và không vượt tenant scope.
2. **Database test:** chạy với dataset lớn, so execution plan/query duration ở page nông và page sâu.
3. **Correctness test:** nhiều rows cùng `CreatedAt` hoặc `Action`, xác nhận ordering deterministic.
4. **Boundary test:** page = 0, pageSize âm hoặc cực lớn; xác nhận validation đúng.
5. **Load test:** nhiều concurrent search với filter khác nhau, theo dõi DB CPU, reads, duration và timeout.

## Quan sát trong production

Nên theo dõi:

- query duration p50/p95/p99
- timeout/error rate
- rows returned và page depth/cursor usage
- database CPU, logical reads/I/O và lock waits
- top normalized query shapes
- search request count theo tenant
- trace từ API tới DB command
- alert khi p95 vượt SLA hoặc timeout tăng bất thường

## Câu hỏi phỏng vấn mở rộng

3. Nếu global admin được phép cross-tenant search, bạn làm authorization boundary ra sao để vẫn audit được mọi truy cập?

# Code Review Challenge 2 — Import ZIP kết quả QA có thể ghi file ra ngoài thư mục và làm cạn tài nguyên server

**Chủ đề:** Input validation, resource lifetime & disposal, memory/allocation, async/cancellation, performance, error handling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một QA automation platform cho phép upload file ZIP chứa screenshot, HTML report và JSON result sau mỗi test run. API giải nén ZIP vào thư mục của run để web portal hiển thị artifact.

File ZIP thông thường khoảng 20–100 MB nhưng đôi lúc lớn hơn. Hệ thống có nhiều team chạy Playwright song song. Sau khi feature được đưa lên production, team ghi nhận memory tăng mạnh khi nhiều upload đồng thời, disk đôi khi đầy và có một security finding liên quan tới filename trong ZIP có thể thoát ra ngoài thư mục dự kiến.

Yêu cầu mới: import phải an toàn với file name không tin cậy, có giới hạn kích thước, hỗ trợ cancellation, cleanup khi lỗi và không giữ toàn bộ ZIP trong memory.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/test-runs")]
public sealed class TestRunArtifactsController : ControllerBase
{
    private readonly IWebHostEnvironment _environment;

    public TestRunArtifactsController(IWebHostEnvironment environment)
    {
        _environment = environment;
    }

    [HttpPost("{runId:guid}/artifacts")]
    public async Task<IActionResult> UploadArtifacts(
        Guid runId,
        IFormFile file)
    {
        using var memory = new MemoryStream();
        await file.CopyToAsync(memory);
        memory.Position = 0;

        var root = Path.Combine(
            _environment.ContentRootPath,
            "artifacts",
            runId.ToString());

        Directory.CreateDirectory(root);

        using var archive = new ZipArchive(memory, ZipArchiveMode.Read);

        foreach (var entry in archive.Entries)
        {
            var destination = Path.Combine(root, entry.FullName);
            var directory = Path.GetDirectoryName(destination);

            if (!string.IsNullOrEmpty(directory))
            {
                Directory.CreateDirectory(directory);
            }

            if (!string.IsNullOrEmpty(entry.Name))
            {
                entry.ExtractToFile(destination, overwrite: true);
            }
        }

        return Ok(new
        {
            RunId = runId,
            Files = archive.Entries.Count
        });
    }
}
```

## Câu hỏi gợi mở

1. `entry.FullName` có phải dữ liệu đáng tin cậy không?
2. `Path.Combine(root, entry.FullName)` có đảm bảo path vẫn nằm dưới `root` không?
3. Điều gì xảy ra khi ZIP nhỏ nhưng uncompressed content rất lớn?
4. Tại sao copy toàn bộ upload vào `MemoryStream` là rủi ro khi nhiều request đồng thời?
5. Nếu client disconnect hoặc disk đầy giữa chừng, cleanup hiện tại diễn ra như thế nào?

## Gợi ý

## Kết quả code review tham khảo

### 1. Path traversal thông qua ZIP entry name

**Problem:** `entry.FullName` được nối trực tiếp vào root path.  
**Why it happens:** ZIP entry name là input không tin cậy và có thể chứa `../` hoặc path pattern khác.  
**Production impact:** File có thể được ghi ra ngoài thư mục run, ghi đè file khác trong phạm vi permission của process.  
**Severity:** Critical  
**Recommended fix:** Lấy full canonical path của destination và xác nhận nó bắt đầu bằng canonical root + directory separator trước khi tạo file.

### 2. Không giới hạn tổng uncompressed size

**Problem:** Code extract mọi entry bất kể tổng kích thước sau giải nén.  
**Why it happens:** Chỉ nhìn kích thước file upload không đủ để đánh giá resource usage sau decompression.  
**Production impact:** Archive được nén mạnh có thể làm đầy disk hoặc kéo dài CPU/I/O đáng kể.  
**Severity:** Critical  
**Recommended fix:** Áp giới hạn số entry, kích thước mỗi entry, tổng uncompressed bytes và tổng thời gian xử lý; reject archive vượt policy.

### 3. Copy toàn bộ ZIP vào `MemoryStream`

**Problem:** Toàn bộ upload được materialize trong RAM trước khi xử lý.  
**Why it happens:** Implementation chọn cách đơn giản để tạo seekable stream.  
**Production impact:** Nhiều upload 100 MB đồng thời có thể gây memory pressure, GC pressure hoặc OOM.  
**Severity:** High  
**Recommended fix:** Dùng file buffering/temp file có giới hạn hoặc stream phù hợp với archive processing, tránh giữ toàn bộ payload trong managed memory.

### 4. Không giới hạn kích thước upload và số entry

**Problem:** Endpoint nhận bất kỳ file size/count nào mà application server cho phép.  
**Why it happens:** Không có business limit trong code.  
**Production impact:** Dễ bị resource exhaustion và tăng chi phí xử lý.  
**Severity:** High  
**Recommended fix:** Enforce max upload size, max entry count và reject sớm.

### 5. Không propagate cancellation

**Problem:** `CopyToAsync` và extraction loop không dùng `HttpContext.RequestAborted`.  
**Why it happens:** Cancellation chưa được xem như một phần resource control.  
**Production impact:** Client đã bỏ request nhưng server vẫn tiếp tục đọc/ghi file lớn.  
**Severity:** High  
**Recommended fix:** Truyền cancellation token vào các thao tác async và kiểm tra token trong loop.

### 6. Failure giữa chừng để lại partial artifact directory

**Problem:** Nếu một entry lỗi hoặc disk đầy, các file đã extract vẫn còn.  
**Why it happens:** Không có staging directory và cleanup strategy.  
**Production impact:** Portal có thể đọc trạng thái artifact không đầy đủ, disk tích tụ file rác và retry khó xác định.  
**Severity:** High  
**Recommended fix:** Extract vào temporary/staging directory riêng, chỉ rename/move vào location chính thức khi toàn bộ import thành công; cleanup staging trong `finally`.

### 7. `overwrite: true` có thể ghi đè artifact đã tồn tại

**Problem:** Retry hoặc concurrent upload cho cùng `runId` có thể overwrite file mà không có concurrency policy.  
**Why it happens:** Endpoint chưa xác định semantics của duplicate upload.  
**Production impact:** Race condition giữa hai upload, artifact set không xác định.  
**Severity:** Medium  
**Recommended fix:** Xác định idempotency/versioning policy; có thể dùng unique import id, optimistic state transition hoặc single-writer rule cho mỗi run.

### 8. Không validate loại file/extension cần cho business

**Problem:** Mọi entry đều được ghi xuống disk.  
**Why it happens:** Archive được coi là trusted QA output.  
**Production impact:** Tăng attack surface, lưu file không cần thiết và khó áp content policy.  
**Severity:** Medium  
**Recommended fix:** Allow-list loại artifact cần thiết như `.png`, `.jpg`, `.html`, `.json`, `.txt` nếu phù hợp requirement; tránh dựa duy nhất vào extension khi nội dung sẽ được phục vụ hoặc xử lý tiếp.

### 9. Thiếu observability cho resource usage

**Problem:** Endpoint chỉ trả số entry, không ghi metrics về compressed/uncompressed bytes, duration hay failure reason.  
**Why it happens:** Import được xem như thao tác file đơn giản.  
**Production impact:** Khó phát hiện abuse, disk pressure hoặc regression.  
**Severity:** Medium  
**Recommended fix:** Theo dõi upload size, extracted bytes, entry count, duration, rejects, cancellation và cleanup failure.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa staging directory, canonical path validation, cancellation và resource limits. Các giới hạn chỉ là policy minh họa và phải được điều chỉnh theo workload thực tế.

```csharp
[ApiController]
[Route("api/test-runs")]
public sealed class TestRunArtifactsController : ControllerBase
{
    private const long MaxUploadBytes = 200L * 1024 * 1024;
    private const long MaxExtractedBytes = 500L * 1024 * 1024;
    private const int MaxEntries = 2_000;

    private readonly IWebHostEnvironment _environment;
    private readonly ILogger<TestRunArtifactsController> _logger;

    public TestRunArtifactsController(
        IWebHostEnvironment environment,
        ILogger<TestRunArtifactsController> logger)
    {
        _environment = environment;
        _logger = logger;
    }

    [HttpPost("{runId:guid}/artifacts")]
    public async Task<IActionResult> UploadArtifacts(
        Guid runId,
        IFormFile file,
        CancellationToken cancellationToken)
    {
        if (file.Length <= 0 || file.Length > MaxUploadBytes)
            return BadRequest("Invalid artifact archive size.");

        var artifactsRoot = Path.Combine(
            _environment.ContentRootPath,
            "artifacts");

        Directory.CreateDirectory(artifactsRoot);

        var staging = Path.Combine(
            artifactsRoot,
            $".staging-{runId:N}-{Guid.NewGuid():N}");

        var finalDirectory = Path.Combine(
            artifactsRoot,
            runId.ToString("N"));

        var tempZip = Path.Combine(staging, "upload.zip");
        Directory.CreateDirectory(staging);

        try
        {
            await using (var output = new FileStream(
                tempZip,
                FileMode.CreateNew,
                FileAccess.Write,
                FileShare.None,
                bufferSize: 64 * 1024,
                useAsync: true))
            {
                await file.CopyToAsync(output, cancellationToken);
            }

            using var archive = ZipFile.OpenRead(tempZip);

            if (archive.Entries.Count > MaxEntries)
                return BadRequest("Too many files in archive.");

            var canonicalRoot = Path.GetFullPath(staging)
                .TrimEnd(Path.DirectorySeparatorChar) + Path.DirectorySeparatorChar;

            long extractedBytes = 0;

            foreach (var entry in archive.Entries)
            {
                cancellationToken.ThrowIfCancellationRequested();

                if (string.IsNullOrEmpty(entry.Name))
                    continue;

                extractedBytes = checked(extractedBytes + entry.Length);
                if (extractedBytes > MaxExtractedBytes)
                    return BadRequest("Archive expands beyond the allowed size.");

                var destination = Path.GetFullPath(
                    Path.Combine(staging, entry.FullName));

                if (!destination.StartsWith(
                        canonicalRoot,
                        StringComparison.Ordinal))
                {
                    return BadRequest("Archive contains an invalid path.");
                }

                Directory.CreateDirectory(
                    Path.GetDirectoryName(destination)!);

                await using var input = entry.Open();
                await using var output = new FileStream(
                    destination,
                    FileMode.CreateNew,
                    FileAccess.Write,
                    FileShare.None,
                    bufferSize: 64 * 1024,
                    useAsync: true);

                await input.CopyToAsync(output, cancellationToken);
            }

            System.IO.File.Delete(tempZip);

            if (Directory.Exists(finalDirectory))
                return Conflict("Artifacts already exist for this run.");

            Directory.Move(staging, finalDirectory);

            _logger.LogInformation(
                "Artifact import completed. RunId={RunId} Files={Files} Bytes={Bytes}",
                runId,
                archive.Entries.Count,
                extractedBytes);

            return Ok(new
            {
                RunId = runId,
                Files = archive.Entries.Count,
                ExtractedBytes = extractedBytes
            });
        }
        finally
        {
            if (Directory.Exists(staging))
            {
                try
                {
                    Directory.Delete(staging, recursive: true);
                }
                catch (Exception ex)
                {
                    _logger.LogWarning(
                        ex,
                        "Failed to clean staging directory for RunId={RunId}",
                        runId);
                }
            }
        }
    }
}
```

Trong production, authorization cho `runId`, upload-size enforcement ở web server/reverse proxy, storage quota, malware/content scanning và concurrent import policy cũng cần được thiết kế theo threat model cụ thể.

## Trade-offs

- Temp file giảm managed-memory pressure nhưng tăng disk I/O và cần disk quota/cleanup.
- Staging directory giúp atomic publish ở mức application flow nhưng yêu cầu đủ disk cho dữ liệu tạm.
- Hard limits bảo vệ hệ thống nhưng có thể chặn legitimate large test run; cần dựa trên workload thực tế.
- Local disk đơn giản cho single-node nhưng không phù hợp nếu artifacts phải survive instance replacement hoặc được dùng từ nhiều node; object storage có thể phù hợp hơn.
- Content scanning tăng security nhưng tăng latency và operational complexity.

## Cách kiểm thử

1. **Security test:** ZIP có entry `../../outside.txt`; xác nhận request bị reject và không có file ngoài staging root.
2. **Resource-limit test:** ZIP có tổng uncompressed size vượt giới hạn hoặc quá nhiều entry; xác nhận reject sớm và cleanup đầy đủ.
3. **Cancellation test:** huỷ request giữa một entry lớn; xác nhận copy dừng và staging được xoá.
4. **Concurrency test:** hai upload cùng `runId`; xác nhận policy deterministic, không tạo artifact set trộn lẫn.
5. **Failure-path test:** giả lập disk full/IOException giữa chừng; xác nhận không publish partial directory và có log phù hợp.

## Quan sát trong production

Nên theo dõi:

- artifact upload compressed bytes
- extracted bytes và entry count
- import duration p50/p95/p99
- reject count theo reason
- cancellation count
- staging cleanup failures
- disk free space / inode usage
- concurrent imports
- IOException rate
- trace từ HTTP request tới import operation
- alert khi disk free space xuống dưới threshold hoặc reject/resource errors tăng mạnh

## Câu hỏi phỏng vấn mở rộng

1. Nếu chạy nhiều application instances, bạn lưu artifact ở local disk hay object storage? Vì sao?
2. Nếu business cho phép re-upload cùng `runId`, bạn thiết kế versioning/idempotency thế nào?
3. Nếu cần serve file HTML do user upload, bạn sẽ bổ sung security control nào trước khi hiển thị trên portal?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Parameterization chỉ giải quyết scalar values; các thành phần cấu trúc như dynamic sort column cần allow-list.
- Deep offset pagination có thể trở thành bottleneck trên bảng rất lớn; keyset/cursor là lựa chọn đáng cân nhắc khi UX cho phép.
- Multi-tenant filtering phải gắn với authorization boundary, không chỉ là một tham số repository.
- File name bên trong archive là input không tin cậy; canonical path validation là bắt buộc trước khi ghi file.
- Resource limits, cancellation và cleanup phải được thiết kế cùng happy path, không thêm sau khi có incident.

## Mẫu tư duy cần nhớ

- **Trust boundary first:** Xác định mọi input user-controlled trước khi review implementation.
- **Separate data from structure:** Parameterize values, allow-list query structure.
- **Design for scale shape, not sample size:** Query chạy tốt với 10.000 rows chưa chắc phù hợp với 80 triệu rows.
- **Bound every expensive resource:** Memory, disk, number of files, concurrency và execution time đều cần giới hạn.
- **Failure cleanup is part of correctness:** Partial state phải có chiến lược staging, rollback hoặc retry rõ ràng.
