# Code Review Challenge 1 — BackgroundService chạy trùng scheduled job sau khi scale-out

**Chủ đề:** C#/.NET, BackgroundService, concurrency, horizontal scaling, SQL Server, idempotency, graceful shutdown  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core application chạy trên Azure App Service có `BackgroundService` quét các invoice quá hạn mỗi phút và gửi reminder qua third-party email API. Khi application chỉ có một instance, hệ thống gần như ổn định. Sau khi scale lên 5 instances để xử lý web traffic, khách hàng bắt đầu nhận nhiều email reminder giống nhau.

Database là SQL Server. Mỗi invoice có `LastReminderSentAtUtc`, nhưng không có durable record đại diện cho từng logical reminder. Email provider hỗ trợ request idempotency key nhưng code hiện tại chưa sử dụng. Deployment/restart cũng có thể hủy process trong lúc batch đang chạy.

## Đoạn code cần review

```csharp
public sealed class InvoiceReminderWorker : BackgroundService
{
    private readonly IServiceProvider _services;
    private readonly HttpClient _emailClient;
    private readonly ILogger<InvoiceReminderWorker> _logger;

    public InvoiceReminderWorker(
        IServiceProvider services,
        HttpClient emailClient,
        ILogger<InvoiceReminderWorker> logger)
    {
        _services = services;
        _emailClient = emailClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = _services.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            var invoices = await db.Invoices
                .Where(x => x.Status == "Overdue" &&
                            (x.LastReminderSentAtUtc == null ||
                             x.LastReminderSentAtUtc < DateTime.UtcNow.AddDays(-1)))
                .Take(100)
                .ToListAsync(stoppingToken);

            foreach (var invoice in invoices)
            {
                var response = await _emailClient.PostAsJsonAsync(
                    "/send-reminder",
                    new { invoice.Id, invoice.CustomerEmail },
                    stoppingToken);

                response.EnsureSuccessStatusCode();

                invoice.LastReminderSentAtUtc = DateTime.UtcNow;
                await db.SaveChangesAsync(stoppingToken);
            }

            await Task.Delay(TimeSpan.FromMinutes(1));
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và distributed-concurrency problems khi có nhiều application instances.
2. Phân tích failure windows giữa query, email side effect và database update.
3. Giải thích vì sao một in-process lock không giải quyết bài toán scale-out.
4. Ưu tiên findings theo severity và business impact.
5. Đề xuất design đơn giản nhưng retry-safe; không mặc định thêm Kubernetes, Service Bus hay distributed lock nếu chưa cần.
6. Giải thích testing cho concurrent workers, restart, timeout và ambiguous email outcome.
7. Nêu telemetry cần có để xác định một logical reminder đã được attempt/send bao nhiêu lần.

## Câu hỏi gợi mở

1. Năm instances chạy cùng query trong cùng một phút có thể đọc những invoice nào?
2. Nếu provider đã gửi email nhưng response bị mất trước khi `LastReminderSentAtUtc` được update thì lần sau chuyện gì xảy ra?
3. `lock` hoặc `SemaphoreSlim` trong worker bảo vệ được phạm vi nào?
4. Business invariant “mỗi invoice tối đa một reminder/ngày” hiện được enforce ở đâu?
5. Điều gì xảy ra với `Task.Delay` khi application đang shutdown?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **nhiều process cùng claim một logical work item mà không có durable ownership/idempotency**.

### Gợi ý 2

Tách ba việc: chọn work, ghi nhận durable processing state và thực hiện external side effect. Sau đó xem mỗi bước có thể retry an toàn hay không.

## Kết quả code review tham khảo

### Critical — Nhiều instances có thể gửi cùng reminder

**Vấn đề:** Mỗi instance độc lập query cùng tập invoice đủ điều kiện rồi gửi email.

**Tại sao xảy ra:** Query không claim work atomically và không có durable unique identity cho logical reminder.

**Ảnh hưởng production:** Duplicate email tăng gần theo số instance/timing, gây customer impact trực tiếp.

**Cách sửa:** Xác định logical reminder key, ví dụ `(InvoiceId, ReminderDate/PolicyVersion)`, và enforce uniqueness trong durable storage. Một worker phải claim/create record bằng database operation chịu concurrency; unique constraint là authority cuối cùng.

### Critical — External email side effect không idempotent

**Vấn đề:** Email được gửi trước khi database ghi nhận thành công.

**Tại sao xảy ra:** Nếu provider xử lý request nhưng caller timeout/crash trước DB update, lần chạy sau không biết email đã được gửi.

**Ảnh hưởng production:** Duplicate email ngay cả khi chỉ có một worker.

**Cách sửa:** Dùng stable idempotency key của provider nếu contract hỗ trợ. Key phải đại diện cho cùng logical reminder và được reuse qua retry, không sinh mới mỗi attempt.

### High — Check/query và claim không atomic

**Vấn đề:** `LastReminderSentAtUtc` chỉ được update sau side effect; nhiều workers có một cửa sổ dài để cùng đọc invoice.

**Tại sao xảy ra:** Read-then-act không có database concurrency boundary.

**Ảnh hưởng production:** Race xảy ra dưới scale/load nhưng khó tái hiện local.

**Cách sửa:** Tạo durable reminder/work row với unique key và trạng thái (`Pending`, `Sent`, `Failed`) hoặc dùng database claim semantics phù hợp. Không chỉ thêm một `AnyAsync` check trước send vì check-then-insert vẫn race.

### High — Một invoice failure dừng cả batch

**Vấn đề:** `EnsureSuccessStatusCode` ném exception ra khỏi vòng lặp và có thể kết thúc `ExecuteAsync` nếu không được xử lý ở mức thích hợp.

**Tại sao xảy ra:** Failure policy không phân biệt item-level transient/permanent failure với worker-level fatal failure.

**Ảnh hưởng production:** Một dependency failure có thể ngừng reminder processing cho các invoice khác cho đến khi host restart.

**Cách sửa:** Có per-item failure handling, bounded retry/backoff theo contract, durable failure state và alert/DLQ-like remediation nếu cần. Không swallow exception im lặng.

### High — `Task.Delay` bỏ qua cancellation

**Vấn đề:** Delay không nhận `stoppingToken`.

**Tại sao xảy ra:** Worker có thể chờ hết một phút dù host đang shutdown.

**Ảnh hưởng production:** Graceful shutdown/deployment chậm, process có thể bị force-terminate.

**Cách sửa:** `await Task.Delay(interval, stoppingToken)` hoặc dùng `PeriodicTimer` với cancellation semantics rõ.

### Medium — Batch selection thiếu deterministic ordering/fairness

**Vấn đề:** `Take(100)` không có ordering.

**Tại sao xảy ra:** Database không được yêu cầu thứ tự cụ thể.

**Ảnh hưởng production:** Dưới backlog lớn, fairness và predictability kém; một số invoice có thể bị trì hoãn.

**Cách sửa:** Order theo due/reminder eligibility và stable tiebreaker phù hợp business SLA.

### Medium — Time dependency và reminder boundary khó test

**Vấn đề:** `DateTime.UtcNow` xuất hiện nhiều nơi.

**Tại sao xảy ra:** Không có time abstraction và một iteration có thể quan sát các timestamps khác nhau quanh boundary.

**Ảnh hưởng production:** Edge-case quanh ngày/TTL khó deterministic test.

**Cách sửa:** Capture một `now` cho operation hoặc dùng time abstraction phù hợp runtime/project.

### Medium — Thiếu telemetry về logical reminder identity

**Vấn đề:** Không có correlation/idempotency key trong logs/state.

**Tại sao xảy ra:** Monitoring tập trung vào worker execution thay vì logical work item.

**Ảnh hưởng production:** Khó chứng minh duplicate đến từ selection race, retry hay provider.

**Cách sửa:** Structured logs/traces với invoice ID, logical reminder ID, worker instance, attempt, provider request ID và durable state transition.

## Phiên bản đề xuất

Một hướng giữ kiến trúc đơn giản là dùng SQL làm durable work/idempotency store và provider idempotency key. Ví dụ rút gọn:

```csharp
public sealed class InvoiceReminderWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly HttpClient _emailClient;
    private readonly TimeProvider _timeProvider;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        do
        {
            await ProcessBatchAsync(stoppingToken);
        }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }

    private async Task ProcessBatchAsync(CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var now = _timeProvider.GetUtcNow().UtcDateTime;
        var reminderDate = DateOnly.FromDateTime(now);

        var candidates = await db.Invoices
            .AsNoTracking()
            .Where(x => x.Status == "Overdue")
            .OrderBy(x => x.DueAtUtc)
            .ThenBy(x => x.Id)
            .Select(x => new { x.Id, x.CustomerEmail })
            .Take(100)
            .ToListAsync(cancellationToken);

        foreach (var invoice in candidates)
        {
            var key = $"invoice-reminder:{invoice.Id}:{reminderDate:yyyy-MM-dd}";

            var claimed = await TryCreateReminderAsync(
                db, invoice.Id, reminderDate, key, now, cancellationToken);

            if (!claimed)
                continue;

            try
            {
                using var request = new HttpRequestMessage(HttpMethod.Post, "/send-reminder")
                {
                    Content = JsonContent.Create(new { invoice.Id, invoice.CustomerEmail })
                };
                request.Headers.TryAddWithoutValidation("Idempotency-Key", key);

                using var response = await _emailClient.SendAsync(request, cancellationToken);
                response.EnsureSuccessStatusCode();

                await MarkSentAsync(db, invoice.Id, reminderDate, now, cancellationToken);
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                await MarkFailedAsync(db, invoice.Id, reminderDate, ex, cancellationToken);
            }
        }
    }
}
```

Database cần unique constraint trên logical key, ví dụ `(InvoiceId, ReminderDate)`. `TryCreateReminderAsync` phải xử lý unique conflict như “worker khác đã claim”; không được dựa chỉ vào check trước insert. Production implementation cần policy cho retry `Failed/Pending` records và recovery các records bị bỏ dở sau process crash.

## Giải thích thiết kế sau khi sửa

Scale-out làm in-process synchronization không đủ vì mỗi process có memory riêng. Durable uniqueness trong SQL cho phép tất cả instances cạnh tranh nhưng chỉ một logical reminder được claim.

Provider idempotency xử lý failure window khó nhất: provider đã commit nhưng caller không nhận được response. Durable local state và external idempotency giải quyết hai boundary khác nhau; một cái không thay thế cái kia.

Không nhất thiết phải thêm Service Bus. Nếu throughput thấp, SQL-backed scheduled worker có thể đơn giản và đủ tin cậy. Messaging đáng cân nhắc khi cần decouple scheduling/processing, backlog control hoặc scale độc lập, nhưng nó vẫn cần idempotent consumer.

## Trade-offs

- Durable work rows tăng schema/state-management complexity.
- Unique constraints thêm contention nhưng bảo vệ correctness.
- Provider idempotency phụ thuộc retention/scope guarantee của provider.
- Database polling tạo query load; cần đo trước khi thêm queue infrastructure.
- `PeriodicTimer` giúp cancellation nhưng scheduler semantics vẫn cần quyết định nếu iteration kéo dài hơn interval.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 5 workers cùng lúc trên cùng candidate set; chỉ một reminder record cho mỗi logical key.
2. **Failure-path test:** provider gửi thành công nhưng client timeout; retry cùng key không tạo email thứ hai.
3. **Restart recovery test:** process chết sau claim; record `Pending` được recovery theo policy mà không duplicate side effect.
4. **Load test:** backlog lớn hơn batch size; kiểm tra fairness, DB load và throughput.
5. **Graceful-shutdown test:** cancel host trong delay và giữa batch; worker dừng đúng budget và durable state vẫn recoverable.

## Quan sát trong production

Theo dõi số reminders `Pending/Sent/Failed`, age của oldest pending item, attempts per logical reminder, provider latency/error rate và duplicate/idempotency responses. Structured logs cần có `InvoiceId`, logical reminder key, application instance và provider request ID.

Application Insights dependency telemetry nên correlate SQL claim và email HTTP dependency với cùng logical operation. Alert khi pending age/backlog tăng, failure rate vượt ngưỡng hoặc một reminder có attempt count bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu email provider không hỗ trợ idempotency key, guarantee nào bạn có thể cung cấp và reconciliation nào cần thiết?
2. Khi nào SQL polling nên được thay bằng Azure Service Bus, và điều gì vẫn không tự động được giải quyết sau khi chuyển?
3. Nếu business đổi rule thành tối đa một reminder mỗi 24 giờ thay vì mỗi calendar day, bạn sẽ thay logical key/state model thế nào?

# Code Review Challenge 2 — SQL OFFSET pagination chậm dần và trả dữ liệu thiếu/trùng khi catalog thay đổi

**Chủ đề:** SQL Server, pagination, composite indexes, query plans, correctness under concurrent writes, API design  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một product catalog API phục vụ website thương mại điện tử. Bảng `Products` có khoảng 18 triệu rows. Endpoint cho phép lọc active products theo category và sắp xếp theo `UpdatedAtUtc DESC`. Frontend gọi page 1, 2, 3 khi user scroll.

Khi page number tăng, p95 database latency tăng mạnh. Trong lúc merchandisers cập nhật products, frontend đôi khi thấy một product lặp ở hai pages hoặc một product biến mất khỏi sequence. Team đề xuất “thêm index vào `UpdatedAtUtc`” nhưng chưa xem execution plan.

## Đoạn code cần review

```sql
CREATE TABLE dbo.Products
(
    Id bigint IDENTITY PRIMARY KEY,
    CategoryId int NOT NULL,
    Name nvarchar(250) NOT NULL,
    Price decimal(18,2) NOT NULL,
    IsActive bit NOT NULL,
    UpdatedAtUtc datetime2 NOT NULL
);
GO

CREATE INDEX IX_Products_UpdatedAtUtc
ON dbo.Products(UpdatedAtUtc DESC);
GO

CREATE OR ALTER PROCEDURE dbo.GetProducts
    @CategoryId int,
    @PageNumber int,
    @PageSize int
AS
BEGIN
    SELECT Id, CategoryId, Name, Price, UpdatedAtUtc
    FROM dbo.Products
    WHERE CategoryId = @CategoryId
      AND IsActive = 1
    ORDER BY UpdatedAtUtc DESC
    OFFSET (@PageNumber - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END;
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và performance risks của pagination/query/index hiện tại.
2. Giải thích vì sao latency có thể tăng theo page depth.
3. Phân tích duplicate/missing items khi rows thay đổi giữa hai requests.
4. Không đoán index: nêu evidence cần thu từ execution plan, statistics và workload.
5. Đề xuất keyset/cursor pagination nếu requirement phù hợp và thiết kế deterministic ordering.
6. Nêu trade-offs khi frontend cần random access tới page 500.
7. Đề xuất database/API tests và production telemetry.

## Câu hỏi gợi mở

1. `ORDER BY UpdatedAtUtc DESC` có deterministic không nếu nhiều products có cùng timestamp?
2. Database phải làm gì với hàng trăm nghìn rows trước `OFFSET` ở page sâu?
3. Index chỉ có `UpdatedAtUtc` có align với predicates `CategoryId` và `IsActive` không?
4. Nếu một product được update sau khi client tải page 1 nhưng trước page 2, vị trí của nó thay đổi thế nào?
5. API thực sự cần page number ngẫu nhiên hay chỉ cần “load next”?

## Gợi ý

### Gợi ý 1

Có hai nhóm rủi ro riêng: **query work tăng theo offset** và **position-based pagination không ổn định khi ordered dataset thay đổi**.

### Gợi ý 2

Nếu UX chủ yếu đi tuần tự, hãy xem cursor chứa đầy đủ sort key để query tiếp tục từ row cuối cùng thay vì đếm bỏ rows từ đầu.

## Dừng lại và tự review

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### High — Ordering không deterministic

**Vấn đề:** Chỉ sort theo `UpdatedAtUtc` trong khi nhiều rows có thể có cùng timestamp.

**Tại sao xảy ra:** SQL không bảo đảm relative order giữa rows có cùng sort value nếu không có tie-breaker.

**Ảnh hưởng production:** Items có thể đổi vị trí giữa executions, tạo duplicate/missing pagination ngay cả khi data không đổi đáng kể.

**Cách sửa:** Dùng stable unique tie-breaker, ví dụ `ORDER BY UpdatedAtUtc DESC, Id DESC` và cursor chứa cả hai values.

### High — Deep OFFSET yêu cầu bỏ qua ngày càng nhiều rows

**Vấn đề:** Page sâu vẫn phải xác định/sắp xếp hoặc traverse các rows trước offset trước khi trả page nhỏ.

**Tại sao xảy ra:** OFFSET biểu diễn vị trí, không phải seek boundary.

**Ảnh hưởng production:** CPU/I/O/latency tăng theo page depth, p95/p99 xấu khi users/bots truy cập page sâu.

**Cách sửa:** Nếu UX là sequential navigation, dùng keyset pagination theo ordered key. Xác nhận bằng actual execution plan và logical reads thay vì chỉ dựa trên intuition.

### High — Index hiện tại không align rõ với filter/query shape

**Vấn đề:** `IX_Products_UpdatedAtUtc` chỉ bắt đầu bằng sort column nhưng query luôn filter `CategoryId` và `IsActive`.

**Tại sao xảy ra:** Index usefulness phụ thuộc selectivity, predicate order, sort và projected columns; một index đơn cột không tự động giải quyết workload.

**Ảnh hưởng production:** Scan/read amplification, sort/key lookup cost hoặc plan không ổn định.

**Cách sửa:** Đo actual plan, logical reads, cardinality/statistics. Một candidate index có thể bắt đầu bằng equality predicates rồi sort keys, ví dụ `(CategoryId, IsActive, UpdatedAtUtc DESC, Id DESC)` với INCLUDE phù hợp, nhưng phải validate write/storage cost và selectivity trước khi deploy.

### High — Position-based pages không ổn định dưới concurrent updates

**Vấn đề:** Product được update có thể nhảy lên đầu sequence giữa request page 1 và page 2.

**Tại sao xảy ra:** OFFSET của request sau áp lên một ordered set khác snapshot trước.

**Ảnh hưởng production:** Duplicate hoặc skipped products trong infinite scroll.

**Cách sửa:** Với feed-like UX, keyset cursor theo last seen `(UpdatedAtUtc, Id)` giảm position shift. Nếu business yêu cầu consistent snapshot xuyên nhiều requests, đó là requirement mạnh hơn và cần snapshot/version strategy riêng.

### Medium — Input pagination không được validate

**Vấn đề:** `@PageNumber <= 0`, page size quá lớn hoặc multiplication lớn có thể tạo invalid/expensive request.

**Tại sao xảy ra:** Procedure tin caller.

**Ảnh hưởng production:** Errors hoặc resource abuse.

**Cách sửa:** Enforce API/procedure bounds và maximum page size phù hợp product contract.

### Medium — Covering strategy chưa được cân nhắc

**Vấn đề:** Query trả `Name`, `Price` ngoài candidate key columns.

**Tại sao xảy ra:** Một non-covering index có thể cần nhiều lookups; một covering index lại tăng storage/write amplification.

**Ảnh hưởng production:** Read latency hoặc write/index-maintenance cost.

**Cách sửa:** Dùng workload/plan để quyết định INCLUDE; không mặc định cover mọi column.

### Medium — Không có cursor contract/versioning

**Vấn đề:** Nếu chuyển sang cursor, raw values dễ bị frontend tự tạo/sửa và khó evolve.

**Tại sao xảy ra:** Pagination thường bị xem chỉ là SQL concern.

**Ảnh hưởng production:** API coupling và validation/security khó hơn.

**Cách sửa:** Encode opaque cursor chứa sort boundary và validation/version metadata; không nhét sensitive state vào cursor.

## Phiên bản đề xuất

Nếu requirement là infinite scroll tuần tự, procedure có thể seek từ row cuối của page trước:

```sql
CREATE OR ALTER PROCEDURE dbo.GetProductsAfter
    @CategoryId int,
    @PageSize int,
    @LastUpdatedAtUtc datetime2 = NULL,
    @LastId bigint = NULL
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 100
        THROW 50001, 'Invalid page size', 1;

    SELECT TOP (@PageSize)
        Id,
        CategoryId,
        Name,
        Price,
        UpdatedAtUtc
    FROM dbo.Products
    WHERE CategoryId = @CategoryId
      AND IsActive = 1
      AND (
            @LastUpdatedAtUtc IS NULL
            OR UpdatedAtUtc < @LastUpdatedAtUtc
            OR (UpdatedAtUtc = @LastUpdatedAtUtc AND Id < @LastId)
          )
    ORDER BY UpdatedAtUtc DESC, Id DESC;
END;
```

Một candidate index cần benchmark có thể là:

```sql
CREATE INDEX IX_Products_Category_Active_Updated_Id
ON dbo.Products
(
    CategoryId,
    IsActive,
    UpdatedAtUtc DESC,
    Id DESC
)
INCLUDE (Name, Price);
```

Đây không phải index “đúng” tuyệt đối. Cần xem data distribution, write rate, filtered-index options, actual execution plans, logical reads và storage overhead. Nếu `IsActive = 1` chiếm gần toàn bộ table, value của key đó khác với trường hợp active rows rất selective.

API trả opaque `nextCursor` được tạo từ `(UpdatedAtUtc, Id)` của row cuối. Client gửi cursor cho request kế tiếp thay vì page number.

## Giải thích thiết kế sau khi sửa

Keyset pagination biến “bỏ qua N rows” thành “seek sau boundary đã thấy”. Composite unique ordering giúp sequence deterministic khi timestamps trùng.

Keyset không tạo immutable snapshot. Nếu một row đã xem được update và nhảy vị trí, semantics cần được product xác định. Nó giải quyết tốt sequential traversal/performance và giảm nhiều anomalies của OFFSET, nhưng không tự cung cấp snapshot isolation xuyên HTTP requests.

Index design phải đi từ query shape và evidence. Equality predicates trước ordered seek keys thường là candidate hợp lý, nhưng actual workload mới quyết định.

## Trade-offs

- Keyset pagination không hỗ trợ trực tiếp “nhảy tới page 500”.
- Cursor contract phức tạp hơn page number.
- Covering index tăng storage và write amplification.
- Consistent snapshot xuyên nhiều requests đòi hỏi state/version semantics phức tạp hơn và có thể không đáng cho product catalog.
- OFFSET vẫn có thể hợp lý cho dataset nhỏ/admin UI có random page navigation; không cần thay mọi endpoint bằng cursor.

## Cách kiểm thử

1. **Database performance test:** so sánh logical reads/duration ở page nông và sâu với OFFSET, rồi so với keyset trên production-like data volume.
2. **Correctness test:** nhiều rows cùng `UpdatedAtUtc`; traversal phải không duplicate do tie ordering.
3. **Concurrent-update test:** update products giữa hai requests và xác minh behavior phù hợp documented cursor semantics.
4. **Plan regression test:** kiểm tra actual plan/index usage với category cardinalities khác nhau và updated statistics.
5. **API validation test:** invalid/oversized page size hoặc malformed cursor bị reject có kiểm soát.

## Quan sát trong production

Theo dõi endpoint p50/p95/p99 theo pagination depth/cursor usage, SQL duration, logical reads, CPU, waits và query-plan regressions. Query Store/actual execution plan khi điều tra cần được correlate với category/selectivity và parameter values.

API telemetry nên ghi page size và loại pagination nhưng tránh log opaque cursor đầy đủ nếu không cần. Sau rollout, so sánh DB load/request và user-visible latency trước khi kết luận index/cursor đã giải quyết bottleneck.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc jump trực tiếp tới page 500, bạn giữ OFFSET hay thiết kế alternative nào và vì sao?
2. Keyset pagination có loại bỏ hoàn toàn duplicate/missing data khi rows update liên tục không? Semantics nào vẫn cần định nghĩa?
3. Bạn sẽ quyết định INCLUDE `Name, Price` vào index dựa trên evidence nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Scheduled/background work trong một web process phải được đánh giá lại ngay khi application scale-out: mỗi instance có scheduler và memory riêng. Correctness cần durable ownership/idempotency thay vì in-process synchronization. Với external side effects, luôn phân tích ambiguous failure và retry semantics.

Pagination cũng là bài toán correctness chứ không chỉ performance. OFFSET có chi phí tăng theo depth và position-based pages có thể không ổn định khi dataset thay đổi. Stable ordering, keyset cursor và index design dựa trên execution evidence là các công cụ cần cân nhắc theo UX requirement.

## Mẫu tư duy cần nhớ

- Khi scale-out, hỏi **ai sở hữu một logical work item** và invariant được enforce ở đâu.
- Thiết kế retry cùng idempotency; đừng coi retry là độc lập với side effects.
- Với SQL performance, **measure execution plan/logical reads before adding indexes**.
- Pagination cần deterministic ordering và semantics rõ dưới concurrent writes.
- Giải pháp đơn giản đủ correctness thường tốt hơn thêm infrastructure chưa được chứng minh cần thiết.
