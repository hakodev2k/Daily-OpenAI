# Code Review Challenge 1 — Retry external API tưởng là tăng reliability nhưng lại tạo retry storm, socket pressure và request latency khó kiểm soát

**Chủ đề:** C#/.NET, ASP.NET Core, `HttpClient`, `IHttpClientFactory`, connection pooling, DNS, timeout, retry, cancellation, dependency failure, resilience, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core .NET 8 API tích hợp với external pricing provider. Mỗi request từ frontend có thể cần gọi provider để lấy giá hiện tại cho tối đa 20 sản phẩm.

Yêu cầu:

- request của user không nên treo quá lâu khi provider chậm;
- provider đôi lúc trả `429`, `503` hoặc timeout;
- application chạy nhiều Azure App Service instances;
- provider có rate limit theo toàn bộ client account, không phải theo từng application instance;
- DNS của provider có thể thay đổi khi họ fail over;
- client cancellation nên dừng work còn hữu ích càng sớm càng tốt;
- retry chỉ được dùng khi operation an toàn để retry;
- p95 của endpoint mục tiêu dưới 2 giây trong điều kiện bình thường;
- khi provider outage, hệ thống nên degrade có kiểm soát thay vì tự khuếch đại traffic.

Production gần đây xuất hiện:

- outbound request count tăng mạnh đúng lúc provider có sự cố;
- một số request người dùng mất 15–30 giây mới fail;
- số connection/TCP socket tăng đáng kể;
- provider phản ánh client đang gửi nhiều request lặp trong thời gian họ trả `503`;
- restart App Service tạm thời làm symptom giảm;
- team chưa có metric cho số retry trên mỗi logical operation, queueing time hoặc active outbound calls.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class PricingGateway
{
    private readonly IConfiguration _configuration;
    private readonly ILogger<PricingGateway> _logger;

    public PricingGateway(
        IConfiguration configuration,
        ILogger<PricingGateway> logger)
    {
        _configuration = configuration;
        _logger = logger;
    }

    public async Task<PriceDto?> GetPriceAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        for (var attempt = 1; attempt <= 5; attempt++)
        {
            try
            {
                using var client = new HttpClient();
                client.Timeout = TimeSpan.FromSeconds(10);

                var apiKey = _configuration["Pricing:ApiKey"];
                client.DefaultRequestHeaders.Add("X-Api-Key", apiKey);

                var response = await client.GetAsync(
                    $"https://pricing.example.com/api/prices/{sku}");

                if ((int)response.StatusCode >= 500 ||
                    response.StatusCode == HttpStatusCode.TooManyRequests)
                {
                    await Task.Delay(500);
                    continue;
                }

                response.EnsureSuccessStatusCode();

                var json = await response.Content.ReadAsStringAsync();
                return JsonSerializer.Deserialize<PriceDto>(json);
            }
            catch (Exception ex)
            {
                _logger.LogWarning(
                    ex,
                    "Pricing call failed for {Sku}, attempt {Attempt}",
                    sku,
                    attempt);

                await Task.Delay(500);
            }
        }

        return null;
    }
}
```

## Kết quả code review tham khảo

### Critical — Retry policy có thể tạo retry amplification khi dependency đang lỗi

**Vấn đề:**  
Mỗi SKU retry tối đa 5 lần với delay cố định 500 ms. Một request có thể có nhiều SKU, nhiều request chạy đồng thời và nhiều App Service instances cùng áp dụng policy này.

**Tại sao xảy ra:**  
Khi provider trả `429`/`503`, tất cả callers có thể retry gần cùng nhịp. Fixed delay làm nhiều requests thức dậy cùng lúc, tạo synchronized retry burst. Nếu mỗi user request fan-out thành nhiều dependency calls, số traffic tới provider có thể tăng mạnh đúng lúc provider yếu nhất.

**Ảnh hưởng production:**  
Provider outage kéo dài, rate limit nặng hơn, latency tăng, outbound resource pressure tăng và failure lan sang API của mình.

**Cách sửa:**  
Thiết kế retry có giới hạn, exponential backoff + jitter khi phù hợp, tôn trọng `Retry-After`, chỉ retry failure thực sự transient và đặt retry trong một tổng latency budget. Bổ sung concurrency/rate control phù hợp với quota toàn client account. Cân nhắc circuit breaker hoặc short-circuit khi dependency đang lỗi kéo dài, nhưng chỉ nếu behavior phù hợp product requirements.

---

### High — Tạo `HttpClient` mới cho từng attempt làm mất lợi ích của connection pooling

**Vấn đề:**  
`new HttpClient()` nằm bên trong retry loop.

**Tại sao xảy ra:**  
Mỗi `HttpClient` instance có connection pool riêng thông qua handler của nó. Tạo và dispose client liên tục ngăn tái sử dụng connections hiệu quả và có thể gây connection/port pressure dưới tải.

**Ảnh hưởng production:**  
Thêm TCP/TLS setup, latency cao hơn, nhiều sockets/TIME_WAIT và nguy cơ resource exhaustion.

**Cách sửa:**  
Dùng `IHttpClientFactory`/typed client hoặc một long-lived `HttpClient` với handler lifecycle được cấu hình phù hợp. Nếu dùng long-lived client, cân nhắc `PooledConnectionLifetime` để connections được tái tạo định kỳ khi cần phản ứng với DNS changes.

---

### High — Không có latency budget tổng cho logical operation

**Vấn đề:**  
Mỗi attempt có timeout 10 giây, nhưng có thể chạy 5 attempts cộng delay.

**Tại sao xảy ra:**  
Per-attempt timeout không đảm bảo toàn operation nằm trong endpoint SLO. Worst-case latency có thể lớn hơn nhiều so với 2 giây mục tiêu.

**Ảnh hưởng production:**  
Request giữ resources lâu, user chờ lâu, downstream retries từ client/load balancer có thể xuất hiện và tạo thêm load.

**Cách sửa:**  
Đặt overall request/dependency budget và phân bổ cho attempts. Cancellation/timeout cần compose với request cancellation. Khi budget hết, dừng retry.

---

### High — `CancellationToken` không được propagate

**Vấn đề:**  
`GetAsync`, `ReadAsStringAsync` và `Task.Delay` không dùng `cancellationToken`.

**Tại sao xảy ra:**  
Khi browser đóng request hoặc ASP.NET Core request bị abort, outbound work vẫn có thể tiếp tục.

**Ảnh hưởng production:**  
Waste outbound capacity, giữ connections/tasks lâu hơn cần thiết và làm outage amplification nặng hơn.

**Cách sửa:**  
Propagate token qua network I/O và delays. Nếu có overall timeout, liên kết token bằng `CancellationTokenSource.CreateLinkedTokenSource` hoặc resilience pipeline tương đương.

---

### High — Catch mọi exception rồi retry làm mất distinction giữa cancellation, permanent và transient failure

**Vấn đề:**  
`catch (Exception)` biến gần như mọi lỗi thành retry.

**Tại sao xảy ra:**  
Caller cancellation, malformed response, authentication failure, serialization bug và transient network error có semantics khác nhau.

**Ảnh hưởng production:**  
Retry vô ích, che bug, tăng latency và traffic.

**Cách sửa:**  
Phân loại exception/status. Cancellation do caller không nên được retry như transient dependency failure. `401/403` thường cần config/credential remediation thay vì immediate retry. Serialization/schema incompatibility cần telemetry rõ và thường không nên retry cùng payload liên tục.

---

### Medium — Không xử lý `Retry-After` và response lifecycle rõ ràng

**Vấn đề:**  
Code retry `429` bằng fixed delay và không dispose response trước vòng lặp tiếp theo một cách explicit.

**Tại sao xảy ra:**  
Provider có thể đưa guidance về thời điểm retry. Response/content cần lifecycle rõ để connections có thể được tái sử dụng đúng cách.

**Ảnh hưởng production:**  
Retry quá sớm, rate-limit kéo dài và connection reuse kém hiệu quả.

**Cách sửa:**  
Dispose response theo scope phù hợp, đọc `Retry-After` nếu contract/provider hỗ trợ và bound delay vào overall budget.

---

### Medium — API key lấy trực tiếp từ generic configuration nhưng không thể hiện secret-management boundary

**Vấn đề:**  
Snippet không cho thấy API key được lấy từ secret store hay được rotate thế nào.

**Tại sao xảy ra:**  
`IConfiguration` có thể aggregate nhiều providers; nếu secret nằm trong plain settings/repository/environment workflow không được kiểm soát, risk tăng.

**Ảnh hưởng production:**  
Credential leakage/rotation difficulty.

**Cách sửa:**  
Dùng approved secret mechanism như Key Vault/Managed Identity-based retrieval path khi phù hợp hệ thống, không log key, và thiết kế rotation rõ. Không cần fetch secret từ remote vault trên mỗi request nếu provider/config integration đã materialize an toàn.

### Medium — `return null` làm mất failure semantics

**Vấn đề:**  
Sau 5 attempts code trả `null` cho mọi failure.

**Tại sao xảy ra:**  
Caller không phân biệt “SKU không có giá” với “dependency unavailable”.

**Ảnh hưởng production:**  
UI/business logic có thể hiểu outage như dữ liệu hợp lệ bị thiếu; observability và fallback behavior khó kiểm soát.

**Cách sửa:**  
Trả typed result/failure hoặc throw domain/integration exception được map rõ. Nếu product cho phép stale/fallback value, thể hiện source/freshness thay vì im lặng trả `null`.

## Phiên bản đề xuất

Ví dụ dưới đây dùng typed client và một overall timeout budget. Retry implementation có thể dùng resilience pipeline chuẩn của application; đoạn code tập trung vào lifecycle và semantics:

```csharp
public sealed class PricingClient
{
    private readonly HttpClient _httpClient;
    private readonly ILogger<PricingClient> _logger;

    public PricingClient(
        HttpClient httpClient,
        ILogger<PricingClient> logger)
    {
        _httpClient = httpClient;
        _logger = logger;
    }

    public async Task<PriceResult> GetPriceAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        using var budgetCts = CancellationTokenSource
            .CreateLinkedTokenSource(cancellationToken);
        budgetCts.CancelAfter(TimeSpan.FromSeconds(2));

        var ct = budgetCts.Token;

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                using var request = new HttpRequestMessage(
                    HttpMethod.Get,
                    $"api/prices/{Uri.EscapeDataString(sku)}");

                using var response = await _httpClient.SendAsync(
                    request,
                    HttpCompletionOption.ResponseHeadersRead,
                    ct);

                if (response.StatusCode == HttpStatusCode.NotFound)
                    return PriceResult.NotFound();

                if (response.IsSuccessStatusCode)
                {
                    await using var stream = await response.Content
                        .ReadAsStreamAsync(ct);

                    var price = await JsonSerializer
                        .DeserializeAsync<PriceDto>(stream, cancellationToken: ct);

                    return price is null
                        ? PriceResult.InvalidResponse()
                        : PriceResult.Success(price);
                }

                if (!IsTransient(response.StatusCode) || attempt == 3)
                {
                    return PriceResult.DependencyFailure(
                        (int)response.StatusCode);
                }

                var delay = GetBoundedRetryDelay(response, attempt);
                await Task.Delay(delay, ct);
            }
            catch (OperationCanceledException)
                when (cancellationToken.IsCancellationRequested)
            {
                throw;
            }
            catch (OperationCanceledException)
                when (budgetCts.IsCancellationRequested)
            {
                return PriceResult.Timeout();
            }
            catch (HttpRequestException ex) when (attempt < 3)
            {
                _logger.LogWarning(
                    ex,
                    "Transient pricing failure for {Sku}; attempt {Attempt}",
                    sku,
                    attempt);

                await Task.Delay(BackoffWithJitter(attempt), ct);
            }
        }

        return PriceResult.DependencyFailure();
    }
}
```

Registration có thể là:

```csharp
builder.Services
    .AddHttpClient<PricingClient>(client =>
    {

            builder.Configuration["Pricing:BaseUrl"]!);

    });
```

Nếu API key là header bắt buộc, thêm qua typed client/delegating handler từ secret material đã được provision an toàn, thay vì tạo client mới mỗi call.

Nếu dùng long-lived `HttpClient` trực tiếp thay cho factory, cấu hình `SocketsHttpHandler.PooledConnectionLifetime` theo DNS/failover characteristics đã đo/biết. Microsoft hướng dẫn rằng `HttpClient` chỉ resolve DNS khi tạo connection; connection lifetime cần được quản lý nếu DNS có thể thay đổi.

Một điểm quan trọng khác: retry policy phải được thiết kế cùng fan-out. Nếu endpoint gọi 20 SKU song song, cần bounded concurrency hoặc preferably provider API hỗ trợ batch nếu có. Per-instance semaphore không đủ để enforce quota toàn client account nếu có nhiều instances; có thể cần rate coordination ở shared layer hoặc giảm fan-out theo provider contract.

## Giải thích thiết kế sau khi sửa

Thiết kế mới coi mỗi pricing lookup là một **logical operation có budget**, thay vì cho từng retry tự quyết định timeout. Long-lived/factory-managed handlers cho phép connection reuse. Retry được giới hạn và chỉ áp dụng cho transient failures; caller cancellation được preserve.

Circuit breaker có thể giúp giảm request flood khi dependency outage, nhưng không phải default answer. Threshold/window phải dựa trên traffic profile, SLO và cách product degrade. Nếu pricing là bắt buộc để checkout, fallback stale price có thể nguy hiểm; nếu chỉ là display estimate, cached last-known value có thể được chấp nhận nếu UI ghi freshness rõ.

## Trade-offs

- Retry ít hơn giảm amplification nhưng có thể giảm success rate cho transient lỗi rất ngắn.
- Overall timeout chặt bảo vệ API SLO nhưng có thể fail những calls mà provider cuối cùng sẽ trả thành công.
- Bounded concurrency bảo vệ dependency nhưng tạo queueing; phải đo queue wait.
- `IHttpClientFactory` đơn giản hóa handler pooling/DI nhưng không tự giải quyết global rate limit hoặc retry correctness.
- Long-lived client với `PooledConnectionLifetime` có ít factory abstraction hơn nhưng team phải quản lý handler settings có chủ đích.

## Cách kiểm thử

1. **Failure-path test:** provider trả `503` liên tục; verify số attempts bị giới hạn, overall duration nằm trong budget và không retry vô hạn.
2. **Rate-limit test:** provider trả `429` + `Retry-After`; verify client không retry trước policy cho phép và không vượt overall budget.
3. **Cancellation test:** hủy request trong lúc outbound call/delay; verify work dừng nhanh và không bị log như dependency error thông thường.
4. **Load test:** nhiều user requests × nhiều SKU; đo active outbound calls, connection reuse, socket count, retry amplification và endpoint p95/p99.
5. **Integration/failover test:** đổi DNS/upstream endpoint trong test environment phù hợp; verify handler lifecycle cho phép application chuyển sang address mới theo expected behavior.

# Code Review Challenge 2 — MongoDB booking counter bị overbook dù mọi request đều “check còn chỗ trước khi update”

**Chủ đề:** MongoDB, concurrency, atomic single-document update, optimistic condition, indexes, data modeling, booking correctness, ASP.NET Core integration, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một event-management platform dùng MongoDB cho inventory của từng event session. Mỗi document biểu diễn một session:

```json
{
  "_id": "session-2026-09-11-am",
  "eventId": "evt-1001",
  "capacity": 100,
  "reserved": 87,
  "updatedAtUtc": "2026-09-11T01:00:00Z"
}
```

API `POST /sessions/{id}/reserve` nhận `quantity` từ 1–5.

Yêu cầu:

- không được để `reserved > capacity`;
- nhiều users có thể reserve cùng lúc khi ticket mở bán;
- mỗi request chỉ cập nhật một session document;
- nếu request không còn đủ chỗ phải trả conflict/business error rõ ràng;
- API chạy nhiều instances;
- traffic burst có thể lên hàng trăm requests/giây cho cùng một session;
- application không muốn dùng distributed lock nếu MongoDB có thể enforce invariant đơn giản hơn;
- retry từ client hoặc reverse proxy có thể xảy ra, nhưng business hiện chưa chốt reservation idempotency contract.

Production test với 100 slots còn trống và 150 concurrent requests đôi khi kết thúc với `reserved` lớn hơn `capacity`. Team ngạc nhiên vì code luôn đọc `reserved` trước rồi mới save.

## Đoạn code cần review

```csharp
[HttpPost("sessions/{id}/reserve")]
public async Task<IActionResult> Reserve(
    string id,
    [FromBody] ReserveRequest request,
    CancellationToken cancellationToken)
{
    if (request.Quantity <= 0)
        return BadRequest();

    var session = await _sessions
        .Find(x => x.Id == id)
        .FirstOrDefaultAsync(cancellationToken);

    if (session is null)
        return NotFound();

    if (session.Reserved + request.Quantity > session.Capacity)
        return Conflict("Not enough capacity");

    session.Reserved += request.Quantity;
    session.UpdatedAtUtc = DateTime.UtcNow;

    await _sessions.ReplaceOneAsync(
        x => x.Id == id,
        session,
        cancellationToken: cancellationToken);

    return Ok(new
    {
        session.Id,
        session.Reserved
    });
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code theo góc nhìn production và:

1. xác định correctness/concurrency issues và các vấn đề input/API semantics;
2. giải thích vì sao read-check-replace vẫn có thể overbook hoặc lost update dưới concurrency;
3. ưu tiên findings theo severity;
4. đề xuất cách enforce invariant `reserved + quantity <= capacity` bằng database operation phù hợp;
5. phân tích khi nào single-document atomicity đủ và khi nào mới cần transaction/distributed coordination;
6. mô tả strategy cho client retry/idempotency;
7. đề xuất indexes, tests và telemetry cho hot-session contention.

## Câu hỏi gợi mở

1. Hai requests cùng đọc `reserved = 87`, mỗi request reserve 5; điều gì có thể xảy ra khi cả hai cùng `ReplaceOne`?
2. Có thể đưa điều kiện “còn đủ capacity” vào chính filter của update thay vì check ở application trước không?
3. MongoDB guarantee atomicity ở mức nào cho một write trên một document?
4. Nếu update trả `MatchedCount = 0`, làm sao phân biệt session không tồn tại với session đã hết chỗ?
5. Nếu client timeout sau khi database đã increment thành công rồi retry request, invariant capacity có đủ để ngăn duplicate reservation business effect không?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **time-of-check vs time-of-use**: quyết định được đưa ra từ snapshot đã cũ trước khi write diễn ra.

### Gợi ý 2

MongoDB có atomic single-document writes. Hãy thử encode business precondition vào cùng operation với `$inc` thay vì dùng read → mutate → replace.

## Kết quả code review tham khảo

### Critical — Check capacity và increment không atomic

**Vấn đề:**  
Code đọc document, check capacity ở application rồi mới `ReplaceOne`.

**Tại sao xảy ra:**  
Giữa read và write, request khác có thể thay đổi cùng document. Application đang đưa quyết định dựa trên state có thể đã stale.

**Ảnh hưởng production:**  
Overbooking hoặc kết quả reservation không phản ánh thứ tự concurrent operations.

**Cách sửa:**  
Đưa precondition vào filter của atomic update và dùng `$inc`, ví dụ chỉ match document khi `reserved <= capacity - quantity`.

---

### High — Full-document replacement có thể tạo lost update

**Vấn đề:**  
`ReplaceOne` ghi lại toàn bộ snapshot đã đọc.

**Tại sao xảy ra:**  
Nếu hai requests đọc cùng version rồi thay đổi độc lập, write sau có thể overwrite fields được write trước hoặc làm response/business state khó reasoning.

**Ảnh hưởng production:**  
Mất update trên `reserved` hoặc các fields khác được sửa đồng thời.

**Cách sửa:**  
Dùng targeted atomic update (`$inc`, `$set`) với concurrency predicate thay vì replace snapshot. Nếu nhiều independent fields có concurrency rules khác nhau, thêm version field/optimistic concurrency policy khi cần.

---

### High — Chỉ validate `quantity > 0`, không enforce business maximum

**Vấn đề:**  
Requirement cho phép 1–5 nhưng code chấp nhận mọi positive integer.

**Tại sao xảy ra:**  
Validation implementation không khớp API contract.

**Ảnh hưởng production:**  
Một caller có thể reserve quantity rất lớn nếu capacity cho phép hoặc gây integer/business edge cases.

**Cách sửa:**  
Validate `quantity is >= 1 and <= 5`, đồng thời enforce domain invariant ở service/database path chứ không chỉ UI.

---

### High — Reservation operation chưa có idempotency contract

**Vấn đề:**  
Một atomic `$inc` giải concurrency invariant nhưng không tự đảm bảo cùng logical request chỉ increment một lần.

**Tại sao xảy ra:**  
Nếu database update thành công nhưng client timeout trước response, client có thể retry và increment lần nữa với request mới giống hệt.

**Ảnh hưởng production:**  
Một user có thể giữ nhiều slots hơn dự định dù `reserved <= capacity` vẫn đúng.

**Cách sửa:**  
Nếu retries phải an toàn, dùng stable reservation/request id và durable idempotency design. Tùy data model, reservation IDs có thể được lưu/enforce cùng document nếu bounded, hoặc trong collection riêng với unique key + transaction khi operation cần atomically cập nhật nhiều documents.

---

### Medium — `MatchedCount == 0` cần mapping business outcome chính xác

**Vấn đề:**  
Sau conditional update, zero match có thể là “session không tồn tại” hoặc “không đủ capacity”.

**Tại sao xảy ra:**  
Một operation filter chứa cả `_id` và capacity predicate không tự nói predicate nào fail.

**Ảnh hưởng production:**  
API có thể trả 409 sai cho missing session hoặc 404 sai cho sold-out session.

**Cách sửa:**  
Nếu contract cần phân biệt, thực hiện read nhỏ bổ sung sau failed conditional update, hoặc model status/result khác. Chấp nhận race trong diagnostic read bằng cách coi nó là classification best-effort và document semantics.

---

### Medium — Hot document có thể trở thành contention hotspot

**Vấn đề:**  
Mọi reservations cho một popular session cập nhật cùng document.

**Tại sao xảy ra:**  
Single-document atomicity đảm bảo correctness nhưng writes vẫn serialize/contend trên một hot key ở traffic lớn.

**Ảnh hưởng production:**  
Latency tăng, write retries/queueing tăng khi campaign burst lớn.

**Cách sửa:**  
Đầu tiên đo throughput/latency. Không shard counter phức tạp nếu current workload vẫn đáp ứng SLO, vì sharded counter làm invariant capacity khó hơn. Nếu hotspot thực sự vượt giới hạn, redesign reservation model/partitioning cần giữ correctness bằng cơ chế phù hợp.

---

### Medium — Response dùng local in-memory value thay vì authoritative updated document

**Vấn đề:**  
Code trả `session.Reserved` từ snapshot local.

**Tại sao xảy ra:**  
Sau khi chuyển sang atomic conditional update, local snapshot không còn là authoritative result.

**Ảnh hưởng production:**  
Client có thể nhận count không chính xác hoặc implementation buộc phải thêm read không cần thiết.

**Cách sửa:**  
Dùng `FindOneAndUpdate` với return document option nếu cần updated count, hoặc chỉ trả reservation success nếu client không cần global count chính xác.

---

### Low — Index/query strategy cần explicit dù `_id` đã có index mặc định

**Vấn đề:**  
Query hiện dùng `Id == id`; nếu map đúng vào Mongo `_id`, default unique `_id` index đã phục vụ lookup. Nhưng nếu domain `Id` là field riêng hoặc future query thêm `eventId/status`, assumptions phải được verify.

**Tại sao xảy ra:**  
Index design phải dựa trên actual persisted field/query shape.

**Ảnh hưởng production:**  
Query scan hoặc incorrect uniqueness assumptions nếu mapping khác dự kiến.

**Cách sửa:**  
Xác minh serializer mapping. Không thêm redundant index nếu `_id` đã đúng key; thêm indexes chỉ theo measured query patterns.

## Phiên bản đề xuất

Vì invariant nằm hoàn toàn trong một session document, single-document conditional update có thể đủ:

```csharp
[HttpPost("sessions/{id}/reserve")]
public async Task<IActionResult> Reserve(
    string id,
    [FromBody] ReserveRequest request,
    CancellationToken cancellationToken)
{
    if (request.Quantity is < 1 or > 5)
        return BadRequest("Quantity must be between 1 and 5.");

    var filter = Builders<EventSession>.Filter.And(
        Builders<EventSession>.Filter.Eq(x => x.Id, id),
        Builders<EventSession>.Filter.Expr(
            new BsonDocument("$lte", new BsonArray
            {
                new BsonDocument("$add", new BsonArray
                {
                    "$reserved",
                    request.Quantity
                }),
                "$capacity"
            })));

    var update = Builders<EventSession>.Update
        .Inc(x => x.Reserved, request.Quantity)
        .Set(x => x.UpdatedAtUtc, DateTime.UtcNow);

    var options = new FindOneAndUpdateOptions<EventSession>
    {
        ReturnDocument = ReturnDocument.After
    };

    var updated = await _sessions.FindOneAndUpdateAsync(
        filter,
        update,
        options,
        cancellationToken);

    if (updated is null)
    {
        var exists = await _sessions
            .Find(x => x.Id == id)
            .Project(x => x.Id)
            .AnyAsync(cancellationToken);

        return exists
            ? Conflict("Not enough capacity")
            : NotFound();
    }

    return Ok(new
    {
        updated.Id,
        updated.Reserved
    });
}
```

Một filter khác dễ index/reasoning hơn có thể lưu thêm `remaining` hoặc dùng expression phù hợp data model, nhưng phải bảo đảm invariant không bị tách thành hai writes độc lập.

MongoDB đảm bảo một write trên một document là atomic. Vì `capacity` và `reserved` nằm cùng document, ta có thể encode predicate và increment vào một atomic single-document update mà không cần distributed lock.

Tuy nhiên, nếu reservation còn phải đồng thời tạo một document riêng, ghi payment hold hoặc enforce unique `reservationId` ở collection khác, single-document atomicity không còn cover toàn business transaction. Khi đó cân nhắc data-model redesign hoặc MongoDB transaction nếu thật sự cần multi-document atomicity; không thêm transaction chỉ vì “concurrency nghe nguy hiểm”.

Nếu idempotency là requirement, một hướng có thể là `reservations` collection với unique `(sessionId, reservationId)` và transaction cập nhật session counter + insert reservation marker. Thiết kế cụ thể phụ thuộc retry/expiry/cancellation semantics.

Tài liệu tham khảo:

- MongoDB Manual — Atomicity and Transactions: `https://www.mongodb.com/docs/manual/core/write-operations-atomicity/`
- MongoDB Manual — Indexes: `https://www.mongodb.com/docs/manual/indexes/`

## Giải thích thiết kế sau khi sửa

Fix chính là chuyển từ:

```text
read → check → modify local object → replace
```

sang:

```text
conditional filter + atomic increment
```

Database trở thành nơi enforce invariant tại write boundary. Đây là cách đơn giản hơn distributed lock cho invariant một-document.

Không nên nhầm **capacity correctness** với **request idempotency**. Atomic update bảo đảm không vượt capacity nếu predicate đúng, nhưng retry cùng logical reservation vẫn có thể tiêu thêm slot. Hai requirements cần hai cơ chế khác nhau.

## Trade-offs

- Single-document counter đơn giản và strongly localized nhưng có thể trở thành hot key dưới burst rất lớn.
- Multi-document transaction có thể giải atomicity rộng hơn nhưng tăng latency/operational cost; chỉ dùng khi invariant thực sự span nhiều documents.
- Idempotency marker embedded cùng session dễ atomic nhưng embedded history có thể tăng document size không giới hạn; collection riêng scalable hơn nhưng cần coordination.
- Trả updated document tiện cho UI nhưng tăng response/read work so với chỉ trả `204` hoặc reservation-specific result.

## Cách kiểm thử

1. **Concurrency test:** capacity còn 100, chạy 150 concurrent requests `quantity=1`; verify số successful reservations đúng giới hạn và `reserved <= capacity` luôn đúng.
2. **Mixed-quantity test:** concurrent quantities 1–5; verify aggregate accepted quantity không vượt remaining capacity.
3. **Retry/idempotency test:** giả lập timeout sau successful database write rồi gửi lại cùng logical reservation ID; verify behavior đúng với contract đã chọn.
4. **Load test:** hàng trăm requests/giây vào cùng session; đo Mongo write latency, failure/conflict rate và API p95/p99.
5. **Validation test:** quantity 0, âm, >5, missing session, sold-out session và cancellation.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `HttpClient` resilience không chỉ là “thêm retry”. Connection lifetime, DNS, timeout budget, fan-out, rate limit và cancellation phải được thiết kế cùng nhau.
- Retry có thể biến dependency outage thành **retry storm** nếu mỗi logical request nhân thành nhiều attempts đồng bộ.
- `IHttpClientFactory` hoặc long-lived `HttpClient` giúp quản lý connection reuse tốt hơn việc tạo-dispose client cho từng call; DNS changes cần được xem cùng connection lifetime.
- Với MongoDB, read-check-write ở application không bảo vệ invariant dưới concurrency. Nếu invariant nằm trong một document, conditional atomic update thường đơn giản và đúng hơn distributed locking.
- Atomicity và idempotency là hai bài toán khác nhau: database update có thể atomic nhưng cùng logical request vẫn bị áp dụng hai lần khi client retry.

## Mẫu tư duy cần nhớ

- **Budget cả logical operation, không chỉ timeout từng attempt.**
- **Retry phải giảm xác suất lỗi, không được khuếch đại outage.**
- **Đưa concurrency invariant xuống atomic write boundary khi có thể.**
- **Phân biệt correctness, idempotency và performance; mỗi loại có failure model riêng.**
- **Measure contention/attempt amplification trước khi thêm coordination phức tạp.**
