# Code Review Challenge 1 — `BackgroundService` chạy ổn một instance nhưng lỗi ngẫu nhiên sau scale-out và shutdown

**Chủ đề:** C#, .NET, `BackgroundService`, dependency injection, `DbContext`, concurrency, cancellation, graceful shutdown, multiple application instances  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 8–12 vấn đề

## Bối cảnh

Một ASP.NET Core application trên .NET 8 có background job đồng bộ trạng thái đơn hàng từ một external provider. Application chạy trên Azure App Service với nhiều instances sau khi traffic tăng.

Business yêu cầu:

- mỗi order cần được đồng bộ định kỳ;
- cùng một order không được bị update cạnh tranh gây lost update;
- external provider có rate limit;
- khi deploy/restart, application cần dừng có kiểm soát;
- một lần provider timeout không được làm toàn bộ worker chết;
- nếu scale từ 1 lên 4 instances, hệ thống vẫn phải giữ correctness.

Production bắt đầu xuất hiện:

- `InvalidOperationException` liên quan đến EF Core concurrent operation;
- một số order được gọi external API nhiều lần gần như đồng thời;
- provider trả 429 nhiều hơn sau scale-out;
- lúc deploy có các request outbound vẫn chạy sau khi instance bắt đầu shutdown;
- đôi lúc toàn bộ worker dừng xử lý sau một exception không được dự kiến;
- local test với một instance và ít dữ liệu thường không tái hiện lỗi.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class OrderSyncWorker : BackgroundService
{
    private readonly AppDbContext _db;
    private readonly IOrderProviderClient _client;
    private readonly ILogger<OrderSyncWorker> _logger;
    private readonly Timer _timer;

    public OrderSyncWorker(
        AppDbContext db,
        IOrderProviderClient client,
        ILogger<OrderSyncWorker> logger)
    {
        _db = db;
        _client = client;
        _logger = logger;
        _timer = new Timer(
            _ => _ = RunOnceAsync(),
            null,
            TimeSpan.Zero,
            TimeSpan.FromMinutes(1));
    }

    protected override Task ExecuteAsync(CancellationToken stoppingToken)
    {
        return Task.CompletedTask;
    }

    private async Task RunOnceAsync()
    {
        var orders = await _db.Orders
            .Where(x => x.Status == OrderStatus.PendingSync)
            .Take(200)
            .ToListAsync();

        var tasks = orders.Select(async order =>
        {
            var remote = await _client.GetStatusAsync(order.ExternalId);

            order.Status = remote.Status;
            order.LastSyncedAt = DateTime.UtcNow;

            await _db.SaveChangesAsync();
        });

        await Task.WhenAll(tasks);

        _logger.LogInformation(
            "Synced {Count} orders at {Time}",
            orders.Count,
            DateTime.UtcNow);
    }

    public override void Dispose()
    {
        _timer.Dispose();
        base.Dispose();
    }
}
```

## Câu hỏi gợi mở

1. `BackgroundService` có lifetime gì và `AppDbContext` thường được đăng ký với lifetime gì trong ASP.NET Core?
2. Điều gì xảy ra khi `Timer` tick lần tiếp theo trong lúc `RunOnceAsync()` cũ chưa xong?

## Kết quả code review tham khảo

### Critical — Một `DbContext` bị dùng đồng thời bởi nhiều tasks

**Vấn đề:** Tất cả tasks trong `Task.WhenAll` cùng dùng `_db` để mutate tracked entities và gọi `SaveChangesAsync()`.

**Tại sao xảy ra:** `DbContext` được thiết kế như một unit of work và không hỗ trợ nhiều operations chạy song song trên cùng instance. Ở đây query ban đầu tạo tracked entities trong cùng context, sau đó nhiều tasks cùng thay đổi state và save.

**Ảnh hưởng production:** Có thể xuất hiện exception về concurrent operations, state tracking không đáng tin cậy, SaveChanges chứa thay đổi của nhiều entities ngoài phạm vi task dự kiến, và failure behavior khó suy luận.

**Cách sửa:** Không chia sẻ một `DbContext` giữa các parallel operations. Tạo DI scope riêng cho một unit of work phù hợp, hoặc xử lý tuần tự nếu throughput đủ. Nếu cần parallelism, mỗi worker item phải có context riêng và concurrency phải bounded.

### Critical — Scale-out làm cùng scheduled job chạy trên mọi instance

**Vấn đề:** Mỗi application instance tự tạo `Timer` và đều query cùng tập `PendingSync` orders.

**Tại sao xảy ra:** In-process scheduling không có cluster-wide ownership. Scale-out từ 1 lên N instances mặc nhiên tạo N schedulers.

**Ảnh hưởng production:** Cùng order có thể được gọi provider và update đồng thời nhiều lần. Điều này làm tăng traffic downstream, 429, duplicate side effects và race trên database state.

**Cách sửa:** Chọn execution model rõ ràng. Nếu chỉ cần một scheduler toàn hệ thống, dùng một scheduler/worker có cluster coordination phù hợp hoặc external scheduling mechanism. Nếu cho phép nhiều consumers để scale throughput, biến workload thành queue-based work với claim/idempotency/optimistic concurrency rõ ràng thay vì để mọi instance scan cùng dữ liệu.

### High — `Timer` cho phép cùng process chạy chồng nhiều lần

**Vấn đề:** Callback `Timer` fire-and-forget `_ = RunOnceAsync()` và không chờ execution trước hoàn tất.

**Tại sao xảy ra:** Fixed-period timer không tự serialize async callbacks. Nếu một run mất hơn một phút, tick tiếp theo vẫn bắt đầu.

**Ảnh hưởng production:** Một instance cũng có thể xử lý cùng rows nhiều lần, tăng DB/provider load và làm lỗi concurrency nghiêm trọng hơn.

**Cách sửa:** Dùng loop tuần tự trong `ExecuteAsync` với `PeriodicTimer` hoặc delay-after-run semantics, hoặc explicit non-overlap guard nếu requirement thật sự fixed-rate. Nếu cần overlap có chủ đích, phải có work claiming/idempotency thay vì dựa vào timer.

### High — Worker bỏ qua hoàn toàn `stoppingToken`

**Vấn đề:** `ExecuteAsync` trả về ngay, còn real work chạy trong `Timer`; query, HTTP call và save không nhận cancellation token.

**Tại sao xảy ra:** Worker lifecycle bị tách khỏi `BackgroundService` lifecycle.

**Ảnh hưởng production:** Host không thể phối hợp graceful shutdown đúng cách. Deploy có thể cắt ngang I/O đang chạy, kéo dài termination hoặc để state ở failure window khó đoán.

**Cách sửa:** Đặt execution loop trực tiếp trong `ExecuteAsync(stoppingToken)` và propagate token xuống EF Core, HTTP client và các waits. Nếu có operation cần atomic completion bất chấp request cancellation, thiết kế shutdown budget có chủ đích thay vì bỏ token.

### High — Exception trong fire-and-forget run không có ownership rõ

**Vấn đề:** Callback bỏ `Task` trả về từ `RunOnceAsync()`.

**Tại sao xảy ra:** Không có caller await hoặc per-run exception boundary.

**Ảnh hưởng production:** Failure có thể không được xử lý/log đầy đủ theo intended policy. Một transient provider/DB lỗi có thể làm execution kết thúc mà scheduler vẫn tiếp tục mù, hoặc tạo unobserved behavior khó điều tra.

**Cách sửa:** Background loop phải `await` run. Bao quanh từng iteration và từng item bằng exception policy phù hợp. Phân loại transient/permanent error; không catch-all rồi nuốt lỗi mà không telemetry.

### High — Không có concurrency/rate budget đối với external provider

**Vấn đề:** `Task.WhenAll` fan-out tới tối đa 200 calls mỗi run, nhân với số timer overlap và số app instances.

**Tại sao xảy ra:** Parallelism bằng số rows thay vì bằng capacity của dependency.

**Ảnh hưởng production:** Provider 429, timeout và retry amplification. Khi provider chậm, run kéo dài hơn, timer overlap nhiều hơn, tạo feedback loop.

**Cách sửa:** Dùng bounded concurrency (`SemaphoreSlim`, channel/worker pool, `Parallel.ForEachAsync` với giới hạn phù hợp, hoặc queue consumer concurrency). Chọn limit dựa trên provider contract, latency và throughput evidence.

### High — Work claiming/idempotency chưa tồn tại

**Vấn đề:** Query chỉ lấy `PendingSync`, không atomically claim work và không có visible processing lease/version/idempotency state.

**Tại sao xảy ra:** Design giả định “đã query row thì row thuộc worker này”. Điều đó không đúng khi có nhiều runners.

**Ảnh hưởng production:** Hai workers có thể đọc cùng row trước khi bất kỳ bên nào update state.

**Cách sửa:** Nếu processing được scale bằng nhiều workers, cần claim protocol: ví dụ conditional update/lease/version để một worker sở hữu item trong một window, cùng retry-safe idempotency. Nếu provider operation có side effect, dùng stable idempotency key khi provider hỗ trợ.

### Medium — `SaveChangesAsync()` cho từng item làm nhiều database round trips

**Vấn đề:** Mỗi task gọi save riêng.

**Tại sao xảy ra:** Per-item unit of work được trộn với shared context.

**Ảnh hưởng production:** Tăng round trips, connection pressure và contention. Tuy nhiên gom tất cả vào một giant transaction cũng không mặc định tốt hơn.

**Cách sửa:** Chọn transaction/batch boundary theo correctness. Với external HTTP + DB, không giữ DB transaction mở trong lúc network call nếu không cần. Có thể mỗi item có context riêng để state transition rõ ràng, hoặc xử lý batch staged phù hợp.

### Medium — Query không có deterministic ordering/claim semantics

**Vấn đề:** `Take(200)` không nói item nào cần ưu tiên và nhiều workers có thể lấy cùng subset.

**Tại sao xảy ra:** Scheduling policy bị implicit.

**Ảnh hưởng production:** Starvation hoặc repeated hot subset nếu một số rows liên tục fail.

**Cách sửa:** Có ordering rõ như `NextAttemptAt`, retry count, priority, và claim semantics. Poison items phải có dead-letter/manual-review equivalent thay vì luôn nằm ở đầu tập pending.

### Medium — Failure state/retry policy chưa được model hóa

**Vấn đề:** Provider timeout, validation error và 429 đều không có state khác nhau.

**Tại sao xảy ra:** Worker chỉ có happy path.

**Ảnh hưởng production:** Retry không kiểm soát, không có backoff, không biết item nào poison hay transient.

**Cách sửa:** Lưu attempt metadata/`NextAttemptAt` khi phù hợp, bounded retry với backoff/jitter, tách lỗi permanent và transient, có alert/recovery path.

## Phiên bản đề xuất

Ví dụ dưới đây dùng một `BackgroundService` loop không overlap trong process, tạo scope cho từng processing unit và giới hạn concurrency. Đây **không** tự giải quyết multi-instance duplicate processing; production design vẫn cần work claiming hoặc queue/idempotency như giải thích bên dưới.

```csharp
public sealed class OrderSyncWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<OrderSyncWorker> _logger;
    private readonly TimeSpan _interval = TimeSpan.FromMinutes(1);
    private const int MaxConcurrency = 8;

    public OrderSyncWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<OrderSyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(_interval);

        do
        {
            try
            {
                await RunOnceAsync(stoppingToken);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Order sync iteration failed");
            }
        }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }

    private async Task RunOnceAsync(CancellationToken cancellationToken)
    {
        IReadOnlyList<Guid> candidateIds;

        await using (var scope = _scopeFactory.CreateAsyncScope())
        {
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

            candidateIds = await db.Orders
                .AsNoTracking()
                .Where(x => x.Status == OrderStatus.PendingSync)
                .OrderBy(x => x.NextAttemptAt)
                .Select(x => x.Id)
                .Take(200)
                .ToListAsync(cancellationToken);
        }

        await Parallel.ForEachAsync(
            candidateIds,
            new ParallelOptions
            {
                MaxDegreeOfParallelism = MaxConcurrency,
                CancellationToken = cancellationToken
            },
            ProcessOrderAsync);
    }

    private async ValueTask ProcessOrderAsync(
        Guid orderId,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var client = scope.ServiceProvider.GetRequiredService<IOrderProviderClient>();

        var order = await db.Orders
            .SingleOrDefaultAsync(x => x.Id == orderId, cancellationToken);

        if (order is null || order.Status != OrderStatus.PendingSync)
            return;

        // Production code should first perform an atomic claim/version check here
        // when multiple application instances may process the same candidate.

        try
        {
            var remote = await client.GetStatusAsync(
                order.ExternalId,
                cancellationToken);

            order.Status = remote.Status;
            order.LastSyncedAt = DateTime.UtcNow;
            order.RetryCount = 0;
            order.NextAttemptAt = DateTime.UtcNow.AddMinutes(1);

            await db.SaveChangesAsync(cancellationToken);
        }
        catch (ProviderRateLimitException)
        {
            order.RetryCount++;
            order.NextAttemptAt = RetryPolicy.NextAttempt(order.RetryCount);
            await db.SaveChangesAsync(cancellationToken);
        }
    }
}
```

Một design production mạnh hơn khi có nhiều instances là tách **discovery** khỏi **execution**:

1. một scheduler hoặc database claim step xác định work đến hạn;
2. work được claim atomically hoặc enqueue bằng một operation ID ổn định;
3. nhiều consumers xử lý song song theo concurrency budget;
4. mỗi consumer idempotent và dùng optimistic concurrency/unique constraint phù hợp;
5. retry state và dead-letter/reconciliation được model hóa rõ.

Nếu hệ thống nhỏ, throughput thấp và chỉ cần một instance chuyên background work, không nhất thiết phải thêm Service Bus. Một dedicated worker singleton deployment với database claim vẫn có thể đơn giản hơn. Nếu cần scale/reliability cao và workload burst, queue-based design có thể đáng chi phí hơn.

## Giải thích thiết kế sau khi sửa

- `BackgroundService` sở hữu execution lifecycle thay vì `Timer` fire-and-forget.
- `PeriodicTimer` tránh in-process overlap khi một iteration lâu hơn interval.
- `IServiceScopeFactory` tạo scoped dependencies đúng unit-of-work boundary.
- Mỗi parallel item có `DbContext` riêng.
- Parallelism bounded để không fan-out 200 calls cùng lúc.
- `CancellationToken` được propagate xuống timer, EF và HTTP.
- Exception handling nằm ở iteration/item boundary có chủ đích.
- Multi-instance correctness vẫn cần claim/idempotency; scope isolation chỉ sửa lỗi trong process.

## Trade-offs

- Context-per-item tăng số context/connection usages; concurrency limit phải dựa trên DB pool và provider capacity.
- Xử lý tuần tự đơn giản hơn nhưng throughput thấp hơn.
- Database leasing/claiming thêm state và recovery complexity.
- Queue-based processing cải thiện decoupling/backpressure nhưng thêm broker, delivery semantics, DLQ và observability.
- Distributed lock có thể phù hợp cho một số singleton job, nhưng lock expiry, ownership, failover và split-brain semantics phải được thiết kế; không nên coi lock là giải pháp universal.

## Cách kiểm thử

1. **Concurrency test:** chạy hai hoặc nhiều worker instances cùng tập orders và assert mỗi logical operation không tạo conflicting business effect.
2. **Load test:** 200–1000 pending items với provider latency tăng dần, verify concurrency không vượt budget và 429 không tăng theo cấp số nhân.
3. **Failure-path test:** provider timeout/429/5xx, kiểm tra bounded retry, `NextAttemptAt` và worker vẫn tiếp tục xử lý item khác.
4. **Graceful-shutdown test:** gửi cancellation giữa HTTP call và DB save; verify behavior đúng với contract và không tạo orphaned claim.
5. **Database concurrency test:** hai workers cố claim cùng order; chỉ một bên phải thắng nếu design yêu cầu exclusive processing.

## Quan sát trong production

- số worker iterations, duration và overlap count;
- active processing count/concurrency;
- queue/claim backlog hoặc số `PendingSync` quá hạn;
- provider p95/p99, 429/5xx/timeout;
- retry count theo reason;
- duplicate processing/idempotency conflict count;
- EF/SQL dependency latency và connection pool pressure;
- graceful shutdown duration và canceled operations;
- correlation theo `OrderId`, operation ID và app instance.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn database lease/claim thay vì Azure Service Bus cho workload này?
2. Nếu provider operation không idempotent và response timeout không cho biết side effect đã xảy ra hay chưa, bạn thiết kế recovery thế nào?
3. Nếu business yêu cầu mỗi order sync đúng mỗi 60 giây theo wall-clock dù một run kéo dài hơn 60 giây, bạn thay đổi scheduler/execution model ra sao?

# Code Review Challenge 2 — Pipeline “deploy thành công” nhưng artifact không reproducible, secret bị lộ và rollback database gần như không thể

**Chủ đề:** Git, CI/CD, Jenkins/TeamCity concepts, Octopus Deploy concepts, ASP.NET Core, database migrations, secrets, artifact consistency, rollout, rollback  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một team deploy ASP.NET Core application lên Azure App Service. CI chạy build/test, sau đó CD deploy package và chạy EF Core migration.

Team có nhiều environments: Dev, Staging, Production. Một deployment gần đây gặp tình huống:

- Production chạy binary không trùng chính xác artifact đã test ở Staging;
- migration xóa cột cũ trước khi toàn bộ instances chuyển sang version mới;
- rollback code về version trước nhưng version cũ không chạy được với schema mới;
- một connection string xuất hiện trong build log;
- developer rerun pipeline và nhận artifact khác dù dùng cùng branch;
- deployment health check chỉ kiểm tra process trả HTTP 200 ở `/`;
- team hiện có Jenkins/TeamCity cho CI và Octopus Deploy cho release, nhưng vấn đề nằm chủ yếu ở flow chứ chưa rõ do tool.

Pipeline rút gọn hiện tại:

## Đoạn code cần review

```yaml
pipeline:
  variables:
    BRANCH: main
    IMAGE_TAG: latest
    PROD_CONNECTION_STRING: Server=prod-sql;Database=app;User Id=app;Password=P@ssw0rd!

  stages:
    - name: build
      steps:
        - run: git pull origin ${BRANCH}
        - run: dotnet restore
        - run: dotnet test
        - run: dotnet publish src/App/App.csproj -c Release -o ./publish
        - run: zip -r app.zip ./publish
        - run: upload-artifact app.zip --name app-${BRANCH}

    - name: staging
      steps:
        - run: download-artifact app-${BRANCH}
        - run: deploy-appservice staging app.zip
        - run: curl -f https://staging.example.com/

    - name: production
      steps:
        - run: git pull origin ${BRANCH}
        - run: dotnet ef database update --project src/App/App.csproj --connection "${PROD_CONNECTION_STRING}"
        - run: dotnet publish src/App/App.csproj -c Release -o ./publish-prod
        - run: zip -r app-prod.zip ./publish-prod
        - run: deploy-appservice production app-prod.zip
        - run: curl -f https://www.example.com/

    - name: rollback
      when: manual
      steps:
        - run: deploy-appservice production previous.zip
```

3. Phân tích migration ordering và backward compatibility khi old/new app versions cùng tồn tại trong rollout.
4. Ưu tiên issues theo severity.
5. Đề xuất pipeline/release strategy đã sửa ở mức principle và configuration.
6. Mô tả validation trước/sau deploy, rollback và database recovery.
7. Đề xuất telemetry/audit để biết chính xác version nào đang chạy và migration nào đã áp dụng.

## Câu hỏi gợi mở

1. Staging và Production hiện có chắc chắn nhận cùng bytes/artifact không?
2. `git pull main` ở hai thời điểm khác nhau có thể cho kết quả gì?
3. Nếu migration drop/rename column trước khi old instances dừng, version cũ còn hoạt động không?
4. Secret hiện tồn tại ở repository/pipeline definition/log boundary nào?
5. HTTP 200 ở homepage chứng minh được bao nhiêu về database, authentication, critical API và compatibility?

## Gợi ý

### Gợi ý 1

Hãy xem artifact là một immutable release candidate có identity rõ, không phải thứ được build lại ở từng environment.

### Gợi ý 2

Database schema là shared compatibility boundary. Code rollback chỉ an toàn nếu migration strategy được thiết kế để old/new versions có một khoảng schema tương thích.

## Kết quả code review tham khảo

### Critical — Production build lại source thay vì promote artifact đã test

**Vấn đề:** Production chạy `git pull` rồi `dotnet publish` lại.

**Tại sao xảy ra:** Pipeline coi environment deployment như một build mới thay vì promotion của một immutable artifact.

**Ảnh hưởng production:** Commit có thể thay đổi giữa staging và production; dependency restore, toolchain hoặc generated output cũng có thể khác. Staging approval không còn chứng minh bytes được deploy Production đã được test.

**Cách sửa:** Build một lần từ một immutable commit SHA. Tạo package/artifact có version + hash, ký/attest nếu organization yêu cầu, rồi promote **chính artifact đó** qua Staging → Production.

### Critical — Secret production nằm plaintext trong pipeline definition

**Vấn đề:** `PROD_CONNECTION_STRING` chứa credential trực tiếp.

**Tại sao xảy ra:** Secret được quản lý như config text thay vì secret material.

**Ảnh hưởng production:** Có nguy cơ lộ qua source history, pipeline UI, logs, exports hoặc người có quyền đọc config. Credential có thể cần rotate ngay nếu đã commit thật.

**Cách sửa:** Lưu secret trong secret store phù hợp như Azure Key Vault hoặc protected CI/CD secret variable, ưu tiên Managed Identity cho application/runtime khi khả thi. Pipeline không echo secret và permissions theo least privilege.

### Critical — Destructive migration chạy trước application rollout

**Vấn đề:** `dotnet ef database update` được chạy trước deploy mà không biết migration có backward-compatible không.

**Tại sao xảy ra:** Application và database evolution được xem như hai bước tuần tự đơn giản.

**Ảnh hưởng production:** Nếu migration drop/rename column, old instances đang phục vụ traffic có thể lỗi ngay. Rollback code sau đó cũng có thể không chạy với schema mới.

**Cách sửa:** Dùng expand/contract cho breaking schema changes: release schema additive trước, deploy code tương thích old+new, backfill/migrate data, chuyển reads/writes, sau khi mọi version cũ đã rời khỏi fleet và rollback window kết thúc mới contract/drop.

### High — Rollback chỉ có `previous.zip`, không có compatibility/recovery plan

**Vấn đề:** Rollback giả định deploy package cũ là đủ.

**Tại sao xảy ra:** Không phân biệt code rollback với data/schema rollback.

**Ảnh hưởng production:** Version cũ có thể fail vì schema đã thay đổi; destructive data migration có thể không thể reverse an toàn.

**Cách sửa:** Mỗi release cần rollback matrix: code rollback safe đến migration nào, migration nào additive, migration nào irreversible, khi nào dùng forward-fix, restore/point-in-time recovery hoặc repair script. Test rollback path trước production.

### High — Artifact identity theo branch name, không theo commit/release

**Vấn đề:** Artifact tên `app-main`.

**Tại sao xảy ra:** Mutable branch được dùng như version.

**Ảnh hưởng production:** Không biết chính xác commit nào được deploy; rerun có thể ghi đè artifact hoặc trả artifact khác cùng tên.

**Cách sửa:** Version artifact theo immutable identifier như commit SHA + build number/release version. Lưu manifest gồm source SHA, build ID, dependency/tool version khi cần.

### High — `git pull` trong pipeline làm build input không được pin rõ

**Vấn đề:** Pipeline thay đổi workspace bằng pull giữa run.

**Tại sao xảy ra:** Build không dựa trực tiếp trên commit đã trigger.

**Ảnh hưởng production:** Race với branch updates, khó reproduce, khó audit.

**Cách sửa:** CI checkout đúng commit SHA mà run được tạo từ đó. Không pull mutable branch trong deployment stages.

### High — Database migration execution không có preflight/locking/operational safeguards

**Vấn đề:** Chạy migration trực tiếp như một command không có đánh giá lock duration, table size, data backfill hay concurrent release.

**Tại sao xảy ra:** Migrations được coi là luôn nhanh và reversible.

**Ảnh hưởng production:** Long table lock, timeout, partial release hoặc hai deployments cùng cố migrate.

**Cách sửa:** Review migration plan như production change. Tách long-running backfill khỏi schema DDL khi cần; chỉ một migration runner có ownership; có timeout/monitoring và acceptance criteria.

### High — Health validation quá nông

**Vấn đề:** Chỉ `curl /` và kiểm tra HTTP 200.

**Tại sao xảy ra:** Deployment validation không đại diện critical journeys.

**Ảnh hưởng production:** Homepage có thể 200 trong khi DB migration sai, authentication fail, API contract lỗi hoặc downstream unavailable.

**Cách sửa:** Có startup/readiness check đúng semantics, smoke tests cho critical APIs, database compatibility check và Playwright E2E nhỏ cho business path quan trọng khi phù hợp. Không biến health endpoint thành dependency bomb làm restart loop.

### Medium — Không có canary/slot/cutover strategy

**Vấn đề:** Deploy thẳng production package mà không thể hiện warm-up hoặc staged traffic.

**Tại sao xảy ra:** Pipeline chỉ có binary deployment step.

**Ảnh hưởng production:** Regression ảnh hưởng toàn bộ user trước khi telemetry phản hồi.

**Cách sửa:** Nếu platform hỗ trợ và phù hợp, dùng deployment slot/canary/rolling strategy, warm-up, validation rồi tăng traffic. Chọn mechanism theo hosting topology; không cần Kubernetes chỉ để có rollout an toàn.

### Medium — Không có quality/security gate cho artifact ngoài unit tests

**Vấn đề:** `dotnet test` là validation duy nhất trước artifact.

**Tại sao xảy ra:** Pipeline thiếu risk-based checks.

**Ảnh hưởng production:** Integration/database/API regressions hoặc static-analysis/security findings có thể lọt qua.

**Cách sửa:** Chọn gates theo rủi ro: integration tests, migration compatibility tests, SonarQube/static analysis, package vulnerability policy, API/E2E smoke. Không chạy mọi test vô hạn; ưu tiên critical confidence.

### Medium — Release observability/version metadata không được thiết kế

**Vấn đề:** Không có evidence rõ instance nào chạy release nào.

**Tại sao xảy ra:** Artifact/release identity không được expose vào telemetry.

**Ảnh hưởng production:** Incident correlation và rollback decision chậm.

**Cách sửa:** Gắn release version/commit SHA vào structured logs, Application Insights properties, health/info endpoint nội bộ phù hợp và deployment events.

## Phiên bản đề xuất

Đây là pseudo-pipeline thể hiện nguyên tắc **build once, promote same artifact, migration compatibility, secret isolation và staged validation**. Syntax thực tế sẽ tùy Jenkins/TeamCity/Octopus implementation.

```yaml
pipeline:
  stages:
    - name: build
      checkout:
        commit: ${TRIGGER_COMMIT_SHA}
      steps:
        - run: dotnet restore --locked-mode
        - run: dotnet test --configuration Release --no-restore
        - run: dotnet publish src/App/App.csproj -c Release -o ./publish --no-restore
        - run: create-release-manifest \
            --commit ${TRIGGER_COMMIT_SHA} \
            --build ${BUILD_ID} \
            --output ./publish/release.json
        - run: zip -r app-${BUILD_ID}-${TRIGGER_COMMIT_SHA}.zip ./publish
        - publish-artifact:
            path: app-${BUILD_ID}-${TRIGGER_COMMIT_SHA}.zip
            immutable: true

    - name: validate-migration
      steps:
        - run: migration-compatibility-check \
            --release ${BUILD_ID} \
            --policy expand-contract

    - name: staging
      artifact: app-${BUILD_ID}-${TRIGGER_COMMIT_SHA}.zip
      steps:
        - deploy: staging-slot
        - run: smoke-test --environment staging
        - run: playwright-test --suite critical-path --environment staging
        - approve: production

    - name: production-schema-expand
      secrets:
        database_identity: protected-runtime-credential
      steps:
        - run: run-approved-additive-migrations --release ${BUILD_ID}

    - name: production
      artifact: app-${BUILD_ID}-${TRIGGER_COMMIT_SHA}.zip
      steps:
        - deploy: production-slot
        - run: warm-up --target production-slot
        - run: smoke-test --target production-slot
        - run: verify-release-version \
            --expected ${TRIGGER_COMMIT_SHA}
        - switch-traffic: production-slot
        - monitor:
            window: release-validation-window
            signals:
              - http_5xx
              - request_p99
              - dependency_failures
              - business_smoke_failures

    - name: schema-contract
      when: separate-approved-release
      steps:
        - run: verify-no-old-app-version-running
        - run: verify-backfill-complete
        - run: run-approved-contract-migrations
```

Một số điểm cố ý **không** tự động hóa mù:

- destructive migration có thể cần release riêng sau rollback window;
- backfill lớn có thể chạy online/background, không nằm trong startup/deploy transaction;
- production secrets không nằm trong artifact hay repo;
- rollback phải tham chiếu artifact immutable đã biết SHA và chỉ được cho phép khi schema compatibility matrix nói an toàn.

## Giải thích thiết kế sau khi sửa

- CI build đúng commit trigger và tạo immutable artifact một lần.
- Staging và Production promote cùng artifact bytes.
- Release metadata làm deployment auditable/reproducible.
- Database change dùng expand/contract để old/new app có overlap compatibility.
- Destructive contract step tách khỏi initial application rollout.
- Secrets lấy từ protected secret mechanism/identity, không plaintext.
- Smoke/E2E checks đánh vào critical behavior thay vì chỉ homepage.
- Traffic cutover/slot strategy cho phép warm-up và giảm blast radius khi hosting hỗ trợ.

## Trade-offs

- Expand/contract thường cần nhiều releases và code tạm hỗ trợ cả schema cũ/mới.
- Immutable artifact promotion cần artifact retention/storage governance.
- Deployment slots/canary thêm pipeline complexity và có thể không phù hợp mọi networking/configuration topology.
- Playwright E2E quá rộng có thể làm pipeline chậm/flaky; chỉ nên chọn critical release checks.
- Managed Identity/Key Vault giảm secret exposure nhưng cần permission/network setup và operational ownership.
- Không phải migration nào cũng cần tách release; additive, fast, low-risk migrations có thể chạy gần deploy nếu đã được evidence-backed review.

## Cách kiểm thử

1. **Artifact reproducibility validation:** verify hash của artifact Staging và Production giống nhau; source SHA được ghi trong manifest và runtime telemetry.
2. **Database compatibility test:** chạy old app + new schema, new app + transitional schema trên integration environment cho migration breaking-risk.
3. **Rollback rehearsal:** deploy new release rồi rollback artifact trong compatibility window; verify critical APIs và data integrity.
4. **Deployment validation:** smoke + Playwright critical path sau slot warm-up/cutover, bao gồm authentication và DB write/read path.
5. **Failure-path test:** migration fail giữa chừng hoặc app health xấu sau deploy; verify pipeline không tiếp tục cutover và operator có runbook rõ.

## Quan sát trong production

- release version/commit SHA trên mỗi instance;
- deployment event timeline;
- migration version/history và duration;
- HTTP 5xx, p95/p99 và dependency failures theo release version;
- App Service instance/slot health;
- authentication/business smoke result;
- DB lock/wait/long-running migration signals;
- rollback/cutover audit trail;
- secret-access audit từ secret store khi phù hợp.

## Câu hỏi phỏng vấn mở rộng

1. Nếu migration cần backfill 500 triệu rows trong 8 giờ, bạn tách schema change, backfill và code rollout thế nào?
2. Khi nào rollback code là lựa chọn kém hơn forward-fix dù artifact cũ vẫn còn?
3. Nếu team muốn thay Jenkins bằng GitHub Actions vì pipeline hiện không reproducible, bạn sẽ giải thích vì sao đổi tool có thể không sửa root cause như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `BackgroundService` là lifecycle-managed hosted service; scheduling, DI scope, cancellation và exception ownership phải được thiết kế cùng nhau.
- In-process non-overlap không giải quyết multi-instance duplicate execution. Scale-out buộc phải suy nghĩ về work ownership, claim, idempotency và downstream capacity.
- `DbContext` nên gắn với một unit-of-work rõ và không được chia sẻ tùy ý giữa concurrent operations.
- CI/CD an toàn cần **build once, promote same immutable artifact**, thay vì build lại theo environment.
- Database rollout phải được xem như compatibility problem giữa old/new application versions; expand/contract thường an toàn hơn destructive migration trước deploy.
- Rollback application không đồng nghĩa rollback database/data; release plan phải mô tả compatibility và recovery riêng.

## Mẫu tư duy cần nhớ

1. **Phân tách các tầng concurrency:** trong một task, trong một process, và giữa nhiều instances.
2. **Correctness trước throughput:** idempotency/claim ownership trước khi tăng parallelism hoặc scale-out.
3. **Build once, promote many:** cùng artifact đã test phải đi qua các environments.
4. **Thiết kế schema cho coexistence:** old/new versions có thể cùng chạy trong rollout và rollback window.
5. **Kiểm thử failure path thật:** shutdown, duplicate runner, provider 429, migration fail và rollback đều phải được rehearsal.
