# Câu 1 — ASP.NET Core middleware đọc request body rồi controller nhận body rỗng: request stream thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, middleware pipeline, request body stream, model binding, buffering, cancellation, memory/I/O, security, production verification

## Bối cảnh

Một ASP.NET Core Web API nhận webhook JSON từ đối tác. Team thêm middleware để tính HMAC signature và ghi diagnostic payload khi validation thất bại. Sau release, một số controller nhận model `null` hoặc báo invalid JSON dù request từ đối tác hợp lệ.

Middleware hiện đọc toàn bộ `HttpRequest.Body` bằng `StreamReader`, sau đó gọi `next(context)`. Developer cho rằng “request body là một property nên controller có thể đọc lại bình thường”. Một đề xuất khác là copy mọi request body vào `MemoryStream` để giải quyết triệt để.

Payload thông thường 5–20 KB nhưng một endpoint import có thể nhận vài chục MB. API chạy nhiều instance; security policy cấm ghi raw secrets/PII vào logs. Chưa có trace chứng minh failure xảy ra ở middleware hay model binding.

## Câu hỏi chính

Hãy giải thích internal/practical behavior của `HttpRequest.Body`, vị trí đọc của stream, middleware ordering và model binding trong scenario này. Vì sao đọc body trước controller có thể thay đổi behavior? Bạn sẽ xác minh root cause và thiết kế signature validation/body inspection thế nào để đúng, bounded về resource và không tạo security problem?

## Câu hỏi làm rõ nên cân nhắc

1. Middleware có chạy cho mọi endpoint hay chỉ webhook cần signature validation?
2. Body hiện có seek được không, và code có bật buffering/rewind trước khi gọi middleware tiếp theo không?
3. Signature được tính trên raw bytes chính xác hay trên JSON đã deserialize/normalize?
4. Maximum request size và concurrency của endpoint import là bao nhiêu?
5. Diagnostic requirement cần lưu payload nào, retention/redaction policy ra sao?

## Gợi ý tư duy

### Gợi ý 1

`Body` là stream; việc đọc có state/position. Đừng coi nó như immutable string property.

### Gợi ý 2

Nếu nhiều pipeline component cần đọc cùng body, cần thiết kế replay/buffering có chủ đích và reset đúng vị trí; nhưng buffering có resource cost.

### Gợi ý 3

Signature verification thường cần exact bytes. Hãy đồng thời xét request-size limits, cancellation và việc không log sensitive payload.

## Cấu trúc trả lời đề xuất

1. Làm rõ endpoint scope và signature contract.
2. Mô tả request stream + pipeline ordering.
3. Xác minh position/read behavior bằng trace/test nhỏ.
4. Thiết kế body replay chỉ nơi cần thiết.
5. Bound request size và memory/disk impact.
6. Tính signature trên representation đúng contract.
7. Không log raw sensitive payload; dùng metadata/hash/redaction phù hợp.
8. Propagate request cancellation.
9. Integration/load/security test.
10. Theo dõi model-binding failures, request size và middleware duration.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Request body là stream có read position; component đọc trước có thể ảnh hưởng component sau nếu không có replay/buffering phù hợp.
- Middleware ordering quyết định component nào quan sát/consume request trước.
- Không nên copy mọi request không giới hạn vào memory chỉ để tiện đọc lại.
- Signature contract phải xác định raw bytes/canonical representation; parse rồi serialize lại có thể thay đổi bytes.
- Diagnostic logging phải tuân thủ policy về secrets/PII.

### Điểm cộng

- Chỉ bật buffering/inspection cho route/content type cần thiết thay vì toàn application.
- Reset stream position sau khi đọc khi replay semantics yêu cầu.
- Có request-size limit và xem xét buffering spill/resource behavior theo runtime/version được dùng.
- Dùng integration test chạy thật qua middleware + model binding thay vì unit-test middleware cô lập.

### Senior+

- Phân biệt correctness requirement của webhook signature với observability requirement; không buộc raw payload logging để debug.
- Đề xuất telemetry như payload length, content type, signature result, correlation ID và body-read duration mà không lộ payload.
- Xem cancellation/slow upload/resource exhaustion như failure mode của body inspection.

## Hướng giải quyết tham khảo

Tôi sẽ xác minh trước bằng một integration test gửi cùng payload qua pipeline có và không có middleware, đồng thời instrument vị trí/body length trước và sau middleware nếu stream hỗ trợ thông tin đó. Nếu middleware đọc body đến cuối rồi gọi `next`, model binding phía sau có thể không còn bytes để đọc theo cách application kỳ vọng.

Tôi không copy mọi request vào `MemoryStream`. Với webhook cần HMAC, tôi scope middleware/filter cho đúng endpoint. Nếu pipeline cần đọc lại, dùng buffering/replay mechanism phù hợp với ASP.NET Core version đang chạy, đọc có giới hạn, sau đó đưa position về vị trí cần thiết trước `next`. Với payload lớn, phải hiểu threshold/storage behavior và đặt request-size/resource guardrail; không biến middleware thành cơ chế materialize vài chục MB trên heap cho mỗi request.

Signature phải tính trên exact representation theo contract của provider. Nếu provider ký raw body bytes, deserialize rồi serialize lại JSON có thể thay whitespace/property formatting và làm signature sai. Tôi đọc bytes theo contract, validate bằng constant-time comparison phù hợp, rồi cho pipeline tiếp tục nếu hợp lệ.

Logging không chứa raw token, authorization header hoặc PII payload. Khi cần điều tra, tôi log correlation ID, payload length, content type, signature validation result, endpoint và một fingerprint/hash chỉ khi security policy cho phép.

Testing gồm valid/invalid signatures, middleware + controller model binding, payload near limit, concurrent large requests, cancellation giữa upload và security tests đảm bảo logs không chứa secret. Production telemetry theo dõi validation failures, model-binding 4xx, request sizes, middleware duration và memory/temp-storage pressure.

## Mẫu trả lời trong phỏng vấn

“Điểm đầu tiên tôi sửa assumption rằng `Request.Body` là property có thể đọc vô hạn. Nó là stream có state. Nếu middleware consume đến cuối rồi gọi `next`, model binding phía sau có thể không còn dữ liệu theo expected position.

Tôi sẽ reproduce bằng integration test qua full pipeline, sau đó scope body inspection chỉ cho webhook cần HMAC. Nếu cần đọc nhiều lần, tôi dùng buffering/replay mechanism phù hợp và reset position trước khi đi tiếp, nhưng có size limits vì buffering mọi request lớn sẽ tạo memory/I/O pressure.

Tôi cũng xác nhận provider ký raw bytes hay canonical form. Nếu là raw bytes, parse rồi serialize lại JSON là sai. Và tôi không log raw payload để debug; telemetry có thể dùng correlation, length, signature outcome và safe metadata. Cuối cùng tôi test large payload, cancellation và concurrency chứ không chỉ happy path.”

## Câu hỏi đào sâu

1. Nếu webhook payload 100 MB nhưng signature bắt buộc trên toàn body trước khi business processing bắt đầu, bạn kiểm soát resource thế nào?
2. Nếu team muốn chuyển signature validation từ middleware sang controller để đơn giản, trade-off về cross-cutting concern và pipeline behavior là gì?
3. Tôi đề xuất luôn `ReadToEndAsync()` mọi request rồi rewind vì code dễ hiểu; bạn phản biện bằng failure modes nào?

## Lỗi trả lời thường gặp

- Coi request body như string có thể đọc lại mặc định.
- Buffer toàn bộ request không giới hạn.
- Parse JSON rồi tính signature trên JSON serialize lại mà không kiểm tra contract.
- Log raw webhook payload chứa PII/secrets.
- Chỉ unit-test middleware mà không test model binding phía sau.

## Thang điểm 0–10

- **0–2:** Chỉ nói “reset stream”.
- **3–4:** Hiểu stream position nhưng bỏ qua resource/security.
- **5–6:** Có buffering scope, signature semantics và integration testing.
- **7–8:** Có limits, cancellation, observability và large-request reasoning.
- **9–10:** Kết nối pipeline mechanism → cryptographic correctness → resource bounds → security → production verification rõ ràng.

# Câu 2 — Playwright suite từ 12 phút thành 45 phút và flaky sau khi bật parallel workers

**Loại câu hỏi:** Production/Engineering Quality Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Playwright, E2E testing, test isolation, parallelism, shared test data, CI/CD, browser/network diagnostics, database/API integration, observability

## Bối cảnh

Một e-commerce team có khoảng 420 Playwright E2E tests chạy trong CI trước production release. Suite từng ổn định khoảng 12–15 phút. Sau khi tăng parallel workers để giảm thời gian, runtime thực tế tăng lên 35–45 phút và khoảng 8–12% pipeline runs có ít nhất một flaky failure.

Failures không cố định: có lúc duplicate email/user, có lúc cart chứa product của test khác, có lúc timeout chờ order status, đôi lúc test pass ngay khi retry. CI dùng cùng một test environment và database cho tất cả workers. Một số tests tạo user với timestamp theo giây, một số dùng account cố định, và cleanup chạy ở `afterAll`.

Team đề xuất tăng timeout và retry lên 5 lần. Chưa có trace/video/network artifact được giữ cho mọi failure, và chưa biết bottleneck nằm ở browser workers, backend, database hay external sandbox.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo trình tự impact → stabilization → evidence → competing hypotheses → root cause → remediation như thế nào? Hãy phân biệt flaky do shared state/test-data collision với backend saturation và legitimate asynchronous business behavior; đồng thời thiết kế suite để parallelism tăng throughput thay vì chỉ tăng contention.

## Câu hỏi làm rõ nên cân nhắc

1. Tests nào được phép chạy parallel và tests nào có dependency/order ngầm?
2. Mỗi worker có namespace/test data riêng hay cùng dùng fixed users/products/orders?
3. Backend/database telemetry thay đổi thế nào khi worker count tăng từ N lên 2N?
4. Retry có lặp lại trên cùng contaminated state hay tạo test context/data mới?
5. Order status là synchronous contract hay eventual workflow có queue/background processing?

## Gợi ý tư duy

### Gợi ý 1

Retry pass không chứng minh test đúng; nó có thể chỉ che race hoặc shared-state contamination.

### Gợi ý 2

Parallelism tăng load lên cả test runner lẫn system under test. Tách test isolation failure khỏi environment capacity failure.

### Gợi ý 3

Một E2E suite tốt cần deterministic data ownership, artifact đủ để điều tra và concurrency phù hợp với capacity của environment.

## Cấu trúc trả lời đề xuất

1. Định lượng release impact và nhóm flaky tests.
2. Tạm giảm worker/retry về mức ổn định để unblock pipeline nếu cần.
3. Giữ trace/video/screenshot/network/log correlation cho failure.
4. Phân loại failure signatures.
5. Kiểm tra data collision và cleanup lifecycle.
6. Correlate worker count với backend/DB/queue saturation.
7. Tách eventual-consistency wait khỏi arbitrary sleeps/timeouts.
8. Thiết kế per-worker/per-test namespace và idempotent setup/cleanup.
9. Tune parallelism bằng measurement.
10. Theo dõi flake rate, duration distribution và failure ownership.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chữa flaky bằng timeout/retry trước khi biết nguyên nhân.
- Shared users/database state và `afterAll` cleanup là competing hypothesis mạnh khi chạy parallel.
- Unique data phải thực sự collision-resistant, không chỉ timestamp độ phân giải thấp.
- Phải đo backend/database/dependency saturation khi tăng workers.
- Wait cho business state nên dựa trên observable condition với bounded timeout, không dùng fixed sleep tùy tiện.

### Điểm cộng

- Tạo worker/test namespace bằng UUID/run ID và ownership rõ ràng.
- API-level setup có thể nhanh và deterministic hơn thao tác UI cho preconditions không phải mục tiêu test.
- Cleanup idempotent; có janitor riêng cho orphan data thay vì để cleanup failure làm contaminate run sau.
- Quarantine chỉ là temporary containment có owner/expiry, không phải nơi chôn flaky tests.

### Senior+

- Phân tầng suite: critical E2E nhỏ cho release gate; integration/API tests cover phần lớn permutations; không ép mọi behavior qua browser.
- Tối ưu worker count dựa trên throughput curve, không mặc định càng nhiều càng nhanh.
- Correlate test run ID từ Playwright qua API logs/database/queue để chứng minh failure path.

## Hướng giải quyết tham khảo

Đầu tiên tôi giảm blast radius: nếu release đang bị block, tạm quay worker count về mức gần đây ổn định thay vì tăng retries. Sau đó tôi bật/giữ artifact cho failure: Playwright trace, screenshot/video khi hữu ích, request/response metadata và một run/test correlation ID đi vào backend logs.

Tôi phân nhóm failures. Duplicate email/cart contamination gợi ý shared-state collision. Timestamp theo giây không đủ khi nhiều workers tạo cùng lúc; fixed account càng nguy hiểm. Tôi chuyển sang unique run/worker/test identifiers, mỗi test sở hữu data nó tạo. Preconditions có thể setup qua API/database fixture được kiểm soát nếu UI flow không phải thứ đang test. Cleanup phải idempotent và không phụ thuộc duy nhất vào `afterAll`; run bị kill vẫn cần cơ chế dọn orphan data.

Timeout order status cần hiểu business semantics. Nếu order processing asynchronous, test nên poll observable status với bounded deadline/backoff hợp lý thay vì sleep cố định. Nhưng nếu queue depth tăng mạnh theo workers, đây có thể là environment saturation chứ không phải flaky assertion.

Tôi chạy controlled experiment với worker counts khác nhau và đo suite throughput, API p95/p99, DB connections/locks, queue depth và external sandbox latency. Nếu 8 workers nhanh hơn 4 nhưng 16 workers làm backend saturate, optimum không phải maximum CPU của runner.

Về chiến lược test, tôi giữ E2E cho critical cross-system journeys. Logic permutations nên được đẩy xuống unit/integration/API tests để release gate nhanh và ít brittle hơn. Tôi theo dõi flake rate theo test, retries, runtime p95, failure categories và quarantined-test age.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không tăng retry lên 5 vì pass-on-retry có thể che shared-state race. Trước tiên tôi quay parallelism về mức ổn định để giảm release impact, rồi giữ trace và correlation cho failures.

Các dấu hiệu duplicate user và cart của test khác làm tôi ưu tiên kiểm tra isolation: fixed accounts, timestamp theo giây và cleanup `afterAll` đều không an toàn khi nhiều workers chia sẻ DB. Tôi dùng run/worker/test IDs collision-resistant, data ownership rõ và cleanup idempotent.

Song song, tôi đo system under test. Parallel Playwright cũng là load test ngoài ý muốn; nếu DB pool, queue hoặc sandbox saturate thì thêm workers sẽ làm suite chậm hơn. Với async order status, tôi wait theo observable condition có deadline, không sleep tùy ý.

Cuối cùng tôi tune worker count theo throughput curve và giảm số browser E2E bằng cách chuyển permutations xuống integration/API tests. Mục tiêu là deterministic release signal, không phải số workers lớn nhất.”

## Câu hỏi đào sâu

1. Nếu mỗi worker có database riêng thì isolation tốt nhưng provisioning tốn 8 phút, bạn cân bằng thế nào?
2. Nếu một test chỉ flaky trên CI nhưng không reproduce local, evidence nào bạn ưu tiên thu?
3. Tôi muốn giữ retry=3 vì giảm false-negative release; bạn đặt policy retry/quarantine nào để không che defect?

## Lỗi trả lời thường gặp

- Tăng timeout/retry như root-cause fix.
- Dùng fixed accounts trong parallel suite.
- Không đo system under test khi tăng workers.
- Dùng `waitForTimeout` cho eventual business state.
- Không lưu artifacts/correlation nên mỗi flaky failure trở thành phỏng đoán.

## Thang điểm 0–10

- **0–2:** Chỉ tăng retry/timeout.
- **3–4:** Nhận ra test data collision nhưng thiếu CI/backend evidence.
- **5–6:** Có isolation, artifacts, controlled parallelism và async waiting.
- **7–8:** Có throughput experiment, layered testing strategy, cleanup và telemetry.
- **9–10:** Xử lý suite như distributed production-like workload với deterministic ownership, capacity model và actionable release signal.

# Câu 3 — Thiết kế upload file lớn: backend proxy hay direct-to-Blob bằng SAS?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–35 phút  
**Kỹ năng được đánh giá:** Azure Blob Storage, ASP.NET Core, SAS, Managed Identity, large-file upload, security, malware scanning, asynchronous processing, metadata, reliability, observability, architecture trade-offs

## Bối cảnh

Một enterprise document platform cần cho web client upload PDF, images và spreadsheet. Hiện tại ASP.NET Core API nhận multipart file rồi stream sang storage. Business chuẩn bị hỗ trợ file lên đến vài GB và traffic upload có thể tăng mạnh theo campaign.

Requirements ban đầu:

- user chỉ được upload vào workspace mình có quyền;
- file chưa scan malware không được download bởi user khác;
- cần hiển thị progress và retry khi mạng client chập chờn;
- metadata nghiệp vụ nằm trong SQL Server;
- application chạy nhiều Azure App Service instances;
- team đang cân nhắc Azure Blob Storage;
- backend có thể dùng Managed Identity;
- kiến trúc phải tránh public write access rộng;
- business chưa yêu cầu Kubernetes hoặc microservices.

Hai đề xuất đang tranh luận:

1. mọi bytes đi qua ASP.NET Core để backend kiểm soát security;
2. backend cấp SAS để browser upload trực tiếp vào Blob, sau đó xử lý asynchronous.

## Câu hỏi chính

Bạn sẽ thiết kế upload workflow và boundaries thế nào? Hãy so sánh backend proxy với direct-to-Blob, thiết kế authorization/SAS scope, metadata state machine, malware scanning, retry/idempotency, orphan cleanup, download authorization, observability và failure recovery. Khi nào bạn chọn giải pháp đơn giản hơn dù direct upload có vẻ scale tốt hơn?

## Câu hỏi làm rõ nên cân nhắc

1. File-size distribution thực tế là gì: phần lớn vài MB hay phần lớn hàng GB?
2. Browser/mobile clients có cần resumable/chunked upload và network conditions ra sao?
3. Malware scan SLA là bao lâu và scanner nhận input bằng cách nào?
4. Compliance yêu cầu retention, encryption, audit và data residency gì?
5. File được immutable sau upload hay có versioning/replacement semantics?

## Gợi ý tư duy

### Gợi ý 1

Tách authorization để “được phép tạo upload” khỏi data plane truyền nhiều GB bytes.

### Gợi ý 2

Direct upload không có nghĩa anonymous/public write. Credential có thể ngắn hạn và scope hẹp theo object/action.

### Gợi ý 3

Upload success ở Blob chưa đồng nghĩa document đã usable. Modeling lifecycle rõ giúp xử lý scan, metadata, retry và orphan objects.

## Cấu trúc trả lời đề xuất

1. Chốt file sizes, clients, security/compliance và SLA.
2. So sánh proxy vs direct upload theo scale và complexity.
3. Thiết kế create-upload authorization endpoint.
4. Sinh object key server-side và credential scope tối thiểu.
5. Modeling SQL states: initiated/uploaded/scanning/ready/rejected/failed.
6. Xác minh upload completion trước processing.
7. Scan malware và chỉ publish/download khi ready.
8. Thiết kế retry/idempotency/orphan cleanup.
9. Download authorization và short-lived access.
10. Telemetry, audit, load/failure tests và operational runbook.

## Ý chính của câu trả lời tốt

### Bắt buộc

- User authorization phải được backend kiểm tra trước khi cấp quyền upload.
- SAS/direct credential phải scope tối thiểu về resource, permissions và lifetime phù hợp; không cấp container-wide write nếu không cần.
- Blob existence không được coi là business document `Ready` trước khi validation/scan hoàn tất.
- Metadata SQL và blob lifecycle cần idempotent state transitions/failure recovery.
- Download path phải kiểm tra authorization và trạng thái scan.
- Orphan upload/abandoned session cần lifecycle cleanup.

### Điểm cộng

- Backend dùng Managed Identity để quản lý storage-side operations thay vì embedded account keys.
- Object name do server sinh, không tin filename client làm storage path; original filename chỉ là metadata sau validation.
- Upload token/session có expiration và expected constraints như size/content metadata theo khả năng thiết kế.
- Scanner xử lý asynchronous; retry scan không được duplicate business document.
- Có quarantine/private area hoặc state-based access model cho unscanned content.

### Senior+

- Nhận ra direct upload giảm bandwidth/connection pressure trên App Service nhưng tăng protocol/state-machine complexity.
- Nếu 99% file nhỏ và traffic thấp, backend streaming proxy có thể là lựa chọn đơn giản, đủ tốt; cần dữ liệu trước khi thêm direct-upload complexity.
- Thiết kế reconciliation job để phát hiện SQL session không có blob, blob không có completed metadata, scan stuck và cleanup an toàn.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng distribution file size và upload concurrency. Nếu workload hiện tại nhỏ, backend streaming có ưu điểm đơn giản: một authorization boundary, dễ enforce limits và ít client protocol. Nhưng với file vài GB và concurrency cao, đưa toàn bộ bytes qua App Service làm application chịu bandwidth, connection lifetime và scale pressure không tạo business value. Khi đó tôi nghiêng về direct-to-Blob.

Workflow direct upload có thể bắt đầu bằng `POST /workspaces/{id}/uploads`. Backend authorize user, validate quota/type policy ở mức metadata, tạo server-generated upload ID/blob key và SQL row `Initiated`. Backend dùng storage identity phù hợp để cấp một short-lived, narrowly scoped upload capability cho đúng blob/action. Không cấp public container write.

Client upload trực tiếp và có retry/chunk strategy phù hợp. Sau completion, backend không tin client chỉ bằng lời khai; nó xác minh object/expected metadata theo contract rồi chuyển state sang `Uploaded` và enqueue/trigger scan. Scanner đọc blob bằng service identity, ghi kết quả. Chỉ state `Ready` mới được download/share; `Rejected`/`Failed` có policy cleanup/audit riêng.

SQL và Blob không có distributed transaction chung, nên workflow phải chịu partial failure. `complete upload` cần idempotent; duplicate callback không tạo duplicate document. Reconciliation tìm session hết hạn chưa có blob, blob orphan, scan stuck và mismatch. Lifecycle policy có thể hỗ trợ cleanup nhưng business reconciliation vẫn cần rõ ownership.

Download cũng là authorization decision. Backend kiểm tra workspace permission + document state rồi hoặc stream file, hoặc cấp read capability ngắn hạn cho đúng object. Unscanned content không được expose chỉ vì user biết URL.

Security gồm file-size limits, allowed types nhưng không tin extension, safe filename handling, malware scanning, least privilege, audit và không log SAS/token. Observability theo upload ID: initiated/completed duration, bytes, failure reason, scan queue latency, scan result, orphan count, retry count và storage dependency errors.

Nếu metrics cho thấy file lớn rất hiếm và proxy hiện đáp ứng p95/SLO với headroom lớn, tôi có thể giữ proxy để tránh state-machine/client complexity. Kiến trúc phải phục vụ workload thực, không phải tối đa hóa distribution.

## Mẫu trả lời trong phỏng vấn

“Tôi tách control plane khỏi data plane. Backend luôn authorize user và quyết định họ được tạo upload nào, nhưng với file vài GB tôi không nhất thiết bắt bytes đi qua ASP.NET Core. Backend có thể tạo upload session, server-generated blob key và cấp capability ngắn hạn chỉ cho đúng blob/action; container vẫn private.

Blob upload xong chưa phải document ready. Tôi modeling states như Initiated, Uploaded, Scanning, Ready, Rejected. Backend xác minh completion rồi scan asynchronous; download chỉ được cấp sau authorization và `Ready`. Vì SQL và Blob không có atomic transaction chung, completion, scan và callback phải idempotent, cộng thêm reconciliation cho orphan/stuck states.

Managed Identity dùng cho service access; SAS/token không được log và phải least privilege. Tôi đo upload/scan latency, failures và orphan count.

Tuy nhiên, nếu dữ liệu cho thấy hầu hết file nhỏ và traffic thấp, streaming proxy có thể vẫn là giải pháp tốt hơn vì đơn giản. Tôi chỉ trả complexity của direct upload khi bandwidth, connection lifetime hoặc scale thực sự justify nó.”

## Câu hỏi đào sâu

1. Nếu malware scanner unavailable 30 phút, bạn cho phép uploader download file của chính họ không? Policy nào quyết định?
2. Nếu client upload thành công nhưng không bao giờ gọi completion endpoint, reconciliation xác định và xử lý object thế nào?
3. Tôi yêu cầu bỏ SAS và proxy toàn bộ file để “an toàn hơn”; bạn so sánh security risk và operational cost thế nào thay vì chỉ nói direct upload scale tốt hơn?

## Lỗi trả lời thường gặp

- Cấp SAS quá rộng hoặc quá lâu.
- Coi blob tồn tại là document đã sẵn sàng.
- Tin filename/content type từ client như security control.
- Không có strategy cho partial failure giữa SQL metadata và Blob.
- Chọn direct upload hoặc microservices chỉ vì file lớn mà không hỏi workload distribution.

## Thang điểm 0–10

- **0–2:** Chỉ chọn proxy hoặc SAS mà không thiết kế lifecycle/security.
- **3–4:** Có direct upload nhưng thiếu scan/state/failure recovery.
- **5–6:** Có least-privilege access, metadata state machine, scan và authorization.
- **7–8:** Có idempotency, reconciliation, observability, load/security testing và proxy trade-off.
- **9–10:** Thiết kế rõ control/data plane, partial-failure model và chọn complexity dựa trên workload/SLO/compliance.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- ASP.NET Core request body là stream có state; middleware đọc body phải hiểu replay/buffering, ordering, size limits và security.
- Playwright parallelism chỉ có ích khi tests sở hữu data độc lập và system under test còn capacity; retry không thay thế root-cause analysis.
- Large-file upload cần tách authorization/control plane khỏi data transfer khi scale justify, đồng thời modeling rõ trạng thái untrusted → scanned → ready.
- Partial failure và observability phải được thiết kế ngay từ đầu cho test infrastructure và storage workflows.

## Mẫu tư duy cần nhớ

1. **Hiểu stateful mechanism trước khi sửa symptom:** stream position, shared test state và upload lifecycle đều có state chuyển tiếp.
2. **Parallelism không miễn phí:** đo contention ở cả caller và dependency trước khi tăng concurrency.
3. **Tách control plane khỏi data plane khi có giá trị thực:** authorization không bắt buộc backend phải proxy toàn bộ bytes.
4. **Model partial failure rõ ràng:** SQL, Blob, scanner và client không tạo một atomic transaction chung.
5. **Security + observability là design constraints:** least privilege, không log secrets và correlation đủ để chứng minh failure path.
