# Câu 1 — Vì sao một request HTTP có thể giữ kết nối SQL dù đã timeout?

**Loại câu hỏi:** Internal mechanism — ASP.NET Core, CancellationToken, ADO.NET, EF Core  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** HTTP cancellation, async I/O, connection pooling, transaction lifetime, instrumentation

## Bối cảnh

Một API .NET 8 truy vấn PostgreSQL qua EF Core. Gateway đặt timeout 15 giây; dashboard ghi nhận HTTP 504, nhưng database vẫn có nhiều truy vấn chạy lâu và số connection đang dùng tăng. API có 6 instances; mỗi instance phục vụ nhiều request đồng thời. Một số endpoint dùng `ToListAsync()`, một số dùng `await foreach` trên `AsAsyncEnumerable()`. Đội phát triển cho rằng “client đã timeout thì mọi tác vụ backend tự hủy”.

## Câu hỏi chính

Giải thích đường đi của cancellation từ client/gateway qua ASP.NET Core, EF Core, database provider đến PostgreSQL; phân biệt timeout, cancellation, transaction rollback và connection release. Bạn sẽ chứng minh nguyên nhân và thiết kế endpoint chịu tải an toàn thế nào?

## Câu hỏi làm rõ nên cân nhắc

1. 504 do gateway hay do application tạo, và gateway có thực sự đóng kết nối upstream?
2. Endpoint truyền `HttpContext.RequestAborted` đến những operation nào?
3. Truy vấn đang stream dữ liệu hay materialize toàn bộ; có transaction mở ngoài query không?
4. Pool size, số instances, thời gian SQL thực tế và loại exception là gì?
5. Có retry policy, command timeout hoặc client timeout riêng không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt một HTTP response hết hạn với vòng đời của task và database command.

### Gợi ý 2
Quan sát cancellation propagation và thời điểm giải phóng reader/connection.

### Gợi ý 3
Kiểm tra `RequestAborted`, `WithCancellation`, `CommandTimeout`, `DisposeAsync`, `pg_stat_activity` và connection-pool metrics.

## Cấu trúc trả lời đề xuất

1. Xác định nơi phát sinh timeout và tín hiệu cancellation.
2. Mô tả chuỗi token qua các tầng.
3. Giải thích provider/database có thể phản ứng khác nhau thế nào.
4. Xây dựng timeline cho query, reader, transaction, connection.
5. Đề xuất instrumentation, sửa code và kiểm thử ngắt kết nối.

## Ý chính của câu trả lời tốt

### Bắt buộc
Không đồng nhất HTTP 504 với database query cancellation; truyền token rõ ràng; đóng reader/transaction đúng cách; đo query duration và pool usage.

### Điểm cộng
Phân biệt timeout của reverse proxy, `HttpClient`, EF command và PostgreSQL `statement_timeout`; chỉ ra rằng cancellation là cooperative, không bảo đảm rollback mọi side effect.

### Senior+
Thiết kế budget cho end-to-end deadline, giới hạn concurrency, chống retry amplification, xử lý kết quả không chắc chắn của write sau client disconnect.

## Hướng giải quyết tham khảo

**Giả định:** Gateway có thể trả 504 khi upstream vượt 15 giây, nhưng chưa xác minh nó có đóng kết nối đến ASP.NET Core. `RequestAborted` chỉ báo khi request bị abort theo quan sát của server; nó không tự hủy tất cả tác vụ không nhận token. EF Core chuyển cancellation đến provider khi gọi overload nhận token; provider cố hủy command nhưng kết quả và thời gian phản ứng tùy driver, mạng và server.

**Cơ chế:** Request nhận token → application truyền vào `ToListAsync(ct)` hoặc `AsAsyncEnumerable().WithCancellation(ct)` → EF Core/provider gửi cancellation phù hợp. Với streaming, enumerator/reader có thể giữ connection cho đến khi kết thúc hoặc dispose; một transaction mở lâu có thể giữ locks. `CommandTimeout` là deadline riêng của database command; không thay thế timeout toàn request. Một read bị hủy không đồng nghĩa transaction ngoài được rollback nếu code vẫn giữ transaction. Sau write commit nhưng response thất lạc, retry phải an toàn.

**Implementation:** Truyền `CancellationToken ct` từ action đến mọi database call; giới hạn số bản ghi, projection, keyset pagination khi phù hợp; tránh `Task.Run` để “chữa” I/O. Đảm bảo `await using` cho transaction/reader thủ công và rollback/dispose trên lỗi; dùng timeout theo budget có chủ đích. Ví dụ:

```csharp
[HttpGet("orders")]
public async Task<ActionResult<IReadOnlyList<OrderDto>>> Get(
    [FromQuery] int limit, CancellationToken ct)
{
    if (limit is < 1 or > 200) return BadRequest();
    var items = await _db.Orders.AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new OrderDto(x.Id, x.Total))
        .Take(limit)
        .ToListAsync(ct);
    return Ok(items);
}
```

**Evidence:** Correlate trace ID, gateway 504, request-aborted events, EF command duration, PostgreSQL `pg_stat_activity` (state, wait_event, query age), active/idle connection counts, locks, p95/p99, exception type. Kiểm tra execution plan và SQL round trips trước khi tăng pool. Dùng load test có abort client và fault injection; xác minh không còn reader/transaction treo. Không tự động retry mọi write.

**Trade-offs:** Timeout ngắn bảo vệ tài nguyên nhưng tăng lỗi ở workload dài; pool lớn che triệu chứng nhưng tăng tải DB; streaming giảm peak memory nhưng giữ connection trong suốt enumeration. Nếu query là report dài hợp lệ, cân nhắc asynchronous job và API trả job status thay vì giữ HTTP request.

## Mẫu trả lời trong phỏng vấn

“Đầu tiên tôi sẽ xác minh 504 phát sinh ở gateway và liệu upstream có nhận tín hiệu disconnect hay không. HTTP timeout không tự động hủy database query. Trong ASP.NET Core, tôi truyền `RequestAborted` qua toàn bộ EF Core call; khi stream phải bảo đảm enumerator được dispose. Sau đó tôi đối chiếu request traces với command duration, `pg_stat_activity` và connection pool để phân biệt query chậm, lock wait và resource leak. Tôi sẽ giới hạn query result, đặt deadline phù hợp, sửa transaction lifetime và test khi client disconnect. Tôi không tăng pool hay thêm cache khi chưa có evidence; với tác vụ dài, tôi đề xuất background job có status riêng.”

## Câu hỏi đào sâu

1. Nếu provider nhận cancellation nhưng PostgreSQL vẫn đang rollback transaction lớn, bạn kỳ vọng pool và latency thế nào?
2. Nếu business yêu cầu export 2 triệu dòng, liệu đề xuất materialize `ToListAsync` còn hợp lý?
3. Nếu write đã commit trước khi gateway 504, làm sao client retry mà không tạo duplicate?

## Lỗi trả lời thường gặp

- Khẳng định 504 luôn hủy mọi task và SQL command.
- Chỉ tăng command timeout hoặc pool size mà không đo.
- Bỏ qua streaming reader và transaction disposal.
- Dùng `Task.Run` cho database I/O.
- Cho rằng cancellation bảo đảm rollback side effects.

## Thang điểm 0–10

- 0–2: Chỉ định nghĩa cancellation, thiếu cơ chế.
- 3–4: Biết truyền token nhưng không phân biệt timeout/connection lifetime.
- 5–6: Giải thích cơ chế, có bước đo và sửa endpoint.
- 7–8: Phân tích provider, streaming, transaction, production evidence và tests.
- 9–10: Thiết kế end-to-end budget, retry semantics, capacity và giải thích trade-offs rõ ràng.

# Câu 2 — Sau release, trang CMS hiển thị nội dung cũ và SEO canonical sai

**Loại câu hỏi:** Production incident — Optimizely CMS, Akamai CDN, Vue.js, SEO, Azure App Service  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** incident response, cache hierarchy, release safety, SEO engineering, observability

## Bối cảnh

Website thương mại có nội dung do Optimizely CMS quản lý; trang sản phẩm được render server-side, Vue.js bổ sung tương tác. Akamai đứng trước origin Azure App Service. Sau release, một số thị trường thấy giá/nội dung khuyến mại cũ; bot tìm kiếm nhận canonical URL trỏ sang ngôn ngữ khác. Lỗi chỉ xuất hiện ở một số edge và không tái hiện ổn định trên máy QA. Traffic cao, không thể purge toàn bộ cache một cách tùy tiện. Chưa rõ giá có được cá nhân hóa hay không.

## Câu hỏi chính

Bạn sẽ xử lý incident theo trình tự nào để giảm ảnh hưởng kinh doanh, phân biệt lỗi CDN/origin/CMS/frontend/SEO và ngăn tái diễn mà không gây cache stampede?

## Câu hỏi làm rõ nên cân nhắc

1. Giá là dữ liệu public theo thị trường hay personalized theo user?
2. Cache key hiện bao gồm host, path, query, locale và currency như thế nào?
3. Response headers thực tế ở edge và origin gồm `Cache-Control`, `Vary`, `Age`, cache-status gì?
4. Canonical được render server-side, CMS cung cấp hay Vue.js thay đổi sau hydration?
5. Release có đổi routing, content publication, TTL, surrogate key hoặc deployment slot không?

## Gợi ý tư duy

### Gợi ý 1
Tách nội dung người dùng thấy, HTML bot nhận và nguồn dữ liệu gốc.

### Gợi ý 2
Đối chiếu edge HIT/MISS, origin response và biến thể locale trước khi purge.

### Gợi ý 3
Thử request cùng URL/headers tại các POP, so sánh HTML thô với DOM hydrated, xác minh canonical và cache-key dimensions.

## Cấu trúc trả lời đề xuất

1. Định lượng phạm vi và mức độ ảnh hưởng.
2. Giảm rủi ro trước khi thay đổi hệ thống.
3. Lấy evidence từ edge, origin, CMS, browser và bot-like fetch.
4. Xây dựng các giả thuyết cạnh tranh.
5. Khoanh vùng bằng so sánh response và release diff.
6. Sửa nguyên nhân, xác minh, giám sát và phòng ngừa.

## Ý chính của câu trả lời tốt

### Bắt buộc
Phân biệt cache ở browser/CDN/origin/CMS; kiểm tra raw HTML canonical; so sánh request theo locale; ưu tiên targeted invalidation và rollback có kiểm soát.

### Điểm cộng
Phân tích cache key thiếu locale/currency, `Vary` không đủ nếu CDN không cấu hình tương ứng, stale-while-revalidate, deployment slot/config drift, SSR vs hydration mismatch.

### Senior+
Đưa ra runbook incident, guardrails về personalized content, chiến lược versioned content keys, kiểm chứng bot rendering và rollout theo thị trường.

## Hướng giải quyết tham khảo

**Impact → stabilize:** Xác định URL/market/POP bị ảnh hưởng, conversion và indexability risk. Nếu giá sai gây thiệt hại, tạm tắt cache đối với endpoint giá động hoặc phục vụ dữ liệu an toàn từ origin theo chính sách đã kiểm tra; rollback release nếu bằng chứng cho thấy regression và rollback không làm hỏng content schema. Không purge toàn bộ trước khi đánh giá origin capacity.

**Evidence:** Thu thập cùng URL với các `Accept-Language`, host, currency cookie và query parameters; ghi request/response headers, `Age`, edge cache status, raw HTML, canonical/hreflang, Vue hydrated DOM, content version từ CMS. So sánh edge vs direct origin qua đường kiểm thử được phép, không vô tình bypass security. Dùng Application Insights và CDN logs theo request correlation, region, cache HIT ratio, origin p95 và 5xx. Xem release diff, publication events, CMS content version và cache invalidation logs.

**Competing hypotheses:** (a) CDN key bỏ qua locale/currency; (b) origin/CMS output cache sai key; (c) invalidation không lan hết edge; (d) canonical template fallback locale; (e) Vue thay DOM sau SSR; (f) cấu hình App Service giữa instances/slots khác nhau. Một edge HIT cũ không chứng minh origin sai; một origin response đúng không chứng minh CDN key đúng.

**Remediation:** Với HTML public, cache key phải tương ứng các chiều tạo ra nội dung khác nhau; nếu personalization theo user, tránh shared public caching hoặc tách personalized API với `private/no-store` phù hợp. Chọn purge theo URL/tag hoặc versioned keys, giãn refresh để tránh thundering herd. Canonical và hreflang nên được tạo nhất quán ở server theo routing/content model; tránh phụ thuộc hydration để bot thấy metadata đúng. Kiểm thử canonical trên raw HTML, locale routing, edge caching và deployment slot; canary theo market, quan sát cache hit, origin traffic và bot fetch.

**Điều kiện thay đổi quyết định:** Nếu giá là public theo country, có thể cache theo market một cách kiểm soát; nếu giá tùy user, thiết kế cache hoàn toàn khác. Nếu CMS publish chưa cập nhật origin, purge edge không chữa root cause. Nếu release không liên quan, tránh rollback mù.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ đánh giá trước thị trường nào đang hiển thị giá sai và có cần chặn cache giá động để giảm thiệt hại hay không. Tôi so sánh raw HTML và headers của cùng URL tại edge với origin, thay đổi locale/currency có kiểm soát, rồi đối chiếu content version trong CMS. Tôi xem canonical trên HTML server trả về chứ không chỉ DOM sau Vue hydration. Có nhiều giả thuyết: cache key thiếu chiều thị trường, invalidation lỗi, origin cache sai hoặc template SEO regression. Sau khi có evidence, tôi chọn targeted purge, sửa key hoặc rollback; đồng thời theo dõi origin load để tránh stampede. Cuối cùng tôi bổ sung test đa thị trường, canary và alert về stale content, canonical mismatch.”

## Câu hỏi đào sâu

1. Nếu CDN không hỗ trợ cache key theo một cookie cụ thể, bạn thay đổi contract URL hoặc kiến trúc dữ liệu thế nào?
2. Targeted purge làm origin CPU tăng gấp ba; bạn ưu tiên availability hay freshness ra sao?
3. Nếu canonical đúng ở origin nhưng sai trong Google Search Console, bạn cần kiểm tra thêm gì?

## Lỗi trả lời thường gặp

- Purge toàn bộ CDN ngay mà không tính origin capacity.
- Cho rằng `Vary: Accept-Language` tự bảo đảm mọi CDN phân biệt cache.
- Chỉ xem browser DOM, bỏ qua HTML cho crawler.
- Quy kết Optimizely hoặc Akamai khi chưa so sánh evidence.
- Cache public dữ liệu cá nhân hóa.

## Thang điểm 0–10

- 0–2: Chỉ đề xuất clear cache.
- 3–4: Nhận biết nhiều tầng cache nhưng không có điều tra.
- 5–6: Có kế hoạch ổn định, edge/origin comparison, SEO checks.
- 7–8: Đưa ra competing hypotheses, rollout, tests và telemetry.
- 9–10: Xử lý business risk, capacity, personalized data, SEO consistency và operational trade-offs.

# Câu 3 — Thiết kế pipeline đồng bộ sản phẩm từ SQL sang Elasticsearch

**Loại câu hỏi:** Architecture / system design — SQL Server, Elasticsearch, Azure Service Bus, ASP.NET Core  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** consistency, integration boundaries, event delivery, search design, reliability, security, deployment

## Bối cảnh

Một e-commerce platform có SQL Server là source of truth cho sản phẩm, giá và tồn kho. Product team muốn tìm kiếm full-text, filter theo category và autocomplete bằng Elasticsearch. Hệ thống có khoảng 1 triệu sản phẩm, cập nhật tồn kho liên tục; search có thể chậm hơn database một khoảng ngắn nhưng checkout không được bán vượt tồn kho. Đội đang cân nhắc Azure Service Bus; hiện hệ thống là Modular Monolith trên Azure App Service. Yêu cầu freshness cụ thể và search SLA chưa được thống nhất.

## Câu hỏi chính

Bạn sẽ thiết kế luồng index, query, recovery và rollout như thế nào; phần nào cần strong consistency, phần nào chấp nhận eventual consistency, và khi nào messaging là đáng giá so với đồng bộ trực tiếp?

## Câu hỏi làm rõ nên cân nhắc

1. Search freshness SLO chấp nhận bao lâu, đặc biệt với giá và trạng thái bán?
2. Autocomplete cần phân tích ngôn ngữ nào, typo tolerance và relevance ra sao?
3. Product updates theo batch hay liên tục, throughput và peak thế nào?
4. Có multi-tenant/multi-market visibility hay hạn chế sản phẩm theo user không?
5. Search outage cần fallback nào; ngân sách vận hành cho messaging và cluster là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1
Đừng dùng search index làm nguồn xác nhận tồn kho khi checkout.

### Gợi ý 2
Xem xét dual-write failure, duplicate/out-of-order events và reindex.

### Gợi ý 3
Tách transaction SQL, outbox publisher, idempotent indexer, alias swap và checkout invariant.

## Cấu trúc trả lời đề xuất

1. Phân loại dữ liệu và consistency requirement.
2. Định nghĩa APIs, ownership và search document.
3. Chọn cơ chế đồng bộ với failure semantics rõ ràng.
4. Thiết kế index lifecycle, security, query performance.
5. Xây dựng recovery, testing, observability và rollout.
6. So sánh direct indexing, queue-based và batch approaches.

## Ý chính của câu trả lời tốt

### Bắt buộc
SQL là source of truth; checkout kiểm tra tồn kho trong transaction/atomic update phù hợp; search eventual consistency; có reindex và reconciliation; đo lag.

### Điểm cộng
Transactional outbox, idempotent consumer, version-aware updates, dead-letter handling, index alias, analyzer design, access-control filters.

### Senior+
Đánh giá có cần Service Bus hay chưa, xây dựng SLO/cost model, kế hoạch schema evolution, backfill song song và rollback search.

## Hướng giải quyết tham khảo

**Boundaries:** Product write API cập nhật SQL Server. Search API chỉ truy vấn Elasticsearch; checkout không tin số lượng tồn kho hiển thị trên search result. Checkout phải kiểm tra lại availability/pricing và dùng concurrency control/atomic stock reservation trong SQL theo business invariant. Index chứa trường cần tìm/filter/sort, tránh đưa dữ liệu nhạy cảm không cần thiết.

**Synchronization:** Direct SQL + Elasticsearch dual-write không atomic: SQL commit rồi index thất bại, hoặc index trước khi SQL commit. Với yêu cầu độ tin cậy cao, ghi outbox event cùng SQL transaction, background publisher đưa event vào Azure Service Bus, consumer cập nhật Elasticsearch. Message có stable event ID, product ID, version và timestamp; consumer idempotent, từ chối event cũ dựa trên monotonic version để tránh out-of-order regression. At-least-once delivery đồng nghĩa duplicate có thể xảy ra; DLQ và replay phải được thiết kế. Nếu hệ thống nhỏ, batch incremental sync + reconciliation có thể đủ và ít complexity hơn.

**Query:** Dùng field mapping thích hợp cho full-text vs exact filter; analyzer theo ngôn ngữ, keyword fields cho filter/sort, autocomplete strategy được đo bằng relevance dataset. Search API thực thi tenant/market authorization ở server, không tin filter client. Paginate có giới hạn; tránh deep pagination không kiểm soát. Không đưa price/stock stale vào quyết định thanh toán.

**Recovery:** Duy trì checkpoint và reconciliation giữa SQL và index; khi đổi mapping, tạo index mới, backfill theo snapshot/version, bắt kịp delta events rồi atomic alias switch sau khi validate. Rollback alias khi lỗi relevance/schema; không xóa index cũ ngay. Khi Elasticsearch outage, trả lỗi search có kiểm soát hoặc fallback hạn chế theo requirement; không làm checkout bị phụ thuộc search. Khi Service Bus outage, outbox backlog tăng nhưng SQL writes vẫn có thể thành công trong giới hạn storage và SLO.

**Observability:** Đo outbox age, queue depth, oldest event age, indexing error/retry/DLQ, search p95, zero-result rate, relevance quality, index document count mismatch, product freshness percentile. Alert theo business SLO, không chỉ CPU. Test duplicate/out-of-order messages, partial failure, schema migration, large reindex và checkout với stale search result.

**Trade-offs:** Messaging tăng độ bền và decoupling nhưng thêm vận hành, eventual consistency và chi phí; direct indexing đơn giản hơn nhưng cần recovery. Elasticsearch cải thiện search nhưng thêm cluster, index tuning, reindex và relevance evaluation. Chỉ tách microservice khi ownership, scale hoặc deployment boundary thực sự cần.

## Mẫu trả lời trong phỏng vấn

“Tôi giữ SQL Server làm source of truth và Elasticsearch làm read model cho search. Checkout luôn kiểm tra tồn kho và giá hiện hành trong SQL, không dựa vào dữ liệu index có thể stale. Trước khi chọn messaging tôi hỏi freshness SLO và update volume. Nếu cần đồng bộ đáng tin cậy, tôi dùng transactional outbox rồi Service Bus và consumer idempotent có product version để tránh event cũ ghi đè event mới. Tôi thiết kế DLQ, reconciliation và quy trình reindex với alias switch. Search API áp dụng authorization theo market, đo p95 và indexing lag. Nếu tải nhỏ và batch sync đáp ứng SLO, tôi chọn giải pháp đơn giản hơn thay vì dựng pipeline phức tạp.”

## Câu hỏi đào sâu

1. Nếu 2 updates cùng product đến consumer ngược thứ tự, bạn bảo đảm index cuối cùng đúng bằng cách nào?
2. Nếu requirement yêu cầu giá hiển thị chính xác tuyệt đối trong mọi search result, thiết kế của bạn phải thay đổi thế nào?
3. Khi reindex 1 triệu documents mất nhiều giờ, làm sao không bỏ sót thay đổi trong thời gian backfill?

## Lỗi trả lời thường gặp

- Dùng Elasticsearch làm source of truth cho checkout.
- Cho rằng Service Bus bảo đảm exactly-once end-to-end.
- Không có cơ chế versioning, replay hoặc reconciliation.
- Đề xuất microservices mặc định mà không giải thích cost.
- Chỉ theo dõi queue length, bỏ qua age/freshness.

## Thang điểm 0–10

- 0–2: Chỉ nêu SQL và Elasticsearch.
- 3–4: Biết eventual consistency nhưng bỏ qua failure.
- 5–6: Thiết kế sync, query, checkout boundary hợp lý.
- 7–8: Có idempotency, ordering, reindex, security, tests và metrics.
- 9–10: Phân tích SLO, rollout/rollback, recovery và lựa chọn complexity theo evidence.

# Tổng kết hôm nay

## Kiến thức trọng tâm

HTTP timeout không đồng nghĩa cancellation xuyên suốt; request/command/transaction/connection có lifecycle riêng. CMS/CDN incident cần so sánh edge, origin, raw HTML và content version trước khi purge. Search index là read model eventual-consistent; transaction invariant của checkout phải nằm tại source of truth.

## Mẫu tư duy cần nhớ

1. Phân biệt tín hiệu timeout với trạng thái thực thi thực tế.
2. Stabilize trước, thu thập evidence rồi mới thay đổi cache/release.
3. Đo trước khi tăng pool, timeout hoặc thêm cache.
4. Thiết kế retry cùng idempotency, versioning và recovery.
5. Chọn mức độ phức tạp theo SLO và failure modes.
