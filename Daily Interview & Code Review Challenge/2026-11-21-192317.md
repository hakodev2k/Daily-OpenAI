# Code Review Challenge 1 — Elasticsearch indexing làm sản phẩm đã xóa xuất hiện trở lại

**Chủ đề:** C#/.NET 8, ASP.NET Core, PostgreSQL, Elasticsearch, asynchronous indexing, consistency

## Bối cảnh

Một marketplace dùng PostgreSQL làm source of truth và Elasticsearch làm search read model. Khi quản trị viên sửa giá, đổi trạng thái hoặc xóa mềm sản phẩm, API ghi PostgreSQL rồi cập nhật search index. Hệ thống chạy 4 instance ASP.NET Core trên Azure App Service; peak khoảng 300 cập nhật/giây, search được phép trễ tối đa 30 giây, nhưng sản phẩm bị vô hiệu hóa phải biến mất khỏi kết quả hiển thị càng sớm càng tốt. Đôi khi search hiển thị giá cũ hoặc sản phẩm đã ẩn; log API vẫn ghi 200. Có cả import bulk chạy đồng thời với chỉnh sửa từ CMS.

Đoạn code sau được rút gọn, giả định `IElasticClient` có `IndexAsync` và `DeleteAsync` trả response chứa `IsValid`; `Product` có `Id`, `Name`, `Price`, `IsActive`, `UpdatedAt`. Đừng giả định index refresh đồng bộ hoặc hệ thống chỉ có một process.

## Đoạn code cần review

```csharp
public sealed class ProductAdminService
{
    private readonly CatalogDbContext _db;
    private readonly IElasticClient _search;
    private readonly ILogger<ProductAdminService> _log;

    public ProductAdminService(
        CatalogDbContext db,
        IElasticClient search,
        ILogger<ProductAdminService> log)
    {
        _db = db;
        _search = search;
        _log = log;
    }

    public async Task UpdateAsync(
        Guid id, UpdateProductRequest request,
        CancellationToken ct)
    {
        var product = await _db.Products.FindAsync(
            new object[] { id }, ct);
        if (product is null) throw new KeyNotFoundException();

        product.Name = request.Name;
        product.Price = request.Price;
        product.IsActive = request.IsActive;
        product.UpdatedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(ct);
        _ = Task.Run(async () =>
        {
            try
            {
                if (product.IsActive)
                    await _search.IndexAsync(product, x => x
                        .Index("products").Id(product.Id));
                else
                    await _search.DeleteAsync<Product>(
                        product.Id, x => x.Index("products"));
            }
            catch (Exception ex)
            {
                _log.LogWarning(ex, "Index failed {Id}", id);
            }
        });
    }

    public async Task RebuildAsync(CancellationToken ct)
    {
        var page = 0;
        while (true)
        {
            var products = await _db.Products
                .Where(x => x.IsActive)
                .OrderBy(x => x.Id)
                .Skip(page * 1000)
                .Take(1000)
                .ToListAsync(ct);
            if (products.Count == 0) break;

            foreach (var product in products)
                await _search.IndexAsync(product, x => x
                    .Index("products").Id(product.Id), ct);

            page++;
        }
    }
}
```

## Kết quả code review tham khảo

### Critical — Fire-and-forget sau database commit

**Vấn đề:** `Task.Run` không được await và không có durable queue.  
**Tại sao xảy ra:** HTTP request hoàn tất trước khi indexing kết thúc; recycle, shutdown hoặc exception có thể làm mất công việc.  
**Ảnh hưởng production:** database đã thay đổi nhưng index không đổi vô thời hạn.  
**Cách sửa:** Ghi transactional outbox trong cùng transaction với product update; worker riêng đọc và xử lý outbox có retry, backoff, dead-letter/reconciliation.

### High — Concurrent updates đảo thứ tự

**Vấn đề:** A cập nhật trước, B cập nhật sau nhưng A có thể index cuối cùng.  
**Tại sao xảy ra:** hai task độc lập, không có version guard.  
**Ảnh hưởng production:** giá cũ ghi đè giá mới; trạng thái đã ẩn có thể bị phục hồi.  
**Cách sửa:** tăng `SearchVersion` đơn điệu trong database khi thay đổi; dùng external versioning phù hợp hoặc serialize theo product key và xác minh version khi xử lý. Version phải gắn với trạng thái đã commit.

### High — Rebuild ghi đè delete/update trực tuyến

**Vấn đề:** Rebuild đọc snapshot cũ rồi index lại sau delete.  
**Tại sao xảy ra:** rebuild và incremental indexing cùng ghi index `products`, không có checkpoint/alias cutover.  
**Ảnh hưởng production:** sản phẩm đã ẩn xuất hiện trở lại, search bị regression hàng loạt.  
**Cách sửa:** rebuild vào index versioned mới, replay change events từ checkpoint, kiểm tra độ trễ rồi atomic alias swap; tiếp tục replay tới khi an toàn.

### High — Không kiểm tra Elasticsearch response

**Vấn đề:** response có thể báo không thành công dù không throw.  
**Tại sao xảy ra:** kết quả `IndexAsync/DeleteAsync` bị bỏ qua.  
**Ảnh hưởng production:** silent failure, 200 giả tạo, backlog không được theo dõi.  
**Cách sửa:** kiểm tra status/result và phân loại retryable vs permanent; chỉ ack outbox khi thao tác được xác nhận thành công.

### High — EF entity mutable bị capture ngoài request scope

**Vấn đề:** closure giữ entity đã tracking, có thể bị sửa/không còn phù hợp khi task chạy.  
**Tại sao xảy ra:** dùng object mutable thay vì immutable event/snapshot sau commit.  
**Ảnh hưởng production:** dữ liệu index không phản ánh một commit cụ thể; vòng đời DI không bảo đảm cho background work.  
**Cách sửa:** outbox lưu product ID + version, worker tạo scope riêng và đọc trạng thái phù hợp.

### Medium — Không có optimistic concurrency ở database

**Vấn đề:** hai admin có thể lost update.  
**Tại sao xảy ra:** không dùng concurrency token hay expected version.  
**Ảnh hưởng production:** trạng thái product cuối cùng không phản ánh ý định người dùng.  
**Cách sửa:** dùng concurrency token/version và trả conflict có ý nghĩa, hoặc xác định rõ last-write-wins theo requirement.

### Medium — Offset pagination khi dữ liệu thay đổi

**Vấn đề:** `Skip(page * 1000)` có thể bỏ sót/trùng khi tập `IsActive` thay đổi.  
**Tại sao xảy ra:** tập dữ liệu không ổn định giữa các trang.  
**Ảnh hưởng production:** index rebuild thiếu document, chi phí truy vấn tăng theo offset.  
**Cách sửa:** keyset pagination trên ID cùng snapshot/cutoff phù hợp; vẫn cần replay changes để đạt consistency.

### Medium — Index tuần tự và không có giới hạn tải

**Vấn đề:** mỗi sản phẩm một request, rebuild tốn thời gian và tạo áp lực lên cluster.  
**Tại sao xảy ra:** không có bulk API, batching, throttling, retry từng phần.  
**Ảnh hưởng production:** backlog, timeout, indexing pressure.  
**Cách sửa:** bulk indexing có bounded batch, bounded concurrency, phân tích lỗi từng item và backpressure.

### Medium — Thiếu cancellation và quan sát tiến độ

**Vấn đề:** task nền không nhận `ct`; warning thiếu operation/version, không có lag metric.  
**Tại sao xảy ra:** xử lý không nằm trong managed worker lifecycle.  
**Ảnh hưởng production:** khó shutdown sạch, không biết dữ liệu nào chưa đồng bộ.  
**Cách sửa:** `BackgroundService` dùng stopping token, structured logs, tracing, outbox age và reconciliation.

### Medium — Không có validation/authorization thể hiện trong service

**Vấn đề:** request cập nhật giá/trạng thái chưa chứng minh được authorization và domain validation.  
**Tại sao xảy ra:** boundary API không được cung cấp; không thể kết luận toàn hệ thống thiếu bảo vệ.  
**Ảnh hưởng production:** nếu API layer không kiểm tra, người dùng sai quyền có thể sửa giá hoặc đưa nội dung không hợp lệ vào index.  
**Cách sửa:** xác minh policy-based authorization ở endpoint và business validation tại boundary/domain; kiểm thử end-to-end.

## Phiên bản đề xuất

Một thiết kế rút gọn dùng PostgreSQL làm source of truth, transactional outbox và worker. Các type `CatalogDbContext`, `SearchOutbox`, `IProductIndexWriter` và schema là contract minh họa cần triển khai cụ thể; không phải thư viện .NET có sẵn.

```csharp
public async Task UpdateAsync(
    Guid id, UpdateProductRequest request, CancellationToken ct)
{
    await using var tx = await _db.Database.BeginTransactionAsync(ct);
    var p = await _db.Products.SingleOrDefaultAsync(x => x.Id == id, ct)
        ?? throw new KeyNotFoundException();

    // SearchVersion là bigint được cập nhật atomically cùng product.
    p.Name = request.Name;
    p.Price = request.Price;
    p.IsActive = request.IsActive;
    p.SearchVersion++;

    _db.SearchOutbox.Add(new SearchOutbox
    {
        EventId = Guid.NewGuid(),
        ProductId = p.Id,
        Version = p.SearchVersion,
        CreatedUtc = DateTime.UtcNow,
        State = "Pending"
    });
    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}

// Worker: mỗi lần claim một batch có lease/visibility timeout.
// Worker khác có thể xử lý trùng; correctness không phụ thuộc exactly-once.
public async Task ProcessAsync(SearchOutbox job, CancellationToken ct)
{
    var snapshot = await _reader.LoadCommittedSnapshotAsync(
        job.ProductId, ct);

    // Nếu event cũ, dùng trạng thái hiện tại với version mới hơn.
    // Delete cũng phải mang version để chống resurrection.
    var version = snapshot?.SearchVersion ?? job.Version;
    var result = snapshot is { IsActive: true }
        ? await _index.UpsertWithExternalVersionAsync(
            snapshot, version, ct)
        : await _index.DeleteWithExternalVersionAsync(
            job.ProductId, version, ct);

    if (!result.Success && !result.IsStaleVersion)
        throw new SearchIndexException(result.Error);

    await _outbox.MarkDoneAsync(job.EventId, ct);
}
```

**Điều kiện bắt buộc của design:** `SearchVersion` phải tăng theo mọi thay đổi liên quan search và được bảo vệ bởi optimistic concurrency hoặc atomic database update; worker phải phân biệt lỗi version conflict do event cũ với lỗi thực sự. Khi delete hard và không còn snapshot, cần tombstone/version bền vững; không suy ra version an toàn từ `UpdatedAt`. Claim outbox phải tránh nhiều worker claim cùng job, nhưng duplicate processing vẫn được xử lý idempotently. `MarkDone` và Elasticsearch không thể commit trong cùng database transaction: crash sau index trước ack dẫn đến retry, do đó versioning/idempotency là thiết yếu.

## Giải thích thiết kế sau khi sửa

Database commit và outbox insert là một transaction: hoặc cả hai tồn tại hoặc cả hai rollback. Worker retry được mà không đảo ngược trạng thái mới vì index operation có version guard. Rebuild vào index mới tránh ghi đè trực tiếp index đang phục vụ; alias swap chỉ sau khi đồng bộ và kiểm chứng. Search có eventual consistency; API admin cần đọc database khi cần trạng thái ngay lập tức. Với yêu cầu tuyệt đối không được hiển thị sản phẩm ẩn, cần thêm authorization/status gate từ nguồn authoritative trước khi hiển thị hoặc định nghĩa SLA và cơ chế chặn; riêng search index không cung cấp strong consistency.

## Trade-offs

Outbox thêm bảng, retention, worker, retry và vận hành; tăng write amplification. Versioned rebuild cần dung lượng index tạm thời và cutover protocol. Kiểm tra trạng thái authoritative trên từng search hit có thể tăng latency và database load; cân nhắc batch lookup hoặc filter bổ sung tùy yêu cầu. Không cần microservices chỉ để giải quyết bài toán này; worker trong cùng deployment có thể đủ nếu quản lý lease và lifecycle đúng.

## Cách kiểm thử

1. **Integration/failure-path:** commit database rồi kill process trước index; restart worker phải hoàn tất outbox.
2. **Concurrency:** hai cập nhật A/B cùng ID, cố tình đảo thứ tự delivery; index cuối phản ánh version mới nhất.
3. **Database test:** hai admin sửa đồng thời; kiểm tra optimistic concurrency, không lost update ngoài chính sách.
4. **Rebuild test:** deactivate và update giữa rebuild, replay rồi alias swap; không resurrection, không thiếu record.
5. **Load test:** 300 updates/giây, Elasticsearch trả 429/5xx và partial bulk failure; kiểm tra backoff, bounded lag, DLQ và recovery.

## Quan sát trong production

Ghi `productId`, `eventId`, `version`, `attempt`, `indexName`, `traceId` (không log PII). Dashboard: outbox pending count/oldest age, successful indexing rate, version conflicts, retries, 429/5xx, dead-letter count, bulk partial failures, search freshness lag p95/p99, alias generation và DB-to-index reconciliation mismatch. Alert khi oldest age vượt 30 giây hoặc index lag liên tục tăng; phân biệt indexing acknowledged với document searchable sau refresh. Dùng Application Insights tracing và Kibana/Elasticsearch metrics để xác định chặng nghẽn.

## Kết quả code review tham khảo

### Critical — Preview được bật bằng query mà không authorization

**Vấn đề:** bất kỳ request có key `preview` đều yêu cầu renderer trả draft.  
**Tại sao xảy ra:** code tin query parameter thay vì kiểm tra authenticated editor và quyền truy cập content.  
**Ảnh hưởng production:** có thể lộ nội dung chưa publish; tùy renderer và upstream, đây là broken access control.  
**Cách sửa:** preview route riêng, authentication/authorization theo content, server-side preview context hoặc signed short-lived preview token có scope; không coi query là quyền.

### Critical — Shared cache có thể lưu preview hoặc personalized HTML

**Vấn đề:** mọi GET được gán `public, s-maxage=86400` trước khi biết response là gì.  
**Tại sao xảy ra:** response phụ thuộc preview, language, campaign cookie nhưng cache policy không phân loại.  
**Ảnh hưởng production:** leak giữa user/campaign hoặc public nhận draft.  
**Cách sửa:** preview/private responses dùng `Cache-Control: private, no-store`; CDN bypass rõ ràng, origin không phát shared-cache headers cho personalized HTML.

### High — Cache key không thể hiện variants

**Vấn đề:** `key` chỉ chứa path; không bao gồm host, language, representation hay campaign.  
**Tại sao xảy ra:** bỏ qua query/cookie; `X-Cache-Key` chỉ là header quan sát, không tự cấu hình Akamai cache key.  
**Ảnh hưởng production:** trả sai language, campaign hoặc site.  
**Cách sửa:** cấu hình edge cache key rõ ràng cho public variants được phép, chuẩn hóa language qua route và host; personalized response bypass thay vì tạo vô số variants.

### High — Publish không có invalidation strategy

**Vấn đề:** TTL 24 giờ ở shared cache nhưng không có purge sau publish/unpublish.  
**Tại sao xảy ra:** origin và CDN không được liên kết với CMS publish event.  
**Ảnh hưởng production:** thông tin cũ và trang đã unpublish vẫn hiện.  
**Cách sửa:** event-driven purge theo surrogate keys/content dependencies hoặc URL set; retry, audit và fallback TTL hợp lý; verify edge response sau purge.

### High — Không phân loại status/error trước khi đặt cache header

**Vấn đề:** header public được gán trước endpoint; có thể ảnh hưởng redirect/error/auth response tùy CDN policy.  
**Tại sao xảy ra:** middleware không xác định response classification.  
**Ảnh hưởng production:** cache nhầm 404/redirect hoặc thông tin auth-related.  
**Cách sửa:** cache policy do endpoint/content type quyết định, mặc định no-store cho nhạy cảm; chỉ public cache các 200 GET anonymous đã được xác minh.

### Medium — Header sau `next` có thể được set quá muộn

**Vấn đề:** `X-Cache-Key` đặt sau response đã bắt đầu.  
**Tại sao xảy ra:** streaming/response start có thể khiến header readonly và throw.  
**Ảnh hưởng production:** lỗi ngẫu nhiên, thiếu diagnostic.  
**Cách sửa:** `OnStarting` hoặc đặt header trước khi body được viết; telemetry dùng server logs/edge logs là chính.

### Medium — Canonical URL ghép chuỗi không encode/normalize

**Vấn đề:** canonical không xử lý language, host aliases, slash, query, ký tự đặc biệt.  
**Tại sao xảy ra:** tự nối `slug` thay vì dùng URL canonical đã validate từ routing/content model.  
**Ảnh hưởng production:** canonical sai, SEO duplication; nếu slug chứa ký tự đặc biệt và không escape đúng context có thể gây HTML injection tùy routing.  
**Cách sửa:** canonical resolver theo site/language/published route, URL encoding và HTML attribute encoding, tránh duplicate canonical tag.

### Medium — `Replace("</head>")` dễ thất bại

**Vấn đề:** HTML có casing khác, không có head, hoặc đã có canonical sẽ không cho kết quả mong muốn.  
**Tại sao xảy ra:** sửa HTML bằng string replace.  
**Ảnh hưởng production:** duplicate/missing canonical, khó bảo trì.  
**Cách sửa:** render canonical bằng template/component/head metadata pipeline trước khi serialize HTML.

### Medium — `lang` và `campaign` không được validate

**Vấn đề:** client kiểm soát input làm thay đổi HTML mà không có whitelist hoặc canonicalization.  
**Tại sao xảy ra:** đưa query/cookie trực tiếp vào renderer.  
**Ảnh hưởng production:** cache fragmentation, sai content hoặc injection nếu renderer không encode.  
**Cách sửa:** validate supported cultures và campaign IDs, áp dụng escaping theo context, giới hạn kích thước input.

### Medium — Không có evidence cho CDN bypass/purge

**Vấn đề:** không ghi cache status, policy classification hoặc publish-to-edge lag.  
**Tại sao xảy ra:** chỉ có header `X-Cache-Key` tại origin.  
**Ảnh hưởng production:** khó phân biệt origin stale với edge stale.  
**Cách sửa:** structured logs và Akamai cache diagnostics/purge audit, synthetic checks cho preview/public.

## Phiên bản đề xuất

Thiết kế tối giản tách route public và preview. Các interface `IContentRenderer`, `ICanonicalUrlResolver`, `IPreviewAccess` là contract minh họa, cần tích hợp với authorization và CMS content lifecycle thực tế.

```csharp
app.MapGet("/preview/{**slug}", async (
    HttpContext ctx, string? slug,
    IPreviewAccess access, IContentRenderer renderer,
    CancellationToken ct) =>
{
    var content = await access.ResolveAuthorizedDraftAsync(
        ctx.User, slug ?? "", ct);
    if (content is null) return Results.NotFound();

    ctx.Response.Headers.CacheControl = "private, no-store";
    ctx.Response.Headers.Pragma = "no-cache";
    var html = await renderer.RenderDraftAsync(content, ct);
    return Results.Content(html, "text/html; charset=utf-8");
}).RequireAuthorization("CmsEditor");

app.MapGet("/{**slug}", async (
    HttpContext ctx, string? slug,
    IPublishedContentResolver published,
    ICanonicalUrlResolver canonical,
    IContentRenderer renderer, CancellationToken ct) =>
{
    var page = await published.ResolveAsync(
        ctx.Request.Host, slug ?? "", ct);
    if (page is null) return Results.NotFound();

    var url = canonical.GetValidatedCanonicalUrl(page);
    var html = await renderer.RenderPublicAsync(page, url, ct);

    // Chỉ anonymous, published, không personalized mới shared-cache.
    if (page.IsSharedCacheSafe && ctx.User.Identity?.IsAuthenticated != true)
        ctx.Response.Headers.CacheControl =
            "public, max-age=60, s-maxage=300";
    else
        ctx.Response.Headers.CacheControl = "private, no-store";

    return Results.Content(html, "text/html; charset=utf-8");
});
```

**Lưu ý implementation:** biểu thức điều kiện anonymous ở ví dụ trên cần viết rõ để tránh nhầm precedence: `ctx.User.Identity?.IsAuthenticated != true`. Dùng biểu thức rõ ràng này trong code production. Preview path phải được Akamai cấu hình bypass caching độc lập với header origin. `GetValidatedCanonicalUrl` trả URL đã được render/HTML-attribute-encode đúng cách trong template, không string replace. Nếu auth cookie được gửi trên trang public nhưng nội dung hoàn toàn giống anonymous, chỉ bật shared caching khi đã chứng minh không phụ thuộc cookie và CDN rules không chia sẻ response có dữ liệu riêng tư. Với `Vary`, chỉ thêm header cho các request dimensions thực sự được hỗ trợ bởi cache key edge; không dùng `Vary: Cookie` như một giải pháp mặc định.

**Publish flow đề xuất:** CMS publish/unpublish → enqueue purge event có content ID + dependent page IDs + site/language → worker purge CDN keys/URLs → verify response hoặc edge invalidation status → retry có idempotency, alert khi purge lag. Dùng TTL ngắn hơn như lớp bảo vệ bổ sung; chọn giá trị theo SLO và đo hit ratio.

## Giải thích thiết kế sau khi sửa

Preview là privileged representation, không chỉ một query variant. Public page được resolve từ published state; cache eligibility là quyết định explicit dựa trên representation và user context. Akamai property configuration phải thống nhất với origin policy, bao gồm cache key, bypass, query handling và purge. Canonical URL là metadata thuộc content routing chứ không phải string manipulation trên HTML cuối.

## Trade-offs

Bypass cache preview/personalization tăng origin load nhưng ngăn leak. Public TTL ngắn làm giảm cache hit ratio, trong khi TTL dài cần purge đáng tin cậy. Purge theo URL dễ triển khai nhưng khó theo dependency của content blocks; surrogate keys/tagging phức tạp hơn nhưng giảm nguy cơ bỏ sót. Route language trong URL tăng số variant có chủ đích, hỗ trợ SEO và debugging. Không nhất thiết cần React SSR hay rewrite CMS để sửa cache correctness.

## Cách kiểm thử

1. **Security/E2E:** anonymous truy cập preview có/không query, editor hợp lệ/không có quyền content; không được lộ draft ở browser hoặc CDN.
2. **Cache matrix:** hai host, hai language, campaign cookie và anonymous; kiểm tra HTML, cache status và edge key không cross-contaminate.
3. **Publish/unpublish integration:** publish content block dùng ở nhiều page, purge và verify cả dependency URLs; thử purge API lỗi rồi retry.
4. **SEO test:** canonical trên localized route, trailing slash, URL encoded slug và redirect; Playwright xác minh chỉ một canonical hợp lệ.
5. **Load/deployment validation:** kiểm tra hit ratio, origin p95, error rate, cache bypass và rollback property config trước/sau release.

## Quan sát trong production

Thu thập `traceId`, `siteId`, `language`, `contentId`, `publishedVersion`, `cachePolicy`, `isPreview` (không log preview token/cookie). Ở Akamai quan sát hit/miss/bypass, Age, cache key behavior theo cấu hình thực tế, purge job ID/status, origin fetch rate và stale-after-publish latency. Ở Application Insights theo dõi origin p95/p99, error rate, auth denials, response classification; synthetic monitoring kiểm tra preview không cache và unpublish biến mất. Alert với preview cache hit, purge failures và content freshness vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Khi một content block xuất hiện ở 10.000 pages, bạn tổ chức invalidation thế nào để không purge toàn site?
2. Khi Akamai bị lỗi purge API nhưng origin đã publish, bạn chọn TTL, soft purge hay cách degrade nào?
3. Nếu website chuyển sang headless CMS + React, ranh giới cache/security nào vẫn phải giữ nguyên?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Transactional outbox giải quyết khoảng trống giữa database commit và tác vụ indexing, nhưng duplicate delivery vẫn phải xử lý bằng versioning/idempotency. Rebuild search index cần cutover và replay để không làm mất thay đổi trực tuyến. Shared HTTP cache chỉ an toàn với representation thật sự public và không phụ thuộc user; preview cần authorization và CDN bypass. CDN invalidation là một phần của publish correctness, không chỉ tối ưu performance.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi thêm async processing.
2. Thiết kế retry đồng thời với idempotency, ordering và reconciliation.
3. Phân loại dữ liệu public/private trước khi quyết định cache key hoặc TTL.
4. Kiểm tra behavior thực tế tại edge và origin, không suy luận chỉ từ response headers.
5. Dùng failure injection và telemetry để chứng minh hệ thống phục hồi được sau partial failure.
