# Câu 1 — Hai transaction đều đúng logic nhưng vẫn deadlock: SQL Server lock, isolation level và execution order thực sự gây ra điều gì?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** SQL Server, transactions, locks, blocking, deadlocks, isolation levels, indexes, execution plans, EF Core, concurrency, production verification

## Bối cảnh

Một ASP.NET Core .NET 8 API dùng EF Core với SQL Server để xử lý đơn hàng. Hai endpoint chạy song song dưới tải cao:

- `POST /orders/{id}/confirm` cập nhật `Orders`, sau đó ghi `InventoryReservations`;
- `POST /inventory/reconcile` cập nhật `InventoryReservations`, sau đó cập nhật `Orders`.

Trong môi trường test với traffic thấp, cả hai đều ổn. Ở production, thỉnh thoảng một request bị rollback với deadlock victim error. Team thấy:

- database CPU không cao;
- request p95 chỉ tăng trong các burst ngắn;
- retry một lần thường thành công;
- cả hai transaction thường hoàn thành trong dưới 100 ms;
- một developer cho rằng “deadlock chỉ xảy ra khi transaction chạy quá lâu”;
- một developer khác muốn đổi toàn bộ database sang `READ UNCOMMITTED` để tránh lock;
- team chưa capture deadlock graph;
- chưa xác minh execution plan và index path thực tế;
- có một composite index mới được thêm gần đây cho `InventoryReservations`;
- application chạy nhiều instances nên hai workflows có thể overlap với concurrency cao.

Không giả định trước root cause duy nhất là thứ tự `UPDATE` trong source code.

## Câu hỏi chính

Hãy giải thích **SQL Server lock acquisition, blocking, wait-for cycle và deadlock detection** hoạt động như thế nào trong scenario này. Vì sao transaction rất ngắn vẫn có thể deadlock? Isolation level và index/execution plan ảnh hưởng ra sao? Sau đó trình bày cách bạn xác minh deadlock thực tế và sửa theo hướng giảm khả năng deadlock mà không hy sinh data correctness một cách mù quáng.

## Câu hỏi làm rõ nên cân nhắc

1. Hai transaction đang chạy isolation level nào và có explicit transaction hay implicit transaction từ EF Core `SaveChanges`?
2. Deadlock graph cho thấy resource nào tạo cycle: key lock, page lock, index key, conversion lock hay resource khác?
3. Hai workflows có luôn access cùng các rows theo cùng thứ tự logical key không?
4. Index mới có làm optimizer chọn access path khác khiến lock acquisition order thay đổi không?
5. Retry policy hiện tại ở application/EF Core có giới hạn, backoff và idempotency phù hợp không?

## Gợi ý tư duy

### Gợi ý 1

Deadlock không đồng nghĩa với “transaction lâu”. Điều kiện cốt lõi là một **cycle of dependencies** giữa các sessions đang giữ và chờ resources.

### Gợi ý 2

Source-code order không phải lúc nào cũng bằng physical lock order. Execution plan, index seek/scan và row access pattern có thể thay đổi thứ tự lock thực tế.

### Gợi ý 3

Giảm isolation level có thể giảm một số locking behavior nhưng cũng thay đổi consistency semantics. Phải chứng minh requirement chấp nhận điều đó trước.

## Cấu trúc trả lời đề xuất

1. Clarify transaction boundaries và isolation level.
2. Giải thích lock acquisition và blocking.
3. Giải thích circular wait và deadlock victim selection ở mức concept.
4. Thu deadlock graph làm evidence chính.
5. Correlate graph với SQL statements, plans và indexes.
6. So sánh hypotheses: inconsistent access order, scan rộng, index change, lock escalation/conversion, transaction scope.
7. Sửa root cause theo mức ưu tiên.
8. Thiết kế bounded retry cho transient deadlock.
9. Load/concurrency test.
10. Monitor recurrence.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Blocking và deadlock không giống nhau. Blocking có thể chỉ là một session chờ session khác; deadlock cần một dependency cycle không thể tự giải quyết nếu không rollback một participant.
- Transaction ngắn vẫn có thể deadlock nếu hai transactions giữ resource khác nhau rồi chờ resource mà transaction kia đang giữ.
- Thứ tự access nhất quán giữa các workflows là một kỹ thuật quan trọng để giảm deadlock.
- Isolation level ảnh hưởng locking/row-versioning semantics nhưng hạ isolation không phải fix mặc định.
- Execution plan và index lựa chọn có thể thay đổi rows/resources được chạm tới và thứ tự lock acquisition.
- Deadlock graph phải được capture trước khi kết luận; stack trace đơn lẻ chỉ cho biết victim, không mô tả đầy đủ cycle.
- Retry có thể là safety net cho transient deadlock nhưng không thay thế root-cause remediation nếu tần suất đáng kể.

### Điểm cộng

- Nhận ra một index tốt hơn có thể giảm số rows/page touched và lock footprint, nhưng một index change cũng có thể đổi execution plan/access order theo cách làm deadlock pattern khác đi.
- Đề xuất giữ transaction scope ngắn, loại bỏ network I/O hoặc work không cần thiết khỏi transaction.
- Phân tích optimistic concurrency/row versioning nếu business semantics phù hợp, thay vì chỉ tăng timeout.
- Có correlation ID giữa application trace và SQL activity/deadlock telemetry.
- Retry phải chỉ áp dụng cho operation có thể retry an toàn và nên có giới hạn/backoff/jitter nếu traffic burst.

### Senior+

- Phân biệt concurrency-control choice theo invariant: không chọn `READ UNCOMMITTED` chỉ để “hết lock” nếu dirty reads làm sai quyết định nghiệp vụ.
- Xem deadlock như hệ quả của **resource ordering + lock footprint + concurrency**, không phải một bug SQL đơn lẻ.
- Đánh giá transaction isolation/row versioning ở cấp workload, bao gồm tempdb/version-store và consistency trade-offs khi dùng snapshot-based options.
- Biết rằng consistent logical ordering phải được verify bằng actual plans/resources; không giả định ORM query order đủ đảm bảo physical lock order.

## Hướng giải quyết tham khảo

Một deadlock có thể xảy ra như sau:

~~~text
Transaction A:
  holds lock on Order 101
  waits for InventoryReservation 9001

Transaction B:
  holds lock on InventoryReservation 9001
  waits for Order 101

A waits for B
B waits for A
=> cycle
~~~

SQL Server phát hiện cycle và chọn một transaction làm deadlock victim để rollback, cho phép transaction còn lại tiếp tục. Điều này có thể xảy ra chỉ trong vài milliseconds nếu overlap timing đúng.

Vì vậy tôi không bắt đầu bằng việc tăng timeout. Timeout không phá cycle; deadlock detector đã phải rollback một participant.

Bước đầu tiên là capture deadlock graph qua Extended Events hoặc telemetry phù hợp. Từ graph cần xác định:

- statements của từng session;
- resource/key/index đang giữ/chờ;
- lock modes;
- transaction sequence;
- application name/request context nếu có;
- victim và surviving transaction.

Sau đó lấy actual/relevant execution plans. Nếu endpoint confirm dùng index seek theo `(OrderId, Status)` nhưng reconcile scan theo một index khác rồi cập nhật order theo thứ tự không nhất quán, physical lock acquisition có thể tạo cycle dù C# nhìn khá đơn giản.

Một remediation khả thi là thống nhất resource ordering. Ví dụ cả hai workflows luôn lock/update `Orders` trước rồi `InventoryReservations`, nếu business transaction thật sự yêu cầu cả hai.

Pseudo-code:

~~~csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = await db.Orders
    .SingleAsync(x => x.Id == orderId, ct);

var reservation = await db.InventoryReservations
    .SingleAsync(x => x.OrderId == orderId, ct);

ApplyChanges(order, reservation);

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
~~~

Tuy nhiên source order chỉ là điểm bắt đầu. Tôi vẫn verify SQL generated và execution plan, vì optimizer có thể chọn plan khác nhau.

Nếu query scan quá rộng vì thiếu selective index, giảm scanned rows có thể giảm lock footprint và contention. Ví dụ nếu reconcile thường lọc theo `(Status, NextCheckAt)` thì index theo access pattern có thể hợp lý hơn một index chỉ phục vụ sorting. Nhưng phải dựa trên actual plan, row counts, selectivity và write cost.

Không dùng `READ UNCOMMITTED` để tránh deadlock trên workflow cập nhật order/inventory. Dirty read có thể làm business logic quyết định trên dữ liệu chưa commit. Nếu read-heavy paths cần giảm reader/writer blocking, có thể đánh giá row-versioning isolation như `READ_COMMITTED_SNAPSHOT`, nhưng đó là database-level concurrency policy với trade-offs riêng và không tự động giải quyết writer-writer deadlocks.

Application vẫn có thể implement bounded retry cho deadlock victim:

~~~csharp
for (var attempt = 1; attempt <= 3; attempt++)
{
    try
    {
        await ExecuteTransactionAsync(ct);
        break;
    }
    catch (SqlException ex) when (IsDeadlock(ex) && attempt < 3)
    {
        await Task.Delay(Backoff(attempt), ct);
    }
}
~~~

Nhưng retry chỉ an toàn khi operation không tạo external side effect ngoài transaction hoặc đã có idempotency mechanism.

Production verification nên theo dõi:

- deadlocks/minute;
- affected query fingerprints;
- lock waits/blocking duration;
- request retry count;
- p95/p99 latency;
- execution-plan regressions;
- rows read vs rows returned;
- index usage/write overhead.

Tài liệu tham khảo:

- Microsoft Learn — Deadlocks guide: `https://learn.microsoft.com/sql/relational-databases/sql-server-deadlocks-guide`
- Microsoft Learn — Transaction locking and row versioning guide: `https://learn.microsoft.com/sql/relational-databases/sql-server-transaction-locking-and-row-versioning-guide`

## Mẫu trả lời trong phỏng vấn

“Em sẽ phân biệt blocking với deadlock. Deadlock xảy ra khi có circular wait: transaction A giữ resource mà B cần, B lại giữ resource mà A cần. Nó không cần transaction chạy lâu; chỉ cần overlap đúng thời điểm.

Em không đổi isolation level hoặc tăng timeout trước. Em capture deadlock graph để biết exact statements, locks, keys/indexes và wait cycle. Sau đó correlate với execution plans vì source-code order không luôn bằng physical lock order.

Fix ưu tiên là giảm lock footprint, giữ transaction ngắn và thống nhất resource access order giữa các workflows. Nếu scan rộng do index/access pattern không phù hợp, em tối ưu dựa trên actual plan. Retry deadlock có thể dùng bounded như safety net nhưng operation phải retry-safe.

Em không dùng READ UNCOMMITTED cho update workflow chỉ để giảm lock vì dirty reads có thể phá correctness. Nếu cân nhắc row versioning thì em đánh giá riêng reader/writer behavior, tempdb/version-store và vẫn kiểm tra writer-writer deadlocks. Sau fix em chạy concurrency test và monitor deadlock graph/frequency chứ không chỉ nhìn CPU.”

## Câu hỏi đào sâu

1. Nếu hai transactions đã update tables theo cùng một logical order nhưng deadlock vẫn xảy ra, bạn điều tra tiếp theo hướng nào?
2. Nếu bật `READ_COMMITTED_SNAPSHOT` làm reader/writer blocking giảm nhưng deadlock writer-writer vẫn còn, bạn giải thích thế nào?
3. Một teammate đề xuất serializable isolation cho “an toàn nhất”; bạn đánh giá recommendation đó dựa trên invariants và contention ra sao?

## Lỗi trả lời thường gặp

- Nghĩ deadlock chỉ do transaction lâu.
- Tăng command timeout như fix chính.
- Dùng `READ UNCOMMITTED` cho business workflow cần consistency.
- Không capture deadlock graph mà đoán từ exception của victim.
- Retry vô hạn mà không xử lý contention/root cause.

## Thang điểm 0–10

- **0–2:** chỉ nói “database lock nhau” và tăng timeout/retry.
- **3–4:** hiểu circular wait nhưng chưa biết cách verify.
- **5–6:** giải thích đúng locks/deadlock, capture graph, access order và transaction scope.
- **7–8:** kết nối execution plan/index/isolation với lock footprint, có concurrency test và bounded retry.
- **9–10:** reasoning theo invariants/workload, phân tích row versioning trade-offs, physical access ordering và đưa remediation dựa trên evidence thay vì folklore.

# Câu 2 — App Service bắt đầu trả 401/500 sau rotation secret: Managed Identity, Key Vault hay application configuration đang lỗi?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure App Service, Managed Identity, Azure Key Vault, Microsoft Entra ID, authentication, authorization, configuration, secret rotation, deployment slots, Application Insights, incident response, security, observability

## Bối cảnh

Một ASP.NET Core application chạy trên Azure App Service Linux. Hệ thống dùng:

- Microsoft Entra ID cho authentication của internal users;
- Managed Identity để application truy cập Azure Key Vault;
- Key Vault chứa một số third-party API credentials vẫn bắt buộc dùng secret;
- deployment slots cho release;
- Application Insights cho telemetry.

Sau một planned secret rotation, production bắt đầu có lỗi:

- khoảng 12% request tới workflow thanh toán trả 500;
- một subset user reports occasional 401 khi login callback hoàn tất;
- App Service health nhìn chung vẫn xanh;
- logs có cả `403` từ Key Vault ở một số instances và `401` từ third-party API ở một số request;
- deployment slot vừa được swap khoảng 20 phút trước incident;
- Key Vault secret version mới đã được tạo nhưng version cũ chưa disable ngay;
- một developer nghi Key Vault cache secret cũ;
- một developer khác muốn cấp Key Vault role rộng hơn cho cả App Service để “đảm bảo hết 403”;
- team chưa xác minh system-assigned/user-assigned identity nào đang được ứng dụng thực sự dùng ở từng slot;
- chưa xác minh Key Vault reference/configuration nào là slot setting;
- application có code đọc một số secrets qua SDK lúc startup và một số config values qua environment settings;
- third-party provider có thể đã reject credential cũ nhưng chưa có timeline chính xác;
- chưa biết 401 của user có cùng root cause hay là một vấn đề redirect URI/cookie/data-protection khác.

Không giả định tất cả symptoms có một root cause duy nhất.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident theo thứ tự **impact → stabilize → evidence → hypotheses → verification → remediation → prevention**. Trình bày cách phân biệt lỗi Managed Identity/Key Vault authorization, stale/wrong secret version, slot configuration mismatch, third-party credential rejection và authentication issue độc lập. Đồng thời giải thích vì sao cấp quyền rộng hơn không phải remediation mặc định và cách thiết kế secret rotation/deployment để giảm blast radius.

## Câu hỏi làm rõ nên cân nhắc

1. `403` Key Vault xuất hiện với identity/object ID nào và permission model đang dùng RBAC hay access policy?
2. Production slot và staging slot có dùng cùng Managed Identity, cùng Key Vault và cùng slot-specific settings không?
3. Application đọc secret lúc startup, theo mỗi request hay qua configuration provider/cache nào?
4. Third-party `401` tương ứng secret version nào và provider đã activate/revoke credentials ở thời điểm nào?
5. User login `401` có correlate với một instance/slot/version cụ thể hay xảy ra trên toàn fleet?

## Gợi ý tư duy

### Gợi ý 1

Tạo timeline và correlation theo **instance + slot + deployment version + identity + secret version** trước khi sửa permission.

### Gợi ý 2

`403` từ Key Vault và `401` từ third-party là hai trust boundaries khác nhau. Một lỗi có thể kéo theo lỗi kia, nhưng không được coi là tương đương.

### Gợi ý 3

Secret rotation an toàn cần overlap/versioning/verification/rollback path; “replace secret rồi deploy” thường chưa đủ cho distributed rollout.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và affected workflows.
2. Pause further deployment/rotation changes.
3. Thu timeline của slot swap, secret version creation/revocation và first failures.
4. Correlate failures theo instance/slot/version/identity.
5. Liệt kê competing hypotheses.
6. Verify Key Vault access với exact principal và secret URI/version.
7. Verify third-party credential behavior.
8. Tách user-auth symptom khỏi service-to-service secret failures.
9. Chọn rollback/roll-forward least-privilege remediation.
10. Add rotation runbook, deployment validation, tests và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không cấp quyền Key Vault rộng hơn trước khi biết principal nào bị deny và operation nào cần thiết.
- Managed Identity giải quyết identity/token acquisition cho Azure resource access; nó không tự bảo đảm authorization nếu RBAC/access policy chưa đúng.
- `403` từ Key Vault cần xác minh caller identity, permission scope, secret URI/vault và slot configuration.
- `401` từ third-party API thường liên quan credential/token mà provider nhận; phải correlate với secret version application đang dùng.
- Deployment slots có thể có configuration/identity differences; cần verify slot settings và identity binding thay vì giả định swap mọi thứ giống nhau.
- User authentication 401 có thể là incident riêng; phải kiểm tra correlation trước khi gộp root cause.
- Secret rotation cần overlap window hoặc staged transition nếu provider hỗ trợ, cùng verification trước khi revoke old credential.
- Rollback application package không nhất thiết rollback external secret state.
- Least privilege vẫn là requirement trong incident; emergency remediation nên bounded và auditable.

### Điểm cộng

- Log secret **version identifier** hoặc config version nhưng tuyệt đối không log secret value.
- Có startup/readiness check phù hợp để phát hiện required dependency configuration trước khi nhận traffic, nhưng không làm health check gọi dependency quá mức.
- Tách secret retrieval failure telemetry khỏi downstream credential rejection.
- Sử dụng Managed Identity + SDK/default credential chain có kiểm soát cho Azure resource access, tránh secrets cho service-to-service Azure auth khi không cần.
- Xác minh Key Vault firewall/private endpoint/network path nếu authz đúng mà access vẫn fail.
- Có synthetic smoke test từ staging slot trước swap.

### Senior+

- Nhận ra identity của slot/app và lifecycle của user-assigned/system-assigned identity có operational consequences khác nhau; phải chọn theo deployment/ownership needs chứ không theo khẩu hiệu.
- Thiết kế rotation như distributed state transition: provider accepts new credential → vault publishes new version → application instances observe/use it → verification → old credential revoked.
- Có canary/slot validation và rollback that accounts for external state, không chỉ artifact version.
- Tách authentication, authorization, secret distribution và downstream authentication thành bốn failure domains với telemetry riêng.

## Hướng giải quyết tham khảo

### 1. Stabilize

Tôi sẽ pause thêm slot swaps/permission/secret changes để timeline không tiếp tục dịch chuyển. Nếu third-party workflow có business impact lớn, có thể tạm route về version/slot đã biết tốt **chỉ khi** version đó còn dùng credential mà provider vẫn chấp nhận.

Nếu old secret vẫn active, rollback application/config về known-good secret version có thể nhanh hơn mở rộng Key Vault permissions. Nhưng trước khi làm phải biết application lấy secret bằng versioned URI hay unversioned latest secret reference.

### 2. Build timeline

Tạo timeline như:

~~~text
T0  new secret version created
T1  staging deployed
T2  staging validation
T3  slot swap
T4  some instances restart / fetch configuration
T5  third-party begins rejecting old credential
T6  first Key Vault 403
T7  first application 500
T8  user-login 401 reports
~~~

Điều này giúp thấy symptoms nào có khả năng cùng causal chain.

### 3. Verify Managed Identity / Key Vault

Với mỗi instance/slot lỗi cần xác định:

- principal/object ID thực tế;
- vault name/resource ID;
- requested secret/action;
- RBAC role/access policy scope;
- network path nếu vault restricted;
- application configuration chỉ tới đúng vault/tenant;
- identity selection nếu app có cả system-assigned và user-assigned identity.

Không log token/secret. Telemetry nên chỉ chứa non-sensitive IDs cần debug.

Nếu principal đúng nhưng thiếu đúng action `secrets/get`, grant **minimum role/scope** cần thiết cho principal đó. Không cấp broad admin role chỉ vì incident.

### 4. Verify secret version behavior

Nếu application đọc secret lúc startup rồi cache trong singleton, các instances restart ở thời điểm khác nhau có thể dùng versions khác nhau. Nếu app dùng unversioned secret URI/config provider, behavior refresh phụ thuộc integration/configuration mechanism; cần verify thay vì đoán.

Một rotation an toàn có thể là:

~~~text
1. Create/activate credential V2 at provider.
2. Write V2 to Key Vault.
3. Deploy/reload canary instance/slot to use V2.
4. Verify provider success and telemetry.
5. Roll out all instances.
6. Verify no calls use V1.
7. Revoke/disable V1.
~~~

Nếu provider chỉ cho một active secret, rotation cần maintenance/coordination strategy khác.

### 5. Separate third-party 401

Third-party 401 cần evidence:

- outbound dependency trace;
- credential version ID/config version;
- provider response code/subcode;
- instance ID;
- time.

Một Key Vault `403` có thể khiến app không lấy được secret, nhưng third-party `401` nghĩa app đã gửi request và provider không chấp nhận authentication. Hai paths phải được trace riêng.

### 6. Separate user authentication 401

User login có thể liên quan:

- redirect URI mismatch sau slot swap;
- cookie/data-protection key issue;
- wrong authority/client config;
- clock/config mismatch;
- instance-specific deployment state.

Không nên gộp user auth vào Key Vault secret rotation nếu logs/correlation không chứng minh.

### 7. App Service slot considerations

Trước swap cần validate:

- slot-specific environment values;
- Managed Identity setup;
- Key Vault connectivity;
- callback URLs/hostnames;
- deployment version;
- health/readiness;
- critical external dependency credentials.

Smoke test staging chỉ có giá trị nếu staging environment đủ giống production trust/config path hoặc có dedicated pre-production dependency validation.

### 8. Prevention

- explicit secret-version/change runbook;
- least-privilege RBAC reviewed as code/process;
- synthetic authentication/dependency checks;
- config validation at startup;
- slot-specific settings inventory;
- dependency dashboards split by Key Vault vs third-party vs Entra user auth;
- alert on Key Vault 401/403 and external API auth failures;
- no secret values in logs;
- canary rollout and revoke-old-secret only after fleet verification.

Tài liệu tham khảo:

- Microsoft Learn — Use managed identities for App Service and Azure Functions: `https://learn.microsoft.com/azure/app-service/overview-managed-identity`
- Microsoft Learn — Key Vault authentication fundamentals: `https://learn.microsoft.com/azure/key-vault/general/authentication`
- Microsoft Learn — Set up staging environments in Azure App Service: `https://learn.microsoft.com/azure/app-service/deploy-staging-slots`

## Mẫu trả lời trong phỏng vấn

“Em sẽ pause thêm rotation/deployment changes rồi build timeline theo slot swap, secret versions và first failures. Em không cấp Key Vault role rộng hơn ngay. Với từng 403 em xác định exact principal/object ID, vault, action, RBAC scope và network path. Managed Identity chỉ cung cấp identity/token; authorization vẫn phải đúng.

Em tách Key Vault 403 khỏi third-party 401. Third-party 401 cho biết credential mà provider nhận không hợp lệ hoặc không được chấp nhận, nên em correlate request với instance và secret-version ID, không log secret value. Nếu app cache secret lúc startup, một rolling restart có thể khiến fleet dùng mixed versions.

Rotation tốt hơn là activate V2 ở provider, publish vào Key Vault, validate trên staging/canary, roll fleet, xác minh calls dùng V2 rồi mới revoke V1. Rollback artifact không đủ nếu external credential state đã đổi.

User-login 401 em điều tra riêng theo instance/slot/redirect URI/cookie/config; chỉ gộp khi correlation chứng minh. Cuối cùng em thêm least-privilege validation, slot smoke tests và telemetry tách Key Vault, Entra user auth và third-party authentication.”

## Câu hỏi đào sâu

1. Nếu Key Vault RBAC hoàn toàn đúng nhưng chỉ production slot nhận 403 còn staging slot không, bạn điều tra tiếp network/identity/configuration theo thứ tự nào?
2. Nếu provider chỉ cho phép một active credential tại mọi thời điểm, bạn thiết kế rotation thế nào để downtime và security exposure chấp nhận được?
3. Một teammate đề xuất copy third-party secret vào App Service environment variable để loại Key Vault khỏi critical path; bạn đánh giá trade-off bảo mật, availability và rotation ra sao?

## Lỗi trả lời thường gặp

- Cấp Key Vault quyền rộng hơn mà không xác minh principal/action.
- Coi Managed Identity đồng nghĩa với auto-authorization.
- Gộp Key Vault 403, third-party 401 và user 401 thành một root cause.
- Rollback code mà quên external secret state đã thay đổi.
- Log secret/token để debug production.

## Thang điểm 0–10

- **0–2:** chỉ rotate lại secret hoặc cấp quyền rộng.
- **3–4:** biết kiểm tra Key Vault/Managed Identity nhưng thiếu timeline và failure-domain separation.
- **5–6:** điều tra đúng principal/config/secret version và rollback/roll-forward có kiểm soát.
- **7–8:** có slot-aware validation, least privilege, secure telemetry và staged rotation.
- **9–10:** xem rotation như distributed state transition, tách trust boundaries rõ ràng và thiết kế recovery/verification cho external state + multi-instance deployment.

# Câu 3 — Modernize hệ thống .NET Framework 4.5 + jQuery: nâng cấp incremental hay rewrite sang .NET 8/React và Kubernetes?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** .NET Framework 4.5, .NET modernization, ASP.NET MVC, ASP.NET Core, .NET 8, jQuery, React.js, IIS, Windows Server, Azure App Service, SQL Server, CI/CD, migration strategy, compatibility, testing, rollout, rollback, architecture trade-offs

## Bối cảnh

Một internal enterprise portal đã hoạt động khoảng 8 năm. Hiện tại:

- ASP.NET MVC trên .NET Framework 4.5;
- host trên IIS/Windows Server;
- frontend dùng Razor views + jQuery;
- SQL Server là database chính;
- một số business logic nằm trong controllers, một số trong service classes;
- authentication tích hợp với enterprise identity cũ;
- có khoảng 150 screens;
- deployment qua Jenkins + Octopus Deploy;
- test automation rất ít, chủ yếu manual regression;
- business vẫn yêu cầu feature delivery hàng tháng;
- uptime quan trọng nhưng không phải 24/7 life-critical;
- một số third-party libraries cũ chưa rõ hỗ trợ modern .NET hay không;
- một subsystem report dùng Windows-only dependency;
- team có kinh nghiệm ASP.NET Core/.NET 8, React/Vue và Azure App Service;
- không có dedicated Kubernetes/SRE team;
- leadership muốn “modernize hoàn toàn trong 9 tháng”.

Có ba đề xuất:

1. rewrite toàn bộ sang .NET 8 + React + microservices + Kubernetes rồi cut over một lần;
2. nâng application lên modern .NET theo từng vertical slice, giữ SQL Server và một phần UI cũ trong giai đoạn chuyển tiếp;
3. chỉ nâng .NET Framework lên bản mới hơn và giữ architecture/UI gần như cũ để giảm rủi ro.

Chưa có inventory đầy đủ về dependencies, runtime compatibility, traffic per module, feature churn, business criticality, data coupling hoặc acceptable dual-running period.

## Câu hỏi chính

Hãy xây dựng một **modernization strategy có thể triển khai thực tế**, bao gồm discovery, dependency inventory, target architecture, migration slicing, UI strategy, authentication, database compatibility, deployment/hosting, testing, observability, rollback và organizational cost. Bạn phải giải thích khi nào incremental migration hợp lý, khi nào rewrite một subsystem là chấp nhận được, và vì sao React/microservices/Kubernetes không nên được chọn chỉ để “hiện đại hơn”.

## Câu hỏi làm rõ nên cân nhắc

1. Module nào thay đổi nhiều nhất, tạo nhiều incident nhất hoặc có business value cao nhất?
2. Third-party/Windows-only dependencies nào chặn modern .NET hoặc Linux hosting?
3. Authentication protocol/provider hiện tại có thể tích hợp song song old và new apps không?
4. Database schema có module boundaries rõ hay mọi màn hình cùng truy cập chéo nhiều tables?
5. Business chấp nhận side-by-side routing/gradual cutover trong bao lâu và rollback window cần thế nào?

## Gợi ý tư duy

### Gợi ý 1

Modernization không bắt đầu bằng framework target. Bắt đầu bằng **inventory, risk và seams**.

### Gợi ý 2

Bạn có thể modernize runtime, hosting, architecture và frontend ở các tốc độ khác nhau. Không bắt buộc đổi tất cả cùng lúc.

### Gợi ý 3

Một migration tốt cần tạo **reversible intermediate states**, không chỉ mô tả target end-state.

## Cấu trúc trả lời đề xuất

1. Discovery và dependency inventory.
2. Baseline telemetry và business criticality.
3. Chọn target principles, không over-specify architecture sớm.
4. Xác định migration seams/vertical slices.
5. Thiết kế old/new coexistence.
6. Authentication/session/data integration.
7. Database/schema transition.
8. Frontend modernization strategy.
9. Hosting/deployment decisions.
10. Testing safety net.
11. Rollout/rollback.
12. Criteria để tách service hoặc rewrite subsystem.
13. Success metrics và completion definition.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không estimate/cam kết rewrite 9 tháng trước dependency/system inventory.
- Incremental modernization thường giảm migration risk khi business vẫn cần feature delivery.
- Không bắt buộc migrate backend + frontend + database + hosting cùng một lần.
- Third-party compatibility và Windows-only dependencies phải được inventory/prototyped sớm.
- Old và new systems cần coexistence strategy: routing, auth, shared data/contracts và rollback.
- Database compatibility phải được giữ trong mixed-version period.
- Testing phải được tăng trước/đồng thời migration; thiếu regression safety net làm rewrite risk cao.
- Microservices/Kubernetes chỉ hợp lý khi service boundaries, scaling/ownership/operational requirements justify complexity.
- App Service hoặc IIS có thể là target/intermediate hosting hợp lý hơn Kubernetes.
- Rewrite có thể hợp lý cho isolated subsystem nhỏ, poorly salvageable hoặc có contract boundary rõ; không nên coi rewrite toàn hệ thống là mặc định.

### Điểm cộng

- Dùng strangler-style routing theo route/module để chuyển từng vertical slice.
- Ưu tiên characterization tests/integration tests cho critical legacy behavior trước khi refactor.
- Có compatibility adapter/facade quanh legacy dependencies để giảm coupling.
- Tách authentication modernization khỏi business-module migration bằng shared/compatible identity boundary nếu có thể.
- Frontend có thể migrate route-by-route; Razor/jQuery không cần biến mất ngày đầu.
- Có observability parity giữa old/new và business KPI comparison trong dual run.

### Senior+

- Tạo dependency/risk matrix và chọn first slice vừa có value vừa đủ bounded để học migration path.
- Xem migration như portfolio of reversible steps với explicit exit criteria.
- Phân biệt “technical modernization” và “architecture rewrite”; không dùng Clean Architecture/microservices như mục tiêu tự thân.
- Đưa organization/operational capability vào hosting decision; platform complexity là một cost thật.
- Có decommission plan: migration chưa hoàn tất nếu old runtime còn hidden dependencies/traffic không được đo.

## Hướng giải quyết tham khảo

### 1. Discovery trước target architecture

Trong 2–4 tuần discovery kỹ thuật đầu, tôi muốn có inventory:

~~~text
Module / route
Business criticality
Change frequency
Incident frequency
Dependencies
Framework APIs
Third-party packages
Windows-only dependencies
Database tables touched
Authentication/session assumptions
File system / scheduled jobs
External integrations
Current test coverage
Traffic / latency
~~`

Dùng tooling/AI-assisted repository analysis để hỗ trợ inventory được, nhưng findings phải verify bằng build, static analysis, runtime traces và developer knowledge.

Không chốt “9 tháng rewrite xong” trước khi biết blockers.

### 2. Baseline target

Một target ban đầu có thể đơn giản:

- ASP.NET Core/.NET 8 cho modules mới/migrated;
- modular application trước, không tách microservices nếu chưa có ownership boundary;
- SQL Server giữ nguyên source of truth trong giai đoạn đầu;
- App Service hoặc IIS tùy Windows dependency/hosting needs;
- CI/CD có automated build/test/deploy;
- Application Insights/structured logging cho new app;
- route-by-route migration.

Target có thể tiến hóa sau khi có evidence.

### 3. Chọn first slice

Không chọn authentication hoặc subsystem khó nhất làm first migration nếu không cần. Một vertical slice tốt nên:

- có route/data boundary tương đối rõ;
- user flow đủ thật để validate architecture;
- không quá critical;
- có business value;
- có manageable dependencies.

Ví dụ migrate một approval/report-management module ít coupled trước.

### 4. Coexistence / strangler routing

Có thể đặt reverse proxy/routing layer trước old/new apps:

~~~text
Browser
   |
Gateway / reverse proxy
   |--------------------|
/legacy/*            /projects/*
   |                    |
.NET Framework       ASP.NET Core
IIS                  App Service/IIS
        \            /
          SQL Server
~~~

Shared DB trong transition có trade-offs nhưng có thể là pragmatic intermediate state. New code không được tùy tiện đổi schema theo cách phá legacy consumers.

Nếu routes migrated hoàn toàn, traffic chuyển sang new app. Rollback route có thể quay lại old app nếu schema/data vẫn backward-compatible.

### 5. Authentication

Phải prototype authentication early. Nếu enterprise identity hỗ trợ standards mà cả old/new có thể dùng, giữ centralized identity boundary sẽ đơn giản hơn copy session state.

Nếu legacy app dùng custom session/cookie không tương thích, có thể cần gateway/SSO transition hoặc explicit re-authentication. Không hack bằng chia sẻ secret/cookie nếu crypto/framework semantics không tương thích và security team chưa approve.

### 6. Database

Không split database per microservice ngay nếu domains chưa rõ.

Áp dụng schema evolution tương thích:

- additive changes trước;
- migrate/backfill;
- old/new code coexist;
- switch reads/writes;
- remove legacy fields sau khi old consumer decommission.

Theo dõi table ownership dần dần để tạo seams cho tương lai.

### 7. Frontend

Không cần rewrite 150 screens sang React trước khi backend migration có value.

Options:

- giữ Razor/jQuery cho legacy routes;
- new modules dùng React/Vue nếu team có component/state complexity đáng justify SPA approach;
- hoặc Razor/modern JavaScript nếu screen đơn giản.

Nếu chuyển React, cần giải quyết auth, routing, API contracts, error handling, accessibility, bundle/performance và Playwright E2E. “React hiện đại hơn” không phải business case đủ.

### 8. Windows-only subsystem

Report subsystem có Windows-only dependency nên làm proof-of-concept sớm:

- thư viện có replacement modern .NET không?
- có thể isolate behind process/service boundary không?
- cần giữ Windows hosting cho module đó không?
- license/behavior có tương thích container/Linux không?

Có thể modernize phần lớn app lên App Service Linux nhưng giữ một bounded Windows worker/service nếu dependency bắt buộc. Hoặc toàn app vẫn chạy Windows App Service/IIS ở intermediate stage. Linux không phải goal bắt buộc.

### 9. Testing safety net

Trước mỗi slice:

- characterization tests cho behavior quan trọng;
- integration tests database/API;
- contract tests với external dependencies;
- Playwright E2E cho critical user journeys;
- migration tests trên production-like schema/data volume;
- rollback validation.

Không cần đạt “100% coverage”. Mục tiêu là risk coverage.

### 10. Deployment / observability

Old và new telemetry phải share correlation/business identifiers để compare:

- error rate;
- p95/p99;
- throughput;
- login failures;
- DB query load;
- user completion rate;
- deployment version;
- route distribution old/new.

Rollout từng slice có canary/percentage/routing gate nếu infrastructure hỗ trợ.

### 11. Khi nào rewrite subsystem?

Rewrite hợp lý khi subsystem:

- nhỏ và bounded;
- business behavior được hiểu/test được;
- legacy code không reuse đáng kể;
- dependencies đã xác minh;
- migration/cutover path rõ;
- cost thấp hơn incremental untangling.

Rewrite toàn hệ thống 150 screens với ít tests, shared DB và unknown dependencies có risk cao hơn nhiều.

### 12. Khi nào microservices/Kubernetes?

Chỉ tách service khi có requirement rõ như:

- independent scaling;
- independent release cadence/team ownership;
- isolation boundary;
- separate data lifecycle;
- asynchronous workload lifecycle rất khác.

Kubernetes chỉ khi orchestration requirements và team operational maturity justify. Nếu App Service đáp ứng scale/deployment/availability, nó thường giảm burden đáng kể.

### 13. Success criteria

Modernization completion không chỉ là “build trên .NET 8”. Cần measurable outcomes:

- % traffic/routes migrated;
- legacy dependency count;
- automated regression coverage cho critical journeys;
- deploy frequency/failure rate;
- incident rate;
- performance baseline;
- old server/runtime decommissioned;
- rollback/runbooks proven.

Tài liệu tham khảo:

- Microsoft Learn — Port from .NET Framework to .NET: `https://learn.microsoft.com/dotnet/core/porting/`
- Microsoft Learn — .NET Upgrade Assistant overview: `https://learn.microsoft.com/dotnet/core/porting/upgrade-assistant-overview`

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhận target rewrite toàn bộ trong 9 tháng trước khi inventory. Hệ thống có 150 screens, ít automated tests, third-party unknown và Windows-only dependency nên big-bang rewrite có rủi ro rất cao.

Em bắt đầu bằng dependency/risk inventory và telemetry baseline, rồi chọn một bounded vertical slice để migrate sang ASP.NET Core/.NET 8. Old và new apps coexist qua route-level routing; SQL Server có thể tạm shared nhưng schema changes phải backward-compatible. Em tăng characterization/integration/Playwright tests cho critical journeys để có safety net.

Frontend không bắt buộc rewrite cùng backend. Legacy routes có thể giữ Razor/jQuery; module mới chỉ dùng React/Vue nếu interaction complexity justify. Hosting cũng không mặc định Kubernetes. App Service hoặc IIS có thể đủ; Windows-only report module có thể tạm isolate/giữ Windows.

Em tách microservice khi có evidence về ownership, independent scale hoặc failure boundary. Migration được coi là chuỗi reversible steps với rollout/rollback, observability và decommission criteria. Rewrite chỉ dùng cho subsystem bounded mà cost thấp hơn untangling legacy, không phải toàn hệ thống mặc định.”

## Câu hỏi đào sâu

1. Nếu new .NET 8 module phải ghi cùng tables với legacy app nhưng business muốn zero downtime, bạn quản lý schema/data compatibility thế nào qua nhiều releases?
2. Nếu leadership bắt buộc dùng Kubernetes vì “company standard” nhưng team chưa có operational skill, bạn sẽ giảm risk ra sao thay vì chỉ phản đối?
3. Nếu authentication là dependency chung khó tách nhất nhưng mọi migrated module đều cần login, bạn sẽ prototype và phase identity transition như thế nào?

## Lỗi trả lời thường gặp

- Chọn big-bang rewrite vì code cũ “xấu”.
- Đổi backend, frontend, database, auth, hosting và architecture cùng một lần.
- Chọn microservices/Kubernetes vì chúng hiện đại hơn.
- Không có coexistence/rollback strategy.
- Không xây regression safety net trước khi migration sâu.

## Thang điểm 0–10

- **0–2:** chỉ chọn framework/architecture target.
- **3–4:** đề xuất incremental migration nhưng thiếu dependency inventory hoặc rollback.
- **5–6:** có slicing, coexistence, compatibility, tests và hosting trade-offs.
- **7–8:** có risk-based sequencing, auth/data transition, observability, decommission criteria và organization-aware decisions.
- **9–10:** thiết kế modernization như chương trình tiến hóa có reversible states, measurable outcomes, explicit cost-of-complexity và biết khi nào rewrite/tách service thực sự có ROI.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Deadlock là circular wait giữa resources; transaction ngắn vẫn có thể deadlock và actual lock order phụ thuộc query plan/access path chứ không chỉ source-code order.
- Isolation level là consistency decision, không phải nút “tắt lock”; thay đổi isolation phải dựa trên business invariants và workload evidence.
- Managed Identity, Key Vault authorization, third-party authentication và user authentication là các trust boundaries khác nhau; incident investigation cần tách chúng bằng correlation và timeline.
- Secret rotation trong multi-instance deployment là một distributed state transition cần versioning, overlap, verification và rollback semantics.
- Modernization an toàn thường là chuỗi bước incremental, observable và reversible; framework, frontend, database và hosting không cần đổi cùng lúc.
- Microservices/Kubernetes/React không phải thước đo của “modern”; complexity chỉ đáng trả khi requirements và operating model justify.

## Mẫu tư duy cần nhớ

- **Capture evidence before changing concurrency or isolation semantics.**
- **Separate trust boundaries before merging incident root causes.**
- **Treat rotation and deployment as state transitions, not file replacement.**
- **Modernize by bounded, reversible slices instead of target-architecture slogans.**
- **Choose complexity only when measurable requirements pay for it.**
