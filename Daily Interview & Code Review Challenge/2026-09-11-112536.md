# Code Review Challenge 1 — Service Bus consumer `Complete` message trước khi transaction hoàn tất: traffic bình thường ổn nhưng mất order khi SQL chập chờn

**Chủ đề:** C#/.NET 8, Azure Service Bus, EF Core, at-least-once delivery, message settlement, idempotency, Inbox/Outbox Pattern, retries, external side effects, cancellation, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một order service nhận message `OrderSubmitted` từ Azure Service Bus. Mỗi message cần:

- tạo order trong SQL Server;
- trừ hạn mức tín dụng nội bộ của customer;
- ghi audit event;
- sau đó gửi email xác nhận qua một external notification API;
- message có thể được deliver lại;
- nhiều replicas của consumer cùng xử lý queue;
- transient SQL/network failure là bình thường và không được gây mất order;
- duplicate delivery không được tạo duplicate order hoặc trừ hạn mức hai lần;
- notification có thể eventual-consistent;
- production cần biết duplicate rate, processing latency, retry/DLQ và age của message backlog.

Sau một incident SQL latency tăng khoảng 40 giây, business phát hiện một số message đã biến mất khỏi queue nhưng order tương ứng không có trong database. Ở một nhóm khác, khách hàng nhận hai email xác nhận dù chỉ submit một order.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class OrderSubmittedConsumer : IHostedService
{
    private readonly ServiceBusProcessor _processor;
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly NotificationClient _notificationClient;
    private readonly ILogger<OrderSubmittedConsumer> _logger;

    public OrderSubmittedConsumer(
        ServiceBusClient client,
        IServiceScopeFactory scopeFactory,
        NotificationClient notificationClient,
        ILogger<OrderSubmittedConsumer> logger)
    {
        _processor = client.CreateProcessor(
            "order-submitted",
            new ServiceBusProcessorOptions
            {
                AutoCompleteMessages = false,
                MaxConcurrentCalls = 32
            });
        _scopeFactory = scopeFactory;
        _notificationClient = notificationClient;
        _logger = logger;
    }

    public async Task StartAsync(CancellationToken cancellationToken)
    {
        _processor.ProcessMessageAsync += ProcessMessageAsync;
        _processor.ProcessErrorAsync += ProcessErrorAsync;
        await _processor.StartProcessingAsync(cancellationToken);
    }

    private async Task ProcessMessageAsync(ProcessMessageEventArgs args)
    {
        var message = args.Message.Body.ToObjectFromJson<OrderSubmitted>()!;

        await args.CompleteMessageAsync(args.Message);

        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var order = new Order
        {
            Id = message.OrderId,
            CustomerId = message.CustomerId,
            Total = message.Total,
            CreatedAtUtc = DateTime.UtcNow
        };

        db.Orders.Add(order);

        var credit = await db.CustomerCredits
            .SingleAsync(x => x.CustomerId == message.CustomerId);

        credit.Available -= message.Total;

        db.AuditEvents.Add(new AuditEvent
        {
            OrderId = message.OrderId,
            Type = "OrderCreated",
            CreatedAtUtc = DateTime.UtcNow
        });

        await db.SaveChangesAsync();

        await _notificationClient.SendOrderConfirmationAsync(
            message.CustomerId,
            message.OrderId);

        _logger.LogInformation(
            "Processed order {OrderId} from message {MessageId}",
            message.OrderId,
            args.Message.MessageId);
    }

    private Task ProcessErrorAsync(ProcessErrorEventArgs args)
    {
        _logger.LogError(args.Exception, "Service Bus processor error");
        return Task.CompletedTask;
    }

    public Task StopAsync(CancellationToken cancellationToken)
        => _processor.StopProcessingAsync(cancellationToken);
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness và data-consistency trong message-processing flow.
2. Xác định reliability, concurrency, idempotency, cancellation và external-side-effect concerns.
3. Giải thích production impact theo từng failure window quan trọng.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa, ưu tiên transaction boundary đơn giản và retry-safe.
6. Giải thích testing cho duplicate delivery, SQL failure, process crash, lock expiry và notification failure.
7. Đề xuất production telemetry để chứng minh consumer không làm mất hoặc xử lý sai message.

## Câu hỏi gợi mở

1. Sau `CompleteMessageAsync`, broker còn có trách nhiệm redeliver message nếu SQL `SaveChangesAsync` thất bại hay process crash không?
2. Nếu cùng `MessageId` hoặc `OrderId` được deliver hai lần, điều gì ngăn business side effect chạy lần hai?
3. Transaction boundary hiện tại gồm những operations nào, và notification API có thể nằm trong cùng SQL transaction một cách hợp lý không?
4. Nếu handler chạy lâu hơn message lock hoặc process mất connectivity với Service Bus, outcome của việc settlement có còn chắc chắn không?
5. `MaxConcurrentCalls = 32` có được chọn dựa trên SQL connection pool/downstream capacity hay chỉ là một con số cấu hình?

## Gợi ý

### Gợi ý 1

Primary risk là **acknowledge/settle message trước khi durable business state được commit**. Hãy đặt process crash hoặc SQL timeout vào từng khoảng của flow.

### Gợi ý 2

Với at-least-once delivery, retry và duplicate không phải edge case. Hãy thiết kế một durable idempotency boundary, rồi tách side effect không transaction được bằng Outbox thay vì cố tạo distributed transaction.

## Kết quả code review tham khảo

### Critical — Message được `Complete` trước khi durable state được commit

**Vấn đề:**  
Handler gọi `CompleteMessageAsync` ngay sau deserialize, trước mọi SQL mutation.

**Tại sao xảy ra:**  
Settlement và business transaction bị đặt sai thứ tự. Khi broker đã chấp nhận completion, một lỗi sau đó không còn được broker redeliver theo normal processing flow.

**Ảnh hưởng production:**  
SQL timeout, process crash hoặc deployment đúng sau completion có thể làm message biến mất trong khi order chưa tồn tại. Đây là failure window giải thích trực tiếp symptom “message mất nhưng không có order”.

**Cách sửa:**  
Chỉ complete sau khi durable local transaction chứa business state + idempotency marker đã commit thành công. Nếu settlement sau commit gặp ambiguous failure, duplicate delivery phải được xử lý an toàn bằng idempotency.

### Critical — Không có durable idempotency cho at-least-once delivery

**Vấn đề:**  
Code không lưu `MessageId`/business idempotency key đã xử lý trong một unique durable store.

**Tại sao xảy ra:**  
Queue delivery có thể lặp lại do lock expiry, transient network failure, settlement ambiguity hoặc retry. `OrderId` có thể có unique PK, nhưng dựa vào exception từ duplicate insert không đủ để bảo vệ các side effect khác một cách có chủ đích.

**Ảnh hưởng production:**  
Duplicate delivery có thể trừ credit nhiều lần, tạo duplicate audit semantics hoặc gửi duplicate notification.

**Cách sửa:**  
Dùng Inbox/ProcessedMessages table với unique key phù hợp (`MessageId`, hoặc domain idempotency key), ghi marker trong cùng SQL transaction với order/credit/audit. Duplicate nhận lại phải trở thành no-op có quan sát được.

### High — Notification side effect không atomic và không retry-safe với database commit

**Vấn đề:**  
SQL commit xong rồi mới gọi external notification API trực tiếp.

**Tại sao xảy ra:**  
Không thể transactionally commit SQL state và HTTP side effect trong một local database transaction. Nếu notification thành công nhưng response bị mất, retry có thể gửi lại; nếu process crash sau SQL commit nhưng trước notification, email có thể không bao giờ gửi.

**Ảnh hưởng production:**  
Khách hàng có thể nhận hai email hoặc không nhận email dù order đã tạo.

**Cách sửa:**  
Trong cùng SQL transaction, ghi một Outbox message `OrderConfirmationRequested`. Một publisher riêng gửi notification với stable idempotency key và đánh dấu trạng thái. Downstream notification service cũng nên hỗ trợ idempotency nếu có thể.

### High — Credit update không bảo vệ business invariant dưới concurrency

**Vấn đề:**  
`credit.Available -= message.Total` dựa vào entity được đọc rồi update; đoạn code không thể hiện check `Available >= Total`, optimistic concurrency token hoặc conditional SQL update.

**Tại sao xảy ra:**  
Hai orders của cùng customer có thể được xử lý đồng thời bởi nhiều handler/replicas.

**Ảnh hưởng production:**  
Có thể overspend credit hoặc phát sinh lost-update/concurrency conflict tùy model và database behavior.

**Cách sửa:**  
Đưa invariant vào database mutation: conditional update (`Available >= amount`), row version/optimistic concurrency với retry có giới hạn, hoặc locking/isolation phù hợp sau khi đo contention. Constraint/domain decision phải rõ khi không đủ credit.

### High — Cancellation token không được propagate vào handler dependencies

**Vấn đề:**  
`ProcessMessageAsync` không dùng `args.CancellationToken` cho SQL, settlement hoặc notification calls.

**Tại sao xảy ra:**  
Shutdown/processor cancellation không tự động cancel mọi async operation.

**Ảnh hưởng production:**  
Deployment có thể kéo dài, work tiếp tục ngoài lifecycle mong đợi, và behavior khi lock lost/shutdown khó reasoning.

**Cách sửa:**  
Propagate handler token đến EF Core, Service Bus settlement và downstream calls hỗ trợ cancellation. Tuy nhiên cancellation sau commit không được hiểu là rollback; idempotency vẫn bắt buộc.

### High — Deserialize failure không có explicit poison-message strategy

**Vấn đề:**  
`ToObjectFromJson<OrderSubmitted>()!` giả định payload hợp lệ và không xác định cách xử lý schema-invalid/permanent message.

**Tại sao xảy ra:**  
Permanent deserialization/domain-validation errors khác transient infrastructure failures nhưng đang đi chung exception path.

**Ảnh hưởng production:**  
Poison message có thể retry nhiều lần, làm noise và tiêu tốn throughput; hoặc bị xử lý không nhất quán tùy processor configuration.

**Cách sửa:**  
Validate schema/version/domain fields, classify permanent failure và dead-letter với reason/diagnostic an toàn; transient failures mới retry theo policy.

### Medium — Concurrency 32 chưa gắn với capacity budget

**Vấn đề:**  
`MaxConcurrentCalls = 32` được hard-code mà không có evidence về SQL pool, lock contention, CPU hay notification capacity.

**Tại sao xảy ra:**  
Concurrency càng cao không đồng nghĩa throughput càng cao; shared bottleneck có thể bị overload.

**Ảnh hưởng production:**  
SQL connection pressure, lock contention, latency amplification và message-lock expiry có thể tăng khi dependency chậm.

**Cách sửa:**  
Chọn concurrency từ load test và dependency budgets; monitor handler duration, DB waits/pool usage và queue age. Scale replicas/concurrency có kiểm soát thay vì tăng mù.

### Medium — Không có explicit handling cho message lock/settlement ambiguity

**Vấn đề:**  
Code giả định `CompleteMessageAsync` có outcome nhị phân rõ ràng.

**Tại sao xảy ra:**  
Trong distributed system, connection failure có thể khiến caller không biết settlement đã được broker áp dụng hay chưa; lock cũng có thể mất khi processing dài.

**Ảnh hưởng production:**  
Message có thể quay lại sau khi business transaction đã commit.

**Cách sửa:**  
Thiết kế duplicate-safe trước; cấu hình lock renewal/processing duration phù hợp; đo lock-lost/settlement errors. Không cố “giải quyết” ambiguity bằng retry settlement mù mà thiếu idempotency.

### Medium — `StopAsync` chưa thể hiện đầy đủ disposal/lifecycle ownership

**Vấn đề:**  
Class tạo và giữ `ServiceBusProcessor` nhưng chỉ stop processing; không thể hiện disposal của processor/client ownership.

**Tại sao xảy ra:**  
Long-lived network resources cần lifecycle rõ ràng.

**Ảnh hưởng production:**  
Trong test/restart hoặc custom hosting lifecycle có thể leak resources hoặc khó shutdown sạch.

**Cách sửa:**  
Dùng `IAsyncDisposable`/hosted-service lifecycle rõ ràng, dispose processor khi service kết thúc và thống nhất ai sở hữu `ServiceBusClient`.

### Medium — Telemetry không chứng minh exactly-once business effect

**Vấn đề:**  
Một success log không đo duplicate, processing attempt, inbox hit, lock lost, dead-letter hay outbox lag.

**Tại sao xảy ra:**  
Operational signal chưa phản ánh delivery semantics và failure windows thực tế.

**Ảnh hưởng production:**  
Team có thể thấy queue depth thấp nhưng vẫn mất business operation hoặc duplicate side effect.

**Cách sửa:**  
Emit structured metrics/traces cho receive attempts, duplicate suppression, transaction outcome, settlement outcome, DLQ, processing latency, message age, outbox lag và downstream notification attempts.

## Phiên bản đề xuất

Một hướng phù hợp khi SQL Server là transaction boundary chính: Inbox + business mutations + Outbox được commit trong **một local transaction**; message chỉ được complete sau commit.

```csharp
private async Task ProcessMessageAsync(ProcessMessageEventArgs args)
{
    var ct = args.CancellationToken;
    OrderSubmitted message;

    try
    {
        message = args.Message.Body
            .ToObjectFromJson<OrderSubmitted>()
            ?? throw new InvalidDataException("Empty OrderSubmitted payload.");

        Validate(message);
    }
    catch (Exception ex) when (ex is JsonException or InvalidDataException)
    {
        await args.DeadLetterMessageAsync(
            args.Message,
            deadLetterReason: "InvalidOrderSubmitted",
            deadLetterErrorDescription: ex.Message,
            cancellationToken: ct);
        return;
    }

    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var alreadyProcessed = await db.ProcessedMessages
        .AnyAsync(x => x.MessageId == args.Message.MessageId, ct);

    if (!alreadyProcessed)
    {
        var affected = await db.CustomerCredits
            .Where(x =>
                x.CustomerId == message.CustomerId &&
                x.Available >= message.Total)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(
                    x => x.Available,
                    x => x.Available - message.Total),
                ct);

        if (affected != 1)
            throw new InsufficientCreditException(message.CustomerId);

        db.Orders.Add(new Order
        {
            Id = message.OrderId,
            CustomerId = message.CustomerId,
            Total = message.Total,
            CreatedAtUtc = DateTime.UtcNow
        });

        db.AuditEvents.Add(new AuditEvent
        {
            OrderId = message.OrderId,
            Type = "OrderCreated",
            CreatedAtUtc = DateTime.UtcNow
        });

        db.OutboxMessages.Add(OutboxMessage.Create(
            "OrderConfirmationRequested",
            new
            {
                message.OrderId,
                message.CustomerId
            }));

        db.ProcessedMessages.Add(new ProcessedMessage
        {
            MessageId = args.Message.MessageId,
            ProcessedAtUtc = DateTime.UtcNow
        });

        await db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }

    await args.CompleteMessageAsync(
        args.Message,
        cancellationToken: ct);
}
```

`ProcessedMessages.MessageId` phải có unique constraint/index để hai concurrent deliveries của cùng key không thể cùng commit. Đoạn `AnyAsync` giúp short-circuit phổ biến nhưng **unique constraint mới là final concurrency guard**. Khi unique violation xảy ra do race, handler cần phân loại đúng duplicate thay vì biến nó thành permanent business failure.

Outbox publisher đọc các rows chưa publish, gọi notification API với stable idempotency key (ví dụ `OrderId + event type`), rồi đánh dấu sent. Nếu publish retry, cùng key không được tạo thêm email khi downstream hỗ trợ idempotency; nếu downstream không hỗ trợ, cần chấp nhận/giảm thiểu duplicate theo contract thay vì tuyên bố exactly-once end-to-end.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đặt correctness vào một local SQL transaction mà hệ thống thực sự kiểm soát. Broker settlement xảy ra sau commit. Nếu crash trước commit, message được redeliver và xử lý lại. Nếu crash sau commit nhưng trước/đang complete, message có thể redeliver nhưng Inbox marker làm business mutation trở thành no-op.

External notification không nằm trong transaction. Outbox biến “SQL commit + HTTP call” thành “SQL commit order + durable intent”, sau đó publisher xử lý intent độc lập. Đây là at-least-once delivery với idempotent effects, không phải distributed exactly-once guarantee.

Credit invariant được đưa xuống conditional database mutation để multiple consumers không cùng dựa vào một stale read. Với workload có contention cao hoặc rules phức tạp hơn, cần benchmark isolation/locking/optimistic-concurrency strategy thay vì mặc định một kỹ thuật.

## Trade-offs

- Inbox/Outbox thêm tables, cleanup/retention và một publisher process, nhưng đổi lại failure windows trở nên reasoning được.
- Unique idempotency keys cần chọn theo business semantics; giữ marker mãi mãi có storage cost, còn xóa quá sớm có thể cho duplicate cũ chạy lại.
- High consumer concurrency tăng throughput tới một điểm, sau đó có thể tăng DB contention và lock expiry.
- Dead-letter permanent invalid messages bảo vệ throughput nhưng cần operational workflow để inspect/replay an toàn.
- Không có giải pháp đơn giản đảm bảo exactly-once xuyên Service Bus + SQL + external HTTP; mục tiêu thực tế là durable processing + idempotent effects.

## Cách kiểm thử

1. **Duplicate/concurrency integration test:** gửi cùng `MessageId` đồng thời qua nhiều handlers; xác minh chỉ một order, một credit decrement, một inbox marker và một outbox intent được commit.
2. **Crash/failure-window test:** fault ngay trước SQL commit, ngay sau commit và trước settlement; xác minh redelivery không làm mất hoặc duplicate business state.
3. **SQL transient failure test:** inject timeout/deadlock/network failure; kiểm tra retry classification, queue redelivery và không complete trước durable commit.
4. **Notification failure test:** outbox publisher gặp timeout/5xx/ambiguous response; xác minh retry dùng stable idempotency key và order transaction không bị rollback vì notification outage.
5. **Load test:** tăng `MaxConcurrentCalls`/replicas từng bước, đo queue age, handler p95, SQL waits/connection usage, lock-lost rate và throughput để tìm capacity knee.

## Quan sát trong production

Theo dõi:

- incoming message rate, active handlers và processing p50/p95/p99;
- queue depth và oldest-message age;
- delivery count/retry count, lock-lost và settlement failures;
- inbox duplicate-hit rate và unique-conflict count;
- SQL transaction latency, deadlocks, connection-pool pressure và conditional-credit conflicts;
- DLQ count theo reason;
- outbox pending count/oldest age/publish retry rate;
- notification dependency success/timeout/ambiguous failures;
- distributed trace/correlation qua `MessageId`, `OrderId` và outbox event ID, tránh log payload nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc giữ thứ tự tất cả orders của cùng customer, bạn sẽ thay đổi partition/session/consumer design thế nào?
2. Nếu `ProcessedMessages` có hàng tỷ rows sau vài năm, bạn thiết kế retention ra sao mà không làm mất idempotency protection cần thiết?
3. Trong trường hợp downstream notification không hỗ trợ idempotency, bạn có thể đảm bảo điều gì và không thể đảm bảo điều gì?

# Code Review Challenge 2 — Vue search box thỉnh thoảng hiển thị kết quả của query cũ và tạo XSS qua highlighted HTML

**Chủ đề:** Vue 3, TypeScript, browser async behavior, request races, cancellation, debouncing, stale state, XSS, API integration, frontend observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một Vue 3 product-search component gọi `GET /api/search?q=...` khi user gõ. Backend trả tối đa 20 kết quả, gồm tên sản phẩm và một field HTML dùng để highlight phần text match.

Yêu cầu:

- user gõ nhanh vẫn chỉ thấy kết quả tương ứng query mới nhất;
- không tạo request storm không cần thiết;
- request cũ nên được bỏ/cancel khi không còn giá trị;
- loading/error state không được bị request cũ ghi đè;
- product name đến từ catalog import nên không được coi là trusted HTML;
- keyboard/network chậm phải vẫn cho UX ổn định;
- production cần biết search latency, error rate và stale-response suppression.

Support báo thỉnh thoảng user gõ `iphone`, nhưng UI sau đó lại hiển thị kết quả của `iph`. Security review cũng phát hiện một catalog item có tên chứa markup khiến browser render nội dung không mong muốn.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
  highlightedName: string
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

watch(query, async (value) => {
  if (value.length < 2) {
    results.value = []
    return
  }

  loading.value = true
  error.value = null

  try {
    const response = await fetch(`/api/search?q=${value}`)
    const data = await response.json() as SearchItem[]
    results.value = data
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <span v-if="loading">Searching...</span>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in results" :key="item.id">
        <a :href="`/products/${item.id}`" v-html="item.highlightedName"></a>
      </li>
    </ul>
  </section>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong async search flow.
2. Xác định performance, security, reliability và maintainability concerns.
3. Giải thích production impact khi user gõ nhanh hoặc network response về không đúng thứ tự.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà không thêm state-management framework nếu component chưa cần.
6. Giải thích testing cho race, cancellation, error, XSS và high typing rate.
7. Đề xuất production/browser telemetry để chứng minh search UI hoạt động đúng.

## Câu hỏi gợi mở

1. JavaScript/Vue có đảm bảo các `fetch` được resolve đúng thứ tự chúng được bắt đầu không?
2. Nếu request `iph` chậm hơn request `iphone`, callback nào được phép ghi `results` cuối cùng?
3. `fetch` có tự URL-encode query string khi ghép raw string như trên không?
4. `v-html` đối xử với `highlightedName` khác interpolation `{{ item.name }}` như thế nào?
5. Khi một request cũ chạy `finally`, nó có thể làm `loading=false` trong lúc request mới vẫn đang chạy không?

## Gợi ý

### Gợi ý 1

Primary correctness risk là **out-of-order async completion**: thứ tự response hoàn tất không được đảm bảo theo thứ tự user nhập query.

### Gợi ý 2

Hãy tách ba vấn đề: giới hạn tần suất request, cancel work đã obsolete, và bảo đảm chỉ generation/query mới nhất được phép commit state; sau đó review rendering boundary như một security boundary riêng.

## Kết quả code review tham khảo

### Critical — `v-html` render HTML không trusted và tạo XSS boundary nguy hiểm

**Vấn đề:**  
`highlightedName` được render bằng `v-html`. Scenario nói product name đến từ catalog import và không được coi là trusted HTML.

**Tại sao xảy ra:**  
`v-html` đưa chuỗi vào DOM như HTML thay vì text-escaping như normal interpolation. Nếu backend highlight logic không sanitize hoàn hảo mọi input, markup/script-capable payload có thể đi vào DOM.

**Ảnh hưởng production:**  
Stored/reflected XSS có thể chạy trong origin của application, truy cập dữ liệu/browser capabilities mà page được phép truy cập và thực hiện action dưới session của user.

**Cách sửa:**  
Ưu tiên API trả plain structured data và render bằng text interpolation. Nếu highlight cần thiết, frontend chia text thành trusted structure (matched/non-matched segments) rồi render nodes/components, không nhận arbitrary HTML. Chỉ dùng sanitizer đã được security-approved nếu HTML thực sự là requirement.

### High — Response race cho phép query cũ ghi đè query mới

**Vấn đề:**  
Mỗi thay đổi `query` tạo một async callback độc lập và mọi callback đều gán `results.value = data` khi hoàn tất.

**Tại sao xảy ra:**  
Network completion order không đảm bảo. Request cũ có thể về sau request mới.

**Ảnh hưởng production:**  
UI hiển thị kết quả không tương ứng text hiện tại; user có thể chọn nhầm product và khó tái hiện bug vì phụ thuộc latency timing.

**Cách sửa:**  
Abort request obsolete và/hoặc dùng generation/request sequence check để chỉ request mới nhất được commit state. Abort giúp tiết kiệm work; sequence check vẫn hữu ích vì cancellation không nên là correctness assumption duy nhất.

### High — Không debounce nên tạo request storm khi user gõ

**Vấn đề:**  
Mỗi keystroke sau hai ký tự gọi API ngay.

**Tại sao xảy ra:**  
Reactive watch chạy theo mọi state change mà không có temporal batching.

**Ảnh hưởng production:**  
Một user có thể tạo nhiều requests cho một search intent; ở traffic cao làm tăng backend QPS, Elasticsearch/DB load và rate-limit pressure.

**Cách sửa:**  
Debounce khoảng thời gian phù hợp UX và measured typing behavior. Không chọn delay quá lớn làm UI chậm; bắt đầu bằng giá trị hợp lý rồi đo.

### High — Request obsolete không được cancel

**Vấn đề:**  
Các fetch cũ tiếp tục chạy dù query đã thay đổi.

**Tại sao xảy ra:**  
Không có `AbortController` gắn với lifecycle của mỗi watch invocation.

**Ảnh hưởng production:**  
Lãng phí browser connection/backend compute và làm race window lớn hơn.

**Cách sửa:**  
Tạo `AbortController` cho mỗi request và abort trong cleanup của watcher. Phân biệt `AbortError` với lỗi thật để không hiển thị error cho expected cancellation.

### High — `loading` có race độc lập với `results`

**Vấn đề:**  
Request cũ có thể chạy `finally` sau khi request mới đã bắt đầu và đặt `loading=false`.

**Tại sao xảy ra:**  
Shared boolean được nhiều overlapping async operations mutate mà không có ownership/version guard.

**Ảnh hưởng production:**  
Spinner biến mất trong khi latest search vẫn pending; UX state không phản ánh actual request.

**Cách sửa:**  
Chỉ generation hiện tại được mutate `loading/error/results`, hoặc derive loading từ current request identity.

### Medium — Query string không được encode an toàn

**Vấn đề:**  
URL được ghép bằng raw `${value}`.

**Tại sao xảy ra:**  
Các ký tự như `&`, `#`, `?`, Unicode/special syntax có thể thay đổi query parsing hoặc tạo request khác ý định.

**Ảnh hưởng production:**  
Search term bị cắt/sai, tạo bug khó hiểu và làm boundary giữa frontend/backend mơ hồ.

**Cách sửa:**  
Dùng `URLSearchParams` hoặc `encodeURIComponent` phù hợp thay vì string concatenation thủ công.

### Medium — Không kiểm tra HTTP status trước `response.json()`

**Vấn đề:**  
`fetch` không tự throw chỉ vì server trả 4xx/5xx; code vẫn parse body như success payload.

**Tại sao xảy ra:**  
Network rejection và HTTP error là hai lớp failure khác nhau.

**Ảnh hưởng production:**  
Error response có thể gây parse exception hoặc bị hiểu sai thành result; telemetry/UX không phân biệt backend error với invalid JSON.

**Cách sửa:**  
Kiểm tra `response.ok`, map status theo contract và chỉ parse success schema khi đúng.

### Medium — Error message đưa raw exception ra UI

**Vấn đề:**  
`String(e)` được render trực tiếp cho user.

**Tại sao xảy ra:**  
Technical diagnostic bị dùng làm UX contract.

**Ảnh hưởng production:**  
User thấy message khó hiểu và có thể lộ implementation details tùy exception/browser.

**Cách sửa:**  
Hiển thị user-safe message; gửi structured diagnostic vào telemetry với privacy controls.

### Medium — Query ngắn reset result nhưng không reset/cancel in-flight request cũ

**Vấn đề:**  
Khi user xóa về `< 2` ký tự, code set `results=[]` rồi return, nhưng request trước đó vẫn có thể hoàn tất và repopulate results.

**Tại sao xảy ra:**  
Không có cleanup/version invalidation khi search intent bị hủy.

**Ảnh hưởng production:**  
Ô search gần trống nhưng UI bất ngờ hiện kết quả cũ.

**Cách sửa:**  
Mỗi query transition phải invalidate generation hiện tại và abort in-flight request, kể cả khi không bắt đầu request mới.

### Low — Thiếu client-side observability cho stale-response/race behavior

**Vấn đề:**  
Không có signal cho search request count, aborted request, stale response suppressed hay latency theo query generation.

**Tại sao xảy ra:**  
Chỉ backend metrics không giải thích được browser-side ordering/abort behavior.

**Ảnh hưởng production:**  
Bug intermittent khó tái hiện và khó chứng minh fix đã giảm request amplification.

**Cách sửa:**  
Đo sanitized search timing/counts, aborted/stale-suppressed rate, HTTP failures và Web Vitals/user interaction timing khi cần; không log raw sensitive queries nếu policy không cho phép.

## Phiên bản đề xuất

Ví dụ dưới đây dùng debounce nhỏ, `AbortController`, generation guard và plain-text rendering. Không cần thêm Pinia/Redux-like state chỉ để giải quyết lifecycle cục bộ này.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface SearchItem {
  id: string
  name: string
}

const query = ref('')
const results = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref<string | null>(null)

let generation = 0

watch(query, (value, _oldValue, onCleanup) => {
  const currentGeneration = ++generation
  const controller = new AbortController()

  const timer = window.setTimeout(async () => {
    const normalized = value.trim()

    if (normalized.length < 2) {
      if (currentGeneration === generation) {
        results.value = []
        loading.value = false
        error.value = null
      }
      return
    }

    if (currentGeneration === generation) {
      loading.value = true
      error.value = null
    }

    try {
      const params = new URLSearchParams({ q: normalized })
      const response = await fetch(`/api/search?${params}`, {
        signal: controller.signal
      })

      if (!response.ok)
        throw new Error(`Search failed with HTTP ${response.status}`)

      const data = await response.json() as SearchItem[]

      if (currentGeneration === generation)
        results.value = data
    } catch (e) {
      if (controller.signal.aborted)
        return

      if (currentGeneration === generation)
        error.value = 'Search is temporarily unavailable.'
    } finally {
      if (currentGeneration === generation)
        loading.value = false
    }
  }, 250)

  onCleanup(() => {
    window.clearTimeout(timer)
    controller.abort()
  })
}, { immediate: true })
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search products" />

    <span v-if="loading">Searching...</span>
    <p v-if="error">{{ error }}</p>

    <ul>
      <li v-for="item in results" :key="item.id">
        <a :href="`/products/${encodeURIComponent(item.id)}`">
          {{ item.name }}
        </a>
      </li>
    </ul>
  </section>
</template>
```

Nếu product highlighting là requirement quan trọng, API có thể trả structured segments, ví dụ:

```ts
interface HighlightSegment {
  text: string
  matched: boolean
}
```

Template sau đó render từng segment bằng text nodes và chỉ áp CSS class cho `matched=true`. Như vậy HTML không trusted không đi qua `v-html`.

Trong code production có thể trích debounce/search lifecycle thành composable nếu nhiều screens cùng dùng, nhưng abstraction chỉ đáng thêm khi có reuse/testability thực tế.

## Giải thích thiết kế sau khi sửa

`generation` là correctness guard: chỉ search intent mới nhất được ghi state. `AbortController` là efficiency/lifecycle mechanism: request obsolete bị hủy sớm khi watcher cleanup chạy. Hai cơ chế bổ sung cho nhau; không nên coi abort là đảm bảo duy nhất rằng response cũ không bao giờ chạm code.

Debounce giảm request amplification, còn `URLSearchParams` giữ URL encoding đúng. HTTP errors được phân biệt với network errors. Rendering dùng interpolation nên Vue escape text thay vì coi catalog content là HTML.

Nếu backend search hỗ trợ cancellation propagation tới Elasticsearch/SQL, browser abort có thể giúp giảm downstream work; nhưng server phải tự propagate cancellation trong request pipeline thì lợi ích mới đi hết chuỗi.

## Trade-offs

- Debounce giảm QPS nhưng thêm một ít perceived latency; delay phải cân bằng bằng UX/load measurements.
- Abort request giảm waste nhưng không thay thế server-side rate limits/capacity controls.
- Generation guard thêm state nhỏ nhưng loại race rõ ràng và test được.
- Structured highlight segments tăng payload/model complexity so với HTML string nhưng tạo security boundary tốt hơn.
- Không dùng global state giữ component đơn giản; nếu nhiều views cần cache/share search state thì composable/store có thể trở nên hợp lý sau.

## Cách kiểm thử

1. **Race test:** mock `iph` response chậm hơn `iphone`; xác minh cuối cùng chỉ `iphone` được render và stale response không đổi `results/loading/error`.
2. **Cancellation/debounce test:** simulate gõ nhanh 10 ký tự; xác minh số request thực tế được giới hạn, timer/request cũ bị cleanup và expected abort không hiện error.
3. **Security test:** backend trả product name chứa `<img onerror=...>`/markup; xác minh UI render thành text và không tạo executable DOM.
4. **HTTP failure test:** trả 429/500/malformed JSON/network failure; xác minh user-safe error state, latest-generation ownership và recovery ở search tiếp theo.
5. **Browser/E2E performance test:** chạy trên throttled network/CPU, đo request count, interaction latency và kết quả luôn khớp query hiện tại.

## Quan sát trong production

Theo dõi:

- search requests per user interaction/session ở dạng aggregate phù hợp privacy;
- client-observed p50/p95 search latency;
- aborted request count và stale-response-suppressed count;
- HTTP 4xx/5xx/network error rate;
- backend search QPS và dependency latency trước/sau debounce;
- frontend error telemetry với release/version correlation;
- CSP violation reports nếu application dùng Content Security Policy;
- tuyệt đối tránh log raw query nếu nó có thể chứa dữ liệu nhạy cảm ngoài nhu cầu vận hành.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Message broker settlement phải được đặt sau durable business commit; duplicate delivery phải được xem là normal behavior và xử lý bằng idempotency.
- Inbox/Outbox giúp đóng các failure window giữa broker, database và external side effects mà không cần distributed transaction.
- Business invariant dưới concurrent consumers cần được enforce ở durable transaction/database boundary, không chỉ bằng read-then-write trong memory.
- Browser async requests có thể hoàn tất out of order; cancel giúp tiết kiệm work nhưng generation/version guard mới bảo vệ state correctness rõ ràng.
- Rendering boundary là security boundary: dữ liệu catalog/API không tự nhiên trở thành trusted HTML.

## Mẫu tư duy cần nhớ

- Vẽ các failure windows trước và sau mỗi durable side effect.
- Thiết kế retry cùng với idempotency, không thêm retry vào operation chưa retry-safe.
- Đưa invariant xuống nơi có thể enforce atomically.
- Phân biệt cancellation để tiết kiệm work với correctness guard để ngăn stale state.
- Treat external data and generated markup as untrusted until proven otherwise.
