# Câu 1 — DI Singleton và tenant isolation

**Loại câu hỏi:** Internal mechanism  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–18 phút  
**Kỹ năng được đánh giá:** ASP.NET Core DI, concurrency, security, Redis

## Bối cảnh

API .NET 8 đa tenant xử lý báo cáo. Sau khi đổi ReportService thành Singleton, một số request đồng thời nhận báo cáo của tenant khác. Có Redis cache và JWT authentication; chưa biết lifetime của ITenantContext hay cache key.

## Câu hỏi chính

Giải thích những cơ chế runtime có thể gây rò dữ liệu, chứng minh nguyên nhân và thiết kế giải pháp bảo vệ tenant isolation.

## Câu hỏi làm rõ nên cân nhắc

1. ITenantContext có lifetime gì?
2. Singleton có giữ mutable field hoặc Scoped dependency không?
3. Cache key gồm những dimension nào?
4. Tenant ID đến từ JWT validated hay header client?

## Gợi ý tư duy

### Gợi ý 1

Kiểm tra object graph và lifetime.

### Gợi ý 2

Phân biệt captive dependency, race condition và cache collision.

### Gợi ý 3

Dùng scope validation, parallel requests và kiểm tra tenant predicate.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement và giả định còn thiếu.
2. Đánh giá impact và rủi ro.
3. Giải thích cơ chế, dependency và các giả thuyết.
4. Chọn bằng chứng để xác minh.
5. So sánh phương án và trade-offs.
6. Đề xuất triển khai, failure recovery, testing và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

Singleton được chia sẻ; không mặc định sai. Captive Scoped dependency, mutable state, cache key thiếu tenant và query thiếu tenant filter là các giả thuyết độc lập.

### Điểm cộng

Scope validation, AsyncLocal/IHttpContextAccessor limitations, cross-tenant security tests.

### Senior+

Defense in depth: authorization tại resource/query, cache namespace, audit exposure.

## Hướng giải quyết tham khảo

Trước hết rollback/tắt cache hoặc endpoint để cô lập nguy cơ lộ dữ liệu, giữ audit bằng correlation ID không chứa PII. Kiểm tra DI registrations, constructors, fields và middleware: Singleton capture scoped context có thể bị scope validation phát hiện; nếu validation không bật, context có thể sống sai scope. Mutable _tenantId trên Singleton có thể bị request khác ghi đè. Cache key report:{id} có thể collision dù service thread-safe. Query không lọc tenant có thể rò ngay cả khi không cache. Bật ValidateScopes và ValidateOnBuild trong test; so sánh hai tenant có report ID trùng nhau qua concurrency tests, kiểm tra SQL và key fingerprints. Sửa bằng Scoped orchestration hoặc stateless Singleton, tenant ID immutable lấy từ validated identity, enforce authorization/query predicate và cache key gồm tenant, report, params, role/user nếu output phụ thuộc quyền. BackgroundService không giả định có HttpContext. Kiểm thử cache hit/miss, 500 parallel requests, unauthorized IDs, Redis outage; đo cache hit theo namespace, denied access và trace. Nếu object thực sự stateless, Singleton vẫn hợp lệ.

## Mẫu trả lời trong phỏng vấn

Tôi xem đây là security incident nên cô lập endpoint hoặc rollback trước. Singleton không tự gây lỗi; tôi sẽ kiểm tra captured scoped dependency, mutable state, cache key và tenant predicate trong query. Tôi bật scope validation, chạy hai tenant song song với cùng report ID và đối chiếu traces để phân biệt nguyên nhân. Giải pháp là request-scoped service hoặc Singleton stateless, tenant ID từ validated claims, authorization ở data layer và cache namespace đúng. Tôi sẽ thêm negative security tests và theo dõi denied access, cache hit và cross-tenant anomalies.

## Câu hỏi đào sâu

1. AsyncLocal có bảo đảm mọi BackgroundService đều có tenant context không?
2. Nếu đổi sang Scoped mà leak vẫn xảy ra thì kiểm tra gì?
3. Khi nào Singleton stateless là lựa chọn tốt hơn?

## Lỗi trả lời thường gặp

- Kết luận Singleton luôn sai.
- Chỉ đổi lifetime mà bỏ qua SQL filter.
- Tin tenant header không xác thực.
- Dùng global lock để che cache collision.

# Câu 2 — Upload Blob 500 MB và partial failure

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–18 phút  
**Kỹ năng được đánh giá:** Azure App Service, Blob Storage, ASP.NET Core, Application Insights

## Bối cảnh

React upload file qua ASP.NET Core API trên App Service Linux tới private Azure Blob Storage. Khi tăng giới hạn lên 500 MB, 9% upload thất bại giờ cao điểm; có 413, 502/504, memory spikes và duplicate metadata sau retry. CPU thấp; chưa rõ request limit, streaming, timeout và retry implementation.

## Câu hỏi chính

Là incident owner, hãy điều tra, ổn định hệ thống, xác minh root cause và triển khai remediation có rollback.

## Câu hỏi làm rõ nên cân nhắc

1. 413 phát sinh ở proxy hay application?
2. IFormFile có bị copy toàn bộ vào MemoryStream không?
3. Lỗi có tương quan file size, concurrency, duration?
4. Metadata commit trước hay sau Blob upload?
5. Có malware scanning, retention, quota và idempotency key không?

## Gợi ý tư duy

### Gợi ý 1

Phân loại error theo tầng trước khi sửa.

### Gợi ý 2

Đo buffering, GC, timeout và Blob dependency telemetry.

### Gợi ý 3

Thiết kế upload session và reconciliation để chịu retry.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement và giả định còn thiếu.
2. Đánh giá impact và rủi ro.
3. Giải thích cơ chế, dependency và các giả thuyết.
4. Chọn bằng chứng để xác minh.
5. So sánh phương án và trade-offs.
6. Đề xuất triển khai, failure recovery, testing và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

Tách 413 khỏi 502/504; stabilize trước; đưa competing hypotheses và evidence; ngăn duplicate bằng idempotency.

### Điểm cộng

Direct-to-Blob scoped SAS, streaming, security validation, orphan cleanup.

### Senior+

Resumable upload state machine, scanning, canary gates và consistency recovery.

## Hướng giải quyết tham khảo

Xác định impact, tỷ lệ lỗi theo kích thước và duplicate/orphan count; tạm giảm file cap hoặc concurrency và rollback nếu cần. Dùng browser network, proxy/App Service request logs, Application Insights dependency traces, Blob metrics, GC/memory, request duration và restart logs. 413 có thể do body limit; 502/504 có thể do timeout/network; memory spike có thể do buffering; Blob throttling có thể tăng duration. Không kết luận root cause khi chưa tái hiện từng nhóm. Ngắn hạn dùng bounded streaming, limit phù hợp và backpressure; không tăng timeout vô hạn. Tạo UploadSession với unique (tenant, clientRequestId), trạng thái Pending→Uploaded→Validated→Available hoặc Failed; unique database constraint và reconciliation để retry/finalize không tạo duplicate. Với upload lớn, cân nhắc browser direct-to-Blob qua short-lived path-scoped SAS; private container, quota, content validation, checksum, scanning trước publish; nếu policy cấm SAS thì giữ backend streaming. Test slow network, disconnect, retry, Blob outage, invalid file và concurrency. Canary theo p95, memory, error buckets, orphan backlog, duplicate count; alert Azure Monitor. Chi phí direct upload là lifecycle/CORS/security complexity.

## Mẫu trả lời trong phỏng vấn

Tôi sẽ giảm impact trước và phân biệt 413 với 502/504 vì không nhất thiết cùng nguyên nhân. Tôi lấy trace từ browser, API, proxy và Blob, so sánh theo size, concurrency, duration và GC. Tôi nghi ngờ request limit, buffering, timeout hoặc Blob throttling nhưng chỉ kết luận khi có bằng chứng. Duplicate metadata phải được xử lý bằng upload session, idempotency key và unique constraint. Nếu policy cho phép, direct-to-Blob upload giảm tải API nhưng cần SAS scope, validation và reconciliation. Tôi rollout canary với failure injection và theo dõi error rate, memory, latency và orphan files.

## Câu hỏi đào sâu

1. Làm sao xác định 413 xảy ra trước middleware?
2. Nếu không thể cấp SAS cho browser thì giải pháp nào?
3. Nếu Blob upload thành công nhưng finalize timeout thì retry thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng timeout.
- Buffer toàn bộ 500 MB vào RAM.
- Cho rằng retry POST an toàn.
- Không đối soát orphan và duplicate.
- Chỉ theo dõi CPU.

# Câu 3 — Modernization .NET Framework/IIS sang modern .NET

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 18–22 phút  
**Kỹ năng được đánh giá:** IIS, .NET modernization, SQL Server, TeamCity, Octopus Deploy

## Bối cảnh

ASP.NET MVC .NET Framework 4.5 trên IIS/Windows Server với SQL Server, Windows Authentication, COM, System.Web, local file storage và ERP integration. Product yêu cầu modern .NET trong 9 tháng, downtime release dưới 5 phút, giữ URL/SSO. TeamCity/Octopus đang deploy; automated tests yếu. Đề xuất đối nghịch: rewrite microservices Kubernetes hoặc nâng cấp in-place.

## Câu hỏi chính

Chọn chiến lược modernization, hosting, database migration và release/rollback dựa trên bằng chứng và trade-offs, không mặc định rewrite.

## Câu hỏi làm rõ nên cân nhắc

1. COM và Windows Authentication có thể thay thế không?
2. Module nào có transaction coupling cao nhất?
3. ERP/network/licensing ràng buộc OS nào?
4. Có thể dùng expand-contract database schema không?
5. Budget, SLA và khả năng vận hành Kubernetes ra sao?

## Gợi ý tư duy

### Gợi ý 1

Inventory dependency trước khi chọn hosting.

### Gợi ý 2

Pilot một vertical slice với contract tests.

### Gợi ý 3

Phân biệt app rollback và database rollback.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement và giả định còn thiếu.
2. Đánh giá impact và rủi ro.
3. Giải thích cơ chế, dependency và các giả thuyết.
4. Chọn bằng chứng để xác minh.
5. So sánh phương án và trade-offs.
6. Đề xuất triển khai, failure recovery, testing và observability.

## Ý chính của câu trả lời tốt

### Bắt buộc

Không đồng nhất framework migration với microservices; đánh giá COM/System.Web compatibility và chiến lược incremental rollout.

### Điểm cộng

Strangler facade, characterization tests, expand-contract, immutable artifact.

### Senior+

Data ownership, dual-write risk, TCO, exit gates, 9-month scope decisions.

## Hướng giải quyết tham khảo

Đo baseline latency, deployment failure, cost, user journeys và inventory COM/System.Web/Windows Auth/ERP dependencies. Viết characterization, contract, Playwright E2E tests cho login, order, ERP và URL. So sánh incremental migration, strangler routing và full rewrite; microservices/Kubernetes chỉ hợp lý nếu cần independent scaling/deployment và có vận hành đủ mạnh. Pilot vertical slice trên modern .NET; chọn App Service Windows/Linux theo compatibility thực tế, giữ Windows adapter cho COM nếu chưa thay được. Dùng reverse proxy route một số endpoint, bảo đảm cookie/SSO interoperability được test chứ không giả định. Giữ SQL schema chung tạm thời nếu transaction coupling lớn; expand-contract với backward-compatible columns, backfill, dual-read có kiểm soát, tránh destructive migrations trước rollback window. Nếu tách ownership cần outbox/reconciliation, không dual-write ngây thơ. TeamCity build immutable artifact, Octopus promote cùng artifact với environment config, approvals, health checks, canary và rollback rehearsal. Theo dõi ERP error, order duplication, auth failure, p95 và change failure. Chốt scope 9 tháng sau pilot; nếu COM hoặc coupling khiến full migration không khả thi thì giữ hybrid và ưu tiên business-critical slices. Trade-off strangler là routing, session và operational complexity; in-place có thể ít complexity nhưng bị dependency block; rewrite rủi ro lớn.

## Mẫu trả lời trong phỏng vấn

Tôi không chọn Kubernetes hay rewrite trước khi hiểu dependency. Tôi inventory System.Web, COM, Windows Authentication và transaction boundaries, sau đó xây characterization tests cho luồng nghiệp vụ quan trọng. Tôi nghiêng về pilot incremental hoặc strangler migration nếu boundary đủ rõ, giữ legacy hoạt động và chuyển từng vertical slice. Hosting Windows hay Linux phụ thuộc compatibility; App Service có thể đủ. Database dùng expand-contract để app rollback vẫn chạy, tránh schema destructive. Tôi giữ TeamCity/Octopus nếu pipeline đáp ứng immutable artifact và release gates. Sau pilot tôi đo effort, downtime, failure rate và cost rồi mới cam kết phạm vi 9 tháng.

## Câu hỏi đào sâu

1. Nếu hai ứng dụng cùng ghi Orders thì transaction ownership ra sao?
2. Nếu COM không thể port thì business case thay đổi thế nào?
3. Điều kiện nào khiến Kubernetes đáng giá hơn App Service?

## Lỗi trả lời thường gặp

- Mặc định rewrite microservices.
- Giả định COM chạy trên Linux.
- Migrate schema destructive trước app.
- Không test SSO/ERP/URL.
- Ước lượng trước pilot.
