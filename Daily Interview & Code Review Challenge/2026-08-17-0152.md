# Code Review Challenge 1 — Cache stampede, dữ liệu stale và race condition dưới tải

**Chủ đề:** Caching, concurrency, performance, async/await  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 15–20 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API trả về cấu hình quyền truy cập của user. Dữ liệu gốc nằm trong SQL Server, còn Redis được dùng để giảm tải database. Endpoint được gọi rất thường xuyên, khoảng 300–800 request/giây vào giờ cao điểm.

Sau khi deploy phiên bản mới, team thấy:

- Redis miss tăng mạnh theo từng đợt.
- SQL CPU đôi lúc tăng đột biến dù traffic không tăng tương ứng.
- P95/P99 latency xuất hiện spike mỗi vài phút.
- Một số user vừa bị thay đổi quyền nhưng vẫn nhận quyền cũ trong một khoảng thời gian.
- Khi Redis chậm hoặc timeout, API latency tăng dây chuyền.

Đây là code hiện tại:

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private readonly IDatabase _redis;
    private readonly AppDbContext _dbContext;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        IConnectionMultiplexer redis,
        AppDbContext dbContext,
        ILogger<PermissionService> logger)
    {
        _redis = redis.GetDatabase();
        _dbContext = dbContext;
        _logger = logger;
    }

    public async Task<List<string>> GetPermissionsAsync(
        Guid tenantId,
        Guid userId,
        CancellationToken cancellationToken)
    {
        var key = $"permissions:{tenantId}:{userId}";

        var cached = await _redis.StringGetAsync(key);
        if (cached.HasValue)
        {
            return JsonSerializer.Deserialize<List<string>>(cached!)!;
        }

        var permissions = await _dbContext.UserRoles
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .SelectMany(x => x.Role.Permissions)
            .Select(x => x.Code)
            .Distinct()
            .ToListAsync(cancellationToken);

        await _redis.StringSetAsync(
            key,
            JsonSerializer.Serialize(permissions),
            TimeSpan.FromMinutes(10));

        _logger.LogInformation(
            "Loaded permissions for {TenantId}/{UserId}: {Permissions}",
            tenantId,
            userId,
            permissions);

        return permissions;
    }

    public async Task UpdateRoleAsync(
        Guid tenantId,
        Guid userId,
        Guid roleId,
        CancellationToken cancellationToken)
    {
        var assignment = await _dbContext.UserRoles
            .SingleAsync(
                x => x.TenantId == tenantId && x.UserId == userId,
                cancellationToken);

        assignment.RoleId = roleId;
        await _dbContext.SaveChangesAsync(cancellationToken);

        await _redis.KeyDeleteAsync($"permissions:{tenantId}:{userId}");
    }
}
```

## Câu hỏi gợi mở

## Kết quả code review tham khảo

### 1. Cache stampede khi key hết hạn hoặc bị xóa

- **Problem:** Mọi request cache miss đều cùng truy vấn SQL.
- **Why it happens:** Không có request coalescing, single-flight, lock theo key hoặc cơ chế stale-while-revalidate.
- **Production impact:** SQL CPU spike, connection pool pressure, P95/P99 tăng mạnh theo chu kỳ TTL hoặc invalidation.
- **Severity:** High
- **Recommended fix:** Dùng distributed lock/single-flight theo key nếu thực sự cần, hoặc cache library hỗ trợ request coalescing; thêm TTL jitter để nhiều key không expire cùng lúc.

### 2. Race condition có thể ghi lại dữ liệu permission cũ sau invalidation

- **Problem:** `GetPermissionsAsync` có thể đọc DB trước update, sau đó `UpdateRoleAsync` commit + xóa cache, rồi request cũ mới ghi stale value trở lại Redis.
- **Why it happens:** Cache population và data mutation không có version/checkpoint liên kết.
- **Production impact:** User bị giữ quyền cũ dù cache vừa được invalidated; với authorization đây có thể là security issue.
- **Severity:** Critical
- **Recommended fix:** Dùng permission version/security stamp hoặc generation number. Cache entry gắn version; update bump version atomically ở database. Hoặc dùng write-through/versioned key để stale writer không thể overwrite generation mới.

### 3. Invalidation sau database commit không có guarantee

- **Problem:** DB commit có thể thành công nhưng Redis delete thất bại.
- **Why it happens:** Hai hệ thống khác nhau, không có transaction phân tán.
- **Production impact:** Cache giữ permission cũ đến hết TTL.
- **Severity:** High
- **Recommended fix:** Với dữ liệu authorization quan trọng, dùng version validation hoặc durable invalidation event/outbox; không dựa hoàn toàn vào best-effort delete.

### 4. TTL cố định có thể tạo synchronized expiration

- **Problem:** Nhiều key có thể expire cùng thời điểm nếu được tạo theo batch hoặc theo traffic pattern giống nhau.
- **Why it happens:** TTL luôn đúng 10 phút.
- **Production impact:** Cache miss burst và DB spike theo chu kỳ.
- **Severity:** Medium
- **Recommended fix:** Thêm TTL jitter, ví dụ base TTL ± random window phù hợp.

### 5. Không có policy rõ ràng khi Redis chậm hoặc timeout

- **Problem:** Request chờ Redis rồi mới fallback logic tiếp theo; code không định nghĩa timeout/bulkhead/failure behavior ở service level.
- **Why it happens:** Cache được coi như dependency luôn sẵn sàng.
- **Production impact:** Redis degradation lan thành API degradation.
- **Severity:** High
- **Recommended fix:** Cấu hình timeout hợp lý, theo dõi dependency latency; xác định rõ khi nào bypass cache, fail closed hoặc fail open. Với authorization, fail-open có thể không chấp nhận được.

### 6. Logging toàn bộ permission list có thể gây noise và lộ thông tin nhạy cảm

- **Problem:** Mỗi miss log toàn bộ permissions ở mức Information.
- **Why it happens:** Log được dùng như debug state.
- **Production impact:** Log volume lớn, chi phí tăng, có thể expose security-related authorization data.
- **Severity:** Medium
- **Recommended fix:** Log count/version/cache source; chỉ log chi tiết ở mức debug có kiểm soát nếu cần.

### 7. Query đọc thuần túy không dùng no-tracking

- **Problem:** EF Core có thể tracking entity trong query path đọc-only nếu entity materialization xảy ra.
- **Why it happens:** Không định nghĩa read-only intent rõ ràng.
- **Production impact:** Có thể tăng overhead; mức ảnh hưởng phụ thuộc query translation/materialization thực tế.
- **Severity:** Low
- **Recommended fix:** Dùng `AsNoTracking()` khi phù hợp và kiểm tra generated SQL thay vì giả định.

### 8. Không có negative-cache policy

- **Problem:** User không có permission cũng được cache như list rỗng, nhưng business semantics của “không có dữ liệu” chưa được phân biệt với query/database lỗi.
- **Why it happens:** Mọi empty result được coi giống nhau.
- **Production impact:** Khó phân biệt legitimate empty permissions với degraded state nếu error handling sau này bị mở rộng không đúng.
- **Severity:** Medium
- **Recommended fix:** Tách success-empty khỏi dependency failure; không cache failure result.

### 9. Lifetime risk nếu `PermissionService` bị đăng ký Singleton

- **Problem:** Service giữ `AppDbContext` scoped.
- **Why it happens:** Constructor không cho thấy lifetime registration.
- **Production impact:** Nếu đăng ký sai lifetime có thể gây captive dependency hoặc concurrent use của `DbContext`.
- **Severity:** High nếu registration sai, không phải bug chắc chắn từ snippet.
- **Recommended fix:** Đảm bảo service scoped/transient phù hợp; không dùng cùng `DbContext` concurrent.

## Phiên bản code đề xuất

Một cách đơn giản hơn là dùng **versioned cache key** để loại bỏ race stale-write:

```csharp
public sealed class PermissionService
{
    private readonly IDatabase _redis;
    private readonly AppDbContext _db;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        IConnectionMultiplexer redis,
        AppDbContext db,
        ILogger<PermissionService> logger)
    {
        _redis = redis.GetDatabase();
        _db = db;
        _logger = logger;
    }

    public async Task<IReadOnlyList<string>> GetPermissionsAsync(
        Guid tenantId,
        Guid userId,
        CancellationToken ct)
    {
        var version = await _db.Users
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Id == userId)
            .Select(x => x.PermissionVersion)
            .SingleAsync(ct);

        var key = $"permissions:{tenantId}:{userId}:v{version}";

        var cached = await _redis.StringGetAsync(key);
        if (cached.HasValue)
        {
            return JsonSerializer.Deserialize<string[]>(cached!) ?? [];
        }

        var permissions = await _db.UserRoles
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.UserId == userId)
            .SelectMany(x => x.Role.Permissions)
            .Select(x => x.Code)
            .Distinct()
            .ToListAsync(ct);

        var ttl = TimeSpan.FromMinutes(8 + Random.Shared.NextDouble() * 4);

        await _redis.StringSetAsync(
            key,
            JsonSerializer.Serialize(permissions),
            ttl);

        _logger.LogDebug(
            "Permission cache populated for {TenantId}/{UserId}, version {Version}, count {Count}",
            tenantId,
            userId,
            version,
            permissions.Count);

        return permissions;
    }

    public async Task UpdateRoleAsync(
        Guid tenantId,
        Guid userId,
        Guid roleId,
        CancellationToken ct)
    {
        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        var assignment = await _db.UserRoles
            .SingleAsync(
                x => x.TenantId == tenantId && x.UserId == userId,
                ct);

        var user = await _db.Users
            .SingleAsync(
                x => x.TenantId == tenantId && x.Id == userId,
                ct);

        assignment.RoleId = roleId;
        user.PermissionVersion++;

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
}
```

Điểm quan trọng là key cũ không cần phải xóa ngay để correctness được giữ: sau khi `PermissionVersion` tăng, request mới đọc generation mới. Cache cũ tự expire sau TTL.

Trong hệ thống cực tải, vẫn nên bổ sung single-flight/request coalescing để tránh nhiều request cùng populate generation mới.

## Trade-offs

- **Versioned key** tăng số cache keys tạm thời nhưng đổi lại tránh stale writer overwrite generation mới.
- Đọc version từ DB mỗi request có thể làm mất phần lớn lợi ích caching; thực tế có thể cache version riêng, embed version trong token/security stamp, hoặc dùng một authoritative lightweight lookup. Thiết kế phải dựa vào latency/security requirement.
- Distributed lock giảm stampede nhưng không tự giải quyết stale-write correctness.
- Với authorization nhạy cảm, correctness và revocation latency quan trọng hơn hit ratio tối đa.

## Cách kiểm thử

1. **Concurrency test:** 500 concurrent requests cùng miss một key; đo số query SQL thực tế.
2. **Race test:** request A đọc quyền cũ, admin update quyền, rồi A cố ghi cache sau commit; verify generation cũ không ảnh hưởng request mới.
3. **Redis failure test:** inject timeout và kiểm tra API fail/fallback đúng policy, không tạo cascading latency.
4. **Load test:** chạy qua nhiều chu kỳ TTL và xác minh không còn spike đồng bộ.
5. **Security test:** revoke một permission nhạy cảm và đo maximum stale window thực tế.

## Quan sát trong production

Nên có:

- Cache hit/miss ratio theo key category.
- Cache populate count và duplicate-population count.
- Redis latency/error/timeout rate.
- SQL query count do permission lookup.
- Permission version mismatch/stale suppression count.
- P50/P95/P99 của permission resolution.
- Alert khi DB lookup tăng đột biến đồng thời với cache miss burst.

2. Nếu permission phải revoke gần như ngay lập tức nhưng access token sống 60 phút, cache fix có đủ không?
3. Nếu muốn tránh đọc `PermissionVersion` từ DB mỗi request, bạn sẽ đặt version ở đâu và đánh đổi gì?

# Code Review Challenge 2 — Logging middleware làm rò rỉ token và biến lỗi nhỏ thành outage

**Chủ đề:** Error handling, logging, sensitive-data exposure, performance, resource lifetime  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 15–20 phút

## Bối cảnh

Một team thêm middleware để debug lỗi production. Mục tiêu là log request/response body cho mọi API call để “dễ điều tra hơn”.

Sau deploy:

- Log ingestion tăng gấp nhiều lần.
- Một số request upload lớn chậm rõ rệt.
- Security team phát hiện bearer token và dữ liệu cá nhân xuất hiện trong logs.
- Một số client nhận response body rỗng khi API lỗi.
- Memory tăng cao khi traffic có request payload lớn.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class RequestResponseLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestResponseLoggingMiddleware> _logger;

    public RequestResponseLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestResponseLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var requestReader = new StreamReader(context.Request.Body);
        var requestBody = await requestReader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        var originalBody = context.Response.Body;
        using var responseBody = new MemoryStream();
        context.Response.Body = responseBody;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Request failed. Headers={Headers}, Body={Body}",
                context.Request.Headers,
                requestBody);

            context.Response.StatusCode = 500;
            await context.Response.WriteAsync(ex.ToString());
        }

        responseBody.Position = 0;
        var responseText = await new StreamReader(responseBody).ReadToEndAsync();

        _logger.LogInformation(
            "HTTP {Method} {Path} Headers={Headers} Request={RequestBody} Response={ResponseBody}",
            context.Request.Method,
            context.Request.Path,
            context.Request.Headers,
            requestBody,
            responseText);

        responseBody.Position = 0;
        await responseBody.CopyToAsync(originalBody);
    }
}
```

## Kết quả code review tham khảo

### 1. Log toàn bộ headers làm lộ secrets

- **Problem:** `Authorization`, cookies và custom security headers có thể bị ghi nguyên văn.
- **Why it happens:** Dump toàn bộ `Request.Headers`.
- **Production impact:** Token/session leak qua log platform; incident severity cao.
- **Severity:** Critical
- **Recommended fix:** Header allowlist hoặc explicit redaction; mặc định không log authorization/cookie/token headers.

### 2. Log toàn request body có thể expose PII/credentials/secrets

- **Problem:** Password, token, personal data hoặc business-sensitive fields có thể bị lưu lâu dài trong log.
- **Why it happens:** Không có schema-aware redaction hay route policy.
- **Production impact:** Security/privacy breach và compliance risk.
- **Severity:** Critical
- **Recommended fix:** Không log body mặc định. Nếu bắt buộc, chỉ với allowlisted endpoint/content type, giới hạn bytes, redaction, sampling và môi trường phù hợp.

### 3. Trả `ex.ToString()` cho client

- **Problem:** Client nhận stack trace, type names và internal implementation details.
- **Why it happens:** Middleware dùng exception text làm response.
- **Production impact:** Information disclosure; response contract không ổn định.
- **Severity:** High
- **Recommended fix:** Trả generic Problem Details/correlation ID; log exception server-side.

### 4. Buffer toàn request và response trong memory

- **Problem:** Mọi body đều được đọc vào string/MemoryStream.
- **Why it happens:** Middleware muốn log full payload.
- **Production impact:** Allocation lớn, LOH pressure, GC tăng, OOM risk dưới concurrency; streaming mất lợi ích.
- **Severity:** High
- **Recommended fix:** Không capture body mặc định; giới hạn size, skip upload/streaming/binary endpoints.

### 5. Exception handling sau khi response đã bắt đầu có thể không an toàn

- **Problem:** Nếu downstream đã commit headers/body rồi mới lỗi, middleware không thể luôn đổi thành clean 500 response.
- **Why it happens:** Exception handler giả định response chưa start.
- **Production impact:** Partial/corrupt response hoặc exception thứ cấp.
- **Severity:** High
- **Recommended fix:** Dùng centralized exception handling sớm trong pipeline; kiểm tra `HasStarted` và không cố rewrite response khi đã commit.

### 6. Logging ở mức Information cho mọi request với payload lớn

- **Problem:** Log volume rất cao.
- **Why it happens:** Mỗi request ghi headers + request + response.
- **Production impact:** I/O/log ingestion cost tăng, log pipeline bottleneck, signal-to-noise kém.
- **Severity:** Medium
- **Recommended fix:** Structured access logs ngắn; error logs chỉ khi cần; sampling cho high-volume endpoints.

### 7. CancellationToken của request không được propagate khi đọc/copy stream

- **Problem:** Một số async stream operations không dùng `context.RequestAborted`.
- **Why it happens:** Các overload không nhận cancellation token được dùng.
- **Production impact:** Client disconnect nhưng server vẫn tiếp tục copy/read dữ liệu lớn.
- **Severity:** Medium
- **Recommended fix:** Dùng overload hỗ trợ `RequestAborted` khi phù hợp.

### 8. Response capture phá semantics của streaming/file endpoints

- **Problem:** `context.Response.Body` bị thay bằng `MemoryStream`.
- **Why it happens:** Middleware muốn đọc response sau khi downstream chạy xong.
- **Production impact:** Tăng latency-to-first-byte và làm mất streaming behavior.
- **Severity:** High
- **Recommended fix:** Skip body capture cho streaming/file/SSE và các content type không phù hợp.

## Phiên bản code đề xuất

Thay vì dump payload, dùng middleware structured metadata và centralized exception handling:

```csharp
public sealed class RequestTelemetryMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTelemetryMiddleware> _logger;

    public RequestTelemetryMiddleware(
        RequestDelegate next,
        ILogger<RequestTelemetryMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        var traceId = Activity.Current?.TraceId.ToString()
                      ?? context.TraceIdentifier;

        try
        {
            await _next(context);
        }
        catch (OperationCanceledException)
            when (context.RequestAborted.IsCancellationRequested)
        {
            _logger.LogInformation(
                "Request aborted by client. TraceId={TraceId} Method={Method} Path={Path}",
                traceId,
                context.Request.Method,
                context.Request.Path);
            throw;
        }
        catch (Exception ex)
        {
            _logger.LogError(
                ex,
                "Unhandled request error. TraceId={TraceId} Method={Method} Path={Path}",
                traceId,
                context.Request.Method,
                context.Request.Path);
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);

            _logger.LogInformation(
                "HTTP {Method} {Path} => {StatusCode} in {ElapsedMs}ms TraceId={TraceId}",
                context.Request.Method,
                context.Request.Path,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                traceId);
        }
    }
}
```

Exception response nên do centralized exception handler xử lý, ví dụ trả `ProblemDetails` với trace/correlation ID nhưng không gửi stack trace cho client.

Nếu business thật sự cần payload debugging, nên có **separate diagnostic capture policy**:

- Chỉ bật theo feature flag hoặc temporary incident mode.
- Chỉ áp dụng route/content-type allowlist.
- Redact field nhạy cảm.
- Giới hạn số bytes.
- Sampling.
- Retention ngắn.
- Audit ai bật/tắt chức năng.

## Trade-offs

- Không log body làm giảm khả năng debug một số lỗi dữ liệu, nhưng đổi lại security/performance tốt hơn rất nhiều.
- Có thể dùng payload fingerprint/hash hoặc selected fields thay vì full body.
- Trong QA environment có thể logging chi tiết hơn production, nhưng vẫn không nên ghi secrets.
- Distributed tracing thường hữu ích hơn full payload cho latency/dependency investigation.

## Cách kiểm thử

1. **Security test:** gửi bearer token, cookie, password field và xác minh logs không chứa raw secret.
2. **Large payload test:** upload/return payload hàng chục MB; đo allocations, peak memory và latency.
3. **Streaming test:** endpoint stream file/SSE vẫn giữ behavior đúng, không bị buffer toàn bộ.
4. **Exception test:** downstream throw trước và sau khi response bắt đầu; verify không leak stack trace.
5. **Client abort test:** client disconnect giữa request; verify cancellation được nhận diện và không log error sai loại.

## Quan sát trong production

Nên theo dõi:

- Request duration P50/P95/P99.
- Status code distribution.
- Exception count theo exception type/route.
- Request aborted count.
- Log volume bytes/sec.
- Memory allocation/GC rate.
- Trace ID + dependency spans để correlation.
- Alert khi log ingestion hoặc allocation tăng bất thường sau deploy.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chấp nhận log một phần request body trong production?
2. Nếu cần điều tra một bug chỉ xảy ra với payload cụ thể, bạn thiết kế temporary diagnostic mode thế nào?
3. Vì sao distributed tracing thường hữu ích hơn việc log toàn bộ request/response để điều tra latency?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Cache-aside đơn giản có thể sai correctness dưới concurrency nếu không xử lý stale writer và invalidation race.
- Cache stampede thường chỉ lộ rõ khi traffic tăng hoặc key expire theo cụm.
- Authorization cache cần ưu tiên revocation correctness hơn hit ratio.
- Observability không đồng nghĩa dump toàn bộ dữ liệu; logs phải có data-minimization và redaction.
- Buffering request/response toàn phần có thể biến middleware debug thành memory/latency bottleneck.
- Centralized error handling cần bảo vệ response contract và tránh leak internal details.

## Mẫu tư duy cần nhớ

1. **Vẽ timeline khi review concurrency** — race condition thường rõ hơn khi mô tả thứ tự read/write/invalidate.
2. **Correctness trước hit ratio** — đặc biệt với authorization, payment và state nhạy cảm.
3. **Dependency failure phải có policy** — Redis, SQL hay external API chậm không được phép kéo toàn hệ thống xuống một cách vô thức.
4. **Observe metadata trước payload** — trace ID, duration, status và dependency spans thường đủ cho phần lớn diagnosis.
5. **Không log thứ bạn không muốn xuất hiện trong một security incident report.**
