# Câu 1 — Scoped DbContext bị giữ trong Singleton: vì sao code “chạy được” nhưng production lại race condition và lỗi tracking khó đoán?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core dependency injection, DI lifetimes, Entity Framework Core, DbContext, thread safety, change tracking, async/concurrency, application lifetime

## Bối cảnh

Một ASP.NET Core API trên .NET 8 có service tổng hợp dữ liệu dùng Entity Framework Core. Team đăng ký dependencies như sau:

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseSqlServer(connectionString));

builder.Services.AddSingleton<IEmployeeCacheBuilder, EmployeeCacheBuilder>();
```

Service singleton hiện nhận một repository qua constructor:

```csharp
public sealed class EmployeeCacheBuilder : IEmployeeCacheBuilder
{
    private readonly IEmployeeRepository _repository;

    public EmployeeCacheBuilder(IEmployeeRepository repository)
    {
        _repository = repository;
    }

    public async Task<EmployeeDto?> BuildAsync(
        Guid employeeId,
        CancellationToken cancellationToken)
    {
        return await _repository.GetByIdAsync(employeeId, cancellationToken);
    }
}
```

Repository dùng `AppDbContext` qua constructor injection.

Trong local test với traffic thấp, hệ thống có vẻ hoạt động. Trong production sau scale-out và tải đồng thời cao, xuất hiện lẻ tẻ:

- lỗi liên quan đến `DbContext` đang thực thi nhiều operation cùng lúc;
- entity state/tracking không như developer kỳ vọng;
- một số request thất bại nhưng retry lại thành công;
- restart instance làm lỗi biến mất tạm thời;
- một developer đề xuất thêm `lock` quanh mọi repository call;
- một developer khác muốn đăng ký `DbContext` thành Singleton để lifetime “khớp” với cache builder;
- service singleton cũng được gọi từ một `BackgroundService`.

Chưa biết chắc:

- repository lifetime đang là Scoped hay Transient;
- DI container có đang phát hiện captive dependency ở startup hay configuration hiện tại cho phép graph này được tạo;
- `EmployeeCacheBuilder` có giữ thêm mutable state hay không;
- BackgroundService gọi service đồng thời bao nhiêu lần;
- có code nào lưu entity tracked qua nhiều request không;
- unit tests hiện có dựng service graph bằng DI container thật hay mock thủ công.

## Câu hỏi chính

Hãy giải thích lifetime mismatch giữa Singleton và Scoped dependency có thể dẫn tới captive dependency như thế nào, vì sao `DbContext` không nên được chia sẻ lâu dài giữa nhiều request/concurrent operations, và bạn sẽ sửa service design/DI boundary ra sao thay vì thêm `lock` hoặc biến `DbContext` thành Singleton.

## Câu hỏi làm rõ nên cân nhắc

1. `IEmployeeRepository` và các dependencies phía dưới đang được đăng ký lifetime nào?
2. `EmployeeCacheBuilder` có thực sự cần Singleton hay chỉ được chọn vì nghĩ rằng “cache service nên là singleton”?
3. BackgroundService cần scope theo từng unit of work hay cần factory để tạo `DbContext` độc lập?
4. Có tracked entity hoặc `IQueryable` nào bị giữ ngoài request/unit-of-work boundary không?
5. Concurrent execution của cache builder hiện có được giới hạn hoặc partition theo key không?

## Gợi ý tư duy

### Gợi ý 1

Singleton sống suốt application lifetime; một Scoped dependency thường chỉ được thiết kế để sống trong một scope ngắn như HTTP request hoặc explicit scope.

### Gợi ý 2

`DbContext` vừa quản lý database connection/work unit vừa giữ change tracker; nó không phải một stateless thread-safe data client.

### Gợi ý 3

Nếu BackgroundService cần dùng scoped services, boundary đúng thường là tạo scope cho từng unit of work thay vì kéo scoped instance lên singleton lifetime.

## Cấu trúc trả lời đề xuất

1. Map dependency graph và lifetimes.
2. Giải thích captive dependency và lifetime inversion.
3. Giải thích `DbContext` unit-of-work/change-tracker behavior.
4. Phân biệt race condition, stale tracked state và database concurrency.
5. Thu evidence từ DI validation/logs/traces.
6. Xác định service nào thực sự cần Singleton.
7. Thiết kế scope/factory boundary cho HTTP và background work.
8. Giữ entity/`IQueryable` trong đúng lifetime.
9. Viết integration/concurrency tests cho DI graph.
10. Monitor lỗi concurrency và request/job failures sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Singleton không nên giữ trực tiếp một Scoped service qua toàn application lifetime.
- `DbContext` được thiết kế như một unit of work ngắn hạn và không thread-safe cho concurrent operations.
- Một `DbContext` sống quá lâu có thể giữ change tracker lớn, stale tracked entities và state ngoài intended transaction/request boundary.
- Đăng ký `DbContext` thành Singleton làm vấn đề tệ hơn, không phải fix.
- `lock` quanh mọi repository call chỉ serialize workload trên một process và không sửa lifetime/data-boundary semantics.
- Với request processing, scoped DbContext/repository theo request hoặc explicit unit of work thường phù hợp.
- Với BackgroundService, tạo scope bằng `IServiceScopeFactory` hoặc dùng một factory như `IDbContextFactory<TContext>` khi phù hợp.
- Không return/lưu `IQueryable` ra ngoài lifetime của context.
- Cần test bằng DI container thật để phát hiện graph/lifetime issue.

### Điểm cộng

- Phân biệt Singleton service “stateless/thread-safe” với singleton object giữ mutable per-operation state.
- Nếu cache cần process-wide state, cache data có thể singleton nhưng data-loading operation vẫn tạo scoped database dependency riêng.
- `AsNoTracking` giảm tracking overhead cho read-only query nhưng không biến một shared `DbContext` thành thread-safe.
- Có cancellation propagation và bounded parallelism cho BackgroundService.
- Không dùng Service Locator tùy tiện; explicit scope/factory chỉ ở boundary cần lifetime transition.

### Senior+

- Nhận ra lifetime validation có thể bắt một số captive-dependency graphs nhưng không nên dựa vào validation như correctness mechanism duy nhất.
- Thiết kế idempotent background unit of work nếu job có thể retry/restart.
- Tách cache population coordination khỏi EF lifetime: per-key deduplication có thể cần, nhưng không được serialize mọi database access bằng global lock.
- Có observability theo request/job scope để correlate context lifetime, concurrent work và lỗi.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng dependency graph thực tế. `AddDbContext` thông thường tạo `DbContext` theo scoped lifetime. Nếu một Singleton giữ repository và repository giữ scoped `DbContext`, scoped object đó có nguy cơ bị “kéo dài tuổi thọ” theo Singleton. Đây là captive dependency: object được thiết kế cho scope ngắn lại bị giữ bởi object sống lâu hơn.

Vấn đề không chỉ là connection. `DbContext` giữ change tracker và internal state cho một unit of work. Nếu cùng instance bị dùng đồng thời từ nhiều requests/jobs, các operations có thể overlap trên cùng context — điều EF Core không thiết kế để hỗ trợ. Nếu context sống quá lâu, tracked entities còn có thể giữ state cũ hoặc làm heap/tracking footprint tăng ngoài dự kiến.

Tôi sẽ không đăng ký `DbContext` thành Singleton. Điều đó biến toàn application thành một unit of work khổng lồ và làm concurrency/thread-safety risk rõ hơn. Tôi cũng không bọc toàn repository bằng một global `lock`: nó chỉ làm throughput giảm, không giải quyết lifecycle, không giúp nhiều application instances và có thể che thiết kế sai.

Nếu `EmployeeCacheBuilder` không có lý do thực sự để Singleton, phương án đơn giản nhất là đổi nó thành Scoped hoặc Transient phù hợp call boundary. Nếu cần Singleton vì nó giữ process-wide cache/coordinator, tôi tách hai trách nhiệm:

- Singleton giữ state/cache thread-safe.
- Mỗi lần cần load dữ liệu, tạo một scope hoặc một `DbContext` mới cho đúng unit of work.

Trong `BackgroundService`, tôi không inject trực tiếp scoped repository rồi giữ suốt process lifetime. Tôi có thể inject `IServiceScopeFactory`, và với mỗi message/job:

```csharp
await using var scope = _scopeFactory.CreateAsyncScope();
var repository = scope.ServiceProvider.GetRequiredService<IEmployeeRepository>();
await repository.ProcessAsync(...);
```

Hoặc nếu design phù hợp với EF Core trực tiếp, dùng `IDbContextFactory<AppDbContext>` để tạo context riêng cho mỗi operation. Lựa chọn phụ thuộc abstraction hiện tại và testability; mục tiêu là một context cho một unit of work, không share concurrent.

Tôi cũng kiểm tra repository có return `IQueryable` để caller enumerate sau khi scope kết thúc hay không. Nếu có, execution/lifetime boundary trở nên khó đoán. Projection/materialization nên diễn ra trước khi context bị dispose nếu caller không sở hữu context.

Nếu cache builder cần collapse nhiều request cùng key, tôi có thể thêm per-key coordination hoặc single-flight pattern, nhưng coordination đó tách biệt khỏi EF context. Mỗi actual load vẫn dùng context riêng.

Testing cần dựng WebApplicationFactory/DI container thật, chạy concurrent requests/jobs và verify không có context-concurrency exceptions. Tôi cũng thêm tests cho background scope disposal và cancellation. Production metrics/logging nên capture job/request correlation, exception fingerprint, context-related failures và cache load duration.

## Mẫu trả lời trong phỏng vấn

“Em sẽ xem đây là lifetime-boundary problem trước khi coi là database issue. Nếu Singleton giữ repository Scoped và repository giữ `DbContext`, scoped object bị captive theo Singleton. `DbContext` không thread-safe và còn giữ change tracker, nên share lâu dài giữa nhiều requests/jobs có thể gây concurrent-operation errors hoặc stale tracked state.

Em không đổi `DbContext` thành Singleton và không global-lock repository. Nếu cache builder không cần Singleton thì đổi lifetime. Nếu nó phải Singleton, em tách cache state khỏi data-loading operation; mỗi operation tạo scope hoặc `IDbContextFactory` để có context riêng. Với BackgroundService cũng tạo scope theo job.

Em sẽ kiểm tra thêm `IQueryable` escaping scope, tracked entities bị giữ lâu và test dependency graph/concurrency bằng DI container thật. Sau fix em monitor context-related exceptions, job/request failures và cache-load concurrency.”

## Câu hỏi đào sâu

1. Nếu đổi cache builder thành Scoped làm cache process-wide biến mất, bạn tách state và data-access lifetime thế nào?
2. Một teammate nói `AsNoTracking()` sẽ làm shared Singleton `DbContext` an toàn; bạn phản biện ra sao?
3. Nếu BackgroundService cần xử lý 50 messages song song, bạn tạo scopes/contexts và giới hạn concurrency như thế nào để không làm cạn DB connection pool?

## Lỗi trả lời thường gặp

- Đổi `DbContext` thành Singleton để “khớp lifetime”.
- Thêm global `lock` quanh repository.
- Cho rằng `AsNoTracking` giải quyết thread safety.
- Inject scoped repository trực tiếp vào long-lived hosted service rồi giữ mãi.
- Không xét `IQueryable`/tracked entity escaping lifetime.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất lock hoặc Singleton DbContext.
- **3–4:** Biết lifetime mismatch nhưng chưa giải thích change tracker/concurrency.
- **5–6:** Có đúng scope/factory boundary và test strategy.
- **7–8:** Tách cache coordination khỏi data access, có bounded concurrency và observability.
- **9–10:** Kết nối DI lifetime, unit-of-work semantics, thread safety và operational behavior thành design rõ ràng, có điều kiện.

# Câu 2 — App Service đột ngột 500 sau secret rotation: Managed Identity, Key Vault và startup path đang hỏng ở đâu?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure App Service, Managed Identity, Azure Key Vault, configuration, secret rotation, authentication/authorization, startup resilience, deployment, observability

## Bối cảnh

Một ASP.NET Core API chạy trên Azure App Service on Linux. Application lấy database credential và một third-party API secret từ Azure Key Vault.

Hệ thống gần đây chuyển từ secret được copy trực tiếp vào App Service settings sang Managed Identity + Key Vault access. Sau một secret rotation và một deployment gần nhau, production xuất hiện:

- một số instances start bình thường;
- một số instances trả 500 ngay từ startup hoặc readiness/health path;
- logs có `403` khi đọc một Key Vault secret ở vài instances;
- database connectivity ở một số request vẫn hoạt động;
- restart instance có lúc làm lỗi biến mất;
- deployment slot staging hoạt động nhưng sau swap production lại lỗi;
- team nghi “Key Vault cache chưa refresh”;
- một developer muốn đưa secret value trở lại App Service settings để tránh dependency startup;
- một developer khác đề xuất catch mọi exception khi load config rồi khởi động với giá trị rỗng.

Chưa biết chắc:

- đang dùng system-assigned hay user-assigned Managed Identity;
- Key Vault đang dùng RBAC hay access policy model;
- staging và production slots có identity/config giống nhau hay không;
- secret được đọc bằng Key Vault reference trong App Settings hay application gọi SDK trực tiếp;
- app có cache secret trong process không;
- secret version được pin hay lấy current version;
- network/private endpoint/firewall rules có khác giữa slots/instances không;
- deployment có đổi identity, role assignment hoặc configuration cùng lúc không.

## Câu hỏi chính

Bạn sẽ stabilize incident và phân biệt identity/authorization, secret-version/configuration, network access và startup-caching hypotheses như thế nào? Sau đó hãy thiết kế secret loading/rotation/deployment flow để production có thể rotate secret an toàn mà không biến Key Vault thành single point of startup failure không quan sát được.

## Câu hỏi làm rõ nên cân nhắc

1. Những instance lỗi và instance khỏe đang dùng cùng identity principal ID hay khác nhau?
2. Key Vault access được cấp bằng RBAC/access policy nào, scope nào và deployment có vừa thay role assignment không?
3. Slot swap có swap cả app settings/identity-related configuration mong muốn không?
4. Secret được resolve trước application startup hay được SDK load/lazy refresh trong runtime?
5. 403 có đến từ authorization hay request thực tế không tới đúng vault/network path?

## Gợi ý tư duy

### Gợi ý 1

`403` là evidence mạnh nhưng chưa đủ để kết luận “secret sai”; cần xác định principal, vault, scope và request path thực tế.

### Gợi ý 2

Slot swap có thể đổi traffic nhanh hơn việc bạn nhận ra staging/production không thật sự có cùng identity/network/configuration.

### Gợi ý 3

Secret rotation là một distributed configuration change; cần overlap/compatibility window và observability, không chỉ “replace value rồi restart”.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact và rollback/stabilization options.
2. Correlate deployment, rotation, slot swap và first failure time.
3. Xác định identity principal của từng slot/instance.
4. Verify authorization và Key Vault audit/access evidence.
5. Verify DNS/network/private endpoint/firewall path.
6. Verify secret identifier/version/configuration semantics.
7. Sửa startup behavior và fallback policy có kiểm soát.
8. Thiết kế rotation + overlap + validation workflow.
9. Test slot swap/identity/network failures.
10. Monitor secret-resolution health, 403, startup và downstream auth failures.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không coi secret rotation đơn thuần là thay một string.
- Xác minh identity thực tế của production/staging và quyền của đúng principal.
- Phân biệt authentication thành công nhưng authorization 403 với network/DNS/path failure.
- Slot configuration/identity/network phải được xem như deployment dependency.
- Không khởi động với secret rỗng nếu dependency đó là bắt buộc cho correctness/security.
- Không log secret value.
- Rotation cần test cả old/new secret overlap khi downstream cho phép, hoặc một cutover strategy tương đương.
- Startup/readiness phải phản ánh đúng dependency criticality thay vì trả healthy khi app chắc chắn không phục vụ được.
- Có rollback/runbook rõ nếu secret/identity change fail.

### Điểm cộng

- Nếu secret có versioned URI/reference, hiểu việc pin version vs lấy latest ảnh hưởng rotation/rollback.
- Dùng Managed Identity thay long-lived credential trong app khi Azure resource support phù hợp.
- Tách secret dùng cho critical startup dependency với optional feature dependency; optional dependency có thể lazy-load/degrade.
- Cache secret trong memory có refresh/expiry semantics rõ, không vĩnh viễn.
- Validate staging bằng chính identity/network path gần production nhất trước swap.

### Senior+

- Thiết kế rotation two-phase: grant/add new credential → validate consumers → switch reference/use → revoke old sau observation window.
- Nếu third-party chỉ hỗ trợ một active secret, có cutover/rollback plan ngắn và synthetic validation trước traffic shift.
- Có audit trail correlation giữa deployment ID, principal ID, vault secret version và application version mà không lộ secret.
- Không tạo blanket retry storm khi Key Vault trả 403 vì permission lỗi không phải transient network failure.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng timeline: secret rotation lúc nào, deployment lúc nào, slot swap lúc nào, instance nào fail đầu tiên. Sau đó lấy principal identity của staging/production và so với Key Vault authorization logs/configuration. Nếu chỉ vài instances lỗi nhưng cùng slot, tôi kiểm tra whether configuration/network path thực sự đồng nhất hoặc instance có stale process state.

`403` thường hướng điều tra về authorization, nhưng tôi vẫn xác minh request đi tới đúng vault và principal nào được dùng. Với system-assigned identity, mỗi App Service/slot topology có thể có identity khác tùy cấu hình; với user-assigned identity, application/config phải thực sự chọn đúng identity. Tôi không giả định staging chạy được nghĩa production chắc chắn có cùng principal.

Nếu dùng Key Vault reference trong App Settings, tôi kiểm tra reference syntax, secret identifier/version và platform resolution behavior của configuration hiện tại. Nếu app dùng SDK trực tiếp, tôi kiểm tra credential chain, requested vault URI, retries và cache semantics. Trong cả hai trường hợp, logs phải ghi secret name/version identifier ở mức an toàn — không ghi value.

Network cũng cần kiểm tra riêng: private endpoint, DNS resolution, VNet integration và firewall rules. Một lỗi access không nên bị gộp thành “Key Vault down”.

Về rotation, nếu downstream hỗ trợ nhiều credentials đồng thời, tôi dùng overlap:

1. tạo/enable secret mới;
2. cấp quyền và deploy/reference consumer mới;
3. validate trên staging/synthetic check;
4. shift traffic;
5. quan sát auth failures;
6. revoke secret cũ sau safety window.

Nếu downstream chỉ cho một credential active, tôi thiết kế coordinated cutover với rollback path và giảm blast radius, ví dụ canary/slot validation trước full traffic.

Ứng dụng không nên catch lỗi đọc required secret rồi chạy với empty string. Nếu DB credential bắt buộc để phục vụ core API, readiness nên fail và instance không nhận traffic; liveness không nhất thiết restart vô hạn chỉ vì permission sai. Với optional third-party feature, lazy load/degraded mode có thể hợp lý nếu business cho phép.

Tôi tránh đưa secret trở lại plaintext App Service settings chỉ để né incident, trừ emergency mitigation được kiểm soát và có kế hoạch remove ngay; root cause vẫn phải là identity/config/network/rotation process.

Testing cần có revoked permission, wrong identity, rotated version, private DNS failure, slot swap với mismatched config và process restart. Metrics gồm Key Vault access failures theo status, startup time/failure, readiness state, secret refresh failures, downstream authentication errors và deployment/rotation correlation.

## Mẫu trả lời trong phỏng vấn

“Em sẽ dựng timeline rotation/deployment/swap trước, rồi xác định principal ID thực tế của từng slot/instance và correlate với Key Vault access logs. `403` cho thấy authorization path có vấn đề nhưng em vẫn verify đúng vault, identity, RBAC/access policy và network/private endpoint.

Em không catch rồi dùng secret rỗng. Required secret fail thì readiness fail để instance không nhận traffic; optional dependency có thể lazy-load/degrade nếu business cho phép. Rotation em ưu tiên two-phase overlap: tạo secret mới, grant + validate consumer, shift traffic, observe rồi mới revoke cũ.

Em cũng test slot swap với đúng identity/network, không log secret value, và monitor Key Vault errors, startup/readiness, secret version identifier và downstream auth failures. Mục tiêu là rotation có rollback/observation window rõ chứ không phải thay value và hy vọng restart thành công.”

## Câu hỏi đào sâu

1. Nếu staging slot dùng user-assigned identity A nhưng production sau swap vẫn dùng identity B, bạn thiết kế slot/config governance thế nào để tránh lặp lại?
2. Một teammate muốn retry Key Vault 403 trong 10 phút để “đợi Azure ổn định”; bạn phản biện thế nào?
3. Nếu third-party chỉ cho một active API key và rotation bắt buộc không downtime, bạn tổ chức cutover/validation ra sao?

## Lỗi trả lời thường gặp

- Chỉ restart App Service nhiều lần.
- Log secret value để debug.
- Retry permission 403 như transient network lỗi.
- Giả định staging/prod slots có cùng identity/config mặc định.
- Khởi động app với secret rỗng rồi để lỗi phát sinh sâu trong request path.

## Thang điểm 0–10

- **0–2:** Chỉ restart hoặc copy secret trở lại config.
- **3–4:** Biết kiểm tra Key Vault permissions nhưng thiếu identity/slot/network reasoning.
- **5–6:** Có timeline, principal verification, readiness và rotation workflow.
- **7–8:** Có two-phase rotation, rollback, synthetic validation, network/slot failure tests.
- **9–10:** Kết nối identity, authorization, configuration versioning, deployment topology và failure semantics thành runbook production hoàn chỉnh.

# Câu 3 — Thiết kế product-detail platform dùng Optimizely CMS + commerce/search/reviews mà vẫn chịu được dependency degradation

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, composable commerce, ASP.NET Core, CMS architecture, REST APIs, Redis, Elasticsearch, CDN/Akamai, third-party integrations, caching, resilience, observability, system design

## Bối cảnh

Một website thương mại điện tử dùng Optimizely CMS để editor quản lý:

- campaign copy;
- hero/banner blocks;
- SEO metadata;
- editorial product storytelling;
- landing pages.

Thông tin product commerce đến từ một Product/Commerce API khác:

- price;
- availability;
- variants;
- promotions.

Search dùng Elasticsearch. Reviews đến từ third-party provider. Public traffic đi qua Akamai CDN. Một số product pages rất nhiều traffic trong campaign.

Business yêu cầu:

- editor publish content mà không cần deploy code;
- product price/availability không được stale quá mức khi user chuẩn bị mua;
- review provider down không được làm product page trắng;
- search lag không được làm canonical product data sai;
- campaign page phải chịu traffic spike lớn;
- personalized/authenticated account data không được cache public;
- SEO metadata, canonical URL và structured data phải ổn định;
- team muốn tránh một “mega backend” gọi tuần tự 5 dependencies cho mỗi page request.

Team đang tranh luận:

1. SSR page gọi trực tiếp CMS + Product API + Search + Review provider mỗi request;
2. Redis cache mọi thứ với TTL dài;
3. build một compositional/BFF layer có cache và degradation policy;
4. pre-render/static toàn bộ product pages ở CDN;
5. tách mỗi integration thành microservice độc lập.

Chưa biết chắc:

- update frequency của price/inventory/campaign content;
- freshness SLO cho từng field;
- review data có ảnh hưởng purchase decision critical flow hay chỉ enrichment;
- current QPS/p95/p99 và campaign peak multiplier;
- CDN purge/invalidation capability hiện dùng;
- personalized fragments xuất hiện trên product page ở mức nào;
- editor preview có cần gọi live commerce/reviews hay mock snapshot;
- ownership/team boundaries thực tế.

## Câu hỏi chính

Hãy thiết kế product-detail delivery architecture cho hệ thống này. Xác định ownership/source of truth cho CMS content, product/price/availability, reviews và search; quyết định rendering/composition boundary, cache/CDN strategy, freshness semantics, degradation behavior, security, observability, editor preview và deployment. So sánh BFF/composition layer, direct dependency calls, aggressive caching/static rendering và microservices; giải thích điều gì làm recommendation của bạn thay đổi.

## Câu hỏi làm rõ nên cân nhắc

1. Freshness SLO riêng cho editorial content, price, inventory, promotion và reviews là bao nhiêu?
2. Product page có thể render thiếu reviews/recommendations nhưng vẫn bán hàng được không?
3. User-specific price, entitlement hoặc account state có xuất hiện trên cùng HTML cacheable không?
4. CMS preview cần xem draft content kết hợp live product data hay chỉ editorial representation?
5. Campaign peak traffic và origin/CDN cache hit ratio mục tiêu là bao nhiêu?

## Gợi ý tư duy

### Gợi ý 1

Không phải mọi field trên cùng page đều cần cùng consistency/freshness policy.

### Gợi ý 2

CDN/Redis cache là derived state; hãy xác định source of truth và invalidation trước khi chọn TTL.

### Gợi ý 3

Dependency degradation nên được thiết kế theo business criticality: product core khác reviews, recommendations hoặc marketing enrichment.

## Cấu trúc trả lời đề xuất

1. Map domain/data ownership và criticality.
2. Làm rõ traffic, freshness, personalization và SEO.
3. Chọn server/rendering/composition boundary.
4. Thiết kế CMS content model/API boundary.
5. Thiết kế cache/CDN theo data class.
6. Thiết kế dependency timeout/bulkhead/fallback.
7. Thiết kế search/review eventual consistency.
8. Thiết kế preview/security/personalization.
9. Thiết kế deployment, purge và rollback.
10. Định nghĩa testing/observability/SLOs.

## Ý chính của câu trả lời tốt

### Bắt buộc

- CMS là source of truth cho editorial content; commerce/product system là source of truth cho transactional product state.
- Elasticsearch không trở thành source of truth cho price/inventory chỉ vì đọc nhanh.
- Không gọi tuần tự mọi dependency trên critical request path nếu có thể parallelize/cache/degrade hợp lý.
- Freshness phải theo field/domain, không một TTL cho toàn page.
- Reviews là candidate cho stale-cache/degraded omission nếu business cho phép.
- Price/inventory tại purchase boundary phải được revalidate từ authoritative commerce source phù hợp.
- CDN public cache không được chứa personalized/authenticated private data.
- CMS publish phải có cache invalidation/purge strategy rõ.
- Timeouts, cancellation và circuit/bulkhead/degradation phải khác nhau theo dependency criticality.
- Editor preview/draft không được leak vào public CDN.

### Điểm cộng

- Server/BFF composition có thể fan-out song song tới independent dependencies với deadline budget, nhưng không tạo request amplification vô hạn.
- Dùng stale-while-revalidate hoặc stale fallback cho non-critical content khi platform semantics/business cho phép.
- Cache key gồm locale, market/currency và public variation cần thiết; tránh high-cardinality user key ở CDN.
- Tách static/editorial shell với dynamic price/inventory fragment nếu personalization/freshness yêu cầu.
- Search index chỉ dùng discovery/candidate retrieval; product detail rehydrates canonical product data khi cần.

### Senior+

- Thiết kế product page theo critical path budget: CMS/content, product core, optional enrichments có timeout riêng và overall deadline.
- Có anti-stampede/single-flight cho hot product cache misses trong campaign.
- Có fallback matrix theo dependency: CMS unavailable, Product API unavailable, Reviews unavailable, Redis unavailable, Elasticsearch lag, CDN purge fail.
- Không tự động tách microservices nếu ownership/scale/deployment boundary không chứng minh lợi ích.
- Có canary/cache-version strategy để rollback rendering contract mà không đọc cache payload incompatible.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng ownership. Optimizely CMS sở hữu editorial content: page/block structure, campaign copy, SEO metadata và publishing workflow. Commerce/Product API sở hữu giá, inventory, variants và promotions. Reviews provider sở hữu review content nhưng đó thường là enrichment. Elasticsearch là derived search index phục vụ discovery, không phải authoritative product state.

Từ đó tôi không dùng một TTL chung cho “product page”. Tôi định nghĩa freshness class:

- editorial content: invalidation theo publish + TTL/edge cache dài hơn;
- price/promotion: TTL ngắn hoặc read-through policy theo business freshness;
- inventory: có thể rất ngắn/stale-tolerant ở browse nhưng phải revalidate trước add-to-cart/checkout;
- reviews: cache lâu hơn và cho phép stale/omit nếu provider down;
- SEO metadata/canonical: gắn với published CMS version và phải deterministic cho crawler.

Một BFF/composition layer trên ASP.NET Core có thể hợp lý nếu nó gom contracts, auth, resilience và cache policy. Nhưng tôi giữ nó mỏng theo responsibility: nó không trở thành một database mới hoặc chứa mọi business rule.

Request path có thể là:

1. Akamai trả cached public HTML/response nếu variant hợp lệ.
2. Origin/BFF lấy published CMS representation từ cache/CMS.
3. Product core được lấy từ commerce cache/API theo freshness requirement.
4. Reviews/recommendations gọi song song với timeout ngắn; nếu fail, render page không có enrichment.
5. Overall deadline budget ngăn một dependency kéo toàn page đến timeout.

Tôi không để third-party review provider trên hard critical path nếu product vẫn có thể mua mà không có review. Có circuit breaker/bulkhead hoặc concurrency limit tùy implementation; mục tiêu là failure isolation, không phải thêm pattern vì checklist.

Với campaign hot products, Redis/cache có thể bảo vệ origin nhưng phải có anti-stampede. Khi key miss/expire cùng lúc, nhiều requests không nên cùng gọi commerce API. Có thể dùng single-flight/per-key coordination trong một instance hoặc distributed strategy khi cần, cộng TTL jitter. Nếu Redis down, fallback phải có rate/concurrency limit để không chuyển outage thành commerce-origin outage.

CDN cache chỉ cho public representation. Nếu page có user-specific wishlist, account, negotiated price hoặc entitlement, tôi tách fragment/API call phía client hoặc server private path thay vì cache HTML personalized công khai. Cache key phải xét locale/market/currency và các public variants thực sự ảnh hưởng representation.

CMS publish cần purge/invalidation. Tôi không purge toàn site nếu một content item đổi; map dependency từ page/product/content key tới edge/cache keys nếu platform cho phép. Preview dùng hostname/path/authenticated mode riêng, bypass public cache và cho phép draft content; nó không được dùng chung cache namespace với published page.

Search lag không được dùng để render authoritative product detail. Search có thể trả product ID; detail path fetch canonical state. Tương tự, checkout luôn revalidate current price/inventory theo transactional rules.

Nếu commerce API down, recommendation phụ thuộc business: có thể render stale product snapshot với banner/unavailable purchase action, hoặc fail closed nếu legal/price correctness yêu cầu. Điều đó phải là explicit product decision.

Tôi chỉ tách integration thành microservice độc lập nếu có ownership, scaling, release cadence hoặc failure-isolation requirement thực. Nếu cùng một team quản lý và BFF đủ rõ, nhiều microservices chỉ thêm network hops, deployment và observability burden.

Testing gồm CMS publish/purge, preview isolation, stale cache, Redis outage, review timeout, commerce degradation, CDN miscache, locale/market keys, price change trong checkout và traffic spike. Observability gồm cache hit ratio theo layer, origin QPS, dependency p95/p99/error, stale-served count, review degradation rate, product freshness lag, CDN purge failures và business conversion impact.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách source of truth trước: CMS sở hữu editorial/SEO, commerce API sở hữu price/inventory/variants, reviews là enrichment, Elasticsearch chỉ là search projection. Vì freshness khác nhau nên em không cache cả page bằng một TTL duy nhất.

Em ưu tiên public CDN + một composition/BFF layer mỏng. CMS content có publish invalidation và edge cache dài hơn; price/inventory có freshness ngắn hơn và được revalidate ở purchase boundary. Reviews có timeout nhỏ, cache/stale fallback và có thể bỏ khỏi page nếu provider down. Các calls độc lập có thể chạy song song trong overall deadline budget.

Personalized data không vào public cache; preview dùng isolated route/cache namespace. Em thêm anti-stampede cho hot products và fallback có rate limit khi Redis/downstream fail. Microservices chỉ tách khi ownership/scale/deployment boundary thật sự cần. Sau đó em failure-test CMS/Redis/review/commerce/CDN và theo dõi cache hit, dependency p99, stale rate, purge failures và product freshness.”

## Câu hỏi đào sâu

1. Nếu business yêu cầu price trên product page luôn đúng tuyệt đối nhưng commerce API p99 là 800 ms, bạn thay đổi UX/architecture/SLO nào?
2. Một teammate muốn cache toàn bộ HTML product page 24 giờ trên Akamai để giảm origin cost; bạn phản biện dựa trên personalization/freshness/invalidation ra sao?
3. Nếu Redis outage làm commerce API quá tải vì toàn bộ cache miss fallback, bạn thiết kế graceful degradation/backpressure thế nào?

## Lỗi trả lời thường gặp

- Coi Elasticsearch là source of truth cho product state.
- Một TTL cho toàn bộ product page.
- Để reviews hoặc recommendations làm fail toàn page.
- Cache personalized HTML công khai ở CDN.
- Tách microservices chỉ vì architecture “hiện đại”.

## Thang điểm 0–10

- **0–2:** Chỉ nói “dùng Redis/CDN/microservices”.
- **3–4:** Có caching và APIs nhưng thiếu ownership/freshness/failure semantics.
- **5–6:** Có source-of-truth boundaries, per-data freshness, degradation và CDN/privacy safety.
- **7–8:** Có deadline budget, anti-stampede, preview isolation, checkout revalidation và failure testing.
- **9–10:** Cân bằng editorial workflow, commerce correctness, SEO, performance, failure isolation và operational complexity thành architecture có điều kiện rõ ràng.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime là một phần của correctness. Singleton giữ Scoped dependency có thể biến short-lived unit of work thành long-lived shared state và làm lỗi concurrency khó đoán.
- `DbContext` nên được giới hạn theo unit of work; `AsNoTracking` không biến shared context thành thread-safe.
- Secret rotation trên cloud là bài toán identity + authorization + configuration version + deployment topology + rollback, không chỉ là thay secret value.
- Managed Identity giảm secret management nhưng vẫn cần đúng principal, đúng permission và đúng network path.
- Trong composable CMS/e-commerce architecture, mỗi data domain cần source of truth, freshness policy và degradation policy riêng.
- CDN/Redis/search là derived delivery/read layers; purchase-critical state phải được xác minh tại authoritative boundary phù hợp.

## Mẫu tư duy cần nhớ

1. **Map lifetimes and ownership before debugging symptoms.**
2. **Separate authentication, authorization, configuration and network hypotheses.**
3. **Design rotation/migration with overlap, validation and rollback windows.**
4. **Give each data class its own freshness and failure policy.**
5. **Do not add distributed architecture complexity unless ownership, scale or failure isolation justify it.**
