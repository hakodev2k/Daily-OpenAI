# Code Review Challenge 1 — Hangfire job gửi thông báo bị chạy trùng dưới tải

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để gửi thông báo email sau khi một business event được tạo. Hệ thống chạy 3 application instances. Mỗi giờ có thể có vài nghìn notification. Gần đây production ghi nhận một số người dùng nhận 2–3 email giống nhau, trong khi database cuối cùng vẫn hiển thị notification là `Sent`.

External email provider đôi khi timeout sau khi đã chấp nhận request. Hangfire được cấu hình retry khi job throw exception. Business yêu cầu không được bỏ sót notification, đồng thời duplicate phải được hạn chế tối đa.

## Đoạn code cần review

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task SendAsync(Guid notificationId)
    {
        var notification = await _db.Notifications
            .FirstOrDefaultAsync(x => x.Id == notificationId);

        if (notification == null)
            return;

        if (notification.Status == "Sent")
            return;

        notification.Status = "Processing";
        notification.AttemptCount++;
        await _db.SaveChangesAsync();

        try
        {
            await _emailSender.SendAsync(
                notification.Email,
                notification.Subject,
                notification.Body);

            notification.Status = "Sent";
            notification.SentAt = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Failed sending notification {NotificationId} to {Email}",
                notification.Id,
                notification.Email);

            notification.Status = "Pending";
            await _db.SaveChangesAsync();
            throw;
        }
    }
}
```

## Câu hỏi gợi mở

- Hai Hangfire worker có thể đọc cùng một row trước khi worker nào cập nhật trạng thái không?
- `Status = Processing` có thực sự tạo ra quyền sở hữu độc quyền đối với notification không?
- Điều gì xảy ra nếu email provider đã nhận request nhưng client timeout trước khi nhận response?
- Database transaction có thể đảm bảo atomicity với external email provider không?
- Retry của Hangfire thay đổi yêu cầu idempotency như thế nào?

## Gợi ý

### Gợi ý 1

Hãy phân biệt **database state transition** với **side effect bên ngoài database**. Hai việc này không thể được gom vào một local EF Core transaction để tạo exactly-once delivery thực sự.

### Gợi ý 2

Hãy xem xét atomic claim/concurrency control, durable idempotency key và trạng thái có khả năng phục hồi khi process chết giữa các bước.

## Kết quả code review tham khảo

### 1. Check-then-act race condition — Critical

**Problem:** Nhiều worker có thể cùng đọc `Pending`, sau đó cùng chuyển row sang `Processing` và cùng gửi email.  
**Why:** Read và update không có optimistic concurrency token, conditional update hay lock tạo ownership.  
**Impact:** Duplicate email xuất hiện chủ yếu dưới tải hoặc khi cùng job bị enqueue nhiều lần.  
**Recommended fix:** Claim row bằng một atomic conditional update, ví dụ chỉ update `Pending -> Processing` nếu trạng thái hiện tại vẫn là `Pending`, rồi kiểm tra affected rows; hoặc dùng optimistic concurrency token phù hợp.

### 2. Không thể đảm bảo exactly-once side effect bằng local DB transaction — Critical

**Problem:** Email có thể đã được provider chấp nhận nhưng client timeout. Job catch exception, đưa row về `Pending`, rồi Hangfire retry và gửi lại.  
**Why:** Database và email provider không nằm trong cùng distributed transaction.  
**Impact:** Duplicate dù database logic nhìn có vẻ đúng.  
**Recommended fix:** Nếu provider hỗ trợ idempotency key, dùng một key ổn định theo notification. Nếu không, xác định rõ semantics là at-least-once và thiết kế deduplication tốt nhất có thể.

### 3. Crash window sau khi gửi nhưng trước khi lưu `Sent` — Critical

**Problem:** Process có thể chết sau `SendAsync` thành công nhưng trước `SaveChangesAsync`.  
**Impact:** Row còn `Processing`; recovery có thể gửi lại hoặc để notification mắc kẹt.  
**Recommended fix:** Có lease/claim timestamp, recovery policy cho stale processing và idempotency key phía provider.

### 4. `Processing` không có lease/owner — High

**Problem:** Không biết worker nào sở hữu job và bao giờ claim hết hạn.  
**Impact:** Job có thể mắc kẹt vô thời hạn sau process crash.  
**Recommended fix:** Lưu `ProcessingStartedAt`, `LeaseUntil`, `WorkerId` hoặc một claim token; chỉ worker sở hữu token mới được finalize.

### 5. Cancellation không được truyền xuống — Medium

**Problem:** DB và network calls không nhận cancellation token.  
**Impact:** Shutdown/deployment có thể kéo dài và work tiếp tục ngoài lifecycle mong muốn.  
**Recommended fix:** Nhận `CancellationToken` phù hợp với execution model và truyền xuống dependency nếu API hỗ trợ.

### 6. Log chứa email người nhận — Medium

**Problem:** PII được ghi trực tiếp vào application log.  
**Impact:** Tăng phạm vi dữ liệu nhạy cảm trong logging system.  
**Recommended fix:** Log notification ID và tenant/correlation ID; mask/hash email nếu thật sự cần.

### 7. String status dễ tạo invalid state — Low

**Problem:** Trạng thái được biểu diễn bằng magic strings.  
**Impact:** Refactor khó, typo có thể tạo trạng thái không hợp lệ.  
**Recommended fix:** Dùng enum/value mapping hoặc state model rõ ràng và constraint ở database.

### 8. Thiếu observability cho retry và duplicate — Medium

**Problem:** Chỉ log exception, không có attempt, latency, provider message ID hay outcome.  
**Impact:** Khó phân biệt provider timeout, retry storm và concurrency bug.  
**Recommended fix:** Structured logging, tracing và metrics theo outcome/attempt/provider.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa atomic claim. Cú pháp cụ thể có thể thay đổi theo SQL Server/PostgreSQL và phiên bản EF Core; ý quan trọng là state transition phải atomic ở database.

```csharp
public sealed class NotificationJob
{
    private readonly AppDbContext _db;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<NotificationJob> _logger;

    public NotificationJob(
        AppDbContext db,
        IEmailSender emailSender,
        ILogger<NotificationJob> logger)
    {
        _db = db;
        _emailSender = emailSender;
        _logger = logger;
    }

    public async Task SendAsync(Guid notificationId, CancellationToken ct)
    {
        var claimToken = Guid.NewGuid();
        var now = DateTime.UtcNow;

        var claimed = await _db.Notifications
            .Where(x => x.Id == notificationId && x.Status == NotificationStatus.Pending)
            .ExecuteUpdateAsync(setters => setters
                .SetProperty(x => x.Status, NotificationStatus.Processing)
                .SetProperty(x => x.ClaimToken, claimToken)
                .SetProperty(x => x.ProcessingStartedAt, now)
                .SetProperty(x => x.AttemptCount, x => x.AttemptCount + 1), ct);

        if (claimed == 0)
            return;

        var notification = await _db.Notifications
            .AsNoTracking()
            .SingleAsync(x => x.Id == notificationId && x.ClaimToken == claimToken, ct);

        try
        {
            var idempotencyKey = $"notification:{notification.Id}";

            var result = await _emailSender.SendAsync(
                notification.Email,
                notification.Subject,
                notification.Body,
                idempotencyKey,
                ct);

            var finalized = await _db.Notifications
                .Where(x => x.Id == notificationId &&
                            x.Status == NotificationStatus.Processing &&
                            x.ClaimToken == claimToken)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, NotificationStatus.Sent)
                    .SetProperty(x => x.SentAt, DateTime.UtcNow)
                    .SetProperty(x => x.ProviderMessageId, result.MessageId), ct);

            if (finalized != 1)
                throw new InvalidOperationException("Notification ownership was lost before finalization.");
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Notification send failed. NotificationId={NotificationId} ClaimToken={ClaimToken}",
                notificationId,
                claimToken);

            await _db.Notifications
                .Where(x => x.Id == notificationId &&
                            x.Status == NotificationStatus.Processing &&
                            x.ClaimToken == claimToken)
                .ExecuteUpdateAsync(setters => setters
                    .SetProperty(x => x.Status, NotificationStatus.Pending), CancellationToken.None);

            throw;
        }
    }
}
```

Điểm quan trọng: đoạn code này giảm race condition trong database nhưng **không tự tạo exactly-once email**. Idempotency phía provider hoặc một cơ chế deduplication tương đương vẫn cần thiết để xử lý ambiguous network failure.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi database là coordination point. Optimistic concurrency cũng khả thi nhưng cần xử lý conflict rõ ràng. Distributed lock có thể hữu ích trong một số workflow nhưng không giải quyết crash window giữa external side effect và database commit. Outbox pattern rất hữu ích để đảm bảo business transaction và việc phát sinh message được lưu atomically, nhưng consumer gửi email vẫn cần idempotent vì message broker/retry thường có thể redeliver.

## Cách kiểm thử

1. **Concurrency test:** enqueue cùng `notificationId` đồng thời cho nhiều worker; xác nhận chỉ một worker claim được row.
2. **Ambiguous failure test:** fake provider ghi nhận request rồi throw timeout; retry phải dùng cùng idempotency key.
3. **Crash/recovery test:** giả lập process chết khi row đang `Processing`; stale lease phải có recovery path rõ ràng.
4. **Database integration test:** xác nhận conditional update trả đúng affected-row count trên database thực tế.
5. **Load test:** chạy hàng nghìn notification với retry/failure injection và đo duplicate rate, queue latency, processing latency.

## Quan sát trong production

Theo dõi `notification_send_attempts`, `notification_send_failures`, retry count, stale-processing count, claim conflicts, provider latency và provider outcome. Trace nên nối Hangfire job → DB claim → provider call → finalize. Alert khi retry rate hoặc stale-processing tăng đột biến. Log correlation bằng notification ID/job ID nhưng tránh PII không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giải quyết phần nào của bài toán này và phần nào nó không giải quyết?
2. Nếu email provider không hỗ trợ idempotency key, bạn sẽ định nghĩa delivery semantics và UX như thế nào?
3. Vì sao distributed lock vẫn không loại bỏ hoàn toàn duplicate khi process chết sau external side effect?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa có lỗ hổng authorization

**Chủ đề:** Authorization, EF Core query execution, input validation, sensitive-data exposure, performance  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cung cấp endpoint cho portal quản trị tìm audit logs. Sau khi số log tăng lên vài triệu rows, endpoint thường mất 4–10 giây và memory của API tăng mạnh khi nhiều admin tìm kiếm đồng thời. Security review đồng thời phát hiện một user thuộc tenant A đôi khi có thể truy vấn dữ liệu tenant B nếu biết tenant ID.

Business cần search theo text, action và khoảng thời gian; kết quả chỉ cần 100 records mới nhất. Một số trường `Payload` có thể chứa dữ liệu nhạy cảm nội bộ.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        Guid tenantId,
        string? text,
        string? action,
        DateTime? from,
        DateTime? to)
    {
        _logger.LogInformation(
            "Audit search tenant={TenantId}, text={Text}", tenantId, text);

        var logs = await _db.AuditLogs
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        var result = logs
            .Where(x => x.TenantId == tenantId)
            .Where(x => string.IsNullOrEmpty(action) || x.Action == action)
            .Where(x => !from.HasValue || x.CreatedAt >= from.Value)
            .Where(x => !to.HasValue || x.CreatedAt <= to.Value)
            .Where(x => string.IsNullOrEmpty(text) ||
                        x.Payload.Contains(text, StringComparison.OrdinalIgnoreCase))
            .Take(100)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.Action,
                x.Payload,
                x.CreatedAt,
                x.UserEmail
            });

        return Ok(result);
    }
}
```

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization — Critical

**Problem:** Caller tự truyền `tenantId`, trong khi endpoint chỉ yêu cầu authenticated user.  
**Why:** `[Authorize]` không tự chứng minh user được phép truy cập tenant cụ thể.  
**Impact:** Cross-tenant data exposure.  
**Recommended fix:** Resolve tenant scope từ trusted claims/server-side membership hoặc gọi authorization policy/resource authorization trước query; không tin tenant ID chỉ vì client gửi lên.

### 2. Load toàn bộ bảng trước khi filter — Critical

**Problem:** `ToListAsync()` materialize toàn bộ `AuditLogs` trước mọi predicate.  
**Why:** Các `Where` sau đó chạy bằng LINQ-to-Objects.  
**Impact:** Full table read, allocation lớn, GC pressure, latency tăng mạnh và có thể gây memory exhaustion dưới concurrency.  
**Recommended fix:** Xây dựng `IQueryable`, filter/order/take/project trước `ToListAsync`.

### 3. Trả raw `Payload` có thể làm lộ dữ liệu nhạy cảm — High

**Problem:** Response luôn chứa payload đầy đủ.  
**Impact:** Caller có quyền xem audit metadata có thể nhận thêm secrets/PII không cần thiết.  
**Recommended fix:** Data minimization; DTO mặc định không chứa raw payload, hoặc dùng permission riêng/redaction.

### 4. Trả `UserEmail` không qua policy/data minimization — High

**Problem:** Email được trả cho mọi authenticated caller có thể truy cập endpoint.  
**Recommended fix:** Chỉ project field cần thiết và áp dụng quyền/ masking theo requirement.

### 5. Tracking hàng triệu entities không cần thiết — High

**Problem:** Query entity mặc định có thể tracking trong DbContext.  
**Impact:** Change tracker và memory tăng thêm.  
**Recommended fix:** Projection trực tiếp sang DTO thường tránh tracking entity; `AsNoTracking()` cũng phù hợp cho read-only entity query.

### 6. Text search không có giới hạn — Medium

**Problem:** Arbitrary substring search trên payload lớn có thể rất đắt ngay cả khi đẩy xuống database.  
**Impact:** Expensive scans và potential abuse.  
**Recommended fix:** Giới hạn length, yêu cầu date window nếu dataset lớn, cân nhắc database-specific full-text/search architecture nếu use case thực sự cần.

### 7. Thiếu validation cho date range — Medium

**Problem:** `from > to` hoặc range quá rộng không bị chặn.  
**Impact:** Query vô nghĩa hoặc rất đắt.  
**Recommended fix:** Validate ordering và maximum allowed window theo requirement.

### 8. Logging raw search text — Medium

**Problem:** Search term do user nhập được ghi trực tiếp.  
**Impact:** Có thể đưa PII/secrets vào log và tăng log injection/noise risk.  
**Recommended fix:** Log metadata như query length/filter presence; sanitize nếu cần giá trị.

### 9. Pagination semantics chưa rõ — Low

**Problem:** Chỉ `Take(100)` không cho client tiếp tục ổn định.  
**Recommended fix:** Nếu cần pagination, dùng keyset/cursor dựa trên `(CreatedAt, Id)` thay vì offset lớn.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "AuditReader")]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantAccessService _tenantAccess;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        AppDbContext db,
        ITenantAccessService tenantAccess,
        ILogger<AuditController> logger)
    {
        _db = db;
        _tenantAccess = tenantAccess;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
        Guid tenantId,
        string? text,
        string? action,
        DateTimeOffset? from,
        DateTimeOffset? to,
        CancellationToken ct)
    {
        if (!await _tenantAccess.CanReadAuditAsync(User, tenantId, ct))
            return Forbid();

        if (from.HasValue && to.HasValue && from > to)
            return BadRequest("Invalid date range.");

        if (text is { Length: > 200 })
            return BadRequest("Search text is too long.");

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(action))
            query = query.Where(x => x.Action == action);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        if (!string.IsNullOrWhiteSpace(text))
        {
            var term = text.Trim();
            query = query.Where(x => x.SearchableText.Contains(term));
        }

        var result = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(100)
            .Select(x => new AuditLogDto(
                x.Id,
                x.Action,
                x.CreatedAt,
                x.ActorDisplayName))
            .ToListAsync(ct);

        _logger.LogInformation(
            "Audit search completed. TenantId={TenantId} HasText={HasText} ResultCount={ResultCount}",
            tenantId,
            !string.IsNullOrWhiteSpace(text),
            result.Count);

        return Ok(result);
    }
}
```

`SearchableText.Contains` ở đây chỉ minh họa API-level query composition, không phải khẳng định đây là chiến lược search tối ưu cho mọi database. Với dataset lớn, cần kiểm tra execution plan và chọn full-text/search/index strategy phù hợp với SQL Server hoặc PostgreSQL và pattern tìm kiếm thực tế.

## Trade-offs

Server-side tenant authorization thêm một dependency/check nhưng là boundary bảo mật cần thiết. Nếu tenant membership đã được encode trong token, vẫn phải cân nhắc token staleness và số lượng tenant. Projection DTO giảm data transfer và allocation nhưng cần endpoint riêng nếu UI thực sự cần raw payload. Full-text search hoặc search engine tăng complexity vận hành; chỉ nên dùng khi query pattern và volume chứng minh rằng relational query/index thông thường không đáp ứng được.

## Cách kiểm thử

1. **Security integration test:** user tenant A gửi `tenantId` của tenant B phải nhận 403 và không có dữ liệu B.
2. **Query integration test:** seed dataset lớn, kiểm tra generated SQL chỉ lấy tenant/filter/limit cần thiết thay vì materialize toàn bảng.
3. **Load test:** nhiều concurrent searches; đo p95/p99 latency, allocation, DB CPU và connection-pool pressure.
4. **Sensitive-data test:** response mặc định không chứa raw payload/email/secrets.
5. **Validation test:** invalid/huge date range và oversized search term phải bị reject theo policy.

## Quan sát trong production

Theo dõi request latency theo endpoint, result count, rejected authorization count, DB query duration, rows read/returned, timeout rate, allocation/GC pressure và connection-pool saturation. Dùng distributed tracing để nối HTTP request với database span. Kiểm tra execution plans/query statistics cho các filter phổ biến và alert khi p95/p99 tăng bất thường. Không ghi raw payload hoặc search term nhạy cảm vào telemetry.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ thiết kế composite index nào nếu phần lớn query luôn filter `TenantId`, date range và order theo `CreatedAt`?
2. Nếu business bắt buộc substring search trên JSON payload hàng trăm triệu rows, khi nào bạn tách search workload khỏi OLTP database?
3. Global query filter cho tenant có đủ để thay thế authorization policy không? Vì sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge hôm nay tập trung vào hai boundary thường gây lỗi production nghiêm trọng. Với background jobs, retry và concurrency khiến **idempotency** trở thành yêu cầu thiết kế chứ không phải optimization; database transaction không thể biến một external side effect thành exactly-once. Với multi-tenant read API, **authentication không thay thế authorization**, và vị trí materialization của EF Core query quyết định phần lớn work chạy ở database hay trong memory của application.

## Mẫu tư duy cần nhớ

- Thiết kế retry cùng với idempotency; không xem chúng là hai vấn đề độc lập.
- Với shared mutable state, ưu tiên atomic state transition thay vì `read → check → write` không bảo vệ.
- Phân biệt transaction boundary với external side-effect boundary.
- Authenticate identity, rồi authorize resource/tenant cụ thể.
- Filter, project và limit ở database trước khi materialize; đo execution plan trước khi tối ưu sâu.
