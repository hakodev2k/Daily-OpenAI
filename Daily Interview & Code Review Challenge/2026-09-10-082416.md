# Câu 1 — API không chậm vì SQL nhưng vẫn timeout: connection pooling, pool exhaustion và `OpenAsync` thực sự hoạt động thế nào?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C#, .NET 8, ASP.NET Core, ADO.NET, `Microsoft.Data.SqlClient`, SQL Server, connection pooling, EF Core, async I/O, timeout, transactions, resource lifetime, performance diagnostics

## Bối cảnh

Một ASP.NET Core .NET 8 API dùng EF Core + SQL Server. Phần lớn request chạy dưới 200 ms. Sau khi release một feature mới, production xuất hiện các đợt spike:

- request p95 tăng từ khoảng 250 ms lên 8–15 giây;
- SQL execution plan của các query chính vẫn tương đối ổn;
- database CPU chỉ khoảng 40–50%;
- một số log báo timeout trước cả khi query thực sự chạy;
- thread dump không cho thấy CPU-bound loop rõ ràng;
- application chạy 6 instances;
- mỗi request có thể mở nhiều repository/use-case calls;
- một đoạn code mới bắt đầu transaction rồi gọi external HTTP API trước khi commit;
- một số paths dùng raw `SqlConnection`, một số dùng EF Core;
- connection strings có vài biến thể nhỏ giữa modules, ví dụ khác `Application Name` hoặc thứ tự/giá trị option;
- team đề xuất tăng `Max Pool Size` thật lớn để “hết timeout”.

Chưa biết chính xác số connection đang active/idle, thời gian giữ connection, transaction duration, số pool thực tế trên mỗi process, hoặc connection timeout hiện tại.

## Câu hỏi chính

Hãy giải thích **connection pooling trong ADO.NET/SqlClient hoạt động như thế nào từ lúc code gọi `OpenAsync()` tới lúc `Close`/`Dispose`**, vì sao request có thể timeout dù SQL query bản thân không chậm, và vì sao tăng `Max Pool Size` chưa chắc là fix đúng. Sau đó trình bày cách bạn đo, xác minh pool exhaustion/fragmentation và sửa architecture/resource lifetime.

## Câu hỏi làm rõ nên cân nhắc

1. Timeout xảy ra ở bước mở connection, command execution hay HTTP request tổng thể?
2. Có transaction nào giữ connection trong lúc chờ external API hoặc business work không liên quan DB không?
3. Các connection strings có thực sự identical sau normalization hay application đang tạo nhiều pools riêng?
4. Peak concurrent requests trên mỗi instance là bao nhiêu, và mỗi request giữ bao nhiêu connection đồng thời?
5. Có code path nào quên dispose connection/reader/context hoặc giữ `DbContext` lâu hơn request scope không?

## Gợi ý tư duy

### Gợi ý 1

Tách **query execution time** khỏi **thời gian chờ để lấy/open connection**.

### Gợi ý 2

Connection pool là per-process và được phân tách theo connection configuration; “database còn CPU” không chứng minh application còn connection slot.

### Gợi ý 3

Tìm chỗ connection bị giữ lâu, đặc biệt transaction kéo dài qua network call hoặc resource lifetime vượt khỏi unit of work cần thiết.

## Cấu trúc trả lời đề xuất

1. Xác định loại timeout và request path.
2. Giải thích pool checkout/check-in.
3. Giải thích vì sao pool exhaustion xảy ra.
4. Phân tích pool fragmentation theo connection configuration.
5. Tìm long-held connections/transactions/readers.
6. Thu metrics và trace để verify.
7. Sửa lifetime/transaction boundary trước khi tăng pool.
8. Load test với concurrency thật.
9. Theo dõi sau release.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Khi pooling bật, `Open`/`OpenAsync` thường lấy một connection khả dụng từ pool phù hợp thay vì luôn tạo physical connection mới.
- `Close`/`Dispose` trả connection về pool khi connection còn hợp lệ; không có nghĩa physical socket/session tới SQL Server luôn bị đóng ngay.
- Pool có thể bị cạn nếu concurrent work giữ quá nhiều connections trong thời gian dài.
- Query chạy nhanh không loại trừ việc request chờ connection lâu trước query.
- Giữ transaction/connection qua external HTTP call làm tăng connection hold time và có thể khuếch đại pool pressure mạnh.
- Connection configuration khác nhau có thể tạo pools khác nhau; nhiều biến thể connection string có thể làm capacity bị phân mảnh.
- Tăng `Max Pool Size` chỉ tăng số connection có thể mở; nếu root cause là transaction quá dài, leak/lifetime sai, downstream chậm hoặc DB không chịu thêm concurrency thì việc này chỉ trì hoãn hoặc chuyển bottleneck.

### Điểm cộng

- Phân biệt connection timeout với command timeout và request timeout.
- Nhận ra mỗi App Service/process có pool riêng; scale-out làm tổng số DB connections tăng theo số instances.
- Kiểm tra EF Core `DbContext` scope nhưng không mặc định đổ lỗi cho EF Core nếu raw ADO.NET paths cũng tồn tại.
- Đề xuất giữ DB transaction càng ngắn càng tốt và không bao quanh external network call nếu business semantics không bắt buộc.
- Đề xuất semaphore/admission control ở một số high-cost workflows nếu application concurrency vượt downstream capacity.

### Senior+

- Nhận ra “mở nhiều connection hơn” có thể làm SQL Server blocking/lock contention nặng hơn dù CPU chưa cao.
- Xem pool exhaustion như queueing problem: throughput phụ thuộc arrival rate × connection hold time, không chỉ pool size.
- Đề xuất correlation giữa request trace, DB dependency, connection-open latency và transaction duration.
- Phân tích connection-string fragmentation, credential/identity differences và deployment topology trước khi tune.

## Hướng giải quyết tham khảo

ADO.NET SQL Server pooling giữ các physical connections để tái sử dụng. Khi code gọi `Open`/`OpenAsync`, pooler tìm một connection khả dụng trong pool tương ứng với connection configuration. Nếu có, nó được checkout cho caller; khi caller `Close` hoặc `Dispose`, connection thường được trả về pool để request khác dùng tiếp.

Tài liệu Microsoft mô tả rằng connection pooling mặc định được bật và các connections chỉ được pooled khi configuration phù hợp. Các connection strings/configurations khác nhau có thể tạo pools riêng. Vì vậy hai modules cùng trỏ một database nhưng khác option có thể không chia sẻ cùng pool.

Tài liệu xác minh:

- Microsoft Learn — SQL Server connection pooling (ADO.NET): `https://learn.microsoft.com/dotnet/framework/data/adonet/sql-server-connection-pooling`

Điểm quan trọng là pool capacity không phải throughput miễn phí. Giả sử mỗi instance cho phép N pooled connections và workload giữ mỗi connection trung bình 50 ms thì throughput DB-side có thể cao. Nhưng nếu feature mới mở transaction rồi chờ external API 2–5 giây, connection hold time tăng hàng chục lần. Cùng traffic rate, số concurrent connections cần thiết tăng tương ứng.

Ví dụ anti-pattern:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = await db.Orders
    .SingleAsync(x => x.Id == orderId, ct);

var quote = await pricingClient.GetQuoteAsync(order.Id, ct);

order.Price = quote.Price;
await db.SaveChangesAsync(ct);

await tx.CommitAsync(ct);
```

Nếu HTTP call mất 3 giây thì transaction/connection có thể bị giữ trong toàn khoảng đó, tùy provider/runtime behavior và lúc connection được checkout. Dù query SQL chỉ 20 ms, pool vẫn có thể cạn dưới load.

Thiết kế tốt hơn thường là:

1. đọc dữ liệu cần thiết;
2. release DB work;
3. gọi external API ngoài transaction;
4. mở transaction ngắn để apply state change với concurrency validation nếu cần.

Ví dụ:

```csharp
var snapshot = await db.Orders
    .AsNoTracking()
    .Where(x => x.Id == orderId)
    .Select(x => new { x.Id, x.RowVersion })
    .SingleAsync(ct);

var quote = await pricingClient.GetQuoteAsync(snapshot.Id, ct);

await using var tx = await db.Database.BeginTransactionAsync(ct);

var order = await db.Orders
    .SingleAsync(x => x.Id == snapshot.Id, ct);

// Revalidate state / concurrency assumptions here.
order.Price = quote.Price;

await db.SaveChangesAsync(ct);
await tx.CommitAsync(ct);
```

Đây không phải lúc nào cũng đủ. Nếu business cần atomicity giữa DB và external system thì local SQL transaction vẫn không biến external call thành distributed atomic transaction; cần design khác như idempotent workflow, outbox, compensation hoặc state machine tùy use case.

Kế hoạch điều tra:

- xác định exception/stack trace: timeout ở `OpenAsync`, command hay HTTP request;
- đo active DB connections, connection-open duration và dependency duration;
- tìm transaction duration;
- trace request nào giữ `DbContext`/connection lâu;
- review mọi raw `SqlConnection`, reader và transaction có `await using`/dispose đầy đủ;
- normalize/review connection strings;
- quan sát SQL blocking/waits/connection count;
- load test với peak concurrency trên số instances thật.

Tôi chỉ tăng `Max Pool Size` sau khi chứng minh DB và application thực sự cần/đủ capacity. Nếu pool hiện quá nhỏ so với legitimate bounded concurrency thì tăng có thể đúng; nhưng nếu hold time bất thường là root cause, tune pool trước sẽ che lỗi.

## Mẫu trả lời trong phỏng vấn

“Em sẽ tách query latency khỏi connection acquisition latency. Với SqlClient pooling, `OpenAsync` thường checkout một connection từ pool phù hợp; `Dispose` trả connection về pool chứ không nhất thiết đóng physical connection. Nếu tất cả pooled connections đang bị giữ, request mới có thể chờ và timeout trước khi query chạy.

Feature mới đáng nghi vì transaction bao external HTTP call. Nếu external call mất vài giây thì connection hold time tăng rất mạnh; cùng request rate sẽ cần nhiều concurrent connections hơn. Em cũng kiểm tra connection strings vì khác configuration có thể tạo nhiều pools riêng và fragment capacity.

Em không tăng `Max Pool Size` ngay. Em sẽ trace connection-open latency, transaction duration, active connections, SQL waits và request concurrency; đồng thời review dispose/lifetime. Fix ưu tiên là thu ngắn transaction boundary, không giữ DB connection qua network I/O, normalize connection configuration và load test lại. Chỉ khi legitimate concurrency vẫn vượt pool hiện tại và SQL chịu được additional connections thì em mới tune pool size.”

## Câu hỏi đào sâu

1. Nếu tăng `Max Pool Size` làm timeout giảm nhưng SQL blocking tăng mạnh, bạn giải thích trade-off đó thế nào?
2. Nếu mọi connection đều dispose đúng nhưng pool vẫn cạn, bạn sẽ tìm bottleneck theo hướng nào tiếp?
3. Nếu transaction bắt buộc phải giữ một invariant xuyên qua external call, bạn sẽ thiết kế lại workflow ra sao thay vì giữ SQL transaction vài giây?

## Lỗi trả lời thường gặp

- Kết luận “SQL chậm” chỉ vì request timeout.
- Chỉ tăng pool size mà không đo connection hold time.
- Nhầm `Dispose` với đóng physical DB connection ngay.
- Không xem connection-string variations và multi-instance topology.
- Giữ SQL transaction qua external API để “đảm bảo atomicity” dù hai systems không cùng transaction boundary.

## Thang điểm 0–10

- **0–2:** chỉ đề xuất tăng timeout/pool size.
- **3–4:** biết connection pooling nhưng chưa gắn với hold time và queueing.
- **5–6:** giải thích đúng checkout/check-in, pool exhaustion, transaction lifetime.
- **7–8:** có evidence plan, pool fragmentation, scale-out connection math và remediation hợp lý.
- **9–10:** phân tích queueing/downstream capacity, transaction semantics, blocking impact và đưa recommendation conditional theo measurement.

# Câu 2 — IIS App Pool cứ recycle rồi xuất hiện 503: điều tra incident mà không nhảy thẳng sang “tăng memory”

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET Core hosting, App Pool recycling, process lifecycle, 503 troubleshooting, memory, deployment, Windows Event Log, observability, incident response, production support

## Bối cảnh

Một internal enterprise portal chạy ASP.NET Core sau IIS trên Windows Server. Hệ thống đã ổn định nhiều tháng. Sau một release, user bắt đầu báo:

- thỉnh thoảng login xong bị 503;
- một số request đang chạy bị reset;
- application warm-up mất khoảng 20–30 giây;
- Event Viewer có nhiều sự kiện liên quan application pool recycle nhưng team chưa phân loại trigger;
- process memory tăng dần trong ngày rồi giảm mạnh sau recycle;
- có scheduled recycle lúc 02:00 nhưng incident cũng xảy ra lúc khác;
- một deployment tool cập nhật files trực tiếp vào site directory;
- application có background job chạy trong web process;
- session state hiện còn một phần lưu in-memory;
- server có endpoint health check nhưng monitoring chỉ biết status code, không correlate với recycle reason/process ID;
- team muốn tắt recycle hoàn toàn hoặc nâng private memory threshold.

Chưa biết recycle bị trigger bởi schedule, memory threshold, config/file change, crash, Rapid-Fail Protection, manual action hay deployment behavior.

## Câu hỏi chính

Bạn đang xử lý incident. Hãy trình bày theo thứ tự **business impact → stabilization → evidence → competing hypotheses → verification → root cause → remediation → prevention**. Bạn sẽ phân biệt scheduled recycle, memory-triggered recycle, deployment/config-triggered restart, worker crash và request-queue/503 issues thế nào? Sau đó đề xuất hosting/deployment changes để giảm user impact mà không che root cause.

## Câu hỏi làm rõ nên cân nhắc

1. 503 đến từ HTTP.sys/IIS queue, application process không available, hay reverse-proxy/backend startup failure?
2. Event Viewer/IIS logs ghi recycle reason gì và process ID trước/sau incident là gì?
3. App Pool đang cấu hình periodic restart, memory limit, idle timeout, Rapid-Fail Protection hoặc overlapping recycle ra sao?
4. Deployment tool thay những files/config nào và có app-offline/cutover strategy không?
5. Background jobs/session state có chịu được multi-process overlap hoặc recycle giữa chừng không?

## Gợi ý tư duy

### Gợi ý 1

“Recycle” là symptom/lifecycle event; phải tìm **trigger cụ thể** và user-visible consequence.

### Gợi ý 2

Tách recycle bình thường khỏi crash/fail-fast/rapid failure, rồi correlate với 503 timestamp và process lifetime.

### Gợi ý 3

Deployment, in-memory state và background work có thể làm recycle trở thành correctness issue, không chỉ availability issue.

## Cấu trúc trả lời đề xuất

1. Xác định impact và timeline.
2. Stabilize bằng cách giảm blast radius.
3. Thu IIS logs, Windows Event Logs, process IDs, memory metrics.
4. Lập competing hypotheses cho recycle trigger.
5. Correlate recycle với deployment/config/memory/crash.
6. Kiểm tra startup/warm-up và request draining.
7. Fix root cause.
8. Tách state/background work khỏi fragile process lifetime nếu cần.
9. Cải thiện deployment/cutover.
10. Load/failure test và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định mọi recycle là memory leak hoặc IIS bug.
- IIS có thể recycle App Pool theo nhiều điều kiện cấu hình, bao gồm schedule và memory-related settings; cần đọc recycle reason/evidence.
- Worker process restart làm in-process state mất và có thể ảnh hưởng in-flight/background work.
- 503 cần được phân loại: process unavailable, queue pressure, startup failure, rapid-fail behavior hoặc upstream routing problem.
- Deployment thay files/config có thể trigger restart/recycle behavior; cần correlate exact timestamp.
- Tắt recycle hoàn toàn hoặc tăng memory threshold chỉ là mitigation nếu chưa biết root cause.

### Điểm cộng

- Nhận ra overlapped recycling có thể làm old/new worker coexist trong một khoảng thời gian; code/background job không nên giả định chỉ có một process logic duy nhất nếu hosting behavior cho phép overlap.
- In-memory session state làm recycle trở thành user-experience issue; nên cân nhắc distributed/external session nếu requirement cần survive recycle.
- Background jobs quan trọng không nên phụ thuộc mù vào web-process lifetime nếu cần exactly-once/durable execution.
- Deployment nên dùng artifact-based, reproducible cutover thay vì copy files tùy tiện vào live directory.

### Senior+

- Phân biệt immediate mitigation với root-cause fix: có thể tạm tăng capacity/disable một problematic scheduled trigger nhưng vẫn giữ investigation.
- Xem process memory bằng live heap/dump/perf counters thay vì kết luận từ working set graph đơn lẻ.
- Đề xuất warm-up/readiness strategy để traffic không đổ vào process chưa sẵn sàng.
- Correlate process ID, app version/build ID, recycle reason, request 503 và memory trend trong cùng dashboard/timeline.

## Hướng giải quyết tham khảo

Đầu tiên, tôi tạo incident timeline chính xác: thời điểm user thấy 503, process ID nào đang serve trước đó, lúc nào worker cũ dừng, worker mới start, release nào đang chạy và Windows/IIS event nào xuất hiện cùng thời điểm.

Microsoft IIS documentation cho phép cấu hình recycling theo interval/schedule, request count và memory thresholds; cũng có logging cho recycle events. Vì vậy câu hỏi đầu tiên không phải “memory bao nhiêu?” mà là “IIS ghi nhận recycle reason gì?”.

Tài liệu xác minh:

- Microsoft Learn — IIS Application Pool Recycling Settings: `https://learn.microsoft.com/iis/configuration/system.applicationhost/applicationpools/add/recycling/`

Competing hypotheses tối thiểu:

1. scheduled periodic recycle;
2. memory-triggered recycle;
3. deployment/file/config change dẫn tới application restart;
4. worker process crash/unhandled fatal failure;
5. repeated worker failures dẫn tới Rapid-Fail Protection;
6. HTTP.sys/application-pool queue pressure gây 503;
7. startup/warm-up fail hoặc quá chậm khiến backend unavailable;
8. antivirus/file lock/deployment partial state làm startup lỗi.

Cần evidence để narrow down:

- IIS access logs + status/substatus;
- Windows Event Viewer / WAS/W3SVC events;
- App Pool recycle settings;
- process start/stop timestamps và exit codes;
- deployment audit timestamps;
- application startup logs;
- memory working set/private bytes + managed heap dump/counters nếu memory nghi ngờ;
- request queue length và latency;
- Application Insights/Kibana correlation nếu application telemetry có.

Nếu recycle là scheduled 02:00 nhưng incident 14:20, schedule không giải thích incident đó. Nếu Event Log ghi memory threshold trigger đúng timestamp, memory becomes stronger hypothesis nhưng vẫn phải tìm lý do memory tăng: legitimate cache/live set, allocation pressure, leak/retention, upload/export, native allocation, etc.

Nếu deployment tool copy files vào live site, tôi sẽ xem lại deployment model. Một chiến lược an toàn hơn là build immutable artifact, deploy vào staging directory/site, validate health rồi switch traffic hoặc dùng deployment mechanism có controlled app offline/startup. Mục tiêu là không để users hit một nửa old files + một nửa new files.

Nếu background job nằm trong web process, recycle có thể dừng job giữa chừng hoặc overlap khi worker mới/old cùng tồn tại. Với work quan trọng, job phải idempotent/durable hoặc được chuyển sang Worker Service/scheduler phù hợp tùy requirement; không mặc định “IIS chỉ chạy một copy”.

In-memory session cũng cần xem lại. Nếu user session phải survive worker restart, external session/distributed cache hoặc stateless token-based design có thể phù hợp hơn. Nếu session data không quan trọng, giữ in-process có thể vẫn là lựa chọn đơn giản hơn.

Immediate stabilization có thể là:

- rollback release nếu temporal correlation mạnh;
- tạm giảm traffic/capacity pressure;
- disable một erroneous recycle trigger nếu đã xác minh nó là nguyên nhân;
- tăng warm capacity nếu process startup chậm;
- chuyển background job nguy hiểm sang pause/manual mode trong incident.

Tôi không tắt mọi recycle hoặc tăng memory limit vô hạn vì nếu process thật sự leak/crash thì điều đó chỉ trì hoãn outage lớn hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ dựng timeline trước: 503 timestamp, IIS status/substatus, worker process ID, Event Viewer/WAS events, recycle reason, memory trend và deployment event. Em không gọi đây là memory leak chỉ vì process memory tăng rồi reset sau recycle.

Hypotheses gồm scheduled/memory recycle, deployment-triggered restart, worker crash, Rapid-Fail Protection, queue pressure và slow/failing warm-up. Em sẽ dùng Event Viewer + IIS logs + process telemetry để loại từng hypothesis.

Nếu release copy files trực tiếp vào live directory, em ưu tiên chuyển sang immutable artifact/cutover có health validation. Nếu session/background jobs đang phụ thuộc web-process lifetime, em đánh giá đưa state ra ngoài process và làm jobs idempotent/durable. Tạm thời có thể rollback hoặc chỉnh một recycle threshold đã chứng minh sai, nhưng em không tắt recycle toàn bộ hay chỉ tăng RAM trước khi biết trigger và retention root cause.”

## Câu hỏi đào sâu

1. Nếu recycle reason đúng là private-memory threshold nhưng heap dump không cho thấy managed leak rõ, bạn sẽ điều tra tiếp theo hướng nào?
2. Nếu overlapped recycle giúp giảm downtime nhưng background job chạy hai lần trong khoảng overlap, bạn sửa job hay tắt overlapped recycle? Vì sao?
3. Nếu deployment bắt buộc dùng IIS/Windows Server thêm 2 năm nữa, bạn cải thiện release safety thế nào mà không cần migrate platform ngay?

## Lỗi trả lời thường gặp

- Tắt recycle ngay để “fix”.
- Chỉ nhìn Task Manager rồi kết luận memory leak.
- Không correlate Event Viewer với IIS logs và deployment timeline.
- Bỏ qua in-process session/background jobs khi worker lifecycle thay đổi.
- Mặc định migrate sang Kubernetes/App Service là câu trả lời cho incident IIS.

## Thang điểm 0–10

- **0–2:** chỉ restart IIS/tăng RAM.
- **3–4:** biết xem Event Viewer nhưng thiếu hypothesis-driven investigation.
- **5–6:** phân biệt recycle triggers, 503 classes và deployment effects.
- **7–8:** có stabilization, state/background-job reasoning, rollout improvement và observability.
- **9–10:** đưa ra evidence-based root-cause process, conditional mitigation, process-lifetime semantics và tránh platform rewrite không cần thiết.

# Câu 3 — Multi-tenant activity platform: SQL Server hay Cosmos DB, và partition key nào thực sự phù hợp?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, SQL Server, multi-tenancy, partitioning, data modeling, API design, consistency, RU/cost reasoning, query patterns, hot partitions, transactions, caching, observability, architecture trade-offs

## Bối cảnh

Một SaaS internal-employee platform đang thêm module **Activity Timeline**. Mỗi tenant có 1.000–100.000 users. Hệ thống ghi các event như:

- task created/completed;
- document published;
- approval status changed;
- comment added;
- login/security event;
- integration event.

Dự kiến toàn hệ thống có vài trăm triệu events sau 2 năm. API cần:

- hiển thị timeline mới nhất của một user;
- hiển thị activity của một project/team;
- audit lookup theo tenant + time range;
- retention khác nhau theo event type;
- một số security events cần immutable/auditable hơn activity thông thường;
- writes có burst khi import/batch jobs chạy;
- read traffic chủ yếu là recent events;
- không yêu cầu join phức tạp trên hot path;
- reporting dài hạn có thể đi qua pipeline riêng;
- hệ thống hiện dùng SQL Server cho transactional modules;
- team có kinh nghiệm SQL nhiều hơn Cosmos DB;
- architect đề xuất Cosmos DB với partition key `/tenantId` vì “mọi query đều thuộc tenant”;
- developer khác muốn giữ toàn bộ trong SQL Server vì “đỡ thêm database mới”.

Chưa có số chính xác về event rate theo tenant lớn nhất, cross-project queries, retention size, consistency SLA, regional deployment hoặc cost budget.

## Câu hỏi chính

Bạn hãy quyết định **giữ SQL Server, dùng Cosmos DB, hay hybrid**, đồng thời thiết kế data model/partition strategy, API query patterns, retention, consistency, failure handling, observability và migration/evolution path. Nếu chọn Cosmos DB, hãy phân tích vì sao `/tenantId` có thể tốt ở một số workload nhưng nguy hiểm ở workload khác; nếu chọn SQL Server, hãy giải thích cách bạn tránh để bảng event trở thành bottleneck theo thời gian.

## Câu hỏi làm rõ nên cân nhắc

1. Tenant lớn nhất tạo bao nhiêu events/giây ở steady state và burst?
2. Query hot path chủ yếu là tenant+user, tenant+project hay tenant-wide time range?
3. Security audit events có retention/immutability/compliance khác activity feed không?
4. Có requirement multi-region write/read hoặc very-low-latency global access không?
5. Reporting có cần chạy trực tiếp trên operational store hay có thể đẩy sang analytical store/pipeline?

## Gợi ý tư duy

### Gợi ý 1

Đừng chọn database trước khi liệt kê **access patterns + transaction boundary + scale distribution**.

### Gợi ý 2

Partition key tốt phải vừa hỗ trợ routing/query pattern vừa phân phối storage/throughput đủ đều.

### Gợi ý 3

Một tenant rất lớn có thể biến `/tenantId` thành logical hot spot; nhưng key quá granular như `/eventId` lại làm tenant-wide queries thành cross-partition workload.

## Cấu trúc trả lời đề xuất

1. Clarify workload và consistency requirements.
2. Phân loại event domains/retention.
3. So sánh SQL Server vs Cosmos DB theo access patterns.
4. Nếu Cosmos: chọn partition key/hierarchical key strategy.
5. Nếu SQL: indexing/partitioning/archive strategy.
6. Thiết kế write API và idempotency.
7. Thiết kế read APIs/pagination.
8. Retention/archive/reporting.
9. Failure/retry consistency.
10. Observability/cost.
11. Migration path và criteria đổi quyết định.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định Cosmos DB chỉ vì dữ liệu lớn hoặc SQL chỉ vì team quen.
- Quyết định storage phải dựa trên access patterns, throughput distribution, transaction semantics, operational complexity và cost.
- Với Cosmos DB, partition key quyết định data distribution và request routing; key cardinality/distribution rất quan trọng.
- `/tenantId` đơn giản cho tenant-scoped queries nhưng tenant cực lớn/hot có thể tập trung throughput/storage vào ít logical partitions.
- Chọn `/eventId` cho write distribution tối đa lại làm user/project/tenant queries phải fan out mạnh.
- Security/audit events có thể cần policy khác activity feed; không nhất thiết mọi event type vào một container/table.
- Search/reporting dài hạn không nên mặc định đè operational store.

### Điểm cộng

- Cân nhắc hierarchical partition key, ví dụ tenant + entity/user/project + time bucket khi access pattern phù hợp.
- Dùng stable cursor/keyset pagination thay vì deep offset cho timeline.
- Event write có idempotency key để retry không tạo duplicates ngoài business intent.
- Dùng TTL/retention policy theo event class nếu datastore hỗ trợ và compliance cho phép.
- Nếu SQL: index theo tenant/entity/timestamp, partition/archive strategy và tránh unbounded secondary indexes.

### Senior+

- Nhận ra hierarchical key cũng là trade-off; prefix queries có lợi nhưng exact schema phải dựa trên dominant access path và hottest tenants.
- Tách audit/security stream khỏi product activity nếu consistency/retention/immutability khác biệt.
- Có path để export events sang Blob/Data Lake/analytics thay vì giữ mọi reporting query trên OLTP store.
- Đưa cost/RU, hot partition rate limiting và retry/backoff vào production design.
- Không tạo dual-write SQL + Cosmos trực tiếp trong request nếu không có durable handoff/idempotency.

## Hướng giải quyết tham khảo

Tôi bắt đầu từ access patterns chứ không từ tên database.

### 1. Khi SQL Server có thể vẫn đủ

Nếu event rate vừa phải, deployment single-region, team SQL mạnh, tenant lớn nhất chưa tạo hotspot đáng kể và APIs chủ yếu query recent events theo indexed keys, SQL Server có thể là lựa chọn đơn giản hơn.

Ví dụ schema:

```text
ActivityEvent
- TenantId
- EventId
- ActorUserId
- SubjectType
- SubjectId
- EventType
- OccurredAtUtc
- PayloadJson
- RetentionClass
```

Indexes chỉ phục vụ query thật sự cần:

- `(TenantId, ActorUserId, OccurredAtUtc DESC, EventId)`;
- `(TenantId, SubjectType, SubjectId, OccurredAtUtc DESC, EventId)`;
- audit index riêng nếu cần.

Timeline dùng keyset pagination theo `(OccurredAtUtc, EventId)` thay vì offset rất sâu.

Dữ liệu cũ có thể partition/archive theo time hoặc export sang analytical storage tùy SQL edition/operational model. Không giữ hàng chục indexes chỉ để phục vụ ad-hoc reporting.

### 2. Khi Cosmos DB có lý do mạnh hơn

Cosmos DB hợp lý hơn nếu workload cần horizontal scale lớn, burst throughput cao, predictable key-based routing, document model phù hợp và team chấp nhận operational/cost model RU + partitioning.

Microsoft documentation nhấn mạnh partition key ảnh hưởng trực tiếp tới logical/physical partition distribution. Throughput được phân phối trên physical partitions; hot keys/partitions có thể dẫn tới rate limiting và sử dụng throughput không hiệu quả.

Tài liệu xác minh:

- Microsoft Learn — Partitioning and horizontal scaling in Azure Cosmos DB: `https://learn.microsoft.com/azure/cosmos-db/partitioning`
- Microsoft Learn — Hierarchical partition keys: `https://learn.microsoft.com/azure/cosmos-db/hierarchical-partition-keys`

`/tenantId` có ưu điểm:

- tenant-scoped point/query routing rõ;
- data isolation logic dễ hiểu;
- query toàn tenant không cần scatter toàn container.

Nhưng nếu tenant lớn tạo phần lớn traffic, một tenant có thể trở thành hotspot. Khi đó cần xem dominant query dimension. Một hierarchical strategy có thể là:

```text
TenantId / SubjectId / TimeBucket
```

hoặc:

```text
TenantId / UserId / TimeBucket
```

nhưng chỉ nếu user timeline là primary access pattern. Nếu project timeline cũng quan trọng ngang user timeline, có thể cần denormalized projection riêng hoặc read model khác thay vì ép một partition key phục vụ mọi query.

### 3. Không cố một store phục vụ mọi concern

Tôi có thể tách:

- operational activity feed;
- security/audit events;
- analytical/reporting pipeline.

Security audit có thể cần retention dài hơn, tamper resistance, restricted access và khác SLA. Việc tách không nhất thiết là microservice; có thể chỉ là table/container/storage boundary khác.

### 4. Write path

API nhận event với stable `EventId`/idempotency key. Producer retry không được tạo duplicate logical event.

Nếu event phát sinh từ transactional module SQL Server, tôi tránh dual-write trực tiếp kiểu:

```text
Save business row in SQL
then write Cosmos
```

vì crash giữa hai bước sẽ làm mất event. Thay vào đó, nếu event delivery cần durable, dùng transactional outbox trong SQL rồi background publisher đưa event sang activity store idempotently.

### 5. Read path

- user timeline: `tenant + user + cursor`;
- project timeline: `tenant + project + cursor`;
- audit: `tenant + time/type` với access control riêng;
- reporting dài hạn: analytical projection/export.

Không hỗ trợ arbitrary filters vô hạn trên operational endpoint nếu chúng phá partition/query model.

### 6. Retention

Event classes nên có retention policy rõ. Activity UI có thể chỉ cần 90/180 ngày hot; audit có thể nhiều năm. Cosmos TTL hoặc scheduled archival có thể dùng nếu phù hợp policy. SQL có thể archive by time/partition strategy.

### 7. Observability

Nếu Cosmos:

- RU consumption theo operation/query type;
- rate-limited responses/retries;
- latency p95/p99;
- hot partition distribution;
- cross-partition query rate;
- item size;
- failed/idempotent duplicate writes.

Nếu SQL:

- query duration;
- logical reads;
- index usage;
- blocking/waits;
- table/index growth;
- archive duration;
- connection pool pressure.

### Recommendation

Với dữ liệu hiện tại tôi chưa tự động chọn Cosmos DB. Nếu event volume thực tế vẫn trong khả năng SQL Server và team cần release nhanh, tôi có thể bắt đầu SQL với append-oriented schema + indexes theo access pattern + archive strategy. Đồng thời instrumentation cho tenant event rate/data growth giúp biết khi nào cần move.

Nếu load test hoặc forecast cho thấy vài tenant lớn tạo sustained throughput khiến SQL scaling/cost phức tạp, hoặc product cần multi-region/key-routed document workload, Cosmos có thể đáng giá. Khi đó partition key phải dựa trên hottest access patterns, không chỉ chọn `/tenantId` vì tiện.

## Mẫu trả lời trong phỏng vấn

“Em chưa chọn Cosmos chỉ vì có vài trăm triệu events. Em sẽ hỏi tenant lớn nhất ghi bao nhiêu events/giây, hot reads theo user hay project, retention và multi-region requirement.

Nếu SQL hiện vẫn đáp ứng throughput, team quen SQL và query chủ yếu là tenant+entity+time, em có thể bắt đầu bằng append-only table, composite indexes đúng access pattern, keyset pagination và archive dữ liệu cũ. Đó là option ít operational complexity nhất.

Nếu scale/burst/multi-region thực sự justify Cosmos, em sẽ không mặc định dùng `/tenantId`. Key đó route tenant queries tốt nhưng tenant lớn có thể thành hotspot. Em đánh giá hierarchical partition key hoặc projection riêng theo user/project. Event writes phải idempotent và nếu source transaction nằm ở SQL thì dùng durable outbox thay vì dual-write trực tiếp.

Audit/security events có thể tách retention/access policy khỏi normal activity. Dù chọn store nào, em theo dõi distribution, latency, cost/RU hoặc SQL waits/index growth để có evidence cho lần architecture decision tiếp theo.”

## Câu hỏi đào sâu

1. Nếu 1 tenant chiếm 60% write traffic nhưng business bắt buộc tenant-wide audit query rất nhanh, bạn thiết kế partition/read model thế nào?
2. Nếu Cosmos DB giảm operational scaling pain nhưng team chưa có kinh nghiệm RU/partitioning, chi phí tổ chức đó ảnh hưởng recommendation ra sao?
3. Bạn đề xuất giữ SQL trước; nếu dữ liệu tăng 10x sau 6 tháng, migration path nào giúp tránh big-bang rewrite?

## Lỗi trả lời thường gặp

- Chọn Cosmos chỉ vì “NoSQL scale tốt hơn”.
- Chọn `/tenantId` mà không xem tenant skew/hotspot.
- Dùng `/eventId` rồi bỏ qua chi phí cross-partition timeline queries.
- Dual-write SQL + Cosmos trực tiếp mà không có failure strategy.
- Cho reporting/ad-hoc queries chạy trực tiếp lên operational store vô hạn.

## Thang điểm 0–10

- **0–2:** chọn database theo sở thích/công nghệ mới.
- **3–4:** có nhắc partition key/index nhưng chưa gắn access pattern.
- **5–6:** so sánh đúng SQL/Cosmos, có hot-partition và query-routing reasoning.
- **7–8:** có idempotency/outbox, retention, pagination, observability và hybrid boundaries.
- **9–10:** đưa ra conditional architecture theo measured workload, migration path, cost-of-complexity và không ép một partition model phục vụ mọi use case.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Connection pooling là resource-reuse mechanism; request có thể chờ connection dù SQL query bản thân nhanh.
- Connection hold time và transaction boundary thường quan trọng hơn việc chỉ tăng pool size.
- IIS recycle phải được điều tra theo trigger/evidence; recycle, crash, queue pressure và deployment restart là các failure mode khác nhau.
- In-process session/background jobs phải được thiết kế với process lifecycle thực tế của hosting platform.
- Cosmos DB partition key là architecture decision về data distribution + query routing, không chỉ là một field bắt buộc.
- SQL Server vẫn là lựa chọn tốt nếu workload, team và operational requirements chưa justify thêm distributed datastore complexity.

## Mẫu tư duy cần nhớ

- **Separate resource-acquisition latency from execution latency.**
- **Measure hold time before increasing capacity.**
- **Stabilize first, then prove the recycle/crash trigger with evidence.**
- **Choose partition keys from access patterns and traffic distribution.**
- **Prefer the simplest datastore that satisfies measured requirements.**
