# Câu 1 — ASP.NET Core middleware đọc request body: vì sao downstream nhận body rỗng và memory tăng dưới tải?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, HTTP request pipeline, streams, buffering, memory allocation, cancellation, security

## Bối cảnh

Một ASP.NET Core API thêm middleware để audit JSON request body trước khi controller chạy. Local test với payload nhỏ thường ổn, nhưng production thỉnh thoảng controller nhận model rỗng. Khi một batch client gửi payload vài MB, memory và p99 latency tăng mạnh. Middleware dùng `StreamReader` đọc `HttpRequest.Body`, ghi toàn bộ text vào structured log rồi gọi `_next(context)`.

API có cả endpoint JSON nhỏ và endpoint import lớn. Một số payload chứa PII. Business cần audit metadata và một số field nghiệp vụ, không yêu cầu lưu nguyên body. Chưa có bằng chứng rằng response compression hay database là bottleneck.

## Câu hỏi chính

Hãy giải thích request body stream được tiêu thụ thế nào trong ASP.NET Core pipeline, vì sao downstream model binding có thể thấy body rỗng, buffering thay đổi resource behavior ra sao, và bạn sẽ thiết kế audit middleware để đáp ứng requirement mà không tạo memory/security risk dưới production load?

## Câu hỏi làm rõ nên cân nhắc

1. Middleware hiện chạy trước hay sau routing/authentication và endpoint-specific metadata có sẵn không?
2. Kích thước payload thực tế p50/p95/max là bao nhiêu và endpoint nào cần audit body fields?
3. Audit requirement cần field nào, retention bao lâu và ai được đọc log?
4. Có request streaming/multipart nào đi qua middleware này không?
5. Model binding failure có correlation với payload size, cancellation hay middleware exception không?

## Gợi ý tư duy

### Gợi ý 1

`HttpRequest.Body` là stream; đọc nó thay đổi vị trí/consumption state mà downstream quan sát.

### Gợi ý 2

Buffering có thể cho phép đọc lại, nhưng “đọc toàn bộ vào string” vẫn có allocation, size và sensitive-data consequences.

### Gợi ý 3

Requirement là audit có chọn lọc, không phải sao chép toàn bộ request body vào logging pipeline.

## Cấu trúc trả lời đề xuất

1. Làm rõ audit contract và payload distribution.
2. Giải thích stream consumption/model binding.
3. Xác minh middleware ordering và reproduction.
4. Phân tích buffering/allocation/security.
5. Thu hẹp audit theo endpoint/field.
6. Đặt size/redaction/failure policy.
7. Test large body, cancellation và PII.
8. Đo allocations, p99 và log volume.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Request body không mặc định là một immutable string có thể đọc vô hạn lần.
- Middleware đọc hết body mà không chuẩn bị rewind/replay phù hợp có thể khiến downstream không còn dữ liệu để model bind.
- `EnableBuffering` có thể hỗ trợ đọc lại nhưng không làm việc đọc toàn bộ payload trở nên miễn phí.
- Không log nguyên body khi requirement chỉ cần metadata/selected fields, đặc biệt khi có PII.

### Điểm cộng

- Đề xuất endpoint-specific policy, size cap, redaction và structured audit event.
- Phân biệt buffering stream với materializing thành `string`/object.
- Propagate `RequestAborted` khi API đọc async và xử lý cancellation như expected behavior.

### Senior+

- Đo allocation/GC/LOH và logging sink backpressure thay vì quy memory spike cho một nguyên nhân duy nhất.
- Cân nhắc parse selected fields theo bounded strategy hoặc audit sau model validation/business boundary nếu phù hợp.
- Xem middleware ordering như một phần security: identity/authorization context có thể cần trước audit event, nhưng không được vô tình log secrets.

## Hướng giải quyết tham khảo

Khi middleware đọc `Request.Body`, nó tiêu thụ stream. Nếu downstream kỳ vọng đọc từ đầu mà middleware không thiết lập khả năng đọc lại và reset position theo contract phù hợp, model binding có thể nhận EOF. `EnableBuffering` là một cơ chế ASP.NET Core hỗ trợ đọc request body nhiều lần, nhưng implementation vẫn phải reset stream position và hiểu rằng buffering có resource cost.

Tôi sẽ bắt đầu bằng reproduction có middleware bật/tắt và telemetry theo endpoint/payload size. Sau đó làm rõ audit requirement. Nếu chỉ cần request ID, actor, route, operation, entity ID và vài field, tôi không lưu raw body. Tôi tạo structured audit event ở boundary nơi các field đã được validate, hoặc middleware chỉ áp dụng cho endpoint thật sự cần thiết.

Nếu bắt buộc đọc body trước downstream, tôi dùng API buffering được framework hỗ trợ, giới hạn kích thước, đọc async, reset position và không materialize payload lớn không cần thiết. Với import lớn/streaming, nên có policy khác hoặc không body-log. PII/secrets phải redact/allow-list field; retention/access control của audit store phải được xác định.

Memory spike cần evidence: request sizes, concurrent requests, allocation rate, Gen 2/LOH, GC pause, logging queue/sink latency. Một chuỗi vài MB đồng thời có thể tạo nhiều bản sao nếu stream → string → JSON parse → structured log serialization. Vì vậy fix không chỉ là “rewind body”.

Testing gồm model-binding correctness sau middleware, size boundary, concurrent large requests, cancellation, invalid JSON và security test đảm bảo field cấm không xuất hiện trong logs. Monitoring gồm audit-event rate/size, rejected oversized audit reads, request duration p95/p99, allocation/GC và logging dependency latency.

## Mẫu trả lời trong phỏng vấn

“Trước tiên tôi không coi `Request.Body` như một string có thể đọc lại tùy ý. Middleware đọc stream trước controller có thể tiêu thụ dữ liệu, nên tôi sẽ xác minh middleware ordering và tái hiện model binding với cùng payload. Nếu thực sự cần đọc trước, ASP.NET Core có buffering support, nhưng phải reset position và vẫn phải tính resource cost. Tôi cũng sẽ hỏi audit requirement thật sự cần gì, vì log nguyên body vài MB chứa PII vừa tốn memory/log I/O vừa tạo security risk. Tôi ưu tiên structured audit với allow-list fields, size policy và endpoint-specific behavior. Với incident memory/p99, tôi đo payload distribution, allocation rate, GC/LOH và logging sink latency trước khi kết luận. Cuối cùng tôi test downstream body correctness, concurrent large requests, cancellation và kiểm tra PII không lọt vào log.”

## Câu hỏi đào sâu

1. Nếu compliance bắt buộc lưu raw request cho một endpoint cụ thể, bạn sẽ thiết kế storage/access/retention khác application logs thế nào?
2. Nếu thêm `EnableBuffering` làm lỗi model binding biến mất nhưng p99 vẫn cao, bạn sẽ thu thập evidence gì tiếp theo?
3. Bạn có đồng ý chuyển toàn bộ audit logic vào controller để đơn giản hóa không? Vì sao có hoặc không?

## Lỗi trả lời thường gặp

- Chỉ nói “set `Position = 0`” mà bỏ qua buffering, stream capability và resource cost.
- Log toàn bộ body vì cho rằng audit càng nhiều càng tốt.
- Kết luận memory spike chắc chắn do LOH mà không đo allocations/GC.
- Không phân biệt endpoint nhỏ với import/streaming workload.
- Bỏ qua cancellation và logging sink/backpressure.

## Thang điểm 0–10

- **0–2:** Chỉ biết middleware đọc body, không giải thích stream/downstream behavior.
- **3–4:** Nhận ra cần rewind/buffering nhưng bỏ qua load/security.
- **5–6:** Giải thích đúng mechanism, đưa ra fix an toàn cơ bản và tests.
- **7–8:** Có measurement, endpoint-specific audit, PII policy, cancellation và observability.
- **9–10:** Cân bằng correctness, memory, logging architecture, compliance, failure behavior và chứng minh recommendation bằng telemetry.

# Câu 2 — Cosmos DB RU tăng đột biến dù traffic không đổi

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Cosmos DB, partitioning, query patterns, Azure observability, performance, incident response

## Bối cảnh

Một product catalog API lưu read model trong Azure Cosmos DB. Sau một release, request rate gần như không đổi nhưng RU consumption tăng mạnh, một số requests bị throttling và p99 API latency xấu đi. Team vừa thêm filter theo `brand`, `availability` và sort theo `updatedAt`. Container có partition key hiện hữu nhưng tài liệu nội bộ không nói query mới luôn cung cấp partition-key value hay không.

Không được giả định partition key hiện tại là sai. Chưa biết regression đến từ cross-partition query, index policy, result cardinality, hot partition, SDK behavior hay application retry. Business cần ổn định search/catalog nhanh trước khi tối ưu dài hạn.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào để giảm impact, thu thập evidence và phân biệt các giả thuyết về query/partition/index/retry? Sau khi tìm được nguyên nhân, bạn quyết định sửa query, index, data model hay partition strategy dựa trên tiêu chí gì?

## Câu hỏi làm rõ nên cân nhắc

1. RU tăng ở endpoint/query shape nào và request charge phân bố ra sao?
2. Query mới có truyền partition key hay fan out qua partitions?
3. Throttling tập trung trên một logical partition hay toàn container?
4. Indexing policy có thay đổi cùng release không?
5. SDK retry metrics và application-level retry có thể khuếch đại load không?

## Gợi ý tư duy

### Gợi ý 1

Bắt đầu từ impact và per-operation evidence; tổng RU của container không đủ để kết luận root cause.

### Gợi ý 2

So sánh query shape trước/sau release, request charge, diagnostics và partition distribution.

### Gợi ý 3

“Đổi partition key” là thay đổi data model lớn; chỉ làm sau khi chứng minh access pattern hiện tại không thể đáp ứng hợp lý.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và affected operations.
2. Stabilize: rollback/feature flag/rate-limit query mới nếu phù hợp.
3. So sánh telemetry trước/sau release.
4. Phân tách hypotheses: cross-partition, index, cardinality, hot partition, retries.
5. Reproduce query với representative data.
6. Chọn remediation nhỏ nhất giải quyết root cause.
7. Load/failure test và rollout có kiểm soát.
8. Thiết lập RU/latency/throttling alerts theo operation/partition.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nhảy thẳng tới scale RU hoặc đổi partition key.
- Thu thập request charge/diagnostics theo query/operation và partition distribution.
- Xem query có partition-key equality hay phải fan-out.
- Kiểm tra throttling/retry vì retries có thể kéo dài latency và tăng work.
- Có stabilization plan như rollback/disable filter mới nếu impact nghiêm trọng.

### Điểm cộng

- So sánh result cardinality và index utilization/query metrics nếu tooling/API hiện hành cung cấp evidence phù hợp.
- Phân biệt hot logical partition với tổng capacity thiếu.
- Xem continuation/pagination và projection thay vì trả dữ liệu dư thừa.

### Senior+

- Đánh giá partition strategy từ access patterns, cardinality, write distribution, transaction boundary và future growth, không chỉ một query.
- Cân nhắc read model/materialized projection riêng nếu một access pattern quan trọng xung đột data model hiện tại, thay vì phá primary model ngay.
- Thiết kế performance budget theo RU/request và p95/p99, có canary/feature flag.

## Hướng giải quyết tham khảo

Tôi sẽ ưu tiên ổn định. Nếu regression correlate rõ với release và feature có thể tắt, rollback hoặc feature-flag query mới giúp giảm throttling trong lúc điều tra. Tôi tránh chỉ tăng capacity nếu chưa biết query đang lãng phí RU, dù temporary scaling có thể là stabilization option khi business impact yêu cầu và cost chấp nhận được.

Evidence cần theo operation: request count, RU/request distribution, throttled requests, latency, SDK diagnostics, query text/shape được normalized, partition key presence, result count và retry behavior. So sánh trước/sau release. Nếu query không cung cấp partition key và fan-out, tôi xác minh đó có phải nguyên nhân chính bằng representative execution; nếu một partition nóng, distribution evidence sẽ khác.

Indexing cũng phải được kiểm tra theo query thực tế, đặc biệt filter/sort mới. Tôi không khẳng định một index cụ thể khi chưa xem indexing policy và diagnostics. Tương tự, application retry có thể chồng lên SDK retry và làm incident nặng hơn; cần xem retry count/backoff thay vì suy đoán.

Remediation ưu tiên nhỏ nhất: sửa query để target partition khi business key cho phép, giảm projection/cardinality, pagination hợp lý, điều chỉnh index nếu evidence chỉ ra, hoặc thay API contract/access path. Chỉ cân nhắc repartition/data migration khi partition key hiện tại thật sự không phù hợp với dominant access/write patterns và growth. Nếu hai access patterns xung đột, read model riêng có thể hợp lý nhưng thêm consistency/operations complexity.

Sau fix, tôi load test bằng data distribution gần production, đo RU/request, p95/p99, throttling và retry. Rollout canary/feature flag, dashboard theo endpoint/query shape và alert trên sustained throttling/RU regression.

## Mẫu trả lời trong phỏng vấn

“Vì traffic không đổi nhưng RU tăng sau release, tôi coi query shape mới là giả thuyết mạnh chứ chưa kết luận. Trước tiên tôi giảm impact bằng rollback hoặc tắt filter mới nếu có thể. Sau đó tôi lấy RU/request, throttling, SDK diagnostics và partition distribution theo endpoint, rồi so sánh trước/sau release. Tôi muốn biết query có target partition hay fan-out, result cardinality thay đổi không, index có phục vụ filter/sort không và retry có khuếch đại work không. Nếu chỉ cần sửa query/index thì tôi chọn thay đổi nhỏ đó; đổi partition key là migration lớn và chỉ đáng làm khi access pattern tổng thể chứng minh model hiện tại không phù hợp. Fix phải được load test với production-like distribution và rollout có dashboard RU, p99, 429/retry để chứng minh hiệu quả.”

## Câu hỏi đào sâu

1. Nếu query bắt buộc cross-partition vì business search toàn catalog, bạn sẽ tối ưu theo hướng nào trước khi tạo read model mới?
2. Nếu tăng provisioned capacity làm 429 biến mất, bạn có coi incident đã giải quyết không? Vì sao?
3. Nếu một brand cực lớn tạo hot partition nhưng phần còn lại cân bằng, partition strategy cần được đánh giá lại thế nào?

## Lỗi trả lời thường gặp

- Thấy Cosmos DB chậm là lập tức tăng RU hoặc đổi partition key.
- Chỉ nhìn total RU mà không phân rã theo operation/partition.
- Không kiểm tra retry amplification.
- Đề xuất index chung chung mà không xem query/index policy.
- Không có rollback/stabilization plan trong incident.

## Thang điểm 0–10

- **0–2:** Chỉ đề xuất scale capacity.
- **3–4:** Biết RU/partition nhưng điều tra tuyến tính, thiếu evidence.
- **5–6:** Có stabilization, diagnostics và phân biệt query/index/partition.
- **7–8:** Có competing hypotheses, retry analysis, representative test và rollout plan.
- **9–10:** Ra quyết định data-model/partition bằng access patterns, cost, consistency và operational trade-offs; telemetry chứng minh từng giả thuyết.

# Câu 3 — Thiết kế upload file lớn: proxy qua ASP.NET Core hay direct-to-Blob?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, security, Managed Identity/SAS concepts, large-file streaming, reliability, observability, architecture trade-offs

## Bối cảnh

Một enterprise portal cần cho authenticated users upload tài liệu từ vài MB đến vài GB. Hiện proof-of-concept gửi multipart file qua ASP.NET Core API rồi API copy vào Azure Blob Storage. Product muốn progress indicator, retry khi mạng chập chờn và không muốn App Service memory/throughput trở thành bottleneck. Security yêu cầu user chỉ upload vào phạm vi được cấp, không có permanent storage credential ở browser và file chưa được kiểm tra không được public/download như tài liệu hợp lệ.

Traffic trung bình thấp nhưng có burst. Team đang cân nhắc giữ backend proxy, phát short-lived upload authorization để browser upload trực tiếp, hoặc kết hợp hai cách. Chưa chốt antivirus/content scanning provider và không được giả định một Azure feature cụ thể giải quyết toàn bộ workflow.

## Câu hỏi chính

Hãy thiết kế upload architecture phù hợp, so sánh backend-proxy với direct-to-Blob, xác định authorization/data model/state transitions/failure recovery và giải thích khi nào bạn sẽ chọn giải pháp đơn giản hơn thay vì direct upload.

## Câu hỏi làm rõ nên cân nhắc

1. File size distribution/max và browser/mobile clients nào cần hỗ trợ?
2. Có yêu cầu resumable/chunked upload hay chỉ retry toàn file?
3. File được coi là “accepted” ở thời điểm upload xong hay sau validation/scanning?
4. User có được overwrite/version file không, và ownership được xác định bằng gì?
5. Retention, encryption, legal/audit và download authorization requirements là gì?

## Gợi ý tư duy

### Gợi ý 1

Tách **control plane** (authorization, metadata, state) khỏi **data plane** (file bytes) khi điều đó giảm bottleneck thực sự.

### Gợi ý 2

Direct upload không có nghĩa browser được storage credential dài hạn hoặc quyền ghi tùy ý.

### Gợi ý 3

Upload hoàn tất ở storage chưa đồng nghĩa file đã an toàn/được publish; cần lifecycle rõ ràng.

## Cấu trúc trả lời đề xuất

1. Clarify file/UX/security requirements.
2. Chọn proxy/direct/hybrid dựa trên size và scale.
3. Thiết kế upload session + ownership metadata.
4. Cấp quyền upload scoped, short-lived nếu direct.
5. Xác minh completion và chuyển trạng thái.
6. Validation/scanning trước publish/download.
7. Retry/resume/cleanup orphan uploads.
8. Observability, testing và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Backend vẫn quyết định ai được upload gì, dù bytes đi trực tiếp tới Blob Storage.
- Không cấp permanent account credential cho client.
- Có trạng thái như PendingUpload → Uploaded/Validating → Ready hoặc Rejected.
- File chưa validated không được coi là trusted content.
- Có strategy cho interrupted upload/orphan data và authorization khi download.

### Điểm cộng

- Dùng server-side identity như Managed Identity cho backend khi phù hợp, và scoped short-lived authorization cho client direct upload theo official platform mechanism được project xác minh.
- Metadata record dùng opaque storage key thay vì tin filename/path từ client.
- Chunk/resume chỉ thêm khi file sizes/UX justify complexity.

### Senior+

- Phân tích control-plane/data-plane threat model: token scope, expiry, overwrite, content type, size, replay và object ownership.
- Thiết kế asynchronous validation/scanning có idempotency và quarantine boundary.
- Nêu rõ direct upload giảm App Service bandwidth/connection pressure nhưng tăng client/storage workflow complexity.

## Hướng giải quyết tham khảo

Với file tới vài GB và yêu cầu progress/retry, tôi nghiêng về hybrid/direct data path: client gọi backend tạo upload session; backend authenticate/authorize user, tạo metadata `PendingUpload`, sinh opaque blob key và cấp quyền ghi ngắn hạn chỉ cho object/prefix cần thiết theo cơ chế Azure Storage chính thức phù hợp. Browser không nhận account key/permanent credential.

Client upload bytes trực tiếp và báo completion hoặc backend xác minh storage state. Upload completion chỉ chuyển sang `Uploaded/Validating`; file nằm ở vùng không được phục vụ như trusted content. Một worker/validation flow kiểm tra size/type/signature và security scanning theo provider được chọn. Chỉ sau khi pass mới chuyển `Ready`. Download đi qua authorization/control metadata hoặc một scoped read mechanism; không suy quyền từ việc biết blob URL.

Failure recovery cần upload-session expiry, idempotent completion, cleanup orphan blobs, retry/chunk strategy nếu requirement cần. Nếu traffic thấp và file nhỏ, backend streaming proxy có thể đơn giản hơn: tránh buffer toàn file vào memory, propagate cancellation và stream tới storage. Tôi không chọn direct upload chỉ vì nó “cloud-native”; complexity phải được file size, throughput hoặc scaling requirement biện minh.

Security: allow-list size/type theo business rule nhưng không tin extension/MIME từ client; storage key do server tạo; token/quyền phải least privilege và short-lived; log metadata/correlation thay vì file content/token. Backend dùng Managed Identity thay static storage secret nếu deployment/support matrix cho phép.

Observability gồm upload-session creation/completion, bytes/duration, failed/resumed uploads, validation queue age, rejected reason categories, orphan count, storage dependency failures và end-to-end time-to-ready. Tests gồm authorization, expired/scoped token, large-file retry, interrupted upload, malicious metadata/content và cleanup.

## Mẫu trả lời trong phỏng vấn

“Với vài-GB files tôi sẽ tách authorization khỏi byte transfer. Backend tạo upload session, kiểm tra quyền, tạo opaque blob key và cấp quyền ghi ngắn hạn, scoped; client upload trực tiếp để App Service không phải relay toàn bộ traffic. Nhưng upload xong chưa phải Ready: metadata chuyển qua Uploaded/Validating, file ở quarantine và chỉ được download như trusted content sau validation/scanning. Tôi thiết kế expiry, idempotent completion và cleanup cho upload dở. Backend dùng service identity thay permanent secret khi phù hợp. Nếu thực tế 99% file nhỏ và traffic thấp, streaming proxy có thể đơn giản và đủ tốt; tôi chỉ nhận thêm direct-upload complexity khi measurement/UX requirement biện minh. Tôi sẽ test authorization, interrupted upload, large file, validation failure và theo dõi time-to-ready, failure rate, orphan count.”

## Câu hỏi đào sâu

1. Nếu Product nói direct upload quá phức tạp và traffic chỉ vài chục file/ngày, bạn có giữ proxy không? Điều kiện nào khiến bạn đổi quyết định?
2. Nếu user upload thành công nhưng callback completion bị mất, hệ thống reconcile trạng thái thế nào?
3. Bạn ngăn một upload authorization bị dùng để overwrite file của user khác như thế nào?

## Lỗi trả lời thường gặp

- Cấp storage credential rộng/dài hạn cho browser.
- Coi blob tồn tại là file đã trusted.
- Proxy file lớn nhưng buffer toàn bộ vào memory.
- Không thiết kế orphan cleanup/retry/reconciliation.
- Chọn direct upload mà không thảo luận complexity và traffic thực tế.

## Thang điểm 0–10

- **0–2:** Chỉ chọn một option, thiếu security/failure reasoning.
- **3–4:** Biết direct upload/SAS concept nhưng lifecycle và ownership mơ hồ.
- **5–6:** Có upload session, scoped authorization, validation và retry cơ bản.
- **7–8:** Có threat model, quarantine, reconciliation, observability và proxy/direct trade-offs.
- **9–10:** Recommendation điều kiện hóa theo workload; boundaries, security, failure recovery và operational cost được giải thích rõ, không over-engineer.

# Tổng kết hôm nay

## Kiến thức trọng tâm

Request streams, partitioned databases và large-file storage đều yêu cầu hiểu resource/data boundaries thay vì chỉ gọi API đúng cú pháp. Middleware phải tôn trọng stream lifetime và data sensitivity; Cosmos DB incident phải được điều tra bằng RU/query/partition evidence; upload architecture phải tách authorization, byte transfer và trust lifecycle.

## Mẫu tư duy cần nhớ

- Hiểu ownership/lifetime của resource trước khi thêm buffering hoặc abstraction.
- Stabilize incident trước, rồi dùng evidence để phân biệt competing hypotheses.
- Đừng thay data model lớn khi một query/index fix nhỏ hơn chưa được loại trừ.
- Tách control plane khỏi data plane khi scale/size thực sự biện minh.
- Dữ liệu đã được nhận chưa đồng nghĩa dữ liệu đã được tin cậy.
