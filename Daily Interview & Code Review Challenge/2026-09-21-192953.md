# Code Review Challenge 1 — `Task.WhenAll` dùng chung `DbContext`: tăng tốc giả, lỗi concurrency và transaction không còn như kỳ vọng

**Chủ đề:** C#/.NET, EF Core, async/concurrency, `DbContext`, transaction boundary, SQL Server, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một API nội bộ xác nhận một batch gồm tối đa 100 expense claims. Phiên bản cũ xử lý tuần tự nên một batch lớn mất vài giây. Team tối ưu bằng cách dùng `Task.WhenAll` để xử lý các claim song song.

`ExpenseService` được đăng ký `Scoped`, `AppDbContext` dùng registration mặc định của `AddDbContext`. Mỗi claim cần đọc dữ liệu, cập nhật trạng thái và ghi audit row. Sau thay đổi, staging thỉnh thoảng xuất hiện lỗi kiểu “A second operation was started on this context instance before a previous operation completed”. Có lần batch trả `500` nhưng một số dữ liệu trong database đã thay đổi từ integration khác được gọi trong quá trình xử lý.

Business chưa xác định rõ batch phải **all-or-nothing** hay cho phép partial success. Bạn phải review mà không tự giả định requirement này.

## Đoạn code cần review

```csharp
public sealed class ExpenseService
{
    private readonly AppDbContext _db;
    private readonly IEmployeeDirectory _directory;
    private readonly ILogger<ExpenseService> _logger;

    public ExpenseService(
        AppDbContext db,
        IEmployeeDirectory directory,
        ILogger<ExpenseService> logger)
    {
        _db = db;
        _directory = directory;
        _logger = logger;
    }

    public async Task ApproveBatchAsync(
        IReadOnlyCollection<Guid> claimIds,
        CancellationToken cancellationToken)
    {
        await using var transaction =
            await _db.Database.BeginTransactionAsync(cancellationToken);

        var tasks = claimIds.Select(id => ApproveOneAsync(id, cancellationToken));
        await Task.WhenAll(tasks);

        await _db.SaveChangesAsync(cancellationToken);
        await transaction.CommitAsync(cancellationToken);
    }

    private async Task ApproveOneAsync(Guid claimId, CancellationToken ct)
    {
        var claim = await _db.ExpenseClaims
            .SingleAsync(x => x.Id == claimId, ct);

        var manager = await _directory.GetManagerAsync(claim.EmployeeId, ct);

        claim.Status = ExpenseStatus.Approved;
        claim.ApprovedBy = manager.Id;
        claim.ApprovedAtUtc = DateTime.UtcNow;

        _db.AuditLogs.Add(new AuditLog
        {
            EntityId = claim.Id,
            Action = "ExpenseApproved",
            CreatedAtUtc = DateTime.UtcNow
        });

        _logger.LogInformation("Approved expense {ClaimId}", claim.Id);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong concurrency và EF Core usage.
2. Xác định reliability/performance concerns, đặc biệt với external dependency và transaction lifetime.
3. Giải thích production impact và failure windows.
4. Ưu tiên findings theo severity thay vì chỉ liệt kê style issues.
5. Đề xuất implementation/design phù hợp cho cả hai khả năng: all-or-nothing và partial success.
6. Giải thích test strategy.
7. Nêu production telemetry cần có để chứng minh bản sửa hoạt động.

## Câu hỏi gợi mở

1. Các task trong `Task.WhenAll` đang chia sẻ những mutable resources nào?
2. Transaction local có bao phủ được `_directory.GetManagerAsync` không?
3. Điều gì xảy ra nếu request bị cancel sau khi external dependency đã được gọi cho 60/100 claims?
4. Nếu hai requests cùng approve một claim, code hiện tại bảo vệ business invariant bằng cách nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính không phải `Task.WhenAll` tự thân, mà là parallel operations trên một dependency có lifetime/state không hỗ trợ concurrent use.

### Gợi ý 2

Phân biệt transaction của relational database với side effects hoặc reads từ external systems; sau đó xác định transaction nên ngắn đến mức nào.

## Kết quả code review tham khảo

### Critical — Chạy nhiều EF Core operations song song trên cùng `DbContext`

**Vấn đề:** `ApproveOneAsync` được chạy đồng thời nhưng tất cả task dùng cùng `_db` scoped instance.  
**Tại sao xảy ra:** `DbContext` là mutable unit-of-work và không được thiết kế để nhiều operations chạy đồng thời trên cùng instance.  
**Ảnh hưởng production:** Có thể throw khi operations overlap; request thất bại không ổn định theo timing và load.  
**Cách sửa:** Không parallelize operations trên cùng context. Nếu thực sự cần parallel independent units, mỗi unit cần context riêng và transaction semantics phải được thiết kế lại; không tạo context riêng chỉ để “né lỗi” mà bỏ qua business atomicity.

### High — Transaction boundary bao gồm network call tới external dependency

**Vấn đề:** Database transaction được mở trước toàn bộ `_directory.GetManagerAsync` calls.  
**Tại sao xảy ra:** Code giữ transaction trong khi chờ I/O không thuộc database transaction.  
**Ảnh hưởng production:** Transaction kéo dài, giữ locks/resources lâu hơn, tăng contention, timeout/deadlock risk khi dependency chậm.  
**Cách sửa:** Thu thập/validate external data trước khi mở transaction nếu semantics cho phép; giữ database transaction chỉ quanh database work cần atomicity.

### High — Chưa định nghĩa atomicity của batch

**Vấn đề:** Implementation ngầm chọn một transaction cho cả batch nhưng requirement chưa nói batch phải all-or-nothing.  
**Tại sao xảy ra:** Technical implementation đang quyết định business semantics.  
**Ảnh hưởng production:** Batch 100 items có thể rollback toàn bộ vì một item lỗi, hoặc team có thể vô tình chuyển sang per-item commits và tạo partial success mà client không hiểu.  
**Cách sửa:** Chốt API contract: atomic batch hoặc per-item outcome. Thiết kế response, transaction và retry theo contract đó.

### High — Concurrent requests có thể cùng approve một claim

**Vấn đề:** Không có optimistic concurrency token, conditional update hoặc business-state guard đủ mạnh.  
**Tại sao xảy ra:** Hai requests có thể đọc cùng state rồi cùng cập nhật/audit.  
**Ảnh hưởng production:** Duplicate audit, last-write-wins hoặc transition không hợp lệ.  
**Cách sửa:** Dùng concurrency token/row version hoặc conditional update phù hợp; validate allowed state transition và xử lý conflict rõ ràng.

### High — External dependency không nằm trong local transaction

**Vấn đề:** Transaction không thể rollback điều gì xảy ra ở `_directory`. Trong scenario hiện tại đây là read, nhưng design dễ bị hiểu sai nếu integration sau này có side effect.  
**Tại sao xảy ra:** Local database transaction chỉ điều phối resource của database connection/transaction tương ứng.  
**Ảnh hưởng production:** Team có thể có false confidence về atomicity khi thêm external writes.  
**Cách sửa:** Ghi rõ boundary. Với external side effects, dùng idempotency/workflow/outbox/compensation khi requirement cần, không dựa vào local transaction.

### Medium — Parallel fan-out không có concurrency limit

**Vấn đề:** Tối đa 100 external calls có thể khởi chạy gần đồng thời cho mỗi request.  
**Tại sao xảy ra:** `Task.WhenAll` trên toàn bộ collection không có bounded concurrency.  
**Ảnh hưởng production:** Nhiều concurrent batches có thể gây connection pressure, downstream throttling và latency amplification.  
**Cách sửa:** Nếu external lookups cần song song, dùng bounded concurrency dựa trên measured capacity; cân nhắc batch API nếu directory hỗ trợ.

### Medium — Cancellation semantics chưa được thiết kế theo batch contract

**Vấn đề:** Caller cancellation được truyền vào mọi operation và transaction.  
**Tại sao xảy ra:** Đây có thể đúng cho request-scoped work, nhưng nếu server đã nhận một durable business command thì việc client disconnect không nhất thiết nên hủy workflow.  
**Ảnh hưởng production:** Behavior phụ thuộc timing và có thể khó giải thích cho client.  
**Cách sửa:** Chốt acceptance semantics. Với synchronous atomic API, cancellation có thể rollback. Với durable async workflow, tách processing lifetime khỏi HTTP request sau khi command được durable-accept.

### Medium — Logging nói “Approved” trước khi commit

**Vấn đề:** Log success được ghi khi entity mới chỉ thay đổi trong change tracker.  
**Tại sao xảy ra:** `SaveChanges` và commit xảy ra sau tất cả tasks.  
**Ảnh hưởng production:** Incident investigation có thể thấy “Approved” dù transaction rollback.  
**Cách sửa:** Log trạng thái chính xác như `approval staged`, hoặc emit success telemetry sau commit; dùng correlation/batch ID.

### Medium — Hai lần lấy thời gian tạo timestamp không nhất quán

**Vấn đề:** `ApprovedAtUtc` và audit timestamp lấy riêng cho từng item.  
**Tại sao xảy ra:** Clock được gọi trực tiếp nhiều lần.  
**Ảnh hưởng production:** Thường nhỏ nhưng gây khó deterministic testing và có thể không phù hợp nếu business cần một batch timestamp.  
**Cách sửa:** Inject `TimeProvider` hoặc capture timestamp theo semantics mong muốn.

## Phiên bản đề xuất

Ví dụ dưới đây giả định requirement là **atomic batch**, directory lookup là read-only và có thể thực hiện trước transaction. Nếu requirement cho phép partial success, nên chuyển sang per-item unit-of-work và trả outcome từng item thay vì dùng một transaction lớn.

```csharp
public sealed class ExpenseService
{
    private readonly AppDbContext _db;
    private readonly IEmployeeDirectory _directory;
    private readonly TimeProvider _timeProvider;

    public async Task ApproveBatchAsync(
        IReadOnlyCollection<Guid> claimIds,
        CancellationToken ct)
    {
        if (claimIds.Count == 0) return;
        if (claimIds.Count > 100)
            throw new ArgumentOutOfRangeException(nameof(claimIds));

        var ids = claimIds.Distinct().ToArray();

        var claims = await _db.ExpenseClaims
            .Where(x => ids.Contains(x.Id))
            .ToListAsync(ct);

        if (claims.Count != ids.Length)
            throw new InvalidOperationException("One or more claims do not exist.");

        if (claims.Any(x => x.Status != ExpenseStatus.Pending))
            throw new InvalidOperationException("Batch contains a non-pending claim.");

        var managerByEmployee = new Dictionary<Guid, Manager>();
        foreach (var employeeId in claims.Select(x => x.EmployeeId).Distinct())
        {
            managerByEmployee[employeeId] =
                await _directory.GetManagerAsync(employeeId, ct);
        }

        var now = _timeProvider.GetUtcNow().UtcDateTime;

        await using var tx = await _db.Database.BeginTransactionAsync(ct);

        foreach (var claim in claims)
        {
            claim.Status = ExpenseStatus.Approved;
            claim.ApprovedBy = managerByEmployee[claim.EmployeeId].Id;
            claim.ApprovedAtUtc = now;

            _db.AuditLogs.Add(new AuditLog
            {
                EntityId = claim.Id,
                Action = "ExpenseApproved",
                CreatedAtUtc = now
            });
        }

        try
        {
            await _db.SaveChangesAsync(ct);
            await tx.CommitAsync(ct);
        }
        catch (DbUpdateConcurrencyException)
        {
            await tx.RollbackAsync(CancellationToken.None);
            throw new InvalidOperationException(
                "At least one claim changed while the batch was being approved.");
        }
    }
}
```

Entity cần concurrency token phù hợp, ví dụ SQL Server `rowversion`, nếu đó là strategy được chọn. Nếu directory có batch endpoint thì nên ưu tiên giảm network round trips thay vì fan-out vô hạn.

Với **partial success**, một hướng khác là mỗi claim có unit-of-work/context riêng, bounded concurrency nếu cần, và API trả kết quả từng claim. Khi đó không được quảng bá toàn batch là atomic.

## Giải thích thiết kế sau khi sửa

External lookup được đưa ra ngoài database transaction để transaction không chờ network I/O. EF operations trên một context diễn ra tuần tự. Batch state transition được validate trước commit và concurrency conflict được coi là business conflict cần xử lý, không phải lỗi ngẫu nhiên để retry mù quáng.

Điểm quan trọng nhất là implementation phải đi sau atomicity requirement. Nếu Product yêu cầu “99 items vẫn approve dù 1 item lỗi”, một transaction cho toàn batch là sai dù code technically sạch. Nếu requirement yêu cầu all-or-nothing, per-item parallel contexts lại phá transaction boundary mong muốn.

## Trade-offs

Atomic batch đơn giản cho caller nhưng transaction lớn hơn và một conflict có thể rollback toàn bộ. Partial success tăng throughput/fault isolation nhưng API/result model, retry và reconciliation phức tạp hơn. Sequential external lookups an toàn về load nhưng có thể tăng latency; bounded concurrency hoặc batch endpoint chỉ nên dùng sau khi đo latency/quota thực tế.

## Cách kiểm thử

1. **Integration/concurrency test:** hai requests approve cùng claim; chỉ một transition hợp lệ và conflict được trả rõ ràng.
2. **Failure-path test:** directory fail ở item giữa batch; xác nhận không có database mutation nếu atomic contract được chọn.
3. **Database test:** `SaveChanges`/commit fail; không có partial database commit và log/response không báo success sai.
4. **Load test:** nhiều batch 100 items; đo SQL lock duration, connection pool, directory concurrency, p95/p99.
5. **Cancellation test:** cancel trước transaction và trong database operation; xác nhận behavior đúng contract.

## Quan sát trong production

Theo dõi batch size, duration, directory dependency latency/error rate, SQL duration, transaction duration, concurrency-conflict count, connection-pool pressure, request cancellation, batch success/failure và số claims affected. Correlate bằng batch/request ID. Log phải phân biệt staged mutation với committed business outcome.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào `IDbContextFactory<TContext>` là lựa chọn hợp lý cho parallel independent work, và khi nào nó che giấu một transaction-design problem?
2. Nếu directory lookup mất 2 giây nhưng database transaction chỉ mất 50 ms, bạn sẽ chứng minh optimization nào đáng làm trước?
3. Nếu batch phải partial-success, API contract và retry semantics nên thay đổi thế nào?

# Code Review Challenge 2 — Elasticsearch index mới làm search “mất sản phẩm” sau deploy dù database vẫn đúng

**Chủ đề:** Elasticsearch, search mapping, aliases, reindexing, eventual consistency, CI/CD, rollback, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một product catalog dùng SQL Server làm source of truth và Elasticsearch phục vụ search. Team cần đổi mapping của `sku` từ analyzed text sang exact-match-friendly field và thêm analyzer mới cho `name`.

Pipeline deploy hiện tạo index mới, chạy một job copy documents rồi đổi application setting `SEARCH_INDEX` sang index mới. Trong staging mọi thứ ổn với vài nghìn products. Production có vài triệu products và catalog vẫn nhận update trong lúc reindex.

Sau một deployment, search không trả một số products vừa được sửa trong khoảng thời gian reindex. Rollback application về version trước cũng không khôi phục kết quả search như kỳ vọng.

## Đoạn code cần review

```csharp
public async Task RebuildAsync(CancellationToken ct)
{
    var newIndex = $"products-{DateTime.UtcNow:yyyyMMddHHmm}";

    await _elastic.Indices.CreateAsync(newIndex, c => c
        .Mappings(m => m.Properties<ProductDocument>(p => p
            .Text(t => t.Sku)
            .Text(t => t.Name, x => x.Analyzer("catalog_name")))), ct);

    var page = 0;
    const int size = 1000;

    while (true)
    {
        var products = await _db.Products
            .OrderBy(x => x.Id)
            .Skip(page * size)
            .Take(size)
            .Select(x => new ProductDocument
            {
                Id = x.Id,
                Sku = x.Sku,
                Name = x.Name,
                Price = x.Price,
                UpdatedAtUtc = x.UpdatedAtUtc
            })
            .ToListAsync(ct);

        if (products.Count == 0)
            break;

        await _elastic.BulkAsync(b => b
            .Index(newIndex)
            .IndexMany(products), ct);

        page++;
    }

    await _configurationStore.SetAsync("SEARCH_INDEX", newIndex, ct);
}
```

Application search code đọc `SEARCH_INDEX` khi process start và query trực tiếp index name đó.

## Nhiệm vụ của ứng viên

1. Xác định correctness/data-consistency problems trong rebuild flow.
2. Xác định performance/reliability/deployment concerns ở production scale.
3. Giải thích tại sao documents có thể bị stale hoặc mất update dù reindex loop hoàn tất.
4. Ưu tiên issues và đề xuất migration strategy an toàn hơn.
5. Đưa ra corrected design/configuration cho cutover và rollback.
6. Giải thích test strategy.
7. Nêu telemetry cần theo dõi trong production.

## Câu hỏi gợi mở

1. Snapshot dữ liệu mà từng page đọc có nhất quán trong toàn bộ rebuild không?
2. Điều gì xảy ra với product được update sau khi page của nó đã được copy nhưng trước cutover?
3. Rollback application binary có đồng nghĩa rollback search index không?
4. `Skip/Take` có đặc điểm gì khi dataset lên tới hàng triệu rows?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **cutover correctness** giữa source of truth đang thay đổi và một derived index được build trong thời gian dài.

### Gợi ý 2

Hãy nghĩ theo ba phase: bulk backfill → catch-up changes → atomic routing switch; sau đó thiết kế rollback độc lập với application binary.

## Kết quả code review tham khảo

### Critical — Rebuild không capture updates xảy ra trong thời gian backfill

**Vấn đề:** Mỗi row được đọc một lần theo page; update xảy ra sau khi row đã được copy sẽ không tự xuất hiện trong new index trước cutover.  
**Tại sao xảy ra:** Reindex là một scan kéo dài trong khi SQL vẫn nhận writes, nhưng không có change capture/catch-up phase.  
**Ảnh hưởng production:** Search sau cutover có thể trả stale document hoặc thiếu business update dù SQL đúng.  
**Cách sửa:** Thiết kế high-water mark/change feed/outbox/CDC-like catch-up phù hợp với hệ thống: capture mốc rebuild, backfill, replay changes phát sinh trong rebuild, xác minh lag về ngưỡng chấp nhận rồi mới cutover.

### High — Cutover bằng application setting không phải routing switch đáng tin cậy cho mọi instance

**Vấn đề:** App đọc setting khi process start; đổi setting không đảm bảo mọi running instances chuyển đồng thời.  
**Tại sao xảy ra:** Configuration propagation và process lifecycle khác với atomic search routing.  
**Ảnh hưởng production:** Một số instances có thể query old index, số khác query new index; behavior phụ thuộc deployment/restart.  
**Cách sửa:** Dùng Elasticsearch alias làm stable logical name và đổi alias atomically theo supported API; application query alias ổn định.

### High — Rollback binary không rollback data routing

**Vấn đề:** Search target là deployment state độc lập với application artifact.  
**Tại sao xảy ra:** Pipeline không lưu rõ previous index/cutover state.  
**Ảnh hưởng production:** Rollback app vẫn có thể trỏ tới index lỗi hoặc instances khác nhau dùng target khác nhau.  
**Cách sửa:** Giữ previous index trong retention window; rollback bằng alias switch có kiểm soát và compatibility check, không chỉ redeploy binary.

### High — Bulk response không được kiểm tra per-item failures

**Vấn đề:** Code await `BulkAsync` nhưng không xác minh từng indexing operation thành công.  
**Tại sao xảy ra:** Bulk request có thể có partial failures.  
**Ảnh hưởng production:** Rebuild có thể tiếp tục và cutover sang index thiếu documents.  
**Cách sửa:** Kiểm tra bulk response/items, classify retryable/permanent failures, retry có bound và fail rebuild nếu completeness invariant không đạt.

### High — Mapping `sku` vẫn là `text` cho use case exact match

**Vấn đề:** Requirement nói cần exact-match-friendly field nhưng snippet vẫn map `Sku` bằng `.Text`.  
**Tại sao xảy ra:** Mapping design không phản ánh query semantics.  
**Ảnh hưởng production:** Exact lookup/filter/sort/aggregation có thể không hoạt động như business mong muốn hoặc dùng analyzed tokens.  
**Cách sửa:** Xác định query requirements; thường `keyword` hoặc multi-field `text` + `keyword` phù hợp hơn cho SKU, nhưng phải dựa trên actual search behavior.

### High — Analyzer được tham chiếu nhưng lifecycle/settings của analyzer không xuất hiện

**Vấn đề:** Mapping dùng `catalog_name` nhưng code không chứng minh analyzer đã được định nghĩa trong index settings.  
**Tại sao xảy ra:** Mapping và settings migration bị tách rời.  
**Ảnh hưởng production:** Index creation có thể fail hoặc behavior khác dự kiến tùy configuration thực tế.  
**Cách sửa:** Version index template/settings/mappings cùng migration và validate trước backfill.

### Medium — Offset pagination bằng `Skip(page * size)` không scale tốt

**Vấn đề:** Deep offset tăng chi phí ở SQL và rebuild kéo dài khi dataset lớn.  
**Tại sao xảy ra:** Mỗi page sau phải bỏ qua ngày càng nhiều rows.  
**Ảnh hưởng production:** Tăng DB load, kéo dài migration window và do đó tăng lượng changes cần catch-up.  
**Cách sửa:** Dùng keyset pagination theo stable unique key, ví dụ `Id > lastId ORDER BY Id`, hoặc snapshot/export mechanism phù hợp.

### Medium — Không có validation gate trước cutover

**Vấn đề:** Code switch ngay khi loop kết thúc.  
**Tại sao xảy ra:** Không kiểm tra document count, sampled queries, failed items, mapping, catch-up lag hoặc business invariants.  
**Ảnh hưởng production:** Index technically “built” nhưng không production-ready vẫn được promote.  
**Cách sửa:** Thêm validation phase và explicit promotion gate.

### Medium — Index name chỉ có precision đến phút

**Vấn đề:** Hai rebuild trong cùng phút có thể collision.  
**Tại sao xảy ra:** Naming scheme không đảm bảo uniqueness.  
**Ảnh hưởng production:** Retry/deployment automation có thể đụng index đang tồn tại.  
**Cách sửa:** Dùng deployment/build ID hoặc timestamp có đủ uniqueness; lưu metadata về schema version.

### Medium — Không có cleanup/retention policy

**Vấn đề:** Old indices có thể tích lũy hoặc bị xóa quá sớm nếu cleanup thủ công.  
**Tại sao xảy ra:** Rebuild lifecycle chưa gồm retention.  
**Ảnh hưởng production:** Tốn storage hoặc mất rollback target.  
**Cách sửa:** Giữ N previous healthy indices hoặc retention theo thời gian sau cutover; chỉ cleanup khi rollback window đóng.

## Phiên bản đề xuất

Pseudo-code dưới đây tập trung vào workflow; cơ chế capture changes phải chọn theo architecture hiện có, không mặc định một sản phẩm cụ thể.

```csharp
public async Task RebuildAsync(CancellationToken ct)
{
    var buildId = Guid.NewGuid().ToString("N");
    var newIndex = $"products-v3-{buildId}";
    const string alias = "products-read";

    var watermark = await _changeLog.GetCurrentPositionAsync(ct);

    await CreateIndexWithVersionedSettingsAndMappingsAsync(newIndex, ct);

    long lastId = 0;
    while (true)
    {
        var products = await _db.Products
            .AsNoTracking()
            .Where(x => x.Id > lastId)
            .OrderBy(x => x.Id)
            .Take(1000)
            .Select(x => new ProductDocument
            {
                Id = x.Id,
                Sku = x.Sku,
                Name = x.Name,
                Price = x.Price,
                UpdatedAtUtc = x.UpdatedAtUtc
            })
            .ToListAsync(ct);

        if (products.Count == 0)
            break;

        await IndexBatchAndRequireSuccessAsync(newIndex, products, ct);
        lastId = products[^1].Id;
    }

    var caughtUpTo = watermark;
    while (true)
    {
        var changes = await _changeLog.ReadAfterAsync(caughtUpTo, 1000, ct);
        if (changes.Count == 0)
            break;

        await ApplyChangesIdempotentlyAsync(newIndex, changes, ct);
        caughtUpTo = changes[^1].Position;
    }

    await ValidateIndexAsync(newIndex, ct);
    await _elastic.Indices.UpdateAliasesAsync(a => a
        .Actions(actions => actions
            .Remove(r => r.Alias(alias).Index("products-*"))
            .Add(add => add.Alias(alias).Index(newIndex))), ct);

    await RecordSuccessfulCutoverAsync(newIndex, caughtUpTo, ct);
}
```

Đây là design sketch, không phải khẳng định rằng một `_changeLog` như trên đã tồn tại. Nếu hệ thống chưa có reliable change log/outbox/CDC mechanism thì đó là phần phải thiết kế. Một lựa chọn khác là dual-write có kiểm soát trong migration window, nhưng dual-write trực tiếp cũng có failure windows và cần reconciliation.

Mapping nên phản ánh query semantics, ví dụ conceptually:

```json
{
  "sku": { "type": "keyword" },
  "name": {
    "type": "text",
    "analyzer": "catalog_name",
    "fields": {
      "raw": { "type": "keyword" }
    }
  }
}
```

Chỉ dùng cấu hình cụ thể này nếu exact SKU và raw-name behavior thực sự cần thiết.

## Giải thích thiết kế sau khi sửa

Search index là derived read model, không phải source of truth. Rebuild an toàn cần biết “new index đại diện dữ liệu tới thời điểm nào”. Backfill tạo baseline; change replay đưa baseline tiến tới current state; validation chứng minh index đủ điều kiện; alias switch tách routing khỏi application deployment.

Rollback cũng là data-plane operation. Giữ previous healthy index trong rollback window cho phép alias quay lại nhanh nếu schema/query compatibility vẫn phù hợp. Nếu writes/search-document schema giữa hai app versions không tương thích, rollback plan phải kiểm tra compatibility thay vì giả định alias switch luôn đủ.

## Trade-offs

Change capture/outbox tăng storage và operational complexity nhưng đóng failure window mà simple scan không xử lý được. Alias-based versioned indices tốn thêm disk trong migration/rollback window nhưng làm cutover và rollback rõ ràng hơn. Keyset pagination yêu cầu stable ordering key nhưng tránh deep-offset cost. Stronger validation làm deployment chậm hơn nhưng giảm xác suất promote index không hoàn chỉnh.

## Cách kiểm thử

1. **Integration test:** update product sau khi backfill đã đi qua product đó nhưng trước cutover; new index sau catch-up phải có version mới nhất.
2. **Failure-path test:** bulk request có một số item fail; rebuild không được promote cho đến khi xử lý/đánh dấu failure đúng policy.
3. **Load/database test:** vài triệu synthetic rows; so sánh keyset với offset pagination và theo dõi DB load/migration duration.
4. **Deployment validation:** chạy sampled exact SKU queries, text queries, document-count/invariant checks trước alias switch; sau switch smoke test qua application.
5. **Rollback test:** switch sang new index rồi rollback alias về previous healthy index; xác minh app version và mapping/query compatibility.

## Quan sát trong production

Theo dõi indexing throughput, bulk item failure rate, rebuild duration, SQL query latency/load, change-log lag, document-count delta, alias target, search zero-result rate, search latency p95/p99 và sampled freshness lag giữa SQL `UpdatedAtUtc` với indexed document. Alert khi cutover xảy ra mà catch-up lag hoặc validation vượt threshold đã định nghĩa.

## Câu hỏi phỏng vấn mở rộng

1. Nếu không có CDC/outbox/change log, bạn có những migration options nào và failure window của từng option là gì?
2. Nếu mapping mới không backward-compatible với query của app version cũ, rollback strategy phải thay đổi ra sao?
3. Vì sao document count bằng nhau vẫn chưa đủ để chứng minh hai indices tương đương về correctness?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `Task.WhenAll` không biến một stateful dependency thành thread-safe; concurrency phải được thiết kế theo lifetime và transaction boundary của dependency.
- Database transaction nên bảo vệ database invariants và thường cần giữ ngắn; network calls bên ngoài transaction tạo failure/latency boundaries riêng.
- Batch atomicity là business/API requirement, không nên bị quyết định ngầm bởi cách viết code.
- Search index là derived data; production reindex cần xử lý concurrent changes, validation, cutover và rollback chứ không chỉ copy hết rows.
- Application deployment và data/search routing là hai state machines khác nhau; rollback binary không mặc nhiên rollback data plane.

## Mẫu tư duy cần nhớ

- Xác định **shared mutable state** trước khi parallelize.
- Chốt **atomicity/delivery contract** trước khi chọn transaction strategy.
- Với migration dữ liệu đang thay đổi: **backfill → catch up → validate → atomic cutover → retain rollback target**.
- Đừng coi request-level success là đủ; kiểm tra **partial failures** ở bulk/distributed operations.
- Measure migration/runtime behavior và test failure windows, không chỉ happy path.
