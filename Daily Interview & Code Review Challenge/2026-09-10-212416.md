# Câu 1 — Configuration đã đổi nhưng service vẫn dùng giá trị cũ: `IOptions<T>`, `IOptionsSnapshot<T>` và `IOptionsMonitor<T>` thực sự khác nhau ở đâu?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, dependency injection, configuration, Options Pattern, `IOptions<T>`, `IOptionsSnapshot<T>`, `IOptionsMonitor<T>`, service lifetime, configuration reload, validation, production verification

## Bối cảnh

Một ASP.NET Core .NET 8 application có chức năng gọi external pricing API. Team đưa timeout và feature switch vào configuration:

```json
{
  "Pricing": {
    "TimeoutSeconds": 10,
    "EnableFallback": true
  }
}
```

Options được đăng ký:

```csharp
builder.Services
    .AddOptions<PricingOptions>()
    .BindConfiguration("Pricing")
    .Validate(o => o.TimeoutSeconds > 0 && o.TimeoutSeconds <= 60)
    .ValidateOnStart();
```

Một singleton service đang inject `IOptions<PricingOptions>`:

```csharp
public sealed class PricingClient
{
    private readonly PricingOptions _options;

    public PricingClient(IOptions<PricingOptions> options)
    {
        _options = options.Value;
    }

    public TimeSpan GetTimeout() =>
        TimeSpan.FromSeconds(_options.TimeoutSeconds);
}
```

Trong production, operations thay `TimeoutSeconds` từ 10 xuống 3 bằng configuration provider có khả năng reload. Một số thành phần application quan sát được giá trị mới nhưng `PricingClient` vẫn dùng 10 giây cho tới khi process restart.

Một developer đề xuất thay tất cả `IOptions<T>` bằng `IOptionsMonitor<T>`. Developer khác nói `IOptionsSnapshot<T>` “luôn đọc config mới ở mỗi lần access”. Hệ thống còn có:

- HTTP request-scoped handlers;
- một `BackgroundService` chạy liên tục;
- configuration lấy từ nhiều providers với precedence khác nhau;
- deployment nhiều application instances;
- một số options thay đổi an toàn lúc runtime, nhưng một số options như endpoint/credential mode cần rollout có kiểm soát;
- chưa có telemetry cho effective configuration version;
- không muốn log secrets.

## Câu hỏi chính

Hãy giải thích cách Options Pattern materialize và cung cấp values cho `IOptions<T>`, `IOptionsSnapshot<T>` và `IOptionsMonitor<T>`, đặc biệt liên quan tới DI lifetime, caching và configuration change notifications. Vì sao `PricingClient` trong ví dụ có thể tiếp tục dùng giá trị cũ ngay cả khi provider reload được? Sau đó đề xuất cách chọn options abstraction cho request-scoped code, singleton/background code và runtime-changeable settings, đồng thời giải thích validation, thread-safety, multi-instance consistency và cách verify behavior trong production.

## Câu hỏi làm rõ nên cân nhắc

1. Configuration provider nào đang thay đổi giá trị, và provider đó có phát change token/reload notification hay không?
2. Requirement thực sự là thay đổi có hiệu lực ngay, theo request mới, hay chỉ sau controlled restart/deployment?
3. `PricingClient` có phải singleton thật không, và nó giữ `options.Value` một lần hay access abstraction ở mỗi operation?
4. Khi config thay đổi giữa chừng, một request đang chạy có cần giữ một consistent snapshot hay được phép thấy value mới giữa các bước?
5. Các instances có nhận configuration update cùng lúc hay có eventual propagation, và business có chấp nhận khoảng lệch đó không?

## Gợi ý tư duy

### Gợi ý 1

Đừng chỉ reasoning từ interface name. Hãy xem **lifetime của consumer**, thời điểm options object được tạo/cached và việc consumer có copy `Value` vào field hay không.

### Gợi ý 2

“Configuration source thay đổi” và “application component quan sát được thay đổi” là hai bước khác nhau. Provider phải hỗ trợ reload/change notification, và abstraction phía consumer phải phù hợp.

### Gợi ý 3

Dynamic configuration là một consistency problem. Một value có thể reload được về kỹ thuật nhưng vẫn không nên thay đổi tức thì nếu nó ảnh hưởng invariants hoặc resource lifetime.

## Cấu trúc trả lời đề xuất

1. Xác định provider và reload semantics.
2. Xác định DI lifetime của từng consumer.
3. Giải thích caching/materialization của ba Options abstractions.
4. Chỉ ra stale-value mechanism trong code hiện tại.
5. Phân loại settings thành static vs runtime-changeable.
6. Chọn abstraction và access pattern tương ứng.
7. Thiết kế validation/change handling.
8. Xử lý multi-instance propagation và failure behavior.
9. Test reload deterministically.
10. Instrument effective non-secret configuration state.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IOptions<T>` phù hợp với options không cần refresh theo runtime change; consumer không nên kỳ vọng nó phản ánh mọi change notification.
- `IOptionsSnapshot<T>` được thiết kế cho scoped consumption và tạo/cached value theo scope, thường phù hợp khi request mới cần thấy config mới nhưng một request nên dùng một snapshot nhất quán.
- `IOptionsMonitor<T>` hỗ trợ theo dõi changes và phù hợp với singleton consumers cần quan sát configuration updates, miễn configuration provider thực sự phát change notifications.
- Trong code ví dụ, `PricingClient` copy `options.Value` vào `_options` ở constructor. Dù đổi abstraction sau đó, nếu consumer tiếp tục copy value một lần ở singleton constructor thì value vẫn có thể bị “đóng băng” theo lifetime của service.
- Không phải mọi provider hoặc mọi nguồn config đều reload theo cùng semantics; phải verify provider cụ thể.
- Runtime config change cần validation và failure policy rõ. Không nên áp dụng một invalid update rồi để application ở trạng thái nửa đúng nửa sai.
- Nhiều instances có thể quan sát update ở thời điểm khác nhau; “hot reload” không tự tạo distributed atomic configuration.

### Điểm cộng

- Với `IOptionsMonitor<T>`, có thể đọc `CurrentValue` tại operation boundary hoặc dùng `OnChange` để cập nhật một immutable local state đã validate.
- Không thực hiện expensive/reentrant work tùy tiện ngay trong change callback; tách change observation khỏi resource reconfiguration nếu cần.
- Nếu setting điều khiển `HttpClient` timeout, cân nhắc timeout ở request/policy boundary thay vì recreate client thiếu kiểm soát.
- Không log API keys/secrets khi quan sát effective configuration; chỉ log version/hash hoặc safe non-secret fields.
- Có test provider thay đổi config rồi phát reload, sau đó xác minh behavior của singleton và scoped consumers.

### Senior+

- Nhận ra config reload là một form của state transition: cần định nghĩa atomicity ở cấp options object, backward compatibility và rollback khi new value không usable.
- Tách settings thành dynamic knobs và deployment-time configuration. Endpoint topology, credential strategy hoặc schema-dependent settings có thể cần controlled rollout thay vì live mutation.
- Với multi-instance system, nếu requirement đòi tất cả nodes chuyển cùng lúc, Options Pattern một mình không cung cấp distributed coordination; cần deployment/config orchestration hoặc version gate phù hợp.
- Tránh để một operation đọc `CurrentValue` nhiều lần nếu change giữa chừng có thể tạo inconsistent decision; capture value một lần ở operation boundary khi consistency quan trọng.

## Hướng giải quyết tham khảo

Điểm đầu tiên là phân biệt **configuration reload** với **options lifetime**.

`IOptions<T>` thường được dùng cho cấu hình ổn định trong lifetime của process. Nếu consumer inject `IOptions<PricingOptions>` rồi lấy `Value`, nó không phải abstraction dành cho việc phản ứng liên tục với runtime changes.

`IOptionsSnapshot<T>` là scoped. Trong web application, một request scope mới có thể nhận materialized value mới sau khi configuration thay đổi, trong khi các lần access trong cùng scope dùng snapshot/cached value của scope đó. Vì vậy nó không phù hợp để inject trực tiếp vào singleton `BackgroundService`.

`IOptionsMonitor<T>` là singleton-friendly và có `CurrentValue`/`OnChange`. Nó có thể quan sát options invalidation khi underlying configuration provider phát change token.

Code hiện tại còn có một yếu tố quan trọng hơn:

```csharp
public PricingClient(IOptions<PricingOptions> options)
{
    _options = options.Value;
}
```

Nếu `PricingClient` là singleton, `_options` chỉ được gán khi singleton được tạo. Đổi registration sang `IOptionsMonitor<PricingOptions>` nhưng vẫn làm:

```csharp
_options = monitor.CurrentValue;
```

trong constructor thì vẫn chỉ capture một object tại thời điểm khởi tạo.

Nếu timeout được phép thay đổi runtime và mỗi outbound call có thể lấy effective setting mới, một design đơn giản là:

```csharp
public sealed class PricingClient
{
    private readonly IOptionsMonitor<PricingOptions> _options;

    public PricingClient(IOptionsMonitor<PricingOptions> options)
    {
        _options = options;
    }

    public async Task<PricingResult> GetPriceAsync(
        PricingRequest request,
        CancellationToken cancellationToken)
    {
        var options = _options.CurrentValue; // capture once for this operation

        using var timeoutCts = CancellationTokenSource
            .CreateLinkedTokenSource(cancellationToken);
        timeoutCts.CancelAfter(TimeSpan.FromSeconds(options.TimeoutSeconds));

        return await SendAsync(
            request,
            options.EnableFallback,
            timeoutCts.Token);
    }
}
```

Capture `CurrentValue` một lần ở operation boundary tránh tình huống timeout đọc value A nhưng fallback decision lại đọc value B sau một change giữa operation.

Với request-scoped business handler, nếu semantics mong muốn là mỗi request có một consistent configuration snapshot, `IOptionsSnapshot<PricingOptions>` có thể hợp lý:

```csharp
public sealed class PriceRequestHandler
{
    private readonly PricingOptions _options;

    public PriceRequestHandler(IOptionsSnapshot<PricingOptions> options)
    {
        _options = options.Value;
    }
}
```

Ở đây việc capture trong constructor là phù hợp vì handler/scoped service chỉ sống trong request scope.

Tôi cũng không biến mọi setting thành hot-reload chỉ vì framework hỗ trợ. Ví dụ:

- timeout, feature percentage hoặc non-critical threshold có thể là dynamic;
- database migration mode, credential source hoặc breaking endpoint contract có thể cần deployment-time change;
- một setting thay đổi resource graph có thể cần coordinated recycle.

Validation cần chạy cho values được materialize sau change. Nếu dynamic update không hợp lệ, application cần behavior đã định nghĩa trước: giữ last-known-good, reject change ở source, hoặc fail controlled tùy criticality; không nên silently sử dụng invalid state.

Trong hệ thống nhiều instances, tôi thêm telemetry không nhạy cảm như:

```text
instance_id
pricing_config_version
pricing_timeout_seconds
fallback_enabled
config_reload_success_total
config_reload_failure_total
last_reload_timestamp
```

Nếu config chứa secret, log version/reference chứ không log value.

Testing nên cover:

1. start với timeout 10;
2. thay provider value thành 3;
3. trigger reload;
4. verify singleton monitor-based operation mới dùng 3;
5. verify request scope cũ giữ snapshot nếu đó là desired semantics;
6. request scope mới dùng 3;
7. invalid update bị xử lý theo failure policy;
8. concurrent requests trong lúc reload không thấy partially-mutated object.

Điểm quyết định không phải interface nào “xịn hơn”, mà là **lifetime + consistency semantics + reload capability của provider**.

## Mẫu trả lời trong phỏng vấn

“Em sẽ kiểm tra cả configuration provider lẫn lifetime của consumer. `IOptions<T>` phù hợp với config ổn định. `IOptionsSnapshot<T>` là scoped nên hợp với request mới cần nhận snapshot mới. `IOptionsMonitor<T>` phù hợp cho singleton/background service cần quan sát changes.

Trong code này vấn đề còn rõ hơn: singleton `PricingClient` copy `options.Value` vào field ở constructor, nên value bị capture theo lifetime của singleton. Nếu timeout được phép đổi runtime, em inject monitor và capture `CurrentValue` một lần ở đầu mỗi operation, không đọc nhiều lần giữa operation.

Em cũng xác minh provider thực sự phát reload notification. Với multi-instance deployment em không giả định tất cả node chuyển cùng millisecond. Nếu requirement cần coordinated switch thì phải giải quyết ở deployment/config orchestration, không phải chỉ Options Pattern.

Cuối cùng em validate dynamic values, định nghĩa failure policy, test reload thật và chỉ log effective non-secret config/version để production có thể chứng minh node nào đang dùng cấu hình nào.”

## Câu hỏi đào sâu

1. Nếu `IOptionsMonitor<T>.CurrentValue` thay đổi giữa hai dòng trong một business operation, bạn thiết kế thế nào để operation vẫn nhất quán?
2. Một teammate muốn dùng `IOptionsMonitor<T>` cho mọi setting, kể cả database endpoint và credential mode, để tránh restart. Bạn phản biện ra sao?
3. Nếu 10 App Service instances nhận config update lệch nhau 20–30 giây nhưng business yêu cầu switch feature atomically, Options Pattern có đủ không? Bạn bổ sung cơ chế gì?

## Lỗi trả lời thường gặp

- Nói `IOptionsSnapshot<T>` đọc file/config source lại ở mỗi property access.
- Cho rằng chỉ đổi interface sang `IOptionsMonitor<T>` là đủ dù singleton vẫn capture value một lần.
- Không kiểm tra provider có support reload notification hay không.
- Hot-reload secrets/settings quan trọng mà không nghĩ tới consistency và rollback.
- Log toàn bộ configuration để debug, vô tình lộ secrets.

## Thang điểm 0–10

- **0–2:** chỉ biết “Monitor tự reload”.
- **3–4:** phân biệt sơ bộ ba interfaces nhưng chưa liên hệ DI lifetime/caching.
- **5–6:** giải thích đúng scoped snapshot, monitor changes và stale capture trong singleton.
- **7–8:** có operation-level consistency, validation, provider verification và production telemetry.
- **9–10:** reasoning rõ dynamic config như distributed state transition, phân loại setting theo rollout semantics và không nhầm local reload với cluster-wide atomicity.

# Câu 2 — Cùng một release nhưng chỉ một số IIS nodes trả 500: artifact, configuration hay database migration đã phá rolling deployment?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, TeamCity, Octopus Deploy, CI/CD, ASP.NET Core/.NET, SQL Server, rolling deployment, artifact immutability, configuration drift, schema migration, backward compatibility, rollback, observability, incident response

## Bối cảnh

Một enterprise management portal chạy trên 6 Windows Server nodes sau load balancer. Application được build bằng TeamCity và deploy qua Octopus Deploy tới IIS theo rolling deployment.

Release `2026.09.10.4` gồm:

- application artifact mới;
- thay đổi một environment variable liên quan tới feature behavior;
- SQL migration đổi một số columns và indexes;
- code mới đọc một field theo schema mới;
- health endpoint hiện chỉ trả `200 OK` nếu process khởi động được, chưa kiểm tra critical dependencies.

Ngay sau deployment:

- khoảng 15–25% requests trả HTTP 500 trong 12 phút;
- refresh cùng URL có lúc thành công, có lúc fail;
- CPU/memory toàn cluster bình thường;
- load balancer health vẫn thấy tất cả nodes healthy;
- Application Insights cho thấy failures tập trung ở 2 instance names nhưng không hoàn toàn 100%;
- SQL Server không có outage tổng thể;
- Octopus dashboard báo deployment successful;
- một operator nói “cùng commit nên tất cả node chắc chắn giống nhau”;
- một developer muốn rollback application ngay;
- developer khác muốn chạy thêm migration sửa schema ngay trên production;
- chưa xác minh exact artifact hash, config snapshot, deployment step ordering, migration history hoặc assembly version trên từng node;
- business đang có giao dịch quan trọng nên ưu tiên giảm lỗi nhanh nhưng không được làm mất dữ liệu.

Không giả định trước root cause là migration. Artifact drift, stale IIS worker process, configuration drift, partial rollout, schema incompatibility hoặc dependency behavior đều là hypotheses hợp lệ cho tới khi có evidence.

## Câu hỏi chính

Bạn đang on-call. Hãy trình bày cách xử lý incident từ business impact đến stabilization, cách chứng minh các nodes đang chạy artifact/config/schema-compatible state nào, cách phân biệt deployment success với application correctness, và cách quyết định rollback hay roll-forward khi database migration có thể không backward-compatible. Sau đó đề xuất release design để loại sự cố kiểu này trong tương lai.

## Câu hỏi làm rõ nên cân nhắc

1. 500 failures correlate chính xác với node, route, user flow hay database operation nào?
2. Database migration được chạy một lần trước rollout, trong rollout hay từ mỗi application node khi startup?
3. Schema change có destructive operation như rename/drop/change-nullability không, và old/new binaries có cùng hoạt động được trên intermediate schema không?
4. Octopus đang deploy cùng một immutable package ID/hash tới mọi target hay có build/package step xảy ra lại theo target/environment?
5. Load balancer có khả năng drain/remove từng node nhanh không, và hiện có bao nhiêu healthy capacity nếu loại hai nodes nghi ngờ?

## Gợi ý tư duy

### Gợi ý 1

Đầu tiên hãy giảm blast radius. Khi lỗi correlate với một số nodes, routing/draining có thể là stabilization an toàn hơn việc lập tức sửa database.

### Gợi ý 2

“Pipeline successful” chỉ chứng minh các deployment steps báo thành công theo checks hiện tại; nó không chứng minh artifact, configuration và schema tạo thành một compatible runtime state.

### Gợi ý 3

Rollback binary chỉ an toàn nếu schema hiện tại vẫn backward-compatible với binary cũ. Deployment và database evolution phải được thiết kế cùng nhau.

## Cấu trúc trả lời đề xuất

1. Xác định user/business impact và error budget.
2. Correlate failure theo node/version/request.
3. Stabilize bằng drain/traffic control nếu đủ capacity.
4. Capture evidence trước khi thay đổi thêm.
5. So sánh artifact hash, assembly version, config version và migration state.
6. Phân tích competing hypotheses.
7. Xác định compatibility matrix giữa old binary, new binary và schema.
8. Chọn rollback hoặc roll-forward có điều kiện.
9. Verify bằng canary/smoke tests và telemetry.
10. Redesign migration/release flow để phòng tái diễn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Bắt đầu bằng impact và stabilization, không bắt đầu bằng “rerun deployment”.
- Dùng instance correlation để xác định failures có gắn với specific nodes hay không; nếu có và capacity cho phép, drain/remove nodes lỗi để giảm user impact.
- Xác minh artifact bằng package/version/hash hoặc assembly metadata; “same Git commit” không đủ nếu pipeline có mutable artifacts hoặc environment-specific build.
- Xác minh effective configuration trên từng node bằng safe metadata/version, không chỉ nhìn desired configuration trong deployment tool.
- Xác minh migration history và actual schema, không giả định migration step thành công đồng nghĩa tất cả code versions đều compatible.
- Không rollback application khi chưa biết old binary có chạy được với schema mới hay không.
- Không chạy ad-hoc destructive SQL để “fix nhanh” mà chưa có diagnosis, backup/rollback strategy và review.
- Health/readiness phải phản ánh khả năng serve critical traffic, không chỉ process alive.

### Điểm cộng

- Thu request correlation ID, instance name, release version, config version và database command/error category trong structured telemetry.
- So sánh failed vs successful nodes: package hash, web.config/environment variables, process start time, app pool worker PID, assembly informational version, machine-level overrides.
- Kiểm tra stale worker process/App Pool recycle hoặc locked files nếu deployment thay file nhưng worker chưa thực sự chạy binary mới.
- Dùng expand-and-contract database migration để old/new application versions cùng chạy trong rolling window.
- Tách schema migration ownership khỏi arbitrary app startup nếu multiple nodes có thể race migration.

### Senior+

- Xây explicit compatibility matrix:

```text
             Schema N    Schema N+1-expanded    Schema N+2-contracted
App N           yes             yes                    maybe no
App N+1         maybe           yes                    yes
```

- Chỉ contract/drop old schema sau khi old binary không còn trong fleet và rollback window đã qua.
- Dùng immutable artifact promote qua environments; không rebuild cùng source commit cho từng environment.
- Thêm deployment verification dựa trên live instance metadata + synthetic business transaction, không chỉ HTTP liveness.
- Nhận ra rollback là một product capability cần được thiết kế, không phải thao tác mặc định luôn khả dụng.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng việc chứng minh blast radius. Application Insights đã gợi ý hai instance names có failure concentration, nên query theo:

```text
timestamp
operation_Id / correlation_id
cloud_RoleInstance
release_version
route
status_code
exception_type
sql_dependency
```

Nếu 2 nodes tạo phần lớn 500 và 4 nodes còn lại đủ capacity, hành động ổn định đầu tiên có thể là **drain hai nodes lỗi khỏi load balancer**, thay vì lập tức chạm database. Mục tiêu là giảm user impact trong khi giữ evidence.

Sau đó lập một per-node state table:

```text
Node | Package hash | Assembly version | Config version | Worker start | Health | Failure rate
```

Tôi kiểm tra package artifact từ TeamCity/Octopus phải là cùng immutable package, ví dụ cùng package ID và checksum. Nếu pipeline rebuild artifact cho từng target thì “same commit” vẫn có thể cho output khác do dependency resolution, generated files hoặc build-time config.

Tiếp theo kiểm tra effective config trên node. Không log secrets; có thể expose protected diagnostics cho:

```text
release=2026.09.10.4
config_version=cfg-381
schema_compatibility=N,N+1
feature_x=true
```

Nếu desired variable trong Octopus là `true` nhưng worker process chưa recycle hoặc machine-level/environment override đang giữ `false`, deployment UI alone không đủ.

Database là phần rủi ro nhất. Tôi lấy migration history và actual schema. Giả sử migration rename:

```text
Orders.LegacyCode -> Orders.ExternalCode
```

và new binary chỉ đọc `ExternalCode`, trong khi old binary chỉ đọc `LegacyCode`. Nếu migration drop/rename destructive ngay lập tức, rolling deployment tạo một khoảng mà old/new versions không thể cùng chạy an toàn.

Trong trường hợp đó, rollback new binary về old có thể làm toàn hệ thống fail nếu schema cũ đã bị drop. Trước khi rollback phải trả lời:

- old binary có compatible với current schema không?
- migration có reversible mà không mất data không?
- có data writes mới mà downgrade không hiểu không?
- restoration point/RPO/RTO thế nào?

Một safer evolution thường là expand-and-contract.

**Release A — Expand**

```sql
ALTER TABLE Orders ADD ExternalCode nvarchar(100) NULL;
```

Application version mới có thể dual-read/dual-write hoặc backfill có kiểm soát. Old app vẫn dùng `LegacyCode`.

**Release B — Migrate traffic/data**

- backfill;
- verify counts/checksums/business invariants;
- chuyển reads sang `ExternalCode`;
- giữ old column trong rollback window.

**Release C — Contract**

- chỉ drop old column khi không còn old binaries và rollback contract đã thay đổi có chủ đích.

Health check cũng cần cải thiện. Liveness có thể chỉ nói process sống. Readiness/traffic eligibility nên phản ánh critical capability cần thiết để serve request, ví dụ schema compatibility check hoặc critical dependency check với timeout chặt, nhưng không biến health endpoint thành một expensive full business transaction.

Release flow tương lai:

1. TeamCity build một immutable artifact duy nhất.
2. Promote đúng artifact đó qua environments.
3. Run compatibility-safe migration theo explicit step.
4. Deploy canary/first node.
5. Verify artifact/config metadata + synthetic request.
6. Tiếp tục rolling only khi SLO/error metrics ổn.
7. Auto/pause rollout nếu 5xx tăng.
8. Contract schema ở release riêng sau rollback window.

Monitoring nên alert theo release + instance, không chỉ cluster aggregate, vì aggregate có thể che một node lỗi.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng rollback hay chạy thêm SQL. Trước tiên em correlate 500 với instance/release và nếu failures tập trung ở hai nodes, em drain chúng nếu cluster còn capacity để giảm user impact.

Sau đó em chứng minh runtime state từng node: immutable package hash, assembly version, effective non-secret config, worker start time và migration/schema version. Deployment tool báo successful không có nghĩa application state compatible.

Database quyết định khả năng rollback. Nếu migration destructive khiến old binary không chạy được trên schema mới, rollback binary có thể làm incident nặng hơn. Em lập compatibility matrix rồi mới chọn rollback hoặc roll-forward.

Về lâu dài em dùng immutable artifact và expand-and-contract migration để old/new versions cùng tồn tại trong rolling window. Canary phải chạy synthetic business check, telemetry phải có instance + release + config version, và rollout nên pause tự động khi error rate tăng. Schema contract/drop chỉ làm sau khi rollback window kết thúc.”

## Câu hỏi đào sâu

1. Nếu package hash và config giống nhau trên cả 6 nodes nhưng chỉ 2 nodes fail, bạn điều tra tầng IIS/Windows/runtime/dependency nào tiếp theo?
2. Nếu migration đã drop column cũ nhưng rollback application là yêu cầu từ incident commander, bạn cần chứng minh điều gì trước khi đồng ý hoặc từ chối?
3. Một teammate đề xuất để mỗi app instance tự chạy EF Core migrations khi startup để “đơn giản pipeline”. Bạn đánh giá rủi ro và trường hợp nào có thể chấp nhận?

## Lỗi trả lời thường gặp

- Tin `deployment successful` đồng nghĩa release healthy.
- Rollback binary ngay mà không kiểm tra schema compatibility.
- Rerun deployment nhiều lần làm mất evidence ban đầu.
- Chỉ nhìn CPU/memory cluster aggregate, bỏ qua per-instance failures.
- Build lại artifact cho từng environment rồi vẫn gọi đó là immutable deployment.

## Thang điểm 0–10

- **0–2:** chỉ nói restart IIS hoặc rollback.
- **3–4:** biết kiểm tra logs/nodes nhưng chưa reasoning về artifact/config/schema compatibility.
- **5–6:** có stabilization, per-node evidence và rollback safety check.
- **7–8:** có immutable artifacts, expand-and-contract, canary, health/readiness và telemetry theo release.
- **9–10:** xem deployment như distributed state transition, xây compatibility matrix và thiết kế rollback/roll-forward dựa trên data/schema invariants thay vì thao tác pipeline máy móc.

# Câu 3 — Optimizely CMS cho website toàn cầu: traditional rendering, headless React hay hybrid với Akamai edge caching?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, CMS architecture, React.js, ASP.NET Core, content modeling, headless architecture, Akamai/CDN, caching, SEO engineering, Core Web Vitals, external APIs, security, editorial workflow, observability, deployment, architecture trade-offs

## Bối cảnh

Một công ty đang rebuild global marketing website. Editorial team dùng Optimizely CMS và cần:

- khoảng 30 thị trường/ngôn ngữ;
- page types + reusable content blocks;
- editor preview trước khi publish;
- marketing pages phải crawl/index tốt;
- Core Web Vitals là KPI quan trọng;
- một số pages có product availability lấy từ external product API;
- header có trạng thái đăng nhập nhưng phần lớn page content là public;
- Akamai được dùng làm CDN/edge cache;
- traffic có burst lớn khi chạy campaign;
- content editors mong publish article rồi thấy live trong vài phút;
- product data thay đổi thường xuyên hơn editorial content;
- security team không muốn expose CMS management APIs không cần thiết ra Internet;
- engineering team có kinh nghiệm ASP.NET Core và React nhưng không muốn tăng số runtime services nếu lợi ích không rõ;
- chưa chốt traditional server rendering từ Optimizely, fully headless React SPA, server-rendered React framework, hay hybrid composition.

Business hỏi một câu tưởng như đơn giản: “Headless hiện đại hơn, vậy có nên dùng headless cho toàn bộ site không?”

## Câu hỏi chính

Hãy thiết kế kiến trúc phù hợp cho website này và so sánh ít nhất ba hướng: traditional CMS rendering, fully headless frontend và hybrid. Trình bày requirements/assumptions bạn cần chốt, boundaries giữa CMS content và product/runtime data, caching/CDN strategy, preview/publishing behavior, SEO/performance, security, failure degradation, observability, deployment và cost of complexity. Kết luận bằng recommendation có điều kiện thay vì mặc định chọn kiến trúc phức tạp nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Editors cần WYSIWYG/on-page preview chính xác tới mức nào, và preview có phải hoạt động với unpublished content + product data hay không?
2. Personalization yêu cầu ở edge/server/client là gì, hay header login state chỉ là một nhỏ client-side island?
3. Content SLA sau publish là bao lâu và có bắt buộc purge ngay tất cả 30 markets không?
4. Product availability là critical để render page hay có thể degrade thành “check availability”/cached stale data khi external API lỗi?
5. Team có operational capability vận hành thêm frontend SSR runtime/build pipeline riêng hay ưu tiên một ASP.NET Core deployment đơn giản?

## Gợi ý tư duy

### Gợi ý 1

“Headless” giải coupling và channel flexibility, nhưng cũng tạo thêm preview, routing, cache invalidation, deployment và observability problems. Hãy định lượng lợi ích trước.

### Gợi ý 2

Không phải mọi data trên page có cùng freshness. Editorial content, product availability và user-specific state nên có caching/ownership khác nhau.

### Gợi ý 3

SEO/performance không được quyết định chỉ bằng framework name. Hãy reasoning từ HTML delivery, JavaScript cost, caching, image strategy, Core Web Vitals và origin dependency.

## Cấu trúc trả lời đề xuất

1. Chốt editorial, SEO, scale, freshness và personalization requirements.
2. Phân loại content/data theo owner và freshness.
3. So sánh traditional, headless và hybrid.
4. Chọn rendering boundary.
5. Thiết kế CDN/cache keys, TTL, purge và stale strategy.
6. Thiết kế product API integration/failure behavior.
7. Thiết kế preview/publish flow.
8. Security boundary và credential flow.
9. Deployment/rollback + observability.
10. Nêu điều kiện làm recommendation thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không chọn headless chỉ vì “modern”. Architecture phải phục vụ requirements và team capability.
- Tách **editorial content**, **dynamic product data** và **user-specific state**; không dùng một cache policy cho tất cả.
- Public marketing HTML nên tối ưu crawlability, canonical URLs, redirects, metadata, structured data và predictable status codes.
- CDN/Akamai caching cần explicit `Cache-Control`, cache key, TTL và purge/invalidation strategy.
- Publish workflow phải liên kết với cache invalidation/freshness expectation; nếu editor publish nhưng edge giữ stale HTML quá lâu thì hệ thống không đáp ứng requirement dù CMS đúng.
- External product API phải được coi là failure-prone; page không nên phụ thuộc tuyệt đối vào synchronous live call nếu business cho phép degrade/cached data.
- Preview unpublished content cần được bảo vệ và không cache/public index nhầm.
- Headless tăng số contracts/deployments/components cần monitor; complexity cost phải được đưa vào decision.

### Điểm cộng

- Đề xuất hybrid/islands: CMS/server-render public shell/content, client-side hoặc server-composed dynamic islands cho login/product state.
- Dùng surrogate/cache tags hoặc URL/content-key mapping nếu Akamai setup hỗ trợ purge granular; nếu không, thiết kế bounded TTL + versioned URLs phù hợp.
- Tách origin cache với edge cache và browser cache; mỗi layer có invalidation semantics riêng.
- Có stale-if-error hoặc last-known-good strategy cho non-critical product metadata nếu requirement cho phép.
- Preview dùng authenticated preview route/domain, `noindex`, bypass public CDN cache và propagate preview context an toàn.

### Senior+

- Nhận ra fully headless có thể khiến content model vô tình phụ thuộc frontend component contract; cần versioning/governance giữa CMS schema và frontend.
- Dùng composition boundary để tránh product API latency phá Time to First Byte của toàn page; prefetch/cache hoặc hydrate dynamic region tùy SEO requirement của product data.
- Thiết kế cache invalidation là event/workflow có thể fail: cần retry, idempotency và telemetry cho purge status thay vì giả định publish→purge luôn thành công.
- So sánh operational cost: hai independent pipelines/runtimes có thể tăng deployment flexibility nhưng cũng tăng incident surface.
- Nếu một marketing page gần như hoàn toàn public/stable, static/edge cache có thể đem lợi ích lớn hơn việc đưa toàn site vào SPA architecture.

## Hướng giải quyết tham khảo

Tôi sẽ không bắt đầu bằng “React hay Optimizely rendering”. Tôi phân loại dữ liệu trước.

| Loại dữ liệu | Owner | Freshness | User-specific | Cacheability |
|---|---|---:|---:|---|
| Editorial page content | Optimizely CMS | phút/giờ tùy SLA | không | rất cao |
| Product availability | Product service | giây/phút | thường không | có điều kiện |
| Login/header state | Identity/application | gần realtime | có | thấp/private |

Từ đó có ba hướng chính.

### Option A — Traditional Optimizely / ASP.NET Core rendering

**Ưu điểm**

- editorial preview/workflow gần CMS model;
- ít runtime/deployment components hơn;
- server-rendered HTML thuận lợi cho SEO;
- team .NET vận hành đơn giản hơn.

**Nhược điểm**

- frontend coupling với CMS application mạnh hơn;
- independent frontend deployment khó hơn;
- nếu composable/channel roadmap lớn, API boundary có thể hạn chế.

### Option B — Fully headless React frontend

CMS cung cấp content APIs, frontend render độc lập.

**Ưu điểm**

- frontend ownership/deployment độc lập;
- reuse content cho nhiều channels dễ hơn nếu content model thực sự channel-neutral;
- frontend technology freedom.

**Nhược điểm**

- preview/unpublished-content integration phức tạp hơn;
- thêm API contract, frontend runtime/build/deployment và observability surface;
- nếu là pure client-side SPA, SEO/initial render/JS cost có thể không phù hợp marketing site;
- cache invalidation tồn tại ở cả content API lẫn rendered output;
- editors có thể mất fidelity nếu component mapping không được governance tốt.

### Option C — Hybrid

Với requirements đã cho, đây là recommendation ban đầu hợp lý nếu team không có multi-channel/headless requirement mạnh.

Ví dụ:

```text
Browser
  |
Akamai CDN
  |
ASP.NET Core + Optimizely rendering
  |---- CMS content
  |---- cached product projection / product API
  |
Client islands
  |---- login state
  |---- highly dynamic availability interaction
```

Public editorial HTML được render server-side và cache ở Akamai. Login state không được đưa vào shared HTML cache key nếu không cần; render một anonymous shell rồi client fetch user-specific state sau authentication.

Product availability có thể có hai modes tùy SEO/business:

1. Nếu availability không cần index: render stable product/editorial content ở server, client fetch availability sau.
2. Nếu availability phải có trong initial HTML: origin dùng short-lived cache/bounded timeout và graceful fallback, nhưng không để external API timeout kéo cả page xuống nếu requirement cho phép degrade.

### Cache strategy

Ví dụ cho public page:

```http
Cache-Control: public, max-age=60, s-maxage=900
```

Con số thực tế phải theo freshness SLA; đây chỉ là minh họa. Quan trọng là ownership:

- browser cache có TTL riêng;
- CDN shared cache có TTL riêng;
- CMS/origin cache có invalidation riêng;
- personalized response không được vô tình shared-cache.

Khi editor publish:

```text
Publish
  -> content event
  -> invalidate origin cache
  -> request Akamai purge for affected URLs/tags
  -> record purge job status
  -> retry transient failures
  -> alert if freshness SLA exceeded
```

Không giả định purge là synchronous magic. Nếu purge provider lỗi, TTL phải đặt bounded để stale content tự hết hạn trong thời gian business chấp nhận được.

### Preview

Preview route/domain phải:

- yêu cầu authentication/authorization;
- access unpublished versions;
- gửi `noindex`;
- bypass hoặc partition cache khỏi public cache;
- không leak preview token/content qua logs;
- ideally render cùng component path với production để preview có fidelity.

### SEO và performance

Tôi đo:

- TTFB;
- LCP;
- INP;
- CLS;
- HTML size;
- JS bundle/hydration cost;
- CDN hit ratio;
- origin p95;
- product dependency p95/failure rate.

SEO engineering còn cần canonical URL, hreflang nếu phù hợp multi-language setup, redirects, sitemap, status-code correctness, metadata/structured data và crawlability. Không có framework nào tự bảo đảm các điều này.

### Security

Public frontend chỉ có access cần thiết tới published content. CMS editing/admin surfaces không expose rộng chỉ để phục vụ website. Server-to-server product credentials dùng secret management/Managed Identity khi applicable; không đưa privileged credentials vào browser bundle.

### Failure behavior

- CMS origin unavailable nhưng CDN có fresh/stale acceptable object → tiếp tục serve theo policy.
- Product API unavailable → degrade dynamic availability nếu business cho phép.
- Purge provider lỗi → retry + TTL backstop + alert.
- Client login-state API lỗi → public content vẫn usable.

### Khi recommendation thay đổi

Tôi sẽ nghiêng về headless mạnh hơn nếu:

- cùng content thực sự phải phục vụ nhiều channels/apps;
- frontend teams cần release cadence độc lập;
- CMS platform chỉ là một nguồn trong composable experience layer;
- team chấp nhận vận hành SSR/content delivery stack riêng;
- preview/editorial requirements đã được giải quyết rõ.

Tôi sẽ nghiêng về traditional hơn nếu:

- website chủ yếu là marketing content;
- editor experience quan trọng;
- một team .NET sở hữu end-to-end;
- multi-channel reuse thấp;
- operational simplicity là mục tiêu lớn.

Kiến trúc tốt nhất ở đây có thể là hybrid vừa đủ, thay vì biến “headless” thành mục tiêu tự thân.

## Mẫu trả lời trong phỏng vấn

“Em không chọn headless chỉ vì hiện đại. Em tách ba loại state: editorial content từ Optimizely, product availability từ external service và user-specific login state. Chúng có freshness và cacheability khác nhau.

Với một marketing site cần SEO, editor preview và traffic campaign lớn, em nghiêng ban đầu về hybrid: server-render public CMS content, Akamai cache mạnh ở edge, còn login state và một số product availability là dynamic islands. Như vậy public HTML crawlable và resilient, đồng thời không đưa personalized state vào shared cache.

Nếu publish phải live trong vài phút, publish workflow cần invalidate origin + request CDN purge, có retry và TTL backstop. Preview phải authenticated, noindex và bypass public cache. External product API được coi là failure-prone; nếu business cho phép, page vẫn render với last-known-good hoặc availability placeholder khi dependency lỗi.

Em chỉ chọn fully headless nếu có lợi ích thật như multi-channel reuse hoặc independent frontend ownership đủ lớn để trả chi phí thêm về contracts, preview, cache invalidation, deployment và observability.”

## Câu hỏi đào sâu

1. Nếu marketing yêu cầu personalized hero banner theo user segment nhưng vẫn muốn CDN hit ratio rất cao, bạn thay cache/render strategy thế nào?
2. Nếu business bắt buộc product availability phải xuất hiện trong initial HTML để search engine index, bạn xử lý external API latency/failure ra sao mà không phá page SLO?
3. Frontend lead nói “headless giúp deploy độc lập nên chắc chắn tốt hơn”. Bạn yêu cầu evidence/requirements nào trước khi chấp nhận thêm một SSR/runtime stack riêng?

## Lỗi trả lời thường gặp

- Chọn fully headless vì “modern” mà không định lượng requirement.
- Cache nguyên personalized HTML ở shared CDN key.
- Coi CMS publish và CDN purge là một atomic operation không thể lỗi.
- Gọi external product API synchronous cho mọi page request mà không có timeout/degradation/cache strategy.
- Chỉ nói Lighthouse/SEO chung chung mà không bàn HTML delivery, crawlability, status codes, JS cost và cache behavior.

## Thang điểm 0–10

- **0–2:** chọn framework/architecture theo sở thích.
- **3–4:** biết CDN/headless nhưng chưa tách data ownership/freshness.
- **5–6:** so sánh được three options, có SEO/cache/security/failure considerations.
- **7–8:** có hybrid boundary, preview/purge workflow, dynamic-data degradation và observability.
- **9–10:** recommendation conditional theo product/editorial/operational constraints, xử lý cache invalidation như failure-prone workflow và cân bằng edge performance với architecture complexity.
