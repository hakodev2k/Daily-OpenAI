# Code Review Challenge 1 — Cache quyền truy cập làm user nhìn thấy dữ liệu của tenant khác

**Chủ đề:** Authentication/authorization, caching, concurrency, sensitive-data exposure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một SaaS nội bộ chạy ASP.NET Core phục vụ nhiều công ty. Mỗi request đã được xác thực bằng JWT. Sau khi xác thực, API dùng một `PermissionService` để kiểm tra user có quyền truy cập một project hay không.

Để giảm tải database, team thêm `IMemoryCache`. Ứng dụng chạy 4 instance sau load balancer. Mỗi user có thể thuộc nhiều tenant và có thể được admin thêm/xóa quyền trong giờ làm việc.

Sau một lần deploy, production xuất hiện các triệu chứng khó tái hiện:

- Một số user vẫn truy cập được project vài phút sau khi quyền đã bị thu hồi.
- Hiếm hơn, một user có quyền vào project ở tenant A nhưng request sang tenant B lại được cho phép sai.
- Khi tải tăng, database query giảm rõ rệt nhưng lỗi authorization tăng theo kiểu không ổn định.
- Log hiện tại chỉ ghi `Allowed=true/false`, không ghi cache hit/miss hoặc tenant context.

Team muốn giữ cache vì query permission khá nóng, nhưng không chấp nhận rò rỉ dữ liệu giữa tenant.

## Đoạn code cần review

```csharp
public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IMemoryCache _cache;
    private readonly IHttpContextAccessor _httpContextAccessor;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        AppDbContext db,
        IMemoryCache cache,
        IHttpContextAccessor httpContextAccessor,
        ILogger<PermissionService> logger)
    {
        _db = db;
        _cache = cache;
        _httpContextAccessor = httpContextAccessor;
        _logger = logger;
    }

    public async Task<bool> CanAccessProjectAsync(
        Guid projectId,
        CancellationToken cancellationToken = default)
    {
        var user = _httpContextAccessor.HttpContext!.User;
        var userId = user.FindFirst("sub")!.Value;
        var tenantId = user.FindFirst("tenant_id")!.Value;

        var cacheKey = $"project-permission:{userId}:{projectId}";

        if (_cache.TryGetValue(cacheKey, out bool allowed))
        {
            _logger.LogInformation(
                "Permission result for {UserId}/{ProjectId}: {Allowed}",
                userId,
                projectId,
                allowed);

            return allowed;
        }

        allowed = await _db.ProjectMembers
            .AnyAsync(
                x => x.UserId == userId &&
                     x.ProjectId == projectId,
                cancellationToken);

        _cache.Set(cacheKey, allowed, TimeSpan.FromMinutes(10));

        _logger.LogInformation(
            "Permission result for {UserId}/{ProjectId}: {Allowed}",
            userId,
            projectId,
            allowed);

        return allowed;
    }
}
```

## Kết quả code review tham khảo

### 1. Cache key không chứa `tenantId`

**Problem:** Cache key chỉ gồm `userId` và `projectId`.

**Why it happens:** Implementation giả định `projectId` hoặc `userId` tự đủ để xác định authorization context.

**Production impact:** Nếu identifier không được đảm bảo global theo đúng mô hình hoặc có logic resource mapping khác giữa tenant, một kết quả cache của tenant A có thể được tái sử dụng trong context tenant B. Với authorization, đây là lỗi isolation nghiêm trọng.

**Severity:** Critical

**Recommended fix:** Cache key phải chứa đầy đủ security boundary, tối thiểu `tenantId`, `userId`, `projectId` và khi phù hợp cả permission/action cụ thể.

### 2. Query không kiểm tra tenant ownership của project/member

**Problem:** Query chỉ kiểm tra `UserId` và `ProjectId`, không có `TenantId`.

**Why it happens:** Authorization được viết như membership lookup thay vì resource-scoped authorization.

**Production impact:** Nếu dữ liệu tồn tại không hoàn toàn global-unique hoặc có lỗi migration/import, request có thể được authorize dựa trên record thuộc tenant khác. Đây là lỗi cross-tenant data exposure.

**Severity:** Critical

**Recommended fix:** Enforce tenant trong predicate hoặc tốt hơn join/relationship theo resource ownership. Ví dụ `x.TenantId == tenantId` và project cũng phải thuộc tenant đó. Nếu schema hỗ trợ, dùng composite unique constraints và global query filter chỉ như defence-in-depth, không phải thay thế cho policy rõ ràng.

### 3. Permission revocation có thể stale tới 10 phút

**Problem:** Positive cache entry tồn tại cố định 10 phút sau khi quyền bị thu hồi.

**Why it happens:** Không có invalidation path khi admin thay đổi membership.

**Production impact:** User đã bị thu hồi quyền vẫn truy cập được dữ liệu trong TTL. Với nghiệp vụ nhạy cảm, đây là security incident chứ không chỉ là eventual consistency thông thường.

**Severity:** High

**Recommended fix:** Thiết kế invalidation cùng mutation. Khi permission thay đổi, xóa cache entry tương ứng. Nếu nhiều instance, dùng distributed invalidation/versioning hoặc một distributed cache phù hợp. Với quyền đặc biệt nhạy cảm, cân nhắc TTL rất ngắn hoặc không cache positive permission.

### 4. `IMemoryCache` không đồng bộ giữa nhiều instance

**Problem:** Mỗi application instance giữ cache riêng.

**Why it happens:** In-memory cache chỉ có phạm vi process.

**Production impact:** Sau khi invalidate trên instance xử lý request admin, instance khác vẫn giữ quyền cũ. User có thể thấy hành vi lúc được phép, lúc bị từ chối tùy request rơi vào node nào.

**Severity:** High

**Recommended fix:** Nếu consistency giữa node là yêu cầu, dùng distributed cache hoặc distributed invalidation signal. Một lựa chọn nhẹ hơn là cache permission version theo user/tenant và bump version khi membership thay đổi.

### 5. Authorization service phụ thuộc trực tiếp vào `HttpContext`

**Problem:** Service lấy identity qua `IHttpContextAccessor` thay vì nhận security context rõ ràng.

**Why it happens:** Identity resolution và domain authorization bị ghép chặt.

**Production impact:** Khó test, khó tái sử dụng trong background job, dễ null-reference hoặc dùng nhầm context. Boundary của authorization cũng khó nhìn thấy khi review code.

**Severity:** Medium

**Recommended fix:** Resolve `userId`/`tenantId` ở application boundary rồi truyền vào authorization service dưới dạng strongly typed context, hoặc xây abstraction như `ICurrentUserContext` có validation tập trung.

### 6. Dùng null-forgiving operator cho claims bắt buộc

**Problem:** `HttpContext!` và `FindFirst(...)!.Value` giả định claims luôn tồn tại.

**Why it happens:** Không có explicit validation cho identity contract.

**Production impact:** Token/configuration lỗi có thể thành `NullReferenceException` và trả 500 thay vì 401/403 có kiểm soát.

**Severity:** Medium

**Recommended fix:** Validate claim bắt buộc và fail closed. Identity không hợp lệ phải bị từ chối, không được fallback sang giá trị mặc định.

### 7. Cache stampede khi nhiều request miss cùng key

**Problem:** Nhiều request đồng thời cho cùng user/project có thể cùng miss và cùng query database.

**Why it happens:** `TryGetValue` + query + `Set` không có coordination.

**Production impact:** Trong giờ cao điểm hoặc sau deploy/cache eviction, database có thể nhận burst query lớn cho hot key.

**Severity:** Medium

**Recommended fix:** Dùng per-key synchronization/single-flight khi thực sự cần. Tuy nhiên không nên thêm lock phức tạp nếu metrics cho thấy tải DB vẫn chấp nhận được.

### 8. Cache cả kết quả deny với TTL dài mà không cân nhắc grant propagation

**Problem:** `false` cũng được cache 10 phút.

**Why it happens:** Positive và negative cache dùng cùng policy.

**Production impact:** User vừa được cấp quyền có thể tiếp tục nhận 403 cho tới khi cache hết hạn, tạo lỗi trải nghiệm và support ticket.

**Severity:** Medium

**Recommended fix:** Tách TTL positive/negative hoặc invalidation trực tiếp khi membership thay đổi.

### 9. Observability không đủ để điều tra authorization anomaly

**Problem:** Log không có tenant, cache hit/miss, source của decision hay policy/action.

**Why it happens:** Logging chỉ tập trung vào kết quả boolean.

**Production impact:** Khó chứng minh lỗi do stale cache, tenant mismatch hay database state; MTTR tăng khi incident xảy ra.

**Severity:** Low

**Recommended fix:** Log structured metadata an toàn như `TenantId`, internal `UserId`, `ProjectId`, action, cache hit/miss, permission version, decision source và trace id. Không log token hoặc toàn bộ claims.

## Phiên bản code đề xuất

Ví dụ dưới đây giả định `tenantId`, `userId` đã được xác thực ở boundary và permission mutation có cơ chế bump version hoặc invalidation. Đây là một hướng thiết kế, không phải lựa chọn duy nhất.

```csharp
public sealed record AccessContext(string TenantId, string UserId);

public sealed class PermissionService
{
    private readonly AppDbContext _db;
    private readonly IMemoryCache _cache;
    private readonly ILogger<PermissionService> _logger;

    public PermissionService(
        AppDbContext db,
        IMemoryCache cache,
        ILogger<PermissionService> logger)
    {
        _db = db;
        _cache = cache;
        _logger = logger;
    }

    public async Task<bool> CanAccessProjectAsync(
        AccessContext access,
        Guid projectId,
        CancellationToken cancellationToken = default)
    {
        ArgumentException.ThrowIfNullOrWhiteSpace(access.TenantId);
        ArgumentException.ThrowIfNullOrWhiteSpace(access.UserId);

        var cacheKey =
            $"project-access:{access.TenantId}:{access.UserId}:{projectId}";

        if (_cache.TryGetValue(cacheKey, out bool cached))
        {
            _logger.LogDebug(
                "Project authorization cache hit. Tenant={TenantId} User={UserId} Project={ProjectId} Allowed={Allowed}",
                access.TenantId,
                access.UserId,
                projectId,
                cached);

            return cached;
        }

        var allowed = await _db.ProjectMembers
            .AsNoTracking()
            .AnyAsync(
                x => x.TenantId == access.TenantId &&
                     x.UserId == access.UserId &&
                     x.ProjectId == projectId &&
                     x.Project.TenantId == access.TenantId,
                cancellationToken);

        var ttl = allowed
            ? TimeSpan.FromMinutes(2)
            : TimeSpan.FromSeconds(30);

        _cache.Set(cacheKey, allowed, ttl);

        _logger.LogInformation(
            "Project authorization evaluated. Tenant={TenantId} User={UserId} Project={ProjectId} Allowed={Allowed} Source=Database",
            access.TenantId,
            access.UserId,
            projectId,
            allowed);

        return allowed;
    }

    public void InvalidateProjectAccess(
        string tenantId,
        string userId,
        Guid projectId)
    {
        _cache.Remove(
            $"project-access:{tenantId}:{userId}:{projectId}");
    }
}
```

Nếu ứng dụng chạy nhiều instance và revocation cần hiệu lực gần như ngay lập tức, local invalidation là chưa đủ. Khi đó có thể dùng distributed cache, publish invalidation event, hoặc permission-version strategy.

## Trade-offs

- `IMemoryCache` rất nhanh và đơn giản, nhưng state nằm riêng từng process.
- Distributed cache làm consistency giữa node tốt hơn nhưng tăng network dependency và operational complexity.
- TTL ngắn giảm cửa sổ stale nhưng tăng query database.
- Event-driven invalidation giảm stale nhưng cần đảm bảo event delivery, retry và xử lý khi node bỏ lỡ event.
- Với permission cực kỳ nhạy cảm, bỏ cache hoặc chỉ cache metadata không ảnh hưởng trực tiếp đến access decision có thể là lựa chọn đúng hơn.

## Cách kiểm thử

1. **Cross-tenant integration test:** cùng `userId`/project-like identifiers ở hai tenant không được tái sử dụng decision lẫn nhau.
2. **Revocation test:** cấp quyền → request thành công → thu hồi quyền → invalidate/bump version → request tiếp theo phải bị từ chối.
3. **Grant propagation test:** deny cache trước đó không được giữ user trong trạng thái 403 quá policy cho phép sau khi được grant.
4. **Concurrency/load test:** hàng trăm request cùng hot key sau cache miss; đo số query DB, latency và lỗi.
5. **Malformed identity test:** thiếu `tenant_id`/`sub` phải fail closed với 401/403 phù hợp, không được 500 hoặc mặc định sang tenant khác.

## Quan sát trong production

- Metric `permission_cache_hit_ratio` và cache evictions.
- Counter cho revocation/grant invalidation.
- Trace span cho permission lookup và database query duration.

# Code Review Challenge 2 — Export CSV làm API hết memory khi dữ liệu tăng lên hàng triệu bản ghi

**Chủ đề:** Memory/allocation, async/await, cancellation, EF Core query execution, resource lifetime, performance  
**Độ khó:** Senior

## Bối cảnh

Một API cho phép admin export lịch sử giao dịch ra CSV. Ban đầu mỗi tenant chỉ có vài nghìn dòng nên implementation chạy ổn. Sau một năm, một số tenant có 1–3 triệu bản ghi.

Production bắt đầu có các triệu chứng:

- Memory của process tăng rất mạnh khi vài người export cùng lúc.
- Request có thể mất vài phút rồi bị reverse proxy timeout.
- Khi user đóng trình duyệt, server đôi khi vẫn tiếp tục query và tạo file.
- GC pause tăng trong thời gian export.
- Database CPU tăng mạnh dù export chỉ là tác vụ đọc.

Team không muốn thêm một hệ thống data warehouse chỉ để giải quyết export. Họ chấp nhận thay đổi API hoặc chuyển export sang background workflow nếu cần.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/transactions")]
public sealed class TransactionsController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<TransactionsController> _logger;

    public TransactionsController(
        AppDbContext db,
        ILogger<TransactionsController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("export")]
    public async Task<IActionResult> Export(
        DateTime from,
        DateTime to)
    {
        var rows = await _db.Transactions
            .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
            .OrderBy(x => x.CreatedAt)
            .ToListAsync();

        var builder = new StringBuilder();
        builder.AppendLine("Id,CreatedAt,Amount,Description");

        foreach (var row in rows)
        {
            builder.Append(row.Id).Append(',')
                .Append(row.CreatedAt.ToString("O")).Append(',')
                .Append(row.Amount).Append(',')
                .Append(row.Description)
                .AppendLine();
        }

        var bytes = Encoding.UTF8.GetBytes(builder.ToString());

        _logger.LogInformation(
            "Exported {Count} transactions from {From} to {To}",
            rows.Count,
            from,
            to);

        return File(bytes, "text/csv", "transactions.csv");
    }
}
```

## Kết quả code review tham khảo

### 1. Materialize toàn bộ dataset bằng `ToListAsync()`

**Problem:** Tất cả transaction được load vào memory trước khi ghi byte đầu tiên.

**Why it happens:** Query được materialize thành `List<Transaction>`.

**Production impact:** Với hàng triệu rows và nhiều export đồng thời, memory tăng mạnh, GC pressure lớn và có nguy cơ OOM/process restart.

**Severity:** High

**Recommended fix:** Không materialize toàn bộ dữ liệu. Dùng projection và stream/batch. Với synchronous export có thể dùng `AsAsyncEnumerable()` trên projection và ghi tuần tự xuống response; với export rất lớn nên cân nhắc background job tạo file.

### 2. EF Core đang tracking các entity dù export chỉ đọc

**Problem:** Query không dùng `AsNoTracking()`.

**Why it happens:** Mặc định query entity có thể được change tracker theo dõi.

**Production impact:** Tăng memory và bookkeeping không cần thiết cho workload read-only lớn.

**Severity:** High

**Recommended fix:** Dùng `AsNoTracking()` hoặc projection trực tiếp sang DTO/anonymous type để chỉ lấy cột cần thiết.

### 3. Tạo nhiều bản sao lớn trong memory

**Problem:** Data tồn tại qua `List`, `StringBuilder`, `string` từ `ToString()` và `byte[]` từ `GetBytes()`.

**Why it happens:** Toàn file được build trong RAM trước khi response được gửi.

**Production impact:** Memory amplification lớn hơn nhiều so với kích thước CSV cuối cùng; large object allocations và GC pause tăng mạnh.

**Severity:** High

**Recommended fix:** Ghi trực tiếp theo stream bằng `StreamWriter` vào response hoặc temporary/object storage. Không build toàn file thành một chuỗi.

### 4. Cancellation không được propagate

**Problem:** Action không nhận `CancellationToken`; query cũng không dùng `HttpContext.RequestAborted`.

**Why it happens:** Export được coi là tác vụ atomic, không để ý client disconnect.

**Production impact:** User đóng browser nhưng DB query và serialization vẫn tiếp tục tiêu tốn CPU/memory/I/O.

**Severity:** High

**Recommended fix:** Nhận `CancellationToken cancellationToken` trong action hoặc dùng `HttpContext.RequestAborted`, truyền nó vào database enumeration và stream write/flush.

### 5. CSV escaping không đúng

**Problem:** `Description` được append trực tiếp.

**Why it happens:** Code giả định text không chứa comma, quote hoặc newline.

**Production impact:** File CSV có thể sai cấu trúc; dữ liệu dịch cột, hỏng import và có thể tạo formula-injection risk nếu file được mở trong spreadsheet software và dữ liệu user-controlled bắt đầu bằng các ký tự công thức.

**Severity:** High

**Recommended fix:** Implement CSV escaping chuẩn hoặc dùng thư viện CSV đáng tin cậy. Với dữ liệu user-controlled, cân nhắc policy chống spreadsheet formula injection tùy threat model.

### 6. Query lấy toàn bộ entity thay vì chỉ cột cần thiết

**Problem:** Entity `Transaction` đầy đủ được tải dù CSV chỉ cần bốn field.

**Why it happens:** Không projection.

**Production impact:** Tăng network bytes từ DB, materialization cost và memory usage.

**Severity:** Medium

**Recommended fix:** `.Select(x => new { x.Id, x.CreatedAt, x.Amount, x.Description })` trước khi enumerate.

### 7. Range filter và ordering cần index phù hợp

**Problem:** Query filter/order theo `CreatedAt`; nếu thiếu index phù hợp hoặc tenant predicate, DB có thể scan/sort lượng dữ liệu lớn.

**Why it happens:** Implementation chỉ nhìn logic C# mà không xét execution plan.

**Production impact:** DB CPU và I/O tăng, export cạnh tranh tài nguyên với traffic giao dịch chính.

**Severity:** Medium

**Recommended fix:** Kiểm tra actual execution plan. Với multi-tenant, thường cần tenant filter và index phù hợp với access pattern như `(TenantId, CreatedAt, Id)` tùy schema và database. Không tạo index chỉ từ phỏng đoán; đo bằng query plan và workload thật.

### 8. Ordering chỉ theo `CreatedAt` có thể không deterministic

**Problem:** Nhiều row có cùng timestamp nhưng không có tie-breaker.

**Why it happens:** Chỉ dùng một sort key không unique.

**Production impact:** Nếu chuyển sang batching/keyset pagination, row có thể bị lặp hoặc bỏ sót nếu cursor không deterministic.

**Severity:** Medium

**Recommended fix:** Dùng ordering ổn định như `OrderBy(CreatedAt).ThenBy(Id)` và cursor tương ứng nếu batch theo keyset.

### 9. Synchronous long-running HTTP export có thể không phù hợp

**Problem:** Một request có thể giữ connection nhiều phút.

**Why it happens:** API cố hoàn thành toàn bộ export trong request lifecycle.

**Production impact:** Proxy timeout, resource occupation dài, retry từ user gây export trùng và tăng tải.

**Severity:** Medium

**Recommended fix:** Với export nhỏ-trung bình, streaming HTTP có thể đủ. Với export rất lớn, dùng background job: tạo export record → process theo batch → ghi file storage → user polling/notification → download bằng URL có authorization/expiry phù hợp.

## Phiên bản code đề xuất

Ví dụ dưới đây minh hoạ synchronous streaming cho dataset trong giới hạn mà tổ chức chấp nhận. Với export hàng triệu row và thời gian dài, background export thường phù hợp hơn.

```csharp
[HttpGet("export")]
public async Task Export(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    Response.StatusCode = StatusCodes.Status200OK;
    Response.ContentType = "text/csv; charset=utf-8";
    Response.Headers.ContentDisposition =
        "attachment; filename=transactions.csv";

    await using var writer = new StreamWriter(
        Response.Body,
        new UTF8Encoding(encoderShouldEmitUTF8Identifier: false),
        bufferSize: 64 * 1024,
        leaveOpen: true);

    await writer.WriteLineAsync(
        "Id,CreatedAt,Amount,Description".AsMemory(),
        cancellationToken);

    var query = _db.Transactions
        .AsNoTracking()
        .Where(x => x.CreatedAt >= from && x.CreatedAt <= to)
        .OrderBy(x => x.CreatedAt)
        .ThenBy(x => x.Id)
        .Select(x => new
        {
            x.Id,
            x.CreatedAt,
            x.Amount,
            x.Description
        })
        .AsAsyncEnumerable()
        .WithCancellation(cancellationToken);

    var count = 0L;

    await foreach (var row in query)
    {
        var line = string.Join(',',
            EscapeCsv(row.Id.ToString()),
            EscapeCsv(row.CreatedAt.ToString("O")),
            EscapeCsv(row.Amount.ToString(CultureInfo.InvariantCulture)),
            EscapeCsv(row.Description));

        await writer.WriteLineAsync(line.AsMemory(), cancellationToken);
        count++;

        if (count % 1000 == 0)
        {
            await writer.FlushAsync(cancellationToken);
        }
    }

    await writer.FlushAsync(cancellationToken);

    _logger.LogInformation(
        "Transaction export completed. Rows={Count} From={From} To={To}",
        count,
        from,
        to);
}

private static string EscapeCsv(string? value)
{
    value ??= string.Empty;

    var escaped = value.Replace("\"", "\"\"");
    return $"\"{escaped}\"";
}
```

Một production implementation cần thêm tenant filter, authorization, export size policy, timeout policy và xử lý trường hợp response đã bắt đầu nhưng downstream lỗi giữa chừng.

## Trade-offs

- Streaming giảm memory nhưng giữ DB reader/HTTP connection lâu hơn.
- Batch/keyset export cho phép kiểm soát transaction/resource tốt hơn nhưng code phức tạp hơn.
- Background export tăng độ bền và UX cho file lớn nhưng cần job state, storage lifecycle, cleanup, authorization cho download và retry/idempotency.
- `Flush` quá thường xuyên tăng syscall/network overhead; quá ít lại làm client chờ lâu hơn. Nên đo.
- Export từ primary database có thể ảnh hưởng OLTP workload; với tải lớn hơn có thể cần read replica hoặc giới hạn concurrency trước khi nghĩ tới kiến trúc phức tạp hơn.

## Cách kiểm thử

1. **Large dataset integration/load test:** export vài trăm nghìn đến hàng triệu row; đo peak memory, GC, throughput và DB duration.
2. **Cancellation test:** huỷ request giữa chừng; xác nhận enumeration/query dừng sớm và connection/resource được giải phóng.
3. **CSV correctness test:** description chứa comma, quote, CR/LF, Unicode và giá trị rỗng vẫn parse lại đúng.
4. **Concurrent export test:** nhiều export cùng lúc không làm API chính vượt memory/DB SLO; kiểm tra concurrency limit nếu có.
5. **Failure-path test:** DB/network exception giữa stream phải được log/traced; nếu response đã bắt đầu thì client nhận kết nối lỗi rõ ràng và server không giữ resource bị leak.

## Quan sát trong production

- Metric số export đang chạy đồng thời.
- Histogram export duration và rows exported.
- Process memory, allocation rate, GC pause, Gen 2 collection.
- Database query duration, rows scanned/read, CPU/I/O và active connections.
- Counter export cancelled, failed, completed.
- Distributed trace span cho query và stream duration.
- Alert nếu export concurrency hoặc DB impact vượt ngưỡng đã định.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chuyển từ HTTP streaming sang background export?
2. Nếu export cần snapshot consistency trong lúc transaction mới vẫn được ghi, bạn chọn isolation/snapshot strategy nào và trade-off là gì?
3. Nếu file export chứa dữ liệu nhạy cảm, bạn thiết kế authorization, expiration và cleanup của file như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authorization cache phải chứa đầy đủ security context; cache key và database predicate đều phải tôn trọng tenant boundary.
- Permission revocation là bài toán consistency, không chỉ là TTL tuning.
- Local cache trên nhiều instance không tự đồng bộ.
- Với large-data pipeline, cần đếm số lần dữ liệu được materialize/copy trong memory.
- Read-only query lớn nên projection tối thiểu, no-tracking và có cancellation.
- Streaming và background processing là hai công cụ khác nhau; lựa chọn phụ thuộc size, duration, UX và recovery requirement.

## Mẫu tư duy cần nhớ

1. **Authorization phải fail closed và luôn gắn với resource boundary.**
2. **Thiết kế cache cùng invalidation, không thiết kế cache riêng lẻ.**
3. **Theo dõi data flow end-to-end để tìm memory amplification.**
4. **Propagate cancellation qua toàn bộ I/O chain.**
5. **Measure production behavior trước khi thêm hạ tầng hoặc tối ưu phức tạp.**
