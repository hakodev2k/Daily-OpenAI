## Đoạn code cần review

~~~csharp
public sealed record ProductPatch(decimal Price, bool IsActive);

[ApiController]
[Route("api/products")]
public sealed class ProductsController : ControllerBase
{
    private readonly CatalogDbContext _db;
    private readonly IElasticClient _search;
    private readonly ILogger<ProductsController> _logger;

    public ProductsController(
        CatalogDbContext db,
        IElasticClient search,
        ILogger<ProductsController> logger)
    {
        _db = db;
        _search = search;
        _logger = logger;
    }

    [HttpPut("{id:guid}")]
    public async Task<IActionResult> Update(
        Guid id, ProductPatch patch, CancellationToken ct)
    {
        var product = await _db.Products
            .SingleOrDefaultAsync(x => x.Id == id, ct);

        if (product is null) return NotFound();

        product.Price = patch.Price;
        product.IsActive = patch.IsActive;
        product.UpdatedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync(ct);

        var result = await _search.IndexAsync(
            new ProductSearchDocument
            {
                Id = product.Id,
                Name = product.Name,
                Price = product.Price,
                IsActive = product.IsActive,
                UpdatedAt = product.UpdatedAt
            }, x => x.Index("catalog").Id(id), ct);

        if (!result.IsValid)
        {
            _logger.LogError("Index failed: {Error}", result.DebugInformation);
            return StatusCode(500, "Index failed");
        }

        return Ok(product);
    }
}

public sealed class CatalogReindexJob
{
    private readonly CatalogDbContext _db;
    private readonly IElasticClient _search;

    public CatalogReindexJob(CatalogDbContext db, IElasticClient search)
    {
        _db = db;
        _search = search;
    }

    public async Task Run(CancellationToken ct)
    {
        var products = await _db.Products.ToListAsync(ct);
        foreach (var product in products)
            await _search.IndexAsync(product,
                x => x.Index("catalog").Id(product.Id), ct);
    }
}
~~~

## Kết quả code review tham khảo

### [Critical] — Database commit thành công nhưng API báo thất bại

**Vấn đề:** SaveChangesAsync commit rồi mới gọi Elasticsearch; lỗi indexing trả 500.  
**Tại sao xảy ra:** Không có atomic transaction giữa hai hệ thống.  
**Ảnh hưởng production:** Client retry gây nhầm lẫn; admin không biết thay đổi đã được lưu.  
**Cách sửa:** Transactional outbox trong cùng PostgreSQL transaction với product update; API phản ánh trạng thái database, search đồng bộ bất đồng bộ.

### [High] — Event cũ ghi đè document mới

**Vấn đề:** IndexAsync không ràng buộc version; retry hoặc concurrent requests có thể đảo thứ tự.  
**Tại sao xảy ra:** Thời điểm hoàn tất network request không tương đương thứ tự commit.  
**Ảnh hưởng production:** Giá và trạng thái bán hàng bị rollback trên search.  
**Cách sửa:** Dùng monotonic database version cho từng product và external versioning phù hợp với Elasticsearch client/version đang sử dụng; hoặc consumer tuần tự theo aggregate và kiểm tra version.

### [High] — Không có durable retry và dead-letter workflow

**Vấn đề:** Index failure chỉ được log; không có hàng đợi bền vững.  
**Tại sao xảy ra:** Request thread chịu trách nhiệm đồng bộ search.  
**Ảnh hưởng production:** Search stale đến lần reindex kế tiếp.  
**Cách sửa:** Outbox dispatcher có retry/backoff, claim lease, attempts, next attempt, quarantine/alert và replay có kiểm soát.

### [High] — Full reindex có thể ghi đè live update

**Vấn đề:** Reindex chạy song song với update, sử dụng snapshot khác nhau.  
**Tại sao xảy ra:** Không có cutover protocol, version check hoặc event replay watermark.  
**Ảnh hưởng production:** Document cũ xuất hiện trở lại.  
**Cách sửa:** Xây index mới theo alias, ghi nhận watermark, replay changes, verify, atomic alias swap; áp dụng version gating trong quá trình chuyển.

### [Medium] — ToListAsync materialize toàn bộ catalog

**Vấn đề:** Tải toàn bộ bảng vào memory và gửi từng request.  
**Tại sao xảy ra:** Không có pagination/streaming/bulk indexing.  
**Ảnh hưởng production:** Memory pressure, GC, database load, thời gian reindex dài.  
**Cách sửa:** Keyset batching, AsNoTracking, projection và bulk requests có giới hạn concurrency.

### [Medium] — Thiếu validation và authorization thể hiện trong endpoint

**Vấn đề:** Không thấy policy giới hạn admin hay quy tắc giá không âm.  
**Tại sao xảy ra:** [ApiController] không tự áp dụng business authorization.  
**Ảnh hưởng production:** Nếu middleware/policy không bổ sung, người không có quyền có thể cập nhật catalog.  
**Cách sửa:** Policy-based authorization và validation tại API/domain; xác minh cấu hình thực tế trước khi kết luận exploit.

### [Medium] — Response trả entity và search payload không có contract riêng

**Vấn đề:** Return Ok(product) có thể lộ thuộc tính ngoài public contract; reindex gửi entity khác schema live index.  
**Tại sao xảy ra:** Persistence entity bị tái sử dụng làm response/search document.  
**Ảnh hưởng production:** Schema drift, mapping conflict, data leakage tùy model.  
**Cách sửa:** DTO riêng, mapping tập trung, schema contract tests.

### [Medium] — Logging thiếu correlation và lag metrics

**Vấn đề:** Chỉ log DebugInformation khi lỗi.  
**Tại sao xảy ra:** Không theo dõi outbox backlog, index version và age.  
**Ảnh hưởng production:** Khó biết dữ liệu stale bao lâu và bao nhiêu bản ghi bị ảnh hưởng.  
**Cách sửa:** Structured logs với ProductId/Version/OperationId; lag, failure rate, backlog age và tracing.

## Phiên bản đề xuất

Ví dụ minh họa contract; giả định entity có Version được tăng trong database với optimistic concurrency, bảng OutboxMessages nằm cùng PostgreSQL database. Không coi đây là implementation đầy đủ của dispatcher.

~~~csharp
[Authorize(Policy = "CatalogEditor")]
[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(
    Guid id, ProductPatch patch, CancellationToken ct)
{
    if (patch.Price < 0)
        return BadRequest("Price must be non-negative.");

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var product = await _db.Products.SingleOrDefaultAsync(
        x => x.Id == id, ct);
    if (product is null) return NotFound();

    product.Price = patch.Price;
    product.IsActive = patch.IsActive;
    product.Version += 1; // concurrency token enforced by DB mapping
    product.UpdatedAt = DateTime.UtcNow;

    _db.OutboxMessages.Add(new OutboxMessage
    {
        Id = Guid.NewGuid(),
        AggregateId = id,
        AggregateVersion = product.Version,
        Type = "ProductChanged",
        CreatedAt = DateTime.UtcNow
    });

    try
    {
        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict("Product changed; reload and retry.");
    }

    return Ok(new
    {
        product.Id, product.Price, product.IsActive,
        product.Version, SearchSync = "Pending"
    });
}
~~~

Dispatcher pseudocode:

~~~text
repeat:
  claim due outbox rows with bounded lease and batch size
  for each row:
    read current product projection (or immutable event payload)
    index/delete using version-aware operation
    on success: mark processed (idempotently)
    on transient failure: schedule bounded exponential backoff + jitter
    on permanent failure: quarantine and alert
  periodically reconcile DB vs index and monitor oldest pending age
~~~

Nếu dispatcher đọc *current state*, phải xử lý delete/tombstone và đảm bảo version không giảm. Nếu event chứa immutable snapshot, phải chống stale writes bằng version. Concurrent update cần concurrency token thực sự ở database; chỉ tăng một property trong memory là chưa đủ nếu mapping không bảo vệ lost updates.

## Giải thích thiết kế sau khi sửa

PostgreSQL là source of truth; search là eventually consistent projection. Product update và outbox record commit cùng transaction. Dispatcher chịu trách nhiệm retries; search API cần quyết định rõ liệu stale results có chấp nhận được, và checkout phải xác nhận giá/trạng thái từ transactional store thay vì tin vào search document.

## Trade-offs

Outbox tăng storage và vận hành worker, đồng thời chấp nhận search lag. External versioning đòi hỏi monotonic version và xử lý delete cẩn thận. Reindex theo alias tốn thêm disk và cần cutover protocol; hệ thống nhỏ có thể bắt đầu bằng outbox + periodic reconciliation thay vì xây pipeline phức tạp.

## Cách kiểm thử

1. **Integration:** PostgreSQL commit xong, Elasticsearch timeout; API vẫn phản ánh trạng thái DB và outbox còn pending.
2. **Concurrency:** Hai updates cạnh tranh; kiểm tra optimistic concurrency và search không quay về version cũ.
3. **Failure-path:** Dispatcher crash sau index nhưng trước mark processed; retry không tạo regression.
4. **Load:** Reindex hàng triệu products với memory ổn định, giới hạn batch và bulk rejection recovery.
5. **Contract:** Deleted/disabled products, mapping drift, alias cutover và price validation.

## Quan sát trong production

Theo dõi outbox pending count, oldest pending age, retry count, dead-letter count, index failure rate, bulk rejection, Elasticsearch cluster health, DB query duration, heap/GC và product-version mismatch sampling. Correlate ProductId, operation ID, outbox ID và version trong logs/traces; alert khi indexing lag vượt SLO đã thống nhất.

3. Khi nào nên bỏ Elasticsearch và dùng PostgreSQL full-text search?

type Product = {
  id: string;
  name: string;
  snippetHtml: string;
};

export function ProductSearch() {
  const [query, setQuery] = React.useState(
    new URLSearchParams(location.search).get("q") ?? "");
  const [items, setItems] = React.useState<Product[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  React.useEffect(() => {
    setLoading(true);
    setError("");

    const token = localStorage.getItem("access_token");
    fetch("/api/search?q=" + query, {
      headers: { Authorization: "Bearer " + token }
    })
      .then(r => r.json())
      .then(data => {
        setItems(data.items);
        setLoading(false);
      })
      .catch(e => {
        setError(String(e));
        setLoading(false);
      });
  }, [query]);

  function onChange(e: React.ChangeEvent<HTMLInputElement>) {
    const next = e.target.value;
    setQuery(next);
    history.replaceState({}, "", "?q=" + next);
  }

  return (
    <section>
      <input value={query} onChange={onChange}
             aria-label="Search products" />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>
        {items.map(p => (
          <li key={p.id}>
            <strong>{p.name}</strong>
            <div dangerouslySetInnerHTML={{
              __html: p.snippetHtml
            }} />
          </li>
        ))}
      </ul>
    </section>
  );
}

**Vấn đề:** Response của query cũ có thể ghi đè query mới.  
**Tại sao xảy ra:** Các promises độc lập không được hủy hoặc kiểm tra request identity.

## Phiên bản đề xuất

Ví dụ dưới đây giả định BFF same-origin dùng secure session cookie và CSRF protection được triển khai ở tầng API; không tự ý chuyển một hệ thống Bearer-token sang cookie nếu backend chưa hỗ trợ. ~~~tsx
type Product = { id: string; name: string; snippet: string };
type SearchResponse = { items: Product[] };

export function ProductSearch() {
  const [query, setQuery] = React.useState(
    new URLSearchParams(window.location.search).get("q") ?? "");
  const [debounced, setDebounced] = React.useState(query);
  const [items, setItems] = React.useState<Product[]>([]);
  const [loading, setLoading] = React.useState(false);
  const [error, setError] = React.useState("");

  React.useEffect(() => {
    const timer = window.setTimeout(() => setDebounced(query), 250);
    return () => window.clearTimeout(timer);
  }, [query]);

  React.useEffect(() => {
    const controller = new AbortController();
    let active = true;

    async function search() {
      setLoading(true);
      setError("");
      try {
        const url = new URL("/api/search", window.location.origin);
        url.searchParams.set("q", debounced);
        const response = await fetch(url, {
          signal: controller.signal,
          credentials: "same-origin"
        });
        if (response.status === 401)
          throw new Error("Session expired");
        if (!response.ok)
          throw new Error("Search unavailable");
        const data: SearchResponse = await response.json();
        if (!Array.isArray(data.items))
          throw new Error("Invalid response");
        if (active) setItems(data.items);
      } catch (e) {
        if (active && !controller.signal.aborted) {
          setError(e instanceof Error ? e.message : "Search failed");
          setItems([]);
        }
      } finally {
        if (active) setLoading(false);
      }
    }

    void search();
    return () => {
      active = false;
      controller.abort();
    };
  }, [debounced]);

  function changeQuery(next: string) {
    setQuery(next);
    const url = new URL(window.location.href);
    url.searchParams.set("q", next);
    window.history.replaceState({}, "", url);
  }

  return (
    <section>
      <input aria-label="Search products" value={query}
        onChange={e => changeQuery(e.target.value)} />
      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}
      <ul>{items.map(p =>
        <li key={p.id}>
          <strong>{p.name}</strong>
          <p>{p.snippet}</p>
        </li>
      )}</ul>
    </section>
  );
}
~~~

Production implementation nên dùng router để đồng bộ back/forward, schema validation đầy đủ cho từng Product và auth redirect flow có kiểm soát. Debounce không thay thế server-side rate limiting; cancellation phía browser không bảo đảm server đã dừng xử lý.

## Giải thích thiết kế sau khi sửa

Mỗi effect sở hữu một AbortController và active flag để loại bỏ stale results. Query encoding do URLSearchParams đảm nhận. Plain text tránh HTML trust boundary không cần thiết. Response.ok và schema check phân biệt network, HTTP và contract failures. Nếu CMS bắt buộc rich text, sanitize ở boundary thích hợp thay vì dùng plain text.

## Trade-offs

Debounce giảm requests nhưng thêm latency; 250ms là giá trị khởi đầu cần đo, không phải hằng số tối ưu. BFF cookie giảm exposure của token với JavaScript nhưng đòi hỏi CSRF/session lifecycle design. AbortController tiết kiệm network khi có thể, song backend vẫn cần cancellation và resource limits.

## Cách kiểm thử

1. **Playwright race:** Delay response A, trả B trước; UI phải giữ kết quả B.
2. **Security:** CMS snippet chứa script/event handler; kiểm tra không có execution.
3. **API failure:** 401, 500, invalid JSON và network offline; hiển thị lỗi đúng, không crash.
4. **Navigation:** Query có &, #, Unicode; reload và back/forward khớp URL.
5. **Load/E2E:** Gõ nhanh, unmount, đổi route; request count và abort behavior phù hợp.

## Quan sát trong production

Đo client search latency, request rate, abort rate, error/status distribution, session-expired count, API p95, browser console errors và Web Vitals. Dùng request/correlation ID để nối frontend telemetry với ASP.NET Core Application Insights; không log raw token hoặc dữ liệu tìm kiếm nhạy cảm.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào nên dùng React Query/TanStack Query thay cho effect tự quản lý?
2. Nếu search backend eventually consistent, UI cần thông báo gì sau admin update?
3. Bạn thiết kế E2E tests thế nào để tránh flaky network timing?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Transactional outbox bảo vệ ranh giới giữa database commit và search projection; retry cần idempotency và version ordering.
- Full reindex cần chiến lược cutover, không được mặc định an toàn khi chạy cùng live updates.
- React asynchronous state có thể sai dù từng request đều thành công; browser security phụ thuộc trust boundary và auth architecture.
- Telemetry phải đo được index lag, stale writes, request races và failure paths.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi chọn cơ chế đồng bộ.
2. Thiết kế retry cùng idempotency, versioning và dead-letter recovery.
3. Đo và kiểm thử các thứ tự hoàn tất bất lợi, không giả định network trả lời theo thứ tự gửi.
4. Xem mọi HTML bên ngoài component là untrusted cho đến khi có bằng chứng ngược lại.
5. Kiểm chứng bằng failure injection và production telemetry thay vì chỉ happy-path tests.
