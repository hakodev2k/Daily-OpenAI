# Code Review Challenge 1 — Elasticsearch index bị lệch sau khi cập nhật sản phẩm

**Chủ đề:** C#/.NET 8, PostgreSQL, Elasticsearch, BackgroundService, eventual consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 45 phút  
**Số vấn đề cần tìm:** Khoảng 9

## Bối cảnh

Một hệ thống thương mại điện tử sử dụng PostgreSQL làm nguồn dữ liệu chính và Elasticsearch phục vụ tìm kiếm. Khi nhân viên chỉnh sửa sản phẩm, API ghi database rồi cập nhật search index. Một worker chạy mỗi 30 giây để đồng bộ những sản phẩm còn pending. Ứng dụng chạy 4 instance trên Azure App Service; mỗi instance có worker riêng. Trong đợt flash sale, một số sản phẩm đã ngừng bán vẫn xuất hiện trong search, có sản phẩm vừa sửa lại quay về giá cũ, và queue pending tăng. Team yêu cầu không mất bản cập nhật, có thể chấp nhận search trễ tối đa 60 giây trong điều kiện bình thường, và không được làm transaction database phụ thuộc Elasticsearch.

## Đoạn code cần review

\`\`\`csharp
public sealed class ProductService(
    ShopDbContext db,
    HttpClient searchHttp)
{
    public async Task UpdateAsync(ProductInput input)
    {
        var product = await db.Products.FindAsync(input.Id)
            ?? throw new KeyNotFoundException();

        product.Name = input.Name;
        product.Price = input.Price;
        product.UpdatedAt = DateTime.UtcNow;
        await db.SaveChangesAsync();

        var response = await searchHttp.PutAsJsonAsync(
            $"/products/_doc/{product.Id}",
            new { product.Id, product.Name, product.Price });

        if (!response.IsSuccessStatusCode)
        {
            product.NeedsIndex = true;
            await db.SaveChangesAsync();
        }
    }
}

public sealed class SearchSyncWorker(
    IServiceScopeFactory scopeFactory,
    HttpClient searchHttp,
    ILogger<SearchSyncWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<ShopDbContext>();

            var pending = await db.Products
                .Where(p => p.NeedsIndex)
                .OrderBy(p => p.UpdatedAt)
                .Take(100)
                .ToListAsync(stoppingToken);

            foreach (var product in pending)
            {
                try
                {
                    await searchHttp.PutAsJsonAsync(
                        $"/products/_doc/{product.Id}",
                        new { product.Id, product.Name, product.Price });
                    product.NeedsIndex = false;
                    await db.SaveChangesAsync(stoppingToken);
                }
                catch (Exception ex)
                {
                    logger.LogError(ex, "Index failed for {Id}", product.Id);
                }
            }

            await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
        }
    }
}

## Kết quả code review tham khảo

### [Critical] — Khoảng trống dual-write làm mất sự kiện cập nhật

**Vấn đề:** \`SaveChangesAsync\` commit trước khi ghi Elasticsearch; \`NeedsIndex\` chỉ được đặt khi có HTTP response lỗi.  
**Tại sao xảy ra:** Crash, cancellation hoặc timeout ở khoảng giữa khiến database đã thay đổi nhưng không có durable work item.  
**Ảnh hưởng production:** Search có thể sai vô thời hạn.  
**Cách sửa:** Ghi dữ liệu sản phẩm và outbox event trong cùng PostgreSQL transaction; worker đọc outbox để đồng bộ.

### [High] — Không kiểm tra status của HTTP response trong worker

**Vấn đề:** Worker coi mọi response HTTP không ném exception là thành công.  
**Tại sao xảy ra:** \`PutAsJsonAsync\` không tự throw cho mọi non-2xx response.  
**Ảnh hưởng production:** 429/503 có thể làm mất pending flag.  
**Cách sửa:** Kiểm tra \`IsSuccessStatusCode\`, phân loại retryable/permanent failures và lưu trạng thái xử lý.

### [High] — Race condition ghi đè document mới bằng document cũ

**Vấn đề:** Hai worker hoặc API và worker cùng ghi cùng document mà không có version guard.  
**Tại sao xảy ra:** Request đến Elasticsearch có thể đảo thứ tự; timestamp \`UpdatedAt\` không phải version monotonic đáng tin cậy.  
**Ảnh hưởng production:** Giá cũ hoặc trạng thái cũ xuất hiện trở lại.  
**Cách sửa:** Sử dụng version tăng đơn điệu theo product và Elasticsearch external versioning phù hợp, hoặc serialize updates theo key; xử lý version conflict như superseded event, không coi là lỗi cần retry vô hạn.

### [High] — Pending flag có thể bị clear sau một update mới

**Vấn đề:** Worker đọc snapshot cũ; API update mới; worker save \`NeedsIndex=false\` không có điều kiện version.  
**Tại sao xảy ra:** Không có claim/compare-and-set theo version của work item.  
**Ảnh hưởng production:** Bỏ qua bản cập nhật mới.  
**Cách sửa:** Claim outbox event bằng lease, chỉ mark event cụ thể đã xử lý, không dùng boolean chung.

### [High] — Không xử lý xóa sản phẩm

**Vấn đề:** Worker chỉ index các row còn tồn tại.  
**Tại sao xảy ra:** Delete xóa luôn nguồn để worker tìm.  
**Ảnh hưởng production:** Ghost products trong search.  
**Cách sửa:** Durable tombstone event \`ProductDeleted\`; index delete theo version và thiết kế retention/tombstone chống event cũ hồi sinh.

### [Medium] — Request không truyền CancellationToken và response không dispose

**Vấn đề:** API không nhận cancellation; worker bỏ qua token khi gửi HTTP và không dispose response.  
**Tại sao xảy ra:** Không có bounded per-request timeout và cancellation propagation.  
**Ảnh hưởng production:** Shutdown chậm, giữ tài nguyên và tăng backlog.  
**Cách sửa:** Truyền token, giới hạn timeout, \`using\` response.

### [Medium] — Không có retry policy, backoff, dead-letter

**Vấn đề:** Worker thử lại sau 30 giây vô hạn, không phân biệt lỗi mapping 400 với 429/503.  
**Tại sao xảy ra:** Không lưu attempt, next attempt, error category.  
**Ảnh hưởng production:** Poison events chiếm capacity; quá tải khi dependency phục hồi.  
**Cách sửa:** Exponential backoff có jitter, giới hạn retry, dead-letter/quarantine và quy trình replay.

### [Medium] — Nhiều worker cùng quét, không claim công việc

**Vấn đề:** Mỗi instance chọn cùng 100 rows.  
**Tại sao xảy ra:** Query không có cơ chế ownership/lease.  
**Ảnh hưởng production:** Duplicate requests, tăng latency và conflict.  
**Cách sửa:** PostgreSQL \`FOR UPDATE SKIP LOCKED\` trong transaction claim ngắn hoặc atomic lease update; không giữ DB lock trong lúc gọi HTTP.

### [Medium] — Thiếu telemetry về độ trễ đồng bộ

**Vấn đề:** Chỉ log exception, không đo outbox age, lag, failure ratio, conflict và throughput.  
**Tại sao xảy ra:** Chưa định nghĩa SLO cho search freshness.  
**Ảnh hưởng production:** Phát hiện trễ và không chứng minh được yêu cầu 60 giây.  
**Cách sửa:** Structured logs, correlation ID, queue age p95/p99, retries, failed events, document version và reconciliation dashboard.

## Phiên bản đề xuất

Thiết kế sau là skeleton minh họa **transactional outbox + claim + versioned indexing**. Phần claim, version và HTTP adapter phải được triển khai/kiểm thử với phiên bản PostgreSQL và Elasticsearch thực tế. Giả định product có \`Version\` tăng atomically trong DB và mọi đường cập nhật đều đi qua cùng transaction.

\`\`\`csharp
public async Task UpdateProductAsync(
    ProductInput input, CancellationToken ct)
{
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    var product = await db.Products.SingleAsync(x => x.Id == input.Id, ct);

    product.Name = input.Name;
    product.Price = input.Price;
    product.Version++; // Chỉ an toàn nếu có optimistic concurrency token.
    db.Outbox.Add(new SearchOutboxEvent
    {
        EventId = Guid.NewGuid(),
        ProductId = product.Id,
        ProductVersion = product.Version,
        Kind = "ProductUpsert",
        PayloadJson = JsonSerializer.Serialize(new
        {
            product.Id, product.Name, product.Price
        }),
        CreatedAtUtc = DateTime.UtcNow,
        NextAttemptAtUtc = DateTime.UtcNow
    });

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
}
\`\`\`

\`Product.Version\` cần được cấu hình concurrency token và xử lý \`DbUpdateConcurrencyException\` bằng reload/retry có giới hạn; \`Version++\` đơn thuần không bảo đảm monotonic khi concurrent writers. Với PostgreSQL có thể dùng row lock hoặc atomic update trả về version mới. Transaction outbox phải dùng cùng DbContext/connection với product.

\`\`\`csharp
public async Task ProcessClaimedAsync(
    SearchOutboxEvent item, CancellationToken ct)
{
    using var request = new HttpRequestMessage(
        HttpMethod.Put, $"/products/_doc/{item.ProductId}?version={item.ProductVersion}&version_type=external");

    request.Content = new StringContent(
        item.PayloadJson, Encoding.UTF8, "application/json");

    using var response = await searchHttp.SendAsync(request, ct);

    if (response.IsSuccessStatusCode)
    {
        await outbox.MarkCompletedIfOwnedAsync(item.EventId, item.LeaseToken, ct);
        return;
    }

    if (response.StatusCode == HttpStatusCode.Conflict)
    {
        // Chỉ mark superseded sau khi xác minh conflict là version cũ.
        await outbox.MarkSupersededIfOwnedAsync(item.EventId, item.LeaseToken, ct);
        return;
    }

    await outbox.ScheduleRetryOrQuarantineAsync(
        item.EventId, item.LeaseToken, (int)response.StatusCode, ct);
}
\`\`\`

Worker claim một batch bằng transaction ngắn, gán \`LeaseToken\`, \`LeaseUntilUtc\` và \`AttemptCount\`, rồi commit trước khi gọi Elasticsearch. Worker chỉ hoàn tất event nếu còn giữ lease. Cần xử lý expired lease, timeout, network exception và event delete riêng. \`version_type=external\` là lựa chọn cần xác minh với Elasticsearch version triển khai; version phải là số nguyên dương tăng đơn điệu và nằm trong phạm vi hợp lệ. Để tránh việc document đã bị xóa bị event cũ tạo lại sau khi tombstone hết hạn, cần retention/reconciliation strategy phù hợp, không chỉ gọi DELETE.

## Giải thích thiết kế sau khi sửa

PostgreSQL là source of truth; outbox bảo đảm thay đổi business và ý định đồng bộ được commit cùng nhau. Worker có thể xử lý at-least-once; duplicate delivery không được làm sai kết quả. Lease giảm công việc trùng nhưng không thay thế idempotency/version ordering. API có thể trả thành công khi DB commit và công khai rằng search cập nhật bất đồng bộ. Cần reconciliation định kỳ giữa source DB và index để phát hiện drift.

## Trade-offs

- Outbox thêm bảng, storage, cleanup và monitoring nhưng loại bỏ khoảng trống dual-write.
- External versioning yêu cầu version đúng và cách xử lý delete; không phải phép màu bảo đảm consistency.
- Batch indexing tăng throughput nhưng có thể tăng latency và độ phức tạp khi xử lý partial failures.
- Một worker đơn giản có thể đủ khi tải thấp; nhiều worker chỉ có ích khi đo được bottleneck.
- Nếu search freshness cần strong consistency, Elasticsearch async index không đáp ứng; cân nhắc query source-of-truth cho những quyết định quan trọng như checkout.

## Cách kiểm thử

1. **Integration test:** Crash sau DB commit nhưng trước index request; outbox vẫn tồn tại và worker replay thành công.
2. **Concurrency test:** Hai update cùng product và nhiều worker; version mới nhất thắng, không mất event.
3. **Failure-path test:** HTTP 429/503, timeout sau server-side success, mapping 400; retry/quarantine đúng.
4. **Database test:** Expired lease được reclaim, stale worker không mark event của owner mới.
5. **Reconciliation test:** Delete rồi replay event cũ; search không hồi sinh sản phẩm trái chính sách.

## Quan sát trong production

Theo dõi \`outbox_pending\`, \`oldest_pending_age_seconds\`, \`index_success_rate\`, HTTP status, retry attempts, quarantine count, version conflict count và p95 end-to-end freshness. Gắn \`EventId\`, \`ProductId\`, \`ProductVersion\`, trace ID vào structured logs/Application Insights; không log toàn bộ payload nhạy cảm. Alert khi p95 freshness vượt 60 giây liên tục hoặc oldest pending tăng dù worker vẫn healthy. So sánh sample DB/index version để phát hiện drift.

[HttpGet("orders")]
public async Task<IActionResult> GetOrders(
    [FromQuery] Guid tenantId,
    [FromQuery] string? status,
    [FromQuery] string? search,
    [FromQuery] int page = 1,
    [FromQuery] int pageSize = 50)
{
    var query = db.Orders.Include(o => o.Customer).AsQueryable();

    if (tenantId != Guid.Empty)
        query = query.Where(o => o.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(status))
        query = query.Where(o => o.Status == status);

    if (!string.IsNullOrWhiteSpace(search))
        query = query.Where(o => o.OrderNumber.Contains(search));

    var count = await query.CountAsync();

    var orders = await query
        .OrderByDescending(o => o.CreatedAtUtc)
        .Skip((page - 1) * pageSize)
        .Take(pageSize)
        .ToListAsync();

    return Ok(new
    {
        total = count,
        items = orders.Select(o => new
        {
            o.Id,
            o.TenantId,
            o.OrderNumber,
            o.Status,
            o.Total,
            customerName = o.Customer.Name
        })
    });
}

## Kết quả code review tham khảo

### [Critical] — Tenant isolation dựa vào tham số do client kiểm soát

**Vấn đề:** API cho phép \`tenantId=Guid.Empty\` để bỏ tenant filter và chấp nhận tenant bất kỳ.  
**Tại sao xảy ra:** Thiếu server-side authorization/tenant scope.  
**Ảnh hưởng production:** Cross-tenant data exposure.  
**Cách sửa:** Resolve allowed tenant từ verified claims/server-side membership; áp dụng tenant predicate bắt buộc. Với multi-tenant admin, kiểm tra quyền truy cập tenant được yêu cầu; cân nhắc database row-level security như defense in depth.

### [High] — Offset pagination không ổn định khi có insert

**Vấn đề:** \`Skip\` theo page number trong dataset liên tục thay đổi.  
**Tại sao xảy ra:** New rows dịch chuyển vị trí offset giữa requests.  
**Ảnh hưởng production:** Duplicate/missing rows giữa các trang.  
**Cách sửa:** Keyset cursor theo \`(CreatedAtUtc, Id)\` cho navigation tuần tự; nếu cần snapshot nhất quán xuyên nhiều requests, thêm snapshot boundary hoặc thiết kế snapshot riêng.

### [High] — ORDER BY không unique

**Vấn đề:** Nhiều orders có cùng \`CreatedAtUtc\`.  
**Tại sao xảy ra:** Không có tie-breaker deterministic.  
**Ảnh hưởng production:** Row ordering có thể đổi ngay cả khi không insert.  
**Cách sửa:** \`OrderByDescending(CreatedAtUtc).ThenByDescending(Id)\`, cursor gồm cả hai trường.

### [High] — Page input không có giới hạn

**Vấn đề:** \`page\` âm, \`pageSize\` cực lớn và overflow của phép nhân.  
**Tại sao xảy ra:** Thiếu validation/maximum page size.  
**Ảnh hưởng production:** 500 errors, high memory, excessive DB load.  
**Cách sửa:** Validate range, cap page size, dùng opaque cursor có kiểm tra và giới hạn.

### [Medium] — Query materialize entity và navigation quá rộng

**Vấn đề:** \`Include(Customer)\` rồi \`ToListAsync\` load entities và change tracking mặc định.  
**Tại sao xảy ra:** Projection sau materialization thay vì SQL projection.  
**Ảnh hưởng production:** Tăng allocations, payload từ DB, GC pressure.  
**Cách sửa:** \`AsNoTracking\` và \`Select\` trực tiếp trước \`ToListAsync\`; chỉ lấy các fields cần thiết.

### [Medium] — Count mỗi request có thể đắt

**Vấn đề:** \`CountAsync\` chạy query riêng trước page query.  
**Tại sao xảy ra:** UI contract buộc exact count cho mỗi request.  
**Ảnh hưởng production:** Scan/count cost và hai queries không nhất thiết cùng snapshot.  
**Cách sửa:** Thống nhất UX \`hasMore\` thay exact total; nếu cần total, tính riêng/cached/approximate với nhãn rõ ràng.

### [Medium] — Search \`Contains\` có thể gây scan

**Vấn đề:** Substring search trên \`OrderNumber\` không chắc sử dụng index seek.  
**Tại sao xảy ra:** SQL translation có thể tạo pattern không sargable, phụ thuộc provider/collation.  
**Ảnh hưởng production:** CPU/IO tăng khi tenant lớn.  
**Cách sửa:** Xác minh SQL thực tế; nếu business cho phép, exact/prefix search với index phù hợp; substring search cần giải pháp search/index chuyên biệt.

### [Medium] — Không có cancellation, observability và query-plan validation

**Vấn đề:** Request cancellation không truyền đến EF; không đo query count, logical reads và wait stats.  
**Tại sao xảy ra:** Endpoint không có telemetry/performance budget.  
**Ảnh hưởng production:** Request bỏ dở vẫn tốn tài nguyên; tối ưu mù.  
**Cách sửa:** Truyền \`CancellationToken\`, gắn tracing, đo p95/p99 và actual execution plan trước/sau.

## Phiên bản đề xuất

Giả định endpoint chỉ cho tenant đã xác thực, cursor do server ký hoặc xác thực integrity, và filter giữ nguyên khi chuyển trang. Ví dụ dùng \`Id\` là GUID; thứ tự GUID chỉ dùng làm tie-breaker ổn định, không biểu thị thời gian. Mẫu này minh họa first page và next page; production phải mã hóa/kiểm tra cursor, ràng buộc filter và tenant, không tin giá trị client tự khai.

\`\`\`csharp
public sealed record OrderCursor(DateTime CreatedAtUtc, Guid Id);
public sealed record OrderRow(
    Guid Id, string OrderNumber, string Status,
    decimal Total, string CustomerName);

public async Task<OrderPage> ListOrdersAsync(
    Guid authorizedTenantId,
    string? status,
    string? orderNumberPrefix,
    OrderCursor? after,
    int requestedSize,
    CancellationToken ct)
{
    var size = Math.Clamp(requestedSize, 1, 100);

    var query = db.Orders.AsNoTracking()
        .Where(o => o.TenantId == authorizedTenantId);

    if (!string.IsNullOrWhiteSpace(status))
        query = query.Where(o => o.Status == status);

    if (!string.IsNullOrWhiteSpace(orderNumberPrefix))
        query = query.Where(o => o.OrderNumber.StartsWith(orderNumberPrefix));

    if (after is not null)
        query = query.Where(o =>
            o.CreatedAtUtc < after.CreatedAtUtc ||
            (o.CreatedAtUtc == after.CreatedAtUtc && o.Id.CompareTo(after.Id) < 0));

    var rows = await query
        .OrderByDescending(o => o.CreatedAtUtc)
        .ThenByDescending(o => o.Id)
        .Select(o => new
        {
            o.Id, o.CreatedAtUtc, o.OrderNumber,
            o.Status, o.Total, CustomerName = o.Customer.Name
        })
        .Take(size + 1)
        .ToListAsync(ct);

    var pageRows = rows.Take(size).ToList();
    var last = pageRows.LastOrDefault();

    return new OrderPage(
        pageRows.Select(o => new OrderRow(
            o.Id, o.OrderNumber, o.Status, o.Total, o.CustomerName)).ToList(),
        rows.Count > size && last is not null
            ? new OrderCursor(last.CreatedAtUtc, last.Id)
            : null);
}

**Lưu ý triển khai:** \`Guid.CompareTo\` trong LINQ phải được xác minh là translatable và có cùng ordering semantics với SQL Server provider/collation. Để tránh phụ thuộc vào khả năng translation này, dùng key sắp xếp dạng \`long\`/sortable sequence duy nhất hoặc viết SQL keyset predicate được kiểm chứng trên provider. Cursor phải bind với \`tenantId\`, \`status\`, \`prefix\`, expiry và version của contract. Endpoint cần trả 400 cho cursor không hợp lệ, không âm thầm reset trang. \`authorizedTenantId\` phải được resolve từ authorization service, không lấy trực tiếp từ query parameter.

## Giải thích thiết kế sau khi sửa

Keyset pagination tránh quét/bỏ qua lượng lớn rows ở trang sâu khi có index hỗ trợ. Ordering unique loại bỏ nondeterministic ties; keyset giữ navigation ổn định hơn offset trong trường hợp insert mới phía trước cursor. Tuy nhiên update \`CreatedAtUtc\` hoặc thay đổi filter/status vẫn có thể làm item chuyển trang; nếu yêu cầu consistent snapshot tuyệt đối, cần cơ chế snapshot riêng. Projection giảm dữ liệu materialize; \`size+1\` cho phép xác định \`hasMore\` mà không bắt buộc count.

Index candidate để kiểm chứng với execution plan: \`(TenantId, CreatedAtUtc DESC, Id DESC)\` INCLUDE các cột select phù hợp. Nếu \`Status\` được filter thường xuyên và đủ selective, thử index \`(TenantId, Status, CreatedAtUtc DESC, Id DESC)\`. Không tạo cả hai chỉ vì trực giác; đo logical reads, actual plan, writes overhead và thống kê dữ liệu.

## Trade-offs

- Cursor không hỗ trợ nhảy trực tiếp tới page 100 như offset; phù hợp infinite scroll hơn numbered pages.
- Extra index tăng storage và write amplification; lựa chọn phụ thuộc workload.
- Exact total count có thể là requirement thật; tách count endpoint hoặc snapshot có thể cần thiết.
- SQL Server và EF Core translation khác theo version; kiểm chứng SQL thực tế thay vì giả định.
- Tenant-level authorization phải được áp dụng xuyên mọi endpoint, kể cả export và count.

## Cách kiểm thử

1. **Security integration test:** User tenant A gửi tenant B hoặc bỏ tenant; không trả bất kỳ row tenant B.
2. **Database test:** Nhiều orders cùng timestamp, đi hết pages không trùng/mất row trên dataset tĩnh.
3. **Concurrency test:** Insert liên tục trong lúc scroll; xác nhận semantics đã cam kết và không duplicate do offset shift.
4. **Load test:** Tenant 2 triệu orders, so sánh p95/p99, logical reads và plan của trang đầu/cuối.
5. **API test:** Cursor bị sửa, sai tenant/filter, hết hạn và page size quá lớn bị từ chối/giới hạn đúng.

## Quan sát trong production

Đo \`orders_list_duration_ms\` theo tenant-size bucket, query duration, logical reads, CPU, SQL waits, connection pool usage, 400 cursor validation, p95/p99 và cancellation rate. Gắn trace ID từ React tới ASP.NET Core và SQL dependency trong Application Insights. Không ghi raw tenant-sensitive cursor hay dữ liệu khách hàng vào logs. Alert khi p95 vượt SLO hoặc logical reads/page tăng bất thường; kiểm tra execution plan regression sau deploy.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product yêu cầu jump-to-page và exact total, bạn thiết kế hybrid pagination thế nào?
2. Nếu \`Status\` thay đổi giữa các page, contract nào đủ rõ để tránh người dùng hiểu sai?
3. Bạn sẽ xác minh một index mới có thực sự cải thiện workload tổng thể thay vì chỉ một query như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Transactional outbox bảo vệ khoảng trống giữa source-of-truth commit và asynchronous indexing; at-least-once delivery cần versioning/idempotency.
- Elasticsearch là read model có độ trễ; không dùng search index như nguồn quyết định tồn kho, giá thanh toán hay quyền truy cập.
- Tenant authorization phải được quyết định ở server; query parameter không phải bằng chứng quyền.
- Keyset pagination cần unique ordering, cursor integrity và index phù hợp; không tự động bảo đảm snapshot consistency.
- Tối ưu database dựa trên actual execution plan, logical reads, workload và p95/p99.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và transaction boundary trước khi chọn retry.
2. Thiết kế failure path cùng với idempotency và ordering.
3. Kiểm tra authorization trước performance.
4. Đo execution plan trước khi thêm index hoặc cache.
5. Phân biệt dữ liệu nhất quán tại một thời điểm với kết quả ổn định qua nhiều requests.
