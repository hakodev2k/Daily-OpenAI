# Câu 1 — File export lớn, LOH và vòng đời buffer trong ASP.NET Core

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C# memory, GC, LOH, ArrayPool<T>, async streaming, cancellation, observability.

## Bối cảnh

Một ASP.NET Core .NET 8 API xuất CSV từ PostgreSQL. Mỗi request xuất khoảng 150–500 MB; 30 request đồng thời trong giờ cao điểm. Nhóm hiện dùng `MemoryStream`, tạo `byte[]` cho toàn bộ file rồi gọi `File(bytes, "text/csv")`. Sau release, working set tăng mạnh, GC pause xuất hiện và p99 latency tăng. CPU SQL không tăng đáng kể. Nhóm đề xuất dùng `ArrayPool<byte>.Shared` và gọi `GC.Collect()` sau mỗi request.

## Câu hỏi chính

Giải thích cơ chế allocation, LOH, GC và ownership của buffer khiến endpoint có thể tăng áp lực bộ nhớ; thiết kế cách xuất file an toàn khi client chậm hoặc hủy kết nối, đồng thời nêu phép đo chứng minh nguyên nhân trước khi sửa.

## Câu hỏi làm rõ nên cân nhắc

1. Dữ liệu đang được materialize ở EF Core/Npgsql hay stream từ `DbDataReader`?
2. Kích thước từng allocation và số request đồng thời thực tế là bao nhiêu?
3. Có yêu cầu biết trước `Content-Length`, hỗ trợ retry/range download hay không?
4. Có proxy/CDN buffering, timeout và giới hạn export nào?
5. Metrics đang phản ánh managed heap, native memory hay container working set?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt tổng kích thước file với kích thước từng object được cấp phát.

### Gợi ý 2
Theo dõi thế hệ GC, Large Object Heap, tốc độ allocation và số buffer còn sống đồng thời.

### Gợi ý 3
Đặt câu hỏi ai sở hữu buffer, khi nào được trả pool, và điều gì xảy ra khi response chưa ghi xong hoặc bị cancel.

## Cấu trúc trả lời đề xuất

1. Xác nhận pipeline hiện tại và đo memory/GC dưới tải có kiểm soát.
2. Giải thích allocation, object lifetime, LOH và áp lực concurrent requests.
3. So sánh materialization, pooled buffering, streaming và export bất đồng bộ.
4. Thiết kế cancellation, backpressure, giới hạn tải và xử lý lỗi.
5. Chứng minh cải thiện bằng load test và production telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `MemoryStream.ToArray()` tạo bản sao; một số bước encoding/materialization tạo thêm bản sao lớn.
- Object lớn (thường từ khoảng 85 KB) có thể được cấp phát trên LOH; không đồng nghĩa tất cả memory tăng là memory leak.
- GC không giải phóng object còn reference; ép `GC.Collect()` trên hot path có thể tăng pause.
- `ArrayPool<T>` chỉ tái sử dụng buffer; không loại bỏ nhu cầu giới hạn số buffer, bảo đảm return đúng lúc và tránh dùng sau return.
- Streaming trực tiếp vào response hỗ trợ backpressure và `RequestAborted`.

### Điểm cộng
- Đo `dotnet-counters`, allocation profile, GC heap size, LOH size, Gen2 count, p95/p99, số export đang chạy và database query duration.
- Dùng bounded concurrency, `CommandBehavior.SequentialAccess`, `AsNoTracking`/projection hoặc `DbDataReader` tùy implementation.
- Nếu export kéo dài, cân nhắc background job + Azure Blob Storage với lifecycle và authorization.

### Senior+
- Phân tích memory budget theo `peak_buffer_per_request × concurrent_requests` cùng các object khác, phân biệt fragmentation và leak.
- Thiết kế download contract, retry, idempotent export job, retention và bảo mật dữ liệu nhạy cảm.

## Hướng giải quyết tham khảo

**Giả định:** Client có thể nhận chunked response, không bắt buộc `Content-Length`, dữ liệu đọc theo từng row và mỗi row có thể encode incrementally. Khi đó không nên tạo toàn bộ file trong RAM. Dùng writer gắn với `HttpResponse.BodyWriter` hoặc `StreamWriter(Response.Body, ...)`; ghi header, lần lượt đọc row từ database, escape CSV đúng quy tắc, `await WriteAsync` và `FlushAsync` theo batch; truyền cancellation từ `HttpContext.RequestAborted` xuống DB. Nếu đã bắt đầu gửi response, không thể đổi sang JSON ProblemDetails khi lỗi giữa stream: cần ghi log và kết thúc kết nối; client phải biết file không hoàn chỉnh.

**Cơ chế:** `MemoryStream` có thể mở rộng capacity bằng cấp phát buffer mới; `ToArray` tạo thêm mảng riêng. Với 30 request × 500 MB, riêng một bản sao/file đã tương đương khoảng 15 GB dữ liệu sống tại cùng thời điểm, chưa kể encoding, query buffering và các bản sao khác. LOH là phân vùng của managed heap dành cho object lớn; object còn sống được giữ qua GC, không được giải quyết bằng gọi GC cưỡng bức. Working set không phải phép đo trực tiếp dung lượng object còn sống.

**ArrayPool:** Chỉ thuê buffer kích thước vừa đủ cho một batch; dùng `try/finally` để trả, không return khi asynchronous write còn dùng buffer; không giữ pooled buffer trong cache hay trả cho caller vượt quá lifetime. Buffer chứa thông tin nhạy cảm cần cân nhắc clear khi return; pool có thể giữ memory để tái sử dụng.

**Kiểm soát:** Áp dụng semaphore hoặc hàng đợi giới hạn số export đồng thời; giới hạn số hàng, thời gian, kích thước, quyền truy cập. Với báo cáo 500 MB và nhiều người tải, tạo job, lưu kết quả vào Blob, trả trạng thái và đường dẫn tải có thời hạn thường ổn định hơn; đổi lại cần storage, cleanup và quản lý quyền. Nếu client bắt buộc `Content-Length`, có thể tạo file tạm/Blob trước rồi stream, không phải materialize trong RAM.

**Xác minh:** A/B benchmark trên cùng dataset và concurrency; so sánh allocation rate, peak managed heap, Gen2 GC, p99, timeout, throughput, số request bị cancel. Xem cả SQL reader lifetime và connection pool để tránh chuyển nút thắt từ memory sang DB.

## Mẫu trả lời trong phỏng vấn

“Tôi chưa kết luận memory leak chỉ từ working set. Trước tiên tôi xác định endpoint có giữ toàn bộ CSV trong `MemoryStream` và có `ToArray` hay không, rồi đo allocation rate, LOH, Gen2 GC và số export đồng thời. Với file hàng trăm MB, một request có thể giữ nhiều bản sao lớn; khi nhiều request chạy cùng lúc, memory tăng và GC pressure là hợp lý. Tôi không thêm `GC.Collect()` vì không xử lý được object còn sống và có thể tăng pause. Nếu contract cho phép, tôi stream từng row ra response, truyền cancellation tới DB và giới hạn concurrency. `ArrayPool` chỉ phù hợp cho buffer ngắn hạn có ownership rõ ràng. Nếu cần tải lại hoặc file rất lớn, tôi cân nhắc background export ra Blob. Tôi xác nhận bằng load test có client chậm và hủy kết nối, đồng thời theo dõi memory, p99 và connection pool. Quyết định cuối phụ thuộc yêu cầu download, dung lượng và giới hạn tài nguyên.”

## Câu hỏi đào sâu

1. Vì sao `ArrayPool<byte>` không đảm bảo working set giảm ngay sau khi trả buffer?
2. Nếu response đã gửi 80 MB rồi DB lỗi, API nên báo lỗi thế nào?
3. Nếu client cần resumable download và audit trail, bạn còn chọn streaming trực tiếp không?

## Lỗi trả lời thường gặp

- Đồng nhất working set tăng với memory leak.
- Ép `GC.Collect()` cho mọi request.
- Nghĩ `ArrayPool` tự động giải quyết mọi allocation hoặc quên buffer ownership.
- Chuyển sang streaming nhưng vẫn `ToListAsync()` toàn bộ query.
- Không test client chậm, cancellation và giới hạn đồng thời.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Làm rõ contract, tải và allocation path | 1.5 |
| Giải thích đúng GC/LOH/ownership | 2.5 |
| Chẩn đoán có metrics và hypothesis | 2 |
| Thiết kế streaming, cancellation, load protection | 2 |
| Trade-offs, testing, observability, trình bày | 2 |
| **Tổng** | **10** |

# Câu 2 — Kubernetes rollout báo Ready nhưng API vẫn 502

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core health checks, deployment, network troubleshooting, incident response, observability.

## Bối cảnh

Một ASP.NET Core .NET 8 API chạy trên Kubernetes, phía trước là Ingress và một reverse proxy. Sau khi cập nhật container image, tỷ lệ 502 tăng từ gần 0 lên 4% trong 12 phút. Deployment hiển thị `availableReplicas=6`, không có pod CrashLoopBackOff. Lỗi tập trung trong lúc rolling update và một số request dài bị ngắt. CPU và memory không vượt limits. Pipeline TeamCity đã build image; Octopus Deploy triển khai manifest. Nhóm chưa biết 502 do ingress, readiness, termination, DNS, dependency hay application.

## Câu hỏi chính

Bạn là incident lead. Hãy trình bày quy trình giảm ảnh hưởng, thu thập bằng chứng, kiểm chứng các giả thuyết cạnh tranh, sửa lỗi trước mắt và thiết kế release/health/termination để tránh lặp lại mà không mặc định một nguyên nhân duy nhất.

## Câu hỏi làm rõ nên cân nhắc

1. 502 do thành phần nào phát sinh, ingress hay upstream reverse proxy?
2. Thời điểm lỗi có trùng pod termination, endpoint removal hoặc upstream reset không?
3. Readiness/liveness/startup probes đang gọi endpoint nào và kiểm tra những dependency gì?
4. `terminationGracePeriodSeconds`, `preStop`, request timeout và drain behavior là gì?
5. Có khác biệt image digest, environment config, service selectors hoặc connection draining giữa phiên bản?

## Gợi ý tư duy

### Gợi ý 1
Đừng coi `Ready` là bằng chứng request end-to-end chắc chắn thành công.

### Gợi ý 2
Liên kết từng 502 với pod UID, deployment revision, upstream address và lifecycle events.

### Gợi ý 3
So sánh thời điểm pod ngừng nhận traffic, process bắt đầu shutdown và các request in-flight hoàn thành.

## Cấu trúc trả lời đề xuất

1. Đánh giá ảnh hưởng theo endpoint, user, SLO và thời điểm.
2. Stabilize bằng pause rollout/rollback nếu phù hợp.
3. Lập timeline từ deploy, ingress logs, traces và Kubernetes events.
4. Phân loại lỗi: no endpoint, connection refused, upstream reset, timeout, application failure.
5. Kiểm tra hypotheses và làm thay đổi có kiểm soát.
6. Fix, test canary, theo dõi và phòng ngừa.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Tách 502 từ proxy với 5xx từ application; quan sát upstream response/error details.
- Không khẳng định readiness đồng nghĩa request đã drain.
- Ưu tiên rollback/pause khi impact vượt ngưỡng; giữ evidence và tránh thay nhiều biến cùng lúc.
- Kiểm tra readiness, termination lifecycle, endpoints, ingress timeout và request duration.
- Thiết kế test rollout under load và metrics theo revision.

### Điểm cộng
- Phân biệt liveness (restart khi không phục hồi), readiness (điều phối traffic) và startup probe (cho khởi động chậm).
- Kiểm tra service endpoint propagation delay, `SIGTERM`, Kestrel graceful shutdown, proxy keep-alive và long-running requests.
- Xác thực image digest/config parity giữa TeamCity và Octopus, rollback DB migration compatibility.

### Senior+
- Đặt error budget/rollback gate, canary và traffic draining với timeout tương thích.
- Xây timeline causal từ distributed tracing, ingress access/error logs, Kubernetes events và application logs.

## Hướng giải quyết tham khảo

**Impact/stabilization:** Xác nhận 502 thuộc user journey nào, tỷ lệ theo deployment revision, và ảnh hưởng thanh toán/đăng nhập nếu có. Nếu lỗi tăng ngay sau rollout và rollback an toàn với schema hiện tại, pause rollout và rollback image/manifest; không rollback schema một cách mù quáng. Giữ snapshot events, deployment spec và ingress logs trước khi pod cũ biến mất.

**Bằng chứng:** Thu thập ingress access/error log (upstream IP, connect/read time, reset reason), request ID, `traceparent`, pod UID, `kubectl describe pod`, events, EndpointSlice membership, readiness transition, restart count, container logs, request duration. Đối chiếu thời gian UTC nhất quán và đánh dấu mỗi request lỗi theo revision.

**Giả thuyết cạnh tranh:**
- *Termination race*: Pod nhận `SIGTERM` trong lúc ingress/service vẫn gửi traffic hoặc in-flight request bị ngắt; xác minh bằng correlation giữa 502, pod deletion timestamp và upstream reset.
- *Probe sai*: readiness endpoint trả 200 trước khi app đủ điều kiện phục vụ hoặc kiểm tra sai port/path; xác minh bằng probe config, direct pod test, logs khởi động.
- *Timeout mismatch*: Ingress/proxy timeout ngắn hơn request dài; so sánh duration phân phối và error reason.
- *Network/endpoint*: service selector, EndpointSlice propagation, port mismatch hoặc transient network; kiểm tra connection refused/no healthy upstream.
- *Application/dependency*: process trả lỗi hoặc reset do downstream connection; kiểm tra application traces, connection pool, DNS, external calls.

**Remediation có điều kiện:** Nếu termination race được chứng minh, bảo đảm readiness chuyển sang false trước khi shutdown, có thời gian drain đủ cho endpoint propagation và requests, cấu hình grace period phù hợp, và ứng dụng xử lý `SIGTERM` gracefully. `preStop` delay có thể hỗ trợ nhưng không phải bảo đảm phổ quát; phải đo. Nếu timeout mismatch, điều chỉnh cả request contract và proxy timeouts; job dài nên chuyển sang async API. Nếu probe sai, tách `/health/live` và `/health/ready`, tránh liveness phụ thuộc DB tạm thời làm restart hàng loạt.

**Prevention:** Canary 1 pod, load test khi rollout và scale-down, request dài, dependency degradation, connection drain; deploy immutable image digest, validate config diff, giữ backward-compatible migrations, alert theo 502 by revision, upstream reset và unavailable endpoints. Rollback tự động chỉ khi signal đủ đáng tin cậy.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận 502 do proxy nào phát sinh, scope impact và mối liên hệ với rollout. Nếu ảnh hưởng vượt SLO, tôi pause rollout hoặc rollback khi tương thích dữ liệu, đồng thời giữ log và events. `availableReplicas=6` không chứng minh đường đi ingress đến pod luôn hoạt động. Tôi tạo timeline kết hợp upstream reset, pod termination, readiness transitions, request IDs và traces. Tôi kiểm tra ít nhất termination race, probe sai, timeout mismatch và endpoint/network issue, rồi dùng log để loại trừ. Nếu là termination race, tôi sửa readiness/draining và grace period dựa trên request duration thực tế; nếu timeout, điều chỉnh contract và timeouts. Cuối cùng tôi chạy rollout dưới tải, canary và alert theo revision. Tôi không chọn fix chỉ từ một biểu đồ CPU.”

## Câu hỏi đào sâu

1. Tại sao tăng `terminationGracePeriodSeconds` một mình có thể không loại bỏ 502?
2. Khi dependency DB bị outage 30 giây, readiness và liveness nên phản ứng thế nào?
3. Nếu rollback image vẫn còn 502, bạn ưu tiên kiểm tra giả thuyết nào tiếp theo?

## Lỗi trả lời thường gặp

- Kết luận ngay “Kubernetes bug” khi chưa xác định nguồn 502.
- Chỉ nhìn CPU/memory và pod Ready.
- Tăng mọi timeout mà không kiểm tra request contract.
- Dùng liveness kiểm tra dependency dễ lỗi tạm thời.
- Không xem xét rollback compatibility và request in-flight.

## Thang điểm 0–10

| Tiêu chí | Điểm |
|---|---:|
| Impact và stabilization có kiểm soát | 1.5 |
| Evidence/timeline và hypothesis cạnh tranh | 2.5 |
| Hiểu lifecycle, probes, ingress và request drain | 2.5 |
| Fix có điều kiện, rollback/canary | 1.5 |
| Testing, telemetry và giao tiếp incident | 2 |
| **Tổng** | **10** |

# Câu 3 — Thiết kế notification platform có preference, audit và giới hạn nhà cung cấp

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** .NET, PostgreSQL, Azure Service Bus, transactional Outbox, security, API contracts, system design.

## Bối cảnh

Một nền tảng nội bộ hiện có ASP.NET Core Modular Monolith và PostgreSQL cần gửi email, in-app notification và webhook cho khoảng 100.000 nhân viên. Sự kiện gồm approval, thay đổi quyền và nhắc lịch. Một số thông báo bảo mật phải gửi kịp thời; marketing/nhắc lịch được phép trễ. Người dùng có preferences theo channel, nhưng policy có thể bắt buộc một số thông báo. Nhà cung cấp email có rate limit và đôi lúc timeout. Product muốn audit, retry và không gửi lặp gây khó chịu. Đội ngũ vận hành nhỏ, đã có Azure App Service và đang cân nhắc Azure Service Bus.

## Câu hỏi chính

Hãy thiết kế kiến trúc và rollout strategy với contract, data ownership, transaction boundary, delivery guarantees, preference enforcement và failure recovery. So sánh bắt đầu bằng Modular Monolith + worker với tách microservice, và khi nào messaging là đáng giá.

## Câu hỏi làm rõ nên cân nhắc

1. “Gửi đúng một lần” nghĩa là exactly-once dispatch hay exactly-once user-visible delivery?
2. SLO cho security notification, reminder và webhook khác nhau ra sao?
3. Preference nào được phép override, có quiet hours và yêu cầu pháp lý nào?
4. Có yêu cầu thứ tự per user, multi-tenant, dữ liệu nhạy cảm và retention không?
5. Có thể nhận callback/provider message ID để reconciliation không?

## Gợi ý tư duy

### Gợi ý 1
Tách business event khỏi delivery attempt và trạng thái user-visible.

### Gợi ý 2
Xem xét crash ngay sau commit DB nhưng trước publish message, và crash sau provider accepted nhưng trước ghi DB.

### Gợi ý 3
Không nhầm at-least-once delivery của queue với exactly-once effect ở email/webhook provider.

## Cấu trúc trả lời đề xuất

1. Chốt SLO, policy và consistency requirements.
2. Xác định bounded contexts, data model và APIs.
3. Chọn event/queue và transaction boundary.
4. Thiết kế worker, retries, dedupe, rate limiting và reconciliation.
5. So sánh các deployment choices.
6. Định nghĩa security, observability, testing và rollout.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Phân biệt event creation, message dispatch, provider acceptance và final delivery.
- Dùng transactional Outbox khi event phát sinh trong cùng PostgreSQL transaction với business change.
- Consumer idempotency, bounded retry, exponential backoff/jitter, poison/DLQ và manual replay.
- Preference/policy tại thời điểm thích hợp, có version/audit và cơ chế override hợp lệ.
- Không hứa exactly-once email khi provider không hỗ trợ idempotency.

### Điểm cộng
- `POST /notifications` với idempotency key nếu cho phép request trực tiếp; `GET /notifications/{id}` và user inbox cursor pagination.
- Schema: `Notification`, `DeliveryAttempt`, `Preference`, `OutboxEvent`, `ProviderReceipt`; unique keys cho business event/channel/recipient.
- Per-provider throttling, circuit breaker, backpressure, retention, encryption, signed webhooks và tenant isolation.

### Senior+
- Chọn deployment đơn giản trước khi tách service; đánh giá operational ownership, compliance và failure domain.
- Định nghĩa measurable SLO: event-to-accepted latency, queue age, attempt rate, dedupe ratio, terminal failure, audit integrity.

## Hướng giải quyết tham khảo

**Giả định:** 100.000 nhân viên là tổng user, không phải 100.000 concurrent send; traffic burst và yêu cầu thời gian cần đo trước khi sizing. Chọn một Notification module trong Modular Monolith và một worker riêng, dùng PostgreSQL làm source of truth. Chỉ đưa Azure Service Bus vào khi cần durable buffering, independent scaling hoặc isolation với provider; với lưu lượng nhỏ, DB-backed outbox worker có thể đủ.

**Data model:** `Notification(id, tenantId, recipientId, type, payloadRef, policyVersion, createdAt, status)`; `Delivery(id, notificationId, channel, dedupeKey, status, nextAttemptAt)`; `DeliveryAttempt(id, deliveryId, providerId, outcome, timestamp)`; `Preference(userId, channel, category, version)`; `Outbox(id, eventType, aggregateId, payload, createdAt, publishedAt)`. Unique constraint trên `dedupeKey` theo scope để chống tạo duplicate. Không lưu secrets hoặc PII thừa trong queue payload.

**Flow:** Business transaction ghi state + Outbox. Publisher đọc outbox theo batch, publish rồi đánh dấu published; nếu crash giữa publish và mark, message có thể được publish lại. Worker validate dedupe, áp policy preference với quy tắc snapshot hoặc evaluation-at-send đã thống nhất, ghi delivery state, gọi provider với timeout, bounded concurrency và rate limit. Nếu provider hỗ trợ idempotency key, dùng stable key; nếu không, timeout sau provider acceptance tạo trạng thái *unknown*, cần reconciliation thay vì retry vô hạn. Callback được xác thực chữ ký và xử lý idempotently.

**Consistency:** In-app inbox và audit có thể cần strong consistency trong PostgreSQL; email/webhook thường eventual. Không đảm bảo exactly-once end-to-end chỉ nhờ Service Bus duplicate detection. Với notification bảo mật, định nghĩa rõ mục tiêu “accepted by provider within X” khác “received by user within X”; bổ sung fallback channel khi policy cho phép.

**Security:** Authorization ở API và worker, tenant-scoped queries, encryption in transit/at rest, Managed Identity/Key Vault, signed webhook payload, secret rotation, redaction trong logs, retention và access audit. Không dùng email address trong correlation labels có cardinality cao.

**Trade-offs:** Modular Monolith + worker giảm network hops và overhead vận hành nhưng chia sẻ DB/schema và có thể tăng contention; microservice giúp ownership/isolation khi tổ chức và traffic đủ lớn nhưng tăng distributed failure, deployment và tracing complexity. Azure Service Bus cải thiện buffering nhưng bổ sung phí và vận hành DLQ; database-only queue đơn giản hơn nhưng phải đo contention và polling cost. Không thêm Redis nếu chưa có bottleneck.

**Rollout:** Shadow mode ghi event nhưng không gửi; so sánh count, thử canary một nhóm nhỏ, áp rate limits, bật theo notification type, hỗ trợ replay an toàn và rollback bằng feature flag. Test crash window, provider timeout, duplicated messages, preference race, tenant isolation và load burst.

## Mẫu trả lời trong phỏng vấn

“Tôi bắt đầu bằng làm rõ SLO và ý nghĩa của gửi đúng một lần. Tôi sẽ giữ notification như một module của Modular Monolith, với PostgreSQL làm source of truth và worker xử lý delivery. Business transaction ghi state cùng Outbox để không mất event. Worker xử lý idempotently, rate-limit theo provider, retry có giới hạn và DLQ cho lỗi không thể tự phục hồi. Tôi phân biệt provider accepted với user received; timeout không có nghĩa provider chưa gửi. Preferences cần policy version và audit, đặc biệt với thông báo bắt buộc. Azure Service Bus đáng dùng khi cần buffering và scale độc lập, nhưng không mặc định microservice. Tôi kiểm chứng bằng failure injection, load burst, security tests và metrics event-to-accepted latency. Nếu đội vận hành nhỏ, tôi ưu tiên kiến trúc đơn giản có khả năng tách sau.”

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Managed heap, LOH và object ownership cần được phân tích bằng allocation profile và concurrency, không suy đoán từ working set.
- Kubernetes readiness, termination và ingress routing là các trạng thái khác nhau; incident cần timeline liên kết evidence giữa các lớp.
- Durable messaging không tự mang lại exactly-once external effects; transaction boundary, idempotency và reconciliation là các phần riêng biệt của thiết kế.
- Độ phức tạp kiến trúc phải tương xứng với SLO, team capacity và failure modes thực tế.

## Mẫu tư duy cần nhớ

1. **Measure before optimize:** Chứng minh allocation, GC hoặc network bottleneck trước khi sửa.
2. **Stabilize before deep investigation:** Giảm blast radius rồi thu thập timeline có correlation.
3. **Distinguish signals from guarantees:** Ready, accepted và delivered mang ý nghĩa khác nhau.
4. **Design retries with idempotency:** Luôn xem xét crash ở cả hai phía external side effect.
5. **Prefer the simplest sufficient architecture:** Tách service chỉ khi lợi ích vượt operational cost.
