# Code Review Challenge 1 — Fan-out HTTP chạy nhanh ở test nhưng tự khuếch đại outage của dependency

**Chủ đề:** C#/.NET, ASP.NET Core, HttpClient, async/concurrency, cancellation, partial failure, resilience, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API tổng hợp trạng thái của nhiều cửa hàng cho màn hình vận hành. Mỗi request nhận tối đa vài trăm `storeIds`; với mỗi store, API gọi một inventory service bên ngoài. `IHttpClientFactory` đã được cấu hình và team cho rằng như vậy mọi vấn đề về outbound HTTP đã được giải quyết.

Ở test chỉ có 5–10 stores nên endpoint nhanh. Production đôi lúc có 150–300 stores/request và nhiều người mở dashboard cùng lúc. Khi inventory service chậm, p95/p99 của API tăng mạnh, outbound request count tăng đột biến, một số request tiếp tục chạy dù browser đã đóng, và dependency có lúc trả 429/503. Team đề xuất tăng timeout lên 2 phút và retry mọi lỗi 5 lần.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/store-status")]
public sealed class StoreStatusController : ControllerBase
{
    private readonly IHttpClientFactory _clientFactory;
    private readonly ILogger<StoreStatusController> _logger;

    public StoreStatusController(
        IHttpClientFactory clientFactory,
        ILogger<StoreStatusController> logger)
    {
        _clientFactory = clientFactory;
        _logger = logger;
    }

    [HttpPost]
    public async Task<IActionResult> GetStatus([FromBody] Guid[] storeIds)
    {
        var client = _clientFactory.CreateClient("inventory");

        var tasks = storeIds.Select(async storeId =>
        {
            for (var attempt = 1; attempt <= 5; attempt++)
            {
                try
                {
                    var response = await client.GetAsync(
                        $"/api/inventory/{storeId}");

                    if (response.IsSuccessStatusCode)
                    {
                        var item = await response.Content
                            .ReadFromJsonAsync<InventoryStatus>();
                        return new StoreStatus(storeId, item, null);
                    }

                    if (attempt == 5)
                        return new StoreStatus(
                            storeId,
                            null,
                            $"HTTP {(int)response.StatusCode}");
                }
                catch (Exception ex)
                {
                    _logger.LogWarning(ex,
                        "Inventory call failed for store {StoreId}", storeId);

                    if (attempt == 5)
                        return new StoreStatus(storeId, null, "Failed");
                }
            }

            return new StoreStatus(storeId, null, "Unknown");
        });

        var results = await Task.WhenAll(tasks);
        return Ok(results);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, concurrency và reliability problems.
2. Giải thích vì sao endpoint có thể khuếch đại load lên dependency khi traffic và số `storeIds` tăng.
3. Phân tích cancellation, timeout, retry và HTTP response lifecycle.
4. Ưu tiên findings theo production severity.
5. Đề xuất implementation/design có bounded concurrency và failure semantics rõ ràng.
6. Nêu cách kiểm thử load, 429/503, timeout, cancellation và partial failure.
7. Nêu telemetry cần có để chứng minh fix hiệu quả.

## Câu hỏi gợi mở

1. Với 100 concurrent API requests, mỗi request chứa 300 stores, code có thể tạo bao nhiêu outbound operations trong một khoảng ngắn?
2. `Task.WhenAll` có tự giới hạn concurrency hay backpressure không?
3. Client disconnect có truyền cancellation tới các outbound calls hiện tại không?
4. Retry ngay lập tức 5 lần khi dependency đang 503/429 có thể tạo feedback loop gì?
5. `HttpResponseMessage` được xử lý lifecycle như thế nào ở các nhánh success/failure?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **unbounded fan-out + retry amplification + thiếu cancellation/failure budget**.

### Gợi ý 2

`IHttpClientFactory` giúp quản lý handler/client lifecycle, nhưng không tự tạo bounded concurrency, timeout policy, backoff, idempotency hay overload protection cho business workflow.

## Kết quả code review tham khảo

### Critical — Fan-out không có giới hạn concurrency

**Vấn đề:** Mỗi `storeId` tạo một asynchronous operation ngay khi `Task.WhenAll` enumerate tập tasks; không có application-level concurrency bound.

**Tại sao xảy ra:** Async không đồng nghĩa với throttling. Khi nhiều requests cùng chạy, số outbound operations tăng theo `requests × storeIds`, còn giới hạn thực tế bị đẩy xuống connection pool/dependency.

**Ảnh hưởng production:** Dependency overload, queueing, latency tăng, 429/503, connection pressure và cascading failure.

**Cách sửa:** Giới hạn `storeIds`, dùng bounded concurrency như `Parallel.ForEachAsync` với `MaxDegreeOfParallelism`, `SemaphoreSlim`, hoặc kiến trúc batch endpoint nếu dependency hỗ trợ. Chọn limit dựa trên load test và capacity, không chọn tùy ý.

### High — Retry tức thời làm khuếch đại outage

**Vấn đề:** Mọi non-success response và exception đều có thể được thử lại ngay tối đa 5 lần.

**Tại sao xảy ra:** Code không phân loại transient/permanent failure, không backoff/jitter, không tôn trọng overload signal như 429/`Retry-After`.

**Ảnh hưởng production:** Khi dependency suy yếu, application gửi nhiều request hơn đúng lúc dependency ít capacity nhất.

**Cách sửa:** Chỉ retry failure được đánh giá transient, có bounded attempts, backoff/jitter và budget. Với 429, cân nhắc server guidance. Không retry validation/auth/not-found một cách máy móc.

### High — Không propagate request cancellation

**Vấn đề:** Action không nhận `CancellationToken` và outbound calls không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Work không gắn với lifecycle của inbound request.

**Ảnh hưởng production:** Browser/client đã bỏ request nhưng server vẫn tiếp tục hàng trăm calls, làm lãng phí capacity trong incident.

**Cách sửa:** Nhận `CancellationToken` ở action và propagate tới concurrency primitive, `GetAsync`, deserialization và delays/retry policy. Phân biệt cancellation do caller với timeout/failure cần log.

### High — Timeout/failure budget không rõ ràng

**Vấn đề:** Workflow không có end-to-end latency budget được thể hiện; tăng timeout lên 2 phút chỉ kéo dài resource occupancy.

**Tại sao xảy ra:** Per-call behavior và overall request SLO chưa được thiết kế cùng nhau.

**Ảnh hưởng production:** Tail latency lớn, queueing kéo dài và dependency degradation lan sang API.

**Cách sửa:** Xác định request deadline và per-dependency budget dựa trên UX/SLO. Dừng work khi deadline hết; cân nhắc partial response nếu business chấp nhận.

### Medium — `HttpResponseMessage` không được dispose rõ ràng

**Vấn đề:** Response được tạo ở mỗi attempt nhưng không có `using`/dispose rõ ràng.

**Tại sao xảy ra:** `HttpClient` lifecycle và response lifecycle là hai vấn đề khác nhau.

**Ảnh hưởng production:** Dưới volume lớn, resource/connection reuse behavior có thể xấu hơn và lifecycle trở nên khó kiểm soát.

**Cách sửa:** Dispose response sau khi hoàn tất đọc nội dung/headers cần thiết; nếu streaming thì giữ response sống đúng tới khi stream consumption hoàn tất.

### Medium — Catch `Exception` làm mờ failure semantics

**Vấn đề:** Cancellation và programming/deserialization failures bị xử lý gần giống transient network failure.

**Tại sao xảy ra:** Catch quá rộng và retry loop không phân loại exception.

**Ảnh hưởng production:** Request cancellation có thể bị log như lỗi dependency; bug schema/deserialization có thể bị retry vô ích.

**Cách sửa:** Để cancellation đúng token propagate; phân loại network/timeout/transient response theo policy đã xác định; unexpected exceptions phải observable và không retry mù.

### Medium — Input không có giới hạn/normalization

**Vấn đề:** Không giới hạn số `storeIds`, không loại duplicate và không validate empty/oversized request.

**Tại sao xảy ra:** API boundary tin caller sẽ gửi tập hợp hợp lý.

**Ảnh hưởng production:** Một request có thể tạo fan-out rất lớn; duplicate IDs tạo calls dư thừa.

**Cách sửa:** Đặt business limit, reject request quá lớn hoặc dùng batching/async workflow; deduplicate khi semantics cho phép.

### Medium — Partial failure contract quá nghèo

**Vấn đề:** Caller chỉ nhận các chuỗi như `Failed`/HTTP code, không phân biệt timeout, cancellation, overload hay unavailable; đồng thời endpoint luôn trả 200 nếu `WhenAll` hoàn tất.

**Tại sao xảy ra:** API contract chưa định nghĩa partial success.

**Ảnh hưởng production:** UI và monitoring khó quyết định retry/hiển thị degraded state.

**Cách sửa:** Thiết kế per-item outcome và overall semantics rõ ràng, không lộ sensitive internal details; Product phải xác nhận partial success có chấp nhận được hay không.

## Phiên bản đề xuất

```csharp
[HttpPost]
public async Task<IActionResult> GetStatus(
    [FromBody] Guid[] storeIds,
    CancellationToken cancellationToken)
{
    const int maxStores = 200;
    const int maxConcurrency = 12; // Tune from measurement/capacity.

    var ids = storeIds.Distinct().ToArray();
    if (ids.Length == 0 || ids.Length > maxStores)
        return BadRequest(new { error = "Invalid store count" });

    var client = _clientFactory.CreateClient("inventory");
    var results = new ConcurrentDictionary<Guid, StoreStatus>();

    await Parallel.ForEachAsync(
        ids,
        new ParallelOptions
        {
            MaxDegreeOfParallelism = maxConcurrency,
            CancellationToken = cancellationToken
        },
        async (storeId, ct) =>
        {
            try
            {
                using var response = await client.GetAsync(
                    $"/api/inventory/{storeId}", ct);

                if (response.IsSuccessStatusCode)
                {
                    var item = await response.Content
                        .ReadFromJsonAsync<InventoryStatus>(cancellationToken: ct);
                    results[storeId] = new(storeId, item, null);
                    return;
                }

                results[storeId] = new(
                    storeId,
                    null,
                    $"HTTP {(int)response.StatusCode}");
            }
            catch (OperationCanceledException) when (ct.IsCancellationRequested)
            {
                throw;
            }
            catch (HttpRequestException ex)
            {
                _logger.LogWarning(ex,
                    "Inventory dependency failed for store {StoreId}", storeId);
                results[storeId] = new(storeId, null, "Unavailable");
            }
        });

    return Ok(ids.Select(id => results[id]));
}
```

Ví dụ cố ý không nhét retry thủ công vào action. Nếu retry thực sự cần, đặt resilience policy có phân loại failure, bounded attempts, backoff/jitter và telemetry; policy phải phù hợp với deadline toàn request. `maxConcurrency` và `maxStores` chỉ là scenario assumptions cần tune bằng capacity/load evidence.

## Giải thích thiết kế sau khi sửa

Boundary mới giới hạn amplification factor và propagate cancellation. `IHttpClientFactory` vẫn quản lý client/handler, còn application chủ động kiểm soát workflow concurrency. Partial-failure semantics được giữ ở mức per-store thay vì biến một dependency lỗi thành crash toàn dashboard. Retry được tách khỏi business loop để tránh retry tất cả failures một cách vô thức.

## Trade-offs

Bounded concurrency có thể làm một request lớn mất lâu hơn khi dependency khỏe, nhưng bảo vệ cả hệ thống dưới aggregate load. Batch API phía dependency có thể giảm request count đáng kể nhưng tăng coupling và cần dependency hỗ trợ. Cache có thể hữu ích nếu freshness requirement cho phép và measurement chứng minh call volume là bottleneck, nhưng cache không thay thế overload control. Async background aggregation có thể phù hợp nếu dashboard không cần synchronous freshness.

## Cách kiểm thử

1. **Load test:** nhiều concurrent API requests với 200 IDs; xác minh outbound concurrency không vượt budget và đo p95/p99.
2. **Failure-path test:** dependency trả 429/503/timeouts; xác minh không có retry storm và partial result đúng contract.
3. **Cancellation test:** abort inbound request; xác minh pending outbound calls giảm/dừng nhanh.
4. **Integration test:** duplicate IDs, oversized input, malformed dependency payload và partial failures.
5. **Capacity test:** sweep `MaxDegreeOfParallelism` để quan sát throughput, dependency latency/error rate và connection pressure trước khi chọn production value.

## Quan sát trong production

Theo dõi inbound request rate/p95/p99, số stores/request, active outbound calls, dependency duration/error/429/503, cancellation count và timeout count. Application Insights dependency telemetry cần correlation với request và store operation nhưng tránh cardinality không kiểm soát. Dashboard nên thể hiện amplification ratio `outbound calls / inbound request`, failure rate theo dependency và saturation signals. Alert khi dependency latency/error tăng cùng outbound concurrency.

3. Nếu Product yêu cầu trả đủ 300 stores trong 500 ms, bạn cần challenge requirement bằng evidence/capacity model nào?

# Code Review Challenge 2 — Kubernetes rollout “xanh” nhưng Pod nhận traffic trước khi ứng dụng thực sự sẵn sàng

**Chủ đề:** Kubernetes, ASP.NET Core, probes, rolling deployment, resource limits, configuration, graceful shutdown, deployment safety  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API trước đây chạy trên App Service đang được thử nghiệm trên Kubernetes. Deployment hoàn tất thành công theo pipeline, nhưng trong mỗi rollout người dùng thấy một đợt 502/503 ngắn. Thỉnh thoảng Pod restart khi traffic tăng. Team thêm cả liveness và readiness vào cùng endpoint `/health` và đặt timeout rất ngắn vì muốn “phát hiện lỗi càng nhanh càng tốt”.

Ứng dụng cần khoảng 20–40 giây để warm configuration/cache và kiểm tra database connectivity. Khi shutdown, một số request có thể chạy 10–15 giây. Chưa có evidence rằng Kubernetes là bắt buộc cho workload này; challenge tập trung vào correctness của manifest hiện tại, không giả định phải giữ Kubernetes bằng mọi giá.

## Kết quả code review tham khảo

### Critical — Production database credential nằm trực tiếp trong Deployment manifest

**Vấn đề:** Username/password xuất hiện trong plaintext manifest.

**Tại sao xảy ra:** Configuration và secret distribution không được tách khỏi deployable manifest.

**Ảnh hưởng production:** Secret có thể lộ qua repository, pipeline logs, rendered manifests hoặc người có quyền đọc workload spec; rotation cũng khó kiểm soát.

**Cách sửa:** Dùng secret-management mechanism phù hợp với platform và organization, least privilege, rotation và workload identity/Managed Identity khi kiến trúc hỗ trợ. Kubernetes `Secret` đơn thuần không có nghĩa là secret đã an toàn nếu RBAC/encryption/distribution không được thiết kế.

### High — Cùng dependency-sensitive `/health` dùng cho readiness và liveness

**Vấn đề:** Một SQL/dependency failure có thể làm cả readiness và liveness fail.

**Tại sao xảy ra:** Hai probe có mục đích khác nhau nhưng dùng cùng health semantics.

**Ảnh hưởng production:** Dependency outage có thể loại Pod khỏi traffic rồi đồng thời restart healthy process, tạo restart storm và làm recovery khó hơn.

**Cách sửa:** Tách liveness check thành process-local health tối thiểu; readiness phản ánh khả năng phục vụ traffic theo dependency policy. Dependency nào phải nằm trong readiness phụ thuộc khả năng degrade của application.

### High — Startup timing không phù hợp và thiếu startup probe

**Vấn đề:** App cần 20–40 giây warm-up nhưng liveness bắt đầu sau 5 giây với `failureThreshold: 1`.

**Tại sao xảy ra:** Liveness được dùng trong giai đoạn startup mà không có startup budget phù hợp.

**Ảnh hưởng production:** Container có thể bị restart lặp trước khi hoàn tất initialization.

**Cách sửa:** Dùng `startupProbe` hoặc cấu hình startup/liveness timing dựa trên measured startup distribution. Khi startup probe chưa thành công, liveness/readiness behavior cần được thiết kế để tránh premature restart/traffic.

### High — Probe quá nhạy với transient latency

**Vấn đề:** Timeout 1 giây, failure threshold 1 và period ngắn tạo sensitivity cao.

**Tại sao xảy ra:** “Detect fast” được tối ưu mà không cân bằng false positives.

**Ảnh hưởng production:** CPU throttling, GC pause hoặc dependency jitter ngắn có thể làm Pod flapping/restart.

**Cách sửa:** Chọn thresholds từ observed startup/health latency và SLO; readiness có thể phản ứng nhanh hơn liveness nhưng vẫn cần tránh flapping.

### High — Không thể hiện graceful termination/rollout budget

**Vấn đề:** Manifest không thể hiện strategy parameters và termination behavior phù hợp với request 10–15 giây.

**Tại sao xảy ra:** Rollout chỉ dựa vào defaults, trong khi application có in-flight work đáng kể.

**Ảnh hưởng production:** Pod có thể bị loại/terminate trong lúc request đang chạy; rollout capacity có thể giảm không như kỳ vọng.

**Cách sửa:** Thiết kế readiness-on-shutdown, `terminationGracePeriodSeconds`, application graceful shutdown và rolling strategy (`maxUnavailable`/`maxSurge`) theo availability/capacity requirements. Có thể dùng lifecycle hooks khi thực sự cần, nhưng phải hiểu ordering và không thay thế app shutdown logic.

### Medium — Image tag `latest` làm artifact không deterministic

**Vấn đề:** Manifest không pin immutable version/digest.

**Tại sao xảy ra:** Cùng manifest có thể trỏ tới image content khác theo thời gian.

**Ảnh hưởng production:** Khó audit, reproduce và rollback chính xác.

**Cách sửa:** Deploy immutable image tag hoặc digest được tạo bởi CI; promotion giữa environments phải giữ artifact identity.

### Medium — Resource requests/limits có vẻ tùy ý và rất thấp

**Vấn đề:** CPU/memory values không có evidence và có thể không phù hợp workload.

**Tại sao xảy ra:** Capacity được cấu hình như một con số mặc định thay vì từ measurement.

**Ảnh hưởng production:** CPU throttling, OOMKilled, latency tăng và probe failures có thể tự khuếch đại.

**Cách sửa:** Profile/load test, quan sát working set, GC, CPU/throttling và chọn requests/limits phù hợp. Không kết luận chỉ từ manifest rằng 128Mi chắc chắn thiếu; phải đo.

### Medium — Không có explicit rollout safety signal ngoài probes

**Vấn đề:** Pipeline coi Deployment rollout thành công là đủ.

**Tại sao xảy ra:** Kubernetes readiness không chứng minh business-critical API behavior, migration compatibility hay downstream correctness.

**Ảnh hưởng production:** Regression vẫn có thể được rollout hoàn chỉnh dù Pods đều Ready.

**Cách sửa:** Thêm smoke/API validation, telemetry gate/canary khi risk justify và rollback criteria rõ ràng.

## Phiên bản đề xuất

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example/orders-api:2026.09.23.1
          ports:
            - containerPort: 8080
          env:
            - name: ASPNETCORE_ENVIRONMENT
              value: Production
            - name: ConnectionStrings__Orders
              valueFrom:
                secretKeyRef:
                  name: orders-api-db
                  key: connectionString
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              cpu: "1"
              memory: "512Mi"
```

Các resource values ở đây chỉ minh họa cấu trúc, **không phải recommendation production**; phải thay bằng số liệu từ profiling/load test. Tương tự, secret reference chỉ tốt hơn plaintext manifest chứ chưa hoàn chỉnh nếu cluster secret storage/RBAC/rotation không được bảo vệ. Nếu platform hỗ trợ workload identity/Managed Identity và database authentication tương thích, có thể giảm phụ thuộc password secret.

## Giải thích thiết kế sau khi sửa

Startup, readiness và liveness được tách theo intent. Startup probe cho app đủ budget khởi động trước khi liveness được dùng để quyết định restart. Readiness có thể phản ánh khả năng phục vụ request, trong khi liveness tránh phụ thuộc trực tiếp vào downstream transient failure. Rolling strategy giữ capacity trong rollout và termination grace cho application cơ hội hoàn tất request.

## Trade-offs

Probe quá “thoáng” làm detection chậm; quá nhạy gây flapping. `maxUnavailable: 0` tăng availability nhưng cần surge capacity. Graceful shutdown dài làm rollout chậm hơn. Workload identity giảm secret handling nhưng thêm platform/IAM setup. Kubernetes cung cấp orchestration controls mạnh, nhưng nếu workload đơn giản và App Service đáp ứng requirements với operational burden thấp hơn thì team nên đánh giá lại cost of complexity thay vì coi migration là mục tiêu tự thân.

## Cách kiểm thử

1. **Deployment validation:** rollout dưới traffic liên tục; xác minh không có 502/503 spike và capacity không tụt ngoài budget.
2. **Startup test:** inject startup 20–40 giây; xác minh Pod không bị liveness restart trước khi ready.
3. **Failure-path test:** làm SQL chậm/unavailable; xác minh readiness/liveness behavior đúng degradation policy, không restart storm.
4. **Load/resource test:** tăng traffic để quan sát CPU throttling, memory, GC, OOMKilled và probe latency.
5. **Graceful shutdown test:** terminate Pod khi có request 10–15 giây; xác minh traffic drain và request completion/cancellation semantics.

## Quan sát trong production

Theo dõi Pod restart count/reason, readiness transitions, OOMKilled, CPU throttling, memory working set, rollout duration và unavailable replicas. Ở application layer theo dõi request p95/p99, 5xx, startup duration, shutdown duration, active requests và SQL dependency latency/error. Correlate deployment version/image digest với Application Insights/Kibana telemetry. Alert khi restart rate, readiness flapping hoặc 5xx tăng sau rollout.

## Câu hỏi phỏng vấn mở rộng

1. Nếu database outage kéo dài 10 phút, readiness và liveness của API nên phản ứng khác nhau như thế nào?
2. Khi nào bạn sẽ bỏ Kubernetes và quay lại App Service cho workload này?
3. Nếu app chạy database migration lúc startup, điều gì xảy ra khi 4 Pods của một rollout cùng khởi động và bạn sẽ thiết kế migration ownership thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IHttpClientFactory` không thay thế concurrency control, timeout budget, cancellation hay resilience design; fan-out phải được giới hạn dựa trên capacity.
- Retry có thể khuếch đại dependency outage nếu không phân loại failure, backoff và giới hạn retry budget.
- Kubernetes readiness, liveness và startup probes có mục tiêu khác nhau; trộn semantics có thể biến dependency degradation thành restart storm.
- Deployment safety gồm artifact identity, secret handling, graceful shutdown, capacity trong rollout, validation và observability — không chỉ “Pods are Ready”.

## Mẫu tư duy cần nhớ

- Tính amplification factor trước khi fan-out hoặc retry.
- Propagate cancellation qua toàn bộ I/O path.
- Tách “có nhận traffic được không?” khỏi “process có cần restart không?”.
- Chọn thresholds/resources từ measurement, không từ cảm giác.
- Xem deployment và failure path như một phần của application design.
