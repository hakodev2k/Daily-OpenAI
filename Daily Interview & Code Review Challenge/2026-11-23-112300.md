## Bối cảnh

Portal nội bộ cho phép nhân viên tài chính tải báo cáo CSV của chính tenant mình. Một báo cáo có thể chứa 800.000 dòng; 20 người có thể tải đồng thời trên mỗi instance App Service. Báo cáo chỉ cần dữ liệu đọc tại thời điểm truy vấn, chưa yêu cầu snapshot nhất quán tuyệt đối. Khi tải báo cáo, API khác tăng p99 và đôi khi instance restart. Người dùng hủy download nhưng SQL vẫn hoạt động. Quyền Finance đã được cấu hình để giới hạn người dùng có quyền xuất báo cáo; tenant ID phải lấy từ identity đã xác thực.

## Đoạn code cần review

```csharp
[Authorize(Policy = "Finance")]
[ApiController]
[Route("api/reports")]
public sealed class ReportsController(
    AppDbContext db,
    ILogger<ReportsController> logger) : ControllerBase
{
    [HttpGet("orders")]
    public async Task<IActionResult> Export()
    {
        var tenant = User.FindFirst("tenant_id")!.Value;
        var rows = await db.Orders
            .Where(o => o.TenantId == tenant)
            .OrderBy(o => o.Id)
            .ToListAsync();

        var csv = new StringBuilder();
        csv.AppendLine("Id,Customer,Amount");

        foreach (var row in rows)
        {
            csv.Append(row.Id).Append(',')
               .Append(row.CustomerName).Append(',')
               .Append(row.Amount).AppendLine();
        }

        var bytes = Encoding.UTF8.GetBytes(csv.ToString());
        logger.LogInformation("Exported {Count} orders", rows.Count);
        return File(bytes, "text/csv", "orders.csv");
    }
}
```

## Kết quả code review tham khảo

### High — Bộ nhớ tăng theo kích thước báo cáo

**Vấn đề:** ToListAsync tải toàn bộ entity, StringBuilder giữ nội dung, ToString và GetBytes tạo thêm bản sao.  
**Tại sao xảy ra:** Không có giới hạn dữ liệu trong bộ nhớ; EF Core còn tracking entity mặc định nếu context không cấu hình khác.  
**Ảnh hưởng production:** Allocation lớn, GC pressure, có thể OOM khi nhiều export đồng thời; không thể khẳng định OOM là nguyên nhân restart nếu chưa xem log.  
**Cách sửa:** Projection, AsNoTracking, đọc từng batch giới hạn, ghi response tuần tự và giới hạn số export đồng thời.

### High — CSV injection

**Vấn đề:** Tên khách hàng có thể bắt đầu bằng ký tự công thức.  
**Tại sao xảy ra:** Spreadsheet có thể diễn giải dữ liệu nhập dưới dạng công thức; quote CSV đơn thuần không vô hiệu hóa công thức.  
**Ảnh hưởng production:** Người mở báo cáo có thể bị tác động bởi công thức không mong muốn, tùy ứng dụng spreadsheet.  
**Cách sửa:** Áp dụng chính sách xuất dành cho spreadsheet, kiểm thử trên ứng dụng đích; nếu cần giữ dữ liệu nguyên bản, dùng định dạng có kiểu cell text rõ ràng như XLSX.

### Medium — CSV sai cấu trúc và culture

**Vấn đề:** Không escape dấu quote, dấu phẩy, newline; decimal phụ thuộc culture.  
**Tại sao xảy ra:** Ghép chuỗi thủ công không tuân thủ quy tắc CSV.  
**Ảnh hưởng production:** Cột lệch, số tiền bị hiểu sai.  
**Cách sửa:** Dùng thư viện CSV đã kiểm thử hoặc escape đúng và định dạng invariant.

### Medium — Không truyền cancellation

**Vấn đề:** Truy vấn không nhận RequestAborted.  
**Tại sao xảy ra:** Cancellation là cooperative; disconnect không tự truyền token vào mọi API.  
**Ảnh hưởng production:** Tốn CPU, SQL và bộ nhớ sau khi client rời đi.  
**Cách sửa:** Truyền token cho truy vấn và response writes; provider có thể không dừng tức thời.

### Medium — Không giới hạn concurrency và thiếu telemetry

**Vấn đề:** Không có admission control; log chỉ ghi số dòng trước khi truyền xong.  
**Tại sao xảy ra:** Mỗi request được phép tạo workload lớn độc lập.  
**Ảnh hưởng production:** Export cạnh tranh tài nguyên với API nghiệp vụ; khó phân biệt thành công và download bị ngắt.  
**Cách sửa:** Giới hạn concurrency, ghi duration và outcome; kiểm tra tenant claim thiếu thay vì dereference null.

## Phiên bản đề xuất

Giả định Id là long tăng dần, dương và bất biến; policy Finance kiểm tra quyền và tenant claim được cấp bởi issuer tin cậy. Ví dụ dưới đây dùng giới hạn 2 export mỗi process, không phải giới hạn toàn cluster.

```csharp
[Authorize(Policy = "Finance")]
[ApiController]
[Route("api/reports")]
public sealed class ReportsController(
    AppDbContext db,
    ILogger<ReportsController> logger) : ControllerBase
{
    private static readonly SemaphoreSlim Slots = new(2, 2);

    [HttpGet("orders")]
    public async Task Export(CancellationToken ct)
    {
        var tenant = User.FindFirst("tenant_id")?.Value;
        if (string.IsNullOrWhiteSpace(tenant))
        {
            Response.StatusCode = 403;
            return;
        }

        if (!await Slots.WaitAsync(0, ct))
        {
            Response.StatusCode = 429;
            Response.Headers["Retry-After"] = "30";
            return;
        }

        long count = 0;
        var watch = Stopwatch.StartNew();
        var outcome = "failed";
        try
        {
            Response.ContentType = "text/csv; charset=utf-8";
            Response.Headers["Content-Disposition"] =
                "attachment; filename=orders.csv";
            Response.Headers["Cache-Control"] = "no-store";

            await Response.WriteAsync("Id,Customer,Amount\r\n", ct);
            long lastId = 0;
            while (true)
            {
                var batch = await db.Orders.AsNoTracking()
                    .Where(o => o.TenantId == tenant && o.Id > lastId)
                    .OrderBy(o => o.Id)
                    .Select(o => new { o.Id, o.CustomerName, o.Amount })
                    .Take(1000).ToListAsync(ct);
                if (batch.Count == 0) break;

                foreach (var row in batch)
                {
                    var amount = row.Amount.ToString(
                        CultureInfo.InvariantCulture);
                    await Response.WriteAsync(
                        $"{row.Id},{CsvText(row.CustomerName)},{amount}\r\n", ct);
                    count++;
                }
                lastId = batch[^1].Id;
                await Response.Body.FlushAsync(ct);
            }
            outcome = "completed";
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            outcome = "cancelled";
            HttpContext.Abort();
        }
        catch
        {
            if (Response.HasStarted) HttpContext.Abort();
            throw;
        }
        finally
        {
            Slots.Release();
            logger.LogInformation(
                "Export {Outcome} {Rows} {ElapsedMs}",
                outcome, count, watch.ElapsedMilliseconds);
        }
    }

    private static string CsvText(string? value)
    {
        var s = value ?? "";
        var trimmed = s.TrimStart();
        if (s.StartsWith('\t') || s.StartsWith('\r') ||
            s.StartsWith('\n') ||
            (trimmed.Length > 0 && "=+-@".Contains(trimmed[0])))
            s = "'" + s;
        return "\"" + s.Replace("\"", "\"\"") + "\"";
    }
}
```

## Giải thích thiết kế sau khi sửa

Keyset pagination theo Id tránh giữ data reader trong suốt thời gian client tải chậm. Index (TenantId, Id) cần được đánh giá bằng actual execution plan. Projection giảm dữ liệu đọc. Response đã bắt đầu thì không thể đổi sang ProblemDetails đáng tin cậy; abort giúp tránh coi lỗi giữa chừng là file hoàn chỉnh, nhưng không thay thế cơ chế kiểm tra tính toàn vẹn phía client. Log completed chỉ xác nhận server hoàn tất ghi, không chứng minh client đã lưu file.

## Trade-offs

Batching tạo thêm round trips và không bảo đảm snapshot xuyên suốt các batch; nếu báo cáo cần đối soát chính xác, thiết kế job tạo artifact bất biến với snapshot phù hợp. Giới hạn theo process không bảo vệ tuyệt đối SQL khi scale out; cân nhắc quota toàn hệ thống nếu load test cho thấy cần thiết. Streaming giảm memory nhưng giữ HTTP request lâu; export bất đồng bộ vào Blob Storage có thể tốt hơn khi báo cáo rất lớn, đổi lại cần job state, quyền tải, expiry và cleanup. Chính sách thêm apostrophe thay đổi biểu diễn dữ liệu và phải được thống nhất với người dùng.

## Cách kiểm thử

1. Integration test CSV chứa quote, newline, dấu phẩy, Unicode, công thức và decimal với culture vi-VN.
2. Security test tenant A không thể đọc dữ liệu tenant B; claim thiếu trả 403.
3. Load test 20 download đồng thời, theo dõi memory, GC, p99 API khác và 429.
4. Failure-path test hủy client giữa batch, kiểm tra slot được trả lại và SQL cancellation.
5. Database test với execution plan thực tế và cập nhật đồng thời để xác nhận semantics đã công bố.

## Quan sát trong production

Application Insights: duration, outcome, số export active, tỷ lệ 429, dependency duration SQL; Azure Monitor: working set, GC heap, restart reason. Theo dõi SQL logical reads và connection pool waits. Alert khi export gây suy giảm p99 API nghiệp vụ. Không log nội dung khách hàng.

## Câu hỏi phỏng vấn mở rộng

- Nếu báo cáo cần snapshot chính xác tại thời điểm bấm nút, bạn thay đổi gì?
- Khi nào nên chuyển sang job tạo file bất đồng bộ thay vì tăng giới hạn streaming?

# Code Review Challenge 2 — Rolling deployment và probe trên Kubernetes

**Chủ đề:** Kubernetes, CI/CD, deployment safety, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30 phút

## Bối cảnh

API danh mục sản phẩm chạy ba replica. Bản mới cần 45–90 giây để warm up; database thỉnh thoảng mất kết nối 15 giây. Endpoint /health kiểm tra database, /live chỉ kiểm tra process, /ready kiểm tra khả năng phục vụ, /startup báo hoàn tất khởi tạo. Các endpoint sau đã có sẵn. Pipeline dùng Jenkins và triển khai manifest bên dưới. Khi rollout, người dùng gặp 503 và pod restart liên tục trong lúc database bảo trì. Image registry hỗ trợ immutable digest. Cluster có đủ tài nguyên cho một pod bổ sung trong điều kiện bình thường.

## Kết quả code review tham khảo

### High — Rollout cho phép mất toàn bộ replica

**Vấn đề:** maxUnavailable 100%, maxSurge 0.  
**Tại sao xảy ra:** Controller được phép giảm toàn bộ replica available trong rollout.  
**Ảnh hưởng production:** Có thể không còn endpoint sẵn sàng khi pod mới warm up.  
**Cách sửa:** maxUnavailable 0, maxSurge 1; kiểm tra capacity và readiness trước rollout.

### High — Liveness phụ thuộc database và không có startup probe

**Vấn đề:** /health dùng chung cho liveness và readiness.  
**Tại sao xảy ra:** Liveness failure có thể dẫn đến restart container dù process vẫn khỏe; startup chưa hoàn tất cũng có thể thất bại probe.  
**Ảnh hưởng production:** Restart storm, tăng tải database khi reconnect và kéo dài outage.  
**Cách sửa:** Tách /live, /ready, /startup; startup budget lớn hơn thời gian khởi tạo đã đo. Readiness chỉ kiểm tra dependency thực sự cần để phục vụ.

### High — Artifact không bất biến

**Vấn đề:** Dùng latest.  
**Tại sao xảy ra:** Tag có thể trỏ sang digest khác, Always không bảo đảm mọi lần khởi động cùng artifact.  
**Ảnh hưởng production:** Khó xác định version đang chạy và rollback không đáng tin cậy.  
**Cách sửa:** Build một lần, promote cùng digest qua môi trường; lưu digest và release metadata.

### Medium — Grace period quá ngắn

**Vấn đề:** 5 giây chưa được chứng minh đủ cho request đang xử lý.  
**Tại sao xảy ra:** Sau grace period, process chưa thoát có thể bị kill; việc cập nhật endpoint và drain không tức thời tuyệt đối.  
**Ảnh hưởng production:** Request đang xử lý có thể bị ngắt.  
**Cách sửa:** Đo thời gian drain, cấu hình shutdown timeout của app phù hợp và kiểm thử với ingress thực tế.

### Medium — Resource budget chưa có căn cứ

**Vấn đề:** Memory limit 128Mi và request 64Mi chưa có số đo.  
**Tại sao xảy ra:** Warm-up, runtime heap và native allocations có thể vượt budget.  
**Ảnh hưởng production:** OOMKilled nếu vượt giới hạn; request quá thấp có thể dẫn đến placement không phù hợp.  
**Cách sửa:** Xem termination reason, working set, CPU và load test trước khi điều chỉnh.

## Phiên bản đề xuất

Manifest template dưới đây yêu cầu pipeline thay IMAGE_DIGEST bằng digest đã kiểm chứng trước khi apply. Resource values chỉ là giả định ban đầu cho staging, không phải benchmark production.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 3
  minReadySeconds: 15
  progressDeadlineSeconds: 600
  selector:
    matchLabels:
      app: catalog-api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      terminationGracePeriodSeconds: 45
      containers:
        - name: api
          image: registry.example.com/catalog@IMAGE_DIGEST
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /startup
              port: 8080
            periodSeconds: 5
            failureThreshold: 30
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
```

## Giải thích thiết kế sau khi sửa

Startup probe trì hoãn liveness/readiness cho đến khi startup thành công. Readiness failure loại pod khỏi tập endpoint phục vụ thông thường mà không tự restart container. Liveness chỉ phát hiện trạng thái process không thể tự phục hồi. Budget startup khoảng 150 giây là cấu hình đề xuất, không phải SLA chính xác. Jenkins phải kiểm tra digest đúng định dạng sha256, render manifest, chạy validation, apply, chờ rollout status và smoke test qua ingress. progressDeadlineSeconds báo rollout không tiến triển; không tự động rollback. Pipeline phải quyết định rollback về digest trước đó sau khi xác minh tương thích schema.

## Trade-offs

maxUnavailable 0 có thể khiến rollout bị kẹt khi cluster thiếu capacity; đây là lựa chọn ưu tiên availability hơn tốc độ release. Nếu toàn bộ pod phụ thuộc database, readiness có thể khiến tất cả endpoint biến mất khi database outage; nếu API hỗ trợ dữ liệu degraded, cần readiness theo khả năng phục vụ thực tế. Grace period dài làm rollout chậm hơn. Không thêm service mesh hay microservices chỉ để giải quyết probe. Cần xác minh app thực sự xử lý SIGTERM và hoàn thành request trong budget.

## Cách kiểm thử

1. Deployment test startup 90 giây, xác nhận không bị liveness restart và replica cũ vẫn phục vụ.
2. Failure injection database outage 15 giây, xác nhận không restart chỉ vì dependency lỗi và readiness phục hồi.
3. Load test qua ingress trong rollout, đo 503, p99 và request bị ngắt khi SIGTERM.
4. Deployment validation đối chiếu imageID của pod với digest đã promote; thử rollback bản tương thích.
5. Resource test warm-up và tải đỉnh; đối chiếu memory usage, OOMKilled, CPU và scheduling events.

## Quan sát trong production

Theo dõi available replicas, ready endpoints, restart count, last termination reason, deployment conditions, scheduling events, memory working set và HTTP 5xx/p99. Correlate timestamp rollout, image digest, Application Insights dependency failures và Kubernetes events. Alert khi available replicas thấp kéo dài hoặc rollout vượt deadline. Khi incident xảy ra, dừng rollout nếu phù hợp, xác định impact, kiểm tra events và dependency telemetry trước khi tăng resource hoặc restart hàng loạt.

Giới hạn tài nguyên theo workload, CSV correctness và security, cancellation propagation, keyset pagination, phân biệt startup/readiness/liveness, immutable artifact và rollout budget.

## Mẫu tư duy cần nhớ

- Đo allocation và dependency latency trước khi tối ưu.
- Thiết kế cancellation cùng resource lifetime.
- Phân biệt dependency failure với process failure.
- Kiểm chứng release bằng artifact identity và traffic thực tế.
- Chọn giải pháp đơn giản nhất đáp ứng consistency và availability.
