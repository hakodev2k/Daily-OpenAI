# Code Review Challenge 1 — `BackgroundService` chạy đúng trên một instance nhưng gửi reminder trùng sau khi scale-out

**Chủ đề:** C#/.NET, `BackgroundService`, ASP.NET Core hosting, multi-instance execution, concurrency, idempotency, SQL Server, EF Core, graceful shutdown, external side effects, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal employee platform có chức năng gửi email reminder cho các approvals sắp quá hạn.

Application chạy ASP.NET Core .NET 8 trên Azure App Service. Ban đầu production chỉ có một instance nên scheduled worker hoạt động ổn. Sau khi bật autoscale lên 4 instances, support bắt đầu nhận phản ánh rằng một số users nhận cùng một reminder 2–4 lần.

Yêu cầu nghiệp vụ:

- reminder đến hạn phải được gửi trong vòng vài phút;
- scale-out không được làm cùng một business reminder được gửi nhiều lần theo chủ đích;
- process restart hoặc deployment không được làm mất reminders;
- transient email failure phải có thể retry;
- shutdown cần dừng cleanly;
- nhiều reminders có thể đến hạn cùng lúc;
- không yêu cầu một scheduler distributed phức tạp nếu một thiết kế đơn giản hơn vẫn đáp ứng reliability;
- SQL Server là source of truth;
- email provider là external dependency, đôi lúc timeout hoặc trả 5xx;
- application dùng Application Insights.

Implementation hiện tại:

## Đoạn code cần review

```csharp
public sealed class ReminderWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly IEmailSender _emailSender;
    private readonly ILogger<ReminderWorker> _logger;

    public ReminderWorker(
        IServiceScopeFactory scopeFactory,
        IEmailSender emailSender,
        ILogger<ReminderWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _emailSender = emailSender;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            _ = ProcessDueRemindersAsync();
        }
    }

    private async Task ProcessDueRemindersAsync()
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var now = DateTime.UtcNow;

        var reminders = await db.Reminders
            .Where(x =>
                x.Status == ReminderStatus.Pending &&
                x.SendAtUtc <= now)
            .OrderBy(x => x.SendAtUtc)
            .Take(100)
            .ToListAsync();

        foreach (var reminder in reminders)
        {
            await _emailSender.SendReminderAsync(
                reminder.UserEmail,
                reminder.Subject,
                reminder.Body,
                CancellationToken.None);

            reminder.Status = ReminderStatus.Sent;
            reminder.SentAtUtc = DateTime.UtcNow;

            await db.SaveChangesAsync();

            _logger.LogInformation(
                "Reminder sent. ReminderId={ReminderId}",
                reminder.Id);
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code dưới góc nhìn production và:

1. xác định các vấn đề về correctness, concurrency, reliability, cancellation và observability;
2. giải thích vì sao scale-out từ 1 lên 4 App Service instances có thể làm một reminder được xử lý nhiều lần;
3. phân tích failure windows giữa đọc database, gửi email và cập nhật trạng thái;
4. chỉ ra vì sao fire-and-forget trong `BackgroundService` có thể làm overlap ngay cả trên cùng một instance;
5. ưu tiên findings theo severity;
6. đề xuất design/implementation có idempotency hoặc durable coordination nhưng không tăng complexity vô lý;
7. mô tả test strategy cho multi-instance, crash, retry, email timeout và shutdown;
8. đề xuất telemetry đủ để biết reminder bị duplicate ở scheduler, database claim hay email provider.

## Câu hỏi gợi mở

1. Nếu cả 4 instances query cùng `Pending` rows trong cùng một giây, điều gì ngăn chúng cùng gọi email provider?
2. Nếu email gửi thành công nhưng process crash trước `SaveChangesAsync`, lần chạy sau sẽ thấy reminder ở trạng thái nào?
3. `_ = ProcessDueRemindersAsync()` ảnh hưởng thế nào nếu một batch chạy hơn một phút hoặc throw exception?
4. `CancellationToken.None` có ý nghĩa gì khi host đang shutdown hoặc deployment đang stop worker?
5. Liệu “chỉ cho một instance chạy scheduler” có phải là giải pháp duy nhất, hay có thể cho nhiều instances chạy nhưng khiến work idempotent?

## Kết quả code review tham khảo

### Critical — Mỗi application instance đều chạy cùng một `BackgroundService`

**Vấn đề:**  
`AddHostedService<ReminderWorker>()`/hosted service semantics khiến mỗi running application process có worker riêng. Khi App Service scale từ 1 lên 4 instances, có 4 independent pollers.

**Tại sao xảy ra:**  
`BackgroundService` cung cấp lifecycle trong một process; nó không phải distributed scheduler và không có built-in leader election hoặc cluster-wide mutex.

**Ảnh hưởng production:**  
Nhiều instances có thể đọc cùng các rows đang `Pending` trước khi bất kỳ instance nào cập nhật trạng thái, sau đó cùng gửi email.

**Cách sửa:**  
Không giả định hosted service chỉ chạy một lần cho toàn deployment. Hoặc dùng một scheduler/worker topology có single logical owner, hoặc thiết kế work để nhiều instances có thể cạnh tranh an toàn bằng database-enforced claim/idempotency. Với requirement hiện tại, database coordination thường đơn giản hơn việc đưa thêm distributed scheduler chỉ để tránh duplicate polling.

---

### Critical — External email side effect xảy ra trước durable state transition

**Vấn đề:**  
Code gửi email trước rồi mới đổi `Status=Sent` và `SaveChangesAsync()`.

**Tại sao xảy ra:**  
Nếu email provider nhận và gửi thành công nhưng process crash, network đứt hoặc database update fail sau đó, row vẫn là `Pending`.

**Ảnh hưởng production:**  
Lần poll sau sẽ gửi lại cùng reminder. Đây là classic ambiguous-completion window của external side effect.

**Cách sửa:**  
Tạo durable dispatch state trước side effect, ví dụ một Outbox/Dispatch record có unique key theo `ReminderId`, rồi một dispatcher riêng gửi email. Nếu provider hỗ trợ idempotency key, dùng `ReminderId`/dispatch id ổn định làm key. Nếu provider không hỗ trợ idempotency, phải chấp nhận rằng exactly-once external delivery không thể được bảo đảm tuyệt đối chỉ bằng local database state; cần reconciliation/duplicate-tolerant UX hoặc provider-specific deduplication.

---

### Critical — Query `Pending` rồi xử lý không có atomic claim hoặc uniqueness barrier

**Vấn đề:**  
Các instances đều có thể chạy:

```csharp
.Where(x => x.Status == ReminderStatus.Pending)
```

và nhận cùng rows.

**Tại sao xảy ra:**  
Read và ownership acquisition là hai bước tách rời. Không có row lock/claim token/version/unique dispatch record nào ngăn hai workers cùng thắng.

**Ảnh hưởng production:**  
Duplicate emails dưới concurrency dù không có crash hoặc retry.

**Cách sửa:**  
Dùng một ownership mechanism có enforcement ở database. Một cách đơn giản là insert `ReminderDispatch` với unique constraint trên `ReminderId`. Nhiều workers có thể nhìn thấy cùng reminder, nhưng chỉ một transaction được tạo durable dispatch cho reminder đó. Cách khác là atomic claim bằng status/lease với optimistic concurrency hoặc SQL locking phù hợp. Chọn cách ít phức tạp nhất đáp ứng throughput và failure semantics.

---

### High — Fire-and-forget làm các batches overlap trên cùng một instance

**Vấn đề:**  
Worker dùng:

```csharp
_ = ProcessDueRemindersAsync();
```

**Tại sao xảy ra:**  
Loop không `await` batch. Sau một phút, tick tiếp theo có thể start batch mới trong khi batch cũ vẫn chạy.

**Ảnh hưởng production:**  
Ngay cả chỉ một application instance cũng có thể có nhiều pollers logic chạy song song và đọc cùng `Pending` rows. Exceptions từ task còn có nguy cơ không được observe theo cách có chủ đích.

**Cách sửa:**  
Nếu chỉ cần một batch tại một thời điểm per process, `await ProcessDueRemindersAsync(stoppingToken)`. Nếu muốn controlled parallelism, implement explicit bounded concurrency và vẫn cần distributed idempotency/claim vì local semaphore không giải quyết nhiều instances.

---

### High — Cancellation không được propagate

**Vấn đề:**  
`ProcessDueRemindersAsync` không nhận `stoppingToken`; EF Core calls không có token; email call dùng `CancellationToken.None`.

**Tại sao xảy ra:**  
Host shutdown không tự động dừng downstream I/O nếu code không truyền token.

**Ảnh hưởng production:**  
Deployment/recycle có thể kéo dài; work tiếp tục sau khi host muốn stop; connection và external call giữ lâu hơn cần thiết; tăng xác suất một instance chết giữa side effect và state update.

**Cách sửa:**  
Propagate `stoppingToken` qua query, transaction và downstream calls. Tuy nhiên cancellation chỉ là cooperative cancellation; nếu provider đã nhận email request thì cancellation phía client không “undo” side effect.

---

### High — Không có retry/failure state rõ cho từng reminder

**Vấn đề:**  
Một exception ở `_emailSender.SendReminderAsync` làm cả batch fail và các reminders còn lại không được xử lý trong batch đó.

**Tại sao xảy ra:**  
Không có per-item retry metadata, backoff, next-attempt time hoặc failure classification.

**Ảnh hưởng production:**  
Một bad reminder hoặc provider outage có thể tạo repeated hot-loop retries mỗi phút, noisy logs và starvation của các reminders khác.

**Cách sửa:**  
Persist dispatch attempts, `NextAttemptAtUtc`, failure category và terminal/dead state nếu phù hợp. Dùng bounded exponential backoff/jitter cho transient errors. Permanent validation errors phải được xử lý khác transient provider 5xx/timeouts.

---

### Medium — Không có deterministic batch ownership/order khi backlog lớn

**Vấn đề:**  
Query chỉ `OrderBy(SendAtUtc).Take(100)`.

**Tại sao xảy ra:**  
Nhiều rows có cùng `SendAtUtc` không có total ordering, và nhiều workers có thể liên tục nhìn cùng đầu backlog nếu chưa có claim semantics.

**Ảnh hưởng production:**  
Khó reasoning về fairness, starvation và repeated selection khi backlog tăng.

**Cách sửa:**  
Thêm deterministic ordering như `ThenBy(Id)` và ownership/claim trước processing. Theo dõi backlog age thay vì chỉ batch size.

---

### Medium — Logging chưa đủ để phân biệt duplicate source

**Vấn đề:**  
Log chỉ có `ReminderId` sau khi gửi thành công.

**Tại sao xảy ra:**  
Không có `instanceId`, dispatch attempt, provider request/idempotency key, batch id, claim outcome hoặc correlation.

**Ảnh hưởng production:**  
Khi user nhận 3 emails, team không biết ba sends đến từ ba App Service instances, từ provider retry hay từ application retry sau ambiguous completion.

**Cách sửa:**  
Structured log/trace các safe identifiers: `ReminderId`, `DispatchId`, `Attempt`, `cloud_RoleInstance`, provider request id, claim result, duration, outcome và next retry. Không log email body hoặc dữ liệu nhạy cảm không cần thiết.

---

### Medium — Thiếu capacity/backpressure strategy khi backlog tăng

**Vấn đề:**  
Mỗi phút chỉ lấy 100 rows, nhưng không có metric cho backlog depth/oldest due age hoặc controlled concurrency tới email provider.

**Tại sao xảy ra:**  
Nếu campaign hoặc outage tạo 100.000 reminders, hệ thống có thể không bắt kịp SLA hoặc có thể tăng concurrency tùy ý khi team cố “fix nhanh”.

**Ảnh hưởng production:**  
Reminder trễ, provider throttling, retry storm hoặc resource contention.

**Cách sửa:**  
Đo throughput, backlog age và provider limits; chọn batch size/concurrency dựa trên capacity. Có thể tăng nhiều workers nếu dispatch idempotent, thay vì dựa vào một process duy nhất.

---

## Phiên bản đề xuất

Một design tương đối đơn giản là tách việc **enqueue durable dispatch** khỏi việc **gửi external email**.

Database cần một unique constraint:

```text
ReminderDispatch.ReminderId UNIQUE
```

Poller có thể chạy trên nhiều instances. Mỗi instance cố tạo dispatch; database uniqueness là correctness barrier.

```csharp
public sealed class ReminderWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly ILogger<ReminderWorker> _logger;

    public ReminderWorker(
        IServiceScopeFactory scopeFactory,
        ILogger<ReminderWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            await EnqueueDueRemindersAsync(stoppingToken);
        }
    }

    private async Task EnqueueDueRemindersAsync(CancellationToken ct)
    {
        using var scope = _scopeFactory.CreateScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
        var now = DateTime.UtcNow;

        var dueIds = await db.Reminders
            .AsNoTracking()
            .Where(x =>
                x.Status == ReminderStatus.Pending &&
                x.SendAtUtc <= now)
            .OrderBy(x => x.SendAtUtc)
            .ThenBy(x => x.Id)
            .Select(x => x.Id)
            .Take(100)
            .ToListAsync(ct);

        foreach (var reminderId in dueIds)
        {
            try
            {
                db.ReminderDispatches.Add(new ReminderDispatch
                {
                    Id = Guid.NewGuid(),
                    ReminderId = reminderId,
                    Status = DispatchStatus.Pending,
                    AttemptCount = 0,
                    CreatedAtUtc = now,
                    NextAttemptAtUtc = now
                });

                await db.SaveChangesAsync(ct);
            }
            catch (DbUpdateException ex) when (IsUniqueReminderDispatchViolation(ex))
            {
                db.ChangeTracker.Clear();

                _logger.LogDebug(
                    "Reminder already enqueued. ReminderId={ReminderId}",
                    reminderId);
            }
        }
    }
}
```

Dispatcher xử lý `ReminderDispatch` records độc lập. Trước production cần chọn một atomic claim strategy phù hợp database/provider để nhiều dispatch workers không cùng xử lý một dispatch. Pseudo-code flow:

```text
atomically claim Pending dispatch
  -> load immutable reminder payload or snapshot
  -> call email provider with stable idempotency key
  -> mark Sent

on transient failure
  -> increment AttemptCount
  -> set NextAttemptAtUtc with backoff
  -> release claim
```

Ví dụ interface gửi email nên nhận stable idempotency key nếu provider hỗ trợ:

```csharp
await _emailSender.SendReminderAsync(
    dispatch.ReminderId.ToString("N"),
    reminder.UserEmail,
    reminder.Subject,
    reminder.Body,
    ct);
```

Nếu provider không hỗ trợ idempotency key, vẫn tồn tại một unavoidable ambiguity:

```text
provider accepted email
→ network response lost
→ application retries
```

Khi đó local SQL transaction không thể chứng minh external provider chưa gửi. System phải định nghĩa semantics thực tế: at-least-once delivery, reconciliation, provider status lookup nếu có, hoặc UX tolerate duplicate. Không nên tuyên bố exactly-once nếu external boundary không hỗ trợ nó.

Một phương án khác là atomic row leasing thay vì unique dispatch table, ví dụ `Pending -> Processing` kèm `LeaseOwner`/`LeaseUntilUtc`. Cách đó có thể giảm thêm table nhưng phải xử lý lease expiry, crash recovery và stale worker ownership. Nếu reminder workflow còn cần audit/retry history, dispatch table thường rõ ràng hơn.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách ba concern:

1. **Scheduling:** phát hiện reminder đã đến hạn.
2. **Durable deduplication:** chỉ tạo một logical dispatch per `ReminderId` bằng unique database constraint.
3. **Delivery:** xử lý retries/external provider riêng với ownership + attempt state.

Nhiều application instances được phép poll đồng thời. Correctness không phụ thuộc vào việc “may mắn chỉ có một scheduler”. Scale-out vì vậy không tự tạo duplicate logical dispatch.

`await` batch trong `ExecuteAsync` chỉ ngăn local overlap; nó không phải distributed lock. Distributed correctness nằm ở database uniqueness/claim.

State và external side effect vẫn cần reasoning riêng. Nếu email provider hỗ trợ idempotency key, stable key giúp closing ambiguous-completion window. Nếu không, system cần documented delivery semantics thay vì giả vờ có exactly-once.

## Trade-offs

- Thêm `ReminderDispatch` table và dispatcher làm tăng schema/code/operations so với một loop đơn giản.
- Unique constraint xử lý correctness tốt nhưng nếu pollers liên tục cạnh tranh cùng backlog, duplicate insert attempts tạo database noise; atomic claim query có thể hiệu quả hơn ở scale lớn.
- Database polling mỗi phút phù hợp workload vừa phải; nếu throughput/latency requirements tăng lớn, queue/message broker có thể trở thành alternative, nhưng không cần đưa Azure Service Bus vào chỉ để giải một scheduler nhỏ nếu SQL polling đã đủ.
- Provider idempotency key có thể có retention/window semantics riêng; phải hiểu contract của provider thay vì coi key là magic exactly-once guarantee.
- Snapshot reminder payload vào dispatch tăng storage nhưng tránh nội dung thay đổi giữa enqueue và send; reference live reminder giảm duplication nhưng semantics phức tạp hơn nếu user edit reminder sau khi đã đến hạn.

## Cách kiểm thử

1. **Concurrency/integration test:** chạy 4 worker instances/process simulations cùng query 1.000 due reminders; verify database chỉ có một dispatch per `ReminderId` và không có duplicate logical sends.
2. **Failure-path test:** email provider nhận request thành công nhưng client nhận timeout; verify retry behavior theo provider idempotency semantics và không ghi trạng thái sai.
3. **Crash-recovery test:** kill worker sau khi claim dispatch nhưng trước khi mark final state; verify lease/claim có thể recovery sau timeout mà không mất reminder.
4. **Graceful-shutdown test:** cancel host token giữa batch; verify EF Core/external calls nhận cancellation hợp lý và host không start batch mới.
5. **Load test:** tạo backlog lớn hơn throughput bình thường; đo oldest-due age, database load, dispatch concurrency, provider throttling và ảnh hưởng tới request APIs.

## Quan sát trong production

Theo dõi ít nhất:

- `reminder_due_backlog_count`;
- `oldest_due_reminder_age_seconds`;
- `dispatch_claim_success_total` / conflict total;
- `dispatch_attempt_total`;
- `dispatch_success_total` / failure total;
- retries theo failure category;
- email provider duration, timeout, 4xx/5xx;
- `ReminderId`, `DispatchId`, attempt và `cloud_RoleInstance` trong structured logs;
- worker loop duration và overlap count kỳ vọng bằng 0 nếu local batches serialized;
- database query duration/lock waits nếu claim contention tăng;
- alert khi oldest due age vượt SLA hoặc retry backlog tăng liên tục.

Trong Application Insights, correlate worker dependency calls tới SQL/email provider với `DispatchId` thay vì chỉ request telemetry, vì hosted work không luôn xuất hiện như HTTP request bình thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu team dùng distributed lock để chỉ một instance chạy poller, lock đó có loại bỏ nhu cầu idempotency cho email delivery không? Vì sao?
2. Nếu email provider không hỗ trợ idempotency key nhưng business tuyệt đối không chấp nhận duplicate email, bạn cần thêm capability/contract nào để đưa guarantee gần hơn tới requirement?
3. Khi backlog tăng 100 lần, bạn sẽ scale số workers, tăng batch size hay chuyển sang queue? Metrics nào quyết định?

# Code Review Challenge 2 — Legacy jQuery marketing page render CMS content: feature vẫn chạy nhưng mở ra DOM XSS và unsafe redirect

**Chủ đề:** JavaScript, jQuery, ASP.NET Core API integration, CMS content, DOM XSS, output encoding, URL validation, authentication token storage, browser security, error handling, legacy modernization  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một marketing website cũ dùng jQuery cho một số authenticated campaign pages. Backend là ASP.NET Core API; editorial content đến từ CMS.

Business muốn giữ page hiện tại trong vài tháng trước khi migrate dần sang React/Vue, nên team chỉ sửa những rủi ro quan trọng thay vì rewrite toàn bộ frontend.

Yêu cầu:

- display name của user phải được render an toàn;
- CMS rich text được phép có một subset HTML như headings, paragraphs, links và emphasis;
- `returnUrl` chỉ được phép điều hướng tới route nội bộ của cùng application;
- access token hiện do SPA shell cung cấp;
- content editors không được coi là trusted code authors;
- CMS/API/network lỗi phải không để page ở trạng thái misleading;
- logging/telemetry cần giúp điều tra browser-side failures nhưng không được ghi token;
- website có Content Security Policy ở mức cơ bản nhưng hiện vẫn cho phép một số legacy scripts.

Code hiện tại:

## Đoạn code cần review

```javascript
$(async function () {
    const token = localStorage.getItem('access_token');
    const campaignId = new URLSearchParams(window.location.search)
        .get('campaignId');
    const returnUrl = new URLSearchParams(window.location.search)
        .get('returnUrl');

    const response = await fetch(
        '/api/campaigns/' + campaignId,
        {
            headers: {
                'Authorization': 'Bearer ' + token
            }
        });

    const data = await response.json();

    $('#welcome').html('Xin chào ' + data.displayName);
    $('#campaign-content').html(data.bodyHtml);

    $('#continue-link')
        .attr('href', returnUrl || data.defaultReturnUrl)
        .attr('target', '_blank');

    localStorage.setItem(
        'last_campaign',
        JSON.stringify(data));

    window.addEventListener('error', function (event) {
        fetch('/api/client-errors', {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'Authorization': 'Bearer ' + token
            },
            body: JSON.stringify({
                message: event.message,
                stack: event.error && event.error.stack,
                page: window.location.href,
                token: token
            })
        });
    });
});
```

## Nhiệm vụ của ứng viên

Hãy review đoạn code dưới góc nhìn security và production maintainability, sau đó:

1. xác định các DOM XSS/injection, URL-navigation, token exposure và error-handling issues;
2. phân biệt data cần output encoding với CMS rich HTML cần sanitization theo allowlist;
3. giải thích vì sao “content đến từ CMS nội bộ” không đủ để coi HTML là trusted executable input;
4. đánh giá rủi ro của access token trong `localStorage` trong presence của XSS;
5. phân tích `returnUrl` validation và các URL schemes nguy hiểm;
6. chỉ ra telemetry nào đang làm tăng security risk;
7. đề xuất một fix incremental phù hợp legacy jQuery page, không bắt buộc rewrite sang framework mới;
8. mô tả security tests và browser telemetry sau khi sửa.

## Câu hỏi gợi mở

1. Nếu `displayName` là `<img src=x onerror=...>`, `.html()` sẽ xử lý khác `.text()` như thế nào?
2. Nếu CMS rich text chứa `<script>`, event handler attribute hoặc `javascript:` URL, source “nội bộ” có làm payload đó an toàn không?
3. `returnUrl=javascript:...` hoặc `https://evil.example` có thể đi qua code hiện tại ra sao?
4. Một XSS chạy trong origin này có thể đọc gì từ `localStorage`?
5. Error telemetry hiện đang gửi dữ liệu nào mà incident/security team tuyệt đối không nên lưu?

## Gợi ý

### Gợi ý 1

Primary risk là **untrusted data đi vào HTML/URL/token-sensitive browser sinks mà không có explicit trust boundary**.

### Gợi ý 2

Đừng chỉ “escape tất cả”. Plain text và intentional rich HTML là hai data classes khác nhau: plain text cần safe text rendering; rich HTML cần policy-based sanitization hoặc structured rendering.

## Kết quả code review tham khảo

### Critical — `displayName` đi thẳng vào `.html()` tạo DOM XSS sink

**Vấn đề:**  
Code dùng:

```javascript
$('#welcome').html('Xin chào ' + data.displayName);
```

**Tại sao xảy ra:**  
`.html()` parse input thành HTML. Nếu `displayName` chứa attacker-controlled markup, browser có thể tạo executable DOM tùy payload/browser/security controls.

**Ảnh hưởng production:**  
XSS trong application origin có thể đọc application data, gọi APIs bằng user context, modify UI và truy cập browser storage mà JavaScript cùng origin có quyền đọc.

**Cách sửa:**  
Plain display name không cần HTML. Dùng `.text()`:

```javascript
$('#welcome').text('Xin chào ' + data.displayName);
```

Output encoding/safe DOM API phải là default cho plain text.

---

### Critical — CMS `bodyHtml` được inject trực tiếp mà không có sanitization contract

**Vấn đề:**  
Code:

```javascript
$('#campaign-content').html(data.bodyHtml);
```

coi CMS HTML là trusted executable markup.

**Tại sao xảy ra:**  
CMS editors, imported content, compromised accounts, integration feeds hoặc stored payloads đều có thể đưa markup nguy hiểm vào rich text. “Internal CMS” là content source, không phải security boundary.

**Ảnh hưởng production:**  
Stored XSS có thể ảnh hưởng nhiều users và tồn tại qua nhiều sessions.

**Cách sửa:**  
Define rich-text allowlist và sanitize ở một controlled boundary. Có thể sanitize server-side trước khi phát content, hoặc dùng một vetted HTML sanitizer ở client như một defense layer. Không tự viết sanitizer bằng regex. Chỉ cho phép tags/attributes/schemes thật sự cần cho editorial content.

---

### Critical — Error telemetry cố tình gửi access token về logging endpoint

**Vấn đề:**  
Payload chứa:

```javascript
token: token
```

**Tại sao xảy ra:**  
Bearer token là credential. Gửi token vào telemetry có thể làm nó xuất hiện trong application logs, Application Insights, downstream log processors, exports hoặc support tooling.

**Ảnh hưởng production:**  
Credential leakage mở rộng blast radius từ browser sang toàn observability pipeline và người có quyền đọc logs.

**Cách sửa:**  
Không log token, authorization header, cookie/session secret hoặc raw credential. Telemetry nên chứa correlation id, route, release version, sanitized error category và non-sensitive context.

---

### High — `returnUrl` được tin trực tiếp, dẫn tới open redirect hoặc dangerous scheme

**Vấn đề:**  
Code đặt raw query-string value vào `href`:

```javascript
.attr('href', returnUrl || data.defaultReturnUrl)
```

**Tại sao xảy ra:**  
Attacker có thể cung cấp external origin hoặc scheme không được phép nếu không có validation.

**Ảnh hưởng production:**  
Open redirect hỗ trợ phishing; dangerous URL schemes có thể trở thành execution/navigation sink tùy element/browser/context.

**Cách sửa:**  
Chỉ cho phép same-origin relative application paths theo explicit policy. Parse bằng `URL`, verify `origin === window.location.origin`, protocol hợp lệ và path nằm trong allowed application boundary. Backend cũng phải validate nếu return URL ảnh hưởng server-side redirect.

---

### High — Access token trong `localStorage` làm XSS impact nặng hơn

**Vấn đề:**  
Page đọc bearer token từ:

```javascript
localStorage.getItem('access_token')
```

**Tại sao xảy ra:**  
JavaScript chạy trong same origin có thể đọc `localStorage`. Nếu có DOM/stored XSS, attacker script có thể exfiltrate bearer token.

**Ảnh hưởng production:**  
Credential theft có thể kéo dài ngoài lifetime của trang bị exploit, tùy token scope/lifetime.

**Cách sửa:**  
Ngắn hạn: loại XSS sinks, giảm token lifetime/scope, không persist token lâu hơn cần thiết và strengthen CSP. Về architecture, đánh giá BFF/HttpOnly Secure cookie hoặc alternative token handling để JavaScript không trực tiếp nắm long-lived credential nếu phù hợp application. Nếu dùng cookies cho authentication, phải xử lý CSRF/SameSite/origin protections; cookie không tự động làm mọi threat biến mất.

---

### High — Không kiểm tra `response.ok` trước khi parse/render

**Vấn đề:**  
Code luôn `response.json()` và render result.

**Tại sao xảy ra:**  
401, 403, 404, 500 hoặc proxy HTML error response có thể tạo parse exception hoặc data shape bất thường.

**Ảnh hưởng production:**  
Page có thể blank, giữ stale DOM, hiển thị misleading CTA hoặc tạo noisy unhandled errors.

**Cách sửa:**  
Check status, xử lý auth failure khác server failure, render explicit error/fallback state và emit sanitized telemetry.

---

### Medium — `campaignId` không được validate ở client và phải được validate/authorize ở server

**Vấn đề:**  
Raw `campaignId` được concatenate vào URL.

**Tại sao xảy ra:**  
`fetch('/api/campaigns/' + campaignId)` dựa vào client input. Encoding/shape không rõ, và quan trọng hơn, client-side validation không đảm bảo authorization.

**Ảnh hưởng production:**  
Malformed requests hoặc, nếu backend authorization yếu, có thể dẫn tới access ngoài campaign scope.

**Cách sửa:**  
Client validate expected identifier format và dùng `encodeURIComponent`. Backend phải independently authenticate/authorize resource access; không tin campaign ID vì nó được page tạo ra.

---

### Medium — `last_campaign` persist toàn response không có data-minimization policy

**Vấn đề:**  
Code lưu nguyên `data` vào `localStorage`.

**Tại sao xảy ra:**  
Response có thể chứa fields không cần persist hoặc sau này API thêm sensitive fields mà frontend vô tình tiếp tục lưu.

**Ảnh hưởng production:**  
Tăng dữ liệu accessible cho XSS, kéo dài lifetime của stale/sensitive data và tạo compatibility bugs.

**Cách sửa:**  
Nếu thật sự cần cache, chỉ lưu explicit non-sensitive subset với TTL/version. Nếu không có requirement offline/cache rõ, không persist response.

---

### Medium — `target="_blank"` thiếu explicit `rel` defense

**Vấn đề:**  
Link mở tab mới nhưng không set `rel="noopener noreferrer"`.

**Tại sao xảy ra:**  
Modern browsers đã cải thiện `window.opener` defaults trong nhiều contexts, nhưng explicit `noopener` vẫn là defense rõ ràng và portable khi mở target mới.

**Ảnh hưởng production:**  
Giảm browser isolation trong environments/legacy behavior không như mong đợi, đặc biệt khi URL validation bị sai.

**Cách sửa:**  
Nếu vẫn cần `_blank`, set `rel="noopener noreferrer"`; nếu link bắt buộc same-origin internal navigation, cân nhắc không cần tab mới.

---

### Medium — Global error handler thiếu filtering và có thể tạo telemetry noise/recursion

**Vấn đề:**  
Mọi `window.error` đều gọi một authenticated logging API bằng `fetch` mà không có sampling/guard.

**Tại sao xảy ra:**  
Nếu logging endpoint hoặc script lỗi lặp, page có thể phát nhiều telemetry requests. Error object/stack/page URL cũng có thể chứa query-string data không nên log nguyên trạng.

**Ảnh hưởng production:**  
Noisy telemetry, chi phí cao và accidental data leakage.

**Cách sửa:**  
Redact URL query values, classify/sampling, dùng correlation/release metadata và tránh recursive reporting. Không gửi raw secrets.

## Phiên bản đề xuất

Đây là một incremental fix vẫn giữ jQuery thay vì rewrite framework ngay:

```javascript
$(async function () {
    const params = new URLSearchParams(window.location.search);
    const campaignId = params.get('campaignId');
    const requestedReturnUrl = params.get('returnUrl');
    const token = sessionStorage.getItem('access_token');

    function safeInternalUrl(value, fallback) {
        if (!value) return fallback;

        try {
            const url = new URL(value, window.location.origin);

            if (url.origin !== window.location.origin) {
                return fallback;
            }

            if (url.protocol !== 'https:' && url.protocol !== 'http:') {
                return fallback;
            }

            return url.pathname + url.search + url.hash;
        } catch {
            return fallback;
        }
    }

    function reportClientError(error, context) {
        const payload = {
            message: String(error && error.message || 'ClientError'),
            context: context,
            path: window.location.pathname,
            release: window.appRelease || 'unknown'
        };

        void fetch('/api/client-errors', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify(payload),
            keepalive: true
        });
    }

    if (!campaignId || !/^[a-zA-Z0-9_-]{1,80}$/.test(campaignId)) {
        $('#campaign-state').text('Campaign không hợp lệ.');
        return;
    }

    if (!token) {
        $('#campaign-state').text('Phiên đăng nhập không hợp lệ.');
        return;
    }

    try {
        const response = await fetch(
            '/api/campaigns/' + encodeURIComponent(campaignId),
            {
                headers: {
                    'Authorization': 'Bearer ' + token
                }
            });

        if (!response.ok) {
            throw new Error('CampaignRequestFailed:' + response.status);
        }

        const data = await response.json();

        $('#welcome').text('Xin chào ' + String(data.displayName || ''));

        // Contract: sanitizeCmsHtml must use a vetted allowlist-based sanitizer.
        // Do not implement HTML sanitization with regex.
        const safeHtml = sanitizeCmsHtml(String(data.bodyHtml || ''));
        $('#campaign-content').html(safeHtml);

        const fallback = safeInternalUrl(data.defaultReturnUrl, '/');
        const finalReturnUrl = safeInternalUrl(requestedReturnUrl, fallback);

        $('#continue-link')
            .attr('href', finalReturnUrl)
            .attr('target', '_blank')
            .attr('rel', 'noopener noreferrer');

        $('#campaign-state').text('');
    } catch (error) {
        $('#campaign-state').text(
            'Không thể tải nội dung campaign. Vui lòng thử lại.');

        reportClientError(error, 'campaign-load');
    }
});
```

`sessionStorage` ở ví dụ chỉ giảm persistence lifetime so với `localStorage`; nó **không** bảo vệ token khỏi XSS đang chạy trong cùng origin. Nếu threat model yêu cầu JavaScript không thể đọc credential, team cần thay authentication architecture, ví dụ BFF + `HttpOnly; Secure` cookie nếu phù hợp, cùng CSRF defenses tương ứng.

`sanitizeCmsHtml` phải dựa trên một sanitizer đã được review/test với explicit policy, ví dụ conceptually:

```text
allowed tags:
  p, h2, h3, strong, em, ul, ol, li, a

allowed attributes:
  a[href], a[title]

allowed URL schemes:
  https, http, same-origin relative

blocked:
  script, iframe, object, style, on* event attributes,
  javascript:, data: where not explicitly required
```

Tốt hơn nữa, nếu CMS/backend có centralized content-delivery layer, sanitizer policy có thể nằm server-side để mọi clients nhận một safe rich-text contract. Client-side defense vẫn có thể được cân nhắc như defense in depth, nhưng không nên có nhiều inconsistent sanitization rules ở từng page.

## Giải thích thiết kế sau khi sửa

Fix tách rõ ba trust classes:

1. **Plain text:** dùng `.text()` hoặc DOM `textContent`.
2. **Intentional rich HTML:** phải đi qua allowlist sanitizer/structured renderer.
3. **Navigation URL:** parse + validate scheme/origin/path policy trước khi đưa vào `href`.

Token không còn bị gửi vào telemetry. Tuy nhiên chuyển từ `localStorage` sang `sessionStorage` chỉ là incremental containment, không phải XSS fix. Root cause vẫn là loại bỏ executable injection paths và giảm credential exposure.

Không rewrite React/Vue chỉ để sửa XSS. Một legacy jQuery page vẫn có thể được làm an toàn hơn bằng safe DOM APIs, centralized sanitizer, URL policy, CSP và server-side authorization. Framework migration chỉ có giá trị nếu product/maintainability roadmap biện minh cho nó.

## Trade-offs

- Sanitization có thể loại một số markup editors đang dùng; cần content policy, migration và preview tests.
- Server-side sanitization tạo centralized rule nhưng cần versioning nếu nhiều clients phụ thuộc rich-content capabilities.
- Strict CSP/Trusted Types có thể phá legacy scripts; rollout nên report-only/measure trước rồi tighten dần nếu hệ thống còn inline scripts.
- BFF/HttpOnly-cookie architecture giảm token readability từ JavaScript nhưng tăng server/session/CSRF concerns; không phải free security win.
- Chỉ cho same-origin return URL có thể loại use case external redirect hợp lệ; nếu business cần external destinations, dùng explicit domain allowlist và UX warning thay vì raw arbitrary URL.

## Cách kiểm thử

1. **Security test:** `displayName` chứa HTML/event-handler payload; verify chỉ hiển thị text và không execute.
2. **Sanitizer test:** CMS `bodyHtml` chứa allowed markup xen `script`, `onerror`, `javascript:` links; verify dangerous nodes/attributes/schemes bị loại nhưng allowed formatting vẫn giữ.
3. **URL-policy test:** test relative path, same-origin absolute URL, external origin, protocol-relative URL, `javascript:`, malformed URL; chỉ internal allowed routes được accept.
4. **Integration/E2E test:** mock 401/403/500/non-JSON response; verify page hiển thị failure state, không giữ stale CTA và telemetry không chứa token.
5. **Browser security test:** chạy Playwright với representative campaign pages, capture console/network, assert không có request payload/header telemetry chứa bearer token và CSP violations được monitor đúng kỳ vọng.

## Quan sát trong production

Theo dõi:

- client error count theo release/page/error category;
- campaign API 401/403/5xx và browser duration;
- CSP violation reports nếu policy hỗ trợ reporting;
- sanitizer rejection counters ở server-side content pipeline nếu có;
- correlation ID giữa browser request và ASP.NET Core API trace;
- count invalid/rejected return URLs;
- không collect raw token, `Authorization` header hoặc full query-string URL trong error telemetry;
- monitor unexpected increase của auth failures sau thay đổi token/session strategy;
- dùng Playwright/synthetic checks cho key campaign flows sau deployment.

Nếu Application Insights thu client telemetry, verify data-collection rules/redaction để query strings hoặc custom properties không vô tình chứa credentials hoặc sensitive content.

## Câu hỏi phỏng vấn mở rộng

1. Nếu CMS business bắt buộc cho phép embedded third-party widgets, bạn sẽ thay đổi sanitization/CSP architecture thế nào mà không mở unrestricted script execution?
2. Nếu chuyển authentication sang HttpOnly cookie, threat model thay đổi ra sao và bạn phải bổ sung CSRF protections nào?
3. Frontend lead đề xuất “migrate ngay sang React thì XSS sẽ hết”. Bạn sẽ phản biện recommendation đó dựa trên sinks, `dangerouslySetInnerHTML`, URL handling và trust boundaries như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `BackgroundService` chạy theo **process/instance**, không phải một lần cho toàn cluster. Scale-out biến local scheduled loop thành distributed-concurrency problem.
- Local serialization bằng `await` hoặc `SemaphoreSlim` không giải quyết duplicate work giữa nhiều application instances; correctness cần durable claim/idempotency/uniqueness ở shared boundary.
- Với external side effect, phải phân tích failure window giữa durable database state và provider completion. Exactly-once không thể tự sinh ra chỉ bằng SQL transaction nếu external provider không tham gia cùng transaction hoặc hỗ trợ idempotency/reconciliation capability.
- `async`/fire-and-forget không đồng nghĩa safe concurrency; un-awaited tasks có thể overlap và làm exceptions/lifecycle khó kiểm soát.
- Plain text, rich HTML và URL là ba trust classes khác nhau. `.text()` phù hợp plain text; rich HTML cần allowlist sanitization; navigation cần URL policy.
- XSS nghiêm trọng hơn khi bearer token nằm trong JavaScript-readable storage. Loại XSS sink là ưu tiên chính; đổi storage chỉ thay đổi một phần blast radius.
- Telemetry cũng là security boundary: token, raw credentials và sensitive payloads không được đưa vào logs chỉ để “debug dễ hơn”.

## Mẫu tư duy cần nhớ

- **Local concurrency control không phải distributed coordination.**
- **Đặt correctness barrier ở shared durable state, không dựa vào timing.**
- **Với side effect external, phân tích ambiguous completion trước khi tuyên bố exactly-once.**
- **Xác định trust class trước khi chọn output sink: text, HTML hay URL.**
- **Telemetry phải giúp điều tra nhưng không được trở thành nơi rò secrets.**
