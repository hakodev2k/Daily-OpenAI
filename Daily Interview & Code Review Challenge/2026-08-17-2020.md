# Code Review Challenge 1 — Hai transaction cập nhật cùng dữ liệu theo thứ tự khác nhau gây deadlock dưới tải

**Chủ đề:** SQL transaction, locks, concurrency, EF Core transaction handling, retry, performance, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API xử lý điều chuyển nhân viên giữa hai cost center. Mỗi lần điều chuyển cần:

- khóa/cập nhật record nhân viên,
- giảm `EmployeeCount` ở cost center cũ,
- tăng `EmployeeCount` ở cost center mới,
- ghi lịch sử điều chuyển.

Song song, một background job cuối ngày cũng đồng bộ lại `EmployeeCount` cho cost center dựa trên dữ liệu nhân viên.

Hệ thống chạy trên nhiều instance. Bình thường endpoint hoạt động tốt, nhưng vào giờ cao điểm có nhiều điều chuyển đồng thời và background job vẫn đang chạy. Production ghi nhận:

- SQL Server/PostgreSQL thỉnh thoảng báo deadlock/serialization failure,
- một số request trả 500 dù retry từ client sau đó lại thành công,
- p99 latency tăng cao trong khi p50 gần như bình thường,
- log ứng dụng chỉ có `SaveChanges failed`, không biết transaction đang giữ lock nào,
- team từng thử “fix” bằng cách tăng command timeout nhưng không giải quyết được.

Business yêu cầu mỗi lần chuyển phải giữ invariant: nhân viên chỉ thuộc một cost center, count của hai cost center phải nhất quán sau commit, và retry không được tạo duplicate history.

## Đoạn code cần review

```csharp
public sealed class EmployeeTransferService
{
    private readonly AppDbContext _db;
    private readonly ILogger<EmployeeTransferService> _logger;

    public EmployeeTransferService(
        AppDbContext db,
        ILogger<EmployeeTransferService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task TransferAsync(
        Guid employeeId,
        Guid targetCostCenterId,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var employee = await _db.Employees
            .SingleAsync(x => x.Id == employeeId, cancellationToken);

        var source = await _db.CostCenters
            .SingleAsync(x => x.Id == employee.CostCenterId, cancellationToken);

        var target = await _db.CostCenters
            .SingleAsync(x => x.Id == targetCostCenterId, cancellationToken);

        if (source.Id == target.Id)
            return;

        source.EmployeeCount--;
        target.EmployeeCount++;
        employee.CostCenterId = target.Id;

        _db.EmployeeTransferHistories.Add(new EmployeeTransferHistory
        {
            EmployeeId = employeeId,
            FromCostCenterId = source.Id,
            ToCostCenterId = target.Id,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);

        await RecalculateBudgetAsync(
            source.Id,
            target.Id,
            cancellationToken);

        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Transferred employee {EmployeeId} from {SourceId} to {TargetId}",
            employeeId,
            source.Id,
            target.Id);
    }

    private async Task RecalculateBudgetAsync(
        Guid sourceId,
        Guid targetId,
        CancellationToken cancellationToken)
    {
        var rows = await _db.Employees
            .Where(x => x.CostCenterId == sourceId ||
                        x.CostCenterId == targetId)
            .ToListAsync(cancellationToken);

        await Task.Delay(150, cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Thứ tự truy cập hai cost center phụ thuộc hướng điều chuyển

**Problem:** Request A→B đọc/cập nhật A rồi B, còn request B→A đọc/cập nhật B rồi A.  
**Why it happens:** Thứ tự lock không được chuẩn hóa. Khi database giữ lock trên các row tương ứng, hai transaction có thể chờ chéo nhau.  
**Production impact:** Deadlock hiếm ở tải thấp nhưng tăng rõ khi nhiều transfer đối nghịch chạy đồng thời; một transaction bị chọn làm victim và request thất bại.  
**Severity:** Critical  
**Recommended fix:** Luôn truy cập/cập nhật resource theo thứ tự xác định, ví dụ sort hai `CostCenterId` rồi load/update theo thứ tự đó; hoặc dùng conditional SQL/locking strategy phù hợp database.

### 2. Transaction bị giữ qua phần `RecalculateBudgetAsync`

**Problem:** Sau `SaveChangesAsync`, transaction vẫn mở trong khi service tiếp tục query toàn bộ employee của hai cost center và `Task.Delay`.  
**Why it happens:** Transaction scope bao trùm cả công việc không cần thiết cho invariant chính.  
**Production impact:** Lock được giữ lâu hơn, tăng lock wait, deadlock probability, connection occupancy và p99 latency.  
**Severity:** High  
**Recommended fix:** Chỉ giữ transaction cho state transition tối thiểu. Budget recalculation nên chạy sau commit hoặc qua durable background work nếu cho phép eventual consistency.

### 3. `return` trước khi commit/dispose transaction rõ nghĩa nghiệp vụ

**Problem:** Khi source và target giống nhau, method return ngay trong transaction vừa mở.  
**Why it happens:** Validation business được thực hiện quá muộn.  
**Production impact:** Không làm sai dữ liệu vì dispose sẽ rollback transaction chưa commit, nhưng tạo transaction/database round-trip không cần thiết và làm flow khó đọc.  
**Severity:** Medium  
**Recommended fix:** Kiểm tra request/target logic sớm hơn khi có thể; nếu cần đọc source trước thì chỉ bắt đầu explicit transaction sau validation cần thiết.

### 4. Counter update dựa trên read-modify-write có thể chịu contention/lost-update tùy cơ chế concurrency

**Problem:** `EmployeeCount--` và `++` dựa trên giá trị entity đã materialize.  
**Why it happens:** Nếu nhiều transaction cùng cập nhật một cost center mà không có row-level serialization/concurrency token phù hợp, correctness phụ thuộc isolation/locking behavior.  
**Production impact:** Count có thể lệch hoặc nhiều request bị conflict/retry khi contention cao.  
**Severity:** High  
**Recommended fix:** Bảo vệ invariant tại database: atomic increment/decrement, concurrency token/version, hoặc locking/isolation phù hợp. Đồng thời có reconciliation job vì derived counter có thể lệch do lỗi lịch sử.

### 5. Không có idempotency cho lịch sử transfer

**Problem:** Client/application retry toàn operation sau timeout hoặc transient database error có thể tạo thêm history nếu lần trước đã commit nhưng response bị mất.  
**Why it happens:** Request không có operation/idempotency key và history không có uniqueness phù hợp.  
**Production impact:** Duplicate history, notification/reporting sai và khó audit.  
**Severity:** High  
**Recommended fix:** Nhận `operationId` từ caller hoặc tạo workflow id ổn định, lưu cùng history và đặt unique constraint theo business semantics.

### 6. Không phân loại lỗi transient trước khi retry

**Problem:** Code không cho thấy policy phân biệt deadlock/serialization failure với validation, constraint hay programming error.  
**Why it happens:** Retry thường được coi là giải pháp chung.  
**Production impact:** Retry lỗi không transient làm tăng tải; retry deadlock đồng thời không jitter có thể tạo lại contention.  
**Severity:** High  
**Recommended fix:** Chỉ retry lỗi transient được xác định, giới hạn attempt, dùng backoff/jitter và đảm bảo operation idempotent.

### 7. Query toàn bộ employee chỉ để “recalculate” làm tăng lock/read pressure

**Problem:** `ToListAsync` materialize mọi employee ở hai cost center trong lúc transaction đang mở.  
**Why it happens:** Workload read lớn nằm trong critical path.  
**Production impact:** Tăng database I/O, memory, transaction duration và khả năng đụng lock với background sync.  
**Severity:** Medium  
**Recommended fix:** Nếu thực sự cần tính tổng, dùng aggregate query nhỏ hơn; tốt hơn là tách sau commit nếu không bắt buộc atomic với transfer.

### 8. Không có correlation/diagnostic context cho retry và transaction conflict

**Problem:** Log cuối chỉ ghi transfer thành công; lỗi chỉ có log chung ở layer khác.  
**Why it happens:** Không ghi operation id, attempt, transaction duration hoặc loại database error.  
**Production impact:** Khó phân biệt deadlock, timeout, connection pool pressure hay slow query.  
**Severity:** Medium  
**Recommended fix:** Structured log với `OperationId`, employee/source/target, attempt, elapsed time, exception category; trace DB spans và theo dõi deadlock/lock wait từ database.

## Phiên bản code đề xuất

Ví dụ dưới đây minh họa ba nguyên tắc: validate sớm, cập nhật hai cost center theo thứ tự xác định và giữ transaction ngắn. Cơ chế concurrency cụ thể có thể thay đổi theo SQL Server/PostgreSQL và model của hệ thống.

```csharp
public sealed class EmployeeTransferService
{
    private readonly AppDbContext _db;
    private readonly IBackgroundTaskQueue _queue;
    private readonly ILogger<EmployeeTransferService> _logger;

    public EmployeeTransferService(
        AppDbContext db,
        IBackgroundTaskQueue queue,
        ILogger<EmployeeTransferService> logger)
    {
        _db = db;
        _queue = queue;
        _logger = logger;
    }

    public async Task TransferAsync(
        Guid employeeId,
        Guid targetCostCenterId,
        Guid operationId,
        CancellationToken cancellationToken)
    {
        if (await _db.EmployeeTransferHistories
            .AsNoTracking()
            .AnyAsync(x => x.OperationId == operationId, cancellationToken))
        {
            return;
        }

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var employee = await _db.Employees
            .SingleAsync(x => x.Id == employeeId, cancellationToken);

        var sourceId = employee.CostCenterId;
        if (sourceId == targetCostCenterId)
        {
            await tx.RollbackAsync(cancellationToken);
            return;
        }

        var ids = new[] { sourceId, targetCostCenterId }
            .OrderBy(x => x)
            .ToArray();

        var centers = await _db.CostCenters
            .Where(x => ids.Contains(x.Id))
            .OrderBy(x => x.Id)
            .ToListAsync(cancellationToken);

        if (centers.Count != 2)
            throw new InvalidOperationException("Cost center not found.");

        var source = centers.Single(x => x.Id == sourceId);
        var target = centers.Single(x => x.Id == targetCostCenterId);

        if (source.EmployeeCount <= 0)
            throw new InvalidOperationException("Invalid source employee count.");

        source.EmployeeCount--;
        target.EmployeeCount++;
        employee.CostCenterId = target.Id;

        _db.EmployeeTransferHistories.Add(new EmployeeTransferHistory
        {
            OperationId = operationId,
            EmployeeId = employeeId,
            FromCostCenterId = source.Id,
            ToCostCenterId = target.Id,
            CreatedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        await _queue.EnqueueAsync(
            new RecalculateCostCenterBudget(source.Id, target.Id, operationId),
            cancellationToken);

        _logger.LogInformation(
            "Transferred employee {EmployeeId} from {SourceId} to {TargetId}. OperationId={OperationId}",
            employeeId,
            source.Id,
            target.Id,
            operationId);
    }
}
```

Ở database nên có unique constraint/index trên `EmployeeTransferHistory.OperationId`. Nếu `EmployeeCount` là invariant quan trọng dưới contention cao, nên cân nhắc atomic SQL update hoặc concurrency token thay vì chỉ dựa vào tracked entity read-modify-write. Background task cũng phải idempotent theo `operationId`.

## Trade-offs

- **Deterministic ordering** giảm khả năng deadlock nhưng không loại bỏ mọi deadlock; database vẫn có thể deadlock qua index/table khác.
- **Transaction ngắn** cải thiện concurrency nhưng budget recalculation trở thành eventual consistency.
- **Atomic SQL update** mạnh về correctness/performance nhưng làm application code ít thuần ORM hơn.
- **Optimistic concurrency** phù hợp khi conflict hiếm; nếu conflict rất cao, retry nhiều có thể tốn kém.
- **Derived counter** giúp read nhanh nhưng tăng complexity write. Nếu không thật sự cần realtime, tính aggregate theo query hoặc cache có thể đơn giản hơn.

## Cách kiểm thử

1. **Concurrency test:** chạy hàng trăm transfer A→B và B→A đồng thời; xác minh không có count âm, không lost update và tổng employee count được bảo toàn.
2. **Deadlock/transient test:** cố tình tạo lock contention, xác minh retry chỉ áp dụng cho lỗi transient và có giới hạn/backoff.
3. **Idempotency test:** gửi cùng `operationId` nhiều lần, kể cả sau simulated response loss; chỉ có một history và một state transition hợp lệ.
4. **Failure-path test:** làm background enqueue/recalculation thất bại sau commit; transfer chính vẫn đúng và task có cơ chế retry/reconciliation.
5. **Load/database test:** đo p50/p95/p99, transaction duration, lock wait, deadlock count, rows read và connection pool usage trước/sau thay đổi.

## Quan sát trong production

- **Logs:** `OperationId`, employee/source/target, attempt number, elapsed time, database error category; không log dữ liệu nhạy cảm không cần thiết.
- **Metrics:** transfer success/failure, retry count, deadlock/serialization failure count, transaction duration, DB command latency, background reconciliation lag.
- **Traces:** span cho transaction, từng query/update và background enqueue; correlation từ API sang worker.
- **Alerts:** deadlock rate tăng, p99 transfer latency, retry storm, reconciliation backlog.
- **Database observations:** deadlock graph/report, lock wait, blocked sessions, execution plan và index usage của các statement liên quan.

# Code Review Challenge 2 — Cho phép QA nhập regex tùy ý khiến API bị CPU spike và treo worker

**Chủ đề:** Input validation, performance, resource exhaustion, cancellation, error handling, security  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một QA automation portal cho phép tester tìm các dòng log phù hợp với pattern trước khi tạo Playwright bug report. Để linh hoạt, backend cho phép người dùng gửi một regular expression và áp dụng regex đó lên log của một test run.

Mỗi test run thường có 5.000–20.000 dòng log, nhưng một số end-to-end suite có hơn 100.000 dòng. Production ghi nhận:

- một vài search request dùng 100% CPU trong thời gian dài,
- request đã bị client hủy nhưng CPU vẫn tiếp tục cao,
- khi nhiều người search cùng lúc, Thread Pool queue tăng và API khác cũng chậm,
- có pattern chỉ vài chục ký tự nhưng xử lý rất lâu trên một số dòng log,
- log service ghi nguyên pattern người dùng nhập, đôi lúc chứa dữ liệu mà tester copy từ production.

Business vẫn muốn hỗ trợ regex cho power user, nhưng search không được làm ảnh hưởng availability của API và cần có giới hạn rõ ràng.

## Đoạn code cần review

```csharp
public sealed class LogSearchService
{
    private readonly ITestRunRepository _repository;
    private readonly ILogger<LogSearchService> _logger;

    public LogSearchService(
        ITestRunRepository repository,
        ILogger<LogSearchService> logger)
    {
        _repository = repository;
        _logger = logger;
    }

    public async Task<IReadOnlyList<string>> SearchAsync(
        Guid testRunId,
        string pattern,
        CancellationToken cancellationToken)
    {
        var lines = await _repository.GetLogLinesAsync(
            testRunId,
            cancellationToken);

        _logger.LogInformation(
            "Searching {Count} lines with regex {Pattern}",
            lines.Count,
            pattern);

        var regex = new Regex(
            pattern,
            RegexOptions.IgnoreCase | RegexOptions.Compiled);

        var matches = new List<string>();

        foreach (var line in lines)
        {
            if (regex.IsMatch(line))
                matches.Add(line);
        }

        return matches;
    }
}
```

4. Ưu tiên vấn đề cần sửa trước.

## Kết quả code review tham khảo

### 1. Regex không có match timeout

**Problem:** `Regex` được tạo mà không có timeout.  
**Why it happens:** Một số pattern có thể gây backtracking rất tốn CPU trên input nhất định.  
**Production impact:** Một request có thể giữ CPU lâu bất thường; nhiều request đồng thời có thể làm giảm availability toàn process.  
**Severity:** Critical  
**Recommended fix:** Tạo regex với timeout hữu hạn phù hợp workload và xử lý `RegexMatchTimeoutException` như lỗi validation/resource limit, không retry mù quáng.

### 2. Request cancellation không dừng một `IsMatch` đang chạy

**Problem:** Token chỉ được dùng khi fetch logs; loop regex không kiểm tra token và một call `IsMatch` sync có thể kéo dài.  
**Why it happens:** Regex matching là CPU-bound synchronous operation.  
**Production impact:** Client disconnect nhưng server vẫn dùng CPU cho đến khi match hoàn tất hoặc timeout regex xảy ra.  
**Severity:** High  
**Recommended fix:** Dùng regex timeout để giới hạn từng match và `cancellationToken.ThrowIfCancellationRequested()` giữa các dòng/batch.

### 3. Không giới hạn độ dài/độ phức tạp pattern

**Problem:** Người dùng có thể gửi pattern rất dài hoặc phức tạp.  
**Why it happens:** Input chỉ được parse bởi `Regex`, không có policy application-level.  
**Production impact:** Tăng compile cost, memory và rủi ro abuse.  
**Severity:** High  
**Recommended fix:** Giới hạn pattern length; nếu business không cần regex đầy đủ thì ưu tiên literal search hoặc DSL hạn chế. Với regex nâng cao, giới hạn role/quota.

### 4. `RegexOptions.Compiled` cho regex ad-hoc theo từng request có thể tốn chi phí không đáng

**Problem:** Mọi pattern đều được compile ngay cả khi chỉ dùng trong một request.  
**Why it happens:** `Compiled` bị coi mặc định là nhanh hơn trong mọi tình huống.  
**Production impact:** Tăng startup/compile work và memory cho workload có rất nhiều pattern khác nhau.  
**Severity:** Medium  
**Recommended fix:** Benchmark theo workload; với regex ad-hoc dùng một lần, compiled regex có thể không đáng. Nếu cache, phải bounded và có eviction.

### 5. Materialize toàn bộ log trước khi search

**Problem:** Repository trả toàn bộ `lines` vào memory rồi mới lọc.  
**Why it happens:** API không stream/paginate dữ liệu.  
**Production impact:** Large test run làm tăng memory pressure và GC, đặc biệt khi nhiều search đồng thời.  
**Severity:** High  
**Recommended fix:** Stream/batch log lines nếu storage hỗ trợ; đặt max lines/bytes per search và pagination/time window.

### 6. Kết quả không bị giới hạn

**Problem:** Mọi matching line đều được giữ trong `List<string>`.  
**Why it happens:** Không có result cap hoặc pagination.  
**Production impact:** Pattern rộng như `.*` có thể trả toàn bộ log, tăng memory, serialization cost và response size.  
**Severity:** High  
**Recommended fix:** `maxResults`, pagination/cursor hoặc stop khi đạt giới hạn; trả `truncated=true`.

### 7. Không có admission control/concurrency limit cho workload CPU-bound

**Problem:** Nhiều regex search nặng có thể chạy đồng thời.  
**Why it happens:** Endpoint được xử lý giống request I/O thông thường.  
**Production impact:** CPU saturation, Thread Pool starvation/queueing và ảnh hưởng endpoint khác.  
**Severity:** High  
**Recommended fix:** Rate limit/concurrency limit riêng cho expensive search; với workload lớn có thể chuyển sang bounded worker queue.

### 8. Log nguyên pattern người dùng nhập

**Problem:** Pattern có thể chứa email, token, đoạn production log hoặc dữ liệu nhạy cảm.  
**Why it happens:** Operational log ghi raw input.  
**Production impact:** Sensitive data bị lưu trong hệ thống log và tăng compliance risk.  
**Severity:** Medium  
**Recommended fix:** Log pattern hash/length và request metadata; chỉ log raw pattern trong môi trường kiểm soát khi thực sự cần.

## Phiên bản code đề xuất

```csharp
public sealed record LogSearchResult(
    IReadOnlyList<string> Matches,
    bool Truncated);

public sealed class LogSearchService
{
    private const int MaxPatternLength = 512;
    private const int MaxResults = 500;
    private static readonly TimeSpan MatchTimeout =
        TimeSpan.FromMilliseconds(100);

    private readonly ITestRunRepository _repository;
    private readonly ILogger<LogSearchService> _logger;

    public LogSearchService(
        ITestRunRepository repository,
        ILogger<LogSearchService> logger)
    {
        _repository = repository;
        _logger = logger;
    }

    public async Task<LogSearchResult> SearchAsync(
        Guid testRunId,
        string pattern,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(pattern) ||
            pattern.Length > MaxPatternLength)
        {
            throw new ArgumentException("Invalid regex pattern length.");
        }

        Regex regex;
        try
        {
            regex = new Regex(
                pattern,
                RegexOptions.IgnoreCase,
                MatchTimeout);
        }
        catch (ArgumentException ex)
        {
            throw new ArgumentException("Invalid regex pattern.", ex);
        }

        var matches = new List<string>(capacity: 64);
        var truncated = false;

        await foreach (var line in _repository
            .StreamLogLinesAsync(testRunId, cancellationToken))
        {
            cancellationToken.ThrowIfCancellationRequested();

            bool isMatch;
            try
            {
                isMatch = regex.IsMatch(line);
            }
            catch (RegexMatchTimeoutException ex)
            {
                _logger.LogWarning(
                    ex,
                    "Regex search timed out for TestRunId={TestRunId}, PatternLength={PatternLength}",
                    testRunId,
                    pattern.Length);

                throw new InvalidOperationException(
                    "The regular expression is too expensive to evaluate.",
                    ex);
            }

            if (!isMatch)
                continue;

            matches.Add(line);

            if (matches.Count >= MaxResults)
            {
                truncated = true;
                break;
            }
        }

        _logger.LogInformation(
            "Regex search completed for TestRunId={TestRunId}, PatternLength={PatternLength}, MatchCount={MatchCount}, Truncated={Truncated}",
            testRunId,
            pattern.Length,
            matches.Count,
            truncated);

        return new LogSearchResult(matches, truncated);
    }
}
```

Trong production, timeout 100 ms chỉ là ví dụ policy; giá trị thực tế phải đo từ workload và SLO. Nếu regex là tính năng phụ, một lựa chọn an toàn hơn là default sang literal/substring search và chỉ bật regex cho user được phân quyền.

## Trade-offs

- **Regex timeout thấp** bảo vệ availability nhưng có thể từ chối pattern hợp lệ trên dòng log rất dài.
- **Streaming** giảm memory nhưng repository/storage phức tạp hơn và có thể tăng round-trip nếu batch quá nhỏ.
- **Result cap** bảo vệ API nhưng UI cần pagination/truncation UX.
- **Concurrency limit** bảo vệ CPU nhưng tạo queue/waiting; cần timeout/admission policy rõ ràng.
- **Literal search** an toàn và dễ tối ưu hơn nhưng giảm expressiveness cho power user.

## Cách kiểm thử

1. **Pathological regex test:** dùng pattern có nguy cơ catastrophic backtracking trên input được kiểm soát; xác minh timeout xảy ra trong budget dự kiến và API không treo lâu.
2. **Cancellation test:** hủy request khi đang scan nhiều dòng; xác minh loop dừng giữa các item/batch và resource được giải phóng.
3. **Large-log test:** search trên 100k+ lines; đo memory allocation, CPU, elapsed time và xác minh result cap.
4. **Concurrency/load test:** chạy nhiều expensive searches đồng thời; xác minh rate/concurrency policy bảo vệ p95/p99 của endpoint khác.
5. **Security/privacy test:** xác minh raw regex/log content không xuất hiện trong operational logs khi policy không cho phép.

## Quan sát trong production

- **Metrics:** regex search duration, timeout count, cancellation count, scanned lines/bytes, match count, truncated result count, active search concurrency, queue wait.
- **Logs:** testRunId, pattern length/hash, timeout/truncation/outcome; tránh raw pattern và raw matching lines.
- **Traces:** span riêng cho load/stream logs và matching phase để phân biệt I/O với CPU cost.
- **Alerts:** regex timeout rate tăng, CPU saturation, active search concurrency chạm giới hạn, p99 của API khác tăng đồng thời.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `Task.Run(() => regex.IsMatch(...), cancellationToken)` không tự giải quyết triệt để vấn đề CPU/resource exhaustion?
2. Khi nào bạn nên chuyển regex search sang background job thay vì xử lý đồng bộ trong request?
3. Nếu business chỉ cần tìm keyword và wildcard đơn giản, bạn sẽ thiết kế DSL hoặc search strategy nào thay regex tùy ý?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Deadlock thường là vấn đề **thứ tự lock + thời gian giữ transaction + contention**, không phải chỉ là “timeout quá ngắn”.
- Transaction nên bảo vệ invariant tối thiểu và được giữ càng ngắn càng tốt.
- Retry phải đi cùng phân loại lỗi, backoff và idempotency; nếu không, retry có thể nhân đôi side effect.
- User-provided regex là workload CPU-bound không đáng tin; phải có timeout và resource limits.
- Cancellation token không thay thế được timeout nội tại của thao tác synchronous CPU-bound.
- Observability cho concurrency/performance cần nhìn cả application metrics lẫn database/runtime evidence.

## Mẫu tư duy cần nhớ

- Lock shared resources theo thứ tự xác định.
- Giữ transaction ngắn; đẩy công việc eventual-consistency ra sau commit khi business cho phép.
- Thiết kế retry cùng idempotency và database invariants.
- Xem input có thể tiêu thụ tài nguyên như một phần của security boundary.
- Đặt giới hạn cho thời gian, kích thước, concurrency và số kết quả — không chỉ validate syntax.
