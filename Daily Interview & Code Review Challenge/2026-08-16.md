# Câu 1 — `HttpClient`, connection pooling và latency tăng dưới tải

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 10–12 phút  
**Kỹ năng được đánh giá:** `HttpClient`, `SocketsHttpHandler`, TCP/TLS, connection pooling, DNS, ASP.NET Core DI, observability

## Bối cảnh

Một ASP.NET Core API gọi Microsoft Graph và một internal REST API. Sau refactor, một service chuyển sang tạo `HttpClient` mới cho mỗi operation:

```csharp
public async Task<string> GetCalendarAsync(
    string userId,
    string accessToken,
    CancellationToken cancellationToken)
{
    using var client = new HttpClient();
    client.DefaultRequestHeaders.Authorization =
        new AuthenticationHeaderValue("Bearer", accessToken);

    using var response = await client.GetAsync(
        $"https://graph.microsoft.com/v1.0/users/{userId}/calendar",
        cancellationToken);

    response.EnsureSuccessStatusCode();
    return await response.Content.ReadAsStringAsync(cancellationToken);
}
```

Production có khoảng 100–300 request/giây. P50 gần như bình thường nhưng P95/P99 tăng mạnh vào giờ cao điểm. Downstream telemetry không cho thấy server processing time tăng tương ứng. Một số request gặp timeout, connect error hoặc `TaskCanceledException`. CPU của application chưa saturation.

Chưa biết outbound NAT/proxy topology, socket statistics, timeout phase hay cách service được đăng ký trước refactor.

## Câu hỏi chính

Điều gì xảy ra bên trong `HttpClient`/`SocketsHttpHandler` và TCP connection lifecycle trong trường hợp này? Vì sao implementation trên có thể tạo latency hoặc resource pressure dưới tải, misconception nào có thể dẫn đến code này, production risk là gì, và bạn sẽ kiểm chứng giả thuyết bằng cách nào?

## Câu hỏi làm rõ nên cân nhắc

1. Trước refactor, service dùng typed client, `IHttpClientFactory` hay long-lived `HttpClient`?
2. Timeout xảy ra ở DNS/connect/TLS, response headers hay toàn request?
3. Hệ thống có NAT, proxy hoặc outbound connection limit không?
4. Downstream có throttling hoặc DNS/IP rotation không?
5. Outbound concurrency thực tế trên mỗi instance là bao nhiêu?

## Gợi ý tư duy

**Gợi ý 1:** Lifetime của object .NET và lifetime của TCP connection không phải cùng một khái niệm.

**Gợi ý 2:** Xem xét handler, connection pool, TCP/TLS handshake, connection reuse và socket states.

**Gợi ý 3:** Thiết kế client/handler lifetime để reuse connection nhưng vẫn refresh connection khi cần; sau đó dùng dependency telemetry và network counters để xác minh.

## Cấu trúc trả lời đề xuất

1. Clarify topology và failure phase.
2. Mô tả `HttpClient → handler → connection pool`.
3. Phân tích connection churn dưới concurrency.
4. Đưa ra giả thuyết cạnh tranh.
5. Chọn telemetry để chứng minh/bác bỏ.
6. Đề xuất client lifetime và timeout policy.
7. Phân tích retry/cancellation.
8. Load test và monitor sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu connection pooling gắn với handler và việc tạo/dispose client/handler liên tục có thể làm giảm connection reuse.
- Connection churn làm tăng TCP/TLS setup cost và có thể tạo socket/port pressure.
- CPU thấp không loại trừ outbound connection bottleneck.
- `TaskCanceledException` không tự động chứng minh caller đã cancel.
- Không kết luận root cause chỉ từ code; cần dependency/network telemetry.

### Điểm cộng

- Dùng `IHttpClientFactory` hoặc long-lived client tùy requirement.
- Gắn bearer token theo `HttpRequestMessage` thay vì mutate shared default header trên client dùng concurrent.
- Xem xét `PooledConnectionLifetime` khi cần refresh connection/DNS trong long-lived handler.
- Phân biệt connect timeout, request timeout và caller cancellation.
- Kiểm tra proxy/NAT limits và downstream throttling.

### Nâng cao

- Hiểu factory có thể tạo `HttpClient` object mới nhưng quản lý/reuse handler theo lifecycle của factory.
- Không retry mù quáng non-idempotent operation.
- Phân biệt socket pressure với Thread Pool starvation, DNS issue và downstream queueing.
- Dùng distributed tracing/HTTP telemetry để tách client-side wait khỏi downstream server time.

## Hướng giải quyết tham khảo

**Assumption:** traffic đủ cao để có nhiều outbound calls đồng thời và code thực sự tạo client mới cho mỗi operation.

`HttpClient` gửi request qua message handler; trong modern .NET, `SocketsHttpHandler` quản lý connection pool. Khi handler được reuse hợp lý, TCP connections có thể được tái sử dụng thay vì thiết lập TCP/TLS mới cho từng call.

Việc tạo/dispose client liên tục có thể làm tăng connection churn. Dispose object không đồng nghĩa mọi TCP state ở OS biến mất ngay. Dưới concurrency, handshake overhead và giới hạn outbound network có thể xuất hiện trước khi CPU application cao.

Một hướng ASP.NET Core phù hợp là typed client:

```csharp
services.AddHttpClient<CalendarService>(client =>
{
    client.BaseAddress = new Uri("https://graph.microsoft.com/");
    client.Timeout = TimeSpan.FromSeconds(15);
});
```

Và token theo request:

```csharp
public sealed class CalendarService(HttpClient client)
{
    public async Task<string> GetCalendarAsync(
        string userId,
        string accessToken,
        CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            $"v1.0/users/{Uri.EscapeDataString(userId)}/calendar");

        request.Headers.Authorization =
            new AuthenticationHeaderValue("Bearer", accessToken);

        using var response = await client.SendAsync(
            request,
            HttpCompletionOption.ResponseHeadersRead,
            cancellationToken);

        response.EnsureSuccessStatusCode();
        return await response.Content.ReadAsStringAsync(cancellationToken);
    }
}
```

Tôi sẽ thu dependency latency, connect/error telemetry, active connections/socket states, timeout classification, request concurrency và downstream processing duration. Nếu downstream xử lý nhanh nhưng client mất nhiều thời gian trước khi request đến server, connection management trở thành giả thuyết mạnh hơn.

**Alternatives/trade-offs:** long-lived `HttpClient` đơn giản và reuse tốt; factory thuận tiện cho DI/configuration/resilience. Cả hai đều cần timeout, DNS/connection lifetime và retry policy phù hợp.

**Failure cases:** DNS/IP rotation, NAT exhaustion, throttling, TLS failure, caller cancellation, timeout quá dài tạo backlog.

**Security/performance:** không log bearer token; escape path input; retry chỉ operation phù hợp.

**Testing:** load test với controlled downstream latency, cancellation, connection failures và concurrency cao; so P95/P99 và connection reuse trước/sau.

**Monitoring:** dependency latency/error rate, timeout classification, active outbound requests, connection/socket counters.

**Điều kiện làm thay đổi recommendation:** low-throughput short-lived CLI có lifetime requirement khác; infrastructure đặc biệt có thể yêu cầu handler configuration khác.

## Mẫu trả lời trong phỏng vấn

“Dấu hiệu đầu tiên tôi chú ý là `HttpClient` được tạo cho từng call, nhưng tôi chưa kết luận ngay socket exhaustion. Tôi cần biết timeout nằm ở phase nào và topology outbound ra sao.

`HttpClient` dùng handler để quản lý connection pool. Nếu handler liên tục bị thay mới, application giảm khả năng reuse connection và có thể tăng TCP/TLS handshake cũng như socket pressure. Vì vậy P95 có thể tăng dù CPU chưa cao và downstream server vẫn xử lý nhanh.

Tôi sẽ kiểm tra dependency traces, connect latency nếu có, socket states, outbound concurrency, timeout classification và downstream server duration. Fix thường là typed client hoặc `IHttpClientFactory`, timeout/cancellation rõ ràng, và token gắn theo từng request. Nếu dùng long-lived handler và cần thích ứng DNS, tôi cân nhắc connection lifetime phù hợp.

Sau fix tôi chạy load test và so P95/P99, connection reuse và error rate. Tôi vẫn kiểm tra NAT/proxy limits và throttling vì symptom này không chỉ có một root cause.”

## Câu hỏi đào sâu

1. Vì sao `IHttpClientFactory` vẫn hữu ích dù có thể tạo `HttpClient` object mới nhiều lần?
2. Long-lived connection có thể ảnh hưởng thế nào khi DNS/backend IP thay đổi?
3. **Thách thức:** Nếu đổi sang factory nhưng latency vẫn cao, bạn điều tra gì trước khi tăng `MaxConnectionsPerServer`?

## Lỗi trả lời thường gặp

- Tạo/dispose `HttpClient` per request chỉ vì nó implement `IDisposable`.
- Khẳng định mọi `TaskCanceledException` là caller cancellation.
- Chỉ tăng timeout.
- Retry vô hạn.
- Dùng shared client nhưng mutate `DefaultRequestHeaders.Authorization` theo từng request.

## Thang điểm 0–10

| Tiêu chí | Điểm tối đa |
|---|---:|
| Requirement clarification | 1.5 |
| Technical correctness | 2.5 |
| Depth | 2.0 |
| Trade-off analysis | 1.5 |
| Production readiness | 1.5 |
| Communication | 1.0 |

# Câu 2 — Incident: Redis cache trả quyền truy cập cũ sau khi role thay đổi

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** caching, authorization, Redis, consistency, incident response, security, observability

## Bối cảnh

Một ASP.NET Core application có authorization layer đọc permissions từ SQL rồi cache vào Redis:

```text
permissions:{tenantId}:{userId}
```

TTL hiện là 30 phút.

Sau deployment, security team báo rằng một số user đã bị admin remove khỏi role `FinanceApprover` nhưng vẫn có thể approve invoice thêm vài phút. Không phải user nào cũng bị. Một số request đi qua instance A bị từ chối, nhưng request khác qua instance B lại thành công.

Team vừa refactor permission cache và bổ sung local in-memory cache trên mỗi instance để giảm Redis traffic.

Chưa rõ cache invalidation flow, deployment version giữa các instances, token claims, local cache TTL hay admin update transaction boundary.

## Câu hỏi chính

Bạn đang on-call. Hãy xử lý incident này từ **impact assessment → mitigation → evidence → hypotheses → root cause → short-term fix → long-term prevention → verification/monitoring**. Không giả định Redis chắc chắn là nguyên nhân duy nhất.

## Câu hỏi làm rõ nên cân nhắc

1. Permission được quyết định từ token claims, memory cache, Redis hay SQL ở từng code path?
2. Remove role có yêu cầu revoke quyền gần như ngay lập tức không?
3. Local cache và Redis TTL/invalidation hiện hoạt động thế nào?
4. Có nhiều application versions cùng chạy sau rolling deployment không?
5. Audit log có thể xác định các unauthorized approvals đã xảy ra không?

## Gợi ý tư duy

**Gợi ý 1:** Đây trước hết là security incident: cần xác định blast radius và ngăn side effect mới trước khi tối ưu cache.

**Gợi ý 2:** Hai cache layers tạo nhiều trạng thái có thể stale; invalidating Redis không tự động invalidating memory của mọi instance.

**Gợi ý 3:** Với authorization data, hãy cân nhắc versioned permission state hoặc invalidation signal cùng bounded stale window thay vì chỉ dựa vào TTL.

## Cấu trúc trả lời đề xuất

1. Xác định business/security impact.
2. Stabilize và giảm blast radius.
3. Dựng timeline từ audit evidence.
4. Liệt kê nhiều hypotheses.
5. Reproduce theo từng cache/token path.
6. Sửa correctness trước performance.
7. Thiết kế invalidation/versioning lâu dài.
8. Reconcile unauthorized actions.
9. Test và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Ưu tiên security impact và audit các action đã xảy ra.
- Không xem TTL là authorization revocation guarantee.
- Nhận ra memory cache của mỗi instance có thể stale độc lập với Redis.
- Kiểm tra token claims như một nguồn stale khác.
- Có immediate mitigation, ví dụ bypass/disable permission cache cho sensitive operation nếu khả thi.
- Có kế hoạch reconcile các invoice approval sai quyền.

### Điểm cộng

- Correlation theo `tenantId`, `userId`, permission version, instance và deployment version.
- Permission version/security stamp để phát hiện stale entries.
- Pub/sub/invalidation event chỉ là signal; consumer failure vẫn cần bounded fallback.
- TTL ngắn hơn cho high-risk permissions hoặc authoritative re-check tại sensitive boundary.
- Cache-aside implementation phải tránh repopulate stale data sau invalidation race.

### Nâng cao

- Phân tích race: transaction role update chưa commit nhưng invalidation phát trước, request khác repopulate old value.
- Transactional outbox cho permission-change event khi cần reliable invalidation.
- Versioned cache key/state để old invalidation không overwrite newer permission state.
- Phân biệt authentication token revocation với application authorization state.

## Hướng giải quyết tham khảo

### 1. Impact assessment

Xác định:

- tenant/users bị ảnh hưởng;
- permission nào stale;
- unauthorized approvals nào đã xảy ra;
- incident còn tiếp diễn không;
- financial/compliance impact.

### 2. Immediate mitigation

Nếu `ApproveInvoice` là sensitive operation, tôi ưu tiên correctness:

- tạm bypass local permission cache;
- có thể bypass toàn bộ permission cache cho action này và đọc authoritative state;
- hoặc giảm TTL mạnh trong khi điều tra;
- đảm bảo các instance chạy cùng known-good version nếu deployment inconsistency đáng nghi.

Không flush toàn Redis nếu blast radius của thao tác đó không được hiểu rõ.

### 3. Evidence

Mỗi authorization decision nên dựng được:

```text
RequestId
TenantId
UserId
Permission
Decision
PermissionVersion
Source = Memory | Redis | Database | Token
InstanceId
DeploymentVersion
```

Không log token hoặc sensitive claims không cần thiết.

### 4. Hypotheses

- local memory cache stale;
- Redis stale;
- invalidation không phát/không nhận;
- role update transaction và invalidation bị race;
- old deployment code path;
- access token chứa role claim cũ;
- cache key thiếu tenant/version;
- stale value được repopulate sau invalidation.

### 5. Long-term design

Một hướng là permission version:

```text
UserSecurityState
- TenantId
- UserId
- PermissionVersion
```

Khi role thay đổi, version tăng. Cache entry chứa cùng version. Sensitive authorization path chỉ tin cache nếu version/state còn hợp lệ theo thiết kế đã chọn.

Nếu dùng invalidation event, publish reliably sau database commit, ví dụ qua outbox. Mỗi instance xóa local cache khi nhận signal. Nhưng signal có thể mất hoặc instance có thể offline, nên vẫn cần TTL/version fallback.

### Alternatives/trade-offs

- **DB check mỗi request:** consistency tốt, tăng database load.
- **Redis-only:** đơn giản hơn memory + Redis, latency tăng nhẹ nhưng giảm stale states.
- **Memory + Redis:** nhanh hơn nhưng invalidation phức tạp.
- **Versioned authorization:** correctness mạnh hơn nhưng thêm read/state management.

Với high-risk action, tôi chấp nhận thêm latency để giảm stale authorization window.

### Failure cases

- invalidation event mất;
- instance restart;
- out-of-order events;
- role update rollback;
- token chứa stale claims;
- Redis unavailable.

### Security/performance

Authorization correctness ưu tiên hơn vài millisecond cache latency. Audit log phải đủ để forensic nhưng không chứa token/secrets.

### Testing

- Remove role rồi lập tức gọi approve qua nhiều instances.
- Race giữa role update và concurrent authorization.
- Drop invalidation event.
- Redis unavailable.
- Rolling deployment với mixed versions.
- Token có stale role claim.

### Monitoring

- authorization source distribution;
- cache hit/miss;
- permission-version mismatch;
- invalidation failures;
- denied/allowed decision anomalies;
- sensitive action audit.

**Điều kiện làm thay đổi recommendation:** nếu business chấp nhận stale permission 30 phút cho low-risk feature, architecture có thể đơn giản hơn; financial/admin operations thường cần revocation semantics chặt hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là security incident trước khi coi là cache bug. Tôi xác định user/tenant nào bị ảnh hưởng, permission nào stale và có approval nào cần reverse hoặc review không. Nếu incident còn tiếp diễn, tôi ưu tiên bypass local cache hoặc authoritative re-check cho `ApproveInvoice` để chặn side effect mới.

Sau đó tôi dựng timeline theo request, user, instance, deployment version và nguồn authorization decision. Tôi kiểm tra cả memory cache, Redis, token claims, invalidation flow và transaction boundary. Một race đáng chú ý là invalidation xảy ra trước commit rồi request khác repopulate permission cũ.

Về lâu dài, tôi không dùng TTL như revocation guarantee. Tôi có thể dùng permission/security version, reliable invalidation sau commit qua outbox, và local cache chỉ là optimization có bounded stale window. Với sensitive action tôi sẵn sàng trả thêm latency để tăng correctness.

Tôi test remove-role đồng thời với requests qua nhiều instances, dropped invalidation, Redis failure và mixed deployment. Sau fix tôi monitor version mismatch, invalidation failures và authorization decisions theo source.”

## Câu hỏi đào sâu

1. Redis Pub/Sub có đủ để đảm bảo mọi instance invalidate permission không?
2. Bạn xử lý race giữa database commit và cache invalidation thế nào?
3. **Thách thức:** Security yêu cầu revoke quyền trong dưới 5 giây nhưng database đang chịu tải cao. Bạn cân bằng correctness và performance ra sao?

## Lỗi trả lời thường gặp

- Chỉ giảm TTL rồi coi như đã giải quyết.
- Flush toàn Redis ngay mà không hiểu impact.
- Bỏ qua local memory cache hoặc token claims.
- Không audit unauthorized side effects đã xảy ra.
- Dùng Pub/Sub như một delivery guarantee tuyệt đối.

# Câu 3 — Quyết định nâng cấp .NET khi business muốn feature mới nhưng team sợ regression

**Loại câu hỏi:** Engineering decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** requirement clarification, upgrade strategy, compatibility, testing, rollout, stakeholder communication, technical debt

## Bối cảnh

Một hệ thống ASP.NET Core business-critical đang chạy một phiên bản .NET cũ hơn target version mà team muốn chuyển tới. Hệ thống có:

- khoảng 20 projects trong solution;
- EF Core;
- Microsoft Graph SDK;
- Hangfire;
- Redis;
- background jobs;
- Docker;
- CI/CD;
- nhiều integrations nội bộ.

Product muốn một feature lớn được release trong 6 tuần. Một engineer đề xuất nâng framework ngay vì “đằng nào cũng phải nâng”. Engineer khác muốn trì hoãn upgrade vì lần trước package upgrade đã gây incompatibility với một thư viện Excel và Graph SDK.

Security team cũng muốn giảm thời gian chạy trên runtime/package versions sắp hoặc đã gần hết support, nhưng chưa cung cấp deadline cụ thể.

Không rõ test coverage, current runtime version, package compatibility, deployment strategy hoặc số môi trường pre-production.

## Câu hỏi chính

Bạn là Senior/Architect chịu trách nhiệm đưa ra quyết định. Bạn sẽ cấu trúc quyết định **nâng cấp ngay, tách upgrade khỏi feature, hay thực hiện theo từng bước** như thế nào? Hãy giải thích cách bạn thu thập evidence, đánh giá risk, thiết kế rollout, kiểm thử, rollback và truyền đạt trade-offs cho product/security/engineering.

## Câu hỏi làm rõ nên cân nhắc

1. Runtime hiện tại còn được vendor support đến khi nào?
2. Feature mới có thực sự phụ thuộc API/runtime mới không?
3. Automated regression/integration test coverage hiện tại thế nào?
4. Những package critical nào chưa xác nhận compatibility?
5. Deployment có canary/blue-green/fast rollback không?

## Gợi ý tư duy

**Gợi ý 1:** Đừng biến câu hỏi thành “upgrade tốt hay xấu”; hãy tách business deadline, support/security risk và technical change surface.

**Gợi ý 2:** Framework upgrade, major package upgrade và feature development không nhất thiết phải nằm trong cùng một change set.

**Gợi ý 3:** Dùng compatibility spike + evidence + staged rollout để giảm uncertainty trước khi commit toàn bộ roadmap.

## Cấu trúc trả lời đề xuất

1. Clarify hard constraints.
2. Xác định decision criteria.
3. Inventory compatibility/risk.
4. Đưa ra 2–3 options.
5. So sánh blast radius và schedule risk.
6. Chọn approach.
7. Thiết kế test/rollout/rollback.
8. Communicate decision và checkpoints.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không nâng chỉ vì “version mới hơn tốt hơn”.
- Kiểm tra official support lifecycle và package compatibility thực tế.
- Tách framework upgrade khỏi unrelated package major upgrades khi có thể.
- Có compatibility spike trước khi estimate chắc chắn.
- Có regression/integration testing và rollback plan.
- Nêu rõ điều kiện làm recommendation thay đổi.

### Điểm cộng

- Inventory package/transitive dependencies và breaking changes.
- Build/test matrix trên old/new target nếu khả thi.
- Container/runtime base image và CI agents cũng nằm trong upgrade scope.
- Database migrations được tách khỏi runtime upgrade nếu không bắt buộc.
- Canary/staged deployment và production telemetry comparison.

### Nâng cao

- Quantify schedule risk thay vì tranh luận bằng cảm giác.
- Feature flags để giảm coupling giữa deployment và release.
- Architecture decision record với assumptions và rollback criteria.
- Nếu current runtime out-of-support, security risk có thể trở thành hard constraint thay vì optional technical debt.

## Hướng giải quyết tham khảo

### Assumptions

Không giả định version cụ thể. Việc đầu tiên là xác minh official support lifecycle của current/target runtime và compatibility của critical packages.

### Decision criteria

Tôi dùng các tiêu chí:

- security/support urgency;
- feature dependency;
- package compatibility;
- test confidence;
- deployment/rollback capability;
- engineering capacity;
- deadline risk.

### Options

**Option A — Upgrade + feature cùng lúc**

Ưu điểm: một migration window.  
Nhược điểm: blast radius lớn, khó phân biệt regression do framework hay feature.

**Option B — Feature trước, upgrade sau**

Ưu điểm: giảm immediate change surface.  
Nhược điểm: có thể kéo dài unsupported runtime risk hoặc tạo double work.

**Option C — Compatibility spike rồi upgrade nền tảng tách biệt trước feature**

Ưu điểm: giảm uncertainty và giữ change sets dễ quan sát.  
Nhược điểm: tiêu tốn một phần 6 tuần trước khi feature tiến nhanh.

Trong phần lớn trường hợp, tôi ưu tiên **spike ngắn → upgrade nền tảng riêng → stabilize → feature**, nếu current version/support deadline và compatibility cho phép timeline đó.

### Implementation approach

1. Inventory target framework và packages.
2. Đọc breaking changes/release notes của các dependencies quan trọng.
3. Tạo branch/spike nâng target framework tối thiểu, không đồng thời major-upgrade mọi thư viện.
4. Build toàn solution.
5. Chạy unit/integration/E2E.
6. Test Microsoft Graph/background jobs/cache/database paths.
7. Deploy pre-production.
8. So telemetry với baseline.
9. Canary production nếu infrastructure hỗ trợ.
10. Chỉ sau stabilization mới merge feature lớn hoặc bật feature flag.

### Failure cases

- package compile được nhưng runtime behavior đổi;
- serialization behavior khác;
- EF provider incompatibility;
- Docker base image/runtime mismatch;
- CI agent thiếu SDK;
- Graph/third-party SDK major version gây API break;
- background job serialization incompatibility với queued jobs cũ.

### Security/performance

Xác minh support/security deadline từ official lifecycle. Không trì hoãn runtime đã out-of-support chỉ để giữ deadline mà không có explicit risk acceptance.

Performance cần benchmark/telemetry trên critical endpoints thay vì mặc định version mới nhanh hơn.

### Testing

- build matrix;
- unit/integration tests;
- database/provider tests;
- Hangfire existing-job compatibility;
- Graph integration tests;
- Playwright critical journeys;
- load/smoke tests.

### Monitoring

So trước/sau:

- error rate;
- P95/P99 latency;
- CPU/memory/GC;
- background-job failures;
- database errors;
- external dependency failures.

### Communication

Tôi trình bày decision như risk matrix, không phải preference cá nhân:

```text
Option              Schedule risk   Regression risk   Security risk
Upgrade + feature   High            High              Low after release
Feature first       Medium          Medium            Depends on support
Upgrade separately  Medium          Lower             Low after upgrade
```

Có checkpoint sau compatibility spike để re-estimate.

**Điều kiện làm thay đổi recommendation:** nếu feature bắt buộc runtime mới thì upgrade trở thành prerequisite; nếu current runtime đã out-of-support thì security urgency tăng mạnh; nếu critical dependency chưa support target runtime thì có thể cần chọn target khác hoặc thay dependency.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không quyết định dựa trên việc version mới tốt hơn hay sợ regression. Tôi tách ba câu hỏi: current runtime còn support bao lâu, feature có phụ thuộc runtime mới không, và chúng ta có đủ test/rollback confidence không.

Tôi làm compatibility spike ngắn: nâng target framework với thay đổi package tối thiểu, build toàn solution, chạy integration/E2E cho Graph, EF, Hangfire, Redis và critical flows. Tôi đặc biệt tránh gộp framework upgrade với nhiều major package upgrades nếu không bắt buộc, vì khi regression xảy ra sẽ khó cô lập nguyên nhân.

Nếu spike tốt, tôi ưu tiên deploy upgrade nền tảng riêng, stabilize rồi phát triển hoặc bật feature qua feature flag. Nếu current runtime đã out-of-support hoặc feature bắt buộc runtime mới thì upgrade trở thành hard constraint. Ngược lại, nếu critical dependency chưa compatible, tôi không ép upgrade chỉ để đạt target version.

Rollout cần pre-production, canary nếu có, baseline telemetry và rollback rõ ràng. Tôi trình bày với product/security bằng risk matrix và có checkpoint sau spike để cập nhật estimate thay vì hứa timeline dựa trên assumption.”

## Câu hỏi đào sâu

1. Bạn có nâng EF Core/Graph SDK major version cùng lúc với target framework không?
2. Làm sao kiểm tra queued Hangfire jobs cũ vẫn deserialize sau deployment?
3. **Thách thức:** Compatibility spike phát hiện một package critical chưa support target runtime nhưng current runtime hết support trong 4 tuần. Bạn xử lý thế nào?

## Lỗi trả lời thường gặp

- Upgrade mọi package lên latest trong cùng PR.
- Chỉ kiểm tra compile thành công.
- Không xác minh support lifecycle.
- Không có rollback/canary strategy.
- Tranh luận với product bằng technical preference thay vì risk/evidence.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `HttpClient` object lifetime, handler lifetime và TCP connection lifetime là các lớp khác nhau; connection reuse là yếu tố quan trọng của outbound scalability.
- Security-sensitive authorization không nên coi TTL cache là revocation guarantee.
- Multi-layer cache tăng performance nhưng cũng tăng số trạng thái stale và complexity của invalidation.
- Incident response cần **stabilize trước**, sau đó dựng evidence và kiểm chứng nhiều giả thuyết cạnh tranh.
- Framework upgrade là một engineering decision dựa trên support lifecycle, dependency compatibility, test confidence và blast radius — không phải cuộc đua dùng version mới nhất.
- Tách các change surface lớn giúp regression dễ cô lập và rollback hơn.

## Mẫu tư duy cần nhớ

1. **Measure before concluding** — code smell tạo giả thuyết, telemetry mới xác nhận root cause.
2. **Stabilize before investigating deeply** — đặc biệt khi incident liên quan security hoặc financial side effects.
3. **Cache is an optimization, not the source of truth** — xác định stale window và invalidation semantics rõ ràng.
4. **Separate unrelated change surfaces** — framework, major packages và feature lớn không nên bị gộp mặc định.
5. **Turn uncertainty into evidence** — compatibility spike, load test, canary và observability giúp quyết định dựa trên dữ liệu.
