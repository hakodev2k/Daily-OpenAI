# Câu 1 — EF Core tracking, deferred execution và memory tăng bất thường

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 10–12 phút  
**Kỹ năng được đánh giá:** EF Core tracking, LINQ deferred execution, query materialization, DbContext lifetime, memory, SQL observability

## Bối cảnh

Một ASP.NET Core API cung cấp endpoint export timesheet. Dữ liệu có thể từ vài nghìn đến vài trăm nghìn rows. Sau một đợt refactor, team thấy memory tăng nhanh trong quá trình export, GC hoạt động nhiều hơn và đôi khi request timeout.

Code rút gọn:

```csharp
public async Task<IReadOnlyList<TimesheetExportRow>> ExportAsync(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    var query = _dbContext.TimesheetEntries
        .Where(x => x.WorkDate >= from && x.WorkDate <= to)
        .Include(x => x.Employee)
        .Include(x => x.Project)
        .OrderBy(x => x.EmployeeId);

    var activeOnly = query.Where(x => x.Employee.IsActive);

    var entries = await activeOnly.ToListAsync(cancellationToken);

    return entries
        .Select(x => new TimesheetExportRow(
            x.Employee.EmployeeCode,
            x.Project.Code,
            x.WorkDate,
            x.Hours,
            x.Note))
        .ToList();
}
```

Developer giải thích rằng `query` chỉ là một biến LINQ nên gần như không tốn memory trước `ToListAsync`, còn sau khi query xong thì EF Core “tự giải phóng tracking data” vì request sắp kết thúc.

Production dùng scoped `DbContext`. Chưa biết query thực tế trả bao nhiêu rows, generated SQL, số entity được tracked, payload export cuối cùng hay việc endpoint có thực sự cần entity graph đầy đủ hay không.

## Câu hỏi chính

Hãy giải thích điều gì xảy ra bên trong từ lúc xây dựng `IQueryable` đến lúc `ToListAsync` hoàn tất. Vì sao cách viết trên có thể gây memory pressure và latency lớn, misconception nào có thể xuất hiện, production risk là gì, và bạn sẽ xác minh giả thuyết bằng cách nào trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

1. Export có thật sự cần toàn bộ rows trong memory cùng lúc không?
2. Có cần tracking để update entity sau khi đọc không?
3. Generated SQL hiện tại có select thừa columns hoặc join tạo dữ liệu lớn không?
4. Peak row count và kích thước trung bình của mỗi row là bao nhiêu?
5. Output được trả trực tiếp, ghi file, stream hay chuyển sang thư viện Excel nào đó?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt giai đoạn xây expression tree với giai đoạn query được materialize.
- **Gợi ý 2:** Hãy quan sát cả object graph được materialize lẫn EF Core Change Tracker.
- **Gợi ý 3:** Nếu đây là read-only export, projection sớm + no-tracking + xử lý theo batch/stream có thể quan trọng hơn việc tối ưu LINQ syntax.

## Cấu trúc trả lời đề xuất

1. Làm rõ volume và output pipeline.
2. Giải thích deferred execution của `IQueryable`.
3. Giải thích SQL translation và materialization.
4. Phân tích tracking, navigation materialization và object allocation.
5. Đưa ra các hypotheses cạnh tranh.
6. Đo generated SQL, row count, allocations, GC và duration.
7. Đề xuất projection/no-tracking/batching hoặc streaming.
8. Test tính đúng đắn và performance sau thay đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chủ yếu xây expression tree; query chưa chạy trước terminal operation như `ToListAsync`.
- `ToListAsync` materialize toàn bộ result set vào memory.
- Mặc định tracking query có thể đưa entity vào Change Tracker nếu query trả entity types.
- `Include` materialize navigation entities, có thể tạo object graph lớn hơn nhu cầu export.
- Scoped `DbContext` không có nghĩa tracking data được giải phóng ngay sau `ToListAsync`; nó sống cùng context cho tới khi context bị dispose hoặc tracker được clear.
- Cần xem generated SQL và đo thực tế trước khi kết luận.

### Điểm cộng

- Dùng projection trực tiếp sang DTO để chỉ select columns cần thiết.
- Dùng `AsNoTracking()` cho read-only query khi phù hợp.
- Tránh materialize entity graph nếu chỉ cần export flat rows.
- Cân nhắc pagination/batching hoặc streaming nếu downstream cho phép.
- Phân biệt database execution time với client-side materialization/serialization time.

### Nâng cao

- Hiểu identity resolution và trade-off giữa `AsNoTracking()` với `AsNoTrackingWithIdentityResolution()` trong các graph có duplicate references.
- Nhận ra `Include` không phải lúc nào cũng cần khi projection có thể translate trực tiếp.
- Đo allocation rate, Gen 0/1/2 collections, LOH nếu payload lớn.
- Không “fix” bằng `GC.Collect()`.

## Hướng giải quyết tham khảo

**Giả định:** đây là read-only export và không cần update các entity đã đọc.

`query` và `activeOnly` là `IQueryable`; chúng chủ yếu tạo expression tree. Khi gọi `ToListAsync`, EF Core dịch expression sang SQL, gửi query xuống database, đọc result set, materialize entity `TimesheetEntry`, `Employee`, `Project`, và với tracking query thì đưa entity vào Change Tracker.

Vấn đề chính không chỉ là SQL. Nếu query trả 200.000 rows, application phải giữ danh sách entity, navigation objects, tracking metadata và sau đó còn tạo thêm danh sách `TimesheetExportRow`. Có thể tồn tại hai representation lớn trong memory cùng lúc.

Một hướng phù hợp hơn:

```csharp
public Task<List<TimesheetExportRow>> ExportAsync(
    DateTime from,
    DateTime to,
    CancellationToken cancellationToken)
{
    return _dbContext.TimesheetEntries
        .AsNoTracking()
        .Where(x =>
            x.WorkDate >= from &&
            x.WorkDate <= to &&
            x.Employee.IsActive)
        .OrderBy(x => x.EmployeeId)
        .Select(x => new TimesheetExportRow(
            x.Employee.EmployeeCode,
            x.Project.Code,
            x.WorkDate,
            x.Hours,
            x.Note))
        .ToListAsync(cancellationToken);
}
```

Projection giúp database chỉ trả về dữ liệu cần thiết và tránh materialize entity graph. `AsNoTracking()` giảm tracking overhead cho read-only flow. Tuy nhiên nếu result set vẫn quá lớn, tôi tiếp tục xem xét batching/streaming thay vì nghĩ rằng projection một mình giải quyết mọi vấn đề.

**Failure cases:** export quá lớn, query plan kém, lock/blocking ở database, network throughput thấp, serialization/Excel library giữ nhiều dữ liệu trong memory.

**Security/performance:** giới hạn date range hoặc yêu cầu async export job nếu user có thể yêu cầu dataset cực lớn; authorization phải giới hạn dữ liệu user được export.

**Testing:** so generated SQL, row count, allocated bytes, peak working set, GC collections, P95 duration và output correctness trước/sau.

**Monitoring:** DB duration, materialization/export duration riêng, rows exported, payload size, memory/GC counters.

**Điều kiện làm thay đổi recommendation:** nếu entity cần được update trong cùng unit of work, tracking có thể là đúng; nếu output library bắt buộc giữ workbook toàn bộ trong memory, bottleneck có thể nằm ở bước sau EF Core.

## Mẫu trả lời trong phỏng vấn

“Điểm đầu tiên tôi làm rõ là volume và endpoint có cần tracking không. `IQueryable` chưa chạy query ngay; nó tích lũy expression cho tới `ToListAsync`. Tại thời điểm đó EF Core translate sang SQL, đọc toàn bộ result set và materialize object graph. Với tracking query, context còn giữ tracking metadata cho các entity đó.

Trong đoạn code này, sau `ToListAsync` chúng ta giữ danh sách entity lớn rồi lại tạo thêm danh sách DTO, nên peak memory có thể rất cao. `Include` cũng có thể materialize nhiều dữ liệu hơn nhu cầu export.

Nếu đây là read-only flow, tôi ưu tiên projection trực tiếp sang DTO và `AsNoTracking`. Nếu volume vẫn rất lớn, tôi sẽ thiết kế batching hoặc streaming tùy output format. Tôi sẽ không tối ưu theo cảm giác: trước hết xem generated SQL, row count, DB duration, allocation rate, GC và peak memory để tách database bottleneck khỏi application materialization.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution()` hữu ích hơn `AsNoTracking()`?
2. Nếu SQL chạy 300 ms nhưng request mất 12 giây, bạn tách phần thời gian còn lại như thế nào?
3. **Thách thức:** Nếu export library bắt buộc giữ toàn bộ workbook trong memory, projection EF Core có còn đủ không?

## Lỗi trả lời thường gặp

- Nghĩ rằng scoped `DbContext` tự clear Change Tracker ngay sau mỗi query.
- Chỉ thêm index mà không đo nơi thời gian thực sự bị mất.
- Dùng `GC.Collect()` để chữa memory pressure.
- Gọi `ToListAsync` sớm rồi mới filter/project trong memory.
- Dùng `Include` theo thói quen cho mọi read query.

# Câu 2 — Incident: background job gửi email và cập nhật trạng thái bị chạy trùng

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** background jobs, Hangfire, idempotency, transactions, concurrency, external side effects, incident response, observability

## Bối cảnh

Một hệ thống .NET dùng Hangfire để xử lý offboarding nhân viên. Job thực hiện ba bước:

1. Đọc cấu hình offboarding từ SQL Server.
2. Gọi Exchange Online/Microsoft Graph để cập nhật mailbox hoặc forwarding.
3. Cập nhật trạng thái `Completed` vào database và ghi history.

Sau deployment, HR báo một số mailbox nhận thao tác hai lần và có user nhận duplicate notification. Log cho thấy cùng một `EmployeeId` đôi lúc được xử lý bởi hai worker cách nhau vài giây. Một số job có retry vì external API timeout.

Team đề xuất thêm distributed lock quanh toàn bộ job và tắt retry.

Chưa rõ job được enqueue từ đâu, có recurring job trùng không, retry policy hiện tại, external operations có idempotent không, database có unique constraint nào, hoặc trạng thái được ghi trước hay sau side effect.

## Câu hỏi chính

Bạn đang xử lý incident này. Hãy trình bày cách đánh giá impact, giảm thiểu ngay, thu thập evidence, xây hypotheses, xác định root cause, sửa ngắn hạn và thiết kế lâu dài để job có thể retry an toàn mà không tạo duplicate side effects.

## Câu hỏi làm rõ nên cân nhắc

1. Cùng business operation có thể được enqueue từ nhiều nguồn hay không?
2. Hangfire retry xảy ra sau exception ở bước nào?
3. External operation có naturally idempotent, overwrite-based hay additive side effect?
4. Có business operation ID / idempotency key ổn định cho mỗi offboarding action không?
5. Database update và enqueue có nằm trong cùng transaction hoặc outbox flow không?

## Gợi ý tư duy

- **Gợi ý 1:** Retry không phải lỗi thiết kế; retry không có idempotency mới là nguy hiểm.
- **Gợi ý 2:** Hãy tách “job được chạy nhiều lần” khỏi “business side effect xảy ra nhiều lần”.
- **Gợi ý 3:** Persistent operation state + idempotency key + atomic state transition thường mạnh hơn chỉ dựa vào lock.

## Cấu trúc trả lời đề xuất

1. Xác định blast radius và business impact.
2. Stabilize: tạm giảm duplicate enqueue/disable nguồn lỗi nếu cần.
3. Correlate theo operation ID, EmployeeId, job ID, retry count và worker.
4. Liệt kê hypotheses: duplicate enqueue, retry, race, deployment, timeout ambiguity.
5. Reproduce failure paths.
6. Thiết kế idempotency boundary.
7. Đảm bảo state transition atomic.
8. Thiết kế retry/backoff và reconciliation.
9. Monitor sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không tắt retry chỉ để che duplicate side effects.
- Phân biệt at-least-once execution với exactly-once business effect.
- Có idempotency key hoặc operation identity ổn định.
- Xử lý “timeout nhưng external system thực ra đã thành công”.
- Persist trạng thái đủ để worker khác nhận biết operation đang/đã hoàn tất.
- Có reconciliation cho các mailbox đã bị tác động sai.

### Điểm cộng

- Unique constraint cho business operation để ngăn duplicate creation.
- Optimistic concurrency hoặc atomic conditional update để claim operation.
- External API read-back để xác minh trạng thái trước khi retry side effect nếu API không hỗ trợ idempotency key.
- Transactional outbox nếu job được sinh từ thay đổi database quan trọng.
- Exponential backoff + jitter và phân loại transient/permanent errors.

### Nâng cao

- Nhận ra distributed lock không giải quyết duplicate đã tồn tại sau lock release, timeout ambiguity hoặc crash giữa side effect và DB update.
- Thiết kế state machine như `Pending → Processing → Completed/Failed` với lease/version khi cần.
- Poison-message/dead-letter equivalent hoặc manual review sau số lần retry hợp lý.
- Metrics theo idempotency conflict, duplicate suppression và retry reason.

## Hướng giải quyết tham khảo

**Immediate mitigation:** xác định nguồn enqueue trùng, tạm disable nguồn sai hoặc giới hạn concurrency cho operation nhạy cảm, nhưng vẫn giữ khả năng retry transient failure. Audit các employee bị tác động hai lần.

**Evidence:** dùng correlation gồm `OffboardingOperationId`, `EmployeeId`, Hangfire job ID, retry attempt, worker instance, external request ID và timestamps.

**Root-cause hypotheses:**

- cùng operation bị enqueue hai lần;
- automatic retry sau timeout;
- worker crash sau external success nhưng trước DB commit;
- hai workers cùng đọc `Pending` trước khi một worker cập nhật;
- deployment tạo recurring registration trùng.

Một model an toàn hơn là persist operation riêng:

```text
OffboardingOperation
- Id
- EmployeeId
- ActionType
- IdempotencyKey (unique)
- Status
- AttemptCount
- Version / RowVersion
- LastError
- CompletedAt
```

Worker trước tiên claim operation bằng atomic conditional update hoặc optimistic concurrency. Nếu đã `Completed`, job return thành công. Nếu external call timeout, worker không mặc định gọi lại ngay; với operation overwrite-based có thể read current remote state để xác định side effect đã áp dụng chưa. Sau đó mới quyết định retry.

Ví dụ pseudo-flow:

```csharp
public async Task ExecuteAsync(Guid operationId, CancellationToken ct)
{
    var op = await _operations.GetAsync(operationId, ct);

    if (op.Status == OperationStatus.Completed)
        return;

    if (!await _operations.TryClaimAsync(operationId, ct))
        return;

    try
    {
        var currentState = await _exchange.ReadStateAsync(op.EmployeeId, ct);

        if (!MatchesDesiredState(currentState, op))
        {
            await _exchange.ApplyAsync(op, ct);
        }

        await _operations.MarkCompletedAsync(operationId, ct);
    }
    catch (TransientDependencyException)
    {
        await _operations.ReleaseForRetryAsync(operationId, ct);
        throw;
    }
}
```

Đây chỉ là skeleton; thiết kế claim/lease phải xử lý worker crash. Với side effect không thể read-back hoặc không idempotent, cần API-level idempotency key nếu dependency hỗ trợ, hoặc một reconciliation/manual workflow phù hợp.

**Trade-offs:** distributed lock có thể giảm concurrent execution nhưng tăng dependency và không tạo exactly-once semantics. Idempotency state phức tạp hơn nhưng bảo vệ business effect ngay cả khi job chạy nhiều lần.

**Testing:** duplicate enqueue, two-worker race, timeout-after-success, crash-after-side-effect, permanent failure.

**Monitoring:** duplicate suppressions, retries theo reason, operations stuck in Processing, external error rate, completion latency.

**Điều kiện làm thay đổi recommendation:** nếu external action tự nhiên là idempotent overwrite và read-back đáng tin cậy, solution có thể đơn giản hơn; nếu side effect là irreversible/additive, cần kiểm soát chặt hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi không bắt đầu bằng việc tắt retry vì background system thực tế phải chịu transient failure. Mục tiêu là cho phép job chạy lại nhưng business effect chỉ được áp dụng một cách an toàn.

Tôi sẽ trước hết xác định blast radius và correlation theo operation ID, EmployeeId, Hangfire job ID, retry attempt và worker. Tôi kiểm tra cả duplicate enqueue lẫn case timeout sau khi Exchange đã thực hiện thành công.

Về design, tôi tạo một business operation có idempotency key unique và persistent state. Worker phải claim operation atomically. Nếu đã completed thì return. Với external API không hỗ trợ idempotency key, tôi cố gắng read current state trước khi apply lại để xử lý timeout ambiguity. Retry vẫn tồn tại nhưng chỉ cho transient failures, có backoff và giới hạn.

Distributed lock có thể là lớp bổ sung, nhưng không phải correctness guarantee vì crash sau side effect nhưng trước DB update vẫn xảy ra. Sau fix tôi chạy concurrency/failure-injection tests và theo dõi duplicate suppression, retry reason và stuck operations.”

## Câu hỏi đào sâu

1. Distributed lock giải quyết được gì và không giải quyết được gì trong case này?
2. Làm sao xử lý worker crash khi operation đang ở trạng thái `Processing`?
3. **Thách thức:** External API trả timeout nhưng không có read API và cũng không hỗ trợ idempotency key — bạn thiết kế thế nào?

## Lỗi trả lời thường gặp

- Tắt retry hoàn toàn.
- Tin rằng Hangfire hoặc message queue đảm bảo exactly-once business effect.
- Chỉ thêm lock mà không có persistent idempotency state.
- Mark `Completed` trước external side effect mà không phân tích failure semantics.
- Retry mọi exception với cùng policy.

# Câu 3 — Thiết kế AI QA Agent có MCP tools nhưng không được phép tự ý gây side effect

**Loại câu hỏi:** AI engineering / system design decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** AI agents, MCP, tool permissions, prompt/context engineering, deterministic validation, evaluation, auditability, Playwright, security

## Bối cảnh

Team muốn xây một AI QA Agent hỗ trợ web application nội bộ. Agent nhận requirement hoặc bug ticket, tự:

1. đọc repository/test guidance;
2. lập test plan;
3. dùng Playwright để thao tác QA environment;
4. thu screenshot/video/log;
5. phân tích failure;
6. đề xuất test case mới hoặc patch;
7. tạo report.

Agent được kết nối qua MCP/tools tới browser, repository, test artifacts và một số internal APIs.

Product owner muốn “agent tự chạy càng nhiều càng tốt”, còn security team yêu cầu agent không được tự ý gửi email, sửa production data, merge code, hoặc gọi tool có side effect nguy hiểm.

Chưa rõ data sensitivity, tool inventory, approval policy, expected test volume, acceptable false-positive rate hay cách đo agent có thật sự tốt hơn workflow hiện tại.

## Câu hỏi chính

Bạn sẽ thiết kế AI QA Agent này như thế nào để xác định phần nào nên dùng LLM, phần nào phải deterministic, context nào được đưa vào model, tools/permissions nào được phép, cách validate output và detect hallucination, cơ chế human approval, evaluation, fallback, audit và monitoring ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. Agent chỉ chạy QA/staging hay có khả năng chạm production?
2. Những tool nào chỉ read-only và tool nào có side effect?
3. Test result “pass/fail” có rule deterministic hay phụ thuộc visual/semantic judgment?
4. Repo hoặc test data có secrets/PII không?
5. KPI của agent là coverage, bug detection, thời gian điều tra, false-positive rate hay chi phí?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng để LLM quyết định những gì có thể kiểm tra bằng invariant rõ ràng.
- **Gợi ý 2:** Permission boundary của tool quan trọng không kém prompt.
- **Gợi ý 3:** Thiết kế agent như một workflow có state, evidence và gates, không phải một prompt rất dài.

## Cấu trúc trả lời đề xuất

1. Xác định use cases và threat model.
2. Chia deterministic steps và probabilistic steps.
3. Thiết kế context contract.
4. Phân loại tools theo risk.
5. Định nghĩa approval gates.
6. Structured output + validators.
7. Evidence-grounded conclusions.
8. Evaluation dataset và regression suite.
9. Fallback/manual takeover.
10. Audit, metrics, cost và privacy.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Giải thích vì sao cần LLM: planning, semantic interpretation, failure analysis, summarization; không dùng LLM cho mọi thứ.
- Assertions, schema validation, authorization checks và critical side-effect gates phải deterministic khi có thể.
- Tool permissions theo least privilege.
- Read-only tools mặc định; write/high-risk tools cần explicit gate/approval.
- Agent conclusion phải gắn evidence: screenshot, DOM state, network log, test output.
- Structured output được validate trước khi workflow tiếp tục.
- Có evaluation và regression tests cho agent, không chỉ manual demo.

### Điểm cộng

- Context budget rõ ràng: repository instructions, relevant files, ticket, environment constraints, prior step outputs.
- Không đưa toàn repo hoặc secrets vào context nếu không cần.
- Tool wrappers enforce allowlist, environment scope và input validation.
- Human approval trước irreversible/high-impact action.
- Run ID và trace cho toàn workflow.
- Fallback sang deterministic scripted test hoặc human review nếu confidence/evidence không đủ.

### Nâng cao

- Phân biệt model confidence với measured reliability; không dùng self-reported confidence làm security control.
- Eval dataset gồm happy path, ambiguous requirement, flaky UI, permission denial, tool failure và prompt injection trong page content.
- Sandbox browser identity và test account riêng.
- Prompt injection từ webpage/repository content được coi là untrusted input; tool policy không được thay đổi chỉ vì model đọc thấy instruction trong content.
- Cost/latency budgets và step limits để tránh runaway loops.

## Hướng giải quyết tham khảo

Tôi chia workflow thành các stage có state rõ ràng:

```text
Requirement/Ticket
    ↓
Deterministic pre-validation
    ↓
LLM test planning
    ↓
Policy validation
    ↓
Browser execution (scoped tools)
    ↓
Evidence collection
    ↓
Deterministic assertions + LLM analysis
    ↓
Result validation
    ↓
Human approval nếu có write/high-risk action
    ↓
Report / suggested patch
```

**LLM phù hợp cho:** diễn giải requirement mơ hồ, sinh candidate test scenarios, phân tích multi-signal failure, đề xuất root-cause hypotheses, viết report.

**Deterministic nên giữ:** schema validation, permission checks, environment allowlist, test data boundaries, explicit assertions, secret redaction, approval gates và việc quyết định có được gọi high-risk tool hay không.

### Tool policy

Tôi phân loại tools:

- **Low risk:** đọc file được allowlist, đọc test artifact, browser navigation trên QA.
- **Medium risk:** tạo test data trong isolated QA tenant, ghi artifact.
- **High risk:** gửi email thật, sửa production data, merge PR, thay secret, thay CI settings.

High-risk tools mặc định không expose cho agent, hoặc yêu cầu explicit human approval. MCP/tool metadata không được coi là đủ để bảo đảm an toàn; host/tool wrapper phải enforce policy.

### Output contract

Agent trả structured result:

```json
{
  "status": "pass|fail|blocked|inconclusive",
  "evidence": [],
  "failedAssertions": [],
  "hypotheses": [],
  "recommendedNextActions": [],
  "requiresHumanApproval": false
}
```

Workflow validate schema và kiểm tra mỗi conclusion quan trọng phải có evidence tương ứng. Nếu evidence thiếu, trạng thái là `inconclusive` thay vì cho model tự “đoán”.

### Hallucination prevention

- Ground answer vào artifacts/tool outputs.
- Không cho model invent test result khi tool chưa chạy.
- Tool output có IDs/timestamps để trace.
- Deterministic validator kiểm tra evidence existence.
- Prompt injection từ page content không được phép thay đổi policy.

### Evaluation

Duy trì gold dataset gồm các case known-pass/known-fail, ambiguous requirements, flaky UI, auth failure, network timeout và adversarial content. Đo precision/recall hoặc pass/fail agreement theo use case, false positives, false negatives, tool error recovery, latency và cost.

### Fallback

Nếu agent không đủ evidence, tool bị deny hoặc workflow vượt step budget, chuyển sang `blocked/inconclusive` và tạo report cho engineer thay vì tự mở rộng quyền.

### Audit/monitoring

Theo dõi run ID, model/version, prompt/instruction version, tools called, parameters đã redacted, approvals, artifacts, token/cost, step count, failure reason và final result.

**Điều kiện làm thay đổi recommendation:** internal read-only research agent có thể ít approval gates hơn; agent có quyền thay production data phải có policy chặt hơn nhiều và thường không nên được autonomous.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế QA agent như một prompt lớn có quyền làm mọi thứ. Tôi chia workflow thành các stage có state và policy rõ ràng.

LLM hữu ích ở chỗ hiểu requirement, lập candidate test plan và phân tích failure. Nhưng permission checks, schema validation, explicit assertions và approval gates phải deterministic. Tool access theo least privilege; browser chỉ được QA environment, read-only repo tools mặc định, còn những action như merge code, gửi email thật hoặc sửa production data thì không expose hoặc bắt buộc human approval.

Mỗi kết luận của agent cần evidence như screenshot, DOM state, request log hoặc test output. Output dùng schema cố định và validator kiểm tra evidence tồn tại. Nếu thiếu evidence thì kết quả là inconclusive chứ không đoán.

Tôi cũng coi page content và repository text là untrusted vì có thể chứa prompt injection; chúng không được phép thay đổi tool policy. Cuối cùng, tôi xây eval dataset gồm known failures, flaky cases, permission denial và adversarial content, rồi theo dõi false positive/negative, latency, cost và tool recovery. Khi workflow không chắc chắn, fallback là human review chứ không mở rộng quyền cho model.”

## Câu hỏi đào sâu

1. Bạn đánh giá chất lượng agent thế nào nếu cùng một bug có nhiều cách diễn đạt requirement khác nhau?
2. Làm sao chống prompt injection từ nội dung webpage mà agent đang test?
3. **Thách thức:** Product owner yêu cầu agent tự merge test-only PR để tiết kiệm thời gian — bạn có cho phép không, và nếu có thì boundary nào bắt buộc?

- Không có evaluation dataset/regression suite cho agent.
- Đưa toàn repo, secrets hoặc production data vào context không cần thiết.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- `IQueryable` và deferred execution chỉ trì hoãn query; khi materialize dataset lớn, memory cost vẫn là thật.
- Read-only EF Core flow nên cân nhắc projection, no-tracking và batching/streaming dựa trên volume thực tế.
- Background jobs nên được thiết kế theo **at-least-once execution + idempotent business effect**, không dựa vào giả định exactly-once.
- Retry phải đi cùng idempotency, state transition, failure classification và observability.
- AI agent cần tách rõ probabilistic reasoning khỏi deterministic control và validation.
- Tool permissions, approval gates và audit trail là một phần của architecture, không phải chỉ là prompt engineering.

## Mẫu tư duy cần nhớ

1. **Clarify before designing** — hỏi volume, failure semantics và business guarantees trước khi chọn pattern.
2. **Measure before optimizing** — tách DB time, materialization time, external dependency time và application overhead.
3. **Design retries together with idempotency** — retry không thể tách khỏi duplicate side effects.
4. **Make state explicit** — workflow quan trọng cần operation state/correlation thay vì suy luận từ log rời rạc.
5. **Validate AI output deterministically** — model đề xuất, hệ thống xác minh và policy quyết định quyền hành động.
