# Câu 1 — EF Core tracking, identity resolution và truy vấn đọc bị chậm dưới tải

**Loại câu hỏi:** Internal mechanism trong tình huống production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** EF Core query pipeline, change tracking, memory allocation, SQL verification, performance diagnosis

## Bối cảnh

Một ASP.NET Core API trả danh sách 2.000–5.000 bản ghi lịch sử sự kiện. Endpoint chỉ đọc dữ liệu nhưng sử dụng `Include`, projection một phần ở phía application và `ToListAsync()`. Sau khi traffic tăng, p95 latency tăng mạnh, CPU và memory của application tăng, GC hoạt động thường xuyên hơn. SQL Server/PostgreSQL không cho thấy CPU tương ứng tăng cao. Một developer đề xuất thêm `AsNoTracking()` và nói rằng “EF Core sẽ không tạo object nữa nên memory sẽ giảm gần như về mức raw SQL”.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra từ lúc LINQ query được xây dựng đến khi kết quả được materialize; vì sao tracking có thể làm endpoint đọc tốn CPU/memory; nhận định trên sai ở đâu; rủi ro production là gì; và bạn sẽ chứng minh nguyên nhân bằng evidence nào trước khi tối ưu?

## Câu hỏi làm rõ nên cân nhắc

- Endpoint có cần cập nhật các entity vừa đọc hay hoàn toàn read-only?
- Query thực tế sinh ra SQL nào và trả bao nhiêu row/column?
- Có cartesian expansion do `Include` collection không?
- Latency nằm ở DB, network, materialization hay serialization?
- Allocation/GC thay đổi thế nào theo số lượng bản ghi?

## Gợi ý tư duy

- **Gợi ý 1:** Tách chi phí database execution khỏi chi phí phía .NET.
- **Gợi ý 2:** Xem xét query translation, materialization, ChangeTracker, identity resolution, serialization và số object được cấp phát.
- **Gợi ý 3:** `AsNoTracking()` bỏ tracking overhead nhưng không loại bỏ việc materialize object; projection và shape của SQL thường quan trọng không kém.

## Cấu trúc trả lời đề xuất

1. Làm rõ read/write semantics và query shape.
2. Mô tả deferred execution và thời điểm query thực thi.
3. Giải thích materialization/tracking.
4. Tách DB time khỏi application time.
5. Đưa ra các hypothesis.
6. Đo trước khi thay đổi.
7. Tối ưu query shape/tracking/pagination.
8. Load test và quan sát sau fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- LINQ query chưa thực thi chỉ vì được khai báo; terminal async operation mới kích hoạt execution.
- EF Core dịch phần query có thể dịch sang SQL, database trả dữ liệu rồi EF materialize kết quả.
- Tracking query tạo/duy trì state cần thiết cho ChangeTracker; read-only query có thể tránh overhead này bằng no-tracking.
- `AsNoTracking()` không có nghĩa là không tạo object.
- Phải xem generated SQL, row count, payload và application allocations trước khi kết luận.

### Điểm cộng

- Phân biệt `AsNoTracking()` với `AsNoTrackingWithIdentityResolution()`.
- Nhận ra `Include` nhiều collection có thể làm result set phình lớn; cân nhắc projection hoặc split query tùy trường hợp.
- Pagination/bounded result thường quan trọng hơn micro-optimization.

### Nâng cao

- Dùng tracing để phân tách DB duration, materialization/application duration và response serialization.
- So sánh allocation profile bằng `dotnet-counters`, `dotnet-trace`/profiler phù hợp và benchmark/load test có dataset production-like.
- Xem compiled queries chỉ sau khi chứng minh query compilation là bottleneck đáng kể.

## Hướng giải quyết tham khảo

**Giả định:** endpoint read-only và không cần entity graph đầy đủ. Query LINQ là biểu thức cho đến khi được enumerate/terminal operation thực thi. Khi `ToListAsync()` chạy, EF Core tạo/thực thi database command, đọc result set và materialize kết quả. Với tracking query, entity được gắn với DbContext/ChangeTracker; điều này hữu ích khi cần update nhưng tạo thêm CPU/memory overhead cho read-heavy workloads.

Tuy nhiên, no-tracking vẫn phải đọc dữ liệu và tạo entity/DTO. Nếu SQL trả hàng chục nghìn row vì join expansion, hoặc endpoint serialize object graph lớn, chỉ thêm `AsNoTracking()` không giải quyết gốc vấn đề.

Thứ tự điều tra nên là: capture trace → xem generated SQL/query plan → đo DB duration và rows returned → đo allocations/GC → kiểm tra serialization → chạy controlled load test. Với endpoint read-only, ưu tiên projection trực tiếp sang DTO, chỉ chọn cột cần thiết, `AsNoTracking()`, pagination có giới hạn và tránh graph quá lớn. Nếu cần tránh duplicate instances nhưng không muốn context tracking lâu dài, đánh giá identity-resolution no-tracking dựa trên workload thực tế.

Failure cases cần xét gồm query timeout, client cancellation, dataset tăng, plan regression và response quá lớn. Monitor p50/p95/p99, DB command duration, rows returned, allocation rate, GC pause, response size và error/timeout rate.

Khuyến nghị sẽ thay đổi nếu entity cần được sửa trong cùng unit of work, hoặc profiling chứng minh bottleneck nằm hoàn toàn ở DB/index/network thay vì tracking/materialization.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ chưa thêm `AsNoTracking()` ngay mà trước tiên xác định thời gian đang mất ở đâu. LINQ query của EF Core chủ yếu mô tả query; đến `ToListAsync()` mới thực thi. Database trả result set và EF vẫn phải materialize entity hoặc DTO. Tracking làm thêm công việc để DbContext quản lý entity state, nên với endpoint read-only nó có thể tạo overhead đáng kể, nhưng `AsNoTracking()` không loại bỏ allocation của kết quả. Tôi sẽ capture generated SQL và execution plan, đo rows/bytes returned, DB duration, allocations, GC và serialization. Nếu query đang `Include` graph lớn, tôi ưu tiên projection đúng DTO, chỉ lấy cột cần, pagination và no-tracking. Sau đó load test cùng dataset tương tự production và so p95, allocation rate, GC và DB metrics. Nếu profiling cho thấy bottleneck thực ra là query plan hoặc response serialization thì tôi sẽ xử lý phần đó thay vì tối ưu ChangeTracker.”

## Câu hỏi đào sâu

1. Khi nào `AsNoTrackingWithIdentityResolution()` có thể đáng dùng hơn `AsNoTracking()`?
2. Nếu thêm `AsNoTracking()` chỉ cải thiện 5% nhưng projection cải thiện 50%, bạn giải thích kết quả thế nào?
3. **Thách thức:** Nếu endpoint sau đó cần sửa một entity đã đọc, bạn có còn áp dụng no-tracking mặc định không?

## Lỗi trả lời thường gặp

- Cho rằng `AsNoTracking()` không materialize object.
- Chỉ nhìn DB CPU mà bỏ qua allocation/serialization phía application.
- Thêm index mà chưa xem SQL/query plan.
- Tải toàn bộ dữ liệu rồi filter/project trong memory.
- Không đặt giới hạn kích thước response.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1.0

# Câu 2 — Incident: Hangfire xử lý tác vụ offboarding hai lần

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** incident response, background jobs, idempotency, distributed concurrency, external API failure handling, observability

## Bối cảnh

Một background job xử lý thay đổi mailbox và dữ liệu nội bộ. Job đọc các record `Pending`, gọi external API, sau đó cập nhật database thành `Completed`. Sau deployment mới, một số người dùng nhận thấy cùng thao tác được thực hiện hai lần. Dashboard cho thấy có job retry và đôi lúc hai worker xử lý gần cùng thời điểm. External API có thể thành công nhưng client nhận timeout trước khi thấy response. Không được phép mất tác vụ, nhưng duplicate side effect cũng có thể gây ảnh hưởng nghiệp vụ.

## Câu hỏi chính

Bạn sẽ xử lý incident này từ phút đầu tiên đến khi có long-term fix như thế nào, khi chưa biết duplicate đến từ retry, concurrent execution, deployment hay timeout sau successful side effect?

## Câu hỏi làm rõ nên cân nhắc

- Side effect nào có thể đảo ngược và side effect nào không?
- Có correlation/idempotency key xuyên suốt DB, job và external request không?
- Hangfire storage và số worker/server đang chạy thế nào?
- Trạng thái được commit trước hay sau external call?
- External API có hỗ trợ idempotency hoặc đọc lại trạng thái hiện tại không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách “job chạy nhiều lần” khỏi “business effect xảy ra nhiều lần”.
- **Gợi ý 2:** Retry và timeout khiến exactly-once end-to-end rất khó; thiết kế handler để repeated delivery an toàn.
- **Gợi ý 3:** Kết hợp durable state, idempotency, concurrency control và reconciliation thay vì chỉ khóa worker.

## Cấu trúc trả lời đề xuất

1. Đánh giá blast radius.
2. Giảm thiểu side effect nguy hiểm.
3. Thu thập evidence/correlation.
4. Lập nhiều hypothesis.
5. Reproduce và xác định failure window.
6. Short-term guard.
7. Durable idempotency/reconciliation design.
8. Verification và alerting.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định retry là root cause duy nhất.
- Xác định ambiguous outcome: external call thành công nhưng caller timeout.
- Business operation cần idempotent hoặc có deduplication durable.
- Không dựa vào in-memory lock trong multi-instance deployment.
- Có audit/correlation để reconstruct từng attempt.

### Điểm cộng

- Unique constraint/idempotency record hoặc state transition có concurrency protection.
- Phân biệt transport/job retry với business command identity.
- Reconciliation job kiểm tra trạng thái external system trước khi retry side effect không an toàn.

### Nâng cao

- Thiết kế state machine như Pending → Processing → ExternalApplied → Completed/NeedsReconciliation với recovery rõ ràng.
- Transactional outbox khi cần đảm bảo DB state và việc phát command/event không rơi vào dual-write gap.
- Alert dựa trên duplicate business operation, retry storm, stuck processing và reconciliation backlog.

## Hướng giải quyết tham khảo

Đầu tiên xác định phạm vi: operation nào bị duplicate, từ version/deployment nào, bao nhiêu user và side effect nào nguy hiểm. Nếu cần, tạm giảm concurrency hoặc dừng riêng loại job gây side effect trong khi vẫn giữ queue, thay vì xóa job.

Thu thập `BusinessOperationId`, Hangfire job ID/attempt, worker/server, DB state transition, external request correlation, timestamps và deployment version. Hypothesis gồm concurrent workers, automatic retry, enqueue duplicate, timeout sau external success, race ở `Pending` check, hoặc deployment chạy song song version cũ/mới.

Long-term, mỗi business command có stable idempotency key. Database phải enforce trạng thái/deduplication bằng primitive durable như unique constraint và atomic/optimistic state transition. Handler phải giả định có thể được gọi lại. Nếu external API hỗ trợ idempotency key, truyền cùng key cho mọi retry. Nếu không, trước khi lặp side effect sau ambiguous timeout cần query/reconcile external state nếu API cho phép.

Không hứa exactly-once chỉ bằng Hangfire configuration. Mục tiêu thực tế là at-least-once execution + idempotent business effect/reconciliation. Với dual write giữa DB và enqueue, cân nhắc outbox nếu consistency requirement biện minh complexity.

Test bằng concurrent execution cùng operation ID, timeout sau server-side success, process crash tại từng state transition, retry sau restart và deployment nhiều worker. Monitor retries, duplicate-key conflicts, state age, external timeout rate và reconciliation backlog.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ coi đây là incident về business idempotency chứ chưa kết luận Hangfire bị lỗi. Trước hết tôi xác định blast radius và nếu duplicate side effect nguy hiểm thì giảm hoặc tạm dừng riêng consumer đó nhưng không làm mất queue. Sau đó tôi correlate business operation ID với job attempt, worker, DB transition và external request. Tôi đặc biệt kiểm tra trường hợp external API đã xử lý thành công nhưng client timeout, vì retry lúc đó có thể lặp side effect. Long-term, mỗi operation cần stable idempotency key và durable dedup/state transition ở database; in-memory lock không đủ khi có nhiều instance. Nếu external API hỗ trợ idempotency thì reuse cùng key; nếu không thì cần reconciliation/read-before-retry cho ambiguous outcome. Tôi sẽ fault-injection ở các điểm trước/sau external call và DB commit, rồi theo dõi duplicate operations, retries, stuck states và reconciliation backlog.”

## Câu hỏi đào sâu

1. Vì sao distributed lock vẫn không tự động bảo đảm exactly-once business effect?
2. Bạn xử lý thế nào nếu external API không có idempotency key và cũng không có endpoint tra trạng thái?
3. **Thách thức:** Outbox có giải quyết được timeout xảy ra sau khi external API đã thành công không?

## Lỗi trả lời thường gặp

- Chỉ tắt retry và coi vấn đề đã xong.
- Dùng static `lock`/`SemaphoreSlim` cho hệ thống nhiều instance.
- Không phân biệt job ID và business operation ID.
- Đánh dấu `Completed` trước external call mà không thiết kế recovery.
- Không test process crash/ambiguous timeout.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0

# Câu 3 — Thiết kế AI code-review agent có quyền truy cập repository nhưng không được tự ý sửa production

**Loại câu hỏi:** AI engineering / system decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, deterministic validation, evaluation, security, auditability

## Bối cảnh

Nhóm muốn xây một AI agent review pull request cho repository .NET. Agent được phép đọc diff, source liên quan, test và coding rules; có thể chạy build/test trong sandbox và đề xuất patch. Mục tiêu là phát hiện correctness, security, performance và maintainability issues trước human review. Nhóm muốn giảm review time nhưng không chấp nhận agent merge code, truy cập production secrets hoặc thực thi command tùy ý trên infrastructure nội bộ. PR có thể chứa text cố tình hướng dẫn agent bỏ qua policy.

## Câu hỏi chính

Bạn sẽ thiết kế agent này như thế nào để AI thực sự tạo giá trị nhưng quyền hạn, context, validation, hallucination detection, evaluation, fallback và audit đều có boundary rõ ràng?

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ comment hay được tạo commit/patch branch?
- Repository có dữ liệu/secrets hoặc generated files cần loại khỏi context không?
- SLA/cost budget cho mỗi PR là bao nhiêu?
- Những finding nào được phép auto-post và finding nào cần human approval?
- Có historical review data để xây evaluation set không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách reasoning không đáng tin cậy khỏi enforcement deterministic.
- **Gợi ý 2:** Least privilege cho tools, untrusted repository content, structured findings và evidence binding.
- **Gợi ý 3:** Đánh giá agent bằng task-level outcomes/false-positive rate và sandbox mọi execution; human giữ quyền write/merge nhạy cảm.

## Cấu trúc trả lời đề xuất

1. Làm rõ mục tiêu và threat model.
2. Xác định phần cần AI và phần deterministic.
3. Thiết kế context pipeline.
4. Thiết kế tool/permission boundaries.
5. Structured output + evidence validation.
6. Human approval/fallback.
7. Evaluation strategy.
8. Audit, cost, latency và monitoring.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI phù hợp để reasoning trên diff/context nhưng policy enforcement phải deterministic khi có thể.
- Repository/PR content là untrusted input; không cho nó thay đổi system/tool policy.
- Tool permissions theo least privilege; không production credentials.
- Build/test chạy trong isolated environment với giới hạn network/resource.
- Finding phải có file/line/evidence và validation trước khi publish.
- Human giữ quyền merge hoặc sensitive write.

### Điểm cộng

- Context retrieval theo diff/dependency/call-site thay vì nhét toàn repository.
- JSON/schema output và deterministic checks rằng cited file/line tồn tại.
- Confidence/risk threshold khác nhau cho comment tự động và human-review queue.
- Eval set chứa true issues, clean PRs và adversarial prompt-injection cases.

### Nâng cao

- Version hóa prompt/rules/model/tool policy để audit regression.
- Canary/shadow mode trước khi bật auto-comment.
- Metrics: precision, recall trên labeled set, false-positive burden, accepted findings, latency, token/tool cost, unsafe tool attempts.
- Permission broker/tool gateway thay vì model giữ credential trực tiếp.

## Hướng giải quyết tham khảo

AI chỉ nên đảm nhiệm phần cần semantic reasoning: hiểu diff, tìm call-site liên quan, tạo hypothesis và giải thích finding. Deterministic components chịu trách nhiệm fetch đúng PR/diff, permission checks, schema validation, file/line existence, build/test/static analysis và publish policy.

Context pipeline bắt đầu từ PR metadata + diff, sau đó retrieval có giới hạn tới symbol/call-site/test/config liên quan. Secrets, binaries và irrelevant generated content bị loại. Nội dung repository được đánh dấu là untrusted data, không phải instruction authority.

Tool gateway expose allow-listed operations như read file, search code, run predefined build/test command trong sandbox. Không cấp shell unrestricted, production secret hoặc merge permission. Patch nếu có chỉ được tạo ở isolated workspace/branch và cần human approval trước write nhạy cảm.

Output dùng structured schema gồm category, severity, file, line/range, evidence, reasoning, suggested fix và confidence. Deterministic validator kiểm tra reference tồn tại; build/test/static analyzer kiểm tra patch khi khả thi. Hallucination không thể loại bỏ hoàn toàn, nên quality được quản lý bằng evidence requirement, threshold, fallback và eval.

Evaluation cần golden/adversarial dataset, clean PRs để đo false positives, known-bug PRs để đo detection, prompt-injection tests và regression theo version. Bắt đầu shadow mode; chỉ auto-comment finding vượt threshold sau khi precision đủ tốt cho team. Audit log ghi model/prompt/rules/tool calls/context IDs/output/approval mà không log secrets.

Recommendation thay đổi nếu agent chỉ chạy local cho developer, hoặc organization chấp nhận quyền tạo branch tự động sau khi permission/evaluation maturity cao hơn.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không thiết kế agent như một developer có toàn quyền. AI chỉ xử lý phần semantic như hiểu diff, tìm rủi ro và đề xuất fix; enforcement, permission và validation phải deterministic. PR và repository content được coi là untrusted nên text trong code không thể cấp thêm quyền cho model. Agent chỉ có allow-listed read/search tools và build/test trong sandbox không có production secrets hay unrestricted network. Context bắt đầu từ diff rồi retrieve symbol, call-site và test liên quan thay vì gửi toàn repo. Finding phải theo schema, có file/line/evidence và validator kiểm tra reference trước khi publish. Merge luôn cần human approval. Tôi sẽ chạy shadow mode với labeled PRs, clean PRs và adversarial injection cases, đo precision, false-positive burden, accepted findings, latency và cost. Mọi prompt/rules/tool policy và tool call đều versioned/audited để khi quality regression có thể truy nguyên và rollback.”

## Câu hỏi đào sâu

1. Làm sao phân biệt instruction hợp lệ của repository với prompt injection nằm trong source/comment?
2. Nếu agent có precision cao nhưng recall thấp, bạn có cho phép auto-comment không?
3. **Thách thức:** Nếu build/test sandbox cần tải NuGet package từ Internet, bạn giữ isolation và supply-chain security như thế nào?

## Lỗi trả lời thường gặp

- “Cho LLM đọc toàn repo và review” mà không có context strategy.
- Cho model shell/write/merge permission quá rộng.
- Tin rằng prompt nói “ignore injection” là đủ security boundary.
- Đo chất lượng chỉ bằng cảm nhận hoặc số comment tạo ra.
- Không có deterministic evidence validation và audit trail.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.0
- Depth: 2.0
- Trade-off analysis: 1.5
- Production readiness: 2.0
- Communication: 1.0

# Tổng kết hôm nay

## Kiến thức trọng tâm

- EF Core no-tracking giảm tracking overhead nhưng không loại bỏ materialization; query shape, result size và serialization phải được đo cùng nhau.
- Background job phải được thiết kế với retry/failure semantics thực tế; idempotency là thuộc tính của business operation, không chỉ của job runner.
- Timeout có thể tạo ambiguous outcome, vì vậy recovery cần reconciliation thay vì retry mù.
- AI agent cần phân tách probabilistic reasoning khỏi deterministic policy/validation và áp dụng least privilege cho tools.
- Observability và evaluation là một phần của thiết kế, không phải công việc thêm sau khi production gặp lỗi.

## Mẫu tư duy cần nhớ

- Clarify và đo trước khi tối ưu.
- Tách database time, application time và serialization time.
- Thiết kế retry cùng idempotency và reconciliation.
- Treat external success + local timeout as an ambiguous outcome.
- Validate AI output deterministically và coi mọi external/repository content là untrusted.
