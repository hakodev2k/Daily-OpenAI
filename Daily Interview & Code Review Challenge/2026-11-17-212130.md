# Code Review Challenge 1 — Export báo cáo trên IIS làm nghẽn request và rò dữ liệu

**Chủ đề:** C#/.NET Framework 4.5, ASP.NET MVC, IIS, Windows Server, file export, security, modernization  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 40 phút  
**Số vấn đề cần tìm:** khoảng 9

## Bối cảnh

Một hệ thống nội bộ ASP.NET MVC chạy trên IIS/Windows Server cho phép nhân viên tải CSV lịch sử lương của phòng ban. Dữ liệu từ SQL Server; một lần export có thể từ 200 đến 300.000 dòng. Sau khi mở tính năng cho nhiều chi nhánh, CPU tăng, ổ đĩa máy web đầy và có báo cáo người dùng tải nhầm dữ liệu. Đội vận hành chưa có quyền thay toàn bộ ứng dụng; yêu cầu sửa an toàn trên .NET Framework trước, sau đó mới cân nhắc migration. Mỗi request đã được authentication nhưng quyền truy cập phòng ban phải kiểm tra riêng.

## Đoạn code cần review

```csharp
[Authorize]
public class PayrollController : Controller
{
    private readonly PayrollDbContext _db = new PayrollDbContext();

    [HttpGet]
    public ActionResult Export(int departmentId, string fileName)
    {
        var rows = _db.Payrolls
            .Where(x => x.DepartmentId == departmentId)
            .ToList();

        var csv = new StringBuilder();
        csv.AppendLine("Employee,Amount,Note");
        foreach (var row in rows)
        {
            csv.AppendLine(row.EmployeeName + "," +
                           row.Amount + "," + row.Note);
        }

        var name = string.IsNullOrEmpty(fileName)
            ? "payroll.csv" : fileName;
        var target = Path.Combine(Server.MapPath("~/exports"), name);
        System.IO.File.WriteAllText(target, csv.ToString());

        Response.AddHeader("Cache-Control", "public,max-age=3600");
        return File(target, "text/csv", name);
    }

    protected override void Dispose(bool disposing)
    {
        if (disposing) _db.Dispose();
        base.Dispose(disposing);
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Broken object-level authorization

**Vấn đề:** `[Authorize]` chỉ yêu cầu đăng nhập, không xác nhận người dùng được xem `departmentId`.  
**Tại sao xảy ra:** API tin ID do client truyền.  
**Ảnh hưởng production:** Lộ dữ liệu lương giữa các phòng ban.  
**Cách sửa:** Kiểm tra quyền từ nguồn server-side theo user và department trước khi truy vấn; áp dụng data-scope vào query; ghi audit.

### [High] — Đường dẫn file do client kiểm soát

**Vấn đề:** `fileName` đi thẳng vào `Path.Combine`; có nguy cơ path traversal hoặc ghi đè file tùy môi trường và cách chuẩn hóa path.  
**Tại sao xảy ra:** Không giới hạn basename và đích lưu.  
**Ảnh hưởng production:** Ghi đè dữ liệu, tiết lộ file, gây gián đoạn.  
**Cách sửa:** Không dùng input làm path; tốt nhất loại bỏ ghi file. Download name do server quyết định.

### [High] — CSV injection và CSV escaping sai

**Vấn đề:** Giá trị chứa dấu phẩy, dấu nháy hoặc xuống dòng làm sai cột; giá trị bắt đầu bằng ký tự công thức có thể bị spreadsheet diễn giải.  
**Tại sao xảy ra:** Ghép chuỗi trực tiếp, không encode CSV và không có chính sách xử lý spreadsheet formulas.  
**Ảnh hưởng production:** Sai báo cáo, có thể gây hành vi nguy hiểm khi người dùng mở file.  
**Cách sửa:** CSV escaping chuẩn; áp dụng chính sách neutralize formula cho các trường text khi file dành cho spreadsheet, đồng thời kiểm thử với Excel và công cụ downstream.

### [High] — Materialize toàn bộ dữ liệu và tạo bản sao lớn

**Vấn đề:** `ToList()`, `StringBuilder` và `ToString()` giữ nhiều bản dữ liệu.  
**Tại sao xảy ra:** Không giới hạn số dòng, không streaming.  
**Ảnh hưởng production:** LOH/GC pressure, memory spike, worker process recycle.  
**Cách sửa:** Projection, `AsNoTracking`, giới hạn phạm vi và xuất tuần tự từng dòng; với export rất lớn chuyển sang job có quota và lưu file riêng.

### [High] — File tạm public, không dọn dẹp và có thể đụng tên

**Vấn đề:** File nằm trong web root, có tên lặp lại, không cleanup.  
**Tại sao xảy ra:** Gắn request export với local disk.  
**Ảnh hưởng production:** Download không qua authorization tùy cấu hình IIS, overwrite giữa request, disk full, lỗi trên nhiều instances.  
**Cách sửa:** Trả response trực tiếp hoặc lưu private storage với authorization và TTL; không đặt file nhạy cảm trong thư mục public.

### [Medium] — HTTP cache policy không phù hợp

**Vấn đề:** `public,max-age=3600` trên dữ liệu lương.  
**Tại sao xảy ra:** Dùng chính sách cache của static assets cho response cá nhân.  
**Ảnh hưởng production:** Proxy/shared cache có thể lưu dữ liệu nhạy cảm.  
**Cách sửa:** `Cache-Control: private, no-store`, kiểm tra chính sách cache tại proxy/CDN.

### [Medium] — Blocking request và thiếu cancellation/quota

**Vấn đề:** Query đồng bộ và ghi đĩa trong request; không có giới hạn concurrent exports.  
**Tại sao xảy ra:** Thiết kế synchronous, không backpressure.  
**Ảnh hưởng production:** Request latency tăng, thread bị chiếm, timeout và tác động endpoint khác.  
**Cách sửa:** Giới hạn export, timeout hợp lý, rate/concurrency limit; cân nhắc background job cho khối lượng lớn. Async I/O không tự giải quyết CPU và dung lượng.

### [Medium] — Không có snapshot consistency và ordering

**Vấn đề:** Dữ liệu thay đổi trong quá trình export có thể khiến phân trang thiếu/trùng; bản hiện tại cũng không xác định thứ tự.  
**Tại sao xảy ra:** Không có yêu cầu consistency hoặc sort ổn định.  
**Ảnh hưởng production:** Báo cáo khó đối soát.  
**Cách sửa:** Xác nhận yêu cầu thời điểm chốt dữ liệu; dùng stable ordering và cơ chế snapshot/transaction phù hợp khi cần.

### [Low] — Thiếu audit và metrics

**Vấn đề:** Không theo dõi actor, scope, row count, duration, failures.  
**Tại sao xảy ra:** Export được coi là action tải file thông thường.  
**Ảnh hưởng production:** Khó điều tra truy cập trái phép và suy giảm hiệu năng.  
**Cách sửa:** Audit không chứa giá trị lương; metrics về số dòng, duration, lỗi và throttling.

## Phiên bản đề xuất

Bản phác thảo tương thích hướng ASP.NET MVC/.NET Framework; `IAuthorizationService` và `IPayrollExportReader` là abstraction của ứng dụng cần triển khai. Reader phải áp dụng scope, projection, stable ordering và giới hạn dòng tại SQL; không dùng toàn bộ entity trong RAM. Ví dụ bên dưới chọn **hard limit 10.000 dòng** và buffer bounded; nếu business yêu cầu 300.000 dòng, chuyển sang export job private storage, không đơn giản tăng giới hạn.

```csharp
[Authorize]
public sealed class PayrollController : Controller
{
    private readonly IAuthorizationService _access;
    private readonly IPayrollExportReader _reader;

    public PayrollController(
        IAuthorizationService access,
        IPayrollExportReader reader)
    {
        _access = access;
        _reader = reader;
    }

    [HttpGet]
    public ActionResult Export(int departmentId)
    {
        var actor = User.Identity.Name;
        if (!_access.CanExportPayroll(actor, departmentId))
            return new HttpStatusCodeResult(403);

        // Reader enforces a server-side row cap and department scope.
        var rows = _reader.ReadBounded(actor, departmentId, 10000);
        var output = new StringBuilder("Employee,Amount,Note\r\n");
        foreach (var row in rows)
        {
            output.Append(CsvCell(row.EmployeeName)).Append(',')
                  .Append(row.Amount.ToString(
                      System.Globalization.CultureInfo.InvariantCulture))
                  .Append(',')
                  .Append(CsvCell(row.Note)).Append("\r\n");
        }

        Response.Cache.SetCacheability(HttpCacheability.Private);
        Response.Cache.SetNoStore();
        Response.Headers["X-Content-Type-Options"] = "nosniff";
        var bytes = new UTF8Encoding(true).GetBytes(output.ToString());
        return File(bytes, "text/csv", "payroll-export.csv");
    }

    private static string CsvCell(string value)
    {
        value = value ?? "";
        // Spreadsheet-facing export policy; validate with target clients.
        var trimmed = value.TrimStart();
        if (trimmed.StartsWith("=") || trimmed.StartsWith("+") ||
            trimmed.StartsWith("-") || trimmed.StartsWith("@"))
            value = "'" + value;
        return "\"" + value.Replace("\"", "\"\"") + "\"";
    }
}
```

**Giới hạn của bản sửa:** Đây là bản mitigation bounded, chưa phải streaming thực sự; cần đặt giới hạn byte, row length và concurrency để tránh memory spike. `ReadBounded` phải phát hiện vượt limit và trả lỗi có chủ đích, không âm thầm cắt báo cáo. Với file lớn, dùng streaming response được kiểm soát hoặc asynchronous export job, private Blob Storage và link có thời hạn; triển khai trên .NET Framework cần kiểm thử behavior của IIS buffering, disconnect và client cancellation.

## Giải thích thiết kế sau khi sửa

Authorization được kiểm tra trước query và tiếp tục ràng buộc ở data-access layer. File name không do người dùng quyết định. Bản vá giữ thay đổi nhỏ để giảm rủi ro release trên legacy stack; việc chuyển sang background export cần thiết kế riêng về trạng thái job, authorization khi download, expiry và retry.

## Trade-offs

Hard cap giúp giảm rủi ro ngay nhưng từ chối export lớn. Streaming tiết kiệm RAM song làm request dài và khó rollback response khi lỗi giữa chừng. Background job tăng độ bền nhưng thêm queue/storage, cleanup, quyền truy cập và observability. Không cần migration toàn bộ ứng dụng chỉ để sửa endpoint này.

## Cách kiểm thử

1. **Security integration:** User phòng A thử export phòng B; assert 403 và không có SQL trả dữ liệu phòng B.
2. **CSV regression:** Dữ liệu chứa dấu phẩy, quote, newline, công thức và Unicode; xác minh parse round-trip và spreadsheet safety.
3. **Load test:** 20 concurrent exports sát giới hạn; đo memory, CPU, request latency và rejection rate.
4. **Failure-path:** Client disconnect, IIS recycle, DB timeout; kiểm tra không có file public hoặc dữ liệu lưu sót.
5. **Database test:** Kiểm tra stable ordering, server-side limit, execution plan và tính đầy đủ của report.

## Quan sát trong production

Ghi structured audit: actor ID, department ID, authorization decision, row count, duration, correlation ID; không log tên nhân viên hoặc số tiền. Theo dõi IIS worker memory/private bytes, GC, disk usage, SQL duration, export concurrency, HTTP 403/429/5xx và p95/p99. Alert khi có spike của export hoặc disk utilization. Với migration, so sánh telemetry trước/sau canary.

# Code Review Challenge 2 — Vue search hiển thị kết quả sai và ghi đè state khi đổi bộ lọc

## Bối cảnh

Portal tìm kiếm tài liệu nội bộ dùng Vue 3, TypeScript và ASP.NET Core search API. Người dùng gõ nhanh từ khóa và đổi project filter liên tục. API trả về kết quả theo quyền hiện tại; thời gian response dao động 100 ms đến 3 giây. Production ghi nhận danh sách đôi lúc thuộc bộ lọc cũ, spinner tắt khi request vẫn chạy, và người dùng thấy lỗi không rõ nguyên nhân. Không giả định API tự loại bỏ request trùng.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type SearchItem = { id: string; title: string; summary: string }
const query = ref('')
const projectId = ref('all')
const items = ref<SearchItem[]>([])
const loading = ref(false)
const error = ref('')
const total = ref(0)

async function search() {
  loading.value = true
  error.value = ''
  const url = '/api/search?q=' + query.value +
              '&project=' + projectId.value
  try {
    const response = await fetch(url, {
      credentials: 'include'
    })
    const body = await response.json()
    items.value = body.items
    total.value = body.total
  } catch (e) {
    error.value = String(e)
    items.value = []
  } finally {
    loading.value = false
  }
}

watch([query, projectId], search, { immediate: true })
</script>

<template>
  <input v-model="query" placeholder="Search documents" />
  <select v-model="projectId">
    <option value="all">All projects</option>
    <option value="a">Project A</option>
    <option value="b">Project B</option>
  </select>
  <p v-if="loading">Loading...</p>
  <p v-if="error">{{ error }}</p>
  <p>{{ total }} results</p>
  <div v-for="item in items" :key="item.id">
    <h3>{{ item.title }}</h3>
    <p>{{ item.summary }}</p>
  </div>
</template>
```

## Nhiệm vụ của ứng viên

3. Xếp severity theo tác động thực tế.
4. Đề xuất phiên bản sửa với cancellation, request identity và debounce.
5. Xây dựng tests và production telemetry để chứng minh không còn stale results.

3. Nếu request bị abort, `finally` của request cũ có được phép tắt spinner mới?

## Kết quả code review tham khảo

### [High] — Stale response ghi đè kết quả mới

**Vấn đề:** Response của query cũ có thể ghi đè items/total mới.  
**Tại sao xảy ra:** Không có request identity hoặc cancellation.  
**Ảnh hưởng production:** Hiển thị tài liệu không khớp filter hiện tại; người dùng có thể đưa ra quyết định sai.  
**Cách sửa:** Abort request cũ và kiểm tra generation ID trước khi mutate state.

### [High] — HTTP error bị xử lý như success

**Vấn đề:** `fetch` vẫn resolve cho HTTP 401/403/429/500; code parse body rồi gán vào items.  
**Tại sao xảy ra:** Không kiểm tra `response.ok`.  
**Ảnh hưởng production:** UI sai hoặc lỗi không rõ, mất thông tin trạng thái.  
**Cách sửa:** Kiểm tra status, phân biệt unauthorized, rate limit và server error.

### [Medium] — Loading state race

**Vấn đề:** `finally` của request cũ tắt loading khi request mới còn chạy.  
**Tại sao xảy ra:** Một boolean được nhiều request quản lý.  
**Ảnh hưởng production:** Spinner biến mất sớm, UI thiếu tín hiệu tiến trình.  
**Cách sửa:** Chỉ latest generation được cập nhật loading.

### [Medium] — Request storm khi gõ

**Vấn đề:** Mỗi thay đổi ký tự kích hoạt request.  
**Tại sao xảy ra:** Không debounce.  
**Ảnh hưởng production:** Tăng load search backend, network và chi phí; tăng nguy cơ 429.  
**Cách sửa:** Debounce nhập từ khóa; đổi project filter có thể chạy ngay nếu UX yêu cầu.

### [Medium] — Không encode query parameters

**Vấn đề:** Ghép URL thủ công gây sai query với ký tự `&`, `#`, dấu cách, Unicode.  
**Tại sao xảy ra:** Không dùng `URLSearchParams`.  
**Ảnh hưởng production:** Search sai hoặc filter bị biến dạng.  
**Cách sửa:** Dùng `URLSearchParams`.

### [Medium] — Không hủy request khi unmount

**Vấn đề:** Request vẫn tiêu tốn tài nguyên và callback tiếp tục chạy sau khi component không còn hiển thị.  
**Tại sao xảy ra:** Thiếu lifecycle cleanup.  
**Ảnh hưởng production:** Lãng phí request, state update khó kiểm soát.  
**Cách sửa:** Cleanup của watcher abort active request và clear debounce timer.

### [Medium] — State cũ vẫn xuất hiện khi lỗi

**Vấn đề:** `total` không reset trong catch; items có thể rỗng nhưng vẫn báo kết quả cũ.  
**Tại sao xảy ra:** State transition không atomic.  
**Ảnh hưởng production:** UI mâu thuẫn.  
**Cách sửa:** Cập nhật items/total/error cùng generation, định nghĩa rõ giữ hay xóa stale content.

### [Low] — Thiếu accessible status và error contract

**Vấn đề:** Search input không có label rõ; loading/error thiếu `role`/`aria-live` và thông điệp thân thiện.  
**Tại sao xảy ra:** Chỉ tối ưu hiển thị trực quan.  
**Ảnh hưởng production:** Trải nghiệm screen reader kém, hỗ trợ lỗi khó.  
**Cách sửa:** Label, `role="status"`, `role="alert"`, thông điệp lỗi chuẩn hóa.

## Phiên bản đề xuất

Ví dụ dùng Vue 3 `watch` cleanup và `AbortController`. Timer chỉ dùng cho debounce; cleanup chạy khi watcher invalidated hoặc component bị tháo. Backend vẫn phải xác thực/authorize từng request, không dựa vào client filter.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

type Item = { id: string; title: string; summary: string }
type SearchResponse = { items: Item[]; total: number }
const query = ref('')
const projectId = ref('all')
const items = ref<Item[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
let generation = 0

watch([query, projectId], ([q, project], _old, onCleanup) => {
  const id = ++generation
  const controller = new AbortController()
  let timer: ReturnType<typeof setTimeout> | undefined

  loading.value = true
  error.value = ''

  const execute = async () => {
    try {
      const params = new URLSearchParams({ q: q.trim(), project })
      const response = await fetch('/api/search?' + params, {
        credentials: 'include',
        signal: controller.signal
      })
      if (!response.ok) {
        throw new Error('Search failed (HTTP ' + response.status + ')')
      }
      const body = (await response.json()) as SearchResponse
      if (id !== generation || controller.signal.aborted) return
      items.value = body.items
      total.value = body.total
    } catch (e) {
      if (id !== generation || controller.signal.aborted) return
      error.value = e instanceof Error ? e.message : 'Search failed'
      items.value = []
      total.value = 0
    } finally {
      if (id === generation && !controller.signal.aborted)
        loading.value = false
    }
  }

  timer = setTimeout(execute, 250)
  onCleanup(() => {
    if (timer !== undefined) clearTimeout(timer)
    controller.abort()
  })
}, { immediate: true })
</script>

<template>
  <label for="search">Search documents</label>
  <input id="search" v-model="query" />
  <label for="project">Project</label>
  <select id="project" v-model="projectId">
    <option value="all">All projects</option>
    <option value="a">Project A</option>
    <option value="b">Project B</option>
  </select>
  <p v-if="loading" role="status">Loading...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <p>{{ total }} results</p>
  <div v-for="item in items" :key="item.id">
    <h3>{{ item.title }}</h3>
    <p>{{ item.summary }}</p>
  </div>
</template>
```

## Giải thích thiết kế sau khi sửa

Mỗi watcher invocation có generation và `AbortController` riêng. Cleanup hủy timer và request cũ; generation check bảo vệ cả trường hợp response đã hoàn tất hoặc cancellation không còn ngăn callback. `response.ok` tách HTTP error khỏi transport error. `URLSearchParams` mã hóa input. Để production-ready, nên thêm runtime schema validation, phân loại 401/403/429, request correlation ID và UI phân biệt empty/loading/error; ví dụ trên chủ ý giữ scope nhỏ.

## Trade-offs

Debounce 250 ms giảm request nhưng thêm độ trễ UX; có thể chạy ngay khi filter thay đổi nếu cần. Abort ở browser không đảm bảo backend đã dừng xử lý: API cần cancellation token, timeout và rate limiting riêng. Request identity tăng logic state nhưng tránh stale overwrite. Giữ kết quả cũ khi loading có thể cải thiện UX, nhưng phải đánh dấu rõ là stale và không cho nhầm với filter mới.

## Cách kiểm thử

1. **Race test:** Mock request A chậm hơn B; assert chỉ kết quả B được hiển thị.
2. **HTTP failure test:** Trả 401, 403, 429, 500 và JSON lỗi; assert không coi là success, state nhất quán.
3. **Debounce test:** Gõ 10 ký tự liên tục; assert số request thực tế theo chính sách debounce.
4. **Lifecycle test:** Unmount component khi request pending; assert request abort và không cập nhật state cũ.
5. **Playwright E2E:** Đổi project liên tục trong mạng throttled, kiểm tra filter, loading, accessibility status và server-side authorization.

## Quan sát trong production

Frontend ghi metrics số request bị abort, duration, error category, latest-request completion và correlation ID, không log raw search term nhạy cảm. Backend đo p95/p99 search duration, HTTP 429/5xx, cancellation, query load và authorization denial; dùng distributed tracing để nối browser request với ASP.NET Core dependency telemetry. Alert theo error-rate và latency, không dựa riêng vào số abort (abort do UX có thể bình thường).

## Câu hỏi phỏng vấn mở rộng

1. Nếu search API dùng Elasticsearch với eventual consistency, bạn sẽ trình bày trạng thái indexing lag cho người dùng như thế nào?
2. Nếu cần pagination/infinite scroll, làm sao tránh trộn pages của hai query khác nhau?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Authorization theo object/data scope phải được thực thi tại backend, không suy ra từ việc đã đăng nhập.
- Export file là bài toán security, resource management và operational lifecycle; CSV escaping và spreadsheet formula safety là hai yêu cầu khác nhau.
- Asynchronous UI phải xử lý response đến không đúng thứ tự; cancellation và generation guard bổ trợ nhau.
- Reliability cần đo và kiểm thử failure path thay vì chỉ xác nhận happy path.

## Mẫu tư duy cần nhớ

1. **Trust boundary trước optimization:** Ai kiểm soát input, ai quyết định quyền truy cập và dữ liệu nào có thể lộ?
2. **Bound resources trước scale:** Đặt giới hạn row count, memory, concurrency và thời gian.
3. **Latest intent wins:** State của UI chỉ được cập nhật bởi request còn hợp lệ với filter hiện tại.
4. **Measure before redesign:** Dùng logs, metrics và traces để phân biệt DB bottleneck, IIS saturation và network race.
5. **Test failure paths:** Out-of-order responses, unauthorized access, disconnect và recycle phải có test riêng.
