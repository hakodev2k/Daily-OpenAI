# Code Review Challenge 1 — File upload API chạy ổn ở test nhưng có thể làm cạn memory, ghi đè file và vượt authorization boundary

**Chủ đề:** ASP.NET Core, file upload, authorization, path handling, resource management, security, production reliability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề

## Bối cảnh

Một internal employee platform cho phép user upload tài liệu đính kèm vào approval request. API chạy ASP.NET Core trên nhiều instance Linux container. File hiện được lưu vào shared mounted storage; metadata lưu trong SQL Server.

Yêu cầu nghiệp vụ:

- user chỉ được upload vào approval request mà họ có quyền chỉnh sửa;
- file tối đa 50 MB;
- chỉ cho phép một số loại tài liệu thông dụng;
- tên file hiển thị cho user phải được giữ lại;
- storage filename không cần giống tên file gốc;
- upload thất bại không được để metadata trỏ tới file không tồn tại;
- request cancellation cần dừng công việc càng sớm càng tốt;
- endpoint có thể nhận vài chục upload đồng thời trong giờ cao điểm.

Production gần đây xuất hiện memory spike khi nhiều user upload file lớn cùng lúc. Operations cũng phát hiện một số file có tên lạ trong storage sau một đợt penetration test.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/approvals")]
public sealed class ApprovalFilesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly IWebHostEnvironment _env;
    private readonly ILogger<ApprovalFilesController> _logger;

    public ApprovalFilesController(
        AppDbContext db,
        IWebHostEnvironment env,
        ILogger<ApprovalFilesController> logger)
    {
        _db = db;
        _env = env;
        _logger = logger;
    }

    [HttpPost("{approvalId:long}/files")]
    public async Task<IActionResult> Upload(
        long approvalId,
        IFormFile file,
        CancellationToken cancellationToken)
    {
        var approval = await _db.Approvals
            .FirstOrDefaultAsync(x => x.Id == approvalId, cancellationToken);

        if (approval is null)
            return NotFound();

        using var memory = new MemoryStream();
        await file.CopyToAsync(memory, cancellationToken);

        var uploads = Path.Combine(_env.ContentRootPath, "uploads");
        Directory.CreateDirectory(uploads);

        var path = Path.Combine(uploads, file.FileName);
        await System.IO.File.WriteAllBytesAsync(
            path,
            memory.ToArray(),
            cancellationToken);

        var entity = new ApprovalFile
        {
            ApprovalId = approvalId,
            FileName = file.FileName,
            Path = path,
            ContentType = file.ContentType,
            Size = file.Length,
            UploadedBy = User.Identity?.Name ?? "unknown",
            UploadedAtUtc = DateTime.UtcNow
        };

        _db.ApprovalFiles.Add(entity);
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Uploaded {FileName} to {Path} for approval {ApprovalId}",
            file.FileName,
            path,
            approvalId);

        return Ok(new { entity.Id, entity.FileName });
    }
}
```

## Nhiệm vụ của ứng viên

2. Xác định các rủi ro security, performance và reliability.
3. Giải thích impact khi chạy nhiều upload lớn đồng thời hoặc nhiều application instances.
4. Ưu tiên findings theo severity thay vì chỉ liệt kê style issues.
5. Đề xuất implementation/design đã sửa.
6. Nêu chiến lược kiểm thử phù hợp với các failure mode chính.
7. Nêu telemetry cần có để phát hiện abuse, memory pressure và storage failure.

## Câu hỏi gợi mở

1. `file.FileName` có phải dữ liệu đáng tin cậy để dùng làm physical storage path không?
2. Có bao nhiêu bản sao của file có thể tồn tại trong managed memory trong flow hiện tại?
3. Điều gì xảy ra nếu ghi file thành công nhưng `SaveChangesAsync` thất bại, hoặc ngược lại nếu flow được đổi thứ tự?

## Kết quả code review tham khảo

### Critical — Thiếu object-level authorization cho approval request

**Vấn đề:** Endpoint chỉ kiểm tra approval tồn tại, không kiểm tra caller có quyền chỉnh sửa approval đó hay không.  
**Tại sao xảy ra:** Authentication identity được dùng gián tiếp để ghi `UploadedBy`, nhưng không có authorization decision gắn với resource.  
**Ảnh hưởng production:** User đã đăng nhập có thể thử `approvalId` khác và gắn file vào resource không thuộc quyền của mình; đây là broken access control.  
**Cách sửa:** Enforce policy/resource-based authorization hoặc query approval theo scope caller được phép thao tác. Authorization phải xảy ra trước khi nhận/ghi nội dung tốn tài nguyên.

### Critical — Dùng tên file do client cung cấp làm physical path

**Vấn đề:** `file.FileName` là untrusted input nhưng được đưa thẳng vào `Path.Combine`.  
**Tại sao xảy ra:** Code nhầm lẫn display filename với storage identifier.  
**Ảnh hưởng production:** Có thể gây path manipulation, filename collision, ghi đè file hoặc behavior khác nhau theo platform. Ngay cả khi framework/browser normalize một số input, server không nên dựa vào đó như security boundary.  
**Cách sửa:** Tạo server-generated storage key ngẫu nhiên/opaque; chỉ giữ sanitized original filename như metadata hiển thị. Không dùng client filename để quyết định path.

### High — Không enforce giới hạn kích thước ở application flow

**Vấn đề:** Requirement là 50 MB nhưng endpoint không validate `file.Length`, đồng thời request/form limits cần được cấu hình phù hợp ở hosting layer.  
**Tại sao xảy ra:** Code giả định upstream luôn chặn file lớn.  
**Ảnh hưởng production:** File quá lớn hoặc nhiều concurrent uploads có thể làm tăng memory, disk I/O và thời gian giữ request.  
**Cách sửa:** Defense in depth: cấu hình request/form limit phù hợp và validate application-level size trước khi copy. Giới hạn phải thống nhất với reverse proxy/hosting configuration.

### High — Buffer toàn bộ file và tạo nhiều bản sao trong memory

**Vấn đề:** File được copy vào `MemoryStream`, sau đó `ToArray()` tạo thêm byte array trước khi ghi.  
**Tại sao xảy ra:** Implementation ưu tiên API tiện dụng thay vì streaming.  
**Ảnh hưởng production:** Nhiều upload 50 MB đồng thời có thể tạo memory pressure, large allocations và GC overhead; process có thể bị OOM/restart dù từng request riêng lẻ chạy tốt.  
**Cách sửa:** Stream trực tiếp từ input sang destination với bounded buffering; nếu storage SDK hỗ trợ streaming thì dùng API đó. Theo dõi concurrency và cân nhắc admission control nếu storage throughput là resource hữu hạn.

### High — Không có consistency strategy giữa file storage và SQL metadata

**Vấn đề:** File được ghi trước, database lưu sau. Nếu database fail/cancel sau khi file đã ghi, orphan file tồn tại.  
**Tại sao xảy ra:** Filesystem và SQL không nằm trong một transaction nguyên tử chung.  
**Ảnh hưởng production:** Storage rác, khó reconcile, retry có thể tạo duplicate.  
**Cách sửa:** Thiết kế explicit workflow: tạo unique storage key, upload, persist metadata với trạng thái phù hợp, cleanup compensation khi persistence fail; hoặc dùng pending/finalized state và background reconciliation. Không giả vờ distributed atomic transaction tồn tại.

### High — Filename collision và race giữa concurrent requests

**Vấn đề:** Hai upload có cùng `file.FileName` ghi cùng path.  
**Tại sao xảy ra:** Physical identity được suy ra từ user filename.  
**Ảnh hưởng production:** Last writer có thể ghi đè file của request khác; metadata của nhiều rows có thể trỏ cùng path.  
**Cách sửa:** Server-generated unique storage key; enforce uniqueness ở metadata nếu cần và không dùng check-then-write dễ race.

### Medium — Validation loại file dựa trên metadata chưa tồn tại

**Vấn đề:** Không kiểm tra extension/type theo allowlist; `file.ContentType` được lưu như thể đáng tin cậy.  
**Tại sao xảy ra:** MIME type từ multipart request là client-controlled metadata.  
**Ảnh hưởng production:** File không mong muốn có thể được lưu/phục vụ lại; nếu hệ thống sau đó render/execute hoặc expose inline, risk tăng đáng kể.  
**Cách sửa:** Xác định allowlist theo business requirement, validate extension/signature khi phù hợp, lưu file ngoài executable/static-web path và khi download trả headers an toàn. Malware scanning có thể cần nếu threat model yêu cầu.

### Medium — Lưu absolute local path vào database làm coupling deployment/storage

**Vấn đề:** `Path` chứa filesystem path của runtime instance.  
**Tại sao xảy ra:** Persistence model bị gắn với physical deployment layout.  
**Ảnh hưởng production:** Migration storage, container path thay đổi hoặc chuyển sang Blob Storage trở nên khó; nếu mount không thật sự shared, instance khác có thể không đọc được file.  
**Cách sửa:** Lưu logical storage key/container/bucket identifier; storage abstraction chịu trách nhiệm resolve physical location.

### Medium — Logging path và filename chưa được threat-model hóa

**Vấn đề:** Log raw filename và physical path.  
**Tại sao xảy ra:** Diagnostic convenience được ưu tiên hơn data minimization.  
**Ảnh hưởng production:** Log có thể chứa control characters/untrusted values hoặc expose infrastructure path; downstream log search cũng có thể bị nhiễu.  
**Cách sửa:** Structured logging với storage key, approval ID, size, result; sanitize/limit user-controlled display filename và tránh physical path nếu không cần.

### Medium — Cancellation/failure cleanup chưa rõ

**Vấn đề:** Cancellation sau khi destination file đã được tạo có thể để partial/orphan state tùy write behavior.  
**Tại sao xảy ra:** Code propagate token nhưng không có compensation/finalization protocol.  
**Ảnh hưởng production:** Partial artifacts và retry ambiguity.  
**Cách sửa:** Ghi vào unique temporary/pending object, finalize atomically ở mức storage nếu khả thi, hoặc cleanup best-effort + reconciliation job.

## Phiên bản đề xuất

Ví dụ dưới đây giữ filesystem abstraction đơn giản nhưng tách display filename khỏi storage key và stream dữ liệu. Trong production, `IFileStore` có thể được implement bằng shared filesystem hoặc Azure Blob Storage tùy requirement.

```csharp
public sealed record StoredFile(string Key, long Length);

public interface IFileStore
{
    Task<StoredFile> PutAsync(
        string key,
        Stream content,
        CancellationToken cancellationToken);

    Task DeleteIfExistsAsync(
        string key,
        CancellationToken cancellationToken);
}

[Authorize]
[ApiController]
[Route("api/approvals")]
public sealed class ApprovalFilesController : ControllerBase
{
    private const long MaxFileSize = 50L * 1024 * 1024;
    private static readonly HashSet<string> AllowedExtensions =
        new(StringComparer.OrdinalIgnoreCase) { ".pdf", ".docx", ".xlsx" };

    private readonly AppDbContext _db;
    private readonly IAuthorizationService _authorization;
    private readonly IFileStore _files;
    private readonly ILogger<ApprovalFilesController> _logger;

    public ApprovalFilesController(
        AppDbContext db,
        IAuthorizationService authorization,
        IFileStore files,
        ILogger<ApprovalFilesController> logger)
    {
        _db = db;
        _authorization = authorization;
        _files = files;
        _logger = logger;
    }

    [HttpPost("{approvalId:long}/files")]
    public async Task<IActionResult> Upload(
        long approvalId,
        IFormFile file,
        CancellationToken cancellationToken)
    {
        if (file is null || file.Length <= 0 || file.Length > MaxFileSize)
            return BadRequest("Invalid file size.");

        var displayName = Path.GetFileName(file.FileName);
        var extension = Path.GetExtension(displayName);

        if (!AllowedExtensions.Contains(extension))
            return BadRequest("Unsupported file type.");

        var approval = await _db.Approvals
            .SingleOrDefaultAsync(x => x.Id == approvalId, cancellationToken);

        if (approval is null)
            return NotFound();

        var auth = await _authorization.AuthorizeAsync(
            User,
            approval,
            "EditApproval");

        if (!auth.Succeeded)
            return Forbid();

        var storageKey = $"approval-files/{Guid.NewGuid():N}{extension.ToLowerInvariant()}";
        var stored = default(StoredFile);

        try
        {
            await using var input = file.OpenReadStream();
            stored = await _files.PutAsync(storageKey, input, cancellationToken);

            var entity = new ApprovalFile
            {
                ApprovalId = approvalId,
                FileName = displayName,
                StorageKey = stored.Key,
                Size = stored.Length,
                UploadedBy = User.Identity?.Name,
                UploadedAtUtc = DateTime.UtcNow
            };

            _db.ApprovalFiles.Add(entity);
            await _db.SaveChangesAsync(cancellationToken);

            _logger.LogInformation(
                "Approval file uploaded. ApprovalId={ApprovalId} FileId={FileId} Size={Size}",
                approvalId,
                entity.Id,
                entity.Size);

            return Ok(new { entity.Id, entity.FileName });
        }
        catch
        {
            if (stored is not null)
            {
                try
                {
                    await _files.DeleteIfExistsAsync(
                        stored.Key,
                        CancellationToken.None);
                }
                catch (Exception cleanupError)
                {
                    _logger.LogWarning(
                        cleanupError,
                        "Failed to clean orphan upload {StorageKey}",
                        stored.Key);
                }
            }

            throw;
        }
    }
}
```

Implementation thực tế vẫn cần request/form size limits ở hosting layer, content validation phù hợp threat model, và reconciliation cho cleanup failure. Nếu dùng Blob Storage, database nên lưu blob key/metadata thay vì local path.

## Giải thích thiết kế sau khi sửa

Authorization được thực hiện trên resource cụ thể trước khi upload vào storage. Original filename chỉ còn vai trò display metadata; storage identity do server tạo. Streaming loại bỏ việc giữ toàn bộ payload và bản sao `ToArray()` trong memory.

Storage và SQL vẫn không thể trở thành một transaction nguyên tử chỉ bằng `try/catch`. Vì vậy implementation dùng compensation best-effort và cần reconciliation. Với hệ thống quan trọng hơn, có thể model upload state `Pending → Ready`, quét orphan objects và retry cleanup để failure behavior có thể quan sát và phục hồi.

`IFileStore` cũng giảm coupling với local filesystem. Nếu workload chạy nhiều containers, logical storage key giúp chuyển sang shared filesystem/Blob Storage mà không để database phụ thuộc runtime path.

## Trade-offs

- Resource-based authorization thêm một dependency/check nhưng đây là correctness/security requirement, không phải optional complexity.
- Streaming làm flow phức tạp hơn buffering nhỏ, nhưng cần thiết khi file có thể lớn và concurrency đáng kể.
- Signature scanning/malware scanning tăng latency và operational cost; mức kiểm tra phải theo threat model và cách file được sử dụng/phục vụ lại.
- Compensation không bảo đảm cleanup 100%; reconciliation/background cleanup tăng complexity nhưng cần nếu orphan storage có chi phí/risk đáng kể.
- Direct-to-Blob upload bằng short-lived SAS có thể giảm tải web server, nhưng cần thiết kế authorization, size/type validation và finalize protocol cẩn thận.

## Cách kiểm thử

1. **Security/integration test:** user A không thể upload vào approval chỉ user B được phép chỉnh sửa; test cả ID enumeration.
2. **Upload validation test:** file vượt 50 MB, extension không cho phép và filename chứa path/control-character variants bị từ chối hoặc sanitize đúng.
3. **Concurrency/load test:** nhiều upload gần 50 MB đồng thời; theo dõi process memory, GC, throughput và storage latency để chứng minh không buffer toàn bộ file.
4. **Failure-path test:** storage thành công nhưng SQL `SaveChanges` fail/cancel; xác minh compensation hoặc reconciliation phát hiện orphan.
5. **Multi-instance integration test:** upload qua instance A rồi download/metadata access qua instance B để xác minh storage thật sự shared và key portable.

## Quan sát trong production

Theo dõi upload request count, bytes uploaded, duration p95/p99, rejection theo reason, concurrent uploads, process working set/GC, storage dependency latency/error, SQL persistence failure và orphan-cleanup failure. Log structured fields như `ApprovalId`, `FileId`, `StorageKey`, `Size`, caller subject identifier phù hợp policy; tránh log file content hoặc secrets. Alert khi memory/GC tăng cùng upload concurrency, storage error rate tăng, hoặc cleanup backlog vượt threshold vận hành đã định.

## Câu hỏi phỏng vấn mở rộng

1. Nếu chuyển sang Azure Blob Storage và muốn browser upload trực tiếp bằng SAS, bạn sẽ giữ authorization và finalize metadata nhất quán thế nào?
2. Nếu antivirus scan mất 20–60 giây, bạn sẽ thiết kế trạng thái file và UX thế nào thay vì giữ HTTP request mở?
3. Khi nào lưu file trong database có thể hợp lý hơn object storage/filesystem, và trade-off là gì?

# Code Review Challenge 2 — Vue search page trả dữ liệu “nhảy lùi”: request race, stale state và XSS trong full-stack flow

**Chủ đề:** Vue.js, TypeScript, async race conditions, request cancellation, stale state, XSS, API integration, browser observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một Vue 3 page trong enterprise management portal cho phép user tìm employee theo tên và hiển thị snippet mô tả do backend trả về. Backend ASP.NET Core đã có authorization và pagination.

Expected behavior:

- khi user gõ nhanh, UI phải hiển thị kết quả tương ứng query mới nhất;
- không gửi request cho query quá ngắn;
- không tạo request storm không cần thiết;
- navigation/unmount không được để stale request tiếp tục update state;
- lỗi transient phải hiển thị trạng thái phù hợp nhưng không ghi đè kết quả của query mới hơn;
- snippet có thể chứa text nhập bởi administrator từ hệ thống khác và không được coi là trusted HTML mặc định.

Production symptom:

- khi network chậm, user gõ `ann`, rồi `anna`, đôi lúc UI cuối cùng lại hiển thị kết quả của `ann`;
- backend thấy nhiều request bị bỏ dở ở browser nhưng vẫn tiếp tục xử lý tới database;
- đôi lúc spinner biến mất trong khi request mới vẫn đang chạy;
- security review phát hiện khả năng render HTML không mong muốn trong snippet.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface EmployeeResult {
  id: number
  name: string
  snippet: string
}

const query = ref('')
const results = ref<EmployeeResult[]>([])
const loading = ref(false)
const error = ref('')

watch(query, async (value) => {
  if (value.length < 2) {
    results.value = []
    return
  }

  loading.value = true
  error.value = ''

  try {
    const response = await fetch(
      `/api/employees/search?q=${value}&page=1&pageSize=20`
    )

    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`)
    }

    results.value = await response.json()
  } catch (e) {
    error.value = String(e)
  } finally {
    loading.value = false
  }
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search employees" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="employee in results" :key="employee.id">
      <h3>{{ employee.name }}</h3>
      <div v-html="employee.snippet"></div>
    </article>
  </section>
</template>
```

## Nhiệm vụ của ứng viên

1. Xác định correctness bugs trong asynchronous UI state.
2. Xác định security và performance/reliability concerns.
3. Giải thích tại sao bug chỉ xuất hiện rõ khi latency thay đổi hoặc user gõ nhanh.
4. Ưu tiên vấn đề theo impact.
5. Đề xuất implementation an toàn hơn, bao gồm cancellation/stale-response protection.
6. Chọn tests có khả năng tái hiện race thay vì chỉ happy-path tests.
7. Nêu browser/backend telemetry giúp chứng minh request storm và cancellation propagation.

## Câu hỏi gợi mở

1. Có đảm bảo request được tạo sau sẽ hoàn thành sau request cũ không?
2. `finally` của request cũ có quyền thay đổi `loading` của request mới không?
3. Query string hiện tại có được encode đúng không?

5. Debounce và cancellation giải quyết cùng một vấn đề hay hai vấn đề khác nhau?

## Gợi ý

## Kết quả code review tham khảo

### Critical — `v-html` render untrusted snippet tạo XSS boundary nguy hiểm

**Vấn đề:** `employee.snippet` được render bằng `v-html` dù dữ liệu đến từ external/admin-controlled source và không có contract rằng nó đã được sanitize.  
**Tại sao xảy ra:** `v-html` đưa chuỗi vào HTML rendering path thay vì text interpolation an toàn mặc định.  
**Ảnh hưởng production:** Malicious hoặc compromised content có thể trở thành scriptable markup trong browser tùy payload/browser/security controls.  
**Cách sửa:** Nếu không thực sự cần markup, render bằng `{{ employee.snippet }}`. Nếu business bắt buộc rich HTML, sanitize bằng một strategy/library được security review và xác định rõ trust boundary; CSP là defense-in-depth, không thay thế sanitization.

### High — Response cũ có thể ghi đè state của query mới

**Vấn đề:** Mỗi lần `query` đổi tạo một async request độc lập và bất kỳ response nào hoàn thành cuối đều ghi `results.value`.  
**Tại sao xảy ra:** Network completion order không đảm bảo request order.  
**Ảnh hưởng production:** User gõ `ann` rồi `anna`, response `ann` chậm hơn có thể ghi đè kết quả đúng của `anna`.  
**Cách sửa:** Abort request trước bằng `AbortController` và/hoặc dùng monotonically increasing request version để chỉ latest request được commit state.

### High — `loading` có race tương tự results

**Vấn đề:** `finally` của request cũ luôn đặt `loading=false`.  
**Tại sao xảy ra:** Boolean loading state không gắn với identity/version của request hiện hành.  
**Ảnh hưởng production:** Spinner biến mất trong khi latest request vẫn đang chạy, tạo UX sai và làm debugging khó.  
**Cách sửa:** Chỉ latest request được cập nhật loading/error, hoặc track active request identity/count theo semantics mong muốn.

### High — Không cancel stale request nên browser/backend làm work vô ích

**Vấn đề:** Request cũ tiếp tục chạy khi query thay đổi hoặc component cleanup.  
**Tại sao xảy ra:** Không dùng `AbortController`/watch cleanup.  
**Ảnh hưởng production:** Request storm tăng backend RPS, database work và bandwidth; user navigation không giải phóng work sớm.  
**Cách sửa:** Abort previous fetch khi watcher invalidated. Backend ASP.NET Core cũng phải propagate request cancellation token xuống database/dependencies để cancellation có giá trị end-to-end.

### Medium — Không debounce input

**Vấn đề:** Mỗi keystroke sau threshold tạo request ngay.  
**Tại sao xảy ra:** Watcher phản ứng trực tiếp với mọi value.  
**Ảnh hưởng production:** Fast typing tạo nhiều requests ngắn hạn; cancellation giúp giảm stale work nhưng vẫn có request creation/connection/backend overhead.  
**Cách sửa:** Debounce hợp lý theo UX requirement; không chọn interval tùy tiện mà nên đo perceived latency và request reduction.

### Medium — Query parameter không được encode bằng URL API

**Vấn đề:** Raw `value` được nối vào URL.  
**Tại sao xảy ra:** String interpolation thay cho `URLSearchParams`.  
**Ảnh hưởng production:** Các ký tự như `&`, `+`, `#` hoặc Unicode combinations có thể tạo query semantics sai. Đây không tự động là SQL injection nếu backend parameterize đúng, nhưng vẫn là correctness bug ở HTTP layer.  
**Cách sửa:** Dùng `URLSearchParams` hoặc URL builder.

### Medium — Error của stale/aborted request có thể ghi đè state mới

**Vấn đề:** `catch` luôn gán `error`; abort cũng có thể đi vào error path nếu không phân biệt.  
**Tại sao xảy ra:** Error state không gắn với latest request.  
**Ảnh hưởng production:** UI hiển thị lỗi cho request user không còn quan tâm hoặc báo cancellation như application failure.  
**Cách sửa:** Ignore expected abort và chỉ latest request được commit error.

### Low — Query ngắn không reset toàn bộ state nhất quán

**Vấn đề:** Khi query xuống dưới threshold, code clear results nhưng không đảm bảo request trước đã bị cancel và không reset loading/error theo lifecycle nhất quán.  
**Tại sao xảy ra:** Early return nằm ngoài request lifecycle management.  
**Ảnh hưởng production:** Request cũ vẫn có thể quay lại populate results cho query hiện tại rỗng/ngắn.  
**Cách sửa:** Cleanup/abort trước, increment request version, rồi reset state cho query không hợp lệ.

## Phiên bản đề xuất

Ví dụ này dùng watcher cleanup để abort stale request, request version để bảo vệ state commit, và debounce nhỏ. Hai lớp cancellation + version guard có mục đích khác nhau: cancellation giảm work, version guard bảo vệ correctness ngay cả khi cancellation không kịp ngăn completion.

```vue
<script setup lang="ts">
import { ref, watch } from 'vue'

interface EmployeeResult {
  id: number
  name: string
  snippet: string
}

const query = ref('')
const results = ref<EmployeeResult[]>([])
const loading = ref(false)
const error = ref('')

let requestVersion = 0

watch(query, (rawValue, _oldValue, onCleanup) => {
  const version = ++requestVersion
  const controller = new AbortController()
  let timer: ReturnType<typeof setTimeout> | undefined

  onCleanup(() => {
    controller.abort()
    if (timer) clearTimeout(timer)
  })

  const value = rawValue.trim()

  if (value.length < 2) {
    results.value = []
    error.value = ''
    loading.value = false
    return
  }

  timer = setTimeout(async () => {
    if (version !== requestVersion) return

    loading.value = true
    error.value = ''

    try {
      const params = new URLSearchParams({
        q: value,
        page: '1',
        pageSize: '20'
      })

      const response = await fetch(
        `/api/employees/search?${params.toString()}`,
        { signal: controller.signal }
      )

      if (!response.ok) {
        throw new Error(`HTTP ${response.status}`)
      }

      const data = await response.json() as EmployeeResult[]

      if (version === requestVersion) {
        results.value = data
      }
    } catch (e) {
      if (controller.signal.aborted) return

      if (version === requestVersion) {
        error.value = e instanceof Error ? e.message : 'Search failed'
      }
    } finally {
      if (version === requestVersion) {
        loading.value = false
      }
    }
  }, 250)
})
</script>

<template>
  <section>
    <input v-model="query" placeholder="Search employees" />

    <p v-if="loading">Loading...</p>
    <p v-if="error">{{ error }}</p>

    <article v-for="employee in results" :key="employee.id">
      <h3>{{ employee.name }}</h3>
      <div>{{ employee.snippet }}</div>
    </article>
  </section>
</template>
```

Nếu product thực sự yêu cầu highlighted HTML snippet, contract phải thay đổi rõ ràng: backend/search layer có thể trả structured highlight segments hoặc sanitized markup theo policy đã thống nhất. Không nên ngầm biến arbitrary string thành trusted HTML ở component.

## Giải thích thiết kế sau khi sửa

Debounce giảm số request được khởi tạo khi user đang gõ. `AbortController` cố dừng stale network work. `requestVersion` bảo đảm chỉ latest logical search được commit `results`, `error` và `loading`; đây là correctness guard ngay cả khi abort xảy ra quá muộn.

Watcher cleanup gắn lifecycle của request với reactive effect. Khi query thay đổi, timer/request trước bị invalidate. Việc dùng `URLSearchParams` tách encoding khỏi string interpolation.

Ở backend, cancellation chỉ hữu ích nếu ASP.NET Core action nhận request cancellation và propagate token xuống EF Core/HTTP dependencies. Nếu browser abort nhưng backend bỏ token, database work vẫn có thể tiếp tục.

## Trade-offs

- Debounce tăng một lượng nhỏ perceived latency; interval nên dựa trên UX và measurements.
- Abort không phải transactional rollback: dependency có thể đã bắt đầu work trước khi cancellation được quan sát. Version guard vẫn cần cho UI correctness.
- Request version thêm state nhưng rất rẻ và làm invariant “latest query wins” explicit.
- Rendering plain text bỏ rich formatting. Nếu rich snippet là requirement thật, sanitization/structured highlights tăng implementation complexity nhưng cần để giữ security boundary.
- Client-side request reduction không thay thế backend rate limiting/query optimization nếu endpoint có thể bị gọi trực tiếp.

## Cách kiểm thử

1. **Race test:** mock `ann` response chậm hơn `anna`; xác minh UI cuối cùng chỉ hiển thị `anna` và stale `finally` không tắt loading sớm.
2. **Cancellation test:** đổi query/unmount trong lúc fetch pending; xác minh request bị aborted và không update results/error sau cleanup.
3. **Request-volume test:** mô phỏng gõ nhanh nhiều ký tự; xác minh debounce giảm số fetch theo contract mong muốn.
4. **Security test:** backend trả snippet chứa HTML/event-handler payload; xác minh UI render text chứ không execute/interpret markup.
5. **Playwright E2E + controlled latency:** intercept API, reorder responses và thêm delay để tái hiện behavior trên browser thực.

## Quan sát trong production

Ở browser/RUM có thể theo dõi search request count trên mỗi interaction, duration, abort count, error rate và stale-response suppression nếu instrument phù hợp. Backend nên correlate request/query telemetry với cancellation, database dependency duration và rows/result count. Application Insights hoặc equivalent tracing giúp thấy browser/user action tạo bao nhiêu API calls và liệu aborted HTTP request có thực sự làm dependency work kết thúc sớm. Alert không cần dựa trên từng abort — abort có thể là behavior bình thường — mà dựa trên request amplification, backend resource pressure và latency/error SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search endpoint dùng Elasticsearch và hỗ trợ highlight HTML, bạn sẽ thiết kế contract thế nào để giữ highlight mà không biến arbitrary content thành XSS?
2. Nếu không dùng `AbortController`, chỉ dùng request version có đủ không? Điều gì đúng về correctness nhưng vẫn tệ về resource usage?
3. Nếu search results được cache ở browser/client store, bạn sẽ thiết kế cache key và freshness thế nào để không táiintroduce stale-state bug?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- File upload là một security/resource-consistency boundary: authorization, untrusted filename, size limits, streaming và storage/database failure phải được thiết kế cùng nhau.
- Không dùng client-provided filename làm physical storage identity; display metadata và storage key là hai concern khác nhau.
- Streaming giảm memory amplification nhưng không tự giải quyết concurrency, storage throughput hay distributed consistency.
- Frontend async code có distributed-systems-like behavior ở quy mô nhỏ: request completion có thể reorder, cancellation có thể đến muộn và stale state cần explicit guard.
- Debounce, cancellation và latest-request validation giải quyết ba vấn đề liên quan nhưng không đồng nhất.
- `v-html` thay đổi trust boundary; dữ liệu từ backend không mặc định trở thành trusted HTML chỉ vì nó đến từ server của mình.

## Mẫu tư duy cần nhớ

1. **Treat user-controlled metadata as untrusted input, kể cả filename và MIME type.**
2. **Thiết kế failure giữa hai persistence systems bằng compensation/reconciliation, không giả định atomicity.**
3. **Bound resource usage trước khi load/concurrency biến bug nhỏ thành incident.**
4. **Latest intent must win: async completion order không phải business order.**
5. **Cancellation giảm work; correctness vẫn cần invariant riêng.**
