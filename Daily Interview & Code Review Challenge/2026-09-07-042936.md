# Code Review Challenge 1 — Elasticsearch index bị lệch khỏi SQL sau partial failure

**Chủ đề:** C#/.NET, Entity Framework Core, Elasticsearch, eventual consistency, retry, idempotency, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một e-commerce backend dùng SQL Server làm source of truth cho product catalog và Elasticsearch để phục vụ full-text search.

Flow hiện tại:

- API update product ghi dữ liệu vào SQL Server;
- sau khi `SaveChangesAsync`, cùng request gọi Elasticsearch để index lại document;
- API chạy trên nhiều Azure App Service instance;
- client có thể retry khi timeout;
- Elasticsearch đôi khi latency cao hoặc tạm unavailable;
- production ghi nhận product đã update trong SQL nhưng search vẫn trả dữ liệu cũ, API update chậm khi search cluster degradation, và support khó biết index đang chứa version nào của product.

Implementation hiện tại:

## Đoạn code cần review

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;
    private readonly IProductSearchIndex _search;
    private readonly ILogger<ProductService> _logger;

    public ProductService(
        AppDbContext db,
        IProductSearchIndex search,
        ILogger<ProductService> logger)
    {
        _db = db;
        _search = search;
        _logger = logger;
    }

    public async Task UpdateAsync(
        Guid productId,
        UpdateProductRequest request)
    {
        var product = await _db.Products
            .SingleAsync(x => x.Id == productId);

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.UpdatedUtc = DateTime.UtcNow;

        await _db.SaveChangesAsync();

        var document = new ProductSearchDocument
        {
            Id = product.Id,
            Name = product.Name,
            Description = product.Description,
            Price = product.Price,
            UpdatedUtc = product.UpdatedUtc
        };

        var result = await _search.UpsertAsync(document);

        if (!result.Success)
        {
            _logger.LogError(
                "Search indexing failed: {Reason}",
                result.Error);

            throw new InvalidOperationException("Search indexing failed.");
        }
    }
}
```

## Nhiệm vụ của ứng viên

Hãy review implementation trên như một Senior .NET Developer.

Bạn cần:

1. xác định correctness và consistency problems;
2. phân tích transaction boundary giữa SQL và Elasticsearch;
3. đánh giá retry/idempotency;
4. đánh giá ordering/versioning;
5. đánh giá impact lên API latency và availability;
6. ưu tiên vấn đề theo severity;
7. đề xuất implementation/design tốt hơn;
8. giải thích testing;
9. giải thích telemetry cần quan sát trong production.

## Câu hỏi gợi mở

1. Nếu SQL commit thành công nhưng Elasticsearch fail thì trạng thái hệ thống là gì?
2. Nếu caller retry vì API trả lỗi sau khi SQL đã commit thì chuyện gì xảy ra?
3. Hai update cùng product hoàn thành indexing sai thứ tự có thể gây lỗi gì?
4. Search index có nhất thiết phải nằm trong critical path của write API không?
5. Làm sao xác định index đang phản ánh version nào của SQL record?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **dual write không atomic**.

### Gợi ý 2

Hãy nghĩ theo hướng **source of truth → durable change record → asynchronous projection → version-aware indexing**.

## Kết quả code review tham khảo

### Critical — SQL và Elasticsearch được dual-write nhưng không atomic

**Vấn đề:**  
SQL commit trước, Elasticsearch update sau.

**Tại sao xảy ra:**  
Hai storage system không có transaction boundary chung.

**Ảnh hưởng production:**  
SQL có dữ liệu mới nhưng search vẫn stale nếu indexing fail. Việc throw sau SQL commit làm caller hiểu nhầm toàn bộ operation thất bại.

**Cách sửa:**  
Commit business data cùng một durable outbox/change record trong SQL transaction. Worker xử lý outbox và update Elasticsearch asynchronously.

---

### High — Retry ambiguity sau khi business write đã commit

**Vấn đề:**  
Method throw dù product đã được update trong SQL.

**Tại sao xảy ra:**  
Business transaction và projection transaction bị gộp thành một success/failure contract.

**Ảnh hưởng production:**  
Caller retry có thể lặp business operation. Nếu sau này update kéo theo side effect khác, duplicate có thể nghiêm trọng.

**Cách sửa:**  
API success/failure nên phản ánh source-of-truth write. Projection lag được theo dõi độc lập.

---

### High — Không có version guard cho out-of-order indexing

**Vấn đề:**  
Document không mang monotonic product version.

**Tại sao xảy ra:**  
Request hoặc background retry có thể hoàn thành sai thứ tự.

**Ảnh hưởng production:**  
Version cũ có thể ghi đè version mới trong search index.

**Cách sửa:**  
Thêm aggregate version/row version và làm indexing idempotent, version-aware. Duplicate cùng version là no-op; stale version không được ghi đè version mới.

---

### High — Search dependency nằm trong critical path của write API

**Vấn đề:**  
Request phải chờ Elasticsearch.

**Tại sao xảy ra:**  
Projection được xử lý synchronous.

**Ảnh hưởng production:**  
Search latency/degradation kéo write latency và availability xuống theo.

**Cách sửa:**  
Nếu business chấp nhận eventual consistency, chuyển indexing sang asynchronous worker.

---

### High — Không propagate `CancellationToken`

**Vấn đề:**  
EF Core và search calls không nhận cancellation.

**Tại sao xảy ra:**  
Method không nhận token.

**Ảnh hưởng production:**  
Caller disconnect nhưng server vẫn tiếp tục I/O không cần thiết. Tuy nhiên durable consistency work sau commit cũng không nên phụ thuộc hoàn toàn vào request cancellation.

**Cách sửa:**  
Propagate request token cho request-scoped work; durable outbox processing có lifecycle riêng.

---

### Medium — Không có replay/idempotency contract

**Vấn đề:**  
Code giả định một update chỉ được index một lần.

**Tại sao xảy ra:**  
Retry và at-least-once processing chưa được coi là normal behavior.

**Ảnh hưởng production:**  
Khi chuyển sang worker, duplicate event có thể tạo bug nếu projection không deterministic.

**Cách sửa:**  
Consumer xử lý theo `ProductId + Version`, cho phép replay an toàn.

---

### Medium — Logging thiếu product identity/version/correlation

**Vấn đề:**  
Error log chỉ có reason.

**Tại sao xảy ra:**  
Không log structured context đủ để trace projection lifecycle.

**Ảnh hưởng production:**  
Khó điều tra stale search result.

**Cách sửa:**  
Log `ProductId`, `ProductVersion`, event ID, retry attempt, duration và trace/correlation ID.

---

### Medium — Không có reconciliation path

**Vấn đề:**  
Một failed projection có thể stale vô thời hạn.

**Tại sao xảy ra:**  
Không có backlog monitoring hoặc reconciliation.

**Ảnh hưởng production:**  
Search sai nhưng hệ thống không phát hiện.

**Cách sửa:**  
Theo dõi failed/outstanding work và định kỳ đối chiếu source version với indexed version.

## Phiên bản đề xuất

```csharp
public sealed class ProductService
{
    private readonly AppDbContext _db;

    public ProductService(AppDbContext db)
    {
        _db = db;
    }

    public async Task UpdateAsync(
        Guid productId,
        UpdateProductRequest request,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .SingleAsync(x => x.Id == productId, cancellationToken);

        product.Name = request.Name;
        product.Description = request.Description;
        product.Price = request.Price;
        product.Version++;
        product.UpdatedUtc = DateTime.UtcNow;

        _db.OutboxMessages.Add(new OutboxMessage
        {
            Id = Guid.NewGuid(),
            Type = "ProductChanged",
            AggregateId = product.Id,
            AggregateVersion = product.Version,
            Payload = JsonSerializer.Serialize(new ProductChanged
            {
                ProductId = product.Id,
                Version = product.Version
            }),
            CreatedUtc = DateTime.UtcNow
        });

        await _db.SaveChangesAsync(cancellationToken);
    }
}

public sealed class ProductIndexHandler
{
    private readonly AppDbContext _db;
    private readonly IProductSearchIndex _search;

    public ProductIndexHandler(
        AppDbContext db,
        IProductSearchIndex search)
    {
        _db = db;
        _search = search;
    }

    public async Task HandleAsync(
        ProductChanged message,
        CancellationToken cancellationToken)
    {
        var product = await _db.Products
            .AsNoTracking()
            .SingleAsync(x => x.Id == message.ProductId, cancellationToken);

        if (product.Version < message.Version)
            return;

        await _search.UpsertIfNewerAsync(
            new ProductSearchDocument
            {
                Id = product.Id,
                Version = product.Version,
                Name = product.Name,
                Description = product.Description,
                Price = product.Price,
                UpdatedUtc = product.UpdatedUtc
            },
            cancellationToken);
    }
}
```

Production implementation vẫn cần outbox claim/lease, retry, poison handling và monitoring. Điểm chính là transaction boundary: product update và outbox record commit cùng nhau; Elasticsearch là projection có thể retry/rebuild.

## Giải thích thiết kế sau khi sửa

- SQL vẫn là source of truth.
- Outbox đóng khoảng trống giữa SQL commit và việc phát sinh projection work.
- Worker chấp nhận duplicate/replay.
- Product version ngăn stale update ghi đè version mới.
- Elasticsearch degradation làm tăng projection lag thay vì kéo write API down ngay lập tức.

## Trade-offs

- Search trở thành eventual-consistent.
- Outbox + worker tăng operational complexity.
- Multi-instance worker cần claim/concurrency strategy.
- Version-aware update cần model và telemetry rõ ràng.
- Rebuild index cần capacity planning để không ảnh hưởng search traffic.

## Cách kiểm thử

1. **Integration test:** product update và outbox record phải cùng commit hoặc cùng rollback.
2. **Failure-path test:** search unavailable; business write vẫn thành công và outbox backlog tăng có kiểm soát.
3. **Ordering test:** replay version cũ sau version mới; index không được rollback về stale data.
4. **Duplicate test:** xử lý cùng event nhiều lần; kết quả phải deterministic.
5. **Load test:** bulk product update đồng thời search traffic; đo write latency, projection lag và search latency.

## Quan sát trong production

Theo dõi:

- outbox backlog count;
- oldest pending event age;
- indexing success/failure rate;
- retry/failed count;
- projection lag theo version hoặc event age;
- Elasticsearch dependency latency;
- search p95/p99;
- SQL write latency;
- stale-version update rejection count;
- correlation giữa ProductId, version và indexing event.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product phải xuất hiện trong search dưới 2 giây, bạn sẽ định nghĩa SLA và alerting cho projection thế nào?
2. Nếu nhiều worker xử lý outbox song song, bạn sẽ claim work an toàn như thế nào?
3. Nếu mapping Elasticsearch thay đổi breaking, bạn sẽ rebuild và switch index thế nào để giảm downtime?

# Code Review Challenge 2 — Release pipeline dùng mutable artifact và migration không tương thích rolling deployment

## Kết quả code review tham khảo

### Critical — Destructive migration chạy trước rolling deployment

**Vấn đề:**  
Column có thể bị rename/drop trước khi old nodes ngừng chạy.

**Tại sao xảy ra:**

### Critical — Rollback code không đồng nghĩa rollback database

**Vấn đề:**

**Tại sao xảy ra:**

Có thể deploy binary A với migration B; audit và incident investigation khó tái hiện.

**Cách sửa:**

### High — Deploy nhiều node nhưng không validate từng node trước khi tiếp tục

```yaml
stages:
  - build
  - validate
  - migrate-expand
  - deploy
  - verify

build:
  script:

  strategy: rolling
```

## Giải thích thiết kế sau khi sửa

- Application artifact và migration manifest cùng một immutable release identity.
- Expand migration giữ old/new code compatible trong rolling window.
- Contract migration bị trì hoãn đến khi dependency cũ biến mất.
- Per-node rollout làm giảm blast radius.
- Migration step được serialize để tránh concurrent schema mutation.

## Trade-offs

- Expand/contract kéo migration qua nhiều release.
- Rolling từng node chậm hơn deploy toàn bộ cùng lúc.
- Versioned artifacts dùng thêm storage nhưng tăng reproducibility.
- Deployment lock giảm concurrency nhưng schema mutation production vốn cần ownership rõ ràng.
- Blue-green có thể an toàn hơn trong vài hệ thống nhưng tốn thêm capacity và operational complexity.

## Cách kiểm thử

1. **Compatibility test:** chạy old application version trên expanded schema mới.
2. **Rollback rehearsal:** deploy new release rồi rollback binary trong staging; app cũ vẫn phải chạy.
3. **Concurrency test:** hai release cùng bắt đầu; schema mutation step phải được serialize.
4. **Failure-path test:** một node fail readiness; rollout phải dừng trước khi tiếp tục các node còn lại.
5. **Deployment validation:** xác minh mọi node report đúng release ID và aggregate p95/error rate không regress.

- rollback events;

- application errors liên quan missing/renamed columns.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- SQL + Elasticsearch synchronous dual-write tạo consistency gap và retry ambiguity.
- Search index nên được coi là derived projection khi business cho phép eventual consistency.
- Retry cần được thiết kế cùng idempotency và ordering/versioning.
- Rolling deployment đòi hỏi old/new application version cùng tương thích với schema trong rollout window.
- Rollback code chỉ an toàn khi database contract vẫn tương thích.
- Release cần immutable artifact, traceability, migration ownership và per-node validation.

## Mẫu tư duy cần nhớ

1. **Separate source of truth from derived projections.**
