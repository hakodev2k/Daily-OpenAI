# Code Review Challenge 1 — Middleware ghi toàn bộ request body làm lộ dữ liệu nhạy cảm và tăng memory dưới load

**Chủ đề:** C#/.NET, ASP.NET Core middleware, request buffering, memory, security, structured logging, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API phục vụ checkout và account-management. Để điều tra lỗi production nhanh hơn, team thêm middleware ghi request body cho mọi request. API nhận JSON thông thường vài KB, nhưng một số endpoint import có body vài MB. Production chạy nhiều instances và có thời điểm hàng trăm requests đồng thời.

Sau deployment, team thấy allocation rate và Gen 2 GC tăng, p99 latency xấu đi khi import traffic tăng. Security review cũng phát hiện logs có thể chứa email, address, access token từ một số payload và thông tin thanh toán đã được token hóa. Team cần giữ correlation và diagnostic value nhưng không có requirement phải lưu raw body của mọi request.

## Đoạn code cần review

```csharp
public sealed class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    public RequestLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        context.Request.EnableBuffering();

        using var reader = new StreamReader(
            context.Request.Body,
            Encoding.UTF8,
            detectEncodingFromByteOrderMarks: false,
            leaveOpen: true);

        var body = await reader.ReadToEndAsync();
        context.Request.Body.Position = 0;

        _logger.LogInformation(
            "HTTP {Method} {Path} body={Body} Authorization={Authorization}",
            context.Request.Method,
            context.Request.Path,
            body,
            context.Request.Headers.Authorization.ToString());

        var stopwatch = Stopwatch.StartNew();
        await _next(context);
        stopwatch.Stop();

        _logger.LogInformation(
            "HTTP {Method} {Path} returned {StatusCode} in {ElapsedMs} ms",
            context.Request.Method,
            context.Request.Path,
            context.Response.StatusCode,
            stopwatch.ElapsedMilliseconds);
    }
}
```

Middleware được đặt sớm trong pipeline để capture mọi request, kể cả authentication failures.

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề security/privacy, correctness và resource usage.
2. Phân tích allocation/memory behavior khi body lớn và nhiều requests đồng thời.
3. Review buffering semantics, cancellation và exception path.
4. Giải thích production impact của việc log `Authorization` và raw payload.
5. Đề xuất logging design có diagnostic value nhưng data-minimizing và bounded.
6. Nêu tests cho large body, client disconnect, exception, sensitive fields và concurrent load.
7. Nêu telemetry giúp xác định middleware có phải nguyên nhân của latency/memory regression hay không.

## Câu hỏi gợi mở

1. Một request body 8 MB có thể tồn tại ở bao nhiêu representation/buffer trong quá trình này?
2. `EnableBuffering()` có biến việc đọc toàn bộ body thành miễn phí về memory/I/O không?
3. Log raw `Authorization` header tạo blast radius gì nếu log backend bị truy cập?
4. Nếu `_next(context)` ném exception, completion log hiện tại có được ghi không?
5. Diagnostic requirement thực sự cần raw payload hay chỉ cần request metadata, identifiers và selected safe fields?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **unbounded diagnostic capture** trên hot request path.

### Gợi ý 2

Tách ba vấn đề: dữ liệu nào được phép log, lượng dữ liệu tối đa, và telemetry nào đủ để điều tra mà không cần copy toàn bộ body.

## Kết quả code review tham khảo

### Critical — Ghi `Authorization` header vào log

**Vấn đề:** Middleware ghi nguyên giá trị `Authorization`.

**Tại sao xảy ra:** Diagnostic logging không có secret-redaction policy.

**Ảnh hưởng production:** Bearer token hoặc credential có thể bị sao chép sang log storage, backup, SIEM và môi trường support; bất kỳ ai có quyền đọc log có thể nhận secret còn hiệu lực.

**Cách sửa:** Không log credential/token. Chỉ log authentication outcome hoặc non-secret identity metadata đã được policy cho phép. Thiết lập redaction và kiểm tra log sinks/retention/permissions.

### Critical — Raw request body có thể chứa PII hoặc dữ liệu nhạy cảm

**Vấn đề:** Mọi body đều được ghi nguyên văn.

**Tại sao xảy ra:** Middleware không phân loại endpoint/content/schema và không áp dụng data minimization.

**Ảnh hưởng production:** Privacy/security incident, retention ngoài ý muốn và blast radius lớn nếu logging platform bị compromise.

**Cách sửa:** Mặc định không log raw body. Dùng allowlist cho metadata/field an toàn; redaction theo schema nếu một use case thực sự cần payload diagnostics. Không dựa vào blacklist đơn giản vì schema thay đổi.

### High — `ReadToEndAsync` materialize toàn bộ body thành string

**Vấn đề:** Request lớn được copy thành một `string` hoàn chỉnh trước khi application xử lý.

**Tại sao xảy ra:** Code đọc tới EOF thay vì bounded capture.

**Ảnh hưởng production:** Allocation rate tăng mạnh; large strings có thể gây GC pressure và concurrency làm working set/p99 xấu hơn. Buffering còn có thể dùng memory hoặc temporary storage tùy kích thước/configuration, nên cần đo runtime thực tế thay vì giả định chỉ có một copy.

**Cách sửa:** Không đọc body nếu không cần. Nếu diagnostic policy cho phép sample, đặt giới hạn bytes nhỏ, content-type/endpoint allowlist và tránh biến toàn bộ payload thành string.

### High — Logging tạo thêm serialization/storage pressure trên request path

**Vấn đề:** Raw body được đưa vào structured log event cho mọi request.

**Tại sao xảy ra:** Volume tỷ lệ với request payload thay vì diagnostic signal.

**Ảnh hưởng production:** Tăng CPU, network/storage ingestion cost, log throttling và có thể làm incident nặng hơn đúng lúc traffic tăng.

**Cách sửa:** Log metadata có cardinality/size kiểm soát; sampling theo policy; dùng traces/dependency telemetry và domain identifiers thay vì payload dump.

### High — Cancellation không được truyền rõ vào body read

**Vấn đề:** Code không gắn body-read lifetime với `context.RequestAborted` theo API overload/runtime được dùng.

**Tại sao xảy ra:** Middleware coi logging như bước bắt buộc trước business processing.

**Ảnh hưởng production:** Client disconnect vẫn có thể khiến server tiếp tục làm diagnostic work không còn giá trị.

**Cách sửa:** Dùng cancellation-aware read API phù hợp target framework hoặc tránh body read. Diagnostic work phải tôn trọng request cancellation khi có thể.

### Medium — Completion log bị mất trên exception path

**Vấn đề:** Nếu downstream ném exception, đoạn log sau `_next` không chạy.

**Tại sao xảy ra:** Timing/completion logging không dùng `try/finally` hoặc exception telemetry riêng.

**Ảnh hưởng production:** Chính requests lỗi lại thiếu duration/status diagnostic, làm bias telemetry.

**Cách sửa:** Dùng `try/finally` cho timing metadata và để centralized exception handling/telemetry capture exception. Không duplicate sensitive exception data.

### Medium — Logging path/query semantics chưa có policy

**Vấn đề:** `Path` thường hữu ích nhưng route/query/user-derived identifiers có thể tạo cardinality hoặc privacy concerns tùy API.

**Tại sao xảy ra:** Logging contract chưa phân biệt route template với raw request target.

**Ảnh hưởng production:** Search/dashboard khó tổng hợp và có thể vô tình lưu identifiers nhạy cảm.

**Cách sửa:** Ưu tiên route name/template và approved identifiers; review query-string policy riêng.

### Low — Custom stopwatch logging có thể trùng platform telemetry

**Vấn đề:** Middleware tự ghi request duration trong khi ASP.NET Core/Application Insights thường đã có request telemetry.

**Tại sao xảy ra:** Observability design chưa xác định source of truth.

**Ảnh hưởng production:** Duplicate logs, ingestion volume và khó thống nhất metric.

**Cách sửa:** Dùng request telemetry/tracing làm nguồn chính; custom log chỉ bổ sung business context có giá trị.

## Phiên bản đề xuất

Một phương án đơn giản hơn là không capture body mặc định, chỉ ghi bounded metadata và correlation. Ví dụ:

```csharp
public sealed class RequestLoggingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestLoggingMiddleware> _logger;

    public RequestLoggingMiddleware(
        RequestDelegate next,
        ILogger<RequestLoggingMiddleware> logger)
    {
        _next = next;
        _logger = logger;
    }

    public async Task InvokeAsync(HttpContext context)
    {
        var started = Stopwatch.GetTimestamp();
        Exception? failure = null;

        try
        {
            await _next(context);
        }
        catch (Exception ex)
        {
            failure = ex;
            throw;
        }
        finally
        {
            var elapsed = Stopwatch.GetElapsedTime(started);
            var endpoint = context.GetEndpoint()?.DisplayName ?? "unmatched";

            _logger.LogInformation(
                "HTTP {Method} endpoint={Endpoint} status={StatusCode} elapsedMs={ElapsedMs} traceId={TraceId} failed={Failed}",
                context.Request.Method,
                endpoint,
                context.Response.StatusCode,
                elapsed.TotalMilliseconds,
                context.TraceIdentifier,
                failure is not null);
        }
    }
}
```

Nếu một số endpoint thật sự cần payload diagnostics, nên dùng một component riêng với policy rõ: chỉ content type được phép, giới hạn kích thước nhỏ, allowlist field, redaction trước khi ghi, sampling, retention ngắn và quyền truy cập hạn chế. Không bật raw-body logging toàn cục chỉ để xử lý một vài incident.

## Giải thích thiết kế sau khi sửa

Thiết kế mới chuyển từ “capture everything” sang “observe request lifecycle”. Request metadata, endpoint, status, duration, trace/correlation ID và dependency telemetry thường đủ để bắt đầu RCA. Khi cần dữ liệu domain, application có thể log selected identifiers ở nơi hiểu schema thay vì middleware mù với nội dung.

`try/finally` bảo đảm duration metadata được ghi cả khi downstream fail. Exception vẫn được rethrow để centralized exception handler/Application Insights xử lý. Không log exception object lần nữa nếu platform telemetry đã capture, tránh duplicate noise.

Quan trọng nhất là security boundary: secrets và raw sensitive payload không được coi là telemetry bình thường.

## Trade-offs

- Không có raw body làm một số incident khó tái hiện hơn, đổi lại giảm privacy/security risk đáng kể.
- Schema-aware redaction cần maintenance khi contract thay đổi.
- Sampling giảm volume nhưng có thể bỏ lỡ request hiếm; traces/correlation và targeted temporary diagnostics có thể bù lại.
- Bounded payload capture vẫn tạo allocation và cần security review; “bounded” không đồng nghĩa “safe”.

## Cách kiểm thử

1. **Security test:** gửi token, email và sensitive fields; xác nhận chúng không xuất hiện trong logs.
2. **Load test:** so sánh allocation rate, GC, working set và p95/p99 trước/sau middleware dưới payload nhỏ/lớn.
3. **Failure-path test:** downstream ném exception; completion metadata vẫn tồn tại và exception flow không bị nuốt.
4. **Cancellation test:** client abort request; xác nhận application không tiếp tục diagnostic body processing không cần thiết.
5. **Observability test:** một trace ID phải liên kết được request telemetry, dependency telemetry và approved business logs.

## Quan sát trong production

Theo dõi request rate, request/response size distribution, allocation rate, GC pause/Gen 2 collections, working set, CPU, p95/p99 latency và log ingestion volume. Trong Application Insights, so sánh duration theo endpoint và deployment version; dùng dependency spans để phân biệt middleware overhead với SQL/HTTP dependency latency.

Kibana/log backend nên có dashboard cho log volume/bytes theo service và event type, cùng alert nếu sensitive-data scanner phát hiện token pattern. Khi rollout fix, xác nhận memory/latency regression giảm mà khả năng correlation/RCA vẫn giữ được.

## Câu hỏi phỏng vấn mở rộng

1. Nếu security team cho phép body logging tạm thời cho một endpoint trong 30 phút, bạn thiết kế feature flag, redaction và audit như thế nào?
2. Nếu import endpoint cần request-body replay để điều tra lỗi, bạn có tiếp tục dùng application logs hay chọn storage/quy trình khác?
3. Khi nào custom request-duration log có giá trị hơn telemetry sẵn có của ASP.NET Core/Application Insights?

# Code Review Challenge 2 — Cosmos DB query quét nhiều partition và biến một tenant lớn thành hot partition

**Chủ đề:** Azure Cosmos DB, partition key, RU consumption, query patterns, multi-tenant data modeling, consistency, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 6–8 vấn đề

## Bối cảnh

Một multi-tenant activity service lưu audit/activity documents trong Azure Cosmos DB. Team chọn `/tenantId` làm partition key vì phần lớn queries ban đầu lọc theo tenant. Sau một năm, một enterprise tenant chiếm gần 40% write traffic và có lượng activity lớn hơn nhiều tenant khác.

Frontend có màn hình support cho phép tìm activity theo `userId` trong khoảng thời gian. API hiện nhận `userId` và query container mà không biết tenant. Production thấy RU consumption tăng mạnh vào giờ support sử dụng màn hình này; latency của cả workload tăng và tenant lớn thường gặp throttling hơn.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class ActivityRepository
{
    private readonly Container _container;

    public ActivityRepository(CosmosClient client)
    {
        _container = client.GetContainer("ActivityDb", "activities");
    }

    public async Task<List<ActivityDocument>> FindByUserAsync(
        string userId,
        DateTime fromUtc,
        DateTime toUtc,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c " +
            "WHERE c.userId = @userId " +
            "AND c.createdAt >= @from " +
            "AND c.createdAt < @to " +
            "ORDER BY c.createdAt DESC")
            .WithParameter("@userId", userId)
            .WithParameter("@from", fromUtc)
            .WithParameter("@to", toUtc);

        var iterator = _container.GetItemQueryIterator<ActivityDocument>(
            query,
            requestOptions: new QueryRequestOptions
            {
                MaxItemCount = 500
            });

        var results = new List<ActivityDocument>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            results.AddRange(page);
        }

        return results;
    }
}
```

Assumption của scenario: container hiện partition theo `/tenantId`; `userId` không globally unique và support user chỉ được phép xem tenants mà họ được authorize.

## Nhiệm vụ của ứng viên

1. Xác định correctness/security concern của query không có tenant context.
2. Phân tích partition-routing và RU/latency impact của query hiện tại.
3. Phân tích vì sao `/tenantId` có thể hợp lý lúc đầu nhưng gặp giới hạn khi một tenant trở nên quá lớn/hot.
4. Review unbounded result accumulation và pagination contract.
5. Đề xuất short-term remediation và các lựa chọn data-model/partition strategy dài hạn mà không mặc định migration toàn bộ.
6. Nêu tests cho authorization, pagination, skewed tenants và throttling/failure.
7. Nêu telemetry cần thu để quyết định có thực sự cần repartition/model mới hay không.

## Câu hỏi gợi mở

1. Nếu query không cung cấp partition key, Cosmos DB phải tìm dữ liệu ở phạm vi nào?
2. `userId` không globally unique ảnh hưởng correctness và authorization thế nào?
3. `MaxItemCount = 500` có giới hạn tổng số documents trả về không?
4. Hot tenant là vấn đề query, write distribution, partition-key cardinality hay có thể là nhiều yếu tố cùng lúc?
5. Trước khi đổi partition key, bạn cần đo những metric nào theo tenant/query shape?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **query không align với partition boundary và security boundary**.

### Gợi ý 2

Đừng nhảy thẳng tới “đổi partition key”. Tách short-term query/API correction khỏi long-term modeling decision, rồi dùng RU/throttling/storage/traffic evidence để chọn.

## Kết quả code review tham khảo

### Critical — API/query không mang tenant authorization boundary

**Vấn đề:** Method chỉ nhận `userId`; scenario xác định `userId` không globally unique và support principal chỉ được phép xem một tập tenants.

**Tại sao xảy ra:** Data lookup key không chứa security scope.

**Ảnh hưởng production:** Query có thể trả activity của user cùng ID ở tenant khác hoặc tạo BOLA/cross-tenant exposure nếu authorization được thực hiện không đúng ở layer khác.

**Cách sửa:** API phải resolve/validate tenant scope từ authorized context, không tin tenant tùy ý từ client. Repository query phải nhận tenant đã được authorize và dùng nó trong query/partition routing. Với support cross-tenant, authorization phải explicit và auditable.

### High — Query không cung cấp partition key nên trở thành cross-partition query

**Vấn đề:** Container partition theo `/tenantId`, nhưng query không lọc/routing theo tenant.

**Tại sao xảy ra:** Cosmos DB không thể định tuyến trực tiếp tới logical partition phù hợp chỉ từ `userId`.

**Ảnh hưởng production:** Fan-out/cross-partition work tăng RU và latency, đặc biệt khi container/partition count lớn.

**Cách sửa:** Sau khi tenant được authorize, thêm `tenantId` predicate và `QueryRequestOptions.PartitionKey` tương ứng. Thiết kế API để caller cung cấp business scope hợp lệ thay vì global scan.

### High — `/tenantId` có thể tạo hot logical workload với tenant skew lớn

**Vấn đề:** Một tenant chiếm tỷ trọng write/read rất cao.

**Tại sao xảy ra:** Partition key có distribution skew theo workload. Tuy nhiên cần phân biệt logical partition constraints, physical partition distribution và provisioned throughput mode trước khi kết luận chính xác bottleneck.

**Ảnh hưởng production:** Throttling/latency có thể tập trung ở key nóng và không được giải quyết chỉ bằng tăng tổng throughput nếu bottleneck nằm ở distribution của một hot key.

**Cách sửa:** Đo normalized RU consumption/throttling theo partition/key và traffic distribution. Nếu tenant thực sự vượt khả năng của single-key design, đánh giá hierarchical/composite bucketing strategy hoặc container/model mới phù hợp query patterns. Không migration chỉ dựa trên cảm giác.

### High — Method materialize toàn bộ kết quả

**Vấn đề:** `MaxItemCount = 500` chỉ ảnh hưởng page request, trong khi loop đọc tất cả pages vào `List`.

**Tại sao xảy ra:** Pagination ở SDK bị nhầm với bounded API result.

**Ảnh hưởng production:** Query khoảng thời gian lớn có thể tiêu thụ nhiều RU, memory và response payload; cancellation tới muộn vẫn đã tốn nhiều work.

**Cách sửa:** Expose bounded pagination với continuation token và page-size limit phù hợp. API contract phải giới hạn time range/result size nếu business cho phép.

### Medium — `SELECT *` đọc document rộng hơn nhu cầu

**Vấn đề:** Support list thường chỉ cần subset fields nhưng query lấy toàn document.

**Tại sao xảy ra:** Repository không phân biệt list projection với detail model.

**Ảnh hưởng production:** Payload/deserialization/network overhead tăng; RU impact cần đo theo actual document/index/query behavior thay vì suy đoán tuyệt đối.

**Cách sửa:** Project các fields cần thiết cho list view và đo RU/latency trước/sau.

### Medium — Không expose request charge/throttling diagnostics

**Vấn đề:** Code bỏ qua metadata trên response pages.

**Tại sao xảy ra:** Repository chỉ trả data, không có observability path cho RU/query diagnostics.

**Ảnh hưởng production:** Team thấy tổng RU tăng nhưng khó quy về query shape/tenant cụ thể.

**Cách sửa:** Ghi metric request charge, latency, continuation/page count và throttling/retry diagnostics với safe dimensions; tránh log raw activity data.

### Medium — Query contract cho time range không có guardrail

**Vấn đề:** Caller có thể yêu cầu khoảng thời gian rất lớn.

**Tại sao xảy ra:** Repository/API không enforce business limit hoặc pagination-first behavior.

**Ảnh hưởng production:** Một support action có thể tạo expensive query kéo dài và memory pressure.

**Cách sửa:** Validate range/page size theo requirement; nếu cần historical bulk export thì dùng workflow khác thay vì biến interactive search thành bulk scan.

## Phiên bản đề xuất

Short-term fix nên align security scope, partition routing và pagination trước khi thay data model:

```csharp
public sealed record ActivityPage(
    IReadOnlyList<ActivityListItem> Items,
    string? ContinuationToken,
    double RequestCharge);

public async Task<ActivityPage> FindByUserAsync(
    string authorizedTenantId,
    string userId,
    DateTime fromUtc,
    DateTime toUtc,
    int pageSize,
    string? continuationToken,
    CancellationToken cancellationToken)
{
    pageSize = Math.Clamp(pageSize, 1, 100);

    var query = new QueryDefinition(
        "SELECT c.id, c.userId, c.type, c.createdAt " +
        "FROM c " +
        "WHERE c.tenantId = @tenantId " +
        "AND c.userId = @userId " +
        "AND c.createdAt >= @from " +
        "AND c.createdAt < @to " +
        "ORDER BY c.createdAt DESC")
        .WithParameter("@tenantId", authorizedTenantId)
        .WithParameter("@userId", userId)
        .WithParameter("@from", fromUtc)
        .WithParameter("@to", toUtc);

    var iterator = _container.GetItemQueryIterator<ActivityListItem>(
        query,
        continuationToken,
        new QueryRequestOptions
        {
            PartitionKey = new PartitionKey(authorizedTenantId),
            MaxItemCount = pageSize
        });

    if (!iterator.HasMoreResults)
        return new ActivityPage([], null, 0);

    var page = await iterator.ReadNextAsync(cancellationToken);

    return new ActivityPage(
        page.Resource.ToList(),
        page.ContinuationToken,
        page.RequestCharge);
}
```

`authorizedTenantId` phải đến từ authorization layer đã xác minh principal có quyền với tenant; repository signature không tự chứng minh authorization. API cũng nên validate `fromUtc/toUtc` và continuation token handling theo contract.

Nếu telemetry chứng minh tenant skew là bottleneck thực sự, long-term options có thể gồm bucketing key như tenant + time/hash dimension, hierarchical partitioning khi phù hợp với current platform capability, hoặc tách workload/container. Mỗi lựa chọn phải được kiểm tra với dominant read/write patterns; partition key mới giúp distribution nhưng có thể làm query khác phức tạp hơn.

## Giải thích thiết kế sau khi sửa

Short-term solution giải quyết hai vấn đề có bằng chứng rõ nhất: security scope và fan-out query. Khi biết tenant, request có thể route đúng partition boundary hiện tại. Continuation token biến interactive API thành bounded work thay vì đọc toàn bộ lịch sử vào memory.

Không tự động repartition. Một tenant chiếm 40% traffic là tín hiệu cần điều tra, chưa đủ để chọn key mới. Cần xem RU distribution, throttled requests, logical partition size/growth, dominant query shapes và write distribution. Data modeling của Cosmos DB phải bắt đầu từ access patterns và partition behavior, không chỉ từ entity schema.

## Trade-offs

- Bắt buộc tenant scope làm API kém tiện cho “global support search”, nhưng đó cũng là security và cost boundary có giá trị.
- Cross-tenant support search có thể cần query fan-out có kiểm soát hoặc một secondary projection/search index riêng; thêm projection đồng nghĩa eventual consistency và sync complexity.
- Bucketing một tenant lớn cải thiện distribution nhưng queries theo tenant có thể phải fan-out qua buckets.
- Container migration/backfill có operational cost và dual-write/consistency concerns; chỉ nên làm khi telemetry chứng minh current key không còn đáp ứng.
- Projection giảm payload nhưng tạo DTO/query maintenance.

## Cách kiểm thử

1. **Authorization test:** cùng `userId` tồn tại ở hai tenants; principal chỉ được thấy tenant đã authorize.
2. **Pagination integration test:** dataset nhiều pages; mỗi call trả bounded page và continuation không mất/trùng item theo ordering assumptions của contract.
3. **Skew/load test:** mô phỏng một tenant nóng và nhiều tenant nhỏ; đo RU, latency và throttling theo partition/query shape.
4. **Failure-path test:** inject 429/transient failure theo SDK retry behavior; xác nhận API timeout/cancellation và telemetry không che dependency pressure.
5. **Cost regression test:** so sánh request charge của cross-partition query cũ với tenant-routed query mới trên representative dataset.

## Quan sát trong production

Theo dõi request charge per operation, query latency, page count, result count, 429/throttling, retry latency và normalized RU consumption theo partition-related dimensions mà platform cung cấp. Application Insights nên correlate API request với Cosmos dependency telemetry và tenant identifier dạng approved/non-sensitive dimension.

Dashboard cần phân biệt interactive search với background/bulk workloads. Với tenant lớn, theo dõi traffic share, RU share, throttling share và data growth theo thời gian. Chỉ khi evidence cho thấy hot-key distribution là structural bottleneck mới tiến tới partition-model migration.

## Câu hỏi phỏng vấn mở rộng

1. Nếu support thật sự cần tìm một `userId` trên mọi tenant, bạn sẽ thiết kế search path nào để không biến primary container thành global scan?
2. Nếu đổi partition key sang `tenantId + month`, read/write trade-offs và migration strategy sẽ thay đổi thế nào?
3. Khi nào bạn chọn một secondary Elasticsearch/search projection thay vì tiếp tục tối ưu Cosmos DB query trực tiếp?

## Kiến thức trọng tâm

Challenge 1 nhấn mạnh rằng observability không được phá security hoặc performance của request path. Logging tốt ưu tiên correlation, bounded metadata và schema-aware safe fields; raw secrets/payload không phải diagnostic mặc định.

- **Measure RU/latency/throttling before repartitioning**; data-model migration là quyết định operational lớn.
- Tách short-term containment khỏi long-term architecture change.
