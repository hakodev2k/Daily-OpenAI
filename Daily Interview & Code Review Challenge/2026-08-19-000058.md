# Code Review Challenge 1 — Hangfire xử lý offboarding bị chạy trùng

**Chủ đề:** Background jobs, concurrency, idempotency, EF Core  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý các cấu hình offboarding đã hết hạn. Job chạy trên nhiều application instance. Mỗi record cần reset trạng thái trong database rồi gọi một external mail service. Production thỉnh thoảng ghi nhận cùng mailbox bị reset/gọi external service hai lần; đôi lúc DB đã đổi trạng thái nhưng external operation thất bại. Traffic không lớn nhưng job có thể overlap khi một lần chạy kéo dài.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IMailAdminClient _mail;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IMailAdminClient mail,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _mail = mail;
        _logger = logger;
    }

    public async Task ResetExpiredAsync()
    {
        var now = DateTime.UtcNow;
        var configs = await _db.EmployeeOffboardingMailConfigs
            .Where(x => x.IsActive && x.EndTime <= now)
            .ToListAsync();

        foreach (var config in configs)
        {
            try
            {
                await _mail.ResetMailboxAsync(config.EmployeeEmail);

                config.IsActive = false;
                config.ResetAt = DateTime.UtcNow;

                await _db.SaveChangesAsync();

                _logger.LogInformation(
                    "Reset mailbox {Email} successfully",
                    config.EmployeeEmail);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Reset mailbox {Email} failed",
                    config.EmployeeEmail);
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định lỗi correctness.
2. Tìm rủi ro concurrency/retry/idempotency.
3. Giải thích tác động production.
4. Xếp ưu tiên vấn đề.
5. Đề xuất implementation tốt hơn.
6. Nêu cách kiểm thử.
7. Đề xuất logs, traces và metrics.

## Câu hỏi gợi mở

- Hai Hangfire worker đọc cùng record thì điều gì xảy ra?
- External call thành công nhưng `SaveChangesAsync` thất bại thì sao?
- Hangfire retry có thể làm thay đổi semantics của operation thế nào?
- Transaction DB có thể làm cho external API call atomic cùng database không?
- Điều kiện nào thực sự đảm bảo một record chỉ được claim bởi một worker?

## Gợi ý

### Gợi ý 1

Hãy phân biệt **exactly-once execution** với **idempotent effect**.

### Gợi ý 2

`SELECT → external side effect → UPDATE` không tạo ra một atomic operation khi nhiều worker cùng chạy.

## Kết quả code review tham khảo

### 1. Race condition khi claim record — Critical

**Problem:** nhiều worker có thể cùng query được `IsActive = true` trước khi worker nào update DB.  
**Why:** read và state transition không được bảo vệ bởi concurrency control.  
**Impact:** external mailbox operation bị gọi nhiều lần.  
**Fix:** claim record bằng atomic conditional update/state machine, optimistic concurrency hoặc database locking phù hợp.

### 2. External side effect và DB update không atomic — Critical

**Problem:** mail reset thành công nhưng DB save thất bại.  
**Impact:** retry thấy record vẫn active và gọi external service lần nữa.  
**Fix:** thiết kế operation idempotent; lưu durable processing state/idempotency key. Nếu cần reliability cao hơn, dùng state machine/outbox-style workflow thay vì giả định distributed transaction.

### 3. Không có idempotency contract — High

`ResetMailboxAsync` phải an toàn khi được gọi lại hoặc client phải truyền operation key để duplicate request không tạo thêm side effect.

### 4. Nuốt exception làm job có vẻ thành công — High

Catch từng record rồi không rethrow khiến scheduler không biết toàn batch có failure. Cần trạng thái retry riêng cho record hoặc tổng hợp failure theo semantics mong muốn.

### 5. Không truyền cancellation token — Medium

Query, save và external call không phản ứng với shutdown/cancellation nếu API hỗ trợ token.

### 6. Load toàn bộ record vào memory — Medium

Backlog lớn sẽ tăng memory và kéo dài DbContext lifetime. Nên xử lý theo batch có giới hạn.

### 7. Một DbContext tracking nhiều entity suốt batch — Medium

Batch dài làm change tracker phình lên; failure/state của một entity cũng khó cô lập. Scope theo batch hoặc item có thể phù hợp hơn.

### 8. Observability chưa đủ — Medium

Log chỉ email và success/failure; thiếu operation id, attempt, latency, claimed count, retry count và trạng thái chuyển đổi.

## Phiên bản code đề xuất

Ví dụ dưới đây dùng state machine + optimistic claim. Việc claim thực tế nên được triển khai bằng conditional update phù hợp với SQL Server/PostgreSQL.

```csharp
public sealed class OffboardingJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IMailAdminClient _mail;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IMailAdminClient mail,
        ILogger<OffboardingJob> logger)
    {
        _dbFactory = dbFactory;
        _mail = mail;
        _logger = logger;
    }

    public async Task ResetExpiredAsync(CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var ids = await db.EmployeeOffboardingMailConfigs
            .AsNoTracking()
            .Where(x => x.Status == ResetStatus.Pending && x.EndTime <= DateTime.UtcNow)
            .OrderBy(x => x.Id)
            .Select(x => x.Id)
            .Take(100)
            .ToListAsync(ct);

        foreach (var id in ids)
        {
            ct.ThrowIfCancellationRequested();

            var claimed = await db.EmployeeOffboardingMailConfigs
                .Where(x => x.Id == id && x.Status == ResetStatus.Pending)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, ResetStatus.Processing)
                    .SetProperty(x => x.ProcessingStartedAt, DateTime.UtcNow), ct);

            if (claimed != 1)
                continue;

            var config = await db.EmployeeOffboardingMailConfigs
                .AsNoTracking()
                .SingleAsync(x => x.Id == id, ct);

            try
            {
                var operationId = $"offboarding-reset:{id}";
                await _mail.ResetMailboxAsync(config.EmployeeEmail, operationId, ct);

                await db.EmployeeOffboardingMailConfigs
                    .Where(x => x.Id == id && x.Status == ResetStatus.Processing)
                    .ExecuteUpdateAsync(s => s
                        .SetProperty(x => x.Status, ResetStatus.Completed)
                        .SetProperty(x => x.ResetAt, DateTime.UtcNow), ct);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Reset failed for config {ConfigId}", id);

                await db.EmployeeOffboardingMailConfigs
                    .Where(x => x.Id == id && x.Status == ResetStatus.Processing)
                    .ExecuteUpdateAsync(s => s
                        .SetProperty(x => x.Status, ResetStatus.Pending), ct);

                throw;
            }
        }
    }
}
```

Điểm quan trọng: atomic claim ngăn hai worker cùng sở hữu record tại cùng thời điểm, nhưng **không tự giải quyết crash sau external success và trước DB completion**. Idempotency ở external boundary hoặc reconciliation vẫn cần thiết.

## Trade-offs

State machine tăng schema và logic recovery nhưng làm trạng thái vận hành rõ ràng. Distributed lock có thể giảm overlap nhưng không thay thế idempotency khi process crash. Nếu external API không hỗ trợ idempotency, có thể cần reconciliation bằng cách đọc trạng thái mailbox trước khi retry.

## Cách kiểm thử

1. Chạy 20 worker đồng thời trên cùng một expired record và xác nhận chỉ một worker claim được.
2. Giả lập external call thành công rồi DB update lỗi; retry không được tạo side effect sai.
3. Kill process ở trạng thái `Processing`; watchdog/recovery phải đưa record stale về trạng thái retry hợp lệ.
4. Load test backlog lớn và kiểm tra memory/query latency.
5. Kiểm tra cancellation giữa các batch và trong external call.

## Quan sát trong production

Theo dõi `pending/processing/completed/failed`, processing age, retry count, duplicate-operation count, external latency/error rate và batch duration. Trace nên mang `configId`/operation id xuyên qua DB và external request; tránh log dữ liệu nhạy cảm không cần thiết.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `[DisableConcurrentExecution]` một mình chưa đủ để bảo đảm exactly-once side effect?
2. Nếu external API không hỗ trợ idempotency key, bạn thiết kế reconciliation thế nào?
3. Khi nào bạn chọn queue/outbox thay vì Hangfire polling trực tiếp DB?

# Code Review Challenge 2 — API tìm kiếm audit log có SQL injection và rò rỉ dữ liệu

**Chủ đề:** SQL correctness/performance, authorization, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Một endpoint nội bộ cho phép support tìm audit log theo tenant và keyword. Sau khi mở endpoint cho nhiều support team, database CPU tăng mạnh. Security review cũng phát hiện một user có thể truy vấn dữ liệu tenant khác nếu biết `tenantId`.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        int page = 1)
    {
        var sql = $@"
            SELECT *
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND (Message LIKE '%{keyword}%'
                   OR Payload LIKE '%{keyword}%')
            ORDER BY CreatedAt DESC";

        _logger.LogInformation("Audit query: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .ToListAsync();

        return Ok(rows
            .Skip((page - 1) * 100)
            .Take(100));
    }
}
```

## Nhiệm vụ của ứng viên

1. Tìm correctness/security/performance problems.
2. Giải thích production impact.
3. Xếp ưu tiên.
4. Đề xuất corrected implementation.
5. Nêu test strategy.
6. Đề xuất telemetry phù hợp.

## Câu hỏi gợi mở

- `[Authorize]` có đồng nghĩa user được truy cập mọi tenant không?
- Input nào đang đi trực tiếp vào SQL text?
- Pagination đang xảy ra ở database hay application?
- `LIKE '%keyword%'` ảnh hưởng khả năng dùng index thế nào?
- Có nên trả nguyên entity `AuditLog` ra client không?

## Gợi ý

### Gợi ý 1

Authentication, authorization và SQL parameterization là ba vấn đề độc lập.

### Gợi ý 2

Hãy kiểm tra vị trí thực thi của `ToListAsync`, `Skip` và `Take`.

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

---

## Kết quả code review tham khảo

### 1. SQL injection — Critical

`tenantId` và `keyword` được interpolate vào `FromSqlRaw`. Attacker có thể thay đổi câu SQL. Dùng LINQ parameterized query hoặc parameter APIs; không concatenate user input vào SQL.

### 2. Broken tenant authorization / IDOR — Critical

`[Authorize]` chỉ yêu cầu authenticated principal; code không chứng minh principal được phép đọc `tenantId` được yêu cầu. Tenant scope nên được derive/validate từ claims hoặc authorization policy/service.

### 3. Có thể expose sensitive payload — High

`SELECT *` + trả entity trực tiếp có thể lộ token, PII, request body hoặc internal metadata nếu entity chứa chúng. Dùng explicit DTO projection/redaction.

### 4. Pagination sau materialization — High

`ToListAsync()` tải toàn bộ matching rows trước rồi mới `Skip/Take` trong memory. Đưa pagination vào IQueryable trước materialization.

### 5. Unbounded wildcard search — High

`%keyword%` trên Message/Payload có thể gây scan lớn. Cần giới hạn keyword, pagination, timeout và cân nhắc full-text/search technology tùy workload.

### 6. Log nguyên SQL chứa user input/payload search — Medium

Có thể tạo log injection/noise và lưu dữ liệu nhạy cảm. Log structured metadata thay vì raw SQL/user-controlled content.

### 7. Page không validate — Medium

`page <= 0` tạo semantics sai hoặc exception tùy phép tính/provider. Bound page/pageSize.

### 8. Không truyền cancellation token — Low/Medium

Client disconnect không hủy DB work. Truyền `HttpContext.RequestAborted`.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "AuditReader")]
[HttpGet("search")]
public async Task<ActionResult<IReadOnlyList<AuditLogDto>>> Search(
    string tenantId,
    string? keyword,
    int page = 1,
    CancellationToken ct = default)
{
    if (page < 1)
        return BadRequest("page must be >= 1");

    if (!await UserCanAccessTenantAsync(User, tenantId, ct))
        return Forbid();

    var normalized = keyword?.Trim();
    if (normalized?.Length > 100)
        return BadRequest("keyword is too long");

    IQueryable<AuditLog> query = _db.AuditLogs
        .AsNoTracking()
        .Where(x => x.TenantId == tenantId);

    if (!string.IsNullOrWhiteSpace(normalized))
    {
        query = query.Where(x =>
            x.Message.Contains(normalized) ||
            x.Payload.Contains(normalized));
    }

    var rows = await query
        .OrderByDescending(x => x.CreatedAt)
        .ThenByDescending(x => x.Id)
        .Skip((page - 1) * 100)
        .Take(100)
        .Select(x => new AuditLogDto(
            x.Id,
            x.CreatedAt,
            x.Action,
            x.Message))
        .ToListAsync(ct);

    return Ok(rows);
}
```

LINQ ở đây giúp provider parameterize values, nhưng `Contains` vẫn có thể tạo search pattern không phù hợp cho dataset rất lớn. Nếu audit search là chức năng quan trọng ở quy mô lớn, cần benchmark query plan và cân nhắc full-text/search index thay vì mặc định dựa vào wildcard search.

## Trade-offs

Offset pagination đơn giản nhưng page sâu ngày càng đắt và dữ liệu mới chèn vào có thể làm page dịch chuyển. Keyset pagination theo `(CreatedAt, Id)` phù hợp hơn cho timeline lớn. Full-text/search engine tăng vận hành và consistency complexity nhưng cải thiện search workload thực sự lớn.

## Cách kiểm thử

1. Security test với `tenantId` thuộc tenant khác phải trả 403 và không leak existence/data.
2. Injection payload trong tenant/keyword phải chỉ được xử lý như data.
3. Integration test xác nhận generated query pagination tại DB và chỉ trả field DTO cho phép.
4. Load test keyword phổ biến trên dataset lớn; xem execution plan, reads, CPU và latency.
5. Cancellation test: hủy HTTP request phải propagate xuống database operation.

## Quan sát trong production

Theo dõi p50/p95/p99 latency, rows scanned/returned nếu DB telemetry cho phép, timeout rate, DB CPU, authorization denial count và page depth. Không ghi raw Payload hoặc keyword nhạy cảm vào log. Trace endpoint → EF/DB để xác định thời gian nằm ở authorization, query hay serialization.

## Câu hỏi phỏng vấn mở rộng

1. Keyset pagination cho `(CreatedAt, Id)` sẽ được thiết kế thế nào?
2. Nếu business bắt buộc search substring trong JSON payload hàng trăm triệu record, bạn chọn giải pháp nào và vì sao?
3. Global query filter theo tenant có đủ thay thế authorization policy không?
