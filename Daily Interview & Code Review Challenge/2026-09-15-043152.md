# Code Review Challenge 1 — Singleton giữ một scope sống mãi: production bắt đầu lỗi `DbContext` ngẫu nhiên khi traffic tăng

**Chủ đề:** C#/.NET, ASP.NET Core DI lifetime, EF Core, concurrency, resource lifetime, reliability, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API có service dùng để ghi audit và cập nhật trạng thái xử lý sau mỗi request. Vì service này được gọi rất nhiều nơi, team đăng ký nó dưới dạng singleton để “giảm số object phải tạo”.

`AuditWriter` cần dùng EF Core `AppDbContext`, vốn được đăng ký theo scoped lifetime. Developer tránh inject trực tiếp scoped service vào singleton bằng cách inject `IServiceScopeFactory`, tạo một scope trong constructor rồi giữ lại `AppDbContext` để tái sử dụng.

Ở môi trường dev với ít traffic hệ thống có vẻ ổn. Sau khi production tăng tải, team thấy:

- thỉnh thoảng xuất hiện `InvalidOperationException` liên quan đến nhiều operation cùng dùng một `DbContext`;
- đôi khi một audit record chứa dữ liệu từ request khác hoặc trạng thái entity không như mong đợi;
- memory của process tăng dần trong các khoảng traffic cao;
- một số request bị timeout dù SQL latency không tăng tương ứng;
- restart application làm symptom biến mất tạm thời;
- lỗi khó tái hiện bằng unit test tuần tự.

Code hiện tại:

## Đoạn code cần review

```csharp
public sealed class AuditWriter : IAuditWriter, IDisposable
{
    private readonly IServiceScope _scope;
    private readonly AppDbContext _db;
    private readonly ILogger<AuditWriter> _logger;

    public AuditWriter(
        IServiceScopeFactory scopeFactory,
        ILogger<AuditWriter> logger)
    {
        _scope = scopeFactory.CreateScope();
        _db = _scope.ServiceProvider.GetRequiredService<AppDbContext>();
        _logger = logger;
    }

    public async Task WriteAsync(
        Guid userId,
        string action,
        string? details,
        CancellationToken cancellationToken)
    {
        var audit = new AuditEntry
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            Action = action,
            Details = details,
            CreatedAt = DateTimeOffset.UtcNow
        };

        _db.AuditEntries.Add(audit);

        var user = await _db.Users
            .SingleAsync(x => x.Id == userId, cancellationToken);

        user.LastActivityAt = DateTimeOffset.UtcNow;

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Audit {AuditId} written for user {UserId}",
            audit.Id,
            userId);
    }

    public void Dispose()
    {
        _scope.Dispose();
    }
}

public static class ServiceRegistration
{
    public static IServiceCollection AddApplicationServices(
        this IServiceCollection services)
    {
        services.AddDbContext<AppDbContext>();
        services.AddSingleton<IAuditWriter, AuditWriter>();
        return services;
    }
}
```

## Câu hỏi gợi mở

1. Scope được tạo trong constructor của một singleton sẽ sống bao lâu?
2. `DbContext` có được thiết kế để nhiều request thực hiện operations đồng thời trên cùng instance hay không?
3. Change tracker sẽ giữ những entity nào nếu cùng một context được tái sử dụng qua hàng nghìn requests?

5. Việc “giảm số object phải tạo” có đáng đánh đổi request isolation và lifetime semantics không?

## Gợi ý

### Gợi ý 1

Hãy theo dõi lifetime theo chuỗi: **singleton → manually-created scope → scoped `DbContext`**. Scope không tự trở thành per-request chỉ vì nó được tạo bằng `IServiceScopeFactory`.

### Gợi ý 2

Đừng chỉ tìm exception. Hãy xem cả **shared mutable state trong change tracker**, lifetime của database context và failure isolation giữa các requests.

## Kết quả code review tham khảo

### Critical — Một `DbContext` bị chia sẻ đồng thời giữa nhiều requests

**Vấn đề:**  
`AuditWriter` là singleton và giữ `_db` trong toàn bộ lifetime của application. Mọi request gọi `WriteAsync` đều sử dụng cùng một `AppDbContext`.

**Tại sao xảy ra:**  
EF Core `DbContext` đại diện cho một unit-of-work có mutable state như change tracker. Nó không được thiết kế để nhiều operations chạy đồng thời trên cùng một instance.

**Ảnh hưởng production:**  
Khi nhiều requests chạy cùng lúc có thể xuất hiện concurrency exceptions, state corruption ở mức application tracking, request timeout và hành vi khó dự đoán. Lỗi thường chỉ lộ ra dưới tải vì dev/test tuần tự không tạo đủ overlap.

**Cách sửa:**  
Không giữ `DbContext` trong singleton. Tốt nhất để service sử dụng `DbContext` có scoped lifetime và bản thân service cũng scoped nếu nó thuộc request unit-of-work. Nếu singleton/background component thực sự cần thực hiện database operation độc lập, tạo **một scope mới cho mỗi unit-of-work**, dùng xong rồi dispose.

### High — Scope được tạo một lần rồi sống gần như suốt process

**Vấn đề:**  
`_scope = scopeFactory.CreateScope()` chạy trong constructor singleton, nên scope này không phải request scope.

**Tại sao xảy ra:**  
Lifetime của scope do code tạo được quyết định bởi nơi code dispose nó. Ở đây scope chỉ bị dispose khi singleton bị dispose, thường gần application shutdown.

**Ả hưởng production:**  
Mọi scoped dependency được resolve từ scope đó có thể sống rất lâu ngoài ý định ban đầu, kéo theo retained state/resources và phá isolation giữa operations.

**Cách sửa:**  
Nếu cần manual scope, tạo scope bên trong từng operation:

```csharp
await using var scope = _scopeFactory.CreateAsyncScope();
var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
```

Sau đó dispose ngay khi unit-of-work hoàn tất.

### High — Change tracker tích lũy state qua nhiều request

**Vấn đề:**  
Context lâu sống tiếp tục track entities được query/add/update qua nhiều lần gọi.

**Tại sao xảy ra:**  
Một `DbContext` thông thường giữ tracking state cho tới khi context bị dispose hoặc state được chủ động clear/detach.

**Ảnh hưởng production:**  
Memory có thể tăng, entity lookup/tracking trở nên phức tạp hơn, và cùng một entity có thể tồn tại trong context từ request trước. Điều này làm behavior phụ thuộc lịch sử sử dụng của process.

**Cách sửa:**  
Giữ context ngắn sống theo unit-of-work. Không dùng `ChangeTracker.Clear()` như cách chữa một lifetime design sai; nó không giải quyết thread safety hoặc failure isolation.

### High — Failure/cancellation có thể để lại context ở trạng thái không phù hợp cho request sau

**Vấn đề:**  
Nếu query hoặc `SaveChangesAsync` fail/cancel, cùng context vẫn được giữ lại và dùng cho lần gọi tiếp theo.

**Tại sao xảy ra:**  
Tracked changes đã được tạo trước failure không tự biến thành một unit-of-work hoàn toàn mới. Context tiếp tục tồn tại với state hiện tại.

**Ảnh hưởng production:**  
Request sau có thể quan sát/trộn với tracked state từ operation thất bại, hoặc lại cố persist các changes không còn đúng business intent.

**Cách sửa:**  
Mỗi operation nên có context/unit-of-work riêng. Khi operation fail, dispose context đó và bắt đầu unit-of-work mới cho request khác.

### Medium — `AuditWriter` đang gộp hai trách nhiệm có transaction semantics chưa được làm rõ

**Vấn đề:**  
Method vừa ghi audit vừa cập nhật `User.LastActivityAt` trong cùng `SaveChangesAsync`, nhưng code không nói rõ hai thay đổi có bắt buộc atomic hay không.

**Tại sao xảy ra:**  
Thiết kế data write đang được quyết định ngầm bởi implementation thay vì business requirement.

**Ảnh hưởng production:**  
Sau này nếu audit chuyển sang storage khác hoặc retry riêng, team có thể vô tình phá semantics mà không biết.

**Cách sửa:**  
Làm rõ transaction boundary. Nếu hai thay đổi phải atomic và cùng database/context thì một scoped unit-of-work có thể phù hợp. Nếu audit chỉ là telemetry/event, cân nhắc boundary khác nhưng phải thiết kế failure/retry rõ ràng.

### Medium — Logging chỉ ghi success, thiếu dữ liệu để chẩn đoán contention/failure

**Vấn đề:**  
Log hiện tại chỉ có message sau khi save thành công.

**Tại sao xảy ra:**  
Không có measurement về latency database operation, exception type, cancellation, concurrent request count hoặc save failure.

**Ảnh hưởng production:**  
Khi lỗi ngẫu nhiên xảy ra, team khó correlate request, user, operation duration và database dependency.

**Cách sửa:**  
Dùng structured telemetry với correlation/trace ID, operation duration, success/failure/cancellation và dependency spans. Không log `details` nếu có khả năng chứa dữ liệu nhạy cảm.

### Low — Tối ưu allocation sai trọng tâm

**Vấn đề:**  
Singleton được chọn để “giảm object allocation” dù service chứa stateful scoped dependency.

**Tại sao xảy ra:**  
Optimization được thực hiện trước khi có bằng chứng allocation/service construction là bottleneck.

**Ảnh hưởng production:**  
Một micro-optimization chưa được đo lường tạo ra correctness risk lớn hơn nhiều chi phí khởi tạo object.

**Cách sửa:**  
Ưu tiên lifetime đúng trước. Chỉ tối ưu object allocation sau khi profiling chứng minh đó là bottleneck đáng kể.

## Phiên bản đề xuất

Nếu operation này thuộc request unit-of-work, thiết kế đơn giản nhất là để cả writer và context đều scoped:

```csharp
public sealed class AuditWriter : IAuditWriter
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditWriter> _logger;

    public AuditWriter(
        AppDbContext db,
        ILogger<AuditWriter> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task WriteAsync(
        Guid userId,
        string action,
        string? details,
        CancellationToken cancellationToken)
    {
        var now = DateTimeOffset.UtcNow;

        var user = await _db.Users
            .SingleAsync(x => x.Id == userId, cancellationToken);

        var audit = new AuditEntry
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            Action = action,
            Details = details,
            CreatedAt = now
        };

        user.LastActivityAt = now;
        _db.AuditEntries.Add(audit);

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Audit {AuditId} written for user {UserId}",
            audit.Id,
            userId);
    }
}

public static class ServiceRegistration
{
    public static IServiceCollection AddApplicationServices(
        this IServiceCollection services)
    {
        services.AddDbContext<AppDbContext>();
        services.AddScoped<IAuditWriter, AuditWriter>();
        return services;
    }
}
```

Nếu writer thực sự phải là singleton, ví dụ được dùng từ một singleton background coordinator, singleton chỉ nên giữ `IServiceScopeFactory` và tạo một scope mới cho **mỗi operation**:

```csharp
public sealed class AuditWriter : IAuditWriter
{
    private readonly IServiceScopeFactory _scopeFactory;

    public AuditWriter(IServiceScopeFactory scopeFactory)
    {
        _scopeFactory = scopeFactory;
    }

    public async Task WriteAsync(
        Guid userId,
        string action,
        string? details,
        CancellationToken cancellationToken)
    {
        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var now = DateTimeOffset.UtcNow;
        var user = await db.Users
            .SingleAsync(x => x.Id == userId, cancellationToken);

        user.LastActivityAt = now;
        db.AuditEntries.Add(new AuditEntry
        {
            Id = Guid.NewGuid(),
            UserId = userId,
            Action = action,
            Details = details,
            CreatedAt = now
        });

        await db.SaveChangesAsync(cancellationToken);
    }
}
```

Hai phương án không hoàn toàn tương đương: phương án scoped có thể tham gia request unit-of-work hiện có; phương án tạo scope riêng tạo transaction/unit-of-work độc lập. Phải chọn theo requirement chứ không chỉ theo DI convenience.

## Giải thích thiết kế sau khi sửa

Mục tiêu chính là khôi phục **lifetime alignment** và **operation isolation**.

Một request-scoped `DbContext` phù hợp khi các repository/services trong request cần chia sẻ cùng unit-of-work. Mỗi request có tracking state riêng, không có cross-request concurrent access vào cùng context, và context được dispose khi scope request kết thúc.

Nếu một singleton cần database access, nó không được capture scoped instance. Nó giữ factory/scope factory và tạo context/scope ngắn sống cho từng logical operation. Khi operation fail, context đó bị dispose; request/job tiếp theo bắt đầu với tracking state sạch.

Không nên thêm một global `lock` quanh `_db` để “fix thread safety”. Lock có thể serialise mọi request, phá throughput và vẫn giữ context lâu sống cùng stale tracking state. Nó che symptom chứ không sửa lifetime boundary.

## Trade-offs

- **Scoped writer + scoped context:** đơn giản, tự nhiên cho HTTP request và có thể chia sẻ transaction với các request services khác; nhưng không thể inject trực tiếp vào singleton.
- **Singleton + scope-per-operation:** phù hợp cho coordinator/background component; đổi lại mỗi call là unit-of-work riêng và transaction sharing phải được thiết kế rõ.
- **`IDbContextFactory<TContext>`:** có thể phù hợp khi cần tạo context độc lập ngoài request scope; vẫn phải dispose mỗi instance và hiểu transaction boundary.
- **Global lock:** giảm concurrent access nhưng làm throughput tệ, giữ lifetime sai và không giải quyết retained tracking state; không nên là durable fix.

## Cách kiểm thử

1. **Concurrency integration test:** chạy hàng chục/hàng trăm `WriteAsync` đồng thời cho nhiều users và xác minh không có cross-operation exception hoặc missing audit rows.
2. **Failure isolation test:** ép một database operation fail/cancel, sau đó chạy operation mới và xác minh state trước không bị persist ngoài ý muốn.
3. **Transaction behavior test:** xác minh audit và `LastActivityAt` commit/rollback đúng theo business requirement.
4. **Load test:** đo p95/p99, DB connection usage, allocation/memory và error rate trước/sau fix ở concurrency gần production.
5. **Sensitive-data logging test:** xác minh telemetry có correlation cần thiết nhưng không ghi `details` hoặc secret/PII ngoài policy.

## Quan sát trong production

Theo dõi tối thiểu:

- request rate và concurrent requests gọi audit path;
- p50/p95/p99 của `WriteAsync` và `SaveChangesAsync`;
- EF Core/database dependency duration và exception rate;
- số lỗi concurrency/invalid operation;
- DB connection pool usage/waits;
- process memory, GC metrics và allocation trend;
- cancellation/timeout rate;
- trace/correlation ID để nối request → audit write → SQL dependency.

Một fix tốt phải làm error rate về mức kỳ vọng **mà không** đổi concurrency bug thành serialization bottleneck.

# Code Review Challenge 2 — Playwright pass khi chạy local nhưng flaky trên CI vì test data bị chia sẻ giữa parallel workers

**Chủ đề:** Playwright, TypeScript, E2E testing, parallelism, test isolation, CI reliability, diagnostics  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút

## Bối cảnh

Một portal nội bộ dùng React frontend và ASP.NET Core API. Team có suite Playwright chạy trên CI cho workflow quản lý employee profile.

Để giảm thời gian pipeline, cấu hình CI chạy nhiều Playwright workers song song. Local thường chạy một worker nên gần như luôn pass.

Sau khi bật parallelism, suite bắt đầu có các symptom:

- cùng một commit có lúc pass, lúc fail;
- retry thường làm test xanh ở lần thứ hai;
- failure phổ biến là không tìm thấy employee, status không đúng, hoặc locator thấy nhiều rows hơn kỳ vọng;
- thứ tự chạy test ảnh hưởng kết quả;
- khi chạy riêng từng test thì hầu hết pass;
- team đề xuất tăng `waitForTimeout` từ 2 giây lên 10 giây và bật 3 retries để “ổn định CI”.

Code hiện tại:

## Đoạn code cần review

```ts
import { test, expect } from '@playwright/test';

const employeeEmail = 'e2e.shared.employee@example.test';

async function login(page) {
  await page.goto('/login');
  await page.getByLabel('Email').fill('qa.admin@example.test');
  await page.getByLabel('Password').fill(process.env.E2E_PASSWORD!);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForTimeout(2000);
}

test.beforeEach(async ({ page }) => {
  await login(page);
  await page.goto('/employees');
});

test('manager can activate employee', async ({ page }) => {
  await page.getByRole('button', { name: 'Add employee' }).click();
  await page.getByLabel('Email').fill(employeeEmail);
  await page.getByLabel('Name').fill('Shared E2E Employee');
  await page.getByRole('button', { name: 'Save' }).click();

  await page.waitForTimeout(2000);

  await page.getByPlaceholder('Search employees').fill(employeeEmail);
  await page.getByText(employeeEmail).click();
  await page.getByRole('button', { name: 'Activate' }).click();

  await page.reload();
  await expect(page.getByText('Active')).toBeVisible();
});

test('manager can deactivate employee', async ({ page }) => {
  await page.getByPlaceholder('Search employees').fill(employeeEmail);
  await page.waitForTimeout(1500);

  await page.getByText(employeeEmail).click();
  await page.getByRole('button', { name: 'Deactivate' }).click();
  await page.waitForTimeout(2000);

  await expect(page.getByText('Inactive')).toBeVisible();
});

test.afterEach(async ({ request }) => {
  await request.delete(`/api/test-data/employees/${employeeEmail}`);
});
```

## Kết quả code review tham khảo

### Critical — Các tests dùng chung một mutable employee record

**Vấn đề:**  
Cả suite dùng một hằng `employeeEmail`, trong khi tests có thể chạy ở nhiều workers/processes.

**Tại sao xảy ra:**  
Parallel workers không chia sẻ execution order nhưng lại cùng thao tác trên cùng business record ở backend.

**Ảnh hưởng production:**  
Một worker có thể tạo/activate/delete record trong lúc worker khác đang search/deactivate. Kết quả trở thành nondeterministic: duplicate data, missing row, sai status hoặc cleanup phá test đang chạy.

**Cách sửa:**  
Mỗi test phải sở hữu unique test data, ví dụ email chứa `testInfo.workerIndex`, project name và random/unique suffix. Tốt hơn nữa, tạo data qua API fixture và cleanup đúng record do test đó tạo.

### High — Test thứ hai phụ thuộc implicit vào test thứ nhất

**Vấn đề:**  
`manager can deactivate employee` không tự tạo employee ở trạng thái phù hợp trước khi test.

**Tại sao xảy ra:**  
Suite đang giả định test activation đã chạy trước và để lại data.

**Ảnh hưởng production:**  
Khi Playwright đổi order, shard suite hoặc chạy test riêng, precondition không tồn tại. Test không độc lập và kết quả phụ thuộc lịch sử suite.

**Cách sửa:**  
Mỗi test tự thiết lập precondition qua fixture/API. Test deactivation nên tạo employee đã active trước khi mở UI.

### High — `afterEach` có thể xóa dữ liệu của test khác

**Vấn đề:**  
Cleanup luôn xóa cùng `employeeEmail` bất kể record đó đang thuộc worker nào.

**Tại sao xảy ra:**  
Test data ownership không được encode vào identifier.

**Ảnh hưởng production:**  
Một test vừa qua bước setup thì test khác kết thúc và cleanup record của nó, tạo race condition khó tái hiện.

**Cách sửa:**  
Fixture trả về ID/email riêng cho test và cleanup chính resource đó. Cleanup nên idempotent để failure ở giữa test không làm pipeline hỏng thêm.

### High — Fixed sleeps không đồng bộ với trạng thái hệ thống

**Vấn đề:**  
`waitForTimeout(1500/2000)` giả định UI/network/backend hoàn thành trong một khoảng cố định.

**Tại sao xảy ra:**  
CI load, network, browser scheduling và backend latency thay đổi theo thời điểm.

**Ảnh hưởng production:**  
Sleep quá ngắn gây flaky test; sleep quá dài làm suite chậm nhưng vẫn không bảo đảm correctness.

**Cách sửa:**  
Dùng web-first assertions/locator state hoặc chờ response/URL/UI condition thực sự chứng minh action hoàn tất.

### Medium — Login được lặp lại bằng UI cho mọi test mà không có boundary rõ

**Vấn đề:**  
Mỗi test đều đi qua login UI dù mục tiêu test là employee workflow.

**Tại sao xảy ra:**  
Authentication setup chưa được tách thành fixture/storage state phù hợp.

**Ảnh hưởng production:**  
Suite chậm hơn, tăng tải identity endpoint và mở rộng failure surface: test employee có thể fail chỉ vì login chậm.

**Cách sửa:**  
Nếu security scenario không cần test login, tạo authenticated state/fixture một cách kiểm soát. Giữ một số test riêng cho login flow. Không chia sẻ mutable session theo cách làm các tests can thiệp nhau.

### Medium — Locator theo text có thể mơ hồ khi data trùng hoặc UI có nhiều vùng chứa cùng text

**Vấn đề:**  
`getByText(employeeEmail)` và `getByText('Active')` có thể match nhiều elements.

**Tại sao xảy ra:**  
Locator không gắn với row/detail region cụ thể.

**Ảnh hưởng production:**  
Khi UI thêm toast, hidden content hoặc duplicate rows, test fail không phản ánh business regression thực tế.

**Cách sửa:**  
Scope locator vào row/detail panel bằng role/test id/business key phù hợp rồi assert trạng thái bên trong đúng entity.

### Medium — Retry có nguy cơ che flakiness thay vì chữa flakiness

**Vấn đề:**  
Team muốn tăng retry để làm pipeline xanh.

**Tại sao xảy ra:**  
Race condition thường thay đổi timing ở lần retry nên test có thể pass ngẫu nhiên.

**Ảnh hưởng production:**  
Pipeline trông ổn định hơn nhưng defect trong test infrastructure tồn tại, thời gian CI tăng và tín hiệu regression kém tin cậy.

**Cách sửa:**  
Dùng retry như diagnostic/safety policy có chủ đích, theo dõi retry rate như flaky-test signal và xử lý root cause về isolation/synchronization.

### Low — Credential lifecycle và artifact redaction chưa được thể hiện

**Vấn đề:**  
Password lấy từ environment variable là hợp lý hơn hard-code, nhưng suite không cho thấy policy về secret scope/redaction.

**Tại sao xảy ra:**  
CI test infrastructure có thể vô tình capture request/log/trace chứa dữ liệu nhạy cảm.

**Ảnh hưởng production:**  
Trace, screenshot hoặc debug log có thể trở thành nguồn leak nếu credential/token xuất hiện.

**Cách sửa:**  
Dùng dedicated least-privilege test identity, secret store của CI, rotate credential và kiểm soát/redact artifacts/logging.

## Phiên bản đề xuất

Một hướng là tạo fixture/API helper để mỗi test có employee riêng và chờ state cụ thể thay vì sleep:

```ts
import { test, expect, APIRequestContext } from '@playwright/test';

async function createEmployee(
  request: APIRequestContext,
  email: string,
  active: boolean
) {
  const response = await request.post('/api/test-data/employees', {
    data: {
      email,
      name: 'E2E Employee',
      active
    }
  });

  expect(response.ok()).toBeTruthy();
  return await response.json() as { id: string };
}

async function deleteEmployee(
  request: APIRequestContext,
  id: string
) {
  await request.delete(`/api/test-data/employees/${id}`);
}

test('manager can activate employee', async ({ page, request }, testInfo) => {
  const email = `e2e.activate.${testInfo.workerIndex}.${testInfo.retry}.${Date.now()}@example.test`;
  const employee = await createEmployee(request, email, false);

  try {
    await page.goto('/employees');
    await page.getByPlaceholder('Search employees').fill(email);

    const row = page.getByRole('row').filter({ hasText: email });
    await expect(row).toBeVisible();
    await row.getByRole('link').click();

    await page.getByRole('button', { name: 'Activate' }).click();
    await expect(page.getByTestId('employee-status')).toHaveText('Active');
  } finally {
    await deleteEmployee(request, employee.id);
  }
});

test('manager can deactivate employee', async ({ page, request }, testInfo) => {
  const email = `e2e.deactivate.${testInfo.workerIndex}.${testInfo.retry}.${Date.now()}@example.test`;
  const employee = await createEmployee(request, email, true);

  try {
    await page.goto('/employees');
    await page.getByPlaceholder('Search employees').fill(email);

    const row = page.getByRole('row').filter({ hasText: email });
    await expect(row).toBeVisible();
    await row.getByRole('link').click();

    await page.getByRole('button', { name: 'Deactivate' }).click();
    await expect(page.getByTestId('employee-status')).toHaveText('Inactive');
  } finally {
    await deleteEmployee(request, employee.id);
  }
});
```

Authentication có thể được đưa vào fixture hoặc pre-generated authenticated storage state nếu mục tiêu của hai tests không phải kiểm tra login. Cách cụ thể phụ thuộc auth architecture và security policy của hệ thống.

## Giải thích thiết kế sau khi sửa

Mỗi test giờ có **test data ownership** riêng:

- setup tạo đúng precondition cần cho test;
- identifier là unique, nên parallel workers không đụng cùng record;
- cleanup xóa bằng ID mà chính test vừa tạo;
- không phụ thuộc order hoặc side effect của test khác;
- assertions chờ business/UI condition thay vì thời gian cố định.

Điểm quan trọng là test isolation, không phải chỉ thay `waitForTimeout` bằng một API chờ khác. Nếu backend tạo data eventual-consistent với search index, fixture cần chờ **đúng observable condition** hoặc expose test-support strategy phù hợp thay vì sleep tùy ý.

Retries vẫn có thể được bật theo CI policy, nhưng retry count phải đi kèm metric: test nào phải retry thường xuyên là test flaky cần xử lý, không phải test “đã ổn”.

## Trade-offs

- **Tạo data qua API:** nhanh, deterministic và tách setup khỏi UI; nhưng test-support endpoint phải được bảo vệ, chỉ tồn tại ở môi trường test hoặc có access control rất chặt.
- **Tạo data qua UI:** gần user behavior hơn nhưng chậm, nhiều failure surface và không cần thiết cho mọi test.
- **Unique data per test:** tốn thêm cleanup/storage nhưng đổi lại parallelism an toàn và debug dễ hơn.
- **Shared seeded dataset:** có thể nhanh cho read-only tests; không phù hợp với tests mutate cùng entities trừ khi có isolation strategy rõ.
- **Retries:** hữu ích với một số hạ tầng không hoàn toàn deterministic, nhưng không thay thế việc sửa shared state hoặc fixed sleeps.

## Cách kiểm thử

1. **Parallel stress:** chạy cùng file với nhiều workers và `--repeat-each` nhiều lần để xác minh không còn race do shared employee.
2. **Order independence:** chạy riêng từng test, đảo order và shard suite để bảo đảm mỗi test tự có precondition.
3. **Failure cleanup:** cố tình fail giữa test và xác minh cleanup/idempotency không xóa data của test khác.
4. **Slow-backend simulation:** tăng response latency và xác minh condition-based assertions vẫn đúng mà không cần tăng fixed sleep.
5. **Artifact security check:** kiểm tra trace/log/screenshot để bảo đảm password/token không bị lộ ngoài policy.

## Quan sát trong production

Theo dõi ở cấp test infrastructure:

- pass/fail rate theo test name và commit;
- **retry rate** và test nào pass chỉ sau retry;
- duration p50/p95 theo test/suite;
- worker count và shard configuration;
- trace/video/screenshot chỉ giữ theo policy cần thiết khi fail;
- network/request log tương ứng với test ID hoặc unique data key;
- số test-data records còn sót sau pipeline;
- backend 4xx/5xx/timeout trong test window;
- flaky-test trend theo tuần thay vì chỉ nhìn một pipeline xanh/đỏ.

Khi một failure xảy ra, artifact nên đủ để trả lời: test nào sở hữu record nào, action cuối cùng là gì, backend trả response gì và worker nào cleanup resource.

## Câu hỏi phỏng vấn mở rộng

1. Nếu backend search index có eventual consistency 5–20 giây, bạn thiết kế E2E synchronization thế nào mà không dùng fixed sleep 20 giây cho mọi test?
2. Khi nào nên dùng authenticated `storageState`, và làm sao tránh chia sẻ session mutable gây cross-test interference?
3. Nếu suite có 2.000 tests, bạn sẽ dùng retry/flaky quarantine thế nào để pipeline vẫn hữu ích mà không che regression thật?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- DI lifetime không chỉ là cấu hình container; lifetime quyết định **ownership, isolation và mutable state boundaries**.
- Tạo một scope trong constructor singleton không biến dependency scoped thành per-request; scope đó sống cho tới khi chính singleton dispose nó.
- `DbContext` nên gắn với một unit-of-work ngắn sống; chia sẻ context giữa concurrent requests vừa phá thread safety vừa làm tracking state tồn tại quá lâu.
- E2E test muốn chạy parallel phải sở hữu dữ liệu riêng và không được phụ thuộc order/side effect của test khác.
- Fixed sleeps và retries có thể làm symptom ít xuất hiện hơn nhưng không sửa race condition hoặc shared-state bug.
- Observability cho test infrastructure cũng quan trọng như observability production: retry rate, artifact, unique test-data identity và timing giúp biến “flaky” thành một failure có bằng chứng.

## Mẫu tư duy cần nhớ

1. **Align lifetime với unit-of-work và ownership của mutable state.**
2. **Concurrency-safe bắt đầu từ isolation, không bắt đầu từ thêm lock.**
3. **Mỗi test phải tự tạo precondition và sở hữu resource nó mutate.**
4. **Chờ condition thực tế, không chờ thời gian cố định.**
5. **Retry là tín hiệu cần đo, không phải bằng chứng rằng root cause đã được sửa.**
