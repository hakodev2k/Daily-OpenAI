# Code Review Challenge 1 — BackgroundService đồng bộ inventory bị chạy trùng sau horizontal scaling

**Chủ đề:** C#/.NET BackgroundService, concurrency, distributed execution, cancellation, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một e-commerce integration service chạy trên Azure App Service. Worker dưới đây đồng bộ inventory từ third-party supplier mỗi phút. Ban đầu production chỉ có một instance nên hệ thống hoạt động ổn. Sau khi scale lên 4 instances để tăng availability, team quan sát thấy cùng một SKU đôi khi được đồng bộ 3–4 lần gần như đồng thời, supplier API bị rate-limit, một số inventory update cũ ghi đè update mới và log khó xác định instance nào đã thực hiện operation.

Business yêu cầu inventory cuối cùng phải phản ánh dữ liệu supplier mới nhất có thể, nhưng không yêu cầu mỗi polling cycle phải chạy chính xác một lần. Third-party API có latency không ổn định và đôi lúc timeout. Service phải shutdown an toàn khi deploy.

## Đoạn code cần review

```csharp
public sealed class InventorySyncWorker : BackgroundService
{
    private static bool _running;
    private readonly IServiceProvider _services;
    private readonly HttpClient _httpClient;
    private readonly ILogger<InventorySyncWorker> _logger;

    public InventorySyncWorker(
        IServiceProvider services,
        HttpClient httpClient,
        ILogger<InventorySyncWorker> logger)
    {
        _services = services;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            if (!_running)
            {
                _running = true;

                try
                {
                    using var scope = _services.CreateScope();
                    var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

                    var response = await _httpClient.GetAsync(
                        "https://supplier.example/api/inventory");

                    response.EnsureSuccessStatusCode();

                    var items = await response.Content
                        .ReadFromJsonAsync<List<SupplierInventoryItem>>();

                    foreach (var item in items!)
                    {
                        var product = await db.Products
                            .SingleAsync(x => x.Sku == item.Sku);

                        product.Stock = item.Stock;
                        product.LastSyncedUtc = DateTime.UtcNow;

                        await db.SaveChangesAsync();
                    }
                }
                catch (Exception ex)
                {
                    _logger.LogError(ex, "Inventory synchronization failed");
                }
                finally
                {
                    _running = false;
                }
            }

            await Task.Delay(TimeSpan.FromMinutes(1));
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Xác định performance, reliability và concurrency concerns.
3. Giải thích impact khi service chạy nhiều instances và khi supplier chậm/fail.
4. Ưu tiên findings theo severity thay vì chỉ liệt kê style issues.
5. Đề xuất implementation/design phù hợp requirement, không mặc định phải dùng distributed lock.
6. Giải thích cách test concurrency, cancellation và dependency failure.
7. Nêu telemetry production cần có để chứng minh worker hoạt động đúng.

## Câu hỏi gợi mở

1. `static bool` bảo vệ phạm vi nào khi có 4 application processes/instances?
2. Điều gì xảy ra nếu deployment gửi cancellation trong lúc HTTP request hoặc database operation đang chạy?
3. Nếu cycle A bắt đầu trước nhưng hoàn thành sau cycle B, dữ liệu nào có thể thắng?
4. Có cần “exactly once scheduler” thật sự không, hay idempotent/latest-wins processing phù hợp hơn?
5. Số database round trips tăng thế nào khi supplier trả hàng nghìn SKUs?

## Kết quả code review tham khảo

### Critical — In-memory flag không ngăn duplicate execution giữa instances

**Vấn đề:** `_running` chỉ tồn tại trong process hiện tại. Mỗi App Service instance có state riêng nên cả bốn instances đều có thể chạy cycle cùng lúc.  
**Tại sao xảy ra:** horizontal scaling tạo nhiều processes/machines; `static` không phải distributed coordination primitive.  
**Ảnh hưởng production:** duplicate supplier traffic, rate limiting, concurrent database writes và khó reasoning về ordering.  
**Cách sửa:** trước hết xác định requirement. Nếu chỉ cần latest inventory và duplicate polling chấp nhận được, làm write path idempotent/version-aware có thể đơn giản hơn distributed lock. Nếu business yêu cầu một poller duy nhất, dùng một execution ownership mechanism có semantics rõ ràng như queue-triggered orchestration/lease hoặc scheduler có distributed coordination và failure recovery.

### High — Update không bảo vệ dữ liệu khỏi out-of-order completion

**Vấn đề:** mọi cycle ghi `Stock` không kèm supplier version/timestamp/ETag.  
**Tại sao xảy ra:** request cũ có thể hoàn thành sau request mới do network latency khác nhau.  
**Ảnh hưởng production:** stale stock có thể ghi đè dữ liệu mới hơn dù mọi request đều “thành công”.  
**Cách sửa:** nếu supplier cung cấp version/updated timestamp, persist nó và chỉ apply update mới hơn. Nếu không có, cần định nghĩa ordering/ownership strategy thay vì giả định completion order bằng freshness order.

### High — CancellationToken không được truyền vào I/O

**Vấn đề:** `GetAsync`, deserialization, EF queries, `SaveChangesAsync` và `Task.Delay` không dùng `stoppingToken`.  
**Tại sao xảy ra:** cancellation chỉ được kiểm tra ở đầu loop.  
**Ảnh hưởng production:** deployment có thể chờ lâu hoặc terminate process khi work vẫn đang chạy; request bị orphan/partial cycle.  
**Cách sửa:** truyền token qua toàn bộ cancellable async path và xử lý `OperationCanceledException` khi host shutdown như expected lifecycle event.

### High — N+1 database query và SaveChanges per item

**Vấn đề:** mỗi SKU thực hiện một SELECT và một SaveChanges.  
**Tại sao xảy ra:** query/update đặt trong loop.  
**Ảnh hưởng production:** hàng nghìn items tạo hàng nghìn round trips, kéo dài cycle và tăng khả năng overlap/failure.  
**Cách sửa:** batch-load products theo SKU, update tracked entities rồi SaveChanges theo bounded batch hoặc một lần tùy volume/transaction requirement.

### Medium — Polling cadence bị drift theo execution duration

**Vấn đề:** một phút được tính sau khi cycle kết thúc, không phải fixed cadence.  
**Tại sao xảy ra:** `Task.Delay` nằm cuối loop.  
**Ảnh hưởng production:** khi supplier chậm, effective polling interval tăng không rõ ràng.  
**Cách sửa:** dùng `PeriodicTimer` nếu fixed interval semantics phù hợp, nhưng phải quyết định rõ skip/overlap behavior khi một iteration dài hơn period.

### Medium — Exception handling che cancellation và thiếu failure classification

**Vấn đề:** catch toàn bộ `Exception` coi cancellation, timeout, HTTP 429 và database failure như nhau.  
**Tại sao xảy ra:** không phân loại transient/permanent/lifecycle failures.  
**Ảnh hưởng production:** alert noise, retry strategy kém và shutdown bị log như incident.  
**Cách sửa:** xử lý cancellation riêng; telemetry HTTP status/dependency duration; retry bounded chỉ cho transient cases và phải xét supplier rate limits.

### Medium — HTTP response không được dispose rõ ràng

**Vấn đề:** `HttpResponseMessage` không được dispose trong scope.  
**Tại sao xảy ra:** response được giữ tới GC thay vì lifetime rõ ràng.  
**Ảnh hưởng production:** resource lifetime kém rõ ràng, đặc biệt khi payload/traffic lớn.  
**Cách sửa:** `using var response = await ...` và consume content trong scope.

### Medium — Null/data validation không đủ

**Vấn đề:** `items!`, giả định SKU tồn tại duy nhất và payload luôn hợp lệ.  
**Tại sao xảy ra:** external dependency được tin tưởng quá mức.  
**Ảnh hưởng production:** một malformed item hoặc unknown SKU có thể fail toàn cycle.  
**Cách sửa:** validate response contract, xác định policy cho unknown/duplicate SKU và xử lý partial invalid data theo business requirement.

### Low — Telemetry thiếu execution identity và outcome metrics

**Vấn đề:** chỉ có một error log chung.  
**Tại sao xảy ra:** worker không emit cycle ID, instance ID, item count, duration hoặc supplier dependency metrics.  
**Ảnh hưởng production:** khó chứng minh duplicate execution, latency và partial failure.  
**Cách sửa:** structured logs/traces và metrics cho cycle, instance, duration, supplier status, item count, applied/skipped/failure counts.

## Phiên bản đề xuất

Một thiết kế đơn giản là chấp nhận nhiều pollers nhưng làm update latest-wins nếu supplier có `UpdatedUtc`. Nếu duplicate supplier traffic không chấp nhận được, execution ownership phải được bổ sung riêng ở orchestration layer.

```csharp
public sealed class InventorySyncWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopeFactory;
    private readonly HttpClient _httpClient;
    private readonly ILogger<InventorySyncWorker> _logger;

    public InventorySyncWorker(
        IServiceScopeFactory scopeFactory,
        HttpClient httpClient,
        ILogger<InventorySyncWorker> logger)
    {
        _scopeFactory = scopeFactory;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(1));

        do
        {
            var cycleId = Guid.NewGuid();
            var started = Stopwatch.GetTimestamp();

            try
            {
                await SynchronizeAsync(cycleId, stoppingToken);

                _logger.LogInformation(
                    "Inventory sync {CycleId} completed in {ElapsedMs} ms",
                    cycleId,
                    Stopwatch.GetElapsedTime(started).TotalMilliseconds);
            }
            catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
            {
                break;
            }
            catch (Exception ex)
            {
                _logger.LogError(ex, "Inventory sync {CycleId} failed", cycleId);
            }
        }
        while (await timer.WaitForNextTickAsync(stoppingToken));
    }

    private async Task SynchronizeAsync(Guid cycleId, CancellationToken ct)
    {
        using var response = await _httpClient.GetAsync(
            "https://supplier.example/api/inventory",
            HttpCompletionOption.ResponseHeadersRead,
            ct);

        response.EnsureSuccessStatusCode();

        var items = await response.Content
            .ReadFromJsonAsync<List<SupplierInventoryItem>>(cancellationToken: ct)
            ?? throw new InvalidDataException("Supplier returned an empty payload.");

        var validItems = items
            .Where(x => !string.IsNullOrWhiteSpace(x.Sku))
            .GroupBy(x => x.Sku)
            .Select(g => g.OrderByDescending(x => x.UpdatedUtc).First())
            .ToList();

        var skus = validItems.Select(x => x.Sku).ToArray();

        await using var scope = _scopeFactory.CreateAsyncScope();
        var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();

        var products = await db.Products
            .Where(x => skus.Contains(x.Sku))
            .ToDictionaryAsync(x => x.Sku, ct);

        foreach (var item in validItems)
        {
            if (!products.TryGetValue(item.Sku, out var product))
            {
                _logger.LogWarning(
                    "Inventory sync {CycleId}: unknown SKU {Sku}",
                    cycleId,
                    item.Sku);
                continue;
            }

            if (product.SupplierUpdatedUtc >= item.UpdatedUtc)
                continue;

            product.Stock = item.Stock;
            product.SupplierUpdatedUtc = item.UpdatedUtc;
            product.LastSyncedUtc = DateTime.UtcNow;
        }

        await db.SaveChangesAsync(ct);
    }
}
```

## Giải thích thiết kế sau khi sửa

Implementation trên sửa cancellation propagation, giảm database round trips và bảo vệ update khỏi payload cũ nếu supplier có timestamp đáng tin cậy. Nó cố ý không giả vờ rằng `PeriodicTimer` giải quyết multi-instance coordination. Nếu supplier API quota không cho phép bốn instances poll song song, team cần thêm một ownership mechanism độc lập hoặc chuyển polling thành một scheduled producer duy nhất phát work qua durable queue.

Nếu `UpdatedUtc` không có hoặc không có semantics đáng tin cậy, latest-wins implementation phải thay đổi; không được tự tạo timestamp local rồi coi đó là supplier ordering.

## Trade-offs

Batch-load nhiều SKUs giảm round trips nhưng tăng memory và có thể chạm giới hạn query parameter/query shape ở volume rất lớn, nên cần bounded batching. Một single poller giảm supplier traffic nhưng tạo bài toán leader/lease recovery. Cho phép duplicate pollers đơn giản hơn operationally nhưng chỉ phù hợp nếu dependency quota và idempotency/version semantics chịu được duplication.

## Cách kiểm thử

1. **Concurrency test:** chạy hai `SynchronizeAsync` với payload versions khác nhau và ép request cũ hoàn thành sau; assert version mới không bị overwrite.
2. **Integration/database test:** hàng nghìn SKUs phải được xử lý với bounded query/save count thay vì per-item round trips.
3. **Failure-path test:** supplier trả 429/500/timeout; verify cycle fail có telemetry và không tạo retry storm.
4. **Cancellation test:** cancel token trong HTTP/database path; worker dừng trong shutdown budget và không log cancellation như unexpected error.
5. **Multi-instance test:** chạy nhiều worker processes để chứng minh in-memory state không coordinate; sau đó verify chosen ownership/idempotency strategy.

## Quan sát trong production

Theo dõi cycle ID, instance ID, supplier request rate/status, dependency p95/p99, sync duration, payload item count, applied/skipped count, stale-version skip count và failure count. Alert khi cycle duration tiến gần polling interval, supplier 429 tăng, hoặc freshness lag vượt business SLO. Application Insights dependency telemetry nên được correlate với structured worker logs.

## Câu hỏi phỏng vấn mở rộng

1. Nếu supplier không cung cấp version/timestamp và business không chấp nhận stale overwrite, bạn thiết kế ordering thế nào?
2. Khi nào Azure Service Bus hoặc một scheduled Azure Function tốt hơn BackgroundService cho workflow này?
3. Nếu distributed lease holder crash giữa cycle, bạn muốn recovery semantics gì và vì sao?

# Code Review Challenge 2 — React product search trả kết quả sai khi người dùng gõ nhanh

**Chủ đề:** React, TypeScript, async race condition, API integration, browser lifecycle, XSS  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một React component trong product catalog gọi ASP.NET Core search API mỗi khi người dùng thay đổi query. Ở development mọi thứ có vẻ ổn. Production có latency biến động 80 ms–2 giây. Khi người dùng gõ nhanh, UI đôi lúc hiển thị kết quả của query cũ sau query mới. Backend thấy lượng request cao, browser console có warning khi chuyển trang trong lúc request đang chạy. Product name có thể chứa text do content editors nhập từ CMS; backend trả cả `highlightHtml` từ search service.

Requirement: search phải responsive, không hiển thị stale result, không gây request storm không cần thiết và phải render content an toàn.

## Đoạn code cần review

```tsx
import React, { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
  highlightHtml?: string;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    if (query.length === 0) {
      setProducts([]);
      return;
    }

    setLoading(true);

    fetch(`/api/products/search?q=${query}`)
      .then(response => response.json())
      .then(data => {
        setProducts(data.items);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [query]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />

      {loading && <p>Loading...</p>}
      {error && <p>{error}</p>}

      <ul>
        {products.map(product => (
          <li key={product.id}>
            <strong>{product.name}</strong>
            {product.highlightHtml && (
              <span
                dangerouslySetInnerHTML={{ __html: product.highlightHtml }}
              />
            )}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong async UI state.
2. Xác định performance, security và reliability concerns.
3. Giải thích production impact dưới latency variance và navigation/unmount.
4. Ưu tiên stale-result/XSS risks trước cosmetic concerns.
5. Đề xuất implementation có cancellation/debounce hoặc strategy tương đương.
6. Giải thích unit/integration/E2E tests phù hợp.
7. Nêu browser/network telemetry hữu ích.

## Câu hỏi gợi mở

1. Request cho `abc` và `abcd` có đảm bảo hoàn thành theo thứ tự được tạo không?
2. Query chứa `&`, `#` hoặc Unicode được gửi như thế nào?
3. Component có lý do gì để tin `highlightHtml` là safe HTML?
4. Khi effect chạy lại, request trước có được hủy không?
5. Error từ query trước có thể xuất hiện sau khi query mới đã thành công không?

## Gợi ý

### Gợi ý 1

Primary correctness risk là nhiều asynchronous requests cạnh tranh ghi vào cùng state.

### Gợi ý 2

Browser không đảm bảo completion order theo issue order. Đồng thời `dangerouslySetInnerHTML` biến trust boundary của search/CMS content thành security decision.

## Dừng lại và tự review

## Kết quả code review tham khảo

### Critical — Untrusted HTML có thể tạo XSS

**Vấn đề:** `highlightHtml` được đưa trực tiếp vào `dangerouslySetInnerHTML`.  
**Tại sao xảy ra:** React escaping bị bypass và component tin HTML từ backend/search/CMS boundary.  
**Ảnh hưởng production:** nếu content hoặc highlighting pipeline cho phép attacker-controlled markup đi qua, script/event payload có thể thực thi trong origin của application.  
**Cách sửa:** tốt nhất trả structured highlight segments/text thay vì raw HTML. Nếu business bắt buộc HTML, sanitize bằng policy/library phù hợp ở trust boundary và defense-in-depth; không tự viết regex sanitizer.

### High — Out-of-order responses có thể ghi stale results

**Vấn đề:** mọi request đều có quyền gọi `setProducts` khi hoàn thành.  
**Tại sao xảy ra:** network completion order không đảm bảo giống request creation order.  
**Ảnh hưởng production:** user gõ `camera`, request cũ `cam` hoàn thành sau và overwrite UI bằng kết quả sai.  
**Cách sửa:** abort request trước trong effect cleanup và/hoặc dùng request generation identity để chỉ latest request được commit state.

### High — Không cancel request khi query đổi hoặc component unmount

**Vấn đề:** effect không cleanup.  
**Tại sao xảy ra:** mỗi keystroke tạo request độc lập sống tới completion.  
**Ảnh hưởng production:** wasted backend work, race conditions và lifecycle warnings/telemetry noise.  
**Cách sửa:** tạo `AbortController` cho mỗi effect và abort trong cleanup; backend cũng nên propagate request cancellation nơi phù hợp.

### Medium — Không debounce input

**Vấn đề:** mỗi keystroke gọi API ngay.  
**Tại sao xảy ra:** `query` trực tiếp là effect dependency.  
**Ảnh hưởng production:** request amplification, backend/search load cao và nhiều races hơn.  
**Cách sửa:** debounce search intent với delay được UX đo/điều chỉnh; cancellation vẫn cần vì debounce không loại mọi overlap.

### Medium — Query string không được encode

**Vấn đề:** interpolation trực tiếp `?q=${query}`.  
**Tại sao xảy ra:** reserved URL characters có semantics riêng.  
**Ảnh hưởng production:** query bị cắt/sai hoặc request không phản ánh input.  
**Cách sửa:** dùng `URLSearchParams` hoặc `encodeURIComponent` phù hợp.

### Medium — Không kiểm tra HTTP status

**Vấn đề:** `response.json()` chạy cả với 4xx/5xx.  
**Tại sao xảy ra:** Fetch không reject promise chỉ vì HTTP status là error.  
**Ảnh hưởng production:** error payload có thể bị xử lý như success shape hoặc sinh lỗi khó hiểu.  
**Cách sửa:** kiểm tra `response.ok`, parse error contract có kiểm soát.

### Medium — Loading/error state có race

**Vấn đề:** request cũ có thể set `loading=false` hoặc `error` sau request mới.  
**Tại sao xảy ra:** state không gắn với request identity.  
**Ảnh hưởng production:** spinner biến mất sớm hoặc error cũ xuất hiện trên kết quả mới.  
**Cách sửa:** chỉ latest non-aborted request được update state; clear error khi bắt đầu request mới.

### Low — Empty query không reset toàn bộ UI state

**Vấn đề:** branch empty chỉ clear products.  
**Tại sao xảy ra:** loading/error từ request cũ có thể còn.  
**Ảnh hưởng production:** stale error/loading UI.  
**Cách sửa:** cleanup request và reset relevant state khi normalized query rỗng.

## Phiên bản đề xuất

Phiên bản dưới đây trả highlight dạng text để tránh raw HTML. API contract minh họa là `highlightText`; nếu backend hiện chỉ có HTML, contract nên được thay đổi hoặc sanitize ở boundary phù hợp.

```tsx
import React, { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
  highlightText?: string;
};

type SearchResponse = {
  items: Product[];
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [debouncedQuery, setDebouncedQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const timer = window.setTimeout(
      () => setDebouncedQuery(query.trim()),
      250
    );

    return () => window.clearTimeout(timer);
  }, [query]);

  useEffect(() => {
    if (!debouncedQuery) {
      setProducts([]);
      setLoading(false);
      setError(null);
      return;
    }

    const controller = new AbortController();

    async function search() {
      setLoading(true);
      setError(null);

      try {
        const params = new URLSearchParams({ q: debouncedQuery });
        const response = await fetch(
          `/api/products/search?${params.toString()}`,
          { signal: controller.signal }
        );

        if (!response.ok) {
          throw new Error(`Search failed with HTTP ${response.status}`);
        }

        const data = (await response.json()) as SearchResponse;

        if (!controller.signal.aborted) {
          setProducts(data.items);
        }
      } catch (err) {
        if (err instanceof DOMException && err.name === "AbortError") {
          return;
        }

        if (!controller.signal.aborted) {
          setError(err instanceof Error ? err.message : "Search failed");
        }
      } finally {
        if (!controller.signal.aborted) {
          setLoading(false);
        }
      }
    }

    void search();

    return () => controller.abort();
  }, [debouncedQuery]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />

      {loading && <p>Loading...</p>}
      {error && <p role="alert">{error}</p>}

      <ul>
        {products.map(product => (
          <li key={product.id}>
            <strong>{product.name}</strong>
            {product.highlightText && <span>{product.highlightText}</span>}
          </li>
        ))}
      </ul>
    </section>
  );
}
```

## Giải thích thiết kế sau khi sửa

Debounce giảm request volume nhưng không được coi là concurrency control; AbortController giải quyết obsolete request ở browser và cleanup lifecycle. State chỉ được commit nếu request chưa bị abort. `URLSearchParams` giữ query semantics đúng. HTTP status được kiểm tra rõ ràng.

Thay raw highlight HTML bằng structured/plain text làm trust boundary đơn giản hơn. Nếu UX cần markup để tô đậm matched fragments, API có thể trả segments `{ text, matched }` để React render elements mà vẫn giữ escaping mặc định.

## Trade-offs

Debounce thêm một lượng latency cố ý trước request; giá trị 250 ms chỉ là scenario choice và phải tune bằng UX/telemetry, không phải universal constant. Abort request giảm client-side waste nhưng server có thể đã bắt đầu xử lý; backend cancellation propagation và query efficiency vẫn quan trọng. Structured highlights làm contract verbose hơn raw HTML nhưng giảm đáng kể security ambiguity.

## Cách kiểm thử

1. **Unit/component test:** fake timers xác minh nhiều keystrokes nhanh chỉ trigger request sau debounce.
2. **Race test:** ép request `cam` hoàn thành sau `camera`; UI phải chỉ hiển thị `camera` results.
3. **Failure-path test:** 500 response hiển thị controlled error và không parse như success.
4. **Security test:** product/highlight chứa `<img onerror=...>` phải render như text/structured segments, không thực thi markup.
5. **Playwright E2E:** dùng network interception để tạo latency khác nhau, gõ nhanh rồi navigate away; verify không stale result và obsolete requests bị abort/cancel theo observable browser behavior.

## Quan sát trong production

Theo dõi request count per search session, aborted request ratio, frontend search latency, backend dependency latency, 4xx/5xx, query length distribution và stale-result regression qua synthetic E2E. Browser RUM/network telemetry có thể giúp correlate keystroke-to-result latency; backend Application Insights cần correlation để thấy request cancellation và expensive search queries.

## Câu hỏi phỏng vấn mở rộng

1. Nếu dùng React Query/TanStack Query hoặc framework data layer, những guarantees nào vẫn phải hiểu thay vì giả định library tự giải quyết mọi race?
2. Nếu backend Elasticsearch highlight bắt buộc trả HTML, bạn đặt sanitization ở đâu và test policy thế nào?
3. Nếu search cần instant suggestions ở mỗi keystroke, bạn giảm debounce nhưng bảo vệ backend capacity bằng những cơ chế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge tập trung vào cùng một nguyên tắc ở hai tầng khác nhau: asynchronous work không có guarantee về ownership hoặc completion order nếu hệ thống không thiết kế guarantee đó. `static` state không coordinate distributed processes; request được gửi trước không nhất thiết hoàn thành trước. Correctness cần idempotency/versioning/cancellation và trust boundaries rõ ràng, không chỉ thêm locks hoặc UI delays.

## Mẫu tư duy cần nhớ

- Xác định phạm vi của state/lock trước khi dùng nó cho concurrency control.
- Thiết kế duplicate execution cùng idempotency hoặc ordering semantics.
- Cancellation phải được propagate qua I/O path, không chỉ kiểm tra ở outer loop.
- Với async UI, chỉ latest valid intent nên được phép commit state.
- Không bypass output escaping nếu chưa xác định và bảo vệ trust boundary.
