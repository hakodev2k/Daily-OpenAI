# Code Review Challenge 1 — Service Bus consumer gửi email hai lần dù message đã được “Complete” đúng chỗ

**Chủ đề:** C#/.NET 8, Azure Service Bus, EF Core, at-least-once delivery, message lock, idempotent consumer, transaction boundary, retries, cancellation, dead-lettering, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 10–12 vấn đề

## Bối cảnh

Một notification worker nhận `OrderConfirmed` từ Azure Service Bus. Mỗi message cần:

- ghi một bản ghi `NotificationDelivery` vào SQL Server;
- gửi email xác nhận đơn hàng qua external email provider;
- không gửi email hai lần cho cùng logical event;
- application chạy 4 replicas;
- processing thông thường mất 2–5 giây nhưng email provider đôi lúc chậm tới hơn 1 phút;
- message có thể được redeliver khi worker crash, mất lock hoặc settlement thất bại;
- transient SQL/email failures cần retry có kiểm soát;
- poison message phải được xử lý riêng thay vì retry vô hạn;
- shutdown phải graceful;
- operations cần biết delivery count, duplicate rate, lock-loss rate, provider failures và backlog.

Production ghi nhận một số khách hàng nhận 2–3 email giống nhau. Logs cho thấy cùng `MessageId` đôi lúc được xử lý bởi hai replicas cách nhau vài chục giây. Team kết luận rằng vì code gọi `CompleteMessageAsync` sau khi gửi email nên duplicate là “không thể xảy ra”.

## Đoạn code cần review

```csharp
public sealed class OrderConfirmedHandler
{
    private readonly AppDbContext _db;
    private readonly EmailClient _emailClient;
    private readonly ServiceBusReceiver _receiver;
    private readonly ILogger<OrderConfirmedHandler> _logger;

    public OrderConfirmedHandler(
        AppDbContext db,
        EmailClient emailClient,
        ServiceBusReceiver receiver,
        ILogger<OrderConfirmedHandler> logger)
    {
        _db = db;
        _emailClient = emailClient;
        _receiver = receiver;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        CancellationToken cancellationToken)
    {
        var order = JsonSerializer.Deserialize<OrderConfirmed>(
            message.Body.ToString())!;

        var alreadySent = await _db.NotificationDeliveries
            .AnyAsync(
                x => x.OrderId == order.OrderId &&
                     x.Type == "OrderConfirmed",
                cancellationToken);

        if (alreadySent)
        {
            await _receiver.CompleteMessageAsync(
                message,
                cancellationToken);
            return;
        }

        await _emailClient.SendOrderConfirmedAsync(
            order.Email,
            order.OrderId,
            cancellationToken);

        _db.NotificationDeliveries.Add(
            new NotificationDelivery
            {
                Id = Guid.NewGuid(),
                OrderId = order.OrderId,
                Type = "OrderConfirmed",
                SentAtUtc = DateTime.UtcNow
            });

        await _db.SaveChangesAsync(cancellationToken);

        await _receiver.CompleteMessageAsync(
            message,
            cancellationToken);

        _logger.LogInformation(
            "Order confirmation email sent for {OrderId}",
            order.OrderId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các correctness problems trong message-processing flow.
2. Xác định reliability, concurrency, security và maintainability concerns.
3. Giải thích production impact khi worker crash, message lock hết hạn, provider timeout hoặc nhiều replicas cùng xử lý duplicate delivery.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected implementation/design với transaction boundary và idempotency rõ ràng.
6. Giải thích cách test duplicate delivery, lock loss, crash window, retry và poison messages.
7. Đề xuất production telemetry để chứng minh consumer đang hoạt động an toàn.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu email provider đã nhận request thành công nhưng process crash trước `SaveChangesAsync`?
2. `AnyAsync` rồi `Add` có phải một atomic “check-and-insert” khi nhiều replicas cùng xử lý không?
3. Nếu message lock hết hạn trong lúc gọi email provider, replica khác có thể nhận cùng message trước khi replica hiện tại hoàn tất không?
4. `CompleteMessageAsync` thành công có chứng minh external side effect chỉ xảy ra đúng một lần không?
5. Nếu email provider timeout sau khi đã gửi email, retry nên dựa trên bằng chứng nào để tránh gửi lần hai?

## Kết quả code review tham khảo

### Critical — External email side effect xảy ra trước durable idempotency state

**Vấn đề:**  
Code gửi email trước khi ghi `NotificationDelivery` vào SQL.

**Tại sao xảy ra:**  
Nếu provider đã gửi email nhưng process crash, SQL lỗi, cancellation xảy ra hoặc message lock bị mất trước `SaveChangesAsync`, database vẫn không chứa bằng chứng rằng logical event đã tạo side effect.

**Ảnh hưởng production:**  
Message được redeliver và consumer lại thấy `alreadySent == false`, từ đó gửi email lần nữa. Đây là failure window điển hình của at-least-once processing với external side effect.

**Cách sửa:**  
Tạo một durable delivery/operation record với stable business key trước khi gọi provider, enforce uniqueness ở database, rồi quản lý state `Pending/Sending/Succeeded/Unknown/Failed`. Nếu email provider hỗ trợ idempotency key, reuse stable key đó cho mọi retry. Nếu provider không hỗ trợ idempotency, cần chấp nhận/định nghĩa semantics thực tế và reconciliation strategy thay vì tuyên bố exactly-once.

### Critical — `AnyAsync` rồi `Add` là check-then-act race

**Vấn đề:**  
Hai consumer instances có thể cùng đọc `alreadySent == false`, cùng gửi email rồi cùng insert delivery record.

**Tại sao xảy ra:**  
Read và insert là hai operations độc lập; application-level check không tạo uniqueness invariant dưới concurrency.

**Ảnh hưởng production:**  
Duplicate message hoặc lock redelivery có thể dẫn tới nhiều side effects ngay cả khi SQL cuối cùng chỉ giữ một record nếu một insert sau đó fail.

**Cách sửa:**  
Enforce unique constraint/index trên stable logical key, ví dụ `(OrderId, Type)` hoặc tốt hơn `EventId/MessageId + ConsumerName` tùy domain semantics. Claim work bằng atomic insert/update và xử lý unique-conflict như duplicate delivery, thay vì dựa vào `AnyAsync`.

### High — Message lock expiry có thể tạo concurrent processing

**Vấn đề:**  
Processing time có thể dài hơn lock window/renewal budget, đặc biệt khi provider chậm hơn một phút.

**Tại sao xảy ra:**  
Peek-lock ownership chỉ tồn tại trong lock duration và có thể cần auto-renewal/manual renewal theo host/processor configuration. Một handler dài không được phép giả định lock luôn còn hiệu lực đến lúc settlement.

**Ảnh hưởng production:**  
Message có thể được delivery lại cho replica khác trong khi replica đầu tiên vẫn đang gọi email provider. Hai workers có thể cùng tạo side effect.

**Cách sửa:**  
Cấu hình processor lock renewal phù hợp với bounded processing time, giảm thời gian giữ message bằng cách tách work nếu cần, và vẫn giữ consumer idempotent vì lock renewal không thay thế idempotency. Theo dõi lock-lost exceptions như một signal vận hành quan trọng.

### High — Timeout/cancellation của email call tạo ambiguous outcome

**Vấn đề:**  
Nếu HTTP request timeout sau khi provider đã nhận và gửi email, caller không biết side effect đã xảy ra hay chưa.

**Tại sao xảy ra:**  
Transport failure không đồng nghĩa business operation thất bại. Response có thể bị mất sau khi server đã commit side effect.

**Ảnh hưởng production:**  
Retry mù có thể gửi lại email; abandon message rồi redelivery cũng gây cùng rủi ro.

**Cách sửa:**  
Dùng provider-supported stable idempotency key nếu có; nếu provider có operation lookup, reconcile ambiguous attempt theo operation ID. Nếu không có cả hai, thiết kế phải ghi nhận trạng thái `Unknown` và có recovery policy rõ thay vì tự động retry non-idempotent side effect vô hạn.

### High — Settlement gắn với request cancellation có thể tạo duplicate delivery không cần thiết

**Vấn đề:**  
`CompleteMessageAsync` dùng cùng `cancellationToken` với application/request shutdown path.

**Tại sao xảy ra:**  
Nếu business processing đã commit thành công nhưng token bị cancel ngay trước settlement, complete có thể không được gửi tới broker.

**Ảnh hưởng production:**  
Message được redeliver dù business state đã thành công. Nếu idempotency tốt thì đây chỉ là duplicate work; nếu không, có thể tạo duplicate side effect.

**Cách sửa:**  
Thiết kế handler để durable business result được commit trước settlement và duplicate-safe. Trong shutdown, dùng processor lifecycle/grace period phù hợp. Không dùng `CancellationToken.None` một cách mù quáng cho mọi thứ; xác định rõ operation nào cần bounded cleanup/settlement budget sau khi main token bị cancel.

### High — Không có explicit poison-message strategy

**Vấn đề:**  
Deserialize failure, invalid payload hoặc permanent provider/domain error không được classify.

**Tại sao xảy ra:**  
Mọi exception dễ bị broker/processor retry cùng một cách cho tới `MaxDeliveryCount` mà không có domain-specific diagnostics.

**Ảnh hưởng production:**  
Poison messages tạo repeated load, noise và cuối cùng vào DLQ nhưng thiếu context; hoặc nếu custom retry không giới hạn có thể block throughput.

**Cách sửa:**  
Validate payload/schema; classify transient vs permanent failures; dead-letter permanent invalid messages với safe reason/metadata; để transient errors retry theo bounded policy và monitor DLQ depth/age.

### Medium — `MessageId` không được đưa vào durable processing identity

**Vấn đề:**  
Database record chỉ có `OrderId` và string `Type`.

**Tại sao xảy ra:**  
Business operation có thể cần phân biệt nhiều legitimate `OrderConfirmed` events hoặc event revisions, trong khi broker duplicate identity cũng cần traceability.

**Ảnh hưởng production:**  
Có thể dedupe quá rộng hoặc quá hẹp, đồng thời khó correlate message delivery với SQL/email attempt.

**Cách sửa:**  
Định nghĩa explicit logical event ID từ producer và stable consumer operation key. Không mặc định `MessageId` luôn là domain idempotency key nếu producer không bảo đảm uniqueness/stability qua retry.

### Medium — Raw email address và payload assumptions cần security/data handling rõ ràng

**Vấn đề:**  
Handler tin trực tiếp `order.Email` từ message mà không thể hiện validation/trust boundary.

**Tại sao xảy ra:**  
Message broker không tự biến payload thành trusted business data; producer identity, schema và data minimization vẫn cần được thiết kế.

**Ảnh hưởng production:**  
Sai/malicious payload có thể gửi notification tới địa chỉ không đúng hoặc làm lộ PII trong logs/provider calls nếu downstream handling không chặt.

**Cách sửa:**  
Validate schema/domain values, xác định producer ownership, cân nhắc dùng recipient/customer ID rồi resolve server-side nếu requirement security cần, và không log raw PII không cần thiết.

### Medium — `DbContext` lifetime phải phù hợp message scope

**Vấn đề:**  
Snippet không cho biết handler lifetime. Nếu handler/processor giữ một scoped `DbContext` dùng lâu dài hoặc dùng concurrently, implementation không an toàn.

**Tại sao xảy ra:**  
`DbContext` không dành cho concurrent operations và thường nên có unit-of-work lifetime ngắn.

**Ảnh hưởng production:**  
Có thể gặp tracking state retention, concurrency exceptions hoặc state leakage giữa messages.

**Cách sửa:**  
Tạo scope/`DbContext` riêng cho mỗi message processing attempt, hoặc dùng `IDbContextFactory<TContext>` khi phù hợp với hosted processor architecture.

### Low — Observability không đủ để chứng minh duplicate handling

**Vấn đề:**  
Log success chỉ có `OrderId`, không ghi durable operation identity, delivery count, duplicate classification, lock state hay provider operation ID.

**Tại sao xảy ra:**  
Telemetry chưa được thiết kế cùng reliability semantics.

**Ảnh hưởng production:**  
Khó phân biệt broker redelivery, application retry, provider retry và actual duplicate side effect.

**Cách sửa:**  
Ghi structured telemetry theo `MessageId`, event ID, delivery count, consumer operation ID, provider request/operation ID, outcome state, processing duration, lock-lost, settlement result và retry reason; không log message body/PII mặc định.

## Phiên bản đề xuất

Một hướng thực dụng là dùng một durable delivery row như **inbox/operation record** để claim logical event trước external call. Ví dụ dưới đây giả định email provider hỗ trợ stable idempotency key hoặc lookup theo operation ID.

```csharp
public enum DeliveryStatus
{
    Pending,
    Sending,
    Succeeded,
    Unknown,
    Failed
}

public sealed class NotificationDelivery
{
    public Guid Id { get; init; }
    public Guid EventId { get; init; }
    public Guid OrderId { get; init; }
    public string Type { get; init; } = default!;
    public DeliveryStatus Status { get; set; }
    public string? ProviderOperationId { get; set; }
    public DateTime CreatedAtUtc { get; init; }
    public DateTime? CompletedAtUtc { get; set; }
}

public async Task HandleAsync(
    ServiceBusReceivedMessage message,
    CancellationToken ct)
{
    var payload = DeserializeAndValidate(message);

    await using var db = await _dbFactory.CreateDbContextAsync(ct);

    var delivery = await TryClaimAsync(
        db,
        payload.EventId,
        payload.OrderId,
        ct);

    if (delivery is null)
    {
        await CompleteWithBoundedCleanupAsync(message, ct);
        return;
    }

    var idempotencyKey = delivery.Id.ToString("N");
    delivery.Status = DeliveryStatus.Sending;
    await db.SaveChangesAsync(ct);

    EmailSendResult result;
    try
    {
        result = await _emailClient.SendOrderConfirmedAsync(
            payload.Email,
            payload.OrderId,
            idempotencyKey,
            ct);
    }
    catch (EmailOutcomeUnknownException)
    {
        delivery.Status = DeliveryStatus.Unknown;
        await db.SaveChangesAsync(CancellationToken.None);
        throw;
    }

    delivery.Status = DeliveryStatus.Succeeded;
    delivery.ProviderOperationId = result.OperationId;
    delivery.CompletedAtUtc = DateTime.UtcNow;

    await db.SaveChangesAsync(ct);

    await CompleteWithBoundedCleanupAsync(message, ct);
}
```

`TryClaimAsync` không được implement bằng `SELECT` rồi `INSERT` đơn thuần. Database phải có unique index trên logical key, ví dụ:

```sql
CREATE UNIQUE INDEX UX_NotificationDeliveries_Event_Type
ON NotificationDeliveries(EventId, Type);
```

Một implementation có thể attempt insert `Pending` row và coi unique-key conflict là “đã được claim”. Tuy nhiên nếu existing row đang ở `Unknown`, `Failed` hoặc `Sending` quá lâu thì cần recovery/reconciliation state machine thay vì luôn coi là success.

Nếu email provider **không** hỗ trợ idempotency hoặc operation lookup, không có cách tổng quát để atomically commit SQL state và external email side effect. Khi đó architecture phải thừa nhận khả năng duplicate trong một số failure windows, giảm rủi ro bằng durable state/reconciliation, hoặc chuyển sang provider/integration có semantics phù hợp hơn nếu business thực sự yêu cầu near-exactly-once delivery.

## Giải thích thiết kế sau khi sửa

Thiết kế mới chuyển “đã xử lý chưa?” từ một application-level read thành một database invariant. SQL chịu trách nhiệm claim logical event, Service Bus vẫn có thể redeliver, và consumer coi duplicate delivery là expected behavior.

Quan trọng nhất, message settlement không còn là nguồn chân lý về business outcome. `Complete` chỉ nói broker có thể bỏ delivery hiện tại; nó không rollback email đã gửi nếu settlement thất bại, và nó cũng không làm external side effect trở thành exactly-once.

Nếu xử lý có thể kéo dài, cấu hình auto-lock renewal phải đủ cho expected bounded runtime. Nhưng idempotency vẫn bắt buộc vì process crash, network partition và settlement ambiguity vẫn tồn tại ngay cả khi lock renewal được cấu hình tốt.

## Trade-offs

- Durable inbox/operation row tăng một database write và cần cleanup/retention policy.
- Unique event key đơn giản hóa duplicate handling nhưng phải được định nghĩa đúng theo business semantics; dedupe quá rộng có thể nuốt event hợp lệ.
- Stable provider idempotency key giảm duplicate side effect nhưng phụ thuộc contract/retention window của provider.
- Auto lock renewal giúp long-running handler nhưng kéo dài thời gian một worker giữ message; không nên dùng để che một handler quá dài không bounded.
- Tách email work thành downstream queue có thể rút ngắn lock duration nhưng thêm component/operational complexity; chỉ nên làm khi throughput/failure isolation biện minh.

## Cách kiểm thử

1. **Duplicate/concurrency integration test:** deliver cùng logical event đồng thời tới nhiều handler instances; xác minh unique claim chỉ tạo một active business operation và provider nhận cùng stable idempotency key.
2. **Crash-window test:** inject crash sau provider success nhưng trước SQL status update hoặc trước settlement; restart/redeliver và xác minh recovery không tạo duplicate side effect khi provider supports idempotency/lookup.
3. **Lock-loss test:** dùng processing delay vượt lock duration/renewal scenario; xác minh second delivery không phá business invariant và lock-lost telemetry xuất hiện.
4. **Failure classification test:** invalid JSON/domain payload phải đi theo permanent/dead-letter path; transient SQL/provider errors retry bounded; poison message không tạo hot loop.
5. **Graceful-shutdown test:** stop worker trong các phase claim/send/save/complete; xác minh durable state cho phép retry/reconciliation an toàn và không mất message.

## Quan sát trong production

Theo dõi:

- Service Bus active message count, dead-letter count, oldest-message age và delivery count distribution;
- handler attempts/success/failure/duplicate-claim rate;
- message lock-lost và settlement failures;
- processing duration so với effective lock-renewal budget;
- SQL unique-conflict rate và delivery state counts (`Pending/Sending/Unknown/Succeeded/Failed`);
- email provider latency/error/timeout/ambiguous-outcome rate;
- reconciliation backlog và age;
- trace correlation `MessageId → EventId → DeliveryId → ProviderOperationId`;
- alert khi duplicate claims, unknown outcomes, DLQ depth hoặc lock-loss tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu email provider không hỗ trợ idempotency key lẫn status lookup, bạn sẽ mô tả delivery guarantee với business như thế nào?
2. Khi nào bạn dùng Service Bus duplicate detection và khi nào vẫn cần application-level inbox/idempotency?
3. Nếu một notification hợp lệ cần được resend theo yêu cầu support, logical deduplication key nên thay đổi ra sao?

# Code Review Challenge 2 — API báo cáo SQL nhanh với 1.000 dòng nhưng chậm hàng chục giây sau khi bảng lên 80 triệu bản ghi

**Chủ đề:** SQL Server, query optimization, SARGability, composite indexes, keyset pagination, `OFFSET/FETCH`, optional filters, execution plans, parameterization, blocking, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một internal operations portal có màn hình tìm kiếm orders. Bảng `Orders` tăng lên khoảng 80 triệu rows.

Schema rút gọn:

```text
Orders(
    Id bigint PK,
    TenantId uniqueidentifier,
    CustomerEmail nvarchar(320),
    Status tinyint,
    CreatedAtUtc datetime2,
    Total decimal(18,2),
    Reference nvarchar(64)
)
```

Yêu cầu:

- mọi query phải được scope theo `TenantId`;
- filters `status`, date range và email là optional;
- UI hiển thị 50 rows mỗi page, sort mới nhất trước;
- user có thể đi tới page sâu nhưng use case chính là next/previous;
- API cần p95 dưới khoảng 1 giây ở tenant lớn;
- database đang phục vụ cả transactional workload nên report query không được tạo load/blocking quá mức;
- không được đổi sang Elasticsearch chỉ vì SQL query hiện chậm;
- operations cần biết query duration, logical reads, blocking và plan regressions.

Production có các triệu chứng:

- page 1 thường dưới 300 ms nhưng page 2.000 có thể mất hơn 15 giây;
- tìm theo email substring rất chậm;
- CPU SQL tăng mạnh trong giờ support team chạy report;
- một engineer thêm index riêng cho `Status`, `CreatedAtUtc`, `TenantId`, nhưng hiệu quả không ổn định;
- team muốn thêm `WITH (NOLOCK)` vì nghĩ blocking là nguyên nhân chính;
- một số query cùng shape nhanh ở tenant nhỏ nhưng rất chậm ở tenant lớn.

## Đoạn code cần review

```sql
CREATE INDEX IX_Orders_Status
ON dbo.Orders(Status);

CREATE INDEX IX_Orders_CreatedAtUtc
ON dbo.Orders(CreatedAtUtc);

CREATE INDEX IX_Orders_TenantId
ON dbo.Orders(TenantId);
GO

CREATE OR ALTER PROCEDURE dbo.SearchOrders
    @TenantId uniqueidentifier,
    @Status tinyint = NULL,
    @FromUtc datetime2 = NULL,
    @ToUtc datetime2 = NULL,
    @Email nvarchar(320) = NULL,
    @PageNumber int = 1,
    @PageSize int = 50
AS
BEGIN
    SELECT
        o.Id,
        o.CustomerEmail,
        o.Status,
        o.CreatedAtUtc,
        o.Total,
        o.Reference
    FROM dbo.Orders o WITH (NOLOCK)
    WHERE
        o.TenantId = @TenantId
        AND (@Status IS NULL OR o.Status = @Status)
        AND (@FromUtc IS NULL OR CONVERT(date, o.CreatedAtUtc) >= CONVERT(date, @FromUtc))
        AND (@ToUtc IS NULL OR CONVERT(date, o.CreatedAtUtc) <= CONVERT(date, @ToUtc))
        AND (@Email IS NULL OR o.CustomerEmail LIKE '%' + @Email + '%')
    ORDER BY o.CreatedAtUtc DESC
    OFFSET (@PageNumber - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và query-design problems.
2. Xác định performance, indexing, concurrency và maintainability concerns.
3. Giải thích tại sao symptom khác nhau giữa page 1/page sâu và tenant nhỏ/tenant lớn.
4. Ưu tiên findings theo severity dựa trên evidence cần thu thập.
5. Đề xuất corrected query/index/pagination design; không được mặc định rằng “thêm index” hay “thêm cache” luôn đúng.
6. Giải thích testing trên data distribution thực tế, execution plan và concurrent transactional load.
7. Đề xuất production telemetry để phát hiện regression.

## Câu hỏi gợi mở

1. `OFFSET 99,950 ROWS` yêu cầu engine làm gì trước khi trả 50 rows cuối cùng?
2. `CONVERT(date, o.CreatedAtUtc)` tác động thế nào tới khả năng seek trên index của cột thời gian?
3. Ba single-column indexes có phục vụ tốt predicate `TenantId` + sort `CreatedAtUtc DESC` + optional filters hay không?
4. `NOLOCK` thay đổi correctness semantics nào và có chứng minh root cause là blocking không?
5. `LIKE '%text%'` có thể dùng B-tree index thông thường theo cách nào, và requirement thực sự cần exact/prefix/substring search?

## Gợi ý

### Gợi ý 1

Primary risk không phải một “missing index” đơn lẻ mà là **query access pattern không khớp với pagination/filter semantics**, đặc biệt deep `OFFSET` và non-SARGable expressions.

### Gợi ý 2

Bắt đầu từ execution plan + logical reads + row estimates + waits, rồi thiết kế index theo equality prefix, range/order và projected columns. Đồng thời xem liệu cursor/keyset pagination có phù hợp hơn page-number pagination cho use case next/previous hay không.

## Kết quả code review tham khảo

### Critical — `NOLOCK` đánh đổi correctness để che symptom chưa được chứng minh

**Vấn đề:**  
Stored procedure đọc `Orders` bằng `WITH (NOLOCK)` dù report có thể được dùng để ra quyết định vận hành.

**Tại sao xảy ra:**  
`NOLOCK` cho phép behavior tương đương `READ UNCOMMITTED`; query có thể quan sát dữ liệu chưa commit và các anomalies trong khi concurrent writes diễn ra. Nó không phải generic “make query faster” switch.

**Ảnh hưởng production:**  
UI có thể hiển thị trạng thái/order values không nhất quán đúng lúc support đang điều tra sự cố. Nếu root cause thực sự là CPU/reads từ deep scan, `NOLOCK` không giải quyết nguyên nhân đó.

**Cách sửa:**  
Bỏ hint mặc định. Đo waits/blocking trước. Nếu workload cần giảm reader/writer blocking với committed semantics, đánh giá database isolation strategy như row-versioning (`READ_COMMITTED_SNAPSHOT`) ở cấp hệ thống sau khi xem tempdb/cost/compatibility, thay vì tự phát thêm hint từng query.

### High — Deep `OFFSET/FETCH` có cost tăng theo vị trí page

**Vấn đề:**  
Page 2.000 với 50 rows yêu cầu database bỏ qua gần 100.000 rows sau filter/order trước khi trả page hiện tại.

**Tại sao xảy ra:**  
`OFFSET` mô hình hóa vị trí tương đối, không đưa cho optimizer một cursor boundary để seek trực tiếp tới hàng cuối page trước.

**Ảnh hưởng production:**  
Latency và logical reads tăng theo page depth; nhiều users deep-page đồng thời khuếch đại CPU/I/O.

**Cách sửa:**  
Với navigation chủ yếu next/previous, dùng keyset/seek pagination bằng stable sort key, ví dụ `(CreatedAtUtc DESC, Id DESC)`. Nếu business bắt buộc random jump tới page N, cần chấp nhận/đo cost hoặc dùng chiến lược khác cho use case đó; không giả vờ keyset hỗ trợ random-page semantics giống hệt.

### High — Date predicates làm cột bị non-SARGable

**Vấn đề:**  
`CONVERT(date, o.CreatedAtUtc)` được áp lên indexed column trong predicates.

**Tại sao xảy ra:**  
Expression trên cột có thể ngăn engine dùng efficient range seek theo raw `datetime2` key.

**Ảnh hưởng production:**  
Nhiều rows phải được scan/evaluate, đặc biệt với tenant lớn và date range rộng.

**Cách sửa:**  
Chuẩn hóa boundary ở parameter/application side rồi so sánh trực tiếp, ví dụ `CreatedAtUtc >= @FromUtc` và `CreatedAtUtc < @ToExclusiveUtc`. Nếu UI dùng ngày local, convert timezone/day boundary ở boundary layer rõ ràng trước khi query UTC.

### High — Các single-column indexes không khớp access pattern chính

**Vấn đề:**  
Ba indexes riêng lẻ trên `TenantId`, `Status`, `CreatedAtUtc` không đồng nghĩa engine có một ordered access path tốt cho `TenantId = ?` và `ORDER BY CreatedAtUtc DESC, Id DESC`.

**Tại sao xảy ra:**  
Index usefulness phụ thuộc key order, selectivity, range predicates, sort và columns cần cover; engine không thể luôn “ghép” các indexes độc lập thành plan tối ưu.

**Ảnh hưởng production:**  
Plan có thể scan nhiều rows, sort lớn, lookup nhiều hoặc thay đổi mạnh theo tenant/filter selectivity.

**Cách sửa:**  
Bắt đầu từ workload thực tế. Một candidate index cho phổ biến no-status/default listing có thể là `(TenantId, CreatedAtUtc DESC, Id DESC)` với selected include columns. Nếu status-filtered query rất phổ biến/selective, một index `(TenantId, Status, CreatedAtUtc DESC, Id DESC)` có thể hữu ích. Không tạo cả hai mà không đo write/storage cost và plan usage.

### High — Sort không deterministic hoàn toàn

**Vấn đề:**  
Query chỉ `ORDER BY CreatedAtUtc DESC` dù nhiều orders có thể cùng timestamp.

**Tại sao xảy ra:**  
Khi sort key không unique, thứ tự giữa rows có cùng timestamp không được xác định bởi query contract.

**Ảnh hưởng production:**  
Giữa các page/request concurrent với inserts, rows có thể appear twice hoặc bị skip theo cách khó reasoning; keyset pagination cũng không thể dùng timestamp đơn độc an toàn.

**Cách sửa:**  
Thêm unique tie-breaker như `ORDER BY CreatedAtUtc DESC, Id DESC` và cursor gồm cả hai values.

### High — Leading-wildcard email search không phù hợp B-tree access path thông thường

**Vấn đề:**  
`CustomerEmail LIKE '%' + @Email + '%'` yêu cầu substring match.

**Tại sao xảy ra:**  
Khi pattern bắt đầu bằng wildcard, engine không có fixed leading prefix để seek theo một index B-tree thông thường trên `CustomerEmail`.

**Ảnh hưởng production:**  
Tenant/date candidate set lớn dẫn tới scan/evaluate nhiều strings, tăng CPU.

**Cách sửa:**  
Clarify requirement. Nếu exact email đủ, dùng equality với normalization phù hợp. Nếu prefix đủ, dùng `LIKE @Email + '%'`. Nếu substring thực sự bắt buộc ở scale lớn, đánh giá search-specific design phù hợp sau khi đo; không chuyển công nghệ chỉ vì một requirement chưa được làm rõ.

### Medium — Optional-filter pattern có thể tạo plan không ổn định theo parameter distribution

**Vấn đề:**  
Một procedure phục vụ tenant nhỏ/lớn, status null/selective và date/email combinations rất khác nhau.

**Tại sao xảy ra:**  
Một cached plan tối ưu cho một parameter shape/distribution có thể kém cho shape khác. Ngoài ra các `OR @Param IS NULL` làm cardinality estimation và predicate simplification khó hơn tùy version/configuration.

**Ảnh hưởng production:**  
Cùng stored procedure đôi lúc nhanh, đôi lúc rất chậm; regression có thể trông “ngẫu nhiên”.

**Cách sửa:**  
Thu execution plans/Query Store evidence theo parameter sets. Tùy workload có thể dùng parameter-sensitive plan capabilities của platform/version, `OPTION (RECOMPILE)` cho low-frequency expensive report, hoặc xây parameterized dynamic SQL chỉ thêm predicates thực sự có mặt. Chọn sau khi đo compile cost và plan stability.

### Medium — Pagination parameters chưa được validate

**Vấn đề:**  
`@PageNumber <= 0`, `@PageSize <= 0` hoặc quá lớn chưa bị chặn.

**Tại sao xảy ra:**  
Stored procedure tin caller cung cấp bounded values.

**Ảnh hưởng production:**  
Có thể tạo lỗi runtime, request cực nặng hoặc abuse làm tăng SQL load.

**Cách sửa:**  
Validate page size/page number ở API boundary và/hoặc procedure; đặt maximum page size phù hợp business. Với keyset pagination, validate cursor format và tenant ownership.

### Medium — Projection có thể gây lookup/storage trade-off cần đo

**Vấn đề:**  
Query trả nhiều columns ngoài index keys.

**Tại sao xảy ra:**  
Một narrow index có thể cần key lookup cho mỗi row; một covering index lại tốn storage và write amplification.

**Ảnh hưởng production:**  
Ở 80 triệu rows, index “cover everything” có thể rất lớn và làm writes/migrations/maintenance đắt hơn.

**Cách sửa:**  
Chọn `INCLUDE` columns dựa trên top query shape và measured lookup cost. Không include columns chỉ để làm execution plan trông đẹp.

### Medium — Chưa có evidence-driven diagnosis cho blocking/CPU/I/O

**Vấn đề:**  
Team chuyển thẳng từ symptom sang `NOLOCK` và index additions.

**Tại sao xảy ra:**  
Không thấy plan, logical reads, Query Store regressions, wait stats hay blocking chain trong workflow hiện tại.

**Ảnh hưởng production:**  
Fix có thể không chạm bottleneck thật và thêm technical debt/index write cost.

**Cách sửa:**  
Thu actual/representative execution plan, duration, CPU, logical reads, spills, waits, row estimates/actuals, blocking chain và Query Store history trước khi thay đổi. Xác nhận improvement bằng cùng workload/data distribution.

### Low — API contract page-number tạo coupling với implementation tốn kém

**Vấn đề:**  
Stored procedure nhận `@PageNumber` như primitive contract mặc dù UX chủ yếu next/previous.

**Tại sao xảy ra:**  
Pagination API được thiết kế theo UI control thay vì access pattern dữ liệu.

**Ảnh hưởng production:**  
Khó chuyển sang seek pagination mà không version/change client contract.

**Cách sửa:**  
Cân nhắc cursor-based API contract (`nextCursor`, `previousCursor`) cho endpoints lớn; giữ page-number chỉ ở nơi random access thực sự có business value.

## Phiên bản đề xuất

Một hướng cho flow phổ biến “next page” là keyset pagination với deterministic ordering. Ví dụ khi không có email substring requirement:

```sql
CREATE INDEX IX_Orders_Tenant_Created_Id
ON dbo.Orders(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC)
INCLUDE (
    Status,
    CustomerEmail,
    Total,
    Reference);
GO

CREATE OR ALTER PROCEDURE dbo.SearchOrdersNext
    @TenantId uniqueidentifier,
    @Status tinyint = NULL,
    @FromUtc datetime2 = NULL,
    @ToExclusiveUtc datetime2 = NULL,
    @AfterCreatedAtUtc datetime2 = NULL,
    @AfterId bigint = NULL,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 200
        THROW 50001, 'Invalid page size', 1;

    SELECT TOP (@PageSize)
        o.Id,
        o.CustomerEmail,
        o.Status,
        o.CreatedAtUtc,
        o.Total,
        o.Reference
    FROM dbo.Orders AS o
    WHERE
        o.TenantId = @TenantId
        AND (@Status IS NULL OR o.Status = @Status)
        AND (@FromUtc IS NULL OR o.CreatedAtUtc >= @FromUtc)
        AND (@ToExclusiveUtc IS NULL OR o.CreatedAtUtc < @ToExclusiveUtc)
        AND (
            @AfterCreatedAtUtc IS NULL
            OR o.CreatedAtUtc < @AfterCreatedAtUtc
            OR (
                o.CreatedAtUtc = @AfterCreatedAtUtc
                AND o.Id < @AfterId
            )
        )
    ORDER BY
        o.CreatedAtUtc DESC,
        o.Id DESC;
END
```

Với workload mà `Status` thường được truyền và rất selective, cần benchmark một index alternative:

```sql
CREATE INDEX IX_Orders_Tenant_Status_Created_Id
ON dbo.Orders(
    TenantId,
    Status,
    CreatedAtUtc DESC,
    Id DESC)
INCLUDE (
    CustomerEmail,
    Total,
    Reference);
```

Không nên giữ tất cả candidate indexes nếu Query Store/usage data cho thấy chúng redundant hoặc write cost không đáng.

Email search nên được tách theo requirement:

- exact: `CustomerEmail = @EmailNormalized`;
- prefix: `CustomerEmail LIKE @EmailPrefix + '%'`;
- substring: đánh giá riêng vì access pattern khác, có thể cần một search-oriented solution hoặc normalized auxiliary model tùy scale/requirements.

Nếu optional predicates tạo plan instability rõ ràng, có thể dùng parameterized dynamic SQL để chỉ emit predicates được dùng. Giá trị vẫn phải truyền dưới dạng parameters; không concatenate raw user input vào SQL text.

## Giải thích thiết kế sau khi sửa

Thiết kế mới đưa `TenantId` lên đầu access path vì mọi query đều tenant-scoped, tiếp theo là ordering keys để database có thể seek/scan một range đã được sắp đúng thay vì sort/skip một lượng lớn rows.

Keyset cursor `(CreatedAtUtc, Id)` biến “next page” thành boundary seek. `Id` đóng vai trò tie-breaker để ordering deterministic.

Date filtering so sánh trực tiếp `datetime2` values, tránh transform indexed column. Day-boundary semantics phải được giải quyết trước khi vào SQL nếu UI dùng timezone local.

Không có một composite index duy nhất tối ưu mọi combination optional filter. Senior-level decision là chọn một vài dominant access paths dựa trên workload evidence và chấp nhận trade-off cho query ít phổ biến, thay vì tạo index cho mọi cột.

## Trade-offs

- Keyset pagination rất tốt cho next/previous nhưng không hỗ trợ “jump to arbitrary page 2.000” trực tiếp như OFFSET.
- Composite covering index giảm reads của hot query nhưng tăng storage, write amplification và index maintenance.
- `OPTION (RECOMPILE)` có thể cải thiện parameter-specific plans nhưng tăng compile CPU; phù hợp hay không phụ thuộc frequency/cost.
- Parameterized dynamic SQL tăng implementation complexity nhưng có thể tạo predicate shape rõ hơn cho optional filters.
- Row-versioning isolation có thể giảm reader/writer blocking nhưng tăng version-store usage và phải được đánh giá toàn database, không phải local query tweak.

## Cách kiểm thử

1. **Data-distribution benchmark:** tạo/clone representative data với tenant nhỏ, tenant rất lớn, skewed statuses và realistic date ranges; đo duration/CPU/logical reads cho page đầu và deep navigation.
2. **Execution-plan test:** so actual plans trước/sau, kiểm tra seek/scan, sort, key lookup, memory grant/spill, estimated-vs-actual rows và index usage.
3. **Pagination correctness test:** nhiều rows cùng `CreatedAtUtc`, concurrent inserts giữa hai page requests; xác minh keyset cursor không duplicate/skip rows theo defined snapshot/consistency semantics.
4. **Concurrent load test:** chạy search workload cùng transactional inserts/updates; đo p95/p99, waits, blocking, CPU, I/O và ảnh hưởng write latency.
5. **Plan-regression test:** chạy các parameter shapes khác nhau (status null/selective, narrow/wide date range, tenant cardinality khác nhau) và kiểm tra Query Store/plan stability.

## Quan sát trong production

Theo dõi:

- stored procedure/query p50/p95/p99 duration;
- CPU time, logical reads, physical reads và returned-row count;
- Query Store plan changes/regressions;
- wait types, blocking duration/blocking chains và deadlocks;
- sort/hash spills và memory grants khi có;
- index usage, size và write overhead;
- requests theo filter shape và cursor/page depth;
- SQL dependency traces từ API với tenant ID được pseudonymize/hash nếu cần;
- alert khi duration/reads tăng theo plan change hoặc tenant cohort.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product owner bắt buộc jump chính xác tới page 2.000, bạn sẽ giữ requirement đó hay đề xuất UX/data-contract nào khác?
2. Khi nào bạn chọn `OPTION (RECOMPILE)`, parameterized dynamic SQL hoặc giữ một cached plan duy nhất?
3. Nếu email substring search trở thành use case cốt lõi với hàng trăm triệu rows, bằng chứng nào khiến bạn cân nhắc một search engine chuyên dụng?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- At-least-once delivery phải được thiết kế cùng durable idempotency; broker settlement không tự tạo exactly-once business side effects.
- External side effects có ambiguous outcome khi network/timeout thất bại; retry chỉ an toàn khi operation semantics hỗ trợ retry.
- Application-level `check then insert` không thay thế database uniqueness invariant dưới concurrency.
- SQL performance cần bắt đầu từ access pattern, execution plan, logical reads và data distribution thay vì thêm index/hint theo cảm tính.
- Deep `OFFSET`, non-SARGable predicates và nondeterministic ordering có thể biến một query “đúng” thành bottleneck production khi dữ liệu lớn.

## Mẫu tư duy cần nhớ

- Design retry together with idempotency and failure windows.
- Put business invariants in durable constraints, not only pre-checks.
- Measure query plans/reads/waits before optimizing.
- Match index order to real predicates and ordering, not individual columns in isolation.
- Prefer a data-access contract that matches the dominant navigation pattern.
