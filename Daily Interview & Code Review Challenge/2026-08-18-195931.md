# Câu 1 — EF Core tracking, deferred execution và truy vấn bị nhân đôi

**Loại câu hỏi:** Internal mechanism trong production  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15 phút  
**Kỹ năng được đánh giá:** EF Core, LINQ, SQL, performance, diagnostics

## Bối cảnh

Một ASP.NET Core API lấy danh sách nhân viên rồi enrich thêm dữ liệu. Sau một thay đổi nhỏ, latency P95 tăng từ khoảng 250 ms lên hơn 2 giây và SQL Server ghi nhận số query/request tăng mạnh. Code có một `IQueryable<Employee>` được filter, sau đó được dùng ở nhiều đoạn để `CountAsync`, `AnyAsync` và `ToListAsync`. Một developer nói: “`IQueryable` đã chứa dữ liệu rồi nên dùng lại không query DB nữa”.

## Câu hỏi chính

Hãy giải thích điều gì thực sự xảy ra bên trong EF Core/LINQ, vì sao hiện tượng trên có thể xảy ra, misconception nằm ở đâu, rủi ro production là gì và bạn sẽ chứng minh giả thuyết bằng cách nào trước khi sửa.

## Câu hỏi làm rõ nên cân nhắc

- Query có tracking hay `AsNoTracking()` không?
- Có navigation property/lazy loading hay query trong loop không?
- Mỗi terminal operation nào đang enumerate/execute query?
- SQL sinh ra và execution plan thực tế thế nào?
- Kích thước result set và tần suất endpoint là bao nhiêu?

## Gợi ý tư duy

- **Gợi ý 1:** Phân biệt query definition với query execution.
- **Gợi ý 2:** Xem các terminal operation và số lần enumeration.
- **Gợi ý 3:** Quan sát generated SQL, command count và thời gian DB thay vì suy luận từ C# בלבד.

## Cấu trúc trả lời đề xuất

1. Làm rõ symptom và code path.
2. Giải thích `IQueryable`/expression tree và deferred execution.
3. Xác định các điểm kích hoạt DB round-trip.
4. Kiểm tra tracking, N+1 và query shape.
5. Đưa ra các phương án tối ưu theo requirement.
6. Đo lại bằng telemetry và load test.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `IQueryable` chủ yếu biểu diễn query; nó không đồng nghĩa result đã được materialize/cache.
- Mỗi terminal operation như `CountAsync`, `AnyAsync`, `ToListAsync` có thể tạo một DB query riêng.
- Không tối ưu mù bằng cách `ToList` sớm; materialization sớm có thể kéo quá nhiều dữ liệu vào memory.
- Cần kiểm tra SQL thực tế và số DB command/request.

### Điểm cộng

- Đề cập projection, `AsNoTracking` cho read-only, pagination và tránh N+1.
- Phân biệt tracking overhead với nguyên nhân round-trip.
- Dùng query tags/structured logging/tracing để nối request với SQL.

### Nâng cao

- So sánh một query phức tạp với nhiều query nhỏ dựa trên cardinality, network round-trip, plan và consistency requirement.
- Nhận ra việc gom `Count`, `Any`, list thành một lần materialization không luôn đúng nếu result set lớn hoặc semantics khác nhau.

## Hướng giải quyết tham khảo

**Giả định:** Endpoint read-only, không cần snapshot transaction xuyên suốt nhiều phép đọc.

EF Core xây dựng expression tree cho `IQueryable`; provider dịch expression khi query được thực thi. Việc giữ biến query không mặc nhiên giữ result. Vì vậy ba terminal operations có thể tạo ba command SQL. Nếu sau đó navigation được load riêng hoặc query nằm trong loop, số round-trip còn tăng thêm.

Trước tiên bật/kiểm tra EF Core command telemetry ở môi trường phù hợp, dùng `ToQueryString()` trong diagnostics, APM trace và DB query statistics. Đếm command/request và so sánh trước/sau deployment.

Sửa theo semantics: nếu chỉ cần page dữ liệu, projection trực tiếp DTO và pagination; nếu cần count tổng, chấp nhận query count riêng hoặc thiết kế response phù hợp. Dùng `AsNoTracking()` cho read-only khi tracking không cần thiết. Tránh materialize toàn bộ chỉ để giảm số query. Với navigation, dùng projection hoặc loading strategy có chủ đích.

Test bằng integration test kiểm tra kết quả, benchmark/load test, và quan sát query count, P95/P99, DB CPU, logical reads. Recommendation thay đổi nếu cần consistency mạnh giữa count và list, result rất nhỏ, hoặc query plan cho một truy vấn hợp nhất tệ hơn.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng việc thêm cache hay `ToList` sớm. Em muốn xác nhận số SQL command/request. `IQueryable` là mô tả query; mỗi terminal operation có thể thực thi một query mới, nên `CountAsync`, `AnyAsync` và `ToListAsync` trên cùng biến không có nghĩa dùng chung result. Em sẽ xem generated SQL, trace EF Core command và execution plan, đồng thời kiểm tra N+1. Với endpoint read-only em ưu tiên projection DTO, pagination và `AsNoTracking` khi phù hợp. Nếu business thực sự cần count và page thì hai query có thể hoàn toàn hợp lý; mục tiêu không phải ít query nhất mà là latency, load DB và semantics đúng. Sau sửa em load-test và theo dõi command count, P95/P99, DB CPU và logical reads.”

## Câu hỏi đào sâu

1. `AsNoTracking()` giải quyết được vấn đề round-trip không?
2. Khi nào split query có thể tốt hơn single query?
3. Nếu count và page phải nhất quán tuyệt đối thì thiết kế thay đổi thế nào?

## Lỗi trả lời thường gặp

- Khẳng định `IQueryable` tự cache result.
- Dùng `ToList()` ngay đầu pipeline cho mọi trường hợp.
- Chỉ nói N+1 mà không thu thập evidence.
- Không xem generated SQL/execution plan.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2.5
- Depth: 2
- Trade-off analysis: 1.5
- Production readiness: 1.5
- Communication: 1

# Câu 2 — Incident: Hangfire xử lý thanh toán bị chạy trùng

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** incident response, Hangfire, idempotency, concurrency, SQL, observability

## Bối cảnh

Sau deployment, một số khách hàng nhận hai email xác nhận và một số integration downstream ghi nhận cùng business operation hai lần. Hangfire dashboard cho thấy một số job retry sau timeout. Hệ thống chạy nhiều worker instance. Chưa rõ duplicate xuất phát từ enqueue, retry, timeout hay logic downstream.

## Câu hỏi chính

Bạn sẽ xử lý incident từ lúc nhận cảnh báo đến khi xác định root cause, giảm thiểu thiệt hại và thiết kế lại để retry/concurrency không tạo duplicate business effect như thế nào?

## Câu hỏi làm rõ nên cân nhắc

- Business effect nào bắt buộc exactly-once về mặt nghiệp vụ?
- Job ID và business operation ID có được lưu/correlate không?
- Timeout xảy ra trước hay sau khi downstream đã commit?
- Downstream có hỗ trợ idempotency key không?
- Có nhiều producer hoặc recurring schedule cùng enqueue không?

## Gợi ý tư duy

- **Gợi ý 1:** Tách delivery semantics khỏi business idempotency.
- **Gợi ý 2:** Retry sau ambiguous failure là vùng nguy hiểm.
- **Gợi ý 3:** Dùng durable business key/unique constraint hoặc inbox/outbox tùy boundary; đừng dựa vào in-memory lock.

## Cấu trúc trả lời đề xuất

1. Đánh giá impact và ngăn thiệt hại lan rộng.
2. Correlate job → business operation → downstream call.
3. Liệt kê nhiều hypothesis.
4. Xác định duplicate enqueue hay duplicate execution/effect.
5. Vá ngắn hạn.
6. Thiết kế idempotency dài hạn.
7. Test failure window và monitor.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không giả định retry là bug; retry là hành vi cần thiết nhưng business handler phải chịu được duplicate execution.
- Dùng stable idempotency/business operation key.
- Có persistence/unique constraint hoặc cơ chế atomic phù hợp để chống duplicate effect.
- Xử lý ambiguous timeout: request có thể đã thành công ở downstream dù caller thấy failure.

### Điểm cộng

- Outbox cho DB state + message/event publication.
- Correlation ID xuyên job, DB và downstream.
- Immediate mitigation không phá dữ liệu: pause nhóm job có rủi ro, reconcile trước khi replay.

### Nâng cao

- Phân biệt scheduler uniqueness, distributed locking và business idempotency.
- Thiết kế reconciliation cho external side effect không thể transaction chung với DB.

## Hướng giải quyết tham khảo

Đầu tiên xác định phạm vi: operation nào bị duplicate, tiền/dữ liệu/email có mức độ nghiêm trọng khác nhau. Nếu side effect nguy hiểm, tạm dừng loại job đó hoặc giảm concurrency có kiểm soát trong khi vẫn giữ evidence.

Thu thập job attempt, exception, worker, timestamps, operation ID, DB transaction và downstream request. Hypothesis gồm enqueue trùng, retry sau timeout, worker mất lease/connection, manual replay hoặc downstream xử lý trùng.

Fix dài hạn đặt idempotency ở business boundary. Ví dụ tạo `OperationId` ổn định và unique constraint trong bảng xử lý; transaction ghi trạng thái nghiệp vụ cùng outbox nếu cần publish. Khi gọi external API, truyền idempotency key nếu provider hỗ trợ; nếu không, lưu trạng thái request và xây reconciliation thay vì retry mù sau ambiguous failure.

Distributed lock có thể giảm concurrency nhưng không thay thế idempotency vì crash/network partition vẫn tồn tại. Test bằng fault injection ở các điểm trước/sau DB commit và trước/sau downstream response. Monitor duplicate suppression count, retries, failed jobs, reconciliation backlog và side-effect success rate.

## Mẫu trả lời trong phỏng vấn

“Em coi đây trước hết là incident về duplicate business effect chứ không chỉ Hangfire. Em sẽ xác định impact, tạm ngăn các job có side effect nghiêm trọng nếu cần, rồi correlate từng attempt bằng một business operation ID. Retry sau timeout đặc biệt nguy hiểm vì downstream có thể đã commit nhưng caller không nhận response. Vì vậy em không cố đạt exactly-once delivery ở scheduler; em thiết kế handler idempotent. Operation ID phải ổn định, được enforce bằng durable storage/unique constraint, và nếu DB update đi cùng event thì cân nhắc transactional outbox. Với external API em dùng idempotency key nếu có; nếu không thì cần state machine và reconciliation. Sau đó em fault-test các crash window và monitor retry, duplicate suppression, failed jobs và reconciliation backlog.”

## Câu hỏi đào sâu

1. Vì sao distributed lock không đủ để đảm bảo không double-charge?
2. Nếu downstream không hỗ trợ idempotency key thì bạn làm gì?
3. Unique constraint có thể tạo bottleneck nào và bạn xử lý ra sao?

## Lỗi trả lời thường gặp

- Tắt retry hoàn toàn.
- Chỉ thêm distributed lock.
- Dùng Hangfire Job ID làm business idempotency key mà không xem lifecycle.
- Replay job lỗi trước khi reconcile side effect cũ.
- Không phân biệt duplicate execution và duplicate effect.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 1.5
- Production readiness: 2
- Communication: 1

# Câu 3 — Thiết kế AI agent review Pull Request có quyền dùng tool

**Loại câu hỏi:** AI engineering / system design  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** agent architecture, context engineering, tool permissions, evaluation, security, observability

## Bối cảnh

Team muốn xây một agent hỗ trợ review PR cho repository .NET. Agent có thể đọc diff, source liên quan, test result và coding rules; đề xuất lỗi correctness/security/performance và có thể đăng review comment. Sau này team muốn cho agent chạy test hoặc tạo patch. Requirement hiện chưa nói rõ agent được phép write ở đâu, dữ liệu nào nhạy cảm, chi phí tối đa hay tiêu chí chất lượng.

## Câu hỏi chính

Hãy thiết kế phiên bản MVP sao cho AI thực sự hữu ích nhưng các phần cần deterministic vẫn deterministic; mô tả context, tools/permissions, validation, hallucination controls, evaluation, fallback, audit và điều kiện để mở rộng quyền write.

## Câu hỏi làm rõ nên cân nhắc

- Agent chỉ advisory hay được phép thay đổi code?
- Repository có secret/PII/proprietary data nào không được gửi model?
- False positive hay false negative loại nào tốn kém hơn?
- Latency/cost budget cho mỗi PR?
- Human approval bắt buộc ở bước nào?

## Gợi ý tư duy

- **Gợi ý 1:** Đừng bắt model làm việc compiler/test/static analyzer làm tốt hơn.
- **Gợi ý 2:** Context selection và permission boundary quan trọng ngang prompt.
- **Gợi ý 3:** Tách propose → deterministic validate → human approve → optional execute.

## Cấu trúc trả lời đề xuất

1. Làm rõ mục tiêu và threat model.
2. Xác định deterministic pipeline.
3. Chọn context tối thiểu cần thiết.
4. Thiết kế read/write tool permissions.
5. Structured output + validation.
6. Evaluation dataset và quality gates.
7. Audit, cost, latency, fallback.
8. Điều kiện nâng quyền.

## Ý chính của câu trả lời tốt

### Bắt buộc

- AI dùng cho reasoning/triage/suggestion, không thay compiler, tests, formatter, analyzers.
- Least privilege: MVP read-only hoặc chỉ comment sau approval.
- Context phải có diff + relevant code/rules, tránh gửi toàn repo mặc định.
- Structured output được schema-validate và evidence phải trỏ tới code thực.
- Human review trước hành động có side effect quan trọng.

### Điểm cộng

- Tool allowlist, path restrictions, timeout/resource limits.
- Evaluation trên bộ PR lịch sử có ground truth tương đối.
- Theo dõi precision/actionability, latency, cost, acceptance rate.

### Nâng cao

- Chống prompt injection từ repository content bằng cách coi source/comment là untrusted data.
- Version prompt/rules/model/config để audit và reproduce.
- Canary/permission tiers khi mở write capability.

## Hướng giải quyết tham khảo

MVP nên chạy sau deterministic checks: build, unit tests, analyzers và secret scanning. Agent nhận PR diff, repository instructions đã được quản trị, các file liên quan được retrieval theo dependency/symbol/search và kết quả checks. Không tự động nạp mọi file.

Tools ban đầu chỉ read repository metadata/source và test results. Nếu đăng comment, giới hạn vào PR hiện tại; patch creation là capability riêng, mặc định off hoặc cần human approval. Nội dung PR/source được coi là untrusted, không được phép tự thay đổi system policy hay tool permissions.

Model trả structured findings gồm category, severity, file/line, claim, evidence và proposed verification. Validator kiểm tra file/line tồn tại, schema hợp lệ, severity allowlist; deterministic tests/analyzers chạy lại khi có patch. Findings thiếu evidence có thể hạ confidence hoặc không publish.

Evaluation dùng tập PR lịch sử gồm bug thật, false positives và clean changes; đo precision, useful-findings rate, acceptance/dismissal, escaped issues, latency và cost. Log model/config version, context references, tool calls, approvals và final actions nhưng redact secrets. Nếu AI unavailable, pipeline deterministic vẫn chạy và PR không bị block trừ khi policy đã quy định rõ.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không bắt đầu bằng một agent có quyền sửa repository. MVP nên augment pipeline hiện có: compiler, tests, analyzers và security checks vẫn deterministic; LLM tập trung vào reasoning trên diff và context liên quan. Context gồm diff, managed repo rules, selected source và test results, không gửi toàn repo mặc định. Source và PR comment là untrusted input nên không được thay đổi policy hoặc permission. Tool access theo least privilege, ban đầu read-only; comment hoặc patch là capability riêng và có approval. Output dùng schema với file, line, claim, evidence và verification; validator kiểm tra reference trước khi publish. Chất lượng được đo trên PR lịch sử bằng precision, acceptance/actionability, latency và cost. Em chỉ mở write permission sau khi có quality gate, audit trail, rollback và human approval rõ ràng.”

## Câu hỏi đào sâu

1. Làm sao giảm prompt injection từ README hoặc PR description?
2. Nếu retrieval bỏ sót file quan trọng, evaluation phát hiện thế nào?
3. Vì sao không cho agent tự sửa và merge khi test đều xanh?

## Lỗi trả lời thường gặp

- “Cho LLM đọc toàn repo rồi review”.
- Không có permission boundary/human approval.
- Đánh giá bằng cảm giác thay vì dataset/metrics.
- Tin line reference/citation do model sinh mà không validate.
- Không có fallback khi model/tool lỗi.

## Thang điểm 0–10

- Requirement clarification: 1.5
- Technical correctness: 2
- Depth: 2
- Trade-off analysis: 1.5
- Production readiness: 2

- Stabilize incident trước, rồi mới điều tra sâu.

- Validate AI output deterministically và giới hạn tool permission.
