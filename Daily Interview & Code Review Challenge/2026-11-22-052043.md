# Câu 1 — Bộ nhớ tăng khi export báo cáo: LOH, ArrayPool và vòng đời buffer

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** C# runtime, GC, LOH, ASP.NET Core streaming, profiling

## Bối cảnh

Một ASP.NET Core API .NET 8 tạo báo cáo CSV cho hệ thống timesheet. Mỗi yêu cầu đọc dữ liệu từ PostgreSQL rồi tạo nội dung bằng `MemoryStream`, cuối cùng gọi `ToArray()` để trả về file. Sau khi có 40–60 export đồng thời, memory của container tăng từ 500 MB lên gần giới hạn 2 GB. Request kết thúc nhưng working set không giảm ngay. p95 tăng mạnh và đôi khi container bị OOMKilled. Một số báo cáo lớn hơn 100 MB; các báo cáo nhỏ vẫn hoạt động bình thường. Chưa có heap dump hay allocation profile.

## Câu hỏi chính

Hãy giải thích các cơ chế runtime có thể gây ra hiện tượng này, phân biệt memory leak với allocation pressure và retained memory, rồi đề xuất cách điều tra và thay đổi luồng export để giới hạn memory mà vẫn xử lý cancellation và client disconnect.

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước file phân bố thế nào (p50/p95/max), bao nhiêu export đồng thời?
2. `MemoryStream` có được dispose và có cache/static reference giữ buffer không?
3. Export cần snapshot nhất quán hay có thể đọc theo cursor/stream?
4. Giới hạn memory container, GC mode và số lượng replica hiện tại?
5. CSV có yêu cầu tải lại, audit, hay xuất file qua Azure Blob Storage không?

## Gợi ý tư duy

### Gợi ý 1
Xem xét peak allocation trên từng request, không chỉ tổng số byte của file cuối cùng.

### Gợi ý 2
Phân biệt object sống, vùng heap đã commit và working set; kiểm tra kích thước allocation lớn.

### Gợi ý 3
Theo dõi capacity của `MemoryStream`, bản sao từ `ToArray()`, LOH, Gen 2 GC và backpressure của response stream.

## Cấu trúc trả lời đề xuất

1. Định lượng mức ảnh hưởng và ràng buộc file.
2. Mô tả vòng đời allocations và GC.
3. Liệt kê giả thuyết, bằng chứng bác bỏ/xác nhận.
4. Đề xuất giải pháp có memory bound.
5. Kiểm tra failure, cancellation và khả năng vận hành.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `MemoryStream` có thể tăng capacity, tạo buffer lớn; `ToArray()` tạo bản sao; nhiều request nhân peak memory.
- Các object đủ lớn thường được cấp phát trên Large Object Heap (LOH); GC không đồng nghĩa working set lập tức giảm.
- Không kết luận memory leak từ biểu đồ RSS đơn thuần.
- Đo allocations, live heap, Gen 2/LOH, concurrent requests và container OOM events.
- Streaming theo batch/reader, giới hạn concurrency, truyền cancellation, tránh materialize toàn bộ báo cáo.

### Điểm cộng
- Nêu rõ streaming vẫn có thể giữ connection/database transaction lâu; cần đo throughput và timeout.
- Xử lý CSV injection đối với dữ liệu do người dùng nhập; quyền truy cập dữ liệu export.
- Giải thích `ArrayPool<T>` có thể giảm allocations nhưng không tự động giải quyết retention, phải return buffer đúng cách.

### Senior+
- Đề xuất asynchronous export job + Blob Storage cho file lớn; quota theo tenant, bounded queue và download URL có hạn.
- Phân biệt `GC.GetTotalMemory`, GC heap metrics, process RSS, container memory; thiết kế load test tái hiện OOM.
- Xem xét snapshot consistency và lifecycle khi client disconnect.

## Hướng giải quyết tham khảo

**Giả định:** báo cáo có thể xuất CSV tuần tự, không bắt buộc biết trước `Content-Length`. Một `MemoryStream` lớn có thể giữ buffer capacity lớn hơn dữ liệu thực; `ToArray()` cấp phát thêm một mảng cùng cỡ dữ liệu. Nếu mỗi request giữ khoảng 150–300 MB trong một giai đoạn, 40 request có thể tạo áp lực hàng GB. Đây là phép ước lượng minh họa, không phải benchmark đã đo.

LOH là vùng dành cho allocations lớn (ngưỡng thường khoảng 85.000 bytes); các mảng lớn và bản sao có thể làm tăng Gen 2 GC và fragmentation. Dispose stream bỏ reference của stream, không bảo đảm hệ điều hành nhận lại RAM tức thì. Cần xác minh liệu live heap có tiếp tục tăng sau full GC hay không, có reference trong cache/singleton, hay chỉ là allocation burst và committed heap chưa thu hồi.

Điều tra theo trình tự: xác nhận OOMKilled qua Kubernetes events; đối chiếu request size/concurrency với memory, GC heap size, allocation rate, Gen 2 collections, pause time; thu `dotnet-counters` và `dotnet-gcdump`/dump trong môi trường được phép, tránh dump chứa dữ liệu nhạy cảm. Profiling staging với file kích thước đại diện để kiểm chứng nguyên nhân. Nếu heap ổn định nhưng RSS cao, điều tra native memory, buffers, runtime và memory accounting thay vì vội kết luận managed leak.

Giải pháp đồng bộ: truy vấn theo streaming hoặc các batch có kích thước giới hạn; ghi CSV tuần tự vào `HttpResponse.BodyWriter` hoặc `Response.Body`, không gọi `ToList()` hay `ToArray()` trên toàn bộ dữ liệu. Với EF Core, `AsAsyncEnumerable()` có thể giảm materialization nhưng cần kiểm tra provider, lifetime `DbContext`, thời gian giữ connection và transaction; không mở nhiều reader trên cùng context. Ví dụ phác thảo:

```csharp
app.MapGet("/reports/timesheets.csv", async (
    HttpContext http, AppDbContext db) =>
{
    http.Response.ContentType = "text/csv; charset=utf-8";
    http.Response.Headers.ContentDisposition =
        "attachment; filename=\"timesheets.csv\"";

    await using var writer = new StreamWriter(
        http.Response.Body, new UTF8Encoding(false),
        bufferSize: 16 * 1024, leaveOpen: true);

    await writer.WriteLineAsync("Employee,Hours");

    var rows = db.Timesheets.AsNoTracking()
        .OrderBy(x => x.Id)
        .Select(x => new { x.EmployeeName, x.Hours })
        .AsAsyncEnumerable();

    await foreach (var row in rows.WithCancellation(
        http.RequestAborted))
    {
        var name = EscapeCsvCell(row.EmployeeName);
        await writer.WriteLineAsync(
            $"{name},{row.Hours.ToString(CultureInfo.InvariantCulture)}");
    }

    await writer.FlushAsync(http.RequestAborted);
});
```

`EscapeCsvCell` là helper cần triển khai và test riêng: escape dấu ngoặc kép, dấu phẩy, newline, đồng thời áp dụng chính sách chống spreadsheet formula injection cho dữ liệu không tin cậy. Ví dụ minh họa bỏ qua auth, pagination và helper để tập trung vào streaming. Trong triển khai thật cần kiểm tra quyền truy cập trước khi ghi response; sau khi headers/body đã gửi thì không thể thay thế lỗi bằng một JSON `ProblemDetails` như request chưa bắt đầu.

Nếu file rất lớn, chuyển sang job nền tạo file trong Blob Storage, quản lý trạng thái, expiration, authorization và tải xuống có kiểm soát. Cả hai hướng cần concurrency cap; nếu database bị chậm, streaming không tự giải quyết bottleneck.

**Kiểm thử:** so sánh peak RSS/live heap với 1, 10, 50 request; abort client giữa file; kiểm tra CSV chứa quote/newline/formula; test database timeout; xác minh report đủ số dòng và thứ tự.

**Quan sát:** `export_duration`, `export_bytes`, `active_exports`, `export_cancelled`, GC heap/LOH, Gen 2 collections, CPU, pod restarts, database query duration và correlation ID; không log nội dung CSV.

**Tài liệu tham khảo:** [Microsoft: Large Object Heap](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/large-object-heap), [ASP.NET Core request/response operations](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/middleware/request-response), [System.IO.MemoryStream.ToArray](https://learn.microsoft.com/en-us/dotnet/api/system.io.memorystream.toarray).

## Mẫu trả lời trong phỏng vấn

“Em chưa gọi đây là memory leak vì RSS không giảm sau request chưa đủ chứng minh object còn bị giữ. Em sẽ đối chiếu peak export concurrency với allocation rate, live managed heap và LOH, sau đó lấy profile trên staging. Luồng hiện tại dùng MemoryStream và ToArray có thể giữ cả buffer gốc lẫn bản sao, làm peak memory tăng theo kích thước file nhân số request. Nếu CSV có thể tạo tuần tự, em sẽ stream từ database đến response, giới hạn số export đồng thời và truyền RequestAborted; cần lưu ý database connection sẽ được giữ trong lúc stream. Với báo cáo rất lớn hoặc chạy lâu, em ưu tiên background job ghi Blob và trả trạng thái. Em sẽ load test với file lớn, client disconnect và đo memory, GC, latency trước khi quyết định.”

## Câu hỏi đào sâu

1. Nếu streaming khiến connection pool cạn khi client tải chậm, bạn thay đổi kiến trúc thế nào?
2. Nếu sau full GC live heap nhỏ nhưng RSS vẫn cao, bạn kiểm chứng tiếp điều gì?
3. Khi nào `ArrayPool<byte>` là tối ưu hợp lý, và rủi ro khi trả buffer sai là gì?

## Lỗi trả lời thường gặp

- Khẳng định cứ memory tăng là leak.
- Chỉ gọi `GC.Collect()` hoặc tăng RAM.
- Dùng `ToArray()` sau khi đã streaming từ database.
- Bỏ qua cancellation, concurrency và thời gian giữ DB connection.
- Không phân biệt dữ liệu nhạy cảm với telemetry an toàn.

# Câu 2 — Kubernetes rolling deployment: API có readiness xanh nhưng checkout trả 502

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Kubernetes, reverse proxy, deployment, observability, incident response

## Bối cảnh

Một API checkout .NET 8 chạy trong Kubernetes với 6 replicas, nhận request từ React frontend qua ingress. Khi rolling deployment bản mới, trong 2–4 phút tỷ lệ 502 tăng lên 3%; bên ngoài khoảng thời gian rollout, lỗi gần như bằng 0. Kubernetes cho thấy phần lớn pods Ready. Lỗi thường liên quan đến request thanh toán có thời gian xử lý 8–15 giây. Đội release đề xuất tăng replicas lên 12; QA chưa tái hiện được trong staging. Chưa biết 502 được sinh ở ingress, upstream proxy hay ứng dụng.

## Câu hỏi chính

Bạn sẽ xử lý incident này như thế nào từ ổn định hệ thống đến root-cause analysis và triển khai bản sửa an toàn, khi chưa biết vấn đề nằm ở readiness, graceful shutdown, connection draining, timeout hay dependency?

## Câu hỏi làm rõ nên cân nhắc

1. 502 xuất phát từ ingress nào, có upstream status và request ID không?
2. Pod termination grace period, `preStop`, readiness probe và rollout strategy hiện tại?
3. API có idempotency key cho thanh toán không; retry từ frontend/proxy có thể tạo charge trùng?
4. Endpoint readiness kiểm tra điều gì; request đang chạy có được drain khi pod nhận SIGTERM không?
5. Có thay đổi timeout, keep-alive, Service endpoint hoặc payment provider trong release không?

## Gợi ý tư duy

### Gợi ý 1
Tách hành động giảm thiệt hại khỏi điều tra sâu.

### Gợi ý 2
Xem timeline pod lifecycle, EndpointSlice changes và upstream errors tại ingress.

### Gợi ý 3
So sánh termination grace period với request duration, proxy drain và `HostOptions.ShutdownTimeout`; phân biệt 502, 503, 504.

## Cấu trúc trả lời đề xuất

1. Xác định tỷ lệ lỗi, doanh thu/rủi ro double charge.
2. Đóng băng rollout hoặc rollback theo tiêu chí đã thống nhất.
3. Correlate ingress → pod → dependency.
4. So sánh các giả thuyết có bằng chứng.
5. Sửa, test dưới tải và rollout canary.
6. Đo sau release và viết postmortem.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Tạm dừng rollout, bảo vệ thanh toán khỏi retry trùng.
- Phân tích ingress upstream errors, pod termination timestamps, readiness transitions, request traces.
- Không coi “pod Ready” là bằng chứng mọi request đều thành công.
- Phân biệt graceful shutdown của ASP.NET Core với propagation delay của Kubernetes endpoints/load balancer.
- Đề xuất kiểm thử rolling deployment dưới tải thật.

### Điểm cộng
- Cân nhắc `maxUnavailable`, `maxSurge`, `terminationGracePeriodSeconds`, `preStop` và ingress/controller-specific draining.
- Theo dõi retry policy của client và payment gateway.
- Chỉ thay đổi timeout khi có bằng chứng, không tăng vô hạn.

### Senior+
- Thiết kế idempotent payment workflow và reconciliation; ưu tiên business correctness hơn việc che 502.
- Đề xuất deployment gates theo error rate, p95 và số giao dịch trạng thái unknown.
- Nêu được rằng 502 không chứng minh request chưa thực hiện side effect.

## Hướng giải quyết tham khảo

**Ảnh hưởng:** 3% checkout failures có thể tạo thất thoát giao dịch và nguy cơ double charge nếu client retry khi trạng thái kết quả không rõ. Xác minh payment provider bằng transaction ID; không tự động retry POST không idempotent. Nếu incident đang diễn ra, tạm dừng rollout; rollback khi phiên bản cũ còn tương thích schema/config. Tránh rollback mù khi migration không backward-compatible.

**Giả thuyết A — termination/draining:** Pod bị loại khỏi endpoints nhưng ingress còn connection cũ; request đang chạy bị ngắt khi process kết thúc. Tìm ingress logs `upstream prematurely closed connection`, pod SIGTERM, `deletionTimestamp`, endpoint changes và trace bị mất. Kiểm tra shutdown timeout và termination grace period. `preStop` chỉ là một phần của lifecycle, không phải bảo đảm mọi ingress lập tức ngừng gửi request.

**Giả thuyết B — readiness:** Probe quá nông (chỉ trả 200) trong khi app chưa load config, dependency hoặc connection warmup. So sánh readiness event với request fail; readiness không nên phụ thuộc mù quáng vào mọi external dependency khiến hệ thống flapping.

**Giả thuyết C — proxy timeout/connection reuse:** Request 8–15 giây có thể vượt cấu hình upstream timeout hoặc bị connection reset. Kiểm tra chính xác ingress/controller, request durations và upstream statuses; timeout thường có thể xuất hiện dưới mã khác nhau tùy layer, không đoán chỉ từ 502.

**Giả thuyết D — ứng dụng/dependency:** Crash, OOM, ThreadPool starvation, DNS hoặc payment API errors trùng với rollout. Đối chiếu CPU/memory, restart reasons, Application Insights dependency spans và logs.

**Remediation có điều kiện:** Nếu xác nhận termination race, cấu hình readiness chuyển NotReady khi bắt đầu drain, cho thời gian endpoint propagation phù hợp, bảo đảm `terminationGracePeriodSeconds` đủ cho request thực tế và ASP.NET Core shutdown timeout tương ứng. Với request thanh toán dài, tốt hơn là API nhận idempotency key, ghi trạng thái giao dịch bền vững, và hỗ trợ truy vấn kết quả thay vì phụ thuộc kết nối HTTP mở suốt quá trình. Nếu lỗi do startup, sửa readiness và warmup; nếu do ingress timeout, thay đổi dựa trên trace và latency budget. Không tăng replicas như phương án chữa chung.

**Kiểm thử:** tạo load checkout trong rolling deployment với requests 1–20 giây; test SIGTERM khi request đang xử lý; test ingress keep-alive/reuse; test payment timeout sau khi provider đã charge; test rollback với migration tương thích. Định nghĩa pass criteria gồm zero duplicate charges, error rate dưới SLO và không có request không thể reconciliation.

**Quan sát:** ingress 502 theo upstream pod/revision, pod Ready/Terminating events, trace ID, deployment version, request duration, checkout attempt ID (không chứa thông tin thẻ), payment provider correlation ID, unknown-payment count, rollout timeline. Alert theo business failures, không chỉ pod health.

**Tài liệu tham khảo:** [Kubernetes: Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination), [Kubernetes: Deployment rolling update](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-update-deployment), [ASP.NET Core hosted services shutdown](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/host/hosted-services).

## Mẫu trả lời trong phỏng vấn

“Em sẽ ưu tiên ngăn tác động tới thanh toán: pause rollout, xác minh transaction bị timeout có được provider xử lý không, và bảo đảm retry đi qua idempotency key. Sau đó em dựng timeline theo ingress logs, pod termination, EndpointSlice và distributed traces. Em không kết luận lỗi do readiness chỉ vì trùng thời điểm rollout. Nếu upstream connection bị đóng trong termination, em sẽ kiểm tra drain behavior, grace period và shutdown timeout; nếu request timeout, em xác minh layer phát sinh và latency budget. Em sẽ tái hiện bằng load test có SIGTERM và keep-alive, triển khai canary với error-rate gate, rồi đo business reconciliation. Tăng replicas chỉ hữu ích nếu có bằng chứng thiếu capacity.”

## Câu hỏi đào sâu

1. Nếu ingress vẫn gửi request vào pod đang terminating dù readiness đã false, bạn xác minh và xử lý thế nào?
2. Nếu gateway đã charge tiền nhưng API trả 502, bạn thiết kế reconciliation và retry ra sao?
3. Nếu tăng `terminationGracePeriodSeconds` làm rollout chậm đáng kể, bạn chọn giải pháp nào khác?

## Lỗi trả lời thường gặp

- Tăng replica hoặc timeout ngay mà không có trace.
- Đồng nhất readiness với việc mọi request thành công.
- Retry checkout POST mà không có idempotency.
- Bỏ qua tính tương thích schema khi rollback.
- Chỉ theo dõi HTTP status, không đo payment state.

# Câu 3 — Hiện đại hóa portal jQuery sang Vue.js mà không dừng hệ thống

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Vue.js, ASP.NET MVC, API contracts, authentication, migration, testing, release engineering

## Bối cảnh

Một enterprise approval portal chạy ASP.NET MVC trên .NET Framework 4.5, IIS/Windows Server, frontend jQuery. Portal có 120 màn hình, 30.000 người dùng, quy trình phê duyệt nhiều bước, role-based authorization và nhiều deep links từ email. Product muốn cải thiện UX bằng Vue.js trong 12 tháng; backend .NET 8 đang được đánh giá nhưng chưa được phê duyệt. Hệ thống phải hoạt động liên tục, có SSO qua Microsoft Entra ID và không được mất audit history. Đội phát triển có 6 engineers, QA automation còn hạn chế.

## Câu hỏi chính

Bạn sẽ lựa chọn kiến trúc và lộ trình modernization như thế nào giữa big-bang rewrite, strangler migration theo màn hình, Vue island trong MVC, và frontend SPA riêng? Hãy nêu tiêu chí quyết định, ranh giới API/auth, kế hoạch release, rollback và cách chứng minh không làm sai quy trình phê duyệt.

## Câu hỏi làm rõ nên cân nhắc

1. Phần nào tạo nhiều lỗi/chi phí bảo trì nhất, và workflow nào có rủi ro cao?
2. SSO hiện dùng cookie, OIDC, SAML hay custom auth; các role/claims được xác minh ở đâu?
3. Có thể thay đổi URL/deep links và session behavior không?
4. Backend có contract/API ổn định hay logic nằm trong MVC controllers/views?
5. Có giới hạn về SEO, accessibility, browser support và deployment pipeline?

## Gợi ý tư duy

### Gợi ý 1
Chọn migration unit nhỏ có khả năng rollback và giá trị đo được.

### Gợi ý 2
Xem xét routing, authentication, authorization, CSRF và ownership của shared UI state.

### Gợi ý 3
Một API façade/BFF có thể hữu ích nếu cần che giấu legacy behavior, nhưng cũng tạo thêm lớp vận hành; so sánh chi phí.

## Cấu trúc trả lời đề xuất

1. Chốt business invariants và constraints.
2. Phân nhóm màn hình theo dependency/risk.
3. So sánh lựa chọn và chọn migration seam.
4. Thiết kế auth/API/URL/data ownership.
5. Đưa ra rollout, tests, observability và rollback.
6. Xác định điều kiện chuyển sang kiến trúc khác.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Không mặc định big-bang rewrite.
- Bảo toàn deep links, workflow state, audit và server-side authorization.
- Thiết kế migration theo vertical slice, feature flag, đo conversion/error và rollback.
- Nêu chiến lược coexistence MVC/jQuery/Vue, tránh hai frontend cùng sửa một state mà không có contract.
- Có Playwright E2E cho các luồng phê duyệt trọng yếu.

### Điểm cộng
- Anti-corruption layer/API façade theo nhu cầu, versioned contracts và contract tests.
- Phân biệt cookie + CSRF với bearer token; không lưu token nhạy cảm trong localStorage theo mặc định.
- Có accessibility, bundle performance và error monitoring.

### Senior+
- Thiết kế schema/API expand-and-contract để backend nâng cấp độc lập.
- Có ownership boundaries, deployment matrix và kế hoạch giảm dần technical debt.
- Định nghĩa exit criteria có thể đo, không biến migration thành dự án vô hạn.

## Hướng giải quyết tham khảo

**Giả định:** legacy MVC vẫn được hỗ trợ trong giai đoạn chuyển đổi; không có yêu cầu SEO công khai; SSO hiện hữu phải giữ tương thích. Trước tiên lập inventory routes, workflow, auth flows, dependencies, integration contracts, lỗi production và độ phủ test. Chọn một màn hình read-heavy, ít ảnh hưởng business để thử nghiệm Vue island; không bắt đầu bằng bước approve/reject có side effect.

**So sánh phương án:**

| Phương án | Khi phù hợp | Rủi ro/chí phí |
|---|---|---|
| Big-bang rewrite | Legacy không thể duy trì, phạm vi nhỏ và có budget/test coverage lớn | Dual maintenance dài, khó parity, rollback khó |
| Vue islands trong MVC | Muốn cải thiện từng màn hình, giữ routing/auth hiện tại | Asset pipeline phức tạp, mixed paradigms, coupling |
| Strangler theo route + API | Có ranh giới nghiệp vụ rõ, cần deploy dần | Routing, shared auth/session, contract versioning |
| SPA độc lập | UX/state phức tạp, API ổn định, đội có năng lực frontend | CORS/cookie/CSRF, BFF, observability và release độc lập |

**Đề xuất ban đầu:** Vue islands hoặc strangler theo route tùy độ phức tạp màn hình. Giữ legacy controller làm authority cho authorization và audit cho đến khi backend boundary đã ổn định. Mỗi slice có URL compatibility, API contract, feature flag và rollback. Nếu SPA riêng dùng cùng origin qua reverse proxy/BFF có thể giảm complexity CORS; xác minh thực tế với auth topology. Với cookie authentication phải chống CSRF; authorization phải kiểm tra ở server theo resource/tenant, không dựa vào Vue route guards. Không tự ý đưa tokens vào browser storage.

**Kế hoạch 12 tháng có điều kiện:** 0–2 tháng lập baseline và smoke/E2E tests; 2–4 tháng pilot một slice; 4–9 tháng mở rộng theo risk và dependency graph; 9–12 tháng retire jQuery trên các vùng đã chuyển, đánh giá tiếp phần legacy còn lại. Đây là mốc lập kế hoạch giả định, phải điều chỉnh theo velocity và acceptance thực tế.

**Data & API:** Không tạo database mới chỉ để phục vụ Vue. Xác định nguồn sự thật duy nhất cho approval status và audit; dùng optimistic concurrency/row version nếu nhiều người duyệt cùng lúc. Nếu API cũ thiếu consistency, xây façade với DTO rõ ràng; không để frontend thực hiện business transition qua nhiều request không atomic. Nâng backend .NET 8 là track riêng: kiểm tra thư viện, auth, IIS hosting, serialization và data access; triển khai expand-and-contract cho schema.

**Quality gate:** Playwright kiểm tra SSO, deep link, approve/reject, concurrency conflict, refresh/back navigation, accessibility và session expiry; API integration tests kiểm tra quyền theo role/resource, CSRF và audit; synthetic monitoring và feature-flag rollback. Theo dõi frontend errors, API p95, workflow completion rate, authorization failures, abandoned approvals và support tickets. Canary theo nhóm người dùng; nếu audit mismatch hoặc unauthorized action, rollback ngay.

**Điều kiện đổi lựa chọn:** Nếu màn hình Vue cần shared state phức tạp và phần lớn routes đã chuyển, SPA/BFF có thể hợp lý; nếu legacy API không thể tách mà không thay đổi nghiệp vụ lớn, ưu tiên backend modularization trước. Tránh xây microservices/Kubernetes chỉ vì modernization.

**Tài liệu tham khảo:** [Vue: Ways of Using Vue](https://vuejs.org/guide/extras/ways-of-using-vue), [Microsoft: ASP.NET Core anti-forgery](https://learn.microsoft.com/en-us/aspnet/core/security/anti-request-forgery), [Microsoft: Migrate from ASP.NET Framework to ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/migration/fx-to-core/).

## Mẫu trả lời trong phỏng vấn

“Em sẽ không chọn rewrite toàn bộ 120 màn hình ngay vì regression risk, deep links và audit history rất lớn. Em sẽ phân loại workflows, lập baseline test rồi thử Vue island trên một màn hình ít side effects. Nếu backend contracts và routing đủ rõ, em chuyển dần theo route bằng strangler; còn nếu API chưa ổn định, em giữ MVC làm nguồn xác thực và nghiệp vụ trước khi tách. Server luôn kiểm tra quyền và ghi audit; Vue chỉ điều khiển UI. Mỗi slice có feature flag, Playwright tests, metrics và rollback. Em tách quyết định frontend modernization khỏi việc nâng .NET backend, dùng expand-and-contract để giảm coupling. Khi số màn hình chuyển đổi đủ lớn và shared state phức tạp, em mới cân nhắc SPA/BFF độc lập dựa trên số liệu.”

## Câu hỏi đào sâu

1. Nếu Product yêu cầu một SPA độc lập ngay từ tháng đầu, bạn phản biện hoặc chấp nhận dựa trên tiêu chí nào?
2. Nếu user mở cùng một approval trên tab MVC và tab Vue, bạn bảo đảm consistency và audit thế nào?
3. Nếu Entra ID login hoạt động nhưng deep links sau login trả về trang sai, bạn truy vết ở những layer nào?

## Lỗi trả lời thường gặp

- Xem modernization là thay framework UI, bỏ qua nghiệp vụ.
- Chuyển authorization sang frontend route guard.
- Bỏ qua cookie/CSRF/session/deep links.
- Không có test baseline hoặc rollback per slice.
- Đề xuất microservices mà không có service boundary hay lợi ích đo được.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Memory tăng không đồng nghĩa memory leak; cần đo live heap, allocations, LOH và peak concurrency trước khi tối ưu.
- Rolling deployment là vấn đề end-to-end từ ingress đến application shutdown và external side effects, không chỉ là trạng thái Ready của pod.
- Modernization thành công cần bảo toàn business invariants, tách migration seams, kiểm soát auth/contracts và rollback từng bước.

## Mẫu tư duy cần nhớ

1. **Measure before optimize:** tách số liệu thực nghiệm khỏi giả thuyết.
2. **Stabilize before deep investigation:** hạn chế thiệt hại trước khi tìm root cause.
3. **Treat ambiguous failure as potentially successful side effect:** đặc biệt với thanh toán và retry.
4. **Migrate by reversible slices:** ưu tiên thay đổi nhỏ, có kiểm thử và rollback.
5. **Complexity has a cost:** chỉ thêm hệ thống/phân lớp khi giải quyết rủi ro đã chứng minh.
