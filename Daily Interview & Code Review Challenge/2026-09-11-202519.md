# Code Review Challenge 1 — HTTP retry giúp “ổn định hơn” nhưng đôi lúc charge khách hai lần và giữ request quá lâu

**Chủ đề:** C#/.NET 8, ASP.NET Core, `HttpClient`, timeout, retry, idempotency, `CancellationToken`, dependency failure, connection management, error classification, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core checkout API gọi payment provider qua HTTP để tạo charge. Application chạy trên nhiều instances phía sau load balancer.

Yêu cầu:

- một checkout attempt không được tạo nhiều charge cho cùng một payment intent;
- payment provider đôi lúc trả `429`, `502`, `503` hoặc timeout;
- provider có thể đã xử lý request thành công nhưng response bị mất trên network;
- client checkout có request timeout khoảng 15 giây;
- cancellation từ client cần được propagate hợp lý;
- retry chỉ được thực hiện khi operation an toàn để retry;
- không được tạo connection/socket pressure dưới load;
- operations cần biết dependency latency, retry count, timeout, ambiguous outcome và duplicate-charge risk.

Sau khi team thêm retry để giảm lỗi transient, production xuất hiện:

- một số khách bị charge hai lần sau network timeout;
- p95 checkout tăng mạnh khi provider degraded;
- request phía client đã timeout nhưng backend vẫn tiếp tục gọi provider;
- lúc traffic cao, số outbound connections tăng mạnh;
- logs chỉ ghi `Payment failed after retry`, khó biết lần nào provider có thể đã commit charge;
- team cho rằng “POST bị lỗi 5xx hoặc timeout thì retry 3 lần là chuẩn”.

## Đoạn code cần review

```csharp
public sealed record ChargeRequest(
    Guid OrderId,
    decimal Amount,
    string Currency,
    string CardToken);

public sealed class PaymentGateway
{
    private readonly ILogger<PaymentGateway> _logger;

    public PaymentGateway(ILogger<PaymentGateway> logger)
    {
        _logger = logger;
    }

    public async Task<ChargeResponse> ChargeAsync(
        ChargeRequest request,
        CancellationToken cancellationToken)
    {
        using var client = new HttpClient
        {
            BaseAddress = new Uri("https://payments.example.com"),
            Timeout = TimeSpan.FromSeconds(30)
        };

        for (var attempt = 1; attempt <= 3; attempt++)
        {
            try
            {
                var response = await client.PostAsJsonAsync(
                    "/v1/charges",
                    new
                    {
                        orderId = request.OrderId,
                        amount = request.Amount,
                        currency = request.Currency,
                        cardToken = request.CardToken
                    });

                if ((int)response.StatusCode >= 500 ||
                    response.StatusCode == HttpStatusCode.TooManyRequests)
                {
                    await Task.Delay(TimeSpan.FromSeconds(2));
                    continue;
                }

                response.EnsureSuccessStatusCode();

                return (await response.Content
                    .ReadFromJsonAsync<ChargeResponse>())!;
            }
            catch (TaskCanceledException ex)
            {
                _logger.LogWarning(ex, "Payment timeout, retrying");
            }
        }

        throw new InvalidOperationException("Payment failed after retry");
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong payment flow.
2. Xác định reliability, performance, security và maintainability concerns.
3. Giải thích production impact, đặc biệt ở timeout, retry và high concurrency.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà vẫn giữ kiến trúc đơn giản nếu có thể.
6. Giải thích testing cho ambiguous outcome, cancellation, throttling và dependency failure.
7. Đề xuất production telemetry để chứng minh retry không tạo duplicate side effects.

## Câu hỏi gợi mở

1. Nếu provider đã tạo charge nhưng response bị mất, request retry tiếp theo có ý nghĩa gì?
2. `OrderId` trong JSON có tự động trở thành idempotency key ở phía provider không?
3. `CancellationToken` của caller hiện được dùng ở những outbound operation nào?

## Gợi ý

### Gợi ý 1

### Gợi ý 2

Hãy phân biệt rõ timeout/cancellation/HTTP status với **business outcome**. Một transport exception không chứng minh rằng remote side effect chưa xảy ra.

## Kết quả code review tham khảo

### Critical — Retry POST tạo charge mà không có idempotency contract

**Vấn đề:**  
Mỗi retry gửi lại cùng business operation nhưng không có stable idempotency key được provider xác nhận hỗ trợ.

**Tại sao xảy ra:**  
HTTP timeout hoặc mất response chỉ nói caller không biết kết quả. Provider có thể đã tạo charge trước khi connection lỗi. Retry mù có thể tạo side effect lần nữa.

**Ảnh hưởng production:**  
Duplicate charge, refund/support cost, reconciliation phức tạp và mất niềm tin người dùng.

**Cách sửa:**  
Dùng provider-supported idempotency key ổn định cho cùng payment intent, lưu key/outcome ở domain persistence, và định nghĩa rõ cách query/reconcile trạng thái khi outcome ambiguous. Nếu provider không có idempotency/query semantics đủ mạnh, không thể biến retry tùy ý thành an toàn chỉ bằng code HTTP client.

### High — Caller cancellation không được propagate tới HTTP call hoặc delay

**Vấn đề:**  
Method nhận `CancellationToken` nhưng `PostAsJsonAsync` và `Task.Delay` không dùng token.

**Tại sao xảy ra:**  
Cancellation không tự động truyền qua chỉ vì method signature nhận token.

**Ảnh hưởng production:**  
Checkout request đã bị client/gateway hủy nhưng backend vẫn giữ resources và có thể tiếp tục tạo charge mà caller không còn chờ kết quả.

**Cách sửa:**  
Truyền token vào HTTP send/read/delay phù hợp. Tuy nhiên không diễn giải cancellation sau khi request đã gửi là rollback; nếu side effect có thể đã xảy ra, outcome vẫn phải được reconcile bằng idempotency/status lookup.

### High — Timeout/retry budget vượt xa end-to-end SLO

**Vấn đề:**  
Mỗi `HttpClient` có timeout 30 giây và loop có thể thử tới ba lần cộng delay, trong khi caller budget khoảng 15 giây.

**Tại sao xảy ra:**  
Retry policy được thiết kế độc lập với end-to-end deadline.

**Ảnh hưởng production:**  
Request pile-up, thread/task/resource retention, gateway timeout trước application và retry amplification khi provider đang degraded.

**Cách sửa:**  
Thiết kế một overall request budget nhỏ hơn upstream deadline, phân bổ per-attempt timeout nếu thật sự retry, và dừng khi remaining budget không đủ. Retry count không nên là hằng số tách rời latency budget.

### High — Tạo `HttpClient` mới cho mỗi payment operation

**Vấn đề:**  
Mỗi call tạo/dispose một `HttpClient` riêng.

**Tại sao xảy ra:**  
Connection pooling nằm ở handler lifetime; tạo handler/client không đúng lifecycle có thể làm mất reuse và tăng connection churn.

**Ảnh hưởng production:**  
Dưới load có thể tăng TCP/TLS setup, connection pressure và latency; DNS/lifetime management cũng khó kiểm soát.

**Cách sửa:**  
Dùng `IHttpClientFactory`/typed client hoặc một properly managed long-lived handler/client, cấu hình timeout/resilience tập trung theo dependency.

### High — Retry mọi `429`/5xx với cùng fixed delay mà không phân loại lỗi

**Vấn đề:**  
`429` và mọi status `>= 500` đều retry giống nhau; code không xem `Retry-After`, không dùng jitter và không phân biệt error có thể permanent.

**Tại sao xảy ra:**  
Policy dựa trên status family thay vì dependency contract và retryability.

**Ảnh hưởng production:**  
Khi provider quá tải, nhiều application instances có thể retry đồng bộ sau 2 giây, tạo retry storm. Một số lỗi server-side business validation được biểu diễn không chuẩn cũng có thể bị retry vô ích.

**Cách sửa:**  
Retry chỉ các failure được provider/documentation xác định transient, honor server backoff signal khi phù hợp, dùng exponential backoff + jitter và bounded attempts trong deadline. Side effect vẫn phải idempotent trước khi retry.

### Medium — `TaskCanceledException` conflates caller cancellation với timeout

**Vấn đề:**  
Catch block gắn mọi `TaskCanceledException` nhãn `Payment timeout`.

**Tại sao xảy ra:**  
Cancellation có thể đến từ caller token, configured timeout hoặc transport behavior; chúng có operational meaning khác nhau.

**Ảnh hưởng production:**  
Telemetry sai khiến incident investigation nhầm root cause và retry khi lẽ ra phải dừng.

**Cách sửa:**  
Phân biệt caller cancellation (`cancellationToken.IsCancellationRequested`) với timeout budget và log/classify outcome rõ ràng. Không retry khi caller đã hủy.

### Medium — Response không được dispose sớm trong retry path

**Vấn đề:**  
`HttpResponseMessage` không nằm trong `using`, đặc biệt các response `429/5xx` bị bỏ qua sau khi delay.

**Tại sao xảy ra:**  
Code loop tiếp mà không đảm bảo response resources được giải phóng đúng lifecycle.

**Ảnh hưởng production:**  
Có thể làm chậm connection reuse và tăng resource pressure tùy content/handler behavior.

**Cách sửa:**  
Dispose response đúng scope; nếu cần đọc error body thì giới hạn kích thước và không giữ resource qua delay.

### Medium — Null-forgiving operator che giấu invalid provider response

**Vấn đề:**  
`ReadFromJsonAsync<ChargeResponse>()!` giả định body luôn hợp lệ và non-null sau status success.

**Tại sao xảy ra:**  
Transport success không đảm bảo response schema/body đúng contract.

**Ảnh hưởng production:**  
Có thể phát sinh `NullReferenceException` ở downstream hoặc mất thông tin failure chính xác.

**Cách sửa:**  
Validate payload và required fields; classify malformed provider response thành dependency protocol error, không retry mù nếu side effect có thể đã xảy ra.

### Medium — Không có durable payment attempt/outcome state

**Vấn đề:**  
Code coi HTTP method call là toàn bộ business transaction nhưng không thể hiện payment intent/idempotency state trong persistence.

**Tại sao xảy ra:**  
Distributed side effect có failure window giữa local system và provider.

**Ảnh hưởng production:**  
Sau process crash hoặc timeout, application khó biết nên retry, query provider hay yêu cầu manual reconciliation.

**Cách sửa:**  
Persist payment attempt với stable business identifier và states như `Pending`, `Succeeded`, `Ambiguous`, `Failed` phù hợp domain; update state dựa trên provider idempotent response/status query. Không cần Saga framework nếu một nhỏ state machine và reconciliation job là đủ.

### Low — Observability không cho biết attempt/outcome semantics

**Vấn đề:**  
Log chỉ nói timeout/retry và final failure.

**Tại sao xảy ra:**  
Không có structured fields cho payment intent, attempt number, dependency status, elapsed budget, idempotency result hoặc ambiguous outcome.

**Ảnh hưởng production:**  
Khó chứng minh duplicate charge đến từ retry, user double-submit hay provider behavior.

**Cách sửa:**  
Ghi metrics/traces theo payment attempt ID an toàn, retry reason, remaining deadline, dependency latency, outcome category và reconciliation result; không log card token hoặc secret payment data.

## Phiên bản đề xuất

Ví dụ dưới đây giả định provider hỗ trợ một `Idempotency-Key` ổn định và endpoint status lookup theo payment intent. Cụ thể header/API phải theo contract thực tế của provider.

```csharp
public sealed class PaymentGateway
{
    private readonly HttpClient _client;
    private readonly ILogger<PaymentGateway> _logger;

    public PaymentGateway(
        HttpClient client,
        ILogger<PaymentGateway> logger)
    {
        _client = client;
        _logger = logger;
    }

    public async Task<ChargeResponse> ChargeAsync(
        ChargeRequest request,
        string paymentIntentId,
        CancellationToken cancellationToken)
    {
        using var overallCts = CancellationTokenSource
            .CreateLinkedTokenSource(cancellationToken);
        overallCts.CancelAfter(TimeSpan.FromSeconds(12));

        var ct = overallCts.Token;
        Exception? lastError = null;

        for (var attempt = 1; attempt <= 2; attempt++)
        {
            using var message = new HttpRequestMessage(
                HttpMethod.Post,
                "/v1/charges")
            {
                Content = JsonContent.Create(new
                {
                    orderId = request.OrderId,
                    amount = request.Amount,
                    currency = request.Currency,
                    cardToken = request.CardToken
                })
            };

            message.Headers.TryAddWithoutValidation(
                "Idempotency-Key",
                paymentIntentId);

            try
            {
                using var response = await _client.SendAsync(
                    message,
                    HttpCompletionOption.ResponseHeadersRead,
                    ct);

                if (response.IsSuccessStatusCode)
                {
                    var charge = await response.Content
                        .ReadFromJsonAsync<ChargeResponse>(cancellationToken: ct);

                    return charge
                        ?? throw new PaymentProtocolException(
                            "Provider returned an empty success response.");
                }

                if (!IsTransient(response.StatusCode) || attempt == 2)
                    throw await CreateProviderExceptionAsync(response, ct);

                var delay = GetBackoff(response, attempt);
                await Task.Delay(delay, ct);
            }
            catch (OperationCanceledException)
                when (!cancellationToken.IsCancellationRequested &&
                      attempt < 2)
            {
                lastError = new TimeoutException(
                    "Payment provider attempt timed out.");
            }
            catch (HttpRequestException ex) when (attempt < 2)
            {
                lastError = ex;
            }
        }

        throw new PaymentOutcomeAmbiguousException(
            paymentIntentId,
            lastError);
    }

    private static bool IsTransient(HttpStatusCode statusCode)
        => statusCode is HttpStatusCode.TooManyRequests
            or HttpStatusCode.BadGateway
            or HttpStatusCode.ServiceUnavailable
            or HttpStatusCode.GatewayTimeout;

    private static TimeSpan GetBackoff(
        HttpResponseMessage response,
        int attempt)
    {
        if (response.Headers.RetryAfter?.Delta is { } retryAfter)
            return retryAfter;

        return TimeSpan.FromMilliseconds(250 * Math.Pow(2, attempt));
    }

    private static async Task<Exception> CreateProviderExceptionAsync(
        HttpResponseMessage response,
        CancellationToken ct)
    {
        var body = await response.Content.ReadAsStringAsync(ct);
        return new PaymentProviderException(
            response.StatusCode,
            body.Length > 512 ? body[..512] : body);
    }
}
```

Typed client registration nên cấu hình base address và handler lifecycle ở composition root. Nếu dùng resilience pipeline/library, policy vẫn phải tuân theo cùng invariant: **không retry non-idempotent side effect chỉ vì library hỗ trợ retry**.

Khi final outcome ambiguous, application nên lưu state và dùng provider status lookup/reconciliation dựa trên `paymentIntentId` thay vì tiếp tục POST vô hạn.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách ba khái niệm:

1. transport attempt;
2. business payment intent;
3. final business outcome.

Stable idempotency key gắn nhiều transport attempts vào một business operation. Overall timeout nằm trong upstream budget. Caller cancellation được propagate, nhưng sau khi request đã có thể tới provider, application vẫn không giả định cancellation nghĩa là charge chưa xảy ra.

Typed `HttpClient` giải quyết connection lifecycle; retry policy chỉ áp dụng cho failures được xem là transient và có bounded attempt/budget. Trường hợp không thể xác nhận outcome được nâng thành trạng thái `Ambiguous` để reconciliation thay vì đoán.

## Trade-offs

- Idempotency phụ thuộc contract thật của payment provider; client-side key không có giá trị nếu server không enforce.
- Fewer retries giảm retry amplification nhưng có thể làm tăng số operation phải reconcile asynchronously.
- Persist payment-attempt state tăng schema/workflow complexity nhưng đổi lại có audit trail và recovery semantics rõ ràng.
- Short timeout bảo vệ SLO nhưng có thể classify nhiều slow successes thành ambiguous; status lookup phải đủ tốt.
- Circuit breaker có thể hữu ích khi provider outage kéo dài, nhưng không thay thế idempotency và không nhất thiết cần nếu traffic nhỏ và timeout/backoff đã đủ.

## Cách kiểm thử

1. **Ambiguous-outcome integration test:** provider fake tạo charge nhưng drop connection trước response; retry với cùng key phải không tạo charge thứ hai và reconciliation xác định đúng outcome.
2. **Cancellation test:** cancel caller trước/during outbound request; xác minh không retry sau caller cancellation và trạng thái business không bị kết luận sai.
3. **Throttling test:** trả `429` với/không `Retry-After`; xác minh backoff bounded trong overall deadline và không tạo synchronized retry burst.
4. **Load test:** chạy concurrency gần peak, đo connection reuse, outbound sockets, p95/p99, retries/request và resource usage.
5. **Protocol-failure test:** success status nhưng body null/malformed; xác minh outcome được classify rõ, không retry mù một side effect đã có thể xảy ra.

## Quan sát trong production

Theo dõi:

- dependency p50/p95/p99 latency theo provider endpoint;
- attempts per payment intent và retry reason;
- `429`/5xx/network-timeout/caller-cancellation counts;
- ambiguous payment outcomes và reconciliation success/age;
- duplicate/idempotent-replay responses từ provider nếu có;
- active outbound connections, connection errors và request queueing;
- end-to-end checkout deadline consumed trước/sau payment call;
- trace correlation bằng payment-intent identifier không chứa card token/secret;
- alert khi ambiguous outcomes, retry ratio hoặc provider latency tăng vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Nếu provider không hỗ trợ idempotency key nhưng có endpoint tra cứu charge theo merchant reference, bạn sẽ thiết kế recovery thế nào?
2. Khi nào bạn thêm circuit breaker, và metric nào chứng minh nó đang giúp thay vì làm fail-fast quá mức?
3. Nếu checkout request bị cancel ngay sau khi provider trả success nhưng trước khi local database lưu kết quả, bạn xử lý failure window đó ra sao?

# Code Review Challenge 2 — API tìm order càng lật trang sâu càng chậm và đôi lúc vừa trùng vừa mất bản ghi

**Chủ đề:** SQL Server, query design, `OFFSET/FETCH`, deterministic ordering, sargability, composite indexes, parameterized filtering, execution plans, pagination consistency, performance troubleshooting  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một back-office API cho phép support tìm orders theo tenant, date range, customer email và status. SQL Server có khoảng 180 triệu rows trong bảng `Orders`; mỗi tenant lớn có vài triệu rows.

Yêu cầu:

- page size tối đa 100;
- user thường xem vài trang đầu, nhưng có thể export/search sâu;
- dữ liệu mới vẫn được insert liên tục;
- p95 của interactive search cần dưới khoảng 1 giây;
- kết quả phải ổn định, không được dễ dàng trùng/mất row khi user chuyển trang;
- email search hiện là exact match case-insensitive;
- team cần chẩn đoán bằng execution plan/IO/CPU trước khi thêm index tùy ý.

Production ghi nhận:

- page 1 thường nhanh, page 5.000 mất nhiều giây;
- CPU/reads tăng mạnh ở SQL khi support chạy nhiều deep searches;
- cùng một user đôi khi thấy một order lặp lại ở hai page hoặc biến mất giữa hai lần bấm Next;
- query theo email chậm hơn đáng kể;
- team đề xuất tạo index riêng cho mọi combination của filters.

## Đoạn code cần review

```sql
CREATE OR ALTER PROCEDURE dbo.SearchOrders
    @TenantId uniqueidentifier,
    @FromDate datetime2,
    @ToDate datetime2,
    @Email nvarchar(320) = NULL,
    @Status int = NULL,
    @Page int = 1,
    @PageSize int = 50
AS
BEGIN
    SELECT
        o.Id,
        o.OrderNumber,
        o.CustomerEmail,
        o.Status,
        o.TotalAmount,
        o.CreatedAtUtc
    FROM dbo.Orders AS o
    WHERE o.TenantId = @TenantId
      AND CAST(o.CreatedAtUtc AS date)
          BETWEEN CAST(@FromDate AS date) AND CAST(@ToDate AS date)
      AND (@Email IS NULL OR LOWER(o.CustomerEmail) = LOWER(@Email))
      AND (@Status IS NULL OR o.Status = @Status)
    ORDER BY o.CreatedAtUtc DESC
    OFFSET (@Page - 1) * @PageSize ROWS
    FETCH NEXT @PageSize ROWS ONLY;
END
```

## Nhiệm vụ của ứng viên

1. Xác định correctness problems trong pagination/query semantics.
2. Xác định performance, reliability và maintainability concerns.
3. Giải thích production impact dựa trên data volume và concurrent writes.
4. Ưu tiên findings theo severity thay vì chỉ nói “thiếu index”.
5. Đề xuất query/API pagination design đã sửa và index strategy có căn cứ.
6. Giải thích cách test correctness, execution plan và load.
7. Đề xuất production telemetry/database observations để chứng minh improvement.

## Câu hỏi gợi mở

1. `ORDER BY CreatedAtUtc DESC` có tạo total ordering nếu nhiều orders có cùng timestamp không?
2. `OFFSET` phải làm bao nhiêu work khi `@Page = 5000`?
3. Bọc indexed column bằng `CAST` hoặc `LOWER` ảnh hưởng thế nào tới khả năng seek?
4. Nếu một order mới được insert trước page boundary giữa hai requests, page-number pagination có thể thay đổi ra sao?
5. Có thực sự cần hỗ trợ jump trực tiếp tới page 5.000 cho interactive UI không?

## Gợi ý

### Gợi ý 1

Primary issue không chỉ là index. Có hai lớp riêng: **pagination correctness dưới dữ liệu thay đổi** và **work tăng theo offset** khi page sâu.

## Kết quả code review tham khảo

### High — `ORDER BY CreatedAtUtc` không deterministic khi timestamp trùng nhau

**Vấn đề:**  
Nhiều rows có thể có cùng `CreatedAtUtc`, nhưng query không có tie-breaker unique.

**Tại sao xảy ra:**  
SQL Server không hứa thứ tự ổn định giữa rows có cùng sort key nếu không có thêm key xác định thứ tự.

**Ảnh hưởng production:**  
Rows ở boundary có thể đổi vị trí giữa executions, gây duplicate/missing rows khi phân trang ngay cả khi dataset không đổi đáng kể.

**Cách sửa:**  
Dùng total ordering, ví dụ `ORDER BY CreatedAtUtc DESC, Id DESC`, và cursor chứa cả hai giá trị.

### High — Deep `OFFSET` có cost tăng theo số rows phải bỏ qua

**Vấn đề:**  
Page 5.000 với page size 50 yêu cầu database đi qua một lượng lớn qualifying rows trước khi trả 50 rows tiếp theo.

**Tại sao xảy ra:**  
`OFFSET` diễn tả vị trí tương đối trong ordered result, không phải điểm bắt đầu seek trực tiếp theo business key.

**Ảnh hưởng production:**  
Logical reads, CPU, memory/sort work và latency tăng theo page depth; nhiều deep queries đồng thời có thể làm ảnh hưởng workload khác.

**Cách sửa:**  
Dùng keyset/seek pagination cho interactive Next/Previous: client gửi cursor `(CreatedAtUtc, Id)` của row cuối page trước. Nếu business thật sự cần arbitrary page jump/export, tách use case và cân nhắc async export/reporting flow.

### High — Page-number pagination không ổn định dưới concurrent inserts/updates

**Vấn đề:**  
Giữa request page 1 và page 2, rows mới có thể xuất hiện trước offset hoặc sort key/status có thể thay đổi.

**Tại sao xảy ra:**  
Offset được tính trên snapshot mới ở mỗi request; boundary không gắn với row cụ thể từ page trước.

**Ảnh hưởng production:**  
User có thể thấy duplicate hoặc bỏ sót orders trong browsing session.

**Cách sửa:**  
Keyset cursor giảm boundary shift cho forward traversal. Nếu requirement đòi snapshot-consistent toàn bộ multi-page session, cần explicit snapshot/version strategy và chấp nhận thêm complexity; đừng giả định cursor tự tạo immutable snapshot.

### High — `CAST(o.CreatedAtUtc AS date)` làm predicate kém sargable và thay đổi semantics thời gian

**Vấn đề:**  
Function được áp dụng lên column trong predicate và cả parameters bị cast xuống date.

**Tại sao xảy ra:**  
Database khó tận dụng ordered index range theo nguyên `datetime2`; đồng thời time-of-day bị loại bỏ nên `@FromDate/@ToDate` không còn giữ semantics ban đầu.

**Ảnh hưởng production:**  
Scan/read nhiều hơn và date boundary có thể không đúng expectation nếu caller truyền exact timestamps.

**Cách sửa:**  
Nếu API dùng timestamp range, viết `CreatedAtUtc >= @FromDate AND CreatedAtUtc < @ToDateExclusive`. Nếu API nhận calendar dates, chuyển chúng thành half-open UTC interval ở boundary có timezone semantics rõ ràng trước khi query.

### High — `LOWER(CustomerEmail) = LOWER(@Email)` có thể cản index seek không cần thiết

**Vấn đề:**  
Function được áp dụng lên column cho exact-match email.

**Tại sao xảy ra:**  
Trong nhiều schema, case-insensitivity nên được giải quyết bằng collation/normalized stored value thay vì function per row. Behavior cụ thể phụ thuộc column/database collation.

**Ảnh hưởng production:**  
Email search trên tenant lớn có thể đọc nhiều rows hơn và tăng CPU.

**Cách sửa:**  
Xác minh collation. Nếu đã case-insensitive, so sánh trực tiếp. Nếu domain cần canonicalization độc lập collation, lưu normalized email (ví dụ computed/persisted hoặc write-time normalized column) và index/query cột đó.

### Medium — Optional-filter pattern có thể tạo execution plan không phù hợp cho nhiều shapes

**Vấn đề:**  
`(@Email IS NULL OR ...)` và `(@Status IS NULL OR ...)` gom nhiều query shapes có selectivity rất khác vào một statement.

**Tại sao xảy ra:**  
Một plan tối ưu cho tenant/date-only có thể không tốt cho exact email lookup hoặc status-heavy query; parameter distribution/skew cũng ảnh hưởng plan choice.

**Ảnh hưởng production:**  
Latency có thể biến động lớn theo parameter combination và tenant size.

**Cách sửa:**  
Đo actual execution plans/Query Store trước. Có thể dùng branch theo vài shapes quan trọng, parameterized dynamic SQL, hoặc compilation strategy phù hợp. Không mặc định `OPTION (RECOMPILE)` hay tạo hàng chục indexes nếu evidence chưa hỗ trợ.

### Medium — Không validate page/page-size boundary

**Vấn đề:**  
Stored procedure cho phép `@Page <= 0`, `@PageSize <= 0` hoặc page size rất lớn nếu caller bypass API validation.

**Tại sao xảy ra:**  
Persistence boundary tin hoàn toàn input.

**Ảnh hưởng production:**  
Có thể lỗi runtime hoặc tạo query quá nặng, đặc biệt nếu endpoint public/internal tooling bị misuse.

**Cách sửa:**  
Validate ở API và database boundary quan trọng; với cursor pagination chỉ cho page size trong bounded range.

### Medium — Index strategy cần phục vụ filter + order + projection, không phải mỗi filter một index

**Vấn đề:**  
Query hiện tại không cho thấy index phù hợp; reaction “một index cho mỗi filter combination” có thể tạo write/storage overhead lớn.

**Tại sao xảy ra:**  
Indexes có cost cho insert/update, maintenance, memory và plan selection; filter combinations tăng tổ hợp rất nhanh.

**Ảnh hưởng production:**  
Có thể cải thiện một query nhưng làm write path chậm, tăng database size và maintenance time.

**Cách sửa:**  
Bắt đầu từ measured dominant query shape. Một candidate cho browsing thường là `(TenantId, CreatedAtUtc DESC, Id DESC)` với `INCLUDE` các projected columns cần thiết; email lookup có thể cần index riêng trên `(TenantId, NormalizedEmail, CreatedAtUtc DESC, Id DESC)` nếu usage chứng minh giá trị. Xác minh bằng plan/IO.

### Medium — Query trả projection rộng hơn mức tối thiểu có thể cần cho list view

**Vấn đề:**  
Mỗi row trả nhiều text/numeric fields; điều này không nghiêm trọng với 50 rows nhưng có thể tăng key lookup/covering-index size nếu tất cả bị `INCLUDE` máy móc.

**Tại sao xảy ra:**  
Tối ưu list query và index design phải cân bằng payload với index width.

**Ảnh hưởng production:**  
Một covering index quá rộng làm tăng storage/write amplification; non-covering plan có thể lookup nhiều dưới broad scans.

**Cách sửa:**  
Xác định fields thực sự cần cho search result, benchmark covering vs lookup, và không thêm large columns vào index chỉ để tránh mọi lookup.

### Low — Không có explicit evidence workflow trước khi thay đổi schema

**Vấn đề:**  
Symptom đã dẫn ngay tới đề xuất thêm indexes.

**Tại sao xảy ra:**  
Không có baseline từ actual execution plan, logical reads, duration, CPU, row estimates, Query Store và wait profile.

**Ảnh hưởng production:**  
Team có thể tối ưu sai bottleneck hoặc tạo regression ở workload khác.

**Cách sửa:**  
Capture representative parameter sets/tenant sizes, actual plan và IO/time metrics trước; benchmark candidate query/index ở realistic data distribution và kiểm tra write impact.

## Phiên bản đề xuất

Ví dụ keyset pagination cho forward navigation, giả định `CreatedAtUtc` và `Id` tạo total ordering. Cursor của page đầu để null; page tiếp theo gửi tuple của row cuối page trước.

```sql
CREATE OR ALTER PROCEDURE dbo.SearchOrdersNextPage
    @TenantId uniqueidentifier,
    @FromUtc datetime2,
    @ToUtcExclusive datetime2,
    @EmailNormalized nvarchar(320) = NULL,
    @Status int = NULL,
    @AfterCreatedAtUtc datetime2 = NULL,
    @AfterId uniqueidentifier = NULL,
    @PageSize int = 50
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 100
        THROW 50001, 'PageSize must be between 1 and 100.', 1;

    SELECT TOP (@PageSize)
        o.Id,
        o.OrderNumber,
        o.CustomerEmail,
        o.Status,
        o.TotalAmount,
        o.CreatedAtUtc
    FROM dbo.Orders AS o
    WHERE o.TenantId = @TenantId
      AND o.CreatedAtUtc >= @FromUtc
      AND o.CreatedAtUtc < @ToUtcExclusive
      AND (@EmailNormalized IS NULL
           OR o.NormalizedCustomerEmail = @EmailNormalized)
      AND (@Status IS NULL OR o.Status = @Status)
      AND (
            @AfterCreatedAtUtc IS NULL
            OR o.CreatedAtUtc < @AfterCreatedAtUtc
            OR (
                o.CreatedAtUtc = @AfterCreatedAtUtc
                AND o.Id < @AfterId
            )
          )
    ORDER BY
        o.CreatedAtUtc DESC,
        o.Id DESC;
END
```

Một candidate index cho dominant tenant/date browsing path có thể là:

```sql
CREATE INDEX IX_Orders_Tenant_Created_Id
ON dbo.Orders
(
    TenantId,
    CreatedAtUtc DESC,
    Id DESC
)
INCLUDE
(
    OrderNumber,
    CustomerEmail,
    Status,
    TotalAmount
);
```

Index này chỉ là hypothesis cần verify, không phải câu trả lời luôn đúng. Nếu `Status` có selectivity cao và phần lớn requests filter status, key order khác hoặc filtered index có thể tốt hơn. Nếu email exact search là workload riêng có tần suất đáng kể, một index theo `(TenantId, NormalizedCustomerEmail, CreatedAtUtc, Id)` có thể hợp lý.

API nên trả opaque cursor encode các ordering keys thay vì expose raw page number. Cursor nên được validate/sign nếu client không được phép chỉnh filter state; ít nhất nó phải gắn với cùng sort/filter contract để tránh dùng cursor của query khác.

## Giải thích thiết kế sau khi sửa

Keyset pagination biến “bỏ qua N rows” thành “bắt đầu sau row X”. Với index phù hợp, database có thể seek gần boundary thay vì work tỷ lệ với page depth.

Tie-breaker `Id` tạo total ordering. Half-open time range giữ predicate sargable và tránh lỗi boundary `23:59:59.999...`. Normalized email tách case-normalization khỏi runtime function trên mỗi row.

Optional filters vẫn cần plan analysis. Không có một stored procedure shape tối ưu cho mọi tenant/filter distribution. Senior-level decision ở đây là dùng evidence để chọn một vài dominant query shapes thay vì cố thiết kế index cho mọi permutation.

## Trade-offs

- Keyset pagination rất tốt cho Next/Previous nhưng không hỗ trợ jump tới arbitrary page number dễ dàng.
- Cursor không tạo snapshot bất biến; nếu rows cũ thay đổi sort/filter keys giữa requests, semantics cần được định nghĩa.
- Covering index giảm lookups nhưng tăng storage và write amplification.
- Normalized email column đơn giản hóa query nhưng cần consistency rule ở write path/computed column.
- Tách async export khỏi interactive search thêm workflow nhưng bảo vệ OLTP database khỏi deep arbitrary scans.

## Cách kiểm thử

1. **Pagination correctness test:** tạo nhiều rows cùng `CreatedAtUtc`, paginate qua toàn set và xác minh không duplicate/missing với stable dataset.
2. **Concurrent-write test:** insert new orders giữa page requests và kiểm tra semantics của keyset cursor; document rõ snapshot guarantee không được cung cấp nếu không có thêm mechanism.
3. **Database performance test:** so sánh actual execution plan, logical reads, CPU và elapsed time của page đầu/page sâu giữa OFFSET và keyset trên data volume/distribution gần production.
4. **Filter-shape test:** benchmark tenant/date-only, email exact, status và email+status; kiểm tra plan stability/Query Store thay vì chỉ một parameter set.
5. **Load test:** chạy nhiều concurrent support searches cùng normal OLTP traffic, đo database CPU, waits, p95/p99 và write latency trước/sau index.

## Quan sát trong production

Theo dõi:

- query duration p50/p95/p99 theo query shape;
- logical reads/CPU/row count và execution-plan regressions qua Query Store;
- frequency của deep page requests để chứng minh có cần support arbitrary page jump;
- index usage, size và write overhead;
- SQL waits, CPU, memory grant/spill và blocking trong incident;
- API search latency/error rate theo tenant-size bucket và filter type;
- số cursor validation errors và page size distribution;
- alert khi query-plan regression hoặc database resource usage vượt baseline sau deployment.

## Câu hỏi phỏng vấn mở rộng

1. Nếu product bắt buộc “nhảy tới trang 5.000”, bạn sẽ giữ tính năng đó thế nào mà không làm OLTP query path chịu chi phí vô hạn?
2. Nếu users yêu cầu một export nhất quán đúng snapshot tại thời điểm bấm Export, bạn sẽ thiết kế khác interactive pagination ra sao?
3. Nếu `Status` thay đổi thường xuyên và được đưa vào index key/include, bạn sẽ đánh giá write amplification như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Retry và idempotency phải được thiết kế cùng nhau; transport failure không chứng minh remote side effect chưa xảy ra.
- End-to-end timeout budget quan trọng hơn một `Timeout` hoặc retry count đặt riêng lẻ ở dependency client.
- Managed `HttpClient` lifecycle, cancellation và structured dependency telemetry là phần của production correctness dưới load.
- Deep `OFFSET` pagination tạo work tăng theo page depth và không tự bảo đảm kết quả ổn định khi dataset thay đổi.
- Sargability, deterministic ordering và index design phải được kiểm chứng bằng execution plan/IO/CPU trên data distribution thực tế.

## Mẫu tư duy cần nhớ

- Design retry together with idempotency and failure windows.
- Budget latency end-to-end, không tối ưu từng dependency cô lập.
- Distinguish transport outcome from business outcome.
- Measure execution plans and logical reads before adding indexes.
- Prefer stable seek boundaries over positional offsets for large mutable datasets.
