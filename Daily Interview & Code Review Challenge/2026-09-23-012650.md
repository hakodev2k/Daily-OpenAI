# Code Review Challenge 1 — Upload file chạy ổn ở dev nhưng làm API cạn memory và mở đường cho file độc hại

**Chủ đề:** ASP.NET Core, C#/.NET, file upload, Azure Blob Storage, memory, security, cancellation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API cho phép người dùng nội bộ upload tài liệu đính kèm. File sau đó được lưu vào Azure Blob Storage và metadata được ghi vào SQL Server. API chạy nhiều Azure App Service instances. Ở môi trường test, file thường dưới 5 MB; production có lúc người dùng upload đồng thời nhiều file 100–300 MB.

Gần đây memory của App Service tăng đột biến trong giờ cao điểm, một số request trả 5xx và process đôi lúc restart. Security team cũng yêu cầu review vì filename và `ContentType` đến trực tiếp từ browser. Business yêu cầu không làm hỏng trải nghiệm upload nhưng chưa xác định rõ maximum file size, loại file hợp lệ hay malware-scanning workflow.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly DocumentsDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        DocumentsDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        var blobName = $"uploads/{file.FileName}";
        var blob = _container.GetBlobClient(blobName);

        using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);
        buffer.Position = 0;

        await blob.UploadAsync(
            buffer,
            new BlobHttpHeaders { ContentType = file.ContentType });

        var document = new Document
        {
            Id = Guid.NewGuid(),
            FileName = file.FileName,
            BlobName = blobName,
            ContentType = file.ContentType,
            Size = file.Length,
            UploadedAtUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} ({Size} bytes) to {BlobName}",
            file.FileName,
            file.Length,
            blobName);

        return Ok(new { document.Id, document.FileName });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness, memory/performance và security problems.
2. Giải thích production impact khi nhiều upload lớn chạy đồng thời.
3. Phân tích trust boundary của filename, MIME type và file content.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design tốt hơn cho streaming, validation và Blob naming.
6. Nêu cách kiểm thử load, cancellation, malicious input và partial failure.
7. Nêu telemetry cần quan sát trong production.

## Câu hỏi gợi mở

1. Điều gì xảy ra với managed memory khi 20 request cùng copy file 200 MB vào `MemoryStream`?
2. Browser gửi `Content-Type` có phải bằng chứng file thực sự thuộc loại đó không?
3. Hai người upload cùng `file.FileName` thì Blob key hiện tại có semantics gì?
4. Nếu client disconnect giữa upload, operation có dừng không?
5. Nếu Blob upload thành công nhưng SQL `SaveChangesAsync` thất bại, hệ thống còn lại trạng thái nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **buffering, untrusted metadata/content, object identity và partial failure**.

### Gợi ý 2

Hãy xem upload như một luồng dữ liệu lớn qua nhiều failure boundaries. Streaming giảm peak memory nhưng không tự giải quyết validation, authorization hay consistency.

## Kết quả code review tham khảo

### Critical — Không có giới hạn kích thước upload ở application boundary

**Vấn đề:** Handler chỉ từ chối file rỗng, không áp maximum size theo business/security policy.

**Tại sao xảy ra:** Code giả định input production giống test và không xem request body là tài nguyên có giới hạn.

**Ảnh hưởng production:** Nhiều file lớn đồng thời có thể tiêu thụ memory, bandwidth, request slots và Blob throughput; attacker hoặc client lỗi có thể gây resource exhaustion.

**Cách sửa:** Xác định size policy với Product/Security, enforce ở các layer phù hợp và trả lỗi rõ ràng. Không dựa duy nhất vào `IFormFile.Length`; hosting/request limits và application validation phải nhất quán.

### High — Copy toàn bộ file vào `MemoryStream` làm peak memory tăng theo kích thước × concurrency

**Vấn đề:** File được copy đầy đủ vào một buffer thứ hai trước khi upload Blob.

**Tại sao xảy ra:** `MemoryStream` giữ toàn bộ payload trong managed memory thay vì truyền stream theo pipeline.

**Ảnh hưởng production:** Upload 200 MB đồng thời có thể tạo allocation rất lớn, GC pressure và process restart/OOM risk. Tổng memory còn phụ thuộc buffering ở request layer nên không thể giả định chỉ có đúng một copy.

**Cách sửa:** Sau khi xác định request/file limits, stream từ input sang Blob khi API/library path cho phép; tránh materialize toàn payload chỉ để chuyển tiếp. Đo memory/GC dưới concurrency thực tế.

### High — Tin `FileName` và `ContentType` do client cung cấp

**Vấn đề:** Client-controlled filename được dùng làm storage key và MIME type được lưu/trả cho Blob như thể đã được xác minh.

**Tại sao xảy ra:** Browser metadata bị coi là trusted classification.

**Ảnh hưởng production:** Tên file bất thường/collision, content-type spoofing và file nguy hiểm có thể đi qua workflow. Nếu file sau này được serve inline, MIME/content handling sai có thể tăng security risk.

**Cách sửa:** Treat cả hai là untrusted. Sinh server-side object key độc lập; chỉ lưu original filename như metadata đã normalize/sanitize cho display. Xác định allowlist và content validation/scanning theo threat model; khi download, kiểm soát response headers/disposition thay vì tin metadata upload.

### High — Blob name không có identity riêng và có thể collision

**Vấn đề:** `uploads/{file.FileName}` không gắn document/user/tenant/generated ID.

**Tại sao xảy ra:** Display name bị dùng đồng thời làm storage identity.

**Ảnh hưởng production:** Hai uploads cùng tên có thể conflict/overwrite hoặc fail tùy upload options/service behavior; semantics không rõ và có thể làm metadata trỏ sai object.

**Cách sửa:** Tạo `DocumentId` trước, dùng key server-generated như `uploads/{tenantId}/{documentId}` và lưu original filename riêng. Chọn overwrite/precondition semantics explicit.

### High — Không propagate request cancellation

**Vấn đề:** `CopyToAsync`, Blob upload và `SaveChangesAsync` không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:** Handler bỏ qua lifetime của HTTP request.

**Ảnh hưởng production:** Client đã disconnect nhưng server vẫn có thể tiếp tục copy/upload/DB work, lãng phí tài nguyên trong lúc load cao.

**Cách sửa:** Propagate cancellation token qua các operation hỗ trợ cancellation; đồng thời thiết kế cleanup/consistency vì cancellation có thể xảy ra sau khi một side effect đã commit.

### Medium — Blob và SQL không có atomic transaction chung

**Vấn đề:** Blob được tạo trước, sau đó SQL insert có thể thất bại.

**Tại sao xảy ra:** Hai external resources không cùng local database transaction.

**Ảnh hưởng production:** Orphan Blob có thể tồn tại dù không có metadata; retry có thể tạo thêm objects nếu naming thay đổi.

**Cách sửa:** Chấp nhận và thiết kế consistency boundary: ví dụ tạo document record trạng thái `Pending`, upload theo generated ID rồi chuyển `Ready`, kèm cleanup/reconciliation cho failed/stale uploads. Không giả vờ có distributed transaction nếu requirement không cần.

### Medium — Không có authorization/ownership policy thể hiện tại endpoint

**Vấn đề:** Snippet không cho thấy ai được phép upload vào document/tenant context nào.

**Tại sao xảy ra:** Authentication thường bị nhầm với authorization.

**Ảnh hưởng production:** Nếu route thực tế chỉ dựa vào authenticated user mà thiếu resource policy, người dùng có thể upload ngoài phạm vi quyền.

**Cách sửa:** Áp policy/resource authorization theo requirement thực tế và derive tenant/user ownership từ trusted identity, không từ form fields do client tự khai.

### Medium — Logging raw filename có thể tạo log-quality/security issue

**Vấn đề:** Raw client-controlled filename được ghi thẳng vào structured log.

**Tại sao xảy ra:** Metadata untrusted đi vào observability pipeline không có normalization/redaction policy.

**Ảnh hưởng production:** Log injection/display confusion, PII leakage hoặc cardinality/noise tùy logging backend.

**Cách sửa:** Log generated document/blob ID là primary correlation; normalize/redact filename theo policy và không log sensitive metadata không cần thiết.

## Phiên bản đề xuất

```csharp
[Authorize(Policy = "CanUploadDocuments")]
[HttpPost("upload")]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    const long maxBytes = 50L * 1024 * 1024; // Example policy; align with configured request limits.

    if (file is null || file.Length <= 0 || file.Length > maxBytes)
        return BadRequest("Invalid file size");

    var documentId = Guid.NewGuid();
    var originalName = Path.GetFileName(file.FileName);
    var blobName = $"uploads/{documentId:N}";

    // Content type is client metadata, not proof of file type.
    // Perform allowlist/signature/scanning according to the actual threat model.
    var document = new Document
    {
        Id = documentId,
        FileName = originalName,
        BlobName = blobName,
        ContentType = "application/octet-stream",
        Size = file.Length,
        Status = "Pending",
        UploadedAtUtc = DateTime.UtcNow
    };

    _db.Documents.Add(document);
    await _db.SaveChangesAsync(cancellationToken);

    try
    {
        await using var input = file.OpenReadStream();
        var blob = _container.GetBlobClient(blobName);

        await blob.UploadAsync(
            input,
            new BlobUploadOptions
            {
                HttpHeaders = new BlobHttpHeaders
                {
                    ContentType = "application/octet-stream"
                }
            },
            cancellationToken);

        document.Status = "Ready";
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Uploaded document {DocumentId} ({Size} bytes)",
            document.Id,
            document.Size);

        return Ok(new { document.Id, document.FileName });
    }
    catch
    {
        document.Status = "Failed";

        try
        {
            await _db.SaveChangesAsync(CancellationToken.None);
        }
        catch (Exception statusError)
        {
            _logger.LogError(statusError,
                "Failed to persist failure status for document {DocumentId}",
                document.Id);
        }

        throw;
    }
}
```

Đây là một skeleton minh họa boundary, không phải policy hoàn chỉnh. Maximum size phải khớp hosting/request configuration. Nếu file cần malware scanning, trạng thái `Pending/Scanning/Ready/Rejected` và quyền download phải phản ánh workflow đó. Với upload cực lớn hoặc yêu cầu scale cao, direct-to-Blob upload bằng short-lived, least-privilege SAS có thể là alternative, nhưng khi đó backend vẫn phải kiểm soát authorization, object key, size/type workflow và completion verification.

## Giải thích thiết kế sau khi sửa

Storage identity được tách khỏi display filename. File không còn được copy toàn bộ vào một `MemoryStream`; operation truyền cancellation và biểu diễn partial state rõ hơn. Database không thể làm Blob + SQL thành một local atomic commit, nên design thừa nhận partial failure và cho phép reconciliation. `application/octet-stream` trong ví dụ tránh giả vờ đã xác minh MIME type; production cần policy cụ thể cho allowed content và cách serve/download.

## Trade-offs

Streaming giảm peak memory nhưng làm validation phức tạp nếu validator cần random access hoặc toàn file. Virus scanning có thể thêm latency và cần quarantine/asynchronous workflow. Pending-state + reconciliation thêm state machine/operations complexity. Direct-to-Blob giảm backend bandwidth nhưng tăng complexity quanh SAS issuance, client retry, completion verification và abandoned uploads. Nếu file luôn rất nhỏ và concurrency thấp, giải pháp đơn giản hơn có thể đủ — nhưng phải dựa trên measurement và threat model.

## Cách kiểm thử

1. **Load test:** upload nhiều file gần maximum size đồng thời; đo process memory, allocations/GC, request p95/p99 và 5xx.
2. **Security test:** filename bất thường, MIME spoofing, disallowed signatures và unauthorized tenant/user; xác minh storage key không phụ thuộc raw filename.
3. **Failure-path test:** Blob thành công nhưng DB update `Ready` fail; reconciliation phát hiện và đưa object về trạng thái hợp lệ.
4. **Cancellation test:** client abort giữa upload; xác minh work dừng hợp lý và partial object/state được cleanup hoặc reconcile.
5. **Integration test:** hai uploads cùng original filename tạo hai document/blob identities độc lập.

## Quan sát trong production

Theo dõi upload count/bytes, concurrent uploads, request duration p95/p99, 413/4xx/5xx, process working set, GC/allocations, App Service restarts, Blob dependency duration/failures và SQL dependency failures. Structured logs dùng `DocumentId`, correlation ID, authenticated subject/tenant identifier phù hợp và status transition. Alert khi failed/pending age tăng, memory pressure vượt baseline hoặc orphan reconciliation count tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn backend streaming và khi nào chọn client direct upload bằng SAS?
2. Nếu malware scanning mất 30 giây, bạn thay đổi API contract và document state machine thế nào?
3. Nếu Product yêu cầu giữ original filename trong Blob path để dễ support, bạn sẽ đáp ứng mục tiêu đó mà không biến filename thành identity như thế nào?

# Code Review Challenge 2 — Endpoint phân trang SQL nhanh ở page 1 nhưng timeout ở page 20.000

**Chủ đề:** SQL Server, pagination, dynamic SQL, indexes, execution plan, API performance, security  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API cho trang quản trị đơn hàng gọi stored procedure dưới đây. UI cho phép sort theo một số cột và nhảy trực tiếp tới bất kỳ page nào. Dataset production đã tăng lên khoảng hàng chục triệu rows. Page đầu thường nhanh, nhưng các page sâu có p95 lên nhiều giây và đôi lúc timeout. CPU/reads trên SQL Server tăng mạnh khi người dùng export hoặc bot nội bộ duyệt nhiều page.

Team đề xuất thêm Redis để cache mọi page. Chưa có execution plan gần nhất, chưa biết distribution của `Status`, và chưa xác định requirement “jump to arbitrary page” có thực sự bắt buộc cho mọi client hay không.

## Đoạn code cần review

```sql
CREATE PROCEDURE dbo.SearchOrders
    @Status nvarchar(30) = NULL,
    @Page int = 1,
    @PageSize int = 50,
    @SortColumn nvarchar(50) = N'CreatedAtUtc',
    @SortDirection nvarchar(4) = N'DESC'
AS
BEGIN
    DECLARE @Offset int = (@Page - 1) * @PageSize;

    DECLARE @sql nvarchar(max) = N'
        SELECT
            o.Id,
            o.CustomerId,
            o.Status,
            o.TotalAmount,
            o.CreatedAtUtc,
            o.UpdatedAtUtc,
            o.Notes
        FROM dbo.Orders o
        WHERE (@Status IS NULL OR o.Status = @Status)
        ORDER BY ' + @SortColumn + N' ' + @SortDirection + N'
        OFFSET ' + CAST(@Offset AS nvarchar(20)) + N' ROWS
        FETCH NEXT ' + CAST(@PageSize AS nvarchar(20)) + N' ROWS ONLY;';

    EXEC sp_executesql
        @sql,
        N'@Status nvarchar(30)',
        @Status = @Status;
END
```

## Nhiệm vụ của ứng viên

1. Xác định security, correctness và performance concerns.
2. Giải thích vì sao deep `OFFSET` có thể ngày càng đắt dù chỉ trả 50 rows.
3. Nêu evidence cần thu thập trước khi thêm index/cache.
4. Ưu tiên findings theo severity.
5. Đề xuất query/API design tốt hơn tùy requirement về arbitrary-page navigation.
6. Nêu cách kiểm thử plan/performance với data distribution thực tế.
7. Nêu production telemetry cần theo dõi.

## Câu hỏi gợi mở

1. `@SortColumn` và `@SortDirection` được ghép trực tiếp vào SQL text có trust boundary gì?
2. Database phải làm gì với các rows đứng trước `OFFSET` khi page càng sâu?
3. Sort có deterministic không nếu nhiều orders có cùng `CreatedAtUtc`?
4. Predicate `(@Status IS NULL OR o.Status = @Status)` có thể tạo plan behavior nào với distribution khác nhau?
5. Nếu UI chỉ có “Next/Previous” thì có cần giữ page-number semantics không?

## Gợi ý

### Gợi ý 1

Có hai nhóm rủi ro chính: **dynamic ORDER BY không được allowlist** và **pagination strategy không scale theo vị trí page**.

### Gợi ý 2

Đừng bắt đầu bằng Redis hay một index đoán mò. Hãy lấy actual execution plan, logical reads, duration và kiểm tra index/order/filter shape; sau đó xem cursor/keyset có phù hợp product semantics không.

## Kết quả code review tham khảo

### Critical — Dynamic `ORDER BY` cho phép SQL injection nếu input không được allowlist

**Vấn đề:** `@SortColumn` và `@SortDirection` được concatenate trực tiếp vào SQL text.

**Tại sao xảy ra:** Identifiers/direction không được parameterize giống scalar values bằng cách đang dùng, nhưng code cũng không map input vào một tập giá trị tin cậy.

**Ảnh hưởng production:** Caller kiểm soát được input có thể thay đổi SQL text; blast radius phụ thuộc quyền database của application account.

**Cách sửa:** Map API sort keys vào allowlist cố định của column expressions và direction `ASC`/`DESC`; không concatenate raw user input. Giữ DB principal least-privilege.

### High — Deep `OFFSET` có work tăng theo số rows phải bỏ qua

**Vấn đề:** Page 20.000 yêu cầu database xác định ordered result rồi skip một lượng rows rất lớn trước khi trả page nhỏ.

**Tại sao xảy ra:** Offset pagination biểu diễn vị trí bằng số lượng rows đứng trước, không bằng seek boundary.

**Ảnh hưởng production:** Logical reads/CPU/duration có thể tăng mạnh ở page sâu, gây contention và timeout dưới concurrency.

**Cách sửa:** Nếu UX cho phép sequential navigation, dùng keyset/seek pagination dựa trên stable ordered key. Nếu arbitrary page là requirement thật, chấp nhận cost hoặc thiết kế alternative phù hợp sau khi đo; không tuyên bố keyset thay thế được mọi semantics.

### High — Sort không deterministic khi cột sort không unique

**Vấn đề:** `ORDER BY CreatedAtUtc` không có tie-breaker.

**Tại sao xảy ra:** Nhiều rows có thể cùng timestamp/value.

**Ảnh hưởng production:** Rows có thể xuất hiện lặp hoặc bị bỏ giữa pages, đặc biệt khi concurrent inserts/updates thay đổi ordered set.

**Cách sửa:** Thêm unique/stable tie-breaker như `Id` vào order và cursor, ví dụ `(CreatedAtUtc, Id)` với direction nhất quán.

### High — Không validate `@Page` và `@PageSize`

**Vấn đề:** Giá trị 0/âm/quá lớn có thể tạo offset không hợp lệ hoặc request cực đắt; multiplication bằng `int` cũng có boundary cần kiểm soát.

**Tại sao xảy ra:** Stored procedure tin pagination input.

**Ảnh hưởng production:** Error, abuse hoặc query quá lớn làm tăng database load.

**Cách sửa:** Enforce page/page-size range ở API và database boundary khi phù hợp; dùng bounded maximum và kiểu tính toán tránh overflow.

### Medium — Optional predicate có thể tạo plan không phù hợp cho mọi parameter distribution

**Vấn đề:** `(@Status IS NULL OR o.Status = @Status)` gom nhiều selectivity patterns vào một query shape.

**Tại sao xảy ra:** Plan phù hợp cho “all statuses” có thể khác plan phù hợp cho status hiếm/phổ biến; actual behavior phụ thuộc data, indexes, statistics và optimizer decisions.

**Ảnh hưởng production:** Một số parameter values có thể có reads/latency rất khác nhau.

**Cách sửa:** Không đoán một fix duy nhất. Capture actual plans/query metrics cho representative values; cân nhắc query shapes tách biệt/dynamic predicate/recompile strategy chỉ khi evidence chứng minh cần thiết.

### Medium — Query trả `Notes` dù list view có thể không cần

**Vấn đề:** Wide payload có thể làm tăng row size/I/O/network và ảnh hưởng khả năng dùng covering index.

**Tại sao xảy ra:** List query dùng entity-like projection thay vì projection theo UI requirement.

**Ảnh hưởng production:** Extra reads/network và index design đắt hơn, đặc biệt ở high-volume list/export.

**Cách sửa:** Chỉ select fields list view thực sự cần; detail endpoint lấy dữ liệu rộng hơn nếu phù hợp.

### Medium — Index strategy không được gắn với filter + sort access pattern

**Vấn đề:** Snippet không cho biết index nào hỗ trợ `Status` và order columns.

**Tại sao xảy ra:** Team đang nhảy sang cache trước khi xem plan/reads.

**Ảnh hưởng production:** SQL có thể scan/sort lượng dữ liệu lớn hoặc dùng index không phù hợp.

**Cách sửa:** Dựa trên actual execution plan, logical reads, selectivity và workload để thiết kế index. Một index có key order phù hợp với filter/sort và INCLUDE projection có thể hữu ích, nhưng không nên thêm máy móc vì write/storage cost.

### Low — Procedure thiếu explicit `SET NOCOUNT ON`

**Vấn đề:** Procedure không tắt row-count messages.

**Tại sao xảy ra:** Operational convention chưa được áp dụng.

**Ảnh hưởng production:** Thường nhỏ so với các vấn đề trên; có thể tạo protocol noise cho một số clients/workflows.

**Cách sửa:** Thêm `SET NOCOUNT ON` theo convention nếu phù hợp.

## Phiên bản đề xuất

Ví dụ dưới đây giả định Product chấp nhận cursor-based navigation theo `CreatedAtUtc DESC, Id DESC`. Nếu arbitrary page number là requirement bắt buộc, cần thiết kế khác thay vì giả vờ cursor giữ nguyên UX.

```sql
CREATE PROCEDURE dbo.SearchOrdersNext
    @Status nvarchar(30) = NULL,
    @PageSize int = 50,
    @AfterCreatedAtUtc datetime2 = NULL,
    @AfterId bigint = NULL
AS
BEGIN
    SET NOCOUNT ON;

    IF @PageSize < 1 OR @PageSize > 200
        THROW 50001, 'Invalid page size', 1;

    SELECT TOP (@PageSize)
        o.Id,
        o.CustomerId,
        o.Status,
        o.TotalAmount,
        o.CreatedAtUtc,
        o.UpdatedAtUtc
    FROM dbo.Orders AS o
    WHERE
        (@Status IS NULL OR o.Status = @Status)
        AND
        (
            @AfterCreatedAtUtc IS NULL
            OR o.CreatedAtUtc < @AfterCreatedAtUtc
            OR (o.CreatedAtUtc = @AfterCreatedAtUtc AND o.Id < @AfterId)
        )
    ORDER BY
        o.CreatedAtUtc DESC,
        o.Id DESC;
END
```

API trả opaque cursor chứa boundary values thay vì cho client tự tạo SQL semantics. Nếu cần nhiều sort options, server map từng public sort key sang một query shape/allowlisted expression; cursor phải encode đầy đủ stable sort tuple tương ứng. Index chỉ được chốt sau khi xem workload. Với query ví dụ, một candidate index có thể bắt đầu từ access pattern như `(Status, CreatedAtUtc DESC, Id DESC)` nếu `Status` filter là phổ biến và selectivity/workload justify; nhưng trường hợp `@Status IS NULL`, distribution và write cost có thể khiến lựa chọn khác tốt hơn.

## Giải thích thiết kế sau khi sửa

Keyset pagination seek từ boundary cuối thay vì đếm và bỏ qua N rows, nên phù hợp hơn cho sequential deep navigation trên large ordered set. `Id` làm tie-breaker để order deterministic. Projection hẹp hơn. Dynamic raw identifiers bị loại khỏi query ví dụ. Tuy nhiên optional `Status` vẫn cần đo bằng actual plan và representative workload; reference solution không giả định một index/plan luôn tối ưu.

## Trade-offs

Keyset pagination không hỗ trợ “jump trực tiếp page 20.000” theo nghĩa page-number tự nhiên và cursor có thể phức tạp với nhiều sort fields. Offset vẫn hợp lý cho dataset nhỏ hoặc UX thật sự cần random page access với cost chấp nhận được. Cursor cần versioning/signing hoặc validation nếu chứa state mà client không nên sửa. Composite indexes cải thiện reads nhưng tăng storage/write cost. Redis không giải quyết injection và có thể tạo invalidation/cardinality problem nếu cache hàng nghìn combinations của filter/sort/page.

## Cách kiểm thử

1. **Database performance test:** seed distribution gần production; so sánh logical reads, CPU, duration và actual plans ở page đầu/deep page hoặc cursor depth tương đương.
2. **Security test:** gửi sort column/direction ngoài allowlist và injection payload; xác minh API từ chối trước khi tạo SQL text.
3. **Correctness test:** nhiều rows cùng `CreatedAtUtc`, concurrent inserts giữa hai page requests; xác minh tie-breaker/cursor không gây duplicate do order ambiguity.
4. **Parameter-distribution test:** `@Status = NULL`, status rất phổ biến và status hiếm; capture plan/reads để phát hiện regressions.
5. **Load test:** concurrent list/export traffic; đo DB CPU, waits, query duration p95/p99 và API timeout rate.

## Quan sát trong production

Theo dõi API request p95/p99 theo endpoint/filter/sort class, timeout/5xx, SQL dependency duration trong Application Insights, Query Store/top queries, logical reads/CPU, waits, execution-plan regressions và connection-pool pressure. Log pagination mode/cursor version và bounded page size, không log raw untrusted SQL fragments. Alert khi query duration/reads hoặc timeout rate vượt baseline thay vì chỉ nhìn average latency.

## Câu hỏi phỏng vấn mở rộng

1. Nếu Product bắt buộc hiển thị “page 1 of 243,812” và cho jump bất kỳ page, bạn sẽ giữ requirement đó thế nào mà không hứa keyset giải quyết được?
2. Với sort `TotalAmount ASC`, cursor và deterministic tie-breaker phải thay đổi ra sao?
3. Khi nào cache list results là hợp lý, và bạn sẽ chứng minh cache đáng complexity trước khi thêm Redis như thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- File upload là resource- và security-boundary: streaming, size limits, untrusted metadata, cancellation và partial failure phải được thiết kế cùng nhau.
- Storage identity không nên phụ thuộc filename do client cung cấp; Blob + SQL cần explicit consistency/reconciliation strategy vì không có local atomic transaction chung.
- Deep offset pagination có cost khác page đầu; cần đo actual plans/reads và cân nhắc keyset khi UX cho phép sequential navigation.
- Dynamic SQL identifiers phải được allowlist; parameterization scalar values không tự bảo vệ raw `ORDER BY` fragments.
- Index/cache chỉ nên được thêm sau khi evidence xác định bottleneck và access pattern.

## Mẫu tư duy cần nhớ

- Treat client metadata as untrusted until verified.
- Bound resource consumption before optimizing throughput.
- Model partial failure explicitly across external resources.
- Measure SQL plans/reads before adding index or cache.
- Match pagination semantics to actual product navigation requirements.
