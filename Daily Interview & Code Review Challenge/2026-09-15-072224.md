# Code Review Challenge 1 — Upload file chạy tốt ở dev nhưng production có thể bị memory spike, overwrite và upload file nguy hiểm

**Chủ đề:** ASP.NET Core, file upload, streaming, security, concurrency, resource limits, cancellation, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một internal document portal cho phép nhân viên upload PDF và ảnh. API chạy nhiều instances sau load balancer. Product yêu cầu file tối đa 200 MB, tên hiển thị phải giữ nguyên cho UI, file phải tải xuống được sau khi upload và request bị hủy thì server không nên tiếp tục ghi file vô ích.

Developer thêm endpoint sau và test local thấy hoạt động tốt:

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly IWebHostEnvironment _environment;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        IWebHostEnvironment environment,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _environment = environment;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file == null || file.Length == 0)
            return BadRequest("Empty file");

        var extension = Path.GetExtension(file.FileName);
        if (extension != ".pdf" && extension != ".jpg" && extension != ".png")
            return BadRequest("Unsupported file");

        var uploadRoot = Path.Combine(_environment.WebRootPath, "uploads");
        Directory.CreateDirectory(uploadRoot);

        var path = Path.Combine(uploadRoot, file.FileName);

        await using var output = System.IO.File.Create(path);
        await file.CopyToAsync(output);

        _db.Documents.Add(new Document
        {
            FileName = file.FileName,
            StoragePath = path,
            Size = file.Length,
            UploadedAt = DateTime.UtcNow
        });

        await _db.SaveChangesAsync();

        _logger.LogInformation("Uploaded {FileName} to {Path}", file.FileName, path);

        return Ok(new { file.FileName, file.Length, path });
    }
}
```

Production dự kiến có hàng trăm concurrent uploads trong giờ cao điểm. Security team yêu cầu không được tin filename/content do client gửi. Operations cũng nhắc rằng containers/instances có thể bị replace bất kỳ lúc nào.

## Nhiệm vụ của ứng viên

Hãy review change này như một production PR. Xác định các vấn đề security, correctness, concurrency, memory/storage, cancellation và distributed-hosting. Ưu tiên findings theo severity; đề xuất corrected design/code; nêu failure behavior khi storage hoặc database lỗi; và đưa ra testing cùng production telemetry.

## Câu hỏi gợi mở

1. `file.FileName` có an toàn để dùng làm filesystem path không?
2. Extension có chứng minh content thực sự là PDF/JPEG/PNG không?
3. Điều gì xảy ra nếu hai users upload cùng filename trên hai requests hoặc hai instances?
4. Local disk của một instance có phải durable/shared storage phù hợp không?
5. Nếu file đã ghi xong nhưng `SaveChangesAsync` thất bại thì hệ thống ở trạng thái nào?

## Gợi ý

### Gợi ý 1

Hãy tách **display filename** do user cung cấp khỏi **storage object key** do server tạo.

### Gợi ý 2

Xem upload như một resource-intensive workflow có size limits, streaming, cancellation, authorization, content validation và partial-failure cleanup.

## Kết quả code review tham khảo

### Critical — Dùng trực tiếp client filename làm storage path

`file.FileName` là untrusted input. Dùng trực tiếp trong `Path.Combine` tạo rủi ro path manipulation, overwrite và collision. Display name và physical/object key phải tách nhau. Server nên sinh opaque key/ID, normalize metadata và không trả physical path cho client.

### Critical — Upload validation chỉ dựa trên extension

Extension là metadata do client kiểm soát. Một file executable hoặc payload khác có thể được đổi tên thành `.pdf`. Cần allowlist content type chỉ như signal ban đầu, kiểm tra signature/magic bytes hoặc parser phù hợp với risk model, giới hạn loại file và cân nhắc malware scanning/quarantine trước khi file trở thành downloadable/public.

### High — Local `wwwroot/uploads` không phù hợp với multi-instance/durable storage

Request có thể ghi file vào instance A nhưng request download sau đó vào instance B. Instance replacement cũng có thể làm mất file. Ngoài ra đặt upload dưới web root có thể vô tình biến file thành static content ngoài authorization path. Dùng durable shared/object storage như Blob Storage hoặc một storage service abstraction; download phải đi qua authorization hoặc signed-access policy phù hợp.

### High — Không có explicit request/file size protection

Requirement là 200 MB nhưng endpoint không enforce business limit. Multipart parsing/buffering behavior và hosting limits phải được cấu hình có chủ đích. Với file lớn/concurrency cao, cần streaming strategy phù hợp thay vì giả định `IFormFile` luôn có memory profile an toàn. Giới hạn request size ở nhiều lớp cần nhất quán.

### High — Collision/overwrite race

Hai requests cùng filename có thể cùng ghi một path. `File.Create` truncate file hiện có. Đây vừa là correctness bug vừa có thể là security issue nếu user A ghi đè file của user B. Server-generated unique storage key + ownership metadata loại bỏ assumption filename là identity.

### High — Storage và database có partial-failure window

Nếu file upload thành công nhưng DB commit thất bại, orphan object còn lại. Nếu DB commit trước rồi storage fail thì metadata có thể trỏ tới object không tồn tại. Không có distributed transaction tự nhiên giữa SQL và object storage; cần state machine/compensation, ví dụ `Pending` → upload → `Ready`, cleanup job cho orphan/stale pending records, hoặc storage-first với deterministic cleanup.

### Medium — CancellationToken không được propagate

Endpoint không nhận `CancellationToken`/`HttpContext.RequestAborted`; copy và DB operation tiếp tục dù client disconnect. Với 200 MB uploads, điều này lãng phí bandwidth, I/O và connection capacity. Propagate cancellation nhưng thiết kế cleanup cho partial object.

### Medium — Trả physical storage path và log path không cần thiết

Response trả `path`, làm lộ internal filesystem layout. Log cũng nên dùng document ID/storage key an toàn thay vì raw path nếu không cần. Client chỉ cần document ID, display name và download URL/API contract.

### Medium — Authorization/ownership không xuất hiện

Internal portal vẫn cần authorization. Upload phải gắn owner/tenant/access policy từ trusted identity, không từ client metadata. Download sau này phải enforce cùng policy.

### Medium — Không có backpressure/concurrency strategy

Hàng trăm uploads × 200 MB có thể saturate network, temp storage, disk/object-storage connections và request slots. Cần capacity test, bounded concurrency/rate limits theo user/tenant khi phù hợp, direct-to-object-storage upload nếu architecture cho phép, và quota.

## Phiên bản sửa tham khảo

Một hướng đơn giản là backend cấp document ID/storage key và stream vào storage abstraction thay vì `wwwroot`:

```csharp
[HttpPost("upload")]
[RequestSizeLimit(210_000_000)]
public async Task<IActionResult> Upload(
    IFormFile file,
    CancellationToken cancellationToken)
{
    if (file.Length is <= 0 or > 200_000_000)
        return BadRequest("Invalid file size");

    var displayName = Path.GetFileName(file.FileName);
    var documentId = Guid.NewGuid();
    var storageKey = $"documents/{documentId:N}";

    await using var input = file.OpenReadStream();

    var detectedType = await _fileInspector.ValidateAsync(
        input,
        displayName,
        cancellationToken);

    input.Position = 0;

    await _storage.UploadAsync(
        storageKey,
        input,
        detectedType,
        cancellationToken);

    try
    {
        _db.Documents.Add(new Document
        {
            Id = documentId,
            DisplayName = displayName,
            StorageKey = storageKey,
            Size = file.Length,
            Status = DocumentStatus.Ready,
            UploadedAt = _clock.GetUtcNow().UtcDateTime
        });

        await _db.SaveChangesAsync(cancellationToken);
    }
    catch
    {
        await _storage.TryDeleteAsync(storageKey, CancellationToken.None);
        throw;
    }

    return CreatedAtAction(
        nameof(GetDocument),
        new { id = documentId },
        new { id = documentId, fileName = displayName });
}
```

Đây vẫn chỉ là một baseline. Với upload lớn hoặc traffic cao, có thể dùng direct upload đến object storage bằng short-lived scoped upload token/SAS, rồi backend finalize metadata sau validation. Malware scanning có thể yêu cầu trạng thái `PendingScan` trước khi file được phép download.

## Testing strategy

- Unit tests cho filename normalization, type allowlist, size boundary và authorization policy.
- Integration tests với storage emulator/test container và database cho success, DB failure sau upload, storage failure, cancellation giữa chừng và cleanup.
- Security tests với traversal-like filenames, double extensions, spoofed MIME, malformed files và unauthorized download.
- Concurrency tests với nhiều uploads cùng display filename để chứng minh không overwrite.
- Load tests với file sizes thực tế, đo memory, temp disk, network, request latency và storage throttling.
- Failure-injection test khi storage chậm/timeout và instance shutdown giữa upload.

## Production observability

Theo dõi upload count/bytes, success/failure/cancellation rate, p50/p95/p99 duration, active uploads, rejected-by-size/type, storage latency/throttling, DB failures, orphan cleanup count, malware-scan backlog, instance memory/temp-disk usage và download authorization failures. Correlate bằng document ID/request ID, không log raw file content.

## Trade-offs cần nêu

Backend proxy upload đơn giản về authorization/control nhưng tốn bandwidth và request capacity. Direct-to-object-storage giảm tải backend nhưng cần scoped credentials, finalize protocol và validation/scanning workflow. Synchronous scan đơn giản nhưng tăng latency; asynchronous quarantine tăng state complexity nhưng phù hợp file lớn/high throughput.

## Câu hỏi đào sâu

1. Nếu chuyển sang direct Blob upload bằng SAS, bạn ngăn user upload object ngoài prefix/quota của họ thế nào?
2. Nếu malware scanner unavailable trong 30 phút, bạn chọn fail-open hay fail-closed và dựa trên requirement nào?
3. Làm sao thiết kế cleanup để không xóa nhầm object hợp lệ khi DB/storage có eventual timing hoặc retry?

# Code Review Challenge 2 — Kubernetes rollout báo Ready quá sớm rồi tạo 5xx storm khi dependency chậm

**Chủ đề:** Kubernetes, ASP.NET Core deployment, readiness/liveness/startup probes, resource limits, graceful shutdown, secrets, rollout safety  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–45 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core API được deploy lên Kubernetes. Khi rollout vào giờ cao điểm, team thấy pods mới nhận traffic gần như ngay lập tức, một số trả 500/503 trong 20–40 giây đầu. Khi SQL hoặc Redis chậm vài giây, pods đôi lúc restart hàng loạt. Trong scale-down, một số in-flight requests bị cắt ngang.

Manifest mới:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-api
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: employee-api
  template:
    metadata:
      labels:
        app: employee-api
    spec:
      containers:
        - name: api
          image: registry.example/employee-api:2026.09.15
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Main
              value: "Server=prod-sql;Database=Employee;User Id=app;Password=SuperSecret123"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 0
            periodSeconds: 2
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
          resources:
            requests:
              cpu: "50m"
              memory: "64Mi"
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 1"]
```

`/health` hiện kiểm tra SQL và Redis bằng cách mở connection/ping. Endpoint trả non-2xx nếu một trong hai dependency không phản hồi trong 1 giây. App cần khoảng 15–25 giây để warm caches/JIT trước khi chịu tải tốt. Production metrics cho thấy mỗi pod thường dùng 250–400m CPU và 250–350 MiB memory dưới tải bình thường.

## Nhiệm vụ của ứng viên

Review manifest và health-check design. Xác định các vấn đề rollout, availability, probe semantics, resource management, secret handling và graceful termination. Giải thích failure cascade khi shared dependency chậm; đề xuất manifest/design sửa; nêu testing và telemetry production.

## Câu hỏi gợi mở

1. Liveness có nên fail chỉ vì SQL/Redis tạm chậm không?
2. Điều gì xảy ra nếu mọi pod cùng restart khi shared dependency degradation xảy ra?
3. Requests/limits hiện phản ánh workload thật không?
4. Secret có nên nằm trực tiếp trong Deployment manifest không?
5. `sleep 1` có đủ để endpoint removal và in-flight requests hoàn tất không?

## Gợi ý

### Gợi ý 1

Phân biệt ba câu hỏi: **process đã khởi động xong chưa**, **pod có nên nhận traffic không**, và **process có bị kẹt đến mức cần restart không**.

### Gợi ý 2

Một dependency outage không nên tự động biến thành self-inflicted restart storm nếu process vẫn khỏe và có thể phục hồi.

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc trực tiếp SQL/Redis tạo restart cascade

Nếu shared dependency chậm, `/health` fail trên tất cả pods; liveness có thể khiến kubelet restart các containers dù process không deadlocked. Restart đồng loạt làm mất warm state, tăng connection churn và tạo recovery storm đúng lúc dependency đang yếu. Liveness nên phản ánh process có khả năng tiếp tục hoạt động/phục hồi, không đơn giản là mọi dependency đều healthy.

### High — Readiness và liveness dùng cùng endpoint/semantics

Readiness trả lời “pod có nên nhận traffic?”. Liveness trả lời “container có cần restart?”. Hai quyết định có failure consequences khác nhau. Tách endpoints/checks và chọn dependency checks theo serving contract. Một critical dependency có thể ảnh hưởng readiness nhưng không nhất thiết liveness.

### High — Không có startup probe dù app warm-up 15–25 giây

Liveness bắt đầu sau 5 giây trong khi startup bình thường dài hơn. Startup probe có thể bảo vệ slow startup khỏi bị liveness giết sớm và cho phép readiness chỉ mở traffic khi app thực sự sẵn sàng.

### High — Resource requests thấp hơn nhiều so với observed steady-state

CPU request 50m và memory 64Mi thấp đáng kể so với workload quan sát 250–400m/250–350Mi. Scheduler có thể overcommit node dựa trên requests không thực tế, dẫn tới contention. Không có limits cũng cần được quyết định có chủ đích; memory limit quá thấp có thể OOMKill, CPU limit có thể throttling. Sizing phải dựa trên load measurements/SLO thay vì copy defaults.

### Critical — Secret hard-coded trong manifest

Database password nằm trong source/deployment artifact và có thể xuất hiện trong Git/history/tool logs. Dùng Kubernetes Secret hoặc tốt hơn external secret store/workload identity phù hợp platform; rotate credential đã lộ. Secret reference không tự giải quyết mọi security issue, nhưng loại plaintext khỏi manifest là baseline.

### High — Graceful termination không đủ

`sleep 1` không bảo đảm Service endpoints đã ngừng route traffic, load balancer propagation đã hoàn tất hoặc ASP.NET Core đã drain in-flight requests. Cần `terminationGracePeriodSeconds` phù hợp, application xử lý SIGTERM/graceful shutdown, readiness chuyển false khi draining và preStop chỉ dùng như một phần của strategy nếu platform cần propagation delay.

### Medium — Probe thresholds/timeouts quá aggressive và chưa được thiết kế từ SLO

Probe mỗi 2 giây/5 giây với dependency timeout 1 giây có thể biến transient latency thành pod churn hoặc endpoint flapping. Cần `timeoutSeconds`, `failureThreshold`, `successThreshold` và periods dựa trên measured behavior và desired detection/recovery time.

### Medium — RollingUpdate không có explicit surge/unavailable policy

Default behavior có thể không phù hợp capacity/SLO. Với traffic cao và warm-up lâu, nên đặt `maxUnavailable`/`maxSurge` có chủ đích, kết hợp readiness để rollout không giảm serving capacity quá mức.

### Medium — Không thể hiện disruption/capacity protection

Nếu node drain/maintenance hoặc rollout trùng autoscaling event, availability có thể giảm. Tùy requirement, cân nhắc PodDisruptionBudget, topology spreading/anti-affinity và HPA dựa trên meaningful metrics. Không thêm chúng máy móc; phải dựa trên cluster topology và SLO.

## Phiên bản sửa tham khảo

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: employee-api
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 2
  selector:
    matchLabels:
      app: employee-api
  template:
    metadata:
      labels:
        app: employee-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example/employee-api:2026.09.15
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Main
              valueFrom:
                secretKeyRef:
                  name: employee-api-db
                  key: main-connection-string
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 2
            failureThreshold: 20
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: "300m"
              memory: "384Mi"
            limits:
              memory: "768Mi"
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 5"]
```

Các con số trên là **scenario baseline**, không phải universal recommendation. Production phải tune bằng load test và telemetry. CPU limit cũng cần benchmark trước khi thêm vì throttling có thể làm tail latency xấu; memory limit phải có headroom dựa trên working set/GC behavior.

`/health/live` nên kiểm tra process/runtime state tối thiểu và không fail chỉ vì SQL/Redis transiently unavailable. `/health/ready` có thể kiểm tra dependencies thực sự bắt buộc để phục vụ request, nhưng cần tránh tạo probe load đáng kể. `/health/startup` phản ánh initialization/warm-up đã hoàn tất.

## Testing strategy

- Deployment test chứng minh pod không nhận traffic trước khi warm-up xong.
- Failure injection: SQL/Redis latency/outage và xác nhận liveness không gây restart storm.
- Load test trong rolling deployment, đo p95/p99/5xx khi old/new pods cùng tồn tại.
- Graceful-shutdown test với long-running requests khi pod nhận SIGTERM.
- Resource stress test để xác định requests/limits từ CPU, working set, GC và throttling/OOM behavior.
- Secret/config test bảo đảm manifest/repository/log không chứa plaintext credential.
- Rollback test với version N-1 và compatibility của config/database.

## Production observability

Theo dõi pod restart count/reason, readiness transitions, probe failures, rollout duration, unavailable replicas, 5xx, request p95/p99, in-flight requests khi termination, CPU throttling, memory working set/OOMKills, dependency latency/error rate, connection counts và node pressure. Correlate metrics theo deployment revision/pod để thấy regression chỉ xuất hiện ở version mới.

## Trade-offs cần nêu

Readiness phụ thuộc critical dependency có thể ngăn pod nhận traffic vô ích, nhưng nếu tất cả pods cùng become unready thì service mất endpoints hoàn toàn; đôi khi degraded response tốt hơn total outage. `maxUnavailable: 0` tăng safety nhưng rollout cần spare capacity. Larger resource requests cải thiện scheduling realism nhưng giảm packing density/cost efficiency. External secret manager/workload identity tăng security nhưng thêm platform integration complexity.

## Câu hỏi đào sâu

1. Nếu SQL outage làm mọi request nghiệp vụ đều không thể thành công, readiness nên fail trên toàn bộ pods hay giữ endpoints để trả controlled degradation? Bạn cần requirement nào để quyết định?
2. Vì sao tăng liveness `failureThreshold` rất lớn có thể giảm restart storm nhưng vẫn không sửa sai semantics của probe?
3. Nếu rollout với `maxUnavailable: 0` bị kẹt vì cluster không còn capacity cho surge pod, bạn sẽ thiết kế deployment/capacity strategy thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- File upload là một security/resource boundary: filename, extension, size và content đều là untrusted input.
- Multi-instance applications không nên giả định local disk là durable/shared storage.
- Khi SQL và object storage không cùng transaction, phải thiết kế partial failure, compensation và reconciliation.
- Kubernetes startup, readiness và liveness probes có semantics khác nhau; dùng chung một dependency-heavy health endpoint có thể tạo failure cascade.
- Resource requests phải phản ánh workload đo được; rollout safety phụ thuộc readiness, capacity và graceful shutdown chứ không chỉ `kubectl` báo successful.
- Secret không nên hard-code trong deployment manifest; credential đã lộ cần được rotate.

## Mẫu tư duy cần nhớ

1. **Treat external input as untrusted, including filenames and metadata.**
2. **Design the partial-failure window explicitly when two systems cannot share a transaction.**
3. **Separate “alive”, “ready” và “started” before configuring health probes.**
4. **Measure resource usage before sizing requests/limits.**
5. **Test deployment and shutdown under load, không chỉ test steady state.**
