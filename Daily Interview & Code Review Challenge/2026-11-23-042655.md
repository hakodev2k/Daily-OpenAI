# Code Review Challenge 1 — Đồng bộ Optimizely CMS sang Elasticsearch khi publish

**Chủ đề:** C#/.NET 8, Optimizely CMS, Elasticsearch, event processing, consistency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–11

## Bối cảnh

Một website marketing có Optimizely CMS làm nguồn dữ liệu nội dung và Elasticsearch phục vụ tìm kiếm. Khi biên tập viên publish, hệ thống cập nhật search document. Website chạy trên nhiều Azure App Service instances; có các thao tác publish/unpublish liên tiếp và một số nội dung giới hạn theo ngôn ngữ, quyền truy cập. Mục tiêu là kết quả tìm kiếm phản ánh nội dung đã publish, không lộ bản nháp hoặc nội dung bị hạn chế. Gần đây, một số trang đã unpublish vẫn xuất hiện trong kết quả; có lúc publish thành công nhưng search thiếu trang. Elasticsearch đôi khi trả lỗi 429. Chưa có bằng chứng xác định nguyên nhân.

Giả định `IContentEvents` và `IContentLoader` đã được đăng ký; `SearchClient` là adapter nội bộ có `IndexAsync` và `DeleteAsync`; `PageData` chứa thuộc tính `Title`, `MainBody`, `Language`, `IsPublic`. Đoạn code sau là simplified application integration, không phải tuyên bố về API cụ thể của mọi phiên bản Optimizely.

## Đoạn code cần review

```csharp
public sealed class CmsSearchSync : IHostedService
{
    private readonly IContentEvents _events;
    private readonly IContentLoader _loader;
    private readonly SearchClient _search;
    private readonly ILogger<CmsSearchSync> _log;

    public CmsSearchSync(IContentEvents events,
        IContentLoader loader, SearchClient search,
        ILogger<CmsSearchSync> log)
    {
        _events = events;
        _loader = loader;
        _search = search;
        _log = log;
    }

    public Task StartAsync(CancellationToken cancellationToken)
    {
        _events.PublishedContent += OnPublished;
        _events.UnPublishedContent += OnUnpublished;
        return Task.CompletedTask;
    }

    private async void OnPublished(object? sender, ContentEventArgs args)
    {
        var page = _loader.Get<PageData>(args.ContentLink);
        var doc = new SearchDocument
        {
            Id = args.ContentLink.ID.ToString(),
            Title = page.Title,
            Body = page.MainBody?.ToString() ?? "",
            Language = page.Language,
            Url = page.ContentLink.ToString()
        };

        await _search.IndexAsync(doc);
        _log.LogInformation("Indexed {ContentId}", doc.Id);
    }

    private async void OnUnpublished(object? sender, ContentEventArgs args)
    {
        await _search.DeleteAsync(args.ContentLink.ID.ToString());
    }

    public Task StopAsync(CancellationToken cancellationToken)
    {
        _events.PublishedContent -= OnPublished;
        _events.UnPublishedContent -= OnUnpublished;
        return Task.CompletedTask;
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Không áp dụng quy tắc public/authorization

**Vấn đề:** Mọi trang publish đều được index mà không kiểm tra quyền, trạng thái hiển thị hoặc thời hạn.

**Tại sao xảy ra:** Đoạn mapping không có eligibility policy; `IsPublic` không được xét.

**Ảnh hưởng production:** Search có thể trả title/snippet của nội dung bị hạn chế; chỉ ẩn ở UI không bảo vệ API search.

**Cách sửa:** Xác định chính sách index cho nội dung công khai, loại nội dung, publish state, expiration, language và quyền; lọc ở indexing và bảo vệ truy vấn theo security boundary. Rebuild index để xóa tài liệu đã lộ; đánh giá sự cố bảo mật.

### [High] — `async void` trong event handler

**Vấn đề:** Callback không trả `Task` cho publisher chờ hoặc xử lý exception.

**Tại sao xảy ra:** Event delegate kiểu `void` kết hợp `async void`; exception sau `await` không thể được caller `await` hay bắt như `Task` thông thường.

**Ảnh hưởng production:** Lỗi khó kiểm soát, có thể ảnh hưởng process và không có retry bền vững.

**Cách sửa:** Event handler chỉ enqueue công việc một cách có kiểm soát; nếu API sự kiện đồng bộ, không giả định có thể `await` trực tiếp. Sử dụng cơ chế durable event/outbox được hỗ trợ bởi CMS/integration hoặc change journal/reconciliation, rồi xử lý bằng worker `Task` với exception handling.

### [High] — Không có cơ chế retry bền vững

**Vấn đề:** Lỗi 429, timeout hoặc restart có thể làm mất cập nhật.

**Tại sao xảy ra:** Trực tiếp gọi Elasticsearch trong callback, không lưu trạng thái pending.

**Ảnh hưởng production:** Search lệch CMS lâu dài mà không có khả năng tự phục hồi.

**Cách sửa:** Durable queue/job store, exponential backoff với jitter, retry budget, DLQ và periodic reconciliation; tôn trọng `Retry-After` khi có.

### [High] — Race giữa publish và unpublish

**Vấn đề:** `IndexAsync` cũ có thể hoàn thành sau `DeleteAsync` mới.

**Tại sao xảy ra:** Các operation độc lập, không có ordering/version guard.

**Ảnh hưởng production:** Trang unpublish tái xuất hiện trong index.

**Cách sửa:** Lưu monotonically increasing content revision hoặc change sequence từ nguồn có thẩm quyền; worker đọc trạng thái CMS mới nhất trước khi upsert/delete; dùng per-key ordering và/hoặc external versioning nếu adapter hỗ trợ, kết hợp reconciliation. Không dùng wall-clock timestamp thiếu kiểm chứng làm sequence.

### [High] — Khóa document thiếu language/variant

**Vấn đề:** `ContentLink.ID` đơn lẻ có thể gom nhiều language variants vào cùng một document.

**Tại sao xảy ra:** Search key bỏ qua language và các chiều định danh cần thiết.

**Ảnh hưởng production:** Bản dịch ghi đè lẫn nhau; unpublish một variant có thể xóa variant khác.

**Cách sửa:** Định nghĩa stable key theo content identity + language (và site/tenant nếu phù hợp); quy định delete theo variant.

### [Medium] — Đọc content chưa bảo đảm phiên bản published phù hợp

**Vấn đề:** `Get<PageData>` từ một reference chưa được kiểm chứng về version/language và không xác nhận trạng thái publish.

**Tại sao xảy ra:** Mapping sử dụng dữ liệu tải tại thời điểm callback mà không xác minh trạng thái cuối cùng.

**Ảnh hưởng production:** Index sai language, version hoặc metadata.

**Cách sửa:** Sử dụng API/version selector phù hợp phiên bản CMS thực tế; xác minh trạng thái được phép xuất bản và xử lý unpublish/expiry.

### [Medium] — URL và body chưa được chuẩn hóa

**Vấn đề:** `ContentLink.ToString()` không mặc nhiên là public canonical URL; `MainBody.ToString()` có thể chứa markup.

**Tại sao xảy ra:** Trộn CMS internal reference với public URL; chưa chuyển rich text thành search-safe plain text.

**Ảnh hưởng production:** Link sai, SEO kém, snippet lộ markup hoặc dữ liệu không phù hợp.

**Cách sửa:** Dùng URL resolver phù hợp site/language và canonical policy; sanitization/text extraction trước khi index.

### [Medium] — Thiếu cancellation, bounded concurrency và lifecycle

**Vấn đề:** Call search không có cancellation, backpressure hoặc giới hạn số tác vụ đang chạy.

**Tại sao xảy ra:** Fire-and-forget theo số lượng event.

**Ảnh hưởng production:** Shutdown mất công việc; burst publish làm tăng memory, request 429 và thời gian phục hồi.

**Cách sửa:** Worker với `CancellationToken`, concurrency limit và queue depth limit; chỉ ack công việc sau khi hoàn tất.

### [Medium] — Telemetry không đủ cho điều tra

**Vấn đề:** Chỉ log thành công theo content ID.

**Tại sao xảy ra:** Thiếu revision, language, operation, attempt, latency và correlation.

**Ảnh hưởng production:** Không xác định được tài liệu nào bị lệch, lỗi có retry hay không.

**Cách sửa:** Structured logging không chứa nội dung nhạy cảm, metrics backlog/lag/error và distributed traces.

## Phiên bản đề xuất

Giải pháp dưới đây minh họa **worker xử lý durable change journal**. Phần ghi journal phải được tích hợp tại một điểm đảm bảo tính bền vững với thay đổi CMS, hoặc bù bằng periodic reconciliation; không giả định event callback và CMS DB có chung transaction. `ICmsSnapshotReader` trả về snapshot đã được xác minh là public và current, hoặc `null` nếu cần xóa. `IChangeStore` có claim/lease và compare-and-set trên revision; `ISearchIndex` hỗ trợ conditional write theo revision hoặc serialized per-key processing.

```csharp
public sealed record ContentChange(
    string Key, long Revision, string CorrelationId);

public sealed record PublicSearchSnapshot(
    string Key, long Revision, string Title,
    string PlainText, string CanonicalUrl, string Language);

public sealed class SearchSyncWorker(
    IChangeStore changes,
    ICmsSnapshotReader cms,
    ISearchIndex index,
    ILogger<SearchSyncWorker> logger)
{
    public async Task ProcessAsync(
        ContentChange change, CancellationToken ct)
    {
        var lease = await changes.TryClaimAsync(change, ct);
        if (lease is null) return;

        try
        {
            var current = await cms.ReadPublicSnapshotAsync(
                change.Key, ct);

            if (current is null)
                await index.DeleteIfNotNewerAsync(
                    change.Key, change.Revision, ct);
            else
                await index.UpsertIfNotNewerAsync(current, ct);

            await changes.MarkCompletedAsync(lease, ct);
        }
        catch (Exception ex) when (!ct.IsCancellationRequested)
        {
            logger.LogError(ex,
                "Search sync failed: {Key} {Revision} {CorrelationId}",
                change.Key, change.Revision, change.CorrelationId);
            await changes.ScheduleRetryAsync(lease, ct);
        }
    }
}
```

**Điều kiện thiết kế:** Revision phải phản ánh thứ tự thay đổi đáng tin cậy cho cùng một key. Khi snapshot hiện tại đã tiến xa hơn event, delete phải sử dụng revision tương ứng với trạng thái hiện tại hoặc được xử lý bằng cơ chế version gate để không xóa dữ liệu mới. `DeleteIfNotNewerAsync` cần lưu tombstone/version nếu search engine không giữ version sau delete. Retry scheduling phải xử lý giới hạn số lần và DLQ. Các interface ở trên là abstraction đề xuất, không phải built-in APIs của Optimizely hay Elasticsearch.

## Giải thích thiết kế sau khi sửa

CMS là source of truth; search index là read model eventually consistent. Một operation không được coi là đồng bộ thành công chỉ vì callback đã bắt đầu. Worker tái đọc snapshot hợp lệ, áp dụng upsert/delete có kiểm soát phiên bản, sau đó ack. Reconciliation định kỳ đối chiếu CMS với search để xử lý event bị mất và thay đổi policy. Nếu hệ thống yêu cầu search nhất quán tức thời, cần đánh giá lại SLA và UX; durable async indexing không cung cấp strong consistency.

## Trade-offs

Durable journal, worker và version gate tăng độ phức tạp vận hành, storage và độ trễ search. Với website nhỏ, có thể dùng scheduled batch reindex kết hợp synchronous best-effort update, nhưng phải chấp nhận staleness và có monitoring. Không mặc định cần Microservices hoặc Azure Service Bus; job table trong cùng hệ thống có thể đủ. Search authorization phức tạp có thể khiến việc index dữ liệu private không phù hợp, nên cân nhắc không index.

## Cách kiểm thử

1. **Integration/security:** Publish nội dung private, draft, expired và nhiều languages; xác minh search API không trả dữ liệu bị hạn chế.
2. **Concurrency:** Publish revision 11, unpublish 12, rồi hoàn tất request index 11 trễ; kết quả cuối cùng không được resurrect.
3. **Failure-path:** Elasticsearch trả 429/timeout, worker restart giữa xử lý; công việc được retry mà không mất, không áp dụng revision cũ.
4. **Reconciliation:** Cố ý bỏ một event và xác nhận job đối chiếu phát hiện, sửa lệch.
5. **Load:** Burst hàng nghìn publish, đo queue depth, indexing lag, error rate và memory.

## Quan sát trong production

Theo dõi `search_sync_pending`, oldest pending age, p95 indexing lag, retry count, DLQ size, Elasticsearch 429/5xx, per-language document count, mismatch sampling và tỷ lệ kết quả search bị 404. Structured logs gắn `content_key`, `revision`, `operation`, `attempt`, `correlation_id`; Application Insights dependency traces và Kibana hỗ trợ điều tra. Alert theo lag vượt SLO và DLQ tăng, không chỉ theo exception count.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue'

type Product = { id: string; name: string; price: number }
type SearchResult = { items: Product[]; total: number }

const props = defineProps<{ tenantId: string }>()
const keyword = ref('')
const page = ref(1)
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')

async function loadProducts() {
  loading.value = true
  error.value = ''
  const url = '/api/products?tenant=' + props.tenantId
    + '&q=' + keyword.value + '&page=' + page.value

  try {
    const response = await fetch(url, { credentials: 'include' })
    const data = await response.json() as SearchResult
    products.value = data.items
    total.value = data.total
  } catch (e) {
    products.value = []
    total.value = 0
    error.value = 'Không có sản phẩm'
  } finally {
    loading.value = false
  }
}

watch(keyword, () => {
  page.value = 1
  loadProducts()
})
watch(page, loadProducts)
watch(() => props.tenantId, loadProducts)
onMounted(loadProducts)
</script>

<template>
  <input v-model="keyword" placeholder="Tìm sản phẩm" />
  <div v-if="loading">Đang tải...</div>
  <div v-if="error">{{ error }}</div>
  <ul>
    <li v-for="item in products" :key="item.id">
      {{ item.name }} — {{ item.price }}
    </li>
  </ul>
  <button @click="page--" :disabled="page <= 1">Trước</button>
  <button @click="page++">Sau</button>
  <span>{{ total }} sản phẩm</span>
</template>
```

## Kết quả code review tham khảo

### [High] — Response cũ ghi đè response mới

**Vấn đề:** Không ràng buộc response với query/tenant hiện tại.

**Tại sao xảy ra:** Các `fetch` chạy đồng thời; response về cuối cùng thắng bất kể request nào mới hơn.

**Ảnh hưởng production:** UI hiển thị kết quả không thuộc bộ lọc hiện tại, đặc biệt nguy hiểm khi chuyển tenant trên máy dùng chung. Server authorization vẫn là ranh giới bắt buộc.

**Cách sửa:** Hủy request trước và dùng generation token kiểm tra trước khi commit state; clear dữ liệu khi tenant thay đổi nếu policy không cho hiển thị stale results.

### [High] — Không kiểm tra HTTP status

**Vấn đề:** `response.json()` được xử lý như thành công kể cả HTTP 401/403/500.

**Tại sao xảy ra:** `fetch` không tự reject chỉ vì HTTP error status.

**Ảnh hưởng production:** Lỗi auth/server biến thành dữ liệu rỗng hoặc cấu trúc sai, che giấu incident.

**Cách sửa:** Kiểm tra `response.ok`; phân biệt 401 (session), 403 (forbidden), 429 (rate limit), 5xx (server error). Không tự retry mọi POST/GET vô hạn.

### [High] — Tenant truyền từ client có thể bị tin nhầm

**Vấn đề:** Nếu backend dựa vào query `tenant` để cho phép truy cập, đây là IDOR/broken authorization.

**Tại sao xảy ra:** UI-controlled tenant ID không chứng minh quyền truy cập.

**Ảnh hưởng production:** Cross-tenant data exposure nếu server thiếu authorization.

**Cách sửa:** Backend kiểm tra principal và quyền tenant cho mọi request; frontend guard chỉ hỗ trợ UX, không thay thế security.

### [Medium] — Query string không encode

**Vấn đề:** Keyword chứa `&`, `#`, `?` hoặc Unicode có thể tạo query sai.

**Tại sao xảy ra:** Nối chuỗi URL trực tiếp.

**Ảnh hưởng production:** Search sai, tham số bị thay đổi, log/diagnostic khó hiểu.

**Cách sửa:** `URLSearchParams` với encode chuẩn.

### [Medium] — Watchers gây request dư thừa

**Vấn đề:** Keyword thay đổi kích hoạt `loadProducts`, đồng thời reset `page` có thể kích hoạt watcher khác.

**Tại sao xảy ra:** Nhiều watcher điều phối cùng một effect; không debounce.

**Ảnh hưởng production:** QPS tăng theo số ký tự và gây thêm race.

**Cách sửa:** Một watcher trên composite query state; debounce keyword ở input hoặc trong pipeline, không debounce tenant change nếu cần xóa dữ liệu ngay.

### [Medium] — Loading flag sai khi nhiều request cùng tồn tại

**Vấn đề:** Request cũ hoàn tất có thể đặt `loading=false` trong khi request mới còn chạy.

**Tại sao xảy ra:** Một boolean được ghi từ nhiều asynchronous operations.

**Ảnh hưởng production:** Spinner biến mất sớm, user thao tác trên dữ liệu cũ.

**Cách sửa:** Chỉ request hiện hành được thay đổi state, hoặc dùng request counter nếu hỗ trợ concurrent loads có chủ đích.

### [Medium] — Error handling đánh đồng lỗi với empty result

**Vấn đề:** Catch xóa danh sách và hiển thị “Không có sản phẩm”.

**Tại sao xảy ra:** Không phân biệt network failure, abort, 401/403, validation và empty search.

**Ảnh hưởng production:** User hiểu sai tình trạng hệ thống; incident bị che.

**Cách sửa:** Typed error state, thông báo riêng, retry button có kiểm soát và empty state chỉ cho response thành công rỗng.

### [Medium] — Pagination thiếu upper bound và reset đúng lúc

**Vấn đề:** Nút “Sau” không bị vô hiệu hóa ở trang cuối; tenant change không reset page.

**Tại sao xảy ra:** Không tính `Math.ceil(total / pageSize)` và không điều phối state.

**Ảnh hưởng production:** Truy vấn trang không tồn tại, hiển thị rỗng sai.

**Cách sửa:** Reset page khi tenant/keyword thay đổi; disable next khi không còn trang; server validate page và page size.

### [Low] — Không có cleanup khi unmount

**Vấn đề:** Request tiếp tục sau khi component không còn hiển thị.

**Tại sao xảy ra:** Không abort trên watcher invalidation/unmount.

**Ảnh hưởng production:** Lãng phí network và có thể giữ state không cần thiết.

**Cách sửa:** Dùng `onCleanup` của watcher hoặc `onWatcherCleanup` phù hợp phiên bản Vue; abort request.

## Phiên bản đề xuất

Ví dụ dùng một watcher theo các dependency và một `AbortController` cho mỗi lần chạy. `searchText` là giá trị đã debounce; `keyword` và tenant được theo dõi để reset page ngay. Trong ứng dụng thực tế, nên tách fetch logic thành composable và thống nhất error contract với backend.

```vue
<script setup lang="ts">
import { ref, watch, onUnmounted } from 'vue'

type Product = { id: string; name: string; price: number }
type SearchResult = { items: Product[]; total: number }
const props = defineProps<{ tenantId: string }>()
const keyword = ref('')
const searchText = ref('')
const page = ref(1)
const products = ref<Product[]>([])
const total = ref(0)
const loading = ref(false)
const error = ref('')
const pageSize = 20
let debounceTimer: ReturnType<typeof setTimeout> | undefined
let generation = 0

watch(keyword, value => {
  page.value = 1
  clearTimeout(debounceTimer)
  debounceTimer = setTimeout(() => { searchText.value = value }, 250)
})
watch(() => props.tenantId, () => {
  page.value = 1
  products.value = []
  total.value = 0
}, { flush: 'sync' })

watch(
  [() => props.tenantId, searchText, page],
  async ([tenantId, q, currentPage], _old, onCleanup) => {
    const id = ++generation
    const controller = new AbortController()
    onCleanup(() => controller.abort())
    loading.value = true
    error.value = ''
    const params = new URLSearchParams({
      tenant: tenantId, q, page: String(currentPage)
    })
    try {
      const response = await fetch('/api/products?' + params, {
        credentials: 'include',
        signal: controller.signal
      })
      if (!response.ok) {
        throw new Error(
          response.status === 401 ? 'Phiên đăng nhập hết hạn'
          : response.status === 403 ? 'Không có quyền truy cập'
          : 'Không thể tải sản phẩm (' + response.status + ')'
        )
      }
      const data = await response.json() as SearchResult
      if (id !== generation || controller.signal.aborted) return
      products.value = data.items
      total.value = data.total
    } catch (e) {
      if (id !== generation || controller.signal.aborted) return
      error.value = e instanceof Error ? e.message : 'Lỗi kết nối'
      products.value = []
      total.value = 0
    } finally {
      if (id === generation) loading.value = false
    }
  },
  { immediate: true }
)
onUnmounted(() => clearTimeout(debounceTimer))
</script>

<template>
  <input v-model="keyword" placeholder="Tìm sản phẩm" />
  <p v-if="loading">Đang tải...</p>
  <p v-if="error" role="alert">{{ error }}</p>
  <p v-if="!loading && !error && total === 0">Không có sản phẩm</p>
  <ul>
    <li v-for="item in products" :key="item.id">
      {{ item.name }} — {{ item.price }}
    </li>
  </ul>
  <button @click="page--" :disabled="page <= 1 || loading">Trước</button>
  <button @click="page++"
    :disabled="loading || page * pageSize >= total">Sau</button>
  <span>{{ total }} sản phẩm</span>
</template>
```

**Giới hạn của bản minh họa:** Nếu user đổi tenant trong khi keyword đang debounce, watcher tenant vẫn fetch với `searchText` cũ trong khoảng ngắn; điều này không gây cross-tenant leak nếu backend authorize đúng, nhưng có thể tạo request dư. Để tránh, đồng bộ searchText khi tenant đổi hoặc thiết kế một query state reducer/composable duy nhất. Khi keyword đang gõ, kết quả cũ vẫn có thể hiện trong 250 ms; có thể clear ngay theo UX policy. `onCleanup` được đăng ký đồng bộ trước `await`. Response JSON vẫn cần runtime validation nếu API contract không đáng tin.

## Giải thích thiết kế sau khi sửa

Generation token bảo đảm chỉ request mới nhất commit state. Abort giảm lãng phí nhưng không thay thế generation check vì server có thể đã xử lý request trước khi nhận cancellation. URLSearchParams giữ query đúng cú pháp. HTTP status được diễn giải thành trạng thái lỗi rõ ràng; empty result chỉ xuất hiện sau response thành công. Server phải enforce tenant authorization dựa trên authenticated principal, không dựa vào UI selection.

## Trade-offs

Debounce giảm request nhưng tăng latency khi gõ; chọn 250 ms chỉ là giả định cần đo. Hủy request giúp tiết kiệm tài nguyên browser nhưng không bảo đảm backend dừng xử lý. Cache kết quả theo `tenantId + keyword + page + auth context` có thể cải thiện UX, nhưng phải invalidation khi quyền/tenant đổi và tránh lưu dữ liệu nhạy cảm ở shared cache. Nếu ứng dụng lớn, thư viện query management có thể giúp nhưng không thay thế server authorization.

## Cách kiểm thử

1. **Component concurrency:** Mock request A chậm hơn B; xác minh chỉ kết quả B được hiển thị.
2. **Security/API integration:** User tenant A sửa query thành tenant B; backend trả 403, không trả data.
3. **Error-path:** HTTP 401, 403, 429, 500, network offline và abort; mỗi trạng thái hiển thị đúng, không bị hiểu là empty result.
4. **Playwright E2E:** Gõ nhanh, chuyển tenant, đổi trang; xác minh danh sách/URL tương ứng và không có kết quả tenant cũ.
5. **Load/network:** Đo request per keystroke, canceled requests, p95 latency và backend QPS trước/sau debounce.

## Quan sát trong production

Browser RUM đo search request count, p95 latency, cancellation ratio, HTTP error rates, tenant-switch latency và empty-result rate. ASP.NET Core/Application Insights ghi request duration, status, tenant scope dạng identifier không nhạy cảm, correlation ID và authorization failures. Không log keyword nếu có thể chứa dữ liệu cá nhân. Alert khi 401/403/5xx tăng bất thường; dùng Network panel và distributed traces để phân biệt frontend race với backend lỗi.

## Câu hỏi phỏng vấn mở rộng

1. Nếu muốn giữ cache kết quả cho mỗi tenant, bạn thiết kế cache key và invalidation thế nào khi user mất quyền?
2. Nếu cancellation không ngăn được truy vấn SQL đang chạy, bạn giới hạn tải server bằng cách nào?
3. Bạn sẽ dùng Vue composable tự viết hay query library, và tiêu chí quyết định là gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai ranh giới cần bảo vệ là **CMS → search index** và **browser state → backend API**. Trong cả hai, thứ tự hoàn thành bất đồng bộ không đồng nghĩa thứ tự nghiệp vụ; phải xác định source of truth, quyền truy cập, version và failure recovery. Durable retry cần đi cùng idempotency/version control; cancellation phía browser không thay thế authorization phía server. Observability phải chứng minh consistency và correctness, không chỉ đếm request thành công.

## Mẫu tư duy cần nhớ

1. Xác định source of truth và trust boundary trước khi thiết kế đồng bộ.
2. Kiểm tra kết quả bất đồng bộ còn thuộc phiên bản state hiện tại không.
3. Thiết kế retry, idempotency, ordering và reconciliation cùng nhau.
4. Phân biệt lỗi hệ thống với kết quả nghiệp vụ hợp lệ.
5. Dùng failure injection và telemetry để kiểm chứng fix dưới tải thực tế.
