# Code Review Challenge 1 — Service Bus retry làm approval được xử lý hai lần

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, idempotency, retry, message settlement, distributed systems  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một employee platform phát message khi một approval được duyệt. Consumer chạy trên nhiều instances và cập nhật SQL Server, gọi một payroll API rồi gửi email. Azure Service Bus có thể redeliver message khi processing vượt quá lock hoặc process chết trước settlement.

Production thỉnh thoảng ghi nhận payroll operation bị gọi hai lần và email được gửi lặp. Logs lại cho thấy cùng `ApprovalId` được xử lý bởi hai instances cách nhau vài giây. Team hiện giả định rằng “message đã vào queue thì mỗi message chỉ được xử lý một lần”.

## Đoạn code cần review

```csharp
public sealed class ApprovalApprovedConsumer
{
    private readonly AppDbContext _db;
    private readonly PayrollClient _payroll;
    private readonly EmailClient _email;
    private readonly ILogger<ApprovalApprovedConsumer> _logger;

    public ApprovalApprovedConsumer(
        AppDbContext db,
        PayrollClient payroll,
        EmailClient email,
        ILogger<ApprovalApprovedConsumer> logger)
    {
        _db = db;
        _payroll = payroll;
        _email = email;
        _logger = logger;
    }

    public async Task HandleAsync(
        ServiceBusReceivedMessage message,
        ServiceBusMessageActions actions,
        CancellationToken cancellationToken)
    {
        var evt = JsonSerializer.Deserialize<ApprovalApproved>(message.Body)!;

        var approval = await _db.Approvals
            .SingleAsync(x => x.Id == evt.ApprovalId, cancellationToken);

        if (approval.Status == "Processed")
        {
            await actions.CompleteMessageAsync(message, cancellationToken);
            return;
        }

        approval.Status = "Processing";
        await _db.SaveChangesAsync(cancellationToken);

        await _payroll.ApplyApprovalAsync(
            evt.EmployeeId,
            evt.ApprovalId,
            cancellationToken);

        await _email.SendApprovalEmailAsync(
            evt.EmployeeId,
            cancellationToken);

        approval.Status = "Processed";
        approval.ProcessedAt = DateTimeOffset.UtcNow;
        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Processed approval {ApprovalId} from message {MessageId}",
            evt.ApprovalId,
            message.MessageId);

        await actions.CompleteMessageAsync(message, cancellationToken);
    }
}
```

2. Xác định reliability/concurrency/data-consistency concerns.
3. Giải thích production impact.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected implementation/design.
6. Giải thích testing strategy.
7. Nêu telemetry cần có trong production.

## Câu hỏi gợi mở

1. Điều gì xảy ra nếu process chết sau payroll call nhưng trước `CompleteMessageAsync`?
2. Hai consumers có thể cùng đọc `Status != "Processed"` không?
3. SQL transaction có thể rollback side effect ở payroll API hay email provider không?
4. Message lock expiry hoặc transient failure ảnh hưởng flow thế nào?
5. `MessageId` và business key nên được dùng ra sao để hỗ trợ deduplication?

## Gợi ý

### Gợi ý 1

Rủi ro chính là **at-least-once delivery + non-atomic external side effects + concurrency**.

### Gợi ý 2

Hãy tách “đã nhận message”, “đã commit business state” và “đã thực hiện external side effect”; retry phải được thiết kế cùng idempotency.

## Kết quả code review tham khảo

### Critical — External payroll side effect không idempotent theo business operation

**Vấn đề:** Consumer gọi payroll trước khi message được settle và không truyền idempotency key được đảm bảo ở downstream.  
**Tại sao xảy ra:** Service Bus delivery và HTTP side effect không nằm trong một atomic transaction; process có thể chết sau HTTP success nhưng trước DB update/settlement.  
**Ảnh hưởng production:** Redelivery có thể thực hiện payroll operation lần hai.  
**Cách sửa:** Thiết kế payroll operation idempotent theo stable business key như `ApprovalId`/operation id; downstream lưu hoặc enforce uniqueness. Nếu downstream không hỗ trợ, cần adapter/store kiểm soát trạng thái và reconciliation, nhưng không được giả định local transaction tạo exactly-once.

### High — Check-then-act trên `approval.Status` có race condition

**Vấn đề:** Hai consumers có thể cùng đọc trạng thái chưa processed rồi cùng tiếp tục.  
**Tại sao xảy ra:** Read và state transition không có concurrency control đủ mạnh.  
**Ảnh hưởng production:** Duplicate side effects và state transitions cạnh tranh.  
**Cách sửa:** Dùng optimistic concurrency/version hoặc atomic conditional update để chỉ một worker claim business operation; xử lý conflict như duplicate/in-flight thay vì tiếp tục.

### High — Email side effect cũng có duplicate window

**Vấn đề:** Crash sau email success nhưng trước final DB commit/settlement làm email được gửi lại.  
**Tại sao xảy ra:** External side effect không atomic với SQL/Service Bus.  
**Ảnh hưởng production:** User nhận notification lặp.  
**Cách sửa:** Dùng durable notification intent/Outbox và consumer idempotent ở notification boundary; deduplicate theo event/business key.

### High — Trạng thái `Processing` có thể bị kẹt

**Vấn đề:** Nếu payroll/email throw sau khi DB lưu `Processing`, retry không có explicit policy cho trạng thái này.  
**Tại sao xảy ra:** State machine không định nghĩa ownership, timeout, retry và recovery.  
**Ảnh hưởng production:** Record có thể tồn tại mãi ở trạng thái trung gian hoặc nhiều worker vẫn chạy.  
**Cách sửa:** Thiết kế state transition với attempt/lease/version và reconciliation cho operation quá hạn.

### High — Không phân loại lỗi retryable và non-retryable

**Vấn đề:** Deserialization, missing approval, validation, payroll 4xx và transient 5xx đều đi qua cùng failure behavior.  
**Tại sao xảy ra:** Consumer không có failure taxonomy.  
**Ảnh hưởng production:** Poison message có thể retry vô ích; transient error có thể bị xử lý thiếu kiểm soát.  
**Cách sửa:** Validate schema; phân loại lỗi; retry/backoff cho transient; dead-letter non-retryable với reason an toàn; alert DLQ.

### Medium — Không có explicit duplicate-processing record

**Vấn đề:** Chỉ dựa vào aggregate status, không lưu processed message/business operation identity.  
**Tại sao xảy ra:** Message delivery identity và business idempotency bị trộn.  
**Ảnh hưởng production:** Khó audit/replay và phân biệt duplicate với legitimate later event.  
**Cách sửa:** Lưu Inbox/processed operation record với unique constraint khi phù hợp. Business idempotency vẫn phải dựa trên semantics, không chỉ random message id.

### Medium — Long external calls có thể tương tác xấu với message lock

**Vấn đề:** Handler thực hiện nhiều remote operations trước settlement.  
**Tại sao xảy ra:** Processing duration có thể vượt lock/renewal budget tùy host configuration và dependency latency.  
**Ảnh hưởng production:** Message có thể được redeliver trong lúc instance cũ còn xử lý.  
**Cách sửa:** Đo processing duration/lock-lost events; cấu hình lock renewal phù hợp nếu framework hỗ trợ, nhưng vẫn phải idempotent vì renewal không loại bỏ redelivery.

### Medium — Cancellation có thể tạo trạng thái partial

**Vấn đề:** Cancellation được propagate nhưng side effect đã thành công không rollback.  
**Tại sao xảy ra:** Cancellation là cooperative cancellation, không phải distributed transaction.  
**Ảnh hưởng production:** Client/host shutdown đúng lúc tạo partial workflow.  
**Cách sửa:** Durable state + idempotent resume/reconciliation; graceful shutdown và telemetry cho incomplete operations.

### Low — Logging chưa đủ để điều tra attempt lifecycle

**Vấn đề:** Chỉ log success cuối flow.  
**Tại sao xảy ra:** Không có structured event cho receive/claim/downstream attempt/retry/settlement.  
**Ảnh hưởng production:** Khó chứng minh duplicate xuất hiện ở delivery hay business layer.  
**Cách sửa:** Log/trace `MessageId`, `ApprovalId`, delivery count, attempt, correlation/trace id và downstream idempotency key; không log sensitive payload.

## Phiên bản đề xuất

```csharp
public async Task HandleAsync(
    ServiceBusReceivedMessage message,
    ServiceBusMessageActions actions,
    CancellationToken ct)
{
    ApprovalApproved evt;
    try
    {
        evt = JsonSerializer.Deserialize<ApprovalApproved>(message.Body)
            ?? throw new InvalidDataException("Empty event.");
    }
    catch (Exception ex) when (ex is JsonException or InvalidDataException)
    {
        await actions.DeadLetterMessageAsync(
            message,
            "InvalidPayload",
            ex.Message,
            ct);
        return;
    }

    var claimed = await _db.Approvals
        .Where(x => x.Id == evt.ApprovalId && x.Status == "Approved")
        .ExecuteUpdateAsync(
            s => s
                .SetProperty(x => x.Status, "Processing")
                .SetProperty(x => x.ProcessingStartedAt, DateTimeOffset.UtcNow),
            ct);

    if (claimed == 0)
    {
        var current = await _db.Approvals
            .AsNoTracking()
            .SingleOrDefaultAsync(x => x.Id == evt.ApprovalId, ct);

        if (current?.Status == "Processed")
            await actions.CompleteMessageAsync(message, ct);

        return;
    }

    // Contract requirement: downstream must treat this key idempotently.
    var operationKey = $"approval:{evt.ApprovalId}:payroll";

    await _payroll.ApplyApprovalAsync(
        evt.EmployeeId,
        evt.ApprovalId,
        operationKey,
        ct);

    // Prefer a durable notification intent / Outbox rather than sending
    // the email as an untracked side effect here.
    _db.NotificationOutbox.Add(new NotificationOutbox
    {
        Id = Guid.NewGuid(),
        BusinessKey = $"approval:{evt.ApprovalId}:email",
        EmployeeId = evt.EmployeeId,
        Type = "ApprovalProcessed"
    });

    var approval = await _db.Approvals
        .SingleAsync(x => x.Id == evt.ApprovalId, ct);

    approval.Status = "Processed";
    approval.ProcessedAt = DateTimeOffset.UtcNow;

    await _db.SaveChangesAsync(ct);
    await actions.CompleteMessageAsync(message, ct);
}
```

Đoạn trên minh họa hướng thiết kế chứ không tạo exactly-once end-to-end. Atomic claim chỉ ngăn hai workers cùng claim trong một trạng thái cụ thể. Nếu process chết sau payroll success nhưng trước final SQL commit, retry vẫn phải dựa vào idempotency key/reconciliation để xác định side effect đã xảy ra.

## Giải thích thiết kế sau khi sửa

At-least-once delivery được coi là normal behavior. Business operation có stable identity và downstream side effect quan trọng phải idempotent. Atomic conditional update giảm race ở local state; Outbox biến notification thành durable intent có thể retry độc lập. Reconciliation xử lý trạng thái `Processing` quá hạn và các trường hợp không thể xác định chỉ bằng local DB.

## Trade-offs

Idempotency store/unique constraints tăng schema và operational complexity. Outbox thêm worker và eventual delivery. Atomic claim có thể cần lease/version nếu processing lâu. Nếu payroll provider không hỗ trợ idempotency, adapter/reconciliation phức tạp hơn và có thể cần manual resolution cho ambiguous outcome. Đổi lại, đây là complexity trực tiếp giải quyết failure model thật thay vì kỳ vọng queue delivery đúng một lần.

## Cách kiểm thử

1. **Concurrency test:** deliver cùng business event cho hai handlers đồng thời; chỉ một operation được claim.
2. **Failure-path test:** crash sau payroll success nhưng trước DB commit; redelivery không được tạo payroll effect thứ hai.
3. **Integration test:** transient payroll timeout/5xx, retry và eventual success; kiểm tra idempotency key giữ nguyên.
4. **Poison-message test:** invalid payload/non-retryable event đi DLQ với reason phù hợp.
5. **Shutdown test:** cancellation giữa các bước; reconciliation đưa workflow về trạng thái có thể xử lý tiếp.

## Quan sát trong production

Theo dõi Service Bus active message count, oldest age, delivery count, DLQ, lock-lost/settlement errors, processing duration và retry rate. Trace phải nối `MessageId` → `ApprovalId` → operation key → payroll dependency → Outbox notification. Dashboard cần số operation stuck ở `Processing`, duplicate claim attempts, idempotency hits và ambiguous downstream outcomes.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao Outbox không tạo exactly-once end-to-end?
2. Nếu payroll API timeout nhưng thực tế đã commit operation, consumer nên xử lý “unknown outcome” thế nào?
3. Khi nào Service Bus Sessions hữu ích, và vì sao ordering vẫn không thay thế idempotency?

# Code Review Challenge 2 — Cosmos DB query chạy tốt ở test nhưng RU và latency tăng mạnh khi catalog lớn

**Chủ đề:** Azure Cosmos DB, partition key, query pattern, concurrency, optimistic concurrency, RU, data modeling  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một product-catalog service dùng Azure Cosmos DB. Container `products` lưu product của nhiều tenant. Partition key hiện là `/tenantId`. Admin API hỗ trợ tìm product theo SKU rồi cập nhật stock.

Trong test chỉ có vài nghìn documents nên mọi thứ nhanh. Production có hàng triệu documents và hàng trăm tenants. Team thấy RU consumption tăng mạnh khi bulk import chạy song song với admin updates; một số stock update bị ghi đè. Chưa có evidence rằng SKU unique toàn hệ thống; requirement hiện chỉ nói SKU unique trong một tenant.

## Đoạn code cần review

```csharp
public sealed class ProductRepository
{
    private readonly Container _container;

    public ProductRepository(CosmosClient client)
    {
        _container = client.GetContainer("catalog", "products");
    }

    public async Task<Product?> FindBySkuAsync(
        string sku,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE c.sku = @sku")
            .WithParameter("@sku", sku);

        using var iterator = _container.GetItemQueryIterator<Product>(query);

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            var product = page.FirstOrDefault();
            if (product is not null)
                return product;
        }

        return null;
    }

    public async Task UpdateStockAsync(
        string sku,
        int newStock,
        CancellationToken cancellationToken)
    {
        var product = await FindBySkuAsync(sku, cancellationToken);

        if (product is null)
            throw new InvalidOperationException("Product not found.");

        product.Stock = newStock;
        product.UpdatedAt = DateTimeOffset.UtcNow;

        await _container.ReplaceItemAsync(
            product,
            product.Id,
            new PartitionKey(product.TenantId),
            cancellationToken: cancellationToken);
    }

    public async Task<List<Product>> SearchAsync(
        string text,
        CancellationToken cancellationToken)
    {
        var query = new QueryDefinition(
            "SELECT * FROM c WHERE CONTAINS(LOWER(c.name), LOWER(@text))")
            .WithParameter("@text", text);

        using var iterator = _container.GetItemQueryIterator<Product>(query);

        var result = new List<Product>();

        while (iterator.HasMoreResults)
        {
            var page = await iterator.ReadNextAsync(cancellationToken);
            result.AddRange(page);
        }

        return result;
    }
}
```

## Gợi ý

### Gợi ý 1

Rủi ro chính là **partition-aware access pattern + business identity + lost update**.

### Gợi ý 2

Cosmos DB data model nên được thiết kế từ query/transaction patterns. Đừng coi container như relational table rồi kỳ vọng mọi query có cùng cost.

## Dừng lại và tự review

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

## Kết quả code review tham khảo

### Critical — `UpdateStockAsync` không có tenant identity

**Vấn đề:** Method nhận SKU nhưng SKU chỉ unique trong tenant.  
**Tại sao xảy ra:** Business key bị mô hình hóa thiếu `tenantId`; cross-partition query trả document đầu tiên phù hợp.  
**Ảnh hưởng production:** Có thể cập nhật nhầm product của tenant khác.  
**Cách sửa:** API/repository contract phải nhận tenant context đã authorize; lookup/update scope theo `tenantId + sku`. Không dùng “first result” để giải quyết ambiguity.

### High — Read-modify-replace có lost-update race

**Vấn đề:** Hai writers đọc cùng stock/version rồi replace toàn document; writer sau có thể overwrite thay đổi của writer trước.  
**Tại sao xảy ra:** Không dùng optimistic concurrency/ETag hoặc atomic operation phù hợp.  
**Ảnh hưởng production:** Stock update mất dữ liệu dưới concurrency.  
**Cách sửa:** Dùng `IfMatchEtag` với ETag đã đọc và xử lý precondition failure bằng domain-specific retry/re-read, hoặc dùng Patch/transactional design phù hợp với semantics. Không blind-retry nếu business operation không commutative.

### High — SKU lookup là cross-partition query

**Vấn đề:** Query chỉ filter SKU và không cung cấp tenant partition key.  
**Tại sao xảy ra:** Repository API thiếu partition context.  
**Ảnh hưởng production:** Fan-out/cross-partition work làm RU/latency tăng theo data distribution.  
**Cách sửa:** Truyền `tenantId`, set `QueryRequestOptions.PartitionKey` hoặc thiết kế deterministic item id/access pattern cho point read khi có thể.

### High — Search không bounded/paginated

**Vấn đề:** Method đọc tất cả pages và materialize mọi result vào memory.  
**Tại sao xảy ra:** API contract không có page size/continuation token.  
**Ảnh hưởng production:** RU, latency, memory và response size tăng theo match count; một request có thể monopolize resources.  
**Cách sửa:** Bounded page size, continuation token và projection chỉ field cần thiết. Nếu requirement là full-text/relevance ở scale lớn, đánh giá search engine chuyên dụng thay vì ép Cosmos query làm mọi search workload.

### Medium — `SELECT *` tăng payload/materialization không cần thiết

**Vấn đề:** Lookup/search luôn đọc full document.  
**Tại sao xảy ra:** Query projection không bám consumer requirement.  
**Ảnh hưởng production:** Tăng response bytes, RU/CPU/memory tùy document shape và query.  
**Cách sửa:** Projection cho read model khi phù hợp; point read vẫn cân nhắc data model/size.

### Medium — `CONTAINS(LOWER(...))` được dùng như full-text search contract

**Vấn đề:** Implementation giả định substring expression là search architecture đủ tốt cho catalog lớn.  
**Tại sao xảy ra:** Requirement về relevance, tokenization, typo, language, sort và scale chưa được làm rõ.  
**Ảnh hưởng production:** Query cost/UX khó dự đoán khi catalog tăng; không có ranking/search semantics rõ.  
**Cách sửa:** Làm rõ search requirement và đo query metrics/RU. Nếu cần full-text/relevance/autocomplete mạnh, cân nhắc Elasticsearch hoặc search service phù hợp, với synchronization/reconciliation rõ ràng.

### Medium — Không expose/đo request charge và diagnostics

**Vấn đề:** Repository bỏ qua RU charge, diagnostics và query behavior.  
**Tại sao xảy ra:** Chỉ đo latency ở application level.  
**Ảnh hưởng production:** Khó phân biệt hot partition, cross-partition fan-out, throttling hay expensive query.  
**Cách sửa:** Thu thập request charge, status/substatus, latency, throttling/retry và diagnostics theo operation; aggregate thành metrics thay vì log verbose diagnostics vô điều kiện.

### Medium — Không có explicit throughput/backpressure cho bulk/search

**Vấn đề:** Repository cho phép caller tạo concurrency tùy ý.  
**Tại sao xảy ra:** RU budget/throttling không được coi là shared resource.  
**Ảnh hưởng production:** Bulk import có thể cạnh tranh RU với interactive admin traffic.  
**Cách sửa:** Đo throttling và workload mix; giới hạn concurrency/batch, tách workload/throughput strategy nếu evidence yêu cầu, và thiết kế retry/backoff theo SDK/service behavior thay vì vòng retry tự phát.

## Phiên bản đề xuất

```csharp
public async Task<Product?> FindBySkuAsync(
    string tenantId,
    string sku,
    CancellationToken ct)
{
    var query = new QueryDefinition(
        "SELECT * FROM c WHERE c.tenantId = @tenantId AND c.sku = @sku")
        .WithParameter("@tenantId", tenantId)
        .WithParameter("@sku", sku);

    var options = new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(tenantId),
        MaxItemCount = 1
    };

    using var iterator =
        _container.GetItemQueryIterator<Product>(query, requestOptions: options);

    if (!iterator.HasMoreResults)
        return null;

    var page = await iterator.ReadNextAsync(ct);
    return page.SingleOrDefault();
}

public async Task UpdateStockAsync(
    string tenantId,
    string sku,
    int newStock,
    CancellationToken ct)
{
    var product = await FindBySkuAsync(tenantId, sku, ct)
        ?? throw new InvalidOperationException("Product not found.");

    product.Stock = newStock;
    product.UpdatedAt = DateTimeOffset.UtcNow;

    var options = new ItemRequestOptions
    {
        IfMatchEtag = product.ETag
    };

    await _container.ReplaceItemAsync(
        product,
        product.Id,
        new PartitionKey(tenantId),
        options,
        ct);
}

public async Task<(IReadOnlyList<ProductSummary> Items, string? Continuation)>
    SearchTenantPageAsync(
        string tenantId,
        string text,
        string? continuation,
        int pageSize,
        CancellationToken ct)
{
    var query = new QueryDefinition(
        @"SELECT c.id, c.sku, c.name, c.stock
          FROM c
          WHERE c.tenantId = @tenantId
            AND CONTAINS(LOWER(c.name), LOWER(@text))")
        .WithParameter("@tenantId", tenantId)
        .WithParameter("@text", text);

    var options = new QueryRequestOptions
    {
        PartitionKey = new PartitionKey(tenantId),
        MaxItemCount = Math.Clamp(pageSize, 1, 100)
    };

    using var iterator =
        _container.GetItemQueryIterator<ProductSummary>(
            query,
            continuation,
            options);

    var page = await iterator.ReadNextAsync(ct);
    return (page.ToList(), page.ContinuationToken);
}
```

Giả định `Product.ETag` được map từ Cosmos item metadata; cách mapping cụ thể cần xác minh theo model/SDK đang dùng. Nếu SKU lookup là cực kỳ hot, có thể cân nhắc item-id strategy hoặc lookup document để đạt point-read pattern, nhưng chỉ sau khi kiểm tra uniqueness, mutation và operational cost.

## Giải thích thiết kế sau khi sửa

Tenant là một phần của authorization/business identity và cũng là partition context. Query tenant-scoped tránh fan-out ngoài tenant. Continuation token biến search thành bounded operation. ETag làm concurrent replace phát hiện conflict thay vì silently overwrite.

Nếu tenant có kích thước/traffic cực kỳ lệch, `/tenantId` có thể tạo hot partition; đó là vấn đề cần đo distribution/partition metrics trước khi đổi partition strategy. Đổi partition key là migration/data-model decision lớn, không phải quick fix.

## Trade-offs

Tenant partitioning đơn giản hóa tenant-scoped reads và transaction boundary, nhưng tenant rất lớn có thể trở thành hot key. ETag làm conflict explicit nhưng caller phải quyết định merge/retry semantics. Pagination làm API phức tạp hơn nhưng giới hạn RU/memory. Đưa full-text search sang Elasticsearch tăng synchronization/eventual-consistency complexity; chỉ đáng giá khi search requirements thực sự cần nó.

## Cách kiểm thử

1. **Security/integration test:** cùng SKU ở hai tenants; update chỉ thay đúng tenant đã authorize.
2. **Concurrency test:** hai writers update cùng product; một stale ETag bị reject và không silently overwrite.
3. **Load test:** catalog lớn với tenant skew; đo RU/request, p95/p99 và throttling cho lookup/search.
4. **Pagination test:** continuation token không duplicate/mất item trong contract đã định nghĩa.
5. **Failure test:** inject 429/transient failures và bulk import concurrency; interactive workload vẫn đáp ứng SLO đã đặt.

## Quan sát trong production

Theo dõi RU/request theo operation, total RU, 429/throttling, retry count, latency p95/p99, request charge distribution, partition-level hotness, query diagnostics sampled, result count/page và ETag conflict rate. Correlate bulk-import throughput với interactive latency/RU. Alert dựa trên sustained throttling, RU anomaly và SLO regression thay vì một request charge đơn lẻ.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào `/tenantId` là partition key tốt, và dấu hiệu nào cho thấy tenant skew trở thành vấn đề?
2. Nếu stock update là increment/decrement thay vì “set absolute value”, concurrency strategy nên thay đổi thế nào?
3. Khi nào bạn chuyển catalog search sang Elasticsearch, và bạn sẽ giữ Cosmos/Elasticsearch đồng bộ ra sao?
