# Code Review Challenge 1 — Rolling deployment khiến Kubernetes phục vụ cấu hình sai

## Bối cảnh

API quản lý đơn hàng chạy 6 Pods trong Kubernetes, triển khai rolling update. Mỗi Pod kết nối PostgreSQL và một hệ thống pricing bên ngoài. Sau release, có request trả giá cũ, 503 tăng trong 1–2 phút và một số request đang xử lý bị ngắt. Dev cho rằng vì Pod vẫn Running nên chắc chắn sẵn sàng. Hệ thống cần zero-downtime theo SLO nhưng chưa định nghĩa cụ thể mức lỗi chấp nhận được. Review manifest và startup code sau.

## Kết quả code review tham khảo

### [Critical] — Credential plaintext trong manifest

**Vấn đề:** Password nằm trong source/manifest.  
**Tại sao xảy ra:** Connection string được hardcode.  
**Ảnh hưởng production:** Lộ credential qua Git, artifact hoặc quyền đọc manifest.  
**Cách sửa:** Secret hoặc external secret provider, quyền RBAC tối thiểu, rotation; tránh ghi secret vào logs. Kubernetes Secret không tự bảo đảm encryption-at-rest nếu cluster chưa cấu hình.

### [High] — Readiness kiểm tra TCP thay vì khả năng phục vụ

**Vấn đề:** Pod nhận traffic trước khi PriceSnapshotLoader hoàn tất.  
**Tại sao xảy ra:** Socket mở không đồng nghĩa warm-up thành công.  
**Ảnh hưởng production:** Response sai/không nhất quán trong rollout.  
**Cách sửa:** Readiness endpoint kiểm tra trạng thái initialized và dependency thiết yếu; xác định rõ liệu pricing cache có bắt buộc để phục vụ.

### [High] — Rolling update làm giảm mạnh capacity

**Vấn đề:** maxUnavailable=3, maxSurge=0.  
**Tại sao xảy ra:** Có thể chỉ còn 3/6 Pods trong rollout, tùy trạng thái.  
**Ảnh hưởng production:** p95 tăng, overload và 503.  
**Cách sửa:** Xem xét maxUnavailable=0, maxSurge=1 hoặc phù hợp capacity; kiểm tra quota và PodDisruptionBudget (không thay thế rollout settings).

### [High] — Thiếu graceful termination strategy

**Vấn đề:** Không có cấu hình hay test bảo đảm drain request.  
**Tại sao xảy ra:** Pod termination, endpoint propagation và request in-flight có race window.  
**Ảnh hưởng production:** Request bị ngắt hoặc client retry tạo duplicate side effect.  
**Cách sửa:** Xác minh terminationGracePeriodSeconds, shutdown timeout, readiness chuyển false, drain và idempotency; không mặc định preStop sleep giải quyết mọi race.

### [High] — Pricing HTTP error bị trả như thành công

**Vấn đề:** API trả raw body qua Results.Content mà không phản ánh upstream status.  
**Tại sao xảy ra:** Không kiểm tra IsSuccessStatusCode, không timeout/cancellation từ request.  
**Ảnh hưởng production:** Client nhận 200 chứa body lỗi, che khuất outage.  
**Cách sửa:** Map lỗi sang ProblemDetails/status phù hợp, đặt timeout budget và truyền RequestAborted.

### [Medium] — Image tag mutable

**Vấn đề:** :latest không xác định artifact bất biến.  
**Tại sao xảy ra:** Tag có thể trỏ sang image khác.  
**Ảnh hưởng production:** Khó audit, rollback và tái hiện lỗi.  
**Cách sửa:** Pin digest, lưu release SHA và deploy artifact đã được kiểm thử.

### [Medium] — Health endpoint dùng chung cho liveness và readiness

**Vấn đề:** /health không phân biệt process sống với khả năng phục vụ.  
**Tại sao xảy ra:** AddHealthChecks mặc định không biết trạng thái cache.  
**Ảnh hưởng production:** Restart loop nếu dependency chập chờn hoặc route traffic quá sớm.  
**Cách sửa:** /health/live và /health/ready với predicates riêng; tránh liveness phụ thuộc remote service dễ lỗi.

### [Medium] — Resource configuration thiếu requests

**Vấn đề:** Chỉ đặt limits, không chủ động định nghĩa CPU/memory requests.  
**Tại sao xảy ra:** Scheduler có thể suy ra requests từ limits nếu không có admission defaults khác.  
**Ảnh hưởng production:** Scheduling, QoS và throttling không như mong muốn.  
**Cách sửa:** Đo CPU, RSS, GC, throttling và chọn requests/limits có chủ đích.

### [Medium] — Startup cache dùng trạng thái toàn cục thiếu hợp đồng

**Vấn đề:** Static Ready có thể không phản ánh dữ liệu thật và không reset đúng khi reload thất bại.  
**Tại sao xảy ra:** Flag rời khỏi lifecycle dữ liệu.  
**Ảnh hưởng production:** Pod sẵn sàng dù snapshot lỗi/stale.  
**Cách sửa:** State service singleton với snapshot version, loadedAt và trạng thái atomic; policy freshness rõ ràng.

## Giải thích thiết kế sau khi sửa

Phân tách liveness và readiness tránh restart vì dependency tạm thời lỗi. Startup probe cho thời gian warm-up mà không bị liveness kill sớm. Pin digest tạo khả năng truy vết release. Budget HTTP và shutdown là hợp đồng vận hành, không phải chỉ cấu hình YAML.

## Trade-offs

maxUnavailable=0 cần spare capacity để surge; nếu quota không đủ rollout sẽ chờ. Readiness phụ thuộc snapshot có thể khiến toàn bộ Pods unready khi hệ thống phụ thuộc lỗi; cần chính sách stale-but-usable có giới hạn. CPU limits quá thấp gây throttling, limits quá cao ảnh hưởng multi-tenancy.

## Cách kiểm thử

1. **Deployment validation:** rollout với 6 Pods, xác nhận không nhận traffic trước khi snapshot ready.
2. **Failure-path:** pricing trả 500/timeout, API không trả 200 giả.
3. **Load test:** đo p95/503 và available endpoints trong rolling update.
4. **Shutdown test:** gửi SIGTERM giữa request dài; xác nhận drain và không mất write.
5. **Security test:** kiểm tra RBAC, Secret access và credential rotation.

## Quan sát trong production

Theo dõi Kubernetes Deployment available/updated replicas, readiness transition, restart/OOMKilled, CPU throttling, request p95/p99, 503 rate, dependency status và snapshot age/version. Correlate trace theo release digest/Pod ID; alert khi ready replicas dưới ngưỡng hoặc stale snapshot vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Khi pricing outage 20 phút, có nên tiếp tục phục vụ snapshot cũ?
2. Nếu cluster không có capacity cho maxSurge=1, bạn chọn chiến lược rollout nào?
3. Phân biệt readiness failure với liveness failure trong incident review.

## Đoạn code cần review

```vue
<script setup lang="ts">
import { ref, watch, onMounted } from 'vue';

type Article = { id: string; title: string; snippet: string };
const props = defineProps<{ tenantId: string }>();
const query = ref('');
const articles = ref<Article[]>([]);
const loading = ref(false);
const error = ref('');
const cache = new Map<string, Article[]>();

async function search() {
  loading.value = true;
  error.value = '';
  const key = query.value.trim();
  if (cache.has(key)) {
    articles.value = cache.get(key)!;
    loading.value = false;
    return;
  }
  try {
    const response = await fetch(
      '/api/articles?tenant=' + props.tenantId + '&q=' + key,
      { credentials: 'include' }
    );
    const data = await response.json();
    cache.set(key, data.items);
    articles.value = data.items;
  } catch (e) {
    error.value = String(e);
  } finally {
    loading.value = false;
  }
}

watch(query, search);
watch(() => props.tenantId, search);
onMounted(search);
</script>

<template>
  <input v-model="query" aria-label="Search articles" />
  <span v-if="loading">Loading...</span>
  <p v-if="error">{{ error }}</p>
  <ul>
    <li v-for="article in articles" :key="article.id">
      <strong>{{ article.title }}</strong>
      <div v-html="article.snippet"></div>
    </li>
  </ul>
</template>
```

## Kết quả code review tham khảo

### [Critical] — Multi-tenant authorization không được bảo đảm

**Vấn đề:** Client gửi tenant tùy ý; không có bằng chứng server xác thực quyền.  
**Tại sao xảy ra:** UI không phải security boundary.  
**Ảnh hưởng production:** Nếu backend chỉ tin query tenant, có thể lộ dữ liệu cross-tenant.  
**Cách sửa:** Backend kiểm tra membership/role cho mỗi request và tenant; test IDOR. Đây là rủi ro cần xác minh, không khẳng định backend hiện đã lỗi.

### [High] — v-html render HTML chưa tin cậy

**Vấn đề:** snippet đưa trực tiếp vào DOM.  
**Tại sao xảy ra:** v-html bypass escaping của interpolation.  
**Ảnh hưởng production:** Stored XSS nếu CMS cho phép markup độc hại.  
**Cách sửa:** Render bằng {{ article.snippet }} khi chỉ cần text; nếu business bắt buộc rich HTML, sanitize phía server theo allowlist và kiểm tra CSP.

### [High] — Race condition ghi đè kết quả mới

**Vấn đề:** Response cũ có thể đến sau response mới.  
**Tại sao xảy ra:** Không abort và không kiểm tra request identity.  
**Ảnh hưởng production:** UI hiển thị bài viết sai tenant hoặc sai query.  
**Cách sửa:** AbortController kết hợp monotonically increasing request ID; clear data khi tenant đổi.

### [High] — Cache key không bao gồm tenant

**Vấn đề:** Hai tenant cùng query dùng chung kết quả.  
**Tại sao xảy ra:** Map chỉ dùng chuỗi tìm kiếm.  
**Ảnh hưởng production:** Lộ nội dung tenant trước trong cùng browser session.  
**Cách sửa:** Key gồm tenant + normalized query + auth scope, hoặc bỏ cache nếu không cần; clear khi identity thay đổi.

### [Medium] — Query string không được encode

**Vấn đề:** & hoặc # làm thay đổi tham số URL.  
**Tại sao xảy ra:** String concatenation.  
**Ảnh hưởng production:** Query sai, khó tái hiện với Unicode/special characters.  
**Cách sửa:** URLSearchParams.

### [Medium] — Không kiểm tra response.ok và shape

**Vấn đề:** JSON lỗi 401/500 có thể bị cache như dữ liệu hợp lệ.  
**Tại sao xảy ra:** response.json() không throw vì HTTP error status.  
**Ảnh hưởng production:** UI hỏng hoặc hiển thị trạng thái sai.  
**Cách sửa:** Kiểm tra status, validate payload, không cache lỗi; xử lý 401 riêng.

### [Medium] — Request storm và loading state sai

**Vấn đề:** Mỗi ký tự tạo request; request cũ finally có thể tắt loading của request mới.  
**Tại sao xảy ra:** Không debounce hoặc sequence guard.  
**Ảnh hưởng production:** Tăng QPS, UI nhấp nháy, rate limit.  
**Cách sửa:** Debounce có cleanup, sequence-aware state và min query length nếu requirement cho phép.

### [Low] — Error message không phù hợp người dùng

**Vấn đề:** String(e) lộ thông tin kỹ thuật, không có retry UX.  
**Tại sao xảy ra:** Error state dùng trực tiếp exception text.  
**Ảnh hưởng production:** UX kém, thiếu khả năng hỗ trợ.  
**Cách sửa:** Thông báo thân thiện, log structured telemetry không chứa search terms nhạy cảm.

## Phiên bản đề xuất

```vue
<script setup lang="ts">
import { ref, watch, onBeforeUnmount } from 'vue';

type Article = { id: string; title: string; snippet: string };
const props = defineProps<{ tenantId: string }>();
const query = ref('');
const articles = ref<Article[]>([]);
const loading = ref(false);
const error = ref('');
let sequence = 0;
let controller: AbortController | undefined;
let timer: ReturnType<typeof setTimeout> | undefined;

async function search(tenant: string, term: string, id: number) {
  controller = new AbortController();
  const signal = controller.signal;
  try {
    const params = new URLSearchParams({ tenant, q: term });
    const response = await fetch('/api/articles?' + params, {
      credentials: 'include', signal
    });
    if (!response.ok) throw new Error('Search failed');
    const data: unknown = await response.json();
    if (!isArticleResult(data)) throw new Error('Invalid payload');
    if (id === sequence) articles.value = data.items;
  } catch (e) {
    if (id === sequence && !signal.aborted)
      error.value = 'Không tải được kết quả. Vui lòng thử lại.';
  } finally {
    if (id === sequence) loading.value = false;
  }
}
function isArticleResult(x: unknown): x is { items: Article[] } {
  return typeof x === 'object' && x !== null &&
    'items' in x && Array.isArray(x.items) &&
    x.items.every((v: unknown) =>
      typeof v === 'object' && v !== null &&
      'id' in v && typeof v.id === 'string' &&
      'title' in v && typeof v.title === 'string' &&
      'snippet' in v && typeof v.snippet === 'string');
}
watch([query, () => props.tenantId], ([term, tenant], _old, onCleanup) => {
  const id = ++sequence;
  controller?.abort();
  if (timer) clearTimeout(timer);
  articles.value = [];
  error.value = '';
  loading.value = true;
  timer = setTimeout(() => { void search(tenant, term.trim(), id); }, 250);
  onCleanup(() => {
    if (timer) clearTimeout(timer);
    controller?.abort();
  });
}, { immediate: true });
onBeforeUnmount(() => { controller?.abort(); if (timer) clearTimeout(timer); });
</script>

<template>
  <input v-model="query" aria-label="Search articles" />
  <span v-if="loading">Loading...</span>
  <p role="alert" v-if="error">{{ error }}</p>
  <ul>
    <li v-for="article in articles" :key="article.id">
      <strong>{{ article.title }}</strong>
      <div>{{ article.snippet }}</div>
    </li>
  </ul>
</template>
```

**Server-side contract bắt buộc:** API xác thực tenant membership/permission dựa trên identity đã xác thực, giới hạn query length, phân trang, kiểm tra rate limits, và chỉ trả dữ liệu của tenant được phép. Client guard chỉ cải thiện UX, không bảo vệ dữ liệu nếu backend sai. Với auth cookie và state-changing endpoints, áp dụng CSRF protection phù hợp; endpoint GET này phải read-only.

## Giải thích thiết kế sau khi sửa

Sequence guard bảo vệ ngay cả khi response đã hoàn thành trước khi abort được xử lý; AbortController giảm công việc dư thừa nhưng không bảo đảm server ngừng xử lý. Debounce giảm QPS. Render text loại bỏ DOM injection khi không yêu cầu rich HTML. Bỏ cache giúp tránh cross-tenant leakage cho bài review này.

## Trade-offs

Debounce tăng độ trễ hiển thị một chút; cancellation không thay thế backend rate limiting. Clear kết quả khi nhập mới tránh stale display nhưng có thể gây UI nhấp nháy; có thể giữ kết quả cũ với nhãn stale rõ ràng nếu product cho phép. Runtime validation tốn thêm CPU nhỏ và có thể dùng schema library trong ứng dụng lớn.

## Cách kiểm thử

1. **Concurrency test:** delay request A, cho B trả trước; UI chỉ hiển thị B.
2. **Security test:** user tenant A gọi API tenant B phải nhận 403/404 theo policy.
3. **XSS test:** snippet chứa script/event handler được hiển thị như text, không thực thi.
4. **Failure-path test:** 401, 500, invalid JSON và abort không làm loading mắc kẹt.
5. **E2E Playwright:** chuyển tenant liên tục khi gõ Unicode và ký tự đặc biệt; không hiển thị dữ liệu tenant trước.

## Quan sát trong production

Theo dõi API QPS per authenticated tenant, p95, 401/403, 429, cancellation rate và backend query duration. Frontend telemetry ghi request sequence và tenant identifier đã pseudonymize, không log raw search term/token. Alert khi cross-tenant authorization test fail trong CI; production audit log các access denied bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu business bắt buộc HTML rich text từ CMS, bạn xây allowlist sanitizer và CSP thế nào?
2. Khi nào nên dùng TanStack Query/Vue Query thay vì tự viết request state?
3. Cache kết quả search có thể an toàn trong điều kiện nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Readiness là hợp đồng về khả năng phục vụ, không phải chỉ mở port. Rolling deployment cần capacity và graceful termination được đo kiểm. Trong frontend multi-tenant, response ordering và cache scoping quyết định tính đúng đắn; backend authorization là security boundary, không phải UI.

## Mẫu tư duy cần nhớ

1. Phân biệt **alive**, **ready** và **correct** trước khi thiết kế health checks.
2. Đo p95, 503, resource pressure và replica availability trước khi đổi rollout strategy.
3. Xem mọi response bất đồng bộ là có thể đến sai thứ tự.
4. Không coi client-side tenant filtering là authorization.
5. Kiểm thử race, failure path và rollback thay vì chỉ happy path.
