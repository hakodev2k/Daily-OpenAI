# Câu 1 — CPU chỉ 35% nhưng API vẫn “đứng hình”: ThreadPool starvation do sync-over-async

**Loại câu hỏi:** Internal Mechanism + Production Debugging  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** C#, .NET ThreadPool, async/await, ASP.NET Core, Kestrel, synchronization, diagnostics, performance engineering, observability

## Bối cảnh

Một ASP.NET Core API chạy .NET 8 trên Linux containers. Bình thường hệ thống xử lý khoảng 800 requests/second với p95 dưới 180 ms.

Sau khi team thêm một integration mới, production bắt đầu có các spike kéo dài 30–90 giây:

- p95/p99 tăng từ dưới 200 ms lên 8–20 giây;
- request queue tăng nhanh;
- CPU process chỉ khoảng 30–40%;
- memory và GC không có spike tương ứng;
- SQL latency bình thường;
- downstream integration có lúc chậm 2–5 giây;
- số lượng threads tăng dần trong lúc incident;
- restart pod làm hệ thống hồi phục ngay nhưng symptom có thể quay lại vài giờ sau;
- scale-out thêm pods giúp tạm thời nhưng không loại bỏ hoàn toàn;
- application log không có deadlock exception.

Code mới có helper synchronous được gọi từ middleware:

```csharp
public sealed class CustomerRiskAccessor
{
    private readonly IRiskClient _riskClient;

    public CustomerRiskAccessor(IRiskClient riskClient)
    {
        _riskClient = riskClient;
    }

    public RiskProfile GetRiskProfile(
        Guid customerId,
        CancellationToken cancellationToken)
    {
        return _riskClient
            .GetRiskProfileAsync(customerId, cancellationToken)
            .GetAwaiter()
            .GetResult();
    }
}
```

Middleware:

```csharp
public async Task InvokeAsync(
    HttpContext context,
    CustomerRiskAccessor riskAccessor)
{
    var customerId = GetCustomerId(context);

    var risk = riskAccessor.GetRiskProfile(
        customerId,
        context.RequestAborted);

    context.Items["RiskProfile"] = risk;

    await _next(context);
}
```

Một số nơi khác còn dùng pattern:

```csharp
var result = Task.Run(() => ExpensiveLegacyCall()).Result;
```

Team có ba giả thuyết:

1. CPU chưa cao nên không thể là ThreadPool starvation.
2. ASP.NET Core không có `SynchronizationContext` kiểu ASP.NET cũ nên `.Result`/`.GetResult()` luôn an toàn.
3. Chỉ cần tăng minimum worker threads là giải quyết được.

## Câu hỏi chính

Hãy giải thích vì sao một ASP.NET Core service có thể bị **ThreadPool starvation** dù CPU còn thấp và không có classic synchronization-context deadlock. Phân tích sync-over-async làm mất worker thread thế nào, cơ chế ThreadPool hill-climbing/injection phản ứng ra sao, vì sao symptom có thể tự hồi phục chậm hoặc biến mất sau restart, và đưa ra cách chẩn đoán + remediation production-safe thay vì chỉ tăng thread count.

## Câu hỏi làm rõ nên cân nhắc

1. `IRiskClient` dùng `HttpClient` async thật hay bọc một synchronous/blocking API?
2. Có bao nhiêu request đồng thời có thể đi qua middleware này?
3. Downstream timeout hiện tại là bao lâu và cancellation có thật sự được propagate không?
4. Có synchronous locks, `SemaphoreSlim.Wait()`, file/network I/O blocking hoặc third-party SDK nào khác không?
5. Container CPU limit và .NET ThreadPool counters trong lúc incident cho thấy gì?

## Gợi ý tư duy

### Gợi ý 1

ThreadPool starvation không yêu cầu CPU saturation. Một worker thread có thể bị **blocked** trong khi gần như không dùng CPU.

### Gợi ý 2

Không có ASP.NET `SynchronizationContext` kiểu cũ giúp tránh một loại deadlock, nhưng không biến blocking wait thành non-blocking wait.

### Gợi ý 3

Hãy phân biệt root cause với mitigation: tăng minimum threads có thể giảm warm-up/starvation window nhưng không sửa việc mỗi request giữ một thread vô ích trong lúc chờ I/O.

## Cấu trúc trả lời đề xuất

1. Vẽ execution flow của request hiện tại.
2. Giải thích worker thread bị giữ tại `.GetResult()` thế nào.
3. So sánh synchronous blocking với `await`.
4. Giải thích vì sao CPU thấp không loại trừ starvation.
5. Giải thích ThreadPool worker injection/hill-climbing ở mức khái niệm.
6. Chỉ ra tác động của downstream latency lên số blocked threads.
7. Nêu diagnostics/counters cần lấy.
8. Đề xuất code fix và timeout/cancellation policy.
9. Đánh giá khi nào `SetMinThreads` chỉ là tactical mitigation.
10. Thiết kế load test để chứng minh fix.

## Ý chính của câu trả lời tốt

### Bắt buộc

- `.GetAwaiter().GetResult()`, `.Result`, `.Wait()` trên một async I/O operation biến request path thành synchronous blocking tại điểm chờ.
- Worker thread đang block không nhất thiết tiêu thụ CPU; vì vậy CPU 35% hoàn toàn tương thích với ThreadPool starvation.
- ASP.NET Core không phụ thuộc `SynchronizationContext` kiểu ASP.NET Framework cũ, nhưng điều đó chỉ loại bỏ một số deadlock patterns; blocking vẫn làm mất khả năng sử dụng worker thread cho request khác.
- Khi downstream chậm, nhiều requests đồng thời cùng block và số worker threads khả dụng giảm; work mới xếp hàng, làm latency lan sang endpoint không liên quan.
- `await` cho phép thread quay lại pool trong thời gian I/O chưa hoàn tất rồi continuation được schedule khi operation complete.
- `Task.Run(...).Result` thường còn tệ hơn với synchronous/blocking work vì vừa chiếm caller thread vừa yêu cầu thêm worker thread cho task.
- Cần propagate async “all the way” thay vì tạo synchronous wrapper trên async call trong request path.

### Điểm cộng

- Theo dõi `dotnet.thread_pool.thread.count`, queue length, completed work item rate, request queue/latency và process CPU theo cùng timeline.
- Dùng `dotnet-counters`, runtime metrics, traces hoặc dump/thread stacks để tìm nhiều threads cùng block tại `.Result`, `GetResult`, `Monitor`, `WaitHandle`, synchronous socket/file I/O.
- Phân biệt starvation với deadlock: starvation có thể tiến triển chậm khi ThreadPool inject thêm workers; deadlock có thể không tiến triển dù thêm threads.
- Có bounded timeout cho downstream và propagate `RequestAborted`.
- Nếu third-party SDK chỉ có synchronous API, giới hạn concurrency riêng thay vì để unbounded requests block toàn pool.

### Senior+

- Hiểu rằng ThreadPool có cơ chế điều chỉnh số threads theo workload, nhưng thread injection có intentionally controlled growth để tránh oversubscription; burst blocking có thể nhanh hơn tốc độ pool thích nghi.
- Không dùng `SetMinThreads` như permanent fix mặc định. Tăng min threads có thể giảm latency trong một số workloads nhưng tăng context switching, memory stack cost và pressure lên downstream dependencies.
- Phân biệt I/O-bound async với CPU-bound work: CPU-bound work vẫn cần CPU; `Task.Run` có thể phù hợp trong một số non-request scenarios nhưng không tạo thêm CPU capacity.
- Có concurrency budget/bulkhead cho downstream chậm để một dependency không chiếm toàn request-processing capacity.
- Thiết kế benchmark bằng mixed workload để chứng minh endpoint không liên quan vẫn giữ SLO khi downstream risk service chậm.

## Hướng giải quyết tham khảo

Trong đoạn code hiện tại, request bắt đầu trên một ThreadPool worker. `GetRiskProfile()` gọi một API async rồi synchronously đợi completion:

```csharp
_riskClient
    .GetRiskProfileAsync(customerId, cancellationToken)
    .GetAwaiter()
    .GetResult();
```

Giả sử downstream mất 5 giây. Worker thread đó nằm blocked gần 5 giây. Nếu 500 requests cùng vào, hàng trăm worker threads có thể cùng bị giữ ở trạng thái wait. CPU vẫn thấp vì các threads này không tính toán; chúng chỉ không thể phục vụ work khác.

Nếu viết đúng async:

```csharp
public async Task<RiskProfile> GetRiskProfileAsync(
    Guid customerId,
    CancellationToken cancellationToken)
{
    return await _riskClient.GetRiskProfileAsync(
        customerId,
        cancellationToken);
}
```

và middleware:

```csharp
public async Task InvokeAsync(
    HttpContext context,
    CustomerRiskAccessor riskAccessor)
{
    var customerId = GetCustomerId(context);

    var risk = await riskAccessor.GetRiskProfileAsync(
        customerId,
        context.RequestAborted);

    context.Items["RiskProfile"] = risk;

    await _next(context);
}
```

thì trong thời gian socket chờ response, worker thread có thể quay về pool để làm việc khác. Khi I/O hoàn tất, continuation được schedule lại.

Không có `SynchronizationContext` kiểu ASP.NET cũ không làm `.Result` trở nên “free”. Classic deadlock như UI thread chờ task trong khi continuation phải quay về đúng UI thread có thể không xảy ra, nhưng throughput starvation vẫn tồn tại.

Tôi sẽ xác minh bằng evidence trước khi sửa hàng loạt. Trong incident window, lấy runtime counters:

```text
thread_pool.thread.count
thread_pool.queue.length
thread_pool.completed_items.count
process CPU
ASP.NET Core request duration / active requests
outbound HTTP duration
```

Nếu thread count tăng, queue length tăng, completed work chậm lại trong khi CPU thấp và traces/stacks cho thấy nhiều workers block ở sync wait, hypothesis rất mạnh.

Với `Task.Run(() => ExpensiveLegacyCall()).Result`, caller giữ một worker để chờ và task cần một worker khác để chạy. Dưới starvation, pattern này có thể khuếch đại nhu cầu threads. Nếu `ExpensiveLegacyCall` là synchronous external I/O từ SDK không thể thay thế ngay, tôi sẽ cô lập nó bằng bounded concurrency, timeout và cân nhắc dedicated worker architecture nếu workload lớn, thay vì queue vô hạn lên shared ThreadPool.

`ThreadPool.SetMinThreads` có thể là emergency mitigation có kiểm chứng nếu application bị latency spike do pool ramp-up, nhưng không được coi là root fix. Nếu tăng từ 100 lên 500 threads mà downstream chỉ chịu được 100 concurrent calls, ta có thể biến starvation thành downstream overload.

Production fix cần thêm resilience boundary: timeout ngắn hơn request budget, cancellation propagation, possibly bulkhead/concurrency limiter và cache nếu domain cho phép. Retry không được unbounded vì retry vào dependency đang chậm có thể nhân đôi contention.

Load test nên mô phỏng downstream 50 ms bình thường rồi chuyển sang 3–5 giây latency trong 60 giây, với mixed traffic. So sánh trước/sau bằng p95/p99, ThreadPool queue, thread count, outbound concurrency và error rate. Mục tiêu không chỉ là risk endpoint phục hồi mà endpoint không phụ thuộc risk service cũng không bị kéo sập.

## Mẫu trả lời trong phỏng vấn

“CPU thấp không loại trừ ThreadPool starvation vì blocked worker gần như không dùng CPU. Ở đây mỗi request lấy một worker rồi `.GetResult()` trên HTTP async call. Khi downstream chậm 5 giây, worker đó bị giữ 5 giây. Burst đủ lớn sẽ làm work mới xếp hàng và latency lan ra toàn process.

ASP.NET Core không có classic `SynchronizationContext` như ASP.NET cũ, nên một loại deadlock biến mất, nhưng blocking wait vẫn là blocking. Fix là async all the way: middleware `await` `GetRiskProfileAsync`, propagate cancellation và đặt timeout/bulkhead cho downstream.

Tôi xác minh bằng ThreadPool thread count, queue length, completed work, CPU, outbound latency và thread stacks. `SetMinThreads` chỉ là mitigation có đo lường; dùng quá mức có thể đẩy overload xuống dependency và tăng context switching. Success criterion là mixed-load p99 ổn định ngay cả khi downstream chậm.”

## Câu hỏi đào sâu

1. Nếu third-party SDK chỉ cung cấp synchronous blocking API và không thể thay trong 6 tháng, bạn cô lập nó khỏi ASP.NET Core request ThreadPool như thế nào?
2. Tại sao tăng `SetMinThreads` có thể làm incident xấu hơn ở SQL/HTTP downstream?
3. Bạn phân biệt ThreadPool starvation với lock contention hoặc connection-pool exhaustion bằng telemetry nào?

## Lỗi trả lời thường gặp

- Cho rằng CPU thấp nghĩa là application còn nhiều capacity.
- Chỉ nói “không có SynchronizationContext nên `.Result` an toàn”.
- Tăng min threads mà không sửa sync-over-async.
- Bọc synchronous I/O trong `Task.Run` rồi `.Result` ngay trong request path.
- Retry aggressive vào downstream đang chậm.
- Chỉ test endpoint bị lỗi, không test blast radius lên endpoint khác.

## Thang điểm 0–10

- **0–2:** Không phân biệt blocking với CPU work.
- **3–4:** Biết `.Result` không tốt nhưng giải thích mơ hồ hoặc chỉ nhắc deadlock.
- **5–6:** Giải thích đúng starvation, async-all-the-way và có runtime metrics cơ bản.
- **7–8:** Có ThreadPool diagnostics, timeout/cancellation, bulkhead và mixed-load testing.
- **9–10:** Reasoning đầy đủ về worker injection, dependency backpressure, tactical vs permanent mitigation và production capacity model.

# Câu 2 — MongoDB đọc “không thấy” order vừa tạo rồi tạo trùng: replication lag, read preference và idempotency

**Loại câu hỏi:** Database Correctness + Distributed Systems + Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** MongoDB, replica sets, read preference, read concern, write concern, consistency, ASP.NET Core, idempotency, unique indexes, retries, observability

## Bối cảnh

Một order-ingestion service dùng MongoDB replica set 3 nodes. API nhận request từ một external marketplace:

```http
POST /api/orders/import
Idempotency-Key: marketplace-ORD-99182
```

Document:

```json
{
  "_id": "...",
  "tenantId": "t-18",
  "externalOrderId": "ORD-99182",
  "status": "Imported",
  "createdAt": "2026-09-14T07:10:00Z"
}
```

Code hiện tại kiểm tra tồn tại trước rồi insert:

```csharp
public async Task ImportAsync(
    string tenantId,
    string externalOrderId,
    CancellationToken cancellationToken)
{
    var existing = await _orders
        .Find(x => x.TenantId == tenantId &&
                   x.ExternalOrderId == externalOrderId)
        .FirstOrDefaultAsync(cancellationToken);

    if (existing is not null)
        return;

    await _orders.InsertOneAsync(
        new OrderDocument
        {
            Id = ObjectId.GenerateNewId(),
            TenantId = tenantId,
            ExternalOrderId = externalOrderId,
            Status = "Imported",
            CreatedAt = DateTime.UtcNow
        },
        cancellationToken: cancellationToken);
}
```

Để giảm tải primary, team cấu hình một số read operations dùng `ReadPreference.SecondaryPreferred`.

Incident:

- marketplace retry request sau 300 ms vì request đầu timeout ở gateway;
- request đầu đã insert order thành công;
- request retry đọc từ secondary và không thấy document vừa insert;
- request retry insert thêm một order có `externalOrderId` giống nhau;
- collection không có unique index trên `(tenantId, externalOrderId)`;
- vài giây sau cả hai documents đều xuất hiện trên mọi replicas;
- developer A nói “MongoDB là eventually consistent nên duplicate là bình thường”; developer B muốn đổi toàn bộ reads thành primary;
- operations muốn giữ khả năng scale read và failover tốt;
- marketplace có thể retry cùng request trong 24 giờ;
- side effect sau insert còn publish một event `OrderImported` tới message bus.

## Câu hỏi chính

Hãy phân tích incident theo cả hai lớp: **consistency semantics** của MongoDB replica set và **application invariant** của idempotent import. Giải thích read preference, replication lag, read/write concern ở mức cần thiết; chỉ ra vì sao `find-then-insert` là race ngay cả khi đọc primary; và thiết kế một giải pháp đúng dựa trên database-enforced uniqueness/atomic operation + idempotent event publication thay vì phụ thuộc vào “đọc thấy trước khi ghi”.

## Câu hỏi làm rõ nên cân nhắc

1. Current write concern là gì (`w:1`, `majority`, journal options)?
2. Read concern đang là `local`, `majority`, hay cấu hình khác?
3. Idempotency identity đúng là `(tenantId, externalOrderId)` hay `Idempotency-Key` riêng?
4. Có workflow nào thực sự cần read-your-own-write ngay sau create không?
5. Event `OrderImported` hiện được publish trước hay sau khi MongoDB write được acknowledged?

## Gợi ý tư duy

### Gợi ý 1

Ngay cả khi mọi reads đi primary, hai requests đồng thời vẫn có thể cùng thực hiện `find` trước khi một request insert.

### Gợi ý 2

Business invariant “mỗi external order chỉ tồn tại một lần” nên được enforce ở nơi có atomic serialization phù hợp — thường là unique index/atomic write — không bằng một pre-check best effort.

### Gợi ý 3

Đừng trộn ba câu hỏi: “write đã được acknowledge chưa?”, “read được phép đọc node nào?”, và “application có duplicate invariant nào?”.

## Cấu trúc trả lời đề xuất

1. Dựng timeline request đầu và retry.
2. Giải thích secondary lag và `SecondaryPreferred`.
3. Tách read preference khỏi write concern/read concern.
4. Chỉ ra TOCTOU race trong `find-then-insert`.
5. Xác định business uniqueness key.
6. Tạo unique compound index.
7. Thiết kế insert/upsert behavior dưới concurrency.
8. Xử lý duplicate-key như idempotent success phù hợp.
9. Thiết kế event publication crash-safe.
10. Nêu consistency policy cho các read use cases khác nhau.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Secondary replica có thể chưa apply write mới khi retry đọc, nên `SecondaryPreferred` có thể không cung cấp read-your-own-write semantics trong flow này.
- Write concern quyết định mức acknowledgement/durability của write; read preference quyết định node selection; read concern quyết định visibility/snapshot semantics. Không được coi ba thứ là một knob duy nhất.
- `find` rồi `insert` là time-of-check/time-of-use race: hai callers có thể cùng thấy “không tồn tại” rồi cùng insert ngay cả trên primary.
- Invariant phải được enforce bằng unique compound index, ví dụ `(TenantId, ExternalOrderId)` hoặc canonical idempotency identity.
- Duplicate-key race nên được map thành idempotent result, không phải tạo document thứ hai.
- Application không cần đổi mọi reads sang primary chỉ để chữa một invariant đáng lẽ database enforce.
- Event publication cần tránh duplicate/lost event khi process crash giữa database write và message publish.

### Điểm cộng

- Tạo index:

```javascript
db.orders.createIndex(
  { tenantId: 1, externalOrderId: 1 },
  { unique: true }
)
```

- Dùng deterministic `_id` hoặc idempotency record nếu domain identity phù hợp, nhưng vẫn cần hiểu scope/collision/migration trade-off.
- Dùng upsert với filter theo business key khi chỉ cần “create if absent”, đồng thời kiểm tra result để biết caller tạo mới hay đã tồn tại.
- Với existing duplicates, phải cleanup/merge trước khi tạo unique index production.
- Tách reads cần freshness cao khỏi analytical/list reads có thể tolerate secondary lag.

### Senior+

- Không hứa rằng `majority` read/write tự động giải quyết duplicate race; concurrency invariant vẫn cần uniqueness/atomic write.
- Cân nhắc retryable writes và driver behavior, nhưng không dựa vào retryable-write mechanism để thay business idempotency.
- Nếu API cần trả lại chính document vừa create, có thể dùng returned write result/state hoặc read policy phù hợp thay vì immediately querying arbitrary secondary.
- Với outbox trong MongoDB, có thể lưu order + outbox event trong cùng transaction nếu cùng deployment/database constraints cho phép; hoặc thiết kế change stream/transactional pattern phù hợp với required guarantees.
- Có telemetry về replication lag, duplicate-key rate, retry count, write concern errors và event publication lag.

## Hướng giải quyết tham khảo

Có hai bug bị trộn với nhau.

Thứ nhất, request retry đọc từ secondary 300 ms sau write. Replication là asynchronous giữa primary và secondaries; secondary có thể chưa apply operation. Vì vậy `SecondaryPreferred` có thể trả trạng thái cũ tại thời điểm đó. Điều này giải thích cụ thể vì sao retry không thấy order đầu.

Nhưng đổi read sang primary vẫn không giải quyết invariant hoàn toàn. Hai requests đồng thời có thể chạy:

```text
A: find -> not found
B: find -> not found
A: insert
B: insert
```

Nếu database không có unique constraint/index, cả hai inserts đều hợp lệ. Đây là TOCTOU race độc lập với replication lag.

Tôi sẽ xác định business identity là `(tenantId, externalOrderId)` rồi enforce tại MongoDB:

```javascript
db.orders.createIndex(
  { tenantId: 1, externalOrderId: 1 },
  { unique: true }
)
```

Trước khi rollout index, cần query existing duplicates, quyết định merge/canonical row và sửa references/events nếu có. Unique index creation sẽ fail nếu dữ liệu hiện tại đã vi phạm invariant.

Code có thể chọn insert-first:

```csharp
try
{
    await _orders.InsertOneAsync(document, cancellationToken: ct);
    return ImportResult.Created(document.Id);
}
catch (MongoWriteException ex)
    when (ex.WriteError?.Category == ServerErrorCategory.DuplicateKey)
{
    return ImportResult.AlreadyImported;
}
```

hoặc atomic upsert nếu cần trả existing/new semantics. Điểm quan trọng là database quyết định concurrency winner bằng unique index, không phải pre-check.

Read preference sau đó được chọn theo use case. List/reporting có thể dùng secondary nếu stale data vài giây chấp nhận được. Flow cần strong freshness sau write có thể đọc primary hoặc tránh re-read bằng cách dùng state/result vừa ghi. Không nên globally force primary nếu phần lớn reads không cần.

Write concern cần được chọn theo durability/SLO. Nếu business không chấp nhận acknowledged write bị mất khi primary failover trước replication, `majority` có thể phù hợp hơn `w:1`, đổi lại latency/availability trade-off. Nhưng dù dùng `majority`, unique index vẫn là thứ bảo vệ duplicate invariant.

Event `OrderImported` tạo failure window khác:

```text
Mongo insert success
process crashes
message publish chưa xảy ra
```

hoặc publish trước rồi DB write fail. Nếu event rất quan trọng, tôi muốn order state và outbox/event intent có atomic relationship. Với MongoDB, có thể dùng transaction cho order + outbox documents khi topology/schema phù hợp, hoặc một pattern dựa trên change stream có semantics được thiết kế rõ. Publisher phải dùng stable event id để consumer deduplicate vì message delivery thường at-least-once.

Idempotency ở HTTP layer có thể lưu `Idempotency-Key` nếu cùng external order có nhiều operation types hoặc response replay requirement. Tuy nhiên key đó không thay unique business constraint nếu `(tenant, externalOrder)` bản chất vẫn phải duy nhất.

Testing phải bắn hàng trăm concurrent imports cùng key, chạy với induced replica lag/retry, rồi assert đúng một order canonical và đúng logical event. Không chỉ test request tuần tự.

## Mẫu trả lời trong phỏng vấn

“Secondary lag giải thích vì sao retry sau 300 ms không thấy write vừa xảy ra, nhưng đó chưa phải root correctness fix. `find-then-insert` vốn đã race: hai callers có thể cùng thấy not-found ngay cả khi đọc primary.

Tôi enforce invariant ở Mongo bằng unique compound index `(tenantId, externalOrderId)`. Sau đó insert-first hoặc atomic upsert; duplicate-key được xử lý như idempotent success. Read preference vẫn chọn theo từng use case — reporting có thể đọc secondary, flow cần freshness thì primary hoặc dùng write result.

Write concern nói về acknowledgement/durability, read preference nói node nào đọc, read concern nói visibility; chúng không thay thế unique constraint. Với `OrderImported`, tôi dùng outbox/change-stream design có stable event id để crash/retry không tạo lost hoặc duplicate logical side effect.”

## Câu hỏi đào sâu

1. Nếu collection đang có 20 triệu documents và hàng nghìn duplicate business keys, bạn rollout unique index mà không gây outage thế nào?
2. `writeConcern: majority` giúp gì và **không** giúp gì cho idempotency incident này?
3. Nếu consumer nhận `OrderImported` hai lần từ message broker, invariant cuối cùng nên được bảo vệ ở producer, broker hay consumer?

## Lỗi trả lời thường gặp

- Nói “MongoDB eventually consistent nên duplicate là chấp nhận được”.
- Chỉ đổi `SecondaryPreferred` thành primary.
- Giữ `find-before-insert` và hy vọng latency nhỏ sẽ tránh race.
- Nhầm `majority` write concern với unique/idempotent business operation.
- Thêm unique index mà không cleanup duplicates hiện hữu.
- Publish event trực tiếp sau insert mà không phân tích crash window.

## Thang điểm 0–10

- **0–2:** Chỉ đổ lỗi cho replication lag.
- **3–4:** Biết cần đọc primary nhưng bỏ sót application race.
- **5–6:** Có unique index + atomic write/idempotent duplicate handling và hiểu read preference cơ bản.
- **7–8:** Phân biệt write/read concerns, có outbox/event semantics và rollout plan.
- **9–10:** Reasoning đầy đủ về replication, concurrency invariant, durability trade-offs, migration dữ liệu và end-to-end at-least-once processing.

# Câu 3 — Thêm một enum value làm mobile client cũ crash: backward compatibility của REST API thực sự là gì?

**Loại câu hỏi:** API Design + Architecture + Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, REST APIs, JSON contracts, backward compatibility, API versioning, schema evolution, OpenAPI, client generation, rollout strategy, observability

## Bối cảnh

Một public REST API trả order:

```http
GET /api/orders/{id}
```

Response hiện tại:

```json
{
  "id": "7a9d...",
  "status": "Processing",
  "total": 125.50
}
```

Server enum:

```csharp
public enum OrderStatus
{
    Pending,
    Processing,
    Completed,
    Cancelled
}
```

Sau khi business thêm workflow fraud review, backend bổ sung:

```csharp
FraudReview
```

Server deploy thành công. Web client mới hoạt động đúng. Nhưng mobile app version cũ dùng generated client có enum đóng:

```kotlin
enum class OrderStatus {
    Pending,
    Processing,
    Completed,
    Cancelled
}
```

JSON deserializer của app throw khi nhận chuỗi `"FraudReview"`, làm order-detail screen crash.

Các chi tiết khác:

- khoảng 22% mobile users vẫn ở app version cũ và không thể ép update ngay;
- API docs trước đây nói endpoint là `v1` nhưng không định nghĩa policy về enum evolution;
- một số consumers là partner integrations do bên ngoài vận hành;
- backend team cho rằng “thêm enum member chỉ là additive change nên không breaking”;
- mobile team nói server phải tạo `/v2` cho mọi enum value mới;
- Product muốn rollout `FraudReview` trong tuần này;
- fraud-reviewed orders không thể đơn giản map thành `Processing` ở mọi business flow vì một số actions cần bị disable;
- OpenAPI được dùng để generate clients cho C#, TypeScript và Kotlin;
- team chưa có contract test chạy old client fixtures against new server responses.

## Câu hỏi chính

Hãy phân tích vì sao một thay đổi **additive trên server schema** vẫn có thể là breaking change đối với consumers. Phân biệt tolerant-reader/extensible-enum design với closed enum, xác định trách nhiệm giữa server/client contract, và đề xuất strategy để rollout business state mới mà không làm client cũ crash. Nêu rõ khi nào cần API version mới, khi nào compatibility adapter là đủ, và guardrails nào phải được thêm vào OpenAPI/client-generation/release process.

## Câu hỏi làm rõ nên cân nhắc

1. API contract hiện tại có hứa enum là closed set hay clients được yêu cầu xử lý unknown values?
2. Old mobile client có thể nhận raw string fallback hay deserializer fail trước application logic?
3. Action permissions có được trả riêng từ server hay client suy ra hoàn toàn từ `status`?
4. Partner SDKs có cùng generated-enum behavior không?
5. API versioning hiện là URL, header, media type hay chỉ là label trong docs?

## Gợi ý tư duy

### Gợi ý 1

Compatibility phải được đánh giá từ phía consumer parser/behavior, không chỉ từ diff của server DTO.

### Gợi ý 2

“Thêm field” thường dễ backward-compatible hơn “thêm value vào closed vocabulary”.

### Gợi ý 3

Nếu client dùng enum để quyết định allowed actions, fallback chỉ để tránh crash chưa chắc đã đủ để giữ business correctness.

## Cấu trúc trả lời đề xuất

1. Xác định existing contract và actual client behavior.
2. Phân loại change theo wire compatibility và semantic compatibility.
3. Đo population các client versions/partners bị ảnh hưởng.
4. Chọn short-term rollout adapter.
5. Thiết kế long-term extensible status contract.
6. Tách state display khỏi action capabilities nếu cần.
7. Xác định tiêu chí tạo API version mới.
8. Update OpenAPI/code generation guidance.
9. Thêm compatibility/consumer contract tests.
10. Thiết kế deprecation/telemetry policy.

## Ý chính của câu trả lời tốt

### Bắt buộc

- “Additive” ở server không tự đồng nghĩa backward-compatible. Một consumer dùng closed enum có thể reject unknown token và fail toàn response.
- Compatibility gồm ít nhất wire-format compatibility và semantic/behavior compatibility.
- Nếu v1 contract thực tế cho phép chỉ bốn enum values và old clients không chịu unknown values, server phải coi việc gửi value thứ năm là breaking đối với population đó.
- Không nhất thiết mọi enum addition đều yêu cầu `/v2`; nếu contract từ đầu định nghĩa extensible string + unknown fallback thì có thể evolve trong cùng version.
- Short-term rollout phải dựa trên client capabilities/version hoặc compatibility representation rõ, không gửi `FraudReview` mù quáng cho clients đã biết sẽ crash.
- Mapping `FraudReview` thành `Processing` chỉ hợp lệ nếu semantic behavior của old client vẫn an toàn; nếu old client cho phép action nguy hiểm, cần server-side authorization/capability enforcement.
- Server luôn phải enforce allowed actions; client UI không phải security/control boundary.

### Điểm cộng

- Trả thêm explicit capabilities như:

```json
{
  "status": "FraudReview",
  "allowedActions": ["View", "CancelRequest"]
}
```

cho clients mới, thay vì để mọi client hard-code state machine.
- Client mới parse unknown status thành `Unknown(rawValue)` hoặc equivalent tolerant representation.
- Dùng OpenAPI extension/generator template để generated clients có unknown-enum fallback nếu ecosystem hỗ trợ.
- Có server-side telemetry về client/app version và response status distribution trước rollout.
- Partner API có deprecation notice/support window thay vì assume instant upgrade.

### Senior+

- Phân biệt syntactic compatibility với semantic compatibility: parser không crash nhưng treating unknown as `Processing` vẫn có thể sai business rule.
- Có compatibility matrix giữa API version × client generation × feature state.
- Dùng capability negotiation/header chỉ khi thật sự cần, tránh tạo matrix vô hạn theo app version.
- Xem enum/vocabulary as a versioned domain contract; document open/closed semantics ngay trong API guidelines.
- Contract tests replay representative old-client deserialization against generated payloads của new server trong CI.

## Hướng giải quyết tham khảo

Backend team gọi đây là additive vì không xóa property hay đổi JSON shape. Nhưng wire consumer không nhìn diff C# enum; nó nhận một token ngoài tập giá trị mà parser biết. Nếu Kotlin generated enum deserializer throw, response mới **không tương thích** với client đó.

Short-term trước rollout, tôi sẽ xác định client population từ telemetry (`appVersion`, SDK version, partner identifier) và contract thực tế. Nếu old app chắc chắn crash với `FraudReview`, server không được gửi value đó cho old contract mà không có adapter.

Có vài options, chọn theo semantics:

### Option A — Compatibility projection cho v1 cũ

Nếu `FraudReview` có thể được biểu diễn an toàn là một state cũ **chỉ cho mục đích display**, server có thể trả compatibility status cho old clients, nhưng mọi mutating action vẫn phải authorize server-side theo canonical state. Ví dụ old client thấy `Processing` nhưng nếu nó gọi endpoint `ship`, server từ chối vì canonical state là `FraudReview`.

Điều này chỉ hợp lệ nếu UX degradation được Product chấp nhận và không dẫn đến dangerous action assumptions.

### Option B — Version/capability-gated representation

Clients mới quảng bá contract capability hoặc dùng API version mới; server trả `FraudReview` chỉ khi consumer hỗ trợ. Old clients nhận compatible projection. Cách này cần lifecycle rõ để không biến code thành hàng chục `if appVersion` khó xoá.

### Option C — API v2

Nếu state mới thay đổi đáng kể response semantics, action model hoặc contract v1 đã rõ ràng là closed enum không thể evolve, version mới là boundary sạch hơn. Nhưng tạo v2 chỉ cho một enum member có cost: duplicate surface, support/deprecation, routing/docs/SDKs. Quyết định phải dựa trên contract semantics, không phải reflex.

Lâu dài, tôi sẽ thiết kế enum-like domain values là extensible khi business biết chắc state machine còn phát triển. Ví dụ client model không deserialize thẳng vào closed enum không fallback:

```kotlin
sealed class OrderStatus {
    data object Pending : OrderStatus()
    data object Processing : OrderStatus()
    data object Completed : OrderStatus()
    data object Cancelled : OrderStatus()
    data class Unknown(val raw: String) : OrderStatus()
}
```

Generated-client ecosystem có thể cần custom converter/template. OpenAPI documentation phải nói rõ whether unknown values may appear. Nếu specification/tooling đánh dấu closed enum và generator tạo parser strict, server phải tôn trọng điều đó cho version hiện tại.

Tôi cũng muốn giảm việc client suy ra business capability từ status. Response mới có thể expose `allowedActions`, nhưng server vẫn là authority khi action endpoint được gọi. Điều này giúp thêm state mới mà UI cũ không vô tình mở operation không hợp lệ.

CI cần compatibility suite. Với mỗi supported client generation/version quan trọng, lấy representative payloads mới — gồm future/unknown enum values — và chạy deserialize/behavior test. Server contract tests cũng kiểm tra rằng old-version response không chứa token ngoài declared vocabulary.

Rollout `FraudReview` nên theo phases:

1. Deploy server support nhưng chưa expose state tới incompatible clients.
2. Release tolerant new clients/SDKs.
3. Theo dõi adoption và partner readiness.
4. Enable state exposure cho capable clients.
5. Duy trì compatibility adapter trong documented support window.
6. Deprecate old representation/version theo policy.

Telemetry cần đo request count theo API/client version, deserialize-related client crash nếu có mobile telemetry, count orders ở `FraudReview`, rejected actions do canonical-state rules và partner adoption.

## Mẫu trả lời trong phỏng vấn

“Thêm enum member chỉ additive ở source schema; với generated client dùng closed enum, token mới có thể làm deserializer throw nên đây là breaking wire change đối với client đó. Tôi đánh giá compatibility từ consumer behavior, không từ C# diff.

Ngắn hạn, tôi không gửi `FraudReview` cho old clients nếu biết chúng crash. Tôi dùng compatibility projection hoặc version/capability-gated representation, nhưng server luôn authorize action theo canonical state — không dựa vào status mà old UI nhìn thấy.

Lâu dài, nếu vocabulary được phép mở rộng, contract phải nói rõ và generated clients phải có unknown fallback. Nếu v1 đã hứa closed enum hoặc semantics mới không thể biểu diễn an toàn, tôi tạo v2. Tôi thêm old-client contract tests vào CI để mọi schema change được kiểm tra cả syntactic và semantic compatibility trước rollout.”

## Câu hỏi đào sâu

1. Nếu old client map `FraudReview` thành `Unknown` nhưng UI vẫn cho phép nút “Cancel”, đó đã là backward-compatible chưa?
2. Bạn sẽ thiết kế OpenAPI/client generator thế nào để enum mới không làm SDK cũ crash mà vẫn giữ type safety tốt?
3. Khi nào capability negotiation tốt hơn API versioning, và khi nào nó tạo quá nhiều compatibility states để vận hành?

## Lỗi trả lời thường gặp

- Khẳng định enum member mới luôn non-breaking vì “chỉ thêm”.
- Chỉ sửa mobile app mới nhưng quên 22% clients cũ/partners.
- Map mọi unknown status thành `Processing` mà không kiểm tra semantic safety.
- Cho client quyết định authorization/action validity dựa trên local enum.
- Tạo `/v2` cho mọi thay đổi nhỏ mà không có versioning policy.
- Không test generated old clients against new response fixtures.

## Thang điểm 0–10

- **0–2:** Chỉ tranh luận “server additive” hay “client bug”.
- **3–4:** Nhận ra unknown enum có thể crash nhưng giải pháp chỉ là ép client update.
- **5–6:** Có compatibility projection/versioning và tolerant-reader design cơ bản.
- **7–8:** Phân biệt syntactic/semantic compatibility, có server-side capability enforcement và contract testing.
- **9–10:** Thiết kế hoàn chỉnh API-evolution policy, generator guardrails, rollout/deprecation matrix và telemetry cho heterogeneous consumer ecosystem.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- ThreadPool starvation có thể xảy ra khi CPU còn thấp vì worker threads bị **blocked**, không phải đang tính toán.
- ASP.NET Core không có classic request `SynchronizationContext` không có nghĩa `.Result`, `.Wait()` hay `.GetResult()` trở thành cách chờ async an toàn về throughput.
- MongoDB secondary lag có thể làm stale read, nhưng duplicate business invariant phải được bảo vệ bằng unique constraint/atomic write thay vì `find-before-insert`.
- `read preference`, `read concern` và `write concern` giải quyết các khía cạnh khác nhau; không knob nào thay thế application idempotency.
- API backward compatibility phải được đánh giá từ actual consumer parser + behavior; server-side additive schema change vẫn có thể breaking.
- Enum/domain vocabulary cần contract rõ là open hay closed, và client tooling phải có strategy cho unknown values nếu muốn evolve cùng API version.

## Mẫu tư duy cần nhớ

- **CPU thấp không đồng nghĩa còn request-processing capacity nếu threads đang blocked.**
- **Async I/O chỉ phát huy giá trị khi call chain không bị chặn lại bằng synchronous wait.**
- **Đưa uniqueness invariant xuống database thay vì dùng read-before-write để “kiểm tra”.**
- **Tách consistency semantics khỏi business idempotency.**
- **Compatibility được quyết định bởi consumer behavior, không chỉ bởi server schema diff.**
- **Phân biệt parser compatibility với business-semantic compatibility.**
