# Code Review Challenge 1 — Endpoint tải file chạy tốt ở test nhưng làm memory tăng vọt và request chết hàng loạt khi tải đồng thời

**Chủ đề:** C#/.NET 8, ASP.NET Core, Azure Blob Storage, streaming, memory allocation, LOH, cancellation, HTTP range requests, dependency failure, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–11 vấn đề

## Bối cảnh

Một ASP.NET Core API cung cấp tài liệu cho web/mobile client. Metadata của file nằm trong SQL Server, binary nằm trong Azure Blob Storage.

Yêu cầu:

- file phổ biến khoảng 5–20 MB, nhưng có thể lên tới 700 MB;
- production chạy nhiều App Service instances;
- khoảng vài trăm download có thể diễn ra đồng thời trong giờ cao điểm;
- user chỉ được tải file thuộc tenant mà họ có quyền truy cập;
- client có thể hủy download hoặc mất mạng;
- download lớn cần hoạt động ổn định khi load tăng;
- backend không được giữ toàn bộ file trong memory nếu không cần thiết;
- operations cần theo dõi latency, bytes transferred, cancellation và Blob dependency failures.

Sau một đợt traffic tăng, production xuất hiện:

- process memory tăng rất nhanh;
- GC time tăng và một số instances bị restart;
- p95 latency của cả các API không liên quan cũng tăng;
- request bị client cancel nhưng Blob download vẫn tiếp tục một lúc;
- tải file lớn dễ gặp 502/504;
- team đề xuất “scale up RAM” vì code hiện tại nhìn khá đơn giản.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/files")]
public sealed class FilesController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly BlobContainerClient _container;
    private readonly ILogger<FilesController> _logger;

    public FilesController(
        AppDbContext db,
        BlobContainerClient container,
        ILogger<FilesController> logger)
    {
        _db = db;
        _container = container;
        _logger = logger;
    }

    [HttpGet("{id:guid}/download")]
    public async Task<IActionResult> Download(Guid id)
    {
        var file = await _db.Files
            .SingleOrDefaultAsync(x => x.Id == id);

        if (file is null)
            return NotFound();

        var blob = _container.GetBlobClient(file.BlobName);

        using var memory = new MemoryStream();
        await blob.DownloadToAsync(memory);

        var bytes = memory.ToArray();

        _logger.LogInformation(
            "Downloaded file {FileId} {FileName} with {Bytes} bytes",
            file.Id,
            file.FileName,
            bytes.Length);

        return File(
            bytes,
            file.ContentType,
            file.FileName);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong endpoint download.
2. Xác định các vấn đề performance, security, reliability và maintainability.
3. Giải thích production impact, đặc biệt khi nhiều file lớn được tải đồng thời.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design đã sửa mà không thêm hạ tầng phức tạp nếu chưa cần.
6. Giải thích testing cho authorization, cancellation, large files, dependency failure và load.
7. Đề xuất production telemetry để chứng minh download path hoạt động an toàn.

## Câu hỏi gợi mở

1. Với file 700 MB, endpoint có bao nhiêu bản sao dữ liệu có thể tồn tại trong managed memory trong cùng một request?
2. Điều gì xảy ra với memory/GC khi hàng chục request lớn chạy đồng thời?
3. Request cancellation hiện được propagate đến EF Core và Azure Blob calls ở đâu?
4. Việc tìm file chỉ bằng `Id` có đủ để chứng minh caller được phép đọc tài nguyên của tenant đó không?
5. Có cần backend materialize toàn bộ blob trước khi gửi byte đầu tiên cho client không?

## Gợi ý

### Gợi ý 1

Primary risk là **buffering toàn bộ payload lớn trong application memory**, sau đó còn tạo thêm một bản sao bằng `ToArray()`.

### Gợi ý 2

Hãy reasoning theo pipeline end-to-end: authorization → metadata query → Blob read → ASP.NET Core response → client disconnect, và xem cancellation/backpressure/partial failure đi qua từng bước như thế nào.

## Kết quả code review tham khảo

### Critical — Thiếu authorization theo tenant/resource

**Vấn đề:**  
Query chỉ dùng `file.Id == id`; không có điều kiện tenant/owner/policy nào trong đoạn code.

**Tại sao xảy ra:**  
Một GUID khó đoán không phải authorization control. Nếu caller biết hoặc lấy được ID của tenant khác, endpoint có thể trả file đó.

**Ảnh hưởng production:**  
Có thể dẫn tới cross-tenant data exposure, là lỗi security nghiêm trọng hơn mọi vấn đề performance trong endpoint.

**Cách sửa:**  
Resolve tenant/user identity từ trusted authenticated context và enforce authorization ở query hoặc policy/service boundary. Ví dụ query theo cả `Id` và `TenantId`, sau đó kiểm tra quyền chi tiết nếu domain yêu cầu.

### High — Toàn bộ blob được buffer vào `MemoryStream`

**Vấn đề:**  
`DownloadToAsync(memory)` giữ toàn bộ file trong process trước khi response bắt đầu gửi.

**Tại sao xảy ra:**  
Implementation biến một workload streaming tự nhiên thành workload memory-bound.

**Ảnh hưởng production:**  
Một vài downloads hàng trăm MB có thể chiếm nhiều GB memory, tạo allocation pressure, GC pauses và process recycle/OOM. Các API khác trên cùng instance bị ảnh hưởng theo.

**Cách sửa:**  
Stream dữ liệu từ Blob Storage tới HTTP response hoặc dùng API trả stream phù hợp, tránh materialize toàn bộ payload.

### High — `ToArray()` tạo thêm một bản sao lớn

**Vấn đề:**  
Sau khi `MemoryStream` đã chứa toàn bộ blob, `ToArray()` allocate một byte array mới có kích thước tương đương.

**Tại sao xảy ra:**  
`ToArray()` trả một copy chứ không chuyển ownership của underlying buffer.

**Ảnh hưởng production:**  
Peak memory của một request lớn có thể cao hơn đáng kể kích thước file; với concurrency, memory amplification trở nên nghiêm trọng.

**Cách sửa:**  
Không buffer file. Nếu payload nhỏ bắt buộc phải buffer, cần giới hạn kích thước rõ ràng và tránh copy không cần thiết.

### High — Cancellation không được propagate

**Vấn đề:**  
Action không nhận `CancellationToken`; EF Core và Blob calls cũng không nhận `HttpContext.RequestAborted`.

**Tại sao xảy ra:**  
Client disconnect không tự động biến mọi downstream operation thành canceled operation nếu token không được truyền.

**Ảnh hưởng production:**  
Application có thể tiếp tục đọc hàng trăm MB từ Blob Storage sau khi client đã rời đi, lãng phí bandwidth, sockets và compute.

**Cách sửa:**  
Nhận `CancellationToken` trong action và propagate tới database/blob operations hỗ trợ token. Treat cancellation như expected request outcome, không log như application error mặc định.

### High — Response bắt đầu quá muộn và không tận dụng backpressure

**Vấn đề:**  
Client chỉ nhận byte đầu tiên sau khi toàn bộ blob đã tải xong vào memory.

**Tại sao xảy ra:**  
Buffering phá streaming pipeline giữa upstream Blob và downstream HTTP client.

**Ảnh hưởng production:**  
Time-to-first-byte cao, proxy timeout dễ xảy ra, và application không tận dụng được natural backpressure khi client đọc chậm.

**Cách sửa:**  
Dùng stream response. Với file rất lớn hoặc traffic cao, cân nhắc direct-to-Blob download bằng short-lived SAS sau khi backend authorization, nếu security/audit requirement cho phép.

### Medium — Không hỗ trợ range processing/resume rõ ràng

**Vấn đề:**  
Byte-array response hiện tại không thể hiện chiến lược hỗ trợ HTTP range cho large-file download.

**Tại sao xảy ra:**  
Mobile/network clients có thể cần resume partial download; proxy/browser cũng hưởng lợi từ range semantics trong một số use cases.

**Ảnh hưởng production:**  
Mất mạng gần cuối file có thể buộc client tải lại toàn bộ payload, tăng cost và load.

**Cách sửa:**  
Nếu requirement cần resume/media seeking, dùng response path hỗ trợ range processing và xác minh Blob stream seek/range behavior tương ứng. Không bật range chỉ theo thói quen nếu client không cần.

### Medium — Metadata query tracking entity không cần thiết

**Vấn đề:**  
Download chỉ đọc metadata nhưng query tạo tracked entity.

**Tại sao xảy ra:**  
Default EF Core tracking được dùng dù request không update entity.

**Ảnh hưởng production:**  
Đây không phải root cause chính nhưng tạo overhead không cần thiết trên hot path.

**Cách sửa:**  
Dùng `AsNoTracking()` và projection chỉ lấy các fields cần cho authorization/download.

### Medium — Không phân loại Blob failure và không có response contract rõ

**Vấn đề:**  
Blob có thể bị xóa, permission/config sai, timeout hoặc transient network failure nhưng endpoint không map các outcome này rõ ràng.

**Tại sao xảy ra:**  
Metadata tồn tại không đảm bảo blob luôn tồn tại hoặc dependency luôn khỏe.

**Ảnh hưởng production:**  
Khách hàng có thể nhận generic 500; operations khó phân biệt orphaned metadata với transient dependency incident.

**Cách sửa:**  
Phân loại `404` từ Blob như data-consistency issue phù hợp domain, transient dependency failures theo retry policy an toàn, và trả `ProblemDetails`/status code nhất quán. Không retry dài trên request path nếu làm vượt SLO.

### Medium — Logging filename có thể làm tăng exposure của dữ liệu nhạy cảm

**Vấn đề:**  
Log ghi nguyên `FileName`; tên file có thể chứa PII hoặc business-sensitive text.

**Tại sao xảy ra:**  
Operational logs thường có retention/access scope rộng hơn application data.

**Ảnh hưởng production:**  
Tăng data exposure và compliance risk.

**Cách sửa:**  
Log stable identifiers/categorized metadata cần thiết; chỉ log filename nếu đã được đánh giá và policy cho phép.

### Low — Telemetry hiện tại chỉ xuất hiện sau khi toàn bộ download hoàn tất

**Vấn đề:**  
Một log success không đủ để quan sát throughput, aborted downloads, dependency duration hay bytes actually sent tới client.

**Tại sao xảy ra:**  
Observability được đặt sau implementation thay vì thiết kế cùng streaming lifecycle.

**Ảnh hưởng production:**  
Team thấy memory/timeout nhưng khó chứng minh bottleneck nằm ở Blob read, server buffering, downstream client hay proxy.

**Cách sửa:**  
Thêm metrics/traces cho request duration, TTFB, blob dependency duration, response bytes, active downloads, cancellations, failure category và memory/GC ở process level.

## Phiên bản đề xuất

Một hướng đơn giản là authorization trong query, đọc Blob dưới dạng stream và để ASP.NET Core stream response thay vì materialize byte array.

```csharp
[HttpGet("{id:guid}/download")]
public async Task<IActionResult> Download(
    Guid id,
    CancellationToken cancellationToken)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    var file = await _db.Files
        .AsNoTracking()
        .Where(x => x.Id == id && x.TenantId == tenantId)
        .Select(x => new
        {
            x.Id,
            x.BlobName,
            x.FileName,
            x.ContentType
        })
        .SingleOrDefaultAsync(cancellationToken);

    if (file is null)
        return NotFound();

    var blob = _container.GetBlobClient(file.BlobName);

    try
    {
        var stream = await blob.OpenReadAsync(
            new BlobOpenReadOptions(allowModifications: false),
            cancellationToken);

        return File(
            stream,
            file.ContentType,
            file.FileName,
            enableRangeProcessing: true);
    }
    catch (RequestFailedException ex) when (ex.Status == 404)
    {
        _logger.LogWarning(
            "Blob missing for authorized file {FileId}",
            file.Id);

        return Problem(
            statusCode: StatusCodes.Status503ServiceUnavailable,
            title: "File is temporarily unavailable");
    }
}
```

Nếu client không cần range support, có thể tắt `enableRangeProcessing`. Nếu traffic/download size đủ lớn và security model cho phép, backend có thể authorize request rồi phát short-lived read-only SAS để client tải trực tiếp từ Blob/CDN; khi đó cần cân nhắc auditability, revocation window, content-disposition, CORS và exposure của Blob URL.

## Giải thích thiết kế sau khi sửa

Thiết kế mới giữ application làm authorization boundary nhưng loại bỏ việc giữ toàn bộ binary trong managed memory. Metadata query chỉ lấy field cần thiết và được scoped theo tenant. Cancellation được propagate tới SQL/Blob acquisition; response stream cho phép ASP.NET Core gửi dữ liệu dần tới client.

Điểm quan trọng là streaming không có nghĩa “memory bằng 0”. Server, SDK và network stack vẫn dùng buffers, nhưng memory footprint trở thành bounded hơn nhiều so với giữ toàn bộ payload theo từng request.

Nếu số download lớn đến mức application instances trở thành data-transfer proxy không cần thiết, direct Blob/CDN delivery có thể là bước tiếp theo. Quyết định đó phải dựa trên security, audit, traffic và cost chứ không phải vì streaming code trông phức tạp.

## Trade-offs

- Stream qua backend giữ authorization/audit control tập trung nhưng tiêu tốn outbound connection/bandwidth của application.
- Direct SAS giảm load backend nhưng tạo short-lived delegated access cần policy chặt chẽ.
- Range processing giúp resume nhưng làm request semantics/cache/proxy behavior phức tạp hơn.
- Retry Blob reads trên request path có thể giúp transient failure nhưng cũng kéo dài latency; cần timeout/budget rõ ràng.
- Tăng RAM có thể trì hoãn symptom nhưng không sửa memory amplification tuyến tính theo file size × concurrency.

## Cách kiểm thử

1. **Security integration test:** user tenant A không tải được file tenant B dù biết `fileId`; verified authorization context phải được dùng trong query/policy.
2. **Large-file/load test:** tải đồng thời nhiều file 500–700 MB, đo working set, allocations, GC pause, p95/p99 và active connections; memory không tăng tuyến tính theo tổng kích thước payload đang tải.
3. **Cancellation test:** client hủy download giữa chừng; xác minh request kết thúc, Blob operation/stream được dispose và không tiếp tục transfer không cần thiết.
4. **Failure-path test:** Blob trả 404/timeout/transient 5xx; xác minh mapping, logs, retry budget và không leak stream/resource.
5. **Range/E2E test:** nếu range được hỗ trợ, kiểm tra `Range` request/resume với reverse proxy/CDN thực tế và xác minh bytes/content-range đúng.

## Quan sát trong production

Theo dõi:

- request rate, p50/p95/p99 duration và TTFB của download endpoint;
- active concurrent downloads và response bytes;
- canceled/aborted download count;
- Azure Blob dependency latency, failure rate và status categories;
- process working set, allocation rate, Gen 2/LOH/GC pause metrics;
- 5xx/502/504 theo instance;
- trace correlation từ HTTP request tới SQL metadata query và Blob dependency;
- alert khi memory, GC time, dependency failure hoặc aborted download tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn backend streaming, khi nào chọn SAS/direct download qua Blob/CDN?
2. Nếu requirement bắt buộc audit chính xác số byte user đã nhận, design sẽ thay đổi như thế nào?
3. Nếu Blob bị thay đổi trong lúc client đang range-download, bạn sẽ dùng ETag/conditional request ra sao?

# Code Review Challenge 2 — Kubernetes rollout “tự chữa lành” nhưng lại tạo restart storm khi database chậm vài giây

**Chủ đề:** Kubernetes, ASP.NET Core health checks, readiness/liveness/startup probes, rolling deployment, resource requests/limits, dependency degradation, configuration, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API được deploy lên Kubernetes với 6 replicas. API dùng SQL Server và một external payment provider.

Yêu cầu:

- rolling deployment không được làm mất capacity đáng kể;
- pod chưa sẵn sàng không được nhận traffic;
- temporary SQL slowdown không nên tự động biến thành hàng loạt process restarts;
- application có thể mất 25–40 giây để warm up sau deploy;
- nếu process deadlock/hang thật sự, platform cần restart pod;
- service có SLO p95 < 500 ms cho phần lớn API;
- operations muốn phân biệt “process sống”, “pod có thể nhận traffic” và “dependency đang degraded”.

Trong incident gần đây, SQL latency tăng khoảng một phút. Sau đó nhiều pods liên tục restart, số ready replicas giảm mạnh và traffic dồn lên số pod còn lại. Team cho rằng Kubernetes đã “phát hiện database lỗi và tự heal đúng như thiết kế”.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
    spec:
      containers:
        - name: orders-api
          image: registry.example.com/orders-api:latest
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Orders
              value: "Server=sql-prod;Database=Orders;User Id=orders;Password=ProdPassword123!"
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
```

Health endpoint hiện tại đánh dấu unhealthy nếu SQL hoặc payment provider không phản hồi trong 1 giây.

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness/deployment trong manifest và health-check semantics.
2. Xác định security, reliability, availability và operability concerns.
3. Giải thích production impact trong startup, rollout và dependency slowdown.
4. Ưu tiên findings theo severity.
5. Đề xuất manifest/health-check design đã sửa.
6. Giải thích cách test rollout, probe failure, dependency degradation và resource pressure.
7. Đề xuất production telemetry để chứng minh workload ổn định.

## Câu hỏi gợi mở

1. Liveness probe và readiness probe có nên hỏi cùng một câu hỏi về SQL/payment dependency hay không?
2. Nếu database chậm nhưng process hoàn toàn khỏe, restart process giải quyết được root cause nào?
3. Application warm up 25–40 giây nhưng probe bắt đầu sau 5 giây thì rollout có thể diễn ra thế nào?
4. `:latest` ảnh hưởng gì đến artifact traceability và rollback?
5. Credentials đang nằm ở đâu và ai có thể đọc manifest/repository/deployment history?

## Gợi ý

### Gợi ý 1

Primary risk là **dùng dependency-aware health check cho liveness**, biến dependency degradation thành process restart loop và làm incident khuếch đại.

### Gợi ý 2

Hãy tách ba câu hỏi: process đã khởi động xong chưa, process còn sống không, và pod có đủ điều kiện nhận traffic không.

## Dừng lại và tự review

---

## Kết quả code review tham khảo

### Critical — Secret được hard-code trực tiếp trong Deployment manifest

**Vấn đề:**  
SQL username/password nằm trong plaintext `env.value`.

**Tại sao xảy ra:**  
Manifest thường đi qua Git, CI/CD logs, deployment history và có thể đọc được bởi nhiều principals hơn database secret cần thiết.

**Ảnh hưởng production:**  
Credential exposure có thể dẫn tới unauthorized database access và làm rotation/audit khó khăn.

**Cách sửa:**  
Không commit raw secret. Dùng Kubernetes Secret được provision qua approved secret-management path, hoặc tốt hơn là workload identity/Managed Identity khi platform/database hỗ trợ. Áp dụng least privilege và rotation.

### High — Liveness phụ thuộc vào SQL/payment health gây restart storm

**Vấn đề:**  
`livenessProbe` gọi `/health`, endpoint lại fail khi SQL hoặc payment provider chậm/lỗi.

**Tại sao xảy ra:**  
Liveness đang kiểm tra dependency availability thay vì process viability.

**Ảnh hưởng production:**  
Một dependency incident có thể khiến toàn bộ healthy processes bị restart. Startup lại tạo thêm load, giảm ready capacity và khuếch đại outage.

**Cách sửa:**  
Liveness chỉ nên phản ánh process có còn có khả năng tiếp tục chạy hay không. Dependency checks phù hợp hơn với readiness/degraded telemetry tùy semantics; không restart chỉ vì SQL chậm tạm thời.

### High — Không có startup probe dù application warm up lâu

**Vấn đề:**  
Liveness/readiness bắt đầu sau 5 giây trong khi startup có thể mất 25–40 giây.

**Tại sao xảy ra:**  
`initialDelaySeconds` không mô hình hóa tốt startup window dài/biến động; liveness có thể kill container trước khi startup hợp lệ hoàn tất.

**Ảnh hưởng production:**  
Pods có thể rơi vào restart loop trong rollout hoặc dưới cold-start pressure.

**Cách sửa:**  
Dùng `startupProbe` với failure budget đủ cho realistic startup time. Trong thời gian startup probe chưa succeed, liveness/readiness behavior cần được cấu hình phù hợp.

### High — Readiness semantics quá nhạy với dependency timeout ngắn

**Vấn đề:**  
Endpoint fail nếu SQL/payment không phản hồi trong 1 giây; probe timeout 2 giây và chỉ cần hai failures liên tiếp để unready.

**Tại sao xảy ra:**  
Một transient latency spike có thể loại nhiều pods khỏi load balancer cùng lúc dù chúng vẫn có thể phục vụ phần lớn endpoints hoặc degrade gracefully.

**Ảnh hưởng production:**  
Traffic dồn lên replicas còn ready, tăng latency rồi tạo positive feedback loop.

**Cách sửa:**  
Define readiness dựa trên khả năng phục vụ traffic thực tế. Nếu mọi request bắt buộc SQL thì SQL availability có thể thuộc readiness, nhưng thresholds phải dựa trên SLO/failure behavior. Optional dependency như payment không nên làm toàn API unready nếu endpoint khác vẫn phục vụ được.

### High — Không khai báo resource requests/limits

**Vấn đề:**  
Container không có CPU/memory requests/limits trong manifest.

**Tại sao xảy ra:**  
Scheduler thiếu capacity signal; workload có thể cạnh tranh tài nguyên không dự đoán được và khó xây HPA/placement hợp lý.

**Ảnh hưởng production:**  
Under node pressure, latency/probe timeout có thể tăng; pod placement và QoS behavior kém predictable.

**Cách sửa:**  
Đặt requests dựa trên measured baseline/load test. Đặt limits khi phù hợp, đặc biệt cẩn thận với CPU throttling và memory OOM; không copy số tùy ý.

### Medium — Image tag `latest` làm artifact không immutable/traceable

**Vấn đề:**  
Deployment tham chiếu mutable tag.

**Tại sao xảy ra:**  
Cùng một manifest có thể resolve tới image khác theo thời điểm/cache/pull behavior.

**Ảnh hưởng production:**  
Khó xác định pod đang chạy artifact nào, rollback/reproduce incident kém tin cậy.

**Cách sửa:**  
Dùng immutable version tag và lý tưởng pin digest trong controlled deployment pipeline.

### Medium — RollingUpdate không có explicit availability policy

**Vấn đề:**  
Không thể hiện `maxUnavailable`/`maxSurge` phù hợp với capacity requirement.

**Tại sao xảy ra:**  
Default có thể không khớp workload/SLO; readiness instability trong rollout có thể làm capacity giảm bất ngờ.

**Ảnh hưởng production:**  
Deployment dưới load có thể làm traffic tập trung lên ít pods hơn dự kiến.

**Cách sửa:**  
Chọn surge/unavailable budget dựa trên headroom, startup time và SLO; kết hợp readiness ổn định và `minReadySeconds` khi cần.

### Medium — Không có graceful termination configuration rõ

**Vấn đề:**  
Manifest không thể hiện shutdown budget hoặc lifecycle behavior phù hợp request duration.

**Tại sao xảy ra:**  
Trong rollout, pod có thể bị terminate trong khi request/in-flight work chưa drain xong nếu application/platform behavior không đồng bộ.

**Ảnh hưởng production:**  
Tăng aborted requests và retry spikes trong deployment.

**Cách sửa:**  
Đảm bảo ASP.NET Core graceful shutdown, `terminationGracePeriodSeconds` phù hợp và readiness/draining strategy đã test. Không dùng sleep hook mù nếu load balancer propagation đã được giải quyết theo cách khác.

### Medium — Một `/health` endpoint không cung cấp đủ operational semantics

**Vấn đề:**  
Cả startup/readiness/liveness dự kiến dùng cùng endpoint với cùng tập checks.

**Tại sao xảy ra:**  
Ba probe có mục tiêu khác nhau nhưng bị collapse thành một boolean.

**Ảnh hưởng production:**  
Kubernetes không phân biệt “đang startup”, “process hỏng” và “dependency degraded”, khiến remediation sai loại.

**Cách sửa:**  
Tách endpoints/tags, ví dụ `/health/startup`, `/health/live`, `/health/ready`, với checks được phân loại có chủ đích.

### Low — Manifest thiếu metadata hỗ trợ traceability

**Vấn đề:**  
Không có version/commit labels/annotations hữu ích cho operations.

**Tại sao xảy ra:**  
Artifact/deployment identity không được đưa vào telemetry/deployment metadata.

**Ảnh hưởng production:**  
Incident triage mất thời gian để nối pod với release/commit.

**Cách sửa:**  
Thêm immutable release identifier, commit SHA/build ID vào image metadata/labels và log startup.

## Phiên bản đề xuất

Ví dụ dưới đây minh họa probe separation và deployment safety. Giá trị resource/probe thực tế phải được hiệu chỉnh bằng startup/load measurements.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
spec:
  replicas: 6
  minReadySeconds: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 2
  selector:
    matchLabels:
      app: orders-api
  template:
    metadata:
      labels:
        app: orders-api
        app.kubernetes.io/version: "2026.09.11.1"
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: orders-api
          image: registry.example.com/orders-api@sha256:<immutable-digest>
          ports:
            - containerPort: 8080
          env:
            - name: ConnectionStrings__Orders
              valueFrom:
                secretKeyRef:
                  name: orders-api-secrets
                  key: orders-connection-string
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              memory: "768Mi"
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3
```

Trong ASP.NET Core, health checks nên được phân nhóm theo semantics. Ví dụ:

- **startup:** initialization bắt buộc đã hoàn tất;
- **live:** process/event loop/runtime vẫn có khả năng tiếp tục chạy; không fail chỉ vì downstream dependency tạm unavailable;
- **ready:** application có thể nhận traffic theo contract. Chỉ include dependency thực sự bắt buộc cho hầu hết request paths;
- **dependency health:** SQL/payment latency/error rate vẫn cần được expose qua metrics/traces/dashboard ngay cả khi không trực tiếp điều khiển liveness.

Nếu payment chỉ được dùng ở một vài endpoints, payment outage nên được xử lý ở application layer bằng timeout/circuit breaker/degraded response phù hợp thay vì loại toàn pod khỏi service.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tránh dùng restart như một generic response cho downstream failure. Kubernetes chỉ restart pod khi process thực sự unhealthy; readiness kiểm soát traffic admission; startup probe bảo vệ application trong warm-up window.

`maxUnavailable: 0` là một lựa chọn minh họa cho requirement giữ capacity trong rollout, nhưng cần đủ cluster capacity cho surge pods. Nếu cluster không có headroom hoặc startup rất đắt, con số khác có thể hợp lý hơn.

Resource requests/limits phải xuất phát từ measurement. Memory limit tạo hard boundary hữu ích, nhưng CPU limit có thể gây throttling nên không nên thêm tùy ý chỉ để manifest “đầy đủ”.

## Trade-offs

- Readiness càng strict càng giảm khả năng gửi traffic tới degraded pod, nhưng có thể gây capacity collapse khi shared dependency lỗi.
- Liveness càng aggressive càng phát hiện hang nhanh, nhưng false positive gây restart storm.
- `maxUnavailable: 0` giữ serving capacity nhưng yêu cầu extra scheduler capacity trong rollout.
- External secret manager/workload identity an toàn hơn plaintext secret nhưng tăng integration/operational complexity.
- Tách health endpoints tăng clarity nhưng đòi hỏi team định nghĩa rõ semantics và ownership của từng check.

## Cách kiểm thử

1. **Startup/deployment validation:** cold-start application 25–40+ giây; xác minh startup probe không kill pod và pod chỉ nhận traffic sau khi ready.
2. **Dependency failure test:** làm SQL chậm/unavailable trong khoảng ngắn; xác minh liveness vẫn healthy, restart count không tăng và readiness/degraded behavior đúng contract.
3. **Load + rollout test:** deploy version mới khi service đang gần expected peak load; đo ready replicas, p95/p99, error rate và capacity trong toàn rollout.
4. **Resource-pressure test:** tạo CPU/memory pressure có kiểm soát; quan sát throttling/OOM/probe latency và hiệu chỉnh requests/limits bằng dữ liệu.
5. **Security/deployment test:** xác minh manifest/repository không chứa raw credential, service account/secret access theo least privilege và release có thể trace về immutable image digest.

## Quan sát trong production

Theo dõi:

- ready/desired replicas, pod restart count và restart reason;
- startup duration và probe success/failure theo loại;
- deployment duration, unavailable replicas và rollout failures;
- CPU usage/throttling, memory working set/OOM kills;
- request rate, p95/p99 latency và 5xx theo pod/release;
- SQL/payment dependency latency/error rate qua Application Insights/OpenTelemetry;
- correlation giữa dependency slowdown → readiness changes → restart count;
- alert riêng cho dependency degradation và process liveness để tránh conflating hai incident classes.

## Câu hỏi phỏng vấn mở rộng

1. Trong trường hợp SQL là dependency bắt buộc cho 100% endpoint, bạn sẽ thiết kế readiness thế nào để tránh capacity collapse?
2. Khi nào liveness probe không nên gọi HTTP endpoint trong application?
3. Nếu cluster không đủ capacity cho `maxSurge: 2`, bạn sẽ thay đổi rollout strategy và SLO trade-off ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Large-file I/O nên được thiết kế theo streaming/backpressure thay vì materialize toàn bộ payload trong memory.
- Security boundary phải được kiểm tra trước performance optimization; resource ID không thay thế authorization.
- Cancellation cần propagate end-to-end nhưng không đồng nghĩa downstream side effect tự rollback.
- Kubernetes startup, liveness và readiness trả lời ba câu hỏi vận hành khác nhau; dùng một dependency-aware endpoint cho tất cả có thể khuếch đại outage.
- Deployment safety cần artifact immutability, secret management, resource measurement, rollout budget và telemetry chứ không chỉ một manifest chạy được.

## Mẫu tư duy cần nhớ

- Ưu tiên invariant/security correctness trước micro-optimization.
- Với tải lớn, tìm memory/load amplification theo `payload × concurrency`.
- Tách process health khỏi dependency health và traffic readiness.
- Đừng dùng restart như generic recovery cho external dependency failure.
- Quan sát và load-test failure path trước khi tăng tài nguyên hoặc thêm hạ tầng.
