# Code Review Challenge 1 — Hangfire: thanh toán bị xử lý hai lần khi retry

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một ASP.NET Core service dùng Hangfire để xử lý hoàn tiền. API tạo `RefundRequest`, sau đó enqueue job gọi payment provider và cập nhật database. Production đôi lúc xuất hiện hai giao dịch hoàn tiền cho cùng một request, chủ yếu khi provider phản hồi chậm hoặc worker restart. Hệ thống chạy nhiều Hangfire workers trên nhiều instance. Provider không đảm bảo request của client chỉ được xử lý một lần nếu client retry.

## Đoạn code cần review

```csharp
public sealed class RefundJob
{
    private readonly AppDbContext _db;
    private readonly HttpClient _http;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(AppDbContext db, HttpClient http, ILogger<RefundJob> logger)
    {
        _db = db;
        _http = http;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid refundId)
    {
        var refund = await _db.Refunds.FirstOrDefaultAsync(x => x.Id == refundId);
        if (refund == null || refund.Status == "Completed")
            return;

        refund.Status = "Processing";
        await _db.SaveChangesAsync();

        var response = await _http.PostAsJsonAsync("/refunds", new
        {
            refund.PaymentId,
            refund.Amount
        });

        response.EnsureSuccessStatusCode();

        var result = await response.Content.ReadFromJsonAsync<RefundResponse>();

        refund.Status = "Completed";
        refund.ProviderRefundId = result!.Id;
        refund.CompletedAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Refund {RefundId} completed as {ProviderRefundId}",
            refund.Id,
            refund.ProviderRefundId);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Tìm rủi ro concurrency, retry và failure handling.
3. Giải thích vì sao duplicate refund chỉ xuất hiện trong một số failure window.
4. Ưu tiên vấn đề theo mức độ ảnh hưởng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách test retry/concurrency.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai workers có thể cùng đọc `Pending` không?
- Điều gì xảy ra nếu provider đã hoàn tiền nhưng process chết trước `SaveChangesAsync()` cuối?
- `Processing` có thực sự là distributed lock không?
- Retry một side effect bên ngoài cần điều kiện gì để an toàn?
- Cancellation và timeout nên được xử lý ra sao?

## Kết quả code review tham khảo

### 1. External refund không idempotent — Critical

**Problem:** Retry có thể gửi lại cùng refund.  
**Why:** Sau khi provider thành công nhưng trước khi local DB ghi `Completed`, worker có thể crash; Hangfire retry sẽ gọi provider lần nữa.  
**Impact:** Hoàn tiền hai lần, tổn thất tài chính.  
**Fix:** Dùng stable idempotency key nếu provider hỗ trợ; nếu không, cần provider lookup/reconciliation hoặc một protocol nghiệp vụ có khả năng xác nhận trạng thái trước retry.

### 2. Check-then-act race giữa workers — Critical

**Problem:** Hai workers đều có thể đọc trạng thái chưa hoàn tất rồi cùng gọi provider.  
**Why:** Read và transition sang `Processing` không phải một conditional atomic operation.  
**Impact:** Duplicate side effect.  
**Fix:** Claim work bằng optimistic concurrency/conditional update, unique constraint hoặc cơ chế distributed coordination phù hợp; database phải quyết định worker nào sở hữu attempt.

### 3. `Processing` có thể bị kẹt — High

Worker chết sau lần save đầu để lại trạng thái `Processing` nhưng code hiện tại vẫn cho lần sau tiếp tục gọi provider. Cần attempt metadata, lease/timeout hoặc reconciliation state rõ ràng.

### 4. Không truyền `CancellationToken` — High

Database và HTTP operation không nhận cancellation. Shutdown hoặc timeout có thể kéo dài và làm failure semantics khó kiểm soát. Job cần token phù hợp với execution model và HTTP timeout policy.

### 5. Không phân loại lỗi retryable/non-retryable — High

`EnsureSuccessStatusCode()` biến mọi non-success thành exception. Retry 400 business validation khác hoàn toàn retry 503/timeout. Cần error taxonomy và retry policy có giới hạn/jitter.

### 6. Không lưu attempt/audit trước external call — Medium

Khó xác định provider đã nhận request nào, attempt nào thất bại và cần reconcile gì. Lưu operation/idempotency key và audit state trước call.

### 7. Null contract từ provider được xử lý bằng `!` — Medium

Response 2xx nhưng payload invalid/null có thể gây exception sau external side effect. Cần validate response schema và chuyển sang trạng thái cần reconciliation thay vì blind retry.

### 8. Observability thiếu correlation — Medium

Log chỉ xuất hiện sau thành công. Cần `refundId`, operation key, attempt, provider request correlation, duration và outcome; không log secret/payment data nhạy cảm.

## Phiên bản code đề xuất

```csharp
public sealed class RefundJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly PaymentClient _payments;
    private readonly ILogger<RefundJob> _logger;

    public RefundJob(
        IDbContextFactory<AppDbContext> dbFactory,
        PaymentClient payments,
        ILogger<RefundJob> logger)
    {
        _dbFactory = dbFactory;
        _payments = payments;
        _logger = logger;
    }

    public async Task ExecuteAsync(Guid refundId, CancellationToken ct)
    {
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var refund = await db.Refunds.SingleOrDefaultAsync(x => x.Id == refundId, ct);
        if (refund is null || refund.Status == RefundStatus.Completed)
            return;

        var operationKey = $"refund:{refund.Id:N}";

        if (refund.Status == RefundStatus.Pending)
        {
            refund.Status = RefundStatus.Processing;
            refund.OperationKey = operationKey;
            refund.AttemptCount++;

            try
            {
                await db.SaveChangesAsync(ct); // RowVersion/optimistic concurrency configured
            }
            catch (DbUpdateConcurrencyException)
            {
                return; // another worker claimed it
            }
        }

        PaymentRefundResult result;
        try
        {
            result = await _payments.RefundAsync(
                refund.PaymentId,
                refund.Amount,
                operationKey,
                ct);
        }
        catch (PaymentOutcomeUnknownException ex)
        {
            refund.Status = RefundStatus.ReconciliationRequired;
            refund.LastError = ex.Code;
            await db.SaveChangesAsync(ct);
            throw;
        }

        refund.Status = RefundStatus.Completed;
        refund.ProviderRefundId = result.ProviderRefundId;
        refund.CompletedAt = DateTimeOffset.UtcNow;
        await db.SaveChangesAsync(ct);

        _logger.LogInformation(
            "Refund completed. RefundId={RefundId} OperationKey={OperationKey}",
            refund.Id, operationKey);
    }
}
```

Giả định trong phiên bản trên: entity được cấu hình optimistic concurrency (`RowVersion` hoặc concurrency token), và `PaymentClient` thực sự truyền stable idempotency key tới provider. Nếu provider không hỗ trợ idempotency thì `ReconciliationRequired` phải được xử lý bằng API tra cứu hoặc quy trình đối soát; chỉ thêm retry không giải quyết được exactly-once side effect.

## Trade-offs

Optimistic concurrency đơn giản và phù hợp khi contention thấp; conditional `UPDATE ... WHERE Status = Pending` có thể rõ ràng hơn cho việc claim job. Distributed lock có thể hữu ích nhưng không thay thế idempotency tại external boundary. Outbox giải quyết đáng tin cậy việc publish message từ DB nhưng tự nó không khiến payment provider trở thành exactly-once.

## Cách kiểm thử

1. Chạy 20 executions đồng thời cho cùng `refundId`, xác nhận chỉ một logical refund được provider chấp nhận.
2. Fault injection: provider thành công rồi process crash trước local completion; retry vẫn không tạo refund thứ hai.
3. Provider trả 503/timeout/400 và xác minh retry policy khác nhau.
4. Response 2xx nhưng body invalid: record chuyển sang trạng thái có thể điều tra/reconcile.
5. Worker cancellation giữa các phase và restart: state vẫn recoverable.

## Quan sát trong production

Theo dõi `refund_attempt_total`, duplicate/idempotency replay count, reconciliation backlog, provider latency/error rate, Hangfire retry count và tuổi của các refund ở `Processing`. Trace nên nối job → DB claim → HTTP provider bằng correlation/operation key. Alert khi `Processing` quá SLA hoặc reconciliation backlog tăng.

## Câu hỏi phỏng vấn mở rộng

1. Outbox pattern giúp phần nào và không giúp phần nào trong bài toán này?
2. Nếu provider không có idempotency API cũng không có lookup API, bạn thay đổi business workflow thế nào?
3. Tại sao distributed lock vẫn không loại bỏ failure window sau external success?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log: authorization và SQL injection

**Chủ đề:** Authorization, input validation, SQL correctness, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–8 vấn đề

## Bối cảnh

Portal nội bộ cho phép support staff tìm audit log của từng tenant. Endpoint nhận `tenantId`, từ khóa và cột sort. Một security review phát hiện user thuộc tenant A đôi khi có thể truy vấn dữ liệu tenant B nếu biết ID; database cũng có spike CPU khi người dùng tìm chuỗi phổ biến. Audit message có thể chứa email, object IDs và một số metadata nghiệp vụ.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ILogger<AuditController> _logger;

    public AuditController(AppDbContext db, ILogger<AuditController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet("search")]
    public async Task<IActionResult> Search(
        Guid tenantId,
        string? keyword,
        string sort = "CreatedAt DESC")
    {
        var sql = $@"
            SELECT *
            FROM AuditLogs
            WHERE TenantId = '{tenantId}'
              AND Message LIKE '%{keyword}%'
            ORDER BY {sort}";

        _logger.LogInformation("Audit search SQL: {Sql}", sql);

        var rows = await _db.AuditLogs
            .FromSqlRaw(sql)
            .Take(5000)
            .ToListAsync();

        return Ok(rows);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/security/performance problems.
2. Giải thích production impact.
3. Ưu tiên remediation.
4. Đề xuất implementation sửa lỗi.
5. Nêu cách kiểm thử authorization và injection.
6. Đề xuất telemetry an toàn.

## Câu hỏi gợi mở

- `[Authorize]` chứng minh điều gì và không chứng minh điều gì?
- Những input nào đang đi trực tiếp vào SQL syntax?
- `Take(5000)` có bảo đảm database chỉ xử lý ít dữ liệu không?
- Response có nên trả nguyên entity audit không?
- Log câu SQL hoàn chỉnh có thể tiết lộ gì?

## Gợi ý

### Gợi ý 1

Authentication không đồng nghĩa với tenant authorization.

### Gợi ý 2

Parameterize values, allowlist identifiers/sort options, enforce tenant scope từ trusted identity và giới hạn projection/pagination.

## Kết quả code review tham khảo

### 1. Broken tenant-level authorization — Critical

**Problem:** Caller tự cung cấp `tenantId`; `[Authorize]` chỉ yêu cầu authenticated identity.  
**Impact:** IDOR/BOLA-style cross-tenant data exposure.  
**Fix:** Derive tenant scope từ trusted claims/session hoặc kiểm tra explicit policy/membership trước query. Với privileged support cross-tenant access, dùng policy riêng và audit access.

### 2. SQL injection qua `keyword` — Critical

String interpolation đưa user input vào raw SQL. Dấu quote/payload có thể thay đổi câu query. Dùng LINQ parameterization hoặc parameterized SQL.

### 3. SQL injection qua `sort` — Critical

Column/direction là SQL syntax nên không thể xử lý như value parameter thông thường. Dùng allowlist enum/map (`created_desc`, `created_asc`, ...), tuyệt đối không nối raw user string.

### 4. Sensitive query được ghi vào application log — High

Full SQL chứa keyword và tenant identifier, có thể đưa dữ liệu nhạy cảm hoặc attacker payload vào log. Log structured metadata cần thiết, không log raw query/user content mặc định.

### 5. `SELECT *` trả quá nhiều dữ liệu — High

Audit entity có thể chứa fields không dành cho caller. Dùng explicit DTO projection và data minimization.

### 6. Search pattern `%keyword%` có thể rất đắt — Medium

Leading wildcard thường làm B-tree index thông thường không giúp được kiểu search này. Cần giới hạn keyword, pagination và cân nhắc full-text/search capability phù hợp theo DB/workload.

### 7. Limit lớn và không có pagination contract — Medium

5.000 records gây allocation, serialization và network cost. Dùng bounded page size/cursor hoặc keyset pagination.

### 8. Không truyền cancellation — Low/Medium

Client disconnect vẫn có thể để query chạy. Truyền `HttpContext.RequestAborted` xuống EF Core.

## Phiên bản code đề xuất

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;
    private readonly ITenantContext _tenant;

    public AuditController(AppDbContext db, ITenantContext tenant)
    {
        _db = db;
        _tenant = tenant;
    }

    [HttpGet("search")]
    public async Task<ActionResult<IReadOnlyList<AuditDto>>> Search(
        [FromQuery] string? keyword,
        [FromQuery] AuditSort sort = AuditSort.CreatedDesc,
        [FromQuery] int pageSize = 50,
        CancellationToken ct = default)
    {
        pageSize = Math.Clamp(pageSize, 1, 100);
        var tenantId = _tenant.RequiredTenantId;

        IQueryable<AuditLog> query = _db.AuditLogs
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            var normalized = keyword.Trim();
            if (normalized.Length > 100)
                return BadRequest("Keyword is too long.");

            query = query.Where(x => x.Message.Contains(normalized));
        }

        query = sort switch
        {
            AuditSort.CreatedAsc => query.OrderBy(x => x.CreatedAt).ThenBy(x => x.Id),
            _ => query.OrderByDescending(x => x.CreatedAt).ThenByDescending(x => x.Id)
        };

        var rows = await query
            .Take(pageSize)
            .Select(x => new AuditDto(x.Id, x.CreatedAt, x.Action, x.Message))
            .ToListAsync(ct);

        return Ok(rows);
    }
}

public enum AuditSort { CreatedDesc, CreatedAsc }
public sealed record AuditDto(Guid Id, DateTimeOffset CreatedAt, string Action, string Message);
```

`Contains` trong LINQ tránh raw SQL injection vì EF Core tạo parameter cho value, nhưng performance/search semantics vẫn phụ thuộc provider và database. Nếu `Message` chứa dữ liệu không được phép expose thì DTO cũng phải redact hoặc loại bỏ field đó; projection không tự động biến dữ liệu thành an toàn.

## Trade-offs

Tenant query filter ở EF Core có thể giảm nguy cơ quên filter nhưng cần thiết kế cẩn thận cho admin/support workflows. Explicit tenant predicates dễ nhìn thấy hơn nhưng phụ thuộc discipline. Full-text search tăng capability/performance cho search lớn nhưng thêm vận hành và semantics riêng. Keyset pagination tốt cho feed ổn định nhưng kém thuận tiện nếu UI cần nhảy tới page N.

## Cách kiểm thử

1. Security integration test: identity tenant A không thể lấy record tenant B dù sửa query string/path/body.
2. Injection payload trong keyword và sort không thay đổi query structure; invalid sort bị reject.
3. Load test với keyword phổ biến và dataset lớn, kiểm tra execution plan, latency và DB CPU.
4. Response contract test bảo đảm fields nhạy cảm không xuất hiện.
5. Cancel request khi query đang chạy và xác nhận cancellation được propagate.

## Quan sát trong production

Theo dõi request latency theo route, DB query duration, rows returned, rejected authorization count, page-size distribution và slow-query plans. Security audit nên ghi actor, tenant scope, action, timestamp và outcome nhưng tránh raw keyword/message nếu không thật sự cần. Alert cross-tenant authorization failures bất thường và latency/DB CPU tăng mạnh.

## Câu hỏi phỏng vấn mở rộng

1. Global query filter cho multi-tenancy có những failure mode nào?
2. Khi nào Row-Level Security ở database đáng cân nhắc?
3. Nếu support admin thực sự cần cross-tenant search, bạn thiết kế authorization và audit trail ra sao?
