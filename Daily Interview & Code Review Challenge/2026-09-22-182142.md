# Câu 1 — React UI hiển thị kết quả tìm kiếm cũ dù request mới đã hoàn tất

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** JavaScript event loop, Promise, React hooks, request cancellation, race conditions, browser networking, TypeScript, API integration

## Bối cảnh

Một React + TypeScript frontend gọi ASP.NET Core search API khi người dùng thay đổi filter. Team đã debounce input 250 ms nên tin rằng duplicate/out-of-order requests không còn đáng lo.

```tsx
useEffect(() => {
  if (!query.trim()) {
    setItems([]);
    return;
  }

  setLoading(true);

  fetch(`/api/search?q=${encodeURIComponent(query)}`)
    .then(r => r.json())
    .then(data => {
      setItems(data.items);
      setLoading(false);
    })
    .catch(() => setLoading(false));
}, [query]);
```

Trong production, khi user gõ nhanh hoặc mạng mobile dao động, đôi lúc UI hiển thị kết quả của query cũ. Network tab cho thấy request cho `laptop` được gửi trước request cho `laptop stand`, nhưng response của request đầu tiên về sau response thứ hai.

API không có server-side session state. Chưa biết component có bị unmount/remount trong navigation hay không, error handling hiện tại có phân biệt cancellation không, và product muốn giữ previous results trong lúc request mới chạy hay clear ngay.

## Câu hỏi chính

Hãy giải thích chính xác vì sao debounce không loại bỏ race này, Promise completion và React state update dẫn đến stale UI như thế nào, assumption nào về request ordering là sai, và bạn sẽ thiết kế request lifecycle để chỉ response còn hợp lệ mới được commit vào UI state.

## Câu hỏi làm rõ nên cân nhắc

1. Requirement khi query thay đổi là giữ kết quả cũ trong lúc loading hay clear ngay?
2. Có nhiều dependencies ngoài `query` ảnh hưởng search như locale, sort hoặc filter không?
3. Search endpoint có hỗ trợ cancellation hiệu quả ở ASP.NET Core và downstream dependencies không?
4. Component có thể unmount/remount hoặc nhiều component cùng chia sẻ search state không?
5. Product có cần caching/deduplication client-side hay chỉ cần correctness trước?

## Gợi ý tư duy

### Gợi ý 1

Debounce kiểm soát thời điểm **bắt đầu** request; nó không đảm bảo thứ tự **hoàn thành** của network operations.

### Gợi ý 2

Hãy xác định response nào còn quyền mutate state tại thời điểm Promise resolve.

### Gợi ý 3

Cancellation giúp giảm công việc thừa, nhưng correctness vẫn nên dựa trên một lifecycle/identity rule rõ ràng thay vì giả định network luôn hủy kịp.

## Cấu trúc trả lời đề xuất

1. Mô tả timeline của hai requests.
2. Giải thích Promise/event-loop completion và state update.
3. Tách debounce khỏi ordering/cancellation semantics.
4. Xác định lifecycle của một search generation.
5. Đề xuất `AbortController` và stale-response guard.
6. Phân tích loading/error state khi request bị supersede.
7. Truyền cancellation xuống backend nếu hữu ích.
8. Test bằng deterministic delayed responses.
9. Quan sát browser/API telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hai HTTP requests độc lập không có guarantee response hoàn thành theo thứ tự gửi.
- Debounce giảm số requests nhưng không serialize hoặc order responses.
- Promise callback của request cũ vẫn có thể chạy sau callback của request mới và ghi đè `items`.
- Cleanup của `useEffect` nên cancel request cũ hoặc đánh dấu generation cũ không còn hợp lệ.
- `AbortController` là cơ chế phù hợp để yêu cầu hủy fetch khi effect bị supersede/unmount.
- Không nên hiển thị cancellation như lỗi người dùng thông thường.
- Correctness nên đảm bảo stale response không commit state kể cả trong trường hợp cancellation không kịp ngăn mọi downstream work.

### Điểm cộng

- Dùng request/generation ID hoặc closure flag để guard state commit.
- Loading state cũng phải gắn với active request; request cũ không được set `loading=false` trong khi request mới còn chạy.
- Backend có thể nhận `HttpContext.RequestAborted`/`CancellationToken`, nhưng cancellation là cooperative và không phải transaction rollback.
- Nếu dùng query library, vẫn cần hiểu cache key, stale policy và cancellation semantics thay vì coi library tự động giải quyết mọi race.
- Test bằng controllable promises/MSW/Playwright để response cũ cố tình về sau.

### Senior+

- Phân biệt UI correctness, resource cancellation và caching thành ba concern khác nhau.
- Thiết kế state machine rõ: idle/loading/success/error cho active generation.
- Nếu nhiều filters tạo search key, generation/cache identity phải đại diện toàn bộ effective request, không chỉ text query.

## Hướng giải quyết tham khảo

Timeline hợp lệ là: effect A gửi query `laptop`; effect B sau đó gửi `laptop stand`; B hoàn tất trước và set đúng kết quả; A hoàn tất sau và callback của A vẫn gọi `setItems`, vì Promise A không biết rằng một effect mới đã supersede nó. Debounce không thay đổi điều đó.

Một implementation đơn giản là tạo `AbortController` cho mỗi effect và cleanup request trước khi effect mới trở thành active:

```tsx
useEffect(() => {
  if (!query.trim()) {
    setItems([]);
    setLoading(false);
    return;
  }

  const controller = new AbortController();
  let active = true;

  setLoading(true);

  (async () => {
    try {
      const response = await fetch(
        `/api/search?q=${encodeURIComponent(query)}`,
        { signal: controller.signal });

      if (!response.ok)
        throw new Error(`HTTP ${response.status}`);

      const data = await response.json();

      if (active)
        setItems(data.items);
    }
    catch (error) {
      if (active && !(error instanceof DOMException && error.name === "AbortError")) {
        // set an error state appropriate for the UI
      }
    }
    finally {
      if (active)
        setLoading(false);
    }
  })();

  return () => {
    active = false;
    controller.abort();
  };
}, [query]);
```

`AbortController` giảm network/client work và có thể propagate cancellation về server nếu connection/request cancellation được framework/downstream code quan sát. `active` guard đảm bảo effect cũ không commit state sau cleanup. Có thể dùng monotonic request ID thay cho boolean khi state orchestration phức tạp hơn.

Nếu search key gồm query + sort + locale + filters, lifecycle phải gắn với toàn bộ key đó. Nếu product muốn giữ previous data khi loading, đó là UX policy riêng; vẫn không được cho stale request overwrite active result.

Verification nên có deterministic test: request A bị delay, request B trả trước, sau đó A trả; final UI phải vẫn là B. Thêm test unmount, cancellation, HTTP error và rapid filter changes. Playwright có thể intercept/route requests để điều khiển thứ tự responses.

Production có thể quan sát search request duration, cancellation rate, error rate, client-side active query/request ID trong debug telemetry phù hợp, và API cancellation/dependency latency. Không log raw search text nếu có privacy concern.

## Mẫu trả lời trong phỏng vấn

“Debounce chỉ giảm tần suất bắt đầu request, không đảm bảo response ordering. Nếu request A gửi trước nhưng chậm hơn B, B có thể set state đúng rồi A resolve sau và overwrite bằng dữ liệu cũ.

Tôi sẽ coi mỗi effect là một search generation. Khi dependency thay đổi, cleanup sẽ abort request cũ và invalidate generation đó. Callback chỉ được commit `items`, `loading` hoặc error nếu generation vẫn active. `AbortController` giúp giảm work, nhưng stale-response guard mới làm lifecycle explicit.

Nếu backend hỗ trợ cancellation, tôi truyền cancellation xuống I/O để tránh làm việc vô ích, nhưng không giả định cancellation là rollback. Tôi sẽ test bằng cách cố tình cho response cũ về sau response mới, cộng thêm unmount/error/cancel cases. Nếu search key có nhiều filters thì identity phải bao gồm toàn bộ effective request.”

## Câu hỏi đào sâu

1. Nếu bỏ `active` guard và chỉ dùng `AbortController`, trong thiết kế production bạn có coi correctness đã đủ mạnh chưa? Vì sao?
2. Nếu dùng React Query/TanStack Query hoặc library tương tự, những assumptions nào về query key, stale data và cancellation vẫn phải review?
3. Nếu ASP.NET Core đã bắt đầu một SQL query khi browser abort request, bạn kỳ vọng cancellation hoạt động thế nào và cần verify gì?

## Lỗi trả lời thường gặp

- Cho rằng debounce đồng nghĩa chỉ có một request đang chạy.
- Chỉ thêm `setTimeout` hoặc tăng debounce interval.
- Abort request nhưng để request cũ thay đổi `loading/error` state không có guard.
- Không cleanup khi component unmount.
- Đổ lỗi cho backend cache dù timeline đã chứng minh client race.

## Thang điểm 0–10

- **0–2:** Không nhận ra out-of-order completion.
- **3–4:** Nhận ra race nhưng chỉ tăng debounce.
- **5–6:** Dùng cancellation/cleanup đúng và guard stale state.
- **7–8:** Xử lý loading/error, backend cancellation và deterministic tests.
- **9–10:** Mô hình hóa lifecycle/state machine rõ ràng, phân biệt correctness/cancellation/cache và giải thích được failure semantics end-to-end.

# Câu 2 — Kubernetes pods restart liên tục sau release nhưng CPU và memory trung bình vẫn thấp

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–30 phút  
**Kỹ năng được đánh giá:** Kubernetes, ASP.NET Core, liveness/readiness, resource limits, container lifecycle, deployment, Application Insights, production troubleshooting

## Bối cảnh

Một ASP.NET Core API vừa được chuyển từ Azure App Service sang Kubernetes. Deployment có 6 replicas. Sau release mới, users thấy burst `5xx` trong vài phút rồi tự hồi phục. Dashboard CPU trung bình khoảng 35%, memory trung bình khoảng 55% limit, nhưng một số pods có restart count tăng nhanh.

Deployment rút gọn:

```yaml
containers:
  - name: api
    image: company/api:2026.09.22
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "1"
        memory: "512Mi"
    livenessProbe:
      httpGet:
        path: /health
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /health
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2
```

`/health` hiện kiểm tra process, SQL Server, Redis và một third-party pricing API trong cùng endpoint. Release mới thêm một startup cache warm-up và tăng traffic tới pricing API. Operations thấy xen kẽ events liên quan probe failures và container restarts nhưng chưa xác định causal chain.

Chưa biết container termination reason, pod-level peak memory, GC behavior, startup duration, pricing API latency, rollout settings hay endpoint nào thực sự trả 5xx.

## Câu hỏi chính

Bạn sẽ xử lý incident theo trình tự nào để phân biệt OOM/resource issue, liveness probe sai semantics, readiness failure, startup delay, external dependency degradation và application crash? Hãy giải thích cách stabilize production trước, thu thập evidence, xác minh root cause và thiết kế probes/rollout/telemetry an toàn hơn.

## Câu hỏi làm rõ nên cân nhắc

1. `kubectl describe pod`/container status cho biết last termination reason và exit code gì?
2. Pod restart xảy ra sau liveness failures, OOM kill hay application exit?
3. `/health` latency/failure đang do SQL, Redis hay pricing API; từng dependency có critical cho process sống hay chỉ cho một feature?
4. Startup warm-up mất bao lâu ở p95/p99 và probes bắt đầu kiểm tra từ thời điểm nào?
5. Rolling update cho phép bao nhiêu unavailable/surge pods và traffic chỉ route sau readiness hay không?

## Gợi ý tư duy

### Gợi ý 1

Average CPU/memory của deployment không loại trừ per-pod spike, OOM hoặc một subset pods bị lỗi.

### Gợi ý 2

Hỏi liveness và readiness đang trả lời hai câu hỏi khác nhau nào. Một third-party API chậm có nhất thiết nghĩa process phải bị kill không?

### Gợi ý 3

Pod restart là evidence quan trọng nhưng chưa phải root cause. Xác định ai yêu cầu termination và điều gì xảy ra ngay trước đó.

## Cấu trúc trả lời đề xuất

1. Đánh giá user impact/blast radius.
2. Pause rollout và giữ capacity khỏe.
3. Thu termination/probe/application evidence theo từng pod.
4. Xây timeline pod lifecycle.
5. So sánh các hypotheses.
6. Xác minh bằng metrics/logs/events/traces.
7. Hotfix hoặc rollback có kiểm soát.
8. Thiết kế lại health semantics.
9. Load/failure-test trước rollout.
10. Thêm alerts và deployment gates.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận từ deployment-level averages; xem per-pod/container peak, working set và termination reason.
- Kubernetes restart có thể do liveness failure, OOM kill hoặc process exit; phải xác minh status/events.
- Readiness nên quyết định pod có nhận traffic; liveness nên trả lời process có cần restart để recover hay không.
- Không nên để một non-critical third-party dependency failure trực tiếp làm liveness fail và tạo restart storm.
- Startup/warm-up cần được phản ánh bằng startup/readiness strategy phù hợp; probes không nên kill app chỉ vì nó chưa warm xong nếu app đang tiến triển bình thường.
- Stabilization có thể pause rollout, rollback compatible image/config, scale healthy capacity hoặc tạm sửa probe/config tùy evidence.
- Health endpoint phải có bounded dependency checks; chính health check không được tạo thêm dependency pressure lớn.

### Điểm cộng

- Correlate pod UID/name, restart count, termination timestamp, probe events, application logs và Application Insights trace/dependency telemetry.
- Nếu pricing API degraded, readiness semantics phụ thuộc API có thể phục vụ meaningful traffic ở degraded mode hay không.
- OOM analysis cần peak/RSS/container memory và allocation/GC evidence; average memory không đủ.
- CPU limit có thể tạo throttling dù average nhìn thấp; cần per-container time-series.
- Rollout nên có readiness gate và capacity budget phù hợp; tránh quá nhiều pods unavailable cùng lúc.
- Dependency-specific health nên tách diagnostic detail khỏi liveness decision.

### Senior+

- Phân biệt **process health**, **traffic eligibility**, **dependency degradation** và **startup completion** thành các signals riêng.
- Thiết kế graceful shutdown/termination để in-flight requests không bị cắt đột ngột.
- Chứng minh fix bằng failure injection: pricing API timeout, Redis outage, slow startup, memory pressure.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng impact và rollout state. Nếu release còn rollout, pause nó. Tôi xác định pods khỏe và giữ đủ capacity; không restart hàng loạt vì sẽ xóa evidence và tăng blast radius. Nếu image trước tương thích với schema/config hiện tại và evidence chỉ vào regression mới, rollback là một stabilization option.

Sau đó dựng timeline từng pod từ container status/events: creation, readiness transitions, liveness failures, termination reason/exit code, restart, first-ready time. Correlate với application logs, dependency traces, pricing API latency và resource metrics.

Các hypotheses:

- **OOM:** termination reason/exit evidence + per-pod memory spike; xem allocations/GC nếu cần.
- **Liveness-induced restart:** repeated `/health` timeout/failure ngay trước termination; xác định dependency nào kéo health xuống.
- **Startup race:** warm-up chưa xong nhưng liveness bắt đầu quá sớm; startup duration tương quan restart loop.
- **Application crash:** process exit/unhandled exception trước restart, không phải kubelet probe kill.
- **Dependency degradation:** pricing API latency tăng làm `/health` timeout; nếu endpoint dùng chung cho liveness thì kubelet có thể biến external outage thành local restart storm.
- **CPU throttling:** xem per-container throttling/time series thay vì average deployment CPU.

Tôi sẽ tách semantics. Liveness nên rất nông: process/app có bị stuck theo một condition mà restart thực sự giúp không. Readiness kiểm tra app có thể nhận traffic hữu ích không, nhưng cũng không nên mù quáng phụ thuộc mọi external service. Nếu pricing chỉ ảnh hưởng một feature và API có fallback/degraded behavior, pricing outage không nhất thiết làm toàn pod unready. Nếu SQL là dependency bắt buộc cho mọi request, readiness có thể phản ánh nó với timeout ngắn và policy được cân nhắc.

Nếu startup warm-up dài, dùng startup gating phù hợp với cluster/version/config hiện hành hoặc cấu hình probe timing sao cho liveness không kill app trước khi startup hoàn tất. Không chỉ tăng timeout tùy tiện; đo startup distribution trước.

Sau fix, tôi chạy load/failure tests: slow pricing, pricing outage, Redis outage, cold startup, memory pressure và rolling update. Theo dõi restart rate, ready replicas, 5xx, probe duration/failure, termination reason, p95/p99, dependency latency, CPU throttling và memory peaks. Alert khi ready capacity giảm hoặc restart rate tăng, không chỉ khi CPU cao.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ pause rollout và giữ capacity khỏe trước. Restart count chưa nói root cause; tôi cần container last termination reason, exit code và pod events để biết OOM, liveness kill hay app tự crash.

Tôi dựng timeline từng pod rồi correlate probe failures với Application Insights dependencies và resource metrics. `/health` hiện dùng cho cả liveness/readiness và gọi SQL, Redis, pricing API nên rất đáng nghi: pricing outage có thể làm liveness fail và kubelet restart một process hoàn toàn khỏe, tạo restart storm.

Tôi sẽ tách process liveness khỏi traffic readiness và dependency degradation. Startup warm-up cũng cần startup/readiness gating phù hợp để liveness không giết app đang khởi động. Average resource toàn deployment không đủ; tôi xem per-pod peaks, OOM reason và CPU throttling.

Cuối cùng tôi verify bằng failure injection và rolling deployment test, rồi alert trên ready capacity, restart rate, probe failures, 5xx và dependency latency.”

## Câu hỏi đào sâu

1. Nếu SQL Server down hoàn toàn và mọi business endpoint đều cần SQL, readiness và liveness của pod nên phản ứng khác nhau thế nào?
2. Nếu pod bị OOMKilled nhưng memory dashboard chưa từng vượt 70%, bạn sẽ nghi ngờ điều gì về sampling/metrics và thu evidence nào tiếp?
3. Team đề xuất tăng toàn bộ probe timeout lên 30 giây. Khi nào đó là mitigation hợp lý và khi nào chỉ che root cause?

## Lỗi trả lời thường gặp

- Nhìn CPU/memory average rồi loại trừ resource issue.
- Dùng cùng một deep health endpoint cho mọi probe mà không xét semantics.
- Tắt probes hoàn toàn để “hết restart”.
- Restart/delete pods trước khi thu termination evidence.
- Chỉ tăng resource limits mà không xác minh OOM/throttling.

## Thang điểm 0–10

- **0–2:** Chỉ tăng limits hoặc restart pods.
- **3–4:** Biết xem events nhưng chưa phân biệt probe semantics.
- **5–6:** Điều tra termination reason đúng, tách liveness/readiness và stabilize hợp lý.
- **7–8:** Có per-pod resource analysis, rollout safety, failure tests và observability.
- **9–10:** Reasoning đầy đủ về process/traffic/dependency/startup lifecycle, causal timeline và capacity/resilience trade-offs.

# Câu 3 — Modernize .NET Framework 4.5 enterprise portal mà không rewrite toàn bộ

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35–45 phút  
**Kỹ năng được đánh giá:** .NET modernization, .NET Framework, ASP.NET Core, IIS, SQL Server, incremental migration, API boundaries, CI/CD, testing, rollback, architecture trade-offs

## Bối cảnh

Một internal enterprise portal đã chạy nhiều năm trên .NET Framework 4.5 + ASP.NET MVC + jQuery + SQL Server + IIS/Windows Server. Solution có khoảng 40 projects, nhiều shared libraries, một số static helpers truy cập database/configuration trực tiếp và vài scheduled jobs chạy trong web process.

Business vẫn phát triển tính năng mới hàng tháng. Hệ thống có các module attendance, approval, timesheet và reporting. Database dùng chung với nhiều foreign keys/stored procedures. Automated tests ít; production deployment qua CI/CD nhưng rollback hiện chủ yếu là redeploy package cũ.

Mục tiêu 12–18 tháng là đưa phần lớn backend sang modern .NET, cải thiện testability/observability và giảm rủi ro support. Team 6 developers không thể dừng feature delivery quá 2–3 sprint. CTO hỏi có nên rewrite toàn bộ sang .NET 10, React và microservices hay không.

Chưa có dependency inventory, traffic/SLO chi tiết, mức coupling giữa modules, compatibility của third-party libraries hoặc danh sách stored procedures quan trọng.

## Câu hỏi chính

Hãy đề xuất modernization strategy có thể triển khai dần mà vẫn giữ production ổn định. Bạn sẽ inventory dependencies, chọn migration boundaries, xử lý shared database/authentication/scheduled jobs, xây testing/observability safety net, tổ chức rollout/rollback và quyết định khi nào nên giữ modular monolith, tách service hoặc rewrite một module.

## Câu hỏi làm rõ nên cân nhắc

1. Những third-party/.NET Framework-only dependencies nào đang block modern .NET và business critical đến mức nào?
2. Module boundaries có rõ về ownership/data hay đang gọi trực tiếp tables/helpers của nhau?
3. Authentication hiện dùng cơ chế nào và có thể cho legacy/new applications cùng trust một identity provider/session strategy phù hợp không?
4. Deployment có thể route theo path/module hoặc chạy legacy và modern app song song không?
5. Stored procedures/shared database có external consumers nào ngoài portal không?

## Gợi ý tư duy

### Gợi ý 1

Rewrite và runtime upgrade là hai quyết định khác nhau. Hãy giảm uncertainty trước khi chọn kiến trúc đích.

### Gợi ý 2

Một migration tốt cần **coexistence boundary**: old và new chạy song song đủ lâu để rollout/rollback được.

### Gợi ý 3

Shared database có thể là transitional constraint. Đừng gọi nó “microservices” nếu các modules vẫn cùng sở hữu schema/transaction boundary.

## Cấu trúc trả lời đề xuất

1. Inventory code/dependencies/runtime constraints.
2. Map module/data/integration boundaries.
3. Xác định measurable modernization goals.
4. Tạo safety net: tests + observability + CI.
5. Chọn một low-risk/high-value migration slice.
6. Thiết kế coexistence/routing/auth/data strategy.
7. Migrate incrementally và giữ backward compatibility.
8. Tách scheduled/background work phù hợp.
9. Rollout/canary/rollback từng slice.
10. Reassess architecture sau khi có evidence.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không mặc định rewrite toàn bộ là phương án tốt; rewrite có feature-parity, hidden behavior và long-running branch risk.
- Bắt đầu bằng dependency/integration/data inventory và production behavior.
- Xây characterization/integration/E2E tests cho critical flows trước khi thay đổi sâu.
- Tạo coexistence strategy để legacy và modern components chạy song song.
- Không tự động gọi shared-database modules là microservices; ownership/transaction boundary phải rõ.
- Database migrations trong giai đoạn coexistence phải backward-compatible với old/new versions khi cần rollback.
- Scheduled jobs trong web process cần được inventory về ownership, idempotency và duplicate execution trước khi chuyển hosting.
- Observability phải cho phép so sánh legacy/new paths và phát hiện regression.

### Điểm cộng

- Dùng strangler-style routing/module extraction khi boundaries phù hợp thay vì big-bang cutover.
- Ưu tiên libraries có thể multi-target/refactor dependency direction trước khi move host, nếu cost hợp lý.
- Tách business logic khỏi static infrastructure access từng bước để tăng testability.
- Authentication migration cần tránh hai nguồn identity/authorization semantics không nhất quán.
- Frontend modernization không bắt buộc phải khóa cùng timeline với backend runtime migration.
- Định nghĩa rollback unit: route traffic về legacy path nếu data/schema vẫn compatible.

### Senior+

- Có decision criteria để rewrite một module: nhỏ, bounded, behavior hiểu rõ, testable, legacy implementation cản trở nghiêm trọng và migration cost thấp hơn refactor.
- Có decision criteria để tách service: independent ownership/deployment/scale/reliability boundary thực sự, không chỉ vì “modern”.
- Xử lý data ownership evolution bằng transitional APIs/schema contracts thay vì distributed transaction ngẫu hứng.
- Theo dõi modernization bằng risk/lead-time/incident/testability metrics, không chỉ phần trăm code ported.

## Hướng giải quyết tham khảo

Tôi sẽ bắt đầu bằng discovery 1–2 sprint có giới hạn, không phải dừng feature delivery. Inventory target frameworks, NuGet/third-party dependencies, Windows/IIS assumptions, static/global state, authentication, scheduled jobs, file system usage, external integrations, stored procedures và module-to-module/database coupling. Đồng thời lấy production telemetry để biết critical paths, latency/error và usage thực tế.

Sau đó map modules và chọn một slice có boundary tương đối rõ, business value thật nhưng blast radius kiểm soát được. Trước migration, bổ sung characterization tests cho behavior hiện tại, API/integration tests quanh database/integrations và Playwright E2E cho critical user journey. Mục tiêu không phải 100% coverage mà là safety net ở những nơi migration dễ làm sai.

Tôi ưu tiên coexistence. Legacy MVC app tiếp tục chạy trên IIS; modern ASP.NET Core module có thể chạy như deployable riêng hoặc host phù hợp, rồi reverse proxy/path routing chuyển một subset traffic. Cơ chế cụ thể phụ thuộc hạ tầng thực tế. Authentication phải có một trust model thống nhất; không tự tạo hai user/session semantics độc lập.

Về database, shared SQL có thể được giữ trong transitional phase. Nhưng mỗi migrated module cần làm rõ tables/stored procedures nào nó sở hữu. Schema change trong giai đoạn old/new coexist phải theo expand/contract hoặc ít nhất backward-compatible để rollback route không bị phá. Không tách database chỉ để đạt nhãn microservice.

Scheduled jobs đang nằm trong web process cần inventory. Những job critical có thể chuyển sang Worker Service/Azure Functions hoặc hosting khác nếu requirements phù hợp, nhưng trước hết phải thiết kế idempotency, retry, cancellation, observability và multi-instance behavior. Chuyển host mà giữ duplicate-execution bug chỉ đổi nơi xảy ra lỗi.

Static helpers/direct DB access được refactor theo seams cần thiết: introduce interfaces/services ở boundary có giá trị, không làm một “Clean Architecture rewrite” toàn solution trước khi ship slice đầu tiên. Shared libraries có thể được tách dependencies/multi-target khi khả thi để giảm coupling giữa old/new runtimes.

Frontend jQuery cũng không bắt buộc rewrite cùng lúc. Nếu một migrated module cần UI mới, có thể dùng React/Vue cho module đó với integration boundary rõ; nếu UI legacy vẫn đáp ứng, backend modernization có thể đi trước. Tách hai chương trình giảm simultaneous change surface.

Mỗi slice rollout bằng canary/path/user cohort nếu khả thi, với dashboards so sánh error/latency/business outcomes legacy vs new. Rollback phải được rehearsal: route về legacy artifact/path trong khi schema vẫn compatible. Sau vài slices, reassess: nếu modular monolith trên modern .NET đáp ứng deployment/scale/team needs, không cần microservices. Chỉ tách service khi có independent lifecycle/ownership/scale/reliability requirement đủ lớn để trả operational cost.

Rewrite chỉ dành cho bounded module khi behavior đã hiểu, tests đủ, dependency surface nhỏ và cost refactor/port lớn hơn implementation mới một cách có evidence. Với hệ thống 40 projects và hidden legacy behavior, big-bang rewrite toàn portal có rủi ro parity và cutover rất cao.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ không bắt đầu bằng rewrite .NET 10 + React + microservices. Đầu tiên tôi inventory dependencies, Windows/IIS assumptions, shared DB/stored procedures, auth, scheduled jobs và module coupling; đồng thời lấy production usage để biết critical paths.

Tôi chọn một bounded slice, tạo characterization/integration/E2E safety net rồi cho legacy và modern implementation coexist. Schema phải backward-compatible để có thể route rollback. Shared database có thể tồn tại tạm thời nhưng ownership phải dần rõ; tôi không gọi đó là microservices nếu modules vẫn share transaction/data ownership.

Scheduled jobs được tách khỏi web process khi có lợi, nhưng phải xử lý idempotency, retry và multi-instance trước. Frontend modernization có thể đi timeline riêng để giảm blast radius.

Sau mỗi slice tôi đo error, latency, incidents và delivery impact. Nếu modular modern .NET đáp ứng nhu cầu thì giữ đơn giản. Tôi chỉ tách service khi có independent ownership/scale/deployment boundary, và chỉ rewrite module khi behavior đủ hiểu và rewrite có risk/cost thấp hơn incremental refactor.”

## Câu hỏi đào sâu

1. Nếu một critical third-party library chỉ hỗ trợ .NET Framework và vendor chưa có roadmap, bạn cô lập blocker đó thế nào mà không dừng toàn migration?
2. Nếu migrated module và legacy module phải update cùng một transaction xuyên nhiều tables, bạn có tách service ngay không? Vì sao?
3. CTO yêu cầu hoàn tất trong 12 tháng và muốn đo “% migrated code”. Bạn đề xuất metrics nào phản ánh progress và risk tốt hơn?

## Lỗi trả lời thường gặp

- Big-bang rewrite vì code cũ “xấu”.
- Tách microservices nhưng vẫn share database ownership và distributed coupling không kiểm soát.
- Upgrade backend, frontend, auth và database cùng một cutover.
- Không xây characterization tests vì “legacy không test được”.
- Có rollout plan nhưng không giữ schema/data compatibility để rollback thực tế.

## Thang điểm 0–10

- **0–2:** Chỉ chọn target stack mới, không có migration strategy.
- **3–4:** Có incremental migration nhưng thiếu coexistence/data/rollback reasoning.
- **5–6:** Có inventory, safety net, bounded slices và backward-compatible rollout.
- **7–8:** Xử lý auth, jobs, shared DB, frontend decoupling và observability tốt.
- **9–10:** Có evidence-based criteria cho refactor/rewrite/service extraction, quản lý transitional architecture và tối ưu cả delivery risk lẫn technical outcome.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Debounce không đảm bảo ordering; async UI cần explicit request lifecycle và stale-response protection.
- Kubernetes liveness, readiness, startup và dependency degradation là các signals khác nhau; trộn chúng có thể biến dependency outage thành restart storm.
- Production troubleshooting phải dựa trên causal timeline theo từng instance/pod thay vì averages hoặc một symptom đơn lẻ.
- Modernization an toàn cần coexistence, backward compatibility, tests, observability và rollback boundary.
- Microservices/Kubernetes/rewrite không phải mục tiêu modernization; complexity phải được biện minh bằng ownership, scale, reliability hoặc deployment requirements thực tế.

## Mẫu tư duy cần nhớ

- **Control completion, not only request initiation.**
- **Stabilize → collect evidence → compare hypotheses → verify → prevent recurrence.**
- **Separate process health from traffic readiness and dependency health.**
- **Create a coexistence boundary before replacing legacy behavior.**
- **Prefer incremental evidence over architecture-by-fashion.**
