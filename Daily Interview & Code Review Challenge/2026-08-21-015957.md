# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng và trạng thái không nhất quán

**Chủ đề:** Background jobs, idempotency, concurrency, EF Core transaction handling  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** Khoảng 7–9 vấn đề

## Bối cảnh

Một hệ thống ASP.NET Core dùng Hangfire để xử lý offboarding nhân viên. Job đọc cấu hình đang chờ xử lý, gọi dịch vụ Exchange/Microsoft 365 để cập nhật mailbox, sau đó đánh dấu bản ghi hoàn tất. Hệ thống chạy nhiều application instance và có retry khi job thất bại.

Trong production thỉnh thoảng cùng một nhân viên bị xử lý hai lần, một số mailbox đã được cập nhật nhưng database vẫn ở trạng thái `Pending`, và log cho thấy cùng `configId` xuất hiện gần như đồng thời trên hai worker. External operation có thể mất vài giây hoặc timeout. Không được giả định external API hỗ trợ distributed transaction với database.

## Đoạn code cần review

```csharp
public sealed class OffboardingJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<OffboardingJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 5)]
    public async Task ProcessAsync(Guid configId)
    {
        var config = await _db.EmployeeOffboardingMailConfigs
            .FirstOrDefaultAsync(x => x.Id == configId);

        if (config == null || config.Status == "Completed")
            return;

        config.Status = "Processing";
        config.LastAttemptAt = DateTime.UtcNow;
        await _db.SaveChangesAsync();

        try
        {
            if (config.Action == "Forward")
            {
                await _exchange.SetForwardingAsync(
                    config.EmployeeEmail,
                    config.TargetEmail);
            }
            else if (config.Action == "Delegate")
            {
                await _exchange.AddDelegateAsync(
                    config.EmployeeEmail,
                    config.TargetEmail);
            }

            config.Status = "Completed";
            config.CompletedAt = DateTime.UtcNow;
            await _db.SaveChangesAsync();
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Failed offboarding config {ConfigId} for {EmployeeEmail}",
                config.Id,
                config.EmployeeEmail);

            config.Status = "Pending";
            await _db.SaveChangesAsync();
            throw;
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness.
2. Xác định rủi ro concurrency, retry và idempotency.
3. Giải thích tác động production của từng vấn đề.
4. Ưu tiên vấn đề theo mức độ nghiêm trọng.
5. Đề xuất implementation an toàn hơn.
6. Giải thích cách kiểm thử fix.
7. Đề xuất logs, traces và metrics cần thiết.

## Câu hỏi gợi mở

- Hai Hangfire worker có thể cùng đọc `Pending` trước khi một worker commit `Processing` không?
- `Processing` trong database có thực sự là một lock không?
- Điều gì xảy ra nếu Exchange đã thay đổi thành công nhưng request timeout trước khi client nhận response?
- Retry có thể biến một lỗi tạm thời thành duplicate side effect như thế nào?
- Cancellation và recovery của bản ghi bị kẹt ở `Processing` nên được thiết kế ra sao?

## Gợi ý

### Gợi ý 1

Hãy tách hai vấn đề: **claim quyền xử lý một work item** và **đảm bảo external side effect có thể retry an toàn**.

### Gợi ý 2

Một lần `SELECT` rồi `UPDATE` sau đó không phải atomic claim. Đồng thời, transaction database không thể rollback một thay đổi đã thành công ở Exchange.

## Kết quả code review tham khảo

### 1. Claim job không atomic — Critical

**Problem:** Nhiều worker có thể đọc cùng bản ghi trước khi bất kỳ worker nào lưu `Processing`.  
**Why:** `SELECT` và `UPDATE` là hai bước riêng biệt; trạng thái application-level không tạo mutual exclusion.  
**Production impact:** Hai worker cùng thực hiện side effect trên mailbox.  
**Recommended fix:** Dùng atomic conditional update/claim ở database, optimistic concurrency token, hoặc cơ chế distributed coordination phù hợp. Điều quan trọng là chỉ một worker chuyển được `Pending -> Processing` cho một attempt hợp lệ.

### 2. External side effect không được thiết kế idempotent — Critical

**Problem:** Retry có thể gọi lại `AddDelegateAsync`/`SetForwardingAsync`.  
**Why:** Worker không biết chắc request trước thất bại trước hay sau khi external system áp dụng thay đổi.  
**Production impact:** Duplicate operation, lỗi conflict hoặc trạng thái mailbox khó dự đoán.  
**Recommended fix:** Thiết kế operation theo desired state: đọc/đối chiếu trạng thái hiện tại hoặc dùng idempotency capability của downstream nếu có; lưu operation/attempt identity và reconcile khi kết quả không chắc chắn.

### 3. Dual-write giữa database và Exchange — High

**Problem:** Exchange thành công nhưng `SaveChangesAsync` cuối thất bại.  
**Why:** Không có atomic transaction xuyên database và external system.  
**Production impact:** Database báo chưa hoàn tất trong khi mailbox đã đổi; retry tiếp tục side effect.  
**Recommended fix:** Chấp nhận eventual consistency và thiết kế state machine + reconciliation. Phân biệt `Unknown`, `Failed`, `Completed`; verify external state trước retry khi outcome không chắc chắn.

### 4. Catch đặt lại `Pending` cho mọi exception — High

**Problem:** Mọi lỗi đều được coi là retryable.  
**Why:** Không phân loại timeout, transient, validation, authorization hay permanent error.  
**Production impact:** Retry vô ích, tạo tải và có thể lặp side effect.  
**Recommended fix:** Phân loại lỗi; retry transient với backoff, đưa permanent failure vào `Failed`/dead-letter/manual review.

### 5. Không có lease/recovery rõ ràng cho `Processing` — High

**Problem:** Process có thể chết sau khi lưu `Processing`.  
**Why:** Không có lease expiry/heartbeat hoặc recovery policy.  
**Production impact:** Work item bị kẹt vĩnh viễn hoặc bị reset thủ công không an toàn.  
**Recommended fix:** Lưu `LeaseUntil`, `AttemptId`, `WorkerId`; chỉ reclaim lease hết hạn và reconcile external state trước khi tiếp tục.

### 6. Không truyền CancellationToken — Medium

**Problem:** EF và external calls không nhận cancellation.  
**Why:** Method không expose token hoặc integration không sử dụng nó.  
**Production impact:** Shutdown/deployment có thể kéo dài; operation tiếp tục khi worker không còn quản lý lifecycle.  
**Recommended fix:** Truyền cancellation token khi framework/integration hỗ trợ và xác định rõ semantics khi cancellation xảy ra giữa side effect.

### 7. String trạng thái/action dễ tạo invalid state — Medium

**Problem:** `"Pending"`, `"Processing"`, `"Completed"`, `"Forward"`, `"Delegate"` không được compiler kiểm soát.  
**Why:** Domain state không được model hóa chặt.  
**Production impact:** Typo hoặc action mới có thể bị bỏ qua nhưng job vẫn đánh dấu completed.  
**Recommended fix:** Dùng enum/value object và fail explicit với unsupported action.

### 8. Observability thiếu attempt/correlation metadata — Medium

**Problem:** Log chỉ có config và email.  
**Why:** Không có attempt ID, worker, elapsed time, downstream operation/result category.  
**Production impact:** Khó chứng minh duplicate do concurrency hay retry sau timeout.  
**Recommended fix:** Structured logging, trace span cho claim/external/reconcile và metrics theo outcome.

## Phiên bản code đề xuất

```csharp
public sealed class OffboardingJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IExchangeService _exchange;
    private readonly ILogger<OffboardingJob> _logger;

    public OffboardingJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IExchangeService exchange,
        ILogger<OffboardingJob> logger)
    {
        _dbFactory = dbFactory;
        _exchange = exchange;
        _logger = logger;
    }

    [AutomaticRetry(Attempts = 3)]
    public async Task ProcessAsync(Guid configId, CancellationToken ct)
    {
        var attemptId = Guid.NewGuid();
        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.EmployeeOffboardingMailConfigs
            .Where(x => x.Id == configId &&
                        (x.Status == OffboardingStatus.Pending ||
                         (x.Status == OffboardingStatus.Processing &&
                          x.LeaseUntil < DateTime.UtcNow)))
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, OffboardingStatus.Processing)
                .SetProperty(x => x.AttemptId, attemptId)
                .SetProperty(x => x.LeaseUntil, DateTime.UtcNow.AddMinutes(5))
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (claimed != 1)
            return;

        var config = await db.EmployeeOffboardingMailConfigs
            .AsNoTracking()
            .SingleAsync(x => x.Id == configId, ct);

        try
        {
            var desiredState = new MailboxDesiredState(
                config.Action,
                config.TargetEmail);

            var alreadyApplied = await _exchange
                .MatchesDesiredStateAsync(config.EmployeeEmail, desiredState, ct);

            if (!alreadyApplied)
            {
                await _exchange.ApplyDesiredStateAsync(
                    config.EmployeeEmail,
                    desiredState,
                    ct);
            }

            var verified = await _exchange
                .MatchesDesiredStateAsync(config.EmployeeEmail, desiredState, ct);

            if (!verified)
                throw new InvalidOperationException("Mailbox state verification failed.");

            await db.EmployeeOffboardingMailConfigs
                .Where(x => x.Id == configId && x.AttemptId == attemptId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, OffboardingStatus.Completed)
                    .SetProperty(x => x.CompletedAt, DateTime.UtcNow)
                    .SetProperty(x => x.LeaseUntil, (DateTime?)null), ct);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex,
                "Offboarding attempt {AttemptId} failed for config {ConfigId}",
                attemptId, configId);

            await db.EmployeeOffboardingMailConfigs
                .Where(x => x.Id == configId && x.AttemptId == attemptId)
                .ExecuteUpdateAsync(s => s
                    .SetProperty(x => x.Status, OffboardingStatus.Unknown)
                    .SetProperty(x => x.LeaseUntil, (DateTime?)null),
                    CancellationToken.None);

            throw;
        }
    }
}
```

`Unknown` ở đây cố ý biểu diễn trường hợp chưa thể chứng minh external side effect đã xảy ra hay chưa. Một reconciliation path riêng nên kiểm tra actual mailbox state trước khi quyết định retry.

## Trade-offs

Atomic conditional update đơn giản và phù hợp khi database là coordination point, nhưng cần index/state model tốt và không thay thế idempotency ở downstream. Distributed lock có thể hữu ích cho một số workload nhưng vẫn không giải quyết ambiguity khi external call timeout. Việc verify desired state thêm network call và latency, đổi lại giảm nguy cơ duplicate side effect. Với throughput rất lớn có thể tách command/outbox/worker pipeline, nhưng không cần thiết chỉ để giải quyết bài toán này.

## Cách kiểm thử

1. **Concurrency integration test:** chạy 20 `ProcessAsync` đồng thời cho cùng `configId`; chỉ một attempt được claim và external mutation chỉ xảy ra tối đa một lần khi state ban đầu chưa đúng.
2. **Ambiguous timeout test:** fake Exchange áp dụng thay đổi rồi throw timeout; lần retry/reconcile phải phát hiện desired state đã tồn tại và không tạo side effect lần hai.
3. **Worker crash test:** dừng worker sau khi claim; sau lease expiry, worker khác reclaim và reconcile an toàn.
4. **Permanent failure test:** permission/validation error không bị retry vô hạn và được đưa sang trạng thái cần xử lý thích hợp.
5. **Database failure test:** external success nhưng completion update thất bại; reconciliation sau đó phải đưa database về `Completed` mà không lặp mutation.

## Quan sát trong production

Log `ConfigId`, `AttemptId`, `WorkerId`, transition trạng thái và downstream outcome nhưng tránh ghi dữ liệu nhạy cảm không cần thiết. Theo dõi metrics: claim conflict, processing duration, retry count, unknown-state count, reconciliation success/failure và lease-expired count. Trace nên tách span `claim -> inspect desired state -> apply -> verify -> persist outcome`. Alert khi `Unknown` hoặc expired lease vượt baseline.

## Câu hỏi phỏng vấn mở rộng

1. Vì sao `[DisableConcurrentExecution]` nếu dùng cũng không nên được xem là toàn bộ chiến lược idempotency?
2. Nếu external API không có endpoint đọc lại trạng thái, bạn sẽ xử lý ambiguous timeout thế nào?
3. Khi nào bạn chọn transactional outbox cho workflow này, và outbox giải quyết phần nào nhưng không giải quyết phần nào?

# Code Review Challenge 2 — Endpoint tìm kiếm audit log vừa chậm vừa có nguy cơ lộ dữ liệu tenant

**Chủ đề:** Authorization, EF Core query execution, input handling, performance, sensitive-data exposure  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** Khoảng 7–8 vấn đề

## Bối cảnh

Một multi-tenant ASP.NET Core API cung cấp màn hình audit log cho quản trị viên. Mỗi tenant có thể có hàng triệu bản ghi. Sau một đợt tăng dữ liệu, endpoint có latency cao, memory tăng mạnh và một báo cáo nội bộ cho thấy admin của tenant A đôi lúc có thể tìm thấy sự kiện thuộc tenant B nếu biết một phần email/message phù hợp.

Business yêu cầu tìm theo text, khoảng thời gian và trả tối đa một trang kết quả. Audit payload đôi khi chứa identifier và diagnostic data; không được trả toàn bộ payload nếu caller không có quyền chi tiết.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;

    public AuditController(AppDbContext db)
    {
        _db = db;
    }

    [HttpGet("search")]
    [Authorize]
    public async Task<IActionResult> Search(
        string? q,
        DateTime? from,
        DateTime? to,
        int page = 1,
        int pageSize = 100)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;

        var events = await _db.AuditEvents
            .OrderByDescending(x => x.CreatedAt)
            .ToListAsync();

        if (!string.IsNullOrWhiteSpace(q))
        {
            events = events
                .Where(x => x.Message.Contains(q,
                    StringComparison.OrdinalIgnoreCase) ||
                    x.UserEmail.Contains(q,
                    StringComparison.OrdinalIgnoreCase))
                .ToList();
        }

        if (from.HasValue)
            events = events.Where(x => x.CreatedAt >= from.Value).ToList();

        if (to.HasValue)
            events = events.Where(x => x.CreatedAt <= to.Value).ToList();

        var result = events
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new
            {
                x.Id,
                x.TenantId,
                x.UserEmail,
                x.Message,
                x.Payload,
                x.CreatedAt
            })
            .ToList();

        return Ok(new
        {
            tenantId,
            total = events.Count,
            items = result
        });
    }
}
```

## Câu hỏi gợi mở

- `[Authorize]` có đảm bảo caller chỉ đọc dữ liệu tenant của mình không?
- Query được thực thi ở database hay phần lớn filtering đang chạy trong memory?

## Gợi ý

### Gợi ý 1

Bắt đầu từ **authorization boundary** trước performance: tenant isolation phải được đưa vào query trước khi dữ liệu rời database.

### Gợi ý 2

`ToListAsync()` xuất hiện quá sớm làm thay đổi toàn bộ execution model: filter, pagination và projection sau đó đều chạy trong process.

## Dừng lại và tự review

---

**Hãy tự review đoạn code trước khi xem phần phân tích bên dưới.**

---

## Kết quả code review tham khảo

### 1. Không filter tenant — Critical

**Problem:** `tenantId` được đọc nhưng không dùng để giới hạn query.  
**Why:** Authentication chỉ xác nhận identity; tenant-level authorization không tự xuất hiện.  
**Production impact:** Cross-tenant data disclosure.  
**Recommended fix:** Validate tenant claim và áp tenant predicate ở database cho mọi query; tốt hơn nữa áp defense-in-depth qua tenant-aware repository/query filter phù hợp với kiến trúc.

### 2. Authorization quá rộng — High

**Problem:** Bất kỳ authenticated user nào cũng có thể gọi endpoint.  
**Why:** `[Authorize]` không kiểm tra role/policy dành cho audit access.  
**Production impact:** User không có quyền quản trị vẫn có thể đọc audit data trong tenant.  
**Recommended fix:** Policy-based authorization, ví dụ `Audit.Read`; quyền xem payload chi tiết có thể là policy riêng.

### 3. Materialize toàn bảng trước filter — High

**Problem:** `ToListAsync()` chạy trước tenant/text/date/page filters.  
**Why:** Sau materialization, LINQ tiếp theo là LINQ-to-Objects.  
**Production impact:** Full-table read, memory pressure, GC pressure, latency và database/network load lớn.  
**Recommended fix:** Giữ `IQueryable`, compose predicates rồi projection/pagination trước `ToListAsync`.

### 4. Không giới hạn page/pageSize/date range — High

**Problem:** Caller có thể truyền giá trị bất hợp lệ hoặc page size cực lớn.  
**Why:** Không validation.  
**Production impact:** Resource exhaustion, overflow/negative skip, expensive queries.  
**Recommended fix:** Validate `page >= 1`, clamp `pageSize` vào giới hạn business và giới hạn search window nếu phù hợp.

### 5. Sensitive payload được trả vô điều kiện — High

**Problem:** `Payload`, email và message được projection trực tiếp cho mọi caller.  
**Why:** DTO không phản ánh field-level authorization/data minimization.  
**Production impact:** Lộ PII hoặc diagnostic secrets.  
**Recommended fix:** DTO tối thiểu; redact/mask; endpoint hoặc policy riêng để xem detail payload khi thực sự cần.

### 6. Pagination thiếu deterministic tie-breaker — Medium

**Problem:** Chỉ sort theo `CreatedAt`.  
**Why:** Nhiều event có thể cùng timestamp; dữ liệu mới được insert giữa các page.  
**Production impact:** Duplicate/missing item giữa các trang.  
**Recommended fix:** Ít nhất sort `CreatedAt DESC, Id DESC`; với feed lớn/biến động cao ưu tiên keyset pagination.

### 7. Search text cần thiết kế theo database/index — Medium

**Problem:** `Contains` case-insensitive trong memory vừa đắt vừa không tận dụng database search strategy.  
**Why:** Query đã materialize.  
**Production impact:** CPU/memory cao; nếu chuyển ngây thơ sang SQL `%term%` vẫn có thể scan lớn.  
**Recommended fix:** Dùng expression được provider translate và chọn index/full-text/trigram strategy theo SQL Server/PostgreSQL, dữ liệu và search semantics thực tế.

### 8. Tracking không cần thiết — Low

**Problem:** Read-only query mặc định có thể tracking entities.  
**Why:** Query entity rồi materialize trước projection.  
**Production impact:** Thêm memory/change-tracker overhead.  
**Recommended fix:** Projection trực tiếp sang DTO thường đủ; hoặc `AsNoTracking()` khi materialize entity read-only.

## Phiên bản code đề xuất

```csharp
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly AppDbContext _db;

    public AuditController(AppDbContext db) => _db = db;

    [HttpGet("search")]
    [Authorize(Policy = "Audit.Read")]
    public async Task<ActionResult<AuditSearchResponse>> Search(
        string? q,
        DateTime? from,
        DateTime? to,
        int page = 1,
        int pageSize = 50,
        CancellationToken ct = default)
    {
        var tenantId = User.FindFirst("tenant_id")?.Value;
        if (string.IsNullOrWhiteSpace(tenantId))
            return Forbid();

        if (page < 1 || pageSize < 1 || pageSize > 100)
            return BadRequest("Invalid paging parameters.");

        if (from.HasValue && to.HasValue && from > to)
            return BadRequest("Invalid date range.");

        IQueryable<AuditEvent> query = _db.AuditEvents
            .AsNoTracking()
            .Where(x => x.TenantId == tenantId);

        if (from.HasValue)
            query = query.Where(x => x.CreatedAt >= from.Value);

        if (to.HasValue)
            query = query.Where(x => x.CreatedAt <= to.Value);

        if (!string.IsNullOrWhiteSpace(q))
        {
            var term = q.Trim();
            query = query.Where(x =>
                x.Message.Contains(term) ||
                x.UserEmail.Contains(term));
        }

        var total = await query.CountAsync(ct);

        var items = await query
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .Select(x => new AuditListItem(
                x.Id,
                MaskEmail(x.UserEmail),
                x.Message,
                x.CreatedAt))
            .ToListAsync(ct);

        return Ok(new AuditSearchResponse(total, items));
    }

    private static string MaskEmail(string email)
    {
        var at = email.IndexOf('@');
        return at <= 1 ? "***" : $"{email[0]}***{email[at..]}";
    }
}
```

Trong production, cần xác nhận `MaskEmail` có translate được nếu đặt bên trong EF projection. Một cách an toàn là chỉ select các field tối thiểu cần thiết từ database rồi mask trên page nhỏ sau materialization, hoặc dùng expression/provider-supported transformation. Search semantics cũng phải được điều chỉnh theo database provider; không nên giả định cùng một strategy tối ưu cho SQL Server và PostgreSQL.

## Trade-offs

Offset pagination đơn giản và phù hợp với UI có page number, nhưng page sâu ngày càng đắt và dữ liệu thay đổi có thể gây drift. Keyset pagination nhanh và ổn định hơn cho audit feed lớn nhưng không thuận tiện cho nhảy trực tiếp tới page N. `CountAsync` chính xác có thể tốn chi phí; nếu UI chỉ cần “còn trang tiếp theo hay không”, có thể lấy `pageSize + 1` thay vì count. Full-text search hoặc PostgreSQL trigram tăng hiệu quả search nhưng thêm index/storage/operational complexity.

## Cách kiểm thử

1. **Tenant isolation integration test:** tạo dữ liệu tenant A/B với cùng search term; token A tuyệt đối không nhận ID/data của B.
2. **Authorization test:** authenticated user thiếu `Audit.Read` nhận 403; user hợp lệ chỉ nhận field được phép.
3. **Large-data query test:** seed dataset lớn, xác minh generated SQL chứa tenant/date/search/pagination và không load toàn bảng vào process.
4. **Paging validation test:** page 0, negative page, pageSize quá lớn và invalid date range phải bị từ chối.
5. **Pagination consistency test:** nhiều rows cùng `CreatedAt`; ordering với `Id` phải deterministic. Nếu chuyển keyset, kiểm thử insert concurrent giữa hai lần fetch.

## Quan sát trong production

Theo dõi endpoint latency p50/p95/p99, rows scanned/returned, DB duration, timeout count, response size và allocation rate. Log tenant identifier dạng phù hợp với chính sách privacy, search duration và paging metadata nhưng không log raw payload/search text nếu có thể chứa dữ liệu nhạy cảm. Dùng tracing từ HTTP request đến EF/database span. Quan sát execution plan/index usage cho các query phổ biến và alert khi latency hoặc scanned/returned ratio tăng bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Bạn sẽ thiết kế tenant isolation defense-in-depth thế nào để developer khó quên `.Where(x => x.TenantId == tenantId)` ở endpoint khác?
2. Với PostgreSQL và nhu cầu substring search lớn, bạn sẽ đánh giá strategy/index nào và đo hiệu quả ra sao?
3. Nếu product bắt buộc hỗ trợ “jump to page 5000”, bạn chọn offset, keyset hay một mô hình khác và trade-off là gì?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Challenge 1 tập trung vào khác biệt giữa **job retry** và **safe retry**: concurrency control chỉ giúp giới hạn worker, còn idempotency/reconciliation mới xử lý external side effect khi kết quả không chắc chắn. Database transaction không thể tự làm cho một remote API call trở thành atomic.

Challenge 2 nhấn mạnh rằng authentication không đồng nghĩa authorization hay tenant isolation. Với EF Core, vị trí materialization quyết định phần nào chạy ở database và phần nào chạy trong memory; security predicate, filtering, projection và pagination nên được đẩy xuống database càng sớm càng hợp lý.

## Mẫu tư duy cần nhớ

- Thiết kế retries cùng idempotency và ambiguous-outcome recovery.
- Claim work atomically; đừng dùng một status update rời rạc như thể nó là lock.
- Authorization boundary phải tồn tại ngay tại data-access boundary, đặc biệt trong multi-tenant system.
- Giữ query dưới dạng `IQueryable` cho tới khi filtering/projection/pagination đã được compose.
- Treat observability và reconciliation như một phần của correctness, không phải phần bổ sung sau cùng.
