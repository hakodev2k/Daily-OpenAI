# Code Review Challenge 1 — Checkout oversell vì `DbContext` transaction không bảo vệ inventory khỏi concurrent requests

**Chủ đề:** C#/.NET, ASP.NET Core, EF Core, SQL Server, optimistic concurrency, transaction isolation, inventory correctness  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề quan trọng

## Bối cảnh

Một e-commerce API chạy nhiều Azure App Service instances. Khi checkout, hệ thống kiểm tra tồn kho, trừ `AvailableQuantity`, tạo `Order`, rồi commit bằng EF Core. Trong traffic bình thường mọi thứ ổn, nhưng khi flash sale có nhiều request đồng thời cho cùng SKU, production thỉnh thoảng bán vượt tồn kho.

Team cho rằng `BeginTransactionAsync()` đã serialize các checkout vì toàn bộ thao tác nằm trong một database transaction. Database là SQL Server. `InventoryItem` hiện không có concurrency token. Một order có thể chứa nhiều items, nhưng snippet rút gọn còn một SKU để tập trung vào transaction boundary.

## Đoạn code cần review

```csharp
public sealed class CheckoutService
{
    private readonly AppDbContext _db;
    private readonly ILogger<CheckoutService> _logger;

    public CheckoutService(
        AppDbContext db,
        ILogger<CheckoutService> logger)
    {
        _db = db;
        _logger = logger;
    }

    public async Task<Guid> CheckoutAsync(
        Guid customerId,
        string sku,
        int quantity,
        CancellationToken cancellationToken)
    {
        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var inventory = await _db.InventoryItems
            .SingleAsync(x => x.Sku == sku, cancellationToken);

        if (inventory.AvailableQuantity < quantity)
            throw new InvalidOperationException("Out of stock");

        inventory.AvailableQuantity -= quantity;

        var order = new Order
        {
            Id = Guid.NewGuid(),
            CustomerId = customerId,
            Sku = sku,
            Quantity = quantity,
            Status = "Confirmed",
            CreatedAtUtc = DateTime.UtcNow
        };

        _db.Orders.Add(order);

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        _logger.LogInformation(
            "Checkout completed for {OrderId} / {Sku} / {Quantity}",
            order.Id, sku, quantity);

        return order.Id;
    }
}
```

2. Xác định performance/security/reliability concerns liên quan.
3. Giải thích production impact và failure windows.
4. Ưu tiên findings theo severity.
5. Đề xuất implementation/design sửa đúng dưới concurrent checkout.
6. Giải thích cách test race condition một cách deterministic nhất có thể.
7. Nêu telemetry cần có để phát hiện oversell hoặc contention trong production.

## Câu hỏi gợi mở

1. Hai transaction cùng đọc `AvailableQuantity = 1` trước khi transaction nào update thì điều gì có thể xảy ra?
2. Default transaction isolation của database có tự biến read-modify-write thành atomic operation không?
3. Có thể biểu diễn điều kiện “chỉ trừ khi còn đủ hàng” ngay trong một SQL statement không?
4. Nếu dùng optimistic concurrency, application nên làm gì khi conflict xảy ra?
5. Với order chứa nhiều SKU, lock ordering hoặc retry strategy ảnh hưởng deadlock thế nào?

## Gợi ý

### Gợi ý 1

Rủi ro chính nằm ở **lost update / check-then-act race**: transaction boundary và atomic business invariant không phải cùng một khái niệm.

### Gợi ý 2

Hãy so sánh optimistic concurrency token với một conditional `UPDATE ... WHERE AvailableQuantity >= @quantity`; sau đó xem affected rows như kết quả của business precondition.

## Kết quả code review tham khảo

### Critical — Check-then-update không atomic, có thể oversell

**Vấn đề:** Code đọc quantity, kiểm tra trong application rồi update sau đó. Hai request có thể cùng quan sát một giá trị đủ hàng.

**Tại sao xảy ra:** Transaction không mặc nhiên khóa business invariant từ lúc đọc tới lúc update theo cách team đang giả định. Với concurrency phù hợp, cả hai request có thể vượt qua check trước khi ghi.

**Ảnh hưởng production:** Inventory có thể bị bán vượt số lượng thực tế hoặc một update ghi đè logic của request khác tùy execution/interleaving.

**Cách sửa:** Đưa precondition vào database write atomically, ví dụ conditional update `WHERE AvailableQuantity >= quantity`, hoặc dùng concurrency token/locking strategy có semantics được hiểu rõ. Chọn giải pháp dựa trên contention và requirement.

### High — Không có concurrency token để phát hiện stale write

**Vấn đề:** Entity không có `rowversion`/concurrency token.

**Tại sao xảy ra:** EF Core không biết giá trị entity đã stale theo business expectation nếu model không cấu hình optimistic concurrency.

**Ảnh hưởng production:** Concurrent modifications có thể không được application phát hiện như conflict cần xử lý.

**Cách sửa:** Nếu chọn optimistic concurrency, cấu hình `rowversion` trên SQL Server hoặc concurrency token phù hợp và xử lý `DbUpdateConcurrencyException`; không retry vô hạn.

### High — Business invariant chỉ tồn tại trong application code

**Vấn đề:** Database không có guard đủ mạnh để đảm bảo quantity không âm hoặc conditional decrement thành công đúng một lần.

**Tại sao xảy ra:** Validation trước write tách rời khỏi write thực tế.

**Ảnh hưởng production:** Một code path khác hoặc race có thể phá invariant.

**Cách sửa:** Đặt invariant càng gần mutation càng tốt: conditional update và, nếu phù hợp schema, `CHECK (AvailableQuantity >= 0)` như defense-in-depth.

### High — Không có idempotency cho checkout request

**Vấn đề:** Retry từ client/gateway sau timeout có thể tạo order thứ hai và trừ stock lần nữa.

**Tại sao xảy ra:** Mỗi invocation tạo `Guid.NewGuid()` và không có stable request identity.

**Ảnh hưởng production:** Duplicate order/reservation dù concurrency update đã đúng.

**Cách sửa:** Nếu API contract cần retry-safe checkout, nhận/generate stable idempotency key ở business boundary, persist unique key cùng outcome và trả lại kết quả cũ khi cùng operation được retry.

### Medium — Input quantity không được validate trong boundary này

**Vấn đề:** `quantity <= 0` không bị từ chối trong snippet.

**Tại sao xảy ra:** Logic giả định upstream validation luôn đúng.

**Ảnh hưởng production:** Quantity âm có thể làm tăng inventory; zero có thể tạo order vô nghĩa nếu không có validation khác.

**Cách sửa:** Enforce domain validation trước mutation và thêm database constraints phù hợp.

### Medium — Transaction có thể giữ lâu hơn cần thiết khi contention tăng

**Vấn đề:** Explicit transaction bắt đầu trước query và kéo dài qua object construction/logical work.

**Tại sao xảy ra:** Scope được chọn theo method thay vì minimal database critical section.

**Ảnh hưởng production:** Khi mở rộng sang nhiều SKU hoặc thêm dependency calls, lock duration/contention/deadlock risk tăng.

**Cách sửa:** Giữ transaction chỉ quanh database operations cần atomicity; tuyệt đối tránh remote calls trong transaction nếu không có lý do đặc biệt.

### Medium — Multi-SKU extension có deadlock risk nếu lock/update order không ổn định

**Vấn đề:** Snippet một SKU che mất vấn đề khi production order chứa nhiều SKU.

**Tại sao xảy ra:** Hai transactions có thể update A→B và B→A.

**Ảnh hưởng production:** Deadlocks, retry storms, checkout latency/error tăng.

**Cách sửa:** Update resources theo deterministic ordering; xử lý deadlock như transient failure có bounded retry/jitter nếu operation idempotent và contract cho phép.

### Medium — Error classification không rõ

**Vấn đề:** `InvalidOperationException("Out of stock")` trộn business rejection với programming/runtime failure.

**Tại sao xảy ra:** Domain outcome chưa được model rõ.

**Ảnh hưởng production:** HTTP mapping, alerting và retry policy dễ sai.

**Cách sửa:** Dùng explicit result/domain exception và map thành response phù hợp; concurrency conflict và transient DB failure phải là categories khác.

### Low — `DateTime.UtcNow` làm test thời gian khó kiểm soát

**Vấn đề:** Clock được gọi trực tiếp.

**Tại sao xảy ra:** Time dependency không injectable.

**Ảnh hưởng production:** Không phải nguyên nhân oversell, nhưng làm deterministic tests và temporal rules khó hơn.

**Cách sửa:** Dùng `TimeProvider` nếu domain/test cần kiểm soát thời gian.

## Phiên bản đề xuất

Một hướng đơn giản là biến stock decrement thành conditional atomic update và kiểm tra affected rows. Ví dụ với EF Core 8+ có thể dùng `ExecuteUpdateAsync`; cần xác minh provider/version thực tế trước khi áp dụng.

```csharp
public sealed class CheckoutService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public CheckoutService(AppDbContext db, TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task<Guid> CheckoutAsync(
        Guid customerId,
        string sku,
        int quantity,
        string idempotencyKey,
        CancellationToken cancellationToken)
    {
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        await using var tx = await _db.Database
            .BeginTransactionAsync(cancellationToken);

        var existing = await _db.Orders
            .AsNoTracking()
            .SingleOrDefaultAsync(
                x => x.IdempotencyKey == idempotencyKey,
                cancellationToken);

        if (existing is not null)
            return existing.Id;

        var affected = await _db.InventoryItems
            .Where(x => x.Sku == sku && x.AvailableQuantity >= quantity)
            .ExecuteUpdateAsync(
                setters => setters.SetProperty(
                    x => x.AvailableQuantity,
                    x => x.AvailableQuantity - quantity),
                cancellationToken);

        if (affected != 1)
            throw new OutOfStockException(sku);

        var order = new Order
        {
            Id = Guid.NewGuid(),
            CustomerId = customerId,
            Sku = sku,
            Quantity = quantity,
            Status = "Confirmed",
            IdempotencyKey = idempotencyKey,
            CreatedAtUtc = _timeProvider.GetUtcNow().UtcDateTime
        };

        _db.Orders.Add(order);

        await _db.SaveChangesAsync(cancellationToken);
        await tx.CommitAsync(cancellationToken);

        return order.Id;
    }
}
```

Database cần unique constraint trên `Orders.IdempotencyKey`; nếu key chỉ unique theo customer/operation scope thì constraint phải phản ánh scope đó. Race giữa hai request cùng idempotency key vẫn phải dựa vào unique constraint thay vì chỉ query-before-insert. Khi unique violation xảy ra, implementation cần phân loại đúng và đọc lại outcome tương ứng.

## Giải thích thiết kế sau khi sửa

Điểm chính là chuyển từ “read → check → mutate” sang một write có precondition nằm cùng statement. Database trả affected row count để application biết reservation thành công hay không. Transaction vẫn hữu ích vì stock decrement và order insert phải commit/rollback cùng nhau.

Idempotency giải quyết một failure dimension khác concurrency inventory: cùng logical checkout bị gửi lại. Unique database constraint là arbiter cuối cùng cho idempotency key trong nhiều application instances.

Với multi-SKU, implementation cần transactionally reserve tất cả items hoặc rollback toàn bộ, update SKU theo thứ tự ổn định, và cân nhắc contention. Nếu contention cực cao, một architecture reservation khác có thể phù hợp, nhưng không nên nhảy sang queue/distributed lock khi conditional SQL update đã đáp ứng requirement.

## Trade-offs

Conditional update đơn giản, atomic và thường hiệu quả nhưng coupling business mutation gần SQL/provider hơn. Optimistic `rowversion` tích hợp tự nhiên với tracked entities nhưng conflict handling phức tạp hơn và có thể tạo retry pressure ở hot SKU. Higher isolation hoặc pessimistic locking có thể bảo vệ invariant nhưng tăng blocking/deadlock risk. Distributed lock thêm failure modes và thường không cần nếu SQL Server đã là source of truth cho inventory.

## Cách kiểm thử

1. **Concurrency integration test:** khởi chạy 50 checkout đồng thời cho SKU có stock 10; tổng confirmed quantity không vượt 10 và database quantity không âm.
2. **Database test:** xác nhận conditional update trả `0` khi stock không đủ và transaction không tạo order.
3. **Idempotency test:** gửi cùng idempotency key đồng thời từ nhiều requests; chỉ một logical order và một stock decrement tồn tại.
4. **Failure-path test:** inject failure sau stock update nhưng trước `SaveChanges`/commit; transaction rollback stock.
5. **Load/deadlock test:** multi-SKU orders với thứ tự input khác nhau; đo deadlocks, p95/p99 và bounded retry behavior.

## Quan sát trong production

Theo dõi checkout success/rejection, out-of-stock rate, concurrency conflict/unique violation count, deadlock count, SQL lock waits, transaction duration, p95/p99 checkout latency và inventory invariant violations. Structured logs nên có order/request correlation, SKU và outcome category nhưng không chứa payment/secrets. Alert nên dựa trên bất thường như quantity âm, duplicate idempotency outcome hoặc deadlock spike chứ không chỉ exception count tổng quát.

## Câu hỏi phỏng vấn mở rộng

1. Nếu inventory được phân bổ theo warehouse thay vì một row/SKU, bạn thay đổi invariant và data model thế nào?
2. Khi flash sale có một SKU cực nóng, conditional update vẫn đúng nhưng contention cao; bạn sẽ thu thập evidence gì trước khi đổi architecture?
3. Nếu payment xảy ra sau reservation stock, bạn thiết kế expiration/release reservation và reconciliation thế nào khi payment outcome không chắc chắn?

# Code Review Challenge 2 — Kubernetes probes khiến rolling deployment gửi traffic vào Pod chưa sẵn sàng và restart khi dependency chậm

**Chủ đề:** Kubernetes, ASP.NET Core, readiness/liveness/startup probes, rolling deployment, dependency degradation, resource limits, graceful termination  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–11 vấn đề quan trọng

## Bối cảnh

Một ASP.NET Core product-catalog API được chuyển từ Azure App Service sang Kubernetes. Pod cần khoảng 20–45 giây để warm local caches và load configuration. API phụ thuộc SQL Server và Elasticsearch; search có thể degraded mà product-detail API vẫn phục vụ được từ SQL.

Sau release, team thấy rolling deployment đôi lúc tăng `5xx`; khi Elasticsearch latency tăng, một số Pods restart liên tục. Manifest hiện dùng cùng `/health` endpoint cho readiness và liveness. Endpoint `/health` trả unhealthy nếu bất kỳ dependency nào không reachable. Container có memory limit nhưng chưa có requests rõ ràng. Application shutdown có thể cần tới 20 giây để dừng nhận work và hoàn tất một số in-flight requests.

## Đoạn code cần review

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 0
  selector:
    matchLabels:
      app: catalog-api
```

## Kết quả code review tham khảo

### Critical — Liveness phụ thuộc SQL/Elasticsearch có thể tạo restart loop khi dependency degraded

**Vấn đề:** `/health` fail khi dependency fail và cùng endpoint được dùng cho liveness.

**Tại sao xảy ra:** Kubelet diễn giải repeated liveness failure như container cần restart. Restart application không sửa được Elasticsearch outage.

**Ảnh hưởng production:** Dependency degradation có thể biến thành application-wide restart storm, giảm capacity và làm incident nặng hơn.

**Cách sửa:** Liveness chỉ kiểm tra process có còn sống/không bị unrecoverable deadlock theo semantics phù hợp. Không đưa remote dependency vào liveness chỉ để phản ánh dependency health.

### High — Không có startup probe dù startup có thể 45 giây

**Vấn đề:** Liveness bắt đầu sau 10 giây và có thể fail trước khi app warm xong.

**Tại sao xảy ra:** `initialDelaySeconds` cố đoán startup time thay vì có startup gate riêng.

**Ảnh hưởng production:** Slow/cold startup có thể bị kill lặp lại và không bao giờ trở thành ready.

**Cách sửa:** Dùng `startupProbe` với budget phù hợp startup worst-case đã đo. Khi startup probe chưa succeed, liveness/readiness semantics được quản lý phù hợp bởi Kubernetes.

### High — Readiness gộp Elasticsearch thành hard dependency dù API có degraded mode

**Vấn đề:** Toàn Pod bị remove khỏi Service endpoints khi search dependency fail, dù product-detail vẫn phục vụ được.

**Tại sao xảy ra:** Một aggregate endpoint không phản ánh capability-specific degradation.

**Ảnh hưởng production:** Mất toàn bộ serving capacity vì một optional/degradable dependency.

**Cách sửa:** Readiness phải phản ánh minimum dependencies cần để instance phục vụ traffic theo routing contract. Nếu endpoint classes có dependency khác nhau, cân nhắc application-level degradation/circuit breaker hoặc routing architecture; không dùng một probe để mô hình hóa mọi feature.

### High — Termination grace ngắn hơn drain requirement

**Vấn đề:** `terminationGracePeriodSeconds: 10` trong khi app có thể cần 20 giây để hoàn tất in-flight requests.

**Tại sao xảy ra:** Pod có thể bị force-kill trước khi graceful shutdown hoàn tất.

**Ảnh hưởng production:** Request bị reset/failed trong rollout; background/in-flight work có thể bị bỏ dở tùy semantics.

**Cách sửa:** Chọn grace period dựa trên measured drain/shutdown budget và application timeout contract; application phải tôn trọng cancellation và ngừng nhận work mới.

### High — Rollout strategy giảm capacity trong khi Pod mới warm chậm

**Vấn đề:** Với 3 replicas, `maxUnavailable: 1` và `maxSurge: 0` cho phép capacity giảm trong rollout và không tạo Pod bổ sung trước khi thay thế.

**Tại sao xảy ra:** Strategy tối ưu resource footprint hơn availability.

**Ảnh hưởng production:** Khi traffic gần capacity hoặc Pod mới warm lâu, rollout có thể làm latency/5xx tăng.

**Cách sửa:** Nếu cluster capacity cho phép và availability quan trọng, cân nhắc `maxUnavailable: 0` cùng `maxSurge` > 0. Quyết định dựa trên capacity/SLO, không theo template máy móc.

### Medium — Không có CPU/memory requests

**Vấn đề:** Chỉ có memory limit.

**Tại sao xảy ra:** Scheduler thiếu resource request để placement/QoS phản ánh nhu cầu dự kiến.

**Ảnh hưởng production:** Pod placement và contention có thể khó dự đoán; startup/latency biến động dưới node pressure.

**Cách sửa:** Đặt requests dựa trên measured working set/CPU; giữ limits theo policy và kiểm chứng bằng load test.

### Medium — `latest` làm artifact identity không immutable

**Vấn đề:** Deployment dùng mutable tag.

**Tại sao xảy ra:** Cùng manifest/tag có thể resolve image khác theo registry/pull behavior.

**Ảnh hưởng production:** Khó audit, reproduce và rollback chính xác.

**Cách sửa:** Dùng immutable version tag hoặc digest do CI/CD phát hành; promote cùng artifact giữa environments.

### Medium — Probe timeout/budget chưa được chứng minh bằng telemetry

**Vấn đề:** `timeoutSeconds: 1` và thresholds có vẻ chọn tùy ý.

**Tại sao xảy ra:** Probe budget không gắn với measured application startup/health handler latency.

**Ảnh hưởng production:** Transient CPU pressure có thể tạo false negative và churn.

**Cách sửa:** Health endpoint phải cực nhẹ; chọn timeout/threshold từ observed behavior và SLO. Không kéo remote dependency chậm vào liveness.

### Medium — Một aggregate health endpoint làm mất semantic separation

**Vấn đề:** `/health` vừa phục vụ startup/readiness/liveness vừa tổng hợp dependencies.

**Tại sao xảy ra:** Health checks được thiết kế như dashboard trạng thái thay vì control-plane signal.

**Ảnh hưởng production:** Một failure signal kích hoạt hành động sai ở orchestrator.

**Cách sửa:** Map endpoints/tags riêng như `/health/live`, `/health/ready`, `/health/startup` với registrations/predicates phù hợp. Dependency diagnostics sâu có thể tồn tại riêng nhưng không nhất thiết dùng làm liveness.

## Phiên bản đề xuất

Ví dụ sau minh họa separation; exact thresholds phải được điều chỉnh từ startup/drain measurements của hệ thống thực tế.

```csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddSqlServer(connectionString, tags: ["ready"]);

app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});

app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});
```

Nếu SQL cũng có degraded behavior thì readiness policy cần điều chỉnh theo requirement. Elasticsearch có thể được monitor bằng dependency telemetry/diagnostic health riêng thay vì bắt buộc loại toàn Pod khỏi service khi search vẫn có fallback.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: catalog-api
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: catalog-api
          image: registry.example/catalog-api:2026.09.21.1
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "250m"
              memory: "256Mi"
            limits:
              memory: "512Mi"
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
spec:
  selector:
    app: catalog-api
  ports:
    - port: 80
      targetPort: 8080
```

Các resource values ở trên là scenario values để review cấu trúc, không phải recommendation phổ quát. Production phải derive từ profiling/load data và cluster policy.

## Giải thích thiết kế sau khi sửa

`startupProbe` cho process thời gian khởi động trước khi liveness có quyền kết luận container cần restart. `readinessProbe` quyết định Pod có nên nhận traffic; dependency nào xuất hiện ở đây phải thực sự cần thiết cho serving contract. `livenessProbe` không phải dependency monitor.

Rollout strategy ưu tiên giữ capacity bằng `maxUnavailable: 0` và cho phép một surge Pod, đổi lại cần cluster headroom. Grace period được tăng vượt drain requirement giả định 20 giây, nhưng vẫn phải phối hợp với application shutdown, ingress/service endpoint removal và request timeout.

Image được version hóa để deployment/rollback xác định đúng artifact. Resource requests phải được hiệu chỉnh bằng evidence thay vì copy sample values.

## Trade-offs

Readiness quá strict giảm chance phục vụ lỗi nhưng có thể loại toàn bộ capacity khi shared dependency fail. Readiness quá loose giữ Pod nhận traffic nhưng có thể trả lỗi nếu application không có degradation strategy. Surge rollout cần thêm cluster resources. Startup budget dài tránh restart false-positive nhưng cũng kéo dài thời gian phát hiện startup thực sự bị treo. Graceful termination dài tăng deployment time nhưng giảm dropped requests.

## Cách kiểm thử

1. **Deployment validation:** rolling deploy dưới representative load; theo dõi ready endpoints và xác nhận không tăng 5xx do capacity gap.
2. **Failure-path test:** làm Elasticsearch unavailable; Pods không restart hàng loạt và product-detail path vẫn hoạt động nếu đó là contract.
3. **Startup test:** inject startup 45 giây; Pod không bị liveness kill trước khi startup budget hết.
4. **Graceful-shutdown test:** terminate Pod khi có long request 15–20 giây; xác nhận drain behavior theo timeout contract.
5. **Load/resource test:** đo CPU, working set, OOM/restart, throttling/latency để hiệu chỉnh requests/limits và replica capacity.

## Quan sát trong production

Theo dõi Pod restart count/reason, readiness transitions, rollout duration, unavailable replicas, OOMKilled events, CPU/memory working set, request p95/p99/5xx, dependency latency/error theo SQL/Elasticsearch, shutdown duration và connection resets. Application Insights hoặc tracing nên tách dependency failures khỏi process-health failures. Kubernetes events và deployment status cần được correlate với release version để phân biệt regression ứng dụng với cluster/dependency incident.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SQL unavailable nhưng catalog có thể phục vụ read-only từ cache trong 5 phút, readiness nên phản ánh requirement đó thế nào?
2. Nếu cluster không có headroom cho `maxSurge: 1`, bạn cân bằng rollout availability với infrastructure cost ra sao?
3. Liveness endpoint chỉ trả `200` có thể bỏ sót process deadlock/starvation nào, và bạn sẽ cải thiện detection mà không biến probe thành dependency fan-out thế nào?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Database transaction không tự động biến một chuỗi **read → check → write** thành atomic business invariant; concurrency correctness cần được thiết kế tại mutation boundary.
- Idempotency và concurrency control giải quyết hai failure dimensions khác nhau: duplicate logical operation và concurrent state mutation.
- Kubernetes liveness, readiness và startup probes là control-plane signals với semantics khác nhau; dùng chung dependency-heavy endpoint có thể tạo cascading failure.
- Rolling deployment phải được review cùng startup time, capacity headroom, readiness và graceful termination, không chỉ nhìn manifest từng field độc lập.
- Correctness cần được chứng minh bằng concurrency/failure tests và production telemetry, không chỉ bằng happy-path unit tests.

## Mẫu tư duy cần nhớ

- Đưa business precondition càng gần atomic mutation càng tốt.
- Phân biệt transaction boundary, idempotency boundary và external failure boundary.
- Một health signal chỉ hữu ích khi action kích hoạt bởi signal đó thực sự giúp hệ thống hồi phục.
- Review deployment theo timeline: start → ready → receive traffic → terminate → drain.
- Test failure path và concurrency path, không suy luận correctness từ code nhìn có vẻ tuần tự.
