# Câu 1 — Vì sao Elasticsearch trả kết quả khác nhau dù PostgreSQL đã commit?

**Loại câu hỏi:** Internal mechanism + practical behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 12–15 phút  
**Kỹ năng được đánh giá:** Elasticsearch refresh, inverted index, consistency, PostgreSQL transactions, search API, debugging.

## Bối cảnh

Một nền tảng quản lý nội dung lưu bài viết trong PostgreSQL; ASP.NET Core API cập nhật trạng thái `Published` rồi gửi thay đổi đến Elasticsearch. Vue.js gọi API tìm kiếm ngay sau khi người biên tập bấm Publish. Trong môi trường thử nghiệm, bài viết thường xuất hiện tức thì; production đôi lúc phải chờ vài giây. Có trường hợp bài viết đã bị unpublish vẫn còn trong kết quả tìm kiếm. Hệ thống có nhiều API instances, indexer chạy bất đồng bộ và lưu lượng khoảng 2 triệu truy vấn tìm kiếm/ngày. Không có bằng chứng PostgreSQL mất dữ liệu.

## Câu hỏi chính

Hãy giải thích các cơ chế có thể khiến kết quả tìm kiếm không phản ánh ngay transaction vừa commit; phân biệt độ trễ bình thường với lỗi đồng bộ, thiết kế cách xác minh và chọn giải pháp theo yêu cầu nghiệp vụ.

## Câu hỏi làm rõ nên cân nhắc

1. UI yêu cầu read-your-writes ngay lập tức hay chấp nhận độ trễ vài giây? Nội dung chưa xuất bản có ràng buộc bảo mật không?
2. PostgreSQL → Elasticsearch được cập nhật qua transaction, Outbox, queue, polling hay gọi trực tiếp? Có retry và DLQ không?
3. Tìm kiếm theo `text`, `keyword`, filter trạng thái, alias hay nhiều indices? Có cache tại API/CDN không?
4. Có nhiều lần cập nhật cùng document, message đến sai thứ tự, hoặc thay đổi mapping/reindex gần đây không?
5. Độ trễ xảy ra với một document hay toàn bộ index, và có trùng thời điểm indexing backlog không?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt nguồn dữ liệu có thẩm quyền với bản sao phục vụ truy vấn.

### Gợi ý 2
Xem xét quá trình index, refresh, visibility, event delivery và cache riêng biệt.

### Gợi ý 3
Thử theo dõi một `documentId` xuyên suốt DB commit → event → indexing response → search visibility; kiểm tra thứ tự version của các event.

## Cấu trúc trả lời đề xuất

1. Xác định contract nhất quán và mức rủi ro hiển thị nội dung.
2. Giải thích PostgreSQL commit, asynchronous replication, Elasticsearch refresh.
3. Liệt kê giả thuyết: refresh latency, queue lag, dropped event, out-of-order, alias/cache.
4. Đề xuất phép đo có correlation ID và document version.
5. Chọn write/read strategy; kiểm thử failure path và đánh đổi.

## Ý chính của câu trả lời tốt

### Bắt buộc
- PostgreSQL commit không đồng nghĩa Elasticsearch đã index hoặc search thấy document.
- Elasticsearch near-real-time search phụ thuộc refresh; indexing acknowledgement và search visibility là hai mốc khác nhau.
- Kiểm tra pipeline đồng bộ và cache thay vì kết luận mọi lỗi đều do refresh.
- Nếu unpublished content nhạy cảm, search index không được là tầng authorization duy nhất.

### Điểm cộng
- Transactional Outbox, idempotent consumer, version ordering, DLQ và reconciliation.
- Đo `commit_to_index_ms`, `index_to_visible_ms`, queue age, refresh/indexing failures.
- Giải thích `refresh=wait_for` chỉ giúp chờ refresh cho write tương ứng; không biến toàn bộ luồng DB→queue→index thành atomic transaction.

### Senior+
- Nêu ranh giới nhất quán, chiến lược migration/reindex bằng alias, kiểm soát ordering và authorization tại authoritative source khi cần.
- Đưa ra SLO rõ ràng và cách kiểm chứng end-to-end dưới retry, crash và reordering.

## Hướng giải quyết tham khảo

**Giả định:** PostgreSQL là system of record; Elasticsearch là read model phục vụ full-text search. Không giả định mọi bản ghi có thể công khai trước khi search đồng bộ.

**Cơ chế:** Transaction PostgreSQL chỉ commit trạng thái trong DB. Nếu event được gửi sau commit mà tiến trình chết trước khi gửi, Elasticsearch có thể không bao giờ nhận cập nhật. Nếu event đã đến, Elasticsearch vẫn có khoảng thời gian từ index đến refresh khiến search chưa nhìn thấy bản mới. Truy vấn theo `keyword` trên field `text`, sai analyzer, stale alias hoặc API cache có thể gây triệu chứng giống nhau. Event update và unpublish có thể xử lý đảo thứ tự nếu nhiều worker và retry, làm document quay về phiên bản cũ.

**Xác minh:** Ghi `documentId`, `version`, `dbCommittedAt`, `eventPublishedAt`, `indexedAt` và kết quả probe tìm kiếm (không log nội dung nhạy cảm). Đọc PostgreSQL để xác minh version; kiểm tra Outbox pending, queue oldest-message age, DLQ, indexing error, Elasticsearch index alias, `_id`/version, và API/CDN response headers. Dùng truy vấn theo ID để phân biệt document chưa index với full-text analyzer/filter không match. Đo độ trễ phân vị p50/p95/p99 theo từng chặng.

**Thiết kế:** Ghi bài viết và Outbox event trong cùng PostgreSQL transaction. Publisher phát event ít nhất một lần; consumer xử lý idempotent theo `documentId + version`, bỏ qua event cũ và retry có backoff; event độc hại chuyển DLQ kèm cảnh báo. Reconciliation định kỳ so sánh version trong DB và index để sửa sai lệch. Khi publish, UI có thể hiện trạng thái “đang cập nhật tìm kiếm” thay vì cam kết tức thì. Nếu bắt buộc read-your-writes cho người biên tập, endpoint chi tiết đọc trực tiếp PostgreSQL; search vẫn eventual. Với unpublish hoặc quyền truy cập, backend phải enforce authorization và trạng thái từ nguồn đáng tin cậy trước khi trả nội dung nhạy cảm; cân nhắc immediate denylist/authoritative filter và không dựa duy nhất vào delayed index.

**Lựa chọn thay thế:** Gọi index đồng bộ với `refresh=wait_for` có thể phù hợp với volume thấp và UX yêu cầu search visibility ngay sau index, nhưng tăng latency, coupling và vẫn không giải quyết atomicity với PostgreSQL. Không nên gọi refresh thủ công cho mọi write vì chi phí. Với hệ thống nhỏ, polling + reconciliation có thể đơn giản hơn triển khai queue mới. Reindex qua index mới, xác minh mapping và alias switch sau khi backfill, có kế hoạch rollback.

**Kiểm thử:** Integration test tạo/sửa/unpublish, xác minh eventual visibility theo deadline; kill publisher giữa DB commit và publish; gửi duplicate/out-of-order events; đổi alias trong reindex; security test đảm bảo bài unpublish không bị lộ qua API dù index stale. **Giám sát:** queue age, Outbox age, DLQ count, indexing failure, version mismatch, search p95 và số lần authorization lọc kết quả stale.

**Tài liệu tham khảo:** [Elasticsearch refresh](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/refresh-parameter); [Elasticsearch optimistic concurrency control](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/optimistic-concurrency-control).

## Mẫu trả lời trong phỏng vấn

“Em sẽ xác nhận yêu cầu nhất quán trước: biên tập viên cần nhìn thấy bài mới ngay, hay tất cả người dùng phải thấy ngay? PostgreSQL commit chỉ đảm bảo transaction của DB, còn Elasticsearch là bản sao tìm kiếm. Có hai loại độ trễ khác nhau: event chưa đến indexer và document đã index nhưng chưa refresh để search nhìn thấy. Em sẽ trace một document theo version qua DB, Outbox, queue, indexer và search, rồi kiểm tra cache và alias để loại trừ các nguyên nhân khác. Với hệ thống có retry, em ưu tiên Outbox, consumer idempotent và reconciliation. UI có thể chấp nhận eventual search nhưng quyền truy cập và trạng thái unpublish phải được kiểm soát bằng nguồn dữ liệu đáng tin cậy. Nếu yêu cầu read-your-writes nghiêm ngặt, em tách endpoint chi tiết đọc DB hoặc cân nhắc đồng bộ index có chờ refresh với đánh đổi latency và availability. Cuối cùng em kiểm thử crash, duplicate, out-of-order và đo p95 lag.”

## Câu hỏi đào sâu

1. Nếu unpublish cần có hiệu lực trong 200 ms, thiết kế nào không phụ thuộc vào refresh của Elasticsearch?
2. Nếu event version 12 đến trước version 11, bạn ngăn dữ liệu quay ngược bằng cách nào khi consumer chạy song song?
3. Khi nào bạn bỏ Elasticsearch và dùng PostgreSQL full-text search để giảm complexity?

## Lỗi trả lời thường gặp

- Không kiểm tra alias, analyzer, cache hoặc event ordering.
- Thiếu metric để phân biệt queue lag và refresh lag.

# Câu 2 — Sau rollout Octopus Deploy, IIS trả 503 theo từng đợt

**Loại câu hỏi:** Production incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 15–20 phút  
**Kỹ năng được đánh giá:** IIS, Windows Server, ASP.NET MVC legacy, deployment safety, Application Pool, telemetry, incident response.

## Bối cảnh

Website thương mại điện tử ASP.NET MVC trên .NET Framework 4.5 chạy hai Windows Server/IIS nodes sau load balancer. TeamCity build artifact, Octopus Deploy rollout theo từng node. Sau release, khoảng 8% request trả HTTP 503, chủ yếu lúc lưu lượng tăng. Một số khách bị mất giỏ hàng; CPU bình quân vẫn dưới 50%. Rollback được cho phép nhưng database vừa chạy migration thêm cột. Product yêu cầu ưu tiên giữ checkout hoạt động. Không rõ 503 do IIS, load balancer, app code hay dependency.

## Câu hỏi chính

Bạn là incident lead: trong 30 phút đầu, bạn sẽ giảm tác động, thu thập bằng chứng, phân biệt nguyên nhân và quyết định rollback/hotfix như thế nào; sau đó ngăn tái diễn ra sao?

## Câu hỏi làm rõ nên cân nhắc

1. 503 do IIS trên node hay do load balancer? Có response header, node ID, request ID và timestamps không?
2. 503 tập trung node mới, URL checkout hay tất cả endpoint? Có thay đổi app pool, web.config, session mode không?
3. Application Pool có rapid-fail protection, recycle, queue saturation, memory pressure hoặc worker process crash không?
4. Migration có backward compatible với artifact cũ không? Có thay đổi contract của external payment provider?
5. Giỏ hàng/session lưu InProc, SQL Server hay distributed store; sticky sessions có được cấu hình không?

## Gợi ý tư duy

### Gợi ý 1
Đừng bắt đầu bằng “tăng CPU/RAM”; khoanh vùng blast radius và nguồn trả 503.

### Gợi ý 2
So sánh per-node health, app pool state, worker process, IIS logs, Windows Event Viewer và deployment timeline.

### Gợi ý 3
Xem xét khác biệt artifact/config, app pool recycle và session affinity khi drain/rollback node.

## Cấu trúc trả lời đề xuất

1. Xác định mức độ ảnh hưởng checkout, error budget, payment double-submit.
2. Stabilize: tạm dừng rollout, route khỏi node lỗi, giảm traffic và bảo vệ session.
3. Thu bằng chứng đồng bộ theo node, thời gian, release và request ID.
4. Đặt giả thuyết có phép kiểm chứng; xác định nguồn 503.
5. Chọn rollback/hotfix có đánh giá migration và session compatibility.
6. Validate chức năng thanh toán, theo dõi phục hồi, RCA và phòng ngừa.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Pause rollout, kiểm tra health từng node, có kế hoạch rollback an toàn.
- Phân biệt IIS-generated 503 với upstream-generated 503.
- Không suy luận CPU trung bình thấp nghĩa là không có resource bottleneck.
- Không rollback database schema một cách mù quáng.

### Điểm cộng
- IIS HTTPERR logs, IIS W3C logs, Windows Event Viewer, app pool rapid-fail, WAS/W3SVC events.
- Session persistence, drain connections, checkout idempotency, synthetic transaction.
- Correlate deploy ID, artifact hash, config diff và per-node telemetry.

### Senior+
- Đưa ra decision tree với stop condition, owner, timebox, reversible steps và communication.
- Thiết kế expand/contract migrations, rolling release gates, runbook và fault injection.

## Hướng giải quyết tham khảo

**Tác động và ổn định:** Tuyên bố incident theo tiêu chí checkout failure, ghi thời điểm release và freeze các deployment khác. Nếu chỉ node vừa cập nhật lỗi, tạm rút node khỏi load balancer theo graceful drain, kiểm tra session impact trước khi cắt hoàn toàn. Nếu cả hai node lỗi, xem xét dependency chung, DB và cấu hình. Ưu tiên tránh duplicate payment bằng idempotency key hoặc kiểm tra trạng thái giao dịch phía provider trước khi retry.

**Bằng chứng:** Phân loại HTTP 503 theo node, URL, status/substatus, thời điểm và origin; so sánh IIS access logs, HTTPERR, Event Viewer, app pool state, WAS errors, worker-process crash/recycle, memory/handles, request queue length, SQL connection failures và dependency latency. Xác minh load balancer health probes và timeout. CPU bình quân 50% không loại trừ queue overflow, deadlock, thread starvation hoặc giới hạn tài nguyên cục bộ.

**Các giả thuyết cạnh tranh:**
- Application Pool stop/crash hoặc rapid-fail protection: kiểm tra WAS/Event Viewer và crash dumps có kiểm soát.
- IIS request queue đầy hoặc worker process không nhận request: HTTPERR queue entries, request queue length và thread dumps.
- Load balancer đánh dấu node unhealthy: probe status, routing logs và backend health.
- Deployment/config mismatch: so sánh artifact hash, web.config, secrets, binding, identity và file permissions giữa hai nodes.
- DB/dependency regression: kiểm tra dependency duration, pool saturation, SQL blocking và các thay đổi migration.
- Session InProc bị mất khi recycle/route: đối chiếu session configuration, sticky session và cart state.

**Rollback/hotfix:** Chỉ rollback application artifact nếu schema migration đã backward compatible. Nếu schema đã phá tương thích, chọn forward-fix hoặc compatibility patch; không drop cột hoặc reverse migration không kiểm chứng. Nếu app pool config sai, rollback config có thể nhanh và ít rủi ro hơn rollback code. Dùng canary một node, synthetic checkout (không tạo charge thật), kiểm tra cart persistence, payment status và p95/503 rate trước khi mở traffic.

**Ngăn tái diễn:** Expand/contract schema; smoke test và health check đo dependency thiết yếu; deployment theo từng node có automatic gate và khả năng drain; giữ artifact immutable và config diff; phân tách readiness với liveness; session externalization khi cần; circuit breaker/timeouts cho third-party; rollback rehearsal. Không tự động recycle app pool liên tục để che lỗi.

**Kiểm thử:** Deploy thử artifact cũ với schema mới; rolling restart trong khi user giữ cart; load test queue saturation; giả lập SQL timeout và payment provider chậm; E2E checkout với idempotency. **Monitoring:** 503 per node, checkout conversion, HTTPERR queue errors, WAS events, worker restarts, session-loss, SQL waits, dependency p95 và synthetic checkout.

## Mẫu trả lời trong phỏng vấn

“Trong 30 phút đầu em ưu tiên checkout availability và tránh thanh toán trùng. Em sẽ dừng rollout, xác định 503 xuất phát từ IIS hay load balancer, chia số liệu theo node và release. Nếu node mới lỗi, em drain traffic khỏi node đó trước khi điều tra sâu, nhưng phải kiểm tra giỏ hàng có dùng InProc session hay không. Song song em xem HTTPERR, IIS logs, WAS/Event Viewer, app pool crash/recycle, request queue và dependency latency. Em không kết luận từ CPU trung bình vì có thể request bị xếp hàng hoặc app pool ngừng. Quyết định rollback phải kiểm tra migration có backward compatible; nếu không, ưu tiên compatibility hotfix. Sau khi ổn định em rollout lại bằng canary, synthetic checkout và gate theo error rate, rồi hoàn thành RCA, load/failure tests và runbook.”

## Câu hỏi đào sâu

1. Nếu lỗi chỉ xuất hiện sau 15 phút và không tái hiện ở staging, bạn thu thập dump/trace thế nào mà không làm gián đoạn checkout?
2. Nếu migration mới đã đổi tên cột và code cũ không còn chạy, phương án phục hồi nào an toàn nhất?
3. Nếu cart lưu InProc session, chiến lược draining/rolling restart phải thay đổi thế nào?

## Lỗi trả lời thường gặp

- Restart toàn bộ IIS ngay khi thấy 503, làm mất thêm session và chứng cứ.
- Chỉ xem Application Insights mà bỏ qua HTTPERR/WAS và load balancer.
- Rollback app và DB đồng thời không kiểm tra tương thích schema.
- Không kiểm tra payment duplicate và cart loss.
- Không xác nhận recovery bằng user-facing business metrics.

| Tiêu chí | Điểm |

# Câu 3 — Thiết kế backend phân phối nội dung Optimizely CMS qua Akamai cho đa thị trường

**Loại câu hỏi:** Architecture / engineering decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 20–25 phút  
**Kỹ năng được đánh giá:** Optimizely CMS, ASP.NET Core, Akamai CDN, Vue.js, SEO, cache invalidation, security, deployment, architecture trade-offs.

## Bối cảnh

Một doanh nghiệp có website marketing đa thị trường, nội dung do editor quản lý trong Optimizely CMS. Frontend mới cân nhắc Vue.js; website cũ là server-rendered ASP.NET MVC. Product muốn nội dung được cập nhật nhanh sau Publish, SEO tốt, preview riêng tư và có thể phục vụ khoảng 300.000 page views/ngày. Một số trang có product price/availability từ e-commerce API, phần còn lại là content tĩnh. Website triển khai trên Azure App Service; Akamai đứng trước origin. Team có 5 engineers, chưa có dedicated platform team. Yêu cầu ngân sách và độ trễ publish chưa được chốt.

## Câu hỏi chính

Bạn sẽ chọn kiến trúc rendering, content delivery, caching và deployment nào để cân bằng SEO, editorial workflow, freshness, reliability và complexity? Trình bày ít nhất hai phương án có thể bảo vệ được.

## Câu hỏi làm rõ nên cân nhắc

1. Thời gian từ Publish đến public visibility tối đa bao nhiêu, và preview có cần xem draft theo từng user/role không?
2. Nội dung theo locale/market/segment; có cá nhân hóa hay giá theo tài khoản không?
3. SEO cần index trang động nào; bot có nhận HTML đầy đủ và canonical/hreflang đúng không?
4. Price/availability yêu cầu độ mới và consistency ra sao? E-commerce API có SLO/rate limit nào?
5. Có chấp nhận dual runtime frontend/backend, cache purge cost và vận hành thêm SSR server không?

## Gợi ý tư duy

### Gợi ý 1
Phân loại dữ liệu theo tính công khai, độ biến động và khả năng cache.

### Gợi ý 2
Phân biệt editor preview với public delivery, và static content với live commerce data.

### Gợi ý 3
Xem xét SSR/SSG/traditional rendering, cache keys, purge event, fallback và SEO verification.

## Cấu trúc trả lời đề xuất

1. Chốt SLO freshness, SEO, personalization và preview.
2. Phân loại page types, blocks, product fragments, locale và auth.
3. So sánh traditional CMS rendering với headless + Vue SSR/SSG.
4. Xác định API/data ownership, cache tiers và invalidation.
5. Thiết kế publish workflow, failure behavior và rollout.
6. Bảo mật preview, kiểm thử SEO, performance và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Phân biệt public HTML cacheable và private/preview/personalized responses.
- Không cache chung user-specific price/session/auth responses.
- SEO cần server-visible HTML hoặc prerender/SSR được kiểm chứng, không chỉ client-side rendering.
- Chọn architecture theo team capability và operational cost.

### Điểm cộng
- Content version/dependency-based invalidation, purge Akamai, stale-while-revalidate có điều kiện.
- Canonical/hreflang, redirects, sitemap, structured data và Lighthouse/Core Web Vitals.
- Graceful degradation khi e-commerce API lỗi, synthetic preview/public tests.

### Senior+
- Bảo vệ được cả phương án monolith truyền thống lẫn composable; nêu migration từng phần và rollback.
- Đề xuất measurable freshness SLO, CDN hit ratio, publish-to-visible latency và security boundary.

## Hướng giải quyết tham khảo

**Giả định:** Public marketing pages có thể cache theo locale, không chứa dữ liệu định danh. Giá cá nhân hóa và draft preview không được public cache. SLO freshness cần Product quyết định; tạm đề xuất đo và thử mục tiêu p95 dưới 60 giây, không cam kết đó là khả năng sẵn có của nền tảng.

**Phương án A — Traditional/server-rendered CMS:** Dùng Optimizely CMS render HTML trên ASP.NET Core (hoặc duy trì MVC cũ trong giai đoạn migration nếu compatibility bắt buộc), Akamai cache HTML public và static assets. Ưu điểm: ít runtime, editor preview tự nhiên hơn, SEO dễ kiểm soát. Nhược điểm: frontend coupling với CMS, modernization chậm, cache invalidation theo content dependency vẫn cần thiết.

**Phương án B — Headless + Vue SSR/SSG:** Optimizely cung cấp content APIs, Vue SSR hoặc build/prerender public routes; Akamai cache output. Ưu điểm: component reuse và tách frontend, triển khai giao diện linh hoạt. Nhược điểm: thêm runtime/build pipeline, preview draft và content dependencies phức tạp, SEO/hydration và rollout phải kiểm thử. Nếu phần lớn site tĩnh, SSG + incremental rebuild có thể hợp lý; nếu content đổi liên tục, SSR với cache rõ ràng dễ đáp ứng hơn. Vue SPA client-only không nên là mặc định cho SEO-critical pages.

**Data model/boundaries:** Content types cho page, blocks, locale và metadata SEO; CMS sở hữu editorial content, commerce service sở hữu price/availability, identity service sở hữu authentication. API public có `GET /pages/{slug}?locale=...`, commerce endpoint riêng có caching policy theo mức độ nhạy cảm. Không trộn price cá nhân hóa vào CDN HTML public; có thể render placeholder và fetch giá riêng, hoặc SSR per-user với `private/no-store` khi cần. Không thiết kế microservices mới chỉ để tách các blocks.

**Cache:** Static assets fingerprinted với TTL dài; public HTML dùng TTL ngắn phù hợp SLO và Akamai purge theo URL/locale khi publish. Cache key chỉ gồm dimensions thực sự thay đổi response, tránh cache fragmentation; `Vary` và query normalization phải được kiểm tra. Preview dùng authenticated origin, `Cache-Control: private, no-store`, không cho Akamai cache, và authorization ở backend. Khi publish event thất bại, có retry, idempotent purge, dead-letter/alert và reconciliation để sửa stale pages; đừng coi purge acknowledgement là bằng chứng end-user đã thấy nội dung mới. Nếu Akamai lỗi, có kế hoạch origin bypass/traffic control đã thử nghiệm và bảo vệ origin khỏi surge.

**SEO và accessibility:** Server-rendered HTML có title, description, canonical, hreflang theo locale, sitemap, redirects 301/308 đúng ngữ cảnh, robots directives và structured data đã validate. Kiểm tra Lighthouse/LCP/CLS/INP, accessibility và crawl bằng Playwright/HTTP fetch không chạy JavaScript. Không cache lỗi 404/500 dài ngoài chủ đích.

**Reliability và deployment:** Azure App Service deployment slots hoặc rolling deployment với health checks, migration content schema có backward compatibility, feature flags cho frontend cutover, canary theo market. E-commerce API có timeout, circuit breaker, bounded retry và fallback “giá đang cập nhật” khi phù hợp nghiệp vụ; không hiển thị giá cũ như giá chính xác nếu pháp lý/checkout không cho phép. Checkout luôn xác nhận giá ở commerce backend. Dùng Managed Identity/Key Vault cho secrets khi tương thích môi trường.

**Lựa chọn:** Với team 5 người, nếu site hiện tại hoạt động và editorial workflow quan trọng, em chọn incremental modernization theo A, tách content APIs theo nhu cầu thực tế; chỉ chuyển sang B nếu product roadmap cần frontend độc lập, nhiều kênh hoặc tái sử dụng component đủ lớn để bù operational complexity. Đo trước khi thay đổi.

**Testing/monitoring:** Publish/update/unpublish/rollback; preview draft unauthorized; Akamai HIT/MISS và purge failure; cache cross-user leakage; SEO snapshots/crawl; load test origin under cache miss; chaos test commerce timeout. Telemetry: `publish_to_public_visible_ms`, purge error, CDN hit ratio, origin p95/p99, CMS API p95, commerce fallback rate, crawler 4xx/5xx, Core Web Vitals và content version mismatch.

**Tài liệu tham khảo:** [Akamai cache documentation](https://techdocs.akamai.com/property-mgr/docs/caching); [Google Search JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics); [Azure App Service deployment slots](https://learn.microsoft.com/en-us/azure/app-service/deploy-staging-slots).

# Tổng kết hôm nay

## Kiến thức trọng tâm

Ba góc nhìn bổ trợ: (1) phân biệt database truth, asynchronous indexing và search visibility; (2) xử lý incident IIS/Windows Server bằng chứng cứ và rollout safety thay vì restart theo phản xạ; (3) thiết kế CMS/CDN dựa trên freshness, authorization, SEO và năng lực vận hành, không dựa vào xu hướng công nghệ.

## Mẫu tư duy cần nhớ

1. **Define consistency before choosing synchronization:** read-your-writes và eventual consistency cần contract riêng.
2. **Stabilize, then investigate:** giới hạn blast radius, giữ evidence và kiểm tra rollback compatibility.
3. **Trace the full path:** commit → event → index → cache → user, hoặc request → load balancer → IIS → dependency.
4. **Separate public from private:** cache, preview và authorization là những boundary phải kiểm thử.
5. **Measure complexity against value:** chọn giải pháp đơn giản nhất đáp ứng SLO, với rollback và observability.
