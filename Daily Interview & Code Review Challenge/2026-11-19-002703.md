# Code Review Challenge 1 — Payment consumer xử lý trùng sau retry

**Chủ đề:** C#/.NET 8, Azure Service Bus, PostgreSQL, concurrency, idempotency  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 8

## Bối cảnh

Một backend ASP.NET Core nhận `PaymentCaptured` qua Azure Service Bus PeekLock, chạy 4 consumer instances, khoảng 80.000 messages/ngày. Mỗi `PaymentId` phải được ghi nhận đúng một lần; một order có thể nhận nhiều payment. Sau deployment, một số order có tổng thanh toán sai. Service Bus có thể redeliver khi lock hết hạn hoặc acknowledgement thất bại. Chưa có kết luận nguyên nhân.

## Đoạn code cần review

```csharp
public record PaymentCaptured(Guid PaymentId, Guid OrderId, decimal Amount);

public sealed class PaymentWorker(
    ServiceBusClient client, AppDbContext db,
    ILogger<PaymentWorker> logger)
{
    public async Task ExecuteAsync(CancellationToken ct)
    {
        var receiver = client.CreateReceiver("payments");
        while (!ct.IsCancellationRequested)
        {
            var message = await receiver.ReceiveMessageAsync(
                TimeSpan.FromSeconds(10), ct);
            if (message is null) continue;

            try
            {
                var evt = JsonSerializer.Deserialize<PaymentCaptured>(
                    message.Body.ToString())!;

                if (await db.Payments.AnyAsync(
                    x => x.Id == evt.PaymentId, ct))
                {
                    await receiver.CompleteMessageAsync(message, ct);
                    continue;
                }

                var order = await db.Orders.SingleAsync(
                    x => x.Id == evt.OrderId, ct);
                order.PaidAmount += evt.Amount;
                db.Payments.Add(new Payment {
                    Id = evt.PaymentId,
                    OrderId = evt.OrderId,
                    Amount = evt.Amount
                });

                await db.SaveChangesAsync(ct);
                await receiver.CompleteMessageAsync(message, ct);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Failed: {Body}",
                    message.Body.ToString());
                await receiver.AbandonMessageAsync(message);
            }
        }
    }
}
```

## Kết quả code review tham khảo

### [Critical] — Check-then-insert không phải idempotency

**Vấn đề:** Hai consumer cùng thấy payment chưa tồn tại rồi cùng insert.  
**Tại sao xảy ra:** `AnyAsync` không khóa business key.  
**Ảnh hưởng production:** Double apply hoặc unique violation nếu đã có constraint.  
**Cách sửa:** PRIMARY KEY/UNIQUE trên `PaymentId`, insert với `ON CONFLICT DO NOTHING`, chỉ apply amount khi insert thành công; so khớp payload nếu trùng ID.

### [Critical] — Lost update trên order aggregate

**Vấn đề:** Hai payment khác nhau đọc cùng `PaidAmount` và ghi đè.  
**Tại sao xảy ra:** Read-modify-write trên tracked entity không có concurrency control.  
**Ảnh hưởng production:** Thiếu tiền dù ledger có đủ records.  
**Cách sửa:** Atomic increment trong DB transaction hoặc optimistic concurrency với bounded retry.

### [High] — DB commit và broker ack không atomic

**Vấn đề:** Commit thành công rồi `CompleteMessageAsync` timeout sẽ redeliver.  
**Tại sao xảy ra:** Hai hệ thống không chia sẻ transaction.  
**Ảnh hưởng production:** Duplicate side effect nếu handler không idempotent.  
**Cách sửa:** Commit business effect trước ack; coi redelivery là bình thường; unique business key làm lần xử lý tiếp theo no-op.

### [High] — DbContext lifetime quá dài

**Vấn đề:** Context được tái sử dụng qua nhiều messages.  
**Tại sao xảy ra:** Change tracker tích lũy entity và state sau failure.  
**Ảnh hưởng production:** Stale state, memory growth, khó retry.  
**Cách sửa:** Một scope/DbContext mới cho mỗi message.

### [High] — Không phân loại transient/permanent failure

**Vấn đề:** Mọi exception đều abandon; lock có thể hết hạn và abandon cũng có thể lỗi.  
**Tại sao xảy ra:** Thiếu delivery-count, poison-message và lock-renewal policy.  
**Ảnh hưởng production:** Retry storm, backlog, DLQ tăng.  
**Cách sửa:** Validate payload, DLQ lỗi vĩnh viễn, retry lỗi transient với bounded policy; cấu hình lock renewal và MaxDeliveryCount.

### [High] — Log raw payment payload

**Vấn đề:** Body có thể chứa thông tin nhạy cảm.  
**Tại sao xảy ra:** Logging không data-minimization.  
**Ảnh hưởng production:** Data exposure.  
**Cách sửa:** Log message ID, payment ID, correlation ID, delivery count; không log body.

### [Medium] — Không validate amount/order

**Vấn đề:** Amount âm/zero, ID rỗng, order không tồn tại.  
**Tại sao xảy ra:** Tin tưởng input từ queue.  
**Ảnh hưởng production:** Invalid ledger hoặc poison messages.  
**Cách sửa:** Validate schema/version, amount, order ownership và trạng thái nghiệp vụ.

### [Medium] — Receiver lifecycle/shutdown thiếu

**Vấn đề:** Receiver không dispose; ack/abandon và graceful shutdown chưa được xử lý rõ.  
**Tại sao xảy ra:** Loop tự quản lý resource và lock.  
**Ảnh hưởng production:** Redelivery nhiều khi deploy hoặc restart.  
**Cách sửa:** `ServiceBusProcessor` hoặc `await using` receiver, cancellation, timeout và shutdown budget.

## Phiên bản đề xuất

Ví dụ cho PostgreSQL, EF Core, bảng `Payments` có PRIMARY KEY `Id`. Giả định `PaidAmount` là aggregate cần cập nhật đồng bộ và DB schema khớp tên bảng/cột. Message validation thực hiện trước handler. Consumer chỉ `CompleteMessageAsync` sau khi handler commit thành công.

```csharp
public sealed class PaymentHandler(
    IDbContextFactory<AppDbContext> factory)
{
    public async Task ApplyAsync(
        PaymentCaptured evt, CancellationToken ct)
    {
        if (evt.PaymentId == Guid.Empty ||
            evt.OrderId == Guid.Empty || evt.Amount <= 0)
            throw new InvalidDataException("Invalid payment");

        await using var db = await factory.CreateDbContextAsync(ct);
        await using var tx = await db.Database.BeginTransactionAsync(ct);

        var inserted = await db.Database.ExecuteSqlInterpolatedAsync(
            $"""
            INSERT INTO "Payments" ("Id", "OrderId", "Amount")
            VALUES ({evt.PaymentId}, {evt.OrderId}, {evt.Amount})
            ON CONFLICT ("Id") DO NOTHING
            """, ct);

        if (inserted == 0)
        {
            await tx.CommitAsync(ct);
            return;
        }

        var updated = await db.Orders
            .Where(x => x.Id == evt.OrderId)
            .ExecuteUpdateAsync(
                s => s.SetProperty(x => x.PaidAmount,
                    x => x.PaidAmount + evt.Amount), ct);

        if (updated != 1)
            throw new InvalidOperationException("Order not found");

        await tx.CommitAsync(ct);
    }
}
```

Consumer orchestration: `ServiceBusProcessor` với `AutoCompleteMessages = false`; deserialize/validate, gọi handler, sau commit mới complete. Lỗi payload không sửa được thì dead-letter với reason không chứa PII; transient error để retry. Cấu hình `MaxConcurrentCalls`, `MaxAutoLockRenewalDuration` và `MaxDeliveryCount` dựa trên đo đạc. Nếu duplicate `PaymentId` có payload khác, không silently accept: kiểm tra fingerprint và đưa vào reconciliation. SQL trên là PostgreSQL-specific và cần kiểm tra mapping/migration trước triển khai.

## Giải thích thiết kế sau khi sửa

Unique constraint enforce idempotency tại nguồn dữ liệu; transaction bao insert ledger và atomic increment để rollback cùng nhau. Atomic update tránh lost update giữa các payment khác nhau. Ack nằm ngoài transaction nên duplicate delivery vẫn có thể xảy ra nhưng không double-apply. Context per-message cô lập tracking và exception state.

## Trade-offs

Counter nhanh nhưng tạo row contention và cần reconciliation; tổng hợp trực tiếp từ ledger giảm derived state nhưng tốn query. Giữ business keys lâu dài có storage cost. Lock renewal giảm false redelivery nhưng không thay thế idempotency. Nếu transaction rollback không rõ do network timeout, cần xác minh bằng business key trước retry.

## Cách kiểm thử

1. **Concurrency:** 100 messages cùng `PaymentId` trên nhiều instances; chỉ một ledger entry và một lần cộng.
2. **Concurrency:** 100 payments khác nhau cùng `OrderId`; tổng chính xác.
3. **Failure injection:** crash sau commit trước ack; redelivery không double-apply.
4. **Integration:** invalid amount, missing order, mismatched duplicate; rollback và DLQ/reconciliation đúng.
5. **Load:** đo p95 processing, DB lock waits, lock-lost, queue depth và throughput.

## Quan sát trong production

Structured logs với `MessageId`, `PaymentId`, `OrderId`, trace ID, không có raw payload. Metrics: processed, duplicates, invalid, lock-lost, DLQ count, queue age, DB transaction duration, row-lock waits, reconciliation mismatch. Alert trên DLQ growth và ledger/aggregate divergence; trace consumer → PostgreSQL.

## Câu hỏi phỏng vấn mở rộng

1. Nếu cùng `PaymentId` nhưng amount khác nhau, chọn canonical record thế nào?
2. Nếu cần publish `OrderPaid` sau DB commit, dùng Outbox Pattern ra sao?
3. Nếu order có hàng nghìn payments đồng thời, có nên bỏ stored counter không?

## Kết quả code review tham khảo

### [Critical] — Database credential hardcoded

**Vấn đề:** Password nằm trong manifest.  
**Tại sao xảy ra:** Không có secret boundary.  
**Ảnh hưởng production:** Credential có thể lộ qua Git hoặc pipeline.  
**Cách sửa:** Rotate secret; dùng Kubernetes Secret hoặc external secret store với RBAC và encryption at rest; Secret không tự bảo đảm bí mật với người có quyền đọc.

### [High] — Liveness/readiness đảo ngược

**Vấn đề:** Liveness gọi ready (có DB), readiness gọi live.  
**Tại sao xảy ra:** Nhầm giữa restart signal và traffic gating.  
**Ảnh hưởng production:** Nhận traffic quá sớm; DB outage có thể restart hàng loạt.  
**Cách sửa:** Liveness → `/health/live`; readiness → `/health/ready`.

### [High] — Rolling update giảm capacity

**Vấn đề:** Cho phép 2/3 Pods unavailable, không có surge.  
**Tại sao xảy ra:** Strategy không bảo toàn serving capacity.  
**Ảnh hưởng production:** 503/latency khi còn 1 ready Pod.  
**Cách sửa:** `maxUnavailable: 0`, `maxSurge: 1` nếu đủ node/quota; đo capacity trước.

### [High] — Image tag mutable

**Vấn đề:** `latest` không pin artifact.  
**Tại sao xảy ra:** Tag có thể bị cập nhật.  
**Ảnh hưởng production:** Rollback không reproducible.  
**Cách sửa:** Deploy image digest hoặc immutable version tag, lưu digest trong release metadata.

### [High] — Startup không được bảo vệ

**Vấn đề:** Liveness bắt đầu quá sớm so với startup 25–50 giây.  
**Tại sao xảy ra:** Không có startupProbe.  
**Ảnh hưởng production:** CrashLoopBackOff hoặc Pod không kịp ready.  
**Cách sửa:** Startup probe với budget dựa trên observed startup p99.

### [Medium] — Resource sizing thiếu cơ sở

**Vấn đề:** Không khai báo requests rõ; limits thấp có thể gây throttling/OOM.  
**Tại sao xảy ra:** Không có load profile; Kubernetes có thể default requests theo limits nếu không khai báo và không bị admission override.  
**Ảnh hưởng production:** Pending pods, CPU throttling hoặc OOMKilled.  
**Cách sửa:** Requests/limits dựa trên telemetry và quota.

### [Medium] — Graceful termination chưa xác minh

**Vấn đề:** Không có evidence về draining và shutdown budget.  
**Tại sao xảy ra:** Chưa test SIGTERM, endpoint propagation và in-flight work.  
**Ảnh hưởng production:** 502, interrupted requests.  
**Cách sửa:** ASP.NET Core graceful shutdown, terminationGracePeriodSeconds và test traffic khi rolling update.

### [Medium] — Thiếu deployment gate

**Vấn đề:** Apply YAML có thể được coi là release success.  
**Tại sao xảy ra:** Không có rollout status/SLO validation trong mô tả.  
**Ảnh hưởng production:** Broken release không được rollback kịp.  
**Cách sửa:** CI/CD wait rollout status, smoke test, monitor errors và rollback theo pinned digest.

## Giải thích thiết kế sau khi sửa

Startup probe cho ứng dụng thời gian khởi động; readiness chặn traffic đến Pod chưa phục vụ được; liveness chỉ restart process không tự phục hồi. Digest bảo đảm artifact identity; secret reference tách credential khỏi manifest. Rolling update giữ serving capacity nếu cluster có đủ tài nguyên. Cần xác minh app bind đúng port 8080 và readiness dependency phản ánh đúng nghiệp vụ.

## Trade-offs

`maxUnavailable: 0` cần surge capacity, có thể khiến rollout Pending khi quota thiếu. DB-dependent readiness có thể loại toàn bộ Pods trong DB outage; nếu API có degraded mode, cần thiết kế endpoint readiness tương ứng. Startup budget dài giảm false restart nhưng tăng thời gian phát hiện dead startup. Requests cao tăng chi phí; thấp quá tăng contention. Nếu hệ thống nhỏ, Azure App Service có thể giảm operational overhead so với Kubernetes.

## Cách kiểm thử

1. **Deployment validation:** pin digest, verify `kubectl rollout status`, available replicas và rollback.
2. **Failure injection:** ngắt DB, quan sát readiness/liveness và restart count.
3. **Startup:** cold start 50–70 giây không gây restart sai.
4. **Load + termination:** rolling update dưới tải, đo p95/p99, 502/503 và in-flight requests.
5. **Security:** quét repo/CI logs, kiểm tra RBAC và credential rotation.

## Quan sát trong production

Theo dõi ready/available replicas, Pod restarts, OOMKilled, CPU throttling, memory, rollout duration, ingress 502/503, API p95/p99 và dependency failures trong Application Insights. Gắn deployment revision/image digest vào logs/traces. Alert khi replicas dưới ngưỡng, rollout stuck hoặc error budget burn tăng. So sánh timestamps của readiness transitions, DB errors và ingress errors trước khi kết luận root cause.
