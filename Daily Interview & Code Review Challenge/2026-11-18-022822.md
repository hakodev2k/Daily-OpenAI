# Câu 1 — Elasticsearch SKU exact lookup bị bỏ sót dù document tồn tại

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20 phút  
**Kỹ năng được đánh giá:** Elasticsearch, analyzer, inverted index, mapping, query DSL

## Bối cảnh

Catalog .NET 8 lưu dữ liệu chuẩn ở PostgreSQL, tìm kiếm bằng Elasticsearch. Tìm tên sản phẩm ổn nhưng SKU AB-1200-X không xuất hiện với match query. Hàng triệu sản phẩm, nhiều lần cập nhật mỗi phút; chưa rõ mapping, analyzer, alias, refresh interval và tenant filter.

## Câu hỏi chính

Giải thích nội bộ quá trình indexing/query, các nguyên nhân cạnh tranh, cách kiểm chứng và thiết kế search đúng mà không làm giảm hiệu năng.

## Câu hỏi làm rõ nên cân nhắc

1. SKU cần exact, prefix, substring hay fuzzy search?
2. Mapping và analyzer/search_analyzer hiện tại của SKU là gì?
3. Query DSL và filter tenant/visibility thực tế ra sao?
4. Document có tồn tại trong đúng alias/index và đã refresh chưa?

## Gợi ý tư duy

### Gợi ý 1

Đừng đồng nhất chuỗi gốc với token được index.

### Gợi ý 2

So sánh text/keyword và match/term.

### Gợi ý 3

Dùng _mapping, _analyze, _explain và query không filter để phân lập nguyên nhân.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement, dữ liệu còn thiếu và giả định.
2. Phân tích cơ chế và các giả thuyết hoặc phương án cạnh tranh.
3. Chọn bằng chứng/measurement để kiểm chứng.
4. Đề xuất implementation, failure handling và trade-offs.
5. Định nghĩa testing, monitoring, rollout và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

text được analyze thành tokens; keyword lưu term nguyên vẹn (có thể dùng normalizer); match phân tích query còn term không phân tích input tương tự. Không khẳng định dấu gạch ngang luôn bị tách nếu chưa xem analyzer.

### Điểm cộng

Phân biệt lỗi tokenization, tenant filter, alias sai, lag indexing và missing document; đo precision/recall, p95 và query profile.

### Senior+

Thiết kế versioned index, reindex/backfill, đồng bộ delta, atomic alias switch, rollback và version chống ghi lùi.

## Hướng giải quyết tham khảo

Trước hết kiểm tra document bằng ID và alias, so sánh query có/không có filter, lấy mapping và chạy _analyze với analyzer thực tế. text có thể tokenize/lowercase nên match và term cho kết quả khác nhau; keyword thường phù hợp SKU exact, text phù hợp tên. Đề xuất SKU keyword với normalizer nếu cần case-insensitive; name text và multi-field keyword cho sort. Nếu cần prefix/autocomplete, đánh giá search_as_you_type hoặc edge n-gram trên dữ liệu mẫu; không mặc định wildcard *x* vì chi phí. Mapping không tương thích phải tạo index mới, backfill và bắt kịp delta có version, kiểm tra dữ liệu rồi đổi alias; giữ index cũ để rollback. PostgreSQL là nguồn chuẩn; Elasticsearch eventual consistency nên định nghĩa lag SLO. Filter tenant/visibility phải do server kiểm soát. Test exact SKU, casing, hyphen, tên, permission, update đồng thời, alias swap, latency và lag. Nếu nhu cầu chỉ exact lookup và DB đã đáp ứng SLO, cân nhắc không dùng search engine cho luồng đó.

## Mẫu trả lời trong phỏng vấn

Tôi không kết luận ngay là lỗi analyzer. Tôi kiểm tra document, alias, mapping, query DSL và filter trước; dùng _analyze để xem token thực tế. match phân tích query còn term tìm term chính xác, vì vậy SKU exact thường dùng keyword với normalization phù hợp, tên dùng text. Tôi đo relevance và latency trước khi sửa mapping. Nếu phải đổi mapping, tôi dùng index version mới, backfill, đồng bộ delta và đổi alias có rollback. Tôi cũng xác định search lag chấp nhận được và kiểm tra quyền tenant.

## Câu hỏi đào sâu

1. Nếu phải tìm substring giữa SKU, bạn chọn giải pháp nào và đo chi phí ra sao?
2. Nếu delta update đến sai thứ tự trong lúc reindex, ngăn ghi lùi thế nào?
3. Nếu Elasticsearch outage, catalog API degrade ra sao?

## Lỗi trả lời thường gặp

- Khẳng định match luôn exact.
- Đổi mọi field thành keyword.
- Dùng wildcard đầu chuỗi cho mọi query.
- Bỏ qua alias, filter tenant và indexing lag.

## Thang điểm 0–10

**Tiêu chí và trọng số:** Clarification 1.5; cơ chế 2.5; evidence 2; migration 2; trade-off/security/communication 2. Không chấm điểm chỉ vì nêu đúng tên công nghệ; cần chứng minh cơ chế, bằng chứng và trade-off.

# Câu 2 — Azure App Service tăng 502/503 sau release trong khi CPU thấp

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, App Service Linux, PostgreSQL, HTTP dependency, observability

## Bối cảnh

API checkout .NET 8 chạy trên hai Azure App Service Linux instances. Sau deploy, 502/503 tăng, p95 từ 300ms lên 9s, CPU 35%, memory bình thường. API gọi PostgreSQL và payment provider. App logs thiếu một số request lỗi. Có deployment slot nhưng chưa rõ schema compatibility, health probes, pool limits hay retry behavior.

## Câu hỏi chính

Lập kế hoạch điều tra và khôi phục theo impact → stabilize → evidence → hypotheses → verification → fix → prevention, bảo vệ giao dịch thanh toán và giải thích vì sao CPU thấp không loại trừ nghẽn.

## Câu hỏi làm rõ nên cân nhắc

1. 5xx phát ra ở proxy, platform hay app?
2. Lỗi tập trung endpoint/instance nào và bắt đầu đúng thời điểm nào?
3. Release đổi code, config, schema, secret hay networking?
4. Checkout có idempotency key và reconciliation chưa?
5. DB waits, active connections và payment latency có tăng không?

## Gợi ý tư duy

### Gợi ý 1

Tách platform status khỏi application exceptions.

### Gợi ý 2

CPU thấp vẫn có thể chờ I/O hoặc connection pool.

### Gợi ý 3

Correlate deployment, dependency traces, instance health và retries.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement, dữ liệu còn thiếu và giả định.
2. Phân tích cơ chế và các giả thuyết hoặc phương án cạnh tranh.
3. Chọn bằng chứng/measurement để kiểm chứng.
4. Đề xuất implementation, failure handling và trade-offs.
5. Định nghĩa testing, monitoring, rollout và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

Đánh giá impact và freeze rollout; rollback chỉ nếu tương thích schema; phân đoạn lỗi; thu App Service diagnostics, Application Insights dependency telemetry, DB waits; không retry payment side effects mù quáng.

### Điểm cộng

Giả thuyết độc lập: DB pool exhaustion, payment timeout/retry storm, startup/health probe, schema lock; xác nhận bằng traces và per-instance evidence.

### Senior+

Idempotency/reconciliation cho unknown payment outcomes; canary/expand-contract migrations, SLO/error-budget alerts, failure injection.

## Hướng giải quyết tham khảo

Đầu tiên xác định tỷ lệ checkout thất bại, đơn có kết quả không chắc chắn, đóng băng rollout và chỉ rollback slot khi phiên bản cũ tương thích schema. Nếu không, dùng feature flag hoặc degrade checkout an toàn. Thu App Service front-end/HTTP diagnostics, container startup logs, restart/health events, Application Insights operation IDs, dependency durations, PostgreSQL pg_stat_activity, locks/waits và payment provider latency. So sánh từng endpoint, instance, thời điểm và version. Ba giả thuyết cạnh tranh: connection pool chờ do query/transaction dài hoặc leak; downstream timeout và retry storm; health probe/startup hoặc config/network sai sau deploy. CPU thấp phù hợp với I/O wait nên không đủ để loại trừ lỗi. Chỉ thay đổi khi bằng chứng ủng hộ: tối ưu DB, giới hạn concurrent calls, bounded timeouts/retries, cancellation, HttpClientFactory, health readiness và warm-up. Payment timeout không chứng minh provider chưa charge; dùng idempotency key, lưu trạng thái và reconciliation. Sau fix canary, kiểm chứng 5xx, p95/p99, checkout success, DB connections, dependency errors và unknown payment count; bổ sung alert, load/failure tests, runbook. Nếu nguyên nhân là provider outage độc lập release thì rollback không giúp; ưu tiên graceful degradation.

## Mẫu trả lời trong phỏng vấn

Tôi ưu tiên giữ tính đúng của thanh toán và khôi phục dịch vụ. Tôi xác định impact, dừng rollout và xem có rollback an toàn với schema hiện tại không. Tôi phân đoạn 5xx theo instance, endpoint và timeline, đối chiếu App Service diagnostics, Application Insights, DB waits và payment latency. CPU thấp không loại trừ chờ connection hoặc I/O. Tôi kiểm chứng ít nhất ba giả thuyết trước khi fix. Payment retry phải có idempotency và reconciliation. Sau canary, tôi đo tỷ lệ checkout thành công, 5xx, p95 và số giao dịch không chắc chắn, rồi thêm alert và failure-path tests.

## Câu hỏi đào sâu

1. Provider đã charge nhưng client timeout rồi retry: xử lý thế nào?
2. Tại sao scale thêm instances có thể làm database nghẽn hơn?
3. Nếu schema migration không backward-compatible, rollback bằng cách nào?

## Lỗi trả lời thường gặp

- Scale ngay mà không đo bottleneck.
- Cho rằng CPU thấp chứng minh ứng dụng khỏe.
- Retry payment vô điều kiện.
- Rollback bất chấp schema compatibility.
- Chỉ xem application logs.

## Thang điểm 0–10

**Tiêu chí và trọng số:** Impact/stabilization 2; telemetry/hypotheses 2.5; technical verification 2; payment correctness/rollout 2; trade-off/communication 1.5. Không chấm điểm chỉ vì nêu đúng tên công nghệ; cần chứng minh cơ chế, bằng chứng và trade-off.

# Câu 3 — Thiết kế upload tài liệu approval: API proxy hay direct Azure Blob?

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, PostgreSQL, Managed Identity, SAS, reliability

## Bối cảnh

Enterprise approval portal dùng React, ASP.NET Core, PostgreSQL; attachment PDF/ảnh hiện được lưu local disk nên không ổn định khi scale nhiều instances. Muốn file lớn, mobile network dễ mất kết nối, audit quyền xem theo approval stage. Chưa biết file-size distribution, PII, malware scanning, retention và concurrency. Đội vận hành nhỏ, tránh microservices không cần thiết.

## Câu hỏi chính

Thiết kế APIs, data model, lifecycle, authorization, upload/download và failure recovery; so sánh streaming API proxy với browser direct-to-Blob, nêu trade-offs và migration/rollback.

## Câu hỏi làm rõ nên cân nhắc

1. File size, concurrency và SLO?
2. Có PII, malware scan, retention hay compliance?
3. Ai được download ở từng approval stage và tenant?
4. Có resumable upload, overwrite/versioning không?
5. Existing files và migration/rollback constraints?

## Gợi ý tư duy

### Gợi ý 1

Tách control plane metadata/quyền khỏi data plane bytes.

### Gợi ý 2

Blob và SQL không có transaction ACID chung.

### Gợi ý 3

Dùng upload intent, quarantine, finalize, cleanup và scoped short-lived SAS.

## Cấu trúc trả lời đề xuất

1. Làm rõ requirement, dữ liệu còn thiếu và giả định.
2. Phân tích cơ chế và các giả thuyết hoặc phương án cạnh tranh.
3. Chọn bằng chứng/measurement để kiểm chứng.
4. Đề xuất implementation, failure handling và trade-offs.
5. Định nghĩa testing, monitoring, rollout và rollback.

## Ý chính của câu trả lời tốt

### Bắt buộc

Không dùng local disk per instance như durable shared storage; kiểm tra authorization cho mỗi download; có state machine Pending/Scanning/Available/Rejected và orphan cleanup.

### Điểm cộng

Private Blob, backend Managed Identity, scoped write/read SAS TTL ngắn, content validation, malware scan, idempotent finalize, audit.

### Senior+

Immutable blob names, ETag/version guards, compensating cleanup, dual-read/backfill/checksum rollout; cân nhắc revocation của issued SAS.

## Hướng giải quyết tham khảo

Nếu file lớn và traffic cao, dùng API làm control plane: POST /requests/{id}/attachments/intents kiểm tra tenant, ownership, quota, content type/size dự kiến; tạo Attachment(Id, RequestId, TenantId, BlobName, Status, Size, ETag, CreatedBy, ExpiresAt) trạng thái Pending. Backend dùng Managed Identity và cấp scoped short-lived write SAS cho blob name ngẫu nhiên trong private container. Client upload block/resumable nếu cần; POST /attachments/{id}/finalize kiểm tra quyền, existence, size, ETag và trạng thái, idempotently chuyển Uploaded/Scanning. Scanner xử lý và chỉ Available được download. Download API kiểm tra quyền hiện tại rồi cấp read SAS ngắn hạn hoặc stream; SAS đã cấp không được coi là thu hồi ngay nên với strict immediate revocation cân nhắc proxy. Blob và SQL không chung transaction: pending quá hạn và blob orphan được cleanup sau grace period; scanner failure retry bounded, giữ quarantine; không tự động hiển thị file chưa scan. Validate magic bytes, size, safe filename/Content-Disposition, CORS, audit và không log SAS. Proxy upload dễ enforce policy và che storage nhưng tốn bandwidth, request duration và scaling; direct upload giảm tải API nhưng tăng SAS/CORS/state complexity. Nếu file nhỏ và traffic thấp, streaming proxy là phương án đơn giản hơn. Migrate local files bằng inventory, checksum, backfill, dual-read, feature flag, kiểm tra download rồi mới xóa bản cũ. Theo dõi completion rate, orphan count, scan latency, authorization failures, Blob errors. Không cần microservices/queue nếu durable job nhỏ đáp ứng SLO; mở rộng khi throughput yêu cầu.

## Mẫu trả lời trong phỏng vấn

Tôi tách API quản lý quyền và metadata khỏi đường truyền bytes. Với file lớn, tôi chọn direct-to-Blob: tạo upload intent sau khi kiểm tra quyền, cấp write SAS giới hạn, client upload rồi finalize. SQL giữ Pending, Scanning, Available; chỉ file đã scan và có quyền mới được tải. Vì Blob và SQL không chung transaction, finalize phải idempotent và có orphan cleanup. Private container, Managed Identity, short-lived SAS và audit bảo vệ dữ liệu. Nếu file nhỏ, traffic thấp hoặc compliance yêu cầu kiểm tra bytes tại API, streaming proxy có thể hợp lý hơn. Migration dùng checksum, dual-read và feature flag để rollback.

## Câu hỏi đào sâu

1. Nếu quyền xem bị revoke ngay sau khi cấp read SAS, giải pháp nào đáp ứng tức thì?
2. Client upload xong nhưng mất mạng trước finalize: tránh duplicate/orphan thế nào?
3. Khi nào proxy tốt hơn direct upload dù file lớn?

## Lỗi trả lời thường gặp

- Giả định local disk luôn shared durable.
- Để client chọn blob path và SAS dài hạn.
- Cho tải file trước malware scan.
- Coi SQL và Blob là một transaction.
- Chỉ nói dùng Blob mà thiếu failure recovery.

## Thang điểm 0–10

**Tiêu chí và trọng số:** Clarification 1.5; API/data model 2; consistency/failure 2.5; security 2; trade-offs/migration/telemetry 2. Không chấm điểm chỉ vì nêu đúng tên công nghệ; cần chứng minh cơ chế, bằng chứng và trade-off.
