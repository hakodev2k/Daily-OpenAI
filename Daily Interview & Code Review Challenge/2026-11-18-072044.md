# Câu 1 — Vì sao EF Core lưu thành công nhưng ghi đè thay đổi của người khác?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 25 phút  
**Kỹ năng được đánh giá:** EF Core change tracking, optimistic concurrency, SQL Server, transaction isolation, HTTP concurrency

## Bối cảnh

Một portal phê duyệt chi phí sử dụng ASP.NET Core .NET 8, EF Core và SQL Server. Hai người quản lý mở cùng một yêu cầu ở trạng thái `Pending`. Người A sửa hạn mức, người B sửa ghi chú và phê duyệt. Cả hai API đều trả 200, nhưng sau đó dữ liệu của A bị ghi đè. Endpoint hiện tải entity, ánh xạ toàn bộ DTO vào entity rồi gọi `SaveChangesAsync`. Không rõ ứng dụng có concurrency token, transaction isolation hay điều kiện chuyển trạng thái. Business yêu cầu không mất cập nhật và không cho phép phê duyệt hai lần.

## Câu hỏi chính

Giải thích cơ chế change tracking và SQL UPDATE của EF Core khiến hai request có thể cùng thành công; đề xuất cách phát hiện và xử lý xung đột, đồng thời bảo vệ invariant của workflow khi nhiều instance cùng phục vụ request.

## Câu hỏi làm rõ nên cân nhắc

1. DTO chứa những field nào và có gửi version từ lúc đọc không?
2. Entity có `rowversion`/concurrency token và có dùng `AsNoTracking` hay detached update không?
3. Khi phê duyệt, có ghi audit, gửi notification hoặc gọi API ngoài không?
4. Hai người có được phép sửa các field khác nhau đồng thời hay mọi xung đột phải báo người dùng?
5. Database có trigger, isolation đặc biệt hoặc các writer khác ngoài API không?

## Gợi ý tư duy

### Gợi ý 1
Một transaction commit thành công không đồng nghĩa không có lost update.

### Gợi ý 2
Xem `WHERE` của UPDATE và giá trị gốc (original value) mà EF Core biết.

### Gợi ý 3
Phân biệt chống lost update của một row với bảo đảm trạng thái nghiệp vụ chỉ chuyển đúng một lần.

## Cấu trúc trả lời đề xuất

1. Nêu invariant, phạm vi field và giả định.
2. Dựng timeline hai request, giải thích tracking và generated SQL.
3. Chọn optimistic concurrency và hợp đồng HTTP.
4. Thiết kế conflict response, merge/retry và workflow guard.
5. Đánh giá side effects, tests và telemetry.

## Ý chính của câu trả lời tốt

### Bắt buộc
- `DbContext` theo request không tự ngăn lost update giữa requests.
- Concurrency token được đưa vào điều kiện UPDATE; không có row bị ảnh hưởng sẽ phát sinh `DbUpdateConcurrencyException` với tracked update phù hợp.
- Client phải gửi version đã đọc, không được lấy version mới ngay trước khi ghi rồi coi như bảo vệ được stale edit.
- Business transition cần kiểm tra trạng thái hiện hành một cách atomic.

### Điểm cộng
- Phân biệt cập nhật một phần và `Update(detachedEntity)` đánh dấu nhiều property modified.
- Thiết kế `409 Conflict` hoặc `412 Precondition Failed` với ETag/`If-Match` và giao diện resolve conflict.
- Outbox cho notification phát sinh sau commit, tránh gửi trước khi transaction thành công.

### Senior+
- Phân tích trade-off giữa optimistic concurrency, conditional SQL update và pessimistic locking dưới contention cao.
- Phân biệt idempotent command, audit append-only, transaction boundary và exactly-once business effect.

## Hướng giải quyết tham khảo

**Giả định:** SQL Server có cột `rowversion`, yêu cầu phải phát hiện stale edit. EF Core khi query tracking lưu original values. Nếu không cấu hình concurrency token, UPDATE thường dựa trên khóa; request sau có thể ghi đè giá trị request trước, nhất là khi DTO map toàn bộ fields. Với `rowversion` cấu hình `IsRowVersion()`, UPDATE sẽ dùng khóa và original version trong `WHERE`. Khi version không còn khớp, UPDATE ảnh hưởng 0 row và EF Core ném `DbUpdateConcurrencyException`. Cần kiểm tra SQL thực tế và trạng thái entity, vì `ExecuteUpdateAsync` không tự áp dụng concurrency-token checking giống `SaveChanges`; phải thêm predicate và kiểm tra affected rows.

Ví dụ entity:

```csharp
public sealed class ExpenseRequest
{
    public long Id { get; set; }
    public decimal Limit { get; set; }
    public string Note { get; set; } = "";
    public string Status { get; set; } = "Pending";
    public byte[] RowVersion { get; set; } = [];
}

// OnModelCreating:
modelBuilder.Entity<ExpenseRequest>()
    .Property(x => x.RowVersion).IsRowVersion();
```

Ở API edit, tải entity theo ID và authorization scope, gán original `RowVersion` từ version client đã đọc, chỉ cập nhật field được phép sửa, rồi `SaveChangesAsync`. Nếu version cũ, trả conflict kèm version mới và thông tin đủ để người dùng so sánh; tuyệt đối không tự động retry bằng cách ghi đè phiên bản mới. Đối với HTTP conditional requests, nếu dùng `If-Match`, đảm bảo ETag phản ánh đúng version của representation và trả `412` khi precondition sai; nếu dùng hợp đồng version trong JSON có thể chọn `409` và nhất quán trong API.

Với Approve, đặt điều kiện `Status == Pending` cùng version/tenant/ID vào một atomic update hoặc transaction; kiểm tra số row affected = 1. Audit và outbox ghi cùng transaction nếu dùng cùng relational database. Consumer notification phải idempotent vì outbox delivery có thể lặp. Kiểm tra authorization trên resource trước thao tác và tránh lộ dữ liệu tenant khác trong conflict response.

**Khi thay đổi lựa chọn:** Nếu hai field độc lập có thể merge, triển khai field-level merge có xác nhận thay vì buộc người dùng sửa lại mọi thứ. Nếu contention rất cao và critical section dài, cân nhắc locking/queue nhưng phải đo deadlock, throughput và độ trễ. Không dùng isolation level `Serializable` mặc định cho mọi request nếu chưa có bằng chứng.

**Kiểm thử:** Hai request cùng version: chỉ một update được chấp nhận; Approve song song chỉ một transition; stale client nhận conflict; retry idempotency không nhân đôi audit/notification; kiểm tra SQL command và query count. **Theo dõi:** tỷ lệ conflict theo endpoint, affected rows, latency, deadlocks, audit correlation ID, số outbox retry.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận liệu hai người đang sửa cùng field hay các field độc lập và API có nhận version lúc client đọc không. EF Core tracking không tạo lock xuyên hai HTTP request. Nếu UPDATE chỉ dựa vào ID thì request sau có thể ghi đè request trước. Tôi sẽ dùng optimistic concurrency với SQL Server rowversion, gửi version qua API và yêu cầu SaveChanges kiểm tra original version. Khi conflict, tôi trả trạng thái rõ ràng để UI so sánh, không retry mù. Với hành động Approve, tôi không chỉ kiểm tra trạng thái bằng một lần đọc trước đó mà thực hiện conditional transition atomically, ghi audit và outbox trong cùng transaction. Tôi sẽ chứng minh bằng concurrency integration test, đo conflict rate và deadlock trước khi cân nhắc locking phức tạp hơn.”

## Câu hỏi đào sâu

1. Nếu người A sửa `Note` và người B sửa `Limit`, có nên coi mọi version conflict là lỗi không?
2. Nếu code chuyển sang `ExecuteUpdateAsync`, điều gì phải thay đổi để vẫn bảo đảm concurrency?
3. Nếu notification gửi qua Azure Service Bus sau commit thất bại, làm sao không mất thông báo và không gửi trùng business effect?

## Lỗi trả lời thường gặp

- Cho rằng mỗi request dùng `DbContext` riêng là đã thread-safe và không thể lost update.
- Cho rằng transaction mặc định luôn ngăn mọi lost update.
- Retry `SaveChanges` bằng cách lấy version mới rồi ghi đè không có quyết định của người dùng.
- Chỉ thêm UI disable button mà không bảo vệ transition ở database.
- Không test đồng thời và không đo tỷ lệ conflict thực tế.

## Thang điểm 0–10

| Giải thích tracking, SQL và cơ chế conflict | 2.5 |

| Phân tích lựa chọn, bảo mật và trade-offs | 1.5 |
| Kiểm thử, telemetry và giao tiếp rõ ràng | 2.5 |

# Câu 2 — Elasticsearch trả kết quả cũ sau khi cập nhật sản phẩm

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 30 phút  
**Kỹ năng được đánh giá:** Elasticsearch, PostgreSQL, eventual consistency, indexing pipeline, incident response, observability

## Bối cảnh

Một hệ thống e-commerce lưu product master ở PostgreSQL và dùng Elasticsearch để tìm kiếm. Sau một release, người bán cập nhật giá và trạng thái `Unavailable` trong database, nhưng trang search đôi lúc hiển thị giá cũ và sản phẩm hết hàng. Chi tiết sản phẩm đọc trực tiếp từ PostgreSQL lại đúng. Tỷ lệ sai tăng khi bulk import chạy; giả định 2% kết quả bị lệch trong 20 phút. Chưa rõ indexer dùng polling, event hay CDC; chưa có thông tin về Elasticsearch refresh, alias, retry, document version và backlog. Không được ngừng checkout; thông tin giá cuối cùng tại checkout phải chính xác.

## Câu hỏi chính

Bạn là engineer on-call: xử lý incident theo thứ tự nào để giảm tác động ngay, xác định nguyên nhân có bằng chứng, phục hồi dữ liệu search và ngăn lỗi tái diễn mà không mặc định reindex toàn bộ?

## Câu hỏi làm rõ nên cân nhắc

1. Search dùng giá hiển thị hay giá chốt giao dịch, và có kiểm tra availability ở checkout không?
2. Độ trễ index bình thường và SLA freshness được cam kết là bao nhiêu?
3. Indexer có event ID, retry, DLQ, watermark, offset và ordering/version không?
4. Release thay đổi mapping, alias, pipeline hoặc serializer ở đâu?
5. Lỗi tập trung vào tenant, shard, bulk batch hay thời điểm nào?

## Gợi ý tư duy

### Gợi ý 1
Phân biệt dữ liệu nguồn sai, pipeline chậm và search đọc nhầm index.

### Gợi ý 2
Một document đã index chưa chắc ngay lập tức xuất hiện trong search; nhưng độ trễ hàng chục phút cần kiểm chứng thêm.

### Gợi ý 3
Hãy kiểm tra cả lost event, out-of-order event và alias cutover, không chỉ queue depth.

## Cấu trúc trả lời đề xuất

1. Định lượng impact và bảo vệ checkout.
2. Stabilize release/pipeline và communication.
3. Trace một product ID xuyên PostgreSQL → event → indexer → Elasticsearch → search API.
4. So sánh nhiều giả thuyết bằng telemetry.
5. Phục hồi có đối soát, kiểm thử và theo dõi sau incident.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Database là nguồn sự thật cho giá và tồn kho theo giả định; checkout phải revalidate.
- Thu thập lag theo thời gian, failed bulk items, retry/DLQ, alias target và document version.
- Phân biệt refresh visibility với pipeline backlog, missing events và ordering.
- Phục hồi có kiểm tra completeness, không chỉ “restart indexer”.

### Điểm cộng
- Correlation theo product ID + change sequence, outbox/CDC và idempotent upsert.
- Canaries cho search freshness, alert dựa trên SLO và đối soát ngẫu nhiên có kiểm soát.
- Reindex vào index mới, alias swap có kế hoạch rollback nếu mapping thay đổi.

### Senior+
- Thiết kế version monotonic để event cũ không ghi đè event mới, kể cả replay và consumer song song.
- Xác định consistency contract cho search versus transactional APIs và chi phí của strong consistency.

## Hướng giải quyết tham khảo

**Impact → stabilize:** Xác nhận checkout lấy giá và availability mới từ database hoặc hệ thống giao dịch có thẩm quyền; nếu không, bổ sung kiểm tra server-side khẩn cấp, chặn giao dịch không hợp lệ. Có thể tạm ẩn giá nhạy cảm trên search hoặc ghi chú dữ liệu đang cập nhật, tùy yêu cầu Product. Tạm dừng bulk import hay rollback indexer release chỉ sau khi kiểm tra nguy cơ làm mất events, checkpoint và khả năng replay. Không xóa queue hoặc index trong lúc điều tra.

**Evidence:** Lấy một tập product ID có sai lệch, ghi thời điểm DB commit, version, event publish, event consume, bulk response từng item, document version trong index, alias và thời điểm search. Kiểm tra dashboard indexing throughput, failure rate, retry count, DLQ, backlog age, Elasticsearch write rejections, cluster health, refresh/merge pressure và query cache nếu liên quan. Elasticsearch near-real-time refresh giải thích độ trễ visibility ngắn, không đủ để tự kết luận nguyên nhân lệch kéo dài 20 phút.

**Giả thuyết phân biệt:** (a) event bị mất giữa DB commit và publish → kiểm tra outbox/event count và gap trong sequence; (b) indexer chậm do bulk import hoặc 429 → đo backlog age, rejected writes, retry backoff; (c) out-of-order event ghi đè giá mới → so sánh source version với document version; (d) alias trỏ index cũ hoặc pipeline ghi sai index → kiểm tra alias read/write và deployment diff; (e) mapping/transform lỗi → kiểm tra failed bulk items và sample payload. Không khẳng định giả thuyết nào đúng trước khi có bằng chứng.

**Remediation:** Sửa lỗi đã chứng minh, replay từ nguồn bền vững theo sequence và version, đối soát những product bị ảnh hưởng; nếu thiếu khả năng replay, backfill có watermark/snapshot nhất quán và xác minh số lượng, checksum hoặc sample record. Chỉ full reindex khi mapping/data corruption hay phạm vi lệch khiến targeted repair không đủ. Nếu cần rebuild, tạo index mới, chạy catch-up và kiểm tra trước khi atomic alias switch; chuẩn bị rollback.

**Prevention:** Dùng transactional outbox hoặc CDC phù hợp với DB, idempotent indexer và version check chống stale overwrite. Tách bulk import với incremental updates bằng capacity/priority policy nếu cần. Đặt freshness SLO dựa trên business, ví dụ giả định p99 lag dưới 60 giây, đo bằng timestamp/sequence end-to-end; cảnh báo khi backlog age, failed writes và mismatch tăng. Đảm bảo tenant authorization tại search API, không tin filter frontend. Load/failure test: bulk import đồng thời với updates, Elasticsearch unavailable, replay duplicate/out-of-order, alias rollout và failback.

## Mẫu trả lời trong phỏng vấn

“Tôi coi đây là sự cố consistency giữa nguồn dữ liệu PostgreSQL và read model Elasticsearch, chưa thể kết luận là lỗi refresh. Đầu tiên tôi bảo vệ checkout bằng revalidation ở server và xác định tỷ lệ người dùng bị ảnh hưởng. Sau đó tôi chọn vài product ID sai để dựng timeline DB commit, event, indexer, document và search response. Tôi kiểm tra backlog, bulk item failures, alias và version để phân biệt mất event, chậm index, sai thứ tự hoặc deployment regression. Tôi chỉ replay hoặc backfill phạm vi bị ảnh hưởng sau khi có cơ chế tránh stale overwrite; full reindex là lựa chọn có điều kiện. Về lâu dài tôi cần outbox/CDC, idempotency, freshness SLO và đối soát dữ liệu tự động.”

## Câu hỏi đào sâu

1. Nếu indexer không có durable event log, bạn backfill thế nào mà không bỏ sót update xảy ra trong lúc quét?
2. Nếu một event cũ đến sau event mới, làm sao ngăn document bị rollback?
3. Nếu Product yêu cầu search luôn hiển thị giá tức thời, bạn có giữ Elasticsearch làm nguồn giá hiển thị không?

## Lỗi trả lời thường gặp

- Quy toàn bộ vấn đề cho refresh interval mà không đo pipeline.
- Reindex toàn bộ ngay, làm tăng tải và che mất bằng chứng.
- Bỏ qua lỗi từng item trong bulk response.
- Tin giá trên search để thanh toán mà không revalidate.
- Không có tiêu chí xác nhận dữ liệu đã phục hồi hoàn toàn.

## Thang điểm 0–10

| Tiêu chí | Điểm |

| Impact, stabilization và bảo vệ giao dịch | 2 |
| Evidence và competing hypotheses | 2.5 |
| Hiểu consistency, indexing và version | 2 |

| Testing, telemetry và communication | 2 |

# Câu 3 — Chọn kiến trúc upload tài liệu lớn cho portal nội bộ

**Loại câu hỏi:** Architecture / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 35 phút  
**Kỹ năng được đánh giá:** ASP.NET Core, Azure Blob Storage, Managed Identity, authorization, asynchronous processing, API design, reliability

## Bối cảnh

Một portal nội bộ cho phép nhân viên đính kèm PDF, ảnh và file Office vào yêu cầu phê duyệt. Backend là ASP.NET Core .NET 8 trên Azure App Service, metadata ở PostgreSQL; tài liệu dự kiến tối đa 500 MB/file, nhiều người upload qua mạng không ổn định. Nhóm cân nhắc (A) proxy file qua API rồi stream lên Blob Storage, hoặc (B) API cấp quyền upload ngắn hạn để browser gửi trực tiếp lên Blob Storage. Có yêu cầu audit, tenant isolation, antivirus scanning và chỉ người được phân quyền mới tải file. Chưa có số liệu concurrency, compliance, browser constraints hay khả năng triển khai event pipeline.

## Câu hỏi chính

Bạn chọn kiến trúc upload/download và vòng đời tài liệu như thế nào, với API, storage, security, trạng thái xử lý, failure recovery, observability và rollout cụ thể? Khi nào chọn proxy thay vì direct upload?

## Câu hỏi làm rõ nên cân nhắc

1. Kích thước, số lượt upload đồng thời, quota tenant và tốc độ mạng p95 thực tế?
2. File có chứa PII, retention/legal hold, yêu cầu mã hóa hoặc residency đặc biệt không?
3. File chỉ được dùng sau antivirus scan hay có loại file được bỏ qua?
4. Client cần resume/chunk upload và có hạn chế CORS hoặc mạng doanh nghiệp không?
5. Có cần audit download, watermark, preview, CDN hay revoke ngay lập tức không?

## Gợi ý tư duy

### Gợi ý 1
Upload thành công vào Blob chưa có nghĩa tài liệu được phép download.

### Gợi ý 2
Tách control plane (authorization, metadata) và data plane (byte transfer).

### Gợi ý 3
Cần nghĩ đến abandoned uploads, replay của scanner và quyền truy cập sau khi người dùng mất role.

## Cấu trúc trả lời đề xuất

1. Chốt NFR, threat model và trạng thái nghiệp vụ.
2. So sánh proxy streaming với direct-to-Blob.
3. Thiết kế API, metadata và upload lifecycle.
4. Thiết kế scan, retry, authorization, cleanup và download.
5. Test tải/failure, triển khai theo giai đoạn và quan sát.

## Ý chính của câu trả lời tốt

### Bắt buộc
- Authorization trước khi cấp quyền upload/download, scope theo tenant và request.
- Không cấp quyền Blob rộng hoặc dài hạn cho browser.
- Quarantine → scan → available, chỉ file đạt kiểm tra mới được phục vụ.
- Không đồng nhất upload completion từ client với xác nhận server về blob content.
- Có chiến lược retry, timeout, cleanup và audit.

### Điểm cộng
- Multipart/block upload, resume, size/checksum validation và content sniffing.
- Managed Identity cho backend, scoped SAS với thời hạn ngắn khi direct upload được phép.
- Idempotent finalize, deduplication logic theo upload ID, lifecycle policy và retention.

### Senior+
- Threat model gồm malicious content, path/tenant confusion, token leakage, replay, race với role revoke và download URL forwarding.
- Định lượng egress/ingress, app CPU/bandwidth, Blob requests, scan throughput và chi phí vận hành trước khi chọn.

## Hướng giải quyết tham khảo

**Giả định:** Browser hiện đại hỗ trợ direct Blob upload, compliance cho phép, cần xử lý file 500 MB qua mạng không ổn định. Tôi ưu tiên direct upload có giới hạn và kiểm soát qua backend; proxy streaming vẫn là phương án hợp lý khi cần gateway kiểm tra bytes inline, client không thể truy cập Blob hoặc chính sách mạng yêu cầu một origin.

**API & state:** `POST /requests/{id}/attachments/uploads` xác thực user, tenant, quyền sửa request, quota, MIME allowlist và dự kiến kích thước; tạo `UploadSession` với `uploadId`, blob key do server sinh (không tin filename), owner, tenant, expected size, expiry và `PendingUpload`. Backend dùng Managed Identity truy cập storage; khi cần client direct upload, cấp user delegation SAS có permission tối thiểu, resource cụ thể và TTL ngắn, cấu hình CORS chặt theo origin cho browser. SAS là bearer capability: ai giữ URL có thể sử dụng trong phạm vi permission và thời hạn; không coi nó là user authentication. Nếu upload lớn cần block staging và resume, thiết kế quyền và block-list/finalization phù hợp SDK/Blob API.

Client gửi bytes trực tiếp; sau đó gọi `POST /uploads/{uploadId}/complete`. Backend kiểm tra ownership, expiry, blob tồn tại, kích thước, loại thực tế theo kiểm tra phù hợp, metadata và điều kiện trạng thái; `complete` idempotent. Không tin Content-Type hay client checksum đơn độc. Chuyển sang `Quarantined`, enqueue scan qua outbox/event sau khi metadata commit. Scanner có least privilege, kiểm tra content và ghi verdict idempotent theo blob version/ETag; chỉ chuyển `Available` nếu scan pass. File không hợp lệ thành `Rejected`, không public. Blob staging tách biệt khỏi vùng phục vụ hoặc enforce policy không cho đọc trước scan.

**Download:** `GET /attachments/{id}/download` luôn kiểm tra current tenant/role/request state và trạng thái `Available`; sau đó proxy stream hoặc phát short-lived read SAS theo threat model. Nếu cần revoke gần như tức thì hoặc audit mỗi byte download, proxy có lợi nhưng thêm tải và chi phí. Short-lived SAS không thể đảm bảo revoke ngay mọi URL đã phát; cần cân nhắc thời hạn, policy và khả năng thu hồi ở tầng storage.

**Reliability:** Dùng expiry cleanup cho session và orphaned blobs; retry có backoff và DLQ cho scan; bảo vệ duplicate events, worker crash và out-of-order completion. Giới hạn concurrency/quota để chống abuse; không giữ request transaction xuyên upload. Metadata PostgreSQL và Blob không nằm trong một ACID transaction; dùng state machine, reconciliation job và compensating cleanup. Nếu Blob/scan unavailable, giữ `Pending` hoặc `Quarantined`, không cho download. Audit user, object, action, decision, correlation ID mà không log SAS/secrets.

**Trade-offs:** Direct upload giảm bandwidth/connection pressure lên App Service, nhưng tăng độ phức tạp CORS, token lifecycle, client resume và state reconciliation. Proxy streaming đơn giản hơn ở phía client và kiểm soát đường truyền, nhưng có thể tăng latency, chi phí và áp lực tài nguyên. Không tự động thêm Kubernetes hay microservices; App Service + Blob + worker phù hợp nếu số liệu tải cho phép. Triển khai canary theo tenant, giới hạn file size ban đầu, test rollback và cleanup.

**Testing:** Integration test quyền tenant/role, malicious MIME và file quá quota; failure injection ngắt mạng giữa block upload, expired SAS, duplicate finalize, scanner crash; concurrency test hai finalize cùng upload ID; load test upload 500 MB và scan backlog; security test truy cập file chưa scan hoặc URL đã hết hạn. **Observability:** upload success/abort rate, time-to-available p50/p95/p99, scan queue age, failed scans, orphan bytes, storage error rate, 403/429, audit trail và alerts theo SLO.

## Mẫu trả lời trong phỏng vấn

“Tôi sẽ xác nhận giới hạn file, số upload đồng thời, yêu cầu bảo mật và liệu browser có thể truy cập Blob trực tiếp. Với file lớn và mạng không ổn định, tôi nghiêng về direct upload để App Service không phải proxy toàn bộ bytes, nhưng backend vẫn kiểm soát authorization và metadata. API tạo upload session, cấp SAS tối thiểu và ngắn hạn, client upload, rồi gọi finalize để server xác minh blob. File đi qua trạng thái quarantine và antivirus scan trước khi available. Download luôn kiểm tra quyền hiện tại; nếu yêu cầu revoke tức thì hoặc audit chặt, tôi cân nhắc proxy thay vì read SAS. Tôi sẽ thiết kế cleanup cho upload bỏ dở, retry idempotent cho scanner và đo time-to-available, lỗi upload, backlog trước khi scale.”

## Câu hỏi đào sâu

1. Nếu mạng doanh nghiệp chặn direct-to-Blob và yêu cầu scan inline, bạn đổi thiết kế thế nào?
2. Nếu SAS download đã phát mà user bị thu hồi quyền, mức revoke nào thực sự bảo đảm?
3. Nếu PostgreSQL commit thành công nhưng Blob upload hoặc scan thất bại, làm sao đối soát và tránh orphaned data?

## Lỗi trả lời thường gặp

- Để browser dùng storage account key hoặc SAS có quyền quá rộng.
- Cho phép download ngay sau khi client báo upload thành công.
- Giữ database transaction mở suốt quá trình upload 500 MB.
- Tin filename/MIME do client gửi và bỏ qua authorization ở download.
- Không xử lý upload dở, scanner failure, duplicate finalize và cleanup.
