# Code Review Challenge 1 — Hangfire job xử lý offboarding bị chạy trùng và trạng thái không nhất quán

**Chủ đề:** Background jobs, idempotency, EF Core concurrency, failure recovery  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 25–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core backend dùng Hangfire để xử lý cấu hình offboarding mailbox. Job tìm các cấu hình hết hạn, gọi Exchange/Microsoft 365 adapter để reset forwarding rồi cập nhật database. Production chạy nhiều Hangfire workers trên hai instance. Thỉnh thoảng cùng mailbox bị xử lý hai lần; có bản ghi DB đã chuyển trạng thái nhưng thao tác external system thất bại, và đôi lúc job retry gây thêm side effect. Yêu cầu là không được mất tác vụ, có thể retry an toàn và phải quan sát được trạng thái.

## Đoạn code cần review

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly AppDbContext _db;
    private readonly IExchangeService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        AppDbContext db,
        IExchangeService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _db = db;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteAsync()
    {
        var expired = await _db.MailConfigs
            .Where(x => x.Status == "Active" && x.EndTime <= DateTime.UtcNow)
            .ToListAsync();

        foreach (var config in expired)
        {
            try
            {
                config.Status = "Completed";
                config.CompletedAt = DateTime.UtcNow;
                await _db.SaveChangesAsync();

                await _exchange.DisableForwardingAsync(config.UserEmail);
                await _exchange.RemoveDelegationAsync(config.UserEmail);

                _logger.LogInformation(
                    "Reset completed for {Email}", config.UserEmail);
            }
            catch (Exception ex)
            {
                _logger.LogError(ex,
                    "Reset failed for {Email}: {Message}",
                    config.UserEmail, ex.Message);
            }
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định lỗi correctness và consistency.
2. Tìm rủi ro concurrency/idempotency khi nhiều worker cùng chạy.
3. Giải thích impact khi external call lỗi giữa chừng.
4. Ưu tiên vấn đề theo mức nghiêm trọng.
5. Đề xuất implementation an toàn hơn.
6. Mô tả cách test retry, concurrency và partial failure.
7. Đề xuất logs, traces và metrics cần có.

## Câu hỏi gợi mở

- Hai worker có thể đọc cùng một bản ghi `Active` không?
- `SaveChangesAsync` trước external calls tạo ra trạng thái gì nếu Exchange lỗi?
- Retry sau khi một external operation đã thành công sẽ thế nào?
- Việc catch toàn bộ exception nhưng không throw lại ảnh hưởng Hangfire retry ra sao?
- Có nên cố tạo distributed transaction giữa database và external API không?

## Kết quả code review tham khảo

### 1. Không có cơ chế atomic claim — High

**Problem:** Nhiều worker có thể query cùng config ở trạng thái `Active`.  
**Why:** Read rồi update là hai bước tách biệt, không có optimistic concurrency/conditional update/locking phù hợp.  
**Impact:** Duplicate external calls, race condition và trạng thái khó dự đoán.  
**Fix:** Claim bản ghi bằng conditional update (`Active -> Processing`) và chỉ worker thắng mới tiếp tục; hoặc dùng concurrency token/DB locking phù hợp.

### 2. Đánh dấu `Completed` trước side effects — High

**Problem:** DB nói hoàn tất trước khi Exchange thực sự hoàn tất.  
**Impact:** External failure tạo false-success và job sau không còn chọn bản ghi đó.  
**Fix:** Dùng trạng thái `Processing`, chỉ chuyển `Completed` sau khi các bước bắt buộc thành công.

### 3. External operations không được thiết kế idempotent — High

Retry có thể chạy lại `DisableForwarding` hoặc `RemoveDelegation`. Adapter nên coi trạng thái đích là mục tiêu (ensure disabled/ensure removed), hoặc nhận operation id/idempotency key nếu downstream hỗ trợ.

### 4. Nuốt exception làm Hangfire coi execution thành công — High

Catch exception rồi tiếp tục khiến scheduler không biết item thất bại. Cần lưu failure state có cấu trúc và/hoặc throw để retry ở đúng boundary. Nếu batch chứa nhiều item, nên enqueue từng item thành job riêng để retry độc lập.

### 5. Partial failure giữa hai external calls — High

Disable forwarding có thể thành công còn remove delegation thất bại. Workflow phải ghi nhận progress hoặc các operations phải idempotent để retry toàn workflow an toàn.

### 6. Một DbContext giữ tracking cho cả batch — Medium

Batch lớn làm change tracker tăng và một item lỗi có thể làm scope xử lý khó kiểm soát. Nên claim theo page/batch nhỏ và xử lý mỗi item trong scope/job riêng.

### 7. Không truyền CancellationToken — Medium

Shutdown/deployment không thể propagate cancellation xuống EF Core/external calls. Điều này làm shutdown chậm và tăng khả năng operation bị cắt ở boundary khó đoán.

### 8. Logging thiếu operation identity/state transition — Medium

Email không đủ để correlate retry. Cần `ConfigId`, `OperationId`, attempt, old/new state, external operation và duration. Tránh log dữ liệu nhạy cảm không cần thiết.

### 9. String status dễ tạo invalid state — Low

Nên dùng enum/value mapping rõ ràng và validate state transitions.

## Phiên bản code đề xuất

```csharp
public sealed class ResetExpiredMailJob
{
    private readonly IDbContextFactory<AppDbContext> _dbFactory;
    private readonly IExchangeService _exchange;
    private readonly ILogger<ResetExpiredMailJob> _logger;

    public ResetExpiredMailJob(
        IDbContextFactory<AppDbContext> dbFactory,
        IExchangeService exchange,
        ILogger<ResetExpiredMailJob> logger)
    {
        _dbFactory = dbFactory;
        _exchange = exchange;
        _logger = logger;
    }

    public async Task ExecuteItemAsync(Guid configId, CancellationToken ct)
    {
        var operationId = Guid.NewGuid();

        await using var db = await _dbFactory.CreateDbContextAsync(ct);

        var claimed = await db.MailConfigs
            .Where(x => x.Id == configId && x.Status == MailStatus.Active)
            .ExecuteUpdateAsync(s => s
                .SetProperty(x => x.Status, MailStatus.Processing)
                .SetProperty(x => x.OperationId, operationId)
                .SetProperty(x => x.LastAttemptAt, DateTime.UtcNow), ct);

        if (claimed == 0)
            return;

        var config = await db.MailConfigs
            .SingleAsync(x => x.Id == configId, ct);

        try
        {
            await _exchange.EnsureForwardingDisabledAsync(
                config.UserEmail, operationId, ct);

            await _exchange.EnsureDelegationRemovedAsync(
                config.UserEmail, operationId, ct);

            config.Status = MailStatus.Completed;
            config.CompletedAt = DateTime.UtcNow;
            config.LastError = null;
            await db.SaveChangesAsync(ct);

            _logger.LogInformation(
                "Offboarding reset completed. ConfigId={ConfigId} OperationId={OperationId}",
                configId, operationId);
        }
        catch (Exception ex)
        {
            config.Status = MailStatus.Failed;
            config.LastError = ex.GetType().Name;
            await db.SaveChangesAsync(CancellationToken.None);

            _logger.LogError(ex,
                "Offboarding reset failed. ConfigId={ConfigId} OperationId={OperationId}",
                configId, operationId);
            throw;
        }
    }
}
```

Điểm quan trọng: ví dụ trên minh họa conditional claim và idempotent target-state operations; production cần policy rõ ràng cho `Failed -> retryable Processing`, lease/timeout để recover job chết khi đang `Processing`, và tránh để retry bị chặn vĩnh viễn bởi state `Failed`.

## Trade-offs

Conditional update đơn giản và phù hợp modular monolith nhưng cần thiết kế recovery cho abandoned `Processing`. Queue/outbox có thể đáng dùng khi yêu cầu durability cao hơn. Distributed lock giảm duplicate execution nhưng không thay thế idempotency vì worker vẫn có thể chết sau side effect nhưng trước khi commit trạng thái.

## Cách kiểm thử

- Concurrency test: 20 workers cùng claim một `configId`; chỉ một worker được thực hiện side effects.
- Failure-path: forwarding thành công, delegation timeout; retry phải hội tụ về đúng trạng thái mà không tạo side effect sai.
- Crash test: process chết sau external success nhưng trước DB completion; retry phải an toàn.
- Database test: conditional update không claim config đã `Processing/Completed`.
- Load test với batch lớn để kiểm tra throughput, DB connection pool và external throttling.

## Quan sát trong production

Theo dõi số item theo state, `processing_age`, retry count, failure rate theo external operation, duration p50/p95/p99, abandoned processing count và Hangfire queue latency. Trace nên correlate `JobId -> ConfigId -> OperationId -> external request`.

## Câu hỏi phỏng vấn mở rộng

1. Bạn recover bản ghi `Processing` nếu worker chết bằng cách nào?
2. Nếu Exchange API không hỗ trợ idempotency key, bạn thiết kế adapter ra sao?
3. Outbox giải quyết phần nào và không giải quyết phần nào của workflow này?

# Code Review Challenge 2 — API tìm kiếm audit log: authorization và SQL injection ẩn sau tính linh hoạt

**Chủ đề:** Authorization, input validation, SQL correctness, sensitive-data exposure, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 20–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9 vấn đề

## Bối cảnh

Một internal API cho phép portal tìm audit log theo tenant, keyword và sort field. API dùng PostgreSQL qua Npgsql. Portal đã đăng nhập bằng JWT. Sau khi mở cho nhiều business units, security review phát hiện người dùng đôi khi xem được log của tenant khác; DBA cũng thấy các query bất thường và API chậm khi keyword rộng.

## Đoạn code cần review

```csharp
[Authorize]
[ApiController]
[Route("api/audit")]
public sealed class AuditController : ControllerBase
{
    private readonly NpgsqlDataSource _dataSource;
    private readonly ILogger<AuditController> _logger;

    public AuditController(
        NpgsqlDataSource dataSource,
        ILogger<AuditController> logger)
    {
        _dataSource = dataSource;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> Search(
        string tenantId,
        string? keyword,
        string sort = "created_at desc")
    {
        var sql = $"""
            select id, tenant_id, user_email, action, payload, created_at
            from audit_logs
            where tenant_id = '{tenantId}'
              and ('{keyword}' = '' or payload::text ilike '%{keyword}%')
            order by {sort}
            limit 5000
            """;

        _logger.LogInformation("Audit query: {Sql}", sql);

        await using var command = _dataSource.CreateCommand(sql);
        await using var reader = await command.ExecuteReaderAsync();

        var rows = new List<object>();
        while (await reader.ReadAsync())
        {
            rows.Add(new
            {
                Id = reader.GetGuid(0),
                TenantId = reader.GetString(1),
                UserEmail = reader.GetString(2),
                Action = reader.GetString(3),
                Payload = reader.GetString(4),
                CreatedAt = reader.GetDateTime(5)
            });
        }

        return Ok(rows);
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/security/performance problems.
2. Phân tích tenant isolation và authorization boundary.
3. Giải thích impact của input-controlled SQL.
4. Ưu tiên remediation.
5. Đưa ra implementation an toàn hơn.
6. Thiết kế security/database/load tests.
7. Đề xuất telemetry không làm lộ dữ liệu nhạy cảm.

## Câu hỏi gợi mở

- `[Authorize]` có chứng minh caller được phép đọc `tenantId` truyền trên query string không?
- Những phần nào của SQL có thể parameterize trực tiếp, phần nào cần allowlist?
- Log toàn SQL có thể làm lộ gì?
- `payload::text ILIKE '%...%'` có đặc điểm performance nào?
- Cancellation của HTTP request hiện có đi tới database không?

### Gợi ý 1

Authentication và tenant authorization là hai bài toán khác nhau.

### Gợi ý 2

Values nên parameterize; identifier/direction động như sort cần map từ một allowlist, không nối trực tiếp input vào SQL.

## Kết quả code review tham khảo

### 1. SQL injection qua `tenantId`, `keyword`, `sort` — Critical

User-controlled values được interpolation trực tiếp vào SQL. `sort` đặc biệt nguy hiểm vì không thể xử lý như value parameter thông thường. Fix: parameterize tenant/keyword; map sort key + direction qua allowlist cố định.

### 2. Broken tenant-level authorization — Critical

`[Authorize]` chỉ yêu cầu authenticated principal theo policy mặc định; code không chứng minh principal được phép truy cập tenant do request cung cấp. Tenant phải lấy từ trusted claim/context hoặc kiểm tra membership/permission server-side.

### 3. Trả `payload` và email không qua data-minimization policy — High

Audit payload có thể chứa PII/secrets. Chỉ select fields caller thực sự cần; redact/mask payload hoặc có permission riêng cho detail view.

### 4. Log nguyên SQL chứa dữ liệu user-controlled/sensitive — High

Có thể đưa tenant, keyword và payload-derived search data vào logs; còn tạo log-forging/volume risk. Log structured metadata thay vì raw SQL/input.

### 5. Limit 5000 không có pagination — Medium

Response lớn gây allocation, latency và DB load. Dùng bounded page size và preferably keyset pagination cho feed theo thời gian.

### 6. Search `payload::text ILIKE '%keyword%'` khó scale — Medium

Leading wildcard/cast toàn JSON/text có thể buộc scan lớn tùy schema/index/query plan. Cần xác định trường search thực sự, index phù hợp hoặc search-specific representation; đo bằng `EXPLAIN (ANALYZE, BUFFERS)` trên dữ liệu đại diện.

### 7. Không propagate request cancellation — Medium

Client disconnect vẫn có thể để query chạy. Nhận `CancellationToken` và truyền xuống `ExecuteReaderAsync`, `ReadAsync`.

### 8. Không giới hạn/validate keyword — Low/Medium

Keyword rất dài hoặc wildcard-heavy có thể tạo workload đắt. Áp dụng length/shape limits phù hợp business requirement.

## Phiên bản code đề xuất

```csharp
[Authorize(Policy = "AuditReader")]
[HttpGet]
public async Task<IActionResult> Search(
    string? keyword,
    string sortBy = "createdAt",
    bool descending = true,
    int pageSize = 100,
    DateTime? before = null,
    CancellationToken ct = default)
{
    var tenantId = User.FindFirst("tenant_id")?.Value;
    if (string.IsNullOrWhiteSpace(tenantId))
        return Forbid();

    if (keyword is { Length: > 100 })
        return BadRequest("keyword is too long");

    pageSize = Math.Clamp(pageSize, 1, 200);

    var sortColumn = sortBy switch
    {
        "createdAt" => "created_at",
        "action" => "action",
        _ => null
    };

    if (sortColumn is null)
        return BadRequest("Unsupported sort field");

    var direction = descending ? "DESC" : "ASC";
    var sql = $"""
        SELECT id, action, created_at
        FROM audit_logs
        WHERE tenant_id = @tenantId
          AND (@keyword IS NULL OR action ILIKE '%' || @keyword || '%')
          AND (@before IS NULL OR created_at < @before)
        ORDER BY {sortColumn} {direction}
        LIMIT @pageSize
        """;

    await using var command = _dataSource.CreateCommand(sql);
    command.Parameters.AddWithValue("tenantId", tenantId);
    command.Parameters.AddWithValue("keyword", (object?)keyword ?? DBNull.Value);
    command.Parameters.AddWithValue("before", (object?)before ?? DBNull.Value);
    command.Parameters.AddWithValue("pageSize", pageSize);

    var rows = new List<AuditListItem>(pageSize);
    await using var reader = await command.ExecuteReaderAsync(ct);

    while (await reader.ReadAsync(ct))
    {
        rows.Add(new AuditListItem(
            reader.GetGuid(0),
            reader.GetString(1),
            reader.GetDateTime(2)));
    }

    _logger.LogInformation(
        "Audit search completed. Tenant={TenantId} Count={Count} Sort={Sort}",
        tenantId, rows.Count, sortBy);

    return Ok(rows);
}
```

Nếu một user có thể thuộc nhiều tenant, không nên đơn giản lấy một claim duy nhất; cần authorization service kiểm tra requested tenant against trusted memberships. Ví dụ trên cố ý thu hẹp response và search field; schema thực tế quyết định index/search strategy.

## Trade-offs

Keyset pagination rất tốt cho ordered feeds nhưng khó hỗ trợ arbitrary page numbers. Full-text/search engine có thể hợp lý nếu audit search phức tạp, nhưng tăng vận hành và consistency concerns. PostgreSQL vẫn đủ tốt nếu query model và index đáp ứng workload thực tế.

## Cách kiểm thử

- Security test: token tenant A yêu cầu dữ liệu tenant B phải bị từ chối.
- Injection tests cho tenant/keyword/sort với payload phá cú pháp; query vẫn an toàn và sort ngoài allowlist bị reject.
- Data exposure test bảo đảm list endpoint không trả payload/email nếu không được yêu cầu.
- Cancellation test: hủy request khi DB query đang chạy và xác nhận operation được cancel.
- Load/database test với dữ liệu production-like, kiểm tra query plan và latency ở keyword phổ biến.

## Quan sát trong production

Theo dõi query duration, rows returned, timeout/cancellation rate, authorization-denied count, DB scanned/read blocks, slow-query fingerprints và response size. Không log raw JWT, payload hoặc keyword nhạy cảm. Alert khi cross-tenant authorization failures tăng bất thường hoặc p95/p99 query latency vượt SLO.

## Câu hỏi phỏng vấn mở rộng

1. Nếu user thuộc 20 tenants và được chọn tenant trên UI, bạn thiết kế authorization thế nào?
2. Khi nào PostgreSQL full-text/trigram index hợp lý hơn external search engine?
3. Bạn ngăn tenant predicate bị quên ở một endpoint mới bằng architecture/test strategy nào?

- Background job đáng tin cậy cần **claim + idempotency + explicit state machine + retry/recovery**, không chỉ dựa vào scheduler.
