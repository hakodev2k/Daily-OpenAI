# Code Review Challenge 1 — API đa tenant: JWT hợp lệ nhưng đọc được hóa đơn của tổ chức khác

**Chủ đề:** ASP.NET Core 8, Microsoft Entra ID, authorization, EF Core, SQL Server, multi-tenancy  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút

## Bối cảnh

Một enterprise portal phục vụ 80 tổ chức. Người dùng đăng nhập qua OIDC; API nhận access token và lưu hóa đơn trong SQL Server. Mỗi hóa đơn có `TenantId`, `OwnerUserId`, `Amount` và `InternalNote`. Frontend React gọi endpoint xem danh sách, xem chi tiết, cập nhật ghi chú. Team thấy đôi khi người dùng thuộc tenant A đọc được invoice ID của tenant B nếu biết ID; vài request audit không có tenant. API chạy nhiều instances, có background integration dùng service principal. Giả định JWT bearer authentication được cấu hình ở startup nhưng chưa biết validation parameters và cách mapping claim.

## Đoạn code cần review

~~~csharp
[ApiController]
[Authorize]
[Route("api/invoices")]
public sealed class InvoicesController : ControllerBase
{
    private readonly BillingDbContext _db;
    private readonly ILogger<InvoicesController> _logger;

    public InvoicesController(BillingDbContext db,
        ILogger<InvoicesController> logger)
    {
        _db = db;
        _logger = logger;
    }

    [HttpGet]
    public async Task<IActionResult> List(
        [FromQuery] Guid tenantId, CancellationToken ct)
    {
        var items = await _db.Invoices
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .Take(100)
            .ToListAsync(ct);

        return Ok(items);
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> Get(Guid id, CancellationToken ct)
    {
        var invoice = await _db.Invoices.FindAsync(
            new object[] { id }, ct);
        return invoice is null ? NotFound() : Ok(invoice);
    }

    [HttpPatch("{id:guid}/note")]
    public async Task<IActionResult> UpdateNote(
        Guid id, [FromBody] NoteRequest request,
        CancellationToken ct)
    {
        var invoice = await _db.Invoices.FindAsync(
            new object[] { id }, ct);
        if (invoice is null) return NotFound();

        invoice.InternalNote = request.Note;
        await _db.SaveChangesAsync(ct);
        _logger.LogInformation(
            "Invoice {InvoiceId} updated by {User}",
            id, User.Identity?.Name);
        return NoContent();
    }
}

public sealed record NoteRequest(string Note);
~~~

## Kết quả code review tham khảo

### [Critical] — IDOR/BOLA ở endpoint Get và UpdateNote

**Vấn đề:** `FindAsync(id)` không kiểm tra quyền với invoice.  
**Tại sao xảy ra:** `[Authorize]` chỉ yêu cầu identity phù hợp policy mặc định; không tự giới hạn bản ghi theo tenant.  
**Ảnh hưởng production:** Đọc/ghi dữ liệu tenant khác, có thể là sự cố bảo mật phải điều tra.  
**Cách sửa:** Resolve tenant từ trusted membership/context; query theo cả `Id` và `TenantId`, đồng thời enforce permission với resource và action.

### [Critical] — Client tự chọn tenant trong List

**Vấn đề:** `tenantId` từ query string được tin như authorization scope.  
**Tại sao xảy ra:** Không xác minh membership/role cho tenant yêu cầu.  
**Ảnh hưởng production:** Lộ danh sách hóa đơn và dữ liệu kinh doanh.  
**Cách sửa:** Kiểm tra membership trên server hoặc resolve active tenant từ verified context; nếu cho phép chọn tenant, bắt buộc authorize lựa chọn.

### [High] — Không có phân quyền read/write theo hành động

**Vấn đề:** Người được phép đọc cũng có thể cập nhật note.  
**Tại sao xảy ra:** Thiếu policy `Invoice.Read` / `Invoice.EditNote`.  
**Ảnh hưởng production:** Người dùng chỉ có quyền xem thay đổi dữ liệu.  
**Cách sửa:** Permission-based policy/resource authorization và kiểm tra ở mọi entry point.

### [High] — Trả EF entity trực tiếp

**Vấn đề:** List/Get có thể serialize `InternalNote` và thuộc tính mới bổ sung trong tương lai.  
**Tại sao xảy ra:** Persistence model được dùng như API contract.  
**Ảnh hưởng production:** Lộ trường nội bộ, khó kiểm soát backward compatibility.  
**Cách sửa:** Projection sang response DTO với field allowlist theo quyền.

### [High] — Thiếu kiểm soát identity/service principal

**Vấn đề:** Không phân biệt user delegation và app-only identity; `Identity.Name` có thể rỗng.  
**Tại sao xảy ra:** Chưa xác minh issuer/audience/token type, tenant mapping, `oid` và app roles.  
**Ảnh hưởng production:** Service token hoặc claim mapping sai có thể được gán quyền không mong muốn.  
**Cách sửa:** Cấu hình JWT validation chính xác, policy tách user/app, xác minh membership hoặc allowlist service identity.

### [Medium] — Audit thiếu tenant, actor ổn định và outcome

**Vấn đề:** Log chỉ ghi invoice ID và display name sau khi cập nhật.  
**Tại sao xảy ra:** Không dùng stable subject ID, tenant ID, correlation/trace ID.  
**Ảnh hưởng production:** Khó điều tra truy cập trái phép và truy nguyên hành động.  
**Cách sửa:** Structured audit gồm actor ID, tenant, resource, action, result, trace ID; không log token/note.

### [Medium] — Thiếu validation, concurrency và giới hạn payload

**Vấn đề:** `Note` không có giới hạn; ghi đè khi nhiều người cùng sửa.  
**Tại sao xảy ra:** Không có validation và optimistic concurrency.  
**Ảnh hưởng production:** Dữ liệu quá lớn, lost updates.  
**Cách sửa:** Max length, validation, rowversion/concurrency token nếu yêu cầu chống lost update.

### [Medium] — Query không phân trang ổn định

**Vấn đề:** `Take(100)` thiếu cursor và tie-breaker.  
**Tại sao xảy ra:** Chỉ sort theo `CreatedAt`.  
**Ảnh hưởng production:** Bỏ sót/trùng dữ liệu giữa các lần tải; query nặng nếu không có index phù hợp.  
**Cách sửa:** Keyset pagination theo `(CreatedAt, Id)`, index theo access pattern.

## Phiên bản đề xuất

Ví dụ tối giản cho **delegated user**; `ITenantAccess` là service phía server kiểm tra membership và permission bằng nguồn tin cậy. Cần triển khai và kiểm thử service này riêng; không được mặc định mọi `tenant_id` claim đều đáng tin hoặc có hiệu lực hiện tại.

~~~csharp
public interface ITenantAccess
{
    Task<bool> CanAsync(ClaimsPrincipal user, Guid tenantId,
        string permission, CancellationToken ct);
}

public sealed record InvoiceDto(
    Guid Id, Guid TenantId, decimal Amount, DateTime CreatedAt);
public sealed record NoteRequest(string Note);

[ApiController]
[Authorize]
[Route("api/tenants/{tenantId:guid}/invoices")]
public sealed class InvoicesController : ControllerBase
{
    private readonly BillingDbContext _db;
    private readonly ITenantAccess _access;

    public InvoicesController(BillingDbContext db, ITenantAccess access)
        => (_db, _access) = (db, access);

    [HttpGet]
    public async Task<IActionResult> List(Guid tenantId, CancellationToken ct)
    {
        if (!await _access.CanAsync(User, tenantId, "Invoice.Read", ct))
            return Forbid();

        var data = await _db.Invoices.AsNoTracking()
            .Where(x => x.TenantId == tenantId)
            .OrderByDescending(x => x.CreatedAt)
            .ThenByDescending(x => x.Id)
            .Take(100)
            .Select(x => new InvoiceDto(
                x.Id, x.TenantId, x.Amount, x.CreatedAt))
            .ToListAsync(ct);
        return Ok(data);
    }

    [HttpGet("{id:guid}")]
    public async Task<IActionResult> Get(
        Guid tenantId, Guid id, CancellationToken ct)
    {
        if (!await _access.CanAsync(User, tenantId, "Invoice.Read", ct))
            return Forbid();

        var item = await _db.Invoices.AsNoTracking()
            .Where(x => x.TenantId == tenantId && x.Id == id)
            .Select(x => new InvoiceDto(
                x.Id, x.TenantId, x.Amount, x.CreatedAt))
            .SingleOrDefaultAsync(ct);
        return item is null ? NotFound() : Ok(item);
    }

    [HttpPatch("{id:guid}/note")]
    public async Task<IActionResult> UpdateNote(
        Guid tenantId, Guid id, NoteRequest request, CancellationToken ct)
    {
        if (!await _access.CanAsync(User, tenantId, "Invoice.EditNote", ct))
            return Forbid();

        if (request.Note is null || request.Note.Length > 2000)
            return BadRequest("Invalid note length.");

        var item = await _db.Invoices.SingleOrDefaultAsync(
            x => x.TenantId == tenantId && x.Id == id, ct);
        if (item is null) return NotFound();

        item.InternalNote = request.Note;
        await _db.SaveChangesAsync(ct);
        return NoContent();
    }
}
~~~

**Lưu ý:** Đây là baseline, chưa hoàn chỉnh cho production: thêm pagination, audit, concurrency token, chống enumeration nếu cần, kiểm soát `ITenantAccess` cache invalidation, và phân tách app-only authorization. Nếu authorization phụ thuộc owner của invoice, phải kiểm tra owner/resource riêng; tenant membership đơn thuần không đủ.

## Giải thích thiết kế sau khi sửa

Tenant được chọn qua route nhưng **không được tin** trước khi kiểm tra quyền. Query luôn scoped theo tenant; DTO giảm bề mặt dữ liệu. Permission khác nhau cho read/write. Tenant filter không thay thế authorization, và EF Core global query filter nếu dùng chỉ là lớp phòng vệ bổ sung, không phải cơ chế cấp quyền độc lập. Khi xử lý nhiều tenant trong cùng request/scope, phải tránh rò state trong singleton hoặc pooled DbContext.

## Trade-offs

Kiểm tra membership mỗi request tăng latency; cache có TTL/invalidation cần đánh đổi với tốc độ thu hồi quyền. `403` vs `404` phải có chính sách tránh resource enumeration. DB Row-Level Security có thể là defense-in-depth nhưng tăng vận hành và yêu cầu session context an toàn. Kiểm tra quyền tại application layer dễ test hơn nhưng phải bảo đảm mọi endpoint và worker đều tuân thủ.

## Cách kiểm thử

1. **Security integration:** Token user A truy cập ID tenant B qua GET/PATCH/List: không đọc/ghi được.
2. **Authorization matrix:** Reader không sửa được; editor đúng tenant được sửa; service principal không được nhận quyền user mặc định.
3. **Revocation:** Thu hồi membership, kiểm tra request sau đó bị chặn theo SLA invalidation.
4. **Concurrency:** Hai PATCH đồng thời; kiểm tra chính sách last-write-wins hoặc `409` với rowversion.
5. **API contract:** Snapshot response không chứa `InternalNote`, kể cả khi EF entity thêm trường mới.

## Quan sát trong production

Ghi structured audit `actorId`, `tenantId`, `invoiceId`, `action`, `decision`, `traceId`; metrics số `403/404` theo route (không đưa ID vào metric labels); cảnh báo tăng đột biến cross-tenant denial; Application Insights dependency spans cho membership lookup và SQL. Trong incident, cô lập endpoint rủi ro, rà access logs và điều tra phạm vi lộ dữ liệu trước khi xác nhận khắc phục.

## Câu hỏi phỏng vấn mở rộng

1. Khi một user thuộc nhiều tenant, bạn thiết kế active tenant và token claims thế nào để không tạo confused-deputy problem?
2. Khi background worker xử lý invoice không có user token, authorization context nào là hợp lệ?
3. Có nên dùng SQL Server Row-Level Security cùng application authorization không, và rủi ro với connection pooling là gì?

# Code Review Challenge 2 — Kubernetes rollout xanh nhưng website mất traffic sau deploy

**Chủ đề:** Kubernetes, ASP.NET Core health checks, Azure App Service alternative, deployment safety, observability  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một website thương mại chạy ASP.NET Core 8 trong Kubernetes, 6 replicas, kết nối PostgreSQL và external product API. CI/CD cập nhật image mỗi ngày. Sau rollout, một số pod được đánh dấu Ready trước khi ứng dụng thực sự phục vụ được traffic; request lỗi `502/503` trong 1–2 phút. Khi product API chậm, nhiều pod bị restart, khiến traffic chuyển sang các pod còn lại. Team muốn giảm downtime nhưng không thể thay đổi platform trong sprint này. Giả định ingress chuyển traffic tới Ready endpoints; ứng dụng có route `/health` nhưng chưa có thông tin cụ thể về implementation.

## Kết quả code review tham khảo

### [High] — Liveness phụ thuộc chung vào /health

**Vấn đề:** Nếu endpoint tổng hợp kiểm tra product API/PostgreSQL, dependency outage có thể làm pod bị restart hàng loạt.  
**Tại sao xảy ra:** Liveness nên phản ánh tiến trình còn khả năng tự phục hồi, không đơn giản là mọi dependency đều healthy.  
**Ảnh hưởng production:** Restart storm, cold-start amplification, mất capacity.  
**Cách sửa:** Endpoint `/health/live` chỉ kiểm tra tình trạng nội tại tối thiểu; readiness có policy riêng.

### [High] — Rollout có thể giảm một nửa capacity

**Vấn đề:** `maxUnavailable: 3` với 6 replicas, `maxSurge: 0`.  
**Tại sao xảy ra:** Cho phép thay thế nhiều pod cũ mà chưa có pod mới Ready.  
**Ảnh hưởng production:** Latency spike, 503 khi peak traffic.  
**Cách sửa:** `maxUnavailable: 0`, `maxSurge: 1` nếu cluster có headroom; kiểm tra quota và capacity trước.

### [High] — Mutable image tag

**Vấn đề:** `latest` không định danh artifact bất biến.  
**Tại sao xảy ra:** Tag có thể trỏ sang digest khác ở các thời điểm pull.  
**Ảnh hưởng production:** Rollback không tái lập chính xác; pod không đồng nhất.  
**Cách sửa:** Pin image digest hoặc immutable release tag được kiểm soát.

### [High] — API key hardcoded trong manifest

**Vấn đề:** Credential nằm trực tiếp trong YAML.  
**Tại sao xảy ra:** Thiếu secret management.  
**Ảnh hưởng production:** Lộ key trong repository, artifact, logs, quyền đọc manifest.  
**Cách sửa:** Rotate key nếu đã lộ; dùng Kubernetes Secret/External Secrets hoặc workload identity phù hợp, RBAC và secret access auditing. Secret không tự mã hóa an toàn ở mọi tầng nếu chưa cấu hình encryption at rest.

### [Medium] — Không có startupProbe cho ứng dụng khởi động chậm

**Vấn đề:** Liveness có thể chạy trước khi startup hoàn tất.  
**Tại sao xảy ra:** `initialDelaySeconds` ngắn, không xét warmup/migrations.  
**Ảnh hưởng production:** Restart loop hoặc rollout kéo dài.  
**Cách sửa:** `startupProbe` với failure budget đo từ startup thực tế; không chạy migrations nguy hiểm trong startup của mọi replica.

### [Medium] — Readiness không định nghĩa rõ contract

**Vấn đề:** `/health` có thể trả 200 khi app chưa sẵn sàng hoặc fail vì dependency không thiết yếu.  
**Tại sao xảy ra:** Endpoint chưa được thiết kế theo khả năng phục vụ traffic cốt lõi.  
**Ảnh hưởng production:** Route traffic quá sớm hoặc rút hết endpoints khi third-party outage.  
**Cách sửa:** Readiness kiểm tra thành phần tối thiểu cần thiết; degradation/circuit breaker cho optional product API.

### [Medium] — Thiếu shutdown/draining policy

**Vấn đề:** Không có `terminationGracePeriodSeconds` phù hợp và shutdown verification.  
**Tại sao xảy ra:** Pod termination có thể cắt request hoặc background work.  
**Ảnh hưởng production:** Interrupted requests, duplicate processing.  
**Cách sửa:** Graceful shutdown, cancellation propagation, đo request duration; cân nhắc preStop khi cần, không thay thế graceful handling.

### [Medium] — Resource requests/limits chưa dựa trên measurements

**Vấn đề:** CPU request 100m, memory limit 256Mi có thể thấp so với load.  
**Tại sao xảy ra:** Chưa đối chiếu working set, GC, peak traffic.  
**Ảnh hưởng production:** CPU throttling do node contention, OOMKilled.  
**Cách sửa:** Profile/load test, đặt requests/limits theo quan sát và capacity planning.

                  key: api-key
          startupProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 5
            failureThreshold: 24
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              memory: 512Mi
~~~

Ví dụ cấu hình ASP.NET Core tương ứng, chỉ để thể hiện contract của probes:

~~~csharp
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(),
        tags: new[] { "live" });

var app = builder.Build();
app.MapHealthChecks("/health/live",
    new HealthCheckOptions
    {
        Predicate = check => check.Tags.Contains("live")
    });
app.MapHealthChecks("/health/ready",
    new HealthCheckOptions
    {
        Predicate = check => !check.Tags.Contains("live")
    });
app.Run();
~~~

**Quan trọng:** Nếu chưa đăng ký readiness checks thì endpoint `/health/ready` ở ví dụ trên có thể trả Healthy mà chưa chứng minh app sẵn sàng. Production phải thêm checks cho các điều kiện phục vụ traffic thực sự và xác nhận readiness behavior; ví dụ chỉ minh họa phân tách probe. Requests/limits và timeouts cũng là giá trị khởi điểm, không phải benchmark đã được xác minh.

## Giải thích thiết kế sau khi sửa

Startup probe cho ứng dụng thời gian warmup; readiness điều khiển routing; liveness chỉ phục vụ quyết định restart. Artifact bất biến cho phép so sánh chính xác deployment. Rolling update duy trì capacity khi cluster đủ tài nguyên. Secrets tách khỏi manifest; nếu workload identity hỗ trợ loại dependency thì có thể loại bỏ static API key.

## Trade-offs

`maxUnavailable: 0` cần spare capacity, nếu cluster hết quota rollout có thể Pending thay vì giảm capacity. Readiness phụ thuộc database có thể rút hết pods trong DB outage; cần cân nhắc fail-open/fail-closed theo chức năng, không có cấu hình chung cho mọi ứng dụng. StartupProbe budget dài làm phát hiện lỗi startup chậm hơn. Secret rotation đòi hỏi rollout hoặc dynamic reload. Không nên chuyển sang App Service chỉ vì probe đang sai; sửa operational contract trước.

## Cách kiểm thử

1. **Deployment validation:** Deploy digest bất biến; kiểm tra tất cả pods cùng digest và rollout history.
2. **Failure injection:** Product API timeout; app vẫn live, readiness theo policy degradation, không restart storm.
3. **Load test:** Rolling update dưới peak traffic; so sánh 5xx, p95/p99, Ready endpoints và CPU/memory.
4. **Startup test:** Warmup chậm hơn 30 giây; không có premature liveness restart.
5. **Shutdown test:** SIGTERM khi đang xử lý request; verify graceful completion/cancellation và retry safety.

## Quan sát trong production

Dashboard theo deployment revision: ready replicas, unavailable replicas, restarts, `OOMKilled`, `CrashLoopBackOff`, probe failures, ingress `502/503`, request p95/p99, pod CPU/memory, dependency timeout và circuit-breaker state. Dùng `kubectl describe pod`, events, logs và Application Insights traces để phân biệt startup, readiness, ingress routing và dependency failure. Alert khi rollout vượt timeout hoặc availability thấp hơn SLO.

## Câu hỏi phỏng vấn mở rộng

1. Khi cluster không đủ capacity cho `maxSurge: 1`, bạn ưu tiên phương án rollout nào và đo rủi ro ra sao?
2. Có nên đưa PostgreSQL vào readiness không nếu API vẫn có thể phục vụ một số read-only endpoints?
3. Làm thế nào chứng minh một lỗi 503 xuất phát từ ingress, pod readiness hay ứng dụng?
