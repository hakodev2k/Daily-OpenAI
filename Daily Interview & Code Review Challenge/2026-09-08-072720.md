# Câu 1 — `Task.WhenAll` có thực sự làm hệ thống “nhanh hơn” hay chỉ chuyển bottleneck sang downstream?

**Loại câu hỏi:** Internal Mechanism + Practical Behavior  
**Độ khó:** Senior  
**Thời gian trả lời đề xuất:** 20–30 phút  
**Kỹ năng được đánh giá:** C#, async/await, `Task.WhenAll`, I/O concurrency, cancellation, connection pools, downstream capacity, ASP.NET Core performance

## Bối cảnh

Một ASP.NET Core API trên .NET 8 trả về dashboard tổng hợp dữ liệu cho một enterprise portal.

Mỗi request cần lấy thông tin từ 3 nguồn:

- SQL Server;
- một internal REST API;
- một CRM API bên ngoài.

Ban đầu code gọi tuần tự và latency trung bình khoảng 1.4 giây. Một developer refactor thành:

```csharp
public async Task<DashboardDto> GetDashboardAsync(
    Guid userId,
    CancellationToken cancellationToken)
{
    var profileTask = _profileRepository.GetProfileAsync(
        userId,
        cancellationToken);

    var ordersTask = _orderRepository.GetRecentOrdersAsync(
        userId,
        cancellationToken);

    var crmTask = _crmClient.GetCustomerStatusAsync(
        userId,
        cancellationToken);

    await Task.WhenAll(profileTask, ordersTask, crmTask);

    return new DashboardDto(
        await profileTask,
        await ordersTask,
        await crmTask);
}
```

Latency giảm rõ trong load test nhỏ.

Sau đó team mở rộng pattern này cho một màn hình khác: một request lấy danh sách 200 products rồi chạy `Task.WhenAll` để gọi pricing API cho từng product.

Production bắt đầu có các triệu chứng:

- p50 tốt nhưng p95/p99 tăng mạnh khi traffic tăng;
- pricing API bắt đầu trả 429 và timeout;
- SQL connection-pool wait xuất hiện;
- số outbound requests tăng đột biến theo số concurrent users;
- retry làm tình hình nặng hơn;
- CPU của API chưa đạt 100%;
- một developer kết luận `Task.WhenAll` gây ThreadPool starvation;
- developer khác đề xuất đổi toàn bộ sang `Parallel.ForEachAsync`;
- người khác đề xuất tăng `MaxDegreeOfParallelism` càng cao càng tốt.

Chưa biết chắc:

- mỗi downstream có concurrency/rate limit bao nhiêu;
- pricing API có bulk endpoint hay không;
- SQL queries có dùng chung transaction/`DbContext` không;
- retry policy hiện tại là gì;
- upstream request timeout budget là bao nhiêu;
- số products trung bình và p99 per request là bao nhiêu;
- client disconnect có propagate cancellation tới các dependency call hay không.

## Câu hỏi chính

Hãy giải thích `Task.WhenAll` thực sự làm gì trong trường hợp I/O-bound, vì sao nó có thể giảm latency cho một request nhỏ nhưng làm toàn hệ thống kém ổn định khi fan-out lớn, và bạn sẽ thiết kế concurrency boundary thế nào để giữ latency tốt mà không làm quá tải SQL, connection pool hoặc downstream APIs.

## Câu hỏi làm rõ nên cân nhắc

1. Ba dependency đầu tiên có độc lập thật sự không, hay có call nào phụ thuộc kết quả call trước?
2. Pricing API có bulk endpoint hoặc giới hạn requests/second/concurrent requests được công bố không?
3. Một request có tối đa bao nhiêu products và có cần price của tất cả products trước khi trả response không?
4. SQL calls có dùng cùng một `DbContext` instance hay mỗi call có ownership riêng?
5. Retry hiện tại có phân biệt 429, timeout, 5xx và caller cancellation không?

## Gợi ý tư duy

### Gợi ý 1

`Task.WhenAll` không tự tạo thread cho mỗi I/O operation. Hãy phân biệt concurrency của asynchronous I/O với parallel CPU execution.

### Gợi ý 2

Một request fan-out 200 calls có thể nhanh trong isolation nhưng khi 100 users cùng chạy thì hệ thống tạo 20.000 downstream operations.

### Gợi ý 3

Concurrency phải bị giới hạn bởi capacity của dependency và end-to-end latency budget; không phải bởi số task mà application có thể tạo.

## Cấu trúc trả lời đề xuất

1. Làm rõ dependency graph và latency budget.
2. Giải thích async I/O và `Task.WhenAll` internals ở mức cần thiết.
3. Phân biệt request-level latency với system throughput.
4. Tính fan-out amplification khi load tăng.
5. Kiểm tra connection pool/downstream rate limit.
6. Chọn batching/bulk/concurrency limit phù hợp.
7. Thiết kế cancellation, timeout và retry.
8. Tránh chia sẻ unsafe state như cùng một `DbContext` giữa tasks.
9. Đo bằng load test và telemetry.
10. Nêu khi nào sequential execution lại hợp lý hơn.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Hiểu `Task.WhenAll` chờ nhiều tasks hoàn tất và phù hợp khi các I/O operation độc lập có thể overlap.
- Không mô tả `Task.WhenAll` như “tạo một thread cho mỗi call”.
- Nhận ra giảm latency của một request không đồng nghĩa tăng capacity toàn hệ thống.
- Phân tích fan-out amplification theo concurrent users × calls/request.
- Không dùng unbounded concurrency tới downstream có rate/capacity limit.
- Không chia sẻ cùng `DbContext` cho concurrent EF Core operations.
- Propagate `CancellationToken` và có timeout budget.
- Retry phải bounded và không làm request storm nặng hơn.

### Điểm cộng

- Ưu tiên bulk endpoint hoặc batch lookup thay vì N calls khi provider hỗ trợ.
- Dùng `SemaphoreSlim`, bounded channel hoặc concurrency limiter ở đúng scope khi cần giới hạn fan-out.
- Có per-dependency concurrency budget thay vì một global number tùy ý.
- Theo dõi pool wait, dependency duration, 429 rate, active requests và retry amplification.

### Senior+

- Dùng Little's Law/capacity reasoning hoặc queueing intuition để giải thích vì sao latency tail tăng khi utilization gần saturation.
- Tách frontend requirement thành critical data vs optional/deferred data để giảm synchronous fan-out.
- Thiết kế bulkhead theo dependency để CRM degradation không chiếm toàn bộ request capacity.
- Có load-shedding/degradation behavior thay vì chỉ tăng timeout.

## Hướng giải quyết tham khảo

Với ba dependency độc lập, `Task.WhenAll` có thể giảm end-to-end latency vì thời gian chờ I/O được overlap. Ví dụ nếu ba call mất khoảng 300 ms, 400 ms và 700 ms, gọi tuần tự có thể gần tổng thời gian; chạy concurrent có thể gần call chậm nhất cộng overhead.

Nhưng cơ chế này không tạo ra capacity miễn phí. Với asynchronous network/database I/O, thread có thể quay lại ThreadPool trong lúc chờ completion. Vấn đề production thường không phải “mỗi task giữ một thread”, mà là số operation đồng thời đổ vào tài nguyên hữu hạn: socket/connection pool, SQL Server, downstream API, rate limit, memory và queues.

Ba call độc lập là fan-out nhỏ. Nhưng 200 pricing requests cho một HTTP request là loại khác hoàn toàn. Nếu có 100 dashboard requests đồng thời, application có thể cố tạo khoảng 20.000 pricing calls cùng lúc. Dù local CPU thấp, downstream hoặc outbound connection pools có thể saturation. Khi latency downstream tăng, operations sống lâu hơn, concurrency tích tụ tiếp và p95/p99 tăng.

Tôi sẽ kiểm tra trước xem pricing provider có bulk endpoint hay không. Nếu có API `POST /prices/query` nhận nhiều SKUs, bulk thường tốt hơn 200 HTTP calls vì giảm handshake/request overhead, rate-limit pressure và fan-out amplification.

Nếu không có bulk API, tôi dùng bounded concurrency. Ví dụ conceptually:

```csharp
public async Task<IReadOnlyList<PriceResult>> LoadPricesAsync(
    IReadOnlyList<string> skus,
    CancellationToken cancellationToken)
{
    const int maxConcurrency = 12;

    using var gate = new SemaphoreSlim(maxConcurrency);

    var tasks = skus.Select(async sku =>
    {
        await gate.WaitAsync(cancellationToken);
        try
        {
            return await _pricingClient.GetPriceAsync(
                sku,
                cancellationToken);
        }
        finally
        {
            gate.Release();
        }
    });

    return await Task.WhenAll(tasks);
}
```

Con số 12 chỉ là ví dụ minh họa, không phải recommendation cố định. Giá trị thực tế phải dựa trên provider rate limit, latency, application concurrency, outbound connection capacity và load test.

Nếu toàn application có nhiều request đồng thời, limiter chỉ nằm bên trong từng request có thể vẫn cho tổng concurrency quá lớn. Tôi có thể cần per-dependency bulkhead/concurrency limiter dùng chung ở client/integration layer để giới hạn tổng in-flight calls của instance, cùng queue bound để không biến limiter thành một queue vô hạn.

`Parallel.ForEachAsync` cũng không tự giải quyết vấn đề. Nó hữu ích khi muốn degree-of-parallelism có giới hạn, nhưng vẫn phải chọn mức phù hợp. Với I/O workload, tăng `MaxDegreeOfParallelism` quá cao vẫn có thể làm downstream saturation.

SQL cũng tương tự. Nếu hai repository methods sử dụng cùng một `DbContext`, chạy concurrent operations trên cùng context là sai vì `DbContext` không hỗ trợ nhiều parallel operations trên cùng instance. Tôi phải kiểm tra lifetime/ownership. Nếu queries thực sự cần chạy song song, mỗi operation phải có context ownership phù hợp; nhưng trước tiên cũng phải hỏi liệu parallel queries có gây pressure vào SQL connection pool/database hay không.

Timeout cần được thiết kế theo end-to-end budget. Nếu upstream request SLA là 2 giây, không hợp lý khi ba dependency mỗi cái có 10 giây timeout độc lập và retry nhiều lần. Tôi phân bổ budget, propagate caller cancellation, và không retry khi caller đã hủy request.

Retry 429/5xx/network errors phải có policy theo dependency contract. Nếu 429 có `Retry-After`, nên tôn trọng khi phù hợp. Nếu downstream đang overload, retry tức thì có thể tạo positive feedback loop. Với mutation không idempotent, retry có thể gây duplicate side effects.

Tôi cũng cân nhắc giảm synchronous dependency requirement. Nếu pricing của 200 products không cần tất cả trước first paint, frontend có thể lấy page data trước rồi request prices theo page/chunk, hoặc backend dùng cached/read-model phù hợp nếu freshness requirement cho phép. Không nên biến mọi dữ liệu thành critical synchronous path.

Verification:

- benchmark 1 user không đủ;
- load test 10/50/100/... concurrent users;
- đo dependency active calls;
- SQL pool wait/active connections;
- 429/timeout rate;
- p50/p95/p99;
- retry count;
- request cancellation;
- queue wait trong limiter;
- downstream throughput.

Nếu bounded concurrency làm p50 của một request tăng nhẹ nhưng p99 và error rate toàn hệ thống giảm mạnh, đó có thể là trade-off đúng.

## Mẫu trả lời trong phỏng vấn

“Với vài I/O độc lập, `Task.WhenAll` giúp overlap thời gian chờ nên latency của một request thường giảm. Nó không có nghĩa mỗi task tạo một thread riêng. Nhưng nó cũng không tạo thêm capacity. Nếu một request fan-out 200 pricing calls và có 100 users cùng lúc thì backend có thể đẩy 20.000 calls xuống dependency, làm rate limit, connection pool và latency tail bùng lên.

Em sẽ ưu tiên bulk API nếu có. Nếu không, em dùng bounded concurrency theo capacity của pricing service, và có thể cần limiter ở integration layer để giới hạn tổng in-flight calls trên instance chứ không chỉ từng request. Em cũng kiểm tra `DbContext` ownership vì không được chạy parallel operations trên cùng context.

Timeout, retry và cancellation phải theo end-to-end budget; retry 429/timeout không được tạo retry storm. Em load-test ở concurrency thực tế và đo p95/p99, active downstream calls, 429, pool wait và retry count trước khi chọn mức parallelism.”

## Câu hỏi đào sâu

1. Nếu pricing API cho phép tối đa 100 requests/second nhưng có 10 App Service instances, bạn đặt limiter ở đâu và xử lý tổng global rate ra sao?
2. Nếu bulk API trả chậm hơn từng request riêng lẻ ở p50 nhưng ổn định hơn nhiều ở p99, bạn chọn phương án nào và cần metric business nào?
3. Nếu một teammate nói “async thì không tốn thread nên concurrency bao nhiêu cũng được”, bạn phản biện thế nào?

## Lỗi trả lời thường gặp

- Đồng nhất asynchronous concurrency với multi-threading.
- Tối ưu latency một request nhưng không tính fan-out amplification.
- Đổi sang `Parallel.ForEachAsync` mà không xác định capacity.
- Chia sẻ một `DbContext` cho nhiều tasks.
- Retry mọi timeout/429 ngay lập tức mà không backoff/budget.

## Thang điểm 0–10

- **0–2:** Chỉ nói `Task.WhenAll` nhanh hơn hoặc chậm hơn mà không hiểu resource capacity.
- **3–4:** Hiểu concurrent I/O nhưng thiếu system-level load reasoning.
- **5–6:** Có bounded concurrency, cancellation, retry và pool awareness.
- **7–8:** Có per-dependency bulkhead, bulk API reasoning, load test và p95/p99 analysis.
- **9–10:** Cân bằng latency/throughput/fairness/degradation bằng measurable capacity model và giải thích rõ khi nào không nên parallelize.

# Câu 2 — Cosmos DB trả 429 dù tổng RU chưa “đầy”: hot partition hay chỉ thiếu throughput?

**Loại câu hỏi:** Production Incident  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 25–35 phút  
**Kỹ năng được đánh giá:** Azure Cosmos DB, partition key, RU/s, hot partition, 429 throttling, autoscale, query design, observability, incident response

## Bối cảnh

Một event-management platform dùng Azure Cosmos DB for NoSQL lưu attendee activity.

Container hiện dùng partition key:

```text
/eventId
```

Mỗi document đại diện một attendee action trong một event.

Trong các sự kiện bình thường hệ thống hoạt động ổn. Khi một event lớn mở check-in cùng lúc cho hàng chục nghìn attendees:

- API latency tăng mạnh;
- Azure Monitor thấy nhiều 429 responses;
- application log lại không thấy nhiều exception 429 tương ứng;
- tổng RU usage nhìn ở dashboard không phải lúc nào cũng đạt mức maximum của autoscale;
- một số event khác vẫn hoạt động bình thường;
- team tăng autoscale max RU/s nhưng cost tăng đáng kể, trong khi event nóng vẫn có throttling từng đợt;
- developer đề xuất đổi partition key sang `/userId` ngay lập tức;
- developer khác nói chỉ cần retry nhiều lần hơn vì SDK đã hỗ trợ retry;
- product yêu cầu check-in phải phản hồi nhanh và không được tạo duplicate attendance.

Chưa biết chắc:

- normalized RU consumption theo từng partition-key range;
- request charge của point reads/writes và queries;
- một event nóng chiếm bao nhiêu phần traffic;
- query patterns đọc theo event hay user;
- document growth theo event;
- consistency requirement;
- write idempotency hiện tại;
- autoscale configuration chính xác;
- SDK retry settings và end-to-end latency impact.

## Câu hỏi chính

Bạn sẽ xử lý incident này theo thứ tự nào, chứng minh có hot partition hay không, giải thích vì sao tổng RU nhìn “chưa đầy” vẫn có thể thấy 429, và nếu partition key hiện tại không còn phù hợp thì bạn sẽ thiết kế/migrate data model thế nào mà không phá các query chính và không làm mất correctness của check-in.

## Câu hỏi làm rõ nên cân nhắc

1. Top query patterns là “all attendees for event”, “status for one attendee”, hay analytics khác?
2. Một event lớn có thể tạo bao nhiêu writes/second và data volume trong một logical partition?
3. `eventId` có phân phối traffic tương đối đều giữa nhiều events hay có một vài event chiếm phần lớn load?
4. Client SDK retry có làm user-visible latency tăng nhưng che phần lớn 429 khỏi application logs không?
5. Check-in mutation đã có idempotency/business uniqueness theo `(eventId, attendeeId)` chưa?

## Gợi ý tư duy

### Gợi ý 1

Đừng chỉ nhìn aggregate RU. Hãy kiểm tra normalized RU theo partition-key range và distribution của request volume.

### Gợi ý 2

429 có thể được SDK retry nội bộ và request cuối cùng vẫn thành công; vì vậy application exception count có thể thấp hơn service metric.

### Gợi ý 3

Partition key là quyết định data + workload. Đổi từ `/eventId` sang `/userId` có thể sửa một hot-write pattern nhưng làm query-by-event đắt hơn rất nhiều.

## Cấu trúc trả lời đề xuất

1. Đánh giá business impact và stabilize.
2. Thu thập 429 rate, normalized RU và latency.
3. Xác định hot partition vs overall throughput exhaustion.
4. Đo request charge theo operation/query.
5. Kiểm tra SDK retry và latency amplification.
6. Phân tích partition-key workload fit.
7. Đề xuất short-term mitigation.
8. Thiết kế long-term partition/data model.
9. Lập migration/cutover/rollback plan.
10. Test load, idempotency và monitor sau migration.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không kết luận chỉ dựa vào total RU usage.
- Kiểm tra normalized RU theo partition/key range để phát hiện hot partition.
- Hiểu một partition nóng có thể throttle dù partitions khác còn capacity.
- Biết SDK Cosmos DB có retry 429 mặc định nên service metrics có thể thấy 429 nhiều hơn application exceptions.
- Không mặc định “tăng RU” là long-term fix cho skewed workload.
- Không đổi partition key mà chưa đánh giá query patterns/data distribution.
- Có idempotency cho check-in mutation.
- Có migration plan vì partition-key redesign thường liên quan container/data migration.

### Điểm cộng

- Dùng point reads với partition key + id khi có thể thay vì cross-partition query.
- Đo `RequestCharge`/RU theo operation để tìm expensive query.
- Phân biệt throughput hot spot với query inefficiency.
- Cân nhắc synthetic/composite partition key khi một natural key quá nóng.
- Có staged dual-write/read migration hoặc change-feed/backfill strategy phù hợp.

### Senior+

- Thiết kế partition strategy dựa trên cardinality + even traffic distribution + query locality + logical partition limits.
- Có strategy cho “celebrity event”/burst workload mà không overprovision toàn account.
- Định nghĩa latency/error SLO thay vì cố đạt 0 service-level 429 trong mọi tình huống.
- Thiết kế reconciliation để bảo đảm duplicate retries không tạo duplicate check-in.

## Hướng giải quyết tham khảo

Tôi sẽ không nhìn một chart tổng RU rồi kết luận thiếu hay đủ throughput. Với Cosmos DB, vấn đề quan trọng là throughput distribution giữa partition-key ranges. Một hot logical partition hoặc một physical partition-key range có thể sử dụng hết capacity được phân bổ trong khi các partition khác còn nhàn.

Tôi kiểm tra Azure Monitor/Insights theo:

- total requests by status code;
- 429 percentage;
- normalized RU consumption theo `PartitionKeyRangeId`;
- requests/RU theo operation;
- p95/p99 latency;
- request charge của representative queries;
- traffic theo `eventId`;
- SDK retry/diagnostics.

Microsoft Learn hiện nêu rằng khi normalized RU consumption của một partition-key range đạt 100%, requests tiếp theo tới range đó trong thời điểm tương ứng có thể nhận 429. Một hot partition có thể tồn tại dù aggregate throughput nhìn chưa đầy. Microsoft cũng giải thích Cosmos DB client SDKs có thể tự retry 429; vì vậy Azure Monitor thấy 429 nhưng application chưa chắc nhận exception nếu retry sau đó thành công. citeturn276560search0turn276560search1

Nếu một event lớn tập trung gần như toàn bộ writes vào cùng `/eventId`, đó là workload skew rất rõ. Tăng autoscale max RU có thể giảm pressure trong ngắn hạn, nhưng nếu traffic vẫn tập trung vào một partition/range thì cost có thể tăng mà efficiency thấp. Official guidance cũng khuyến nghị xem lại partition-key strategy khi hot partition gây 429 kéo dài thay vì chỉ overprovision tổng RU. citeturn276560search0

Tuy nhiên, tôi không lập tức đổi sang `/userId`. Partition key phải phù hợp cả write distribution và query locality. Nếu application thường xuyên cần query toàn bộ attendees theo event, `/userId` có thể biến query-by-event thành cross-partition fan-out rất lớn.

Tôi sẽ model các access patterns chính:

1. check-in một attendee;
2. verify status của attendee trong event;
3. list/filter attendees theo event;
4. aggregate count theo event;
5. admin export/report;
6. historical lookup theo user.

Một lựa chọn có thể là synthetic partition key có bucket/shard:

```text
/eventId-bucket
```

ví dụ bucket xác định từ hash của `attendeeId`. Khi đó event lớn được phân tán qua nhiều logical partitions. Nhưng trade-off là query toàn event phải fan-out across buckets hoặc dùng read model/aggregation riêng. Số bucket không nên chọn cảm tính; phải dựa trên expected traffic/data volume và operational simplicity.

Một alternative là tách transactional write model và read model: check-in writes được partition để phân phối đều, trong khi event-level counts/listing được materialize asynchronously hoặc maintain theo controlled aggregation. Điều này thêm eventual consistency và complexity, chỉ hợp lý nếu scale thực tế yêu cầu.

Short-term stabilization có thể gồm:

- scale throughput tạm thời nếu cost chấp nhận được;
- giảm expensive queries trong hot path;
- chuyển point reads đúng partition key;
- bounded retry/backoff;
- admission control nếu upstream burst vượt capacity;
- cache/read model cho reads phù hợp;
- giảm analytics/report queries cạnh tranh với transactional check-in.

Retry nhiều hơn không phải fix. Nếu capacity chưa có, retry chỉ tăng latency và thêm RU/request pressure. SDK retry có ích cho transient throttling nhưng user-facing SLO vẫn phải được đo end-to-end.

Check-in correctness cần business idempotency. Ví dụ document ID hoặc unique operation key derive từ `(eventId, attendeeId)` để retry cùng operation không tạo hai attendance records. Nếu business cho phép re-check-in update timestamp/state, semantics phải rõ.

Nếu cần repartition, tôi tạo container mới với partition key mới; không overwrite production in-place một cách mạo hiểm. Migration plan có thể:

1. tạo new container;
2. backfill historical data;
3. enable dual-write hoặc change-feed synchronization cho delta;
4. verify counts/checksums/business invariants;
5. shadow reads một phần;
6. switch read traffic theo cohort/feature flag;
7. monitor latency/RU/error;
8. switch writes hoàn toàn;
9. giữ rollback window;
10. decommission old container sau validation.

Chi tiết tool migration cụ thể phải được chọn theo supported Cosmos DB capabilities và operational constraints tại thời điểm triển khai. Microsoft hiện cũng đề cập live data migration tool cho trường hợp cần đổi partition key trong troubleshooting guidance. citeturn276560search0

Testing:

- hot event burst;
- many small events evenly distributed;
- cross-partition listing;
- point-read check-in verification;
- duplicate retry cùng attendee;
- 429 injection/throttling;
- backfill + delta migration;
- cutover/rollback;
- consistency of event counts.

Production monitoring cần ít nhất 429 percentage, normalized RU per partition range, request charge by operation, p95/p99, retries, hot event traffic distribution và check-in duplicate/conflict count.

## Mẫu trả lời trong phỏng vấn

“Em sẽ không nhìn tổng RU rồi tăng autoscale ngay. Em kiểm tra normalized RU theo partition-key range, traffic theo `eventId`, request charge và 429 rate. Nếu một range luôn 100% còn các range khác thấp thì đó là hot partition. Cosmos SDK có thể retry 429 nội bộ nên Azure Monitor có thể thấy throttling nhiều hơn application exception; điều em quan tâm vẫn là end-to-end latency và retry cost.

`/eventId` tốt cho query locality nhưng một celebrity event có thể dồn toàn bộ writes vào một logical key. Em không đổi ngay sang `/userId` vì sẽ phá query-by-event. Em sẽ model access patterns và cân nhắc synthetic key như event + bucket, hoặc tách write/read model nếu scale justify.

Short-term có thể tăng RU và giảm expensive queries để stabilize. Long-term nếu đổi partition key, em tạo container mới, backfill + sync delta, shadow/verify rồi cutover có rollback. Check-in phải idempotent theo business key để retry không tạo duplicate.”

## Câu hỏi đào sâu

1. Nếu 95% workload là query all attendees by event nhưng chỉ 1% events có burst rất lớn, bạn có chấp nhận bucketed partition key cho toàn bộ data không?
2. Nếu autoscale đã tăng nhưng normalized RU của một partition range vẫn 100%, bạn cần thêm evidence nào trước khi repartition?
3. Nếu product yêu cầu check-in response dưới 300 ms p99 trong peak event, bạn sẽ thay đổi architecture hay capacity plan như thế nào?

## Lỗi trả lời thường gặp

- Chỉ tăng RU/s mà không kiểm tra workload skew.
- Đổi partition key chỉ dựa trên cardinality mà bỏ qua query locality.
- Cho rằng SDK retry làm 429 “không còn vấn đề”.
- Không đo request charge của queries.
- Migration partition key kiểu big-bang không có validation/rollback.

## Thang điểm 0–10

- **0–2:** Chỉ nói tăng RU hoặc bật autoscale.
- **3–4:** Biết hot partition nhưng không biết chứng minh hoặc redesign.
- **5–6:** Có normalized RU, request charge, partition-key trade-off và retry awareness.
- **7–8:** Có synthetic partition/read-model reasoning, idempotency, migration và load testing.
- **9–10:** Thiết kế partitioning theo workload thật, cân bằng cost/latency/query locality và có safe migration/operational evidence.

# Câu 3 — Public API đang được mobile app, SPA và partner sử dụng: nâng contract mà không tạo “flag day” như thế nào?

**Loại câu hỏi:** Architecture / System Design / Engineering Decision  
**Độ khó:** Senior+  
**Thời gian trả lời đề xuất:** 30–40 phút  
**Kỹ năng được đánh giá:** ASP.NET Core API design, HTTP semantics, API versioning, backward compatibility, deployment, database migration, mobile compatibility, observability, engineering process

## Bối cảnh

Một customer platform có ASP.NET Core REST API đang phục vụ:

- React/Vue web application được deploy hàng tuần;
- mobile app mà user có thể không update trong nhiều tháng;
- 6 partner integrations;
- một legacy internal portal vẫn dùng contract cũ.

Endpoint hiện tại:

```http
GET /api/orders/{id}
```

Response rút gọn:

```json
{
  "id": "123",
  "status": "Paid",
  "customerName": "A",
  "total": 120.5,
  "currency": "USD"
}
```

Business muốn thay đổi model:

- `status` từ string đơn giản thành state chi tiết hơn;
- tách customer thành nested object;
- hỗ trợ multiple payments;
- thêm field cho localization;
- một số field cũ sẽ không còn source-of-truth tương ứng;
- database cũng cần schema migration.

Một developer đề xuất thay response hiện tại và deploy frontend cùng lúc.

Một architect đề xuất tạo `/api/v2` cho mọi thay đổi, copy toàn bộ controller/service rồi duy trì v1 và v2 vô thời hạn.

Một developer khác đề xuất GraphQL rewrite để “khỏi version API”.

Constraints:

- mobile users không thể bị ép update ngay;
- partner cần ít nhất một khoảng deprecation notice nhưng thời gian cụ thể chưa được chốt;
- release phải rollback được;
- database migration không được gây downtime dài;
- API chạy nhiều App Service instances;
- team muốn giảm duplicate logic;
- Product cần biết client nào vẫn dùng contract cũ trước khi decommission.

Chưa biết chắc:

- breaking changes nào thật sự bắt buộc;
- versioning style hiện tại;
- mobile minimum supported versions;
- partner SLA/deprecation contract;
- schema migration có thể backward-compatible không;
- field cũ có thể derive tạm thời từ model mới hay không;
- traffic theo từng client/version.

## Câu hỏi chính

Hãy thiết kế chiến lược API evolution và rollout cho thay đổi này: xác định khi nào cần version mới, khi nào có thể mở rộng contract không breaking, cách tránh duplicate business logic, cách migrate database theo từng bước, cách theo dõi adoption và cuối cùng decommission contract cũ một cách an toàn.

## Câu hỏi làm rõ nên cân nhắc

1. Client nào do cùng team kiểm soát và client nào có lifecycle độc lập?
2. `status` mới có thể map backward về status cũ một cách deterministic hay không?
3. Partner agreement hiện quy định deprecation notice/support window như thế nào?
4. Mobile app cũ có thể tiếp tục hoạt động nếu backend giữ compatibility trong bao lâu?
5. Database change có thể triển khai theo expand-contract hay bắt buộc destructive migration?

## Gợi ý tư duy

### Gợi ý 1

API versioning là một phần của compatibility strategy, không phải lý do để copy toàn bộ application logic.

### Gợi ý 2

Tách external contract khỏi internal domain/application model. Hai API versions có thể map vào cùng use case/business logic.

### Gợi ý 3

Schema migration và API migration phải phối hợp theo deployment order để old và new app versions có thể cùng chạy trong rollout/rollback window.

## Cấu trúc trả lời đề xuất

1. Inventory clients và compatibility obligations.
2. Phân loại additive vs breaking changes.
3. Định nghĩa versioning/deprecation policy.
4. Tách contract DTO mapping khỏi business logic.
5. Thiết kế database expand-contract migration.
6. Deploy backend backward-compatible trước.
7. Migrate web/mobile/partners theo cohort.
8. Theo dõi version adoption/usage.
9. Decommission theo evidence và contract.
10. Test rollback, mixed-version và schema compatibility.

## Ý chính của câu trả lời tốt

### Bắt buộc

- Không thay breaking response in-place khi uncontrolled clients còn dùng.
- Không giả định deploy frontend và backend cùng lúc giải quyết mobile/partner compatibility.
- Phân biệt additive non-breaking change với breaking semantic/shape change.
- Tách API DTO/version adapter khỏi shared business logic.
- Không copy toàn bộ controller/service stack cho mỗi version nếu không cần.
- Có deprecation policy và usage telemetry theo client/version.
- Schema migration phải backward-compatible trong rollout window.
- Có rollback strategy.

### Điểm cộng

- Dùng expand-contract: add new schema → dual-read/write hoặc compatibility mapping → migrate data → switch → remove old later.
- Version negotiation có thể qua URL/header/media type tùy project conventions; không coi một style là universal.
- Có consumer contract tests cho partner/mobile versions.
- Có `Sunset`/deprecation communication strategy khi ecosystem/client contract phù hợp.
- Feature flags/cohort rollout cho new behavior.

### Senior+

- Thiết kế compatibility matrix giữa app version × API version × schema version.
- Có anti-corruption/translation layer để old status vẫn được derive trong migration window.
- Có telemetry để phát hiện “unknown legacy clients” trước decommission.
- Định nghĩa governance để không giữ v1/v2 vô thời hạn.

## Hướng giải quyết tham khảo

Tôi bắt đầu bằng client inventory. Web app do team kiểm soát có thể update nhanh; mobile và partners có release lifecycle độc lập; legacy portal có thể có owner khác. Vì vậy “deploy frontend cùng lúc” chỉ giải quyết một phần consumers.

Tiếp theo tôi phân loại thay đổi:

- thêm field optional thường có thể non-breaking nếu clients ignore unknown fields;
- đổi type/shape từ `customerName` sang `customer: {...}` là breaking nếu bỏ field cũ;
- đổi semantics của `status` dù JSON type vẫn là string cũng có thể breaking nếu client logic phụ thuộc enum values;
- multiple payments có thể additive nếu giữ `total`/legacy aggregate semantics rõ;
- remove/rename field là breaking.

Tôi không version chỉ vì thêm field. Version mới nên xuất hiện khi external contract/semantics thật sự không thể tương thích hợp lý.

Kiến trúc nên tách external contracts khỏi application/domain model. Ví dụ:

```text
Order application use case
        ↓
Canonical application result
        ↓
 ┌──────────────┬──────────────┐
 │ V1 mapper    │ V2 mapper    │
 │ legacy shape │ new shape    │
 └──────────────┴──────────────┘
```

V1 và V2 không cần copy business logic, repositories hoặc domain services. Chúng có thể có endpoint/controller adapters riêng nhưng dùng cùng core use case. V1 mapper derive legacy `customerName`/`status` từ canonical model nếu mapping còn xác định được.

Nếu status mới không thể map losslessly về old status, Product/business phải quyết định degraded legacy semantics trong deprecation period. Ví dụ nhiều detailed states có thể collapse về `Processing`; cần document rõ chứ không silently đổi behavior.

Tôi không rewrite sang GraphQL chỉ để tránh versioning. GraphQL cũng có schema-evolution/field-deprecation concerns và client compatibility. Chọn GraphQL chỉ khi query flexibility/consumer patterns justify operational/tooling complexity.

Database migration cần chịu mixed-version deployment. Với App Service rolling/slot deployment, có thể tồn tại old/new code cùng thời điểm hoặc cần rollback. Vì vậy destructive migration trước code là nguy hiểm.

Một expand-contract sequence có thể:

1. thêm new tables/columns nullable/backward-compatible;
2. deploy code version A hiểu old schema và có thể populate new schema;
3. backfill data;
4. verify consistency;
5. deploy API V2/read path từ new model;
6. migrate clients;
7. ngừng phụ thuộc old fields;
8. chỉ sau support/deprecation window mới drop old schema.

Nếu dual-write cần thiết, phải xác định source of truth và failure behavior. Dual-write vô thời hạn dễ drift. Có thể dùng single transaction khi cùng database, hoặc migration adapter có clear ownership.

Rollout:

- backend compatibility trước client;
- expose V2 without removing V1;
- update web first để validate;
- mobile rollout theo store adoption;
- partner sandbox/contract docs + migration window;
- legacy portal migration;
- monitor usage.

Telemetry nên ghi API version/route, client/application identity khi có, user-agent/app version, success/error rate và traffic volume. Không log secrets/token. Tôi cần dashboard biết V1 còn client nào gọi, volume bao nhiêu và critical endpoint nào.

Deprecation phải có policy. Ví dụ announce date, migration guide, support window, warning headers/docs nếu phù hợp, owner contacts và final cutoff. Con số thời gian phải theo partner contract/business risk, không tự bịa.

Testing:

- golden/contract tests cho V1 response;
- V2 contract tests;
- old mobile client against new backend;
- partner consumer tests;
- mixed schema during rollout;
- rollback new backend after schema expand;
- status translation edge cases;
- API version routing;
- Playwright/E2E web flow cho new contract.

Deployment safety:

- schema expand deploy trước;
- application compatible với both schema states;
- health/smoke tests;
- staged traffic/slot swap nếu phù hợp;
- rollback app không yêu cầu rollback destructive DB change;
- contract removal chỉ ở release riêng sau khi telemetry chứng minh usage gần/đạt zero và approval đã có.

Tôi cũng định nghĩa governance để v1 không sống mãi. Mỗi version có owner, deprecation criteria và telemetry. Nếu một partner không migrate, đó là product/commercial decision cần escalation, không phải lý do kỹ thuật để silently break họ.

## Mẫu trả lời trong phỏng vấn

“Em sẽ inventory consumers trước vì web, mobile và partners có lifecycle khác nhau. Em phân loại additive change với breaking change; thêm optional field không cần tạo version mới, nhưng đổi shape hoặc semantics mà client cũ không hiểu thì cần compatibility layer/version mới.

Em không copy toàn bộ service cho V2. V1/V2 chỉ là contract adapters map vào cùng application use case. Trong migration window, V1 mapper có thể derive legacy fields từ canonical model nếu mapping deterministic.

Database em dùng expand-contract: add schema mới trước, deploy code backward-compatible, backfill/verify, rồi mới switch reads và sau cùng mới remove old schema. Backend V2 deploy trước clients; web migrate sớm, mobile/partners theo rollout window. Em đo traffic theo API/client version để biết ai còn dùng V1 và chỉ decommission khi contract + telemetry cho phép. Rollback phải vẫn chạy được trên schema đã expand.”

## Câu hỏi đào sâu

1. Nếu status mới có 12 states nhưng V1 chỉ có 4 và một số state mới không map chính xác, bạn giữ backward compatibility thế nào?
2. Nếu một partner quan trọng vẫn dùng V1 sau deprecation deadline, bạn sẽ xử lý technical risk và business decision ra sao?
3. Nếu database migration cần đổi một column từ nullable sang non-null và drop field cũ, bạn sequence deployment thế nào để rollback application vẫn an toàn?

## Lỗi trả lời thường gặp

- Deploy breaking contract cùng frontend rồi coi như đã giải quyết compatibility.
- Tạo V2 bằng cách copy toàn bộ business logic.
- Giữ mọi version vĩnh viễn không có deprecation governance.
- Drop/rename DB columns trong cùng release với code mới.
- Không có telemetry để biết client nào còn dùng V1.

## Thang điểm 0–10

- **0–2:** Chỉ nói thêm `/v2` hoặc rewrite frontend/backend cùng lúc.
- **3–4:** Hiểu breaking changes nhưng thiếu migration/rollback.
- **5–6:** Có DTO adapters, deprecation, expand-contract và tests.
- **7–8:** Có client lifecycle, telemetry-driven decommission, compatibility matrix và staged rollout.
- **9–10:** Thiết kế API/schema evolution như một operational capability, cân bằng technical correctness, partner commitments và rollback safety.

# Tổng kết hôm nay

## Kiến thức trọng tâm

- **Async concurrency không tạo capacity miễn phí:** `Task.WhenAll` giúp overlap I/O nhưng fan-out lớn có thể làm saturate downstream, connection pools và latency tail.
- **Concurrency phải bounded theo dependency:** bulk API, batching, per-dependency limits và retry budget thường quan trọng hơn việc tạo thêm tasks.
- **Cosmos DB cần nhìn distribution, không chỉ aggregate RU:** hot partition có thể gây 429 dù tổng throughput chưa được dùng đều. citeturn276560search0turn276560search1
- **Partition key là workload decision:** cần cân bằng write distribution, query locality, data growth và migration cost.
- **API evolution là compatibility problem:** versioning chỉ là một công cụ; contract adapters, deprecation policy, telemetry và schema evolution mới tạo rollout an toàn.
- **Database migration phải hỗ trợ mixed-version deployment:** expand-contract giúp giảm blast radius và giữ rollback path.

## Mẫu tư duy cần nhớ

1. **Optimize system throughput, not only single-request latency.**
2. **Measure distribution, not only aggregates.**
3. **Retry is not capacity; design it with backoff, idempotency and latency budget.**
4. **Separate external contracts from internal models.**
5. **Expand first, migrate, verify, then contract.**
