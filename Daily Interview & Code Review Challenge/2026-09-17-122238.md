# Code Review Challenge 1 — File upload API đọc toàn bộ file vào RAM và tin `FileName` từ client

**Chủ đề:** C#/.NET, ASP.NET Core file handling, Azure Blob Storage, security, streaming, cancellation  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–35 phút  
**Số vấn đề cần tìm:** khoảng 8–10

## Bối cảnh

Một enterprise portal cho phép người dùng upload tài liệu đính kèm. API chạy nhiều instances trên Azure App Service Linux và lưu file vào Azure Blob Storage. File thông thường 1–10 MB, nhưng business cho phép tối đa 250 MB. Sau khi feature được mở rộng cho nhiều users, memory của application tăng mạnh khi có nhiều uploads đồng thời; một số instances restart. Security review cũng phát hiện blob name và content type đang lấy trực tiếp từ dữ liệu client gửi lên.

Business cần upload đáng tin cậy, không overwrite file ngoài ý muốn, không giữ toàn bộ payload trong memory, hỗ trợ client cancellation và phải có audit metadata. Chưa xác định requirement về malware scanning; ứng viên cần nêu đây là điểm phải làm rõ thay vì tự giả định.

## Đoạn code cần review

```csharp
[ApiController]
[Route("api/documents")]
public sealed class DocumentsController : ControllerBase
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;
    private readonly ILogger<DocumentsController> _logger;

    public DocumentsController(
        BlobContainerClient container,
        AppDbContext db,
        ILogger<DocumentsController> logger)
    {
        _container = container;
        _db = db;
        _logger = logger;
    }

    [HttpPost("upload")]
    public async Task<IActionResult> Upload(IFormFile file)
    {
        if (file.Length == 0)
            return BadRequest("Empty file");

        using var buffer = new MemoryStream();
        await file.CopyToAsync(buffer);

        var bytes = buffer.ToArray();
        var blob = _container.GetBlobClient(file.FileName);

        await blob.UploadAsync(
            new BinaryData(bytes),
            overwrite: true);

        var document = new Document
        {
            Id = Guid.NewGuid(),
            FileName = file.FileName,
            BlobName = file.FileName,
            ContentType = file.ContentType,
            Size = bytes.Length,
            UploadedAtUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync();

        _logger.LogInformation(
            "Uploaded {FileName} ({Size} bytes)",
            file.FileName,
            bytes.Length);

        return Ok(new { document.Id, document.FileName });
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness và data-consistency problems.
2. Xác định memory, security, reliability và scalability concerns.
3. Giải thích production impact khi nhiều users upload file lớn đồng thời.
4. Ưu tiên findings theo severity.
5. Đề xuất corrected design cho streaming, blob naming, validation và metadata persistence.
6. Giải thích testing cho large files, cancellation, duplicate names và dependency failure.
7. Nêu telemetry production cần có để chứng minh upload path an toàn và ổn định.

## Câu hỏi gợi mở

1. Một file 250 MB tạo bao nhiêu bản copy trong managed memory với `MemoryStream` + `ToArray()` + `BinaryData`?
2. `file.FileName` có phải server-controlled identifier không?
3. Điều gì xảy ra nếu blob upload thành công nhưng `SaveChangesAsync()` thất bại?
4. `overwrite: true` có đúng business semantics khi hai users upload cùng tên file không?
5. Client disconnect giữa upload có dừng copy/blob/database work hiện tại không?

## Gợi ý

### Gợi ý 1

Primary risks là unbounded memory amplification và việc dùng client metadata như storage identity.

### Gợi ý 2

Blob Storage và SQL không nằm trong cùng local transaction. Hãy xem failure window giữa hai systems và thiết kế trạng thái/recovery thay vì giả định atomicity.

## Kết quả code review tham khảo

### Critical — Upload materialize toàn bộ file và tạo nhiều memory copies

**Vấn đề:** request được copy vào `MemoryStream`, sau đó `ToArray()` tạo thêm byte array trước khi upload.  
**Tại sao xảy ra:** implementation biến streaming input thành fully buffered payload.  
**Ảnh hưởng production:** concurrent large uploads tạo allocation pressure rất lớn, GC/LOH pressure và có thể làm instance restart/OOM.  
**Cách sửa:** stream trực tiếp từ upload stream tới Blob Storage, áp request/file-size limit và bounded concurrency phù hợp capacity. Không dùng full-memory buffering cho file lớn.

### Critical — Client-controlled filename được dùng làm blob identity với overwrite

**Vấn đề:** `file.FileName` trở thành blob name và `overwrite: true`.  
**Tại sao xảy ra:** display metadata bị trộn với server storage identity.  
**Ảnh hưởng production:** hai uploads cùng tên có thể overwrite nhau; malicious/odd names gây ambiguity và khó audit.  
**Cách sửa:** tạo server-controlled blob key, ví dụ document ID + normalized extension nếu extension thực sự cần. Lưu original filename chỉ như display metadata đã được xử lý phù hợp.

### High — Blob và database có failure window không atomic

**Vấn đề:** blob được upload trước, DB metadata commit sau.  
**Tại sao xảy ra:** hai external resources không cùng transaction.  
**Ảnh hưởng production:** DB failure để lại orphan blob; ngược lại các redesign khác có thể để metadata trỏ tới blob chưa tồn tại.  
**Cách sửa:** thiết kế explicit state machine/reconciliation: tạo metadata `Pending`, upload blob, mark `Ready`; cleanup/retry orphan/pending records. Với requirement đơn giản có thể upload trước rồi cleanup orphan theo deterministic blob ID, nhưng phải có recovery job/telemetry.

### High — CancellationToken không được propagate

**Vấn đề:** file copy, blob upload và EF save không dùng `RequestAborted`.  
**Tại sao xảy ra:** async APIs được gọi mà bỏ qua request cancellation.  
**Ảnh hưởng production:** client disconnect vẫn tiêu tốn network/storage/database resources.  
**Cách sửa:** propagate `HttpContext.RequestAborted` qua cancellable operations và quyết định cleanup semantics khi cancellation xảy ra giữa các bước.

### High — Validation chỉ kiểm tra `Length == 0`

**Vấn đề:** không enforce maximum size, allowed file types/business rules hoặc server-side content policy.  
**Tại sao xảy ra:** tin client metadata và framework binding là đủ.  
**Ảnh hưởng production:** oversized/unexpected files tăng resource risk; content type có thể bị spoof.  
**Cách sửa:** enforce server-side limits, validate business-supported extensions/content signatures khi cần. Nếu malware scanning là requirement, thiết kế quarantine/scanning workflow; không tự tuyên bố file “safe” chỉ từ MIME type.

### Medium — `ContentType` từ client được lưu như authoritative metadata

**Vấn đề:** `file.ContentType` do request cung cấp.  
**Tại sao xảy ra:** MIME metadata được tin mà không phân biệt claimed và validated type.  
**Ảnh hưởng production:** downstream download/render logic có thể xử lý file sai hoặc tạo security issue nếu serve inline.  
**Cách sửa:** coi đây là claimed content type; validate/detect theo policy nếu downstream behavior phụ thuộc nó, và khi download dùng safe content-disposition/content-type rules.

### Medium — Controller chịu cả transport, storage workflow và persistence orchestration

**Vấn đề:** endpoint trực tiếp điều phối mọi responsibility.  
**Tại sao xảy ra:** thiếu application-level upload workflow abstraction.  
**Ảnh hưởng production:** khó test failure windows, retry/reconciliation và security policy.  
**Cách sửa:** đưa workflow vào service/use case có explicit states; controller chỉ bind request, authorize và map result.

### Medium — Không có concurrency/capacity control

**Vấn đề:** mọi request có thể stream/upload đồng thời không giới hạn ngoài infrastructure defaults.  
**Tại sao xảy ra:** không có capacity model cho large uploads.  
**Ảnh hưởng production:** dù streaming, quá nhiều concurrent 250 MB uploads vẫn có thể saturate bandwidth/connections/storage throughput.  
**Cách sửa:** đo capacity; dùng request limits, quotas/rate limits hoặc direct-to-Blob upload bằng short-lived SAS khi phù hợp để offload application path.

### Low — Telemetry không mô tả lifecycle/failure stage

**Vấn đề:** chỉ log success filename/size.  
**Tại sao xảy ra:** không có upload ID, stage, duration hoặc failure classification.  
**Ảnh hưởng production:** khó tìm orphan/pending uploads và bottleneck.  
**Cách sửa:** structured telemetry với document ID, safe blob ID, size, duration, stage, outcome, storage dependency duration và correlation ID; không log sensitive content.

## Phiên bản đề xuất

Ví dụ dưới đây dùng server-generated identity, streaming và explicit `Pending` → `Ready`. Cleanup/reconciliation vẫn cần cho failure giữa storage và DB.

```csharp
public sealed class DocumentUploadService
{
    private readonly BlobContainerClient _container;
    private readonly AppDbContext _db;

    public DocumentUploadService(
        BlobContainerClient container,
        AppDbContext db)
    {
        _container = container;
        _db = db;
    }

    public async Task<Guid> UploadAsync(IFormFile file, CancellationToken ct)
    {
        const long maxBytes = 250L * 1024 * 1024;

        if (file.Length <= 0 || file.Length > maxBytes)
            throw new InvalidDataException("Invalid file size.");

        var id = Guid.NewGuid();
        var extension = Path.GetExtension(Path.GetFileName(file.FileName));
        var blobName = $"documents/{id:N}{extension}";

        var document = new Document
        {
            Id = id,
            FileName = Path.GetFileName(file.FileName),
            BlobName = blobName,
            ClaimedContentType = file.ContentType,
            Size = file.Length,
            Status = DocumentStatus.Pending,
            UploadedAtUtc = DateTime.UtcNow
        };

        _db.Documents.Add(document);
        await _db.SaveChangesAsync(ct);

        var blob = _container.GetBlobClient(blobName);

        try
        {
            await using var input = file.OpenReadStream();
            await blob.UploadAsync(input, overwrite: false, cancellationToken: ct);

            document.Status = DocumentStatus.Ready;
            await _db.SaveChangesAsync(ct);
            return id;
        }
        catch
        {
            document.Status = DocumentStatus.Failed;

            try
            {
                await _db.SaveChangesAsync(CancellationToken.None);
            }
            catch
            {
                // Reconciliation must detect stale Pending records.
            }

            throw;
        }
    }
}
```

## Giải thích thiết kế sau khi sửa

Server-generated blob name tách storage identity khỏi display filename và loại overwrite do name collision. Streaming tránh full-file memory copies. `Pending/Ready/Failed` làm failure state quan sát được thay vì giả atomic transaction giữa SQL và Blob Storage.

Nếu traffic/file size lớn và browser/mobile client có thể upload trực tiếp, một lựa chọn khác là backend cấp short-lived, least-privilege SAS cho một server-chosen blob name rồi client upload trực tiếp. Backend sau đó xác minh completion và finalize metadata. Thiết kế đó giảm application bandwidth nhưng tăng protocol/state/security complexity, nên chỉ dùng khi scale/cost chứng minh cần thiết.

## Trade-offs

State machine/reconciliation thêm complexity nhưng đổi lại failure behavior rõ ràng. Streaming giảm memory nhưng không loại network/storage capacity limits. Direct-to-Blob SAS offload server tốt hơn nhưng cần expiration, permissions, completion verification và cleanup abandoned uploads. Malware scanning, nếu bắt buộc, thường cần quarantine lifecycle và không nên được giả định miễn phí trong synchronous request.

## Cách kiểm thử

1. **Load test:** nhiều concurrent large uploads; memory phải bounded và không tỷ lệ tuyến tính theo tổng file bytes đang upload.
2. **Cancellation test:** client abort giữa stream; verify operation dừng và record chuyển/reconcile về trạng thái phù hợp.
3. **Concurrency test:** hai users upload cùng original filename; blob identities phải khác và không overwrite.
4. **Failure-path integration test:** inject Blob failure và DB failure ở từng transition; verify pending/orphan recovery semantics.
5. **Security test:** filename/path-like input, spoofed MIME type và unsupported content phải được xử lý theo policy; download không được render unsafe content ngoài ý muốn.

## Quan sát trong production

Theo dõi active uploads, upload bytes, p95/p99 duration theo size bucket, request-abort count, App Service memory/GC, Blob dependency latency/failure, Pending age, Failed count và orphan cleanup outcomes. Alert khi Pending vượt lifecycle SLO hoặc memory tăng bất thường theo concurrent upload count.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn direct-to-Blob SAS thay vì proxy upload qua ASP.NET Core?
2. Nếu malware scanning bắt buộc nhưng scanner mất vài phút, bạn thiết kế download availability/state transitions thế nào?
3. Nếu DB commit `Ready` thất bại sau blob upload thành công, reconciliation xác định ownership và cleanup thế nào?

# Code Review Challenge 2 — Jenkins pipeline build lại artifact ở production và làm rollback không còn deterministic

**Chủ đề:** CI/CD, Jenkins, artifact provenance, secrets, deployment safety, rollback  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–30 phút  
**Số vấn đề cần tìm:** khoảng 7–9

## Bối cảnh

Một .NET application được deploy lên IIS qua Jenkins. Team có ba environments: test, staging, production. Pipeline hiện checkout source và chạy `dotnet publish` riêng ở từng environment. Production deployment đôi khi chứa binary khác staging dù cùng commit được ghi trong ticket. Khi rollback, pipeline checkout branch rồi build lại “version trước”. Một connection string production được truyền trực tiếp trong command. Team muốn giữ quy trình đơn giản nhưng cần bảo đảm artifact đã test chính là artifact được promote và rollback có thể tái lập.

## Đoạn code cần review

```groovy
pipeline {
    agent any

    parameters {
        string(name: 'BRANCH', defaultValue: 'main')
        choice(name: 'ENVIRONMENT', choices: ['test', 'staging', 'production'])
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: params.BRANCH,
                    url: 'https://github.com/example/portal.git'
            }
        }

        stage('Build') {
            steps {
                bat 'dotnet restore'
                bat 'dotnet publish src/Portal/Portal.csproj -c Release -o publish'
            }
        }

        stage('Test') {
            when {
                expression { params.ENVIRONMENT != 'production' }
            }
            steps {
                bat 'dotnet test -c Release'
            }
        }

        stage('Deploy') {
            steps {
                bat """
                    deploy-iis.cmd publish \
                      ${params.ENVIRONMENT} \
                      Server=prod-sql;Database=Portal;User Id=portal;Password=P@ssw0rd
                """
            }
        }
    }

    post {
        failure {
            echo 'Rollback: rerun this job with the previous branch.'
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định correctness/release-safety problems.
2. Xác định secret exposure và supply-chain/provenance concerns.
3. Giải thích vì sao staging và production có thể khác dù ticket ghi cùng commit.
4. Ưu tiên các vấn đề ảnh hưởng production/rollback.
5. Đề xuất pipeline design theo nguyên tắc build once, promote immutable artifact.
6. Giải thích testing/deployment validation/rollback tests.
7. Nêu telemetry/audit metadata cần lưu cho mỗi release.

## Câu hỏi gợi mở

1. `BRANCH=main` có xác định immutable source revision không?
2. Nếu production build chạy một ngày sau staging, dependency restore/build environment có thể thay đổi điều gì?
3. “Build lại previous branch” có đảm bảo tạo đúng bytes đã chạy trước đây không?
4. Secret xuất hiện ở command/script có thể bị lộ ở đâu?
5. Production đang bỏ qua test stage dựa trên environment; artifact nào thực sự đã được test?

## Gợi ý

### Gợi ý 1

Primary issue là artifact identity/provenance: pipeline đang coi source branch là release artifact.

### Gợi ý 2

Rollback đáng tin cậy cần deploy lại một immutable artifact đã biết, không phải tái tạo artifact bằng một build mới trong tương lai.

## Kết quả code review tham khảo

### Critical — Secret production được hard-code/truyền trực tiếp trong pipeline command

**Vấn đề:** credential nằm trong Jenkinsfile/command arguments.  
**Tại sao xảy ra:** configuration secret bị trộn với deployment script.  
**Ảnh hưởng production:** secret có thể xuất hiện trong source, console logs, process arguments hoặc job metadata tùy tooling.  
**Cách sửa:** dùng Jenkins credentials/secret store hoặc environment-specific secret mechanism với least privilege; tránh echo và không đóng gói production secrets vào artifact.

### High — Build riêng cho từng environment phá artifact promotion

**Vấn đề:** staging và production đều rebuild source.  
**Tại sao xảy ra:** pipeline promote branch/commit intent thay vì immutable artifact.  
**Ảnh hưởng production:** production bytes có thể khác artifact đã test do source ref movement, dependency resolution, SDK/tooling/environment hoặc build inputs thay đổi.  
**Cách sửa:** CI build một artifact từ immutable commit SHA, test artifact/build outputs, publish vào artifact repository với digest/version; CD promote đúng artifact đó qua environments.

### High — Branch parameter không phải immutable release identity

**Vấn đề:** `main` hoặc bất kỳ branch nào có thể move.  
**Tại sao xảy ra:** mutable ref được dùng làm deployment source.  
**Ảnh hưởng production:** rerun cùng parameters có thể deploy code khác.  
**Cách sửa:** resolve và record exact commit SHA ở build; release reference phải trỏ artifact version/digest gắn với SHA.

### High — Rollback bằng rebuild không deterministic

**Vấn đề:** hướng dẫn rerun previous branch để rollback.  
**Tại sao xảy ra:** không giữ immutable deployable artifact/version manifest.  
**Ảnh hưởng production:** rollback có thể tạo binary mới khác binary cũ và kéo dependency/tooling khác.  
**Cách sửa:** retain known-good artifacts và deployment manifests; rollback bằng redeploy exact artifact. Database/schema compatibility vẫn phải được thiết kế riêng vì app rollback không đồng nghĩa DB rollback an toàn.

### High — Production path bỏ test

**Vấn đề:** `dotnet test` không chạy khi `ENVIRONMENT == production`.  
**Tại sao xảy ra:** testing gắn với deployment environment thay vì artifact lifecycle.  
**Ảnh hưởng production:** production rebuild chưa được test trong chính run đó; quan trọng hơn, nó cũng không phải artifact đã test trước.  
**Cách sửa:** test ở CI trước khi artifact được publish/promote; production CD không rebuild và có deployment smoke/health validation riêng.

### Medium — Restore/build không pin đủ build inputs

**Vấn đề:** snippet không cho thấy locked dependencies, pinned SDK/toolchain hoặc reproducibility controls.  
**Tại sao xảy ra:** build được xem là deterministic mặc định.  
**Ảnh hưởng production:** dependency/toolchain drift làm cùng source có output/behavior khác.  
**Cách sửa:** pin SDK/toolchain phù hợp, lock dependencies khi policy yêu cầu, record build metadata/SBOM/digest; không tuyên bố byte-for-byte reproducible nếu pipeline chưa chứng minh.

### Medium — Không có approval/gating hoặc production-specific validation rõ ràng

**Vấn đề:** bất kỳ selected environment đều đi cùng một deploy stage trong snippet.  
**Tại sao xảy ra:** release governance không được model thành pipeline gates.  
**Ảnh hưởng production:** accidental production deploy hoặc promote artifact chưa đủ validation.  
**Cách sửa:** environment permissions/approval theo organizational policy, automated pre-deploy checks và post-deploy smoke/health checks.

### Medium — Deployment metadata/audit trail thiếu

**Vấn đề:** pipeline không record artifact digest, commit SHA, build ID, deployer, target và previous version.  
**Tại sao xảy ra:** release được nhận diện bằng branch/environment.  
**Ảnh hưởng production:** incident response/rollback khó xác định chính xác production đang chạy gì.  
**Cách sửa:** release manifest và structured deployment events; expose application version/commit safely qua telemetry/health metadata.

### Low — `agent any` làm build environment khó kiểm soát

**Vấn đề:** build có thể chạy trên agents khác nhau.  
**Tại sao xảy ra:** không pin build image/toolchain label.  
**Ảnh hưởng production:** môi trường build drift và debugging khó hơn.  
**Cách sửa:** dùng controlled build agent/container/image hoặc toolchain configuration được version hóa.

## Phiên bản đề xuất

Ví dụ conceptual Jenkins pipeline dưới đây tách CI build artifact khỏi deployment. Production deploy nhận `ARTIFACT_VERSION`, không nhận branch để rebuild.

```groovy
pipeline {
    agent { label 'dotnet-build' }

    parameters {
        string(name: 'COMMIT_SHA', description: 'Immutable Git commit SHA')
    }

    stages {
        stage('Checkout') {
            steps {
                checkout([$class: 'GitSCM',
                    branches: [[name: params.COMMIT_SHA]],
                    userRemoteConfigs: [[url: 'https://github.com/example/portal.git']]])
            }
        }

        stage('Build and Test') {
            steps {
                bat 'dotnet restore --locked-mode'
                bat 'dotnet test -c Release --no-restore'
                bat 'dotnet publish src/Portal/Portal.csproj -c Release --no-restore -o publish'
            }
        }

        stage('Package') {
            steps {
                bat 'package-release.cmd publish %COMMIT_SHA%'
                archiveArtifacts artifacts: 'artifacts/**', fingerprint: true
            }
        }
    }
}
```

```groovy
}
```

Exact Jenkins credential syntax/tooling có thể khác theo plugin/configuration; nguyên tắc cần giữ là secret không nằm trong source/artifact/log và deployment promote immutable artifact đã được CI kiểm chứng.

## Giải thích thiết kế sau khi sửa

Build once tạo một release unit có identity rõ: commit SHA + artifact version/digest + build metadata. Test/staging/production chỉ promote cùng release unit. Environment configuration/secrets được inject ở deployment/runtime boundary thay vì rebuild application.

Rollback trở thành chọn known-good artifact trước đó và redeploy. Tuy nhiên database migration phải tương thích với rollback; nếu release có destructive schema change thì exact old binary vẫn có thể không chạy với new schema. Vì vậy release strategy cần expand/contract hoặc compatibility window khi DB thay đổi.

## Trade-offs

Artifact repository/retention và pipeline separation thêm operational setup. Pinning dependencies/toolchain tăng maintenance khi upgrade nhưng giảm drift. Approval gates có thể làm lead time dài hơn, nên nên tự động hóa validation nhiều nhất có thể và chỉ giữ human gate nơi risk/governance yêu cầu.

## Cách kiểm thử

1. **Artifact promotion test:** staging và production release phải có cùng digest/version.
2. **Rollback drill:** deploy version N+1 rồi redeploy exact N artifact; verify application và schema compatibility.
3. **Secret leakage test:** Jenkins logs/artifacts không chứa credentials; credential rotation không cần rebuild artifact.
4. **Deployment failure test:** fail giữa deploy; verify previous version/partial deployment recovery procedure.
5. **Provenance validation:** release manifest phải map artifact → commit SHA → build/test run → target deployment.

## Quan sát trong production

Record deployment event gồm artifact version/digest, commit SHA, Jenkins build ID, target environment, deployment timestamp, previous version và validation outcome. Application Insights/logs nên include application version để correlate regressions với deployment. Alert theo post-deploy error rate, p95/p99 và health checks, nhưng rollback decision phải dựa trên service impact và compatibility chứ không chỉ một metric đơn lẻ.

## Câu hỏi phỏng vấn mở rộng

1. Nếu application dùng environment-specific frontend compile-time variables, bạn vẫn giữ build-once semantics bằng cách nào?
2. Artifact rollback an toàn nhưng database đã chạy destructive migration thì bạn xử lý release design thế nào?
3. Khi nào container image digest giúp đơn giản hóa provenance so với ZIP/IIS artifact, và khi nào chuyển sang containers là complexity không cần thiết?

# Tổng kết hôm nay

## Kiến thức trọng tâm

File upload là streaming và distributed consistency problem chứ không chỉ là `IFormFile` API usage. Storage identity phải do server kiểm soát; client metadata không nên được coi là authoritative. SQL và Blob Storage cần explicit failure/reconciliation semantics.

CI/CD cũng cần một identity bất biến: source branch không phải deployable artifact. Release đáng tin cậy phải build/test một lần, promote immutable artifact, giữ secrets ngoài artifact và rollback bằng known-good artifact thay vì rebuild quá khứ.

## Mẫu tư duy cần nhớ

- Không materialize dữ liệu lớn nếu downstream hỗ trợ streaming.
- Tách client display metadata khỏi server-controlled identity.
- Khi hai resources không cùng transaction, thiết kế failure state và reconciliation.
- Build once, test once, promote the same immutable artifact.
- Rollback phải dựa trên known-good artifact và compatibility, không dựa trên việc “build lại code cũ”.
