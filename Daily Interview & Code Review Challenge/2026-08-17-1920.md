# Code Review Challenge 1 — `Channel<T>` không giới hạn làm worker ăn hết memory khi downstream chậm

**Chủ đề:** Background jobs, async/await, concurrency, backpressure, resource lifetime, cancellation, error handling, observability  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** Khoảng 8–10 vấn đề

## Bối cảnh

Một ASP.NET Core API nhận event từ nhiều endpoint và đẩy event vào `Channel<T>` để xử lý bất đồng bộ. Worker đọc event rồi gọi một external analytics service.

Bình thường hệ thống nhận khoảng 100–200 event/giây. Trong campaign có thể burst lên 2.000–5.000 event/giây trong vài phút. External analytics service đôi lúc chậm hoặc trả `5xx` trong 5–10 phút.

Production ghi nhận:

- memory process tăng liên tục khi downstream chậm,
- GC hoạt động mạnh và API latency tăng theo,
- deploy/restart làm mất những event còn nằm trong memory,
- một event lỗi có lúc làm worker ngừng xử lý tiếp,
- shutdown kéo dài nhưng vẫn không biết còn bao nhiêu event chưa xử lý,
- team không có metric queue depth hoặc processing lag.

Business cho phép analytics eventual consistency trong vài phút, nhưng không được làm API chính mất ổn định. Với event quan trọng, mất dữ liệu im lặng là không chấp nhận được.

## Đoạn code cần review

```csharp
public sealed record AnalyticsEvent(
    Guid Id,
    string Type,
    string Payload,
    DateTime CreatedAt);

public sealed class AnalyticsQueue
{
    private readonly Channel<AnalyticsEvent> _channel =
        Channel.CreateUnbounded<AnalyticsEvent>();

    public void Enqueue(AnalyticsEvent item)
    {
        _channel.Writer.TryWrite(item);
    }

    public IAsyncEnumerable<AnalyticsEvent> ReadAllAsync(
        CancellationToken cancellationToken)
        => _channel.Reader.ReadAllAsync(cancellationToken);
}

public sealed class AnalyticsWorker : BackgroundService
{
    private readonly AnalyticsQueue _queue;
    private readonly HttpClient _httpClient;
    private readonly ILogger<AnalyticsWorker> _logger;

    public AnalyticsWorker(
        AnalyticsQueue queue,
        HttpClient httpClient,
        ILogger<AnalyticsWorker> logger)
    {
        _queue = queue;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        await foreach (var item in _queue.ReadAllAsync(stoppingToken))
        {
            var response = await _httpClient.PostAsJsonAsync(
                "/api/events",
                item,
                stoppingToken);

            response.EnsureSuccessStatusCode();

            _logger.LogInformation(
                "Processed analytics event {EventId}",
                item.Id);
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề correctness trong queue/worker lifecycle.
2. Xác định rủi ro concurrency, memory, backpressure và failure handling.
3. Giải thích production impact dưới burst traffic hoặc downstream outage.
4. Ưu tiên các vấn đề cần sửa trước.
5. Đề xuất implementation đáng tin cậy hơn.
6. Giải thích cách test burst load, outage, restart và graceful shutdown.
7. Đề xuất logs, traces hoặc metrics phù hợp.

## Câu hỏi gợi mở

1. `CreateUnbounded` sẽ làm gì khi producer nhanh hơn consumer trong 10 phút?
2. `TryWrite` thất bại thì caller có biết event đã bị mất không?
3. Điều gì xảy ra nếu `EnsureSuccessStatusCode()` ném exception trong vòng lặp?
4. Event đang nằm trong RAM sẽ ra sao khi process restart?
5. Queue có cơ chế backpressure hay admission control nào không?

## Kết quả code review tham khảo

### 1. Queue không giới hạn gây memory growth không có trần

**Problem:** `Channel.CreateUnbounded` cho phép producer tiếp tục enqueue khi consumer chậm.  
**Why it happens:** Không có capacity hay backpressure.  
**Production impact:** Downstream outage kéo dài khiến event tích tụ trong RAM, gây GC pressure, latency tăng và có thể OOM.  
**Severity:** Critical  
**Recommended fix:** Dùng bounded channel với capacity được xác định từ throughput/SLA; chọn `FullMode` phù hợp business hoặc dùng durable broker nếu event không được phép mất.

### 2. Queue chỉ ở memory nên event mất khi restart/crash

**Problem:** Event chưa consume không được lưu bền vững.  
**Why it happens:** `Channel<T>` chỉ là in-process coordination primitive.  
**Production impact:** Rolling deployment, crash hoặc VM restart làm mất event im lặng.  
**Severity:** High  
**Recommended fix:** Với event quan trọng, dùng durable queue/broker hoặc transactional outbox rồi worker đọc từ storage bền vững.

### 3. Một exception có thể kết thúc toàn bộ `BackgroundService`

**Problem:** `EnsureSuccessStatusCode()` ném exception ra ngoài vòng lặp.  
**Why it happens:** Không có per-item failure boundary.  
**Production impact:** Một dependency error có thể làm worker dừng và queue tiếp tục phình.  
**Severity:** High  
**Recommended fix:** Bắt lỗi theo item, phân loại transient/permanent, retry có giới hạn và đưa poison event sang dead-letter/manual review khi cần.

### 4. Không có retry/backoff rõ ràng

**Problem:** Mỗi event chỉ gọi một lần.  
**Why it happens:** Failure strategy chưa được thiết kế.  
**Production impact:** Transient lỗi làm mất xử lý; retry ngây thơ ở caller sau này lại dễ tạo retry storm.  
**Severity:** High  
**Recommended fix:** Retry giới hạn với exponential backoff + jitter cho lỗi transient, tôn trọng timeout/cancellation và downstream guidance nếu có.

### 5. `TryWrite` làm mất semantics enqueue

**Problem:** Method trả `void`, kết quả `TryWrite` bị bỏ qua.  
**Why it happens:** API queue không phản ánh admission outcome.  
**Production impact:** Khi chuyển sang bounded channel hoặc writer đã complete, event có thể bị drop mà caller không biết.  
**Severity:** High  
**Recommended fix:** Dùng `WriteAsync` với cancellation để tạo backpressure hoặc trả explicit result nếu business muốn reject/drop.

### 6. Không có timeout riêng cho downstream call

**Problem:** Worker chỉ phụ thuộc cancellation token lifecycle.  
**Why it happens:** Không có per-attempt deadline.  
**Production impact:** Một call chậm giữ consumer lâu, làm queue lag tăng nhanh.  
**Severity:** Medium  
**Recommended fix:** Có timeout/deadline riêng cho dependency call, phân biệt timeout với shutdown cancellation.

### 7. `HttpResponseMessage` không được dispose rõ ràng

**Problem:** `response` sống đến khi GC dọn.  
**Why it happens:** Code chỉ gọi `EnsureSuccessStatusCode`.  
**Production impact:** Giữ resource lâu hơn cần thiết dưới throughput cao.  
**Severity:** Medium  
**Recommended fix:** `using var response = await ...`.

### 8. Không có queue depth, lag, throughput hoặc failure metrics

**Problem:** Chỉ log từng event thành công.  
**Why it happens:** Observability không được xem là phần của queue design.  
**Production impact:** Team không biết đang tích backlog hay worker đã dừng.  
**Severity:** Medium  
**Recommended fix:** Theo dõi depth, enqueue rate, dequeue rate, processing latency, oldest-event age, success/failure/retry/dead-letter count.

### 9. Logging per-event ở `Information` có thể quá lớn

**Problem:** Mỗi event thành công tạo một log entry.  
**Why it happens:** Operational summary và diagnostic detail bị trộn.  
**Production impact:** Log volume/chi phí tăng mạnh ở hàng nghìn event/giây.  
**Severity:** Low  
**Recommended fix:** Dùng metric cho throughput; log sampled/batch summary, và log chi tiết khi lỗi.

## Phiên bản code đề xuất

Ví dụ dưới đây phù hợp khi event có thể chờ trong memory ngắn hạn và caller chấp nhận backpressure. Nếu không được phép mất event qua restart, nên thay producer path bằng durable queue/outbox.

```csharp
public sealed class AnalyticsQueue
{
    private readonly Channel<AnalyticsEvent> _channel =
        Channel.CreateBounded<AnalyticsEvent>(
            new BoundedChannelOptions(5_000)
            {
                SingleReader = true,
                SingleWriter = false,
                FullMode = BoundedChannelFullMode.Wait
            });

    public ValueTask EnqueueAsync(
        AnalyticsEvent item,
        CancellationToken cancellationToken)
        => _channel.Writer.WriteAsync(item, cancellationToken);

    public IAsyncEnumerable<AnalyticsEvent> ReadAllAsync(
        CancellationToken cancellationToken)
        => _channel.Reader.ReadAllAsync(cancellationToken);
}

public sealed class AnalyticsWorker : BackgroundService
{
    private readonly AnalyticsQueue _queue;
    private readonly HttpClient _httpClient;
    private readonly ILogger<AnalyticsWorker> _logger;

    public AnalyticsWorker(
        AnalyticsQueue queue,
        HttpClient httpClient,
        ILogger<AnalyticsWorker> logger)
    {
        _queue = queue;
        _httpClient = httpClient;
        _logger = logger;
    }

    protected override async Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        await foreach (var item in _queue.ReadAllAsync(stoppingToken))
        {
            try
            {
                using var timeoutCts = CancellationTokenSource
                    .CreateLinkedTokenSource(stoppingToken);
                timeoutCts.CancelAfter(TimeSpan.FromSeconds(10));

                using var response = await _httpClient.PostAsJsonAsync(
                    "/api/events",
                    item,
                    timeoutCts.Token);

                response.EnsureSuccessStatusCode();
            }
            catch (OperationCanceledException)
                when (!stoppingToken.IsCancellationRequested)
            {
                _logger.LogWarning(
                    "Analytics event {EventId} timed out",
                    item.Id);
            }
            catch (Exception ex)
            {
                _logger.LogError(
                    ex,
                    "Analytics event {EventId} failed",
                    item.Id);
            }
        }
    }
}
```

Trong production, phần retry/dead-letter nên được tách rõ khỏi ví dụ ngắn này. Với event quan trọng, durability nên nằm ở broker/outbox thay vì chỉ ở `Channel<T>`.

## Trade-offs

- Bounded channel bảo vệ memory nhưng có thể làm request producer chậm lại.
- `Wait` tạo backpressure; `DropOldest`/`DropWrite` giảm latency nhưng chỉ phù hợp nếu business chấp nhận mất event.
- Durable broker tăng độ tin cậy nhưng thêm hạ tầng và operational cost.
- Một consumer đơn giản dễ reasoning; nhiều consumer tăng throughput nhưng cần xem ordering, downstream quota và idempotency.

## Cách kiểm thử

1. **Load test:** producer 5.000 event/giây trong khi consumer chỉ xử lý 200 event/giây; xác nhận memory có trần và producer chịu backpressure.
2. **Failure-path test:** downstream trả `500`/timeout liên tục; xác nhận worker không chết toàn bộ.
3. **Restart test:** xác nhận rõ event nào được phép mất với in-memory design; nếu dùng broker/outbox thì xác nhận recovery sau restart.
4. **Cancellation test:** shutdown khi còn backlog; xác nhận behavior graceful shutdown đúng policy.
5. **Observability test:** tạo backlog và xác nhận alert queue depth/lag hoạt động.

## Quan sát trong production

Nên theo dõi:

- queue depth/capacity utilization,
- enqueue/dequeue rate,
- processing duration,
- oldest event age,
- retry/dead-letter count,
- downstream latency/status/timeout,
- process memory, GC heap size, Gen 2 collections,
- worker heartbeat và lần xử lý thành công gần nhất.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn chọn RabbitMQ/Azure Service Bus thay cho `Channel<T>`?
2. Nếu event bắt buộc xử lý đúng một lần theo business, bạn bảo vệ invariant ở đâu?
3. Bạn sẽ chọn `FullMode.Wait` hay drop policy nào cho telemetry không quan trọng?

# Code Review Challenge 2 — `Update(entity)` từ DTO làm ghi đè dữ liệu và cho phép sửa field không nên sửa

**Chủ đề:** EF Core tracking, authorization, mass assignment, optimistic concurrency, correctness, validation  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 25–35 phút

## Bối cảnh

Một API multi-tenant cho phép manager chỉnh sửa hồ sơ nhân viên. Frontend chỉ hiển thị `DisplayName`, `Department` và `Title`, nhưng request DTO hiện tại tái sử dụng model khá rộng vì team muốn giảm mapping code.

API chạy trên nhiều instance. Production ghi nhận:

- đôi lúc field `IsAdmin` hoặc `TenantId` thay đổi ngoài ý muốn sau request update,
- hai manager sửa cùng một employee gần nhau và thay đổi của người sau ghi đè thay đổi người trước,
- một số field không được gửi từ client bị reset về default,
- audit log không thể hiện chính xác field nào đã đổi.

Business yêu cầu manager chỉ được sửa một tập field cho phép trong tenant của mình. Các thay đổi đồng thời không được silently overwrite nếu người dùng đang sửa từ phiên bản cũ.

## Đoạn code cần review

```csharp
public sealed class UpdateEmployeeRequest
{
    public Guid Id { get; set; }
    public Guid TenantId { get; set; }
    public string? DisplayName { get; set; }
    public string? Department { get; set; }
    public string? Title { get; set; }
    public bool IsAdmin { get; set; }
    public bool IsActive { get; set; }
    public DateTime CreatedAt { get; set; }
}

public sealed class EmployeeService
{
    private readonly AppDbContext _db;

    public EmployeeService(AppDbContext db)
    {
        _db = db;
    }

    public async Task UpdateAsync(
        UpdateEmployeeRequest request,
        Guid currentTenantId,
        CancellationToken cancellationToken)
    {
        if (request.TenantId != currentTenantId)
            throw new UnauthorizedAccessException();

        var employee = new Employee
        {
            Id = request.Id,
            TenantId = request.TenantId,
            DisplayName = request.DisplayName,
            Department = request.Department,
            Title = request.Title,
            IsAdmin = request.IsAdmin,
            IsActive = request.IsActive,
            CreatedAt = request.CreatedAt,
            UpdatedAt = DateTime.UtcNow
        };

        _db.Employees.Update(employee);
        await _db.SaveChangesAsync(cancellationToken);
    }
}
```

## Kết quả code review tham khảo

### 1. Mass assignment cho các field nhạy cảm

**Problem:** DTO chứa và code ghi `IsAdmin`, `IsActive`, `TenantId`, `CreatedAt`.  
**Why it happens:** Request contract phản ánh persistence model thay vì use case.  
**Production impact:** Caller có thể sửa field mà manager không được phép thay đổi.  
**Severity:** Critical  
**Recommended fix:** DTO chỉ chứa field cho phép chỉnh sửa; field privileged phải qua use case/policy riêng.

### 2. Authorization phụ thuộc `TenantId` do client gửi

**Problem:** Code chỉ so sánh `request.TenantId` với `currentTenantId`.  
**Why it happens:** Không load resource thực tế trước khi authorize.  
**Production impact:** Caller có thể gửi `currentTenantId` hợp lệ nhưng `Id` thuộc tenant khác; entity stub sau đó còn có thể ghi lại tenant theo request.  
**Severity:** Critical  
**Recommended fix:** Query employee bằng `Id` và tenant từ identity/context đáng tin; nếu không tìm thấy thì trả not found/forbidden theo policy.

### 3. `Update(entity)` có thể đánh dấu toàn bộ graph/property là modified

**Problem:** Entity được dựng mới rồi gọi `Update`.  
**Why it happens:** Không có tracked original state để EF biết field nào thật sự thay đổi.  
**Production impact:** Nhiều cột bị update dù client chỉ muốn đổi một field.  
**Severity:** High  
**Recommended fix:** Load entity có tracking rồi gán explicit allowed properties; hoặc attach và mark chính xác từng property nếu có lý do performance đặc biệt.

### 4. Field không gửi/không hiển thị có thể bị reset về default

**Problem:** Request object quyết định toàn bộ giá trị entity.  
**Why it happens:** Full replacement semantics được dùng cho use case partial edit.  
**Production impact:** Mất dữ liệu ngoài ý muốn, đặc biệt với boolean/default values và metadata.  
**Severity:** High  
**Recommended fix:** Dùng use-case-specific request và explicit mapping; phân biệt PUT/PATCH semantics rõ ràng.

### 5. Không có optimistic concurrency

**Problem:** Không có version/row version trong update condition.  
**Why it happens:** Mỗi request blind-write trạng thái cuối.  
**Production impact:** Hai manager sửa gần nhau có thể silently overwrite dữ liệu.  
**Severity:** High  
**Recommended fix:** Dùng concurrency token phù hợp database/model; khi conflict, trả lỗi xác định để client reload/merge.

### 6. `CreatedAt` có thể bị client sửa

**Problem:** Immutable server metadata lấy từ request.  
**Why it happens:** DTO tái sử dụng persistence fields.  
**Production impact:** Audit/history mất độ tin cậy.  
**Severity:** High  
**Recommended fix:** Không expose `CreatedAt` trong update contract; giữ giá trị từ database.

### 7. Không validate business constraints cho text fields

**Problem:** `DisplayName`, `Department`, `Title` được gán trực tiếp.  
**Why it happens:** Mapping và validation chưa tách rõ.  
**Production impact:** Null/whitespace/oversized data có thể gây dữ liệu xấu hoặc DB exception.  
**Severity:** Medium  
**Recommended fix:** Validate length, required/optional semantics và normalization theo domain rule.

### 8. Không có audit before/after state

**Problem:** Update không ghi field nào đổi, ai đổi, version nào.  
**Why it happens:** Audit được coi là phụ trợ thay vì business requirement.  
**Production impact:** Khó điều tra security incident và lost update.  
**Severity:** Medium  
**Recommended fix:** Ghi structured audit với actor, employee id, tenant, changed fields, old/new values phù hợp policy và correlation id.

## Phiên bản code đề xuất

```csharp
public sealed record UpdateEmployeeRequest(
    string? DisplayName,
    string? Department,
    string? Title,
    byte[] Version);

public sealed class EmployeeService
{
    private readonly AppDbContext _db;
    private readonly TimeProvider _timeProvider;

    public EmployeeService(
        AppDbContext db,
        TimeProvider timeProvider)
    {
        _db = db;
        _timeProvider = timeProvider;
    }

    public async Task UpdateAsync(
        Guid employeeId,
        Guid currentTenantId,
        UpdateEmployeeRequest request,
        CancellationToken cancellationToken)
    {
        var employee = await _db.Employees
            .SingleOrDefaultAsync(
                x => x.Id == employeeId &&
                     x.TenantId == currentTenantId,
                cancellationToken)
            ?? throw new KeyNotFoundException("Employee not found.");

        _db.Entry(employee)
            .Property(x => x.Version)
            .OriginalValue = request.Version;

        employee.DisplayName = request.DisplayName?.Trim();
        employee.Department = request.Department?.Trim();
        employee.Title = request.Title?.Trim();
        employee.UpdatedAt = _timeProvider.GetUtcNow().UtcDateTime;

        try
        {
            await _db.SaveChangesAsync(cancellationToken);
        }
        catch (DbUpdateConcurrencyException)
        {
            throw new InvalidOperationException(
                "Employee was changed by another user. Reload and retry.");
        }
    }
}
```

Ví dụ giả định `Employee.Version` đã được cấu hình làm concurrency token phù hợp với database đang dùng. Cách tạo/version token cụ thể cần bám theo database/provider và model thực tế.

## Trade-offs

- Load entity trước update thêm một database round-trip nhưng tăng correctness, authorization clarity và auditability.
- Blind attach có thể hữu ích ở hot path đặc biệt, nhưng cần explicit allowed properties và concurrency condition; complexity cao hơn.
- Optimistic concurrency phù hợp khi conflict hiếm; nếu conflict rất thường xuyên và invariant mạnh, có thể cần transaction/locking strategy khác.
- Trả `409 Conflict` hoặc domain-specific response giúp client xử lý tốt hơn nhưng cần UX cho reload/merge.

## Cách kiểm thử

1. **Security test:** gửi `employeeId` thuộc tenant khác nhưng `currentTenantId` hợp lệ; xác nhận không update được.
2. **Mass-assignment test:** cố gửi field privileged qua payload; contract không bind hoặc không áp dụng field đó.
3. **Concurrency test:** hai request cùng version; request đầu thành công, request sau nhận conflict thay vì silent overwrite.
4. **Data-preservation test:** update `Title` nhưng `IsAdmin`, `IsActive`, `CreatedAt`, `TenantId` giữ nguyên.
5. **Validation test:** null/whitespace/oversized values được xử lý theo business rule.

## Quan sát trong production

Nên theo dõi:

- concurrency conflict count,
- forbidden/cross-tenant access attempts,
- update latency và DB command duration,
- audit event count và changed-field distribution,
- validation failure rate,
- correlation id giữa request, audit và DB trace.

## Câu hỏi phỏng vấn mở rộng

1. Khi nào bạn dùng `ExecuteUpdateAsync` thay vì load entity rồi update?
2. Nếu PostgreSQL và SQL Server cùng được hỗ trợ, bạn thiết kế concurrency token abstraction thế nào?
3. Với PATCH thật sự, bạn làm sao phân biệt “không gửi field” với “gửi field = null”?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- In-memory queue cần có capacity và backpressure; nếu event phải survive restart thì cần durability ngoài process.
- Failure boundary của background worker nên ở cấp item/batch thay vì để một exception giết toàn worker.
- Retry phải đi cùng timeout, backoff, idempotency và observability.
- Update contract không nên mirror database entity; chỉ expose field đúng use case.
- Authorization phải dựa trên resource thực tế và identity đáng tin, không dựa trên tenant/resource id do client tự khai báo.
- Optimistic concurrency giúp biến lost update từ lỗi im lặng thành conflict có thể xử lý.

## Mẫu tư duy cần nhớ

- Thiết kế backpressure trước khi production buộc bạn phải học nó bằng OOM.
- Durability là business property, không phải đặc tính mặc định của background task.
- Validate quyền trên resource thực tế, không trên dữ liệu client tự khai.
- Chỉ update những field use case cho phép.
- Biến concurrent overwrite thành explicit conflict thay vì silent data loss.
