# Code Review Challenge 1 — EF Core multi-tenant query filter bị bypass và pooled DbContext làm tenant state trở nên nguy hiểm

**Chủ đề:** C#, ASP.NET Core, EF Core, multi-tenancy, global query filters, DbContext pooling, authorization, background processing, security  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một SaaS ASP.NET Core trên .NET 8 dùng shared SQL Server database cho nhiều khách hàng doanh nghiệp. Mọi bảng nghiệp vụ quan trọng đều có `TenantId`.

Team muốn giảm nguy cơ developer quên thêm điều kiện tenant nên dùng EF Core global query filters. Hệ thống đồng thời có:

- HTTP request của user bình thường;
- support flow cho phép nhân viên hỗ trợ truy cập **một tenant cụ thể** sau khi có authorization grant;
- background export job, trong đó `TenantId` đã được lưu cùng job;
- `AddDbContextPool` để giảm allocation;
- một repository method dùng `IgnoreQueryFilters()` để làm báo cáo support.

Production vừa có incident rất khó tái hiện: một export chứa vài record thuộc tenant khác. Incident chỉ xuất hiện dưới load. Logs chỉ có `UserId`, không ghi effective tenant, job ID hay support grant.

Một developer nghi SQL Server “trả nhầm cache”. Một developer khác muốn bỏ `AddDbContextPool` và coi vấn đề đã giải quyết. Team hiện xem global query filter như security boundary chính.

## Đoạn code cần review

```csharp
public interface ITenantContext
{
    Guid TenantId { get; }
}

public sealed class HttpTenantContext : ITenantContext
{
    private readonly IHttpContextAccessor _http;

    public HttpTenantContext(IHttpContextAccessor http)
        => _http = http;

    public Guid TenantId =>
        Guid.Parse(_http.HttpContext!
            .User.FindFirst("tenant_id")!.Value);
}

public sealed class AppDbContext : DbContext
{
    private readonly ITenantContext _tenant;

    public AppDbContext(
        DbContextOptions<AppDbContext> options,
        ITenantContext tenant) : base(options)
        => _tenant = tenant;

    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Order>()
            .HasQueryFilter(x => x.TenantId == _tenant.TenantId);
    }
}

services.AddHttpContextAccessor();
services.AddScoped<ITenantContext, HttpTenantContext>();
services.AddDbContextPool<AppDbContext>(o =>
    o.UseSqlServer(connectionString));

public sealed class OrderRepository
{
    private readonly AppDbContext _db;

    public OrderRepository(AppDbContext db) => _db = db;

    public Task<Order?> GetAsync(
        Guid id,
        CancellationToken ct) =>
        _db.Orders.SingleOrDefaultAsync(x => x.Id == id, ct);

    public Task<List<Order>> GetForSupportAsync(
        DateTime fromUtc,
        CancellationToken ct) =>
        _db.Orders
            .IgnoreQueryFilters()
            .Where(x => x.CreatedAtUtc >= fromUtc)
            .ToListAsync(ct);
}

public sealed class ExportWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly IJobQueue _queue;

    public ExportWorker(
        IServiceScopeFactory scopes,
        IJobQueue queue)
        => (_scopes, _queue) = (scopes, queue);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var job in _queue.ReadAllAsync(ct))
        {
            await using var scope = _scopes.CreateAsyncScope();
            var db = scope.ServiceProvider
                .GetRequiredService<AppDbContext>();

            var rows = await db.Orders
                .Where(x => x.Status == OrderStatus.Completed)
                .ToListAsync(ct);

            await job.WriteExportAsync(rows, ct);
        }
    }
}
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề security, correctness, DI lifetime và tenant isolation.
2. Giải thích vì sao bug có thể chỉ xuất hiện ở background flow hoặc dưới load.
3. Phân tích rủi ro của pooled `DbContext` khi context phụ thuộc state theo request/tenant.
4. Giải thích vì sao global query filter là guardrail hữu ích nhưng không phải authorization boundary hoàn chỉnh.
5. Review `IgnoreQueryFilters()` và đề xuất cách giới hạn privileged data access.
6. Đề xuất tenant propagation rõ ràng cho HTTP request, support flow và background job.
7. Đề xuất database constraints, tests và telemetry để phát hiện cross-tenant access.

## Câu hỏi gợi mở

1. `HttpContext` tồn tại ở đâu khi `ExportWorker` resolve `AppDbContext`?
2. Pooled `DbContext` có lifetime/reuse semantics khác context scoped thông thường như thế nào?
3. Sau khi gọi `IgnoreQueryFilters()`, authorization nào còn giới hạn query về đúng tenant?
4. Claim `tenant_id` có tự chứng minh user đang được phép truy cập tenant đó không?
5. Schema có constraint nào bảo đảm relationship/unique key không thể liên kết chéo tenant?

## Gợi ý

### Gợi ý 1

Tenant identity là một phần của security context. Nó phải được resolve, validate và propagate có chủ đích; không nên phụ thuộc ngầm vào “chắc lúc nào cũng có HttpContext”.

### Gợi ý 2

Hãy tách ba lớp: authorization của actor, tenant scope của operation và filtering ở data-access layer. Một lớp không nên âm thầm thay thế hai lớp còn lại.

## Kết quả code review tham khảo

### Critical — Background worker lấy tenant từ HTTP-specific context

**Vấn đề:** `HttpTenantContext` giả định luôn có `HttpContext` và claim `tenant_id`, trong khi background worker không chạy trong HTTP request.

**Tại sao:** Tenant resolution bị gắn vào transport-specific state thay vì explicit operation context.

**Ảnh hưởng:** Worker có thể fail, rơi vào fallback nguy hiểm nếu code thực tế có fallback, hoặc chạy với tenant state không đúng. Với export, blast radius lớn vì một query trả nhiều record.

**Cách sửa:** Job phải mang `TenantId` đã được xác thực tại lúc enqueue. Worker tạo scope mới cho mỗi job, thiết lập tenant execution context từ `job.TenantId`, rồi mới resolve tenant-aware service/DbContext.

### Critical — `IgnoreQueryFilters()` mở đường đọc cross-tenant không giới hạn

**Vấn đề:** Method support tắt filter và không thêm predicate `TenantId`.

**Tại sao:** Privileged capability được đặt trong repository phổ thông và không yêu cầu explicit target tenant.

**Ảnh hưởng:** Chỉ cần caller thiếu authorization check hoặc gọi nhầm method là có thể trả dữ liệu của nhiều khách hàng.

**Cách sửa:** Tách privileged repository/service riêng; bắt buộc explicit `targetTenantId`, support grant, reason và audit. Nếu use case chỉ cho phép một tenant thì query vẫn phải có `TenantId == targetTenantId` sau khi tắt filter mặc định.

### Critical — Global query filter đang bị coi như security boundary duy nhất

**Vấn đề:** Filter có thể bị bỏ qua bởi `IgnoreQueryFilters()`, raw SQL, query path khác hoặc entity mới chưa cấu hình filter.

**Tại sao:** Một convenience mechanism của ORM bị nâng thành authorization mechanism.

**Ảnh hưởng:** Một refactor nhỏ có thể trở thành cross-tenant data disclosure.

**Cách sửa:** Defense-in-depth: authorization ở application boundary; tenant-aware repository contract; schema constraints phù hợp; convention/integration tests cho mọi tenant-owned entity. Với threat model nghiêm ngặt hơn có thể đánh giá database Row-Level Security hoặc stronger physical isolation, nhưng đó là decision riêng chứ không thay application authorization.

### High — Pooled `DbContext` và request-specific tenant dependency là coupling rủi ro

**Vấn đề:** Context giữ dependency liên quan tenant trong khi context pooling tái sử dụng context instances. EF Core reset internal EF state, nhưng application-specific state/lifetime assumptions phải được quản lý cẩn thận.

**Tại sao:** Pooling được thêm như optimization mà chưa thiết kế tenant state cho reusable context lifecycle.

**Ảnh hưởng:** Tenant-related bug có thể phụ thuộc reuse/timing/load và khó tái hiện bằng request đơn lẻ.

**Cách sửa:** Lựa chọn đơn giản nhất là bỏ pooling cho tenant-sensitive context rồi đo lại. Nếu pooling thật sự cần, dùng documented factory pattern: pooled factory tạo context và một scoped wrapper/factory thiết lập tenant state cho mỗi lần thuê context, đồng thời bảo đảm state không rò sang lần dùng sau.

### High — Authentication claim bị dùng như authorization decision

**Vấn đề:** Code đọc `tenant_id` trực tiếp rồi coi đó là tenant hợp lệ cho operation.

**Tại sao:** Authentication identity, membership và authorization bị trộn lẫn.

**Ảnh hưởng:** Claim mapping lỗi, stale membership hoặc support flow sai có thể scope request tới tenant không hợp lệ.

**Cách sửa:** Resolve effective tenant từ authenticated principal + server-side membership/grant. Support access cần target tenant + grant ID + expiry/reason, rồi policy authorization quyết định operation được phép.

### High — Repository contract che giấu tenant invariant

**Vấn đề:** `GetAsync(Guid id)` không thể hiện tenant trong signature; safety phụ thuộc hoàn toàn vào hidden filter.

**Tại sao:** Tenant scoping bị xem như infrastructure magic.

**Ảnh hưởng:** Refactor sang raw SQL/compiled query/context khác dễ làm mất tenant predicate mà caller không nhận ra.

**Cách sửa:** Với security-sensitive aggregate, ưu tiên contract tenant-aware hoặc repository chỉ có thể được tạo trong một verified tenant scope không-null. Invariant quan trọng nên nhìn thấy được trong design.

### High — Schema có thể không enforce tenant ownership

**Vấn đề:** Code không cho thấy unique keys/foreign keys có bao gồm tenant boundary.

**Tại sao:** Multi-tenancy thường được thêm ở application layer mà không review relational constraints.

**Ảnh hưởng:** Child row có thể tham chiếu parent tenant khác, hoặc business key uniqueness bị enforce sai phạm vi.

**Cách sửa:** Với tenant-owned relationship, review composite candidate keys/foreign keys hoặc constraint tương đương để chứng minh parent/child cùng tenant. Business unique keys thường cần dạng `(TenantId, BusinessKey)`.

### Medium — Missing/invalid tenant claim trở thành generic exception

**Vấn đề:** `Guid.Parse(...!.Value)` dựa vào null-forgiving và format hợp lệ.

**Tại sao:** Security context được coi là luôn đúng.

**Ảnh hưởng:** Auth/config problem trở thành 500, gây noise và làm khó phân biệt auth incident với application defect.

**Cách sửa:** Tenant resolver trả typed result, fail closed sớm bằng 401/403 phù hợp và log structured reason không lộ dữ liệu nhạy cảm.

### Medium — Telemetry không đủ để chứng minh tenant isolation

**Vấn đề:** Incident logs không có effective tenant, job ID, source của tenant context hoặc support grant.

**Tại sao:** Tenant isolation chưa được coi là observable invariant.

**Ảnh hưởng:** Khó xác định blast radius và reproduce timeline.

**Cách sửa:** Log/trace structured tenant identifier theo privacy policy, operation/job ID, actor type, support grant ID và privileged-access audit event.

## Phiên bản đề xuất

Một phương án dễ audit là dùng scoped tenant execution context độc lập với `HttpContext`, không pool `DbContext` trước khi chứng minh pooling thực sự cần:

```csharp
public sealed class TenantExecutionContext
{
    public Guid? TenantId { get; private set; }

    public void Initialize(Guid tenantId)
    {
        if (TenantId is not null)
            throw new InvalidOperationException(
                "Tenant context already initialized.");

        TenantId = tenantId;
    }

    public Guid RequireTenantId() =>
        TenantId ?? throw new InvalidOperationException(
            "Tenant context is not initialized.");
}

services.AddScoped<TenantExecutionContext>();
services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(connectionString));

public sealed class AppDbContext : DbContext
{
    private readonly TenantExecutionContext _tenant;

    public AppDbContext(
        DbContextOptions<AppDbContext> options,
        TenantExecutionContext tenant) : base(options)
        => _tenant = tenant;

    public DbSet<Order> Orders => Set<Order>();

    protected override void OnModelCreating(ModelBuilder builder)
    {
        builder.Entity<Order>()
            .HasQueryFilter(
                x => x.TenantId == _tenant.RequireTenantId());
    }
}

public sealed class ExportWorker : BackgroundService
{
    private readonly IServiceScopeFactory _scopes;
    private readonly IJobQueue _queue;

    public ExportWorker(
        IServiceScopeFactory scopes,
        IJobQueue queue)
        => (_scopes, _queue) = (scopes, queue);

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        await foreach (var job in _queue.ReadAllAsync(ct))
        {
            await using var scope = _scopes.CreateAsyncScope();

            var tenant = scope.ServiceProvider
                .GetRequiredService<TenantExecutionContext>();
            tenant.Initialize(job.TenantId);

            var exporter = scope.ServiceProvider
                .GetRequiredService<IOrderExporter>();

            await exporter.ExportAsync(job, ct);
        }
    }
}
```

HTTP pipeline cũng cần initialize cùng scoped context **sau** khi authentication/authorization đã xác định effective tenant. Privileged support flow không được reuse normal repository method một cách mơ hồ; nó nên có API riêng yêu cầu target tenant và grant.

## Giải thích thiết kế sau khi sửa

Thiết kế mới tách tenant identity khỏi transport. HTTP request, background job và support operation đều phải đưa tenant vào một execution context rõ ràng.

Global query filter vẫn hữu ích vì giảm lỗi bỏ quên predicate trong normal query path, nhưng security không phụ thuộc duy nhất vào filter. Authorization quyết định actor được làm gì; execution context quyết định operation đang ở tenant nào; database/query constraints tạo lớp phòng vệ thứ ba.

Bỏ pooling ban đầu làm lifecycle dễ audit hơn. Sau khi isolation tests ổn định, team có thể benchmark lại. Chỉ nếu pooling tạo lợi ích đủ lớn mới đưa trở lại bằng factory pattern được thiết kế cho tenant state.

Privileged support access được coi là một capability riêng: explicit target tenant, explicit grant, explicit audit. Điều này làm blast radius của `IgnoreQueryFilters()` nhỏ hơn và dễ review hơn.

## Trade-offs

- **Không pooling:** đơn giản và dễ chứng minh isolation hơn, nhưng có thể tăng allocation/context construction cost; cần benchmark trước khi kết luận đáng kể.
- **Global query filter:** giảm repetition và lỗi vô tình, nhưng tạo hidden behavior; integration tests và repository conventions vẫn cần.
- **Explicit tenant parameters/context:** verbose hơn nhưng security invariant dễ nhìn thấy trong API và logs.
- **Database RLS hoặc database-per-tenant:** có thể tăng isolation nhưng thêm migration, operations, connection-management và observability complexity; chỉ chọn theo threat model/compliance/scale.
- **Privileged repository riêng:** tăng số abstraction nhưng đổi lại capability boundary rõ và audit tốt hơn.

## Cách kiểm thử

1. Integration test hai tenant có dữ liệu tương tự nhau; mọi read/update/delete normal path phải chỉ tác động tenant hiện tại.
2. Chạy hàng nghìn background jobs A/B xen kẽ với scope mới; mỗi export phải chứa đúng một tenant.
3. Support tests: không grant → deny; grant tenant A → không đọc tenant B; expired grant → deny.
4. Nếu bật context pooling trở lại, dùng pool nhỏ và load test để ép reuse liên tục giữa tenants.
5. Database tests cố tạo cross-tenant FK/reference hoặc duplicate business key sai scope và xác minh constraint reject.

## Quan sát trong production

- Structured trace attributes: operation/job ID, effective tenant, actor type, support grant ID khi có.
- Metric `tenant_context_missing` trên business data path; mục tiêu là 0.
- Audit log riêng cho privileged cross-tenant capability.
- Invariant telemetry cho export/single-tenant response: phát hiện nếu result chứa nhiều `TenantId` khi contract cấm.
- Dashboard/alert cho authorization denial, tenant-resolution failure và privileged access volume bất thường.

## Câu hỏi phỏng vấn mở rộng

1. Nếu SuperAdmin cần query nhiều tenant trong một báo cáo thật sự hợp lệ, bạn tách capability đó khỏi normal tenant-scoped context như thế nào?
2. Bạn chọn shared-schema isolation, Row-Level Security hay database-per-tenant dựa trên tiêu chí nào?
3. Nếu bỏ `DbContext` pooling làm allocation tăng nhưng isolation dễ chứng minh hơn, bạn cần metrics nào trước khi quyết định bật lại?

# Code Review Challenge 2 — GitHub Actions chạy code từ fork PR với secrets và write token: CI trở thành đường supply-chain compromise

**Chủ đề:** GitHub Actions, CI/CD, software supply chain, pull requests, secrets, token permissions, artifact provenance, least privilege  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 30–40 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một public repository chứa ASP.NET Core + Node.js monorepo. Team muốn PR từ fork chạy full integration tests, comment coverage và tạo package artifact.

Do `pull_request` từ fork không có repository secrets, team đổi sang `pull_request_target`, rồi checkout chính commit của contributor. Workflow có cloud credential dài hạn và `GITHUB_TOKEN` quyền ghi để bot comment.

Một deployment workflow khác tải artifact tên `app-package` rồi deploy.

Maintainer tin rằng workflow an toàn vì YAML được lấy từ default branch chứ không phải từ fork. Họ cũng dùng label `safe-to-test` như bước approval.

GitHub security guidance hiện cảnh báo rõ rằng `pull_request_target` có elevated trust và trở nên nguy hiểm khi workflow checkout rồi chạy untrusted pull-request code. GitHub cũng khuyến nghị pin actions tới full-length commit SHA cho immutable references và áp dụng least privilege cho token permissions.

## Đoạn code cần review

```yaml
name: pr-ci

on:
  pull_request_target:
    types: [opened, synchronize, reopened, labeled]

permissions:
  contents: write
  pull-requests: write
  actions: write

jobs:
  test:
    if: |
      github.event.action != 'labeled' ||
      github.event.label.name == 'safe-to-test'
    runs-on: ubuntu-latest

    steps:
      - name: Checkout contributor code
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }}

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Login cloud
        run: |
          echo "${{ secrets.CLOUD_SERVICE_ACCOUNT_JSON }}" > /tmp/cloud.json
          ./scripts/cloud-login.sh /tmp/cloud.json

      - name: Start integration environment
        run: docker compose -f docker-compose.ci.yml up -d --build

      - name: Test
        run: ./scripts/test-all.sh

      - name: Upload package
        uses: actions/upload-artifact@v4
        with:
          name: app-package
          path: ./artifacts/**

      - name: Comment coverage
        uses: acme-corp/pr-comment@main
        with:
          github-token: ${{ secrets.GITHUB_TOKEN }}
          body-file: coverage-summary.md
```

Deployment workflow rút gọn:

```yaml
- uses: actions/download-artifact@v4
  with:
    name: app-package

- run: ./deploy.sh ./app-package
```

## Nhiệm vụ của ứng viên

1. Xác định các vấn đề supply-chain/security trong trigger, checkout, permissions, secrets và artifact flow.
2. Giải thích chính xác vì sao `pull_request_target` + checkout PR head + chạy build/test là dangerous trust-boundary violation.
3. Liệt kê các đường exfiltrate secret/token dù contributor không sửa workflow YAML.
4. Đánh giá `npm ci`, Docker build/Compose, test scripts và generated files như executable/untrusted inputs.
5. Đề xuất architecture tách untrusted PR validation khỏi privileged operations.
6. Đề xuất least-privilege permissions, OIDC/short-lived identity và action pinning.
7. Đề xuất artifact provenance/authorization để deployment không nhận package từ untrusted PR.

## Câu hỏi gợi mở

1. Workflow YAML đến từ base branch, nhưng code nào thực sự chạy sau khi checkout `head.sha`?
2. Contributor có cần sửa workflow file để đánh cắp secret không, hay chỉ cần sửa `package.json`, Dockerfile hoặc `test-all.sh`?
3. Nếu `GITHUB_TOKEN` bị lấy với `contents: write`, blast radius thay đổi thế nào?
4. Label `safe-to-test` có còn bảo vệ immutable commit nếu contributor push commit mới sau khi được label?
5. Artifact name có phải bằng chứng rằng package đến từ trusted commit/trusted workflow không?

## Gợi ý

### Gợi ý 1

Theo dõi **trust của mọi executable input**, không chỉ trust của workflow YAML.

### Gợi ý 2

Privileged workflow có thể xử lý metadata hoặc thao tác nhỏ đã kiểm soát; nó không nên checkout rồi thực thi arbitrary code từ trust domain thấp hơn.

## Kết quả code review tham khảo

### Critical — `pull_request_target` + checkout head SHA + privileged credentials tạo “pwn request” pattern

**Vấn đề:** Workflow chạy trong elevated base-repository context, nhận write token/secrets, rồi checkout PR head và thực thi code từ contributor.

**Tại sao:** Team đúng ở chỗ workflow definition đến từ base branch, nhưng sai khi suy ra mọi executable code trong job đều trusted. Sau checkout, `npm ci`, shell scripts và Docker build chạy nội dung do contributor kiểm soát.

**Ảnh hưởng:** Fork contributor có thể thực thi code với access tới secrets/token của job và exfiltrate hoặc dùng chúng cho repository/cloud actions.

**Cách sửa:** PR từ fork phải chạy bằng `pull_request` với read-only/minimal permissions và không có repository/cloud secrets. Privileged follow-up tách riêng và tuyệt đối không checkout/execute PR head.

### Critical — Secret exfiltration không cần sửa YAML

**Vấn đề:** `npm ci` có thể chạy lifecycle scripts; `docker-compose.ci.yml`, Dockerfile, `test-all.sh` và test code đều có thể được contributor sửa.

**Tại sao:** Build/test pipeline chính là arbitrary code execution by design.

**Ảnh hưởng:** Malicious PR có thể đọc environment, temp credential file, GitHub token hoặc filesystem rồi gửi dữ liệu ra ngoài.

**Cách sửa:** Treat toàn bộ fork code là untrusted. Chạy trong secretless, ephemeral, network-restricted environment theo threat model. Không cố xây file allowlist để biến arbitrary build/test code thành trusted.

### Critical — Long-lived cloud credential nằm trong cùng job với untrusted code

**Vấn đề:** Workflow ghi `CLOUD_SERVICE_ACCOUNT_JSON` ra file rồi tiếp tục chạy contributor-controlled code.

**Tại sao:** Integration-test convenience được ưu tiên hơn credential boundary.

**Ảnh hưởng:** Nếu bị lấy, credential có thể tiếp tục dùng ngoài GitHub Actions tới khi revoke/rotate; blast radius phụ thuộc cloud IAM role.

**Cách sửa:** Untrusted PR không được có production-capable credential. Trusted deployment/integration workflow nên ưu tiên OIDC/workload identity federation với short-lived token, explicit subject/ref/environment conditions và least-privilege role.

### Critical — Deployment artifact không có provenance/authorization boundary rõ

**Vấn đề:** Deployment tải artifact chỉ theo tên `app-package`.

**Tại sao:** Artifact name bị coi như identity và trust proof.

**Ảnh hưởng:** Nếu deployment có thể consume artifact từ PR/untrusted run, attacker có đường từ fork PR tới deployed payload ngay cả khi production credential không có trong PR job.

**Cách sửa:** Deployment chỉ dùng artifact build từ protected branch/tag hoặc trusted workflow. Validate repository, source workflow, run ID, commit SHA, artifact digest và provenance/attestation theo platform capability. Tách PR artifacts khỏi release artifacts.

### High — `GITHUB_TOKEN` permissions quá rộng

**Vấn đề:** Test job có `contents: write`, `pull-requests: write`, `actions: write`.

**Tại sao:** Permissions đặt ở workflow level “cho tiện”.

**Ảnh hưởng:** Token bị compromise có API capability lớn hơn nhiều nhu cầu test.

**Cách sửa:** Đặt default permissions tối thiểu; PR validation thường chỉ cần `contents: read`. Tách comment job nếu cần `pull-requests: write`; deployment permissions chỉ xuất hiện trong trusted protected workflow/environment.

### High — Mutable action tags/branch tăng supply-chain risk

**Vấn đề:** `@v4` và đặc biệt `@main` không phải immutable code identity.

**Tại sao:** Team coi release tag/branch như content-addressed dependency.

**Ảnh hưởng:** Nếu upstream action/tag bị compromise hoặc retarget, workflow có thể chạy code mới mà repo này không đổi.

**Cách sửa:** Với high-trust workflows, pin action tới full-length commit SHA đã review và dùng dependency-update automation để nâng SHA có kiểm soát. GitHub security guidance xác định full-length commit SHA là immutable reference mạnh nhất cho actions.

### High — Label `safe-to-test` không phải trust boundary đủ mạnh

**Vấn đề:** Label gắn với PR object, trong khi contributor có thể cập nhật head commit sau đó; condition còn cho nhiều event khác chạy job.

**Tại sao:** Human approval không được bind vào immutable SHA/trust transition.

**Ảnh hưởng:** Maintainer có thể vô tình cấp privileged execution cho code chưa review.

**Cách sửa:** Preferred design là không bao giờ cấp secret/write token cho arbitrary fork code. Nếu có exceptional gated workflow, approval phải gắn immutable SHA, trusted actor và protected environment; head update phải invalidate approval.

### High — Test/repository mutation nằm cùng trust zone

**Vấn đề:** Job vừa chạy arbitrary code vừa dùng write-capable action để comment PR.

**Tại sao:** Build evidence và privileged repository mutation bị gộp vào một job.

**Ảnh hưởng:** Token theft là rủi ro trực tiếp; ngoài ra output do untrusted code tạo có thể trở thành malicious input cho downstream action.

**Cách sửa:** Untrusted job tạo bounded machine-readable result. Privileged job chỉ đọc/sanitize metadata được phép và post comment, không checkout PR head, không execute artifact.

### Medium — Credential được materialize thành file và sống qua nhiều steps

**Vấn đề:** `/tmp/cloud.json` tồn tại trong runner trong khi các bước sau thực thi untrusted code.

**Tại sao:** Credential lifetime không được minimize.

**Ảnh hưởng:** Tăng số đường đọc/exfiltrate và có thể bị thu thập bởi debug/artifact step sai cấu hình.

**Cách sửa:** Đây không phải root-cause fix — untrusted job vẫn không được có credential. Trong trusted workflow, ưu tiên short-lived federation; nếu buộc dùng file thì permission/lifetime tối thiểu và cleanup chắc chắn.

### Medium — PR package và release package không được tách lifecycle

**Vấn đề:** Cùng tên `app-package` tạo cảm giác PR artifact có thể promote trực tiếp.

**Tại sao:** Build once/deploy philosophy được áp dụng mà không có trust distinction.

**Ảnh hưởng:** Một pipeline configuration mistake có thể promote untrusted binary.

**Cách sửa:** PR artifacts chỉ phục vụ diagnostics/testing. Release artifact phải được rebuild hoặc attested trong trusted context từ protected source; deployment verify source + digest + provenance.

## Phiên bản đề xuất

PR validation dùng `pull_request`, token đọc tối thiểu và **không có secrets**:

```yaml
name: pr-validation

on:
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@<FULL_COMMIT_SHA>

      - uses: actions/setup-node@<FULL_COMMIT_SHA>
        with:
          node-version: 22
          cache: npm

      - run: npm ci
      - run: docker compose -f docker-compose.ci.yml up -d --build
      - run: ./scripts/test-all.sh

      - uses: actions/upload-artifact@<FULL_COMMIT_SHA>
        with:
          name: pr-test-result
          path: ./test-results/**
```

Một privileged workflow có thể comment dựa trên **validated metadata**, nhưng không execute PR content:

```yaml
permissions:
  contents: read
  pull-requests: write

jobs:
  comment:
    runs-on: ubuntu-latest

    steps:
      - name: Validate source run metadata
        run: ./trusted/validate-source-run.sh

      - name: Render bounded comment
        run: ./trusted/render-comment.sh

      - name: Post comment
        run: ./trusted/post-comment.sh
```

Release/deployment workflow nên chạy từ protected branch/tag hoặc trusted promotion event, build/obtain artifact có source identity rõ, authenticate cloud bằng OIDC short-lived identity và verify artifact digest/provenance trước deploy.

## Giải thích thiết kế sau khi sửa

Thiết kế mới dựa trên **trust zones** thay vì cố làm một workflow vừa chạy untrusted code vừa có privileged credentials.

Fork PR validation được coi là hostile-code execution. Vì mục tiêu build/test chính là chạy code do contributor gửi, job đó phải không có valuable secrets/write token. Ephemeral runner giảm persistence nhưng không biến secrets trong cùng job thành an toàn.

Privileged operations — comment bằng token ghi, mint cloud credentials, release và deploy — chuyển sang workflow khác chỉ chạy trusted code từ protected source. Dữ liệu đi từ untrusted zone sang privileged zone phải được coi là untrusted input, validate schema/size/source và không execute.

Artifact cũng cần authorization, không chỉ checksum. Digest chứng minh bytes không đổi; provenance/source policy chứng minh bytes được build bởi workflow/commit nào; deployment authorization quyết định source đó có được phép lên môi trường hay không.

## Trade-offs

- **Secretless fork CI:** an toàn hơn nhưng một số integration tests không thể chạy với production-like cloud credential; có thể dùng emulator, local dependency hoặc ephemeral sandbox có blast radius chấp nhận được.
- **Rebuild release artifact từ protected branch:** tốn compute thêm nhưng tạo trust boundary rõ hơn so với promote arbitrary PR artifact.
- **Pin full SHA:** tăng update maintenance; bù lại dependency identity immutable và reviewable.
- **Tách workflows/jobs:** pipeline phức tạp hơn một chút nhưng permissions và audit boundary rõ ràng hơn.
- **OIDC short-lived identity:** cần cloud IAM setup tốt; đổi lại loại bỏ nhiều long-lived static secrets và giới hạn trust theo repo/ref/environment.

## Cách kiểm thử

1. Tạo fork PR thêm malicious `preinstall`/test script cố đọc marker secret; PR job phải không có secret/write token để lấy.
2. Verify GitHub API write từ PR validation thất bại do permissions tối thiểu.
3. Label PR rồi push head SHA mới; privileged approval không được tự động áp dụng cho commit mới.
4. Tạo artifact cùng tên từ untrusted PR run; deployment phải reject vì source workflow/ref/provenance không hợp lệ.
5. Policy test fail workflow khi third-party action không pin full commit SHA hoặc khi cloud deployment job không dùng protected trust conditions.

## Quan sát trong production

- Audit/alert nếu workflow từ fork nhận environment/repository secret hoặc write-capable token; target = 0.
- Inventory permissions theo workflow/job để phát hiện permission creep.
- Inventory action references và tỷ lệ pinned-to-full-SHA.
- Cloud IAM logs cho OIDC subject: repository, workflow, ref/environment và token lifetime.
- Deployment record phải gắn commit SHA, workflow run ID, artifact digest và provenance/source identity.
- Alert nếu release artifact đến từ PR/fork/untrusted workflow hoặc source khác protected branch/tag policy.

## Câu hỏi phỏng vấn mở rộng

1. Nếu integration test thật sự cần cloud service, bạn thiết kế ephemeral test environment và credential scope thế nào để chấp nhận việc PR code có thể cố exfiltrate credential?
2. Artifact integrity, provenance và deployment authorization khác nhau thế nào?
3. Nếu team chuyển từ GitHub-hosted runner sang long-lived self-hosted runner, threat model của untrusted fork code thay đổi ra sao?

# Tổng kết hôm nay

## Kiến thức trọng tâm

- Multi-tenant security cần **authorization + explicit tenant execution context + data-layer/database guardrails**; global query filter chỉ là một lớp phòng vệ.
- `DbContext` pooling là performance optimization có lifecycle semantics cần hiểu rõ; request-specific mutable state không được đưa vào pooled context một cách ngầm định.
- Background processing phải mang tenant/business context trong job/message thay vì trông chờ HTTP state.
- CI chạy fork code phải được xem là **untrusted arbitrary-code execution**. Secrets, write token và production credentials không được đặt cùng trust zone.
- Artifact name/checksum không đủ cho deployment trust; cần source identity, provenance và authorization policy.

## Mẫu tư duy cần nhớ

1. **Security invariant phải có nhiều lớp phòng vệ, không dựa vào một convenience feature.**
2. **State theo request/tenant phải có lifetime và propagation rõ ràng.**
3. **Trace mọi executable input qua trust boundary, không chỉ workflow/config file.**
4. **Least privilege trước, rồi mới thêm capability có lý do.**
5. **Integrity, provenance và authorization là ba câu hỏi khác nhau.**
