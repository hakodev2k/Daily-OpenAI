# Code Review Challenge 1 — Azure Service Bus consumer hoàn tất message trước khi transaction nghiệp vụ thật sự an toàn

**Chủ đề:** C#/.NET, Azure Service Bus, EF Core, idempotency, message settlement, transaction boundary, retry  
**Độ khó:** Senior+  
**Thời gian review đề xuất:** 35 phút  
**Số vấn đề cần tìm:** khoảng 9–12 vấn đề

## Bối cảnh

Một order service nhận `OrderPaid` từ Azure Service Bus. Mỗi message phải cập nhật order trong SQL Server, tạo fulfillment record và gọi warehouse API. Hệ thống chạy nhiều replicas. Service Bus có thể redeliver message khi lock hết hạn hoặc consumer lỗi.

Production có hai triệu chứng hiếm: một số order đã `Completed` nhưng không có fulfillment; một số order tạo hai shipment khi warehouse chậm. Team cho rằng `AutoCompleteMessages = true` và kiểm tra `order.Status` đã đủ chống duplicate.

## Đoạn code cần review

```csharp
public sealed class OrderPaidConsumer
{
    private readonly AppDbContext _db;
    private readonly WarehouseClient _warehouse;
    private readonly ILogger<OrderPaidConsumer> _logger;

    public OrderPaidConsumer(
        AppDbContext db,
        WarehouseClient warehouse,
        ILogger<OrderPaidConsumer> logger)
    {
        _db = db;
        _warehouse = warehouse;
        _logger = logger;
    }

    public async Task HandleAsync(
        ProcessMessageEventArgs args,
        CancellationToken cancellationToken)
    {
        var message = JsonSerializer.Deserialize<OrderPaid>(args.Message.Body)!;

        var order = await _db.Orders
            .SingleAsync(x => x.Id == message.OrderId, cancellationToken);

        if (order.Status == "Completed")
            return;

        order.Status = "Completed";
        await _db.SaveChangesAsync(cancellationToken);

        var shipmentId = await _warehouse.CreateShipmentAsync(
            message.OrderId,
            message.Address,
            cancellationToken);

        _db.Fulfillments.Add(new Fulfillment
        {
            OrderId = message.OrderId,
            ShipmentId = shipmentId
        });

        await _db.SaveChangesAsync(cancellationToken);

        _logger.LogInformation(
            "Order {OrderId} fulfilled as {ShipmentId}",
            message.OrderId,
            shipmentId);
    }
}
```

Processor được cấu hình:

```csharp
var options = new ServiceBusProcessorOptions

    AutoCompleteMessages = true,
    MaxConcurrentCalls = 16,
    MaxAutoLockRenewalDuration = TimeSpan.FromMinutes(2)
```

### Gợi ý 2

## Kết quả code review tham khảo

### Critical — Order có thể `Completed` nhưng fulfillment chưa tồn tại

**Vấn đề:** Code persist `Completed` trước khi tạo shipment và fulfillment.

**Tại sao xảy ra:** Hai `SaveChangesAsync` tạo hai local commit boundaries. Crash hoặc warehouse failure sau commit đầu tiên để lại trạng thái trung gian không được mô hình hóa.

**Ảnh hưởng production:** Redelivery thấy `Completed` và return, khiến order vĩnh viễn không được fulfill.

**Cách sửa:** Không dùng `Completed` như marker idempotency trước khi workflow hoàn tất. Mô hình hóa trạng thái `Paid/Processing/Fulfilled/Failed/Unknown` và persist durable operation state.

### Critical — External shipment có thể được tạo hai lần

**Vấn đề:** `CreateShipmentAsync` là external side effect nhưng không có stable idempotency key.

**Tại sao xảy ra:** Warehouse có thể commit shipment rồi response timeout; consumer retry/redelivery gọi lại.

**Ảnh hưởng production:** Duplicate shipment, chi phí vận chuyển và reconciliation thủ công.

**Cách sửa:** Nếu provider hỗ trợ idempotency, dùng stable operation key gắn với order/fulfillment attempt. Nếu không, cần provider lookup/reconciliation hoặc business protocol chống duplicate.

### High — `order.Status` không phải idempotency record đáng tin cậy

**Vấn đề:** Check-then-update không chứng minh event cụ thể đã được xử lý.

**Tại sao xảy ra:** Nó trộn business state với message-processing identity và không lưu `MessageId`/event identity.

**Ảnh hưởng production:** Duplicate, out-of-order event hoặc workflow khác thay đổi status có thể cho kết quả sai.

**Cách sửa:** Dùng Inbox/idempotency record với unique constraint trên stable event ID khi requirement phù hợp.

### High — Concurrent processing có race condition

**Vấn đề:** Hai handlers có thể cùng đọc status chưa `Completed` trước khi một bên commit.

**Tại sao xảy ra:** Không có optimistic concurrency token, unique invariant hoặc transactional claim.

**Ảnh hưởng production:** Cả hai có thể gọi warehouse.

**Cách sửa:** Enforce invariant ở database bằng unique constraint/concurrency control; đừng chỉ dựa vào `if` trong memory.

### High — `AutoCompleteMessages` che mờ settlement boundary

**Vấn đề:** Handler return thành công thì SDK có thể complete message, nhưng điều đó không biến SQL + warehouse thành atomic transaction.

**Tại sao xảy ra:** Broker settlement là boundary riêng với database và HTTP dependency.

**Ảnh hưởng production:** Business state có thể incomplete dù message đã được settlement.

**Cách sửa:** Chọn explicit settlement khi cần kiểm soát rõ; chỉ complete sau khi durable processing state đạt condition đã định nghĩa. Vẫn phải idempotent vì crash có thể xảy ra trước/after settlement.

### High — Lock duration/renewal không phải correctness guarantee

**Vấn đề:** Team có thể coi auto lock renewal là bảo đảm single execution.

**Tại sao xảy ra:** Processing có thể vượt renewal budget, network failure hoặc process pause/crash; message có thể redeliver.

**Ảnh hưởng production:** Concurrent/redelivered processing.

**Cách sửa:** Thiết kế consumer chịu được redelivery; theo dõi lock-lost và processing duration. Không dùng lock như idempotency mechanism.

### Medium — Không phân loại transient/permanent failure

**Vấn đề:** Code không thể hiện retry budget, dead-letter policy hay poison-message strategy.

**Tại sao xảy ra:** Mọi exception được đẩy cho processor behavior mặc định.

**Ảnh hưởng production:** Hot retry, backlog hoặc poison message lặp lại.

**Cách sửa:** Xác định retryable dependency errors, delivery-count threshold, DLQ/recovery workflow và alerting.

### Medium — Deserialize/validation quá tin tưởng payload

**Vấn đề:** `!` bỏ qua invalid/null payload và không validate version/business invariants.

**Tại sao xảy ra:** Message contract được coi là luôn hợp lệ.

**Ảnh hưởng production:** Poison message hoặc invalid address đi sâu vào workflow.

**Cách sửa:** Validate schema/version/required fields; classify malformed messages và dead-letter với reason an toàn.

### Medium — Cancellation có thể tạo unknown outcome

**Vấn đề:** Cancellation trong lúc warehouse request đang thực hiện không chứng minh side effect chưa xảy ra.

**Tại sao xảy ra:** Cancellation chỉ mô tả local wait/control flow.

**Ảnh hưởng production:** Retry mù quáng có thể duplicate shipment.

**Cách sửa:** Reconcile external outcome bằng idempotency key/reference trước khi retry side effect.

## Phiên bản đề xuất

Ví dụ dưới đây giả định warehouse hỗ trợ stable idempotency key và database có unique constraint trên `ProcessedMessage.MessageId` cùng unique fulfillment operation theo order. Production implementation còn cần policy cho retry/DLQ và transaction isolation phù hợp.

```csharp
public async Task HandleAsync(
    ProcessMessageEventArgs args,
    CancellationToken ct)
{
    var evt = DeserializeAndValidate(args.Message);
    var messageId = args.Message.MessageId;

    await using (var tx = await _db.Database.BeginTransactionAsync(ct))
    {
        if (await _db.ProcessedMessages.AnyAsync(x => x.MessageId == messageId, ct))
        {
            await tx.RollbackAsync(ct);
            await args.CompleteMessageAsync(args.Message, ct);
            return;
        }

        var order = await _db.Orders.SingleAsync(x => x.Id == evt.OrderId, ct);

        var operation = await _db.FulfillmentOperations
            .SingleOrDefaultAsync(x => x.OrderId == evt.OrderId, ct);

        if (operation is null)
        {
            operation = new FulfillmentOperation
            {
                Id = Guid.NewGuid(),
                OrderId = evt.OrderId,
                Status = "Pending"
            };
            _db.FulfillmentOperations.Add(operation);
        }

        _db.ProcessedMessages.Add(new ProcessedMessage(messageId));
        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }

    var op = await _db.FulfillmentOperations
        .SingleAsync(x => x.OrderId == evt.OrderId, ct);

    if (op.Status != "Succeeded")
    {
        var shipment = await _warehouse.CreateShipmentAsync(
            evt.OrderId,
            evt.Address,
            idempotencyKey: op.Id.ToString("N"),
            ct);

        await using var tx = await _db.Database.BeginTransactionAsync(ct);
        op.Status = "Succeeded";
        op.ShipmentId = shipment.Id;

        var order = await _db.Orders.SingleAsync(x => x.Id == evt.OrderId, ct);
        order.Status = "Fulfilled";

        await _db.SaveChangesAsync(ct);
        await tx.CommitAsync(ct);
    }

    await args.CompleteMessageAsync(args.Message, ct);
}
```

Điểm quan trọng: snippet này minh họa durable operation identity, không phải tuyên bố rằng mọi workflow nên đánh dấu Inbox trước external call. Nếu đánh dấu message processed trước khi side effect hoàn tất, recovery phải dựa trên `FulfillmentOperation` chứ không được đơn giản skip toàn bộ workflow. Một thiết kế khác là transactional state machine/outbox với worker riêng cho warehouse call.

## Giải thích thiết kế sau khi sửa

Broker delivery, SQL commit và warehouse side effect là ba failure domains. Không thể biến chúng thành một transaction đơn giản. Design cần stable identity, durable workflow state và idempotent/reconcilable external call. Database constraints bảo vệ invariant dưới concurrency; message settlement chỉ diễn ra khi durable state cho phép recovery an toàn.

## Trade-offs

Inbox/state machine tăng schema và code. Explicit settlement tăng responsibility cho consumer. Provider idempotency có thể có retention window và semantics riêng cần xác minh. Tách warehouse call qua outbox/worker tăng eventual consistency nhưng thường làm recovery boundary rõ hơn.

## Cách kiểm thử

1. **Integration/failure-path:** crash sau SQL commit đầu nhưng trước warehouse call; redelivery phải tiếp tục workflow đúng.
2. **Failure injection:** warehouse tạo shipment nhưng response timeout; retry không tạo shipment thứ hai.
3. **Concurrency:** hai deliveries cùng event/order chạy song song; chỉ một logical fulfillment được tạo.
4. **Service Bus integration:** lock expiry/redelivery và delivery count tăng; consumer vẫn idempotent.
5. **Database test:** unique constraints chặn duplicate inbox/fulfillment operation.

## Quan sát trong production

Theo dõi `MessageId`, `OrderId`, delivery count, processing duration, lock-lost events, settlement outcome, retry/DLQ count, fulfillment-operation state, warehouse idempotency/reference, unknown outcomes và duplicate-prevention events. Correlate trace Service Bus → SQL → warehouse dependency; alert theo DLQ growth, oldest-message age và tỷ lệ workflow mắc ở `Pending/Unknown`.

## Câu hỏi phỏng vấn mở rộng

1. Nếu warehouse không hỗ trợ idempotency key hoặc lookup theo client reference, bạn giảm duplicate risk thế nào?
2. Inbox Pattern khác gì với việc chỉ check `Order.Status`?
3. Nếu requirement cần giữ thứ tự event theo từng order, bạn đánh giá Service Bus sessions như thế nào?

# Code Review Challenge 2 — React search page bị stale response ghi đè state và tạo request storm

**Chủ đề:** React, TypeScript, browser fetch, async race condition, request cancellation, UX, API load  
**Độ khó:** Senior  
**Thời gian review đề xuất:** 30 phút  
**Số vấn đề cần tìm:** khoảng 8–10 vấn đề

## Bối cảnh

Một product-search page gọi ASP.NET Core search API mỗi khi user thay đổi query, category hoặc sort. Với mạng nhanh mọi thứ có vẻ đúng. Trên mobile network, user gõ nhanh thấy kết quả đôi lúc quay về query cũ. Backend ghi nhận lượng request tăng mạnh và nhiều request tiếp tục chạy dù user đã thay đổi search criteria.

Component được dùng trong React application chạy client-side. Search API hỗ trợ `CancellationToken` khi client disconnect, nhưng team chưa xác minh browser/proxy có propagate cancellation đến backend trong mọi trường hợp.

## Đoạn code cần review

```tsx
import { useEffect, useState } from "react";

type Product = {
  id: string;
  name: string;
  price: number;
};

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [sort, setSort] = useState("relevance");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    setLoading(true);
    setError(null);

    fetch(`/api/products?q=${query}&category=${category}&sort=${sort}`)
      .then(r => {
        if (!r.ok) throw new Error(`HTTP ${r.status}`);
        return r.json();
      })
      .then(data => {
        setProducts(data.items);
        setLoading(false);
      })
      .catch(err => {
        setError(err.message);
        setLoading(false);
      });
  }, [query, category, sort]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      <select value={category} onChange={e => setCategory(e.target.value)}>
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="electronics">Electronics</option>
      </select>
      <select value={sort} onChange={e => setSort(e.target.value)}>
        <option value="relevance">Relevance</option>
        <option value="price">Price</option>
      </select>
      {loading && <p>Loading...</p>}
      {error && <p>{error}</p>}
      <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>
    </section>
  );
}
```

4. Ưu tiên findings theo severity.
5. Đề xuất implementation tốt hơn mà không over-engineer.

## Kết quả code review tham khảo

### High — Stale response có thể ghi đè kết quả mới

**Vấn đề:** Mọi response đều gọi `setProducts`, bất kể criteria hiện tại đã thay đổi.

**Tại sao xảy ra:** Network completion order không đảm bảo giống request order.

**Ảnh hưởng production:** User nhập `iphone`, request mới trả trước, sau đó response cho `iph` trả muộn và ghi đè UI.

**Cách sửa:** Abort request cũ và/hoặc dùng request generation/identity để chỉ latest request được commit state.

### High — Mỗi keystroke tạo request mới

**Vấn đề:** Query thay đổi lập tức kích hoạt effect.

**Tại sao xảy ra:** Không có debounce/minimum query policy.

**Ảnh hưởng production:** Request storm từ một user, tăng API/search dependency load và chi phí.

**Cách sửa:** Debounce input theo UX requirement; cân nhắc minimum query length và server-side protection.

### High — Request cũ không được cleanup

**Vấn đề:** Effect không return cleanup function.

**Tại sao xảy ra:** Không có `AbortController`.

**Ảnh hưởng production:** Browser tiếp tục chờ/nhận response không còn hữu ích; backend có thể tiếp tục work.

**Cách sửa:** Tạo controller cho mỗi effect và abort trong cleanup. Backend vẫn phải có timeout/cancellation/capacity controls riêng.

### Medium — Loading state có race

**Vấn đề:** Request cũ có thể `setLoading(false)` trong khi request mới vẫn pending.

**Tại sao xảy ra:** Loading state không gắn với active request identity.

**Ảnh hưởng production:** UI báo hết loading nhưng latest search chưa hoàn tất.

**Cách sửa:** Chỉ latest request được cập nhật loading/error/products.

### Medium — Error state có thể hiển thị lỗi của request obsolete

**Vấn đề:** Catch của request cũ vẫn `setError`.

**Tại sao xảy ra:** Không phân biệt abort/stale request với active failure.

**Ảnh hưởng production:** UI hiển thị error dù latest request thành công.

**Cách sửa:** Ignore `AbortError` và guard state updates bằng request identity.

### Medium — Query string không encode parameters

**Vấn đề:** Raw user input được nội suy vào URL.

**Tại sao xảy ra:** Không dùng `URLSearchParams`.

**Ảnh hưởng production:** Các ký tự `&`, `+`, `#`, Unicode edge cases có thể làm request semantics sai.

**Cách sửa:** Dùng `URLSearchParams`.

### Medium — Response shape được trust hoàn toàn

**Vấn đề:** `r.json()` được dùng như `data.items` mà không validate contract.

**Tại sao xảy ra:** TypeScript type không validate runtime JSON.

**Ảnh hưởng production:** API regression/malformed response gây runtime error hoặc state sai.

**Cách sửa:** Có contract validation phù hợp mức rủi ro hoặc ít nhất defensive shape handling; shared generated API types không thay thế runtime validation nếu boundary cần trust validation.

### Low — Accessibility/UX state chưa đầy đủ

**Vấn đề:** Loading/error text chưa có live-region semantics; stale products vẫn hiển thị mà không có UX decision rõ.

**Tại sao xảy ra:** Component tập trung happy path.

**Ảnh hưởng production:** Screen-reader feedback kém và user khó hiểu trạng thái.

**Cách sửa:** Thiết kế loading/error semantics rõ, dùng `aria-live`/status phù hợp và quyết định có giữ stale results trong lúc loading hay không.

## Phiên bản đề xuất

```tsx
import { useEffect, useRef, useState } from "react";

export function ProductSearch() {
  const [query, setQuery] = useState("");
  const [category, setCategory] = useState("all");
  const [sort, setSort] = useState("relevance");
  const [debouncedQuery, setDebouncedQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<string | null>(null);
  const generation = useRef(0);

  useEffect(() => {
    const timer = window.setTimeout(() => setDebouncedQuery(query.trim()), 300);
    return () => window.clearTimeout(timer);
  }, [query]);

  useEffect(() => {
    const controller = new AbortController();
    const current = ++generation.current;

    const run = async () => {
      setLoading(true);
      setError(null);

      const qs = new URLSearchParams({
        q: debouncedQuery,
        category,
        sort
      });

      try {
        const response = await fetch(`/api/products?${qs}`, {
          signal: controller.signal
        });

        if (!response.ok)
          throw new Error(`HTTP ${response.status}`);

        const data = await response.json();
        if (current !== generation.current) return;

        setProducts(Array.isArray(data.items) ? data.items : []);
      } catch (err) {
        if (controller.signal.aborted || current !== generation.current)
          return;

        setError(err instanceof Error ? err.message : "Search failed");
      } finally {
        if (current === generation.current)
          setLoading(false);
      }
    };

    void run();
    return () => controller.abort();
  }, [debouncedQuery, category, sort]);

  return (
    <section>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search products"
      />
      <select value={category} onChange={e => setCategory(e.target.value)}>
        <option value="all">All</option>
        <option value="books">Books</option>
        <option value="electronics">Electronics</option>
      </select>
      <select value={sort} onChange={e => setSort(e.target.value)}>
        <option value="relevance">Relevance</option>
        <option value="price">Price</option>
      </select>
      <p role="status" aria-live="polite">
        {loading ? "Loading..." : error ?? ""}
      </p>
      <ul>{products.map(p => <li key={p.id}>{p.name}</li>)}</ul>
    </section>
  );
}
```

## Giải thích thiết kế sau khi sửa

Debounce giảm số request do typing burst. `AbortController` hủy work không còn cần ở browser khi có thể, còn generation guard đảm bảo stale completion không được commit state kể cả khi cancellation không ngăn response hoàn tất. Hai cơ chế bổ sung nhau.

Backend vẫn phải tự bảo vệ bằng request timeout, cancellation propagation tới downstream, query limits và capacity controls. Client cancellation không phải distributed transaction hay guarantee rằng SQL/search engine đã dừng ngay.

## Trade-offs

Debounce tăng một ít perceived latency; thời gian 300 ms chỉ là ví dụ và cần UX measurement. Abort làm giảm wasted work nhưng không đảm bảo dependency đã hủy. Runtime response validation tăng code/bundle complexity nên mức độ cần thiết phụ thuộc trust boundary và API tooling.

## Cách kiểm thử

1. **Component test:** response cho query cũ trả sau query mới; UI phải giữ kết quả mới.
2. **Component test:** thay criteria nhanh; request trước bị abort và `AbortError` không hiện ra UI.
3. **Fake-timer test:** nhiều keystrokes trong debounce window chỉ phát request theo policy đã định.
4. **E2E/Playwright:** throttle network, gõ nhanh và đổi category/sort; UI cuối cùng phải khớp criteria hiện tại.
5. **Load/API test:** đo request amplification trước/sau debounce và xác minh backend cancellation/timeout behavior.

## Quan sát trong production

Frontend theo dõi search request count/session, aborted requests, latency, error rate và criteria-to-result mismatch nếu có instrumentation phù hợp. Backend theo dõi request rate, p95/p99, cancelled requests, downstream query duration, CPU, connection usage và search dependency load. Browser Network panel và distributed tracing giúp xác định request nào obsolete nhưng vẫn tiêu tốn backend work.

## Câu hỏi phỏng vấn mở rộng

1. Nếu search dùng React Query/TanStack Query hoặc framework data layer, bạn vẫn cần hiểu guarantee nào thay vì giả định library tự giải quyết mọi race?
2. Nếu backend search rất đắt nhưng browser abort không propagate tới Elasticsearch, bạn bảo vệ server bằng cách nào?
3. Khi nào giữ stale results trong lúc fetch mới tốt hơn việc clear list ngay lập tức?

# Tổng kết hôm nay

## Kiến thức trọng tâm

Hai challenge cùng kiểm tra một nguyên tắc quan trọng: **completion ở một layer không đồng nghĩa toàn workflow đã an toàn**. Service Bus settlement không tạo atomicity với SQL và external warehouse; browser cancellation không đảm bảo backend/downstream đã dừng. Correctness cần stable identity, explicit state boundaries và thiết kế chịu được out-of-order/duplicate/partial failure.

## Mẫu tư duy cần nhớ

- Xác định transaction/failure boundary trước khi thiết kế retry.
- Thiết kế duplicate delivery cùng với idempotency, không dựa vào happy-path state check.
- Async completion có thể out-of-order; chỉ đúng operation được quyền commit state.
- Cancellation là tín hiệu điều khiển, không phải bằng chứng side effect chưa xảy ra.
- Test failure window và concurrency thay vì chỉ test success path.
