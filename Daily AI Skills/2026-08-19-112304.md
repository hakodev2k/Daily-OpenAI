## 3. Prompt, Skills, Rules, and Context Engineering

### Technique A — Biến prompt experiment thành reproducible test fixture

**Problem:** Prompt thường được tinh chỉnh trong chat UI, sau đó copy thủ công sang code. Kết quả production khác UI nhưng không rõ do prompt, parameter, model hay harness.

**Proposed improvement:**

1. Dùng Playground hoặc API client tạo một canonical request.
2. Lưu `system/developer/user`, tools, model, reasoning/effort, temperature-like parameters nếu hợp lệ, expected schema và fixture input trong repository.
3. Ghi rõ acceptance criteria bằng deterministic assertions trước, LLM-as-a-judge sau.
4. Khi đổi prompt/rule, chạy lại cùng fixture.

**Why it may work:** Nó tách “prompt quality” khỏi accidental UI state và tạo regression history.

**Suitable use cases:** Requirement analysis agent, code review agent, SQL review agent, architecture recommendation agent, interview question generator.

**Limitations:** Model output vẫn stochastic; exact string comparison hiếm khi phù hợp.

**Risks:** Test fixture quá hẹp có thể overfit prompt vào benchmark.

**Recommendation:** Mỗi reusable skill quan trọng nên có 5–20 golden cases thay vì chỉ một prompt file.

**Uncertainty:** Số lượng test case tối ưu phụ thuộc variation của task; không có một con số chung.

---

### Technique B — Tách repository guidance thành policy, knowledge và procedure

**Problem:** Một `AGENTS.md`, Cursor rule hoặc Claude instruction file quá dài dễ trộn ba loại nội dung khác nhau: nguyên tắc bắt buộc, kiến thức dự án và quy trình thực hiện.

**Proposed improvement:**

- **Policy:** điều agent không được vi phạm — security, dependency boundaries, forbidden operations.
- **Knowledge:** architecture map, domain glossary, data ownership, service dependencies.
- **Procedure:** cách chạy test, migration, review, release, incident investigation.

**Why it may work:** Agent có thể retrieve đúng loại context theo task; conflict cũng dễ phát hiện hơn.

**Suitable use cases:** Cursor rules/skills, Claude Code project instructions, Codex skills, multi-agent repository workflows.

**Limitations:** Tool/harness khác nhau có cơ chế loading context khác nhau.

**Risks:** Duplicate rule giữa nhiều file gây drift.

**Recommendation:** Đặt một source-of-truth policy rồi generate hoặc reference các tool-specific wrappers khi có thể.

**Uncertainty:** Không nên giả định một format portable hoàn toàn giữa Cursor, Claude Code, Copilot và Codex.

---

### Technique C — Thêm explicit evidence contract cho research/review agents

**Problem:** Agent có thể trộn confirmed fact, inference và recommendation trong cùng một đoạn, khiến reviewer khó biết phần nào cần verify.

**Proposed improvement:** Mỗi finding bắt buộc trả về:

- `Fact`
- `Evidence`
- `Inference`
- `Recommendation`
- `Confidence`
- `Unknowns`

**Why it may work:** Buộc reasoning output có provenance và làm failure triage dễ hơn.

**Suitable use cases:** Architecture research, production incident analysis, package upgrade assessment, security review, vendor comparison.

**Limitations:** Structured output không đảm bảo evidence đúng; nguồn vẫn cần validation.

**Risks:** Agent có thể tạo “confidence theater” nếu confidence không gắn với concrete evidence criteria.

**Recommendation:** Confidence chỉ nên tăng khi có source độc lập, deterministic check hoặc reproducible experiment.

## 4. Agent, Workflow, and Loop Engineering

### Workflow 1 — Session fork để so sánh hai solution từ cùng một context

**Problem:** So sánh solution A/B thường bị lệch vì mỗi session thu thập context khác nhau.

**Technique:** Với Codex CLI 0.148.0, fork từ cùng một session state rồi áp dụng hai strategy khác nhau. [OpenAI Codex changelog — 2026-08-18](https://developers.openai.com/codex/changelog)

**Expected benefit:** Fairer comparison và giảm duplicated exploration.

**Suggested loop:**

`Explore -> checkpoint -> fork A/B -> implement -> build/test -> collect metrics -> compare -> human decision`

**Evaluation criteria:**

- build/test pass rate
- changed lines/files
- benchmark latency nếu có
- architectural rule violations
- number of retries
- human review comments
- token/credit cost

**Failure risks:** Hai fork vẫn có stochastic variation; không được kết luận tool/model tốt hơn chỉ từ một run.

**Suitable use cases:** Refactor lớn, EF Core query optimization, architecture migration, competing bug fixes.

---

### Workflow 2 — Async hook cho observability, sync reasoning loop cho critical decisions

**Problem:** Agent loop bị chậm nếu mọi telemetry/log/export đều block turn; nhưng nếu mọi thứ async thì dễ mất control ở write operations.

**Technique:**

- Async: telemetry, transcript export, metrics, read-only metadata sync.
- Sync + approval: deploy, merge, secret access, DB write, issue state transition quan trọng.

**Expected benefit:** Giảm latency nhưng vẫn giữ risk boundary.

**Failure risks:** Async hook có thể fail silently nếu không có retry/dead-letter/health signal.

**Suitable use cases:** Long-running coding agent, CI diagnosis, QA regression agents.

**Recommendation:** Mỗi async hook cần `timeout`, retry budget, idempotency key và log result.

---

### Workflow 3 — Cost-aware stop condition

**Problem:** Agent có thể tiếp tục search/refine nhưng marginal value rất thấp.

**Technique:** Kết hợp progress checkpoints với cost/credit signal. Codex 0.148.0 có estimated thread credit/cost cho eligible workspaces. [OpenAI Codex changelog — 2026-08-18](https://developers.openai.com/codex/changelog)

**Expected benefit:** Phát hiện low-value loops sớm hơn.

**Possible rule:**

- Nếu 2 consecutive iterations không tạo evidence mới hoặc không làm giảm failing tests, dừng và escalate.
- Nếu cost tăng > predefined budget nhưng completion score không cải thiện, checkpoint rồi yêu cầu human decision.

**Failure risks:** Cost thấp không đồng nghĩa hiệu quả; stop rule quá cứng có thể cắt mất task khó nhưng hợp lệ.

**Suitable use cases:** Root-cause analysis, dependency upgrade, flaky test investigation, codebase-wide migration.

---

### Workflow 4 — Human approval theo action class thay vì theo từng tool name

**Problem:** Tool list lớn làm permission policy khó maintain.

**Technique:** Phân action thành class:

- Read local/repo
- Read external
- Write local
- Write remote reversible
- Write remote irreversible
- Secrets/privileged access

**Expected benefit:** Policy rõ hơn và portable hơn giữa MCP/Codex/Copilot/Claude Code.

**Failure risks:** Tool description sai hoặc tool thay behavior có thể bị classify nhầm.

**Suitable use cases:** Multi-MCP systems, internal developer assistants, deployment agents.

**Recommendation:** Tool registry nên có machine-readable risk metadata và owner.

**Security/permission concerns:** Approval message phải hiển thị action chính xác, target, diff, blast radius; tránh generic “Approve”.
