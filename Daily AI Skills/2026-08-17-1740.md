## 1. Executive Summary

### 1. Codex thêm configurable **skill catalog token budget** — thay đổi mới đáng chú ý nhất cho Context Engineering

- **One-sentence summary:** Codex `main` vừa thêm `[skills].max_context_tokens` để override token budget dành cho available-skills catalog; giá trị phải >0, bị cap ở 10.000 tokens, và khi unset vẫn dùng mặc định 2% model context window. [Codex #38978, 17/08/2026](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d)
- **Affected skill area:** Skills architecture, context budgeting, skill discovery, prompt efficiency, evaluation.
- **Why it matters:** Khi số reusable skills tăng, metadata discovery có thể cạnh tranh trực tiếp token với requirements, repository context, evidence và conversation state.
- **Practical implication:** Skill catalog nên được coi là một **bounded retrieval surface** có ngân sách, telemetry và regression tests riêng, thay vì một danh sách càng dài càng tốt.
- **Priority:** **Critical** cho hệ thống nhiều skills; **High** cho coding agent cá nhân.
- **Confirmed facts:** Commit thêm `SkillsConfig.max_context_tokens`; schema yêu cầu minimum 1; configured value capped ở 10.000; tests cover parsing, override, cap và rendering dưới configured budget.
- **Analysis:** Context Engineering cần quản lý **allocation** theo từng surface, không chỉ “viết prompt ngắn hơn”. Với nhiều agent/skills, token budget là một architecture concern có thể đo được.
- **Recommendation:** Định nghĩa `ContextBudget` cho ít nhất `Policy`, `Skill Catalog`, `Repository Context`, `Task Evidence`, `Conversation`, `Tool Results`; log estimated/actual token usage theo surface.
- **Uncertainty:** Đây là source-level change trên `main`; Codex stable `0.147.0` chưa được xác nhận hỗ trợ option này.

### 2. Skill discovery cần được benchmark như một retrieval/routing system

- **One-sentence summary:** Việc Codex giới hạn catalog theo budget cho thấy quality của skill system phụ thuộc vào `routing recall ↔ context cost ↔ latency ↔ task success`, không phải số lượng skills được cài. [Codex #38978](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d)
- **Affected skill area:** Skill routing, prompt evaluation, context retrieval, agent reliability.
- **Why it matters:** Budget quá thấp có thể khiến relevant skill không được expose; quá cao có thể làm catalog lấn át code/evidence và tăng input cost.
- **Practical implication:** Một skill library nên có benchmark corpus với positive/negative triggers và nhiều budget tiers.
- **Priority:** **High**.
- **Confirmed facts:** Codex tests xác nhận catalog rendering phải nằm trong configured budget và budget được chia sẻ giữa catalog sections.
- **Analysis:** Skill catalog thực chất là một **index/retrieval layer**. Progressive disclosure — metadata ngắn để discovery, full procedure chỉ load sau selection — phù hợp hơn full-body injection.
- **Recommendation:** Benchmark `300 / 600 / 1200 / 2400` token catalog budgets trên cùng 30–50 representative tasks; đo `correct skill selected`, `wrong skill selected`, `no skill selected`, task success, input tokens và latency.
- **Uncertainty:** Không có public benchmark cho một “optimal budget” chung; budget tốt phụ thuộc số skills, overlap giữa triggers và task domain.

## 3. Prompt, Skills, Rules, and Context Engineering

### A. Treat **Skill Catalog** như một context surface có ngân sách riêng

- **Problem:** Khi số skills tăng, discovery metadata có thể chiếm context trước cả code, requirements và evidence.
- **Proposed improvement:** Đặt explicit budget cho skill catalog, đồng thời log token allocation theo context surface.
- **Why it may work:** Codex commit mới implement đúng pattern này và có tests đảm bảo catalog nằm trong budget. [Source](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d)
- **Suitable use cases:** Codex skills, Cursor skill libraries, Claude reusable instructions/subagents, internal AI engineering kits.
- **Limitations:** Budget thấp có thể giảm discoverability; budget cao làm tăng cost/latency.
- **Risks:** Chọn budget theo cảm tính mà không eval routing quality.
- **Recommendation:** Mỗi run log dạng:

```text
ContextBudget:
  policy: 700
  skill_catalog: 1200
  repository: 6000
  task_evidence: 5000
  conversation: 4000
  tool_results: dynamic
```

Sau đó so sánh actual usage với task outcome.

### B. Metadata của skill nên tối ưu cho **discovery**, không biến thành full procedure

- **Problem:** Description dài giúp giải thích skill nhưng làm catalog phình nhanh.
- **Proposed improvement:** Discovery metadata chỉ giữ:
  - `name`
  - `when to use / trigger`
  - `expected outcome`
  - `important exclusions`
  - optional `required capability`

  Full workflow, commands, examples, validation rules load sau khi skill được chọn.
- **Why it may work:** Progressive disclosure giảm baseline context nhưng vẫn preserve depth khi cần.
- **Suitable use cases:** QA skills, research skills, code-review skills, architecture skills, GitHub/CI skills.
- **Limitations:** Metadata quá ngắn/ambiguous sẽ giảm routing accuracy.
- **Risks:** Hai skills có trigger overlap dễ gây false selection.
- **Recommendation:** Mỗi skill có ít nhất 3 positive + 3 negative trigger examples và một routing regression test.

### C. Tách `Policy`, `Procedure`, `Context`, `Task`

- **Problem:** Một file `rules.md` lớn dễ trộn security constraints, coding conventions, workflow steps và task-specific details.
- **Proposed improvement:**
  - `policy/`: boundaries, permissions, approval rules, secret/data restrictions.
  - `skills/`: reusable procedures/checklists.
  - `context/`: architecture, repo facts, domain knowledge.
  - `task/`: objective, acceptance criteria, current evidence.
- **Why it may work:** Codex restrictive environment-policy change là evidence cụ thể cho principle scope-aware policy composition. [Source](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)
- **Suitable use cases:** Cursor Rules/Skills, Claude Code `CLAUDE.md`, Codex skills, QA/research/review agents.
- **Limitations:** Nhiều layers hơn cần deterministic loading order.
- **Risks:** Duplicate/conflicting instructions nếu ownership không rõ.
- **Recommendation:** Viết precedence contract ngắn, ví dụ `Policy > Environment restrictions > Task > Skill defaults`; context chỉ cung cấp facts, không tự grant permission.

### D. Explicit provenance cho facts/assumptions/inferences

- **Problem:** Agent dễ biến inference thành “fact” sau nhiều bước, đặc biệt trong architecture review hoặc root-cause analysis.
- **Proposed improvement:** Ở decision points, bắt output theo taxonomy:

```text
FACT
ASSUMPTION
INFERENCE
RECOMMENDATION
UNKNOWN
```

- **Why it may work:** Tạo deterministic review surface cho verifier agent; dễ detect reasoning drift.
- **Suitable use cases:** Incident RCA, requirements analysis, architecture planning, research, interview story verification.
- **Limitations:** Tăng verbosity nếu áp dụng cho mọi câu.
- **Risks:** Agent có thể gắn nhãn đúng nhưng evidence vẫn yếu.
- **Recommendation:** Chỉ enforce taxonomy ở decisions, root causes, risk acceptance và architecture trade-offs.

### E. Context budget phải được eval cùng **information loss**, không chỉ token savings

- **Problem:** Giảm context thường được coi là tốt, nhưng compression có thể làm mất exception/constraint quan trọng.
- **Proposed improvement:** Mỗi context-budget experiment đo cả:
  - tokens
  - latency
  - cost
  - routing recall
  - task success
  - omitted-critical-fact rate
- **Why it may work:** Tránh tối ưu token nhưng làm task quality giảm.
- **Suitable use cases:** Skill catalogs, repository summaries, long-running memory compaction, research handoff.
- **Limitations:** Cần labeled test corpus.
- **Risks:** Dùng LLM-as-a-judge đơn độc có thể che failure; nên có deterministic assertions cho facts bắt buộc.
- **Recommendation:** Kết hợp deterministic validators + rubric judge; judge chỉ chấm phần fuzzy như completeness/readability.

## 4. Agent, Workflow, and Loop Engineering

### A. Loop `Detect → Classify → Verify → Act → Stop`

- **Problem:** Monitoring/research agents dễ tiếp tục search dù không có delta.
- **Technique:**
  1. `Detect`: primary-source delta.
  2. `Classify`: release/security/behavior/doc/none.
  3. `Verify`: source status + date + release channel.
  4. `Act`: deep-dive/test only if material.
  5. `Stop`: `NO_MATERIAL_DELTA` nếu không có evidence mới.
- **Expected benefit:** Giảm duplicate briefing, token waste và low-value loops.
- **Failure risks:** Có thể miss private rollout hoặc source-indexing delay.
- **Suitable use cases:** Daily briefings, GitHub radar, dependency monitoring, release intelligence.
- **Recommendation:** Lưu `last_verified_source_cursor` và `last_material_event_id`; không rerun deep analysis nếu cả hai không đổi.

### B. `Plan → Execute → Verify → Decide` với independent verifier

- **Problem:** Agent vừa tạo solution vừa tự đánh giá solution dễ rationalize lỗi.
- **Technique:** Tách executor và verifier; verifier đọc output + acceptance criteria + evidence nhưng không cần full reasoning transcript.
- **Expected benefit:** Giảm confirmation bias và giúp regression testing reproducible hơn.
- **Failure risks:** Verifier dùng cùng model/prompt có thể chia sẻ blind spot.
- **Suitable use cases:** Code review, test generation, migrations, RCA, architecture plans.
- **Recommendation:** Verifier ưu tiên deterministic checks trước; LLM judge chỉ dùng khi assertion không đủ.

### C. Re-plan sau repeated same-signature failure

- **Problem:** Test-fix-retest loop có thể lặp cùng một lỗi với patch khác nhau mà không học gì mới.
- **Technique:** Chuẩn hóa failure signature từ exception type + stage + key message + relevant state; nếu cùng signature lặp 2 lần, stop patching và chuyển root-cause mode.
- **Expected benefit:** Giảm low-value loop và accidental over-editing.
- **Failure risks:** Signature quá coarse có thể gộp các lỗi khác nhau.
- **Suitable use cases:** Selenium/Playwright UI automation, CI repair, deployment agents, API integration debugging.
- **Recommendation:** Track `attempt`, `failure_signature`, `new_evidence`, `hypothesis_changed`, `next_action`; retry chỉ khi có new evidence/hypothesis.

### D. Approval cache phải gắn với **policy revision**

- **Problem:** Một approval hợp lệ ở policy cũ có thể trở nên quá rộng sau config/environment change.
- **Technique:** Cache key bao gồm command/tool + scope + policy fingerprint/revision.
- **Expected benefit:** Fresh approval khi authority context thay đổi.
- **Failure risks:** Too-frequent invalidation tạo approval fatigue.
- **Suitable use cases:** Production agents, Git write, deploy, DB mutations, cloud-resource operations.
- **Confirmed facts:** Codex source hiện bind environment-policy fingerprint vào approval cache. [Source](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)
- **Recommendation:** Với framework riêng, cache approval theo `(action, normalized target, policyRevision, environment, identity)`.

### E. Durable state phải tách khỏi transcript

- **Problem:** Long-running agents khó resume nếu toàn bộ state chỉ nằm trong chat history.
- **Technique:** Tách:
  - project state
  - run state
  - evidence/artifacts
  - decisions
  - checkpoints
  - transcript
- **Expected benefit:** Resume/fork/retry/audit rõ ràng hơn; dễ compaction transcript mà không mất durable facts.
- **Failure risks:** State schema phức tạp; concurrent updates cần versioning.
- **Suitable use cases:** QA campaigns, research projects, interview knowledge systems, multi-repo architecture work.
- **Recommendation:** Dùng optimistic concurrency/version field cho state objects; transcript chỉ là supporting artifact.

| **Browser automation** | QA agents có thể verify UI end-to-end | Session cookies, auth state, stale DOM, accidental destructive clicks | **Moderate** | Re-query elements; deterministic state checks; restrict destructive actions |
| **Database tools** | Research/QA agents query evidence directly | SQL write, PII, production data | **Advanced** | Read-only identity by default; separate write role with approval |
| **Local file tools** | Repository context, generated artifacts, knowledge transfer | Path traversal, secret files, broad filesystem scope | **Easy–Moderate** | Workspace-root allowlist; deny credential directories |
| **Teams/Slack workflow** | Human-in-the-loop approvals, progress updates, context retrieval | Cross-channel data exposure, impersonation, over-broad scopes | **Moderate** | Separate read/send permissions; explicit target/channel validation |
| **Azure DevOps / CI** | PR/test/deploy orchestration for .NET projects | Service connection privilege, production stage access | **Advanced** | Keep build/test agent separate from deploy agent; production requires explicit gate |

### Hook design rule worth adopting

**Confirmed facts:** Codex’s recent secret-scrubbing change specifically protects model-reachable shell commands and hooks from inheriting an execution-server token. [Source](https://github.com/openai/codex/commit/89e297729ebc1a8c243cef73c7ab64cd842ecd5a)

**Analysis:** A hook should be treated like third-party code at a process boundary even when it lives in the same repository.

**Recommendation:** Every hook execution should resolve four things before spawn: `allowed executable`, `working directory`, `sanitized environment`, `permission profile`. Log these metadata without secrets.

**Uncertainty:** Repository-level hooks can still exfiltrate data through permitted network paths; env scrubbing alone is not a complete sandbox.

## 7. Opportunities and Trends to Watch

### 1. **Context budgets becoming first-class runtime configuration**

- **What is changing:** Skill catalog hiện có explicit budget trong Codex `main`; nhiều agent frameworks đã phải quản lý context compaction/retrieval nhưng thường chưa expose per-surface budget rõ ràng.
- **Why it matters:** Long-context không loại bỏ bài toán allocation; chỉ làm hidden waste dễ tồn tại lâu hơn.
- **Opportunity:** Xây `Context Budget Profiler`/eval harness cho agents: đo system/rules/skills/repo/tool-results/memory allocation và task quality.
- **Risk:** Chỉ tối ưu token count mà không đo information loss.
- **Status:** **Growing**.
- **Confirmed facts:** Codex added configurable skill-catalog budget ngày 17/08/2026. [Source](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d)

### 2. **Skills libraries moving toward retrieval systems, not static prompt bundles**

- **What is changing:** Bounded catalogs, skill search/discovery và progressive loading đang trở thành architecture pattern hợp lý khi số skills tăng.
- **Why it matters:** “More skills installed” có thể giảm quality nếu routing không được eval.
- **Opportunity:** Skill registry có triggers, negative examples, capability requirements, routing metrics và versioning.
- **Risk:** Metadata quality trở thành bottleneck; near-duplicate skills gây collision.
- **Status:** **Growing**.

### 3. **Runtime permission composition over prompt-only safety**

- **What is changing:** Codex source đang strengthen environment-specific policy + approval invalidation.
- **Why it matters:** Agent có quyền thực thi phải có security boundary độc lập model reasoning.
- **Opportunity:** Reusable .NET agent authorization middleware, policy engine, approval service.
- **Risk:** Over-engineering cho low-risk local workflows; approval fatigue nếu granularity sai.
- **Status:** **Established → strengthening**.
- **Confirmed facts:** Environment policy source change rejects allow rules và fingerprints approval cache. [Source](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)

### 4. **Provider-native adapters behind a unified governance layer**

- **What is changing:** OpenCode native OpenAI/Anthropic passthrough illustrates pressure away from lowest-common-denominator compatibility paths.
- **Why it matters:** Reasoning/tool/stream semantics differ across providers and routes.
- **Opportunity:** .NET provider SDK abstraction giữ native request/response while normalizing telemetry, policy, retries, evals.
- **Risk:** Adapter maintenance cost; provider API churn.
- **Status:** **Growing**.
- **Confirmed facts:** OpenCode main merged native OpenAI/Anthropic passthrough. [Source](https://github.com/anomalyco/opencode/commit/cba6b5f2f74080239cdc7405efcb83219c980136)

### 5. **Agent host / durable sessions becoming IDE infrastructure**

- **What is changing:** VS Code 1.131 tiếp tục Agent Host architecture và tăng visibility cho running subagents. [VS Code 1.131, 29/07/2026](https://code.visualstudio.com/updates/v1_131/)
- **Why it matters:** Agent session increasingly behaves như long-running process/resource, không còn chỉ là chat tab.
- **Opportunity:** Standardize run metadata, state handoff, subagent observability, checkpoints và artifact contracts.
- **Risk:** Multi-agent parallelism có thể tăng cost/noise nhanh nếu thiếu budgets và stop conditions.
- **Status:** **Growing**.
