## 3. Prompt, Skills, Rules, and Context Engineering

### A. Tách **policy** khỏi **procedure** và **task context**

- **Problem:** Một file rules lớn thường trộn “must never”, cách thực hiện, convention repo và task-specific instructions; agent khó hiểu precedence và user khó audit.
- **Proposed improvement:** Chia thành 4 lớp: `Organization/Runtime Policy` → `Repository Rules` → `Reusable Skill/Procedure` → `Task Context`.
- **Why it may work:** Pattern Codex environment policy cho thấy permission enforcement có hiệu quả hơn khi layer thấp chỉ thu hẹp quyền. Cùng tư duy này áp dụng cho instructions giúp giảm conflict.
- **Suitable use cases:** Cursor Rules, Claude Code instructions, Codex `AGENTS.md`, QA agent procedures, code-review skills.
- **Limitations:** Prompt hierarchy không thay thế runtime enforcement; model vẫn có thể misinterpret text.
- **Risks:** Quá nhiều layer gây context overhead nếu load tất cả cùng lúc.
- **Recommendation:** Rules chỉ chứa invariant; Skills chứa step-by-step procedure; task prompt chứa objective/input/output; runtime guardrails nằm ngoài model.

### B. Dùng **capability-aware context**, không hard-code model/tool assumptions

- **Problem:** Context limits, tool availability và behavior có thể khác theo provider route, auth mode hoặc tool version.
- **Proposed improvement:** Mỗi run inject compact capability snapshot: `model`, `inputLimit`, `outputLimit`, `tools`, `network`, `writeAccess`, `version`, `providerRoute`.
- **Why it may work:** OpenCode vừa phải sửa metadata GPT-5.6 cho ChatGPT subscription path, cho thấy “same model family” chưa đủ để suy ra effective capabilities. [OpenCode #39082](https://github.com/anomalyco/opencode/commit/4d68d30b48a99379b2baaf597dbad576707ea36d)
- **Suitable use cases:** Long-context research, multi-model QA, agent benchmark harnesses.
- **Limitations:** Capability registry cũng có thể stale.
- **Risks:** Nếu registry là single source of truth nhưng không probe runtime, metadata sai sẽ thành systematic failure.
- **Recommendation:** Registry + runtime probes + timestamp/source attribution.

### C. Context handoff nên truyền **state artifact**, không truyền toàn transcript

Một handoff tốt có thể dùng schema:

```yaml
objective: ...
confirmed_facts: []
assumptions: []
open_questions: []
decisions: []
completed_steps: []
remaining_steps: []
evidence: []
risks: []
next_action: ...
```

- **Why:** giảm context noise, dễ fork verifier/reviewer agent, dễ resume sau crash.
- **Suitable:** research agents, interview intelligence, code review, architecture planning.
- **Risk:** summary artifact có thể bỏ mất nuance; cần link evidence/raw artifacts thay vì chỉ paraphrase.

## 4. Agent, Workflow, and Loop Engineering

### A. Dùng stop condition để phát hiện low-value research loops

- **Problem:** Agent có thể search 10 nguồn gần giống nhau sau khi đã đủ evidence.
- **Technique:** Sau mỗi search round, classify result thành `NEW_MATERIAL_EVIDENCE`, `CONFIRMATION_ONLY`, `DUPLICATE`, `NO_SIGNAL`. Stop khi 2 round liên tiếp không có `NEW_MATERIAL_EVIDENCE`.
- **Expected benefit:** Giảm latency/cost, tăng signal-to-noise.
- **Failure risk:** Stop quá sớm nếu source set quá hẹp.
- **Suitable use cases:** Daily briefing, job radar, GitHub opportunity radar, research agents.

### B. Approval cache phải phụ thuộc policy revision

- **Problem:** User approve command dưới policy A; policy đổi thành stricter B nhưng approval cache cũ vẫn được reuse.
- **Technique:** Cache key = `ActionSignature + EnvironmentId + PolicyFingerprint + ToolVersion`.
- **Expected benefit:** Approval không vượt qua policy change.
- **Failure risk:** Cache churn làm tăng approval prompts nếu fingerprint không stable.
- **Suitable use cases:** shell execution, database writes, deployment, PR merge, Teams/Slack outbound actions.

### C. Retry strategy phải dựa trên failure signature, không chỉ retry count

- **Problem:** `test → fail → fix → same fail → fix → same fail` dễ thành loop.
- **Technique:** Normalize failure signature; nếu cùng signature lặp lại 2 lần thì **re-plan/root-cause**, không tiếp tục patch cùng giả thuyết.
- **Expected benefit:** Giảm blind retries và hallucinated fixes.
- **Failure risk:** Signature normalization quá thô có thể coi hai failures khác nhau là một.
- **Suitable:** Selenium/Playwright, CI debugging, API integration, flaky tests, migration jobs.

### D. Verifier agent nên độc lập với executor

- **Problem:** Agent tạo solution có xu hướng “confirm” solution của chính nó.
- **Technique:** Executor output chỉ artifact + claimed evidence; verifier nhận acceptance criteria + artifact + raw evidence, không nhận chain-of-thought/justification của executor.
- **Expected benefit:** Giảm confirmation bias và tăng reproducibility.
- **Failure risk:** Hai agents dùng cùng model/prompt family vẫn có correlated errors.
- **Suitable:** code review, QA evidence, architecture review, research fact-checking.

## 5. Hooks and Integrations

### 1. .NET agent runtime → sanitized subprocess execution

- **Integrate:** `ProcessStartInfo`, test runner, Git CLI, dotnet CLI, PowerShell.
- **Workflow benefit:** Cho phép agent build/test/debug trong controlled environment.
- **Security concerns:** Không inherit tokens, connection strings, Azure credentials, GitHub tokens hoặc MCP control-plane secrets theo mặc định.
- **Difficulty:** **Moderate**.
- **Recommended design:** explicit env allowlist + working-directory scope + timeout + stdout/stderr capture + command policy check trước spawn.

### 2. MCP / Teams / Slack → policy-aware outbound actions

- **Integrate:** MCP server cho repo/docs/data; Teams/Slack bot hoặc workflow connector.
- **Workflow benefit:** Research/QA agent có thể đọc context và post status/evidence.
- **Security concerns:** read và write permissions phải tách riêng; channel-scoped authorization; outbound post nên require approval khi chứa external/customer data.
- **Difficulty:** **Advanced**.
- **Recommendation:** tool schema nên encode `readOnly`, `sideEffect`, `requiresApproval`, `dataClassification`.

### 3. GitHub Actions → regression harness cho agent behaviors

- **Integrate:** prompt/skill fixtures, deterministic validators, model/provider matrix, result artifacts.
- **Workflow benefit:** Detect prompt/tool/model regressions khi thay rule, model hoặc provider route.
- **Security concerns:** Không expose production secrets cho untrusted PR workflows; separate eval credentials.
- **Difficulty:** **Moderate**.
- **Recommendation:** CI nên fail theo deterministic constraints trước, LLM-as-a-judge chỉ là secondary signal.

### 4. Provider gateway → native protocol adapters

- **Integrate:** OpenAI Responses API, Anthropic Messages API, compatible endpoints, Cloudflare/own proxy.
- **Workflow benefit:** Unified routing/telemetry nhưng giữ native capabilities.
- **Security concerns:** BYOK token routing, upstream authorization, audit logs.
- **Difficulty:** **Advanced**.
- **Recommendation:** Không forward gateway/control-plane token tới upstream provider ngoài intended route.

## 7. Opportunities and Trends to Watch

### 1. **Runtime policy semantics thay prompt-only safety** — Status: **Growing**

- **What is changing:** Agent tooling đang formalize permissions, environment restrictions và managed configuration ở runtime.
- **Why it matters:** Prompt rules không đủ để enforce security-critical behavior.
- **Opportunity:** Reusable policy engine cho coding/QA agents, đặc biệt .NET worker + browser + shell + DB tools.
- **Risk:** False sense of security nếu policy chỉ cover command layer nhưng không cover MCP/network/filesystem.

### 2. **Persistent project/workspace state tách khỏi chat thread** — Status: **Growing**

- **What is changing:** Project-level state và thread/run lifecycle ngày càng explicit.
- **Why it matters:** Long-running/multi-agent work cần resume/fork/audit.
- **Opportunity:** Agent orchestration framework với Project/Run/Artifact model, hữu ích cho QA/research/interview systems.
