## 1. Executive Summary

### 1. Cost nên trở thành first-class agent telemetry, không chỉ là billing hậu kiểm
- **One-sentence summary:** Codex app-server có thể emit `codex.turn_cost` qua OTLP cho OpenAI API-key sessions sau completed hoặc aborted turns, kèm estimated USD cost, interruption state, model, speed và reasoning effort. [Codex #39006, 17/08/2026](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)
- **Affected skill area:** Agent evaluation, observability, model comparison, cost/latency optimization.
- **Why it matters:** Một agent loop không thể được đánh giá đầy đủ chỉ bằng pass/fail; production fitness cần cả quality, latency và cost.
- **Practical implication:** Mỗi run nên log `outcome + latency + estimated cost + model + reasoning effort + retry/interruption` để phát hiện regression và low-value loops.
- **Priority:** **Critical**.
- **Confirmed facts:** Turn-cost worker chỉ chạy khi OTLP exporter bật và provider là OpenAI; theo dõi turn lifecycle, response count, completed/aborted state; query turn-cost endpoint; emit estimated USD cost; preserve organization/project headers; bounded polling/retry; re-probe sau auth changes. [Source](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)
- **Analysis:** Đây là nền tảng để đánh giá `success-per-dollar`, `quality-per-dollar`, `retry-cost`, `verification-cost` và `cost of low-value loops`.
- **Recommendation:** Với QA/research/code-review/interview agents, thêm telemetry fields `runId, stepId, model, reasoningEffort, latencyMs, estimatedCostUsd, retryCount, verifierCostUsd, outcome`.
- **Uncertainty:** Turn-cost endpoint trong commit không được xác nhận là public contract; chỉ nên lấy pattern observability, không phụ thuộc endpoint cụ thể.

### 2. Async verifier cần explicit committed-progress signal
- **One-sentence summary:** Codex sửa Guardian tests để đợi `latest_scored_tool_call` advance thay vì chỉ chờ `SecurityRiskScore` xuất hiện, vì score có thể visible trước khi progress state hoàn tất. [Codex #39007, 17/08/2026](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)
- **Affected skill area:** Async verification, deterministic testing, concurrency, multi-agent handoff.
- **Why it matters:** “Output đã tồn tại” không đồng nghĩa “state machine đã hoàn tất”; consumer đọc quá sớm dễ tạo flaky behavior.
- **Practical implication:** Workflow nên có state `Started → OutputProduced → StateCommitted → ReadyForConsumption`.
- **Priority:** **Critical**.
- **Confirmed facts:** Guardian stores `SecurityRiskScore` trước khi advance `latest_scored_tool_call`; test cũ chờ score có thể chạy approval assertion quá sớm; test mới chờ progress counter. [Source](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)
- **Analysis:** Pattern này áp dụng cho background jobs, browser screenshots, CI artifacts, MCP tasks và multi-agent handoff.
- **Recommendation:** Tests/consumers phải await completion/version markers thay vì polling file/row/message existence.
- **Uncertainty:** Đây là implementation evidence từ Guardian, không phải API guarantee tổng quát của Codex.

### 3. Managed reviewer policy phải thắng local feature preference
- **One-sentence summary:** Codex force-disable Guardian v2 nếu managed `allowed_approvals_reviewers` không cho phép reviewer `user`, kể cả khi local config bật `guardianv2 = true`. [Codex #39005, 17/08/2026](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576)
- **Affected skill area:** Permission boundaries, human approval, enterprise config, reviewer architecture.
- **Why it matters:** Local preference không được phép re-enable một approval path mà organization policy đã loại bỏ.
- **Practical implication:** Agent platforms nên tách `desiredConfig` và `effectiveConfig`, với policy/requirements là authoritative constraints.
- **Priority:** **Critical**.
- **Confirmed facts:** Disable áp dụng cho local requirements và cloud config bundles; `config/read` phản ánh effective `false`; Guardian v2 vẫn có thể bật khi `user` reviewer còn allowed. [Source](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576)
- **Analysis:** Đây là concrete evidence cho monotonic policy model, không phải “last config wins”.
- **Recommendation:** Mọi feature liên quan approval/security nên resolve theo `FeatureDesired ∩ OrgPolicy ∩ EnvironmentPolicy ∩ HumanApproval`.
- **Uncertainty:** Không nên suy rộng rằng mọi Codex feature đã dùng cùng precedence model.

### 4. Async verdict cần freshness bound riêng với confidence
- **One-sentence summary:** Guardian v2 bỏ qua approval review nếu risk score chậm hơn latest tool activity quá `max_tool_call_lag`, mặc định 3 tool calls. [Codex #39001, 17/08/2026](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1)
- **Affected skill area:** Async reviewers, agent state synchronization, approval systems.
- **Why it matters:** Một score có thể rất confident nhưng đã stale với current action.
- **Practical implication:** Reviewer output nên bind với `subjectVersion`/`toolCallIndex`, evidence hash và reviewer version.
- **Priority:** **Critical**.
- **Confirmed facts:** Codex track `latest_tool_call` và `latest_scored_tool_call`; nếu lag vượt config thì approval review trả `None`; default `3`; tests cover boundary và recovery. [Source](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1)
- **Analysis:** `confidence`, `freshness`, `evidence completeness` là ba dimensions độc lập của verifier correctness.
- **Recommendation:** Chuẩn hóa `ReviewVerdict { subjectVersion, evidenceHash, decision, score, createdAt, reviewerVersion }`.
- **Uncertainty:** Default `3` không có bằng chứng tối ưu cho workload khác.

### 5. Retry phải bounded trên toàn logical operation

- **Affected skill area:** Failure recovery, long-running agents, verifier reliability.
- **Why it matters:** Retry từng phase độc lập dễ phình total attempts hoặc tạo low-value loops.
- **Practical implication:** Mỗi logical step cần `RetryBudget`, error classifier, idempotency check và stop condition.
- **Priority:** **High**.
- **Confirmed facts:** Retry categories gồm timeout/connection/network, retryable/stream errors, overload, HTTP 5xx và `429`; tests cover `503` recovery và stop khi budget exhausted. [Source](https://github.com/openai/codex/commit/4885eb6c52c4d9915698671395aaa327072afca9)

- **Recommendation:** Sau retry budget hết, chuyển `ReplanRequired`; log cost/latency per attempt.
- **Uncertainty:** `2` retries chỉ là Guardian implementation choice.

## 3. Prompt, Skills, Rules, and Context Engineering

### A. Treat skill selection as retrieval, not prompt concatenation
- **Problem:** Large skill catalogs consume context and reduce routing precision.
- **Proposed improvement:** Store compact routing metadata for every skill; rank candidates from current query, recent-use history and structured routing/dependency signals; only load full skill instructions after selection.
- **Why it may work:** Codex now exposes both a bounded catalog budget and shadow hybrid selectors. [Budget](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d) · [Routing](https://github.com/openai/codex/commit/ea10ae7d0fe6a2fb0614a32adb5e095853319355)
- **Suitable use cases:** Cursor rules/skills, Codex skills, Claude Code reusable procedures, QA/research/interview/code-review agent catalogs.
- **Limitations:** Recent-use signal can bias toward stale skills; metadata quality can dominate router quality.
- **Risks:** Hiding too much skill detail can reduce recall; injecting too much defeats the budget.
- **Recommendation:** Evaluate `top-1`, `top-k recall`, wrong-skill rate, downstream success, latency and token cost.
- **Uncertainty:** No evidence yet that Codex shadow variants outperform baseline in production.

### B. Separate desired configuration from effective configuration
- **Problem:** Developers often inspect a local config file and assume that is runtime behavior.
- **Proposed improvement:** Persist both `desiredConfig` and policy-resolved `effectiveConfig`; expose reasons for every override.
- **Why it may work:** Guardian v2 can be locally enabled yet effectively forced off by managed reviewer policy, and `config/read` reports that effective value. [Codex #39005](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576)
- **Suitable use cases:** Enterprise agent runners, MCP permissions, deployment agents, Teams/Slack integrations, repository bots.
- **Limitations:** More config provenance increases implementation complexity.
- **Risks:** Without good diagnostics, users may perceive “feature randomly disabled”.
- **Recommendation:** Emit `source`, `desired`, `effective`, `overrideReason`, `policyVersion`.
- **Uncertainty:** Not every tool currently exposes policy provenance this explicitly.

### C. Context/evidence objects should carry version and hash
- **Problem:** A verifier may reason correctly over stale evidence.
- **Proposed improvement:** Every evidence bundle carries `subjectVersion`, `capturedAt`, `hash`, `source`, `redacted` and artifact reference.
- **Why it may work:** Guardian freshness logic proves version distance matters independently of score confidence. [Codex #39001](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1)
- **Suitable use cases:** Browser QA screenshots, code-review diffs, research evidence, architecture decision reviews.
- **Limitations:** Requires consistent versioning across executor and verifier.
- **Risks:** Poor version semantics can produce false stale/fresh decisions.
- **Recommendation:** Prefer monotonic action index/run version over wall-clock timestamp alone.

## 4. Agent, Workflow, and Loop Engineering

### A. Cost-aware `Plan → Execute → Verify → Decide`
- **Problem:** A loop can succeed but be economically inefficient.
- **Technique:** Record cost and latency per phase and per retry; include verifier cost separately.
- **Expected benefit:** Detects expensive plans, excessive verification and low-value retries.
- **Failure risks:** Estimated cost can lag or be missing; avoid making hard production decisions from incomplete telemetry.
- **Suitable use cases:** Research agents, code-review agents, browser QA, architecture agents, CI/CD fix loops.
- **Confirmed evidence:** Codex turn-cost worker tracks completed/aborted turns and emits estimated cost telemetry. [Codex #39006](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)

### B. Explicit async completion barriers
- **Problem:** Producer output becomes visible before all related state is committed.
- **Technique:** Add a completion/version barrier; consumer waits for `ReadyForConsumption` or a monotonically advanced counter.
- **Expected benefit:** Fewer flaky tests and fewer races between executor/reviewer.
- **Failure risks:** Incorrect barrier placement can deadlock or hide partial progress.
- **Suitable use cases:** QA screenshots + metadata, CI test result + summary, research evidence + citation index, multi-agent handoff.
- **Confirmed evidence:** Guardian approval test now waits for scored progress counter rather than score presence. [Codex #39007](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)

### C. Bounded retry with re-plan exit
- **Problem:** Infinite or repeated same-signature retries waste time and money.
- **Technique:** Shared retry budget across a logical step; transient classifier; retry only if idempotent/safe; after budget exhaustion switch to `ReplanRequired`.
- **Expected benefit:** Predictable latency/cost and clearer failure analysis.
- **Failure risks:** Too-small budget reduces recovery; too-large budget hides systemic failure.
- **Suitable use cases:** MCP calls, browser automation, API gateways, model/verifier sampling, CI interactions.
- **Confirmed evidence:** Guardian retries bounded transient failures across full sampling flow. [Codex #38997](https://github.com/openai/codex/commit/4885eb6c52c4d9915698671395aaa327072afca9)

### D. Reviewer verdict = content quality + freshness + policy eligibility
- **Problem:** A correct but stale verdict, or a valid verdict from a disallowed reviewer, is still unusable.
- **Technique:** Before consuming verdict: check `policyAllowed`, `subjectVersion`, `evidenceHash`, `reviewerVersion`, then confidence/decision.
- **Expected benefit:** Safer async approvals and cleaner separation between scoring and authority.
- **Failure risks:** Overly strict freshness rules can reduce throughput.
- **Suitable use cases:** destructive commands, deployments, database migrations, high-risk code changes.
- **Evidence:** [Freshness #39001](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1) · [Policy #39005](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576)

## 7. Opportunities and Trends to Watch

### 1. **Cost-aware agent evaluation** — Status: **Growing**
- **What is changing:** Cost is moving into per-turn telemetry rather than remaining a monthly billing aggregate.
- **Why it matters:** Enables model/workflow comparison on quality, latency and dollars simultaneously.
- **Opportunity:** Build cost-regression dashboards and automatic alerts for retry/verification waste.
- **Risk:** Estimated cost may be incomplete or delayed; do not over-optimize at the expense of correctness.
- **Evidence:** [Codex #39006](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)

### 2. **Verifier freshness as a first-class contract** — Status: **Early signal → Growing**
- **What is changing:** Async security/review systems are tracking how far verdict state lags behind executor state.
- **Why it matters:** Confidence alone cannot guarantee current validity.
- **Opportunity:** Standardize versioned evidence and verdict contracts across agent types.
- **Risk:** Poor lag thresholds may reduce throughput or over-reject valid work.
- **Evidence:** [Codex #39001](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1)

### 3. **Policy-resolved effective configuration** — Status: **Growing**
- **What is changing:** Managed constraints increasingly determine effective capabilities regardless of local feature preference.
- **Why it matters:** Enterprise agent adoption requires predictable policy precedence.
- **Opportunity:** Build explainable config provenance and policy diagnostics into internal agent platforms.
- **Risk:** Hidden overrides without observability create operational confusion.
- **Evidence:** [Codex #39005](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576)

### 4. **Skills becoming retrieval systems** — Status: **Growing**
- **What is changing:** Catalog budgets, candidate ranking, recent-use memory and shadow evaluation are becoming separate mechanisms.
- **Why it matters:** Large reusable skill sets cannot scale as one monolithic developer prompt.
- **Opportunity:** Build vendor-neutral skill routers usable by Cursor, Claude Code, Codex and custom .NET agents.
- **Risk:** Sophisticated routing without evaluation can become hidden complexity.
- **Evidence:** [Budget #38978](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d) · [Routing #38993](https://github.com/openai/codex/commit/ea10ae7d0fe6a2fb0614a32adb5e095853319355)

### 5. **Provider-native semantics behind gateways** — Status: **Growing**
- **What is changing:** OpenCode routes OpenAI/Anthropic through native passthroughs rather than flattening everything into one compatibility API. [OpenCode commit](https://github.com/anomalyco/opencode/commit/cba6b5f2f74080239cdc7405efcb83219c980136)
- **Why it matters:** New provider features often do not map cleanly through generic compatibility layers.
- **Opportunity:** Architect a normalized internal interface with provider-native adapters, not protocol flattening.
- **Risk:** More adapters and test matrix complexity.
