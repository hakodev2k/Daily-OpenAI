## 1. Executive Summary

### 1. Cost cần trở thành first-class telemetry của agent run
- **One-sentence summary:** Codex app-server có thể emit `codex.turn_cost` qua OTLP cho OpenAI API-key sessions sau completed hoặc aborted turns, kèm estimated USD cost, interruption state, model, speed và reasoning effort. [Codex #39006, 17/08/2026](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)
- **Affected skill area:** Agent evaluation, observability, model comparison, cost/latency optimization.
- **Why it matters:** Hai workflows cùng đạt task success nhưng chênh 2–3× cost hoặc latency không có cùng production fitness.
- **Practical implication:** Mỗi run nên log `outcome + latency + cost + model + reasoning effort + retry/interruption` để phát hiện regression và low-value loops.
- **Priority:** **Critical**.
- **Confirmed facts:** Turn-cost worker chỉ chạy khi OTLP exporter bật và provider là OpenAI; theo dõi turn lifecycle, response count, completed/aborted state; query turn-cost endpoint; emit estimated USD cost; preserve organization/project headers; bounded polling/retry; re-probe sau auth changes. [Source](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)
- **Analysis:** Cost observability nên là một eval dimension, không phải billing hậu kiểm. Có thể đo `success-per-dollar`, `verification-cost`, `retry-cost` và `cost of low-value loops`.
- **Recommendation:** Với QA/research/code-review/interview agents, thêm telemetry fields `runId, stepId, model, reasoningEffort, latencyMs, estimatedCostUsd, retryCount, verifierCostUsd, outcome`.
- **Uncertainty:** Turn-cost endpoint trong commit không được xác nhận là public contract; chỉ nên lấy pattern observability.

### 2. Async verifier cần explicit committed-progress signal
- **One-sentence summary:** Codex sửa Guardian approval tests để đợi `latest_scored_tool_call` advance thay vì chỉ chờ `SecurityRiskScore` xuất hiện, vì score có thể visible trước khi progress state hoàn tất. [Codex #39007, 17/08/2026](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)
- **Affected skill area:** Async verification, deterministic testing, concurrency, multi-agent handoff.
- **Why it matters:** “Output đã tồn tại” không đồng nghĩa “state machine đã hoàn tất”. Consumer đọc quá sớm có thể tạo flaky behavior và false confidence.
- **Practical implication:** Workflow nên phân biệt `Started → OutputProduced → StateCommitted → ReadyForConsumption`.
- **Priority:** **Critical**.
- **Confirmed facts:** Guardian stores `SecurityRiskScore` trước khi advance `latest_scored_tool_call`; test cũ chờ score có thể assert approval quá sớm; test mới chờ progress counter. [Source](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)
- **Analysis:** Pattern này áp dụng cho background jobs, browser screenshots, CI artifacts, MCP tasks và multi-agent handoff.
- **Recommendation:** Tests/consumers phải await explicit completion/version markers thay vì polling file/row/message existence.
- **Uncertainty:** Đây là implementation evidence từ Guardian, không phải API guarantee tổng quát của Codex.

## 3. Prompt, Skills, Rules, and Context Engineering

### A. Problem: skill catalogs consume context even when routing quality is poor
- **Confirmed facts:** Codex exposes `[skills].max_context_tokens`; unset default is 2% of model context and configured value is capped at 10,000 tokens. [Codex #38978](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d)
- **Proposed improvement:** Split skill architecture into:
  1. compact discovery metadata;
  2. candidate router;
  3. lazy full-skill load;
  4. recent-use memory;
  5. post-run routing telemetry.
- **Why it may work:** It minimizes context consumed before the system has evidence that a skill is relevant.
- **Suitable use cases:** Cursor rules/skills, Codex skills, Claude Code sub-workflows, interview agents, QA agents with dozens of reusable procedures.
- **Limitations:** Aggressive budgets can reduce recall; weak metadata makes routing brittle.
- **Risk:** Teams may “solve” routing failures by inflating token budgets, hiding the real retrieval problem.
- **Recommendation:** Benchmark at multiple catalog budgets and report `top-k skill recall`, task success, tokens, latency and cost.

### B. Problem: short follow-up turns are hard to route lexically
- **Confirmed facts:** Codex shadows selectors that fuse recently invoked skills, character routing metadata and optionally lexical matches via RRF. [Codex #38993](https://github.com/openai/codex/commit/ea10ae7d0fe6a2fb0614a32adb5e095853319355)
- **Proposed improvement:** Keep a small `RecentSkillHistory` and fuse it with current-query retrieval rather than injecting full conversation history.
- **Why it may work:** “Continue”, “retry”, “same approach” are semantically underspecified but recent procedural context is strong evidence.
- **Suitable use cases:** Multi-turn coding sessions, QA reruns, code-review follow-ups, interview simulation, research refinement.
- **Limitations:** Recency can become a false prior after task/topic switches.
- **Risk:** LRU-only routing can repeatedly select a stale skill.
- **Recommendation:** Add test cases for abrupt topic switches and stale recent skills; compare lexical-only vs recent-only vs fused routing in shadow mode.

### C. Problem: rules and preferences are often mixed with hard policy
- **Confirmed facts:** Managed reviewer requirements can force Guardian v2 off; environment exec policy can only tighten active command policy. [Codex #39005](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576) · [Codex #38942](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)
- **Proposed improvement:** Separate:
  - `Preferences`: style, workflow defaults, preferred tools;
  - `Capabilities`: what is technically enabled;
  - `Requirements`: mandatory behavior;
  - `Policies`: non-bypassable security/approval limits.
- **Why it may work:** It removes ambiguity when repository rules, local config, enterprise settings and human approvals conflict.
- **Suitable use cases:** Cursor `.mdc`/rules, Codex config, CI/CD agents, enterprise MCP servers.
- **Limitations:** More layers increase debugging complexity unless provenance is visible.
- **Risk:** Hidden precedence creates surprising effective behavior.
- **Recommendation:** Always expose `desiredConfig`, `effectiveConfig`, source layer and override reason in diagnostics.

### D. Problem: verifier context can differ materially from executor context
- **Confirmed facts:** Guardian can include recent images from messages/tool outputs with strict count/byte bounds; model catalog can supply reviewer defaults. [Codex #38987](https://github.com/openai/codex/commit/37cf6c84c086229ed78d69e726b965c0252e9b3e) · [Codex #38990](https://github.com/openai/codex/commit/8bf50439f2ebbcd98785c858e22174f919451cf7)
- **Proposed improvement:** Define an `EvidenceEnvelope` with source, captured time, content hash, redaction state, version and artifact reference.
- **Why it may work:** Verifier decisions become reproducible and can be checked for missing/stale evidence.
- **Suitable use cases:** Browser QA screenshots, UI regressions, architecture review diagrams, generated test reports.
- **Limitations:** Evidence storage has privacy, cost and retention implications.
- **Risk:** More evidence does not guarantee better judgment; it can increase distraction and token cost.
- **Recommendation:** Use bounded, task-specific evidence selection and run text-only vs multimodal evaluation before defaulting to images.

## 4. Agent, Workflow, and Loop Engineering

### A. Freshness-aware verifier loop
- **Problem:** Asynchronous reviewer finishes after executor has already advanced.
- **Technique:** Bind verdict to `subjectVersion` and reject it when `currentVersion - subjectVersion > allowedLag`.
- **Expected benefit:** Prevents valid-but-stale decisions from governing a newer action.
- **Failure risks:** An overly strict lag can make approvals unavailable under load; overly loose lag accepts outdated evidence.
- **Suitable use cases:** QA verifier, security reviewer, code-review agent, deployment approver.
- **Confirmed facts:** Guardian now implements `max_tool_call_lag` with default three tool calls. [Codex #39001](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1)
- **Recommendation:** Determine lag from measured execution/review latency, not by copying `3` blindly.

### B. Completion-aware async state machine
- **Problem:** An artifact exists before all related state has committed.
- **Technique:** Require explicit completion marker/version advancement before downstream consumption.
- **Expected benefit:** Fewer flaky tests, false-ready states and race-condition bugs.
- **Failure risks:** Busy-wait polling or poor signaling can increase latency.
- **Suitable use cases:** Playwright screenshots/videos, async database writes, background analysis, multi-agent handoff.
- **Confirmed facts:** Codex Guardian test had to wait for `latest_scored_tool_call`, not merely `SecurityRiskScore`. [Codex #39007](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)
- **Recommendation:** Prefer event/task completion, sequence numbers or durable checkpoint status over repeated existence checks.

### C. Bounded retry + re-plan
- **Problem:** `test → fail → retry` loops can burn time/tokens without changing strategy.
- **Technique:** Shared retry budget per logical operation, retryable error taxonomy, idempotency guard, then transition to `ReplanRequired`.
- **Expected benefit:** Stops low-value loops while retaining resilience to transient faults.
- **Failure risks:** Misclassification may stop recoverable work or retry non-idempotent actions.
- **Suitable use cases:** MCP calls, browser actions, API calls, CI jobs, verifier sampling.
- **Confirmed facts:** Guardian retries transient transport/stream/server/rate-limit failures across the full sampling flow with a bounded budget. [Codex #38997](https://github.com/openai/codex/commit/4885eb6c52c4d9915698671395aaa327072afca9)
- **Recommendation:** After two same-signature failures, capture RCA evidence and re-plan rather than simply retrying again.

### D. Cost-aware evaluation loop
- **Problem:** An agent improves task success by using more model calls/retries/verifiers, but operating cost grows silently.
- **Technique:** Add cost to evaluation alongside correctness and latency.
- **Expected benefit:** Enables comparison by `success-per-dollar`, `verified-success-per-dollar`, and marginal value of each verifier/retry.
- **Failure risks:** Optimizing cost too aggressively can reduce quality or safety.
- **Suitable use cases:** Research agents, code review, interview generation, large QA suites.
- **Confirmed facts:** Codex app-server now emits turn-cost telemetry for API-key sessions when OTLP telemetry export is enabled. [Codex #39006](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)
- **Recommendation:** Evaluate quality first, then optimize cost under a minimum quality/safety threshold.

### E. Policy-aware execution loop
- **Problem:** Local agent config or previous approval unintentionally preserves authority after policy changes.
- **Technique:** Compute effective permissions at execution time and include policy fingerprint/version in approval cache keys.
- **Expected benefit:** Prevents stale approvals and local config from widening authority.
- **Failure risks:** Poor UX if policy changes are not explained clearly.
- **Suitable use cases:** Shell tools, database migrations, Git operations, deployment agents.
- **Confirmed facts:** Codex environment policy only restricts; policy fingerprint participates in saved approval cache behavior. [Codex #38942](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)
- **Recommendation:** Surface “approval invalidated because policy changed” explicitly in run logs.

## 7. Opportunities and Trends to Watch

### 1. Agent observability is moving from tokens/latency to **cost + outcome + reasoning configuration**
- **What is changing:** Turn-level cost is joining traditional telemetry.
- **Why it matters:** Production agent evaluation needs economics, not just accuracy.
- **Opportunity:** Build reusable .NET/OpenTelemetry dashboards for `verified success`, `cost/run`, `cost/failure`, `retry cost`, `verifier cost`.
- **Risk:** Cost optimization can accidentally trade away quality or safety.
- **Status:** **Growing**.
- **Evidence:** Codex #39006. [Source](https://github.com/openai/codex/commit/04caa22c8220c24b1428dbeaebcb744bf3875771)

### 2. Async reviewer systems are becoming **versioned and freshness-aware**
- **What is changing:** Review outputs increasingly need state/version contracts, not just scores.
- **Why it matters:** Executors can move faster than reviewers; stale decisions are a correctness problem.
- **Opportunity:** Generic `VersionedVerdict<T>` / `EvidenceEnvelope` libraries for internal agent platforms.
- **Risk:** Poor lag settings create false unavailability or stale approvals.
- **Status:** **Early signal**.
- **Evidence:** Codex #39001 and #39007. [Freshness](https://github.com/openai/codex/commit/8e89e98cf6d4d79f7add5c04ddd4bbd76b1594a1) · [Progress synchronization](https://github.com/openai/codex/commit/def7ed55725052ac4119c759ff8b5952a5f955ee)

### 3. Skill systems are becoming retrieval systems, not static prompt collections
- **What is changing:** Token budgets, ranking fusion, recent-use signals and shadow evaluation are appearing together.
- **Why it matters:** Large skill libraries need search/eval discipline similar to RAG.
- **Opportunity:** Build skill-router benchmark harnesses and reusable metadata schemas.
- **Risk:** Over-engineered routing can cost more than it saves for small catalogs.
- **Status:** **Growing**.
- **Evidence:** Codex #38978 and #38993. [Budget](https://github.com/openai/codex/commit/632e35ce8d5dec43b75dbf99f9e6fa52bed47c3d) · [Routing](https://github.com/openai/codex/commit/ea10ae7d0fe6a2fb0614a32adb5e095853319355)

### 4. Enterprise agent control is converging on **effective config + monotonic policy**
- **What is changing:** Managed reviewer policy, restrictive environment policy and effective config reporting are becoming explicit.
- **Why it matters:** Enterprise adoption depends on proving local instructions cannot widen authority.
- **Opportunity:** Policy provenance UI, effective-config diff, permission simulators, approval-cache invalidation tests.
- **Risk:** Too many opaque policy layers reduce developer trust and debuggability.
- **Status:** **Growing**.
- **Evidence:** Codex #39005 and #38942. [Reviewer policy](https://github.com/openai/codex/commit/02e9bfaac7577a3ab77a40de6b0c3cc37b934576) · [Exec policy](https://github.com/openai/codex/commit/e38290846c11424567c9c8226f2be8a2886c5929)

### 5. Multi-provider gateways are preserving provider-native agent semantics
- **What is changing:** OpenCode routes OpenAI and Anthropic through native passthroughs rather than flattening everything into a generic compatibility API. [OpenCode #42634, 17/08/2026](https://github.com/anomalyco/opencode/commit/cba6b5f2f74080239cdc7405efcb83219c980136)
- **Why it matters:** Agent features often depend on provider-specific request/response semantics.
- **Opportunity:** Design internal model adapters around a common orchestration interface while retaining provider-native transports.
- **Risk:** More adapters and test matrices; abstraction leakage remains.
- **Status:** **Growing**.
