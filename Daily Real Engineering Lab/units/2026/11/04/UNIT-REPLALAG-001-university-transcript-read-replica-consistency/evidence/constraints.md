# Evidence & constraints (synthetic incident)
- Write path: payment webhook confirms settlement, primary transaction commits `receipt.status=PAID` and `transcript.revision=12` atomically. HTTP 200 to payment caller means primary commit succeeded.
- Current download path: API reads a read-only replica selected by connection pool; returns 404 when PAID not visible, otherwise returns whichever transcript revision is visible.
- Contract: for the same student after a confirmed payment, download must return **at least the committed revision**, or a clearly labeled retriable response; silently serving an older revision is forbidden.
- Load: 3,000 read RPS, 35 payment confirmations/s peak; only 4% of reads occur within 60s of a payment confirmation.
- Primary budget: up to 350 read RPS headroom before write latency risks; replica handles routine reads.
- SLO: 99.9% successful confirmed-payment downloads within 2s when primary is healthy; during primary outage, explicitly degrade rather than falsely claim freshness.
- Observed replica apply delay: median 180ms, p95 2.4s, p99 11s, maximum in sample 28s. No synchronous replica or managed cloud feature is available in the current budget.
- Privacy: a student's transcript may be read only by that authenticated student; cache keys must include authorization scope.
- Delivery: 2 engineers, 2 weeks, reversible rollout; do not require a wholesale database migration.
- Timeline values are controlled synthetic evidence; timings do not imply the exact delay distribution for production.
