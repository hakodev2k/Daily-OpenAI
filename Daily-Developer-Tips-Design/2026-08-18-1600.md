# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` xuyên suốt request pipeline

**Mẹo:**
Truyền `CancellationToken` từ ASP.NET Core controller xuống service, database call và external API.

**Tại sao hữu ích:**
Giúp hủy các tác vụ không còn cần thiết khi client disconnect hoặc timeout, giảm lãng phí tài nguyên.

**Ví dụ:**
```csharp
public async Task<Order?> GetAsync(Guid id, CancellationToken cancellationToken)
{
    return await db.Orders.FirstOrDefaultAsync(x => x.Id == id, cancellationToken);
}
```

**Lưu ý:**
Không nên bỏ qua cancellation trong các tác vụ quan trọng cần hoàn thành như payment processing.

### Tip 2 — Sử dụng SQL execution plan khi tối ưu query

**Mẹo:**
Kiểm tra `Actual Execution Plan` thay vì chỉ nhìn thời gian chạy query.

**Tại sao hữu ích:**
Giúp phát hiện index scan, missing index, expensive operator và vấn đề query design.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index theo mọi suggestion của database nếu chưa đánh giá write cost.

### Tip 3 — Dùng `record` cho immutable DTO trong C#

**Mẹo:**
Sử dụng `record` khi tạo request/response model cần value equality và immutable design.

**Tại sao hữu ích:**
Giảm boilerplate code, tránh thay đổi object ngoài ý muốn và code rõ ràng hơn.

**Ví dụ:**
```csharp
public record CreateUserRequest(string Email, string Name);
```

**Lưu ý:**
Không nên dùng `record` cho Entity Framework Core entity cần tracking mutation.

### Tip 4 — Kiểm tra memory leak bằng `dotnet-counters`

**Mẹo:**
Sử dụng runtime diagnostics tools trước khi kết luận ứng dụng bị thiếu memory.

**Tại sao hữu ích:**
Có thể quan sát GC heap size, allocation rate và exception trong production.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Metrics runtime chỉ là dấu hiệu ban đầu, cần kết hợp với dump analysis khi điều tra sâu.

### Tip 5 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Áp dụng binary search trong Git history để xác định commit làm phát sinh bug.

**Tại sao hữu ích:**
Tiết kiệm thời gian khi bug xuất hiện sau nhiều thay đổi.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0.0
```

**Lưu ý:**
Cần có cách kiểm tra pass/fail rõ ràng để bisect hiệu quả.

## 🧠 Software Design

### Design 1 — Transaction Boundary Design

**Khái niệm:**
Xác định chính xác phạm vi dữ liệu và business operation cần được xử lý trong cùng một transaction.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn gây lock lâu hoặc transaction quá nhỏ làm dữ liệu không nhất quán.

**Ví dụ thực tế:**
Trong order system, tạo Order và cập nhật Inventory có thể cần consistency cao, nhưng gửi email xác nhận nên tách thành background process.

**Trade-off:**
Transaction lớn đơn giản về consistency nhưng giảm scalability. Transaction nhỏ tăng throughput nhưng cần xử lý eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết transaction không chỉ là database command. Senior developer cần thiết kế boundary dựa trên business consistency requirement.

### Design 2 — Modular Monolith thay vì Microservices mặc định

**Khái niệm:**
Tách hệ thống thành các module độc lập trong cùng một application deployment.

**Vấn đề nó giải quyết:**
Giúp tạo boundary rõ ràng mà không chịu toàn bộ complexity của distributed system.

**Ví dụ thực tế:**
Một hệ thống ERP có thể tách Inventory, Billing, Customer thành module riêng với database access riêng trước khi cân nhắc tách service.

**Trade-off:**
Đơn giản vận hành hơn microservices nhưng vẫn có giới hạn về scaling độc lập.

**Middle → Senior insight:**
Middle developer cần hiểu module boundary. Senior developer cần quyết định khi nào complexity của microservices thực sự tạo ra giá trị.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Thiết kế API sao cho cùng một request được gửi nhiều lần vẫn tạo ra một kết quả an toàn.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate action trong retry, timeout hoặc network failure.

**Ví dụ thực tế:**
Payment API sử dụng `Idempotency-Key` để đảm bảo client retry không tạo thêm giao dịch.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và quản lý lifecycle của idempotency key.

**Middle → Senior insight:**
Middle developer cần biết retry có thể gây duplicate. Senior developer cần thiết kế API behavior trong môi trường distributed system.
