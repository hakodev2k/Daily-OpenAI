# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` xuyên suốt các tác vụ async để request bị hủy có thể dừng xử lý không cần thiết.

**Tại sao hữu ích:**
Giảm resource waste khi client disconnect hoặc timeout.

**Ví dụ:**
```csharp
public async Task<IActionResult> GetData(CancellationToken cancellationToken)
{
    var data = await service.LoadAsync(cancellationToken);
    return Ok(data);
}
```

**Lưu ý:**
Không bỏ qua token trong các operation dài như database query hoặc HTTP call.

### Tip 2 — Dùng SQL execution plan để tìm bottleneck thật sự

**Mẹo:**
Kiểm tra execution plan trước khi tối ưu query thay vì chỉ đoán dựa trên câu SQL.

**Tại sao hữu ích:**
Giúp phát hiện missing index, table scan và query cost cao.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
```

**Lưu ý:**
Index nhiều không luôn tốt vì có thể làm chậm insert/update.

### Tip 3 — Dùng `ProblemDetails` chuẩn hóa lỗi REST API

**Mẹo:**
Sử dụng `ProblemDetails` thay vì tự tạo nhiều format error response khác nhau.

**Tại sao hữu ích:**
Client dễ xử lý lỗi và API có contract rõ ràng hơn.

**Ví dụ:**
```csharp
builder.Services.AddProblemDetails();
```

**Lưu ý:**
Không trả stack trace hoặc thông tin nhạy cảm trong production response.

### Tip 4 — Dùng Docker multi-stage build để giảm image size

**Mẹo:**
Tách build environment và runtime environment thành các stage khác nhau.

**Tại sao hữu ích:**
Giảm image size, tăng tốc deployment và giảm attack surface.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
```

**Lưu ý:**
Không copy toàn bộ source code vào runtime image nếu không cần thiết.

### Tip 5 — Dùng `Assert` có mục đích trong unit test

**Mẹo:**
Mỗi test nên kiểm tra behavior quan trọng thay vì kiểm tra quá nhiều chi tiết implementation.

**Tại sao hữu ích:**
Test bền vững hơn khi code được refactor.

**Ví dụ:**
```csharp
Assert.Equal(expectedTotal, result.Total);
```

**Lưu ý:**
Tránh viết test phụ thuộc vào thứ tự hoặc internal state không phải business requirement.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction Boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một operation.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn gây lock lâu hoặc transaction quá nhỏ làm dữ liệu không nhất quán.

**Ví dụ thực tế:**
Trong hệ thống đặt hàng, tạo Order và trừ Inventory có thể cần cân nhắc giữa cùng transaction hoặc xử lý qua event.

**Trade-off:**
Transaction lớn tăng consistency nhưng giảm scalability. Transaction nhỏ tăng khả năng scale nhưng cần xử lý failure phức tạp hơn.

**Middle → Senior insight:**
Middle cần biết transaction không chỉ là database concern. Senior cần xác định boundary dựa trên business invariant.

### Design 2 — Modular Monolith trước Microservices

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng một deployment.

**Vấn đề nó giải quyết:**
Giảm complexity của microservices khi domain chưa đủ lớn nhưng vẫn cần boundary rõ ràng.

**Ví dụ thực tế:**
Một hệ thống ERP có module Sales, HR, Finance với database access và business rule riêng.

**Trade-off:**
Đơn giản vận hành hơn microservices nhưng cần kỷ luật để tránh module phụ thuộc lẫn nhau.

**Middle → Senior insight:**
Senior không chọn microservices vì xu hướng. Quyết định dựa trên team structure, scale requirement và domain complexity.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo một request gửi nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Giảm lỗi duplicate operation trong distributed system.

**Ví dụ thực tế:**
API thanh toán dùng `Idempotency-Key` để tránh charge khách hàng nhiều lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle cần hiểu retry có thể tạo side effect. Senior cần thiết kế API chịu được network failure và duplicate message.
