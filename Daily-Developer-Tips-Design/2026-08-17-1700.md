# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` xuyên suốt từ Controller đến service, database query và HTTP call.

**Tại sao hữu ích:**
Giúp hủy các tác vụ không còn cần thiết khi client disconnect hoặc request timeout, tránh lãng phí tài nguyên.

**Ví dụ:**
```csharp
public async Task<IActionResult> GetData(CancellationToken cancellationToken)
{
    var result = await service.GetAsync(cancellationToken);
    return Ok(result);
}
```

**Lưu ý:**
Không nên bỏ qua token trong các operation dài như database query, file processing hoặc external API call.

### Tip 2 — Sử dụng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Dùng binary search của Git để xác định commit nào làm phát sinh bug.

**Tại sao hữu ích:**
Tiết kiệm thời gian debug khi lỗi xuất hiện sau nhiều tuần phát triển.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.2.0
```

Sau mỗi lần test:
```bash
git bisect good
# hoặc
 git bisect bad
```

**Lưu ý:**
Cần có cách kiểm tra pass/fail rõ ràng, nếu không kết quả sẽ không đáng tin cậy.

### Tip 3 — Dùng SQL Execution Plan trước khi tối ưu query

**Mẹo:**
Kiểm tra Execution Plan thay vì đoán index hoặc rewrite SQL ngay lập tức.

**Tại sao hữu ích:**
Giúp phát hiện Table Scan, Missing Index, Key Lookup hoặc vấn đề về cardinality.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT *
FROM Orders
WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi query; quá nhiều index làm chậm INSERT/UPDATE.

### Tip 4 — Dùng Structured Logging thay vì nối chuỗi log

**Mẹo:**
Sử dụng message template với placeholder trong `ILogger`.

**Tại sao hữu ích:**
Log có cấu trúc dễ tìm kiếm trong Application Insights, ELK, Seq hoặc Grafana Loki.

**Ví dụ:**
```csharp
_logger.LogInformation("Processing order {OrderId} for user {UserId}", orderId, userId);
```

**Lưu ý:**
Tránh ghi dữ liệu nhạy cảm như password, token hoặc personal information vào log.

### Tip 5 — Dùng Docker multi-stage build để giảm kích thước image

**Mẹo:**
Tách bước build và runtime trong Dockerfile.

**Tại sao hữu ích:**
Image nhỏ hơn, deploy nhanh hơn và giảm attack surface.

**Ví dụ:**
```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:8.0
COPY --from=build /app .
ENTRYPOINT ["dotnet", "App.dll"]
```

**Lưu ý:**
Không copy toàn bộ source code hoặc build tools vào production image.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction Boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một transaction.

**Vấn đề nó giải quyết:**
Ngăn trạng thái hệ thống bị dở dang khi một business operation thất bại giữa chừng.

**Ví dụ thực tế:**
Trong hệ thống thanh toán, tạo Invoice và cập nhật Payment Status có thể cần cùng một transaction nếu business yêu cầu consistency tuyệt đối.

**Trade-off:**
Transaction lớn tăng consistency nhưng giảm scalability và dễ gây locking. Transaction nhỏ tăng throughput nhưng cần xử lý eventual consistency.

**Middle → Senior insight:**
Middle developer cần biết cách sử dụng transaction. Senior developer cần quyết định đúng boundary dựa trên business invariant thay vì dựa trên table.

### Design 2 — Modular Monolith trước Microservices

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng một deployment unit.

**Vấn đề nó giải quyết:**
Giảm complexity của microservices nhưng vẫn tạo boundary rõ ràng.

**Ví dụ thực tế:**
Một hệ thống ERP có thể tách Employee, Payroll, Timesheet thành các module riêng với database boundary và domain logic riêng.

**Trade-off:**
Ưu điểm là dễ deploy, debug và vận hành. Nhược điểm là cần kỷ luật để tránh module gọi trực tiếp vào nhau.

**Middle → Senior insight:**
Middle developer nên hiểu module boundary. Senior developer cần đánh giá khi nào hệ thống thực sự cần distributed architecture.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo một request gửi nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Xử lý retry trong distributed system mà không tạo duplicate data.

**Ví dụ thực tế:**
API tạo payment sử dụng `Idempotency-Key` để tránh việc user bị charge hai lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle developer cần biết implement idempotent endpoint. Senior developer cần xem xét retry strategy, consistency model và failure scenarios.
