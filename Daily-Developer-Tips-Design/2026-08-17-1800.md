# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` xuyên suốt async workflow

**Mẹo:**
Truyền `CancellationToken` từ API endpoint xuống service, database call và background operation thay vì bỏ qua.

**Tại sao hữu ích:**
Giúp giải phóng tài nguyên khi client hủy request, tránh xử lý vô ích và cải thiện khả năng chịu tải.

**Ví dụ:**
```csharp
public async Task<IActionResult> Get(CancellationToken cancellationToken)
{
    var result = await service.ProcessAsync(cancellationToken);
    return Ok(result);
}
```

**Lưu ý:**
Không nên dùng cancellation cho các transaction bắt buộc hoàn tất như payment settlement nếu hệ thống cần đảm bảo trạng thái cuối cùng.

### Tip 2 — Sử dụng SQL execution plan trước khi tối ưu query

**Mẹo:**
Kiểm tra `Actual Execution Plan` thay vì chỉ nhìn thời gian chạy query.

**Tại sao hữu ích:**
Giúp phát hiện vấn đề như missing index, table scan, key lookup hoặc join không hiệu quả.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi cột được filter vì có thể làm chậm `INSERT`, `UPDATE` và tăng storage.

### Tip 3 — Dùng Structured Logging thay vì string interpolation

**Mẹo:**
Sử dụng placeholder trong `ILogger` để giữ dữ liệu có cấu trúc.

**Tại sao hữu ích:**
Log dễ tìm kiếm, filter và phân tích trong hệ thống observability.

**Ví dụ:**
```csharp
_logger.LogInformation("Order {OrderId} created for {UserId}", order.Id, user.Id);
```

**Lưu ý:**
Không ghi log dữ liệu nhạy cảm như password, token hoặc thông tin cá nhân không cần thiết.

### Tip 4 — Tách Git commit theo mục đích thay đổi

**Mẹo:**
Mỗi commit nên đại diện cho một thay đổi logic rõ ràng.

**Tại sao hữu ích:**
Dễ review, rollback, cherry-pick và tìm nguyên nhân lỗi bằng `git bisect`.

**Ví dụ:**
Thay vì một commit chứa API change + refactor + formatting, tách thành các commit riêng.

**Lưu ý:**
Không nên chia commit quá nhỏ đến mức khó hiểu lịch sử thay đổi.

### Tip 5 — Dùng `dotnet-counters` để kiểm tra runtime health

**Mẹo:**
Sử dụng công cụ runtime diagnostics của .NET để quan sát ứng dụng đang chạy.

**Tại sao hữu ích:**
Giúp phát hiện CPU spike, GC pressure, thread pool starvation mà không cần debug trực tiếp.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Metrics runtime chỉ cho biết dấu hiệu; cần kết hợp logs, traces và profiling để tìm root cause.

## 🧠 Software Design

### Design 1 — Transaction Boundary Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau để đảm bảo consistency.

**Vấn đề nó giải quyết:**
Tránh trạng thái dữ liệu dở dang khi một workflow gồm nhiều bước thất bại giữa chừng.

**Ví dụ thực tế:**
Trong hệ thống đặt hàng, việc tạo Order và cập nhật Inventory có thể cần transaction hoặc cơ chế saga tùy kiến trúc.

**Trade-off:**
Transaction lớn tăng consistency nhưng giảm concurrency và dễ gây lock contention.
Transaction nhỏ tăng hiệu năng nhưng cần xử lý compensation.

**Middle → Senior insight:**
Middle developer cần biết đặt transaction đúng chỗ. Senior developer cần quyết định khi nào dùng database transaction, distributed transaction hay eventual consistency.

### Design 2 — Modular Monolith thay vì Microservices mặc định

**Khái niệm:**
Modular Monolith chia hệ thống thành các module có boundary rõ ràng nhưng vẫn deploy cùng một application.

**Vấn đề nó giải quyết:**
Giảm complexity vận hành của microservices khi domain chưa đủ lớn.

**Ví dụ thực tế:**
Một hệ thống quản lý doanh nghiệp có thể tách module Identity, Billing, Reporting với API nội bộ rõ ràng trước khi tách service riêng.

**Trade-off:**
Modular Monolith đơn giản vận hành nhưng cần kỷ luật dependency. Microservices tăng scalability nhưng thêm network, deployment và monitoring complexity.

**Middle → Senior insight:**
Senior không chọn microservices vì xu hướng; quyết định dựa trên team structure, domain boundary, scaling requirement và operational cost.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo cùng một request được gửi nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Xử lý retry, network failure và duplicate request trong distributed system.

**Ví dụ thực tế:**
Payment API sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần khi client retry.

**Trade-off:**
Có thêm storage và logic kiểm tra request history nhưng đổi lại hệ thống resilient hơn.

**Middle → Senior insight:**
Middle developer cần biết implement idempotent endpoint. Senior developer cần thiết kế strategy cho retry, message processing và consistency giữa nhiều service.
