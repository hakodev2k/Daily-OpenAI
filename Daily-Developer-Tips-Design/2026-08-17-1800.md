# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable<T>` cho xử lý dữ liệu streaming

**Mẹo:**
Sử dụng `IAsyncEnumerable<T>` khi cần xử lý tập dữ liệu lớn theo từng phần thay vì load toàn bộ vào memory.

**Tại sao hữu ích:**
Giảm memory usage, cải thiện response time và phù hợp với export lớn, data processing hoặc API streaming.

**Ví dụ:**
```csharp
public async IAsyncEnumerable<Order> GetOrdersAsync()
{
    await foreach (var order in repository.StreamAsync())
    {
        yield return order;
    }
}
```

**Lưu ý:**
Không nên dùng streaming nếu consumer luôn cần toàn bộ dữ liệu để xử lý transaction hoặc aggregate.

### Tip 2 — Kiểm tra `HttpClient` usage để tránh socket exhaustion

**Mẹo:**
Dùng `IHttpClientFactory` thay vì tạo mới `HttpClient` liên tục trong code.

**Tại sao hữu ích:**
Giúp quản lý connection lifetime, DNS refresh và tránh lỗi production do cạn socket.

**Ví dụ:**
```csharp
builder.Services.AddHttpClient<PaymentClient>();
```

**Lưu ý:**
Không nên tạo quá nhiều named client với cấu hình khác nhau nếu không có nhu cầu rõ ràng.

### Tip 3 — Dùng `BenchmarkDotNet` trước khi tối ưu code

**Mẹo:**
Đo lường performance bằng benchmark thay vì dựa trên cảm giác.

**Tại sao hữu ích:**
Giúp xác định optimization thực sự có cải thiện hay chỉ làm code phức tạp hơn.

**Ví dụ:**
```csharp
[Benchmark]
public void ParseData()
{
    Parser.Parse(input);
}
```

**Lưu ý:**
Benchmark micro không luôn phản ánh production nếu bỏ qua database, network hoặc concurrency.

### Tip 4 — Sử dụng `git reflog` để cứu thay đổi bị mất

**Mẹo:**
Dùng `git reflog` khi branch bị reset, rebase sai hoặc commit bị mất khỏi history thông thường.

**Tại sao hữu ích:**
Git vẫn lưu reference history trong một khoảng thời gian, giúp khôi phục trạng thái trước đó.

**Ví dụ:**
```bash
git reflog
git checkout -b recovery HEAD@{3}
```

**Lưu ý:**
`reflog` không thay thế backup; dữ liệu quá cũ có thể bị garbage collection xóa.

### Tip 5 — Thêm correlation ID cho distributed troubleshooting

**Mẹo:**
Gắn một request identifier xuyên suốt API gateway, service, logs và background jobs.

**Tại sao hữu ích:**
Giúp trace một request qua nhiều component khi debug production.

**Ví dụ:**
```csharp
app.Use(async (context, next) =>
{
    context.TraceIdentifier = Guid.NewGuid().ToString();
    await next();
});
```

**Lưu ý:**
Correlation ID cần được propagate đúng cách, không nên dùng nó để chứa dữ liệu nghiệp vụ nhạy cảm.

## 🧠 Software Design

### Design 1 — Outbox Pattern trong Event-Driven Architecture

**Khái niệm:**
Outbox Pattern lưu database change và event message trong cùng một transaction trước khi publish ra message broker.

**Vấn đề nó giải quyết:**
Tránh tình trạng database commit thành công nhưng event publish thất bại hoặc ngược lại.

**Ví dụ thực tế:**
Khi tạo Order, hệ thống lưu Order và OrderCreatedEvent vào outbox table. Background worker đọc bảng này và gửi message tới RabbitMQ.

**Trade-off:**
Tăng reliability nhưng thêm bảng, worker và cơ chế retry. Event processing cần xử lý duplicate.

**Middle → Senior insight:**
Middle developer cần hiểu cách implement event publishing an toàn. Senior developer cần thiết kế delivery guarantee, retry strategy và monitoring cho event pipeline.

### Design 2 — Composition Over Inheritance

**Khái niệm:**
Ưu tiên kết hợp nhiều component nhỏ thay vì tạo hierarchy kế thừa sâu.

**Vấn đề nó giải quyết:**
Giảm coupling và tránh base class trở thành điểm phụ thuộc khó thay đổi.

**Ví dụ thực tế:**
Thay vì `PremiumCustomerService : CustomerService : BaseService`, tạo các component như `IPricingRule`, `INotificationSender`, `IDiscountCalculator` rồi compose behavior.

**Trade-off:**
Composition linh hoạt hơn nhưng có thể tạo nhiều abstraction nhỏ cần quản lý.
Inheritance đôi khi vẫn phù hợp với quan hệ "is-a" ổn định.

**Middle → Senior insight:**
Middle developer cần nhận biết inheritance abuse. Senior developer cần cân bằng giữa extensibility, readability và complexity của abstraction.

### Design 3 — Database as Integration Boundary

**Khái niệm:**
Xác định rõ database ownership và cách các module/service truy cập dữ liệu.

**Vấn đề nó giải quyết:**
Ngăn chặn coupling khi nhiều phần hệ thống cùng phụ thuộc trực tiếp vào schema chung.

**Ví dụ thực tế:**
Trong hệ thống lớn, Billing module không nên query trực tiếp bảng Customer của Identity module mà giao tiếp qua API hoặc event.

**Trade-off:**
Boundary rõ ràng tăng maintainability nhưng có thể tạo thêm API call hoặc data duplication.

**Middle → Senior insight:**
Middle developer cần tránh shared database tùy tiện. Senior developer cần thiết kế ownership, consistency model và data access strategy phù hợp với domain.
