# Daily Developer Tips & Design — 2026-08-17

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` xuyên suốt async flow để dừng tác vụ khi request bị hủy.

**Tại sao hữu ích:**
Tránh tiếp tục xử lý tốn tài nguyên khi client đã disconnect.

**Ví dụ:**
```csharp
public async Task<IActionResult> Get(CancellationToken cancellationToken)
{
    var data = await service.LoadAsync(cancellationToken);
    return Ok(data);
}
```

**Lưu ý:**
Không bỏ qua token trong các tác vụ dài như database query hoặc external API call.

### Tip 2 — Sử dụng SQL execution plan trước khi tối ưu query

**Mẹo:**
Kiểm tra execution plan để biết SQL Server đang scan, seek hay thiếu index.

**Tại sao hữu ích:**
Giúp tối ưu dựa trên dữ liệu thực thay vì đoán.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi cột vì có thể làm chậm write operation.

### Tip 3 — Dùng structured logging thay vì nối chuỗi log

**Mẹo:**
Sử dụng message template để giữ dữ liệu log có cấu trúc.

**Tại sao hữu ích:**
Dễ tìm kiếm trên Application Insights, ELK hoặc Grafana Loki.

**Ví dụ:**
```csharp
logger.LogInformation("Order {OrderId} created by {UserId}", order.Id, user.Id);
```

**Lưu ý:**
Không log password, token hoặc dữ liệu nhạy cảm.

### Tip 4 — Kiểm tra thay đổi trước khi merge bằng `git diff`

**Mẹo:**
Luôn review diff trước commit hoặc pull request.

**Tại sao hữu ích:**
Phát hiện file thay đổi ngoài ý muốn và giảm bug do merge.

**Ví dụ:**
```bash
git diff --staged
```

**Lưu ý:**
Diff không thay thế code review từ người khác.

### Tip 5 — Dùng `IOptionsSnapshot` cho configuration thay đổi runtime

**Mẹo:**
Sử dụng `IOptionsSnapshot<T>` khi cần reload configuration theo request scope.

**Tại sao hữu ích:**
Giúp thay đổi settings mà không cần restart application trong một số scenario.

**Ví dụ:**
```csharp
public class Service
{
    public Service(IOptionsSnapshot<AppSettings> options)
    {
    }
}
```

**Lưu ý:**
Không dùng cho singleton service vì lifetime không phù hợp.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một transaction.

**Vấn đề nó giải quyết:**
Tránh transaction quá lớn hoặc trạng thái dữ liệu không nhất quán.

**Ví dụ thực tế:**
Khi tạo Order, việc tạo Order và cập nhật Inventory có thể cần được thiết kế lại thay vì gom tất cả vào một transaction dài.

**Trade-off:**
Transaction nhỏ tăng scalability nhưng có thể yêu cầu event hoặc compensation logic.

**Middle → Senior insight:**
Middle cần hiểu transaction trong database. Senior cần quyết định consistency level phù hợp với business flow.

### Design 2 — Modular Monolith thay vì Microservices sớm

**Khái niệm:**
Chia hệ thống thành các module độc lập trong cùng một application deployment.

**Vấn đề nó giải quyết:**
Giữ boundary rõ ràng nhưng tránh complexity của distributed system.

**Ví dụ thực tế:**
Hệ thống ERP có module Employee, Payroll, Notification với database boundary rõ ràng.

**Trade-off:**
Đơn giản vận hành hơn nhưng scale từng module riêng lẻ khó hơn microservices.

**Middle → Senior insight:**
Middle cần biết tách module. Senior cần đánh giá khi nào business complexity đủ lớn để tách service.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Một request có thể thực hiện nhiều lần nhưng kết quả cuối cùng vẫn giống nhau.

**Vấn đề nó giải quyết:**
Xử lý retry an toàn trong distributed system.

**Ví dụ thực tế:**
Payment API dùng `Idempotency-Key` để tránh charge khách hàng hai lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và quản lý lifecycle của key.

**Middle → Senior insight:**
Middle cần biết implement idempotent endpoint. Senior cần thiết kế retry, timeout và failure recovery strategy.
