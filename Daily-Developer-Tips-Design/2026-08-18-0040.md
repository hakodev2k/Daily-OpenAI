# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `AsNoTracking` cho EF Core query chỉ đọc

**Mẹo:**
Sử dụng `AsNoTracking()` khi lấy dữ liệu chỉ để hiển thị hoặc export.

**Tại sao hữu ích:**
Giảm memory usage và tăng performance vì EF Core không cần theo dõi entity changes.

**Ví dụ:**
```csharp
var users = await dbContext.Users
    .AsNoTracking()
    .ToListAsync();
```

**Lưu ý:**
Không dùng khi cần update entity sau khi query vì EF Core không track object.

### Tip 2 — Dùng `ProblemDetails` chuẩn hóa lỗi API

**Mẹo:**
Trả lỗi API theo chuẩn RFC 7807 thay vì tự tạo nhiều format khác nhau.

**Tại sao hữu ích:**
Client dễ xử lý lỗi, logging và monitoring nhất quán hơn.

**Ví dụ:**
```csharp
return Problem(
    detail: "Order not found",
    statusCode: StatusCodes.Status404NotFound);
```

**Lưu ý:**
Không đưa stack trace hoặc thông tin nội bộ database ra response production.

### Tip 3 — Dùng `dotnet-counters` để kiểm tra vấn đề runtime

**Mẹo:**
Sử dụng `dotnet-counters` khi cần nhanh chóng xem CPU, GC, exception và thread pool.

**Tại sao hữu ích:**
Hỗ trợ điều tra production issue mà không cần attach debugger.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Đây là công cụ chẩn đoán nhanh, không thay thế observability đầy đủ.

### Tip 4 — Viết Git commit nhỏ theo mục đích thay đổi

**Mẹo:**
Mỗi commit nên tập trung vào một thay đổi logic rõ ràng.

**Tại sao hữu ích:**
Dễ review, rollback và tìm nguyên nhân lỗi bằng Git history.

**Ví dụ:**
```bash
git commit -m "Fix duplicate payment processing"
```

**Lưu ý:**
Không chia nhỏ commit một cách máy móc nếu làm mất tính toàn vẹn của một feature.

### Tip 5 — Dùng timeout cho external dependency

**Mẹo:**
Luôn cấu hình timeout khi gọi HTTP API, database hoặc message broker.

**Tại sao hữu ích:**
Tránh request treo vô hạn làm cạn kiệt resource của hệ thống.

**Ví dụ:**
```csharp
httpClient.Timeout = TimeSpan.FromSeconds(10);
```

**Lưu ý:**
Timeout cần phù hợp với business operation; quá thấp có thể gây false failure.

## 🧠 Software Design

### Design 1 — Separation of Concerns trong Application Layer

**Khái niệm:**
Tách các trách nhiệm khác nhau như business logic, persistence, transport và infrastructure thành các phần riêng biệt.

**Vấn đề nó giải quyết:**
Giảm coupling và giúp thay đổi một phần hệ thống mà không ảnh hưởng toàn bộ codebase.

**Ví dụ thực tế:**
Controller chỉ nhận request và gọi application service; không trực tiếp chứa logic tính giá hoặc truy cập database phức tạp.

**Trade-off:**
Tăng khả năng maintain nhưng có thể tạo thêm nhiều class nếu áp dụng quá mức.

**Middle → Senior insight:**
Middle developer cần biết phân chia trách nhiệm. Senior developer cần xác định boundary hợp lý thay vì tạo abstraction không cần thiết.

### Design 2 — Cache-Aside Pattern trong hệ thống có read nhiều

**Khái niệm:**
Application chủ động đọc cache trước, nếu không có dữ liệu thì đọc database rồi cập nhật cache.

**Vấn đề nó giải quyết:**
Giảm tải database và cải thiện latency cho dữ liệu truy cập thường xuyên.

**Ví dụ thực tế:**
Product catalog sử dụng Redis để lưu thông tin sản phẩm phổ biến trước khi fallback về PostgreSQL.

**Trade-off:**
Tăng performance nhưng phải xử lý cache invalidation và stale data.

**Middle → Senior insight:**
Middle cần hiểu cách implement cache. Senior cần quyết định dữ liệu nào nên cache, TTL bao nhiêu và consistency chấp nhận được.

### Design 3 — Outbox Pattern cho Event-Driven System

**Khái niệm:**
Lưu database change và event message trong cùng một transaction trước khi publish ra message broker.

**Vấn đề nó giải quyết:**
Tránh tình trạng database commit thành công nhưng message publish thất bại.

**Ví dụ thực tế:**
Khi tạo Order, hệ thống lưu Order và OrderCreatedEvent vào Outbox table, background worker sau đó gửi event tới RabbitMQ.

**Trade-off:**
Tăng reliability nhưng thêm complexity trong việc retry, cleanup và monitoring.

**Middle → Senior insight:**
Middle cần hiểu failure scenario trong distributed system. Senior cần thiết kế workflow chịu được partial failure và eventual consistency.
