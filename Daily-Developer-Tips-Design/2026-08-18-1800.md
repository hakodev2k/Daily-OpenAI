# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `CancellationToken` đúng cách trong ASP.NET Core

**Mẹo:**
Truyền `CancellationToken` xuyên suốt các async operation để hủy request khi client disconnect hoặc timeout.

**Tại sao hữu ích:**
Tránh xử lý vô ích, giảm tải database và external service khi request không còn cần kết quả.

**Ví dụ:**
```csharp
public async Task<Order?> GetOrderAsync(Guid id, CancellationToken cancellationToken)
{
    return await db.Orders
        .FirstOrDefaultAsync(x => x.Id == id, cancellationToken);
}
```

**Lưu ý:**
Không nên bỏ qua token trong các operation có thời gian chạy dài.

### Tip 2 — Kiểm tra execution plan trước khi tối ưu SQL

**Mẹo:**
Dùng `Execution Plan` thay vì đoán index hoặc viết lại query ngay lập tức.

**Tại sao hữu ích:**
Biết chính xác database đang scan table, thiếu index hay join không hiệu quả.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Orders
WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi column vì có thể làm chậm insert/update.

### Tip 3 — Dùng `Health Checks` để kiểm tra dependency

**Mẹo:**
Expose health endpoint cho database, Redis, message broker hoặc external service quan trọng.

**Tại sao hữu ích:**
Giúp Kubernetes, monitoring tool và team vận hành biết hệ thống đang gặp vấn đề ở đâu.

**Ví dụ:**
```csharp
builder.Services.AddHealthChecks()
    .AddSqlServer(connectionString);
```

**Lưu ý:**
Không đưa thông tin nhạy cảm của dependency vào health response public.

### Tip 4 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Sử dụng binary search của Git khi biết lỗi xuất hiện giữa hai commit nhưng không biết nguyên nhân.

**Tại sao hữu ích:**
Giảm thời gian tìm bug regression trong repository lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.0.0
```

**Lưu ý:**
Cần có test hoặc cách xác định rõ commit nào bị lỗi.

### Tip 5 — Dùng Structured Logging thay vì nối chuỗi log

**Mẹo:**
Ghi log bằng template parameters để giữ dữ liệu có cấu trúc.

**Tại sao hữu ích:**
Log dễ search, filter và phân tích trong Application Insights, Elasticsearch hoặc Grafana Loki.

**Ví dụ:**
```csharp
logger.LogInformation(
    "Created order {OrderId} for customer {CustomerId}",
    order.Id,
    customer.Id);
```

**Lưu ý:**
Không ghi dữ liệu nhạy cảm như password, token hoặc personal data.

## 🧠 Software Design

### Design 1 — Idempotency trong Distributed System

**Khái niệm:**
Idempotency đảm bảo một operation có thể được gọi nhiều lần nhưng kết quả cuối cùng vẫn giống như chỉ xử lý một lần.

**Vấn đề nó giải quyết:**
Xử lý retry, network failure và duplicate request trong hệ thống phân tán.

**Ví dụ thực tế:**
API thanh toán nhận `Idempotency-Key` để tránh việc khách hàng bị trừ tiền hai lần khi client retry.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và thiết kế storage phù hợp.

**Middle → Senior insight:**
Middle developer cần biết retry có thể tạo duplicate action. Senior developer cần xác định operation nào bắt buộc idempotent.

### Design 2 — Transaction Boundary trong Application Design

**Khái niệm:**
Transaction boundary xác định phạm vi các thay đổi dữ liệu phải thành công hoặc thất bại cùng nhau.

**Vấn đề nó giải quyết:**
Tránh trạng thái dữ liệu không nhất quán khi một business operation gồm nhiều bước.

**Ví dụ thực tế:**
Tạo đơn hàng gồm lưu Order, OrderItem và cập nhật Inventory cần có transaction phù hợp.

**Trade-off:**
Transaction lớn tăng consistency nhưng có thể giảm concurrency và performance.

**Middle → Senior insight:**
Middle cần hiểu cách dùng transaction. Senior cần quyết định boundary dựa trên business invariant thay vì chỉ dựa trên database operation.

### Design 3 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia hệ thống thành các module có boundary rõ ràng nhưng vẫn deploy như một ứng dụng.

**Vấn đề nó giải quyết:**
Giúp quản lý complexity mà không phải trả toàn bộ chi phí vận hành của microservices.

**Ví dụ thực tế:**
Hệ thống e-commerce có module Catalog, Order, Payment tách biệt về code, database access và domain logic nhưng deploy chung.

**Trade-off:**
Đơn giản vận hành hơn microservices nhưng cần discipline để giữ module không phụ thuộc lẫn nhau.

**Middle → Senior insight:**
Middle cần hiểu cách tách module. Senior cần biết khi nào domain đủ lớn để tách thành service độc lập.
