# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `required` modifier trong C# để bảo vệ object state

**Mẹo:**
Sử dụng `required` property khi tạo các DTO hoặc domain object cần dữ liệu bắt buộc.

**Tại sao hữu ích:**
Giảm lỗi runtime do object được tạo nhưng thiếu field quan trọng.

**Ví dụ:**
```csharp
public class CreateOrderRequest
{
    public required string CustomerId { get; init; }
    public required List<OrderItem> Items { get; init; }
}
```

**Lưu ý:**
Không thay thế validation business rule; `required` chỉ kiểm tra lúc compile/object initialization.

### Tip 2 — Sử dụng SQL execution plan trước khi tối ưu query

**Mẹo:**
Kiểm tra `Execution Plan` thay vì chỉ nhìn thời gian chạy query.

**Tại sao hữu ích:**
Giúp phát hiện `Table Scan`, index thiếu hoặc join không hiệu quả.

**Ví dụ:**
```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;
SELECT * FROM Orders WHERE CustomerId = 100;
```

**Lưu ý:**
Không tạo index cho mọi column; quá nhiều index làm chậm write operation.

### Tip 3 — Dùng structured logging thay vì nối chuỗi log

**Mẹo:**
Truyền parameter vào logger thay vì build string thủ công.

**Tại sao hữu ích:**
Log dễ search trong Application Insights, Seq hoặc Elasticsearch.

**Ví dụ:**
```csharp
_logger.LogInformation("Order {OrderId} created for {CustomerId}", order.Id, order.CustomerId);
```

**Lưu ý:**
Không log sensitive data như token, password hoặc personal information.

### Tip 4 — Dùng `git bisect` để tìm commit gây lỗi

**Mẹo:**
Khi biết code từng chạy tốt nhưng hiện tại bị lỗi, dùng binary search trong Git history.

**Tại sao hữu ích:**
Giảm thời gian tìm regression trong repository lớn.

**Ví dụ:**
```bash
git bisect start
git bisect bad
git bisect good v1.2.0
```

**Lưu ý:**
Cần có test hoặc cách kiểm tra rõ ràng để xác định commit tốt/xấu.

### Tip 5 — Sử dụng cancellation token trong background processing

**Mẹo:**
Luôn propagate `CancellationToken` trong API call, database call và background job.

**Tại sao hữu ích:**
Tránh task chạy vô ích khi request bị huỷ hoặc service shutdown.

**Ví dụ:**
```csharp
await dbContext.SaveChangesAsync(cancellationToken);
```

**Lưu ý:**
Không bỏ qua cancellation trong các tác vụ dài như batch processing.

## 🧠 Software Design

### Design 1 — Transaction Boundary trong Domain Design

**Khái niệm:**
Transaction boundary xác định phạm vi dữ liệu phải thay đổi cùng nhau trong một atomic operation.

**Vấn đề nó giải quyết:**
Giúp tránh transaction quá lớn gây lock database hoặc quá nhỏ gây inconsistent state.

**Ví dụ thực tế:**
Một hệ thống thanh toán cần cập nhật Payment, Order và Inventory. Không phải mọi bước đều cần nằm trong một database transaction duy nhất; có thể kết hợp transaction với message queue.

**Trade-off:**
Transaction lớn đảm bảo consistency nhưng giảm scalability. Transaction nhỏ tăng throughput nhưng cần xử lý failure.

**Middle → Senior insight:**
Middle developer cần biết transaction hoạt động thế nào. Senior developer cần thiết kế boundary phù hợp với business workflow.

### Design 2 — Modular Monolith thay vì Microservices quá sớm

**Khái niệm:**
Modular Monolith chia hệ thống thành các module độc lập trong cùng một deployment.

**Vấn đề nó giải quyết:**
Giữ được boundary rõ ràng mà không phải trả chi phí vận hành distributed system.

**Ví dụ thực tế:**
Một hệ thống ERP mới có module Customer, Billing, Inventory. Các module dùng chung database nhưng không truy cập trực tiếp internal logic của nhau.

**Trade-off:**
Đơn giản hơn microservices nhưng vẫn cần kỷ luật architecture boundary.

**Middle → Senior insight:**
Middle cần hiểu module separation. Senior cần đánh giá khi nào tách service thực sự tạo giá trị.

### Design 3 — Idempotency trong API Design

**Khái niệm:**
Idempotency đảm bảo một request gửi nhiều lần vẫn tạo ra cùng một kết quả cuối cùng.

**Vấn đề nó giải quyết:**
Xử lý retry trong network failure, timeout hoặc distributed system.

**Ví dụ thực tế:**
API tạo payment sử dụng `Idempotency-Key` để tránh charge khách hàng hai lần.

**Trade-off:**
Tăng reliability nhưng cần lưu trạng thái request và xử lý cleanup.

**Middle → Senior insight:**
Middle cần biết retry có thể gây duplicate action. Senior cần thiết kế API chịu được failure của distributed environment.
