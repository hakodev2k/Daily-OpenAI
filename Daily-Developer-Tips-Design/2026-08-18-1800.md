# Daily Developer Tips & Design — 2026-08-18

## 🛠 Developer Tips & Tricks

### Tip 1 — Dùng `IAsyncEnumerable` để xử lý dữ liệu streaming trong .NET

**Mẹo:**
Sử dụng `IAsyncEnumerable<T>` khi cần đọc và xử lý dữ liệu từng phần thay vì load toàn bộ collection vào memory.

**Tại sao hữu ích:**
Giảm memory usage và cải thiện khả năng xử lý các tập dữ liệu lớn.

**Ví dụ:**
```csharp
public async IAsyncEnumerable<Order> GetOrdersAsync()
{
    await foreach (var order in repository.StreamOrdersAsync())
    {
        yield return order;
    }
}
```

**Lưu ý:**
Không nên dùng cho dữ liệu nhỏ vì có thể làm code phức tạp hơn không cần thiết.

### Tip 2 — Dùng `Query Tagging` trong Entity Framework Core để debug SQL

**Mẹo:**
Thêm tag vào LINQ query để dễ truy vết câu SQL sinh ra từ EF Core.

**Tại sao hữu ích:**
Khi production có query chậm, log database có thể xác định chính xác nguồn gọi.

**Ví dụ:**
```csharp
var users = await db.Users
    .TagWith("Get active users for dashboard")
    .Where(x => x.IsActive)
    .ToListAsync();
```

**Lưu ý:**
Không lạm dụng tag cho mọi query nhỏ vì log database có thể bị nhiễu.

### Tip 3 — Sử dụng `dotnet-counters` để kiểm tra vấn đề runtime

**Mẹo:**
Dùng công cụ CLI của .NET để xem CPU, GC, exception và thread pool trong lúc ứng dụng đang chạy.

**Tại sao hữu ích:**
Giúp chẩn đoán nhanh memory pressure, GC issue hoặc thread starvation mà không cần attach debugger.

**Ví dụ:**
```bash
dotnet-counters monitor --process-id 1234
```

**Lưu ý:**
Đây là công cụ quan sát nhanh, không thay thế profiling chuyên sâu.

### Tip 4 — Dùng `git reflog` để khôi phục thay đổi bị mất

**Mẹo:**
Khi reset nhầm branch hoặc mất commit chưa push, kiểm tra `git reflog` trước khi tạo lại code thủ công.

**Tại sao hữu ích:**
Git vẫn lưu lịch sử di chuyển của HEAD trong một khoảng thời gian nhất định.

**Ví dụ:**
```bash
git reflog

git checkout -b recovery-branch <commit-sha>
```

**Lưu ý:**
`reflog` không phải backup vĩnh viễn; cần push hoặc tag các trạng thái quan trọng.

### Tip 5 — Áp dụng `ProblemDetails` chuẩn hóa lỗi API trong ASP.NET Core

**Mẹo:**
Sử dụng `ProblemDetails` thay vì tự tạo nhiều format error response khác nhau.

**Tại sao hữu ích:**
Client dễ xử lý lỗi, logging nhất quán và API contract rõ ràng hơn.

**Ví dụ:**
```csharp
return Results.Problem(
    title: "Validation failed",
    detail: "Email is required",
    statusCode: 400);
```

**Lưu ý:**
Không trả stack trace hoặc thông tin nội bộ trong production response.

## 🧠 Software Design

### Design 1 — Separation of Concerns trong Layered Architecture

**Khái niệm:**
Separation of Concerns là nguyên tắc chia hệ thống thành các phần có trách nhiệm rõ ràng, tránh một component xử lý quá nhiều loại logic.

**Vấn đề nó giải quyết:**
Giảm coupling giữa business logic, infrastructure, presentation và giúp thay đổi một phần không ảnh hưởng toàn hệ thống.

**Ví dụ thực tế:**
Trong ASP.NET Core, Controller chỉ xử lý HTTP concern, Application Service xử lý use case, Repository xử lý persistence.

**Trade-off:**
Boundary rõ ràng giúp maintain tốt hơn nhưng có thể tạo thêm abstraction và nhiều file hơn.

**Middle → Senior insight:**
Middle developer cần biết phân chia responsibility. Senior developer cần thiết kế boundary dựa trên khả năng thay đổi của hệ thống.

### Design 2 — Outbox Pattern cho Event-Driven Architecture

**Khái niệm:**
Outbox Pattern lưu event cùng transaction với dữ liệu business trước khi publish ra message broker.

**Vấn đề nó giải quyết:**
Tránh tình trạng database commit thành công nhưng message publish thất bại hoặc ngược lại.

**Ví dụ thực tế:**
Khi tạo Order, hệ thống lưu Order và `OrderCreatedEvent` vào outbox table trong cùng transaction, background worker sau đó publish event lên RabbitMQ.

**Trade-off:**
Tăng độ tin cậy nhưng thêm bảng, worker và cơ chế retry.

**Middle → Senior insight:**
Middle cần hiểu message có thể thất bại. Senior cần thiết kế workflow chịu được distributed failure.

### Design 3 — Cache-Aside Pattern trong hệ thống có read-heavy workload

**Khái niệm:**
Cache-Aside là mô hình application tự kiểm tra cache trước, nếu thiếu dữ liệu thì đọc database rồi cập nhật cache.

**Vấn đề nó giải quyết:**
Giảm database load và cải thiện latency cho dữ liệu đọc nhiều.

**Ví dụ thực tế:**
API lấy product detail kiểm tra Redis trước, nếu miss thì query SQL Server và lưu lại Redis với TTL.

**Trade-off:**
Tăng performance nhưng phải xử lý cache invalidation và dữ liệu stale.

**Middle → Senior insight:**
Middle cần biết cách dùng cache. Senior cần quyết định dữ liệu nào được cache, TTL bao lâu và mức consistency chấp nhận được.
